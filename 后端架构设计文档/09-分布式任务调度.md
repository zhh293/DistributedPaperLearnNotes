# 分布式任务调度

## 一、问题背景

### 1.1 从单机定时任务到分布式调度

在单体架构时代，定时任务通常通过操作系统的crontab或编程语言内置的定时器（如Java的Timer、ScheduledExecutorService）来实现。这些方案简单直接，但在分布式架构下面临诸多挑战：

**问题1：任务重复执行**。当应用部署多台实例时，每台实例都会执行相同的定时任务，导致数据重复处理。例如，一个订单超时取消任务，如果每台机器都执行，可能导致同一个订单被取消多次。

**问题2：任务无法分片**。面对海量数据处理，单台机器处理能力有限。例如需要刷新数据库中1000万条订单的状态，单节点处理耗时极长，无法利用集群的并行能力。

**问题3：任务不可观测**。定时任务散落在各应用中，缺乏统一的执行记录、失败告警和任务管理能力。任务执行失败后无法自动重试，需要人工介入。

**问题4：任务调度不灵活**。传统的crontab只支持cron表达式，不支持API触发、延迟任务、工作流编排等复杂调度场景。

### 1.2 分布式任务调度的核心需求

一个成熟的分布式任务调度系统需要满足以下核心需求：

- **调度中心化**：统一的调度中心负责任务的触发和分发，避免多节点重复执行
- **执行分布式**：任务可以在多台执行节点上并行运行，支持分片处理
- **高可用**：调度中心和执行节点都需要具备高可用能力，单点故障不影响整体
- **任务管理**：支持任务的创建、更新、删除、暂停、手动触发等生命周期管理
- **可观测性**：提供执行历史记录、实时日志、失败告警和任务报表
- **工作流编排**：支持DAG图式调度，任务间可以定义依赖关系和数据传递

### 1.3 业界方案概览

当前业界主流的分布式任务调度方案包括：

| 方案 | 特点 | 外部依赖 | 适用场景 |
| --- | --- | --- | --- |
| XXL-JOB | 轻量级，开箱即用，社区活跃 | DB | 中小规模，进程内任务 |
| Elastic-Job | 基于Zookeeper，高可用 | DB + Zookeeper | 对一致性要求高的场景 |
| PowerJob | 功能全面，支持MapReduce | DB | 大规模，复杂计算 |
| Apache Airflow | Python生态，DAG工作流 | DB + MQ | 数据工程，ETL |
| DolphinScheduler | 可视化DAG，多租户 | DB + Zookeeper | 企业级数据平台 |

各方案在触发方式、任务类型、分布式计算模型、工作流支持等方面各有侧重，需要根据业务场景进行选型。

### 2.2 调度中心设计

调度中心是整个系统的核心，负责以下职责：

**调度引擎**：根据任务的cron表达式、固定频率、固定延迟等触发策略，在正确的时间点触发任务执行。支持秒级、分钟级调度精度。

**路由策略**：当任务被触发时，决定将任务分发到哪个执行节点。常见的路由策略包括：
- 轮询路由：依次将任务分配给各执行节点
- 随机路由：随机选择一个执行节点
- 一致性哈希：根据任务标识进行一致性哈希分配
- 故障转移：优先选择健康节点，节点故障自动切换
- 分片广播：将任务分片后广播到所有节点

**分片引擎**：将一个大任务拆分为多个小任务分片，分配到不同节点并行执行。

**高可用协调器**：调度中心本身需要高可用部署，通常通过主备切换或集群选举实现。依赖Zookeeper或数据库实现协调。

### 2.3 执行节点设计

执行节点部署在业务应用中，负责接收调度中心的任务执行请求并执行业务逻辑：

```java
public class JobExecutor {

    private final ExecutorService jobThreadPool;
    private final Map<String, IJobHandler> jobHandlerMap;
    private final JobLogRepository logRepository;
    private final JobRegisterService registerService;

    public void start() {
        // 1. 注册到调度中心
        registerService.register(buildRegisterInfo());
        // 2. 启动心跳保活
        registerService.startHeartbeat();
        // 3. 启动任务执行线程池
        jobThreadPool = new ThreadPoolExecutor(
            corePoolSize, maxPoolSize, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(1000),
            new ThreadFactoryBuilder().setNameFormat("job-executor-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );
    }

    public ReturnT<String> execute(TriggerParam param) {
        // 1. 查找任务处理器
        IJobHandler handler = jobHandlerMap.get(param.getJobHandler());
        if (handler == null) {
            return new ReturnT<>(ReturnT.FAIL_CODE,
                "job handler not found: " + param.getJobHandler());
        }

        // 2. 记录执行日志
        JobLog jobLog = createJobLog(param);

        // 3. 执行任务
        try {
            ReturnT<String> result = handler.execute(param.getParams());
            jobLog.setResult(result);
            return result;
        } catch (Exception e) {
            jobLog.setResult(new ReturnT<>(ReturnT.FAIL_CODE, e.getMessage()));
            throw e;
        } finally {
            jobLog.setEndTime(new Date());
            logRepository.save(jobLog);
        }
    }
}
```

## 三、核心链路设计

### 3.1 任务调度核心流程

#### 3.1.1 调度触发流程

调度中心的核心调度流程如下：

```java
// 调度中心核心调度引擎
public class ScheduleEngine {

    @Autowired
    private JobInfoRepository jobInfoRepository;
    @Autowired
    private JobTriggerPoolHelper triggerPoolHelper;
    @Autowired
    private RouteStrategyFactory routeStrategyFactory;

    // 调度主循环
    @Scheduled(fixedRate = 1000) // 每秒扫描一次
    public void scheduleTrigger() {
        // 1. 查询未来5秒内需要触发的任务
        long nextTime = System.currentTimeMillis() + 5000;
        List<JobInfo> jobs = jobInfoRepository.findNextTriggerJobs(nextTime);

        for (JobInfo job : jobs) {
            // 2. 检查任务状态
            if (job.getStatus() != JobStatus.NORMAL) {
                continue;
            }

            // 3. 检查并发策略（是否允许并发执行）
            if (!checkConcurrent(job)) {
                continue;
            }

            // 4. 异步触发任务
            triggerPoolHelper.trigger(job);
        }
    }

    // 实际触发逻辑
    public void doTrigger(JobInfo job) {
        // 1. 获取可用的执行节点列表
        List<ExecutorInfo> availableExecutors = getAvailableExecutors(job.getJobGroup());

        if (availableExecutors.isEmpty()) {
            // 无可用执行节点，记录告警
            alertService.alert(job, "无可用执行节点");
            return;
        }

        // 2. 根据路由策略选择执行节点
        RouteStrategy strategy = routeStrategyFactory.getStrategy(job.getRouteStrategy());
        ExecutorInfo targetExecutor = strategy.route(job, availableExecutors);

        // 3. 构造触发参数
        TriggerParam param = new TriggerParam();
        param.setJobId(job.getId());
        param.setJobHandler(job.getJobHandler());
        param.setParams(job.getParams());
        param.setShardCount(job.getShardCount());
        param.setShardItem(calculateShardItem(job, targetExecutor));

        // 4. 发送执行请求
        try {
            ReturnT<String> result = executorClient.execute(targetExecutor.getAddress(), param);
            // 5. 记录执行日志
            recordTriggerResult(job, targetExecutor, result);
        } catch (Exception e) {
            // 6. 触发失败处理
            handleTriggerFailure(job, targetExecutor, e);
        }
    }
}
```

#### 3.1.2 路由策略实现

```java
// 路由策略接口
public interface RouteStrategy {
    ExecutorInfo route(JobInfo job, List<ExecutorInfo> executors);
}

// 轮询路由
public class RoundRobinStrategy implements RouteStrategy {
    private final ConcurrentHashMap<Integer, AtomicInteger> counters = new ConcurrentHashMap<>();

    @Override
    public ExecutorInfo route(JobInfo job, List<ExecutorInfo> executors) {
        AtomicInteger counter = counters.computeIfAbsent(
            job.getId(), k -> new AtomicInteger(0));
        int index = Math.abs(counter.getAndIncrement()) % executors.size();
        return executors.get(index);
    }
}

// 一致性哈希路由
public class ConsistentHashStrategy implements RouteStrategy {
    @Override
    public ExecutorInfo route(JobInfo job, List<ExecutorInfo> executors) {
        // 构建一致性哈希环
        TreeMap<Long, ExecutorInfo> hashRing = new TreeMap<>();
        for (ExecutorInfo executor : executors) {
            for (int i = 0; i < 160; i++) { // 虚拟节点
                long hash = hash(executor.getAddress() + "#" + i);
                hashRing.put(hash, executor);
            }
        }
        // 根据任务ID查找最近的节点
        long jobHash = hash(String.valueOf(job.getId()));
        SortedMap<Long, ExecutorInfo> tail = hashRing.tailMap(jobHash);
        long key = tail.isEmpty() ? hashRing.firstKey() : tail.firstKey();
        return hashRing.get(key);
    }
}

// 故障转移路由
public class FailoverStrategy implements RouteStrategy {
    @Override
    public ExecutorInfo route(JobInfo job, List<ExecutorInfo> executors) {
        for (ExecutorInfo executor : executors) {
            if (checkExecutorHealth(executor)) {
                return executor;
            }
        }
        throw new RuntimeException("无健康执行节点");
    }

    private boolean checkExecutorHealth(ExecutorInfo executor) {
        try {
            return executorClient.healthCheck(executor.getAddress());
        } catch (Exception e) {
            return false;
        }
    }
}

// 路由策略工厂
public class RouteStrategyFactory {
    public RouteStrategy getStrategy(String strategyName) {
        switch (strategyName) {
            case "ROUND_ROBIN": return new RoundRobinStrategy();
            case "CONSISTENT_HASH": return new ConsistentHashStrategy();
            case "FAILOVER": return new FailoverStrategy();
            case "RANDOM": return new RandomStrategy();
            case "SHARDING_BROADCAST": return new ShardingBroadcastStrategy();
            default: return new RoundRobinStrategy();
        }
    }
}
```

### 3.2 任务分片机制

#### 3.2.1 分片场景与原理

任务分片用于分布式环境下数据分片的场景，提高数据处理能力。例如：用户需要刷新数据库中1000万条订单的状态，单节点处理耗时极长，通过分片机制将任务下发给多个节点并行处理，5个节点理想情况下每个节点只需处理200万条数据。

分片的核心原理是：调度中心在触发任务时，将分片总数和各节点对应的分片值下发给执行节点，执行节点根据分片值处理对应的数据范围。

#### 3.2.2 分片策略

**平均分片策略**：

将分片值平均分配给各执行节点。以3台机器6分片为例：

| 分片数 | IP1 | IP2 | IP3 |
| --- | --- | --- | --- |
| 6 | 0, 1 | 2, 3 | 4, 5 |

以3台机器8分片为例（多出的分片会循环分配）：

| 分片数 | IP1 | IP2 | IP3 |
| --- | --- | --- | --- |
| 8 | 0, 1, 6 | 2, 3, 7 | 4, 5 |

**随机分片策略**：将分片值随机分配给执行节点，每次调度时分片分配可能不同。

**哈希分片策略**：根据任务名的哈希值奇偶数决定IP列表的升降序，再进行平均分片。当任务名的哈希值为偶数时，将IP列表进行反转后分配，确保不同任务的分片分配更加均匀。

#### 3.2.3 分片实现

```java
// 分片上下文 - 通过ThreadLocal传递分片信息
public class ShardItemsContext {
    private static final ThreadLocal<List<Integer>> SHARD_ITEMS = new ThreadLocal<>();
    private static final ThreadLocal<Integer> SHARD_COUNT = new ThreadLocal<>();

    public static void setShardItems(List<Integer> items) {
        SHARD_ITEMS.set(items);
    }

    public static List<Integer> getShardItems() {
        return SHARD_ITEMS.get();
    }

    public static void setShardCount(int count) {
        SHARD_COUNT.set(count);
    }

    public static int getShardCount() {
        Integer count = SHARD_COUNT.get();
        return count == null ? 1 : count;
    }

    public static void clear() {
        SHARD_ITEMS.remove();
        SHARD_COUNT.remove();
    }
}

// 分片任务处理器示例
public class OrderStatusRefreshJob implements IJobHandler {

    @Autowired
    private OrderMapper orderMapper;

    @Override
    public ReturnT<String> execute(String param) {
        // 1. 获取当前节点的分片信息
        List<Integer> shardItems = ShardItemsContext.getShardItems();
        int shardCount = ShardItemsContext.getShardCount();

        if (shardItems == null || shardItems.isEmpty()) {
            return new ReturnT<>(ReturnT.SUCCESS_CODE, "无分片分配，跳过执行");
        }

        logger.info("开始处理分片: items={}, totalCount={}", shardItems, shardCount);

        // 2. 根据分片值处理对应数据
        for (Integer shardItem : shardItems) {
            processShard(shardItem, shardCount);
        }

        return new ReturnT<>(ReturnT.SUCCESS_CODE,
            String.format("分片处理完成: %s", shardItems));
    }

    private void processShard(int shardItem, int shardCount) {
        int pageSize = 1000;
        int offset = 0;

        while (true) {
            // 根据分片值计算数据范围：取模方式分片
            List<Order> orders = orderMapper.findByShard(
                shardItem, shardCount, offset, pageSize);

            if (orders.isEmpty()) {
                break;
            }

            for (Order order : orders) {
                try {
                    refreshOrderStatus(order);
                } catch (Exception e) {
                    logger.error("刷新订单状态失败: orderId={}", order.getId(), e);
                }
            }

            offset += pageSize;
        }
    }

    private void refreshOrderStatus(Order order) {
        // 业务逻辑：刷新订单状态
        OrderStatus latestStatus = queryLatestStatus(order.getId());
        if (latestStatus != order.getStatus()) {
            order.setStatus(latestStatus);
            order.setUpdateTime(new Date());
            orderMapper.updateById(order);
        }
    }
}
```

#### 3.2.4 分片配置最佳实践

分片数推荐设置为机器节点数的2倍，这样即使扩容也能保证分片数大于机器节点数。分片数不建议设置过大，需要根据机器节点规模和业务场景合理配置。

需要注意：当机器节点数大于分片数时，部分节点会分配不到分片，这些节点目前仍然会进行调度（下发分片为空），执行节点需要处理空分片的情况。

分片值通过ThreadLocal传递，如果执行逻辑中使用了自定义线程池进行异步处理，将无法获取分片信息。需要在异步前保存分片值，并在异步线程中手动设置。

```java
// 正确处理异步场景下的分片传递
public class AsyncShardJob implements IJobHandler {

    @Override
    public ReturnT<String> execute(String param) {
        List<Integer> shardItems = ShardItemsContext.getShardItems();
        int shardCount = ShardItemsContext.getShardCount();

        // 错误写法：直接在异步线程中获取分片信息会返回null
        // CompletableFuture.runAsync(() -> {
        //     List<Integer> items = ShardItemsContext.getShardItems(); // null!
        // });

        // 正确写法：在主线程捕获分片信息，传递给异步线程
        final List<Integer> finalShardItems = new ArrayList<>(shardItems);
        final int finalShardCount = shardCount;

        List<CompletableFuture<Void>> futures = finalShardItems.stream()
            .map(shardItem -> CompletableFuture.runAsync(() -> {
                ShardItemsContext.setShardItems(Collections.singletonList(shardItem));
                ShardItemsContext.setShardCount(finalShardCount);
                try {
                    processShard(shardItem, finalShardCount);
                } finally {
                    ShardItemsContext.clear();
                }
            }, executorService))
            .collect(Collectors.toList());

        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
        return ReturnT.SUCCESS;
    }
}
```

### 3.3 工作流编排

#### 3.3.1 DAG调度模型

工作流调度支持DAG（有向无环图）图式调度，支持图形化配置。任务之间可以定义依赖关系，前置任务完成后自动触发后置任务。

```java
// DAG工作流定义
public class DAGWorkflow {

    private String workflowId;
    private List<DAGNode> nodes;
    private List<DAGEdge> edges;

    // 拓扑排序，确定执行顺序
    public List<DAGNode> topologicalSort() {
        Map<String, Integer> inDegree = new HashMap<>();
        Map<String, List<DAGNode>> adjacency = new HashMap<>();

        for (DAGNode node : nodes) {
            inDegree.putIfAbsent(node.getId(), 0);
            adjacency.putIfAbsent(node.getId(), new ArrayList<>());
        }

        for (DAGEdge edge : edges) {
            adjacency.get(edge.getFrom()).add(getNode(edge.getTo()));
            inDegree.merge(edge.getTo(), 1, Integer::sum);
        }

        // Kahn算法
        Queue<DAGNode> queue = new LinkedList<>();
        for (DAGNode node : nodes) {
            if (inDegree.get(node.getId()) == 0) {
                queue.offer(node);
            }
        }

        List<DAGNode> sorted = new ArrayList<>();
        while (!queue.isEmpty()) {
            DAGNode current = queue.poll();
            sorted.add(current);
            for (DAGNode next : adjacency.get(current.getId())) {
                int newDegree = inDegree.merge(next.getId(), -1, Integer::sum);
                if (newDegree == 0) {
                    queue.offer(next);
                }
            }
        }
        return sorted;
    }
}

// 工作流执行引擎
public class WorkflowEngine {

    @Autowired
    private JobExecutor jobExecutor;
    @Autowired
    private WorkflowRepository workflowRepository;

    public void executeWorkflow(String workflowId) {
        DAGWorkflow workflow = workflowRepository.findById(workflowId);
        List<DAGNode> sortedNodes = workflow.topologicalSort();

        // 并行执行无依赖的节点，串行执行有依赖的节点
        Map<String, CompletableFuture<ReturnT<String>>> futures = new ConcurrentHashMap<>();

        for (DAGNode node : sortedNodes) {
            List<String> dependencies = node.getDependencies();

            if (dependencies.isEmpty()) {
                // 无依赖，直接执行
                futures.put(node.getId(),
                    CompletableFuture.supplyAsync(() -> executeNode(node)));
            } else {
                // 等待所有依赖完成后执行
                CompletableFuture<?>[] depFutures = dependencies.stream()
                    .map(futures::get)
                    .toArray(CompletableFuture[]::new);

                futures.put(node.getId(),
                    CompletableFuture.allOf(depFutures)
                        .thenApplyAsync(v -> {
                            // 检查依赖是否全部成功
                            boolean allSuccess = dependencies.stream()
                                .allMatch(dep ->
                                    futures.get(dep).join().getCode() == ReturnT.SUCCESS_CODE);
                            if (!allSuccess) {
                                // 依赖失败，根据失败策略处理
                                if (node.getFailStrategy() == FailStrategy.SKIP) {
                                    return new ReturnT<>(ReturnT.FAIL_CODE, "依赖任务失败，跳过执行");
                                }
                            }
                            return executeNode(node);
                        }));
            }
        }

        // 等待所有任务完成
        CompletableFuture.allOf(futures.values().toArray(new CompletableFuture[0])).join();
    }

    private ReturnT<String> executeNode(DAGNode node) {
        logger.info("执行工作流节点: nodeId={}, jobHandler={}",
            node.getId(), node.getJobHandler());
        return jobExecutor.execute(node.buildTriggerParam());
    }
}
```

#### 3.3.2 工作流特性

- **任务间数据传递**：前置任务的输出可以作为后置任务的输入参数
- **失败点重试**：工作流执行失败后，可以从失败的节点重新开始，不需要从头执行
- **拥塞控制**：限制工作流中同时执行的节点数量，防止资源耗尽
- **子工作流**：一个工作流可以嵌套调用另一个工作流
- **条件分支**：根据前置任务的结果决定后续执行路径

### 3.5 失败重试机制

对于被拆分的每个小任务，如果某台机器上的任务执行失败，调度端会自动将失败的分片发往其他可用节点重新执行，直到任务执行成功或者达到失败重试次数。

```java
// 失败重试引擎
public class RetryEngine {

    @Autowired
    private JobLogRepository logRepository;
    @Autowired
    private ScheduleEngine scheduleEngine;
    @Autowired
    private AlertService alertService;

    public void handleFailure(JobLog jobLog) {
        JobInfo job = jobLog.getJobInfo();
        int currentRetryCount = jobLog.getRetryCount();

        if (currentRetryCount >= job.getMaxRetryCount()) {
            // 达到最大重试次数，发送告警
            alertService.alert(job, String.format(
                "任务执行失败，已达最大重试次数(%d)", job.getMaxRetryCount()));
            return;
        }

        // 延迟重试（指数退避）
        long delay = calculateRetryDelay(currentRetryCount + 1);
        scheduleEngine.scheduleRetry(jobLog, delay);
    }

    private long calculateRetryDelay(int retryCount) {
        // 指数退避策略
        long baseDelay = 1000L; // 1秒
        long maxDelay = 300000L; // 5分钟
        long delay = baseDelay * (long) Math.pow(2, retryCount - 1);
        return Math.min(delay, maxDelay);
    }
}
```

当执行节点宕机时，调度中心通过心跳检测发现节点不可用，将正在执行的任务转移到其他健康节点重新执行。

```java
// 节点健康检测
public class ExecutorHealthChecker {

    @Scheduled(fixedRate = 10000)
    public void checkExecutorHealth() {
        List<ExecutorInfo> allExecutors = executorRepository.findAll();

        for (ExecutorInfo executor : allExecutors) {
            long lastHeartbeat = executor.getLastHeartbeatTime();
            long timeout = 90000; // 90秒无心跳视为宕机

            if (System.currentTimeMillis() - lastHeartbeat > timeout) {
                // 标记节点为不可用
                executor.setStatus(ExecutorStatus.DEAD);
                executorRepository.update(executor);

                // 查找该节点上正在执行的任务
                List<JobLog> runningJobs = logRepository
                    .findByExecutorAddressAndStatus(
                        executor.getAddress(), JobStatus.RUNNING);

                for (JobLog jobLog : runningJobs) {
                    // 转移到其他节点重新执行
                    scheduleEngine.failover(jobLog);
                }

                alertService.alert("执行节点宕机",
                    String.format("节点 %s 已宕机，%d 个任务正在转移",
                        executor.getAddress(), runningJobs.size()));
            }
        }
    }
}
```

```java
// 任务超时处理
public class JobTimeoutHandler {

    public ReturnT<String> executeWithTimeout(IJobHandler handler,
                                               String param, int timeoutSeconds) {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        Future<ReturnT<String>> future = executor.submit(() -> handler.execute(param));

        try {
            return future.get(timeoutSeconds, TimeUnit.SECONDS);

        } catch (Exception e) {

        } finally {
            executor.shutdownNow();
        }
    }
}
```

### 4.4 任务幂等性

分布式调度场景下，任务可能被重复触发（网络超时后重试、故障转移等），需要保证任务执行的幂等性。

```java
// 幂等任务处理器
public abstract class IdempotentJobHandler implements IJobHandler {

    @Autowired
    private JobIdempotentRepository idempotentRepository;

    @Override
    public ReturnT<String> execute(String param) {
        String idempotentKey = generateIdempotentKey(param);

        // 尝试获取幂等锁
        boolean acquired = idempotentRepository.tryAcquireLock(
            idempotentKey, 3600); // 锁1小时

        if (!acquired) {
            // 检查是否已完成
            JobResult existing = idempotentRepository.getResult(idempotentKey);
            if (existing != null) {
                return new ReturnT<>(existing.getCode(), existing.getMsg());
            }
            return new ReturnT<>(ReturnT.FAIL_CODE, "任务正在执行中");
        }

        try {
            ReturnT<String> result = doExecute(param);
            idempotentRepository.saveResult(idempotentKey, result);
            return result;
        } finally {
            idempotentRepository.releaseLock(idempotentKey);
        }
    }

    protected abstract ReturnT<String> doExecute(String param);

    protected abstract String generateIdempotentKey(String param);
}
```

### 5.1 调度线程池优化

调度中心触发任务时使用独立的线程池，避免任务触发阻塞调度主线程。根据任务量大小配置不同的线程池：

```java
    // 快任务线程池（执行时间<1秒）
    private ThreadPoolExecutor fastTriggerPool;
    // 慢任务线程池（执行时间>1秒）
    private ThreadPoolExecutor slowTriggerPool;

            10, 200, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(1000),
            new ThreadFactoryBuilder().setNameFormat("fast-trigger-%d").build()
        );

        slowTriggerPool = new ThreadPoolExecutor(
            10, 100, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(2000),
            new ThreadFactoryBuilder().setNameFormat("slow-trigger-%d").build()
        );
    }

    public void trigger(JobInfo job) {
        // 根据任务历史执行时间选择线程池
        ThreadPoolExecutor pool = getTriggerPool(job);
        pool.execute(() -> scheduleEngine.doTrigger(job));
    }

    private ThreadPoolExecutor getTriggerPool(JobInfo job) {
        // 最近5次执行平均时间超过1秒使用慢线程池
        double avgDuration = logRepository.getAvgDuration(job.getId(), 5);
        return avgDuration > 1000 ? slowTriggerPool : fastTriggerPool;
    }
}
```

## 六、最佳实践

### 6.1 方案选型

**XXL-JOB**：轻量级方案，适合中小规模场景。部署简单（仅依赖数据库），开箱即用，社区活跃。支持Cron触发、API触发、分片广播、故障转移等核心能力，但不支持MapReduce和工作流编排。

**Elastic-Job**：基于Zookeeper实现，适合对一致性要求较高的场景。支持丰富的分片策略，但部署较重（依赖Zookeeper），运维成本相对较高。

**PowerJob**：功能最全面的开源方案，支持Cron、固定频率、固定延迟、API触发，支持Map/MapReduce分布式计算模型，支持DAG工作流。外部依赖精简（仅依赖数据库），适合大规模复杂调度场景。

**Apache Airflow**：Python生态，适合数据工程和ETL场景。强大的DAG工作流能力，支持任务间数据传递和失败点重试，但不支持Java进程内任务。

**DolphinScheduler**：企业级方案，支持可视化DAG配置、多租户、丰富的任务类型。适合企业级数据平台建设。

### 6.2 任务设计原则

**1. 任务应设计为幂等**。分布式调度场景下任务可能被重复触发，幂等设计是必须的。可以通过唯一业务标识去重，或通过状态机控制避免重复处理。

**2. 合理设置分片数**。分片数推荐设置为执行节点数的2倍，兼顾并行度和扩容弹性。分片数不宜过大，避免调度开销超过业务处理时间。

**3. 避免长事务**。任务执行中如果涉及数据库操作，避免在事务中执行耗时操作。采用批量提交、分批处理的方式减少事务持有时间。

**4. 设置合理的超时时间**。根据任务的正常执行时间设置超时阈值，避免任务卡死占用执行线程。超时时间通常设置为正常执行时间的2-3倍。

**5. 日志要详细但不冗余**。记录任务开始、结束、关键里程碑和异常信息，避免记录过多调试信息影响性能。

### 6.4 常见踩坑

**坑1：分片信息在异步线程中丢失**。分片值通过ThreadLocal传递，如果在任务执行中使用自定义线程池异步处理，子线程中无法获取分片信息。需要在异步前保存分片值，在子线程中手动设置。

**坑2：任务并发执行导致数据不一致**。如果任务执行时间超过调度间隔，可能导致同一任务的多个实例并发执行。需要根据业务场景配置合适的并发策略（串行、丢弃、覆盖）。

**坑3：执行节点扩缩容时分片不均匀**。节点数变化后分片分配可能不均匀，特别是在使用一致性哈希策略时。建议分片数设置为节点数的整数倍或2倍。

**坑4：调度中心时间与执行节点时间不同步**。调度基于时间触发，如果各节点时间不同步，可能导致任务在错误的时间执行或重复执行。需要部署NTP时间同步服务。

**坑5：大量任务同时触发导致资源争抢**。如果多个任务的cron表达式设置为同一时间点（如每天凌晨0点），可能同时触发大量任务，导致系统资源紧张。建议错峰设置任务触发时间。

**坑6：外部依赖不可用导致任务无限重试**。任务依赖外部服务（如数据库、API），外部服务不可用时任务会持续失败重试。需要设置最大重试次数和告警机制。

### 6.5 多SET与泳道支持

在多SET部署架构下，每个SET（或泳道）需要独立获取全量的分片信息。例如有5个分片，SET1和SET2各有节点，则SET1的节点可以分配到0-4的分片，SET2的节点也可以分配到0-4的分片。这样每个SET内部独立完成全量数据处理，避免跨SET调用。

```java
// 多SET分片路由
public class MultiSetShardingStrategy implements RouteStrategy {

    @Override
    public ExecutorInfo route(JobInfo job, List<ExecutorInfo> executors) {
        // 按SET分组
        Map<String, List<ExecutorInfo>> setGroups = executors.stream()
            .collect(Collectors.groupingBy(ExecutorInfo::getSetName));

        // 每个SET内独立分片
        for (Map.Entry<String, List<ExecutorInfo>> entry : setGroups.entrySet()) {
            List<ExecutorInfo> setExecutors = entry.getValue();
            // 在SET内进行分片分配
            assignShardsWithinSet(job, setExecutors);
        }
        return null; // 分片广播模式返回null
    }
}
```

## 七、总结

分布式任务调度是微服务架构下不可或缺的基础设施。选择调度方案时需要综合考虑业务规模、任务复杂度、运维成本等因素：

- **中小规模、简单调度需求**：XXL-JOB是最佳选择，轻量级、易部署、社区活跃
- **大规模、复杂计算需求**：PowerJob提供Map/MapReduce和DAG工作流能力
- **数据工程、ETL场景**：Apache Airflow或DolphinScheduler更适合
- **对一致性要求极高**：Elastic-Job基于Zookeeper提供强一致性保证

无论选择哪种方案，任务幂等性、合理的分片策略、完善的监控告警都是系统稳定运行的基石。在实践中，建议先从简单的Cron调度开始，随着业务复杂度增长逐步引入分片、工作流等高级特性。

## 八、全链路实战案例

前面的章节介绍了分布式任务调度的原理与关键设计点，本章通过三个贴近生产环境的完整案例，串联任务触发、分片执行、延迟处理、失败告警与自动恢复的全链路实现，每个案例均包含完整的Java代码、异常处理、日志记录与幂等控制。

### 8.1 案例一：分片任务执行全链路（任务触发 → 分片策略 → 并行执行 → 结果汇总 → 失败分片重试）

#### 8.1.1 业务场景

某电商平台需要每天凌晨对千万级订单进行超时状态核对，单机处理无法在允许的窗口时间内完成。要求：调度中心按cron触发任务、按节点数动态计算分片、各执行节点并行处理分片内数据、调度中心汇总各分片执行结果、对失败分片自动重试直至成功或达到重试上限。

#### 8.1.2 整体链路

```
Cron触发 → 计算可用执行节点 → 生成分片计划 → 广播下发分片 → 节点并行执行
    → 上报分片结果 → 调度中心汇总 → 存在失败分片？
                                        ├─ 是 → 失败分片重试（指数退避，直至上限）
                                        └─ 否 → 任务标记成功，写入完成日志
```

#### 8.1.3 分片计划与下发

```java
/**
 * 分片任务全链路 - 分片计划生成与下发
 * 调度中心侧：负责生成分片计划、广播下发、汇总结果、驱动失败重试
 */
@Component
public class ShardingJobCoordinator {

    private static final Logger logger = LoggerFactory.getLogger(ShardingJobCoordinator.class);

    @Autowired
    private ExecutorRegistryRepository executorRepository;
    @Autowired
    private ShardingTaskResultRepository resultRepository;
    @Autowired
    private ExecutorRpcClient executorRpcClient;
    @Autowired
    private AlertService alertService;

    private static final int MAX_RETRY_COUNT = 3;

    /**
     * 任务入口：由ScheduleEngine在cron触发时调用
     */
    public void runShardingJob(JobInfo job) {
        // 幂等控制：以 jobId + 触发时间戳(精确到分钟) 作为批次唯一键，避免重复触发生成重复批次
        String batchId = buildBatchId(job);
        if (resultRepository.existsBatch(batchId)) {
            logger.warn("分片任务批次已存在，跳过重复触发: batchId={}", batchId);
            return;
        }

        try {
            // 1. 获取健康执行节点
            List<ExecutorInfo> executors = executorRepository.findHealthyByGroup(job.getJobGroup());
            if (executors.isEmpty()) {
                alertService.alert(AlertLevel.P1,
                    String.format("任务[%s]无可用执行节点，本次调度跳过", job.getDesc()));
                return;
            }

            // 2. 生成分片计划：分片数取节点数的2倍，保证扩容弹性
            int shardCount = Math.max(job.getShardCount(), executors.size() * 2);
            List<ShardPlan> shardPlans = buildShardPlans(shardCount, executors);

            // 3. 创建批次记录（用于汇总与幂等校验）
            resultRepository.createBatch(batchId, job.getId(), shardPlans.size());

            logger.info("分片任务开始下发: batchId={}, jobId={}, shardCount={}, executorCount={}",
                batchId, job.getId(), shardCount, executors.size());

            // 4. 并行下发分片到各执行节点
            List<CompletableFuture<Void>> futures = shardPlans.stream()
                .map(plan -> CompletableFuture.runAsync(
                    () -> dispatchShard(batchId, job, plan, 0)))
                .collect(Collectors.toList());

            CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
                .orTimeout(10, TimeUnit.MINUTES)
                .whenComplete((v, ex) -> {
                    if (ex != null) {
                        logger.error("分片下发阶段异常: batchId={}", batchId, ex);
                    }
                    // 5. 下发完成后触发一轮汇总检查（真正的完成判定以节点异步上报为准）
                    checkAndSummarize(batchId);
                });

        } catch (Exception e) {
            logger.error("分片任务调度失败: jobId={}, batchId={}", job.getId(), batchId, e);
            alertService.alert(AlertLevel.P1,
                String.format("任务[%s]分片调度异常: %s", job.getDesc(), e.getMessage()));
        }
    }

    /**
     * 平均分片策略：将shardCount个分片均匀分配给executors，多余分片循环分配
     */
    private List<ShardPlan> buildShardPlans(int shardCount, List<ExecutorInfo> executors) {
        List<ShardPlan> plans = new ArrayList<>();
        for (int i = 0; i < shardCount; i++) {
            ExecutorInfo executor = executors.get(i % executors.size());
            plans.add(new ShardPlan(i, shardCount, executor));
        }
        return plans;
    }

    /**
     * 下发单个分片，包含异常处理与重试计数
     */
    private void dispatchShard(String batchId, JobInfo job, ShardPlan plan, int retryCount) {
        // 分片级幂等键：batchId + shardItem，保证同一分片重复下发时执行端可识别
        String shardKey = batchId + "-shard-" + plan.getShardItem();

        TriggerParam param = new TriggerParam();
        param.setJobId(job.getId());
        param.setJobHandler(job.getJobHandler());
        param.setShardCount(plan.getShardCount());
        param.setShardItem(plan.getShardItem());
        param.setIdempotentKey(shardKey);
        param.setBatchId(batchId);

        try {
            logger.info("下发分片: batchId={}, shardItem={}/{}, executor={}, retryCount={}",
                batchId, plan.getShardItem(), plan.getShardCount(),
                plan.getExecutor().getAddress(), retryCount);

            ReturnT<String> result = executorRpcClient.execute(plan.getExecutor().getAddress(), param);

            if (result.getCode() == ReturnT.SUCCESS_CODE) {
                resultRepository.markShardSuccess(batchId, plan.getShardItem(), result.getMsg());
                logger.info("分片执行成功: batchId={}, shardItem={}", batchId, plan.getShardItem());
            } else {
                handleShardFailure(batchId, job, plan, retryCount, result.getMsg());
            }
        } catch (Exception e) {
            logger.error("分片下发/执行异常: batchId={}, shardItem={}, retryCount={}",
                batchId, plan.getShardItem(), retryCount, e);
            handleShardFailure(batchId, job, plan, retryCount, e.getMessage());
        }
    }

    /**
     * 失败分片重试：指数退避，切换到其他健康节点重试，超过上限记录最终失败并告警
     */
    private void handleShardFailure(String batchId, JobInfo job, ShardPlan plan,
                                     int retryCount, String errorMsg) {
        resultRepository.markShardFailure(batchId, plan.getShardItem(), errorMsg, retryCount);

        if (retryCount >= MAX_RETRY_COUNT) {
            logger.error("分片重试达到上限，标记最终失败: batchId={}, shardItem={}, retryCount={}",
                batchId, plan.getShardItem(), retryCount);
            alertService.alert(AlertLevel.P2, String.format(
                "任务[%s]分片[%d]重试%d次后仍然失败: %s",
                job.getDesc(), plan.getShardItem(), retryCount, errorMsg));
            checkAndSummarize(batchId);
            return;
        }

        // 指数退避：1s, 2s, 4s...
        long delayMs = Math.min(1000L << retryCount, 60000L);

        // 故障转移：优先换一个健康节点重试，避免固定节点反复失败
        List<ExecutorInfo> healthyExecutors = executorRepository.findHealthyByGroup(job.getJobGroup());
        ExecutorInfo retryTarget = healthyExecutors.stream()
            .filter(e -> !e.getAddress().equals(plan.getExecutor().getAddress()))
            .findFirst()
            .orElse(plan.getExecutor());

        ShardPlan retryPlan = new ShardPlan(plan.getShardItem(), plan.getShardCount(), retryTarget);

        logger.warn("分片将在{}ms后重试: batchId={}, shardItem={}, nextExecutor={}",
            delayMs, batchId, plan.getShardItem(), retryTarget.getAddress());

        retryScheduler.schedule(
            () -> dispatchShard(batchId, job, retryPlan, retryCount + 1),
            delayMs, TimeUnit.MILLISECONDS);
    }

    /**
     * 结果汇总：统计批次内所有分片状态，全部成功则标记任务成功，存在失败则触发告警
     */
    private void checkAndSummarize(String batchId) {
        ShardBatchSummary summary = resultRepository.summarize(batchId);

        logger.info("分片批次汇总: batchId={}, total={}, success={}, failed={}, pending={}",
            batchId, summary.getTotal(), summary.getSuccessCount(),
            summary.getFailedCount(), summary.getPendingCount());

        if (summary.getPendingCount() > 0) {
            // 仍有分片在执行/重试中，本次不做终态判定
            return;
        }

        if (summary.getFailedCount() == 0) {
            resultRepository.markBatchSuccess(batchId);
            logger.info("分片任务批次全部成功: batchId={}", batchId);
        } else {
            resultRepository.markBatchPartialFailure(batchId);
            alertService.alert(AlertLevel.P2, String.format(
                "分片任务批次[%s]存在%d个失败分片（共%d个），请人工介入排查",
                batchId, summary.getFailedCount(), summary.getTotal()));
        }
    }

    private String buildBatchId(JobInfo job) {
        String minuteSlot = new SimpleDateFormat("yyyyMMddHHmm").format(new Date());
        return "batch-" + job.getId() + "-" + minuteSlot;
    }

    private final ScheduledExecutorService retryScheduler =
        Executors.newScheduledThreadPool(4, new ThreadFactoryBuilder()
            .setNameFormat("shard-retry-%d").build());
}
```

#### 8.1.4 执行节点侧：分片处理与幂等控制

```java
/**
 * 执行节点侧：处理下发的分片任务，内置幂等校验，避免重试/故障转移导致的重复处理
 */
@Component
public class OrderReconcileShardHandler implements IJobHandler {

    private static final Logger logger = LoggerFactory.getLogger(OrderReconcileShardHandler.class);

    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private ShardExecutionRecordRepository executionRecordRepository;

    @Override
    public ReturnT<String> execute(TriggerParam param) {
        String idempotentKey = param.getIdempotentKey();

        // 幂等校验：同一分片键已成功执行过，直接返回历史结果，不重复处理数据
        ShardExecutionRecord existing = executionRecordRepository.find(idempotentKey);
        if (existing != null && existing.getStatus() == ExecutionStatus.SUCCESS) {
            logger.info("分片已处理过，直接返回幂等结果: idempotentKey={}", idempotentKey);
            return new ReturnT<>(ReturnT.SUCCESS_CODE, existing.getResultMsg());
        }

        // 记录执行开始（用于崩溃恢复后判断是否曾经开始但未完成）
        executionRecordRepository.markRunning(idempotentKey, param.getBatchId(), param.getShardItem());

        long startTime = System.currentTimeMillis();
        int processedCount = 0;

        try {
            int shardItem = param.getShardItem();
            int shardCount = param.getShardCount();

            logger.info("开始处理分片: idempotentKey={}, shardItem={}/{}", idempotentKey, shardItem, shardCount);

            long lastMaxId = 0;
            int pageSize = 1000;

            while (true) {
                List<Order> orders;
                try {
                    orders = orderMapper.findByShardAndIdAfter(shardItem, shardCount, lastMaxId, pageSize);
                } catch (DataAccessException dae) {
                    // 数据库瞬时异常，记录日志后向上抛出，由调度中心走分片重试链路
                    logger.error("查询分片数据失败，触发上层重试: idempotentKey={}", idempotentKey, dae);
                    throw new ShardExecutionException("数据库查询异常: " + dae.getMessage(), dae);
                }

                if (orders.isEmpty()) {
                    break;
                }

                for (Order order : orders) {
                    try {
                        reconcileSingleOrder(order);
                        processedCount++;
                    } catch (Exception e) {
                        // 单条数据处理失败不阻断整体分片，记录后继续，最后汇总失败明细
                        logger.error("订单核对失败: orderId={}, idempotentKey={}", order.getId(), idempotentKey, e);
                        executionRecordRepository.appendFailedItem(idempotentKey, order.getId(), e.getMessage());
                    }
                }
                lastMaxId = orders.get(orders.size() - 1).getId();
            }

            long costMs = System.currentTimeMillis() - startTime;
            String resultMsg = String.format("分片处理完成: processedCount=%d, costMs=%d", processedCount, costMs);

            executionRecordRepository.markSuccess(idempotentKey, resultMsg);
            logger.info("分片处理成功: idempotentKey={}, {}", idempotentKey, resultMsg);

            return new ReturnT<>(ReturnT.SUCCESS_CODE, resultMsg);

        } catch (ShardExecutionException see) {
            executionRecordRepository.markFailed(idempotentKey, see.getMessage());
            return new ReturnT<>(ReturnT.FAIL_CODE, see.getMessage());
        } catch (Exception e) {
            logger.error("分片处理发生未预期异常: idempotentKey={}", idempotentKey, e);
            executionRecordRepository.markFailed(idempotentKey, e.getMessage());
            return new ReturnT<>(ReturnT.FAIL_CODE, "未预期异常: " + e.getMessage());
        }
    }

    private void reconcileSingleOrder(Order order) {
        OrderStatus latestStatus = queryUpstreamStatus(order.getId());
        if (latestStatus != order.getStatus()) {
            order.setStatus(latestStatus);
            order.setUpdateTime(new Date());
            orderMapper.updateById(order);
        }
    }

    private OrderStatus queryUpstreamStatus(Long orderId) {
        // 调用上游支付/物流系统查询真实状态（示例中省略远程调用细节）
        return orderMapper.queryLatestStatusFromUpstream(orderId);
    }

    /** 分片执行异常，携带明确语义，便于上层区分是否需要重试 */
    static class ShardExecutionException extends RuntimeException {
        ShardExecutionException(String message, Throwable cause) {
            super(message, cause);
        }
    }
}
```

#### 8.1.5 关键设计说明

- **幂等控制**：批次级使用`batchId`（jobId + 触发分钟）防止重复触发生成重复批次；分片级使用`idempotentKey`（batchId + shardItem）在执行节点侧记录执行状态，重试或故障转移到新节点时可直接识别"已成功"从而跳过重复处理。
- **异常分层处理**：数据库查询异常包装为`ShardExecutionException`向上抛出以触发分片级重试；单条订单处理异常仅记录不中断整个分片，避免因个别脏数据导致整个分片反复失败。
- **失败重试**：采用指数退避（1s→2s→4s，上限60s）并优先切换到其他健康节点，达到`MAX_RETRY_COUNT`后停止重试并触发P2告警，等待人工介入。
- **结果汇总**：调度中心通过`ShardBatchSummary`统计成功/失败/待处理分片数，只有全部分片终态确定后才判定批次成功或部分失败。

### 8.2 案例二：延迟任务处理全链路（定时轮询Redis/延迟队列 → 到期任务投递 → 执行 → 超时监控）

#### 8.2.1 业务场景

某订单系统需要实现"下单30分钟未支付自动取消"。由于延迟时间跨度大且订单量大，不适合为每个订单创建一个JVM定时器，采用Redis ZSet作为延迟队列，score为到期时间戳，通过轮询扫描到期任务并投递执行，同时对执行过程做超时监控。

#### 8.2.2 整体链路

```
下单成功 → 写入延迟队列(ZSet, score=到期时间戳) → 定时轮询扫描到期任务
    → 到期任务投递到执行线程池 → 执行取消逻辑（幂等）→ 执行成功则从队列移除
                                                    → 执行超时/异常 → 监控告警 + 重新入队重试
```

#### 8.2.3 延迟任务写入与轮询投递

```java
/**
 * 延迟任务全链路 - 基于Redis ZSet的延迟队列
 */
@Component
public class RedisDelayQueueService {

    private static final Logger logger = LoggerFactory.getLogger(RedisDelayQueueService.class);

    private static final String DELAY_QUEUE_KEY = "delay_queue:order_cancel";
    private static final String PROCESSING_SET_KEY = "delay_queue:order_cancel:processing";
    private static final String TASK_PAYLOAD_PREFIX = "delay_queue:order_cancel:payload:";

    @Autowired
    private StringRedisTemplate redisTemplate;

    /**
     * 提交延迟任务：下单成功后调用，写入ZSet并保存任务载荷
     */
    public void submitDelayTask(String taskId, String payloadJson, long delayMillis) {
        try {
            long dueTime = System.currentTimeMillis() + delayMillis;

            // 幂等：使用taskId作为唯一成员，重复提交同一订单的延迟任务不会产生重复数据
            redisTemplate.opsForZSet().add(DELAY_QUEUE_KEY, taskId, dueTime);
            redisTemplate.opsForValue().set(
                TASK_PAYLOAD_PREFIX + taskId, payloadJson, Duration.ofHours(6));

            logger.info("延迟任务提交成功: taskId={}, dueTime={}", taskId, new Date(dueTime));
        } catch (Exception e) {
            // Redis写入失败降级：记录到本地补偿表，由补偿任务定期重新提交，避免任务丢失
            logger.error("延迟任务提交到Redis失败，写入本地补偿表: taskId={}", taskId, e);
            fallbackRepository.saveFailedSubmission(taskId, payloadJson, delayMillis);
        }
    }

    /**
     * 取消延迟任务：订单提前支付成功时调用，从队列中移除
     */
    public void cancelDelayTask(String taskId) {
        try {
            redisTemplate.opsForZSet().remove(DELAY_QUEUE_KEY, taskId);
            redisTemplate.opsForZSet().remove(PROCESSING_SET_KEY, taskId);
            redisTemplate.delete(TASK_PAYLOAD_PREFIX + taskId);
            logger.info("延迟任务已取消: taskId={}", taskId);
        } catch (Exception e) {
            logger.error("取消延迟任务失败: taskId={}", taskId, e);
        }
    }

    @Autowired
    private DelayTaskFallbackRepository fallbackRepository;
}
```

```java
/**
 * 延迟任务轮询投递器：定时扫描到期任务，投递到执行线程池
 */
@Component
public class DelayTaskDispatcher {

    private static final Logger logger = LoggerFactory.getLogger(DelayTaskDispatcher.class);

    private static final String DELAY_QUEUE_KEY = "delay_queue:order_cancel";
    private static final String PROCESSING_SET_KEY = "delay_queue:order_cancel:processing";
    private static final String TASK_PAYLOAD_PREFIX = "delay_queue:order_cancel:payload:";
    private static final long VISIBILITY_TIMEOUT_MS = 60_000L; // 处理中超时时间，用于崩溃恢复

    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private OrderCancelExecutor cancelExecutor;
    @Autowired
    private AlertService alertService;

    private final ExecutorService dispatchPool = new ThreadPoolExecutor(
        20, 50, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(2000),
        new ThreadFactoryBuilder().setNameFormat("delay-task-worker-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy());

    /**
     * 每秒轮询一次到期任务，批量拉取避免单次拉取量过大
     */
    @Scheduled(fixedDelay = 1000)
    public void pollDueTasks() {
        try {
            long now = System.currentTimeMillis();

            // 1. 先恢复因节点崩溃而滞留在processing集合中超时未完成的任务
            recoverStuckProcessingTasks(now);

            // 2. 拉取到期任务（score <= now），限制单次拉取100条防止瞬时压垮线程池
            Set<String> dueTaskIds = redisTemplate.opsForZSet()
                .rangeByScore(DELAY_QUEUE_KEY, 0, now, 0, 100);

            if (dueTaskIds == null || dueTaskIds.isEmpty()) {
                return;
            }

            for (String taskId : dueTaskIds) {
                // 3. 使用ZSet原子移除作为"任务领取"的互斥手段：
                //    只有移除成功（返回1）的节点才真正获得该任务的执行权，避免多实例轮询时重复投递
                Long removed = redisTemplate.opsForZSet().remove(DELAY_QUEUE_KEY, taskId);
                if (removed == null || removed == 0) {
                    continue; // 已被其他节点/线程领取
                }

                // 4. 标记为处理中，记录领取时间用于超时监控
                redisTemplate.opsForZSet().add(PROCESSING_SET_KEY, taskId, System.currentTimeMillis());

                dispatchPool.execute(() -> handleTask(taskId));
            }
        } catch (Exception e) {
            // 轮询本身异常不能中断定时任务调度，记录并告警，等待下一轮重试
            logger.error("延迟任务轮询异常", e);
            alertService.alert(AlertLevel.P1, "延迟任务轮询异常: " + e.getMessage());
        }
    }

    /**
     * 单个到期任务的执行入口：包含超时控制、异常处理、执行后清理
     */
    private void handleTask(String taskId) {
        String payloadJson = redisTemplate.opsForValue().get(TASK_PAYLOAD_PREFIX + taskId);
        if (payloadJson == null) {
            logger.warn("延迟任务载荷已丢失，可能已被处理或过期: taskId={}", taskId);
            redisTemplate.opsForZSet().remove(PROCESSING_SET_KEY, taskId);
            return;
        }

        long startTime = System.currentTimeMillis();
        try {
            // 超时监控：执行逻辑最多允许10秒，超时则中断并记录，避免占用线程池
            ReturnT<String> result = executeWithTimeout(taskId, payloadJson, 10);

            if (result.getCode() == ReturnT.SUCCESS_CODE) {
                logger.info("延迟任务执行成功: taskId={}, costMs={}",
                    taskId, System.currentTimeMillis() - startTime);
                cleanupTask(taskId);
            } else {
                logger.warn("延迟任务执行失败: taskId={}, msg={}", taskId, result.getMsg());
                rescheduleFailedTask(taskId, payloadJson);
            }
        } catch (Exception e) {
            logger.error("延迟任务执行异常: taskId={}", taskId, e);
            rescheduleFailedTask(taskId, payloadJson);
        }
    }

    /**
     * 超时控制封装：使用独立Future避免慢任务拖垮整个dispatchPool
     */
    private ReturnT<String> executeWithTimeout(String taskId, String payloadJson, int timeoutSeconds) {
        ExecutorService singleTaskExecutor = Executors.newSingleThreadExecutor();
        Future<ReturnT<String>> future = singleTaskExecutor.submit(
            () -> cancelExecutor.execute(taskId, payloadJson));

        try {
            return future.get(timeoutSeconds, TimeUnit.SECONDS);
        } catch (TimeoutException te) {
            future.cancel(true);
            alertService.alert(AlertLevel.P2,
                String.format("延迟任务执行超时: taskId=%s, timeout=%ds", taskId, timeoutSeconds));
            return new ReturnT<>(ReturnT.FAIL_CODE, "执行超时");
        } catch (Exception e) {
            return new ReturnT<>(ReturnT.FAIL_CODE, "执行异常: " + e.getMessage());
        } finally {
            singleTaskExecutor.shutdownNow();
        }
    }

    /**
     * 失败任务重新入队：短延迟后重试，超过最大重试次数则告警并转人工
     */
    private void rescheduleFailedTask(String taskId, String payloadJson) {
        int retryCount = incrementAndGetRetryCount(taskId);
        redisTemplate.opsForZSet().remove(PROCESSING_SET_KEY, taskId);

        if (retryCount > 5) {
            logger.error("延迟任务重试超过上限，转人工处理: taskId={}, retryCount={}", taskId, retryCount);
            alertService.alert(AlertLevel.P2,
                String.format("延迟任务[%s]重试%d次仍失败，请人工介入", taskId, retryCount));
            return;
        }

        long retryDelayMs = Math.min(5000L * retryCount, 60000L);
        long nextDueTime = System.currentTimeMillis() + retryDelayMs;
        redisTemplate.opsForZSet().add(DELAY_QUEUE_KEY, taskId, nextDueTime);
        logger.warn("延迟任务将在{}ms后重试: taskId={}, retryCount={}", retryDelayMs, taskId, retryCount);
    }

    private int incrementAndGetRetryCount(String taskId) {
        String retryKey = "delay_queue:order_cancel:retry:" + taskId;
        Long count = redisTemplate.opsForValue().increment(retryKey);
        redisTemplate.expire(retryKey, Duration.ofHours(6));
        return count == null ? 1 : count.intValue();
    }

    private void cleanupTask(String taskId) {
        redisTemplate.opsForZSet().remove(PROCESSING_SET_KEY, taskId);
        redisTemplate.delete(TASK_PAYLOAD_PREFIX + taskId);
        redisTemplate.delete("delay_queue:order_cancel:retry:" + taskId);
    }

    /**
     * 超时监控与崩溃恢复：定期扫描processing集合中滞留过久的任务，重新投递
     * 用于覆盖"节点在执行过程中崩溃，任务停留在processing集合但永远不会完成"的场景
     */
    private void recoverStuckProcessingTasks(long now) {
        Set<String> stuckTasks = redisTemplate.opsForZSet()
            .rangeByScore(PROCESSING_SET_KEY, 0, now - VISIBILITY_TIMEOUT_MS);

        if (stuckTasks == null || stuckTasks.isEmpty()) {
            return;
        }

        for (String taskId : stuckTasks) {
            logger.warn("检测到滞留处理中任务，重新投递: taskId={}", taskId);
            redisTemplate.opsForZSet().remove(PROCESSING_SET_KEY, taskId);
            redisTemplate.opsForZSet().add(DELAY_QUEUE_KEY, taskId, now);
            alertService.alert(AlertLevel.P2,
                String.format("延迟任务[%s]处理超时未确认，已重新投递", taskId));
        }
    }
}
```

#### 8.2.5 关键设计说明

- **幂等控制**：延迟队列以`taskId`（通常为订单号）作为ZSet唯一成员，重复提交不会重复入队；投递领取阶段通过`ZREM`的原子返回值作为互斥锁，只有真正移除成功的调用方才获得执行权，天然避免多实例重复投递；业务执行层再基于订单状态机+乐观锁版本号做二次幂等兜底，防止与支付回调并发时误取消。
- **超时监控**：执行阶段使用独立单线程`Future.get(timeout)`控制单任务最长执行时间，超时后中断线程并告警；同时通过`PROCESSING_SET_KEY`记录任务领取时间，由`recoverStuckProcessingTasks`定期扫描处理超时（默认60秒）未完成的任务并重新投递，覆盖执行节点崩溃导致任务"卡死"的场景。
- **失败重试**：执行失败或超时的任务会重新计算延迟时间写回ZSet（阶梯延迟，上限60秒），并对重试次数做计数，超过5次后停止重试并触发P2告警，避免无限重试拖累系统。
- **降级处理**：延迟任务提交到Redis失败时，写入本地补偿表由独立的补偿任务定期重新提交，避免Redis抖动导致任务丢失。

### 8.3 案例三：任务失败告警与自动恢复全链路（失败检测 → 重试策略 → 手动/自动恢复 → 告警通知）

#### 8.3.1 业务场景

调度平台需要对所有任务的执行失败情况进行统一检测，按照失败次数分级采取不同的恢复策略：轻微失败自动重试恢复，连续失败达到阈值后升级告警并尝试自动熔断恢复，多次自动恢复无效后转人工介入，全程留痕并支持手动一键恢复。

#### 8.3.2 整体链路

```
任务执行失败上报 → 失败检测（记录失败流水）→ 判断失败级别
    ├─ 轻微失败(retryCount < 3)   → 自动重试（指数退避）
    ├─ 中度失败(3<=retryCount<max) → 告警通知 + 尝试自动熔断恢复（切换节点/降级）
    └─ 重度失败(达到max或熔断恢复也失败) → P1告警 + 创建人工工单，等待手动恢复
                                                 └─ 手动恢复触发 → 重新执行 → 恢复结果回写
```

#### 8.3.3 失败检测与分级处理

```java
/**
 * 任务失败告警与自动恢复 - 失败检测入口
 * 所有任务执行失败均通过此入口统一上报，做分级处理
 */
@Component
public class JobFailureDetector {

    private static final Logger logger = LoggerFactory.getLogger(JobFailureDetector.class);

    @Autowired
    private JobFailureRecordRepository failureRecordRepository;
    @Autowired
    private JobAutoRecoveryService autoRecoveryService;
    @Autowired
    private AlertService alertService;
    @Autowired
    private ManualTicketService manualTicketService;

    private static final int LIGHT_FAILURE_THRESHOLD = 3;
    private static final int MAX_RETRY_COUNT = 8;

    /**
     * 失败上报入口：由执行节点/调度中心在任务执行失败时调用
     */
    public void reportFailure(JobInfo job, JobLog jobLog, String errorMsg, Throwable cause) {
        // 幂等控制：同一次执行(以jobLog.getExecutionId()为唯一键)的失败只记录一次流水，
        // 避免网络重试导致的重复上报造成失败计数虚高
        String failureRecordKey = "failure-" + jobLog.getExecutionId();
        if (failureRecordRepository.existsByRecordKey(failureRecordKey)) {
            logger.info("失败记录已存在，跳过重复上报: recordKey={}", failureRecordKey);
            return;
        }

        try {
            int consecutiveFailures = failureRecordRepository
                .countConsecutiveFailures(job.getId()) + 1;

            JobFailureRecord record = new JobFailureRecord();
            record.setRecordKey(failureRecordKey);
            record.setJobId(job.getId());
            record.setExecutionId(jobLog.getExecutionId());
            record.setErrorMsg(truncate(errorMsg, 2000));
            record.setStackTrace(cause == null ? null : truncate(ExceptionUtils.getStackTrace(cause), 4000));
            record.setConsecutiveFailures(consecutiveFailures);
            record.setCreateTime(new Date());
            record.setStatus(FailureStatus.DETECTED);
            failureRecordRepository.save(record);

            logger.error("检测到任务执行失败: jobId={}, jobDesc={}, consecutiveFailures={}, error={}",
                job.getId(), job.getDesc(), consecutiveFailures, errorMsg, cause);

            // 按失败级别分流处理
            dispatchByFailureLevel(job, record, consecutiveFailures);

        } catch (Exception e) {
            // 失败检测自身不能再抛异常导致告警链路中断，兜底记录到日志并直接触发P1告警
            logger.error("失败检测处理异常，直接触发兜底告警: jobId={}", job.getId(), e);
            alertService.alert(AlertLevel.P1,
                String.format("任务[%s]失败检测处理异常: %s", job.getDesc(), e.getMessage()));
        }
    }

    private void dispatchByFailureLevel(JobInfo job, JobFailureRecord record, int consecutiveFailures) {
        if (consecutiveFailures < LIGHT_FAILURE_THRESHOLD) {
            // 轻微失败：自动重试，不打扰人工
            scheduleAutoRetry(job, record, consecutiveFailures);

        } else if (consecutiveFailures < MAX_RETRY_COUNT) {
            // 中度失败：发出告警，同时尝试自动熔断恢复（如切换执行节点、降级参数）
            alertService.alert(AlertLevel.P2, String.format(
                "任务[%s]连续失败%d次，尝试自动恢复", job.getDesc(), consecutiveFailures));
            autoRecoveryService.tryAutoRecover(job, record);

        } else {
            // 重度失败：P1告警 + 创建人工工单，停止自动重试避免无效消耗资源
            record.setStatus(FailureStatus.ESCALATED);
            failureRecordRepository.update(record);

            alertService.alert(AlertLevel.P1, String.format(
                "任务[%s]连续失败%d次，已达上限，自动恢复停止，已创建人工工单",
                job.getDesc(), consecutiveFailures));

            String ticketId = manualTicketService.createTicket(job, record);
            logger.error("任务失败已升级为人工工单: jobId={}, ticketId={}", job.getId(), ticketId);
        }
    }

    private void scheduleAutoRetry(JobInfo job, JobFailureRecord record, int retryCount) {
        long delayMs = Math.min(2000L * (1L << retryCount), 120000L); // 指数退避，上限2分钟

        logger.info("安排自动重试: jobId={}, retryCount={}, delayMs={}", job.getId(), retryCount, delayMs);

        retryScheduler.schedule(() -> {
            try {
                ReturnT<String> result = jobExecutorClient.retryExecute(job, record.getExecutionId());
                if (result.getCode() == ReturnT.SUCCESS_CODE) {
                    onRecoverySuccess(job, record, "自动重试成功");
                } else {
                    logger.warn("自动重试仍然失败: jobId={}, msg={}", job.getId(), result.getMsg());
                    // 重试失败会再次进入execute的失败回调，由reportFailure统一继续分级处理
                }
            } catch (Exception e) {
                logger.error("自动重试执行异常: jobId={}", job.getId(), e);
            }
        }, delayMs, TimeUnit.MILLISECONDS);
    }

    /**
     * 恢复成功的统一收口：清理失败计数、更新记录状态、发送恢复通知
     */
    public void onRecoverySuccess(JobInfo job, JobFailureRecord record, String recoveryMethod) {
        record.setStatus(FailureStatus.RECOVERED);
        record.setRecoveryMethod(recoveryMethod);
        record.setRecoveryTime(new Date());
        failureRecordRepository.update(record);

        failureRecordRepository.resetConsecutiveFailureCounter(job.getId());

        logger.info("任务失败已恢复: jobId={}, method={}", job.getId(), recoveryMethod);
        alertService.alertRecovery(AlertLevel.P2, String.format(
            "任务[%s]已通过[%s]恢复正常", job.getDesc(), recoveryMethod));
    }

    private String truncate(String text, int maxLen) {
        if (text == null) return null;
        return text.length() > maxLen ? text.substring(0, maxLen) : text;
    }

    private final ScheduledExecutorService retryScheduler =
        Executors.newScheduledThreadPool(4, new ThreadFactoryBuilder()
            .setNameFormat("failure-retry-%d").build());

    @Autowired
    private JobExecutorClient jobExecutorClient;
}
```

#### 8.3.4 自动恢复策略与手动恢复入口

```java
/**
 * 自动恢复服务：针对中度失败尝试自动化恢复手段，恢复失败则交由检测器继续升级
 */
@Component
public class JobAutoRecoveryService {

    private static final Logger logger = LoggerFactory.getLogger(JobAutoRecoveryService.class);

    @Autowired
    private ExecutorRegistryRepository executorRepository;
    @Autowired
    private JobExecutorClient jobExecutorClient;
    @Autowired
    private JobFailureDetector failureDetector;
    @Autowired
    private JobFailureRecordRepository failureRecordRepository;

    /**
     * 自动恢复入口：依次尝试"切换健康节点重跑"和"降级参数重跑"两种手段
     */
    public void tryAutoRecover(JobInfo job, JobFailureRecord record) {
        // 幂等控制：同一条失败记录只允许发起一次自动恢复流程，避免并发告警回调重复触发恢复
        boolean locked = failureRecordRepository.tryLockForRecovery(record.getId());
        if (!locked) {
            logger.info("该失败记录已在自动恢复流程中，跳过: recordId={}", record.getId());
            return;
        }

        try {
            logger.info("开始自动恢复流程: jobId={}, recordId={}", job.getId(), record.getId());

            if (tryRecoverByFailover(job, record)) {
                return;
            }
            if (tryRecoverByDegrade(job, record)) {
                return;
            }

            logger.warn("自动恢复手段均未成功，等待失败计数继续累积以升级人工处理: jobId={}", job.getId());

        } catch (Exception e) {
            logger.error("自动恢复流程执行异常: jobId={}, recordId={}", job.getId(), record.getId(), e);
        } finally {
            failureRecordRepository.unlockRecovery(record.getId());
        }
    }

    /**
     * 恢复手段1：故障转移，切换到其他健康执行节点重新执行
     */
    private boolean tryRecoverByFailover(JobInfo job, JobFailureRecord record) {
        try {
            List<ExecutorInfo> healthyExecutors = executorRepository.findHealthyByGroup(job.getJobGroup());
            if (healthyExecutors.isEmpty()) {
                logger.warn("无健康节点可用于故障转移恢复: jobId={}", job.getId());
                return false;
            }

            ExecutorInfo target = healthyExecutors.get(0);
            logger.info("尝试故障转移恢复: jobId={}, targetExecutor={}", job.getId(), target.getAddress());

            ReturnT<String> result = jobExecutorClient.executeOn(target.getAddress(), job, record.getExecutionId());

            if (result.getCode() == ReturnT.SUCCESS_CODE) {
                failureDetector.onRecoverySuccess(job, record, "故障转移到" + target.getAddress());
                return true;
            }
            logger.warn("故障转移恢复未成功: jobId={}, msg={}", job.getId(), result.getMsg());
            return false;

        } catch (Exception e) {
            logger.error("故障转移恢复执行异常: jobId={}", job.getId(), e);
            return false;
        }
    }

    /**
     * 恢复手段2：降级参数重跑（如缩小批处理量、关闭非核心校验），提升成功概率
     */
    private boolean tryRecoverByDegrade(JobInfo job, JobFailureRecord record) {
        try {
            String degradedParam = buildDegradedParam(job.getParams());
            logger.info("尝试降级参数恢复: jobId={}, degradedParam={}", job.getId(), degradedParam);

            ReturnT<String> result = jobExecutorClient.retryExecuteWithParam(
                job, record.getExecutionId(), degradedParam);

            if (result.getCode() == ReturnT.SUCCESS_CODE) {
                failureDetector.onRecoverySuccess(job, record, "降级参数重跑");
                return true;
            }
            logger.warn("降级参数恢复未成功: jobId={}, msg={}", job.getId(), result.getMsg());
            return false;

        } catch (Exception e) {
            logger.error("降级参数恢复执行异常: jobId={}", job.getId(), e);
            return false;
        }
    }

    private String buildDegradedParam(String originalParam) {
        // 示例：将批处理大小降低为原来的一半，降低单次执行资源消耗与出错概率
        JSONObject json = JSON.parseObject(originalParam == null ? "{}" : originalParam);
        int batchSize = json.getIntValue("batchSize");
        json.put("batchSize", Math.max(batchSize / 2, 100));
        json.put("degraded", true);
        return json.toJSONString();
    }
}
```

```java
/**

@RestController

    @PostMapping("/manual/{recordId}")
    public ApiResponse<String> manualRecover(@PathVariable long recordId,
                                              @RequestParam String operator) {
        // 幂等控制：已处于恢复中或已恢复的记录不允许重复触发，防止运营人员重复点击导致任务并发执行
        JobFailureRecord record = failureRecordRepository.findById(recordId);
        if (record == null) {
            return ApiResponse.fail("失败记录不存在: " + recordId);
        }
        if (record.getStatus() == FailureStatus.RECOVERED) {
            return ApiResponse.fail("该记录已恢复，无需重复操作");
        }

        boolean locked = failureRecordRepository.tryLockForRecovery(recordId);
        if (!locked) {
            return ApiResponse.fail("该记录正在恢复中，请勿重复提交");
        }

        try {
            JobInfo job = jobInfoRepository.findById(record.getJobId());
            logger.info("人工触发手动恢复: recordId={}, jobId={}, operator={}",
                recordId, job.getId(), operator);

            ReturnT<String> result = jobExecutorClient.retryExecute(job, record.getExecutionId());

            if (result.getCode() == ReturnT.SUCCESS_CODE) {
                failureDetector.onRecoverySuccess(job, record, "人工手动恢复(operator=" + operator + ")");
                manualTicketService.closeTicket(record.getId(), operator, "手动恢复成功");
                return ApiResponse.success("手动恢复成功");
            } else {
                record.setLastManualRetryTime(new Date());
                record.setLastManualRetryOperator(operator);
                failureRecordRepository.update(record);
                logger.error("人工手动恢复执行仍然失败: recordId={}, msg={}", recordId, result.getMsg());
                return ApiResponse.fail("手动恢复执行失败: " + result.getMsg());
            }

        } catch (Exception e) {
            logger.error("手动恢复处理异常: recordId={}", recordId, e);
            return ApiResponse.fail("手动恢复处理异常: " + e.getMessage());
        } finally {
            failureRecordRepository.unlockRecovery(recordId);
        }
    }
}
```

#### 8.3.5 告警通知服务

```java
/**
 * 告警通知服务：统一告警出口，支持多渠道通知与告警恢复通知，内置去重防止告警风暴
 */
@Component
public class AlertService {

    private static final Logger logger = LoggerFactory.getLogger(AlertService.class);

    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private List<AlertChannel> alertChannels; // 大象机器人、邮件、短信等多渠道实现

    private static final String DEDUP_KEY_PREFIX = "alert:dedup:";
    private static final long DEDUP_WINDOW_SECONDS = 300; // 5分钟内相同告警去重

    public void alert(AlertLevel level, String message) {
        try {
            String dedupKey = DEDUP_KEY_PREFIX + DigestUtils.md5Hex(level + ":" + message);

            // 幂等/去重控制：相同级别+内容的告警5分钟内只发送一次，避免故障期间告警刷屏
            Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(dedupKey, "1", Duration.ofSeconds(DEDUP_WINDOW_SECONDS));

            if (Boolean.FALSE.equals(firstTime)) {
                logger.info("告警在去重窗口内，跳过重复发送: level={}, message={}", level, message);
                return;
            }

            logger.warn("触发告警: level={}, message={}", level, message);

            for (AlertChannel channel : alertChannels) {
                try {
                    channel.send(level, message);
                } catch (Exception e) {
                    // 单个渠道发送失败不影响其他渠道，记录日志即可
                    logger.error("告警渠道[{}]发送失败: message={}", channel.getName(), message, e);
                }
            }
        } catch (Exception e) {
            // 告警系统自身异常绝不能抛出影响主流程，只记录日志
            logger.error("告警发送流程异常: level={}, message={}", level, message, e);
        }
    }

    /**
     * 恢复通知：任务从失败状态恢复正常时调用，告知相关人员问题已解决
     */
    public void alertRecovery(AlertLevel level, String message) {
        try {
            logger.info("触发恢复通知: level={}, message={}", level, message);
            for (AlertChannel channel : alertChannels) {
                try {
                    channel.sendRecovery(level, message);
                } catch (Exception e) {
                    logger.error("恢复通知渠道[{}]发送失败: message={}", channel.getName(), message, e);
                }
            }
        } catch (Exception e) {
            logger.error("恢复通知发送流程异常: level={}, message={}", level, message, e);
        }
    }
}
```

#### 8.3.6 关键设计说明

- **失败检测**：以`jobLog.getExecutionId()`构造幂等键`failure-{executionId}`，确保同一次执行的失败只记录一条流水，避免网络重试或RPC超时导致的重复上报虚增失败计数。
- **分级重试策略**：按连续失败次数分为轻微（<3次，静默自动重试）、中度（3~8次，告警+自动熔断恢复）、重度（≥8次，P1告警+人工工单）三级，逐级升级处理，避免小故障也打扰人工，同时保证严重故障不会被自动重试掩盖。
- **自动恢复**：`tryLockForRecovery`对同一条失败记录加锁，防止并发触发多次恢复流程；依次尝试故障转移（切换执行节点）和参数降级（缩小批处理量）两种自动化手段，均失败则放弃自动恢复等待人工介入。
- **手动恢复**：管理控制台提供一键恢复入口，同样通过记录状态与分布式锁保证幂等，恢复成功后自动关闭人工工单并发送恢复通知，形成闭环。
- **告警通知**：所有告警统一经过`AlertService`出口，基于Redis `SETNX`实现5分钟窗口内的相同告警去重，避免故障期间产生告警风暴；恢复时发送独立的恢复通知，告知相关人员问题已解决，形成"检测-告警-恢复-通知"完整闭环。
