# 认证授权体系架构设计文档

## 一、问题背景

### 1.1 要解决的核心问题

任何一个多用户、多系统协作的软件平台，都必须回答两个基础性问题：**"你是谁"（认证）**和**"你能做什么"（授权）**。随着系统规模从单体演变为由几十上百个微服务组成的分布式体系，认证授权面临的核心问题也随之升级：

1. **重复登录与身份割裂问题**：企业内部往往同时存在多个业务系统（OA、CRM、财务系统等），如果每个系统都独立维护一套账号体系，用户需要在每个系统分别登录，且各系统之间的用户身份无法关联，体验割裂，也给账号安全管理带来隐患。
2. **第三方授权的安全边界问题**：当需要允许第三方应用访问用户在本平台上的部分数据（如允许一个第三方工具读取用户的日历），如果直接把用户的账号密码告知第三方应用，会造成密码泄露和权限失控的严重安全风险，必须有一套机制让用户在不暴露密码的前提下，精细化地控制第三方应用能访问的数据范围和时长。
3. **令牌被窃取后的风险控制问题**：认证凭证（Session、Token）一旦被窃取，攻击者就能冒充合法用户执行任意操作，如何设计令牌的生命周期管理机制（短期有效、可主动吊销、异常检测），最大程度降低令牌泄露造成的损失，是认证体系设计的核心挑战。
4. **精细化权限管理的复杂度问题**：企业级系统的权限需求远比"登录后即可访问所有功能"复杂得多，需要支持"不同角色看到不同菜单""不同人员只能操作自己部门的数据"等精细化的权限控制需求，且这些权限规则会随着组织架构调整频繁变化，如果权限判断逻辑散落在各处业务代码中会难以维护。
5. **多租户场景下的数据隔离问题**：SaaS 类产品需要服务多个独立的企业客户（租户），必须保证租户之间的数据和权限严格隔离，杜绝跨租户的数据泄露风险。

### 1.2 典型场景

- **企业级应用矩阵的统一登录**：员工登录一次即可无感访问企业内部所有授权的子系统，避免每个系统单独登录的体验割裂。
- **开放平台的第三方授权**：允许用户授权第三方应用读取自己在平台上的特定数据，同时保证用户可以随时查看和撤销已授予的授权。
- **企业后台管理系统的权限精细化管控**：不同岗位角色（超级管理员、部门主管、普通员工）能看到和操作的功能、数据范围完全不同，需要一套灵活的权限模型支撑复杂的组织架构。
- **SaaS 多租户平台**：同一套系统代码服务成百上千个独立企业客户，必须保证每个租户只能访问自己的数据，且各租户可以独立配置自己的角色权限体系。
- **金融、支付等高安全等级场景**：除了常规的账号密码认证外，还需要结合设备指纹、异地登录检测、二步验证等多重安全手段防范账号被盗用的风险。

### 1.3 不解决的后果

- **账号被盗用造成资损**：没有异地登录检测、暴力破解防护等机制，攻击者可以通过撞库攻击等手段轻易获取用户账号权限，进而造成资金损失或数据泄露。
- **权限管理混乱导致越权访问**：如果权限判断逻辑分散在各业务代码中且缺乏统一模型，极易出现"某个接口忘记加权限校验"的疏漏，造成敏感数据被越权访问的安全事故，这是安全审计中最常见也最严重的问题类型之一。
- **令牌无法吊销导致风险敞口持续**：一旦发现某个 Token 存在异常使用行为，如果系统不具备主动吊销能力，只能被动等待 Token 自然过期，这期间攻击者可以持续利用该 Token 造成损失。
- **多租户数据串号引发信任危机**：一旦发生跨租户数据泄露，不仅会造成直接的经济和法律责任，还会对平台的商业信誉造成难以挽回的打击。

## 二、整体架构设计

### 2.1 认证（Authentication）与授权（Authorization）的概念区分

这两个概念经常被混淆，但在架构设计上承担完全不同的职责：

- **认证**：回答"你是谁"的问题，验证用户身份的真实性，输出是一个可信的身份标识（如用户 ID）。
- **授权**：回答"你能做什么"的问题，基于已确认的身份，判断该身份是否有权限执行某个操作或访问某个资源。

两者是**先后依赖关系**：必须先完成认证确认身份，才能基于该身份进行授权判断。架构上通常也分层设计：

```
┌─────────────────────────────────────────────┐
│                客户端请求                     │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│  认证层：验证身份凭证（Token/Session）的合法性  │  回答"你是谁"，失败则直接拒绝（401）
└─────────────────────────────────────────────┘
        │  身份确认通过，携带身份信息继续
        ▼
┌─────────────────────────────────────────────┐
│  授权层：基于身份判断是否有权限访问目标资源      │  回答"你能做什么"，失败则拒绝（403）
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│                业务逻辑处理                    │
└─────────────────────────────────────────────┘
```

### 2.2 组件职责划分

| 组件 | 职责 |
|---|---|
| **身份提供方（Identity Provider, IdP）** | 统一管理用户账号、密码等身份凭证，提供登录认证能力 |
| **SSO 认证中心** | 统一处理多系统间的单点登录/登出，签发全局身份凭证 |
| **OAuth2 授权服务器** | 处理第三方应用的授权申请，签发访问令牌 |
| **权限管理中心** | 维护角色、权限、资源的定义和分配关系（RBAC模型） |
| **会话管理组件** | 管理用户会话的创建、续期、失效 |
| **风控组件** | 检测异常登录行为（暴力破解、异地登录、设备异常） |

### 2.3 设计权衡

- **有状态 Session vs 无状态 Token**：Session 依赖服务端存储会话状态，适合内部系统、对安全性要求高于扩展性的场景；Token（尤其是 JWT）自包含身份信息，适合分布式、跨域、对水平扩展要求高的场景，但牺牲了主动吊销的便利性。
- **认证凭证的有效期设置**：过短的有效期会频繁打断用户操作，影响体验；过长的有效期会放大凭证泄露后的风险敞口，需要结合业务安全等级和用户体验诉求综合权衡，通常通过双 Token 机制（短期访问凭证+长期刷新凭证）折中。
- **权限模型的粒度**：过粗的权限粒度（如只能按整个模块开关权限）无法满足精细化管控需求；过细的权限粒度（如按字段级别控制）会带来管理和维护的复杂度爆炸，需要根据实际业务需求选择合适的粒度层级。

## 三、核心链路设计

### 3.1 SSO 单点登录完整原理

单点登录（Single Sign-On）解决的核心问题是：用户在多个系统组成的应用矩阵中，只需要登录一次，即可无感访问所有互相信任的系统。

#### 3.1.1 方案一：基于 Cookie 的 SSO（适用于同域或可控制 Cookie 域的场景）

```java
// 将SSO认证中心和各业务子系统部署在同一顶级域名下的不同子域（如sso.example.com, app1.example.com）
// 通过设置Cookie的Domain属性为顶级域（.example.com），使其在所有子域下均可被读取
@RestController
public class SsoLoginController {

    @PostMapping("/sso/login")
    public ResponseEntity<Void> login(@RequestBody LoginRequest request, HttpServletResponse response) {
        User user = authenticate(request.getUsername(), request.getPassword());
        String sessionId = sessionService.createSession(user.getId());

        Cookie ssoCookie = new Cookie("SSO_SESSION_ID", sessionId);
        ssoCookie.setDomain(".example.com"); // 关键：设置为顶级域，所有子域共享该Cookie
        ssoCookie.setHttpOnly(true);          // 防止XSS窃取Cookie
        ssoCookie.setSecure(true);            // 仅通过HTTPS传输
        ssoCookie.setMaxAge(7200);
        response.addCookie(ssoCookie);
        return ResponseEntity.ok().build();
    }
}
```

这种方案实现简单，但局限性明显：只适用于所有系统共享同一顶级域名的场景，无法支持完全不同域名的系统间单点登录（如 `a.com` 和 `b.com` 之间），且强依赖浏览器 Cookie 机制，不适合 App 等非浏览器客户端场景。

#### 3.1.2 方案二：基于中心化 Token 校验的 SSO

各子系统不直接管理用户凭证，而是统一将客户端携带的 Token 转发给 SSO 中心校验，SSO 中心是唯一的身份权威来源：

```java
// 各业务子系统的统一认证拦截器，将Token校验委托给中心化的SSO服务
@Component
public class SsoAuthInterceptor implements HandlerInterceptor {

    private final SsoServiceClient ssoServiceClient; // 调用独立部署的SSO认证中心

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String token = extractToken(request);
        if (token == null) {
            redirectToSsoLogin(response, request.getRequestURL().toString());
            return false;
        }
        // 业务子系统不直接维护用户身份数据，每次请求都委托SSO中心验证Token合法性
        UserPrincipal principal = ssoServiceClient.validateToken(token);
        if (principal == null) {
            redirectToSsoLogin(response, request.getRequestURL().toString());
            return false;
        }
        UserContextHolder.set(principal); // 将身份信息放入当前请求上下文，供后续业务逻辑使用
        return true;
    }

    private void redirectToSsoLogin(HttpServletResponse response, String returnUrl) throws IOException {
        response.sendRedirect("https://sso.example.com/login?redirect=" + URLEncoder.encode(returnUrl, "UTF-8"));
    }
}
```

#### 3.1.3 方案三：基于授权码模式的 SSO（跨域场景的标准方案）

这是最通用、最能应对完全不同域名系统间单点登录的方案，本质上是 OAuth2 授权码模式在企业内部身份场景的应用。完整流程如下：

```
1. 用户访问业务系统A（app1.example.com）的受保护页面，A发现本地没有有效会话
2. A将用户浏览器重定向到SSO认证中心（sso.example.com），并携带自己的回调地址redirect_uri
3. 用户在SSO认证中心完成登录（如果SSO中心已有该用户的全局会话，此步骤自动跳过，用户无感）
4. SSO认证中心生成一次性的授权码（Authorization Code），重定向回A的回调地址，并附带该授权码
5. 业务系统A的后端拿着授权码，直接向SSO认证中心的后端服务发起请求（服务器间通信，不经过浏览器），换取访问令牌
6. SSO认证中心验证授权码有效性后，返回访问令牌（及用户身份信息）
7. A使用该访问令牌为当前用户建立本地会话，后续该用户在A系统内的请求都基于本地会话验证
8. 用户访问业务系统B时，重复步骤2-3，由于SSO中心已存在全局会话（通过SSO中心自己域下的Cookie维持），用户无需重新输入账号密码，直接跳转到步骤4，实现单点登录的无感体验
```

```java
// SSO认证中心：处理授权码的生成
@RestController
public class SsoAuthorizationController {

    @GetMapping("/sso/authorize")
    public void authorize(@RequestParam String clientId, @RequestParam String redirectUri,
                            HttpServletRequest request, HttpServletResponse response) throws IOException {
        String globalSessionId = extractGlobalSession(request);
        if (globalSessionId == null || !sessionService.isValid(globalSessionId)) {
            // 全局会话不存在或已过期，引导用户完成登录
            response.sendRedirect("/sso/login-page?clientId=" + clientId + "&redirectUri=" + redirectUri);
            return;
        }
        // 全局会话有效，说明用户已经在SSO中心登录过，直接签发一次性授权码，用户全程无感
        String userId = sessionService.getUserId(globalSessionId);
        String authCode = authCodeService.generate(userId, clientId); // 授权码通常一次性、短时效（如60秒）
        response.sendRedirect(redirectUri + "?code=" + authCode);
    }
}

// SSO认证中心：处理授权码换取访问令牌的服务器间请求
@RestController
public class SsoTokenController {

    @PostMapping("/sso/token")
    public TokenResponse exchangeToken(@RequestParam String code, @RequestParam String clientId,
                                         @RequestParam String clientSecret) {
        // 校验clientId和clientSecret，确保是合法注册的业务子系统在发起换取请求，而非任意第三方
        if (!clientService.verify(clientId, clientSecret)) {
            throw new UnauthorizedException("invalid client credentials");
        }
        String userId = authCodeService.consumeAndGetUserId(code, clientId); // 授权码一次性消费，防止重放
        if (userId == null) {
            throw new UnauthorizedException("invalid or expired authorization code");
        }
        String accessToken = tokenService.generateAccessToken(userId);
        return new TokenResponse(accessToken, userService.getUserInfo(userId));
    }
}

// 业务子系统A：接收授权码回调，向SSO中心换取访问令牌并建立本地会话
@RestController
public class SsoCallbackController {

    @GetMapping("/sso/callback")
    public ResponseEntity<Void> callback(@RequestParam String code, HttpServletResponse response) {
        // 关键安全设计：这一步是服务器到服务器的直接调用，授权码不经过浏览器暴露给中间环节
        TokenResponse tokenResponse = ssoServiceClient.exchangeToken(code, LOCAL_CLIENT_ID, LOCAL_CLIENT_SECRET);
        String localSessionId = localSessionService.create(tokenResponse.getUserInfo());

        Cookie localCookie = new Cookie("APP1_SESSION_ID", localSessionId);
        localCookie.setHttpOnly(true);
        response.addCookie(localCookie);
        return ResponseEntity.status(HttpStatus.FOUND).header("Location", "/dashboard").build();
    }
}
```

**这套流程为什么是安全的**：授权码本身生命周期极短（通常 30~60 秒）且一次性有效（消费后立即失效），即使在浏览器重定向过程中被截获，攻击者也很难在有效期内完成利用；更关键的是，"授权码换取访问令牌"这一步是**服务器与服务器之间的直接通信**（不经过用户浏览器），需要业务子系统提供预先注册好的 `clientSecret` 作为身份凭证，这就杜绝了授权码即使泄露也无法被非授权的第三方直接兑换为访问令牌的风险，是纵深防御思想的典型体现。

### 3.2 OAuth2.0 四种授权模式详解

OAuth2.0 是行业标准的授权框架，核心思想是让用户能够授权第三方应用访问自己在资源服务器上的部分数据，而无需将账号密码直接暴露给第三方应用。其核心角色包括：**资源所有者**（用户）、**客户端**（第三方应用）、**授权服务器**（颁发令牌）、**资源服务器**（存储受保护数据）。

#### 3.2.1 授权码模式（Authorization Code Grant）

前文 SSO 方案三描述的流程本质上就是授权码模式。这是**安全性最高、最推荐用于有后端服务器的 Web 应用**的模式，因为访问令牌的获取过程完全在服务器端完成，不会暴露给浏览器端的 JavaScript 代码。适用场景：拥有后端服务的第三方 Web 应用需要访问用户数据。

#### 3.2.2 隐式授权模式（Implicit Grant）

授权服务器直接将访问令牌通过浏览器重定向的 URL 片段（Fragment）返回给客户端，不经过授权码这个中间步骤，也不需要客户端提供 `clientSecret`（因为纯前端应用无法安全保管密钥）。

```
用户授权后，浏览器被重定向到：
https://client-app.com/callback#access_token=xxx&token_type=bearer&expires_in=3600
```

**安全分析**：由于访问令牌直接暴露在浏览器的 URL 中（可能被浏览器历史记录、第三方 JS 脚本、Referer 头等途径窃取），且无法使用 Refresh Token（因为没有安全的服务器端存储密钥的能力），安全性明显低于授权码模式。OAuth 2.1 规范已经明确废弃了这一模式，推荐即使是纯前端应用也应该使用"授权码模式 + PKCE（Proof Key for Code Exchange）扩展"来替代，PKCE 通过客户端生成一次性的随机校验码参与授权码交换过程，弥补了纯前端应用无法安全存储 `clientSecret` 的短板。

#### 3.2.3 密码模式（Resource Owner Password Credentials Grant）

用户直接将账号密码提供给客户端，客户端使用该密码向授权服务器换取访问令牌：

```java
public class PasswordGrantClient {
    public TokenResponse getToken(String username, String password) {
        // 客户端直接持有用户的账号密码，这与OAuth2"避免密码直接暴露给第三方"的核心设计初衷相悖
        Map<String, String> params = new HashMap<>();
        params.put("grant_type", "password");
        params.put("username", username);
        params.put("password", password);
        params.put("client_id", CLIENT_ID);
        return httpClient.post("/oauth/token", params);
    }
}
```

**安全分析**：这种模式要求用户完全信任客户端应用（因为密码直接经过客户端），只适用于客户端本身就是高度受信任的第一方应用（如企业自己开发的官方 App 需要对接自己的授权服务器），**绝不应该用于第三方应用的授权场景**，这与 OAuth2 "无需暴露密码给第三方"的核心设计目标是矛盾的，业界普遍建议尽量避免使用此模式。

#### 3.2.4 客户端凭证模式（Client Credentials Grant）

不涉及用户身份，客户端使用自己的身份（`clientId` + `clientSecret`）直接向授权服务器申请令牌，用于访问客户端自己拥有的资源而非代表某个用户访问数据：

```java
public class ClientCredentialsGrantClient {
    public TokenResponse getToken() {
        Map<String, String> params = new HashMap<>();
        params.put("grant_type", "client_credentials");
        params.put("client_id", CLIENT_ID);
        params.put("client_secret", CLIENT_SECRET);
        return httpClient.post("/oauth/token", params); // 获得的令牌代表客户端本身，而非某个具体用户
    }
}
```

**适用场景**：机器对机器（Machine-to-Machine）的场景，如后台定时任务调用开放平台接口同步数据，不存在真实用户参与授权的交互过程。

#### 3.2.5 四种模式的选型建议

| 模式 | 安全性 | 适用场景 |
|---|---|---|
| 授权码模式（+PKCE） | 高 | 有后端的 Web 应用、需要 PKCE 增强的移动端/单页应用，是当前推荐的主流方案 |
| 隐式授权模式 | 低（已废弃） | 历史遗留的纯前端应用场景，新项目不应再采用 |
| 密码模式 | 中（要求高度信任客户端） | 仅限第一方官方客户端，不适用于真正的第三方授权场景 |
| 客户端凭证模式 | 高（但不涉及用户身份） | 服务间机器对机器的调用，无用户参与的场景 |

### 3.3 JWT Token 设计与生命周期管理

#### 3.3.1 JWT 结构详解

JWT 由三段组成，用点号分隔：`Header.Payload.Signature`。

```java
public class JwtDeepDiveDemo {

    public String issueToken(String userId, List<String> roles, String tenantId) {
        // Header部分（Base64URL编码后成为Token第一段）：{"alg":"HS256","typ":"JWT"}
        // Payload部分（Base64URL编码后成为Token第二段）：携带标准声明和自定义业务声明
        Map<String, Object> claims = new HashMap<>();
        claims.put("roles", roles);
        claims.put("tenantId", tenantId); // 多租户场景下必须携带租户标识，供后续所有数据访问做隔离过滤

        return Jwts.builder()
                .setClaims(claims)
                .setSubject(userId)                                    // sub: 主体标识
                .setIssuer("auth.example.com")                         // iss: 签发者
                .setIssuedAt(new Date())                                // iat: 签发时间
                .setExpiration(Date.from(Instant.now().plus(30, ChronoUnit.MINUTES))) // exp: 过期时间
                .setId(UUID.randomUUID().toString())                    // jti: Token唯一ID，配合黑名单机制使用
                // Signature部分（Token第三段）：对前两段的Base64URL编码结果做HMAC-SHA256摘要，防止内容被篡改
                .signWith(SignatureAlgorithm.HS256, getSigningKey())
                .compact();
    }
}
```

需要特别强调：**Payload 部分只是 Base64URL 编码，任何拿到 Token 的人都可以直接解码查看其中内容，这不是加密**。Signature 部分的作用是防止 Payload 内容被篡改（篡改后签名校验会失败），而不是防止内容被窥探。因此绝对不能在 Payload 中存放密码、身份证号等真正敏感的信息。

#### 3.3.2 Token 生命周期管理：颁发、刷新、吊销、黑名单

```java
@Service
public class TokenLifecycleService {

    private final StringRedisTemplate redisTemplate;

    // 颁发：生成Access Token + Refresh Token双令牌对
    public TokenPair issue(String userId) {
        String accessToken = generateAccessToken(userId);
        String refreshToken = UUID.randomUUID().toString();
        redisTemplate.opsForValue().set("refresh:" + refreshToken, userId, 30, TimeUnit.DAYS);
        return new TokenPair(accessToken, refreshToken);
    }

    // 刷新：Refresh Token轮换机制，每次刷新后旧的Refresh Token立即失效
    public TokenPair refresh(String oldRefreshToken) {
        String userId = redisTemplate.opsForValue().get("refresh:" + oldRefreshToken);
        if (userId == null) {
            throw new UnauthorizedException("refresh token invalid or expired");
        }
        redisTemplate.delete("refresh:" + oldRefreshToken); // 旧token立即作废，缩小被截获重用的风险窗口
        return issue(userId); // 签发全新的一对Token
    }

    // 吊销：主动使某个Token失效（如用户主动登出、检测到账号异常）
    public void revoke(String accessToken) {
        Claims claims = parseTokenClaims(accessToken);
        String jti = claims.getId();
        long remainingTtl = claims.getExpiration().getTime() - System.currentTimeMillis();
        if (remainingTtl > 0) {
            // 将Token的jti加入黑名单，黑名单的过期时间设置为Token本身的剩余有效期，到期后黑名单记录自动清理
            redisTemplate.opsForValue().set("blacklist:" + jti, "1", remainingTtl, TimeUnit.MILLISECONDS);
        }
    }

    // 校验：验证签名有效性的同时，还要检查是否命中黑名单
    public boolean isValid(String accessToken) {
        try {
            Claims claims = parseTokenClaims(accessToken); // 内部会自动校验签名和exp
            String jti = claims.getId();
            Boolean isBlacklisted = redisTemplate.hasKey("blacklist:" + jti);
            return !Boolean.TRUE.equals(isBlacklisted);
        } catch (JwtException e) {
            return false;
        }
    }
}
```

**JWT 自包含特性与主动吊销能力之间的矛盾及解决方案**：JWT 的设计初衷是无状态验证（不查数据库/缓存即可验证签名合法性），但这与"需要支持用户主动登出、异常账号紧急封禁"这类主动吊销需求天然冲突。业界的实践折中方案是引入一张轻量级的黑名单（只存储被吊销 Token 的 `jti` 和剩余有效期，而非完整会话状态），在牺牲一部分"完全无状态"纯粹性的前提下，获得了主动吊销的能力，同时因为 Access Token 本身有效期较短，黑名单的数据量和存活时间都被限制在一个可控范围内，不会退化成传统 Session 那样需要为每个在线用户长期维护状态。

### 3.4 RBAC 权限模型设计

#### 3.4.1 用户-角色-权限-资源四元组模型

RBAC（Role-Based Access Control，基于角色的访问控制）的核心思想是在"用户"和"权限"之间引入"角色"这一层间接层，避免直接给每个用户单独分配权限带来的管理复杂度爆炸。

```
用户（User）  ──分配──>  角色（Role）  ──拥有──>  权限（Permission）  ──作用于──>  资源（Resource）
   张三              部门主管                查看报表                    财务报表模块
   李四              普通员工                提交申请                    请假申请功能
```

```java
// 核心数据模型
public class User {
    private Long id;
    private String username;
    private List<Long> roleIds; // 用户与角色多对多关联
}

public class Role {
    private Long id;
    private String name;        // 如"部门主管"
    private List<Long> permissionIds; // 角色与权限多对多关联
}

public class Permission {
    private Long id;
    private String code;        // 权限唯一标识，如"report:finance:view"
    private String resourceType; // 权限作用的资源类型，如"menu"、"button"、"api"
    private String resourceId;   // 具体资源标识
}
```

#### 3.4.2 权限校验的 Java 实现

```java
@Service
public class PermissionCheckService {

    private final RoleRepository roleRepository;
    private final PermissionRepository permissionRepository;

    // 核心校验逻辑：用户 -> 角色集合 -> 权限集合的两跳查询（生产环境应缓存该结果，避免每次请求都做多表关联查询）
    public boolean hasPermission(Long userId, String permissionCode) {
        Set<String> userPermissionCodes = getUserPermissionCodes(userId);
        return userPermissionCodes.contains(permissionCode);
    }

    @Cacheable(value = "userPermissions", key = "#userId") // 权限数据变化不频繁，适合缓存，配合角色变更时主动失效缓存
    public Set<String> getUserPermissionCodes(Long userId) {
        List<Role> roles = roleRepository.findRolesByUserId(userId);
        Set<String> permissionCodes = new HashSet<>();
        for (Role role : roles) {
            List<Permission> permissions = permissionRepository.findByRoleId(role.getId());
            permissionCodes.addAll(permissions.stream().map(Permission::getCode).collect(Collectors.toSet()));
        }
        return permissionCodes;
    }
}

// 基于注解的声明式权限校验，业务代码无需重复编写权限判断逻辑
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequirePermission {
    String value();
}

@Aspect
@Component
public class PermissionCheckAspect {

    private final PermissionCheckService permissionCheckService;

    @Before("@annotation(requirePermission)")
    public void checkPermission(JoinPoint joinPoint, RequirePermission requirePermission) {
        Long userId = UserContextHolder.getCurrentUserId();
        if (!permissionCheckService.hasPermission(userId, requirePermission.value())) {
            throw new ForbiddenException("insufficient permission: " + requirePermission.value());
        }
    }
}

// 业务代码中的使用方式非常简洁，权限声明与业务逻辑清晰分离

    @RequirePermission("report:finance:view")
```

#### 3.4.3 权限树与权限继承

企业级系统的权限通常呈现树状层级结构（模块 → 子模块 → 具体操作），高层级角色应能自动继承其下所有子权限，避免逐条勾选带来的管理负担：

```java
public class PermissionTreeNode {
    private Long id;
    private String code;
    private String name;
    private List<PermissionTreeNode> children = new ArrayList<>();
}

@Service
public class PermissionTreeService {

    // 递归展开权限树：为角色勾选一个父节点权限时，自动包含其所有子节点权限
    public Set<Long> expandPermissionIds(Long selectedPermissionId) {
        PermissionTreeNode node = permissionTreeRepository.findById(selectedPermissionId);
        Set<Long> result = new HashSet<>();
        collectAllDescendants(node, result);
        return result;
    }

    private void collectAllDescendants(PermissionTreeNode node, Set<Long> result) {
        result.add(node.getId());
        for (PermissionTreeNode child : node.getChildren()) {
            collectAllDescendants(child, result); // 递归收集所有子孙节点
        }
    }
}
```

权限树的另一个重要应用场景是**数据权限的范围继承**：如"部门主管"角色的数据权限范围是"本部门及所有下级部门"，需要结合组织架构树进行范围计算，而非简单的角色-权限二元关系能够表达，这类场景通常需要在 RBAC 基础模型之上叠加"数据权限"这一独立维度（区分"功能权限"——能否看到某个菜单/按钮，与"数据权限"——能看到哪些范围的数据）。

### 3.5 多租户权限隔离方案

#### 3.5.1 三种隔离方案对比

| 方案 | 隔离强度 | 成本 | 适用场景 |
|---|---|---|---|
| **独立数据库** | 最强，物理隔离 | 高（每租户一套数据库实例，运维成本随租户数线性增长） | 大型企业客户，对数据隔离和合规性要求极高 |
| **共享数据库、独立 Schema** | 较强，逻辑隔离但物理资源共享 | 中 | 中等规模租户，兼顾隔离性与成本 |
| **共享数据库、行级隔离（租户 ID 字段区分）** | 较弱，依赖应用层严格执行过滤 | 低，扩展性最好 | 大量中小租户的 SaaS 平台，是当前最主流的方案 |

#### 3.5.2 行级隔离的 Java 实现

```java
// 所有涉及租户数据的表都包含tenant_id字段，通过统一的拦截机制强制在每条SQL中自动附加租户过滤条件
@Component
public class TenantContext {
    private static final ThreadLocal<String> CURRENT_TENANT = new ThreadLocal<>();

    public static void setTenantId(String tenantId) {
        CURRENT_TENANT.set(tenantId);
    }

    public static String getTenantId() {
        return CURRENT_TENANT.get();
    }

    public static void clear() {
        CURRENT_TENANT.remove(); // 请求结束后必须清理，避免线程池复用导致租户信息串号——这是多租户系统最容易忽视也最危险的疏漏
    }
}

// MyBatis拦截器：在SQL执行前自动注入租户过滤条件，从基础设施层面兜底，避免业务开发遗忘手写租户过滤条件
@Intercepts({@Signature(type = Executor.class, method = "query",
        args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class})})
public class TenantIsolationInterceptor implements Interceptor {

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        MappedStatement ms = (MappedStatement) invocation.getArgs()[0];
        BoundSql boundSql = ms.getBoundSql(invocation.getArgs()[1]);
        String originalSql = boundSql.getSql();

        String tenantId = TenantContext.getTenantId();
        if (tenantId == null) {
            throw new IllegalStateException("tenant context missing, refuse to execute query without tenant scope");
        }
        // 自动在WHERE子句中注入tenant_id过滤条件，业务代码无需在每个Mapper方法中手写该条件，杜绝遗漏风险
        String tenantScopedSql = appendTenantCondition(originalSql, tenantId);
        // ... 反射修改boundSql的sql字段为tenantScopedSql，实际实现依赖具体ORM框架的拦截器API
        return invocation.proceed();
    }
}
```

**行级隔离方案的核心风险与应对**：这种方案的隔离强度完全依赖应用层代码是否严格执行了租户过滤，一旦某个查询遗漏了 `tenant_id` 条件（哪怕只有一处代码疏漏），就可能导致跨租户数据泄露这一严重安全事故。因此生产实践中**不能依赖开发人员自觉在每个 SQL 中手写租户过滤条件**，而应该通过统一的 ORM 拦截器/AOP 机制在基础设施层面强制注入，从架构层面杜绝人为疏漏的可能性，这是"默认安全"设计原则在多租户场景下的具体应用。

### 3.6 会话管理架构

#### 3.6.1 分布式 Session 方案

传统单机 Session 存储在应用服务器本地内存，多实例部署场景下会出现"用户请求被路由到不同实例导致会话丢失"的问题。分布式 Session 将会话数据集中存储在共享的缓存/存储介质中：

```java
@Service
public class DistributedSessionService {

    private final StringRedisTemplate redisTemplate;
    private static final long SESSION_TTL_SECONDS = 1800;

    public String createSession(UserPrincipal principal) {
        String sessionId = UUID.randomUUID().toString();
        redisTemplate.opsForValue().set("session:" + sessionId,
                JsonUtils.toJson(principal), SESSION_TTL_SECONDS, TimeUnit.SECONDS);
        return sessionId;
    }

    public UserPrincipal getSession(String sessionId) {
        String json = redisTemplate.opsForValue().get("session:" + sessionId);
        if (json != null) {
            // 访问时自动续期，实现"活跃用户持续保持登录状态，长期不活跃则自然过期"的滑动过期语义
            redisTemplate.expire("session:" + sessionId, SESSION_TTL_SECONDS, TimeUnit.SECONDS);
            return JsonUtils.fromJson(json, UserPrincipal.class);
        }
        return null;
    }
}
```

#### 3.6.2 Session 粘滞（Sticky Session）vs Session 复制

- **Session 粘滞**：负载均衡器根据某种规则（如源 IP 哈希、Cookie 标识）将同一用户的所有请求固定路由到同一台应用服务器，该服务器本地保存 Session 即可正常工作。优点是实现简单、无需额外存储；缺点是该服务器一旦宕机会导致其上所有用户的会话丢失，且负载均衡的均匀性会受到影响（长期活跃用户可能集中在少数几台机器上）。
- **Session 复制**：应用服务器集群之间互相同步 Session 数据，任意一台服务器都持有全量 Session 副本。优点是任意节点故障不影响其他节点服务能力；缺点是节点数量增多时，同步流量呈平方级增长，扩展性差，目前已较少采用。
- **分布式 Session（集中存储）**：目前的主流方案，应用服务器本身无状态，Session 数据集中存储在 Redis 等外部存储中，兼顾了高可用（任意应用节点故障不影响会话）和良好的水平扩展性，是当前分布式架构下的推荐方案。

### 3.7 安全防护体系

#### 3.7.1 暴力破解防护

```java
@Service
public class LoginSecurityService {

    private final StringRedisTemplate redisTemplate;
    private static final int MAX_FAILED_ATTEMPTS = 5;
    private static final long LOCK_DURATION_MINUTES = 15;

    public void recordFailedAttempt(String username) {
        String key = "login:failed:" + username;
        Long failCount = redisTemplate.opsForValue().increment(key);
        if (failCount == 1) {
            redisTemplate.expire(key, 30, TimeUnit.MINUTES); // 失败计数窗口
        }
        if (failCount >= MAX_FAILED_ATTEMPTS) {
            // 连续失败次数超过阈值，锁定账号一段时间，防止暴力破解穷举密码
            redisTemplate.opsForValue().set("login:locked:" + username, "1", LOCK_DURATION_MINUTES, TimeUnit.MINUTES);
        }
    }

    public boolean isLocked(String username) {
        return Boolean.TRUE.equals(redisTemplate.hasKey("login:locked:" + username));
    }

    public void clearFailedAttempts(String username) {
        redisTemplate.delete("login:failed:" + username); // 登录成功后清除失败计数
    }
}
```

登录接口还应结合验证码机制（连续失败若干次后强制要求图形/短信验证码）和 IP 维度的限流，多重手段组合应对暴力破解和撞库攻击。

#### 3.7.2 设备指纹与异地登录检测

```java
@Service
public class AbnormalLoginDetectionService {

    public RiskLevel assessLoginRisk(String userId, LoginContext context) {
        LoginHistory lastLogin = loginHistoryRepository.findLatest(userId);
        if (lastLogin == null) {
            return RiskLevel.NORMAL; // 首次登录，暂无历史基线可比对
        }

        int riskScore = 0;
        // 设备指纹变化：与历史常用设备指纹不匹配，说明可能是新设备或被盗用
        if (!context.getDeviceFingerprint().equals(lastLogin.getDeviceFingerprint())) {
            riskScore += 30;
        }
        // 地理位置异常：短时间内地理位置发生了物理上不可能达到的跳变（如1小时内从北京跳转到境外）
        double distanceKm = GeoUtils.calculateDistance(lastLogin.getLocation(), context.getLocation());
        long hoursSinceLastLogin = Duration.between(lastLogin.getLoginTime(), LocalDateTime.now()).toHours();
        double maxPossibleSpeedKmh = 900; // 民航飞机大致速度作为合理性判断基线
        if (hoursSinceLastLogin > 0 && distanceKm / hoursSinceLastLogin > maxPossibleSpeedKmh) {
            riskScore += 50;
        }
        // 登录时段异常：与用户历史活跃时段差异明显（如惯常白天活跃的用户在凌晨3点登录）
        if (isUnusualLoginTime(userId, LocalDateTime.now())) {
            riskScore += 20;
        }

        if (riskScore >= 50) {
            return RiskLevel.HIGH;   // 高风险，触发二步验证或直接拦截
        } else if (riskScore >= 30) {
            return RiskLevel.MEDIUM; // 中风险，触发短信/邮件通知用户核实
        }
        return RiskLevel.NORMAL;
    }
}
```

#### 3.7.3 二步验证（2FA）

```java
@Service
public class TwoFactorAuthService {

    // 基于TOTP（Time-based One-Time Password）算法生成动态验证码，与Google Authenticator等标准App兼容
    public boolean verifyTotpCode(String secretKey, String userInputCode) {
        long currentTimeWindow = System.currentTimeMillis() / 1000 / 30; // 30秒为一个时间窗口
        // 允许当前窗口及前后各一个窗口的时间误差容忍，应对客户端与服务端的时钟轻微不同步
        for (long window = currentTimeWindow - 1; window <= currentTimeWindow + 1; window++) {
            String expectedCode = generateTotpCode(secretKey, window);
            if (expectedCode.equals(userInputCode)) {
                return true;
            }
        }
        return false;
    }

    private String generateTotpCode(String secretKey, long timeWindow) {
        // 基于HMAC-SHA1对时间窗口值做摘要运算，再从摘要结果中动态截取生成6位数字验证码（RFC 6238标准算法）
        // 具体实现略，核心是secretKey与timeWindow的组合摘要结果具有不可预测性和时效性
        return TotpAlgorithm.generate(secretKey, timeWindow);
    }
}
```

风险检测（3.7.2）与二步验证（3.7.3）通常组合使用，形成风险自适应的认证策略：正常场景下用户只需账号密码即可登录，一旦风控系统判定当前登录行为存在中高风险特征，则动态提升验证要求（触发短信验证码或 TOTP 二次验证），在安全性和用户体验之间取得平衡，而非对所有登录场景一律要求二步验证（会造成不必要的体验负担）。

## 四、异常处理与容错机制

### 4.1 认证失败的统一处理

```java
@RestControllerAdvice
public class AuthExceptionHandler {

```

### 4.2 授权服务器的容灾降级

SSO 认证中心和 OAuth2 授权服务器是整个系统的单点信任源，一旦不可用会导致所有依赖它的业务系统无法完成登录，因此必须具备高可用设计：

- **多机房部署 + 本地缓存兜底**：业务子系统对已验证通过的 Token 结果进行短时间本地缓存，即使认证中心短暂不可用，已登录用户的后续请求仍可基于缓存结果正常访问（但新增登录请求会受影响）。
- **Token 校验的降级策略**：对于 JWT 这类自包含 Token，签名校验本身不依赖认证中心在线（只依赖预先分发的公钥/密钥），即使认证中心整体不可用，业务服务依然可以独立完成签名校验，只是无法查询黑名单（可根据业务安全等级决定黑名单校验失败时是放行还是拒绝）。

### 4.3 权限数据变更的一致性

角色权限调整后，已经登录的用户可能仍持有反映旧权限的缓存或 Token，需要考虑：

- **权限缓存的主动失效**：角色权限变更时，应主动清除相关用户的权限缓存（而非被动等待 TTL 过期），确保权限收紧类的变更能够尽快生效，避免权限降级不及时导致的越权访问风险。
- **权限信息不建议直接编码进长期有效的 Token 中**：如果权限列表直接写入 JWT Payload，一旦权限被收回，在 Token 过期之前用户依然持有旧权限（因为 JWT 内容一旦签发不可更改），更稳妥的做法是 Token 只携带身份标识，权限信息通过实时查询（配合短 TTL 缓存）获取，保证权限变更的时效性。

### 4.4 多租户上下文丢失的兜底

```java
// 请求入口处统一设置租户上下文，并在finally中强制清理，防止线程池复用导致的上下文串号
public class TenantContextFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        String tenantId = extractTenantId((HttpServletRequest) request);
        if (tenantId == null) {
            // 默认拒绝而非默认放行，杜绝因租户上下文缺失导致的查询"误命中"全量数据的风险
            ((HttpServletResponse) response).sendError(HttpStatus.BAD_REQUEST.value(), "tenant context required");
            return;
        }
        TenantContext.setTenantId(tenantId);
        try {
            chain.doFilter(request, response);
        } finally {
            TenantContext.clear(); // 无论成功失败都必须清理，这是多租户系统的生命线
        }
    }
}
```

## 五、性能优化

### 5.1 权限校验的性能优化

- **多级缓存**：用户权限数据变化频率低但读取频率极高，是典型的适合缓存的场景，可采用"本地缓存（Caffeine，亚毫秒级）+ 分布式缓存（Redis，毫秒级）"两级缓存架构，本地缓存设置较短的 TTL 并配合分布式缓存的主动失效通知，兼顾性能和一致性。
- **权限预计算**：对于组织架构复杂、数据权限范围计算开销较大的场景（如需要遍历组织树计算某个角色能看到哪些部门的数据），可以在角色权限变更时异步预计算并缓存最终结果，而非每次请求都实时递归计算。

### 5.2 JWT 校验的性能优化

- **本地验签，避免每次请求都远程调用认证中心**：JWT 的自包含特性使得签名验证可以完全在本地完成（只需要预先分发的公钥），这是 JWT 相对传统 Session 机制在分布式场景下的核心性能优势，避免了每次请求都产生一次跨网络的认证中心调用。
- **黑名单查询的性能优化**：黑名单通常存储在 Redis 中，查询开销是毫秒级的网络往返，可以结合布隆过滤器（Bloom Filter）先做一次本地快速判断（"绝对不在黑名单中"可以直接跳过 Redis 查询），只有布隆过滤器判断"可能在黑名单中"时才真正查询 Redis，减少大部分正常请求的额外开销。

### 5.3 会话存储的性能优化

- **合理设置过期时间与滑动续期策略的权衡**：滑动续期（每次访问自动刷新过期时间）能提供更好的用户体验，但会增加对存储介质的写入压力，高并发场景下可以采用"距离过期时间较近时才触发续期写入"的优化（如剩余有效期低于 50% 时才执行一次续期操作），减少不必要的写操作。

## 六、最佳实践与总结

### 6.1 设计原则总结

1. **认证与授权职责分离，各自解决"你是谁"和"你能做什么"两个独立问题**，架构上应该清晰分层，不要混在一起判断。
2. **令牌设计要兼顾安全性与可用性**：双 Token 机制、合理的有效期、可主动吊销的黑名单机制，是在安全和体验之间取得平衡的核心手段。
3. **权限模型要与实际组织架构和业务规则匹配**：RBAC 基础模型解决"功能权限"问题，数据权限需要结合组织架构、业务归属关系单独设计，不能指望一套模型解决所有权限诉求。
4. **多租户隔离必须从基础设施层面强制保证**，不能依赖开发人员在每处业务代码中自觉遵守约定，这是安全设计中"默认安全"和"纵深防御"原则的直接体现。
5. **安全防护应该是风险自适应的**，而非对所有场景一刀切地要求最高强度的验证，在安全性和用户体验之间根据实际风险动态调整。

### 6.2 常见陷阱

- **JWT Payload 中存放敏感信息**：Payload 只是编码而非加密，任何人都能解码查看，绝不能存放密码等敏感字段。
- **忘记处理 Token 黑名单的场景**：只做了签名和过期时间校验，没有考虑用户主动登出或账号被封禁后 Token 应该立即失效的需求。
- **多租户查询遗漏租户过滤条件**：这是多租户系统中最危险也最容易发生的疏漏，必须通过基础设施层的强制拦截机制杜绝，而非依赖代码审查。
- **登录失败信息过于具体**：返回"用户不存在"和"密码错误"这类区分度高的错误信息，会帮助攻击者更高效地进行撞库和账号枚举攻击，应统一返回模糊的"用户名或密码错误"。
- **权限缓存不及时失效**：角色权限收紧后，如果缓存没有主动失效机制，会导致用户在缓存过期之前依然拥有已被收回的权限，构成越权访问的安全隐患。

### 6.3 演进方向

- **无密码认证（Passwordless）的普及**：基于生物识别、设备密钥（如 WebAuthn/FIDO2 标准）的认证方式正在逐步替代传统密码，从根本上消除密码泄露、撞库攻击等一大类安全风险。
- **零信任架构下的持续认证**：传统"一次登录、长期信任"的模式正在向"持续评估、动态调整信任级别"演进，每一次敏感操作都可能触发风险重新评估，而非仅在登录时刻做一次性判断。
- **权限治理的自动化与可视化**：随着系统规模扩大，权限配置本身的复杂度也会成为新的风险来源（过度授权、僵尸权限长期未清理），未来会有更多自动化工具辅助权限审计、异常权限检测和最小权限收敛。
- **联邦身份（Federated Identity）与跨组织协作**：企业间协作场景下，如何在不同组织各自独立的身份体系之间建立可信的身份联邦关系（而非要求所有参与方共享同一套身份系统），是认证授权体系面向更复杂协作场景的重要演进方向。

认证授权体系是整个系统安全的第一道防线，也是最后一道防线——几乎所有的数据访问都要经过"你是谁、你能做什么"这两个问题的检验。设计这套体系时，既要有严谨的安全意识（纵深防御、默认安全、最小权限），也要充分考虑实际业务场景下的用户体验和系统性能，在安全、体验、性能三者之间找到符合业务特点的平衡点。

## 七、全链路实战案例

前面几章从整体架构、核心链路（认证、令牌、RBAC权限、多租户隔离）到异常处理和性能优化，系统梳理了认证授权体系的技术要点。本章通过三个贯穿全链路的实战案例，将登录认证、令牌校验、权限判定、异常安全防护等能力串联起来，展示一次完整请求从用户登录到访问受保护资源的全过程。

### 7.1 案例一：用户登录到访问受保护资源全链路

#### 7.1.1 场景描述

某企业管理系统的用户从登录到访问一个需要特定权限的接口，需要经过完整的认证授权链路，要求：

- 登录时校验用户名密码，成功后签发Access Token和Refresh Token双令牌；
- 访问受保护接口时校验Access Token的签名、有效期和黑名单状态；
- 校验通过后进行RBAC权限判断，确认用户是否拥有访问该接口的权限；
- 全程记录关键日志，登录失败和越权访问都要有明确的审计记录。

```
登录到访问受保护资源全链路：

  用户提交用户名密码登录
       │
       ▼
  ① 登录安全校验（失败次数/异常登录检测）── 触发风控 ──▶ 拒绝登录
       │ 通过
       ▼
  ② 校验用户名密码 ── 失败 ──▶ 返回模糊错误提示 + 记录失败次数
       │ 成功
       ▼
  ③ 签发双Token（Access Token + Refresh Token），写入会话存储
       │
       ▼
  客户端携带Access Token访问受保护接口
       │
       ▼
  ④ JWT本地验签 + 过期时间校验 ── 失败 ──▶ 返回401
       │ 通过
       ▼
  ⑤ 黑名单查询（布隆过滤器 + Redis）── 命中黑名单 ──▶ 返回401
       │ 未命中
       ▼
  ⑥ RBAC权限校验 ── 无权限 ──▶ 返回403 + 记录越权审计日志
       │ 有权限
       ▼
  ⑦ 执行业务逻辑，返回结果
```

#### 7.1.2 完整实现代码

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.List;
import java.util.Set;

/**
 * 登录到访问受保护资源全链路处理器
 *
 * 覆盖登录安全校验、密码验证、双Token签发、JWT验签、
 * 黑名单查询、RBAC权限校验的完整认证授权链路。
 */
public class LoginToProtectedResourceFullChainProcessor {

    private static final Logger logger = LoggerFactory.getLogger(
        LoginToProtectedResourceFullChainProcessor.class);

    private final LoginSecurityService loginSecurityService;
    private final UserAccountService userAccountService;
    private final TokenLifecycleService tokenLifecycleService;
    private final TokenBlacklistService tokenBlacklistService;
    private final PermissionCheckService permissionCheckService;
    private final AuditLogService auditLogService;

    public LoginToProtectedResourceFullChainProcessor(
            LoginSecurityService loginSecurityService,
            UserAccountService userAccountService,
            TokenLifecycleService tokenLifecycleService,
            TokenBlacklistService tokenBlacklistService,
            PermissionCheckService permissionCheckService,
            AuditLogService auditLogService) {
        this.loginSecurityService = loginSecurityService;
        this.userAccountService = userAccountService;
        this.tokenLifecycleService = tokenLifecycleService;
        this.tokenBlacklistService = tokenBlacklistService;
        this.permissionCheckService = permissionCheckService;
        this.auditLogService = auditLogService;
    }

    /**
     * 登录全链路处理
     */
    public LoginResult login(String username, String password, String clientIp) {
        // ========== 第①步：登录安全校验 ==========
        if (loginSecurityService.isBlockedByRiskControl(username, clientIp)) {
            logger.warn("登录被风控拦截: username={}, ip={}", username, clientIp);
            auditLogService.recordLoginBlocked(username, clientIp);
            return LoginResult.fail("登录失败次数过多，请稍后重试");
        }

        // ========== 第②步：校验用户名密码 ==========
        User user = userAccountService.findByUsername(username);
        if (user == null || !userAccountService.verifyPassword(user, password)) {
            loginSecurityService.recordLoginFailure(username, clientIp);
            logger.warn("登录失败: username={}, ip={}", username, clientIp);
            // 统一返回模糊错误提示，避免暴露用户是否存在
            return LoginResult.fail("用户名或密码错误");
        }
        loginSecurityService.resetFailureCount(username);

        // ========== 第③步：签发双Token ==========
        TokenPair tokenPair = tokenLifecycleService.issueTokenPair(user);
        logger.info("登录成功: userId={}, username={}", user.getId(), username);
        auditLogService.recordLoginSuccess(user.getId(), clientIp);

        return LoginResult.success(tokenPair);
    }

    /**
     * 访问受保护资源全链路处理
     */
    public AccessResult accessProtectedResource(
            String accessToken, String requiredPermission, String traceId) {

        // ========== 第④步：JWT本地验签与过期校验 ==========
        JwtClaims claims;
        try {
            claims = tokenLifecycleService.verifyAndParse(accessToken);
        } catch (TokenExpiredException | TokenInvalidException e) {
            logger.warn("[TraceId={}] Token校验失败: {}", traceId, e.getMessage());
            return AccessResult.unauthorized("登录已过期，请重新登录");
        }

        // ========== 第⑤步：黑名单查询（布隆过滤器 + Redis） ==========
        if (tokenBlacklistService.isBlacklisted(claims.getJti())) {
            logger.warn("[TraceId={}] Token在黑名单中: jti={}, userId={}",
                traceId, claims.getJti(), claims.getUserId());
            return AccessResult.unauthorized("登录状态已失效，请重新登录");
        }

        // ========== 第⑥步：RBAC权限校验 ==========
        boolean hasPermission = permissionCheckService.hasPermission(
            claims.getUserId(), requiredPermission);
        if (!hasPermission) {
            logger.warn("[TraceId={}] 越权访问: userId={}, " 
                + "requiredPermission={}", traceId, claims.getUserId(),
                requiredPermission);
            auditLogService.recordUnauthorizedAccess(
                claims.getUserId(), requiredPermission, traceId);
            return AccessResult.forbidden("无权限访问该资源");
        }

        // ========== 第⑦步：权限校验通过，允许访问 ==========
        logger.info("[TraceId={}] 权限校验通过: userId={}, permission={}",
            traceId, claims.getUserId(), requiredPermission);
        return AccessResult.success(claims.getUserId());
    }
}
```

### 7.2 案例二：Token刷新与主动登出全链路

#### 7.2.1 场景描述

某移动端App需要处理Access Token过期后的无感刷新，以及用户主动登出时的安全下线，要求：

- Access Token过期但Refresh Token仍有效时，客户端可用Refresh Token换取新的Token对；
- Refresh Token本身也有过期时间，且只能使用一次（用后即焚，防止重放攻击）；
- 用户主动登出时，需要将当前Access Token和Refresh Token都加入黑名单，立即失效；
- 检测到Refresh Token被重复使用时，判定为潜在的Token泄露，强制该用户全部会话下线。

```
Token刷新与主动登出全链路：

  Access Token过期，客户端携带Refresh Token请求刷新
       │
       ▼
  ① 校验Refresh Token签名与过期时间 ── 失效 ──▶ 要求重新登录
       │ 有效
       ▼
  ② 检查Refresh Token是否已被使用过 ── 已使用 ──▶ ③ 判定Token泄露
       │ 未使用                                      │
       ▼                                            ▼
  ④ 标记该Refresh Token为已使用                 强制该用户全部会话下线
       │                                            + 告警通知安全团队
       ▼
  ⑤ 签发新的Access Token + Refresh Token对
       │
       ▼
  返回新Token对给客户端

  ─────────────────────────────────────

  用户主动登出
       │
       ▼
  ⑥ 将当前Access Token和Refresh Token的jti加入黑名单
       │
       ▼
  ⑦ 清理服务端会话数据，返回登出成功
```

#### 7.2.2 完整实现代码

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

/**
 * Token刷新与主动登出全链路处理器
 *
 * 覆盖Refresh Token的一次性使用校验、Token泄露检测与强制下线、
 * 以及用户主动登出时的双Token黑名单处理。
 */
public class TokenRefreshAndLogoutFullChainProcessor {

    private static final Logger logger = LoggerFactory.getLogger(
        TokenRefreshAndLogoutFullChainProcessor.class);

    private final TokenLifecycleService tokenLifecycleService;
    private final TokenBlacklistService tokenBlacklistService;
    /** 已使用过的RefreshToken jti集合，用于检测重放 */
    private final Set<String> usedRefreshTokenIds = ConcurrentHashMap.newKeySet();
    private final SessionRevocationService sessionRevocationService;
    private final AlertNotifier alertNotifier;

    public TokenRefreshAndLogoutFullChainProcessor(
            TokenLifecycleService tokenLifecycleService,
            TokenBlacklistService tokenBlacklistService,
            SessionRevocationService sessionRevocationService,
            AlertNotifier alertNotifier) {
        this.tokenLifecycleService = tokenLifecycleService;
        this.tokenBlacklistService = tokenBlacklistService;
        this.sessionRevocationService = sessionRevocationService;
        this.alertNotifier = alertNotifier;
    }

    /**
     * Token刷新全链路
     */
    public TokenRefreshResult refreshToken(String refreshToken, String traceId) {
        // ========== 第①步：校验Refresh Token有效性 ==========
        JwtClaims claims;
        try {
            claims = tokenLifecycleService.verifyRefreshToken(refreshToken);
        } catch (TokenExpiredException | TokenInvalidException e) {
            logger.warn("[TraceId={}] RefreshToken无效: {}", traceId, e.getMessage());
            return TokenRefreshResult.requireRelogin();
        }

        String jti = claims.getJti();

        // ========== 第②③步：检测Refresh Token重放 ==========
        if (usedRefreshTokenIds.contains(jti)) {
            logger.error("[TraceId={}] 检测到RefreshToken重放, " 
                + "判定Token泄露: userId={}, jti={}",
                traceId, claims.getUserId(), jti);
            handleTokenLeakage(claims.getUserId(), traceId);
            return TokenRefreshResult.requireRelogin();
        }

        // ========== 第④步：标记为已使用（用后即焚） ==========
        usedRefreshTokenIds.add(jti);

        // ========== 第⑤步：签发新的Token对 ==========
        TokenPair newTokenPair = tokenLifecycleService.issueTokenPair(
            claims.getUserId());
        logger.info("[TraceId={}] Token刷新成功: userId={}",
            traceId, claims.getUserId());
        return TokenRefreshResult.success(newTokenPair);
    }

    /**
     * 检测到Token泄露后，强制该用户全部会话下线并告警
     */
    private void handleTokenLeakage(String userId, String traceId) {
        sessionRevocationService.revokeAllSessions(userId);
        alertNotifier.notify(String.format(
            "检测到用户[%s]的RefreshToken被重放使用，疑似Token泄露，" 
            + "已强制下线全部会话", userId));
        logger.error("[TraceId={}] 用户{}的全部会话已被强制下线",
            traceId, userId);
    }

    /**
     * 主动登出全链路
     */
    public void logout(String accessToken, String refreshToken, String traceId) {
        // ========== 第⑥步：将Token加入黑名单 ==========
        JwtClaims accessClaims = tokenLifecycleService.parseWithoutVerify(accessToken);
        tokenBlacklistService.addToBlacklist(
            accessClaims.getJti(), accessClaims.getExpirationTime());

        if (refreshToken != null) {
            JwtClaims refreshClaims = tokenLifecycleService.parseWithoutVerify(refreshToken);
            tokenBlacklistService.addToBlacklist(
                refreshClaims.getJti(), refreshClaims.getExpirationTime());
        }

        // ========== 第⑦步：清理服务端会话数据 ==========
        sessionRevocationService.revokeSession(accessClaims.getUserId(),
            accessClaims.getJti());
        logger.info("[TraceId={}] 用户主动登出成功: userId={}",
            traceId, accessClaims.getUserId());
    }
}
```

### 7.3 案例三：多租户数据权限校验全链路

#### 7.3.1 场景描述

某SaaS平台需要保证不同租户之间的数据严格隔离，同时在租户内部还要按角色控制数据可见范围，要求：

- 每个请求必须携带租户上下文，基础设施层强制拼接租户过滤条件，业务代码无需感知；
- 在租户内部，还需要根据用户角色判断其能访问的部门/组织范围（数据权限）；
- 检测到跨租户访问尝试时，直接拒绝并记录高优先级安全审计日志；
- 数据权限的计算结果可以缓存，避免每次请求都重新递归计算组织树。

```
多租户数据权限校验全链路：

  请求到达服务端（携带TenantContext）
       │
       ▼
  ① 租户上下文解析与校验 ── 缺失或非法 ──▶ 拒绝请求
       │ 通过
       ▼
  ② 数据库拦截器强制拼接租户过滤条件（tenant_id = ?）
       │
       ▼
  ③ 检测请求参数中是否存在跨租户访问的资源ID
       │
       ├── 检测到跨租户访问 ──▶ 拒绝请求 + 高优先级安全审计日志
       │
       └── 未检测到 ──▶ ④ 查询用户数据权限范围（优先读缓存）
                             │
                             ├── 缓存命中 ──▶ 直接使用缓存的部门范围
                             │
                             └── 缓存未命中 ──▶ 递归计算组织树可见范围，回写缓存
       │
       ▼
  ⑤ 按数据权限范围过滤查询结果，返回给调用方
```

#### 7.3.2 完整实现代码

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.List;
import java.util.Set;
import java.util.concurrent.TimeUnit;

/**
 * 多租户数据权限校验全链路处理器
 *
 * 覆盖租户上下文强制校验、跨租户访问检测、数据权限范围计算与缓存、
 * 最终按数据权限过滤查询结果的完整链路。
 */
public class MultiTenantDataPermissionFullChainProcessor {

    private static final Logger logger = LoggerFactory.getLogger(
        MultiTenantDataPermissionFullChainProcessor.class);

    private final TenantValidationService tenantValidationService;
    private final DataPermissionCacheService dataPermissionCacheService;
    private final OrganizationTreeService organizationTreeService;
    private final AuditLogService auditLogService;

    /** 数据权限缓存过期时间 */
    private static final long PERMISSION_CACHE_TTL_SECONDS = 300L;

    public MultiTenantDataPermissionFullChainProcessor(
            TenantValidationService tenantValidationService,
            DataPermissionCacheService dataPermissionCacheService,
            OrganizationTreeService organizationTreeService,
            AuditLogService auditLogService) {
        this.tenantValidationService = tenantValidationService;
        this.dataPermissionCacheService = dataPermissionCacheService;
        this.organizationTreeService = organizationTreeService;
        this.auditLogService = auditLogService;
    }

    /**
     * 多租户数据权限校验全链路入口
     *
     * @param context 当前请求的租户与用户上下文
     * @param requestedResourceTenantId 请求参数中携带的资源所属租户ID（如有）
     * @return 数据权限过滤结果，包含允许访问的部门ID集合
     */
    public DataPermissionResult checkAndResolve(
            TenantContext context, String requestedResourceTenantId) {
        String traceId = context.getTraceId();

        // ========== 第①步：租户上下文校验 ==========
        if (!tenantValidationService.isValid(context)) {
            logger.error("[TraceId={}] 租户上下文缺失或非法", traceId);
            return DataPermissionResult.denied("租户上下文非法");
        }

        // ========== 第②步：数据库拦截器已在SQL层强制拼接租户条件 ==========
        // 此处仅记录，实际拼接逻辑见TenantIsolationInterceptor
        logger.debug("[TraceId={}] 租户过滤条件已生效: tenantId={}",
            traceId, context.getTenantId());

        // ========== 第③步：跨租户访问检测 ==========
        if (requestedResourceTenantId != null
                && !requestedResourceTenantId.equals(context.getTenantId())) {
            logger.error("[TraceId={}] 检测到跨租户访问尝试: " 
                + "currentTenant={}, requestedTenant={}, userId={}",
                traceId, context.getTenantId(), requestedResourceTenantId,
                context.getUserId());
            auditLogService.recordCrossTenantAccessAttempt(
                context.getUserId(), context.getTenantId(),
                requestedResourceTenantId, traceId);
            return DataPermissionResult.denied("禁止跨租户访问");
        }

        // ========== 第④步：查询数据权限范围（优先读缓存） ==========
        Set<String> visibleDeptIds = resolveVisibleDepartments(context);

        // ========== 第⑤步：返回数据权限过滤范围 ==========
        logger.info("[TraceId={}] 数据权限解析完成: userId={}, " 
            + "visibleDeptCount={}", traceId, context.getUserId(),
            visibleDeptIds.size());
        return DataPermissionResult.allowed(visibleDeptIds);
    }

    private Set<String> resolveVisibleDepartments(TenantContext context) {
        String cacheKey = context.getTenantId() + ":" + context.getUserId();
        Set<String> cached = dataPermissionCacheService.get(cacheKey);
        if (cached != null) {
            logger.debug("数据权限缓存命中: cacheKey={}", cacheKey);
            return cached;
        }

        // 缓存未命中，递归计算组织树可见范围（开销较大的操作）
        Set<String> computed = organizationTreeService.computeVisibleDepartments(
            context.getTenantId(), context.getUserId());
        dataPermissionCacheService.put(cacheKey, computed,
            PERMISSION_CACHE_TTL_SECONDS, TimeUnit.SECONDS);
        logger.debug("数据权限缓存未命中, 已重新计算并回写: cacheKey={}, " 
            + "deptCount={}", cacheKey, computed.size());
        return computed;
    }
}
```

### 7.4 三个案例的协同关系

三个案例分别覆盖了认证授权体系中"登录鉴权""令牌生命周期管理""数据权限隔离"三条核心链路，在实际系统中共同构成完整的安全防护体系：

| 协同维度 | 案例一（登录到访问） | 案例二（Token刷新登出） | 案例三（多租户数据权限） |
|---------|---------------------|--------------------------|---------------------------|
| 触发时机 | 用户登录及每次接口访问 | Token过期刷新、用户主动登出 | 每次涉及数据查询的请求 |
| 核心目标 | 完成"认证+鉴权"闭环 | 保障令牌全生命周期安全可控 | 保证租户隔离与组织级数据权限 |
| 关键机制 | 双Token签发、本地验签、黑名单查询 | Refresh Token一次性使用、重放检测 | 强制租户过滤、跨租户检测、权限缓存 |
| 异常处理 | 越权返回403并记录审计日志 | 检测到Token泄露强制全部会话下线 | 跨租户访问直接拒绝并高优先级告警 |
| 共同依赖 | RBAC权限模型、Token黑名单机制 | 依赖案例一的Token签发与黑名单基础设施 | 依赖案例一确认的用户身份（userId） |

在实际请求处理链路中，案例三的数据权限校验通常发生在案例一"RBAC功能权限校验通过"之后——先确认用户能否访问某个功能接口（案例一），再确认该用户在当前租户内能看到哪些范围的数据（案例三）；而案例二则是贯穿整个用户会话生命周期、独立于单次请求之外的令牌管理链路，为案例一提供持续可靠的身份凭证基础。</new_string>
