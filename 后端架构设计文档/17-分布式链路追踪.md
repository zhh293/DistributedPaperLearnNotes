## 1. 问题背景

### 1.1 核心问题

在微服务架构中，一个用户请求可能需要经过数十个甚至上百个服务的协同处理才能完成。当请求出现延迟或错误时，传统的单体应用调试方式（如查看本地日志）完全失效——因为问题的根源可能隐藏在调用链的任何一个环节中。

分布式链路追踪（Distributed Tracing）的核心目标是：**将一个跨多个服务的请求还原为完整的调用链路，让开发者能够清晰地看到请求经过了哪些服务、每一步耗时多少、在哪里出现了异常**。

这一需求的典型场景如下：

```
用户请求 → 网关(2ms) → 订单服务(5ms) → 商品服务(3ms) → 库存服务(???ms)
                                        → 用户服务(8ms) → 积分服务(???ms)
                                        → 支付服务(15ms) → 风控服务(???ms)

问题：用户反馈下单慢，但每个服务自己的监控都显示正常。
根因可能是：商品服务调用库存服务超时，但库存服务的超时没有反映在商品服务的监控中。
没有链路追踪，定位此类问题可能需要数小时甚至数天，需要人工在数十台机器上grep日志、
对齐时间戳、猜测调用关系，效率极低且极易遗漏关键线索。
```

### 1.2 Google Dapper论文的启示

Google在2010年发表的论文《Dapper, a Large-Scale Distributed Systems Tracing Infrastructure》是分布式链路追踪的奠基之作。Dapper最初是为了解决Google内部服务数量爆炸式增长后，工程师无法理解复杂系统行为和性能问题而设计的基础设施，其设计理念影响了后来几乎所有链路追踪系统的实现，包括Zipkin（Twitter基于Dapper论文实现并开源）、Jaeger（Uber开源，遵循OpenTracing/OpenTelemetry标准）、SkyWalking（国产APM系统，采用探针字节码增强的方式实现）等。

Dapper论文提出的三个核心设计原则，至今仍是评价一套链路追踪系统是否合格的基本标准：

1. **低开销（Low Overhead）**：追踪系统本身不能对业务服务产生明显的性能影响。Dapper通过采样机制将追踪对系统吞吐量和延迟的影响降到几乎可以忽略不计的程度。任何一个链路追踪方案，如果因为埋点和上报本身拖慢了业务系统，那么这个方案就是失败的。

2. **应用透明（Application-Level Transparency）**：业务代码不应该感知到追踪系统的存在。追踪埋点应该由框架层（RPC框架、HTTP框架、数据库驱动、消息队列客户端）自动完成，业务开发者无需在每一行代码里手动创建Span、手动传递TraceId。这是Dapper能够在Google内部大规模推广的关键——如果每个业务开发者都需要手动埋点，推广成本和出错概率都会非常高。

3. **可扩展性（Scalability）**：追踪系统需要能够处理海量请求。以一个中大型互联网公司的规模估算，全站每天的调用总量可以达到千亿级别的Span，如果每一次调用都全量采集、全量存储，无论是采集通道还是存储系统都会被压垮，因此必须要有采样机制、分层存储机制和数据生命周期管理机制。

Dapper论文中还有几个对工程实现影响深远的设计点，会在后文的核心链路设计中逐一展开：

- 用**Trace树**来描述一次完整的请求调用关系，树中的每个节点是一个Span；
- 用**Annotation（标注）**机制记录一个Span生命周期中的关键时间点，特别是RPC调用的四个阶段（Client Send、Server Receive、Server Send、Client Receive）；
- 通过**进程内上下文传播**（Dapper论文中称为in-process context propagation）解决同一进程内多个模块之间如何共享TraceId和SpanId的问题，这也是本文重点讨论的ThreadLocal传播与跨线程传播问题的理论来源。

### 1.3 不解决的后果

如果没有分布式链路追踪能力，系统将面临以下严重问题：

- **故障定位困难**：跨服务的问题无法快速定位，需要人工排查每个服务的日志，效率极低。一个简单的"下单慢"问题可能需要多个团队协作排查数小时，期间用户体验持续受损，故障影响范围不断扩大。

- **性能瓶颈不可见**：无法精确知道请求在每个服务、每次RPC调用、每次数据库访问上的耗时分布，无法识别性能瓶颈所在。系统优化只能凭经验"盲猜"，缺乏数据支撑。

- **服务依赖不透明**：不清楚服务之间的调用关系和依赖路径，架构演进、容量规划、故障演练缺乏依据。一个服务下线前甚至不知道有哪些上游还在调用它。

- **异常链路丢失**：偶发的异常请求难以复现和追踪，无法进行根因分析。如果没有全量采集异常链路的机制，很多低概率但高影响的问题永远无法被发现。

- **缺乏全链路视角**：每个服务只有自己的视角，无法看到完整的请求路径，难以理解系统整体行为，也无法进行准确的SLA评估和容量评估。

### 1.4 解决思路

分布式链路追踪的核心解决思路是：**唯一标识 + 上下文传播 + 数据采集 + 链路重建**。

1. **唯一标识**：为每个请求分配全局唯一的TraceId，请求经过的每个服务都携带这个TraceId；同时为链路中的每一次调用分配层级化的SpanId，用于还原调用的父子关系和先后顺序。

2. **上下文传播**：在同一进程内通过ThreadLocal传播上下文；在跨服务调用时，通过RPC协议头、HTTP Header等方式，将TraceId、SpanId、调用信息在服务间传递。

3. **数据采集**：每个服务在处理请求时，记录当前调用的Span信息，包括应用标识、方法名、开始时间、结束时间、机器信息、自定义标注等，通过日志文件异步落盘，再由采集Agent统一收集。

4. **链路重建**：将分散在各个服务中的Span数据收集到中心化存储（如基于TraceId做rowKey的HBase），根据TraceId和SpanId的父子关系重建完整的调用链路树，供查询和分析使用。

### 2.2 各组件职责

**追踪SDK（埋点层）**：以Jar包依赖的形式集成到每个业务服务中，负责在RPC调用发生时自动生成或延续TraceId/SpanId，在客户端和服务端两侧分别构造Span并记录四个关键时间点，执行采样判断，最终将Span数据异步写入本地日志文件。SDK通过AOP、RPC框架的Filter/Interceptor扩展点、HTTP框架的拦截器等方式自动完成埋点，业务代码无需任何改造，真正做到Dapper论文所强调的"应用透明"。

**本地日志文件**：每台机器上的追踪数据先落盘到本地日志文件（而不是直接同步网络调用发送到远端），这样即使网络抖动或者采集端不可用，也不会影响业务的正常处理，只是追踪数据的采集会有短暂延迟或者丢失，做到了追踪链路对业务链路的完全解耦。

**采集Agent**：部署在每台业务机器上，以类似`tail -f`的方式实时读取本地追踪日志文件，做基本的格式校验和过滤后，批量打包发送到Kafka。Agent与业务进程完全独立，Agent的故障或重启不会影响业务进程。

**Kafka消息队列**：作为采集端和计算端之间的缓冲层，削峰填谷，避免下游存储和计算被大促、突增流量等场景下的海量Span数据冲垮。生产者按照TraceId做Key路由，尽量保证同一条链路的Span落到同一个分区，便于后续流计算按序处理。

**Storm实时流计算**：消费Kafka中的Span数据，完成Span清洗、按TraceId做窗口聚合（把同一条Trace下的所有Span拼接成一棵调用树）、异常链路检测（发现超时、错误状态的Span并触发告警）、服务依赖关系提取（用于生成拓扑图）等实时处理逻辑。

**存储层（HBase + ES + HDFS）**：三种存储各自承担不同职责——HBase以TraceId作为rowKey，天然支持按TraceId精确、快速地查询一条完整链路的所有Span，满足"点查"场景；Elasticsearch对服务名、方法名、机器IP、时间范围、自定义标签等多维度字段建立倒排索引，满足"检索"场景（例如"查询过去1小时内订单服务下所有耗时超过1秒的调用"）；HDFS存储全量原始数据，供离线MapReduce任务做统计报表、容量分析、异常模式挖掘等重量级分析任务，不占用在线查询链路的资源。

**查询展示层**：提供链路查询、调用拓扑图、服务依赖图等可视化能力，支持按TraceId查看完整调用链路树、按时间轴展示每个Span的起止时间和耗时、按服务维度展示依赖关系图，同时对接告警系统，在检测到异常链路时主动推送通知。

### 2.3 数据规模与设计权衡

以一个中大型互联网公司为例，全站微服务数量可达数千个，每天的调用总量（即Span总量）可以达到**2000亿（200,000,000,000+）** 量级。面对如此庞大的数据量，如果不做采样、全量采集全量存储，无论是Kafka的吞吐、Storm的计算能力还是HBase/ES的存储成本都是难以承受的，因此**采样**是分布式链路追踪系统能够落地的前提条件，而不是可选项。

| 设计决策 | 选择 | 理由 |
|---------|------|------|
| 埋点方式 | 自动埋点为主，手动埋点为辅 | 自动埋点覆盖RPC、HTTP、DB、MQ等主流框架，业务无感知；手动埋点用于补充关键业务节点的自定义标注 |
| 采样策略 | 默认1%概率采样 + 方法级可配置 + 异常强制采集 + Debug全采样 | 平衡存储成本和可观测性；核心链路可单独调高采样率；异常/超时链路必须采集；排查问题时可临时开启全采样 |
| 上报方式 | SDK异步写本地日志 + Agent异步采集 | 彻底解耦追踪链路与业务链路，避免追踪系统故障影响业务 |
| 存储选型 | HBase（点查） + ES（检索） + HDFS（离线分析） | 三种存储各司其职，兼顾在线查询性能与离线分析能力 |
| 上下文传播 | ThreadLocal（进程内） + RPC上下文/HTTP Header（跨进程） | ThreadLocal解决单机内多层调用共享上下文的问题；RPC上下文解决跨服务传播问题 |
| 跨线程传播 | 包装线程池（Runnable/Callable装饰器） | 原生ThreadLocal无法跨线程传播，必须在提交任务时显式拷贝并在执行完成后清理上下文 |
| SpanId生成规则 | 层级化编号（0.1、0.1.1、0.1.2） | 无需查询即可从SpanId本身还原出调用的父子关系与兄弟顺序，重建链路树时无需额外的父子索引 |
| Span数据格式 | 轻量文本/二进制混合编码 | 减少日志落盘和网络传输的开销 |

## 3. 核心链路设计

### 3.1 Trace/Span数据模型

#### 3.1.1 Dapper的核心概念

Dapper论文提出了两个核心概念：**Trace**（调用链）和**Span**（跨度）。

- **Trace**：代表一次完整的请求调用链，从入口（如网关接收到的一次HTTP请求）到出口的所有服务调用组成一棵树。一个Trace在全局范围内由唯一的TraceId标识。
- **Span**：代表调用链中的一次调用行为。每一次RPC调用会产生两个Span——调用方视角的**客户端Span（clientSpan）** 和被调用方视角的**服务端Span（serverSpan）**，二者共享同一个SpanId，但分别记录各自视角的时间戳和状态信息。

Span之间通过SpanId的层级编码组成树形结构，还原请求的调用路径：

```
Trace (TraceId = a1b2c3d4-e5f6-...)
│
├── Span(spanId=0)      : 网关.handleRequest
│   ├── Span(spanId=0.1)    : 订单服务.createOrder
│   │   ├── Span(spanId=0.1.1) : 商品服务.getProduct
│   │   │   └── Span(spanId=0.1.1.1) : 库存服务.checkStock
│   │   ├── Span(spanId=0.1.2) : 用户服务.getUser
│   │   └── Span(spanId=0.1.3) : 支付服务.pay
│   │       └── Span(spanId=0.1.3.1) : 风控服务.check
```

上面这棵树中，`0.1.1`和`0.1.2`是兄弟节点（同为`0.1`的子调用），从SpanId的编码本身就能直接看出"商品服务调用"和"用户服务调用"是订单服务在同一层发起的两次并行/串行调用，且发生顺序为先`0.1.1`后`0.1.2`——这正是层级化SpanId设计相较于"随机SpanId + parentId索引"方案的最大优势：**重建链路树时不需要额外做父子关系的递归查询，直接按字符串排序和前缀匹配即可还原出完整的调用树结构**。

#### 3.1.2 Span数据结构

**设计模式**：使用**建造者模式**构建Span对象，**不可变对象模式**保证已完成的Span不被并发修改。


### 3.2 TraceId与SpanId生成规则

#### 3.2.1 TraceId：全局唯一

TraceId必须满足**全局唯一**且**生成开销极低**两个条件，因为它会在整条调用链的入口生成一次，之后所有下游服务都只是透传而不会重新生成。常见的生成方式是"时间戳 + 机器标识 + 进程内自增序号"的组合编码，兼顾唯一性、生成效率和一定的可读性（例如可以从TraceId前缀直接反解出大致的生成时间和来源机器，便于排障时的快速定位）。

```java
/**
 * TraceId生成器
 * 生成规则：本机IP的十六进制表示 + 当前时间戳 + 进程内自增序号 + 随机数
 * 保证在分布式环境下全局唯一，同时不依赖任何中心化服务
 */
public final class TraceIdGenerator {

    /** 本机IP的十六进制编码，进程启动时计算一次 */
    private static final String IP_HEX = ipToHex(LocalIpUtil.getLocalIp());

    /** 进程内自增序号，保证同一毫秒内生成的TraceId不重复 */
    private static final AtomicInteger COUNTER = new AtomicInteger(0);

    private TraceIdGenerator() {
    }

    public static String generate() {
        long timestamp = System.currentTimeMillis();
        int counter = COUNTER.incrementAndGet() & 0xFFFFFF;
        // 格式：ip十六进制(8位) + 时间戳(13位) + 自增序号(6位) + 进程标识(4位)
        return IP_HEX
                + Long.toString(timestamp)
                + String.format("%06x", counter)
                + Integer.toHexString(ProcessHandle.current().pid().hashCode() & 0xFFFF);
    }

    private static String ipToHex(String ip) {
        String[] segments = ip.split("\\.");
        StringBuilder sb = new StringBuilder();
        for (String segment : segments) {
            sb.append(String.format("%02x", Integer.parseInt(segment)));
        }
        return sb.toString();
    }
}
```

#### 3.2.2 SpanId：层级化编码

SpanId的设计是本文的核心要点之一。与"随机UUID + parentSpanId字段"的方案不同，层级化SpanId直接把父子关系和调用顺序编码进了SpanId字符串本身：

- 根Span的SpanId固定为`0`；
- 每向下发起一次子调用，就在父SpanId后面追加`.` + 从1开始的序号，例如父Span是`0.1`，它发起的第一个子调用SpanId是`0.1.1`，第二个子调用SpanId是`0.1.2`；
- 同一层级的兄弟调用序号递增，天然反映"谁先谁后"；
- 只需要看SpanId的层级深度，就知道这次调用在整条链路中处于第几层；只需要看SpanId的公共前缀，就能判断两个Span是否有祖先-后代关系。

```java
/**
 * SpanId生成与传播工具
 * SpanId采用层级化编码，例如：0、0.1、0.1.1、0.1.2
 * 每发起一次下游调用，在当前SpanId基础上追加"."+序号
 */
public final class SpanIdGenerator {

    /** 根Span的固定标识 */
    public static final String ROOT_SPAN_ID = "0";

    private SpanIdGenerator() {
    }

    /**
     * 根据父SpanId和当前调用的序号生成子SpanId
     *
     * @param parentSpanId 父级SpanId，例如 "0.1"
     * @param childIndex   当前是父Span发起的第几个子调用，从1开始
     * @return 子SpanId，例如 "0.1.1"
     */
    public static String nextChildSpanId(String parentSpanId, int childIndex) {
        return parentSpanId + "." + childIndex;
    }

    /**
     * 判断candidate是否是ancestor的子孙节点（含自身）
     */
    public static boolean isDescendant(String ancestor, String candidate) {
        return candidate.equals(ancestor) || candidate.startsWith(ancestor + ".");
    }

    /**
     * 计算SpanId所在的调用层级深度，根节点深度为0
     */
    public static int depthOf(String spanId) {
        return spanId.split("\\.").length - 1;
    }
}

/**
 * 每个Span上下文内部维护一个"下一个子序号"的计数器，
 * 用于在同一个Span下发起多次子调用时正确生成兄弟SpanId
 */
public final class ChildSpanIndexHolder {

    /** key为父spanId，value为已分配出去的子序号计数 */
    private final Map<String, AtomicInteger> childIndexMap = new ConcurrentHashMap<>();

    public int nextIndex(String parentSpanId) {
        return childIndexMap
                .computeIfAbsent(parentSpanId, k -> new AtomicInteger(0))
                .incrementAndGet();
    }
}
```

### 3.3 RPC四阶段模型（CS/SR/SS/CR）

Dapper论文中一个非常重要但容易被忽视的设计，是对**一次RPC调用**的四个关键时间点建模，业界通常用四个缩写表示：

- **CS（Client Send）**：客户端发出请求的时刻；
- **SR（Server Recv）**：服务端接收到请求的时刻；
- **SS（Server Send）**：服务端处理完成、发出响应的时刻；
- **CR（Client Recv）**：客户端收到响应的时刻。

这四个时间点的价值在于：把一次RPC调用的总耗时精确拆解成**网络传输耗时**和**服务端处理耗时**两部分，而不是笼统地只有一个"耗时"数字。

```
时间轴：
Client:  ──CS───────────────────────────CR──►
                 │                     ▲
                 │  网络+服务端总耗时     │
                 ▼                     │
Server:          ──SR──────────SS──────┘
                       │        │
                       └─服务端─┘
                        处理耗时

计算公式：
  客户端到服务端的网络耗时(上行) ≈ SR - CS
  服务端处理耗时              ≈ SS - SR
  服务端到客户端的网络耗时(下行) ≈ CR - SS
  整个RPC调用总耗时           ≈ CR - CS
```

有了这四个时间点，排查"某次调用为什么慢"时就能精确定位：是网络传输慢（上行或下行耗时异常），还是服务端自身处理慢（SS-SR过大）。如果只有一个笼统的总耗时，遇到"客户端认为调用耗时500ms，但服务端自己监控显示处理只用了5ms"这种典型的网络问题时，将完全无法定位问题出在网络还是代码。

**客户端上报clientSpan，服务端上报serverSpan**，两者虽然共享同一个traceId和spanId，但各自独立采集、独立上报、独立落盘，在数据聚合阶段（Storm链路聚合任务）再按traceId+spanId把两条记录关联到同一个调用节点上，分别填充CS/CR（客户端记录）和SR/SS（服务端记录）四个时间戳。

```java
/**
 * RPC调用四阶段时间戳模型
 * clientSpan记录CS/CR，serverSpan记录SR/SS
 * 两者通过traceId+spanId在链路聚合阶段进行关联
 */
public final class RpcTimestamps {

    /** Client Send：客户端发出请求时间 */
    private long cs;

    /** Server Recv：服务端接收到请求时间 */
    private long sr;

    /** Server Send：服务端发出响应时间 */
    private long ss;

    /** Client Recv：客户端收到响应时间 */
    private long cr;

    public void markClientSend() {
        this.cs = System.currentTimeMillis();
    }

    public void markServerRecv() {
        this.sr = System.currentTimeMillis();
    }

    public void markServerSend() {
        this.ss = System.currentTimeMillis();
    }

    public void markClientRecv() {
        this.cr = System.currentTimeMillis();
    }

    /** 上行网络耗时：请求从客户端到服务端的传输耗时 */
    public long upstreamNetworkCost() {
        return sr - cs;
    }

    /** 服务端处理耗时 */
    public long serverProcessCost() {
        return ss - sr;
    }

    /** 下行网络耗时：响应从服务端到客户端的传输耗时 */
    public long downstreamNetworkCost() {
        return cr - ss;
    }

    /** 客户端视角的总耗时 */
    public long totalCost() {
        return cr - cs;
    }
}

/**
 * RPC客户端拦截器：负责在调用前后打点并上报clientSpan
 * 通过RPC框架提供的Filter扩展点织入，业务代码无感知
 */
public class TracingClientFilter implements RpcFilter {

    private final SpanReporter spanReporter;
    private final SampleDecider sampleDecider;

    public TracingClientFilter(SpanReporter spanReporter, SampleDecider sampleDecider) {
        this.spanReporter = spanReporter;
        this.sampleDecider = sampleDecider;
    }

    @Override
    public RpcResponse invoke(RpcInvoker invoker, RpcRequest request) {
        TraceContext parentContext = TraceContextHolder.get();
        String traceId = parentContext != null ? parentContext.getTraceId() : TraceIdGenerator.generate();
        String parentSpanId = parentContext != null ? parentContext.getSpanId() : SpanIdGenerator.ROOT_SPAN_ID;
        int childIndex = ChildSpanIndexHolder.INSTANCE.nextIndex(parentSpanId);
        String currentSpanId = SpanIdGenerator.nextChildSpanId(parentSpanId, childIndex);

        boolean sampled = parentContext != null
                ? parentContext.isSampled()
                : sampleDecider.decide(request.getMethodName());

        // 将追踪信息写入RPC请求的附件（attachment），随请求一起发送到服务端
        request.putAttachment("traceId", traceId);
        request.putAttachment("spanId", currentSpanId);
        request.putAttachment("sampled", String.valueOf(sampled));
        request.putAttachment("swimlane", parentContext != null ? parentContext.getSwimlane() : "");

        RpcTimestamps timestamps = new RpcTimestamps();
        timestamps.markClientSend();
        RpcResponse response;
        SpanStatus status = SpanStatus.SUCCESS;
        try {
            response = invoker.invoke(request);
            if (response.hasError()) {
                status = SpanStatus.ERROR;
            }
        } catch (RpcTimeoutException e) {
            status = SpanStatus.TIMEOUT;
            throw e;
        } finally {
            timestamps.markClientRecv();
            if (sampled) {
                Span clientSpan = Span.builder()
                        .traceId(traceId)
                        .spanId(currentSpanId)
                        .role(SpanRole.CLIENT)
                        .appKey(AppKeyHolder.current())
                        .method(request.getMethodName())
                        .startTime(timestamps.cs())
                        .endTime(timestamps.cr())
                        .status(status)
                        .ip(LocalIpUtil.getLocalIp())
                        .sampled(true)
                        .build();
                spanReporter.report(clientSpan);
            }
        }
        return response;
    }
}

/**
 * RPC服务端拦截器：负责解析上游传来的追踪信息并上报serverSpan
 */
public class TracingServerFilter implements RpcFilter {

    private final SpanReporter spanReporter;

    public TracingServerFilter(SpanReporter spanReporter) {
        this.spanReporter = spanReporter;
    }

    @Override
    public RpcResponse invoke(RpcInvoker invoker, RpcRequest request) {
        String traceId = request.getAttachment("traceId");
        String spanId = request.getAttachment("spanId");
        boolean sampled = Boolean.parseBoolean(request.getAttachment("sampled"));
        String swimlane = request.getAttachment("swimlane");

        // 服务端接收到请求，构造本地TraceContext并写入ThreadLocal，供业务逻辑和下游调用使用
        TraceContext context = TraceContext.builder()
                .traceId(traceId)
                .spanId(spanId)
                .sampled(sampled)
                .swimlane(swimlane)
                .build();
        TraceContextHolder.set(context);

        RpcTimestamps timestamps = new RpcTimestamps();
        timestamps.markServerRecv();
        RpcResponse response;
        SpanStatus status = SpanStatus.SUCCESS;
        try {
            response = invoker.invoke(request);
            if (response.hasError()) {
                status = SpanStatus.ERROR;
            }
            return response;
        } finally {
            timestamps.markServerSend();
            if (sampled) {
                Span serverSpan = Span.builder()
                        .traceId(traceId)
                        .spanId(spanId)
                        .role(SpanRole.SERVER)
                        .appKey(AppKeyHolder.current())
                        .method(request.getMethodName())
                        .startTime(timestamps.sr())
                        .endTime(timestamps.ss())
                        .status(status)
                        .ip(LocalIpUtil.getLocalIp())
                        .sampled(true)
                        .build();
                spanReporter.report(serverSpan);
            }
            // 必须清理ThreadLocal，避免线程池复用导致上下文污染
            TraceContextHolder.clear();
        }
    }
}
```

### 3.4 上下文传播机制

#### 3.4.1 进程内传播：ThreadLocal

一次请求在单个服务内部，往往会经过Controller、Service、Manager、DAO等多层调用，这些调用通常运行在同一个线程上（Web容器的请求处理模型默认是一个请求绑定一个工作线程）。为了让这一层层调用都能访问到当前的TraceId、SpanId而不需要在每个方法签名里显式传递，最自然的做法就是用**ThreadLocal**把追踪上下文绑定到当前线程。

```java
/**
 * 线程级别的追踪上下文持有者
 * 基于ThreadLocal实现，保证同一线程内的多层方法调用都能访问到同一份上下文
 * 注意：ThreadLocal只能在同一个线程内传播，无法跨线程自动传播（见3.5节）
 */
public final class TraceContextHolder {

    /**
     * 使用InheritableThreadLocal而非普通ThreadLocal，
     * 使得父线程创建子线程时能自动继承一份上下文快照，
     * 但要注意InheritableThreadLocal只在线程创建那一刻做浅拷贝，
     * 无法覆盖线程池复用线程的场景（线程池的线程是预先创建好的，
     * 不是在提交任务时创建的），因此线程池场景仍然需要3.5节的显式传播方案
     */
    private static final ThreadLocal<TraceContext> CONTEXT_HOLDER = new InheritableThreadLocal<>();

    private TraceContextHolder() {
    }

    public static void set(TraceContext context) {
        CONTEXT_HOLDER.set(context);
    }

    public static TraceContext get() {
        return CONTEXT_HOLDER.get();
    }

    public static void clear() {
        CONTEXT_HOLDER.remove();
    }

    /**
     * 在当前上下文基础上派生一个子Span上下文，用于发起下一次子调用
     */
    public static TraceContext deriveChild(int childIndex) {
        TraceContext parent = get();
        if (parent == null) {
            // 没有上游上下文，说明是链路的起点，生成根上下文
            return TraceContext.builder()
                    .traceId(TraceIdGenerator.generate())
                    .spanId(SpanIdGenerator.ROOT_SPAN_ID)
                    .sampled(true)
                    .build();
        }
        return TraceContext.builder()
                .traceId(parent.getTraceId())
                .spanId(SpanIdGenerator.nextChildSpanId(parent.getSpanId(), childIndex))
                .sampled(parent.isSampled())
                .swimlane(parent.getSwimlane())
                .debug(parent.isDebug())
                .build();
    }
}
```

#### 3.4.2 跨进程传播：RPC上下文 / HTTP Header

当调用跨越进程边界（服务A调用服务B）时，ThreadLocal自然失效，此时需要依赖传输协议本身的扩展能力来传递上下文：

- 基于HTTP的调用：通过自定义Header传递，例如`X-Trace-Id`、`X-Span-Id`、`X-Sampled`等；
- 基于RPC框架的调用：通过RPC协议预留的attachment/attribute机制传递（如3.3节示例代码中的`putAttachment`）；
- 基于消息队列的异步调用：将追踪信息作为消息的Header或者消息体的一部分一起发送，消费端解析后延续链路。

```java
/**
 * HTTP场景下的上下文传播：通过自定义Header透传
 */
public final class HttpTraceHeaders {

    public static final String HEADER_TRACE_ID = "X-Trace-Id";
    public static final String HEADER_SPAN_ID = "X-Span-Id";
    public static final String HEADER_SAMPLED = "X-Sampled";
    public static final String HEADER_SWIMLANE = "X-Swimlane";
    public static final String HEADER_DEBUG = "X-Trace-Debug";

    private HttpTraceHeaders() {
    }

    /** 将当前上下文写入HTTP请求头，供下游HTTP服务解析 */
    public static void inject(HttpRequestBuilder builder, TraceContext context) {
        builder.header(HEADER_TRACE_ID, context.getTraceId());
        builder.header(HEADER_SPAN_ID, context.getSpanId());
        builder.header(HEADER_SAMPLED, String.valueOf(context.isSampled()));
        if (context.getSwimlane() != null) {
            builder.header(HEADER_SWIMLANE, context.getSwimlane());
        }
        if (context.isDebug()) {
            builder.header(HEADER_DEBUG, "true");
        }
    }

    /** 从HTTP请求头解析出上游传来的上下文 */
    public static TraceContext extract(HttpServletRequest request) {
        String traceId = request.getHeader(HEADER_TRACE_ID);
        if (traceId == null || traceId.isEmpty()) {
            // 没有上游上下文，说明当前是链路入口，生成新的根上下文
            traceId = TraceIdGenerator.generate();
            return TraceContext.builder()
                    .traceId(traceId)
                    .spanId(SpanIdGenerator.ROOT_SPAN_ID)
                    .sampled(SampleDecider.INSTANCE.decide(request.getRequestURI()))
                    .build();
        }
        return TraceContext.builder()
                .traceId(traceId)
                .spanId(request.getHeader(HEADER_SPAN_ID))
                .sampled(Boolean.parseBoolean(request.getHeader(HEADER_SAMPLED)))
                .swimlane(request.getHeader(HEADER_SWIMLANE))
                .debug("true".equals(request.getHeader(HEADER_DEBUG)))
                .build();
    }
}
```

### 3.5 跨线程传播问题与线程池改造

这是分布式链路追踪工程实践中**最容易踩坑、也是最重要的技术细节之一**。ThreadLocal的语义决定了它只能在"设置它的那个线程"内被正确读取，一旦业务代码涉及线程切换（提交到线程池异步执行、使用CompletableFuture、使用消息队列异步消费等），追踪上下文就会"丢失"或者更严重地发生"串号"问题。下面详细拆解三类典型问题。

#### 3.5.1 问题一：ThreadLocal天生无法跨线程

最直观的问题：主线程设置了TraceContext，提交一个任务到线程池由另一个线程执行，子线程读取ThreadLocal得到的是`null`，因为ThreadLocal的存储实际上是挂在`Thread`对象内部的一个`ThreadLocalMap`字段上，每个线程有自己独立的Map，彼此完全不可见。

```java
/**
 * 反面示例：直接使用线程池会导致追踪上下文丢失
 */
public class BadAsyncExample {

    private final ExecutorService executor = Executors.newFixedThreadPool(10);

    public void handleRequest() {
        TraceContextHolder.set(TraceContext.builder()
                .traceId("trace-001")
                .spanId("0")
                .sampled(true)
                .build());

        executor.submit(() -> {
            // 这里get()到的是null！因为当前线程是线程池的工作线程，
            // 不是刚才set()的那个线程，ThreadLocalMap完全不同
            TraceContext context = TraceContextHolder.get();
            System.out.println("子线程读取到的上下文: " + context); // 输出 null
        });
    }
}
```

#### 3.5.2 问题二：浅拷贝导致的上下文污染（一个线程改，所有线程都看到）

即使做了"传递上下文"的处理，如果传递的方式是**共享同一个可变对象的引用**（浅拷贝）而不是深拷贝一份新对象，就会出现更隐蔽的bug：多个线程共享同一个TraceContext实例，其中一个线程对上下文做了修改（例如追加了自定义annotation、切换了spanId去发起子调用），会导致其它所有持有同一引用的线程都看到这次修改，造成链路数据互相污染、张冠李戴。

```java
/**
 * 反面示例：浅拷贝上下文导致多线程互相污染
 */
public class ShallowCopyPitfallExample {

    public void handleConcurrentSubCalls(TraceContext parentContext, ExecutorService executor) {
        // 错误做法：多个子任务共享同一个parentContext引用
        for (int i = 0; i < 3; i++) {
            final int index = i;
            executor.submit(() -> {
                TraceContextHolder.set(parentContext); // 所有子任务set的是同一个对象引用！
                // 子任务A把parentContext的spanId改成了 "0.1.1"
                // 由于是同一个对象引用，子任务B、C此时读到的spanId也会变成 "0.1.1"
                // 导致三次本应并行、各自独立编号的子调用全部记录成了同一个spanId，
                // 链路重建时会把三条本不相关的调用误判为同一次调用，数据完全错乱
                String childSpanId = SpanIdGenerator.nextChildSpanId(parentContext.getSpanId(), index + 1);
                parentContext.setSpanId(childSpanId); // 直接修改了共享对象的字段！
                doSubCall(childSpanId);
            });
        }
    }

    private void doSubCall(String spanId) {
        // 实际的子调用逻辑
    }
}
```

正确的做法是：TraceContext本身应设计为**不可变对象**（参考3.1.2节Span的不可变设计），任何"修改"操作都返回一个新对象，而不是就地修改原对象；同时，向子线程传播上下文时必须做一次**深拷贝（或者说是基于不可变对象的"派生"）**，保证每个线程拿到的是独立的上下文实例。

```java
/**
 * 不可变的TraceContext，任何变更都返回新对象，从根本上杜绝浅拷贝污染问题

public final class TraceContext {

    /** 使用不可变Map存储自定义透传信息，避免被外部修改 */

    public TraceContext withSpanId(String newSpanId) {
        return TraceContext.builder()
                .traceId(this.traceId)
                .spanId(newSpanId)
                .sampled(this.sampled)
                .swimlane(this.swimlane)
                .debug(this.debug)
                .baggageAll(this.baggage)
                .build();
    }

    public String getTraceId() {
        return traceId;
    }

    public String getSpanId() {
        return spanId;
    }

    public boolean isSampled() {
        return sampled;
    }

    public String getSwimlane() {
        return swimlane;
    }

    public boolean isDebug() {
        return debug;
    }

    public Map<String, String> getBaggage() {
```

#### 3.5.3 问题三：线程池复用导致上下文"串号"

线程池中的线程是被反复复用的，一个线程执行完任务A之后，紧接着会被复用去执行任务B。如果任务A在执行过程中把TraceContext设置进了ThreadLocal，但执行结束后没有主动清理（`remove()`），那么当同一个线程被复用去执行完全不相关的任务B时，任务B会"意外地"读到任务A遗留下来的上下文——这就是**线程池复用导致的上下文污染（串号）问题**，是生产环境中非常典型且难以复现的诡异Bug来源（表现为：明明是两个不相关的请求，链路追踪系统里却显示它们是同一条Trace，或者子调用挂到了错误的父节点下）。

解决方案是：**必须封装/包装线程池**，在任务提交时显式捕获当前线程的上下文快照，在任务实际执行前将快照设置到工作线程的ThreadLocal中，在任务执行完成后（无论成功还是异常）都必须清理掉这个ThreadLocal，恢复工作线程的"干净"状态，避免影响下一次任务复用该线程。

```java
/**
 * 支持追踪上下文传播的线程池包装器
 * 核心思路：
 * 1. 提交任务时，捕获调用线程（提交任务的线程）当前的TraceContext快照
 * 2. 任务真正在工作线程执行前，把快照写入工作线程的ThreadLocal
 * 3. 任务执行完毕后，无论成败都要清理工作线程的ThreadLocal，
 *    避免因为线程池复用导致上下文"串"到下一个不相关的任务里
 */
public class TraceContextAwareExecutor implements ExecutorService {

    private final ExecutorService delegate;

    public TraceContextAwareExecutor(ExecutorService delegate) {
        this.delegate = delegate;
    }

    @Override
    public void execute(Runnable command) {
        delegate.execute(wrap(command));
    }

    @Override
    public <T> Future<T> submit(Callable<T> task) {
        return delegate.submit(wrap(task));
    }

    @Override
    public Future<?> submit(Runnable task) {
        return delegate.submit(wrap(task));
    }

    /**
     * 包装Runnable：提交时捕获快照，执行时设置并在finally清理
     */
    private Runnable wrap(Runnable task) {
        // 捕获提交任务那一刻，调用线程的上下文快照（TraceContext本身是不可变对象，
        // 直接持有引用是安全的，不存在浅拷贝互相污染的问题）
        TraceContext snapshot = TraceContextHolder.get();
        return () -> {
            TraceContext previous = TraceContextHolder.get();
            try {
                TraceContextHolder.set(snapshot);
                task.run();
            } finally {
                // 关键步骤：任务执行完必须恢复/清理工作线程的上下文，
                // 而不是简单地remove，因为如果这个工作线程本身在嵌套场景下
                // 已经持有了别的上下文，remove可能会误删；
                // 更严谨的做法是恢复到进入前的状态（通常为null，因为线程池线程默认不持有业务上下文）
                if (previous == null) {
                    TraceContextHolder.clear();
                } else {
                    TraceContextHolder.set(previous);
                }
            }
        };
    }

    /**
     * 包装Callable，逻辑与wrap(Runnable)一致
     */
    private <T> Callable<T> wrap(Callable<T> task) {
        TraceContext snapshot = TraceContextHolder.get();
        return () -> {
            TraceContext previous = TraceContextHolder.get();
            try {
                TraceContextHolder.set(snapshot);
                return task.call();
            } finally {
                if (previous == null) {
                    TraceContextHolder.clear();
                } else {
                    TraceContextHolder.set(previous);
                }
            }
        };
    }

    @Override
    public <T> List<Future<T>> invokeAll(Collection<? extends Callable<T>> tasks) throws InterruptedException {
        List<Callable<T>> wrapped = tasks.stream().map(this::wrap).collect(Collectors.toList());
        return delegate.invokeAll(wrapped);
    }

    @Override
    public void shutdown() {
        delegate.shutdown();
    }

    @Override
    public List<Runnable> shutdownNow() {
        return delegate.shutdownNow();
    }

    @Override
    public boolean isShutdown() {
        return delegate.isShutdown();
    }

    @Override
    public boolean isTerminated() {
        return delegate.isTerminated();
    }

    @Override
    public boolean awaitTermination(long timeout, TimeUnit unit) throws InterruptedException {
        return delegate.awaitTermination(timeout, unit);
    }

    // 其余ExecutorService方法（invokeAny等）省略，均按相同的wrap模式实现
}
```

需要特别强调三个容易被忽视的工程细节：

1. **线程池的所有提交入口都要包装**：不仅`execute`、`submit`，还包括`invokeAll`、`invokeAny`、定时任务的`schedule`系列方法，任何一个遗漏都可能造成局部的上下文丢失。

2. **CompletableFuture的默认线程池同样需要处理**：`CompletableFuture.supplyAsync`如果不指定线程池会使用`ForkJoinPool.commonPool()`，这是一个全局共享的线程池，同样存在跨线程传播问题，必须显式传入包装过的线程池。

3. **清理必须在finally中执行、且要考虑嵌套场景**：如果简单地在任务结束后调用`remove()`，在某些线程池线程本身已经处于嵌套调用（线程池线程内部又提交了子任务到同一个线程池，理论上应避免但业务代码难以完全杜绝）的场景下，可能会错误地清空外层还需要用到的上下文。更稳妥的写法是像上面代码那样，记录进入前的状态，结束后恢复到该状态，而不是无差别清空。

```java
/**
 * CompletableFuture场景下的正确用法示例
 */
public class CompletableFutureTraceExample {

    private final TraceContextAwareExecutor tracedExecutor =
            new TraceContextAwareExecutor(Executors.newFixedThreadPool(20));

    public CompletableFuture<String> queryUserInfoAsync(String userId) {
        // 显式指定包装后的线程池，而不是使用默认的ForkJoinPool.commonPool()
        return CompletableFuture.supplyAsync(() -> {
            // 此处能正确读取到调用方线程的TraceContext
            TraceContext context = TraceContextHolder.get();
            System.out.println("异步任务中的traceId: " + context.getTraceId());
            return doQueryUserInfo(userId);
        }, tracedExecutor);
    }

    private String doQueryUserInfo(String userId) {
        return "user-" + userId;
    }
}
```

### 3.6 上下文的分类与生命周期

追踪上下文中承载的信息种类繁多，如果不加区分地把所有信息都随着每一次RPC调用无脑透传下去，会带来两个问题：一是浪费网络带宽（很多信息只在当前这一跳有意义，没必要传给下游）；二是语义混乱（有些信息应该随着链路一直存在，有些信息只在当前这一跳临时使用）。因此需要从两个维度对上下文信息做分类。

#### 3.6.1 按信息内容分类

| 分类 | 包含字段 | 说明 |
|------|---------|------|
| **基础信息** | traceId、spanId、debug标记 | 标识一次调用在整条链路中的位置，是链路重建的核心依据 |
| **调用信息** | appkey（调用方/被调方标识）、method（方法名）、startTime、endTime | 描述"谁在什么时间调用了谁的什么方法"，是耗时分析和拓扑构建的数据来源 |
| **机器信息** | ip（本机IP）、swimlane（泳道标识） | 用于定位具体是哪台机器处理的请求，以及在多环境/灰度发布场景下判断该请求应该被路由到哪个环境 |
| **自定义信息** | annotation（业务标注）、context（透传上下文/baggage） | 业务方可以自行往上下文中塞入自定义的key-value，例如订单ID、用户等级、实验分桶号等，便于按业务维度检索链路 |

#### 3.6.2 按生命周期分类：永久上下文 vs 一次性上下文

除了按内容分类，上下文信息还必须按**生命周期**做区分，这决定了信息在向下游传播时是"一直带着走"还是"只带一跳就丢弃"：

- **永久上下文（forever context）**：与整条调用链的生命周期保持一致，从入口生成后，无论经过多少跳、多少个服务，都要原样透传下去，不能中途丢失。典型例子：traceId本身、swimlane泳道标识、灰度实验分桶号、根请求的用户身份标识。这类信息的特点是"下游所有节点都可能需要用到"。

- **一次性上下文（one-step context）**：只在当前这一跳（当前发起方到直接下游）之间有效，下游服务收到后不需要、也不应该继续往更下游传播。典型例子：spanId（每一跳都要重新派生出新的子spanId，而不是原样传递父spanId）、当前这一跳的调用开始时间/结束时间、当前这一跳的重试次数标记。

```java
/**
 * 上下文生命周期管理器
 * 区分"永久上下文"（跟随整条链路）与"一次性上下文"（仅传递一跳）
 */
public final class ContextLifecycleManager {

    /**
     * 永久上下文的key集合：这些key会在每一跳调用时被自动带入下一跳的请求中
     * 典型：泳道、灰度标识、根用户身份等需要贯穿全链路的信息
     */
    private static final Set<String> FOREVER_CONTEXT_KEYS = Set.of(
            "swimlane", "gray.label", "root.userId", "trace.debug"
    );

    private ContextLifecycleManager() {
    }

    /**
     * 构造下一跳需要透传的上下文：
     * 1. 永久上下文原样带入
     * 2. 一次性上下文（本次调用临时塞入的自定义信息）不会自动带入下一跳，
     *    除非业务显式声明该key属于永久上下文
     */
    public static Map<String, String> buildNextHopContext(TraceContext current, Map<String, String> oneStepExtra) {
        Map<String, String> nextHop = new HashMap<>();
        // 只透传永久上下文中标记过的字段
        for (String key : FOREVER_CONTEXT_KEYS) {
            String value = current.getBaggage().get(key);
            if (value != null) {
                nextHop.put(key, value);
            }
        }
        // 一次性上下文只会被当前这一次调用使用，不会写入nextHop，
        // 调用完成后即失效，不会污染下游或者被再下一跳继续传播
        return nextHop;
    }

    /**
     * 判断某个上下文key是否属于永久上下文
     */
    public static boolean isForever(String key) {
        return FOREVER_CONTEXT_KEYS.contains(key);
    }
}
```

这个区分在实际排障中非常关键：如果把本应是一次性的上下文（比如某次调用的临时重试标记）错误地设计成永久上下文一路透传下去，会导致下游所有服务都携带着这个本不该属于它们的标记，污染下游的行为判断（例如下游服务看到"重试标记"以为自己也该走重试逻辑）；反过来，如果把本应贯穿全链路的信息（比如泳道标识）错误地设计成一次性上下文，会导致灰度流量在经过第二跳之后"失联"，错误地路由回了正常环境，造成灰度验证失真。

### 3.7 采样策略体系

#### 3.7.1 为什么必须采样

前文提到，全站每天的Span总量可以达到2000亿级别，如果全量采集，无论是消息队列的吞吐能力、流计算的处理能力，还是HBase/ES的存储成本，都会成为无法承受之重。因此，**默认情况下系统按1%的概率对请求进行采样**，即平均每100次调用中只有1次会被完整采集并上报。这个比例经过实践验证，既能将存储和计算成本控制在合理范围内，又能通过统计规律较好地反映系统的整体健康状况（大数定律保证只要样本量足够大，1%的采样依然能准确反映延迟分布、错误率等关键指标）。

#### 3.7.2 采样决策的层次

采样并不是"一刀切"的全局单一比例，而是支持多个层次的精细化配置：

1. **全局默认采样率**：未做任何特殊配置的方法，默认按1%采样；
2. **方法级别可配置采样率**：对于核心链路（如支付下单）或者问题排查中的重点方法，可以单独配置更高的采样率，甚至配置为100%；
3. **异常强制采集**：无论采样决策的结果如何，只要一次调用发生了错误（抛异常、返回错误码）或者超时，都强制完整采集并上报，因为异常链路的排查价值远高于正常链路，而异常本身发生频率通常较低，全量采集不会带来太大的存储压力；
4. **Debug模式全量采样**：当开发或测试人员需要临时排查某条具体链路时，可以在请求上显式携带debug参数，一旦上游检测到debug标记，会强制对这条链路及其后续所有下游调用都按100%采样，并且开启"动态Debug"（见3.11节）采集方法的入参和出参，问题定位完成后关闭该标记即可恢复默认采样率，不需要修改任何代码或者重启服务。

```java
/**
 * 采样决策器
 * 决策优先级：debug模式 > 异常强制采集 > 方法级配置采样率 > 全局默认采样率
 */
public class SampleDecider {

    public static final SampleDecider INSTANCE = new SampleDecider();

    /** 全局默认采样率：1% */
    private static final double DEFAULT_SAMPLE_RATE = 0.01;

    /** 方法级采样率配置，支持动态从配置中心下发热更新 */
    private final Map<String, Double> methodSampleRateConfig = new ConcurrentHashMap<>();

    private final Random random = new Random();

    /**
     * 请求入口处的采样决策：还未知道调用结果是否异常，
     * 因此这里只能基于debug标记和方法级/全局采样率做初步决策
     */
    public boolean decide(String method) {
        double sampleRate = methodSampleRateConfig.getOrDefault(method, DEFAULT_SAMPLE_RATE);
        return random.nextDouble() < sampleRate;
    }

    /**
     * 请求结束后的二次决策：即使初步决策未命中采样，
     * 只要本次调用出现了异常或超时，也要强制标记为需要上报，
     * 这样才能保证"异常链路必采集"
     */
    public boolean shouldForceSample(boolean initiallySampled, SpanStatus status) {
        if (initiallySampled) {
            return true;
        }
        return status == SpanStatus.ERROR || status == SpanStatus.TIMEOUT;
    }

    /**
     * debug模式下强制全量采样，且标记为debug span
     */
    public boolean isDebugForced(TraceContext context) {
        return context != null && context.isDebug();
    }

    /** 支持运行时动态更新某个方法的采样率，无需重启应用 */
    public void updateMethodSampleRate(String method, double rate) {
        if (rate < 0 || rate > 1) {
            throw new IllegalArgumentException("采样率必须在0到1之间");
        }
        methodSampleRateConfig.put(method, rate);
    }
}
```

#### 3.7.3 头部采样 vs 尾部采样

采样决策还可以按"决策时机"分为两种模式：

- **头部采样（Head-based Sampling）**：在链路入口处（例如网关接收到请求的一瞬间）就决定这条链路是否被采样，一旦决定采样，这个决策会通过永久上下文（见3.6.2节）一路透传给所有下游服务，所有下游都遵循同一个采样决策，保证一条链路要么完整地被采集，要么完全不被采集，不会出现"链路采集了一半"的情况。这是本文重点介绍的方案，也是Dapper论文采用的方案，优点是实现简单、开销可预测。

- **尾部采样（Tail-based Sampling）**：先完整采集所有Span并临时缓存，等一条链路完全结束后，再根据整条链路的综合特征（是否有异常、总耗时是否超过阈值等）决定是否保留这条链路的数据，否则丢弃。优点是可以"事后诸葛亮"，精确捕获所有异常/慢链路而不遗漏，缺点是需要额外的临时存储和更复杂的收集逻辑，实现和运维成本更高。

工程实践中通常采用头部采样为主（保证低成本的常态运行），辅以异常强制采集和debug模式（相当于对尾部采样理念的简化补偿），在实现复杂度和可观测性之间取得平衡。

### 3.8 数据采集与上报链路

#### 3.8.1 SDK侧：异步写日志

为了保证追踪系统"零阻塞"业务线程，SDK在生成Span之后，并不会同步地发起网络调用去上报，而是先写入本地的一个有界内存队列，再由专门的后台线程批量写入本地日志文件。

```java
/**
 * Span上报器：业务线程只负责把Span丢进队列，真正的落盘由后台线程异步完成
 * 队列采用有界队列，队列满时直接丢弃（宁可丢部分追踪数据，也不能阻塞业务线程）
 */
public class SpanReporter {

    private static final int QUEUE_CAPACITY = 100_000;

    /** 有界阻塞队列，防止内存无限增长 */
    private final BlockingQueue<Span> spanQueue = new ArrayBlockingQueue<>(QUEUE_CAPACITY);

    /** 丢弃计数器，用于监控告警 */
    private final LongAdder droppedCount = new LongAdder();

    private final ScheduledExecutorService flushExecutor =
            Executors.newSingleThreadScheduledExecutor(r -> {
                Thread t = new Thread(r, "span-flush-thread");
                t.setDaemon(true);
                return t;
            });

    private final SpanFileWriter fileWriter;

    public SpanReporter(SpanFileWriter fileWriter) {
        this.fileWriter = fileWriter;
        // 每100毫秒批量flush一次，兼顾实时性和IO效率
        flushExecutor.scheduleWithFixedDelay(this::flush, 100, 100, TimeUnit.MILLISECONDS);
    }

    /**
     * 业务线程调用的上报入口：非阻塞，队列满则直接丢弃并计数
     */
    public void report(Span span) {
        boolean offered = spanQueue.offer(span);
        if (!offered) {
            droppedCount.increment();
        }
    }

    /**
     * 后台线程批量取出Span并写入本地日志文件
     */
    private void flush() {
        List<Span> batch = new ArrayList<>();
        spanQueue.drainTo(batch, 5000);
        if (!batch.isEmpty()) {
            fileWriter.writeBatch(batch);
        }
    }

    public long getDroppedCount() {
        return droppedCount.sum();
    }
}
```

#### 3.8.2 Agent侧：日志采集与推送

部署在每台机器上的采集Agent，以类似`tail -f`的方式持续监听追踪日志文件的新增内容，解析后批量推送到Kafka。Agent自身也要做限流和背压处理，避免机器上日志量突增时把Kafka或者自己的内存打爆。

```java
/**
 * 采集Agent核心逻辑：实时Tail日志文件，批量推送到Kafka
 */
public class TraceLogAgent {

    private final KafkaProducer<String, byte[]> kafkaProducer;
    private final String topic;
    /** 每批次最大条数 */
    private static final int BATCH_SIZE = 500;
    /** 每批次最大等待时间，避免消息量小时数据迟迟不发送 */
    private static final long BATCH_MAX_WAIT_MS = 200;

    public TraceLogAgent(KafkaProducer<String, byte[]> kafkaProducer, String topic) {
        this.kafkaProducer = kafkaProducer;
        this.topic = topic;
    }

    /**
     * 处理从日志文件中读取到的一行原始记录
     */
    public void onLogLine(String rawLine, List<String> batchBuffer) {
        if (!isValidTraceLog(rawLine)) {
            return; // 过滤掉格式不合法的行，避免污染下游
        }
        batchBuffer.add(rawLine);
        if (batchBuffer.size() >= BATCH_SIZE) {
            flushBatch(batchBuffer);
        }
    }

    private boolean isValidTraceLog(String line) {
        return line != null && line.contains("traceId=");
    }

    private void flushBatch(List<String> batchBuffer) {
        if (batchBuffer.isEmpty()) {
            return;
        }
        byte[] payload = compress(String.join("\n", batchBuffer));
        // 按TraceId做Key路由到Kafka分区，尽量让同一条链路的数据落到同一分区，
        // 便于下游Storm按Key做窗口聚合时减少跨分区join的开销
        String traceId = extractTraceId(batchBuffer.get(0));
        ProducerRecord<String, byte[]> record = new ProducerRecord<>(topic, traceId, payload);
        kafkaProducer.send(record, (metadata, exception) -> {
            if (exception != null) {
                // 发送失败仅记录本地监控指标，不重试阻塞采集流程，
                // 保证采集侧的稳定性优先于数据的绝对完整性
                AgentMetrics.incrementSendFailure();
            }
        });
        batchBuffer.clear();
    }

    private String extractTraceId(String line) {
        int idx = line.indexOf("traceId=");
        int end = line.indexOf(',', idx);
        return line.substring(idx + 8, end > 0 ? end : line.length());
    }

    private byte[] compress(String content) {
        // 实际实现使用GZIP或Snappy压缩，减少网络传输开销，此处简化
        return content.getBytes(StandardCharsets.UTF_8);
    }
}
```

#### 3.8.3 Storm侧：链路聚合

Storm消费Kafka中的原始Span数据，核心任务是按TraceId做窗口聚合，把分散的clientSpan和serverSpan拼接成完整的调用树，同时在聚合过程中做异常检测和拓扑关系提取。

```java
/**
 * Storm Bolt：按TraceId聚合Span，拼接完整调用链路
 * 简化示意，实际生产实现会涉及状态存储、超时窗口清理等更复杂的逻辑
 */
public class TraceAggregationBolt extends BaseRichBolt {

    private OutputCollector collector;
    /** 按traceId缓存尚未聚合完成的Span集合，超过窗口时间未收全则强制输出当前已有数据 */
    private final Map<String, List<Span>> traceBuffer = new ConcurrentHashMap<>();
    /** 每条链路的聚合等待窗口，超时后强制flush，避免长尾链路无限占用内存 */
    private static final long AGGREGATION_WINDOW_MS = 30_000;

    @Override
    public void prepare(Map<String, Object> topoConf, TopologyContext context, OutputCollector collector) {
        this.collector = collector;
    }

    @Override
    public void execute(Tuple input) {
        Span span = deserialize(input.getBinaryByField("payload"));
        traceBuffer.computeIfAbsent(span.getTraceId(), k -> new CopyOnWriteArrayList<>()).add(span);
        collector.ack(input);
    }

    /**
     * 定时任务调用：检查所有缓存中的链路，把已经超过聚合窗口时间的链路强制输出
     */
    public void flushExpiredTraces() {
        long now = System.currentTimeMillis();
        Iterator<Map.Entry<String, List<Span>>> iterator = traceBuffer.entrySet().iterator();
        while (iterator.hasNext()) {
            Map.Entry<String, List<Span>> entry = iterator.next();
            List<Span> spans = entry.getValue();
            long lastUpdateTime = spans.stream().mapToLong(Span::getEndTime).max().orElse(0);
            if (now - lastUpdateTime > AGGREGATION_WINDOW_MS) {
                TraceTree tree = TraceTreeBuilder.build(entry.getKey(), spans);
                emitToStorage(tree);
                detectAnomaly(tree);
                extractTopology(tree);
                iterator.remove();
            }
        }
    }

    private void emitToStorage(TraceTree tree) {
        collector.emit(new Values(tree));
    }

    private void detectAnomaly(TraceTree tree) {
        if (tree.hasErrorSpan() || tree.totalDuration() > tree.getSlaThreshold()) {
            collector.emit("anomaly-stream", new Values(tree));
        }
    }

    private void extractTopology(TraceTree tree) {
        collector.emit("topology-stream", new Values(tree.extractCallEdges()));
    }

    private Span deserialize(byte[] bytes) {
        // 反序列化逻辑省略
        return null;
    }

    @Override
    public void declareOutputFields(OutputFieldsDeclarer declarer) {
        declarer.declare(new Fields("traceTree"));
        declarer.declareStream("anomaly-stream", new Fields("traceTree"));
        declarer.declareStream("topology-stream", new Fields("edges"));
    }
}
```

### 3.9 数据存储与索引设计

#### 3.9.1 HBase：以TraceId为rowKey

链路查询中最高频的场景是"根据一个TraceId查出这条链路的完整信息"，这是一个典型的点查场景。HBase天然支持按rowKey做高效的精确查询和范围扫描，因此把TraceId直接设计为HBase的rowKey，同一TraceId下的所有Span作为该行的多个列或者序列化为一个大的列值存储，一次get操作即可拿到完整链路数据，查询延迟可以稳定在毫秒级。

```java
/**
 * HBase存储客户端：以TraceId为rowKey存取完整链路数据
 */
public class TraceHBaseStore {

    private static final byte[] COLUMN_FAMILY = Bytes.toBytes("t");
    private static final byte[] SPANS_QUALIFIER = Bytes.toBytes("spans");

    private final Table table;

    public TraceHBaseStore(Table table) {
        this.table = table;
    }

    /**
     * 写入一条完整链路：rowKey直接使用traceId，
     * 由于traceId生成时已经包含了时间戳前缀，天然具备一定的时间局部性，
     * 有利于HBase按时间做Region的均衡拆分，避免热点
     */
    public void saveTrace(String traceId, List<Span> spans) throws IOException {
        Put put = new Put(Bytes.toBytes(traceId));
        byte[] serialized = SpanSerializer.serializeList(spans);
        put.addColumn(COLUMN_FAMILY, SPANS_QUALIFIER, serialized);
        table.put(put);
    }

    /**
     * 按TraceId精确查询完整链路，典型的点查场景，毫秒级返回
     */
    public List<Span> getTrace(String traceId) throws IOException {
        Get get = new Get(Bytes.toBytes(traceId));
        Result result = table.get(get);
        if (result.isEmpty()) {
            return Collections.emptyList();
        }
        byte[] value = result.getValue(COLUMN_FAMILY, SPANS_QUALIFIER);
        return SpanSerializer.deserializeList(value);
    }
}
```

#### 3.9.2 Elasticsearch：多维度检索

除了"按TraceId点查"，另一大类查询需求是"按业务条件检索"，例如"查询过去1小时内订单服务下耗时超过1秒的所有调用"、"查询某个IP上发生过的所有错误链路"。这类多维度、组合条件的检索场景是HBase的短板，但正是Elasticsearch的强项。因此在Storm聚合完链路数据后，除了写入HBase存完整数据，还会把每个Span的关键字段（服务名、方法名、IP、状态、耗时、时间戳、自定义标签）抽取出来写入ES，建立倒排索引。

```java
/**
 * Elasticsearch索引写入器：抽取Span关键字段，支持多维度检索
 */
public class SpanEsIndexer {

    private final RestHighLevelClient esClient;
    private static final String INDEX_PREFIX = "trace-span-";

    public SpanEsIndexer(RestHighLevelClient esClient) {
        this.esClient = esClient;
    }

    public void index(Span span) throws IOException {
        Map<String, Object> doc = new HashMap<>();
        doc.put("traceId", span.getTraceId());
        doc.put("spanId", span.getSpanId());
        doc.put("appKey", span.getAppKey());
        doc.put("method", span.getMethod());
        doc.put("ip", span.getIp());
        doc.put("status", span.getStatus().name());
        doc.put("duration", span.getDuration());
        doc.put("startTime", span.getStartTime());
        doc.put("swimlane", span.getSwimlane());

        // 按天分索引，便于历史数据的冷热分离和定期清理过期索引
        String indexName = INDEX_PREFIX + DateUtil.formatDate(span.getStartTime());
        IndexRequest request = new IndexRequest(indexName).source(doc, XContentType.JSON);
        esClient.index(request, RequestOptions.DEFAULT);
    }

    /**
     * 典型检索场景：按服务名+时间范围+耗时阈值查询慢调用
     */
    public SearchResponse searchSlowCalls(String appKey, long startTime, long endTime, long durationThresholdMs)
            throws IOException {
        BoolQueryBuilder query = QueryBuilders.boolQuery()
                .must(QueryBuilders.termQuery("appKey", appKey))
                .must(QueryBuilders.rangeQuery("startTime").gte(startTime).lte(endTime))
                .must(QueryBuilders.rangeQuery("duration").gte(durationThresholdMs));

        SearchSourceBuilder sourceBuilder = new SearchSourceBuilder()
                .query(query)
                .sort("duration", SortOrder.DESC)
                .size(100);

        SearchRequest searchRequest = new SearchRequest(INDEX_PREFIX + "*").source(sourceBuilder);
        return esClient.search(searchRequest, RequestOptions.DEFAULT);
    }
}
```

#### 3.9.3 HDFS：离线全量分析

HBase和ES主要服务于在线查询场景，对存储成本和查询延迟都比较敏感，因此通常只保留近期（例如最近7天到15天）的数据。而全量的原始Span数据会额外落一份到HDFS，用于支撑一些不要求实时性、但计算量较大的离线分析任务，例如：全站服务依赖关系的月度统计报表、慢调用模式的挖掘、容量规划所需的历史调用量趋势分析等。这类任务通过MapReduce（或Spark）批处理完成，不占用在线查询链路的计算和存储资源。

```java
/**
 * MapReduce离线任务示例：统计每个服务每天的平均耗时和错误率
 */
public class DailyServiceStatsJob {

    /** Mapper：从HDFS上的原始Span文件中解析出(appKey_date, duration/status)键值对 */
    public static class StatsMapper extends Mapper<LongWritable, Text, Text, Text> {

        @Override
        protected void map(LongWritable key, Text value, Context context)
                throws IOException, InterruptedException {
            Span span = SpanTextParser.parse(value.toString());
            if (span == null) {
                return;
            }
            String date = DateUtil.formatDate(span.getStartTime());
            String outKey = span.getAppKey() + "_" + date;
            String outValue = span.getDuration() + "," + span.getStatus().name();
            context.write(new Text(outKey), new Text(outValue));
        }
    }

    /** Reducer：按(appKey, date)聚合，计算平均耗时和错误率 */
    public static class StatsReducer extends Reducer<Text, Text, Text, Text> {

        @Override
        protected void reduce(Text key, Iterable<Text> values, Context context)
                throws IOException, InterruptedException {
            long totalDuration = 0;
            long count = 0;
            long errorCount = 0;
            for (Text value : values) {
                String[] parts = value.toString().split(",");
                totalDuration += Long.parseLong(parts[0]);
                count++;
                if (!"SUCCESS".equals(parts[1])) {
                    errorCount++;
                }
            }
            double avgDuration = count == 0 ? 0 : (double) totalDuration / count;
            double errorRate = count == 0 ? 0 : (double) errorCount / count;
            context.write(key, new Text(String.format("avgDuration=%.2f,errorRate=%.4f,count=%d",
                    avgDuration, errorRate, count)));
        }
    }
}
```

### 3.10 调用拓扑图构建

服务依赖拓扑图是链路追踪数据的一个重要衍生产物，它回答的问题是"服务A的上下游都有谁"，而不是"某一次具体请求经过了哪些服务"。拓扑图的构建思路是：在Storm聚合链路时，把每个Span的"调用方appKey → 被调方appKey"这一条边提取出来，按时间窗口做去重聚合，统计每条边的调用次数、平均耗时、错误率，最终汇总成一张服务依赖关系图。

```java
/**
 * 服务依赖边：表示两个服务之间的调用关系统计
 */
public final class ServiceCallEdge {

    private final String fromAppKey;
    private final String toAppKey;
    private final long callCount;
    private final long errorCount;
    private final double avgDurationMs;

    public ServiceCallEdge(String fromAppKey, String toAppKey, long callCount, long errorCount, double avgDurationMs) {
        this.fromAppKey = fromAppKey;
        this.toAppKey = toAppKey;
        this.callCount = callCount;
        this.errorCount = errorCount;
        this.avgDurationMs = avgDurationMs;
    }

    public String getFromAppKey() {
        return fromAppKey;
    }

    public String getToAppKey() {
        return toAppKey;
    }

    public long getCallCount() {
        return callCount;
    }

    public long getErrorCount() {
        return errorCount;
    }

    public double getAvgDurationMs() {
        return avgDurationMs;
    }

    public double getErrorRate() {
        return callCount == 0 ? 0 : (double) errorCount / callCount;
    }
}

/**
 * 拓扑图聚合器：按时间窗口滑动聚合调用边，构建全站服务依赖图
 */
class TopologyAggregator {

    /** key为"fromAppKey->toAppKey"，value为该边的滑动窗口统计数据 */
    private final Map<String, EdgeStatWindow> edgeStats = new ConcurrentHashMap<>();

    public void onCallEdge(String fromAppKey, String toAppKey, long durationMs, boolean success) {
        String edgeKey = fromAppKey + "->" + toAppKey;
        edgeStats.computeIfAbsent(edgeKey, k -> new EdgeStatWindow()).record(durationMs, success);
    }

    public List<ServiceCallEdge> snapshot() {
        List<ServiceCallEdge> result = new ArrayList<>();
        for (Map.Entry<String, EdgeStatWindow> entry : edgeStats.entrySet()) {
            String[] parts = entry.getKey().split("->");
            EdgeStatWindow window = entry.getValue();
            result.add(new ServiceCallEdge(parts[0], parts[1], window.getCallCount(),
                    window.getErrorCount(), window.getAvgDurationMs()));
        }
        return result;
    }

    /** 单条边的滑动窗口统计 */
    private static class EdgeStatWindow {
        private final LongAdder callCount = new LongAdder();
        private final LongAdder errorCount = new LongAdder();
        private final LongAdder totalDuration = new LongAdder();

        void record(long durationMs, boolean success) {
            callCount.increment();
            totalDuration.add(durationMs);
            if (!success) {
                errorCount.increment();
            }
        }

        long getCallCount() {
            return callCount.sum();
        }

        long getErrorCount() {
            return errorCount.sum();
        }

        double getAvgDurationMs() {
            long count = callCount.sum();
            return count == 0 ? 0 : (double) totalDuration.sum() / count;
        }
    }
}
```

拓扑图构建完成后，可视化层将其渲染为一张有向图（DAG），节点为服务（appKey），边为调用关系，边上标注调用量、平均耗时、错误率等指标，颜色可以按错误率或耗时做梯度渲染（例如错误率超过阈值的边标红），帮助运维和开发人员一眼看出系统中的薄弱环节。拓扑图还可以按泳道（swimlane）过滤，单独查看某个灰度环境下的调用关系，验证灰度发布是否按预期路由。

### 3.11 动态Debug与方法级采参

#### 3.11.1 为什么需要动态Debug

默认1%的采样率下，大多数具体的一次调用是不会被采集的；即使命中采样，正常情况下Span中也只记录耗时、状态等元信息，并不会记录方法的具体入参和返回值——这是出于两个考虑：一是入参出参往往包含大对象或者敏感信息，序列化开销和存储开销都不小；二是绝大多数正常调用并不需要看到具体参数，元信息已经足够支撑耗时分析和链路重建。

但在实际问题排查中，经常会遇到"某个方法在特定参数下才会出错或者变慢"的场景，仅凭耗时和状态码无法定位根因，必须能看到方法的实际入参和返回值才能复现问题。为此需要支持**动态Debug**能力：无需修改代码、无需重启应用，运行时动态开启某个方法（甚至精确到某一次请求）的详细参数采集，问题定位完成后再动态关闭，避免长期开启带来的性能和存储负担。

#### 3.11.2 动态Debug的触发方式

动态Debug通常支持两种触发方式：

1. **按TraceId/请求维度触发**：在请求入口显式携带debug标记（例如HTTP Header中带上`X-Trace-Debug: true`，或者接口参数中加入`debug=true`），该标记会作为永久上下文（见3.6.2节）随链路一路透传到所有下游服务，所有经过这条链路的调用都会被强制全量采样，并且采集详细的方法入参和出参。这种方式适合"针对一次具体的问题请求"做端到端排查。

2. **按方法维度触发（运行时开关）**：通过配置中心动态下发"对某个appKey的某个方法开启参数采集"的指令，SDK监听到配置变更后，对该方法后续所有经过的调用都临时开启参数采集，不需要请求方显式携带任何标记。这种方式适合"已知某个方法有问题，但不确定具体是哪次请求触发"的排查场景，可以先开启采集观察一段时间，收集到足够样本后再关闭。

```java
/**
 * 动态Debug配置：支持按方法维度运行时开启/关闭参数采集，
 * 配置来源于配置中心，支持热更新，无需重启应用
 */
public class DynamicDebugConfig {

    public static final DynamicDebugConfig INSTANCE = new DynamicDebugConfig();

    /** key为方法全限定名，value为该方法是否开启参数采集 */
    private volatile Set<String> debugEnabledMethods = ConcurrentHashMap.newKeySet();

    /** 开启参数采集的方法，其采集能力会在到期时间后自动关闭，避免忘记手动关闭 */
    private final Map<String, Long> debugExpireTime = new ConcurrentHashMap<>();

    private DynamicDebugConfig() {
    }

    /** 配置中心推送变更时回调，全量替换当前配置 */
    public void onConfigChange(Set<String> methods, long durationMs) {
        this.debugEnabledMethods = new HashSet<>(methods);
        long expireAt = System.currentTimeMillis() + durationMs;
        for (String method : methods) {
            debugExpireTime.put(method, expireAt);
        }
    }

    /**
     * 判断某次调用是否应该采集详细的方法入参出参：
     * 1. 请求本身携带了debug标记（按请求维度）
     * 2. 该方法被运行时配置为全局开启debug，且未过期（按方法维度）
     */
    public boolean shouldCaptureParams(TraceContext context, String method) {
        if (context != null && context.isDebug()) {
            return true;
        }
        Long expireAt = debugExpireTime.get(method);
        return expireAt != null && System.currentTimeMillis() < expireAt
                && debugEnabledMethods.contains(method);
    }
}
```

#### 3.11.3 参数采集的实现

参数采集通常通过AOP切面在方法调用前后拦截，把方法的入参和返回值序列化后作为Span的一个特殊标注字段（复用3.6.1节annotation字段），需要注意对敏感字段（如身份证号、手机号、密码）做脱敏处理，并且要对超大对象做截断，避免一次调用产生的Span数据过大影响存储和传输效率。

```java
/**
 * 动态Debug切面：在开启动态Debug的方法上采集入参和返回值
 * 通过AOP环绕通知实现，业务代码无需任何改造
 */
@Aspect
public class DynamicDebugAspect {

    private static final int MAX_PARAM_LENGTH = 2000;

    @Around("execution(* com.example.service..*.*(..))")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        String method = joinPoint.getSignature().toShortString();
        TraceContext context = TraceContextHolder.get();
        boolean captureParams = DynamicDebugConfig.INSTANCE.shouldCaptureParams(context, method);

        if (!captureParams) {
            return joinPoint.proceed();
        }

        String requestSnapshot = safeSerialize(joinPoint.getArgs());
        long start = System.currentTimeMillis();
        Object result = null;
        Throwable thrown = null;
        try {
            result = joinPoint.proceed();
            return result;
        } catch (Throwable t) {
            thrown = t;
            throw t;
        } finally {
            long cost = System.currentTimeMillis() - start;
            String responseSnapshot = thrown != null
                    ? "exception:" + thrown.getClass().getName() + ":" + thrown.getMessage()
                    : safeSerialize(result);
            if (context != null) {
                // 将采集到的入参出参写入annotation，最终随Span一起上报，
                // 仅当前这一次调用记录，不会作为永久上下文透传给下游
                Span debugSpan = Span.builder()
                        .traceId(context.getTraceId())
                        .spanId(context.getSpanId())
                        .role(SpanRole.SERVER)
                        .method(method)
                        .startTime(start)
                        .endTime(start + cost)
                        .debug(true)
                        .addAnnotation("request.params", requestSnapshot)
                        .addAnnotation("response.result", responseSnapshot)
                        .sampled(true)
                        .build();
                SpanReporterHolder.get().report(debugSpan);
            }
        }
    }

    /**
     * 安全序列化：脱敏 + 截断，避免敏感信息泄露和Span数据体积过大
     */
    private String safeSerialize(Object obj) {
        try {
            String json = JsonUtil.toJson(obj);
            json = SensitiveDataMasker.mask(json);
            if (json.length() > MAX_PARAM_LENGTH) {
                json = json.substring(0, MAX_PARAM_LENGTH) + "...(truncated)";
            }
            return json;
        } catch (Exception e) {
            return "serialize_error:" + e.getMessage();
        }
    }
}

/**
 * 敏感信息脱敏工具：对常见敏感字段做掩码处理
 */
final class SensitiveDataMasker {

    private static final Pattern PHONE_PATTERN = Pattern.compile("(\\d{3})\\d{4}(\\d{4})");
    private static final Pattern ID_CARD_PATTERN = Pattern.compile("(\\d{6})\\d{8,10}(\\w{4})");

    private SensitiveDataMasker() {
    }

    static String mask(String json) {
        String masked = PHONE_PATTERN.matcher(json).replaceAll("$1****$2");
        masked = ID_CARD_PATTERN.matcher(masked).replaceAll("$1********$2");
        return masked;
    }
}
```

#### 3.11.4 动态Debug的安全边界

动态Debug能力如果不加限制，本身会成为新的风险点，因此需要设置若干安全边界：

- **自动过期**：任何一次动态Debug开启操作都必须带上过期时间（如30分钟），到期自动失效，避免遗忘关闭导致长期产生大量详细采集数据；
- **采集范围限制**：按方法维度开启debug时，应支持只对特定机器、特定泳道生效，而不是全网所有实例同时开启，降低对整体系统性能的影响；
- **脱敏前置**：任何入参出参在落盘和上报之前必须先脱敏，脱敏规则应作为公共基础能力统一维护，而不是依赖各业务方自行实现，避免遗漏；
- **权限管控**：开启动态Debug的操作本身需要走权限审批，并留存操作审计日志，防止被滥用于获取业务敏感数据。

## 4. 异常处理与容错机制

### 4.1 追踪系统自身故障不能影响业务

分布式链路追踪系统的第一原则是：**追踪系统的任何故障都不能影响业务系统的正常运行**。这一原则贯穿了前面所有的设计决策——从SDK异步写本地日志、有界队列满了直接丢弃，到Agent发送Kafka失败仅记录监控指标而不重试阻塞，都是这一原则的具体体现。下面系统梳理各个环节可能出现的异常场景及应对策略。

```java
/**
 * SDK埋点层的异常隔离：任何追踪相关的异常都必须被捕获，绝不能向上抛出影响业务调用
 */
public class SafeTracingInterceptor implements RpcFilter {

    private static final Logger LOGGER = LoggerFactory.getLogger(SafeTracingInterceptor.class);

    private final RpcFilter delegateTracingLogic;

    public SafeTracingInterceptor(RpcFilter delegateTracingLogic) {
        this.delegateTracingLogic = delegateTracingLogic;
    }

    @Override
    public RpcResponse invoke(RpcInvoker invoker, RpcRequest request) {
        try {
            return delegateTracingLogic.invoke(invoker, request);
        } catch (TracingException e) {
            // 追踪逻辑本身出错，记录日志后直接透传原始业务调用，不影响业务结果
            LOGGER.warn("链路追踪埋点异常，已降级为直接调用，method={}", request.getMethodName(), e);
            return invoker.invoke(request);
        }
    }
}
```

### 4.2 各环节的异常场景与应对

| 环节 | 可能出现的异常 | 应对策略 |
|------|---------------|---------|
| SDK生成Span | 序列化异常、ThreadLocal脏数据 | try-catch包裹埋点逻辑，异常时降级为不采集，但不影响业务方法本体执行 |
| 本地队列写入 | 队列已满 | 直接丢弃并计数告警，不阻塞、不抛异常给业务线程 |
| 本地日志落盘 | 磁盘满、IO异常 | 日志文件按大小/时间滚动，设置最大保留数量；写入失败仅记录内部监控，不影响业务 |
| Agent采集 | 日志格式错误、文件被误删 | Agent对格式错误的行直接跳过并计数；对文件监听失败做自动重试和告警 |
| Kafka发送 | Broker不可用、网络分区 | 生产者设置合理的重试次数和超时时间，超过重试仍失败则丢弃并告警，不做无限重试 |
| Storm处理 | 单条Span反序列化失败、计算节点宕机 | 单条数据异常仅跳过该条，不影响整个Bolt；Storm自身的ACK机制保证任务级别的容错重放 |
| 存储写入 | HBase/ES短暂不可用 | 引入本地重试队列和降级开关，短时间不可用时降级为只写HDFS，恢复后补偿写入 |
| 查询链路 | 数据量过大导致查询超时 | 分页查询、限制返回的Span数量上限，前端展示时做懒加载 |

### 4.3 上下文丢失的兜底处理

3.5节详细讨论了跨线程传播可能导致上下文丢失的问题，即便做了线程池包装，仍然可能存在业务代码使用了未被纳管的异步框架（例如直接`new Thread()`、使用第三方库内部自建的线程池）导致上下文丢失的情况。对此，追踪SDK需要有兜底策略，而不是简单地在上下文为空时抛异常中断业务：

```java
/**
 * 上下文缺失时的兜底处理：不影响业务执行，但要保证数据的可追溯性
 */
public class MissingContextFallbackHandler {

    private static final Logger LOGGER = LoggerFactory.getLogger(MissingContextFallbackHandler.class);

    /**
     * 当发起下游调用时发现当前线程没有可用的TraceContext，
     * 采取的策略是：生成一个新的根级别上下文，保证这次调用依然能够被追踪，
     * 只是它会被记录为一条独立的新链路，而不是原本预期链路的延续；
     * 同时记录一条警告日志，附带调用栈信息，便于事后定位是哪个未被纳管的
     * 异步调用点导致了上下文丢失，推动后续修复
     */
    public static TraceContext fallbackOrCreateNew(String method) {
        TraceContext context = TraceContextHolder.get();
        if (context != null) {
            return context;
        }
        LOGGER.warn("检测到方法[{}]调用时追踪上下文缺失，可能存在未被纳管的跨线程调用，已生成新的根上下文，调用栈：{}",
                method, captureStackTrace());
        MissingContextMetrics.increment(method);
        return TraceContext.builder()
                .traceId(TraceIdGenerator.generate())
                .spanId(SpanIdGenerator.ROOT_SPAN_ID)
                .sampled(SampleDecider.INSTANCE.decide(method))
                .build();
    }

    private static String captureStackTrace() {
        StackTraceElement[] elements = Thread.currentThread().getStackTrace();
        StringBuilder sb = new StringBuilder();
        for (int i = 2; i < Math.min(elements.length, 8); i++) {
            sb.append(elements[i]).append(" <- ");
        }
        return sb.toString();
    }
}
```

`MissingContextMetrics`会把每个方法出现上下文丢失的次数上报到监控系统，运维和开发人员可以据此发现代码中哪些地方还存在未被线程池包装覆盖的异步调用，逐步收敛，而不是让这类问题无声无息地一直存在。

### 4.4 链路聚合阶段的容错：长尾链路与不完整链路

Storm在做链路聚合时（3.8.3节），面临的一个现实问题是：不可能无限期地等待一条链路的所有Span都到齐才做聚合输出，因为存在：

- **长尾请求**：某些请求由于业务逻辑本身（如异步回调、长轮询）耗时很长，可能几分钟甚至几十分钟才结束；
- **Span丢失**：由于采样决策不一致（虽然理论上头部采样应该全链路一致，但极端情况下如版本不一致的SDK可能出现偏差）、网络丢包、Agent重启等原因，个别Span可能永远不会到达。

因此聚合逻辑必须设置一个合理的等待窗口（如30秒到1分钟），超过窗口后不管数据是否收全，都强制输出当前已收集到的Span，标记为"可能不完整"的链路。查询展示层在渲染这类链路时，应当明确提示用户"部分数据可能缺失"，而不是让用户误以为这就是完整的调用链路。

```java
/**
 * 链路完整性校验：基于SpanId的层级关系判断一条链路的Span集合是否存在明显的"断点"
 */
public class TraceCompletenessChecker {

    /**
     * 检查链路是否完整：遍历所有Span的spanId，如果存在某个spanId的父级spanId
     * 没有出现在集合中（且父级不是根节点之前应当忽略网关层），则认为链路存在缺失
     */
    public static boolean isComplete(List<Span> spans) {
        Set<String> spanIds = spans.stream().map(Span::getSpanId).collect(Collectors.toSet());
        for (Span span : spans) {
            String parentSpanId = parentOf(span.getSpanId());
            if (parentSpanId != null && !spanIds.contains(parentSpanId)) {
                return false;
            }
        }
        return true;
    }

    private static String parentOf(String spanId) {
        int lastDot = spanId.lastIndexOf('.');
        return lastDot > 0 ? spanId.substring(0, lastDot) : null;
    }
}
```

## 5. 性能优化

### 5.1 埋点开销优化

追踪SDK的埋点逻辑运行在业务调用的关键路径上（虽然上报是异步的，但生成TraceId/SpanId、写入ThreadLocal、采样判断这几步是同步执行的），必须做到极致轻量：

- **TraceId/SpanId生成避免使用UUID.randomUUID()**：JDK自带的`UUID.randomUUID()`底层依赖`SecureRandom`，在高并发场景下存在锁竞争，会成为性能瓶颈。3.2.1节的实现采用"IP+时间戳+自增序号"的组合方式，避免了这个问题。

- **采样判断前置，未命中采样时跳过后续所有埋点开销**：如3.7.2节的设计，采样决策在请求入口就完成，如果未命中采样（且非debug、非最终异常），后续的Span构建、annotation收集等逻辑都可以直接跳过，只保留最基本的上下文传播（因为下游服务需要知道"这条链路不采样"这一决策本身，即使不采集也要传播这个标记）。

```java
/**
 * 采样感知的Span构建器：未采样时直接返回空实现，避免不必要的对象创建和字段填充开销
 */
public final class SpanBuilderFactory {

    private static final Span NOOP_SPAN = null;

    public static SpanRecorder create(boolean sampled, String traceId, String spanId) {
        if (!sampled) {
            // 返回一个空实现，所有record方法都是空操作，
            // 避免在未采样场景下产生任何对象分配和字段计算开销
            return NoopSpanRecorder.INSTANCE;
        }
        return new RealSpanRecorder(traceId, spanId);
    }

    interface SpanRecorder {
        void recordAnnotation(String key, String value);

        Span finish();
    }

    /** 空实现，未采样场景下使用，所有操作均为no-op，JIT可以很好地内联优化掉这些空方法调用 */
    static final class NoopSpanRecorder implements SpanRecorder {
        static final NoopSpanRecorder INSTANCE = new NoopSpanRecorder();

        @Override
        public void recordAnnotation(String key, String value) {
            // no-op
        }

        @Override
        public Span finish() {
            return null;
        }
    }

    static final class RealSpanRecorder implements SpanRecorder {
        private final Span.Builder builder;

        RealSpanRecorder(String traceId, String spanId) {
            this.builder = Span.builder().traceId(traceId).spanId(spanId);
        }

        @Override
        public void recordAnnotation(String key, String value) {
            builder.addAnnotation(key, value);
        }

        @Override
        public Span finish() {
            return builder.build();
        }
    }
}
```

- **序列化优化**：Span数据的序列化格式应尽量紧凑，避免使用JSON这种冗余度较高的文本格式做高频序列化，优先采用二进制编码，减少CPU开销和网络/磁盘IO。

- **批量与异步**：如3.8.1节所述，Span上报必须是"业务线程只管往队列里丢，真正的IO操作由独立的后台线程批量完成"，业务线程不能有任何同步的网络调用或者磁盘写入。

### 5.2 采样率的动态调节

固定的1%采样率在流量平稳时是合适的，但在流量出现剧烈波动（如大促、突发热点事件）时，固定比例可能导致绝对采集量暴增，冲击下游存储；反过来在流量极低的长尾时段，固定比例又可能导致采集样本量过小，不足以反映系统状态。因此更精细的做法是**基于QPS做动态采样率调节**，控制的目标从"固定比例"变为"固定绝对量"。

```java
/**
 * 基于QPS的动态采样率调节器：
 * 目标是让每秒采集的Span数量维持在一个相对稳定的目标值附近，
 * 而不是让采集量随QPS剧增/剧减而剧烈波动
 */
public class AdaptiveSampleRateAdjuster {

    /** 期望每秒采集的目标Span数量 */
    private static final long TARGET_SAMPLES_PER_SECOND = 1000;

    private final AtomicLong requestCountInWindow = new AtomicLong(0);
    private volatile double currentSampleRate = 0.01;

    /** 每秒调度一次，根据上一秒的实际请求量重新计算采样率 */
    public void adjustEverySecond() {
        long requestCount = requestCountInWindow.getAndSet(0);
        if (requestCount <= 0) {
            return;
        }
        double idealRate = (double) TARGET_SAMPLES_PER_SECOND / requestCount;
        // 采样率上下限保护，避免极端流量下采样率被调节到不合理的区间
        currentSampleRate = Math.max(0.0001, Math.min(1.0, idealRate));
    }

    public void onRequest() {
        requestCountInWindow.incrementAndGet();
    }

    public double getCurrentSampleRate() {
        return currentSampleRate;
    }
}
```

### 5.3 存储层性能优化

- **HBase的rowKey设计避免热点**：虽然直接用TraceId作为rowKey能获得很好的点查性能，但如果TraceId的生成规则导致前缀过于集中（例如所有TraceId都以相同的服务标识开头），会导致写入压力集中在少数几个Region上形成热点。3.2.1节的TraceId生成方案通过"IP的十六进制+时间戳"作为前缀，天然具备了较好的离散性。

- **ES索引的分片与冷热分离**：按天创建索引（如3.9.2节的`trace-span-2024-01-01`），近期索引使用SSD等高性能存储节点，超过一定时间（如7天）的历史索引自动迁移到低成本的机械盘存储节点，并定期删除超过保留期限（如15天）的索引，控制ES集群的整体存储成本。

- **HBase与ES的批量写入**：Storm聚合完成后，向HBase和ES的写入都应采用批量接口（如HBase的`BufferedMutator`、ES的`BulkRequest`），而不是逐条写入，大幅减少网络往返次数。

```java
/**
 * ES批量写入优化：攒批后统一提交，减少网络往返
 */
public class BatchEsIndexer {

    private final RestHighLevelClient esClient;
    private final List<IndexRequest> buffer = new ArrayList<>();
    private static final int BATCH_SIZE = 1000;
    private final Object lock = new Object();

    public BatchEsIndexer(RestHighLevelClient esClient) {
        this.esClient = esClient;
    }

    public void add(IndexRequest request) throws IOException {
        List<IndexRequest> toFlush = null;
        synchronized (lock) {
            buffer.add(request);
            if (buffer.size() >= BATCH_SIZE) {
                toFlush = new ArrayList<>(buffer);
                buffer.clear();
            }
        }
        if (toFlush != null) {
            flush(toFlush);
        }
    }

    private void flush(List<IndexRequest> requests) throws IOException {
        BulkRequest bulkRequest = new BulkRequest();
        requests.forEach(bulkRequest::add);
        BulkResponse response = esClient.bulk(bulkRequest, RequestOptions.DEFAULT);
        if (response.hasFailures()) {
            BulkFailureMetrics.record(response.buildFailureMessage());
        }
    }
}
```

### 5.4 查询性能优化

- **链路详情查询走HBase点查，避免走ES做全字段扫描**：查询单条完整链路时应始终使用TraceId直接查HBase，而不是用ES做条件检索后再拼接，前者是O(1)的点查，后者涉及倒排索引查找和多文档聚合，延迟高一个数量级。

- **拓扑图查询走预聚合结果，不做实时全量计算**：3.10节的拓扑聚合结果应当定期（如每分钟）持久化一份快照到缓存，前端查询拓扑图时直接读取最近的快照，而不是每次查询都重新扫描全量Span数据做实时计算。

- **查询结果分页与懒加载**：单条链路可能包含数百个Span（微服务调用层级深、扇出多的场景），前端展示时应支持按需展开子树，而不是一次性把所有Span节点都渲染到页面上，避免浏览器卡顿。

### 5.5 网络传输优化

- **压缩**：Agent向Kafka发送数据、Span在网络间传输时都应启用压缩（如Snappy、LZ4），在CPU开销和网络带宽之间取得平衡，通常能减少60%以上的传输体积。

- **批量合并**：无论是SDK到本地日志、Agent到Kafka，还是Storm到存储层，都应尽量采用批量接口，减少网络往返次数带来的延迟叠加。

- **上下文透传字段精简**：如3.6.2节所述，严格区分永久上下文和一次性上下文，只把真正需要贯穿全链路的字段放入永久上下文向下游透传，避免每一跳RPC调用都携带大量冗余的Header/Attachment数据，增加不必要的网络开销。

## 6. 最佳实践与总结

### 6.1 与业界主流方案的对比

| 维度 | 本文方案（Dapper派生） | Zipkin | Jaeger | SkyWalking |
|------|----------------------|--------|--------|------------|
| 理论基础 | Google Dapper论文 | Google Dapper论文 | Google Dapper论文 + OpenTracing | 自研 + 兼容OpenTracing/OpenTelemetry |
| SpanId设计 | 层级化编码（0.1.1），无需额外索引即可还原父子关系 | 随机ID + parentId字段，需要索引重建树 | 随机ID + References字段，支持更复杂的Span关系（如FollowsFrom） | 基于SegmentId + SpanId的两级模型 |

| 拓扑图能力 | 支持，基于调用边聚合统计 | 支持（Zipkin Dependencies） | 支持（Jaeger Dependencies） | 支持，且可视化能力较为完善 |
| 典型优势 | 落地成本可控、层级SpanId利于快速重建、动态Debug排障效率高 | 生态成熟、轻量、社区活跃 | 原生支持OpenTracing标准、多语言支持好 | 无侵入式接入、开箱即用、国内文档和社区活跃度高 |
| 典型局限 | SpanId层级编码在超深调用链场景下字符串较长 | 采样策略相对简单，精细化控制能力弱于自研方案 | 部署组件相对复杂（Agent+Collector+Query多组件） | 字节码增强对JVM版本和框架版本有一定兼容性要求 |

需要说明的是，实践中并不需要在"完全自研"和"直接使用开源方案"之间做非此即彼的选择，很多团队采用的策略是：核心数据模型和传播机制自研（保留层级化SpanId、动态Debug等符合自身场景的能力），而在存储、可视化等相对通用的环节，尽量复用SkyWalking、Jaeger等成熟开源组件的能力或者与之对接，减少重复造轮子的成本。

### 6.2 埋点设计的最佳实践

1. **优先自动埋点，谨慎使用手动埋点**：自动埋点（AOP、框架拦截器）覆盖RPC、HTTP、数据库、消息队列等主流通信方式，能覆盖绝大多数场景且业务无感知。手动埋点应仅用于关键业务逻辑节点（如一个复杂计算过程的几个阶段划分），且要有统一的规范约束命名和标签使用方式，避免不同团队各自为政导致数据难以聚合分析。

2. **上下文对象一律设计为不可变对象**：3.5.2节详细讨论过浅拷贝导致的上下文污染问题，从设计源头上把TraceContext、Span等核心数据结构都设计为不可变对象（所有字段`final`，只提供返回新对象的"变更"方法），是杜绝这类问题最根本的方法，比在每个使用点小心翼翼地做防御性拷贝要可靠得多。

3. **任何跨线程的地方都必须显式包装**：不能依赖开发者的记忆去"记得"在用线程池的地方做上下文传播，而应该在团队的基础框架层面统一提供包装好的线程池、包装好的CompletableFuture工具类，并通过代码扫描规则检测直接使用`Executors.newXxxPool`或者`ForkJoinPool.commonPool()`的代码，在CI阶段就拦截下来。

4. **永久上下文的字段要有严格的准入机制**：3.6.2节的永久上下文会跟随链路一直透传下去，如果没有准入限制，容易被滥用（业务方为了方便，把各种临时信息都塞进永久上下文），导致每一跳RPC调用的Header/Attachment体积不断膨胀。应当由框架团队统一维护一份"允许进入永久上下文的字段白名单"，业务方新增字段需要走评审。

### 6.3 采样与成本控制的最佳实践

1. **默认采样率不是一成不变的**：1%是一个通用的经验起点，具体数值应结合自身的流量规模和存储预算做压测校准——目标是让HBase/ES的存储增长速度和查询延迟都维持在可接受范围内，同时保证统计意义上的样本量足够支撑P99延迟等关键指标的准确估算。

2. **核心链路单独配置更高采样率**：涉及资金、核心交易等高价值链路，即使全局采样率是1%，也应该单独配置为更高比例甚至100%，因为这类链路一旦出问题的业务影响远大于存储成本的增加。

3. **异常强制采集是保障可观测性下限的关键兜底**：无论正常流量的采样率设置得多低，只要发生异常或超时就必须全量采集，这是保证"关键问题不会因为采样而被遗漏"的最后一道防线，不能因为任何理由弱化这一策略。

4. **动态Debug要建立完善的权限和审计机制**：3.11.4节讨论的安全边界必须落到实处，包括自动过期、范围限制、脱敏前置、操作审计，防止动态Debug这一强大的排障能力被滥用或者引入新的数据安全风险。

### 6.4 排障流程的最佳实践

一次典型的基于链路追踪系统的问题排查流程如下：

```
1. 用户/监控系统反馈某个请求异常或者耗时超标
        │
        ▼
2. 通过日志或者用户上报，获取到这次请求的TraceId
   （建议在所有对外接口的响应Header或者错误提示中都携带TraceId，
    方便用户反馈问题时能直接提供，而不是靠猜测时间范围去检索）
        │
        ▼
3. 在链路查询平台，按TraceId直接点查HBase，秒级拿到完整调用树
        │
        ▼
4. 观察调用树中每个Span的CS/SR/SS/CR四个时间点，
   定位是网络传输慢还是某个具体服务的处理慢
        │
        ▼
5. 如果元信息不足以定位根因（比如需要看具体的入参），
   针对该方法开启动态Debug，等待复现或主动重新触发一次请求
        │
        ▼
6. 拿到详细的入参出参后，结合代码逻辑定位具体的根因代码
        │
        ▼
7. 修复问题后，关闭动态Debug，问题闭环
```

### 6.5 总结

分布式链路追踪的核心价值在于，把原本分散在数十上百个服务、无数台机器本地日志中的碎片化信息，通过统一的TraceId和层级化SpanId串联成一棵可读、可查询、可分析的调用树，让复杂系统的可观测性从"靠猜"变成"靠数据说话"。

回顾整套设计，几个最核心的技术决策贯穿始终：

- **理论基础**：以Google Dapper论文的三大原则（低开销、应用透明、可扩展性）作为设计的基本准绳；
- **数据模型**：TraceId保证全局唯一，层级化SpanId（0.1、0.1.1）让父子关系和调用顺序无需额外索引即可直接从编码中还原；
- **四阶段时间模型**：CS/SR/SS/CR精确拆分网络耗时与服务处理耗时，客户端上报clientSpan、服务端上报serverSpan，各自独立采集又能在聚合阶段准确关联；
- **上下文传播**：进程内依赖ThreadLocal，跨进程依赖RPC上下文/HTTP Header，而线程池场景必须通过显式包装解决ThreadLocal无法跨线程、浅拷贝互相污染、线程复用串号这三类典型问题；
- **上下文治理**：按内容分为基础信息、调用信息、机器信息、自定义信息四类，按生命周期分为永久上下文和一次性上下文两类，从设计层面避免信息传播的滥用和混乱；
- **架构管道**：业务应用→本地日志→采集Agent→Kafka→Storm→HBase/ES/HDFS的分层管道，把追踪系统的稳定性与业务系统彻底解耦；
- **采样与Debug**：默认1%采样应对千亿级别的日调用量，方法级采样率、异常强制采集、动态Debug三重机制相结合，在成本与可观测性之间取得平衡，并为深度排障提供了不依赖代码修改和重启的动态能力。

## 7. 全链路实战案例

前六章分别从架构设计、核心链路、异常处理、性能优化等维度阐述了分布式链路追踪的理论体系，本章通过三个贯穿多个模块的实战案例，把前文分散的知识点串联成端到端的完整流程，并给出可直接参考的Java工程实现，包括异常处理、日志记录与幂等控制。

### 7.1 案例一：一次慢请求的链路追踪全链路排查

#### 7.1.1 场景描述

用户反馈"下单"接口偶发卡顿，从点击到返回结果耗时超过3秒，但订单服务、商品服务、库存服务各自的监控面板都显示P99延迟正常。这是链路追踪系统最典型的应用场景：**单点监控正常不代表全链路正常**，必须通过TraceId把一次具体请求的完整调用路径还原出来，才能定位到具体是哪一跳出现了异常。

排查全链路可以拆解为五个环节：**用户反馈慢 → 通过TraceId定位请求 → 还原调用链路树 → 找到耗时节点 → 针对性优化**。下面按这五个环节逐一给出工程实现。

#### 7.1.2 第一步：接口响应中携带TraceId，便于用户反馈时提供

如果用户投诉时无法提供TraceId，后续所有排查都只能靠猜测时间范围做全量检索，效率极低。因此第一个关键设计是：**所有对外接口无论成功还是失败，都必须在响应中回传本次请求的TraceId**，前端捕获后可以在用户反馈入口自动带上，或者在报错页面直接展示给用户。

```java
import javax.servlet.Filter;
import javax.servlet.FilterChain;
import javax.servlet.ServletException;
import javax.servlet.ServletRequest;
import javax.servlet.ServletResponse;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;

/**
 * TraceId回传过滤器：将本次请求的TraceId写入响应Header，
 * 保证任何一次请求（无论成功还是异常）用户端都能拿到TraceId，
 * 这是后续所有排查手段的入口，必须保证100%覆盖，不能有遗漏的接口
 */
public class TraceIdResponseFilter implements Filter {

    private static final Logger LOGGER = LoggerFactory.getLogger(TraceIdResponseFilter.class);
    private static final String TRACE_ID_HEADER = "X-Trace-Id";

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        try {
            chain.doFilter(request, response);
        } finally {
            // 无论业务处理成功、抛出异常还是返回错误码，都在finally中回写TraceId，
            // 保证响应Header的TraceId回传不会因为业务异常而被跳过
            try {
                TraceContext context = TraceContextHolder.get();
                if (context != null) {
                    httpResponse.setHeader(TRACE_ID_HEADER, context.getTraceId());
                }
            } catch (Exception e) {
                // 回写TraceId本身失败不能影响响应正常返回，仅记录告警日志
                LOGGER.warn("回写TraceId到响应Header失败", e);
            }
        }
    }

    @Override
    public void init(javax.servlet.FilterConfig filterConfig) {
        // 无需初始化资源
    }

    @Override
    public void destroy() {
        // 无需释放资源
    }
}
```

#### 7.1.3 第二步：根据TraceId点查HBase，还原完整调用链路树

拿到用户反馈的TraceId后，排障平台直接以TraceId为rowKey查询HBase（对应3.9.1节的存储设计），一次get操作即可拿到这条链路下的全部Span，再按SpanId的层级编码规则重建父子关系，构造出可视化的调用树。

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * 链路排障服务：根据TraceId查询完整调用链路并重建调用树，
 * 是慢请求排查流程中承上启下的核心环节
 */
public class TraceDiagnosisService {

    private static final Logger LOGGER = LoggerFactory.getLogger(TraceDiagnosisService.class);

    private final HBaseTraceStorage traceStorage;

    /** 查询结果的短时缓存，避免同一TraceId在短时间内被反复点查HBase（例如页面刷新） */
    private final Map<String, CachedTraceTree> queryCache = new ConcurrentHashMap<>();
    private static final long CACHE_TTL_MS = 30_000;

    public TraceDiagnosisService(HBaseTraceStorage traceStorage) {
        this.traceStorage = traceStorage;
    }

    /**
     * 根据TraceId查询并重建完整调用链路树
     * 幂等说明：同一个TraceId多次调用本方法，只要数据未过期，返回的调用树结构完全一致，
     * 不会因为重复查询产生任何副作用或数据变化
     */
    public TraceQueryResult diagnose(String traceId) {
        if (traceId == null || traceId.isEmpty()) {
            throw new IllegalArgumentException("traceId不能为空");
        }

        CachedTraceTree cached = queryCache.get(traceId);
        if (cached != null && !cached.isExpired()) {
            LOGGER.info("命中链路查询缓存，traceId={}", traceId);
            return TraceQueryResult.success(cached.tree);
        }

        try {
            List<Span> spans = traceStorage.getByTraceId(traceId);
            if (spans == null || spans.isEmpty()) {
                LOGGER.warn("未查询到链路数据，traceId={}，可能未采样或数据已过期清理", traceId);
                return TraceQueryResult.notFound(traceId);
            }

            TraceTree tree = buildTree(traceId, spans);
            queryCache.put(traceId, new CachedTraceTree(tree, System.currentTimeMillis() + CACHE_TTL_MS));
            LOGGER.info("链路查询完成，traceId={}，spanCount={}", traceId, spans.size());
            return TraceQueryResult.success(tree);
        } catch (HBaseAccessException e) {
            // 存储层异常需要明确区分于"数据不存在"，避免误导用户以为链路本身有问题
            LOGGER.error("查询HBase失败，traceId={}", traceId, e);
            return TraceQueryResult.error(traceId, "存储查询异常，请稍后重试");
        } catch (Exception e) {
            LOGGER.error("链路重建过程出现未预期异常，traceId={}", traceId, e);
            return TraceQueryResult.error(traceId, "链路重建异常");
        }
    }

    /**
     * 按SpanId层级编码（如0.1.1）重建父子关系，构造调用树
     */
    private TraceTree buildTree(String traceId, List<Span> spans) {
        List<Span> sorted = new ArrayList<>(spans);
        // 按SpanId字符串排序即可保证父节点一定排在子节点之前，简化建树逻辑
        sorted.sort(Comparator.comparing(Span::getSpanId));

        SpanNode root = null;
        Map<String, SpanNode> nodeIndex = new ConcurrentHashMap<>();
        for (Span span : sorted) {
            SpanNode node = new SpanNode(span);
            nodeIndex.put(span.getSpanId(), node);
            String parentSpanId = parentOf(span.getSpanId());
            if (parentSpanId == null) {
                root = node;
            } else {
                SpanNode parent = nodeIndex.get(parentSpanId);
                if (parent != null) {
                    parent.addChild(node);
                } else {
                    // 父节点缺失（可能因为该Span未被采样或数据丢失），
                    // 挂到一个虚拟根节点下，保证树结构依然完整可展示，而不是直接抛异常中断查询
                    LOGGER.warn("链路存在断点，spanId={}的父节点{}缺失，traceId={}",
                            span.getSpanId(), parentSpanId, traceId);
                    node.markIncomplete();
                }
            }
        }
        return new TraceTree(traceId, root, nodeIndex);
    }

    private String parentOf(String spanId) {
        int lastDot = spanId.lastIndexOf('.');
        return lastDot > 0 ? spanId.substring(0, lastDot) : null;
    }

    /** 短时缓存的调用树包装，携带过期时间 */
    private static final class CachedTraceTree {
        final TraceTree tree;
        final long expireAt;

        CachedTraceTree(TraceTree tree, long expireAt) {
            this.tree = tree;
            this.expireAt = expireAt;
        }

        boolean isExpired() {
            return System.currentTimeMillis() > expireAt;
        }
    }
}
```

#### 7.1.4 第三步：遍历调用树，定位耗时最长的节点

拿到调用树之后，下一步是通过CS/SR/SS/CR四阶段时间点（3.3节）逐层计算每个Span自身的处理耗时（排除子调用耗时），从而定位出真正的性能瓶颈节点，而不是简单地看哪个Span的总耗时最长（父Span的总耗时天然包含所有子Span耗时，直接比较总耗时会误判）。

```java
import java.util.ArrayList;
import java.util.List;

/**
 * 耗时分析器：计算调用树中每个节点的"自身耗时"（Self Time），
 * 自身耗时 = 该Span的总耗时 - 所有直接子Span的总耗时之和，
 * 只有自身耗时高的节点才是真正需要优化的瓶颈点
 */
public class SlowSpanAnalyzer {

    private static final Logger LOGGER = LoggerFactory.getLogger(SlowSpanAnalyzer.class);

    /**
     * 分析整棵调用树，返回按自身耗时降序排列的节点列表
     */
    public List<SpanTimingResult> analyze(TraceTree tree) {
        List<SpanTimingResult> results = new ArrayList<>();
        if (tree == null || tree.getRoot() == null) {
            LOGGER.warn("传入的调用树为空，无法进行耗时分析，traceId={}",
                    tree == null ? "unknown" : tree.getTraceId());
            return results;
        }
        try {
            computeSelfTime(tree.getRoot(), results);
        } catch (Exception e) {
            LOGGER.error("耗时分析过程出现异常，traceId={}", tree.getTraceId(), e);
            return results;
        }
        results.sort((a, b) -> Long.compare(b.getSelfTimeMs(), a.getSelfTimeMs()));
        return results;
    }

    private long computeSelfTime(SpanNode node, List<SpanTimingResult> results) {
        long totalDuration = node.getSpan().getEndTime() - node.getSpan().getStartTime();
        long childrenDuration = 0L;
        for (SpanNode child : node.getChildren()) {
            childrenDuration += computeSelfTime(child, results);
        }
        // 自身耗时不应为负，如果出现负值说明时钟不同步或数据异常，兜底为0并记录警告
        long selfTime = Math.max(0L, totalDuration - childrenDuration);
        if (totalDuration - childrenDuration < 0) {
            LOGGER.warn("检测到自身耗时计算为负，可能存在跨机器时钟不同步问题，spanId={}",
                    node.getSpan().getSpanId());
        }
        results.add(new SpanTimingResult(node.getSpan(), selfTime, totalDuration));
        return totalDuration;
    }
}
```

#### 7.1.5 第四步：结合动态Debug拿到详细上下文，定位根因并验证优化效果

假设上一步分析发现库存服务的`deductStock`方法自身耗时高达2.6秒，元信息（方法名、耗时）不足以判断具体原因，此时按照3.11节的动态Debug能力，对该方法临时开启入参出参采集，等待下一次调用命中后即可拿到详细的调用现场。

```java
/**
 * 慢请求根因定位工作流：串联"开启动态Debug -> 等待复现 -> 拉取详情 -> 关闭Debug"的完整流程，
 * 通过状态机保证操作的幂等性和资源的可靠释放
 */
public class SlowRequestRootCauseWorkflow {

    private static final Logger LOGGER = LoggerFactory.getLogger(SlowRequestRootCauseWorkflow.class);

    private final DynamicDebugService dynamicDebugService;
    private final Map<String, DebugSession> activeSessions = new ConcurrentHashMap<>();

    public SlowRequestRootCauseWorkflow(DynamicDebugService dynamicDebugService) {
        this.dynamicDebugService = dynamicDebugService;
    }

    /**
     * 针对指定方法开启动态Debug，幂等处理：如果该方法已经存在处于活跃状态的Debug会话，
     * 直接复用现有会话而不是重复创建，避免同一个方法被并发开启多个Debug任务
     */
    public DebugSession startDebugging(String targetMethod, String operatorId, long durationMs) {
        if (targetMethod == null || targetMethod.isEmpty()) {
            throw new IllegalArgumentException("targetMethod不能为空");
        }
        DebugSession existing = activeSessions.get(targetMethod);
        if (existing != null && !existing.isExpired()) {
            LOGGER.info("方法[{}]已存在活跃的Debug会话，直接复用，sessionId={}",
                    targetMethod, existing.getSessionId());
            return existing;
        }

        try {
            String sessionId = dynamicDebugService.enableDebug(targetMethod, durationMs);
            DebugSession session = new DebugSession(sessionId, targetMethod, operatorId,
                    System.currentTimeMillis() + durationMs);
            activeSessions.put(targetMethod, session);
            LOGGER.info("已为方法[{}]开启动态Debug，操作人={}，有效期{}ms，sessionId={}",
                    targetMethod, operatorId, durationMs, sessionId);
            return session;
        } catch (DebugServiceException e) {
            LOGGER.error("开启动态Debug失败，targetMethod={}", targetMethod, e);
            throw new RootCauseAnalysisException("开启动态Debug失败: " + e.getMessage(), e);
        }
    }

    /**
     * 拉取Debug会话捕获到的调用现场数据
     */
    public List<DebugCaptureRecord> fetchCapturedRecords(String targetMethod) {
        DebugSession session = activeSessions.get(targetMethod);
        if (session == null) {
            LOGGER.warn("尝试拉取一个不存在的Debug会话数据，targetMethod={}", targetMethod);
            return java.util.Collections.emptyList();
        }
        try {
            return dynamicDebugService.fetchRecords(session.getSessionId());
        } catch (Exception e) {
            LOGGER.error("拉取Debug捕获数据失败，sessionId={}", session.getSessionId(), e);
            return java.util.Collections.emptyList();
        }
    }

    /**
     * 关闭Debug会话，幂等处理：重复关闭同一个会话不会抛异常，只会记录一条提示日志
     */
    public void stopDebugging(String targetMethod) {
        DebugSession session = activeSessions.remove(targetMethod);
        if (session == null) {
            LOGGER.info("方法[{}]当前没有活跃的Debug会话，无需关闭", targetMethod);
            return;
        }
        try {
            dynamicDebugService.disableDebug(session.getSessionId());
            LOGGER.info("已关闭方法[{}]的动态Debug会话，sessionId={}", targetMethod, session.getSessionId());
        } catch (Exception e) {
            // 关闭失败也不应影响主流程，Debug配置本身有自动过期兜底（3.11.4节），
            // 即使这次关闭调用失败，会话也会在有效期结束后自动失效
            LOGGER.warn("关闭Debug会话失败，将依赖自动过期兜底，sessionId={}", session.getSessionId(), e);
        }
    }

    /** Debug会话是否已过期的辅助类 */
    private static final class DebugSession {
        private final String sessionId;
        private final String targetMethod;
        private final String operatorId;
        private final long expireAt;

        DebugSession(String sessionId, String targetMethod, String operatorId, long expireAt) {
            this.sessionId = sessionId;
            this.targetMethod = targetMethod;
            this.operatorId = operatorId;
            this.expireAt = expireAt;
        }

        boolean isExpired() {
            return System.currentTimeMillis() > expireAt;
        }

        String getSessionId() {
            return sessionId;
        }
    }
}
```

最终，通过详细的调用现场数据发现：`deductStock`方法在扣减库存前会先查询一次商品的实时价格用于日志记录，而这次价格查询走的是一个未加缓存、且未加索引的慢SQL。定位到根因后，团队增加了价格缓存并补充了数据库索引，该接口的P99耗时从3秒以上降低到200毫秒以内。整个从"用户反馈慢"到"确认根因并验证优化效果"的过程，在链路追踪系统的支撑下控制在30分钟以内完成。

### 7.2 案例二：跨服务调用链路传播全链路

#### 7.2.1 场景描述

一次下单请求会依次经过HTTP网关、Dubbo风格的RPC调用、以及一次异步的消息队列通知（订单创建后发MQ消息触发积分服务异步加积分）。这三种协议的上下文传播机制完全不同，如果任何一环传播断裂，链路就会在该处"断链"，后续的Span会变成一条无法追溯到原链路的新链路。本案例展示如何在HTTP、RPC、MQ三种协议上分别正确地传播TraceId/SpanId，并结合采样决策的一致性要求。

#### 7.2.2 HTTP协议传播：通过请求头透传

```java
import java.io.IOException;
import javax.servlet.Filter;
import javax.servlet.FilterChain;
import javax.servlet.ServletException;
import javax.servlet.ServletRequest;
import javax.servlet.ServletResponse;
import javax.servlet.http.HttpServletRequest;

/**
 * HTTP服务端入口过滤器：从请求头中提取上游透传的TraceId/SpanId/采样标记，
 * 如果不存在（说明是链路的起点，例如用户直接从浏览器发起请求），则新建根上下文
 */
public class HttpTraceContextFilter implements Filter {

    private static final Logger LOGGER = LoggerFactory.getLogger(HttpTraceContextFilter.class);

    private static final String HEADER_TRACE_ID = "X-Trace-Id";
    private static final String HEADER_SPAN_ID = "X-Span-Id";
    private static final String HEADER_SAMPLED = "X-Sampled";

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        TraceContext context = null;
        try {
            context = extractOrCreate(httpRequest);
            TraceContextHolder.set(context);
        } catch (Exception e) {
            // 上下文提取失败不能中断请求处理，降级为新建一条根链路，
            // 保证即使传播机制出现异常，业务请求依然能够正常处理
            LOGGER.warn("HTTP请求头解析追踪上下文失败，降级为新建根链路", e);
            context = TraceContext.builder()
                    .traceId(TraceIdGenerator.generate())
                    .spanId(SpanIdGenerator.ROOT_SPAN_ID)
                    .sampled(SampleDecider.INSTANCE.decide(httpRequest.getRequestURI()))
                    .build();
            TraceContextHolder.set(context);
        }

        try {
            chain.doFilter(request, response);
        } finally {
            // 必须在finally中清理ThreadLocal，避免线程池复用线程时发生串号（3.5.2节讨论过的问题）
            TraceContextHolder.clear();
        }
    }

    private TraceContext extractOrCreate(HttpServletRequest request) {
        String traceId = request.getHeader(HEADER_TRACE_ID);
        String parentSpanId = request.getHeader(HEADER_SPAN_ID);
        String sampledHeader = request.getHeader(HEADER_SAMPLED);

        if (traceId == null || traceId.isEmpty()) {
            // 没有上游传入TraceId，说明本请求就是链路的起点
            boolean sampled = SampleDecider.INSTANCE.decide(request.getRequestURI());
            return TraceContext.builder()
                    .traceId(TraceIdGenerator.generate())
                    .spanId(SpanIdGenerator.ROOT_SPAN_ID)
                    .sampled(sampled)
                    .build();
        }

        // 采样决策必须直接沿用上游传下来的结果，不能在中间节点重新判断，
        // 否则会出现同一条链路里部分Span被采集、部分被丢弃的不一致情况
        boolean sampled = "1".equals(sampledHeader);
        String currentSpanId = (parentSpanId == null || parentSpanId.isEmpty())
                ? SpanIdGenerator.ROOT_SPAN_ID
                : SpanIdGenerator.nextChildSpanId(parentSpanId, 1);

        return TraceContext.builder()
                .traceId(traceId)
                .spanId(currentSpanId)
                .sampled(sampled)
                .build();
    }
}
```

```java
import java.io.IOException;
```

#### 7.2.3 RPC协议传播：通过RpcContext/Attachment透传

RPC框架（如Dubbo）通常提供隐式传参机制（Attachment），比HTTP Header更贴近RPC调用的编程模型，传播方式与HTTP类似，但需要注意RPC框架的Filter链执行顺序和异步调用场景下的上下文回收问题。

```java
/**
 * RPC调用过滤器：在服务提供方解析上游传播的上下文，在服务消费方写入待传播的上下文，
 * 与3.3节介绍的CS/SR/SS/CR四阶段模型配合，在四个时间点分别打点
 */
public class RpcTraceContextFilter implements RpcFilter {

    private static final Logger LOGGER = LoggerFactory.getLogger(RpcTraceContextFilter.class);

    @Override
    public RpcResponse invoke(RpcInvoker invoker, RpcRequest request) {
        boolean isConsumerSide = request.isConsumerSide();
        TraceContext context = null;
        try {
            context = isConsumerSide
                    ? prepareConsumerContext(request)
                    : extractProviderContext(request);
            TraceContextHolder.set(context);
            long csTime = System.currentTimeMillis();

            RpcResponse response = invoker.invoke(request);

            long crTime = System.currentTimeMillis();
            recordSpanSafely(context, request, csTime, crTime, response);
            return response;
        } catch (RpcTimeoutException e) {
            // 超时是明确需要全量采集的场景（4.3节采样策略），即使原始采样决策是不采集，
            // 也要强制标记本次调用的Span为需要上报，用于异常追溯
            LOGGER.warn("RPC调用超时，method={}，traceId={}", request.getMethodName(),
                    context != null ? context.getTraceId() : "unknown", e);
            forceRecordOnError(context, request);
            throw e;
        } catch (Exception e) {
            LOGGER.error("RPC调用异常，method={}", request.getMethodName(), e);
            forceRecordOnError(context, request);
            throw e;
        } finally {
            if (isConsumerSide) {
                // 消费端每次调用都会set一个新的子Span上下文，需要在finally里恢复，
                // 避免影响同一线程后续的其他调用
                TraceContextHolder.clear();
            }
        }
    }

    private TraceContext prepareConsumerContext(RpcRequest request) {
        TraceContext parent = TraceContextHolder.get();
        if (parent == null) {
            // 兜底：没有父上下文时新建根节点，见4.3节的MissingContextFallbackHandler
            parent = MissingContextFallbackHandler.fallbackOrCreateNew(request.getMethodName());
        }
        String childSpanId = SpanIdGenerator.nextChildSpanId(parent.getSpanId(), request.getInvokeIndex());
        TraceContext childContext = TraceContext.builder()
                .traceId(parent.getTraceId())
                .spanId(childSpanId)
                .sampled(parent.isSampled())
                .build();
        // 通过RpcContext的隐式传参（Attachment）机制透传，服务提供方框架层会自动收到
        request.setAttachment("traceId", childContext.getTraceId());
        request.setAttachment("spanId", childContext.getSpanId());
        request.setAttachment("sampled", childContext.isSampled() ? "1" : "0");
        return childContext;
    }

    private TraceContext extractProviderContext(RpcRequest request) {
        String traceId = request.getAttachment("traceId");
        String spanId = request.getAttachment("spanId");
        String sampled = request.getAttachment("sampled");
        if (traceId == null) {
            LOGGER.warn("RPC服务提供方未接收到上游传播的TraceId，method={}，可能是消费方版本过旧",
                    request.getMethodName());
            return MissingContextFallbackHandler.fallbackOrCreateNew(request.getMethodName());
        }
        return TraceContext.builder()
                .traceId(traceId)
                .spanId(spanId)
                .sampled("1".equals(sampled))
                .build();
    }

    private void recordSpanSafely(TraceContext context, RpcRequest request,
                                   long startTime, long endTime, RpcResponse response) {
        if (context == null || !context.isSampled()) {
            return;
        }
        try {
            Span span = Span.builder()
                    .traceId(context.getTraceId())
                    .spanId(context.getSpanId())
                    .methodName(request.getMethodName())
                    .startTime(startTime)
                    .endTime(endTime)
                    .success(response != null && response.isSuccess())
                    .build();
            SpanReporterHolder.getReporter().report(span);
        } catch (Exception e) {
            LOGGER.warn("记录RPC Span失败，method={}", request.getMethodName(), e);
        }
    }

    private void forceRecordOnError(TraceContext context, RpcRequest request) {
        if (context == null) {
            return;
        }
        try {
            Span span = Span.builder()
                    .traceId(context.getTraceId())
                    .spanId(context.getSpanId())
                    .methodName(request.getMethodName())
                    .success(false)
                    .forceSampled(true)
                    .build();
            SpanReporterHolder.getReporter().report(span);
        } catch (Exception e) {
            LOGGER.warn("异常场景下强制记录Span失败，method={}", request.getMethodName(), e);
        }
    }
}
```

#### 7.2.4 MQ协议传播：通过消息属性透传，并解决消费幂等问题

消息队列场景的上下文传播和HTTP/RPC有本质区别：生产者发送消息和消费者消费消息是两个完全独立的线程甚至完全独立的进程，中间隔着消息队列的持久化和异步投递，因此必须把TraceId/SpanId作为消息的**属性**（而不是消息体本身的业务字段）一起发送，消费端从消息属性中还原上下文。此外，消费端处理消息必须考虑MQ"至少一次投递"语义下的重复消费问题，需要做幂等控制。

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.ConcurrentHashMap;

/**
 * MQ生产者端：发送消息时把当前追踪上下文写入消息属性
 */
public class TraceAwareMessageProducer {

    private static final Logger LOGGER = LoggerFactory.getLogger(TraceAwareMessageProducer.class);

    private final MessageQueueClient mqClient;

    public TraceAwareMessageProducer(MessageQueueClient mqClient) {
        this.mqClient = mqClient;
    }

    /**
     * 发送消息，自动携带当前链路的追踪上下文和一个业务幂等键
     */
    public void send(String topic, String bizPayload, String idempotentKey) {
        TraceContext context = TraceContextHolder.get();
        Message message = new Message(topic, bizPayload);

        try {
            if (context != null) {
                message.putProperty("traceId", context.getTraceId());
                // MQ场景下用一个固定的子SpanId标记"消息发送"这个动作，
                // 消费端收到后再基于此生成自己的子Span，保持父子关系可追溯
                message.putProperty("spanId", SpanIdGenerator.nextChildSpanId(context.getSpanId(), 99));
                message.putProperty("sampled", context.isSampled() ? "1" : "0");
            } else {
                LOGGER.warn("发送MQ消息[{}]时未发现追踪上下文，消费端将无法关联到生产链路", topic);
            }
            // 幂等键作为消息属性传递，供消费端做重复消费检测，而不是依赖消息体解析
            message.putProperty("idempotentKey", idempotentKey);
            mqClient.send(message);
        } catch (MessageSendException e) {
            LOGGER.error("MQ消息发送失败，topic={}，idempotentKey={}", topic, idempotentKey, e);
            throw new TraceAwareMessagingException("消息发送失败: " + e.getMessage(), e);
        }
    }
}
```

```java
/**
 * MQ消费者端：从消息属性还原追踪上下文，并基于幂等键做去重处理，
 * 保证同一条消息因网络抖动、Broker重试等原因被重复投递时，业务逻辑只会被真正执行一次
 */
public class TraceAwareMessageConsumer {

    private static final Logger LOGGER = LoggerFactory.getLogger(TraceAwareMessageConsumer.class);

    /** 幂等去重存储，生产环境应使用Redis等外部存储，此处用本地Map示意接口语义 */
    private final ConcurrentHashMap<String, Long> processedKeys = new ConcurrentHashMap<>();
    private static final long IDEMPOTENT_KEY_TTL_MS = TimeUnit.HOURS.toMillis(24);

    private final BizMessageHandler bizMessageHandler;

    public TraceAwareMessageConsumer(BizMessageHandler bizMessageHandler) {
        this.bizMessageHandler = bizMessageHandler;
    }

    /**
     * 消费入口：还原追踪上下文 + 幂等校验 + 业务处理，三者缺一不可
     */
    public void onMessage(Message message) {
        TraceContext context = null;
        try {
            context = restoreContext(message);
            TraceContextHolder.set(context);

            String idempotentKey = message.getProperty("idempotentKey");
            if (!tryMarkProcessing(idempotentKey)) {
                LOGGER.info("消息重复投递，已跳过处理，idempotentKey={}，traceId={}",
                        idempotentKey, context.getTraceId());
                return;
            }

            long startTime = System.currentTimeMillis();
            bizMessageHandler.handle(message);
            long endTime = System.currentTimeMillis();
            recordConsumeSpan(context, message, startTime, endTime, true);
        } catch (BizProcessException e) {
            // 业务处理异常：记录失败Span后重新抛出，交由MQ框架的重试机制处理，
            // 幂等键已经写入，重试时tryMarkProcessing会识别为重复并跳过重复执行的风险，
            // 因此这里需要在真正处理失败时回滚幂等标记，允许重试真正生效
            String idempotentKey = message.getProperty("idempotentKey");
            rollbackProcessingMark(idempotentKey);
            LOGGER.error("消息业务处理失败，traceId={}", context != null ? context.getTraceId() : "unknown", e);
            recordConsumeSpan(context, message, 0, 0, false);
            throw e;
        } catch (Exception e) {
            LOGGER.error("消息消费过程出现未预期异常", e);
            throw new TraceAwareMessagingException("消息消费失败: " + e.getMessage(), e);
        } finally {
            TraceContextHolder.clear();
        }
    }

    private TraceContext restoreContext(Message message) {
        String traceId = message.getProperty("traceId");
        String spanId = message.getProperty("spanId");
        String sampled = message.getProperty("sampled");
        if (traceId == null) {
            LOGGER.warn("MQ消息缺失追踪上下文属性，可能是生产方未正确埋点，topic={}", message.getTopic());
            return MissingContextFallbackHandler.fallbackOrCreateNew("mq-consume:" + message.getTopic());
        }
        // 消费端在生产端记录的spanId基础上再生成一层子SpanId，代表"消费处理"这个动作本身
        String consumeSpanId = SpanIdGenerator.nextChildSpanId(spanId, 1);
        return TraceContext.builder()
                .traceId(traceId)
                .spanId(consumeSpanId)
                .sampled("1".equals(sampled))
                .build();
    }

    /**
     * 幂等标记：只有成功插入标记的线程才被允许继续处理业务逻辑，
     * 使用putIfAbsent保证并发场景下即使多个消费线程同时收到重复消息，也只有一个能获得处理权
     */
    private boolean tryMarkProcessing(String idempotentKey) {
        if (idempotentKey == null || idempotentKey.isEmpty()) {
            // 没有幂等键的消息无法去重，记录告警但依然放行处理，避免正常消息因缺少幂等键被误拦截
            LOGGER.warn("消息缺失幂等键，跳过幂等校验直接处理");
            return true;
        }
        cleanupExpiredKeys();
        Long previous = processedKeys.putIfAbsent(idempotentKey, System.currentTimeMillis());
        return previous == null;
    }

    private void rollbackProcessingMark(String idempotentKey) {
        if (idempotentKey != null) {
            processedKeys.remove(idempotentKey);
        }
    }

    private void cleanupExpiredKeys() {
        long now = System.currentTimeMillis();
        processedKeys.entrySet().removeIf(entry -> now - entry.getValue() > IDEMPOTENT_KEY_TTL_MS);
    }

    private void recordConsumeSpan(TraceContext context, Message message,
                                    long startTime, long endTime, boolean success) {
        if (context == null || (!context.isSampled() && success)) {
            return;
        }
        try {
            Span span = Span.builder()
                    .traceId(context.getTraceId())
                    .spanId(context.getSpanId())
                    .methodName("mq-consume:" + message.getTopic())
                    .startTime(startTime)
                    .endTime(endTime)
                    .success(success)
                    .forceSampled(!success)
                    .build();
            SpanReporterHolder.getReporter().report(span);
        } catch (Exception e) {
            LOGGER.warn("记录MQ消费Span失败", e);
        }
    }
}
```

#### 7.2.5 三种协议传播的一致性要点

| 协议 | 传播载体 | 采样决策一致性保证 | 特殊问题 |
|------|---------|-------------------|---------|
| HTTP | 请求头（X-Trace-Id等） | 服务端直接沿用请求头中的sampled标记，不重新判断 | 需要在Filter的finally块中清理ThreadLocal |
| RPC | 隐式传参/Attachment | 消费端生成子Span时继承父上下文的sampled标记 | 异步调用场景需要显式传递上下文快照（3.5节） |
| MQ | 消息属性（非消息体） | 消费端从消息属性还原sampled标记 | 必须结合幂等键解决"至少一次投递"导致的重复处理问题 |

三种协议虽然传播载体不同，但设计原则完全一致：**采样决策只在链路起点做一次，后续所有节点都只负责透传和继承，不重新判断**，这是保证一条链路内部采样结果一致的关键（对应3.7节采样策略体系的头部采样原则）。

### 7.3 案例三：链路数据采集与存储全链路

#### 7.3.1 场景描述

本案例把3.8节和3.9节涉及的"Agent采集 → 数据上报 → Collector处理 → 存储 → 查询"链路串联成一个端到端的可运行流程，重点展示各环节之间如何通过明确的接口契约衔接，以及每个环节自身的异常隔离和幂等保证，避免出现"上游重复发送导致下游重复存储"或者"单条脏数据拖垮整个批次"的问题。

#### 7.3.2 采集层：本地日志 Tail 与断点续传

Agent以Tail方式持续读取本地追踪日志文件，为了保证Agent重启后不会重复采集已经处理过的数据，也不会漏掉重启期间新增的数据，需要维护读取位点（offset）并定期持久化。

```java
import java.io.RandomAccessFile;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.nio.file.StandardOpenOption;

/**
 * 带断点续传能力的日志文件Tail读取器：
 * 定期把已读取的文件位点持久化到本地checkpoint文件，
 * Agent重启后从上次的checkpoint位点继续读取，避免重复采集或数据丢失
 */
public class CheckpointedLogTailer {

    private static final Logger LOGGER = LoggerFactory.getLogger(CheckpointedLogTailer.class);

    private final Path logFilePath;
    private final Path checkpointFilePath;
    private volatile long currentOffset;

    public CheckpointedLogTailer(String logFile, String checkpointFile) {
        this.logFilePath = Paths.get(logFile);
        this.checkpointFilePath = Paths.get(checkpointFile);
        this.currentOffset = loadCheckpoint();
    }

    /**
     * 加载上次持久化的读取位点，文件不存在或内容损坏时从0开始，
     * 保证Agent首次启动或checkpoint文件异常时依然能够正常工作
     */
    private long loadCheckpoint() {
        try {
            if (!Files.exists(checkpointFilePath)) {
                return 0L;
            }
            String content = new String(Files.readAllBytes(checkpointFilePath)).trim();
            return content.isEmpty() ? 0L : Long.parseLong(content);
        } catch (Exception e) {
            LOGGER.warn("读取checkpoint文件失败，将从头开始采集，checkpointFile={}", checkpointFilePath, e);
            return 0L;
        }
    }

    /**
     * 持久化当前读取位点，采用临时文件+原子rename的方式，避免写入过程中进程崩溃导致checkpoint文件损坏
     */
    private void saveCheckpoint(long offset) {
        try {
            Path tempFile = Paths.get(checkpointFilePath.toString() + ".tmp");
            Files.write(tempFile, String.valueOf(offset).getBytes(),
                    StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING);
            Files.move(tempFile, checkpointFilePath,
                    java.nio.file.StandardCopyOption.ATOMIC_MOVE,
                    java.nio.file.StandardCopyOption.REPLACE_EXISTING);
        } catch (Exception e) {
            // checkpoint保存失败不应中断采集流程，只是意味着下次重启可能会有少量重复采集，
            // 重复数据会在下游Collector环节通过幂等键去重（7.3.3节），不会导致数据错误
            LOGGER.warn("持久化checkpoint失败，offset={}", offset, e);
        }
    }

    /**
     * 从上次的位点开始读取新增内容，读取完成后更新并持久化位点
     */
    public java.util.List<String> pollNewLines(int maxLines) {
        java.util.List<String> lines = new java.util.ArrayList<>();
        try (RandomAccessFile raf = new RandomAccessFile(logFilePath.toFile(), "r")) {
            long fileLength = raf.length();
            if (fileLength < currentOffset) {
                // 文件长度小于上次记录的位点，说明日志文件被切割重建（滚动切分），
                // 从头开始读取新文件，避免seek到一个不存在的位置抛出异常
                LOGGER.info("检测到日志文件被切分重建，重置读取位点，file={}", logFilePath);
                currentOffset = 0L;
            }
            raf.seek(currentOffset);
            String line;
            while (lines.size() < maxLines && (line = raf.readLine()) != null) {
                lines.add(line);
            }
            currentOffset = raf.getFilePointer();
            saveCheckpoint(currentOffset);
        } catch (java.io.IOException e) {
            LOGGER.error("读取日志文件失败，file={}，currentOffset={}", logFilePath, currentOffset, e);
        }
        return lines;
    }
}
```

#### 7.3.3 上报层：Collector端接收与幂等去重

Agent向Collector上报数据时，网络超时可能导致Agent误判发送失败而重试，从而使同一批Span被重复上报。Collector端必须基于每条Span的唯一标识（TraceId+SpanId的组合）做幂等去重，保证重复上报不会导致存储层出现重复数据或者聚合计算结果偏差。

```java
import java.util.List;
import java.util.concurrent.TimeUnit;
import com.google.common.cache.Cache;
import com.google.common.cache.CacheBuilder;

/**
 * Collector端接收服务：负责校验、去重、分发写入下游存储，
 * 是采集链路中数据质量的最后一道防线
 */
public class SpanCollectorService {

    private static final Logger LOGGER = LoggerFactory.getLogger(SpanCollectorService.class);

    /**
     * 短时幂等缓存：记录最近处理过的Span唯一键，用于识别Agent重试导致的重复上报，
     * 采用带过期时间的LRU缓存，容量和过期时间需要结合Agent的重试窗口设置
     * （只要Agent的重试间隔小于该缓存的过期时间，就能有效拦截重复数据）
     */
    private final Cache<String, Boolean> dedupCache = CacheBuilder.newBuilder()
            .maximumSize(5_000_000)
            .expireAfterWrite(10, TimeUnit.MINUTES)
            .build();

    private final StorageDispatcher storageDispatcher;
    private final Counter duplicateCounter;
    private final Counter invalidCounter;

    public SpanCollectorService(StorageDispatcher storageDispatcher) {
        this.storageDispatcher = storageDispatcher;
        this.duplicateCounter = MetricRegistry.getInstance()
                .counter("trace_collector_duplicate_total", "重复Span计数", null);
        this.invalidCounter = MetricRegistry.getInstance()
                .counter("trace_collector_invalid_total", "非法Span计数", null);
    }

    /**
     * 接收一批Span数据，逐条校验、去重后转发写入存储，
     * 单条数据的异常不会影响批次内其他数据的正常处理
     */
    public BatchProcessResult receive(List<Span> batch) {
        if (batch == null || batch.isEmpty()) {
            return BatchProcessResult.empty();
        }

        int accepted = 0;
        int duplicated = 0;
        int invalid = 0;

        for (Span span : batch) {
            try {
                if (!isValid(span)) {
                    invalid++;
                    invalidCounter.increment(null);
                    LOGGER.warn("接收到非法Span，已丢弃，span={}", span);
                    continue;
                }

                String dedupKey = buildDedupKey(span);
                // putIfAbsent语义：只有第一次出现的key才能写入成功，
                // 后续重复到达的相同key会被直接判定为重复数据
                Boolean existing = dedupCache.asMap().putIfAbsent(dedupKey, Boolean.TRUE);
                if (existing != null) {
                    duplicated++;
                    duplicateCounter.increment(null);
                    continue;
                }

                storageDispatcher.dispatch(span);
                accepted++;
            } catch (Exception e) {
                // 单条Span处理异常只记录日志并跳过，不能因为一条脏数据导致整批次失败回滚
                LOGGER.error("处理单条Span异常，已跳过，traceId={}",
                        span != null ? span.getTraceId() : "unknown", e);
                invalid++;
            }
        }

        LOGGER.info("批次处理完成，总数={}，接受={}，重复={}，非法={}",
                batch.size(), accepted, duplicated, invalid);
        return new BatchProcessResult(batch.size(), accepted, duplicated, invalid);
    }

    private boolean isValid(Span span) {
        return span != null
                && span.getTraceId() != null && !span.getTraceId().isEmpty()
                && span.getSpanId() != null && !span.getSpanId().isEmpty()
                && span.getEndTime() >= span.getStartTime();
    }

    /** 幂等键：TraceId+SpanId组合足以唯一标识一条Span记录 */
    private String buildDedupKey(Span span) {
        return span.getTraceId() + ":" + span.getSpanId();
    }
}
```

#### 7.3.4 存储层：多存储并行写入与失败补偿

对应3.9节"HBase点查 + ES检索 + HDFS离线"的三写方案，需要保证一个存储介质写入失败不影响其他存储介质的写入，并且失败的写入能够被补偿重试，而不是静默丢失数据。

```java
import java.util.List;
import java.util.concurrent.CompletableFuture;

/**
 * 存储分发器：并行写入HBase/ES/HDFS三种存储介质，
 * 任一存储介质写入失败都不影响其他介质，失败的写入进入补偿队列异步重试
 */
public class StorageDispatcher {

    private static final Logger LOGGER = LoggerFactory.getLogger(StorageDispatcher.class);

    private final HBaseTraceStorage hBaseStorage;
    private final EsTraceIndexer esIndexer;
    private final HdfsArchiveWriter hdfsWriter;
    private final CompensationQueue compensationQueue;

    public StorageDispatcher(HBaseTraceStorage hBaseStorage, EsTraceIndexer esIndexer,
                              HdfsArchiveWriter hdfsWriter, CompensationQueue compensationQueue) {
        this.hBaseStorage = hBaseStorage;
        this.esIndexer = esIndexer;
        this.hdfsWriter = hdfsWriter;
        this.compensationQueue = compensationQueue;
    }

    /**
     * 并行分发写入三种存储，各自独立捕获异常，互不影响
     */
    public void dispatch(Span span) {
        CompletableFuture<Void> hBaseFuture = CompletableFuture.runAsync(() -> writeToHBase(span));
        CompletableFuture<Void> esFuture = CompletableFuture.runAsync(() -> writeToEs(span));
        CompletableFuture<Void> hdfsFuture = CompletableFuture.runAsync(() -> writeToHdfs(span));

        // 等待三路写入全部完成（无论成功失败），任何一路的异常都已经在各自的方法内部捕获，
        // 不会通过CompletableFuture向外抛出而影响调用方
        CompletableFuture.allOf(hBaseFuture, esFuture, hdfsFuture).join();
    }

    private void writeToHBase(Span span) {
        try {
            // HBase是点查主路径，写入失败必须有补偿机制，否则会导致该条链路永远无法被点查到
            hBaseStorage.put(span);
        } catch (Exception e) {
            LOGGER.error("写入HBase失败，traceId={}，spanId={}，已进入补偿队列",
                    span.getTraceId(), span.getSpanId(), e);
            compensationQueue.enqueue(new CompensationTask(StorageType.HBASE, span));
        }
    }

    private void writeToEs(Span span) {
        try {
            esIndexer.index(span);
        } catch (Exception e) {
            LOGGER.error("写入ES失败，traceId={}，spanId={}，已进入补偿队列",
                    span.getTraceId(), span.getSpanId(), e);
            compensationQueue.enqueue(new CompensationTask(StorageType.ES, span));
        }
    }

    private void writeToHdfs(Span span) {
        try {
            hdfsWriter.append(span);
        } catch (Exception e) {
            // HDFS是离线分析用途，重要程度相对较低，记录日志和监控指标即可，不强制补偿重试
            LOGGER.warn("写入HDFS失败，traceId={}，spanId={}，本条记录将在离线分析中缺失",
                    span.getTraceId(), span.getSpanId(), e);
        }
    }
}

/**
 * 补偿任务处理器：定期消费补偿队列，对写入失败的数据做有限次数的重试，
 * 超过最大重试次数后转入死信记录，由人工介入排查根因
 */
public class CompensationTaskProcessor {

    private static final Logger LOGGER = LoggerFactory.getLogger(CompensationTaskProcessor.class);
    private static final int MAX_RETRY_TIMES = 5;

    private final CompensationQueue compensationQueue;
    private final HBaseTraceStorage hBaseStorage;
    private final EsTraceIndexer esIndexer;

    public CompensationTaskProcessor(CompensationQueue compensationQueue,
                                      HBaseTraceStorage hBaseStorage, EsTraceIndexer esIndexer) {
        this.compensationQueue = compensationQueue;
        this.hBaseStorage = hBaseStorage;
        this.esIndexer = esIndexer;
    }

    /**
     * 定时调度调用：批量处理补偿队列中的任务
     */
    public void processPendingTasks() {
        List<CompensationTask> tasks = compensationQueue.pollBatch(200);
        for (CompensationTask task : tasks) {
            try {
                retryWrite(task);
            } catch (Exception e) {
                LOGGER.error("补偿写入仍然失败，storageType={}，traceId={}，retryCount={}",
                        task.getStorageType(), task.getSpan().getTraceId(), task.getRetryCount(), e);
                handleRetryFailure(task);
            }
        }
    }

    private void retryWrite(CompensationTask task) throws Exception {
        switch (task.getStorageType()) {
            case HBASE:
                hBaseStorage.put(task.getSpan());
                break;
            case ES:
                esIndexer.index(task.getSpan());
                break;
            default:
                LOGGER.warn("未知的补偿存储类型：{}", task.getStorageType());
        }
        LOGGER.info("补偿写入成功，storageType={}，traceId={}", task.getStorageType(), task.getSpan().getTraceId());
    }

    private void handleRetryFailure(CompensationTask task) {
        task.incrementRetryCount();
        if (task.getRetryCount() >= MAX_RETRY_TIMES) {
            // 超过最大重试次数，记录死信日志供人工排查，不再继续重试避免无限占用补偿队列资源
            LOGGER.error("补偿任务超过最大重试次数，转入死信记录，storageType={}，traceId={}，spanId={}",
                    task.getStorageType(), task.getSpan().getTraceId(), task.getSpan().getSpanId());
            DeadLetterRecorder.record(task);
        } else {
            compensationQueue.enqueue(task);
        }
    }
}
```

#### 7.3.5 查询层：对外提供统一查询接口

最后，查询服务对外暴露统一接口，屏蔽底层HBase/ES两种存储的差异：按TraceId精确查询走HBase点查（7.1.3节已展示），按服务名/方法名/时间范围的模糊检索走ES。

```java
/**
 * 统一链路查询服务：根据查询条件的不同特征，路由到最合适的底层存储，
 * 对调用方屏蔽HBase和ES两种存储引擎的差异
 */
public class UnifiedTraceQueryService {

    private static final Logger LOGGER = LoggerFactory.getLogger(UnifiedTraceQueryService.class);

    private final TraceDiagnosisService hBaseQueryService;
    private final EsTraceSearchService esSearchService;

    public UnifiedTraceQueryService(TraceDiagnosisService hBaseQueryService,
                                     EsTraceSearchService esSearchService) {
        this.hBaseQueryService = hBaseQueryService;
        this.esSearchService = esSearchService;
    }

    /**
     * 统一查询入口：精确TraceId查询走HBase点查（毫秒级），
     * 条件检索（服务名/方法名/耗时范围等）走ES倒排索引查询
     */
    public TraceQueryResult query(TraceQueryCondition condition) {
        try {
            if (condition.isExactTraceIdQuery()) {
                return hBaseQueryService.diagnose(condition.getTraceId());
            }
            return esSearchService.search(condition);
        } catch (IllegalArgumentException e) {
            LOGGER.warn("查询参数非法，condition={}", condition, e);
            return TraceQueryResult.error(condition.getTraceId(), "查询参数非法: " + e.getMessage());
        } catch (Exception e) {
            LOGGER.error("链路查询发生未预期异常，condition={}", condition, e);
            return TraceQueryResult.error(condition.getTraceId(), "查询服务暂不可用，请稍后重试");
        }
    }
}
```

#### 7.3.6 全链路小结

本案例展示的"Agent采集 → 上报 → Collector处理 → 存储 → 查询"全链路中，每一个环节都遵循了三个共同的工程原则：

1. **断点可续、幂等可控**：采集层通过持久化checkpoint保证重启不丢数据，Collector层通过TraceId+SpanId幂等键保证重复上报不产生脏数据；
2. **异常隔离、互不影响**：单条数据异常不影响整批次处理，单个存储介质故障不影响其他存储介质的写入，全部通过try-catch分段隔离实现；
3. **失败可补偿、可观测**：写入失败的数据不会静默丢失，而是进入补偿队列限次重试，超限后转入死信记录并保留完整的监控指标，供运维人员事后介入排查。

这套设计思路不是一次性建成的终态，而是需要随着业务规模、技术栈演进持续迭代的基础设施。团队在落地时应当结合自身的流量规模、团队规模、存储预算，在自研与复用开源组件（如SkyWalking、Zipkin、Jaeger）之间做出合理取舍，把有限的研发资源投入到最能体现自身业务特点的差异化能力上（例如本文重点介绍的层级化SpanId和动态Debug），而在通用的存储、可视化等环节尽量复用业界已经验证成熟的方案。
