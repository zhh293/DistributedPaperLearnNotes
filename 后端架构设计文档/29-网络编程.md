# 网络编程架构设计文档

## 一、问题背景

### 1.1 要解决的核心问题

在后端服务的世界里，几乎所有的分布式系统、RPC 框架、消息队列、网关都建立在一个共同的地基之上：**如何用有限的系统资源（线程、内存、CPU）支撑海量并发的网络连接与数据收发**。

具体来说，网络编程要解决的核心问题可以拆解为四个层面：

1. **并发连接的可扩展性问题**：一个后端服务在生产环境中，往往需要同时维持成千上万甚至上百万条 TCP 连接（长连接网关、IM 系统、RPC 服务端）。如果采用最朴素的"一个连接一个线程"模型，线程数量会随连接数线性增长，而操作系统线程的栈内存开销（默认 512KB~2MB）和上下文切换成本会迅速压垮系统。这就是经典的 C10K 乃至 C10M 问题。
2. **I/O 等待与计算资源利用率的矛盾**：网络 I/O 天然是"慢"的操作——等待数据到达、等待数据写出，这些时间比 CPU 执行指令的时间长几个数量级（网络 RTT 通常是毫秒级，CPU 指令周期是纳秒级，相差百万倍）。如果线程在等待 I/O 时被阻塞而无法处理其他任务，CPU 大量时间被浪费在无意义的阻塞等待上。
3. **数据在用户态与内核态之间频繁拷贝导致的性能损耗**：一次典型的网络数据收发，数据需要经过"网卡缓冲区 -> 内核缓冲区 -> 用户态缓冲区 -> 内核态 socket 缓冲区 -> 网卡"的多次拷贝，每次拷贝都伴随着上下文切换和 CPU 拷贝开销，在大文件传输、大 Payload 场景下这个开销会成为系统瓶颈。
4. **协议解析的粘包/半包问题**：TCP 是面向字节流的协议，没有消息边界的概念。应用层如果不设计合理的编解码协议，会出现一次读取包含多条消息（粘包）或一条消息被拆分成多次读取（半包）的问题，导致业务数据解析错乱。

### 1.2 典型场景

- **RPC 框架的服务端**：需要同时处理数万个客户端的并发请求，每个请求的处理时间通常在毫秒级，如果每个连接独占一个线程，线程池会被迅速耗尽。
- **网关/接入层**：作为流量入口，需要维持海量长连接（如 IM 长连接网关、物联网设备接入网关），单机连接数可能达到几十万到上百万。
- **大文件/大 Payload 传输服务**：如静态资源分发服务、RPC 序列化数据传输，如果不做零拷贝优化，数据在内存中被反复复制会导致 GC 压力剧增、P99 延迟劣化。
- **高频心跳与长连接保活**：长连接场景下需要检测连接的存活状态，及时清理僵死连接、断线重连，否则会造成连接泄漏和资源浪费。
- **自定义二进制协议通信**：微服务之间的 RPC 调用通常不直接用 HTTP/JSON（序列化体积大、解析慢），而是自定义二进制协议 + Protobuf/Hessian 等高效序列化方式，此时编解码框架的设计至关重要。

### 1.3 不解决的后果

如果不能妥善设计网络编程模型，会直接导致：

- **线程资源耗尽，服务雪崩**：C10K 问题如果没有被妥善解决，服务在流量高峰期会因为线程数暴涨、上下文切换开销剧增而彻底瘫痪。
- **CPU 利用率低但吞吐上不去**：大量线程阻塞在 I/O 等待上，CPU 空闲率高但实际业务吞吐量却很低，表现为"看起来很闲但是处理不过来"的反直觉现象。
- **P99 延迟长尾问题**：某文件分发服务因为 ByteBuf 频繁拷贝和 Reactor 线程模型配置不当（EventLoop 线程被业务阻塞操作占用），导致 P99 延迟从 30ms（P50）飙升到 800ms+，这种"两极分化"的延迟分布是 I/O 模型设计缺陷的典型症状。
- **连接泄漏与资源浪费**：长连接场景下如果没有合理的心跳检测和空闲连接清理机制，僵死连接会持续占用文件描述符和内存资源，最终导致"Too many open files"错误。

### 1.4 五种网络 I/O 模型对比

根据《UNIX 网络编程》的经典分类，操作系统提供的网络 I/O 模型主要分为五种。理解这五种模型的差异是设计高性能网络编程架构的基础。

用户进程的一个完整 I/O 操作分为两个阶段：
1. **等待数据准备就绪**（Waiting for data to be ready）：数据从网卡到达内核缓冲区。
2. **将数据从内核空间复制到用户空间**（Copying data from kernel to user）：系统调用 read() 将数据从内核态拷贝到用户态缓冲区。

以下五种模型在这两个阶段的处理方式各有不同：

| I/O 模型 | 第一阶段（等待数据） | 第二阶段（数据拷贝） | 适用场景 |
|---------|-------------------|-------------------|---------|
| 阻塞 I/O（BIO） | 阻塞，直到数据到达 | 阻塞，直到拷贝完成 | 连接数少、请求简单 |
| 非阻塞 I/O（NIO） | 非阻塞，立即返回（需轮询） | 阻塞，直到拷贝完成 | 不推荐单独使用 |
| I/O 多路复用 | 阻塞在 select/poll/epoll 上 | 阻塞，直到拷贝完成 | 高并发服务端（主流） |
| 信号驱动 I/O | 非阻塞，内核就绪时发信号 | 阻塞，直到拷贝完成 | 较少使用 |
| 异步 I/O（AIO） | 非阻塞，内核全程完成 | 非阻塞，内核完成后回调 | 理论最优，Linux 支持差 |

**关键结论**：前四种模型在第二阶段（数据拷贝）都是阻塞的，本质上都属于同步 I/O。只有异步 I/O 在两个阶段都是非阻塞的。但由于 Linux 下 AIO 的实现性能不佳，JDK 和 Netty 在 Linux 平台上并没有使用 AIO，而是基于 I/O 多路复用（epoll）+ Reactor 模式来实现高性能的异步事件驱动框架。

## 二、整体架构设计

### 2.1 架构分层

网络编程架构从底向上分为五层：

```
┌──────────────────────────────────────────────────────┐
│                  业务处理层 (Business Layer)            │
│    RPC Service / IM Handler / Gateway Filter           │
├──────────────────────────────────────────────────────┤
│               编解码层 (Codec Layer)                    │
│   Protocol Decoder/Encoder / Serialization / Frame     │
├──────────────────────────────────────────────────────┤
│            事件分发层 (Event Dispatch Layer)             │
│    ChannelPipeline / ChannelHandler / EventLoop        │
├──────────────────────────────────────────────────────┤
│            I/O 模型层 (I/O Model Layer)                 │
│   Selector(epoll) / Reactor Pattern / EventLoopGroup   │
├──────────────────────────────────────────────────────┤
│          操作系统网络层 (OS Network Layer)               │
│   TCP/IP / Socket FD / Kernel Buffer / epoll           │
└──────────────────────────────────────────────────────┘
```

### 2.2 核心组件

基于 Netty 框架的网络编程架构包含以下核心组件：

**EventLoop（事件循环）**：Netty 中最核心的概念，相当于 Reactor 模式中的 Reactor。一个 EventLoop 对应一个 Java 线程，负责监听网络事件并调用事件处理器进行处理。网络连接与 EventLoop 是稳定的多对一关系，即一个网络连接只会对应唯一的一个 EventLoop，且这个关系一旦确定就不再变化。这意味着一个网络连接的所有事件处理都是单线程执行的，避免了各种并发问题。

**EventLoopGroup（事件循环组）**：由一组 EventLoop 组成。实际使用中一般创建两个 EventLoopGroup：bossGroup 负责处理连接请求（OP_ACCEPT），workerGroup 负责处理读写请求（OP_READ/OP_WRITE）。bossGroup 处理完连接请求后，通过轮询算法将新连接分配给 workerGroup 中的某个 EventLoop。

**Channel（通道）**：代表一个网络连接（或一个可以执行 I/O 操作的实体），封装了 socket 的底层操作。

**ChannelPipeline（通道管线）**：每个 Channel 拥有一个 ChannelPipeline，其中包含一组按顺序排列的 ChannelHandler。入站事件从 pipeline 的头部流向尾部，出站事件从尾部流向头部。这种责任链模式使得编解码、日志、业务处理等逻辑可以灵活组合。

**ChannelHandler（通道处理器）**：处理 I/O 事件的核心组件，分为 InboundHandler（处理入站事件）和 OutboundHandler（处理出站事件）。

**ByteBuf（字节缓冲区）**：Netty 自己实现的字节缓冲区，相比 JDK 的 ByteBuffer 提供了零拷贝支持（CompositeByteBuf、Unpooled.wrappedBuffer）、池化管理（PooledByteBufAllocator）和引用计数等功能。

### 2.3 Reactor 模式详解

Reactor 模式是高性能网络编程的核心设计模式。其核心思想是：通过 I/O 多路复用监听多个 socket 上的事件，当有事件就绪时，分发给对应的事件处理器进行处理。

Reactor 模式包含三个核心角色：

1. **Reactor（反应器）**：运行在一个独立线程中，负责通过多路复用器（Selector）监听 I/O 事件，并将事件分发给对应的 Handler。
2. **Acceptor（接收器）**：处理连接建立事件，接受新的客户端连接，并将新连接注册到 Reactor 上。
3. **Handler（处理器）**：处理具体的 I/O 读写事件和业务逻辑。

Reactor 模式的核心逻辑伪代码：

```java
void Reactor::handleEvents() {
    // 通过同步事件多路选择器监听网络事件
    select(handlers);
    // 处理就绪的网络事件
    for (handler in handlers) {
        handler.handleEvent();
    }
}

// 在主程序中启动事件循环
while (true) {
    handleEvents();
}
```

Reactor 模式有三种经典变体：

**单线程 Reactor**：所有 I/O 操作（多路复用、事件分发、业务处理）都在一个线程上完成。优点是简单、无线程竞争；缺点是一个线程无法支撑大量请求，且业务处理慢会阻塞 I/O。

**多线程 Reactor**：有一组 NIO 线程处理 I/O 读写和业务处理。Reactor 线程只负责监听和分发事件，具体的 I/O 读写和业务处理由线程池中的线程完成。

**主从多线程 Reactor**（Netty 默认）：一个主 Reactor（bossGroup）专门处理连接请求，多个从 Reactor（workerGroup）处理读写请求。这是生产环境中最常用的模式。

## 三、核心链路设计

### 3.1 I/O 多路复用机制设计

I/O 多路复用是高性能网络编程的基石。其核心思想是：通过一次系统调用，同时监控多个文件描述符（socket）的状态，只有当某个文件描述符上有事件就绪时，才进行实际的 I/O 操作。

#### 3.1.1 select/poll 机制

select 和 poll 是 POSIX 标准定义的 I/O 多路复用系统调用。它们的工作原理类似：

1. 在内核态开辟空间，将感兴趣的文件描述符集合传入内核
2. 内核遍历所有文件描述符，检查是否有就绪事件
3. 返回就绪的文件描述符数量，应用程序再次遍历找出具体就绪的 fd

select 的关键系统调用：

```c
// select 系统调用签名
int select(int nfds, fd_set *readfds, fd_set *writefds,
           fd_set *exceptfds, struct timeval *timeout);

// 操作 fd_set 的宏
void FD_ZERO(fd_set *set);     // 清空集合
void FD_SET(int fd, fd_set *set);   // 将 fd 加入集合
void FD_CLR(int fd, fd_set *set);   // 从集合中移除 fd
int  FD_ISSET(int fd, fd_set *set); // 检查 fd 是否就绪
```

select/poll 的核心缺陷：
- **全量遍历**：每次调用都需要遍历所有注册的文件描述符，时间复杂度 O(n)
- **数据拷贝**：每次调用都需要将 fd 集合从用户态拷贝到内核态，返回时再拷贝回来
- **fd 数量限制**：select 默认限制 1024 个文件描述符（FD_SETSIZE），poll 虽然没有硬限制但仍有性能问题

#### 3.1.2 epoll 机制

epoll 是 Linux 特有的高性能 I/O 多路复用机制，通过三个核心系统调用解决 select/poll 的性能问题：

```c
// 1. 创建 epoll 实例，返回 epoll 文件描述符
int epoll_create1(int flags);

// 2. 向 epoll 实例的兴趣列表中添加/修改/删除文件描述符
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
// op: EPOLL_CTL_ADD / EPOLL_CTL_MOD / EPOLL_CTL_DEL

// 3. 等待 I/O 事件，从就绪列表中获取就绪的文件描述符
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
```

epoll 的核心优势在于：
- **内核维护兴趣列表**：fd 只需注册一次（epoll_ctl），不需要每次调用都传入全部 fd
- **就绪列表 O(1)**：内核通过回调机制将就绪的 fd 放入就绪列表，epoll_wait 只返回就绪的 fd，时间复杂度 O(1)
- **无 fd 数量限制**：理论上只受系统文件描述符上限限制

epoll 支持两种触发模式：

**水平触发（Level Triggered, LT）**——epoll 默认模式：
- 只要文件描述符的缓冲区中有数据可读，每次 epoll_wait 都会返回该事件
- 编程简单，但如果读取不完整会反复触发
- JDK NIO 的 Selector 在 Linux 下默认使用 LT 模式

**边缘触发（Edge Triggered, ET）**：
- 只在文件描述符状态发生变化时通知一次（例如从无数据变为有数据）
- 必须使用非阻塞 I/O，且必须读到 EAGAIN 才能停止
- 编程复杂但效率更高，减少了 epoll_wait 的唤醒次数

```java
// epoll ET 模式的正确使用方式
// 必须使用非阻塞文件描述符，且循环读取直到返回 EAGAIN
while (true) {
    int bytesRead = channel.read(buffer);
    if (bytesRead > 0) {
        // 处理数据
        processData(buffer);
    } else if (bytesRead == 0) {
        // 没有更多数据可读
        break;
    } else {
        // bytesRead == -1 表示连接关闭
        // 或者抛出异常时检查是否为 EAGAIN
        break;
    }
}
```

#### 3.1.3 Java NIO Selector 封装

Java NIO 的 Selector 屏蔽了不同操作系统的多路复用器差异。在 Linux 上默认使用 epoll，在 macOS 上使用 kqueue，在不支持的平台上回退到 select。

```java
// 使用 JDK 原生 NIO Selector 的服务端实现
public class NioSelectorServer {
    
    private Selector selector;
    private ExecutorService workerPool = Executors.newCachedThreadPool();
    
    public void start(int port) throws IOException {
        // 1. 创建 ServerSocketChannel 并配置为非阻塞
        ServerSocketChannel serverChannel = ServerSocketChannel.open();
        serverChannel.configureBlocking(false);
        serverChannel.socket().bind(new InetSocketAddress(port));
        
        // 2. 创建 Selector（底层调用 epoll_create）
        this.selector = Selector.open();
        
        // 3. 注册 OP_ACCEPT 事件到 Selector（底层调用 epoll_ctl）
        serverChannel.register(selector, SelectionKey.OP_ACCEPT);
        
        System.out.println("Server started on port " + port);
        
        // 4. 事件循环（底层调用 epoll_wait）
        while (true) {
            selector.select(); // 阻塞直到有事件就绪
            
            Iterator<SelectionKey> iterator = selector.selectedKeys().iterator();
            while (iterator.hasNext()) {
                SelectionKey key = iterator.next();
                iterator.remove(); // 必须移除已处理的 key
                
                if (key.isAcceptable()) {
                    handleAccept(key);
                } else if (key.isReadable()) {
                    // JDK NIO 是水平触发，需要先移除 OP_READ 事件
                    // 防止在数据未读完时反复触发
                    key.interestOps(key.interestOps() & (~SelectionKey.OP_READ));
                    workerPool.execute(() -> handleRead(key));
                }
            }
        }
    }
    
    private void handleAccept(SelectionKey key) throws IOException {
        ServerSocketChannel serverChannel = (ServerSocketChannel) key.channel();
        SocketChannel clientChannel = serverChannel.accept();
        clientChannel.configureBlocking(false);
        clientChannel.register(selector, SelectionKey.OP_READ);
        System.out.println("Client connected: " + clientChannel.getRemoteAddress());
    }
    
    private void handleRead(SelectionKey key) {
        SocketChannel channel = (SocketChannel) key.channel();
        ByteBuffer buffer = ByteBuffer.allocate(2048);
        try {
            ByteArrayOutputStream baos = new ByteArrayOutputStream();
            int size;
            while ((size = channel.read(buffer)) > 0) {
                buffer.flip();
                baos.write(buffer.array(), 0, size);
                buffer.clear();
            }
            
            if (size == -1) {
                // 连接关闭
                channel.close();
                return;
            }
            
            byte[] data = baos.toByteArray();
            String message = new String(data);
            System.out.println("Received: " + message);
            
            // 重新注册 OP_READ 事件
            if (key.isValid()) {
                key.interestOps(key.interestOps() | SelectionKey.OP_READ);
            }
        } catch (IOException e) {
            e.printStackTrace();
            try {
                channel.close();
            } catch (IOException ignored) {}
        }
    }
}
```

### 3.2 Netty Reactor 线程模型设计

#### 3.2.1 主从 Reactor 模型实现

Netty 的主从 Reactor 模型通过 bossGroup 和 workerGroup 两个 EventLoopGroup 实现：

```java
public class NettyServer {
    
    public void start(int port) throws InterruptedException {
        // 事件处理器
        final ServerHandler serverHandler = new ServerHandler();
        
        // boss 线程组：处理连接请求
        // 监听一个端口只需要 1 个 EventLoop
        EventLoopGroup bossGroup = new NioEventLoopGroup(1);
        
        // worker 线程组：处理读写请求
        // 默认创建 2 * CPU 核数 个 EventLoop
        EventLoopGroup workerGroup = new NioEventLoopGroup();
        
        try {
            ServerBootstrap bootstrap = new ServerBootstrap();
            bootstrap.group(bossGroup, workerGroup)
                     .channel(NioServerSocketChannel.class)
                     .option(ChannelOption.SO_BACKLOG, 1024)
                     .childOption(ChannelOption.TCP_NODELAY, true)
                     .childOption(ChannelOption.SO_KEEPALIVE, true)
                     .childHandler(new ChannelInitializer<SocketChannel>() {
                         @Override
                         protected void initChannel(SocketChannel ch) {

        } finally {

            bossGroup.shutdownGracefully();
        }
    }
```

#### 3.2.2 EventLoop 的核心职责

EventLoop 是 Netty 的发动机，其核心职责包括：

1. **I/O 事件监听**：通过 Selector 监听注册在其上的所有 Channel 的 I/O 事件
2. **事件分发处理**：将就绪的 I/O 事件分发给 ChannelPipeline 中的 ChannelHandler 处理
3. **定时任务执行**：执行通过 EventLoop 的 schedule() 提交的定时任务
4. **普通任务执行**：执行通过 EventLoop 的 execute() 提交的普通任务

```java
// EventLoop 的简化执行逻辑
public class NioEventLoop {
    
    private final Selector selector;
    private final Queue<Runnable> taskQueue = new LinkedBlockingQueue<>();
    private volatile boolean running = true;
    
    public void run() {
        while (running) {
            try {
                // 1. 执行 I/O 事件选择（带有超时，确保能及时处理任务队列）
                int readyCount = selector.select(1000);
                
                // 2. 处理就绪的 I/O 事件
                if (readyCount > 0) {
                    processSelectedKeys();
                }
                
                // 3. 执行任务队列中的任务
                runAllTasks();
                
            } catch (Exception e) {
                handleException(e);
            }
        }
    }
    
    private void processSelectedKeys() {
        Iterator<SelectionKey> iterator = selector.selectedKeys().iterator();
        while (iterator.hasNext()) {
            SelectionKey key = iterator.next();
            iterator.remove();
            
            try {
                if (key.isReadable()) {
                    processRead(key);
                } else if (key.isWritable()) {
                    processWrite(key);
                }
            } catch (Exception e) {
                key.cancel();
                handleChannelException(key, e);
            }
        }
    }
    
    private void runAllTasks() {
        Runnable task;
        while ((task = taskQueue.poll()) != null) {
            try {
                task.run();
            } catch (Exception e) {
                // 记录异常但不中断循环
                e.printStackTrace();
            }
        }
    }
    
    // 提交任务到 EventLoop
    public void execute(Runnable task) {
        taskQueue.add(task);
        selector.wakeup(); // 唤醒被 select 阻塞的线程
    }
}
```

#### 3.2.3 连接分配机制

当 bossGroup 接收到新的连接请求后，需要将新连接分配给 workerGroup 中的某个 EventLoop。Netty 使用轮询算法进行分配：

```java
// 简化的连接分配逻辑
public class EventLoopGroup {
    
    private final EventLoop[] children;
    private int idx = 0;
    
    public EventLoopGroup(int nThreads) {
        this.children = new EventLoop[nThreads];
        for (int i = 0; i < nThreads; i++) {
            children[i] = new EventLoop();
            new Thread(children[i], "event-loop-" + i).start();
        }
    }
    
    // 轮询选择一个 EventLoop
    public EventLoop next() {
        return children[idx++ % children.length];
    }
    
    // 注册新连接到某个 EventLoop
    public void register(Channel channel) {
        EventLoop eventLoop = next();
        eventLoop.register(channel);
        // channel 和 eventLoop 的绑定关系一旦确定就不再变化
        channel.setEventLoop(eventLoop);
    }
}
```

**关键设计原则**：一个网络连接只会对应到一个 EventLoop，且这个对应关系在连接的生命周期内不会变化。这意味着对于同一个连接的所有 I/O 操作（读、写、连接关闭）都在同一个线程中执行，天然避免了并发问题。

### 3.4 粘包与半包解决方案

TCP 是面向字节流的协议，没有消息边界。如果不做处理，会出现粘包（多条消息粘在一起）和半包（一条消息被拆分）问题。

常见的解决方案有四种：

```java
// 方案1：固定长度解码器（每个消息固定 N 字节）
pipeline.addLast("fixedLength", new FixedLengthFrameDecoder(100));

// 方案2：行分隔符解码器（以 \n 或 \r\n 分隔）
pipeline.addLast("lineBased", new LineBasedFrameDecoder(1024));

// 方案3：自定义分隔符解码器
pipeline.addLast("delimiter", new DelimiterBasedFrameDecoder(
    1024, Unpooled.wrappedBuffer(new byte[]{'$', '$'})));

// 方案4：基于长度字段的解码器（最常用，推荐）
// 协议格式：[长度(4字节)] [消息体(N字节)]
pipeline.addLast("lengthField", new LengthFieldBasedFrameDecoder(
    1024 * 1024,  // maxFrameLength：最大帧长度
    0,             // lengthFieldOffset：长度字段偏移量
    4,             // lengthFieldLength：长度字段占用的字节数
    0,             // lengthAdjustment：长度调整值
    4              // initialBytesToStrip：跳过的初始字节数（跳过长度字段本身）
));

// 对应的编码器
pipeline.addLast("lengthFieldEncoder", new LengthFieldPrepender(4));
```

基于长度字段的编解码是最推荐的方案，因为它兼顾了通用性和效率。其协议格式为：

```
+--------+-------------------+
| Length |    Message Body    |
| 4 bytes|    N bytes         |
+--------+-------------------+
```

### 3.5 ByteBuf 与零拷贝设计

ByteBuf 是 Netty 重新设计的字节缓冲区，相比 JDK 的 ByteBuffer 提供了以下核心优势：

```java
public class ByteBufExample {
    
    public void zeroCopyExample() {
        // 1. 组合多个 ByteBuf，无需内存拷贝（CompositeByteBuf）
        ByteBuf header = Unpooled.wrappedBuffer("HEADER".getBytes());
        ByteBuf body = Unpooled.wrappedBuffer("BODY".getBytes());
        
        CompositeByteBuf composite = Unpooled.compositeBuffer();
        composite.addComponents(true, header, body);
        // composite 逻辑上包含 "HEADERBODY"，但物理上是两个独立的 buffer
        // 没有发生内存拷贝
        
        // 2. 包装现有字节数组，无需拷贝
        byte[] data = new byte[1024];
        ByteBuf wrappedBuf = Unpooled.wrappedBuffer(data);
        // 修改 data 会直接影响 wrappedBuf
        
        // 3. 切片，共享底层数组
        ByteBuf sliced = wrappedBuf.slice(0, 100);
        // sliced 和 wrappedBuf 共享同一块内存
        
        // 4. 池化 ByteBuf（减少 GC 压力）
        ByteBuf pooledBuf = PooledByteBufAllocator.DEFAULT.directBuffer(1024);
        // 使用完毕后必须释放
        pooledBuf.release();
    }
    
    public void readWriteExample() {
        ByteBuf buf = Unpooled.buffer(256);
        
        // 读写索引分离，无需 flip()
        buf.writeInt(100);        // writeIndex += 4
        buf.writeLong(200L);      // writeIndex += 8
        buf.writeBytes("hello".getBytes()); // writeIndex += 5
        
        // 读取时不需要 flip
        int intValue = buf.readInt();   // readIndex += 4
        long longValue = buf.readLong(); // readIndex += 8
        byte[] strBytes = new byte[5];
        buf.readBytes(strBytes);         // readIndex += 5
        
        // 可读字节数 = writeIndex - readIndex
        int readableBytes = buf.readableBytes();
        
        // 可写字节数 = capacity - writeIndex
        int writableBytes = buf.writableBytes();
    }
    
    // 堆内 ByteBuf vs 堆外 ByteBuf
    public void bufferTypeComparison() {
        // 堆内缓冲区（Heap Buffer）
        // 优点：分配/释放快，GC 自动管理
        // 缺点：I/O 操作需要额外拷贝（堆内 -> 内核态）
        ByteBuf heapBuf = ByteBufAllocator.DEFAULT.heapBuffer(1024);
        
        // 堆外缓冲区（Direct Buffer）
        // 优点：I/O 操作零拷贝（直接在内核态操作），减少一次内存拷贝
        // 缺点：分配/释放慢，需要手动管理（引用计数）
        // 推荐：网络 I/O 场景使用 Direct Buffer
        ByteBuf directBuf = ByteBufAllocator.DEFAULT.directBuffer(1024);
        
        // 使用完毕必须释放引用
        heapBuf.release();
        directBuf.release();
    }
}
```

### 3.6 自定义协议设计

在高性能 RPC 和网关场景中，通常需要设计自定义二进制协议来替代 HTTP：

```java
// 自定义协议格式
// +----------+----------+----------+----------+----------+----------+
// |  Magic   |  Version |   Type   |    RequestId     |  Length   |
// |  2 bytes |  1 byte  |  1 byte  |     4 bytes      |  4 bytes  |
// +----------+----------+----------+----------+----------+----------+
// |                         Message Body                            |
// |                        N bytes (N = Length)                     |
// +----------+----------+----------+----------+----------+----------+

public class ProtocolConstants {
    public static final short MAGIC = (short) 0xCAFEBABE;
    public static final byte VERSION = 1;
    
    // 消息类型
    public static final byte TYPE_REQUEST = 0x01;
    public static final byte TYPE_RESPONSE = 0x02;
    public static final byte TYPE_HEARTBEAT = 0x03;
    public static final byte TYPE_HANDSHAKE = 0x04;
    
    // 协议头长度
    public static final int HEADER_LENGTH = 12;
}

public class ProtocolMessage implements Serializable {
    private short magic;
    private byte version;
    private byte type;
    private int requestId;
    private int length;
    private byte[] body;
    
    // getters and setters...
}

// 协议解码器
public class ProtocolDecoder extends ByteToMessageDecoder {
    
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        // 确保有足够的数据读取协议头
        if (in.readableBytes() < ProtocolConstants.HEADER_LENGTH) {
            return;
        }
        
        // 标记当前读取位置，用于半包回退
        in.markReaderIndex();
        
        // 读取 magic
        short magic = in.readShort();
        if (magic != ProtocolConstants.MAGIC) {
            // 协议错误，关闭连接
            ctx.close();
            return;
        }
        
        byte version = in.readByte();
        byte type = in.readByte();
        int requestId = in.readInt();
        int length = in.readInt();
        
        // 防止恶意大包攻击
        if (length > 1024 * 1024) {
            throw new DecoderException("Message too large: " + length);
        }
        
        // 检查是否有完整的消息体
        if (in.readableBytes() < length) {
            // 半包：重置读取位置，等待更多数据到达
            in.resetReaderIndex();
            return;
        }
        
        // 读取消息体
        byte[] body = new byte[length];
        in.readBytes(body);
        
        ProtocolMessage message = new ProtocolMessage();
        message.setMagic(magic);
        message.setVersion(version);
        message.setType(type);
        message.setRequestId(requestId);
        message.setLength(length);
        message.setBody(body);
        
        out.add(message);
    }
}

// 协议编码器
public class ProtocolEncoder extends MessageToByteEncoder<ProtocolMessage> {
    
    @Override
    protected void encode(ChannelHandlerContext ctx, ProtocolMessage msg, ByteBuf out) {
        out.writeShort(msg.getMagic());
        out.writeByte(msg.getVersion());
        out.writeByte(msg.getType());
        out.writeInt(msg.getRequestId());
        out.writeInt(msg.getBody().length);
        out.writeBytes(msg.getBody());
    }
}
```

### 3.7 心跳保活机制设计

长连接场景下，需要通过心跳机制检测连接的存活状态，及时清理僵死连接：

```java
public class HeartbeatHandler extends ChannelInboundHandlerAdapter {
    
    private static final int HEARTBEAT_INTERVAL = 30; // 秒
    private static final int MAX_HEARTBEAT_TIMEOUT = 3; // 最大超时次数
    
    @Override
    public void userEventTriggered(ChannelHandlerContext ctx, Object evt) throws Exception {
        if (evt instanceof IdleStateEvent) {
            IdleStateEvent event = (IdleStateEvent) evt;
            switch (event.state()) {
                case READER_IDLE:
                    // 读空闲：服务端长时间没有收到客户端数据
                    // 可能客户端已断开，关闭连接
                    System.out.println("Read idle, closing connection: " + ctx.channel());
                    ctx.close();
                    break;
                    
                case WRITER_IDLE:
                    // 写空闲：长时间没有向对端发送数据
                    // 发送心跳包
                    ProtocolMessage heartbeat = new ProtocolMessage();
                    heartbeat.setMagic(ProtocolConstants.MAGIC);
                    heartbeat.setVersion(ProtocolConstants.VERSION);
                    heartbeat.setType(ProtocolConstants.TYPE_HEARTBEAT);
                    heartbeat.setRequestId(RequestIdGenerator.next());
                    heartbeat.setBody(new byte[0]);
                    ctx.writeAndFlush(heartbeat);
                    System.out.println("Sent heartbeat to: " + ctx.channel().remoteAddress());
                    break;
                    
                case ALL_IDLE:
                    // 读写都空闲
                    break;
            }
        } else {
            super.userEventTriggered(ctx, evt);
        }
    }
}
```

```java
                 .option(ChannelOption.SO_KEEPALIVE, true)
                 .handler(new ChannelInitializer<SocketChannel>() {
                     @Override
                     protected void initChannel(SocketChannel ch) {
                         ChannelPipeline pipeline = ch.pipeline();
                         pipeline.addLast("idleState", 
                             new IdleStateHandler(0, 30, 0, TimeUnit.SECONDS));
                         pipeline.addLast("heartbeat", new HeartbeatHandler());
                         pipeline.addLast("frameDecoder", 
                             new LengthFieldBasedFrameDecoder(1024*1024, 0, 4, 0, 4));
                         pipeline.addLast("frameEncoder", new LengthFieldPrepender(4));
                         pipeline.addLast("decoder", new ProtocolDecoder());
                         pipeline.addLast("encoder", new ProtocolEncoder());
                         pipeline.addLast("reconnect", new ReconnectHandler(this));
                         pipeline.addLast("business", new ClientBusinessHandler());
                     }
                 });
    }
    
    // 轮询选择一个连接
    private final AtomicInteger counter = new AtomicInteger(0);
    
    public Channel getChannel() {
        if (channels.isEmpty()) {
            throw new IllegalStateException("No available connection");
        }
        int index = counter.getAndIncrement() % channels.size();
        return channels.get(Math.abs(index));
    }
    
    // 建立连接
    public ChannelFuture connect() {
        ChannelFuture future = bootstrap.connect(host, port);
        future.addListener((ChannelFutureListener) f -> {
            if (f.isSuccess()) {
                channels.add(f.channel());
                System.out.println("Connected to " + host + ":" + port);
            } else {
                System.err.println("Connect failed, retrying...");
                // 延迟重连
                eventLoopGroup.schedule(() -> connect(), 3, TimeUnit.SECONDS);
            }
        });
        return future;
    }
    
    // 断线重连处理器
    private class ReconnectHandler extends ChannelInboundHandlerAdapter {
        private final ConnectionManager manager;
        private int retryCount = 0;
        private static final int MAX_RETRY = 10;
        
        ReconnectHandler(ConnectionManager manager) {
            this.manager = manager;
        }
        
        @Override
        public void channelInactive(ChannelHandlerContext ctx) {
            channels.remove(ctx.channel());
            
            if (retryCount < MAX_RETRY) {
                retryCount++;
                long delay = Math.min(retryCount * 2L, 60); // 指数退避，最大60秒
                System.out.println("Connection lost, retrying in " + delay + "s...");
                ctx.channel().eventLoop().schedule(() -> {
                    manager.connect();
                }, delay, TimeUnit.SECONDS);
            } else {
                System.err.println("Max retry count reached, giving up.");
            }
        }
    }
}
```

## 四、异常处理

### 4.1 I/O 异常处理策略

网络编程中的异常主要分为以下几类，需要分别设计处理策略：

```java
// 统一异常处理器
public class GlobalExceptionHandler extends ChannelDuplexHandler {
    
    private static final Logger logger = LoggerFactory.getLogger(GlobalExceptionHandler.class);
    
    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
        if (cause instanceof IOException) {
            // 1. I/O 异常：网络中断、连接重置等
            handleIOException(ctx, (IOException) cause);
        } else if (cause instanceof DecoderException) {
            // 2. 解码异常：协议格式错误、半包/粘包处理失败
            handleDecoderException(ctx, (DecoderException) cause);
        } else if (cause instanceof EncoderException) {
            // 3. 编码异常：序列化失败
            handleEncoderException(ctx, (EncoderException) cause);
        } else if (cause instanceof TooLongFrameException) {
            // 4. 帧长度超限：可能的恶意攻击或配置错误
            handleTooLongFrameException(ctx, (TooLongFrameException) cause);
        } else if (cause instanceof ReadTimeoutException) {
            // 5. 读超时
            handleReadTimeoutException(ctx, (ReadTimeoutException) cause);
        } else if (cause instanceof WriteTimeoutException) {
            // 6. 写超时
            handleWriteTimeoutException(ctx, (WriteTimeoutException) cause);
        } else {
            // 7. 其他未预期异常
            handleUnexpectedException(ctx, cause);
        }
    }
    
    private void handleIOException(ChannelHandlerContext ctx, IOException cause) {
        logger.warn("I/O exception on channel {}: {}", 
            ctx.channel().remoteAddress(), cause.getMessage());

        ctx.close();

        logger.error("Decode exception on channel {}: {}", 
            ctx.channel().remoteAddress(), cause.getMessage());

        ctx.close();
```

### 4.2 连接异常恢复

```java
// 连接异常恢复管理器
public class ConnectionRecoveryManager {
    
    private final ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
    private final Map<Channel, Integer> failureCount = new ConcurrentHashMap<>();
    private static final int MAX_FAILURES = 5;
    private static final long RECOVERY_DELAY = 5000; // 5秒
    
    public void onFailure(Channel channel) {
        int count = failureCount.merge(channel, 1, Integer::sum);
        
        if (count >= MAX_FAILURES) {
            // 超过最大失败次数，关闭连接
            channel.close();
            failureCount.remove(channel);
            logger.warn("Channel {} closed after {} failures", channel.remoteAddress(), count);
        } else {
            // 调度恢复检查
            scheduler.schedule(() -> {
                if (channel.isActive()) {
                    failureCount.remove(channel);
                }
            }, RECOVERY_DELAY, TimeUnit.MILLISECONDS);
        }
    }
    
    public void onSuccess(Channel channel) {
        failureCount.remove(channel);
    }
}
```

```java
            // 使用 ByteBuf
            processBuffer(buf);

            // buf.retain();
            // asyncProcess(buf, () -> buf.release());

        ByteBuf direct = ctx.alloc().directBuffer(in.readableBytes());
        try {
            direct.writeBytes(in);
            processDirectBuffer(direct);
        } finally {
            direct.release();
        }
```

### 5.3 批量写入优化

```java
public class BatchWriteOptimizer {
    
    // 利用 Channel 的批量写入能力
    public void batchWrite(Channel channel, List<ByteBuf> messages) {
        // 方法1：使用 Channel 的 write 方法（不立即 flush）
        for (ByteBuf msg : messages) {
            channel.write(msg);
        }
        // 一次性 flush，减少系统调用
        channel.flush();
        
        // 方法2：使用 CompositeByteBuf 合并多个消息
        CompositeByteBuf composite = ByteBufAllocator.DEFAULT.compositeBuffer();
        for (ByteBuf msg : messages) {
            composite.addComponent(true, msg);
        }
        channel.writeAndFlush(composite);
        
        // 方法3：使用 ChannelPromise 批量等待
        ChannelPromise promise = channel.newPromise();
        int pendingWrites = messages.size();
        for (ByteBuf msg : messages) {
            channel.write(msg, promise.addListener(future -> {
                if (--pendingWrites == 0) {
                    // 所有写入完成
                }
            }));
        }
        channel.flush();
    }
}
```

## 六、最佳实践

### 6.1 Reactor 线程模型选择

根据不同的业务场景选择合适的 Reactor 模式：

| 场景 | 推荐模式 | bossGroup 线程数 | workerGroup 线程数 |
|------|---------|-----------------|-------------------|
| 单端口、低并发 | 单线程 Reactor | 1 | 1 |
| 单端口、中高并发 | 主从 Reactor（推荐） | 1 | 2 * CPU |
| 多端口、高并发 | 主从 Reactor | 端口数 | 2 * CPU |
| 超高并发、长连接 | 主从 Reactor + 业务线程池 | 1 | 2~4 * CPU |

### 6.2 不要在 EventLoop 中执行阻塞操作

这是 Netty 使用中最重要的原则。EventLoop 线程负责处理多个连接的 I/O 事件，如果被阻塞，会导致该 EventLoop 上所有连接的事件处理被阻塞：

```java
// 错误做法：在 EventLoop 线程中执行阻塞操作
public class BadHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        // 错误：数据库查询是阻塞操作，会阻塞 EventLoop 线程
        User user = userDao.findById(userId); // 阻塞！
        
        // 错误：Thread.sleep 也是阻塞操作
        Thread.sleep(1000); // 阻塞！
        
        // 错误：同步 RPC 调用
        String result = rpcService.call(); // 阻塞！
        
        ctx.writeAndFlush(result);
    }
}

// 正确做法：使用业务线程池处理阻塞操作
public class GoodHandler extends ChannelInboundHandlerAdapter {
    
    private final ExecutorService businessExecutor = Executors.newFixedThreadPool(
        Runtime.getRuntime().availableProcessors() * 8);
    
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        businessExecutor.submit(() -> {
            try {
                // 在业务线程池中执行阻塞操作
                User user = userDao.findById(userId);
                String result = processBusiness(user);
                
                // 写回响应时需要回到 EventLoop 线程
                // ctx.writeAndFlush 会自动切回 EventLoop 线程
                ctx.writeAndFlush(result);
            } catch (Exception e) {
                ctx.fireExceptionCaught(e);
            }
        });
    }
}
```

### 6.6 安全防护

```java
public class SecurityHandler extends ChannelInboundHandlerAdapter {
    
    // 连接速率限制
    private final RateLimiter connectionRateLimiter = RateLimiter.create(100); // 每秒100个新连接
    
    // 单连接消息速率限制
    private final Map<Channel, RateLimiter> messageRateLimiters = new ConcurrentHashMap<>();
    private static final double MAX_MESSAGES_PER_SECOND = 1000;
    
    // 黑名单 IP
    private final Set<String> blacklist = ConcurrentHashMap.newKeySet();
    
    @Override
    public void channelActive(ChannelHandlerContext ctx) {
        String remoteIp = getRemoteIp(ctx.channel());
        
        // 检查黑名单
        if (blacklist.contains(remoteIp)) {
            ctx.close();
            return;
        }
        
        // 连接速率限制
        if (!connectionRateLimiter.tryAcquire()) {
            logger.warn("Connection rate limit exceeded, rejecting: {}", remoteIp);
            ctx.close();
            return;
        }
        
        // 为每个连接创建消息速率限制器
        messageRateLimiters.put(ctx.channel(), RateLimiter.create(MAX_MESSAGES_PER_SECOND));
        
        ctx.fireChannelActive();
    }
    
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        RateLimiter limiter = messageRateLimiters.get(ctx.channel());
        if (limiter != null && !limiter.tryAcquire()) {
            logger.warn("Message rate limit exceeded on channel: {}", ctx.channel());
            ctx.close();
            return;
        }
        
        ctx.fireChannelRead(msg);
    }
    
    @Override
    public void channelInactive(ChannelHandlerContext ctx) {
        messageRateLimiters.remove(ctx.channel());
        ctx.fireChannelInactive();
    }
    
    private String getRemoteIp(Channel channel) {
        if (channel.remoteAddress() instanceof InetSocketAddress) {
            return ((InetSocketAddress) channel.remoteAddress()).getAddress().getHostAddress();
        }
        return "unknown";
    }
}
```

## 七、总结

网络编程是后端架构的基础设施层，其设计质量直接影响整个系统的并发能力、稳定性和性能。核心要点回顾：

1. **I/O 模型选择**：在高并发场景下，I/O 多路复用（epoll）是当前 Linux 平台的主流选择。epoll 通过内核维护兴趣列表和就绪列表，将事件通知的时间复杂度从 O(n) 降到 O(1)，是支撑百万连接的关键。

2. **Reactor 模式**：通过事件驱动的方式，用少量线程处理大量连接。主从 Reactor 模式（bossGroup 处理连接、workerGroup 处理读写）是生产环境的标配。核心设计原则是一个连接只绑定一个 EventLoop 线程，避免并发问题。

3. **协议设计**：自定义二进制协议 + 基于长度字段的帧解码器是解决粘包/半包问题的推荐方案。协议设计需要兼顾扩展性（版本号、魔数）和安全性（最大帧长度限制）。

4. **内存管理**：池化 ByteBuf + 堆外 Direct Buffer 是网络 I/O 场景的最佳组合，通过零拷贝技术（CompositeByteBuf、slice、wrappedBuffer）减少内存拷贝，通过引用计数管理内存生命周期。

5. **线程模型纪律**：永远不要在 EventLoop 线程中执行阻塞操作，这是 Netty 使用的第一原则。重计算或阻塞操作应该提交到业务线程池异步处理。

6. **异常与安全**：建立完善的异常分类处理机制（I/O 异常、协议异常、超时异常等），配合连接速率限制、消息速率限制、黑名单等安全防护手段，保障系统在异常和攻击场景下的稳定性。
