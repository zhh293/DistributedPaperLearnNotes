# 分布式锁架构设计

## 一、问题背景

### 1.1 为什么需要分布式锁

在单机应用中，当多个线程需要访问共享资源时，可以通过语言层面提供的同步机制来实现互斥控制，例如 Java 中的 `synchronized` 关键字、`ReentrantLock`、`ReadWriteLock` 等。这些机制依赖单一 JVM 内的内存模型，能够保证同一时刻只有一个线程进入临界区。然而，当系统从单机演进到分布式架构后，多个服务实例部署在不同的物理机上，各自拥有独立的 JVM 和内存空间，传统的单机锁机制完全失效。

考虑以下典型场景：一个电商系统部署了 4 个订单服务实例，前端请求经过负载均衡后分发到不同实例。如果用户对同一商品快速发起多次下单请求，这些请求可能被路由到不同的服务实例上。每个实例在本地 JVM 内部完成加锁，但跨实例之间没有任何协调机制，导致库存超卖。

**单机锁失效的根本原因：**

- `synchronized` 和 `ReentrantLock` 的锁状态存储在当前 JVM 的对象头或 AQS 队列中
- 不同 JVM 之间无法共享锁状态
- 分布式环境下，锁状态必须存储在所有实例都能访问的共享存储中

### 1.2 典型应用场景

**场景一：库存扣减**

电商秒杀活动中，商品库存为 100 件，瞬时涌入 10 万请求。多个服务实例同时读取库存、判断库存是否充足、执行扣减。如果没有分布式锁，多个实例可能同时读到库存为 1，然后各自扣减，导致超卖。

**场景二：订单去重**

用户因网络抖动连续点击"提交订单"按钮，同一笔请求被发送到不同的服务实例。如果没有分布式锁保护，可能创建重复订单，造成业务数据异常和用户投诉。

**场景三：定时任务单次执行**

分布式系统中通常部署多个实例做高可用，但定时任务（如每日对账、数据同步、报表生成）只需要执行一次。如果每个实例都执行定时任务，会导致重复处理、数据错乱。需要分布式锁确保只有一个实例执行。

**场景四：分布式限流**

在网关层或服务层实现分布式限流时，需要统计全局的请求速率。多个实例需要共享计数器，通过分布式锁保证计数操作的原子性，或使用分布式锁实现对限流窗口的互斥访问。

**场景五：配置热更新**

当配置中心推送配置变更时，多个实例同时监听到变更并尝试重新加载配置。某些场景下需要确保配置加载的顺序性或避免并发加载冲突，可以通过分布式锁串行化配置刷新操作。

### 1.3 分布式锁的核心要求

一个生产可用的分布式锁必须满足以下核心要求：

**互斥性（Mutual Exclusion）：**
- 这是最基本的要求，同一时刻只有一个客户端能持有锁
- 不仅要求同一资源同一时刻只有一个持有者，还要求在不同节点上的客户端也能正确互斥
- 互斥性必须在任何网络条件和故障场景下都能得到保证

**防死锁（Deadlock Prevention）：**
- 即使持有锁的客户端发生崩溃（如进程被 kill、机器宕机），锁也必须最终被释放
- 不能出现锁永远无法被释放的情况，否则其他客户端将永远无法获取锁
- 通常通过设置锁的过期时间（TTL）或依赖会话超时机制来实现

**可重入性（Reentrancy）：**
- 同一个客户端（或同一个线程）在持有锁的情况下，可以再次获取同一把锁
- 避免递归调用或嵌套调用时出现自我死锁
- 需要记录锁的持有者和重入次数

**容错性（Fault Tolerance）：**
- 锁服务本身不能成为单点故障
- 当锁服务的部分节点宕机时，锁服务仍能正常工作
- 客户端能够感知锁服务的状态并做出正确的处理

**高性能（Performance）：**
- 加锁和解锁操作应该足够快，不能成为系统的性能瓶颈
- 锁的获取和释放通常应在毫秒级别完成
- 锁服务应能支撑高并发的锁操作请求

### 1.4 缺少分布式锁的后果

| 问题类型 | 具体表现 | 业务影响 |
|---------|---------|---------|
| 超卖 | 库存为 1 时多个请求同时扣减成功 | 直接资金损失，客诉 |
| 重复处理 | 同一消息被多个实例消费 | 数据重复，幂等性破坏 |
| 重复执行 | 定时任务被多实例同时执行 | 资源浪费，数据错乱 |
| 竞态条件 | 配置并发修改导致状态不一致 | 系统行为不可预测 |
| 资源争用 | 多实例同时写同一文件/数据库行 | 数据损坏 |

### 1.5 分布式锁与单机锁的关系

分布式锁并不是单机锁的简单替代，两者在适用范围和实现机制上有本质区别：

- 单机锁解决的是同一进程内多线程的并发问题，延迟在纳秒到微秒级别
- 分布式锁解决的是跨进程、跨机器的并发问题，延迟在毫秒级别（取决于网络 RTT）
- 分布式锁通常需要与本地锁配合使用：先获取分布式锁保证跨实例互斥，再在本地使用单机锁保证多线程安全
- 分布式锁的获取和释放成本远高于单机锁，应尽量减少锁的持有时间和获取频率

## 二、整体架构设计

### 2.1 三种主流实现方案

分布式锁的实现本质上是寻找一个所有参与方都能访问的共享存储介质，利用该介质的原子性操作来实现互斥。目前业界有三种主流方案：

**方案一：基于数据库实现**

利用关系型数据库的唯一索引约束或行锁机制。通过 `INSERT` 唯一键冲突来实现互斥，或通过 `SELECT ... FOR UPDATE` 实现行级锁。优点是简单直接，不需要引入额外组件；缺点是性能较差、扩展性有限。

**方案二：基于 Redis 实现**

利用 Redis 的 `SET key value NX EX` 原子命令实现互斥。Redis 是内存数据库，单机 QPS 可达 10 万+，性能极高。配合 Lua 脚本可以保证解锁操作的原子性。Redisson 框架提供了可重入锁、公平锁、读写锁、看门狗等丰富功能。缺点是 Redis 主从异步复制可能导致锁丢失。

**方案三：基于 ZooKeeper 实现**

利用 ZooKeeper 的临时顺序节点和 Watcher 机制实现。ZK 基于 ZAB 协议保证强一致性，客户端会话失效时临时节点自动删除，天然具备防死锁能力。Curator 框架封装了完善的锁实现。缺点是性能低于 Redis，且 ZK 集群部署和运维成本较高。

### 2.2 方案对比

| 维度 | 数据库 | Redis | ZooKeeper |
|------|--------|-------|-----------|
| 性能（QPS） | 1000-3000 | 10万+ | 1万-2万 |
| 可靠性 | 中（依赖DB主从） | 中（异步复制可能丢锁） | 高（ZAB强一致） |
| 复杂度 | 低 | 中 | 高 |
| 可用性 | 依赖DB可用性 | AP，高可用 | CP，半数以上节点存活即可 |
| 防死锁 | 需额外实现（定时清理） | TTL自动过期 | 会话超时自动删除 |
| 可重入 | 需自行实现 | Redisson原生支持 | Curator原生支持 |
| 公平锁 | 难以实现 | Redisson支持 | 顺序节点天然支持 |
| 运维成本 | 低（复用现有DB） | 中 | 高（需独立ZK集群） |
| 适用场景 | 低频、简单场景 | 高并发场景 | 强一致性要求场景 |

### 2.3 CAP 理论下的选型考量

分布式锁的实现方案本质上是在 CAP 理论下做权衡：

**CP 方案（ZooKeeper）：**
- 保证一致性和分区容错性，牺牲可用性
- 当 ZK 集群发生分区时，未拥有多数派节点的分区会停止服务
- 锁的状态在所有节点间强一致，不会出现两个客户端同时持有锁的情况
- 适合对正确性要求极高的场景，如金融转账

**AP 方案（Redis）：**
- 保证可用性和分区容错性，牺牲强一致性
- Redis 主从异步复制，主节点宕机时从节点可能还未同步到锁数据
- 极端情况下可能出现锁丢失，即两个客户端同时认为自己持有锁
- 适合对性能要求高、能容忍极小概率锁丢失的场景，如库存扣减（可配合幂等兜底）

**选型建议：**

```
对正确性 > 性能 → ZooKeeper（如金融交易、配置变更）
对性能 > 正确性 → Redis（如秒杀抢购、限流）
已有DB无额外组件 → 数据库（如低频后台任务）
需要多种锁类型 → Redis（Redisson 支持丰富锁类型）
```

## 三、核心链路设计

### 3.1 基于数据库的分布式锁

#### 3.1.1 唯一索引方案

最简单的数据库锁方案是利用 MySQL 的唯一索引约束。创建一张锁表，以资源名称作为唯一键，`INSERT` 成功即获取锁，`DELETE` 即释放锁。

**建表语句：**

```sql
CREATE TABLE `distributed_lock` (
    `id`          BIGINT       NOT NULL AUTO_INCREMENT,
    `resource`    VARCHAR(128) NOT NULL COMMENT '锁定的资源名称',
    `owner`       VARCHAR(128) NOT NULL COMMENT '锁持有者标识(UUID)',
    `thread_id`   VARCHAR(64)  NOT NULL COMMENT '线程标识',
    `reentrant_count` INT      NOT NULL DEFAULT 0 COMMENT '重入次数',
    `created_at`  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `expire_at`   TIMESTAMP    NOT NULL COMMENT '锁过期时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_resource` (`resource`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分布式锁表';
```

**加锁逻辑：**

```java
/**
 * 基于数据库唯一索引的分布式锁
 */
public class DatabaseDistributedLock {

    private final JdbcTemplate jdbcTemplate;
    private final String lockOwner = UUID.randomUUID().toString();

    public DatabaseDistributedLock(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    /**
     * 尝试获取锁
     * @param resource 资源名称
     * @param expireSeconds 过期时间（秒）
     * @return 是否获取成功
     */
    public boolean tryLock(String resource, int expireSeconds) {
        try {
            // 先清理过期的锁记录（防止死锁）
            String deleteExpiredSql = "DELETE FROM distributed_lock WHERE expire_at < NOW()";
            jdbcTemplate.update(deleteExpiredSql);

            // 尝试 INSERT，利用唯一索引冲突实现互斥
            String insertSql = "INSERT INTO distributed_lock (resource, owner, thread_id, reentrant_count, expire_at) " +
                    "VALUES (?, ?, ?, 0, DATE_ADD(NOW(), INTERVAL ? SECOND))";
            int rows = jdbcTemplate.update(insertSql, resource, lockOwner,
                    String.valueOf(Thread.currentThread().getId()), expireSeconds);
            return rows > 0;
        } catch (DuplicateKeyException e) {
            // 唯一索引冲突，说明锁已被其他实例持有
            return false;
        }
    }

    /**
     * 释放锁
     * @param resource 资源名称
     */
    public void unlock(String resource) {
        // 只能释放自己持有的锁
        String sql = "DELETE FROM distributed_lock WHERE resource = ? AND owner = ?";
        jdbcTemplate.update(sql, resource, lockOwner);
    }

    /**
     * 带重试的获取锁
     */
    public boolean tryLock(String resource, int expireSeconds, long retryIntervalMillis, int maxRetries) {
        for (int i = 0; i <= maxRetries; i++) {
            if (tryLock(resource, expireSeconds)) {
                return true;
            }
            if (i < maxRetries) {
                try {
                    Thread.sleep(retryIntervalMillis);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return false;
                }
            }
        }
        return false;
    }
}
```

#### 3.1.2 SELECT FOR UPDATE 方案

利用 MySQL InnoDB 的行锁，通过 `SELECT ... FOR UPDATE` 实现悲观锁：

```java
/**
 * 基于 SELECT FOR UPDATE 的数据库分布式锁
 */
public class PessimisticDatabaseLock {

    private final DataSource dataSource;

    public PessimisticDatabaseLock(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    /**
     * 获取锁（阻塞式）
     * 在事务中执行 SELECT FOR UPDATE，获取行级排他锁
     */
    public Connection lock(String resource, int timeoutSeconds) throws SQLException {
        Connection conn = dataSource.getConnection();
        try {
            conn.setAutoCommit(false);
            // 设置锁等待超时
            conn.createStatement().execute("SET innodb_lock_wait_timeout = " + timeoutSeconds);

            // 查询并加行锁（需要确保该资源记录已存在）
            String sql = "SELECT resource FROM lock_resource WHERE resource = ? FOR UPDATE";
            PreparedStatement ps = conn.prepareStatement(sql);
            ps.setString(1, resource);
            ResultSet rs = ps.executeQuery();

            if (!rs.next()) {
                // 记录不存在，尝试插入
                try {
                    conn.createStatement().execute(
                            "INSERT INTO lock_resource (resource) VALUES ('" + resource + "')");
                    // 重新加锁
                    ps.setString(1, resource);
                    rs = ps.executeQuery();
                } catch (SQLException e) {
                    // 并发插入冲突，重试
                    conn.rollback();
                    return null;
                }
            }
            // 返回连接，调用方需要保持连接不断开
            // 释放锁时调用 conn.commit() 或 conn.close()
            return conn;
        } catch (SQLException e) {
            conn.rollback();
            conn.close();
            throw e;
        }
    }

    /**
     * 释放锁（提交事务即释放行锁）
     */
    public void unlock(Connection conn) {
        if (conn != null) {
            try {
                conn.commit();
            } catch (SQLException e) {
                try {
                    conn.rollback();
                } catch (SQLException ignored) {
                }
            } finally {
                try {
                    conn.close();
                } catch (SQLException ignored) {
                }
            }
        }
    }
}
```

#### 3.1.3 数据库锁的局限性

**性能瓶颈：**
- 每次加锁/解锁都需要访问数据库，网络 I/O 开销大
- 数据库连接数有限，高并发时连接池可能耗尽
- `FOR UPDATE` 会持有行锁，可能阻塞其他正常的业务查询

**无自动续期：**
- 唯一索引方案依赖过期时间，如果业务执行时间超过过期时间，锁会被其他实例获取
- `FOR UPDATE` 方案依赖事务，事务超时或连接断开才能释放锁，不够灵活

**无阻塞唤醒机制：**
- 获取锁失败后只能轮询重试，无法像 `synchronized` 那样自动等待唤醒
- 轮询频率高则浪费数据库资源，轮询频率低则响应延迟大

**适用场景：**
- 并发量不高（QPS < 1000）的后台任务调度
- 系统已部署数据库但未引入 Redis/ZK，不想增加额外组件
- 对锁的可靠性要求不高，能容忍偶发的锁失效

### 3.2 基于 Redis 的分布式锁

Redis 是实现分布式锁最常用的方案，其优势在于内存级的高性能和丰富的原子操作命令。本节将从最基础的实现逐步演进到生产级的完整方案。

#### 3.2.1 基础实现：SET key value NX EX

**核心命令解析：**

```
SET lock_key uuid_value NX EX 30
```

- `NX`（Not eXists）：只有 key 不存在时才设置成功，保证互斥性
- `EX 30`：设置 30 秒过期时间，防止死锁
- `NX` 和 `EX` 必须在同一个 `SET` 命令中（Redis 2.6.12+），保证加锁操作的原子性

**为什么 NX 和 EX 必须一起使用？**

如果分两步操作：

```
# 错误做法：先 SETNX，再 EXPIRE
SETNX lock_key uuid_value    # 步骤1：设置成功
EXPIRE lock_key 30           # 步骤2：设置过期时间
```

如果步骤1成功但步骤2执行前客户端崩溃，锁将永远不会过期，导致死锁。使用 `SET ... NX EX` 单条命令保证原子性，避免这个问题。

**为什么 value 必须使用唯一标识（UUID）？**

考虑以下场景：

1. 客户端 A 获取锁，TTL = 30s
2. 客户端 A 业务执行超过 30s，锁自动过期
3. 客户端 B 获取到锁
4. 客户端 A 业务执行完毕，执行 DEL lock_key
5. 客户端 B 的锁被客户端 A 误删

使用 UUID 作为 value，解锁时先校验 value 是否匹配，只有持有者才能删除锁。

**完整 Java 实现：**

```java
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.params.SetParams;

import java.util.Collections;
import java.util.UUID;

/**
 * Redis 分布式锁 - 基础实现
 */
public class RedisDistributedLock {

    private final JedisPool jedisPool;
    private static final String LOCK_PREFIX = "lock:";
    private static final String LOCK_OK = "OK";

    /**
     * Lua 脚本：校验 value 并删除（原子操作）
     * KEYS[1] = lock key
     * ARGV[1] = expected value (UUID)
     *
     * 如果 key 的值等于 ARGV[1]，则删除 key 并返回 1；否则返回 0
     */
    private static final String UNLOCK_LUA_SCRIPT =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('DEL', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";

    /**
     * 加锁
     *
     * @param resource 资源名称
     * @param expireSeconds 锁过期时间（秒）
     * @return 锁标识（UUID），用于解锁时校验；返回 null 表示加锁失败
     */
    public String tryLock(String resource, int expireSeconds) {
        String lockKey = LOCK_PREFIX + resource;
        String lockValue = UUID.randomUUID().toString() + ":" + Thread.currentThread().getId();

        try (Jedis jedis = jedisPool.getResource()) {
            SetParams params = SetParams.setParams().nx().ex(expireSeconds);
            String result = jedis.set(lockKey, lockValue, params);
            if (LOCK_OK.equals(result)) {
                return lockValue;
            }
            return null;
        }
    }

    /**
     * 解锁（使用 Lua 脚本保证原子性）
     *
     * @param resource 资源名称
     * @param lockValue 加锁时返回的锁标识
     * @return 是否解锁成功
     */
    public boolean unlock(String resource, String lockValue) {
        String lockKey = LOCK_PREFIX + resource;

        try (Jedis jedis = jedisPool.getResource()) {
            Object result = jedis.eval(
                    UNLOCK_LUA_SCRIPT,
                    Collections.singletonList(lockKey),
                    Collections.singletonList(lockValue)
            );
            return result != null && ((Long) result) == 1L;
        }
    }

    /**
     * 带重试的加锁
     *
     * @param resource 资源名称
     * @param expireSeconds 锁过期时间（秒）
     * @param timeoutMillis 总超时时间（毫秒）
     * @param retryIntervalMillis 重试间隔（毫秒）
     * @return 锁标识，null 表示超时未获取到锁
     */
    public String tryLockWithTimeout(String resource, int expireSeconds,
                                     long timeoutMillis, long retryIntervalMillis) {
        long deadline = System.currentTimeMillis() + timeoutMillis;
        String lockValue = null;

        while (System.currentTimeMillis() < deadline) {
            lockValue = tryLock(resource, expireSeconds);
            if (lockValue != null) {
                return lockValue;
            }
            try {
                Thread.sleep(retryIntervalMillis);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return null;
            }
        }
        return null;
    }

    public RedisDistributedLock(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }
}
```

**使用示例：**

```java
public class OrderService {

    private final InventoryService inventoryService;

        String resource = "inventory:" + productId;
        String lockValue = null;
```

#### 3.2.2 锁超时与看门狗（Watchdog）机制

**问题分析：**

基础实现设置了固定的过期时间（如 30 秒），但业务执行时间无法精确预估：

- 如果 TTL 太短，业务还没执行完锁就过期了，其他实例可能获取到锁，导致并发问题
- 如果 TTL 太长，持有锁的实例崩溃后，其他实例需要等待很长时间才能获取锁

**看门狗机制原理：**

看门狗（Watchdog）是一种自动续期机制。当客户端获取锁后，启动一个后台守护线程，定期（通常为 TTL 的 1/3）延长锁的过期时间。当业务执行完毕后，停止续期线程并释放锁。

```
时间线：
0s   ─── 获取锁，TTL=30s，启动看门狗
10s  ─── 看门狗续期，TTL 重置为 30s
20s  ─── 看门狗续期，TTL 重置为 30s
25s  ─── 业务执行完毕，停止看门狗，释放锁

如果客户端崩溃：
0s   ─── 获取锁，TTL=30s，启动看门狗
10s  ─── 看门狗续期
20s  ─── 看门狗续期
25s  ─── 客户端崩溃，看门狗停止
50s  ─── 锁自动过期（最后一次续期后 30s）
```

**Redisson 的实现原理：**

Redisson 的看门狗机制基于 Netty 的 HashedWheelTimer（时间轮）实现定时任务。默认情况下：

- 锁的初始 TTL 为 30 秒（`lockWatchdogTimeout` 参数，默认 30000ms）
- 看门狗每 10 秒（TTL/3）执行一次续期
- 续期操作通过 Lua 脚本保证原子性：检查 key 存在且 value 匹配后，重置 TTL
- 如果客户端正常关闭或崩溃，定时任务不再执行，锁在 TTL 后自动过期

**看门狗续期 Lua 脚本：**

```lua
-- Redisson 的 renewal Lua 脚本核心逻辑
-- KEYS[1] = lock key
-- ARGV[1] = expected value (UUID:threadId)
-- ARGV[2] = new expire time (milliseconds)

if redis.call('EXISTS', KEYS[1]) == 1 then
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('PEXPIRE', KEYS[1], ARGV[2])
    end
end
return 0
```

**完整看门狗 Java 实现：**

```java
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.params.SetParams;

import java.util.Collections;
import java.util.UUID;
import java.util.concurrent.*;

/**
 * Redis 分布式锁 - 带看门狗自动续期
 */
public class RedisLockWithWatchdog {

    private final JedisPool jedisPool;
    private static final String LOCK_PREFIX = "lock:";
    private static final long DEFAULT_TTL = 30_000L; // 30秒
    private static final long RENEW_INTERVAL = DEFAULT_TTL / 3; // 10秒续期一次

    /**
     * 续期 Lua 脚本
     * KEYS[1] = lock key
     * ARGV[1] = expected value
     * ARGV[2] = expire time in milliseconds
     */
    private static final String RENEW_LUA_SCRIPT =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "else " +
            "    return 0 " +
            "end";

    /**
     * 解锁 Lua 脚本
     */
    private static final String UNLOCK_LUA_SCRIPT =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('DEL', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";

    /**
     * 存储每个锁的续期任务，key = lockKey，value = ScheduledFuture
     */
    private final ConcurrentHashMap<String, ScheduledFuture<?>> renewalTasks = new ConcurrentHashMap<>();
    private final ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(
            Runtime.getRuntime().availableProcessors(),
            new ThreadFactory() {
                private final AtomicInteger counter = new AtomicInteger(0);
                @Override
                public Thread newThread(Runnable r) {
                    Thread t = new Thread(r, "lock-watchdog-" + counter.getAndIncrement());
                    t.setDaemon(true); // 守护线程，JVM退出时自动结束
                    return t;
                }
            });

    public RedisLockWithWatchdog(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * 获取锁（带看门狗自动续期）
     * 不指定 TTL，使用默认 30s，看门狗每 10s 续期一次
     *
     * @param resource 资源名称
     * @return LockContext 对象，null 表示获取失败
     */
    public LockContext tryLock(String resource) {
        return tryLock(resource, DEFAULT_TTL / 1000, true);
    }

    /**
     * 获取锁
     *
     * @param resource 资源名称
     * @param expireSeconds 锁过期时间（秒）
     * @param enableWatchdog 是否启用看门狗
     * @return LockContext 对象，null 表示获取失败
     */
    public LockContext tryLock(String resource, int expireSeconds, boolean enableWatchdog) {
        String lockKey = LOCK_PREFIX + resource;
        String lockValue = UUID.randomUUID().toString() + ":" + Thread.currentThread().getId();

        try (Jedis jedis = jedisPool.getResource()) {
            SetParams params = SetParams.setParams().nx().ex(expireSeconds);
            String result = jedis.set(lockKey, lockValue, params);
            if ("OK".equals(result)) {
                LockContext context = new LockContext(lockKey, lockValue);

                if (enableWatchdog) {
                    startWatchdog(context, expireSeconds * 1000L);
                }
                return context;
            }
        }
        return null;
    }

    /**
     * 启动看门狗
     */
    private void startWatchdog(LockContext context, long ttlMillis) {
        long renewInterval = ttlMillis / 3;

        ScheduledFuture<?> future = scheduler.scheduleAtFixedRate(() -> {
            try (Jedis jedis = jedisPool.getResource()) {
                Object result = jedis.eval(
                        RENEW_LUA_SCRIPT,
                        Collections.singletonList(context.lockKey),
                        Arrays.asList(context.lockValue, String.valueOf(ttlMillis))
                );
                if (result == null || ((Long) result) == 0L) {
                    // 续期失败（锁已被删除或被其他实例获取），停止续期
                    ScheduledFuture<?> task = renewalTasks.remove(context.lockKey);
                    if (task != null) {
                        task.cancel(false);
                    }
                }
            } catch (Exception e) {
                // Redis 连接异常，停止续期
                ScheduledFuture<?> task = renewalTasks.remove(context.lockKey);
                if (task != null) {
                    task.cancel(false);
                }
            }
        }, renewInterval, renewInterval, TimeUnit.MILLISECONDS);

        renewalTasks.put(context.lockKey, future);
    }

    /**
     * 释放锁
     */
    public boolean unlock(LockContext context) {
        // 先停止看门狗
        ScheduledFuture<?> task = renewalTasks.remove(context.lockKey);
        if (task != null) {
            task.cancel(false);
        }

        try (Jedis jedis = jedisPool.getResource()) {
            Object result = jedis.eval(
                    UNLOCK_LUA_SCRIPT,
                    Collections.singletonList(context.lockKey),
                    Collections.singletonList(context.lockValue)
            );
            return result != null && ((Long) result) == 1L;
        }
    }

    /**
     * 锁上下文，持有锁的关键信息
     */
    public static class LockContext {
        private final String lockKey;
        private final String lockValue;

        public LockContext(String lockKey, String lockValue) {
            this.lockKey = lockKey;
            this.lockValue = lockValue;
        }

        public String getLockKey() { return lockKey; }
        public String getLockValue() { return lockValue; }
    }
}
```

**看门狗使用示例：**

```java
public class ScheduledTaskService {

    private final RedisLockWithWatchdog lock;

    public void executeDailyReport() {
        RedisLockWithWatchdog.LockContext ctx = null;
        try {
            // 获取锁，启用看门狗自动续期
            ctx = lock.tryLock("task:daily-report");

            if (ctx == null) {
                // 其他实例正在执行，跳过
                return;
            }

            // 执行可能耗时的报表生成任务
            // 看门狗会自动续期，不用担心锁过期
            generateReport();

        } catch (Exception e) {
            // 异常处理
            throw new RuntimeException("报表生成失败", e);
        } finally {
            if (ctx != null) {
                lock.unlock(ctx);
            }
        }
    }
}
```

**看门狗的注意事项：**

1. 看门狗线程应设为守护线程，避免阻止 JVM 正常退出
2. 续期操作失败时应停止看门狗，避免无意义的重试
3. 看门狗不是万能的：如果业务线程无限阻塞（如死循环、无限等待），锁会被无限续期，需要结合业务超时机制
4. 线程池大小应根据并发锁数量合理设置
5. 如果显式指定了 TTL（`leaseTime`），Redisson 默认不会启动看门狗，需要业务自行确保在 TTL 内完成

#### 3.2.3 可重入锁

**需求分析：**

可重入锁允许同一个线程多次获取同一把锁，在递归调用或嵌套调用场景下避免自我死锁。例如：

```java
public void processOrder(String orderId) {
    lock.lock();  // 第一次获取锁
    try {
        // ... 处理订单
        updateOrderStatus(orderId);  // 内部也需要获取锁
    } finally {
        lock.unlock();  // 第一次释放锁
    }
}

public void updateOrderStatus(String orderId) {
    lock.lock();  // 第二次获取锁（重入）
    try {
        // ... 更新状态
    } finally {
        lock.unlock();  // 第二次释放锁
    }
}
```

如果锁不可重入，`updateOrderStatus` 中的 `lock.lock()` 会阻塞，因为锁已被 `processOrder` 持有，导致死锁。

**实现方案：使用 Redis Hash 结构**

普通锁使用 String 结构存储，只有一个 value。可重入锁需要记录"谁持有锁"和"重入了几次"，使用 Hash 结构：

```
lock_key: {
    "uuid:threadId": 2    # 持有者标识 -> 重入次数
}
```

- 加锁：`HINCRBY lock_key uuid:threadId 1`，然后设置 TTL
- 解锁：`HINCRBY lock_key uuid:threadId -1`，如果值为 0 则 `DEL lock_key`

**加锁 Lua 脚本：**

```lua
-- 可重入锁加锁 Lua 脚本
-- KEYS[1] = lock key
-- ARGV[1] = lock value (uuid:threadId)
-- ARGV[2] = expire time (milliseconds)
--
-- 逻辑：
-- 1. 如果锁不存在，设置 Hash 并设置过期时间
-- 2. 如果锁存在且持有者是当前线程，重入次数 +1
-- 3. 否则返回 0（加锁失败）

if redis.call('EXISTS', KEYS[1]) == 0 then
    -- 锁不存在，首次加锁
    redis.call('HSET', KEYS[1], ARGV[1], 1)
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
end

if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then
    -- 锁存在且持有者是当前线程，重入次数 +1
    redis.call('HINCRBY', KEYS[1], ARGV[1], 1)
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
end

-- 锁被其他线程持有，加锁失败
return 0
```

**解锁 Lua 脚本：**

```lua
-- 可重入锁解锁 Lua 脚本
-- KEYS[1] = lock key
-- ARGV[1] = lock value (uuid:threadId)
-- ARGV[2] = expire time (milliseconds) -- 用于续期，防止其他线程的锁被误删
--
-- 逻辑：
-- 1. 如果锁不存在或持有者不是当前线程，返回 0（无需解锁）
-- 2. 重入次数 -1
-- 3. 如果重入次数 > 0，刷新过期时间
-- 4. 如果重入次数 = 0，删除锁

if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 0 then
    return 0
end

local count = redis.call('HINCRBY', KEYS[1], ARGV[1], -1)

if count > 0 then
    -- 还有重入次数，刷新过期时间
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
else
    -- 重入次数归零，删除锁
    redis.call('DEL', KEYS[1])
    return 1
end
```

**完整可重入锁 Java 实现：**

```java
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.params.SetParams;

import java.util.Arrays;
import java.util.Collections;
import java.util.UUID;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * Redis 可重入分布式锁
 */
public class ReentrantRedisLock {

    private final JedisPool jedisPool;
    private static final String LOCK_PREFIX = "reentrant_lock:";
    private static final long DEFAULT_TTL_MS = 30_000L;

    /**
     * 加锁 Lua 脚本
     */
    private static final String LOCK_LUA =
            "if redis.call('EXISTS', KEYS[1]) == 0 then " +
            "    redis.call('HSET', KEYS[1], ARGV[1], 1) " +
            "    redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "    return 1 " +
            "end " +
            "if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then " +
            "    redis.call('HINCRBY', KEYS[1], ARGV[1], 1) " +
            "    redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "    return 1 " +
            "end " +
            "return 0";

    /**
     * 解锁 Lua 脚本
     */
    private static final String UNLOCK_LUA =
            "if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 0 then " +
            "    return 0 " +
            "end " +
            "local count = redis.call('HINCRBY', KEYS[1], ARGV[1], -1) " +
            "if count > 0 then " +
            "    redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "    return 1 " +
            "else " +
            "    redis.call('DEL', KEYS[1]) " +
            "    return 1 " +
            "end";

    /**
     * 续期 Lua 脚本
     */
    private static final String RENEW_LUA =
            "if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then " +
            "    return redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "else " +
            "    return 0 " +
            "end";

    /**
     * ThreadLocal 存储每个线程的锁上下文
     */
    private final ThreadLocal<LockState> lockStateHolder = new ThreadLocal<>();

    private final ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(
            Runtime.getRuntime().availableProcessors(),
            r -> {
                Thread t = new Thread(r, "reentrant-lock-watchdog");
                t.setDaemon(true);
                return t;
            });

    private final ConcurrentHashMap<String, ScheduledFuture<?>> watchdogTasks = new ConcurrentHashMap<>();

    public ReentrantRedisLock(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * 生成当前线程的锁标识
     */
    private String getLockValue() {
        return UUID.randomUUID() + ":" + Thread.currentThread().getId();
    }

    /**
     * 获取锁（可重入）
     */
    public boolean lock(String resource) {
        return lock(resource, DEFAULT_TTL_MS, true);
    }

    public boolean lock(String resource, long ttlMillis, boolean enableWatchdog) {
        String lockKey = LOCK_PREFIX + resource;
        String lockValue = getLockValue();

        // 检查当前线程是否已持有此锁（重入）
        LockState state = lockStateHolder.get();
        if (state != null && state.lockKey.equals(lockKey)) {
            // 重入：直接调用 Lua 脚本增加重入计数
            try (Jedis jedis = jedisPool.getResource()) {
                Object result = jedis.eval(LOCK_LUA,
                        Collections.singletonList(lockKey),
                        Arrays.asList(lockValue, String.valueOf(ttlMillis)));
                if (result != null && ((Long) result) == 1L) {
                    state.reentrantCount.incrementAndGet();
                    return true;
                }
            }
            return false;
        }

        // 首次加锁
        try (Jedis jedis = jedisPool.getResource()) {
            Object result = jedis.eval(LOCK_LUA,
                    Collections.singletonList(lockKey),
                    Arrays.asList(lockValue, String.valueOf(ttlMillis)));

            if (result != null && ((Long) result) == 1L) {
                LockState newState = new LockState(lockKey, lockValue);
                lockStateHolder.set(newState);

                if (enableWatchdog) {
                    startWatchdog(lockKey, lockValue, ttlMillis);
                }
                return true;
            }
        }
        return false;
    }

    /**
     * 尝试获取锁（带超时）
     */
    public boolean tryLock(String resource, long timeoutMillis) throws InterruptedException {
        long deadline = System.currentTimeMillis() + timeoutMillis;
        while (System.currentTimeMillis() < deadline) {
            if (lock(resource)) {
                return true;
            }
            Thread.sleep(50);
        }
        return false;
    }

    /**
     * 释放锁
     */
    public boolean unlock(String resource) {
        String lockKey = LOCK_PREFIX + resource;
        LockState state = lockStateHolder.get();
        if (state == null || !state.lockKey.equals(lockKey)) {
            return false;
        }

        // 重入次数递减
        int count = state.reentrantCount.decrementAndGet();
        if (count > 0) {
            // 还有重入层级，只减少 Redis 中的计数
            try (Jedis jedis = jedisPool.getResource()) {
                jedis.eval(UNLOCK_LUA,
                        Collections.singletonList(lockKey),
                        Arrays.asList(state.lockValue, String.valueOf(DEFAULT_TTL_MS)));
            }
            return true;
        }

        // 所有重入层级都释放，删除锁并清除上下文
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.eval(UNLOCK_LUA,
                    Collections.singletonList(lockKey),
                    Arrays.asList(state.lockValue, String.valueOf(DEFAULT_TTL_MS)));
        }

        // 停止看门狗
        ScheduledFuture<?> task = watchdogTasks.remove(lockKey);
        if (task != null) {
            task.cancel(false);
        }

        lockStateHolder.remove();
        return true;
    }

    private void startWatchdog(String lockKey, String lockValue, long ttlMillis) {
        long interval = ttlMillis / 3;
        ScheduledFuture<?> future = scheduler.scheduleAtFixedRate(() -> {
            try (Jedis jedis = jedisPool.getResource()) {
                Object result = jedis.eval(RENEW_LUA,
                        Collections.singletonList(lockKey),
                        Arrays.asList(lockValue, String.valueOf(ttlMillis)));
                if (result == null || ((Long) result) == 0L) {
                    ScheduledFuture<?> task = watchdogTasks.remove(lockKey);
                    if (task != null) task.cancel(false);
                }
            } catch (Exception e) {
                ScheduledFuture<?> task = watchdogTasks.remove(lockKey);
                if (task != null) task.cancel(false);
            }
        }, interval, interval, TimeUnit.MILLISECONDS);
        watchdogTasks.put(lockKey, future);
    }

    /**
     * 锁状态
     */
    private static class LockState {
        final String lockKey;
        final String lockValue;
        final AtomicInteger reentrantCount = new AtomicInteger(1);

        LockState(String lockKey, String lockValue) {
            this.lockKey = lockKey;
            this.lockValue = lockValue;
        }
    }
}
```

#### 3.2.4 公平锁

**需求分析：**

前面实现的锁都是非公平锁，获取锁的顺序与请求顺序无关。在极端情况下，某些线程可能长时间获取不到锁（"饥饿"问题）。公平锁保证先请求的线程先获取锁，按 FIFO 顺序排队。

**实现思路：使用 Redis List 作为等待队列**

1. 每个线程获取锁时生成一个递增的序号
2. 如果锁可用且当前线程是队列头部，则获取锁
3. 否则将线程加入等待队列
4. 释放锁时通知队列头部线程

**公平锁 Lua 脚本（加锁）：**

```lua
-- 公平锁加锁 Lua 脚本
-- KEYS[1] = lock key (Hash, 存储持有者信息)
-- KEYS[2] = queue key (List, 等待队列)
-- ARGV[1] = thread identifier
-- ARGV[2] = expire time (milliseconds)
--
-- 逻辑：
-- 1. 如果锁不存在且队列为空，直接获取锁
-- 2. 如果锁不存在且队列头部是当前线程，获取锁
-- 3. 如果锁已被当前线程持有，重入
-- 4. 否则加入队列

-- 检查锁是否存在
if redis.call('EXISTS', KEYS[1]) == 0 then
    -- 锁不存在
    if redis.call('LLEN', KEYS[2]) == 0 then
        -- 队列为空，直接加锁
        redis.call('HSET', KEYS[1], ARGV[1], 1)
        redis.call('PEXPIRE', KEYS[1], ARGV[2])
        return 1
    end
    -- 队列不为空，检查队列头部
    local head = redis.call('LINDEX', KEYS[2], 0)
    if head == ARGV[1] then
        -- 当前线程在队列头部，出队并加锁
        redis.call('LPOP', KEYS[2])
        redis.call('HSET', KEYS[1], ARGV[1], 1)
        redis.call('PEXPIRE', KEYS[1], ARGV[2])
        return 1
    end
    -- 不在队列头部，加入队列
    redis.call('RPUSH', KEYS[2], ARGV[1])
    return 0
end

-- 锁存在，检查是否是重入
if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then
    redis.call('HINCRBY', KEYS[1], ARGV[1], 1)
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
end

-- 锁被其他线程持有，加入等待队列
redis.call('RPUSH', KEYS[2], ARGV[1])
return 0
```

**公平锁 Lua 脚本（解锁）：**

```lua
-- 公平锁解锁 Lua 脚本
-- KEYS[1] = lock key
-- KEYS[2] = queue key
-- ARGV[1] = thread identifier
-- ARGV[2] = expire time (milliseconds)

if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 0 then
    return 0
end

local count = redis.call('HINCRBY', KEYS[1], ARGV[1], -1)
if count > 0 then
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
end

-- 重入次数归零，删除锁
redis.call('DEL', KEYS[1])

-- 发布通知（队列头部线程可以尝试获取锁）
redis.call('PUBLISH', KEYS[1] .. ':channel', 'unlocked')
return 1
```

```java
import redis.clients.jedis.JedisPubSub;

import java.util.Arrays;

/**
 * Redis 公平锁（简化实现）
 * 完整实现可参考 Redisson 的 RedissonFairLock

public class FairRedisLock {

    private final JedisPool jedisPool;
    private static final String LOCK_PREFIX = "fair_lock:";
    private static final String QUEUE_PREFIX = "fair_queue:";
    private static final long DEFAULT_TTL_MS = 30_000L;

    private static final String LOCK_LUA =
            "if redis.call('EXISTS', KEYS[1]) == 0 then " +
            "    if redis.call('LLEN', KEYS[2]) == 0 then " +
            "        redis.call('HSET', KEYS[1], ARGV[1], 1) " +
            "        redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "        return 1 " +
            "    end " +
            "    local head = redis.call('LINDEX', KEYS[2], 0) " +
            "    if head == ARGV[1] then " +
            "        redis.call('LPOP', KEYS[2]) " +
            "        redis.call('HSET', KEYS[1], ARGV[1], 1) " +
            "        redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "        return 1 " +
            "    end " +
            "    redis.call('RPUSH', KEYS[2], ARGV[1]) " +
            "    return 0 " +
            "end " +
            "if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then " +
            "    redis.call('HINCRBY', KEYS[1], ARGV[1], 1) " +
            "    redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "    return 1 " +
            "end " +
            "redis.call('RPUSH', KEYS[2], ARGV[1]) " +
            "return 0";

    private static final String UNLOCK_LUA =
            "if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 0 then " +
            "    return 0 " +
            "end " +
            "local count = redis.call('HINCRBY', KEYS[1], ARGV[1], -1) " +
            "if count > 0 then " +
            "    redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "    return 1 " +
            "end " +
            "redis.call('DEL', KEYS[1]) " +
            "redis.call('PUBLISH', KEYS[1] .. ':channel', 'unlocked') " +
            "return 1";

    public FairRedisLock(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * 获取公平锁（阻塞式）
     */
    public boolean lock(String resource, long timeoutMillis) throws InterruptedException {
        String lockKey = LOCK_PREFIX + resource;
        String queueKey = QUEUE_PREFIX + resource;
        String threadId = UUID.randomUUID() + ":" + Thread.currentThread().getId();
        String channel = lockKey + ":channel";

        long deadline = System.currentTimeMillis() + timeoutMillis;

        // 订阅解锁通知频道
        CountDownLatch latch = new CountDownLatch(1);
        Thread subThread = new Thread(() -> {
            try (Jedis jedis = jedisPool.getResource()) {
                jedis.subscribe(new JedisPubSub() {
                    @Override
                    public void onMessage(String channel, String message) {
                        latch.countDown();
                    }
                }, channel);
            }
        }, "fair-lock-subscriber");
        subThread.setDaemon(true);
        subThread.start();

        while (System.currentTimeMillis() < deadline) {
            try (Jedis jedis = jedisPool.getResource()) {
                Object result = jedis.eval(LOCK_LUA,
                        Arrays.asList(lockKey, queueKey),
                        Arrays.asList(threadId, String.valueOf(DEFAULT_TTL_MS)));

                if (result != null && ((Long) result) == 1L) {
                    return true;
                }

                // 等待解锁通知或超时
                if (latch.await(100, TimeUnit.MILLISECONDS)) {
                    // 收到通知，重置 latch 继续尝试
                    // 实际实现中需要重新订阅
                }
            }
        }

        // 超时，从队列中移除自己
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.lrem(queueKey, 0, threadId);
        }
        return false;
    }

    /**
     * 释放公平锁
     */
    public boolean unlock(String resource, String threadId) {
        String lockKey = LOCK_PREFIX + resource;
        String queueKey = QUEUE_PREFIX + resource;

        try (Jedis jedis = jedisPool.getResource()) {
            Object result = jedis.eval(UNLOCK_LUA,
                    Arrays.asList(lockKey, queueKey),
                    Arrays.asList(threadId, String.valueOf(DEFAULT_TTL_MS)));
            return result != null && ((Long) result) == 1L;
        }
    }
}
```

#### 3.2.5 RedLock 算法

**问题背景：Redis 主从切换导致的锁丢失**

Redis 通常以主从模式部署，主节点负责读写，从节点负责备份。主从之间的复制是异步的：

1. 客户端在主节点上获取锁（`SET lock NX EX 30`）
2. 主节点将锁写入内存，返回成功
3. 主节点在将复制命令同步给从节点之前发生宕机
4. 哨兵（Sentinel）将从节点提升为主节点
5. 新主节点上没有锁数据，其他客户端可以再次获取同一把锁
6. 此时有两个客户端同时持有锁

**RedLock 算法设计**

RedLock 是 Redis 作者 antirez 提出的多节点 RedLock 算法，不依赖主从复制，而是使用多个独立的 Redis 实例来保证锁的可靠性。

**核心思想：**

假设有 N 个（通常为 5 个）完全独立的 Redis 实例（不构成主从集群），客户端需要向多数派（N/2 + 1，即至少 3 个）实例成功获取锁，才算真正获取到分布式锁。

**算法步骤详解：**

```
步骤1：记录当前时间 T1（毫秒）

步骤2：依次向所有 N 个 Redis 实例发送加锁请求
   - 使用相同的 key 和 value
   - 设置较短的网络超时（如 50ms），避免某个实例宕机阻塞
   - 每个实例使用 SET key value NX EX TTL

步骤3：记录当前时间 T2，计算获取锁消耗的时间 = T2 - T1

步骤4：判断是否获取锁成功
   - 条件1：在 N/2 + 1 个（多数派）实例上成功获取锁
   - 条件2：获取锁消耗的时间 < 锁的 TTL
   - 两个条件同时满足才算成功

步骤5：锁的有效时间 = TTL - (T2 - T1)
   - 需要扣除获取锁过程中消耗的时间

步骤6：如果获取锁失败
   - 向所有 Redis 实例发送解锁请求（包括未成功的）
   - 防止残留锁数据影响后续请求
```

**时间线示例（5 个 Redis 实例，TTL = 10s）：**

```
T1 = 0ms
  ├─ 请求实例1 → 成功 (10ms)
  ├─ 请求实例2 → 成功 (15ms)
  ├─ 请求实例3 → 成功 (20ms)
  ├─ 请求实例4 → 超时 (50ms)
  ├─ 请求实例5 → 成功 (30ms)
T2 = 125ms

判断：
  成功实例数 = 4（≥ 3，多数派满足） ✓
  消耗时间 = 125ms < 10s ✓
  锁获取成功，有效时间 = 10s - 0.125s = 9.875s
```

**RedLock 完整 Java 实现：**

```java
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.params.SetParams;

import java.util.*;
import java.util.concurrent.*;

/**
 * RedLock 算法实现
 * 基于多个独立 Redis 实例的分布式锁
 */
public class RedLock {

    private final List<JedisPool> jedisPools;
    private final int quorum; // 多数派数量

    /**
     * 解锁 Lua 脚本
     */
    private static final String UNLOCK_LUA =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('DEL', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";

    /**
     * @param jedisPools 多个独立的 Redis 连接池（非主从关系）
     */
    public RedLock(List<JedisPool> jedisPools) {
        if (jedisPools == null || jedisPools.isEmpty()) {
            throw new IllegalArgumentException("Redis 实例列表不能为空");
        }
        this.jedisPools = new ArrayList<>(jedisPools);
        this.quorum = jedisPools.size() / 2 + 1;
    }

    /**
     * 尝试获取 RedLock
     *
     * @param resource 资源名称
     * @param ttlMillis 锁有效时间（毫秒）
     * @return RedLock 实例，null 表示获取失败
     */
    public RedLockInstance tryLock(String resource, long ttlMillis) {
        String lockKey = "redlock:" + resource;
        String lockValue = UUID.randomUUID().toString();

        int successCount = 0;
        long startTime = System.currentTimeMillis();

        // 依次向所有 Redis 实例请求加锁
        for (JedisPool pool : jedisPools) {
            try {
                try (Jedis jedis = pool.getResource()) {
                    // 设置较短的网络超时
                    jedis.getClient().setSoTimeout(50);

                    SetParams params = SetParams.setParams().nx().px(ttlMillis);
                    String result = jedis.set(lockKey, lockValue, params);

                    if ("OK".equals(result)) {
                        successCount++;
                    }
                }
            } catch (Exception e) {
                // 单个实例异常不影响其他实例
            }
        }

        long endTime = System.currentTimeMillis();
        long elapsed = endTime - startTime;

        // 判断是否获取锁成功
        if (successCount >= quorum && elapsed < ttlMillis) {
            // 成功，计算实际有效时间
            long validityTime = ttlMillis - elapsed;
            return new RedLockInstance(lockKey, lockValue, validityTime);
        } else {
            // 失败，向所有实例发送解锁请求（包括成功的）
            unlockInternal(lockKey, lockValue);
            return null;
        }
    }

    /**
     * 带重试和超时的加锁
     */
    public RedLockInstance lock(String resource, long ttlMillis, long timeoutMillis)
            throws InterruptedException {
        long deadline = System.currentTimeMillis() + timeoutMillis;
        long retryDelay = 100; // 重试间隔

        while (System.currentTimeMillis() < deadline) {
            RedLockInstance instance = tryLock(resource, ttlMillis);
            if (instance != null) {
                return instance;
            }
            Thread.sleep(retryDelay);
        }
        return null;
    }

    /**
     * 释放锁
     */
    public void unlock(RedLockInstance instance) {
        unlockInternal(instance.lockKey, instance.lockValue);
    }

    /**
     * 向所有 Redis 实例发送解锁请求
     */
    private void unlockInternal(String lockKey, String lockValue) {
        for (JedisPool pool : jedisPools) {
            try {
                try (Jedis jedis = pool.getResource()) {
                    jedis.eval(UNLOCK_LUA,
                            Collections.singletonList(lockKey),
                            Collections.singletonList(lockValue));
                }
            } catch (Exception e) {
                // 忽略解锁异常
            }
        }
    }

    /**
     * RedLock 实例
     */
    public static class RedLockInstance {
        private final String lockKey;
        private final String lockValue;
        private final long validityTime; // 实际有效时间（毫秒）

        public RedLockInstance(String lockKey, String lockValue, long validityTime) {
            this.lockKey = lockKey;
            this.lockValue = lockValue;
            this.validityTime = validityTime;
        }

        public String getLockKey() { return lockKey; }
        public String getLockValue() { return lockValue; }
        public long getValidityTime() { return validityTime; }
    }
}
```

**RedLock 的争议：Martin Kleppmann 的批评**

Martin Kleppmann（《Designing Data-Intensive Applications》作者）对 RedLock 算法提出了严厉批评，主要集中在以下方面：

**争议一：时钟依赖问题**

RedLock 依赖各机器的系统时钟来判断锁的有效时间。如果某台机器的时钟发生跳跃（如 NTP 同步、虚拟机迁移），可能导致锁的有效时间计算错误：

```
场景：客户端 A 在实例 1-3 获取锁成功，TTL=10s
  1. 客户端 A 获取锁后，其所在机器的时钟被向前调整了 5s（NTP同步）
  2. 客户端 A 认为 TTL 还有 9s，但实际只过了 4s
  3. 同时，其他客户端 B 在实例 4-5 上获取锁（实例1-3的锁因时钟跳跃提前过期）
  4. 两个客户端同时持有锁
```

antirez 的回应：Redis 实例不需要依赖客户端时钟，锁过期由 Redis 服务端的 TTL 控制。但客户端计算 validityTime 时确实依赖本地时钟。

**争议二：GC 暂停问题**

```
场景：
  1. 客户端 A 获取锁，TTL=10s
  2. 客户端 A 触发 Full GC，STW 持续 15s
  3. 锁已过期，客户端 B 获取到锁
  4. 客户端 A GC 结束，认为自己仍持有锁
  5. 两个客户端同时操作共享资源
```

**争议三：是否真的需要 RedLock？**

Kleppmann 认为：
- 如果对正确性要求极高，应该使用 ZooKeeper（基于共识算法，不依赖时钟）
- 如果能容忍偶尔的锁失效，普通 Redis 单实例锁 + 幂等设计就足够了
- RedLock 处于"既不够快，又不够正确"的尴尬位置

antirez 的反驳：
- RedLock 在实际场景中的可靠性远高于单实例 Redis 锁
- 时钟跳跃在实际生产环境中很少发生（可通过运维手段避免）
- GC 暂停问题是所有分布式锁都面临的，不仅限于 RedLock

**实践建议：**

| 场景 | 建议方案 |
|------|---------|
| 对正确性要求极高（金融） | ZooKeeper + Fencing Token |
| 高并发+可容忍偶发失效 | Redis 单实例/集群锁 + 幂等 |
| 介于两者之间 | RedLock + Fencing Token |
| 不想引入额外组件 | 数据库锁 + 幂等 |

### 3.3 基于 ZooKeeper 的分布式锁

ZooKeeper 是一个分布式的、开放源码的协调服务，基于 ZAB（ZooKeeper Atomic Broadcast）协议实现强一致性。其临时顺序节点和 Watcher 机制天然适合实现分布式锁。

#### 3.3.1 临时顺序节点实现

**核心原理：**

1. 每个客户端在指定的父节点下创建一个临时顺序节点（EPHEMERAL_SEQUENTIAL）
2. 临时节点在客户端会话断开时自动删除（防死锁）
3. 顺序节点会自动追加递增的序号后缀
4. 客户端检查自己创建的节点是否是父节点下序号最小的节点
5. 如果是最小的，获取锁成功
6. 如果不是，监听前一个节点（序号比自己小的最近一个节点）的删除事件
7. 前一个节点被删除时（持有者释放锁或会话超时），当前客户端被唤醒，重新检查

**为什么监听前一个节点而不是所有节点？**

如果所有等待者都监听最小节点（锁持有者的节点），当锁释放时，所有等待者同时被唤醒去竞争锁，产生"惊群效应"（Thundering Herd）。监听前一个节点形成一条等待链，每次只有一个客户端被唤醒，避免惊群。

**锁创建流程图：**

```
/locks/order_lock
├── lock_00000001   ← 客户端A（持有锁）
├── lock_00000002   ← 客户端B（监听 lock_00000001）
├── lock_00000003   ← 客户端C（监听 lock_00000002）
└── lock_00000004   ← 客户端D（监听 lock_00000003）

客户端A释放锁 → lock_00000001 被删除
→ 客户端B被唤醒 → 检查发现自己是新的最小节点 → 获取锁
→ 客户端C、D不受影响
```

**完整 Java 实现（使用原生 ZooKeeper API）：**

```java
import org.apache.zookeeper.*;
import org.apache.zookeeper.data.Stat;

import java.io.IOException;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

/**
 * 基于 ZooKeeper 的分布式锁（原生 API 实现）
 */
public class ZkDistributedLock implements Watcher {

    private final ZooKeeper zooKeeper;
    private final String lockPath;
    private final String lockPrefix;
    private String currentLockPath;
    private String previousLockPath;

    private final CountDownLatch connectedLatch = new CountDownLatch(1);
    private CountDownLatch lockLatch;

    /**
     * @param connectString ZK 集群地址，如 "host1:2181,host2:2181,host3:2181"
     * @param lockPath 锁路径，如 "/locks/order_lock"
     */
    public ZkDistributedLock(String connectString, String lockPath)
            throws IOException, InterruptedException, KeeperException {
        this.lockPath = lockPath;
        this.lockPrefix = "/lock_";

        // 创建 ZooKeeper 连接
        this.zooKeeper = new ZooKeeper(connectString, 30000, this);
        connectedLatch.await();

        // 确保锁的父节点存在（持久节点）
        ensurePathExists(lockPath);
    }

    @Override
    public void process(WatchedEvent event) {
        if (event.getState() == Event.KeeperState.SyncConnected) {
            connectedLatch.countDown();
        }

        // 前一个节点被删除，唤醒等待
        if (event.getType() == Event.EventType.NodeDeleted
                && event.getPath() != null
                && event.getPath().equals(previousLockPath)) {
            if (lockLatch != null) {
                lockLatch.countDown();
            }
        }
    }

    /**
     * 获取锁（阻塞式）
     */
    public void lock() throws KeeperException, InterruptedException {
        // 1. 创建临时顺序节点
        currentLockPath = zooKeeper.create(
                lockPath + lockPrefix,
                new byte[0],
                ZooDefs.Ids.OPEN_ACL_UNSAFE,
                CreateMode.EPHEMERAL_SEQUENTIAL
        );

        // 2. 尝试获取锁
        while (true) {
            List<String> children = zooKeeper.getChildren(lockPath, false);
            Collections.sort(children);

            // 当前节点是否是最小节点
            String currentNodeName = currentLockPath.substring(lockPath.length() + 1);
            int currentIndex = children.indexOf(currentNodeName);

            if (currentIndex == 0) {
                // 是最小节点，获取锁成功
                return;
            }

            // 3. 不是最小节点，监听前一个节点
            previousLockPath = lockPath + "/" + children.get(currentIndex - 1);

            // 检查前一个节点是否还存在（可能在我们获取子节点列表时已被删除）
            Stat stat = zooKeeper.exists(previousLockPath, true);
            if (stat == null) {
                // 前一个节点已删除，重新检查
                continue;
            }

            // 等待前一个节点被删除
            lockLatch = new CountDownLatch(1);
            lockLatch.await();
        }
    }

    /**
     * 尝试获取锁（带超时）
     */
    public boolean tryLock(long timeout, TimeUnit unit)
            throws KeeperException, InterruptedException {
        // 1. 创建临时顺序节点
        currentLockPath = zooKeeper.create(
                lockPath + lockPrefix,
                new byte[0],
                ZooDefs.Ids.OPEN_ACL_UNSAFE,
                CreateMode.EPHEMERAL_SEQUENTIAL
        );

        long deadline = System.nanoTime() + unit.toNanos(timeout);

        // 2. 尝试获取锁
        while (true) {
            List<String> children = zooKeeper.getChildren(lockPath, false);
            Collections.sort(children);

            String currentNodeName = currentLockPath.substring(lockPath.length() + 1);
            int currentIndex = children.indexOf(currentNodeName);

            if (currentIndex == 0) {
                return true;
            }

            previousLockPath = lockPath + "/" + children.get(currentIndex - 1);
            Stat stat = zooKeeper.exists(previousLockPath, true);
            if (stat == null) {
                continue;
            }

            long remaining = deadline - System.nanoTime();
            if (remaining <= 0) {
                // 超时，删除自己创建的节点
                zooKeeper.delete(currentLockPath, -1);
                currentLockPath = null;
                return false;
            }

            lockLatch = new CountDownLatch(1);
            if (!lockLatch.await(remaining, TimeUnit.NANOSECONDS)) {
                zooKeeper.delete(currentLockPath, -1);
                currentLockPath = null;
                return false;
            }
        }
    }

    /**
     * 释放锁
     */
    public void unlock() {
        if (currentLockPath != null) {
            try {
                zooKeeper.delete(currentLockPath, -1);
            } catch (Exception e) {
                // 节点可能已被删除（会话超时）
            } finally {
                currentLockPath = null;
            }
        }
    }

    /**
     * 确保路径存在
     */
    private void ensurePathExists(String path) throws KeeperException, InterruptedException {
        if (zooKeeper.exists(path, false) == null) {
            try {
                zooKeeper.create(path, new byte[0],
                        ZooDefs.Ids.OPEN_ACL_UNSAFE, CreateMode.PERSISTENT);
            } catch (KeeperException.NodeExistsException e) {
                // 并发创建，忽略
            }
        }
    }

    /**
     * 关闭 ZooKeeper 连接
     */
    public void close() {
        try {
            zooKeeper.close();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

#### 3.3.2 Watcher 机制详解

**Watcher 的工作原理：**

ZooKeeper 的 Watcher 是一次性触发的客户端回调机制。客户端在读取节点数据或子节点列表时可以注册 Watcher，当被监听的节点发生变化时，ZooKeeper 服务端会向客户端发送通知。

**分布式锁中 Watcher 的使用策略：**

```
错误的监听方式（惊群效应）：
  所有等待者都监听最小节点（lock_00000001）
  当 lock_00000001 被删除时，所有等待者同时被唤醒
  纷纷调用 getChildren 获取子节点列表，判断自己是否是最小

正确的监听方式（链式等待）：
  客户端B（lock_00000002）监听 lock_00000001
  客户端C（lock_00000003）监听 lock_00000002
  客户端D（lock_00000004）监听 lock_00000003

  当 lock_00000001 被删除时，只有客户端B被唤醒
  客户端B获取锁，其他客户端不受影响
```

**Watcher 的一次性问题：**

ZooKeeper 的 Watcher 是一次性的，触发后需要重新注册。在分布式锁实现中需要注意：

```java
// 每次被唤醒后，需要重新检查前一个节点
// 因为在注册 Watcher 和节点删除之间可能存在时间窗口
// 如果在这期间前一个节点被删除，Watcher 可能不会触发

// 解决方案：先 exists 检查，再注册 Watcher
Stat stat = zooKeeper.exists(previousLockPath, true);
if (stat == null) {
    // 节点已删除，直接重新检查
    continue;
}
// 节点存在，等待 Watcher 触发
lockLatch.await();
```

**会话超时与自动释放：**

ZooKeeper 的临时节点在客户端会话结束后自动删除。会话超时由 `sessionTimeout` 参数控制：

- 如果客户端与 ZK 集群之间的网络中断超过 `sessionTimeout`，会话失效
- 临时节点被自动删除，锁自动释放
- 这保证了即使持有锁的客户端崩溃，锁也不会被永久持有（防死锁）

需要注意 `sessionTimeout` 的合理设置：

- 太短：网络抖动可能导致会话频繁失效，锁频繁释放
- 太长：客户端崩溃后锁释放延迟过长
- 通常设置为 10-30 秒

#### 3.3.3 Curator 框架实现

Apache Curator 是 ZooKeeper 的高级客户端框架，提供了丰富的分布式锁实现，大大简化了开发工作。

**InterProcessMutex（可重入锁）：**

```java
import org.apache.curator.framework.CuratorFramework;
import org.apache.curator.framework.CuratorFrameworkFactory;
import org.apache.curator.framework.recipes.locks.InterProcessMutex;
import org.apache.curator.retry.ExponentialBackoffRetry;

import java.util.concurrent.TimeUnit;

/**
 * 基于 Curator 的可重入分布式锁
 */
public class CuratorLockExample {

    private final CuratorFramework client;
    private final String lockPath = "/locks/order_lock";

    public CuratorLockExample(String connectString) {
        client = CuratorFrameworkFactory.builder()
                .connectString(connectString)
                .sessionTimeoutMs(30000)
                .connectionTimeoutMs(10000)
                .retryPolicy(new ExponentialBackoffRetry(1000, 3))
                .build();
        client.start();
    }

    /**
     * 使用可重入锁
     */
    public void processWithReentrantLock(String orderId) throws Exception {
        InterProcessMutex lock = new InterProcessMutex(client, lockPath);

        try {
            // 尝试获取锁，最多等待5秒
            if (lock.acquire(5, TimeUnit.SECONDS)) {
                try {
                    // 执行业务逻辑
                    processOrder(orderId);

                    // 可重入：同一客户端可以再次获取同一把锁
                    if (needReentrant(orderId)) {
                        lock.acquire();
                        try {
                            doAdditionalWork(orderId);
                        } finally {
                            lock.release();
                        }
                    }
                } finally {
                    lock.release();
                }
            } else {
                throw new RuntimeException("获取锁超时");
            }
        } catch (Exception e) {
            throw new RuntimeException("分布式锁操作失败", e);
        }
    }

    private void processOrder(String orderId) {
        // 业务逻辑
    }

    private boolean needReentrant(String orderId) {
        return true;
    }

    private void doAdditionalWork(String orderId) {
        // 额外业务逻辑
    }

    public void close() {
        client.close();
    }
}
```

```java
    try {

            try {

            } finally {
```

**Curator 锁的内部实现原理：**

Curator 的 `InterProcessMutex` 实现与前面手写的 ZK 锁原理一致，但增加了以下功能：

1. **可重入支持**：使用 `ConcurrentMap<Thread, LockData>` 记录每个线程的锁信息，同一线程多次 acquire 只增加计数
2. **锁路径优化**：使用 `leaseName` 区分不同锁实例
3. **异常恢复**：在连接断开重连后，能正确处理未完成的锁操作
4. **线程安全**：内部使用 `ConcurrentMap` 和原子操作保证线程安全

### 3.4 Redis vs ZooKeeper 详细对比

#### 3.4.1 性能对比

| 指标 | Redis | ZooKeeper |
|------|-------|-----------|
| 加锁延迟 | 0.5-1ms（网络RTT） | 5-15ms（ZAB共识） |
| 解锁延迟 | 0.5-1ms | 5-15ms |
| 单机 QPS | 10万+ | 1万-2万 |
| 锁等待机制 | 轮询/发布订阅 | Watcher回调 |
| 并发锁支持 | 高 | 中 |

Redis 的性能优势主要来自：
- 内存操作，无需磁盘持久化（可选 RDB/AOF）
- 单线程模型避免锁竞争（Redis 6.0+ 网络 I/O 多线程，命令执行仍单线程）
- 无需共识协议开销

ZooKeeper 性能较低的原因：
- 每次写操作需要 ZAB 协议达成共识（半数以上节点确认）
- 需要将事务日志写入磁盘（fsync）
- 集群节点间网络通信开销

#### 3.4.2 可靠性对比

| 维度 | Redis | ZooKeeper |
|------|-------|-----------|
| 一致性模型 | 最终一致（异步复制） | 强一致（ZAB协议） |
| 锁丢失风险 | 主从切换时可能丢失 | 不会丢失 |
| 故障恢复 | 需要手动/哨兵处理 | 自动选举恢复 |
| 数据持久化 | 可选（RDB/AOF） | 强制（事务日志+快照） |
| 网络分区行为 | AP，各分区可独立服务 | CP，少数派分区停止服务 |

#### 3.4.3 可用性对比

**Redis 可用性：**
- 主从切换通常在秒级完成（Sentinel 或 Cluster）
- 切换期间存在短暂的不可用窗口
- AP 模型：即使发生网络分区，各分区仍可独立提供锁服务
- 代价：分区期间可能产生锁不一致

**ZooKeeper 可用性：**
- 需要半数以上节点存活才能提供服务
- Leader 选举通常在 200ms-2s 完成
- CP 模型：少数派分区会停止服务，避免脑裂
- 代价：在分区期间部分客户端无法获取锁

#### 3.4.4 锁释放机制对比

| 机制 | Redis | ZooKeeper |
|------|-------|-----------|
| 主动释放 | DEL key（Lua脚本校验） | delete node |
| 超时释放 | TTL 自动过期 | Session timeout 删除临时节点 |
| 崩溃释放 | 依赖 TTL（等待过期） | 会话断开立即删除临时节点 |
| 释放及时性 | 取决于 TTL 设置 | 几乎实时（会话超时后立即） |

Redis 的锁释放延迟取决于 TTL：
- TTL 太短：业务未完成锁就过期
- TTL 太长：崩溃后等待时间长
- 看门狗缓解但增加了复杂度

ZooKeeper 的锁释放更加优雅：
- 客户端正常释放：主动删除节点
- 客户端崩溃：会话超时后自动删除临时节点
- 释放后通过 Watcher 实时通知下一个等待者
- 无需设置 TTL，无需看门狗

### 3.5 读写锁

**需求分析：**

在很多场景中，读操作远多于写操作。如果所有操作都使用排他锁，读操作之间也需要互斥，造成不必要的性能损耗。读写锁允许多个读操作同时进行，但写操作需要排他访问。

**读写锁规则：**

- 读锁（共享锁）：多个客户端可以同时持有读锁
- 写锁（排他锁）：同一时刻只有一个客户端可以持有写锁
- 读写互斥：有客户端持有写锁时，其他客户端不能获取读锁或写锁
- 写写互斥：有客户端持有写锁时，其他客户端不能获取写锁

**基于 Redis 的读写锁实现：**

使用两个 key 来实现：

- `lock:resource:read` — 读锁，值为当前持有读锁的客户端数量
- `lock:resource:write` — 写锁，值为写锁持有者标识

**加读锁 Lua 脚本：**

```lua
-- 加读锁
-- KEYS[1] = read lock key
-- KEYS[2] = write lock key
-- ARGV[1] = client identifier
-- ARGV[2] = expire time (milliseconds)
--
-- 逻辑：如果写锁不存在，则增加读锁计数

if redis.call('EXISTS', KEYS[2]) == 1 then
    -- 写锁存在，不能获取读锁
    return 0
end

-- 写锁不存在，增加读锁计数
redis.call('HINCRBY', KEYS[1], ARGV[1], 1)
redis.call('PEXPIRE', KEYS[1], ARGV[2])
return 1
```

**加写锁 Lua 脚本：**

```lua
-- 加写锁
-- KEYS[1] = read lock key
-- KEYS[2] = write lock key
-- ARGV[1] = client identifier
-- ARGV[2] = expire time (milliseconds)
--
-- 逻辑：如果读锁和写锁都不存在，则获取写锁

if redis.call('EXISTS', KEYS[2]) == 1 then
    -- 写锁已存在，检查是否重入
    if redis.call('GET', KEYS[2]) == ARGV[1] then
        redis.call('PEXPIRE', KEYS[2], ARGV[2])
        return 1
    end
    return 0
end

-- 检查是否有读锁（包括自己持有的读锁）
if redis.call('EXISTS', KEYS[1]) == 1 then
    -- 有读锁存在，检查是否是锁降级（自己持有所有读锁）
    local readHolders = redis.call('HLEN', KEYS[1])
    if readHolders > 0 then
        return 0
    end
end

-- 获取写锁
redis.call('SET', KEYS[2], ARGV[1])
redis.call('PEXPIRE', KEYS[2], ARGV[2])
return 1
```

**解锁 Lua 脚本：**

```lua
-- 解读锁
-- KEYS[1] = read lock key
-- ARGV[1] = client identifier
if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then
    local count = redis.call('HINCRBY', KEYS[1], ARGV[1], -1)
    if count <= 0 then
        redis.call('HDEL', KEYS[1], ARGV[1])
    end
    return 1
end
return 0
```

**读写锁 Java 实现（基于 Redisson）：**

```java
import org.redisson.Redisson;
import org.redisson.api.RReadWriteLock;
import org.redisson.api.RedissonClient;
import org.redisson.config.Config;

/**
 * 基于 Redisson 的读写锁实现
 */
public class RedissonReadWriteLockExample {

    private final RedissonClient redisson;

    public RedissonReadWriteLockExample(String redisAddress) {
        Config config = new Config();
        config.useSingleServer()
                .setAddress(redisAddress)
                .setConnectionPoolSize(32)
                .setConnectionMinimumIdleSize(8);
        this.redisson = Redisson.create(config);
    }

    /**
     * 读操作
     */
    public String readData(String resource) {
        RReadWriteLock rwLock = redisson.getReadWriteLock("rwlock:" + resource);

        try {
            // 获取读锁
            boolean locked = rwLock.readLock().tryLock(5, 30, TimeUnit.SECONDS);
            if (!locked) {
                throw new RuntimeException("获取读锁失败");
            }

            try {
                // 多个线程可以同时读取
                return doReadFromCache(resource);
            } finally {
                rwLock.readLock().unlock();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("线程中断", e);
        }
    }

    /**
     * 写操作
     */
    public void writeData(String resource, String data) {
        RReadWriteLock rwLock = redisson.getReadWriteLock("rwlock:" + resource);

        try {
            // 获取写锁（排他）
            boolean locked = rwLock.writeLock().tryLock(5, 30, TimeUnit.SECONDS);
            if (!locked) {
                throw new RuntimeException("获取写锁失败");
            }

            try {
                // 独占访问，更新数据
                doWriteToCache(resource, data);
                doWriteToDB(resource, data);
            } finally {
                rwLock.writeLock().unlock();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("线程中断", e);
        }
    }

    /**
     * 锁降级：写锁 → 读锁
     * 场景：更新数据后需要立即读取验证
     */
    public String writeThenRead(String resource, String data) {
        RReadWriteLock rwLock = redisson.getReadWriteLock("rwlock:" + resource);

        try {
            // 先获取写锁
            rwLock.writeLock().lock(30, TimeUnit.SECONDS);
            try {
                doWriteToCache(resource, data);

                // 获取读锁（此时持有写锁+读锁）
                rwLock.readLock().lock(30, TimeUnit.SECONDS);
            } finally {
                // 释放写锁，降级为读锁
                rwLock.writeLock().unlock();
            }

            try {
                // 此时只持有读锁，其他读线程可以进入
                return doReadFromCache(resource);
            } finally {
                rwLock.readLock().unlock();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        }
    }

    private String doReadFromCache(String key) { return "data"; }
    private void doWriteToCache(String key, String value) { }
    private void doWriteToDB(String key, String value) { }

    public void close() {
        redisson.shutdown();
    }
}
```

**读写锁适用场景：**

- 配置中心：读多写少，配置变更时需要排他写入
- 缓存更新：多线程读取缓存，偶尔需要刷新
- 状态管理：多线程读取设备状态，偶尔更新状态
- 统计报表：多线程查询统计数据，定时任务写入统计结果

## 四、异常处理与容错

### 4.1 锁持有者崩溃

**Redis 场景：**

当持有锁的客户端崩溃时，锁不会立即释放，而是等待 TTL 过期后才自动释放。这期间其他客户端无法获取锁。

应对措施：
- 设置合理的 TTL（通常为业务预期执行时间的 1.5-2 倍）
- 使用看门狗机制自动续期
- 在 TTL 之外设置业务超时，避免无限等待

```java
public void safeBusinessWithLock() {
    String lockValue = lock.tryLock(resource, 30);
    if (lockValue == null) {
        throw new RuntimeException("获取锁失败");
    }

    try {
        // 设置业务超时，防止业务线程无限阻塞
        Future<?> future = executor.submit(() -> doBusiness());
        try {
            future.get(25, TimeUnit.SECONDS); // 略小于锁 TTL
        } catch (TimeoutException e) {
            future.cancel(true);
            throw new RuntimeException("业务执行超时");
        }
    } finally {
        lock.unlock(resource, lockValue);
    }
}
```

**ZooKeeper 场景：**

客户端崩溃后，ZooKeeper 的会话超时机制会自动删除临时节点，释放锁。其他等待客户端通过 Watcher 被通知。

应对措施：
- 合理设置 `sessionTimeout`（10-30秒）
- 注意网络抖动可能导致误判会话超时
- 使用 Curator 的 ConnectionStateListener 监控连接状态

```java
client.getConnectionStateListenable().addListener((client, state) -> {
    if (state == ConnectionState.LOST) {
        // 连接丢失，锁可能已被释放
        // 需要停止业务操作，防止在无锁状态下继续执行
        handleConnectionLost();
    } else if (state == ConnectionState.SUSPENDED) {
        // 连接暂时中断，锁可能还在但不确定
        // 建议暂停业务操作
        handleConnectionSuspended();
    } else if (state == ConnectionState.RECONNECTED) {
        // 连接恢复
        handleReconnected();
    }
});
```

### 4.2 网络分区与脑裂

**问题描述：**

网络分区将集群分成多个互不可见的子网络。在 AP 系统（如 Redis）中，各分区可能独立提供服务，导致同一个锁被多个分区中的客户端同时持有。

**Redis 主从切换中的脑裂：**

1. 客户端 A 在主节点获取锁
2. 网络分区，主节点与从节点断开
3. 哨兵判定主节点下线，提升从节点为新主
4. 客户端 B 在新主节点获取锁（新主没有客户端 A 的锁数据）
5. 两个客户端同时持有锁

**应对方案：**

```
方案1：RedLock 算法
  - 使用多个独立 Redis 实例，需要多数派同意
  - 网络分区时少数派实例不可达，无法达到多数派

方案2：Fencing Token（见 4.6）

方案3：业务幂等设计
  - 不完全依赖分布式锁，在业务层做幂等校验
  - 即使锁失效，重复操作也不会造成数据错误
```

### 4.3 时钟漂移问题

**对 RedLock 的影响：**

RedLock 算法依赖系统时钟计算锁的有效时间。如果客户端的时钟发生跳跃，可能导致：

- 时钟前进：锁的有效时间被高估，实际可能已经过期
- 时钟后退：锁的有效时间被低估，可能提前释放

**时钟跳跃的原因：**

- NTP 时钟同步：NTP 可能调整系统时钟（包括向前跳跃）
- 虚拟机迁移：VM 迁移后时钟可能与物理机不同步
- 手动修改系统时间

**应对方案：**

```java
/**
 * 使用单调时钟（Monotonic Clock）减少时钟漂移影响
 */
public class MonotonicClockTimer {

    // System.nanoTime() 返回单调时钟，不受系统时间调整影响
    private final long startNanos = System.nanoTime();

    /**
     * 获取经过的时间（毫秒）
     */
    public long elapsedMillis() {
        return TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNanos);
    }
}

// 在 RedLock 中使用单调时钟
public boolean tryLockWithMonotonicClock(String resource, long ttlMillis) {
    MonotonicClockTimer timer = new MonotonicClockTimer();

    // ... 向各 Redis 实例加锁 ...

    long elapsed = timer.elapsedMillis();
    if (elapsed < ttlMillis) {
        long validityTime = ttlMillis - elapsed;
        // 使用 validityTime
    }
}
```

### 4.4 GC 暂停导致锁过期

**问题描述：**

JVM 的 Stop-The-World (STW) GC 会暂停应用线程。如果 GC 暂停时间超过锁的 TTL：

1. 客户端 A 获取锁，TTL=10s
2. 客户端 A 触发 Full GC，STW 持续 15s
3. 锁已过期，客户端 B 获取到锁
4. 客户端 A GC 结束，从暂停点继续执行，以为自己仍持有锁
5. 两个客户端同时操作共享资源

**应对方案：**

**方案一：Fencing Token（推荐）**

```java
/**
 * Fencing Token 模式
 * 每次获取锁时生成一个单调递增的 token
 * 存储层在执行操作时校验 token，拒绝旧 token 的操作
 */
public class FencingTokenLock {

    private final JedisPool jedisPool;
    private static final String TOKEN_KEY = "fencing_token:";

    /**
     * 获取锁并返回 Fencing Token
     */
    public LockResult tryLock(String resource, int expireSeconds) {
        String lockKey = "lock:" + resource;
        String lockValue = UUID.randomUUID().toString();

        try (Jedis jedis = jedisPool.getResource()) {
            SetParams params = SetParams.setParams().nx().ex(expireSeconds);
            String result = jedis.set(lockKey, lockValue, params);

            if ("OK".equals(result)) {
                // 获取一个单调递增的 token
                Long token = jedis.incr(TOKEN_KEY + resource);
                return new LockResult(lockValue, token);
            }
        }
        return null;
    }

    /**
     * 业务操作时携带 Fencing Token
     * 存储层需要校验 token
     */
    public void updateData(String resource, String data, long fencingToken) {
        // SQL 示例：只有 token 大于已记录的 token 才执行更新
        // UPDATE data_table SET value = ?, last_token = ?
        // WHERE resource = ? AND last_token < ?
        jdbcTemplate.update(
                "UPDATE data_table SET value = ?, last_token = ? WHERE resource = ? AND last_token < ?",
                data, fencingToken, resource, fencingToken
        );
    }

    public static class LockResult {
        public final String lockValue;
        public final long fencingToken;

        LockResult(String lockValue, long fencingToken) {
            this.lockValue = lockValue;
            this.fencingToken = fencingToken;
        }
    }
}
```

**方案二：GC 前检查锁有效性**

在关键业务操作前，再次检查锁是否仍然有效：

```java
public void safeBusiness(String resource, String lockValue) {
    // 业务操作前检查锁是否仍属于自己
    try (Jedis jedis = jedisPool.getResource()) {
        String currentValue = jedis.get("lock:" + resource);
        if (!lockValue.equals(currentValue)) {
            // 锁已不属于自己（可能因 GC 暂停导致过期）
            throw new LockLostException("锁已失效，可能因 GC 暂停导致");
        }
    }

    // 锁仍然有效，执行业务
    doBusiness();
}
```

> **注意：** 方案二存在 TOCTOU（Time of Check to Time of Use）竞态问题：检查完之后、执行业务之前锁可能恰好过期。Fencing Token 是更可靠的方案。

### 4.5 锁续期失败

看门狗续期可能因以下原因失败：

- Redis 节点故障
- 网络抖动
- 锁已被其他客户端获取（TTL 过期后被重新分配）

**应对方案：**

```java
/**
 * 续期失败时的处理策略
 */
public void startWatchdogWithFailureHandling(LockContext context, long ttlMillis) {
    long interval = ttlMillis / 3;
    final int[] failureCount = {0};
    final int MAX_FAILURES = 3;

    ScheduledFuture<?> future = scheduler.scheduleAtFixedRate(() -> {
        try {
            boolean renewed = renewLock(context, ttlMillis);
            if (renewed) {
                failureCount[0] = 0; // 重置失败计数
            } else {
                failureCount[0]++;
                if (failureCount[0] >= MAX_FAILURES) {
                    // 续期连续失败，触发降级策略
                    onLockRenewalFailed(context);
                    stopWatchdog(context.lockKey);
                }
            }
        } catch (Exception e) {
            failureCount[0]++;
            if (failureCount[0] >= MAX_FAILURES) {
                onLockRenewalFailed(context);
                stopWatchdog(context.lockKey);
            }
        }
    }, interval, interval, TimeUnit.MILLISECONDS);
}

/**
 * 锁续期失败的降级处理
 */
private void onLockRenewalFailed(LockContext context) {
    // 策略1：快速完成业务（如果可能）
    // 策略2：记录告警日志
    log.warn("锁续期失败，lockKey={}, 当前线程可能在无锁状态下执行", context.lockKey);

    // 策略3：中断业务线程
    Thread.currentThread().interrupt();

    // 策略4：通知其他系统做补偿
    notifyCompensationSystem(context);
}
```

### 4.6 异常场景总结

| 异常场景 | Redis 表现 | ZK 表现 | 应对策略 |
|---------|-----------|---------|---------|
| 持有者崩溃 | TTL 后释放 | 会话超时后立即释放 | 设置合理 TTL/session |
| 网络分区 | 可能双持锁 | 少数派停止服务 | RedLock/Fencing Token |
| 时钟漂移 | 影响锁有效期 | 影响较小 | 使用单调时钟 |
| GC 暂停 | 锁可能过期 | 锁可能过期 | Fencing Token |
| 续期失败 | 锁过期后失效 | 无需续期 | 降级+补偿 |
| Redis/ZK 宕机 | 锁不可用 | 半数以上存活即可 | 多节点部署 |

## 五、性能优化

### 5.1 锁粒度优化

**粗粒度锁 vs 细粒度锁：**

```java
// 粗粒度锁（不推荐）：所有商品共用一把锁
String lockKey = "inventory_lock"; // 所有商品竞争同一把锁
lock.tryLock(lockKey, 30);

// 细粒度锁（推荐）：按商品维度加锁
String lockKey = "inventory_lock:" + productId; // 不同商品互不影响
lock.tryLock(lockKey, 30);

// 更细粒度锁：按商品+仓库维度加锁
String lockKey = "inventory_lock:" + productId + ":" + warehouseId;
lock.tryLock(lockKey, 30);
```

锁粒度越细，并发度越高，但锁管理开销也越大。需要根据业务场景找到平衡点。

### 5.2 无锁替代方案

在某些场景下，可以使用无锁方案替代分布式锁：

**CAS 乐观锁：**

```java
/**
 * 使用数据库 CAS 实现库存扣减，无需分布式锁
 */
public boolean deductInventoryWithCAS(String productId, int quantity) {
    // SELECT version, stock FROM inventory WHERE product_id = ?
    Inventory inv = inventoryDao.getByProductId(productId);
    if (inv.getStock() < quantity) {
        return false; // 库存不足
    }

    // CAS 更新：version 必须匹配
    int rows = jdbcTemplate.update(
            "UPDATE inventory SET stock = stock - ?, version = version + 1 " +
            "WHERE product_id = ? AND version = ? AND stock >= ?",
            quantity, productId, inv.getVersion(), quantity
    );

    return rows > 0; // 返回 false 表示并发冲突，需要重试
}
```

**Redis 原子操作：**

```java
/**
 * 使用 Redis 原子递减实现库存扣减，无需分布式锁
 */
public boolean deductInventoryAtomically(String productId, int quantity) {
    try (Jedis jedis = jedisPool.getResource()) {
        // Lua 脚本保证原子性
        String lua = "local stock = redis.call('GET', KEYS[1]) " +
                     "if stock and tonumber(stock) >= tonumber(ARGV[1]) then " +
                     "    return redis.call('DECRBY', KEYS[1], ARGV[1]) " +
                     "else " +
                     "    return -1 " +
                     "end";
        Object result = jedis.eval(lua,
                Collections.singletonList("stock:" + productId),
                Collections.singletonList(String.valueOf(quantity)));
        return ((Long) result) >= 0;
    }
}
```

### 5.3 分段锁

对于热点资源（如爆款商品库存），单个锁可能成为瓶颈。可以将资源分成多段，每段独立加锁：

```java
/**
 * 分段锁实现热点库存扣减
 * 将 1000 件库存分成 10 段，每段 100 件
 */
public class SegmentedInventoryLock {

    private final RedisDistributedLock lock;
    private final int segmentCount = 10; // 10个分段
    private final String productId;

    public SegmentedInventoryLock(RedisDistributedLock lock, String productId) {
        this.lock = lock;
        this.productId = productId;
    }

    /**
     * 扣减库存（分段锁）
     */
    public boolean deduct(int quantity) {
        // 随机选择一个分段开始尝试
        int startSegment = ThreadLocalRandom.current().nextInt(segmentCount);

        for (int i = 0; i < segmentCount; i++) {
            int segment = (startSegment + i) % segmentCount;
            String lockKey = "inventory:" + productId + ":segment:" + segment;

            String lockValue = lock.tryLock(lockKey, 10);
            if (lockValue != null) {
                try {
                    int segmentStock = getSegmentStock(productId, segment);
                    if (segmentStock >= quantity) {
                        deductSegmentStock(productId, segment, quantity);
                        return true;
                    }
                    // 当前分段库存不足，尝试下一个分段
                } finally {
                    lock.unlock(lockKey, lockValue);
                }
            }
        }
        return false; // 所有分段都不足
    }

    private int getSegmentStock(String productId, int segment) { return 0; }
    private void deductSegmentStock(String productId, int segment, int quantity) { }
}
```

### 5.4 锁超时调优

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| 锁 TTL | 业务预期执行时间 x 1.5~2 | 留出安全余量 |
| 看门狗续期间隔 | TTL / 3 | 在 TTL 的 1/3 处续期 |
| 获取锁重试间隔 | 50-100ms | 避免过于频繁重试 |
| 获取锁总超时 | 3-5秒 | 根据业务 SLA 调整 |
| ZK 会话超时 | 10-30秒 | 太短易误判，太长恢复慢 |
| 网络超时 | 50-200ms | 单次 Redis/ZK 操作超时 |

### 5.5 锁等待队列优化

对于高竞争场景，可以使用 Redis 的发布订阅机制实现高效的通知唤醒，替代轮询：

```java
/**
 * 基于发布订阅的锁等待通知
 * 获取锁失败时订阅频道，被唤醒后再尝试
 * 比轮询更高效，延迟更低
 */
public class PubSubLock {

    private final JedisPool jedisPool;

    public boolean lockWithNotify(String resource, String lockValue,
                                   long timeoutMillis) throws InterruptedException {
        long deadline = System.currentTimeMillis() + timeoutMillis;
        String channel = "lock_notify:" + resource;

        while (System.currentTimeMillis() < deadline) {
            // 尝试加锁
            if (tryLockInternal(resource, lockValue)) {
                return true;
            }

            // 加锁失败，订阅通知频道
            CountDownLatch latch = new CountDownLatch(1);
            Thread subThread = new Thread(() -> {
                try (Jedis jedis = jedisPool.getResource()) {
                    jedis.subscribe(new JedisPubSub() {
                        @Override
                        public void onMessage(String channel, String message) {
                            latch.countDown();
                        }
                    }, channel);
                }
            }, "lock-sub-" + resource);
            subThread.setDaemon(true);
            subThread.start();

            // 等待通知或超时
            long remaining = deadline - System.currentTimeMillis();
            if (remaining > 0) {
                latch.await(Math.min(remaining, 1000), TimeUnit.MILLISECONDS);
            }
        }
        return false;
    }

    /**
     * 释放锁并通知等待者
     */
    public void unlockWithNotify(String resource, String lockValue) {
        try (Jedis jedis = jedisPool.getResource()) {
            // Lua 脚本：校验并删除，然后发布通知
            String lua = "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
                         "  redis.call('DEL', KEYS[1]) " +
                         "  redis.call('PUBLISH', KEYS[2], 'unlocked') " +
                         "  return 1 " +
                         "else " +
                         "  return 0 " +
                         "end";
            jedis.eval(lua,
                    Arrays.asList("lock:" + resource, "lock_notify:" + resource),
                    Collections.singletonList(lockValue));
        }
    }

    private boolean tryLockInternal(String resource, String lockValue) {
        // ... 基础加锁逻辑 ...
        return false;
    }
}
```

## 六、最佳实践与总结

### 6.1 必须遵守的实践

**1. 永远使用 try-finally 保证锁释放**

```java
// 正确：try-finally 确保锁一定被释放
String lockValue = null;
try {
    lockValue = lock.tryLock(resource, 30);
    if (lockValue != null) {
        doBusiness();
    }
} finally {
    if (lockValue != null) {
        lock.unlock(resource, lockValue);
    }
}

// 错误：忘记 finally，异常时锁不会被释放
String lockValue = lock.tryLock(resource, 30);
if (lockValue != null) {
    doBusiness(); // 如果这里抛异常，锁不会被释放
    lock.unlock(resource, lockValue);
}
```

**2. 设置合理的锁过期时间**

- TTL 应大于业务正常执行时间，小于业务最大容忍时间
- 不确定执行时间时使用看门狗自动续期
- 绝对不要使用没有 TTL 的锁（可能死锁）

**3. 解锁时必须校验锁持有者**

```java
// 正确：使用 Lua 脚本校验后删除
jedis.eval(UNLOCK_LUA, keys, args);

// 错误：直接 DEL，可能删除别人的锁
jedis.del(lockKey);
```

**4. 加锁和解锁操作必须保证原子性**

```java
// 正确：SET NX EX（原子）
jedis.set(key, value, SetParams.setParams().nx().ex(30));

// 错误：SETNX + EXPIRE（非原子）
jedis.setnx(key, value);
jedis.expire(key, 30);
```

### 6.2 推荐的实践

**1. 将幂等性作为分布式锁的补充**

分布式锁不能 100% 保证互斥（网络分区、GC 暂停等极端情况），应该在业务层实现幂等性作为兜底：

```java
public void processOrder(String orderId) {
    // 幂等校验（兜底）
    if (orderDao.existsByOrderId(orderId)) {
        return; // 已处理，跳过
    }

    // 分布式锁（减少并发冲突）
    String lockValue = lock.tryLock("order:" + orderId, 30);
    if (lockValue == null) return;

    try {
        // 再次幂等校验（Double-Check）
        if (orderDao.existsByOrderId(orderId)) {
            return;
        }
        createOrder(orderId);
    } finally {
        lock.unlock("order:" + orderId, lockValue);
    }
}
```

**2. 评估是否真的需要分布式锁**

很多时候，分布式锁可以被更轻量的方案替代：

| 场景 | 分布式锁替代方案 |
|------|----------------|
| 库存扣减 | Redis Lua 原子递减 |
| 订单去重 | 数据库唯一索引 |
| 定时任务去重 | 任务调度框架（如 XXL-Job） |
| 配置更新 | 版本号/CAS |
| 限流 | Redis + Lua / 令牌桶 |

**3. 监控与告警**

```java
// 加锁耗时监控
long start = System.currentTimeMillis();
String lockValue = lock.tryLock(resource, 30);
long lockTime = System.currentTimeMillis() - start;

if (lockTime > 100) {
    metrics.record("lock.acquire.slow", lockTime);
}
if (lockValue == null) {
    metrics.increment("lock.acquire.failed");
}

// 锁持有时间监控
try {
    doBusiness();
} finally {
    long holdTime = System.currentTimeMillis() - start - lockTime;
    if (holdTime > 20_000) {
        log.warn("锁持有时间过长: {}ms, resource={}", holdTime, resource);
        metrics.record("lock.hold.too_long", holdTime);
    }
    lock.unlock(resource, lockValue);
}
```

### 6.3 常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|---------|
| 忘记设置 TTL | 持有者崩溃后死锁 | 必须设置过期时间 |
| 解锁不校验持有者 | 误删他人的锁 | 使用 Lua 脚本校验 value |
| SETNX + EXPIRE 非原子 | 中间崩溃导致死锁 | 使用 SET NX EX 原子命令 |
| 锁内执行耗时网络操作 | 锁持有时间过长 | 缩小锁范围，减少锁内操作 |
| 不处理获取锁失败 | 业务逻辑不执行 | 明确处理失败场景 |
| 锁 value 不唯一 | 解锁时无法区分持有者 | 使用 UUID 作为 value |
| 可重入锁但不释放 | 重入计数永远不归零 | 确保 lock/unlock 配对 |
| 看门狗续期失败不处理 | 锁过期后业务继续执行 | 续期失败时降级或中断 |

### 6.4 总结

分布式锁是分布式系统中保障数据一致性的重要基础设施，但没有一种方案是完美的：

- **数据库锁** 简单但性能差，适合低频场景
- **Redis 锁** 高性能但有锁丢失风险，适合高并发场景
- **ZooKeeper 锁** 强一致但性能较低，适合高可靠性场景
- **RedLock** 在可靠性和性能间折中，但存在争议

选型时应根据业务场景的 CAP 需求、性能要求、运维成本综合考虑。无论选择哪种方案，都应遵循以下原则：

1. **防御性设计**：不信任锁的绝对可靠性，在业务层实现幂等兜底
2. **原子性保证**：加锁、解锁操作必须原子化
3. **超时保护**：设置合理的 TTL，防止死锁
4. **监控告警**：对锁的获取、持有、续期进行全链路监控
5. **降级预案**：锁服务不可用时有降级方案（如本地锁 + 幂等）

分布式锁不是银弹，在引入前应仔细评估是否真的需要。很多时候，通过业务设计（如幂等、CAS、唯一索引）可以更优雅地解决并发问题，避免分布式锁带来的复杂性和风险。

### 7.1 案例一：Redis 分布式锁在订单防重复提交中的应用全链路

#### 7.1.1 业务背景

用户在电商平台提交订单时，由于网络抖动、前端按钮未禁用等原因，可能在短时间内发送多次相同的下单请求。这些请求经过负载均衡后被分发到不同的服务实例，如果没有防重复提交机制，将导致创建多笔重复订单，引发用户投诉和资金损失。

**全链路防重设计（三层防护）：**

```
第一层：幂等 Token（前端生成，后端校验并消费）
   ↓ Token 有效
第二层：Redis 分布式锁（SET NX EX + 看门狗续期 + Lua 脚本释放）
   ↓ 获取锁成功
第三层：数据库唯一索引（user_id + idempotent_token 联合唯一索引兜底）
```

#### 7.1.2 幂等 Token 服务

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;

import java.util.Collections;
import java.util.UUID;

/**
 * 幂等 Token 服务
 *
 * 流程：
 * 1. 用户进入下单页面时，前端调用 generateToken 接口获取 Token
 * 2. 提交订单时携带 Token
 * 3. 后端通过 Lua 脚本原子性地校验并消费 Token（GET + DEL 原子操作）
 * 4. 同一个 Token 只能被消费一次，第二次请求会被拒绝
 */
@Service
public class IdempotentTokenService {

    private static final Logger log = LoggerFactory.getLogger(IdempotentTokenService.class);

    private final JedisPool jedisPool;
    private static final String TOKEN_PREFIX = "idempotent:token:";
    private static final int TOKEN_EXPIRE_SECONDS = 600; // Token 有效期 10 分钟

    /**
     * 消费 Token 的 Lua 脚本（原子操作：校验存在性 + 删除）
     * 返回 1 表示 Token 有效且已消费，返回 0 表示 Token 无效或已被消费
     */
    private static final String CONSUME_TOKEN_LUA =
            "if redis.call('EXISTS', KEYS[1]) == 1 then " +
            "    redis.call('DEL', KEYS[1]) " +
            "    return 1 " +
            "else " +
            "    return 0 " +
            "end";

    public IdempotentTokenService(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * 生成幂等 Token
     * 用户进入下单页面时调用，Token 存入 Redis 并返回给前端
     */
    public String generateToken(Long userId) {
        String token = UUID.randomUUID().toString().replace("-", "");
        String key = TOKEN_PREFIX + userId + ":" + token;

        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(key, TOKEN_EXPIRE_SECONDS, "1");
        }

        log.info("[幂等Token] 生成成功, userId={}, token={}", userId, token);
        return token;
    }

    /**
     * 消费幂等 Token（原子操作）
     * 提交订单时调用，同一个 Token 只能被消费一次
     *
     * @return true=Token 有效且已消费, false=Token 无效或已被消费
     */
    public boolean consumeToken(Long userId, String token) {
        String key = TOKEN_PREFIX + userId + ":" + token;

        try (Jedis jedis = jedisPool.getResource()) {
            Object result = jedis.eval(
                    CONSUME_TOKEN_LUA,
                    Collections.singletonList(key),
                    Collections.emptyList()
            );

            boolean consumed = result != null && ((Long) result) == 1L;
            log.info("[幂等Token] 消费结果, userId={}, token={}, consumed={}",
                    userId, token, consumed);
            return consumed;
        }
    }
}
```

#### 7.1.3 分布式锁封装（看门狗续期 + Lua 脚本释放）

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.params.SetParams;

import java.util.Arrays;
import java.util.Collections;
import java.util.UUID;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * 订单分布式锁
 * 基于 Redis SET NX EX + 看门狗续期 + Lua 脚本释放
 */
@Component
public class OrderDistributedLock {

    private static final Logger log = LoggerFactory.getLogger(OrderDistributedLock.class);

    private final JedisPool jedisPool;
    private static final String LOCK_PREFIX = "order:lock:";
    private static final long DEFAULT_TTL_MS = 30_000L;     // 默认 TTL 30 秒
    private static final long WATCHDOG_INTERVAL_MS = DEFAULT_TTL_MS / 3; // 看门狗每 10 秒续期

    /**
     * Lua 脚本：续期（校验持有者后重置 TTL）
     */
    private static final String RENEW_LUA =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
            "else " +
            "    return 0 " +
            "end";

    /**
     * Lua 脚本：释放锁（校验持有者后删除）
     */
    private static final String UNLOCK_LUA =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('DEL', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";

    private final ConcurrentHashMap<String, ScheduledFuture<?>> watchdogTasks = new ConcurrentHashMap<>();
    private final ScheduledExecutorService watchdogExecutor = Executors.newScheduledThreadPool(
            Runtime.getRuntime().availableProcessors(),
            new ThreadFactory() {
                private final AtomicInteger counter = new AtomicInteger(0);
                @Override
                public Thread newThread(Runnable r) {
                    Thread t = new Thread(r, "order-lock-watchdog-" + counter.getAndIncrement());
                    t.setDaemon(true);
                    return t;
                }
            }
    );

    public OrderDistributedLock(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * 获取分布式锁（带重试和看门狗）
     *
     * @param orderKey        订单唯一标识
     * @param timeoutMillis   获取锁的最大等待时间（毫秒）
     * @param retryIntervalMs 重试间隔（毫秒）
     * @return LockContext，null 表示获取失败
     */
    public LockContext tryLock(String orderKey, long timeoutMillis, long retryIntervalMs) {
        String lockKey = LOCK_PREFIX + orderKey;
        String lockValue = UUID.randomUUID() + ":" + Thread.currentThread().getId();
        long deadline = System.currentTimeMillis() + timeoutMillis;

        while (System.currentTimeMillis() < deadline) {
            try (Jedis jedis = jedisPool.getResource()) {
                SetParams params = SetParams.setParams().nx().px(DEFAULT_TTL_MS);
                String result = jedis.set(lockKey, lockValue, params);

                if ("OK".equals(result)) {
                    LockContext ctx = new LockContext(lockKey, lockValue, System.currentTimeMillis());

                    // 启动看门狗自动续期
                    startWatchdog(ctx);

                    log.info("[订单锁] 获取成功, lockKey={}, lockValue={}", lockKey, lockValue);
                    return ctx;
                }
            } catch (Exception e) {
                log.error("[订单锁] 获取异常, lockKey={}", lockKey, e);
            }

            try {
                Thread.sleep(retryIntervalMs);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                log.warn("[订单锁] 获取锁等待被中断, lockKey={}", lockKey);
                return null;
            }
        }

        log.warn("[订单锁] 获取超时, lockKey={}, timeout={}ms", lockKey, timeoutMillis);
        return null;
    }

    /**
     * 释放分布式锁（Lua 脚本保证原子性）
     */
    public boolean unlock(LockContext ctx) {
        // 先停止看门狗
        stopWatchdog(ctx.getLockKey());

        try (Jedis jedis = jedisPool.getResource()) {
            Object result = jedis.eval(
                    UNLOCK_LUA,
                    Collections.singletonList(ctx.getLockKey()),
                    Collections.singletonList(ctx.getLockValue())
            );

            boolean released = result != null && ((Long) result) == 1L;
            if (released) {
                log.info("[订单锁] 释放成功, lockKey={}", ctx.getLockKey());
            } else {
                log.warn("[订单锁] 释放失败(锁可能已过期或被其他实例持有), lockKey={}",
                        ctx.getLockKey());
            }
            return released;

        } catch (Exception e) {
            log.error("[订单锁] 释放异常, lockKey={}", ctx.getLockKey(), e);
            return false;
        }
    }

    /**
     * 启动看门狗
     * 每 10 秒（TTL/3）执行一次续期，将 TTL 重置为 30 秒
     */
    private void startWatchdog(LockContext ctx) {
        ScheduledFuture<?> future = watchdogExecutor.scheduleAtFixedRate(() -> {
            try (Jedis jedis = jedisPool.getResource()) {
                Object result = jedis.eval(
                        RENEW_LUA,
                        Collections.singletonList(ctx.getLockKey()),
                        Arrays.asList(ctx.getLockValue(), String.valueOf(DEFAULT_TTL_MS))
                );

                if (result == null || ((Long) result) == 0L) {
                    log.warn("[看门狗] 续期失败(锁可能已丢失), lockKey={}", ctx.getLockKey());
                    stopWatchdog(ctx.getLockKey());
                } else {
                    log.debug("[看门狗] 续期成功, lockKey={}, TTL={}ms",
                            ctx.getLockKey(), DEFAULT_TTL_MS);
                }
            } catch (Exception e) {
                log.error("[看门狗] 续期异常, lockKey={}", ctx.getLockKey(), e);
                stopWatchdog(ctx.getLockKey());
            }
        }, WATCHDOG_INTERVAL_MS, WATCHDOG_INTERVAL_MS, TimeUnit.MILLISECONDS);

        watchdogTasks.put(ctx.getLockKey(), future);
    }

    /**
     * 停止看门狗
     */
    private void stopWatchdog(String lockKey) {
        ScheduledFuture<?> task = watchdogTasks.remove(lockKey);
        if (task != null) {
            task.cancel(false);
            log.debug("[看门狗] 已停止, lockKey={}", lockKey);
        }
    }

    /**
     * 锁上下文
     */
    public static class LockContext {
        private final String lockKey;
        private final String lockValue;
        private final long acquiredAt;

        public LockContext(String lockKey, String lockValue, long acquiredAt) {
            this.lockKey = lockKey;
            this.lockValue = lockValue;
            this.acquiredAt = acquiredAt;
        }

        public String getLockKey() { return lockKey; }
        public String getLockValue() { return lockValue; }
        public long getAcquiredAt() { return acquiredAt; }
    }
}
```

#### 7.1.4 订单服务（完整全链路）

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * 订单服务 - 防重复提交全链路实现
 *
 * 全链路流程：
 * 1. 前端携带幂等 Token 提交订单
 * 2. 校验并消费幂等 Token（原子操作）
 * 3. 获取分布式锁（看门狗自动续期）
 * 4. 幂等校验（Double-Check：数据库唯一索引兜底）
 * 5. 创建订单 + 扣减库存（事务）
 * 6. 释放分布式锁
 */
@Service
public class OrderService {

    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    private final IdempotentTokenService tokenService;
    private final OrderDistributedLock distributedLock;
    private final OrderRepository orderRepository;
    private final InventoryService inventoryService;

    public OrderService(IdempotentTokenService tokenService,
                        OrderDistributedLock distributedLock,
                        OrderRepository orderRepository,
                        InventoryService inventoryService) {
        this.tokenService = tokenService;
        this.distributedLock = distributedLock;
        this.orderRepository = orderRepository;
        this.inventoryService = inventoryService;
    }

    /**
     * 提交订单（防重复提交全链路）
     *
     * @param request 订单请求
     * @return 订单创建结果
     */
    public OrderResult submitOrder(OrderRequest request) {
        Long userId = request.getUserId();
        String token = request.getIdempotentToken();
        String orderKey = userId + ":" + token;

        log.info("[订单提交] 开始处理, userId={}, productId={}, quantity={}, token={}",
                userId, request.getProductId(), request.getQuantity(), token);

        // ====== 第一层防重：幂等 Token 校验 ======
        // Token 是一次性的，第二次请求携带相同 Token 会被拒绝
        if (!tokenService.consumeToken(userId, token)) {
            log.warn("[订单提交] 幂等Token无效或已被消费（重复提交）, userId={}, token={}", userId, token);
            return OrderResult.duplicate("订单已提交，请勿重复操作");
        }

        // ====== 第二层防重：分布式锁 ======
        // 防止 Token 校验通过后、订单创建前的并发窗口
        OrderDistributedLock.LockContext lockCtx = null;
        try {
            lockCtx = distributedLock.tryLock(orderKey, 3000, 100);
            if (lockCtx == null) {
                log.warn("[订单提交] 获取分布式锁失败（并发冲突）, orderKey={}", orderKey);
                return OrderResult.fail("系统繁忙，请稍后重试");
            }

            // ====== 第三层防重：数据库幂等校验（Double-Check） ======
            // 即使分布式锁在极端场景下失效，数据库唯一索引仍能兜底
            if (orderRepository.existsByUserIdAndToken(userId, token)) {
                log.warn("[订单提交] 数据库幂等校验命中（极端场景兜底）, userId={}, token={}", userId, token);
                return OrderResult.duplicate("订单已创建");
            }

            // ====== 执行核心业务：创建订单 + 扣减库存 ======
            OrderResult result = doCreateOrder(request, token);

            long holdTime = System.currentTimeMillis() - lockCtx.getAcquiredAt();
            log.info("[订单提交] 订单创建成功, orderId={}, 锁持有时间={}ms",
                    result.getOrderId(), holdTime);

            return result;

        } catch (InsufficientStockException e) {
            log.warn("[订单提交] 库存不足, productId={}, requestQty={}",
                    request.getProductId(), request.getQuantity());
            return OrderResult.fail("商品库存不足");

        } catch (Exception e) {
            log.error("[订单提交] 创建订单异常, orderKey={}", orderKey, e);
            return OrderResult.fail("系统异常，请稍后重试");

        } finally {
            // ====== 释放分布式锁 ======
            if (lockCtx != null) {
                boolean released = distributedLock.unlock(lockCtx);
                if (!released) {
                    log.error("[订单提交] 释放锁失败, lockKey={}", lockCtx.getLockKey());
                }
            }
        }
    }

    /**
     * 核心业务：创建订单 + 扣减库存（事务保证一致性）
     */
    @Transactional(rollbackFor = Exception.class)
    public OrderResult doCreateOrder(OrderRequest request, String token) {
        // 1. 扣减库存（带乐观锁校验，防止超卖）
        boolean deducted = inventoryService.deductStock(
                request.getProductId(), request.getQuantity());
        if (!deducted) {
            throw new InsufficientStockException("库存扣减失败");
        }

        // 2. 创建订单记录
        Order order = new Order();
        order.setOrderId(generateOrderId());
        order.setUserId(request.getUserId());
        order.setProductId(request.getProductId());
        order.setQuantity(request.getQuantity());
        order.setIdempotentToken(token);     // 存储 Token，用于数据库唯一索引兜底
        order.setStatus(OrderStatus.CREATED);
        order.setCreatedAt(System.currentTimeMillis());

        // INSERT 时如果 Token 对应的唯一索引冲突，会抛出 DuplicateKeyException
        // 这是最后一层幂等保障
        orderRepository.insert(order);

        log.info("[订单创建] 订单入库成功, orderId={}, productId={}, quantity={}",
                order.getOrderId(), request.getProductId(), request.getQuantity());

        return OrderResult.success(order.getOrderId());
    }

    private String generateOrderId() {
        return "ORD" + System.currentTimeMillis() + (int) (Math.random() * 10000);
    }
}
```

#### 7.1.5 建表语句与幂等兜底

```sql
CREATE TABLE `t_order` (
    `id`               BIGINT       NOT NULL AUTO_INCREMENT,
    `order_id`         VARCHAR(64)  NOT NULL COMMENT '订单号',
    `user_id`          BIGINT       NOT NULL COMMENT '用户ID',
    `product_id`       BIGINT       NOT NULL COMMENT '商品ID',
    `quantity`          INT          NOT NULL COMMENT '购买数量',
    `idempotent_token` VARCHAR(64)  NOT NULL COMMENT '幂等Token',
    `status`           TINYINT      NOT NULL DEFAULT 0 COMMENT '订单状态',
    `created_at`       BIGINT       NOT NULL COMMENT '创建时间戳',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_order_id` (`order_id`),
    UNIQUE KEY `uk_user_token` (`user_id`, `idempotent_token`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
```

`uk_user_token` 唯一索引是最后一层幂等兜底。即使分布式锁在 Redis 主从切换等极端场景下失效，数据库层面仍能通过唯一索引阻止重复订单的插入。

#### 7.1.6 全链路时序图

```

 │                  │                    │                    │                    │                     │
 │── 点击提交 ──────→│                    │                    │                    │                     │

 │                  │                    │                    │                    │                     │
 │                  │                    │                    │── 启动看门狗(10s续期)│                     │
 │                  │                    │                    │                    │                     │
 │                  │                    │                    │── existsByToken ───→│── SELECT ──────────→│
 │                  │                    │                    │←── false(不存在) ───│←── 0 rows ──────────│
 │                  │                    │                    │                    │                     │
 │                  │                    │                    │── deductStock ─────→│── UPDATE SET        │
 │                  │                    │                    │                    │   stock=stock-1     │
 │                  │                    │                    │                    │   WHERE stock>=1 ──→│
 │                  │                    │                    │←── 扣减成功 ────────│←── affected=1 ──────│
 │                  │                    │                    │                    │                     │
 │                  │                    │                    │── INSERT order ────→│── INSERT ──────────→│
 │                  │                    │                    │←── 插入成功 ────────│←── OK ──────────────│
 │                  │                    │                    │                    │                     │
 │                  │                    │                    │── Lua: GET+DEL ────→│                     │
 │                  │                    │                    │   (释放锁)          │                     │
 │                  │                    │                    │←── 释放成功 ────────│                     │
 │                  │                    │                    │                    │                     │
 │                  │                    │←── 返回结果 ────────│                    │                     │
 │                  │←── 返回结果 ────────│                    │                    │                     │
 │←── 显示结果 ──────│                    │                    │                    │                     │
```

#### 7.1.7 案例小结

| 防重层级 | 机制 | 作用 | 失效场景 |
|---------|------|------|---------|
| 第一层 | 幂等 Token（Redis 原子消费） | 拦截绝大部分重复请求 | Redis 主从切换丢失 Token |
| 第二层 | 分布式锁（SET NX EX + 看门狗） | 防止并发窗口内的重复创建 | Redis 主从切换丢锁 |
| 第三层 | 数据库唯一索引（兜底） | 极端场景下阻止重复插入 | 几乎不会失效 |

三层防重机制层层递进、互为补充，即使前两层在极端情况下同时失效，第三层的数据库唯一索引仍能保证数据的最终一致性。

### 7.2 案例二：Redisson 可重入锁在库存扣减中的应用全链路

#### 7.2.1 业务背景

电商秒杀场景下，商品库存有限（例如 100 件），瞬时涌入大量请求。多个服务实例需要对同一商品的库存执行"读取 → 判断 → 扣减"操作，这是一个典型的 Check-Then-Act 竞态条件问题。

**为什么需要可重入锁？**

在实际业务中，库存扣减逻辑往往不是一个简单的原子操作，而是由多个方法嵌套调用组成的复杂链路。例如：

```
deductStock()  →  加锁
    ├── checkAndDeduct()  →  需要重入锁（校验+扣减）
    │       └── recordDeductLog()  →  需要重入锁（记录扣减流水）
    └── notifyDownstream()  →  锁外执行（不需要锁保护）
```

如果使用不可重入锁，`checkAndDeduct` 内部再次获取锁时会死锁。Redisson 的可重入锁（`RLock`）基于 Hash 结构记录持有者和重入次数，天然支持嵌套调用。

**全链路目标：**

1. 使用 Redisson `RLock` 的 `tryLock` 方法，设置等待时间和持有时间
2. 在嵌套调用场景中正确处理锁的重入和释放
3. 对获取锁超时、业务执行超时、Redis 连接异常等场景做完善的异常处理
4. 库存扣减使用数据库乐观锁（版本号）兜底，防止分布式锁极端失效时的超卖

#### 7.2.2 Redisson 客户端配置

#### 7.2.3 库存扣减服务（含可重入锁全链路）

```java
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.concurrent.TimeUnit;

/**
 * 库存扣减服务 - Redisson 可重入锁全链路实现
 *
 * 加锁策略说明：
 * - 使用 tryLock(waitTime, leaseTime, unit) 非阻塞获取锁
 * - waitTime=3s：最多等待 3 秒获取锁，超时则快速失败
 * - leaseTime=-1（不指定）：启用看门狗自动续期，防止慢 SQL 导致锁提前过期
 * - 如果指定了 leaseTime（如 10s），Redisson 不会启用看门狗，必须自行确保在此时间内完成业务
 */
@Service
public class InventoryDeductService {

    private static final Logger log = LoggerFactory.getLogger(InventoryDeductService.class);

    private static final String LOCK_PREFIX = "inventory:lock:";
    private static final long WAIT_TIME_SECONDS = 3L;
    // 不指定 leaseTime，由 Redisson 看门狗自动续期
    // 如果业务对持有时间有严格要求，可以指定 leaseTime 并禁用看门狗

    private final RedissonClient redissonClient;
    private final InventoryRepository inventoryRepository;
    private final DeductLogRepository deductLogRepository;

    public InventoryDeductService(RedissonClient redissonClient,
                                   InventoryRepository inventoryRepository,
                                   DeductLogRepository deductLogRepository) {
        this.redissonClient = redissonClient;
        this.inventoryRepository = inventoryRepository;
        this.deductLogRepository = deductLogRepository;
    }

    /**
     * 扣减库存（入口方法）
     *
     * @param productId 商品ID
     * @param quantity  扣减数量
     * @param orderId   关联订单号（用于幂等校验和日志追踪）
     * @return 扣减结果
     */
    public DeductResult deductStock(Long productId, int quantity, String orderId) {
        String lockKey = LOCK_PREFIX + productId;
        RLock lock = redissonClient.getLock(lockKey);

        log.info("[库存扣减] 开始, productId={}, quantity={}, orderId={}", productId, quantity, orderId);

        boolean lockAcquired = false;
        try {
            // ====== 获取可重入锁 ======
            // tryLock(waitTime, unit)：不指定 leaseTime，看门狗自动续期
            // 等待 3 秒获取锁，超时返回 false
            lockAcquired = lock.tryLock(WAIT_TIME_SECONDS, TimeUnit.SECONDS);

            if (!lockAcquired) {
                log.warn("[库存扣减] 获取锁超时, lockKey={}, orderId={}", lockKey, orderId);
                return DeductResult.fail("系统繁忙，请稍后重试");
            }

            log.info("[库存扣减] 获取锁成功, lockKey={}, holdCount={}, orderId={}",
                    lockKey, lock.getHoldCount(), orderId);

            // ====== 幂等校验：同一 orderId 不重复扣减 ======
            if (deductLogRepository.existsByOrderId(orderId)) {
                log.warn("[库存扣减] 幂等校验命中, orderId={}", orderId);
                return DeductResult.duplicate("库存已扣减，请勿重复操作");
            }

            // ====== 执行库存扣减（嵌套调用，锁会自动重入） ======
            return checkAndDeduct(productId, quantity, orderId, lock);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("[库存扣减] 获取锁时被中断, lockKey={}, orderId={}", lockKey, orderId, e);
            return DeductResult.fail("操作被中断");

        } catch (Exception e) {
            log.error("[库存扣减] 业务执行异常, productId={}, orderId={}", productId, orderId, e);
            return DeductResult.fail("系统异常: " + e.getMessage());

        } finally {
            // ====== 释放锁 ======
            // 必须检查当前线程是否持有锁，避免释放其他线程的锁
            if (lockAcquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.info("[库存扣减] 释放锁成功, lockKey={}, orderId={}", lockKey, orderId);
            } else if (lockAcquired) {
                log.error("[库存扣减] 锁已不被当前线程持有(可能已过期), lockKey={}, orderId={}",
                        lockKey, orderId);
            }
        }
    }

    /**
     * 校验库存并执行扣减（重入锁场景）
     * 此方法在 deductStock 持有锁的上下文中被调用，锁会自动重入
     */
    private DeductResult checkAndDeduct(Long productId, int quantity, String orderId, RLock lock) {
        // ====== 演示重入：在已持有锁的情况下再次获取同一把锁 ======
        // 注意：可重入锁允许同一线程多次获取，holdCount 会递增
        // 这里是为了演示重入机制，实际业务中如果确定调用链路都在同一线程，
        // 可以不需要在内部方法中再次显式加锁
        boolean reentrantAcquired = false;
        try {
            reentrantAcquired = lock.tryLock(1, TimeUnit.SECONDS);
            if (!reentrantAcquired) {
                // 对于可重入锁，同一线程再次获取不应失败
                // 如果失败，说明锁可能已丢失
                log.error("[库存扣减] 重入获取锁失败(锁可能已丢失), productId={}", productId);
                return DeductResult.fail("锁状态异常");
            }

            log.debug("[库存扣减] 重入获取锁成功, holdCount={}", lock.getHoldCount());

            // 1. 查询当前库存
            Inventory inventory = inventoryRepository.findByProductId(productId);
            if (inventory == null) {
                log.warn("[库存扣减] 商品不存在, productId={}", productId);
                return DeductResult.fail("商品不存在");
            }

            // 2. 校验库存是否充足
            if (inventory.getStock() < quantity) {
                log.warn("[库存扣减] 库存不足, productId={}, currentStock={}, requestQty={}",
                        productId, inventory.getStock(), quantity);
                return DeductResult.fail("库存不足");
            }

            // 3. 执行扣减（数据库乐观锁兜底）
            boolean updated = doDeductWithOptimisticLock(inventory, quantity);
            if (!updated) {
                log.warn("[库存扣减] 乐观锁冲突(并发竞争), productId={}", productId);
                return DeductResult.fail("操作冲突，请重试");
            }

            // 4. 记录扣减流水（嵌套调用，锁再次重入）
            recordDeductLog(productId, quantity, orderId, lock);

            return DeductResult.success(inventory.getStock() - quantity);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return DeductResult.fail("操作被中断");
        } finally {
            // 释放重入层级（holdCount 减 1，不会真正释放锁）
            if (reentrantAcquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.debug("[库存扣减] 释放重入层级, holdCount={}", lock.getHoldCount());
            }
        }
    }

    /**
     * 数据库乐观锁扣减库存
     * 使用 version 字段做 CAS，防止分布式锁极端失效时的超卖
     *
     * UPDATE t_inventory
     * SET stock = stock - #{quantity}, version = version + 1
     * WHERE product_id = #{productId} AND version = #{version} AND stock >= #{quantity}
     */
    private boolean doDeductWithOptimisticLock(Inventory inventory, int quantity) {
        int maxRetries = 3;
        for (int i = 0; i < maxRetries; i++) {
            try {
                int affected = inventoryRepository.deductWithVersion(
                        inventory.getProductId(), quantity, inventory.getVersion());
                if (affected > 0) {
                    log.info("[库存扣减] 乐观锁扣减成功, productId={}, deductQty={}, version={}",
                            inventory.getProductId(), quantity, inventory.getVersion());
                    return true;
                }
                // 版本号冲突，重新加载库存数据后重试
                inventory = inventoryRepository.findByProductId(inventory.getProductId());
                if (inventory == null || inventory.getStock() < quantity) {
                    return false;
                }
            } catch (OptimisticLockingFailureException e) {
                log.warn("[库存扣减] 乐观锁冲突, 重试次数={}/{}", i + 1, maxRetries);
                if (i == maxRetries - 1) {
                    return false;
                }
            }
        }
        return false;
    }

    /**
     * 记录扣减流水（锁再次重入）
     */
    private void recordDeductLog(Long productId, int quantity, String orderId, RLock lock) {
        boolean reentrantAcquired = false;
        try {
            reentrantAcquired = lock.tryLock(1, TimeUnit.SECONDS);
            log.debug("[库存扣减] 流水记录-重入获取锁, holdCount={}", lock.getHoldCount());

            DeductLog deductLog = new DeductLog();
            deductLog.setProductId(productId);
            deductLog.setQuantity(quantity);
            deductLog.setOrderId(orderId);
            deductLog.setCreatedAt(System.currentTimeMillis());

            deductLogRepository.insert(deductLog);
            log.info("[库存扣减] 扣减流水记录成功, orderId={}", orderId);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("[库存扣减] 记录流水时被中断, orderId={}", orderId, e);
        } finally {
            if (reentrantAcquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.debug("[库存扣减] 流水记录-释放重入层级, holdCount={}", lock.getHoldCount());
            }
        }
    }
}
```

#### 7.2.5 可重入锁状态变化图

```
时间线（同一线程内的调用链路）：

deductStock() 调用：
  lock.tryLock()     →  Redis Hash: { "uuid:threadId": 1 }   holdCount=1
    │
    ├── checkAndDeduct() 调用：
    │     lock.tryLock()   →  Redis Hash: { "uuid:threadId": 2 }   holdCount=2
    │       │
    │       ├── recordDeductLog() 调用：
    │       │     lock.tryLock() →  Redis Hash: { "uuid:threadId": 3 }   holdCount=3
    │       │     lock.unlock()  →  Redis Hash: { "uuid:threadId": 2 }   holdCount=2
    │       │
    │     lock.unlock()   →  Redis Hash: { "uuid:threadId": 1 }   holdCount=1
    │
  lock.unlock()     →  Redis DEL lock_key                        holdCount=0（锁释放）
```

**关键要点：**
- 每次 `tryLock` 成功时 `holdCount` 加 1，Redis Hash 中的重入次数也加 1
- 每次 `unlock` 时 `holdCount` 减 1，Redis Hash 中的重入次数也减 1
- 只有 `holdCount` 归零时，锁才会真正释放（Redis 中的 key 被删除）
- 看门狗在 `holdCount > 0` 期间持续续期，`holdCount` 归零后自动停止

#### 7.2.6 异常场景处理矩阵

| 异常场景 | 表现 | 处理策略 | 代码位置 |
|---------|------|---------|---------|
| tryLock 等待超时 | `tryLock` 返回 `false` | 快速失败，返回"系统繁忙" | `deductStock` |
| 获取锁时线程中断 | 抛出 `InterruptedException` | 恢复中断标志，返回失败 | `deductStock` catch 块 |
| 重入获取锁失败 | `tryLock` 返回 `false` | 说明锁已丢失，返回锁状态异常 | `checkAndDeduct` |
| 业务执行中锁过期 | 看门狗自动续期，正常不会过期 | 指定 leaseTime 时需自行控制 | 看门狗机制 |
| 数据库乐观锁冲突 | `affected = 0` | 重新加载数据，最多重试 3 次 | `doDeductWithOptimisticLock` |
| 释放锁时非当前线程 | `isHeldByCurrentThread()` 为 `false` | 记录错误日志，不执行释放 | `deductStock` finally 块 |
| Redis 连接异常 | Redisson 内部抛出异常 | 外层 catch 捕获，返回系统异常 | `deductStock` catch 块 |

### 7.3 案例三：RedLock 在跨机房场景中的应用全链路

#### 7.3.1 业务背景

金融清结算系统部署在北京和上海两个机房，采用双活架构。每日凌晨执行清算任务时，必须保证全局只有一个实例在执行，避免重复清算导致资金错误。

**为什么不用单实例 Redis 锁？**

- 单实例 Redis 存在主从切换丢锁风险，对金融场景不可接受
- 跨机房网络延迟较高（通常 2-5ms），需要考虑网络超时对锁获取的影响
- 单一 Redis 集群如果部署在一个机房，该机房整体故障时锁服务完全不可用

**为什么不用 ZooKeeper？**

- ZK 是 CP 系统，在网络分区时牺牲可用性，清算任务可能无法启动
- 清算任务本身具备幂等性（可通过清算批次号控制），容忍极低概率的锁失效
- 团队已有 Redis 运维经验，不想引入 ZK 增加运维负担

**RedLock 方案：**

在 5 个独立的 Redis 实例（2 个在北京、2 个在上海、1 个在深圳）上执行 RedLock 算法，需要至少 3 个实例加锁成功才认为获取锁成功。

#### 7.3.2 RedLock 管理器（含时钟漂移补偿）

```java
import org.redisson.Redisson;
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.redisson.config.Config;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

import javax.annotation.PostConstruct;
import javax.annotation.PreDestroy;
import java.util.*;
import java.util.concurrent.*;

/**
 * RedLock 管理器
 * 基于 Redisson RedLock 实现跨机房分布式锁
 *
 * 部署架构：
 * - 5 个独立 Redis 实例（非主从、非集群关系）
 * - 北京机房：redis-bj-1, redis-bj-2
 * - 上海机房：redis-sh-1, redis-sh-2
 * - 深圳机房：redis-sz-1
 * - 多数派 quorum = 3
 */
@Component
public class RedLockManager {

    private static final Logger log = LoggerFactory.getLogger(RedLockManager.class);

    /**
     * 时钟漂移补偿因子
     * RedLock 的有效时间需要减去时钟漂移的影响
     * 实际有效时间 = TTL - (T2 - T1) - CLOCK_DRIFT_FACTOR * TTL
     * Martin Kleppmann 建议预留 2% 的时钟漂移余量
     */
    private static final double CLOCK_DRIFT_FACTOR = 0.02;

    /**
     * 5 个独立的 Redisson 客户端
     */
    private final List<RedissonClient> redissonClients = new ArrayList<>();

    /**
     * 各节点地址配置
     */
    private static final String[] REDIS_NODES = {
            "redis://redis-bj-1.example.com:6379",
            "redis://redis-bj-2.example.com:6379",
            "redis://redis-sh-1.example.com:6379",
            "redis://redis-sh-2.example.com:6379",
            "redis://redis-sz-1.example.com:6379"
    };

    @PostConstruct
    public void init() {
        for (String node : REDIS_NODES) {
            Config config = new Config();
            config.useSingleServer()
                    .setAddress(node)
                    .setConnectionPoolSize(16)
                    .setConnectionMinimumIdleSize(4)
                    .setConnectTimeout(3000)
                    .setTimeout(2000)
                    .setRetryAttempts(1)           // 快速失败，不做过多重试
                    .setRetryInterval(500);

            try {
                RedissonClient client = Redisson.create(config);
                redissonClients.add(client);
                log.info("[RedLock] Redis节点初始化成功: {}", node);
            } catch (Exception e) {
                log.error("[RedLock] Redis节点初始化失败: {}", node, e);
                // 某个节点初始化失败不影响其他节点
                // 但如果失败节点数超过 N - quorum，RedLock 将无法工作
            }
        }

        int quorum = redissonClients.size() / 2 + 1;
        log.info("[RedLock] 初始化完成, 可用节点数={}, 多数派阈值={}",
                redissonClients.size(), quorum);

        if (redissonClients.size() < 3) {
            log.error("[RedLock] 可用节点数不足3个，RedLock 无法保证正确性！");
        }
    }

    @PreDestroy
    public void destroy() {
        for (RedissonClient client : redissonClients) {
            try {
                client.shutdown();
            } catch (Exception e) {
                log.warn("[RedLock] Redis节点关闭异常", e);
            }
        }
    }

    /**
     * 使用 RedLock 算法获取分布式锁
     *
     * @param resource     资源名称
     * @param ttlMs        锁过期时间（毫秒）
     * @param waitTimeMs   最大等待时间（毫秒）
     * @return RedLockContext，null 表示获取失败
     */
    public RedLockContext tryLock(String resource, long ttlMs, long waitTimeMs) {
        String lockKey = "redlock:" + resource;
        String lockValue = UUID.randomUUID().toString();
        int quorum = redissonClients.size() / 2 + 1;
        long deadline = System.currentTimeMillis() + waitTimeMs;

        log.info("[RedLock] 开始获取锁, resource={}, ttlMs={}, quorum={}",
                resource, ttlMs, quorum);

        while (System.currentTimeMillis() < deadline) {
            long startTime = System.currentTimeMillis();
            int successCount = 0;
            List<Integer> successNodes = new ArrayList<>();

            // ====== 步骤1：依次向所有节点请求加锁 ======
            for (int i = 0; i < redissonClients.size(); i++) {
                try {
                    RedissonClient client = redissonClients.get(i);
                    RLock lock = client.getLock(lockKey);

                    // 每个节点使用极短的等待时间（跨机房延迟通常 2-5ms）
                    boolean acquired = lock.tryLock(50, ttlMs, TimeUnit.MILLISECONDS);
                    if (acquired) {
                        successCount++;
                        successNodes.add(i);
                        log.debug("[RedLock] 节点{}加锁成功, node={}", i, REDIS_NODES[i]);
                    } else {
                        log.debug("[RedLock] 节点{}加锁失败, node={}", i, REDIS_NODES[i]);
                    }
                } catch (Exception e) {
                    log.warn("[RedLock] 节点{}加锁异常, node={}", i, REDIS_NODES[i], e);
                    // 单节点异常不影响全局判断
                }
            }

            long endTime = System.currentTimeMillis();
            long elapsed = endTime - startTime;

            // ====== 步骤2：计算时钟漂移补偿后的有效时间 ======
            long clockDrift = (long) (ttlMs * CLOCK_DRIFT_FACTOR) + 2; // 额外加 2ms 容错
            long validityTime = ttlMs - elapsed - clockDrift;

            // ====== 步骤3：判断是否获取锁成功 ======
            if (successCount >= quorum && validityTime > 0) {
                log.info("[RedLock] 获取锁成功, resource={}, successNodes={}, " +
                                "elapsed={}ms, validityTime={}ms, clockDrift={}ms",
                        resource, successNodes, elapsed, validityTime, clockDrift);

                return new RedLockContext(lockKey, lockValue, successNodes,
                        validityTime, redissonClients);
            }

            // ====== 步骤4：获取失败，释放所有已加锁的节点 ======
            log.warn("[RedLock] 获取锁失败(未达多数派), resource={}, successCount={}/{}, " +
                            "elapsed={}ms, validityTime={}ms",
                    resource, successCount, quorum, elapsed, validityTime);

            releaseAllNodes(lockKey, redissonClients);

            // 随机延迟后重试，避免多个客户端同时重试导致活锁
            try {
                long retryDelay = ThreadLocalRandom.current().nextLong(50, 200);
                Thread.sleep(retryDelay);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                log.warn("[RedLock] 重试等待被中断, resource={}", resource);
                return null;
            }
        }

        log.warn("[RedLock] 获取锁超时, resource={}, waitTimeMs={}", resource, waitTimeMs);
        return null;
    }

    /**
     * 释放 RedLock
     */
    public void unlock(RedLockContext context) {
        if (context == null) {
            return;
        }
        releaseAllNodes(context.getLockKey(), context.getRedissonClients());
        log.info("[RedLock] 释放锁完成, lockKey={}", context.getLockKey());
    }

    /**
     * 向所有节点发送释放锁请求
     * 必须向所有节点发送（包括加锁失败的节点），防止残留锁数据
     */
    private void releaseAllNodes(String lockKey, List<RedissonClient> clients) {
        for (int i = 0; i < clients.size(); i++) {
            try {
                RedissonClient client = clients.get(i);
                RLock lock = client.getLock(lockKey);
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                    log.debug("[RedLock] 节点{}释放锁成功", i);
                }
            } catch (Exception e) {
                log.warn("[RedLock] 节点{}释放锁异常", i, e);
                // 释放失败不影响其他节点，锁最终会 TTL 过期
            }
        }
    }

    /**
     * RedLock 上下文
     */
    public static class RedLockContext {
        private final String lockKey;
        private final String lockValue;
        private final List<Integer> successNodes;
        private final long validityTime;
        private final List<RedissonClient> redissonClients;
        private final long acquiredAt;

        public RedLockContext(String lockKey, String lockValue, List<Integer> successNodes,
                              long validityTime, List<RedissonClient> redissonClients) {
            this.lockKey = lockKey;
            this.lockValue = lockValue;
            this.successNodes = successNodes;
            this.validityTime = validityTime;
            this.redissonClients = redissonClients;
            this.acquiredAt = System.currentTimeMillis();
        }

        public String getLockKey() { return lockKey; }
        public String getLockValue() { return lockValue; }
        public List<Integer> getSuccessNodes() { return successNodes; }
        public long getValidityTime() { return validityTime; }
        public List<RedissonClient> getRedissonClients() { return redissonClients; }
        public long getAcquiredAt() { return acquiredAt; }

        /**
         * 检查锁是否仍在有效期内
         */
        public boolean isValid() {
            return (System.currentTimeMillis() - acquiredAt) < validityTime;
        }
    }
}
```

#### 7.3.3 清结算任务全链路（含降级策略）

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Service;

/**
 * 清结算任务服务 - RedLock 跨机房全链路实现
 *
 * 策略：
 * 1. 优先使用 RedLock 保证跨机房互斥
 * 2. RedLock 获取失败时降级为单节点 Redis 锁
 * 3. 降级锁也获取失败时放弃本次执行（等待下一个调度周期）
 * 4. 清算任务本身具备幂等性（基于清算批次号），即使极端情况下锁失效也不会重复清算
 */
@Service
public class SettlementTaskService {

    private static final Logger log = LoggerFactory.getLogger(SettlementTaskService.class);

    private static final String SETTLEMENT_LOCK_RESOURCE = "settlement:daily-clearing";
    private static final long LOCK_TTL_MS = 600_000L;       // 锁 TTL 10 分钟
    private static final long LOCK_WAIT_MS = 10_000L;       // 等待 10 秒
    private static final long DEGRADED_LOCK_TTL_MS = 300_000L; // 降级锁 TTL 5 分钟

    private final RedLockManager redLockManager;
    private final SettlementRepository settlementRepository;
    private final NotificationService notificationService;

    public SettlementTaskService(RedLockManager redLockManager,
                                  SettlementRepository settlementRepository,
                                  NotificationService notificationService) {
        this.redLockManager = redLockManager;
        this.settlementRepository = settlementRepository;
        this.notificationService = notificationService;
    }

    /**
     * 每日清算定时任务
     * 每日凌晨 2:00 执行
     */
    @Scheduled(cron = "0 0 2 * * ?")
    public void dailySettlement() {
        // 生成清算批次号（日期维度唯一，用于幂等控制）
        String batchNo = generateBatchNo();

        log.info("[清算任务] 开始执行, batchNo={}", batchNo);

        // ====== 幂等校验：检查该批次是否已经完成 ======
        if (settlementRepository.existsByBatchNo(batchNo)) {
            log.info("[清算任务] 批次已完成, batchNo={}", batchNo);
            return;
        }

        // ====== 策略1：尝试 RedLock ======
        RedLockManager.RedLockContext lockCtx = null;
        boolean useDegraded = false;

        try {
            lockCtx = redLockManager.tryLock(SETTLEMENT_LOCK_RESOURCE, LOCK_TTL_MS, LOCK_WAIT_MS);

            if (lockCtx != null) {
                log.info("[清算任务] RedLock 获取成功, successNodes={}, validityTime={}ms",
                        lockCtx.getSuccessNodes(), lockCtx.getValidityTime());

                // 在 validityTime 内完成清算
                executeSettlement(batchNo, lockCtx);
                return;
            }

            // ====== 策略2：RedLock 失败，降级为单节点锁 ======
            log.warn("[清算任务] RedLock 获取失败, 尝试降级为单节点锁");
            useDegraded = true;

            lockCtx = tryDegradedLock(SETTLEMENT_LOCK_RESOURCE, DEGRADED_LOCK_TTL_MS);
            if (lockCtx != null) {
                log.warn("[清算任务] 降级锁获取成功, 注意：降级模式下锁可靠性降低");
                notificationService.alert("清算任务使用降级锁",
                        "RedLock 获取失败，已降级为单节点锁。请检查 Redis 集群状态。");

                executeSettlement(batchNo, lockCtx);
                return;
            }

            // ====== 策略3：降级锁也失败，放弃本次执行 ======
            log.error("[清算任务] 所有锁策略失败, batchNo={}", batchNo);
            notificationService.alert("清算任务未执行",
                    "RedLock 和降级锁均获取失败，清算任务本次未执行。请人工检查并补偿。");

        } catch (Exception e) {
            log.error("[清算任务] 执行异常, batchNo={}", batchNo, e);
            notificationService.alert("清算任务异常",
                    "batchNo=" + batchNo + ", error=" + e.getMessage());
        } finally {
            if (lockCtx != null) {
                if (useDegraded) {
                    releaseDegradedLock(lockCtx);
                } else {
                    redLockManager.unlock(lockCtx);
                }
            }
        }
    }

    /**
     * 执行清算业务
     * 在锁保护下执行，需要检查锁是否仍然有效
     */
    private void executeSettlement(String batchNo, RedLockManager.RedLockContext lockCtx) {
        log.info("[清算任务] 开始执行清算逻辑, batchNo={}", batchNo);

        // ====== 创建清算批次记录（标记为处理中） ======
        SettlementBatch batch = new SettlementBatch();
        batch.setBatchNo(batchNo);
        batch.setStatus(BatchStatus.PROCESSING);
        batch.setStartTime(System.currentTimeMillis());
        settlementRepository.insertBatch(batch);

        try {
            // ====== 分批处理清算数据 ======
            int totalCount = 0;
            int pageNo = 1;
            int pageSize = 1000;

            while (true) {
                // 每批处理前检查锁是否仍然有效
                if (!lockCtx.isValid()) {
                    log.error("[清算任务] 锁已失效(validityTime超时), batchNo={}, " +
                                    "已处理={}条, 剩余数据需人工补偿",
                            batchNo, totalCount);
                    notificationService.alert("清算锁提前失效",
                            "batchNo=" + batchNo + ", 已处理=" + totalCount + "条");
                    // 标记批次为部分完成
                    settlementRepository.updateBatchStatus(batchNo, BatchStatus.PARTIAL);
                    return;
                }

                List<SettlementItem> items = settlementRepository.queryPending(pageNo, pageSize);
                if (items.isEmpty()) {
                    break;
                }

                for (SettlementItem item : items) {
                    processSettlementItem(item, batchNo);
                    totalCount++;
                }

                pageNo++;

                log.info("[清算任务] 处理进度, batchNo={}, page={}, totalProcessed={}, " +
                                "锁剩余有效时间={}ms",
                        batchNo, pageNo - 1, totalCount,
                        lockCtx.getValidityTime() - (System.currentTimeMillis() - lockCtx.getAcquiredAt()));
            }

            // ====== 标记批次完成 ======
            settlementRepository.updateBatchStatus(batchNo, BatchStatus.COMPLETED);

            log.info("[清算任务] 清算完成, batchNo={}, totalCount={}, 耗时={}ms",
                    batchNo, totalCount, System.currentTimeMillis() - batch.getStartTime());

        } catch (Exception e) {
            settlementRepository.updateBatchStatus(batchNo, BatchStatus.FAILED);
            throw e;
        }
    }

    /**
     * 处理单条清算记录（幂等）
     */
    private void processSettlementItem(SettlementItem item, String batchNo) {
        // 幂等校验：已清算的记录跳过
        if (item.getStatus() == ItemStatus.SETTLED) {
            return;
        }

        try {
            // 执行清算计算
            long settlementAmount = calculateSettlement(item);

            // 更新清算状态（带乐观锁）
            int affected = settlementRepository.updateItemStatus(
                    item.getId(), ItemStatus.SETTLED, batchNo, settlementAmount, item.getVersion());

            if (affected == 0) {
                log.warn("[清算任务] 乐观锁冲突, itemId={}", item.getId());
            }
        } catch (Exception e) {
            log.error("[清算任务] 单条清算异常, itemId={}, batchNo={}", item.getId(), batchNo, e);
            settlementRepository.updateItemStatus(
                    item.getId(), ItemStatus.FAILED, batchNo, 0L, item.getVersion());
        }
    }

    /**
     * 降级锁：使用第一个可用的 Redis 节点获取单实例锁
     */
    private RedLockManager.RedLockContext tryDegradedLock(String resource, long ttlMs) {
        // 降级为单节点模式，不提供跨机房互斥保障
        // 但仍优于完全无锁
        return redLockManager.tryLock(resource, ttlMs, 5000);
    }

    private void releaseDegradedLock(RedLockManager.RedLockContext context) {
        redLockManager.unlock(context);
    }

    private long calculateSettlement(SettlementItem item) {
        // 清算金额计算逻辑
        return item.getAmount() - item.getFee();
    }

    private String generateBatchNo() {
        java.time.LocalDate today = java.time.LocalDate.now();
        return "SETTLE-" + today.toString().replace("-", "");
    }
}
```

#### 7.3.4 时钟漂移处理策略

RedLock 算法的正确性依赖于各 Redis 实例的系统时钟不发生大幅跳跃。在跨机房场景中，时钟漂移问题更加突出。

**时钟漂移的来源：**

| 来源 | 漂移幅度 | 发生概率 |
|------|---------|--------|
| NTP 同步调整 | 通常 < 1ms，偶尔 10-100ms | 高 |
| 虚拟机迁移（vMotion） | 可达秒级 | 低 |
| 闰秒 | 1 秒 | 极低（约每 1.5 年一次） |
| 硬件时钟偏差 | 累积效应，每日数十毫秒 | 持续发生 |

**代码中的时钟漂移补偿逻辑解析：**

```
锁的实际有效时间计算公式：
validityTime = TTL - elapsed - clockDrift

其中：
- TTL = 600,000ms（10 分钟）
- elapsed = 加锁过程消耗的时间（依次请求 5 个节点）
- clockDrift = TTL * 0.02 + 2ms = 12,002ms

示例：
- TTL = 600,000ms
- elapsed = 150ms（5 个节点加锁总耗时）
- clockDrift = 12,002ms
- validityTime = 600,000 - 150 - 12,002 = 587,848ms ≈ 9 分 48 秒

即：10 分钟的 TTL，实际可用时间约 9 分 48 秒，预留了约 12 秒的时钟漂移容错
```

**运维侧的时钟漂移防护措施：**

1. 所有 Redis 实例和业务服务器配置 NTP 同步，偏差控制在 1ms 以内
2. NTP 使用 `slew` 模式而非 `step` 模式，避免时钟突变
3. 避免在虚拟机上部署 Redis 实例（时钟不稳定）
4. 监控各节点的时钟偏差，超过 10ms 时告警

#### 7.3.5 降级策略详解

```
                    ┌────────────────────┐
                    │    清算任务触发      │
                    └─────────┬──────────┘
                              │
                    ┌─────────▼──────────┐
                    │   幂等校验          │
                    │ (批次号是否已完成)   │
                    └─────────┬──────────┘
                              │ 未完成
                    ┌─────────▼──────────┐
                    │  策略1: RedLock     │
                    │  (5节点多数派)      │
                    └────┬─────────┬─────┘
                    成功 │         │ 失败
               ┌─────────▼──┐  ┌──▼──────────────┐
               │  执行清算   │  │ 策略2: 降级锁    │
               │  (锁有效期  │  │ (单节点Redis锁) │
               │   内完成)   │  └────┬───────┬────┘
               └────────────┘  成功 │       │ 失败
                          ┌────────▼───┐ ┌─▼──────────────┐
                          │ 执行清算    │ │ 策略3: 放弃     │
                          │ + 告警通知  │ │ 等待下次调度    │
                          │ (可靠性降低)│ │ + 告警通知      │
                          └────────────┘ │ + 人工介入      │
                                         └────────────────┘
```

**降级决策矩阵：**

| 场景 | 可用节点数 | 多数派是否达成 | 降级决策 |
|------|-----------|-------------|---------|
| 全部正常 | 5 | 是 | 不降级，正常 RedLock |
| 1 节点宕机 | 4 | 是（≥3） | 不降级，正常 RedLock |
| 2 节点宕机 | 3 | 是（=3） | 不降级，但余量为 0 |
| 3 节点宕机 | 2 | 否（<3） | 降级为单节点锁 |
| 北京机房整体故障 | 3 | 是（上海2+深圳1） | 不降级 |
| 上海机房整体故障 | 3 | 是（北京2+深圳1） | 不降级 |
| 北京+深圳故障 | 2 | 否 | 降级为单节点锁 |
| 全部不可用 | 0 | 否 | 放弃，告警 |

#### 7.3.6 案例小结

| 设计要点 | 实现方式 | 作用 |
|---------|---------|------|
| 跨机房互斥 | 5 节点 RedLock，3 节点多数派 | 单机房故障不影响锁的可用性 |
| 时钟漂移补偿 | validityTime 扣除 2% 漂移量 | 避免时钟跳跃导致锁提前过期 |
| 锁有效性检查 | 每批数据处理前检查 `isValid()` | 防止锁过期后继续操作共享资源 |
| 三级降级策略 | RedLock → 单节点锁 → 放弃+告警 | 逐级降级，优雅应对不同故障 |
| 幂等控制 | 清算批次号 + 乐观锁 + 状态机 | 即使锁失效也不会重复清算 |
| 部分完成处理 | 锁过期时标记 PARTIAL 状态 | 支持后续人工补偿 |
| 监控告警 | 降级和异常时发送告警 | 运维及时感知，快速介入 |
