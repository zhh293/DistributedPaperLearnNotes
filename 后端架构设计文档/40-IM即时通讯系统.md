# IM 即时通讯系统架构设计

## 一、问题背景

在大型互联网公司中，即时通讯（IM）是一个基础公共服务，需要支撑公司全业务线的沟通需求。包括但不限于：消费者与商家客服之间的单聊、骑手与站长的群聊、系统服务号向用户推送消息、设备端数据透传等场景。

核心挑战包括：

1. **连接可靠性**：移动端网络环境复杂（弱网、频繁切换WiFi/4G、后台进程被杀），需要保证长连接的稳定性，连接成功率需达到99%以上
2. **消息必达性**：消息不能丢失，存储成功率需达到99.9999%，在线投递率需达到92%~98%
3. **低延迟**：在线消息投递延迟，WiFi环境下P90需在200ms以内，移动网络下P90需在1s以内
4. **高吞吐**：日均处理数十亿级数据包，单聊群聊消息日流转量达到亿级
5. **多端多App**：同一用户可能在不同App、不同设备上同时在线，需要支持跨App通信和多端同步
6. **数据安全**：全链路TLS加密传输，本地存储加密，通信数据不可被中间人抓包窃取

如果不解决这些问题，用户沟通体验会严重退化，业务方（如外卖配送、商家客服）的核心业务流程将受阻。

### 2.2 各层职责说明

**信令接入层**是整个IM系统的门面，负责维护客户端的长连接。长连接服务部署在多机房（如光环、永丰、贤人、兆丰等），通过DNS解析为不同机房配置独立的TCP接入域名，客户端根据DNS解析结果连接到最近的接入点。接入负载均衡服务负责登录时的流量分发，支持多种可配置的负载均衡策略。节点注册与发现服务支持信令节点的无缝增删，当某个节点故障时可以自动摘除。

**认证与在线管理层**负责用户身份校验和在线状态维护。长连认证服务处理SDK用户的登录认证，验证Token有效性。在线状态管理服务通过Redis集群读写用户在线状态表，记录用户当前连接的网关节点。上下线通知服务通过Thrift或消息队列向业务方推送用户上下线事件。香港部署了独立的接入点，支持境外用户的网络体验。

**IM逻辑层**是消息处理的核心。单群聊代理服务作为入口，将消息分类投递到单聊逻辑服务或群聊逻辑服务。单聊逻辑服务负责消息转发，群聊逻辑服务负责群聊消息的扩散。服务号下行逻辑服务从消息队列消费消息并推送到终端。数据透传服务处理不关心消息体内容的二进制数据传递。

**消息存储层**采用异步持久化架构（详见核心链路设计）。存储代理服务作为消息写入的统一入口，将消息写入消息队列，然后由多个消费者异步写入不同存储介质：Redis/分布式KV用于消息体缓存，MySQL用于热数据，HBase用于冷数据。

**消息读取与回调层**提供消息查询API和业务回调能力。消息读取服务处理客户端的会话列表、历史消息、离线消息查询请求。已读同步服务负责多端已读状态同步。回调服务将IM消息实时回调给接入SDK的业务方后端。

## 三、核心链路设计

### 3.1 长连接管理全链路

长连接是IM系统的基石，所有在线消息收发都依赖长连接。以下是长连接从建立到断开的完整生命周期。

#### 3.1.1 连接建立流程

```
1. 客户端启动，请求接入负载均衡服务获取接入点
       │
       ▼
2. 负载均衡服务根据策略（地理位置/机房负载/IPHash）返回长连接服务地址
       │
       ▼
3. 客户端向长连接服务发起TCP连接（或WebSocket连接）
       │
       ▼
4. 长连接服务接收到连接后，将认证请求转发给长连认证服务
       │
       ▼
5. 认证服务校验Token：
   a) 从Redis集群读取用户alToken，校验客户端Token有效性
   b) 从Redis集群读取xsid（长连鉴权凭证），校验连接合法性
   c) 校验通过后，返回用户基础信息（uid、appId、channel等）
       │
       ▼
6. 长连接服务向在线状态管理服务注册用户在线：
   a) 在Redis中写入 uid -> {gatewayNodeId, connectionId, appId, deviceType} 映射
   b) 设置TTL（与心跳周期匹配），超时自动过期
       │
       ▼
7. 上下线通知服务感知到用户上线，通过Thrift/MQ通知业务方
       │
       ▼
8. 长连接服务向客户端返回登录成功，连接建立完成
```

**设计模式与算法**：

- **一致性哈希**：负载均衡服务在分配接入点时，使用一致性哈希将同一用户尽量路由到同一网关节点，减少在线状态迁移
- **装饰器模式**：认证流程中，Token校验、xsid校验、设备校验等步骤层层嵌套，每层增加一层认证逻辑
- **TTL+心跳双重保活**：在线状态在Redis中设置TTL，客户端定期发送心跳包刷新TTL。如果心跳超时，Redis中的在线状态自动过期，实现隐式下线

```java
public class ConnectionAuthService {
    private final RedisCluster onlineStatusStore;  // 在线状态Redis集群
    private final TokenValidator tokenValidator;    // Token校验
    private final XsidValidator xsidValidator;      // xsid校验
    
    private static final int ONLINE_TTL_SECONDS = 120;  // 在线状态TTL，2倍心跳周期
    
    public AuthResult authenticate(ConnectionContext ctx) {
        // 1. Token校验（装饰器模式：逐层校验）
        TokenInfo tokenInfo = tokenValidator.validate(ctx.getAlToken());
        if (!tokenInfo.isValid()) {
            return AuthResult.fail("token invalid");
        }
        
        // 2. xsid长连鉴权校验
        XsidInfo xsidInfo = xsidValidator.validate(ctx.getXsid());
        if (!xsidInfo.isValid()) {
            return AuthResult.fail("xsid invalid");
        }
        
        // 3. 构建在线状态信息
        OnlineStatus status = new OnlineStatus();
        status.setUid(tokenInfo.getUid());
        status.setGatewayNodeId(ctx.getGatewayNodeId());
        status.setConnectionId(ctx.getConnectionId());
        status.setAppId(tokenInfo.getAppId());
        status.setChannel(tokenInfo.getChannel());
        status.setDeviceType(ctx.getDeviceType());
        status.setLoginTime(System.currentTimeMillis());
        
        // 4. 写入Redis在线状态表（TTL = 2倍心跳周期）
        String key = "online:" + tokenInfo.getUid() + ":" + tokenInfo.getAppId();
        onlineStatusStore.setex(key, ONLINE_TTL_SECONDS, status.toJson());
        
        // 5. 发布上线通知（通过消息队列异步通知业务方）
        publishOnlineEvent(status);
        
        return AuthResult.success(tokenInfo.getUid(), tokenInfo.getAppId());
    }
}
```

#### 3.1.2 心跳保活机制

心跳保活的核心思路是**时间轮算法**。当连接建立后，连接被注册到时间轮的一个slot中。时间轮按心跳周期转动，每次转动检查slot中的连接是否在当前周期内收到过心跳包。如果收到过，将连接移动到下一个slot；如果没有收到，触发断线检测。

```
心跳保活流程：
┌─────────────┐     ┌─────────────┐     ┌─────────────────┐
│ 客户端发送    │────▶│ 网关收到心跳  │────▶│ 刷新时间轮slot   │
│ 心跳包       │     │ 更新最后活跃  │     │ 刷新Redis TTL   │
│ (每60s)     │     │ 时间         │     │                 │
└─────────────┘     └─────────────┘     └─────────────────┘

超时检测流程：
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 时间轮转动到     │────▶│ 检查slot中的连接 │────▶│ 超时：触发断线   │
│ 某个slot        │     │ 最后活跃时间     │     │ 未超时：移到下个  │
│                 │     │                 │     │ slot            │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

```java
public class HeartbeatManager {
    private final TimeWheel<Connection> timeWheel;  // 时间轮
    private final RedisCluster onlineStatusStore;
    private static final int HEARTBEAT_INTERVAL = 60;  // 心跳周期60秒
    private static final int HEARTBEAT_TIMEOUT = 120;  // 超时时间120秒
    
    public HeartbeatManager() {
        // 时间轮：120个slot，每个slot代表1秒，轮转一圈120秒
        this.timeWheel = new TimeWheel<>(120, 1, TimeUnit.SECONDS);
    }
    
    // 连接建立时注册到时间轮
    public void register(Connection conn) {
        timeWheel.add(conn, HEARTBEAT_TIMEOUT);
    }
    
    // 收到心跳包时刷新
    public void onHeartbeat(Connection conn) {
        conn.setLastActiveTime(System.currentTimeMillis());
        timeWheel.reschedule(conn, HEARTBEAT_TIMEOUT);
        
        // 异步刷新Redis在线状态TTL
        String key = "online:" + conn.getUid() + ":" + conn.getAppId();
        onlineStatusStore.expire(key, HEARTBEAT_TIMEOUT);
    }
    
    // 时间轮超时回调
    public void onTimeout(Connection conn) {
        // 1. 标记连接为断开
        conn.markDisconnected();
        // 2. 从在线状态表删除
        String key = "online:" + conn.getUid() + ":" + conn.getAppId();
        onlineStatusStore.del(key);
        // 3. 发布下线通知
        publishOfflineEvent(conn.getUid(), conn.getAppId());
    }
}
```

#### 3.1.3 断线重连

客户端检测到连接断开后，执行指数退避重连策略：

```
第1次重连：立即
第2次重连：等待1s
第3次重连：等待2s
第4次重连：等待4s
第5次重连：等待8s
第6次及以后：等待30s（上限）
```

重连时，客户端携带已有的Token和xsid直接认证，避免完整的登录流程。如果Token已过期（超过3天），需要重新走完整登录流程。

### 3.2 消息发送完整链路（核心中的核心）

以A给B发送一条单聊消息为例，完整链路如下。**这个流程中最关键的设计是：消息持久化通过消息队列异步完成，而不是同步写存储。**

```
1. A客户端组装消息（本地临时ID + 会话ID + 内容），通过长连接上行发送
       │
       ▼
2. 长连接服务（ComConn）收到上行数据包，解码为统一信令包，透传给信令路由
       │
       ▼
3. 信令路由（Router）根据信令类型，转发至单群聊代理服务（ImProxy）
       │
       ▼
4. 单群聊代理服务（ImProxy）将消息分类，投递给单聊逻辑服务（ImServer）
       │
       ▼
5. 单聊逻辑服务（ImServer）处理消息：
   a) 通过消息ID生成器（IdGenerator）生成全局消息ID
   b) 生成会话内序列号（seqId），用于消息有序性保证
   c) 敏感词过滤检查（Shield服务，弱依赖，调用失败仍能发送）
   d) 将消息发送给存储代理服务（MsgLogic）—— 注意：这里不是直接写DB！
       │
       ▼
6. 存储代理服务（MsgLogic）将消息写入消息队列（MQ）：
   a) 消息写入「单聊群聊消息入库队列」Topic
   b) MQ自身通过副本+刷盘机制保证消息持久化（不丢失）
   c) 写入MQ成功后，立即返回，不等存储层完成 —— 异步持久化！
       │
       ▼
7. 单聊逻辑服务收到存储代理的ACK后，向A回复发送ACK：
   a) ACK携带全局消息ID和seqId
   b) A客户端收到ACK后将本地临时消息状态更新为"已发送"
       │
       ▼
   ┌───┴───────────────────────────────────────────────────────────────┐
   │                                                                   │
   │  以下步骤与步骤7并行执行，互不阻塞                                     │
   │                                                                   │
   ▼                          ▼                                        ▼
8a. 消息队列消费者         8b. 消息下行路由               8c. 消息回调
    (MsgCache)               (JBridge)                     (CallbackWriter)
    消费MQ消息             查询B的在线状态                将消息异步回调给
    写入Redis/分布式KV          ├── B在线：通过路由            接入SDK的业务方
    (消息体缓存)              │   下行推送给B的网关           后端，业务方可以
    写入会话列表              │   B客户端收到后回复           在此做自定义处理
    写入最近消息              │   送达ACK                    （如存储到ES建立
                             └── B离线：写入离线消息         搜索索引）
                                 队列，触发离线推送
                                 (PushLogic服务调用
                                  push平台推送)
       │                          │                             │
       ▼                          ▼                             ▼
9a. 热数据异步写入          9b. (已完成投递)                 9c. (已完成回调)
    (ImHotData)消费
    MQ消息
    写入MySQL
    (历史消息热数据)
       │
       ▼
9d. 冷数据异步写入
    (ImColdData)消费
    MQ消息
    写入HBase
    (历史消息冷数据)
```

**这是整个IM系统最核心的设计：消息队列异步持久化。** 存储代理服务（MsgLogic）将消息写入MQ后立即返回ACK，不等待MySQL/HBase/Redis写入完成。MQ的副本机制和刷盘机制自身已经保证了消息不丢失。下游的多个消费者（MsgCache、ImHotData、ImColdData）各自独立消费MQ消息，写入不同的存储介质。这种设计的好处是：

1. **低延迟**：发送方只需等待一次MQ写入（毫秒级），而不是等待多次DB写入
2. **高可用**：即使MySQL或HBase暂时不可用，消息已经在MQ中，不会丢失，消费者可以在DB恢复后继续消费
3. **解耦**：缓存写入、热数据写入、冷数据写入互不依赖，任何一个失败不影响其他
4. **削峰**：消息高峰期，MQ作为缓冲，DB按自己的节奏消费

```java
// 存储代理服务 —— 消息写入的统一入口
public class MessageStorageProxy {
    private final MQProducer mqProducer;  // 消息队列生产者
    private static final String IM_MSG_TOPIC = "xm-msgbox";  // 单聊群聊消息Topic
    private static final String PUB_MSG_TOPIC = "xm-xaibox"; // 服务号消息Topic
    
    public StoreResult storeMessage(MessageEntity msg) {
        // 1. 消息序列化
        byte[] data = MessageSerializer.serialize(msg);
        
        // 2. 写入MQ消息队列（关键步骤！不是直接写DB）
        MQSendResult result = mqProducer.send(IM_MSG_TOPIC, 
            String.valueOf(msg.getMsgId()), data);
        
        // 3. MQ写入成功即可返回，下游异步消费
        if (result.isSuccess()) {
            return StoreResult.success(msg.getMsgId());
        } else {
            // MQ写入失败，重试
            return retryStore(msg, 3);
        }
    }
}

// 消息缓存消费者 —— 从MQ消费消息，写入Redis/分布式KV缓存
public class MessageCacheConsumer {
    private final MQConsumer mqConsumer;

    }
}
```

#### 3.2.1 单聊逻辑服务的处理细节

单聊逻辑服务在收到消息后，除了触发存储代理写入MQ外，还需要：

1. **生成全局消息ID**：调用IdGenerator服务（基于号段模式），全局唯一
2. **生成会话序列号seqId**：基于Redis的INCR命令，保证同一会话内消息序列号单调递增
3. **敏感词检查**：调用Shield服务（弱依赖，超时或失败不阻塞发送）
4. **消息下行投递**：查询接收方在线状态，在线则通过JBridge下行推送，离线则进入离线推送流程

```java
public class SingleChatService {
    private final IdGenerator idGenerator;           // 消息ID生成器
    private final SeqIdGenerator seqIdGenerator;     // 会话序列号生成器
    private final ShieldService shieldService;       // 敏感词过滤（弱依赖）
    private final MessageStorageProxy storageProxy;  // 存储代理
    private final OnlineStatusService onlineStatus;  // 在线状态查询
    private final MessageRouter messageRouter;       // 下行路由
    private final OfflinePushService offlinePush;    // 离线推送
    
    public SendResult sendMessage(SendMessageRequest req) {
        // 1. 生成全局消息ID（号段模式，一次获取一批ID缓存在本地）
        long msgId = idGenerator.nextId();
        
        // 2. 生成会话内序列号（Redis INCR保证单调递增）
        long seqId = seqIdGenerator.nextSeq(req.getConversationId());
        
        // 3. 构建消息实体
        MessageEntity msg = new MessageEntity();
        msg.setMsgId(msgId);
        msg.setSeqId(seqId);
        msg.setConversationId(req.getConversationId());
        msg.setSenderId(req.getSenderId());
        msg.setReceiverId(req.getReceiverId());
        msg.setContent(req.getContent());
        msg.setMsgType(req.getMsgType());
        msg.setChannel(req.getChannel());
        msg.setAppId(req.getAppId());
        msg.setTimestamp(System.currentTimeMillis());
        
        // 4. 敏感词检查（弱依赖，超时跳过）
        try {
            ShieldResult shieldResult = shieldService.check(msg.getContent());
            if (shieldResult.isBlocked()) {
                return SendResult.rejected("message blocked by shield");
            }
        } catch (Exception e) {
            // 敏感词服务不可用时不阻塞消息发送
            log.warn("shield service unavailable, skip check", e);
        }
        
        // 5. 写入消息队列（异步持久化，关键步骤）
        StoreResult storeResult = storageProxy.storeMessage(msg);
        if (!storeResult.isSuccess()) {
            return SendResult.fail("store failed");
        }
        
        // 6. 查询接收方在线状态，决定投递方式
        Optional<OnlineStatus> receiverStatus = onlineStatus.getOnline(
            req.getReceiverId(), req.getAppId());
        
        if (receiverStatus.isPresent()) {
            // 7a. 接收方在线：通过下行路由推送
            messageRouter.pushDownstream(receiverStatus.get(), msg);
        } else {
            // 7b. 接收方离线：写入离线消息，触发离线推送
            offlinePush.enqueueOfflineMessage(req.getReceiverId(), msg);
            offlinePush.triggerPushNotification(req.getReceiverId(), msg);
        }
        
        return SendResult.success(msgId, seqId);
    }
}
```

#### 3.2.2 下行路由：如何找到接收方的网关节点

下行路由服务（JBridge）的任务是将消息准确投递到接收方当前连接的网关节点。这个过程是一个分布式KV查询：

```
下行路由流程：
1. 从Redis在线状态表读取 receiverId -> {gatewayNodeId, connectionId}
2. 通过gatewayNodeId查找网关节点的RPC地址
3. 通过内部RPC将消息包发送给目标网关节点
4. 网关节点通过connectionId找到具体的TCP连接
5. 将消息通过TCP连接发送给接收方
```

```java
public class MessageDownstreamRouter {
    private final RedisCluster onlineStatusStore;  // 在线状态Redis
    private final GatewayNodeRegistry nodeRegistry; // 网关节点注册表
    private final Map<String, GatewayRpcClient> rpcClients; // 网关RPC客户端池
    
    public void pushDownstream(OnlineStatus status, MessageEntity msg) {
        // 1. 从在线状态中获取网关节点ID
        String gatewayNodeId = status.getGatewayNodeId();
        String connectionId = status.getConnectionId();
        
        // 2. 查找网关节点的RPC地址（从节点注册表）
        String gatewayAddr = nodeRegistry.getNodeAddress(gatewayNodeId);
        if (gatewayAddr == null) {
            // 网关节点已下线，走离线推送兜底
            offlinePushService.enqueueOfflineMessage(msg.getReceiverId(), msg);
            return;
        }
        
        // 3. 构建下行信令包
        DownlinkPacket packet = new DownlinkPacket();
        packet.setConnectionId(connectionId);
        packet.setCommand(SignalCommand.MSG_RECEIVE);
        packet.setPayload(MessageSerializer.serialize(msg));
        
        // 4. 通过RPC发送给目标网关节点
        GatewayRpcClient client = rpcClients.get(gatewayAddr);
        try {
            client.push(packet);
        } catch (RpcException e) {
            // 网关节点不可达，重试一次后走离线推送
            log.error("push to gateway failed, gateway={}", gatewayNodeId, e);
            offlinePushService.enqueueOfflineMessage(msg.getReceiverId(), msg);
        }
    }
}
```

### 3.3 群聊消息扩散设计

群聊消息的扩散是IM系统中最复杂的部分之一。核心问题是：一条群消息需要投递给群内所有成员，如何高效地完成这个扩散过程？

#### 3.3.1 写扩散 vs 读扩散

**写扩散（Push模型）**：发送方发一条消息时，系统为群内每个成员都写一份消息副本到各自的收件箱。

- 优点：接收方读取消息时只需查自己的收件箱，读取性能好
- 缺点：群成员多时写入放大严重，N人群发一条消息需要写N份

**读扩散（Pull模型）**：发送方只写一份消息到群的会话存储，接收方读取时去查群的会话存储。

- 优点：写入量小，一条消息只写一份
- 缺点：接收方需要主动拉取，实时性差；多人同时读取时存储压力

#### 3.3.2 混合策略（实际采用的方案）

实际系统中采用混合策略，结合写扩散和读扩散的优点：

```
群消息扩散流程：
┌─────────────┐
│ 用户A发送    │
│ 群消息       │
└──────┬──────┘
       │
       ▼
┌─────────────────────────────────────────────────┐
│ 群聊逻辑服务（GIm）                                │
│ 1. 生成消息ID + 会话seqId                         │
│ 2. 消息写入MQ队列（只写一份）                    │
│ 3. 查询群成员列表                                  │
│ 4. 遍历群成员的在线状态                             │
│    ├── 在线成员：直接下行推送（写扩散到在线收件箱）   │
│    └── 离线成员：写入离线消息队列（写扩散到离线收件箱）│
│ 5. 消息写入群会话存储（读扩散的共享存储）             │
└─────────────────────────────────────────────────┘
```

**策略模式的Java实现**：

```java
public class GroupChatService {
    private final GroupMemberService groupMemberService;
    private final OnlineStatusService onlineStatusService;
    private final MessageStorageProxy storageProxy;
    private final MessageDownstreamRouter router;
    private final OfflinePushService offlinePush;
    
    // 群消息扩散采用混合策略
    private final GroupMessageStrategy strategy;
    
    public SendResult sendGroupMessage(SendGroupMessageRequest req) {
        long msgId = idGenerator.nextId();
        long seqId = seqIdGenerator.nextSeq(req.getGroupId());
        
        MessageEntity msg = MessageEntity.builder()
            .msgId(msgId)
            .seqId(seqId)
            .conversationId(req.getGroupId())
            .senderId(req.getSenderId())
            .content(req.getContent())
            .timestamp(System.currentTimeMillis())
            .build();
        
        // 1. 写入消息队列（只写一份到群会话存储）
        storageProxy.storeMessage(msg);
        
        // 2. 获取群成员列表
        List<Long> memberIds = groupMemberService.getMembers(req.getGroupId());
        
        // 3. 根据群大小选择扩散策略
        if (memberIds.size() <= 100) {
            // 小群：写扩散，为每个在线成员推送
            strategy = new WriteDiffusionStrategy(router, onlineStatusService, offlinePush);
        } else {
            // 大群：读扩散，只写入群会话存储，客户端主动拉取
            strategy = new ReadDiffusionStrategy(storageProxy);
        }
        
        strategy.diffuse(msg, memberIds);
        
        return SendResult.success(msgId, seqId);
    }
}

// 策略接口
public interface GroupMessageStrategy {
    void diffuse(MessageEntity msg, List<Long> memberIds);
}

// 写扩散策略：小群使用
public class WriteDiffusionStrategy implements GroupMessageStrategy {
    @Override
    public void diffuse(MessageEntity msg, List<Long> memberIds) {
        for (Long memberId : memberIds) {
            Optional<OnlineStatus> status = onlineStatusService.getOnline(memberId);
            if (status.isPresent()) {
                // 在线：直接下行推送
                router.pushDownstream(status.get(), msg);
            } else {
                // 离线：写入离线消息队列
                offlinePush.enqueueOfflineMessage(memberId, msg);
            }
        }
    }
}

// 读扩散策略：大群使用
public class ReadDiffusionStrategy implements GroupMessageStrategy {
    @Override
    public void diffuse(MessageEntity msg, List<Long> memberIds) {
        // 只写入群会话存储，客户端通过增量同步拉取
        // 客户端定期或收到通知后拉取群消息
        storageProxy.storeGroupMessage(msg);
        
        // 对于在线成员，发送一个轻量的"新消息通知"（不含消息内容）
        // 客户端收到通知后主动拉取消息内容
        for (Long memberId : memberIds) {
            Optional<OnlineStatus> status = onlineStatusService.getOnline(memberId);
            if (status.isPresent()) {
                router.pushNotification(status.get(), msg.getConversationId(), msg.getSeqId());
            }
        }
    }
}
```

### 3.4 消息有序性保证

消息有序性是IM系统的基本要求。用户看到的消息顺序必须与发送顺序一致。这里有两层有序性：

1. **会话内有序**：同一会话（单聊或群聊）内的消息按发送时间有序
2. **全局有序**：用于消息ID生成，便于全局排序和去重

**会话内有序**通过seqId实现。每个会话维护一个单调递增的seqId，消息发送时通过Redis INCR命令获取下一个seqId。客户端收到消息后，根据seqId排序展示。如果收到的消息seqId不连续（如收到seqId=5后收到seqId=7，缺少seqId=6），客户端主动向服务端拉取缺失的消息。

```java
public class SeqIdGenerator {
    private final RedisCluster redis;
    
    public long nextSeq(long conversationId) {
        String key = "seq:" + conversationId;
        return redis.incr(key);
    }
}
```

**全局消息ID**通过号段模式生成。IdGenerator服务从数据库批量获取ID号段，缓存在本地内存中，每次生成ID从本地号段取。当号段用尽时，再从数据库获取新号段。消息ID中嵌入时间戳信息，因此可以从消息ID直接提取时间戳（反过来不行，因为同一毫秒内可能有多条消息）。

### 3.5 已读未读机制

已读未读分为两个层面：

1. **本端已读同步**：用户在设备A上阅读了消息，设备B上也需要标记为已读
2. **对端已读回执**：A发消息给B，B阅读后，A需要看到"对方已读"标记

**本端已读同步**通过ImRead服务实现。用户在某个设备上标记已读后，ImRead服务更新Redis中的已读位置（conversationId -> lastReadSeqId），然后通过消息队列通知用户的其他在线设备同步已读状态。

**对端已读回执**通过ReadSync服务实现。B阅读消息后，ReadSync服务标记每条消息的阅读状态，并通过下行路由向A推送"对方已读"通知。A客户端收到通知后更新消息的已读标记。

```java
// 本端已读同步
public class ReadSyncService {
    private final RedisCluster readStatusStore;
    private final MQProducer mqProducer;
    
    public void markRead(long uid, long conversationId, long lastReadSeqId) {
        // 1. 更新Redis中的已读位置
        String key = "read:" + uid + ":" + conversationId;
        readStatusStore.set(key, String.valueOf(lastReadSeqId));
        
        // 2. 通过消息队列通知其他设备同步
        ReadSyncEvent event = new ReadSyncEvent(uid, conversationId, lastReadSeqId);
        mqProducer.send("read-sync-topic", event);
    }
}

// 对端已读回执
public class PeerReadReceiptService {
    private final MessageDownstreamRouter router;
    private final OnlineStatusService onlineStatus;
    
    public void sendReadReceipt(long senderId, long receiverId, 
                                 long conversationId, long lastReadSeqId) {
        // 构建已读回执消息
        ReadReceipt receipt = new ReadReceipt();
        receipt.setConversationId(conversationId);
        receipt.setLastReadSeqId(lastReadSeqId);
        receipt.setTimestamp(System.currentTimeMillis());
        
        // 向发送方推送已读回执
        Optional<OnlineStatus> status = onlineStatus.getOnline(senderId);
        if (status.isPresent()) {
            router.pushReadReceipt(status.get(), receipt);
        }
    }
}
```

### 3.6 离线消息与增量同步

当用户离线时，消息需要存储并在用户上线后投递。离线消息采用**游标驱动的增量同步协议**：

```
1. 客户端本地记录最后同步的seqId（lastSyncSeqId）
2. 客户端上线后，向服务端发送同步请求：{conversationId, lastSyncSeqId}
3. 服务端从lastSyncSeqId+1开始，返回所有新消息
4. 如果消息量过大，分页返回
5. 客户端同步完成后，更新本地lastSyncSeqId
```

```java
public class OfflineMessageSyncService {
    private final MessageCacheService cacheService;    // Redis缓存
    private final MessageHotDataService hotDataService; // MySQL热数据
    private final MessageColdDataService coldDataService; // HBase冷数据
    
    public SyncResult sync(long uid, long conversationId, long lastSyncSeqId) {
        // 1. 先从Redis缓存读取最近消息（快速路径）
        List<MessageEntity> recentMsgs = cacheService.getMessagesAfter(
            conversationId, lastSyncSeqId, 100);
        
        if (recentMsgs.size() >= 100) {
            // 缓存中消息足够，直接返回
            return SyncResult.success(recentMsgs, recentMsgs.get(recentMsgs.size()-1).getSeqId());
        }
        
        // 2. 缓存中消息不足，查询MySQL热数据
        List<MessageEntity> hotMsgs = hotDataService.getMessagesAfter(
            conversationId, lastSyncSeqId, 500);
        
        if (recentMsgs.size() + hotMsgs.size() < 10) {
            // 3. 热数据也不够（可能是长时间未上线），查询HBase冷数据
            List<MessageEntity> coldMsgs = coldDataService.getMessagesAfter(
                conversationId, lastSyncSeqId, 1000);
            hotMsgs.addAll(coldMsgs);
        }
        
        // 合并去重排序
        List<MessageEntity> allMsgs = mergeAndSort(recentMsgs, hotMsgs);
        
        return SyncResult.success(allMsgs, 
            allMsgs.get(allMsgs.size()-1).getSeqId());
    }
}
```

### 3.7 服务号消息推送链路

服务号（公众号）是IM系统的重要开放能力，业务方通过服务号向用户推送消息。服务号消息有两种类型：

1. **单播消息**：向指定用户推送（如配送状态通知）
2. **广播消息**：向所有关注用户推送（如公告）

```
服务号消息推送完整链路：

1. 业务方后端调用服务号推送API（PubApi），传入channel、appId、消息内容
       │
       ▼
2. PubApi服务校验权限（channel-appId维度鉴权），将消息写入消息队列
       │
       ▼
3. 服务号下行逻辑服务（PubPushServer）从消息队列消费消息
       │
       ▼
4. PubPushServer处理消息：
   a) 生成消息ID和seqId
   b) 查询目标用户在线状态
   c) 在线：通过JBridge下行推送
   d) 离线：写入离线消息队列，触发离线推送
       │
       ▼
5. 存储代理（MsgLogic）将消息写入MQ队列（异步持久化）
       │
       ├── PubCache消费者：写入Redis/分布式KV缓存
       ├── PubHotData消费者：写入MySQL热数据
       └── PubColdData消费者：写入HBase冷数据
       │
       ▼
6. 服务号回调服务（PubCallback）将消息回调给业务方后端
   （业务方可以在回调中做自定义处理，如建立ES搜索索引）
```

**channel和appId两种鉴权维度**：

- **channel**：代表业务维度，是消息的归属方。一个channel可以投放在不同的appId上（如同一个业务既有App A的用户也有App B的用户）
- **appId**：代表App维度。权限管控时会加强对appId维度的管控力度，因为appId维度可能影响该App下的其他业务channel

### 3.8 消息回调机制

IM系统提供回调能力，将IM消息实时回调给接入SDK的业务方后端。这是通过CallbackWriter服务实现的。

回调服务从消息队列消费消息，然后通过Thrift RPC调用业务方预先注册的回调接口。回调是**异步的**——消息回调和消息存储是两个独立的消费链路，互不阻塞。这意味着即使业务方回调接口响应慢，也不会影响消息存储和投递。

业务方可以利用回调实现：
1. **消息数据存储**：将消息存储到自己的数据库或ES中建立搜索索引（IM存储本身不提供全文搜索功能）
2. **消息内容审核**：对消息内容做业务层面的审核处理
3. **消息触发业务逻辑**：如收到配送状态消息后触发订单状态更新

```java
public class MessageCallbackService {
    private final MQConsumer mqConsumer;
    private final Map<String, CallbackEndpoint> callbackRegistry;  // 业务回调地址注册表
    
    @MQListener(topic = "xm-msgbox", group = "callback-group")
    public void onMessage(MQRecord record) {
        MessageEntity msg = MessageSerializer.deserialize(record.getValue());
        
        // 根据channel查找注册的业务方回调地址
        CallbackEndpoint endpoint = callbackRegistry.get(msg.getChannel());
        if (endpoint == null) {
            return;  // 该channel没有注册回调
        }
        
        // 构建回调请求
        CallbackRequest callbackReq = new CallbackRequest();
        callbackReq.setMsgId(msg.getMsgId());
        callbackReq.setConversationId(msg.getConversationId());
        callbackReq.setSenderId(msg.getSenderId());
        callbackReq.setContent(msg.getContent());
        callbackReq.setMsgType(msg.getMsgType());
        callbackReq.setChannel(msg.getChannel());
        callbackReq.setTimestamp(msg.getTimestamp());
        
        // 异步回调业务方（超时3s，失败重试3次）
        try {
            callbackExecutor.submit(() -> {
                retryCallback(endpoint, callbackReq, 3);
            });
        } catch (Exception e) {
            log.error("callback failed, channel={}", msg.getChannel(), e);
        }
    }
    
    private void retryCallback(CallbackEndpoint endpoint, CallbackRequest req, int maxRetry) {
        for (int i = 0; i < maxRetry; i++) {
            try {
                thriftClient.invoke(endpoint.getApikey(), endpoint.getMethod(), req);
                return;  // 成功则返回
            } catch (Exception e) {
                log.warn("callback retry {}/{}, endpoint={}", i+1, maxRetry, 
                    endpoint.getApikey(), e);
                if (i == maxRetry - 1) {
                    // 最后一次重试仍失败，记录到死信队列
                    deadLetterQueue.send("callback-dlq", req);
                }
            }
        }
    }
}
```

## 四、异常处理与容错机制

### 4.1 消息不丢失保障

消息从发送到持久化，经历多个环节，每个环节都可能出现异常。保障消息不丢失的策略：

| 环节 | 异常场景 | 保障措施 |
| --- | --- | --- |
| 客户端到网关 | 网络断开 | 客户端本地缓存未ACK消息，重连后重发 |
| 网关到逻辑服务 | 网关宕机 | 消息在网关的WAL（Write-Ahead Log）中，重启后恢复 |
| 逻辑服务到存储代理 | 逻辑服务宕机 | 存储代理收到消息后先写WAL再写MQ |
| 存储代理到MQ | MQ不可用 | 重试3次，仍失败则写入本地磁盘，后台线程补偿 |
| MQ到消费者 | 消费者宕机 | MQ消息有副本机制（ISR），消费者重启后从上次offset继续消费 |
| 消费者到MySQL/HBase | DB不可用 | 消费者暂停消费（不提交offset），等待DB恢复后继续 |
| 离线推送 | Push平台不可用 | 消息保留在离线队列，用户上线后通过增量同步获取 |

### 4.2 幂等性保证

消息发送可能出现重复（如客户端重发、MQ重复消费），系统需要保证幂等：

1. **客户端到服务端**：客户端为每条消息生成临时ID，服务端根据临时ID去重
2. **MQ消费**：消费者通过msgId去重，同一个msgId只处理一次
3. **下行推送**：接收方根据msgId去重，重复消息丢弃

```java
public class IdempotentChecker {
    private final RedisCluster redis;
    private static final int DEDUP_TTL = 3600;  // 去重缓存1小时
    
    public boolean isDuplicate(long msgId) {
        String key = "dedup:" + msgId;
        // SETNX：不存在则设置，返回true；已存在返回false
        boolean firstTime = redis.setnx(key, "1", DEDUP_TTL);
        return !firstTime;  // 非第一次则是重复
    }
}
```

### 4.3 容灾架构

IM系统采用多机房部署，核心服务分布在5+个机房（如光环、永丰、贤人、兆丰、铭泰等），上海部署热备集群，香港部署独立接入点。

容灾等级分为1-5级，1级最高（容灾等级过低的服务需要整改）。核心服务如长连接服务、信令路由、认证服务、在线状态管理均为4级以上容灾。

数据层容灾：
- **Redis**：三机房1主2从部署，北京主集群+上海热备集群
- **MySQL**：1主2从，跨机房部署，S级容灾
- **HBase**：单集群3副本
- **MQ**：双机房集群部署

## 五、性能优化

### 5.1 消息存储三级缓存

消息读取采用三级缓存策略，从热到冷逐级降级：

1. **一级缓存（Redis/分布式KV）**：最近消息缓存，QPS可达45000+，毫秒级响应
2. **二级存储（MySQL热数据）**：最近3个月消息，十毫秒级响应
3. **三级存储（HBase冷数据）**：全量历史消息，百毫秒级响应

当Redis缓存抗不住高峰流量时，配置限流策略，让一部分流量直接走到HBase（有损降级）。

### 5.2 序列化优化

IM系统处理数十亿级数据包，序列化性能至关重要。Thrift序列化在高峰期可能成为CPU热点。优化方案：

1. 服务间通信使用Thrift二进制协议（比JSON高效）
2. 客户端与网关之间使用自研加密二进制协议（不可被抓包）
3. 对热路径上的消息结构做字段精简，减少序列化数据量

### 5.3 连接复用

长连接服务与后端服务之间使用Thrift RPC连接池，复用TCP连接，避免频繁建连开销。连接池配置：maxActive=100, maxIdle=20, minIdle=1, maxWait=3000ms, testOnBorrow=true。

### 5.4 关键性能指标

| 指标 | 目标值 | 实际值 |

| 连接成功率 | 99%+ | 99% |

## 六、最佳实践与总结

### 6.1 核心设计原则

1. **消息队列异步持久化**：这是整个IM存储架构的核心。消息不直接写DB，而是先写消息队列，再由多个消费者异步写入不同存储介质。好处是低延迟、高可用、解耦、削峰。

2. **冷热数据分离**：消息按时间维度分热数据和冷数据，热数据存MySQL（查询快），冷数据存HBase（存储成本低）。配合Redis缓存最近消息，形成三级存储体系。

3. **弱依赖降级**：敏感词过滤、消息回调等非核心链路服务设为弱依赖，超时或失败时不阻塞消息发送主流程。

4. **channel与appId双维度鉴权**：channel代表业务维度，appId代表App维度。同一channel可跨App投放，实现了多App之间的消息互通。

5. **消息回调与存储独立**：消息回调给业务方和消息持久化是两条独立的消费链路，互不影响。业务方回调慢不会影响消息存储。

### 6.2 常见陷阱

1. **同步写存储导致高延迟**：如果消息发送时同步写MySQL+HBase+Redis，P99延迟会飙升。正确做法是通过消息队列异步持久化。

2. **群消息无差别写扩散**：大群（100人+）如果采用写扩散，写入放大会导致存储压力。正确做法是小群写扩散、大群读扩散的混合策略。

3. **忽略消息有序性**：不使用seqId保证会话内有序，导致消息乱序。正确做法是每个会话维护单调递增的seqId。

4. **离线消息全量拉取**：用户长时间离线后上线，一次性拉取所有离线消息导致带宽和性能问题。正确做法是游标驱动的增量同步，分页返回。

5. **回调阻塞主流程**：消息回调同步执行，业务方接口慢导致消息投递延迟。正确做法是回调异步化，通过独立的消费链路处理。

### 6.3 架构演进方向

1. **单元化架构**：从多机房部署演进到单元化架构，每个单元自治，减少跨机房调用
2. **流批一体**：消息存储从Lambda架构（批流分离）演进到Kappa架构（流批一体）
3. **国际化部署**：香港、法兰克福等海外接入点，支持出海业务
4. **AI能力融合**：结合大模型能力，支持智能客服、消息摘要、内容审核等AI场景
5. **端到端加密**：在现有全链路TLS加密基础上，增加端到端加密方案，提供更强的隐私保护

#### 7.1.2 客户端SDK：消息封包与本地状态机

客户端SDK在发送消息前，先在本地生成一个临时ID（clientMsgId），并将消息状态置为"发送中"，用于处理网络抖动下的重发与去重。

```java
/**
 * 客户端SDK消息发送模块（简化版，运行于Android/iOS的Java/Kotlin层）
 */
public class ImMessageSender {
    private static final Logger log = LoggerFactory.getLogger(ImMessageSender.class);

    private final LongConnectionClient connectionClient;   // 长连接客户端
    private final LocalMessageStore localStore;            // 本地消息状态存储（SQLite）
    private final RetryScheduler retryScheduler;            // 本地重发调度器

    private static final int SEND_TIMEOUT_MS = 8000;   // 单次发送等待ACK超时
    private static final int MAX_CLIENT_RETRY = 3;     // 客户端最大重发次数

    /**
     * 发送单聊消息，返回客户端本地生成的临时ID，供UI层乐观展示
     */
    public String sendTextMessage(long fromUid, long toUid, String content) {
        // 1. 生成本地临时ID（UUID），用于本地状态跟踪与服务端幂等去重
        String clientMsgId = UUID.randomUUID().toString();

        try {
            // 2. 组装消息包
            ImMessagePacket packet = ImMessagePacket.builder()
                .clientMsgId(clientMsgId)
                .conversationId(buildConversationId(fromUid, toUid))
                .fromUid(fromUid)
                .toUid(toUid)
                .msgType(MsgType.TEXT)
                .content(content)
                .clientTimestamp(System.currentTimeMillis())
                .build();

            // 3. 本地先落库为"发送中"状态（乐观UI + 断线可恢复）
            localStore.saveLocalMessage(packet, LocalMsgStatus.SENDING);
            log.info("[IM-SDK] local message saved, clientMsgId={}, from={}, to={}",
                clientMsgId, fromUid, toUid);

            // 4. 通过长连接上行发送，并注册ACK等待
            sendWithRetry(packet, 0);
        } catch (Exception e) {
            // 封包或本地存储异常，直接标记失败，避免无限挂起
            log.error("[IM-SDK] send message build failed, clientMsgId={}", clientMsgId, e);
            localStore.updateStatus(clientMsgId, LocalMsgStatus.FAILED);
        }
        return clientMsgId;
    }

    /**
     * 待ACK重发逻辑：网络抖动、连接短暂不可用时的自愈手段
     */
    private void sendWithRetry(ImMessagePacket packet, int retryCount) {
        if (retryCount >= MAX_CLIENT_RETRY) {
            log.warn("[IM-SDK] give up sending after {} retries, clientMsgId={}",
                retryCount, packet.getClientMsgId());
            localStore.updateStatus(packet.getClientMsgId(), LocalMsgStatus.FAILED);
            return;
        }

        try {
            connectionClient.sendUpstream(SignalCommand.MSG_SEND, packet.toBytes());

            // 注册超时任务：若SEND_TIMEOUT_MS内未收到服务端ACK，触发重发
            retryScheduler.schedule(SEND_TIMEOUT_MS, () -> {
                if (localStore.isStillSending(packet.getClientMsgId())) {
                    log.warn("[IM-SDK] ack timeout, retrying, clientMsgId={}, retry={}",
                        packet.getClientMsgId(), retryCount + 1);
                    sendWithRetry(packet, retryCount + 1);
                }
            });
        } catch (ConnectionNotReadyException e) {
            // 长连接未就绪（如正在重连），等待重连成功后由重连回调统一补发
            log.warn("[IM-SDK] connection not ready, defer send, clientMsgId={}",
                packet.getClientMsgId(), e);
            localStore.updateStatus(packet.getClientMsgId(), LocalMsgStatus.PENDING_RECONNECT);
        }
    }

    /**
     * 服务端ACK回调：收到服务端确认后更新本地状态为"已发送"
     */
    public void onServerAck(String clientMsgId, long globalMsgId, long seqId) {
        localStore.updateStatusWithServerId(clientMsgId, globalMsgId, seqId, LocalMsgStatus.SENT);
        log.info("[IM-SDK] server ack received, clientMsgId={}, globalMsgId={}, seqId={}",
            clientMsgId, globalMsgId, seqId);
    }

    private String buildConversationId(long uidA, long uidB) {
        // 单聊会话ID：小uid在前，保证A发给B与B发给A落在同一个会话
        long min = Math.min(uidA, uidB);
        long max = Math.max(uidA, uidB);
        return "c2c_" + min + "_" + max;
    }
}
```

#### 7.1.3 网关解码与信令路由

网关（ComConn）收到二进制包后解码为统一信令包，透传给信令路由（Router），再转发到单群聊代理（ImProxy）。这一层不解析业务内容，只做协议解码和路由分发，异常需要快速失败并断开异常连接，避免脏数据污染下游。

```java
/**
 * 长连接网关：上行数据包解码与路由转发
 */
public class GatewayUpstreamHandler {
    private static final Logger log = LoggerFactory.getLogger(GatewayUpstreamHandler.class);

    private final SignalRouter signalRouter;      // 信令路由客户端
    private final ConnectionRegistry connRegistry; // 连接注册表

    public void onUpstreamPacket(Connection conn, byte[] rawData) {
        SignalPacket packet;
        try {
            // 1. 协议解码（自研二进制协议，含长度前缀+校验和）
            packet = SignalCodec.decode(rawData);
        } catch (CodecException e) {
            // 解码失败：说明协议版本不兼容或数据被篡改，直接断开连接防止攻击
            log.error("[Gateway] decode failed, connId={}, remote={}",
                conn.getConnectionId(), conn.getRemoteAddress(), e);
            conn.close();
            return;
        }

        // 2. 校验连接是否已认证，未认证的连接除登录信令外一律拒绝
        if (!conn.isAuthenticated() && packet.getCommand() != SignalCommand.LOGIN) {
            log.warn("[Gateway] unauthenticated upstream rejected, connId={}, command={}",
                conn.getConnectionId(), packet.getCommand());
            conn.sendError(ErrorCode.NOT_AUTHENTICATED);
            return;
        }

        try {
            // 3. 附加网关侧上下文（网关节点ID、连接ID），供下行时定位回连接
            packet.setGatewayNodeId(connRegistry.getLocalNodeId());
            packet.setConnectionId(conn.getConnectionId());
            packet.setUid(conn.getUid());

            // 4. 转发给信令路由（内部RPC，带超时与重试）
            signalRouter.route(packet);
        } catch (RpcTimeoutException e) {
            // 路由层超时：给客户端返回明确的重试信号，而不是让客户端长时间等待
            log.error("[Gateway] route timeout, connId={}, msgSeq={}",
                conn.getConnectionId(), packet.getClientSeq(), e);
            conn.sendError(ErrorCode.SERVER_BUSY_RETRY);
        } catch (Exception e) {
            log.error("[Gateway] route unexpected error, connId={}", conn.getConnectionId(), e);
            conn.sendError(ErrorCode.INTERNAL_ERROR);
        }
    }
}
```

#### 7.1.4 单聊逻辑服务：幂等控制、消息落库与投递决策

这是整个案例的核心。服务端必须对客户端可能的重复上行做幂等处理（例如客户端重发同一个clientMsgId的消息），同时保证消息ID生成、落库、下行投递三步互不阻塞、互不影响。

```java
/**
 * 单聊逻辑服务：接收上行消息，完成幂等校验、消息生成、异步落库与投递
 */
public class SingleChatMessageHandler {
    private static final Logger log = LoggerFactory.getLogger(SingleChatMessageHandler.class);

    private final RedisCluster idempotentStore;       // 幂等去重存储
    private final IdGenerator idGenerator;             // 全局消息ID生成器（号段模式）
    private final SeqIdGenerator seqIdGenerator;       // 会话内序列号生成器
    private final MessageStorageProxy storageProxy;    // 存储代理（写MQ异步持久化）
    private final OnlineStatusService onlineStatus;    // 在线状态查询
    private final MessageDownstreamRouter downstreamRouter; // 下行路由
    private final OfflinePushService offlinePush;      // 离线推送兜底
    private final GatewayCallback gatewayCallback;     // 回写ACK给网关

    private static final int CLIENT_MSG_DEDUP_TTL_SECONDS = 24 * 3600; // 客户端消息幂等窗口：24小时

    public void handle(SignalPacket packet) {
        ImMessagePacket msgReq = ImMessagePacket.parseFrom(packet.getPayload());
        String clientMsgId = msgReq.getClientMsgId();

        try {
            // ============ 第一步：幂等控制 ============
            // 使用clientMsgId做幂等键，防止客户端断线重发/网络抖动导致的重复下发
            String dedupKey = "c2c:dedup:" + msgReq.getFromUid() + ":" + clientMsgId;
            IdempotentRecord existing = idempotentStore.get(dedupKey, IdempotentRecord.class);
            if (existing != null) {
                // 命中幂等记录：直接返回上次生成的结果，不重复生成ID、不重复入库、不重复投递
                log.info("[ImServer] duplicate request hit idempotent cache, clientMsgId={}, msgId={}",
                    clientMsgId, existing.getMsgId());
                gatewayCallback.sendAck(packet, existing.getMsgId(), existing.getSeqId());
                return;
            }

            // ============ 第二步：生成全局ID与会话序列号 ============
            long msgId = idGenerator.nextId();
            long seqId = seqIdGenerator.nextSeq(msgReq.getConversationId());

            MessageEntity msg = MessageEntity.builder()
                .msgId(msgId)
                .seqId(seqId)
                .conversationId(msgReq.getConversationId())
                .senderId(msgReq.getFromUid())
                .receiverId(msgReq.getToUid())
                .content(msgReq.getContent())
                .msgType(msgReq.getMsgType())
                .clientMsgId(clientMsgId)
                .timestamp(System.currentTimeMillis())
                .build();

            // ============ 第三步：先占位幂等记录，避免生成ID后并发重复请求穿透 ============
            // SETNX原子占位：若并发的两次重发同时到达，只有一个能成功占位
            boolean placed = idempotentStore.setnx(dedupKey,
                IdempotentRecord.of(msgId, seqId), CLIENT_MSG_DEDUP_TTL_SECONDS);
            if (!placed) {
                // 极端并发下，占位失败说明另一个线程已经在处理，读取其结果直接返回
                IdempotentRecord raceResult = idempotentStore.get(dedupKey, IdempotentRecord.class);
                log.warn("[ImServer] idempotent race detected, clientMsgId={}", clientMsgId);
                gatewayCallback.sendAck(packet, raceResult.getMsgId(), raceResult.getSeqId());
                return;
            }

            // ============ 第四步：异步持久化（写MQ，不等DB） ============
            StoreResult storeResult = storageProxy.storeMessage(msg);
            if (!storeResult.isSuccess()) {
                // MQ写入失败：回滚幂等占位，允许客户端重试
                idempotentStore.delete(dedupKey);
                log.error("[ImServer] store to MQ failed, msgId={}, clientMsgId={}", msgId, clientMsgId);
                gatewayCallback.sendError(packet, ErrorCode.STORE_FAILED);
                return;
            }

            // ============ 第五步：回复发送方ACK ============
            gatewayCallback.sendAck(packet, msgId, seqId);
            log.info("[ImServer] message stored and acked, msgId={}, seqId={}, from={}, to={}",
                msgId, seqId, msgReq.getFromUid(), msgReq.getToUid());

            // ============ 第六步：投递决策（在线推送 / 离线暂存），与ACK并行，互不阻塞 ============
            deliverToReceiver(msg);

        } catch (IdGeneratorException e) {
            // ID生成器号段耗尽且刷新失败，属于服务级故障，需要告警
            log.error("[ImServer] id generator exhausted, clientMsgId={}", clientMsgId, e);
            gatewayCallback.sendError(packet, ErrorCode.SERVER_BUSY_RETRY);
        } catch (Exception e) {
            log.error("[ImServer] unexpected error handling message, clientMsgId={}", clientMsgId, e);
            gatewayCallback.sendError(packet, ErrorCode.INTERNAL_ERROR);
        }
    }

    private void deliverToReceiver(MessageEntity msg) {
        try {
            Optional<OnlineStatus> receiverStatus =
                onlineStatus.getOnline(msg.getReceiverId(), msg.getAppId());

            if (receiverStatus.isPresent()) {
                // 接收方在线：下行推送，若网关不可达内部会自动降级为离线暂存
                downstreamRouter.pushDownstream(receiverStatus.get(), msg);
                log.info("[ImServer] pushed online, msgId={}, receiver={}, gateway={}",
                    msg.getMsgId(), msg.getReceiverId(), receiverStatus.get().getGatewayNodeId());
            } else {
                // 接收方离线：写入离线消息队列 + 触发厂商推送通知
                offlinePush.enqueueOfflineMessage(msg.getReceiverId(), msg);
                offlinePush.triggerPushNotification(msg.getReceiverId(), msg);
                log.info("[ImServer] receiver offline, enqueued for later sync, msgId={}, receiver={}",
                    msg.getMsgId(), msg.getReceiverId());
            }
        } catch (Exception e) {
            // 投递决策异常不能影响已经完成的存储与ACK，只记录日志+告警，消息本身不会丢
            // 因为消息已落MQ，接收方上线后仍可通过增量同步(7.2/7.3案例)拉取到
            log.error("[ImServer] deliver decision failed, msgId={}, receiver={}",
                msg.getMsgId(), msg.getReceiverId(), e);
        }
    }
}
```

#### 7.1.5 推送到用户B与已读回执

B在线时，网关将消息推送到B的客户端，B客户端本地展示消息并回复"已送达"，用户实际点击查看消息后再回复"已读"。已读回执沿着下行路由的逆向路径推送给A。

```java
/**
 * B端：收到下行消息后的处理，含送达回执与已读回执上报
 */
public class ImMessageReceiver {
    private static final Logger log = LoggerFactory.getLogger(ImMessageReceiver.class);

    private final LongConnectionClient connectionClient;
    private final LocalMessageStore localStore;
    private final RedisCluster clientDedupCache; // 客户端侧幂等：防止同一msgId被重复渲染

    /**
     * 收到服务端下行推送的消息
     */
    public void onDownstreamMessage(ImMessagePacket packet) {
        long msgId = packet.getMsgId();
        try {
            // 客户端侧幂等：网络抖动可能导致同一条消息被下发两次（如网关重试）
            if (localStore.existsByMsgId(msgId)) {
                log.info("[IM-SDK-Receiver] duplicate downstream message ignored, msgId={}", msgId);
                // 依然需要回ACK，否则服务端会认为未送达而持续重推
                connectionClient.sendUpstream(SignalCommand.MSG_DELIVERED_ACK,
                    DeliveredAck.of(msgId).toBytes());
                return;
            }

            // 落地本地消息库，供UI展示
            localStore.saveReceivedMessage(packet);
            log.info("[IM-SDK-Receiver] message received and saved, msgId={}, from={}",
                msgId, packet.getFromUid());

            // 回复"已送达"回执（区别于"已读"，送达只代表客户端收到，不代表用户看到）
            connectionClient.sendUpstream(SignalCommand.MSG_DELIVERED_ACK,
                DeliveredAck.of(msgId).toBytes());
        } catch (Exception e) {
            log.error("[IM-SDK-Receiver] handle downstream message failed, msgId={}", msgId, e);
            // 即使本地处理异常也不能吞掉ACK缺失的问题：这里选择不回ACK，
            // 让服务端的重推机制（案例三）在超时后重新投递，保证最终不丢
        }
    }

    /**
     * 用户在UI上实际打开会话并看到消息时触发已读上报
     */
    public void reportRead(long conversationId, long lastReadSeqId) {
        try {
            ReadReceiptRequest req = ReadReceiptRequest.builder()
                .conversationId(conversationId)
                .lastReadSeqId(lastReadSeqId)
                .readTimestamp(System.currentTimeMillis())
                .build();
            connectionClient.sendUpstream(SignalCommand.MSG_READ_REPORT, req.toBytes());
            log.info("[IM-SDK-Receiver] read report sent, conversationId={}, lastReadSeqId={}",
                conversationId, lastReadSeqId);
        } catch (ConnectionNotReadyException e) {
            // 已读上报失败不影响本地已读展示，仅影响对端已读回执的实时性，
            // 待连接恢复后由本端已读同步机制补偿上报
            log.warn("[IM-SDK-Receiver] read report deferred, conversationId={}", conversationId, e);
        }
    }
}

/**
 * 服务端：处理B的已读上报，向A推送已读回执
 */
public class ReadReceiptHandler {
    private static final Logger log = LoggerFactory.getLogger(ReadReceiptHandler.class);

    private final RedisCluster readStatusStore;
    private final MessageDownstreamRouter downstreamRouter;
    private final OnlineStatusService onlineStatus;
    private final ConversationParticipantService participantService; // 查询会话对端

    public void handleReadReport(long readerUid, ReadReceiptRequest req) {
        try {
            // 1. 幂等更新已读位置：只有当新的lastReadSeqId比已记录的大时才更新，
            //    避免旧的已读上报（如网络乱序）覆盖新的已读进度
            String key = "read:" + readerUid + ":" + req.getConversationId();
            Long previous = readStatusStore.get(key, Long.class);
            if (previous != null && previous >= req.getLastReadSeqId()) {
                log.info("[ReadReceipt] stale read report ignored, uid={}, conversationId={}, "
                    + "previous={}, incoming={}", readerUid, req.getConversationId(),
                    previous, req.getLastReadSeqId());
                return;
            }
            readStatusStore.set(key, req.getLastReadSeqId());

            // 2. 查询会话对端（单聊场景对端只有一个人）
            long peerUid = participantService.getPeerUid(req.getConversationId(), readerUid);

            // 3. 推送已读回执给对端（若在线）
            Optional<OnlineStatus> peerStatus = onlineStatus.getOnline(peerUid);
            if (peerStatus.isPresent()) {
                ReadReceipt receipt = ReadReceipt.builder()
                    .conversationId(req.getConversationId())
                    .lastReadSeqId(req.getLastReadSeqId())
                    .readTimestamp(req.getReadTimestamp())
                    .build();
                downstreamRouter.pushReadReceipt(peerStatus.get(), receipt);
                log.info("[ReadReceipt] pushed to peer, conversationId={}, peer={}, lastReadSeqId={}",
                    req.getConversationId(), peerUid, req.getLastReadSeqId());
            } else {
                // 对端离线：已读回执不做离线暂存（低价值信息），对端上线拉取会话时
                // 直接展示当前的readStatusStore状态即可，无需补推历史已读事件
                log.info("[ReadReceipt] peer offline, skip push, will be visible on next sync, peer={}",
                    peerUid);
            }
        } catch (Exception e) {
            log.error("[ReadReceipt] handle read report failed, reader={}, conversationId={}",
                readerUid, req.getConversationId(), e);
        }
    }
}
```

### 7.2 案例二：群聊消息扩散全链路

#### 7.2.1 场景描述

群G（groupId=9527，成员50人）中，用户A发送一条群消息。完整链路为：**消息入库（写MQ） → 查询群成员列表 → 写扩散到在线成员的收件箱并实时推送 → 离线成员写入离线消息表 → 离线成员上线后触发增量拉取**。本案例聚焦写扩散策略下的完整落地代码（对应3.3节的小群策略），并补充离线暂存与上线拉取的完整实现。

#### 7.2.2 群聊消息发送：入库与写扩散

```java
/**
 * 群聊逻辑服务：接收群消息，完成入库与写扩散
 */
public class GroupChatMessageHandler {
    private static final Logger log = LoggerFactory.getLogger(GroupChatMessageHandler.class);

    private final RedisCluster idempotentStore;
    private final IdGenerator idGenerator;
    private final SeqIdGenerator seqIdGenerator;
    private final MessageStorageProxy storageProxy;
    private final GroupMemberService groupMemberService;
    private final OnlineStatusService onlineStatus;
    private final MessageDownstreamRouter downstreamRouter;
    private final OfflineMessageStore offlineMessageStore; // 离线消息暂存表
    private final GatewayCallback gatewayCallback;

    private static final int GROUP_MSG_DEDUP_TTL_SECONDS = 24 * 3600;
    private static final int SMALL_GROUP_THRESHOLD = 100; // 小群/大群分界线

    public void handle(long senderId, GroupMessageRequest req) {
        String clientMsgId = req.getClientMsgId();
        long groupId = req.getGroupId();

        try {
            // ============ 幂等控制：同3.1.4案例，客户端clientMsgId维度去重 ============
            String dedupKey = "group:dedup:" + senderId + ":" + clientMsgId;
            boolean placed = idempotentStore.setnx(dedupKey, "placeholder", GROUP_MSG_DEDUP_TTL_SECONDS);
            if (!placed) {
                IdempotentRecord existing = idempotentStore.get(dedupKey, IdempotentRecord.class);
                if (existing != null) {
                    log.info("[GIm] duplicate group message ignored, clientMsgId={}, groupId={}",
                        clientMsgId, groupId);
                    gatewayCallback.sendAck(req, existing.getMsgId(), existing.getSeqId());
                    return;
                }
                // 占位存在但结果尚未写入（极端时序），让客户端重试
                gatewayCallback.sendError(req, ErrorCode.SERVER_BUSY_RETRY);
                return;
            }

            // ============ 生成ID并落库（只写一份，走读扩散的共享存储） ============
            long msgId = idGenerator.nextId();
            long seqId = seqIdGenerator.nextSeq(groupId);

            MessageEntity msg = MessageEntity.builder()
                .msgId(msgId)
                .seqId(seqId)
                .conversationId(groupId)
                .senderId(senderId)
                .content(req.getContent())
                .msgType(req.getMsgType())
                .clientMsgId(clientMsgId)
                .timestamp(System.currentTimeMillis())
                .build();

            StoreResult storeResult = storageProxy.storeMessage(msg);
            if (!storeResult.isSuccess()) {
                idempotentStore.delete(dedupKey);
                log.error("[GIm] store group message failed, msgId={}, groupId={}", msgId, groupId);
                gatewayCallback.sendError(req, ErrorCode.STORE_FAILED);
                return;
            }

            // 更新幂等记录为最终结果，供后续重复请求命中
            idempotentStore.set(dedupKey, IdempotentRecord.of(msgId, seqId), GROUP_MSG_DEDUP_TTL_SECONDS);

            gatewayCallback.sendAck(req, msgId, seqId);
            log.info("[GIm] group message stored and acked, msgId={}, seqId={}, groupId={}, sender={}",
                msgId, seqId, groupId, senderId);

            // ============ 写扩散：查群成员，逐一判断在线状态并投递 ============
            diffuseToMembers(groupId, senderId, msg);

        } catch (Exception e) {
            log.error("[GIm] unexpected error handling group message, clientMsgId={}, groupId={}",
                clientMsgId, groupId, e);
            gatewayCallback.sendError(req, ErrorCode.INTERNAL_ERROR);
        }
    }

    private void diffuseToMembers(long groupId, long senderId, MessageEntity msg) {
        List<Long> memberIds;
        try {
            memberIds = groupMemberService.getMembers(groupId);
        } catch (Exception e) {
            // 成员列表查询失败：消息已经落库，只是本轮实时推送缺失，
            // 成员后续通过增量同步（7.2.3）仍能拿到消息，不算消息丢失
            log.error("[GIm] fetch group members failed, groupId={}, msgId={}",
                groupId, msg.getMsgId(), e);
            return;
        }

        int onlineCount = 0;
        int offlineCount = 0;
        int failCount = 0;

        for (Long memberId : memberIds) {
            if (memberId.equals(senderId)) {
                continue; // 发送者自己不需要被推送，客户端本地已展示
            }
            try {
                Optional<OnlineStatus> status = onlineStatus.getOnline(memberId);
                if (status.isPresent()) {
                    // 在线：写扩散到在线成员收件箱（直接下行推送）
                    downstreamRouter.pushDownstream(status.get(), msg);
                    onlineCount++;
                } else {
                    // 离线：写扩散到离线成员的暂存表，等待上线拉取
                    offlineMessageStore.append(memberId, groupId, msg);
                    offlineCount++;
                }
            } catch (Exception e) {
                // 单个成员投递失败不能影响其他成员，记录日志后继续下一个
                failCount++;
                log.error("[GIm] deliver to member failed, groupId={}, member={}, msgId={}",
                    groupId, memberId, msg.getMsgId(), e);
            }
        }

        log.info("[GIm] diffusion finished, groupId={}, msgId={}, total={}, online={}, "
            + "offline={}, failed={}", groupId, msg.getMsgId(), memberIds.size(),
            onlineCount, offlineCount, failCount);
    }
}
```

#### 7.2.3 离线成员消息暂存与上线拉取

离线成员的消息不能只依赖群共享存储的seqId游标同步（否则群消息量大时，长期离线用户上线要拉取大量无关消息）。这里采用"离线消息暂存表 + 未读游标"的方式，专门服务于"用户上线那一刻，快速知道有哪些会话有新消息"的场景，具体历史消息内容仍从群共享存储按需拉取。

```java
/**
 * 离线消息暂存服务：仅记录“会话+最新未读seqId”的轻量索引，不重复存储消息全文
 */
public class OfflineMessageStore {
    private static final Logger log = LoggerFactory.getLogger(OfflineMessageStore.class);

    private final RedisCluster offlineIndexStore; // 用户维度的离线会话索引（ZSet：conversationId -> lastMsgSeqId）
    private final KVClient offlineCounterStore;    // 未读计数

    /**
     * 追加一条离线消息索引：仅记录该会话对该用户来说的最新seqId，
     * 具体消息内容不重复存储，避免离线消息表膨胀
     */
    public void append(long uid, long conversationId, MessageEntity msg) {
        try {
            String zsetKey = "offline:idx:" + uid;
            // ZADD：score为seqId，member为conversationId，天然去重且保留最大seqId
            offlineIndexStore.zaddIfGreater(zsetKey, conversationId, msg.getSeqId());

            // 未读计数+1，用于客户端角标展示
            String counterKey = "unread:" + uid + ":" + conversationId;
            offlineCounterStore.incr(counterKey);

            log.info("[OfflineStore] indexed offline message, uid={}, conversationId={}, seqId={}",
                uid, conversationId, msg.getSeqId());
        } catch (Exception e) {
            // 索引写入失败：不影响消息本身（已在群共享存储中持久化），
            // 只是用户上线时可能少一条"有新消息"的提醒，需要告警关注但不阻断主流程
            log.error("[OfflineStore] index offline message failed, uid={}, conversationId={}, "
                + "msgId={}", uid, conversationId, msg.getMsgId(), e);
        }
    }

    /**
     * 用户上线时调用：获取所有有新消息的会话及各自的最新seqId
     */
    public List<ConversationCursor> getPendingConversations(long uid) {
        String zsetKey = "offline:idx:" + uid;
        return offlineIndexStore.zrangeAll(zsetKey).stream()
            .map(entry -> new ConversationCursor(entry.getMember(), entry.getScore()))
            .collect(Collectors.toList());
    }

    public void clearAfterSync(long uid, long conversationId) {
        offlineIndexStore.zrem("offline:idx:" + uid, conversationId);
        offlineCounterStore.set("unread:" + uid + ":" + conversationId, "0");
    }
}

/**
 * 用户上线拉取服务：结合离线索引与消息共享存储，完成增量消息拉取
 */
public class OnlineSyncOnLoginService {
    private static final Logger log = LoggerFactory.getLogger(OnlineSyncOnLoginService.class);

    private final OfflineMessageStore offlineMessageStore;
    private final OfflineMessageSyncService messageSyncService; // 见3.6节，按会话拉取消息详情
    private final ClientSyncCursorService clientCursorService;  // 客户端上报的本地已同步游标

    /**
     * 用户上线（长连接建立成功）后触发的全量会话增量同步
     */
    public SyncOnLoginResult syncOnLogin(long uid) {
        List<SyncedConversation> result = new ArrayList<>();
        int failedConversations = 0;

        List<ConversationCursor> pending;
        try {
            pending = offlineMessageStore.getPendingConversations(uid);
        } catch (Exception e) {
            log.error("[OnlineSync] fetch pending conversations failed, uid={}", uid, e);
            // 索引查询整体失败时，退化为让客户端按本地记录的每个会话游标逐个拉取（兜底路径）
            return SyncOnLoginResult.fallbackToClientDriven();
        }

        log.info("[OnlineSync] user login, uid={}, pendingConversationCount={}", uid, pending.size());

        for (ConversationCursor cursor : pending) {
            try {
                long clientLastSeq = clientCursorService.getClientCursor(uid, cursor.getConversationId());

                // 按需拉取该会话在clientLastSeq之后的所有消息（复用3.6节的三级缓存查询）
                SyncResult syncResult = messageSyncService.sync(
                    uid, cursor.getConversationId(), clientLastSeq);

                result.add(new SyncedConversation(cursor.getConversationId(), syncResult.getMessages()));

                // 同步成功后清理离线索引与未读计数
                offlineMessageStore.clearAfterSync(uid, cursor.getConversationId());
            } catch (Exception e) {
                // 单个会话同步失败不影响其他会话，客户端可针对该会话单独重试
                failedConversations++;
                log.error("[OnlineSync] sync conversation failed, uid={}, conversationId={}",
                    uid, cursor.getConversationId(), e);
            }
        }

        log.info("[OnlineSync] sync on login finished, uid={}, succeeded={}, failed={}",
            uid, result.size(), failedConversations);

        return SyncOnLoginResult.success(result, failedConversations);
    }
}
```

### 7.3 案例三：消息可靠性保证全链路

#### 7.3.1 场景描述

本案例聚焦IM系统"不丢不重"的核心机制：**全局消息ID生成 → 客户端/服务端双重ACK确认 → 未确认消息的重试与告警 → 离线消息的增量同步游标 → 端到端幂等**。这是对4.1、4.2节异常处理机制的完整工程化落地。

```
消息可靠性全景：
┌──────────┐   generate   ┌───────────┐   ACK1    ┌──────────┐   ACK2    ┌──────────┐
│ 消息ID    │────────────▶│  发送方    │──────────▶│ 服务端    │──────────▶│ 接收方    │
│ 生成器     │              │ (等待ACK1) │           │(等待ACK2) │           │(消费并回执)│
└──────────┘              └─────┬─────┘           └─────┬────┘           └─────┬────┘
                                 │ 超时未收到ACK1           │ 超时未收到ACK2          │
                                 ▼                        ▼                        │
                           指数退避重发              重新下行推送(限次)                │
                                                          │                        │
                                                          ▼                        │
                                                    超过重试上限 ────────────────────┘
                                                    转入离线暂存
                                                    (案例二 7.2.3)，
                                                    等待客户端增量同步
```

#### 7.3.2 全局消息ID生成器（号段模式）

```java
/**
 * 号段模式ID生成器：本地缓存一批ID，减少数据库访问，同时保证全局唯一与趋势递增
 */
public class SegmentIdGenerator implements IdGenerator {
    private static final Logger log = LoggerFactory.getLogger(SegmentIdGenerator.class);

    private final IdSegmentDao segmentDao;      // 号段存储（MySQL）
    private final Object lock = new Object();

    private volatile long currentMax;    // 当前号段已分配到的最大值
    private volatile long segmentEnd;    // 当前号段的上界
    private static final int SEGMENT_STEP = 10000; // 每次申请1万个ID
    private static final String BIZ_TAG = "im_message";

    @Override
    public long nextId() {
        // 双重检查锁：号段未耗尽时直接自增返回，性能接近本地自增
        if (currentMax < segmentEnd) {
            synchronized (lock) {
                if (currentMax < segmentEnd) {
                    return ++currentMax;
                }
            }
        }

        synchronized (lock) {
            // 再次检查，避免多线程并发耗尽后重复申请号段
            if (currentMax < segmentEnd) {
                return ++currentMax;
            }
            return fetchNextSegmentAndAllocate();
        }
    }

    private long fetchNextSegmentAndAllocate() {
        int retry = 0;
        Exception lastError = null;
        // 号段申请失败重试3次，DB短暂抖动不至于导致整个IM系统无法生成消息ID
        while (retry < 3) {
            try {
                IdSegment segment = segmentDao.fetchNextSegment(BIZ_TAG, SEGMENT_STEP);
                this.currentMax = segment.getStart();
                this.segmentEnd = segment.getEnd();
                log.info("[IdGenerator] fetched new segment, start={}, end={}",
                    segment.getStart(), segment.getEnd());
                return ++currentMax;
            } catch (Exception e) {
                lastError = e;
                retry++;
                log.warn("[IdGenerator] fetch segment failed, retry={}/3", retry, e);
                sleepQuietly(50L * retry); // 简单退避
            }
        }
        // 三次重试均失败，属于严重故障，抛出异常由上层转为“服务繁忙，请重试”返回给客户端
        log.error("[IdGenerator] fetch segment failed after retries, bizTag={}", BIZ_TAG, lastError);
        throw new IdGeneratorException("id segment exhausted and refresh failed", lastError);
    }

    private void sleepQuietly(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException ie) {
            Thread.currentThread().interrupt();
        }
    }
}
```

#### 7.3.3 双重ACK确认机制

消息可靠性依赖两级ACK：**ACK1（客户端→服务端，确认服务端已接收并持久化）**和**ACK2（服务端→接收端→服务端，确认对端已实际收到）**。任意一级ACK缺失都会触发对应层级的重试。

```java
/**
 * ACK确认管理器：统一管理"待确认消息"的注册、确认、超时重试
 */
public class AckConfirmationManager {
    private static final Logger log = LoggerFactory.getLogger(AckConfirmationManager.class);

    private final RedisCluster pendingAckStore; // 待确认消息表：key=msgId, value=重试次数+目标信息
    private final MessageDownstreamRouter downstreamRouter;
    private final OfflineMessageStore offlineMessageStore;
    private final ScheduledExecutorService retryExecutor =
        Executors.newScheduledThreadPool(4, new NamedThreadFactory("im-ack-retry"));

    private static final int[] RETRY_BACKOFF_SECONDS = {2, 5, 15}; // 三次重试的退避间隔
    private static final int MAX_DOWNSTREAM_RETRY = RETRY_BACKOFF_SECONDS.length;
    private static final int PENDING_ACK_TTL_SECONDS = 300;

    /**
     * 服务端下行推送消息后，注册一条待ACK记录并安排超时检查
     */
    public void registerPendingAck(MessageEntity msg, OnlineStatus receiverStatus) {
        String key = pendingAckKey(msg.getMsgId(), msg.getReceiverId());
        PendingAckRecord record = PendingAckRecord.builder()
            .msgId(msg.getMsgId())
            .receiverId(msg.getReceiverId())
            .gatewayNodeId(receiverStatus.getGatewayNodeId())
            .retryCount(0)
            .build();

        pendingAckStore.setex(key, PENDING_ACK_TTL_SECONDS, record.toJson());
        scheduleRetryCheck(msg, receiverStatus, 0);
    }

    /**
     * 接收方回复送达ACK时调用，清除待确认记录，终止后续重试
     */
    public void onDeliveredAck(long msgId, long receiverId) {
        String key = pendingAckKey(msgId, receiverId);
        boolean removed = pendingAckStore.delIfExists(key);
        if (removed) {
            log.info("[AckManager] delivered ack confirmed, msgId={}, receiver={}", msgId, receiverId);
        } else {
            // 可能是重复ACK（如客户端网络抖动重发了ACK），属正常现象，仅记录debug日志
            log.debug("[AckManager] ack for already-cleared record, msgId={}, receiver={}",
                msgId, receiverId);
        }
    }

    private void scheduleRetryCheck(MessageEntity msg, OnlineStatus receiverStatus, int retryIndex) {
        if (retryIndex >= MAX_DOWNSTREAM_RETRY) {
            // 超过最大重试次数：判定为投递失败，转离线暂存，交给增量同步兜底（不丢消息）
            handleMaxRetryExceeded(msg);
            return;
        }

        int delaySeconds = RETRY_BACKOFF_SECONDS[retryIndex];
        retryExecutor.schedule(() -> {
            String key = pendingAckKey(msg.getMsgId(), msg.getReceiverId());
            String recordJson = pendingAckStore.get(key);
            if (recordJson == null) {
                // 记录已被清除，说明ACK已确认或已被其他分支处理，无需重试
                return;
            }

            try {
                log.warn("[AckManager] ack timeout, retrying downstream push, msgId={}, "
                    + "receiver={}, retryIndex={}", msg.getMsgId(), msg.getReceiverId(), retryIndex);

                // 重新查询在线状态：接收方可能已切换网关节点甚至已下线
                Optional<OnlineStatus> latestStatus = onlineStatus().getOnline(msg.getReceiverId());
                if (latestStatus.isPresent()) {
                    downstreamRouter.pushDownstream(latestStatus.get(), msg);
                    scheduleRetryCheck(msg, latestStatus.get(), retryIndex + 1);
                } else {
                    // 重试期间用户下线了：直接转离线暂存，无需继续重试在线推送
                    handleMaxRetryExceeded(msg);
                }
            } catch (Exception e) {
                log.error("[AckManager] retry push failed, msgId={}, receiver={}, retryIndex={}",
                    msg.getMsgId(), msg.getReceiverId(), retryIndex, e);
                scheduleRetryCheck(msg, receiverStatus, retryIndex + 1);
            }
        }, delaySeconds, TimeUnit.SECONDS);
    }

    private void handleMaxRetryExceeded(MessageEntity msg) {
        try {
            // 最终兜底：写入离线索引，用户下次上线通过增量同步（案例二 7.2.3）必然能拉到，
            // 因为消息本体在案例一/二中早已通过MQ持久化成功，这里只是补充“未读提醒”
            offlineMessageStore.append(msg.getReceiverId(), msg.getConversationId(), msg);
            pendingAckStore.delIfExists(pendingAckKey(msg.getMsgId(), msg.getReceiverId()));
            log.warn("[AckManager] max retry exceeded, fallback to offline sync, msgId={}, receiver={}",
                msg.getMsgId(), msg.getReceiverId());
        } catch (Exception e) {
            // 即使兜底写入失败，消息仍然安全存在于群/单聊共享存储中，
            // 只是缺少一次主动提醒，需触发监控告警人工介入排查
            log.error("[AckManager] fallback to offline sync failed, msgId={}, receiver={}",
                msg.getMsgId(), msg.getReceiverId(), e);
        }
    }

    private String pendingAckKey(long msgId, long receiverId) {
        return "pending_ack:" + msgId + ":" + receiverId;
    }

    private OnlineStatusService onlineStatus() {
        // 省略依赖注入细节，实际实现中通过构造函数注入
        throw new UnsupportedOperationException("injected in real implementation");
    }
}
```

#### 7.3.4 消息不丢不重的端到端校验

最后，通过消费端幂等 + 客户端序号连续性校验，形成完整的"不丢不重"闭环：MQ消费端保证同一条消息不会被重复处理，客户端通过seqId连续性检测发现丢消息并主动补拉。

```java
/**
 * MQ消费端幂等处理器：所有消费MQ消息的下游（缓存、热数据、冷数据、回调）统一复用该组件
 */
public class MessageConsumeIdempotentHandler {
    private static final Logger log = LoggerFactory.getLogger(MessageConsumeIdempotentHandler.class);

    private final RedisCluster consumeDedupStore;
    private static final int CONSUME_DEDUP_TTL_SECONDS = 2 * 3600;

    /**
     * 在具体业务处理前调用，判断该消费组是否已处理过该消息
     */
    public boolean tryMarkProcessed(String consumerGroup, long msgId) {
        String key = "consume:dedup:" + consumerGroup + ":" + msgId;
        try {
            // SETNX原子操作：第一次处理返回true，重复消费返回false
            return consumeDedupStore.setnx(key, "1", CONSUME_DEDUP_TTL_SECONDS);
        } catch (Exception e) {
            // Redis异常时的降级策略：宁可放行重复消费（下游业务应保证插入幂等，
            // 如MySQL使用msgId唯一索引 INSERT IGNORE），也不能因为去重服务故障导致消息丢失
            log.error("[ConsumeIdempotent] dedup check failed, degrade to allow-through, "
                + "group={}, msgId={}", consumerGroup, msgId, e);
            return true;
        }
    }
}

/**
 * 示例：热数据消费者接入幂等处理器，并配合MySQL唯一索引形成双重保险
 */
public class ReliableMessageHotDataConsumer {
    private static final Logger log = LoggerFactory.getLogger(ReliableMessageHotDataConsumer.class);

    private final MessageConsumeIdempotentHandler idempotentHandler;
    private final MessageHotDataRepository hotDataRepo; // msg_id字段建有唯一索引

    private static final String CONSUMER_GROUP = "im-hotdata-group-v2";

    @MQListener(topic = "xm-msgbox", group = CONSUMER_GROUP)
    public void onMessage(MQRecord record) {
        MessageEntity msg;
        try {
            msg = MessageSerializer.deserialize(record.getValue());
        } catch (Exception e) {
            // 反序列化失败：消息格式异常，记录到死信队列人工排查，不能让异常阻塞后续消息消费
            log.error("[HotDataConsumer] deserialize failed, offset={}", record.getOffset(), e);
            deadLetterQueue().send("hotdata-dlq-parse-error", record.getValue());
            return; // 提交offset，跳过这条脏数据
        }

        // 第一层幂等：Redis前置去重，避免绝大多数重复消费直接打到DB
        if (!idempotentHandler.tryMarkProcessed(CONSUMER_GROUP, msg.getMsgId())) {
            log.info("[HotDataConsumer] duplicate consume skipped by redis dedup, msgId={}",
                msg.getMsgId());
            return;
        }

        try {
            // 第二层幂等：DB唯一索引兜底，即使Redis去重失效（如故障降级放行），
            // INSERT IGNORE / ON DUPLICATE KEY 保证DB层面绝不重复
            int affected = hotDataRepo.insertIgnoreOnDuplicate(msg);
            if (affected == 0) {
                log.info("[HotDataConsumer] duplicate consume skipped by db unique index, msgId={}",
                    msg.getMsgId());
            } else {
                log.info("[HotDataConsumer] message persisted to hot storage, msgId={}, "
                    + "conversationId={}", msg.getMsgId(), msg.getConversationId());
            }
        } catch (Exception e) {
            // DB写入异常：不提交offset（由MQ框架的异常传播机制控制），
            // 触发消费重试；同一分区消费会暂停直到问题解决或告警人工介入
            log.error("[HotDataConsumer] persist to hot storage failed, msgId={}", msg.getMsgId(), e);
            throw new RuntimeException("persist failed, trigger mq redelivery", e);
        }
    }

    private DeadLetterQueue deadLetterQueue() {
        throw new UnsupportedOperationException("injected in real implementation");
    }
}

/**
 * 客户端：基于seqId连续性检测丢消息并主动补拉，是端到端不丢消息的最后一道防线
 */
public class SeqContinuityChecker {
    private static final Logger log = LoggerFactory.getLogger(SeqContinuityChecker.class);

    private final LocalMessageStore localStore;
    private final MessageSyncApi syncApi; // 对应服务端3.6节的OfflineMessageSyncService

    /**
     * 每次收到一条下行消息时调用，检测与上一条消息的seqId是否连续
     */
    public void onMessageReceived(long conversationId, long incomingSeqId) {
        long lastKnownSeqId = localStore.getLastSeqId(conversationId);

        if (lastKnownSeqId <= 0) {
            // 会话首次收到消息，无需连续性校验
            localStore.updateLastSeqId(conversationId, incomingSeqId);
            return;
        }

        if (incomingSeqId == lastKnownSeqId + 1) {
            // 完全连续，正常场景
            localStore.updateLastSeqId(conversationId, incomingSeqId);
        } else if (incomingSeqId <= lastKnownSeqId) {
            // 收到的seqId不大于本地已知的最大值：说明是重复推送，直接丢弃不更新游标
            log.info("[SeqChecker] duplicate or stale message ignored, conversationId={}, "
                + "incoming={}, lastKnown={}", conversationId, incomingSeqId, lastKnownSeqId);
        } else {
            // incomingSeqId > lastKnownSeqId + 1：中间存在空洞，说明有消息丢失或乱序到达
            log.warn("[SeqChecker] seq gap detected, conversationId={}, lastKnown={}, incoming={}, "
                + "triggering gap-fill sync", conversationId, lastKnownSeqId, incomingSeqId);
            try {
                // 主动向服务端补拉 (lastKnownSeqId, incomingSeqId) 区间内的消息
                List<MessageEntity> gapMessages = syncApi.fetchRange(
                    conversationId, lastKnownSeqId, incomingSeqId);
                localStore.saveBatch(gapMessages);
                localStore.updateLastSeqId(conversationId, incomingSeqId);
                log.info("[SeqChecker] gap-fill sync succeeded, conversationId={}, filled={}",
                    conversationId, gapMessages.size());
            } catch (Exception e) {
                // 补拉失败：先保存当前消息（不更新游标为incomingSeqId避免掩盖空洞），
                // 并安排延迟重试补拉，避免用户看到的消息永久性缺失中间段
                log.error("[SeqChecker] gap-fill sync failed, conversationId={}, will retry later",
                    conversationId, e);
                localStore.scheduleGapFillRetry(conversationId, lastKnownSeqId, incomingSeqId);
            }
        }
    }
}
```

#### 7.3.5 三个案例的共性设计小结

| 环节 | 单聊(7.1) | 群聊(7.2) | 可靠性(7.3) |
| --- | --- | --- | --- |
| 幂等键 | clientMsgId（发送方维度） | clientMsgId（发送方维度） | msgId（消费组维度）+ DB唯一索引 |
| 去重实现 | Redis SETNX + TTL | Redis SETNX + TTL | Redis前置去重 + DB兜底去重 |
| 重试策略 | 客户端指数退避重发 | 单成员投递失败不影响整体 | 三级退避重试(2s/5s/15s)后转离线 |
| 不丢兜底 | MQ持久化 + 离线暂存 | MQ持久化 + 离线索引 | seqId连续性校验 + 主动补拉 |
| 日志埋点 | 关键节点info、异常error | 扩散结果汇总统计 | 每次重试与降级均有warn/error |

这三个案例共同验证了文档前半部分的核心设计原则：**消息队列异步持久化**保证了消息不丢，**多层幂等**保证了消息不重，**seqId + ACK双机制**保证了消息有序且最终必达。
