# 故障演练与混沌工程架构设计

## 一、问题背景

### 1.1 核心问题

分布式系统的复杂度随着服务数量的增长呈指数级上升。一个看似简单的用户下单操作，背后可能涉及几十个微服务的协同调用、多种中间件的数据流转、跨机房甚至跨地域的网络通信。在这样的系统里，**故障不是"是否会发生"的问题，而是"何时发生、以什么形式发生"的问题**。

传统的质量保障手段——单元测试、集成测试、性能压测——只能覆盖"已知的已知"，也就是我们能够预见并编写测试用例的场景。但真正导致重大生产事故的，往往是"未知的未知"：那些设计阶段完全没有考虑到的故障组合。典型案例包括：

- 缓存集群某个从节点因网络分区与主节点断开，恰好赶上大批缓存集中过期，请求全部穿透到数据库，引发数据库过载雪崩；
- 某下游依赖的响应时间从 50ms 悄悄劣化到 5s（并未完全不可用），调用方的超时时间设置为 10s，线程池被慢请求迅速占满，最终导致整个上游服务不可用；
- 磁盘空间被日志文件缓慢耗尽，写入失败又反过来导致异常信息记录不全，问题定位耗时成倍增加，故障恢复时间大幅拉长；
- 一个可用区的核心交换机固件升级失败，该可用区内所有服务瞬间失联，但流量调度层并未及时感知，仍在向该可用区分发请求。

这些场景单独来看都不复杂，但它们与真实业务逻辑、真实流量、真实数据状态交织在一起时，会产生远超预期的级联效应。这正是混沌工程要解决的核心问题：**在故障真正到来之前，用可控的方式主动制造它，验证系统是否具备预期的韧性**。

### 1.2 从传统故障演练到混沌工程的演进

故障演练与混沌工程并非两套割裂的体系，而是一个循序渐进的能力演进过程：

1. **第一阶段：传统故障演练**——运维或研发人员根据经验，手工制造某个已知故障（如重启一台机器、拔掉一根网线），观察系统反应。这种方式覆盖面窄、依赖个人经验、难以规模化、也难以量化结果。
2. **第二阶段：故障注入平台化**——将常见故障场景抽象为可配置、可复用的注入能力，通过平台统一编排、执行、观测，大幅降低了执行门槛，具备了批量化、常态化演练的基础。
3. **第三阶段：混沌工程实验**——在平台化能力之上，引入"稳态假设-实验-观察-改进"的科学实验方法论，演练不再是随机的破坏性操作，而是有目的、有对照、有结论的系统性验证过程，并逐步从测试环境走向生产环境常态化演练。

混沌工程的本质是一门**在分布式系统上做实验的学科**，目的是建立我们对系统在生产环境中承受各种紊乱条件的信心（Building confidence in the system's capability to withstand turbulent conditions in production）。

### 1.3 什么场景下会遇到

- **大促或重大活动前夕**：系统经历了大量变更，需要在真实流量到来之前验证各类降级、限流、熔断策略是否真正生效；
- **架构升级期**：从单体迁移到微服务、从单机房迁移到同城双活或异地多活，新架构的真实容灾能力必须靠演练验证，不能只靠设计文档"自证清白"；
- **日常运维中**：团队对系统的容灾能力缺乏信心，不清楚某个节点、某个可用区挂掉之后系统究竟会表现成什么样子；
- **重大故障复盘之后**：一次线上事故往往会暴露出系统的若干脆弱点，需要通过持续的回归演练验证修复措施的有效性，防止同样的问题再次发生；
- **新链路/新服务上线前**：核心链路必须先过一遍故障注入的"体检"，确认其在依赖异常时的降级行为符合预期。

### 1.4 不解决的后果

- **故障恢复时间居高不下（高 MTTR）**：团队从未真正经历过故障场景，真正出问题时手忙脚乱，恢复时间从分钟级劣化为小时级；
- **隐患持续累积、无法自证**：系统中大量的"纸面容灾能力"从未被验证过，很可能因为一次不起眼的配置变更或代码重构就悄然失效，成为埋在系统里的定时炸弹；
- **容灾能力随时间退化**：限流阈值、熔断规则、主备切换脚本如果长期不被真实触发，往往会与系统的实际状态脱节；
- **对系统稳定性缺乏量化认知**：团队无法准确回答"我们系统的容灾等级是多少""能承受什么级别的故障""恢复时间目标（RTO）和恢复点目标（RPO）是否达标"这些关键问题，业务侧对系统稳定性的信心也无从谈起。

### 1.5 混沌工程的核心理念

混沌工程不是"随便搞破坏"，而是一套有假设、有控制、有观察、有结论的严谨实验方法论，其经典实践可以归纳为四个步骤：

1. **定义稳态假设**：明确系统在正常情况下的关键行为指标，例如 P99 响应时间 < 200ms、错误率 < 0.1%、订单创建成功率 > 99.95%；
2. **引入真实世界事件**：模拟生产环境中真实可能发生的故障，如节点宕机、网络延迟、磁盘写满、可用区级网络中断；
3. **对比观察差异**：持续采集故障注入前后的关键指标，判断系统行为是否偏离了稳态假设；
4. **收敛并改进系统**：根据观察到的偏差定位系统脆弱点，推动修复，并将该场景固化为回归用例，持续验证修复效果。

需要强调的是，混沌工程与故障演练的关系是**演进而非替代**——绝大多数团队都需要先把故障注入能力平台化、把演练流程标准化，才能真正进入"用科学实验的方式持续验证系统韧性"的混沌工程阶段。

## 二、整体架构设计

### 2.1 演练类型体系

在设计整体架构之前，首先要明确"演练要覆盖哪些类型"，因为不同类型的演练对平台能力的要求差异很大。按照爆炸半径（Blast Radius）从小到大、验证目标从局部到全局，可以将演练划分为五大类：

**（1）单点演练（Single-point Drill）**

针对某一个具体角色/模块的定向故障注入，例如只对某个服务的一个节点、某个数据库实例的从库注入故障。特点是爆炸半径最小、风险最可控，是故障演练体系的基础能力，也是新场景上线前必须先跑通的第一道关卡。绝大多数日常演练都属于这一类。

**（2）大规模演练（Large-scale Drill）**

同时对多个集群/多个节点批量注入同类故障，验证的不是单个模块的容错能力，而是整个系统在大范围故障下的**响应效率**：告警是否及时、自动化恢复机制能否在大规模场景下依然稳定工作、值班人员的处置流程是否会被"信息过载"拖垮。大规模演练通常要求平台具备成百上千个目标同时可控地并发注入与并发恢复的能力。

**（3）长链路演练（Long-chain Drill）**

针对某个组件从数据面到管控面的完整管理链条，组合注入多个环节的故障（例如同时模拟"数据节点故障 + 控制器与数据节点通信中断 + 元数据存储抖动"），验证的核心是**管控面（Control Plane）在数据面已经出问题的情况下是否仍然可用**。很多系统的数据面容错做得很好，但管控面一旦在故障期间也失效，就会导致"知道哪里坏了但改不了、切不动"的被动局面，长链路演练正是为了暴露这类问题。

**（4）混合演练（Fusion Drill）**

大规模演练与长链路演练的组合，既有广度（多个集群同时故障）又有深度（管理链路的多环节故障），用于模拟最极端的复合故障场景，是对系统韧性的终极压力测试，一般安排在前两类演练都已经稳定通过之后再进行。

**（5）生产级容灾演练（Production DR Drill）**

在真实生产环境中进行的最高风险等级演练，典型形式包括可用区级流量切走（Escape）、可用区网络断开（Cutoff）、以及分阶段的"二阶段演练"（先验证影响范围可控，再逐步扩大演练规模）。这一类演练直接关系到真实用户体验，必须建立在前四类演练都已经充分验证的基础之上，并配合严格的审批、灰度和实时熔断机制。

这五种类型并非相互独立，而是构成了一条**能力递进的演练路径**：单点演练验证基础容错 → 大规模演练验证响应效率 → 长链路演练验证管控面可用性 → 混合演练验证复合场景韧性 → 生产级容灾演练验证真实世界的最终效果。

### 2.3 各组件职责

**（1）演练编排器**

负责定义"做什么实验"：

- 目标选择：对哪些服务/机器/集群进行故障注入，支持按角色（主库/从库）、按拓扑位置（可用区/机架）等多种维度圈定目标；
- 故障类型：从故障场景库中选择要注入的故障；
- 执行策略：确定演练类型（单点/大规模/长链路/混合/生产级），编排执行顺序、并发度、时间窗口；
- 观察指标：定义关注哪些指标来判断实验结果，即稳态假设。

**（2）故障注入引擎**

负责"怎么注入故障"，支持多种故障类型：

- 主机层面：CPU 满载、内存耗尽、磁盘填满、进程 Kill；
- 网络层面：网络延迟、丢包、断网、DNS 故障、可用区级网络分区；
- 应用层面：方法异常、方法延迟、线程池满、JVM GC；
- 中间件层面：数据库主库故障、从库故障、主从延迟、磁盘故障、线程数飙高等。

**（3）安全管控器**

负责"控制爆炸半径"：

- 演练范围限制：只对部分节点/部分流量注入故障，而不是全部；
- 自动终止：当核心业务指标异常时自动停止演练并回滚；
- 审批流程：生产环境演练需要走风险评估与多级审批；
- 演练窗口：限制演练的时间窗口（如只允许在低峰期，或凌晨窗口）。

**（4）实验控制中心**

负责"管理实验生命周期"：

- 使用有限状态机管理实验的各个阶段；
- 实时采集被演练系统的指标数据；
- 根据预设规则自动判定实验结果；
- 生成结构化的演练报告。

### 2.4 演练环境类型

不同风险等级的演练需要匹配不同的执行环境，环境类型的选择直接决定了演练结果的真实性与安全性之间的权衡：

| 环境类型 | 硬件资源 | 流量来源 | 存储隔离方式 | 适用场景 |
|---------|---------|---------|------------|---------|
| 独立环境 | 与生产共享硬件，但打散部署 | 构造流量（压测/回放流量） | 独立存储，通过服务分组做链路隔离 | 新场景验证、日常回归、随需构建随需销毁 |
| 灰度环境 | 与生产共享硬件 | 真实流量（白名单用户） | 与生产共享存储，通过环境标打标区分 | 验证真实用户行为下的故障影响，风险中等 |
| 仿真环境 | 独立硬件资源 | 复制生产流量 | 存储与生产保持同步 | 高保真度验证，用于生产级演练前的最后一道关卡 |

三种环境构成了一条"由虚到实"的验证路径：独立环境成本最低、可以随意破坏，用于快速试错；灰度环境引入真实流量，验证在真实用户行为下的表现；仿真环境几乎与生产环境等价，是生产级容灾演练前必须通过的最后验证环节。

### 2.5 设计权衡

| 设计决策 | 选项A | 选项B | 最终选择及理由 |
|---------|-------|-------|-------------|
| 故障注入方式 | Agent 探针注入 | Sidecar 注入 | Agent 方式更灵活，可以深入到 JVM 层面做代码无侵入的方法级故障注入 |
| 演练环境 | 仅测试环境 | 独立/灰度/仿真/生产多环境分层 | 分层推进：低风险场景在独立环境快速迭代，高风险场景逐级晋升到生产环境 |
| 故障注入粒度 | 机器级 | 容器/Pod 级，乃至连接/线程级 | 尽量做细粒度：粒度越细，爆炸半径越小，越适合在生产环境常态化执行 |
| 安全管控策略 | 手动终止 | 自动终止 + 手动兜底 | 自动优先：核心指标越界立即自动回滚，人工终止作为补充手段 |
| 演练可见性 | 提前通知 | 部分场景不预告 | 常规演练提前通知参与方以保证效率；针对应急响应能力验证的场景采用不预告方式 |

## 三、核心链路设计

### 3.1 故障注入引擎设计

#### 3.1.1 故障注入类型体系

故障注入的核心是将故障抽象为可编程、可复制、可控制的实验操作。业界常见的实现路径主要有三种：**Agent 注入**（在目标进程中挂载探针，深入到方法级、字节码级）、**SDK 自定义注入**（业务代码显式集成注入 SDK，精细控制注入点）、**Server 端注入**（在网关、代理、Sidecar 层面拦截请求进行故障模拟）。此外，基于 JVM 沙箱技术还可以实现完全无代码侵入的方法级故障注入，无需重启进程、无需修改代码即可动态挂载和卸载故障逻辑。

```java
/**
 * 故障注入抽象体系
 *
 * 设计模式：命令模式 + 策略模式
 *
 * 命令模式：每种故障封装为一个独立的命令对象，
 *           支持执行(inject)和回滚(recover)
 * 策略模式：不同的故障类型采用不同的实现策略
 */
public abstract class FaultInjector {

    /**
     * 故障类型枚举
     */
    public enum FaultType {
        // === 主机层 ===
        CPU_BURN,          // CPU满载
        MEMORY_FILL,       // 内存填充
        DISK_FILL,         // 磁盘填满
        PROCESS_KILL,      // 进程Kill

        // === 网络层 ===
        NETWORK_DELAY,     // 网络延迟
        NETWORK_LOSS,      // 网络丢包
        NETWORK_PARTITION, // 网络分区
        DNS_FAILURE,       // DNS解析失败

        // === 应用层 ===
        METHOD_EXCEPTION,  // 方法抛异常
        METHOD_DELAY,      // 方法延迟
        THREAD_POOL_FULL,  // 线程池满
        JVM_GC,            // 触发Full GC

        // === 中间件层（数据库场景） ===
        DB_MASTER_DOWN,       // 主库故障
        DB_SLAVE_DOWN,        // 从库故障
        DB_REPLICATION_DELAY, // 主从延迟
        DB_DISK_FAILURE,      // 磁盘故障
        DB_THREAD_HIGH,       // 线程数飙高
        CACHE_TIMEOUT,        // 缓存超时
        MQ_SEND_FAIL,         // 消息发送失败
        RPC_TIMEOUT           // RPC调用超时
    }

    /**
     * 注入方式枚举，对应不同的技术实现路径
     */
    public enum InjectionMethod {
        AGENT_ATTACH,     // Agent挂载注入（JVM字节码增强）
        SDK_EXPLICIT,     // SDK显式埋点注入
        SERVER_PROXY,     // 网关/代理层拦截注入
        SANDBOX_HOTSWAP,  // JVM沙箱热替换，无需重启
        KERNEL_TC,        // 内核态流量控制（网络类故障）
        SYSCALL_HOOK,      // 系统调用劫持（磁盘/文件类故障）
        DB_PROXY,          // 数据库代理层注入
        ORCHESTRATOR_API,  // 编排平台API下发（如容器编排层面驱逐节点）
        CONFIG_PUSH        // 配置中心推送异常配置模拟故障
    }

    /**
     * 故障注入参数
     */
    public static class FaultConfig {
        private FaultType type;
        private InjectionMethod method;
        private String target;          // 目标（IP/服务名/方法名）
        private int durationSeconds;    // 持续时间
        private Map<String, String> params; // 额外参数

        // 网络故障相关
        private int delayMillis;        // 延迟毫秒数
        private double lossRate;        // 丢包率
        private int port;              // 目标端口

        // 资源故障相关
        private int cpuPercent;         // CPU使用率目标
        private long memoryBytes;       // 内存填充量
        private long diskBytes;         // 磁盘填充量

        // getter/setter 省略
    }

    /**
     * 注入故障（模板方法）
     */
    public final InjectionResult inject(FaultConfig config) {
        // 1. 前置检查
        if (!preCheck(config)) {
            return InjectionResult.rejected("前置检查未通过");
        }

        // 2. 记录注入前的系统状态（用于后续对比和恢复）
        SystemSnapshot beforeSnapshot = captureSnapshot(config.getTarget());

        // 3. 执行故障注入
        try {
            doInject(config);
        } catch (Exception e) {
            return InjectionResult.failed("注入失败: " + e.getMessage());
        }

        // 4. 验证故障已生效
        boolean effective = verifyInjection(config);
        if (!effective) {
            doRecover(config);
            return InjectionResult.failed("故障注入未生效，已回滚");
        }

        return InjectionResult.success(beforeSnapshot);
    }

    /**
     * 恢复故障
     */
    public final InjectionResult recover(FaultConfig config) {
        try {
            doRecover(config);
            boolean recovered = verifyRecovery(config);
            if (!recovered) {
                return InjectionResult.failed("故障恢复未确认");
            }
            return InjectionResult.success(null);
        } catch (Exception e) {
            return InjectionResult.failed("恢复失败: " + e.getMessage());
        }
    }

    // 子类实现的抽象方法
    protected abstract boolean preCheck(FaultConfig config);
    protected abstract void doInject(FaultConfig config);
    protected abstract void doRecover(FaultConfig config);
    protected abstract boolean verifyInjection(FaultConfig config);
    protected abstract boolean verifyRecovery(FaultConfig config);
    protected abstract SystemSnapshot captureSnapshot(String target);

    public static class InjectionResult {
        boolean success;
        String message;
        SystemSnapshot snapshot;

        static InjectionResult success(SystemSnapshot snapshot) {
            InjectionResult r = new InjectionResult();
            r.success = true;
            r.snapshot = snapshot;
            return r;
        }

        static InjectionResult failed(String msg) {
            InjectionResult r = new InjectionResult();
            r.success = false;
            r.message = msg;
            return r;
        }

        static InjectionResult rejected(String msg) {
            return failed("拒绝执行: " + msg);
        }
    }

    public static class SystemSnapshot {
        double cpuUsage;
        double memoryUsage;
        double diskUsage;
        long activeConnections;
        double errorRate;
        double avgRT;
    }
```

#### 3.1.2 主机层故障注入

```java
/**
 * CPU满载故障注入
 *
 * 实现原理：
 * 创建与CPU核心数相同的线程，每个线程执行无限循环的浮点运算，
 * 消耗CPU资源使CPU使用率达到目标百分比。
 *
 * 控制精度：
 * 使用占空比（Duty Cycle）控制CPU使用率。
 * 例如要达到80%的CPU使用率：
 *   - 在100ms的周期内，繁忙计算80ms，休眠20ms
 *   - 通过调整繁忙时间和休眠时间的比例来精确控制CPU使用率
 */
public class CpuBurnInjector extends FaultInjector {

    private final List<Thread> burnThreads = new ArrayList<>();
    private volatile boolean burning = false;

    @Override
    protected void doInject(FaultConfig config) {
        int targetPercent = config.getCpuPercent();
        int cpuCount = Runtime.getRuntime().availableProcessors();
        burning = true;

        for (int i = 0; i < cpuCount; i++) {
            Thread t = new Thread(() -> {
                while (burning) {
                    long cycleStart = System.nanoTime();
                    long busyDuration = targetPercent * 1_000_000L; // 纳秒
                    long cycleDuration = 100_000_000L; // 100ms周期

                    // 忙等阶段：执行浮点运算消耗CPU
                    while (System.nanoTime() - cycleStart < busyDuration) {
                        Math.sqrt(Math.random());
                    }

                    // 休眠阶段
                    long sleepNanos = cycleDuration - busyDuration;
                    if (sleepNanos > 0) {
                        try {
                            Thread.sleep(sleepNanos / 1_000_000,
                                        (int)(sleepNanos % 1_000_000));
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                            break;
                        }
                    }
                }
            }, "cpu-burn-" + i);
            t.setDaemon(true);
            t.start();
            burnThreads.add(t);
        }
    }

    @Override
    protected void doRecover(FaultConfig config) {
        burning = false;
        for (Thread t : burnThreads) {
            t.interrupt();
        }
        burnThreads.clear();
    }

    @Override
    protected boolean preCheck(FaultConfig config) {
        return config.getCpuPercent() > 0 && config.getCpuPercent() <= 100;
    }

    @Override
    protected boolean verifyInjection(FaultConfig config) {
        // 等待2秒后检查CPU使用率是否达到目标
        try { Thread.sleep(2000); } catch (InterruptedException ignored) {}
        double currentCpuUsage = getCpuUsage();
        return currentCpuUsage > config.getCpuPercent() * 0.8; // 允许20%偏差
    }

    @Override
    protected boolean verifyRecovery(FaultConfig config) {
        try { Thread.sleep(2000); } catch (InterruptedException ignored) {}
        return getCpuUsage() < 50; // CPU恢复到50%以下认为恢复成功
    }

    @Override
    protected SystemSnapshot captureSnapshot(String target) {
        SystemSnapshot snapshot = new SystemSnapshot();
        snapshot.cpuUsage = getCpuUsage();
        return snapshot;
    }

    private double getCpuUsage() {
        OperatingSystemMXBean osBean = ManagementFactory
            .getPlatformMXBean(OperatingSystemMXBean.class);
        return osBean.getProcessCpuLoad() * 100;
    }
}

/**
 * 内存填充故障注入
 *
 * 实现原理：
 * 分配指定大小的字节数组并持有引用，阻止GC回收，
 * 模拟内存泄漏或内存不足的场景。
 *
 * 注意事项：
 * 1. 分批分配，每批1MB，避免一次性分配导致OOM
 * 2. 持有引用防止GC回收
 * 3. 恢复时释放引用并触发GC
 */
public class MemoryFillInjector extends FaultInjector {

    private final List<byte[]> memoryHolder = new ArrayList<>();

    @Override
    protected void doInject(FaultConfig config) {
        long targetBytes = config.getMemoryBytes();
        long allocated = 0;
        int batchSize = 1024 * 1024; // 每批1MB

        while (allocated < targetBytes) {
            int size = (int) Math.min(batchSize, targetBytes - allocated);
            try {
                byte[] block = new byte[size];
                // 写入数据防止操作系统延迟分配（Copy-on-Write优化）
                Arrays.fill(block, (byte) 0xFF);
                memoryHolder.add(block);
                allocated += size;
            } catch (OutOfMemoryError e) {
                // 已达到JVM内存上限，停止分配
                break;
            }
        }
    }

    @Override
    protected void doRecover(FaultConfig config) {
        memoryHolder.clear();
        System.gc(); // 建议GC回收
    }

    @Override
    protected boolean preCheck(FaultConfig config) {
        return config.getMemoryBytes() > 0;
    }

    @Override
    protected boolean verifyInjection(FaultConfig config) {
        return !memoryHolder.isEmpty();
    }

    @Override
    protected boolean verifyRecovery(FaultConfig config) {
        return memoryHolder.isEmpty();
    }

    @Override
    protected SystemSnapshot captureSnapshot(String target) {
        SystemSnapshot snapshot = new SystemSnapshot();
        Runtime rt = Runtime.getRuntime();
        snapshot.memoryUsage = (double)(rt.totalMemory() - rt.freeMemory())
                               / rt.maxMemory() * 100;
        return snapshot;
    }
}
```

#### 3.1.3 网络层故障注入

```java
/**
 * 网络故障注入器
 *
 * 实现原理：通过Linux TC (Traffic Control) 命令操控网络
 *
 * TC 是 Linux 内核提供的流量控制工具，位于网络协议栈的出口处，
 * 可以对发送的数据包进行延迟、丢弃、重排序等操作。
 *
 * TC的核心概念：
 * - qdisc（排队规则）：控制数据包如何排队和发送
 * - class（类别）：将流量分类
 * - filter（过滤器）：将数据包匹配到特定类别
 *
 * 使用netem（Network Emulator）模块模拟各种网络故障
 */
public class NetworkFaultInjector extends FaultInjector {

    /**
     * 网络延迟注入
     *
     * 算法：使用TC netem在网卡出口添加延迟
     *
     * 命令解析：
     * tc qdisc add dev eth0 root netem delay 200ms 50ms
     *   - dev eth0: 操作的网卡
     *   - root: 根排队规则
     *   - netem: Network Emulator模块
     *   - delay 200ms: 固定延迟200ms
     *   - 50ms: 延迟波动范围（200±50ms）
     *
     * 可以进一步限制只对特定IP/端口注入延迟：
     * 使用tc filter配合iptables mark实现精准控制
     */
    public static class NetworkDelayInjector extends FaultInjector {

        @Override
        protected void doInject(FaultConfig config) {
            int delayMs = config.getDelayMillis();
            String targetIp = config.getTarget();
            int targetPort = config.getPort();

            // 步骤1：创建根qdisc（使用prio分类排队规则）
            executeCommand("tc qdisc add dev eth0 root handle 1: prio");

            // 步骤2：在band 3上添加netem延迟
            executeCommand(String.format(
                "tc qdisc add dev eth0 parent 1:3 handle 30: netem delay %dms",
                delayMs
            ));

            // 步骤3：添加过滤器，只对目标IP和端口的流量生效
            if (targetIp != null && !targetIp.isEmpty()) {
                executeCommand(String.format(
                    "tc filter add dev eth0 protocol ip parent 1:0 prio 3 " +
                    "u32 match ip dst %s match ip dport %d 0xffff flowid 1:3",
                    targetIp, targetPort
                ));
            }
        }

        @Override
        protected void doRecover(FaultConfig config) {
            // 删除根qdisc，所有子qdisc和filter自动删除
            executeCommand("tc qdisc del dev eth0 root");
        }

        @Override
        protected boolean preCheck(FaultConfig config) {
            return config.getDelayMillis() > 0;
        }

        @Override
        protected boolean verifyInjection(FaultConfig config) {
            // 使用ping验证延迟是否生效
            String result = executeCommand(
                "ping -c 3 " + config.getTarget());
            return result.contains("time=");
        }

        @Override
        protected boolean verifyRecovery(FaultConfig config) {
            String qdiscInfo = executeCommand("tc qdisc show dev eth0");
            return !qdiscInfo.contains("netem");
        }

        @Override
        protected SystemSnapshot captureSnapshot(String target) {
            return new SystemSnapshot();
        }

        private String executeCommand(String cmd) {
            // 实际实现中通过ProcessBuilder执行shell命令并返回输出
            // 此处为示意
            return "";
        }
    }

    /**
     * 可用区级网络分区注入
     *
     * 用于模拟某个可用区与其他可用区完全失联的场景，
     * 是"长链路演练"和"生产级容灾演练"中最常用的故障类型。
     *
     * 实现思路：
     * 1. 在可用区边界的核心交换机/路由器上下发ACL规则，
     *    丢弃所有跨可用区的流量
     * 2. 或者在每台机器上通过iptables封禁目标可用区网段
     * 3. 支持"逃逸优先"（先把流量切走再断网）和
     *    "直接断网"（不预先切流，直接制造网络分区）两种模式，
     *    分别验证不同的故障场景
     */
    public static class AzPartitionInjector extends FaultInjector {

        @Override
        protected void doInject(FaultConfig config) {
            String azCidr = config.getParams().get("azCidr");
            String mode = config.getParams().getOrDefault("mode", "cutoff");

            if ("escape".equals(mode)) {
                // 逃逸模式：先通知流量调度层将该可用区权重降为0
                drainTrafficFromAz(config.getTarget());
                waitForTrafficDrain(30); // 等待流量排空
            }

            // 下发网络隔离规则，实现可用区级网络分区
            executeCommand(String.format(
                "iptables -A INPUT -s %s -j DROP", azCidr));
            executeCommand(String.format(
                "iptables -A OUTPUT -d %s -j DROP", azCidr));
        }

        @Override
        protected void doRecover(FaultConfig config) {
            String azCidr = config.getParams().get("azCidr");
            executeCommand(String.format(
                "iptables -D INPUT -s %s -j DROP", azCidr));
            executeCommand(String.format(
                "iptables -D OUTPUT -d %s -j DROP", azCidr));
            restoreTrafficToAz(config.getTarget());
        }

        @Override
        protected boolean preCheck(FaultConfig config) {
            // 生产级演练前置检查：确认已完成审批、确认演练窗口、
            // 确认存在至少两个健康可用区可以承接流量
            return config.getParams().containsKey("azCidr")
                   && isApproved(config)
                   && hasEnoughHealthyAzs();
        }

        @Override
        protected boolean verifyInjection(FaultConfig config) {
            return true;
        }

        @Override
        protected boolean verifyRecovery(FaultConfig config) {
            return true;
        }

        @Override
        protected SystemSnapshot captureSnapshot(String target) {
            return new SystemSnapshot();
        }

        private void drainTrafficFromAz(String az) {}
        private void waitForTrafficDrain(int seconds) {}
        private void restoreTrafficToAz(String az) {}
        private boolean isApproved(FaultConfig config) { return true; }
        private boolean hasEnoughHealthyAzs() { return true; }
        private String executeCommand(String cmd) { return ""; }
    }
}
```

### 3.2 数据库混沌演练平台设计

数据库是几乎所有系统里"爆炸半径最大、恢复最复杂"的一环，因此专门为数据库设计一套独立的混沌演练平台是非常必要的。一个成熟的数据库混沌演练平台通常需要同时支持 **MySQL 主从架构**和 **MGR（MySQL Group Replication，多主复制组）架构**两类主流部署形态，覆盖主库故障、从库故障、主从延迟、磁盘故障、线程数飙高等 6 类典型故障场景，并通过 9 种不同的故障注入手段实现，具备对 2000+ 集群同时发起演练的规模化能力。

#### 3.2.2 演练全生命周期管理

数据库故障演练的风险等级远高于普通应用层故障，因此必须建立一套完整的全生命周期管理流程：**权限认证 → 演练规划 → 编排调度 → 风险评估 → 故障注入 → 指标观测 → 演练复盘**，每一步都有明确的准入条件和产出物。

```java
/**
 * 数据库混沌演练全生命周期管理器
 *
 * 生命周期七个阶段，每个阶段都是下一阶段的前置条件，
 * 任何一个阶段失败都会导致演练被拒绝或中止
 */
public class DbChaosLifecycleManager {

    public enum Phase {
        AUTHENTICATION,   // 1. 权限认证：确认发起人对目标集群有演练权限
        PLANNING,         // 2. 演练规划：选择集群、场景、时间窗口
        ORCHESTRATION,    // 3. 编排调度：生成执行计划，处理集群依赖关系
        RISK_ASSESSMENT,  // 4. 风险评估：评估爆炸半径、业务影响面、回滚方案
        FAULT_INJECTION,  // 5. 故障注入：实际执行故障注入动作
        METRIC_OBSERVATION, // 6. 指标观测：持续采集关键指标，判断是否符合预期
        DRILL_REVIEW      // 7. 演练复盘：生成报告，沉淀问题清单和改进项
    }

    private final PermissionService permissionService;
    private final RiskAssessmentService riskAssessmentService;
    private final FaultInjectionService injectionService;
    private final MetricObservationService observationService;

    public DbChaosLifecycleManager(PermissionService permissionService,
                                    RiskAssessmentService riskAssessmentService,
                                    FaultInjectionService injectionService,
                                    MetricObservationService observationService) {
        this.permissionService = permissionService;
        this.riskAssessmentService = riskAssessmentService;
        this.injectionService = injectionService;
        this.observationService = observationService;
    }

    /**
     * 执行完整的数据库混沌演练全流程
     */
    public DrillResult runFullLifecycle(DrillPlan plan) {
        DrillResult result = new DrillResult();
        result.planId = plan.id;

        // === 1. 权限认证 ===
        if (!permissionService.hasPermission(plan.operator, plan.clusterIds)) {
            result.phase = Phase.AUTHENTICATION;
            result.success = false;
            result.message = "发起人无权限操作目标集群";
            return result;
        }

        // === 2. 演练规划：校验计划完整性 ===
        if (!validatePlan(plan)) {
            result.phase = Phase.PLANNING;
            result.success = false;
            result.message = "演练计划校验失败：缺少必要字段或时间窗口不合法";
            return result;
        }

        // === 3. 编排调度：处理多集群依赖，生成执行批次 ===
        List<ExecutionBatch> batches = orchestrate(plan);
        result.totalBatches = batches.size();

        // === 4. 风险评估 ===
        RiskAssessmentResult risk = riskAssessmentService.assess(plan);
        if (risk.riskLevel == RiskLevel.CRITICAL) {
            result.phase = Phase.RISK_ASSESSMENT;
            result.success = false;
            result.message = "风险评估未通过：" + risk.reason;
            return result;
        }
        result.riskLevel = risk.riskLevel;

        // === 5~6. 逐批执行故障注入 + 实时指标观测 ===
        for (ExecutionBatch batch : batches) {
            BatchResult batchResult = executeBatchWithObservation(batch, plan);
            result.batchResults.add(batchResult);

            // 一旦某批次触发了紧急终止条件，立即停止后续批次
            if (batchResult.emergencyStopped) {
                result.emergencyStopped = true;
                break;
            }
        }

        // === 7. 演练复盘 ===
        result.reviewSummary = generateReviewSummary(result);
        result.success = !result.emergencyStopped;

        return result;
    }

    /**
     * 单个批次：注入 + 观测 + 恢复 的完整闭环
     */
    private BatchResult executeBatchWithObservation(ExecutionBatch batch,
                                                     DrillPlan plan) {
        BatchResult result = new BatchResult();
        result.batchId = batch.id;

        // 注入前采集基线
        MetricBaseline baseline = observationService.captureBaseline(
            batch.clusterIds, plan.baselineWindowSeconds);

        // 执行注入
        InjectionOutcome outcome = injectionService.injectBatch(batch);
        result.injectionOutcome = outcome;

        if (!outcome.allSucceeded()) {
            result.emergencyStopped = true;
            result.reason = "批次内存在注入失败的集群，触发保护性终止";
            injectionService.recoverBatch(batch); // 立即回滚已注入的部分
            return result;
        }

        // 持续观测：期间任何时刻发现核心指标越界都会中断
        boolean withinBounds = observationService.observeDuring(
            batch.clusterIds,
            baseline,
            plan.injectionDurationSeconds,
            (deviation) -> {
                if (deviation.severity == Severity.CRITICAL) {
                    injectionService.recoverBatch(batch);
                }
            }
        );

        if (!withinBounds) {
            result.emergencyStopped = true;
            result.reason = "指标观测期间发现严重偏离，已自动回滚";
        } else {
            // 正常结束，主动恢复故障
            injectionService.recoverBatch(batch);
        }

        return result;
    }

    private boolean validatePlan(DrillPlan plan) {
        return plan.clusterIds != null && !plan.clusterIds.isEmpty()
               && plan.scenario != null
               && plan.windowStart != null;
    }

    private List<ExecutionBatch> orchestrate(DrillPlan plan) {
        // 按集群拓扑分批，避免同一批次内出现相互依赖的集群
        // （例如避免把某个业务的主库集群和它强依赖的配置集群分到同一批）
        List<ExecutionBatch> batches = new ArrayList<>();
        int batchSize = plan.maxConcurrency; // 单批最大并发集群数
        List<String> clusters = plan.clusterIds;
        for (int i = 0; i < clusters.size(); i += batchSize) {
            ExecutionBatch batch = new ExecutionBatch();
            batch.id = "batch-" + (i / batchSize);
            batch.clusterIds = clusters.subList(
                i, Math.min(i + batchSize, clusters.size()));
            batches.add(batch);
        }
        return batches;
    }

    private String generateReviewSummary(DrillResult result) {
        return String.format(
            "演练计划 %s 共执行 %d 个批次，%s",
            result.planId, result.totalBatches,
            result.emergencyStopped ? "因触发保护性终止提前结束" : "全部正常完成");
    }

    // ==== 数据结构定义 ====

    public static class DrillPlan {
        String id;
        String operator;
        List<String> clusterIds;
        DbFaultScenario scenario;
        Date windowStart;
        int maxConcurrency;
        int baselineWindowSeconds;
        int injectionDurationSeconds;
    }

    public static class ExecutionBatch {
        String id;
        List<String> clusterIds;
    }

    public static class DrillResult {
        String planId;
        Phase phase;
        boolean success;
        boolean emergencyStopped;
        String message;
        int totalBatches;
        RiskLevel riskLevel;
        String reviewSummary;
        List<BatchResult> batchResults = new ArrayList<>();
    }

    public static class BatchResult {
        String batchId;
        InjectionOutcome injectionOutcome;
        boolean emergencyStopped;
        String reason;
    }

    public enum RiskLevel { LOW, MEDIUM, HIGH, CRITICAL }
    public enum Severity { INFO, WARNING, CRITICAL }

    public static class RiskAssessmentResult {
        RiskLevel riskLevel;
        String reason;
    }

    public static class InjectionOutcome {
        boolean allSucceeded() { return true; }
    }

    public static class MetricBaseline {}

    // 依赖的服务接口
    public interface PermissionService {
        boolean hasPermission(String operator, List<String> clusterIds);
    }
    public interface RiskAssessmentService {
        RiskAssessmentResult assess(DrillPlan plan);
    }
    public interface FaultInjectionService {
        InjectionOutcome injectBatch(ExecutionBatch batch);
        void recoverBatch(ExecutionBatch batch);
    }
    public interface MetricObservationService {
        MetricBaseline captureBaseline(List<String> clusterIds, int windowSeconds);
        boolean observeDuring(List<String> clusterIds, MetricBaseline baseline,
                              int durationSeconds,
                              java.util.function.Consumer<Deviation> onDeviation);
    }
    public static class Deviation {

    }
```

#### 3.2.3 规模化能力：面向 2000+ 集群的并发演练调度

当演练规模扩大到成千上万个数据库集群时，单纯的串行执行完全无法满足时效性要求，必须依靠合理的并发调度、限流保护和进度追踪机制。

```java
/**
 * 大规模集群并发演练调度器
 *
 * 设计目标：支持2000+集群同时具备演练能力，
 * 核心手段是"分片并发 + 全局限流 + 实时进度追踪"
 *
 * 并发控制的关键考量：
 * 1. 不能对同一个物理机房/同一个上游依赖服务造成过大瞬时压力
 * 2. 需要预留足够的观测窗口，而不是"注入完就立刻切下一批"
 * 3. 任意集群的异常都不应该阻塞其他集群的正常调度
 */
public class MassiveScaleDrillScheduler {

    private final ExecutorService executorPool;
    private final Semaphore globalConcurrencyLimiter;
    private final Map<String, ClusterDrillProgress> progressMap
        = new ConcurrentHashMap<>();

    public MassiveScaleDrillScheduler(int maxGlobalConcurrency,
                                       int workerThreads) {
        this.executorPool = Executors.newFixedThreadPool(workerThreads);
        this.globalConcurrencyLimiter = new Semaphore(maxGlobalConcurrency);
    }

    /**
     * 提交大规模演练任务
     *
     * @param clusterIds 目标集群列表（可达2000+）
     * @param scenario   故障场景
     * @param perClusterLimiter 按机房/依赖服务维度的二级限流器
     */
    public CompletableFuture<ScheduleSummary> submitMassiveDrill(
            List<String> clusterIds,
            DbFaultScenario scenario,
            Map<String, Semaphore> perClusterLimiter) {

        List<CompletableFuture<ClusterDrillProgress>> futures =
            new ArrayList<>();

        for (String clusterId : clusterIds) {
            ClusterDrillProgress progress = new ClusterDrillProgress();
            progress.clusterId = clusterId;
            progress.status = DrillStatus.QUEUED;
            progressMap.put(clusterId, progress);

            CompletableFuture<ClusterDrillProgress> future =
                CompletableFuture.supplyAsync(
                    () -> executeSingleClusterDrill(clusterId, scenario,
                                                     perClusterLimiter),
                    executorPool
                );
            futures.add(future);
        }

        return CompletableFuture.allOf(
                futures.toArray(new CompletableFuture[0]))
            .thenApply(v -> summarize(futures));
    }

    private ClusterDrillProgress executeSingleClusterDrill(
            String clusterId,
            DbFaultScenario scenario,
            Map<String, Semaphore> perClusterLimiter) {

        ClusterDrillProgress progress = progressMap.get(clusterId);

        try {
            // 全局并发闸门：控制整体并发规模，避免瞬时资源冲击
            globalConcurrencyLimiter.acquire();

            // 机房级/依赖服务级二级闸门：避免单个机房被过度集中演练
            String room = resolveRoom(clusterId);
            Semaphore roomLimiter = perClusterLimiter.get(room);
            if (roomLimiter != null) {
                roomLimiter.acquire();
            }

            progress.status = DrillStatus.INJECTING;
            progress.startTime = System.currentTimeMillis();

            // 实际注入逻辑（复用前文的FaultInjector体系）
            boolean injected = doInject(clusterId, scenario);
            if (!injected) {
                progress.status = DrillStatus.INJECTION_FAILED;
                return progress;
            }

            progress.status = DrillStatus.OBSERVING;
            boolean healthy = observeAndValidate(clusterId, scenario);

            progress.status = healthy ? DrillStatus.PASSED
                                       : DrillStatus.FAILED_DEVIATION;

            // 无论结果如何，都要主动恢复
            doRecover(clusterId, scenario);
            progress.status = healthy ? DrillStatus.COMPLETED
                                       : DrillStatus.COMPLETED_WITH_ISSUES;

            if (roomLimiter != null) {
                roomLimiter.release();
            }

        } catch (Exception e) {
            progress.status = DrillStatus.ERROR;
            progress.errorMessage = e.getMessage();
            // 异常场景下强制尝试恢复，避免故障遗留在生产环境
            try {
                doRecover(clusterId, scenario);
            } catch (Exception ignore) {
                progress.recoveryFailed = true;
            }
        } finally {
            globalConcurrencyLimiter.release();
            progress.endTime = System.currentTimeMillis();
        }

        return progress;
    }

    private ScheduleSummary summarize(
            List<CompletableFuture<ClusterDrillProgress>> futures) {
        ScheduleSummary summary = new ScheduleSummary();
        for (CompletableFuture<ClusterDrillProgress> f : futures) {
            ClusterDrillProgress p = f.join();
            summary.total++;
            if (p.status == DrillStatus.COMPLETED) summary.passed++;
            else if (p.status == DrillStatus.COMPLETED_WITH_ISSUES
                     || p.status == DrillStatus.FAILED_DEVIATION) {
                summary.failed++;
            } else if (p.status == DrillStatus.ERROR
                       || p.status == DrillStatus.INJECTION_FAILED) {
                summary.errored++;
            }
        }
        return summary;
    }

    private String resolveRoom(String clusterId) { return "room-default"; }
    private boolean doInject(String clusterId, DbFaultScenario scenario) {
        return true;
    }
    private boolean observeAndValidate(String clusterId,
                                       DbFaultScenario scenario) {
        return true;
    }
    private void doRecover(String clusterId, DbFaultScenario scenario) {}

    public enum DrillStatus {
        QUEUED, INJECTING, INJECTION_FAILED, OBSERVING,
        PASSED, FAILED_DEVIATION, COMPLETED, COMPLETED_WITH_ISSUES, ERROR
    }

    public static class ClusterDrillProgress {
        String clusterId;
        DrillStatus status;
        long startTime;
        long endTime;
        String errorMessage;
        boolean recoveryFailed;
    }

    public static class ScheduleSummary {
        int total;
        int passed;
        int failed;
        int errored;
    }
}
```

#### 3.2.4 高级能力：随机无预告演练与链路故障演练

平台化能力成熟之后，还可以进一步演进出两类高级演练模式：

- **随机无预告演练**：由平台按照预设的故障场景库和目标集群池，随机选择时间、随机选择场景、随机选择目标发起演练，值班人员事先并不知情。这种方式最大程度还原了真实故障"猝不及防"的特点，是检验值班响应流程、监控告警灵敏度的最有效手段。
- **链路故障演练**：不再局限于单个数据库实例的故障，而是沿着一条业务链路（应用 → 连接池 → 代理层 → 数据库主库 → 数据库从库）依次或组合注入故障，验证链路上每一环的容错设计是否形成了完整闭环，而不是"点上都通、连起来就断"。

```java
/**
 * 随机无预告演练调度器
 *
 * 核心思想：把"什么时候演练、演练什么"从人工计划
 * 转变为平台按策略随机决策，从而模拟真实故障的不可预测性
 */
public class RandomUnannouncedDrillScheduler {

    private final List<DbFaultScenario> scenarioPool;
    private final List<String> eligibleClusterPool; // 已具备演练资质的集群池
    private final Random random = new Random();

    public RandomUnannouncedDrillScheduler(List<DbFaultScenario> scenarioPool,
                                            List<String> eligibleClusterPool) {
        this.scenarioPool = scenarioPool;
        this.eligibleClusterPool = eligibleClusterPool;
    }

    /**
     * 每日随机触发一次无预告演练
     * 由定时任务在业务低峰的随机时间点调用
     */
    public void triggerRandomDrill() {
        // 1. 随机选择场景
        DbFaultScenario scenario = scenarioPool.get(
            random.nextInt(scenarioPool.size()));

        // 2. 随机选择目标集群（通常一次只选1~3个，控制爆炸半径）
        int targetCount = 1 + random.nextInt(3);
        List<String> targets = pickRandomClusters(targetCount);

        // 3. 不发送提前通知，直接进入演练流程
        //    但会记录审计日志，演练结束后才对外披露
        DbChaosLifecycleManager.DrillPlan plan =
            new DbChaosLifecycleManager.DrillPlan();
        plan.id = "random-" + System.currentTimeMillis();
        plan.operator = "SYSTEM_SCHEDULER";
        plan.clusterIds = targets;
        plan.scenario = scenario;
        plan.maxConcurrency = targetCount;
        plan.baselineWindowSeconds = 60;
        plan.injectionDurationSeconds = 120;

        // 交由生命周期管理器执行，全程与常规演练走相同的安全管控流程
        // lifecycleManager.runFullLifecycle(plan);
    }

    private List<String> pickRandomClusters(int count) {
        List<String> shuffled = new ArrayList<>(eligibleClusterPool);
        Collections.shuffle(shuffled, random);
        return shuffled.subList(0, Math.min(count, shuffled.size()));
    }
}
```

### 3.3 通用演练实验生命周期管理

除了数据库这类专项场景，平台还需要为应用层、中间件层的通用演练场景提供统一的实验生命周期管理能力。核心是用状态机固化"实验从创建到结束"的每一步，避免出现"注入了故障但没人记得回滚"这类低级但后果严重的问题。

#### 3.3.1 实验状态机

```java
/**
 * 演练实验状态机
 *
 * 设计模式：状态模式
 *
 * 状态流转：
 * CREATED → APPROVED → PREPARING → RUNNING → RECOVERING → COMPLETED
 *                                     ↓
 *                                  EMERGENCY_STOP → RECOVERED
 *
 * 每个状态都有明确的进入条件和退出条件
 */
public class ExperimentStateMachine {

    public enum State {
        CREATED,         // 已创建，等待审批
        APPROVED,        // 已审批，等待执行
        PREPARING,       // 准备中（检查环境、采集基线）
        RUNNING,         // 运行中（故障已注入）
        RECOVERING,      // 恢复中（正在撤销故障）
        COMPLETED,       // 已完成（正常结束）
        EMERGENCY_STOP,  // 紧急终止（触发安全条件）
        RECOVERED,       // 已恢复（紧急终止后恢复完成）
        FAILED           // 失败（注入或恢复过程出错）
    }

    /**
     * 状态转换规则
     */
    private static final Map<State, Set<State>> TRANSITIONS = Map.of(
        State.CREATED, Set.of(State.APPROVED),
        State.APPROVED, Set.of(State.PREPARING),
        State.PREPARING, Set.of(State.RUNNING, State.FAILED),
        State.RUNNING, Set.of(State.RECOVERING, State.EMERGENCY_STOP),
        State.RECOVERING, Set.of(State.COMPLETED, State.FAILED),
        State.EMERGENCY_STOP, Set.of(State.RECOVERED, State.FAILED),
        State.COMPLETED, Set.of(),  // 终态
        State.RECOVERED, Set.of(),  // 终态
        State.FAILED, Set.of()      // 终态
    );

    private volatile State currentState = State.CREATED;
    private final List<StateChangeListener> listeners = new ArrayList<>();

    /**
     * 状态变更监听器接口
     * 使用观察者模式通知各模块状态变化
     */
    public interface StateChangeListener {
        void onStateChange(State from, State to, String reason);
    }

    /**
     * 尝试状态转换
     *
     * @param targetState 目标状态
     * @param reason      转换原因
     * @return 是否转换成功
     */
    public synchronized boolean transition(State targetState, String reason) {
        Set<State> allowedTargets = TRANSITIONS.get(currentState);
        if (allowedTargets == null || !allowedTargets.contains(targetState)) {
            System.err.println(String.format(
                "非法状态转换: %s -> %s", currentState, targetState));
            return false;
        }

        State from = currentState;
        currentState = targetState;

        // 通知所有监听器
        for (StateChangeListener listener : listeners) {
            listener.onStateChange(from, targetState, reason);
        }

        return true;
    }

    public State getCurrentState() {
        return currentState;
    }

    public void addListener(StateChangeListener listener) {
        listeners.add(listener);
    }
}

/**
 * 演练实验执行器
 *
 * 将状态机与故障注入引擎串联，实现完整的演练流程
 */
public class ExperimentExecutor {

    private final ExperimentStateMachine stateMachine;
    private final FaultInjector injector;
    private final SafetyGuard safetyGuard;
    private final MetricsCollector metricsCollector;

    /**
     * 实验定义
     */
    public static class Experiment {
        String id;
        String name;
        String description;
        FaultInjector.FaultConfig faultConfig;

        // 稳态假设
        double maxErrorRate;    // 最大可接受错误率
        double maxP99RT;        // 最大可接受P99 RT（秒）
        double maxCpuUsage;     // 最大可接受CPU使用率

        // 演练参数
        int baselineDurationSeconds;  // 基线采集时间
        int injectionDurationSeconds; // 故障注入时间
        int recoveryWaitSeconds;      // 恢复等待时间
    }

    public ExperimentExecutor(FaultInjector injector,
                             SafetyGuard safetyGuard,
                             MetricsCollector metricsCollector) {
        this.stateMachine = new ExperimentStateMachine();
        this.injector = injector;
        this.safetyGuard = safetyGuard;
        this.metricsCollector = metricsCollector;

        // 注册安全守卫监听器
        stateMachine.addListener(safetyGuard);
    }

    /**
     * 执行完整的演练实验
     *
     * 算法流程（核心链路）：
     *
     * 1. PREPARING阶段：
     *    a. 采集当前系统基线指标（作为"稳态"的参考值）
     *    b. 注册安全守卫（自动终止条件）
     *    c. 通知相关团队演练即将开始
     *
     * 2. RUNNING阶段：
     *    a. 执行故障注入
     *    b. 持续监控系统指标
     *    c. 实时对比基线，检测是否超出稳态假设
     *    d. 安全守卫随时准备紧急终止
     *
     * 3. RECOVERING阶段：
     *    a. 撤销故障注入
     *    b. 等待系统恢复到稳态
     *    c. 验证恢复完成
     *
     * 4. COMPLETED阶段：
     *    a. 生成实验报告
     *    b. 评估实验结果（通过/未通过）
     */
    public ExperimentReport execute(Experiment experiment) {
        ExperimentReport report = new ExperimentReport();
        report.experimentId = experiment.id;
        report.experimentName = experiment.name;
        report.startTime = System.currentTimeMillis();

        try {
            // === Phase 1: 准备 ===
            stateMachine.transition(
                ExperimentStateMachine.State.APPROVED, "自动审批");
            stateMachine.transition(
                ExperimentStateMachine.State.PREPARING, "开始准备");

            // 采集基线指标
            MetricsSnapshot baseline = metricsCollector
                .collectBaseline(experiment.baselineDurationSeconds);
            report.baseline = baseline;

            // 注册安全守卫
            safetyGuard.register(experiment);

            // === Phase 2: 故障注入 ===
            stateMachine.transition(
                ExperimentStateMachine.State.RUNNING, "开始注入故障");

            FaultInjector.InjectionResult injectResult =
                injector.inject(experiment.faultConfig);
            if (!injectResult.success) {
                stateMachine.transition(
                    ExperimentStateMachine.State.FAILED,
                    injectResult.message);
                report.success = false;
                report.failureReason = injectResult.message;
                return report;
            }

            // 持续监控（在故障注入持续期间）
            List<MetricsSnapshot> duringFault = new ArrayList<>();
            long endTime = System.currentTimeMillis()
                          + experiment.injectionDurationSeconds * 1000L;

            while (System.currentTimeMillis() < endTime) {
                // 检查安全守卫是否触发紧急终止
                if (stateMachine.getCurrentState()
                    == ExperimentStateMachine.State.EMERGENCY_STOP) {
                    break;
                }

                MetricsSnapshot snapshot = metricsCollector.collectCurrent();
                duringFault.add(snapshot);

                // 检查是否超出稳态假设
                if (isDeviated(snapshot, experiment)) {
                    report.deviationDetected = true;
                    report.deviationDetails = describeDeviation(
                        snapshot, experiment);
                }

                Thread.sleep(1000); // 每秒采集一次
            }
            report.duringFaultMetrics = duringFault;

            // === Phase 3: 恢复 ===
            stateMachine.transition(
                ExperimentStateMachine.State.RECOVERING, "开始恢复");

            injector.recover(experiment.faultConfig);

            // 等待系统恢复
            Thread.sleep(experiment.recoveryWaitSeconds * 1000L);

            // 采集恢复后的指标
            MetricsSnapshot afterRecovery =
                metricsCollector.collectCurrent();
            report.afterRecovery = afterRecovery;

            // === Phase 4: 完成 ===
            stateMachine.transition(
                ExperimentStateMachine.State.COMPLETED, "实验完成");

            report.success = true;
            report.endTime = System.currentTimeMillis();

            // 评估实验结果
            evaluateResult(report, experiment);

        } catch (Exception e) {
            // 异常情况下也要恢复故障
            try {
                injector.recover(experiment.faultConfig);
            } catch (Exception recoverErr) {
                report.recoveryFailed = true;
            }
            stateMachine.transition(
                ExperimentStateMachine.State.FAILED, e.getMessage());
            report.success = false;
            report.failureReason = e.getMessage();
        }

        return report;
    }

    /**
     * 检测是否偏离稳态假设
     */
    private boolean isDeviated(MetricsSnapshot snapshot,
                               Experiment experiment) {
        return snapshot.errorRate > experiment.maxErrorRate
               || snapshot.p99RT > experiment.maxP99RT
               || snapshot.cpuUsage > experiment.maxCpuUsage;
    }

    private String describeDeviation(MetricsSnapshot snapshot,
                                     Experiment experiment) {
        StringBuilder sb = new StringBuilder("偏离检测: ");
        if (snapshot.errorRate > experiment.maxErrorRate) {
            sb.append(String.format("错误率 %.2f%% > %.2f%%; ",
                snapshot.errorRate * 100, experiment.maxErrorRate * 100));
        }
        if (snapshot.p99RT > experiment.maxP99RT) {
            sb.append(String.format("P99 RT %.0fms > %.0fms; ",
                snapshot.p99RT * 1000, experiment.maxP99RT * 1000));
        }
        return sb.toString();
    }

    /**
     * 评估实验结果
     *
     * 通过条件：
     * 1. 故障注入后，系统指标虽然有波动，但仍在稳态假设范围内
     *    → 说明系统具备对该故障的抵抗能力
     *
     * 未通过条件：
     * 1. 故障注入后，系统指标超出稳态假设
     *    → 说明系统对该故障缺乏抵抗能力，需要改进
     * 2. 故障恢复后，系统未能在规定时间内恢复
     *    → 说明系统的自愈能力不足
     */
    private void evaluateResult(ExperimentReport report,
                                Experiment experiment) {
        if (report.deviationDetected) {
            report.verdict = "FAILED";
            report.recommendations.add("系统在故障场景下偏离了稳态假设，"
                + "需要加强对应的容错机制");
        } else {
            report.verdict = "PASSED";
            report.recommendations.add("系统成功抵御了故障，"
                + "建议提高故障强度继续验证");
        }

        // 检查恢复速度
        if (report.afterRecovery != null) {
            boolean recovered = !isDeviated(report.afterRecovery, experiment);
            if (!recovered) {
                report.verdict = "FAILED";
                report.recommendations.add("故障恢复后系统未完全恢复，"
                    + "需要改进自愈机制");
            }
        }
    }

    /**
     * 实验报告
     */
    public static class ExperimentReport {
        String experimentId;
        String experimentName;
        long startTime;
        long endTime;
        boolean success;
        String verdict;         // PASSED / FAILED
        String failureReason;
        boolean deviationDetected;
        String deviationDetails;
        boolean recoveryFailed;
        MetricsSnapshot baseline;
        List<MetricsSnapshot> duringFaultMetrics;
        MetricsSnapshot afterRecovery;
        List<String> recommendations = new ArrayList<>();
    }

    /**
     * 指标快照
     */
    public static class MetricsSnapshot {
        long timestamp;
        double errorRate;
        double avgRT;
        double p99RT;
        double cpuUsage;
        double memoryUsage;
        double qps;
    }
}
```

### 3.4 行业可用区级容灾演练实践对标

可用区（AZ）级容灾演练是所有演练类型中风险最高、收益也最大的一类，直接关系到"某个机房整体不可用时，业务能否在可接受的时间窗口内恢复"。通过对行业内多家一线互联网公司的实践进行调研对比，可以总结出几种典型的技术路线，各有取舍：

| 对比维度 | 实践一：网络断开（Cutoff）优先 | 实践二：逃逸+断开分阶段 | 实践三：仅逃逸不断开 | 实践四：网络拥塞+局部断开 |
|---------|------------------------|------------------|--------------|----------------|
| 核心做法 | 提前切走大部分流量，仅保留一个分片验证，随后直接断网 | 先做流量逃逸（Escape），确认无影响后再做网络断开（Cutoff） | 触发全量流量切走（Escape），所有服务执行AZ级故障转移，但不真正切断网络 | 单可用区网络拥塞（丢包率从5%逐步提升到50%），并对多组TOR交换机做断开 |
| 覆盖范围 | 核心链路 | 识别出330条核心链路，实际演练139条，分7个阶段逐步扩大范围 | 全量服务触发AZ级故障转移 | 45台TOR交换机、约1600台机器 |
| 演练频率 | 每2~3个月一次 | 未特别说明周期，采用分阶段推进 | 每季度一次 | 未特别说明周期 |
| 演练窗口 | 凌晨3点 | 凌晨2点到6点 | 未特别说明 | 未特别说明 |
| 单次时长 | 15~30分钟 | 未特别说明 | 未特别说明 | 未特别说明 |
| RPO/RTO 目标 | RPO=0，RTO<30秒（依赖分布式数据库的自动故障转移能力） | 未特别说明具体数值，以链路是否受影响作为通过标准 | 未特别说明 | 未特别说明 |
| 风险控制手段 | 提前切走多数流量降低真实影响面，仅用最小分片验证断网效果 | 逃逸和断开分离为两个独立阶段，前一阶段验证通过才进入下一阶段 | 只做故障转移演练，不引入真实网络中断的不确定性 | 丢包率逐步递增（从5%到50%），避免瞬间全量冲击 |

从这份对比可以提炼出几条具有普适性的经验：

1. **"先逃逸、再断网"是更稳妥的路径**：大部分成熟实践都会先把流量从目标可用区切走（或大部分切走），确认业务无感知之后，再进行真正的网络断开，这样即使断网环节出现意外，真实影响面也已经被控制在最小范围。
2. **核心链路要预先梳理并分级**，不可能一次性对全部链路做可用区级演练，必须先识别出真正的核心链路清单，再按照重要程度、影响面大小分阶段扩大演练范围，循序渐进地积累信心。
3. **演练窗口普遍选择在业务低峰期的凌晨时段**，且大多控制在半小时以内，尽量把"即使出现意外，恢复也可以很快完成"作为硬性前提。
4. **"渐进式故障强度"优于"一步到位"**：无论是网络丢包率从 5% 逐步爬升到 50%，还是分 7 个阶段逐步扩大演练链路范围，本质上都是通过控制变量、逐步加压的方式，在每一步都留出观察和止损的空间。
5. **RPO/RTO 指标是可用区级演练的终极考核标准**，只有把恢复时间目标和恢复点目标量化下来，演练才有明确的"通过/不通过"判定依据，而不是停留在"感觉还行"的主观判断上。

### 3.5 混沌工程工具生态

在建设自有平台的同时，理解业界主流开源与商业工具的能力边界，有助于合理选型或者复用现成能力，避免重复造轮子。

| 工具/平台 | 类型 | 核心能力 | 特点 |
|----------|------|---------|------|
| 随机实例终止工具 | 商业实践先驱（对标 Chaos Monkey 理念） | 在生产环境中随机、持续地终止服务实例 | 混沌工程的开创性实践，倒逼团队从设计之初就假设"任何实例随时可能消失" |
| 可用区级关闭工具 | 商业实践先驱（对标 Chaos Kong 理念） | 模拟整个可用区/区域级别的能力丧失 | 验证跨区域容灾架构在最极端场景下的真实表现 |
| 故障注入测试框架 | 商业实践先驱（对标 FIT 理念） | 提供统一的故障注入元数据协议，可在请求级别精确控制注入范围 | 通过在请求头中传递"故障注入上下文"，实现极细粒度的爆炸半径控制 |
| 混沌自动化平台 | 商业实践先驱（对标 ChAP 理念） | 将混沌工程实验自动化、常态化，自动挑选实验对象和参数 | 强调用算法自动决策"下一个实验做什么"，而不是完全依赖人工规划 |
| 通用故障注入工具 | 开源（对标 ChaosBlade 理念） | 将故障抽象为统一的场景模型，提供命令行/API两种调用方式 | 模型抽象层次高，覆盖基础资源、Java应用、容器、云原生等多种场景 |
| 云原生混沌平台 | 开源（对标 Chaos Mesh 理念） | 基于 Kubernetes CRD 实现故障编排，原生支持容器和 Pod 级注入 | 与容器编排体系深度集成，声明式定义实验，易于纳入 GitOps 流程 |
| 商业化混沌工程平台 | 商业 SaaS/托管服务 | 提供开箱即用的故障场景库、可视化编排、安全管控能力 | 降低了自建平台的门槛，适合尚未具备自研能力的团队快速起步 |

选型时通常遵循以下原则：

- **已经是 Kubernetes 为主体基础设施的团队**，优先考虑基于 CRD 声明式编排的方案，可以与现有的持续交付流水线无缝集成；
- **需要覆盖非容器化的传统主机/虚拟机场景**，选择基于 Agent + 命令行的通用故障注入工具会更加灵活；
- **团队规模较小、尚未具备自研平台能力**，可以优先采购商业化的托管服务，把精力集中在梳理稳态假设和分析演练结果上，而不是重复搭建基础设施；
- **有严格合规和数据安全要求的场景**，仍然建议以自研平台为主，工具生态中的开源组件作为其中的故障注入执行层被内部平台封装调用。

### 3.6 容灾架构演进与故障转移设计

演练的最终目的不是"演练"本身，而是驱动容灾架构持续演进。容灾能力通常经历四个递进的阶段：

1. **主备容灾**：一主一备，正常情况下只有主节点对外服务，备节点保持数据同步，主节点故障后手动或半自动切换到备节点。RTO 通常在分钟级，且切换过程往往需要人工介入确认，恢复速度受限于值班人员的响应速度。
2. **同城双活**：同一地域内部署两个（或多个）对等的可用区，正常情况下多个可用区同时对外提供服务、共同分担流量，任意一个可用区故障时，流量自动切换到其余可用区，数据通过同步或准同步复制保持强一致或接近强一致。RTO 可以压缩到秒级到十几秒级别。
3. **异地多活**：进一步扩展到跨地域部署，不同地域之间距离更远、网络延迟更高，需要通过单元化架构、就近路由、异步复制加冲突解决等机制来平衡一致性和可用性。异地多活主要应对的是地域级的大范围灾难（如整个城市的网络骨干中断）。
4. **单元化容灾**：将系统按照用户维度切分成多个自包含的"单元"，每个单元内部闭环处理请求，跨单元只有少量的核心数据交互。单元故障时，只需要将该单元的用户请求路由到其他健康单元，几乎不需要跨单元的数据迁移，切换速度可以做到秒级甚至更快。

这四个阶段并非非此即彼，绝大多数系统会根据业务的核心程度进行分层：核心链路投入单元化改造，一般链路保持同城双活，非核心链路可能只做主备容灾。而故障演练正是验证"某条链路声称达到的容灾等级，是否真正名副其实"的唯一手段。

#### 3.6.1 故障检测

```java
/**
 * 多维度故障检测器
 *
 * 单一维度的健康检查很容易产生误判（例如仅凭一次心跳超时
 * 就判定节点故障，可能只是网络瞬时抖动）。
 * 因此采用多维度综合判定 + 连续多次确认的方式提高检测准确性。
 */
public class MultiDimensionFaultDetector {

    private final Map<String, NodeHealthState> healthStates
        = new ConcurrentHashMap<>();

    /**
     * 健康检查维度
     */
    public enum CheckDimension {
        HEARTBEAT,       // 心跳检测
        BUSINESS_METRIC, // 业务指标检测（错误率/RT）
        RESOURCE_USAGE,  // 资源使用率检测
        DEPENDENCY_CHECK // 依赖服务连通性检测
    }

    /**
     * 节点健康状态
     */
    public static class NodeHealthState {
        String nodeId;
        Map<CheckDimension, Boolean> dimensionResults = new HashMap<>();
        int consecutiveFailures = 0;
        long lastCheckTime;
        boolean judgedAsFaulty = false;
    }

    /**
     * 执行一轮健康检查
     *
     * 判定规则：
     * - 单一维度异常：记录但不立即判定为故障（避免误判）
     * - 心跳 + 业务指标 同时异常：提高怀疑等级
     * - 连续3轮检查都判定异常：正式判定为故障，触发转移流程
     */
    public FaultDetectionResult check(String nodeId,
                                       Map<CheckDimension, Boolean> results) {
        NodeHealthState state = healthStates.computeIfAbsent(
            nodeId, id -> {
                NodeHealthState s = new NodeHealthState();
                s.nodeId = id;
                return s;
            });

        state.dimensionResults = results;
        state.lastCheckTime = System.currentTimeMillis();

        long failedDimensions = results.values().stream()
            .filter(healthy -> !healthy)
            .count();

        boolean suspiciousThisRound = failedDimensions >= 2
            || (results.getOrDefault(CheckDimension.HEARTBEAT, true) == false
                && failedDimensions >= 1);

        if (suspiciousThisRound) {
            state.consecutiveFailures++;
        } else {
            state.consecutiveFailures = 0;
            state.judgedAsFaulty = false;
        }

        FaultDetectionResult result = new FaultDetectionResult();
        result.nodeId = nodeId;
        result.consecutiveFailures = state.consecutiveFailures;

        // 连续3轮异常才正式判定为故障，避免网络抖动导致误判
        if (state.consecutiveFailures >= 3 && !state.judgedAsFaulty) {
            state.judgedAsFaulty = true;
            result.faultConfirmed = true;
        }

        return result;
    }

    public static class FaultDetectionResult {
        String nodeId;
        int consecutiveFailures;
        boolean faultConfirmed;
    }
}
```

#### 3.6.2 自动故障转移

```java
/**
 * 自动故障转移执行器
 *
 * 故障转移的核心挑战不是"切换动作本身"，而是：
 * 1. 如何避免脑裂（Split-Brain）：新旧主节点同时对外提供服务
 * 2. 如何最小化数据丢失（RPO）
 * 3. 如何让切换尽可能快（RTO）
 * 4. 如何保证切换过程本身是幂等和可重入的
 */
public class AutoFailoverExecutor {

    private final DistributedLock failoverLock;
    private final ReplicationStatusChecker replicationChecker;
    private final TrafficRouter trafficRouter;

    public AutoFailoverExecutor(DistributedLock failoverLock,
                                ReplicationStatusChecker replicationChecker,
                                TrafficRouter trafficRouter) {
        this.failoverLock = failoverLock;
        this.replicationChecker = replicationChecker;
        this.trafficRouter = trafficRouter;
    }

    /**
     * 执行故障转移
     *
     * 流程：
     * 1. 抢占分布式锁，防止多个检测节点并发触发转移（避免脑裂的第一道防线）
     * 2. 确认原主节点确实不可写（二次确认，防止误判）
     * 3. 选出复制进度最接近原主节点的备节点作为新主节点
     * 4. 将新主节点提升为可写状态
     * 5. 切换流量路由指向新主节点
     * 6. 将原主节点标记为待修复状态，禁止其自行恢复为主角色
     */
    public FailoverResult executeFailover(String clusterId,
                                          String faultyNodeId) {
        FailoverResult result = new FailoverResult();
        result.clusterId = clusterId;
        long startTime = System.currentTimeMillis();

        // 1. 抢占分布式锁
        boolean lockAcquired = failoverLock.tryLock(
            "failover:" + clusterId, 10, TimeUnit.SECONDS);
        if (!lockAcquired) {
            result.success = false;
            result.reason = "未能获取故障转移锁，可能已有转移在进行中";
            return result;
        }

        try {
            // 2. 二次确认原主节点确实故障（防止误判导致不必要的切换）
            if (isNodeActuallyHealthy(faultyNodeId)) {
                result.success = false;
                result.reason = "二次确认原主节点健康，取消转移";
                return result;
            }

            // 3. 选出最优备节点（复制进度最接近的）
            String candidateId = selectBestCandidate(clusterId, faultyNodeId);
            if (candidateId == null) {
                result.success = false;
                result.reason = "没有可用的备节点，转移失败";
                return result;
            }

            // 4. 提升新主节点
            boolean promoted = promoteToMaster(candidateId);
            if (!promoted) {
                result.success = false;
                result.reason = "提升新主节点失败";
                return result;
            }

            // 5. 隔离原主节点，防止其在网络恢复后继续以主节点身份写入（脑裂防护）
            fenceOldMaster(faultyNodeId);

            // 6. 切换流量路由
            trafficRouter.switchTo(clusterId, candidateId);

            result.success = true;
            result.newMasterId = candidateId;
            result.rtoMillis = System.currentTimeMillis() - startTime;

        } finally {
            failoverLock.unlock("failover:" + clusterId);
        }

        return result;
    }

    /**
     * 选择复制进度最接近原主节点的备节点
     * 目的是最小化数据丢失（RPO）
     */
    private String selectBestCandidate(String clusterId, String faultyNodeId) {
        List<String> candidates = getReplicaNodes(clusterId, faultyNodeId);
        String best = null;
        long minLag = Long.MAX_VALUE;

        for (String candidate : candidates) {
            long lag = replicationChecker.getReplicationLagMillis(candidate);
            if (lag < minLag) {
                minLag = lag;
                best = candidate;
            }
        }
        return best;
    }

    private boolean isNodeActuallyHealthy(String nodeId) { return false; }
```

## 四、异常处理与容错机制

演练平台自身也是一个分布式系统，它同样需要具备强大的异常处理能力——不仅要保证被演练的目标系统在故障后能够恢复，更要保证演练平台本身不会因为自身的异常而让故障"卡"在生产环境无法回滚。这是整个体系里"容错的容错"，重要程度甚至高于故障注入能力本身。

### 4.1 演练过程中的异常处理原则

1. **任何异常都必须触发恢复动作**：无论是注入过程中的异常，还是观测过程中的异常，还是平台自身进程崩溃，都不能允许故障停留在生产环境中不被处理。
2. **恢复动作必须具备幂等性**：故障恢复的代码可能会被重复调用（例如平台重启后重新扫描到"未完成"的实验），必须保证多次调用恢复逻辑不会产生副作用。
3. **恢复失败要有兜底告警**：如果自动恢复本身也失败了，必须第一时间通过多渠道（电话、短信、即时消息）告知责任人，绝不能让"自动恢复失败"这件事被静默吞掉。
4. **必须有独立于目标系统的看门狗**：注入故障的载体本身很可能因为故障而不可用（比如注入了断网故障，那么负责发起恢复指令的组件也可能因为断网而联系不上目标机器），因此至少需要有一个独立链路（如带外管理网络）能够在任何情况下触达目标并执行恢复。

### 4.2 演练安全守卫设计

```java
/**
 * 演练安全守卫
 *
 * 职责：在演练进行的全过程中充当"刹车片"，
 * 一旦发现任何异常迹象立即触发终止和恢复，
 * 是保护生产环境不因演练本身引发次生事故的最后一道防线
 */
public class SafetyGuard implements ExperimentStateMachine.StateChangeListener {

    private final List<SafetyRule> rules = new ArrayList<>();
    private final ScheduledExecutorService watchdogExecutor
        = Executors.newScheduledThreadPool(2);
    private final Map<String, ScheduledFuture<?>> activeWatchdogs
        = new ConcurrentHashMap<>();

    /**
     * 安全规则接口，支持插件式扩展多种检查维度
     */
    public interface SafetyRule {
        String getName();
        boolean isViolated(ExperimentExecutor.MetricsSnapshot current,
                           ExperimentExecutor.MetricsSnapshot baseline);
    }

    public SafetyGuard() {
        // 默认规则一：错误率相对基线的绝对涨幅超过阈值
        rules.add(new SafetyRule() {
            public String getName() { return "错误率暴涨检测"; }
            public boolean isViolated(ExperimentExecutor.MetricsSnapshot cur,
                                      ExperimentExecutor.MetricsSnapshot base) {
                return cur.errorRate - base.errorRate > 0.05; // 绝对值涨5%
            }
        });

        // 默认规则二：核心业务指标（QPS）断崖式下跌
        rules.add(new SafetyRule() {
            public String getName() { return "QPS断崖检测"; }
            public boolean isViolated(ExperimentExecutor.MetricsSnapshot cur,
                                      ExperimentExecutor.MetricsSnapshot base) {
                if (base.qps <= 0) return false;
                return cur.qps < base.qps * 0.5; // QPS跌去一半以上
            }
        });

        // 默认规则三：P99 RT相对基线倍数放大
        rules.add(new SafetyRule() {
            public String getName() { return "RT放大检测"; }
            public boolean isViolated(ExperimentExecutor.MetricsSnapshot cur,
                                      ExperimentExecutor.MetricsSnapshot base) {
                if (base.p99RT <= 0) return false;
                return cur.p99RT > base.p99RT * 5; // RT放大5倍以上
            }
        });
    }

    public void register(ExperimentExecutor.Experiment experiment) {
        // 启动独立看门狗线程，即使主流程阻塞或崩溃也能兜底终止演练
        ScheduledFuture<?> watchdog = watchdogExecutor.scheduleAtFixedRate(
            () -> checkWatchdogTimeout(experiment),
            0, 5, TimeUnit.SECONDS
        );
        activeWatchdogs.put(experiment.id, watchdog);
    }

    /**
     * 看门狗超时保护：即使正常的实验流程因为异常卡住，
     * 到达故障注入最大允许时长后也会强制触发恢复
     */
    private void checkWatchdogTimeout(ExperimentExecutor.Experiment experiment) {
        // 实际实现中会检查实验开始时间是否超过
        // (injectionDurationSeconds + 安全冗余) 的上限
        // 一旦超时，无论主流程状态如何，都直接调用注入器的recover方法
    }

    /**
     * 核心检查方法：遍历所有安全规则，任意一条命中就返回违规详情
     */
    public List<String> checkViolations(
            ExperimentExecutor.MetricsSnapshot current,
            ExperimentExecutor.MetricsSnapshot baseline) {
        List<String> violations = new ArrayList<>();
        for (SafetyRule rule : rules) {
            if (rule.isViolated(current, baseline)) {
                violations.add(rule.getName());
            }
        }
        return violations;
    }

    @Override
    public void onStateChange(ExperimentStateMachine.State from,
                              ExperimentStateMachine.State to,
                              String reason) {
        if (to == ExperimentStateMachine.State.COMPLETED
            || to == ExperimentStateMachine.State.FAILED
            || to == ExperimentStateMachine.State.RECOVERED) {
            // 实验结束，取消看门狗任务，避免资源泄漏
            // activeWatchdogs对应的future在此处cancel
        }
    }

    public void addRule(SafetyRule rule) {
        rules.add(rule);
    }
}

/**
 * 幂等恢复保障器
 *
 * 确保恢复操作无论被调用多少次，最终效果都是一致的，
 * 避免因为重复恢复而产生额外的副作用（例如重复删除iptables规则报错、
 * 重复释放已经释放的内存等）
 */
public class IdempotentRecoveryGuard {

    private final Map<String, RecoveryRecord> recoveryLog
        = new ConcurrentHashMap<>();

    public static class RecoveryRecord {
        String faultId;
        int attemptCount;
        boolean confirmedRecovered;
        long lastAttemptTime;
    }

    /**
     * 幂等地执行恢复操作
     *
     * 算法：
     * 1. 检查该故障是否已经被确认恢复，如果是则直接跳过（幂等短路）
     * 2. 否则执行恢复逻辑，恢复逻辑本身也需要写成幂等的
     *    （例如用"确保规则不存在"代替"删除规则"，前者对已经不存在的情况也安全）
     * 3. 验证恢复效果，只有验证通过才标记为confirmedRecovered
     * 4. 如果重试次数超过上限仍未成功，升级告警
     */
    public boolean ensureRecovered(String faultId,
                                   Runnable recoveryAction,
                                   Supplier<Boolean> verifyAction) {
        RecoveryRecord record = recoveryLog.computeIfAbsent(faultId, id -> {
            RecoveryRecord r = new RecoveryRecord();
            r.faultId = id;
            return r;
        });

        if (record.confirmedRecovered) {
            return true; // 已确认恢复，幂等短路
        }

        record.attemptCount++;
        record.lastAttemptTime = System.currentTimeMillis();

        try {
            recoveryAction.run();
        } catch (Exception e) {
            // 恢复动作本身抛异常也不能中断流程，继续走验证逻辑
            // 因为很可能异常本身就是因为"已经处于目标状态"而导致的
            // （例如尝试删除一个已经不存在的iptables规则会报错）
        }

        boolean verified = verifyAction.get();
        record.confirmedRecovered = verified;

        if (!verified && record.attemptCount >= 5) {
            escalateAlert(faultId, record.attemptCount);
        }

        return verified;
    }

    private void escalateAlert(String faultId, int attempts) {
        // 升级为P0级告警，通知值班人员人工介入
        System.err.println(String.format(
            "故障 %s 自动恢复已重试 %d 次仍未成功，需要人工介入！",
            faultId, attempts));
    }
}
```

### 4.3 演练风险分级与审批机制

不同类型的演练对应不同的风险等级，风险等级决定了需要经过的审批层级：

| 风险等级 | 典型场景 | 审批要求 | 是否需要值班保障 |
|---------|---------|---------|----------------|
| 低风险 | 独立环境的单点演练 | 无需审批，平台自动放行 | 否 |
| 中风险 | 灰度环境的单点/小范围演练 | 团队负责人审批 | 建议 |
| 高风险 | 生产环境的单点演练、大规模演练 | 团队负责人 + 稳定性负责人双重审批 | 必须 |
| 极高风险 | 长链路演练、混合演练、生产级可用区容灾演练 | 多级审批 + 事先报备 + 现场值守 | 必须，且需要多方联合值守 |

### 4.4 常见异常场景及应对

| 异常场景 | 可能原因 | 应对策略 |
|---------|---------|---------|
| 故障注入后长时间未观测到预期变化 | 注入未真正生效、监控数据延迟、目标选择错误 | 设置注入生效验证步骤，验证失败则立即终止并告警 |
| 恢复指令下发后目标无响应 | 目标机器本身处于网络分区中，无法接收指令 | 预留带外恢复通道（如通过独立管理网络或云厂商控制台API强制恢复） |
| 演练造成了非预期范围的影响 | 爆炸半径评估不足、影响面存在未知的隐式依赖 | 演练前进行依赖关系梳理，演练中扩大监控覆盖面，一旦发现立即扩大终止范围 |
| 演练平台自身故障 | 平台进程崩溃、平台所在机房故障 | 演练平台自身需要具备高可用部署，且核心的"恢复"能力应尽量下沉到目标机器本地（如本地Agent的自动超时回滚），不完全依赖中心控制面 |
| 演练结果与预期严重不符 | 系统实际容灾能力与设计文档不一致 | 这恰恰是演练的价值所在，应第一时间上报并推动专项修复，而非掩盖问题 |

## 五、性能优化

演练平台的性能优化目标与一般业务系统不同，它追求的不是"吞吐量越大越好"，而是"注入越快越准、恢复越快越稳、观测越实时越有效"。

### 5.1 故障注入性能优化

| 优化点 | 方案 | 效果 |
|-------|------|------|
| 故障注入延迟 | 预加载 Agent，避免运行时类加载和字节码增强的耗时 | 注入延迟从秒级降至毫秒级 |
| 大规模节点演练 | 并行注入 + 分批执行 + 全局与二级并发闸门 | 支持同时对 2000+ 数据库集群、1000+ 应用节点注入故障 |
| 指标采集开销 | 异步采集 + 批量上报，避免同步阻塞主流程 | 演练带来的额外 CPU 开销 < 1% |
| 故障恢复速度 | 预编译恢复脚本，恢复路径与注入路径解耦，恢复优先级高于其他任务 | 恢复时间 < 2 秒 |
| JVM 沙箱注入耗时 | 复用已挂载的沙箱环境，避免每次演练都重新挂载/卸载 Agent | 单次注入耗时从数百毫秒降至十毫秒级 |
| 网络故障注入精度 | 使用 TC filter 配合精确的五元组匹配，避免误伤非目标流量 | 故障影响范围精确控制在目标 IP/端口 |

### 5.2 观测与判定性能优化

在大规模演练场景下，指标观测环节很容易成为瓶颈——如果对每个目标都单独发起一次指标查询，2000+ 集群同时演练时监控系统本身就可能被压垮。因此需要针对性优化：

```java
/**
 * 批量指标观测优化器
 *
 * 核心思路：将N个独立的单集群指标查询，
 * 合并为少量的批量查询请求，大幅降低对监控系统的压力
 */
public class BatchMetricObserver {

    private final MetricQueryClient queryClient;
    private static final int BATCH_SIZE = 50; // 单批查询的集群数上限

    public BatchMetricObserver(MetricQueryClient queryClient) {
        this.queryClient = queryClient;
    }

    /**
     * 批量拉取多个集群的当前指标快照
     *
     * 优化点：
     * 1. 按BATCH_SIZE分片，避免单次查询请求过大导致监控系统超时
     * 2. 分片之间并行发起，缩短总体等待时间
     * 3. 使用本地短TTL缓存，避免短时间内对同一集群重复查询
     */
    public Map<String, MetricSnapshot> batchObserve(List<String> clusterIds) {
        Map<String, MetricSnapshot> result = new ConcurrentHashMap<>();
        List<List<String>> batches = partition(clusterIds, BATCH_SIZE);

        List<CompletableFuture<Void>> futures = batches.stream()
            .map(batch -> CompletableFuture.runAsync(() -> {
                Map<String, MetricSnapshot> batchResult =
                    queryClient.queryBatch(batch);
                result.putAll(batchResult);
            }))
            .collect(Collectors.toList());

        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
            .join();

        return result;
    }

    private List<List<String>> partition(List<String> list, int size) {
        List<List<String>> partitions = new ArrayList<>();
        for (int i = 0; i < list.size(); i += size) {
            partitions.add(list.subList(i, Math.min(i + size, list.size())));
        }
        return partitions;
    }

    public interface MetricQueryClient {
        Map<String, MetricSnapshot> queryBatch(List<String> clusterIds);
    }

    public static class MetricSnapshot {
        double errorRate;
        double p99RT;
        double qps;
    }
}
```

### 5.3 容灾切换性能指标参考

| 容灾级别 | 目标 RTO | 目标 RPO | 典型实测 RTO | 典型实测 RPO |
|---------|---------|---------|-------------|-------------|
| 主备切换 | < 5 分钟 | < 1 分钟 | 2~3 分钟 | 约 30 秒 |
| 同城双活 | < 30 秒 | 0 | 10~20 秒 | 0 |
| 异地多活 | < 10 秒 | < 1 秒 | 5~8 秒 | < 100 毫秒 |
| 单元化切换 | < 5 秒 | 0 | 2~3 秒 | 0 |
| 可用区级容灾（分布式数据库自动故障转移） | RTO < 30 秒 | RPO = 0 | 实测普遍能达到设计目标 | 依赖多副本强一致复制 |

需要注意的是，这些数字只有在**真实演练验证过**的前提下才有意义。任何未经演练验证的 RTO/RPO 目标都只是"理论值"，实际故障发生时的表现往往会因为一些平时被忽略的细节（如 DNS 缓存 TTL、连接池重连策略、客户端本地缓存的过期时间）而与理论值产生较大偏差。

### 5.4 演练平台自身的可扩展性设计

- **无状态化调度层**：演练编排器和调度器本身应设计为无状态，实例可以水平扩展，配合分布式锁保证同一演练计划不会被重复调度；
- **执行层与控制层分离**：真正的故障注入执行逻辑尽量下沉到目标节点本地的轻量级 Agent，控制层只负责下发指令和汇总结果，避免控制层成为大规模演练的瓶颈；
- **观测数据的采样与降级**：在观测数据量极大的场景下，可以采用采样统计代替全量拉取，在保证判定准确性的前提下降低系统开销；
- **演练任务队列削峰**：多个演练计划同时到达时，通过消息队列进行削峰填谷，避免瞬时创建过多演练实例抢占资源。

## 六、最佳实践与总结

### 6.1 故障演练最佳实践

1. **从小做起，循序渐进**：
   - 第一阶段：在独立环境做全量故障场景验证；
   - 第二阶段：在灰度环境对非核心链路做真实流量下的验证；
   - 第三阶段：在生产环境对核心链路的部分节点做单点演练；
   - 第四阶段：逐步升级到大规模演练、长链路演练，最终具备生产级可用区容灾演练的能力。

2. **先建可观测性，再做混沌工程**：
   - 如果连系统当前的状态都看不清楚，注入故障之后就更加无从判断了；
   - 至少要具备三大件：指标监控（Metrics）、日志中心（Logging）、链路追踪（Tracing），并且这三者要能够快速关联定位。

3. **演练常态化，而非运动式突击**：
   - 不要只在大促前才想起演练，要建立"周期性演练日历"，形成固定节奏；
   - 引入随机无预告演练，持续检验值班响应和自动化处置能力，避免"重要但不紧急"的稳定性工作被日常业务需求挤占。

4. **GameDay 全真模拟演练**：
   - 定期组织跨团队的大规模联合演练，模拟真实的复合故障场景；
   - 不提前告知具体注入什么故障，考验团队的故障发现、定位、协同、恢复全流程能力；
   - 演练结束后进行复盘，把发现的问题转化为具体的改进事项并跟踪闭环。

5. **建立核心链路清单并分级管理**：
   - 参考行业内"识别核心链路 → 分阶段扩大演练范围"的经验，先梳理出真正影响用户核心体验的链路清单；
   - 按照业务重要程度为链路分级，优先投入资源保障最高优先级链路的容灾能力，并优先纳入常态化演练。

6. **将演练结果与容灾能力认证挂钩**：
   - 一条链路声称自己具备"同城双活"能力，必须要有对应的演练记录作为证据；
   - 建立容灾能力认证机制，未通过演练验证的链路不允许标注为已具备某种容灾等级。

### 6.2 常见陷阱

1. **只在测试环境演练**：测试环境的架构、配置、流量模式与生产环境往往存在巨大差异，在测试环境发现的问题可能在生产环境根本不存在，反之亦然，最终验证还是要落到生产环境（或高保真的仿真环境）。

2. **演练前通知所有相关人员并详细说明故障细节**：这会让"故障发现"这个关键环节失去意义。混沌工程的核心价值之一就是验证监控告警和值班响应流程是否真的有效，如果提前把答案告诉了所有人，演练就退化成了一场排练好的表演。

3. **忽视恢复演练，只演练故障注入**：很多团队把大量精力花在"如何制造故障"上，却很少认真演练"如何快速恢复"，而实际线上事故里，恢复流程本身出问题的比例往往更高。

4. **一次注入多种故障，无法定位问题根因**：应当遵循"每次只注入一种故障，充分观察其影响后再尝试组合故障"的原则。多种故障同时叠加会让问题定位变得极其困难，也难以准确归因。

5. **没有明确的回滚预案就贸然升级演练规模**：任何一次演练都必须提前准备好回滚预案，尤其是长链路演练、混合演练和生产级容灾演练。如果故障注入之后系统无法恢复，造成的后果远比不做演练更严重。

6. **爆炸半径评估流于形式**：只是走个审批流程走过场，没有真正梳理清楚目标节点/目标集群的上下游依赖关系，导致演练影响范围远超预期。

7. **把演练"通过"等同于"万事大吉"**：一次演练通过只能说明系统在当前的架构、配置、流量水平下具备相应的容灾能力，架构变更、流量增长、配置调整都可能让原本通过的能力失效，因此演练必须是持续、周期性的活动。

### 6.3 演进方向

1. **AI 驱动的智能混沌工程**：利用机器学习分析系统拓扑结构和历史故障数据，自动推荐最有价值的故障注入方案，通过强化学习不断优化故障注入的参数组合，让"选择做什么实验"这件事逐步从依赖专家经验转向数据驱动。

2. **持续验证（Continuous Verification）**：将故障演练深度集成到持续交付流水线中，每次重要部署后自动执行一组基本的故障场景验证，一旦发现回归问题立即阻断发布，把"稳定性回归测试"变成和单元测试、集成测试同等重要的标准发布环节。

3. **混沌工程即代码（Chaos as Code）**：将故障演练方案用声明式代码（如 YAML/JSON）描述，纳入版本管理，支持代码评审和自动化执行，使演练场景本身也具备可追溯、可复用、可协作的软件工程属性。

4. **跨地域容灾能力的持续演进**：随着业务全球化和多地域部署的普及，容灾架构需要覆盖跨洲际的故障场景，面临更长的网络延迟（100~300 毫秒级别）和更复杂的数据合规要求，演练体系也需要相应地扩展到跨地域网络分区、跨地域数据一致性冲突等新场景。

5. **系统韧性量化评分体系**：建立量化的系统韧性评分体系，从故障类型覆盖率、平均恢复时间、爆炸半径控制精度、演练常态化程度等多个维度综合打分，将"系统有多抗打"从一句模糊的口号变成一个可以横向对比、持续追踪的量化指标，推动组织整体韧性水平的持续提升。

6. **演练能力与组织文化的深度融合**：故障演练与混沌工程最终要沉淀为一种组织习惯，而不是某个团队的专项任务——从架构设计阶段就默认考虑"这个组件挂了会怎样"，从新人培训阶段就安排参与真实演练，让"为故障做好准备"成为团队默认的工作方式，而不是事后才想起的补救措施。

## 七、全链路实战案例

前面六个章节系统地阐述了故障演练与混沌工程的理论体系、架构设计、核心链路、异常处理、性能优化和最佳实践。但"纸上得来终觉浅"——要真正把这套体系落地到生产环境中，需要把各个模块串联起来，形成端到端的完整实战流程。本章通过三个完整的全链路案例，展示从需求发起到演练报告闭环的每一步应该如何实现，每个案例都包含完整的 Java 代码实现，涵盖异常处理、日志记录和幂等控制。

### 7.1 案例一：故障注入演练全链路

#### 7.1.1 场景概述

这是最基础也最高频的演练场景。一次完整的故障注入演练流程包括六个阶段：**选择故障类型 → 配置注入规则 → 执行注入 → 监控影响 → 自动恢复 → 演练报告**。本案例以"对订单服务注入 RPC 超时故障"为例，完整展示如何将这六个阶段串联为一个可执行、可追踪、可复现的自动化流程。

核心设计要点：

- 每个阶段都有明确的输入和输出，阶段之间通过上下文对象传递状态；
- 故障注入和恢复操作都具备幂等性，重复执行不会产生副作用；
- 全程结构化日志，支持事后审计和问题排查；
- 任何阶段出现异常，都会触发自动恢复并生成包含异常信息的演练报告。

#### 7.1.2 完整代码实现

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * 故障注入演练全链路执行器
 *
 * 设计模式：模板方法 + 责任链 + 观察者
 *
 * 模板方法：六个阶段的执行顺序固定，每个阶段的具体实现可扩展
 * 责任链：多个监控规则按优先级链式检查
 * 观察者：演练状态变更通知所有订阅方（日志、告警、报告等）
 *
 * 全链路流程：
 * 选择故障类型 → 配置注入规则 → 执行注入 → 监控影响 → 自动恢复 → 演练报告
 *
 * 幂等控制：
 * 每次演练生成唯一的 drillId，所有操作都绑定 drillId，
 * 恢复操作通过 "检查当前状态 → 仅在需要时执行恢复" 的方式保证幂等
 */
public class FaultInjectionDrillPipeline {

    private static final Logger logger = LoggerFactory.getLogger(
        FaultInjectionDrillPipeline.class);

    /**
     * 演练阶段枚举
     */
    public enum DrillPhase {
        FAULT_SELECTION,     // 阶段一：选择故障类型
        RULE_CONFIGURATION,  // 阶段二：配置注入规则
        FAULT_INJECTION,     // 阶段三：执行故障注入
        IMPACT_MONITORING,   // 阶段四：监控影响
        AUTO_RECOVERY,       // 阶段五：自动恢复
        REPORT_GENERATION    // 阶段六：生成演练报告
    }

    /**
     * 故障类型定义
     */
    public enum FaultCategory {
        RPC_TIMEOUT("RPC调用超时", "模拟下游服务响应超时"),
        RPC_EXCEPTION("RPC调用异常", "模拟下游服务返回异常"),
        NETWORK_DELAY("网络延迟", "模拟网络链路延迟增加"),
        CPU_OVERLOAD("CPU过载", "模拟CPU资源耗尽"),
        MEMORY_LEAK("内存泄漏", "模拟内存资源逐步耗尽"),
        DISK_FULL("磁盘写满", "模拟磁盘空间耗尽"),
        DB_SLOW_QUERY("数据库慢查询", "模拟数据库查询延迟");

        private final String name;
        private final String description;

        FaultCategory(String name, String description) {
            this.name = name;
            this.description = description;
        }

        public String getName() { return name; }
        public String getDescription() { return description; }
    }

    /**
     * 注入规则配置
     *
     * 定义了故障注入的所有参数，包括目标范围、持续时间、
     * 故障强度、安全阈值等
     */
    public static class InjectionRule {
        private String drillId;               // 演练唯一ID
        private FaultCategory faultCategory;  // 故障类型
        private String targetService;         // 目标服务
        private String targetMethod;          // 目标方法（可选）
        private List<String> targetNodes;     // 目标节点IP列表
        private double injectionRatio;        // 注入比例（0~1）
        private int durationSeconds;          // 持续时间（秒）
        private Map<String, String> faultParams; // 故障参数

        // 安全阈值
        private double maxErrorRate;          // 最大可接受错误率
        private double maxP99Millis;          // 最大可接受P99响应时间
        private double minQps;               // 最低可接受QPS

        // getter/setter 省略
        public String getDrillId() { return drillId; }
        public void setDrillId(String drillId) { this.drillId = drillId; }
        public FaultCategory getFaultCategory() { return faultCategory; }
        public void setFaultCategory(FaultCategory c) { this.faultCategory = c; }
        public String getTargetService() { return targetService; }
        public void setTargetService(String s) { this.targetService = s; }
        public String getTargetMethod() { return targetMethod; }
        public void setTargetMethod(String m) { this.targetMethod = m; }
        public List<String> getTargetNodes() { return targetNodes; }
        public void setTargetNodes(List<String> n) { this.targetNodes = n; }
        public double getInjectionRatio() { return injectionRatio; }
        public void setInjectionRatio(double r) { this.injectionRatio = r; }
        public int getDurationSeconds() { return durationSeconds; }
        public void setDurationSeconds(int d) { this.durationSeconds = d; }
        public Map<String, String> getFaultParams() { return faultParams; }
        public void setFaultParams(Map<String, String> p) { this.faultParams = p; }
        public double getMaxErrorRate() { return maxErrorRate; }
        public void setMaxErrorRate(double r) { this.maxErrorRate = r; }
        public double getMaxP99Millis() { return maxP99Millis; }
        public void setMaxP99Millis(double m) { this.maxP99Millis = m; }
        public double getMinQps() { return minQps; }
        public void setMinQps(double q) { this.minQps = q; }
    }

    /**
     * 演练上下文：在各阶段之间传递状态数据
     */
    public static class DrillContext {
        String drillId;
        DrillPhase currentPhase;
        InjectionRule rule;
        long startTimeMillis;
        long endTimeMillis;

        // 各阶段产出
        MetricBaseline baseline;              // 基线指标
        List<MetricSample> monitoringSamples; // 监控采样
        boolean injectionConfirmed;           // 注入已确认生效
        boolean recoveryConfirmed;            // 恢复已确认完成
        boolean emergencyStopped;             // 是否触发紧急终止
        String emergencyReason;               // 紧急终止原因
        List<String> anomalies;               // 发现的异常列表
        DrillReport report;                   // 最终报告

        DrillContext(String drillId, InjectionRule rule) {
            this.drillId = drillId;
            this.rule = rule;
            this.monitoringSamples = new ArrayList<>();
            this.anomalies = new ArrayList<>();
        }
    }

    /**
     * 指标基线
     */
    public static class MetricBaseline {
        double avgErrorRate;
        double avgP99Millis;
        double avgQps;
        double avgCpuPercent;
        double avgMemoryPercent;
        long sampleCount;
    }

    /**
     * 指标采样点
     */
    public static class MetricSample {
        long timestamp;
        double errorRate;
        double p99Millis;
        double qps;
        double cpuPercent;
        double memoryPercent;
    }

    /**
     * 演练报告
     */
    public static class DrillReport {
        String drillId;
        String faultType;
        String targetService;
        String verdict;           // PASSED / FAILED / ABORTED
        long startTime;
        long endTime;
        long durationMillis;
        MetricBaseline baseline;
        MetricSample peakImpact;  // 影响峰值
        boolean emergencyStopped;
        String emergencyReason;
        List<String> anomalies;
        List<String> recommendations;
        Map<String, String> phaseTimeline;  // 各阶段时间线

        DrillReport() {
            this.anomalies = new ArrayList<>();
            this.recommendations = new ArrayList<>();
            this.phaseTimeline = new LinkedHashMap<>();
        }
    }

    // === 依赖组件 ===
    private final FaultInjectorAgent injectorAgent;
    private final MetricsQueryService metricsService;
    private final IdempotentRecoveryManager recoveryManager;
    private final AlertNotifier alertNotifier;

    public FaultInjectionDrillPipeline(FaultInjectorAgent injectorAgent,
                                        MetricsQueryService metricsService,
                                        IdempotentRecoveryManager recoveryManager,
                                        AlertNotifier alertNotifier) {
        this.injectorAgent = injectorAgent;
        this.metricsService = metricsService;
        this.recoveryManager = recoveryManager;
        this.alertNotifier = alertNotifier;
    }

    /**
     * 执行完整的故障注入演练全链路
     *
     * 算法流程：
     * 1. 选择故障类型并校验合法性
     * 2. 配置注入规则并进行安全性预检查
     * 3. 采集基线指标 → 执行故障注入 → 确认注入生效
     * 4. 持续监控，实时对比基线，超阈值则紧急终止
     * 5. 到达预设时间或紧急终止后，执行幂等恢复
     * 6. 汇总数据生成结构化演练报告
     *
     * 异常处理策略：
     * - 任何阶段抛出异常，都先尝试恢复故障再抛出
     * - 恢复操作本身如果失败，升级为P0告警
     * - 所有关键操作都有结构化日志
     */
    public DrillReport executeDrill(InjectionRule rule) {
        String drillId = generateDrillId();
        rule.setDrillId(drillId);
        DrillContext ctx = new DrillContext(drillId, rule);
        ctx.startTimeMillis = System.currentTimeMillis();

        logger.info("[Drill:{}] ====== 故障注入演练开始 ======", drillId);
        logger.info("[Drill:{}] 故障类型={}, 目标服务={}, 持续时间={}s",
            drillId, rule.getFaultCategory().getName(),
            rule.getTargetService(), rule.getDurationSeconds());

        try {
            // === 阶段一：选择故障类型 ===
            phaseFaultSelection(ctx);

            // === 阶段二：配置注入规则 ===
            phaseRuleConfiguration(ctx);

            // === 阶段三：执行故障注入 ===
            phaseFaultInjection(ctx);

            // === 阶段四：监控影响 ===
            phaseImpactMonitoring(ctx);

            // === 阶段五：自动恢复 ===
            phaseAutoRecovery(ctx);

        } catch (Exception e) {
            logger.error("[Drill:{}] 演练过程发生异常, 触发紧急恢复",
                drillId, e);
            ctx.anomalies.add("演练异常: " + e.getMessage());

            // 无论如何都要尝试恢复
            try {
                forceRecovery(ctx);
            } catch (Exception recoveryEx) {
                logger.error("[Drill:{}] 紧急恢复也失败, 升级P0告警",
                    drillId, recoveryEx);
                alertNotifier.sendP0Alert(drillId,
                    "故障注入恢复失败，需要人工介入: " + recoveryEx.getMessage());
            }
        } finally {
            // === 阶段六：生成演练报告（无论成功失败都要生成） ===
            ctx.endTimeMillis = System.currentTimeMillis();
            phaseReportGeneration(ctx);
            logger.info("[Drill:{}] ====== 故障注入演练结束, 结论={} ======",
                drillId, ctx.report.verdict);
        }

        return ctx.report;
    }

    /**
     * 阶段一：选择故障类型
     *
     * 校验所选故障类型是否适用于目标服务，
     * 检查目标服务当前是否处于可演练状态
     */
    private void phaseFaultSelection(DrillContext ctx) {
        ctx.currentPhase = DrillPhase.FAULT_SELECTION;
        logger.info("[Drill:{}] [阶段一] 选择故障类型: {}",
            ctx.drillId, ctx.rule.getFaultCategory().getName());

        // 校验故障类型是否支持
        if (ctx.rule.getFaultCategory() == null) {
            throw new IllegalArgumentException("未选择故障类型");
        }

        // 校验目标服务是否存在且健康
        boolean serviceHealthy = metricsService.isServiceHealthy(
            ctx.rule.getTargetService());
        if (!serviceHealthy) {
            throw new IllegalStateException(String.format(
                "目标服务 %s 当前不健康，拒绝执行演练",
                ctx.rule.getTargetService()));
        }

        // 校验目标节点列表不为空
        if (ctx.rule.getTargetNodes() == null
                || ctx.rule.getTargetNodes().isEmpty()) {
            throw new IllegalArgumentException("目标节点列表不能为空");
        }

        logger.info("[Drill:{}] [阶段一] 故障类型校验通过, 目标节点数={}",
            ctx.drillId, ctx.rule.getTargetNodes().size());
        ctx.report = new DrillReport();
        ctx.report.phaseTimeline.put("FAULT_SELECTION", now());
    }

    /**
     * 阶段二：配置注入规则
     *
     * 对注入规则进行安全性预检查，包括：
     * 1. 注入比例不能超过安全上限（防止爆炸半径过大）
     * 2. 持续时间不能超过最大允许时长
     * 3. 安全阈值必须已配置
     * 4. 采集注入前的基线指标
     */
    private void phaseRuleConfiguration(DrillContext ctx) {
        ctx.currentPhase = DrillPhase.RULE_CONFIGURATION;
        logger.info("[Drill:{}] [阶段二] 配置注入规则", ctx.drillId);

        InjectionRule rule = ctx.rule;

        // 安全性校验：注入比例上限
        if (rule.getInjectionRatio() > 0.5) {
            throw new IllegalArgumentException(String.format(
                "注入比例 %.0f%% 超过安全上限 50%%",
                rule.getInjectionRatio() * 100));
        }

        // 安全性校验：持续时间上限
        if (rule.getDurationSeconds() > 600) {
            throw new IllegalArgumentException(String.format(
                "持续时间 %d 秒超过最大允许时长 600 秒",
                rule.getDurationSeconds()));
        }

        // 安全性校验：安全阈值必须配置
        if (rule.getMaxErrorRate() <= 0 || rule.getMaxP99Millis() <= 0) {
            throw new IllegalArgumentException(
                "安全阈值（maxErrorRate / maxP99Millis）未配置");
        }

        // 采集基线指标（注入前30秒的平均值）
        logger.info("[Drill:{}] [阶段二] 开始采集基线指标（30秒）",
            ctx.drillId);
        ctx.baseline = metricsService.collectBaseline(
            rule.getTargetService(), 30);
        logger.info("[Drill:{}] [阶段二] 基线指标采集完成: "
            + "错误率={}, P99={}ms, QPS={}",
            ctx.drillId, ctx.baseline.avgErrorRate,
            ctx.baseline.avgP99Millis, ctx.baseline.avgQps);

        ctx.report.phaseTimeline.put("RULE_CONFIGURATION", now());
    }

    /**
     * 阶段三：执行故障注入
     *
     * 通过 Agent 向目标节点下发故障注入指令，
     * 注入完成后验证故障是否确实生效（而非静默失败）
     *
     * 幂等控制：
     * 注入指令携带 drillId，Agent 端对同一 drillId 的重复注入请求
     * 会返回 "已注入" 而非重复执行，保证幂等
     */
    private void phaseFaultInjection(DrillContext ctx) {
        ctx.currentPhase = DrillPhase.FAULT_INJECTION;
        InjectionRule rule = ctx.rule;
        logger.info("[Drill:{}] [阶段三] 开始执行故障注入", ctx.drillId);

        // 向每个目标节点下发注入指令
        List<String> failedNodes = new ArrayList<>();
        for (String node : rule.getTargetNodes()) {
            try {
                boolean injected = injectorAgent.injectFault(
                    ctx.drillId, node, rule.getFaultCategory(),
                    rule.getFaultParams(), rule.getInjectionRatio());

                if (injected) {
                    logger.info("[Drill:{}] [阶段三] 节点 {} 故障注入成功",
                        ctx.drillId, node);
                } else {
                    logger.warn("[Drill:{}] [阶段三] 节点 {} 故障注入未生效",
                        ctx.drillId, node);
                    failedNodes.add(node);
                }
            } catch (Exception e) {
                logger.error("[Drill:{}] [阶段三] 节点 {} 故障注入异常",
                    ctx.drillId, node, e);
                failedNodes.add(node);
            }
        }

        // 如果所有节点都注入失败，则演练终止
        if (failedNodes.size() == rule.getTargetNodes().size()) {
            throw new RuntimeException("所有目标节点故障注入均失败: "
                + failedNodes);
        }

        // 等待2秒后验证注入效果
        sleepQuietly(2000);

        ctx.injectionConfirmed = injectorAgent.verifyInjection(
            ctx.drillId, rule.getTargetService());
        if (!ctx.injectionConfirmed) {
            logger.warn("[Drill:{}] [阶段三] 故障注入验证未通过, "
                + "可能需要等待更长时间生效", ctx.drillId);
            ctx.anomalies.add("故障注入验证未立即通过");
        }

        logger.info("[Drill:{}] [阶段三] 故障注入完成, "
            + "失败节点数={}/{}, 注入确认={}",
            ctx.drillId, failedNodes.size(),
            rule.getTargetNodes().size(), ctx.injectionConfirmed);

        ctx.report.phaseTimeline.put("FAULT_INJECTION", now());
    }

    /**
     * 阶段四：监控影响
     *
     * 在故障注入持续期间，每秒采集一次核心指标，
     * 实时与基线和安全阈值对比，一旦超阈值立即触发紧急终止
     *
     * 算法：
     * 1. 按秒级粒度采集 errorRate / P99 RT / QPS / CPU / Memory
     * 2. 与基线对比计算偏差幅度
     * 3. 连续3个采样点超阈值才触发终止（避免毛刺误触发）
     * 4. 记录影响峰值用于报告
     */
    private void phaseImpactMonitoring(DrillContext ctx) {
        ctx.currentPhase = DrillPhase.IMPACT_MONITORING;
        logger.info("[Drill:{}] [阶段四] 开始监控影响, 持续 {} 秒",
            ctx.drillId, ctx.rule.getDurationSeconds());

        AtomicInteger consecutiveViolations = new AtomicInteger(0);
        final int VIOLATION_THRESHOLD = 3; // 连续3次超阈值才触发终止

        MetricSample peakImpact = null;
        double peakErrorRate = 0;

        long monitorEndTime = System.currentTimeMillis()
            + ctx.rule.getDurationSeconds() * 1000L;

        while (System.currentTimeMillis() < monitorEndTime) {
            try {
                MetricSample sample = metricsService.collectCurrentSample(
                    ctx.rule.getTargetService());
                sample.timestamp = System.currentTimeMillis();
                ctx.monitoringSamples.add(sample);

                // 记录峰值
                if (sample.errorRate > peakErrorRate) {
                    peakErrorRate = sample.errorRate;
                    peakImpact = sample;
                }

                // 检查是否超出安全阈值
                boolean violated = false;
                StringBuilder violationMsg = new StringBuilder();

                if (sample.errorRate > ctx.rule.getMaxErrorRate()) {
                    violated = true;
                    violationMsg.append(String.format(
                        "错误率=%.4f(阈值%.4f) ",
                        sample.errorRate, ctx.rule.getMaxErrorRate()));
                }
                if (sample.p99Millis > ctx.rule.getMaxP99Millis()) {
                    violated = true;
                    violationMsg.append(String.format(
                        "P99=%.0fms(阈值%.0fms) ",
                        sample.p99Millis, ctx.rule.getMaxP99Millis()));
                }
                if (ctx.rule.getMinQps() > 0
                        && sample.qps < ctx.rule.getMinQps()) {
                    violated = true;
                    violationMsg.append(String.format(
                        "QPS=%.0f(下限%.0f) ",
                        sample.qps, ctx.rule.getMinQps()));
                }

                if (violated) {
                    int count = consecutiveViolations.incrementAndGet();
                    logger.warn("[Drill:{}] [阶段四] 安全阈值告警 "
                        + "(连续第{}次): {}",
                        ctx.drillId, count, violationMsg);

                    if (count >= VIOLATION_THRESHOLD) {
                        logger.error("[Drill:{}] [阶段四] 连续{}次超阈值, "
                            + "触发紧急终止",
                            ctx.drillId, VIOLATION_THRESHOLD);
                        ctx.emergencyStopped = true;
                        ctx.emergencyReason = "连续" + VIOLATION_THRESHOLD
                            + "次超安全阈值: " + violationMsg;
                        break;
                    }
                } else {
                    consecutiveViolations.set(0); // 重置连续计数
                }

                sleepQuietly(1000); // 每秒采集一次

            } catch (Exception e) {
                logger.error("[Drill:{}] [阶段四] 指标采集异常",
                    ctx.drillId, e);
                ctx.anomalies.add("指标采集异常: " + e.getMessage());
                // 采集异常不终止演练，但记录异常
            }
        }

        if (peakImpact != null) {
            ctx.report.peakImpact = peakImpact;
        }

        logger.info("[Drill:{}] [阶段四] 监控结束, 采样点数={}, "
            + "是否紧急终止={}",
            ctx.drillId, ctx.monitoringSamples.size(),
            ctx.emergencyStopped);

        ctx.report.phaseTimeline.put("IMPACT_MONITORING", now());
    }

    /**
     * 阶段五：自动恢复
     *
     * 撤销所有已注入的故障，恢复系统到正常状态
     *
     * 幂等控制：
     * 1. 通过 recoveryManager 保证同一 drillId 的恢复操作
     *    无论调用多少次，最终效果一致
     * 2. 恢复逻辑采用 "检查-执行" 模式：
     *    先检查目标状态，已恢复则跳过，未恢复才执行
     * 3. 恢复完成后通过验证确认，验证通过才标记为已恢复
     */
    private void phaseAutoRecovery(DrillContext ctx) {
        ctx.currentPhase = DrillPhase.AUTO_RECOVERY;
        logger.info("[Drill:{}] [阶段五] 开始自动恢复", ctx.drillId);

        ctx.recoveryConfirmed = recoveryManager.idempotentRecover(
            ctx.drillId,
            // 恢复动作
            () -> {
                for (String node : ctx.rule.getTargetNodes()) {
                    try {
                        injectorAgent.recoverFault(ctx.drillId, node);
                        logger.info("[Drill:{}] [阶段五] 节点 {} 恢复指令已下发",
                            ctx.drillId, node);
                    } catch (Exception e) {
                        logger.error("[Drill:{}] [阶段五] 节点 {} "
                            + "恢复指令下发失败", ctx.drillId, node, e);
                        // 单节点恢复失败不中断整体恢复流程，
                        // 后续验证环节会检测到未恢复的节点
                    }
                }
            },
            // 验证动作
            () -> {
                sleepQuietly(3000); // 等待恢复生效
                return injectorAgent.verifyRecovery(
                    ctx.drillId, ctx.rule.getTargetService());
            },
            // 最大重试次数
            5
        );

        if (!ctx.recoveryConfirmed) {
            logger.error("[Drill:{}] [阶段五] 自动恢复验证未通过, "
                + "升级P0告警", ctx.drillId);
            alertNotifier.sendP0Alert(ctx.drillId,
                "故障注入恢复验证未通过，需要人工介入");
            ctx.anomalies.add("自动恢复验证未通过");
        } else {
            logger.info("[Drill:{}] [阶段五] 自动恢复验证通过", ctx.drillId);
        }

        ctx.report.phaseTimeline.put("AUTO_RECOVERY", now());
    }

    /**
     * 阶段六：生成演练报告
     *
     * 汇总所有阶段的数据，生成结构化的演练报告
     */
    private void phaseReportGeneration(DrillContext ctx) {
        ctx.currentPhase = DrillPhase.REPORT_GENERATION;
        logger.info("[Drill:{}] [阶段六] 生成演练报告", ctx.drillId);

        DrillReport report = ctx.report;
        if (report == null) {
            report = new DrillReport();
            ctx.report = report;
        }

        report.drillId = ctx.drillId;
        report.faultType = ctx.rule.getFaultCategory().getName();
        report.targetService = ctx.rule.getTargetService();
        report.startTime = ctx.startTimeMillis;
        report.endTime = ctx.endTimeMillis;
        report.durationMillis = ctx.endTimeMillis - ctx.startTimeMillis;
        report.baseline = ctx.baseline;
        report.emergencyStopped = ctx.emergencyStopped;
        report.emergencyReason = ctx.emergencyReason;
        report.anomalies = ctx.anomalies;

        // 判定演练结论
        if (ctx.emergencyStopped) {
            report.verdict = "ABORTED";
            report.recommendations.add(
                "演练因超安全阈值被紧急终止，说明系统对该故障类型"
                + "的容错能力不足，需要加强熔断/降级/限流策略");
        } else if (!ctx.anomalies.isEmpty()) {
            report.verdict = "FAILED";
            report.recommendations.add(
                "演练过程中发现异常，需要排查并修复后重新演练");
        } else if (!ctx.recoveryConfirmed) {
            report.verdict = "FAILED";
            report.recommendations.add(
                "故障恢复验证未通过，需要检查恢复机制的可靠性");
        } else {
            report.verdict = "PASSED";
            report.recommendations.add(
                "系统成功抵御了本次故障注入，"
                + "建议逐步提高注入比例或故障强度继续验证");
        }

        report.phaseTimeline.put("REPORT_GENERATION", now());

        logger.info("[Drill:{}] [阶段六] 演练报告: verdict={}, "
            + "耗时={}ms, 异常数={}",
            ctx.drillId, report.verdict,
            report.durationMillis, report.anomalies.size());
    }

    /**
     * 强制恢复（异常场景下的兜底恢复）
     */
    private void forceRecovery(DrillContext ctx) {
        logger.warn("[Drill:{}] 执行强制恢复", ctx.drillId);
        recoveryManager.idempotentRecover(
            ctx.drillId,
            () -> {
                for (String node : ctx.rule.getTargetNodes()) {
                    try {
                        injectorAgent.recoverFault(ctx.drillId, node);
                    } catch (Exception ignored) {
                        // 强制恢复模式下，单节点失败不阻断
                    }
                }
            },
            () -> injectorAgent.verifyRecovery(
                ctx.drillId, ctx.rule.getTargetService()),
            10 // 强制恢复允许更多重试次数
        );
    }

    private String generateDrillId() {
        return "DRILL-" + LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
            + "-" + UUID.randomUUID().toString().substring(0, 8);
    }

    private String now() {
        return LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
    }

    private void sleepQuietly(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    // === 依赖接口定义 ===

    /**
     * 故障注入 Agent 接口
     */
    public interface FaultInjectorAgent {
        boolean injectFault(String drillId, String node,
                            FaultCategory category,
                            Map<String, String> params,
                            double ratio);
        void recoverFault(String drillId, String node);
        boolean verifyInjection(String drillId, String service);
        boolean verifyRecovery(String drillId, String service);
    }

    /**
     * 指标查询服务接口
     */
    public interface MetricsQueryService {
        boolean isServiceHealthy(String service);
        MetricBaseline collectBaseline(String service, int durationSeconds);
        MetricSample collectCurrentSample(String service);
    }

    /**
     * 幂等恢复管理器
     *
     * 核心思想：对同一个 drillId，无论 idempotentRecover 被调用多少次，
     * 实际的恢复动作只会在 "尚未确认恢复" 的情况下执行，
     * 一旦验证通过则后续调用直接短路返回 true
     */
    public interface IdempotentRecoveryManager {
        boolean idempotentRecover(String drillId,
                                  Runnable recoveryAction,
                                  java.util.function.Supplier<Boolean> verify,
                                  int maxRetries);
    }

    /**
     * 告警通知接口
     */
    public interface AlertNotifier {
        void sendP0Alert(String drillId, String message);
    }
}
```

### 7.2 案例二：容灾切换演练全链路

#### 7.2.1 场景概述

容灾切换演练是所有演练中业务影响最大、操作风险最高的类型，直接关系到"当整个机房不可用时，系统能否在 RTO 目标内恢复"这个关键问题。一次完整的容灾切换演练流程包括五个阶段：**模拟机房故障 → 流量切换 → 验证可用性 → 回切 → 演练总结**。本案例以"同城双活架构下，模拟 A 机房整体不可用，验证流量切换到 B 机房后业务可用性"为例，展示完整的容灾切换演练实现。

核心设计要点：

- 分阶段执行：先排空流量（Escape）再断网（Cutoff），最大限度降低对真实用户的冲击；
- 每个阶段都设有"继续/中止"决策点，一旦发现异常指标超预期，立即中止并回切；
- 流量切换和回切操作均具备幂等性，重复操作不会导致状态混乱；
- 全程记录 RTO（恢复时间目标）的实测值，与设计目标对比。

#### 7.2.2 完整代码实现

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicReference;

/**
 * 容灾切换演练全链路执行器
 *
 * 设计模式：状态机 + 策略模式 + 命令模式
 *
 * 状态机：管理演练的五个阶段及其合法转换路径
 * 策略模式：不同的容灾架构（同城双活/异地多活）采用不同的切换策略
 * 命令模式：每个阶段的操作封装为可执行、可回滚的命令
 *
 * 全链路流程：
 * 模拟机房故障 → 流量切换 → 验证可用性 → 回切 → 演练总结
 *
 * 幂等控制：
 * 流量切换和回切操作基于目标状态驱动（声明式），
 * 而非操作步骤驱动（命令式），天然具备幂等性——
 * "确保 A 机房权重为 0" 无论执行多少次结果都一致
 */
public class DisasterRecoveryDrillPipeline {

    private static final Logger logger = LoggerFactory.getLogger(
        DisasterRecoveryDrillPipeline.class);

    /**
     * 容灾演练阶段枚举
     */
    public enum DRPhase {
        SIMULATE_FAILURE,     // 阶段一：模拟机房故障
        TRAFFIC_SWITCH,       // 阶段二：流量切换
        VERIFY_AVAILABILITY,  // 阶段三：验证可用性
        TRAFFIC_SWITCHBACK,   // 阶段四：回切
        DRILL_SUMMARY         // 阶段五：演练总结
    }

    /**
     * 容灾架构类型
     */
    public enum DRArchitecture {
        ACTIVE_STANDBY("主备切换"),
        ACTIVE_ACTIVE_SAME_CITY("同城双活"),
        ACTIVE_ACTIVE_CROSS_REGION("异地多活"),
        UNIT_BASED("单元化");

        private final String name;

        DRArchitecture(String name) { this.name = name; }
        public String getName() { return name; }
    }

    /**
     * 容灾切换演练计划
     */
    public static class DRDrillPlan {
        private String drillId;
        private DRArchitecture architecture;
        private String failoverSourceDc;      // 故障模拟目标机房
        private String failoverTargetDc;      // 流量承接机房
        private List<String> criticalServices; // 核心服务列表
        private int rtoTargetSeconds;          // RTO目标（秒）
        private int rpoTargetSeconds;          // RPO目标（秒）
        private boolean escapeBeforeCutoff;    // 是否先排空流量再断网

        // 安全阈值
        private double maxErrorRateDuringSwitch;  // 切换期间最大错误率
        private double maxP99MillisDuringSwitch;  // 切换期间最大P99 RT
        private int maxSwitchDurationSeconds;     // 最大切换耗时

        // getter/setter 省略
        public String getDrillId() { return drillId; }
        public void setDrillId(String id) { this.drillId = id; }
        public DRArchitecture getArchitecture() { return architecture; }
        public void setArchitecture(DRArchitecture a) { this.architecture = a; }
        public String getFailoverSourceDc() { return failoverSourceDc; }
        public void setFailoverSourceDc(String dc) { this.failoverSourceDc = dc; }
        public String getFailoverTargetDc() { return failoverTargetDc; }
        public void setFailoverTargetDc(String dc) { this.failoverTargetDc = dc; }
        public List<String> getCriticalServices() { return criticalServices; }
        public void setCriticalServices(List<String> s) {
            this.criticalServices = s;
        }
        public int getRtoTargetSeconds() { return rtoTargetSeconds; }
        public void setRtoTargetSeconds(int s) { this.rtoTargetSeconds = s; }
        public int getRpoTargetSeconds() { return rpoTargetSeconds; }
        public void setRpoTargetSeconds(int s) { this.rpoTargetSeconds = s; }
        public boolean isEscapeBeforeCutoff() { return escapeBeforeCutoff; }
        public void setEscapeBeforeCutoff(boolean b) {
            this.escapeBeforeCutoff = b;
        }
        public double getMaxErrorRateDuringSwitch() {
            return maxErrorRateDuringSwitch;
        }
        public void setMaxErrorRateDuringSwitch(double r) {
            this.maxErrorRateDuringSwitch = r;
        }
        public double getMaxP99MillisDuringSwitch() {
            return maxP99MillisDuringSwitch;
        }
        public void setMaxP99MillisDuringSwitch(double m) {
            this.maxP99MillisDuringSwitch = m;
        }
        public int getMaxSwitchDurationSeconds() {
            return maxSwitchDurationSeconds;
        }
        public void setMaxSwitchDurationSeconds(int s) {
            this.maxSwitchDurationSeconds = s;
        }
    }

    /**
     * 容灾演练上下文
     */
    public static class DRDrillContext {
        String drillId;
        DRPhase currentPhase;
        DRDrillPlan plan;
        long drillStartMillis;
        long drillEndMillis;

        // 阶段产出
        long failureSimulatedAt;              // 故障模拟时间点
        long trafficSwitchStartAt;            // 流量切换开始时间点
        long trafficSwitchCompleteAt;         // 流量切换完成时间点
        long availabilityVerifiedAt;          // 可用性验证通过时间点
        long switchbackCompleteAt;            // 回切完成时间点

        // RTO实测
        int measuredRtoSeconds;               // 实测RTO

        // 状态标记
        boolean failureSimulated;
        boolean trafficSwitched;
        boolean availabilityVerified;
        boolean switchedBack;
        boolean aborted;
        String abortReason;

        List<ServiceAvailabilityCheck> availabilityChecks;
        List<String> issues;
        DRDrillReport report;

        DRDrillContext(String drillId, DRDrillPlan plan) {
            this.drillId = drillId;
            this.plan = plan;
            this.availabilityChecks = new ArrayList<>();
            this.issues = new ArrayList<>();
        }
    }

    /**
     * 服务可用性检查结果
     */
    public static class ServiceAvailabilityCheck {
        String serviceName;
        boolean available;
        double errorRate;
        double p99Millis;
        double qps;
        long checkTimestamp;
    }

    /**
     * 容灾演练报告
     */
    public static class DRDrillReport {
        String drillId;
        String architecture;
        String sourceDc;
        String targetDc;
        String verdict;             // PASSED / FAILED / ABORTED
        long startTime;
        long endTime;
        int rtoTarget;
        int rtoMeasured;
        boolean rtoMet;             // RTO是否达标
        boolean aborted;
        String abortReason;
        List<ServiceAvailabilityCheck> serviceChecks;
        List<String> issues;
        List<String> recommendations;
        Map<String, String> phaseTimeline;

        DRDrillReport() {
            this.serviceChecks = new ArrayList<>();
            this.issues = new ArrayList<>();
            this.recommendations = new ArrayList<>();
            this.phaseTimeline = new LinkedHashMap<>();
        }
    }

    // === 依赖组件 ===
    private final TrafficScheduler trafficScheduler;
    private final NetworkController networkController;
    private final ServiceHealthChecker healthChecker;
    private final IdempotentSwitchManager switchManager;
    private final AlertNotifier alertNotifier;

    public DisasterRecoveryDrillPipeline(
            TrafficScheduler trafficScheduler,
            NetworkController networkController,
            ServiceHealthChecker healthChecker,
            IdempotentSwitchManager switchManager,
            AlertNotifier alertNotifier) {
        this.trafficScheduler = trafficScheduler;
        this.networkController = networkController;
        this.healthChecker = healthChecker;
        this.switchManager = switchManager;
        this.alertNotifier = alertNotifier;
    }

    /**
     * 执行完整的容灾切换演练全链路
     *
     * 算法流程：
     * 1. 模拟机房故障（排空流量 → 网络隔离）
     * 2. 流量切换（将故障机房的流量调度到备份机房）
     * 3. 验证可用性（逐个检查核心服务的健康状态）
     * 4. 回切（恢复网络 → 恢复流量分配 → 验证回切后的可用性）
     * 5. 生成演练总结报告
     *
     * 异常处理策略：
     * - 任何阶段出现不可接受的异常，都立即中止并执行回切
     * - 回切操作采用幂等设计，重复执行不会产生副作用
     * - 关键操作（流量切换/网络隔离）都有操作前确认和操作后验证
     */
    public DRDrillReport executeDrill(DRDrillPlan plan) {
        String drillId = generateDrillId("DR");
        plan.setDrillId(drillId);
        DRDrillContext ctx = new DRDrillContext(drillId, plan);
        ctx.drillStartMillis = System.currentTimeMillis();

        logger.info("[DR:{}] ====== 容灾切换演练开始 ======", drillId);
        logger.info("[DR:{}] 架构={}, 故障机房={}, 承接机房={}, "
            + "RTO目标={}s",
            drillId, plan.getArchitecture().getName(),
            plan.getFailoverSourceDc(), plan.getFailoverTargetDc(),
            plan.getRtoTargetSeconds());

        try {
            // === 阶段一：模拟机房故障 ===
            phaseSimulateFailure(ctx);

            // === 阶段二：流量切换 ===
            if (!ctx.aborted) {
                phaseTrafficSwitch(ctx);
            }

            // === 阶段三：验证可用性 ===
            if (!ctx.aborted) {
                phaseVerifyAvailability(ctx);
            }

        } catch (Exception e) {
            logger.error("[DR:{}] 演练过程发生异常", drillId, e);
            ctx.aborted = true;
            ctx.abortReason = "演练异常: " + e.getMessage();
            ctx.issues.add("演练异常: " + e.getMessage());
        } finally {
            // === 阶段四：回切（无论成功失败都必须执行） ===
            try {
                phaseTrafficSwitchback(ctx);
            } catch (Exception e) {
                logger.error("[DR:{}] 回切失败, 升级P0告警", drillId, e);
                alertNotifier.sendP0Alert(drillId,
                    "容灾回切失败，需要人工介入: " + e.getMessage());
                ctx.issues.add("回切失败: " + e.getMessage());
            }

            // === 阶段五：演练总结 ===
            ctx.drillEndMillis = System.currentTimeMillis();
            phaseDrillSummary(ctx);

            logger.info("[DR:{}] ====== 容灾切换演练结束, 结论={}, "
                + "实测RTO={}s ======",
                drillId, ctx.report.verdict, ctx.report.rtoMeasured);
        }

        return ctx.report;
    }

    /**
     * 阶段一：模拟机房故障
     *
     * 根据配置决定是否先排空流量（Escape模式）再断网，
     * 还是直接断网（Cutoff模式）
     *
     * Escape模式（推荐）：
     *   1. 先将故障机房的流量权重降为0
     *   2. 等待存量请求处理完毕（30秒）
     *   3. 再执行网络隔离
     *   优点：对用户影响最小；缺点：无法验证"突发故障"场景
     *
     * Cutoff模式：
     *   1. 直接执行网络隔离，不预先排空流量
     *   优点：模拟真实的突发故障；缺点：会有短暂的请求失败
     */
    private void phaseSimulateFailure(DRDrillContext ctx) {
        ctx.currentPhase = DRPhase.SIMULATE_FAILURE;
        DRDrillPlan plan = ctx.plan;
        logger.info("[DR:{}] [阶段一] 开始模拟机房故障, 目标机房={}",
            ctx.drillId, plan.getFailoverSourceDc());

        if (plan.isEscapeBeforeCutoff()) {
            // === Escape模式：先排空流量 ===
            logger.info("[DR:{}] [阶段一] Escape模式: "
                + "先排空流量再断网", ctx.drillId);

            // 幂等地将故障机房权重设为0
            switchManager.ensureTrafficWeight(
                ctx.drillId, plan.getFailoverSourceDc(), 0);

            logger.info("[DR:{}] [阶段一] 流量已排空, 等待30秒处理存量请求",
                ctx.drillId);
            sleepQuietly(30_000);

            // 验证流量已排空
            double remainingQps = healthChecker.getQpsForDc(
                plan.getFailoverSourceDc());
            if (remainingQps > 1.0) {
                logger.warn("[DR:{}] [阶段一] 排空后仍有残留流量: "
                    + "QPS={}", ctx.drillId, remainingQps);
                ctx.issues.add(String.format(
                    "流量排空不完全，残留QPS=%.1f", remainingQps));
            }
        }

        // 执行网络隔离
        logger.info("[DR:{}] [阶段一] 执行网络隔离", ctx.drillId);
        networkController.isolateDc(
            ctx.drillId, plan.getFailoverSourceDc());

        ctx.failureSimulated = true;
        ctx.failureSimulatedAt = System.currentTimeMillis();

        logger.info("[DR:{}] [阶段一] 机房故障模拟完成", ctx.drillId);
        ctx.report = new DRDrillReport();
        ctx.report.phaseTimeline.put("SIMULATE_FAILURE", now());
    }

    /**
     * 阶段二：流量切换
     *
     * 确保所有流量都调度到目标（承接）机房
     *
     * 幂等控制：
     * 流量切换使用声明式的 "确保目标机房权重为100" 语义，
     * 无论当前状态如何，最终都收敛到目标状态
     */
    private void phaseTrafficSwitch(DRDrillContext ctx) {
        ctx.currentPhase = DRPhase.TRAFFIC_SWITCH;
        DRDrillPlan plan = ctx.plan;
        ctx.trafficSwitchStartAt = System.currentTimeMillis();
        logger.info("[DR:{}] [阶段二] 开始流量切换, 目标机房={}",
            ctx.drillId, plan.getFailoverTargetDc());

        // 幂等地将目标机房权重设为100
        switchManager.ensureTrafficWeight(
            ctx.drillId, plan.getFailoverTargetDc(), 100);

        // 等待流量调度生效（DNS TTL + 负载均衡刷新）
        logger.info("[DR:{}] [阶段二] 等待流量调度生效（10秒）",
            ctx.drillId);
        sleepQuietly(10_000);

        // 验证流量已切换
        double targetDcQps = healthChecker.getQpsForDc(
            plan.getFailoverTargetDc());
        if (targetDcQps <= 0) {
            logger.error("[DR:{}] [阶段二] 目标机房无流量进入, "
                + "流量切换可能失败", ctx.drillId);
            ctx.issues.add("流量切换后目标机房无流量");
        }

        ctx.trafficSwitched = true;
        ctx.trafficSwitchCompleteAt = System.currentTimeMillis();

        // 计算流量切换耗时
        long switchDurationMs = ctx.trafficSwitchCompleteAt
            - ctx.failureSimulatedAt;
        logger.info("[DR:{}] [阶段二] 流量切换完成, 耗时={}ms, "
            + "目标机房QPS={}",
            ctx.drillId, switchDurationMs, targetDcQps);

        // 检查切换耗时是否超出限制
        if (switchDurationMs > plan.getMaxSwitchDurationSeconds() * 1000L) {
            logger.warn("[DR:{}] [阶段二] 切换耗时 {}ms 超出限制 {}s",
                ctx.drillId, switchDurationMs,
                plan.getMaxSwitchDurationSeconds());
            ctx.issues.add(String.format("切换耗时 %dms 超出限制 %ds",
                switchDurationMs, plan.getMaxSwitchDurationSeconds()));
        }

        ctx.report.phaseTimeline.put("TRAFFIC_SWITCH", now());
    }

    /**
     * 阶段三：验证可用性
     *
     * 逐个检查所有核心服务在目标机房的健康状态，
     * 包括错误率、响应时间、QPS 等关键指标
     *
     * 算法：
     * 1. 对每个核心服务进行健康检查
     * 2. 检查结果分为 "可用" 和 "不可用" 两类
     * 3. 所有核心服务都可用才算验证通过
     * 4. 记录每个服务的详细指标用于报告
     */
    private void phaseVerifyAvailability(DRDrillContext ctx) {
        ctx.currentPhase = DRPhase.VERIFY_AVAILABILITY;
        logger.info("[DR:{}] [阶段三] 开始验证可用性, 核心服务数={}",
            ctx.drillId, ctx.plan.getCriticalServices().size());

        boolean allAvailable = true;

        for (String service : ctx.plan.getCriticalServices()) {
            ServiceAvailabilityCheck check = new ServiceAvailabilityCheck();
            check.serviceName = service;
            check.checkTimestamp = System.currentTimeMillis();

            try {
                // 查询服务在目标机房的指标
                check.errorRate = healthChecker.getErrorRate(
                    service, ctx.plan.getFailoverTargetDc());
                check.p99Millis = healthChecker.getP99Millis(
                    service, ctx.plan.getFailoverTargetDc());
                check.qps = healthChecker.getQps(
                    service, ctx.plan.getFailoverTargetDc());

                // 判断是否可用
                check.available =
                    check.errorRate <= ctx.plan.getMaxErrorRateDuringSwitch()
                    && check.p99Millis <= ctx.plan.getMaxP99MillisDuringSwitch()
                    && check.qps > 0;

                if (!check.available) {
                    allAvailable = false;
                    String reason = String.format(
                        "服务 %s 不可用: errorRate=%.4f, P99=%.0fms, QPS=%.0f",
                        service, check.errorRate,
                        check.p99Millis, check.qps);
                    logger.warn("[DR:{}] [阶段三] {}", ctx.drillId, reason);
                    ctx.issues.add(reason);
                } else {
                    logger.info("[DR:{}] [阶段三] 服务 {} 可用: "
                        + "errorRate={}, P99={}ms, QPS={}",
                        ctx.drillId, service, check.errorRate,
                        check.p99Millis, check.qps);
                }

            } catch (Exception e) {
                logger.error("[DR:{}] [阶段三] 服务 {} 健康检查异常",
                    ctx.drillId, service, e);
                check.available = false;
                allAvailable = false;
                ctx.issues.add("服务 " + service + " 健康检查异常: "
                    + e.getMessage());
            }

            ctx.availabilityChecks.add(check);
        }

        ctx.availabilityVerified = allAvailable;
        if (allAvailable) {
            ctx.availabilityVerifiedAt = System.currentTimeMillis();
            // 计算实测RTO
            ctx.measuredRtoSeconds = (int) (
                (ctx.availabilityVerifiedAt - ctx.failureSimulatedAt) / 1000);
            logger.info("[DR:{}] [阶段三] 所有核心服务可用性验证通过, "
                + "实测RTO={}s (目标RTO={}s)",
                ctx.drillId, ctx.measuredRtoSeconds,
                ctx.plan.getRtoTargetSeconds());
        } else {
            logger.error("[DR:{}] [阶段三] 部分核心服务可用性验证未通过",
                ctx.drillId);
        }

        ctx.report.phaseTimeline.put("VERIFY_AVAILABILITY", now());
    }

    /**
     * 阶段四：回切
     *
     * 恢复网络连通性，将流量分配恢复到演练前的状态
     *
     * 执行顺序：
     * 1. 恢复故障机房的网络连通性
     * 2. 等待服务在故障机房重新就绪
     * 3. 逐步恢复故障机房的流量权重
     * 4. 验证回切后双机房都健康
     *
     * 幂等控制：
     * 每一步操作都使用 switchManager 的声明式接口，
     * 重复调用收敛到同一目标状态
     */
    private void phaseTrafficSwitchback(DRDrillContext ctx) {
        ctx.currentPhase = DRPhase.TRAFFIC_SWITCHBACK;
        logger.info("[DR:{}] [阶段四] 开始回切", ctx.drillId);

        // 步骤1：恢复网络连通性
        if (ctx.failureSimulated) {
            logger.info("[DR:{}] [阶段四] 恢复网络连通性", ctx.drillId);
            networkController.restoreDc(
                ctx.drillId, ctx.plan.getFailoverSourceDc());
            sleepQuietly(5000); // 等待网络恢复
        }

        // 步骤2：等待故障机房服务恢复就绪
        logger.info("[DR:{}] [阶段四] 等待故障机房服务恢复就绪",
            ctx.drillId);
        int maxWaitSeconds = 60;
        boolean servicesReady = false;
        for (int i = 0; i < maxWaitSeconds; i += 5) {
            servicesReady = healthChecker.isDcReady(
                ctx.plan.getFailoverSourceDc());
            if (servicesReady) {
                break;
            }
            sleepQuietly(5000);
        }

        if (!servicesReady) {
            logger.error("[DR:{}] [阶段四] 故障机房服务未能在 {}s 内恢复",
                ctx.drillId, maxWaitSeconds);
            ctx.issues.add("故障机房服务未能在回切等待时间内恢复");
            // 即使未就绪也恢复流量权重，但记录问题
        }

        // 步骤3：逐步恢复流量权重（渐进式，避免瞬间冲击）
        logger.info("[DR:{}] [阶段四] 逐步恢复故障机房流量权重",
            ctx.drillId);

        int[] weightSteps = {10, 30, 50}; // 分三步恢复到50%
        for (int weight : weightSteps) {
            switchManager.ensureTrafficWeight(
                ctx.drillId, ctx.plan.getFailoverSourceDc(), weight);
            logger.info("[DR:{}] [阶段四] 故障机房权重已设为 {}%",
                ctx.drillId, weight);
            sleepQuietly(5000);

            // 每步都检查是否出现异常
            double errorRate = healthChecker.getErrorRate(
                ctx.plan.getCriticalServices().get(0),
                ctx.plan.getFailoverSourceDc());
            if (errorRate > ctx.plan.getMaxErrorRateDuringSwitch()) {
                logger.warn("[DR:{}] [阶段四] 回切过程中错误率偏高: {}",
                    ctx.drillId, errorRate);
                ctx.issues.add(String.format(
                    "回切到权重%d%%时错误率偏高: %.4f", weight, errorRate));
            }
        }

        ctx.switchedBack = true;
        ctx.switchbackCompleteAt = System.currentTimeMillis();

        logger.info("[DR:{}] [阶段四] 回切完成", ctx.drillId);
        ctx.report.phaseTimeline.put("TRAFFIC_SWITCHBACK", now());
    }

    /**
     * 阶段五：演练总结
     *
     * 汇总所有阶段数据，生成结构化报告，
     * 重点对比 RTO 实测值与目标值
     */
    private void phaseDrillSummary(DRDrillContext ctx) {
        ctx.currentPhase = DRPhase.DRILL_SUMMARY;
        logger.info("[DR:{}] [阶段五] 生成演练总结", ctx.drillId);

        DRDrillReport report = ctx.report;
        if (report == null) {
            report = new DRDrillReport();
            ctx.report = report;
        }

        report.drillId = ctx.drillId;
        report.architecture = ctx.plan.getArchitecture().getName();
        report.sourceDc = ctx.plan.getFailoverSourceDc();
        report.targetDc = ctx.plan.getFailoverTargetDc();
        report.startTime = ctx.drillStartMillis;
        report.endTime = ctx.drillEndMillis;
        report.rtoTarget = ctx.plan.getRtoTargetSeconds();
        report.rtoMeasured = ctx.measuredRtoSeconds;
        report.rtoMet = ctx.measuredRtoSeconds <= ctx.plan.getRtoTargetSeconds();
        report.aborted = ctx.aborted;
        report.abortReason = ctx.abortReason;
        report.serviceChecks = ctx.availabilityChecks;
        report.issues = ctx.issues;

        // 判定演练结论
        if (ctx.aborted) {
            report.verdict = "ABORTED";
            report.recommendations.add(
                "演练被中止，需要排查中止原因并修复后重新演练");
        } else if (!ctx.availabilityVerified) {
            report.verdict = "FAILED";
            report.recommendations.add(
                "部分核心服务在故障切换后不可用，"
                + "需要排查服务在目标机房的部署和配置");
        } else if (!report.rtoMet) {
            report.verdict = "FAILED";
            report.recommendations.add(String.format(
                "实测RTO(%ds)未达标(目标%ds)，"
                + "需要优化流量调度和服务发现的收敛速度",
                report.rtoMeasured, report.rtoTarget));
        } else if (!ctx.issues.isEmpty()) {
            report.verdict = "PASSED_WITH_ISSUES";
            report.recommendations.add(
                "演练基本通过但存在告警项，建议逐项排查后再次验证");
        } else {
            report.verdict = "PASSED";
            report.recommendations.add(
                "容灾切换演练通过，建议定期重复执行以持续验证");
        }

        report.phaseTimeline.put("DRILL_SUMMARY", now());

        logger.info("[DR:{}] [阶段五] 演练总结: verdict={}, "
            + "RTO实测={}s/目标={}s, 问题数={}",
            ctx.drillId, report.verdict,
            report.rtoMeasured, report.rtoTarget, report.issues.size());
    }

    private String generateDrillId(String prefix) {
        return prefix + "-" + LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
            + "-" + UUID.randomUUID().toString().substring(0, 8);
    }

    private String now() {
        return LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
    }

    private void sleepQuietly(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    // === 依赖接口定义 ===

    /**
     * 流量调度器接口
     */
    public interface TrafficScheduler {
        void setDcWeight(String dc, int weight);
        int getDcWeight(String dc);
    }

    /**
     * 网络控制器接口
     */
    public interface NetworkController {
        void isolateDc(String drillId, String dc);
        void restoreDc(String drillId, String dc);
    }

    /**
     * 服务健康检查器接口
     */
    public interface ServiceHealthChecker {
        double getErrorRate(String service, String dc);
        double getP99Millis(String service, String dc);
        double getQps(String service, String dc);
        double getQpsForDc(String dc);
        boolean isDcReady(String dc);
    }

    /**
     * 幂等切换管理器
     *
     * 核心思想：流量权重切换采用声明式语义——
     * "确保某机房权重为 X" 而非 "将某机房权重改为 X"，
     * 前者天然幂等，后者在并发或重试场景下可能产生意外行为
     */
    public interface IdempotentSwitchManager {
        void ensureTrafficWeight(String drillId, String dc, int weight);
    }

    /**
     * 告警通知接口
     */
    public interface AlertNotifier {
        void sendP0Alert(String drillId, String message);
    }
}
```

### 7.3 案例三：混沌实验自动化全链路

#### 7.3.1 场景概述

混沌工程的最终形态是将实验自动化——不再依赖人工编排和执行，而是由系统自动完成"实验设计 → 稳态假设 → 注入扰动 → 观察偏差 → 自动中止 → 改进措施"的完整闭环。本案例实现一个混沌实验自动化引擎，支持声明式定义实验计划（Chaos as Code），自动执行、自动判定、自动生成改进建议，并可集成到 CI/CD 流水线中作为"稳定性回归测试"的一环。

核心设计要点：

- 实验计划以声明式的 YAML/JSON 配置描述，纳入版本管理，支持代码评审；
- 稳态假设是实验的核心——先定义"正常应该是什么样"，再注入扰动看是否偏离；
- 自动中止机制基于"安全边界"与"稳态偏离"的双重判定，任一触发则立即终止；
- 所有操作都有完整的日志记录和幂等保障，实验可以安全地重复执行；
- 实验结束后自动生成结构化的改进措施清单，与团队的问题跟踪系统对接。

#### 7.3.2 完整代码实现

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.stream.Collectors;

/**
 * 混沌实验自动化全链路引擎
 *
 * 设计模式：模板方法 + 策略模式 + 观察者模式
 *
 * 模板方法：定义实验的六个阶段骨架，子类/策略可定制每个阶段的具体行为
 * 策略模式：不同的扰动类型（网络/资源/应用）采用不同的注入策略
 * 观察者模式：实验状态变化时通知所有观察者（日志/告警/报告生成器）
 *
 * 全链路流程：
 * 实验设计 → 稳态假设 → 注入扰动 → 观察偏差 → 自动中止 → 改进措施
 *
 * 幂等控制：
 * 1. 实验以 experimentId 为幂等键，同一 experimentId 不会被并发执行
 * 2. 扰动注入和恢复都基于 experimentId 做幂等判断
 * 3. 实验执行记录持久化，重启后可恢复未完成的实验
 */
public class ChaosExperimentAutomationEngine {

    private static final Logger logger = LoggerFactory.getLogger(
        ChaosExperimentAutomationEngine.class);

    /**
     * 混沌实验阶段枚举
     */
    public enum ChaosPhase {
        EXPERIMENT_DESIGN,     // 阶段一：实验设计
        STEADY_STATE_HYPOTHESIS, // 阶段二：稳态假设
        PERTURBATION_INJECTION,  // 阶段三：注入扰动
        DEVIATION_OBSERVATION,   // 阶段四：观察偏差
        AUTO_HALT,               // 阶段五：自动中止
        IMPROVEMENT_ACTIONS       // 阶段六：改进措施
    }

    /**
     * 扰动类型
     */
    public enum PerturbationType {
        NETWORK_DELAY("网络延迟"),
        NETWORK_PARTITION("网络分区"),
        RESOURCE_PRESSURE("资源压力"),
        DEPENDENCY_FAILURE("依赖故障"),
        DATA_INCONSISTENCY("数据不一致"),
        TRAFFIC_SPIKE("流量突增");

        private final String name;
        PerturbationType(String name) { this.name = name; }
        public String getName() { return name; }
    }

    /**
     * 混沌实验声明式定义
     *
     * 可从 YAML/JSON 配置反序列化，实现 "Chaos as Code"
     */
    public static class ChaosExperimentDefinition {
        private String experimentId;
        private String experimentName;
        private String description;
        private String targetService;
        private PerturbationType perturbationType;
        private Map<String, String> perturbationParams;

        // 稳态假设定义
        private double steadyStateMaxErrorRate;
        private double steadyStateMaxP99Millis;
        private double steadyStateMinQps;
        private double steadyStateMaxQpsDropPercent; // QPS最大下降比例

        // 安全边界（比稳态假设更宽松，触发则立即中止）
        private double safetyBoundaryErrorRate;
        private double safetyBoundaryP99Millis;
        private double safetyBoundaryMinQps;

        // 实验参数
        private int baselineCollectionSeconds;  // 基线采集时长
        private int perturbationDurationSeconds; // 扰动持续时长
        private int observationIntervalMillis;   // 观察采样间隔
        private int recoveryTimeoutSeconds;       // 恢复超时时间

    /**
     * 执行混沌实验全链路
     *
     * 算法流程：
     * 1. 实验设计：校验实验定义的完整性和合理性
     * 2. 稳态假设：采集系统基线并验证当前处于稳态
     * 3. 注入扰动：按定义注入扰动，验证注入生效
     * 4. 观察偏差：持续观察指标，检测是否偏离稳态假设
     * 5. 自动中止：偏离超过安全边界时自动中止并恢复
     * 6. 改进措施：根据偏差分析生成改进建议
     *
     * 幂等控制：
     * - 同一 experimentId 不允许并发执行（通过 CAS 实现）
     * - 扰动注入和恢复通过 experimentLock 保证幂等
     *
     * 异常处理：
     * - 任何阶段的异常都会触发恢复流程
     * - 恢复流程本身的异常会升级为 P0 告警
     */
    public ChaosExperimentReport runExperiment(
            ChaosExperimentDefinition definition) {

        String experimentId = definition.getExperimentId();
        String runId = generateRunId(experimentId);

        // === 并发控制：同一实验不允许并发执行 ===
        AtomicBoolean running = runningExperiments.computeIfAbsent(
            experimentId, k -> new AtomicBoolean(false));
        if (!running.compareAndSet(false, true)) {
            logger.warn("[Chaos:{}] 实验 {} 正在运行中, 拒绝重复执行",
                runId, experimentId);
            ChaosExperimentReport rejectReport = new ChaosExperimentReport();
            rejectReport.runId = runId;
            rejectReport.experimentId = experimentId;
            rejectReport.verdict = "REJECTED";
            rejectReport.conclusions.add(
                "实验正在运行中，拒绝重复执行（幂等控制）");
            return rejectReport;
        }

        ExperimentRunContext ctx = new ExperimentRunContext(
            runId, definition);
        ctx.startTimeMillis = System.currentTimeMillis();

        logger.info("[Chaos:{}] ====== 混沌实验开始 ======", runId);
        logger.info("[Chaos:{}] 实验={}, 目标服务={}, 扰动类型={}",
            runId, definition.getExperimentName(),
            definition.getTargetService(),
            definition.getPerturbationType().getName());

        try {
            // === 阶段一：实验设计 ===
            phaseExperimentDesign(ctx);

            // === 阶段二：稳态假设 ===
            phaseSteadyStateHypothesis(ctx);

            // === 阶段三：注入扰动 ===
            phasePerturbationInjection(ctx);

            // === 阶段四：观察偏差 ===
            phaseDeviationObservation(ctx);

        } catch (Exception e) {
            logger.error("[Chaos:{}] 实验执行异常", runId, e);
            ctx.autoHalted = true;
            ctx.haltReason = "实验执行异常: " + e.getMessage();
        } finally {
            // === 阶段五：自动中止与恢复 ===
            try {
                phaseAutoHalt(ctx);
            } catch (Exception recoveryEx) {
                logger.error("[Chaos:{}] 恢复过程异常, 升级P0告警",
                    runId, recoveryEx);
                alertNotifier.sendP0Alert(runId,
                    "混沌实验恢复失败: " + recoveryEx.getMessage());
            }

            // === 阶段六：改进措施 ===
            ctx.endTimeMillis = System.currentTimeMillis();
            phaseImprovementActions(ctx);

            // 释放并发控制锁
            running.set(false);

            logger.info("[Chaos:{}] ====== 混沌实验结束, 结论={} ======",
                runId, ctx.report.verdict);
        }

        return ctx.report;
    }

    /**
     * 阶段一：实验设计
     *
     * 校验实验定义的完整性和合理性，
     * 确保所有必要的参数都已配置且在合理范围内
     *
     * 校验规则：
     * 1. 实验ID和名称不能为空
     * 2. 目标服务必须存在且可达
     * 3. 稳态假设阈值必须严格低于安全边界阈值
     * 4. 扰动持续时间不能超过平台允许的上限
     * 5. 观察间隔不能小于指标采集的最小粒度
     */
    private void phaseExperimentDesign(ExperimentRunContext ctx) {
        ctx.currentPhase = ChaosPhase.EXPERIMENT_DESIGN;
        ChaosExperimentDefinition def = ctx.definition;
        logger.info("[Chaos:{}] [阶段一] 实验设计校验", ctx.runId);

        // 校验基本字段
        if (def.getExperimentId() == null
                || def.getExperimentId().isEmpty()) {
            throw new IllegalArgumentException("实验ID不能为空");
        }
        if (def.getTargetService() == null
                || def.getTargetService().isEmpty()) {
            throw new IllegalArgumentException("目标服务不能为空");
        }
        if (def.getPerturbationType() == null) {
            throw new IllegalArgumentException("扰动类型不能为空");
        }

        // 校验稳态假设阈值 < 安全边界阈值
        if (def.getSteadyStateMaxErrorRate()
                >= def.getSafetyBoundaryErrorRate()) {
            throw new IllegalArgumentException(String.format(
                "稳态假设错误率阈值(%.4f)必须低于安全边界(%.4f)",
                def.getSteadyStateMaxErrorRate(),
                def.getSafetyBoundaryErrorRate()));
        }
        if (def.getSteadyStateMaxP99Millis()
                >= def.getSafetyBoundaryP99Millis()) {
            throw new IllegalArgumentException(String.format(
                "稳态假设P99阈值(%.0fms)必须低于安全边界(%.0fms)",
                def.getSteadyStateMaxP99Millis(),
                def.getSafetyBoundaryP99Millis()));
        }

        // 校验扰动持续时间
        if (def.getPerturbationDurationSeconds() <= 0
                || def.getPerturbationDurationSeconds() > 300) {
            throw new IllegalArgumentException(String.format(
                "扰动持续时间 %ds 不在合理范围 (0, 300]s 内",
                def.getPerturbationDurationSeconds()));
        }

        // 校验目标服务可达性
        boolean reachable = metricsObserver.isServiceReachable(
            def.getTargetService());
        if (!reachable) {
            throw new IllegalStateException(String.format(
                "目标服务 %s 不可达", def.getTargetService()));
        }

        logger.info("[Chaos:{}] [阶段一] 实验设计校验通过", ctx.runId);
        ctx.report = new ChaosExperimentReport();
        ctx.report.phaseTimeline.put("EXPERIMENT_DESIGN", now());
    }

    /**
     * 阶段二：稳态假设
     *
     * 采集系统当前的基线指标，验证系统确实处于稳态，
     * 只有在稳态下注入扰动才能准确判断扰动的影响
     *
     * 算法：
     * 1. 在指定时间窗口内持续采集指标
     * 2. 计算各指标的均值和标准差
     * 3. 验证均值在稳态假设范围内
     * 4. 验证标准差在合理范围内（波动不能太大）
     * 5. 如果当前不处于稳态，拒绝执行实验
     */
    private void phaseSteadyStateHypothesis(ExperimentRunContext ctx) {
        ctx.currentPhase = ChaosPhase.STEADY_STATE_HYPOTHESIS;
        ChaosExperimentDefinition def = ctx.definition;
        logger.info("[Chaos:{}] [阶段二] 稳态假设验证, 采集基线 {}s",
            ctx.runId, def.getBaselineCollectionSeconds());

        // 采集基线指标
        List<ObservationSample> baselineSamples = new ArrayList<>();
        long baselineEndTime = System.currentTimeMillis()
            + def.getBaselineCollectionSeconds() * 1000L;

        while (System.currentTimeMillis() < baselineEndTime) {
            try {
                ObservationSample sample = metricsObserver.collectSample(
                    def.getTargetService());
                sample.timestamp = System.currentTimeMillis();
                baselineSamples.add(sample);
            } catch (Exception e) {
                logger.warn("[Chaos:{}] [阶段二] 基线采集异常: {}",
                    ctx.runId, e.getMessage());
            }
            sleepQuietly(def.getObservationIntervalMillis());
        }

        if (baselineSamples.isEmpty()) {
            throw new IllegalStateException(
                "基线采集失败，未收集到任何有效采样点");
        }

        // 计算统计值
        SteadyStateBaseline baseline = new SteadyStateBaseline();
        baseline.sampleCount = baselineSamples.size();
        baseline.collectionStartTime = baselineSamples.get(0).timestamp;
        baseline.collectionEndTime = baselineSamples
            .get(baselineSamples.size() - 1).timestamp;

        baseline.avgErrorRate = baselineSamples.stream()
            .mapToDouble(s -> s.errorRate).average().orElse(0);
        baseline.avgP99Millis = baselineSamples.stream()
            .mapToDouble(s -> s.p99Millis).average().orElse(0);
        baseline.avgQps = baselineSamples.stream()
            .mapToDouble(s -> s.qps).average().orElse(0);

        // 计算标准差
        baseline.errorRateStdDev = calculateStdDev(
            baselineSamples.stream()
                .mapToDouble(s -> s.errorRate).toArray(),
            baseline.avgErrorRate);
        baseline.p99MillisStdDev = calculateStdDev(
            baselineSamples.stream()
                .mapToDouble(s -> s.p99Millis).toArray(),
            baseline.avgP99Millis);
        baseline.qpsStdDev = calculateStdDev(
            baselineSamples.stream()
                .mapToDouble(s -> s.qps).toArray(),
            baseline.avgQps);

        ctx.baseline = baseline;

        // 验证当前是否处于稳态
        if (baseline.avgErrorRate > def.getSteadyStateMaxErrorRate()) {
            throw new IllegalStateException(String.format(
                "当前错误率 %.4f 已超出稳态假设 %.4f，"
                + "系统未处于稳态，拒绝执行实验",
                baseline.avgErrorRate,
                def.getSteadyStateMaxErrorRate()));
        }
        if (baseline.avgP99Millis > def.getSteadyStateMaxP99Millis()) {
            throw new IllegalStateException(String.format(
                "当前P99 %.0fms 已超出稳态假设 %.0fms，"
                + "系统未处于稳态，拒绝执行实验",
                baseline.avgP99Millis,
                def.getSteadyStateMaxP99Millis()));
        }

        logger.info("[Chaos:{}] [阶段二] 稳态验证通过, "
            + "基线: errorRate={}, P99={}ms, QPS={}, 采样数={}",
            ctx.runId,
            baseline.avgErrorRate,
            baseline.avgP99Millis,
            baseline.avgQps,
            baseline.sampleCount);

        ctx.report.phaseTimeline.put("STEADY_STATE_HYPOTHESIS", now());
    }

    /**
     * 阶段三：注入扰动
     *
     * 按照实验定义注入扰动，并验证扰动确实已生效
     *
     * 幂等控制：
     * 通过 experimentLock 对同一 runId 的注入操作做幂等保护，
     * 重复调用不会产生叠加效果
     */
    private void phasePerturbationInjection(ExperimentRunContext ctx) {
        ctx.currentPhase = ChaosPhase.PERTURBATION_INJECTION;
        ChaosExperimentDefinition def = ctx.definition;
        logger.info("[Chaos:{}] [阶段三] 开始注入扰动: {}",
            ctx.runId, def.getPerturbationType().getName());

        // 幂等注入：同一 runId 只执行一次实际注入
        boolean injected = experimentLock.idempotentExecute(
            ctx.runId + ":inject",
            () -> {
                perturbationInjector.inject(
                    ctx.runId,
                    def.getTargetService(),
                    def.getPerturbationType(),
                    def.getPerturbationParams());
                return true;
            }
        );

        if (!injected) {
            throw new RuntimeException("扰动注入执行失败");
        }

        // 等待扰动生效
        sleepQuietly(3000);

        // 验证扰动已生效
        boolean effective = perturbationInjector.verifyPerturbation(
            ctx.runId, def.getTargetService());
        if (!effective) {
            logger.warn("[Chaos:{}] [阶段三] 扰动注入验证未通过, "
                + "可能需要更长时间生效", ctx.runId);
        } else {
            logger.info("[Chaos:{}] [阶段三] 扰动注入验证通过",
                ctx.runId);
        }

        ctx.perturbationInjected = true;

        ctx.report.phaseTimeline.put("PERTURBATION_INJECTION", now());
    }

    /**
     * 阶段四：观察偏差
     *
     * 在扰动持续期间持续观察系统指标，检测是否偏离稳态假设
     *
     * 算法：
     * 1. 按配置的间隔持续采集指标
     * 2. 将每个采样点与稳态假设进行对比
     * 3. 偏离稳态假设记录为 WARNING 级偏差
     * 4. 突破安全边界记录为 CRITICAL 级偏差
     * 5. 连续 N 个采样点出现 CRITICAL 偏差时触发自动中止标记
     * 6. 记录影响峰值用于报告
     */
    private void phaseDeviationObservation(ExperimentRunContext ctx) {
        ctx.currentPhase = ChaosPhase.DEVIATION_OBSERVATION;
        ChaosExperimentDefinition def = ctx.definition;
        logger.info("[Chaos:{}] [阶段四] 开始观察偏差, 持续 {}s",
            ctx.runId, def.getPerturbationDurationSeconds());

        AtomicInteger consecutiveCritical = new AtomicInteger(0);
        ObservationSample peakImpactSample = null;
        double peakErrorRate = 0;

        long observeEndTime = System.currentTimeMillis()
            + def.getPerturbationDurationSeconds() * 1000L;

        while (System.currentTimeMillis() < observeEndTime) {
            try {
                ObservationSample sample = metricsObserver.collectSample(
                    def.getTargetService());
                sample.timestamp = System.currentTimeMillis();
                ctx.observations.add(sample);

                // 记录峰值
                if (sample.errorRate > peakErrorRate) {
                    peakErrorRate = sample.errorRate;
                    peakImpactSample = sample;
                }

                // 检测稳态偏离（WARNING级）
                checkSteadyStateDeviation(ctx, sample, def);

                // 检测安全边界突破（CRITICAL级）
                boolean critical = false;
                StringBuilder criticalMsg = new StringBuilder();

                if (sample.errorRate > def.getSafetyBoundaryErrorRate()) {
                    critical = true;
                    criticalMsg.append(String.format(
                        "错误率=%.4f(安全边界%.4f) ",
                        sample.errorRate,
                        def.getSafetyBoundaryErrorRate()));
                }
                if (sample.p99Millis > def.getSafetyBoundaryP99Millis()) {
                    critical = true;
                    criticalMsg.append(String.format(
                        "P99=%.0fms(安全边界%.0fms) ",
                        sample.p99Millis,
                        def.getSafetyBoundaryP99Millis()));
                }
                if (def.getSafetyBoundaryMinQps() > 0
                        && sample.qps < def.getSafetyBoundaryMinQps()) {
                    critical = true;
                    criticalMsg.append(String.format(
                        "QPS=%.0f(安全下限%.0f) ",
                        sample.qps,
                        def.getSafetyBoundaryMinQps()));
                }

                if (critical) {
                    int count = consecutiveCritical.incrementAndGet();
                    logger.warn("[Chaos:{}] [阶段四] CRITICAL偏差 "
                        + "(连续第{}次): {}",
                        ctx.runId, count, criticalMsg);

                    DeviationRecord deviation = new DeviationRecord();
                    deviation.timestamp = sample.timestamp;
                    deviation.metric = criticalMsg.toString();
                    deviation.severity = "CRITICAL";
                    ctx.deviations.add(deviation);

                    if (count >= def.getConsecutiveDeviationThreshold()) {
                        logger.error("[Chaos:{}] [阶段四] 连续{}次突破"
                            + "安全边界, 标记自动中止",
                            ctx.runId,
                            def.getConsecutiveDeviationThreshold());
                        ctx.autoHalted = true;
                        ctx.haltReason = "连续"
                            + def.getConsecutiveDeviationThreshold()
                            + "次突破安全边界: " + criticalMsg;
                        break;
                    }
                } else {
                    consecutiveCritical.set(0);
                }

            } catch (Exception e) {
                logger.error("[Chaos:{}] [阶段四] 观察采集异常",
                    ctx.runId, e);
            }

            sleepQuietly(def.getObservationIntervalMillis());
        }

        ctx.deviationDetected = !ctx.deviations.isEmpty();

        if (peakImpactSample != null) {
            ctx.report.peakImpact = peakImpactSample;
        }

        logger.info("[Chaos:{}] [阶段四] 观察结束, 采样点={}, "
            + "偏差记录={}, 自动中止={}",
            ctx.runId, ctx.observations.size(),
            ctx.deviations.size(), ctx.autoHalted);

        ctx.report.phaseTimeline.put("DEVIATION_OBSERVATION", now());
    }

    /**
     * 检测稳态偏离（WARNING级）
     */
    private void checkSteadyStateDeviation(
            ExperimentRunContext ctx,
            ObservationSample sample,
            ChaosExperimentDefinition def) {

        // 错误率偏离
        if (sample.errorRate > def.getSteadyStateMaxErrorRate()) {
            DeviationRecord deviation = new DeviationRecord();
            deviation.timestamp = sample.timestamp;
            deviation.metric = "errorRate";
            deviation.actual = sample.errorRate;
            deviation.expected = def.getSteadyStateMaxErrorRate();
            deviation.deviationPercent =
                (sample.errorRate - def.getSteadyStateMaxErrorRate())
                / Math.max(def.getSteadyStateMaxErrorRate(), 0.0001) * 100;
            deviation.severity = "WARNING";
            ctx.deviations.add(deviation);
            ctx.deviationDetected = true;
        }

        // P99偏离
        if (sample.p99Millis > def.getSteadyStateMaxP99Millis()) {
            DeviationRecord deviation = new DeviationRecord();
            deviation.timestamp = sample.timestamp;
            deviation.metric = "p99Millis";
            deviation.actual = sample.p99Millis;
            deviation.expected = def.getSteadyStateMaxP99Millis();
            deviation.deviationPercent =
                (sample.p99Millis - def.getSteadyStateMaxP99Millis())
                / Math.max(def.getSteadyStateMaxP99Millis(), 1.0) * 100;
            deviation.severity = "WARNING";
            ctx.deviations.add(deviation);
            ctx.deviationDetected = true;
        }

        // QPS下降
        if (ctx.baseline != null && ctx.baseline.avgQps > 0
                && def.getSteadyStateMaxQpsDropPercent() > 0) {
            double dropPercent = (ctx.baseline.avgQps - sample.qps)
                / ctx.baseline.avgQps * 100;
            if (dropPercent > def.getSteadyStateMaxQpsDropPercent()) {
                DeviationRecord deviation = new DeviationRecord();
                deviation.timestamp = sample.timestamp;
                deviation.metric = "qpsDrop";
                deviation.actual = dropPercent;
                deviation.expected = def.getSteadyStateMaxQpsDropPercent();
                deviation.deviationPercent = dropPercent;
                deviation.severity = "WARNING";
                ctx.deviations.add(deviation);
                ctx.deviationDetected = true;
            }
        }
    }

    /**
     * 阶段五：自动中止与恢复
     *
     * 无论实验是正常结束还是被中止，都必须确保扰动被撤销
     *
     * 幂等控制：
     * 恢复操作通过 experimentLock 做幂等保护，
     * 同一 runId 的恢复操作无论调用多少次，
     * 最终效果都是 "扰动已撤销"
     */
    private void phaseAutoHalt(ExperimentRunContext ctx) {
        ctx.currentPhase = ChaosPhase.AUTO_HALT;
        logger.info("[Chaos:{}] [阶段五] 自动中止与恢复, "
            + "是否需要紧急中止={}", ctx.runId, ctx.autoHalted);

        if (!ctx.perturbationInjected) {
            logger.info("[Chaos:{}] [阶段五] 未注入扰动, 无需恢复",
                ctx.runId);
            ctx.recoveryConfirmed = true;
            ctx.report.phaseTimeline.put("AUTO_HALT", now());
            return;
        }

        // 幂等恢复扰动
        ctx.recoveryConfirmed = experimentLock.idempotentExecute(
            ctx.runId + ":recover",
            () -> {
                perturbationInjector.recover(
                    ctx.runId, ctx.definition.getTargetService());

                // 等待恢复生效
                sleepQuietly(3000);

                // 验证恢复
                boolean recovered = perturbationInjector.verifyRecovery(
                    ctx.runId, ctx.definition.getTargetService());

                if (!recovered) {
                    // 重试一次
                    logger.warn("[Chaos:{}] [阶段五] 恢复验证未通过, "
                        + "重试一次", ctx.runId);
                    perturbationInjector.recover(
                        ctx.runId, ctx.definition.getTargetService());
                    sleepQuietly(5000);
                    recovered = perturbationInjector.verifyRecovery(
                        ctx.runId, ctx.definition.getTargetService());
                }

                return recovered;
            }
        );

        if (!ctx.recoveryConfirmed) {
            logger.error("[Chaos:{}] [阶段五] 恢复验证未通过, "
                + "升级P0告警", ctx.runId);
            alertNotifier.sendP0Alert(ctx.runId,
                "混沌实验扰动恢复失败，需要人工介入");
        } else {
            logger.info("[Chaos:{}] [阶段五] 恢复验证通过",
                ctx.runId);
        }

        // 等待系统恢复到稳态后再验证一次
        if (ctx.recoveryConfirmed) {
            logger.info("[Chaos:{}] [阶段五] 等待系统恢复稳态 {}s",
                ctx.runId, ctx.definition.getRecoveryTimeoutSeconds());
            sleepQuietly(
                ctx.definition.getRecoveryTimeoutSeconds() * 1000L);

            ObservationSample postRecovery = metricsObserver.collectSample(
                ctx.definition.getTargetService());
            boolean backToSteady =
                postRecovery.errorRate
                    <= ctx.definition.getSteadyStateMaxErrorRate()
                && postRecovery.p99Millis
                    <= ctx.definition.getSteadyStateMaxP99Millis();

            if (!backToSteady) {
                logger.warn("[Chaos:{}] [阶段五] 系统未恢复到稳态: "
                    + "errorRate={}, P99={}ms",
                    ctx.runId, postRecovery.errorRate,
                    postRecovery.p99Millis);
            } else {
                logger.info("[Chaos:{}] [阶段五] 系统已恢复到稳态",
                    ctx.runId);
            }
        }

        ctx.report.phaseTimeline.put("AUTO_HALT", now());
    }

    /**
     * 阶段六：改进措施
     *
     * 根据观察到的偏差自动分析并生成改进建议，
     * 不同类型的偏差对应不同的改进方向
     *
     * 改进建议的生成规则：
     * 1. 错误率偏离 → 建议加强熔断/降级策略
     * 2. RT偏离 → 建议优化超时设置/增加缓存
     * 3. QPS下降 → 建议优化限流策略/扩容
     * 4. 安全边界突破 → 建议提升对应容错机制为P0优先级
     * 5. 恢复未通过 → 建议增强自愈能力
     */
    private void phaseImprovementActions(ExperimentRunContext ctx) {
        ctx.currentPhase = ChaosPhase.IMPROVEMENT_ACTIONS;
        logger.info("[Chaos:{}] [阶段六] 生成改进措施", ctx.runId);

        // 使用改进分析器自动生成建议
        ctx.improvements = improvementAnalyzer.analyze(
            ctx.definition, ctx.baseline, ctx.deviations,
            ctx.autoHalted, ctx.recoveryConfirmed);

        // 如果分析器未生成建议，根据偏差类型手动补充
        if (ctx.improvements.isEmpty() && ctx.deviationDetected) {
            // 检查是否存在错误率相关偏差
            boolean hasErrorRateDeviation = ctx.deviations.stream()
                .anyMatch(d -> "errorRate".equals(d.metric));
            if (hasErrorRateDeviation) {
                ImprovementAction action = new ImprovementAction();
                action.id = "IMP-" + UUID.randomUUID().toString()
                    .substring(0, 8);
                action.category = "熔断/降级";
                action.description = "系统在故障场景下错误率超出稳态假设，"
                    + "建议检查并加强下游依赖的熔断策略，"
                    + "确保降级逻辑能够正确兜底";
                action.priority = ctx.autoHalted ? "P0" : "P1";
                ctx.improvements.add(action);
            }

            // 检查是否存在RT相关偏差
            boolean hasRtDeviation = ctx.deviations.stream()
                .anyMatch(d -> "p99Millis".equals(d.metric));
            if (hasRtDeviation) {
                ImprovementAction action = new ImprovementAction();
                action.id = "IMP-" + UUID.randomUUID().toString()
                    .substring(0, 8);
                action.category = "超时优化";
                action.description = "P99响应时间在故障场景下显著增长，"
                    + "建议检查超时时间设置是否合理，"
                    + "是否存在慢请求阻塞线程池的风险";
                action.priority = ctx.autoHalted ? "P0" : "P1";
                ctx.improvements.add(action);
            }

            // 检查是否存在QPS下降偏差
            boolean hasQpsDeviation = ctx.deviations.stream()
                .anyMatch(d -> "qpsDrop".equals(d.metric));
            if (hasQpsDeviation) {
                ImprovementAction action = new ImprovementAction();
                action.id = "IMP-" + UUID.randomUUID().toString()
                    .substring(0, 8);
                action.category = "限流/容量";
                action.description = "QPS在故障场景下大幅下降，"
                    + "建议检查限流策略是否过于激进，"
                    + "或目标服务容量是否需要扩充";
                action.priority = "P1";
                ctx.improvements.add(action);
            }
        }

        // 如果恢复未通过，增加自愈能力改进建议
        if (!ctx.recoveryConfirmed) {
            ImprovementAction action = new ImprovementAction();
            action.id = "IMP-" + UUID.randomUUID().toString()
                .substring(0, 8);
            action.category = "自愈能力";
            action.description = "故障恢复验证未通过，"
                + "说明系统的自愈机制存在缺陷，"
                + "需要排查恢复链路是否存在单点或死锁";
            action.priority = "P0";
            ctx.improvements.add(action);
        }

        // 构建最终报告
        ChaosExperimentReport report = ctx.report;
        report.runId = ctx.runId;
        report.experimentId = ctx.experimentId;
        report.experimentName = ctx.definition.getExperimentName();
        report.startTime = ctx.startTimeMillis;
        report.endTime = ctx.endTimeMillis;
        report.durationMillis = ctx.endTimeMillis - ctx.startTimeMillis;
        report.baseline = ctx.baseline;
        report.totalObservations = ctx.observations.size();
        report.deviationCount = ctx.deviations.size();
        report.autoHalted = ctx.autoHalted;
        report.haltReason = ctx.haltReason;
        report.recoveryConfirmed = ctx.recoveryConfirmed;
        report.deviations = ctx.deviations;
        report.improvements = ctx.improvements;

        // 判定实验结论
        if (ctx.autoHalted) {
            report.verdict = "HALTED";
            report.conclusions.add(
                "实验因突破安全边界被自动中止，"
                + "系统对该扰动类型的抵抗能力不足");
        } else if (ctx.deviationDetected) {
            report.verdict = "FAILED";
            report.conclusions.add(
                "实验过程中检测到稳态偏离，"
                + "系统虽未突破安全边界但已偏离正常行为");
        } else {
            report.verdict = "PASSED";
            report.conclusions.add(
                "系统在扰动注入期间保持稳态，"
                + "对该扰动类型具备足够的抵抗能力");
        }

        if (!ctx.recoveryConfirmed) {
            report.conclusions.add(
                "警告：扰动恢复验证未通过，需要人工确认系统已恢复正常");
        }

        report.phaseTimeline.put("IMPROVEMENT_ACTIONS", now());

        logger.info("[Chaos:{}] [阶段六] 改进措施生成完成, "
            + "verdict={}, 改进项数={}, 结论数={}",
            ctx.runId, report.verdict,
            report.improvements.size(), report.conclusions.size());
    }

    /**
     * 计算标准差
     */
    private double calculateStdDev(double[] values, double mean) {
        if (values.length <= 1) return 0;
        double sumSquaredDiff = 0;
        for (double v : values) {
            sumSquaredDiff += (v - mean) * (v - mean);
        }
        return Math.sqrt(sumSquaredDiff / (values.length - 1));
    }

    private String generateRunId(String experimentId) {
        return experimentId + "-RUN-" + LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
            + "-" + UUID.randomUUID().toString().substring(0, 6);
    }

    private String now() {
        return LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
    }

    private void sleepQuietly(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    /**

    public interface PerturbationInjector {

    public interface MetricsObserver {

    /**
     * 幂等实验锁
     *
     * 保证同一操作键（operationKey）对应的操作只会被执行一次，
     * 后续调用直接返回首次执行的结果

    public interface IdempotentExperimentLock {

    }

    /**
     * 改进分析器接口

    public interface ImprovementAnalyzer {
        List<ImprovementAction> analyze(
            ChaosExperimentDefinition definition,
            SteadyStateBaseline baseline,
            List<DeviationRecord> deviations,
            boolean autoHalted,
            boolean recoveryConfirmed);
    }

    /**
     * 告警通知接口
     */
    public interface AlertNotifier {
        void sendP0Alert(String runId, String message);
    }
```
