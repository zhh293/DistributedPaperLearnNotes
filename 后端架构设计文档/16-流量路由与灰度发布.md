# 流量路由与灰度发布

## 一、问题背景

### 1.1 分布式系统的流量调度挑战

在大规模微服务架构中，随着系统规模不断增长，一个来自客户端的请求进入系统后，会经过多个服务节点形成调用链。流量路由决定了请求在服务之间如何流动，直接影响核心业务链路的正确性和稳定性。

流量路由面临的核心挑战包括：

- **容灾隔离**：当某个机房或可用区发生故障时，需要将流量快速切换到其他区域
- **灰度发布**：新版本上线时，需要先在小范围验证，逐步扩大影响面
- **多环境隔离**：线下测试环境中多个团队并行开发，需要隔离测试流量
- **业务隔离**：不同业务线的流量需要隔离运行，避免相互影响
- **路由规则复杂**：多种路由策略（SET、LiteSet、泳道、地理位置）需要协同工作

### 1.2 基本概念

**服务与服务组**：在微服务范畴中，服务可以理解为一个appkey所代表的资源实体。由于适用场景不同，多个服务的集合被划分为不同的"服务组"——在SET化场景下称为SET，在灰度场景下称为灰度链路（LiteSet），在线下测试场景下称为泳道。

**调用链**：客户端请求进入系统后形成的服务调用序列。调用链本质上是树状（更准确说是图状）结构。在调用链中，调用方是被调用方的上游，被调用方是调用方的下游。

**流量染色**：对流量打标记的方法。被染色的流量在整个调用链生命周期里会携带特殊标记，这个标记会影响每一跳的路由决策。

```java
/**
 * 流量上下文
 * 在整个调用链中传递的流量元数据
 */
public class TrafficContext {
    
    /** 链路追踪ID */
    private String traceId;
    
    /** SET标识 */
    private String cellId;
    
    /** LiteSet链路标识 */
    private String liteSetId;
    
    /** 泳道标识 */
    private String swimlaneId;
    
    /** 流量染色标识 */
    private Map<String, String> colorTags;
    
    /** 是否为压测流量 */
    private boolean stressTest;
    
    /** 来源应用 */
    private String sourceAppKey;
    
    /** 来源IP */
    private String sourceIp;
    
    /** 用户自定义上下文 */
    private Map<String, String> userContext;
}
```

## 二、整体架构设计

### 2.1 路由分类

RPC流量路由根据路由目标的定义不同，分为**逻辑路由**和**物理路由**两大类：

```
┌──────────────────────────────────────────────────────────┐
│                    流量路由体系                            │
├─────────────────────────┬────────────────────────────────┤
│       逻辑路由（标签路由）  │       物理路由（地理位置路由）    │
│  ┌─────────────────────┐│  ┌────────────────────────────┐│
│  │  SET路由             ││  │  同机房路由                  ││
│  │  - 隔离优先          ││  │  - 低延迟优先                ││
│  │  - 不支持fallback    ││  │  - 支持fallback             ││
│  │  - 适用线上线下       ││  │  - 强制/非强制模式           ││
│  ├─────────────────────┤│  ├────────────────────────────┤│
│  │  LiteSet路由         ││  │  同城路由                    ││
│  │  - 可用性优先         ││  │  - 容灾权衡                  ││
│  │  - 支持fallback      ││  │  - 跨城fallback             ││
│  │  - 流量染色          ││  │  - 强制/非强制模式           ││
│  ├─────────────────────┤│  └────────────────────────────┘│
│  │  泳道路由            ││                                │
│  │  - 测试隔离          ││                                │
│  │  - 仅线下环境         ││                                │
│  │  - 流量染色          ││                                │
│  └─────────────────────┘│                                │
└─────────────────────────┴────────────────────────────────┘
```

### 2.2 路由优先级

多种路由规则同时使用时，需要有明确的优先级控制。对于一次调用，客户端会先应用标签路由（逻辑路由），再应用地理位置路由（物理路由）：

```
RPC自定义分流 > SET/LiteSet路由 > 泳道路由 > 同机房路由 > 同地域路由
    (最高优先级)                                        (最低优先级)
```

```java
/**
 * 路由优先级链
 * 按优先级依次应用路由规则，逐步缩小候选节点范围
 */
public class RoutingPipeline {
    
    private final List<RouterStage> stages;
    
    public RoutingPipeline() {
        this.stages = new ArrayList<>();
        // 按优先级注册路由阶段
        stages.add(new CustomRpcRouter());      // 1. 用户自定义RPC分流
        stages.add(new SetLiteSetRouter());     // 2. SET/LiteSet路由
        stages.add(new SwimlaneRouter());       // 3. 泳道路由
        stages.add(new SameIdcRouter());        // 4. 同机房路由
        stages.add(new SameRegionRouter());     // 5. 同地域路由
    }
    
    /**
     * 执行路由决策
     * @param candidates 所有候选服务节点
     * @param context 流量上下文
     * @return 经过路由筛选后的目标节点列表
     */
    public List<ServiceNode> route(List<ServiceNode> candidates, TrafficContext context) {
        List<ServiceNode> result = candidates;
        
        for (RouterStage stage : stages) {
            if (stage.isApplicable(context)) {
                List<ServiceNode> filtered = stage.filter(result, context);
                if (!filtered.isEmpty()) {
                    result = filtered;
                } else if (stage.supportsFallback()) {
                    // 当前阶段无可用节点，尝试fallback
                    result = stage.fallback(result, context);
                }
                // 如果不支持fallback且过滤结果为空，保持上一步结果
            }
        }
        
        return result;
    }
}
```

## 三、核心链路设计

### 3.1 SET化路由

SET是软件系统架构里的概念，将一个大的系统集群从逻辑上划分为多个小集群（单元），每个SET承担一部分流量。SET是一个封闭的业务闭环，除了业务应用外，SET还包括消息队列、数据库等所有基础组件。流量进入SET后可以完成所有业务逻辑，无需调用SET外的服务。

```java
/**
 * SET路由器
 * 核心原则：隔离优先，不支持fallback
 */
public class SetRouter implements RouterStage {
    
    /**
     * SET路由规则：
     * 1. 如果下游开启了SET开关：
     *    a. 有用户自定义路由规则则应用自定义规则
     *    b. 否则调用同SET节点
     * 2. 如果下游没有开启SET开关，调用中心SET的节点
     * 3. 不支持fallback：选定的节点不可用则调用失败
     * 
     * 重要：以SET开关为准，而不是以实际部署情况为准
     */
    @Override
    public List<ServiceNode> filter(List<ServiceNode> candidates, TrafficContext context) {
        String currentCell = context.getCellId();
        if (currentCell == null) {
            // 当前不在任何SET中，返回中心SET节点
            return filterByCenterSet(candidates);
        }
        
        // 检查下游服务是否开启SET开关
        String targetAppKey = context.getTargetAppKey();
        boolean setEnabled = isSetEnabled(targetAppKey);
        
        if (!setEnabled) {
            // 下游未开SET开关，强制路由到中心
            return filterByCenterSet(candidates);
        }
        
        // 检查是否有自定义路由规则
        CustomSetRule customRule = getCustomSetRule(targetAppKey, currentCell);
        if (customRule != null) {
            return customRule.apply(candidates, context);
        }
        
        // 默认路由到同SET节点
        return candidates.stream()
            .filter(node -> currentCell.equals(node.getCell()))
            .collect(Collectors.toList());
    }
    
    @Override
    public boolean supportsFallback() {
        // SET路由不支持fallback，保证隔离性
        return false;
    }
    
    /**
     * SET化特点：
     * - 中心SET包含所有服务
     * - 打开SET开关的服务需要部署在所有SET里
     * - 未打开SET开关的服务只部署于中心SET
     * - 每个SET单独保留自己的数据，SET之间数据隔离
     * - 不共享DB、MQ等基础组件
     */
    private List<ServiceNode> filterByCenterSet(List<ServiceNode> candidates) {
        return candidates.stream()
            .filter(node -> "center".equals(node.getCell()) || node.getCell() == null)
            .collect(Collectors.toList());
    }
}
```

### 3.2 LiteSet路由（灰度链路）

LiteSet是基于SET底层能力构建的、生产环境下的链路粒度流量隔离方案。与SET不同，LiteSet基于流量中的标记识别并进行流量路由，标记在整个链路透传，使流量具备"回流"的能力。LiteSet只隔离服务层流量，不隔离数据库、缓存等。

```java
/**
 * LiteSet路由器
 * 核心原则：可用性优先，支持fallback
 */
public class LiteSetRouter implements RouterStage {
    
    /**
     * LiteSet路由规则：
     * 1. 优先选择与当前流量标记相同的LiteSet内的服务
     *    a. 下游服务可用 → 直接调用
     *    b. 下游服务不可用（不存在或故障）：
     *       - 非中心LiteSet → fallback到中心
     *       - 中心LiteSet → 调用失败
     * 2. 流量标记一旦被设置，下游所有调用都携带此标记
     * 3. 用户可以在调用链的任意节点修改流量标记
     */
    @Override
    public List<ServiceNode> filter(List<ServiceNode> candidates, TrafficContext context) {
        String liteSetId = context.getLiteSetId();
        if (liteSetId == null || liteSetId.isEmpty()) {
            // 未染色的流量进入中心LiteSet
            return filterByCenterLiteSet(candidates);
        }
        
        // 查找与流量标记匹配的LiteSet节点
        List<ServiceNode> matchedNodes = candidates.stream()
            .filter(node -> liteSetId.equals(node.getLiteSetCell()))
            .filter(node -> node.getStatus() == NodeStatus.ALIVE)
            .collect(Collectors.toList());
        
        if (!matchedNodes.isEmpty()) {
            return matchedNodes;
        }
        
        // 匹配的LiteSet无可用节点，执行fallback
        return fallback(candidates, context);
    }
    
    @Override
    public List<ServiceNode> fallback(List<ServiceNode> candidates, TrafficContext context) {
        // 非中心LiteSet可以fallback到中心
        String liteSetId = context.getLiteSetId();
        if (!"center".equals(liteSetId)) {
            return filterByCenterLiteSet(candidates);
        }
        // 中心LiteSet不能再fallback
        return Collections.emptyList();
    }
    
    @Override
    public boolean supportsFallback() {
        return true;
    }
    
    private List<ServiceNode> filterByCenterLiteSet(List<ServiceNode> candidates) {
        return candidates.stream()
            .filter(node -> node.getLiteSetCell() == null 
                    || "center".equals(node.getLiteSetCell()))
            .filter(node -> node.getStatus() == NodeStatus.ALIVE)
            .collect(Collectors.toList());
    }
}
```

### 3.3 泳道路由

泳道的定位是线下测试时隔离测试人员之间的相互干扰，提升测试效率。泳道不在线上生产环境使用。

```java
/**
 * 泳道路由器
 * 核心原则：测试隔离，仅用于线下环境
 */
public class SwimlaneRouter implements RouterStage {
    
    /**
     * 泳道路由规则与LiteSet类似，但有一个关键区别：
     * - LiteSet：下游不存在或故障时都会fallback到中心
     * - 泳道：只有下游不存在时才fallback到中心，故障时直接调用失败
     * 
     * 这样设计的原因：泳道用于测试环境，故障时应该暴露问题而非隐藏
     */
    @Override
    public List<ServiceNode> filter(List<ServiceNode> candidates, TrafficContext context) {
        String swimlaneId = context.getSwimlaneId();
        if (swimlaneId == null || swimlaneId.isEmpty()) {
            return filterByCenterSwimlane(candidates);
        }
        
        // 查找泳道内的节点（包括不健康的）
        List<ServiceNode> laneNodes = candidates.stream()
            .filter(node -> swimlaneId.equals(node.getSwimlane()))
            .collect(Collectors.toList());
        
        if (laneNodes.isEmpty()) {
            // 泳道内没有部署该服务，fallback到中心泳道
            return filterByCenterSwimlane(candidates);
        }
        
        // 泳道内有节点但可能不健康
        List<ServiceNode> healthyNodes = laneNodes.stream()
            .filter(node -> node.getStatus() == NodeStatus.ALIVE)
            .collect(Collectors.toList());
        
        if (healthyNodes.isEmpty()) {
            // 节点存在但不健康，不fallback，直接返回空（调用失败）
            return Collections.emptyList();
        }
        
        return healthyNodes;
    }
    
    /**
     * 泳道特点：
     * - 中心泳道包含所有服务
     * - 各泳道共享数据（共用DB、MQ等基础组件）
     * - 仅用于线下测试环境
     */
    private List<ServiceNode> filterByCenterSwimlane(List<ServiceNode> candidates) {
        return candidates.stream()
            .filter(node -> node.getSwimlane() == null 
                    || "center".equals(node.getSwimlane()))
            .collect(Collectors.toList());
    }
}
```

### 3.4 地理位置路由

地理位置路由考虑的是性能和容灾，是物理现实的反映：

```java
/**
 * 地理位置路由器
 * 支持同机房优先和同城优先两种策略
 */
public class GeoLocationRouter implements RouterStage {
    
    /**
     * 地理位置路由详细规则
     * ┌──────────┬────────────────┬──────────────┬───────────────┬──────────────┐
     * │          │ 非强制-范围可用 │ 非强制-不可用 │ 强制-范围可用  │ 强制-不可用   │
     * ├──────────┼────────────────┼──────────────┼───────────────┼──────────────┤
     * │同机房优先 │ 同机房调用      │ 同城跨机房    │ 同机房调用     │ 调用失败      │
     * │同城优先  │ 同城调用        │ 跨城调用      │ 同城调用       │ 调用失败      │
     * │未配置   │ 全局调用        │ -            │ -             │ -            │
     * └──────────┴────────────────┴──────────────┴───────────────┴──────────────┘
     */
    @Override
    public List<ServiceNode> filter(List<ServiceNode> candidates, TrafficContext context) {
        GeoPolicy policy = context.getGeoPolicy();
        if (policy == null) {
            return candidates; // 未配置，全局调用
        }
        
        String currentIdc = context.getCurrentIdc();
        String currentRegion = context.getCurrentRegion();
        
        switch (policy.getLevel()) {
            case SAME_IDC:
                return routeWithIdcPreference(candidates, currentIdc, currentRegion, 
                                              policy.isForced());
            case SAME_REGION:
                return routeWithRegionPreference(candidates, currentRegion, 
                                                 policy.isForced());
            default:
                return candidates;
        }
    }
    
    private List<ServiceNode> routeWithIdcPreference(List<ServiceNode> candidates, 
            String currentIdc, String currentRegion, boolean forced) {
        // 1. 先尝试同机房
        List<ServiceNode> sameIdc = candidates.stream()
            .filter(node -> currentIdc.equals(node.getIdc()))
            .collect(Collectors.toList());
        
        if (!sameIdc.isEmpty()) {
            return sameIdc;
        }
        
        if (forced) {
            return Collections.emptyList(); // 强制模式下，同机房无节点则失败
        }
        
        // 2. 非强制模式，fallback到同城
        List<ServiceNode> sameRegion = candidates.stream()
            .filter(node -> currentRegion.equals(node.getRegion()))
            .collect(Collectors.toList());
        
        return sameRegion.isEmpty() ? candidates : sameRegion;
    }
}
```

### 3.5 全链路灰度发布

全链路灰度是一种端到端的灰度发布方案，不需要关心链路上经过哪些服务，仅需要少量的路由规则即可构建出从网关到整个后端服务的流量隔离环境。

```java
/**
 * 全链路灰度管理器
 * 管理灰度发布的全生命周期
 */
public class FullChainGrayManager {
    
    /**
     * 创建灰度链路
     * @param grayName 灰度链路名称
     * @param services 需要参与灰度的服务列表
     * @param trafficRule 灰度流量分流规则
     */
    public GrayChain createGrayChain(String grayName, List<String> services, 
                                      TrafficRule trafficRule) {
        GrayChain chain = new GrayChain();
        chain.setName(grayName);
        chain.setStatus(GrayChainStatus.CREATED);
        
        // 1. 为每个服务创建灰度分组
        for (String serviceAppKey : services) {
            GrayGroup group = new GrayGroup();
            group.setAppKey(serviceAppKey);
            group.setCellLabel(grayName); // LiteSet标签
            group.setStatus(GroupStatus.PENDING);
            chain.addGroup(group);
        }
        
        // 2. 设置流量分流规则
        chain.setTrafficRule(trafficRule);
        
        return chain;
    }
    
    /**
     * 激活灰度链路
     * 将灰度流量规则下发到全链路
     */
    public void activateGrayChain(GrayChain chain) {
        // 1. 在网关层配置流量分流入口
        configureGatewayTrafficSplit(chain);
        
        // 2. 在RPC框架层配置LiteSet路由
        configureRpcRouting(chain);
        
        // 3. 在消息队列层配置消息路由
        configureMessageRouting(chain);
        
        chain.setStatus(GrayChainStatus.ACTIVE);
    }
    
    /**
     * 调整灰度流量比例
     * 逐步增加灰度流量，观察系统表现
     */
    public void adjustTrafficRatio(GrayChain chain, int newPercentage) {
        if (newPercentage < 0 || newPercentage > 100) {
            throw new IllegalArgumentException("Traffic percentage must be 0-100");
        }
        
        TrafficRule rule = chain.getTrafficRule();
        int oldPercentage = rule.getPercentage();
        
        // 记录变更日志
        logTrafficChange(chain.getName(), oldPercentage, newPercentage);
        
        // 更新分流规则
        rule.setPercentage(newPercentage);
        
        // 下发到网关
        updateGatewayTrafficRule(chain);
    }
}

/**
 * 流量分流规则
 */
public class TrafficRule {
    
    /** 分流方式 */
    private SplitMode splitMode;
    
    /** 分流比例（百分比） */
    private int percentage;
    
    /** 分流条件（按条件分流时使用） */
    private List<SplitCondition> conditions;
    
    /**
     * 分流方式枚举
     */
    public enum SplitMode {
        /** 按比例随机分流 */
        RATIO,
        /** 按条件分流（如指定用户ID、IP段等） */
        CONDITION,
        /** 按比例+条件组合分流 */
        RATIO_WITH_CONDITION,
        /** 直接指定（所有流量都进入灰度） */
        DIRECT
    }
    
    /**
     * 判断请求是否命中灰度
     */
    public boolean matchGray(TrafficContext context) {
        switch (splitMode) {
            case RATIO:
                // 基于TraceId的hash保证同一请求链路一致性
                int hash = Math.abs(context.getTraceId().hashCode() % 100);
                return hash < percentage;
            case CONDITION:
                return conditions.stream().allMatch(c -> c.evaluate(context));
            case RATIO_WITH_CONDITION:
                boolean conditionMatch = conditions.stream()
                    .allMatch(c -> c.evaluate(context));
                if (!conditionMatch) return false;
                int h = Math.abs(context.getTraceId().hashCode() % 100);
                return h < percentage;
            case DIRECT:
                return true;
            default:
                return false;
        }
    }
}
```

### 3.6 流量染色与透传

流量染色是全链路灰度的核心基础，确保灰度标记能在整个调用链中透传：

```java
/**
 * 流量染色管理器
 * 负责在全链路中传递染色标识
 */
public class TrafficColorManager {
    
    /** 染色标识的ThreadLocal存储 */
    private static final ThreadLocal<Map<String, String>> COLOR_TAGS = 
        ThreadLocal.withInitial(HashMap::new);
    
    /**
     * 设置染色标识
     * 在流量入口处（网关或分流点）调用
     */
    public static void setColorTag(String key, String value) {
        COLOR_TAGS.get().put(key, value);
    }
    
    /**
     * 获取染色标识
     */
    public static String getColorTag(String key) {
        return COLOR_TAGS.get().get(key);
    }
    
    /**
     * 获取所有染色标识
     */
    public static Map<String, String> getAllColorTags() {
        return Collections.unmodifiableMap(COLOR_TAGS.get());
    }
    
    /**
     * 清除染色标识
     * 在请求结束时必须调用，防止线程复用导致标识污染
     */
    public static void clearColorTags() {
        COLOR_TAGS.remove();
    }
    
    /**
     * 跨线程传递染色标识
     * 使用装饰器模式包装Runnable/Callable
     */
    public static Runnable wrap(Runnable task) {
        Map<String, String> parentTags = new HashMap<>(COLOR_TAGS.get());
        return () -> {
            Map<String, String> backup = COLOR_TAGS.get();
            COLOR_TAGS.set(parentTags);
            try {
                task.run();
            } finally {
                COLOR_TAGS.set(backup);
            }
        };
    }
    
    public static <T> Callable<T> wrap(Callable<T> task) {
        Map<String, String> parentTags = new HashMap<>(COLOR_TAGS.get());
        return () -> {
            Map<String, String> backup = COLOR_TAGS.get();
            COLOR_TAGS.set(parentTags);
            try {
                return task.call();
            } finally {
                COLOR_TAGS.set(backup);
            }
        };
    }
}
```

## 六、最佳实践

### 6.1 灰度发布流程

1. **创建灰度链路**：在流量调度平台上创建LiteSet链路
2. **部署灰度服务**：将新版本服务部署到灰度链路对应的节点
3. **配置分流规则**：按条件或比例将少量流量引入灰度链路
4. **观察验证**：通过监控和日志验证灰度链路的业务正确性
5. **逐步放量**：确认无误后，逐步增加灰度流量比例
6. **全量发布**：灰度验证通过后，将新版本推广到中心链路
7. **清理链路**：发布完成后回收灰度链路资源

### 6.2 SET化注意事项

1. SET路由以SET开关为准，而非以实际部署情况为准
2. 未打开SET开关的服务，即使在SET内有部署，也不会被SET路由命中
3. SET化需要同时隔离DB、MQ等基础组件，改造成本较高
4. 推荐使用LiteSet替代纯SET化方案，降低改造成本

### 6.3 流量调度安全

1. 灰度链路的fallback开关需要谨慎配置，避免灰度流量回流污染主干
2. SET映射关系数据需要定期清理，防止共享内存撑爆
3. 动态策略变更需要支持灰度发布和回滚
4. 全链路问题排查工具是必备能力，确保流量路由可追溯

## 七、全链路实战案例

前面几章从路由分类、SET化路由、LiteSet灰度链路到一致性巡检，系统梳理了流量路由与灰度发布的核心设计。本章通过三个贯穿全链路的实战案例，展示一次调用请求如何在多种路由规则的共同作用下完成路由决策，以及一次完整的灰度发布如何从创建链路到全量上线。

### 7.1 案例一：多路由规则协同决策全链路

#### 7.1.1 场景描述

某跨机房部署的交易系统在一次RPC调用中，需要依次应用自定义分流、SET/LiteSet路由、泳道路由、同机房路由、同地域路由这五级路由规则，最终从数千个候选节点中筛选出目标节点，要求：

- 严格按照优先级链路依次应用规则，前一级筛选结果作为后一级的输入；
- 不支持fallback的路由阶段（如SET路由）筛选结果为空时不允许回退，直接判定失败；
- 支持fallback的路由阶段筛选结果为空时自动回退到上一步结果，保证可用性；
- 记录每一级路由决策依据，便于故障排查时还原路由路径。

```
多路由规则协同决策全链路：

  全部候选节点(数千个)
       │
       ▼
  ① 自定义RPC分流规则匹配 ── 命中 ──▶ 缩小候选集
       │ 未配置规则，跳过
       ▼
  ② SET/LiteSet路由匹配
       ├── SET开启且命中 ──▶ 缩小候选集（不支持fallback）
       ├── SET开启但未命中 ──▶ 直接失败
       └── SET未开启 ──▶ 进入LiteSet灰度判断，未命中则fallback继续
       │
       ▼
  ③ 泳道路由匹配（仅线下环境生效）── 未命中 ──▶ 保持上一步结果
       │
       ▼
  ④ 同机房路由匹配 ── 未命中 ──▶ fallback到同地域候选节点
       │
       ▼
  ⑤ 同地域路由匹配 ── 得到最终候选节点集合
       │
       ▼
  从最终候选集合中执行负载均衡，选出目标节点
```

#### 7.1.2 完整实现代码

```java
import java.util.ArrayList;
import java.util.List;
import java.util.stream.Collectors;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

/**
 * 多路由规则协同决策全链路处理器
 *
 * 按照"自定义分流 > SET/LiteSet路由 > 泳道路由 > 同机房路由 > 同地域路由"
 * 的优先级依次应用路由规则，逐级收窄候选节点范围，并记录每一步的决策依据。
 */
public class MultiRouteDecisionFullChainProcessor {

    private static final Logger logger = LoggerFactory.getLogger(
        MultiRouteDecisionFullChainProcessor.class);

    private final CustomRpcRouter customRpcRouter;
    private final SetLiteSetRouter setLiteSetRouter;
    private final SwimlaneRouter swimlaneRouter;
    private final SameIdcRouter sameIdcRouter;
    private final SameRegionRouter sameRegionRouter;
    private final LoadBalancer loadBalancer;
    private final MetricsCollector metricsCollector;

    public MultiRouteDecisionFullChainProcessor(
            CustomRpcRouter customRpcRouter,
            SetLiteSetRouter setLiteSetRouter,
            SwimlaneRouter swimlaneRouter,
            SameIdcRouter sameIdcRouter,
            SameRegionRouter sameRegionRouter,
            LoadBalancer loadBalancer,
            MetricsCollector metricsCollector) {
        this.customRpcRouter = customRpcRouter;
        this.setLiteSetRouter = setLiteSetRouter;
        this.swimlaneRouter = swimlaneRouter;
        this.sameIdcRouter = sameIdcRouter;
        this.sameRegionRouter = sameRegionRouter;
        this.loadBalancer = loadBalancer;
        this.metricsCollector = metricsCollector;
    }

    /**
     * 全链路路由决策入口
     *
     * @param allCandidates 服务发现返回的全部候选节点
     * @param context 本次调用的流量上下文
     * @return 最终选定的目标节点
     */
    public ServiceNode decide(List<ServiceNode> allCandidates, TrafficContext context) {
        String traceId = context.getTraceId();
        List<RouteDecisionLog> decisionLogs = new ArrayList<>();
        List<ServiceNode> candidates = allCandidates;

        logger.info("[TraceId={}] 开始路由决策, 初始候选节点数={}",
            traceId, candidates.size());

        // ========== 第①级：自定义RPC分流 ==========
        candidates = applyStage("CustomRpcRouter", customRpcRouter,
            candidates, context, traceId, decisionLogs, false);

        // ========== 第②级：SET/LiteSet路由（SET部分不支持fallback） ==========
        candidates = applyStage("SetLiteSetRouter", setLiteSetRouter,
            candidates, context, traceId, decisionLogs, false);

        // ========== 第③级：泳道路由（支持fallback） ==========
        candidates = applyStage("SwimlaneRouter", swimlaneRouter,
            candidates, context, traceId, decisionLogs, true);

        // ========== 第④级：同机房路由（支持fallback） ==========
        candidates = applyStage("SameIdcRouter", sameIdcRouter,
            candidates, context, traceId, decisionLogs, true);

        // ========== 第⑤级：同地域路由（支持fallback） ==========
        candidates = applyStage("SameRegionRouter", sameRegionRouter,
            candidates, context, traceId, decisionLogs, true);

        if (candidates.isEmpty()) {
            logger.error("[TraceId={}] 全链路路由决策后无可用节点, " 
                + "决策路径={}", traceId, decisionLogs);
            metricsCollector.recordRouteFailure(context.getSourceAppKey());
            throw new NoAvailableInstanceException("路由决策后无可用节点");
        }

        ServiceNode selected = loadBalancer.select(candidates);
        logger.info("[TraceId={}] 路由决策完成, 最终选定节点={}:{}, " 
            + "决策路径={}", traceId, selected.getHost(), selected.getPort(),
            decisionLogs);
        return selected;
    }

    /**
     * 应用单个路由阶段，记录决策日志，处理fallback逻辑
     */
    private List<ServiceNode> applyStage(
            String stageName, RouterStage stage, List<ServiceNode> candidates,
            TrafficContext context, String traceId,
            List<RouteDecisionLog> decisionLogs, boolean allowFallback) {

        if (!stage.isApplicable(context)) {
            decisionLogs.add(new RouteDecisionLog(stageName, "SKIPPED", candidates.size()));
            return candidates;
        }

        List<ServiceNode> filtered = stage.filter(candidates, context);
        if (!filtered.isEmpty()) {
            decisionLogs.add(new RouteDecisionLog(stageName, "HIT", filtered.size()));
            logger.info("[TraceId={}] 路由阶段[{}]命中, 剩余候选数={}",
                traceId, stageName, filtered.size());
            return filtered;
        }

        if (allowFallback) {
            decisionLogs.add(new RouteDecisionLog(stageName, "FALLBACK", candidates.size()));
            logger.warn("[TraceId={}] 路由阶段[{}]未命中, fallback保留上一步" 
                + "结果, 候选数={}", traceId, stageName, candidates.size());
            return candidates;
        }

        decisionLogs.add(new RouteDecisionLog(stageName, "MISS_NO_FALLBACK", 0));
        logger.error("[TraceId={}] 路由阶段[{}]未命中且不支持fallback",
            traceId, stageName);
        return new ArrayList<>();
    }

    /** 路由决策日志，记录每一级路由阶段的处理结果 */
    private static class RouteDecisionLog {
        final String stageName;
        final String result;
        final int remainingCount;

        RouteDecisionLog(String stageName, String result, int remainingCount) {
            this.stageName = stageName;
            this.result = result;
            this.remainingCount = remainingCount;
        }

        @Override
        public String toString() {
            return stageName + "=" + result + "(" + remainingCount + ")";
        }
    }
}
```

### 7.2 案例二：灰度发布全生命周期链路

#### 7.2.1 场景描述

- 创建灰度链路后先按固定用户白名单验证功能正确性；

```
       ▼
  ③ 按比例放量：10% ──▶ 观察指标 ──▶ 异常则暂停/回滚
```

```java
 *
 * 负责驱动一次灰度发布从白名单验证、逐步放量到全量发布、
 * 资源回收的完整流程，并在每个放量阶段进行指标对比校验。
 */
public class GrayReleaseLifecycleManager {

    private static final Logger logger = LoggerFactory.getLogger(
        GrayReleaseLifecycleManager.class);

    /** 放量比例阶梯 */
    private static final int[] ROLLOUT_STAGES = {1, 10, 50, 100};

    /** 每个阶段观察时长（毫秒），生产环境通常是分钟到小时级别 */
    private static final long OBSERVE_DURATION_MS = 5 * 60 * 1000L;

    private final LiteSetLinkManager liteSetLinkManager;
    private final MetricsComparator metricsComparator;
    private final AlertNotifier alertNotifier;

    private final AtomicReference<ReleaseState> state =
        new AtomicReference<>(ReleaseState.CREATED);

    public GrayReleaseLifecycleManager(
            LiteSetLinkManager liteSetLinkManager,
            MetricsComparator metricsComparator,
            AlertNotifier alertNotifier) {
        this.liteSetLinkManager = liteSetLinkManager;
        this.metricsComparator = metricsComparator;
        this.alertNotifier = alertNotifier;
    }

    /**
     * 执行完整的灰度发布流程
     *
     * @param liteSetId 灰度链路标识
     * @param whitelistUsers 用于功能验证的白名单用户集合
     * @return 发布是否最终成功
     */
    public boolean executeFullRelease(String liteSetId, Set<String> whitelistUsers) {
        logger.info("[LiteSetId={}] 开始灰度发布全流程", liteSetId);

        try {
            // ========== 第①步：白名单验证 ==========
            state.set(ReleaseState.WHITELIST_VALIDATING);
            liteSetLinkManager.routeWhitelistUsers(liteSetId, whitelistUsers);
            boolean whitelistOk = observeAndValidate(liteSetId, 0);
            if (!whitelistOk) {
                logger.error("[LiteSetId={}] 白名单验证失败, 终止发布并回滚",
                    liteSetId);
                rollback(liteSetId);
                return false;
            }
            logger.info("[LiteSetId={}] 白名单验证通过", liteSetId);

            // ========== 第②③④⑤步：按比例逐步放量 ==========
            for (int percentage : ROLLOUT_STAGES) {
                state.set(ReleaseState.ROLLING_OUT);
                liteSetLinkManager.setTrafficPercentage(liteSetId, percentage);
                logger.info("[LiteSetId={}] 放量至{}%, 开始观察",
                    liteSetId, percentage);

                boolean stageOk = observeAndValidate(liteSetId, percentage);
                if (!stageOk) {
                    logger.error("[LiteSetId={}] 放量至{}%阶段指标异常, " 
                        + "暂停放量并回滚", liteSetId, percentage);
                    alertNotifier.notify(String.format(
                        "灰度发布在%d%%阶段被自动回滚: liteSetId=%s",
                        percentage, liteSetId));
                    rollback(liteSetId);
                    return false;
                }
                logger.info("[LiteSetId={}] {}%放量阶段验证通过",
                    liteSetId, percentage);
            }

            // ========== 第⑥步：全量发布后回收灰度链路 ==========
            state.set(ReleaseState.COMPLETED);
            liteSetLinkManager.promoteToCenterLink(liteSetId);
            liteSetLinkManager.recycleLiteSetLink(liteSetId);
            logger.info("[LiteSetId={}] 全量发布完成, 灰度链路资源已回收",
                liteSetId);
            return true;

        } catch (Exception e) {
            logger.error("[LiteSetId={}] 灰度发布流程异常: {}",
                liteSetId, e.getMessage(), e);
            rollback(liteSetId);
            return false;
        }
    }

    /**
     * 观察当前阶段的核心指标（成功率、延迟、错误率），
     * 与主干链路进行对比，判断本阶段是否可以继续放量
     */
    private boolean observeAndValidate(String liteSetId, int percentage) {
        try {
            Thread.sleep(Math.min(OBSERVE_DURATION_MS, 200L)); // 示例中缩短观察时长
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        MetricsComparisonResult result = metricsComparator.compare(
            liteSetId, percentage);
        if (!result.isHealthy()) {
            logger.warn("[LiteSetId={}] 指标对比异常: successRateDiff={}, " 
                + "latencyDiff={}, errorRateDiff={}",
                liteSetId, result.getSuccessRateDiff(),
                result.getLatencyDiff(), result.getErrorRateDiff());
        }
        return result.isHealthy();
    }

    private void rollback(String liteSetId) {
        state.set(ReleaseState.ROLLED_BACK);
        liteSetLinkManager.setTrafficPercentage(liteSetId, 0);
        liteSetLinkManager.recycleLiteSetLink(liteSetId);
        logger.info("[LiteSetId={}] 已回滚，流量切回主干链路", liteSetId);
    }

    private enum ReleaseState {
        CREATED, WHITELIST_VALIDATING, ROLLING_OUT, COMPLETED, ROLLED_BACK
    }
}
```

### 7.3 案例三：多机房容灾切流全链路

#### 7.3.1 场景描述

某系统部署在多个可用区，当监测到某机房故障时，需要自动将该机房流量切换到其他健康机房，要求：

- 通过健康检查持续监测各机房的服务健康度；
- 检测到机房级别故障时自动触发切流，将流量路由到健康机房；
- 切流决策需要防止误判导致的抖动（连续多次探测失败才判定故障）；
- 故障恢复后按策略决定是否自动切回或需要人工确认。

```
多机房容灾切流全链路：

  健康检查探针持续探测各机房
       │
       ▼
  ① 单次探测失败 ── 未达到连续失败阈值 ──▶ 继续观察，不触发切流
       │ 达到连续失败阈值（如连续5次）
       ▼
  ② 判定机房故障，触发切流决策
       │
       ▼
  ③ 更新路由表：故障机房权重置0，流量路由到健康机房
       │
       ▼
  ④ 发送告警通知 + 记录切流事件
       │
       ▼
  ⑤ 持续探测故障机房恢复情况
       │
       ├── 连续多次探测成功 ──▶ 按策略自动切回或等待人工确认
       │
       └── 仍然异常 ──▶ 保持切流状态，继续观察
```

#### 7.3.2 完整实现代码

```java
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

/**
 * 多机房容灾切流全链路处理器
 *
 * 持续监测各机房健康度，在连续多次探测失败后判定机房故障并自动切流，
 * 故障恢复后根据配置决定是否自动切回，避免探测抖动导致的误切流。
 */
public class MultiIdcFailoverFullChainProcessor {

    private static final Logger logger = LoggerFactory.getLogger(
        MultiIdcFailoverFullChainProcessor.class);

    /** 连续失败达到该阈值才判定机房故障，避免抖动 */
    private static final int FAILURE_THRESHOLD = 5;

    /** 连续成功达到该阈值才认为机房恢复 */
    private static final int RECOVERY_THRESHOLD = 10;

    /** 机房ID -> 连续失败计数 */
    private final Map<String, AtomicInteger> failureCounters = new ConcurrentHashMap<>();

    /** 机房ID -> 连续成功计数（用于故障恢复判断） */
    private final Map<String, AtomicInteger> recoveryCounters = new ConcurrentHashMap<>();

    /** 当前处于切流状态的机房集合 */
    private final Map<String, Boolean> failoverState = new ConcurrentHashMap<>();

    private final RouteTableUpdater routeTableUpdater;
    private final AlertNotifier alertNotifier;

    /** 是否允许故障恢复后自动切回，false则需要人工确认 */
    private final boolean autoFailback;

    public MultiIdcFailoverFullChainProcessor(
            RouteTableUpdater routeTableUpdater,
            AlertNotifier alertNotifier,
            boolean autoFailback) {
        this.routeTableUpdater = routeTableUpdater;
        this.alertNotifier = alertNotifier;
        this.autoFailback = autoFailback;
    }

    /**
     * 处理一次健康检查探测结果
     *
     * @param idcId 机房标识
     * @param healthy 本次探测是否健康
     */
    public void onHealthCheckResult(String idcId, boolean healthy) {
        if (healthy) {
            handleSuccessProbe(idcId);
        } else {
            handleFailureProbe(idcId);
        }
    }

    // ========== 第①②步：处理探测失败，达到阈值判定故障 ==========
    private void handleFailureProbe(String idcId) {
        recoveryCounters.computeIfAbsent(idcId, k -> new AtomicInteger()).set(0);
        int failures = failureCounters
            .computeIfAbsent(idcId, k -> new AtomicInteger())
            .incrementAndGet();

        if (failures < FAILURE_THRESHOLD) {
            logger.warn("[IdcId={}] 探测失败, 连续失败次数={}, 未达到阈值",
                idcId, failures);
            return;
        }

        if (Boolean.TRUE.equals(failoverState.get(idcId))) {
            return; // 已经处于切流状态，避免重复触发
        }

        // ========== 第③步：触发切流，更新路由表 ==========
        logger.error("[IdcId={}] 连续失败达到阈值{}, 判定机房故障, 触发切流",
            idcId, FAILURE_THRESHOLD);
        failoverState.put(idcId, true);
        routeTableUpdater.setIdcWeight(idcId, 0);
        routeTableUpdater.redistributeWeightToHealthyIdcs(idcId);

        // ========== 第④步：告警通知 ==========
        alertNotifier.notify(String.format(
            "机房[%s]健康检查连续失败%d次，已自动切流至其他机房",
            idcId, failures));
    }

    // ========== 第⑤步：处理探测成功，判断是否满足恢复条件 ==========
    private void handleSuccessProbe(String idcId) {
        failureCounters.computeIfAbsent(idcId, k -> new AtomicInteger()).set(0);

        if (!Boolean.TRUE.equals(failoverState.get(idcId))) {
            return; // 未处于切流状态，无需处理恢复逻辑
        }

        int successes = recoveryCounters
            .computeIfAbsent(idcId, k -> new AtomicInteger())
            .incrementAndGet();

        if (successes < RECOVERY_THRESHOLD) {
            logger.info("[IdcId={}] 探测恢复中, 连续成功次数={}, " 
                + "未达到恢复阈值", idcId, successes);
            return;
        }

        if (autoFailback) {
            logger.info("[IdcId={}] 连续成功达到恢复阈值{}, 自动切回",
                idcId, RECOVERY_THRESHOLD);
            routeTableUpdater.restoreIdcWeight(idcId);
            failoverState.put(idcId, false);
            alertNotifier.notify(String.format(
                "机房[%s]已自动恢复流量切回", idcId));
        } else {
            logger.info("[IdcId={}] 机房已达到恢复条件, 等待人工确认切回",
                idcId);
            alertNotifier.notify(String.format(
                "机房[%s]健康检查已恢复正常，请人工确认是否切回流量", idcId));
        }
    }
}
```

### 7.4 三个案例的协同关系

三个案例分别覆盖了流量路由体系在"常规调用路由决策""版本灰度发布""机房级容灾"三个典型场景下的核心链路，实际生产环境中它们相互配合：

| 协同维度 | 案例一（多规则路由决策） | 案例二（灰度发布） | 案例三（容灾切流） |
|---------|------------------------|--------------------|--------------------|
| 触发时机 | 每次RPC调用必经的路由阶段 | 新版本上线时主动发起 | 健康检查探测到故障时自动触发 |
| 核心目标 | 从多种路由规则中筛选正确节点 | 新版本渐进式验证与放量 | 快速隔离故障、保障可用性 |
| Fallback策略 | SET不支持fallback，其余阶段支持 | 指标异常时自动回滚 | 连续失败判定后切流，避免误判抖动 |
| 结果落地 | 选定最终目标节点 | 完成全量发布或安全回滚 | 更新路由表权重，流量重新分配 |
| 共同依赖 | 统一的路由优先级链、流量上下文 | 依赖路由体系中的LiteSet能力 | 依赖路由体系中的机房权重与健康检查 |

灰度发布（案例二）本质上是流量路由能力（案例一中的LiteSet路由阶段）在版本发布场景下的应用，而容灾切流（案例三）则是路由体系在故障场景下的自动化响应。三者共享同一套路由决策基础设施，只是驱动路由变化的触发条件和目标不同。</new_string>
