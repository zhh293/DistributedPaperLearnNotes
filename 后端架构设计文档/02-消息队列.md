# 消息队列架构设计

## 一、问题背景

### 1.1 为什么需要消息队列

在分布式系统中，服务间的通信方式主要有两种：同步通信（RPC）和异步通信（消息队列）。RPC适用于需要即时返回结果的场景，但在以下场景中，RPC方式会遇到瓶颈：

1. **异步解耦**：用户下单后需要发送短信通知、推送消息、更新积分等，这些操作不需要在下单主流程中同步完成。如果用RPC同步调用，任何一个下游服务超时都会影响下单响应时间。
2. **流量削峰**：秒杀活动瞬间流量可达平时的100倍，如果直接打到数据库会导致系统崩溃。消息队列作为缓冲层，将瞬时流量平滑为匀速处理。
3. **数据分发**：一条订单消息需要被多个系统消费（结算系统、配送系统、营销系统），使用RPC需要调用方知道所有下游，耦合度极高。
4. **最终一致性**：分布式事务中，通过消息队列实现事务消息，保证跨系统的最终一致性。

### 1.2 不解决的后果

- **系统脆弱**：任何下游服务的故障都会导致上游服务阻塞，形成级联失败。
- **资源浪费**：为应对峰值流量，所有下游系统都需要按峰值扩容，成本极高。
- **耦合严重**：新增一个消费方需要修改生产方代码，违反开闭原则。

### 1.3 核心需求

一个企业级消息队列系统需要满足以下核心需求：

| 需求 | 说明 | 优先级 |
|------|------|--------|
| 高可用 | 服务可用率 >= 99.999% | P0 |
| 高吞吐 | 日消息量万亿级别 | P0 |
| 消息可靠 | 消息不丢失（at least once） | P0 |
| 低延迟 | 端到端延迟 < 100ms | P1 |
| 消息有序 | 同一Key的消息保证有序 | P1 |
| 消息回溯 | 支持按时间点回溯消费 | P2 |

## 二、整体架构设计

### 2.1 核心组件

消息队列系统由以下核心组件组成：

```
┌─────────────┐                                    ┌─────────────┐
│  Producer    │    ┌──────────────────────────┐    │  Consumer    │
│  消息生产者  │───▶│      Broker集群           │───▶│  消息消费者  │
│             │    │                          │    │             │
│  Producer    │    │  ┌──────┐  ┌──────┐     │    │  Consumer    │
│  消息生产者  │───▶│  │Broker│  │Broker│     │───▶│  消息消费者  │
└─────────────┘    │  │  -1  │  │  -2  │ ... │    └─────────────┘
                   │  └──────┘  └──────┘     │
                   └──────────┬───────────────┘
                              │
                   ┌──────────▼───────────────┐
                   │     调度/协调服务          │
                   │  (ZooKeeper/自研)         │
                   └──────────────────────────┘
```

各组件职责：

| 组件 | 职责 |
|------|------|
| **Producer** | 消息生产者，将消息发送到Broker指定的Topic |
| **Broker** | 消息存储和转发，负责消息的持久化、副本复制、消费管理 |
| **Consumer** | 消息消费者，从Broker拉取消息进行消费 |
| **Coordinator** | 协调服务，管理Broker的元数据、分区分配、Consumer Group协调 |
| **Admin Platform** | 管理平台，提供Topic申请、监控、消费进度查看等 |

### 2.2 核心数据模型

```
Topic (主题)
  ├── Partition-0 (分区0)
  │   ├── Message[offset=0]
  │   ├── Message[offset=1]
  │   ├── Message[offset=2]
  │   └── ...
  ├── Partition-1 (分区1)
  │   ├── Message[offset=0]
  │   ├── Message[offset=1]
  │   └── ...
  └── Partition-N (分区N)
      └── ...
```

**关键概念**：
- **Topic**：消息的逻辑分类，如"订单Topic"、"支付Topic"。
- **Partition**：Topic的物理分片，是消息存储和并行消费的最小单位。
- **Offset**：消息在Partition内的唯一偏移量，单调递增，Consumer通过Offset记录消费进度。
- **Consumer Group**：一组Consumer实例组成的逻辑消费组，组内消费者共同消费一个Topic的所有Partition。
- **Replica**：Partition的副本，用于容灾。分为Leader和Follower。

### 2.3 部署架构

典型的多机房部署架构：

```
机房A (北京)                          机房B (上海)
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  Broker Cluster A           │     │  Broker Cluster B           │
│  ┌─────┐ ┌─────┐ ┌─────┐  │     │  ┌─────┐ ┌─────┐ ┌─────┐  │
│  │BR-1 │ │BR-2 │ │BR-3 │  │     │  │BR-4 │ │BR-5 │ │BR-6 │  │
│  └─────┘ └─────┘ └─────┘  │     │  └─────┘ └─────┘ └─────┘  │
│                             │     │                             │
│  Producer ──► 本地集群       │     │  Producer ──► 本地集群       │
│  Consumer ◄── 本地集群       │     │  Consumer ◄── 本地集群       │
└─────────────────────────────┘     └─────────────────────────────┘
          │                                   │
          └──────── 跨机房数据同步 ─────────────┘
```

设计原则：
- **就近生产消费**：Producer和Consumer优先访问本机房的Broker集群
- **跨机房容灾**：通过数据同步实现异地容灾
- **按业务部门隔离**：不同业务部门使用不同的Broker集群，避免相互影响

## 三、核心链路设计

### 3.1 消息生产链路

#### 3.1.1 生产流程总览

```
Producer
  │
  ▼
1. 构造消息（Topic, Key, Value, Headers）
  │
  ▼
2. 序列化消息
  │
  ▼
3. 分区路由（决定发送到哪个Partition）
  │  ├── 指定Partition：直接发送
  │  ├── 指定Key：hash(key) % partitionCount
  │  └── 未指定Key：Round-Robin轮询
  │
  ▼
4. 追加到本地发送缓冲区（RecordAccumulator）
  │
  ▼
5. Sender线程批量发送到Broker
  │
  ▼
6. 等待Broker ACK确认
  │  ├── acks=0：不等待确认（最高性能，可能丢消息）
  │  ├── acks=1：Leader写入即确认（平衡性能与可靠性）
  │  └── acks=-1/all：所有ISR副本写入后确认（最高可靠性）
  │
  ▼
7. 回调Callback（成功/失败）
```

#### 3.1.2 分区路由策略

分区路由决定消息发送到哪个Partition，直接影响消息的有序性和负载均衡：

```java
public class PartitionRouter {
    
    /**
     * 分区路由策略
     */
    public int selectPartition(String topic, String key, byte[] value, 
                               int partitionCount) {
        if (key != null) {
            // 1. 有Key：按Key哈希取模，保证相同Key的消息落在同一Partition
            //    使用Murmur2哈希算法，分布均匀，碰撞率低
            return (murmur2Hash(key.getBytes()) & 0x7FFFFFFF) % partitionCount;
        }
        
        // 2. 无Key：使用粘性分区（Sticky Partition）策略
        //    同一批次的消息发往同一Partition，减少请求次数
        return stickyPartition(topic, partitionCount);
    }
    
    /**
     * Murmur2哈希算法 - Kafka使用的默认哈希算法
     * 特点：非加密哈希，性能极高，分布均匀
     */
    private int murmur2Hash(byte[] data) {
        int length = data.length;
        int seed = 0x9747b28c;
        int m = 0x5bd1e995;
        int r = 24;
        int h = seed ^ length;
        int length4 = length / 4;
        
        for (int i = 0; i < length4; i++) {
            int i4 = i * 4;
            int k = (data[i4] & 0xff) 
                  + ((data[i4 + 1] & 0xff) << 8) 
                  + ((data[i4 + 2] & 0xff) << 16) 
                  + ((data[i4 + 3] & 0xff) << 24);
            k *= m;
            k ^= k >>> r;
            k *= m;
            h *= m;
            h ^= k;
        }
        
        // 处理剩余字节
        switch (length % 4) {
            case 3: h ^= (data[(length & ~3) + 2] & 0xff) << 16;
            case 2: h ^= (data[(length & ~3) + 1] & 0xff) << 8;
            case 1: h ^= (data[length & ~3] & 0xff);
                    h *= m;
        }
        
        h ^= h >>> 13;
        h *= m;
        h ^= h >>> 15;
        return h;
    }
    
    /**
     * 粘性分区策略
     * 当RecordAccumulator中当前分区的batch已满或超时时，才切换到新分区
     */
    private final AtomicInteger stickyIndex = new AtomicInteger(0);
    
    private int stickyPartition(String topic, int partitionCount) {
        // 每当一个batch完成发送，才轮换到下一个分区
        return stickyIndex.get() % partitionCount;
    }
    
    public void onBatchCompleted() {
        stickyIndex.incrementAndGet();
    }
}
```

#### 3.1.3 消息批量发送机制

Producer内部使用**RecordAccumulator**（记录累加器）实现消息的批量发送，核心思路是：

- 消息先追加到本地内存Buffer中
- 当Buffer满（batch.size）或等待超过linger.ms时，触发发送
- 同一Partition的消息会被打包为一个batch发送，减少网络IO次数

```java
public class RecordAccumulator {
    
    // 每个Partition维护一个消息队列
    private final ConcurrentMap<Integer, Deque<RecordBatch>> batches = 
        new ConcurrentHashMap<>();
    
    // 内存池（复用ByteBuffer，减少GC）
    private final BufferPool bufferPool;
    
    // 批量大小（默认16KB）
    private final int batchSize;
    
    // 等待时间（默认0ms，即不等待。设为>0可提高吞吐但增加延迟）
    private final long lingerMs;
    
    /**
     * 追加消息到缓冲区
     * 设计模式：生产者-消费者模式
     */
    public RecordAppendResult append(int partition, byte[] key, byte[] value) {
        Deque<RecordBatch> deque = getOrCreateDeque(partition);
        
        synchronized (deque) {
            // 尝试追加到当前batch
            RecordBatch last = deque.peekLast();
            if (last != null) {
                int appendResult = last.tryAppend(key, value);
                if (appendResult != -1) {
                    return new RecordAppendResult(last.future, false);
                }
            }
            
            // 当前batch已满，创建新batch
            ByteBuffer buffer = bufferPool.allocate(batchSize);
            RecordBatch batch = new RecordBatch(partition, buffer);
            batch.tryAppend(key, value);
            deque.addLast(batch);
            
            return new RecordAppendResult(batch.future, true);
        }
    }
    
    /**
     * 获取准备好发送的batch
     * 条件：batch已满 || 等待时间超过lingerMs || 内存池耗尽
     */
    public List<RecordBatch> drain(long now) {
        List<RecordBatch> readyBatches = new ArrayList<>();
        
        for (Map.Entry<Integer, Deque<RecordBatch>> entry : batches.entrySet()) {
            Deque<RecordBatch> deque = entry.getValue();
            synchronized (deque) {
                RecordBatch first = deque.peekFirst();
                if (first == null) continue;
                
                boolean batchFull = first.isFull();
                boolean expired = now - first.createdMs >= lingerMs;
                boolean memoryExhausted = bufferPool.queued() > 0;
                
                if (batchFull || expired || memoryExhausted) {
                    readyBatches.add(deque.pollFirst());
                }
            }
        }
        
        return readyBatches;
    }
}
```

#### 3.1.4 ACK机制详解

```java
public class AckConfig {
    
    /**
     * acks=0: Fire and Forget
     * - Producer发送后不等待任何确认
     * - 性能最高，但可能丢消息
     * - 适用场景：日志收集、监控指标等允许少量丢失的场景
     */
    public static final int ACKS_NONE = 0;
    
    /**
     * acks=1: Leader Acknowledged
     * - Leader Broker接收并写入本地日志后返回ACK
     * - 不等待Follower同步
     * - 平衡了性能和可靠性
     * - 风险：Leader宕机后，未同步到Follower的消息会丢失
     * - 适用场景：大部分业务消息
     */
    public static final int ACKS_LEADER = 1;
    
    /**
     * acks=-1/all: All ISR Acknowledged
     * - Leader等待所有ISR中的Follower都同步完成后返回ACK
     * - 可靠性最高，但延迟最大
     * - ISR（In-Sync Replicas）：与Leader保持同步的副本集合
     * - 配合min.insync.replicas=2使用，确保至少2个副本写入
     * - 适用场景：金融交易、支付等不允许丢消息的场景
     */
    public static final int ACKS_ALL = -1;
}
```

#### 3.1.5 同步与异步发送

```java
public class MessageProducer {
    
    /**
     * 同步发送 - 阻塞等待结果
     * 优点：可靠性高，失败立即可知
     * 缺点：吞吐量低，阻塞发送线程
     */
    public SendResult sendSync(String topic, String key, String value) {
        Message message = new Message(topic, key, value.getBytes());
        try {
            // 阻塞等待发送结果
            Future<SendResult> future = producer.send(message);
            return future.get(3000, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            throw new SendException("Send timeout", e);
        } catch (ExecutionException e) {
            throw new SendException("Send failed", e.getCause());
        }
    }
    
    /**
     * 异步发送 - 非阻塞，通过回调获取结果
     * 优点：吞吐量高，不阻塞业务线程
     * 缺点：客户端异常宕机时，缓冲区中的消息可能丢失
     */
    public void sendAsync(String topic, String key, String value, 
                          SendCallback callback) {
        Message message = new Message(topic, key, value.getBytes());
        producer.send(message, (result, exception) -> {
            if (exception != null) {
                // 发送失败
                callback.onException(exception);
                // 可选：加入重试队列
                retryQueue.offer(message);
            } else {
                callback.onSuccess(result);
            }
        });
    }
    
    /**
     * 带连接池的同步发送 - 兼顾可靠性和吞吐
     * 使用线程池并发发送，适合消息量大且不能丢的场景
     */
    public SendResult sendWithPool(String topic, String key, String value) {
        return sendExecutor.submit(() -> sendSync(topic, key, value)).get();
    }
}
```

### 3.2 消息存储链路

#### 3.2.1 日志存储结构

Broker使用**顺序追加写日志文件**的方式存储消息，这是消息队列实现高吞吐的核心设计：

```
Topic: order-topic
Partition: 0
  │
  ├── 00000000000000000000.log    (日志文件，存储消息数据)
  ├── 00000000000000000000.index  (偏移量索引文件)
  ├── 00000000000000000000.timeindex (时间戳索引文件)
  │
  ├── 00000000000000065536.log    (第二个Segment)
  ├── 00000000000000065536.index
  ├── 00000000000000065536.timeindex
  │
  └── ...
```

**Segment分段设计**：
- 每个Partition的日志被分成多个Segment文件
- 每个Segment文件大小有上限（默认1GB）
- Segment文件名为该文件中第一条消息的Offset
- 旧的Segment根据保留策略（时间/大小）被清理

```java
public class LogSegment {
    
    private final FileChannel logChannel;     // 日志文件
    private final MappedByteBuffer indexBuffer; // 索引文件（内存映射）
    private final long baseOffset;            // 该Segment的起始Offset
    private volatile long maxOffset;          // 当前最大Offset
    
    /**
     * 追加消息到日志文件
     * 核心优化：顺序写磁盘，性能接近内存写入
     */
    public long append(byte[] messageBytes) {
        // 1. 顺序写入日志文件
        ByteBuffer buffer = ByteBuffer.wrap(messageBytes);
        long position = logChannel.position();
        logChannel.write(buffer);
        
        // 2. 更新稀疏索引（每隔N条消息记录一个索引条目）
        long currentOffset = maxOffset++;
        if (currentOffset % INDEX_INTERVAL == 0) {
            // 索引条目：<relativeOffset, filePosition>
            indexBuffer.putInt((int)(currentOffset - baseOffset));
            indexBuffer.putInt((int) position);
        }
        
        return currentOffset;
    }
    
    /**
     * 根据Offset查找消息
     * 算法：二分查找索引 -> 定位到日志文件位置 -> 顺序扫描
     */
    public byte[] read(long targetOffset) {
        // 1. 在索引文件中二分查找，找到 <= targetOffset 的最大索引条目
        int relativeOffset = (int)(targetOffset - baseOffset);
        int position = binarySearchIndex(relativeOffset);
        
        // 2. 从该位置开始顺序扫描日志文件
        logChannel.position(position);
        while (logChannel.position() < logChannel.size()) {
            byte[] message = readNextMessage(logChannel);
            long offset = extractOffset(message);
            if (offset == targetOffset) {
                return message;
            }
            if (offset > targetOffset) {
                break;
            }
        }
        return null;
    }
}
```

#### 3.2.2 页缓存与零拷贝

消息队列高吞吐的两大核心技术：

**Page Cache（页缓存）**：
- 消息写入时，先写入操作系统的Page Cache（内存），然后异步刷盘
- 消息读取时，如果数据在Page Cache中，直接从内存读取，不需要磁盘IO
- 对于"生产即消费"的场景，消息几乎100%命中Page Cache

**Zero Copy（零拷贝）**：

传统数据传输：
```
磁盘 → 内核缓冲区 → 用户缓冲区 → Socket缓冲区 → 网卡
（4次拷贝，4次上下文切换）
```

零拷贝（sendfile）：
```
磁盘 → 内核缓冲区 → 网卡
（2次拷贝，2次上下文切换）
```

```java
public class ZeroCopyTransfer {
    
    /**
     * 使用Java NIO的transferTo实现零拷贝
     * 底层调用Linux sendfile系统调用
     */
    public long transferTo(FileChannel fileChannel, long position, 
                           long count, SocketChannel socketChannel) {
        // 直接从文件通道传输到Socket通道，不经过用户空间
        return fileChannel.transferTo(position, count, socketChannel);
    }
}
```

#### 3.2.3 刷盘机制

```java
public class FlushPolicy {
    
    /**
     * 异步刷盘（默认）
     * - 消息写入Page Cache后即返回
     * - 由操作系统决定刷盘时机（通常30秒）
     * - 性能最高，但宕机可能丢失Page Cache中未刷盘的数据
     * - 配合多副本机制可以保证可靠性
     */
    public void asyncFlush(FileChannel channel) {
        // 不主动调用force，依赖OS的pdflush机制
    }
    
    /**
     * 同步刷盘
     * - 每条消息（或每个batch）写入后立即调用fsync
     * - 可靠性最高，但性能下降10倍以上
     * - 通常不推荐，除非单副本且对可靠性要求极高
     */
    public void syncFlush(FileChannel channel) {
        channel.force(false); // 将Page Cache中的数据强制刷入磁盘
    }
    
    /**
     * 定时刷盘（折中方案）
     * - 每隔N秒或每写入N条消息后刷盘
     * - 在性能和可靠性之间取得平衡
     */
    public void periodicFlush(FileChannel channel, int intervalMs) {
        scheduler.scheduleAtFixedRate(() -> {
            channel.force(false);
        }, intervalMs, intervalMs, TimeUnit.MILLISECONDS);
    }
}
```

### 3.3 副本机制与可靠性

#### 3.3.1 副本架构

每个Partition有多个副本（Replica），分布在不同的Broker上：

```
Partition-0:
  Broker-1: Leader   (处理所有读写请求)
  Broker-2: Follower (从Leader同步数据)
  Broker-3: Follower (从Leader同步数据)
  
ISR (In-Sync Replicas) = {Broker-1, Broker-2, Broker-3}
  当Follower落后过多时，会被踢出ISR
```

**ISR（In-Sync Replicas）机制**：
- ISR是与Leader保持同步的副本集合
- Follower需要在replica.lag.time.max.ms时间内追上Leader的写入进度，否则被踢出ISR
- acks=all时，只需要ISR中的所有副本确认即可

```java
public class ReplicaManager {
    
    // ISR列表
    private final Set<Integer> inSyncReplicas = ConcurrentHashMap.newKeySet();
    
    // 所有副本的同步进度
    private final ConcurrentMap<Integer, Long> replicaOffsets = new ConcurrentHashMap<>();
    
    // Leader的最新写入Offset
    private volatile long leaderEndOffset = 0;
    
    /**
     * Leader写入消息
     */
    public long appendAsLeader(byte[] message) {
        // 1. 写入Leader本地日志
        long offset = localLog.append(message);
        leaderEndOffset = offset;
        
        // 2. 等待ISR中的Follower同步（如果acks=all）
        if (acksAll) {
            waitForIsrSync(offset);
        }
        
        return offset;
    }
    
    /**
     * Follower从Leader拉取数据并同步
     * 设计模式：Pull模式 - Follower主动拉取，而非Leader推送
     * 优点：Follower可以按自己的速度拉取，不会因Leader推送过快导致问题
     */
    public void fetchFromLeader(int followerId, long fetchOffset) {
        // 1. 从Leader日志中读取fetchOffset之后的消息
        List<byte[]> messages = localLog.read(fetchOffset, MAX_FETCH_SIZE);
        
        // 2. 更新该Follower的同步进度
        if (!messages.isEmpty()) {
            long newOffset = fetchOffset + messages.size();
            replicaOffsets.put(followerId, newOffset);
        }
    }
    
    /**
     * ISR维护 - 定期检查Follower同步状态
     */
    public void updateIsr() {
        long now = System.currentTimeMillis();
        
        for (Map.Entry<Integer, Long> entry : replicaOffsets.entrySet()) {
            int replicaId = entry.getKey();
            long replicaOffset = entry.getValue();
            
            // 检查Follower是否在规定时间内追上Leader
            long lag = leaderEndOffset - replicaOffset;
            long lastFetchTime = getLastFetchTime(replicaId);
            
            if (now - lastFetchTime > replicaLagTimeMaxMs) {
                // 超时未同步，踢出ISR
                inSyncReplicas.remove(replicaId);
                log.warn("Replica {} removed from ISR, lag={}", replicaId, lag);
            }
        }
    }
    
    /**
     * 等待ISR中所有副本同步到指定Offset
     */
    private void waitForIsrSync(long targetOffset) {
        long deadline = System.currentTimeMillis() + requestTimeoutMs;
        
        while (System.currentTimeMillis() < deadline) {
            boolean allSynced = inSyncReplicas.stream()
                .allMatch(replicaId -> {
                    Long offset = replicaOffsets.get(replicaId);
                    return offset != null && offset >= targetOffset;
                });
            
            if (allSynced) return;
            
            LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(1));
        }
        
        throw new TimeoutException("Waiting for ISR sync timed out");
    }
}
```

```java
public class LeaderElection {

     * 从ISR中选举新Leader
     * 算法：选择ISR中同步进度最新的副本作为新Leader
     */
    public int electLeader(int partitionId, Set<Integer> isr,

        if (isr.isEmpty()) {

            if (uncleanLeaderElectionEnabled) {

                throw new LeaderElectionException(
                    "No in-sync replicas available for partition " + partitionId);
            }

        int newLeader = -1;
        long maxOffset = -1;
        
        for (int replicaId : isr) {
            long offset = replicaOffsets.getOrDefault(replicaId, 0L);
            if (offset > maxOffset) {
                maxOffset = offset;
                newLeader = replicaId;
            }
        }
        
        return newLeader;
    }
```

#### 3.4.2 分区分配策略

消费组中的Consumer如何分配Partition是核心问题：

```java
/**
 * Range分配策略
 * 将Partition按范围分配给Consumer
 * 例如：6个Partition, 2个Consumer
 * C0: P0, P1, P2
 * C1: P3, P4, P5
 */
public class RangeAssignor implements PartitionAssignor {
    
    @Override
    public Map<String, List<Integer>> assign(int partitionCount, 
                                              List<String> consumers) {
        int consumersCount = consumers.size();
        int partitionsPerConsumer = partitionCount / consumersCount;
        int extra = partitionCount % consumersCount;
        
        Map<String, List<Integer>> assignment = new HashMap<>();
        int currentPartition = 0;
        
        for (int i = 0; i < consumersCount; i++) {
            // 前extra个Consumer多分配一个Partition
            int numPartitions = partitionsPerConsumer + (i < extra ? 1 : 0);
            List<Integer> partitions = new ArrayList<>();
            for (int j = 0; j < numPartitions; j++) {
                partitions.add(currentPartition++);
            }
            assignment.put(consumers.get(i), partitions);
        }
        
        return assignment;
    }
}

/**
 * RoundRobin分配策略
 * 将所有Partition轮询分配给Consumer
 * 例如：6个Partition, 2个Consumer
 * C0: P0, P2, P4
 * C1: P1, P3, P5
 */
public class RoundRobinAssignor implements PartitionAssignor {
    
    @Override
    public Map<String, List<Integer>> assign(int partitionCount, 
                                              List<String> consumers) {
        Map<String, List<Integer>> assignment = new HashMap<>();
        consumers.forEach(c -> assignment.put(c, new ArrayList<>()));
        
        for (int p = 0; p < partitionCount; p++) {
            String consumer = consumers.get(p % consumers.size());
            assignment.get(consumer).add(p);
        }
        
        return assignment;
    }
}

/**
 * 粘性分配策略（Sticky）
 * 在保持均衡的前提下，尽量保持现有分配不变
 * 优点：减少Rebalance时的分区迁移量
 */
public class StickyAssignor implements PartitionAssignor {
    
    @Override
    public Map<String, List<Integer>> assign(int partitionCount, 
                                              List<String> consumers,
                                              Map<String, List<Integer>> previousAssignment) {
        Map<String, List<Integer>> newAssignment = new HashMap<>();
        
        // 1. 保留仍然有效的分配
        for (Map.Entry<String, List<Integer>> entry : previousAssignment.entrySet()) {
            if (consumers.contains(entry.getKey())) {
                newAssignment.put(entry.getKey(), new ArrayList<>(entry.getValue()));
            }
        }
        
        // 2. 将未分配的Partition均匀分配给Consumer
        Set<Integer> assigned = newAssignment.values().stream()
            .flatMap(List::stream).collect(Collectors.toSet());
        
        List<Integer> unassigned = new ArrayList<>();
        for (int p = 0; p < partitionCount; p++) {
            if (!assigned.contains(p)) {
                unassigned.add(p);
            }
        }
        
        // 按照当前分配数量从少到多的顺序分配
        consumers.sort(Comparator.comparingInt(c -> 
            newAssignment.getOrDefault(c, Collections.emptyList()).size()));
        
        int idx = 0;
        for (int p : unassigned) {
            String consumer = consumers.get(idx % consumers.size());
            newAssignment.computeIfAbsent(consumer, k -> new ArrayList<>()).add(p);
            idx++;
        }
        
        return newAssignment;
    }
}
```

```java
                // 串行处理，保证顺序
                processMessage(record);
            }
            consumer.commitSync();
        }

     * 按Key分桶并行消费
     * 同一Key串行，不同Key并行，兼顾有序性和吞吐量
     * 设计模式：分桶策略
     */
    public void consumeWithKeyOrdering() {
        // 按Key的hashCode分配到不同的有序队列
        int bucketCount = 16;
        BlockingQueue<ConsumerRecord>[] buckets = new LinkedBlockingQueue[bucketCount];
        ExecutorService[] executors = new ExecutorService[bucketCount];
        
        for (int i = 0; i < bucketCount; i++) {
            buckets[i] = new LinkedBlockingQueue<>();
            final int idx = i;
            executors[i] = Executors.newSingleThreadExecutor();
            executors[i].submit(() -> {
                while (running) {
                    ConsumerRecord record = buckets[idx].poll(100, TimeUnit.MILLISECONDS);
                    if (record != null) {
                        processMessage(record);
                    }
                }
            });
        }
        
        // 消费线程：将消息分发到对应的桶
        while (running) {
            ConsumerRecords records = consumer.poll(Duration.ofMillis(500));
            for (ConsumerRecord record : records) {
                int bucket = (record.key().hashCode() & 0x7FFFFFFF) % bucketCount;
                buckets[bucket].put(record);
            }
        }
    }

        }
```

```java
public class ProducerExceptionHandler {
    
    /**
     * 发送失败重试策略
     */
    public void sendWithRetry(String topic, String key, String value, int maxRetries) {
        int retryCount = 0;
        Exception lastException = null;
        
        while (retryCount <= maxRetries) {
            try {
                SendResult result = producer.sendSync(topic, key, value);
                return; // 发送成功

                throw e;
            }
        }
```

```java
            producer.beginTransaction();
            
            for (ProducerRecord record : records) {
                producer.send(record);
            }
            
            // 提交事务
            producer.commitTransaction();
        } catch (Exception e) {
            // 回滚事务
            producer.abortTransaction();
            throw e;
        }
    }
}

public class ExactlyOnceConsumer {
    
    /**
     * 消费端实现Exactly-Once
     * 方法：消费消息 + 提交Offset 作为一个事务
     * 
     * 方式1：Consumer-Transform-Producer模式
     * 消费消息后，将处理结果和Offset一起写入目标Topic
     */
    public void consumeTransformProduce() {
        producer.initTransactions();
        
        while (running) {
            ConsumerRecords records = consumer.poll(Duration.ofMillis(500));
            
            if (!records.isEmpty()) {
                producer.beginTransaction();
                
                try {
                    for (ConsumerRecord record : records) {
                        // 处理消息并发送到下游Topic
                        String result = transform(record);
                        producer.send(new ProducerRecord<>("output-topic", result));
                    }
                    
                    // 将Offset也作为事务的一部分提交
                    producer.sendOffsetsToTransaction(
                        getOffsets(records), consumer.groupMetadata());
                    
                    producer.commitTransaction();
                } catch (Exception e) {
                    producer.abortTransaction();
                }
            }
        }
    }
    
    /**
     * 方式2：消费+数据库操作 在同一个本地事务中
     * 将Offset存储在业务数据库中，与业务操作在同一事务
     */
    public void consumeWithLocalTransaction() {
        while (running) {
            ConsumerRecords records = consumer.poll(Duration.ofMillis(500));
            
            for (ConsumerRecord record : records) {
                // 开启本地数据库事务
                Connection conn = dataSource.getConnection();
                conn.setAutoCommit(false);
                
                try {
                    // 1. 执行业务逻辑
                    processBusinessLogic(conn, record);
                    
                    // 2. 将Offset保存到数据库（同一事务）
                    saveOffset(conn, record.topic(), record.partition(), 
                        record.offset());
                    
                    conn.commit();
                } catch (Exception e) {
                    conn.rollback();
                }
            }
        }
    }
}
```

## 六、最佳实践与总结

### 6.1 设计原则

1. **Topic设计**：一个Topic对应一种业务事件，不要混用。Topic名称规范化，如`{业务域}.{事件类型}`。
2. **Partition数量**：根据目标吞吐量计算。分区数 >= 消费者最大实例数。分区数确定后增加容易，减少困难。
3. **消息大小**：控制单条消息 < 1MB。大消息拆分或存储到对象存储，消息中传递引用。
4. **Key设计**：有序性需求的消息必须设置Key。Key的分布要均匀，避免数据倾斜。

### 6.2 常见陷阱

1. **消费乱序**：多线程消费时，同一Key的消息被不同线程处理导致乱序。解决：按Key分桶。
2. **Rebalance风暴**：Consumer频繁加入/退出导致反复Rebalance。解决：增大session.timeout.ms，使用粘性分配。
3. **消息堆积**：Consumer处理速度跟不上生产速度。解决：扩分区+扩Consumer，优化消费逻辑。
4. **重复消费**：位点提交失败或Rebalance导致消息重复。解决：业务端做幂等处理。

### 6.3 监控指标

| 指标 | 说明 | 告警阈值 |
|------|------|----------|
| 消息积压量（Lag） | Consumer未消费的消息数 | > 10000 |
| 生产成功率 | 生产消息的成功比例 | < 99.9% |
| 消费延迟 | 从生产到消费的时间差 | > 10s |
| Broker磁盘使用率 | 日志文件占用的磁盘空间 | > 80% |
| ISR缩减 | ISR中的副本数减少 | < min.insync.replicas |

### 6.4 演进方向

1. **Serverless消费**：按消费量弹性伸缩Consumer实例
2. **Schema管理**：集成Schema Registry，管理消息格式的演进兼容性
3. **流批一体**：消息队列与流处理框架深度融合
4. **云原生**：基于Kubernetes的弹性调度，存储计算分离

### 7.1 案例一：可靠消息发送全链路

#### 7.1.1 场景说明

电商系统中，用户下单后需要通知积分系统为用户增加积分。核心诉求：

- **业务一致性**：订单创建成功，积分一定要加上；订单创建失败，积分一定不能加
- **不丢消息**：网络抖动、Broker宕机等异常下消息不能丢失
- **不重复处理**：消费端即使收到重复消息，积分也只加一次

#### 7.1.4 生产端完整实现

```java
/**
 * 可靠消息生产者 - 基于本地事务表
 * 
 * 核心思路：
 * 1. 业务操作与消息写表在同一个本地事务中，保证原子性
 * 2. 异步线程负责将消息表中的待发送消息投递到MQ
 * 3. 定时补偿任务兜底，确保消息最终一定发送成功
 */
@Service
@Slf4j
public class ReliableMessageProducer {

    @Autowired
    private TransactionMessageMapper messageMapper;

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    /**
     * 在业务事务中保存待发送消息
     * 由业务方在@Transactional方法内调用，与业务操作同事务
     *
     * @param topic  目标Topic
     * @param key    消息Key（用于分区路由和有序性保证）
     * @param body   消息体
     * @return 全局唯一消息ID
     */
    public String saveTransactionMessage(String topic, String key, Object body) {
        String messageId = generateMessageId();

        TransactionMessage message = new TransactionMessage();
        message.setMessageId(messageId);
        message.setTopic(topic);
        message.setMessageKey(key);
        message.setMessageBody(JSON.toJSONString(body));
        message.setStatus(MessageStatus.PENDING.getCode());
        message.setRetryCount(0);
        message.setMaxRetry(5);
        message.setNextRetryTime(new Date());

        messageMapper.insert(message);
        log.info("[可靠消息] 事务消息已落库, messageId={}, topic={}, key={}",
                messageId, topic, key);

        return messageId;
    }

    /**
     * 生成全局唯一消息ID
     * 格式：时间戳 + 机器标识 + 序列号，保证全局唯一
     */
    private String generateMessageId() {
        return UUID.randomUUID().toString().replace("-", "");
    }

    /**
     * 异步投递消息到MQ
     * 事务提交后由事件监听器触发，或由定时任务触发
     */
    @Async("mqSendExecutor")
    public void asyncSendMessage(TransactionMessage message) {
        try {
            doSendMessage(message);
        } catch (Exception e) {
            log.error("[可靠消息] 异步发送异常, messageId={}, error={}",
                    message.getMessageId(), e.getMessage(), e);
            // 异常不抛出，由定时补偿任务兜底
        }
    }

    /**
     * 执行消息发送
     * 发送成功后更新消息状态，失败则等待重试
     */
    private void doSendMessage(TransactionMessage message) {
        String messageId = message.getMessageId();

        // 构造Kafka消息，将messageId放入Header用于消费端幂等
        ProducerRecord<String, String> record = new ProducerRecord<>(
                message.getTopic(),
                message.getMessageKey(),
                message.getMessageBody()
        );
        record.headers().add("MESSAGE_ID", messageId.getBytes(StandardCharsets.UTF_8));
        record.headers().add("SEND_TIMESTAMP",
                String.valueOf(System.currentTimeMillis()).getBytes(StandardCharsets.UTF_8));

        try {
            // 同步发送，确保Broker确认接收
            SendResult<String, String> result = kafkaTemplate.send(record).get(5, TimeUnit.SECONDS);

            // 发送成功，更新消息状态
            messageMapper.updateStatus(messageId, MessageStatus.SENT.getCode());
            log.info("[可靠消息] 消息发送成功, messageId={}, topic={}, partition={}, offset={}",
                    messageId,
                    result.getRecordMetadata().topic(),
                    result.getRecordMetadata().partition(),
                    result.getRecordMetadata().offset());

        } catch (TimeoutException e) {
            log.warn("[可靠消息] 消息发送超时, messageId={}, 等待重试", messageId, e);
            updateRetryInfo(message);

        } catch (ExecutionException e) {
            Throwable cause = e.getCause();
            if (cause instanceof RetriableException) {
                log.warn("[可靠消息] 消息发送可重试异常, messageId={}, error={}",
                        messageId, cause.getMessage());
                updateRetryInfo(message);
            } else {
                log.error("[可靠消息] 消息发送不可重试异常, messageId={}", messageId, cause);
                messageMapper.updateStatus(messageId, MessageStatus.FAILED.getCode());
            }

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("[可靠消息] 消息发送被中断, messageId={}", messageId, e);
        }
    }

    /**
     * 更新重试信息
     * 使用指数退避策略计算下次重试时间
     */
    private void updateRetryInfo(TransactionMessage message) {
        int newRetryCount = message.getRetryCount() + 1;

        if (newRetryCount > message.getMaxRetry()) {
            // 超过最大重试次数，标记为失败，人工介入
            messageMapper.updateStatus(message.getMessageId(), MessageStatus.FAILED.getCode());
            log.error("[可靠消息] 消息超过最大重试次数, messageId={}, retryCount={}",
                    message.getMessageId(), newRetryCount);
            // 触发告警通知
            alertService.sendAlert("消息发送失败超过最大重试次数",
                    "messageId=" + message.getMessageId());
            return;
        }

        // 指数退避：1s, 2s, 4s, 8s, 16s
        long delaySeconds = (long) Math.pow(2, newRetryCount - 1);
        Date nextRetryTime = new Date(System.currentTimeMillis() + delaySeconds * 1000);

        messageMapper.updateRetry(message.getMessageId(), newRetryCount, nextRetryTime);
        log.info("[可靠消息] 消息将在{}后重试, messageId={}, retryCount={}",
                delaySeconds + "s", message.getMessageId(), newRetryCount);
    }

    /**
     * 定时补偿任务
     * 每10秒扫描一次待发送和需要重试的消息
     * 分布式环境下需要加分布式锁，避免多实例重复扫描
     */
    @Scheduled(fixedDelay = 10000)
    public void compensateSend() {
        // 分布式锁，防止多实例并发执行
        boolean locked = distributedLock.tryLock("mq_compensate_lock", 30, TimeUnit.SECONDS);
        if (!locked) {
            return;
        }

        try {
            // 查询待发送和需要重试的消息（每次最多处理100条，避免单次处理量过大）
            List<TransactionMessage> messages = messageMapper.selectPendingMessages(
                    Arrays.asList(MessageStatus.PENDING.getCode()),
                    new Date(),
                    100
            );

            if (messages.isEmpty()) {
                return;
            }

            log.info("[可靠消息] 补偿任务扫描到{}条待发送消息", messages.size());

            for (TransactionMessage message : messages) {
                try {
                    doSendMessage(message);
                } catch (Exception e) {
                    log.error("[可靠消息] 补偿发送异常, messageId={}",
                            message.getMessageId(), e);
                }
            }
        } finally {
            distributedLock.unlock("mq_compensate_lock");
        }
    }

    /**
     * 消息状态枚举
     */
    @Getter
    @AllArgsConstructor
    public enum MessageStatus {
        PENDING(0, "待发送"),
        SENT(1, "已发送"),
        CONFIRMED(2, "已确认"),
        FAILED(3, "发送失败");

        private final int code;
        private final String desc;
    }
}
```

#### 7.1.6 消费端幂等消费实现

```java
/**
 * 积分消费者 - 幂等消费实现
 *
 * 幂等策略：
 * 1. 消费前查询消费记录表，已消费则直接跳过
 * 2. 业务处理与消费记录写入在同一个本地事务中
 * 3. 消费记录表对(messageId, consumerGroup)建唯一索引，数据库层面兜底防重
 */
@Component
@Slf4j
public class PointsConsumer {

    private static final String CONSUMER_GROUP = "points-consumer-group";

    @Autowired
    private ConsumeRecordMapper consumeRecordMapper;

    @Autowired
    private PointsService pointsService;

    @Autowired
    private PlatformTransactionManager transactionManager;

    /**
     * 消费入口
     * 手动提交ACK，确保消费处理完成后才确认
     */
    @KafkaListener(
            topics = "points-topic",
            groupId = CONSUMER_GROUP,
            containerFactory = "manualAckListenerContainerFactory"
    )
    public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
        // 1. 提取消息ID
        String messageId = extractMessageId(record);
        if (messageId == null) {
            log.error("[积分消费] 消息缺少MESSAGE_ID, topic={}, partition={}, offset={}",
                    record.topic(), record.partition(), record.offset());
            ack.acknowledge(); // 无法幂等的消息直接ACK跳过，避免阻塞
            return;
        }

        log.info("[积分消费] 收到消息, messageId={}, partition={}, offset={}",
                messageId, record.partition(), record.offset());

        // 2. 幂等校验
        if (isAlreadyConsumed(messageId)) {
            log.warn("[积分消费] 消息已消费，跳过, messageId={}", messageId);
            ack.acknowledge();
            return;
        }

        // 3. 消费处理
        boolean success = consumeWithIdempotent(messageId, record);

        // 4. 处理结果
        if (success) {
            ack.acknowledge();
            log.info("[积分消费] 消费成功并ACK, messageId={}", messageId);
        } else {
            // 不ACK，消息将在下次poll时重新投递
            // 配合max.poll.interval.ms防止无限重试导致Rebalance
            log.error("[积分消费] 消费失败，等待重试, messageId={}", messageId);
        }
    }

    /**
     * 从消息Header中提取消息ID
     */
    private String extractMessageId(ConsumerRecord<String, String> record) {
        Header header = record.headers().lastHeader("MESSAGE_ID");
        if (header == null || header.value() == null) {
            return null;
        }
        return new String(header.value(), StandardCharsets.UTF_8);
    }

    /**
     * 检查消息是否已经被消费
     */
    private boolean isAlreadyConsumed(String messageId) {
        ConsumeRecord existRecord = consumeRecordMapper.selectByMessageIdAndGroup(
                messageId, CONSUMER_GROUP);
        return existRecord != null && existRecord.getStatus() == 1;
    }

    /**
     * 幂等消费核心逻辑
     * 业务处理与消费记录写入在同一个本地事务中
     */
    private boolean consumeWithIdempotent(String messageId, 
                                          ConsumerRecord<String, String> record) {
        TransactionStatus txStatus = transactionManager.getTransaction(
                new DefaultTransactionDefinition());

        try {
            // 1. 再次检查并插入消费记录（利用唯一索引防并发重复）
            ConsumeRecord consumeRecord = new ConsumeRecord();
            consumeRecord.setMessageId(messageId);
            consumeRecord.setConsumerGroup(CONSUMER_GROUP);
            consumeRecord.setStatus(1); // 消费成功

            try {
                consumeRecordMapper.insert(consumeRecord);
            } catch (DuplicateKeyException e) {
                // 唯一索引冲突，说明已被其他线程/实例消费
                log.warn("[积分消费] 并发消费检测到重复, messageId={}", messageId);
                transactionManager.rollback(txStatus);
                return true; // 返回成功，让调用方ACK
            }

            // 2. 执行业务逻辑
            PointsMessage pointsMsg = JSON.parseObject(record.value(), PointsMessage.class);
            pointsService.addPoints(
                    pointsMsg.getUserId(),
                    pointsMsg.getPoints(),
                    pointsMsg.getOrderId()
            );

            log.info("[积分消费] 积分增加成功, userId={}, points={}, orderId={}",
                    pointsMsg.getUserId(), pointsMsg.getPoints(), pointsMsg.getOrderId());

            // 3. 提交事务（业务操作和消费记录一起提交）
            transactionManager.commit(txStatus);
            return true;

        } catch (Exception e) {
            log.error("[积分消费] 消费处理异常, messageId={}", messageId, e);
            transactionManager.rollback(txStatus);
            return false;
        }
    }
}
```

#### 7.1.7 关键设计总结

| 环节 | 风险点 | 解决方案 |
|------|--------|----------|
| 业务操作与消息发送 | 事务不一致（业务成功但消息没发） | 本地事务表，业务操作与消息落库同事务 |
| 消息投递到Broker | 网络异常导致消息丢失 | 同步发送 + ACK确认 + 重试 + 定时补偿 |
| Broker端存储 | Broker宕机导致消息丢失 | acks=all + min.insync.replicas=2 |
| 消费端处理 | 重复消费导致数据不一致 | 消费记录表唯一索引 + 业务事务原子提交 |
| 消费端ACK | 处理成功但ACK失败导致重复消费 | 幂等校验前置，重复消费直接跳过 |

### 7.2 案例二：延迟消息处理全链路

#### 7.2.1 场景说明

电商系统中，用户下单后30分钟内未支付，系统需要自动取消订单并释放库存。核心诉求：

- **精确触发**：延迟时间到达后及时处理，误差控制在秒级
- **可靠性**：延迟消息不丢失，即使服务重启也能正常触发
- **幂等取消**：订单已支付或已取消时，不重复操作

解决方案：**发送延迟消息 -> 延迟投递 -> 消费处理（状态校验 + 幂等取消）**

#### 7.2.3 延迟消息生产端

```java
/**
 * 订单超时取消 - 延迟消息发送
 *
 * 实现方式说明：
 * - RocketMQ原生支持延迟级别消息（18个级别，最大2小时）
 * - Kafka不原生支持延迟消息，需要自建延迟服务或使用第三方组件
 * - 本实现基于RocketMQ延迟消息 + 自建补偿机制的混合方案
 */
@Service
@Slf4j
public class OrderTimeoutProducer {

    /** 订单超时时间：30分钟 */
    private static final long ORDER_TIMEOUT_MS = 30 * 60 * 1000L;

    /** 延迟消息Topic */
    private static final String DELAY_TOPIC = "order-timeout-check";

    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    @Autowired
    private OrderMapper orderMapper;

    /**
     * 下单成功后发送延迟消息
     * 在订单创建事务提交后调用
     *
     * @param orderId 订单ID
     * @param userId  用户ID
     */
    public void sendOrderTimeoutMessage(String orderId, String userId) {
        // 1. 构造延迟消息体
        OrderTimeoutMessage timeoutMsg = new OrderTimeoutMessage();
        timeoutMsg.setOrderId(orderId);
        timeoutMsg.setUserId(userId);
        timeoutMsg.setCreateTime(System.currentTimeMillis());
        timeoutMsg.setExpireTime(System.currentTimeMillis() + ORDER_TIMEOUT_MS);
        timeoutMsg.setMessageId(generateMessageId());

        String msgBody = JSON.toJSONString(timeoutMsg);

        // 2. 构造RocketMQ消息
        Message message = MessageBuilder
                .withPayload(msgBody)
                .setHeader(RocketMQHeaders.KEYS, orderId)
                .setHeader("MESSAGE_ID", timeoutMsg.getMessageId())
                .build();

        try {
            // 3. 发送延迟消息
            //    RocketMQ延迟级别16 = 30分钟
            //    级别对照：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
            SendResult result = rocketMQTemplate.syncSend(
                    DELAY_TOPIC,
                    message,
                    5000,  // 发送超时5秒
                    16     // 延迟级别16 = 30分钟
            );

            if (result.getSendStatus() == SendStatus.SEND_OK) {
                log.info("[订单超时] 延迟消息发送成功, orderId={}, messageId={}, " +
                                "msgId={}, 预计触发时间={}",
                        orderId,
                        timeoutMsg.getMessageId(),
                        result.getMsgId(),
                        formatTime(timeoutMsg.getExpireTime()));
            } else {
                log.error("[订单超时] 延迟消息发送状态异常, orderId={}, status={}",
                        orderId, result.getSendStatus());
                // 降级：写入数据库，由定时任务补偿
                saveToCompensationTable(timeoutMsg);
            }

        } catch (Exception e) {
            log.error("[订单超时] 延迟消息发送失败, orderId={}", orderId, e);
            // 降级：写入数据库，由定时任务补偿
            saveToCompensationTable(timeoutMsg);
        }
    }

    /**
     * 降级补偿：延迟消息发送失败时，写入补偿表
     * 由定时任务扫描处理
     */
    private void saveToCompensationTable(OrderTimeoutMessage timeoutMsg) {
        try {
            OrderTimeoutCompensation compensation = new OrderTimeoutCompensation();
            compensation.setOrderId(timeoutMsg.getOrderId());
            compensation.setExpireTime(new Date(timeoutMsg.getExpireTime()));
            compensation.setStatus(0); // 待处理
            compensationMapper.insert(compensation);
            log.info("[订单超时] 已写入补偿表, orderId={}", timeoutMsg.getOrderId());
        } catch (Exception ex) {
            log.error("[订单超时] 写入补偿表失败, orderId={}", timeoutMsg.getOrderId(), ex);
            // 最终告警兜底
            alertService.sendAlert("延迟消息和补偿表均失败",
                    "orderId=" + timeoutMsg.getOrderId());
        }
    }

    /**
     * 定时补偿任务
     * 每分钟扫描已过期但未处理的订单
     * 作为延迟消息的兜底方案
     */
    @Scheduled(fixedDelay = 60000)
    public void compensateTimeoutOrders() {
        boolean locked = distributedLock.tryLock("order_timeout_compensate", 
                50, TimeUnit.SECONDS);
        if (!locked) {
            return;
        }

        try {
            // 查询已过期且待处理的补偿记录
            List<OrderTimeoutCompensation> compensations =
                    compensationMapper.selectExpiredPending(new Date(), 50);

            for (OrderTimeoutCompensation comp : compensations) {
                try {
                    // 直接调用取消逻辑，不再发延迟消息
                    orderCancelService.checkAndCancelOrder(comp.getOrderId());
                    compensationMapper.updateStatus(comp.getId(), 1); // 标记已处理
                } catch (Exception e) {
                    log.error("[订单超时] 补偿处理异常, orderId={}", 
                            comp.getOrderId(), e);
                }
            }
        } finally {
            distributedLock.unlock("order_timeout_compensate");
        }
    }

    /**
     * 消息体定义
     */
    @Data
    public static class OrderTimeoutMessage {
        private String messageId;
        private String orderId;
        private String userId;
        private long createTime;
        private long expireTime;
    }

    private String formatTime(long timestamp) {
        return new SimpleDateFormat("yyyy-MM-dd HH:mm:ss").format(new Date(timestamp));
    }

    private String generateMessageId() {
        return "OT-" + UUID.randomUUID().toString().replace("-", "");
    }
}
```

#### 7.2.4 延迟消息消费端

```java
/**
 * 订单超时取消 - 消费端
 *
 * 消费到延迟消息后执行订单取消流程
 * 核心保障：
 * 1. 状态前置校验 - 只有"待支付"状态的订单才执行取消
 * 2. 乐观锁更新 - CAS方式更新状态，防止并发操作
 * 3. 取消操作幂等 - 重复消费不会产生副作用
 */
@Component
@Slf4j
public class OrderTimeoutConsumer {

    @Autowired
    private OrderMapper orderMapper;

    @Autowired
    private InventoryService inventoryService;

    @Autowired
    private NotificationService notificationService;

    @Autowired
    private PlatformTransactionManager transactionManager;

    /**
     * 消费延迟消息
     */
    @RocketMQMessageListener(
            topic = "order-timeout-check",
            consumerGroup = "order-timeout-consumer-group",
            consumeMode = ConsumeMode.CONCURRENTLY,
            maxReconsumeTimes = 5
    )
    @Component
    public class OrderTimeoutListener implements RocketMQListener<String> {

        @Override
        public void onMessage(String messageBody) {
            OrderTimeoutMessage msg = null;
            try {
                msg = JSON.parseObject(messageBody, OrderTimeoutMessage.class);
                log.info("[订单超时消费] 收到延迟消息, orderId={}, messageId={}, " +
                                "创建时间={}, 预期触发时间={}",
                        msg.getOrderId(), msg.getMessageId(),
                        formatTime(msg.getCreateTime()),
                        formatTime(msg.getExpireTime()));

                // 执行订单超时检查与取消
                checkAndCancelOrder(msg);

            } catch (Exception e) {
                String orderId = (msg != null) ? msg.getOrderId() : "UNKNOWN";
                log.error("[订单超时消费] 处理异常, orderId={}", orderId, e);
                // 抛出异常触发RocketMQ重试机制
                throw new RuntimeException("订单超时消费处理失败, orderId=" + orderId, e);
            }
        }
    }

    /**
     * 检查订单状态并执行取消
     */
    public void checkAndCancelOrder(OrderTimeoutMessage msg) {
        String orderId = msg.getOrderId();

        // 1. 查询订单当前状态
        Order order = orderMapper.selectByOrderId(orderId);
        if (order == null) {
            log.warn("[订单超时消费] 订单不存在, orderId={}", orderId);
            return; // 不抛异常，直接消费成功
        }

        // 2. 状态校验 - 只处理"待支付"状态
        if (order.getStatus() != OrderStatus.PENDING_PAYMENT.getCode()) {
            log.info("[订单超时消费] 订单状态非待支付, 跳过取消, " +
                            "orderId={}, currentStatus={}",
                    orderId, OrderStatus.of(order.getStatus()).getDesc());
            return; // 已支付或已取消，直接消费成功
        }

        // 3. 二次时间校验 - 防止消息过早投递
        if (System.currentTimeMillis() < msg.getExpireTime()) {
            long remainMs = msg.getExpireTime() - System.currentTimeMillis();
            log.warn("[订单超时消费] 消息投递过早, orderId={}, 剩余{}ms",
                    orderId, remainMs);
            // 短暂等待后重试（如果剩余时间较短）
            if (remainMs < 5000) {
                try {
                    Thread.sleep(remainMs);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                }
            } else {
                // 剩余时间较长，抛异常触发延迟重试
                throw new RuntimeException("消息投递过早，等待重试");
            }
        }

        // 4. 执行取消流程
        doCancelOrder(order, msg);
    }

    /**
     * 执行订单取消
     * 使用乐观锁（CAS）确保并发安全
     */
    private void doCancelOrder(Order order, OrderTimeoutMessage msg) {
        String orderId = order.getOrderId();
        TransactionStatus txStatus = transactionManager.getTransaction(
                new DefaultTransactionDefinition());

        try {
            // 1. CAS更新订单状态：待支付 -> 已取消
            //    SQL: UPDATE orders SET status=CANCELLED, cancel_reason='超时未支付',
            //         update_time=NOW() WHERE order_id=? AND status=PENDING_PAYMENT
            int affected = orderMapper.cancelOrderByCas(
                    orderId,
                    OrderStatus.PENDING_PAYMENT.getCode(),
                    OrderStatus.CANCELLED.getCode(),
                    "超时未支付自动取消"
            );

            if (affected == 0) {
                // CAS失败：订单状态已变更（可能已支付或已被其他线程取消）
                log.info("[订单超时消费] CAS取消失败, 订单状态已变更, orderId={}", orderId);
                transactionManager.rollback(txStatus);
                return;
            }

            // 2. 释放库存
            List<OrderItem> items = orderMapper.selectOrderItems(orderId);
            for (OrderItem item : items) {
                inventoryService.releaseStock(item.getSkuId(), item.getQuantity(), orderId);
                log.info("[订单超时消费] 库存已释放, orderId={}, skuId={}, quantity={}",
                        orderId, item.getSkuId(), item.getQuantity());
            }

            // 3. 提交事务
            transactionManager.commit(txStatus);
            log.info("[订单超时消费] 订单取消成功, orderId={}, userId={}",
                    orderId, msg.getUserId());

            // 4. 事务提交后发送通知（异步，不影响主流程）
            try {
                notificationService.notifyOrderCancelled(
                        msg.getUserId(), orderId, "您的订单已因超时未支付自动取消");
            } catch (Exception e) {
                log.warn("[订单超时消费] 发送通知失败, orderId={}", orderId, e);
                // 通知失败不影响主流程
            }

        } catch (Exception e) {
            log.error("[订单超时消费] 取消流程异常, orderId={}", orderId, e);
            transactionManager.rollback(txStatus);
            throw e; // 抛出异常触发消息重试
        }
    }

    /**
     * 库存释放的幂等保证
     * inventoryService.releaseStock内部实现示例
     */
    @Service
    @Slf4j
    public static class InventoryService {

        /**
         * 释放库存（幂等）
         * 通过orderId + skuId作为幂等键，防止重复释放
         */
        @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED)
        public void releaseStock(String skuId, int quantity, String orderId) {
            // 1. 查询是否已释放
            StockOperationLog existLog = stockLogMapper.selectByOrderAndSku(orderId, skuId);
            if (existLog != null && existLog.getOperation().equals("RELEASE")) {
                log.info("[库存服务] 库存已释放，跳过, orderId={}, skuId={}", orderId, skuId);
                return;
            }

            // 2. 释放库存
            int affected = inventoryMapper.increaseStock(skuId, quantity);
            if (affected == 0) {
                log.error("[库存服务] 库存释放失败, skuId={}, quantity={}", skuId, quantity);
                throw new RuntimeException("库存释放失败");
            }

            // 3. 记录操作日志（幂等依据）
            StockOperationLog opLog = new StockOperationLog();
            opLog.setOrderId(orderId);
            opLog.setSkuId(skuId);
            opLog.setQuantity(quantity);
            opLog.setOperation("RELEASE");
            stockLogMapper.insert(opLog);
        }
    }
}
```

#### 7.2.5 关键设计总结

| 环节 | 风险点 | 解决方案 |
|------|--------|----------|
| 延迟消息发送 | MQ不可用，消息发不出去 | 降级写补偿表 + 定时任务兜底 |
| 延迟投递精度 | 延迟时间不精确 | 消费端二次时间校验 |
| 订单已被支付 | 到期时订单状态已变更 | 消费前状态前置校验 |
| 并发取消 | 多个消费者同时取消同一订单 | CAS乐观锁更新订单状态 |
| 库存重复释放 | 消息重试导致库存多次释放 | 操作日志表幂等控制 |
| 消费异常 | 取消流程部分失败 | 本地事务保证原子性 + 消息重试 |

### 7.3 案例三：消息堆积与消费者扩容全链路

#### 7.3.1 场景说明

大促活动期间，订单消息的生产速度远超平时，消费端处理能力不足导致消息大量堆积。核心诉求：

- **及时发现**：堆积量超过阈值时自动告警
- **动态扩容**：根据堆积量自动增加消费者实例
- **消费限流**：扩容后的消费者不能对下游造成过大压力
- **平稳恢复**：堆积消化完毕后自动缩容，恢复正常状态

解决方案：**堆积检测 -> 动态扩容消费者 -> 消费限流 -> 自动缩容恢复**

#### 7.3.2 整体链路流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                      监控检测阶段                                     │
│                                                                     │
│  堆积监控服务（每30秒执行）                                            │
│       │                                                             │
│       ▼                                                             │
│  计算Consumer Lag = Broker最新Offset - Consumer已提交Offset           │
│       │                                                             │
│       ▼                                                             │
│  Lag > 告警阈值(10000)?                                              │
│       │                                                             │
│       ├── 否 -> 检查是否需要缩容                                      │
│       │                                                             │
│       ▼ 是                                                          │
│  发送告警通知 + 计算所需消费者数量                                      │
│       │                                                             │
│       ▼                                                             │
│  触发扩容                                                            │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                      动态扩容阶段                                     │
│                                                                     │
│  1. 计算目标消费者数量（不超过Partition数）                               │
│  2. 启动新的消费者实例（线程池方式 / K8s Pod扩容）                        │
│  3. 触发Consumer Group Rebalance                                     │
│  4. 新消费者分配到Partition开始消费                                      │
│  5. 消费端启用限流（RateLimiter），保护下游服务                           │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                      消费追赶阶段                                     │
│                                                                     │
│  扩容后的消费者集群并行消费                                             │
│  限流器控制消费速率，避免下游过载                                        │
│  持续监控Lag变化趋势                                                  │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                      恢复缩容阶段                                     │
│                                                                     │
│  Lag < 缩容阈值(1000) 且持续5分钟                                     │
│       │                                                             │
│       ▼                                                             │
│  1. 逐步关闭扩容的消费者实例                                           │
│  2. 触发Rebalance，剩余消费者接管分区                                   │
│  3. 移除限流器，恢复正常消费速率                                        │
```

#### 7.3.3 堆积监控服务

```java
/**
 * 消息堆积监控服务
 *
 * 职责：
 * 1. 定时采集Consumer Lag指标
 * 2. 根据阈值判断是否需要告警/扩容/缩容
 * 3. 记录Lag历史趋势，用于判断堆积是否在收敛
 */
@Service
@Slf4j
public class ConsumerLagMonitor {

    /** 告警阈值：Lag超过10000触发告警 */
    private static final long ALERT_THRESHOLD = 10000L;

    /** 扩容阈值：Lag超过50000触发自动扩容 */
    private static final long SCALE_OUT_THRESHOLD = 50000L;

    /** 缩容阈值：Lag低于1000触发缩容评估 */
    private static final long SCALE_IN_THRESHOLD = 1000L;

    /** 缩容稳定期：Lag持续低于阈值的时间（毫秒） */
    private static final long SCALE_IN_STABLE_PERIOD_MS = 5 * 60 * 1000L;

    /** Lag历史记录，用于趋势分析 */
    private final Map<String, LinkedList<LagSnapshot>> lagHistory = new ConcurrentHashMap<>();

    @Autowired
    private AdminClient kafkaAdminClient;

    @Autowired
    private ConsumerScaler consumerScaler;

    @Autowired
    private AlertService alertService;

    /**
     * 定时监控任务 - 每30秒执行一次
     */
    @Scheduled(fixedDelay = 30000)
    public void monitorConsumerLag() {
        List<MonitorTarget> targets = getMonitorTargets();

        for (MonitorTarget target : targets) {
            try {
                monitorSingleGroup(target);
            } catch (Exception e) {
                log.error("[堆积监控] 监控异常, group={}, topic={}",
                        target.getConsumerGroup(), target.getTopic(), e);
            }
        }
    }

    /**
     * 监控单个消费组
     */
    private void monitorSingleGroup(MonitorTarget target) {
        String group = target.getConsumerGroup();
        String topic = target.getTopic();

        // 1. 计算总Lag
        long totalLag = calculateTotalLag(group, topic);
        int partitionCount = getPartitionCount(topic);
        int activeConsumerCount = getActiveConsumerCount(group);

        log.info("[堆积监控] group={}, topic={}, totalLag={}, partitions={}, consumers={}",
                group, topic, totalLag, partitionCount, activeConsumerCount);

        // 2. 记录Lag快照
        recordLagSnapshot(group, totalLag);

        // 3. 根据Lag阈值执行不同策略
        if (totalLag >= SCALE_OUT_THRESHOLD) {
            // 超过扩容阈值
            handleScaleOut(target, totalLag, partitionCount, activeConsumerCount);

        } else if (totalLag >= ALERT_THRESHOLD) {
            // 超过告警阈值但未达到扩容阈值
            handleAlert(target, totalLag, activeConsumerCount);

        } else if (totalLag < SCALE_IN_THRESHOLD) {
            // 低于缩容阈值，评估是否需要缩容
            handleScaleIn(target, totalLag, activeConsumerCount);
        }
    }

    /**
     * 计算消费组在指定Topic上的总Lag
     */
    private long calculateTotalLag(String group, String topic) {
        long totalLag = 0;

        try {
            // 获取消费组已提交的Offset
            Map<TopicPartition, OffsetAndMetadata> committedOffsets =
                    kafkaAdminClient.listConsumerGroupOffsets(group)
                            .partitionsToOffsetAndMetadata().get(5, TimeUnit.SECONDS);

            // 获取各分区的最新Offset
            Set<TopicPartition> partitions = committedOffsets.keySet().stream()
                    .filter(tp -> tp.topic().equals(topic))
                    .collect(Collectors.toSet());

            Map<TopicPartition, ListOffsetsResult.ListOffsetsResultInfo> endOffsets =
                    kafkaAdminClient.listOffsets(
                            partitions.stream().collect(Collectors.toMap(
                                    tp -> tp,
                                    tp -> OffsetSpec.latest()
                            ))
                    ).all().get(5, TimeUnit.SECONDS);

            // 计算各分区Lag并累加
            for (TopicPartition tp : partitions) {
                long committed = committedOffsets.get(tp).offset();
                long latest = endOffsets.get(tp).offset();
                long partitionLag = latest - committed;
                totalLag += Math.max(0, partitionLag);

                if (partitionLag > ALERT_THRESHOLD / partitions.size() * 2) {
                    log.warn("[堆积监控] 分区堆积严重, group={}, partition={}, lag={}",
                            group, tp.partition(), partitionLag);
                }
            }

        } catch (Exception e) {
            log.error("[堆积监控] 计算Lag失败, group={}, topic={}", group, topic, e);
            throw new RuntimeException("计算Consumer Lag失败", e);
        }

        return totalLag;
    }

    /**
     * 处理扩容逻辑
     */
    private void handleScaleOut(MonitorTarget target, long totalLag,
                                int partitionCount, int currentConsumerCount) {
        String group = target.getConsumerGroup();
        String topic = target.getTopic();

        // 消费者数量上限 = Partition数量（超过后多余的Consumer空闲）
        if (currentConsumerCount >= partitionCount) {
            log.warn("[堆积监控] 消费者数已达Partition上限, 无法继续扩容, " +
                            "group={}, consumers={}, partitions={}",
                    group, currentConsumerCount, partitionCount);
            alertService.sendAlert("消费堆积且已达扩容上限",
                    String.format("group=%s, lag=%d, 建议增加Partition数", group, totalLag));
            return;
        }

        // 计算目标消费者数量
        // 策略：基于消费速率和堆积量计算，每次最多翻倍
        int targetCount = calculateTargetConsumerCount(
                totalLag, currentConsumerCount, partitionCount, target);

        if (targetCount > currentConsumerCount) {
            log.info("[堆积监控] 触发扩容, group={}, {} -> {}, totalLag={}",
                    group, currentConsumerCount, targetCount, totalLag);

            consumerScaler.scaleOut(target, targetCount);

            alertService.sendAlert("消费堆积已触发自动扩容",
                    String.format("group=%s, lag=%d, 消费者 %d -> %d",
                            group, totalLag, currentConsumerCount, targetCount));
        }
    }

    /**
     * 计算目标消费者数量
     */
    private int calculateTargetConsumerCount(long totalLag, int currentCount,
                                             int partitionCount, MonitorTarget target) {
        // 方案1：基于Lag估算
        // 假设单Consumer每秒处理1000条，期望5分钟内消化完堆积
        long expectedConsumeRate = target.getExpectedRatePerConsumer(); // 默认1000/s
        long targetTimeSeconds = 300; // 5分钟

        int neededByLag = (int) Math.ceil(
                (double) totalLag / (expectedConsumeRate * targetTimeSeconds));

        // 方案2：简单翻倍
        int neededByDouble = currentCount * 2;

        // 取较小值，但不超过Partition数
        int targetCount = Math.min(neededByLag, neededByDouble);
        targetCount = Math.min(targetCount, partitionCount);
        targetCount = Math.max(targetCount, currentCount + 1); // 至少增加1个

        return targetCount;
    }

    /**
     * 处理告警（未达扩容阈值）
     */
    private void handleAlert(MonitorTarget target, long totalLag, int currentConsumerCount) {
        // 检查Lag趋势：如果持续增长则提前告警
        LagTrend trend = analyzeLagTrend(target.getConsumerGroup());

        String message = String.format("group=%s, lag=%d, consumers=%d, 趋势=%s",
                target.getConsumerGroup(), totalLag, currentConsumerCount, trend);

        if (trend == LagTrend.INCREASING) {
            log.warn("[堆积监控] Lag持续增长, {}", message);
            alertService.sendAlert("消费堆积持续增长", message);
        } else {
            log.info("[堆积监控] Lag超过告警阈值但趋势收敛, {}", message);
        }
    }

    /**
     * 处理缩容评估
     */
    private void handleScaleIn(MonitorTarget target, long totalLag, int currentConsumerCount) {
        int baseCount = target.getBaseConsumerCount(); // 基准消费者数量

        if (currentConsumerCount <= baseCount) {
            return; // 已经是基准数量，不需要缩容
        }

        // 检查Lag是否持续低于阈值（稳定期）
        boolean stable = isLagStableBelow(target.getConsumerGroup(), 
                SCALE_IN_THRESHOLD, SCALE_IN_STABLE_PERIOD_MS);

        if (stable) {
            log.info("[堆积监控] Lag持续低位，触发缩容, group={}, {} -> {}, totalLag={}",
                    target.getConsumerGroup(), currentConsumerCount, baseCount, totalLag);
            consumerScaler.scaleIn(target, baseCount);

            alertService.sendAlert("消费堆积已消化，自动缩容",
                    String.format("group=%s, lag=%d, 消费者 %d -> %d",
                            target.getConsumerGroup(), totalLag, currentConsumerCount, baseCount));
        }
    }

    /**
     * 记录Lag快照
     */
    private void recordLagSnapshot(String group, long totalLag) {
        lagHistory.computeIfAbsent(group, k -> new LinkedList<>())
                .addLast(new LagSnapshot(System.currentTimeMillis(), totalLag));

        // 只保留最近30分钟的记录
        LinkedList<LagSnapshot> snapshots = lagHistory.get(group);
        long threshold = System.currentTimeMillis() - 30 * 60 * 1000L;
        while (!snapshots.isEmpty() && snapshots.peekFirst().getTimestamp() < threshold) {
            snapshots.pollFirst();
        }
    }

    /**
     * 分析Lag趋势
     */
    private LagTrend analyzeLagTrend(String group) {
        LinkedList<LagSnapshot> snapshots = lagHistory.getOrDefault(group, new LinkedList<>());

        if (snapshots.size() < 3) {
            return LagTrend.UNKNOWN;
        }

        // 取最近5个快照进行趋势判断
        List<LagSnapshot> recent = new ArrayList<>(snapshots.subList(
                Math.max(0, snapshots.size() - 5), snapshots.size()));

        int increasingCount = 0;
        for (int i = 1; i < recent.size(); i++) {
            if (recent.get(i).getLag() > recent.get(i - 1).getLag()) {
                increasingCount++;
            }
        }

        if (increasingCount >= recent.size() - 1) {
            return LagTrend.INCREASING;
        } else if (increasingCount == 0) {
            return LagTrend.DECREASING;
        }
        return LagTrend.FLUCTUATING;
    }

    /**
     * 检查Lag是否持续低于阈值
     */
    private boolean isLagStableBelow(String group, long threshold, long stablePeriodMs) {
        LinkedList<LagSnapshot> snapshots = lagHistory.getOrDefault(group, new LinkedList<>());
        if (snapshots.isEmpty()) return false;

        long now = System.currentTimeMillis();
        long periodStart = now - stablePeriodMs;

        return snapshots.stream()
                .filter(s -> s.getTimestamp() >= periodStart)
                .allMatch(s -> s.getLag() < threshold)
                && snapshots.getLast().getTimestamp() >= periodStart;
    }

    @Data
    @AllArgsConstructor
    public static class LagSnapshot {
        private long timestamp;
        private long lag;
    }

    public enum LagTrend {
        INCREASING, DECREASING, FLUCTUATING, UNKNOWN
    }
}
```

#### 7.3.4 消费者动态扩缩容服务

```java
/**
 * 消费者动态扩缩容服务
 *
 * 支持两种扩缩容模式：
 * 1. 线程池模式 - 在单JVM内通过增减消费线程实现（适合中小规模）
 * 2. K8s模式 - 通过调整Deployment副本数实现（适合云原生场景）
 */
@Service
@Slf4j
public class ConsumerScaler {

    /** 已启动的扩容消费线程 */
    private final Map<String, List<ScalableConsumerThread>> scaledConsumers =
            new ConcurrentHashMap<>();

    @Autowired(required = false)
    private KubernetesClient k8sClient;

    /**
     * 扩容 - 线程池模式
     * 在当前JVM中启动新的消费线程
     */
    public void scaleOut(MonitorTarget target, int targetCount) {
        String group = target.getConsumerGroup();
        String topic = target.getTopic();
        int currentCount = getActiveConsumerCount(group);

        if (targetCount <= currentCount) {
            log.info("[消费者扩容] 目标数量不大于当前数量, 跳过, group={}", group);
            return;
        }

        int addCount = targetCount - currentCount;
        log.info("[消费者扩容] 开始扩容, group={}, 新增{}个消费者", group, addCount);

        List<ScalableConsumerThread> newConsumers =
                scaledConsumers.computeIfAbsent(group, k -> new CopyOnWriteArrayList<>());

        for (int i = 0; i < addCount; i++) {
            try {
                ScalableConsumerThread consumer = new ScalableConsumerThread(
                        group, topic, target.getRateLimitPerSecond());
                consumer.start();
                newConsumers.add(consumer);
                log.info("[消费者扩容] 新消费者已启动, group={}, threadName={}",
                        group, consumer.getName());
            } catch (Exception e) {
                log.error("[消费者扩容] 启动消费者失败, group={}", group, e);
            }
        }
    }

    /**
     * 缩容 - 优雅关闭扩容的消费线程
     */
    public void scaleIn(MonitorTarget target, int targetCount) {
        String group = target.getConsumerGroup();
        List<ScalableConsumerThread> consumers = scaledConsumers.get(group);

        if (consumers == null || consumers.isEmpty()) {
            log.info("[消费者缩容] 无扩容消费者需要关闭, group={}", group);
            return;
        }

        int removeCount = consumers.size();
        log.info("[消费者缩容] 开始缩容, group={}, 关闭{}个扩容消费者", group, removeCount);

        // 逐个优雅关闭
        Iterator<ScalableConsumerThread> iterator = consumers.iterator();
        while (iterator.hasNext()) {
            ScalableConsumerThread consumer = iterator.next();
            try {
                consumer.shutdown();
                log.info("[消费者缩容] 消费者已关闭, group={}, threadName={}",
                        group, consumer.getName());
            } catch (Exception e) {
                log.error("[消费者缩容] 关闭消费者异常, group={}", group, e);
            }
            iterator.remove();
        }
    }

    /**
     * 扩容 - K8s模式
     * 通过调整Deployment副本数实现Pod级别的扩缩容
     */
    public void scaleOutByK8s(MonitorTarget target, int targetCount) {
        if (k8sClient == null) {
            log.warn("[K8s扩容] K8s客户端不可用，降级为线程池模式");
            scaleOut(target, targetCount);
            return;
        }

        String deploymentName = target.getK8sDeploymentName();
        String namespace = target.getK8sNamespace();

        try {
            k8sClient.apps().deployments()
                    .inNamespace(namespace)
                    .withName(deploymentName)
                    .scale(targetCount);

            log.info("[K8s扩容] Deployment已扩容, deployment={}, replicas={}",
                    deploymentName, targetCount);
        } catch (Exception e) {
            log.error("[K8s扩容] 扩容失败, deployment={}", deploymentName, e);
            // 降级为线程池模式
            scaleOut(target, targetCount);
        }
    }
}
```

#### 7.3.5 带限流的可扩缩消费线程

```java
/**
 * 可动态扩缩的消费线程
 *
 * 特性：
 * 1. 独立的KafkaConsumer实例，加入同一Consumer Group触发Rebalance
 * 2. 内置RateLimiter限流，保护下游服务
 * 3. 支持优雅关闭，关闭前提交Offset
 */
@Slf4j
public class ScalableConsumerThread extends Thread {

    private final String consumerGroup;
    private final String topic;
    private final AtomicBoolean running = new AtomicBoolean(true);
    private final RateLimiter rateLimiter;
    private KafkaConsumer<String, String> consumer;

    /** 限流统计 */
    private final AtomicLong totalConsumed = new AtomicLong(0);
    private final AtomicLong totalThrottled = new AtomicLong(0);

    public ScalableConsumerThread(String consumerGroup, String topic,
                                  int rateLimitPerSecond) {
        this.consumerGroup = consumerGroup;
        this.topic = topic;
        this.rateLimiter = RateLimiter.create(rateLimitPerSecond);
        setName("scalable-consumer-" + consumerGroup + "-" + 
                System.currentTimeMillis() % 10000);
        setDaemon(true);
    }

    @Override
    public void run() {
        initConsumer();
        log.info("[扩容消费者] 启动, group={}, topic={}, 限流={}条/秒",
                consumerGroup, topic, rateLimiter.getRate());

        try {
            while (running.get()) {
                try {
                    ConsumerRecords<String, String> records =
                            consumer.poll(Duration.ofMillis(500));

                    if (records.isEmpty()) {
                        continue;
                    }

                    for (ConsumerRecord<String, String> record : records) {
                        if (!running.get()) {
                            break;
                        }

                        // 限流：等待令牌
                        double waitSeconds = rateLimiter.acquire();
                        if (waitSeconds > 0.01) {
                            totalThrottled.incrementAndGet();
                        }

                        try {
                            // 处理消息
                            processRecord(record);
                            totalConsumed.incrementAndGet();
                        } catch (Exception e) {
                            log.error("[扩容消费者] 消费异常, topic={}, partition={}, offset={}",
                                    record.topic(), record.partition(), record.offset(), e);
                            // 消费失败不中断循环，继续处理下一条
                        }
                    }

                    // 批量提交Offset
                    consumer.commitAsync((offsets, exception) -> {
                        if (exception != null) {
                            log.error("[扩容消费者] Offset提交失败", exception);
                        }
                    });

                    // 定期输出消费统计
                    if (totalConsumed.get() % 1000 == 0 && totalConsumed.get() > 0) {
                        log.info("[扩容消费者] 消费统计, thread={}, 已消费={}, 被限流次数={}",
                                getName(), totalConsumed.get(), totalThrottled.get());
                    }

                } catch (WakeupException e) {
                    if (running.get()) {
                        log.error("[扩容消费者] 非预期的WakeupException", e);
                    }
                }
            }
        } finally {
            closeConsumer();
        }
    }

    /**
     * 初始化KafkaConsumer
     */
    private void initConsumer() {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-broker:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, consumerGroup);
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class.getName());
        // 扩容消费者的特殊配置
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, "200");    // 每次少拉一些
        props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, "60000"); // 60秒处理超时
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");   // 手动提交
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "latest");   // 从最新开始

        consumer = new KafkaConsumer<>(props);
        consumer.subscribe(Collections.singletonList(topic));
    }

    /**
     * 处理单条消息
     */
    private void processRecord(ConsumerRecord<String, String> record) {
        // 具体业务处理逻辑由子类实现或通过策略模式注入
        log.debug("[扩容消费者] 处理消息, partition={}, offset={}, key={}",
                record.partition(), record.offset(), record.key());
        // ... 业务处理 ...
    }

    /**
     * 优雅关闭
     */
    public void shutdown() {
        log.info("[扩容消费者] 开始优雅关闭, thread={}, 已消费={}",
                getName(), totalConsumed.get());
        running.set(false);
        consumer.wakeup(); // 中断poll阻塞

        try {
            this.join(10000); // 等待最多10秒
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    /**
     * 关闭Consumer，提交最后的Offset
     */
    private void closeConsumer() {
        try {
            consumer.commitSync(Duration.ofSeconds(5));
            log.info("[扩容消费者] 最终Offset已提交, thread={}", getName());
        } catch (Exception e) {
            log.error("[扩容消费者] 最终Offset提交失败, thread={}", getName(), e);
        } finally {
            consumer.close(Duration.ofSeconds(5));
            log.info("[扩容消费者] 已关闭, thread={}, 总消费={}, 总限流={}",
                    getName(), totalConsumed.get(), totalThrottled.get());
        }
    }

    /**
     * 动态调整限流速率
     * 在堆积消化过程中可根据下游系统负载动态调整
     */
    public void adjustRateLimit(int newRatePerSecond) {
        double oldRate = rateLimiter.getRate();
        rateLimiter.setRate(newRatePerSecond);
        log.info("[扩容消费者] 限流速率调整, thread={}, {} -> {} 条/秒",
                getName(), oldRate, newRatePerSecond);
    }
}
```

#### 7.3.6 关键设计总结

| 环节 | 风险点 | 解决方案 |
|------|--------|----------|
| 堆积检测 | 监控服务自身故障导致漏检 | 多实例部署 + 分布式锁轮转 + 独立告警 |
| Lag计算 | 多分区Lag不均匀 | 按分区粒度计算，单分区异常也告警 |
| 自动扩容 | 扩容过多导致Rebalance风暴 | 每次最多翻倍 + 上限不超过Partition数 |
| 消费限流 | 扩容后下游服务被打垮 | RateLimiter令牌桶限流 + 动态调速 |
| 自动缩容 | 缩容后堆积又起来 | 稳定期观察5分钟 + 逐步缩容 |
| 优雅关闭 | 缩容时消息丢失或重复 | 关闭前同步提交Offset + 等待处理完成 |
