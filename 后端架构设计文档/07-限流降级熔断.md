## 1. 问题背景

### 1.1 核心问题

在分布式微服务架构中，服务之间存在复杂的依赖关系。一个上层服务可能依赖多个下游服务，而下游服务又可能依赖更多的服务，形成深层次的调用链路。当调用链路中某个服务出现故障或响应变慢时，如果不加以保护，故障会沿着调用链路向上传播，引发连锁反应，最终导致整个系统不可用。这种现象被称为"雪崩效应"（Cascading Failure）。

雪崩效应的典型演进过程如下：

```
1. ServiceD 因负载过高响应变慢（如响应时间从50ms上升到5s）
2. ServiceA 调用 ServiceD 的线程被长时间阻塞
3. ServiceA 的线程池被耗尽，无法处理新的请求
4. ServiceA 整体不可用，调用 ServiceA 的上游服务也开始超时
5. 故障逐级传播，整个调用链路崩溃
```

### 1.2 常见触发场景

以下是引发系统过载或雪崩的典型场景：

1. **流量突增**：大促活动、秒杀场景、热点事件导致请求量瞬间激增，远超系统承载能力。例如平时QPS为1000的服务，在大促期间可能面临10万QPS的冲击。

2. **下游服务故障**：依赖的数据库、缓存或第三方服务出现网络抖动、慢查询、连接池耗尽等问题，导致请求处理变慢。

3. **资源竞争**：服务内部不同业务模块共享线程池、连接池等资源，某个模块的异常消耗大量资源，影响其他正常模块的运行。

4. **机器异常**：集群中某台机器因CPU飙升、Full GC频繁、磁盘满等原因导致性能骤降，负载均衡仍将流量分发到该机器。

5. **级联调用放大**：一次外部请求在内部扇出为多次服务调用，若每次调用都有重试机制，实际内部调用量可能呈指数级放大。

### 1.3 不解决的后果

如果不引入限流、降级、熔断等保护机制，系统将面临以下严重后果：

- **系统雪崩**：一个服务的故障扩散到整个系统，造成大面积服务不可用，恢复时间可能长达数小时。
- **资源耗尽**：线程池、连接池、内存等关键资源被耗尽，正常请求无法得到处理。
- **用户体验恶化**：用户请求长时间无响应，超时后返回错误，严重影响用户体验和业务收入。
- **故障恢复困难**：系统过载后，即使重启也可能因瞬时流量再次被打垮，形成"重启-过载-再重启"的恶性循环。
- **运维成本高昂**：频繁的人工介入处理故障，运维人员疲于奔命，无法进行有效的容量规划和系统优化。

### 1.4 解决思路

针对上述问题，业界发展出了三大核心服务保护手段：

| 手段 | 核心思想 | 作用层面 | 触发时机 |
|------|---------|---------|---------|
| **限流** | 控制进入系统的请求速率，拒绝超出容量的请求 | 入口防护 | 流量超过阈值时 |
| **熔断** | 当下游服务异常率过高时，快速失败不再调用下游 | 调用链防护 | 错误率/慢调用率达到阈值时 |
| **降级** | 主动放弃部分非核心功能，保障核心业务可用 | 业务逻辑层 | 资源紧张或依赖不可用时 |

三者协同工作，构成分布式系统的稳定性保障体系：限流是第一道屏障，防止系统被过量流量压垮；熔断是第二道屏障，防止下游故障蔓延到上游；降级是第三道屏障，通过牺牲局部保障整体。

### 2.2 各组件职责

**接入层**：提供多种接入方式，降低使用门槛。注解方式通过AOP拦截方法调用，零代码侵入；API方式提供最大灵活性，业务代码显式调用限流/熔断方法；框架接入方式由RPC框架、HTTP框架在内部自动集成，业务方只需配置规则；网关接入方式在流量入口处统一管控。

**规则管理层**：负责限流、熔断、降级规则的存储、推送和动态生效。规则通过配置中心集中管理，支持动态修改、灰度发布。SDK端维护本地缓存，当配置中心不可用时降级使用本地缓存的规则，保证可用性。

**核心引擎层**：系统的心脏，包含三大引擎和隔离机制。限流引擎实现多种限流算法，支持单机和集群两种模式；熔断引擎实现三态状态机，管理熔断器的开启、探测和恢复；降级引擎提供多种降级策略路由和兜底执行；隔离机制通过线程池或信号量实现资源隔离，防止故障扩散。

**数据存储层**：单机限流使用本地内存（如Guava令牌桶），无网络开销；集群限流1.0基于Redis原子计数实现，利用Lua脚本保证原子性；集群限流2.0基于自建限流服务器，通过长连接减少网络开销。

**监控告警层**：实时采集限流通过/拒绝量、熔断状态变更、降级执行次数等指标，通过时序数据库存储，支持大盘展示和告警通知。

### 2.3 设计权衡

| 设计决策 | 选择 | 理由 |
|---------|------|------|
| 单机限流 vs 集群限流 | 两者都支持 | 单机限流无网络开销，适合入口总限流；集群限流精确控制总量，适合AppKey维度限频 |
| 推模式 vs 拉模式规则 | 推模式为主 | 实时性要求高，规则变更需秒级生效；同时维护本地缓存作为兜底 |
| 令牌桶 vs 漏桶 | 默认令牌桶 | 令牌桶允许突发流量，更符合实际业务场景；漏桶适合需要严格匀速的场景 |
| 线程池隔离 vs 信号量隔离 | 两者都支持 | 线程池隔离更彻底但有线程切换开销；信号量隔离轻量但无法异步 |
| 同步限流 vs 异步限流 | 同步为主 | 大多数场景同步限流足够；异步限流适用于对延迟极度敏感且允许批量处理的场景 |

## 3. 核心链路设计

### 3.1 限流算法体系

限流算法是限流引擎的基础。根据搜索结果和实践经验，主流限流算法包括四种：固定窗口（计数器）算法、滑动窗口算法、漏桶算法和令牌桶算法。每种算法有其适用场景和优缺点。

#### 3.1.1 固定窗口算法（计数器算法）

**算法原理**：将时间划分为固定大小的窗口（如1秒），每个窗口维护一个计数器。请求到来时，如果当前窗口计数器值小于阈值，则允许通过并计数器加1；否则拒绝。窗口结束时计数器清零。

**设计模式**：该算法本质上是一个简单的状态机，状态只有"允许"和"拒绝"两种，转换条件是计数器值是否达到阈值。

**实现思路**：

```java
public class FixedWindowRateLimiter {

    /** 限流阈值 */
    private final long threshold;

    /** 时间窗口大小（毫秒） */
    private final long windowSizeInMillis;

    /** 当前窗口的起始时间 */
    private long windowStartTime;

    /** 当前窗口内的请求计数 */
    private long count = 0;

    public FixedWindowRateLimiter(long threshold, long windowSizeInMillis) {
        this.threshold = threshold;
        this.windowSizeInMillis = windowSizeInMillis;
        this.windowStartTime = System.currentTimeMillis();
    }

    /**
     * 尝试获取许可
     * 使用synchronized保证线程安全
     */
    public synchronized boolean tryAcquire() {
        long currentTime = System.currentTimeMillis();

        // 如果当前时间已经超出了窗口范围，重置窗口
        if (currentTime - windowStartTime > windowSizeInMillis) {
            count = 0;
            windowStartTime = currentTime;
        }

        // 如果当前计数小于阈值，允许通过并计数
        if (count < threshold) {
            count++;
            return true;
        }

        // 超过阈值，拒绝
        return false;
    }
}
```

**临界问题分析**：固定窗口算法存在一个经典缺陷——临界问题。假设限流阈值为5次/秒，如果在0.8s-1.0s内来了5个请求，在1.0s-1.2s内又来了5个请求，虽然两个窗口内都没有超过阈值，但在0.8s-1.2s这0.4秒内实际通过了10个请求，是阈值的2倍。

```
时间轴:
  0s        0.8s    1.0s    1.2s        2s
  |----------|-------|-------|------------|
  窗口1: 5个请求 --->|       窗口2: 5个请求 --->|
                    |
              临界区域(0.8s-1.2s)实际10个请求!
```

**适用场景**：对精度要求不高的场景，如粗粒度的入口总限流。优点是实现简单、内存开销小。

#### 3.1.2 滑动窗口算法

**算法原理**：滑动窗口算法是对固定窗口算法的改进。它将一个大窗口划分为多个小窗口（格子），每个小窗口独立计数。随着时间推移，窗口整体向前滑动，过期的小窗口被移除，新的小窗口被加入。限流判断时，统计当前大窗口内所有有效小窗口的计数总和，与阈值比较。

**设计模式**：滑动窗口使用的是**环形缓冲区模式**（Ring Buffer Pattern）。通过一个固定大小的数组循环复用，避免频繁创建和销毁对象。

**实现思路**：

```java
public class SlidingWindowRateLimiter {

    /** 限流阈值 */
    private final long threshold;

    /** 窗口总大小（毫秒） */
    private final long windowSizeInMillis;

    /** 将窗口划分为多少个小格子 */
    private final int sampleCount;

    /** 每个小格子的时间跨度 */
    private final long intervalLengthMillis;

    /** 每个小格子的计数 */
    private final long[] counts;

    /** 每个小格子的开始时间 */
    private final long[] startTimes;

    public SlidingWindowRateLimiter(long threshold, long windowSizeInMillis, int sampleCount) {
        this.threshold = threshold;
        this.windowSizeInMillis = windowSizeInMillis;
        this.sampleCount = sampleCount;
        this.intervalLengthMillis = windowSizeInMillis / sampleCount;
        this.counts = new long[sampleCount];
        this.startTimes = new long[sampleCount];
        long currentTime = System.currentTimeMillis();
        for (int i = 0; i < sampleCount; i++) {
            startTimes[i] = currentTime;
        }
    }

    /**
     * 尝试获取许可
     * 核心思路：
     * 1. 计算当前时间属于哪个格子
     * 2. 检查并更新过期的格子
     * 3. 统计有效窗口内的总请求数
     * 4. 判断是否超过阈值
     */
    public synchronized boolean tryAcquire() {
        long currentTime = System.currentTimeMillis();

        // 计算当前时间应该落在哪个格子
        int currentIndex = (int) ((currentTime / intervalLengthMillis) % sampleCount);

        // 如果当前格子的时间已过期，重置该格子
        if (currentTime - startTimes[currentIndex] >= windowSizeInMillis) {
            counts[currentIndex] = 0;
            startTimes[currentIndex] = currentTime;
        }

        // 统计有效窗口内的总请求数
        long totalCount = 0;
        for (int i = 0; i < sampleCount; i++) {
            // 只统计在有效时间范围内的格子
            if (currentTime - startTimes[i] < windowSizeInMillis) {
                totalCount += counts[i];
            }
        }

        // 判断是否超过阈值
        if (totalCount < threshold) {
            counts[currentIndex]++;
            return true;
        }

        return false;
    }

    /**
     * 获取当前窗口的统计信息（用于监控）
     */
    public WindowStat getStat() {
        long currentTime = System.currentTimeMillis();
        long total = 0;
        for (int i = 0; i < sampleCount; i++) {
            if (currentTime - startTimes[i] < windowSizeInMillis) {
                total += counts[i];
            }
        }
        return new WindowStat(total, threshold, windowSizeInMillis, sampleCount);
    }
}
```

**滑动窗口如何解决临界问题**：以2个格子为例，窗口大小1秒，每个格子0.5秒。当时间从第一个格子滑到第二个格子时，统计的是最近1秒内的数据，而不是简单地在整秒处重置。因此即使0.8s-1.0s有5个请求，1.0s-1.2s再来5个请求时，由于前5个请求仍在有效窗口内，总计已达5个，后续请求会被拒绝。

**Sentinel的滑动窗口优化**：Sentinel框架使用了LeapArray数据结构来实现滑动窗口。它通过CAS操作实现无锁并发统计，减少了线程竞争。LeapArray的核心是一个AtomicReference数组，每个元素包装了一个WindowWrap对象，包含窗口起始时间和统计数据。

```java
/**
 * Sentinel风格的LeapArray滑动窗口实现
 * 使用CAS保证并发安全，避免synchronized的性能开销
 */
public class LeapArray<T> {

    /** 窗口总时间跨度 */
    private final int intervalInMs;

    /** 采样窗口数 */
    private final int sampleCount;

    /** 每个采样窗口的时间长度 */
    private final int windowLengthInMs;

    /** 使用AtomicReferenceArray存储窗口数据 */
    private final AtomicReferenceArray<WindowWrap<T>> array;

    public LeapArray(int sampleCount, int intervalInMs) {
        this.sampleCount = sampleCount;
        this.intervalInMs = intervalInMs;
        this.windowLengthInMs = intervalInMs / sampleCount;
        this.array = new AtomicReferenceArray<>(sampleCount);
    }

    /**
     * 计算当前时间对应的窗口索引
     */
    private int calculateTimeIdx(long timeMillis) {
        long timeId = timeMillis / windowLengthInMs;
        return (int) (timeId % array.length());
    }

    /**
     * 计算窗口的起始时间
     */
    private long calculateWindowStart(long timeMillis) {
        return timeMillis - timeMillis % windowLengthInMs;
    }

    /**
     * 获取当前时间对应的窗口
     * 使用CAS更新，避免锁竞争
     */
    public WindowWrap<T> currentWindow(long timeMillis) {
        int idx = calculateTimeIdx(timeMillis);
        long windowStart = calculateWindowStart(timeMillis);

        while (true) {
            WindowWrap<T> old = array.get(idx);
            if (old == null) {
                // 窗口尚未初始化，创建新窗口
                WindowWrap<T> window = new WindowWrap<>(windowLengthInMs, windowStart, newEmptyValue());
                if (array.compareAndSet(idx, null, window)) {
                    return window;
                } else {
                    // CAS失败，重试
                    Thread.yield();
                }
            } else if (windowStart == old.windowStart()) {
                // 窗口时间匹配，直接返回
                return old;
            } else if (windowStart > old.windowStart()) {
                // 窗口已过期，需要更新
                if (updateLock.compareAndSet(false, true)) {
                    try {
                        // 重置过期窗口的数据
                        old.resetTo(windowStart);
                        return old;
                    } finally {
                        updateLock.set(false);
                    }
                } else {
                    Thread.yield();
                }
            }
        }
    }

    /**
     * 统计有效窗口内的数据
     */
    public List<WindowWrap<T>> list() {
        int size = array.length();
        List<WindowWrap<T>> result = new ArrayList<>(size);
        for (int i = 0; i < size; i++) {
            WindowWrap<T> windowWrap = array.get(i);
            if (windowWrap == null || isWindowDeprecated(windowWrap)) {
                continue;
            }
            result.add(windowWrap);
        }
        return result;
    }

    private boolean isWindowDeprecated(WindowWrap<T> windowWrap) {
        return System.currentTimeMillis() - windowWrap.windowStart() > intervalInMs;
    }

    protected T newEmptyValue() {
        // 返回新的统计对象
        return (T) new SimpleStatistics();
    }
}
```

#### 3.1.3 漏桶算法

**算法原理**：漏桶算法将请求比作水，桶的容量有限，水以固定速率从桶底漏出。请求到来时倒入桶中，如果桶未满则等待处理；如果桶已满则直接溢出（拒绝）。漏桶算法的核心特点是**匀速处理**，无论请求多么突发，输出速率始终恒定。

**设计模式**：漏桶算法使用的是**生产者-消费者模式**，请求是生产者，固定速率的处理逻辑是消费者。桶本身是一个有界缓冲队列。

**实现思路**：

```java
public class LeakyBucketRateLimiter {

    /** 桶的容量 */
    private final int capacity;

    /** 漏出速率（每秒处理的请求数） */
    private final double leakRatePerSecond;

    /** 当前桶中的水量 */
    private double water = 0;

    /** 上次漏水时间 */
    private long lastLeakTime;

    public LeakyBucketRateLimiter(int capacity, double leakRatePerSecond) {
        this.capacity = capacity;
        this.leakRatePerSecond = leakRatePerSecond;
        this.lastLeakTime = System.currentTimeMillis();
    }

    /**
     * 尝试将请求放入漏桶
     * 
     * 核心步骤：
     * 1. 计算自上次漏水以来应该漏出的水量
     * 2. 更新当前水量
     * 3. 判断桶是否有空间容纳新请求
     */
    public synchronized boolean tryAcquire() {
        long currentTime = System.currentTimeMillis();

        // 计算自上次漏水以来经过的时间（秒）
        double elapsedTime = (currentTime - lastLeakTime) / 1000.0;

        // 计算这段时间内应该漏出的水量
        double leakedWater = elapsedTime * leakRatePerSecond;

        // 更新当前水量（不能小于0）
        water = Math.max(0, water - leakedWater);

        // 更新漏水时间
        lastLeakTime = currentTime;

        // 判断桶是否有空间
        if (water < capacity) {
            water += 1;
            return true;
        }

        // 桶已满，拒绝
        return false;
    }
}
```

**适用场景**：需要严格匀速处理请求的场景，如消息队列消费限流、第三方API调用限流（对方有严格的QPS限制）。

#### 3.1.4 令牌桶算法

**算法原理**：令牌桶算法是实际应用最广泛的限流算法。系统以固定速率向令牌桶中放入令牌，桶有最大容量限制，满了则丢弃多余令牌。请求到来时需要从桶中获取令牌，获取到则处理，获取不到则拒绝或等待。令牌桶算法的关键特性是**允许突发流量**——当桶中积累了一定令牌时，可以应对短时间的流量突增。

**设计模式**：令牌桶算法使用的是**令牌预取模式**和**懒计算模式**。不需要真正的后台线程不断放令牌，而是在每次请求时计算从上次到现在的应放令牌数，这种惰性计算大幅减少了资源消耗。

**实现思路**（基于Guava RateLimiter原理）：

```java
public class TokenBucketRateLimiter {

    /** 令牌放入速率（每秒放入的令牌数） */
    private final long tokenRatePerSecond;

    /** 令牌桶最大容量 */
    private final long capacity;

    /** 当前桶中的令牌数 */
    private double currentTokens;

    /** 上次令牌补充时间 */
    private long lastRefillTime;

    public TokenBucketRateLimiter(long capacity, long tokenRatePerSecond) {
        this.capacity = capacity;
        this.tokenRatePerSecond = tokenRatePerSecond;
        // 初始化时桶满
        this.currentTokens = capacity;
        this.lastRefillTime = System.currentTimeMillis();
    }

    /**
     * 尝试获取一个令牌
     * 
     * 核心步骤：
     * 1. 懒计算：根据时间差补充令牌
     * 2. 判断令牌是否足够
     * 3. 消耗令牌
     */
    public synchronized boolean tryAcquire() {
        return tryAcquire(1);
    }

    /**
     * 尝试获取多个令牌（批量场景）
     */
    public synchronized boolean tryAcquire(int tokens) {
        long currentTime = System.currentTimeMillis();

        // 懒计算：补充从上次到现在的令牌
        long elapsedTime = currentTime - lastRefillTime;
        double newTokens = (elapsedTime / 1000.0) * tokenRatePerSecond;

        // 更新令牌数（不超过容量上限）
        currentTokens = Math.min(capacity, currentTokens + newTokens);
        lastRefillTime = currentTime;

        // 判断令牌是否足够
        if (currentTokens >= tokens) {
            currentTokens -= tokens;
            return true;
        }

        return false;
    }

    /**
     * 获取需要等待的时间（毫秒）
     * 用于有等待场景的限流
     */
    public synchronized long getWaitTimeMillis(int tokens) {
        long currentTime = System.currentTimeMillis();
        long elapsedTime = currentTime - lastRefillTime;
        double newTokens = (elapsedTime / 1000.0) * tokenRatePerSecond;
        currentTokens = Math.min(capacity, currentTokens + newTokens);
        lastRefillTime = currentTime;

        if (currentTokens >= tokens) {
            currentTokens -= tokens;
            return 0;
        }

        // 计算需要等待多久才能积累足够的令牌
        double needTokens = tokens - currentTokens;
        return (long) Math.ceil(needTokens / tokenRatePerSecond * 1000);
    }
}
```

**Guava RateLimiter的平滑突发限流（SmoothBursty）**：Guava的RateLimiter在标准令牌桶基础上做了优化。它引入了"预存令牌"的概念，默认存储1秒钟的令牌量用于应对突发流量。同时使用storedPermits和nextFreeTicketMicros两个关键变量，实现了无需后台线程的精确令牌计算。

```java
/**
 * Guava风格平滑突发限流器
 * 核心改进：
 * 1. 支持预消费（先发令牌后等待）
 * 2. 平滑处理突发流量
 * 3. 无锁设计（使用synchronized但逻辑极轻）
 */
public class SmoothBurstyRateLimiter {

    /** 令牌放入速率（每微秒放入的令牌数） */
    private final double permitsPerMicrosecond;

    /** 最大存储的预存令牌数 */
    private final double maxBurstSeconds;

    /** 当前存储的令牌数 */
    private double storedPermits;

    /** 下一个令牌可以发放的时间（微秒） */
    private long nextFreeTicketMicros;

    public SmoothBurstyRateLimiter(double permitsPerSecond, double maxBurstSeconds) {
        this.permitsPerMicrosecond = permitsPerSecond / 1_000_000.0;
        this.maxBurstSeconds = maxBurstSeconds;
        this.storedPermits = 0;
        this.nextFreeTicketMicros = System.nanoTime() / 1000;
    }

    /**
     * 核心方法：获取令牌，如果需要则等待
     */
    public void acquire(int permits) throws InterruptedException {
        long waitMicros = reserve(permits);
        if (waitMicros > 0) {
            Thread.sleep(waitMicros / 1000, (int) (waitMicros % 1000) * 1000);
        }
    }

    /**
     * 预约令牌
     * 关键设计：预消费模式
     * - 如果有存储的令牌，立即消费
     * - 如果不够，记录需要等待的时间
     * - 下一个请求的等待时间会累积
     */
    private synchronized long reserve(int permits) {
        long nowMicros = System.nanoTime() / 1000;
        resync(nowMicros);

        long momentAvailable = nextFreeTicketMicros;
        double storedPermitsToSpend = Math.min(permits, this.storedPermits);
        double freshPermits = permits - storedPermitsToSpend;

        // 存储令牌立即可用，新令牌需要等待
        long waitMicros = (long) (freshPermits / permitsPerMicrosecond);

        // 更新状态
        this.storedPermits -= storedPermitsToSpend;
        this.nextFreeTicketMicros = momentAvailable + waitMicros;

        return Math.max(0, momentAvailable - nowMicros);
    }

    /**
     * 同步令牌状态
     * 懒计算核心：根据时间差补充令牌
     */
    private void resync(long nowMicros) {
        if (nowMicros > nextFreeTicketMicros) {
            double newPermits = (nowMicros - nextFreeTicketMicros) * permitsPerMicrosecond;
            this.storedPermits = Math.min(maxBurstSeconds / permitsPerMicrosecond, 
                                          this.storedPermits + newPermits);
            this.nextFreeTicketMicros = nowMicros;
        }
    }
}
```

#### 3.2.2 限流器工厂与规则管理

**设计模式**：使用**工厂模式**创建限流器实例，**策略模式**根据配置选择不同的限流算法，**观察者模式**监听规则变更并更新限流器。

```java
/**
 * 限流器工厂
 * 负责根据规则创建和管理限流器实例
 * 使用ConcurrentHashMap缓存限流器，避免重复创建
 */
public class RateLimiterFactory {

    /** 限流器缓存：key -> limiter */
    private final ConcurrentHashMap<String, RateLimiter> limiterCache = new ConcurrentHashMap<>();

    /** 规则管理器 */
    private final RuleManager ruleManager;

    public RateLimiterFactory(RuleManager ruleManager) {
        this.ruleManager = ruleManager;
        // 注册规则变更监听器
        this.ruleManager.addListener(this::onRuleChanged);
    }

    /**
     * 获取限流器
     * 如果缓存中不存在，则根据规则创建
     */
    public RateLimiter getLimiter(String key) {
        return limiterCache.computeIfAbsent(key, k -> {
            LimitRule rule = ruleManager.getRule(k);
            if (rule == null) {
                // 没有配置规则，返回通过所有限流的NoopLimiter
                return new NoopRateLimiter();
            }
            return createLimiter(rule);
        });
    }

    /**
     * 根据规则创建限流器
     * 策略模式：根据算法类型选择不同的限流器实现
     */
    private RateLimiter createLimiter(LimitRule rule) {
        switch (rule.getAlgorithm()) {
            case TOKEN_BUCKET:
                return new TokenBucketRateLimiter(rule.getCapacity(), rule.getRate());
            case LEAKY_BUCKET:
                return new LeakyBucketRateLimiter(rule.getCapacity(), rule.getRate());
            case SLIDING_WINDOW:
                return new SlidingWindowRateLimiter(rule.getThreshold(), 
                    rule.getWindowSize(), rule.getSampleCount());
            case FIXED_WINDOW:
                return new FixedWindowRateLimiter(rule.getThreshold(), rule.getWindowSize());
            default:
                return new TokenBucketRateLimiter(rule.getCapacity(), rule.getRate());
        }
    }

    /**
     * 规则变更回调
     * 当规则变更时，清除旧的限流器缓存
     */
    private void onRuleChanged(String key, LimitRule newRule) {
        if (newRule == null) {
            limiterCache.remove(key);
        } else {
            limiterCache.put(key, createLimiter(newRule));
        }
    }
}
```

#### 3.2.3 注解方式接入

**设计模式**：使用**模板方法模式**定义限流拦截的标准流程，**AOP代理模式**实现非侵入式接入。

```java
/**
 * 限流注解
 * 标注在方法上，声明该方法的限流规则
 */
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface RateLimit {
    /** 限流Key，用于标识限流规则 */
    String key();
    /** 限流算法，默认令牌桶 */
    LimitAlgorithm algorithm() default LimitAlgorithm.TOKEN_BUCKET;
    /** 降级方法名 */
    String fallbackMethod() default "";
    /** 限流参数，支持从方法参数中提取（如userId） */
    String paramExpression() default "";
}

/**
 * 限流AOP切面
 * 拦截标注了@RateLimit的方法调用
 */
@Aspect
@Component
public class RateLimitAspect {

    private final RateLimiterFactory limiterFactory;
    private final MeterRegistry meterRegistry;

    public RateLimitAspect(RateLimiterFactory limiterFactory, MeterRegistry meterRegistry) {
        this.limiterFactory = limiterFactory;
        this.meterRegistry = meterRegistry;
    }

    @Around("@annotation(rateLimit)")
    public Object around(ProceedingJoinPoint joinPoint, RateLimit rateLimit) throws Throwable {
        String limiterKey = rateLimit.key();

        // 如果配置了参数表达式，提取参数值作为限流维度
        // 例如 paramExpression = "#userId" 会从方法参数中提取userId
        if (!rateLimit.paramExpression().isEmpty()) {
            String paramValue = extractParam(joinPoint, rateLimit.paramExpression());
            limiterKey = limiterKey + ":" + paramValue;
        }

        // 获取限流器并尝试获取令牌
        RateLimiter limiter = limiterFactory.getLimiter(limiterKey);
        boolean acquired = limiter.tryAcquire();

        // 记录监控指标
        meterRegistry.counter("rate_limit.total", "key", limiterKey).increment();
        if (acquired) {
            meterRegistry.counter("rate_limit.pass", "key", limiterKey).increment();
        } else {
            meterRegistry.counter("rate_limit.reject", "key", limiterKey).increment();
        }

        if (!acquired) {
            // 被限流，执行降级逻辑
            return handleFallback(joinPoint, rateLimit);
        }

        // 通过限流，执行业务逻辑
        return joinPoint.proceed();
    }

    /**
     * 处理降级逻辑
     * 通过反射调用降级方法
     */
    private Object handleFallback(ProceedingJoinPoint joinPoint, RateLimit rateLimit) throws Throwable {
        if (rateLimit.fallbackMethod().isEmpty()) {
            throw new RateLimitException("Request rate limited: " + rateLimit.key());
        }

        // 通过反射获取降级方法
        MethodSignature signature = (MethodSignature) joinPoint.getSignature();
        Method fallbackMethod = signature.getDeclaringType()
            .getMethod(rateLimit.fallbackMethod(), signature.getParameterTypes());

        return fallbackMethod.invoke(joinPoint.getTarget(), joinPoint.getArgs());
    }

    /**
     * 从方法参数中提取限流维度值
     * 使用SpEL表达式解析
     */
    private String extractParam(ProceedingJoinPoint joinPoint, String expression) {
        MethodSignature signature = (MethodSignature) joinPoint.getSignature();
        EvaluationContext context = new StandardEvaluationContext();
        String[] paramNames = signature.getParameterNames();
        Object[] args = joinPoint.getArgs();
        for (int i = 0; i < paramNames.length; i++) {
            context.setVariable(paramNames[i], args[i]);
        }
        ExpressionParser parser = new SpelExpressionParser();
        return parser.parseExpression(expression).getValue(context, String.class);
    }
}
```

### 3.3 集群限流实现

#### 3.3.1 为什么需要集群限流

单机限流只能控制单台机器的流量，存在以下问题：

1. **总量不可控**：假设集群有10台机器，每台限流1000 QPS，理论上集群总量可达10000 QPS。但如果实际只需限制总量为5000 QPS，单机限流无法做到。
2. **流量不均**：负载均衡可能将更多流量分发到某些机器，导致部分机器过载而其他机器空闲。
3. **弹性伸缩问题**：当集群扩容或缩容时，单机限流阈值需要重新调整，运维成本高。

集群限流通过统一的计数中心，精确控制整个集群的流量总量。

#### 3.3.2 基于Redis的集群限流（1.0方案）

**算法选择**：固定窗口算法（Redis原子计数）和令牌桶算法（Redis Lua脚本）。

**设计模式**：使用**Lua脚本**保证Redis操作的原子性，避免多命令之间的竞态条件。

**固定窗口算法的Redis实现**：

```java
/**
 * 基于Redis的集群固定窗口限流
 * 
 * 核心思路：
 * 1. 使用Redis的INCR命令原子递增计数器
 * 2. 使用EXPIRE设置窗口过期时间
 * 3. 通过Lua脚本保证INCR和EXPIRE的原子性
 */
public class RedisClusterRateLimiter {

    private final RedisTemplate<String, String> redisTemplate;

    /**
     * Lua脚本：原子性地执行计数和过期设置
     * KEYS[1] = 限流key
     * ARGV[1] = 限流阈值
     * ARGV[2] = 窗口大小（秒）
     */
    private static final String LUA_SCRIPT =
        "local key = KEYS[1]\n" +
        "local limit = tonumber(ARGV[1])\n" +
        "local window = tonumber(ARGV[2])\n" +
        "local current = tonumber(redis.call('INCR', key))\n" +
        "if current == 1 then\n" +
        "    redis.call('EXPIRE', key, window)\n" +
        "end\n" +
        "if current <= limit then\n" +
        "    return 1\n" +
        "else\n" +
        "    return 0\n" +
        "end";

    private final DefaultRedisScript<Long> redisScript;

    public RedisClusterRateLimiter(RedisTemplate<String, String> redisTemplate) {
        this.redisTemplate = redisTemplate;
        this.redisScript = new DefaultRedisScript<>(LUA_SCRIPT, Long.class);
    }

    /**
     * 尝试获取许可
     * 
     * 执行流程：
     * 1. 构建限流Key（包含窗口时间戳，确保窗口正确切换）
     * 2. 执行Lua脚本进行原子计数
     * 3. 返回结果
     */
    public boolean tryAcquire(String limiterKey, long threshold, int windowSeconds) {
        // 计算当前窗口的Key
        long currentWindow = System.currentTimeMillis() / (windowSeconds * 1000);
        String redisKey = "rate_limit:" + limiterKey + ":" + currentWindow;

        Long result = redisTemplate.execute(
            redisScript,
            Collections.singletonList(redisKey),
            String.valueOf(threshold),
            String.valueOf(windowSeconds)
        );

        return result != null && result == 1L;
    }

    /**
     * 带降级的集群限流
     * 当Redis不可用时，降级为本地单机限流
     */
    public boolean tryAcquireWithFallback(String limiterKey, long threshold, 
                                           int windowSeconds, RateLimiter localFallback) {
        try {
            return tryAcquire(limiterKey, threshold, windowSeconds);
        } catch (Exception e) {
            // Redis不可用，降级为单机限流
            // 降级策略：将集群阈值按机器数均分
            long localThreshold = Math.max(1, threshold / getClusterSize());
            return localFallback.tryAcquire();
        }
    }

    private int getClusterSize() {
        // 从注册中心获取集群大小
        return ServiceRegistry.getClusterSize();
    }
}
```

**令牌桶算法的Redis实现**：

```java
/**
 * 基于Redis的集群令牌桶限流
 * 使用Lua脚本实现原子性的令牌补充和消费
 */
public class RedisTokenBucketLimiter {

    private final RedisTemplate<String, String> redisTemplate;

    /**
     * Lua脚本：令牌桶算法
     * KEYS[1] = 令牌桶key
     * ARGV[1] = 桶容量
     * ARGV[2] = 令牌放入速率（每秒）
     * ARGV[3] = 当前时间（毫秒）
     * ARGV[4] = 请求的令牌数
     */
    private static final String TOKEN_BUCKET_SCRIPT =
        "local key = KEYS[1]\n" +
        "local capacity = tonumber(ARGV[1])\n" +
        "local rate = tonumber(ARGV[2])\n" +
        "local now = tonumber(ARGV[3])\n" +
        "local requested = tonumber(ARGV[4])\n" +
        "\n" +
        "-- 获取当前桶状态\n" +
        "local bucket = redis.call('HMGET', key, 'tokens', 'last_time')\n" +
        "local tokens = tonumber(bucket[1])\n" +
        "local lastTime = tonumber(bucket[2])\n" +
        "\n" +
        "-- 初始化桶\n" +
        "if tokens == nil then\n" +
        "    tokens = capacity\n" +
        "    lastTime = now\n" +
        "end\n" +
        "\n" +
        "-- 计算应该补充的令牌\n" +
        "local elapsed = (now - lastTime) / 1000.0\n" +
        "local newTokens = elapsed * rate\n" +
        "tokens = math.min(capacity, tokens + newTokens)\n" +
        "\n" +
        "-- 判断是否有足够的令牌\n" +
        "if tokens >= requested then\n" +
        "    tokens = tokens - requested\n" +
        "    redis.call('HMSET', key, 'tokens', tokens, 'last_time', now)\n" +
        "    redis.call('EXPIRE', key, math.ceil(capacity / rate) + 1)\n" +
        "    return 1\n" +
        "else\n" +
        "    redis.call('HMSET', key, 'tokens', tokens, 'last_time', now)\n" +
        "    redis.call('EXPIRE', key, math.ceil(capacity / rate) + 1)\n" +
        "    return 0\n" +
        "end";

    private final DefaultRedisScript<Long> script;

    public RedisTokenBucketLimiter(RedisTemplate<String, String> redisTemplate) {
        this.redisTemplate = redisTemplate;
        this.script = new DefaultRedisScript<>(TOKEN_BUCKET_SCRIPT, Long.class);
    }

    public boolean tryAcquire(String key, long capacity, long ratePerSecond, int tokens) {
        long now = System.currentTimeMillis();
        Long result = redisTemplate.execute(
            script,
            Collections.singletonList("token_bucket:" + key),
            String.valueOf(capacity),
            String.valueOf(ratePerSecond),
            String.valueOf(now),
            String.valueOf(tokens)
        );
        return result != null && result == 1L;
    }
}
```

#### 3.3.3 基于自建限流服务器的集群限流（2.0方案）

**设计动机**：Redis方案虽然简单，但存在网络延迟较高、Redis单点压力等问题。自建限流服务器通过长连接通信，减少网络开销，同时可以在服务器端实现更复杂的限流算法。

**架构设计**：

```
┌──────────────┐     长连接      ┌──────────────────┐
│  SDK客户端    │ ←──────────→  │  限流服务器集群    │
│              │               │                  │
│ ┌──────────┐ │               │ ┌──────────────┐ │
│ │本地缓存   │ │  ←预分配令牌─  │ │令牌分配引擎   │ │
│ │(预取令牌) │ │               │ │              │ │
│ └──────────┘ │               │ └──────────────┘ │
│ ┌──────────┐ │               │ ┌──────────────┐ │
│ │熔断器     │ │               │ │规则存储      │ │
│ │(保护通信) │ │               │ │              │ │
│ └──────────┘ │               │ └──────────────┘ │
└──────────────┘               │ ┌──────────────┐ │
                               │ │监控上报      │ │
                               │ └──────────────┘ │
                               └──────────────────┘
```

**令牌预分配机制**：SDK客户端不是每次请求都向服务器申请令牌，而是批量预取一定数量的令牌到本地缓存。当本地令牌耗尽时再向服务器申请下一批。这种机制大幅减少了网络通信次数。

```java
/**
 * 集群限流SDK客户端
 * 结合令牌预分配和本地缓存机制
 */
public class ClusterLimiterClient {

    /** 限流服务器客户端 */
    private final LimiterServerClient serverClient;

    /** 本地令牌缓存 */
    private final AtomicLong localTokens;

    /** 本地缓存容量（预取的令牌数量） */
    private final long localCacheSize;

    /** 限流Key */
    private final String limiterKey;

    /** 熔断器（保护限流服务器通信） */
    private final CircuitBreaker circuitBreaker;

    /** 单机限流降级器 */
    private final RateLimiter fallbackLimiter;

    public ClusterLimiterClient(String limiterKey, LimiterServerClient serverClient,
                                 long localCacheSize, CircuitBreaker circuitBreaker) {
        this.limiterKey = limiterKey;
        this.serverClient = serverClient;
        this.localCacheSize = localCacheSize;
        this.localTokens = new AtomicLong(0);
        this.circuitBreaker = circuitBreaker;
        this.fallbackLimiter = new TokenBucketRateLimiter(localCacheSize, localCacheSize);
    }

    /**
     * 尝试获取许可
     * 
     * 核心流程：
     * 1. 先检查本地缓存是否有令牌
     * 2. 本地缓存不足时，向服务器批量申请
     * 3. 服务器不可用时，熔断降级为单机限流
     */
    public boolean tryAcquire() {
        // Step 1: 尝试从本地缓存获取令牌
        while (true) {
            long current = localTokens.get();
            if (current > 0) {
                if (localTokens.compareAndSet(current, current - 1)) {
                    return true;
                }
                continue;
            }
            break;
        }

        // Step 2: 本地令牌不足，尝试向服务器申请
        return refillTokensAndAcquire();
    }

    /**
     * 向服务器批量申请令牌并获取
     */
    private boolean refillTokensAndAcquire() {
        // 通过熔断器保护服务器调用
        try {
            boolean allowed = circuitBreaker.allowRequest();
            if (!allowed) {
                // 熔断器打开，降级为单机限流
                return fallbackLimiter.tryAcquire();
            }

            // 批量申请令牌
            AcquireResponse response = serverClient.acquireTokens(limiterKey, localCacheSize);
            circuitBreaker.setSuccess();

            if (response.getAcquiredTokens() > 0) {
                // 更新本地缓存
                localTokens.addAndGet(response.getAcquiredTokens() - 1);
                return true;
            }
            return false;

        } catch (Exception e) {
            circuitBreaker.setFailed(e);
            // 降级为单机限流
            return fallbackLimiter.tryAcquire();
        } finally {
            circuitBreaker.complete();
        }
    }
}
```

### 3.4 熔断器设计

#### 3.4.1 熔断器三态状态机

熔断器是防止级联故障的核心组件。它通过三态状态机管理熔断器的开启和恢复过程。

```
                    错误率超过阈值
    ┌──────────┐ ─────────────────→ ┌──────────┐
    │  CLOSED  │                     │   OPEN   │
    │ (正常状态) │ ←───────────────── │ (熔断状态) │
    └──────────┘   探测请求成功       └──────────┘
         ↑                               │
         │                               │ 等待熔断恢复时间
         │                               ▼
         │                          ┌────────────┐
         └──────────探测请求成功──── │ HALF-OPEN  │
                                    │ (半开探测)  │
                                    └────────────┘
                                         │
                                    探测请求失败
                                         │
                                         ▼
                                    回到OPEN状态
```

**三态详解**：

1. **CLOSED（关闭状态）**：正常状态，所有请求正常通过。熔断器持续统计请求的成功率和响应时间。当错误率或慢调用率达到配置的阈值时，状态转换为OPEN。

2. **OPEN（打开状态）**：熔断状态，所有请求被直接拒绝（快速失败），不再调用下游服务。等待配置的恢复时间后，状态转换为HALF-OPEN。

3. **HALF-OPEN（半开状态）**：探测恢复状态，允许少量请求通过以测试下游服务是否恢复。如果探测请求成功率达到要求，状态转换为CLOSED，恢复正常；如果探测请求失败，状态转换回OPEN，重新等待恢复时间。

**设计模式**：状态机模式（State Machine Pattern）。每个状态封装了该状态下允许的行为和状态转换逻辑。

```java
/**
 * 熔断器状态枚举
 */
public enum CircuitBreakerState {
    CLOSED,    // 关闭状态，正常通过
    OPEN,      // 打开状态，快速失败
    HALF_OPEN  // 半开状态，探测恢复
}

/**
 * 熔断器实现
 * 
 * 核心设计：
 * 1. 使用滑动窗口统计请求成功率和响应时间
 * 2. 三态状态机管理熔断生命周期
 * 3. 支持基于错误率和基于慢调用率两种熔断策略
 * 4. 线程安全（使用volatile + CAS）
 */
public class CircuitBreaker {

    /** 熔断器Key */
    private final String name;

    /** 熔断策略 */
    private final CircuitBreakerStrategy strategy;

    /** 熔断阈值（错误率或慢调用率，0-1之间） */
    private final double threshold;

    /** 最小请求数（达到此数量才进行熔断判断） */
    private final int minRequestAmount;

    /** 熔断恢复时间（毫秒） */
    private final long recoveryTimeoutMs;

    /** 半开状态最大探测请求数 */
    private final int halfOpenMaxRequests;

    /** 滑动窗口统计器 */
    private final SlidingWindowStatistics statistics;

    /** 当前状态（volatile保证可见性） */
    private volatile CircuitBreakerState state = CircuitBreakerState.CLOSED;

    /** 熔断打开时间 */
    private volatile long openedTime;

    /** 半开状态探测请求计数 */
    private final AtomicInteger halfOpenRequests = new AtomicInteger(0);

    /** 半开状态成功计数 */
    private final AtomicInteger halfOpenSuccess = new AtomicInteger(0);

    /** 状态变更监听器列表 */
    private final List<CircuitBreakerStateChangeListener> listeners = new CopyOnWriteArrayList<>();

    public CircuitBreaker(String name, CircuitBreakerStrategy strategy, 
                          double threshold, int minRequestAmount,
                          long recoveryTimeoutMs, int halfOpenMaxRequests,
                          int windowSize, int sampleCount) {
        this.name = name;
        this.strategy = strategy;
        this.threshold = threshold;
        this.minRequestAmount = minRequestAmount;
        this.recoveryTimeoutMs = recoveryTimeoutMs;
        this.halfOpenMaxRequests = halfOpenMaxRequests;
        this.statistics = new SlidingWindowStatistics(windowSize, sampleCount);
    }

    /**
     * 判断是否允许请求通过
     * 
     * 这是熔断器的核心入口方法
     * 根据当前状态决定是否允许请求通过
     */
    public boolean allowRequest() {
        switch (state) {
            case CLOSED:
                return true;
            case OPEN:
                return tryTransitionToHalfOpen();
            case HALF_OPEN:
                return tryHalfOpenRequest();
            default:
                return true;
        }
    }

    /**
     * 尝试从OPEN转换为HALF_OPEN
     * 只有当熔断恢复时间到达后才转换
     */
    private boolean tryTransitionToHalfOpen() {
        long currentTime = System.currentTimeMillis();
        if (currentTime - openedTime >= recoveryTimeoutMs) {
            // 恢复时间到达，尝试转换为HALF_OPEN
            // 使用CAS避免并发问题
            if (compareAndSetState(CircuitBreakerState.OPEN, CircuitBreakerState.HALF_OPEN)) {
                halfOpenRequests.set(0);
                halfOpenSuccess.set(0);
                notifyStateChange(CircuitBreakerState.OPEN, CircuitBreakerState.HALF_OPEN);
            }
            return tryHalfOpenRequest();
        }
        return false;
    }

    /**
     * 半开状态下尝试获取探测请求许可
     * 限制探测请求数量，避免恢复期间流量过大
     */
    private boolean tryHalfOpenRequest() {
        if (halfOpenRequests.incrementAndGet() <= halfOpenMaxRequests) {
            return true;
        }
        // 探测请求数已满，拒绝
        halfOpenRequests.decrementAndGet();
        return false;
    }

    /**
     * 记录请求成功
     */
    public void setSuccess() {
        if (state == CircuitBreakerState.HALF_OPEN) {
            // 半开状态下记录成功
            int success = halfOpenSuccess.incrementAndGet();
            if (success >= halfOpenMaxRequests / 2) {
                // 成功率足够，转换为CLOSED
                if (compareAndSetState(CircuitBreakerState.HALF_OPEN, CircuitBreakerState.CLOSED)) {
                    statistics.reset();
                    notifyStateChange(CircuitBreakerState.HALF_OPEN, CircuitBreakerState.CLOSED);
                }
            }
        } else if (state == CircuitBreakerState.CLOSED) {
            statistics.recordSuccess();
        }
    }

    /**
     * 记录请求失败
     */
    public void setFailed(Throwable cause) {
        if (state == CircuitBreakerState.HALF_OPEN) {
            // 半开状态下失败，重新熔断
            if (compareAndSetState(CircuitBreakerState.HALF_OPEN, CircuitBreakerState.OPEN)) {
                openedTime = System.currentTimeMillis();
                notifyStateChange(CircuitBreakerState.HALF_OPEN, CircuitBreakerState.OPEN);
            }
        } else if (state == CircuitBreakerState.CLOSED) {
            statistics.recordFailure(cause);
            tryTransitionToOpen();
        }
    }

    /**
     * 尝试从CLOSED转换为OPEN
     * 当统计指标达到阈值时触发
     */
    private void tryTransitionToOpen() {
        CircuitBreakerStat stat = statistics.getStat();
        
        // 最小请求数检查
        if (stat.getTotalCount() < minRequestAmount) {
            return;
        }

        boolean shouldOpen = false;
        switch (strategy) {
            case ERROR_RATIO:
                // 错误率策略
                shouldOpen = stat.getErrorRatio() >= threshold;
                break;
            case SLOW_CALL_RATIO:
                // 慢调用率策略
                shouldOpen = stat.getSlowCallRatio() >= threshold;
                break;
            case ERROR_COUNT:
                // 错误数策略
                shouldOpen = stat.getErrorCount() >= (int) threshold;
                break;
        }

        if (shouldOpen) {
            if (compareAndSetState(CircuitBreakerState.CLOSED, CircuitBreakerState.OPEN)) {
                openedTime = System.currentTimeMillis();
                notifyStateChange(CircuitBreakerState.CLOSED, CircuitBreakerState.OPEN);
            }
        }
    }

    /**
     * 完成请求（清理ThreadLocal等资源）
     */
    public void complete() {
        // 清理线程上下文
    }

    private boolean compareAndSetState(CircuitBreakerState expect, CircuitBreakerState update) {
        // 使用AtomicReference或自定义CAS逻辑
        // 简化实现，实际应使用CAS
        if (state == expect) {
            state = update;
            return true;
        }
        return false;
    }

    private void notifyStateChange(CircuitBreakerState from, CircuitBreakerState to) {
        for (CircuitBreakerStateChangeListener listener : listeners) {
            listener.onStateChange(name, from, to);
        }
    }

    public void addStateChangeListener(CircuitBreakerStateChangeListener listener) {
        listeners.add(listener);
    }

    public CircuitBreakerState getState() {
        return state;
    }
}
```

#### 3.4.2 滑动窗口统计器

熔断器的判断依赖于滑动窗口统计器，它记录了最近一段时间的请求成功、失败、慢调用等指标。

```java
/**
 * 滑动窗口统计器
 * 为熔断器提供实时统计数据
 */
public class SlidingWindowStatistics {

    /** 窗口大小（毫秒） */
    private final long windowSizeMs;

    /** 采样窗口数 */
    private final int sampleCount;

    /** 每个采样窗口的统计数据 */
    private final WindowBucket[] buckets;

    /** 慢调用阈值（毫秒） */
    private final long slowCallThresholdMs;

    public SlidingWindowStatistics(long windowSizeMs, int sampleCount) {
        this(windowSizeMs, sampleCount, 1000); // 默认1秒为慢调用
    }

    public SlidingWindowStatistics(long windowSizeMs, int sampleCount, long slowCallThresholdMs) {
        this.windowSizeMs = windowSizeMs;
        this.sampleCount = sampleCount;
        this.slowCallThresholdMs = slowCallThresholdMs;
        this.buckets = new WindowBucket[sampleCount];
        long now = System.currentTimeMillis();
        for (int i = 0; i < sampleCount; i++) {
            buckets[i] = new WindowBucket(now);
        }
    }

    /**
     * 记录成功请求
     */
    public synchronized void recordSuccess() {
        recordSuccess(System.currentTimeMillis() - getCallStartTime(), true);
    }

    /**
     * 记录失败请求
     */
    public synchronized void recordFailure(Throwable cause) {
        WindowBucket bucket = getCurrentBucket();
        bucket.errorCount++;
        if (isBusinessError(cause)) {
            bucket.businessErrorCount++;
        }
    }

    /**
     * 记录请求完成（带耗时）
     */
    public synchronized void recordCompletion(long durationMs, boolean success) {
        WindowBucket bucket = getCurrentBucket();
        bucket.totalCount++;
        if (!success) {
            bucket.errorCount++;
        }
        if (durationMs > slowCallThresholdMs) {
            bucket.slowCallCount++;
        }
        bucket.totalDurationMs += durationMs;
    }

    /**
     * 获取聚合统计
     */
    public synchronized CircuitBreakerStat getStat() {
        long now = System.currentTimeMillis();
        long totalCount = 0;
        long errorCount = 0;
        long slowCallCount = 0;
        long totalDurationMs = 0;

        for (WindowBucket bucket : buckets) {
            if (now - bucket.startTime < windowSizeMs) {
                totalCount += bucket.totalCount;
                errorCount += bucket.errorCount;
                slowCallCount += bucket.slowCallCount;
                totalDurationMs += bucket.totalDurationMs;
            }
        }

        double errorRatio = totalCount > 0 ? (double) errorCount / totalCount : 0;
        double slowCallRatio = totalCount > 0 ? (double) slowCallCount / totalCount : 0;
        double avgDurationMs = totalCount > 0 ? (double) totalDurationMs / totalCount : 0;

        return new CircuitBreakerStat(totalCount, errorCount, errorRatio, 
                                       slowCallCount, slowCallRatio, avgDurationMs);
    }

    /**
     * 获取当前时间对应的统计桶
     * 如果桶过期则重置
     */
    private WindowBucket getCurrentBucket() {
        long now = System.currentTimeMillis();
        int idx = (int) ((now / (windowSizeMs / sampleCount)) % sampleCount);
        WindowBucket bucket = buckets[idx];
        if (now - bucket.startTime >= windowSizeMs) {
            bucket.reset(now);
        }
        return bucket;
    }

    public synchronized void reset() {
        long now = System.currentTimeMillis();
        for (WindowBucket bucket : buckets) {
            bucket.reset(now);
        }
    }

    private long getCallStartTime() {
        // 从ThreadLocal中获取调用开始时间
        return 0;
    }

    private boolean isBusinessError(Throwable cause) {
        // 判断是否为业务异常（不计入熔断统计）
        return cause instanceof BusinessException;
    }

    /**
     * 统计桶
     */
    private static class WindowBucket {
        long startTime;
        long totalCount;
        long errorCount;
        long businessErrorCount;
        long slowCallCount;
        long totalDurationMs;

        WindowBucket(long startTime) {
            this.startTime = startTime;
        }

        void reset(long newStartTime) {
            startTime = newStartTime;
            totalCount = 0;
            errorCount = 0;
            businessErrorCount = 0;
            slowCallCount = 0;
            totalDurationMs = 0;
        }
    }
}
```

#### 3.4.3 熔断策略对比

| 策略 | 触发条件 | 适用场景 | 优点 | 缺点 |
|------|---------|---------|------|------|
| 错误率策略 | 错误率 >= 阈值 | 下游服务故障 | 直观，最常用 | 慢调用不会触发 |
| 慢调用率策略 | 慢调用占比 >= 阈值 | 下游服务响应变慢 | 能捕捉性能退化 | 需要合理设置慢调用阈值 |
| 组合策略 | 错误率或慢调用率任一达标 | 综合场景 | 覆盖面广 | 参数调优复杂 |
| 错误数策略 | 错误数 >= 阈值 | 低QPS场景 | 避免低QPS下误判 | 高QPS下过于敏感 |

### 3.5 降级策略体系

#### 3.5.1 降级策略分类

降级是服务保护的最后一道防线。当系统资源紧张或依赖不可用时，主动放弃部分非核心功能，保障核心业务可用。

根据触发方式，降级分为两类：
- **自动降级**：由系统根据预设条件自动触发，如熔断器打开、超时、限流等
- **手动降级**：通过配置开关人工触发，适用于大促前预处理、故障应急等场景

根据降级方式，分为以下几种：

| 降级方式 | 实现思路 | 适用场景 |
|---------|---------|---------|
| 返回默认值 | 直接返回预设的默认结果 | 推荐列表、配置查询等可容忍数据缺失的场景 |
| 返回兜底数据 | 返回缓存的上一次成功结果 | 用户信息、商品详情等需要展示内容的场景 |
| 返回空结果 | 返回空列表或null | 日志记录、监控上报等非关键路径 |
| 异步降级 | 将同步操作改为异步，先返回响应 | 日志写入、消息发送等可异步化的场景 |
| 功能关闭 | 直接跳过某个功能模块 | 非核心功能，如推荐、广告等 |

#### 3.5.2 降级策略路由实现

**设计模式**：策略模式（Strategy Pattern）+ 责任链模式（Chain of Responsibility）。

```java
/**
 * 降级策略接口
 */
public interface DegradeStrategy {
    /**
     * 执行降级
     * @param context 降级上下文
     * @return 降级结果
     */
    Object degrade(DegradeContext context);

    /**
     * 策略类型
     */
    DegradeType getType();
}

/**
 * 降级上下文
 */
public class DegradeContext {
    /** 原始请求 */
    private final Object request;
    /** 方法签名 */
    private final MethodSignature methodSignature;
    /** 降级原因 */
    private final DegradeReason reason;
    /** 缓存数据提供者 */
    private final CacheProvider cacheProvider;
    /** 降级配置 */
    private final DegradeConfig config;
}

/**
 * 返回默认值降级策略
 */
public class DefaultValueDegradeStrategy implements DegradeStrategy {

    @Override
    public Object degrade(DegradeContext context) {
        Method method = context.getMethodSignature().getMethod();
        Class<?> returnType = method.getReturnType();

        // 根据返回类型返回对应的默认值
        if (returnType == int.class || returnType == Integer.class) {
            return context.getConfig().getDefaultIntValue();
        } else if (returnType == long.class || returnType == Long.class) {
            return context.getConfig().getDefaultLongValue();
        } else if (returnType == boolean.class || returnType == Boolean.class) {
            return false;
        } else if (returnType == String.class) {
            return context.getConfig().getDefaultStringValue();
        } else if (returnType == List.class) {
            return Collections.emptyList();
        } else if (returnType == Map.class) {
            return Collections.emptyMap();
        } else if (returnType == void.class) {
            return null;
        } else {
            // 对于复杂对象，尝试返回null或通过反射创建默认实例
            return null;
        }
    }

    @Override
    public DegradeType getType() {
        return DegradeType.DEFAULT_VALUE;
    }
}

/**
 * 返回兜底数据降级策略
 * 从缓存中获取上一次成功的响应
 */
public class FallbackDataDegradeStrategy implements DegradeStrategy {

    @Override
    public Object degrade(DegradeContext context) {
        String cacheKey = buildCacheKey(context);
        Object cached = context.getCacheProvider().get(cacheKey);

        if (cached != null) {
            return cached;
        }

        // 缓存也没有，降级为返回默认值
        return new DefaultValueDegradeStrategy().degrade(context);
    }

    private String buildCacheKey(DegradeContext context) {
        // 根据方法签名和请求参数构建缓存Key
        return context.getMethodSignature().getName() + ":" + 
               Objects.hash(context.getRequest());
    }

    @Override
    public DegradeType getType() {
        return DegradeType.FALLBACK_DATA;
    }
}

/**
 * 异步降级策略
 * 将同步操作改为异步执行，先返回响应
 */
public class AsyncDegradeStrategy implements DegradeStrategy {

    private final ExecutorService asyncExecutor;
    private final DegradeCallback callback;

    public AsyncDegradeStrategy(ExecutorService asyncExecutor, DegradeCallback callback) {
        this.asyncExecutor = asyncExecutor;
        this.callback = callback;
    }

    @Override
    public Object degrade(DegradeContext context) {
        // 异步执行原始操作
        asyncExecutor.submit(() -> {
            try {
                callback.execute(context.getRequest());
            } catch (Exception e) {
                // 异步操作失败不影响主流程
                // 仅记录日志
            }
        });

        // 先返回成功响应
        Method method = context.getMethodSignature().getMethod();
        return getDefaultReturnValue(method.getReturnType());
    }

    @Override
    public DegradeType getType() {
        return DegradeType.ASYNC;
    }
}

/**
 * 降级策略路由器
 * 根据配置选择合适的降级策略
 */
public class DegradeStrategyRouter {

    private final Map<DegradeType, DegradeStrategy> strategyMap = new ConcurrentHashMap<>();

    public DegradeStrategyRouter() {
        // 注册默认策略
        register(new DefaultValueDegradeStrategy());
        register(new FallbackDataDegradeStrategy());
    }

    public void register(DegradeStrategy strategy) {
        strategyMap.put(strategy.getType(), strategy);
    }

    /**
     * 执行降级
     */
    public Object degrade(DegradeContext context) {
        DegradeType type = context.getConfig().getDegradeType();
        DegradeStrategy strategy = strategyMap.get(type);

        if (strategy == null) {
            strategy = strategyMap.get(DegradeType.DEFAULT_VALUE);
        }

        return strategy.degrade(context);
    }
}
```

### 3.6 线程池隔离与信号量隔离

#### 3.6.1 线程池隔离

**设计思想**：为不同的服务调用分配独立的线程池，当某个服务调用出现问题时，只会耗尽自己的线程池，不会影响其他服务的调用。

```
┌──────────────────────────────────────────────────────────┐
│                    服务A（调用方）                          │
│                                                          │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐      │
│  │ 线程池1      │  │ 线程池2      │  │ 线程池3      │      │
│  │ (服务B调用)  │  │ (服务C调用)  │  │ (服务D调用)  │      │
│  │             │  │             │  │             │      │
│  │ core=10     │  │ core=5      │  │ core=20     │      │
│  │ max=20      │  │ max=10      │  │ max=40     │      │
│  │ queue=100   │  │ queue=50    │  │ queue=200   │      │
│  └─────────────┘  └─────────────┘  └─────────────┘      │
│                                                          │
│  如果服务D故障，只有线程池3被耗尽，                          │
│  服务B和C的调用不受影响                                     │
└──────────────────────────────────────────────────────────┘
```

```java
/**
 * 线程池隔离管理器
 * 为每个下游服务调用维护独立的线程池
 */
public class ThreadPoolIsolationManager {

    /** 线程池缓存 */
    private final ConcurrentHashMap<String, ExecutorService> poolCache = new ConcurrentHashMap<>();

    /**
     * 获取或创建线程池
     */
    public ExecutorService getThreadPool(String isolationKey, ThreadPoolConfig config) {
        return poolCache.computeIfAbsent(isolationKey, key -> {
            return new ThreadPoolExecutor(
                config.getCoreSize(),
                config.getMaxSize(),
                config.getKeepAliveSeconds(),
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(config.getQueueSize()),
                new NamedThreadFactory("isolation-" + key),
                new CallerRunsPolicy() // 队列满时由调用线程执行，实现背压
            );
        });
    }

    /**
     * 在隔离的线程池中执行调用
     * 
     * @param isolationKey 隔离Key（通常是下游服务名）
     * @param config 线程池配置
     * @param supplier 要执行的业务逻辑
     * @param fallback 降级逻辑
     */
    public <T> T executeWithIsolation(String isolationKey, ThreadPoolConfig config,
                                       Supplier<T> supplier, Supplier<T> fallback) {
        ExecutorService pool = getThreadPool(isolationKey, config);

        try {
            Future<T> future = pool.submit(supplier::get);
            return future.get(config.getTimeoutMs(), TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            // 超时，执行降级
            return fallback.get();
        } catch (RejectedExecutionException e) {
            // 线程池满，执行降级
            return fallback.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return fallback.get();
        } catch (ExecutionException e) {
            // 业务异常，执行降级或抛出
            return fallback.get();
        }
    }
}
```

#### 3.6.2 信号量隔离

**设计思想**：不创建独立线程池，而是使用信号量限制并发请求数。请求在当前线程中执行，但需要先获取信号量许可。信号量隔离更轻量，没有线程切换开销，但无法实现异步和超时控制。

```java
/**
 * 信号量隔离实现
 */
public class SemaphoreIsolation {

    private final Semaphore semaphore;

    public SemaphoreIsolation(int permits) {
        this.semaphore = new Semaphore(permits);
    }

    public <T> T execute(Supplier<T> supplier, Supplier<T> fallback) {
        if (semaphore.tryAcquire()) {
            try {
                return supplier.get();
            } finally {
                semaphore.release();
            }
        } else {
            // 获取信号量失败，执行降级
            return fallback.get();
        }
    }
}
```

#### 3.6.3 两种隔离方式对比

| 维度 | 线程池隔离 | 信号量隔离 |
|------|----------|----------|
| 线程开销 | 高（每个隔离Key独立线程池） | 低（在调用线程中执行） |
| 异步支持 | 支持 | 不支持 |
| 超时控制 | 支持（Future.get + timeout） | 不支持（需业务自行实现） |
| 资源隔离 | 强（完全独立） | 弱（共享线程） |
| 适用场景 | 调用外部服务、IO密集型 | 内部计算、CPU密集型 |
| 代表实现 | Hystrix | Sentinel |

### 3.7 Hystrix与Sentinel对比

| 维度 | Hystrix | Sentinel |
|------|---------|---------|
| 隔离方式 | 线程池隔离为主 | 信号量隔离为主 |
| 熔断策略 | 错误率 | 错误率 + 慢调用率 |
| 限流能力 | 不支持 | 支持（滑动窗口/令牌桶/漏桶） |
| 实时统计 | 滑动窗口（RxJava） | 滑动窗口（LeapArray） |
| 规则配置 | 静态配置 | 动态配置（支持规则源） |
| 控制台 | Hystrix Dashboard | Sentinel Dashboard |
| 扩展性 | 一般 | 高（SPI扩展点） |
| 维护状态 | 停止维护 | 活跃维护 |
| 系统自适应 | 不支持 | 支持（基于Load自适应） |

Sentinel的系统自适应限流是一个亮点特性。它综合考量系统的Load1（CPU负载）、CPU使用率、平均RT（响应时间）、入口QPS和并发线程数等指标，自动判断是否需要限流。这种基于系统整体负载的自适应限流比简单的阈值限流更加智能。

```java
/**
 * Sentinel风格的系统自适应限流
 * 基于BBP（BBrake System）算法
 */
public class SystemAdaptiveLimiter {

    /** 系统负载阈值 */
    private double maxLoad = 4.0;

    /** CPU使用率阈值 */
    private double maxCpuUsage = 0.8;

    /** 最大并发线程数 */
    private int maxThreads = 100;

    /** 最大平均RT（毫秒） */
    private long maxAvgRt = 100;

    /** 最大入口QPS */
    private long maxQps = 1000;

    /** 当前并发线程数 */
    private final AtomicInteger currentThreads = new AtomicInteger(0);

    /** 滑动窗口统计 */
    private final SlidingWindowStatistics stats;

    public boolean tryAcquire() {
        // 获取系统指标
        double currentLoad = getSystemLoad1();
        double currentCpu = getCpuUsage();

        // 检查各项指标
        if (currentLoad > maxLoad) {
            return false;
        }
        if (currentCpu > maxCpuUsage) {
            return false;
        }

        // 检查并发线程数
        if (currentThreads.incrementAndGet() > maxThreads) {
            currentThreads.decrementAndGet();
            return false;
        }

        // 检查平均RT和QPS
        CircuitBreakerStat stat = stats.getStat();
        if (stat.getAvgDurationMs() > maxAvgRt) {
            currentThreads.decrementAndGet();
            return false;
        }
        if (stat.getTotalCount() > maxQps) {
            currentThreads.decrementAndGet();
            return false;
        }

        return true;
    }

    private double getSystemLoad1() {
        return ManagementFactory.getOperatingSystemMXBean().getSystemLoadAverage();
    }

    private double getCpuUsage() {
        // 通过JMX或操作系统接口获取CPU使用率
        return 0; // 简化实现
    }
}
```

## 4. 异常处理与容错机制

### 4.1 限流环节异常处理

**Redis不可用时的降级策略**：

当集群限流依赖的Redis不可用时，系统需要自动降级为单机限流，保证业务不受影响。

```java
public class ClusterRateLimiterWithFallback {

    private final RedisClusterRateLimiter redisLimiter;
    private final RateLimiter localLimiter;
    private final CircuitBreaker redisCircuitBreaker;

    /**
     * 降级策略：
     * 1. 正常情况：使用Redis集群限流
     * 2. Redis故障：降级为单机限流（阈值 = 集群阈值 / 机器数）
     * 3. 熔断器保护：当Redis连续失败时触发熔断，直接使用单机限流
     */
    public boolean tryAcquire(String key, long clusterThreshold, int windowSeconds) {
        try {
            if (redisCircuitBreaker.allowRequest()) {
                boolean result = redisLimiter.tryAcquire(key, clusterThreshold, windowSeconds);
                redisCircuitBreaker.setSuccess();
                return result;
            } else {
                // 熔断器打开，降级为单机限流
                return localLimit(clusterThreshold);
            }
        } catch (Exception e) {
            redisCircuitBreaker.setFailed(e);
            return localLimit(clusterThreshold);
        } finally {
            redisCircuitBreaker.complete();
        }
    }

    private boolean localLimit(long clusterThreshold) {
        long localThreshold = Math.max(1, clusterThreshold / ClusterInfo.getSize());
        return localLimiter.tryAcquire();
    }
}
```

### 4.3 幂等性保证

```java
/**

        return getCachedResult(requestId);

    }

        return null;
```

### 4.4 数据一致性保证

在集群限流场景中，多个节点可能同时向Redis发起计数请求，需要保证计数的原子性。这通过Lua脚本已经解决。但在限流服务器方案中，需要考虑以下一致性问题：

1. **令牌分配一致性**：限流服务器需要确保令牌的总量不超过配置的阈值。通过在服务器端使用原子操作或分布式锁保证。

2. **规则变更一致性**：当规则变更时，所有SDK客户端需要尽快感知。通过配置中心的推模式 + 本地缓存兜底实现。

3. **状态转换一致性**：熔断器的状态转换在单机内通过CAS保证，集群级别的熔断状态不共享（每个实例独立判断）。

### 4.5 重试与退避策略

当请求被限流或熔断时，合理的重试策略可以提高请求成功率。但不当的重试会加剧系统负载。

```java
/**
 * 指数退避重试策略
 * 
 * 核心思路：
 * 1. 初始等待时间较短
 * 2. 每次重试等待时间指数增长
 * 3. 设置最大重试次数和最大等待时间
 * 4. 加入随机抖动，避免重试风暴
 */
public class ExponentialBackoffRetry {

    private final int maxRetries;
    private final long initialIntervalMs;
    private final double multiplier;
    private final long maxIntervalMs;
    private final double randomFactor;

    public RetryResult execute(Supplier<RetryResult> action) {
        int attempt = 0;
        while (attempt < maxRetries) {
            RetryResult result = action.get();
            if (result.isSuccess()) {
                return result;
            }

            attempt++;
            if (attempt >= maxRetries) {
                return result; // 重试次数用完
            }

            // 计算等待时间
            long waitTime = calculateWaitTime(attempt);
            try {
                Thread.sleep(waitTime);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return RetryResult.failure("Interrupted");
            }
        }
        return RetryResult.failure("Max retries exceeded");
    }

    private long calculateWaitTime(int attempt) {
        // 指数增长
        long waitTime = (long) (initialIntervalMs * Math.pow(multiplier, attempt - 1));
        // 限制最大值
        waitTime = Math.min(waitTime, maxIntervalMs);
        // 加入随机抖动（避免重试风暴）
        waitTime = (long) (waitTime * (1.0 + (Math.random() - 0.5) * randomFactor));
        return waitTime;
    }
}
```

## 5. 性能优化

### 5.1 瓶颈分析

| 瓶颈点 | 影响分析 | 优化方向 |
|--------|---------|---------|
| 集群限流网络开销 | 每次请求都需与Redis/限流服务器通信，增加延迟 | 令牌预分配、批量请求 |
| 滑动窗口内存开销 | 每个限流Key维护独立的滑动窗口 | 共享窗口、LRU淘汰 |
| 熔断器统计开销 | 每次请求都需要更新统计数据 | 无锁CAS、异步统计 |
| AOP拦截开销 | 反射和SpEL解析增加延迟 | 编译时增强、缓存解析结果 |
| 监控上报开销 | 频繁的指标采集和上报影响性能 | 异步批量上报、采样 |

### 5.2 优化手段

#### 5.2.1 令牌预分配优化

集群限流的最大性能瓶颈是网络通信。通过令牌预分配，SDK客户端一次性向服务器申请一批令牌（如100个），存入本地缓存。后续请求优先从本地缓存获取令牌，只有缓存耗尽时才再次向服务器申请。这样可以将网络通信频率降低100倍。

#### 5.2.2 无锁统计优化

使用CAS（Compare-And-Swap）替代synchronized进行统计更新，减少线程竞争。Sentinel的LeapArray就是这种优化的典型实现。

```java
/**
 * 无锁统计计数器
 * 使用LongAdder替代AtomicLong，在高并发下性能更好
 */
public class LockFreeCounter {

    private final LongAdder counter = new LongAdder();

    public void increment() {
        counter.increment();
    }

    public long get() {
        return counter.sum();
    }

    public void reset() {
        counter.reset();
    }
}
```

#### 5.2.3 异步监控上报

监控指标采集使用异步批量上报，避免影响业务请求的延迟。

```java
/**
 * 异步批量指标上报器
 * 
 * 核心设计：
 * 1. 使用Disruptor或ArrayBlockingQueue作为缓冲队列
 * 2. 后台线程批量读取并上报
 * 3. 队列满时丢弃最旧的数据（保护内存）
 */
public class AsyncMetricsReporter {

    private final BlockingQueue<MetricEvent> queue;
    private final MetricsClient client;
    private final int batchSize;
    private final long flushIntervalMs;

    public AsyncMetricsReporter(int queueSize, MetricsClient client, 
                                 int batchSize, long flushIntervalMs) {
        this.queue = new ArrayBlockingQueue<>(queueSize);
        this.client = client;
        this.batchSize = batchSize;
        this.flushIntervalMs = flushIntervalMs;
        
        // 启动后台上报线程
        startFlushThread();
    }

    public void report(MetricEvent event) {
        // 非阻塞式入队，队列满时丢弃
        queue.offer(event);
    }

    private void startFlushThread() {
        Thread thread = new Thread(() -> {
            List<MetricEvent> batch = new ArrayList<>(batchSize);
            long lastFlushTime = System.currentTimeMillis();
            
            while (!Thread.currentThread().isInterrupted()) {
                MetricEvent event = queue.poll();
                if (event != null) {
                    batch.add(event);
                }

                boolean sizeReady = batch.size() >= batchSize;
                boolean timeReady = System.currentTimeMillis() - lastFlushTime >= flushIntervalMs;

                if (sizeReady || (timeReady && !batch.isEmpty())) {
                    try {
                        client.batchReport(batch);
                    } catch (Exception e) {
                        // 上报失败，记录日志，不重试
                    }
                    batch.clear();
                    lastFlushTime = System.currentTimeMillis();
                }
            }
        }, "metrics-reporter");
        thread.setDaemon(true);
        thread.start();
    }
}
```

## 6. 最佳实践与总结

### 6.1 设计原则

1. **分层防御**：限流、熔断、降级三层保护，各司其职。限流防入口，熔断防下游，降级保核心。

2. **快速失败**：当系统过载或下游故障时，快速返回错误比长时间等待更好。快速失败释放资源，防止线程堆积。

3. **优雅降级**：降级不等于报错。返回默认值、兜底数据、空结果等都是降级手段，核心是保证用户体验可接受。

4. **可观测**：所有限流、熔断、降级行为都需要可观测。通过监控指标、告警通知，让运维人员及时了解系统状态。

5. **动态配置**：规则应该支持动态调整，避免修改代码和重启。通过配置中心推送，秒级生效。

6. **渐进恢复**：熔断恢复时应该渐进式放行流量，避免恢复瞬间流量突增再次打垮系统。半开状态的探测请求数量应该逐步增加。

### 6.2 常见陷阱

1. **限流阈值设置不当**：阈值过高起不到保护作用，过低影响正常业务。建议通过压测确定合理阈值，设置为压测最高QPS的70%-80%。

2. **忽略慢调用**：只关注错误率而忽略慢调用，可能导致下游响应变慢时线程池被耗尽，但熔断器不触发。建议同时配置错误率策略和慢调用率策略。

3. **降级逻辑不可用**：降级方法中调用了其他服务，但这些服务也可能不可用。降级逻辑应该是最简单的、不依赖外部服务的。

4. **重试风暴**：上游重试导致下游流量放大。例如上游重试3次，下游实际收到3倍流量。建议限制重试次数，使用指数退避，并在请求头中传递重试次数。

5. **集群限流成为单点**：过度依赖Redis或限流服务器，当其故障时影响所有限流。必须实现降级方案，确保限流基础设施故障时业务仍能运行。

6. **熔断恢复太快**：恢复时间设置过短，导致系统在未完全恢复时大量流量涌入，再次触发熔断。建议恢复时间设置为故障持续时间的1/3到1/2。

7. **忽略业务异常**：将业务异常（如参数校验失败）计入熔断统计，可能导致误熔断。需要在统计时区分系统异常和业务异常。

### 6.3 演进方向

1. **自适应限流**：基于系统实时负载（CPU、内存、响应时间）自动调整限流阈值，无需人工配置。Sentinel的系统自适应限流是这一方向的初步实践。

2. **AI驱动的异常检测**：利用机器学习模型检测异常流量模式，提前预警和自动调整限流策略。

3. **全链路限流**：从网关到服务到数据库的全链路流量管控，实现端到端的流量整形和保护。

4. **Serverless限流**：在Serverless架构中，限流需要考虑实例动态伸缩的特性，传统单机限流不再适用。

5. **多维度精细限流**：不仅按QPS限流，还按并发数、响应时间、资源消耗等多维度进行精细化控制。

6. **限流即服务**：将限流能力从应用中解耦，作为独立的服务提供，应用通过Sidecar或SDK接入，实现统一管控。

## 7. 全链路实战案例

前面的章节从算法原理、引擎实现、异常处理到性能优化，系统地梳理了限流、降级、熔断三大保护机制。本章通过三个贯穿全链路的实战案例，把这些机制串联起来，展示从请求进入、规则匹配、保护触发、兜底处理到用户可感知结果的完整闭环。每个案例都包含完整的Java代码、异常处理、日志记录和幂等控制，力求可直接落地。

### 7.1 案例一：接口限流全链路

#### 7.1.1 场景描述

某电商平台的下单接口 `POST /order/create` 在大促期间面临瞬时流量冲击。系统的处理能力经压测确定为单机 2000 QPS，集群维度总量限制为 20000 QPS。要求：

- 单机维度使用令牌桶，允许一定突发流量；
- 全局维度使用滑动窗口，精确控制总量；
- 超出阈值的请求不能直接抛异常给用户，需要通过自定义 BlockHandler 返回友好提示；
- 限流拦截需要幂等，同一请求的重复提交不能因为限流器计数问题产生重复扣减。

全链路流转如下：

```
请求进入
   │
   ▼
[网关/入口幂等校验] ── 已处理 ──▶ 返回上次结果（幂等）
   │ 未处理
   ▼
[令牌桶单机限流] ── 无令牌 ──▶ BlockHandler ──▶ 友好提示
   │ 通过
   ▼
[滑动窗口集群限流] ── 超阈值 ──▶ BlockHandler ──▶ 友好提示
   │ 通过
   ▼
[业务处理：创建订单]
   │
   ▼
[写入幂等结果缓存] ──▶ 返回成功
```

#### 7.1.2 令牌桶与滑动窗口限流器

单机维度采用令牌桶算法，天然支持突发流量；全局维度采用滑动窗口，精确控制单位时间总量。两者组合形成两级限流。

```java
/**
 * 令牌桶限流器（单机维度）
 *
 * 设计要点：
 * 1. 惰性生成令牌：不使用后台线程定时投放，而是在获取时按时间差补充令牌，减少线程开销
 * 2. 支持突发：桶容量 capacity 大于每秒速率 rate 时允许突发
 * 3. 线程安全：使用 synchronized 保证补充与扣减的原子性
 */
public class TokenBucketRateLimiter {

    private static final Logger log = LoggerFactory.getLogger(TokenBucketRateLimiter.class);

    /** 桶容量（最大突发令牌数） */
    private final long capacity;

    /** 每毫秒生成的令牌数 */
    private final double tokensPerMillis;

    /** 当前可用令牌数 */
    private double availableTokens;

    /** 上次补充令牌的时间戳 */
    private long lastRefillTimestamp;

    /**
     * @param permitsPerSecond 每秒允许的请求数（如 2000）
     * @param capacity         桶容量，控制突发上限
     */
    public TokenBucketRateLimiter(long permitsPerSecond, long capacity) {
        if (permitsPerSecond <= 0 || capacity <= 0) {
            throw new IllegalArgumentException("permitsPerSecond 和 capacity 必须大于 0");
        }
        this.capacity = capacity;
        this.tokensPerMillis = permitsPerSecond / 1000.0;
        this.availableTokens = capacity;
        this.lastRefillTimestamp = System.currentTimeMillis();
    }

    /**
     * 尝试获取一个令牌
     *
     * @return true 表示获取成功（放行），false 表示限流
     */
    public synchronized boolean tryAcquire() {
        refill();
        if (availableTokens >= 1) {
            availableTokens -= 1;
            return true;
        }
        return false;
    }

    /**
     * 按时间差惰性补充令牌
     */
    private void refill() {
        long now = System.currentTimeMillis();
        if (now > lastRefillTimestamp) {
            double newTokens = (now - lastRefillTimestamp) * tokensPerMillis;
            availableTokens = Math.min(capacity, availableTokens + newTokens);
            lastRefillTimestamp = now;
        }
    }
}
```

```java
/**
 * 滑动窗口限流器（全局维度，可扩展为基于 Redis 的集群实现）
 *
 * 这里给出单机内存版的滑动窗口，用于说明算法。
 * 生产环境的集群限流应替换为 Redis + Lua 的原子实现（见 3.3 集群限流实现）。
 */
public class SlidingWindowRateLimiter {

    private static final Logger log = LoggerFactory.getLogger(SlidingWindowRateLimiter.class);

    /** 窗口总时长（毫秒） */
    private final long windowSizeMs;

    /** 窗口内允许的最大请求数 */
    private final long threshold;

    /** 分片数量，分片越多滑动越平滑 */
    private final int sampleCount;

    private final long[] bucketCounts;
    private final long[] bucketStartTimes;

    public SlidingWindowRateLimiter(long windowSizeMs, long threshold, int sampleCount) {
        this.windowSizeMs = windowSizeMs;
        this.threshold = threshold;
        this.sampleCount = sampleCount;
        this.bucketCounts = new long[sampleCount];
        this.bucketStartTimes = new long[sampleCount];
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        long bucketLen = windowSizeMs / sampleCount;
        int idx = (int) ((now / bucketLen) % sampleCount);

        // 若当前分片已过期，重置该分片
        if (now - bucketStartTimes[idx] >= bucketLen) {
            bucketCounts[idx] = 0;
            bucketStartTimes[idx] = now - (now % bucketLen);
        }

        // 汇总窗口内所有有效分片计数
        long total = 0;
        for (int i = 0; i < sampleCount; i++) {
            if (now - bucketStartTimes[i] < windowSizeMs) {
                total += bucketCounts[i];
            }
        }

        if (total < threshold) {
            bucketCounts[idx]++;
            return true;
        }
        return false;
    }
}
```

#### 7.1.3 Sentinel 风格的规则配置

在实际项目中，通常通过注解 + 规则配置的方式接入限流。下面给出 Sentinel 风格的规则初始化与注解使用，规则支持从配置中心动态推送。

```java
/**
 * 限流规则配置初始化
 *
 * 生产环境应通过配置中心（如 Nacos）动态加载规则，
 * 这里演示程序化配置，规则变更时调用 loadRules 即可热更新。
 */
@Component
public class FlowRuleInitializer {

    private static final Logger log = LoggerFactory.getLogger(FlowRuleInitializer.class);

    /** 下单接口的资源名，与 @SentinelResource 的 value 保持一致 */
    public static final String RESOURCE_ORDER_CREATE = "order:create";

    @PostConstruct
    public void init() {
        List<FlowRule> rules = new ArrayList<>();

        // 单机维度限流：QPS 2000，采用快速失败
        FlowRule singleRule = new FlowRule();
        singleRule.setResource(RESOURCE_ORDER_CREATE);
        singleRule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        singleRule.setCount(2000);
        singleRule.setClusterMode(false);
        singleRule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT);

        // 集群维度限流：总量 20000 QPS
        FlowRule clusterRule = new FlowRule();
        clusterRule.setResource(RESOURCE_ORDER_CREATE);
        clusterRule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        clusterRule.setCount(20000);
        clusterRule.setClusterMode(true);
        ClusterFlowConfig clusterConfig = new ClusterFlowConfig();
        clusterConfig.setThresholdType(ClusterRuleConstant.FLOW_THRESHOLD_GLOBAL);
        clusterConfig.setFallbackToLocalWhenFail(true); // 集群限流失败时降级为单机限流
        clusterRule.setClusterConfig(clusterConfig);

        rules.add(singleRule);
        rules.add(clusterRule);

        FlowRuleManager.loadRules(rules);
        log.info("[限流规则初始化] 资源={} 单机阈值={} 集群阈值={} 规则数={}",
                RESOURCE_ORDER_CREATE, 2000, 20000, rules.size());
    }
}
```

#### 7.1.4 接入层：注解 + 自定义 BlockHandler + 幂等控制

Controller 通过 `@SentinelResource` 声明资源并指定 BlockHandler；同时结合幂等 token，确保限流触发或重试时不会产生重复下单。

```java
@RestController
@RequestMapping("/order")
public class OrderController {

    private static final Logger log = LoggerFactory.getLogger(OrderController.class);

    @Autowired
    private OrderService orderService;

    @Autowired
    private IdempotentService idempotentService;

    /**
     * 创建订单接口
     *
     * @param request      下单请求体
     * @param idempotentKey 幂等键，由客户端在进入下单页时申请，保证同一次下单唯一
     */
    @PostMapping("/create")
    @SentinelResource(
            value = FlowRuleInitializer.RESOURCE_ORDER_CREATE,
            blockHandler = "handleOrderBlock",
            blockHandlerClass = OrderBlockHandler.class
    )
    public Result<OrderVO> createOrder(@RequestBody @Valid OrderCreateRequest request,
                                       @RequestHeader("Idempotent-Key") String idempotentKey) {
        // 幂等控制：先查缓存，命中则直接返回上次结果，避免限流重试导致重复下单
        OrderVO cached = idempotentService.getResult(idempotentKey, OrderVO.class);
        if (cached != null) {
            log.info("[下单幂等] 命中幂等缓存 idempotentKey={} orderId={}", idempotentKey, cached.getOrderId());
            return Result.success(cached);
        }

        // 使用幂等键抢占执行权，防止并发重复提交
        boolean locked = idempotentService.tryLock(idempotentKey, 10_000);
        if (!locked) {
            log.warn("[下单幂等] 重复提交被拦截 idempotentKey={}", idempotentKey);
            return Result.fail("REPEAT_SUBMIT", "订单正在处理中，请勿重复提交");
        }

        try {
            OrderVO vo = orderService.createOrder(request);
            // 写入幂等结果缓存，后续重试直接返回
            idempotentService.saveResult(idempotentKey, vo, 24, TimeUnit.HOURS);
            log.info("[下单成功] idempotentKey={} orderId={} userId={}",
                    idempotentKey, vo.getOrderId(), request.getUserId());
            return Result.success(vo);
        } catch (BusinessException e) {
            // 业务异常：释放锁，允许用户重试
            idempotentService.unlock(idempotentKey);
            log.warn("[下单业务异常] idempotentKey={} code={} msg={}",
                    idempotentKey, e.getCode(), e.getMessage());
            return Result.fail(e.getCode(), e.getMessage());
        } catch (Exception e) {
            idempotentService.unlock(idempotentKey);
            log.error("[下单系统异常] idempotentKey={} userId={}",
                    idempotentKey, request.getUserId(), e);
            return Result.fail("SYSTEM_ERROR", "系统繁忙，请稍后重试");
        }
    }
}
```

```java
/**
 * 自定义 BlockHandler
 *
 * 说明：
 * 1. 方法签名必须与被保护方法一致，并在末尾追加 BlockException 参数
 * 2. 必须为 public static
 * 3. 限流时返回用户友好提示，而不是抛出堆栈异常
 */
public class OrderBlockHandler {

    private static final Logger log = LoggerFactory.getLogger(OrderBlockHandler.class);

    public static Result<OrderVO> handleOrderBlock(OrderCreateRequest request,
                                                    String idempotentKey,
                                                    BlockException ex) {
        // 区分限流类型，便于监控与排查
        String blockType = ex instanceof FlowException ? "FLOW_LIMIT"
                : ex instanceof DegradeException ? "DEGRADE"
                : "OTHER_BLOCK";

        log.warn("[下单限流触发] blockType={} idempotentKey={} userId={} rule={}",
                blockType, idempotentKey,
                request != null ? request.getUserId() : null,
                ex.getRule());

        // 上报限流监控指标
        Metrics.counter("order.create.blocked", "type", blockType).increment();

        // 返回用户友好提示，前端可据此弹出排队/稍后重试的引导
        return Result.fail("RATE_LIMITED", "当前下单人数较多，请稍后再试~");
    }
}
```

#### 7.1.5 幂等服务实现

幂等控制是限流重试场景下防止重复下单的关键。基于 Redis 实现分布式幂等锁与结果缓存。

```java
/**
 * 幂等服务：基于 Redis 实现
 *
 * 幂等三要素：
 * 1. tryLock：SETNX 抢占执行权，防止并发重复提交
 * 2. saveResult：缓存执行结果，重试直接返回
 * 3. getResult：查询是否已执行
 */
@Service
public class IdempotentService {

    private static final Logger log = LoggerFactory.getLogger(IdempotentService.class);

    private static final String LOCK_PREFIX = "idem:lock:";
    private static final String RESULT_PREFIX = "idem:result:";

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Autowired
    private ObjectMapper objectMapper;

    /**
     * 抢占执行权
     *
     * @param key         幂等键
     * @param expireMillis 锁过期时间，防止死锁
     */
    public boolean tryLock(String key, long expireMillis) {
        try {
            Boolean ok = redisTemplate.opsForValue()
                    .setIfAbsent(LOCK_PREFIX + key, "1", expireMillis, TimeUnit.MILLISECONDS);
            return Boolean.TRUE.equals(ok);
        } catch (Exception e) {
            // Redis 异常时的容错策略：放行（宁可重复也不阻断），并告警
            log.error("[幂等] 获取幂等锁异常，降级放行 key={}", key, e);
            return true;
        }
    }

    public void unlock(String key) {
        try {
            redisTemplate.delete(LOCK_PREFIX + key);
        } catch (Exception e) {
            log.error("[幂等] 释放幂等锁异常 key={}", key, e);
        }
    }

    public <T> void saveResult(String key, T result, long timeout, TimeUnit unit) {
        try {
            String json = objectMapper.writeValueAsString(result);
            redisTemplate.opsForValue().set(RESULT_PREFIX + key, json, timeout, unit);
        } catch (Exception e) {
            log.error("[幂等] 保存幂等结果异常 key={}", key, e);
        }
    }

    public <T> T getResult(String key, Class<T> clazz) {
        try {
            String json = redisTemplate.opsForValue().get(RESULT_PREFIX + key);
            if (json == null) {
                return null;
            }
            return objectMapper.readValue(json, clazz);
        } catch (Exception e) {
            log.error("[幂等] 读取幂等结果异常 key={}", key, e);
            return null;
        }
    }
}
```

| 环节 | 组件 | 作用 |
|------|------|------|
| 入口幂等 | IdempotentService | 防止限流重试导致重复下单 |
| 单机限流 | TokenBucketRateLimiter | 快速拦截突发流量，无网络开销 |
| 集群限流 | SlidingWindowRateLimiter / Redis | 精确控制全局总量 |
| 规则管理 | FlowRuleManager | 动态推送阈值，秒级生效 |
| 限流兜底 | OrderBlockHandler | 返回友好提示，避免堆栈暴露 |
| 可观测 | Metrics 埋点 | 统计限流类型与拒绝量 |

关键注意点：BlockHandler 必须区分 `FlowException`（限流）与 `DegradeException`（熔断），二者虽都继承自 `BlockException`，但监控与用户提示需分别处理；幂等锁的 Redis 异常必须有容错策略，避免限流基础设施故障时阻断全部下单。

### 7.2 案例二：服务降级全链路

#### 7.2.1 场景描述

商品详情页 `GET /product/{id}` 需要聚合调用「商品基础服务」和「个性化推荐服务」。推荐服务属于非核心链路，在高峰期偶发超时。要求：

- 推荐服务超时（如 200ms）时触发降级，不能阻塞商品详情返回；
- 降级时优先返回缓存的历史推荐数据，缓存也不可用时返回静态兜底推荐；
- 支持通过配置中心的降级开关，运维可手动强制降级，摘除推荐服务；
- 降级逻辑本身不能依赖任何可能失败的远程服务。

全链路流转如下：

```
请求进入 /product/{id}
   │
   ▼
[并行调用] ── 商品基础服务（核心，不降级）
          └─ 推荐服务（非核心）
                 │
                 ▼
         [降级开关] ── 开启 ──▶ 直接走兜底，不发起调用
                 │ 关闭
                 ▼
         [超时/异常判断] ── 超时/失败 ──▶ 降级
                 │ 成功
                 ▼
         返回实时推荐
   │
   ▼
[降级路由] ── L1 缓存推荐 ──▶ 命中返回
          └─ L2 静态兜底 ──▶ 返回默认推荐
   │
   ▼
聚合结果返回
```

#### 7.2.2 降级开关管理

降级开关通过配置中心动态下发，支持手动强制降级与自动降级两种模式。

```java
/**
 * 降级开关管理器
 *
 * 支持两级开关：
 * 1. forceDegrade：手动强制降级（运维应急）
 * 2. autoDegradeEnabled：是否允许自动降级（超时/异常触发）
 *
 * 开关从配置中心（Nacos）监听，变更实时生效。
 */
@Component
public class DegradeSwitchManager {

    private static final Logger log = LoggerFactory.getLogger(DegradeSwitchManager.class);

    /** 强制降级开关：resource -> 是否强制降级 */
    private final Map<String, Boolean> forceDegradeMap = new ConcurrentHashMap<>();

    /** 自动降级总开关 */
    private volatile boolean autoDegradeEnabled = true;

    /**
     * 配置中心回调，规则变更时刷新本地缓存
     */
    public void onConfigChange(DegradeSwitchConfig config) {
        this.autoDegradeEnabled = config.isAutoDegradeEnabled();
        this.forceDegradeMap.clear();
        if (config.getForceDegradeResources() != null) {
            config.getForceDegradeResources().forEach(r -> forceDegradeMap.put(r, true));
        }
        log.info("[降级开关] 配置更新 autoEnabled={} 强制降级资源={}",
                autoDegradeEnabled, forceDegradeMap.keySet());
    }

    public boolean isForceDegrade(String resource) {
        return forceDegradeMap.getOrDefault(resource, false);
    }

    public boolean isAutoDegradeEnabled() {
        return autoDegradeEnabled;
    }
}
```

#### 7.2.3 带超时与降级的推荐服务调用

使用带超时的线程池隔离调用推荐服务，超时或异常时进入降级路由。

```java
/**
 * 推荐服务调用（含降级）
 */
@Service
public class RecommendFacade {

    private static final Logger log = LoggerFactory.getLogger(RecommendFacade.class);

    private static final String RESOURCE = "recommend:list";

    /** 隔离推荐调用的线程池，避免拖垮 Web 容器线程 */
    private final ExecutorService recommendPool = new ThreadPoolExecutor(
            20, 40, 60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(200),
            new ThreadFactoryBuilder().setNameFormat("recommend-pool-%d").build(),
            new ThreadPoolExecutor.AbortPolicy());

    /** 推荐调用超时时间（毫秒） */
    private static final long TIMEOUT_MS = 200;

    @Autowired
    private RecommendRpcClient recommendRpcClient;

    @Autowired
    private RecommendCache recommendCache;

    @Autowired
    private DegradeSwitchManager degradeSwitchManager;

    /**
     * 获取商品推荐列表，任何异常都不会向上抛出，保证详情页可用
     *
     * @param productId 商品ID
     * @param userId    用户ID
     */
    public List<RecommendItem> getRecommend(long productId, long userId) {
        // 1. 手动强制降级：直接走兜底，不发起远程调用
        if (degradeSwitchManager.isForceDegrade(RESOURCE)) {
            log.warn("[推荐降级] 命中强制降级开关 productId={} userId={}", productId, userId);
            return degradeRecommend(productId, userId, "FORCE");
        }

        // 2. 提交到隔离线程池，带超时执行
        Future<List<RecommendItem>> future = null;
        try {
            future = recommendPool.submit(() -> recommendRpcClient.query(productId, userId));
            List<RecommendItem> result = future.get(TIMEOUT_MS, TimeUnit.MILLISECONDS);
            // 成功则异步刷新缓存，供后续降级使用
            recommendCache.asyncSave(productId, result);
            return result;
        } catch (TimeoutException e) {
            if (future != null) {
                future.cancel(true);
            }
            log.warn("[推荐降级] 调用超时 timeout={}ms productId={} userId={}", TIMEOUT_MS, productId, userId);
            return degradeRecommend(productId, userId, "TIMEOUT");
        } catch (RejectedExecutionException e) {
            log.warn("[推荐降级] 线程池已满，快速降级 productId={} userId={}", productId, userId);
            return degradeRecommend(productId, userId, "POOL_FULL");
        } catch (Exception e) {
            log.error("[推荐降级] 调用异常 productId={} userId={}", productId, userId, e);
            return degradeRecommend(productId, userId, "EXCEPTION");
        }
    }

    /**
     * 降级路由：L1 缓存推荐 -> L2 静态兜底
     * 降级逻辑不依赖任何可能失败的远程服务
     */
    private List<RecommendItem> degradeRecommend(long productId, long userId, String reason) {
        Metrics.counter("recommend.degrade", "reason", reason).increment();

        // L1：本地/近端缓存的历史推荐
        List<RecommendItem> cached = recommendCache.getLocal(productId);
        if (cached != null && !cached.isEmpty()) {
            log.info("[推荐降级] 返回缓存推荐 reason={} productId={} size={}", reason, productId, cached.size());
            return cached;
        }

        // L2：静态兜底（热门商品，进程内常量，绝不失败）
        List<RecommendItem> fallback = StaticRecommendHolder.getHotItems();
        log.info("[推荐降级] 返回静态兜底 reason={} productId={} size={}", reason, productId, fallback.size());
        return fallback;
    }
}
```

#### 7.2.4 推荐缓存与静态兜底

降级数据源分两级：缓存的历史推荐与进程内静态热门推荐。静态兜底保证在缓存全部失效时仍有可返回的数据。

```java
/**
 * 推荐缓存：本地缓存 + Redis 二级缓存
 */
@Service
public class RecommendCache {

    private static final Logger log = LoggerFactory.getLogger(RecommendCache.class);

    /** 本地缓存，10 分钟过期，容量 1 万 */
    private final Cache<Long, List<RecommendItem>> localCache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(10, TimeUnit.MINUTES)
            .build();

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    private final ExecutorService saveExecutor = Executors.newSingleThreadExecutor(
            new ThreadFactoryBuilder().setNameFormat("recommend-cache-save-%d").setDaemon(true).build());

    /**
     * 读取本地缓存，本地未命中回源 Redis（回源同样容错）
     */
    @SuppressWarnings("unchecked")
    public List<RecommendItem> getLocal(long productId) {
        List<RecommendItem> local = localCache.getIfPresent(productId);
        if (local != null) {
            return local;
        }
        try {
            Object v = redisTemplate.opsForValue().get("recommend:cache:" + productId);
            if (v instanceof List) {
                List<RecommendItem> remote = (List<RecommendItem>) v;
                localCache.put(productId, remote);
                return remote;
            }
        } catch (Exception e) {
            // 降级读缓存失败绝不抛出，返回 null 让上层走静态兜底
            log.error("[推荐缓存] 读取 Redis 异常 productId={}", productId, e);
        }
        return null;
    }

    /**
     * 异步写缓存，不阻塞主流程
     */
    public void asyncSave(long productId, List<RecommendItem> items) {
        if (items == null || items.isEmpty()) {
            return;
        }
        localCache.put(productId, items);
        saveExecutor.execute(() -> {
            try {
                redisTemplate.opsForValue().set("recommend:cache:" + productId, items, 30, TimeUnit.MINUTES);
            } catch (Exception e) {
                log.error("[推荐缓存] 写入 Redis 异常 productId={}", productId, e);
            }
        });
    }
}
```


#### 7.2.5 聚合层：核心与非核心分离

商品详情聚合时，核心服务失败直接报错，非核心服务失败走降级，二者严格隔离。

```java
@Service
public class ProductDetailService {

    private static final Logger log = LoggerFactory.getLogger(ProductDetailService.class);

    @Autowired
    private ProductBaseFacade productBaseFacade;

    @Autowired
    private RecommendFacade recommendFacade;

     * 聚合商品详情

    public ProductDetailVO getDetail(long productId, long userId) {
```

#### 7.2.6 链路小结

| 环节 | 组件 | 作用 |
|------|------|------|
| 开关管理 | DegradeSwitchManager | 支持手动强制降级与自动降级 |
| 隔离调用 | RecommendFacade 线程池 | 超时/池满快速降级，不拖垮主线程 |
| 一级降级 | RecommendCache | 返回缓存的历史推荐 |
| 二级降级 | StaticRecommendHolder | 进程内静态兜底，绝不失败 |
| 核心隔离 | ProductDetailService | 核心失败即失败，非核心失败降级 |

关键注意点：降级方法内部必须自我消化所有异常，绝不能再向上抛；降级数据源要分级，最终兜底必须是进程内不依赖任何 IO 的静态数据；核心链路与非核心链路要在聚合层严格区分，避免非核心服务故障影响核心功能。

### 7.3 案例三：熔断器工作全链路

#### 7.3.1 场景描述

订单服务调用「支付网关」`payGateway.pay()`。当支付网关故障率飙升时，继续调用只会堆积线程、加剧故障。要求实现一个完整的三态熔断器：

- 基于滑动窗口统计失败率与慢调用率；
- 失败率超过阈值时熔断器打开（OPEN），快速失败；
- 打开一段时间后进入半开（HALF_OPEN），放行少量探测请求；
- 探测成功达标则关闭（CLOSED）恢复，探测失败则重新打开；
- 支付调用必须幂等，熔断恢复后的重试不能导致重复扣款。

状态机流转如下：

```
            失败率/慢调用率超阈值
   ┌──────────────────────────────┐
   │                              ▼
[CLOSED] ◀────探测成功达标──── [HALF_OPEN]
   ▲                              │
   │                              │ 探测失败
   │        等待恢复时间到         │
   └────────── [OPEN] ◀───────────┘
              快速失败
```

#### 7.3.2 熔断器状态机实现

```java
/**
 * 熔断器状态
 */
public enum CircuitBreakerState {
    /** 关闭：正常放行，统计失败率 */
    CLOSED,
    /** 打开：快速失败，不发起真实调用 */
    OPEN,
    /** 半开：放行少量探测请求 */
    HALF_OPEN
}
```

```java
/**
 * 三态熔断器
 *
 * 状态转换：
 * CLOSED  --失败率/慢调用率超阈值--> OPEN
 * OPEN    --恢复等待时间到--------> HALF_OPEN
 * HALF_OPEN --探测成功达标--------> CLOSED
 * HALF_OPEN --探测失败-----------> OPEN
 *
 * 线程安全：状态切换使用 AtomicReference + CAS，统计使用滑动窗口。
 */
public class CircuitBreaker {

    private static final Logger log = LoggerFactory.getLogger(CircuitBreaker.class);

    private final String resource;

    /** 当前状态 */
    private final AtomicReference<CircuitBreakerState> state =
            new AtomicReference<>(CircuitBreakerState.CLOSED);

    /** 滑动窗口统计（复用 3.4 熔断器设计中的实现） */
    private final CircuitBreakerStatistics statistics;

    /** 失败率阈值，如 0.5 表示失败率超过 50% 触发熔断 */
    private final double errorRatioThreshold;

    /** 慢调用率阈值 */
    private final double slowCallRatioThreshold;

    /** 触发熔断的最小请求数，样本太少不熔断，避免误判 */
    private final long minRequestCount;

    /** OPEN 状态持续时间（毫秒），到期后转 HALF_OPEN */
    private final long openTimeoutMs;

    /** 进入 OPEN 状态的时间戳 */
    private volatile long openTimestamp;

    /** 半开状态允许的探测请求数 */
    private final int halfOpenMaxProbes;

    /** 半开状态需要连续成功多少次才恢复 */
    private final int halfOpenSuccessThreshold;

    /** 半开状态已放行的探测数 */
    private final AtomicInteger halfOpenProbeCount = new AtomicInteger(0);

    /** 半开状态成功数 */
    private final AtomicInteger halfOpenSuccessCount = new AtomicInteger(0);

    public CircuitBreaker(String resource, double errorRatioThreshold, double slowCallRatioThreshold,
                          long minRequestCount, long openTimeoutMs, int halfOpenMaxProbes,
                          int halfOpenSuccessThreshold, CircuitBreakerStatistics statistics) {
        this.resource = resource;
        this.errorRatioThreshold = errorRatioThreshold;
        this.slowCallRatioThreshold = slowCallRatioThreshold;
        this.minRequestCount = minRequestCount;
        this.openTimeoutMs = openTimeoutMs;
        this.halfOpenMaxProbes = halfOpenMaxProbes;
        this.halfOpenSuccessThreshold = halfOpenSuccessThreshold;
        this.statistics = statistics;
    }

    /**
     * 是否允许本次请求通过
     */
    public boolean allowRequest() {
        CircuitBreakerState current = state.get();
        switch (current) {
            case CLOSED:
                return true;
            case OPEN:
                // 判断是否到达恢复探测时间
                if (System.currentTimeMillis() - openTimestamp >= openTimeoutMs) {
                    // 尝试从 OPEN 转到 HALF_OPEN
                    if (state.compareAndSet(CircuitBreakerState.OPEN, CircuitBreakerState.HALF_OPEN)) {
                        halfOpenProbeCount.set(0);
                        halfOpenSuccessCount.set(0);
                        log.warn("[熔断器] {} 状态切换 OPEN -> HALF_OPEN，开始探测", resource);
                    }
                    return tryAcquireProbe();
                }
                return false;
            case HALF_OPEN:
                return tryAcquireProbe();
            default:
                return true;
        }
    }

    /**
     * 半开状态限量放行探测请求
     */
    private boolean tryAcquireProbe() {
        if (state.get() != CircuitBreakerState.HALF_OPEN) {
            return state.get() == CircuitBreakerState.CLOSED;
        }
        int probe = halfOpenProbeCount.incrementAndGet();
        if (probe <= halfOpenMaxProbes) {
            return true;
        }
        // 探测名额已满，其余请求快速失败
        return false;
    }

    /**
     * 记录成功
     */
    public void onSuccess(long durationMs) {
        statistics.recordCompletion(durationMs, true);
        if (state.get() == CircuitBreakerState.HALF_OPEN) {
            int success = halfOpenSuccessCount.incrementAndGet();
            if (success >= halfOpenSuccessThreshold) {
                // 探测达标，恢复到 CLOSED
                if (state.compareAndSet(CircuitBreakerState.HALF_OPEN, CircuitBreakerState.CLOSED)) {
                    statistics.reset();
                    log.warn("[熔断器] {} 状态切换 HALF_OPEN -> CLOSED，服务已恢复", resource);
                }
            }
        }
    }

    /**
     * 记录失败
     */
    public void onFailure(long durationMs, Throwable cause) {
        statistics.recordCompletion(durationMs, false);
        CircuitBreakerState current = state.get();

        if (current == CircuitBreakerState.HALF_OPEN) {
            // 半开探测失败，立即重新打开
            if (state.compareAndSet(CircuitBreakerState.HALF_OPEN, CircuitBreakerState.OPEN)) {
                openTimestamp = System.currentTimeMillis();
                log.warn("[熔断器] {} 探测失败，状态切换 HALF_OPEN -> OPEN cause={}",
                        resource, cause == null ? "unknown" : cause.getMessage());
            }
            return;
        }

        if (current == CircuitBreakerState.CLOSED) {
            // 判断是否达到熔断条件
            CircuitBreakerStat stat = statistics.getStat();
            if (stat.getTotalCount() >= minRequestCount
                    && (stat.getErrorRatio() >= errorRatioThreshold
                        || stat.getSlowCallRatio() >= slowCallRatioThreshold)) {
                if (state.compareAndSet(CircuitBreakerState.CLOSED, CircuitBreakerState.OPEN)) {
                    openTimestamp = System.currentTimeMillis();
                    log.error("[熔断器] {} 触发熔断，状态切换 CLOSED -> OPEN 失败率={} 慢调用率={} 样本={}",
                            resource, stat.getErrorRatio(), stat.getSlowCallRatio(), stat.getTotalCount());
                    Metrics.counter("circuit.open", "resource", resource).increment();
                }
            }
        }
    }

    public CircuitBreakerState getState() {
        return state.get();
    }
}
```

#### 7.3.3 熔断器包装的支付调用（含幂等）

支付调用通过熔断器保护，并携带幂等流水号，保证熔断恢复后的重试不会重复扣款。

```java
@Service
public class PaymentService {

    private static final Logger log = LoggerFactory.getLogger(PaymentService.class);

    private static final String RESOURCE = "pay:gateway";

    private final CircuitBreaker circuitBreaker;

    @Autowired
    private PayGatewayClient payGatewayClient;

    @Autowired
    private PaymentRecordRepository paymentRecordRepository;

    public PaymentService(CircuitBreakerFactory factory) {
        // 失败率 50%、慢调用率 60%、最小样本 20、熔断 5s、半开探测 5 次、连续成功 3 次恢复
        this.circuitBreaker = factory.create(RESOURCE, 0.5, 0.6, 20,
                5000, 5, 3);
    }

    /**
     * 发起支付
     *
     * @param payNo 支付流水号，全局唯一，用于幂等
     */
    public PayResult pay(String payNo, long orderId, long amount) {
        // 幂等校验：同一流水号若已支付成功，直接返回历史结果
        PaymentRecord existing = paymentRecordRepository.findByPayNo(payNo);
        if (existing != null && existing.isSuccess()) {
            log.info("[支付幂等] 命中已支付流水 payNo={} orderId={}", payNo, orderId);
            return PayResult.of(existing);
        }

        // 熔断判断
        if (!circuitBreaker.allowRequest()) {
            log.warn("[支付熔断] 熔断器打开，快速失败 payNo={} orderId={} state={}",
                    payNo, orderId, circuitBreaker.getState());
            Metrics.counter("pay.circuit.rejected", "resource", RESOURCE).increment();
            // 熔断兜底：返回处理中，由后续对账/重试补偿，不阻塞用户
            return PayResult.pending(payNo, "支付通道繁忙，请稍后查询支付结果");
        }

        long start = System.currentTimeMillis();
        try {
            // 携带 payNo 保证网关侧幂等（网关根据 payNo 去重）
            PayResult result = payGatewayClient.pay(payNo, orderId, amount);
            long cost = System.currentTimeMillis() - start;

            if (result.isSuccess()) {
                circuitBreaker.onSuccess(cost);
                paymentRecordRepository.saveSuccess(payNo, orderId, amount);
                log.info("[支付成功] payNo={} orderId={} amount={} cost={}ms", payNo, orderId, amount, cost);
            } else {
                // 网关返回业务失败（如余额不足），不计入熔断统计
                paymentRecordRepository.saveFail(payNo, orderId, result.getCode());
                log.warn("[支付业务失败] payNo={} orderId={} code={}", payNo, orderId, result.getCode());
            }
            return result;
        } catch (PayGatewayTimeoutException | PayGatewayServerException e) {
            // 系统异常：计入熔断统计
            long cost = System.currentTimeMillis() - start;
            circuitBreaker.onFailure(cost, e);
            log.error("[支付系统异常] payNo={} orderId={} cost={}ms", payNo, orderId, cost, e);
            // 结果未知，标记为处理中，交由对账补偿，绝不直接判失败以免误判
            return PayResult.pending(payNo, "支付结果确认中，请稍后查询");
        } catch (Exception e) {
            long cost = System.currentTimeMillis() - start;
            circuitBreaker.onFailure(cost, e);
            log.error("[支付未知异常] payNo={} orderId={}", payNo, orderId, e);
            return PayResult.pending(payNo, "支付结果确认中，请稍后查询");
        }
    }
}
```

#### 7.3.4 链路小结

| 状态 | 行为 | 转换条件 |
|------|------|---------|
| CLOSED | 正常放行，统计失败率/慢调用率 | 达阈值且样本足够 → OPEN |
| OPEN | 快速失败，走兜底 | 等待恢复时间到 → HALF_OPEN |
| HALF_OPEN | 限量放行探测 | 连续成功达标 → CLOSED；任一失败 → OPEN |

关键注意点：熔断统计要区分系统异常与业务异常，业务失败（如余额不足）不能计入熔断；触发熔断需设置最小样本数，避免流量极低时的偶发失败误触发；支付这类涉及资金的调用，熔断兜底应返回「处理中」并交由对账补偿，而不是直接判定失败，配合 payNo 幂等保证不重复扣款；半开状态必须限量探测并渐进恢复，防止恢复瞬间流量再次打垮下游。
