# 分布式事务

## 一、问题背景

### 1.1 从单机事务到分布式事务

在互联网应用井喷式增长的背景下，业务系统从单体架构演进为微服务架构。以电商场景为例，最初可能只是一个单一系统，随着用户量和交易量的增长，系统被垂直拆分为用户系统、订单系统、支付系统、交易系统等。每个子系统拥有独立的数据库实例，一次完整的业务操作需要跨多个服务、多个数据库协作完成。

在单体架构下，一次操作涉及多张数据表的数据变更，可以通过本地数据库事务保证ACID特性——要么全部变更成功，要么全部不变更回滚。但在微服务架构下，原本在一个服务内闭环的简单操作变成了需要多个不同服务协作完成的复杂操作，不同服务对应不同的数据资源，传统的单机事务管理器控制域只作用于本地，不支持跨服务传递，分布式事务问题由此产生。

产生分布式事务的原因可以归纳为两类：

**服务多节点**：SOA/微服务场景下，大而全的服务按业务领域拆分。例如服务B的某个方法既需要更新本地数据库B的数据，又需要通过RPC调用服务A和服务C更新各自数据库的数据，如何保证这组操作的原子性就成了分布式事务问题。

```java
// 服务B - 跨服务操作场景
public class OrderService {

    public void createOrder() {
        // 更新本地数据库的订单数据
        this.updateOrderInLocalDB();
        // 调用远程库存服务扣减库存
        inventoryService.deductStock();
        // 调用远程积分服务增加积分
        pointService.addPoints();
    }
}
```

**资源多节点**：业务规模发展到一定程度后，除了纵向拆分，还会进行数据水平拆分——分库分表、分库分集群。原本在单个数据库内的简单数据操作变成了涉及多个数据库的跨库操作，此时如果对操作有事务要求，同样产生分布式事务问题。

```java
// 同一服务内跨数据库操作场景
public class LocalService {

    public void updateAll() {
        // 更新数据库A的数据
        this.updateSthInDatabaseA();
        // 更新数据库B的数据
        this.updateSthInDatabaseB();
        // 更新数据库C的数据
        this.updateSthInDatabaseC();
    }
}
```

### 1.2 CAP与BASE理论

**CAP理论**是分布式系统的基石。该理论认为一个分布式系统中，一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance）三者不可得兼：

| 选择 | 说明 |
| --- | --- |
| CA | 放弃分区容错性，保证一致性和可用性，即传统单机数据库的选择 |
| AP | 放弃强一致性，追求分区容错性和可用性，这是大多数分布式系统的选择 |
| CP | 放弃可用性，追求一致性和分区容错性，网络问题会导致系统不可用 |

由于分布式系统必然部署在不同网络节点上，分区容错性是基本要求。因此设计分布式系统时，主要精力放在一致性与可用性之间寻求平衡。

**BASE理论**是对CAP中一致性和可用性权衡的结果，包含三个要素：

- **基本可用（Basically Available）**：分布式系统在出现故障后，允许部分可用性损失，保证核心服务或链路可用。例如电商大促时，部分非核心功能降级，保证核心交易链路可用。
- **软状态（Soft State）**：允许系统中的数据存在中间状态，该中间状态不影响系统整体功能。例如商品剩余数量、评论数、点赞数等允许短暂不一致。
- **最终一致性（Eventually Consistent）**：所有数据副本在经过一段时间的同步后，最终达到一致状态，不需要实时保证强一致性。

BASE理论面向大型高可用可扩展的分布式系统，与ACID强一致性模型相反，通过牺牲强一致性来获得可用性，允许数据在一段时间内不一致，但最终达到一致状态。

### 1.3 分布式事务的核心挑战

分布式事务面临的核心挑战包括：

1. **网络不可靠**：分布式系统通过网络通信，网络分区、超时、丢包等问题不可避免
2. **协调者单点**：事务协调者宕机会导致整个事务状态不确定
3. **同步阻塞**：资源锁定期间其他操作被阻塞，影响系统吞吐量
4. **数据不一致**：部分参与者提交成功、部分失败导致数据不一致
5. **性能损耗**：跨网络的多轮交互带来显著的延迟开销

## 二、整体架构设计

### 2.1 核心概念与角色

分布式事务框架中涉及以下核心概念：

| 名词 | 概念 |
| --- | --- |
| 事务管理器（Transaction Manager） | 独立服务，控制分布式事务生命周期，包括创建主事务记录、分支事务记录，根据事务状态调用参与者提交或回滚 |
| 资源管理器（Resource Manager） | 持久化数据存储，如关系型数据库、消息队列，通常理解为数据源适配器 |
| 事务协调器（Transaction Coordinator） | 独立模块，控制事务提交和回滚操作，可嵌入客户端或作为独立服务部署 |
| 全局事务（Global Transaction） | 逻辑概念，包含多个分支事务，发起方通过修改全局事务状态控制分支事务的提交/回滚 |
| 分支事务（Branch Transaction） | 逻辑概念，一个分布式事务可能包含多个数据库本地事务 |
| 事务发起方（Launcher） | 发起分布式事务的一方，有且仅有一个，决定整个事务提交或回滚 |
| 事务参与方（Participant） | 提供分支事务服务，被发起方调用后纳入分布式事务，可以有多个 |

### 2.2 解决方案全景

分布式事务解决方案按一致性要求和适用场景可分为以下几类：

```
┌─────────────────────────────────────────────────────────┐
│                  分布式事务解决方案                        │
├──────────────┬──────────────┬──────────────┬────────────┤
│   2PC/XA     │     TCC      │    Saga      │  可靠消息   │
│  (强一致性)   │ (最终一致性)  │ (最终一致性)  │ (最终一致性) │
├──────────────┼──────────────┼──────────────┼────────────┤
│ 数据库层面控制 │ 业务层面控制  │ 长流程补偿    │ 异步解耦    │
│ 代码无侵入    │ 代码侵入高    │ 代码侵入中    │ 代码侵入低  │
│ 性能差       │ 性能好        │ 性能好        │ 性能好      │

```

## 三、核心链路设计

### 3.1 两阶段提交（2PC）

#### 3.1.1 协议原理

两阶段提交协议是使用最广泛的分布式事务协议，很多分布式事务处理方式都基于该协议或以其为基础进行优化。协议将事务分为两个阶段：

**第一阶段——准备阶段（Prepare Phase）**：
事务协调者向每个事务参与者发送"准备"指令，每个参与者执行本地事务（写redo和undo日志），但不进行commit，到达临界状态后返回准备完成或失败。此时参与者持有锁资源不释放。

**第二阶段——提交阶段（Commit Phase）**：
协调者收集所有参与者在准备阶段的返回信息。如果都成功，通知所有参与者进行Commit；如果有失败或超时，通知所有参与者进行Rollback。参与者根据指令执行操作，释放锁资源。

将事务划分为两个阶段的目的：在准备阶段完成几乎所有正式提交工作，最后的提交动作是一个耗时极少的操作，这样"网络通信的危险期"很短，从而确保分布式事务的成功率。

#### 3.1.2 2PC的问题分析

**场景一：准备阶段失败**

在第一阶段向资源管理器2发送准备命令时出现失败，那么需要在第二阶段向所有参与者发起回滚操作。此时存在以下问题：
- 如果参与者1准备成功后，参与者2一直不返回，整个业务流程无法推进，存在阻塞问题
- 如果协调者获取所有准备就绪结果后、发起二阶段前宕机，存在单点问题

**场景二：提交阶段失败**

在第二阶段向参与者2发送提交时出现网络超时，导致参与者1已提交、参与者2无法提交，产生数据不一致。

2PC的三大核心缺陷：
1. **协调者单点问题**：事务管理器宕机后，整个事务状态无法保证
2. **同步阻塞**：准备就绪后，如果其他参与者无法返回结果，资源无法释放
3. **数据一致性问题**：部分参与者提交成功、部分失败导致数据不一致

三阶段提交（3PC）在2PC基础上加入了超时机制与自动提交，但本质上仍未解决一致性问题。

#### 3.1.3 XA协议

XA协议是X/OPEN提出的分布式事务处理规范，采用两阶段提交方式管理分布式事务。目前主流数据库（MySQL、Oracle等）都通过XA协议支持了2PC方案。以下是Java中使用XA协议的示例：

```java
import javax.transaction.xa.XAResource;
import javax.sql.XAConnection;
import com.mysql.cj.jdbc.MysqlXADataSource;

public class XATransactionExample {

    public void executeXATransaction() throws Exception {
        // 创建两个数据源的XA连接
        MysqlXADataSource ds1 = createXADataSource("jdbc:mysql://db1:3306/order_db");
        MysqlXADataSource ds2 = createXADataSource("jdbc:mysql://db2:3306/inventory_db");

        XAConnection xaConn1 = ds1.getXAConnection();
        XAConnection xaConn2 = ds2.getXAConnection();

        XAResource xaRes1 = xaConn1.getXAResource();
        XAResource xaRes2 = xaConn2.getXAResource();

        // 创建全局事务ID
        Xid xid1 = createXid(1);
        Xid xid2 = createXid(2);

        try {
            // 第一阶段：准备
            xaRes1.start(xid1, XAResource.TMNOFLAGS);
            Connection conn1 = xaConn1.getConnection();
            conn1.createStatement().executeUpdate(
                "UPDATE order_table SET status = 'PAID' WHERE order_id = '12345'");
            xaRes1.end(xid1, XAResource.TMSUCCESS);

            xaRes2.start(xid2, XAResource.TMNOFLAGS);
            Connection conn2 = xaConn2.getConnection();
            conn2.createStatement().executeUpdate(
                "UPDATE inventory SET stock = stock - 1 WHERE sku_id = 'SKU001'");
            xaRes2.end(xid2, XAResource.TMSUCCESS);

            // 两阶段提交
            int prepare1 = xaRes1.prepare(xid1);
            int prepare2 = xaRes2.prepare(xid2);

            // 第二阶段：根据准备结果决定提交或回滚
            if (prepare1 == XAResource.XA_OK && prepare2 == XAResource.XA_OK) {
                xaRes1.commit(xid1, false);
                xaRes2.commit(xid2, false);
                System.out.println("全局事务提交成功");
            } else {
                xaRes1.rollback(xid1);
                xaRes2.rollback(xid2);
                System.out.println("全局事务回滚");
            }
        } catch (Exception e) {
            // 异常回滚
            xaRes1.rollback(xid1);
            xaRes2.rollback(xid2);
            throw e;
        } finally {
            xaConn1.close();
            xaConn2.close();
        }
    }

    private MysqlXADataSource createXADataSource(String url) {
        MysqlXADataSource ds = new MysqlXADataSource();
        ds.setUrl(url);
        ds.setUser("root");
        ds.setPassword("password");
        return ds;
    }

    private Xid createXid(int branchId) {
        byte[] gtrid = new byte[36];
        byte[] bqual = new byte[36];
        // 填充全局事务ID和分支限定符
        return new XidImpl(gtrid, bqual, branchId);
    }
}
```

### 3.2 TCC（Try-Confirm-Cancel）

#### 3.2.1 模型原理

TCC实际上是服务化的两阶段提交协议，主要实现最终一致性，面向业务层面的事务控制。整个方案有三段业务逻辑：

- **Try（尝试操作）**：事务发起方对所有参与方执行Try操作，进行业务检查（一致性），完成业务资源的预留和锁定（准隔离性）
- **Confirm（确认操作）**：如果Try阶段全部成功，不做业务检查，直接执行业务逻辑，使用Try阶段预留的资源
- **Cancel（取消操作）**：如果流程中出现失败，执行补偿逻辑，释放Try阶段预留的资源

TCC巧妙规避了2PC的问题：
1. **协调者单点**→将协调者变为多点集群
2. **同步阻塞**→引入超时机制，超时后补偿处理
3. **数据不一致**→引入补偿后，数据会在一定时间后达到一致

#### 3.2.2 角色划分

在TCC模型中，协调者由两个组件担任：

**主业务活动**：发起业务活动，登记业务操作，只参与一阶段，业务活动的最终状态就是分布式事务的最终状态。

**业务活动管理器**：记录活动日志，推进业务活动，在业务处理超时后进行补偿操作，保证分布式事务达到一致状态。

参与者负责提供Try、Confirm、Cancel三个方法，由于业务活动管理器在超时后会发起重试，Confirm/Cancel接口需要支持幂等。

#### 3.2.3 两种TCC实现模式

**应用级模式（本地化TCC）**：

协调者的业务活动与活动管理器都属于应用中，服务多台部署，不存在单点问题。业务活动的注册、提交/回滚操作与业务操作在一个线程中处理，效率高。但活动日志记录侵入业务系统数据库，且扩容受应用系统影响。

```java
// 应用级TCC实现示例
public class OrderTccAction {

    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private TransactionLogMapper logMapper;

    // Try阶段：创建待确认状态的订单
    public boolean tryCreateOrder(OrderDTO orderDTO) {
        // 业务检查
        if (orderMapper.findByOrderId(orderDTO.getOrderId()) != null) {
            return true; // 幂等处理
        }
        // 预留资源，创建待确认状态订单
        Order order = new Order();
        order.setOrderId(orderDTO.getOrderId());
        order.setStatus(OrderStatus.TRYING);
        order.setAmount(orderDTO.getAmount());
        orderMapper.insert(order);

        // 记录事务日志
        TransactionLog log = new TransactionLog();
        log.setTxId(orderDTO.getTxId());
        log.setBranchId(orderDTO.getBranchId());
        log.setStatus("TRY");
        log.setAction("CREATE_ORDER");
        logMapper.insert(log);
        return true;
    }

    // Confirm阶段：确认订单
    public boolean confirmCreateOrder(String txId) {
        TransactionLog log = logMapper.findByTxIdAndAction(txId, "CREATE_ORDER");
        if ("CONFIRMED".equals(log.getStatus())) {
            return true; // 幂等处理
        }
        // 使用Try阶段预留的资源，更新订单状态
        Order order = orderMapper.findByTxId(txId);
        order.setStatus(OrderStatus.CONFIRMED);
        orderMapper.updateStatus(order);

        log.setStatus("CONFIRMED");
        logMapper.updateStatus(log);
        return true;
    }

    // Cancel阶段：取消订单
    public boolean cancelCreateOrder(String txId) {
        TransactionLog log = logMapper.findByTxIdAndAction(txId, "CREATE_ORDER");
        if ("CANCELLED".equals(log.getStatus())) {
            return true; // 幂等处理
        }
        // 释放Try阶段预留的资源
        Order order = orderMapper.findByTxId(txId);
        if (order != null && order.getStatus() == OrderStatus.TRYING) {
            order.setStatus(OrderStatus.CANCELLED);
            orderMapper.updateStatus(order);
        }

        log.setStatus("CANCELLED");
        logMapper.updateStatus(log);
        return true;
    }
}
```

**集群模式（远程式TCC）**：

将一个分布式事务分为一个全局事务加若干个分支事务，采用中心化部署的协调者集群完成全局事务的提交。业务数据与活动日志数据分离存储，系统便于扩容。但实现难度大，活动日志的注册、提交/回滚的协调通过RPC实现，稳定性相对较差。

#### 3.2.4 TCC的异常问题处理

**空回滚问题**：因网络延时，Cancel请求可能比Try请求先到达事务参与方。如果Cancel直接返回成功，当Try后到达时会导致资源一直被锁定无法释放。框架一般通过默认生成一个回滚记录来保证Try请求后到达也不会造成资源锁定。

**事务悬挂问题**：空回滚后Try请求到达，参与方执行了Try操作预留资源，但全局事务已经回滚，这些预留资源永远不会被Confirm或Cancel。解决方案是在Try操作前检查是否已有回滚记录。

```java
// 空回滚和事务悬挂的处理
public class TccParticipantHandler {

    @Autowired
    private TccTransactionRecordMapper recordMapper;

    public boolean tryAction(String xid, String branchId, BusinessParam param) {
        // 检查是否已经执行过Cancel（防止事务悬挂）
        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);
        if (record != null && "CANCELLED".equals(record.getStatus())) {
            // 已经回滚过，拒绝执行Try
            return false;
        }
        // 正常执行Try逻辑
        return doTry(param);
    }

    public boolean cancelAction(String xid, String branchId) {
        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);
        if (record == null) {
            // Try未执行，插入回滚记录（防止空回滚后的悬挂）
            record = new TccTransactionRecord();
            record.setXid(xid);
            record.setBranchId(branchId);
            record.setStatus("CANCELLED");
            recordMapper.insert(record);
            return true; // 空回滚成功
        }
        if ("CANCELLED".equals(record.getStatus())) {
            return true; // 幂等
        }
        // 正常执行Cancel逻辑
        return doCancel(record);
    }

    public boolean confirmAction(String xid, String branchId) {
        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);
        if (record == null) {
            return false; // Try未执行，不能Confirm
        }
        if ("CONFIRMED".equals(record.getStatus())) {
            return true; // 幂等
        }
        return doConfirm(record);
    }
}
```

#### 3.2.5 TCC的业务拆分案例

用户接入TCC，最重要的是考虑如何将业务模型拆成两阶段来实现。以转账场景为例：

```java
// 转账场景的TCC实现
public class AccountTccService {

    @Autowired
    private AccountMapper accountMapper;

    // Try：冻结转出金额
    public boolean tryTransfer(String fromAccountId, String toAccountId, 
                                BigDecimal amount, String txId) {
        // 幂等检查
        if (isProcessed(txId, "TRY")) {
            return true;
        }
        Account fromAccount = accountMapper.findById(fromAccountId);
        // 业务检查：余额是否充足
        if (fromAccount.getAvailableBalance().compareTo(amount) < 0) {
            throw new RuntimeException("余额不足");
        }
        // 预留资源：冻结金额
        fromAccount.setFrozenAmount(
            fromAccount.getFrozenAmount().add(amount));
        fromAccount.setAvailableBalance(
            fromAccount.getAvailableBalance().subtract(amount));
        accountMapper.update(fromAccount);
        markProcessed(txId, "TRY");
        return true;
    }

    // Confirm：确认扣款和入账
    public boolean confirmTransfer(String fromAccountId, String toAccountId,
                                    BigDecimal amount, String txId) {
        if (isProcessed(txId, "CONFIRM")) {
            return true; // 幂等
        }
        Account fromAccount = accountMapper.findById(fromAccountId);
        Account toAccount = accountMapper.findById(toAccountId);

        // 扣减冻结金额
        fromAccount.setFrozenAmount(
            fromAccount.getFrozenAmount().subtract(amount));
        fromAccount.setTotalBalance(
            fromAccount.getTotalBalance().subtract(amount));
        // 入账
        toAccount.setAvailableBalance(
            toAccount.getAvailableBalance().add(amount));
        toAccount.setTotalBalance(
            toAccount.getTotalBalance().add(amount));

        accountMapper.update(fromAccount);
        accountMapper.update(toAccount);
        markProcessed(txId, "CONFIRM");
        return true;
    }

    // Cancel：解冻金额
    public boolean cancelTransfer(String fromAccountId, String toAccountId,
                                   BigDecimal amount, String txId) {
        if (isProcessed(txId, "CANCEL")) {
            return true; // 幂等
        }
        Account fromAccount = accountMapper.findById(fromAccountId);
        // 解冻
        fromAccount.setFrozenAmount(
            fromAccount.getFrozenAmount().subtract(amount));
        fromAccount.setAvailableBalance(
            fromAccount.getAvailableBalance().add(amount));
        accountMapper.update(fromAccount);
        markProcessed(txId, "CANCEL");
        return true;
    }

    private boolean isProcessed(String txId, String phase) {
        // 查询事务记录表判断是否已处理
        return false;
    }

    private void markProcessed(String txId, String phase) {
        // 记录事务处理状态
    }
}
```

### 3.3 Saga模式

#### 3.3.1 模型原理

Saga是一种处理长活事务（Long Lived Transaction）的方案，核心思想是将一个跨服务跨数据库的业务流程（全局事务）分解为一系列可以保证事务性的业务动作（分支事务）集合。每个业务动作（Do）都是保持ACID特性的真实事务，且都需要提供相应的补偿操作（Compensate）。

Saga模式是一种分布式异步事务，保证最终一致性，最早由H.Garcia-Molina等人提出。与TCC不同，Saga一阶段就会提交本地事务，不需要资源预留。

按照执行顺序分为两种流程：

- **正向业务流程**：按顺序依次执行所有业务动作（Do），每个动作执行完立即提交
- **逆向补偿流程**：如果流程中出现异常，通过补偿操作（Compensate）按反向顺序依次撤销已执行的业务操作

```
正向流程:  Do(A) → Do(B) → Do(C) → Do(D)  [全部成功，事务完成]
逆向补偿:  Do(A) → Do(B) → Do(C) [失败] → Compensate(B) → Compensate(A) [回滚完成]
```

#### 3.3.2 Saga的两种实现方式

**编排式（Orchestration）**：由一个中央协调器控制整个Saga的执行流程，负责按顺序调用各参与者的Do操作，并在失败时调用Compensate操作。

**协同式（Choreography）**：没有中央协调器，各参与者通过事件驱动的方式响应和触发后续操作。

```java
// 编排式Saga实现
public class OrderSagaOrchestrator {

    @Autowired
    private OrderService orderService;
    @Autowired
    private PaymentService paymentService;
    @Autowired
    private InventoryService inventoryService;
    @Autowired
    private LogisticsService logisticsService;
    @Autowired
    private SagaLogRepository sagaLogRepository;

    public void executeOrderSaga(OrderRequest request) {
        String sagaId = generateSagaId();
        SagaContext context = new SagaContext(sagaId, request);

        try {
            // Step 1: 创建订单
            sagaLogRepository.log(sagaId, "CREATE_ORDER", "STARTED");
            orderService.createOrder(request);
            sagaLogRepository.log(sagaId, "CREATE_ORDER", "COMPLETED");

            // Step 2: 支付
            sagaLogRepository.log(sagaId, "PAYMENT", "STARTED");
            paymentService.processPayment(request.getOrderId(), request.getAmount());
            sagaLogRepository.log(sagaId, "PAYMENT", "COMPLETED");

            // Step 3: 扣减库存
            sagaLogRepository.log(sagaId, "DEDUCT_INVENTORY", "STARTED");
            inventoryService.deduct(request.getSkuId(), request.getQuantity());
            sagaLogRepository.log(sagaId, "DEDUCT_INVENTORY", "COMPLETED");

            // Step 4: 创建物流单
            sagaLogRepository.log(sagaId, "CREATE_LOGISTICS", "STARTED");
            logisticsService.createShipment(request.getOrderId(), request.getAddress());
            sagaLogRepository.log(sagaId, "CREATE_LOGISTICS", "COMPLETED");

            sagaLogRepository.markSagaCompleted(sagaId);

        } catch (Exception e) {
            sagaLogRepository.log(sagaId, "SAGA_FAILED", e.getMessage());
            compensate(sagaId, context);
        }
    }

    private void compensate(String sagaId, SagaContext context) {
        // 按反向顺序执行补偿
        List<SagaLog> completedSteps = sagaLogRepository
            .findCompletedStepsInReverseOrder(sagaId);

        for (SagaLog step : completedSteps) {
            try {
                switch (step.getAction()) {
                    case "CREATE_LOGISTICS":
                        logisticsService.cancelShipment(context.getOrderId());
                        break;
                    case "DEDUCT_INVENTORY":
                        inventoryService.restore(context.getSkuId(), context.getQuantity());
                        break;
                    case "PAYMENT":
                        paymentService.refund(context.getOrderId(), context.getAmount());
                        break;
                    case "CREATE_ORDER":
                        orderService.cancelOrder(context.getOrderId());
                        break;
                }
                sagaLogRepository.log(sagaId, step.getAction() + "_COMPENSATE", "COMPLETED");
            } catch (Exception e) {
                sagaLogRepository.log(sagaId, step.getAction() + "_COMPENSATE", "FAILED");
                // 补偿失败，记录后继续尝试其他步骤的补偿
                // 实际场景中需要重试机制
            }
        }
    }
}
```

#### 3.3.3 Saga的适用场景与优劣

**适用场景**：
- 业务流程长、业务流程多，且需要保证事务最终一致性的业务系统
- 参与者包含其他公司或遗留系统服务，无法提供TCC模式要求的三个接口
- 弱隔离性、弱一致性要求的业务活动
- 适合执行时间较长的业务活动，如工作流

**优势**：
- 一阶段提交本地事务，无资源锁定，性能好
- 每个子事务都是独立的本地事务，不存在长期锁定资源的问题

**缺陷**：
- 隔离性差：一旦事务A执行完即提交，整个全局事务未完成时，外部已可以获取事务A提交的数据，容易造成脏读
- 还原度差：由于隔离性差，一旦走逆向补偿流程，完全还原到提交前的状态在高并发时基本不可能

### 3.4 AT模式（自动补偿模式）

#### 3.4.1 AT模式原理

AT模式是2PC方案的应用层实现，开发者只需关注业务逻辑实现，不需要关注分布式场景下的事务保证。框架通过代理SQL的方式自动完成事务的注册、提交、回滚等操作，具有代码无侵入、接入简单、适用场景广泛等优点。

AT模式的核心原理是在应用层实现SQL解析并自动补偿。一阶段拦截业务SQL，解析SQL语义，在数据变更前后保存快照（before image和after image），生成undo log，最后提交本地事务。二阶段提交时异步删除undo log；二阶段回滚时根据undo log自动生成反向SQL进行数据恢复。

#### 3.4.2 一阶段执行流程

```java
// AT模式一阶段执行的核心逻辑
protected T executeAutoCommitFalse(Object[] args) throws Exception {
    // 1. 解析SQL语义，查询变更前数据（before image）
    TableRecords beforeImage = beforeImage();

    // 2. 执行业务SQL
    T result = statementCallback.execute(
        statementProxy.getTargetStatement(), args);

    // 3. 查询变更后数据（after image）
    TableRecords afterImage = afterImage(beforeImage);

    // 4. 通过before image和after image生成undo log
    prepareUndoLog(beforeImage, afterImage);

    // 5. 返回业务SQL执行结果
    return result;
}
```

以一条UPDATE语句为例，AT模式的执行步骤：

```sql
-- 原始业务SQL
UPDATE table_1 SET biz_status = 10 WHERE id = 10 AND biz_status = 0;
```

执行过程中框架自动生成的SQL：

```sql
-- Step 1: 查询变更前数据（before image）
SELECT id, order_id, biz_status, add_by, add_time, update_by, update_time
FROM table_1 WHERE id = 10 AND biz_status = 0 FOR UPDATE;

-- Step 2: 执行业务SQL
UPDATE table_1 SET biz_status = 10 WHERE id = 10 AND biz_status = 0;

-- Step 3: 查询变更后数据（after image）
SELECT id, order_id, biz_status, add_by, add_time, update_by, update_time
FROM table_1 WHERE id = 10;
```

生成的undo log结构：

```java
public class SQLUndoLog {
    private SQLType sqlType;       // SQL类型：UPDATE
    private String tableName;       // 表名：table_1
    private TableRecords beforeImage;  // 变更前快照
    private TableRecords afterImage;   // 变更后快照
}
```

#### 3.4.3 本地事务提交流程

```java
// AT模式本地事务提交
public void commit() throws SQLException {
    if (context.inGlobalTransaction()) {
        processGlobalTransactionCommit();
    } else if (context.isGlobalLockRequire()) {
        processLocalCommitWithGlobalLocks();
    } else {
        targetConnection.commit();
    }
}

private void processGlobalTransactionCommit() throws SQLException {
    try {
        // Step 1: 注册分支事务并获取全局锁
        register();
    } catch (TransactionException e) {
        recognizeLockKeyConflictException(e);
    }
    try {
        // Step 2: 将undo log刷至数据库
        if (context.hasUndoLog()) {
            UndoLogManager.flushUndoLogs(this);
        }
        // Step 3: 提交本地事务（业务数据+undo log在同一本地事务中提交）
        targetConnection.commit();
    } catch (Throwable ex) {
        // Step 4: 异常时报告失败
        report(false);
        if (ex instanceof SQLException) {
            throw new SQLException(ex);
        }
    }
    // Step 5: 报告本地事务状态正常
    report(true);
    context.reset();
}
```

#### 3.4.4 二阶段回滚流程

当全局事务决定回滚时，协调器通知各分支事务进行回滚。框架根据undo log中的before image自动生成反向SQL进行数据恢复：

```java
public class UndoLogManager {

    public void undo(DataSource dataSource, String xid, long branchId) {
        // 1. 查询undo log
        SQLUndoLog undoLog = getUndoLog(dataSource, xid, branchId);

        // 2. 根据SQL类型生成反向SQL
        switch (undoLog.getSqlType()) {
            case UPDATE:
                // 生成反向UPDATE：用before image的数据覆盖当前数据
                generateUpdateUndo(undoLog);
                break;
            case INSERT:
                // 生成反向DELETE：删除插入的记录
                generateDeleteUndo(undoLog);
                break;
            case DELETE:
                // 生成反向INSERT：重新插入被删除的记录
                generateInsertUndo(undoLog);
                break;
        }

        // 3. 执行反向SQL恢复数据
        executeUndo(dataSource, undoLog);

        // 4. 删除undo log
        deleteUndoLog(dataSource, xid, branchId);
    }
}
```

### 3.5 可靠消息方案

#### 3.5.1 本地消息表方案

本地消息表方案最初由ebay提出，在基本的消息中间件方案基础上加入重新投递、ACK等机制保证事务最终一致性。

**实现流程**：
1. 业务活动主动方通过本地事务，将业务数据变更和消息记录同时写入本地数据库，保证操作业务数据与消息表信息在本地事务中一致
2. 业务活动处理完成后，通过可靠消息系统将消息发送给业务被动方
3. 消息发送完成后，删除本地数据库中的消息信息
4. 消息恢复系统定期找到未成功发送的消息，交给实时消息服务补发送
5. 业务活动被动方获取消息后处理业务

```java
// 本地消息表方案实现
@Service
public class LocalMessageTableService {

    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private MessageTableMapper messageTableMapper;
    @Autowired
    private MessageSender messageSender;

    @Transactional
    public void createOrderAndSendMessage(OrderDTO orderDTO) {
        // 1. 业务操作：创建订单
        Order order = new Order();
        order.setOrderId(orderDTO.getOrderId());
        order.setStatus("CREATED");
        orderMapper.insert(order);

        // 2. 同一本地事务中记录消息
        MessageTable message = new MessageTable();
        message.setMessageId(UUID.randomUUID().toString());
        message.setTopic("ORDER_CREATED");
        message.setBody(JSON.toJSONString(orderDTO));
        message.setStatus("PENDING");
        message.setRetryCount(0);
        message.setCreateTime(new Date());
        messageTableMapper.insert(message);
        // 本地事务提交，保证订单和消息记录同时成功或同时失败
    }

    // 定时任务扫描未发送的消息
    @Scheduled(fixedDelay = 5000)
    public void scanAndSendMessages() {
        List<MessageTable> pendingMessages =
            messageTableMapper.findByStatus("PENDING", 100);

        for (MessageTable message : pendingMessages) {
            try {
                // 发送消息到MQ
                messageSender.send(message.getTopic(), message.getBody());
                // 发送成功，更新状态
                message.setStatus("SENT");
                messageTableMapper.updateStatus(message);
            } catch (Exception e) {
                // 发送失败，增加重试次数
                message.setRetryCount(message.getRetryCount() + 1);
                if (message.getRetryCount() >= 10) {
                    message.setStatus("FAILED");
                }
                messageTableMapper.update(message);
            }
        }
    }
}
```

**本地消息表的缺陷**：
- 本地消息表与业务耦合在一起，难于做成通用性，不可独立伸缩
- 本地消息表基于数据库实现，数据库读写磁盘IO，高并发下有性能瓶颈

#### 3.5.2 事务消息方案

部分消息中间件（如RocketMQ 4.3+）实现了完整的事务消息，实际上是对本地消息表的封装，将本地消息表移动到MQ内部，解决Producer端消息发送与本地事务执行的原子性问题。

**实现流程**：
1. 消息中间件支持一种中间状态Half消息，保证此状态消息不会被消费端消费
2. 客户端先发送Half消息，成功后执行本地事务。若本地事务成功，Commit Half消息，MQ将Half消息转为正常消息投递给消费者；若本地事务失败，Rollback消息，MQ删除该消息
3. MQ服务端定时向生产者查询未确认状态的消息，根据本地事务状态决定Commit或Rollback

```java
// 基于RocketMQ事务消息的实现
public class TransactionMessageProducer {

    private final TransactionMQProducer producer;

    public TransactionMessageProducer() throws MQClientException {
        producer = new TransactionMQProducer("order_producer_group");
        producer.setNamesrvAddr("127.0.0.1:9876");
        // 设置事务回查监听器
        producer.setTransactionListener(new TransactionListenerImpl());
        producer.start();
    }

    public void sendOrderTransactionMessage(OrderDTO orderDTO) throws MQClientException {
        Message msg = new Message("ORDER_TOPIC",
            JSON.toJSONString(orderDTO).getBytes(StandardCharsets.UTF_8));

        // 发送事务消息
        TransactionSendResult result = producer.sendMessageInTransaction(
            msg, orderDTO);

        if (result.getLocalTransactionState() == LocalTransactionState.COMMIT_MESSAGE) {
            System.out.println("事务消息提交成功");
        } else if (result.getLocalTransactionState() == LocalTransactionState.ROLLBACK_MESSAGE) {
            System.out.println("事务消息回滚");
        }
    }
}

// 事务监听器实现
class TransactionListenerImpl implements TransactionListener {

    @Autowired
    private OrderService orderService;

    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        OrderDTO orderDTO = JSON.parseObject(
            new String(msg.getBody()), OrderDTO.class);
        try {
            // 执行本地事务
            orderService.createOrder(orderDTO);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 事务状态回查：根据本地事务状态决定Commit或Rollback
        OrderDTO orderDTO = JSON.parseObject(
            new String(msg.getBody()), OrderDTO.class);
        Order order = orderService.findByOrderId(orderDTO.getOrderId());
        if (order != null && "CREATED".equals(order.getStatus())) {
            return LocalTransactionState.COMMIT_MESSAGE;
        }
        return LocalTransactionState.ROLLBACK_MESSAGE;
    }
}
```

**事务消息方案的优势**：
- 消息系统消息独立存储，独立伸缩
- 主动方实现分布式事务逻辑简单，更加关注业务
- 通过将大事务拆分为本地事务和MQ消息投递两个小事务，配合事务状态反查机制兜底

### 3.6 最大努力通知

最大努力通知是一种较简单也是现实中常用的实现最终一致性的分布式事务解决方案：

1. **投递消息**：业务主动方完成业务处理后向被动方发送消息，允许消息丢失
2. **消息补偿**：业务被动方通过一定策略主动向主动方发起查询，恢复丢失的业务消息

与可靠消息方案的区别：
- **可靠消息**：关注主动方发消息过程的事务性，主动方需要为消息系统提供查询补偿操作
- **最大努力通知**：关注被动方是否收到消息，主动方需要为被动方提供查询补偿操作

```java
// 最大努力通知方案实现
@Service
public class BestEffortNotificationService {

    @Autowired
    private PaymentService paymentService;
    @Autowired
    private NotificationService notificationService;

    // 主动方：支付完成后尽力通知商户
    public void processPaymentResult(PaymentResult result) {
        // 执行本地业务
        paymentService.updatePaymentStatus(result);

        // 尽力通知（允许失败）
        try {
            notificationService.notifyMerchant(result.getMerchantId(), result);
        } catch (Exception e) {
            // 通知失败不阻断业务流程，由被动方主动查询补偿
            log.warn("通知商户失败，商户将通过主动查询获取结果", e);
        }
    }

    // 主动方：提供查询接口供被动方补偿
    public PaymentResult queryPaymentResult(String paymentId) {
        return paymentService.findById(paymentId);
    }
}

// 被动方：定时查询补偿
@Service
public class MerchantCompensationService {

    @Autowired
    private PaymentQueryService paymentQueryService;

    @Scheduled(fixedDelay = 60000)
    public void compensateMissedNotifications() {
        // 查找可能遗漏通知的支付记录
        List<String> pendingPayments = findPendingPayments();

        for (String paymentId : pendingPayments) {
            try {
                // 主动查询支付结果
                PaymentResult result = paymentQueryService.query(paymentId);
                if (result != null) {
                    processPaymentResult(result);
                }
            } catch (Exception e) {
                log.error("补偿查询失败: paymentId={}", paymentId, e);
            }
        }
    }
}
```

## 四、异常处理

### 4.1 幂等性设计

分布式事务下，方案涉及流程重试、业务补偿以及业务隔离，要求在设计开发相关业务操作时必须考虑操作的**可查询**和**幂等**。

幂等指的是针对一个操作，任意多次执行产生的业务影响和一次执行产生的业务影响相同。实现上有两种思路：

- **通过业务逻辑实现幂等性**：如创建订单，如果对应订单之前已创建成功则返回创建成功的订单信息
- **存储所有请求和结果**：检测到重复请求后直接返回之前处理的结果

```java
// 幂等性设计的通用方案
public abstract class IdempotentService<T, R> {

    @Autowired
    protected RedisTemplate<String, String> redisTemplate;

    public R executeIdempotent(String requestId, Supplier<T> requestSupplier,
                                Function<T, R> businessFunction) {
        // 1. 尝试获取分布式锁
        String lockKey = "idempotent:" + requestId;
        Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "PROCESSING", 30, TimeUnit.SECONDS);

        if (locked == null || !locked) {
            // 2. 锁获取失败，说明已有请求在处理中或已处理完成
            String status = redisTemplate.opsForValue().get(lockKey);
            if ("COMPLETED".equals(status)) {
                // 已处理完成，返回缓存结果
                String cachedResult = redisTemplate.opsForValue()
                    .get(lockKey + ":result");
                return JSON.parseObject(cachedResult, getResultType());
            }
            // 处理中，返回处理中状态
            throw new BusinessException("请求处理中，请稍后重试");
        }

        try {
            // 3. 执行业务逻辑
            T request = requestSupplier.get();
            R result = businessFunction.apply(request);

            // 4. 缓存结果
            redisTemplate.opsForValue()
                .set(lockKey, "COMPLETED", 24, TimeUnit.HOURS);
            redisTemplate.opsForValue()
                .set(lockKey + ":result", JSON.toJSONString(result),
                    24, TimeUnit.HOURS);

            return result;
        } catch (Exception e) {
            // 5. 异常时删除锁，允许重试
            redisTemplate.delete(lockKey);
            throw e;
        }
    }

    protected abstract Class<R> getResultType();
}
```

```java
// 重试机制设计
public class RetryTemplate {

    public <T> T executeWithRetry(Callable<T> task, RetryPolicy policy) {
        int attempt = 0;
        Exception lastException = null;

        while (attempt < policy.getMaxAttempts()) {
            try {
                return task.call();
            } catch (Exception e) {
                lastException = e;
                attempt++;
                if (attempt >= policy.getMaxAttempts()) {
                    break;
                }
                // 指数退避
                long delay = calculateDelay(attempt, policy);
                try {
                    Thread.sleep(delay);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("重试被中断", ie);
                }
            }
        }
        throw new RuntimeException("重试次数耗尽", lastException);
    }

    private long calculateDelay(int attempt, RetryPolicy policy) {
        // 指数退避 + 随机抖动
        long baseDelay = policy.getInitialInterval();
        long maxDelay = policy.getMaxInterval();
        long delay = (long) (baseDelay * Math.pow(policy.getMultiplier(), attempt - 1));
        delay = Math.min(delay, maxDelay);
        // 添加抖动，避免重试风暴
        delay = delay + (long) (Math.random() * delay * 0.1);
        return delay;
    }
}
```

```java
// 异步二阶段提交
public class AsyncCommitCoordinator {

    @Autowired
    private ThreadPoolExecutor commitExecutor;

    public void asyncCommit(String xid, List<BranchTransaction> branches) {
        // 提交请求放入异步队列
        commitExecutor.submit(() -> {
            for (BranchTransaction branch : branches) {
                try {
                    branchService.commit(branch.getBranchId());
                    branch.setStatus("COMMITTED");
                } catch (Exception e) {
                    // 异步提交失败，记录后重试
                    branch.setStatus("COMMIT_RETRYING");
                    scheduleRetry(branch);
                }
            }
        });
    }

    // 二阶段回滚必须同步执行，确保数据一致性
    public void syncRollback(String xid, List<BranchTransaction> branches) {
        for (BranchTransaction branch : branches) {
            int retryCount = 0;
            while (retryCount < MAX_RETRY) {
                try {
                    branchService.rollback(branch.getBranchId());
                    break;
                } catch (Exception e) {
                    retryCount++;
                    if (retryCount >= MAX_RETRY) {
                        // 记录告警，人工介入
                        alertService.alert("回滚失败", branch, e);
                    }
                }
            }
        }
    }
}
```

```java
// 批量TCC操作
public class BatchTccService {

    public void batchTry(List<BranchRequest> requests) {
        // 批量注册分支事务
        List<CompletableFuture<Boolean>> futures = requests.stream()
            .map(req -> CompletableFuture.supplyAsync(
                () -> participantService.tryAction(req)))
            .collect(Collectors.toList());

        // 等待所有Try完成
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

        // 检查结果
        boolean allSuccess = futures.stream()
            .allMatch(f -> f.getNow(false));
        if (!allSuccess) {
            // 部分失败，对成功的执行Cancel
            compensateBatch(requests, futures);
        }
    }
}
```

```java
public class GlobalLockOptimizer {

    // 减小锁粒度：按行级别加锁而非表级别
    public boolean tryGlobalLock(String tableName, List<String> rowKeys,
                                  String xid, int retryTimes) {
        for (String rowKey : rowKeys) {
            String lockKey = tableName + ":" + rowKey;
            int retry = 0;
            while (retry < retryTimes) {
                String existing = redisTemplate.opsForValue().get(lockKey);
                if (existing == null || existing.equals(xid)) {
                    redisTemplate.opsForValue()
                        .setIfAbsent(lockKey, xid, 30, TimeUnit.SECONDS);
                    break;
                }
                retry++;
                sleep(calculateBackoff(retry));
            }
            if (retry >= retryTimes) {
                // 锁获取失败，释放已获取的锁
                releaseLocks(tableName, rowKeys, xid);
                return false;
            }
        }
        return true;
    }
}
```

## 六、最佳实践

### 6.1 方案选型指南

1. **同步强一致场景**：优先选择TCC。虽然开发成本高，但能保证隔离性和较强的一致性，适合核心交易链路如支付、转账。
2. **长流程业务场景**：选择Saga。适合业务流程长、参与者多的场景，如旅行预订、订单履约等。
3. **异步解耦场景**：选择可靠消息。适合下游结果不影响上游执行的异步流程，如消费送积分、消费送券。
4. **通知场景**：选择最大努力通知。适合业务执行结果的通知，对实时性要求不高的场景。
5. **低改造成本场景**：选择AT模式。代码无侵入，适合遗留系统快速接入分布式事务。

### 6.2 设计原则

**避免大事务**：将大事务拆分为小事务加异步化，减少资源锁定时间。

**确保幂等性**：所有可能被重试的接口（Confirm、Cancel、Compensate、消息消费）必须实现幂等。

**保证可查询**：每次业务操作应有全局唯一标识，便于状态查询和补偿。

**设计补偿优先于回滚**：在分布式场景下，补偿比回滚更实用。补偿是"逻辑撤销"，一次真实操作用于撤销之前操作的影响，而回滚只能取消未提交的事务。

**合理设置超时**：各环节设置合理的超时时间，避免无限等待导致资源耗尽。

### 6.4 常见踩坑总结

**坑1：TCC的Confirm/Cancel忘记做幂等**
框架在超时后会重试Confirm/Cancel操作，如果不做幂等，可能导致重复扣款或重复入账。

**坑2：Saga的补偿操作不可逆**
补偿操作本身也可能失败，需要设计重试机制和最终兜底的告警人工介入流程。

**坑3：可靠消息的消费端未处理幂等**
消息可能被重复投递，消费端必须通过唯一标识判断是否已处理。

**坑4：AT模式的脏写问题**
AT模式在一阶段提交后、二阶段回滚前，如果其他全局事务修改了同一行数据，会导致回滚时数据不一致。框架通过全局锁来避免，但需要确保所有数据访问都经过框架代理。

**坑5：事务悬挂导致资源泄漏**
TCC模式下，Cancel先于Try到达时如果处理不当，Try操作预留的资源将永远无法释放。必须在Try操作前检查是否已有Cancel记录。

**坑6：忽略网络分区的影响**
在网络分区场景下，协调者可能认为参与者已宕机而发起回滚，但参与者实际仍在执行Try操作。需要通过超时机制和状态检查来处理这种场景。

### 6.5 演进路线

分布式事务的引入应循序渐进：

1. **第一阶段**：优先使用可靠消息方案处理异步场景，这是成本最低的方案
2. **第二阶段**：对核心同步链路引入TCC，保证强一致性
3. **第三阶段**：对复杂长流程引入Saga，处理多步骤补偿
4. **第四阶段**：建设统一的分布式事务平台，支持多模式接入，提供监控告警和自动化补偿能力

## 七、总结

分布式事务是微服务架构落地的核心挑战之一。没有适用于所有场景的完美方案，需要根据业务特点进行选型：

- **2PC/XA**：数据库层面强一致性方案，性能差，不推荐生产使用
- **TCC**：业务层面最终一致性方案，隔离性好，适合核心交易链路
- **Saga**：长流程补偿方案，适合业务流程长的场景，隔离性差
- **可靠消息**：异步解耦方案，适合下游结果不影响上游的场景
- **AT模式**：无侵入自动补偿方案，适合遗留系统快速接入

无论选择哪种方案，幂等性、可查询性和补偿机制都是必须考虑的基础能力。在实际工程中，通常是多种方案的组合使用——核心链路用TCC保证强一致，非核心链路用可靠消息保证最终一致，复杂流程用Saga编排，形成分层次的一致性保障体系。

### 8.1 案例一：TCC分布式事务在转账中的应用全链路

#### 8.1.1 业务场景

用户A向用户B转账1000元，涉及两个独立的账户服务（Account-A和Account-B），分属不同的数据库实例。采用TCC模式保证转账的最终一致性，完整链路为：Try冻结转出账户余额 -> Confirm扣减转出账户并入账到转入账户 -> Cancel解冻转出账户余额。同时需要处理空回滚和事务悬挂两个经典异常场景。

```
       │                            │                        │
       │   全部Try成功               │                        │
       │◀── Confirm(扣减1000元)────│── Confirm(确认入账)─────▶│
       │                            │                        │
       │   Try有失败                 │                        │
```

#### 8.1.3 转出账户服务（AccountA）完整实现

```java
package com.example.tcc.transfer.from;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.math.BigDecimal;

/**
 * 转出账户TCC参与方实现
 *
 * Try阶段：冻结转出金额（可用余额减少，冻结金额增加）
 * Confirm阶段：扣减冻结金额和总余额
 * Cancel阶段：解冻金额（冻结金额转回可用余额）
 */
@Service
public class AccountFromTccService {

    private static final Logger log = LoggerFactory.getLogger(AccountFromTccService.class);

    private final AccountMapper accountMapper;
    private final TccTransactionRecordMapper recordMapper;

    public AccountFromTccService(AccountMapper accountMapper,
                                  TccTransactionRecordMapper recordMapper) {
        this.accountMapper = accountMapper;
        this.recordMapper = recordMapper;
    }

    /**
     * Try阶段：冻结转出金额
     * 幂等 + 悬挂防护（检查是否已执行Cancel）
     */
    @Transactional(rollbackFor = Exception.class)
    public boolean tryDeduct(String xid, String branchId,
                             String accountId, BigDecimal amount) {
        log.info("[TCC-Try] 开始冻结转出金额, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);

        // 1. 幂等检查：是否已处理过该分支事务
        TccTransactionRecord existRecord = recordMapper.findByXidAndBranchId(xid, branchId);
        if (existRecord != null) {
            if ("TRY".equals(existRecord.getStatus())) {
                log.warn("[TCC-Try] 分支事务已执行Try, 幂等返回, xid={}, branchId={}", xid, branchId);
                return true;
            }
            if ("CONFIRMED".equals(existRecord.getStatus())
                    || "CANCELLED".equals(existRecord.getStatus())) {
                log.warn("[TCC-Try] 分支事务已进入{}阶段, 拒绝重复Try, xid={}, branchId={}",
                        existRecord.getStatus(), xid, branchId);
                return true;
            }
        }

        // 2. 悬挂防护：检查是否已执行过Cancel（空回滚场景下Cancel先于Try到达）
        if (existRecord != null && "CANCELLED".equals(existRecord.getStatus())) {
            log.warn("[TCC-Try] 检测到悬挂: Cancel已执行, 拒绝Try, xid={}, branchId={}", xid, branchId);
            return false;
        }

        // 3. 查询账户并校验余额
        Account account = accountMapper.findByAccountId(accountId);
        if (account == null) {
            log.error("[TCC-Try] 账户不存在, accountId={}", accountId);
            throw new BusinessException("账户不存在: " + accountId);
        }
        if (account.getAvailableBalance().compareTo(amount) < 0) {
            log.error("[TCC-Try] 余额不足, accountId={}, available={}, need={}",
                    accountId, account.getAvailableBalance(), amount);
            throw new BusinessException("余额不足");
        }

        // 4. 冻结金额：可用余额减少，冻结金额增加（乐观锁防并发）
        int rows = accountMapper.freezeAmount(
                accountId, amount, account.getVersion());
        if (rows == 0) {
            log.error("[TCC-Try] 冻结金额失败(并发冲突), accountId={}", accountId);
            throw new BusinessException("并发冲突，请重试");
        }

        // 5. 记录TCC事务状态
        TccTransactionRecord record = new TccTransactionRecord();
        record.setXid(xid);
        record.setBranchId(branchId);
        record.setStatus("TRY");
        record.setBusinessKey(accountId);
        record.setAmount(amount);
        recordMapper.insert(record);

        log.info("[TCC-Try] 冻结转出金额成功, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);
        return true;
    }

    /**
     * Confirm阶段：确认扣款
     * 幂等 + 空操作防护（Try未执行则不Confirm）
     */
    @Transactional(rollbackFor = Exception.class)
    public boolean confirmDeduct(String xid, String branchId,
                                 String accountId, BigDecimal amount) {
        log.info("[TCC-Confirm] 开始确认扣款, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);

        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);

        // 1. 空操作防护：Try未执行不能Confirm
        if (record == null) {
            log.error("[TCC-Confirm] Try未执行, 拒绝Confirm, xid={}, branchId={}", xid, branchId);
            return false;
        }

        // 2. 幂等检查
        if ("CONFIRMED".equals(record.getStatus())) {
            log.warn("[TCC-Confirm] 已确认, 幂等返回, xid={}, branchId={}", xid, branchId);
            return true;
        }

        // 3. 扣减冻结金额和总余额
        Account account = accountMapper.findByAccountId(accountId);
        if (account == null) {
            log.error("[TCC-Confirm] 账户不存在, accountId={}", accountId);
            throw new BusinessException("账户不存在: " + accountId);
        }

        int rows = accountMapper.confirmDeduct(accountId, amount, account.getVersion());
        if (rows == 0) {
            log.error("[TCC-Confirm] 扣款失败(并发冲突), accountId={}", accountId);
            throw new BusinessException("并发冲突，请重试");
        }

        // 4. 更新事务记录
        recordMapper.updateStatus(xid, branchId, "CONFIRMED");

        log.info("[TCC-Confirm] 确认扣款成功, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);
        return true;
    }

    /**
     * Cancel阶段：解冻金额
     * 幂等 + 空回滚处理（Try未执行时插入Cancel记录防悬挂）
     */
    @Transactional(rollbackFor = Exception.class)
    public boolean cancelDeduct(String xid, String branchId,
                                String accountId, BigDecimal amount) {
        log.info("[TCC-Cancel] 开始解冻金额, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);

        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);

        // 1. 空回滚处理：Try未执行，直接插入CANCELLED记录
        if (record == null) {
            log.warn("[TCC-Cancel] 检测到空回滚: Try未执行, 插入CANCELLED记录防悬挂, xid={}, branchId={}",
                    xid, branchId);
            record = new TccTransactionRecord();
            record.setXid(xid);
            record.setBranchId(branchId);
            record.setStatus("CANCELLED");
            record.setBusinessKey(accountId);
            record.setAmount(amount);
            recordMapper.insert(record);
            log.info("[TCC-Cancel] 空回滚完成, xid={}, branchId={}", xid, branchId);
            return true;
        }

        // 2. 幂等检查
        if ("CANCELLED".equals(record.getStatus())) {
            log.warn("[TCC-Cancel] 已取消, 幂等返回, xid={}, branchId={}", xid, branchId);
            return true;
        }

        // 3. 解冻金额：冻结金额转回可用余额
        Account account = accountMapper.findByAccountId(accountId);
        if (account == null) {
            log.error("[TCC-Cancel] 账户不存在, accountId={}", accountId);
            throw new BusinessException("账户不存在: " + accountId);
        }

        int rows = accountMapper.unfreezeAmount(
                accountId, amount, account.getVersion());
        if (rows == 0) {
            log.error("[TCC-Cancel] 解冻失败(并发冲突), accountId={}", accountId);
            throw new BusinessException("并发冲突，请重试");
        }

        // 4. 更新事务记录
        recordMapper.updateStatus(xid, branchId, "CANCELLED");

        log.info("[TCC-Cancel] 解冻金额成功, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);
        return true;
    }
}
```

#### 8.1.4 转入账户服务（AccountB）完整实现

```java
package com.example.tcc.transfer.to;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.math.BigDecimal;

/**
 * 转入账户TCC参与方实现
 *
 * Try阶段：预增金额（记录待入账金额，不直接修改可用余额）
 * Confirm阶段：确认入账（预增金额转为可用余额）
 * Cancel阶段：撤销预增（删除待入账记录）
 */
@Service
public class AccountToTccService {

    private static final Logger log = LoggerFactory.getLogger(AccountToTccService.class);

    private final AccountMapper accountMapper;
    private final TccTransactionRecordMapper recordMapper;

    public AccountToTccService(AccountMapper accountMapper,
                                TccTransactionRecordMapper recordMapper) {
        this.accountMapper = accountMapper;
        this.recordMapper = recordMapper;
    }

    @Transactional(rollbackFor = Exception.class)
    public boolean tryIncrease(String xid, String branchId,
                               String accountId, BigDecimal amount) {
        log.info("[TCC-Try] 开始预增转入金额, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);

        // 幂等检查
        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);
        if (record != null) {
            log.warn("[TCC-Try] 已处理, 幂等返回, xid={}, branchId={}, status={}",
                    xid, branchId, record.getStatus());
            return true;
        }

        // 悬挂防护
        if (record != null && "CANCELLED".equals(record.getStatus())) {
            log.warn("[TCC-Try] 检测到悬挂: Cancel已执行, 拒绝Try, xid={}, branchId={}",
                    xid, branchId);
            return false;
        }

        // 预增冻结金额到转入账户（不直接增加可用余额，保证隔离性）
        Account account = accountMapper.findByAccountId(accountId);
        if (account == null) {
            log.error("[TCC-Try] 账户不存在, accountId={}", accountId);
            throw new BusinessException("账户不存在: " + accountId);
        }

        accountMapper.increaseFrozenAmount(accountId, amount, account.getVersion());

        // 记录事务状态
        record = new TccTransactionRecord();
        record.setXid(xid);
        record.setBranchId(branchId);
        record.setStatus("TRY");
        record.setBusinessKey(accountId);
        record.setAmount(amount);
        recordMapper.insert(record);

        log.info("[TCC-Try] 预增转入金额成功, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);
        return true;
    }

    @Transactional(rollbackFor = Exception.class)
    public boolean confirmIncrease(String xid, String branchId,
                                   String accountId, BigDecimal amount) {
        log.info("[TCC-Confirm] 开始确认入账, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);

        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);
        if (record == null) {
            log.error("[TCC-Confirm] Try未执行, 拒绝Confirm, xid={}, branchId={}", xid, branchId);
            return false;
        }
        if ("CONFIRMED".equals(record.getStatus())) {
            log.warn("[TCC-Confirm] 已确认, 幂等返回, xid={}, branchId={}", xid, branchId);
            return true;
        }

        // 冻结金额转为可用余额
        Account account = accountMapper.findByAccountId(accountId);
        accountMapper.confirmIncrease(accountId, amount, account.getVersion());

        recordMapper.updateStatus(xid, branchId, "CONFIRMED");

        log.info("[TCC-Confirm] 确认入账成功, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);
        return true;
    }

    @Transactional(rollbackFor = Exception.class)
    public boolean cancelIncrease(String xid, String branchId,
                                  String accountId, BigDecimal amount) {
        log.info("[TCC-Cancel] 开始撤销预增, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);

        TccTransactionRecord record = recordMapper.findByXidAndBranchId(xid, branchId);

        // 空回滚处理
        if (record == null) {
            log.warn("[TCC-Cancel] 检测到空回滚: Try未执行, 插入CANCELLED记录, xid={}, branchId={}",
                        xid, branchId);
            record = new TccTransactionRecord();
            record.setXid(xid);
            record.setBranchId(branchId);
            record.setStatus("CANCELLED");
            record.setBusinessKey(accountId);
            record.setAmount(amount);
            recordMapper.insert(record);
            return true;
        }

        if ("CANCELLED".equals(record.getStatus())) {
            log.warn("[TCC-Cancel] 已取消, 幂等返回, xid={}, branchId={}", xid, branchId);
            return true;
        }

        // 撤销预增冻结金额
        Account account = accountMapper.findByAccountId(accountId);
        accountMapper.cancelIncrease(accountId, amount, account.getVersion());

        recordMapper.updateStatus(xid, branchId, "CANCELLED");

        log.info("[TCC-Cancel] 撤销预增成功, xid={}, branchId={}, accountId={}, amount={}",
                xid, branchId, accountId, amount);
        return true;
    }
}
```

#### 8.1.5 事务协调器与转账入口

```java
package com.example.tcc.transfer;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import java.math.BigDecimal;
import java.util.UUID;

/**
 * 转账TCC事务协调器
 *
 * 负责编排Try -> Confirm/Cancel全流程，处理全局事务状态和异常重试
 */
@Service
public class TransferTccCoordinator {

    private static final Logger log = LoggerFactory.getLogger(TransferTccCoordinator.class);

    private final AccountFromTccService fromService;
    private final AccountToTccService toService;
    private final TccGlobalTransactionMapper globalTxMapper;

    public TransferTccCoordinator(AccountFromTccService fromService,
                                   AccountToTccService toService,
                                   TccGlobalTransactionMapper globalTxMapper) {
        this.fromService = fromService;
        this.toService = toService;
        this.globalTxMapper = globalTxMapper;
    }

    /**
     * 转账入口：执行TCC全流程
     */
    public TransferResult transfer(String fromAccountId, String toAccountId,
                                   BigDecimal amount) {
        // 生成全局事务ID
        String xid = "TX_TRANSFER_" + UUID.randomUUID().toString().replace("-", "");
        String fromBranchId = "BR_FROM_" + xid;
        String toBranchId = "BR_TO_" + xid;

        log.info("[TCC-Coordinator] 转账开始, xid={}, from={}, to={}, amount={}",
                xid, fromAccountId, toAccountId, amount);

        // 记录全局事务
        globalTxMapper.insert(xid, "TRANSFER", "TRYING");

        try {
            // ===== Try阶段 =====
            boolean fromTryResult = fromService.tryDeduct(
                    xid, fromBranchId, fromAccountId, amount);
            boolean toTryResult;
            try {
                toTryResult = toService.tryIncrease(
                        xid, toBranchId, toAccountId, amount);
            } catch (Exception e) {
                // 转入方Try失败，回滚转出方
                log.error("[TCC-Coordinator] 转入方Try失败, 开始Cancel转出方, xid={}", xid, e);
                safeCancel(xid, fromBranchId, fromAccountId, amount, "from");
                globalTxMapper.updateStatus(xid, "CANCELLED");
                return TransferResult.fail("转账失败: 转入方Try异常");
            }

            if (!fromTryResult || !toTryResult) {
                // 任一Try失败，执行全局Cancel
                log.warn("[TCC-Coordinator] Try阶段部分失败, fromTry={}, toTry={}, 执行全局Cancel, xid={}",
                        fromTryResult, toTryResult, xid);
                globalTxMapper.updateStatus(xid, "CANCELLING");
                safeCancel(xid, fromBranchId, fromAccountId, amount, "from");
                safeCancel(xid, toBranchId, toAccountId, amount, "to");
                globalTxMapper.updateStatus(xid, "CANCELLED");
                return TransferResult.fail("转账失败: Try阶段未全部成功");
            }

            // ===== Confirm阶段 =====
            log.info("[TCC-Coordinator] Try全部成功, 开始Confirm, xid={}", xid);
            globalTxMapper.updateStatus(xid, "CONFIRMING");

            boolean fromConfirm = safeConfirm(xid, fromBranchId, fromAccountId, amount, "from");
            boolean toConfirm = safeConfirm(xid, toBranchId, toAccountId, amount, "to");

            if (fromConfirm && toConfirm) {
                globalTxMapper.updateStatus(xid, "CONFIRMED");
                log.info("[TCC-Coordinator] 转账成功, xid={}, from={}, to={}, amount={}",
                        xid, fromAccountId, toAccountId, amount);
                return TransferResult.success(xid);
            } else {
                // Confirm失败需要重试，记录告警
                log.error("[TCC-Coordinator] Confirm部分失败, 需重试, xid={}, fromConfirm={}, toConfirm={}",
                        xid, fromConfirm, toConfirm);
                globalTxMapper.updateStatus(xid, "CONFIRM_RETRYING");
                // 实际场景中由定时任务异步重试Confirm
                return TransferResult.fail("转账处理中, Confirm待重试");
            }

        } catch (Exception e) {
            log.error("[TCC-Coordinator] 转账异常, 开始全局Cancel, xid={}", xid, e);
            globalTxMapper.updateStatus(xid, "CANCELLING");
            safeCancel(xid, fromBranchId, fromAccountId, amount, "from");
            safeCancel(xid, toBranchId, toAccountId, amount, "to");
            globalTxMapper.updateStatus(xid, "CANCELLED");
            return TransferResult.fail("转账异常: " + e.getMessage());
        }
    }

    /**
     * 安全执行Confirm（异常不外抛，记录日志用于重试）
     */
    private boolean safeConfirm(String xid, String branchId,
                                String accountId, BigDecimal amount, String side) {
        try {
            if ("from".equals(side)) {
                return fromService.confirmDeduct(xid, branchId, accountId, amount);
            } else {
                return toService.confirmIncrease(xid, branchId, accountId, amount);
            }
        } catch (Exception e) {
            log.error("[TCC-Coordinator] Confirm异常, side={}, xid={}, branchId={}",
                    side, xid, branchId, e);
            return false;
        }
    }

    /**
     * 安全执行Cancel（异常不外抛，记录日志用于重试）
     */
    private void safeCancel(String xid, String branchId,
                            String accountId, BigDecimal amount, String side) {
        try {
            if ("from".equals(side)) {
                fromService.cancelDeduct(xid, branchId, accountId, amount);
            } else {
                toService.cancelIncrease(xid, branchId, accountId, amount);
            }
        } catch (Exception e) {
            log.error("[TCC-Coordinator] Cancel异常, side={}, xid={}, branchId={}, 需异步重试",
                    side, xid, branchId, e);
        }
    }
}
```

#### 8.1.6 异常场景说明

**空回滚场景**：网络延迟导致Cancel先于Try到达转出方。`cancelDeduct`方法中发现`record == null`，直接插入CANCELLED记录并返回成功，不执行任何业务解冻操作。后续Try到达时，`tryDeduct`方法检查到已有CANCELLED记录，拒绝执行Try，避免事务悬挂。

**事务悬挂场景**：空回滚后Try请求到达。Try方法中的悬挂防护逻辑检测到已存在CANCELLED记录，直接返回false，不冻结任何资源，避免预留资源永远无法释放。

**Confirm/Cancel重试场景**：协调器对Confirm和Cancel做了异常兜底（`safeConfirm`/`safeCancel`），异常不外抛，记录日志后由定时任务异步重试。由于Confirm/Cancel方法内部都实现了幂等检查，重试不会导致重复执行。

### 8.2 案例二：Saga分布式事务在下单中的应用全链路

#### 8.2.1 业务场景

用户下单流程包含四个步骤：创建订单 -> 扣减库存 -> 扣减优惠券 -> 扣减积分。任意步骤失败时，需要按反向顺序对已执行成功的步骤执行补偿操作。采用编排式Saga模式实现。

```
正向流程:
  创建订单 → 扣减库存 → 扣减优惠券 → 扣积分 → [全部成功，下单完成]

逆向补偿（假设扣积分失败）:
  创建订单 → 扣减库存 → 扣减优惠券 → 扣积分[失败]
  ← 还原优惠券 ← 恢复库存 ← 取消订单 ← [补偿完成]
```

#### 8.2.3 Saga编排器完整实现

```java
package com.example.saga.order;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import java.util.Arrays;
import java.util.List;

/**
 * 下单Saga编排器
 *
 * 正向流程: 创建订单 → 扣库存 → 扣优惠券 → 扣积分
 * 逆向补偿: 还原优惠券 → 恢复库存 → 取消订单
 */
@Service
public class OrderSagaOrchestrator {

    private static final Logger log = LoggerFactory.getLogger(OrderSagaOrchestrator.class);

    // 正向步骤定义（顺序执行）
    private static final List<String> FORWARD_STEPS = Arrays.asList(
            "CREATE_ORDER", "DEDUCT_INVENTORY", "DEDUCT_COUPON", "DEDUCT_POINTS"
    );

    private final OrderService orderService;
    private final InventoryService inventoryService;
    private final CouponService couponService;
    private final PointsService pointsService;
    private final SagaInstanceMapper sagaInstanceMapper;
    private final SagaStepLogMapper stepLogMapper;

    public OrderSagaOrchestrator(OrderService orderService,
                                  InventoryService inventoryService,
                                  CouponService couponService,
                                  PointsService pointsService,
                                  SagaInstanceMapper sagaInstanceMapper,
                                  SagaStepLogMapper stepLogMapper) {
        this.orderService = orderService;
        this.inventoryService = inventoryService;
        this.couponService = couponService;
        this.pointsService = pointsService;
        this.sagaInstanceMapper = sagaInstanceMapper;
        this.stepLogMapper = stepLogMapper;
    }

    /**
     * 执行下单Saga全流程
     */
    public SagaResult execute(OrderRequest request) {
        String sagaId = "SAGA_ORDER_" + System.currentTimeMillis()
                + "_" + request.getUserId();
        log.info("[Saga] 下单流程开始, sagaId={}, userId={}, skuId={}, quantity={}",
                sagaId, request.getUserId(), request.getSkuId(), request.getQuantity());

        // 1. 创建Saga实例
        SagaInstance instance = new SagaInstance();
        instance.setSagaId(sagaId);
        instance.setBusinessType("PLACE_ORDER");
        instance.setStatus("RUNNING");
        instance.setPayload(JSON.toJSONString(request));
        sagaInstanceMapper.insert(instance);

        try {
            // ===== Step 1: 创建订单 =====
            if (!executeStep(sagaId, "CREATE_ORDER", request)) {
                return failAndCompensate(sagaId, request, "CREATE_ORDER");
            }

            // ===== Step 2: 扣减库存 =====
            if (!executeStep(sagaId, "DEDUCT_INVENTORY", request)) {
                return failAndCompensate(sagaId, request, "DEDUCT_INVENTORY");
            }

            // ===== Step 3: 扣减优惠券 =====
            if (request.getCouponId() != null) {
                if (!executeStep(sagaId, "DEDUCT_COUPON", request)) {
                    return failAndCompensate(sagaId, request, "DEDUCT_COUPON");
                }
            }

            // ===== Step 4: 扣减积分 =====
            if (request.getPointsToUse() > 0) {
                if (!executeStep(sagaId, "DEDUCT_POINTS", request)) {
                    return failAndCompensate(sagaId, request, "DEDUCT_POINTS");
                }
            }

            // 全部成功
            sagaInstanceMapper.updateStatus(sagaId, "COMPLETED");
            log.info("[Saga] 下单流程全部成功, sagaId={}, orderId={}",
                    sagaId, request.getOrderId());
            return SagaResult.success(sagaId, request.getOrderId());

        } catch (Exception e) {
            log.error("[Saga] 下单流程异常, sagaId={}", sagaId, e);
            return failAndCompensate(sagaId, request, "UNKNOWN");
        }
    }

    /**
     * 执行单个正向步骤（含幂等检查和日志记录）
     */
    private boolean executeStep(String sagaId, String stepName, OrderRequest request) {
        // 幂等检查：如果该步骤已成功执行，直接跳过
        SagaStepLog existLog = stepLogMapper.findBySagaIdAndStepAndType(
                sagaId, stepName, "DO");
        if (existLog != null && "SUCCESS".equals(existLog.getStatus())) {
            log.warn("[Saga] 步骤已执行成功, 幂等跳过, sagaId={}, step={}", sagaId, stepName);
            return true;
        }

        // 记录步骤开始
        logStep(sagaId, stepName, "DO", "STARTED", request);
        log.info("[Saga] 执行正向步骤: {}, sagaId={}", stepName, sagaId);

        try {
            switch (stepName) {
                case "CREATE_ORDER":
                    orderService.createOrder(request);
                    break;
                case "DEDUCT_INVENTORY":
                    inventoryService.deduct(request.getSkuId(), request.getQuantity());
                    break;
                case "DEDUCT_COUPON":
                    couponService.useCoupon(request.getCouponId(), request.getOrderId());
                    break;
                case "DEDUCT_POINTS":
                    pointsService.deductPoints(
                            request.getUserId(), request.getPointsToUse(), request.getOrderId());
                    break;
                default:
                    log.error("[Saga] 未知步骤: {}, sagaId={}", stepName, sagaId);
                    return false;
            }
            logStep(sagaId, stepName, "DO", "SUCCESS", request);
            log.info("[Saga] 正向步骤成功: {}, sagaId={}", stepName, sagaId);
            return true;

        } catch (Exception e) {
            logStepWithError(sagaId, stepName, "DO", "FAILED", request, e.getMessage());
            log.error("[Saga] 正向步骤失败: {}, sagaId={}, error={}",
                    stepName, sagaId, e.getMessage(), e);
            return false;
        }
    }

    /**
     * 失败后执行逆向补偿
     */
    private SagaResult failAndCompensate(String sagaId, OrderRequest request,
                                         String failedStep) {
        log.warn("[Saga] 开始逆向补偿, sagaId={}, failedStep={}", sagaId, failedStep);
        sagaInstanceMapper.updateStatus(sagaId, "COMPENSATING");

        // 查询已成功的步骤（按反向顺序）
        List<String> completedSteps = stepLogMapper.findSuccessfulDoSteps(sagaId);
        // 反转列表，按反向顺序补偿
        java.util.Collections.reverse(completedSteps);

        boolean allCompensateSuccess = true;
        for (String stepName : completedSteps) {
            boolean success = compensateStep(sagaId, stepName, request);
            if (!success) {
                allCompensateSuccess = false;
                // 补偿失败不中断，继续补偿其他步骤
                log.error("[Saga] 补偿步骤失败, 继续补偿其他步骤, sagaId={}, step={}",
                        sagaId, stepName);
            }
        }

        if (allCompensateSuccess) {
            sagaInstanceMapper.updateStatus(sagaId, "COMPENSATED");
            log.info("[Saga] 逆向补偿全部成功, sagaId={}", sagaId);
        } else {
            sagaInstanceMapper.updateStatus(sagaId, "FAILED");
            log.error("[Saga] 逆向补偿部分失败, 需人工介入, sagaId={}", sagaId);
        }

        return SagaResult.fail(sagaId, "下单失败, 已执行补偿, 失败步骤: " + failedStep);
    }

    /**
     * 执行单个补偿步骤（含幂等检查）
     */
    private boolean compensateStep(String sagaId, String stepName,
                                   OrderRequest request) {
        // 幂等检查：如果该补偿已成功执行，直接跳过
        SagaStepLog existLog = stepLogMapper.findBySagaIdAndStepAndType(
                sagaId, stepName, "COMPENSATE");
        if (existLog != null && "SUCCESS".equals(existLog.getStatus())) {
            log.warn("[Saga] 补偿步骤已执行, 幂等跳过, sagaId={}, step={}", sagaId, stepName);
            return true;
        }

        logStep(sagaId, stepName, "COMPENSATE", "STARTED", request);
        log.info("[Saga] 执行补偿步骤: {}, sagaId={}", stepName, sagaId);

        try {
            switch (stepName) {
                case "CREATE_ORDER":
                    orderService.cancelOrder(request.getOrderId());
                    break;
                case "DEDUCT_INVENTORY":
                    inventoryService.restore(request.getSkuId(), request.getQuantity());
                    break;
                case "DEDUCT_COUPON":
                    couponService.restoreCoupon(request.getCouponId(), request.getOrderId());
                    break;
                case "DEDUCT_POINTS":
                    pointsService.restorePoints(
                            request.getUserId(), request.getPointsToUse(), request.getOrderId());
                    break;
                default:
                    log.error("[Saga] 未知补偿步骤: {}, sagaId={}", stepName, sagaId);
                    return false;
            }
            logStep(sagaId, stepName, "COMPENSATE", "SUCCESS", request);
            log.info("[Saga] 补偿步骤成功: {}, sagaId={}", stepName, sagaId);
            return true;

        } catch (Exception e) {
            logStepWithError(sagaId, stepName, "COMPENSATE", "FAILED",
                    request, e.getMessage());
            log.error("[Saga] 补偿步骤失败: {}, sagaId={}, error={}",
                    stepName, sagaId, e.getMessage(), e);
            return false;
        }
    }

    private void logStep(String sagaId, String stepName, String stepType,
                         String status, OrderRequest request) {
        SagaStepLog stepLog = new SagaStepLog();
        stepLog.setSagaId(sagaId);
        stepLog.setStepName(stepName);
        stepLog.setStepType(stepType);
        stepLog.setStatus(status);
        stepLog.setRequestData(JSON.toJSONString(request));
        stepLogMapper.insertOrUpdate(stepLog);
    }

    private void logStepWithError(String sagaId, String stepName, String stepType,
                                  String status, OrderRequest request, String error) {
        SagaStepLog stepLog = new SagaStepLog();
        stepLog.setSagaId(sagaId);
        stepLog.setStepName(stepName);
        stepLog.setStepType(stepType);
        stepLog.setStatus(status);
        stepLog.setRequestData(JSON.toJSONString(request));
        stepLog.setErrorMsg(error);
        stepLogMapper.insertOrUpdate(stepLog);
    }
}
```

```java
        String opId = "DEDUCT_" + skuId + "_" + quantity + "_" + Thread.currentThread().getId();
        // 幂等检查
        if (opRecordMapper.existsByOpId(opId)) {
            log.warn("[Inventory] 扣减已执行, 幂等返回, opId={}", opId);

        }
        if (inventory.getStock() < quantity) {
            throw new BusinessException("库存不足, skuId=" + skuId
                    + ", stock=" + inventory.getStock() + ", need=" + quantity);
        }

        inventoryMapper.deductStock(skuId, quantity, inventory.getVersion());

        InventoryOpRecord record = new InventoryOpRecord();
        record.setOpId(opId);
        record.setSkuId(skuId);
        record.setOpType("DEDUCT");
        record.setQuantity(quantity);
        opRecordMapper.insert(record);

        log.info("[Inventory] 扣减库存成功, skuId={}, quantity={}", skuId, quantity);
    }

    /**
     * 恢复库存（补偿操作，幂等）
     */

    public void restore(String skuId, int quantity) {

            log.warn("[Inventory] 恢复已执行, 幂等返回, opId={}", opId);

        InventoryOpRecord record = new InventoryOpRecord();
        record.setOpId(opId);
        record.setSkuId(skuId);
        record.setOpType("RESTORE");
        record.setQuantity(quantity);
        opRecordMapper.insert(record);

        log.info("[Inventory] 恢复库存成功(补偿), skuId={}, quantity={}", skuId, quantity);
    }
```

#### 8.2.5 异常处理说明

**步骤失败补偿**：以扣减积分失败为例，`executeStep`返回false后触发`failAndCompensate`。该方法查询saga_step_log表中状态为SUCCESS的DO步骤，反转顺序后依次执行补偿。补偿顺序为：还原优惠券 -> 恢复库存 -> 取消订单，与正向执行顺序严格相反。

**补偿失败处理**：单个补偿步骤失败不会中断其他步骤的补偿。`compensateStep`方法返回false后，编排器记录错误日志但继续执行后续补偿。如果存在补偿失败的步骤，Saga实例状态标记为FAILED，等待人工介入或定时任务重试。补偿方法内部实现幂等，重试不会产生副作用。

**幂等控制**：每个参与方的Do和Compensate方法都实现了幂等。订单服务通过orderId去重，库存和积分服务通过操作记录表opId去重，优惠券服务通过状态+orderId组合判断。Saga编排器层面也通过saga_step_log表的唯一约束保证步骤不会重复执行。

### 8.3 案例三：本地消息表实现最终一致性全链路

#### 8.3.1 业务场景

订单服务完成下单后，需要通知积分服务为用户增加积分。采用本地消息表方案：订单业务操作和消息表写入在同一个本地事务中完成，定时任务扫描消息表并通过MQ发送到积分服务，积分服务消费消息后执行加积分操作并保证幂等。

```
订单服务(主动方)                    MQ Broker              积分服务(被动方)
     │                                 │                        │
     │── 本地事务: 创建订单 + 写消息表 ──│                        │
     │                                 │                        │
     │── 定时扫描消息表 ──发送消息───▶│                        │
     │                                 │── 投递消息 ────────────▶│
     │                                 │                        │── 幂等检查
     │                                 │                        │── 增加积分
     │◀─────────── ACK ───────────────│◀── 确认消费 ────────────│
     │── 更新消息状态为SENT            │                        │
```

```java
package com.example.localmsg.order;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.util.Date;
import java.util.List;

/**
 * 消息发送定时任务
 *
 * 定期扫描PENDING状态的消息，发送到MQ，发送成功更新为SENT，失败则重试
 */
@Component
public class MessageSendScheduler {

    private static final Logger log = LoggerFactory.getLogger(MessageSendScheduler.class);

    private final LocalMessageMapper messageMapper;
    private final RocketMQSender mqSender;

    public MessageSendScheduler(LocalMessageMapper messageMapper,
                                 RocketMQSender mqSender) {
        this.messageMapper = messageMapper;
        this.mqSender = mqSender;
    }

    /**
     * 每5秒扫描一次待发送消息
     */
    @Scheduled(fixedDelay = 5000)
    public void scanAndSend() {
        List<LocalMessage> messages = messageMapper.findPendingMessages(100);
        if (messages.isEmpty()) {
            return;
        }
        log.info("[MessageScheduler] 扫描到{}条待发送消息", messages.size());

        for (LocalMessage message : messages) {
            sendSingleMessage(message);
        }
    }

    /**
     * 发送单条消息（含异常处理和重试控制）
     */
    private void sendSingleMessage(LocalMessage message) {
        try {
            log.info("[MessageScheduler] 发送消息, messageId={}, topic={}, retryCount={}",
                    message.getMessageId(), message.getTopic(), message.getRetryCount());

            // 发送到MQ
            SendResult result = mqSender.send(
                    message.getTopic(), message.getTag(),
                    message.getBody(), message.getMessageId());

            if (result != null && result.getSendStatus() == SendStatus.SEND_OK) {
                // 发送成功，更新状态为SENT
                messageMapper.updateStatus(message.getMessageId(), "SENT");
                log.info("[MessageScheduler] 消息发送成功, messageId={}",
                        message.getMessageId());
            } else {
                // 发送状态异常，走重试逻辑
                handleSendFailure(message, "MQ返回非OK状态: "
                        + (result == null ? "null" : result.getSendStatus()));
            }

        } catch (Exception e) {
            handleSendFailure(message, e.getMessage());
        }
    }

    /**
     * 处理发送失败：增加重试次数，计算下次重试时间
     */
    private void handleSendFailure(LocalMessage message, String error) {
        int newRetryCount = message.getRetryCount() + 1;
        log.error("[MessageScheduler] 消息发送失败, messageId={}, retryCount={}, error={}",
                message.getMessageId(), newRetryCount, error);

        if (newRetryCount >= message.getMaxRetry()) {
            // 超过最大重试次数，标记为FAILED，需人工介入
            messageMapper.updateStatusAndRetry(
                    message.getMessageId(), "FAILED", newRetryCount, null);
            log.error("[MessageScheduler] 消息超过最大重试次数, 标记为FAILED, messageId={}, "
                    + "需人工介入", message.getMessageId());
        } else {
            // 指数退避计算下次重试时间: 5s, 10s, 20s, 40s, 80s...
            long delayMs = (long) (5000 * Math.pow(2, newRetryCount - 1));
            Date nextRetryTime = new Date(System.currentTimeMillis() + delayMs);
            messageMapper.updateStatusAndRetry(
                    message.getMessageId(), "PENDING", newRetryCount, nextRetryTime);
            log.info("[MessageScheduler] 消息将在{}后重试, messageId={}",
                    nextRetryTime, message.getMessageId());
        }
    }
}
```

```java
package com.example.localmsg.points;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * 积分服务（被动方核心逻辑）
 *
 * 幂等控制：通过points_op_record表的唯一索引(op_id = messageId)保证
 * 同一消息重复消费不会导致积分重复增加
 */
@Service
public class PointsService {

    private static final Logger log = LoggerFactory.getLogger(PointsService.class);

    private final PointsAccountMapper pointsAccountMapper;
    private final PointsOpRecordMapper opRecordMapper;

    public PointsService(PointsAccountMapper pointsAccountMapper,
                         PointsOpRecordMapper opRecordMapper) {
        this.pointsAccountMapper = pointsAccountMapper;
        this.opRecordMapper = opRecordMapper;
    }

    /**
     * 增加积分（幂等：基于messageId去重）
     */
    @Transactional(rollbackFor = Exception.class)
    public void addPoints(PointsMessagePayload payload) {
        String opId = payload.getMessageId();

        // 1. 幂等检查：查询是否已处理过该消息
        PointsOpRecord existRecord = opRecordMapper.findByOpId(opId);
        if (existRecord != null) {
            log.warn("[PointsService] 积分已增加, 幂等返回, opId={}, orderId={}",
                    opId, payload.getOrderId());
            return;
        }

        // 2. 查询或创建积分账户
        PointsAccount account = pointsAccountMapper.findByUserId(payload.getUserId());
        if (account == null) {
            account = new PointsAccount();
            account.setUserId(payload.getUserId());
            account.setBalance(0);
            account.setVersion(0);
            try {
                pointsAccountMapper.insert(account);
            } catch (DuplicateKeyException e) {
                // 并发创建，重新查询
                account = pointsAccountMapper.findByUserId(payload.getUserId());
            }
        }

        // 3. 增加积分（乐观锁防并发）
        int updatedRows = pointsAccountMapper.addPoints(
                payload.getUserId(), payload.getPoints(), account.getVersion());
        if (updatedRows == 0) {
            // 乐观锁冲突，重试一次
            account = pointsAccountMapper.findByUserId(payload.getUserId());
            updatedRows = pointsAccountMapper.addPoints(
                    payload.getUserId(), payload.getPoints(), account.getVersion());
            if (updatedRows == 0) {
                throw new BusinessException("积分增加失败(并发冲突), userId="
                        + payload.getUserId());
            }
        }

        // 4. 记录操作日志（唯一索引保证幂等）
        PointsOpRecord opRecord = new PointsOpRecord();
        opRecord.setOpId(opId);
        opRecord.setUserId(payload.getUserId());
        opRecord.setOpType("ADD");
        opRecord.setPoints(payload.getPoints());
        opRecord.setOrderId(payload.getOrderId());
        try {
            opRecordMapper.insert(opRecord);
        } catch (DuplicateKeyException e) {
            // 并发消费同一消息，操作记录已存在，回滚积分（因为前面加了积分）
            log.warn("[PointsService] 操作记录已存在(并发消费), 回滚积分, opId={}", opId);
            pointsAccountMapper.deductPoints(
                    payload.getUserId(), payload.getPoints(), account.getVersion() + 1);
            return;
        }

        log.info("[PointsService] 积分增加成功, userId={}, points={}, orderId={}, opId={}",
                payload.getUserId(), payload.getPoints(), payload.getOrderId(), opId);
    }
}
```

#### 8.3.6 全链路异常处理说明

**消息发送失败**：定时任务扫描PENDING状态消息时，如果MQ发送抛异常或返回非OK状态，`handleSendFailure`方法会增加重试计数并按指数退避策略计算下次重试时间（5s, 10s, 20s, 40s...）。超过最大重试次数（默认10次）后，消息状态标记为FAILED，触发告警等待人工介入。消息状态始终保持在本地消息表中，不会丢失。

**消息重复消费**：MQ的At-Least-Once语义保证消息至少被消费一次，但可能重复投递。积分服务通过`points_op_record`表的唯一索引（op_id = messageId）保证幂等。首次消费时插入操作记录并增加积分；重复消费时查询到操作记录已存在，直接幂等返回，不重复增加积分。

**消费失败重试**：积分服务消费消息时如果发生异常（如数据库不可用），消费者返回`RECONSUME_LATER`，MQ会自动稍后重新投递该消息。重试次数由MQ配置控制，超过最大重试次数后消息进入死信队列，需人工处理。

**业务事务与消息的原子性**：订单服务和消息表的写入在同一个`@Transactional`事务中。如果创建订单成功但写消息表失败，整个事务回滚，订单也不会创建；如果创建订单失败，消息表也不会有记录。这保证了业务操作与消息记录的原子性，不会出现"订单创建了但消息丢失"或"消息发了但订单没创建"的数据不一致问题。

**并发消费冲突**：当MQ重复投递同一消息被多个消费者实例同时处理时，`PointsService.addPoints`方法通过乐观锁和操作记录表唯一索引双重保障。先通过`findByOpId`查询做第一层幂等检查；若并发绕过检查，`opRecordMapper.insert`的唯一索引约束会抛出`DuplicateKeyException`，捕获后回滚已增加的积分，保证最终数据一致。
