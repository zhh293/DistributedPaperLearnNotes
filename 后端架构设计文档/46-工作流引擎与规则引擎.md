# 工作流引擎与规则引擎

## 一、问题背景

### 1.1 业务痛点

在企业级应用开发中，业务流程管理和业务规则决策是两大核心难题：

**工作流方面的痛点：**
- **流程控制与业务逻辑耦合**：订单审批、采购流程、报销审批等业务场景有明显的状态转化步骤，传统的硬编码方式将流程控制逻辑与业务操作耦合在一起，导致维护和迭代成本极高
- **流程变更困难**：业务流程经常变化（如增加审批节点、调整审批顺序），传统方式需要修改代码、重新部署才能生效
- **跨系统协作复杂**：采购系统下单后需转到财务系统付款，再转入物流系统配送，最后转入仓储系统管理——整个流程横跨多个系统，缺乏统一的编排能力
- **流程可视化缺失**：业务方无法直观地查看流程当前进展、历史轨迹和积压情况

**规则引擎方面的痛点：**
- **硬编码实现业务规则难以维护**：以信用卡申请场景为例，合法性检查规则可能包含数十条条件判断，使用if-else实现会导致代码极其臃肿
- **规则变更需要重启服务**：业务规则（如优惠策略、风险评级标准）频繁变化，传统方式修改代码后需要重新部署才能生效
- **规则无法被业务人员理解**：规则以代码形式存在，业务分析人员无法参与规则的编辑和维护
- **规则之间缺乏隔离**：不同业务模块的规则相互交织，修改一处可能影响其他模块

### 1.2 解决方案

工作流引擎和规则引擎分别解决上述两类问题：

- **工作流引擎**：对工作流程及其各操作步骤之间业务规则的抽象、概括描述。将工作流程中的工作如何前后组织在一起的逻辑和规则，在计算机中以恰当的模型表达并对其实施计算，实现业务流程的自动化
- **规则引擎**：全称为业务规则管理系统（BRMS），将应用程序中的业务决策部分分离出来，使用预定义的语义模块编写业务规则，由用户或开发者在需要时进行配置、管理。接收数据输入，解释业务规则，并根据规则做出业务决策

### 1.3 适用场景

工作流引擎适用于需要人工参与的或每一个步骤执行时间超过秒级的自动化业务场景：
- 关键业务流程：订单处理、报价处理、采购处理、合同审核、供应链管理
- 行政管理类：出差申请、加班申请、请假申请、用车申请、各种办公用品申请
- 人事管理类：员工培训安排、绩效考评、职位变动处理
- 财务相关类：付款请求、应收款处理、日常报销处理、预算和计划申请
- 客户服务类：客户信息管理、客户投诉处理、售后服务管理
- 跨系统协作：多个系统之间的打通和协作，充当系统间交互的胶水角色

规则引擎适用于存在比较复杂的业务规则并且业务规则会频繁变动的系统：
- 风险控制系统：风险贷款、风险评估
- 反欺诈项目：银行贷款、征信验证
- 决策平台系统：财务计算
- 促销平台系统：满减、打折、加价购

## 二、整体架构设计

### 2.1 架构总览

工作流引擎与规则引擎的整体架构分为六层：

```
┌─────────────────────────────────────────────────────────────┐
│                      管理控制层                               │
│  流程设计器 | 规则编辑器 | 动态表单 | 模板管理 | 权限管理     │
├─────────────────────────────────────────────────────────────┤
│                      编排调度层                               │
│  DAG执行引擎 | 状态机调度 | 任务分配 | 自适应路由 | Checkpoint │
├─────────────────────────────────────────────────────────────┤
│                      引擎执行层                               │
│  流程引擎(BPMN) | 规则引擎(Drools) | 推理引擎 | 模式匹配器    │
├─────────────────────────────────────────────────────────────┤
│                      事件驱动层                               │
│  事件回调 | 消息通知 | 任务触发 | 规则激活 | 事件溯源          │
├─────────────────────────────────────────────────────────────┤
│                      数据持久层                               │
│  流程实例存储 | 任务实例存储 | 规则库 | 工作内存 | 执行日志     │
├─────────────────────────────────────────────────────────────┤
│                      接入交互层                               │
│  Thrift接口 | HTTP接口 | SDK | 动态表单UI | 审批页面           │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 工作流引擎核心概念

| 概念 | 说明 |
|------|------|
| 流程定义(Process Definition) | 对业务流程的静态描述，包括节点、连线和网关，遵循BPMN 2.0标准 |
| 流程实例(Process Instance) | 流程定义的一次具体执行，每个流程实例有唯一的实例ID |
| 任务(Task) | 流程中需要人工或自动完成的工作单元，是流程执行的核心 |
| 节点(Node) | 流程中的执行单元，包括开始节点、结束节点、用户任务节点、服务节点、脚本节点等 |
| 网关(Gateway) | 控制流程走向的决策点，包括排他网关（XOR）、并行网关（AND）、包容网关（OR） |
| 事件(Event) | 流程中发生的特定事情，包括开始事件、结束事件、中间事件、边界事件 |
| 变量(Variable) | 流程执行过程中传递的数据，分为流程变量和任务变量 |

### 2.3 规则引擎核心概念

| 概念 | 说明 |
|------|------|
| 工作内存(Working Memory) | 规则引擎运行时的数据存储区，应用程序将数据插入工作内存供规则匹配 |
| 事实(Fact) | 插入到工作内存中的JavaBean对象，是应用程序与规则引擎进行数据交互的桥梁 |
| 规则库(Rule Base) | 存储所有规则定义的集合，规则以.drl文件或数据库形式存储 |
| 匹配器(Pattern Matcher) | 将规则库中的规则与工作内存中的事实进行模式匹配，匹配成功的规则被激活 |
| 议程(Agenda) | 存放通过匹配器激活的规则，按优先级排序等待执行 |
| 执行引擎(Execution Engine) | 执行议程中被激活的规则的动作部分 |

### 2.4 DAG工作流编排架构

现代工作流引擎引入了DAG（有向无环图）驱动的编排架构，支持确定性节点和智能节点的混合编排：

- **确定性节点**：分支管理、编译构建、单元测试、创建PR等，通过脚本执行，快速、稳定、可预测
- **智能节点**：需求理解、技术方案设计、代码编写、CI失败修复等，需要AI的创造力
- **并行执行**：多个独立节点可以并行执行，完成后自动汇合
- **自适应路由**：系统在执行前根据任务画像（类型 x 复杂度 x 风险）动态裁剪执行路径

```java
public class ProcessDefinition {
    private String id;
    private String name;
    private String version;
    private List<FlowElement> flowElements;  // 流程元素列表
    private List<FlowNode> flowNodes;        // 流程节点

/**
 * 流程节点基类
 */
public abstract class FlowNode {
    private String id;
    private String name;
    private NodeType type;
    private List<SequenceFlow> incomingFlows;  // 入边
    private List<SequenceFlow> outgoingFlows;  // 出边
    private Map<String, Object> properties;    // 节点属性
}

/**
 * 用户任务节点
 */
public class UserTask extends FlowNode {
    private String assignee;              // 任务负责人
    private List<String> candidateUsers;   // 候选用户列表
    private List<String> candidateGroups;  // 候选组列表
    private String formKey;               // 表单标识
    private TaskPriority priority;        // 任务优先级
    private int dueDate;                  // 超时时间（小时）
}

/**
 * 服务任务节点
 */
public class ServiceTask extends FlowNode {
    private String serviceName;      // 服务名称
    private String interfaceType;    // 接口类型: THRIFT, HTTP, MQ
    private String interfaceUrl;     // 接口地址
    private Map<String, String> inputParameters;  // 输入参数
    private Map<String, String> outputParameters; // 输出参数
}

/**
 * 网关类型枚举
 */
public enum GatewayType {
    EXCLUSIVE,    // 排他网关(XOR): 只有一条路径被执行
    PARALLEL,     // 并行网关(AND): 所有路径同时执行
    INCLUSIVE,    // 包容网关(OR): 满足条件的路径同时执行
    EVENT_BASED   // 事件网关: 基于事件选择路径
}
```

#### 3.1.2 流程执行引擎

```java
/**
 * 流程执行引擎
 * 负责流程实例的创建、执行和状态管理
 */
public class ProcessEngine {

    private final ProcessDefinitionRegistry definitionRegistry;
    private final ProcessInstanceRepository instanceRepository;
    private final TaskService taskService;
    private final EventDispatcher eventDispatcher;

    /**
     * 启动流程实例
     */
    public ProcessInstance startProcess(String processDefinitionId,
                                         Map<String, Object> variables) {
        // 1. 获取流程定义
        ProcessDefinition definition = definitionRegistry.get(processDefinitionId);
        if (definition == null) {
            throw new ProcessDefinitionNotFoundException(processDefinitionId);
        }

        // 2. 创建流程实例
        ProcessInstance instance = ProcessInstance.builder()
                .id(generateInstanceId())
                .processDefinitionId(processDefinitionId)
                .processDefinitionName(definition.getName())
                .status(ProcessStatus.RUNNING)
                .variables(variables)
                .startTime(new Date())
                .currentNode(definition.getStartNode())
                .build();

        // 3. 持久化流程实例
        instanceRepository.save(instance);

        // 4. 从开始节点执行
        executeNode(instance, definition.getStartNode());

        return instance;
    }

    /**
     * 执行节点
     */
    private void executeNode(ProcessInstance instance, FlowNode node) {
        try {
            // 触发节点开始事件
            eventDispatcher.dispatchNodeStartEvent(instance, node);

            // 根据节点类型执行
            switch (node.getType()) {
                case START_EVENT:
                    handleStartEvent(instance, node);
                    break;
                case USER_TASK:
                    handleUserTask(instance, (UserTask) node);
                    break;
                case SERVICE_TASK:
                    handleServiceTask(instance, (ServiceTask) node);
                    break;
                case EXCLUSIVE_GATEWAY:
                    handleExclusiveGateway(instance, (Gateway) node);
                    break;
                case PARALLEL_GATEWAY:
                    handleParallelGateway(instance, (Gateway) node);
                    break;
                case END_EVENT:
                    handleEndEvent(instance, node);
                    break;
                default:
                    throw new UnsupportedNodeTypeException(node.getType());
            }

            // 触发节点结束事件
            eventDispatcher.dispatchNodeEndEvent(instance, node);

        } catch (Exception e) {
            handleExecutionError(instance, node, e);
        }
    }

    /**
     * 处理用户任务
     */
    private void handleUserTask(ProcessInstance instance, UserTask userTask) {
        // 创建任务实例
        Task task = Task.builder()
                .id(generateTaskId())
                .processInstanceId(instance.getId())
                .processDefinitionId(instance.getProcessDefinitionId())
                .nodeId(userTask.getId())
                .nodeName(userTask.getName())
                .assignee(userTask.getAssignee())
                .candidateUsers(userTask.getCandidateUsers())
                .candidateGroups(userTask.getCandidateGroups())
                .status(TaskStatus.PENDING)
                .priority(userTask.getPriority())
                .createTime(new Date())
                .dueDate(calculateDueDate(userTask.getDueDate()))
                .build();

        taskService.createTask(task);

        // 如果配置了调度规则，自动分配任务负责人
        if (userTask.getAssignee() == null) {
            assignTaskByRule(task, userTask);
        }

        // 推送任务通知
        eventDispatcher.dispatchTaskCreatedEvent(task);
    }

    /**
     * 处理服务任务
     */
    private void handleServiceTask(ProcessInstance instance, ServiceTask serviceTask) {
        // 根据接口类型调用外部服务
        Object result;
        switch (serviceTask.getInterfaceType()) {
            case "THRIFT":
                result = thriftInvoker.invoke(serviceTask.getInterfaceUrl(),
                        serviceTask.getInputParameters());
                break;
            case "HTTP":
                result = httpInvoker.invoke(serviceTask.getInterfaceUrl(),
                        serviceTask.getInputParameters());
                break;
            case "MQ":
                mqSender.send(serviceTask.getInterfaceUrl(),
                        serviceTask.getInputParameters());
                result = null; // 异步调用，不等待结果
                break;
            default:
                throw new UnsupportedInterfaceTypeException(serviceTask.getInterfaceType());
        }

        // 将结果写入流程变量
        if (result != null) {
            for (Map.Entry<String, String> entry : serviceTask.getOutputParameters().entrySet()) {
                String variableName = entry.getKey();
                String resultKey = entry.getValue();
                Object value = extractValue(result, resultKey);
                instance.setVariable(variableName, value);
            }
            instanceRepository.update(instance);
        }

        // 服务任务完成后自动流向下一节点
        moveToNextNode(instance, serviceTask);
    }

    /**
     * 处理排他网关
     */
    private void handleExclusiveGateway(ProcessInstance instance, Gateway gateway) {
        // 评估所有出边的条件，选择第一个满足条件的路径
        for (SequenceFlow flow : gateway.getOutgoingFlows()) {
            String condition = flow.getCondition();
            if (evaluateCondition(condition, instance.getVariables())) {
                moveToNode(instance, flow.getTargetNode());
                return;
            }
        }
        // 如果没有条件满足，使用默认路径
        SequenceFlow defaultFlow = gateway.getOutgoingFlows().stream()
                .filter(SequenceFlow::isDefault)
                .findFirst()
                .orElseThrow(() -> new NoConditionMatchedException(gateway.getId()));
        moveToNode(instance, defaultFlow.getTargetNode());
    }

    /**
     * 处理并行网关
     * 并行网关一般需要有开有闭，不要使用只有奇数个并行网关的流程图
     */
    private void handleParallelGateway(ProcessInstance instance, Gateway gateway) {
        // 并行网关-分叉：创建所有出边的并行执行分支
        if (gateway.getOutgoingFlows().size() > 1) {
            for (SequenceFlow flow : gateway.getOutgoingFlows()) {
                // 为每个分支创建并行执行上下文
                ExecutionContext branchContext = ExecutionContext.builder()
                        .processInstanceId(instance.getId())
                        .parentNode(gateway)
                        .targetNode(flow.getTargetNode())
                        .build();
                // 异步执行每个分支
                asyncExecutor.execute(() -> executeNode(instance, flow.getTargetNode()));
            }
        }
        // 并行网关-汇合：等待所有分支到达后继续
        else if (gateway.getIncomingFlows().size() > 1) {
            int arrivedBranches = incrementArrivedBranches(instance, gateway);
            if (arrivedBranches == gateway.getIncomingFlows().size()) {
                // 所有分支都到达，继续执行
                resetArrivedBranches(instance, gateway);
                moveToNextNode(instance, gateway);
            }
        }
    }

    /**
     * 完成任务，推进流程
     */
    public void completeTask(String taskId, Map<String, Object> taskVariables,
                              Map<String, Object> processVariables) {
        // 1. 获取任务并校验状态
        Task task = taskService.getTask(taskId);
        if (task.getStatus() != TaskStatus.PENDING) {
            throw new TaskAlreadyCompletedException(taskId);
        }

        // 2. 更新任务状态
        task.setStatus(TaskStatus.COMPLETED);
        task.setCompleteTime(new Date());
        task.setVariables(taskVariables);
        taskService.updateTask(task);

        // 3. 获取流程实例
        ProcessInstance instance = instanceRepository.get(task.getProcessInstanceId());

        // 4. 将任务变量合并到流程变量
        if (processVariables != null) {
            instance.getVariables().putAll(processVariables);
        }
        if (taskVariables != null) {
            instance.getVariables().putAll(taskVariables);
        }
        instanceRepository.update(instance);

        // 5. 获取当前节点，流向下一节点
        FlowNode currentNode = definitionRegistry.getNode(
                instance.getProcessDefinitionId(), task.getNodeId());
        moveToNextNode(instance, currentNode);
    }
}
```

#### 3.1.3 事件回调机制

```java
/**
 * 事件回调管理器
 * 工作流引擎对外提供两类接口：主动触发类（事件回调）和调用类接口
 */
public class EventCallbackManager {

    private final Map<String, List<EventCallback>> callbackRegistry = new ConcurrentHashMap<>();

    /**
     * 注册事件回调
     * @param nodeId 节点ID
     * @param trigger 触发时机：NODE_START, NODE_END, TASK_ASSIGNED
     * @param action 触发动作：THRIFT回调, HTTP回调, MQ消息
     */
    public void registerCallback(String nodeId, EventTrigger trigger,
                                  CallbackAction action) {
        String key = nodeId + ":" + trigger.name();
        callbackRegistry.computeIfAbsent(key, k -> new ArrayList<>()).add(
                new EventCallback(nodeId, trigger, action));
    }

    /**
     * 触发节点事件
     */
    public void dispatchNodeEvent(ProcessInstance instance, FlowNode node,
                                   EventTrigger trigger) {
        String key = node.getId() + ":" + trigger.name();
        List<EventCallback> callbacks = callbackRegistry.get(key);
        if (callbacks == null || callbacks.isEmpty()) {
            return;
        }

        for (EventCallback callback : callbacks) {
            try {
                executeCallback(callback, instance, node);
            } catch (Exception e) {
                // 回调失败不影响流程执行，记录日志后继续
                log.error("Event callback failed for node {}", node.getId(), e);
                // 对于关键回调，触发重试
                if (callback.getAction().isCritical()) {
                    retryExecutor.scheduleRetry(callback, instance, node);
                }
            }
        }
    }

    /**
     * 执行回调
     * 注意：回调接口需要做幂等性处理，因为可能存在重复调用
     */
    private void executeCallback(EventCallback callback, ProcessInstance instance,
                                  FlowNode node) {
        CallbackAction action = callback.getAction();
        Map<String, Object> payload = buildCallbackPayload(instance, node);

        switch (action.getType()) {
            case THRIFT:
                thriftClient.invoke(action.getTarget(), payload);
                break;
            case HTTP:
                httpClient.post(action.getTarget(), payload);
                break;
            case MQ:
                mqProducer.send(action.getTarget(), payload);
                break;
        }
    }
}
```

```java
/**
 * 任务调度服务
 * 支持通过规则设置任务负责人，自动分配任务
 */
public class TaskSchedulingService {

    private final RuleEvaluator ruleEvaluator;
    private final UserService userService;

    /**
     * 根据调度规则自动分配任务负责人
     */
    public void assignTaskByRule(Task task, String schedulingRule) {
        // 1. 解析调度规则
        SchedulingRule rule = parseSchedulingRule(schedulingRule);

        // 2. 根据规则类型执行分配
        switch (rule.getType()) {
            case DIRECT_ASSIGN:
                // 直接指定负责人
                task.setAssignee(rule.getAssignee());
                break;
            case ROLE_BASED:
                // 基于角色分配
                List<String> candidates = userService.getUsersByRole(rule.getRole());
                task.setCandidateUsers(candidates);
                break;
            case ROUND_ROBIN:
                // 轮询分配
                String nextUser = roundRobinSelector.select(
                        rule.getRole(), task.getProcessDefinitionId());
                task.setAssignee(nextUser);
                break;
            case LOAD_BALANCE:
                // 负载均衡分配
                String leastLoadedUser = loadBalancer.selectLeastLoaded(
                        rule.getRole());
                task.setAssignee(leastLoadedUser);
                break;
            case RULE_ENGINE:
                // 使用规则引擎动态决定
                Map<String, Object> context = buildRuleContext(task);
                String assignee = ruleEvaluator.evaluate(rule.getRuleId(), context);
                task.setAssignee(assignee);
                break;
        }

        // 3. 更新任务
        taskService.updateTask(task);

        // 4. 发送通知
        if (task.getAssignee() != null) {
            notificationService.notifyTaskAssigned(task);
        }
    }
}
```

### 3.2 规则引擎核心设计

#### 3.2.1 规则定义与执行

```java
/**
 * 规则引擎核心
 * 基于Drools实现，包含工作内存、规则库、推理引擎
 */
public class RuleEngine {

    private final KieContainer kieContainer;
    private final RuleRepository ruleRepository;

    /**
     * 执行规则
     * @param ruleSet 规则集标识
     * @param facts 输入的事实对象列表
     * @return 规则执行结果
     */
    public RuleExecutionResult execute(String ruleSet, List<Object> facts) {
        // 1. 创建KieSession
        KieSession session = kieContainer.newKieSession(ruleSet);

        try {
            // 2. 将事实对象插入工作内存(Working Memory)
            for (Object fact : facts) {
                session.insert(fact);
            }

            // 3. 设置全局变量
            session.setGlobal("resultCollector", new ResultCollector());

            // 4. 激活规则引擎，执行模式匹配
            // Pattern Matcher将规则库中的规则与工作内存中的Fact进行模式匹配
            // 匹配成功的规则被放入Agenda
            // Execution Engine执行Agenda中的规则
            int firedRules = session.fireAllRules();

            // 5. 获取执行结果
            ResultCollector collector = (ResultCollector) session.getGlobal("resultCollector");
            return RuleExecutionResult.builder()
                    .firedRuleCount(firedRules)
                    .results(collector.getResults())
                    .build();

        } finally {
            // 6. 关闭会话，释放资源
            session.dispose();
        }
    }

    /**
     * 动态加载规则（不重启服务即可生效）
     */
    public void loadRules(String ruleSetId, List<RuleDefinition> rules) {
        // 1. 将规则定义转换为DRL格式
        StringBuilder drlBuilder = new StringBuilder();
        drlBuilder.append("package ").append(ruleSetId).append("\n");

        // 添加import语句
        Set<String> imports = collectImports(rules);
        for (String imp : imports) {
            drlBuilder.append("import ").append(imp).append("\n");
        }

        // 添加规则
        for (RuleDefinition rule : rules) {
            drlBuilder.append(convertToDrl(rule)).append("\n");
        }

        // 2. 编译规则
        KieHelper helper = new KieHelper();
        helper.addContent(drlBuilder.toString(), ResourceType.DRL);
        KieModule module = helper.build();

        // 3. 更新KieContainer
        kieContainer.updateToVersion(module.getReleaseId());

        log.info("Rules loaded for ruleSet {}, rule count: {}", ruleSetId, rules.size());
    }

    /**
     * 将规则定义转换为DRL格式
     */
    private String convertToDrl(RuleDefinition rule) {
        StringBuilder sb = new StringBuilder();
        sb.append("rule \"").append(rule.getName()).append("\"\n");

        // 规则属性
        if (rule.getSalience() != null) {
            sb.append("    salience ").append(rule.getSalience()).append("\n");
        }
        if (rule.isNoLoop()) {
            sb.append("    no-loop true\n");
        }
        if (rule.getActivationGroup() != null) {
            sb.append("    activation-group \"").append(rule.getActivationGroup()).append("\"\n");
        }

        // LHS (条件部分)
        sb.append("    when\n");
        for (Condition condition : rule.getConditions()) {
            sb.append("        ").append(condition.toDrl()).append("\n");
        }

        // RHS (动作部分)
        sb.append("    then\n");
        for (Action action : rule.getActions()) {
            sb.append("        ").append(action.toDrl()).append("\n");
        }

        sb.append("end\n");
        return sb.toString();
    }
}
```

```java
 * 对应DRL中的 rule "ruleName" when LHS then RHS end

    private Integer salience;         // 优先级（数值越大优先级越高）
    private boolean noLoop;           // 是否禁止循环执行
    private String activationGroup;   // 激活组（同组只执行一个）

 * 语法：绑定变量名:Object(Field约束)
 * 示例：$order:Order(originalPrice < 100)
 */

    private String bindingVariable;   // 绑定变量名（以$开头，可省略）
    private String objectType;        // 对象类型
    private List<FieldConstraint> constraints; // 字段约束

    public String toDrl() {
        StringBuilder sb = new StringBuilder();
        if (bindingVariable != null) {
            sb.append(bindingVariable).append(":");
        }
        sb.append(objectType).append("(");
        for (int i = 0; i < constraints.size(); i++) {
            if (i > 0) sb.append(", ");
            sb.append(constraints.get(i).toDrl());
        }
        sb.append(")");
        return sb.toString();
    }
}

/**
 * 字段约束
 */

    private String fieldName;      // 字段名
    private String operator;       // 操作符: <, >, ==, !=, >=, <=, in, not in
    private Object value;          // 比较值

    public String toDrl() {
        return fieldName + " " + operator + " " + formatValue(value);
    }
```

```java
        RuleDefinition oldRule = ruleRepository.getRule(ruleSetId, ruleName);
        if (oldRule == null) {
            throw new RuleNotFoundException(ruleSetId, ruleName);
        }

        // 2. 更新规则
        ruleRepository.update(ruleSetId, ruleName, newRule);

        // 3. 记录版本（支持回滚）
        versionManager.createVersion(ruleSetId,
                "修改规则: " + ruleName + " from " + oldRule.getVersion() + " to " + newRule.getVersion());

        // 4. 热加载
        List<RuleDefinition> allRules = ruleRepository.getAllRules(ruleSetId);
        ruleEngine.loadRules(ruleSetId, allRules);
    }

     * 回滚规则到指定版本
     */
    public void rollbackRule(String ruleSetId, String version) {
        List<RuleDefinition> rules = versionManager.getRulesByVersion(ruleSetId, version);
        ruleRepository.replaceAll(ruleSetId, rules);
        ruleEngine.loadRules(ruleSetId, rules);
        log.info("Rules rolled back: ruleSet={}, version={}", ruleSetId, version);
    }

        if (rule.getConditions() == null || rule.getConditions().isEmpty()) {
            throw new InvalidRuleException("Rule must have at least one condition");

        if (rule.getActions() == null || rule.getActions().isEmpty()) {
            throw new InvalidRuleException("Rule must have at least one action");

            ruleEngine.compileTest(rule);
```

```java
/**
 * DAG工作流节点定义
 * 支持确定性节点和智能节点的混合编排

public class DAGNode {
    private String id;
    private String name;
    private NodeType type;           // DETERMINISTIC(确定性), AGENT(智能), CHECKPOINT(检查点)
    private String executor;         // 执行器标识
    private Map<String, Object> config; // 节点配置
    private List<String> dependencies;  // 依赖节点ID列表
    private RetryPolicy retryPolicy;    // 重试策略
    private TimeoutConfig timeout;      // 超时配置
}

/**
 * DAG工作流定义
 */
public class DAGWorkflow {
    private String id;
    private String name;
    private List<DAGNode> nodes;
    private Map<String, List<String>> adjacencyList; // 邻接表
    private CheckpointConfig checkpointConfig;       // 检查点配置
    private BudgetConfig budgetConfig;               // 预算限制（如最多重试次数）
}

/**
 * DAG执行引擎
 */
public class DAGExecutionEngine {

    private final ExecutorService executor;
    private final NodeExecutorRegistry executorRegistry;
    private final CheckpointManager checkpointManager;

    /**
     * 执行DAG工作流
     */
    public WorkflowResult execute(DAGWorkflow workflow, WorkflowContext context) {
        // 1. 拓扑排序，确定执行顺序
        List<String> topologicalOrder = topologicalSort(workflow);

        // 2. 初始化检查点
        checkpointManager.initCheckpoint(workflow, context);

        // 3. 按拓扑序执行节点
        Map<String, CompletableFuture<NodeResult>> futures = new ConcurrentHashMap<>();

        for (String nodeId : topologicalOrder) {
            DAGNode node = workflow.getNode(nodeId);

            // 等待所有依赖节点完成
            CompletableFuture<Void> dependenciesFuture = waitForDependencies(
                    node.getDependencies(), futures);

            // 创建当前节点的执行Future
            CompletableFuture<NodeResult> nodeFuture = dependenciesFuture.thenApplyAsync(v -> {
                // 检查是否需要人工确认（Checkpoint）
                if (node.getType() == NodeType.CHECKPOINT) {
                    checkpointManager.waitForApproval(nodeId, context);
                }

                // 执行节点
                return executeNodeWithRetry(node, context);
            }, executor);

            futures.put(nodeId, nodeFuture);
        }

        // 4. 等待所有节点完成
        CompletableFuture.allOf(futures.values().toArray(new CompletableFuture[0])).join();

        // 5. 收集结果
        return collectResults(workflow, futures, context);
    }

    /**
     * 带重试的节点执行
     */
    private NodeResult executeNodeWithRetry(DAGNode node, WorkflowContext context) {
        int maxRetries = node.getRetryPolicy() != null ? node.getRetryPolicy().getMaxRetries() : 0;
        int attempts = 0;

        while (attempts <= maxRetries) {
            try {
                NodeExecutor executor = executorRegistry.get(node.getExecutor());
                NodeResult result = executor.execute(node, context);

                // 检查是否需要触发应急预案
                if (!result.isSuccess() && attempts < maxRetries) {
                    attempts++;
                    log.warn("Node {} failed (attempt {}/{}), retrying...",
                            node.getId(), attempts, maxRetries);
                    Thread.sleep(node.getRetryPolicy().getRetryInterval());
                    continue;
                }

                return result;

            } catch (Exception e) {
                attempts++;
                if (attempts > maxRetries) {
                    // 超过最大重试次数，触发应急预案
                    return handleNodeFailure(node, context, e);
                }
                log.warn("Node {} threw exception (attempt {}/{})",
                        node.getId(), attempts, maxRetries, e);
            }
        }

        return NodeResult.failure("Max retries exceeded");
    }

    /**
     * 节点失败处理（应急预案）
     */
    private NodeResult handleNodeFailure(DAGNode node, WorkflowContext context, Exception e) {
        // 编码连续失败3次 → 回退到技术方案重新评审
        // 测试连续失败2次 → 携带失败上下文重试编码
        // 任何阶段超时 → 升级到人工处理
        EmergencyPlan plan = EmergencyPlanFactory.create(node, e);
        return plan.execute(context);
    }
}
```

```java
/**
 * 自适应路由器
 * 根据任务画像动态裁剪执行路径
 */
public class AdaptiveRouter {

    /**
     * 生成执行路径
     */
    public ExecutionPath planPath(DAGWorkflow workflow, TaskProfile profile) {
        ExecutionPath path = new ExecutionPath();

        for (DAGNode node : workflow.getNodes()) {
            RouteDecision decision = decide(node, profile);

            switch (decision.getAction()) {
                case EXECUTE:
                    path.addNode(node, NodeAction.EXECUTE);
                    break;
                case SKIP:
                    path.addNode(node, NodeAction.SKIP);
                    log.info("Skipping node {} due to {}", node.getId(), decision.getReason());
                    break;
                case MERGE:
                    // 快速路径：简单任务合并多个阶段
                    path.mergeNode(node);
                    break;
                case PARALLEL:
                    // 动态并行：多仓库需求自动开启并行
                    path.enableParallel(node);
                    break;
            }
        }

        return path;
    }

    /**
     * 路由决策（双层决策：LLM推理 + 规则兜底）
     */
    private RouteDecision decide(DAGNode node, TaskProfile profile) {
        // 规则兜底（Guardrail）
        if (isMandatory(node, profile)) {
            return RouteDecision.execute();
        }

        // 条件跳过
        if (shouldSkip(node, profile)) {
            return RouteDecision.skip(node.getSkipReason());
        }

        // 快速路径：简单配置变更(<50 LOC)压缩路径
        if (profile.getComplexity() == Complexity.SIMPLE
                && profile.getCodeChangeLOC() < 50) {
            return RouteDecision.merge();
        }

        // 经验驱动：参考历史执行路径
        ExecutionHistory history = historyService.findSimilar(profile);
        if (history != null && history.hasOptimizedPath()) {
            return RouteDecision.fromHistory(history);
        }

        return RouteDecision.execute();
    }
}
```

```java
/**
 * 工作内存管理

public class WorkingMemory {

    private final Map<FactHandle, Object> facts = new ConcurrentHashMap<>();
    private final EventSupport eventSupport;

    /**
     * 插入事实对象到工作内存
     */
    public FactHandle insert(Object fact) {
        FactHandle handle = new DefaultFactHandle(fact);
        facts.put(handle, fact);

        // 触发规则重新匹配
        eventSupport.fireObjectInserted(handle, fact);

        return handle;
    }

    /**
     * 更新工作内存中的事实对象
     * 更新后规则引擎会重新进行相关规则的匹配
     */
    public void update(FactHandle handle, Object newFact) {
        Object oldFact = facts.get(handle);
        facts.put(handle, newFact);

        // 触发规则重新匹配
        eventSupport.fireObjectUpdated(handle, oldFact, newFact);
    }

    /**
     * 从工作内存中删除事实对象
     */
    public void delete(FactHandle handle) {
        Object fact = facts.remove(handle);

        // 触发规则重新匹配
        eventSupport.fireObjectDeleted(handle, fact);
    }

    /**
     * 获取指定类型的所有事实对象
     */
    public <T> Collection<T> getFacts(Class<T> type) {
        return facts.values().stream()
                .filter(type::isInstance)
                .map(type::cast)
                .collect(Collectors.toList());
    }
```

```java
/**
 * 流程执行异常处理器
 */
public class ProcessExceptionHandler {

    /**
     * 处理流程执行错误
     */
    public void handleExecutionError(ProcessInstance instance, FlowNode node, Exception e) {
        log.error("Process execution error: instance={}, node={}", 
                instance.getId(), node.getId(), e);

        if (e instanceof ProcessDefinitionNotFoundException) {
            // 流程定义不存在
            instance.setStatus(ProcessStatus.FAILED);
            instance.setErrorMessage("流程定义不存在: " + e.getMessage());

        } else if (e instanceof TaskAlreadyCompletedException) {
            // 任务已被完成（非法操作）
            // 流程实例已结束的情况下操作变量是非法操作
            // 某个任务已完成后再次完成也属于非法操作
            log.warn("Illegal operation on completed task, ignoring");
            // 不重试非法操作

        } else if (e instanceof ConflictOperationException) {
            // 冲突操作：同一时刻对同一流程实例只会有一个操作被正确执行
            // 业务进行重试可以保证操作不被漏掉
            retryExecutor.scheduleRetry(() -> {
                processEngine.executeNode(instance, node);
            }, 3, 1000);

        } else if (e instanceof ServiceInvocationException) {
            // 服务调用失败
            handleServiceInvocationFailure(instance, node, (ServiceInvocationException) e);

        } else {
            // 未知异常
            instance.setStatus(ProcessStatus.ERROR);
            instance.setErrorMessage(e.getMessage());
            alertManager.sendAlert("流程执行异常: " + e.getMessage());
        }

        instanceRepository.update(instance);
    }

    /**
     * 处理服务调用失败
     */
    private void handleServiceInvocationFailure(ProcessInstance instance,
                                                  FlowNode node,
                                                  ServiceInvocationException e) {
        ServiceTask serviceTask = (ServiceTask) node;
        int maxRetries = 3;
        int retryCount = 0;

        while (retryCount < maxRetries) {
            try {
                Thread.sleep(1000L * (retryCount + 1)); // 递增等待
                processEngine.executeNode(instance, node);
                return;
            } catch (Exception retryError) {
                retryCount++;
                log.warn("Service task retry {}/{} failed for node {}",
                        retryCount, maxRetries, node.getId(), retryError);
            }
        }

        // 重试失败，将任务标记为异常
        instance.setStatus(ProcessStatus.ERROR);
        alertManager.sendAlert(String.format(
                "服务调用失败: node=%s, service=%s, error=%s",
                node.getId(), serviceTask.getServiceName(), e.getMessage()));
    }
}
```

```java
        if (e instanceof OutOfMemoryError || e instanceof StackOverflowError) {
            ruleEngine.pauseRuleSet(ruleSetId);
            alertManager.sendCriticalAlert(String.format(
                    "规则引擎严重错误，已暂停规则集 %s: %s", ruleSetId, e.getMessage()));
        }
    }

    /**
     * 处理规则死循环
     */
    public void handleRuleLoop(String ruleSetId, String ruleName) {
        log.error("Rule loop detected: ruleSet={}, rule={}", ruleSetId, ruleName);

        // 建议设置 no-loop true 属性防止规则循环执行
        alertManager.sendAlert(String.format(
                "规则死循环检测: ruleSet=%s, rule=%s, 建议添加 no-loop true 属性",
                ruleSetId, ruleName));
    }
}
```

### 4.3 回调接口幂等处理

```java
/**
 * 回调接口幂等处理器
 * 工作流引擎的主动触发类接口基于分布式事务消息实现
 * 只保证数据不丢，无法保证数据不重复，需要业务系统进行幂等性处理
 */
public class CallbackIdempotencyHandler {

    private final Cache<String, Boolean> processedCache;

    /**
     * 幂等处理
     */
    public void handleCallback(String callbackId, Runnable callbackAction) {
        // 1. 检查是否已处理过
        if (processedCache.getIfPresent(callbackId) != null) {
            log.warn("Callback {} already processed, skipping", callbackId);
            return;
        }

        // 2. 执行回调
        try {
            callbackAction.run();
            // 3. 标记为已处理
            processedCache.put(callbackId, true);
        } catch (Exception e) {
            log.error("Callback {} failed, will be retried", callbackId, e);
            // 失败时不标记为已处理，允许重试
            throw e;
        }
    }
}
```

```java
public class RuleEngineOptimization {

    /**
     * 优化一：KieSession池化
     * 避免每次执行规则都创建新的KieSession

    public class KieSessionPool {
        private final Queue<KieSession> pool = new ConcurrentLinkedQueue<>();
        private final KieContainer kieContainer;
        private final int maxSize = 50;

            KieSession session = pool.poll();
            if (session == null) {
                session = kieContainer.newKieSession();
            }
            return session;

            if (pool.size() < maxSize) {

            } else {
                session.dispose();
            }
        }
    }
```

### 5.3 DAG并行执行优化

```java
/**
 * DAG并行执行优化
 */
public class DAGParallelOptimizer {

    private final ForkJoinPool forkJoinPool;

    /**
     * 最大化并行度：识别可并行执行的节点组
     */
    public List<List<String>> identifyParallelGroups(DAGWorkflow workflow) {
        // 使用Kahn算法进行拓扑排序，同一层级的节点可以并行执行
        Map<String, Integer> inDegree = calculateInDegrees(workflow);
        List<List<String>> levels = new ArrayList<>();

        Queue<String> queue = new LinkedList<>();
        for (Map.Entry<String, Integer> entry : inDegree.entrySet()) {
            if (entry.getValue() == 0) {
                queue.offer(entry.getKey());
            }
        }

        while (!queue.isEmpty()) {
            List<String> currentLevel = new ArrayList<>();
            int size = queue.size();
            for (int i = 0; i < size; i++) {
                String node = queue.poll();
                currentLevel.add(node);
                for (String successor : workflow.getSuccessors(node)) {
                    inDegree.put(successor, inDegree.get(successor) - 1);
                    if (inDegree.get(successor) == 0) {
                        queue.offer(successor);
                    }
                }
            }
            levels.add(currentLevel);
        }

        return levels;
    }

    /**
     * 并行执行同一层级的节点
     */
    public void executeLevel(List<String> nodeIds, WorkflowContext context) {
        List<CompletableFuture<NodeResult>> futures = nodeIds.stream()
                .map(nodeId -> CompletableFuture.supplyAsync(
                        () -> executeNode(nodeId, context), forkJoinPool))
                .collect(Collectors.toList());

        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
    }
}
```

## 六、最佳实践

### 6.1 工作流引擎最佳实践

1. **不要滥用多任务实例**：多任务实例是为了解决审批流中加签、会签、或签等复杂场景。如果业务场景固定且参与审批的角色确定，可以通过网关实现加签和会签，或签可通过任务候选人方式实现。

2. **不要滥用并行网关**：并行网关一般需要有开有闭，不要使用只有奇数个并行网关的流程图，这是BPMN的规范。

3. **不要设计无限循环的流程**：防止流程任务实例无限膨胀。如果一个流程的任务实例超过2000个，该流程实例将不能被查询接口查询到，完成时将造成大量数据的删除操作而产生大事务，可能造成数据库表不可用。

4. **保存业务数据与流程实例的关联关系**：将业务数据唯一键与流程实例唯一键的关联关系保存在业务系统中，大大减少对工作流引擎查询接口的依赖，提升流程流转效率和稳定性。

5. **对回调接口做幂等性处理**：工作流引擎的主动触发类接口基于分布式事务消息实现，只保证数据不丢不保证不重复。同时引擎自身也存在错误重试逻辑，可能导致重复调用。

6. **区分操作型接口和非法操作**：对操作型接口设计重试机制；对非法操作（如流程已结束后再修改变量、已完成任务再次完成）需要捕获特殊异常并阻止重试。

7. **动态表单 vs 业务自建UI**：对于只包含审批意见、通过/驳回的简单表单，使用动态表单；对于存在联动关系或复杂的表单场景，建议业务自建UI。

8. **不适合高并发场景**：工作流引擎属于重量级系统，不适合于业务流程简单明确且变化很少的场景，也不适合于高并发场景。

### 6.2 规则引擎最佳实践

1. **规则与代码分离**：将业务规则从应用程序代码中分离出来，存储在规则库中，实现业务规则的集中管理。

2. **使用规则属性控制执行**：
   - `salience`：设置规则优先级，数值越大优先级越高
   - `no-loop`：防止规则修改数据后触发自身循环执行
   - `activation-group`：同组规则只执行一个，用于互斥规则

3. **规则动态加载**：支持运行时添加、修改、删除规则，无需重启服务。同时提供版本管理和回滚能力。

4. **规则预编译**：在服务启动时预编译所有规则，避免运行时编译开销。

5. **规则集分区**：将规则按业务场景分区，避免无关规则的匹配开销。

6. **KieSession池化**：避免每次执行规则都创建新的KieSession，使用对象池复用。

7. **规则合法性校验**：添加规则前进行编译测试，确保规则语法正确。

### 6.3 DAG工作流最佳实践

1. **确定性优先**：能用脚本写死的绝不交给AI。确定性节点（拉分支、跑测试、创建PR）用脚本执行，智能节点（需求理解、代码编写）才使用AI。

2. **Checkpoint体系**：在对的地方让人决策。强制确认（需求理解、技术方案）不可跳过；产出物确认（PR、测试用例）可基于用户画像自动通过。

3. **应急预案引擎**：当流水线在某个阶段卡住时，自动触发应急预案而非报错退出。设置Budget硬限制（全局最多5次重试、单阶段最多2次），防止无限循环。

4. **自适应路由**：根据任务画像动态裁剪执行路径，支持条件跳过、快速路径、动态并行、经验驱动四种模式。

5. **工作流记忆**：通过通用记忆中间件让多个Agent共享经验索引。每个Agent完成任务后自动沉淀经验，进入类似场景时自动注入相关经验到上下文。

6. **插件机制**：提供多级插件配置系统，支持Strategy替换和Hook扩展，按"系统默认 → 团队 → 用户 → 项目 → CLI参数"五级逐层覆盖。

7. **接口契约传递**：跨仓库编码时，当上游仓库的接口签名确定后，下游仓库即可启动编码，无需等待上游完全完成，实现并行开发。

## 七、实战应用案例

前面的章节主要从理论和架构角度讲解了工作流引擎和规则引擎的设计原理。但很多开发者可能会问：**这些东西到底能应用在哪里？** 本章将通过多个真实业务场景，详细、不跳步地展示工作流引擎和规则引擎在实际业务中是如何发挥作用的。所有案例均基于真实业务实践，但不涉及具体公司名称和产品名称。

### 7.1 工作流引擎应用案例

#### 案例一：配送申诉审批平台

**业务背景**

某配送平台的骑手每天都会产生大量申诉：超时罚款申诉、差评申诉、异常订单申诉等。这些申诉需要经过多级审核——先是站点管理员初审，再是城市经理复审，金额较大的还需要区域总监终审。不同类型的申诉走的审批链路不同，而且审批规则经常调整（比如某个月临时调整了金额阈值，或者新增了一种申诉类型）。

**传统方式的痛点**

在引入工作流引擎之前，这个申诉审批系统是这样实现的：开发人员把审批流程的每一步都写死在代码里——用 if-else 判断申诉类型，用 switch-case 控制流转到哪个审批人，金额阈值用常量定义。每次业务方说"我们要调整审批链路"或者"新增一种申诉类型"，开发就要改代码、测试、发布上线，周期长、成本高，而且容易出错。更麻烦的是，不同城市的审批流程还有差异，代码里的条件分支越堆越多，最终变成了一个谁也不敢碰的"大泥球"。

**基于工作流引擎的解决方案**

引入工作流引擎后，整个申诉审批流程被抽象成 BPMN 2.0 流程定义。下面是完整的流程设计：

```
┌─────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌─────────┐
│  开始    │────→│  骑手提交     │────→│  系统初审     │────→│  排他网关     │────→│  结束    │
│  事件    │     │  申诉单       │     │ (服务任务)    │     │ (金额判断)    │     │  事件    │
└─────────┘     └──────────────┘     └──────────────┘     └──────┬───────┘     └─────────┘
                                                              │
                                              ┌───────────────┼───────────────┐
                                              ↓               ↓               ↓
                                     ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
                                     │ 站点管理员    │ │ 城市经理      │ │ 区域总监      │
                                     │ 人工审批      │ │ 人工审批      │ │ 人工审批      │
                                     │ (用户任务)    │ │ (用户任务)    │ │ (用户任务)    │
                                     └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
                                            │                │                │
                                            └───────────────┬┘───────────────┘
                                                          ↓
                                                   ┌──────────────┐
                                                   │  审批结果     │
                                                   │  回调通知     │
                                                   │ (服务任务)    │
                                                   └──────┬───────┘
                                                          ↓
                                                   ┌──────────────┐
                                                   │  结束事件     │
                                                   └──────────────┘
```

**关键设计细节**

第一步：流程定义。在流程设计器中拖拽出上述流程图，每个节点配置属性。骑手提交申诉单是一个开始事件，后面紧跟一个服务任务节点（系统初审），该节点通过 Thrift 接口调用风控系统，自动检查申诉是否涉及恶意行为。系统初审的结果写入流程变量 `autoCheckResult`。

第二步：排他网关配置。排他网关读取流程变量 `appealAmount`（申诉金额），根据条件表达式决定走哪条分支：

```xml
<!-- 金额 ≤ 50元：站点管理员审批 -->
<sequenceFlow sourceRef="gateway" targetRef="siteManagerTask">
    <conditionExpression>${appealAmount <= 50}</conditionExpression>
</sequenceFlow>

<!-- 50元 < 金额 ≤ 500元：城市经理审批 -->
<sequenceFlow sourceRef="gateway" targetRef="cityManagerTask">
    <conditionExpression>${appealAmount > 50 && appealAmount <= 500}</conditionExpression>
</sequenceFlow>

<!-- 金额 > 500元：区域总监审批 -->
<sequenceFlow sourceRef="gateway" targetRef="regionalDirectorTask">
    <conditionExpression>${appealAmount > 500}</conditionExpression>
</sequenceFlow>
```

第三步：任务自动分配。每个用户任务节点开启任务自动分配开关，配置工作组。比如站点管理员审批节点配置的工作组是"站点管理员组"，引擎会从该工作组中选择当前任务量最少的成员进行分配，同时根据工作时段过滤（只分配当前在线的管理员）。这样避免了某个管理员任务堆积而其他人空闲的情况。

第四步：事件回调。在审批完成后，"审批结果回调通知"这个服务任务节点通过 HTTP 接口回调业务系统，将审批结果（通过/驳回/需要补充材料）推送到申诉系统。业务系统不需要轮询工作流引擎的状态，而是被动等待回调即可。

第五步：动态表单。每个审批节点绑定一个动态表单，表单中展示申诉详情（骑手姓名、订单号、申诉类型、申诉理由、附件图片等），并提供"通过""驳回""转交"等操作按钮。这样业务方无需投入前端开发人力，直接在工作流引擎的 Web 管理平台上就能完成表单设计和审批页面展示。

**实际效果**

当业务方需要调整审批流程时——比如"新增一种申诉类型，金额阈值从 50 元调整到 100 元"——只需要在流程设计器中修改流程定义并重新部署，无需修改任何代码。整个调整过程从原来的"开发-测试-上线"一周周期，缩短到业务人员在 Web 界面上操作 10 分钟即可完成。

#### 案例二：供应链审批任务协同

**业务背景**

某供应链平台涉及采购、库存、财务、物流等多个子系统。当一笔采购订单发起后，需要经过多个环节的协同：采购系统创建订单→财务系统审核预算→物流系统确认配送→仓储系统确认入库。每个环节都涉及不同系统的不同角色，且环节之间存在依赖关系（财务审核通过后才能进入物流确认）。

**传统方式的痛点**

各系统各自维护自己的状态流转逻辑，系统间通过消息队列或 HTTP 接口通知对方。问题在于：流程状态分散在多个系统中，没有统一的流程视图；某个环节卡住了，很难快速定位问题出在哪个系统；流程变更需要多个系统协同修改，联调成本极高。

**基于工作流引擎的解决方案**

将整个采购订单流程统一编排到工作流引擎中，各系统通过服务任务节点接入：

```
开始 → 创建采购订单(采购系统) → 预算审核(财务系统) → 排他网关(预算是否充足)
                                        ↓
                              ┌─────────┴─────────┐
                              ↓                   ↓
                        预算通过               预算不足
                        物流确认配送            退回采购修改
                        (物流系统)             (采购系统)
                              ↓
                        仓储确认入库
                        (仓储系统)
                              ↓
                        并行网关
                        ┌─────┴─────┐
                        ↓           ↓
                  通知采购方     通知财务付款
                  (MQ消息)      (财务系统)
                        └─────┬─────┘
                              ↓
                            结束
```

**关键设计细节**

采购系统通过 Thrift 接口调用工作流引擎创建流程实例，传入订单信息作为流程变量。流程引擎按照定义的流程图自动驱动流程前进：当流程流转到"预算审核"节点时，引擎通过事件回调通知财务系统进行审核；财务系统审核完成后，调用引擎的"完成任务"接口，传入审核结果；引擎根据结果走排他网关，决定是继续流转还是退回。

并行网关的使用是这个案例的一个亮点。当仓储确认入库后，流程需要同时做两件事：通知采购方订单已完成、通知财务系统发起付款。这两个操作互不依赖，使用并行网关让它们同时执行，而不是串行等待。这大大缩短了整个流程的完成时间。

**实际效果**

引入工作流引擎后，整个采购流程的状态流转由引擎统一管理。业务方可以在引擎的 Web 管理平台上看到每个流程实例的当前状态、历史轨迹和积压情况。当某个环节超时未处理时，引擎自动触发超时提醒。流程变更时，只需要修改流程定义并重新部署，各系统无需改动代码（因为各系统只是通过回调接口接收事件通知，不关心流程的具体走向）。

#### 案例三：品牌流水返佣审批流

**业务背景**

某平台针对中大型连锁品牌提供费率优惠政策，将费率优惠部分以返佣形式打给品牌方。整个返佣流程非常复杂：创建返佣规则→存储流水→出账→调账→发起结算→发起付款。其中调账环节需要人工审批，结算单可以配置人工审核开关，付款成功或失败都需要回调并记录操作日志，同时还要将资金变化事件同步至财务核算系统（传账）。

**传统方式的痛点**

这个流程涉及返佣系统、财务核算系统、付款系统三个系统的协作，且流程中有多个需要人工审批的节点。传统方式下，每个审批节点都要单独开发审批页面、审批逻辑、状态管理代码，而且流程中任何一个环节出错（比如付款失败）都需要人工介入处理，缺乏统一的异常处理和重试机制。

**基于工作流引擎的解决方案**

将整个返佣流程编排为一条工作流，每个关键节点配置事件回调：

```
开始 → 创建返佣规则 → 系统出账(定时任务触发) → 排他网关(流水是否达标)
                                                        ↓
                                              ┌─────────┴─────────┐
                                              ↓                   ↓
                                        流水达标               流水不达标
                                        调账审批              流程终止
                                        (用户任务)
                                              ↓
                                        排他网关(审批结果)
                                              ↓
                                        ┌─────┴─────┐
                                        ↓           ↓
                                   审批通过     审批驳回
                                   生成结算单   通知提交人
                                   (服务任务)   (MQ消息)
                                        ↓
                                   排他网关(是否需人工审核)
                                        ↓
                                   ┌─────┴─────┐
                                   ↓           ↓
                              需人工审核    无需审核
                              (用户任务)    自动通过
                                   └─────┬─────┘
                                         ↓
                                   创建付款单(服务任务)
                                         ↓
                                   排他网关(付款结果)
                                         ↓
                                   ┌─────┴─────┐
                                   ↓           ↓
                              付款成功     付款失败
                              传账通知     触发重试
                              (服务任务)   (服务任务)
                                   └─────┬─────┘
                                         ↓
                                       结束
```

**关键设计细节**

这个案例中，最值得关注的几个设计点：

第一，调账审批流支持单条调账和批量调账。每次调账以上一次调账后的金额为基础（而非原始出账金额），这意味着调账是一个可叠加的操作。工作流引擎通过流程变量保存"当前调账后金额"，每次调账审批时传入"调账差额"，审批通过后更新流程变量。

第二，结算单的人工审核开关通过流程变量控制。创建结算单时，系统根据规则配置设置 `needManualReview` 变量，排他网关根据该变量决定是否走人工审核分支。开关开启时生成"待审核"状态，审核通过后转为"待结算"；开关关闭时直接生成"待结算"状态并自动创建付款单。

第三，传账逻辑通过服务任务节点实现。付款成功和付款失败（存在资金变化时）均会触发传账，传账的三个核心要素是：系统来源、业务类型代码和明细业务名称。服务任务节点通过 Thrift 接口调用财务核算系统，传入这三个要素完成会计分录。

第四，付款失败时的自动重试机制。当付款失败时，引擎不会直接结束流程，而是触发一个"重试"服务任务节点，该节点根据重试次数判断是否继续重试（最多 3 次）。超过重试次数后，流程转入"人工处理"用户任务节点，通知财务人员介入。

**实际效果**

整个返佣流程从原来的"散落在多个系统中的代码逻辑"变成了"一条可视化、可追踪的流程"。运营人员可以在引擎管理平台上看到每笔返佣的当前状态（出账中、调账审批中、结算审核中、付款中、已完成），历史操作轨迹一目了然。当付款失败时，系统自动重试而非直接报错，大幅减少了人工介入的频率。

#### 案例四：AI 驱动的研发交付工作流（DAG 工作流）

**业务背景**

在软件开发领域，一个需求从提出到交付需要经过多个环节：需求理解→技术方案设计→拉分支→编写代码→单元测试→创建 PR→代码审查→部署。传统模式下，开发者需要在这些环节之间手动切换，在七八个系统之间来回跳转。即使 AI 写代码再快，流程割裂的问题依然存在，整体效率提不上去。

**基于 DAG 工作流的解决方案**

将整个研发交付流程编排成一条 DAG 工作流，由 AI 主动推动执行，开发者只在关键决策点介入。工作流中混合了确定性节点（脚本执行，快速稳定）和智能节点（AI 执行，需要创造力）：

```
需求理解 → 技术方案设计 → 拉分支 → 代码编写 → 编译构建 → 单元测试 → 创建PR → 代码审查 → 部署
(AI节点)   (AI节点)       (脚本)   (AI节点)   (脚本)     (脚本)     (脚本)   (人工)     (脚本)
```

**关键设计细节**

第一步：自适应路由。系统在执行前根据任务画像（类型 x 复杂度 x 风险）动态裁剪执行路径。比如一个简单的文案修改，可以跳过技术方案设计环节直接进入编码；而一个涉及 18 个文件、1970 行代码的大改造，则需要完整走完所有环节。

第二步：Checkpoint 体系。强制确认点（需求理解、技术方案）不可跳过，AI 完成需求分析后必须等待开发者确认"理解是否正确"才能继续；技术方案也需要开发者审核通过后才能开始编码。产出物确认点（PR、测试用例）则可以基于用户画像自动通过——如果是资深开发者且改动范围可控，PR 可以自动合并。

第三步：应急预案引擎。当流水线在某个阶段卡住时（比如编译失败、测试不通过），系统自动触发应急预案而非报错退出。比如编译失败时，AI 会自动分析编译日志，定位错误原因，提供修复方案，在 Budget 限制内自动重试。Budget 硬限制为：全局最多 5 次重试、单阶段最多 2 次重试。

第四步：工作流记忆。通过通用记忆中间件让多个 Agent 共享经验索引。每个 Agent 完成任务后自动沉淀经验（比如"这个项目的数据库迁移脚本需要特殊处理"），进入类似场景时自动注入相关经验到上下文，避免重复踩坑。

**实际效果**

在一个真实案例中，某后端服务改造需求涉及 18 个文件、1970 行代码改动，包括新增 DAO 全套、定时任务和状态机扩展。传统模式需要 3.5 天完成，使用 DAG 工作流后缩短到 1.1 天，提效 68% 以上。AI 在编码前主动澄清了 6 个关键问题，技术方案一次通过零返工。开发者的角色从"逐行写代码"变成了"做三个关键决策"——需求理解对不对？技术方案行不行？最终代码要不要？

在另一个案例中，某客户端底层接入需求（将网络下载模块替换为自研网络库），开发者一次性交出需求描述和依赖列表，系统自动完成了从需求分析到提测单的全链路。开发者全程只做了三件事：确认编译修复方向、本机执行安装命令、处理 git push 关联工作项。

### 7.2 规则引擎应用案例

#### 案例五：风控系统的规则引擎实践

**业务背景**

某大型生活服务平台每天面临着各类欺诈、盗号、作弊、套现以及营销活动被恶意刷单、恶意抢占资源等风险。业务安全团队需要在用户请求中识别出"谁、在什么时间、通过什么方式、做了什么事"，并快速做出风控决策。

**传统方式的痛点**

在业务发展初期，风控逻辑通过硬编码方式部署在业务逻辑中。但随着业务从单一形态发展到涵盖餐饮、到店、外卖、金融、酒店、旅游等多个垂直领域，细分业务多达上百个，硬编码方式暴露出严重问题：策略分散无法管理、逻辑同业务强耦合、策略更新迭代受限于开发排期、对接成本高。每次新增一个业务或新出现一个风险场景，风控系统和业务系统都要重新对接联调。

**基于规则引擎的解决方案**

团队打造了自有规则引擎平台，采用因子-规则-决策-场景的四层模型：

```
┌──────────────────────────────────────────────────────────┐
│                     场景层 (Scenario)                      │
│   用户注册场景 | 商户入驻场景 | 下单场景 | 支付场景 | 提现场景 │
├──────────────────────────────────────────────────────────┤
│                     决策层 (Decision)                      │
│   通过 | 拒绝 | 人工审核 | 限流 | 验证码挑战 | 短信确认      │
├──────────────────────────────────────────────────────────┤
│                     规则层 (Rule)                          │
│   规则1: 同一设备24小时内注册>3次 → 拒绝                    │
│   规则2: 同一IP下单频率>10次/分钟 → 限流                   │
│   规则3: 账号异地登录+修改密码+提现 → 人工审核              │
│   规则4: 商户评分<3.0+投诉率>15%+月交易额骤降 → 人工审核   │
│   规则5: 新注册用户+大额优惠券+立即使用 → 验证码挑战       │
├──────────────────────────────────────────────────────────┤
│                     因子层 (Factor)                        │
│   设备指纹 | IP地址 | 注册时间 | 登录地点 | 交易金额 |       │
│   投诉率 | 评分 | 优惠券使用频率 | 提现频率 | ...           │
└──────────────────────────────────────────────────────────┘
```

**关键设计细节**

第一步：通用节点接入。规则引擎不与每个业务单独对接，而是在每个业务都会经过的通用节点接入——用户中心（注册、登录）、商户中心（入驻、信息变更）、订单中心（下单、取消）、收银台（支付、退款）。业务系统调用这些通用节点时，通用节点自动调用规则引擎，完成风控检查。这样任何新业务只要走通用节点就自动具备风控能力，接入成本几乎为零。

第二步：因子采集与计算。因子是规则判断的最小数据单元，分为基础因子（设备指纹、IP、时间等，直接从请求中提取）和计算因子（注册频率、投诉率等，需要实时或离线计算）。规则引擎维护一个因子库，支持因子的动态注册和热更新。比如新增一个"近30天平均交易额"的因子，只需要编写计算逻辑并注册到因子库，所有规则都可以立即使用该因子。

第三步：规则编写采用表达式引擎。规则不使用复杂的 DRL（Drools Rule Language），而是使用更简洁的表达式语法。例如：

```
// 规则1：同一设备24小时内注册超过3次
device_register_count_24h > 3 → 拒绝

// 规则2：账号异地登录且修改密码后立即提现
login_city != usual_city AND password_changed_within_1h AND withdraw_amount > 1000 → 人工审核

// 规则3：新商户评分低且投诉率高
merchant_age_days < 30 AND merchant_score < 3.0 AND complaint_rate > 0.15 → 人工审核
```

这种表达式语法比 DRL 更容易理解，业务人员经过简单培训就能编写和维护规则，不需要开发介入。

第四步：规则的优先级与互斥。同一场景下可能有多条规则同时命中。通过优先级机制，优先级高的规则先生效。比如"拒绝"类规则的优先级高于"限流"类，"限流"类高于"验证码挑战"类。同时支持规则互斥——如果"拒绝"规则已命中，其他规则不再执行。

第五步：规则版本管理与灰度发布。每次规则变更生成新版本，支持灰度发布——先对 5% 的流量生效，观察误伤率和命中率，确认无异常后逐步放大到全量。如果发现问题，可以一键回滚到上一个版本。

**实际效果**

规则引擎上线后，风控策略与业务逻辑完全解耦。策略人员可以在规则管理平台上自行编写、测试、发布规则，无需开发介入。新规则从"提需求→开发排期→编码→测试→上线"的一周周期，缩短到策略人员配置后即时生效。通用节点接入模式让新业务的风控覆盖从"逐个对接联调"变成"自动覆盖"。面对黑产产业链的快速升级，风控团队能够在分钟级别响应新出现的风险模式。

#### 案例六：促销满减活动配置

**业务背景**

某餐饮商家营销平台为商家提供多种促销能力，如整单折扣、整单满减、单品折扣、单品买赠等多达十余种不同类型的促销活动。以满减活动为例，商家可以配置"满30元减5元""满100元减20元"等规则。看似简单，但实际配置维度非常多：门槛可以是金额也可以是人数，优惠方式可以是满减也可以是每满减，适用商品可以是全部菜品也可以是指定菜品，优惠规则可以是单个也可以是多梯度递进，活动还可以设置限购次数。

**传统方式的痛点**

每种促销类型的计算逻辑都写死在代码中，满减是一种逻辑、每满减是另一种逻辑、多梯度又是另一种。新增一种促销类型需要开发新的计算模块；修改现有促销的某个维度（比如给满减增加"按人数门槛"）也需要改代码。更麻烦的是，促销活动之间还有同享互斥关系——满减活动和优惠券能不能同时使用？会员价和满减能不能叠加？这些互斥规则也散落在代码各处。

**基于规则引擎的解决方案**

将促销活动的配置和计算逻辑从代码中抽离，用规则引擎管理：

```
┌──────────────────────────────────────────────────────────┐
│                   促销规则配置界面                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  门槛设置：                                               │
│    ○ 按金额门槛（满 X 元）                                │
│    ○ 按人数门槛（满 N 人，仅拼单场景）                     │
│                                                          │
│  优惠方式：                                               │
│    ○ 满额减（满 X 元减 Y 元，减一次）                     │
│    ○ 每满额减（每满 X 元减 Y 元，可多次）                  │
│                                                          │
│  适用商品：                                               │
│    ○ 全部菜品参与                                         │
│    ○ 指定菜品参与                                         │
│    ○ 指定分类参与                                         │
│                                                          │
│  不适用商品：                                             │
│    ○ 排除特定菜品                                         │
│    ○ 排除特定分类                                         │
│                                                          │
│  优惠规则：                                               │
│    ○ 单个规则（满30减5）                                  │
│    ○ 多梯度规则（满30减5 / 满50减10 / 满100减25）         │
│    ○ 递进关系（低梯度不满足时是否回退）                    │
│                                                          │
│  活动限制：                                               │
│    ○ 不设限                                               │
│    ○ 每天限购 N 次                                        │
│    ○ 活动时间内限购 N 次                                  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**关键设计细节**

第一步：将配置项抽象为因子。每个配置项对应一个因子：`thresholdType`（门槛类型）、`thresholdValue`（门槛值）、`discountType`（优惠方式）、`discountValue`（优惠金额）、`applicableProducts`（适用商品列表）、`excludedProducts`（排除商品列表）、`ruleType`（规则类型：单/多梯度/递进）、`gradientRules`（梯度规则列表）、`purchaseLimit`（限购设置）。

第二步：规则计算逻辑。以"每满减多梯度"为例，完整的计算过程如下：

用户下单金额为 130 元，配置了每满减多梯度规则：每满 30 元减 5 元（第一梯度），每满 100 元减 20 元（第二梯度）。

计算过程：首先判断订单金额满足哪个梯度——130 元满足第二梯度（≥100），不满足则回退到第一梯度。在第二梯度下，每满 100 元减 20 元，130 元中有 1 个 100 元，所以减 20 元。如果配置了递进关系（低梯度不满足时回退），还需要检查是否同时满足第一梯度——130 元也满足第一梯度（≥30），每满 30 元减 5 元，130 元中有 4 个 30 元，减 20 元。最终根据互斥规则取最优优惠（第二梯度的 20 元 vs 第一梯度的 20 元，取相同值或取较大值）。

第三步：适用商品的过滤。订单中可能包含多个菜品，但只有"适用商品"参与门槛计算。比如商家配置"指定菜品参与"，订单中菜品 A（15 元，参与）、菜品 B（20 元，不参与）、菜品 C（10 元，参与），则门槛计算金额为 15+10=25 元。如果门槛是 30 元，则不满足。同时，"不适用商品"即使在"适用商品"范围内也要排除——比如配置了"全部菜品参与"但"排除特定菜品 D"，那么菜品 D 的金额不计入门槛。

第四步：活动限购的校验。在规则计算之前，先检查限购条件。通过用户 ID + 活动 ID 查询当日已享受次数和活动期内已享受次数，如果超过限制则直接跳过该促销规则。限购的粒度是"每卡"（每个会员卡），而非每个用户或每台设备。

**实际效果**

商家可以在营销平台上自行配置各种促销活动，配置完成后规则即时生效，无需开发介入。新增促销类型时，只需要在规则引擎中新增一套规则模板，不需要修改订单计算的核心代码。促销活动之间的同享互斥关系也由规则引擎统一管理，避免了一处修改影响全局的问题。

#### 案例七：优惠券同享互斥规则

**业务背景**

某平台的用户在下单时可能同时拥有多种优惠权益：商家自建的促销活动（满减、折扣、买赠）、平台发放的优惠券（满减券、折扣券、代金券）、会员权益（会员价、会员折扣）。这些优惠能不能同时享受？如果不能，应该优先使用哪个？这就是"同享互斥"问题。

**传统方式的痛点**

互斥规则散落在算价代码的各个角落，用 if-else 硬编码实现。比如"促销活动之间走默认逻辑""会员价与会员活动需要在会员卡配置""折扣券与其他会员优惠券之间有特殊互斥规则"。这些规则互相交织，修改一处可能引发连锁反应。而且新增一种优惠类型时，需要手动将其添加到互斥组中，时效性差，容易遗漏。

**基于规则引擎的解决方案**

将同享互斥规则统一抽取到规则引擎中，建立互斥组矩阵：

```
┌────────────┬─────────┬─────────┬─────────┬─────────┬─────────┐
│            │ 整单满减 │ 单品折扣 │ 优惠券   │ 会员价   │ 会员折扣 │
├────────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│ 整单满减    │  同享    │  互斥    │  同享    │  同享    │  互斥    │
├────────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│ 单品折扣    │  互斥    │  同享    │  同享    │  互斥    │  同享    │
├────────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│ 优惠券      │  同享    │  同享    │  互斥    │  同享    │  同享    │
├────────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│ 会员价      │  同享    │  互斥    │  同享    │  同享    │  互斥    │
├────────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│ 会员折扣    │  互斥    │  同享    │  同享    │  互斥    │  同享    │
└────────────┴─────────┴─────────┴─────────┴─────────┴─────────┘
```

**关键设计细节**

第一步：互斥组的动态管理。每种优惠类型注册到规则引擎时，自动加入互斥组矩阵。运营人员在管理界面上配置"同享"或"互斥"关系，规则即时生效。新增一种优惠类型时，只需要在矩阵中新增一行一列，配置与其他类型的互斥关系即可。

第二步：择优计算。当多种优惠互斥时，系统需要自动择优——计算每种优惠方案的最终价格，选择对用户最优的方案。比如用户同时拥有"满100减20"的促销活动和"打8折"的优惠券，两者互斥。订单金额 150 元：满减方案最终价格 130 元（150-20），优惠券方案最终价格 120 元（150×0.8）。系统自动选择优惠券方案。

第三步：跨品类、跨店的互斥规则。某些优惠券支持跨店使用（比如平台级优惠券），需要在与商家自建促销活动叠加时进行特殊处理。规则引擎通过场景上下文（`scenarioType: single_store / cross_store / cross_category`）区分不同场景，同一对优惠在不同场景下的互斥关系可以不同。

第四步：互斥规则的部分支持。系统支持配置部分优惠类型的同享互斥规则，而非全部。这意味着某些优惠类型之间的互斥关系可以由商家自行配置（比如商家决定自己的满减活动是否与平台优惠券同享），而某些关系是系统级的固定规则（比如同类型的促销活动之间默认互斥）。

**实际效果**

互斥规则从散落在代码各处的 if-else 变成了统一管理的一张矩阵表。运营人员在管理界面上修改互斥关系后即时生效，无需开发介入。新增优惠类型时自动加入互斥矩阵，不再需要手动添加到互斥组。择优计算确保用户始终获得最优价格，提升了用户体验。

#### 案例八：POS 机计费规则配置

**业务背景**

某支付平台为商户提供 POS 机服务，商户的费率不是固定的，而是根据交易行为动态调整。比如：某商户 POS 机单天消费累计达到 1000 元后，费率从标准费率 0.6% 降至 0.48%（打 8 折）；如果单月累计达到 50000 元，费率进一步降至 0.38%。这种阶梯式计费规则在传统方式下需要硬编码实现，且每次调整费率方案都需要修改代码。

**基于规则引擎的解决方案**

将计费规则抽象为规则引擎中的条件-动作模型：

```
规则1: 单天累计交易额 < 1000元
  → 费率 = 0.6%

规则2: 1000元 ≤ 单天累计交易额 < 50000元
  → 费率 = 0.48%

规则3: 单月累计交易额 ≥ 50000元
  → 费率 = 0.38%

规则4: 商户类型 = "公益类"（医院、学校等）
  → 费率 = 0%（直接覆盖以上规则）
```

**关键设计细节**

第一步：因子定义。定义 `dailyTransactionAmount`（单天累计交易额）、`monthlyTransactionAmount`（单月累计交易额）、`merchantType`（商户类型）三个因子。前两个因子通过实时累加计算获得（每笔交易完成后更新累计值），第三个因子从商户信息中直接读取。

第二步：规则优先级。规则 4（公益类商户零费率）的优先级最高，一旦命中直接输出结果，不再执行其他规则。规则 1-3 按金额范围互斥，同一时间只有一条规则命中。

第三步：规则的动态调整。当运营方需要调整费率方案时（比如将门槛从 1000 元调整为 800 元），只需要在规则管理界面修改规则的阈值参数，保存后即时生效。甚至可以配置时间窗口——"仅在周末享受折扣费率"，只需要在规则条件中增加时间因子的判断。

第四步：规则的组合与继承。某些商户可能同时满足多个费率优惠条件（比如既是公益类商户又达到了交易额门槛），规则引擎通过优先级和互斥机制确保最终只应用一个费率。运营人员也可以配置"取最低费率"的聚合策略，让多条规则的结果取最优值。

**实际效果**

计费规则从硬编码变为可配置，运营人员可以自行调整费率方案，无需开发介入。费率调整的响应时间从"提需求→开发排期→测试→上线"的一周周期缩短到分钟级别。新商户类型（如公益类）的费率优惠也可以快速配置上线，不再需要修改计费核心代码。

### 7.3 工作流引擎与规则引擎的协同应用

#### 案例九：商户入驻全流程

**业务背景**

某平台的商户入驻流程是一个典型的需要工作流引擎和规则引擎协同的场景。商户提交入驻申请后，系统需要：验证商户资质（规则引擎）→审核商户信息（人工审批，工作流引擎）→风控检查（规则引擎）→签订合同（工作流引擎驱动合同审批流）→开通账号和权限（工作流引擎的服务任务节点）→配置支付费率（规则引擎）→完成入驻通知（工作流引擎）。

**协同设计**

```
                    规则引擎负责                    工作流引擎负责
                    ──────────                    ────────────
开始 → 资质验证 ←──────规则1:营业执照有效期检查
                    规则2:经营范围合规检查
                    规则3:法人信用评分检查      → 人工审核(用户任务)
                                                     ↓
                风控检查 ←──规则4:法人黑名单检查
                    规则5:关联商户风险检查      → 排他网关(风控结果)
                                                     ↓
                                              ┌──────┴──────┐
                                              ↓             ↓
                                         风控通过       风控拒绝
                                         签订合同        流程终止
                                         (工作流)         ↓
                                              ↓          结束
                                         开通账号权限
                                         (服务任务)
                                              ↓
                费率配置 ←──规则6:商户类型→费率映射
                    规则7:交易额预估→费率档位      → 入驻完成通知
                                              ↓
                                            结束
```

在这个案例中，规则引擎负责"判断和决策"（资质是否合格、是否有风控风险、费率应该设多少），工作流引擎负责"流程驱动和状态管理"（驱动流程从资质验证到人工审核再到合同签订）。两者通过流程变量交互：规则引擎的计算结果写入流程变量，工作流引擎的排他网关读取流程变量决定流程走向。

这种协同模式的核心优势在于：规则变更（比如调整商户信用评分的阈值）和流程变更（比如在风控检查后新增一个"线下尽调"环节）可以独立进行，互不影响。规则引擎专注业务决策逻辑，工作流引擎专注流程编排逻辑，各司其职。

### 7.4 小结

通过以上九个案例，我们可以总结出工作流引擎和规则引擎在实际业务中的核心价值：

工作流引擎解决的是"流程"问题——将复杂的、多步骤的、跨系统的业务流程从代码中抽离出来，变成可视化、可配置、可追踪的流程定义。当流程需要变更时，业务人员或开发人员只需在流程设计器中修改流程图并重新部署，无需修改业务代码。这大幅降低了流程变更的成本和风险，同时提供了完整的流程可视化和监控能力。

规则引擎解决的是"决策"问题——将复杂的、频繁变化的、多条件的业务规则从代码中抽离出来，变成可配置、可测试、可灰度发布的规则集。当规则需要变更时，策略人员只需在规则管理界面修改规则并发布，无需开发介入。这使得业务规则能够快速响应市场变化和风险升级。

两者的协同——工作流引擎负责"怎么走"（流程编排），规则引擎负责"走不走"（业务决策）——构成了一套完整的业务流程管理基础设施。在实际业务中，几乎所有涉及多步骤审批、跨系统协作的场景都能受益于工作流引擎，几乎所有涉及复杂条件判断、频繁规则变更的场景都能受益于规则引擎。

## 八、全链路实战案例

前一章的案例侧重于"为什么用"和"怎么设计"，本章聚焦于"代码怎么写"。以下三个案例分别覆盖工作流引擎、规则引擎、异常处理三条核心链路，每个案例都包含完整的 Java 代码实现，并内建异常处理、日志追踪和幂等控制机制，可以直接作为项目脚手架参考。

### 8.1 案例一：工作流任务执行全链路

**业务背景**

以报销审批流程为例，完整链路为：员工发起报销（启动流程实例）→ 系统自动校验发票（自动节点执行）→ 根据金额分配审批人（人工任务分配）→ 审批人审批（审批/完成）→ 根据审批结果流转到出纳付款或退回（流程流转）→ 流程结束（结束）。

**全链路代码实现**

```java
/**
 * 报销审批全链路服务
 * 覆盖：启动流程 → 自动节点 → 人工任务分配 → 审批完成 → 流程流转 → 结束
 */
@Service
@Slf4j
public class ExpenseWorkflowService {

    @Resource
    private ProcessEngine processEngine;
    @Resource
    private TaskService taskService;
    @Resource
    private ProcessInstanceRepository instanceRepository;
    @Resource
    private InvoiceValidationService invoiceValidationService;
    @Resource
    private TaskSchedulingService taskSchedulingService;
    @Resource
    private PaymentService paymentService;
    @Resource
    private RedisTemplate<String, String> redisTemplate;

    private static final String IDEMPOTENT_PREFIX = "wf:expense:start:";
    private static final int IDEMPOTENT_TTL_SECONDS = 86400;

    // ==================== 第一步：启动流程实例 ====================

    /**
     * 发起报销审批流程
     *
     * @param request 报销请求
     * @return 流程实例ID
     */
    @Transactional(rollbackFor = Exception.class)
    public String startExpenseProcess(ExpenseRequest request) {
        // -------- 幂等控制：基于业务唯一键防止重复发起 --------
        String idempotentKey = IDEMPOTENT_PREFIX + request.getRequestId();
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(idempotentKey, "1", IDEMPOTENT_TTL_SECONDS, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(firstTime)) {
            log.warn("重复发起报销流程, requestId={}, 直接返回已存在的实例", request.getRequestId());
            // 查询已有实例并返回
            ProcessInstance existing = instanceRepository.findByBusinessKey(request.getRequestId());
            if (existing != null) {
                return existing.getId();
            }
            throw new WorkflowException("幂等校验通过但未找到已有实例, requestId=" + request.getRequestId());
        }

        log.info("开始启动报销流程, requestId={}, applicant={}, amount={}",
                request.getRequestId(), request.getApplicant(), request.getAmount());

        try {
            // 构造流程变量
            Map<String, Object> variables = new HashMap<>();
            variables.put("requestId", request.getRequestId());
            variables.put("applicant", request.getApplicant());
            variables.put("amount", request.getAmount());
            variables.put("expenseType", request.getExpenseType());
            variables.put("invoiceUrls", request.getInvoiceUrls());
            variables.put("department", request.getDepartment());

            // 启动流程实例（流程定义ID: expense_approval_v1）
            ProcessInstance instance = processEngine.startProcess(
                    "expense_approval_v1", variables);

            log.info("报销流程启动成功, instanceId={}, requestId={}",
                    instance.getId(), request.getRequestId());

            // 保存业务键与流程实例的关联关系（性能优化：减少后续查询依赖）
            instanceRepository.saveBusinessKeyAssociation(
                    request.getRequestId(), instance.getId());

            return instance.getId();

        } catch (ProcessDefinitionNotFoundException e) {
            log.error("流程定义不存在: expense_approval_v1", e);
            redisTemplate.delete(idempotentKey); // 回滚幂等标记，允许重试
            throw new WorkflowException("流程定义不存在，请联系管理员", e);

        } catch (Exception e) {
            log.error("启动报销流程失败, requestId={}", request.getRequestId(), e);
            redisTemplate.delete(idempotentKey); // 回滚幂等标记，允许重试
            throw new WorkflowException("启动流程失败: " + e.getMessage(), e);
        }
    }

    // ==================== 第二步：自动节点执行（发票校验） ====================

    /**
     * 自动节点：发票校验服务任务
     * 由流程引擎在 SERVICE_TASK 节点自动回调
     *
     * @param context 流程执行上下文
     * @return 校验结果
     */
    public InvoiceValidationResult executeInvoiceValidation(ExecutionContext context) {
        String instanceId = context.getProcessInstanceId();
        log.info("[自动节点] 开始执行发票校验, instanceId={}", instanceId);

        try {
            // 从流程变量中获取发票信息
            @SuppressWarnings("unchecked")
            List<String> invoiceUrls = (List<String>) context.getVariable("invoiceUrls");
            BigDecimal amount = (BigDecimal) context.getVariable("amount");

            if (invoiceUrls == null || invoiceUrls.isEmpty()) {
                log.warn("[自动节点] 发票列表为空, instanceId={}", instanceId);
                return InvoiceValidationResult.fail("发票不能为空");
            }

            // 调用发票校验服务（含OCR识别 + 真伪验证）
            InvoiceValidationResult result = invoiceValidationService.validate(invoiceUrls, amount);

            if (result.isPassed()) {
                log.info("[自动节点] 发票校验通过, instanceId={}, invoiceCount={}",
                        instanceId, invoiceUrls.size());
                // 将校验结果写入流程变量，供后续网关判断
                context.setVariable("invoiceValid", true);
                context.setVariable("validatedAmount", result.getValidatedAmount());
            } else {
                log.warn("[自动节点] 发票校验未通过, instanceId={}, reason={}",
                        instanceId, result.getReason());
                context.setVariable("invoiceValid", false);
                context.setVariable("rejectReason", result.getReason());
            }

            return result;

        } catch (Exception e) {
            log.error("[自动节点] 发票校验异常, instanceId={}", instanceId, e);
            // 自动节点异常时，标记为需人工介入，而非直接终止流程
            context.setVariable("invoiceValid", false);
            context.setVariable("rejectReason", "发票校验服务异常，需人工介入");
            context.setVariable("needManualInvoiceCheck", true);
            return InvoiceValidationResult.fail("校验服务异常");
        }
    }

    // ==================== 第三步：人工任务分配 ====================

    /**
     * 根据报销金额自动分配审批人
     * 由流程引擎在 USER_TASK 节点通过任务调度规则触发
     *
     * @param task 待分配的任务
     */
    public void assignApprovalTask(Task task) {
        String instanceId = task.getProcessInstanceId();
        log.info("[任务分配] 开始分配审批任务, taskId={}, instanceId={}",
                task.getId(), instanceId);

        try {
            ProcessInstance instance = instanceRepository.get(instanceId);
            BigDecimal amount = (BigDecimal) instance.getVariables().get("amount");
            String department = (String) instance.getVariables().get("department");

            // 根据金额决定审批层级
            String schedulingRule;
            if (amount.compareTo(new BigDecimal("1000")) <= 0) {
                // 金额 <= 1000：组长审批
                schedulingRule = "ROLE:TEAM_LEADER:" + department;
                log.info("[任务分配] 金额={}, 分配给组长审批, instanceId={}", amount, instanceId);
            } else if (amount.compareTo(new BigDecimal("10000")) <= 0) {
                // 1000 < 金额 <= 10000：部门经理审批
                schedulingRule = "ROLE:DEPT_MANAGER:" + department;
                log.info("[任务分配] 金额={}, 分配给部门经理审批, instanceId={}", amount, instanceId);
            } else {
                // 金额 > 10000：部门经理 + 财务总监会签
                schedulingRule = "ROLE:DEPT_MANAGER+FINANCE_DIRECTOR:" + department;
                log.info("[任务分配] 金额={}, 分配给部门经理+财务总监会签, instanceId={}",
                        amount, instanceId);
            }

            // 委托任务调度服务执行分配
            taskSchedulingService.assignTaskByRule(task, schedulingRule);

        } catch (Exception e) {
            log.error("[任务分配] 任务分配异常, taskId={}", task.getId(), e);
            // 分配失败时，设置默认审批人（兜底策略），避免任务无人处理
            task.setAssignee("admin_fallback");
            taskService.updateTask(task);
            log.warn("[任务分配] 已设置兜底审批人 admin_fallback, taskId={}", task.getId());
        }
    }

    // ==================== 第四步：审批/完成任务 ====================

    /**
     * 审批人完成审批任务
     *
     * @param request 审批请求
     */
    @Transactional(rollbackFor = Exception.class)
    public void completeApprovalTask(ApprovalRequest request) {
        log.info("[审批完成] 开始处理审批, taskId={}, approver={}, action={}",
                request.getTaskId(), request.getApprover(), request.getAction());

        // -------- 幂等控制：防止重复提交审批 --------
        String completeIdempotentKey = "wf:expense:complete:" + request.getTaskId();
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(completeIdempotentKey, request.getApprover(),
                        3600, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(firstTime)) {
            log.warn("[审批完成] 重复提交审批, taskId={}, 已跳过", request.getTaskId());
            return;
        }

        try {
            // 1. 获取任务并校验状态
            Task task = taskService.getTask(request.getTaskId());
            if (task == null) {
                throw new TaskNotFoundException("任务不存在: " + request.getTaskId());
            }
            if (task.getStatus() != TaskStatus.PENDING) {
                log.warn("[审批完成] 任务已完成或已取消, taskId={}, status={}",
                        request.getTaskId(), task.getStatus());
                redisTemplate.delete(completeIdempotentKey);
                return;
            }

            // 2. 校验审批人权限
            if (!isAuthorizedApprover(task, request.getApprover())) {
                throw new UnauthorizedException(
                        "无权审批此任务, taskId=" + request.getTaskId()
                                + ", approver=" + request.getApprover());
            }

            // 3. 构造任务变量
            Map<String, Object> taskVariables = new HashMap<>();
            taskVariables.put("approvalAction", request.getAction().name()); // APPROVE / REJECT
            taskVariables.put("approvalComment", request.getComment());
            taskVariables.put("approver", request.getApprover());
            taskVariables.put("approvalTime", new Date());

            // 4. 构造流程变量（供后续排他网关判断）
            Map<String, Object> processVariables = new HashMap<>();
            processVariables.put("approved",
                    request.getAction() == ApprovalAction.APPROVE);

            // 5. 完成任务，引擎自动流转到下一节点
            processEngine.completeTask(
                    request.getTaskId(), taskVariables, processVariables);

            log.info("[审批完成] 审批完成, taskId={}, action={}, instanceId={}",
                    request.getTaskId(), request.getAction(), task.getProcessInstanceId());

        } catch (TaskNotFoundException | UnauthorizedException e) {
            log.error("[审批完成] 业务校验失败, taskId={}", request.getTaskId(), e);
            redisTemplate.delete(completeIdempotentKey); // 回滚幂等标记
            throw e;

        } catch (TaskAlreadyCompletedException e) {
            log.warn("[审批完成] 任务已被完成（并发操作），忽略, taskId={}", request.getTaskId());
            // 幂等：不回滚、不抛异常，静默处理
            return;

        } catch (Exception e) {
            log.error("[审批完成] 审批处理异常, taskId={}", request.getTaskId(), e);
            redisTemplate.delete(completeIdempotentKey); // 回滚幂等标记
            throw new WorkflowException("审批处理失败: " + e.getMessage(), e);
        }
    }

    // ==================== 第五步：流程流转（排他网关 -> 出纳付款/退回） ====================

    /**
     * 出纳付款服务任务（审批通过后自动触发）
     *
     * @param context 流程执行上下文
     */
    public PaymentResult executePayment(ExecutionContext context) {
        String instanceId = context.getProcessInstanceId();
        log.info("[流程流转] 开始执行付款, instanceId={}", instanceId);

        try {
            String requestId = (String) context.getVariable("requestId");
            BigDecimal amount = (BigDecimal) context.getVariable("validatedAmount");
            String applicant = (String) context.getVariable("applicant");

            // -------- 幂等控制：防止重复付款 --------
            String paymentIdempotentKey = "wf:expense:payment:" + requestId;
            Boolean firstTime = redisTemplate.opsForValue()
                    .setIfAbsent(paymentIdempotentKey, "processing", 3600, TimeUnit.SECONDS);
            if (Boolean.FALSE.equals(firstTime)) {
                log.warn("[流程流转] 重复付款请求, requestId={}, 跳过", requestId);
                // 查询已有付款结果
                PaymentResult existing = paymentService.queryByBusinessKey(requestId);
                if (existing != null) {
                    return existing;
                }
                throw new WorkflowException("付款正在处理中，请勿重复提交");
            }

            // 执行付款
            PaymentResult result = paymentService.pay(PaymentRequest.builder()
                    .businessKey(requestId)
                    .payee(applicant)
                    .amount(amount)
                    .type("EXPENSE_REIMBURSEMENT")
                    .build());

            if (result.isSuccess()) {
                log.info("[流程流转] 付款成功, instanceId={}, paymentId={}, amount={}",
                        instanceId, result.getPaymentId(), amount);
                context.setVariable("paymentId", result.getPaymentId());
                context.setVariable("paymentStatus", "SUCCESS");
            } else {
                log.error("[流程流转] 付款失败, instanceId={}, reason={}",
                        instanceId, result.getReason());
                context.setVariable("paymentStatus", "FAILED");
                context.setVariable("paymentFailReason", result.getReason());
                redisTemplate.delete(paymentIdempotentKey); // 允许重试
            }

            return result;

        } catch (Exception e) {
            log.error("[流程流转] 付款服务异常, instanceId={}", instanceId, e);
            context.setVariable("paymentStatus", "ERROR");
            throw new WorkflowException("付款执行失败: " + e.getMessage(), e);
        }
    }

    // ==================== 第六步：流程结束 ====================

    /**
     * 流程结束回调（END_EVENT 触发）
     *
     * @param context 流程执行上下文
     */
    public void onProcessComplete(ExecutionContext context) {
        String instanceId = context.getProcessInstanceId();
        String requestId = (String) context.getVariable("requestId");
        Boolean approved = (Boolean) context.getVariable("approved");
        String paymentStatus = (String) context.getVariable("paymentStatus");

        log.info("[流程结束] 报销流程结束, instanceId={}, requestId={}, approved={}, paymentStatus={}",
                instanceId, requestId, approved, paymentStatus);

        // 发送通知给申请人
        String applicant = (String) context.getVariable("applicant");
        if (Boolean.TRUE.equals(approved) && "SUCCESS".equals(paymentStatus)) {
            notificationService.notify(applicant,
                    "您的报销申请已审批通过并完成付款， requestId=" + requestId);
        } else if (Boolean.FALSE.equals(approved)) {
            notificationService.notify(applicant,
                    "您的报销申请已被驳回， requestId=" + requestId);
        } else {
            notificationService.notify(applicant,
                    "您的报销流程已结束但付款异常，请联系财务， requestId=" + requestId);
        }

        // 清理流程相关临时缓存
        redisTemplate.delete(IDEMPOTENT_PREFIX + requestId);
    }

    // ==================== 辅助方法 ====================

    private boolean isAuthorizedApprover(Task task, String approver) {
        if (task.getAssignee() != null && task.getAssignee().equals(approver)) {
            return true;
        }
        if (task.getCandidateUsers() != null && task.getCandidateUsers().contains(approver)) {
            return true;
        }
        return false;
    }
}
```

**关键设计要点**

- **幂等控制三道防线**：发起流程用业务唯一键 + Redis SETNX；完成任务用 taskId + Redis SETNX；付款用 requestId + Redis SETNX。任何一道防线的幂等标记在操作失败时都会被清除以允许重试，在操作成功时保留以防止重复。
- **异常处理分级**：业务校验异常（TaskNotFound、Unauthorized）直接抛出给调用方；并发冲突异常（TaskAlreadyCompleted）静默处理保证幂等；系统异常包装为 WorkflowException 统一抛出。
- **自动节点兜底策略**：发票校验服务异常时不直接终止流程，而是标记 `needManualInvoiceCheck=true`，让人工介入处理，保证流程不中断。
- **任务分配兜底**：当调度规则分配失败时，设置兜底审批人 `admin_fallback`，避免任务无人认领导致流程卡死。

### 8.2 案例二：规则引擎动态决策全链路

**业务背景**

以电商订单风控场景为例，完整链路为：用户下单（业务请求）→ 规则引擎加载风控规则集（规则匹配）→ 评估用户信用 + 设备指纹 + 行为特征多个维度（多条件组合评估）→ 输出风控决策（通过/拦截/人审）（决策输出）→ 将决策结果缓存供后续查询（结果缓存）。

**全链路代码实现**

```java
/**
 * 订单风控规则决策全链路服务
 * 覆盖：业务请求 → 规则匹配 → 多条件组合评估 → 决策输出 → 结果缓存
 */
@Service
@Slf4j
public class RiskControlRuleService {

    @Resource
    private RuleEngine ruleEngine;
    @Resource
    private RuleRepository ruleRepository;
    @Resource
    private RedisTemplate<String, Object> redisTemplate;
    @Resource
    private RiskControlLogService riskControlLogService;

    /** 决策结果缓存前缀 */
    private static final String DECISION_CACHE_PREFIX = "risk:decision:";
    /** 决策结果缓存TTL（秒） */
    private static final long DECISION_CACHE_TTL = 300;
    /** 幂等请求缓存前缀 */
    private static final String IDEMPOTENT_PREFIX = "risk:idempotent:";

    // ==================== 第一步：业务请求入口 ====================

    /**
     * 订单风控决策入口
     *
     * @param request 风控决策请求
     * @return 风控决策结果
     */
    public RiskDecision decide(OrderRiskRequest request) {
        long startTime = System.currentTimeMillis();
        String traceId = TraceContext.getTraceId();

        log.info("[风控决策] 收到决策请求, traceId={}, orderId={}, userId={}, amount={}",
                traceId, request.getOrderId(), request.getUserId(), request.getAmount());

        // -------- 幂等控制：同一订单只决策一次 --------
        String idempotentKey = IDEMPOTENT_PREFIX + request.getOrderId();
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(idempotentKey, "1", 3600, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(firstTime)) {
            log.info("[风控决策] 重复请求，尝试返回缓存结果, orderId={}", request.getOrderId());
            RiskDecision cached = getCachedDecision(request.getOrderId());
            if (cached != null) {
                log.info("[风控决策] 命中幂等缓存, orderId={}, decision={}",
                        request.getOrderId(), cached.getDecision());
                return cached;
            }
            log.warn("[风控决策] 幂等标记存在但缓存未命中，继续执行决策, orderId={}",
                    request.getOrderId());
        }

        try {
            // 第二步：规则匹配
            // 第三步：多条件组合评估
            RiskDecision decision = executeRuleEvaluation(request, traceId);

            // 第四步：决策输出
            log.info("[风控决策] 决策完成, orderId={}, decision={}, riskLevel={}, reason={}",
                    request.getOrderId(), decision.getDecision(),
                    decision.getRiskLevel(), decision.getReason());

            // 第五步：结果缓存
            cacheDecision(request.getOrderId(), decision);

            // 记录决策日志
            riskControlLogService.log(RiskControlLog.builder()
                    .traceId(traceId)
                    .orderId(request.getOrderId())
                    .userId(request.getUserId())
                    .decision(decision.getDecision())
                    .riskLevel(decision.getRiskLevel())
                    .firedRules(decision.getFiredRules())
                    .durationMs(System.currentTimeMillis() - startTime)
                    .build());

            return decision;

        } catch (RuleEngineException e) {
            log.error("[风控决策] 规则引擎执行异常, orderId={}", request.getOrderId(), e);
            // 规则引擎异常时，降级为人工审核（不直接放行，也不直接拦截）
            RiskDecision fallbackDecision = RiskDecision.builder()
                    .decision(DecisionType.MANUAL_REVIEW)
                    .riskLevel(RiskLevel.UNKNOWN)
                    .reason("规则引擎异常，降级为人工审核: " + e.getMessage())
                    .firedRules(Collections.emptyList())
                    .build();
            cacheDecision(request.getOrderId(), fallbackDecision);
            return fallbackDecision;

        } catch (Exception e) {
            log.error("[风控决策] 决策过程未知异常, orderId={}", request.getOrderId(), e);
            redisTemplate.delete(idempotentKey); // 回滚幂等标记
            throw new RiskControlException("风控决策失败: " + e.getMessage(), e);
        }
    }

    // ==================== 第二步：规则匹配 ====================

    /**
     * 规则匹配：加载风控规则集并执行
     */
    private RiskDecision executeRuleEvaluation(OrderRiskRequest request, String traceId) {
        // 1. 根据业务场景选择规则集分区（性能优化：避免无关规则匹配开销）
        String ruleSetId = selectRuleSet(request);
        log.info("[规则匹配] 选择规则集, ruleSetId={}, orderId={}", ruleSetId, request.getOrderId());

        // 2. 构造Fact对象（插入工作内存的数据）
        OrderFact orderFact = buildOrderFact(request);
        UserFact userFact = buildUserFact(request);
        DeviceFact deviceFact = buildDeviceFact(request);
        BehaviorFact behaviorFact = buildBehaviorFact(request);

        // 3. 创建结果收集器
        RiskDecisionResult resultCollector = new RiskDecisionResult();
        resultCollector.setTraceId(traceId);
        resultCollector.setOrderId(request.getOrderId());

        // 4. 执行规则引擎
        //    内部流程：
        //    a) 将 orderFact / userFact / deviceFact / behaviorFact 插入 Working Memory
        //    b) Pattern Matcher 将规则库中的规则与 Fact 进行模式匹配
        //    c) 匹配成功的规则进入 Agenda，按 salience 优先级排序
        //    d) Execution Engine 依次执行 Agenda 中的规则动作
        //    e) 规则动作将决策结果写入 resultCollector
        List<Object> facts = Arrays.asList(orderFact, userFact, deviceFact, behaviorFact);
        RuleExecutionResult executionResult = ruleEngine.execute(ruleSetId, facts, resultCollector);

        log.info("[规则匹配] 规则执行完毕, ruleSetId={}, firedRules={}, orderId={}",
                ruleSetId, executionResult.getFiredRuleCount(), request.getOrderId());

        // 5. 从结果收集器中提取最终决策
        return buildDecisionFromResult(resultCollector, executionResult);
    }

    // ==================== 第三步：多条件组合评估 ====================

    /**
     * 构造订单Fact（规则匹配的输入数据之一）
     */
    private OrderFact buildOrderFact(OrderRiskRequest request) {
        return OrderFact.builder()
                .orderId(request.getOrderId())
                .userId(request.getUserId())
                .amount(request.getAmount())
                .productCategory(request.getProductCategory())
                .quantity(request.getQuantity())
                .orderTime(new Date())
                .ipAddress(request.getIpAddress())
                .build();
    }

    /**
     * 构造用户Fact（包含信用评分、注册时间、历史订单数等）
     */
    private UserFact buildUserFact(OrderRiskRequest request) {
        UserProfile profile = userService.getProfile(request.getUserId());
        return UserFact.builder()
                .userId(request.getUserId())
                .creditScore(profile.getCreditScore())
                .registerDays(profile.getRegisterDays())
                .totalOrderCount(profile.getTotalOrderCount())
                .completedOrderCount(profile.getCompletedOrderCount())
                .complaintRate(profile.getComplaintRate())
                .isBlacklisted(profile.isBlacklisted())
                .build();
    }

    /**
     * 构造设备Fact（包含设备指纹、是否模拟器、IP风险等）
     */
    private DeviceFact buildDeviceFact(OrderRiskRequest request) {
        DeviceProfile deviceProfile = deviceService.getProfile(
                request.getDeviceId(), request.getIpAddress());
        return DeviceFact.builder()
                .deviceId(request.getDeviceId())
                .ipAddress(request.getIpAddress())
                .isEmulator(deviceProfile.isEmulator())
                .isProxy(deviceProfile.isProxy())
                .ipRiskScore(deviceProfile.getIpRiskScore())
                .deviceFirstSeen(deviceProfile.getFirstSeen())
                .build();
    }

    /**
     * 构造行为Fact（包含下单频率、页面停留时间、操作轨迹等）
     */
    private BehaviorFact buildBehaviorFact(OrderRiskRequest request) {
        BehaviorProfile behavior = behaviorService.getProfile(request.getUserId());
        return BehaviorFact.builder()
                .userId(request.getUserId())
                .ordersInLastHour(behavior.getOrdersInLastHour())
                .ordersInLastDay(behavior.getOrdersInLastDay())
                .avgPageDurationMs(behavior.getAvgPageDurationMs())
                .abnormalActionCount(behavior.getAbnormalActionCount())
                .build();
    }

    // ==================== 第四步：决策输出 ====================

    /**
     * 从规则执行结果中构建最终决策
     */
    private RiskDecision buildDecisionFromResult(RiskDecisionResult resultCollector,
                                                   RuleExecutionResult executionResult) {
        // 规则引擎可能命中多条规则，按优先级取最终决策
        DecisionType finalDecision = resultCollector.getFinalDecision();
        RiskLevel riskLevel = resultCollector.getRiskLevel();
        List<String> firedRules = resultCollector.getFiredRuleNames();

        // 如果规则引擎未给出明确决策，使用默认策略（放行）
        if (finalDecision == null) {
            finalDecision = DecisionType.PASS;
            riskLevel = RiskLevel.LOW;
        }

        String reason = String.format("命中规则: %s, 风险等级: %s, 触发规则数: %d",
                String.join(", ", firedRules),
                riskLevel,
                executionResult.getFiredRuleCount());

        return RiskDecision.builder()
                .decision(finalDecision)
                .riskLevel(riskLevel)
                .reason(reason)
                .firedRules(firedRules)
                .build();
    }

    // ==================== 第五步：结果缓存 ====================

    /**
     * 缓存决策结果
     */
    private void cacheDecision(String orderId, RiskDecision decision) {
        String cacheKey = DECISION_CACHE_PREFIX + orderId;
        try {
            redisTemplate.opsForValue().set(cacheKey, decision,
                    DECISION_CACHE_TTL, TimeUnit.SECONDS);
            log.info("[结果缓存] 决策结果已缓存, orderId={}, ttl={}s", orderId, DECISION_CACHE_TTL);
        } catch (Exception e) {
            // 缓存失败不影响主流程
            log.warn("[结果缓存] 缓存写入失败, orderId={}", orderId, e);
        }
    }

    /**
     * 获取缓存的决策结果
     */
    private RiskDecision getCachedDecision(String orderId) {
        String cacheKey = DECISION_CACHE_PREFIX + orderId;
        try {
            return (RiskDecision) redisTemplate.opsForValue().get(cacheKey);
        } catch (Exception e) {
            log.warn("[结果缓存] 缓存读取失败, orderId={}", orderId, e);
            return null;
        }
    }

    // ==================== 辅助方法 ====================

    /**
     * 根据业务场景选择规则集（规则集分区）
     */
    private String selectRuleSet(OrderRiskRequest request) {
        if (request.getAmount().compareTo(new BigDecimal("50000")) > 0) {
            return "risk_control_high_value";  // 大额订单规则集
        }
        if ("DIGITAL_PRODUCT".equals(request.getProductCategory())) {
            return "risk_control_digital";     // 虚拟商品规则集
        }
        return "risk_control_default";          // 默认规则集
    }
}
```

**关键设计要点**

- **四维Fact组合评估**：OrderFact（订单维度）、UserFact（用户维度）、DeviceFact（设备维度）、BehaviorFact（行为维度）同时插入工作内存，规则引擎自动完成跨维度组合匹配，无需在代码中手写多条件 if-else。
- **规则集分区**：根据订单金额和商品类别选择不同规则集，避免无关规则的匹配开销。大额订单走 `risk_control_high_value` 规则集，虚拟商品走 `risk_control_digital` 规则集，普通订单走 `risk_control_default`。
- **activation-group 互斥控制**：所有终审规则放入 `final-decision` 激活组，同一组内只有一条规则会被执行，避免多条规则冲突写入不同决策结果。
- **降级策略**：规则引擎异常时不直接放行（避免风险）也不直接拦截（避免误杀），而是降级为人工审核，平衡安全性和用户体验。
- **双层缓存**：幂等缓存（1小时TTL）防止同一订单重复决策；决策结果缓存（5分钟TTL）供短时间内的重复查询直接返回，减少规则引擎执行开销。缓存读写失败不影响主流程。

### 8.3 案例三：流程超时与异常处理全链路

**业务背景**

以合同审批流程为例，完整链路为：定时任务扫描超时任务（节点超时检测）→ 向审批人发送催办消息（自动催办）→ 超过催办次数后升级到上级审批人（升级处理）→ 最终超时后根据策略自动通过或驳回（超时自动通过/驳回）。

**全链路代码实现**

```java
/**
 * 流程超时处理全链路服务
 * 覆盖：超时检测 → 自动催办 → 升级处理 → 超时自动通过/驳回
 */
@Service
@Slf4j
public class WorkflowTimeoutService {

    @Resource
    private TaskService taskService;
    @Resource
    private ProcessInstanceRepository instanceRepository;
    @Resource
    private ProcessEngine processEngine;
    @Resource
    private NotificationService notificationService;
    @Resource
    private UserService userService;
    @Resource
    private RedisTemplate<String, String> redisTemplate;

    /** 催办缓存前缀，防止重复催办 */
    private static final String URGE_PREFIX = "wf:timeout:urge:";
    /** 升级缓存前缀，防止重复升级 */
    private static final String ESCALATE_PREFIX = "wf:timeout:escalate:";
    /** 自动处理缓存前缀，防止重复自动通过/驳回 */
    private static final String AUTO_HANDLE_PREFIX = "wf:timeout:auto:";

    /** 催办间隔（秒）——两次催办之间至少间隔2小时 */
    private static final long URGE_INTERVAL_SECONDS = 7200;
    /** 最大催办次数 */
    private static final int MAX_URGE_COUNT = 3;
    /** 超时自动处理延迟（秒）——最后一次催办后24小时未处理则自动处理 */
    private static final long AUTO_HANDLE_DELAY_SECONDS = 86400;

    // ==================== 第一步：节点超时检测 ====================

    /**
     * 定时扫描超时任务
     * 每分钟执行一次，检测所有已超时但尚未处理的任务
     */
    @Scheduled(fixedDelay = 60000)
    public void detectTimeoutTasks() {
        log.info("[超时检测] 开始扫描超时任务...");

        try {
            // 查询所有已超时的待处理任务
            List<Task> overdueTasks = taskService.findOverdueTasks();

            if (overdueTasks.isEmpty()) {
                return;
            }

            log.info("[超时检测] 发现 {} 个超时任务", overdueTasks.size());

            for (Task task : overdueTasks) {
                try {
                    processTimeoutTask(task);
                } catch (Exception e) {
                    // 单个任务处理异常不影响其他任务
                    log.error("[超时检测] 处理超时任务异常, taskId={}", task.getId(), e);
                }
            }

        } catch (Exception e) {
            log.error("[超时检测] 超时扫描异常", e);
        }
    }

    /**
     * 处理单个超时任务（根据超时阶段决定催办/升级/自动处理）
     */
    private void processTimeoutTask(Task task) {
        String taskId = task.getId();
        long overdueHours = calculateOverdueHours(task);
        int urgeCount = getUrgeCount(taskId);

        log.info("[超时检测] 任务超时, taskId={}, assignee={}, overdueHours={}, urgeCount={}",
                taskId, task.getAssignee(), overdueHours, urgeCount);

        if (urgeCount < MAX_URGE_COUNT) {
            // 第二步：自动催办
            sendUrgeNotification(task, urgeCount + 1);

        } else if (urgeCount == MAX_URGE_COUNT
                && overdueHours >= MAX_URGE_COUNT * (URGE_INTERVAL_SECONDS / 3600)
                && !isEscalated(taskId)) {
            // 第三步：升级处理
            escalateTask(task);

        } else if (isEscalated(taskId)
                && getEscalateTime(taskId) != null
                && (System.currentTimeMillis() - getEscalateTime(taskId)) / 1000
                        >= AUTO_HANDLE_DELAY_SECONDS) {
            // 第四步：超时自动通过/驳回
            autoHandleTimeoutTask(task);
        }
    }

    // ==================== 第二步：自动催办 ====================

    /**
     * 发送催办通知
     *
     * @param task      超时任务
     * @param urgeCount 本次催办次数（第几次催办）
     */
    private void sendUrgeNotification(Task task, int urgeCount) {
        String taskId = task.getId();

        // -------- 幂等控制：防止短时间内重复催办 --------
        String urgeKey = URGE_PREFIX + taskId + ":" + urgeCount;
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(urgeKey, "1", URGE_INTERVAL_SECONDS, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(firstTime)) {
            log.debug("[自动催办] 催办冷却期内，跳过, taskId={}, urgeCount={}", taskId, urgeCount);
            return;
        }

        String assignee = task.getAssignee();
        if (assignee == null) {
            // 任务未分配，从候选人中选一个催办
            if (task.getCandidateUsers() != null && !task.getCandidateUsers().isEmpty()) {
                assignee = task.getCandidateUsers().get(0);
            } else {
                log.warn("[自动催办] 任务无分配人且无候选人，跳过催办, taskId={}", taskId);
                redisTemplate.delete(urgeKey); // 回滚标记
                return;
            }
        }

        try {
            // 构造催办消息
            ProcessInstance instance = instanceRepository.get(task.getProcessInstanceId());
            String processName = instance != null ? instance.getProcessDefinitionName() : "未知流程";
            long overdueHours = calculateOverdueHours(task);

            String urgeMessage = String.format(
                    "【催办提醒】第%d次催办\n流程: %s\n任务: %s\n已超时: %d小时\n请尽快处理！",
                    urgeCount, processName, task.getNodeName(), overdueHours);

            // 发送通知（大象消息 + 邮件 + 短信，根据催办次数递增通知渠道）
            notificationService.sendUrgNotification(UrgNotification.builder()
                    .receiver(assignee)
                    .message(urgeMessage)
                    .channels(getChannelsByUrgeCount(urgeCount))
                    .taskId(taskId)
                    .build());

            // 更新催办次数
            incrementUrgeCount(taskId);

            log.info("[自动催办] 催办通知已发送, taskId={}, assignee={}, urgeCount={}, channels={}",
                    taskId, assignee, urgeCount, getChannelsByUrgeCount(urgeCount));

        } catch (Exception e) {
            log.error("[自动催办] 催办通知发送失败, taskId={}", taskId, e);
            redisTemplate.delete(urgeKey); // 回滚标记，允许下次扫描重试
        }
    }

    /**
     * 根据催办次数递增通知渠道
     * 第1次：大象消息
     * 第2次：大象消息 + 邮件
     * 第3次：大象消息 + 邮件 + 短信
     */
    private List<NotificationChannel> getChannelsByUrgeCount(int urgeCount) {
        List<NotificationChannel> channels = new ArrayList<>();
        channels.add(NotificationChannel.ELEPHANT); // 大象消息
        if (urgeCount >= 2) {
            channels.add(NotificationChannel.EMAIL);
        }
        if (urgeCount >= 3) {
            channels.add(NotificationChannel.SMS);
        }
        return channels;
    }

    // ==================== 第三步：升级处理 ====================

    /**
     * 升级任务到上级审批人
     *
     * @param task 超时任务
     */
    private void escalateTask(Task task) {
        String taskId = task.getId();

        // -------- 幂等控制：防止重复升级 --------
        String escalateKey = ESCALATE_PREFIX + taskId;
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(escalateKey, String.valueOf(System.currentTimeMillis()),
                        AUTO_HANDLE_DELAY_SECONDS * 2, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(firstTime)) {
            log.debug("[升级处理] 任务已升级过，跳过, taskId={}", taskId);
            return;
        }

        try {
            String originalAssignee = task.getAssignee();
            String escalatedAssignee = userService.getSuperior(originalAssignee);

            if (escalatedAssignee == null) {
                log.warn("[升级处理] 无法找到上级审批人, taskId={}, assignee={}",
                        taskId, originalAssignee);
                // 无法升级时，标记为需要自动处理
                redisTemplate.opsForValue().set(escalateKey,
                        String.valueOf(System.currentTimeMillis()));
                return;
            }

            log.info("[升级处理] 任务升级, taskId={}, from={}, to={}",
                    taskId, originalAssignee, escalatedAssignee);

            // 转交任务给上级
            task.setAssignee(escalatedAssignee);
            task.setEscalated(true);
            task.setEscalatedFrom(originalAssignee);
            task.setEscalatedTime(new Date());
            taskService.updateTask(task);

            // 通知上级审批人
            String escalateMessage = String.format(
                    "【任务升级】下属 %s 的审批任务已超时，已升级给您处理。\n任务: %s\n原超时人: %s",
                    originalAssignee, task.getNodeName(), originalAssignee);
            notificationService.notify(escalatedAssignee, escalateMessage);

            // 通知原审批人（告知其任务已被升级）
            String notifyOriginal = String.format(
                    "【任务升级通知】您的审批任务 "%s" 因超时已被升级给上级处理。",
                    task.getNodeName());
            notificationService.notify(originalAssignee, notifyOriginal);

            log.info("[升级处理] 升级完成, taskId={}, newAssignee={}", taskId, escalatedAssignee);

        } catch (Exception e) {
            log.error("[升级处理] 升级失败, taskId={}", taskId, e);
            redisTemplate.delete(escalateKey); // 回滚标记，允许重试
        }
    }

    // ==================== 第四步：超时自动通过/驳回 ====================

    /**
     * 超时自动处理任务
     * 根据流程配置的超时策略自动通过或驳回
     *
     * @param task 超时任务
     */
    private void autoHandleTimeoutTask(Task task) {
        String taskId = task.getId();

        // -------- 幂等控制：防止重复自动处理 --------
        String autoKey = AUTO_HANDLE_PREFIX + taskId;
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(autoKey, "1", 86400, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(firstTime)) {
            log.debug("[自动处理] 任务已自动处理过，跳过, taskId={}", taskId);
            return;
        }

        try {
            // 获取流程的超时策略配置
            TimeoutPolicy policy = getTimeoutPolicy(task);

            log.info("[自动处理] 开始自动处理超时任务, taskId={}, policy={}, assignee={}",
                    taskId, policy, task.getAssignee());

            // 构造自动处理的任务变量
            Map<String, Object> taskVariables = new HashMap<>();
            Map<String, Object> processVariables = new HashMap<>();

            switch (policy) {
                case AUTO_APPROVE:
                    // 自动通过
                    taskVariables.put("approvalAction", "APPROVE");
                    taskVariables.put("approvalComment", "任务超时自动通过");
                    taskVariables.put("approver", "SYSTEM_TIMEOUT_HANDLER");
                    taskVariables.put("approvalTime", new Date());
                    taskVariables.put("isAutoHandled", true);
                    processVariables.put("approved", true);
                    processVariables.put("autoHandledReason", "TIMEOUT_AUTO_APPROVE");
                    break;

                case AUTO_REJECT:
                    // 自动驳回
                    taskVariables.put("approvalAction", "REJECT");
                    taskVariables.put("approvalComment", "任务超时自动驳回");
                    taskVariables.put("approver", "SYSTEM_TIMEOUT_HANDLER");
                    taskVariables.put("approvalTime", new Date());
                    taskVariables.put("isAutoHandled", true);
                    processVariables.put("approved", false);
                    processVariables.put("autoHandledReason", "TIMEOUT_AUTO_REJECT");
                    break;

                case NOTIFY_ONLY:
                    // 仅通知，不自动处理
                    log.info("[自动处理] 超时策略为仅通知，不自动处理, taskId={}", taskId);
                    notificationService.notify(task.getAssignee(),
                            "【超时警告】您的审批任务已严重超时，请立即处理！");
                    redisTemplate.delete(autoKey); // 清除标记，允许下次继续检测
                    return;

                default:
                    log.warn("[自动处理] 未知超时策略, taskId={}, policy={}", taskId, policy);
                    redisTemplate.delete(autoKey);
                    return;
            }

            // 执行任务完成（触发流程流转）
            processEngine.completeTask(taskId, taskVariables, processVariables);

            log.info("[自动处理] 超时任务已自动处理, taskId={}, policy={}", taskId, policy);

            // 发送通知
            String notifyMessage = String.format(
                    "【超时自动处理】您的审批任务 "%s" 已因超时被系统自动%s。",
                    task.getNodeName(),
                    policy == TimeoutPolicy.AUTO_APPROVE ? "通过" : "驳回");
            notificationService.notify(
                    task.getEscalated() ? task.getEscalatedFrom() : task.getAssignee(),
                    notifyMessage);

            // 记录审计日志
            auditLogService.log(AuditLogEntry.builder()
                    .action("TIMEOUT_AUTO_HANDLE")
                    .taskId(taskId)
                    .processInstanceId(task.getProcessInstanceId())
                    .operator("SYSTEM_TIMEOUT_HANDLER")
                    .detail(String.format("超时自动%s, 策略=%s",
                            policy == TimeoutPolicy.AUTO_APPROVE ? "通过" : "驳回", policy))
                    .timestamp(new Date())
                    .build());

        } catch (TaskAlreadyCompletedException e) {
            // 任务已被人工处理（并发场景），静默处理
            log.info("[自动处理] 任务已被人工处理，跳过自动处理, taskId={}", taskId);

        } catch (Exception e) {
            log.error("[自动处理] 自动处理失败, taskId={}", taskId, e);
            redisTemplate.delete(autoKey); // 回滚标记，允许下次扫描重试
        }
    }

    // ==================== 辅助方法 ====================

    /**
     * 计算任务超时小时数
     */
    private long calculateOverdueHours(Task task) {
        if (task.getDueDate() == null) {
            return 0;
        }
        long diffMs = System.currentTimeMillis() - task.getDueDate().getTime();
        return diffMs > 0 ? diffMs / (1000 * 60 * 60) : 0;
    }

    /**
     * 获取催办次数
     */
    private int getUrgeCount(String taskId) {
        String count = redisTemplate.opsForValue().get(URGE_PREFIX + taskId + ":count");
        return count != null ? Integer.parseInt(count) : 0;
    }

    /**
     * 递增催办次数
     */
    private void incrementUrgeCount(String taskId) {
        String key = URGE_PREFIX + taskId + ":count";
        redisTemplate.opsForValue().increment(key);
        redisTemplate.expire(key, 7, TimeUnit.DAYS); // 7天后自动清理
    }

    /**
     * 是否已升级
     */
    private boolean isEscalated(String taskId) {
        return Boolean.TRUE.equals(redisTemplate.hasKey(ESCALATE_PREFIX + taskId));
    }

    /**
     * 获取升级时间戳
     */
    private Long getEscalateTime(String taskId) {
        String value = redisTemplate.opsForValue().get(ESCALATE_PREFIX + taskId);
        return value != null ? Long.parseLong(value) : null;
    }

    /**
     * 获取流程的超时策略
     */
    private TimeoutPolicy getTimeoutPolicy(Task task) {
        ProcessInstance instance = instanceRepository.get(task.getProcessInstanceId());
        if (instance == null) {
            return TimeoutPolicy.NOTIFY_ONLY; // 默认仅通知
        }
        // 从流程定义中读取节点配置的超时策略
        String policyStr = (String) instance.getVariables()
                .getOrDefault("timeoutPolicy_" + task.getNodeId(), "NOTIFY_ONLY");
        try {
            return TimeoutPolicy.valueOf(policyStr);
        } catch (IllegalArgumentException e) {
            log.warn("[超时策略] 未知策略值, 使用默认值 NOTIFY_ONLY, value={}", policyStr);
            return TimeoutPolicy.NOTIFY_ONLY;
        }
    }
}
```

**超时策略枚举定义**

```java
/**
 * 超时处理策略
 */
public enum TimeoutPolicy {
    /** 仅通知，不自动处理（持续催办 + 通知上级） */
    NOTIFY_ONLY,
    /** 超时自动通过 */
    AUTO_APPROVE,
    /** 超时自动驳回 */
    AUTO_REJECT
}
```

**关键设计要点**

- **四阶段渐进式处理**：超时检测 → 3次催办（递增通知渠道）→ 升级到上级 → 自动通过/驳回。每个阶段都有独立的触发条件，不会跳跃执行。
- **幂等控制贯穿全链路**：催办用 `urgeKey` 保证2小时内不重复催办；升级用 `escalateKey` 保证只升级一次；自动处理用 `autoKey` 保证只自动处理一次。所有幂等标记在操作失败时回滚，操作成功时保留。
- **催办渠道递增**：第1次催办仅发大象消息（轻量提醒）；第2次追加邮件（正式提醒）；第3次追加短信（紧急提醒）。既避免过度打扰，又确保信息触达。
- **异常处理分层**：`TaskAlreadyCompletedException` 表示人工已处理（并发场景），静默跳过；其他异常回滚幂等标记允许下次扫描重试；单个任务处理异常不影响其他任务的检测和处理。
- **审计日志**：所有自动处理操作都记录审计日志，包含操作人（SYSTEM_TIMEOUT_HANDLER）、操作类型、任务ID、流程实例ID和操作详情，确保可追溯。
- **超时策略可配置**：通过流程变量 `timeoutPolicy_{nodeId}` 为每个节点单独配置超时策略（NOTIFY_ONLY / AUTO_APPROVE / AUTO_REJECT），不同节点可以使用不同策略。
