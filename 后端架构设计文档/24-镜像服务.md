# 镜像服务架构设计

## 一、问题背景

### 1.1 核心问题

在云原生与容器化技术全面普及的今天，容器镜像已经成为应用交付的标准单元。一个典型的中大型互联网公司可能拥有数万个微服务，每天产生数十万次镜像构建与拉取操作，存储的镜像总量可达PB级别。容器镜像服务（Container Image Service）作为容器基础设施的核心组件，承担着镜像的构建、存储、分发、安全扫描和生命周期管理等关键职责。

在大规模生产环境中，镜像服务面临以下核心挑战：

1. **存储效率问题**：数万个镜像之间存在大量重复层（Layer），一个Java应用镜像约500MB~1GB，若不去重，存储量将突破PB级。
2. **分发性能瓶颈**：数千节点同时拉取同一镜像时，中心化Registry的出口带宽和IOPS成为瓶颈。
3. **构建效率不足**：缺乏缓存策略和多阶段构建优化时，单次构建可能耗时数十分钟。
4. **安全合规风险**：镜像中的已知漏洞若不主动扫描和准入控制，会随分发扩散到整个集群。
5. **跨数据中心同步**：多活架构下，同步延迟可能导致部署失败或版本不一致。
6. **生命周期管理缺失**：过期镜像层持续占用存储空间，导致成本失控。

### 1.2 场景描述

容器镜像服务是容器化基础设施的核心枢纽，核心定位包括：

- **统一镜像仓库**：符合OCI标准，兼容Docker Registry V2 API。
- **高效构建引擎**：支持多阶段构建、构建缓存、并行构建等优化策略。
- **大规模分发加速**：通过P2P分发、按需加载、多级缓存将拉取时间优化到秒级。
- **安全保障体系**：漏洞扫描、镜像签名、准入控制全链路保障安全。
- **自动化生命周期管理**：基础镜像升级、版本追踪、垃圾回收自动化。

### 1.3 不解决的后果

- **Pod启动缓慢**：镜像拉取时间占容器启动总时间76%以上，而实际只使用了镜像中6.4%的数据。
- **存储成本失控**：缺乏去重和GC机制，冗余数据持续膨胀。
- **安全漏洞扩散**：未扫描镜像部署到生产环境，排查极其困难。
- **运维复杂度高**：基础镜像升级需人工逐一协调，安全补丁无法及时推广。

### 2.2 镜像生命周期

```
代码提交 → 触发构建 → Dockerfile解析 → 分层构建 → 推送Registry
    → 安全扫描 → 通过? → 跨机房同步 → 预分发 → 容器调度拉取
    → 版本迭代 → 旧版标记 → 保留期后GC清理
```

### 2.3 核心设计原则

1. **内容可寻址**：所有数据通过SHA256哈希值唯一标识，天然支持去重和完整性校验。
2. **分层存储**：镜像由多个只读层叠加组成，层可跨镜像共享。
3. **分布式分发**：通过P2P和多级缓存将分发压力从中心Registry分散到边缘节点。
4. **安全左移**：在构建阶段即进行安全扫描，而非等到部署阶段。
5. **最终一致性**：跨数据中心采用异步复制，在一致性和可用性之间取得平衡。

## 三、核心链路设计

### 3.1 镜像分层存储

#### 3.1.1 OCI镜像规范

OCI镜像由三部分组成：**Manifest**（目录，记录Config和Layer的摘要）、**Config**（运行时配置）、**Layers**（文件系统层，tar.gz格式）。

```
Image Manifest
├── Config Descriptor → Config JSON (env, cmd, ports, rootfs)
│     digest: sha256:abc123...
└── Layer Descriptors[]
      [0] digest: sha256:def456...  (基础OS层, 50MB)
      [1] digest: sha256:789abc...  (JDK运行时层, 10MB)
      [2] digest: sha256:cde012...  (应用代码层, 2MB)
```

Manifest示例：

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:a1b2c3d4...",
    "size": 7023
  },
  "layers": [
    {"mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
     "digest": "sha256:1a2b3c4d...", "size": 52428800},
    {"mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
     "digest": "sha256:7a8b9c0d...", "size": 10485760}
  ]
}
```

#### 3.1.2 内容可寻址存储

每块数据（Blob）通过其SHA256哈希值作为唯一标识符，实现**天然去重**、**完整性校验**和**不可变性**：

```java
public class ContentAddressableStorage {
    private final ObjectStorageBackend backend;
    private final ConcurrentMap<String, ReentrantLock> uploadLocks = new ConcurrentHashMap<>();

    /** 存储Blob: 计算摘要 -> 检查去重 -> 存储 -> 验证 */
    public BlobDescriptor putBlob(InputStream inputStream) throws Exception {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        Path tempFile = Files.createTempFile("blob-upload-", ".tmp");
        long size = 0;
        try (DigestInputStream dis = new DigestInputStream(inputStream, digest);
             OutputStream out = Files.newOutputStream(tempFile)) {
            byte[] buf = new byte[8192];
            int n;
            while ((n = dis.read(buf)) != -1) { out.write(buf, 0, n); size += n; }
        }
        String blobDigest = "sha256:" + bytesToHex(digest.digest());

        // digest粒度锁防止并发写入
        ReentrantLock lock = uploadLocks.computeIfAbsent(blobDigest, k -> new ReentrantLock());
        lock.lock();
        try {
            if (backend.exists(blobPath(blobDigest))) {  // 去重核心：已存在则跳过
                return new BlobDescriptor(blobDigest, size);
            }
            try (InputStream fs = Files.newInputStream(tempFile)) {
                backend.put(blobPath(blobDigest), fs, size);
            }
        } finally {
            lock.unlock();
            Files.deleteIfExists(tempFile);
        }
        return new BlobDescriptor(blobDigest, size);
    }

    /** 存储路径：blobs/sha256/ab/abcdef... (两级目录防单目录过多) */
    private String blobPath(String digest) {
        String hash = digest.replace("sha256:", "");
        return String.format("blobs/sha256/%s/%s", hash.substring(0, 2), hash);
    }
}
```

#### 3.1.3 Layer去重与共享

大量镜像共享相同的基础层。例如基于`openjdk:17-slim`的所有Java应用共享OS层和JDK层：

```
镜像A (order-service)          镜像B (payment-service)
┌──────────────────┐          ┌──────────────────┐
│ Layer 3: app.jar │ 独有     │ Layer 3: app.jar │ 独有
│ sha256:aaa...    │          │ sha256:bbb...    │
├──────────────────┤          ├──────────────────┤
│ Layer 2: JDK 17  │ ←共享──→ │ Layer 2: JDK 17  │ (物理只存一份)
│ sha256:777...    │          │ sha256:777...    │
├──────────────────┤          ├──────────────────┤
│ Layer 1: Debian  │ ←共享──→ │ Layer 1: Debian  │ (物理只存一份)
│ sha256:555...    │          │ sha256:555...    │
└──────────────────┘          └──────────────────┘
```

去重效果：10000个同类Java镜像，基础层占85%，理论存储8PB，去重后约1.2TB，去重率超99.98%。

#### 3.1.4 联合文件系统（OverlayFS）

容器运行时通过OverlayFS将多个只读层叠加，顶层添加可写层组成容器rootfs。写时复制（CoW）确保底层数据不可变，多容器安全共享只读层：

```
┌─────────────────────┐ ← 可写层 (容器运行时修改)
│ Container Layer (RW) │
├─────────────────────┤
│ Layer 3: app (RO)    │ ← 只读层叠加
│ Layer 2: JDK (RO)    │
│ Layer 1: OS  (RO)    │
└─────────────────────┘

mount -t overlay overlay \
  -o lowerdir=layer3:layer2:layer1,upperdir=container-rw,workdir=work /merged
```

### 3.2 镜像构建流程

#### 3.2.1 Dockerfile指令处理流水线

每条Dockerfile指令按序执行，产生对应镜像层。**关键优化**：将变化频率低的指令（依赖安装）放前面，高的（源码复制）放后面，最大化缓存复用。

```
FROM openjdk:17-slim          → 引用基础镜像所有层
COPY pom.xml .                → 产生新层（变化少，可缓存）
RUN mvn dependency:resolve    → 产生新层（依赖缓存层）
COPY src/ ./src/              → 产生新层（变化频繁）
RUN mvn package               → 产生新层（编译结果层）
CMD ["java", "-jar", "app.jar"] → 仅修改Config，不产新层
```

#### 3.2.2 BuildKit架构

BuildKit采用 Frontend(Dockerfile→LLB) → Solver(DAG求解+并行) → Worker(执行) 三层架构。LLB将构建过程表示为DAG，无依赖操作可并行执行：

```java
public class LLBSolver {
    private final ExecutorService executor;
    private final BuildCacheManager cacheManager;

    /** 拓扑排序 + 并行执行无依赖节点 */
    public BuildResult solve(LLBDefinition definition) throws Exception {
        DirectedAcyclicGraph<BuildOp> dag = definition.getOperationGraph();
        Map<String, AtomicInteger> inDegree = new HashMap<>();
        BlockingQueue<BuildOp> readyQueue = new LinkedBlockingQueue<>();
        Map<String, LayerResult> results = new ConcurrentHashMap<>();

        // 初始化入度，入度为0的节点入队
        for (BuildOp op : dag.getNodes()) {
            int degree = dag.getIncomingEdges(op.getId()).size();
            inDegree.put(op.getId(), new AtomicInteger(degree));
            if (degree == 0) readyQueue.add(op);
        }

        // 并行执行：完成后更新后继节点入度
        while (!allCompleted(dag, results)) {
            BuildOp op = readyQueue.poll(100, TimeUnit.MILLISECONDS);
            if (op == null) continue;
            final BuildOp currentOp = op;
            executor.submit(() -> {
                String cacheKey = computeCacheKey(currentOp, results);
                LayerResult cached = cacheManager.get(cacheKey);
                LayerResult result = (cached != null) ? cached : executeOp(currentOp, results);
                if (cached == null) cacheManager.put(cacheKey, result);
                results.put(currentOp.getId(), result);
                // 更新后继节点入度，入度降为0则入队
                for (String succ : dag.getOutgoingEdges(currentOp.getId())) {
                    if (inDegree.get(succ).decrementAndGet() == 0)
                        readyQueue.add(dag.getNode(succ));
                }
            });
        }
        return assembleResult(results, dag);
    }
}
```

#### 3.2.4 构建缓存策略

分为本地缓存和远程缓存（Registry-based Cache）两种模式。CI/CD场景中将构建缓存导出为特殊镜像推送到Registry，供后续构建复用：

```java
public class BuildCacheManager {
    private final Map<String, CacheEntry> localCache;       // 本地LRU缓存
    private final RegistryClient registryClient;             // 远程缓存

    /** 查询缓存：本地 → 远程 → 未命中 */
    public LayerResult get(String cacheKey) {
        CacheEntry local = localCache.get(cacheKey);
        if (local != null) return local.getResult();
        try {
            CacheManifest remote = registryClient.getCacheManifest(cacheKey);
            if (remote != null) {
                LayerResult result = downloadCacheLayer(remote);
                localCache.put(cacheKey, new CacheEntry(result)); // 回填
                return result;
            }
        } catch (Exception e) { log.warn("Remote cache failed", e); }
        return null;
    }

    /** 导出缓存到远程Registry，供CI/CD跨构建复用 */
    public void exportToRemote(String cacheKey, LayerResult result) throws IOException {
        registryClient.pushCacheManifest("cache/" + cacheKey, CacheManifest.of(result));
    }
}
```

#### 3.2.5 CI/CD集成流水线

```
代码提交 → 单元测试 → 镜像构建 → 安全扫描 → 推送仓库 → 跨机房同步 → 预分发 → 滚动部署
```

```java
public class ImageBuildPipeline {
    public PipelineResult execute(BuildRequest request) {
        // 1. 构建镜像
        BuildResult buildResult = buildEngine.build(request);
        // 2. 安全扫描 — 发现高危漏洞则阻断
        ScanResult scanResult = scanner.scan(buildResult.getImageId());
        if (scanResult.hasBlockingVulnerabilities()) {
            notifyDevelopers(request, scanResult);
            return PipelineResult.blocked(scanResult);
        }
        // 3. 推送Registry
        registryClient.push(buildResult.getImageId(), request.getImageRef());
        // 4. 触发跨机房同步

        // 5. 预分发到目标节点
        if (request.isPreDistribute())
            preDistService.distribute(request.getImageRef(), request.getTargetClusters());
        return PipelineResult.success();
    }
}
```

### 3.3 镜像分发与加速

#### 3.3.1 四级缓存架构

```
Level 4: 源站 (中心Registry, 跨机房同步)
    ↑ 缓存未命中回源
Level 3: 同机房Registry缓存副本 (每个机房部署)
    ↑ 缓存未命中
Level 2: 超级节点缓存 (每可用区2-3个，P2P种子节点)
    ↑ 缓存未命中
Level 1: 宿主机本地缓存 (containerd本地存储)
```

| 缓存层级 | 命中率 | 延迟 |
|---------|-------|------|
| L1 本地 | ~60% | <1ms |
| L2 超级节点 | ~25% | <5ms |
| L3 同机房Registry | ~12% | <10ms |
| L4 源站 | ~3% | 50-200ms |

#### 3.3.2 P2P分发架构

大规模部署时，P2P将中心Registry的带宽压力分散到各节点间。借鉴BitTorrent协议，将Layer切分为4MB的chunk，节点间互传：

```java
public class P2PDistributionScheduler {
    private static final int CHUNK_SIZE = 4 * 1024 * 1024; // 4MB

    /** 为拉取请求创建下载计划：查询每个chunk的可用源节点 */
    public DownloadPlan createDownloadPlan(String layerDigest, String requestNodeId) {
        LayerMetadata metadata = chunkTracker.getLayerMetadata(layerDigest);
        int totalChunks = (int) Math.ceil((double) metadata.getSize() / CHUNK_SIZE);
        DownloadPlan plan = new DownloadPlan(layerDigest, requestNodeId);

        for (int i = 0; i < totalChunks; i++) {
            List<PeerInfo> peers = chunkTracker.getPeersWithChunk(layerDigest, i);
            if (peers.isEmpty()) {
                // 无Peer拥有此chunk → 从超级节点获取
                plan.addChunkSource(i, superNodeManager.selectSuperNode(requestNodeId));
            } else {
                // 选最优Peer: 同机架 > 同可用区 > 同机房，同级中选负载最低的
                plan.addChunkSource(i, selectBestPeer(peers, requestNodeId));
            }
        }
        plan.shuffleChunkOrder(); // 随机化避免热点
        return plan;
    }

    /** 节点完成chunk下载后上报，使自己成为该chunk的新种子 */
    public void reportChunkCompleted(String nodeId, String layerDigest, int chunkIndex) {
        chunkTracker.registerChunk(nodeId, layerDigest, chunkIndex);
    }
}
```

#### 3.3.3 预分发机制

基础镜像和高频镜像在部署前提前推送到目标节点。策略：**先推到超级节点**（种子）→ **通过P2P批量扩散到普通节点**（每批10%节点，滚动分发）。

```java
public class PreDistributionService {
    public PreDistributionTask distribute(String imageRef, List<String> targetClusters) {
        List<String> layerDigests = registryClient.getManifest(imageRef).getLayerDigests();
        for (String clusterId : targetClusters) {
            ClusterInfo cluster = clusterManager.getCluster(clusterId);
            // 第一波: 推送到超级节点
            cluster.getSuperNodes().forEach(sn -> prePullToNode(sn, imageRef, layerDigests));
            // 第二波: 通过P2P滚动扩散到普通节点
            List<String> workers = cluster.getWorkerNodes();
            int batchSize = Math.max(workers.size() / 10, 10);
            for (int i = 0; i < workers.size(); i += batchSize) {
                List<String> batch = workers.subList(i, Math.min(i + batchSize, workers.size()));
                batch.parallelStream().forEach(nodeId ->
                    layerDigests.forEach(d -> p2pScheduler.createDownloadPlan(d, nodeId)));
                waitForBatchCompletion(batch, layerDigests);
            }
        }
        return PreDistributionTask.completed(imageRef);
    }
}
```

#### 3.3.4 按需加载（Lazy Pulling）

容器启动时实际只需镜像中约**6.4%**的数据。按需加载允许容器在镜像未完全下载时就启动：

```
传统拉取: 下载100%数据(分钟级) → 解压(分钟级) → 启动
按需加载: 下载索引(<1秒) → 立即启动 → 后台按需下载6.4%数据
```

核心是改变镜像格式支持随机访问（Range Read），使用块级远程读取：

```java
public class LazyPullStorageDriver {
    private static final int BLOCK_SIZE = 256 * 1024; // 256KB

    /** FUSE回调：容器进程读取文件时，按需从远程获取数据块 */
    public byte[] readFile(String layerDigest, String filePath,
                           long offset, int length) throws IOException {
        FileEntry entry = getFileEntry(layerDigest, filePath);
        long layerOffset = entry.getOffset() + offset;
        int startBlock = (int) (layerOffset / BLOCK_SIZE);
        int endBlock = (int) ((layerOffset + length - 1) / BLOCK_SIZE);

        ByteArrayOutputStream result = new ByteArrayOutputStream(length);
        for (int b = startBlock; b <= endBlock; b++) {
            byte[] blockData = readBlock(layerDigest, b); // 优先本地缓存，回退远程Range Read
            int bStart = (b == startBlock) ? (int)(layerOffset % BLOCK_SIZE) : 0;
            int bEnd = (b == endBlock) ? (int)((layerOffset + length - 1) % BLOCK_SIZE) + 1 : BLOCK_SIZE;
            result.write(blockData, bStart, bEnd - bStart);
        }
        readAheadPredictor.onAccess(layerDigest, startBlock, endBlock); // 触发预读
        return result.toByteArray();
    }
}
```

#### 3.3.5 加速镜像格式

传统tar.gz不支持随机访问。eStargz/Nydus RAFS格式在层末尾添加TOC（Table of Contents）索引，每个文件数据独立压缩为chunk，支持HTTP Range请求单独获取：

```
eStargz格式:
┌──────────────────┐
│ TOC (文件索引JSON)│ ← 记录每个文件的offset/size/digest
├──────────────────┤
│ Chunk 1 (独立压缩)│ ← 可单独解压，支持Range Read
│ Chunk 2 (独立压缩)│
│ ...              │
│ Footer (TOC偏移) │
└──────────────────┘
```

```java
public class CrossDatacenterReplicationService {
```

#### 3.4.2 镜像签名与验证

基于Cosign/Notary V2方案，对Manifest的SHA256摘要进行ECDSA签名，签名作为OCI Artifact存储在Registry中。验证时用公钥验证签名有效性并检查摘要一致性。

```java
public class ImageSignatureService {
    /** 签名：SHA256(Manifest) → ECDSA签名 → 存为OCI Artifact */
    public SignatureResult sign(String imageRef, String signingKeyId) throws Exception {
        byte[] manifestBytes = registryClient.getManifest(imageRef).toJsonBytes();
        String manifestDigest = sha256(manifestBytes);
        Signature signer = Signature.getInstance("SHA256withECDSA");
        signer.initSign(keyStore.getPrivateKey(signingKeyId));
        signer.update(manifestDigest.getBytes(StandardCharsets.UTF_8));
        byte[] sig = signer.sign();
        // 将签名存储为OCI Artifact
        registryClient.pushArtifact(imageRef, manifestDigest + ".sig",
            new SignaturePayload(manifestDigest, Base64.getEncoder().encodeToString(sig)));
        return new SignatureResult(imageRef, manifestDigest);
    }

    /** 验证：取签名 → 公钥验证 → 检查摘要一致性 */
    public VerificationResult verify(String imageRef, String trustedKeyId) throws Exception {
        String currentDigest = sha256(registryClient.getManifest(imageRef).toJsonBytes());
        SignaturePayload payload = registryClient.getArtifact(imageRef, currentDigest + ".sig");
        if (payload == null) return VerificationResult.unsigned(imageRef);
        Signature verifier = Signature.getInstance("SHA256withECDSA");
        verifier.initVerify(keyStore.getPublicKey(trustedKeyId));
        verifier.update(payload.getManifestDigest().getBytes(StandardCharsets.UTF_8));
        boolean valid = verifier.verify(Base64.getDecoder().decode(payload.getSignature()));
        return valid && currentDigest.equals(payload.getManifestDigest())
            ? VerificationResult.verified(imageRef) : VerificationResult.tampered(imageRef);
    }
}
```

#### 3.4.3 准入控制

通过Kubernetes Admission Webhook拦截Pod创建请求，验证镜像安全合规性：检查签名有效性、漏洞扫描结果、是否使用latest标签等。不合规则拒绝部署：

```java
@PostMapping("/webhook/validate")
public AdmissionResponse validate(@RequestBody AdmissionRequest request) {
    List<String> violations = new ArrayList<>();
    for (Container c : request.getObject().getSpec().getContainers()) {
        String imageRef = c.getImage();
        // 1. 验证签名
        if (policy.requiresSignature(imageRef) && !signatureService.verify(imageRef).isVerified())
            violations.add("镜像 " + imageRef + " 签名验证失败");
        // 2. 检查漏洞
        ScanResult scan = scanner.scan(imageRef);
        if (scan.getCriticalCount() > 0 && policy.blockOnCritical())
            violations.add("镜像 " + imageRef + " 包含 " + scan.getCriticalCount() + " 个严重漏洞");
        // 3. 禁止latest标签
        if (imageRef.endsWith(":latest") && policy.blockLatestTag())
            violations.add("镜像 " + imageRef + " 禁止使用latest标签");
    }
    return violations.isEmpty() ? AdmissionResponse.allowed() : AdmissionResponse.denied(violations);
}
```

### 3.5 镜像垃圾回收

#### 3.5.1 非阻塞GC算法

采用三阶段**标记-清扫-延迟清除**策略，不停止Registry服务：

```
阶段1 Mark:  遍历所有Manifest → 收集引用的Layer摘要 → 构建引用集合
阶段2 Sweep: 遍历所有Blob → 不在引用集合中且创建于GC开始前 → 标记软删除
阶段3 Purge: 软删除超过保留期(7天)的Blob → 再次确认无引用 → 物理删除
```

```java
public class OnlineGarbageCollector {
    private final Duration softDeleteRetention; // 默认7天

    public GcResult performGc() {
        Instant gcStartTime = Instant.now();

        // Mark: 收集所有被Manifest引用的digest
        Set<String> referencedDigests = new ConcurrentSkipListSet<>();
        for (String repo : metadataStore.listRepositories()) {
            for (String tag : metadataStore.listTags(repo)) {
                ImageManifest m = metadataStore.getManifest(repo, tag);
                referencedDigests.add(m.getConfig().getDigest());
                m.getLayers().forEach(l -> referencedDigests.add(l.getDigest()));
                referencedDigests.add(m.getDigest());
            }
        }

        // Sweep: 未被引用且在GC开始前创建的Blob → 软删除
        for (String blobPath : storageBackend.list("blobs/")) {
            String digest = extractDigest(blobPath);
            if (!referencedDigests.contains(digest)
                    && storageBackend.stat(blobPath).getLastModified().isBefore(gcStartTime)) {
                metadataStore.markSoftDeleted(digest, Instant.now());
            }
        }

        // Purge: 超过保留期且仍无引用的Blob → 物理删除
        Instant threshold = Instant.now().minus(softDeleteRetention);
        for (String digest : metadataStore.getSoftDeletedBefore(threshold)) {
            if (!isReferencedByAnyManifest(digest)) {
                storageBackend.delete(constructBlobPath(digest));
            } else {
                metadataStore.removeSoftDeleteMarker(digest); // 保留期内被新Manifest引用
            }
        }
        return result;
    }
}
```

### 3.6 镜像版本管理与升级

#### 3.6.1 基础镜像升级工作流

```
构建新版基础镜像 → 查找所有依赖的下游镜像 → 触发下游重建 → 预分发 → 金丝雀灰度 → 全量滚动升级
```

```java
public class BaseImageUpgradeOrchestrator {
    public UpgradeResult executeUpgrade(UpgradeRequest request) {
        // 1. 构建新版基础镜像
        PipelineResult buildResult = buildPipeline.execute(request.toBuildRequest());
        if (!buildResult.isSuccess()) return UpgradeResult.buildFailed(buildResult);

        // 2. 查找所有依赖此基础镜像的下游镜像（BFS遍历依赖图）
        List<DependentImage> dependents = dependencyTracker.findDependentImages(request.getBaseImageRef());

        // 3. 触发下游镜像重建
        dependents.forEach(dep -> buildPipeline.execute(dep.toRebuildRequest(request.getNewVersion())));

        // 4. 预分发 → 金丝雀灰度 → 全量
        preDistService.distribute(request.getNewImageRef(), request.getTargetClusters());
        CanaryResult canary = canaryService.startCanary(request.getNewImageRef(), 5, Duration.ofHours(2));
        if (!canary.isSuccessful()) { canaryService.rollback(canary.getId()); return UpgradeResult.canaryFailed(); }
        return UpgradeResult.success();
    }
}

/** 依赖追踪: BFS遍历FROM依赖图 */
public class DependencyTracker {
    public List<DependentImage> findDependentImages(String baseImageRef) {
        List<DependentImage> result = new ArrayList<>();
        Queue<String> queue = new LinkedList<>(List.of(baseImageRef));
        Set<String> visited = new HashSet<>(queue);
        while (!queue.isEmpty()) {
            for (String child : metadataStore.getChildImages(queue.poll())) {
                if (visited.add(child)) { queue.add(child); result.add(new DependentImage(child)); }
            }
        }
        return result;
    }
}
```

```java
            @RequestHeader(value = "Range", required = false) String rangeHeader) throws IOException {

        if (rangeHeader != null) {
            long[] range = parseRange(rangeHeader);
            return ResponseEntity.status(206)
                .body(new InputStreamResource(cas.getBlobRange(digest, range[0], range[1] - range[0] + 1)));
```

#### 3.7.2 推送与拉取流程

#### 3.7.3 反向代理与故障转移

Registry前端部署反向代理层，读请求优先本机房（降级跨机房），写请求路由到主Registry。当某机房不可用时自动切换：

```java
public class RegistryReverseProxy {
    public HttpResponse proxy(HttpRequest request) throws IOException {
        RequestType type = classifyRequest(request);
        List<RegistryBackend> healthy = backends.stream()
            .filter(b -> circuitBreakers.get(b.getId()).isAllowed()).collect(Collectors.toList());
        RegistryBackend selected = (type == RequestType.PULL_MANIFEST || type == RequestType.PULL_BLOB)
            ? loadBalancer.selectForRead(healthy, request)   // 读请求优先本机房
            : loadBalancer.selectForWrite(healthy, request); // 写请求路由到主
        try {
            return forwardRequest(request, selected);
        } catch (Exception e) {
            // 故障转移：尝试其他后端
            for (RegistryBackend fallback : healthy) {
                if (!fallback.getId().equals(selected.getId())) {
                    try { return forwardRequest(request, fallback); } catch (Exception ignored) {}
                }
            }
            throw new RegistryUnavailableException("所有Registry后端不可用");
        }
    }
}
```

## 四、异常处理与容错

### 4.1 Registry故障转移

通过定期健康检查（每5秒探测`/v2/`端点）+ 熔断器模式实现故障检测。拉取请求优先本机房Registry，不可用时自动降级到其他机房。

### 4.2 同步延迟处理

从本地Registry拉取失败（NotFound）时，自动回源到源Registry拉取，同时异步触发即时同步加速后续请求：

```java
public ImageManifest pullWithFallback(String imageRef) throws IOException {
    try {
        return localRegistry.getClient().getManifest(imageRef); // 本地优先
    } catch (NotFoundException e) {
        ImageManifest manifest = sourceRegistry.getClient().getManifest(imageRef); // 回源
        CompletableFuture.runAsync(() -> triggerImmediateSync(imageRef)); // 异步同步
        return manifest;
    }
}
```

### 4.3 构建失败恢复

区分可重试失败（网络超时）和不可重试失败（语法错误、依赖缺失）。可重试失败采用指数退避重试（2^n秒，上限30秒），不可重试失败直接返回错误。

### 4.4 存储后端故障

对象存储不可用时，Registry进入只读降级模式：拉取请求基于本地缓存继续服务，推送请求返回503。存储恢复后自动恢复写入能力。

## 六、最佳实践与总结

### 6.1 架构设计原则

1. **内容寻址是基石**: SHA256摘要实现去重、校验和缓存一体化。
2. **不可变性保证安全**: 镜像层一旦写入不可修改，多容器安全共享。
3. **分层设计降低成本**: 跨镜像层共享，生产环境可达99%以上去重率。
4. **异步解耦提升吞吐**: 构建、扫描、同步、GC通过消息队列异步解耦。

### 6.2 关键技术决策

| 技术决策 | 选择方案 | 核心理由 |
|---------|---------|--------|
| 存储寻址 | Content-Addressable (SHA256) | 去重、校验、缓存一体化 |
| 分发架构 | P2P + 四级缓存 | 线性可扩展，去中心化 |
| 镜像格式 | OCI Image Spec + eStargz | 标准化 + 按需加载 |
| GC策略 | 非阻塞标记-清扫 + 软删除 | 在线GC不影响服务 |
| 安全集成 | 构建时扫描 + 部署时准入 | 安全左移，纵深防御 |
| 同步方案 | 异步增量复制 | 只传差异层，节省带宽 |

### 6.3 容量规划参考

| 指标 | 中小规模 | 大规模 |
|------|---------|-------|
| 镜像总数 | <10,000 | 100,000+ |
| 日均构建次数 | <1,000 | 50,000+ |

| 并发拉取QPS | <500 | 10,000+ |
| 平均拉取延迟 | <5s | <3s (P2P+预分发) |

### 6.4 总结

镜像服务作为容器化基础设施的核心组件，其设计质量直接影响发布效率、运行稳定性和安全合规性。本文从分层存储、构建流程、分发加速、安全扫描、垃圾回收、版本管理和Registry实现七个维度进行了深入分析。

核心价值归纳：
- **效率**: P2P分发、按需加载、预分发将容器冷启动从分钟级降到秒级。
- **成本**: 内容寻址去重在大规模场景下实现99%以上存储去重率。
- **安全**: 构建时扫描、签名验证、准入控制构建全生命周期安全防线。

这些技术形成完整闭环：构建产生镜像 → 扫描确保安全 → 同步实现多活 → P2P加速分发 → 按需加载提速启动 → GC回收空间。
