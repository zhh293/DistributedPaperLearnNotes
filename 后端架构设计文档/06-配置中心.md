# 配置中心架构设计

---

## 一、问题背景

### 1.1 为什么需要配置中心

在传统的单体应用时代，应用程序的配置通常以配置文件的形式（如 Java 中的 `application.properties`、`application.yml`）与代码一同打包部署。这种方式在应用规模较小、部署实例有限的情况下运作良好。然而，随着业务快速发展，系统架构从单体演进为微服务架构后，配置管理面临一系列根本性的挑战：

**1. 配置与代码强耦合，修改配置需重新发布**

在传统模式下，配置文件被打进 JAR/WAR 包中随应用一起部署。当需要修改一个数据库连接超时时间或调整线程池大小时，即使只改一个数字，也需要经历完整的"修改配置 → 构建 → 测试 → 发布"流程。对于频繁需要调整的运行时参数（如限流阈值、降级开关、灰度策略），这种方式效率极低，无法满足线上快速响应的需求。

```
传统配置修改流程（分钟级甚至小时级）：
修改代码/配置 → 提交代码 → CI构建 → 测试验证 → 审批发布 → 逐步灰度 → 全量上线
                                     ↑
                              仅仅为了改一个超时时间？
```

**2. 微服务架构下配置分散管理困难**

一个中大型互联网系统通常由数百甚至上千个微服务组成，每个微服务又部署了多个实例。假设系统有 200 个微服务，每个微服务部署 10 个实例，那么总共有 2000 个配置副本需要管理。如果每个微服务独立维护自己的配置文件，运维人员面临的挑战是：

- 如何保证 2000 个实例上的配置一致性？
- 如何快速定位某个实例的配置是否正确？
- 如何避免不同环境之间的配置混用（如测试环境误用生产数据库地址）？
- 公共配置（如中间件地址、通用超时设置）如何统一管理？

**3. 多环境配置管理混乱**

一个标准的交付流程通常涉及多套环境：开发环境（dev）、测试环境（test）、预发布环境（staging）、生产环境（prod）。每套环境的数据库地址、Redis 集群、消息队列地址、第三方服务 API Key 等都不同。在没有配置中心的情况下，开发者通常采用以下方式管理多环境配置：

```
# 方式一：通过 Spring Profile 区分配置文件
src/main/resources/
├── application.yml              # 通用配置
├── application-dev.yml          # 开发环境
├── application-test.yml         # 测试环境
├── application-staging.yml      # 预发布环境
└── application-prod.yml         # 生产环境

# 问题：生产环境的敏感配置（数据库密码、密钥）暴露在代码仓库中
# 问题：修改任何环境的配置都需要提交代码、重新构建
```

**4. 动态调参需求无法满足**

在大规模分布式系统的日常运维中，经常需要动态调整以下类型的配置，而这些调整不应该需要重启应用：

| 配置类型 | 典型场景 | 要求 |
|---------|---------|------|
| 功能开关（Feature Toggle） | 新功能灰度发布、快速回滚 | 秒级生效，按用户/区域灰度 |
| 降级开关 | 大促期间关闭非核心功能降低系统负载 | 秒级生效，一键切换 |
| 限流阈值 | 根据实时流量调整接口限流 QPS | 秒级生效，不重启 |
| 线程池参数 | 根据负载动态调整核心线程数 | 秒级生效，不重启 |
| 超时时间 | 下游服务响应变慢时调大超时阈值 | 秒级生效，不重启 |
| 日志级别 | 线上问题排查时临时开启 DEBUG 日志 | 秒级生效，不重启 |

**5. 配置漂移难以发现**

在手动管理配置的模式下，不同实例上的配置可能因为人为失误或部分发布失败而产生差异。这种"配置漂移"（Configuration Drift）往往在运行一段时间后才被发现，通常是在线上故障排查过程中，才发现某几台机器的配置与其他机器不一致。

### 1.2 配置中心的核心需求

一个生产级的配置中心需要满足以下核心需求：

| 需求维度 | 具体要求 | 优先级 |
|---------|---------|--------|
| 配置集中管理 | 所有应用的配置统一存储在配置中心，实现配置与代码的完全分离 | P0（必须） |
| 实时推送 | 配置变更后在秒级（通常 5 秒内）推送到所有客户端节点 | P0（必须） |
| 灰度发布 | 支持配置变更按 IP、百分比、分组等维度灰度发布 | P0（必须） |
| 版本管理 | 每次配置变更自动生成版本号，支持历史回溯和一键回滚 | P0（必须） |
| 高可用 | 配置中心本身不能成为系统单点故障，SLA 达到 99.99% 以上 | P0（必须） |
| 多环境隔离 | 支持 dev/test/staging/prod 等多环境的配置隔离 | P0（必须） |
| 权限控制 | 不同角色对配置拥有不同的读写权限，生产配置变更需审批 | P1（重要） |
| 变更审计 | 所有配置变更留下完整的审计日志，满足合规要求 | P1（重要） |
| 客户端容灾 | 配置中心不可用时，客户端能使用本地缓存继续运行 | P0（必须） |
| 最终一致性 | 配置变更最终推送到所有客户端，保证全局一致 | P0（必须） |

### 1.3 业界主流配置中心方案对比

在深入架构设计之前，先对业界主流的配置中心方案做一个整体对比：

| 维度 | Apollo | Nacos | Spring Cloud Config | ZooKeeper | etcd |
|------|--------|-------|---------------------|-----------|------|
| 开源方 | 携程 | 阿里巴巴 | Pivotal (Spring) | Apache | CNCF |
| 配置推送 | 长轮询 + 通知 | 长轮询 | Git Webhook + Bus | Watch 机制 | Watch 机制 |
| 推送时效 | 秒级 | 秒级 | 依赖 MQ 广播 | 实时 | 实时 |
| 灰度发布 | 支持（IP/标签） | 支持（Beta） | 不原生支持 | 不支持 | 不支持 |
| 版本管理 | 支持（Release） | 支持（历史版本） | 依赖 Git | 依赖 ZNode 版本 | 依赖 Revision |
| 管理界面 | 功能丰富 | 功能丰富 | 无（需额外开发） | 无 | 无 |

### 1.4 设计目标

本文将系统性地设计一个完整的配置中心架构方案，主要目标包括：

1. 深入剖析配置中心的核心架构，包括数据模型、推送机制、灰度发布等关键设计
2. 详细讲解长轮询（Long Polling）推送机制的服务端与客户端完整实现
3. 系统阐述配置灰度发布的策略设计与实现，包括按 IP、百分比、SET 等多维度灰度
4. 通过完整的 Java 代码示例展示每个核心模块的实现逻辑
5. 分析配置中心在高可用、容灾、一致性等方面的工程实践

## 二、整体架构设计

### 2.1 三层架构总览

配置中心采用经典的三层架构设计：**Admin Portal（管理门户）→ Config Server（配置服务端）→ Config Client SDK（客户端 SDK）**。各层职责清晰，通过标准协议通信。

### 2.2 各层核心职责

**Admin Portal（管理门户）：**

- 提供 Web 界面进行配置的增删改查操作
- 支持配置灰度发布、全量发布、版本回滚
- 提供配置变更审批流程
- 提供配置变更审计日志查询
- 支持多环境（Namespace）管理
- 支持权限控制（基于 RBAC 模型）

**Config Server（配置服务端）：**

- 配置数据的持久化存储与管理（基于 MySQL）
- 配置变更的检测与推送通知
- 处理客户端的配置拉取请求（全量拉取 / 增量拉取）
- 处理客户端的长轮询（Long Polling）请求
- 灰度发布的规则匹配与配置下发
- 服务端集群无状态设计，支持水平扩展

**Config Client SDK（客户端 SDK）：**

- 应用启动时从服务端拉取全量配置
- 通过长轮询机制监听配置变更
- 维护本地内存缓存，提供高性能的配置读取
- 维护本地文件缓存，作为服务端不可用时的容灾手段
- 提供配置变更监听器（Listener），支持应用响应配置变更
- 与 Spring Boot 等框架深度集成

### 2.3 配置数据流

```
配置发布流程：
运维人员 → Admin Portal → Config Server → 写入 MySQL
                                        → 写入 publish 表（变更事件）
                                        → 通知 Long Polling 等待的客户端

配置读取流程：
应用启动 → Client SDK → Config Server → 读取 MySQL → 返回配置
                     → 写入本地内存缓存
                     → 写入本地文件缓存
                     → 启动 Long Polling 监听

配置变更推送流程：
Config Server 检测到 publish 事件
  → 找到所有监听该配置的 Long Polling 连接
  → 立即返回响应，通知客户端有配置变更
  → 客户端收到通知后重新拉取最新配置
  → 更新内存缓存和文件缓存
  → 触发变更监听器回调
```

## 三、核心链路设计

### 3.1 配置数据模型

#### 3.1.1 配置层级结构

配置中心采用层次化的数据组织模型，从上到下分为：**Namespace（命名空间）→ Application（应用）→ Group（分组）→ Config Key（配置键）→ Config Value（配置值）**。

```
配置层级结构：

Namespace (命名空间 — 通常对应环境)
├── dev          开发环境
├── test         测试环境
├── staging      预发布环境
└── prod         生产环境
    ├── Application (应用)
    │   ├── order-service        订单服务
    │   ├── payment-service      支付服务
    │   └── user-service         用户服务
    │       ├── Group (分组 — 逻辑隔离)
    │       │   ├── default              默认分组
    │       │   ├── database             数据库配置组
    │       │   └── redis                Redis配置组
    │       │       ├── Config Key (配置键)
    │       │       │   ├── redis.host = 10.0.1.100
    │       │       │   ├── redis.port = 6379
    │       │       │   ├── redis.timeout = 3000
    │       │       │   └── redis.pool.maxActive = 200
    │       │       └── ...
    │       └── ...
    └── ...
```

这种层级结构的设计意图：

- **Namespace** 实现环境级别的隔离，确保不同环境的配置完全独立
- **Application** 实现应用级别的隔离，每个微服务管理自己的配置
- **Group** 实现同一应用下的配置分组，便于配置的逻辑归类
- **Config Key/Value** 是配置的最小粒度，每个 Key 对应一个值和版本号

#### 3.1.2 数据库表设计

配置中心的核心数据存储基于关系型数据库（MySQL），主要包含以下核心表：

```sql
-- 1. 配置主表：存储配置的当前生效值
CREATE TABLE config_item (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT,
    namespace_id    VARCHAR(64)     NOT NULL DEFAULT 'default'  COMMENT '命名空间ID',
    app_id          VARCHAR(128)    NOT NULL                     COMMENT '应用ID',
    group_id        VARCHAR(128)    NOT NULL DEFAULT 'DEFAULT_GROUP' COMMENT '分组ID',
    config_key      VARCHAR(256)    NOT NULL                     COMMENT '配置键',
    config_value    LONGTEXT                                     COMMENT '配置值',
    config_type     VARCHAR(16)     NOT NULL DEFAULT 'TEXT'      COMMENT '配置类型: TEXT/JSON/YAML/PROPERTIES',
    md5_value       VARCHAR(32)     NOT NULL                     COMMENT '配置值的MD5摘要',
    version         INT             NOT NULL DEFAULT 1           COMMENT '当前版本号（单调递增）',
    description     VARCHAR(512)                                 COMMENT '配置说明',
    is_deleted      TINYINT         NOT NULL DEFAULT 0           COMMENT '逻辑删除标记',
    gmt_create      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    gmt_modified    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    UNIQUE KEY uk_config (namespace_id, app_id, group_id, config_key),
    KEY idx_app_id (app_id),
    KEY idx_gmt_modified (gmt_modified)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配置主表';

-- 2. 配置发布表：记录每次发布事件，用于驱动推送通知
CREATE TABLE config_release (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT,
    namespace_id    VARCHAR(64)     NOT NULL                     COMMENT '命名空间ID',
    app_id          VARCHAR(128)    NOT NULL                     COMMENT '应用ID',
    group_id        VARCHAR(128)    NOT NULL DEFAULT 'DEFAULT_GROUP' COMMENT '分组ID',
    config_key      VARCHAR(256)    NOT NULL                     COMMENT '配置键',
    config_value    LONGTEXT                                     COMMENT '发布时的配置值',
    release_type    VARCHAR(16)     NOT NULL                     COMMENT '发布类型: NORMAL/GRAY/ROLLBACK',
    release_version INT             NOT NULL                     COMMENT '发布版本号',
    operator        VARCHAR(64)     NOT NULL                     COMMENT '操作人',
    release_desc    VARCHAR(512)                                 COMMENT '发布描述',
    gmt_create      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    KEY idx_app_config (app_id, config_key),
    KEY idx_gmt_create (gmt_create)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配置发布记录表';

-- 3. 配置历史表：记录每次变更的完整快照，用于审计和回滚
CREATE TABLE config_history (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT,
    namespace_id    VARCHAR(64)     NOT NULL,
    app_id          VARCHAR(128)    NOT NULL,
    group_id        VARCHAR(128)    NOT NULL,
    config_key      VARCHAR(256)    NOT NULL,
    old_value       LONGTEXT                                     COMMENT '变更前的值',
    new_value       LONGTEXT                                     COMMENT '变更后的值',
    old_version     INT                                          COMMENT '变更前的版本号',
    new_version     INT                                          COMMENT '变更后的版本号',
    change_type     VARCHAR(16)     NOT NULL                     COMMENT '变更类型: CREATE/UPDATE/DELETE/ROLLBACK',
    operator        VARCHAR(64)     NOT NULL                     COMMENT '操作人',
    client_ip       VARCHAR(64)                                  COMMENT '操作人IP',
    gmt_create      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    KEY idx_app_config (app_id, config_key),
    KEY idx_operator (operator),
    KEY idx_gmt_create (gmt_create)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配置变更历史表';

-- 4. 灰度规则表：记录灰度发布的规则
CREATE TABLE config_gray_rule (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT,
    namespace_id    VARCHAR(64)     NOT NULL,
    app_id          VARCHAR(128)    NOT NULL,
    group_id        VARCHAR(128)    NOT NULL,
    config_key      VARCHAR(256)    NOT NULL,
    gray_name       VARCHAR(128)    NOT NULL                     COMMENT '灰度名称',
    gray_type       VARCHAR(16)     NOT NULL                     COMMENT '灰度类型: IP/PERCENTAGE/SET/SET_PERCENTAGE',
    gray_rule       TEXT            NOT NULL                     COMMENT '灰度规则（JSON格式）',
    gray_value      LONGTEXT        NOT NULL                     COMMENT '灰度配置值',
    gray_version    INT             NOT NULL                     COMMENT '灰度版本号',
    status          TINYINT         NOT NULL DEFAULT 1           COMMENT '状态: 1=生效 0=失效',
    operator        VARCHAR(64)     NOT NULL,
    gmt_create      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    gmt_modified    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    KEY idx_app_config (app_id, config_key),
    KEY idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='灰度发布规则表';

-- 5. 配置推送事件表：用于驱动服务端检测变更并通知客户端
CREATE TABLE config_publish_event (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT,
    namespace_id    VARCHAR(64)     NOT NULL,
    app_id          VARCHAR(128)    NOT NULL,
    group_id        VARCHAR(128)    NOT NULL,
    config_key      VARCHAR(256)    NOT NULL,
    event_type      VARCHAR(16)     NOT NULL                     COMMENT '事件类型: PUBLISH/GRAY_PUBLISH/ROLLBACK',
    publish_version INT             NOT NULL                     COMMENT '发布版本号',
    operator        VARCHAR(64)     NOT NULL,
    gmt_create      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    KEY idx_gmt_create (gmt_create)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配置推送事件表';
```

#### 3.1.3 配置数据模型 Java 实体

```java
/**
 * 配置项实体
 */
public class ConfigItem {
    private Long id;
    private String namespaceId;
    private String appId;
    private String groupId;
    private String configKey;
    private String configValue;
    private String configType;  // TEXT, JSON, YAML, PROPERTIES
    private String md5Value;
    private int version;
    private String description;
    private Date gmtCreate;
    private Date gmtModified;
    
    /**
     * 生成配置唯一标识
     */
    public String buildConfigId() {
        return namespaceId + ":" + appId + ":" + groupId + ":" + configKey;
    }
    
    /**
     * 计算配置值的 MD5 摘要
     */
    public String calculateMd5() {
        if (configValue == null || configValue.isEmpty()) {
            return "";
        }
        return DigestUtils.md5DigestAsHex(configValue.getBytes(StandardCharsets.UTF_8));
    }
    
    // getter/setter 省略
}

 * 配置发布记录

    private String grayRule;   // JSON: {"ips":["10.0.1.1","10.0.1.2"]} 或 {"percentage":10}
    private String grayValue;  // 灰度配置值
    private int grayVersion;
    private int status;
    private String operator;
```

### 3.2 配置推送机制

配置推送机制是配置中心最核心的技术环节，它决定了配置变更后客户端获取最新配置的时效性和可靠性。业界主流方案包括 Pull（客户端拉取）、Push（服务端推送）、Long Polling（长轮询）、Watch（监听）四种模式。

#### 3.2.1 Pull 模型（客户端定时轮询）

**基本原理：** 客户端启动一个定时任务，每隔固定时间间隔向服务端发起 HTTP 请求，检查配置是否有变更。

```
┌──────────┐                        ┌──────────┐
│  Client  │                        │  Server  │
└────┬─────┘                        └────┬─────┘
     │                                   │
     │  GET /config?version=1            │
     │ ────────────────────────────────> │
     │                                   │
     │  200 OK (version=1, no change)    │
     │ <──────────────────────────────── │
     │                                   │
     │  ... 等待 30 秒 ...               │
     │                                   │
     │  GET /config?version=1            │
     │ ────────────────────────────────> │
     │                                   │
     │  200 OK (version=2, new config)   │
     │ <──────────────────────────────── │
     │                                   │
```

```java
/**
 * Pull 模型 - 客户端定时轮询（简单但有明显缺陷）
 */
public class PullConfigClient {
    
    private final String serverUrl;
    private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
    private final Map<String, String> localConfigCache = new ConcurrentHashMap<>();
    private final Map<String, Integer> configVersions = new ConcurrentHashMap<>();
    
    public PullConfigClient(String serverUrl) {
        this.serverUrl = serverUrl;
    }
    
    /**
     * 启动定时拉取
     */
    public void start() {
        // 每 30 秒拉取一次
        scheduler.scheduleAtFixedRate(this::pullConfig, 0, 30, TimeUnit.SECONDS);
    }
    
    private void pullConfig() {
        try {
            String url = serverUrl + "/api/config/list?appId=order-service";
            HttpResponse response = HttpClient.newHttpClient()
                .send(HttpRequest.newBuilder(URI.create(url)).GET().build(),
                      HttpResponse.BodyHandlers.ofString());
            
            if (response.statusCode() == 200) {
                List<ConfigItem> configs = JSON.parseArray(response.body(), ConfigItem.class);
                for (ConfigItem config : configs) {
                    Integer oldVersion = configVersions.get(config.getConfigKey());
                    if (oldVersion == null || config.getVersion() > oldVersion) {
                        String oldValue = localConfigCache.get(config.getConfigKey());
                        localConfigCache.put(config.getConfigKey(), config.getConfigValue());
                        configVersions.put(config.getConfigKey(), config.getVersion());
                        
                        // 触发变更通知
                        fireConfigChanged(config.getConfigKey(), oldValue, config.getConfigValue());
                    }
                }
            }
        } catch (Exception e) {
            log.warn("Pull config failed, will retry next interval", e);
        }
    }
}
```

**Pull 模型的优缺点：**

| 维度 | 说明 |
|------|------|
| 优点 | 实现简单，客户端主动拉取，服务端无状态 |
| 缺点-时效性 | 配置变更的感知延迟 = 轮询间隔/2（平均），30秒轮询意味着平均15秒延迟 |
| 缺点-资源浪费 | 绝大多数轮询请求返回"无变更"，浪费带宽和服务端资源 |
| 缺点-不可调和 | 缩短轮询间隔提升时效 → 服务端压力线性增长；加大间隔降低压力 → 时效性更差 |

#### 3.2.2 Push 模型（服务端主动推送）

**基本原理：** 服务端与客户端之间建立长连接（TCP 长连接或 WebSocket），当配置变更时，服务端主动将变更推送给所有订阅了该配置的客户端。

```
┌──────────┐                        ┌──────────┐
│  Client  │                        │  Server  │
└────┬─────┘                        └────┬─────┘
     │                                   │
     │  建立 WebSocket 连接               │
     │ ────────────────────────────────> │
     │                                   │
     │  连接建立成功                       │
     │ <──────────────────────────────── │
     │                                   │
     │       （长时间空闲，无通信）         │
     │                                   │
     │                    配置发生变更 →   │
     │                                   │
     │  PUSH: config changed (key=xxx)   │
     │ <──────────────────────────────── │
     │                                   │
```

**Push 模型的优缺点：**

| 维度 | 说明 |
|------|------|
| 优点 | 实时性好，配置变更后立即推送，延迟极低（毫秒级） |
| 优点 | 无无效请求，只在有变更时才通信 |
| 缺点-连接管理 | 服务端需要维护与所有客户端的长连接，内存和文件描述符开销大 |
| 缺点-扩展性 | 数十万客户端意味着数十万长连接，服务端扩展难度大 |
| 缺点-可靠性 | 网络闪断、客户端重启等场景下，推送消息可能丢失 |
| 缺点-复杂性 | 需要额外的心跳保活、断线重连、消息确认等机制 |

#### 3.2.3 长轮询模型（Long Polling）—— 生产首选方案

长轮询是 Pull 和 Push 的折中方案，也是 Apollo、Nacos 等主流配置中心采用的推送机制。它的核心思想是：**客户端发起 HTTP 请求后，如果服务端没有配置变更，不立即返回，而是将请求挂起（Hold）一段时间（通常 30 秒）；在挂起期间如果配置发生了变更，服务端立即返回通知客户端。**

```
场景一：挂起期间配置发生变更 —— 立即响应

┌──────────┐                              ┌──────────┐
│  Client  │                              │  Server  │
└────┬─────┘                              └────┬─────┘
     │                                         │
     │  POST /config/listen                    │
     │  Body: {configs: [{key:"db.url",        │
     │         md5:"abc123"}]}                 │
     │ ──────────────────────────────────────> │
     │                                         │
     │       Server 对比 MD5，无变更，挂起请求    │
     │                                         │
     │       ... 等待 10 秒 ...                 │
     │                                         │
     │                 运维人员修改了 db.url →   │
     │                 Server 检测到变更         │
     │                                         │
     │  200 OK: {changedKeys: ["db.url"]}      │
     │ <────────────────────────────────────── │  ← 立即响应！
     │                                         │
     │  GET /config?key=db.url                 │
     │ ──────────────────────────────────────> │  ← 客户端拉取最新值
     │                                         │
     │  200 OK: {value: "jdbc:mysql://new.."}  │
     │ <────────────────────────────────────── │
     │                                         │
     │  POST /config/listen  (重新发起长轮询)    │
     │ ──────────────────────────────────────> │
     │                                         │


场景二：挂起期间无变更 —— 超时返回

┌──────────┐                              ┌──────────┐
│  Client  │                              │  Server  │
└────┬─────┘                              └────┬─────┘
     │                                         │
     │  POST /config/listen                    │
     │  Body: {configs: [{key:"db.url",        │
     │         md5:"abc123"}]}                 │
     │ ──────────────────────────────────────> │
     │                                         │
     │       Server 对比 MD5，无变更，挂起请求    │
     │                                         │
     │       ... 等待 30 秒（超时） ...          │
     │                                         │
     │  304 Not Modified                       │
     │ <────────────────────────────────────── │  ← 超时返回
     │                                         │
     │  POST /config/listen  (立即重新发起)      │
     │ ──────────────────────────────────────> │
     │                                         │
```

**长轮询的核心算法步骤：**

1. 客户端发起 HTTP 请求，携带当前持有的配置键及其 MD5 摘要列表
2. 服务端收到请求后，逐一比较客户端的 MD5 与服务端最新配置的 MD5
3. 如果存在 MD5 不匹配的配置项（即有变更），立即返回变更列表
4. 如果所有 MD5 都匹配（即无变更），将该请求挂起，加入等待队列
5. 挂起期间，如果有配置发布事件，服务端从等待队列中找到关联的请求并立即响应
6. 挂起超过 30 秒，返回 304 表示无变更
7. 客户端无论收到哪种响应，都立即重新发起下一轮长轮询

**服务端完整实现：**

```java
/**
 * 配置长轮询控制器 —— 服务端核心实现
 * 
 * 核心机制：使用 Servlet 3.0 的 AsyncContext（或 Spring 的 DeferredResult）
 * 实现请求的异步挂起和唤醒，避免阻塞 Tomcat 工作线程。
 */
@RestController
@RequestMapping("/api/config")
public class ConfigLongPollingController {
    
    private static final Logger log = LoggerFactory.getLogger(ConfigLongPollingController.class);
    
    /**
     * 长轮询超时时间：30 秒
     * 实际设置为 29.5 秒，预留 0.5 秒给响应传输，确保客户端不会因为 HTTP 超时而断开
     */
    private static final long LONG_POLLING_TIMEOUT_MS = 29500L;
    
    /**
     * 挂起的客户端连接池
     * Key: configId (namespace:app:group:key)
     * Value: 所有监听该配置的客户端连接
     */
    private final ConcurrentHashMap<String, CopyOnWriteArrayList<LongPollingClient>> 
        holdingClients = new ConcurrentHashMap<>();
    
    /**
     * 超时调度线程池 —— 用于在超时后自动响应挂起的请求
     */
    private final ScheduledExecutorService timeoutScheduler = 
        Executors.newScheduledThreadPool(4, r -> {
            Thread t = new Thread(r, "config-longpoll-timeout");
            t.setDaemon(true);
            return t;
        });
    
    @Autowired
    private ConfigService configService;
    
    /**
     * 长轮询接口 —— 客户端发起监听请求
     * 
     * @param request 客户端当前持有的配置 MD5 列表
     * @return DeferredResult 异步结果
     */
    @PostMapping("/listen")
    public DeferredResult<ResponseEntity<LongPollingResponse>> listen(
            @RequestBody LongPollingRequest request,
            HttpServletRequest httpRequest) {
        
        String clientIp = getClientIp(httpRequest);
        log.info("Long polling request from client: {}, app: {}, configs: {}", 
                 clientIp, request.getAppId(), request.getConfigs().size());
        
        // 创建 DeferredResult，设置超时时间
        DeferredResult<ResponseEntity<LongPollingResponse>> deferredResult = 
            new DeferredResult<>(LONG_POLLING_TIMEOUT_MS);
        
        // ========== Step 1: 立即检查是否已有变更 ==========
        List<String> changedKeys = checkChangedConfigs(request);
        
        if (!changedKeys.isEmpty()) {
            // 有变更，立即返回
            log.info("Config changed detected immediately for client: {}, changedKeys: {}", 
                     clientIp, changedKeys);
            LongPollingResponse response = new LongPollingResponse();
            response.setChangedKeys(changedKeys);
            response.setHasChange(true);
            deferredResult.setResult(ResponseEntity.ok(response));
            return deferredResult;
        }
        
        // ========== Step 2: 无变更，挂起请求 ==========
        LongPollingClient client = new LongPollingClient(
            clientIp, request.getAppId(), request, deferredResult
        );
        
        // 将客户端注册到每个监听的配置项
        for (ConfigDigest config : request.getConfigs()) {
            String configId = buildConfigId(request.getNamespaceId(), 
                                            request.getAppId(), 
                                            config.getGroupId(), 
                                            config.getConfigKey());
            holdingClients.computeIfAbsent(configId, k -> new CopyOnWriteArrayList<>())
                          .add(client);
        }
        
        // ========== Step 3: 设置超时回调 ==========
        ScheduledFuture<?> timeoutFuture = timeoutScheduler.schedule(() -> {
            // 超时后返回 304 Not Modified
            if (!deferredResult.isSetOrExpired()) {
                log.debug("Long polling timeout for client: {}", clientIp);
                LongPollingResponse response = new LongPollingResponse();
                response.setHasChange(false);
                response.setChangedKeys(Collections.emptyList());
                deferredResult.setResult(ResponseEntity.status(HttpStatus.NOT_MODIFIED).body(response));
            }
            // 清理已超时的客户端连接
            removeClient(client, request);
        }, LONG_POLLING_TIMEOUT_MS, TimeUnit.MILLISECONDS);
        
        client.setTimeoutFuture(timeoutFuture);
        
        // ========== Step 4: 设置完成回调（正常响应或超时后清理资源） ==========
        deferredResult.onCompletion(() -> {
            removeClient(client, request);
        });
        
        deferredResult.onTimeout(() -> {
            log.debug("DeferredResult timeout for client: {}", clientIp);
            removeClient(client, request);
        });
        
        return deferredResult;
    }
    
    /**
     * 当配置发布时，唤醒所有监听该配置的长轮询客户端
     * 
     * 此方法由配置发布服务调用
     */
    public void notifyConfigChanged(String namespaceId, String appId, 
                                     String groupId, String configKey) {
        String configId = buildConfigId(namespaceId, appId, groupId, configKey);
        
        CopyOnWriteArrayList<LongPollingClient> clients = holdingClients.get(configId);
        if (clients == null || clients.isEmpty()) {
            log.info("No holding clients for config: {}", configId);
            return;
        }
        
        log.info("Notifying {} clients for config change: {}", clients.size(), configId);
        
        // 创建客户端列表的快照，避免并发修改
        List<LongPollingClient> clientsSnapshot = new ArrayList<>(clients);
        
        for (LongPollingClient client : clientsSnapshot) {
            try {
                DeferredResult<ResponseEntity<LongPollingResponse>> deferredResult = 
                    client.getDeferredResult();
                
                if (deferredResult != null && !deferredResult.isSetOrExpired()) {
                    // 取消超时任务
                    if (client.getTimeoutFuture() != null) {
                        client.getTimeoutFuture().cancel(false);
                    }
                    
                    // 立即响应客户端
                    LongPollingResponse response = new LongPollingResponse();
                    response.setHasChange(true);
                    response.setChangedKeys(Collections.singletonList(configKey));
                    deferredResult.setResult(ResponseEntity.ok(response));
                    
                    log.info("Notified client {} for config change: {}", 
                             client.getClientIp(), configId);
                }
            } catch (Exception e) {
                log.warn("Failed to notify client: {}", client.getClientIp(), e);
            }
        }
        
        // 清理已通知的客户端
        clients.removeAll(clientsSnapshot);
    }
    
    /**
     * 检查客户端持有的配置是否已发生变更
     */
    private List<String> checkChangedConfigs(LongPollingRequest request) {
        List<String> changedKeys = new ArrayList<>();
        
        for (ConfigDigest clientConfig : request.getConfigs()) {
            // 从数据库（或服务端缓存）获取最新配置的 MD5
            ConfigItem serverConfig = configService.getConfig(
                request.getNamespaceId(), 
                request.getAppId(),
                clientConfig.getGroupId(), 
                clientConfig.getConfigKey()
            );
            
            if (serverConfig != null && !serverConfig.getMd5Value().equals(clientConfig.getMd5())) {
                changedKeys.add(clientConfig.getConfigKey());
            }
        }
        
        return changedKeys;
    }
    
    /**
     * 从等待队列中移除客户端
     */
    private void removeClient(LongPollingClient client, LongPollingRequest request) {
        for (ConfigDigest config : request.getConfigs()) {
            String configId = buildConfigId(request.getNamespaceId(), 
                                            request.getAppId(),
                                            config.getGroupId(), 
                                            config.getConfigKey());
            CopyOnWriteArrayList<LongPollingClient> clients = holdingClients.get(configId);
            if (clients != null) {
                clients.remove(client);
            }
        }
    }
    
    private String buildConfigId(String namespace, String app, String group, String key) {
        return namespace + ":" + app + ":" + group + ":" + key;
    }
    
    private String getClientIp(HttpServletRequest request) {
        String ip = request.getHeader("X-Forwarded-For");
        if (ip == null || ip.isEmpty()) {
            ip = request.getRemoteAddr();
        }
        return ip;
    }
}
```

**客户端完整实现：**

```java
/**
 * 配置中心客户端 SDK —— 长轮询核心实现
 * 
 * 职责：
 * 1. 应用启动时从服务端拉取全量配置
 * 2. 通过长轮询持续监听配置变更
 * 3. 维护本地内存缓存和文件缓存
 * 4. 提供配置变更监听器机制
 */
public class ConfigClient {
    
    private static final Logger log = LoggerFactory.getLogger(ConfigClient.class);
    
    /** 长轮询 HTTP 超时时间，需比服务端 Hold 时间长（30s + 5s 余量） */
    private static final int LONG_POLLING_READ_TIMEOUT_MS = 35000;
    
    /** 长轮询失败后的重试间隔 */
    private static final long RETRY_INTERVAL_MS = 3000L;
    
    /** 服务端地址列表（支持多个，容灾切换） */
    private final List<String> serverUrls;
    private final String namespaceId;
    private final String appId;
    
    /** 本地内存缓存：key -> value */
    private final ConcurrentHashMap<String, String> configCache = new ConcurrentHashMap<>();
    
    /** 本地配置 MD5 缓存：key -> md5 */
    private final ConcurrentHashMap<String, String> configMd5Cache = new ConcurrentHashMap<>();
    
    /** 配置变更监听器列表：key -> listeners */
    private final ConcurrentHashMap<String, List<ConfigChangeListener>> listeners = new ConcurrentHashMap<>();
    
    /** 长轮询专用线程 */
    private final ExecutorService longPollingExecutor = Executors.newSingleThreadExecutor(
        r -> new Thread(r, "config-longpoll-worker")
    );
    
    /** 监听器回调专用线程池（避免阻塞长轮询线程） */
    private final ExecutorService listenerExecutor = Executors.newFixedThreadPool(4,
        r -> new Thread(r, "config-listener-callback")
    );
    
    /** 本地文件缓存目录 */
    private final String localCacheDir;
    
    /** 运行标记 */
    private volatile boolean running = false;
    
    /** HTTP 客户端 */
    private final OkHttpClient httpClient;
    
    public ConfigClient(List<String> serverUrls, String namespaceId, String appId) {
        this.serverUrls = serverUrls;
        this.namespaceId = namespaceId;
        this.appId = appId;
        this.localCacheDir = System.getProperty("user.home") + 
                             "/.config-client/cache/" + namespaceId + "/" + appId;
        
        this.httpClient = new OkHttpClient.Builder()
            .connectTimeout(5, TimeUnit.SECONDS)
            .readTimeout(LONG_POLLING_READ_TIMEOUT_MS, TimeUnit.MILLISECONDS)
            .writeTimeout(5, TimeUnit.SECONDS)
            .build();
    }
    
    /**
     * 启动客户端
     */
    public void start() {
        log.info("ConfigClient starting, namespace: {}, appId: {}", namespaceId, appId);
        
        // Step 1: 尝试从本地文件缓存加载配置（快速启动）
        loadLocalCache();
        
        // Step 2: 从服务端拉取全量配置
        try {
            pullFullConfig();
            log.info("Pull full config success, total keys: {}", configCache.size());
        } catch (Exception e) {
            log.warn("Pull full config failed, using local cache. Error: {}", e.getMessage());
            // 如果服务端不可用，使用本地缓存继续启动
        }
        
        // Step 3: 启动长轮询
        running = true;
        longPollingExecutor.submit(this::longPollingLoop);
        
        log.info("ConfigClient started successfully");
    }
    
    /**
     * 停止客户端
     */
    public void shutdown() {
        running = false;
        longPollingExecutor.shutdownNow();
        listenerExecutor.shutdownNow();
        log.info("ConfigClient shutdown");
    }
    
    /**
     * 获取配置值
     */
    public String getConfig(String key) {
        return configCache.get(key);
    }
    
    /**
     * 获取配置值，带默认值
     */
    public String getConfig(String key, String defaultValue) {
        return configCache.getOrDefault(key, defaultValue);
    }
    
    /**
     * 获取 int 类型配置
     */
    public int getIntConfig(String key, int defaultValue) {
        String value = configCache.get(key);
        if (value == null) return defaultValue;
        try {
            return Integer.parseInt(value.trim());
        } catch (NumberFormatException e) {
            return defaultValue;
        }
    }
    
    /**
     * 获取 boolean 类型配置
     */
    public boolean getBooleanConfig(String key, boolean defaultValue) {
        String value = configCache.get(key);
        if (value == null) return defaultValue;
        return Boolean.parseBoolean(value.trim());
    }
    
    /**
     * 注册配置变更监听器
     */
    public void addListener(String key, ConfigChangeListener listener) {
        listeners.computeIfAbsent(key, k -> new CopyOnWriteArrayList<>()).add(listener);
    }
    
    /**
     * 从服务端拉取全量配置
     */
    private void pullFullConfig() throws IOException {
        String url = selectServer() + "/api/config/list" +
                     "?namespaceId=" + namespaceId + "&appId=" + appId;
        
        Request request = new Request.Builder().url(url).get().build();
        
        try (Response response = httpClient.newCall(request).execute()) {
            if (response.isSuccessful() && response.body() != null) {
                String body = response.body().string();
                List<ConfigItem> configs = JSON.parseArray(body, ConfigItem.class);
                
                for (ConfigItem config : configs) {
                    configCache.put(config.getConfigKey(), config.getConfigValue());
                    configMd5Cache.put(config.getConfigKey(), config.getMd5Value());
                }
                
                // 持久化到本地文件
                saveLocalCache();
            } else {
                throw new IOException("Pull config failed, status: " + response.code());
            }
        }
    }
    
    /**
     * 长轮询主循环 —— 核心逻辑
     */
    private void longPollingLoop() {
        while (running) {
            try {
                doLongPolling();
            } catch (Exception e) {
                if (running) {
                    log.warn("Long polling error: {}, will retry after {}ms", 
                             e.getMessage(), RETRY_INTERVAL_MS);
                    try {
                        Thread.sleep(RETRY_INTERVAL_MS);
                    } catch (InterruptedException ie) {
                        Thread.currentThread().interrupt();
                        break;
                    }
                }
            }
        }
    }
    
    /**
     * 执行一次长轮询
     */
    private void doLongPolling() throws IOException {
        // 构建请求：将当前持有的配置 MD5 列表发送给服务端
        LongPollingRequest pollRequest = new LongPollingRequest();
        pollRequest.setNamespaceId(namespaceId);
        pollRequest.setAppId(appId);
        
        List<ConfigDigest> configDigests = new ArrayList<>();
        for (Map.Entry<String, String> entry : configMd5Cache.entrySet()) {
            ConfigDigest digest = new ConfigDigest();
            digest.setGroupId("DEFAULT_GROUP");
            digest.setConfigKey(entry.getKey());
            digest.setMd5(entry.getValue());
            configDigests.add(digest);
        }
        pollRequest.setConfigs(configDigests);
        
        String url = selectServer() + "/api/config/listen";
        String requestBody = JSON.toJSONString(pollRequest);
        
        Request httpRequest = new Request.Builder()
            .url(url)
            .post(RequestBody.create(requestBody, MediaType.parse("application/json")))
            .build();
        
        try (Response response = httpClient.newCall(httpRequest).execute()) {
            if (response.code() == 200 && response.body() != null) {
                String body = response.body().string();
                LongPollingResponse pollResponse = JSON.parseObject(body, LongPollingResponse.class);
                
                if (pollResponse.isHasChange() && pollResponse.getChangedKeys() != null) {
                    log.info("Config changed detected: {}", pollResponse.getChangedKeys());
                    
                    // 拉取变更的配置
                    for (String changedKey : pollResponse.getChangedKeys()) {
                        pullSingleConfig(changedKey);
                    }
                }
            }
            // 304 Not Modified 表示无变更，继续下一轮
        }
    }
    
    /**
     * 拉取单个配置的最新值
     */
    private void pullSingleConfig(String configKey) {
        try {
            String url = selectServer() + "/api/config/get" +
                         "?namespaceId=" + namespaceId + 
                         "&appId=" + appId + 
                         "&key=" + configKey;
            
            Request request = new Request.Builder().url(url).get().build();
            
            try (Response response = httpClient.newCall(request).execute()) {
                if (response.isSuccessful() && response.body() != null) {
                    ConfigItem config = JSON.parseObject(response.body().string(), ConfigItem.class);
                    
                    String oldValue = configCache.get(configKey);
                    String newValue = config.getConfigValue();
                    
                    // 更新内存缓存
                    configCache.put(configKey, newValue);
                    configMd5Cache.put(configKey, config.getMd5Value());
                    
                    // 持久化到本地文件
                    saveLocalCache();
                    
                    // 触发监听器回调
                    fireConfigChanged(configKey, oldValue, newValue);
                    
                    log.info("Config updated: key={}, version={}", configKey, config.getVersion());
                }
            }
        } catch (Exception e) {
            log.error("Pull single config failed: key={}", configKey, e);
        }
    }
    
    /**
     * 触发配置变更监听器
     */
    private void fireConfigChanged(String key, String oldValue, String newValue) {
        List<ConfigChangeListener> keyListeners = listeners.get(key);
        if (keyListeners == null || keyListeners.isEmpty()) {
            return;
        }
        
        ConfigChangeEvent event = new ConfigChangeEvent(key, oldValue, newValue);
        
        for (ConfigChangeListener listener : keyListeners) {
            // 在独立线程池中执行回调，避免阻塞长轮询线程
            listenerExecutor.submit(() -> {
                try {
                    listener.onConfigChanged(event);
                } catch (Exception e) {
                    log.error("Config change listener error: key={}, listener={}", 
                              key, listener.getClass().getName(), e);
                }
            });
        }
    }
    
    /**
     * 加载本地文件缓存
     */
    private void loadLocalCache() {
        File cacheFile = new File(localCacheDir, "config-cache.json");
        if (!cacheFile.exists()) {
            return;
        }
        
        try {
            String content = new String(Files.readAllBytes(cacheFile.toPath()), StandardCharsets.UTF_8);
            Map<String, String> cachedConfigs = JSON.parseObject(content, 
                new TypeReference<Map<String, String>>() {});
            
            if (cachedConfigs != null) {
                configCache.putAll(cachedConfigs);
                // 重新计算 MD5
                for (Map.Entry<String, String> entry : cachedConfigs.entrySet()) {
                    String md5 = DigestUtils.md5DigestAsHex(
                        entry.getValue().getBytes(StandardCharsets.UTF_8));
                    configMd5Cache.put(entry.getKey(), md5);
                }
                log.info("Loaded {} configs from local cache", cachedConfigs.size());
            }
        } catch (Exception e) {
            log.warn("Load local cache failed", e);
        }
    }
    
    /**
     * 保存配置到本地文件缓存
     */
    private void saveLocalCache() {
        try {
            File cacheDir = new File(localCacheDir);
            if (!cacheDir.exists()) {
                cacheDir.mkdirs();
            }
            
            File cacheFile = new File(cacheDir, "config-cache.json");
            String content = JSON.toJSONString(configCache, SerializerFeature.PrettyFormat);
            Files.write(cacheFile.toPath(), content.getBytes(StandardCharsets.UTF_8));
            
            log.debug("Saved {} configs to local cache", configCache.size());
        } catch (Exception e) {
            log.warn("Save local cache failed", e);
        }
    }
    
    /**
     * 选择可用的服务端地址（简单轮询）
     */
    private String selectServer() {
        int index = ThreadLocalRandom.current().nextInt(serverUrls.size());
        return serverUrls.get(index);
    }
}
```

#### 3.2.4 Watch 机制

ZooKeeper 和 etcd 等分布式协调服务提供了原生的 Watch 机制，可以用于实现配置变更的实时通知。

**ZooKeeper Watch 模式：**

```java
/**
 * 基于 ZooKeeper Watch 的配置监听
 * 
 * 注意：ZooKeeper 的 Watch 是一次性的，触发后需要重新注册
 */
public class ZkConfigWatcher {
    
    private final CuratorFramework zkClient;
    private final String configBasePath = "/config";
    private final Map<String, String> configCache = new ConcurrentHashMap<>();
    
    public ZkConfigWatcher(String zkAddress) {
        this.zkClient = CuratorFrameworkFactory.builder()
            .connectString(zkAddress)
            .sessionTimeoutMs(30000)
            .connectionTimeoutMs(10000)
            .retryPolicy(new ExponentialBackoffRetry(1000, 3))
            .build();
        zkClient.start();
    }
    
    /**
     * 监听某个配置键
     */
    public void watchConfig(String appId, String key, ConfigChangeListener listener) 
            throws Exception {
        String path = configBasePath + "/" + appId + "/" + key;
        
        // 使用 Curator 的 NodeCache 自动重复注册 Watch
        NodeCache nodeCache = new NodeCache(zkClient, path);
        nodeCache.getListenable().addListener(() -> {
            ChildData currentData = nodeCache.getCurrentData();
            if (currentData != null) {
                String newValue = new String(currentData.getData(), StandardCharsets.UTF_8);
                String oldValue = configCache.put(key, newValue);
                listener.onConfigChanged(new ConfigChangeEvent(key, oldValue, newValue));
            }
        });
        nodeCache.start(true);
    }
}
```

**Watch 机制的局限：**

| 局限 | 说明 |
|------|------|
| ZK Watch 一次性 | 原生 Watch 触发后失效，需重新注册，存在窗口期丢失事件的风险 |
| ZK 不适合大量数据 | ZK 的 ZNode 数据限制为 1MB，且所有数据存于内存，不适合存储大量配置 |
| etcd Watch 复杂性 | etcd Watch 需要处理 Compaction 导致的 revision 失效问题 |
| 运维复杂度 | 依赖 ZK/etcd 集群的稳定性，增加了运维成本 |

**各推送机制对比总结：**

| 维度 | Pull | Push | Long Polling | Watch (ZK/etcd) |
|------|------|------|-------------|-----------------|
| 实时性 | 差（分钟级） | 好（毫秒级） | 好（秒级） | 好（毫秒级） |
| 服务端复杂度 | 低 | 高 | 中 | 中（依赖外部组件） |
| 连接管理 | 无 | 需维护长连接 | HTTP 短连接 | 长连接 |
| 可靠性 | 高 | 中（推送可能丢失） | 高 | 中（Watch 可能丢失） |
| 可扩展性 | 好 | 差 | 好 | 中 |
| 典型使用方 | 简单场景 | 消息推送系统 | Apollo/Nacos | ZK/etcd 配置 |

### 3.3 配置灰度发布

灰度发布（Gray Release / Canary Release）是配置中心的核心能力之一。它允许运维人员在正式全量发布前，将配置变更先下发到部分客户端实例，观察效果后再决定全量推广还是回滚。

#### 3.3.1 灰度发布类型

配置中心支持以下四种灰度发布策略：

```
灰度发布策略：

1. 按 IP 列表灰度
   ┌───────────────────────────┐
   │  Master Config: value=A   │
   │                           │
   │  10.0.1.1 ──── value=A   │
   │  10.0.1.2 ──── value=B ← │── 灰度 IP
   │  10.0.1.3 ──── value=B ← │── 灰度 IP
   │  10.0.1.4 ──── value=A   │
   │  10.0.1.5 ──── value=A   │
   └───────────────────────────┘

2. 按百分比灰度
   ┌───────────────────────────┐
   │  100 台实例，灰度 20%       │
   │                           │
   │  ████████████████████░░░░ │
   │  ←── 20台灰度 ──→│← 80台 →│
   │    value = B       value=A│
   └───────────────────────────┘

3. 按 SET 分组灰度
   ┌───────────────────────────┐
   │  SET-BJ (北京) ── value=B │ ← 灰度 SET
   │  SET-SH (上海) ── value=A │
   │  SET-GZ (广州) ── value=A │
   └───────────────────────────┘

4. 按 SET + 百分比灰度
   ┌───────────────────────────┐
   │  SET-BJ (50台)             │
   │    灰度 20% ── 10台 value=B│
   │    其余 80% ── 40台 value=A│
   │  SET-SH ── 全部 value=A   │
   └───────────────────────────┘
```

#### 3.3.2 灰度发布工作流

完整的灰度发布包含以下步骤：

```
灰度发布完整工作流：

Step 1: 创建灰度规则
运维人员 → Admin Portal → 选择灰度类型 → 配置灰度规则（IP列表/百分比/SET）
                       → 填写灰度配置值
                       → 提交审批

Step 2: 灰度发布
审批通过 → Config Server 写入灰度规则表
        → 写入 publish 事件（类型=GRAY_PUBLISH）
        → 通知所有长轮询客户端

Step 3: 客户端灰度配置解析
客户端收到变更通知 → 拉取最新配置 + 灰度规则
                  → 判断自身是否命中灰度规则
                  → 命中：使用灰度配置值
                  → 未命中：继续使用 Master 配置值

Step 4: 观察灰度效果
运维人员观察灰度实例的运行状况（监控指标、日志、告警）
  → 正常：执行全量发布（Step 5a）
  → 异常：执行灰度回滚（Step 5b）

Step 5a: 全量发布
灰度配置值提升为 Master 配置值 → 删除灰度规则
→ 写入 publish 事件（类型=NORMAL）
→ 所有客户端获取到新的 Master 配置

Step 5b: 灰度回滚
删除灰度规则 → 灰度实例回退到 Master 配置值
→ 写入 publish 事件（类型=ROLLBACK）
→ 灰度实例恢复原配置
```

#### 3.3.3 灰度规则匹配与配置解析

```java
/**
 * 灰度规则匹配引擎
 * 
 * 配置解析优先级：灰度配置 > Master 配置
 * 即客户端命中灰度规则时，使用灰度配置值；否则使用 Master 配置值。
 */
public class GrayRuleEngine {
    
    private static final Logger log = LoggerFactory.getLogger(GrayRuleEngine.class);
    
    /**
     * 解析客户端应该使用的配置值
     * 
     * @param masterValue   Master 配置值
     * @param grayRules     当前生效的灰度规则列表
     * @param clientContext 客户端上下文（IP、SET 等信息）
     * @return 最终配置值
     */
    public static String resolveConfigValue(String masterValue, 
                                             List<ConfigGrayRule> grayRules,
                                             ClientContext clientContext) {
        if (grayRules == null || grayRules.isEmpty()) {
            return masterValue;
        }
        
        // 按优先级遍历灰度规则（IP 规则优先级最高）
        List<ConfigGrayRule> sortedRules = grayRules.stream()
            .filter(r -> r.getStatus() == 1)
            .sorted(Comparator.comparingInt(GrayRuleEngine::getRulePriority))
            .collect(Collectors.toList());
        
        for (ConfigGrayRule rule : sortedRules) {
            if (matchGrayRule(rule, clientContext)) {
                log.info("Client {} matched gray rule: type={}, name={}", 
                         clientContext.getClientIp(), rule.getGrayType(), rule.getGrayName());
                return rule.getGrayValue();
            }
        }
        
        // 未命中任何灰度规则，返回 Master 配置
        return masterValue;
    }
    
    /**
     * 匹配灰度规则
     */
    private static boolean matchGrayRule(ConfigGrayRule rule, ClientContext context) {
        switch (rule.getGrayType()) {
            case "IP":
                return matchByIp(rule, context);
            case "PERCENTAGE":
                return matchByPercentage(rule, context);
            case "SET":
                return matchBySet(rule, context);
            case "SET_PERCENTAGE":
                return matchBySetPercentage(rule, context);
            default:
                log.warn("Unknown gray type: {}", rule.getGrayType());
                return false;
        }
    }
    
    /**
     * 按 IP 列表匹配
     * 灰度规则示例：{"ips": ["10.0.1.2", "10.0.1.3", "10.0.1.5"]}
     */
    private static boolean matchByIp(ConfigGrayRule rule, ClientContext context) {
        JSONObject ruleJson = JSON.parseObject(rule.getGrayRule());
        List<String> grayIps = ruleJson.getJSONArray("ips").toJavaList(String.class);
        return grayIps.contains(context.getClientIp());
    }
    
    /**
     * 按百分比匹配
     * 灰度规则示例：{"percentage": 20}
     * 
     * 实现原理：对客户端 IP 做一致性哈希，取模判断是否落入灰度区间
     * 这样保证同一个 IP 每次判断结果一致（不会因为重启而变化）
     */
    private static boolean matchByPercentage(ConfigGrayRule rule, ClientContext context) {
        JSONObject ruleJson = JSON.parseObject(rule.getGrayRule());
        int percentage = ruleJson.getIntValue("percentage");
        
        if (percentage <= 0) return false;
        if (percentage >= 100) return true;
        
        // 使用 IP 的哈希值取模，保证同一 IP 的判断结果稳定
        int hash = Math.abs(context.getClientIp().hashCode());
        return (hash % 100) < percentage;
    }
    
    /**
     * 按 SET 分组匹配
     * 灰度规则示例：{"sets": ["SET-BJ", "SET-GZ"]}
     */
    private static boolean matchBySet(ConfigGrayRule rule, ClientContext context) {
        if (context.getSetName() == null || context.getSetName().isEmpty()) {
            return false;
        }
        JSONObject ruleJson = JSON.parseObject(rule.getGrayRule());
        List<String> graySets = ruleJson.getJSONArray("sets").toJavaList(String.class);
        return graySets.contains(context.getSetName());
    }
    
    /**
     * 按 SET + 百分比匹配
     * 灰度规则示例：{"set": "SET-BJ", "percentage": 30}
     * 含义：SET-BJ 分组中，30% 的实例使用灰度配置
     */
    private static boolean matchBySetPercentage(ConfigGrayRule rule, ClientContext context) {
        if (context.getSetName() == null || context.getSetName().isEmpty()) {
            return false;
        }
        JSONObject ruleJson = JSON.parseObject(rule.getGrayRule());
        String targetSet = ruleJson.getString("set");
        int percentage = ruleJson.getIntValue("percentage");
        
        // 首先判断是否属于目标 SET
        if (!targetSet.equals(context.getSetName())) {
            return false;
        }
        
        // 然后按百分比判断
        int hash = Math.abs(context.getClientIp().hashCode());
        return (hash % 100) < percentage;
    }
    
    /**
     * 灰度规则优先级（数字越小优先级越高）
     * IP 精确匹配优先级最高
     */
    private static int getRulePriority(ConfigGrayRule rule) {
        switch (rule.getGrayType()) {
            case "IP":             return 1;
            case "SET":            return 2;
            case "SET_PERCENTAGE": return 3;
            case "PERCENTAGE":     return 4;
            default:               return 99;
        }
    }
}
```

#### 3.3.4 灰度发布服务端逻辑

```java
/**
 * 灰度发布服务 —— 处理灰度发布的全生命周期
 */
@Service
public class GrayReleaseService {
    
    @Autowired
    private ConfigItemMapper configItemMapper;
    @Autowired
    private ConfigGrayRuleMapper grayRuleMapper;
    @Autowired
    private ConfigReleaseMapper releaseMapper;
    @Autowired
    private ConfigPublishEventMapper publishEventMapper;
    @Autowired

    /**
     * 创建灰度发布
     */
    @Transactional(rollbackFor = Exception.class)
    public void grayPublish(GrayPublishRequest request) {
        // 1. 校验配置是否存在
        ConfigItem configItem = configItemMapper.selectByConfigId(
            request.getNamespaceId(), request.getAppId(), 
            request.getGroupId(), request.getConfigKey()
        );
        if (configItem == null) {
            throw new BizException("配置不存在");
        }
        
        // 2. 创建灰度规则
        ConfigGrayRule grayRule = new ConfigGrayRule();
        grayRule.setNamespaceId(request.getNamespaceId());
        grayRule.setAppId(request.getAppId());
        grayRule.setGroupId(request.getGroupId());
        grayRule.setConfigKey(request.getConfigKey());
        grayRule.setGrayName(request.getGrayName());
        grayRule.setGrayType(request.getGrayType());
        grayRule.setGrayRule(request.getGrayRule());
        grayRule.setGrayValue(request.getGrayValue());
        grayRule.setGrayVersion(configItem.getVersion() + 1);
        grayRule.setStatus(1);
        grayRule.setOperator(request.getOperator());
        grayRuleMapper.insert(grayRule);
        
        // 3. 记录灰度发布事件
        ConfigRelease release = new ConfigRelease();
        release.setNamespaceId(request.getNamespaceId());
        release.setAppId(request.getAppId());
        release.setGroupId(request.getGroupId());
        release.setConfigKey(request.getConfigKey());
        release.setConfigValue(request.getGrayValue());
        release.setReleaseType("GRAY");
        release.setReleaseVersion(grayRule.getGrayVersion());
        release.setOperator(request.getOperator());
        release.setReleaseDesc("灰度发布 - " + request.getGrayName());
        releaseMapper.insert(release);
        
        // 4. 写入推送事件
        ConfigPublishEvent event = new ConfigPublishEvent();
        event.setNamespaceId(request.getNamespaceId());
        event.setAppId(request.getAppId());
        event.setGroupId(request.getGroupId());
        event.setConfigKey(request.getConfigKey());
        event.setEventType("GRAY_PUBLISH");
        event.setPublishVersion(grayRule.getGrayVersion());
        event.setOperator(request.getOperator());
        publishEventMapper.insert(event);
        
        // 5. 通知长轮询客户端
        longPollingController.notifyConfigChanged(
            request.getNamespaceId(), request.getAppId(),
            request.getGroupId(), request.getConfigKey()
        );
    }
    
    /**
     * 灰度转全量发布
     * 将灰度配置值提升为 Master 配置值，删除灰度规则
     */
    @Transactional(rollbackFor = Exception.class)
    public void fullPublishFromGray(String namespaceId, String appId, 
                                     String groupId, String configKey, 
                                     String operator) {
        // 1. 获取当前生效的灰度规则
        ConfigGrayRule grayRule = grayRuleMapper.selectActiveRule(
            namespaceId, appId, groupId, configKey
        );
        if (grayRule == null) {
            throw new BizException("无生效的灰度规则");
        }
        
        // 2. 将灰度值更新为 Master 值
        ConfigItem configItem = configItemMapper.selectByConfigId(
            namespaceId, appId, groupId, configKey
        );
        
        String oldValue = configItem.getConfigValue();
        String newValue = grayRule.getGrayValue();
        int newVersion = configItem.getVersion() + 1;
        
        configItem.setConfigValue(newValue);
        configItem.setMd5Value(DigestUtils.md5DigestAsHex(
            newValue.getBytes(StandardCharsets.UTF_8)));
        configItem.setVersion(newVersion);
        configItemMapper.updateById(configItem);
        
        // 3. 使灰度规则失效
        grayRule.setStatus(0);
        grayRuleMapper.updateById(grayRule);
        
        // 4. 记录变更历史
        ConfigHistory history = new ConfigHistory();
        history.setNamespaceId(namespaceId);
        history.setAppId(appId);
        history.setGroupId(groupId);
        history.setConfigKey(configKey);
        history.setOldValue(oldValue);
        history.setNewValue(newValue);
        history.setOldVersion(configItem.getVersion() - 1);
        history.setNewVersion(newVersion);
        history.setChangeType("UPDATE");
        history.setOperator(operator);
        configHistoryMapper.insert(history);
        
        // 5. 写入推送事件并通知客户端
        ConfigPublishEvent event = new ConfigPublishEvent();
        event.setNamespaceId(namespaceId);
        event.setAppId(appId);
        event.setGroupId(groupId);
        event.setConfigKey(configKey);
        event.setEventType("PUBLISH");
        event.setPublishVersion(newVersion);
        event.setOperator(operator);
        publishEventMapper.insert(event);
        
        longPollingController.notifyConfigChanged(namespaceId, appId, groupId, configKey);
    }
    
    /**
     * 灰度回滚 —— 撤销灰度规则，灰度实例恢复 Master 配置
     */
    @Transactional(rollbackFor = Exception.class)
    public void rollbackGray(String namespaceId, String appId, 
                              String groupId, String configKey, String operator) {
        // 1. 使灰度规则失效
        ConfigGrayRule grayRule = grayRuleMapper.selectActiveRule(
            namespaceId, appId, groupId, configKey
        );
        if (grayRule == null) {
            throw new BizException("无生效的灰度规则");
        }
        
        grayRule.setStatus(0);
        grayRuleMapper.updateById(grayRule);
        
        // 2. 写入回滚事件
        ConfigPublishEvent event = new ConfigPublishEvent();
        event.setNamespaceId(namespaceId);
        event.setAppId(appId);
        event.setGroupId(groupId);
        event.setConfigKey(configKey);
        event.setEventType("ROLLBACK");
        event.setPublishVersion(grayRule.getGrayVersion());
        event.setOperator(operator);
        publishEventMapper.insert(event);
        
        // 3. 通知客户端重新拉取（灰度实例将回退到 Master 配置）
        longPollingController.notifyConfigChanged(namespaceId, appId, groupId, configKey);
    }
}
```

#### 3.4.1 版本管理设计

```
配置版本演进示例：

Version 1: value = "3000"    (初始创建, 2024-01-10, operator: alice)
    ↓
Version 2: value = "5000"    (增大超时, 2024-01-15, operator: bob)
    ↓
Version 3: value = "2000"    (优化后减小, 2024-02-01, operator: alice)
    ↓
```

```java
/**
 * 配置发布服务 —— 含版本管理和乐观锁控制
 */
@Service
public class ConfigPublishService {
    
    @Autowired
    private ConfigItemMapper configItemMapper;
    @Autowired
    private ConfigHistoryMapper configHistoryMapper;
    @Autowired
    private ConfigReleaseMapper releaseMapper;
    @Autowired
    private ConfigPublishEventMapper publishEventMapper;
    @Autowired
    private ConfigLongPollingController longPollingController;
    
    /**
     * 发布配置变更
     * 
     * 使用乐观锁防止并发修改冲突：
     * UPDATE config_item SET config_value=?, version=version+1 
     * WHERE id=? AND version=?
     */
    @Transactional(rollbackFor = Exception.class)
    public void publishConfig(ConfigPublishRequest request) {
        // 1. 查询当前配置
        ConfigItem currentConfig = configItemMapper.selectByConfigId(
            request.getNamespaceId(), request.getAppId(),
            request.getGroupId(), request.getConfigKey()
        );
        
        if (currentConfig == null) {
            // 新建配置
            createNewConfig(request);
            return;
        }
        
        // 2. 乐观锁更新：version 必须与请求中的一致
        if (request.getExpectedVersion() != null && 
            !request.getExpectedVersion().equals(currentConfig.getVersion())) {
            throw new BizException("配置已被其他人修改（版本冲突），请刷新后重试。" +
                "当前版本: " + currentConfig.getVersion() + 
                ", 期望版本: " + request.getExpectedVersion());
        }
        
        String oldValue = currentConfig.getConfigValue();
        String newValue = request.getConfigValue();
        int oldVersion = currentConfig.getVersion();
        int newVersion = oldVersion + 1;
        
        // 3. 使用乐观锁更新配置
        String newMd5 = DigestUtils.md5DigestAsHex(newValue.getBytes(StandardCharsets.UTF_8));
        int affectedRows = configItemMapper.updateWithVersion(
            currentConfig.getId(), newValue, newMd5, newVersion, oldVersion
        );
        
        if (affectedRows == 0) {
            throw new BizException("配置更新失败（并发冲突），请重试");
        }
        
        // 4. 记录变更历史
        ConfigHistory history = new ConfigHistory();
        history.setNamespaceId(request.getNamespaceId());
        history.setAppId(request.getAppId());
        history.setGroupId(request.getGroupId());
        history.setConfigKey(request.getConfigKey());
        history.setOldValue(oldValue);
        history.setNewValue(newValue);
        history.setOldVersion(oldVersion);
        history.setNewVersion(newVersion);
        history.setChangeType("UPDATE");
        history.setOperator(request.getOperator());
        history.setClientIp(request.getClientIp());
        configHistoryMapper.insert(history);
        
        // 5. 记录发布记录
        ConfigRelease release = new ConfigRelease();
        release.setNamespaceId(request.getNamespaceId());
        release.setAppId(request.getAppId());
        release.setGroupId(request.getGroupId());
        release.setConfigKey(request.getConfigKey());
        release.setConfigValue(newValue);
        release.setReleaseType("NORMAL");
        release.setReleaseVersion(newVersion);
        release.setOperator(request.getOperator());
        release.setReleaseDesc(request.getDescription());
        releaseMapper.insert(release);
        
        // 6. 写入推送事件
        ConfigPublishEvent event = new ConfigPublishEvent();
        event.setNamespaceId(request.getNamespaceId());
        event.setAppId(request.getAppId());
        event.setGroupId(request.getGroupId());
        event.setConfigKey(request.getConfigKey());
        event.setEventType("PUBLISH");
        event.setPublishVersion(newVersion);
        event.setOperator(request.getOperator());
        publishEventMapper.insert(event);
        
        // 7. 通知长轮询客户端
        longPollingController.notifyConfigChanged(
            request.getNamespaceId(), request.getAppId(),
            request.getGroupId(), request.getConfigKey()
        );
        
        log.info("Config published: app={}, key={}, version {} -> {}, operator={}", 
                 request.getAppId(), request.getConfigKey(), oldVersion, newVersion,
                 request.getOperator());
    }
    
    /**
     * 回滚到指定历史版本
     */
    @Transactional(rollbackFor = Exception.class)
    public void rollbackToVersion(String namespaceId, String appId, String groupId,
                                   String configKey, int targetVersion, String operator) {
        // 1. 查找目标版本的历史记录
        ConfigHistory targetHistory = configHistoryMapper.selectByVersion(
            namespaceId, appId, groupId, configKey, targetVersion
        );
        if (targetHistory == null) {
            throw new BizException("目标版本不存在: version=" + targetVersion);
        }
        
        // 2. 获取当前配置
        ConfigItem currentConfig = configItemMapper.selectByConfigId(
            namespaceId, appId, groupId, configKey
        );
        
        String rollbackValue = targetHistory.getNewValue();
        int newVersion = currentConfig.getVersion() + 1;
        
        // 3. 执行回滚（本质是创建一个新版本，值等于历史版本的值）
        String newMd5 = DigestUtils.md5DigestAsHex(rollbackValue.getBytes(StandardCharsets.UTF_8));
        configItemMapper.updateWithVersion(
            currentConfig.getId(), rollbackValue, newMd5, 
            newVersion, currentConfig.getVersion()
        );
        
        // 4. 记录回滚历史
        ConfigHistory history = new ConfigHistory();
        history.setNamespaceId(namespaceId);
        history.setAppId(appId);
        history.setGroupId(groupId);
        history.setConfigKey(configKey);
        history.setOldValue(currentConfig.getConfigValue());
        history.setNewValue(rollbackValue);
        history.setOldVersion(currentConfig.getVersion());
        history.setNewVersion(newVersion);
        history.setChangeType("ROLLBACK");
        history.setOperator(operator);
        configHistoryMapper.insert(history);
        
        // 5. 记录发布
        ConfigRelease release = new ConfigRelease();
        release.setNamespaceId(namespaceId);
        release.setAppId(appId);
        release.setGroupId(groupId);
        release.setConfigKey(configKey);
        release.setConfigValue(rollbackValue);
        release.setReleaseType("ROLLBACK");
        release.setReleaseVersion(newVersion);
        release.setOperator(operator);
        release.setReleaseDesc("回滚到版本 " + targetVersion);
        releaseMapper.insert(release);
        
        // 6. 推送通知
        ConfigPublishEvent event = new ConfigPublishEvent();
        event.setNamespaceId(namespaceId);
        event.setAppId(appId);
        event.setGroupId(groupId);
        event.setConfigKey(configKey);
        event.setEventType("ROLLBACK");
        event.setPublishVersion(newVersion);
        event.setOperator(operator);
        publishEventMapper.insert(event);
        
        longPollingController.notifyConfigChanged(namespaceId, appId, groupId, configKey);
        
        log.info("Config rolled back: key={}, rollback to version {}, new version={}", 
                 configKey, targetVersion, newVersion);
    }
}
```

#### 3.5.1 审计日志设计

```java
/**
 * 配置变更审计服务
 */
@Service
public class ConfigAuditService {
    
    @Autowired
    private ConfigHistoryMapper historyMapper;
    
    /**
     * 查询配置变更历史
     */
    public PageResult<ConfigAuditRecord> queryAuditLog(ConfigAuditQuery query) {
        List<ConfigHistory> histories = historyMapper.selectByCondition(
            query.getNamespaceId(),
            query.getAppId(),
            query.getConfigKey(),
            query.getOperator(),
            query.getStartTime(),
            query.getEndTime(),
            query.getPageNo(),
            query.getPageSize()
        );
        
        List<ConfigAuditRecord> records = histories.stream()
            .map(this::convertToAuditRecord)
            .collect(Collectors.toList());
        
        long total = historyMapper.countByCondition(
            query.getNamespaceId(), query.getAppId(), 
            query.getConfigKey(), query.getOperator(),
            query.getStartTime(), query.getEndTime()
        );
        
        return new PageResult<>(records, total, query.getPageNo(), query.getPageSize());
    }
    
    /**
     * 转换为审计记录
     */
    private ConfigAuditRecord convertToAuditRecord(ConfigHistory history) {
        ConfigAuditRecord record = new ConfigAuditRecord();
        record.setConfigKey(history.getConfigKey());
        record.setAppId(history.getAppId());
        record.setChangeType(history.getChangeType());
        record.setOldValue(maskSensitiveValue(history.getOldValue()));
        record.setNewValue(maskSensitiveValue(history.getNewValue()));
        record.setOldVersion(history.getOldVersion());
        record.setNewVersion(history.getNewVersion());
        record.setOperator(history.getOperator());
        record.setOperatorIp(history.getClientIp());
        record.setChangeTime(history.getGmtCreate());
        
        // 计算变更差异摘要
        record.setDiffSummary(generateDiffSummary(history.getOldValue(), history.getNewValue()));
        
        return record;
    }
    
    /**
     * 敏感配置脱敏显示
     */
    private String maskSensitiveValue(String value) {
        if (value == null) return null;
        // 对包含 password、secret、key 等关键词的配置做脱敏
        if (containsSensitiveKeyword(value)) {
            if (value.length() <= 4) return "****";
            return value.substring(0, 2) + "****" + value.substring(value.length() - 2);
        }
        return value;
    }
    
    private boolean containsSensitiveKeyword(String value) {
        String lower = value.toLowerCase();
        return lower.contains("password") || lower.contains("secret") || 
               lower.contains("token") || lower.contains("credential");
    }
    
    /**
     * 生成变更差异摘要
     */
    private String generateDiffSummary(String oldValue, String newValue) {
        if (oldValue == null && newValue != null) return "新增配置";
        if (oldValue != null && newValue == null) return "删除配置";
        if (oldValue == null) return "无变化";
        
        if (oldValue.length() < 100 && newValue.length() < 100) {
            return "\"" + oldValue + "\" → \"" + newValue + "\"";
        }
        return "配置值已变更（内容过长，请查看详情）";
    }
}
```

```java
@ConfigurationProperties(prefix = "config-center")
public class ConfigCenterProperties {
    private String serverUrls;
    private String namespace = "default";
    private String appId;
    
    // getter/setter
}

/**
 * 通过注解实现配置自动注入和动态刷新
 */
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface DynamicConfig {
    String key();
    String defaultValue() default "";
}

/**
 * 动态配置注入处理器
 */
@Component
public class DynamicConfigProcessor implements BeanPostProcessor {
    
    @Autowired
    private ConfigClient configClient;
    
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        Class<?> clazz = bean.getClass();
        
        for (Field field : clazz.getDeclaredFields()) {
            DynamicConfig annotation = field.getAnnotation(DynamicConfig.class);
            if (annotation != null) {
                String key = annotation.key();
                String defaultValue = annotation.defaultValue();
                
                // 初始值注入
                String value = configClient.getConfig(key, defaultValue);
                setFieldValue(bean, field, value);
                
                // 注册动态刷新监听器
                configClient.addListener(key, event -> {
                    setFieldValue(bean, field, event.getNewValue());
                    log.info("Dynamic config refreshed: bean={}, field={}, key={}, newValue={}", 
                             beanName, field.getName(), key, event.getNewValue());
                });
            }
        }
        
        return bean;
    }
    
    private void setFieldValue(Object bean, Field field, String value) {
        try {
            field.setAccessible(true);
            Class<?> fieldType = field.getType();
            
            if (fieldType == String.class) {
                field.set(bean, value);
            } else if (fieldType == int.class || fieldType == Integer.class) {
                field.set(bean, Integer.parseInt(value));
            } else if (fieldType == long.class || fieldType == Long.class) {
                field.set(bean, Long.parseLong(value));
            } else if (fieldType == boolean.class || fieldType == Boolean.class) {
                field.set(bean, Boolean.parseBoolean(value));
            } else if (fieldType == double.class || fieldType == Double.class) {
                field.set(bean, Double.parseDouble(value));
            }
        } catch (Exception e) {
            log.error("Set dynamic config field value failed", e);
        }
    }
}
```

### 3.7 配置最终一致性

#### 3.7.1 一致性模型

配置中心采用**最终一致性**（Eventual Consistency）模型。即配置变更后，不保证所有客户端在同一时刻看到最新配置，但保证在一定时间窗口内（通常 5 秒内），所有客户端最终都会收敛到最新的配置值。

```
最终一致性时序图：

时间轴  t0        t1        t2        t3        t4        t5
       │         │         │         │         │         │
配置变更  ★ ────────────────────────────────────────────────
       │         │         │         │         │         │
Client-1 ────────── ★ 收到通知，更新配置                     
Client-2 ──────────────── ★ 收到通知，更新配置                
Client-3 ──────────────────────── ★ 收到通知，更新配置        
Client-4 ────────────────────────────── ★ 长轮询超时重连后更新 
       │         │         │         │         │         │
       │←─────── 一致性窗口（≤5秒） ──────────────→│

t0: 配置变更写入数据库
t1~t4: 各客户端陆续收到通知并更新
t5: 所有客户端达成一致
```

#### 3.7.2 变更传播链路

```
配置变更传播的完整链路：

Step 1: Admin Portal 提交变更
        ↓
Step 2: Config Server 写入 config_item 表（配置数据）
        写入 config_publish_event 表（变更事件）
        ↓
Step 3: Config Server 变更检测器扫描 config_publish_event 表
        发现新的事件记录
        ↓
Step 4: 查找所有监听该配置的 Long Polling 客户端连接
        通过 DeferredResult 立即响应
        ↓
Step 5: 客户端收到变更通知
        → 向 Config Server 发起 GET 请求拉取最新配置值
        → 更新内存缓存
        → 更新本地文件缓存
        → 触发 ConfigChangeListener 回调
        ↓
Step 6: 应用业务逻辑使用新配置
```

#### 3.7.3 服务端变更检测

在多 Server 集群部署时，配置可能由 Server-A 节点写入，而长轮询连接挂在 Server-B 节点。因此需要一个变更检测机制，确保所有 Server 节点都能感知到配置变更。

```java
/**
 * 配置变更检测器
 * 
 * 在多 Server 节点的场景下，通过定时扫描 publish_event 表来检测配置变更。
 * 这是一种简单高效的方案，避免了 Server 节点之间的直接通信。
 */
@Component
public class ConfigChangeDetector {
    
    private static final Logger log = LoggerFactory.getLogger(ConfigChangeDetector.class);
    
    /** 上次扫描到的最大事件 ID */
    private volatile long lastEventId = 0L;
    
    @Autowired
    private ConfigPublishEventMapper publishEventMapper;
    
    @Autowired
    private ConfigLongPollingController longPollingController;
    
    /**
     * 定时扫描变更事件
     * 每 500ms 扫描一次，确保配置变更在 1 秒内被检测到
     */
    @Scheduled(fixedDelay = 500)
    public void scanPublishEvents() {
        try {
            List<ConfigPublishEvent> newEvents = publishEventMapper.selectAfterEventId(lastEventId);
            
            if (newEvents.isEmpty()) {
                return;
            }
            
            for (ConfigPublishEvent event : newEvents) {
                log.info("Detected config change event: id={}, app={}, key={}, type={}", 
                         event.getId(), event.getAppId(), event.getConfigKey(), event.getEventType());
                
                // 通知长轮询客户端
                longPollingController.notifyConfigChanged(
                    event.getNamespaceId(), event.getAppId(),
                    event.getGroupId(), event.getConfigKey()
                );
                
                // 更新最大事件 ID
                if (event.getId() > lastEventId) {
                    lastEventId = event.getId();
                }
            }
        } catch (Exception e) {
            log.error("Scan publish events failed", e);
        }
    }
    
    /**
     * 启动时初始化 lastEventId
     */
    @PostConstruct
    public void init() {
        Long maxId = publishEventMapper.selectMaxEventId();
        if (maxId != null) {
            lastEventId = maxId;
        }
        log.info("ConfigChangeDetector initialized, lastEventId: {}", lastEventId);
    }
}
```

#### 3.7.4 不适用场景

配置中心的最终一致性模型并不适用于所有场景，以下场景应避免使用配置中心：

| 不适用场景 | 原因 | 替代方案 |
|-----------|------|---------|
| 高频变更（>1 QPS） | 频繁的配置推送会产生大量长轮询响应，影响系统稳定性 | 使用消息队列或缓存 |
| 写后立读要求 | 写入后 5 秒内可能读不到最新值，不满足强一致性要求 | 使用数据库或分布式锁 |
| 事务性配置 | 多个配置需要原子性生效，最终一致性无法保证原子性 | 使用分布式事务 |
| 大文件配置 | 超大配置值（>1MB）会影响推送性能和网络带宽 | 使用对象存储 + URL 引用 |

#### 3.8.2 客户端容灾

客户端 SDK 的容灾设计确保即使 Config Server 完全不可用，应用服务仍然能够正常运行：

```java
/**
 * 客户端容灾机制
 * 
 * 三级缓存策略：内存缓存 → 本地文件缓存 → 默认值
 */
public class ConfigClientFailover {
    
    private static final Logger log = LoggerFactory.getLogger(ConfigClientFailover.class);
    
    /** 一级缓存：内存 */
    private final ConcurrentHashMap<String, String> memoryCache;
    
    /** 二级缓存：本地文件 */
    private final LocalFileCache localFileCache;
    
    /** 默认值注册表 */
    private final ConcurrentHashMap<String, String> defaultValues;
    
    public ConfigClientFailover(String cacheDir, String appId) {
        this.memoryCache = new ConcurrentHashMap<>();
        this.localFileCache = new LocalFileCache(cacheDir, appId);
        this.defaultValues = new ConcurrentHashMap<>();
    }
    
    /**
     * 获取配置值（三级容灾）
     */
    public String getConfig(String key, String defaultValue) {
        // 注册默认值
        if (defaultValue != null) {
            defaultValues.putIfAbsent(key, defaultValue);
        }
        
        // 第一级：内存缓存
        String value = memoryCache.get(key);
        if (value != null) {
            return value;
        }
        
        // 第二级：本地文件缓存
        value = localFileCache.get(key);
        if (value != null) {
            log.warn("Config loaded from local file cache: key={}", key);
            memoryCache.put(key, value);  // 回填内存缓存
            return value;
        }
        
        // 第三级：默认值
        log.warn("Config not found anywhere, using default: key={}, default={}", key, defaultValue);
        return defaultValue;
    }
    
    /**
     * 更新配置（同时刷新内存和文件缓存）
     */
    public void updateConfig(String key, String value) {
        String oldValue = memoryCache.put(key, value);
        localFileCache.put(key, value);  // 异步写入本地文件
        
        if (oldValue != null && !oldValue.equals(value)) {
            log.info("Config updated: key={}, oldValue={}, newValue={}", key, oldValue, value);
        }
    }
    
    /**
     * 批量更新配置（全量拉取后调用）
     */
    public void batchUpdateConfig(Map<String, String> configs) {
        configs.forEach(this::updateConfig);
        localFileCache.flush();  // 确保写入磁盘
    }
}

/**
 * 本地文件缓存
 * 
 * 将配置持久化到本地 JSON 文件，作为容灾备份
 */
public class LocalFileCache {
    
    private static final Logger log = LoggerFactory.getLogger(LocalFileCache.class);
    
    private final File cacheFile;
    private final ConcurrentHashMap<String, String> fileCache;
    private final ScheduledExecutorService flushExecutor;
    private volatile boolean dirty = false;
    
    public LocalFileCache(String cacheDir, String appId) {
        this.cacheFile = new File(cacheDir, appId + "-config-cache.json");
        this.fileCache = new ConcurrentHashMap<>();
        this.flushExecutor = Executors.newSingleThreadScheduledExecutor(
            r -> new Thread(r, "config-file-cache-flush"));
        
        // 加载已有缓存
        loadFromFile();
        
        // 定时刷新到磁盘（每 5 秒）
        flushExecutor.scheduleWithFixedDelay(this::flush, 5, 5, TimeUnit.SECONDS);
    }
    
    public String get(String key) {
        return fileCache.get(key);
    }
    
    public void put(String key, String value) {
        fileCache.put(key, value);
        dirty = true;
    }
    
    public synchronized void flush() {
        if (!dirty) return;
        
        try {
            File parentDir = cacheFile.getParentFile();
            if (!parentDir.exists()) {
                parentDir.mkdirs();
            }
            
            String json = JSON.toJSONString(fileCache, SerializerFeature.PrettyFormat);
            
            // 先写临时文件，再原子性重命名，防止写入中途崩溃导致文件损坏
            File tmpFile = new File(cacheFile.getAbsolutePath() + ".tmp");
            Files.write(tmpFile.toPath(), json.getBytes(StandardCharsets.UTF_8));
            Files.move(tmpFile.toPath(), cacheFile.toPath(), StandardCopyOption.ATOMIC_MOVE);
            
            dirty = false;
        } catch (IOException e) {
            log.error("Flush config file cache failed: {}", cacheFile.getAbsolutePath(), e);
        }
    }
    
    private void loadFromFile() {
        if (!cacheFile.exists()) return;
        
        try {
            String json = new String(Files.readAllBytes(cacheFile.toPath()), StandardCharsets.UTF_8);
            Map<String, String> cached = JSON.parseObject(json, 
                new TypeReference<Map<String, String>>() {});
            if (cached != null) {
                fileCache.putAll(cached);
                log.info("Loaded {} configs from local file cache: {}", 
                         cached.size(), cacheFile.getAbsolutePath());
            }
        } catch (Exception e) {
            log.error("Load config file cache failed: {}", cacheFile.getAbsolutePath(), e);
        }
    }
}
```

## 四、异常处理与容错

### 4.1 异常场景分类

| 异常场景 | 影响范围 | 处理策略 | 恢复时间 |
|---------|---------|---------|--------|
| 单个 Server 节点宕机 | 该节点上的长轮询连接 | 客户端自动重连到其他节点 | 秒级 |
| Server 集群全部宕机 | 所有客户端无法拉取新配置 | 客户端使用本地文件缓存 | 依赖运维恢复 |
| MySQL 主库宕机 | 无法写入新配置 | MGR 自动切换，只读降级 | 秒~分钟级 |
| 网络分区 | 部分客户端无法连接 Server | 本地缓存 + 定时重连 | 网络恢复后自动 |
| 客户端进程重启 | 内存缓存丢失 | 从本地文件加载 + 全量拉取 | 秒级 |
| 错误配置推送 | 业务异常 | 紧急回滚到上一版本 | 分钟级 |

### 4.2 推送失败处理

```java
/**
 * 推送确认机制
 * 
 * 配置推送后，验证所有（或指定比例的）客户端是否成功接收新配置
 */
@Service
public class PushVerificationService {
    
    @Autowired
    private ClientRegistryService clientRegistry;
    
    /**
     * 验证配置推送结果
     * 
     * @return 推送验证报告
     */
    public PushVerifyReport verifyPush(String namespaceId, String appId, 
                                       String groupId, String configKey, 
                                       int targetVersion) {
        // 1. 获取所有注册的客户端实例
        List<ClientInstance> clients = clientRegistry.getClients(namespaceId, appId);
        
        int totalClients = clients.size();
        int confirmedClients = 0;
        int pendingClients = 0;
        List<String> failedIps = new ArrayList<>();
        
        // 2. 检查每个客户端的配置版本
        for (ClientInstance client : clients) {
            int clientVersion = client.getConfigVersion(configKey);
            
            if (clientVersion >= targetVersion) {
                confirmedClients++;
            } else {
                pendingClients++;
                failedIps.add(client.getIp());
            }
        }
        
        // 3. 生成验证报告
        PushVerifyReport report = new PushVerifyReport();
        report.setTotalClients(totalClients);
        report.setConfirmedClients(confirmedClients);
        report.setPendingClients(pendingClients);
        report.setFailedIps(failedIps);
        report.setSuccessRate(
            totalClients > 0 ? (double) confirmedClients / totalClients * 100 : 100
        );
        report.setFullyPushed(pendingClients == 0);
        
        return report;
    }
}
```

### 4.3 危险配置检测

```java
/**
 * 危险配置变更检测
 * 
 * 在配置发布前进行安全检查，防止危险配置上线
 */
@Component
public class DangerousConfigDetector {
    
    /**
     * 检测危险配置变更
     */
    public List<String> detectDangerousChange(String key, String oldValue, String newValue) {
        List<String> warnings = new ArrayList<>();
        
        // 1. 超时时间不能设置过小
        if (key.contains("timeout")) {
            try {
                long timeoutMs = Long.parseLong(newValue);
                if (timeoutMs < 100) {
                    warnings.add("超时时间设置过小（<100ms），可能导致大量超时异常");
                }
                if (timeoutMs > 60000) {
                    warnings.add("超时时间设置过大（>60s），可能导致线程长时间阻塞");
                }
            } catch (NumberFormatException e) {
                warnings.add("超时时间值不是合法数字: " + newValue);
            }
        }
        
        // 2. 线程池大小不能设置为 0
        if (key.contains("threadPool") || key.contains("poolSize")) {
            try {
                int poolSize = Integer.parseInt(newValue);
                if (poolSize <= 0) {
                    warnings.add("线程池大小不能为 0 或负数");
                }
                if (poolSize > 1000) {
                    warnings.add("线程池大小过大（>1000），可能导致内存不足");
                }
            } catch (NumberFormatException e) {
                warnings.add("线程池大小不是合法整数: " + newValue);
            }
        }
        
        // 3. 开关类配置值校验
        if (key.contains("switch") || key.contains("toggle") || key.contains("enabled")) {
            if (!"true".equalsIgnoreCase(newValue) && !"false".equalsIgnoreCase(newValue)) {
                warnings.add("开关类配置值应为 true 或 false，当前值: " + newValue);
            }
        }
        
        // 4. 配置值变化幅度过大
        if (oldValue != null) {
            try {
                double oldNum = Double.parseDouble(oldValue);
                double newNum = Double.parseDouble(newValue);
                if (oldNum != 0) {
                    double changeRatio = Math.abs(newNum - oldNum) / Math.abs(oldNum);
                    if (changeRatio > 10.0) {
                        warnings.add(String.format(
                            "配置值变化幅度过大（%.0f%%），请确认是否正确", changeRatio * 100));
                    }
                }
            } catch (NumberFormatException ignored) {
                // 非数值类配置，跳过幅度检查
            }
        }
        
        // 5. JSON 格式校验
        if (newValue.startsWith("{") || newValue.startsWith("[")) {
            try {
                JSON.parse(newValue);
            } catch (Exception e) {
                warnings.add("配置值不是合法的 JSON 格式: " + e.getMessage());
            }
        }
        
        return warnings;
    }
}
```

## 五、性能优化

### 5.1 减少数据库压力

#### 5.1.1 事件驱动替代全表扫描

在高配置量场景下，定时扫描 `config_publish_event` 表可能产生较大的数据库压力。优化方案是引入消息队列实现事件驱动：

```
优化前（定时扫描）：
  Config Server 每 500ms 扫描 publish_event 表
  → 在配置量大时，扫描开销显著

优化后（事件驱动 + 扫描兜底）：
  Config Server 写入 publish_event 后，同时发送 MQ 消息
  → 其他 Server 节点通过消费 MQ 消息实时感知变更
  → 保留 5 秒一次的扫描作为兜底（防止 MQ 消息丢失）
```

#### 5.1.2 客户端请求合并

当一个应用有大量配置项时，客户端不应为每个配置项单独建立长轮询连接，而是将多个配置项合并为一个连接：

```java
/**
 * 客户端请求合并
 * 
 * 将同一个 app 的所有配置项合并到一个长轮询请求中
 * 使用 MD5 摘要列表来标识配置版本
 */
public class BatchLongPollingRequest {
    private String namespaceId;
    private String appId;
    
    /**
     * 配置版本摘要列表
     * 格式：key1:md5_1,key2:md5_2,key3:md5_3
     * 
     * 服务端收到后，逐个比较 MD5，找出变更的配置项
     */
    private String configDigests;
    
    /**
     * 构建摘要列表
     */
    public static String buildDigests(Map<String, String> configMd5Map) {
        return configMd5Map.entrySet().stream()
            .map(entry -> entry.getKey() + ":" + entry.getValue())
            .collect(Collectors.joining(","));
    }
    
    /**
     * 解析摘要列表
     */
    public static Map<String, String> parseDigests(String digests) {
        Map<String, String> result = new HashMap<>();
        if (digests == null || digests.isEmpty()) return result;
        
        for (String item : digests.split(",")) {
            String[] parts = item.split(":");
            if (parts.length == 2) {
                result.put(parts[0].trim(), parts[1].trim());
            }
        }
        return result;
    }
}
```

### 5.2 海量连接管理

当客户端数量达到百万级时，长轮询连接的管理成为关键挑战：

```
连接规模估算：

假设：
- 10,000 个微服务应用
- 每个应用平均 50 个实例
- 每个实例 1 个长轮询连接
- 总连接数 = 10,000 × 50 = 500,000

单 Server 节点承载能力：
- 使用 Spring DeferredResult 异步处理（不占用 Tomcat 工作线程）
- 单节点可承载 5~10 万长轮询连接
- 5~10 个 Server 节点即可承载 50 万连接

优化措施：
1. 使用 Netty 替代 Tomcat 作为 HTTP 容器，提升连接承载能力
2. 调整 Linux 内核参数：
   - fs.file-max = 1000000          # 系统级最大文件描述符
   - net.ipv4.ip_local_port_range = 1024 65535  # 可用端口范围
   - net.core.somaxconn = 65535     # 最大连接排队数
3. JVM 参数优化：
   - 增大堆内存（每个 DeferredResult 约占 1~2KB 内存）
   - 50 万连接约需 500MB ~ 1GB 额外堆内存
```

### 5.3 大配置文件处理

对于超过 1MB 的大配置文件（如规则引擎配置、复杂 JSON Schema），不适合直接通过长轮询推送，应采用「引用 + 下载」模式：

```
大配置文件处理流程：

1. Admin Portal 上传大配置文件到对象存储（如 S3/MinIO/OSS）
2. 配置中心存储的是文件 URL 和 MD5（而非文件内容本身）
3. 配置变更推送时，推送的是 URL 和 MD5
4. 客户端收到通知后：
   - 比较 MD5，判断是否需要更新
   - 如需更新，从对象存储直接下载文件
   - 下载完成后更新本地缓存

配置值示例：
{
    "type": "FILE_REF",
    "url": "https://oss.example.com/configs/rule-engine/v42.json",
    "md5": "a1b2c3d4e5f6...",
    "size": 2048576,
    "version": 42
}
```

### 7.2 敏感配置加密

数据库密码、API Key、Secret 等敏感配置不应以明文存储。配置中心应支持加密存储和运行时解密：

```java
/**
 * 敏感配置加密/解密
 * 
 * 使用 AES-256-GCM 对敏感配置值进行加密
 * 加密密钥由 KMS（密钥管理服务）管理
 */
public class ConfigEncryptor {
    
    private static final String ENCRYPTED_PREFIX = "ENC(";
    private static final String ENCRYPTED_SUFFIX = ")";
    
    private final SecretKey secretKey;
    
    public ConfigEncryptor(byte[] keyBytes) {
        this.secretKey = new SecretKeySpec(keyBytes, "AES");
    }
    
    /**
     * 加密配置值
     */
    public String encrypt(String plainText) throws Exception {
        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        byte[] iv = new byte[12];
        SecureRandom.getInstanceStrong().nextBytes(iv);
        GCMParameterSpec spec = new GCMParameterSpec(128, iv);
        cipher.init(Cipher.ENCRYPT_MODE, secretKey, spec);
        
        byte[] encrypted = cipher.doFinal(plainText.getBytes(StandardCharsets.UTF_8));
        byte[] combined = new byte[iv.length + encrypted.length];
        System.arraycopy(iv, 0, combined, 0, iv.length);
        System.arraycopy(encrypted, 0, combined, iv.length, encrypted.length);
        
        return ENCRYPTED_PREFIX + Base64.getEncoder().encodeToString(combined) + ENCRYPTED_SUFFIX;
    }
    
    /**
     * 解密配置值
     */
    public String decrypt(String encryptedText) throws Exception {
        if (!isEncrypted(encryptedText)) {
            return encryptedText;
        }
        
        String base64 = encryptedText.substring(
            ENCRYPTED_PREFIX.length(), 
            encryptedText.length() - ENCRYPTED_SUFFIX.length()
        );
        byte[] combined = Base64.getDecoder().decode(base64);
        
        byte[] iv = Arrays.copyOfRange(combined, 0, 12);
        byte[] encrypted = Arrays.copyOfRange(combined, 12, combined.length);
        
        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        GCMParameterSpec spec = new GCMParameterSpec(128, iv);
        cipher.init(Cipher.DECRYPT_MODE, secretKey, spec);
        
        byte[] decrypted = cipher.doFinal(encrypted);
        return new String(decrypted, StandardCharsets.UTF_8);
    }
    
    public boolean isEncrypted(String value) {
        return value != null && value.startsWith(ENCRYPTED_PREFIX) && value.endsWith(ENCRYPTED_SUFFIX);
    }
}
```

### 7.3 配置生命周期管理

```
配置生命周期：

创建 → 开发环境验证 → 测试环境验证 → 预发布环境验证 → 灰度发布 → 全量发布 → 日常运维 → 下线清理

关键管理要点：

1. 【创建阶段】
   - 明确配置的用途和默认值
   - 设定配置的数据类型和取值范围
   - 标注是否为敏感配置

2. 【发布阶段】
   - 开发环境：自由修改，无审批要求
   - 测试环境：自由修改，需通知测试人员
   - 预发布环境：需要 TL 审批
   - 生产环境：需要 TL + SRE 审批，必须先灰度

3. 【运维阶段】
   - 定期审计配置使用情况（是否有未使用的配置）
   - 监控配置变更频率
   - 配置依赖分析（哪些服务依赖哪些配置）

4. 【清理阶段】
   - 识别不再使用的配置项
   - 确认无任何服务依赖后下线
   - 保留审计日志至少 6 个月
```

### 7.5 总结

配置中心是分布式系统基础设施的核心组件，它解决了配置与代码分离、动态调整、多环境管理等关键问题。本文从问题背景出发，系统性地设计了一个完整的配置中心架构，核心要点如下：

1. **架构分层**：采用 Admin Portal + Config Server + Client SDK 三层架构，职责清晰，各层可独立演进。

2. **推送机制**：长轮询（Long Polling）是当前最主流的配置推送方案，兼顾了实时性和资源效率。Apollo 和 Nacos 都采用了这一方案。

3. **灰度发布**：支持按 IP、百分比、SET 等多维度灰度策略，配合全量发布和回滚机制，确保配置变更的安全性。

4. **版本管理**：每次配置变更都生成新版本，支持任意版本回滚。乐观锁机制防止并发冲突。

5. **客户端容灾**：三级缓存（内存 → 本地文件 → 默认值）确保 Server 故障时业务不受影响。

6. **最终一致性**：配置变更在 5 秒内传播到所有客户端，满足绝大多数业务场景的要求。

7. **安全与审计**：完整的审计日志、审批工作流、敏感配置加密和危险配置检测，保障生产环境的安全性。

在技术选型上，大规模微服务系统推荐使用 Apollo 或 Nacos，Spring Cloud 技术栈推荐 Spring Cloud Config，Kubernetes 环境推荐 etcd。选择时应综合考虑团队技术栈、运维能力、功能需求和规模预期。

## 八、全链路实战案例

前面的章节从架构、推送机制、灰度发布、版本管理等维度分别剖析了配置中心的各个模块。本章通过三个贯穿全链路的实战案例，把这些模块串联起来，展示一次配置操作从触发到最终生效的完整流转过程。每个案例都给出可落地的 Java 代码，并重点关注三个工程要点：

- **异常处理**：链路每一环都可能失败（数据库超时、审批系统不可用、推送风暴、客户端解析异常），必须明确失败边界与补偿手段。
- **日志**：全链路串一个 `traceId`，关键节点打点，便于事后追溯"配置为什么没生效""哪台机器还是旧值"。
- **幂等控制**：发布、推送、回滚都可能被重试（网络抖动、MQ 重投、人工重复点击），必须保证重复执行不会产生副作用（重复扣版本、重复推送、脏数据）。

### 8.1 案例一：配置发布与推送全链路

#### 8.1.1 场景描述

运营同学在大促前需要把限流阈值 `ratelimit.order.qps` 从 `2000` 调整为 `5000`。这是一个生产环境的核心配置变更，完整链路为：

```
运营在 Admin Portal 修改配置
   → 提交发布单（草稿态，不生效）
   → 触发审批流（TL + SRE 审批）
   → 审批通过后执行发布（写库 + 版本+1 + 写发布事件）
   → 先灰度推送（10% 实例 / 指定 IP）
   → 观察灰度指标无异常
   → 灰度转全量推送
   → 客户端长轮询收到通知 → 拉取新值 → 热更新内存缓存 → 触发监听器回调
```

其时序如下：

```
运营       Portal      ApprovalSvc   PublishSvc     ConfigServer   Client(灰度)  Client(全量)
 │  修改并提交  │            │             │              │            │            │
 │─────────────>│  创建发布单 │             │              │            │            │
 │            │────────────>│  发起审批    │              │            │            │
 │            │            │─── 审批中 ───│              │            │            │
 │            │  审批通过回调 │             │              │            │            │
 │            │<────────────│             │              │            │            │
 │            │────────────────────────>│  执行灰度发布   │            │            │
 │            │            │             │─ 写库+事件 ──>│  通知灰度连接 │            │
 │            │            │             │              │───────────>│ 拉取+热更新 │
 │  观察灰度指标（人工/自动 5~10min）      │              │            │            │
 │            │───────────────────────>│  灰度转全量     │            │            │
 │            │            │             │─ 写库+事件 ──>│  通知全部连接 │            │
 │            │            │             │              │────────────────────────>│ 拉取+热更新
```

#### 8.1.2 发布单与审批（草稿态，幂等提交）

发布不直接改动生效配置，而是先落一张 `config_change_ticket`（发布单）表，处于草稿/待审批态。这样做的目的是：变更与生效解耦，审批可回溯，并且天然支持幂等——同一个发布单只会被执行一次。

```sql
-- 发布单表：变更请求的载体，审批通过后才会真正发布
CREATE TABLE config_change_ticket (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT,
    ticket_no       VARCHAR(64)     NOT NULL                     COMMENT '发布单号（业务唯一，用于幂等）',
    namespace_id    VARCHAR(64)     NOT NULL,
    app_id          VARCHAR(128)    NOT NULL,
    group_id        VARCHAR(128)    NOT NULL DEFAULT 'DEFAULT_GROUP',
    config_key      VARCHAR(256)    NOT NULL,
    old_value       LONGTEXT                                     COMMENT '提单时的旧值快照',
    new_value       LONGTEXT                                     COMMENT '待发布的新值',
    base_version    INT             NOT NULL                     COMMENT '提单时基于的版本（乐观锁基线）',
    release_strategy VARCHAR(32)    NOT NULL DEFAULT 'GRAY_FIRST' COMMENT '发布策略: GRAY_FIRST/FULL',
    status          VARCHAR(16)     NOT NULL DEFAULT 'DRAFT'     COMMENT 'DRAFT/APPROVING/APPROVED/GRAY_RELEASED/RELEASED/REJECTED/CANCELED',
    operator        VARCHAR(64)     NOT NULL,
    gmt_create      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    gmt_modified    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE KEY uk_ticket_no (ticket_no),
    KEY idx_status (status),
    KEY idx_app_config (app_id, config_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配置发布单';
```

```java
/**
 * 配置发布单服务 —— 负责提单、审批回调、幂等提交
 */
@Service
public class ConfigTicketService {

    private static final Logger log = LoggerFactory.getLogger(ConfigTicketService.class);

    @Autowired
    private ConfigChangeTicketMapper ticketMapper;
    @Autowired
    private ConfigItemMapper configItemMapper;
    @Autowired
    private ApprovalClient approvalClient;

    /**
     * 提交发布单（幂等）。
     *
     * 幂等控制：以调用方传入的 ticketNo 为业务唯一键。重复提交（如页面重复点击、
     * 网络重试导致的重放）直接返回已存在的发布单，不会产生第二条记录。
     */
    @Transactional(rollbackFor = Exception.class)
    public ConfigChangeTicket submitTicket(SubmitTicketRequest request) {
        String traceId = TraceContext.getOrCreateTraceId();
        log.info("[{}] submit ticket start: ticketNo={}, app={}, key={}, operator={}",
                traceId, request.getTicketNo(), request.getAppId(),
                request.getConfigKey(), request.getOperator());

        // 幂等：先查后建，唯一索引兜底
        ConfigChangeTicket exist = ticketMapper.selectByTicketNo(request.getTicketNo());
        if (exist != null) {
            log.info("[{}] ticket already exists, return directly: ticketNo={}, status={}",
                    traceId, request.getTicketNo(), exist.getStatus());
            return exist;
        }

        // 读取当前生效配置，作为乐观锁基线
        ConfigItem current = configItemMapper.selectByConfigId(
                request.getNamespaceId(), request.getAppId(),
                request.getGroupId(), request.getConfigKey());
        if (current == null) {
            throw new BizException("配置不存在，无法发布: key=" + request.getConfigKey());
        }

        ConfigChangeTicket ticket = new ConfigChangeTicket();
        ticket.setTicketNo(request.getTicketNo());
        ticket.setNamespaceId(request.getNamespaceId());
        ticket.setAppId(request.getAppId());
        ticket.setGroupId(request.getGroupId());
        ticket.setConfigKey(request.getConfigKey());
        ticket.setOldValue(current.getConfigValue());
        ticket.setNewValue(request.getNewValue());
        ticket.setBaseVersion(current.getVersion());
        ticket.setReleaseStrategy(request.getReleaseStrategy());
        ticket.setStatus("DRAFT");
        ticket.setOperator(request.getOperator());

        try {
            ticketMapper.insert(ticket);
        } catch (DuplicateKeyException e) {
            // 并发提交：唯一索引冲突，说明另一线程已插入，回查返回
            log.warn("[{}] concurrent submit detected, fallback to query: ticketNo={}",
                    traceId, request.getTicketNo());
            return ticketMapper.selectByTicketNo(request.getTicketNo());
        }

        // 生产环境需要审批：置为审批中并发起审批流
        if (isProdEnv(request.getNamespaceId())) {
            ticket.setStatus("APPROVING");
            ticketMapper.updateStatus(ticket.getId(), "DRAFT", "APPROVING");
            try {
                approvalClient.createApproval(buildApprovalRequest(ticket));
            } catch (Exception e) {
                // 审批系统不可用：发布单保持 APPROVING，事务不回滚提单本身，
                // 由定时补偿任务重试发起审批，避免用户重复提单
                log.error("[{}] create approval failed, will retry by scheduler: ticketNo={}",
                        traceId, request.getTicketNo(), e);
                throw new RetryableException("审批发起失败，请稍后重试或等待系统自动重试");
            }
        } else {
            ticket.setStatus("APPROVED");
            ticketMapper.updateStatus(ticket.getId(), "DRAFT", "APPROVED");
        }

        log.info("[{}] submit ticket done: ticketNo={}, status={}",
                traceId, ticket.getTicketNo(), ticket.getStatus());
        return ticket;
    }

    /**
     * 审批系统回调：审批通过。
     *
     * 幂等控制：只有当发布单处于 APPROVING 时才推进到 APPROVED，
     * 用状态机的 CAS 更新（updateStatus 带 expectedStatus）保证回调重投不会重复触发发布。
     */
    @Transactional(rollbackFor = Exception.class)
    public void onApproved(String ticketNo, String approver) {
        String traceId = TraceContext.getOrCreateTraceId();
        ConfigChangeTicket ticket = ticketMapper.selectByTicketNo(ticketNo);
        if (ticket == null) {
            log.warn("[{}] approval callback for unknown ticket: {}", traceId, ticketNo);
            return;
        }
        if (!"APPROVING".equals(ticket.getStatus())) {
            log.info("[{}] approval callback ignored, current status={}, ticketNo={}",
                    traceId, ticket.getStatus(), ticketNo);
            return; // 幂等：非审批中状态直接忽略，防止回调重复
        }
        int affected = ticketMapper.updateStatus(ticket.getId(), "APPROVING", "APPROVED");
        if (affected == 0) {
            log.info("[{}] approval CAS lost, another thread handled it: ticketNo={}",
                    traceId, ticketNo);
            return;
        }
        log.info("[{}] ticket approved: ticketNo={}, approver={}", traceId, ticketNo, approver);
    }

    private boolean isProdEnv(String namespaceId) {
        return "prod".equalsIgnoreCase(namespaceId) || "staging".equalsIgnoreCase(namespaceId);
    }

    private ApprovalRequest buildApprovalRequest(ConfigChangeTicket ticket) {
        ApprovalRequest req = new ApprovalRequest();
        req.setBizNo(ticket.getTicketNo());
        req.setTitle("配置发布审批: " + ticket.getAppId() + "/" + ticket.getConfigKey());
        req.setDetail(String.format("%s -> %s", ticket.getOldValue(), ticket.getNewValue()));
        req.setCallbackType("CONFIG_RELEASE");
        return req;
    }
```

#### 8.1.3 执行发布：先灰度，再全量

审批通过后，`ReleaseOrchestrator` 负责编排发布动作。它复用了前文的 `GrayReleaseService` 与 `ConfigPublishService`，并在外层加上发布单状态机推进与幂等保护。

```java
/**
 * 发布编排器 —— 把审批通过的发布单转化为实际的灰度/全量发布动作
 */
@Service
public class ReleaseOrchestrator {

    private static final Logger log = LoggerFactory.getLogger(ReleaseOrchestrator.class);

    @Autowired
    private ConfigChangeTicketMapper ticketMapper;
    @Autowired
    private GrayReleaseService grayReleaseService;
    @Autowired
    private ConfigPublishService configPublishService;
    @Autowired
    private ConfigItemMapper configItemMapper;

    /**
     * 执行灰度发布（发布单驱动，幂等）。
     *
     * @param ticketNo 发布单号
     * @param grayRule 灰度规则（如 10% 或指定 IP 列表）
     */
    @Transactional(rollbackFor = Exception.class)
    public void executeGrayRelease(String ticketNo, GrayRuleSpec grayRule) {
        String traceId = TraceContext.getOrCreateTraceId();
        ConfigChangeTicket ticket = loadForRelease(ticketNo, traceId);

        // 幂等：只允许从 APPROVED 推进到 GRAY_RELEASED
        if (!"APPROVED".equals(ticket.getStatus())) {
            log.info("[{}] skip gray release, status={}, ticketNo={}",
                    traceId, ticket.getStatus(), ticketNo);
            return;
        }

        // 乐观锁校验：发布单基线版本必须与当前生效版本一致，否则说明期间有人插队修改
        ConfigItem current = configItemMapper.selectByConfigId(
                ticket.getNamespaceId(), ticket.getAppId(),
                ticket.getGroupId(), ticket.getConfigKey());
        if (current.getVersion() != ticket.getBaseVersion()) {
            throw new BizException(String.format(
                    "配置在审批期间被修改，基线版本=%d, 当前版本=%d, 请重新提单",
                    ticket.getBaseVersion(), current.getVersion()));
        }

        // CAS 推进状态，防止并发/重复执行
        int affected = ticketMapper.updateStatus(ticket.getId(), "APPROVED", "GRAY_RELEASED");
        if (affected == 0) {
            log.info("[{}] gray release CAS lost, ticketNo={}", traceId, ticketNo);
            return;
        }

        try {
            GrayPublishRequest req = new GrayPublishRequest();
            req.setNamespaceId(ticket.getNamespaceId());
            req.setAppId(ticket.getAppId());
            req.setGroupId(ticket.getGroupId());
            req.setConfigKey(ticket.getConfigKey());
            req.setGrayName("ticket-" + ticketNo);
            req.setGrayType(grayRule.getType());          // IP / PERCENTAGE
            req.setGrayRule(JSON.toJSONString(grayRule));
            req.setGrayValue(ticket.getNewValue());
            req.setOperator(ticket.getOperator());
            grayReleaseService.grayPublish(req);
        } catch (Exception e) {
            // 发布动作失败：状态回退到 APPROVED，交由重试；因处于同一事务，抛出即整体回滚
            log.error("[{}] gray publish failed, rollback ticket status: ticketNo={}",
                    traceId, ticketNo, e);
            throw new BizException("灰度发布执行失败: " + e.getMessage());
        }

        log.info("[{}] gray release done: ticketNo={}, grayType={}", traceId, ticketNo, grayRule.getType());
    }

    /**
     * 灰度转全量发布（发布单驱动，幂等）。
     */
    @Transactional(rollbackFor = Exception.class)
    public void executeFullRelease(String ticketNo) {
        String traceId = TraceContext.getOrCreateTraceId();
        ConfigChangeTicket ticket = loadForRelease(ticketNo, traceId);

        if ("RELEASED".equals(ticket.getStatus())) {
            log.info("[{}] already released, idempotent return: ticketNo={}", traceId, ticketNo);
            return; // 幂等：已全量发布，直接返回
        }
        if (!"GRAY_RELEASED".equals(ticket.getStatus())) {
            throw new BizException("发布单状态非法，无法全量发布: status=" + ticket.getStatus());
        }

        int affected = ticketMapper.updateStatus(ticket.getId(), "GRAY_RELEASED", "RELEASED");
        if (affected == 0) {
            log.info("[{}] full release CAS lost, ticketNo={}", traceId, ticketNo);
            return;
        }

        try {
            // 灰度转全量：把灰度值提升为 Master 并清理灰度规则（复用前文实现）
            grayReleaseService.fullPublishFromGray(
                    ticket.getNamespaceId(), ticket.getAppId(),
                    ticket.getGroupId(), ticket.getConfigKey(), ticket.getOperator());
        } catch (Exception e) {
            log.error("[{}] full release failed: ticketNo={}", traceId, ticketNo, e);
            throw new BizException("全量发布执行失败: " + e.getMessage());
        }

        log.info("[{}] full release done: ticketNo={}", traceId, ticketNo);
    }

    private ConfigChangeTicket loadForRelease(String ticketNo, String traceId) {
        ConfigChangeTicket ticket = ticketMapper.selectByTicketNo(ticketNo);
        if (ticket == null) {
            log.error("[{}] ticket not found: {}", traceId, ticketNo);
            throw new BizException("发布单不存在: " + ticketNo);
        }
        return ticket;
    }
}
```

#### 8.1.4 客户端热更新（推送落地端）

客户端长轮询收到变更通知后，拉取最新值并热更新内存缓存，最后触发监听器回调。这里的幂等要点是：**用 MD5 判重，值没变就不触发回调**，避免推送重投导致业务方监听器被无意义地重复执行。

```java
/**
 * 客户端配置变更处理 —— 收到通知后的拉取与热更新
 * （该逻辑位于 ConfigClient 内部，此处单独展开说明）
 */
private void onConfigChanged(String configKey) {
    String traceId = TraceContext.getOrCreateTraceId();
    try {
        // 1. 拉取服务端最新值（灰度实例会命中灰度规则返回灰度值）
        ConfigValueResult result = pullSingleConfig(configKey);
        if (result == null) {
            log.warn("[{}] pull config returned null, keep old value: key={}", traceId, configKey);
            return;
        }

        String newValue = result.getValue();
        String newMd5 = result.getMd5();
        String oldMd5 = configMd5Cache.get(configKey);

        // 2. 幂等：MD5 未变化，说明是重复通知，直接忽略，不触发回调
        if (newMd5 != null && newMd5.equals(oldMd5)) {
            log.info("[{}] config md5 unchanged, skip callback: key={}, md5={}",
                    traceId, configKey, newMd5);
            return;
        }

        String oldValue = configCache.get(configKey);

        // 3. 热更新内存缓存 + 本地文件缓存
        configCache.put(configKey, newValue);
        configMd5Cache.put(configKey, newMd5);
        persistLocalCache(configKey, newValue);

        log.info("[{}] config hot-reloaded: key={}, {} -> {}",
                traceId, configKey, oldValue, newValue);

        // 4. 触发监听器回调（放到独立线程池，避免阻塞长轮询线程；单个监听器异常隔离）
        List<ConfigChangeListener> keyListeners = listeners.get(configKey);
        if (keyListeners != null) {
            ConfigChangeEvent event = new ConfigChangeEvent(configKey, oldValue, newValue);
            for (ConfigChangeListener listener : keyListeners) {
                listenerExecutor.submit(() -> {
                    try {
                        listener.onChange(event);
                    } catch (Exception e) {
                        // 单个业务监听器异常不能影响其他监听器与后续推送
                        log.error("[{}] listener callback error: key={}, listener={}",
                                traceId, configKey, listener.getClass().getName(), e);
                    }
                });
            }
        }
    } catch (IOException e) {
        // 拉取失败：保留旧值，等待下一次长轮询重试，业务不中断
        log.error("[{}] pull latest config failed, keep old value: key={}", traceId, configKey, e);
    }
}
```

#### 8.1.5 案例一小结

| 环节 | 异常处理 | 日志 | 幂等控制 |
|------|---------|------|---------|
| 提单 | 审批发起失败抛 `RetryableException`，定时补偿 | 打点 ticketNo/operator | `ticketNo` 唯一键 + 先查后建 + 唯一索引兜底 |
| 审批回调 | 未知单/非法态忽略 | 记录 approver | 状态机 CAS（APPROVING→APPROVED） |
| 灰度/全量发布 | 基线版本校验（乐观锁）、失败整体回滚 | traceId 串联 | 状态机 CAS + 已发布直接返回 |
| 客户端热更新 | 拉取失败保留旧值；监听器异常隔离 | 打点新旧值 | MD5 判重，值不变不回调 |

### 8.2 案例二：应用启动加载配置全链路

#### 8.2.1 场景描述

`order-service` 应用启动时需要加载配置中心的配置，并注入到 Spring Bean。完整链路为：

```
应用启动
   → ConfigClient.start()
   → 优先加载本地文件缓存（保证 Server 挂了也能启动）
   → 从 Server 拉取全量配置（失败则降级用本地缓存）
   → 批量写入内存缓存 + 本地文件缓存
   → 通过 BeanPostProcessor 注入 @DynamicConfig 字段
   → 关键配置缺失时执行启动降级策略（用默认值/兜底继续启动，或强依赖时快速失败）
   → 启动长轮询，进入运行态
```

启动阶段的核心诉求是：**配置中心不可用不能阻塞应用启动**。因此三级容灾（内存 → 本地文件 → 默认值）在启动链路必须闭环。

#### 8.2.2 启动加载编排

```java
/**
 * 应用启动配置加载器 —— 在 Spring 容器刷新早期完成配置拉取与缓存预热
 */
public class ConfigBootstrapLoader {

    private static final Logger log = LoggerFactory.getLogger(ConfigBootstrapLoader.class);

    /** 启动拉取的最大重试次数 */
    private static final int MAX_PULL_RETRY = 3;
    /** 每次重试间隔 */
    private static final long PULL_RETRY_INTERVAL_MS = 1000L;

    private final ConfigClient configClient;
    private final ConfigClientFailover failover;
    /** 强依赖配置键：缺失则启动失败（fail-fast） */
    private final Set<String> requiredKeys;

    public ConfigBootstrapLoader(ConfigClient configClient,
                                 ConfigClientFailover failover,
                                 Set<String> requiredKeys) {
        this.configClient = configClient;
        this.failover = failover;
        this.requiredKeys = requiredKeys == null ? Collections.emptySet() : requiredKeys;
    }

    /**
     * 启动加载入口。
     *
     * 幂等控制：用 loaded 标记 + CAS 保证多线程/重复调用只加载一次。
     */
    private final AtomicBoolean loaded = new AtomicBoolean(false);

    public void load() {
        if (!loaded.compareAndSet(false, true)) {
            log.info("config bootstrap already loaded, skip");
            return; // 幂等：重复调用直接返回
        }

        String traceId = TraceContext.getOrCreateTraceId();
        log.info("[{}] config bootstrap start", traceId);

        // Step 1: 先加载本地文件缓存，保证即使 Server 不可用也有可用配置
        Map<String, String> localSnapshot = Collections.emptyMap();
        try {
            localSnapshot = failover.loadAllFromLocalFile();
            log.info("[{}] local cache loaded, keys={}", traceId, localSnapshot.size());
        } catch (Exception e) {
            log.warn("[{}] load local cache failed, continue: {}", traceId, e.getMessage());
        }

        // Step 2: 从 Server 拉取全量配置（带重试）
        Map<String, String> remoteConfig = pullWithRetry(traceId);

        // Step 3: 决定最终生效配置
        boolean usingRemote = remoteConfig != null && !remoteConfig.isEmpty();
        Map<String, String> effective = usingRemote ? remoteConfig : localSnapshot;

        if (effective.isEmpty()) {
            log.error("[{}] both remote and local config empty!", traceId);
        }

        // Step 4: 批量写入内存 + 回刷本地文件缓存
        failover.batchUpdateConfig(effective);

        // Step 5: 启动降级校验 —— 强依赖配置缺失处理
        checkRequiredConfigs(effective, usingRemote, traceId);

        log.info("[{}] config bootstrap done, source={}, keys={}",
                traceId, usingRemote ? "REMOTE" : "LOCAL_CACHE", effective.size());
    }

    private Map<String, String> pullWithRetry(String traceId) {
        for (int i = 1; i <= MAX_PULL_RETRY; i++) {
            try {
                Map<String, String> remote = configClient.pullFullConfigAsMap();
                log.info("[{}] pull remote config success on attempt {}, keys={}",
                        traceId, i, remote.size());
                return remote;
            } catch (Exception e) {
                log.warn("[{}] pull remote config failed, attempt {}/{}: {}",
                        traceId, i, MAX_PULL_RETRY, e.getMessage());
                if (i < MAX_PULL_RETRY) {
                    sleepQuietly(PULL_RETRY_INTERVAL_MS);
                }
            }
        }
        // 重试耗尽：不抛异常，返回 null 触发本地缓存降级，保证应用能启动
        log.error("[{}] pull remote config exhausted, will fall back to local cache", traceId);
        return null;
    }

    /**
     * 启动降级策略：
     * - 强依赖配置缺失且无本地缓存兜底 -> 快速失败，避免带病启动；
     * - 非强依赖缺失 -> 记录告警，由 @DynamicConfig 的 defaultValue 兜底。
     */
    private void checkRequiredConfigs(Map<String, String> effective,
                                      boolean usingRemote, String traceId) {
        List<String> missing = new ArrayList<>();
        for (String key : requiredKeys) {
            if (!effective.containsKey(key) || effective.get(key) == null) {
                missing.add(key);
            }
        }
        if (missing.isEmpty()) {
            return;
        }
        if (!usingRemote) {
            // 用本地缓存启动，且缺失强依赖：告警但允许启动（降级运行）
            log.error("[{}] required configs missing under LOCAL_CACHE degraded mode: {}",
                    traceId, missing);
            return;
        }
        // 远端在线却缺失强依赖：配置本身有问题，fail-fast
        throw new IllegalStateException(
                "启动失败：缺失强依赖配置 " + missing + "，请检查配置中心");
    }

    private void sleepQuietly(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

#### 8.2.3 配置注入 Spring Bean

启动加载完成后，配置需要注入到业务 Bean。前文 `DynamicConfigProcessor`（`BeanPostProcessor`）已实现字段注入与监听绑定，这里在其基础上补充启动注入时的降级与异常隔离。

```java
/**
 * 动态配置注入处理器 —— 启动时注入初值，并注册变更监听实现热更新
 */
@Component
public class DynamicConfigInjector implements BeanPostProcessor {

    private static final Logger log = LoggerFactory.getLogger(DynamicConfigInjector.class);

    @Autowired
    private ConfigClientFailover failover;
    @Autowired
    private ConfigClient configClient;

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        Class<?> clazz = bean.getClass();
        for (Field field : clazz.getDeclaredFields()) {
            DynamicConfig anno = field.getAnnotation(DynamicConfig.class);
            if (anno == null) {
                continue;
            }
            injectField(bean, beanName, field, anno);
            bindListener(bean, beanName, field, anno);
        }
        return bean;
    }

    /**
     * 注入初始值：优先取生效配置，缺失则用注解 defaultValue 降级。
     */
    private void injectField(Object bean, String beanName, Field field, DynamicConfig anno) {
        String key = anno.key();
        String value = failover.getConfig(key, anno.defaultValue());
        try {
            ReflectionUtils.makeAccessible(field);
            setFieldValue(bean, field, value);
            log.info("inject config: bean={}, field={}, key={}, value={}",
                    beanName, field.getName(), key, value);
        } catch (Exception e) {
            // 注入失败（如类型转换异常）：使用默认值兜底，保证 Bean 可用，不阻塞启动
            log.error("inject config failed, fallback to default: bean={}, key={}, default={}",
                    beanName, key, anno.defaultValue(), e);
            try {
                setFieldValue(bean, field, anno.defaultValue());
            } catch (Exception ex) {
                log.error("fallback inject also failed: bean={}, key={}", beanName, key, ex);
            }
        }
    }

    /**
     * 绑定变更监听器实现热更新。
     *
     * 幂等控制：监听器内部通过重新读取并比较目标字段现值，避免重复回调导致的无意义 set。
     */
    private void bindListener(Object bean, String beanName, Field field, DynamicConfig anno) {
        configClient.addListener(anno.key(), event -> {
            try {
                ReflectionUtils.makeAccessible(field);
                Object currentVal = field.get(bean);
                Object newVal = convert(event.getNewValue(), field.getType());
                if (Objects.equals(currentVal, newVal)) {
                    return; // 幂等：值未变，跳过
                }
                setFieldValue(bean, field, event.getNewValue());
                log.info("hot update config field: bean={}, field={}, key={}, {} -> {}",
                        beanName, field.getName(), anno.key(), currentVal, newVal);
            } catch (Exception e) {
                log.error("hot update config field failed: bean={}, key={}",
                        beanName, anno.key(), e);
            }
        });
    }

    private void setFieldValue(Object bean, Field field, String rawValue) throws IllegalAccessException {
        Object typed = convert(rawValue, field.getType());
        field.set(bean, typed);
    }

    private Object convert(String value, Class<?> type) {
        if (value == null) {
            return null;
        }
        if (type == int.class || type == Integer.class) {
            return Integer.parseInt(value.trim());
        }
        if (type == long.class || type == Long.class) {
            return Long.parseLong(value.trim());
        }
        if (type == boolean.class || type == Boolean.class) {
            return Boolean.parseBoolean(value.trim());
        }
        if (type == double.class || type == Double.class) {
            return Double.parseDouble(value.trim());
        }
        return value;
    }
}
```

#### 8.2.4 启动降级策略总览

```
启动降级决策树：

从 Server 拉取全量配置
   │
   ├── 成功 ──> 用远端配置，回刷本地缓存
   │              │
   │              └── 强依赖配置缺失? ──是──> fail-fast，拒绝启动（配置本身有问题）
   │                                   └─否─> 正常启动
   │
   └── 失败（重试 3 次仍失败）
          │
          ├── 本地文件缓存存在 ──> 用本地缓存降级启动（告警），长轮询后台持续重连
          │                          │
          │                          └── 强依赖缺失? ──是──> 告警但允许启动（降级运行）
          │                                          └─否─> 降级启动
          │
          └── 本地缓存也没有 ──> 仅靠 @DynamicConfig 的 defaultValue 兜底启动（严重告警）
```

#### 8.2.5 案例二小结

| 环节 | 异常处理 | 日志 | 幂等控制 |
|------|---------|------|---------|
| 启动加载 | 拉取重试 3 次，失败降级本地缓存 | traceId + 数据来源 | `AtomicBoolean` CAS 只加载一次 |
| 强依赖校验 | 远端在线缺失则 fail-fast；降级态告警放行 | 打印缺失 key 列表 | —— |
| Bean 注入 | 注入失败用 defaultValue 兜底 | 记录 bean/field/key | —— |
| 热更新监听 | 单监听器异常隔离 | 打点新旧值 | 现值比较，值不变不 set |

### 8.3 案例三：配置回滚全链路

#### 8.3.1 场景描述

上线新的连接池配置 `db.pool.maxActive=500` 后，监控发现数据库连接被打满、错误率飙升。值班同学需要立即把配置回滚到上一个稳定版本。完整链路为：

```
监控/人工发现配置问题（错误率飙升 / 连接打满）
   → 打开配置版本历史，定位最近一个稳定版本
   → 发起回滚（选择目标版本）
   → ConfigPublishService.rollbackToVersion（写库 + 版本+1 + 回滚事件）
   → 全量推送（通知所有长轮询客户端）
   → 客户端拉取回滚后的值，热更新
   → 验证生效（校验各实例配置 MD5 一致 + 监控恢复）
```

回滚的本质是"用历史版本的值创建一个新版本"（前文 `rollbackToVersion` 已实现），因此天然可审计、可再回滚。

#### 8.3.2 回滚编排与全量推送

```java
/**
 * 配置回滚编排器 —— 发起回滚、全量推送、并驱动生效校验
 */
@Service
public class ConfigRollbackOrchestrator {

    private static final Logger log = LoggerFactory.getLogger(ConfigRollbackOrchestrator.class);

    @Autowired
    private ConfigPublishService configPublishService;
    @Autowired
    private ConfigItemMapper configItemMapper;
    @Autowired
    private ConfigHistoryMapper configHistoryMapper;
    @Autowired
    private ConfigRollbackRecordMapper rollbackRecordMapper;
    @Autowired
    private PushVerificationService verificationService;

    /**
     * 执行回滚（幂等）。
     *
     * 幂等控制：以 rollbackNo（回滚单号）为业务唯一键落一条回滚记录，
     * 重复请求（重复点击、超时重试）识别后直接返回，不会重复回滚扣版本。
     */
    @Transactional(rollbackFor = Exception.class)
    public RollbackResult rollback(RollbackRequest request) {
        String traceId = TraceContext.getOrCreateTraceId();
        String rollbackNo = request.getRollbackNo();
        log.warn("[{}] rollback start: rollbackNo={}, app={}, key={}, targetVersion={}, operator={}",
                traceId, rollbackNo, request.getAppId(), request.getConfigKey(),
                request.getTargetVersion(), request.getOperator());

        // 幂等：回滚单号唯一
        ConfigRollbackRecord exist = rollbackRecordMapper.selectByRollbackNo(rollbackNo);
        if (exist != null) {
            log.info("[{}] rollback already executed, idempotent return: rollbackNo={}, newVersion={}",
                    traceId, rollbackNo, exist.getNewVersion());
            return RollbackResult.of(exist.getNewVersion(), true);
        }

        // 校验目标版本存在
        ConfigHistory target = configHistoryMapper.selectByVersion(
                request.getNamespaceId(), request.getAppId(), request.getGroupId(),
                request.getConfigKey(), request.getTargetVersion());
        if (target == null) {
            throw new BizException("目标回滚版本不存在: version=" + request.getTargetVersion());
        }

        ConfigItem current = configItemMapper.selectByConfigId(
                request.getNamespaceId(), request.getAppId(),
                request.getGroupId(), request.getConfigKey());
        if (current == null) {
            throw new BizException("配置不存在，无法回滚: key=" + request.getConfigKey());
        }

        // 防呆：目标值与当前值相同，无需回滚
        if (Objects.equals(current.getConfigValue(), target.getNewValue())) {
            log.info("[{}] target value equals current, skip rollback: key={}",
                    traceId, request.getConfigKey());
            return RollbackResult.of(current.getVersion(), true);
        }

        int expectedNewVersion = current.getVersion() + 1;

        // 先落回滚记录（幂等锚点），唯一索引兜底并发
        ConfigRollbackRecord record = new ConfigRollbackRecord();
        record.setRollbackNo(rollbackNo);
        record.setNamespaceId(request.getNamespaceId());
        record.setAppId(request.getAppId());
        record.setGroupId(request.getGroupId());
        record.setConfigKey(request.getConfigKey());
        record.setFromVersion(current.getVersion());
        record.setTargetVersion(request.getTargetVersion());
        record.setNewVersion(expectedNewVersion);
        record.setOperator(request.getOperator());
        try {
            rollbackRecordMapper.insert(record);
        } catch (DuplicateKeyException e) {
            log.warn("[{}] concurrent rollback detected, fallback to query: rollbackNo={}",
                    traceId, rollbackNo);
            ConfigRollbackRecord done = rollbackRecordMapper.selectByRollbackNo(rollbackNo);
            return RollbackResult.of(done.getNewVersion(), true);
        }

        try {
            // 复用前文实现：用目标历史版本的值创建新版本 + 写回滚事件 + 全量通知客户端
            configPublishService.rollbackToVersion(
                    request.getNamespaceId(), request.getAppId(), request.getGroupId(),
                    request.getConfigKey(), request.getTargetVersion(), request.getOperator());
        } catch (Exception e) {
            // 回滚执行失败：整个事务回滚（含回滚记录），对外抛出让调用方重试
            log.error("[{}] rollback execution failed, tx will rollback: rollbackNo={}",
                    traceId, rollbackNo, e);
            throw new BizException("回滚执行失败: " + e.getMessage());
        }

        log.warn("[{}] rollback done: rollbackNo={}, {} -> version {} (value of v{})",
                traceId, rollbackNo, current.getVersion(), expectedNewVersion,
                request.getTargetVersion());
        return RollbackResult.of(expectedNewVersion, false);
    }

    /**
     * 回滚后生效校验：确认各客户端实例都已收敛到回滚后的版本。
     */
    public RollbackVerifyResult verifyRollback(RollbackRequest request, int newVersion) {
        String traceId = TraceContext.getOrCreateTraceId();
        try {
            // 复用推送校验服务：比对各实例上报的 MD5 与服务端目标 MD5
            PushVerifyReport report = verificationService.verifyPush(
                    request.getNamespaceId(), request.getAppId(),
                    request.getGroupId(), request.getConfigKey());

            boolean allConverged = report.getMismatchInstances().isEmpty();
            if (allConverged) {
                log.info("[{}] rollback verified: all {} instances converged to version {}",
                        traceId, report.getTotalInstances(), newVersion);
            } else {
                // 部分实例未收敛：告警并触发补偿推送，不影响已生效实例
                log.error("[{}] rollback NOT fully converged: mismatch={}, total={}",
                        traceId, report.getMismatchInstances(), report.getTotalInstances());
            }
            return new RollbackVerifyResult(allConverged, report);
        } catch (Exception e) {
            log.error("[{}] rollback verify failed: key={}", traceId, request.getConfigKey(), e);
            return new RollbackVerifyResult(false, null);
        }
    }
}
```

#### 8.3.3 回滚生效校验（推送落地端）

验证阶段要回答"回滚是否真的在每台机器上生效了"。做法是让客户端定时上报当前配置的 MD5，服务端聚合比对。

```java
/**
 * 客户端配置版本上报 —— 供服务端做回滚/发布生效校验
 * （运行于 ConfigClient 内部的定时上报任务）
 */
private void reportConfigDigest() {
    String traceId = TraceContext.getOrCreateTraceId();
    try {
        List<ConfigDigest> digests = new ArrayList<>();
        configMd5Cache.forEach((key, md5) ->
                digests.add(new ConfigDigest(key, md5)));

        InstanceReport report = new InstanceReport();
        report.setNamespaceId(namespaceId);
        report.setAppId(appId);
        report.setInstanceIp(NetUtils.getLocalIp());
        report.setDigests(digests);

        boolean ok = postReport(selectServer() + "/api/config/report", report);
        if (!ok) {
            log.warn("[{}] report config digest not accepted, will retry next round", traceId);
        }
    } catch (Exception e) {
        // 上报失败不影响业务，仅影响服务端可观测性，下个周期重试
        log.warn("[{}] report config digest failed: {}", traceId, e.getMessage());
    }
}
```

#### 8.3.5 案例三小结

| 环节 | 异常处理 | 日志 | 幂等控制 |
|------|---------|------|---------|
| 发起回滚 | 目标版本不存在/配置不存在抛 `BizException`；执行失败整体回滚 | warn 级串 traceId | `rollbackNo` 唯一键 + 先查后建 + 唯一索引兜底 |
| 值相同防呆 | 目标值==当前值直接返回 | 记录 skip | 避免无意义扣版本 |
| 全量推送 | 复用回滚事件通知，失败重试 | 打点新旧版本 | 客户端 MD5 判重 |
| 生效校验 | 未收敛告警 + 补偿推送；校验异常降级 | 打印 mismatch 实例 | 上报可重复，幂等聚合 |

### 8.4 三个案例的共性工程经验

1. **状态机 + 唯一键是幂等的两把钥匙**：写操作（发布、回滚）用业务唯一单号（ticketNo/rollbackNo）加唯一索引挡住重复请求；状态流转用 CAS（带 expectedStatus 的 update）挡住并发与回调重投。

2. **失败要有明确的降级方向**：启动链路失败降级到本地缓存，绝不阻塞启动；发布/回滚执行失败则整体事务回滚并对外抛出，交由上层重试，宁可不生效也不产生脏数据。

3. **全链路一个 traceId**：从 Portal 提单到客户端热更新，关键节点都带上同一个 traceId，排查"配置为什么没生效"时能一路串起来。

4. **值不变不动作**：无论是推送落地还是字段注入，都以 MD5 / 现值比较作为最后一道幂等闸门，避免重复通知引发业务监听器的无意义抖动。

5. **生效必须可验证**：发布和回滚都不是"推出去就完事"，通过客户端 MD5 上报 + 服务端聚合比对，明确回答"是否所有实例都已收敛"，未收敛则补偿推送。
