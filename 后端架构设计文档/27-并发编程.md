# Java并发编程：从底层原理到工程实践

## 1. 问题背景

### 1.1 CPU、内存与I/O设备的速度鸿沟

现代计算机体系结构中，CPU、内存和I/O设备之间存在巨大的速度差异：

| 设备 | 访问延迟 | 相对速度比 |
|------|---------|--------|
| CPU寄存器 / L1 Cache | ~1ns | 1 |
| L2 Cache | ~3ns | 3 |
| L3 Cache | ~10ns | 10 |
| 主内存（DRAM） | ~100ns | 100 |
| SSD磁盘 | ~100μs | 100,000 |
| 机械磁盘 | ~10ms | 10,000,000 |

CPU执行一条指令约1纳秒，而访问内存需要约100纳秒，访问磁盘则需要数十毫秒。如果CPU串行等待每一次内存和I/O操作，其利用率会极低。

### 1.2 三种解决方案

为平衡这种速度差异，计算机体系结构和操作系统分别从三个层面做出优化：

**（1）CPU增加多级缓存** —— 平衡CPU与内存的速度差异。CPU不直接读写主内存，而是先把数据加载到L1/L2/L3高速缓存中，利用程序的时间/空间局部性，缓存命中率可达95%以上。

**（2）操作系统引入进程与线程** —— 平衡CPU与I/O设备的速度差异。当线程因等待I/O而阻塞时，操作系统可通过上下文切换让CPU执行其他线程，避免CPU因等待I/O而空闲。

**（3）编译器与CPU指令重排序** —— 充分利用CPU流水线。编译器和CPU可以在不改变单线程语义的前提下调整指令执行顺序，减少流水线阻塞，提升吞吐率。

### 1.3 三种方案引发的三大并发问题

这三种优化方案在多线程环境下分别引发了三个核心问题：

| 优化方案 | 引发的并发问题 | 本质原因 |
|---------|--------------|---------|
| CPU缓存 | **可见性问题** | 多核CPU各自缓存，导致共享变量在不同核心间不一致 |
| 线程切换 | **原子性问题** | 高级语言一条语句对应多条CPU指令，线程切换可能发生在指令间隙 |
| 指令重排序 | **有序性问题** | 编译器/CPU重排序后，多线程执行结果可能与代码顺序预期不符 |

理解这三个问题的本质，是学习Java并发编程的基石，也是后续所有工具（volatile、synchronized、JMM）设计初衷的来源。

## 2. 整体架构设计

### 2.1 并发编程的三大核心问题

从工程角度看，并发编程需要解决三大核心问题：**分工（Division of Work）**、**同步（Synchronization）**、**互斥（Mutual Exclusion）**。

- **分工：** 如何将大任务拆分给多个线程并行执行 —— ThreadPoolExecutor、ForkJoinPool、Future、CompletableFuture。
- **同步：** 线程之间如何协调执行顺序，一个线程如何等待另一个线程的结果 —— wait/notify、Condition、CountDownLatch、CyclicBarrier、Semaphore。
- **互斥：** 同一时刻只允许一个线程访问共享资源 —— synchronized、ReentrantLock、ReadWriteLock、原子类。

### 2.2 Java并发工具全景图

```
应用层：线程池 / 并发容器 / Future / CompletableFuture
工具层：ReentrantLock / Semaphore / CountDownLatch / CyclicBarrier / ReadWriteLock
基础层：synchronized / volatile / final / CAS(Unsafe) / AQS / Atomic*
规范层：Java内存模型（JMM）/ Happens-Before规则
硬件层：CPU Cache / MESI协议 / Memory Barrier / 指令重排序
```

各层自底向上逐层封装：硬件层的问题由JMM规范化，JMM之上构建了volatile/synchronized/CAS等基础同步原语，再向上封装出AQS及其衍生的高层工具，最终服务于业务层的线程池与并发容器。

## 3. 核心链路设计

### 3.1 并发三大问题

#### 3.1.1 可见性问题（Visibility）

**问题根源：CPU缓存。** 多核CPU中每个核心都有独立的L1/L2缓存。线程A运行在核心1上修改共享变量V，写入的是核心1的缓存，尚未刷新到主内存；线程B运行在核心2上读取V，读到的是自己缓存中的旧值。这就是可见性问题。

```java
public class VisibilityProblem {
    private static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> { for (int i = 0; i < 10000; i++) count++; };
        Thread t1 = new Thread(task), t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();
        // 预期20000，实际往往小于20000
        System.out.println("count = " + count);
    }
}
```

两个线程各自在CPU缓存中读取、修改count，写回主内存的时机不确定，导致一部分自增操作互相覆盖丢失，既有可见性问题也有原子性问题。

**MESI缓存一致性协议：** 硬件层面通过MESI协议维护缓存行的四种状态：M（Modified，已修改）、E（Exclusive，独占）、S（Shared，共享）、I（Invalid，失效）。当某个核心修改了缓存行，会通过总线嗅探通知其他核心将对应缓存行标记为I，其他核心下次访问时会重新从主内存加载。但由于Store Buffer、Invalidate Queue等异步优化机制的存在，MESI协议不能完全消除可见性问题，因此Java仍需在软件层面提供volatile和JMM作为补充。

#### 3.1.2 原子性问题（Atomicity）

**问题根源：线程切换。** 原子性指一个或多个操作在CPU执行过程中不可被中断。`count++` 在CPU层面实际是三条指令：

```
LOAD  count 到寄存器
ADD   寄存器值加1
STORE 寄存器值写回内存
```

操作系统基于时间片调度线程，线程切换可能发生在这三条指令之间的任意位置。例如线程A执行完LOAD和ADD后被切换出去，线程B执行了完整的LOAD-ADD-STORE，随后线程A恢复执行STORE，会用自己寄存器中的旧计算结果覆盖线程B的结果，导致一次自增丢失。

```java
public class AtomicityProblem {
    private static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            threads[i] = new Thread(() -> { for (int j = 0; j < 10000; j++) count++; });
            threads[i].start();
        }
        for (Thread t : threads) t.join();
        // 预期100000，实际是小于100000的随机值
        System.out.println("count = " + count);
    }
}
```

在64位JVM上基本类型的单次读写是原子的，但任何复合操作（i++、i += 1、check-then-act）都不是原子的。

#### 3.1.3 有序性问题（Ordering）

**问题根源：指令重排序。** 编译器和CPU可能在不影响单线程执行结果的前提下调整指令顺序。经典案例是双重检查锁定（DCL）单例：

```java
public class Singleton {
    private static Singleton instance; // 缺少volatile

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton(); // 问题所在
                }
            }
        }
        return instance;
    }
}
```

`instance = new Singleton()` 实际分为三步：① 分配内存 ② 初始化对象 ③ 将instance指向内存地址。指令重排序可能把顺序变成 ①③②，即先让instance指向未初始化的内存，再执行构造函数。此时如果线程B在①③之后、②之前读取instance，会发现instance != null，直接返回一个尚未初始化完成的对象，读到字段的默认值而非真实初始化值。

正确写法是给instance加上volatile：

```java
private static volatile Singleton instance; // volatile禁止重排序，保证可见性
```

### 3.2 Java内存模型（JMM）

#### 3.2.1 JMM概述

Java内存模型（JMM）规定：所有共享变量存储在**主内存**中，每个线程有自己的**工作内存**，保存共享变量的副本；线程只能操作工作内存，线程间通信必须通过主内存中转。JMM本质上定义了一种偏序关系——**Happens-Before**，用来描述两个操作之间的内存可见性：如果操作A Happens-Before操作B，那么A的结果对B可见。

#### 3.2.2 Happens-Before八条规则

**规则1：程序顺序规则。** 同一线程内，代码前面的操作Happens-Before后面的操作（编译器可重排序，但必须保证单线程语义不变）。

**规则2：监视器锁规则。** 对一个锁的解锁 Happens-Before 后续对同一把锁的加锁。

```java
public synchronized void setValue(int v) { this.value = v; }   // 释放锁
public synchronized int getValue() { return this.value; }       // 获取锁后一定能看到最新value
```

**规则3：volatile变量规则。** 对volatile变量的写 Happens-Before 后续对该变量的读。

```java
private volatile boolean flag = false;
private int data = 0;

// 线程A：data=42; flag=true;
// 线程B：if (flag) { 读到的data一定是42 }  —— 依据程序顺序+volatile+传递性
```

**规则4：线程启动规则。** `Thread.start()` Happens-Before 该线程内的每一个操作。

**规则5：线程终止规则。** 线程内的所有操作 Happens-Before 其他线程通过 `join()` 检测到该线程结束。

**规则6：线程中断规则。** `interrupt()` 的调用 Happens-Before 被中断线程检测到中断事件（`isInterrupted()`）。

**规则7：对象终结规则。** 构造函数执行结束 Happens-Before `finalize()` 方法开始。

**规则8：传递性。** A Happens-Before B，B Happens-Before C，则A Happens-Before C。

#### 3.2.3 JMM解决了什么

| | 可见性 | 有序性 | 原子性 |
|---|---|---|---|
| volatile | √ | √ | × |
| synchronized | √ | √ | √ |
| Atomic* | √ | √ | √ |

JMM及其Happens-Before规则解决了**可见性**和**有序性**问题，但**不解决原子性问题**，原子性需要依赖锁或原子类来保证。

### 3.3 Synchronized锁升级

#### 3.3.1 Monitor机制

synchronized在JVM层面通过Monitor（管程）实现。每个对象都关联一个ObjectMonitor，其核心字段包括：

- **`_owner`**：当前持有锁的线程
- **`_recursions`**：重入次数
- **ContentionList**：新来的竞争线程首先进入的队列
- **EntryList**：从ContentionList转移过来、有资格竞争锁的线程队列
- **WaitSet**：调用`wait()`后进入等待、被`notify()`唤醒后转入EntryList的线程队列

```
ContentionList ──转移──> EntryList ──获取锁──> Owner ──wait()──> WaitSet
                                                    ▲                  │
                                                    └────notify()唤醒──┘
```

synchronized代码块编译后生成`monitorenter`/`monitorexit`字节码指令：

```java
synchronized (obj) {
    // 临界区代码
}
// 编译后大致对应：
//   monitorenter          // 获取obj的Monitor，_owner置为当前线程，_recursions+1
//   ... 临界区字节码 ...
//   monitorexit            // 正常退出释放锁
//   ... 异常表 ...
//   monitorexit            // 异常路径也会释放锁，确保锁一定被释放
```

编译器会在异常处理路径上额外生成一条`monitorexit`，确保即便临界区抛出异常，锁也一定会被释放，不会造成锁泄漏。

在JDK 1.6之前，synchronized直接基于操作系统的Mutex Lock实现，获取/释放锁需要用户态到内核态的切换，开销高达数十微秒。正因如此，JDK 1.6引入了锁升级机制：**偏向锁 → 轻量级锁 → 自旋锁 → 重量级锁**，逐级递进只在必要时才付出重量级同步的代价。

#### 3.3.2 Java对象头 Mark Word

对象头中的Mark Word（64位）根据锁状态呈现不同布局：

```
无锁态   (锁标志01, 偏向0): unused(25) | hashcode(31) | unused(1) | age(4) | 0 | 01
偏向锁   (锁标志01, 偏向1): thread ID(54) | epoch(2) | unused(1) | age(4) | 1 | 01
轻量级锁 (锁标志00): 指向栈中Lock Record的指针(62) | 00
重量级锁 (锁标志10): 指向ObjectMonitor的指针(62) | 10
GC标记   (锁标志11): 空(62) | 11
```

锁升级的本质就是Mark Word中锁标志位和存储内容的变化过程。

#### 3.3.3 偏向锁（Biased Locking）

**设计动机：** 大多数场景中锁不存在多线程竞争，且总是被同一线程反复获得。偏向锁让该线程后续再次进入同步块时无需任何同步操作。

**获取流程：** 第一次获取锁时，通过CAS将Mark Word中的Thread ID设为当前线程；此后同一线程再次进入，只需比较Thread ID是否等于自身，无需CAS。若CAS失败（说明有竞争）或Thread ID属于其他线程，则触发**偏向锁撤销**：JVM需要等待全局安全点（SafePoint，所有线程暂停），检查原持锁线程是否还存活、是否仍在同步块中，进而决定重新偏向新线程还是直接升级为轻量级锁。

由于撤销过程需要等待全局安全点，代价较高，JDK 15开始偏向锁被标记为废弃（`-XX:-UseBiasedLocking`），JDK 18中已被移除，取而代之的是更快的CAS操作和轻量级锁。

#### 3.3.4 轻量级锁（Lightweight Locking）

**设计动机：** 适用于多线程**交替**执行同步块（无激烈竞争）的场景。

**获取流程：** 线程在自己的栈帧中创建Lock Record，将对象Mark Word复制为Displaced Mark Word；然后通过CAS将对象的Mark Word替换为指向该Lock Record的指针。CAS成功则获取轻量级锁成功；CAS失败则检查Mark Word是否指向当前线程栈帧（是则为锁重入），否则说明存在竞争，进入自旋尝试，自旋失败则膨胀为重量级锁。

释放时，通过CAS将Displaced Mark Word换回对象头；如果CAS失败，说明持锁期间已有其他线程膨胀为重量级锁，此时需要释放锁并唤醒被阻塞的线程。

#### 3.3.5 自旋锁（Spin Locking）

线程阻塞/唤醒涉及用户态到内核态的切换，开销巨大。如果临界区代码执行很短，让等待线程原地自旋（忙等）可能比阻塞更高效。JDK 1.6引入**自适应自旋**：JVM根据同一锁对象最近一次自旋是否成功来动态调整本次允许的自旋次数——最近成功则允许更长时间自旋，最近失败则减少甚至跳过自旋直接阻塞。

#### 3.3.6 重量级锁（Heavyweight Locking）

自旋失败后，锁膨胀为重量级锁，基于操作系统Mutex Lock实现。线程尝试获取`_owner`失败后，会先自旋，仍失败则封装为节点加入ContentionList，随后被操作系统挂起。持锁线程释放时，从ContentionList转移部分节点到EntryList，并唤醒其中一个线程重新竞争锁。

**完整锁升级路径：**

```
┌────────┐  首次加锁   ┌────────┐  第二线程竞争，撤销偏向  ┌─────────┐  CAS失败/自旋仍失败  ┌─────────┐
│ 无锁态  │ ─────────> │ 偏向锁  │ ───────────────────>   │ 轻量级锁 │ ───────────────────> │ 重量级锁 │
└────────┘            └────────┘   （等待全局SafePoint）  └─────────┘   （自适应自旋失败）    └─────────┘
```

锁只能升级，不能降级，这是JVM为了避免在高竞争场景下反复升降级带来的额外开销所做的权衡。下表汇总了四种锁状态的适用场景与代价：

| 锁状态 | 适用场景 | 加锁开销 | 缺点 |
|---|---|---|---|
| 偏向锁 | 单线程反复获取同一把锁 | 仅首次CAS，之后比较Thread ID | 撤销需等待安全点，JDK 15+已废弃 |
| 轻量级锁 | 多线程交替执行，无激烈竞争 | CAS替换Mark Word | 竞争加剧时需要自旋或膨胀 |
| 自旋锁 | 临界区执行时间很短 | CPU忙等，不阻塞线程 | 长时间自旋浪费CPU |
| 重量级锁 | 多线程长时间激烈竞争 | 用户态/内核态切换 | 线程阻塞/唤醒开销大 |

### 3.4 CAS与ABA问题

#### 3.4.1 CAS原理

CAS（Compare And Swap）包含三个操作数：内存值V、预期值E、新值N。语义为：当且仅当V==E时，才将V更新为N，整个操作由CPU硬件（如x86的CMPXCHG+LOCK前缀）保证原子性。Java通过`sun.misc.Unsafe`提供CAS原语，`AtomicInteger`等原子类基于此实现：

```java
public final int getAndIncrement() {
    return unsafe.getAndAddInt(this, valueOffset, 1);
}
// 内部实现思路：
// do { v = getIntVolatile(obj, offset); }
// while (!compareAndSwapInt(obj, offset, v, v + delta));
```

CAS的优点是无需阻塞线程、避免内核态切换，适合读多写少、竞争不激烈的场景；缺点是竞争激烈时自旋消耗CPU，且只能保证单个变量的原子性，同时存在ABA问题。

#### 3.4.2 ABA问题及解决方案

CAS只检查"当前值是否等于预期值"，无法感知"值是否被修改过又改回来"。例如线程T1读取V=A，尚未CAS前，线程T2把V从A改为B再改回A，T1的CAS仍会成功，但期间V实际上发生过变化——如果这是链表节点引用，可能导致数据结构被破坏（如无锁栈中节点被重复使用）。

**解决方案：AtomicStampedReference（版本戳）。** 在比较值的同时比较一个版本号，只有值和版本号都匹配才更新成功：

```java
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
int stamp = ref.getStamp();
String value = ref.getReference();
// ... 期间其他线程做了 A→B→A 的修改，版本号从0变为2 ...
boolean success = ref.compareAndSet(value, "C", stamp, stamp + 1);
// success为false，因为版本号不匹配，即使值仍然是"A"
```

**解决方案：AtomicMarkableReference（布尔标记）。** 只关心"是否被修改过"而不关心修改次数时，可用布尔标记代替版本号，用法与AtomicStampedReference类似，`compareAndSet(expectedRef, newRef, expectedMark, newMark)`。

### 3.5 volatile语义

#### 3.5.1 可见性与有序性保证

volatile提供两个语义：**可见性**和**有序性**，但**不保证原子性**。

- **可见性：** 写volatile变量时，JMM强制将该线程工作内存中的修改刷新到主内存；读volatile变量时，强制使工作内存缓存失效，重新从主内存加载。
- **有序性：** 通过插入内存屏障禁止特定重排序。JMM定义四种屏障：LoadLoad、StoreStore、LoadStore、StoreLoad。volatile写前插入StoreStore屏障、写后插入StoreLoad屏障；volatile读后插入LoadLoad和LoadStore屏障，从而保证volatile写之前的普通写不会被重排到写之后，volatile读之后的普通读写不会被重排到读之前。

#### 3.5.2 不保证原子性

```java
private static volatile int count = 0;
// count++ 依然是LOAD-ADD-STORE三步操作
// volatile只保证每一步单独执行时读到最新值、写完立刻可见
// 但LOAD和STORE之间仍可能被其他线程的完整count++操作打断
```

#### 3.5.3 典型使用场景

**状态标志：**

```java
private volatile boolean stop = false;
public void shutdown() { stop = true; }               // 控制线程写
public void run() { while (!stop) { doWork(); } }       // 工作线程读，能及时感知
```

**双重检查锁定单例（正确版本）：**

```java
private static volatile Singleton instance; // 禁止重排序 + 保证可见性
public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton();
        }
    }
    return instance;
}
```

**一次性发布配置对象：** 管理线程通过volatile字段发布完整初始化好的对象，工作线程读取该volatile字段即可看到完整状态，无需额外同步。

### 3.6 ReentrantLock

#### 3.6.1 与synchronized对比

| 特性 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 实现层面 | JVM关键字 | Java API |
| 公平性 | 仅非公平 | 支持公平/非公平 |
| 可中断获取 | 不支持 | `lockInterruptibly()` |
| 超时获取 | 不支持 | `tryLock(timeout)` |
| 条件变量 | 单一（wait/notify） | 支持多个Condition |
| 释放方式 | JVM自动 | 必须手动在finally中释放 |

#### 3.6.2 AQS框架

AQS（AbstractQueuedSynchronizer）是ReentrantLock、Semaphore、CountDownLatch、ReadWriteLock等的公共基础。核心结构：

- **`state`**（volatile int）：同步状态，ReentrantLock中0表示未锁定，>0表示锁定（重入次数）
- **CLH等待队列**：双向链表，每个Node包含线程引用、等待状态（waitStatus）、前驱/后继指针
- **`exclusiveOwnerThread`**：当前持有独占锁的线程

```
head ──> Node(T1) ──> Node(T2) ──> ... ──> Node(Tn) <── tail
（哨兵节点，不代表任何等待线程）
```

Node的`waitStatus`取值含义：

| 取值 | 名称 | 含义 |
|---|---|---|
| 0 | 初始值 | 新建节点的默认状态 |
| -1 | SIGNAL | 释放锁时需要唤醒后继节点 |
| 1 | CANCELLED | 因超时或中断而取消等待 |
| -2 | CONDITION | 节点处于Condition等待队列中 |
| -3 | PROPAGATE | 共享模式下释放操作需向后传播 |

**获取锁流程（非公平锁）：**

```java
final void lock() {
    if (compareAndSetState(0, 1))            // 先尝试插队CAS
        setExclusiveOwnerThread(Thread.currentThread());
    else
        acquire(1);                           // CAS失败，走AQS标准流程：
                                              // tryAcquire再试一次 → 失败则入队 → 自旋/阻塞等待
}
```

线程入队后，只有前驱是head节点时才会尝试获取锁；否则确保前驱的waitStatus为SIGNAL后调用`LockSupport.park()`阻塞，等待前驱释放锁时唤醒。

#### 3.6.3 公平锁与非公平锁

公平锁严格按FIFO顺序从CLH队列中唤醒线程获取锁，不会有线程饥饿，但吞吐量较低（每次释放都要唤醒并切换线程，切换期间锁处于空闲浪费状态）。非公平锁允许新来的线程直接CAS抢锁，减少了线程切换、提升吞吐量，但可能导致队列中的线程长时间得不到锁。

```java
ReentrantLock fairLock = new ReentrantLock(true);    // 公平锁
ReentrantLock lock = new ReentrantLock();            // 非公平锁（默认）
```

#### 3.6.4 Condition条件变量

一个Lock可以创建多个Condition，各自维护独立的等待队列，比synchronized+wait/notify更精细：

```java
public class BoundedBlockingQueue<T> {
    private final Queue<T> queue = new LinkedList<>();
    private final int capacity;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    public BoundedBlockingQueue(int capacity) { this.capacity = capacity; }

    public void put(T item) throws InterruptedException {
        lock.lock();
        try {
            while (queue.size() == capacity) notFull.await();
            queue.offer(item);
            notEmpty.signal();      // 只唤醒等待"非空"的消费者，而非所有线程
        } finally { lock.unlock(); }
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (queue.isEmpty()) notEmpty.await();
            T item = queue.poll();
            notFull.signal();       // 只唤醒等待"非满"的生产者
            return item;
        } finally { lock.unlock(); }
    }
}
```

#### 3.6.5 tryLock与可中断获取

```java
if (lock.tryLock()) { ... }                                 // 非阻塞尝试
if (lock.tryLock(3, TimeUnit.SECONDS)) { ... }               // 超时尝试
try { lock.lockInterruptibly(); ... }                        // 可响应中断
catch (InterruptedException e) { Thread.currentThread().interrupt(); }
```

### 3.7 线程池（ThreadPoolExecutor）

#### 3.7.1 为什么需要线程池

直接创建线程存在创建/销毁开销大、栈内存占用高（默认约1MB/线程）、缺乏统一管理、响应延迟等问题。线程池通过**线程复用**解决这些问题：预创建一组线程，任务提交后由空闲线程执行，执行完不销毁而是等待下一个任务。

#### 3.7.2 核心参数与提交流程

```java
new ThreadPoolExecutor(corePoolSize, maximumPoolSize, keepAliveTime, unit,
                        workQueue, threadFactory, rejectedExecutionHandler);
```

- **corePoolSize**：核心线程数，默认不会被回收
- **maximumPoolSize**：最大线程数
- **keepAliveTime**：非核心线程空闲存活时间
- **workQueue**：等待队列
- **threadFactory**：线程创建工厂
- **handler**：拒绝策略

**任务提交流程：**

```
提交任务 execute(task)
   │
   ▼
当前线程数 < corePoolSize？ ──是──> 创建核心线程执行任务
   │否
   ▼
尝试放入workQueue ──成功──> 等待空闲线程取出执行
   │失败（队列已满）
   ▼
当前线程数 < maximumPoolSize？ ──是──> 创建非核心线程执行任务
   │否
   ▼
执行拒绝策略 handler.rejectedExecution(task, this)
```

#### 3.7.3 工作队列类型

- **LinkedBlockingQueue**：默认容量Integer.MAX_VALUE的链表队列，若不限容量会使maximumPoolSize形同虚设
- **ArrayBlockingQueue**：必须指定容量的数组队列
- **SynchronousQueue**：容量为0，直接将任务移交给空闲线程，`Executors.newCachedThreadPool()`使用它
- **PriorityBlockingQueue**：按优先级排序的无界队列

#### 3.7.4 拒绝策略

```java
new ThreadPoolExecutor.AbortPolicy();         // 默认，抛出RejectedExecutionException
new ThreadPoolExecutor.CallerRunsPolicy();    // 由提交任务的线程自己执行，间接限流
new ThreadPoolExecutor.DiscardPolicy();       // 静默丢弃
new ThreadPoolExecutor.DiscardOldestPolicy(); // 丢弃队列最老任务，重新提交当前任务
```

生产环境建议自定义拒绝策略，在任务被拒绝时记录日志、持久化补偿、触发告警，而不是简单丢弃或抛异常了事：

```java
RejectedExecutionHandler customHandler = (task, executor) -> {
    log.error("Task rejected: pool={}, active={}, queue={}",
            executor.getPoolSize(), executor.getActiveCount(), executor.getQueue().size());
    taskPersistenceService.save(task);   // 持久化到存储，后续补偿执行
    alertService.sendAlert("线程池任务被拒绝，请关注");
};
```

#### 3.7.5 线程池大小设定

- **CPU密集型任务：** 线程数 = CPU核心数 + 1
- **IO密集型任务：** 线程数 = CPU核心数 × (1 + 等待时间/计算时间)，粗略估算可取CPU核心数 × 2

```java
int cpuCores = Runtime.getRuntime().availableProcessors();
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    cpuCores, cpuCores * 2, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(500),
    new CustomThreadFactory("biz-pool"),
    new ThreadPoolExecutor.CallerRunsPolicy());
pool.allowCoreThreadTimeOut(true);
```

不推荐使用`Executors.newFixedThreadPool()`/`newCachedThreadPool()`等快捷方法，因为它们默认使用无界队列或无限最大线程数，容易在高负载下导致OOM。

### 3.8 并发容器

#### 3.8.1 ConcurrentHashMap

**JDK 7：分段锁（Segment）。** 数组被划分为默认16个Segment，每个Segment继承ReentrantLock，并发度等于Segment个数且创建后不可变，不同Segment间的读写可完全并行。缺点是并发度固定不可调，且Segment本身带来额外的内存开销。

**JDK 8：CAS + synchronized，锁粒度细化到桶。** 目标桶为空时用CAS直接插入（无锁）；目标桶非空时用synchronized锁定桶的头节点（Node或TreeBin），不影响其他桶的并发操作；链表长度达到8且数组长度达到64时转为红黑树，提升查找效率。这种设计使得锁粒度不再受限于固定的Segment数量，而是随数组容量自适应变化，并发度更高。

```java
// put()核心逻辑简化
for (Node<K,V>[] tab = table;;) {
    Node<K,V> f; int n, i;
    if (tab == null || (n = tab.length) == 0) {
        tab = initTable();                       // 数组未初始化，先初始化
    } else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
        if (casTabAt(tab, i, null, new Node<>(hash, key, value, null)))
            break;                                // 目标桶为空，CAS直接插入，无锁
    } else if ((f.hash) == MOVED) {
        tab = helpTransfer(tab, f);               // 正在扩容，帮忙迁移数据
    } else {
        synchronized (f) {                        // 锁粒度仅为该桶的头节点 f
            // 链表或红黑树中查找/插入
        }
    }
}
```

#### 3.8.2 CopyOnWriteArrayList

采用**写时复制**：读操作完全无锁，直接读取当前数组引用；写操作加锁后复制一份新数组，在新数组上修改，再用volatile写替换数组引用。

```java
public boolean add(E e) {
    lock.lock();
    try {
        Object[] newElements = Arrays.copyOf(getArray(), getArray().length + 1);
        newElements[newElements.length - 1] = e;
        setArray(newElements);          // volatile写替换引用
        return true;
    } finally { lock.unlock(); }
}
public E get(int index) { return (E) getArray()[index]; }  // 无锁读
```

适合读多写少、可以容忍短暂数据不一致的场景（如配置列表、监听器列表）；不适合写频繁或数据量巨大的场景，因为每次写都要复制整个数组，内存分配和拷贝开销会随数据量线性增长。

#### 3.8.3 BlockingQueue家族

- **ArrayBlockingQueue**：有界数组队列，读写共用一把锁
- **LinkedBlockingQueue**：可选有界的链表队列，读写使用双锁（putLock/takeLock），并发度更高
- **SynchronousQueue**：容量为0，put必须等待对应的take，反之亦然，适合任务直接移交场景
- **PriorityBlockingQueue**：无界优先级堆队列，take总是取出优先级最高的元素

```java
BlockingQueue<String> q = new LinkedBlockingQueue<>(1000);
q.put("task");             // 队列满时阻塞
q.offer("task", 1, TimeUnit.SECONDS); // 超时等待放入
String v = q.take();       // 队列空时阻塞
```

## 4. 异常处理与容错

### 4.1 死锁

死锁产生需同时满足四个必要条件：互斥、请求并保持、不可剥夺、循环等待。

```java
// 经典死锁：T1持有lockA等lockB，T2持有lockB等lockA
Thread t1 = new Thread(() -> {
    synchronized (lockA) { sleep(); synchronized (lockB) { /* ... */ } }
});
Thread t2 = new Thread(() -> {
    synchronized (lockB) { sleep(); synchronized (lockA) { /* ... */ } }
});
```

**预防策略：**

**策略一：固定加锁顺序，破坏循环等待条件。**

所有线程始终按相同顺序获取锁，例如始终先获取lockA再获取lockB，这样就不可能形成循环等待：

```java
// 所有方法都按相同顺序加锁
public void method1() {
    synchronized (lockA) { synchronized (lockB) { /* 业务逻辑 */ } }
}
public void method2() {
    synchronized (lockA) { synchronized (lockB) { /* 业务逻辑 */ } }  // 顺序相同！
}
```

**策略二：tryLock + 超时重试，破坏“请求并保持”条件。**

获取不到第二把锁时主动释放已持有的锁，随机退避后重试：

```java
public void safeMethod() throws InterruptedException {
    while (true) {
        if (lockA.tryLock(100, TimeUnit.MILLISECONDS)) {
            try {
                if (lockB.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try { /* 两把锁都获取成功 */ return; } finally { lockB.unlock(); }
                }
            } finally { lockA.unlock(); }  // lockB获取失败时主动释放lockA
        }
        Thread.sleep(ThreadLocalRandom.current().nextInt(10, 50)); // 随机退避避免活锁
    }
}
```

**检测手段：**

- `jstack <pid>` 会在输出中标注“Found one Java-level deadlock”和死锁链信息
- `jconsole` 图形化工具提供一键死锁检测
- 代码中可用`ThreadMXBean.findDeadlockedThreads()`主动检测：

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads();
if (ids != null) {
    for (long id : ids)
        System.err.println("死锁线程: " + bean.getThreadInfo(id).getThreadName());
}
```

### 4.2 线程饥饿

线程长期无法获得CPU时间或锁资源。常见诱因：公平锁下某线程持锁时间过长、线程优先级设置不当、线程池核心线程数配置过小导致任务长期排队。应避免人为设置极端线程优先级，并通过合理的线程池参数和锁粒度控制来规避。

### 4.3 活锁

线程未被阻塞，却因不断相互谦让而无法推进任务，类似走廊里两人反复朝同一侧让路。解决方案是在冲突后引入**随机退避时间**，打破多个线程同步谦让的节奏：

```java
while (active) {
    if (other.isActive()) {
        Thread.sleep(ThreadLocalRandom.current().nextInt(10, 100)); // 随机退避
        continue;
    }
    doWork();
    active = false;
}
```

## 5. 性能优化

### 5.1 减少锁竞争

**减小锁粒度：** 将一把大锁拆分为多把细粒度锁，让互不相关的操作可以并行执行。典型做法是为不同的共享资源分配独立的锁对象，而不是整个方法共用一把锁：

```java
// 反例：粗粒度锁
public synchronized void process(String key, String val) {
    map.put(key, val);   // 操作1
    counter++;           // 操作2（与操作1无关，但被同一把锁保护）
}

// 正例：细粒度锁
private final Object mapLock = new Object();
private final Object counterLock = new Object();
public void process(String key, String val) {
    synchronized (mapLock)     { map.put(key, val); }
    synchronized (counterLock) { counter++; }
}
```

**缩短锁持有时间：** 把数据库查询、网络调用、日志记录等耗时操作移出临界区，临界区内只保留真正需要同步的共享状态更新：

```java
public void goodMethod() {
    String data = queryFromDatabase();        // 锁外执行耗时操作
    synchronized (lock) { updateSharedState(data); }  // 只在更新共享状态时加锁
    sendNotification(data);                   // 锁外执行通知
}
```

**读写锁分离：** 读多写少场景使用`ReentrantReadWriteLock`，允许多个读线程并行，仅在写时独占：

```java
ReadWriteLock rwLock = new ReentrantReadWriteLock();
public V get(K key) {
    rwLock.readLock().lock();
    try { return cache.get(key); } finally { rwLock.readLock().unlock(); }
}
public void put(K key, V value) {
    rwLock.writeLock().lock();
    try { cache.put(key, value); } finally { rwLock.writeLock().unlock(); }
}
```

需要注意的是ReentrantReadWriteLock不支持从读锁直接升级为写锁（会导致死锁），只能先释放读锁再申请写锁；但支持写锁降级为读锁（持有写锁时再获取读锁，再释放写锁），从而安全地在更新后继续读取而不被其他写线程插入。

### 5.2 无锁算法

**LongAdder优于AtomicLong的高竞争场景：** AtomicLong所有线程竞争同一个变量的CAS，高并发下失败重试频繁；LongAdder内部维护`base`和`Cell[]`数组，将竞争分散到不同Cell上，最终汇总求和，显著降低CAS冲突概率。

```java
LongAdder counter = new LongAdder();
counter.increment();      // 高并发下性能优于 AtomicLong.incrementAndGet()
long total = counter.sum();
```

**无锁队列：** `ConcurrentLinkedQueue`基于Michael-Scott算法，通过CAS实现入队/出队，避免加锁开销，适合高并发生产消费场景。

### 5.3 ThreadLocal线程局部变量

为每个线程提供独立变量副本，避免共享变量的同步开销，典型场景是包裹非线程安全的工具类（如`SimpleDateFormat`）或传递请求上下文（用户信息、TraceId）：

```java
private static final ThreadLocal<SimpleDateFormat> SDF =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));
```

**内存泄漏风险：** `ThreadLocalMap`的Entry继承`WeakReference<ThreadLocal<?>>`，key是弱引用会被GC回收，但value是强引用不会被自动回收。在线程池场景下线程长期存活，若不手动清理，会造成value对象持续累积的内存泄漏。因此**使用完毕后务必调用`remove()`**：

```java
try {
    RequestContext.init(userId, traceId);
    // 业务处理
} finally {
    RequestContext.clear(); // 对应 ThreadLocal.remove()，防止内存泄漏
}
```

## 6. 最佳实践与总结

### 6.1 编码规范要点

- 锁必须在`finally`块中释放；`wait()`必须放在`while`循环中判断条件，防止虚假唤醒。
- 不要在持锁代码块中调用不可控的外部回调，避免嵌套锁导致死锁。
- 优先使用JDK提供的高层并发工具（并发容器、线程池、原子类、CountDownLatch/Semaphore等），而非手写wait/notify。
- 线程池必须手动创建并显式设置所有参数，避免使用`Executors`快捷方法造成的无界队列/无限线程数风险；关闭时使用`shutdown()`+`awaitTermination()`+必要时`shutdownNow()`的组合实现优雅停机。
- 为线程池中的线程设置有意义的名字，并妥善捕获、记录任务执行中的异常，防止异常被静默吞掉。

### 6.2 常见陷阱

**陷阱1：锁定自动装箱对象。** 对`Integer`等使用值缓存的包装类型加锁，值变化时自动装箱会产生新对象，导致锁对象本身发生变化：

```java
// 危险：每次count++后自动装箱产生新Integer对象，锁不住！
private Integer count = 0;
public void bad()  { synchronized (count) { count++; } }

// 正确：使用专门的不可变锁对象
private final Object lock = new Object();
private int count = 0;
public void good() { synchronized (lock) { count++; } }
```

**陷阱2：误以为volatile保证原子性。** `volatile int count; count++;`在多线程下仍然不安全，应改用`AtomicInteger`。

**陷阱3：锁对象逸出。** 不要把内部锁对象通过getter暴露给外部代码，外部可能用该锁做不当操作，导致死锁。

**陷阱4：this逃逸。** 不要在构造函数中启动引用了`this`的线程，因为此时对象可能还未完全初始化。应通过静态工厂方法在对象构造完成后再启动线程：

```java
// 反例
public class Foo {
    public Foo() {
        new Thread(() -> System.out.println(this.value)).start();
        this.value = 42;  // 新线程可能在这行执行前就读取了value
    }
}
// 正例：工厂方法
public static Foo create() {
    Foo f = new Foo(42);  // 先完成构造
    f.startThread();      // 再启动线程
    return f;
}
```

### 6.3 总结

并发编程的本质是解决**分工、同步、互斥**三大核心问题。理解并发编程需要从硬件架构出发：CPU缓存带来可见性问题，线程切换带来原子性问题，指令重排序带来有序性问题。Java通过JMM及Happens-Before规则规范了可见性和有序性，通过synchronized/Lock/CAS/原子类解决了原子性问题，并在此基础上构建了AQS框架，进而衍生出ReentrantLock、Semaphore、CountDownLatch等高层工具，以及ConcurrentHashMap、CopyOnWriteArrayList等并发容器。

并发编程没有银弹。工程实践中应先分析业务的并发特征（读多写少、计算密集、IO密集），再选择匹配的工具：低竞争场景优先CAS和无锁结构，高竞争写场景考虑分段/读写锁分离，任务调度统一通过规范配置的线程池执行，并通过充分的测试与压测验证正确性与性能，才能真正发挥并发编程带来的吞吐提升，同时规避死锁、饥饿、活锁等隐患。
