# 目的

## 为了在测试每个被@Test注解修饰的方法前后，记录测试的日志，最后统一生成一个测试报告，上报到远程服务系统（这个就是子类powerbankTestListener主要扩展的功能）

### 架构

- PowerbankTestListener 继承自 JsonReportNG，而 JsonReportNG 本身又是public class JsonReportNG extends TestListenerAdapter implements IAnnotationTransformer, IReporter ，也就是说整条链路是

```
TestListenerAdapter
TestNG 官方提供的监听器适配类
封装了 onTestStart、onTestSuccess、onTestFailure 等回调入口

IAnnotationTransformer
用来在测试执行前动态修改 @Test 注解配置
这里主要用来自动设置重试器 RetryAnalyzer


IReporter
在整个 suite 结束后生成测试报告


JsonReportNG
mario 框架自己的测试报告/失败信息/trace 信息整合器


PowerbankTestListener
在 mario 的公共能力上，再加上 powerbank 业务自己的规则和上传动作

```



- 存在的目的

```
测试开始前做业务校验
这个 case 是否应该执行
是否满足 scope/case 级别筛选条件
当前泳道环境是否允许执行


测试结果落库/上报

整个执行批次结束后，也要上传汇总结果、bug 信息、报告产物

```

## 先补一条总主线：@Test、TestNG、监听器到底怎么串起来


- surefire如何拉起TestNG

```
这不是简单的函数调用，而是一次“跨进程”的精密协作。我们可以分三个层面来拆解这个过程：

1. 自动发现：谁来干活？
当你运行 mvn test 时，Surefire 插件会扫描你项目的类路径（Classpath）。

扫描依赖：如果 Surefire 在你的 pom.xml 依赖里发现了 org.testng:testng，它会意识到：“哦，这是一份 TestNG 的试卷，我得找个懂 TestNG 的人来改卷。”

加载 Provider：Surefire 内部有一套适配器叫 Provider。对于 TestNG，对应的组件叫 surefire-testng。Surefire 会动态加载这个 Provider。

2. 启动进程：在哪里干活？
Surefire 默认会开启一个全新的 JVM 进程（也就是所谓的 Fork 模式）来运行测试。

为什么要 Fork？ 这样测试代码崩溃了、内存溢出了，或者改了系统属性，都不会影响到 Maven 主进程。

命令行拼接：Surefire 会拼接一条长长的 java 命令，把所有的测试依赖、TestNG 核心库、以及 surefire-testng 适配器都塞进 -classpath 里，然后启动这个新进程。

3. 握手与执行：怎么交接工作？
新进程启动后，真正的“交接棒”发生在 surefire-testng 这个适配器里：

参数传递：Surefire 会把你在 pom.xml 里配置的 <suiteXmlFiles>（如 apiTest.xml）路径通过配置文件或系统变量传给 Provider。

实例化 TestNG 核心对象：适配器会执行类似下面的伪代码：

Java

// Surefire Provider 内部逻辑
TestNG testng = new TestNG();
List<String> suites = new ArrayList<>();
suites.add("path/to/apiTest.xml");
testng.setTestSuites(suites); // 告诉 TestNG 该看哪个 XML
调用 testng.run()：一旦调用了这个方法，控制权就正式从 Maven 移交给了 TestNG。

```



- `@Test` 本身只是一个运行时注解，它不会自己执行。
- 真正让它“生效”的是 TestNG：TestNG 启动后通过反射扫描测试类，识别出哪些方法带了 `@Test`，再把这些方法加入执行计划。
- 这个项目里 TestNG 不是手工启动的，而是 `mvn test` 时由 `maven-surefire-plugin` 拉起；`mario-test-parent/pom.xml` 里已经指定了 suite 文件 `src/test/apiTest.xml`。
- TestNG 读取 `apiTest.xml` 后，会扫描里面配置的包，比如 `http.testsuites`、`pigeon.testsuites`、`thrift.testsuites`，然后找到对应测试类和测试方法。
- 找到测试方法后，TestNG 会先加载监听器。这个项目不是用 `@Listeners`，而是通过 `META-INF/services/org.testng.ITestNGListener` 做 SPI 自动注册，所以 `MarioTestClassListener`、`MarioTestListener`、`JsonReportNG` 会在启动阶段被 TestNG 自动装配进去。
- `JsonReportNG` 还实现了 `IAnnotationTransformer`，所以它能在测试真正执行前动态修改 `@Test` 的配置，例如自动补上 `retryAnalyzer`。这一步说明：`@Test` 不是扫描完就立刻执行，而是先进入 TestNG 的测试模型，再允许框架做一次增强。
- 后面 TestNG 才会按生命周期触发各类回调：suite 开始、class 开始、方法调用前、`onTestStart`、测试执行、成功/失败/跳过、suite 结束、`generateReport` 生成最终报告。

可以把完整链路记成一句话：

`mvn test` -> Surefire 启动 TestNG -> 读取 `apiTest.xml` -> 扫描测试包 -> 反射识别 `@Test` -> SPI 加载监听器 -> `IAnnotationTransformer` 动态增强 -> 执行测试 -> 回调各类 Listener -> `IReporter` 汇总生成报告。

所以要分清两件事：

- `@Test` 决定“这是不是测试方法”。
- TestNG 决定“什么时候执行、执行前后回调谁、最后怎么汇总”。

监听器不是让 `@Test` 生效的根因，监听器只是挂在 TestNG 生命周期里的扩展点；真正负责解释和触发 `@Test` 的，是 TestNG 本身。

```
public void transform(ITestAnnotation annotation, Class testClass, Constructor testConstructor, Method testMethod) {
    if (ConfigManage.isFstRunTest()) {
        return;
    }
    Object retryAnalyzer = annotation.getRetryAnalyzer();
    try {
        Method retryAnalyzerMethod = Test.class.getDeclaredMethod("retryAnalyzer");
        if (retryAnalyzerMethod != null) {
            if (retryAnalyzer == null || !(retryAnalyzer instanceof TestngRetry) && retryAnalyzerMethod.getDefaultValue().equals(retryAnalyzer)) {
                annotation.setRetryAnalyzer(TestngRetry.class);
            }
        }
    } catch (NoSuchMethodException e) {
        throw new RuntimeException(e);
    }
}

     * TestNG的case最大运行次数，case运行失败后会触发重试
     */
    public static final int MaxRetryCount = getMaxRetryCount();
    /**
     * 记录每个测试数据的剩余重试次数，解决由于数据被修改导致生成新重试类，导致重试最大次数失效
     */
    private static final ConcurrentMap<String, AtomicInteger> retryCountMap = new ConcurrentHashMap<>();

    public TestngRetry() {
        setCount(MaxRetryCount);
    }

    private static int getMaxRetryCount() {
        int maxRetryCount = 0;
        try {
            if (StringUtils.isNotBlank(System.getenv("RETRY_TIME"))) {
                maxRetryCount = Integer.valueOf(System.getenv("RETRY_TIME"));
                if (maxRetryCount < 1) {
                    maxRetryCount = 0;
                }
            } else {
                maxRetryCount = Integer.valueOf(ConfigManage.getValue("RETRY_TIME"));
            }
        } catch (Exception e) {
            maxRetryCount = 0;
        }
        return maxRetryCount;
    }

    @Override
    public boolean retryMethod(ITestResult result) {
        boolean isSucceed = result.isSuccess();
        if (!isSucceed) {
            String retryKey = String.format("%s-%s-%s-%s", result.getTestClass().getName(), result.getMethod().getMethodName()
                    , ((TestResult) result).getParameterIndex(), result.getTestContext().getName());
            AtomicInteger retriesLeft = retryCountMap.getOrDefault(retryKey, new AtomicInteger(MaxRetryCount));
            if (retriesLeft.getAndDecrement() > 0) {
                result.setAttribute("RETRY", new Integer(MaxRetryCount - retriesLeft.get()-1)); // 记录重试次数，不能删除，有业务使用
                retryCountMap.put(retryKey, retriesLeft);
                return true;
            }
        }
        return false;
    }

    public void resetRetryCount() {
        setCount(getMaxRetryCount());
    }
}
```

## 完整调用链逐步详解（结合源码，一步不跳）

这一节的目标是：从 `mvn test` 敲下回车的那一刻开始，到最终测试报告上传到远程平台，把每一个方法调用、每一次回调、每一行关键代码，按照真实的时间顺序完整串起来，不跳任何一步。

---

### 第一阶段：Maven 拉起 TestNG（进程启动）

**触发点：** 你在命令行执行 `mvn test`。

Maven 主进程启动后，`maven-surefire-plugin` 接管测试执行。Surefire 扫描项目依赖，发现 `org.testng:testng` 存在，于是加载 `surefire-testng` 这个适配器 Provider。

Surefire 默认开启 Fork 模式，**新起一个独立的 JVM 子进程**来跑测试。这样做的原因是隔离：测试代码崩溃、OOM、修改系统属性，都不会污染 Maven 主进程。

新 JVM 进程启动后，`surefire-testng` 适配器在内部执行如下逻辑（伪代码）：

```java
// surefire-testng 适配器内部
TestNG testng = new TestNG();
testng.setTestSuites(Arrays.asList("src/test/apiTest.xml")); // 从 pom.xml 配置读取
testng.run(); // 控制权正式移交给 TestNG
```

`testng.run()` 一旦被调用，后续所有事情都由 TestNG 引擎驱动，Surefire 只负责等待子进程结束并收集退出码。

---

### 第二阶段：TestNG 读取 XML，扫描测试类

**触发点：** `testng.run()` 内部。

TestNG 解析 `apiTest.xml`，找到里面配置的包路径，例如：

```xml
<packages>
    <package name="thrift.testsuites"/>
    <package name="pigeon.testsuites"/>
</packages>
```

TestNG 用类加载器扫描这些包下的所有 `.class` 文件，通过反射找到带有 `@Test` 注解的方法，把它们登记进内部的"测试方法元数据表"（`ITestNGMethod` 列表）。

注意：**`@Test` 本身只是一个运行时注解，它不会自己执行**。它只是一个标记，告诉 TestNG "这个方法是测试方法"。真正让它生效的是 TestNG 的反射扫描。

---

### 第三阶段：SPI 加载监听器，自动注册

**触发点：** TestNG 初始化阶段，扫描 classpath。

TestNG 在启动时会调用 Java 标准的 `ServiceLoader` 机制，扫描 classpath 下所有 `META-INF/services/org.testng.ITestNGListener` 文件。

这个项目在 `demo/src/test/resources/META-INF/services/org.testng.ITestNGListener` 文件里写了：

```
com.sankuai.toolchain.mario.listener.MarioTestClassListener
com.sankuai.toolchain.mario.listener.MarioTestListener
com.sankuai.toolchain.mario.listener.JsonReportNG
org.uncommons.reportng.HTMLReporter
org.uncommons.reportng.JUnitXMLReporter
```

TestNG 内部执行的逻辑等价于：

```java
ServiceLoader<ITestNGListener> loader = ServiceLoader.load(ITestNGListener.class);
for (ITestNGListener listener : loader) {
    testng.addListener(listener); // 逐个注册进 TestNG 引擎
}
```

这样，`MarioTestClassListener`、`MarioTestListener`、`JsonReportNG` 三个监听器就被自动装配进去了，**完全不需要在 testng.xml 里手动配置 `<listeners>` 标签**，这就是 SPI 机制的价值：框架使用者零配置，框架自动发现并注册。

同理，`META-INF/services/com.sankuai.toolchain.mario.report.IReport` 文件里注册了自定义上报实现，这是第二层 SPI，后面 `ReportFactory` 会用到，先记住这里。

---

### 第四阶段：`IAnnotationTransformer.transform()` — 动态增强 @Test 注解

**触发点：** TestNG 扫描完测试方法、构建测试方法元数据时，对每一个 `@Test` 方法触发一次。**早于任何测试方法的执行，也早于 `onTestStart`。**

**调用者：** TestNG 引擎内部。**被调用者：** `JsonReportNG.transform()`（第 323 行）。

```java
// JsonReportNG.java 第 323-348 行
@Override
public void transform(ITestAnnotation annotation, Class testClass,
                      Constructor testConstructor, Method testMethod) {
    // FST 平台触发的执行不加重试，直接返回
    if (ConfigManage.isFstRunTest()) {
        return;
    }
    // 拿到这个 @Test 方法当前配置的 retryAnalyzer
    Object retryAnalyzer = annotation.getRetryAnalyzer();
    try {
        // 用反射拿到 @Test 注解里 retryAnalyzer 属性的默认值（默认是 Class.class，即没配置）
        Method retryAnalyzerMethod = Test.class.getDeclaredMethod("retryAnalyzer");
        if (retryAnalyzerMethod != null) {
            // 如果没有配置自定义重试器，或者配置的不是 TestngRetry
            if (retryAnalyzer == null
                    || !(retryAnalyzer instanceof TestngRetry)
                    && retryAnalyzerMethod.getDefaultValue().equals(retryAnalyzer)) {
                // 动态把 TestngRetry.class 注入进去
                annotation.setRetryAnalyzer(TestngRetry.class);
            }
        }
    } catch (NoSuchMethodException e) {
        throw new RuntimeException(e);
    }
}
```

这一步的效果是：**所有 `@Test` 方法，在真正执行之前，都被悄悄挂上了 `TestngRetry` 重试器**，测试方法自己完全感知不到这件事。

`TestngRetry` 的核心逻辑在 `retryMethod()` 里：

```java
// TestngRetry.java
@Override
public boolean retryMethod(ITestResult result) {
    boolean isSucceed = result.isSuccess();
    if (!isSucceed) {
        // retryKey 由 类名 + 方法名 + 参数索引 + 上下文名 拼成，唯一标识一条测试数据
        String retryKey = String.format("%s-%s-%s-%s",
            result.getTestClass().getName(),
            result.getMethod().getMethodName(),
            ((TestResult) result).getParameterIndex(),
            result.getTestContext().getName());

        // 从 ConcurrentHashMap 里取这条数据剩余的重试次数
        AtomicInteger retriesLeft = retryCountMap.getOrDefault(retryKey, new AtomicInteger(MaxRetryCount));
        if (retriesLeft.getAndDecrement() > 0) {
            // 还有重试次数，记录当前是第几次重试，返回 true 告诉 TestNG 重跑
            result.setAttribute("RETRY", MaxRetryCount - retriesLeft.get() - 1);
            retryCountMap.put(retryKey, retriesLeft);
            return true; // TestNG 收到 true，会把这个方法重新加入执行队列
        }
    }
    return false; // 成功了，或者重试次数耗尽，返回 false
}
```

`MaxRetryCount` 从环境变量 `RETRY_TIME` 或配置文件读取，默认为 0（不重试）。用 `ConcurrentHashMap<String, AtomicInteger>` 存每条数据的剩余次数，保证多线程并发执行时计数不乱。

### 第十阶段：测试方法体执行

**触发点：** TestNG 通过反射调用测试方法，DataProvider 已经把参数注入好了。

这一步是你自己写的测试代码执行的地方，例如：

```java
// UserRpcInvokeTest.java

    Integer misId = request.getInteger("misId");
    String response = ThriftProcessor.invoke(misId); // 发起 RPC 调用
    AssertUtil.assertNewJsonEquals(response, expect, JSONCompareMode.STRICT, null, 200);

```

`ThriftProcessor.invoke()` 内部完成服务发现、建连、序列化、发送、等待响应的全过程，最终把 JSON 字符串响应写入 `ResponseRecorder`（ThreadLocal 存储）。`AssertUtil` 做断言，断言结果写入 `AssertRecorder`（也是 ThreadLocal）。

如果断言失败，TestNG 捕获到异常，标记这个 `ITestResult` 为 `FAILURE`，然后询问 `TestngRetry.retryMethod()`：还有重试次数吗？有的话重新执行，没有的话进入失败回调。

### 第十一阶段：成功/失败/跳过回调 — 采集现场，单条上报

#### 成功时：`onTestSuccess()`

**调用者：** TestNG 引擎。**被调用者：** `JsonReportNG.onTestSuccess()`（第 229 行）。

```java

    setAssertInfo(tr);       // 把 AssertRecorder 里的断言信息、errorCode 写入 ITestResult
```

```java
    String caseName = tr.getTestClass().getRealClass().getName();
```

```java
    // 从 LogRecorder（ThreadLocal）取出这条用例执行期间记录的所有错误日志
```

```java
public void generateReport(List<XmlSuite> list, List<ISuite> suites, String outputDirectory) {
    marioSuiteResult = new SuiteResult(); // 创建最终的汇总结果对象

    for (ISuite suite : suites) {
        Map<String, ISuiteResult> suiteResults = suite.getResults();
        for (ISuiteResult suiteResult : suiteResults.values()) {
            ITestContext testContext = suiteResult.getTestContext();

            // 检查是否是重跑失败用例的 suite（名字以 "Failed suite" 开头）
            if (suite.getName().startsWith("Failed suite")) {
                marioSuiteResult.setRetryFailed(true);
            }

            // 收集配置方法（@BeforeClass/@AfterClass）的失败/跳过情况

            for (ITestResult r : testContext.getSkippedConfigurations().getAllResults()) {
                failErrorConfig.add(r);
            }
            for (ITestResult r : testContext.getFailedConfigurations().getAllResults()) {
                failErrorConfig.add(r);
            }

            // 收集 @BeforeMethod/@AfterMethod 的执行结果，用于后续关联到具体用例
            for (ITestResult tr : suiteResult.getTestContext().getPassedConfigurations().getAllResults()) {
                if (tr.getMethod().isBeforeMethodConfiguration()) {
                    befores.put(tr.getInstance(), tr); // key=测试类实例，value=before结果
                }
                if (tr.getMethod().isAfterMethodConfiguration()) {
                    afters.put(tr.getInstance(), tr);
                }
            }

            // 更新整体开始/结束时间（取所有 suite 的最早开始和最晚结束）
            if (startTime > testContext.getStartDate().getTime()) {
                startTime = testContext.getStartDate().getTime();
            }
            if (endTime < testContext.getEndDate().getTime()) {
                endTime = testContext.getEndDate().getTime();
            }

            addCaseResult(testContext.getPassedTests(), xmlName, team_id);   // 成功用例
            addCaseResult(testContext.getFailedTests(), xmlName, team_id);   // 失败用例
            addCaseResult(testContext.getSkippedTests(), failErrorConfig, xmlName, team_id); // 跳过用例

            // 按 P1/P2/P3/NA 分组统计通过/失败/跳过/重试数量
            addGroupResult(suiteResultTmp.getDetail().getPasses(), groupsPassCount, groups);
            addGroupResult(suiteResultTmp.getDetail().getFailures(), groupsFailureCount, groups);
            addGroupResult(suiteResultTmp.getDetail().getSkips(), groupsSkipCount, groups);
            addGroupResult(suiteResultTmp.getDetail().getRetries(), groupsRetryCount, groups);
```

### 第十七阶段：`ReportFactory.process()` — 两层 SPI 驱动所有上报器

**调用者：** `JsonReportNG.generateReport()`（第 115 行）。**被调用者：** `ReportFactory.process()`（第 31 行）。

```java
// ReportFactory.java 第 22-36 行
public class ReportFactory {
    // 第二层 SPI：加载用户在 META-INF/services/com.sankuai.toolchain.mario.report.IReport 里注册的自定义上报器
    private static ServiceLoader<IReport> reports = ServiceLoader.load(IReport.class);

    // 内置上报器列表（硬编码，顺序固定）
    private static List<IReport> defaults = Arrays.asList(
        new JSONFileReport(),  // 生成本地 JSON 格式报告文件
        new HtmlReport(),      // 生成本地 HTML 格式报告文件
        new FuzzingReport(),   // Fuzzing 测试专用报告
        new FocusReport(),     // 上报到 Focus 平台（美团内部测试管理平台）
        new EagleReport()      // 上报到 Eagle 平台（ES 存储，必须放最后，因为会清理部分字段）
    );

    public static void process(String filePath, SuiteResult suiteResult) {
        // 先做内存清理：如果 SuiteResult 超过 50MB，按优先级裁剪字段，防止 OOM
        cleanupReportContent(suiteResult);

        // 依次执行所有内置上报器
        defaults.forEach(iReport -> process(iReport, filePath, suiteResult));

        // 依次执行所有通过 SPI 注册的自定义上报器
        reports.forEach(report -> process(report, filePath, suiteResult));
    }

    private static void process(IReport iReport, String filePath, SuiteResult suiteResult) {
        // 每个上报器都有一个 condition() 方法，只有条件满足才执行
        // 默认条件是 ConfigManage.getValue("STATS") == true
        if (iReport.condition()) {
            // 关键：每个上报器拿到的是 SuiteResult 的深拷贝，互相隔离
            // 防止一个上报器修改了数据（如 EagleReport 会清空某些字段）影响后续上报器
            SuiteResult cloneResult = JSONObject.parseObject(suiteResult.toString(), SuiteResult.class);
            iReport.process(filePath, cloneResult);
        }
    }
}
```

```java
}
```

### 第十八阶段：各上报器执行 — 以 `EagleReport` 为例

```java
// EagleReport.java 第 24-72 行
@Override
public void process(String filePath, SuiteResult suiteResult) {
    // 第一步：只保留 P1/P2/P3/NA 四个分组，过滤掉其他自定义分组
    Map<String, GroupResult> result = suiteResult.getSummary().getGroupsResults();
    List<String> removeKeys = new ArrayList();
    result.keySet().forEach(k -> {
        if (!k.equalsIgnoreCase("P1") && !k.equalsIgnoreCase("P2")
                && !k.equalsIgnoreCase("P3") && !k.equalsIgnoreCase("NA")) {
            removeKeys.add(k);
        }
    });
    removeKeys.forEach(key -> result.remove(key));

    // 第二步：清理不需要上传到 Eagle（ES）的字段，减小数据体积
    // 成功/跳过/失败/重试用例都要清理：parameters、consoleLogs、assertInfo、responseMaps 等
    for (CaseResult caseResult : suiteResult.getDetail().getPasses()) {
        caseResult.setParameters(null);
        caseResult.setConsoleLogs(null);
        clearWoodPeckerData(caseResult); // 清空 assertInfo、responseMaps、errorLog、errorCodes
    }
    // ... 对 skips、failures、retries 做同样处理 ...

    // 第三步：把所有用例详情（通过+失败+跳过+重试）合并成一个列表，上传到 Eagle
    List<CaseResult> allDetails = new ArrayList<>();
    allDetails.addAll(suiteResult.getDetail().getPasses());
    allDetails.addAll(suiteResult.getDetail().getFailures());
    allDetails.addAll(suiteResult.getDetail().getSkips());
    allDetails.addAll(suiteResult.getDetail().getRetries());
    EagleUtil.uploadTestDetails(JSONArray.parseArray(JSONObject.toJSONString(allDetails)));
    // EagleUtil 内部发 HTTP POST 请求到 Eagle 平台的 ES 写入接口

    // 第四步：清空 detail（用例详情已经单独上传了，汇总结果里不需要再带）
    suiteResult.setDetail(null);
    suiteResult.getBaseInfo().setPipelineInfo(null);
    suiteResult.getBaseInfo().setConfig(null);

    // 第五步：上传汇总结果（通过率、分组统计、执行时间等）
    EagleUtil.uploadTestResult(suiteResult.toString());
}
```

`EagleReport` 必须放在 `defaults` 列表最后的原因就在这里：它会把 `detail` 置为 `null`，如果放在前面，后面的上报器就拿不到用例详情了。

### 完整调用链时序总结

把上面十八个阶段压缩成一张时序表，方便记忆和讲述：

```
mvn test
  │
  ├─[Surefire] Fork 新 JVM，实例化 TestNG，调用 testng.run()
  │
  ├─[TestNG] 解析 apiTest.xml，反射扫描 @Test 方法
  │
  ├─[TestNG] ServiceLoader 扫描 META-INF/services/org.testng.ITestNGListener
  │           → 注册 MarioTestClassListener、MarioTestListener、JsonReportNG
  │
  ├─[TestNG] 对每个 @Test 方法调用 IAnnotationTransformer.transform()
  │           → JsonReportNG.transform() 动态注入 TestngRetry 重试器
  │
  ├─[TestNG] Suite 开始
  │           → MarioTestClassListener.onStart(ISuite)：打印机器信息，配置日志开关
  │
  ├─[TestNG] <test> 上下文开始
  │           → MarioTestListener.onStart(ITestContext)：（泳道注入逻辑已下线）
  │
  ├─[TestNG] 测试类开始（每个类一次）
  │           → MarioTestClassListener.onBeforeClass()
  │                 → ThriftProcessor.initRPCService()：初始化字段注入的 RPC 代理
  │                 → MtraceUtil.initTrace()：初始化链路追踪
  │
  │  ┌─── 对每条测试数据循环 ───────────────────────────────────────────────┐
  │  │                                                                      │
  │  ├─[TestNG] 方法调用前                                                  │
  │  │           → MarioTestClassListener.beforeInvocation()               │
  │  │                 → MtraceUtil.initTrace()：生成新 traceId             │
  │  │                 → log.info("start ...")                              │
  │  │                                                                      │
  │  ├─[TestNG] 测试方法开始                                                │
  │  │           → MarioTestListener.onTestStart()                         │
  │  │                 → Tracer.putContext(MARIO_AUTOTEST_FLAG, ...)        │
  │  │                                                                      │
  │  ├─[TestNG] 执行测试方法体（你写的代码）                                 │
  │  │           → ThriftProcessor.invoke() → RPC → ResponseRecorder       │
  │  │           → AssertUtil.assertXxx() → AssertRecorder                 │
  │  │                                                                      │
  │  ├─[TestNG] 测试方法结束（成功/失败/跳过）                               │
  │  │           → JsonReportNG.onTestSuccess/Failure/Skipped()            │
  │  │                 → setMarioDebugInfo()：写入 traceId、Mtrace 链路     │
  │  │                 → setAssertInfo()：写入断言信息、errorCode           │
  │  │                 → setErrorMessage()（失败/跳过）：写入 errorLog、响应 │
  │  │                 → clearRecorder()：清空四个 ThreadLocal              │
  │  │                                                                      │
  │  ├─[TestNG] 方法调用后                                                  │
  │  │           → MarioTestClassListener.afterInvocation()                │
  │  │                 → log.info("end ...")                                │
  │  │                                                                      │
  │  └──────────────────────────────────────────────────────────────────────┘
  │
  ├─[TestNG] 测试类结束（每个类一次）
  │           → MarioTestClassListener.onAfterClass()
  │                 → Tracer.clearContext()：清空 Mtrace 上下文
  │
  ├─[TestNG] <test> 上下文结束
  │           → MarioTestListener.onFinish(ITestContext)
  │                 → ThriftProcessor.destroy()：销毁 Netty 连接池
  │
  ├─[TestNG] Suite 结束
  │           → MarioTestClassListener.onFinish(ISuite)
  │                 → MtraceUtil.uploadTrace()：批量上传链路数据
  │
  └─[TestNG] 生成报告
              → JsonReportNG.generateReport()
                    → 遍历所有 ISuite/ITestContext，把 ITestResult 转成 CaseResult
                    → 填充 SuiteResult（汇总统计、分组统计、时间信息）
                    → setRaptorInfoDetail()：查询 Raptor 监控数据（可选）
                    → ReportFactory.process(outputDirectory, suiteResult)
                          → cleanupReportContent()：超 50MB 时裁剪字段防 OOM
                          → JSONFileReport.process()：生成本地 JSON 报告
                          → HtmlReport.process()：生成本地 HTML 报告
                          → FocusReport.process()：上报到 Focus 平台
                          → EagleReport.process()：上传用例详情 + 汇总结果到 Eagle/ES

```

整条链路的核心设计思想是**分层解耦**：TestNG 只负责驱动测试执行，监听器只负责在生命周期节点做扩展，上报器只负责把结果送到各个平台。每一层都通过接口（`ITestListener`、`IReporter`、`IReport`）和 SPI 机制解耦，框架使用者可以在任意一层插入自己的逻辑，而不需要修改框架本身的代码。
