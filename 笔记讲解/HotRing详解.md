## 1. 背景：为什么需要 HotRing？

### 1.1 内存 KVS 的广泛应用

内存键值存储（In-Memory Key-Value Store，KVS）是现代互联网基础设施的核心组件，Memcached、Redis 等系统被 Facebook、Amazon、Twitter、LinkedIn 等公司大规模部署，每秒需要处理数十亿次请求。

KVS 的核心作用是**将频繁访问的热点数据缓存在内存中**，以解决磁盘存储或分布式系统中的热点访问瓶颈。

### 1.2 被忽视的"内部热点"问题

人们通常关注集群层面的热点（通过一致性哈希、数据迁移、前端缓存等手段解决），却忽视了一个更基础的问题：**内存 KVS 自身内部的热点问题**。

论文作者从阿里巴巴生产环境中收集了真实访问分布数据，发现：

- **日常场景**：50% 的访问集中在 1% 的数据上
- **极端场景（如大促）**：90% 的访问集中在 1% 的数据上

这种极度倾斜的访问模式在互联网时代愈发普遍，背后原因有两个：

1. **用户规模爆炸**：一个实时事件（线上促销、突发新闻）能在短时间内吸引数十亿次访问集中于少量条目
2. **系统复杂性**：软件 bug 或配置失误可能导致某个条目被不可预测地反复访问

### 1.3 现有方案的局限性

面对内部热点，现有方案的效果都很有限：

- **CPU Cache**：可以加速热点数据块的访问，但容量通常只有约 32MB，而内存往往超过 256GB，可缓存比例仅约 **0.012%**，远低于实际热点比例
- **Rehash 扩容**：通过扩大哈希表来缩短冲突链，但代价极高——每次 rehash 需要额外两倍内存，且收益递减

## 2. 哈希冲突的传统解法

理解 HotRing 之前，需要先了解哈希冲突的两种经典解决方案。

### 2.1 开放地址法（Open Addressing）

将冲突的 item 放在哈希表**内部**的其他空位，常见探测方式有：

- **线性探测**：放到相邻的空位
- **平方探测**：按 1、4、9、16 的间隔探测
- **二次哈希**：用另一个哈希函数计算新位置

**缺点**：负载因子高时，探测路径变长，性能急剧下降；需要预留大量空间。

### 2.2 链表法（Collision Chain）

将冲突的 item 存储在哈希表**外部**，每个哈希桶保存一个指向链表头部的指针，查找时顺序遍历链表。

```
哈希表
┌─────┐
│ 桶0 │──→ [Item A] → [Item B] → [Item C] → NULL
├─────┤
│ 桶1 │──→ [Item D] → NULL
├─────┤
│ 桶2 │──→ [Item E] → [Item F] → NULL
└─────┘
```

**优点**：允许 item 数量超过哈希表大小，负载因子增长时性能线性下降（而非急剧下降）。

**热点问题**：热点 item 可能随机分布在链表的任意位置。如果热点 item 恰好在链尾，每次访问都需要遍历整条链，代价极高。

## 3. 热点问题的量化分析

### 3.1 传统链式哈希的期望访问代价

设哈希表有 `B` 个桶，共存储 `N` 个 item，则每个桶的平均链长为：

```
L = N / B
```

在链式结构中检索一个 item 的期望内存访问次数为：

```
E_chain = 1 + L/2 = 1 + N/(2B)
```

其中前导的 `1` 是对哈希表本身的一次访问，`L/2` 是平均遍历半条链。

### 3.2 理想热点感知哈希的期望访问代价

在理想情况下，访问次数应与热度**负相关**——越热的 item 越快被找到。

使用 Zipfian 分布建模访问频率，第 `x` 个最热 item 的访问频率为：

```
f(x) = (1 / x^q) / Σ_{n=1..N}(1 / n^q)
```

其中 `q` 为偏斜因子（越大表示越集中）。

若能按访问频率降序排列每条链中的 item，理想期望访问次数为：

```
E_ideal = 1 + Σ_{k=1..L} F(k) * k
```

其中 `F(k)` 是各链中第 `k` 个位置上 item 的累积访问频率。

**结论**：随着链长增加，热点感知设计能带来显著的性能提升，这是 HotRing 的理论基础。

## 4. HotRing 的核心思想

### 4.1 基本直觉

HotRing 的核心直觉非常简单：

> **查找某个 item 所需的内存访问次数，应该与该 item 的热度负相关。**

要实现这一目标，需要解决两个核心挑战：

**挑战一：热点迁移（Hotspot Shift）**
热点集合会随时间不断变化（比如今天热门的商品明天可能就不热了），系统需要及时检测并适配这些变化。

**挑战二：并发访问（Concurrent Access）**
热点 item 天然会被海量并发请求同时访问，必须在高并发下保持正确性和高性能。

### 4.2 解决思路

针对热点迁移：**不重新排列链中 item 的顺序，而是移动头指针**，让头指针始终指向热点 item 或访问代价最优的位置。

针对并发访问：采用**无锁（Lock-Free）设计**，通过原子 CAS（Compare-And-Swap）操作替代锁机制。

## 5. 有序环哈希索引（Ordered-Ring Hash Index）

### 5.1 从链表到环

HotRing 对传统冲突链做了一个关键改造：**将链表的最后一个 item 的 next 指针指回第一个 item，形成一个环（Ring）**。

```
传统链表：
头指针 → [Item A] → [Item B] → [Item C] → NULL

HotRing 环：
头指针 ↓
      [Item A] → [Item B] → [Item C]
         ↑___________________________|
```

这样，头指针可以指向环中的**任意** item，而不再固定指向链首。当热点发生变化时，只需修改头指针，无需移动任何 item。

### 5.2 有序性：解决无限遍历问题

环结构带来一个严重问题：如果目标 item 不存在，遍历可能永远不会终止。

HotRing 的解决方案是**维护环的有序性**：按照 `(tag, key)` 的字典序对环中的 item 进行排序。

每个 item 的排序依据是二元组：

```
order_k = (tag_k, key_k)
```

其中 `tag` 是哈希值的低位部分（用于快速比较，避免直接比较长字符串 key）。

### 5.3 查找终止条件

在有序环中查找 item `k`，设当前访问到 item `i`，可以在以下情况立即终止：

**命中（Hit）条件：**
```
order_i = order_k
```

**未命中（Miss）条件，满足以下任一即可：**
```
order_{i-1} < order_k < order_i    （目标在两个相邻节点之间，不存在）
order_k < order_i < order_{i-1}    （目标比当前最小值还小，不存在）
order_i < order_{i-1} < order_k    （目标比当前最大值还大，不存在）
```

**直观理解**：由于环是有序的，如果遍历过程中发现目标 key 应该插入的位置已经"跳过去了"，就说明目标不存在，可以立即停止。

### 5.4 查找效率

有序环的平均查找代价：假设环中有 `n` 个 item，平均只需比较约 **(n/2) + 1** 个 item 即可完成查找（与传统链表相同），但由于头指针会指向热点，热点 item 通常能在 **2 次内存访问**内被找到。

## 6. 热点迁移识别策略

HotRing 设计了两种策略来识别热点并移动头指针，分别针对不同的精度和延迟需求。

### 6.1 索引格式设计

为了支持统计信息，HotRing 充分利用了 64 位指针中的空闲位（现代机器物理地址只用 48 位）：

**头指针格式（64 位）：**

```
┌──────────┬──────────────────┬──────────────────────────────────────────────────┐
│ Active   │  Total Counter   │              Address（48 位）                     │
│  (1 位)  │    (15 位)       │                                                  │
└──────────┴──────────────────┴──────────────────────────────────────────────────┘
```

- **Active bit**：控制是否开启统计采样
- **Total Counter**：记录该环被访问的总次数

**Item 格式（next 指针的 64 位）：**

```
┌──────────┬──────────┬──────────────────┬──────────────────────────────────────┐
│  Rehash  │ Occupied │  Item Counter    │         Next Address（48 位）         │
│  (1 位)  │  (1 位)  │    (14 位)       │                                      │
└──────────┴──────────┴──────────────────┴──────────────────────────────────────┘
```

- **Rehash bit**：控制 rehash 过程
- **Occupied bit**：保证并发操作的正确性
- **Item Counter**：记录该 item 被访问的次数

### 6.2 策略一：随机移动策略（Random Movement Strategy）

**核心思想**：利用热点 item 被访问概率远大于冷 item 这一特性，周期性地将头指针指向当前访问到的 item。

**具体流程**：

1. 每个线程维护一个本地计数器，记录已处理的请求数
2. 每经过 `R` 次请求（默认 `R=5`），判断是否需要移动头指针：
   - 若第 `R` 次访问是**热访问**（访问到的 item 正好是头指针指向的 item）→ 头指针不变
   - 若第 `R` 次访问是**冷访问** → 将头指针移动到此次访问的 item

```
示意图：
环：[A(热)] → [B] → [C] → [D] → 回到A

第5次请求访问了 C（冷访问）
→ 头指针移动到 C

新状态：
头指针 → [C] → [D] → [A] → [B] → 回到C
```

**优点**：实现极简，反应延迟低，无需额外内存开销。

**缺点**：
- 当环中存在**多个热点**时效果差，头指针会频繁抖动
- 工作负载偏斜性不明显时，准确率下降

### 6.3 策略二：统计采样策略（Statistical Sampling Strategy）

**核心思想**：通过周期性采样收集访问统计信息，计算出最优头指针位置。

**触发时机**：

每经过 `R` 次请求后，判断是否需要开启新一轮采样：
- 若第 `R` 次是热访问 → 热点未变，无需采样
- 若第 `R` 次是冷访问 → 热点可能已迁移，将 Active bit 置为 1，开启采样

**采样过程**：

Active bit 被设置后，后续对该环的每次访问都会：
1. 将 Total Counter 加 1
2. 将对应 item 的 Item Counter 加 1

采样数量设置为"环中 item 数"这一数量级，足以推导新的热点位置。

**最优头指针计算**：

采样结束后，计算头指针指向每个候选 item `t` 时的加权平均访问代价 `W_t`：

```
W_t = Σ_{i=1..k} (n_i / N) * ((i - t) mod k)
```

其中：
- `n_i`：item `i` 在采样期间的访问次数
- `N`：采样期间总访问次数
- `(i - t) mod k`：从头指针位置 `t` 出发，到达 item `i` 需要遍历的步数

选择使 `W_t` 最小的 item 作为新的头指针位置，通过 CAS 原子地更新头指针。

**示例**：

```
环中有 4 个 item：A、B、C、D
采样结果：A 被访问 60 次，B 10 次，C 20 次，D 10 次，共 100 次

计算 W_A（头指针指向 A）：
W_A = (60/100)*0 + (10/100)*1 + (20/100)*2 + (10/100)*3
    = 0 + 0.1 + 0.4 + 0.3 = 0.8

计算 W_C（头指针指向 C）：
W_C = (20/100)*0 + (10/100)*1 + (60/100)*2 + (10/100)*3
    = 0 + 0.1 + 1.2 + 0.3 = 1.6

→ 选择 W_A 最小，头指针指向 A（最热的 item）
```

**优点**：准确率高，能处理多热点场景，找到全局最优位置。

**缺点**：采样期间需要额外 CAS 操作，有短暂性能开销。

### 6.4 RCU 场景下的写热点优化

对于大于 8 字节的值，更新操作需要使用 **Read-Copy-Update（RCU）** 协议：创建新 item，修改前驱 item 的指针指向新 item。

这带来一个特殊情况：**写密集型热点 item 的前驱 item 也会变热**（因为每次 RCU 更新都需要找到前驱）。

HotRing 的优化：在统计采样时，对于 RCU 更新操作，不增加目标 item 的计数，而是增加其**前驱 item** 的计数。这样头指针会移动到写热点的前驱位置，使 RCU 更新更快。

### 6.5 热点继承（Hotspot Inheritance）

当头指针指向的 item（热项）被删除或 RCU 更新时，需要将头指针移动到其他 item：

- **RCU 更新头项**：头指针移动到该 item 的**新版本**（利用时间局部性，刚更新的 item 很可能立即被再次访问）
- **删除头项**：头指针直接移动到**下一个 item**，后续由热点识别策略进一步调整

## 7. 无锁并发操作设计

HotRing 的所有操作都基于原子 CAS 操作实现无锁设计，核心原则是：**两个线程不会同时修改同一个 next-item address**，若发生竞争，只有一个线程成功，其余线程重试。

### 7.1 读操作（Read）

读操作按照有序环的查找规则遍历，**不需要任何同步操作**，完全无锁。

### 7.2 插入操作（Insertion）

1. 找到新 item 应插入的位置（维护有序性）
2. 设置新 item 的 next 指针指向后继 item
3. 通过 CAS 将前驱 item 的 next 指针改为指向新 item

若两个线程同时插入，CAS 保证只有一个成功，另一个失败后重试。

### 7.3 更新操作（Update）

**原地更新**（值 ≤ 8 字节）：直接通过 CAS 原子更新值，不影响其他操作。

**RCU 更新**（值 > 8 字节）：需要特殊处理并发冲突。

问题场景：线程 1 正在 RCU 更新 item B（需要修改 B 的前驱 A 的指针），线程 2 同时在 B 之后插入新 item C（需要修改 B 的 next 指针）。两个操作修改的是不同指针，可能都成功，但 C 会因为 B 被替换而变得不可达。

**解决方案（Occupied bit）**：

```
步骤 1：将 B 的 next 指针中的 Occupied bit 置为 1
        → 此时任何试图修改 B 的 next 指针的操作（如插入 C）都会失败并重试

步骤 2：通过 CAS 将 A 的 next 指针改为指向新 item B'
        → 同时清除 B' 的 Occupied bit
```

### 7.4 删除操作（Deletion）

删除通过将"指向待删 item 的指针"改为"指向待删 item 的后继"来完成。同样使用 Occupied bit 防止并发冲突：

1. 将待删 item 的 Occupied bit 置为 1（防止其他线程修改其 next 指针）
2. 通过 CAS 将前驱 item 的 next 指针改为指向待删 item 的后继

### 7.5 头指针移动（Head Pointer Movement）

头指针移动通过 CAS 原子地更新哈希表中的头指针，需要处理与其他并发操作的冲突（如头指针移动与删除操作同时发生）。

## 8. 无锁 Rehash

### 8.1 触发条件

HotRing 的 rehash 触发条件与传统哈希表不同：

- **传统哈希表**：基于负载因子（item 数 / 桶数）触发
- **HotRing**：基于**查找所需的平均内存访问次数**触发

这种方式能结合热点分布情况，避免不必要的 rehash，减少 rehash 次数。

### 8.2 Tag 与哈希表的关系

理解 rehash 需要先理解 tag 的设计：

一个 `n` 位哈希值被分为两部分：
- 前 `k` 位：用于定位哈希桶（哈希表部分）
- 后 `t = n-k` 位：作为 tag（存储在每个 item 中）

当哈希表扩容 2 倍时，需要使用 `k+1` 位定位桶，tag 缩小为 `t-1` 位。

### 8.3 Rehash 三阶段

**阶段一：初始化（Initialization）**

1. 创建一个后台 rehash 线程
2. 新建一个原有哈希表 **2 倍大小**的新哈希表
3. 创建一个 rehash 节点，包含两个 rehash item，tag 分别为 `0` 和 `range/2`（其中 `range = 2^t`）
4. 新哈希表对应槽的头指针指向这两个 rehash item

**阶段二：分裂（Splitting）**

将两个 rehash item 插入原有的环中，它们作为 tag 范围的边界：

```
原有环（tag 范围 [0, range)）：
... → [Item(tag=10)] → [Item(tag=50)] → [Item(tag=80)] → ...

插入 rehash item 后：
... → [RehashItem(tag=0)] → [Item(tag=10)] → ... → [RehashItem(tag=range/2=64)] → [Item(tag=80)] → ...

分裂为两个新环：
新环1（tag 范围 [0, range/2)）：[RehashItem(0)] → [Item(10)] → [Item(50)] → 回到RehashItem(0)
新环2（tag 范围 [range/2, range)）：[RehashItem(64)] → [Item(80)] → 回到RehashItem(64)
```

整个过程通过无锁 CAS 完成，**无需复制或迁移任何 item**，开销极低。

**阶段三：清理（Cleanup）**

1. 等待所有对旧哈希表的访问结束
2. 删除旧哈希表
3. 清理所有 rehash item（将其从环中移除）

注意：旧哈希表的访问会阻塞 rehash 线程进入清理阶段，但**不影响主线程的正常读写**。

## 9. 性能评估结果

论文在模拟真实工作负载的基准测试中，将 HotRing 与以下系统进行了比较：

- **Chaining**：无锁链式哈希（基线）
- **Memcached**：广泛使用的内存 KVS
- **MemC3**：Memcached 的优化版本
- **MICA**：高性能内存 KVS

### 9.1 读性能

在极度偏斜的工作负载下（90% 访问集中在 1% 的 item）：

- HotRing 每秒最多处理 **565M 次读请求**
- 相比其他系统最多实现 **2.58× 的性能提升**
- 热点 item 通常能在 **2 次内存访问**内被找到

### 9.2 写性能

- **原地更新**：相比基线实现 **2.17× 的性能提升**
- **RCU 更新**：相比基线实现 **1.32× 的性能提升**

### 9.3 热点识别策略对比

| 策略 | 识别准确率 | 反应延迟 | 多热点支持 |
|------|-----------|---------|-----------|
| 随机移动策略 | 较低 | 极低 | 差 |
| 统计采样策略 | 高 | 较低 | 好 |

## 10. 总结与适用场景

### 10.1 HotRing 的设计亮点

HotRing 的设计可以概括为以下几个关键点：

**结构层面**：将传统冲突链改造为有序环，使头指针可以指向任意 item，从而通过移动头指针（而非移动 item）来优化热点访问路径。

**热点感知层面**：提供两种互补的热点识别策略——随机移动策略（低延迟、低开销）和统计采样策略（高准确率、支持多热点），并通过热点继承机制处理热项被修改或删除的情况。

**并发层面**：全程使用无锁 CAS 操作，通过 Occupied bit 解决 RCU 更新与插入/删除的并发冲突，支持海量并发请求。

**Rehash 层面**：基于平均访问代价触发 rehash，通过插入 rehash item 作为边界实现无数据迁移的环分裂，rehash 过程不阻塞正常读写。

### 10.2 适用场景

HotRing 特别适合以下场景：

- 访问模式**高度倾斜**（少量 item 承受绝大多数访问）
- 需要**极低延迟**的热点访问（如电商大促、实时事件）
- **多核并发**环境下的高吞吐量需求
- 热点会**动态迁移**的场景

### 10.3 局限性

- 当访问分布**均匀**时，HotRing 的优势不明显，与普通链式哈希性能相近
- 有序环的维护需要在插入时保持顺序，略微增加写入开销
- 统计采样期间有短暂的性能抖动
