## 一、为什么需要这么多层网关

看到上面的架构图，你可能会问：为什么不直接用一层网关搞定所有事情？答案是"术业有专攻"——不同层级的网关解决不同层面的问题，性能特征也完全不同。

### 1.1 四层与七层的本质区别

四层负载均衡工作在OSI模型的传输层（TCP/UDP层），它只看IP地址和端口号，不理解HTTP协议的内容。你可以把它想象成一个快递分拣中心，它只看包裹上的地址标签（IP+Port），不拆包裹。正因为不拆包裹，它的处理速度极快——经验上来说，4台四层负载集群能转发的流量，需要几十上百台七层负载才能处理。

七层负载均衡工作在应用层（HTTP层），它会"拆开包裹"看里面的内容——根据域名（server_name）、路径（URI）、请求头（Header）等信息做更精细的路由决策。它能理解"这个请求是要访问 docs.sankuai.com 的 /page 路径"，然后把它转发到学城的Web服务集群；而另一个访问 api.sankuai.com/orders 的请求则被转发到订单服务集群。这种智能路由是四层负载做不到的，代价是处理速度慢得多。

### 1.2 为什么不只用七层

如果直接用七层负载面对公网流量，因为性能瓶颈，需要在DNS层面配置大量解析记录来扩容，管理成本极高。而且DNS不会做健康检查——如果某个七层负载节点挂了，DNS仍然会把流量分过去，直到人工介入修改配置。引入四层负载后，四层负载会对后端的七层节点做健康检查，自动摘除故障节点。同时四层负载的Anycast机制能在30秒内完成跨机房容灾切换，而DNS切换的生效时间受TTL和各级DNS缓存影响，不可控且通常超过10分钟。

### 1.3 为什么还需要API网关

Oceanus是通用的七层HTTP网关，它处理的是"域名+路径"级别的路由。但有些业务场景需要更细粒度的控制：不同API有不同的鉴权方式（SSO、Passport、EPassport）、不同的限流策略、不同的协议转换需求（HTTP→MTThrift RPC）、不同的灰度规则。如果每个业务都自己搭一个Web应用来处理这些，研发效率极低且资源浪费。Shepherd API网关就是把这些通用的API管理能力收敛到一个统一平台，业务研发人员只需配置就能对外开放接口。

## 二、DNS层：流量的第一站

当用户在浏览器输入 `w.mt.cn` 或者App发起一个请求时，第一步是DNS解析。美团公网域名的DNS解析采用CNAME方式，指向多个四层负载的VIP地址。

```
用户请求 w.mt.cn
    │
    ├── 公网DNS解析 → w.mt.cn CNAME → mgw-vip-1.sankuai.com
    │                                  mgw-vip-2.sankuai.com  (轮询返回)
    │
    ├── 用户拿到一个VIP地址（如 103.37.142.166）
    │
    └── TCP连接建立到该VIP对应的MGW集群
```

DNS层的关键设计是CNAME中间域名机制：域名不直接指向多个IP，而是指向一个中间CNAME域名，由中间域名指向多个四层负载VIP。这样当某个VIP不可用时，只需修改中间域名的配置，所有相关域名的解析都会自动更新，不用逐个修改。

公网域名解析的IP地址是公网IP，经过公网DNS解析后，流量到达美团在北上两地的PoP点（网络接入点），这里部署着MGW四层负载集群。

## 三、四层负载均衡：MGW

### 3.1 MGW是什么

MGW（美团 Gateway）是美团自研的四层负载均衡系统，基于DPDK（Data Plane Development Kit）技术开发。DPDK是一个高性能的数据包处理框架，它绕过了Linux内核协议栈，在用户空间直接处理网络数据包，从而实现极高的转发性能。

### 3.2 MGW的部署架构

MGW的部署采用"PoP点集中部署 + Anycast"的架构：

北京和上海各设有PoP点（网络接入点），每个PoP点部署多个MGW集群。公网流量通过BGP协议路由到最近的PoP点。新建的机房（如次渠、铭泰、汇海、浦江）不再单独建设外网MGW集群，业务统一使用PoP点MGW集群。

MGW集群采用Anycast机制：不同机房的多组MGW集群宣告相同的VIP地址。当某个机房的MGW集群发生故障时，通过BGP协议自动撤销该机房的路由宣告，流量会自动切换到另一个机房的MGW集群。这个切换过程的RTO（Recovery Time Objective，恢复时间目标）小于30秒，远优于DNS切换的10分钟以上。

机房内部，MGW部署在核心交换机下方，常规的ToR（Top of Rack）交换机故障不会影响MGW。3.0架构机房统一使用100G容量的集群。

### 3.3 MGW与后端七层负载的关系

MGW作为四层负载，将收到的TCP连接转发给后端的Oceanus七层负载节点。它会：

对后端的Oceanus节点做健康检查，发现不可用节点自动摘除。支持平滑下线（权重调零仅对新连接生效，存量连接保持）和强制下线（对后续数据包返回RST，连接立即断开）两种模式。通过TOA（TCP Option Address）模块获取并透传真实客户端IP给后端服务。

### 3.4 MGW的容灾逃生方案

当整个AZ（可用区）发生故障时，MGW的逃生方式是主动停BGP邻居触发Anycast切换——故障AZ的MGW集群停止宣告路由，流量自动切换到其他AZ的集群。对于公有云上的CLB（Cloud Load Balancer），则通过云平台API批量摘流来实现逃生。

## 四、七层负载均衡：Oceanus

### 4.1 Oceanus是什么

Oceanus是美团的七层网关服务，针对HTTP/HTTPS/HTTP2/WebSocket协议的出入口流量提供网关服务。它的核心能力包括服务注册与发现、动态负载均衡、可视化管理、定制化路由、Session复用、熔断降级、一键截流和性能统计等。

用数字感受一下它的规模：已接入站点6939+（各环境26000+），已接入服务13600+（线上8725），日访问3000亿次，峰值QPS 890万+。

### 4.2 Oceanus的技术架构

Oceanus的整体架构由以下几个核心组件构成：

**OpenResty引擎层**：这是七层负载均衡器的基础。OpenResty是一个基于Nginx的Web平台，集成了Lua脚本能力。Oceanus v3.0弃用了早期基于Tengine的方案，拥抱OpenResty官方迭代。OpenResty负责实际的HTTP请求处理、反向代理、负载均衡等核心功能。

**Lua统一框架**：这是OpenResty的扩展功能层，用Lua脚本实现了精细化分流、MTSI反扒、统一延签等高级功能。v2.0版本抽象了插件资源，封装了基础功能组件，支持动态加载生效，大大提高了插件迭代速度。

**Tethys管理端**：负责域名配置、精细化分流配置、插件降级配置等管理功能。这是面向用户的配置入口。

**Manager（Oceanus Manager）**：这是一个与Nginx运行在同一台机器上的程序（旧名HLBManager），负责各种元数据的变更同步、Nginx交互控制、服务粒度动态路由。它打通了Nginx的dyups模块和服务治理平台，实现了不触发Nginx reload就能动态感知服务节点列表的变化。

**服务治理相关组件**：复用OCTO治理的组件（MNS、MSGP等），实现HTTP和MTThrift服务治理的统一化。

**Oceanus-Registry SDK**：服务启动时上报appkey、IP、端口、泳道等元数据信息。

### 4.3 动态upstream：不reload就能更新节点列表

原生Nginx的服务IP列表保存在配置文件中（upstream块），修改后需要执行reload命令才能生效。对于美团这种频繁变更的场景，频繁reload会导致公网长连接不稳定、worker进程内存占用等问题。

Oceanus通过dyups（dynamic upstream）模块解决了这个问题。dyups模块提供了直接修改Nginx内存中upstream信息的API，无需触发reload。工作原理是：通过API接收变更请求 → 将变更放入共享内存队列 → 各个worker进程从队列拉取变更并在本地生效 → 落地到本地内存。第一次调用时需要加锁同步未消费的数据，保证数据串行化。

Oceanus Manager会控制Nginx配置reload的频率：如果5分钟内有过reload，本次reload会在5分钟倒计时后执行，即触发发布的配置会在0-5分钟内生效。

### 4.4 Oceanus的核心功能

Oceanus提供以下核心功能：

**服务自动注册与发现**：服务节点自动导流，失效节点自动摘除。服务启动时通过gateway-registry SDK上报appkey、IP、端口、泳道等元数据。Oceanus Manager从OCTO的服务治理组件获取节点列表，通过dyups同步到Nginx内存。

**多种负载均衡策略**：支持加权轮询（Weighted Round Robin）、IDC优化（同机房优先）、IP Hash、最小响应时间等策略。

**节点健康检查**：Scanner自动扫描服务节点的健康状况，主动进行异常节点摘除和可用节点恢复。当前摘掉节点的经验值时间约为40秒，其中10秒为Oceanus Manager同步延迟，30秒为OCTO同步至本机SGAgent的同步延迟。

**精细化分流**：基于Lua框架实现的高级路由能力，支持按域名、路径、Header、Cookie等维度做细粒度的流量分发。

**限流与过载保护**：提供service级别的过载保护和一键截流能力。Oceanus v2.0建设了限流2.0，更精准地保护业务服务。

**监控与报警**：支持API粒度的监控报警，指标包括Avg Latency、TP90、TP95、Total Request Count、Backend 2XX/3XX/4XX/5XX Response Count等。接入了Raptor统一监控和MCM2.0智能监控。

**SET路由与泳道路由**：支持SET化和泳道等七层路由能力，这是全链路灰度的基础（后文详述）。

### 4.5 Oceanus的演进历程

Oceanus v1.0（2016年）提供了服务动态注册与发现、健康检查、慢启动等HTTP服务治理功能，从0%到100%覆盖了公司所有HTTP服务。

Oceanus v2.0重点演进七层网关，丰富了泳道/Set路由等七层能力，完成了集群拆分、监控打点、配置结构化管理。期间协助SRE团队把北上两地积累多年的Nginx配置做了彻底梳理、合并、迁移，涉及几百次SOP操作，2018年10月上海SLB平台下线标志着迁移完成。

Oceanus v3.0做了全面升级：弃用Tengine拥抱OpenResty，研发Lua统一框架v2.0，与Avatar团队合作统一线上线下管理界面，建设Ark集群管理平台实现集群自动化管理。

## 五、API网关：Shepherd

### 5.1 Shepherd是什么

如果说Oceanus是"HTTP流量的统一大门"，那么Shepherd就是"API接口的精细管理者"。Shepherd是美团统一API网关服务，运行在外部请求与内部服务之间的流量入口，实现协议转换、鉴权、流控、参数校验、监控等通用功能。

在没有Shepherd之前，业务研发人员要把内部服务输出为对外HTTP API，需要自己搭建Web应用完成鉴权、限流、监控日志、参数校验、协议转换等工作，还要维护机器和基础组件升级，研发效率极低。Shepherd把这些通用能力收敛到统一平台，业务研发人员只需配置就能对外开放接口。

目前接入Shepherd的API数量超过18000个，线上运行90多个集群，日均总调用次数在百亿以上。

### 5.2 Shepherd的整体架构

Shepherd的架构分为三层：控制面、配置中心、数据面。

**控制面**由Shepherd管理平台和监控中心组成。管理平台完成API的全生命周期管理——从创建API、参数录入、DSL脚本生成，到API测试（文档和MOCK功能）、发布审批、灰度上线、版本回滚，再到运行期监控和最终的API下线。监控中心负责收集API请求的监控数据并发出业务告警。

**配置中心**使用公司统一配置服务Lion和本地缓存结合的方式，实现动态配置。API的配置信息使用自定义的DSL（Domain Specified Language，领域专用语言）来描述，包含路由信息、请求/响应规则、功能组件配置、后端服务调用规则等。

**数据面**即Shepherd服务端，是实际处理API请求的引擎。一次完整的API请求流程是：从移动应用/Web应用/合作伙伴/内部系统发起 → 经Nginx（Oceanus）负载均衡 → 到达Shepherd服务端 → 服务端执行一系列基础功能组件和业务自定义组件 → 通过泛化调用请求后端RPC/HTTP/函数/服务编排服务 → 返回响应结果。

### 5.3 API路由：前缀树的设计

当请求到达Shepherd数据面时，第一步是API路由——根据请求的域名和路径找到对应的API配置。HTTP请求路径中可能包含路径变量（如 `/api/orders/{orderId}`），Shepherd没有采用正则匹配（性能差），而是设计了两种数据结构来存储路由信息：

第一种是不包含路径变量的直接映射MAP结构：key是完整的域名和路径信息，value是具体的API配置。第二种是包含路径变量的前缀树（Trie树）数据结构：通过前缀匹配方式查找，先进行叶子节点精确查找并将查找节点入栈，如果匹配不上则将栈顶节点出栈，再将同级的变量节点入栈，如果仍然找不到则继续回溯，直到找到或没找到路径节点并退出。

这种设计兼顾了精确路径的O(1)查找效率和带变量路径的高效匹配。

### 5.4 功能组件：过滤器链

当请求命中API路径后，具体的处理逻辑由DSL中配置的一系列功能组件（过滤器）完成。Shepherd提供了丰富的系统组件：

链路追踪（Mtrace集成）、实时监控（Raptor集成）、访问日志、参数校验、鉴权（SSO/Passport/EPassport/反爬等）、限流（UUID/APP/IP/集群多维度）、熔断降级、灰度分流等。

除了系统组件，Shepherd还支持业务研发人员开发自定义组件。通过加载自定义Jar包，业务可以实现自定义验签、自定义结果处理等特殊逻辑。目前已有200多个自定义组件接入，覆盖优选、外卖、餐饮、打车等重要业务。自定义组件支持插件化部署模式，可以动态加载生效。

### 5.5 协议转换与服务调用

API调用的最后一步是协议转换。Shepherd需要完成：获取HTTP请求参数和Context本地参数 → 拼装后端服务参数 → 完成HTTP协议到后端服务的协议转换（HTTP→MTThrift RPC 或 HTTP→HTTP） → 调用后端服务获取响应 → 转换为HTTP响应返回。

以调用后端RPC服务为例：通过JsonPath表达式获取HTTP请求不同部位（query、header、body、cookie、path）的参数值，替换RPC请求参数相应部位的value，生成服务参数DSL，最后借助RPC泛化调用完成服务调用。

Shepherd还支持服务编排能力——一个HTTP请求可以编排调用多个后端服务并聚合结果。这是通过与客服团队开发的海盗组件合作实现的，海盗独立部署提供服务编排能力，Shepherd通过RPC调用海盗，对业务透明。

### 5.6 Shepherd的高可用设计

**全异步化处理**：请求通过Jetty IO线程（后升级为Netty）异步提交到业务处理线程池，调用后端服务使用异步方式，释放了网络等待引起的线程占用。经过多次优化（长连接、请求预热、日志异步化、Netty替换Jetty），单机端到端QPS从2000提升到15000以上。

**集群隔离**：按业务线维度进行集群隔离，也支持重要业务独立部署。

**快慢线程池隔离**：统计API请求处理时间，将耗时超过容忍阈值的请求隔离到慢线程池，避免影响其他正常API调用。也支持业务配置自定义线程池。

**熔断降级**：实时监控请求统计信息，达到失败阈值后自动熔断返回默认值。

**弹性伸缩**：接入弹性伸缩模块，根据CPU等指标快速扩缩容，还支持快速摘除问题节点和问题组件。

### 5.7 Shepherd的灰度能力

Shepherd支持两种灰度维度：

**灰度API自身逻辑**：通过将流量分流到不同的API版本实现灰度。灰度策略支持按比例灰度和按条件灰度。

**灰度下游服务**：通过给流量打标，分流到指定的下游灰度单元中。具体包括灰度链路（基于LiteSET的流量隔离）、SET链路路由和业务分组（GroupTags）。

Shepherd的灰度链路支持三种分流规则：

条件分流——分流字段表达式取值等于条件值时进行分流，多个值用英文分号分割。

比例分流——对分流字段表达式取值的hash值取模，如果余值小于分流数则命中灰度。

直接分流——将分流字段表达式取值的结果直接作为流量路由的灰度链路值。

## 六、服务治理与流量路由：OCTO

### 6.1 OCTO是什么

OCTO（Open Communication Technology Organization）是美团的服务治理平台，管理着服务注册发现、负载均衡、熔断、灰度路由等核心治理能力。如果说Oceanus和Shepherd是流量的"大门"和"分拣中心"，那OCTO就是整个路由体系的"大脑"——它知道每个服务有哪些实例在运行、每个实例的健康状态、流量应该按什么规则路由到哪个实例。

### 6.2 OCTO的整体架构

OCTO 1.0架构包含以下核心组件：

**Provider（服务提供者）**：将服务信息注册到Sg_agent中，由Sg_agent统一将节点信息注册到MNS注册中心。

**Consumer（服务消费者）**：通过SgAgent从MNS中获取服务数据。

**MNS（命名服务）**：基于ZooKeeper持久化存储服务节点信息。后续存储从CP型的ZK改为AP型的KV存储Cellar，直接替换ZK。MNS-Controller作为ZK的缓存层，承担ZK的读请求和数据推送。

**Scanner**：对服务节点做健康检查，发现节点不健康时降低权重。

**MSGP**：OCTO的服务治理平台门户，用户可以在其上查询服务状态以及修改应用规则。

OCTO还向Service Mesh架构演进（OCTO 2.0），通过Sidecar解耦业务和RPC流量，轻量化客户端SDK。不过Mesh架构在美团内部项目曾暂停，实际的流量路由主要由OCTO的路由规则引擎来承载。

### 6.3 流量路由设计总览

OCTO的流量路由分为两大类：逻辑路由（标签路由）和物理路由（地理位置路由）。

逻辑路由包括SET路由、LiteSET路由和泳道路由，它们都是基于给服务实例打标签实现的，所以也叫标签路由。物理路由包括同机房路由和同城市路由，基于地理位置实现。

每种路由都有默认规则，也允许用户自定义。用户自定义路由规则优先于默认规则。路由规则控制的是单次调用——选择下游服务的规则，把这个规则应用到每一次调用上，就构成了流量在服务之间流动的路线。

### 6.4 SET路由：单元化架构的流量隔离

SET是软件系统架构里的概念，阿里巴巴叫"单元化架构"，美团叫"SET化架构"。SET化架构把一个大的系统集群从逻辑上划分为多个小集群，每个SET承担一部分流量，是一个封闭的业务闭环——除了业务应用，SET还包括消息队列、数据库等基础组件。流量进入SET内可以完成所有业务逻辑，无需调用SET外的服务。

SET路由的规则：

如果下游服务开启了SET开关，优先调用同SET（包括中心SET）的节点。如果用户自定义了路由规则则应用自定义规则。如果下游服务没有开启SET开关，则调用中心SET的下游服务——即使该服务在当前SET有部署，也不会调用本SET内的实例。如果选定的下游服务可用则调用成功，否则调用失败（SET不支持fallback）。

SET路由的关键特点是"隔离优先"——它不支持fallback，一旦流量进入某个SET，就必须在SET内完成所有调用，不能回退到中心SET。这保证了SET之间的严格隔离，适用于容灾和系统扩展场景。

### 6.5 LiteSET路由：生产环境的灰度链路

LiteSET（原"灰度链路"）是基于SET底层能力构建的，生产环境下的链路粒度LiteSET。与SET不同，LiteSET基于流量中的标记识别并进行路由，标记在整个链路透传，使流量具备"回流"能力。另外，LiteSET只隔离服务层流量，不隔离数据库、缓存等。

LiteSET的路由规则遵循"可用性优先"原则：

优先选择LiteSET名称与当前流量标记相同的LiteSET内的服务。如果该服务可用则直接调用。如果该服务不可用（不存在或故障），且当前是非中心LiteSET，则fallback调用中心的对应服务。如果选定的中心服务也不可用则调用失败。

流量标记一旦被设置，下游的所有调用都会携带这个标记，直到被修改。这就是"流量染色"——给流量打上标记，标记在整个调用链生命周期里一直存在。

LiteSET的fallback机制是它与SET的关键区别：SET是"隔离优先不支持fallback"，LiteSET是"可用性优先支持fallback"。这使得LiteSET特别适合灰度发布——只有需要灰度的服务部署灰度实例，其他服务自动fallback到主干，不用全量部署。

### 6.6 泳道路由：线下测试的流量隔离

泳道的定位是线下测试时隔离测试人员之间的相互干扰。泳道不在线上生产环境使用。

泳道的路由规则与LiteSET类似，区别在于fallback条件：LiteSET在下游服务"不存在或故障"时都fallback到中心；泳道只在下游服务"不存在"时fallback到中心，如果服务存在但节点故障则直接调用失败，不fallback。

这个细微区别的设计意图是：泳道用于测试环境，如果某个服务实例挂了你应该知道（测试失败），而不是悄悄回退到主干让你以为测试通过了。

### 6.7 地理位置路由

地理位置路由考虑的是性能，是物理现实的反映。包括同机房优先和同城优先两种策略，每种都有强制和非强制两种模式：

非强制同机房优先：同机房可用时走同机房，同机房不可用时走同城跨机房。强制同机房优先：同机房可用时走同机房，同机房不可用时直接失败，不允许跨机房。非强制同城优先：同城可用时走同城，同城不可用时跨城调用。未配置：全局无差别调用。

### 6.8 路由优先级

当多种路由规则同时使用时，优先级如下（从高到低）：

1. RPC分流（用户自定义的可配置路由，优先级最高）
2. SET/LiteSET路由（标签路由-逻辑路由）
3. 泳道路由（标签路由-逻辑路由）
4. 同机房路由（地理位置路由-物理路由）
5. 同城路由（地理位置路由-物理路由）

即先应用标签路由（逻辑路由），再应用地理位置路由（物理路由）。标签路由内部先SET/LiteSET后泳道，地理位置路由内部先机房后地域。

```
一次调用的路由决策流程：

请求进来
  │
  ├── 1. 有用户自定义RPC分流规则? → 是 → 应用自定义规则
  │                                 否 ↓
  ├── 2. 下游开启了SET/LiteSET?   → 是 → 应用SET/LiteSET路由
  │                                 否 ↓
  ├── 3. 有泳道标记?              → 是 → 应用泳道路由
  │                                 否 ↓
  ├── 4. 配置了同机房优先?        → 是 → 同机房优先路由
  │                                 否 ↓
  ├── 5. 配置了同城优先?          → 是 → 同城优先路由
  │                                 否 ↓
  └── 6. 全局无差别调用
```

## 七、全链路灰度：多组件协同的流量调度

### 7.1 为什么需要全链路灰度

单服务灰度只控制一个应用的新旧版本流量比例，但一个请求通常会经过多个服务。如果只有入口服务走了新版本，下游服务还是旧版本，新旧逻辑混合就会出问题。全链路灰度解决的是"整条调用链从头到尾都按灰度身份走新版本"的问题。

### 7.2 核心组件分工

全链路灰度涉及多个组件的协同：

**大禹（大禹）**：大禹，管理流量染色、隔离规则和泳道路由策略。它是"统一灰度控制面"，决定"哪些流量走哪条泳道"。

**Cargo**：Cargo，管理泳道和测试环境的创建/销毁/配置。它是"泳道的物业管理处"。

**Oceanus/Shepherd**：入口层网关，识别灰度流量、注入灰度Header。Oceanus是HTTP流量入口，Shepherd是API接口入口。

**OCTO**：核心路由引擎，根据灰度Header决定请求路由到哪个泳道的实例。

**Pigeon/MTThrift**：RPC框架，负责在服务间调用时传播灰度Header。

**Lion**：配置中心，支持按灰度上下文返回不同配置。

**Mafka**：消息队列，支持灰度消息隔离（独立Topic或Header过滤）。

**Zebra**：数据库中间件，根据灰度上下文路由到灰度数据源。

**Squirrel**：缓存服务，灰度key加命名空间隔离。

**Mtrace**：链路追踪，记录灰度维度，区分灰度和基准的错误。

**Raptor**：监控平台，按灰度泳道统计错误率、延迟、限流次数。

### 7.3 灰度上下文如何穿透整条链路

灰度的核心机制是"流量染色"——在入口处给请求打上灰度标记（Header），这个标记在整条调用链中自动传播：

1. 用户请求到达Oceanus/Shepherd网关。
2. 网关调用大禹规则引擎，判断该请求是否命中灰度规则。
3. 如果命中，网关注入灰度Header（如 `x-gray-lane: gray-canary`），同时生成签名防止伪造。
4. 网关向OCTO查询下游服务的灰度实例，路由过去。
5. 服务A调用服务B时，Pigeon/MTThrift RPC框架自动把灰度Header复制到出站请求。
6. OCTO根据Header中的灰度标记，将请求路由到服务B的灰度实例。
7. 如果服务B没有灰度实例，按策略fallback到主干（LiteSET）或报错（STRICT）。
8. 灰度标记通过Mtrace的Baggage机制在整个链路中传播和记录。

### 7.4 灰度规则的优先级

当多条灰度规则同时存在时，必须有确定性的优先级链（从高到低）：

1. 测试账号/指定用户白名单（QA定向测试）
2. 指定机器/IP（如办公网出口IP全部走灰度）
3. 指定标签（如App版本>=8.0）
4. 指定租户（B端SaaS场景，某商户的所有请求走灰度）
5. 百分比灰度桶（按用户ID取模，最常见的"放5%流量"方式）
6. 以上都没命中 → 走baseline主干

关键原则是：入口层（Oceanus+大禹）计算出最终结果后写入Header，下游服务不再重新计算。如果让每个服务自己判断优先级，一百个服务可能算出一百个不同结果，链路就乱了。

### 7.5 灰度Header的安全设计

如果任何人都能在请求头里写一个 `x-gray-lane` 就进入灰度链路，外部用户就能伪造Header进入测试环境。美团的做法是：

**外部请求清洗**：从App/H5进来的外部请求，如果携带了 `x-gray-*` 开头的Header，网关直接剥掉。外部用户不可能通过伪造Header进入灰度链路。

**入口签名机制**：网关根据大禹规则判断请求应进入灰度后，注入灰度Header的同时生成HMAC-SHA256签名，包含泳道标识、规则ID、过期时间。下游服务（或Sidecar）在接收请求时验证签名，不匹配或已过期则拒绝按灰度路由处理。

**Header传播白名单**：只有特定的灰度相关Header（x-gray-enabled、x-gray-lane、x-gray-tag、x-gray-rule-id、x-gray-expire-at、x-gray-signature）以及追踪相关Header（traceparent、tracestate、baggage）允许在内部链路中传播。其他任何 `x-*` Header都不允许透传。

### 7.6 服务治理规则的灰度隔离

这是一个容易被忽略但很容易出事的问题。如果灰度实例和主干实例共享同一个限流计数器或熔断窗口，灰度出了问题会连带影响主干。

在OCTO和大禹的规则配置中，限流、熔断、鉴权都按泳道独立建桶：

```
主干限流桶：OrderService + /api/order/create + baseline → QPS 1000
灰度限流桶：OrderService + /api/order/create + gray-canary → QPS 100

主干熔断窗口：OrderService + /api/order/create + baseline → 独立统计
灰度熔断窗口：OrderService + /api/order/create + gray-canary → 独立统计
```

这样灰度链路出了任何问题，主干都不受影响。灰度的限流阈值通常设得更低（因为只有5%的流量），更容易在小流量阶段就暴露性能问题。

## 八、一次请求的完整旅程

让我们用一个具体的例子把所有组件串联起来。假设用户在App上点击"下单"，这个请求的完整旅程如下：

### 8.1 DNS解析与四层负载

用户App发起请求 `api.sankuai.com/orders/create`。公网DNS解析返回一个MGW的VIP地址。TCP连接到达MGW集群。MGW根据负载策略将TCP连接转发给后端的Oceanus节点，同时通过TOA模块透传真实客户端IP。

### 8.2 Oceanus七层网关处理

Oceanus收到HTTP请求后执行以下处理链：

**安全组件**：WAF（Web Application Firewall）检查请求是否有攻击特征，MTSI反扒检查是否是爬虫。如果被拦截，分别返回HTTP 456和HTTP 403。

**TLS卸载**：如果是HTTPS请求，在此完成TLS解密（Oceanus管理着所有域名的SSL证书）。

**路由匹配**：根据请求的Host头（`api.sankuai.com`）和URI（`/orders/create`）匹配站点配置，找到对应的后端服务。

**灰度判断**：调用大禹规则引擎，检查该用户是否命中灰度规则。如果命中，注入灰度Header和签名。

**服务发现**：向OCTO查询后端服务的可用实例列表（考虑灰度标记、SET/LiteSET标签、机房位置等路由规则）。

**负载均衡**：根据策略（加权轮询、同机房优先等）选择一个后端实例。

**限流检查**：检查该服务是否触发限流规则。

**转发请求**：将请求转发给后端实例，同时注入TraceId用于全链路追踪。

### 8.3 Shepherd API网关处理（如果请求经过API网关）

某些API会经过Shepherd做更精细的处理：

**API路由**：根据域名和路径在前缀树中匹配到对应的API配置。

**过滤器链执行**：依次执行参数校验 → SSO鉴权 → 限流检查 → 灰度分流等过滤器。

**协议转换**：将HTTP请求参数通过JsonPath提取，拼装成后端MTThrift RPC调用的参数。

**泛化调用**：通过Pigeon RPC框架调用后端订单服务。Pigeon会自动透传灰度Header和TraceId。

**响应组装**：将RPC返回结果转换为HTTP响应格式返回。

### 8.4 后端微服务间调用

订单服务收到请求后，可能需要调用支付服务、库存服务等。这些服务间调用通过Pigeon/MTThrift RPC框架完成：

Pigeon从OCTO获取支付服务的实例列表。OCTO根据路由规则（灰度标记→SET/LiteSET→泳道→同机房→同城）选择合适的实例。Pigeon建立连接，发送RPC请求，自动透传灰度Header和TraceId。支付服务处理完返回结果。订单服务还可以通过Mafka发送异步消息（如通知库存扣减），消息中也携带灰度标记。通过Zebra访问数据库，通过Squirrel访问缓存，这些中间件都会根据灰度上下文做相应隔离。

### 8.5 全链路可观测

整个过程中，Mtrace通过TraceId把所有调用串成一棵树，每个Span上标记了灰度信息。Raptor实时监控各服务的QPS、延迟、错误率，按灰度泳道独立统计。如果灰度实例的错误率上升，可以在Mtrace上按灰度标签过滤，快速定位是哪个服务哪个接口报了错，然后通过DevTools/Plus一键回滚——大禹立即摘除灰度规则，所有流量回到主干。

## 九、稳定性保障体系

### 9.1 多层容灾

美团的网关体系采用多层容灾设计：

**DNS层**：CNAME指向多个VIP，单VIP故障通过DNS切换恢复（RTO < 10分钟，2022Q4后通过Anycast优化到RTO < 30秒）。

**MGW四层负载层**：Anycast机制，AZ故障时BGP自动切换（RTO < 30秒）。支持2AZ 2集群双发VIP容灾。

**Oceanus七层负载层**：多机房部署，MGW对Oceanus节点做健康检查自动摘除故障节点。支持平滑逃生（通过MGW平滑下线后分批重启）和快速逃生（权重调零，连接立即断开重连）。

**Shepherd API网关层**：弹性伸缩，根据CPU等指标快速扩缩容。支持快速摘除问题节点和问题组件。集群隔离避免业务互相影响。

### 9.2 节点摘除的时效

从服务节点故障到被自动摘除，整个链路的经验值时间约为40秒：OCTO自身健康检查周期约15秒（SLA为30秒）→ OCTO同步至本机SGAgent约30秒 → Oceanus Manager同步延迟约10秒。在此期间，流量可能继续打到故障节点，出现超时或报错。

### 9.3 Oceanus的稳定性建设

Oceanus在稳定性方面做了大量工作：

**三板斧之可变更性**：核心变更流程接入MCM2.0实现高峰期预检、新人卡控和审批流，降低变更风险。

**三板斧之可观测性**：接入Raptor常态化智能监控和MCM2.0智能监控并持续调优。

**三板斧之可回滚**：站点配置回滚功能的幂等性能力，加固变更安全的最后一道防火墙。

**架构解耦**：数据面移除对MCC、OCTO全量appkey查询、RDS等外部组件的依赖，闭环到依赖中间层服务，提升整体稳定性。

**容灾能力**：联合业务建设SET动态和静态降级能力，进行故障和容灾演练，建设一致性巡检能力。

### 9.4 Shepherd的稳定性保障

Shepherd提供了全方位的稳定性保障：

**流量管控**：从UUID限流、APP限流、IP限流、集群限流等多维度提供流量保护。

**请求缓存**：对幂等的、查询频繁的、数据及时性不敏感的请求可开启请求缓存。

**超时管理**：每个API都设置了处理超时时间，超时快速失败。

**熔断降级**：实时监控请求统计，达到失败阈值自动熔断返回默认值。

**立体化监控**：Raptor（应用层+系统层监控）、Mtrace（全链路追踪）、Logscan（异常关键字监控）、远程日志中心、Scanner（健康检查）。

**多维度告警**：限流告警、请求失败告警、组件异常告警、API异常告警、健康检查失败告警。

## 十一、手把手实战：你的服务从部署到被访问的完整旅程

前面讲了这么多架构和概念，你可能还是觉得脑袋一团浆糊——"我知道有Oceanus、Shepherd、OCTO这些东西了，但我组里的服务部署上去之后，到底是怎么通过域名访问到的？那么多域名是怎么分配的？映射关系到底是什么？泳道又是怎么串起来的？"

别急，这一节我们完全不跳步，用一个虚构但真实的例子，从你的团队写完代码开始，一步步走完"服务部署→域名注册→网关配置→用户访问→泳道测试→灰度发布"的全流程。你会看到每一步在哪个平台上操作、配置了什么、这些配置之间怎么串联起来形成一条完整的路由链路。

### 11.1 设定场景：你的团队和服务

假设你所在的团队叫"到店订单组"，你们负责三个微服务：

**OrderService**（订单服务）：AppKey 是 `com.sankuai.daodian.orderservice`，提供创建订单、查询订单等RPC接口，同时也对外提供HTTP接口。

**ShopService**（门店服务）：AppKey 是 `com.sankuai.daodian.shopservice`，提供门店信息查询的RPC接口。

**StockService**（库存服务）：AppKey 是 `com.sankuai.daodian.stockservice`，提供库存扣减的RPC接口，同时作为消息消费者监听Mafka的订单消息。

用户在App上点击"下单"时，请求最终会到达OrderService，OrderService内部会通过RPC调用ShopService查门店信息、通过RPC调用StockService扣库存，还会通过Mafka发消息通知其他系统。

现在你要把这整套服务部署上去，让用户能通过 `order.sankuai.com` 这个域名访问到。同时你还要能在测试环境里建泳道做联调测试，以及在生产环境做灰度发布。

下面我们一步一步来。

### 11.2 第一步：服务注册——让系统知道你的服务存在

你的代码写完了，打成了JAR包。在美团，服务部署用的是DevTools/Plus平台。你在DevTools上创建发布单，选择你的AppKey（比如 `com.sankuai.daodian.orderservice`），选择要部署到的环境（线下Test / 线上Prod），选择机房，然后点击部署。

DevTools调用Avatar平台在对应的机房里找到一台物理机或容器，把你的JAR包部署上去。服务进程启动后，第一件事不是开始处理业务请求，而是向OCTO注册中心"报到"。

注册的具体过程是这样的：你的服务进程里集成了一个叫 `sg_agent` 的本地代理（部署在同一台机器上，端口5266）。服务启动时，通过 `mns-invoker` SDK向sg_agent发送注册请求，信息包括：

```
AppKey:     com.sankuai.daodian.orderservice
IP:         10.65.12.34
Port:       8080
环境:        prod（或test）
机房:        永丰(YF)
状态:        正常
```

sg_agent收到注册信息后，将其上报到MNS（美团 Naming Service，命名服务）注册中心。MNS底层基于ZooKeeper（后改为Cellar KV存储）持久化存储这些信息。从这一刻起，OCTO的注册中心就知道了："`com.sankuai.daodian.orderservice` 这个服务在 `10.65.12.34:8080` 有一个正常运行的实例，在永丰机房。"

如果你的服务是通过 `gateway-registry SDK` 注册的（HTTP服务），注册信息里还会包含泳道等元数据。如果是通过 `mns-invoker` 注册的（RPC服务），则注册到OCTO的标准注册流程中。

ShopService和StockService也各自走同样的注册流程。三个服务都注册完毕后，OCTO的注册中心里就有了这三个AppKey各自的实例列表。

关键理解：AppKey是服务在整个美团基础设施中的唯一身份标识。后面所有的路由、配置、监控、告警，全都是以AppKey为单位组织的。你在任何平台（OCTO、Oceanus、Shepherd、Raptor）上查一个服务，第一步都是输入AppKey。

### 11.3 第二步：域名注册——让域名指向你的服务

服务注册好了，但现在用户还不能通过域名访问到它。你需要把 `order.sankuai.com` 这个域名和你的服务关联起来。这一步涉及几个平台的协作。

#### 11.3.1 在Domain系统注册域名解析

美团内部有一个叫 **Domain系统**（domain.mws.sankuai.com）的域名管理平台。你在上面创建一条解析记录：

```
域名:    order.sankuai.com
类型:    CNAME
解析值:  order.sankuai.com.mgw.sankuai.com
```

这条CNAME记录把 `order.sankuai.com` 指向了一个MGW的中间域名 `order.sankuai.com.mgw.sankuai.com`。这个中间域名背后对应着多个MGW集群的VIP地址——北京PoP点的VIP和上海PoP点的VIP。

为什么是CNAME而不是直接指向IP？因为MGW集群的VIP可能会变更（比如扩容、机房调整），用CNAME指向中间域名后，VIP变更时只需修改中间域名的解析，所有指向它的业务域名自动跟着变，不用逐个修改。

用户在浏览器输入 `order.sankuai.com` 后，公网DNS解析链路是：

```
order.sankuai.com
  → CNAME → order.sankuai.com.mgw.sankuai.com
  → A记录 → 103.37.142.166（北京PoP点MGW VIP）
             103.37.142.167（上海PoP点MGW VIP）
```

DNS轮询返回其中一个VIP给用户，用户的TCP连接就到达了MGW。

#### 11.3.2 在MGW管理平台配置四层转发

MGW收到TCP连接后，需要知道把它转发给谁。这需要在 **MGW管理平台**（beidou.sankuai.com）上配置一条VS（Virtual Server）规则：

```
VIP:        103.37.142.166:443
协议:        TCP
后端RS列表:  Oceanus集群的各个节点IP:80
健康检查:    TCP探针，每5秒一次
```

这条配置告诉MGW："凡是在VIP `103.37.142.166:443` 上收到的TCP连接，都转发给后端的Oceanus七层负载节点列表，哪个Oceanus节点不健康就自动摘掉。"

注意：MGW不关心HTTP内容，它只做TCP层面的连接转发。它不知道请求的是 `order.sankuai.com` 还是 `docs.sankuai.com`——所有域名的TCP连接都打到同一组MGW VIP上，由MGW统一转发给Oceanus。区分域名是Oceanus的事。

#### 11.3.3 在Oceanus上创建站点——这是最关键的一步

现在TCP连接到了Oceanus，Oceanus需要根据HTTP请求里的Host头来判断"这个请求是要访问哪个域名的，应该转发给哪个后端服务"。这就需要在 **Oceanus管理平台**（Oceanus.mws.sankuai.com）上创建一个"站点"。

你在Oceanus上创建站点，填写以下信息：

```
站点域名:    order.sankuai.com
后端AppKey:  com.sankuai.daodian.orderservice
负载策略:    weighted round robin（加权轮询）
健康检查:    开启
HTTPS:      开启（上传SSL证书）
```

这条站点配置做了什么？它告诉Oceanus："当收到HTTP请求的Host头是 `order.sankuai.com` 时，去OCTO查询 `com.sankuai.daodian.orderservice` 这个AppKey的实例列表，然后用加权轮询策略选一个实例转发过去。"

Oceanus Manager（运行在每台Oceanus机器上的管理程序）会持续从OCTO的MNS注册中心拉取 `com.sankuai.daodian.orderservice` 的实例列表变化，通过dyups模块动态更新到Nginx内存中的upstream配置里。当你的服务新增了一台机器（通过DevTools扩容），新机器向OCTO注册后，Oceanus Manager会在约10秒内感知到这个变化并更新Nginx配置——不需要reload，不需要你做任何操作。

至此，域名到服务的映射链路就建好了。我们把整条链路画出来：

```
用户输入 order.sankuai.com
    │
    ▼
DNS解析: order.sankuai.com → CNAME → MGW VIP (103.37.142.166)
    │
    ▼
MGW四层负载: VIP 103.37.142.166:443 → 转发给 Oceanus集群节点列表
    │
    ▼
Oceanus七层网关: 
    1. 收到HTTP请求，读取Host头 → "order.sankuai.com"
    2. 匹配站点配置 → 后端AppKey = com.sankuai.daodian.orderservice
    3. 向OCTO查询该AppKey的实例列表 → [10.65.12.34:8080, 10.65.12.35:8080, ...]
    4. 加权轮询选择一个实例 → 10.65.12.34:8080
    5. 转发HTTP请求到 10.65.12.34:8080
    │
    ▼
OrderService 实例 (10.65.12.34:8080) 处理请求，返回响应
```

这就是你的服务"部署上去之后通过域名就能访问"的完整答案。每一个环节都有对应的平台和配置，不是魔法，是配置。

### 11.4 第三步：映射关系全景——域名、站点、AppKey、实例之间到底是什么关系

你可能会问："美团有那么多域名、那么多服务，它们之间的映射关系是怎么管理的？会不会乱？"答案是：每一层都有明确的映射关系，层层递进，不会乱。

```
域名                Oceanus站点            AppKey                    实例
───────────────    ──────────────    ──────────────────────    ──────────────────
order.sankuai.com  → 站点#9588       → com.sankuai.daodian     → 10.65.12.34:8080
                     后端AppKey=       .orderservice              10.65.12.35:8080
                     com.sankuai.                                10.65.12.36:8080
                     daodian.
                     orderservice
```

映射关系的本质是四层一对一（或一对多）的关联：

**第一层：域名 → Oceanus站点**。一个域名对应一个Oceanus站点配置。但一个站点也可以配置多个域名（比如 `order.sankuai.com` 和 `order.dianping.com` 都指向同一个站点）。域名在Domain系统注册，站点在Oceanus管理平台配置。

**第二层：Oceanus站点 → AppKey**。一个站点配置中指定后端服务的AppKey。Oceanus通过这个AppKey向OCTO查询实例列表。一个站点只对应一个AppKey，但一个AppKey可以被多个站点引用（比如一个内网站点一个外网站点都指向同一个服务）。

**第三层：AppKey → 实例列表**。一个AppKey对应一组运行中的服务实例（IP:Port）。这个映射关系是动态的——服务扩容时新增实例自动注册，缩容或故障时实例自动摘除。OCTO的MNS注册中心实时维护这个映射。

如果后端是RPC服务而不是HTTP服务，用户不能直接通过域名访问——需要通过Shepherd API网关做协议转换。这时候映射关系多了一层：

```
域名                Shepherd API          AppKey                    实例
───────────────    ──────────────    ──────────────────────    ──────────────────
api.sankuai.com    → API: /orders     → com.sankuai.daodian     → 10.65.12.34:8080
  /orders/create      create             .orderservice              10.65.12.35:8080
                      invoker.appkey=
                      com.sankuai.
                      daodian.
                      orderservice
                      invoker.method=
                      createOrder
```

Shepherd的映射更细：域名+路径 → API配置 → 后端AppKey+方法名 → RPC泛化调用。一个域名下可以配置多个API（多个路径），每个API可以指向不同的后端AppKey和不同的方法。

```
api.sankuai.com/orders/create  → AppKey: orderservice, Method: createOrder
api.sankuai.com/orders/query   → AppKey: orderservice, Method: queryOrder
api.sankuai.com/shop/info      → AppKey: shopservice,   Method: getShopInfo
```

这就是为什么"Shepherd是API接口层的精细管理者"——它能在同一个域名下，按路径把不同的API路由到不同的后端服务和不同的方法。

### 11.5 第四步：线上正常请求的完整链路

现在你的三个服务都在线上正常跑了。用户在App上点击"下单"，我们来看这个请求从发起到返回的完整旅程，每一步都不跳。

**第1步：App发起HTTP请求。**

用户App发出一个HTTPS请求：

```
POST https://order.sankuai.com/api/order/create
Headers:
  Content-Type: application/json
  User-Agent: 美团App/8.0
Body:
  {"shopId": 12345, "userId": 67890, "items": [...]}
```

**第2步：DNS解析。**

App的DNS解析器查询 `order.sankuai.com`。公网DNS返回CNAME链路，最终拿到MGW的VIP地址 `103.37.142.166`。

**第3步：TCP连接到MGW。**

App与 `103.37.142.166:443` 建立TCP连接和TLS握手。MGW在TCP层面接收这个连接。MGW通过TOA（TCP Option Address）模块在TCP Options中记录了用户的真实IP，后面传给Oceanus时Oceanus能拿到真实客户端IP。

**第4步：MGW转发给Oceanus。**

MGW根据自己的VS配置，把这个TCP连接转发给后端的某个Oceanus节点（比如 `10.23.184.29:80`）。MGW做这一步时不关心HTTP内容，只看TCP连接。如果这个Oceanus节点健康检查失败了，MGW会自动选择另一个Oceanus节点。

**第5步：Oceanus处理HTTP请求。**

Oceanus节点 `10.23.184.29` 收到HTTP请求后，执行以下处理链：

（a）**TLS卸载**：如果请求是HTTPS，Oceanus在这里完成TLS解密。SSL证书是在Oceanus站点配置中上传的，Oceanus统一管理所有域名的证书。

（b）**安全组件检查**：WAF（Web Application Firewall）检查请求是否有SQL注入、XSS等攻击特征。如果有，返回HTTP 456。MTSI反扒组件检查是否是爬虫。如果是，返回HTTP 403。

（c）**路由匹配**：Oceanus读取HTTP请求的Host头 `order.sankuai.com`，在内存中的站点配置表里查找。找到了——这个域名对应站点#9588，后端AppKey是 `com.sankuai.daodian.orderservice`。

（d）**灰度判断**：Oceanus调用大禹（大禹）规则引擎，检查当前请求是否命中任何灰度规则。假设目前没有灰度，跳过。

（e）**服务发现**：Oceanus Manager已经从OCTO的MNS注册中心获取并缓存了 `com.sankuai.daodian.orderservice` 的实例列表。当前有三个健康实例：

```
10.65.12.34:8080  权重=100  机房=永丰
10.65.12.35:8080  权重=100  机房=永丰
10.66.20.11:8080  权重=100  机房=光环
```

（f）**负载均衡**：根据配置的"同机房优先"策略，当前Oceanus节点在永丰机房，所以优先从永丰机房的实例中选。加权轮询选中了 `10.65.12.34:8080`。

（g）**限流检查**：检查 `com.sankuai.daodian.orderservice` 的请求是否超过限流阈值。假设没有，放行。

（h）**注入追踪标识**：Oceanus生成一个TraceId（如 `trace-abc123`），注入到请求头中。同时记录请求开始时间。

（i）**转发请求**：将HTTP请求转发到 `10.65.12.34:8080`。

**第6步：OrderService处理请求。**

OrderService实例 `10.65.12.34:8080` 收到请求。它需要执行以下业务逻辑：

（a）解析请求参数，创建订单对象。

（b）**调用ShopService查门店信息**：OrderService通过Pigeon RPC框架发起对 `com.sankuai.daodian.shopservice` 的调用。Pigeon的内部流程是：Pigeon SDK向本机的sg_agent查询 `com.sankuai.daodian.shopservice` 的实例列表，sg_agent返回当前可用的实例 `[10.65.20.33:8080, 10.65.20.34:8080]`，Pigeon根据OCTO路由规则选择实例（同机房优先 → 选中 `10.65.20.33:8080`），Pigeon建立RPC连接发送MTThrift协议请求并自动透传TraceId，ShopService处理完返回门店信息。

（c）**调用StockService扣库存**：同样的Pigeon RPC流程，调用 `com.sankuai.daodian.stockservice`。

（d）**写入数据库**：通过Zebra数据库中间件写入订单数据。Zebra决定写入主库还是从库、写入哪个分片。

（e）**写入缓存**：通过Squirrel缓存服务缓存订单信息。

（f）**发送消息**：通过Mafka消息队列发送"订单创建成功"消息。StockService作为消费者会异步消费这条消息做库存扣减。

（g）返回HTTP响应给Oceanus，Oceanus再返回给MGW，MGW再返回给App。用户看到"下单成功"。

**第7步：链路追踪记录。**

整个过程被Mtrace记录下来。通过TraceId `trace-abc123`，你在Mtrace控制台上能看到完整的调用链：

```
App → Oceanus(10.23.184.29) → OrderService(10.65.12.34)
                                ├→ ShopService(10.65.20.33)    15ms
                                ├→ StockService(10.65.20.55)   22ms
                                ├→ Zebra(DB写入)                35ms
                                ├→ Squirrel(缓存写入)            3ms
                                └→ Mafka(消息发送)               2ms
                              总耗时: 120ms
```

这就是线上正常请求的完整旅程。每一步都有明确的路由决策，每一步都有对应的平台和配置支撑。

### 11.6 第五步：线下测试——建泳道

现在你要开发一个新功能：OrderService新增"预约到店"接口，ShopService新增"查询可预约时段"接口。两个服务都有改动，你需要在测试环境联调。

如果直接在主干（baseline）上测，其他同事也在主干上测他们的功能，互相会干扰。所以你需要建一条泳道。

**第1步：在Cargo平台创建泳道。**

你登录Cargo平台，创建一条新泳道，命名为 `lane-reserve-zhh`。Cargo做了以下几件事：在OCTO注册了一组路由规则——当请求头中携带 `x-gray-lane: lane-reserve-zhh` 时，对OrderService和ShopService优先路由到泳道实例。在Mafka中配置了消息隔离策略。在Lion中创建了泳道级别的配置副本。

**第2步：在Cargo上部署服务到泳道。**

你选择OrderService和ShopService的最新构建产物，点击"部署到泳道"。Cargo调用Avatar在测试集群中拉起这两个服务的新版本实例，并为实例打上标签 `lane=lane-reserve-zhh`。

部署完成后，OCTO的注册表中就有了每个服务的两组实例：

```
com.sankuai.daodian.orderservice:
  - 10.65.12.34:8080  lane=baseline（主干，旧版本）
  - 10.65.12.35:8080  lane=baseline（主干，旧版本）
  - 10.65.90.21:8080  lane=lane-reserve-zhh（泳道，新版本）← 新部署的

com.sankuai.daodian.shopservice:
  - 10.65.20.33:8080  lane=baseline（主干，旧版本）
  - 10.65.90.22:8080  lane=lane-reserve-zhh（泳道，新版本）← 新部署的

com.sankuai.daodian.stockservice:
  - 10.65.20.55:8080  lane=baseline（主干，旧版本）
  （泳道中没有部署，因为StockService这次没改动）
```

**第3步：发起测试请求。**

你在测试工具中发起请求，需要携带特殊的Header才能进入泳道。你可以通过Cargo平台的"流量入口"功能自动注入，或者手动添加：

```

**第4步：测试请求在泳道中的路由过程。**

请求到达Oceanus后，Oceanus识别到 `x-gray-lane: lane-reserve-zhh` 这个Header（线下环境的Oceanus不会清洗这个Header，因为这是内部测试入口）。Oceanus在查询OCTO时，告诉OCTO"这个请求的泳道标记是 `lane-reserve-zhh`"。

OCTO收到查询后，按照泳道路由规则处理：

```

OCTO: 该AppKey有 lane-reserve-zhh 的实例吗？
      → 有！10.65.90.21:8080
      → 路由到 10.65.90.21:8080（泳道中的新版本）
```

请求到达OrderService新版本实例。它内部调用ShopService时，Pigeon SDK自动把 `x-gray-lane: lane-reserve-zhh` 这个Header复制到RPC调用的上下文里。OCTO收到ShopService的实例查询请求时：

```
查询: com.sankuai.daodian.shopservice, lane=lane-reserve-zhh
OCTO: 该AppKey有 lane-reserve-zhh 的实例吗？
      → 有！10.65.90.22:8080
      → 路由到 10.65.90.22:8080（泳道中的新版本）
```

ShopService新版本处理完返回结果。如果OrderService还需要调用StockService呢？

```
查询: com.sankuai.daodian.stockservice, lane=lane-reserve-zhh
OCTO: 该AppKey有 lane-reserve-zhh 的实例吗？
      → 没有！泳道中没有部署StockService
      → 按照泳道路由规则：服务不存在 → fallback到主干

StockService在主干上的旧版本处理请求——这没问题，因为StockService这次没有改动，旧版本完全能正常工作。

**第5步：测试完毕，销毁泳道。**

测试通过后，你在Cargo上点击"销毁泳道"。Cargo销毁泳道中的实例，移除OCTO路由规则，清理Mafka和Lion的隔离配置。测试资源释放，主干不受任何影响。

**第1步：部署灰度实例。**

    6. 该AppKey有 gray-canary 标签的实例吗？
       → 有！10.65.90.31:8080

    7. 处理请求，需要调用ShopService

**第4步：灰度期间出问题怎么办。**

假设Raptor监控发现灰度实例的错误率从0.1%上升到2%。你在Mtrace上按 `gray.lane=gray-canary` 过滤，定位到是ShopService新接口在某个边界条件下抛了空指针。

你在DevTools/Plus上点击"一键回滚"。大禹立即摘除灰度入口规则——从这一秒起，Oceanus不再对任何新请求注入灰度Header。所有新请求都走主干。正在灰度实例中处理的请求会等待优雅退出（通常30秒）。灰度实例保留但不再接收流量，方便事后排查。

整个过程对用户的影响：那5%的灰度用户下一次请求自动走主干稳定版本。回滚速度在秒级到十几秒之间完成。

### 11.9 几个容易困惑的问题

**Q: 我的HTTP服务直接注册到Oceanus就行了吗？为什么有的服务还要走Shepherd？**

如果你的服务本身就是HTTP服务（比如一个Spring Boot应用暴露了HTTP接口），用户通过域名直接访问，那在Oceanus上配一个站点指向你的AppKey就行了。Oceanus做反向代理，把HTTP请求直接转发给你的服务实例。

但如果你需要更精细的能力——比如把HTTP请求转换成MTThrift RPC调用（你的后端是RPC服务不是HTTP服务）、需要API级别的鉴权（不同API用不同鉴权方式）、需要API文档自动生成、需要服务编排（一个HTTP请求聚合多个RPC调用的结果），那就需要走Shepherd。Shepherd接在Oceanus后面，Oceanus把流量转给Shepherd，Shepherd做协议转换后再调你的RPC服务。

**Q: 域名是按什么规则分配的？我组的域名是谁决定的？**

域名是业务团队自己申请的。你在Domain系统上申请域名，填写域名名称和解析目标。公网域名（`*.sankuai.com`、`*.dianping.com`）需要安全审核——必须开启强制HTTPS并接入WAF。内网域名（`*.sankuai.com`）相对宽松一些。域名命名通常遵循团队或业务线的约定，比如到店业务用 `daodian.internal.sankuai.com`，外卖用 `wm.internal.sankuai.com` 等。

**Q: Oceanus怎么知道我的服务有哪些实例？是我在Oceanus上配置的吗？**

不是你在Oceanus上手动配置的。Oceanus Manager会自动从OCTO的MNS注册中心订阅你的AppKey对应的实例列表变化。你在DevTools上部署服务、服务启动后自动向OCTO注册，Oceanus Manager约10秒内就能感知到新实例并通过dyups更新到Nginx内存里。你不需要在Oceanus上手动维护IP列表——你只需要在Oceanus上创建站点时填写AppKey，剩下的实例发现是自动的。

**Q: 一个域名只能对应一个服务吗？**

不是。通过Oceanus的精细化分流，一个域名可以根据路径、Header、Cookie等维度把流量分发到不同的后端服务。比如 `api.sankuai.com/orders/*` 转发给OrderService，`api.sankuai.com/shop/*` 转发给ShopService。这就像Nginx的location配置一样，但Oceanus做了更高级的动态化和管理界面化。

**Q: 线上灰度和线下泳道到底有什么区别？**

线下泳道（Cargo管理）：在测试环境做的，跑的是人工构造的测试流量，不影响真实用户。隔离粒度是服务实例级别的，但共用DB和MQ（测试环境的DB和MQ）。

线上灰度（DevTools+大禹管理）：在生产环境做的，跑的是真实用户流量的一小部分。隔离粒度更细——不仅服务实例隔离，限流桶、熔断窗口都按泳道独立建桶。DB通常不隔离（因为灰度写入的是真实业务数据），但会在数据记录中打灰度标记方便追溯。

底层机制是一样的——都是标签路由，都是流量染色+Header透传。区别在于场景（测试vs生产）、管理平台（Cargo vs DevTools）、和隔离严格度。

**Q: 为什么我ping一个域名能通但服务访问不了？**

因为ping用的是ICMP协议，走的是网络层（三层），而你的服务用的是TCP协议走传输层（四层）。防火墙控制的是TCP端口级别的连通性，不管ICMP。所以ping能通不代表你的TCP连接能建立。正确的测试方式是 `telnet 目标IP 端口` 或 `curl -v 域名`。

### 11.10 一句话总结

你的服务部署上去之后能通过域名访问，是因为有人（可能是你组里的前辈或SRE）在五个平台上做了配置：Domain系统配了域名解析指向MGW VIP，MGW管理平台配了VIP到Oceanus的转发，Oceanus管理平台配了站点（域名→AppKey的映射），OCTO注册中心自动维护着AppKey→实例列表的映射，DevTools部署服务时服务自动向OCTO注册。这五层配置串联起来，就形成了一条从域名到服务实例的完整路由链路。泳道和灰度则是通过在这条链路上叠加"流量染色→标签匹配→按标记路由"的机制，实现了流量的精细化分配和隔离。

不是魔法，是配置。一层一层拆开看，每一步都很清楚。

## 十二、成千上万的域名是怎么管清楚的：域名体系与路由映射全景

上一节我们用一个三个服务的例子走了一遍流程。但你可能还有一个更大的困惑：美团内部有成千上万个域名，线上不同组有不同域名，线下不同组也有不同域名，这些域名最终都要经过网关，那"域名→集群→站点→服务"的映射关系到底是怎么管清楚的？谁决定域名叫什么？域名解析怎么配？线下和线上的域名规则有什么不同？一个域名下面多个路径多个服务是怎么路由的？

这一节我们从学城文档中整理出来的资料，把域名体系从顶层规范到具体落地彻底讲清楚。

### 12.1 域名的命名规范：域名不是随便取的

美团的域名不是你想叫什么就叫什么，有一套明确的命名规范。这套规范区分了生产环境和非生产环境，区分了内网和外网，区分了不同业务线（OWT）。

#### 12.1.1 基本命名格式

```
生产环境:
  内网域名:  {name}.{公司内网域}         例: order.vip.sankuai.com
  外网域名:  {name}.{公司外网域}         例: order.sankuai.com

非生产环境:
  内网域名:  {name}.{owt}.{env}.{公司内网域}    例: order.inf.test.sankuai.com
  外网域名:  {name}.{env}.{公司外网域}           例: order.test.sankuai.com
```

这里的字段含义：

name 是域名名称，一级不含点号，比如 Oceanus、e、api、crm、wmapi、order 等。这是你的服务或站点在域名层面的标识。

owt 是业务线名称（Organization of Technology），比如 inf（基础架构）、waimai（外卖）、pay（支付）、hotel（酒店）、ee（到店）、sjst（数据建设）等。美团内部有上百个OWT，每个业务线有自己的OWT标识。这个标识决定了线下环境域名会解析到哪个Nginx集群。

env 是环境标识，非生产环境使用，包括 st（预发）、test（测试）、dev（开发）、isolt（演练隔离）。

公司域 是公司公共域或业务域后缀，主要包括：

```
sankuai.com     国内外网域（公网可访问）
sankuai.com     国内内网域（仅内网可访问）
maoyan.com      猫眼业务域
dianping.com    点评业务域
zservery.com    特定业务域
mykeeta.com     香港域名
isoldeploy.com  PaaS海外测试域（仅test）
mtoversea.com   PaaS海外非敏感区正式域
```

#### 12.1.2 为什么要有这套规范

你可能会问"为什么搞这么复杂"，原因有三个：

第一，环境隔离。线上域名 `order.sankuai.com` 和线下域名 `order.inf.test.sankuai.com` 从命名上就能区分是哪个环境的，不会搞混。DNS解析也是隔离的——线上域名解析到线上MGW集群，线下域名解析到线下Nginx集群。

第二，集群自动匹配。线下环境的域名采用泛域名解析 `*.{owt}.{env}.sankuai.com`，系统会根据域名中的OWT标识自动选择对应的Nginx集群。比如 `order.inf.test.sankuai.com` 中的 `inf` 标识会让系统自动选择 `ng-inf-offlinebeijing` 集群。你不需要手动指定集群，系统帮你匹配。

第三，安全管控。公网域名（`*.sankuai.com`）必须强制HTTPS并接入WAF，内网域名（`*.sankuai.com`）相对宽松。域名命名规范让安全团队能通过域名后缀判断内外网，实施不同的安全策略。

### 12.2 域名管理的参与方和流程

域名管理不是一个人或一个团队能搞定的，涉及多个团队的协作。下面是域名从申请到使用的完整流程和各方分工：

```
环节                    对接人/团队              做什么
─────────────          ──────────────          ──────────────
1.域名注册(购买/续费)    合规管理组              业务在Domain系统发起购买需求，
                                               合规组承担成本并统一注册管理

2.网站备案              合规管理组              备案通过前网站不得开通访问

3.DNS解析托管           中间件SRE组             通过Domain系统添加解析，
                                               系统自动同步到DNSPod和内部DNS

4.域名证书管理          中间件SRE组             SSL证书的购买、续期、部署,
                                               Oceanus站点创建时自动匹配证书

5.Oceanus站点创建       业务RD或SRE             在Oceanus管理平台创建站点,
                                               配置域名→AppKey的映射关系

6.域名解析配置(线上)     业务SRE                在Domain系统配置域名CNAME指向
                                               对应的MGW VIP/Oceanus集群

7.域名解析配置(线下)     系统自动               线下采用泛域名解析,系统自动匹配
```

关键理解：域名注册（买域名）和域名解析配置（让域名指向服务器）是两个不同的环节。注册是在合规组统一管理下购买域名名称；解析是在Domain系统上配置域名指向哪个IP或CNAME。

### 12.3 线下环境的域名体系：泛域名解析是核心

线下环境（test/dev/st）的域名管理方式和线上完全不同，理解泛域名解析是关键。

#### 12.3.1 什么是泛域名解析

泛域名解析就是用一条 `*.{owt}.{env}.sankuai.com` 的DNS记录，匹配该模式下的所有域名。比如：

```
DNS记录: *.inf.test.sankuai.com → CNAME → hlb.test.sankuai.com

这意味着以下域名全部解析到同一个CNAME:
  order.inf.test.sankuai.com     ✓ 匹配
  api.inf.test.sankuai.com       ✓ 匹配
  myservice.inf.test.sankuai.com ✓ 匹配
  anything.inf.test.sankuai.com  ✓ 匹配
```

你不需要为每个域名单独配置DNS解析——只要你的域名符合 `{name}.{owt}.test.sankuai.com` 的格式，DNS就会自动解析到对应的Nginx集群。这就是为什么线下环境你只要在Oceanus上创建站点填个域名，就能直接访问——DNS解析是泛域名自动搞定的。

#### 12.3.2 OWT到集群的映射关系

线下test环境，系统会根据域名中的OWT标识，通过Lion配置中的 `owtToNgx` 映射表自动选择Nginx集群。这个映射表很长，这里列出部分典型映射：

```
owt标识        →  Nginx集群名称
────────       ─  ──────────────────────
inf            →  ng-inf-ep              (基础架构-线上入口)
hotel          →  ng-hotel-ep            (酒店)
waimai         →  ng-waimai-ep           (外卖)
ee             →  ng-inf-ep              (到店)
it             →  ng-inf-ep              (IT)
fe             →  ng-wpt-ep              (前端)
cap            →  ng-inf-ep              (客服)
xm             →  ng-inf-ep              (大象)
dzu            →  ng-inf-offlineshanghai (到店综合-上海)
dc             →  ng-inf-offlineshanghai (到店-上海)
ad             →  ng-inf-offlineshanghai (广告-上海)
hotel          →  ng-hotel-ep            (酒店)
mykeeta        →  ng-waimai-ep           (Keeta)
...            →  ...
```

大部分OWT的线下流量都打到 `ng-inf-offlinebeijing`（北京线下通用集群），少数有独立集群的（如hotel、waimai、fe、cap）会打到各自的专用集群。

这意味着：线下环境，你只要按规范取个域名比如 `myservice.inf.test.sankuai.com`，系统自动帮你完成DNS解析和集群匹配，你只需要在Oceanus上创建站点配置好后端AppKey就能访问。整个流程5分钟搞定。

#### 12.3.3 线下各环境的域名格式

```
test环境:
  内网:  {name}.{owt}.test.sankuai.com       泛域名解析: *.inf.test.sankuai.com
  内网:  {name}.{owt}.isolt.sankuai.com      演练隔离环境
  外网:  {name}.test.sankuai.com              线下外网（Avatar管理，强制HTTPS）

dev环境:
  内网:  {name}.{owt}.dev.sankuai.com        泛域名解析: *.inf.dev.sankuai.com
  外网:  {name}.dev.sankuai.com

st环境（预发）:
  内网:  {name}.{owt}.st.sankuai.com         泛域名解析: *.inf.st.sankuai.com
  外网:  {name}.st.sankuai.com
```

线下环境的HTTPS配置无限制（可以选仅HTTP），因为线下不需要安全审核。线下外网域名（`*.test.sankuai.com`）则需要强制HTTPS。

#### 12.3.4 泳道域名

线下环境创建泳道时，泳道域名是在基础域名前加泳道前缀。比如基础域名是 `order.inf.test.sankuai.com`，泳道 `lane-zhh` 的域名可能是 `lane-zhh-order.inf.test.sankuai.com`。Oceanus基于泳道域名前缀或HTTP请求头进行流量转发。

泳道域名有一个限制：不能包含 `-sl-`（这是Set-Lite的保留标识）。

### 12.4 线上环境的域名体系：手动配置与自动配置结合

线上环境的域名管理比线下严格得多，不再使用泛域名解析，每个域名都需要明确的DNS解析配置。

#### 12.4.1 线上内网域名

线上内网域名格式：`{name}.sankuai.com` 或 `{name}.vip.sankuai.com`。

限制条件：只能使用 `sankuai.com`、`vip.sankuai.com`、`shanshan666.com` 作为域名后缀。不能使用 `st.sankuai.com`、`dev.sankuai.com`、`test.sankuai.com`、`51ping.com`、`st.sankuai.com`、`dev.sankuai.com`、`test.sankuai.com`（这些是环境域名，不能用于线上）。

在Oceanus上创建线上站点时，如果域名还没有DNS解析，系统会根据你选择的集群自动配置解析：从Ark集群管理平台获取该集群的CNAME → 从Domain系统获取CNAME对应的线路 → 添加域名解析记录。如果域名已有解析记录，系统不会覆盖，会显示当前的解析情况。

#### 12.4.2 线上外网域名

线上外网域名格式：`{name}.sankuai.com`（或 `dianping.com` 等业务域）。

限制条件：强制HTTPS，必须接入WAF。不能使用 `vip.sankuai.com`（内网域名后缀）。安全部门要求公网域名必须开启强制HTTPS。

外网域名解析指向公网MGW集群的VIP。MGW通过Anycast机制在北上PoP点之间做容灾。

#### 12.4.3 线上线下的关键区别总结

```
维度              线下环境                           线上环境
────────         ──────────                        ──────────
DNS解析          泛域名解析(自动)                    逐域名配置(手动或半自动)
域名格式          {name}.{owt}.{env}.sankuai.com    {name}.sankuai.com / {name}.sankuai.com
集群选择          根据OWT自动匹配                     手动选择
HTTPS            无限制(可仅HTTP)                   强制HTTPS(外网)
安全审核          不需要                             需要(外网域名)
域名证书          无限制                             必须匹配SSL证书
管理平台          Oceanus直接操作                     线上在Avatar操作(迁移中),部分在Oceanus
```

### 12.5 Oceanus站点的内部结构：站点、域名、映射规则的层级关系

现在来回答最核心的问题：那么多的域名和服务，在Oceanus内部是怎么组织的？答案是一个三层结构：站点→域名→映射规则。

#### 12.5.1 站点（Site）：一份Nginx server配置

站点是Oceanus中承载一份负载均衡配置的最小单位，对应Nginx配置中的 `server` 块。一个站点包含以下资源：

域名列表（可以多个域名共享同一份配置）、SSL证书、映射规则列表（关联后端服务）、全局规则（server级别的配置）、流量调度策略等。

关键理解：站点和域名是两个不同的概念。一个站点可以对应多个域名，这些域名共享同一份负载均衡配置。比如 `order.sankuai.com` 和 `order.dianping.com` 可以属于同一个站点，它们的请求会被同样的映射规则处理。反过来，多个服务也可以通过不同的映射规则在同一个站点内对外提供服务。

Oceanus目前管理着各环境共26000+站点（线上7764个），2600+HTTP服务（线上8725个）。

#### 12.5.2 域名（Domain）：站点的访问入口

域名对应Nginx配置中的 `server_name` 部分。当HTTP请求到达Oceanus时，Oceanus通过读取请求的Host头来匹配站点的域名列表，找到对应的站点配置。

在Oceanus上创建站点时需要设置一个初始域名，这个域名同时作为站点的名称。后续可以为站点添加更多域名。域名本身的DNS解析管理是在Domain系统中完成的（不是在Oceanus中），但Oceanus在创建线上站点时会自动帮你在Domain系统配置解析。

#### 12.5.3 映射规则（Mapping Rule）：路径到服务的路由

映射规则又称为路由规则或location，是基于Nginx原生的 `location` 指令提供的请求分发方式。映射规则的核心属性是路径（path），它决定了请求由哪个后端服务处理。

一个站点下可以有多个映射规则，每个映射规则关联一个后端AppKey。比如：

```
站点: api.sankuai.com
  ├── 映射规则1: /orders/create  → AppKey: com.sankuai.orderservice
  ├── 映射规则2: /orders/query   → AppKey: com.sankuai.orderservice
  ├── 映射规则3: /shop/info      → AppKey: com.sankuai.shopservice
  └── 映射规则4: /stock/check    → AppKey: com.sankuai.stockservice
```

这就是"一个域名下面多个路径路由到不同服务"的实现方式。映射规则的路径匹配遵循Nginx的location匹配规则（精确匹配、前缀匹配、正则匹配等），多个规则之间的匹配顺序需要注意截流问题。

映射规则的添加类型有三种：关联后端AppKey（在OCTO注册了HTTP节点的后端服务）、关联前端AppKey（在Camel注册的前端服务，用于静态页面托管）、自定义Return（自行编写返回值）。

#### 12.5.4 完整的Nginx配置对应关系

把Oceanus的概念和Nginx配置对应起来看就更清楚了：

```nginx
# Oceanus站点 → Nginx server块
server {
    listen 443 ssl http2;
    
    # Oceanus域名 → Nginx server_name
    server_name api.sankuai.com;
    
    # Oceanus证书 → Nginx ssl_certificate
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    
    # Oceanus全局规则 → server块级别的配置
    client_max_body_size 20m;
    waf on;
    
    # Oceanus映射规则1 → Nginx location块
    location /orders/create {
        proxy_pass http://com.sankuai.orderservice;
        # 映射规则指令
        proxy_set_header X-Real-IP $remote_addr;
    }
    
    # Oceanus映射规则2 → Nginx location块
    location /shop/info {
        proxy_pass http://com.sankuai.shopservice;
    }
    
    # Oceanus映射规则3 → Nginx location块
    location /stock/check {
        proxy_pass http://com.sankuai.stockservice;
    }
}

# Oceanus的upstream（由dyups动态管理，不在静态配置中）
# upstream com.sankuai.orderservice {
#     server 10.65.12.34:8080 weight=100;
#     server 10.65.12.35:8080 weight=100;
# }
```

每一个Oceanus概念都能在Nginx配置中找到对应。Oceanus做的事情本质上就是把Nginx的静态配置文件管理做成了一个可视化平台，加上了动态upstream、审批流程、灰度发布、监控告警等企业级能力。

### 12.6 流量调度策略：比映射规则更精细的分流

映射规则解决的是"路径→服务"的路由问题。但有些场景需要更精细的分流——同一个路径下的请求，根据请求头、Cookie、URI参数等条件分流到不同的后端。这就是流量调度策略。

#### 12.6.1 流量调度策略是什么

流量调度策略是Oceanus基于HTTP请求特征进行分流的功能。它关联到特定的域名和路径（映射规则）后，可以使满足特定条件的请求走与默认规则不同的处理逻辑。

比如你的站点 `api.sankuai.com/orders/*` 默认路由到OrderService的v1版本，但你想让带有特定Header的请求路由到v2版本（灰度实例），就可以用流量调度策略：

```
映射规则: /orders/* → 默认 → OrderService (baseline实例)
流量调度策略: 
  条件: Header[x-gray-lane] = gray-canary
  命中时 → OrderService (gray-canary实例)
```

流量调度策略支持的条件类型包括：Header（请求头）、Args/Query（URL参数）、Cookie。可以按条件分流（等于某个值）、按比例分流（hash取模）、直接分流（取值直接作为标签）。

#### 12.6.2 流量调度策略与映射规则的关系

流量调度策略是绑定在映射规则上的，不是独立的。一个映射规则可以关联一个流量调度策略，流量调度策略中的分流条件优先于映射规则的默认转发逻辑。

```
请求: GET /orders/create
  │
  ├── 匹配到映射规则: /orders/*  → 默认AppKey: orderservice
  │
  ├── 检查该映射规则是否关联了流量调度策略?
  │   ├── 是 → 检查请求是否命中分流条件
  │   │   ├── 命中 → 按分流策略路由(如走gray-canary实例)
  │   │   └── 未命中 → 按默认规则路由(baseline实例)
  │   └── 否 → 按默认规则路由
  │
  └── 转发到对应的OrderService实例
```

#### 12.6.3 流量调度策略支持的分流类型

流量调度策略中可以配置LiteSET分流和SET分流：

**LiteSET分流**：基于LiteSET标签做流量隔离，适用于灰度发布和AB Test。分流命中后请求被路由到指定LiteSET的实例。

**SET分流**：基于SET做流量隔离，适用于外卖、配送、金融等SET化业务。普通业务不需要关注。

**业务分组（GroupTags）**：在SET/LiteSET基础上新增的二级隔离能力，实现线上二级（SET/业务分组）、线下三级（SET/业务分组/泳道）隔离。

### 12.7 域名与集群的映射关系：DNS解析决定流量去向

这是一个容易混淆但非常关键的概念：域名解析决定流量打到哪个Nginx集群，Oceanus站点配置决定流量打到哪个后端服务。两者必须一致，否则请求会出错。

#### 12.7.1 两层配置的职责划分

```
Domain系统（DNS解析）:
  域名 → CNAME → Nginx集群
  职责: 决定流量打到哪个Nginx集群(物理位置)

Oceanus系统（站点配置）:
  域名 → 映射规则 → 后端AppKey
  职责: 决定流量打到哪个后端服务(逻辑路由)
```

这两层配置是独立的，但必须匹配。如果DNS解析把域名指向集群A，但Oceanus站点配置在集群B上，那么请求到达集群A的Nginx后，Nginx上没有这个站点的配置，就会返回错误。

#### 12.7.2 线下环境：自动匹配不会出问题

线下环境因为使用泛域名解析，系统根据域名中的OWT自动选择集群，同时在Oceanus创建站点时也是根据OWT自动匹配同一个集群。所以线下基本不会出现"域名解析的集群和站点配置的集群不一致"的问题。

#### 12.7.3 线上环境：需要手动确保一致

线上环境，域名解析由SRE在Domain系统配置，站点集群由RD或SRE在Oceanus选择。如果两边配置不一致就会出问题。

Oceanus在创建线上站点时已经做了自动化：如果你选了一个集群，系统会自动在Domain系统配置域名解析指向这个集群。但如果你后来在Domain系统手动修改了解析指向另一个集群，而Oceanus站点配置没有同步修改，就会出现"域名解析到集群A但站点配置在集群B"的不一致问题。

Oceanus平台提供了集群一致性检查功能，在站点域名页面会显示域名当前解析到的集群和站点绑定的集群是否一致。如果不一致会提示修复。

### 12.8 多个域名多个服务的全景示例

最后，我们用一个更完整的例子，展示多个团队、多个域名、多个服务在美团网关体系中是如何共存的。

假设有三个团队，各自有多个服务：

```
到店订单组 (OWT=ee):
  OrderService    AppKey: com.sankuai.ee.orderservice
  ShopService     AppKey: com.sankuai.ee.shopservice

外卖组 (OWT=waimai):
  WmOrderService  AppKey: com.sankuai.waimai.wmorderservice
  WmDeliveryService AppKey: com.sankuai.waimai.wmdelivery

酒店组 (OWT=hotel):
  HotelService    AppKey: com.sankuai.hotel.hotelservice
```

#### 线下环境：

```
Domain系统泛域名解析:
  *.ee.test.sankuai.com     → hlb.test.sankuai.com → ng-inf-ep集群
  *.waimai.test.sankuai.com → hlb.test.sankuai.com → ng-waimai-ep集群
  *.hotel.test.sankuai.com  → hlb.test.sankuai.com → ng-hotel-ep集群

Oceanus站点配置:
  站点1: order.ee.test.sankuai.com
    映射规则: /  → com.sankuai.ee.orderservice
  
  站点2: shop.ee.test.sankuai.com
    映射规则: /  → com.sankuai.ee.shopservice
  
  站点3: wmorder.waimai.test.sankuai.com
    映射规则: /  → com.sankuai.waimai.wmorderservice
  
  站点4: wmdelivery.waimai.test.sankuai.com
    映射规则: /  → com.sankuai.waimai.wmdelivery
  
  站点5: hotel.hotel.test.sankuai.com
    映射规则: /  → com.sankuai.hotel.hotelservice
    映射规则: /api/search → com.sankuai.hotel.hotelservice (Method: searchHotel)
    映射规则: /api/book   → com.sankuai.hotel.hotelservice (Method: bookHotel)
```

每个团队按规范取域名，DNS自动解析，Oceanus上配好站点和映射规则就能访问。不同OWT的流量自动路由到不同的Nginx集群，互不干扰。

#### 线上环境：

```
Domain系统逐域名配置:
  order.sankuai.com     → CNAME → mgw-prod.sankuai.com → 公网MGW VIP → Oceanus集群A
  shop.sankuai.com      → CNAME → mgw-prod.sankuai.com → 公网MGW VIP → Oceanus集群A
  wmorder.sankuai.com   → CNAME → mgw-prod.sankuai.com → 公网MGW VIP → Oceanus集群B
  hotel.sankuai.com     → CNAME → mgw-prod.sankuai.com → 公网MGW VIP → Oceanus集群C
  
  order.vip.sankuai.com → CNAME → hlb.prod.sankuai.com → 内网MGW VIP → Oceanus集群A
  hotel.vip.sankuai.com → CNAME → hlb.prod.sankuai.com → 内网MGW VIP → Oceanus集群C

Oceanus站点配置:
  站点#100: order.sankuai.com (外网)
    域名: order.sankuai.com, order.dianping.com
    HTTPS: 强制HTTPS
    映射规则: / → com.sankuai.ee.orderservice
  
  站点#101: order.vip.sankuai.com (内网)
    域名: order.vip.sankuai.com
    HTTPS: 仅HTTP
    映射规则: / → com.sankuai.ee.orderservice
  
  站点#200: wmorder.sankuai.com (外网)
    域名: wmorder.sankuai.com
    映射规则: / → com.sankuai.waimai.wmorderservice
    流量调度策略: Header[x-gray-lane]=gray-canary → LiteSET: gray-canary
  
  站点#300: hotel.sankuai.com (外网)
    域名: hotel.sankuai.com
    映射规则1: / → com.sankuai.hotel.hotelservice (首页)
    映射规则2: /api/search → com.sankuai.hotel.hotelservice (搜索)
    映射规则3: /api/book → com.sankuai.hotel.hotelservice (预订)
    映射规则4: /static/ → 前端AppKey: com.sankuai.hotel.web (静态资源)
```

从这个例子中可以看到几个关键模式：

同一个服务可以有多个域名入口。OrderService同时通过外网域名 `order.sankuai.com` 和内网域名 `order.vip.sankuai.com` 提供服务，两个站点指向同一个AppKey，但HTTPS配置不同（外网强制HTTPS，内网仅HTTP）。

同一个域名下可以通过映射规则路由到多个服务。`hotel.sankuai.com` 下有4条映射规则，3条指向后端RPC服务的不同方法，1条指向前端静态资源服务。

流量调度策略叠加在映射规则上做灰度分流。`wmorder.sankuai.com` 的映射规则关联了流量调度策略，命中灰度条件的请求走灰度实例，其他走主干。

不同团队的服务通过OWT隔离和独立域名互不干扰。到店订单组用 `*.ee.test.sankuai.com`，外卖用 `*.waimai.test.sankuai.com`，酒店用 `*.hotel.test.sankuai.com`，线下自动路由到各自集群，线上通过独立域名和DNS配置各自管理。

### 12.9 域名与网关配置的常见问题排查

**问题1：线下域名访问返回404**

原因：Oceanus上没有创建对应的站点配置，或者站点配置中没有匹配到请求路径的映射规则。泛域名解析只解决了DNS层的问题（域名能解析到Nginx），但Nginx上没有对应的server配置就会返回404。

解决：在Oceanus上创建站点，确保域名和请求路径配置正确。

**问题2：线上域名访问返回502**

原因：域名解析的集群和Oceanus站点配置的集群不一致。DNS把流量打到了集群A的Nginx，但站点配置只在集群B上，集群A的Nginx找不到后端服务配置。

解决：在Oceanus站点域名页面检查"域名解析到的集群"和"站点绑定的集群"是否一致。不一致则修改其中一方使其一致。

**问题3：域名包含大写字母导致访问异常**

原因：DNS域名解析不区分大小写，但Nginx的server_name匹配默认区分大小写。如果域名配置中包含大写字母，可能导致Nginx匹配不到对应的server块。此外，带有下划线的HTTPS域名在iOS设备上会提示证书不安全。

解决：域名一律使用小写字母，不包含下划线。

**问题4：线下跨OWT调用失败**

原因：线下域名按OWT解析到不同的Nginx集群。如果A服务（OWT=ee）通过HTTP调用B服务（OWT=hotel），请求会从ee集群的Nginx出去，经过DNS解析到hotel集群的Nginx，再到B服务。如果B服务的域名没有在hotel集群的Oceanus上创建站点，就会404。

解决：确保被调用的服务在对应OWT的Oceanus集群上创建了站点配置。

**问题5：公网域名访问被WAF拦截**

原因：公网域名（`*.sankuai.com`）必须接入WAF。如果请求中包含SQL注入特征、XSS攻击特征等，WAF会拦截并返回HTTP 456。

解决：检查请求内容是否触发了WAF规则。如果是误拦截，联系安全团队调整WAF规则。可以通过响应头 `X-Sec3-Forbidden: 1` 确认是WAF拦截。

### 12.10 终极总结：域名路由体系的本质

回到你最初的困惑——"那么多域名都是怎么分配好的，怎么路由这么清楚的"——现在可以清晰地回答了：

域名的分配遵循命名规范。线下环境用 `{name}.{owt}.{env}.sankuai.com` 格式，系统通过泛域名解析自动匹配Nginx集群。线上环境用 `{name}.sankuai.com`（外网）或 `{name}.sankuai.com`（内网），由SRE在Domain系统逐域名配置解析。

路由的清晰来自分层配置的明确职责。Domain系统负责"域名→Nginx集群"的物理路由（DNS解析），Oceanus负责"域名+路径→后端AppKey"的逻辑路由（站点+映射规则），OCTO负责"AppKey→具体实例"的实例路由（服务发现+负载均衡）。每一层只做自己的事，不越界，不混淆。

映射关系的维护是自动化和手动结合的。线下高度自动化——泛域名解析自动匹配集群，服务注册自动发现实例，你只需要在Oceanus创建站点配好AppKey。线上半自动化——域名解析需要SRE在Domain配置（Oceanus创建站点时可自动配置），集群需要手动选择，但服务发现和实例管理仍然是自动的。

成千上万的域名之所以不会乱，是因为每一层都有规范的命名约定、明确的职责划分和自动化的匹配机制。你只需要遵守命名规范取个域名，在Oceanus上创建站点关联AppKey，剩下的DNS解析、集群匹配、实例发现都是系统帮你完成的。当这套体系运转起来后，26000+站点、13600+服务、日均3000亿访问就能井然有序地运行。

## 十三、七个实战场景：从配置第一步到请求最后一跳，一步都不跳

上面讲了那么多规范和概念，你心里可能还是有点虚：到底怎么操作？请求真的按那个路走的吗？这一节我们用七个具体场景，每一个都从"你坐在工位上打开浏览器"开始，到"请求到达你服务实例的某一行代码"为止，一步都不跳。

### 场景一：线下test环境——新服务上线后通过域名访问

#### 背景

你是酒店技术组的新人小张，OWT 是 hotel。你刚写好一个酒店搜索服务 HotelSearchService，AppKey 是 `com.sankuai.hotel.searchservice`，已经通过 DevTools 部署到 test 环境，2台实例跑在 `10.65.30.11:8080` 和 `10.65.30.12:8080` 上。你的 mentor 说："你给它配个域名，让前端同学能在测试环境调通。"

#### 第一步：按命名规范取域名

你要取一个线下 test 环境的内网域名。按规范，格式是 `{name}.{owt}.{env}.sankuai.com`。你的 OWT 是 hotel，环境是 test，服务名你想叫 hotelsearch。所以域名是：

```
hotelsearch.hotel.test.sankuai.com
```

你不需要去 Domain 系统注册这个域名，也不需要配 DNS 解析。因为线下 test 环境有泛域名解析——DNS 里已经有一条 `*.hotel.test.sankuai.com → hlb.test.sankuai.com` 的记录。只要你的域名符合 `{任意名}.hotel.test.sankuai.com` 这个模式，DNS 就能自动解析。

#### 第二步：在 Oceanus 管理平台创建站点

打开 Oceanus 管理平台（Oceanus.sankuai.com），点击"创建站点"。

填写信息：

```
站点域名:  hotelsearch.hotel.test.sankuai.com
环境:      test
协议:      HTTP（线下不强制HTTPS，选HTTP就行）
```

点击创建。Oceanus 看到域名中的 OWT 是 hotel，自动帮你选择了 `ng-hotel-ep` 集群（这就是 owtToNgx 映射表干的事——hotel 对应 ng-hotel-ep）。你不需要手动选集群。

#### 第三步：添加映射规则

站点创建好后，进入站点详情页，点击"添加映射规则"。

填写信息：

```
路径（location）:  /
类型:              关联后端AppKey
AppKey:            com.sankuai.hotel.searchservice
```

保存。这一步的意思是：所有访问 `hotelsearch.hotel.test.sankuai.com/` 的请求，都转发给 AppKey 为 `com.sankuai.hotel.searchservice` 的后端服务。

Oceanus 保存后，会把这条配置通过 dyups 模块动态推送到 `ng-hotel-ep` 集群的所有 Nginx 实例上。Nginx 不需要 reload，配置秒级生效。

#### 第四步：Oceanus 自动获取后端实例列表

Oceanus 的 Nginx 收到这条配置后，会通过 OCTO 的 MNS（Naming Service）查询 AppKey `com.sankuai.hotel.searchservice` 在 test 环境下注册的所有 HTTP 实例。因为你的服务已经通过 DevTools 部署并自动向 OCTO 注册了，MNS 返回：

```
com.sankuai.hotel.searchservice (test环境):
  实例1: 10.65.30.11:8080  weight=100  status=UP
  实例2: 10.65.30.12:8080  weight=100  status=UP
```

Oceanus 把这两个实例写入 Nginx 的 upstream 配置（通过 dyups 动态管理，不需要重启）。

#### 第五步：配置完成，全链路已打通

此时整条链路已经就绪。我们来看前端同学小李在浏览器里输入 `http://hotelsearch.hotel.test.sankuai.com/api/search?city=beijing` 后发生了什么：

```
第1跳 — 浏览器发起DNS查询:
  小李的电脑 → 办公网DNS(11.11.11.11)
  查询: hotelsearch.hotel.test.sankuai.com 的A记录是什么？

第2跳 — 办公网DNS转发到IDC DNS:
  办公网DNS → IDC内部DNS(10.10.10.10/内部DNS)
  内部DNS查找: hotelsearch.hotel.test.sankuai.com
  匹配到泛域名记录: *.hotel.test.sankuai.com → CNAME → hlb.test.sankuai.com
  继续解析: hlb.test.sankuai.com → A记录 → 10.32.100.50（ng-hotel-ep集群的VIP）
  返回给小李的电脑: 10.32.100.50

第3跳 — 浏览器建立TCP连接:
  小李的电脑(172.16.5.88) → TCP SYN → 10.32.100.50:80
  注意: 线下test环境没有MGW四层负载，DNS直接解析到Nginx集群的VIP。
  这个VIP后面可能是LVS或直连Nginx，但对你来说不需要关心。

第4跳 — HTTP请求到达Nginx:
  请求到达ng-hotel-ep集群的某一台Nginx实例（比如10.32.100.51）
  Nginx读取HTTP请求头:
    Host: hotelsearch.hotel.test.sankuai.com
    URI:  /api/search?city=beijing
    Method: GET

第5跳 — Nginx匹配server块:
  Nginx用Host头匹配server_name。
  找到了你刚创建的站点配置:
    server {
        server_name hotelsearch.hotel.test.sankuai.com;
        location / {
            proxy_pass http://com.sankuai.hotel.searchservice;
        }
    }
  命中了 location / 这条映射规则。

第6跳 — Nginx选择后端实例:
  Nginx查找upstream com.sankuai.hotel.searchservice 的实例列表:
    10.65.30.11:8080  weight=100
    10.65.30.12:8080  weight=100
  按加权轮询算法选中 10.65.30.11:8080。

第7跳 — Nginx转发请求到后端:
  Nginx → HTTP请求 → 10.65.30.11:8080
  请求头中添加:
    X-Real-IP: 172.16.5.88（小李的真实IP）
    X-Forwarded-For: 172.16.5.88
    X-Forwarded-Host: hotelsearch.hotel.test.sankuai.com

第8跳 — 你的服务处理请求:
  HotelSearchService的10.65.30.11:8080实例收到请求:
    GET /api/search?city=beijing
  执行搜索逻辑，返回JSON响应:
    {"hotels": [{"name": "北京测试酒店", "price": 299}]}

第9跳 — 响应原路返回:
  HotelSearchService → Nginx(10.32.100.51) → 小李的浏览器
  浏览器显示搜索结果。
```

从你坐下来配置到前端同学访问成功，总共就做了两件事：在 Oceanus 创建站点、添加映射规则。DNS 解析是泛域名自动搞定的，后端实例列表是 OCTO 自动同步的，Nginx 配置是 dyups 动态推送的。

### 场景二：线上外网域名——从购买域名到用户手机访问

#### 背景

酒店搜索服务在 test 环境验证通过了，现在要上线。产品经理要求用户在App 里能通过 `https://hotelsearch.sankuai.com` 访问。你需要把这个服务从线下搬到线上，配上公网域名。

#### 第一步：域名注册

`hotelsearch.sankuai.com` 是一个新的公网域名，需要先注册。你在 Domain 系统（domain.mws.sankuai.com）发起域名购买申请。合规管理组审核通过后，会在域名注册商处注册这个域名，费用由公司统一承担。

同时，合规组会发起网站备案（ICP 备案）。备案通过前，这个域名不能对外提供服务——这是工信部的法律要求。

这一步通常需要 1-2 周，需要提前规划。

#### 第二步：SSL 证书准备

公网域名必须强制 HTTPS。中间件 SRE 组会为 `hotelsearch.sankuai.com` 购买并部署 SSL 证书。如果公司已有 `*.sankuai.com` 的通配符证书，可以直接复用，不需要额外购买。

证书会预先导入到 Oceanus 的证书管理模块中，后续创建站点时可以直接选择。

#### 第三步：服务部署到线上环境

你通过 DevTools 将 HotelSearchService 部署到线上（prod）环境。假设线上分配了 4 台实例：

```
com.sankuai.hotel.searchservice (prod环境):
  实例1: 10.72.10.21:8080  weight=100  status=UP  机房=北京亦庄
  实例2: 10.72.10.22:8080  weight=100  status=UP  机房=北京亦庄
  实例3: 10.83.10.31:8080  weight=100  status=UP  机房=上海宝山
  实例4: 10.83.10.32:8080  weight=100  status=UP  机房=上海宝山
```

服务启动后自动向 OCTO 注册，MNS 中已经能查到这 4 个实例。

#### 第四步：在 Oceanus 创建线上站点

打开 Oceanus 管理平台，选择"线上环境"，点击"创建站点"。

填写信息：

```
站点域名:  hotelsearch.sankuai.com
环境:      prod
协议:      强制HTTPS
集群:      ng-hotel-prod（酒店线上Nginx集群）
SSL证书:   选择已有的 *.sankuai.com 通配符证书
```

Oceanus 创建站点时发现 `hotelsearch.sankuai.com` 这个域名还没有 DNS 解析记录，于是自动做了以下事情：

```
1. 从Ark集群管理平台查询ng-hotel-prod集群的CNAME: hotel-prod.Oceanus.sankuai.com
2. 从Domain系统查询该CNAME对应的DNS线路
3. 在Domain系统自动添加DNS记录:
   hotelsearch.sankuai.com → CNAME → hotel-prod.Oceanus.sankuai.com
4. hotel-prod.Oceanus.sankuai.com → A记录 → 公网MGW VIP: 103.37.xx.xx
```

你不需要手动配 DNS，Oceanus 帮你配好了。

#### 第五步：添加映射规则

进入站点详情页，添加映射规则：

```
路径（location）:  /
类型:              关联后端AppKey
AppKey:            com.sankuai.hotel.searchservice
```

保存。配置通过 dyups 推送到 `ng-hotel-prod` 集群的所有 Nginx 实例。

#### 第六步：WAF 接入

公网域名必须接入 Web 应用防火墙（WAF）。安全团队在 WAF 平台上为 `hotelsearch.sankuai.com` 开启防护规则，包括 SQL 注入检测、XSS 攻击检测、CC 攻击防护等。WAF 部署在 MGW 和 Oceanus 之间（或集成在 Oceanus 内），对请求进行安全过滤。

#### 第七步：配置完成，全链路就绪

现在一个用户在北京打开App，点击"酒店搜索"，App 向 `https://hotelsearch.sankuai.com/api/search?city=beijing` 发起请求：

```
第1跳 — App发起DNS查询:
  用户手机 → 运营商公网DNS（或手机配置的公共DNS如114.114.114.114）
  查询: hotelsearch.sankuai.com 的A记录
  公网DNS递归查询:
    → 根DNS → .com DNS → sankuai.com 权威DNS（DNSPod托管）
    → DNSPod返回: hotelsearch.sankuai.com → CNAME → hotel-prod.Oceanus.sankuai.com
    → 继续解析: hotel-prod.Oceanus.sankuai.com → A记录 → 103.37.xx.xx（公网MGW VIP）
  DNSPod支持智能解析，北京用户返回北京PoP点的VIP，上海用户返回上海PoP点的VIP。
  假设这个北京用户拿到的VIP是 103.37.152.10。

第2跳 — TLS握手:
  用户手机 → TCP SYN → 103.37.152.10:443
  三次握手成功后，开始TLS握手。
  手机在ClientHello中发送SNI: hotelsearch.sankuai.com
  MGW的VIP 103.37.152.10通过Anycast路由，实际到达北京PoP点的MGW集群。

第3跳 — MGW四层负载均衡:
  MGW是四层负载，它不看HTTP内容，只看TCP连接。
  MGW根据四元组(源IP、源端口、目的IP、目的端口)做一致性哈希，
  选中ng-hotel-prod集群中的一台Nginx实例: 10.72.5.101:443
  MGW把TCP包转发给10.72.5.101（使用DR模式，直接路由，不修改目的MAC以外的包内容）。

第4跳 — TLS终止 + HTTP解析:
  请求到达Nginx实例10.72.5.101。
  Nginx完成TLS握手（使用*.sankuai.com的通配符证书），解密得到明文HTTP请求:
    Host: hotelsearch.sankuai.com
    URI:  /api/search?city=beijing
    Method: GET
    User-Agent: 美团App/12.5.0 (iPhone; iOS 17.4)

第5跳 — WAF安全检查:
  Nginx内的WAF模块检查请求内容:
    URI参数 city=beijing → 不包含SQL注入特征 → 通过
    请求头 → 不包含XSS攻击特征 → 通过
    请求频率 → 未超过CC攻击阈值 → 通过
  WAF放行，请求继续处理。

第6跳 — Nginx匹配server块和location:
  Nginx用Host头 hotelsearch.sankuai.com 匹配server_name，
  找到你创建的站点配置。
  URI /api/search?city=beijing 匹配 location /（前缀匹配）。
  映射规则指向 upstream com.sankuai.hotel.searchservice。

第7跳 — Nginx选择后端实例:
  upstream中有4个实例:
    10.72.10.21:8080 (北京) weight=100
    10.72.10.22:8080 (北京) weight=100
    10.83.10.31:8080 (上海) weight=100
    10.83.10.32:8080 (上海) weight=100
  当前Nginx在北京机房，OCTO的就近路由策略优先选择同机房实例。
  选中 10.72.10.21:8080。

第8跳 — Nginx转发请求到后端:
  Nginx → HTTP请求 → 10.72.10.21:8080
  添加的请求头:
    X-Real-IP: 用户手机的公网IP（如219.142.xx.xx）
    X-Forwarded-For: 219.142.xx.xx
    X-Forwarded-Proto: https
    X-Request-ID: 一个唯一的请求追踪ID

第9跳 — 服务处理请求:
  HotelSearchService的10.72.10.21:8080实例收到请求，
  执行酒店搜索逻辑（可能还会通过RPC调用其他微服务），
  返回JSON响应:
    {"hotels": [{"name": "北京国贸大酒店", "price": 899}, ...]}

第10跳 — 响应原路返回:
  HotelSearchService → Nginx(10.72.5.101) → TLS加密 → MGW(103.37.152.10) → 用户手机
  App解析JSON，在界面上展示酒店搜索结果。
```

和线下环境相比，线上多了域名注册/备案（第1步）、SSL证书（第2步）、WAF接入（第6步）三个环节，全链路多了TLS握手、MGW四层负载、WAF安全检查三个跳转。这就是线上比线下"重"的地方——安全性和可靠性要求更高。

### 场景三：一个域名下多路径路由到多个服务

#### 背景

酒店业务发展起来了，现在不只有搜索服务，还有预订服务 HotelBookService（AppKey: `com.sankuai.hotel.bookservice`）、支付服务 HotelPayService（AppKey: `com.sankuai.hotel.payservice`）、前端静态页面 HotelWeb（前端AppKey: `com.sankuai.hotel.web`，部署在 Camel 上）。产品要求这些服务都通过同一个域名 `hotelsearch.sankuai.com` 对外提供。

#### 第一步：在已有站点上添加多条映射规则

你不需要创建新站点。进入 Oceanus 上已有的 `hotelsearch.sankuai.com` 站点详情页，现在站点下只有一条映射规则 `/ → com.sankuai.hotel.searchservice`。你需要添加更多规则：

```
添加映射规则2:
  路径:    /api/book
  类型:    关联后端AppKey
  AppKey:  com.sankuai.hotel.bookservice

添加映射规则3:
  路径:    /api/pay
  类型:    关联后端AppKey
  AppKey:  com.sankuai.hotel.payservice

添加映射规则4:
  路径:    /static/
  类型:    关联前端AppKey
  AppKey:  com.sankuai.hotel.web
```

保存后，站点的映射规则列表变成：

```
hotelsearch.sankuai.com 站点:
  location /api/book    → proxy_pass com.sankuai.hotel.bookservice   (预订)
  location /api/pay     → proxy_pass com.sankuai.hotel.payservice    (支付)
  location /static/     → proxy_pass com.sankuai.hotel.web           (前端静态)
  location /            → proxy_pass com.sankuai.hotel.searchservice (搜索,兜底)
```

注意映射规则的顺序很重要。Nginx 的 location 匹配规则是：精确匹配 > 最长前缀匹配 > 正则匹配。`/api/book` 比 `/` 更长，所以请求 `/api/book/create` 会优先匹配到 `/api/book` 这条规则，而不会被 `/` 截流。

#### 第二步：Oceanus 自动获取各服务的实例列表

Oceanus 分别向 OCTO 查询三个 AppKey 的实例列表：

```
com.sankuai.hotel.bookservice (prod):
  10.72.10.41:8080, 10.72.10.42:8080
  
com.sankuai.hotel.payservice (prod):
  10.72.10.51:8080, 10.72.10.52:8080

com.sankuai.hotel.web (prod, Camel前端):
  camel-hotel-web-01.sankuai.com, camel-hotel-web-02.sankuai.com
```

每个 AppKey 的实例列表独立维护，互不影响。Nginx 中会生成三个 upstream 块。

#### 第三步：配置完成，看看不同请求怎么路由

现在同一个域名下有四个服务。用户在App 中的不同操作，会命中不同的映射规则：

**用户打开酒店搜索页面：**

```
请求: GET https://hotelsearch.sankuai.com/static/index.html
  ↓ DNS解析 → MGW → Nginx
  ↓ Nginx匹配Host: hotelsearch.sankuai.com
  ↓ URI: /static/index.html → 匹配 location /static/
  ↓ 转发到 upstream com.sankuai.hotel.web
  ↓ Camel前端服务返回index.html页面
```

**用户搜索酒店：**

```
请求: GET https://hotelsearch.sankuai.com/api/search?city=beijing&checkin=2024-03-15
  ↓ DNS解析 → MGW → Nginx
  ↓ Nginx匹配Host: hotelsearch.sankuai.com
  ↓ URI: /api/search → 匹配 location /（最长前缀匹配，/api/search 不匹配 /api/book 也不匹配 /api/pay，退到 /）
  ↓ 转发到 upstream com.sankuai.hotel.searchservice
  ↓ HotelSearchService返回酒店列表JSON
```

**用户点击预订：**

```
请求: POST https://hotelsearch.sankuai.com/api/book/create
  ↓ DNS解析 → MGW → Nginx
  ↓ Nginx匹配Host: hotelsearch.sankuai.com
  ↓ URI: /api/book/create → 匹配 location /api/book（前缀匹配）
  ↓ 转发到 upstream com.sankuai.hotel.bookservice
  ↓ HotelBookService处理预订，返回订单ID
```

**用户支付：**

```
请求: POST https://hotelsearch.sankuai.com/api/pay/submit
  ↓ DNS解析 → MGW → Nginx
  ↓ Nginx匹配Host: hotelsearch.sankuai.com
  ↓ URI: /api/pay/submit → 匹配 location /api/pay（前缀匹配）
  ↓ 转发到 upstream com.sankuai.hotel.payservice
  ↓ HotelPayService处理支付
```

四个请求都走的是同一个域名、同一个 MGW VIP、同一台 Nginx 实例，但在 Nginx 内部通过 location 路径匹配分别路由到了四个不同的后端服务。这就是"一个域名、多个服务"的实现方式——关键在于映射规则的路径配置。

### 场景四：流量调度灰度分流——线上发版只让1%的用户先用新版本

#### 背景

你的 HotelSearchService 要发布 v2 版本，重构了搜索算法。直接全量上线风险太大，leader 要求先灰度1%的流量到 v2，观察一天没问题再全量。

#### 第一步：部署灰度实例

你在 DevTools 上为 HotelSearchService 创建一个 LiteSET，命名为 `gray-v2`。然后把 v2 版本的代码部署到这个 LiteSET 中，分配 2 台实例：

```
com.sankuai.hotel.searchservice (prod):
  baseline（主干实例）:
    10.72.10.21:8080  weight=100  LiteSET=无（主干）
    10.72.10.22:8080  weight=100  LiteSET=无（主干）
    10.83.10.31:8080  weight=100  LiteSET=无（主干）
    10.83.10.32:8080  weight=100  LiteSET=无（主干）
  
  gray-v2（灰度实例）:
    10.72.10.23:8080  weight=100  LiteSET=gray-v2
    10.72.10.24:8080  weight=100  LiteSET=gray-v2
```

这 6 个实例都注册在 OCTO 中同一个 AppKey 下，但灰度实例带了 `LiteSET=gray-v2` 标签。OCTO 的服务发现能区分它们。

#### 第二步：在 Oceanus 配置流量调度策略

进入 Oceanus 上 `hotelsearch.sankuai.com` 站点的映射规则 `/ → com.sankuai.hotel.searchservice`，点击"关联流量调度策略"。

配置分流规则：

```
分流类型:    LiteSET分流
分流依据:    按比例分流
分流Key:     Header: X-Request-ID（或Cookie中的某个字段）
分流比例:    1%
命中时路由:  LiteSET = gray-v2
未命中时:    走默认主干实例
```

这条策略的意思是：对每个请求，取 `X-Request-ID` 的值做哈希，如果哈希结果落在1%的区间内，就把请求路由到 `LiteSET=gray-v2` 的实例；其余99%的请求继续走主干实例。

#### 第三步：配置完成，看看灰度请求怎么走

**99%的正常请求（未命中灰度）：**

```
请求: GET https://hotelsearch.sankuai.com/api/search?city=beijing
请求头: X-Request-ID: req-abc-123

  ↓ DNS → MGW → Nginx(10.72.5.101)
  ↓ 匹配站点 hotelsearch.sankuai.com
  ↓ 匹配映射规则 location /
  ↓ 检查流量调度策略:
      取X-Request-ID值 "req-abc-123"，计算哈希值 → hash("req-abc-123") % 100 = 67
      67 不在 [0,1) 区间 → 未命中灰度
  ↓ 按默认规则路由，选择主干实例
  ↓ upstream中过滤掉LiteSET=gray-v2的实例，只在主干实例中选:
      10.72.10.21:8080, 10.72.10.22:8080, 10.83.10.31:8080, 10.83.10.32:8080
  ↓ 选中 10.72.10.21:8080
  ↓ 转发请求，HotelSearchService v1 处理，返回结果
```

**1%的灰度请求（命中灰度）：**

```
请求: GET https://hotelsearch.sankuai.com/api/search?city=shanghai
请求头: X-Request-ID: req-xyz-789

  ↓ DNS → MGW → Nginx(10.72.5.101)
  ↓ 匹配站点 hotelsearch.sankuai.com
  ↓ 匹配映射规则 location /
  ↓ 检查流量调度策略:
      取X-Request-ID值 "req-xyz-789"，计算哈希值 → hash("req-xyz-789") % 100 = 0
      0 在 [0,1) 区间 → 命中灰度！
  ↓ 按灰度规则路由，选择LiteSET=gray-v2的实例
  ↓ upstream中只选LiteSET=gray-v2的实例:
      10.72.10.23:8080, 10.72.10.24:8080
  ↓ 选中 10.72.10.23:8080
  ↓ 转发请求，HotelSearchService v2 处理，返回结果
  ↓ Nginx在响应头中添加: X-Lane: gray-v2（标记这个响应来自灰度实例）
```

你在监控平台（如 Raptor）上可以按 LiteSET 标签分别查看 v1 和 v2 的响应时间、错误率、成功率。如果 v2 一切正常，下一步就是在 Oceanus 上把灰度比例从1%调到10%、50%、100%，最终全量上线后删除灰度 LiteSET。

### 场景五：线下泳道域名——多人并行开发互不干扰

#### 背景

你在开发 HotelSearchService 的 v3 版本（新增了"按距离排序"功能），同事小王在开发 HotelBookService 的优惠券功能。你们都在 test 环境开发，但不想互相干扰——你的改动可能导致搜索结果格式变化，影响小王的联调。怎么办？答案是泳道。

#### 第一步：在 Cargo 平台创建泳道

你打开 Cargo 平台（Cargo.sankuai.com），创建一条泳道：

```
泳道名称:  lane-zhangsan
泳道描述:  小张开发酒店搜索v3
包含服务:  com.sankuai.hotel.searchservice
基线环境:  test
```

小王也创建一条泳道：

```
泳道名称:  lane-wangwu
泳道描述:  小王开发预订优惠券
包含服务:  com.sankuai.hotel.bookservice
基线环境:  test
```

#### 第二步：部署泳道实例

你通过 DevTools 将 HotelSearchService v3 的代码部署到泳道 `lane-zhangsan` 中，分配1台实例：

```
com.sankuai.hotel.searchservice (test环境):
  baseline（基线实例）:
    10.65.30.11:8080  泳道=无（基线）
    10.65.30.12:8080  泳道=无（基线）
  
  lane-zhangsan（你的泳道实例）:
    10.65.30.13:8080  泳道=lane-zhangsan
```

小王将 HotelBookService 优惠券版本部署到泳道 `lane-wangwu`：

```
com.sankuai.hotel.bookservice (test环境):
  baseline:
    10.65.30.21:8080  泳道=无（基线）
  
  lane-wangwu:
    10.65.30.22:8080  泳道=lane-wangwu
```

#### 第三步：通过泳道域名访问

泳道创建后，Oceanus 自动生成泳道域名。你要访问你的泳道，在浏览器中输入：

```
http://lane-zhangsan-hotelsearch.hotel.test.sankuai.com/api/search?city=beijing
```

这个域名的构成是 `{泳道名}-{原域名name}.{owt}.{env}.sankuai.com`。泛域名解析 `*.hotel.test.sankuai.com` 同样能覆盖这个域名，DNS 不需要额外配置。

#### 第四步：全链路走一遍

**你访问你的泳道：**

```
请求: GET http://lane-zhangsan-hotelsearch.hotel.test.sankuai.com/api/search?city=beijing

第1跳 — DNS解析:
  lane-zhangsan-hotelsearch.hotel.test.sankuai.com
  匹配泛域名 *.hotel.test.sankuai.com → 10.32.100.50 (ng-hotel-ep集群VIP)

第2跳 — 请求到达Nginx:
  Nginx读取Host头: lane-zhangsan-hotelsearch.hotel.test.sankuai.com
  Oceanus识别出域名中包含泳道前缀 lane-zhangsan，
  在转发请求时自动注入泳道标识:
    请求头添加: X-Lane-Id: lane-zhangsan

第3跳 — Nginx选择后端实例:
  查找upstream com.sankuai.hotel.searchservice
  因为请求携带了 X-Lane-Id: lane-zhangsan，
  OCTO的路由策略优先匹配泳道=lane-zhangsan的实例:
    10.65.30.13:8080  泳道=lane-zhangsan  ← 选中这个！
  不会选基线实例 10.65.30.11/12。

第4跳 — 你的v3代码处理请求:
  10.65.30.13:8080 是你部署的v3版本，执行了"按距离排序"的新逻辑。
  返回结果。
```

**你的泳道中HotelSearchService调用HotelBookService：**

```
你的HotelSearchService v3在处理请求时，需要RPC调用HotelBookService查询酒店是否可预订。

  ↓ HotelSearchService v3 → RPC调用 com.sankuai.hotel.bookservice
  ↓ RPC框架（Pigeon/MTThrift）检查当前请求上下文中的泳道标识: X-Lane-Id=lane-zhangsan
  ↓ 向OCTO查询 com.sankuai.hotel.bookservice 的实例列表
  ↓ 查找泳道=lane-zhangsan的实例 → 没有！（HotelBookService没有部署在lane-zhangsan中）
  ↓ 泳道机制的兜底策略: 如果目标服务在当前泳道没有实例，自动fallback到基线实例
  ↓ 选择基线实例: 10.65.30.21:8080
  ↓ 调用基线版本的HotelBookService
```

这就是泳道的精妙之处——你的搜索服务在泳道中跑的是 v3 新代码，但它调用的预订服务因为你没有在泳道中部署预订服务的改动版本，所以自动走基线的稳定版本。你的改动不会影响小王，小王的改动也不会影响你。每个人在自己的泳道里独立开发、独立测试，只有自己改了的服务走泳道实例，其他服务走公共基线。

**小王访问他自己的泳道：**

```
请求: GET http://lane-wangwu-hotelsearch.hotel.test.sankuai.com/api/book/create

  ↓ DNS → Nginx → 识别泳道 lane-wangwu
  ↓ 匹配映射规则 /api/book → com.sankuai.hotel.bookservice
  ↓ OCTO查找泳道=lane-wangwu的实例 → 10.65.30.22:8080 ← 命中小王的泳道实例
  ↓ 小王的优惠券版本代码处理请求
```

你和小王的请求虽然走的是同一个 Nginx 集群，但通过泳道标识路由到各自的实例，互不干扰。

### 场景六：线下跨 OWT 调用——你的服务要调另一个团队的服务

#### 背景

你的 HotelSearchService（OWT=hotel）在 test 环境运行时，需要通过 HTTP 调用基础架构组的用户画像服务 UserProfileService。这个服务的域名是 `userprofile.inf.test.sankuai.com`（OWT=inf），AppKey 是 `com.sankuai.inf.userprofile`。

你在代码里写了 `httpClient.get("http://userprofile.inf.test.sankuai.com/api/profile?uid=12345")`，但调用返回了 404。怎么回事？

#### 第一步：理解为什么会 404

先理清你的请求走了哪条路：

```
你的服务实例 10.65.30.11 发起HTTP请求:
  目标: http://userprofile.inf.test.sankuai.com/api/profile?uid=12345

第1跳 — DNS解析:
  userprofile.inf.test.sankuai.com
  匹配泛域名 *.inf.test.sankuai.com → hlb.test.sankuai.com → 10.32.200.50
  注意: 这里解析到的是 ng-inf-ep 集群的VIP，不是你所在的 ng-hotel-ep 集群！
  因为域名中的OWT是inf，owtToNgx映射表把inf映射到ng-inf-ep。

第2跳 — 请求到达ng-inf-ep集群的Nginx:
  Nginx读取Host: userprofile.inf.test.sankuai.com
  Nginx在自己的server配置中查找是否有这个域名的站点。
  
  如果基础架构组的同学已经在ng-inf-ep集群的Oceanus上创建了站点
  userprofile.inf.test.sankuai.com → com.sankuai.inf.userprofile,
  那请求就能正常转发。
  
  但如果他们忘记创建了（或者创建在了别的集群上），Nginx找不到匹配的
  server块，就会返回默认的404页面。
```

问题的根源是：你的请求从 hotel 集群出去，经过 DNS 解析到了 inf 集群，但 inf 集群的 Nginx 上没有 `userprofile.inf.test.sankuai.com` 这个站点的配置。

#### 第二步：确认对方站点配置

你联系基础架构组的同学小赵，问他 UserProfileService 在 Oceanus 上配了站点没有。小赵说："配了啊，域名就是 `userprofile.inf.test.sankuai.com`，在 ng-inf-ep 集群上。"

你让他在 Oceanus 站点详情页确认一下。小赵检查后发现问题了——他当时创建站点的时候选错了集群，选成了 `ng-inf-offlinebeijing` 而不是 `ng-inf-ep`。域名 `*.inf.test.sankuai.com` 解析到的是 `ng-inf-ep` 集群，但站点配置在 `ng-inf-offlinebeijing` 集群上。请求到达 `ng-inf-ep` 的 Nginx 后，找不到站点配置，所以 404。

#### 第三步：修复集群配置

小赵在 Oceanus 上把站点集群从 `ng-inf-offlinebeijing` 改成 `ng-inf-ep`，Oceanus 自动把站点配置推送到 `ng-inf-ep` 集群的 Nginx 实例上。

#### 第四步：修复后的完整链路

```
你的代码发起HTTP请求:
  httpClient.get("http://userprofile.inf.test.sankuai.com/api/profile?uid=12345")

第1跳 — DNS解析:
  userprofile.inf.test.sankuai.com → *.inf.test.sankuai.com → 10.32.200.50 (ng-inf-ep)

第2跳 — 请求到达ng-inf-ep的Nginx:
  Nginx匹配Host: userprofile.inf.test.sankuai.com
  这次在ng-inf-ep集群上找到了站点配置:
    server_name userprofile.inf.test.sankuai.com;
    location / { proxy_pass http://com.sankuai.inf.userprofile; }

第3跳 — Nginx查询后端实例:
  OCTO返回 com.sankuai.inf.userprofile 在test环境的实例:
    10.65.40.11:8080, 10.65.40.12:8080

第4跳 — Nginx转发到后端:
  选中10.65.40.11:8080，转发请求。
  UserProfileService处理请求，返回用户画像数据。

第5跳 — 响应返回:
  UserProfileService → ng-inf-ep的Nginx → 你的HotelSearchService(10.65.30.11)
  你的代码拿到用户画像数据，继续处理搜索逻辑。
```

跨 OWT 调用的要点是：请求会离开你的 Nginx 集群，经过 DNS 解析进入对方 OWT 的 Nginx 集群。对方的站点配置必须在对方的集群上。如果站点配置和 DNS 解析指向的集群不一致，就会 404。

#### 第五步：更好的做法——用 RPC 替代 HTTP

实际上，跨服务调用更推荐使用 RPC（通过 OCTO 的 Pigeon/MTThrift 框架），而不是通过 HTTP 域名调用。RPC 调用直接通过 OCTO 的服务发现找到目标服务的实例，不经过 Nginx 网关，避免了跨集群路由的问题：

```
RPC调用方式:
  你的代码: rpcClient.invoke("com.sankuai.inf.userprofile", "getProfile", uid=12345)
  ↓ RPC框架向OCTO查询 com.sankuai.inf.userprofile 的实例列表
  ↓ OCTO直接返回: 10.65.40.11:8080, 10.65.40.12:8080
  ↓ RPC框架直连后端实例，不经过Nginx
  ↓ 调用成功
```

RPC 走的是"AppKey→实例"的直连路由，绕过了 DNS 和 Nginx 这两层，既简单又高效。HTTP 域名调用走的是"域名→DNS→Nginx集群→实例"的间接路由，多了两层中转。除非是外部用户请求或者必须走 HTTP 协议的场景，内部服务间调用应该优先用 RPC。

### 场景七：线上域名解析与集群不一致——502 错误排查

#### 背景

某天早上，你收到告警：`hotelsearch.sankuai.com` 的错误率飙升到30%，大量用户报告搜索页面显示"服务器错误"。打开监控看到返回了大量 502 Bad Gateway。

#### 第一步：定位问题

你打开 Oceanus 的站点详情页，发现站点域名那里有一个红色警告：

```
⚠️ 域名解析不一致
域名: hotelsearch.sankuai.com
DNS解析到的集群: ng-hotel-prod-bj（北京酒店线上集群）
站点绑定的集群: ng-hotel-prod-sh（上海酒店线上集群）
```

原来昨晚 SRE 小李在做集群迁移时，在 Domain 系统里把 `hotelsearch.sankuai.com` 的 DNS 解析从原来的 `ng-hotel-prod` 改成了 `ng-hotel-prod-bj`（北京新集群），但忘记在 Oceanus 上把站点也迁移到 `ng-hotel-prod-bj`。站点配置还留在旧的 `ng-hotel-prod-sh`（上海集群）上。

#### 第二步：理解502是怎么发生的

```
用户请求: GET https://hotelsearch.sankuai.com/api/search?city=beijing

第1跳 — DNS解析:
  hotelsearch.sankuai.com → CNAME → hotel-prod-bj.Oceanus.sankuai.com
  → 103.37.xx.xx（北京MGW VIP）

第2跳 — MGW转发:
  MGW → ng-hotel-prod-bj集群的某台Nginx: 10.72.5.201

第3跳 — Nginx查找站点配置:
  Nginx在ng-hotel-prod-bj集群的配置中查找 server_name=hotelsearch.sankuai.com
  → 找不到！因为站点配置在ng-hotel-prod-sh集群上，不在bj集群上。
  
  Nginx找不到匹配的server块，走了default_server配置。
  default_server返回502 Bad Gateway（或者返回一个默认错误页）。

第4跳 — 响应返回:
  502 Bad Gateway → MGW → 用户手机
  用户看到"服务器错误"。
```

核心问题：DNS 把流量打到了北京集群，但站点配置在上海集群。北京集群的 Nginx 上没有这个站点的 server 配置，所以返回 502。

#### 第三步：为什么只有30%的请求报错

你可能注意到错误率是30%而不是100%。这是因为 DNS 有缓存——部分用户的 DNS 缓存还保留着旧的解析结果（指向上海集群的 VIP），这些用户的请求还能正常到达上海集群的 Nginx 并正确处理。随着 DNS 缓存逐渐过期（TTL 通常是几分钟到几十分钟），越来越多的用户会拿到新的 DNS 解析结果（指向北京集群），错误率会逐渐上升到接近100%。

#### 第四步：修复——两种方案

**方案A：改DNS解析（回滚，快速止血）**

在 Domain 系统里把 `hotelsearch.sankuai.com` 的 CNAME 改回 `hotel-prod-sh.Oceanus.sankuai.com`（指向上海集群）。DNS 变更大约 10 秒生效（内网 内部DNS），公网 DNS 缓存过期后也会刷新。

**方案B：迁移站点配置（正向修复）**

在 Oceanus 上把 `hotelsearch.sankuai.com` 站点从 `ng-hotel-prod-sh` 集群迁移到 `ng-hotel-prod-bj` 集群。迁移后，北京集群的 Nginx 就有了这个站点的配置，请求能正常处理。

紧急情况下先执行方案A快速止血，然后再按计划执行方案B完成集群迁移。

#### 第五步：修复后验证

```
修复后（假设用方案A回滚DNS）:

用户请求: GET https://hotelsearch.sankuai.com/api/search?city=beijing

第1跳 — DNS解析:
  hotelsearch.sankuai.com → CNAME → hotel-prod-sh.Oceanus.sankuai.com
  → 103.37.yy.yy（上海MGW VIP）  ← 改回了上海集群

第2跳 — MGW转发:
  MGW → ng-hotel-prod-sh集群的Nginx: 10.83.5.101

第3跳 — Nginx查找站点配置:
  在ng-hotel-prod-sh集群中查找 server_name=hotelsearch.sankuai.com
  → 找到了！站点配置就在这个集群上。

第4跳 — 正常路由:
  匹配 location / → com.sankuai.hotel.searchservice
  选择后端实例 → 转发 → 正常响应

监控上的错误率逐渐从30%降回0%。
```

#### 这个场景的教训

DNS 解析指向的集群和 Oceanus 站点绑定的集群必须一致。任何时候修改 DNS 解析或迁移站点集群，都要确保两边同步。Oceanus 提供了集群一致性检查功能——在站点域名页面会用红色警告提示不一致的情况。做集群迁移的正确流程是：先在目标集群创建站点配置 → 验证目标集群的站点配置能正常工作 → 最后再切 DNS 解析到目标集群。切完 DNS 后等旧 DNS 缓存全部过期，确认所有流量都走新集群了，再下线旧集群的站点配置。

### 七个场景的回顾

```
场景一: 线下test新建服务域名
  → 泛域名解析自动搞定DNS，Oceanus创建站点+映射规则，5分钟搞定

场景二: 线上外网域名从0到1
  → 域名注册+备案+证书+Oceanus站点+WAF，完整的企业级上线流程

场景三: 一个域名多路径路由多服务
  → 同一个站点下添加多条映射规则(location)，路径匹配分发到不同AppKey

场景四: 灰度分流
  → 流量调度策略关联映射规则，按比例/按条件分流到LiteSET灰度实例

场景五: 泳道隔离并行开发
  → 泳道域名自动注入泳道标识，OCTO按标识路由到泳道实例，未部署的服务fallback基线

场景六: 线下跨OWT调用
  → 请求跨Nginx集群路由，站点必须配在对方OWT的集群上；内部调用优先用RPC

场景七: 域名解析与集群不一致导致502
  → DNS指向集群A但站点在集群B，Nginx找不到server配置返回502，确保两边一致
```

到这里，你应该对美团网关体系中"域名是怎么配的、请求是怎么走的、出了问题怎么排查"有了一个完整的、从头到尾的理解。不管是新建域名、多路径路由、灰度发布、泳道隔离，还是跨团队调用和故障排查，每一个场景的全链路都是由 Domain 系统（DNS）、MGW（四层）、Oceanus/Nginx（七层）、OCTO（服务发现）这四层组件协作完成的。理解了这四层的职责和它们之间的关系，你就能从容应对任何域名和路由相关的问题。
