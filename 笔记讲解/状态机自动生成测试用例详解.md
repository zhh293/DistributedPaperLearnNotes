# Mario 状态机自动生成测试用例详解

> 本文从"为什么要这么做"出发，完整讲清楚状态机测试用例自动生成的思路、业务流程和代码实现。

---

## 一、先理解问题：手写测试用例有什么痛点？

假设你在测一个**订单系统**，这个系统的业务流程是这样的：

```
[初始] --创建订单--> [待支付] --支付--> [已支付] --发货--> [已发货] --确认收货--> [已完成]
                                        --取消--> [已取消]
                    --取消--> [已取消]
```

作为测试工程师，你需要覆盖：

- **正常路径**：创建订单 → 支付 → 发货 → 确认收货（这是一条完整的正常流程）
- **正常路径**：创建订单 → 支付 → 取消（另一条正常流程）
- **正常路径**：创建订单 → 取消（还没支付就取消）
- **异常路径**：在"待支付"状态直接发货（非法操作，系统应该拒绝并报错）
- **异常路径**：在"已完成"状态再次支付（非法操作）
- **异常路径**：……还有很多

**问题来了：**

1. 状态和操作一多，组合爆炸，手写用例很容易漏掉某些边界情况
2. 业务逻辑变了（比如新增了一个"退款"状态），所有相关用例都要手动更新
3. 异常路径（非法操作）往往是最容易被忽略的，但也是最容易出 Bug 的地方

**Mario 的解法：** 用状态机模型描述业务，让算法自动算出所有路径，再自动生成可执行的测试用例文件。这就是 **MBT（Model-Based Testing，基于模型的测试）**。

---

## 二、整体思路：三件事，三个角色

整个方案把"测什么"和"怎么测"彻底分开，分成三个部分：

| 你需要准备的 | 是什么 | 谁来维护 |
|---|---|---|
| **状态机模型（model.json）** | 描述系统有哪些状态、哪些操作、哪些跳转合法 | 测试工程师根据业务设计来画 |
| **metadata.json** | 描述每个操作对应的具体测试步骤（调什么接口、传什么参数、断言什么） | 测试工程师来写 |
| **框架自动生成** | 根据模型算出所有路径，拼接 metadata，生成可执行的用例文件 | 框架自动完成，不需要人工干预 |

业务变了？只改模型和 metadata，用例重新生成，不用一条一条手改。

## 四、第一步：画状态机模型

状态机模型是一个 JSON 文件，用 [GraphWalker](https://graphwalker.github.io/) 工具来画和生成。

**核心概念：**
- **顶点（vertex）**：系统的状态，比如"待支付"、"已支付"
- **边（edge）**：状态之间的操作，比如"支付"、"取消"
- **起始节点**：必须命名为 `start`
- **结束边**：从终态指回 `start` 的边，必须命名为 `e_end`（这是算法切割路径的标记）
- **遍历策略**：告诉 GraphWalker 怎么走图，`quick_random(edge_coverage(100))` 表示随机遍历直到所有边都被覆盖

**模型文件示例（model.json）：**


## 五、第二步：计算正常路径

**代码位置：** `StateMachineCalculator.java`

### 5.1 GraphWalker 遍历得到原始长路径

```java
// StateMachineCalculator.java
private static List<String> getRawPathByGraphWalker(String modelFilePath) throws IOException {
    List<String> rawPath = new ArrayList<>();
    ContextFactory factory = new JsonContextFactory();
    List<Context> contexts = factory.create(Paths.get(modelFilePath));
    SimpleMachine machine = new SimpleMachine(contexts);
    // GraphWalker 按遍历策略不断走下一步，直到所有边都被覆盖
    while (machine.hasNextStep()) {
        machine.getNextStep();
        rawPath.add(machine.getCurrentContext().getCurrentElement().getName());
    }
    rawPath.add("e_end"); // 手动补上最后一个结束标记
    return rawPath;
}
```

GraphWalker 会按照 `quick_random(edge_coverage(100))` 策略随机游走，直到图中每一条边都至少被走过一次。

**得到的原始路径长这样（交替出现"操作"和"状态"）：**

```
[createOrder, 待支付, pay, 已支付, ship, 已发货, confirm, 已完成, e_end,
 createOrder, 待支付, cancelBeforePay, 已取消, e_end,
 createOrder, 待支付, pay, 已支付, ship, 已发货, confirm, 已完成, e_end, ...]
```

### 5.2 按 `e_end` 切割，去掉状态节点，去重

```java
// StateMachineCalculator.java
public static List<List<String>> calculateNormalPaths(String modelFilePath, Boolean onlyEdges) throws IOException {
    List<String> rawPath = getRawPathByGraphWalker(modelFilePath);
    List<List<String>> normalPaths = new ArrayList<>();
    int headCursor = 1;
    int endCursor = 1;
    while (endCursor < rawPath.size()) {
        if (rawPath.get(endCursor).equals("e_end")) {
            // 截取两个 e_end 之间的片段，就是一条完整路径
            List<String> oneNormalPath = rawPath.subList(headCursor, endCursor);
            if (onlyEdges) {
                // 只保留偶数索引的元素（操作/边），去掉奇数索引的元素（状态/顶点）
                List<String> tempPath = deleteVertex(oneNormalPath);
                normalPaths.add(tempPath);
            }
            headCursor = endCursor + 2;
            endCursor += 3;
        } else {
            endCursor++;
        }
    }
    // 去重，同一条路径只保留一条
    normalPaths = normalPaths.stream().distinct().collect(Collectors.toList());
    return normalPaths;
}

// 删除顶点（状态），只保留边（操作）
// 原始片段：[createOrder, 待支付, pay, 已支付, ship, 已发货, confirm, 已完成]
// 索引：       0           1      2    3       4     5       6       7
// 保留偶数索引：[createOrder, pay, ship, confirm]
private static List<String> deleteVertex(List<String> path) {
    List<String> tempPath = new ArrayList<>();
    for (int i = 0; i < path.size(); i++) {
        if (i % 2 == 0) { // 只保留偶数索引
            tempPath.add(path.get(i));
        }
    }
    return tempPath;
}
```

**最终得到的正常路径列表：**

```
正常路径 0: [createOrder, pay, ship, confirm]
正常路径 1: [createOrder, cancelBeforePay]
```

## 六、第三步：计算异常路径

**核心思想：** 在某个状态下，"不能做的操作"就是异常跳转。

比如在"待支付"状态，合法操作只有"支付"和"取消"，那么"发货"、"确认收货"就是非法操作。

### 6.1 计算每个状态的"非法操作"

```java
// StateMachineCalculator.java
private static Map<String, List<String>> calculateAbnormalJump(JSONObject modelJson) {
    JSONArray edgesArray = ...; // 所有边
    JSONArray vertexArray = ...; // 所有顶点

    // 第一步：计算每个状态的"合法操作"
    // 遍历每个状态，找出以该状态为起点的所有边，这些边就是合法操作
    Map<String, List<String>> normalJumpsMap = new HashMap<>();
    for (Object vertexObject : vertexArray) {
        String verticesName = ...; // 状态名
        List<String> normalEdgeList = new ArrayList<>();
        for (Object edgeObject : edgesArray) {
            // 如果这条边的起点 == 当前状态，则这条边是合法操作
            if (sourceVertexId.equals(verticesId)) {
                normalEdgeList.add(edgeName);
            }
        }
        normalJumpsMap.put(verticesName, normalEdgeList);
    }
    // normalJumpsMap 结果：
    // { "待支付": ["pay", "cancelBeforePay"],
    //   "已支付": ["ship"],
    //   "已发货": ["confirm"],
    //   ... }

    // 第二步：全集（所有操作）减去合法操作 = 非法操作
    List<String> allEdges = ["createOrder", "pay", "cancelBeforePay", "ship", "confirm"];
    Map<String, List<String>> abnormalJumpsMap = new HashMap<>();
    for (每个状态) {
        List<String> 非法操作 = 全集 - 该状态的合法操作;
        abnormalJumpsMap.put(状态名, 非法操作);
    }
    // abnormalJumpsMap 结果：
    // { "待支付": ["createOrder", "ship", "confirm"],
    //   "已支付": ["createOrder", "pay", "cancelBeforePay", "confirm"],
    //   ... }
    return abnormalJumpsMap;
}
```

### 6.2 生成异常路径

**思路：** 找一条最短的正常路径走到"前置状态"，然后接上一个"非法操作"，就构成一条异常路径。

```java
// StateMachineCalculator.java
public static List<List<String>> calculateAbnormalPaths(String modelFilePath) throws Exception {
    // 先拿到所有正常路径（带状态节点，用于定位前置状态）
    List<List<String>> normalPathsList = calculateNormalPaths(modelFilePath, false);
    // 按路径长度排序，短的在前，目的是找到最短的前缀路径
    normalPathsList.sort(Comparator.comparingInt(List::size));

    Map<String, List<String>> abnormalJumpsMap = calculateAbnormalJump(modelJson);

    List<List<String>> abnormalPathsList = new ArrayList<>();
    for (每个状态 及其 非法操作列表) {
        String illegalPreVertex = 状态名; // 比如"待支付"
        List<String> illegalJumpsList = 非法操作列表; // 比如["ship", "confirm"]

        // 在正常路径中找第一条包含"待支付"这个状态的路径
        for (List<String> normalPath : normalPathsList) {
            if (normalPath 包含 illegalPreVertex) {
                // 截取到"待支付"之前的部分（只保留操作，去掉状态）
                // 比如正常路径是 [createOrder, 待支付, pay, ...]
                // 截取到"待支付"之前 = [createOrder]
                List<String> prefix = 截取并去掉状态节点;

                // 逐个拼接非法操作
                for (String illegalJump : illegalJumpsList) {
                    List<String> abnormalPath = new ArrayList<>(prefix);
                    abnormalPath.add(illegalJump); // 比如 [createOrder, ship]
                    abnormalPathsList.add(abnormalPath);
                }
                break; // 找到第一条就够了
            }
        }
    }
    return abnormalPathsList;
}
```

**最终得到的异常路径列表（示例）：**

```
异常路径 0: [createOrder, ship]         ← 待支付状态下非法发货
异常路径 1: [createOrder, confirm]      ← 待支付状态下非法确认收货
异常路径 2: [createOrder, pay, confirm] ← 已支付状态下非法确认收货（跳过发货）
...
```

## 七、第四步：拼接 metadata，生成用例数据

**代码位置：** `StateMachineExecute.java` + `CaseFormatter.java`

有了路径列表，接下来要把每条路径"翻译"成可执行的测试用例。

### 7.1 metadata 是什么

metadata 是你提前写好的"操作字典"，每个操作名对应一段测试步骤描述：

```json
// metadata.json
{
  "createOrder": {
    "step_login": {
      "desc": "用户登录",
      "serviceName": "scenario.service.LoginService",
      "request": { "username": "testuser", "password": "123456" },
      "asserts": { "response": { "code": 200 } }
    },
    "step_createOrder": {
      "desc": "创建订单",
      "serviceName": "scenario.service.CreateOrderService",
      "request": { "goodsId": "G001", "userId": "$.step_login.response.userId" },
      "asserts": { "response": { "code": 200, "orderId": "${not null}" } }
    }
  },
  "pay": {
    "step_pay": {
      "desc": "支付订单",
      "serviceName": "scenario.service.PayService",
      "request": { "orderId": "$.step_createOrder.response.orderId" },
      "asserts": { "response": { "code": 200 } },
      "asserts_abnormal": { "response": { "code": 403 } }
    }
  },
  "ship": {
    "step_ship": {
      "desc": "发货",
      "serviceName": "scenario.service.ShipService",
      "request": { "orderId": "$.step_createOrder.response.orderId" },
      "asserts": { "response": { "code": 200 } },
      "asserts_abnormal": { "response": { "code": 403 } }
    }
  }
}
```

注意 `asserts_abnormal`：这是异常路径下的预期断言（比如期望返回 403 拒绝），正常路径用 `asserts`，异常路径用 `asserts_abnormal`。

### 7.2 按路径拼接步骤

### 7.3 处理重复步骤的情况

如果一条路径里同一个操作出现了多次（比如"取消后重新下单"），步骤名会自动加后缀避免冲突，并且后续步骤里引用这个步骤的 JSONPath 也会自动更新：

```java
// CaseFormatter.java
// 如果 "step_createOrder" 出现第二次，自动重命名为 "step_createOrder_1"
// 并把后续步骤里的 "$.step_createOrder.xxx" 替换为 "$.step_createOrder_1.xxx"
if (count != null) {
    duplicateJson.put(key + "_" + count.toString(), tempJson);
    // 更新后续步骤中依赖这个步骤的 JSONPath
    for (JSONObject futureJsonObject : jsonObjectList.subList(index + 1, ...)) {
        updateJsonPath(futureJsonObject, key, count);
    }
}
```

## 八、第五步：生成可执行的文件

**代码位置：** `CaseCreator.java`

框架会生成两种文件：

### 8.1 数据文件（.json）

直接把上一步生成的 case JSON 写入文件：

```java
// CaseCreator.java
public static void createDataFile(JSONObject caseJsonObj, String dataPath, String caseName) {

```

### 8.2 测试类文件（.java）

用 **FreeMarker 模板引擎**生成 Java 测试类，模板文件是 `hello.ftl`：


## 九、第六步：用例执行时发生了什么

**代码位置：** `ScenarioProcessor.java` + `SingleStepProcessor.java`

生成的测试类被执行时，`ScenarioProcessor.run()` 负责按顺序执行每个步骤：

```
ScenarioProcessor.run(caseName, scenarioCaseModel)
│
├── 初始化上下文 contextData = {}
│
├── 循环执行每个步骤（按 steps 中的顺序）
│   │
│   └── SingleStepProcessor.handleSingleStep(stepName, caseStep, contextData)
│       │
│       ├── 1. 解析入参中的 JSONPath 引用（从 contextData 中取上游步骤的结果）
│       │      比如 "$.step_login.response.userId" → 替换为实际的 userId 值
│       │
│       ├── 2. 计算动态表达式（比如随机数、时间戳等）
│       │
│       ├── 3. 反射实例化 serviceName 对应的 Service 类
│       │
│       ├── 4. 调用 service.doWork()（发送 HTTP/Thrift 请求）
│       │
│       ├── 5. 把 response 写入 contextData["stepName"]["response"]
│       │      供后续步骤通过 JSONPath 引用
│       │
│       ├── 6. 校验 response（对比 asserts 中的预期值）
│       │
│       ├── 7. 校验 DB / Redis / Kafka 等（如果 asserts 中有配置）
│       │
│       └── 8. 如果配置了 loopCheck，循环执行直到通过或超时
│
└── 所有步骤执行完毕，case 通过
```

**上下文传递的关键：** 每个步骤执行完后，它的 request 和 response 都会存入 `contextData`，后续步骤可以通过 JSONPath 引用：

```
执行完 step_login 后，contextData = {
    "step_login": {
        "request": { "username": "testuser" },
        "response": { "code": 200, "userId": "U12345" }
    }
}

执行 step_createOrder 时，入参 "userId": "$.step_login.response.userId"
→ 框架自动替换为 "userId": "U12345"
```

## 十、触发用例生成的入口

用户只需要在测试代码里调用一行：

```java
// 你的测试类里
public void generateCases() throws Exception {
    // 生成正常路径用例
    Execute.generateStateMachineCases(
        "orderModel",                                    // 模型名称（用于生成文件路径）
        "src/test/java/scenario/data/model.json",        // 状态机模型文件路径
        "src/test/java/scenario/data/metadata.json",     // metadata 文件路径
        true                                             // true=正常路径，false=异常路径
    );

    // 生成异常路径用例
    Execute.generateStateMachineCases(
        "orderModel",
        "src/test/java/scenario/data/model.json",
        "src/test/java/scenario/data/metadata.json",
        false
    );
}
```

`Execute.java` 是对外暴露的统一入口，内部直接调用 `StateMachineExecute.generateStateMachineCases()`：

```java
// Execute.java（对外入口，非常简洁）
public class Execute {
    public static void generateStateMachineCases(
            String modelName, String modelPath, String metaDataPath, Boolean isNormal) {
        StateMachineExecute.generateStateMachineCases(modelName, modelPath, metaDataPath, isNormal);
    }
}
```

## 十一、完整流程总结

```
你写的东西                    框架做的事                      最终产出
─────────────────────────────────────────────────────────────────────────
model.json          →   GraphWalker 遍历图          →
（状态机模型）           得到原始长路径
                         ↓
                    按 e_end 切割 + 去重            →   正常路径列表
                         ↓
                    计算每个状态的非法操作           →   异常路径列表
                         ↓
metadata.json       →   按路径从 metadata 取步骤     →
（操作步骤定义）          拼接成完整 case JSON
                         ↓
                    CaseCreator 写文件              →   .json 数据文件
                    FreeMarker 渲染模板             →   .java 测试类
                         ↓
                    mvn clean test                 →   测试执行 + 报告
```

**这套方案的本质是：** 把"测试覆盖的完整性"这件事，从依赖人的经验和记忆，变成了依赖图论算法的自动计算。只要模型画得准确，正常路径和异常路径的覆盖就是数学上可以保证的。
