# 分布式事务知识体系全面总结

## 一、为什么需要分布式事务

在单体应用中，一个业务操作通常只涉及一个数据库，我们可以依赖数据库自身的 ACID 事务来保证数据一致性。但当系统演进为微服务架构后，一个业务操作可能横跨多个服务、多个数据库、多个消息队列，这时候单机事务无法覆盖全局的一致性问题，分布式事务应运而生。

举个典型场景：用户下单时，需要同时完成"扣减库存"（库存服务）+ "创建订单"（订单服务）+ "扣减余额"（支付服务）。这三个操作分布在不同的服务和数据库中，任何一个失败都应该让整体回滚，这就是分布式事务要解决的核心问题。

### 1.1 CAP 定理

分布式系统中存在一个基本约束 - CAP 定理，它指出在网络分区（P）发生时，一致性（C）和可用性（A）不可兼得：

- C（Consistency）：所有节点在同一时刻看到的数据是一致的。
- A（Availability）：每个请求都能在有限时间内收到响应（不保证是最新数据）。
- P（Partition Tolerance）：网络分区发生时，系统仍然能继续运转。

由于网络分区在分布式环境中不可避免（P 必须保证），所以实际系统只能在 CP 和 AP 之间做选择。大多数互联网业务选择 AP（保可用性，牺牲强一致），然后通过分布式事务方案来尽可能保证数据的最终一致性。

### 1.2 BASE 理论

BASE 是对 CAP 中 AP 方案的进一步阐述：

- BA（Basically Available）：基本可用，允许损失部分可用性（如响应时间变长、降级服务）。
- S（Soft State）：软状态，允许系统中存在中间状态，这个中间状态不影响系统整体可用性。
- E（Eventually Consistent）：最终一致性，系统保证在没有新的更新操作的情况下，数据最终会达到一致状态。

BASE 理论是分布式事务方案设计的理论基础 - 我们不追求强一致性（像单机数据库那样每一刻都一致），而是追求最终一致性（允许短暂的不一致窗口，但最终数据会对齐）。

### 1.3 一致性的分类

理解以下一致性级别对于选择分布式事务方案至关重要：

- 强一致性：写入成功后，任何后续读取都能立即看到最新值。代价是性能和可用性。
- 弱一致性：写入成功后，不保证后续读取能立即看到最新值。
- 最终一致性：弱一致性的特殊形式，保证在一定时间窗口后，所有副本的数据最终一致。这是互联网分布式系统最常采用的一致性模型。

## 二、分布式事务方案全景图

所有分布式事务方案，本质上是在"一致性强度"和"性能/可用性"之间做取舍。按照一致性从强到弱，可以分为以下几大类：

```
强一致性                                                最终一致性
  <-------------------------------------------------------------->
  2PC/3PC    |    TCC    |    Saga    |    本地消息表/事务消息    |    尽最大努力通知
  (刚性事务)                    (柔性事务)
```

- 刚性事务（强一致）：2PC、3PC，追求各参与方在事务结束时状态完全一致。
- 柔性事务（最终一致）：TCC、Saga、本地消息表、事务消息、尽最大努力通知，允许短暂不一致但最终对齐。

## 三、2PC（两阶段提交）

### 3.1 核心思想

2PC（Two-Phase Commit）是最经典的分布式事务协议，由 Jim Gray 在 1978 年提出。它引入一个协调者（Coordinator / Transaction Manager）来统一管理所有参与者（Participant / Resource Manager）的提交和回滚。

### 3.2 执行流程

第一阶段：准备阶段（Prepare / Voting Phase）

1. 协调者向所有参与者发送 Prepare 请求。
2. 每个参与者执行事务操作（写 redo/undo 日志），但不提交。
3. 如果参与者执行成功，返回 Yes（可以提交）；否则返回 No（需要回滚）。

第二阶段：提交阶段（Commit / Decision Phase）

- 所有参与者都返回 Yes：协调者发送 Commit 命令，所有参与者正式提交事务，释放锁资源。
- 任何一个参与者返回 No 或超时：协调者发送 Rollback 命令，所有参与者回滚事务。

```
协调者                    参与者A              参与者B
  |-- Prepare ---------->|                    |
  |-- Prepare -------------------------------->|
  |                       |                    |
  |<-- Yes --------------|                    |
  |<-- Yes -----------------------------------|
  |                       |                    |
  |-- Commit ----------->|                    |
  |-- Commit --------------------------------->|
  |                       |                    |
  |<-- ACK --------------|                    |
  |<-- ACK -----------------------------------|
```

### 3.3 典型实现

- XA 协议：X/Open 组织定义的分布式事务规范，MySQL（InnoDB）、Oracle、PostgreSQL 都支持。Java 中通过 JTA（Java Transaction API）接口使用，常见实现有 Atomikos、Bitronix、Narayana。
- 数据库层面的分布式事务：如 MySQL 的 XA START / XA END / XA PREPARE / XA COMMIT。

### 3.4 XA 协议详解

XA 是一个标准化接口规范，定义了 Transaction Manager（TM）和 Resource Manager（RM）之间的通信协议：

```
Application Program (AP)
        |
        v
Transaction Manager (TM)   <----- XA 接口 ----->   Resource Manager (RM)
  (如 Atomikos)                                      (如 MySQL InnoDB)
```

XA 接口定义的核心方法：
- xa_open / xa_close：打开/关闭与 RM 的连接
- xa_start / xa_end：标记事务分支的开始/结束
- xa_prepare：请求 RM 准备提交
- xa_commit：请求 RM 提交
- xa_rollback：请求 RM 回滚
- xa_recover：恢复未完成的事务分支

MySQL XA 使用示例：

```sql
-- 参与者A（MySQL实例1）
XA START 'global_tx_001', 'branch_a';
UPDATE account SET balance = balance - 100 WHERE user_id = 1;
XA END 'global_tx_001', 'branch_a';
XA PREPARE 'global_tx_001', 'branch_a';
-- 等待协调者决定
XA COMMIT 'global_tx_001', 'branch_a';

-- 参与者B（MySQL实例2）
XA START 'global_tx_001', 'branch_b';
UPDATE account SET balance = balance + 100 WHERE user_id = 2;
XA END 'global_tx_001', 'branch_b';
XA PREPARE 'global_tx_001', 'branch_b';
-- 等待协调者决定
XA COMMIT 'global_tx_001', 'branch_b';
```

### 3.5 优缺点

优点：
- 原理简单，保证强一致性。
- 有成熟的标准（XA）和工业实现。
- 对业务代码无侵入（数据库层面透明处理）。

缺点：
- 同步阻塞：Prepare 阶段所有参与者持有锁并等待协调者的最终决定，期间资源被锁定无法被其他事务使用，吞吐量低。
- 单点故障：协调者是单点，如果协调者在第二阶段宕机，参与者将一直处于阻塞等待状态（资源锁无法释放）。
- 数据不一致风险：如果协调者在发送部分 Commit 命令后宕机，已收到 Commit 的参与者提交了，没收到的参与者没提交，造成数据不一致。
- 性能差：跨网络的多次通信 + 长时间锁定资源，不适合高并发场景。

### 3.6 适用场景

- 对一致性要求极高、并发量不大的场景，如银行核心转账、金融清结算。
- 同构数据库之间的分布式事务（如 MySQL 跨库事务）。
- 内部系统且网络环境稳定的场景。

## 四、3PC（三阶段提交）

### 4.1 核心思想

3PC 是对 2PC 的改进，在准备阶段之前增加了一个 CanCommit 阶段，并且在参与者侧引入了超时机制（2PC 只有协调者有超时），目的是减少阻塞。

### 4.2 执行流程

第一阶段：CanCommit（询问阶段）

协调者询问参与者"你能否参与这个事务？"参与者根据自身状态（资源是否可用、是否有冲突等）返回 Yes/No。这个阶段不会锁定任何资源，只是一个轻量级预检。

第二阶段：PreCommit（预提交阶段）

如果所有参与者返回 Yes，协调者发送 PreCommit 请求，参与者执行事务操作并写日志（但不提交），返回 ACK。如果有参与者返回 No 或超时，协调者发送 Abort，所有参与者中止。

第三阶段：DoCommit（正式提交阶段）

协调者收到所有 ACK 后，发送 DoCommit。参与者正式提交并释放资源。

```
协调者                参与者A            参与者B
  |-- CanCommit ---->|                  |
  |-- CanCommit ---------------------------->|
  |<-- Yes ----------|                  |
  |<-- Yes ----------------------------------|
  |                   |                  |
  |-- PreCommit ---->|                  |
  |-- PreCommit ---------------------------->|
  |<-- ACK ----------|                  |
  |<-- ACK ----------------------------------|
  |                   |                  |
  |-- DoCommit ----->|                  |
  |-- DoCommit ----------------------------->|
  |<-- HaveCommitted-|                  |
  |<-- HaveCommitted-------------------------| 
```

### 4.3 相对 2PC 的改进

- 参与者有超时机制：如果参与者在 PreCommit 阶段后长时间未收到 DoCommit 命令，默认自动提交（因为能走到 PreCommit 说明大概率是要提交的）。这解决了 2PC 中协调者宕机导致参与者永久阻塞的问题。
- CanCommit 阶段作为轻量预检：提前发现明显不可行的参与者，避免进入重量级的 PreCommit 阶段浪费资源。

### 4.4 缺点

- 仍然不能完全解决数据不一致问题（如网络分区时，部分参与者超时自动提交，另一部分收到了 Abort 命令）。
- 增加了一轮网络通信，延迟更高。
- 实际生产中很少使用，更多是理论研究价值。

## 五、TCC（Try-Confirm-Cancel）

### 5.1 核心思想

TCC 是一种业务层面的两阶段提交方案。与 2PC 在数据库/资源层面操作不同，TCC 把事务的 prepare 和 commit/rollback 逻辑上升到业务代码中，由开发者自己实现三个接口：

- Try：尝试执行业务，预留资源（冻结/预扣），但不真正完成业务。
- Confirm：确认执行，正式使用 Try 阶段预留的资源完成业务。
- Cancel：取消执行，释放 Try 阶段预留的资源。

### 5.2 与 2PC 的本质区别

2PC 是资源层面的协议（数据库自己实现 Prepare/Commit），业务代码无感知；TCC 是业务层面的协议，需要开发者在业务代码中显式实现 Try/Confirm/Cancel 三个方法。

2PC 在 Prepare 阶段不释放数据库锁（事务挂起但未提交）；TCC 在 Try 阶段执行完毕后就可以提交本地事务释放锁，只是通过"业务状态"（如冻结字段）来隔离资源。

### 5.3 执行流程

```
TCC 事务管理器              服务A (库存)            服务B (支付)
     |-- Try ------------->| 冻结库存              |
     |-- Try ----------------------------------------->| 冻结余额
     |                      |                       |
     |<-- Try成功 ---------|                       |
     |<-- Try成功 ------------------------------------|
     |                      |                       |
     |-- Confirm ---------->| 扣减库存              |
     |-- Confirm -------------------------------------->| 扣减余额
```

如果任何一个 Try 失败：

```
     |-- Cancel ----------->| 解冻库存              |
     |-- Cancel ---------------------------------------->| 解冻余额
```

### 5.4 典型示例：电商下单

| 步骤 | 库存服务 | 账户服务 |
|------|---------|---------|
| Try | 冻结 2 件库存（available -= 2, frozen += 2） | 冻结 100 元（available -= 100, frozen += 100） |
| Confirm | 扣减冻结量（frozen -= 2, sold += 2） | 扣减冻结额（frozen -= 100） |
| Cancel | 释放冻结量（frozen -= 2, available += 2） | 释放冻结额（frozen -= 100, available += 100） |

对应的数据库设计：

```sql
-- 库存表（增加 frozen 字段支持 TCC）
CREATE TABLE inventory (
    product_id BIGINT PRIMARY KEY,
    available INT NOT NULL DEFAULT 0,   -- 可用库存
    frozen INT NOT NULL DEFAULT 0,      -- 冻结库存（Try 阶段预留）
    sold INT NOT NULL DEFAULT 0         -- 已售
);

-- Try: 冻结库存
UPDATE inventory SET available = available - 2, frozen = frozen + 2
WHERE product_id = 1001 AND available >= 2;

-- Confirm: 扣减冻结
UPDATE inventory SET frozen = frozen - 2, sold = sold + 2
WHERE product_id = 1001 AND frozen >= 2;

-- Cancel: 释放冻结
UPDATE inventory SET frozen = frozen - 2, available = available + 2
WHERE product_id = 1001 AND frozen >= 2;
```

### 5.5 TCC 需要解决的三大问题

**问题一：空回滚（Empty Rollback）**

场景：Try 请求因网络超时未到达参与者，但事务管理器超时后触发了 Cancel。此时参与者收到 Cancel 但之前没有执行过 Try。

解决：Cancel 执行前先检查是否有对应的 Try 记录，没有则直接返回成功（空回滚）。

```java
public boolean cancel(String txId) {
    // 检查是否有 Try 记录
    TccRecord record = tccRecordDao.findByTxId(txId);
    if (record == null) {
        // 空回滚：没有 Try 记录，插入一条 Cancel 记录防止后续悬挂
        tccRecordDao.insert(new TccRecord(txId, "CANCELLED"));
        return true;  // 直接返回成功
    }
    // 正常 Cancel 逻辑...
    doCancel(record);
    return true;
}
```

**问题二：悬挂（Suspend）**

场景：Try 请求在网络中延迟，Cancel 先到达并执行了空回滚，之后 Try 请求才到达。如果此时 Try 继续执行冻结资源，这些资源将永远无法释放（因为 Cancel 已经执行过了）。

解决：Try 执行前检查是否已有 Cancel 记录，有则拒绝执行。

```java
public boolean tryAction(String txId) {
    // 检查是否已经 Cancel 过（防悬挂）
    TccRecord record = tccRecordDao.findByTxId(txId);
    if (record != null && "CANCELLED".equals(record.getStatus())) {
        return false;  // 已取消，拒绝 Try
    }
    // 正常 Try 逻辑：冻结资源
    doTry(txId);
    tccRecordDao.insert(new TccRecord(txId, "TRIED"));
    return true;
}
```

**问题三：幂等性**

Confirm 和 Cancel 可能因网络重试被调用多次，必须保证幂等（重复执行结果相同）。

```java
public boolean confirm(String txId) {
    TccRecord record = tccRecordDao.findByTxId(txId);
    if (record == null || !"TRIED".equals(record.getStatus())) {
        return true;  // 未 Try 或已 Confirm/Cancel，幂等返回
    }
    doConfirm(record);
    tccRecordDao.updateStatus(txId, "CONFIRMED");
    return true;
}
```

### 5.6 优缺点

优点：
- 不依赖数据库的分布式事务支持，完全在业务层面实现。
- Try 阶段预留资源后即可释放数据库锁，不会长期锁定资源，性能远优于 2PC。
- 适合跨异构系统的分布式事务（如同时涉及 MySQL、Redis、HTTP 接口的场景）。
- 资源隔离性好（通过 frozen 字段实现业务级隔离）。

缺点：
- 业务侵入性强：每个参与方都要实现 Try/Confirm/Cancel 三个接口，开发工作量大。
- 设计复杂：需要处理空回滚、悬挂、幂等等边界情况。
- Confirm/Cancel 阶段可能失败：需要引入重试机制和人工干预手段。
- 需要改造数据模型（如增加 frozen 字段）。

### 5.7 开源框架

- Seata（阿里巴巴开源）：支持 TCC 模式，提供事务管理器和 SDK。
- Hmily（dromara 开源）：专注 TCC 模式的轻量级框架。
- ByteTCC：早期 TCC 实现。
- DTM（Go 语言）：支持 TCC 模式。

## 六、Saga 模式

### 6.1 核心思想

Saga 最初由 Hector Garcia-Molina 和 Kenneth Salem 在 1987 年论文中提出。核心思想是：将一个长事务拆分为多个本地短事务（称为子事务 Ti），每个子事务有对应的补偿操作（Ci）。如果某个子事务失败，按照逆序依次执行已完成子事务的补偿操作来回滚。

```
正向执行：T1 -> T2 -> T3 -> ... -> Tn
如果 T3 失败：执行 C2 -> C1（逆序补偿）
```

与 TCC 的核心区别：TCC 有 Try 阶段做资源预留（两阶段），而 Saga 没有预留阶段，每个子事务直接执行并提交。失败后靠补偿操作来"反向撤销"。

### 6.2 两种执行策略

**策略一：编排式（Choreography）**

各服务通过事件驱动相互协作，没有中央协调者。服务 A 完成后发布事件，服务 B 监听到事件后执行自己的逻辑，依次传递。

```
订单服务 --创建订单--> 发布"订单已创建"事件
                         |
库存服务 <--监听事件---- 扣减库存 --> 发布"库存已扣减"事件
                                        |
支付服务 <--监听事件---------------- 扣款 --> 发布"支付完成"事件
```

失败时反向补偿：

```
支付服务扣款失败 --> 发布"支付失败"事件
                        |
库存服务 <--监听---- 恢复库存 --> 发布"库存已恢复"事件
                                    |
订单服务 <--监听---------------- 取消订单
```

优点：去中心化，服务间松耦合，无单点。
缺点：流程分散在各服务中，难以理解全貌；存在循环依赖风险；调试和追踪困难；随着步骤增多，复杂度指数增长。

**策略二：协调式（Orchestration）**

有一个中央协调器（Saga Orchestrator）负责决定调用哪个服务的哪个操作，以及在失败时按什么顺序执行补偿。

```
Saga 协调器
  |-- 步骤1: 创建订单 --> 订单服务
  |<- 成功
  |-- 步骤2: 扣减库存 --> 库存服务
  |<- 成功
  |-- 步骤3: 扣款 ------> 支付服务
  |<- 失败!
  |-- 补偿2: 恢复库存 --> 库存服务
  |-- 补偿1: 取消订单 --> 订单服务
```

优点：流程清晰可控，集中管理；容易添加新步骤；便于测试和调试。
缺点：协调器本身需要保证高可用；存在集中式管理的复杂性。

### 6.3 Saga vs TCC 对比

| 维度 | TCC | Saga |
|------|-----|------|
| 阶段数 | 两阶段（Try + Confirm/Cancel） | 单阶段（直接执行 + 补偿） |
| 资源隔离 | Try 阶段冻结资源，隔离性好 | 无资源预留，中间状态对外可见 |
| 回滚方式 | Cancel 释放 Try 冻结的资源 | 补偿操作反向撤销已提交的操作 |
| 业务侵入 | 高（3 个接口：Try/Confirm/Cancel） | 中（2 个接口：正向 + 补偿） |
| 适用场景 | 短流程、需要高隔离性 | 长流程、步骤多、可接受中间态 |
| 补偿难度 | 低（释放冻结资源即可） | 高（需要设计反向操作，有些操作不可逆） |

### 6.4 Saga 的隔离性问题

由于 Saga 没有 Try 阶段做资源预留，每个子事务直接提交后，中间状态对外可见。这意味着在 Saga 执行过程中，其他事务可能读到"半完成"的数据。

例如：T1（创建订单）已提交，T2（扣库存）正在执行。此时另一个用户查询看到了这个订单，但库存还没扣。如果 T2 失败导致整个 Saga 回滚（取消订单），那个用户看到的就是脏数据。

解决办法：

- 语义锁：在业务表中加状态字段标记"处理中"，其他业务读到该状态时做特殊处理（如提示"订单处理中，请稍后"）。
- 交换律设计：设计业务操作使得执行顺序不影响最终结果。
- 悲观/乐观锁：对关键数据加锁或版本号控制。
- 读隔离：在查询时过滤掉"处理中"状态的记录。

### 6.5 补偿操作的设计原则

- 补偿操作必须是幂等的（可能被重复调用）。
- 补偿操作应该"语义上撤销"而非"物理上回退"（如退款而非删除支付记录）。
- 有些操作天然不可逆（如发送了短信/邮件），只能做"补偿通知"（如再发一条取消短信）。
- 补偿操作应该始终能成功（如果补偿本身也会失败，需要引入重试和人工介入）。

### 6.6 开源框架

- Seata Saga 模式：提供状态机引擎，通过 JSON 定义 Saga 流程。
- Eventuate Tram Saga：基于事件驱动的 Saga 框架（Java）。
- Temporal / Cadence：工作流引擎，天然支持 Saga 编排模式。
- Axon Framework：基于 CQRS/Event Sourcing 的框架，内置 Saga 支持。

## 七、本地消息表

### 7.1 核心思想

本地消息表是 eBay 架构师 Dan Pritchett 在 2008 年提出的方案。核心思想是：利用本地数据库事务来保证业务操作和消息记录的原子性，然后通过异步机制将消息投递给下游服务，实现最终一致性。

这个方案之所以也被归入分布式事务，是因为它解决的核心问题是一样的 - 保证"做业务操作"和"通知下游"这两件事要么都成功，要么都不发生。

### 7.2 为什么需要它 - 核心问题分析

考虑一个典型问题：订单服务创建订单后，需要发消息通知库存服务扣库存。

方案A - 先操作数据库再发消息：
```
1. INSERT 订单（成功）
2. 发送 MQ 消息（失败！）
结果：订单已创建但库存未扣减 -- 数据不一致
```

方案B - 先发消息再操作数据库：
```
1. 发送 MQ 消息（成功，库存服务收到后扣库存）
2. INSERT 订单（失败！）
结果：库存已扣减但没有对应订单 -- 数据不一致
```

方案C - 把发消息放在事务里：
```
BEGIN TRANSACTION;
  INSERT 订单;
  send_mq_message();  -- 如果这里失败，可以回滚订单
COMMIT;
问题：MQ 不是事务参与者，无法真正回滚已发出的消息
```

本质上这是一个"跨资源的原子操作"问题 - 数据库和消息队列是两个不同的资源，无法用单个本地事务同时保证它们的一致性。本地消息表通过"先在同一个数据库事务中把消息也记下来"来绕过这个问题。

### 7.3 执行流程

```
+--------------------------- 订单服务 ---------------------------+
|  BEGIN TRANSACTION;                                            |
|    INSERT INTO orders (...) VALUES (...);  -- 创建订单         |
|    INSERT INTO message_table (                                 |
|      msg_id, topic, body, status, retry_count                  |
|    ) VALUES (..., 'ORDER_CREATED', ..., 'PENDING', 0);        |
|  COMMIT;  -- 利用本地事务保证原子性                              |
+----------------------------------------------------------------+
                            |
                   (异步调度器 / 定时任务)
                            |
                            v
         +------- 读取 PENDING 消息 -------+
         |  发送到 MQ (Kafka/RocketMQ)     |
         |  发送成功 -> 更新状态为 SENT     |
         |  发送失败 -> 等待下次重试         |
         +---------------------------------+
                            |
                            v
              +---- 库存服务 (消费者) ----+
              |  消费消息，执行扣库存      |
              |  处理成功 -> ACK           |
              |  处理失败 -> 重试或人工处理  |
              +---------------------------+
```

### 7.4 关键设计要素

消息表结构（示例）：

```sql
CREATE TABLE local_message (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    msg_id VARCHAR(64) UNIQUE NOT NULL COMMENT '消息唯一ID（幂等键）',
    topic VARCHAR(128) NOT NULL COMMENT '消息主题/目标',
    tag VARCHAR(64) COMMENT '消息标签（用于路由）',
    body TEXT NOT NULL COMMENT '消息体（JSON）',
    status ENUM('PENDING','SENDING','SENT','CONSUMED','FAILED') DEFAULT 'PENDING',
    retry_count INT DEFAULT 0 COMMENT '已重试次数',
    max_retry INT DEFAULT 10 COMMENT '最大重试次数',
    next_retry_time DATETIME COMMENT '下次重试时间（指数退避）',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status_retry (status, next_retry_time)
) COMMENT '本地消息表';
```

定时任务调度：

```java
// 每隔 5 秒扫描待发送消息
@Scheduled(fixedDelay = 5000)
public void scanAndSendMessages() {
    List<LocalMessage> pendingMessages = messageDao.findByStatusAndNextRetryTimeBefore(
        "PENDING", LocalDateTime.now(), 100  // 每次最多处理 100 条
    );
    
    for (LocalMessage msg : pendingMessages) {
        try {
            mqProducer.send(msg.getTopic(), msg.getBody(), msg.getMsgId());
            messageDao.updateStatus(msg.getId(), "SENT");
        } catch (Exception e) {
            // 指数退避：1s, 2s, 4s, 8s, 16s, 32s...
            int nextRetry = msg.getRetryCount() + 1;
            if (nextRetry > msg.getMaxRetry()) {
                messageDao.updateStatus(msg.getId(), "FAILED");
                alertService.notify("消息发送超过最大重试次数: " + msg.getMsgId());
            } else {
                long delaySeconds = (long) Math.pow(2, nextRetry);
                messageDao.updateRetry(msg.getId(), nextRetry,
                    LocalDateTime.now().plusSeconds(delaySeconds));
            }
        }
    }
}
```

消费端幂等处理：

```java
@RocketMQMessageListener(topic = "ORDER_CREATED")
public class InventoryConsumer implements RocketMQListener<String> {
    @Override
    public void onMessage(String messageBody) {
        OrderCreatedEvent event = JSON.parseObject(messageBody, OrderCreatedEvent.class);
        
        // 幂等检查：是否已处理过
        if (consumeRecordDao.exists(event.getMsgId())) {
            log.info("消息已消费，幂等跳过: {}", event.getMsgId());
            return;
        }
        
        // 执行业务逻辑
        inventoryService.deduct(event.getProductId(), event.getQuantity());
        
        // 记录消费成功
        consumeRecordDao.insert(new ConsumeRecord(event.getMsgId(), "SUCCESS"));
    }
}
```

### 7.5 它为什么是分布式事务方案

回到你的困惑：本地消息表看起来只是"可靠消息投递"，为什么也算分布式事务？

因为分布式事务的本质是保证跨多个服务/资源的操作要么都成功，要么有机制保证最终一致。本地消息表保证了：

1. 业务操作和"发起通知下游的意图"是原子的（同一个数据库事务）。
2. 通过重试机制保证消息最终一定能投递出去。
3. 下游消费成功后，全链路最终达到一致状态。

它和 2PC/TCC 的区别在于：它不追求同步的强一致性，而是通过"业务原子 + 异步投递 + 重试 + 幂等"实现最终一致性。这是一种柔性分布式事务方案。

### 7.6 优缺点

优点：
- 实现简单，不依赖特殊中间件，任何关系型数据库都能用。
- 与业务逻辑解耦程度较好（只需要在同一事务里多写一条消息记录）。
- 性能好，不会阻塞资源，不影响主流程响应时间。
- 可靠性高，消息持久化在数据库中不会丢失。

缺点：
- 需要维护消息表和定时任务，增加运维负担。
- 消息表会越来越大，需要定期归档清理（如已消费超过7天的记录转移到归档表）。
- 实时性不如同步方案，存在延迟（取决于定时任务扫描频率，通常秒级到分钟级）。
- 只适合"一方做完通知另一方"的场景，不适合需要多方协调决定是否提交的场景。
- 消息表和定时任务本身也需要做高可用（如集群部署 + 分布式锁防重复扫描）。

## 八、事务消息（RocketMQ 半消息）

### 8.1 核心思想

事务消息是消息队列层面对"本地消息表"模式的封装和升级。RocketMQ 原生支持事务消息，将"本地消息表 + 定时调度"的逻辑下沉到 MQ 内部，开发者只需要关注业务逻辑。

### 8.2 执行流程

```
生产者                          RocketMQ Broker                    消费者
  |                                  |                              |
  |-- 1. 发送半消息(Half Message) -->| (消息暂存，对消费者不可见)     |
  |<-- 2. 半消息发送成功确认 --------|                              |
  |                                  |                              |
  |-- 3. 执行本地事务               |                              |
  |   (如插入订单到数据库)           |                              |
  |                                  |                              |
  |-- 4a. 本地事务成功 -> Commit --->|-- 消息变为可消费状态 -------->|
  |                                  |                              |
  |    或                            |                              |
  |-- 4b. 本地事务失败 -> Rollback ->|-- 删除/标记半消息             |
  |                                  |                              |
  |   如果长时间未收到 4:            |                              |
  |<-- 5. Broker 回查本地事务状态 ---|                              |
  |-- 6. 返回 Commit/Rollback ----->|                              |
```

关键步骤解析：

1. 生产者先发送半消息（Half Message），此消息被 Broker 存储但对消费者不可见。
2. Broker 确认半消息已持久化。
3. 生产者执行本地事务（这是业务逻辑核心，如创建订单）。
4. 根据本地事务执行结果：
   - 成功 -> 向 Broker 发送 Commit，半消息变为正常消息，消费者可见。
   - 失败 -> 向 Broker 发送 Rollback，Broker 删除（或标记丢弃）半消息。
5. 如果 Broker 长时间未收到 Commit/Rollback（如生产者宕机或网络问题），Broker 会主动回查（check back）生产者的本地事务状态。
6. 生产者根据本地事务的实际结果返回 Commit 或 Rollback。

### 8.3 代码示例（RocketMQ 事务消息 Java）

```java
// 创建事务消息生产者
TransactionMQProducer producer = new TransactionMQProducer("order_tx_group");
producer.setNamesrvAddr("namesrv:9876");

// 设置事务监听器
producer.setTransactionListener(new TransactionListener() {
    
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 第3步：执行本地事务
        try {
            OrderDTO order = (OrderDTO) arg;
            orderService.createOrder(order);
            return LocalTransactionState.COMMIT_MESSAGE;  // 本地事务成功，提交消息
        } catch (Exception e) {
            log.error("本地事务执行失败", e);
            return LocalTransactionState.ROLLBACK_MESSAGE;  // 本地事务失败，回滚消息
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 第5步：Broker 回查时调用
        // 根据消息中的业务信息查询本地事务状态
        String orderId = msg.getProperty("orderId");
        Order order = orderService.findById(orderId);
        if (order != null) {
            return LocalTransactionState.COMMIT_MESSAGE;   // 订单存在，说明本地事务成功
        }
        return LocalTransactionState.ROLLBACK_MESSAGE;     // 订单不存在，说明本地事务失败
    }
});

producer.start();

// 发送事务消息
Message msg = new Message("ORDER_TOPIC", "创建订单事件JSON".getBytes());
msg.putUserProperty("orderId", "ORD_20260101_001");
TransactionSendResult result = producer.sendMessageInTransaction(msg, orderDTO);
```

### 8.4 与本地消息表的对比

| 维度 | 本地消息表 | 事务消息(RocketMQ) |
|------|-----------|-------------------|
| 消息存储位置 | 业务数据库中的消息表 | MQ Broker 内部 |
| 原子性保证 | 数据库本地事务 | 半消息 + 回查机制 |
| 消息投递机制 | 需要自己实现定时任务扫描 | MQ 内置投递机制 |
| 消息表维护 | 需要定期归档清理 | 不需要（Broker 管理） |
| 运维复杂度 | 中（需维护定时任务） | 低（依赖 MQ 自身能力） |
| MQ 依赖 | 任意 MQ（Kafka/RabbitMQ等） | 必须用支持事务消息的 MQ |
| 回查能力 | 无（依赖定时补偿扫描） | Broker 主动回查，实时性更高 |
| 适用团队 | 任何团队 | 使用 RocketMQ 的团队 |

### 8.5 Kafka 的事务消息

Kafka 0.11 版本开始也支持事务消息，但实现方式与 RocketMQ 不同：

```java
// Kafka 事务消息（Exactly-Once 语义）
Properties props = new Properties();
props.put("transactional.id", "order-tx-001");
KafkaProducer<String, String> producer = new KafkaProducer<>(props);

producer.initTransactions();

try {
    producer.beginTransaction();
    
    // 发送多条消息（可以跨 topic/partition）
    producer.send(new ProducerRecord<>("order-topic", orderJson));
    producer.send(new ProducerRecord<>("inventory-topic", inventoryJson));
    
    // 如果涉及消费-处理-生产模式，可以提交消费偏移量
    producer.sendOffsetsToTransaction(offsets, consumerGroupId);
    
    producer.commitTransaction();  // 原子提交
} catch (Exception e) {
    producer.abortTransaction();   // 原子回滚
}
```

Kafka 事务更适合"消费-处理-生产"的流式处理场景（Exactly-Once），而非跨服务的业务事务场景。

## 九、最大努力通知

### 9.1 核心思想

最大努力通知是最终一致性方案中最简单的一种。核心思想是：通知方尽最大努力将通知送达接收方，但不保证一定成功。如果通知失败，接收方需要提供主动查询接口让通知方来对账。

### 9.2 典型场景

最经典的场景是第三方支付回调：

```
用户 --> 商户系统 --> 支付宝/微信支付
                         |
                         | (支付成功)
                         |
                         v
               支付平台主动回调商户
               (最大努力通知)
                         |
         +----- 重试策略：15s, 30s, 1min, 5min, 30min, 1h, 12h -----+
         |                                                            |
         v                                                            v
     回调成功 -> 结束                                    重试耗尽 -> 停止通知
                                                                      |
                                                            商户主动查询订单状态
                                                            (对账接口)
```

### 9.3 与本地消息表的区别

| 维度 | 本地消息表 | 最大努力通知 |
|------|-----------|------------|
| 可靠性 | 高（保证消息最终一定投递） | 中（尽力投递，不保证） |
| 重试 | 无限重试直到成功（或人工介入） | 有限次数重试后放弃 |
| 对账 | 不需要（保证投递） | 需要接收方主动对账 |
| 适用 | 内部服务间通信 | 跨系统/跨公司通知 |
| 典型场景 | 订单->库存 | 支付平台->商户回调 |

### 9.4 实现要点

- 通知方：使用消息队列 + 延迟消息实现多次重试（间隔逐渐增大）。
- 接收方：提供幂等的通知接收接口 + 主动对账查询接口。
- 对账机制：接收方定期（如每隔30分钟）调用通知方的查询接口，核实是否有遗漏。

## 十、幂等性：分布式事务的基石保障

### 10.1 为什么幂等性是必需的

在分布式环境中，网络超时、重试、消息重复投递都是常态。无论使用哪种分布式事务方案，下游操作必须是幂等的，否则重试会导致数据错乱。

幂等性的数学定义：f(f(x)) = f(x)，即对同一操作执行一次和执行多次，产生的效果完全相同。

在业务中的含义：用同一笔订单号重复支付，只会扣一次钱；用同一个消息ID重复消费，只会执行一次业务逻辑。

### 10.2 哪些操作天然幂等，哪些不是

天然幂等的操作：
- SELECT 查询
- DELETE WHERE id = ? （删除同一条记录多次，结果一样）
- UPDATE SET status = 'PAID' WHERE id = ? （设置为固定值）

天然不幂等的操作：
- INSERT（重复插入会报错或产生重复数据）
- UPDATE SET balance = balance - 100 （每次执行都会减 100）
- UPDATE SET version = version + 1 （每次执行都会加 1）

### 10.3 幂等性实现方案大全

**方案一：唯一业务ID + 去重表**

```sql
-- 去重表
CREATE TABLE idempotent_record (
    biz_id VARCHAR(64) PRIMARY KEY,  -- 业务唯一ID（如消息ID、订单号）
    biz_type VARCHAR(32) NOT NULL,   -- 业务类型
    status VARCHAR(20),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 处理前先尝试插入去重记录
INSERT IGNORE INTO idempotent_record (biz_id, biz_type, status)
VALUES ('msg_001', 'deduct_inventory', 'processing');
-- affected_rows == 0 说明已存在，幂等跳过
-- affected_rows == 1 说明首次处理，继续执行业务
```

**方案二：状态机控制**

利用业务状态流转的单向性实现幂等：

```java
// 利用 UPDATE 的 WHERE 条件实现状态机幂等
// 订单状态流转：CREATED -> PAID -> SHIPPED -> COMPLETED
int affected = orderDao.update(
    "UPDATE orders SET status = 'PAID', pay_time = NOW() " +
    "WHERE order_id = ? AND status = 'CREATED'",  // 前置状态约束
    orderId
);

if (affected == 0) {
    // 状态已经不是 CREATED，说明已处理过或状态不对
    log.info("订单状态已变更，幂等跳过 orderId={}", orderId);
    return;
}
// affected == 1, 继续后续逻辑
```

**方案三：数据库唯一约束**

```sql
-- 利用唯一索引天然防重
CREATE TABLE payment_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id VARCHAR(64) NOT NULL,
    amount DECIMAL(10,2),
    UNIQUE KEY uk_order_id (order_id)  -- 同一订单只能有一条支付记录
);

-- 重复插入会报唯一约束冲突
INSERT INTO payment_record (order_id, amount) VALUES ('ORD_001', 100.00);
-- 第二次执行会报 Duplicate entry，catch 后返回成功即可
```

**方案四：Token 机制（防止表单重复提交）**

```
1. 客户端请求服务端生成 Token
2. 服务端生成 Token 并存入 Redis（SET token_xxx 1 NX EX 300）
3. 客户端提交请求时带上 Token
4. 服务端用 Redis DEL 操作删除 Token（原子操作）
   - DEL 返回 1（删除成功）-> 首次请求，处理业务
   - DEL 返回 0（key 不存在）-> 重复请求，拒绝
```

```java
public Result submit(String token, OrderRequest request) {
    // 原子删除 Token（Lua 脚本保证原子性）
    Long deleted = redis.eval(
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('del', KEYS[1]) " +
        "else return 0 end",
        Collections.singletonList("token:" + token), 
        "1"
    );
    
    if (deleted == 0) {
        return Result.fail("请勿重复提交");
    }
    
    // 执行业务逻辑
    return orderService.createOrder(request);
}
```

**方案五：乐观锁（版本号）**

```sql
-- 带版本号的更新
UPDATE account 
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;

-- affected_rows == 0 说明版本已变更（被其他操作修改过）
-- 需要重新读取最新版本后重试，或返回冲突错误
```

**方案六：Redis 分布式锁（防止并发重复处理）**

```java
public void processMessage(String msgId, String body) {
    String lockKey = "lock:msg:" + msgId;
    
    // 尝试获取分布式锁（带超时）
    boolean locked = redis.set(lockKey, "1", "NX", "EX", 60);
    if (!locked) {
        log.info("消息正在被其他实例处理，跳过: {}", msgId);
        return;
    }
    
    try {
        // 二次检查是否已消费
        if (consumeRecordDao.exists(msgId)) {
            return;
        }
        // 执行业务
        doBusiness(body);
        consumeRecordDao.insert(msgId);
    } finally {
        redis.del(lockKey);
    }
}
```

### 10.4 幂等性与分布式事务各方案的关系

```
分布式事务方案                  需要幂等的环节
    |
    +-- 2PC/XA             参与者的 Commit/Rollback 必须幂等
    |                      （协调者可能因超时重复发送决定）
    |
    +-- TCC                Confirm 和 Cancel 必须幂等
    |                      （TCC 框架可能重复调用）
    |
    +-- Saga               每个正向操作和补偿操作都必须幂等
    |                      （协调器可能重复触发步骤）
    |
    +-- 本地消息表          消费者处理消息必须幂等
    |                      （消息可能重复投递：MQ 重试、网络问题）
    |
    +-- 事务消息            同上，消费端必须幂等
    |
    +-- 最大努力通知         接收方处理通知必须幂等
                           （通知方会多次重试）
```

结论：幂等性不是一种独立的分布式事务方案，而是所有方案都必须具备的基础能力。它是分布式事务正确运作的前提条件。

## 十一、Seata AT 模式（补充重要方案）

### 11.1 核心思想

Seata 是阿里巴巴开源的分布式事务框架，其独创的 AT（Auto Transaction）模式是对传统 2PC 的重大优化。核心思想是：一阶段就提交本地事务（释放锁），通过 undo_log 实现二阶段的快速提交或回滚。

### 11.2 与传统 2PC/XA 的区别

传统 XA：
- 一阶段 Prepare：执行 SQL 但不提交，持有数据库锁
- 二阶段 Commit/Rollback：提交或回滚，释放锁
- 问题：锁从一阶段持有到二阶段，时间长，性能差

Seata AT：
- 一阶段：执行 SQL 并直接提交（生成 beforeImage/afterImage 存入 undo_log）
- 二阶段 Commit：异步删除 undo_log（因为已经提交了，无需额外操作）
- 二阶段 Rollback：根据 undo_log 生成反向 SQL 执行回滚
- 优势：一阶段就释放数据库锁，性能远好于 XA

### 11.3 执行流程详解

```
应用层                     Seata TC (事务协调器)           数据库
  |                              |                        |
  |-- 1. 开始全局事务 ---------->|                        |
  |<-- 返回 XID ----------------|                        |
  |                              |                        |
  |-- 2. 执行业务 SQL (拦截) ----|----------------------->|
  |   a. 查询 beforeImage        |                        |
  |   b. 执行业务 SQL            |                        |
  |   c. 查询 afterImage         |                        |
  |   d. 写入 undo_log           |                        |
  |   e. COMMIT 本地事务         |   <--- 锁已释放!       |
  |                              |                        |
  |-- 3. 注册分支事务 ---------->|                        |
  |                              |                        |
  |-- 4. 全局提交/回滚 -------->|                        |
  |                              |                        |
  |   [如果提交]                 |                        |
  |   异步删除 undo_log ---------|----------------------->|
  |                              |                        |
  |   [如果回滚]                 |                        |
  |   读取 undo_log              |                        |
  |   生成反向 SQL 执行 ---------|----------------------->|
  |   删除 undo_log              |                        |
```

### 11.4 undo_log 表结构

```sql
CREATE TABLE undo_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    branch_id BIGINT NOT NULL,
    xid VARCHAR(100) NOT NULL,
    context VARCHAR(128) NOT NULL COMMENT '序列化方式',
    rollback_info LONGBLOB NOT NULL COMMENT 'beforeImage + afterImage',
    log_status INT NOT NULL COMMENT '0:正常 1:全局已完成',
    log_created DATETIME NOT NULL,
    log_modified DATETIME NOT NULL,
    UNIQUE KEY ux_undo_log (xid, branch_id)
);
```

### 11.5 AT 模式的写隔离

问题：一阶段已经提交了本地事务，如果此时另一个全局事务修改了同一条数据，回滚时怎么办？

解决：Seata AT 引入全局锁机制：

```
全局事务1:
  1. 获取本地锁 -> 执行 SQL
  2. 获取全局锁（向 TC 注册）-> 本地 COMMIT
  3. 释放本地锁

全局事务2 (并发修改同一行):
  1. 获取本地锁 -> 执行 SQL
  2. 尝试获取全局锁 -> 发现被事务1持有 -> 等待/重试
  3. 如果等待超时 -> 本地 ROLLBACK，释放本地锁
```

### 11.6 优缺点

优点：
- 对业务代码完全无侵入（不像 TCC 需要写三个接口）。
- 一阶段就释放数据库锁，性能远好于 XA。
- 使用简单，只需加注解 @GlobalTransactional。

缺点：
- 需要每个数据库中创建 undo_log 表。
- 全局锁可能影响并发性能（虽然比 XA 的锁粒度更细）。
- 回滚时如果数据已被非 Seata 事务修改（脏写），会回滚失败需要人工介入。
- 仅支持关系型数据库，且对 SQL 类型有限制。

### 11.7 使用示例

```java
@Service
public class OrderService {
    
    @GlobalTransactional(name = "create-order", timeoutMills = 60000)
    public void createOrder(OrderDTO dto) {
        // 1. 创建订单（订单库）
        orderDao.insert(dto);
        
        // 2. 扣减库存（库存库 - 远程调用）
        inventoryClient.deduct(dto.getProductId(), dto.getQuantity());
        
        // 3. 扣减余额（账户库 - 远程调用）
        accountClient.debit(dto.getUserId(), dto.getAmount());
        
        // 任何一步抛异常，Seata 自动回滚所有分支事务
    }
}
```

### 12.3 实际工程中的组合使用

实际项目中，往往不是单独使用某一种方案，而是根据不同子流程的一致性要求组合使用：

```
电商下单场景：

1. 创建订单 + 扣减库存 + 预扣余额
   -> TCC 或 Seata AT（强一致，防止超卖和余额透支）

2. 订单支付成功后 -> 发放积分
   -> 本地消息表 / 事务消息（最终一致，积分晚几秒到账可接受）

3. 订单支付成功后 -> 发短信/推送通知
   -> 最大努力通知（通知丢失影响不大）

4. 所有下游服务
   -> 幂等性保障（基础设施层面，防止重试导致问题）
```

## 十三、补偿机制详解

### 13.1 什么是补偿

补偿（Compensation）是分布式事务中"回滚"的一种实现方式。与数据库事务的 ROLLBACK（物理回滚，恢复到事务前状态）不同，补偿是逻辑上的"反向操作"（undo），它不能真正让时间倒流，而是执行一个新操作来抵消之前操作的效果。

例如：
- 转账操作的补偿不是删除转账记录，而是再转回去。
- 发货操作的补偿不是让快递消失，而是发起退货流程。
- 已发送的短信无法撤回，补偿只能是再发一条更正短信。

### 13.2 补偿的设计原则

1. 补偿操作必须幂等：可能因重试被多次执行。
2. 补偿操作应该最终能成功：如果补偿本身也可能失败，需要引入更多层次的重试和人工介入。
3. 补偿是"语义反向"而非"物理回退"：不是 DELETE 之前 INSERT 的记录，而是记录一笔相反的业务。
4. 补偿的顺序很重要：通常按正向执行的逆序执行补偿。

### 13.3 补偿在各方案中的体现

| 方案 | 补偿形式 | 说明 |
|------|---------|------|
| TCC | Cancel 接口 | 释放 Try 阶段预留的资源 |
| Saga | 补偿事务 Ci | 逆向撤销子事务 Ti 的效果 |
| 本地消息表 | 不需要补偿 | 通过"保证消息一定发出去"来避免需要补偿 |
| 人工对账 | 最终兜底 | 所有方案的最后手段 |

## 十四、分布式事务的监控与运维

### 14.1 需要监控的指标

- 事务成功率 / 失败率
- 事务平均执行时间
- 悬挂事务数量（长时间未完成的事务）
- 补偿操作执行次数和成功率
- 消息积压量（本地消息表/事务消息方案）
- 重试次数分布

### 14.2 故障处理

事务悬挂（长时间未提交/回滚）：
- 设置超时阈值，超时自动回滚。
- 告警通知运维人员。

补偿失败：
- 有限次自动重试。
- 重试耗尽后标记为"待人工处理"。
- 提供管理后台让运维人员查看详情并手动触发重试或确认。

数据不一致兜底：
- 定时对账任务（如每天凌晨跑批，对比上下游数据）。
- 差异数据自动修复或人工确认后修复。

### 14.3 分布式事务的设计原则

1. 能不用分布式事务就不用：优先通过业务设计避免（如合并服务、使用同一数据库、允许最终一致）。
2. 优先选择最终一致性：大多数互联网业务场景不需要强一致性。
3. 做好幂等和补偿：这是所有方案的基础，也是最容易被忽视的。
4. 监控和告警：对悬挂事务、补偿失败、消息积压建立完善的监控。
5. 人工介入兜底：极端情况下需要人工对账和修复，提前准备好工具和流程。
6. 最小化事务范围：事务跨越的资源越少越好，能局部事务解决的不要升级为分布式事务。
7. 异步优于同步：能用异步最终一致的场景，不要用同步强一致。

## 十六、回答你最初的困惑

现在可以正面回答你的问题了：

**"本地消息表算分布式事务吗？"**

算。本地消息表是分布式事务在"最终一致性"流派下的经典实现方案。它通过"本地事务保证消息一定会发出去 + 下游幂等消费"来保证跨服务的数据最终一致。

**"它和 TCC、2PC 为什么看起来完全不一样？"**

因为它们属于不同的一致性流派：
- 2PC/TCC 追求的是强一致性 - 所有参与者在同一时刻达成一致
- 本地消息表追求的是最终一致性 - 允许中间状态不一致，但保证最终会一致

它们解决的是同一个问题（跨服务数据一致性），但选择了不同的 trade-off。打个比方：你要确保"转账"成功，2PC/TCC 相当于"我跟你面对面，我把钱递给你，你确认收到，交易完成"（同步强一致）；本地消息表相当于"我把钱存到可靠的快递柜里，快递员一定会送达给你，你最终一定能收到"（异步最终一致）。

**"幂等性和分布式事务是什么关系？"**

幂等性是分布式事务的地基，不是独立的事务方案。无论你用 2PC、TCC、Saga 还是本地消息表，参与者的操作都必须是幂等的，否则网络重试和消息重复投递会破坏数据一致性。说"幂等性是分布式事务保障措施"是正确的，但它是保障措施中的基础设施层，而非与 TCC 平级的事务协议。

**知识体系的关系梳理：**

```
分布式事务（核心问题：跨服务数据一致性）
  |
  +-- 理论基础：CAP、BASE、一致性分类
  |
  +-- 解决方案（按一致性强度排列）：
  |   |
  |   +-- 强一致：2PC/XA -> 3PC -> TCC -> Seata AT
  |   +-- 最终一致：Saga -> 本地消息表 -> 事务消息 -> 最大努力通知
  |
  +-- 基础设施（所有方案都需要）：
      |
      +-- 幂等性（防止重复操作）
      +-- 补偿机制（失败后恢复）
      +-- 超时控制（防止无限等待）
      +-- 监控对账（兜底保障）
```
