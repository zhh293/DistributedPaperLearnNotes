# Mario 测试框架数据库能力专题整理

## 1. 文档目的

本文面向 `mario-test-framework_副本` 项目，对仓库中和数据库相关的能力做一次系统整理，重点覆盖：

- 数据库模块的定位、背景与设计目标
- 支持的数据源类型与接入方式
- 配置来源、关键配置项与配置加载机制
- 基础用法与典型调用链
- 高级能力：多数据源、分库分表、对象映射、扩展 JDBC 参数、异步落库等待
- 索引、分库分表、多数据源等进阶主题在当前项目中的落地情况
- 适合沉淀为实习产出的亮点与表达方式

本文以项目真实代码为基础，不把“理论可做”误写成“框架已经实现”。如果某项能力在代码中没有直接实现，也会明确标注。

---

## 2. 项目中的数据库能力定位

在 Mario 测试框架中，数据库能力不是一个独立业务系统，而是一个测试辅助组件。它的核心目标不是做通用 ORM，也不是做数据库中间件，而是为自动化测试场景提供统一、轻量、可直接落地的数据操作能力。

换句话说，这部分能力主要解决的是下面几类测试问题：

- 接口调用后，需要验证数据库是否正确落库
- 某些业务是异步写库，测试需要轮询等待最终状态
- 同一套测试代码可能要连接不同类型的数据源，例如 MySQL、Zebra、ZebraShard
- 测试中既需要执行原生 SQL，也需要链式方式快速拼接 SQL
- 查询结果既可能直接拿 `Map`，也可能映射成 Java 对象，方便断言

因此，这套数据库组件更像是“面向测试验证场景的数据访问工具层”。

## 4. 核心设计思路

### 4.1 统一入口：`DBUtil`

`DBUtil` 是数据库组件的统一入口，负责两件事：

- 从配置中读取指定前缀对应的数据源信息
- 根据 URL 前缀自动识别数据源类型，并实例化不同的客户端

它还带有一个 `ConcurrentHashMap` 类型的客户端缓存 `clintMap`，同一个前缀的客户端会复用，避免重复初始化。

里面有两个核心方法

```

public DBClient getClient(String prefix) {
        DBClient dbClient = null;
        synchronized (clintMap) {
            dbClient = (DBClient) clintMap.get(prefix);
            try {
                if (dbClient == null) {
                    dbClient = createClient(prefix);
                }
            } catch (UnsupportedOperationException e) {
                dbClient = createClient(prefix);
                ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_CLIENT_INIT_FAIL.getErrorCode());
                log.error("获取client error", e);
            }
        }
        return dbClient;
    }



    public DBClient createClient(String prefix) {
        DBClient dbClient = null;
        String url = ConfigManage.getValue(prefix + "_url");
        if (url.startsWith("jdbc:mysql")) {
            String userName = ConfigManage.getValue(prefix + "_username");
            String password = ConfigManage.getValue(prefix + "_password");
            dbClient = new MysqlClient(url, userName, password);
        } else if (url.startsWith("Zebra:")) {
            dbClient = new ZebraClient(url.substring(6));
        } else if (url.startsWith("ZebraShard")) {
            dbClient = new ZebraShardClient(url.substring(11));
        }
        if (dbClient != null) {
            clintMap.put(prefix, dbClient);
        } else {
            ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_CLIENT_INIT_FAIL.getErrorCode());
            throw new AssertionError("获取Client失败: " + url);
        }
        return dbClient;
    }

```

说白了就是获取或者创建DBClient用的


### 4.2 抽象客户端：`DBClient`

`DBClient` 是统一的抽象客户端，对外定义一套一致的数据库能力接口，包括：

- 查询单条记录
- 查询多条记录
- 增删改
- 返回自增主键
- 查询结果映射为对象
- 关闭连接

它的意义在于：无论底层连接的是 MySQL、Zebra 还是 ZebraShard，对测试代码来说，调用方式基本统一。


反正就是方法固定就那么几个，然后你们用不同数据库的老老实实继承这个抽象类然后针对你们这个特色的数据库重写里面的方法就行了，之后我获取就获取DBClient，使用多态的特性提高了代码的扩展性。。。。

比如说MysqlClient：

```

public class MysqlClient extends DBClient {
    //数据库用户名
    private String userName;
    //数据库密码
    private String password;
    //驱动信息
    private static final String DRIVER = "com.mysql.jdbc.Driver";

    private static final String CAMEL_CONFIG = "mapUnderscoreToCamelCase";

    //数据库地址
    private String url;
    public Connection connection;

    public MysqlClient(String url, String userName, String password) {
        super(DRIVER, url, userName, password);
        this.url = url;
        this.userName = userName;
        this.password = password;
    }

    public MysqlClient() {
    }

    @Override
    synchronized public Connection getConnection() {
        try {
            connection = super.getConnection();
        } catch (SQLException e) {
            ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_MYSQL_CONNECTION_CLOSE_FAIL.getErrorCode());
            log.error("get connect error", e);
        }
        return connection;
    }


    /**
     * 增加、删除、改
     *
     * @param sql
     * @param params
     * @return
     * @
     */
    public synchronized boolean update(String sql, List<Object> params) {
        boolean flag = false;
        int result = -1;
        PreparedStatement pstmt = null;
        try {
            pstmt = getConnection().prepareStatement(sql);
            int index = 1;
            if (params != null && !params.isEmpty()) {
                for (int i = 0; i < params.size(); i++) {
                    pstmt.setObject(index++, params.get(i));
                }
            }
            result = pstmt.executeUpdate();
            flag = result > 0 ? true : false;
        } catch (SQLException e) {
            ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_UPDATE_ERROR.getErrorCode());
            log.error("update error, sql: {}, params {}", sql, params, e);
        } finally {
            if (pstmt != null) {
                try {
                    pstmt.close();
                } catch (SQLException e) {
                    log.error("close error", e);
                }
            }
            closeConn();
        }
        return flag;
    }

    /**
     * 增加、删除、改
     *
     * @param sql
     * @return
     * @
     */
    public boolean update(String sql) {
        return update(sql, null);
    }

    /**
     * 增加、删除、改
     * 更新并返回自增主键id
     *
     * @param sql
     * @return
     */
    public synchronized int updateReturnId(String sql, List<Object> params) {
        ResultSet resultSet = null;
        int id = -1;
        PreparedStatement pstmt = null;
        try {
            pstmt = getConnection().prepareStatement(sql, com.mysql.jdbc.Statement.RETURN_GENERATED_KEYS);
            int index = 1;
            if (params != null && !params.isEmpty()) {
                for (int i = 0; i < params.size(); ++i) {
                    pstmt.setObject(index++, params.get(i));
                }
            }
            if (pstmt.executeUpdate() > 0) {
                resultSet = pstmt.getGeneratedKeys();
                if (resultSet.next())
                    id = resultSet.getInt(1);
            }
            return id;
        } catch (SQLException e) {
            ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_UPDATE_ERROR.getErrorCode());
            log.error("update error, sql: {}, params {}", sql, params, e);
        } finally {
            if (pstmt != null) {
                try {
                    pstmt.close();
                } catch (SQLException e) {
                    log.error("close error", e);
                }
            }
            this.closeConn();
        }
        return id;
    }

    /**
     * 增加、删除、改
     * 更新并返回自增主键id
     *
     * @param sql
     * @return
     */
    public int updateReturnId(String sql) {
        return this.updateReturnId(sql, (List) null);
    }

    /**
     * 查询单条记录
     *
     * @param sql
     * @param params
     * @return
     * @
     */
    public Map<String, Object> queryOne(String sql, List<Object> params) {
        List<Map<String, Object>> data = query(sql, params);
        if (data != null && data.size() > 0) {
            return data.get(0);
        }
        return new HashMap<>();
    }

    /**
     * base query
     *
     * @param sql
     * @param params
     * @return
     */
    public synchronized List<Map<String, Object>> query(String sql, List<Object> params) {
        List<Map<String, Object>> list = new ArrayList<>();
        PreparedStatement pstmt = null;
        ResultSet resultSet = null;
        try {
            pstmt = getConnection().prepareStatement(sql);
            int index = 1;
            if (params != null && !params.isEmpty()) {
                for (int i = 0; i < params.size(); i++) {
                    pstmt.setObject(index++, params.get(i));
                }
            }
            resultSet = pstmt.executeQuery();//返回查询结果
            ResultSetMetaData metaData = resultSet.getMetaData();
            int col_len = metaData.getColumnCount();
            while (resultSet.next()) {
                Map<String, Object> map = new HashMap<String, Object>();
                for (int i = 0; i < col_len; i++) {
                    String cols_name = metaData.getColumnLabel(i + 1);
                    Object cols_value = null;
                    try {
                        cols_value = resultSet.getObject(cols_name);
                    } catch (Exception e) {
                        ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_GET_RESULT_ERROR.getErrorCode());
                        log.error(" init result eror, sql: {}", sql, e);
                    }
                    map.put(cols_name, cols_value);
                }
                list.add(map);
            }

        } catch (Exception e) {
            ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_QUERY_ERROR.getErrorCode());
            log.error("query error,sql: {}", sql, e);
        } finally {
            try {
                if (resultSet != null) {
                    resultSet.close();
                }
                if (pstmt != null) {
                    pstmt.close();
                }
            } catch (SQLException e) {
            }
            closeConn();
        }
        return list;
    }

    /**
     * 查询单条记录
     *
     * @param sql
     * @return
     * @
     */
    public Map<String, Object> queryOne(String sql) {
        return queryOne(sql, null);
    }


    /**
     * 查询多条记录
     *
     * @param sql
     * @param params
     * @return
     * @
     */
    public List<Map<String, Object>> queryMultiple(String sql, List<Object> params) {
        return query(sql, params);
    }

    /**
     * 查询多条记录
     *
     * @param sql
     * @return
     * @
     */
    public List<Map<String, Object>> queryMultiple(String sql) {
        return queryMultiple(sql, null);
    }

    /**
     * 通过反射机制查询单条记录
     *
     * @param sql
     * @param params
     * @param cls
     * @return
     * @throws Exception
     */
    public <T> T queryOneObject(String sql, List<Object> params,
                                Class<T> cls) {
        T resultObject = null;
        List<T> list = queryMultipleObject(sql, params, cls);
        if (CollectionUtils.isNotEmpty(list)) {
            resultObject = list.get(0);
        }
        return resultObject;

    }

    /**
     * 通过反射机制查询多条记录
     *
     * @param sql
     * @param params
     * @param cls
     * @return
     * @throws Exception
     */
    public <T> List<T> queryMultipleObject(String sql, List<Object> params,
                                           Class<T> cls) {
        List<T> list = new ArrayList<T>();
        List<Map<String, Object>> result = query(sql, params);
        String useCamelConfigStr = ConfigManage.getValue(CAMEL_CONFIG);
        boolean useCamel = false;
        if (!StringUtils.isBlank(useCamelConfigStr) && ("true".equals(useCamelConfigStr)
                || "false".equals(useCamelConfigStr))) {
            useCamel = Boolean.parseBoolean(useCamelConfigStr);
        }
        if (result != null) {
            for (Map<String, Object> row : result) {
                //通过反射机制创建一个实例
                T resultObject = null;
                try {
                    resultObject = cls.newInstance();
                    for (String name : row.keySet()) {
                        String clsFieldName = name;
                        if (useCamel) {
                            clsFieldName = CaseFormat.LOWER_UNDERSCORE.to(CaseFormat.LOWER_CAMEL, name);
                        }
                        // 判断模型中是否存在映射字段，不存在则跳过
                        if (!hasField(cls, clsFieldName)) {
                            continue;
                        }
                        Field field = cls.getDeclaredField(clsFieldName);
                        field.setAccessible(true); //打开javabean的访问权限
                        field.set(resultObject, row.get(name));
                    }
                } catch (Exception e) {
                    ErrorCodeUtil.setErrorCode(ErrorCodeEnum.DB_GET_RESULT_ERROR.getErrorCode());
                    log.error("创建实例失败", e);
                }
                list.add(resultObject);
            }
        }
        return list;
    }
}

```

还是非常好理解的，JDBC的基本使用，没什么特别难的算法或者思路。。。。



### 4.3 两种使用风格并存

当前项目提供两条并行使用路线：

#### 路线 A：直接 SQL 风格

适合：

- 直接执行现成 SQL
- 验证某条业务数据是否存在
- 测试中快速补一条 DB 断言

典型客户端：

- `MysqlClient`
- `ZebraClient`
- `ZebraShardClient`

#### 路线 B：链式 SQL 构建风格

适合：

- 动态拼 SQL
- 测试代码想写得更结构化
- 结合异步等待逻辑一起使用

典型入口：

- `PlatformSql`
- `DBBuild`
- `DBSelectImpl` / `DBInsertImpl` / `DBUpdateImpl` / `DBWhereImpl`

### 4.4 责任链构建 SQL

链式 SQL 的底层不是简单字符串拼接，而是通过一组 Handler 按步骤构建：

- `TableHandler`
- `SelectHandler`
- `InsertHandler`
- `UpdateHandler`
- `DeleteHandler`
- `WhereHandler`

这是一种典型的责任链/处理器链思路。优点是：

- 各阶段职责更清晰
- 后续如果要扩展新的 SQL 处理环节，改动边界较明确
- 对测试框架来说，比引入完整 ORM 成本更低

## 5. 支持的数据源类型

根据 `DBUtil` 与 `docs/data.md`，当前数据库组件明确支持以下几类数据源。

### 5.1 MySQL 直连

识别方式：配置值以 `jdbc:mysql` 开头。

典型配置：

```properties
default_url=jdbc:mysql://127.0.0.1:3306/test_db
default_username=root
default_password=123456
```

对应客户端：

- `MysqlClient`

特点：

- 通过 JDBC 直连数据库
- 需要用户名和密码
- 使用项目内置轻量连接池 `DB`
- 支持参数化查询、对象映射、自增主键返回

### 5.2 Zebra 数据源

识别方式：配置值以 `Zebra:` 开头。

典型配置：

```properties
zy_url=Zebra:hbqa_hbsonar_test
```

对应客户端：

- `ZebraClient`

特点：

- 通过 Zebra 的 `GroupDataSource` 建连
- 配置项不是 JDBC URL，而是 DBA 平台上的 `JDBCRef`
- 支持扩展 JDBC 参数
- 支持 SQL 执行超时设置
- `docs/data.md` 中明确提到 Blade 数据源接入依赖 Zebra 统一数据源能力

### 5.3 Zebra 分库分表数据源

识别方式：配置值以 `ZebraShard:` 开头。

典型配置：

```properties
productRule_url=ZebraShard:pepper_mall_product_basic_test
```

对应客户端：

- `ZebraShardClient`

特点：

- 通过 `ShardDataSource` 建连
- 配置项是 Zebra 分库分表规则名 `ruleName`
- SQL 中使用逻辑表名，由 Zebra 负责路由到具体物理表
- 支持并行执行超时与扩展 JDBC 参数

## 6. 背景与价值：为什么测试框架要自己封装数据库层

从代码设计和文档描述看，这套数据库能力有很明显的测试框架属性，它解决了美团测试中的几个现实问题。

### 6.1 统一不同类型数据源的接入方式

项目并没有要求测试人员分别学习多套数据库接入方式，而是通过 `DBUtil.getClient(prefix, clazz)` 做统一入口。这意味着：

- 同一套测试代码可以接入 MySQL、Zebra、ZebraShard
- 数据源切换主要通过配置完成
- 测试代码更聚焦业务验证，不必关心底层建连细节

### 6.2 降低测试代码中的样板代码

如果每个测试都自己写 JDBC 建连、准备 SQL、遍历 `ResultSet`、关闭连接，代码会非常冗长。这套封装把这些重复逻辑统一收口到客户端中。

### 6.3 为异步业务提供“等待数据库最终一致”的能力

很多真实业务不是同步落库，而是：

- 先写消息
- 再由下游消费
- 再异步写数据库

如果测试在接口返回后立刻查库，经常会查不到数据。Mario 数据库组件专门内置了等待机制，这一点非常适合测试场景，也是它区别于普通工具类封装的核心优势之一。

### 6.4 保持轻量而不是引入重型 ORM

框架没有引入 Hibernate/MyBatis 这类面向业务开发的 ORM 体系，而是保留：

- 原生 SQL 可控性
- 轻量查询与对象映射
- 链式构建能力
- 对测试断言友好的返回结构

这使得它更适合“测试验证层”，而不是“业务持久化层”。

## 7. 配置体系与配置来源

### 7.1 配置读取入口

数据库模块使用的是项目统一配置中心 `ConfigManage`。

`DBUtil` 在静态代码块里调用：

```java
ConfigManage.appendConfig("db.properties");
```

这说明数据库模块会主动把 `db.properties` 纳入配置体系。

### 7.2 配置文件位置

根据 `docs/data.md` 与 `docs/configManange.md`，数据库配置通常放在：

- `src/test/resources/db.properties`
- `src/test/profiles/<env>/env.properties`

也就是说，数据库配置既可以写在独立的 `db.properties`，也可以写进某个测试环境的 `env.properties`。

### 7.3 配置加载顺序

根据 `docs/configManange.md`，配置覆盖顺序是：

1. `config.properties`
2. `env.properties`
3. Maven `-D` 系统属性
4. 环境变量

后加载的同名配置会覆盖先加载的配置。

对于数据库场景，这意味着：

- 可以在默认配置里定义数据库连接
- 可以按环境覆盖连接串
- 也可以在执行 Maven 命令时临时切换
- 最终还可以通过环境变量注入覆盖值

### 7.4 关键配置项

数据库配置采用“前缀 + 字段名”的风格。

#### 基础配置

- `prefix_url`：数据库连接串或数据源标识
- `prefix_username`：用户名，仅 MySQL 直连需要
- `prefix_password`：密码，仅 MySQL 直连需要

#### SQL 配置

还支持把 SQL 配置到属性文件中，例如：

- `querySku_sql=select * from sku where product_id=? and sku_id=?`

然后通过：

```java
ConfigManage.getValue("querySku_sql")
```

读取。

#### 示例配置

```properties
zy_url=Zebra:hbqa_hbsonar_test
ZebraShard_url=ZebraShard:ppstockhotel0_pp_stock_test
productRule_url=ZebraShard:pepper_mall_product_basic_test
querySku_sql=select * from sku where product_id=? and sku_id=?
```

### 7.5 配置识别规则

数据库组件会根据 `prefix_url` 的值自动识别客户端类型：

- `jdbc:mysql...` -> `MysqlClient`
- `Zebra:xxx` -> `ZebraClient`
- `ZebraShard:xxx` -> `ZebraShardClient`

这一点是数据库模块最重要的配置驱动能力。

## 9. 查询结果处理与对象映射逻辑

### 9.1 基础返回结构

直接 SQL 查询时，底层主要返回两类结构：

- `Map<String, Object>`：单行记录
- `List<Map<String, Object>>`：多行记录

这是测试里最常见、最直接的断言方式。

### 9.2 反射对象映射

`MysqlClient.queryMultipleObject()` 支持把查询结果自动映射成 Java 对象，关键逻辑是：

- 先执行 SQL，拿到 `List<Map<String, Object>>`
- 通过 `cls.newInstance()` 创建对象实例
- 遍历每一列，按字段名反射赋值
- 如果目标类没有对应字段，则跳过而不是报错

这种设计对测试很友好，因为数据库字段通常比断言需要的字段更多。

### 9.3 下划线转驼峰

对象映射支持通过配置项 `mapUnderscoreToCamelCase` 控制字段名转换。

例如：

- 数据库字段：`user_name`
- Java 字段：`userName`

当配置为 `true` 时，会自动把下划线风格转成驼峰风格。

这一点很适合写结果模型类，减少手动映射成本。

## 10. 链式 SQL 构建能力

数据库模块除了直接执行 SQL，还支持链式 SQL 构建。

入口类是：

- `PlatformSql`

返回构建结果的核心类是：

- `DBBuild`

### 10.1 常见用法

#### 插入

```java
DBUtil.getClient("default")
    .insert("user")
    .insert("name", "test")
    .insert("age", 18)
    .build();
```

#### 查询

```java
JSONArray data = DBUtil.getClient("default")
    .select("user")
    .select("id", "name")
    .where("id", "=", 1)
    .toJson();
```

#### 更新

```java
DBUtil.getClient("default")
    .update("user")
    .set("name", "newName")
    .where("id", "=", 1)
    .build();
```

#### 删除

```java
DBUtil.getClient("default")
    .delete("user")
    .where("id", "=", 1)
    .build();
```

#### 原生 SQL

```java
JSONArray data = DBUtil.getClient("default")
    .setSql("SELECT * FROM user WHERE id = 1")
    .toJson();
```

### 10.2 `DBBuild` 的结果能力

`DBBuild` 除了 `build()`，还提供：

- `toJson()`：返回 `JSONArray`
- `toJson(index)`：返回指定行的 `JSONObject`
- `toList()`：返回结果列表
- `toList(key)`：抽取某个字段列
- `toStr()`：取第一行第一个选择字段的字符串值
- `toInt()`：取第一行第一个选择字段的整型值
- `getInsertId()`：获取插入后返回的主键

这说明链式 API 不只是“拼 SQL”，而是把“执行 + 等待 + 结果读取”也统一包进来了。

## 11. 连接管理与连接池实现

### 11.1 MySQL 使用项目内置连接池

对于 MySQL 直连，`PlatformSql` 构造时会创建 `DB` 对象，而 `DB` 是项目内置的一个轻量连接池。

它具备以下能力：

- 初始化连接数 `initialConnections`
- 增量扩容 `incrementalConnections`
- 最大连接数 `maxConnections`
- 空闲/忙碌状态标记 `PooledConnection.busy`
- 获取空闲连接
- 连接有效性检测
- 连接归还
- 刷新连接池

### 11.2 连接池的工作思路

大致流程如下：

1. 初始化时先创建一批连接
2. 取连接时先找空闲连接
3. 如果没有空闲连接，则尝试按增量创建新连接
4. 若仍拿不到，则短暂等待再试
5. 使用完后把连接归还池中，而不是直接关闭

### 11.3 Zebra / ZebraShard 的连接方式不同

需要注意：

- `ZebraClient` 并不走 `DB` 这个轻量连接池，而是直接使用 Zebra 的 `GroupDataSource`
- `ZebraShardClient` 则使用 Zebra 的 `ShardDataSource`

因此，这个项目实际上有两种连接管理模式：

- MySQL：项目自己的轻量连接池
- Zebra / ZebraShard：依赖 Zebra 数据源本身的连接管理能力

这也是为什么三个客户端虽然统一继承 `DBClient`，但底层实现并不完全相同。

## 12. 多数据源能力

### 12.1 已实现的多数据源方式

## 13. 分库分表能力

### 13.1 当前项目中的实现方式

分库分表不是框架自己实现的，而是对 ZebraShard 做了接入封装。

核心类：

- `ZebraShardClient`

关键逻辑：

- 通过 `ShardDataSource` 初始化数据源
- 通过 `setRuleName(jdbcRef)` 指定分库分表规则名
- SQL 执行时交给 ZebraShard 进行路由

### 13.2 使用要求

`docs/data.md` 中明确说明：

> 分库分表使用时 SQL 中的表名称请使用逻辑表名

这意味着：

- 测试代码不要直接写某个物理分表名
- 应写逻辑表名，由 Zebra 分片规则决定最终落到哪张表

### 13.3 适用测试场景

分库分表能力非常适合下列自动化测试：

- 验证某个商品/订单/库存等逻辑数据最终是否正确落在分片库表中
- 按业务 ID 查询逻辑表，校验 Zebra 路由后的结果
- 在不感知物理分片细节的前提下，统一写数据库断言

### 13.4 当前边界

需要区分清楚：

- 框架支持的是“接入 ZebraShard 并查询逻辑表”
- 框架本身不负责“设计分片规则”
- 框架也不负责“自动分析路由策略是否合理”

也就是说，它是分库分表的使用层封装，不是分库分表平台本身。

### 14.1 扩展 JDBC 参数

可以通过：

ZebraClient.setExtraJdbcUrlParams("tinyIntlisBit=false");

给 Zebra / ZebraShard 透传扩展 JDBC 参数。

- SQL 异常与业务异常难以区分
- 大量回归任务的整体耗时被放大

## 15. 异步落库等待机制

这是当前数据库模块最值得重点整理的高级能力之一。

### 15.1 为什么需要异步落库等待

很多业务链路不是“接口成功 -> 数据立即可查”，而是：

1. 接口先返回
2. 后续消息投递或异步任务执行
3. 下游消费者处理完成后才真正写库

如果测试代码直接在接口返回后立刻查库，经常会因为最终一致性延迟导致误报失败。

为了解决这个问题，项目内置了一套数据库等待机制。

### 15.2 核心类

- `DBWait`
- `DBWaitImpl`
- `Wait`
- `WaitType`
- `WaitNotNullHandler`

### 15.3 等待参数

等待参数由 `Wait` 对象承载，默认值如下：

- `time = 10000L`：最长等待 10 秒
- `frequency = 10L`：最多轮询 10 次
- `intervalTime = 1000L`：每次间隔 1 秒
- `waitType = NOTNULL`

### 15.4 支持的等待类型

当前 `WaitType` 中支持：

- `NULL`：等待结果为空
- `NOTNULL`：等待结果非空
- `KEY_EQUAL`：等待某些字段值等于预期值
- `KEY_NOTEQUAL`：等待某些字段值不等于预期值
- `SIZE_EQUAL`：等待结果数量等于指定值
- `SIZE_NOTEQUAL`：等待结果数量不等于指定值
- `SIZE_GREATER`：等待结果数量大于指定值
- `SIZE_LESS`：等待结果数量小于指定值
- `INSERT`
- `UPDATE`
- `DELETE`
- `CREATE`

其中对测试最实用的是前八种条件型等待。

### 15.5 典型使用方式

#### 初始化默认等待策略

```java
DBUtil.getClient("default")
    .initWait(10000, 10, 1000)
    .select("user")
    .select("id", "status")
    .where("id", "=", 123)
    .waitdbNotNull()
    .toJson();
```

#### 等待字段值等于预期

```java
DBUtil.getClient("default")
    .select("task_record")
    .select("status")
    .where("task_id", "=", 123)
    .waitdbEqual("status", "SUCCESS")
    .toJson();
```

#### 等待记录数量变化

```java
DBUtil.getClient("default")
    .select("task_record")
    .selectAll()
    .where("biz_id", "=", 123)
    .waitdbGreaterSize(0)
    .toJson();
```

### 15.6 具体执行逻辑

`WaitNotNullHandler.waitdb()` 的核心逻辑可以概括为：

1. 先执行一次 SQL
2. 根据 `WaitType` 判断当前结果是否满足条件
3. 如果不满足，则继续执行 SQL
4. 每轮之间按 `intervalTime` 休眠
5. 如果超过总等待时间，或者超过最大轮询次数，则抛出异常

这其实就是一个“带超时与次数限制的轮询模型”。

### 15.7 异步落库的真实价值

这一能力非常适合下面这些测试场景：

- 接口调用后，消息异步消费写库
- 状态字段会经历多次流转，需要等最终状态稳定
- 某些业务会先写一条初始记录，再补充完整字段
- 需要等待下游任务执行完成后再做 DB 断言

### 15.8 可作为实习产出的表达方式

如果把这部分写成实习产出，可以重点强调：

- 该机制解决的是自动化测试中的最终一致性问题
- 采用统一轮询模型承接多种等待条件
- 通过时间、频次、间隔三个参数控制等待策略
- 把等待逻辑沉淀到框架层，避免每个测试用例重复写 `sleep + while` 的脏代码

这会比简单说“支持数据库查询”更有含金量。

## 16. 数据库高级应用逻辑整理

除了基础查库，当前项目中真正值得作为“高级应用逻辑”整理的有以下几个点。

### 16.1 用数据库校验异步业务链路最终状态

这是当前项目最强的高级应用场景。其本质不是“数据库访问”，而是“数据库作为最终状态验证面”。

典型链路：

- 调用被测接口
- 业务侧发消息或触发异步任务
- 下游消费并落库
- 测试用数据库等待机制校验最终状态

这种模式常用于：

- 订单状态变更
- 库存同步
- 补偿任务执行结果
- 审核流/任务流最终写库结果

### 16.2 数据库配置与 SQL 配置解耦

当前项目允许把 SQL 单独配置到属性文件，然后用 `ConfigManage.getValue()` 读取。这有几个好处：

- 测试代码不需要硬编码所有 SQL
- 同一套逻辑可以按环境替换 SQL
- 查询语句可以集中管理，便于维护

这对大型测试项目特别重要，因为数据库断言 SQL 往往会越来越多。

### 16.3 原生 SQL 与链式 API 并存

这实际上是一种实用主义设计：

- 简单场景直接写 SQL，快
- 复杂场景用链式 API，结构更清晰
- 两种方式最终都可以复用同一套等待和执行能力

这种设计兼顾了灵活性和可维护性。

### 16.4 查询结果既能直接断言，也能抽象成模型

对于简单断言，可以直接取：

- `Map<String, Object>`
- `JSONArray`

对于复杂断言，则可以映射成对象模型，提高语义清晰度。

这对测试框架来说很重要，因为它兼顾了：

- 快速验证
- 代码可读性
- 复杂字段断言能力

## 23. 最终结论

Mario 项目中的数据库部分，本质上是一套面向自动化测试的轻量数据访问与状态校验能力层。

它的重点不在于替代业务 ORM，也不在于承担数据库治理平台职责，而在于：

- 统一接入不同数据库类型
- 支持配置驱动的数据源切换
- 提供简洁的 SQL 查询与更新能力
- 通过对象映射提升测试代码可读性
- 借助异步落库等待机制解决最终一致性测试难题
- 在多数据源、分库分表场景中为自动化测试提供稳定支撑

如果你要把它转成实习产出，最值得重点强调的不是“会查数据库”，而是：

- 你理解了测试框架中的数据库基础设施设计
- 你能讲清楚异步落库验证链路
- 你能把多数据源、分库分表、等待机制、配置驱动这些内容整理成体系化文档

这会比单纯罗列 API 更像真正的工程产出。

## 24. 补充：异步等待机制的源码实现拆解

从源码实现上看，这套“异步落库等待”并不是单独写了一个轮询工具类，而是把等待参数、SQL 构建、SQL 执行、结果校验、超时退出几层逻辑串成了一条链路。整体设计思路是：

- 先把等待策略挂到当前 `PlatformSql` 上
- 在 `select/update/delete/setSql` 时，把等待配置复制到本次 SQL 对应的 `DBBase`
- 执行 `toJson()` / `build()` / `getInsertId()` 时，统一进入等待处理器
- 等待处理器不断调用 `DBService.runSql(base)` 轮询数据库
- 满足条件就返回，不满足就继续查，直到超时或超过频次

所以它本质上是一个基于 SQL 执行结果的条件轮询模型。

### 24.1 先看几个核心对象各自负责什么

#### 1）`Wait`：等待参数载体

`Wait` 是纯参数对象，里面放的是一次等待所需的全部上下文：

- 最长等待时间 `time`
- 最大轮询次数 `frequency`
- 每轮间隔 `intervalTime`
- 等待类型 `waitType`
- 条件字段 `waitKey`
- 结果数量条件 `siz`

也就是说，异步等待不是靠硬编码 `sleep`，而是把等待策略收敛成一个对象，后面所有流程都围绕这个对象来走。

#### 2）`DBWaitImpl`：等待条件配置入口

`DBWaitImpl` 本身并不执行 SQL，它主要负责“设置这次等待要怎么等”。

比如：

- `initWait(...)`：设置默认等待模板
- `waitdbNotNull()`：设置等待结果非空
- `waitdbEqual(key, value)`：设置等待某字段等于预期值
- `waitdbGreaterSize(size)`：设置等待结果数量大于某值

这层的职责可以概括成一句话：

- 不负责执行，只负责描述“我要等什么结果”

### 24.2 等待配置是怎么挂到一次 SQL 上的

这一层是 `PlatformSql` 在做。

`PlatformSql` 继承了 `DBWaitImpl`，所以它自己带着一份“当前等待策略”。当你开始执行 `select()` 时，它会把当前 `wait` 复制一份到新的 `DBBase` 里，然后把这次 SQL 的上下文也一起塞进去。

这里有两个关键点：

#### 第一，`DBBase` 是一次 SQL 的运行上下文

`DBBase` 里同时放了：

- 数据库连接对象 `db`
- 表名 `table`
- SQL 字符串 `sql`
- 查询条件 `where`
- 查询字段 `select`
- 插入/更新/删除信息
- 当前等待参数 `wait`

也就是说，等待不是脱离 SQL 独立存在的，而是作为 SQL 上下文的一部分被一起传递下去。

#### 第二，`init()` 的作用是“恢复默认等待模板”

`PlatformSql.select()` 在复制完当前等待配置后会调用一次 `init()`，它的本质是把 `super.wait` 重置回 `initWait`。

这意味着：

- `initWait(...)` 更像“默认模板”
- `waitdbEqual(...)` / `waitdbNotNull()` 更像“本次 SQL 的临时等待条件”
- 一次查询结束后，不会把临时等待条件污染到下一次查询

这个设计其实挺细的，说明作者有意识地区分了：

- 全局默认等待策略
- 当前一次查询的临时等待策略

### 24.3 真正触发等待执行的入口在哪里

真正开始执行等待，不是在 `waitdbNotNull()` 这种方法里，而是在 `DBBuild` 的这些终态方法里：

- `toJson()`
- `getInsertId()`
- `toList()`
- `toStr()`
- `toInt()`
- `build()`

这些方法都会先构建 SQL，然后统一交给 `WaitNotNullHandler.waitdb(dbBase)`。

这里很关键，说明源码里的真实执行顺序是：

1. 先通过 `TableHandler` 等把 SQL 拼好
2. 再进入等待处理器
3. 等待处理器内部循环执行 SQL 并判断条件
4. 最终返回查询结果

所以这套等待机制并不是“先查再额外等”，而是把等待直接内嵌进结果获取过程。

### 24.4 轮询核心：`WaitNotNullHandler.waitdb()`

这个类才是整个异步落库等待的核心实现。

一进来先执行一次 SQL，拿到：

- 当前 SQL 的首次查询结果 `jsonArray`
- 等待类型 `waitType`
- 需要比对的字段集合 `keys`
- 当前轮询次数 `frequency`
- 起始时间 `nowTime`

然后根据 `waitType` 进入不同的 `while` 逻辑。

#### 1）等待非空：`NOTNULL`

逻辑非常直接：

- 只要结果为空，就继续等
- 一旦查出数据，就返回

#### 2）等待字段相等：`KEY_EQUAL`

逻辑是：

- 如果没查到数据，继续查
- 查到了但字段值还不对，也继续查
- 直到字段值完全满足预期才返回

#### 3）等待数量变化：`SIZE_GREATER` 等

也就是把“结果集条数”作为轮询条件。

### 24.5 超时与退出机制是怎么做的

每轮等待时，都会走 `waits(...)` 或 `waitsNull(...)`，这里面负责两件事：

- 判断是不是超时/超频
- 决定要不要 `sleep`

也就是说它的退出条件有两个：

- 当前时间超过“起始时间 + 最大等待时间”
- 轮询次数超过 `frequency`

如果任一条件触发，就直接抛异常，把当前 SQL 和当前查询结果一起带出去，方便排查。

这点对测试排错挺重要，因为失败时不是只告诉你“超时了”，而是会把：

- 执行的 SQL
- 当时的数据库结果

一并带出来。

### 24.6 真正执行 SQL 的底层：`DBService.runSql()`

轮询里每次查库，底层都落到 `DBService.runSql(base)`。

对于非 `SELECT`：

- 执行更新
- 如果有自增主键，则把主键塞进 `JSONArray` 返回

对于 `SELECT`：

- 执行查询
- 把结果集统一转成 `JSONArray`
- 上层等待逻辑只面对一个统一结果结构，不必关心 JDBC 的 `ResultSet`

这就是它设计里很实用的一点：

- SQL 执行层负责把 JDBC 细节抹平
- 等待层只负责判断“结果是否满足条件”

层次分得比较干净。

### 24.7 整个调用链可以怎么理解

如果按源码真实调用链来画，大概是这样：

```text
DBUtil.getClient(prefix)
    -> 返回 DBClient / PlatformSql
    -> 先设置等待参数（initWait / waitdbEqual / waitdbNotNull ...）
    -> select / update / delete / setSql
    -> 生成 DBBase（里面包含 db + sql片段 + wait）
    -> DBBuild.toJson() / build() / getInsertId()
    -> TableHandler.opera(dbBase) 组装 SQL
    -> WaitNotNullHandler.waitdb(dbBase)
    -> DBService.runSql(dbBase)
    -> 判断结果是否满足 WaitType
    -> 满足则返回，不满足则继续轮询，直到超时
```

你可以把它理解成：

- `DBWaitImpl`：配置等待策略
- `PlatformSql`：把等待策略绑定到这次 SQL
- `DBBuild`：统一执行入口
- `WaitNotNullHandler`：轮询控制器
- `DBService`：实际查库执行器

### 24.8 这套设计的优点

#### 1）等待逻辑和 SQL 执行逻辑解耦

不是每种查询都自己写 `while + sleep + query`，而是统一收敛到等待处理器中。

#### 2）等待条件抽象得比较通用

不是只支持“等非空”，而是支持：

- 等结果有/无
- 等字段值变化
- 等结果数量变化

这对测试场景已经够用了。

#### 3）支持“默认模板 + 单次覆写”

`initWait()` 和 `waitdbXxx()` 的组合让等待策略既能复用，又能按当前 SQL 临时调整。

#### 4）结果结构统一

等待层只看 `JSONArray`，不直接碰 `ResultSet`，减少了复杂度。

### 24.9 从源码上看的一些实现细节和注意点

这个部分如果想写得更像“源码分析”，可以顺手强调下面几个点。

#### 1）`WaitHandler` 虽然有链式字段，但当前实现里基本没真正用起来

`WaitHandler` 里有：

- `private WaitHandler waitHandler;`
- `getWaitHandler()`
- `setWaitHandler()`

但当前真正执行业务时，核心还是直接 new 一个 `WaitNotNullHandler` 来跑，并没有看到完整的等待处理器责任链真正接起来。

所以它更像是：

- 预留了处理器链扩展位
- 当前主实现仍然是单处理器核心驱动

#### 2）源码语义上，等待条件更适合“先挂再 select”

从实现上看，`PlatformSql.select()` 会把当前 `super.wait` 复制进 `DBBase`。所以严格按源码语义，更合理的顺序其实是：

```java
DBUtil.getClient("default")
    .waitdbNotNull()
    .select("user")
    .select("id", "status")
    .where("id", "=", 123)
    .toJson();
```

也就是说，等待条件本质上是挂在 `PlatformSql` 上，然后在 `select()` 时拷贝到本次 SQL 上下文里。

#### 3）`KEY_NOTEQUAL` 的比较实现比较朴素

`waitsNotEqual()` 里用的是 `==` 比较对象引用，不是标准的 `.equals()` 语义。

这说明它更像是一个“够用型测试工具实现”，不是那种非常精雕细琢的通用库。

#### 4）频次判断略偏宽松

退出条件里写的是：

- `frequency >= base.getWait().getFrequency() + 1`

所以实际允许的轮询次数会比配置值略宽一轮。

这个点不一定要写进正式文档，但如果是做源码分析，提一句会显得看得比较细。

### 24.10 一句话总结这套异步等待机制

如果压缩成一句最适合写在总结里的话，可以这么写：

Mario 的异步落库等待机制，本质上是把等待参数抽象为 `Wait` 对象，并在 SQL 构建阶段绑定到 `DBBase` 上下文中，最终由 `WaitNotNullHandler` 统一驱动轮询执行与条件判断，通过 `DBService.runSql()` 反复查库，直到结果满足条件或超时退出，从而解决自动化测试中最终一致性带来的误判问题。
