## 1. 背景与起源：为什么不能直接用原生 Redis

在正式介绍 Squirrel 之前，你可能会有一个很自然的疑问：**Squirrel 这么好用，为什么美团还要自己再造一个缓存系统？直接用开源的 Redis Cluster 不就行了吗？**

这个问题问得非常好，我们先站在一个业务研发工程师的视角想一想。假如你现在负责一个日活几千万的业务，比如外卖平台的商品详情页服务，你需要用缓存来抗住数据库压力。你打开 Redis 官网，下载了 Redis，自己搭了一个三主三从的 Redis Cluster。看起来一切正常，直到有一天凌晨三点，你的手机突然响了——报警短信告诉你，其中一台 Redis 主节点所在的物理机宕机了。

这时候你会遇到一连串的现实问题：

- **谁来发现这个节点挂了？** 需要有一套监控系统 7x24 小时盯着几千个 Squirrel 实例的健康状态。
- **谁来把流量切走？** Redis 官方的故障转移（Failover）需要经过 Gossip 协议在集群内传播信息，一般至少要 30 秒才能把一个节点标记为 FAIL 并完成主从切换。这 30 秒里，业务请求会持续报错。
- **谁来补一个新的从节点回去？** 一主两从的结构，如果从节点没了要不要重新拉一个新实例加进集群？这个操作需要有专门的自动化平台来做，否则就要运维工程师半夜手动处理。
- **如果要扩容怎么办？** 业务量涨了，内存不够用了，需要往集群里加节点、迁移 Slot（哈希槽），这个过程如果做得不好，会导致业务请求大量超时甚至丢数据。
- **如果某个 Key 突然变成热点怎么办？** 比如一场秒杀活动，某个库存 Key 每秒被访问几十万次，这个 Key 所在的那台物理机的 CPU、网卡都会被打满，进而拖累同一个分片上的所有其他 Key。

这些问题，**原生 Redis 开源版本本身是不提供解决方案的**——它只提供了"能用"的能力，但不提供"稳定、可靠、自动化运维、可观测"的能力。而这些恰恰是企业级场景下最重要、最消耗人力成本的部分。

美团内部对这个问题有一个非常精炼的总结，业务研发工程师直接使用开源缓存系统，通常会撞上三堵墙：

1. **可用性差**：开源系统的高可用体系不完善，普通业务研发工程师并不具备专业的存储运维能力，所以系统实际跑起来的可用性往往达不到预期。
2. **性能有瓶颈**：开源系统在设计的时候，很少会针对"美团体量"这种超大规模场景做优化，业务规模一旦上去，很容易撞到性能天花板。
3. **扩展性弱**：开源系统在弹性扩容方面能力有限，扩容往往会导致集群短暂不稳定，进而影响到线上业务。

给你一个数字体感：Squirrel 目前在美团内部的接入应用数已经超过 **8000 个**，覆盖了公司几乎所有的事业群，集群数量接近 **5000 个**，服务端整体日均调用量超过 **62 万亿次**。在这个体量下，如果每个业务团队都各自维护一套 Squirrel 集群，光是故障处理和运维成本就会是天文数字。这就是为什么美团需要在开源 Redis 之上，构建一个"企业级"的缓存服务——这正是 Squirrel 诞生的初衷。

值得一提的是，美团的 KV 存储演进其实经历了三个阶段：

- **第一代：客户端一致性哈希 + Memcached**。客户端做哈希路由，后端部署大量 Memcached 实例。问题很明显：一旦某个节点宕机被摘除，这个节点上的数据就直接丢了；扩容的时候一致性哈希也会导致数据错乱。
- **第二代：一致性哈希 + Redis 主从 + 哨兵**。引入了 Redis 的主从复制和哨兵机制，节点挂了可以自动切换，但扩缩容依然会因为一致性哈希丢数据的问题没有得到根本解决。
- **第三代：基于 Redis Cluster 自主演进的 Squirrel**。2015 年 Redis 官方发布了正式的集群版本 Redis Cluster，美团紧跟社区步伐，在这个基础上结合自己的业务场景做了大量二次开发，最终演进出了今天的 Squirrel。

## 2. Squirrel 是什么：一句话讲清定位

用一句话来说：**Squirrel 是美团基础架构团队基于 Redis Cluster 二次开发的高可用、高性能、易扩展的纯内存分布式 KV 缓存系统。**

拆开这句话，有几个关键词你需要理解：

- **"基于 Redis Cluster"**：这意味着 Squirrel 的内核依然是 Redis，兼容 Redis 的数据结构（String、Hash、List、Set、SortedSet）和大部分命令，你如果会用 Squirrel，学习成本很低。
- **"二次开发"**：Squirrel 不是简单地部署了几百套 Redis Cluster，而是在 Redis 源码层面做了大量优化（比如持久化机制重构、迁移算法优化），并且在 Redis Cluster 之外新增了一整套调度、监控、高可用、迁移的服务体系。
- **"纯内存"**：数据全部放在内存里，这是 Squirrel 保持极低延迟的根本原因，但也意味着它的成本比"内存+磁盘"混合型存储要高得多，因此不适合存储超大规模数据。
- **"分布式"**：数据是分片（Sharding）存储在多台机器上的，通过 16384 个哈希槽（Slot）来实现数据的均匀分布和水平扩展。

Squirrel 明确适用于**对延迟要求极高（TP99 < 10ms）且数据总量在 500GB 以内**的缓存场景。具体来说，官方推荐的典型场景包括：

- 对延迟极度敏感的基础公共服务，比如账号信息缓存；
- 突发流量场景，比如热点视频、热搜词；
- 大型促销秒杀系统、库存计数系统；
- 需要特殊数据结构的场景，比如用 SortedSet 实现排行榜，用 Bit 实现布隆过滤器/签到统计。

反过来，以下场景**不建议**用 Squirrel：

- 数据总量特别大，比如超过 500GB（纯内存存储，成本会爆炸）；
- 单个 Value 超过 1MB（大 Value 会拖慢整个 Squirrel 的单线程处理能力）；
- 对数据可靠性要求极高、任何情况下都不能丢数据的场景（比如支付流水，这种场景应该用持久化存储，见后文 Cellar 部分）。

给你一个成本的直观感受：Squirrel 的资源成本大约是 **100 元/GB/年**，而它的姊妹系统 Cellar（持久化 KV 存储）只要 **20 元/GB/年**。这个 5 倍的成本差距，本质上就是"纯内存"和"内存+磁盘混合"两种存储介质之间的成本差异，这也是为什么 Redis 官方反复强调它只适合"数据量小、延迟敏感"的场景——用它来存海量数据，账算下来是不划算的。

## 3. 整体架构：Proxy 层？不，Squirrel 走的是另一条路

如果你之前了解过一些分布式缓存方案（比如 Twitter 的 Twemproxy、豌豆荚的 Codis），你可能会下意识地认为分布式 Squirrel 集群一定需要一个 Proxy 层来做请求转发。但 Squirrel 选择的架构路线不太一样——它是**基于 Redis Cluster 官方的去中心化（无 Proxy）架构**，客户端直连存储节点，在这个基础之上叠加了一套独立的"控制面"来做集群管理。

先看一下整体的架构图（这是根据技术团队分享内容整理的示意）：

这套架构可以拆成四个部分来理解：

**（1）存储层——Redis Cluster 本身**

中间的存储层其实就是标准的 Redis Cluster：多个分片（Shard），每个分片由一主多从组成，主从之间通过 Gossip 协议互相通信，感知彼此的健康状态。这一层跟你自己手搭一套 Redis Cluster 没有本质区别。

**（2）控制面——集群调度平台**

这是 Squirrel 相比原生 Redis Cluster 最大的增量部分。它包含调度服务、扩缩容服务、HA（高可用）服务等模块，负责实时监控集群里所有节点的状态，一旦发现异常（网络抖动、宕机等），会主动介入处理，并把处理结果作为最新的集群元数据写入 ZooKeeper。

**（3）元数据层——ZooKeeper**

ZooKeeper 在这里承担的角色是"集群拓扑的真相来源"，存储了 Slot 到节点的映射关系、节点的健康状态等信息。客户端启动后会订阅 ZooKeeper 上的元数据变更，一旦集群拓扑发生变化（比如某个节点被摘除、新节点加入），客户端能够实时感知并更新本地路由表，而不需要重启应用。

**（4）客户端 SDK**

业务应用通过标准的 Redis 客户端直连 Squirrel 存储节点进行读写，不经过任何中间代理层，这也是 Squirrel 能做到极低延迟（平均时延 < 0.7ms，TP99 < 10ms）的关键原因——因为省掉了 Proxy 转发这一跳的网络开销。

**（5）监控与运维能力**

在这套架构之外，Squirrel 还额外提供了慢查询分析、应用鉴权、热点 Key 自动治理、智能数据迁移、跨机房数据同步等一整套企业级运维能力，这些内容我们会在后面的章节详细展开。

## 4. 核心概念：集群、Category、AppKey、配额

如果你是第一次接触 Squirrel，下面这几个概念你必须先搞清楚，否则看后面的接入流程会一头雾水。

### 4.1 集群（Cluster）

集群是 Squirrel 资源分配的最小物理单位，一个集群对应一套独立部署的 Redis Cluster。**Squirrel 按照业务线来划分集群**——也就是说，不同的业务线（比如"外卖商品"、"酒店订单"）通常会有自己独立的集群，而不是所有业务共用一个巨大的集群。

为什么要这样设计？想象一下，如果全公司所有业务都挤在同一个集群里，一旦某个业务写入了一个超大的 Value 或者产生了热点 Key，影响的就不是这一个业务，而是集群里的所有业务——这就是典型的"噪声邻居"问题。通过按业务线拆分集群，Squirrel 实现了物理层面的资源隔离，一个业务出问题不会波及其他业务。

申请一个新集群时，你需要提供的信息包括：业务归属地、事业群/业务线、集群部署位置、服务等级、是否涉及现金交易、容量预估、峰值 QPS 预估、读写分布比例、客户端类型、集群名称、是否开启持久化等。这些信息会被用来做资源规划和后续的运维管理。

### 4.2 Category（分类）

如果说集群类似于"数据库实例"，那么 **Category 就类似于数据库里的"表"**。在同一个集群里，不同业务模块可以申请不同的 Category 来隔离数据，Category 支持独立的权限管理和批量清理（相当于清空整张表）。

Squirrel 对存储 Key 的结构做了统一的规范，最终存到 Squirrel 里的 Key 字符串结构是：

```
${category}.${template}_${version}
```

举个具体例子：假设你申请了一个 Category 叫 `walle`，Template（模板）定义为 `c{0}d{1}`，那么在代码里这样使用：

```java
// StoreKey 的构造函数接受 category 和若干个模板参数
StoreKey key = new StoreKey("walle", 1, 1);
// 最终落到 Squirrel 里的真实 Key 大致类似：walle.c1d1_v1
```

这里的 `template` 类似于数据库里"列"的概念，用来定义 Key 的组成规则，可以有效避免不同业务模块之间 Key 冲突或者裸写字符串拼接导致的混乱。

### 4.3 AppKey 与应用鉴权

AppKey 是美团内部标识一个应用身份的唯一凭证，每个服务在美团的服务目录（Service Catalog）里都有自己的 AppKey。Squirrel 在新版本中引入了**基于 AppKey 粒度的访问鉴权机制**：集群管理员需要在管理平台的"应用鉴权"页面里，把允许访问这个集群的 AppKey 显式注册进去，没有注册的应用（可能是配置错误、误连接、甚至是恶意访问）会被直接拒绝。

这跟原生 Redis 只有一个全局密码（`requirepass`）的鉴权方式完全不是一个维度——AppKey 鉴权能做到"哪个具体的应用在访问我的集群"这种精细化的可观测和权限控制，这对于一个有几千个集群、上万个应用接入的平台来说是必需的安全能力。

### 4.4 配额管理

由于 Squirrel 是纯内存存储，资源成本高昂（100 元/GB/年），公司必须对每个业务的资源使用量做精细化管理，这就是配额（Quota）管理的意义所在。每个集群在申请的时候都要填写容量预估、QPS 预估，平台会根据这些信息分配对应的机器资源；Category 也有内存上限（比如线下环境的 Category 默认限制 1GB），超过限制会拒绝写入。这套配额体系配合计费系统，使得资源使用和成本能够精确分摊到具体的业务和 AppKey 上。

## 5. 数据分布原理：一个 Key 是怎么找到自己的家的

理解了基本概念之后，我们来看一个更底层的问题：当你调用 `client.set("some_key", "some_value")` 的时候，这个 Key 到底是怎么知道该往哪台机器上写的？

Squirrel（以及它的兄弟系统 Cellar）采用了业界经典的**哈希槽（Hash Slot）分片方案**：

1. 整个集群预先划分好 **16384 个槽位（Slot）**，编号从 0 到 16383。
2. 每个 Master 节点负责其中一部分连续或不连续的 Slot，尽量保证每个节点负责的 Slot 数量均摊。
3. 客户端对某个 Key 做操作时，先用公式 `HASH_SLOT = CRC16(key) mod 16384` 算出这个 Key 归属的 Slot 编号。
4. 客户端本地维护了一张"Slot → 节点"的路由表（这张表是通过解析 `CLUSTER NODES` 或 `CLUSTER SLOTS` 命令得到并缓存在本地的），查表得知这个 Slot 在哪个节点上，然后直接与该节点建立连接进行读写。

**写请求一定会先落到 Master 节点**，然后再异步复制给它的 Slave 节点；**读请求**则会根据你配置的"路由策略"来决定具体连接哪个节点。Squirrel 提供了三种典型的读策略：

| 读策略 | 行为 |
| --- | --- |
| `master-only` | 所有读写都只走主节点，数据最新但主节点压力最大 |
| `master-slave` | 读请求可以打到主节点或从节点（优先同机房），兼顾数据新鲜度和负载均衡 |
| `slave-only` | 读请求只打到从节点，最大化保护主节点的写入性能，但读到的数据可能有轻微延迟 |

这几种策略之上还叠加了"同机房优先"（`idcSensitive`）和"同城优先"（`regionSensitive`）的路由规则：策略优先级是"读策略 > 同机房路由策略"，如果按照当前策略筛选不出候选节点，就退回到上一级策略的候选集合里去找。这套设计的目的是尽可能让请求落在离客户端物理距离最近的节点上，从而降低网络延迟。

### 5.1 扩容和缩容时数据怎么迁移

当业务量增长，你需要给集群扩容时，Squirrel 会经历"加节点"和"数据迁移"两个阶段：

1. 通过美团内部的弹性伸缩系统 Hulk，可以做到新节点的**秒级扩容**（本质上是拉起一个新的容器实例）。
2. 新节点加入集群后，需要通过数据迁移服务，把一部分 Slot 从老节点迁移到新节点，重新达到负载均衡。这个迁移过程一般需要 5~30 分钟，具体取决于集群规模和数据量。

在迁移过程中，Slot 会经历几种中间状态：迁出的节点把 Slot 标记为 `MOVED`（表示这个 Slot 的归属已经永久转移给新节点），迁入的节点把 Slot 标记为 `IMPORTING`（open 状态）。如果客户端在迁移过程中恰好访问了一个"部分 Key 已迁走、部分还在原地"的 Slot，源节点会先在本地查一次，查不到就返回一个 `ASK` 错误，告诉客户端"去目标节点问问看"。客户端遇到 `MOVED` 或 `ASK` 错误时，会重新拉取一次完整的路由表，刷新本地缓存。

Squirrel 在这个官方机制的基础上做了大量优化：

- **迁移速度动态调节**：借鉴 TCP 慢启动的思路，迁移服务会实时采集客户端的成功率、耗时以及服务端负载、QPS 等指标，根据这些反馈动态调整迁移速度——一开始速度较慢，逐步提速，一旦发现业务请求成功率下降就立刻降速，最终在一个"动态平衡点"稳定下来，做到既快又不影响线上业务。
- **异步 Migrate 命令**：原生 Redis 的 `MIGRATE` 命令在处理大 Value 时会阻塞主线程很久。Squirrel 实现了异步版本，迁移大 Value 时主线程可以继续处理其他正常请求，如果这期间有针对正在迁移的 Key 的写请求，会直接返回错误，最大限度保证不阻塞正常流量。

## 6. 高可用设计：从节点宕机到跨机房容灾

高可用是 Squirrel 花费最多精力去打磨的能力，因为这直接对应了本文开头提到的那个痛点——"我用了缓存服务，但总担心它挂了影响我的系统"。我们分宏观（容灾）和微观（端到端成功率）两个维度来看。

### 6.1 单节点宕机的自动化处理

原生 Redis Cluster 对节点宕机已经有一套机制：一个节点从宕机到被标记为 `FAIL` 并摘除，一般需要经过约 **30 秒**（这是为了避免网络抖动造成的误判，Gossip 协议需要多个节点达成共识）。

但 Squirrel 团队认为，对于**从节点**（Slave）而言，这 30 秒完全没必要——因为从节点宕机并不影响数据完整性（主节点上数据还在），完全可以做得更快。为此，Squirrel 单独实现了一套 **HA 高可用服务**，它的工作机制是：

1. HA 服务实时监控集群内所有节点，一旦发现某个从节点异常（网络抖动或真的宕机），会立刻更新 ZooKeeper，把这个节点从可用列表里摘除。
2. 客户端订阅了 ZooKeeper 的元数据变更，几乎实时收到通知，把读流量路由到集群里其他健康的从节点上。
3. 如果只是短暂的网络抖动（几十秒内恢复），HA 服务检测到节点恢复后，会重新把它加回集群。
4. 如果经过一段观察期后判断这是一次**永久性宕机**，HA 服务会直接向 Hulk 集群申请一个新的容器实例，自动把它加入集群，重新形成"一主两从"的标准拓扑结构，然后更新 ZooKeeper 并通知客户端更新路由。

通过这套设计，Squirrel 把从库的摘除时间从官方的 30 秒**降低到了 5 秒**，并且把"宕机后补副本"从需要人工介入的操作，变成了一个**分钟级、完全自动化**的过程。

### 6.2 三机房部署与脑裂防护

高可用不仅要考虑单节点故障，还要考虑整个机房级别的故障（比如机房断电、网络中断）。Squirrel 支持**三机房部署**：一个分片的主从节点会平均分布在三个不同的机房里，一旦其中一个机房整体不可用，另外两个机房的节点依然能够正常提供服务，不影响业务。

这里有一个很重要的细节问题需要展开讲一下：**脑裂（Split-Brain）**。假设你只用两个机房部署（而不是三个），一旦两个机房之间的网络中断，两边都会认为"对方挂了，我要选出新的主节点"，结果就是两个机房里同时存在两个"自认为是主"的节点，都在接受写入，数据产生了分叉——这就是脑裂，是分布式系统里最危险的故障场景之一。

Squirrel 给出的解法：

- **架构层面优先用三机房部署**：三机房架构能保证任何一个机房内的 Master 数量不会超过总数的一半。当某个机房断网时，机房内部由于 Master 数量不足法定人数，会主动拒绝所有写请求，从而从根本上避免脑裂。
- **两机房部署引入见证者（Witness）机制**：如果条件所限只能用两机房，可以引入一个不存储数据、只参与选主投票的"见证者"节点来打破平局。
- **SET 化架构**：把每个 SET（业务的一个逻辑分组）都做成单机房部署，SET 之间互相独立，一个机房断网只影响这个机房内的 SET，不会引发跨机房的脑裂问题。
- **业务侧兜底**：如果架构层面依然存在残余的脑裂风险，业务方需要意识到"存到 Squirrel 里的数据一致性要求不能太高"，并且最好有能从 MySQL 或 Cellar 里重建数据的兜底手段。

### 6.3 跨地域容灾与异地多活

如果说三机房容灾解决的是同城范围内的故障，那么**跨地域容灾**要解决的是更极端的场景，比如整个城市的机房都不可用。

跨地域场景面临的现实约束跟同城机房完全不同：跨地域专线的网络质量远不如同城机房间的内网稳定，而且专线带宽非常有限且昂贵。如果简单粗暴地让主库直接给多个异地从库做复制，会浪费大量的专线带宽（比如同一份数据要在北京—上海专线上传输两次）。

Squirrel 为此设计了**集群间复制方案**：在两个物理隔离的集群之间，通过一个专门的同步服务（`redis-keeper-service`）建立同步链路。这个同步服务会伪装成 Redis 的 Slave，通过标准的 Redis 复制协议从主集群的从库上拉取 RDB 全量数据和后续的增量变更，再把这些数据转换成写命令，写入到目标集群的主节点里。如果要实现异地多活，只需要再建一条反方向的同步链路，就能形成双向同步。

## 7. 一致性保障：缓存与数据库如何"对得上账"

前面讲的都是 Squirrel 自身的高可用，但作为一个使用方，你可能更关心一个更贴近日常开发的问题：**缓存里的数据和数据库里的数据不一致了怎么办？**

### 7.1 主从数据一致性：Squirrel 选择了"弱一致性"

首先要明确一点：Squirrel 的主从复制是**异步**的，也就是说主节点写成功之后，会立即返回给客户端，然后再把这条写命令异步同步给从节点。这意味着在某个极短的时间窗口内（正常情况下是**毫秒级**，取决于主从网络和节点负载），主从之间的数据是不一致的。

为什么 Squirrel 要选择"弱一致性"而不是"强一致性"？答案很直接：**性能**。如果每次写入都要等待所有副本确认（同步复制），写入延迟会大幅增加，这与 Squirrel"低延迟、高吞吐"的核心定位是相悖的。所以官方的态度非常明确：**Squirrel 只保证最终一致性，副本间的数据复制是异步进行的**——如果你的业务场景要求线性一致（比如用它实现分布式锁），必须自行设计降级方案，业务逻辑层面也要能容忍偶发的不一致。

### 7.2 缓存与数据库的一致性：Cache-Aside 模式与双删策略

这是几乎每个使用缓存的业务都会遇到的经典问题。美团内部对这块的实践总结得相当系统，我们完整地过一遍。

业界最常用的缓存更新模式是 **Cache-Aside（旁路缓存）模式**：应用方自己负责缓存和数据库的读写逻辑，规则很简单：

- **读请求**：先读缓存，命中就直接返回；没命中就查数据库，把结果写入缓存后再返回。
- **写请求**：先更新数据库，然后把缓存中对应的数据**删除**（注意：是删除失效，而不是直接更新缓存值）。

这里必然会引出两个新手常问的问题：

**问题一：为什么写请求不是"先删缓存，再更新数据库"，而是"先更新数据库，再删缓存"？**

假设你先删缓存、再更新数据库，考虑下面这个并发场景：

```
时间线：
t1: 写请求A 删除缓存（成功）
t2: 读请求B 读缓存 → 未命中 → 查询数据库（此时数据库还是旧值）→ 把旧值写回缓存
t3: 写请求A 继续把新值写入数据库

结果：数据库是新值，但缓存里被B错误地重新种回了旧值，并且会一直脏下去，
      直到这个Key过期或者下一次写操作。
```

而如果换成"先更新数据库、再删缓存"，虽然理论上也存在极小概率的并发窗口问题，但风险要小得多，也是业界的主流实践。

**问题二：为什么写操作是把缓存"删除"（失效），而不是直接把缓存"更新"成新值？**

如果写操作直接更新缓存，同样存在并发问题：

```
时间线：
t1: 写请求A 更新数据库为值X
t2: 写请求B 更新数据库为值Y，并立即更新缓存为Y
t3: 写请求A 姗姗来迟地把缓存更新为X

结果：数据库最终值是Y，但缓存里却是X，产生了脏数据。
```

除此之外，直接更新缓存还违背了"懒加载"的设计初衷——很多写多读少的 Key，你辛辛苦苦每次写入都同步更新缓存，结果这个 Key 可能压根没有人读，等于白白浪费了计算资源。所以更合理的做法是写请求只负责让缓存失效，真正的缓存值由下一次读请求触发时"按需"重新加载。

**双删策略（延迟双删）**：即便遵循了"先更新数据库、再删缓存"的原则，依然存在一个经典的竞态条件——线程 A 正在读缓存未命中、准备去查数据库回填的过程中，线程 B 恰好完成了"更新数据库 + 删缓存"的操作，随后线程 A 才把从数据库里查到的**旧值**写回了缓存，导致缓存里长期存在脏数据。

针对这种场景，业界（也是美团内部缓存测试规范里明确要求验证的场景）给出的标准解法是**延迟双删**：

```
写请求的完整流程：
1. 先删除缓存
2. 再更新数据库
3. 休眠一小段时间（比如几百毫秒，覆盖读请求的典型执行时间）
4. 再次删除缓存（这是"延迟"的那一次删除，用来清掉步骤2和3之间，
   可能被并发读请求重新回填进去的脏数据）
```

延迟的时间通常需要结合业务的读请求平均耗时来评估，一般设置为比读请求平均处理时间稍长一点。当然，延迟双删并不是银弹，它只是把不一致的概率降到足够低，并没有做到理论上的强一致；如果业务对一致性要求非常高，还是建议引入分布式锁或者消息队列做异步重试删除。

**缓存删除失败怎么办？** 这也是容易被忽视的一个环节：如果第二次删除缓存的操作因为网络抖动等原因失败了怎么办？标准做法是**捕获异常后，把"删 Key 任务"放入消息队列或者重试表，进行异步重试，直到确认删除成功为止**，而不是简单地吞掉这个异常。

### 7.3 一致性方案的选型总结

| 一致性要求 | 推荐方案 |
| --- | --- |
| 极致性能优先，容忍短暂不一致 | Cache-Aside + 设置合理的 TTL 兜底 |
| 中等一致性要求 | Cache-Aside + 延迟双删 |
| 高一致性要求 | Cache-Aside + 延迟双删 + 分布式锁/消息队列兜底重试 |
| 极高一致性要求（如金融支付） | 不建议使用 Squirrel，应使用支持强一致复制（Raft）的持久化存储，如 Cellar |

## 8. 缓存三大杀手：穿透、击穿、雪崩的防护方案

除了一致性问题，使用分布式缓存还必须面对三个经典的"杀手场景"，这三个词几乎是缓存领域面试必考题，我们逐一讲清楚它们的区别和应对方案。

### 8.1 缓存穿透（Cache Penetration）

**现象**：大量请求查询的是数据库里根本不存在的数据（比如恶意攻击者故意构造一批不存在的商品 ID 来请求）。由于数据库里没有这条数据，缓存自然也不会有，于是每一次请求都会绕过缓存，直接打到数据库上，如果请求量足够大，数据库可能被打垮。

**解决方案**：
- **布隆过滤器（Bloom Filter）拦截**：布隆过滤器是一种利用 Bit 数组和多个哈希函数来判断一个元素"一定不存在"或"可能存在"的概率型数据结构。把数据库中所有存在的 ID 提前灌入布隆过滤器，查询缓存之前先过一遍布隆过滤器，如果过滤器判断"一定不存在"，直接拒绝这次查询，根本不去查数据库。Squirrel 提供的 Bit 数据结构原生就可以用来实现布隆过滤器。
- **空值缓存**：对于确认数据库里不存在的 Key，把一个"空值"（比如一个特殊的哨兵值）也写入缓存，并设置一个比较短的 TTL（比如几十秒到几分钟）。这样后续同样的无效查询会命中这个空值缓存，而不会再打到数据库。

### 8.2 缓存击穿（Cache Breakdown）

**现象**：某一个访问量极高的热点 Key（比如一个爆款商品的详情），在缓存中恰好过期的那一瞬间，会有海量并发请求同时穿透缓存去查询数据库，瞬间给数据库造成很大压力。它和"穿透"的核心区别在于：穿透是查询不存在的数据，击穿是查询一个原本存在但恰好过期的热点数据。

**解决方案**：
- **互斥锁**：热点 Key 过期时，只允许第一个发现缓存未命中的请求去查询数据库并回填缓存，其他并发请求原地等待（或者短暂重试），等缓存被回填后再从缓存里读取，而不是让所有请求一拥而上去查数据库。
- **逻辑过期**：给热点数据设置一个"逻辑过期时间"字段，缓存本身永不过期。当发现逻辑过期时间已到时，返回旧数据的同时，异步触发一次后台任务去更新缓存，用户几乎感知不到延迟，数据库也不会被瞬间打垮。

### 8.3 缓存雪崩（Cache Avalanche）

**现象**：大量 Key 在同一时间点集中失效（比如业务代码里给一批 Key 设置了同样的固定 TTL），导致某个时间点大量请求同时穿透缓存打到数据库，造成数据库负载瞬间飙升甚至宕机，这是范围最大、也最危险的场景。

**解决方案**：
- **过期时间加随机抖动**：给 TTL 加上一个随机值（比如基础过期时间 30 分钟，再加上 0~5 分钟的随机偏移量），避免大批 Key 在同一时刻集中失效。
- **多级缓存兜底**：本地缓存（如 Caffeine）+ 分布式缓存（Squirrel）的多级架构，即使分布式缓存层出现问题，本地缓存依然能顶住一部分流量。
- **服务端限流和熔断**：Squirrel 新版本在服务端增加了限流能力，避免在极端流量场景下集群被彻底打垮；同时业务方应该在数据库前端配置好熔断降级策略，作为最后一道防线。

下面用一张表总结三者的区别，方便你记忆：

| 场景 | 请求的数据 | 触发原因 | 核心解决思路 |
| --- | --- | --- | --- |
| 缓存穿透 | 数据库中不存在的数据 | 恶意攻击或参数校验缺失 | 布隆过滤器 + 空值缓存 |
| 缓存击穿 | 单个热点 Key 恰好过期 | 高并发对同一 Key 的访问 | 互斥锁 + 逻辑过期 |
| 缓存雪崩 | 大批量 Key 同时过期 | TTL 设置不合理、集中失效 | 过期时间加随机抖动 + 多级缓存 + 限流熔断 |

## 9. 热点 Key 与大 Key 治理

这一节我们单独讲讲 Redis 官方在架构层面（而不仅仅是业务代码层面）是怎么应对热点 Key 和大 Key 问题的，这是它区别于"自己裸搭 Squirrel"的另一个重要能力。

### 9.1 热点 Key 的自动发现与隔离

想象一个场景：某场大促活动，一个爆款商品的库存 Key 每秒被读取几十万次。在标准的 Redis Cluster 架构下，这个 Key 所在的那个 Slot、进而是那台物理机，会承受远超其他节点的流量压力，CPU 和网卡都可能被打满，进而拖慢**同一分片上其他毫不相关的 Key** 的访问——这就是所谓的热点 Key 问题。

Squirrel 的解决思路是"实时发现 + 自动隔离"：

1. 每个 Squirrel 节点在处理正常读写请求的同时，会对 Key 的访问量、带宽占用做实时统计。
2. 一旦某个 Key 的访问量或带宽占用超过阈值，节点会**自动触发流控**，限制对这个 Key 的访问速率，防止节点被彻底打满。
3. 与此同时，Squirrel 的监控服务会周期性地扫描所有节点上统计到的热点 Key 信息，一旦发现热点，会把这个热点 Key 所在的 Slot 上报给迁移服务。
4. 迁移服务会在集群里额外准备一组"热点主从节点"（游离于正常分片结构之外，专门用来承接热点流量），把这个热点 Slot 迁移过去。由于热点主从上只承载这一个热点 Slot 的请求，处理能力得到大幅提升。

通过这套机制，Squirrel 做到了**实时热点监控、及时流控止损，并配合自动化的热点隔离和快速容量扩充**，业务方基本不需要感知这个过程，也不需要在代码里做特殊处理。

### 9.2 大 Key 的危害与处理

**大 Key** 通常指的是：一个简单字符串（String）的 Value 超过 5KB；或者一个复杂数据结构（Hash、List、Set）里的元素数量超过 1000 个（如果每个元素平均是 1KB，那这一个 Key 的总大小就已经达到 1MB）。

大 Key 的危害是多方面的：

1. **阻塞主线程**：Redis 是单线程模型处理命令的，`GET` 一个超大 Value 会独占处理线程和网络输出缓冲区较长时间，期间其他请求都要排队等待。
2. **数据倾斜**：如果集群里有的节点存了很多大 Key，有的节点几乎没有，会导致节点间的内存使用非常不均衡。
3. **网卡瓶颈**：如果一个大 Value 同时还是热点 Key，会对存储该 Key 的物理机网卡带宽造成巨大压力，这是最糟糕的组合。

Squirrel 客户端在协议层面直接对单个 Value 的大小做了硬性限制：**超过 1MB 会直接抛出 `StoreBigValueException` 异常**，从源头上拦截明显不合理的大 Value 写入。对于批量操作，也有个数限制：`pipeline` 操作上限是 512 个 Key，`multiGet` 上限是 1024 个 Key，用来避免一次批量请求占用过多的服务端资源。

如果业务确实有存储较大数据的需求，官方建议使用"大 Value 多 Value 分拆方案"——把一个大 Value 按照某种规则（比如分页、分片）拆分成多个较小的 Key 分别存储，读取时再由客户端做合并，从而避免单个 Key 过大带来的一系列问题。

## 10. 与 Cellar 的关系和区别：兄弟系统怎么分工

在美团的存储技术栈里，Squirrel 从来不是孤立存在的，它有一个"孪生兄弟"——**Cellar**，两者都是基础架构团队自研的 KV 存储系统，但定位截然不同，理解它们的分工对你做技术选型至关重要。

### 10.1 一句话区分

- **Squirrel**：基于 Redis Cluster 改进的**纯内存型** KV 存储，定位是"缓存"，适合小容量、延迟敏感的场景。
- **Cellar**：基于阿里开源 Tair 改进的**内存+硬盘混合引擎**持久化 KV 存储，定位是"存储"，适合大容量、要求数据可靠性的场景。

一个很形象的类比：Squirrel 更像是你书桌上的一个小抽屉，拿取速度极快，但空间有限，东西可能会被意外碰掉；Cellar 更像是一个大仓库，空间几乎无限，东西放进去基本不会丢，但每次去取需要多走两步路。

### 10.2 详细对比表

| 对比维度 | Squirrel | Cellar |
| --- | --- | --- |
| 底层技术演进基础 | Redis Cluster（开源社区活跃，持续迭代） | 阿里开源 Tair（已停更，完全靠美团自研迭代） |
| 存储引擎 | 纯内存 | 内存 + 硬盘混合引擎 |
| 数据容量上限 | 单集群最大约 1.5TB，建议不超过 300GB | 内存+硬盘引擎，容量可近乎无限扩充（PB 级） |
| 平均时延 | < 0.7ms | 1-2ms |
| TP99 时延 | < 10ms（官方目标 < 6ms） | < 20ms |
| 数据可靠性 | 用户可选是否开启持久化，副本间弱一致（最终一致） | 强，有持久化存储，支持 Raft 强一致复制，最高可达 11 个 9 |
| 支持数据结构 | String, List, Hash, Set, SortedSet | String, HashMap, List, Set |
| 成本 | 约 100 元/GB/年 | 约 20 元/GB/年 |
| 极限负载稳定性 | 新版本支持服务端限流 | 支持过载保护、防雪崩 |
| 适用场景 | 延迟极敏感、数据量小、复杂数据结构（元素数 > 1000）需求 | 数据规模大、不能容忍数据丢失（如订单、金融支付） |
| 业界对标 | 腾讯 Tendis、Codis、阿里云 Squirrel | Amazon DynamoDB、阿里 Tair、腾讯 PaxosKV |

### 10.3 架构上的关键差异

除了上表列出的这些表层差异，两者在架构设计的哲学上也有明显不同，这一点在美团内部技术分享中讲得很清楚：

- **Squirrel 走的是"官方兼容"路线**：因为 Squirrel 社区非常活跃，Squirrel 的策略是"自研和社区并重"，尽量与官方架构保持兼容，这样能持续享受到社区的技术红利。
- **Cellar 走的是"完全自研"路线**：因为 Tair 的开源版本已经停止更新多年，Cellar 的所有后续演进（比如引入 Raft 协议做强一致复制、引入 ZooKeeper 做分布式仲裁解决脑裂）完全依靠美团自己的团队完成，这也使得 Cellar 在架构改动上可以更加自由，比如它引入了 OB（类似 ZooKeeper 的 Observer）节点来隔离路由查询和集群管理，Squirrel 则没有这个设计。

### 10.4 什么时候该选谁

给你一个简单的决策流程：

```
是否需要复杂数据结构（Map/Set），且元素数量可能超过1000个？
  是 → 优先考虑 Squirrel
  否 → 继续往下看

数据总量是否超过 300GB？
  是 → 使用 Cellar
  否 → 继续往下看

是否对延迟极度敏感（TP99 要求 < 10ms）？
  是 → 使用 Squirrel
  否 → 继续往下看

是否绝对不能容忍数据丢失（如金融、支付、订单类核心数据）？
  是 → 使用 Cellar
  否 → 两者均可，结合团队既有技术栈和运维经验选择
```

## 11. 客户端 SDK：初始化、连接池、序列化、异常处理

理解完架构原理后，我们回到最实际的问题：作为业务研发，你要怎么把 Squirrel 用起来？

Squirrel 提供了多语言客户端 SDK，支持 Java、C++、Node.js、Go、Python，这里以最常用的 Java 客户端为例，Squirrel 提供了两种 SDK：

- **Squirrel-client**：基于同步 Socket 实现的传统客户端，接口简单，适合大多数场景。
- **Squirrel-async-client**：基于 Netty 实现的全异步客户端，适合追求极致吞吐、希望通过异步编程模型减少线程阻塞的场景。

### 11.1 初始化方式

**方式一：Spring 方式接入**（推荐，生产环境常用）

```xml
<!-- pom.xml -->
<dependency>
    <groupId>com.dianping.Squirrel</groupId>
    <artifactId>Squirrel-client</artifactId>
</dependency>
```

在 Spring 配置里声明一个 Bean，注入进去直接使用：

```java
@Component
public class Bean {
    @Resource(name = "redisClient")
    private SquirrelStoreClient storeClient;

    public String getValue(String key) {
        StoreKey storeKey = new StoreKey("myredis", key);
        return storeClient.get(storeKey);
    }
}
```

**方式二：API 方式初始化**（适合脱离 Spring 环境的简单场景）

```java
SquirrelStoreClient baseClient = new SquirrelClientBuilder("clusterName")
        .readTimeout(1000)          // 超时时间，单位毫秒
        .routerType("master-slave") // 路由策略
        .idcSensitive(false)        // 是否同机房优先，无特殊需求建议设为false
        .build();                   // 创建客户端
```

这里有一个非常重要的注意事项：**`build()` 方法每调用一次都会创建一个全新的客户端实例（背后对应一套连接池）**，所以一定要做到全局只创建一次，然后复用这一个客户端实例。`SquirrelStoreClient` 本身是线程安全的，不需要每次使用时都重新创建。这是新手最容易踩的坑之一——如果你在每个请求处理方法里都调用一次 `build()`，会导致连接池被大量重复创建，很快耗尽机器资源。

### 11.2 连接池

Squirrel 客户端内部为每个节点维护一个连接池，默认最大连接数是 **16 个**（用户可配置，但不建议超过 32 个）。当连接池里的连接都被占用、且新建连接的时间超过了你设置的 `readTimeout` 时，客户端会直接抛出异常而不是无限等待——这是一个有意的设计：**Squirrel 希望所有 API 调用总耗时都能被严格控制在 `readTimeout` 之内**，不管这段时间里到底是在等待读取响应，还是在等待新建连接。

### 11.3 序列化

Squirrel 客户端默认使用 **Hessian** 序列化协议。这里有几个需要注意的坑：

- 如果你存储的是自定义对象，Hessian 序列化时会把完整的类路径信息也存进去，反序列化时需要能找到对应的类。如果"写"的应用和"读"的应用类路径不一致，会导致反序列化失败或者被强制反序列化成 `HashMap`（进而在业务代码里做类型转换时抛出 `ClassCastException`）。
- 自定义类最好提供一个无参构造函数，避免 Hessian 反射构造对象时因为构造函数参数是引用类型而传入 `null` 触发空指针异常。
- 不同版本的 Hessian（Hessian3 与 Hessian4）协议并不兼容，如果没有特殊需求，建议全公司统一使用 Hessian3。
- 如果不希望依赖 Hessian 的反射机制，也可以选择直接把数据序列化成 `byte[]` 后用 `setBytes`/`getBytes` 接口存取，完全自行掌控序列化逻辑。

### 11.4 异常处理

Squirrel 客户端定义了几种典型异常，业务代码需要针对性地做好兜底处理：

| 异常类型 | 触发原因 | 处理建议 |
| --- | --- | --- |
| `StoreKeysOverFlowException` | 批量操作超过个数限制（pipeline > 512，multiGet > 1024） | 拆分批次，控制单批次的 Key 数量和总数据量 |
| `StoreBigValueException` | 单个 Value 超过 1MB | 拆分大 Value，或评估是否应该用 Cellar |
| `JedisConnectionException` | 连接池耗尽、节点异常、网络问题 | 设置合理的超时和重试策略，配合熔断机制 |
| `SerializeException` | 序列化/反序列化失败 | 检查类路径一致性、Hessian 版本、构造函数设计 |

一个常见的最佳实践是：**缓存读取失败不应该导致整个业务请求失败**。也就是说，在读缓存的代码外面包一层 try-catch，一旦 Squirrel 抛出异常（网络问题、超时等），应该直接降级为查询数据库，而不是让这个异常直接抛给上层调用方——毕竟缓存的本质是"锦上添花"的加速手段，不应该成为影响主流程可用性的单点。

## 12. 与原生 Redis 的区别：企业级能力清单

到这里，我们已经把 Squirrel 的方方面面都讲得比较透彻了。这一节做一个横向的系统性总结，直观地对比"自己裸搭 Redis Cluster"和"使用 Squirrel"到底差在哪里。

| 能力维度 | 原生 Redis / 自建 Redis Cluster | Squirrel |
| --- | --- | --- |
| 多租户隔离 | 无原生支持，需要自己规划 Key 前缀避免冲突 | Category 机制天然隔离不同业务的数据和权限 |
| 访问鉴权 | 只有全局密码（requirepass），粒度粗 | AppKey 级别的精细化鉴权，能追踪具体是哪个应用在访问 |
| 资源配额 | 无内置配额概念 | 集群/Category 级别的容量、QPS 配额管理，配合计费系统 |
| 故障自愈 | 节点摘除需约30秒，补副本需人工介入 | 从库摘除5秒完成，永久故障自动申请新容器补齐，全程自动化 |
| 扩缩容 | 官方支持迁移，但速度和影响面需要人工把控 | 智能迁移服务，动态调节迁移速度，业务近乎无感知 |
| 跨机房容灾 | 需要自己搭建复制链路和脑裂防护方案 | 原生支持三机房部署、集群间复制、异地多活 |
| 热点 Key 治理 | 无内置能力，需要业务自己做本地缓存等兜底 | 自动发现热点 Key，自动限流、自动迁移隔离 |
| 大 Key 防护 | 无限制，容易在不知情的情况下写入超大 Value | 客户端强制限制单 Value 不超过 1MB，主动拦截风险 |
| 监控告警 | 需要自建 Squirrel Exporter + Raptor + Grafana | 内置管理平台，命中率、QPS、慢查询等一应俱全，接入 CAT |
| Avatar | 需要自研运维工具或使用第三方方案 | 官方管理平台支持集群申请、权限管理、Key 查询、任务审批 |
| 数据迁移 | 需要手动执行迁移命令并监控影响 | 平台化操作，全程自动化，带宽和速度自适应调节 |
| 持久化机制 | 官方 RDB/AOF 存在秒级阻塞风险 | 重构持久化机制，异步刷盘，大幅降低抖动概率 |
| 成本核算 | 需要自己评估机器成本并分摊到业务 | 按 Category/AppKey 自动分摊计费，成本可视化 |

简单来说，原生 Redis 给了你"发动机"，而 Squirrel 给了你一辆"配齐了导航、安全气囊、自动驾驶辅助和 4S 店售后服务的整车"。两者内核相同，但在企业级大规模、多团队协作的场景下，Squirrel 帮你屏蔽掉了绝大部分本该由专业存储团队处理的复杂度。

## 13. 完整使用示例：从申请集群到读写缓存

理论讲了很多，我们完整走一遍从零开始接入 Squirrel 的全流程，让你对整个过程有一个具体的时间线感受。

### 第一步：申请集群（如果业务线已有集群可跳过）

1. 打开 Squirrel 管理平台（`https://Squirrel.mws.sankuai.com`），进入"申请资源"页面。
2. 填写申请信息：业务归属地、事业群/业务线、集群部署位置、服务等级、是否涉及现金交易、容量预估、峰值 QPS 预估、读写分布、客户端类型、集群名称（建议见名知意，比如 `redis-waimai-menu`）、集群描述、是否开启持久化等。
3. 提交后进入审批流程（可在"我的申请"里跟踪进度），DBA 审核通过后集群创建成功。
4. 注意：由于线上资源紧张，申请前建议先跟 DBA 沟通清楚容量和用途。

### 第二步：申请 Category

1. 进入对应集群的管理页面，找到 Category 申请入口。
2. 填写 Category 名称、Key 模板（比如 `c{0}d{1}`，代表这个 Category 下的 Key 需要两个参数拼接组成）、数据类型（String/Hash/List/Set 等）、过期时间等。
3. 提交后需要集群管理员（Owner）审批，通过后 Category 生效。

### 第三步：本地开发环境准备

在本地开发或线下测试机器上，需要保证以下目录存在并有相应权限（用于打印日志）：

```bash
sudo mkdir -p /data/applogs
sudo chown -R {username} /data/applogs
sudo mkdir -p /data/appdatas
sudo chown -R {username} /data/appdatas
```

同时在 `/data/webapps/appenv` 文件中配置环境标识，例如北京侧 dev 环境：

```
env=dev
deployenv=dev
zkserver=apollo.dev.sankuai.com:2181
```

这个配置文件的作用是让客户端知道当前运行环境是哪个，进而去正确的 ZooKeeper 地址拉取配置。

### 第四步：引入客户端依赖并编写代码

```xml
<!-- pom.xml -->
<dependencies>
    <dependency>
        <groupId>com.sankuai</groupId>
        <artifactId>inf-bom</artifactId>
        <version>{参见inf-bom ChangeLog的最新版本}</version>
        <type>pom</type>
        <scope>import</scope>
    </dependency>
    <dependency>
        <groupId>com.dianping.Squirrel</groupId>
        <artifactId>Squirrel-client</artifactId>
    </dependency>
</dependencies>
```

```java
package com.dianping.Squirrel;

import com.dianping.Squirrel.client.StoreKey;
import com.dianping.Squirrel.client.impl.redis.SquirrelClientBuilder;
import com.dianping.Squirrel.client.impl.redis.SquirrelStoreClient;

public class HelloSquirrel {
    public static void main(String[] args) {
        // 创建客户端：全局只应该创建一次，不要每次调用都新建
        SquirrelStoreClient baseClient = new SquirrelClientBuilder("redis-zhangjiao")
                .readTimeout(1000)
                .routerType("master-slave")
                .idcSensitive(false)
                .build();

        // 使用之前申请好的 category（walle）构造一个 StoreKey
        // 假设 template 定义为 c{0}d{1}，这里传入两个模板参数 1 和 1
        StoreKey key = new StoreKey("walle", 1, 1);

        // 写入
        baseClient.set(key, "eve");

        // 读取
        String result = baseClient.get(key);
        System.out.println(result); // 输出: eve
    }
}
```

写入成功后，你可以到 Squirrel 管理平台的"KV 查询"页面，输入对应集群和 Category 信息，直接查到刚才写入的 Key-Value，用来验证代码是否生效。

### 第五步：接入监控和权限

代码上线之前，建议顺手完成两件事：

1. 在集群的"应用鉴权"页面，把你服务的 AppKey 注册进这个集群的白名单，避免鉴权失败导致空指针异常。
2. 关注管理平台上的命中率、QPS、慢查询等监控指标（客户端调用信息会自动上报到 CAT），后续可以据此判断缓存策略是否合理。

## 14. 最佳实践：Key 设计、过期策略、大 Key/热点 Key 处理

结合前面讲到的所有原理，这一节汇总一些实战中反复验证有效的经验，帮你少踩坑。

### 14.1 Key 设计原则

- **使用 Category + Template 的规范化结构，不要裸写字符串拼接 Key**。裸拼接容易在多人协作时产生冲突，也不方便后续做批量清理、权限管理。
- **Key 的命名要能够"见名知意"**，比如 `poi.detail_{poiId}`，一眼就能看出这是门店详情缓存。
- **不同业务、不同用途的数据，尽量使用不同的 Category**，即使它们在同一个集群里，Category 级别的隔离能让你在排查问题、评估影响面时事半功倍。
- **避免不同应用共用同一个 Category 存储不同结构的数据**，这是历史上出现过真实故障的场景——两个系统共用同一套缓存路径，一个系统的清理动作污染了另一个系统的数据，最终导致反序列化失败报错。

### 14.2 过期策略

- **所有非永久缓存都必须设置 TTL**，这是防止内存无限增长、集群被无意义数据撑爆的底线要求。
- **同一批次写入的 Key，过期时间要加随机抖动**，避免集中过期引发缓存雪崩。比如基础过期时间是 1 小时，可以在此基础上加一个 0~10 分钟的随机偏移。
- 需要特别注意：**Squirrel 对于复杂数据结构（Hash、List、Set、ZSet）的写入 API（如 `hset`、`lpush`、`sadd`）默认不会自动应用 Category 配置的过期时间**，也不会自己去设置过期时间（即默认永不过期）。如果你希望这些 Key 也能过期，必须显式调用 `expire` 接口去设置，这是一个非常容易被忽略的细节，也是历史上导致内存占用异常增长的常见原因之一。
- Squirrel 不支持 Key 过期事件的订阅（不同于 Squirrel 的 Keyspace Notification），原因是主动删除的频率不会太高，如果业务强依赖过期事件通知，需要自己设计替代方案（比如定时任务扫描）。

### 14.3 大 Key 处理

- 简单类型（String）超过 5KB、复杂类型元素数超过 1000 就要开始警惕。
- 优先考虑业务层面拆分：把一个大 Hash 拆成多个小 Hash（比如按照某个维度取模分片），或者把一个大 List 分页存储。
- 对于确实无法避免的大 Value，一定要评估它是否可能同时是热点 Key——这个组合是最危险的，会同时消耗节点的 CPU、内存和网卡带宽。
- 避免使用 `hgetall` 这类会一次性返回整个大集合的 API，考虑使用 `hgetallByScan` 分批获取，虽然延迟会略高，但不会造成服务端阻塞。

### 14.4 热点 Key 处理

- 对于可预知的热点场景（比如提前知道某个大促活动会有一个爆款商品），可以提前在业务代码层面做**本地缓存兜底**（比如用 Guava Cache/Caffeine 缓存几秒钟），从源头减少对 Squirrel 集群的直接冲击，形成"本地缓存 + 分布式缓存"的多级架构。
- 相信 Squirrel 平台的自动热点探测和隔离机制，但不要完全依赖它作为唯一防线——自动发现和迁移毕竟需要一点响应时间（涉及监控扫描周期），业务如果能提前预判热点，主动做削峰，效果会更好也更平滑。
- 避免在业务代码里使用会对单个 Key 产生放大效应的命令，比如 `spop(key, count)` 传入较大的 count 值，会导致从节点的 QPS 远高于主节点，产生不必要的负载不均衡。

## 15. 业界对标：阿里 Tair、腾讯 Tendis、Codis

最后，我们把视野拉到公司之外，看看 Squirrel 在整个业界的分布式缓存版图里处于什么位置。Redis 官方明确列出的对标产品包括：**腾讯 Tendis、Codis、阿里云 Squirrel、推特 Twemproxy+Squirrel**。

| 方案 | 架构模式 | 核心特点 | 与 Squirrel 的异同 |
| --- | --- | --- | --- |
| **原生 Redis Cluster** | 去中心化，客户端直连 | 官方标准方案，社区活跃，但缺少企业级运维能力 | Squirrel 的架构基础，Squirrel 在其上叠加了控制面和运维能力 |
| **Codis** | 中心化 Proxy 架构 | 引入 Proxy 层做请求转发和路由，对客户端友好（几乎零改造成本），但 Proxy 层本身增加了一跳网络延迟，也是潜在的单点/瓶颈 | Squirrel 走的是无 Proxy 直连路线，延迟更低，但客户端需要维护本地路由表逻辑 |
| **Twemproxy** | 中心化 Proxy 架构 | Twitter 开源的轻量级 Proxy，功能相对简单，不支持在线扩缩容 | 同样是 Proxy 模式，扩展性和运维自动化程度不如 Squirrel |
| **阿里 Tair（Redis 版）** | 云托管服务，兼容 Redis 协议 | 阿里云提供的商业化托管方案，多可用区部署，运维交给云厂商 | 和 Squirrel 的定位类似（企业级托管缓存服务），Squirrel 是美团内部自建版本 |
| **腾讯 Tendis** | 兼容 Redis 协议的持久化存储 | 支持把数据存储在 SSD 上，突破了纯内存的容量限制，成本更低 | 这个特点其实更接近美团的 Cellar，而不是 Squirrel（Squirrel 坚持纯内存） |

从这个对比可以看出一个很有意思的行业趋势：**几乎所有大厂都不会满足于直接使用开源 Redis Cluster，而是会在其上做一层甚至几层自研封装**，核心诉求高度一致——多租户隔离、精细化运维、自动化容灾、成本可控。这背后的根本原因是，当美团的业务规模膨胀到一定量级后，"稳定性和运维效率"会取代"功能丰富度"，成为存储团队最核心的 KPI，而这恰恰是开源社区版本天然缺失的部分。

Squirrel 选择"不引入 Proxy 层、走官方 Redis Cluster 直连架构"这条路径，本质上是在**延迟和运维复杂度**之间做了一个取舍：牺牲了一部分 Proxy 架构带来的客户端简化便利，换取了更低的端到端延迟（省掉了 Proxy 转发的一跳）。这个选择跟美团自身"对延迟极度敏感"的业务特性（比如外卖、打车这类实时交易场景）是高度匹配的。

## 17. Redis Cluster 协议深入：从 CLUSTER 命令到重定向机制

前面章节中我们多次提到 Redis Cluster 的 `CLUSTER NODES`、`CLUSTER SLOTS` 以及 `ASK`/`MOVED` 重定向，但都是点到为止。这一节我们把镜头拉近，深入到底层协议层面，看看这些机制到底是怎么运作的。理解这些底层细节，对于排查 Squirrel 的路由问题、迁移抖动、客户端报错等线上故障至关重要。

### 17.1 CLUSTER NODES 命令详解

`CLUSTER NODES` 是 Redis Cluster 中最基础的信息查询命令，客户端用它来获取整个集群的拓扑快照。执行这个命令不需要参数，它会返回一个文本块，每行描述一个节点：

```
$ redis-cli -p 7000 cluster nodes

a1b2c3d4... 192.168.1.1:7000@17000 myself,master - 0 1609459200000 1 connected 0-5460
e5f6g7h8... 192.168.1.2:7000@17000 slave a1b2c3d4... 0 1609459205000 2 connected
i9j0k1l2... 192.168.1.3:7000@17000 master - 0 1609459203000 3 connected 5461-10922
m3n4o5p6... 192.168.1.4:7000@17000 slave i9j0k1l2... 0 1609459204000 4 connected
q7r8s9t0... 192.168.1.5:7000@17000 master - 0 1609459202000 5 connected 10923-16383
u1v2w3x4... 192.168.1.6:7000@17000 slave q7r8s9t0... 0 1609459201000 6 connected
```

每一行的字段含义如下表所示：

| 字段位置 | 字段名称 | 说明 |
| --- | --- | --- |
| 1 | Node ID | 40 字符的十六进制字符串，节点唯一标识，集群创建时生成，终身不变 |
| 2 | Address | `IP:Port@BusPort` 格式，BusPort 是集群总线端口（默认为数据端口 + 10000） |
| 3 | Flags | 节点角色和状态标志，逗号分隔，常见值见下表 |
| 4 | Master ID | 如果当前节点是从节点，这里记录其主节点的 ID；如果是主节点则为 `-` |
| 5 | Ping Sent | 最近一次发送 PING 消息的时间戳（毫秒） |
| 6 | Pong Received | 最近一次收到 PONG 消息的时间戳（毫秒） |
| 7 | Config Epoch | 节点的配置纪元，用于冲突解决和故障转移 |
| 8 | Link State | 与该节点的连接状态，`connected` 表示正常，`disconnected` 表示断开 |
| 9 | Slots | 该节点负责的 Slot 范围，如 `0-5460` 或 `0-1000 11000-12000`（不连续） |

Flags 字段常见取值：

| Flag 值 | 含义 |
| --- | --- |
| `myself` | 表示这行描述的是当前接收命令的节点自身 |
| `master` | 该节点是主节点 |
| `slave` | 该节点是从节点 |
| `fail?` | 节点处于 PFAIL 状态（主观下线，尚未达成共识） |
| `fail` | 节点处于 FAIL 状态（客观下线，已达成共识） |
| `handshake` | 节点正在握手阶段，尚未完全加入集群 |
| `noaddr` | 节点地址不可用 |
| `nofailover` | 该从节点被禁止参与故障转移选主 |

Squirrel 的客户端 SDK 在初始化阶段会向集群中任意一个节点发送 `CLUSTER NODES` 命令，解析返回的文本，构建出完整的路由表。这个过程可以用下面的伪代码描述：

```java
// 客户端路由表初始化伪代码
public RouteTable buildRouteTable(String seedNodeAddr) {
    // 1. 连接种子节点
    Jedis connection = new Jedis(seedNodeAddr);
    
    // 2. 发送 CLUSTER NODES 命令
    String nodesInfo = connection.clusterNodes();
    
    // 3. 逐行解析
    Map<String, NodeInfo> nodeMap = new HashMap<>();
    Map<Integer, String> slotMap = new HashMap<>(); // slot -> nodeId
    
    for (String line : nodesInfo.split("\n")) {
        String[] parts = line.split(" ");
        String nodeId = parts[0];
        String addr = parts[1];
        String flags = parts[2];
        String masterId = parts[3];
        String slots = parts.length > 8 ? parts[8] : "";
        
        NodeInfo node = new NodeInfo(nodeId, addr, flags, masterId);
        nodeMap.put(nodeId, node);
        
        // 如果是 master 节点，解析其负责的 slot 范围
        if (flags.contains("master")) {
            parseSlotRanges(slots, nodeId, slotMap);
        }
    }
    
    // 4. 建立从节点到主节点的映射
    for (NodeInfo node : nodeMap.values()) {
        if (node.isSlave()) {
            NodeInfo master = nodeMap.get(node.getMasterId());
            master.addSlave(node);
        }
    }
    
    return new RouteTable(nodeMap, slotMap);
}
```

### 17.2 CLUSTER SLOTS 命令详解

`CLUSTER SLOTS` 是另一个常用的集群信息查询命令，返回格式与 `CLUSTER NODES` 不同，它以数组形式返回每个 Slot 范围及其对应的主从节点信息：

```
$ redis-cli -p 7000 cluster slots

1) 1) (integer) 0           -- 起始 slot
   2) (integer) 5460        -- 结束 slot
   3) 1) "192.168.1.1"      -- master IP
      2) (integer) 7000     -- master Port
      3) "a1b2c3d4..."      -- master Node ID
   4) 1) "192.168.1.2"      -- slave IP
      2) (integer) 7000     -- slave Port
      3) "e5f6g7h8..."      -- slave Node ID
2) 1) (integer) 5461
   2) (integer) 10922
   3) 1) "192.168.1.3"
      2) (integer) 7000
      3) "i9j0k1l2..."
   4) 1) "192.168.1.4"
      2) (integer) 7000
      3) "m3n4o5p6..."
3) 1) (integer) 10923
   2) (integer) 16383
   3) 1) "192.168.1.5"
      2) (integer) 7000
      3) "q7r8s9t0..."
   4) 1) "192.168.1.6"
      2) (integer) 7000
      3) "u1v2w3x4..."
```

两个命令的对比：

| 对比维度 | CLUSTER NODES | CLUSTER SLOTS |
| --- | --- | --- |
| 返回格式 | 纯文本，每行一个节点 | RESP 数组，每个元素是一个 Slot 范围 |
| 信息维度 | 以节点为中心 | 以 Slot 范围为中心 |
| 包含的信息 | 节点 ID、地址、角色、Flags、Epoch、连接状态、Slot 范围 | Slot 范围、主节点信息、从节点信息 |
| 解析复杂度 | 文本解析，较简单 | 数组解析，需处理嵌套结构 |
| 适用场景 | 需要获取节点全量信息（如故障检测、连接管理） | 只需要 Slot 到节点的映射关系 |
| Squirrel 中的使用 | 客户端初始化时使用 | 路由表更新时使用 |

Squirrel 客户端实际上在内部同时实现了两种解析逻辑，根据不同场景选择使用哪个命令。初始化阶段用 `CLUSTER NODES` 获取完整的节点拓扑（包括从节点信息、连接状态等），而在后续的路由表刷新中则优先使用 `CLUSTER SLOTS`，因为它的返回数据量更小、解析更快。

### 17.3 MOVED 重定向

`MOVED` 重定向是 Redis Cluster 中最基本的路由纠错机制。当客户端把一个请求发到了错误的节点（即这个 Key 对应的 Slot 不在当前节点上），节点会返回一个 `MOVED` 错误：

```
GET some_key
(error) MOVED 1234 192.168.1.3:7000
```

这个错误信息的格式是 `MOVED <slot> <ip:port>`，含义是"Slot 1234 已经在 192.168.1.3:7000 上，请去那里请求"。

客户端收到 `MOVED` 错误后的处理流程：

```
┌──────────────────────────────────────────────────────────────┐
│                    MOVED 重定向处理流程                        │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 客户端计算 key 的 slot：CRC16(key) mod 16384 = 1234      │
│                                                              │
│  2. 查本地路由表，slot 1234 → Node A                        │
│                                                              │
│  3. 向 Node A 发送 GET some_key                              │
│                                                              │
│  4. Node A 返回：MOVED 1234 Node-B-Addr                     │
│     （说明 slot 1234 已经永久迁移到 Node B）                   │
│                                                              │
│  5. 客户端处理：                                              │
│     a. 更新本地路由表：slot 1234 → Node B                    │
│     b. 向 Node B 重新发送 GET some_key                       │
│     c. 获取结果，返回给业务代码                                │
│                                                              │
│  6. 后续所有针对 slot 1234 的请求都直接发往 Node B             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

`MOVED` 重定向的关键特征是**永久性**——它意味着 Slot 的归属已经发生了永久变更（比如扩容时把一部分 Slot 分配给了新节点）。客户端应该更新本地路由表，避免下次再走错。

需要注意的是，如果集群正在大规模迁移 Slot，客户端可能会频繁收到 `MOVED` 错误。如果每次 `MOVED` 都只更新单个 Slot 的映射，会导致大量请求需要两次往返（先走错，再重定向）。因此，Squirrel 客户端在连续收到多个 `MOVED` 错误后，会触发一次全量路由表刷新（重新执行 `CLUSTER SLOTS`），以批量获取最新的拓扑信息。

### 17.4 ASK 重定向

`ASK` 重定向与 `MOVED` 的本质区别在于它是**临时性**的——发生在 Slot 迁移过程中，表示"这个 Slot 的一部分 Key 已经迁移到了目标节点，但迁移还没完成，Slot 的归属还没正式变更"。

```
GET some_key
(error) ASK 1234 192.168.1.3:7000
```

客户端收到 `ASK` 错误后的处理流程与 `MOVED` 不同：

```
┌──────────────────────────────────────────────────────────────┐
│                     ASK 重定向处理流程                         │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 客户端计算 key 的 slot：CRC16(key) mod 16384 = 1234      │
│                                                              │
│  2. 查本地路由表，slot 1234 → Node A（源节点）                 │
│                                                              │
│  3. 向 Node A 发送 GET some_key                              │
│                                                              │
│  4. Node A 在本地查找，发现这个 key 已经迁移走了               │
│     返回：ASK 1234 Node-B-Addr                               │
│                                                              │
│  5. 客户端处理（与 MOVED 的关键区别）：                        │
│     a. 不更新本地路由表（slot 1234 仍然指向 Node A）           │
│     b. 向 Node B 发送 ASKING 命令                            │
│     c. 紧接着向 Node B 发送 GET some_key                     │
│     d. 获取结果，返回给业务代码                                │
│                                                              │
│  6. 后续针对 slot 1234 的请求仍然先发往 Node A                 │
│     （因为迁移还没完成，有些 key 可能还在 Node A 上）           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

这里有一个非常关键的细节：**客户端在向目标节点发送请求之前，必须先发送一个 `ASKING` 命令**。这是因为目标节点在迁移过程中会把对应 Slot 标记为 `IMPORTING` 状态，在这个状态下，节点默认会拒绝所有针对这个 Slot 的正常请求（返回 `MOVED` 让你回源节点去），只有收到 `ASKING` 命令后才会临时放行这一次请求。这个设计是为了确保在迁移过程中，只有被 `ASK` 重定向过来的请求才能访问目标节点上的迁移中数据，避免数据不一致。

`MOVED` 和 `ASK` 的对比总结：

| 对比维度 | MOVED | ASK |
| --- | --- | --- |
| 触发场景 | Slot 归属永久变更（迁移完成后） | Slot 迁移过程中，Key 已被迁走但 Slot 归属未变更 |
| 永久性 | 永久重定向 | 临时重定向 |
| 是否更新路由表 | 是，更新本地缓存 | 否，不更新 |
| 是否需要 ASKING | 不需要 | 需要，先发 ASKING 再发实际命令 |
| 对性能的影响 | 第一次多一次往返，之后正常 | 每次访问迁移中的 Key 都需要两次往返 |

### 17.5 集群总线与节点握手

Redis Cluster 的每个节点除了监听客户端连接的数据端口（如 7000）外，还会监听一个**集群总线端口**（默认为数据端口 + 10000，如 17000）。节点之间的 Gossip 通信就是通过这个总线端口进行的。

当一个新的节点想要加入集群时，需要经历**握手（Handshake）**过程：

```
# 假设集群已有节点 A(7000)、B(7001)、C(7002)，现在要让 D(7003) 加入

# 在节点 A 上执行：
$ redis-cli -p 7000 cluster meet 192.168.1.4 7003

# 握手过程：
# 1. A 向 D 发送 MEET 消息（通过总线端口 17003）
# 2. D 收到 MEET 后，回复 PONG 给 A，确认自己已加入集群
# 3. A 通过 Gossip 协议把 D 的信息传播给 B 和 C
# 4. B 和 C 也各自与 D 完成握手
# 5. 最终所有节点都知道了 D 的存在
```

握手完成后，新节点 D 还没有负责任何 Slot，只是一个"空节点"。需要通过 `CLUSTER ADDSLOTS` 命令给它分配 Slot，或者通过迁移把一部分 Slot 从其他节点转移到 D 上。

在 Squirrel 中，整个"加节点 → 握手 → 分配 Slot → 迁移数据"的过程是由调度控制面自动完成的，业务方完全不需要手动执行这些命令。但理解这些底层机制，对于排查"新节点加入后客户端报错"、"迁移过程中请求失败"等问题非常有帮助。

### 17.6 CRC16 哈希算法

Redis Cluster 使用 CRC16-CCITT 哈希算法来计算 Key 的 Slot 归属。具体公式是：

```
slot = CRC16(key) mod 16384
```

CRC16 是一种循环冗余校验码，具有以下特性：
- 计算速度快，适合在高吞吐场景下使用
- 分布均匀性较好，能够把 Key 相对均匀地分布到 16384 个 Slot 中
- 确定性：同一个 Key 每次计算结果都相同

Squirrel 在实现中还引入了**Hash Tag（哈希标签）**机制，允许你强制让多个 Key 落在同一个 Slot 上。方法是用 `{}` 把 Key 的一部分括起来，CRC16 只对 `{}` 内的内容做哈希：

```
# 这三个 Key 会落在不同的 Slot 上
SET user:1001:name "Alice"   → slot = CRC16("user:1001:name") mod 16384 = 5473
SET user:1001:age 25          → slot = CRC16("user:1001:age") mod 16384 = 9821
SET user:1001:email "..."     → slot = CRC16("user:1001:email") mod 16384 = 3294

# 使用 Hash Tag 后，三个 Key 落在同一个 Slot 上
SET {user:1001}:name "Alice"  → slot = CRC16("user:1001") mod 16384 = 5061
SET {user:1001}:age 25         → slot = CRC16("user:1001") mod 16384 = 5061
SET {user:1001}:email "..."    → slot = CRC16("user:1001") mod 16384 = 5061
```

Hash Tag 的典型使用场景是**需要在同一个节点上执行事务（MULTI/EXEC）或 Lua 脚本的场景**——Redis Cluster 要求事务中涉及的所有 Key 必须在同一个 Slot 上，否则会报 `CROSSSLOT` 错误。

在 Squirrel 中，Hash Tag 的使用需要格外谨慎，因为强制把多个 Key 放在同一个 Slot 上会破坏数据的均匀分布，可能导致某个分片上的数据量或访问量远超平均水平，引发数据倾斜。

## 18. Gossip 协议详解：分布式状态传播的基石

Gossip 协议是 Redis Cluster 的"神经系统"——它负责在节点之间传播集群状态信息，包括节点的加入和离开、故障检测和传播、Slot 分布的变更等。Squirrel 的 HA 高可用服务虽然在外部叠加了自己的监控和切换逻辑，但 Redis Cluster 内部的基础状态传播依然依赖 Gossip 协议。理解 Gossip 的运作机制，对于排查"节点状态不一致"、"故障检测延迟过长"等问题至关重要。

### 18.1 Gossip 协议基本原理

Gossip 协议（也叫" epidemic protocol"——流行病协议）的核心思想非常简单：**每个节点周期性地随机选取几个其他节点，把自己知道的信息告诉对方，对方再把这些信息传播给其他节点，如此往复，最终所有节点都会收到全量信息**。

这个过程就像谣言传播：你告诉几个朋友一个消息，这几个朋友又各自告诉他们的朋友，很快所有人就都知道了。传播速度是指数级的——如果每次传播给 3 个人，那么经过 k 轮传播后，知道消息的节点数为 3^k。

Gossip 协议的特性：

| 特性 | 说明 |
| --- | --- |
| 最终一致性 | 不保证所有节点在同一时刻看到相同的状态，但最终会收敛到一致 |
| 去中心化 | 没有中心节点，每个节点的角色对等 |
| 容错性好 | 即使部分节点不可用，消息依然能通过其他路径传播 |
| 传播速度可控 | 通过调整每轮传播的节点数量和传播间隔来控制收敛速度 |
| 消息冗余 | 同一条消息可能通过不同路径到达同一节点，需要去重机制 |

### 18.2 Redis Cluster 中的 Gossip 消息类型

Redis Cluster 的 Gossip 协议定义了以下几种消息类型：

| 消息类型 | 方向 | 携带内容 | 用途 |
| --- | --- | --- | --- |
| `MEET` | 新节点 → 集群 | 发送方基本信息 | 请求加入集群，触发握手 |
| `PING` | 节点 → 随机节点 | 发送方已知的部分节点状态 | 心跳检测 + 状态传播 |
| `PONG` | 节点 → PING 发送方 | 发送方已知的部分节点状态 | 确认存活 + 状态传播 |
| `FAIL` | 节点 → 集群所有节点 | 失效节点的 ID | 广播某节点已客观下线 |
| `PUBLISH` | 节点 → 集群所有节点 | 频道名 + 消息内容 | Pub/Sub 消息广播 |
| `FAILOVER_AUTH_REQUEST` | 从节点 → 集群所有节点 | 发起故障转移的从节点信息 | 从节点请求投票当选新主 |
| `FAILOVER_AUTH_ACK` | 主节点 → 请求方 | 同意/拒绝投票 | 主节点对故障转移投票 |
| `UPDATE` | 节点 → 目标节点 | 节点配置信息 | 通知对端更新过期的配置信息 |

其中最核心的是 `PING` 和 `PONG`，它们承担了心跳检测和状态传播两个关键职责。

### 18.3 PING/PONG 消息的结构与传播机制

每次发送 `PING` 消息时，节点会携带以下两部分信息：

```
┌──────────────────────────────────────────────────────────────────┐
│                        PING 消息结构                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │                    消息头（Header）                         │  │
│  │  - 发送方 Node ID                                          │  │
│  │  - 发送方 IP:Port@BusPort                                  │  │
│  │  - 发送方 Flags（master/slave/...）                         │  │
│  │  - 发送方 Config Epoch                                     │  │
│  │  - 发送方负责的 Slot 范围                                   │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │              Gossip 部分（最多 N 条）                       │  │
│  │  每条包含：                                                 │  │
│  │  - 被描述节点的 Node ID                                     │  │
│  │  - 被描述节点的 IP:Port@BusPort                              │  │
│  │  - 被描述节点的最近一次 PONG 时间戳                          │  │
│  │  - 被描述节点的 Flags（PFAIL/FAIL/...）                      │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

Gossip 部分携带的不是全量节点列表，而是发送方从本地节点列表中**随机选取的少量节点**（默认最多 3 个）的状态信息。这种"每次只带一小部分"的设计是为了控制单条消息的大小，避免在集群规模较大时 Gossip 消息变得过大。

传播流程的时间线：

```
时间轴 ──────────────────────────────────────────────────────────────▶

Node A 的 Gossip 周期（默认每 100ms 执行一次）：

  T0: Node A 随机选取 Node B，发送 PING
      ├── Header: A 自己的最新状态
      └── Gossip: A 随机选取 3 个已知节点的状态（比如 D、E、F）

  T1: Node B 收到 PING，处理：
      ├── 更新本地关于 A 的状态（A 还活着）
      ├── 更新本地关于 D、E、F 的状态（如果 B 本地的信息比 A 发来的旧）
      └── 回复 PONG 给 A
          ├── Header: B 自己的最新状态
          └── Gossip: B 随机选取 3 个已知节点的状态

  T2: Node A 收到 PONG，处理：
      ├── 更新本地关于 B 的状态（B 还活着）
      └── 更新本地关于 B 携来的节点状态

  T3（100ms 后）: Node A 又随机选取 Node C，发送 PING
      └── Gossip 中可能包含 B 的最新状态（因为 A 刚从 B 收到 PONG）

  T4: Node C 收到 PING，了解到 B 的状态...
      └── 继续传播给其他节点
```

通过这种"滚雪球"式的传播，一个节点的状态变更最终会传播到集群中的所有节点。在 1000 个节点的集群中，一条信息的传播通常在几秒内就能完成。

### 18.4 故障检测流程：从 PFAIL 到 FAIL

Redis Cluster 的故障检测分为两个阶段：

**阶段一：主观下线（PFAIL，Possible Failure）**

```
┌──────────────────────────────────────────────────────────────┐
│                   主观下线检测流程                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. Node A 定期向 Node B 发送 PING                           │
│                                                              │
│  2. Node A 等待 Node B 的 PONG 回复                          │
│     - 超时时间：cluster-node-timeout（默认 15 秒）             │
│                                                              │
│  3. 如果超时未收到 PONG：                                      │
│     - Node A 把 Node B 标记为 PFAIL（主观下线）                │
│     - 这个标记只在 Node A 本地有效                             │
│     - 其他节点此时可能还认为 Node B 是正常的                    │
│                                                              │
│  4. Node A 在后续的 Gossip 消息中会携带                        │
│     "Node B 处于 PFAIL 状态"的信息                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**阶段二：客观下线（FAIL）**

```
┌──────────────────────────────────────────────────────────────┐
│                   客观下线检测流程                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. Node A 通过 Gossip 传播 "Node B = PFAIL"                 │
│                                                              │
│  2. 其他节点收到后，也会开始关注 Node B 的状态                  │
│     如果它们也发现 Node B 不可达，也会标记为 PFAIL              │
│                                                              │
│  3. 当集群中超过半数的主节点都报告 Node B = PFAIL 时：          │
│     - 第一个发现这一点的节点（比如 Node A）                     │
│       会把 Node B 标记为 FAIL（客观下线）                       │
│     - Node A 向集群广播 FAIL 消息                              │
│     - 所有节点收到 FAIL 消息后，更新本地状态                    │
│                                                              │
│  4. Node B 被标记为 FAIL 后：                                  │
│     - 如果 B 是主节点，B 的从节点开始发起故障转移               │
│     - 客户端收到针对 B 的请求时返回错误                        │
│     - B 的从节点被选为新主后，广播更新                         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

这个两阶段设计的核心目的是**避免误判**——网络抖动可能导致 A 和 B 之间暂时不可达，但 B 其实是正常的。通过要求"超过半数的主节点都报告 PFAIL"才标记为 FAIL，有效降低了误判概率。

故障检测的关键参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `cluster-node-timeout` | 15000ms | 节点超时时间，超过此时间未收到 PONG 则标记 PFAIL |
| `cluster-require-full-coverage` | yes | 如果集群中有 Slot 没有节点负责，是否拒绝所有请求 |
| `cluster-failover-timeout` | 180000ms | 故障转移超时时间，从节点在这个时间内未完成切换则放弃 |

### 18.5 配置纪元（Config Epoch）与冲突解决

当集群中发生 Slot 迁移或故障转移时，不同节点可能对"某个 Slot 现在归谁"有不同的看法，这就产生了配置冲突。Redis Cluster 使用**配置纪元（Config Epoch）**来解决这个问题。

规则很简单：**纪元大的配置优先于纪元小的配置**。

```
场景示例：

1. 集群初始状态：Slot 1234 归 Node A，Config Epoch = 1

2. Node A 宕机，Node A 的从节点 Node A' 发起故障转移
   - Node A' 获得多数票，成为新的主节点
   - Node A' 的 Config Epoch 升级为 2
   - Slot 1234 现在归 Node A'（Config Epoch = 2）

3. 由于网络分区，Node A 暂时"复活"了（其实只是网络恢复）
   - Node A 本地记录：Slot 1234 归我（Config Epoch = 1）
   - Node A 通过 Gossip 了解到 Node A' 的状态
   - 因为 2 > 1，Node A 接受 Node A' 的配置
   - Node A 更新本地状态：Slot 1234 归 Node A'（Config Epoch = 2）

4. 如果 Node A 尝试宣称 "Slot 1234 归我"（Config Epoch = 1）
   - 其他节点会比较 Epoch：2 > 1
   - 拒绝 Node A 的声明，保持 Node A' 的配置
```

这个机制确保了在配置冲突时，集群总是收敛到最新的有效配置，避免了脑裂导致的数据分叉。

### 18.6 Squirrel 对 Gossip 协议的增强

虽然 Squirrel 保留了 Redis Cluster 原生的 Gossip 协议，但它在之上叠加了自己的增强机制：

1. **外部 HA 服务加速故障检测**：原生 Gossip 的故障检测需要约 30 秒（`cluster-node-timeout` + PFAIL 传播 + FAIL 广播），Squirrel 的 HA 服务通过独立的监控通道，可以在 5 秒内发现节点异常并更新 ZooKeeper，客户端通过订阅 ZooKeeper 几乎实时感知到拓扑变更。

2. **客户端主动探测**：Squirrel 客户端在检测到某个节点连续超时后，会主动尝试连接该节点的其他端口（如 Redis 的 INFO 命令端口），判断是真的宕机还是只是数据端口有问题，避免因为单端口异常导致误判。

3. **Gossip 消息压缩**：在节点数量较多的大集群中，Gossip 消息的开销不可忽视。Squirrel 对 Gossip 消息做了压缩优化，减少总线端口的带宽占用。

## 19. Slot 迁移算法深入：从 MIGRATE 到异步迁移

Slot 迁移是 Redis Cluster 扩缩容的核心操作，也是最容易引发线上问题的环节之一。前面章节我们对 Squirrel 的智能迁移做了概述，这里我们深入到算法层面，看看迁移过程中到底发生了什么。

### 19.1 原生 MIGRATE 命令的原理与问题

Squirrel 原生的 `MIGRATE` 命令用于在节点之间迁移 Key，基本语法是：

```
MIGRATE target_host target_port "" target_db timeout KEYS key1 key2 key3 ...
```

`MIGRATE` 命令的执行流程：

```
┌──────────────────────────────────────────────────────────────┐
│                  MIGRATE 命令执行流程                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  源节点 (Node A)                  目标节点 (Node B)           │
│                                                              │
│  1. 检查 key 是否存在                                         │
│     └── 不存在则直接返回 NOKEY                                │
│                                                              │
│  2. 与目标节点建立连接                                        │
│     ──────────────────────────▶                              │
│                                  3. 接收连接                  │
│                                                              │
│  4. 发送 RESTORE 命令                                         │
│     （包含 key 的值、TTL、序列化后的数据）                      │
│     ──────────────────────────▶                              │
│                                  5. 反序列化数据              │
│                                  6. 写入本地                  │
│                                  7. 返回 OK                   │
│     ◀──────────────────────────                              │
│                                                              │
│  8. 收到 OK，删除本地 key                                     │
│                                                              │
│  9. 返回 OK 给调用方                                          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

这个流程最大的问题是：**步骤 4 到步骤 8 期间，源节点的主线程是阻塞的**——它在等待目标节点的响应，期间无法处理任何其他客户端请求。如果迁移的 Value 很大（比如几百 KB），这个阻塞时间可能达到几十甚至上百毫秒，对所有其他 Key 的访问都会造成明显的延迟抖动。

原生 MIGRATE 的主要问题汇总：

| 问题 | 影响 |
| --- | --- |
| 主线程阻塞 | 迁移期间无法处理其他请求，导致 TP99 飙升 |
| 大 Value 放大效应 | Value 越大，阻塞时间越长，抖动越严重 |
| 无断点续传 | 如果迁移过程中断，已迁移的 Key 不会回滚，但未迁移的 Key 需要重新开始 |
| 无流量控制 | 迁移速度不可调节，可能压满网络带宽或 CPU |
| 原子性问题 | MIGRATE 是原子操作，要么全部成功要么全部失败，无法部分迁移 |

### 19.2 Squirrel 的异步迁移方案

为了解决原生 MIGRATE 的阻塞问题，Squirrel 实现了**异步迁移（Async Migrate）**机制。核心思路是：把迁移操作从主线程中拆出来，放到一个独立的后台线程中执行，主线程继续处理正常请求。

```
┌──────────────────────────────────────────────────────────────┐
│                Squirrel 异步迁移流程                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  源节点 (Node A)                                              │
│                                                              │
│  ┌──────────────────┐    ┌──────────────────┐               │
│  │   主线程          │    │  迁移后台线程      │               │
│  │                  │    │                  │               │
│  │  正常处理请求     │    │  1. 选取待迁移 key │               │
│  │  (不阻塞)        │    │  2. 序列化 value   │               │
│  │                  │    │  3. 发送到目标节点  │               │
│  │  如果收到针对     │    │  4. 等待响应        │               │
│  │  迁移中 key 的   │    │  5. 收到 OK         │               │
│  │  请求：           │    │  6. 标记 key 已迁移 │               │
│  │  → 返回 TRYAGAIN │    │     （主线程可见）  │               │
│  │    或 ASK 重定向  │    │                  │               │
│  └──────────────────┘    └──────────────────┘               │
│                                                              │
│  两个线程通过共享的迁移状态表协调：                              │
│  ┌────────────────────────────────────────┐                  │
│  │         迁移状态表（Migration State）    │                  │
│  │  key1 → MIGRATING（正在迁移中）          │                  │
│  │  key2 → MIGRATED（已迁移完成）           │                  │
│  │  key3 → PENDING（等待迁移）              │                  │
│  └────────────────────────────────────────┘                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

异步迁移的关键设计点：

1. **迁移状态表**：主线程和后台线程共享一张迁移状态表，记录每个正在迁移的 Key 的状态。当主线程收到针对正在迁移中的 Key 的请求时，会根据状态返回不同的响应：
   - 状态为 `MIGRATING`：返回 `TRYAGAIN` 错误，让客户端短暂重试
   - 状态为 `MIGRATED`：返回 `ASK` 重定向，引导客户端去目标节点
   - 状态为 `PENDING`（还未开始迁移）：正常处理请求

2. **分批迁移**：不一次性迁移整个 Slot 的所有 Key，而是按批次迁移（每批几十到几百个 Key），每批之间插入一个短暂的暂停（如 1ms），给主线程留出处理正常请求的时间窗口。

3. **大 Key 特殊处理**：对于超过一定大小的 Value，后台线程会先把 Value 分块传输到目标节点，目标节点收到所有分块后再组装。这样即使 Value 很大，也不会长时间占用网络缓冲区。

### 19.3 断点续传机制

迁移过程可能因为网络中断、节点重启等原因而中断。Squirrel 的断点续传机制确保中断后可以从中断点继续，而不需要从头开始。

```java
// 断点续传的核心数据结构（伪代码）

    private String sourceNodeId;
    private String targetNodeId;
    private int slot;
    private long lastMigratedKeyIndex;   // 最后成功迁移的 Key 序号
    private Set<String> migratedKeys;     // 已迁移完成的 Key 集合
    private Set<String> pendingKeys;      // 尚未迁移的 Key 集合
    private long startTime;
    private long lastUpdateTime;
    
    // 持久化到 ZooKeeper，确保迁移服务重启后能恢复
    public void persistToZooKeeper(ZooKeeperClient zk) {
        String path = "/Squirrel/migration/" + slot;
        zk.setData(path, this.serialize(), -1);
    }
    
    // 从 ZooKeeper 恢复断点
    public static MigrationCheckpoint restoreFromZooKeeper(
            ZooKeeperClient zk, int slot) {
        String path = "/Squirrel/migration/" + slot;
        byte[] data = zk.getData(path, false, null);
        return MigrationCheckpoint.deserialize(data);
    }
}
```

### 19.4 流量控制算法

Squirrel 的迁移流量控制借鉴了 TCP 拥塞控制的**慢启动（Slow Start）**思想：

```
迁移速度变化曲线（示意）：

速度(keys/s)
    │
    │                          ╭─────── 稳定区
    │                        ╱
    │                      ╱
    │                    ╱     ← 降速：检测到业务请求成功率下降
    │    ╲             ╱
    │     ╲          ╱
    │      ╲       ╱
    │       ╲    ╱
    │        ╲╱╱         ← 加速：业务指标正常，逐步提速
    │
    └──────────────────────────────────────────────── 时间
         慢启动    降速    恢复    稳定
```

流量控制算法的伪代码：

```java
public class MigrationFlowController {
    // 控制参数
    private static final int MIN_BATCH_SIZE = 10;       // 最小批次大小
    private static final int MAX_BATCH_SIZE = 1000;     // 最大批次大小
    private static final int INITIAL_BATCH_SIZE = 50;   // 初始批次大小
    private static final long BATCH_INTERVAL_MS = 1;    // 批次间隔（毫秒）
    
    // 业务健康度指标
    private double successRateThreshold = 0.99;  // 成功率阈值
    private double latencyThreshold = 10.0;      // 延迟阈值（ms）
    
    private int currentBatchSize = INITIAL_BATCH_SIZE;
    
    // 每批次迁移后，根据业务指标调整速度
    public void adjustSpeed(MetricsSnapshot metrics) {
        if (metrics.getSuccessRate() < successRateThreshold 
                || metrics.getLatencyP99() > latencyThreshold) {
            // 业务受影响，降速
            currentBatchSize = Math.max(MIN_BATCH_SIZE, 
                currentBatchSize / 2);
            log.warn("Migration speed reduced to {} due to business impact", 
                currentBatchSize);
        } else if (metrics.getSuccessRate() > 0.999 
                && metrics.getLatencyP99() < latencyThreshold * 0.5) {
            // 业务正常，加速
            currentBatchSize = Math.min(MAX_BATCH_SIZE, 
                currentBatchSize + currentBatchSize / 4);
        }
        // 否则保持当前速度
    }
    
    public void executeBatch(List<String> keysToMigrate) {
        int batchSize = Math.min(currentBatchSize, keysToMigrate.size());
        List<String> batch = keysToMigrate.subList(0, batchSize);
        
        // 执行异步迁移
        asyncMigrateKeys(batch);
        
        // 采集业务指标
        MetricsSnapshot metrics = collectMetrics();
        
        // 根据指标调整下一批的速度
        adjustSpeed(metrics);
        
        // 批次间暂停
        Thread.sleep(BATCH_INTERVAL_MS);
    }
}
```

这个算法的关键设计点在于：它不是简单地将迁移速度固定在一个"安全值"上，而是**根据实时业务反馈动态调节**。在业务负载较低的时候（比如凌晨），迁移速度可以更快；在业务高峰期，迁移速度自动降低。这样既保证了迁移效率，又不会影响线上业务。

### 19.5 迁移过程中的请求路由

在 Slot 迁移的不同阶段，客户端的请求会被路由到不同的节点。完整的 Slot 状态变迁如下：

```
     │                    │
```

### 20.3 路由表的刷新策略

Squirrel 客户端采用**多级刷新策略**来保证路由表的时效性：

| 触发条件 | 刷新方式 | 刷新范围 | 响应速度 |
| --- | --- | --- | --- |
| ZooKeeper 节点变更通知 | 主动刷新 | 全量路由表 | 毫秒级 |
| 收到 MOVED 重定向 | 被动刷新 | 单个 Slot | 即时 |
| 连续收到多个 MOVED | 被动刷新 | 全量路由表 | 即时 |
| 定时刷新（默认 60 秒） | 定时刷新 | 全量路由表 | 60 秒 |
| 节点连接异常 | 主动探测 | 单个节点 | 秒级 |

```java
// 路由表刷新的核心逻辑（简化版）
public class RouteTableManager {
    private volatile RouteTable currentTable;
    private final Object refreshLock = new Object();
    private final AtomicLong lastRefreshTime = new AtomicLong(0);
    private static final long MIN_REFRESH_INTERVAL = 1000; // 最小刷新间隔 1 秒
    
    // ZooKeeper Watcher 回调
    public void onZooKeeperNodeChanged() {
        refreshRouteTable("ZooKeeper notification");
    }
    
    // MOVED 重定向触发
    public void onMovedRedirect(int slot, String targetNodeAddr) {
        // 先快速更新单个 Slot（乐观更新）
        currentTable.updateSlot(slot, targetNodeAddr);
        
        // 如果短时间内收到多个 MOVED，触发全量刷新
        if (movedCounter.incrementAndGet() > MOVED_THRESHOLD) {
            refreshRouteTable("multiple MOVED redirects");
            movedCounter.set(0);
        }
    }
    
    // 全量刷新
    public void refreshRouteTable(String reason) {
        // 防抖：避免短时间内的重复刷新
        long now = System.currentTimeMillis();
        if (now - lastRefreshTime.get() < MIN_REFRESH_INTERVAL) {
            return;
        }
        
        synchronized (refreshLock) {
            // 双重检查
            if (now - lastRefreshTime.get() < MIN_REFRESH_INTERVAL) {
                return;
            }
            
            try {
                // 1. 从 ZooKeeper 或 Squirrel 获取最新拓扑
                ClusterTopology newTopology = fetchLatestTopology();
                
                // 2. 构建新的路由表
                RouteTable newTable = buildRouteTable(newTopology);
                
                // 3. 平滑切换：先让新表就绪，再切换引用
                RouteTable oldTable = currentTable;
                currentTable = newTable;
                
                // 4. 异步清理旧连接池
                asyncCleanupOldConnections(oldTable, newTable);
                
                // 5. 更新时间戳
                lastRefreshTime.set(System.currentTimeMillis());
                
                log.info("Route table refreshed: {}, version={}", 
                    reason, newTable.getVersion());
            } catch (Exception e) {
                log.error("Failed to refresh route table", e);
                // 刷新失败时保持旧路由表，避免影响正常请求
            }
        }
    }
}
```

### 20.4 并发安全设计

路由表是一个被所有业务线程共享的全局数据结构，它的并发安全设计至关重要。Squirrel 客户端采用了**Copy-on-Write（写时复制）**的思想来实现无锁读取：

```
┌──────────────────────────────────────────────────────────────┐
│              路由表的并发安全设计                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  业务线程（读多写少）                                          │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐                      │
│  │ Thread 1│  │ Thread 2│  │ Thread 3│                      │
│  │  get()  │  │  set()  │  │  get()  │                      │
│  └────┬────┘  └────┬────┘  └────┬────┘                      │
│       │            │            │                            │
│       ▼            ▼            ▼                            │
│  ┌─────────────────────────────────────┐                     │
│  │     volatile RouteTable             │  ← 读操作无锁       │
│  │     (currentTable 引用)              │                    │
│  └─────────────────────────────────────┘                     │
│                    ▲                                         │
│                    │ 写操作（路由表刷新，低频）                 │
│  ┌─────────────────────────────────────┐                     │
│  │     synchronized (refreshLock)       │  ← 写操作加锁      │
│  │     1. 构建新的 RouteTable           │                    │
│  │     2. currentTable = newTable       │  ← 原子引用切换     │
│  │     3. 异步清理旧表                  │                    │
│  └─────────────────────────────────────┘                     │
│                                                              │
│  关键点：                                                     │
│  - 读操作直接读取 volatile 引用，不加锁，性能极高              │
│  - 写操作创建全新的 RouteTable 对象，不影响正在读旧表的线程     │
│  - 引用切换是原子操作（volatile 写），保证可见性               │
│  - 旧表通过引用计数管理生命周期，所有引用释放后才回收           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

这种设计的优势在于：
- **读操作完全无锁**：业务请求的路由查询不需要任何同步操作，避免了锁竞争
- **写操作不影响读**：刷新路由表时创建新对象，正在使用旧表的线程不受影响
- **内存安全**：旧表通过引用计数管理，确保没有线程在使用时才回收

### 20.5 连接池的动态管理

路由表刷新后，可能涉及连接池的创建和销毁。Squirrel 客户端的连接池管理策略：

```java
public class ConnectionPoolManager {
    private final Map<String, ConnectionPool> pools = new ConcurrentHashMap<>();
    
    // 路由表更新后，同步连接池
    public void syncWithRouteTable(RouteTable newTable, RouteTable oldTable) {
        // 1. 为新表中的节点创建连接池
        for (NodeInfo newNode : newTable.getAllNodes()) {
            if (!pools.containsKey(newNode.getId())) {
                ConnectionPool pool = createPool(newNode);
                pools.put(newNode.getId(), pool);
                log.info("Created connection pool for new node: {}", newNode.getId());
            }
        }
        
        // 2. 标记旧表中不再存在的节点的连接池为"待回收"
        Set<String> currentNodeIds = newTable.getAllNodeIds();
        for (String oldNodeId : pools.keySet()) {
            if (!currentNodeIds.contains(oldNodeId)) {
                ConnectionPool pool = pools.get(oldNodeId);
                pool.markForEviction();
                // 延迟 60 秒后关闭，给正在使用连接的请求留出完成时间
                schedulePoolShutdown(pool, 60, TimeUnit.SECONDS);
            }
        }
    }
    
    // 获取连接（带降级逻辑）
    public Connection getConnection(NodeInfo node) {
        ConnectionPool pool = pools.get(node.getId());
        if (pool == null || pool.isEvicting()) {
            // 节点可能刚被移除，尝试使用同分片的从节点
            NodeInfo alternative = findAlternativeNode(node);
            if (alternative != null) {
                pool = pools.get(alternative.getId());
            }
        }
        
        if (pool == null) {
            throw new StoreConnectionException("No available connection pool for node: " + node.getId());
        }
        
        try {
            return pool.borrowObject(100, TimeUnit.MILLISECONDS); // 最多等待 100ms
        } catch (Exception e) {
            throw new StoreConnectionException("Failed to borrow connection", e);
        }
    }
}
```

### 20.6 同机房路由策略的实现

Squirrel 客户端支持"同机房优先"（`idcSensitive`）和"同城优先"（`regionSensitive`）的路由策略。实现逻辑如下：

```java
public class ReadNodeSelector {
    
    /**
     * 为读请求选择目标节点
     * @param slot 目标 slot
     * @param readStrategy 读策略（master-only / master-slave / slave-only）
     * @param idcSensitive 是否同机房优先
     * @param currentIdc 当前客户端所在机房
     * @return 选中的节点
     */
    public NodeInfo selectReadNode(int slot, String readStrategy, 
            boolean idcSensitive, String currentIdc) {
        
        NodeInfo master = routeTable.getMaster(slot);
        List<NodeInfo> slaves = routeTable.getSlaves(slot);
        
        // 1. 根据读策略确定候选集合
        List<NodeInfo> candidates = new ArrayList<>();
        switch (readStrategy) {
            case "master-only":
                candidates.add(master);
                break;
            case "slave-only":
                candidates.addAll(slaves);
                break;
            case "master-slave":
                candidates.add(master);
                candidates.addAll(slaves);
                break;
        }
        
        // 2. 过滤掉不健康的节点
        candidates = candidates.stream()
            .filter(NodeInfo::isHealthy)
            .collect(Collectors.toList());
        
        if (candidates.isEmpty()) {
            throw new NoAvailableNodeException("No healthy node for slot: " + slot);
        }
        
        // 3. 如果开启了同机房优先，优先选择同机房的节点
        if (idcSensitive) {
            List<NodeInfo> sameIdcNodes = candidates.stream()
                .filter(n -> currentIdc.equals(n.getIdc()))
                .collect(Collectors.toList());
            if (!sameIdcNodes.isEmpty()) {
                candidates = sameIdcNodes;
            }
            // 如果没有同机房节点，退回到全量候选集合
        }
        
        // 4. 在候选集合中随机选择（负载均衡）
        return candidates.get(ThreadLocalRandom.current().nextInt(candidates.size()));
    }
}
```

路由策略的优先级和降级链路：

```
读请求路由选择优先级链路：

  1. 读策略筛选（master-only / master-slave / slave-only）
       │
       ▼
  2. 健康状态过滤（排除 PFAIL / FAIL 节点）
       │
       ▼
  3. 同机房优先（如果开启 idcSensitive）
       │  有同机房节点 → 使用同机房节点
       │  无同机房节点 → 降级
       ▼
  4. 同城优先（如果开启 regionSensitive）
       │  有同城节点 → 使用同城节点
       │  无同城节点 → 降级
       ▼
  5. 全量候选集合中随机选择（最终兜底）
```

## 21. 序列化协议深入：Hessian、Kryo、JSON、Protobuf 全面对比

序列化是客户端 SDK 中看似不起眼但实际影响深远的组件。序列化协议的选择直接影响网络带宽消耗、CPU 占用、跨语言兼容性和版本演进能力。这一节我们深入对比 Squirrel 支持和常见的几种序列化协议。

### 21.1 Hessian 序列化详解

Hessian 是 Squirrel 默认使用的序列化协议，由 Caucho 公司开发，是一种二进制序列化协议。美团内部大量使用 Hessian 作为服务调用的序列化协议，Squirrel 沿用这一选择可以保持技术栈一致性。

**Hessian3 vs Hessian4 的差异：**

| 对比维度 | Hessian3 | Hessian4 |
| --- | --- | --- |
| 版本 | 1.x / 2.x（传统版本） | 4.x（基于 Hessian2 协议） |
| 序列化效率 | 较低 | 较高（紧凑的二进制格式） |
| 兼容性 | 广泛兼容旧系统 | 与 Hessian3 不完全兼容 |
| 对枚举的处理 | 按名称序列化 | 按名称序列化，但有行为差异 |
| 对循环引用的处理 | 不支持 | 支持 |
| 美团内部推荐 | 推荐使用 | 不推荐（兼容性问题多） |

Hessian 序列化自定义对象时的存储格式：

```
Hessian 序列化一个 User 对象的示例：

Java 对象：
class User {
    String name = "Alice";
    int age = 25;
    List<String> tags = ["vip", "new"];
}

Hessian3 序列化后的二进制（简化表示）：
┌─────────────────────────────────────────────────────────┐
│ M com.sankuai.User           ← 类名                     │
│ name                         ← 字段名                    │
│ age                          ← 字段名                    │
│ tags                         ← 字段名                    │
│ S Alice                      ← 字段值（String）          │
│ I 25                         ← 字段值（Integer）         │
│ List                         ← 字段值类型                │
│   S vip                      ← 列表元素                  │
│   S new                      ← 列表元素                  │
│ z                            ← 结束标记                  │
└─────────────────────────────────────────────────────────┘

注意：类名和字段名每次都会完整序列化，这是 Hessian 的一个性能开销点。
```

**Hessian 使用的常见坑：**

```java
// 坑1：缺少无参构造函数
// Hessian 反序列化时会通过反射调用无参构造函数创建对象实例
// 如果没有无参构造函数，可能会创建出字段全为 null 的对象
public class User {
    private String name;
    
    // 只有有参构造函数 → Hessian 反序列化时可能出问题
    public User(String name) {
        this.name = name;
    }
    
    // 正确做法：提供无参构造函数
    public User() {}
}

// 坑2：类路径不一致
// 应用 A 中 User 类的包名是 com.waimai.User
// 应用 B 中 User 类的包名是 com.jiudian.User
// 应用 A 写入的对象，应用 B 读取时无法反序列化为 User，会退化为 HashMap
// 然后在业务代码里 (User) map 时抛出 ClassCastException

// 坑3：serialVersionUID 不一致
// 虽然不像 Java 原生序列化那样强制要求，但建议显式声明
// 避免类结构变更后反序列化失败
public class User implements Serializable {
    private static final long serialVersionUID = 1L;
    // ...
}

// 坑4：Hessian3 和 Hessian4 混用
// 应用 A 用 Hessian3 写入，应用 B 用 Hessian4 读取（或反之）
// 可能导致反序列化失败或数据错误
// 解决方案：全公司统一使用同一个版本
```

### 21.2 Kryo 序列化

Kryo 是另一种高性能的 Java 序列化框架，在社区中也有广泛应用。

```java
// Kryo 序列化示例
public class KryoSerializer {
    private static final ThreadLocal<Kryo> kryoLocal = ThreadLocal.withInitial(() -> {
        Kryo kryo = new Kryo();
        kryo.setReferences(true);        // 支持循环引用
        kryo.setRegistrationRequired(false);  // 不强制注册
        return kryo;
    });
    
    private static final ThreadLocal<Output> outputLocal = ThreadLocal.withInitial(() -> 
        new Output(4096, 65536));
    
    private static final ThreadLocal<Input> inputLocal = ThreadLocal.withInitial(() -> 
        new Input(4096));
    
    public byte[] serialize(Object obj) {
        Kryo kryo = kryoLocal.get();
        Output output = outputLocal.get();
        output.clear();
        kryo.writeClassAndObject(output, obj);
        return output.toBytes();
    }
    
    public Object deserialize(byte[] bytes) {
        Kryo kryo = kryoLocal.get();
        Input input = inputLocal.get();
        input.setBuffer(bytes);
        return kryo.readClassAndObject(input);
    }
}
```

### 21.3 JSON 序列化

JSON 是最通用的序列化格式，跨语言支持最好，但序列化后的体积最大。

```java
// JSON 序列化示例（以 Jackson 为例）
public class JsonSerializer {
    private static final ObjectMapper mapper = new ObjectMapper();
    
    static {
        mapper.configure(SerializationFeature.FAIL_ON_EMPTY_BEANS, false);
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        mapper.registerModule(new JavaTimeModule()); // 支持 Java 8 时间类型
    }
    
    public byte[] serialize(Object obj) throws IOException {
        return mapper.writeValueAsBytes(obj);
    }
    
    public <T> T deserialize(byte[] bytes, Class<T> clazz) throws IOException {
        return mapper.readValue(bytes, clazz);
    }
}
```

### 21.4 Protobuf 序列化

Protocol Buffers 是 Google 开发的高效序列化协议，需要预定义 `.proto` 文件。

```protobuf
// user.proto
syntax = "proto3";

message User {
    string name = 1;
    int32 age = 2;
    repeated string tags = 3;
}
```

```java
// Protobuf 序列化示例
public class ProtobufSerializer {
    public byte[] serialize(User user) {
        return user.toByteArray();
    }
    
    public User deserialize(byte[] bytes) throws InvalidProtocolBufferException {
        return User.parseFrom(bytes);
    }
}
```

### 21.5 四种序列化协议的全面对比

| 对比维度 | Hessian3 | Kryo | JSON (Jackson) | Protobuf |
| --- | --- | --- | --- | --- |
| 序列化格式 | 二进制 | 二进制 | 文本 | 二进制 |
| 序列化速度 | 中等 | 快 | 慢 | 快 |
| 反序列化速度 | 中等 | 快 | 慢 | 快 |
| 序列化体积 | 中等 | 小 | 大 | 最小 |
| 跨语言支持 | 支持（Java/C++/Python等） | 仅 Java | 支持（所有语言） | 支持（所有主流语言） |
| 是否需要预编译 | 否 | 否 | 否 | 是（需要 .proto 文件） |
| Schema 演进 | 支持增删字段 | 支持增删字段 | 天然兼容 | 支持增删字段（有规则） |
| 循环引用支持 | Hessian4 支持 | 支持 | 不支持 | 不支持 |
| 美团内部使用 | 默认推荐 | 不常用 | 不常用 | 不常用（部分新系统使用） |
| 适用场景 | 通用 Java 对象 | 纯 Java 高性能场景 | 跨语言、人类可读 | 跨语言、高性能、严格 schema |

**序列化体积对比（以 User 对象为例）：**

```
User 对象：name="Alice", age=25, tags=["vip","new"]

Hessian3：约 85 字节
Kryo：    约 45 字节
JSON：    约 62 字节  {"name":"Alice","age":25,"tags":["vip","new"]}
Protobuf：约 22 字节

体积比 ≈ Hessian3 : Kryo : JSON : Protobuf = 3.9 : 2.1 : 2.8 : 1.0
```

### 21.6 自定义序列化

如果默认的 Hessian 序列化不满足需求，Squirrel 也支持自定义序列化。最简单的方式是直接使用 `setBytes` / `getBytes` 接口，完全自行掌控序列化逻辑：

```java
// 使用自定义序列化的示例
public class CustomSerializationExample {
    private SquirrelStoreClient client;
    private ProtobufSerializer protobufSerializer = new ProtobufSerializer();
    
    // 写入：自定义序列化后以 byte[] 形式存储
    public void storeUser(StoreKey key, User user) {
        byte[] data = protobufSerializer.serialize(user);
        client.setBytes(key, data);
    }
    
    // 读取：以 byte[] 形式取出后自行反序列化
    public User getUser(StoreKey key) {
        byte[] data = client.getBytes(key);
        if (data == null) {
            return null;
        }
        return protobufSerializer.deserialize(data);
    }
}
```

### 21.7 序列化协议选型建议

```
序列化协议选型决策树：

是否需要跨语言？
  是 → 对性能要求极高？
        是 → Protobuf
        否 → JSON
  否 → 对性能要求极高？
        是 → Kryo
        否 → Hessian3（默认推荐，与美团技术栈一致）

补充建议：
- 如果没有特殊需求，始终使用默认的 Hessian3
- 如果存储的是基本类型（String/Integer/Long），不需要序列化，直接用 set/get
- 如果存储的是大对象，考虑使用更紧凑的序列化协议（如 Protobuf）来减少网络开销
- 切换序列化协议时，必须先清理旧数据，否则新协议无法反序列化旧数据
```

## 22. 持久化机制优化：从 RDB 到混合持久化

虽然 Squirrel 定位为"纯内存缓存"，默认情况下数据不持久化，但在某些场景下（比如缓存重建成本极高的场景），业务方会选择开启持久化。原生 Redis 的 RDB 和 AOF 持久化机制存在一些已知的性能问题（特别是 `fork()` 造成的阻塞），Squirrel 在这方面做了大量优化。

### 22.1 RDB 快照机制

RDB（Squirrel Database）是 Squirrel 的全量持久化方式，通过 `fork()` 子进程把内存数据以二进制格式写入磁盘文件。

```
┌──────────────────────────────────────────────────────────────┐
│                    RDB 快照流程                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  主进程                       子进程                          │
│                                                              │
│  1. 执行 BGSAVE                                              │
│  2. fork() ──────────────────▶ 创建子进程                     │
│     (写时复制 COW)                                           │
│                              3. 遍历内存数据                  │
│                              4. 序列化为 RDB 格式             │
│                              5. 写入临时文件 dump.rdb.tmp     │
│                              6. rename 为 dump.rdb            │
│  7. 收到子进程完成信号 ◀────── 8. 退出                        │
│  9. 更新统计信息                                              │
│                                                              │
│  注意：fork() 本身是阻塞的！                                 │
│  - 小实例（< 1GB）：fork 耗时几毫秒到几十毫秒                 │
│  - 大实例（> 10GB）：fork 耗时可能达到数百毫秒甚至秒级        │
│  - fork 期间主线程无法处理任何请求                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

RDB 的优缺点：

| 优点 | 缺点 |
| --- | --- |
| 文件紧凑，恢复速度快 | fork() 阻塞主线程（大内存实例尤为严重） |
| 适合做定期全量备份 | 两次快照之间的数据可能丢失 |
| 对日常性能影响小（除了 fork 瞬间） | 不适合对数据完整性要求高的场景 |

### 22.2 AOF 追加日志机制

AOF（Append Only File）是 Squirrel 的增量持久化方式，把每条写命令追加到日志文件中。

```
AOF 工作流程：

  客户端写入命令
       │
       ▼
  ┌─────────────┐
  │  Squirrel 主线程 │
  │  执行命令     │
  └──────┬──────┘
         │
         ▼
  ┌─────────────────┐
  │  AOF 缓冲区      │  ← 命令追加到内存缓冲区
  │  (aof_buf)       │
  └──────┬──────────┘
         │  根据 appendfsync 策略刷盘
         ▼
  ┌─────────────────┐
  │  AOF 文件        │  ← 写入磁盘文件
  │  appendonly.aof  │
  └─────────────────┘

  appendfsync 策略：
  ┌──────────┬───────────────────┬───────────────┐
  │  策略     │  刷盘时机          │  数据安全性    │
  ├──────────┼───────────────────┼───────────────┤
  │  always  │  每条命令都刷盘     │  最高（不丢数据）│
  │  everysec│  每秒刷一次         │  高（最多丢1秒）│
  │  no      │  由操作系统决定     │  最低          │
  └──────────┴───────────────────┴───────────────┘
```

### 22.3 AOF 重写机制

AOF 文件会随着写操作不断增长，需要进行重写（Rewrite）来压缩文件体积。重写的原理是：遍历当前内存中的所有数据，用最少的命令重新生成一份 AOF 文件。

```
AOF 重写流程：

  1. 主进程 fork() 出子进程

  2. 子进程遍历内存，生成新的 AOF 文件
     例如：原来的 AOF 中有：
       SET key1 "v1"
       SET key1 "v2"    ← 覆盖了 v1
       SET key1 "v3"    ← 覆盖了 v2
       LPUSH list "a"
       LPUSH list "b"
       LPUSH list "c"
     重写后变成：
       SET key1 "v3"
       LPUSH list "a" "b" "c"

  3. 重写期间，主进程继续处理新的写命令
     新命令同时写入：
     ├── 旧 AOF 文件（保底）
     └── AOF 重写缓冲区（aof_rewrite_buf）

  4. 子进程完成重写后通知主进程

  5. 主进程把重写缓冲区中的增量命令追加到新 AOF 文件

  6. 原子替换旧 AOF 文件
```

AOF 重写同样需要 `fork()`，存在与 RDB 相同的阻塞问题。此外，如果重写期间写入量很大，重写缓冲区可能占用大量内存。

### 22.4 Squirrel 的持久化优化

Squirrel 针对原生 Redis 持久化的问题做了以下优化：

**优化一：异步 fork（forkless RDB）**

```
原生 Redis：                    Squirrel 优化：
┌──────────┐                   ┌──────────────────────┐
│ 主线程    │                   │ 主线程                │
│ fork()   │ ← 阻塞            │ 触发持久化            │
│ 等待...  │                   │ └── 委托给后台线程     │
│ 继续处理 │                   │     后台线程执行 fork │
└──────────┘                   │ 主线程继续处理请求     │
                               └──────────────────────┘

原理：利用 Linux 的 clone() 系统调用和内存映射技术，
      在后台线程中创建子进程，主线程不阻塞。
```

**优化二：增量 RDB**

```
传统 RDB：每次全量快照，数据量大时耗时长
Squirrel 增量 RDB：
  - 第一次做全量快照
  - 后续只记录自上次快照以来的变更
  - 定期合并增量数据到全量快照
  - 大幅减少单次持久化的数据量和耗时
```

**优化三：混合持久化（RDB + AOF）**

```
Squirrel 4.0+ 支持的混合持久化格式：

  ┌───────────────────────────────────────────┐
  │              AOF 文件                      │
  │  ┌─────────────────────────────────────┐  │
  │  │  RDB 格式的全量数据                  │  │  ← 前半部分
  │  │  （二进制，紧凑）                     │  │
  │  └─────────────────────────────────────┘  │
  │  ┌─────────────────────────────────────┐  │
  │  │  AOF 格式的增量命令                  │  │  ← 后半部分
  │  │  （文本，自 RDB 后的变更）            │  │
  │  └─────────────────────────────────────┘  │
  └───────────────────────────────────────────┘

恢复时：
  1. 先加载 RDB 部分（快速恢复大部分数据）
  2. 再重放 AOF 部分（恢复最近的增量变更）

优点：
  - 恢复速度快（RDB 部分加载比纯 AOF 重放快得多）
  - 数据完整性高（AOF 部分保证不丢最近的变更）
```

**优化四：异步刷盘**

```java
// Squirrel 持久化配置示例
// Squirrel.conf
"""
# 持久化模式：none / rdb / aof / hybrid
persistence-mode: hybrid

# RDB 快照触发条件
save 900 1      # 900秒内至少1个key变更则触发快照
save 300 10     # 300秒内至少10个key变更则触发快照
save 60 10000   # 60秒内至少10000个key变更则触发快照

# AOF 配置
appendonly yes
appendfsync everysec  # 每秒刷盘一次

# 混合持久化
aof-use-rdb-preamble yes

# Squirrel 特有：异步刷盘线程数
async-fsync-threads 4

# Squirrel 特有：forkless RDB
forkless-rdb yes

# Squirrel 特有：增量 RDB
incremental-rdb yes
incremental-rdb-interval 300
"""
```

### 22.5 持久化对性能的影响

| 持久化方式 | 对写入延迟的影响 | 对内存的影响 | 数据丢失风险 | 适用场景 |
| --- | --- | --- | --- | --- |
| 关闭持久化 | 无 | 无 | 完全丢失（重启即清空） | 纯缓存，数据可从 DB 重建 |
| RDB only | fork 瞬间有抖动 | fork 时 COW 可能翻倍内存 | 丢失最近一次快照后的数据 | 可接受少量数据丢失的缓存 |
| AOF only (everysec) | 极小（每秒一次 fsync） | AOF 缓冲区约几 MB | 最多丢失 1 秒数据 | 对数据完整性有一定要求 |
| 混合持久化 | RDB 部分有 fork 抖动 | 同 AOF | 最多丢失 1 秒数据 | 兼顾恢复速度和数据完整性 |

### 22.6 Squirrel 中持久化的使用建议

```
是否需要开启持久化的决策树：

数据是否可以从数据库重建？
  是 → 不需要开启持久化（纯缓存模式，性能最优）
  否 → 继续判断

数据丢失（最多1秒）是否可接受？
  否 → 不适合用 Squirrel，考虑使用 Cellar（强持久化）
  是 → 继续判断

数据总量是否小于 10GB？
  是 → 开启混合持久化（RDB + AOF）
       - fork 抖动可控
       - 恢复速度快
  否 → 开启 AOF only（everysec）
       - 避免 fork 大内存实例的严重抖动
       - 配合 Squirrel 的 forkless 优化

补充注意：
- 开启持久化会增加 CPU 和 IO 开销，QPS 会有 5%~15% 的下降
- 大内存实例（> 20GB）开启 RDB 时务必开启 forkless-rdb
- 持久化文件建议存放到独立磁盘，避免 IO 竞争
```

## 23. 读写分离详细实现：同机房优先与降级策略

Squirrel 的读写分离不仅仅是简单地把读请求分发到从节点，它还涉及到同机房路由、延迟检测、降级策略等一系列复杂逻辑。这一节我们完整拆解这套机制。

### 23.1 读写分离的整体架构

```
┌──────────────────────────────────────────────────────────────┐
│                  读写分离路由架构                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                        业务请求                               │
│                            │                                 │
│                            ▼                                 │
│                    ┌──────────────┐                          │
│                    │  读写判断     │                          │
│                    └──┬───────┬───┘                          │
│                       │       │                              │
│              写请求   │       │  读请求                      │
│                       ▼       ▼                              │
│              ┌──────────┐  ┌──────────────────────┐          │
```

### 23.2 同机房优先路由

同机房优先路由的核心目标是：**让读请求尽可能落在与客户端同一机房的节点上**，从而避免跨机房网络延迟。

```java
public class IdcAwareNodeSelector {
    
    // 机房延迟矩阵（由后台线程定期探测并更新）
    // idcLatency[fromIdc][toIdc] = 平均延迟（ms）
    private volatile Map<String, Map<String, Double>> idcLatencyMatrix;
    
    // 各节点的延迟统计
    private Map<String, LatencyStats> nodeLatencyStats = new ConcurrentHashMap<>();
    
    /**
     * 选择读节点（完整逻辑）
     */
    public NodeInfo selectReadNode(ReadContext ctx) {
        int slot = ctx.getSlot();
        String currentIdc = ctx.getClientIdc();
        String currentRegion = ctx.getClientRegion();
        
        // 获取该 slot 的所有候选节点
        List<NodeInfo> candidates = getCandidates(slot, ctx.getReadStrategy());
        
        // 第一优先级：同机房 + 健康 + 低延迟
        List<NodeInfo> sameIdcHealthy = candidates.stream()
            .filter(n -> currentIdc.equals(n.getIdc()))
            .filter(n -> n.isHealthy())
            .filter(n -> getAvgLatency(n) < 2.0)  // 延迟 < 2ms
            .collect(Collectors.toList());
        
        if (!sameIdcHealthy.isEmpty()) {
            return loadBalance(sameIdcHealthy);
        }
        
        // 第二优先级：同机房 + 健康（放宽延迟要求）
        List<NodeInfo> sameIdcAny = candidates.stream()
            .filter(n -> currentIdc.equals(n.getIdc()))
            .filter(NodeInfo::isHealthy)
            .collect(Collectors.toList());
        
        if (!sameIdcAny.isEmpty()) {
            log.warn("Same-IDC node latency > 2ms, but still using it");
            return loadBalance(sameIdcAny);
        }
        
        // 第三优先级：同城 + 健康
        List<NodeInfo> sameRegionHealthy = candidates.stream()
            .filter(n -> currentRegion.equals(n.getRegion()))
            .filter(NodeInfo::isHealthy)
            .collect(Collectors.toList());
        
        if (!sameRegionHealthy.isEmpty()) {
            return loadBalance(sameRegionHealthy);
        }
        
        // 第四优先级：任意健康节点
        List<NodeInfo> anyHealthy = candidates.stream()
            .filter(NodeInfo::isHealthy)
            .collect(Collectors.toList());
        
        if (!anyHealthy.isEmpty()) {
            log.warn("No same-IDC or same-region node available, using remote node");
            return loadBalance(anyHealthy);
        }
        
        // 所有从节点都不可用，降级到主节点
        NodeInfo master = routeTable.getMaster(slot);
        if (master != null && master.isHealthy()) {
            log.warn("All slaves unavailable, falling back to master for read");
            return master;
        }
        
        throw new NoAvailableNodeException("No available node for slot: " + slot);
    }
    
    // 负载均衡：在候选节点中随机选择
    private NodeInfo loadBalance(List<NodeInfo> candidates) {
        // 可以加入权重因子：延迟低的节点被选中概率更高
        return candidates.get(ThreadLocalRandom.current().nextInt(candidates.size()));
    }
}
```

### 23.3 延迟检测机制

Squirrel 客户端内置了延迟检测机制，定期探测各节点的响应延迟，用于路由决策：

```java
public class LatencyDetector {
    private static final long DETECT_INTERVAL = 5000; // 5 秒探测一次
    private static final int SAMPLE_SIZE = 10;        // 每次探测 10 个样本
    
    private ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
    private Map<String, LatencyStats> statsMap = new ConcurrentHashMap<>();
    
    public void start() {
        scheduler.scheduleAtFixedRate(this::detectAllNodes, 
            0, DETECT_INTERVAL, TimeUnit.MILLISECONDS);
    }
    
    private void detectAllNodes() {
        for (NodeInfo node : routeTable.getAllNodes()) {
            if (!node.isHealthy()) continue;
            
            long totalLatency = 0;
            int successCount = 0;
            
            for (int i = 0; i < SAMPLE_SIZE; i++) {
                try {
                    long start = System.nanoTime();
                    // 发送一个轻量级命令（PING）
                    Connection conn = getConnection(node);
                    conn.sendCommand("PING");
                    String response = conn.getBulkReply();
                    long latency = (System.nanoTime() - start) / 1_000_000; // 转为毫秒
                    
                    if ("PONG".equals(response)) {
                        totalLatency += latency;
                        successCount++;
                    }
                } catch (Exception e) {
                    // 探测失败
                }
            }
            
            if (successCount > 0) {
                double avgLatency = (double) totalLatency / successCount;
                LatencyStats stats = statsMap.computeIfAbsent(
                    node.getId(), k -> new LatencyStats());
                stats.update(avgLatency, successCount, SAMPLE_SIZE);
                
                // 如果延迟过高，标记节点为"慢节点"
                if (avgLatency > 10.0) {
                    log.warn("Node {} latency too high: {}ms", 
                        node.getId(), avgLatency);
                    stats.setSlow(true);
                }
            }
        }
    }
}

// 延迟统计
public class LatencyStats {
    private volatile double avgLatency;      // 平均延迟
    private volatile double p99Latency;      // P99 延迟
    private volatile double successRate;     // 探测成功率
    private volatile boolean isSlow;         // 是否被标记为慢节点
    private volatile long lastUpdate;        // 最后更新时间
    
    public void update(double avgLatency, int successCount, int totalCount) {
        this.avgLatency = avgLatency;
        this.successRate = (double) successCount / totalCount;
        this.isSlow = avgLatency > 10.0;
        this.lastUpdate = System.currentTimeMillis();
    }
}
```

### 23.4 降级策略

当读请求在从节点上失败时，Squirrel 客户端有一套完整的降级链路：

```
读请求降级链路：

  1. 尝试从同机房从节点读取
     │
     ├─ 成功 → 返回结果
     │
     └─ 失败（超时/连接异常）
         │
         ▼
  2. 重试同机房的其他从节点
     │
     ├─ 成功 → 返回结果
     │
     └─ 失败 或 无其他同机房从节点
         │
         ▼
  3. 尝试同城其他机房的从节点
     │
     ├─ 成功 → 返回结果
     │
     └─ 失败
         │
         ▼
  4. 降级到主节点读取
     │
     ├─ 成功 → 返回结果
     │
     └─ 失败
         │
         ▼
  5. 最终兜底：返回 null 或抛出异常
     └── 由业务代码决定是否降级到数据库
```

```java
// 降级策略的代码实现（简化版）
public class ReadWithFallback {
    private SquirrelStoreClient client;
    private int maxRetries = 2;
    private long retryIntervalMs = 50;
    
    public <T> T readWithFallback(StoreKey key, Class<T> type) {
        Exception lastException = null;
        
        for (int attempt = 0; attempt <= maxRetries; attempt++) {
            try {
                T result = client.get(key, type);
                return result; // 成功，直接返回
            } catch (JedisConnectionException e) {
                lastException = e;
                log.warn("Read attempt {} failed for key: {}", attempt, key, e);
                
                if (attempt < maxRetries) {
                    try {
                        Thread.sleep(retryIntervalMs * (attempt + 1)); // 退避
                    } catch (InterruptedException ie) {
                        Thread.currentThread().interrupt();
                        break;
                    }
                }
            } catch (StoreException e) {
                // 非连接异常，不重试
                throw e;
            }
        }
        
        // 所有重试都失败，业务自行决定是否降级到数据库
        log.error("All read attempts failed for key: {}", key, lastException);
        return null; // 或 throw new StoreReadException(lastException);
    }
}
```

### 23.5 读写分离的数据不一致问题

使用读写分离时，读从节点可能读到旧数据（因为主从复制是异步的）。Squirrel 提供了几种应对策略：

| 策略 | 实现方式 | 适用场景 |
| --- | --- | --- |
| 写后强制读主 | 写操作后，在短时间窗口内（如 500ms）的读请求强制路由到主节点 | 对一致性有一定要求的场景 |
| 会话粘连 | 同一会话内的读写都路由到主节点 | 用户级数据（如用户信息修改后立即查看） |
| 版本号校验 | 数据带版本号，从节点读到旧版本时触发从主节点重读 | 对一致性要求较高的场景 |
| 异步复制延迟监控 | 监控主从延迟，延迟过大时自动切换到读主 | 自动化的一致性保障 |

```java
// 写后强制读主的实现示例
public class WriteAwareReadPolicy {
    // 记录最近写入的 key 和时间
    private Cache<String, Long> recentWrites = Caffeine.newBuilder()
        .expireAfterWrite(500, TimeUnit.MILLISECONDS)  // 500ms 窗口
        .maximumSize(100000)
        .build();
    
    public void set(StoreKey key, Object value) {
        client.set(key, value);
        // 记录写入时间
        recentWrites.put(key.toString(), System.currentTimeMillis());
    }
    
    public <T> T get(StoreKey key, Class<T> type) {
        // 检查是否在写入窗口内
        Long writeTime = recentWrites.getIfPresent(key.toString());
        if (writeTime != null) {
            // 强制读主
            return client.getFromMaster(key, type);
        }
        // 正常的读写分离读
        return client.get(key, type);
    }
}
```

```java
// 复制延迟监控（简化版）
public class ReplicationLatencyMonitor {
    // 记录主集群写入时间 → 备集群确认时间
    private BlockingQueue<LatencyRecord> latencyQueue = 
        new LinkedBlockingQueue<>(10000);
    
    // 写入标记
    public void markWrite(String key, String value) {
        LatencyRecord record = new LatencyRecord(
            key, value, System.currentTimeMillis());
        latencyQueue.offer(record);
    }
    
    // 备集群确认
    public void markReplicated(String key, String value) {
        long now = System.currentTimeMillis();
        // 查找对应的写入记录
        Iterator<LatencyRecord> it = latencyQueue.iterator();
        while (it.hasNext()) {
            LatencyRecord record = it.next();
            if (record.matches(key, value)) {
                long latency = now - record.getWriteTime();
                updateLatencyStats(latency);
                it.remove();
                break;
            }
        }
    }
    
    // 延迟统计
    private DescriptiveStatistics latencyStats = new DescriptiveStatistics(1000);
    
    private void updateLatencyStats(long latencyMs) {
        latencyStats.addValue(latencyMs);
        
        if (latencyMs > 1000) {
            // 延迟超过 1 秒，告警
            log.warn("Replication latency too high: {}ms", latencyMs);
            alertService.sendAlert("replication_latency_high", 
                String.format("Latency: %dms", latencyMs));
        }
    }
    
    public double getAvgLatency() {
        return latencyStats.getMean();
    }
    
    public double getP99Latency() {
        return latencyStats.getPercentile(99);
    }
}
```

## 25. 热点 Key 检测算法：从滑动窗口到自适应阈值

热点 Key 检测是 Squirrel 最具技术含量的能力之一。前面章节概述了"自动发现 + 自动隔离"的机制，这里我们深入到算法层面。

### 25.1 滑动窗口计数器

滑动窗口是最基础的热点检测算法，通过在时间窗口内统计 Key 的访问频次来识别热点。

```
滑动窗口计数器原理：

  时间窗口：5 秒，子窗口粒度：1 秒（5 个子窗口）

  时间轴 ──────────────────────────────────────▶
  
  子窗口:  [T-4]  [T-3]  [T-2]  [T-1]  [T-0]
  
  T-4 时刻: key_A 访问 100 次
  T-3 时刻: key_A 访问 150 次
  T-2 时刻: key_A 访问 200 次
  T-1 时刻: key_A 访问 180 次
  T-0 时刻: key_A 访问 220 次
  
  当前窗口内 key_A 的总访问量 = 100+150+200+180+220 = 850 次
  
  如果阈值 = 500 次/5秒，则 key_A 被判定为热点
```

```java
// 滑动窗口计数器实现（简化版）
public class SlidingWindowCounter {
    private static final int WINDOW_SIZE = 5;        // 窗口大小 5 秒
    private static final int SLICE_SIZE = 1;          // 子窗口 1 秒
    private static final int SLICE_COUNT = WINDOW_SIZE / SLICE_SIZE;
    
    // 每个 key 对应一个环形数组
    private ConcurrentHashMap<String, WindowSlice[]> keyWindows = 
        new ConcurrentHashMap<>();
    
    // 窗口切片
    static class WindowSlice {
        long timestamp;  // 切片起始时间戳
        int count;       // 计数
        
        void increment() {
            count++;
        }
        
        void reset(long ts) {
            timestamp = ts;
            count = 1;
        }
    }
    
    public void record(String key) {
        WindowSlice[] windows = keyWindows.computeIfAbsent(key, 
            k -> new WindowSlice[SLICE_COUNT]);
        
        long now = System.currentTimeMillis() / 1000;
        int sliceIndex = (int)(now % SLICE_COUNT);
        
        synchronized (windows) {
            WindowSlice slice = windows[sliceIndex];
            if (slice == null) {
                slice = new WindowSlice();
                windows[sliceIndex] = slice;
                slice.reset(now);
            } else if (now - slice.timestamp >= SLICE_COUNT) {
                // 切片过期，重置
                slice.reset(now);
            } else {
                slice.increment();
            }
        }
    }
    
    public int getCount(String key) {
        WindowSlice[] windows = keyWindows.get(key);
        if (windows == null) return 0;
        
        long now = System.currentTimeMillis() / 1000;
        int totalCount = 0;
        
        for (WindowSlice slice : windows) {
            if (slice != null && (now - slice.timestamp) < WINDOW_SIZE) {
                totalCount += slice.count;
            }
        }
        return totalCount;
    }
}
```

### 25.2 TopK 算法

在海量 Key 中找出访问量最高的 TopK 个 Key，如果对每个 Key 都维护计数器，内存开销会非常大。Squirrel 使用了**Space-Saving 算法**来高效地跟踪 TopK 热点 Key。

```
Space-Saving 算法原理：

  维护一个固定大小 K 的计数器集合（如 K=1000）

  对于每个访问的 key：
  1. 如果 key 已在集合中，计数器 +1
  2. 如果 key 不在集合中：
     a. 如果集合未满（< K），添加新条目，计数器 = 1
     b. 如果集合已满（= K），替换计数最小的条目：
        - 新 key 的计数 = 被替换 key 的计数 + 1
        - 这是一种"近似"——新 key 的实际访问量可能小于计数值
        
  特性：
  - 空间复杂度 O(K)，与总 Key 数量无关
  - 真正的热点 Key 一定会被保留在集合中
  - 非热点 Key 可能被误报（计数偏高），但不会漏报热点
  - 适合在 Squirrel 服务端实现，内存开销可控
```

```java
// Space-Saving TopK 算法实现（简化版）
public class SpaceSavingTopK {
    private final int capacity;
    private final ConcurrentHashMap<String, Long> counters;
    private final PriorityQueue<Map.Entry<String, Long>> minHeap;
    
    public SpaceSavingTopK(int capacity) {
        this.capacity = capacity;
        this.counters = new ConcurrentHashMap<>(capacity * 2);
        this.minHeap = new PriorityQueue<>(
            Comparator.comparingLong(Map.Entry::getValue));
    }
    
    public void increment(String key) {
        counters.compute(key, (k, v) -> v == null ? 1L : v + 1);
        
        // 如果超过容量，淘汰最小值
        if (counters.size() > capacity) {
            // 找到计数最小的 key
            String minKey = null;
            long minCount = Long.MAX_VALUE;
            for (Map.Entry<String, Long> entry : counters.entrySet()) {
                if (entry.getValue() < minCount) {
                    minCount = entry.getValue();
                    minKey = entry.getKey();
                }
            }
            if (minKey != null) {
                counters.remove(minKey);
            }
        }
    }
    
    public List<Map.Entry<String, Long>> getTopK(int k) {
        return counters.entrySet().stream()
            .sorted(Map.Entry.<String, Long>comparingByValue().reversed())
            .limit(k)
            .collect(Collectors.toList());
    }
}
```

### 25.3 LFU（Least Frequently Used）统计

Squirrel 4.0+ 引入了 LFU 淘汰策略，Squirrel 借助 LFU 的访问频次统计来辅助热点检测。

```
Squirrel LFU 计数器的编码方式：

  每个 Key 的 LRU 字段（24 bit）被重新编码为：
  
  ┌────────────────┬──────────────────────┐
  │  高 16 bit      │  低 8 bit             │
  │  最后访问时间    │  对数计数器           │
  │  （分钟精度）    │  (counter)            │
  └────────────────┴──────────────────────┘

  对数计数器的特性：
  - 8 bit 最大值为 255
  - 但使用对数衰减算法，可以表示远大于 255 的访问次数
  - 计数器递增概率：1 / (counter * lfu_log_factor + 1)
  - counter=255 时约表示 10,000,000 次访问
  
  对数计数器值与实际访问次数的对应关系（lfu_log_factor=10）：
  ┌────────────┬──────────────────┐
  │ counter 值  │ 实际访问次数（约） │
  ├────────────┼──────────────────┤
  │     1      │        1         │
  │     5      │       ~30        │
  │    10      │      ~150        │
  │    50      │    ~10,000       │
  │   100      │   ~100,000       │
  │   200      │  ~1,000,000      │
  │   255      │  ~10,000,000     │
  └────────────┴──────────────────┘
```

### 25.4 自适应阈值

固定的热点阈值难以适应不同时间段和不同集群规模的场景。Squirrel 使用了**自适应阈值**算法：

```java
// 自适应阈值算法（简化版）
public class AdaptiveHotKeyThreshold {
    // 基于历史访问分布动态计算阈值
    private DescriptiveStatistics accessFrequencyStats = 
        new DescriptiveStatistics(10000); // 保留最近 10000 个 Key 的访问频次
    
    private double multiplier = 3.0;  // 阈值 = 均值 * multiplier
    
    public boolean isHotKey(String key, int accessCount) {
        double threshold = calculateThreshold();
        return accessCount > threshold;
    }
    
    private double calculateThreshold() {
        if (accessFrequencyStats.getN() < 100) {
            return 500; // 默认阈值
        }
        
        double mean = accessFrequencyStats.getMean();
        double stdDev = accessFrequencyStats.getStandardDeviation();
        
        // 阈值 = 均值 + 3 倍标准差（99.7% 置信区间外为热点）
        return mean + multiplier * stdDev;
    }
    
    // 定期更新统计
    public void recordAccessFrequency(int frequency) {
        accessFrequencyStats.addValue(frequency);
    }
}
```

```
自适应阈值的效果示意：

  正常时段（QPS = 10,000）：
    平均每 Key QPS = 10
    标准差 = 20
    阈值 = 10 + 3*20 = 70
    → QPS > 70 的 Key 被判定为热点

  大促时段（QPS = 100,000）：
    平均每 Key QPS = 100
    标准差 = 200
    阈值 = 100 + 3*200 = 700
    → QPS > 700 的 Key 被判定为热点

  自适应的优势：不需要人工调整阈值，随负载自动适配
```

### 26.1 大 Key 扫描算法

Squirrel 的大 Key 扫描基于 Squirrel 的 `SCAN` 命令，采用渐进式扫描避免阻塞主线程：

```java
// 大 Key 扫描器（简化版）
public class BigKeyScanner {
    private static final int SCAN_COUNT = 100;  // 每次扫描 100 个 Key
    private static final long STRING_THRESHOLD = 5 * 1024;      // String 5KB
    private static final int COLLECTION_THRESHOLD = 1000;        // 集合 1000 个元素
    private static final long TOTAL_SIZE_THRESHOLD = 100 * 1024; // 总大小 100KB
    
    private Jedis jedis;
    private BigKeyReport report = new BigKeyReport();
    
    public BigKeyReport scan(String host, int port) {
        String cursor = "0";
        int totalScanned = 0;
        
        do {
            // 渐进式扫描
            ScanResult<String> scanResult = jedis.scan(cursor, 
                new ScanParams().count(SCAN_COUNT));
            
            List<String> keys = scanResult.getResult();
            cursor = scanResult.getCursor();
            
            for (String key : keys) {
                analyzeKey(key);
                totalScanned++;
                
                // 每扫描 1000 个 Key，休眠 1ms，避免影响正常请求
                if (totalScanned % 1000 == 0) {
                    try {
                        Thread.sleep(1);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        break;
                    }
                }
            }
        } while (!cursor.equals("0") && !Thread.currentThread().isInterrupted());
        
        report.setTotalScanned(totalScanned);
        return report;
    }
    
    private void analyzeKey(String key) {
        String type = jedis.type(key);
        
        switch (type) {
            case "string":
                analyzeString(key);
                break;
            case "hash":
                analyzeHash(key);
                break;
            case "list":
                analyzeList(key);
                break;
            case "set":
                analyzeSet(key);
                break;
            case "zset":
                analyzeZSet(key);
                break;
        }
    }
    
    private void analyzeString(String key) {
        long ttl = jedis.pttl(key);
        long size = jedis.strlen(key);
        
        if (size > STRING_THRESHOLD) {
            report.addBigKey(new BigKeyInfo(key, "string", size, 1, ttl));
        }
    }
    
    private void analyzeHash(String key) {
        long ttl = jedis.pttl(key);
        long fieldCount = jedis.hlen(key);
        
        if (fieldCount > COLLECTION_THRESHOLD) {
            // 采样估算总大小
            long sampleSize = Math.min(fieldCount, 10);
            Map<String, String> sample = jedis.hrandfieldWithValues(key, (int)sampleSize);
            long avgFieldSize = sample.entrySet().stream()
                .mapToLong(e -> e.getKey().length() + e.getValue().length())
                .sum() / sampleSize;
            long estimatedSize = avgFieldSize * fieldCount;
            
            report.addBigKey(new BigKeyInfo(key, "hash", 
                estimatedSize, fieldCount, ttl));
        }
    }
    
    // analyzeList / analyzeSet / analyzeZSet 类似...
}
```

### 26.3 渐进式删除

直接 `DEL` 一个大 Key 会阻塞主线程很长时间（特别是大 Hash/List/Set），Squirrel 提供了渐进式删除方案：

```java
// 渐进式删除工具（简化版）
public class ProgressiveBigKeyDeleter {
    private static final int BATCH_SIZE = 100;  // 每批删除 100 个元素
    private static final long SLEEP_BETWEEN_BATCH = 2; // 批次间休眠 2ms
    
    public void deleteBigKey(String key, String type) {
        switch (type) {
            case "hash":
                progressiveDeleteHash(key);
                break;
            case "list":
                progressiveDeleteList(key);
                break;
            case "set":
                progressiveDeleteSet(key);
                break;
            case "zset":
                progressiveDeleteZSet(key);
                break;
            case "string":
                // String 类型直接删除（DEL 的阻塞时间 = 网络传输时间）
                // 如果 String 超过 1MB，考虑先 SET 为空再 DEL
                if (jedis.strlen(key) > 1024 * 1024) {
                    jedis.set(key, ""); // 先清空内容
                    Thread.sleep(10);   // 等待复制传播
                    jedis.del(key);     // 再删除 Key
                } else {
                    jedis.del(key);
                }
                break;
        }
    }
    
    // 渐进式删除 Hash
    private void progressiveDeleteHash(String key) {
        long remaining = jedis.hlen(key);
        
        while (remaining > 0) {
            // 使用 HSCAN 获取一批 field
            ScanResult<Map.Entry<String, String>> scanResult = 
                jedis.hscan(key, String.valueOf(cursor), 
                    new ScanParams().count(BATCH_SIZE));
            
            // 批量删除这批 field
            String[] fieldsToDelete = scanResult.getResult().stream()
                .map(Map.Entry::getKey)
                .toArray(String[]::new);
            
            if (fieldsToDelete.length > 0) {
                jedis.hdel(key, fieldsToDelete);
            }
            
            remaining = jedis.hlen(key);
            
            // 休眠，避免影响正常请求
            Thread.sleep(SLEEP_BETWEEN_BATCH);
            
            cursor = scanResult.getCursor();
            if (cursor.equals("0")) break;
        }
        
        // 最终删除空 Key
        if (remaining == 0) {
            jedis.del(key);
        }
    }
    
    // 渐进式删除 List（使用 LTRIM）
    private void progressiveDeleteList(String key) {
        long length = jedis.llen(key);
        
        while (length > 0) {
            // 每次保留后半部分，删除前 BATCH_SIZE 个元素
            int batchSize = (int) Math.min(BATCH_SIZE, length);
            jedis.ltrim(key, batchSize, -1);
            length = jedis.llen(key);
            Thread.sleep(SLEEP_BETWEEN_BATCH);
        }
        
        jedis.del(key);
    }
    
    // 渐进式删除 Set（使用 SSCAN + SREM）
    private void progressiveDeleteSet(String key) {
        // 类似 Hash 的实现
    }
    
    // 渐进式删除 ZSet（使用 ZREMRANGEBYRANK）
    private void progressiveDeleteZSet(String key) {
        long cardinality = jedis.zcard(key);
        
        while (cardinality > 0) {
            // 每次删除排名最低的 BATCH_SIZE 个元素
            int batchSize = (int) Math.min(BATCH_SIZE, cardinality);
            jedis.zremrangeByRank(key, 0, batchSize - 1);
            cardinality = jedis.zcard(key);
            Thread.sleep(SLEEP_BETWEEN_BATCH);
        }
        
        jedis.del(key);
    }
}
```

### 27.2 内存碎片

内存碎片是 Squirrel 运维中最常见的问题之一。当 Squirrel 频繁修改和删除 Key 时，虽然逻辑上使用的内存减少了，但物理内存可能不会立即释放给操作系统，导致内存碎片。

```
内存碎片示例：

  初始状态（连续分配）：
  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │K1│K2│K3│K4│K5│K6│K7│K8│K9│K10│
  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  
  删除 K2, K4, K6, K8, K10 后：
  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │K1│  │K3│  │K5│  │K7│  │K9│   │
  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
       ↑     ↑     ↑     ↑     ↑
       碎片  碎片  碎片  碎片  碎片
  
  此时 used_memory = 5 个 Key 的大小
  但 used_memory_rss = 10 个 Key 的大小（物理内存未释放）
  碎片率 = used_memory_rss / used_memory = 2.0

碎片率解读：
  < 1.0：内存被有效利用（很少见，通常出现在 swap 场景）
  1.0 ~ 1.5：正常范围
  1.5 ~ 2.0：有碎片，建议关注
  > 2.0：碎片严重，需要处理
```

```bash

used_memory_rss:3221225472        # 操作系统分配的物理内存（3GB）

mem_allocator:jemalloc-5.1.0     # 分配器版本

# 手动触发碎片整理（Squirrel 4.0+）
$ redis-cli MEMORY PURGE

# 开启自动碎片整理（Squirrel 4.0+）

active-defrag-threshold-lower 10        # 碎片率超过 10% 才触发
active-defrag-threshold-upper 100       # 碎片率超过 100% 强制触发
active-defrag-cycle-min 1               # 最小 CPU 占比（%）
active-defrag-cycle-max 25              # 最大 CPU 占比（%）
```

### 27.3 内存池优化

Squirrel 对 Squirrel 的内存管理做了一个重要优化：**内存池预分配**。

```
原生 Redis 内存分配模式：
  每个 Key 的创建/修改/删除都向 jemalloc 申请/释放内存
  → 频繁的 malloc/free 系统调用
  → 内存碎片逐渐积累

Squirrel 内存池模式：
  ┌──────────────────────────────────────────┐
  │           Squirrel 内存池                  │
  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐   │

  - 分配/释放速度更快
```

### 27.4 大页（Huge Pages）与 THP

Linux 的透明大页（THP, Transparent Huge Pages）可以把传统的 4KB 内存页合并为 2MB 大页，减少 TLB miss。但对于 Squirrel 来说，THP 可能带来负面影响：

```
THP 对 Squirrel 的影响：

  原生场景（THP 关闭，4KB 页）：
  - fork() 时 COW 的粒度是 4KB
  - 即使只修改了 1 个字节，也只复制 1 个 4KB 页
  
  THP 场景（THP 开启，2MB 页）：
  - fork() 时 COW 的粒度是 2MB
  - 修改 1 个字节会复制整个 2MB 页
  - 在写入密集场景下，内存使用量可能暴增 512 倍（2MB/4KB）
  
  结论：Squirrel 应该关闭 THP
  $ echo never > /sys/kernel/mm/transparent_hugepage/enabled
```

### 27.5 内存优化最佳实践

| 优化项 | 方法 | 效果 |
| --- | --- | --- |
| 使用高效数据结构 | 用 Hash 替代多个 String（当字段数 < 100 时） | 减少 30%~50% 内存 |
| 压缩存储 | 使用 ziplist 编码的 Hash/List/ZSet | 减少 50%~80% 内存 |
| 共享对象池 | Squirrel 内置的整数对象池（0-9999） | 减少小整数对象的重复分配 |
| 设置 maxmemory | 限制 Squirrel 最大内存使用量 | 防止 OOM |
| 选择合适的淘汰策略 | allkeys-lru / volatile-lru / allkeys-lfu | 控制内存增长 |
| 关闭 THP | `echo never > .../enabled` | 避免 fork 内存暴增 |
| 开启 active defrag | `activedefrag yes` | 自动整理碎片 |
| 定期重启 | 在低峰期重启实例 | 彻底清理碎片 |

```
Squirrel 数据结构编码优化：

  Hash 类型：
  - 元素数 <= hash-max-ziplist-entries（默认 128）
  - 且每个元素大小 <= hash-max-ziplist-value（默认 64 字节）
  → 使用 ziplist 编码（紧凑、省内存）
  → 否则使用 hashtable 编码（快速、费内存）

  List 类型：
  - 元素数 <= list-max-ziplist-size（默认 -2，即 8KB）
  → 使用 ziplist 编码
  → 否则使用 quicklist 编码（ziplist + 链表）

  ZSet 类型：
  - 元素数 <= zset-max-ziplist-entries（默认 128）
  - 且每个元素大小 <= zset-max-ziplist-value（默认 64 字节）
  → 使用 ziplist 编码
  → 否则使用 skiplist 编码

  优化建议：
  - 适当调大 ziplist 阈值（如 entries=256, value=128）
  - 让更多数据使用 ziplist 编码
  - 但不要调太大（如 entries > 1000），否则影响写入性能
```

### 28.1 操作系统内核参数调优

```bash
# ========== 网络相关 ==========

# TCP backlog（连接队列大小）
```

| 场景 | 建议连接数 | 说明 |
| --- | --- | --- |
| 低 QPS（< 1000/s） | 8 | 足够处理请求，资源浪费最小 |
| 中等 QPS（1K-10K/s） | 16（默认） | 平衡性能和资源 |

```
连接数估算公式：

  理想连接数 = (QPS × 平均请求耗时ms) / 1000 × 安全系数

  安全系数 = 1.5

  - 突发流量（取 2~3 倍）
  - 不同节点的连接分配
  - 连接建立开销
  
  最终建议：max(默认值16, 估算值 × 3) = max(16, 12) = 16
```

### 28.4 Pipeline 与批量操作调优

```java
// Pipeline 批量操作示例
public class PipelineExample {
    private SquirrelStoreClient client;
    
    // 正确使用 Pipeline
    public Map<String, String> multiGet(List<StoreKey> keys) {
        // 分批：每批最多 512 个 Key（Squirrel 限制）
        int batchSize = 500;
        Map<String, String> results = new HashMap<>();
        
        for (int i = 0; i < keys.size(); i += batchSize) {
            List<StoreKey> batch = keys.subList(i, 
                Math.min(i + batchSize, keys.size()));
            
            // 使用 Pipeline 减少网络往返
            List<Object> responses = client.pipelined(batch, key -> {
                client.get(key);
            });
            
            for (int j = 0; j < batch.size(); j++) {
                String value = (String) responses.get(j);
                if (value != null) {
                    results.put(batch.get(j).toString(), value);
                }
            }
        }
        
        return results;
    }
}
```

```
Pipeline 性能对比：

  逐条 GET 1000 个 Key：
  - 网络往返：1000 次
  - 总耗时 ≈ 1000 × 0.5ms = 500ms
  
  Pipeline GET 1000 个 Key（1 批）：
  - 网络往返：1 次
  - 总耗时 ≈ 1 × 0.5ms + 1000 × 0.05ms（服务端处理）= 50.5ms
  
  性能提升 ≈ 10 倍
  
  但注意：
  - Pipeline 过大（> 512 Key）会被 Squirrel 拦截
  - Pipeline 中的 Key 可能分布在不同节点，客户端需要按节点分组
  - Pipeline 不保证原子性（不是事务）
```

### 29.2 命中率监控

```
命中率 = 命中次数 / (命中次数 + 未命中次数) × 100%

命中率分级：

  ≥ 95%：健康，缓存策略有效
  90% ~ 95%：一般，需要关注
  80% ~ 90%：较差，可能存在以下问题：
    - TTL 设置过短
    - Key 设计不合理（冲突率高）
    - 数据写入后立即被淘汰（内存不足）
  < 80%：严重，需要立即排查

命中率突降的常见原因：
  1. 大批量 Key 同时过期（雪崩前兆）
  2. 内存达到上限，大量 Key 被 LRU 淘汰
  3. 业务逻辑变更导致 Key 命名规则变化
  4. 主从切换后从节点数据不完整
  5. 缓存预热不充分（大促前未提前加载）
```

## 30. 典型故障案例分析

理论讲了很多，这一节我们通过真实的故障案例来加深理解。每个案例都包含"现象 → 排查过程 → 根因分析 → 解决方案 → 经验总结"的完整链条。

### 30.1 案例：主从切换导致数据丢失

**现象**：某业务集群主节点宕机触发自动切换后，约 0.1% 的 Key 丢失。

**排查过程**：

```
1. 确认数据丢失范围
   - 对比切换前后的 Key 数量：丢失约 1200 个 Key
   - 丢失的 Key 集中在特定 Slot 范围

2. 检查主从复制状态
   - 切换前主从复制延迟：约 50ms
   - min-replicas 配置：未配置
   
3. 分析时间线
   T0: 主节点收到写入命令，写入内存
   T1: 主节点异步复制到从节点（尚未到达）
   T2: 主节点宕机
   T3: 从节点被提升为新主节点
   → T1 到 T3 之间的写入丢失
```

**根因分析**：主从复制是异步的，主节点宕机时，尚未同步到从节点的写入会丢失。

**解决方案**：

```bash
# 配置最小从节点确认（半同步复制效果）
min-replicas-to-write 1        # 至少 1 个从节点确认才算写入成功
min-replicas-max-lag 10        # 从节点延迟超过 10 秒则拒绝写入

# 注意：这会降低写入性能，仅在数据丢失不可接受时开启
```

**经验总结**：Squirrel 默认只保证最终一致性，如果业务不能容忍任何数据丢失，应该使用 Cellar 或在写入后做幂等性校验。

### 30.2 案例：脑裂导致数据分叉

**现象**：双机房部署的集群，网络分区恢复后发现两个机房的主节点都接受过写入，数据产生分叉。

**排查过程**：

```
1. 检查集群历史状态
   - 网络分区前：机房 A 的 Master-1 负责写，机房 B 的 Slave-1 同步
   - 网络分区期间：两个机房的 Gossip 通信中断
   - 机房 B 的 Slave-1 认为Master-1 宕机，自行升级为 Master
   - 机房 A 的 Master-1 依然正常工作
   - 两个 Master 同时接受写入

2. 数据对比
   - 同一批 Key 在两个 Master 上有不同的值
   - 冲突 Key 数量：约 5000 个
```

**根因分析**：双机房部署 + 网络分区 = 经典脑裂场景。

**解决方案**：

```
1. 短期方案（数据修复）：
   - 以机房 A（原主）的数据为准
   - 把机房 A 的数据覆盖到机房 B
   - 通知受影响的业务方做数据修正

2. 长期方案（架构优化）：
   - 改为三机房部署，从根本上避免脑裂
   - 或引入 Witness 见证者节点
   - 配置 min-replicas-to-write 防止少数派写入
```

### 30.3 案例：数据倾斜导致单节点过载

**现象**：某集群 6 个分片，其中一个分片的 CPU 使用率持续 90%+，而其他分片只有 30%。

**排查过程**：

```
1. 检查各分片的数据量
   分片1: 0.5 GB  分片2: 0.6 GB  分片3: 5.2 GB  ← 异常
   分片4: 0.4 GB  分片5: 0.5 GB  分片6: 0.3 GB

2. 检查各分片的 QPS
   分片1: 8,000   分片2: 10,000  分片3: 45,000  ← 异常
   分片4: 7,000   分片5: 9,000   分片6: 6,000

3. 大 Key 扫描
   分片3 上存在大量大 Key（单个 Hash 1-5MB）
   这些大 Key 使用了 Hash Tag，全部落在同一个 Slot

4. 热点 Key 分析
   分片3 上有一个热点 Key（QPS = 30,000）
```

**根因分析**：Hash Tag 使用不当 + 大 Key + 热点 Key 三重因素叠加。

**解决方案**：

```
1. 拆分大 Key：
   - 把 5MB 的大 Hash 按字段前缀拆分为 10 个小 Hash
   - 使用不同的 Hash Tag，分散到不同 Slot

2. 热点 Key 处理：
   - 在业务层增加本地缓存（Caffeine，TTL=5s）
   - 本地缓存可抵挡 80% 的读请求

3. 临时扩容：
   - 给分片3 增加从节点，分担读压力
   - 迁移部分 Slot 到新节点
```

### 30.4 案例：迁移抖动导致 TP99 飙升

**现象**：集群扩容迁移 Slot 期间，TP99 从 3ms 飙升到 200ms。

**排查过程**：

```
1. 确认抖动时间点
   - 抖动与 Slot 迁移时间完全吻合
   - 每次迁移一个 Slot 批次后，TP99 出现一个尖峰

2. 分析慢查询日志
   - 迁移期间出现大量 ASK 重定向
   - 部分 Key 的 GET 耗时 > 100ms（正常 < 1ms）

3. 检查迁移配置
   - 迁移批次大小：500 Keys/batch（过大）
   - 迁移间隔：0ms（未做限流）
   - 大 Key 迁移阻塞主线程
```

**根因分析**：迁移批次过大 + 无限流 + 大 Key 阻塞。

**解决方案**：

```
1. 调整迁移参数：
   - 批次大小从 500 降到 50
   - 批次间隔从 0ms 改为 5ms
   - 开启异步迁移（forkless migrate）

2. 迁移前预处理大 Key：
   - 先拆分大 Key
   - 或在低峰期单独迁移大 Key

3. 迁移流量控制：
   - 开启 Squirrel 的自适应流量控制
   - 设置业务成功率阈值（99.9%）
   - 当成功率下降时自动降速
```

### 30.5 案例：连接风暴导致服务不可用

**现象**：某个应用的 Squirrel 连接数从 200 突增到 5000，随后 Squirrel 节点因 maxclients 限制拒绝新连接。

**排查过程**：

```
1. 分析连接来源
   - 5000 个连接全部来自同一个应用的同一台机器
   - 该应用刚发版上线

2. 代码审查
   - 新版本代码在每个请求处理方法中都调用了 client.build()
   - 每次创建一个新的客户端实例和连接池
   - 旧的客户端实例没有被关闭，连接泄漏

3. 确认问题
   - 每个请求创建 16 个连接（连接池大小）
   - QPS = 300/s → 每秒新增 300 × 16 = 4800 个连接
   - 几秒内连接数爆炸
```

**根因分析**：客户端实例未复用，导致连接泄漏。

**解决方案**：

```java
// 错误代码（每个请求都创建新客户端）
public String getValue(String key) {
    // 错误：每次调用都 build()，导致连接泄漏
    SquirrelStoreClient client = new SquirrelClientBuilder("cluster")
            .build();
    return client.get(new StoreKey("category", key));
}

// 正确代码（全局单例复用）
private static final SquirrelStoreClient CLIENT = 
    new SquirrelClientBuilder("cluster").build();

public String getValue(String key) {
    return CLIENT.get(new StoreKey("category", key));
}
```

**经验总结**：Squirrel 客户端必须全局复用，绝不能在每次请求中创建新实例。代码审查时必须检查客户端的初始化位置。

## 31. 缓存设计模式：从 Cache-Aside 到 Write-Behind

缓存设计模式是业务架构设计的基础知识，不同的模式适用于不同的场景。这一节我们全面对比四种经典缓存设计模式。

### 31.1 Cache-Aside（旁路缓存）

这是最常用的缓存模式，前面章节已经详细讨论过，这里做一个结构化的总结。

```
Cache-Aside 模式：

  读流程：
  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  应用代码  │───▶│  查缓存   │───▶│  返回结果 │
  │          │    └────┬─────┘    └──────────┘
  │          │         │ 未命中
  │          │    ┌────▼─────┐
  │          │───▶│  查数据库 │
  │          │    └────┬─────┘
  │          │    ┌────▼─────┐
  │          │───▶│  写缓存   │
  └──────────┘    └──────────┘

  写流程：
  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  应用代码  │───▶│ 更新数据库 │───▶│ 删除缓存  │
  └──────────┘    └──────────┘    └──────────┘
  
  特点：
  - 应用同时管理缓存和数据库
  - 缓存和数据库不是强一致的
  - 简单直观，最常用
  - 适合读多写少的场景
```

### 31.2 Read-Through（读穿透）

```
Read-Through 模式：

  读流程：
  ┌──────────┐    ┌──────────────┐    ┌──────────┐
  │  应用代码  │───▶│   缓存层      │───▶│  返回结果 │
  │          │    │  (Cache Provider)│ └──────────┘
  │          │    │              │
  │          │    │  命中？直接返回 │
  │          │    │  未命中？      │
  │          │    │    查数据库    │
  │          │    │    写缓存      │
  │          │    │    返回结果    │
  └──────────┘    └──────────────┘

  与 Cache-Aside 的区别：
  - 应用只与缓存层交互，不直接访问数据库
  - 缓存层负责"缓存未命中时加载"的逻辑
  - 应用代码更简洁
  - 需要缓存层支持自动加载功能
```

```java
// Read-Through 实现示例
public class ReadThroughCache {
    private SquirrelStoreClient cache;
    private DataSource dataSource;
    
    // 应用层只调用这个方法
    public User getUser(Long userId) {
        StoreKey key = new StoreKey("user", userId);
        
        // 缓存层封装了"查缓存 → 未命中查 DB → 回填缓存"的完整逻辑
        return cache.getOrLoad(key, User.class, () -> {
            return dataSource.queryUser(userId);
        }, 3600); // TTL = 3600 秒
    }
}
```

### 31.3 Write-Through（写穿透）

```
Write-Through 模式：

  写流程：
  ┌──────────┐    ┌──────────────┐    ┌──────────┐
  │  应用代码  │───▶│   缓存层      │    │          │
  │          │    │  (Cache Provider)│    │          │
  │          │    │              │    │          │
  │          │    │  1. 更新缓存   │───▶│ 更新数据库│
  │          │    │  2. 同步更新DB │    │          │
  │          │◀───│  3. 返回成功   │◀───│          │
  └──────────┘    └──────────────┘    └──────────┘

  特点：
  - 缓存和数据库同步更新
  - 数据一致性好（但仍非强一致）
  - 写延迟较高（需要同时写两个地方）
  - 适合写少读多的场景
```

### 31.4 Write-Behind（写回/异步写）

```
Write-Behind 模式：

  写流程：
  ┌──────────┐    ┌──────────────┐
  │  应用代码  │───▶│   缓存层      │
  │          │    │              │
  │          │    │  1. 更新缓存   │
  │          │◀───│  2. 立即返回   │
  └──────────┘    │              │
                  │  3. 异步更新DB │───▶ 数据库
                  └──────────────┘

  特点：
  - 写延迟极低（只写缓存）
  - 数据库异步更新，可能丢失数据
  - 适合写密集、可容忍数据丢失的场景
  - 实现复杂（需要处理异步写失败、重试等）
```

### 31.5 四种模式对比

| 模式 | 读性能 | 写性能 | 一致性 | 复杂度 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| Cache-Aside | 高 | 高 | 弱 | 低 | 通用场景，最常用 |
| Read-Through | 高 | - | 弱 | 中 | 读多写少，简化应用代码 |
| Write-Through | 高 | 中 | 中 | 中 | 需要较好一致性的场景 |
| Write-Behind | 高 | 最高 | 最弱 | 高 | 写密集，可容忍数据丢失 |

```
模式选型决策树：

  对写入延迟的要求？
    极低（< 1ms） → Write-Behind（异步写数据库）
    可接受同步延迟 → 继续判断

  对数据一致性的要求？
    极高（不能丢数据） → 不适合用缓存，直接操作数据库
    中等（可短暂不一致） → Write-Through 或 Cache-Aside + 双删
    低（最终一致即可） → Cache-Aside（最简单）

  Squirrel 中的推荐：
  - 默认使用 Cache-Aside（简单、有效）
  - 如需自动加载，使用 Read-Through（需客户端支持）
  - Write-Through 和 Write-Behind 在 Squirrel 中不常用
    （Squirrel 定位是缓存，不是数据库的替代品）
```

## 32. 面试常见问题与解答

以下是关于 Squirrel 和分布式缓存的 25 个深入面试问题及其参考解答，覆盖架构原理、实践经验和故障排查等多个维度。

### Q1：Squirrel 为什么选择基于 Redis Cluster 而不是 Codis 的 Proxy 架构？

**答**：核心原因是**延迟**。美团的核心业务（外卖、打车等实时交易场景）对延迟极度敏感。Proxy 架构虽然对客户端友好（几乎零改造成本），但每个请求都要多经过一跳网络转发，这会额外增加 0.5~2ms 的延迟。Squirrel 选择客户端直连的去中心化架构，省掉了 Proxy 转发这一跳，能够做到平均延迟 < 0.7ms、TP99 < 10ms。这个取舍跟美团的业务特性高度匹配。代价是客户端需要维护本地路由表逻辑，复杂度有所增加，但这部分由 Squirrel SDK 封装好了，业务方不需要感知。

### Q2：Redis Cluster 为什么是 16384 个 Slot 而不是 65536 个？

**答**：这是 Squirrel 作者 antirez 在邮件列表中亲自回答过的问题。主要有两个原因：

1. **Gossip 消息大小**：Redis Cluster 的心跳消息中会携带节点负责的 Slot 位图。16384 个 Slot 只需要 2KB（16384/8）的位图，而 65536 个 Slot 需要 8KB。在集群节点较多时，8KB 的心跳消息会对带宽造成明显压力。
2. **集群规模上限**：Squirrel 作者建议集群节点数不超过 1000 个。16384 个 Slot 对于 1000 个节点来说，每个节点平均负责约 16 个 Slot，已经足够使用。65536 个 Slot 对于这个规模的集群来说是过度设计。

### Q3：Squirrel 的主从复制是同步还是异步？为什么不做同步复制？

**答**：Squirrel 的主从复制是**异步**的。主节点写入成功后立即返回给客户端，然后再异步把写命令同步给从节点。不做同步复制的原因是**性能**：如果每次写入都等待所有副本确认，写入延迟会成倍增加，与 Squirrel "低延迟、高吞吐"的核心定位相悖。异步复制的代价是在主节点宕机的极端情况下可能丢失少量数据（尚未同步到从节点的写入），对于缓存场景来说这个代价是可接受的——因为缓存数据通常可以从数据库重建。

### Q4：MOVED 和 ASK 重定向有什么区别？客户端分别怎么处理？

**答**：
- **MOVED** 是永久重定向，表示 Slot 的归属已经永久变更。客户端收到后应更新本地路由表，后续直接请求新节点。
- **ASK** 是临时重定向，发生在 Slot 迁移过程中。客户端收到后**不更新**本地路由表，而是先向目标节点发送 `ASKING` 命令，再发送实际请求。后续请求仍然先走源节点。

两者的本质区别在于：MOVED 意味着"迁移已完成，Slot 归属已正式变更"，ASK 意味着"迁移进行中，部分 Key 已在新节点，但 Slot 归属未变"。

### Q5：缓存穿透、击穿、雪崩三者有什么区别？分别怎么解决？

**答**：
- **穿透**：查询数据库中不存在的数据，每次请求都穿透到数据库。解决：布隆过滤器 + 空值缓存。
- **击穿**：单个热点 Key 过期的瞬间，大量并发请求同时打到数据库。解决：互斥锁（只允许一个请求查 DB）+ 逻辑过期。
- **雪崩**：大量 Key 在同一时间集中失效。解决：过期时间加随机抖动 + 多级缓存 + 限流熔断。

三者的核心区别：穿透是"查不存在的数据"，击穿是"查一个过期的热点数据"，雪崩是"大量 Key 同时过期"。

### Q6：为什么写操作是"先更新数据库，再删缓存"而不是"先删缓存，再更新数据库"？

**答**：如果先删缓存再更新数据库，存在以下并发问题：线程 A 删除缓存后、还没来得及更新数据库时，线程 B 来读数据，发现缓存未命中，去查数据库拿到旧值并回填缓存，随后线程 A 把新值写入数据库——结果缓存里是旧值，数据库是新值，缓存会一直脏下去。而"先更新数据库再删缓存"虽然理论上也有极小概率的并发窗口，但风险要小得多。

### Q7：延迟双删的原理是什么？延迟时间怎么确定？

**答**：延迟双删是为了解决"先更新数据库再删缓存"后，并发读请求可能把旧值重新回填到缓存的竞态条件。流程是：先删缓存 → 更新数据库 → 休眠一段延迟时间 → 再删一次缓存。延迟时间通常设置为比读请求的平均处理时间稍长一点（如读请求平均耗时 200ms，延迟设为 300~500ms），确保在延迟期间内并发的读请求已经完成"读旧值 → 回填缓存"的过程，第二次删除能把这个脏数据清掉。

### Q8：Squirrel 的热点 Key 自动隔离是怎么工作的？

**答**：分四步：① 每个 Squirrel 节点在处理请求时实时统计 Key 的访问频次（使用 Space-Saving TopK 算法）；② 当某 Key 的 QPS 超过自适应阈值时，节点先做本地限流止损；③ 监控服务定期采集各节点的 TopK 列表，发现全局热点后通知迁移服务；④ 迁移服务把热点 Slot 迁移到一组专门的"热点专享节点"上，这些节点只承载热点 Slot，处理能力大幅提升。整个过程对业务方透明。

### Q9：大 Key 有哪些危害？怎么处理？

**答**：大 Key 的危害包括：① 阻塞主线程（Squirrel 单线程模型，操作大 Value 耗时长）；② 数据倾斜（存大 Key 的分片内存占用远超其他分片）；③ 网卡瓶颈（大 Value + 高 QPS = 网卡打满）。处理方法：① 业务层面拆分（大 Hash 拆成多个小 Hash，大 List 分页存储）；② 使用渐进式删除（HSCAN + HDEL，避免 DEL 阻塞）；③ Squirrel 客户端层面有 1MB 的硬性限制，直接拦截大 Value 写入。

### Q10：Squirrel 的智能迁移和原生 Redis 的迁移有什么区别？

**答**：三个核心区别：① Squirrel 实现了异步 MIGRATE，把迁移操作放到后台线程，不阻塞主线程；原生 Redis 的 MIGRATE 是阻塞的。② Squirrel 有自适应流量控制，根据业务请求成功率和延迟动态调节迁移速度；原生 Redis 没有流量控制。③ Squirrel 支持断点续传，迁移中断后可从中断点继续；原生 Redis 不支持。

### Q11：Squirrel 和 Cellar 的核心区别是什么？怎么选型？

**答**：Squirrel 是纯内存缓存（基于 Redis Cluster），延迟低（avg < 0.7ms）但成本高（100 元/GB/年），数据可靠性弱（异步复制，可选持久化）。Cellar 是内存+硬盘混合存储（基于 Tair），延迟稍高（1-2ms）但成本低（20 元/GB/年），数据可靠性强（Raft 强一致复制）。选型原则：数据量小、延迟敏感、可接受偶发数据丢失 → Squirrel；数据量大、不能丢数据、延迟要求不那么极致 → Cellar。

### Q12：Squirrel 的 Gossip 协议是怎么做故障检测的？

**答**：分两个阶段。第一阶段"主观下线（PFAIL）"：节点 A 向节点 B 发 PING，如果超过 `cluster-node-timeout`（默认 15 秒）没收到 PONG 回复，A 把 B 标记为 PFAIL，这个标记只在 A 本地有效。第二阶段"客观下线（FAIL）"：A 通过 Gossip 把"B=PFAIL"的信息传播给其他节点，当超过半数的主节点都报告 B=PFAIL 时，第一个发现这一点的节点把 B 标记为 FAIL，并向全网广播。B 的从节点收到 FAIL 消息后开始发起故障转移。

### Q13：什么是脑裂？Squirrel 怎么避免脑裂？

**答**：脑裂是指网络分区导致集群中同时存在两个或多个"自认为是主"的节点，各自接受写入，数据产生分叉。Squirrel 的防护方案：① 优先使用三机房部署，保证任何机房断网时，机房内 Master 数量不超过半数，无法达成共识就不会选新主；② 两机房部署引入 Witness 见证者节点打破平局；③ 配置 `min-replicas-to-write` 防止少数派写入；④ SET 化架构做机房内自包含。

### Q14：Squirrel 客户端的路由表是怎么维护的？发生故障时怎么更新？

**答**：客户端启动时从 ZooKeeper 读取集群拓扑构建路由表，并注册 Watcher 监听变更。日常维护有多级刷新策略：① ZooKeeper 通知（毫秒级）；② 收到 MOVED 时被动更新单个 Slot；③ 连续多个 MOVED 触发全量刷新；④ 定时刷新（默认 60 秒）；⑤ 节点连接异常时主动探测。路由表使用 Copy-on-Write 思想实现并发安全：读操作无锁（直接读 volatile 引用），写操作创建新对象后原子切换引用。

### Q15：Hessian 序列化有哪些常见坑？

**答**：① 缺少无参构造函数会导致反序列化时反射创建对象失败；② 类路径不一致（写应用和读应用的包名不同）会导致反序列化退化为 HashMap，后续类型转换抛 ClassCastException；③ Hessian3 和 Hessian4 不兼容，混用会出问题；④ serialversionUID 建议显式声明，避免类结构变更后反序列化失败；⑤ 如果不想依赖 Hessian，可以用 setBytes/getBytes 自行控制序列化。

### Q16：Squirrel 的读写分离中，怎么避免读到从节点的旧数据？

**答**：几种策略：① 写后强制读主——写入后在短时间窗口内（如 500ms）的读请求强制路由到主节点；② 会话粘连——同一会话的读写都走主节点；③ 版本号校验——数据带版本号，从节点读到旧版本时触发从主节点重读；④ 复制延迟监控——主从延迟过大时自动切换到读主。实际使用中，"写后强制读主"最常用也最有效。

### Q17：Squirrel 为什么是单线程？Squirrel 有没有改成多线程？

**答**：Squirrel 单线程的原因是：① 内存操作本身就极快，瓶颈在网络 IO 而非 CPU；② 单线程避免了锁竞争和上下文切换的开销；③ 数据结构操作（如 Hash、ZSet）不需要加锁。Squirrel 6.0 引入了多线程 IO（只用于网络读写，命令执行仍是单线程）。Squirrel 在此基础上没有把命令执行改成多线程（这会破坏 Squirrel 的原子性保证），但在持久化、迁移、大 Key 删除等操作上使用了后台线程。

### Q18：什么是缓存预热？怎么做？

**答**：缓存预热是在系统上线或大促前，提前把热点数据加载到缓存中，避免上线后大量请求直接打到数据库。实现方式：① 编写预热脚本，批量查询数据库并写入 Squirrel；② 在应用启动时通过 `@PostConstruct` 或 `CommandLineRunner` 加载热点数据；③ 大促前通过离线任务把热点数据预先灌入缓存。注意预热的并发度要控制，避免预热本身把数据库或缓存压垮。

### Q19：Pipeline 和事务（MULTI/EXEC）有什么区别？

**答**：Pipeline 是"打包发送多个命令，减少网络往返"，不保证原子性——中间某个命令失败不影响后续命令执行。事务（MULTI/EXEC）是"把多个命令打包成一个原子操作，要么全部执行要么全部不执行"，但 Squirrel 的事务不支持回滚（EXEC 后命令执行出错不会撤销已执行的命令）。在 Squirrel 中，事务还要求所有 Key 在同一个 Slot 上（否则报 CROSSSLOT 错误），而 Pipeline 没有这个限制。

### Q20：Squirrel 的配额管理是怎么做的？超出配额会怎样？

**答**：配额管理在集群和 Category 两个层面实施。集群层面：申请集群时填写容量预估和 QPS 预估，平台据此分配机器资源。Category 层面：每个 Category 有内存上限（如线下环境默认 1GB），超过上限会拒绝写入。配额数据配合计费系统，按 Category/AppKey 精确分摊成本。超出配额时：① 内存超限——新的写入请求被拒绝（返回 OOM 错误）；② QPS 超限——触发服务端限流，部分请求被拒绝。

### Q21：Squirrel 的过期 Key 删除策略是什么？

**答**：Squirrel 使用两种策略结合：① **惰性删除**——访问 Key 时检查是否过期，过期则删除。优点是 CPU 友好（只在访问时检查），缺点是过期但无人访问的 Key 会一直占用内存。② **定期删除**——Squirrel 每 100ms 随机抽取一部分设置了 TTL 的 Key 检查过期，删除已过期的。如果过期 Key 比例超过 25%，继续抽查。两种策略结合，既不过度消耗 CPU，又能及时回收内存。如果两种策略都没来得及清理，还有 `maxmemory-policy` 淘汰策略兜底。

### Q22：Squirrel 的 redis-keeper-service 跨机房复制原理是什么？

**答**：redis-keeper-service 伪装成 Redis 的 Slave，通过标准的 Redis 复制协议（PSYNC）从主集群的从节点上拉取 RDB 全量数据和后续增量命令流。然后把这些数据转换为写命令，通过专线发送到目标集群侧的 keeper-service，由后者写入目标集群的主节点。如果要实现异地多活（双向同步），再建一条反方向的同步链路即可。复制过程中有命令合并、压缩传输、批量发送等带宽优化手段。

### Q23：什么是渐进式删除？为什么要用它？

**答**：渐进式删除是指分批次删除大 Key 中的元素，而不是一次性 `DEL` 整个 Key。比如删除一个有 10000 个 field 的大 Hash，每次用 HSCAN 取 100 个 field 然后 HDEL，间隔 2ms，分 100 批完成。原因：Squirrel 单线程模型下，直接 `DEL` 一个大 Key 会阻塞主线程数百毫秒甚至数秒，期间所有其他请求都要排队等待，造成严重的延迟抖动。渐进式删除把一次大阻塞分散成很多次微小阻塞，对正常请求几乎无感知。

### Q24：内存碎片率多少算正常？怎么处理？

**答**：碎片率（used_memory_rss / used_memory）在 1.0~1.5 之间算正常。1.5~2.0 需要关注，>2.0 需要处理。处理方式：① Squirrel 4.0+ 开启 `activedefrag yes`，自动整理碎片；② 手动执行 `MEMORY PURGE`；③ 如果以上无效，在低峰期重启 Squirrel 实例（彻底清理碎片）。预防措施：避免频繁创建和删除大量 Key，合理设置 TTL，避免大 Key。

### Q25：如果你来设计一个分布式缓存系统，会怎么考虑高可用？

**答**：我会从以下几个层面来设计：

1. **存储层高可用**：一主多从 + 自动故障转移。主节点宕机时从节点自动提升为主。使用三机房部署避免脑裂。
2. **检测层高可用**：独立的 HA 监控服务，不依赖存储层自身的 Gossip（太慢），通过 ZooKeeper 实现秒级拓扑变更通知。
3. **客户端高可用**：本地路由表 + 多级刷新策略 + 自动重试 + 降级到其他节点/主节点。全局复用连接池，避免连接泄漏。
4. **流量层高可用**：服务端限流（保护节点不被打垮）+ 客户端熔断（快速失败避免级联故障）+ 多级缓存兜底。
5. **数据层高可用**：异步复制（性能优先）+ 可选的半同步（一致性优先）+ 定期数据校验。
6. **运维层高可用**：自动化扩缩容 + 智能迁移（动态调速）+ 大 Key/热点 Key 自动治理。

```java
// 业务服务类
@Service
public class MenuCacheService {
    
    @Resource(name = "redisClient")
    private SquirrelStoreClient cache;
    
    private static final String CATEGORY = "menu";
    private static final int TTL = 3600; // 1 小时
    private static final Random random = new Random();
    
    /**
     * 获取门店菜单
     */
    public Menu getMenu(long poiId) {
        StoreKey key = new StoreKey(CATEGORY, poiId);
        try {
            Menu menu = cache.get(key, Menu.class);
            if (menu != null) {
                return menu; // 缓存命中
            }
        } catch (Exception e) {
            log.warn("Cache read failed, fallback to DB", e);
        }
        
        // 缓存未命中或异常，查数据库
        Menu menu = menuDao.queryByPoiId(poiId);
        if (menu != null) {
            try {
                // 写入缓存，TTL 加随机抖动（避免雪崩）
                int ttl = TTL + random.nextInt(600); // 3600~4200 秒
                cache.set(key, menu, ttl);
            } catch (Exception e) {
                log.warn("Cache write failed", e);
            }
        }
        return menu;
    }
    
    /**
     * 更新门店菜单
     */
    @Transactional
    public void updateMenu(long poiId, Menu menu) {
        // 1. 更新数据库
        menuDao.update(poiId, menu);
        
        // 2. 删除缓存
        StoreKey key = new StoreKey(CATEGORY, poiId);
        try {
            cache.del(key);
        } catch (Exception e) {
            log.warn("Cache delete failed, will retry", e);
            // 发送到消息队列异步重试
            retryQueue.send(new CacheDeleteTask(key));
        }
    }
    
    /**
     * 批量获取门店菜单
     */
    public Map<Long, Menu> batchGetMenus(List<Long> poiIds) {
        if (poiIds.size() > 1024) {
            throw new IllegalArgumentException("Too many keys: " + poiIds.size());
        }
        
        List<StoreKey> keys = poiIds.stream()
            .map(id -> new StoreKey(CATEGORY, id))
            .collect(Collectors.toList());
        
        Map<Long, Menu> result = new HashMap<>();
        
        try {
            List<Object> values = cache.multiGet(keys);
            for (int i = 0; i < poiIds.size(); i++) {
                Menu menu = (Menu) values.get(i);
                if (menu != null) {
                    result.put(poiIds.get(i), menu);
                }
            }
        } catch (Exception e) {
            log.warn("Batch cache read failed", e);
        }
        
        // 未命中的查数据库
        List<Long> missedIds = poiIds.stream()
            .filter(id -> !result.containsKey(id))
            .collect(Collectors.toList());
        
        if (!missedIds.isEmpty()) {
            List<Menu> dbMenus = menuDao.batchQuery(missedIds);
            for (Menu menu : dbMenus) {
                result.put(menu.getPoiId(), menu);
                // 回填缓存
                try {
                    StoreKey key = new StoreKey(CATEGORY, menu.getPoiId());
                    int ttl = TTL + random.nextInt(600);
                    cache.set(key, menu, ttl);
                } catch (Exception e) {
                    log.warn("Cache backfill failed", e);
                }
            }
        }
        
        return result;
    }
}
```

### 附录 F：Squirrel 常见错误码与处理建议

| 错误码 | 错误信息 | 原因 | 处理建议 |
| --- | --- | --- | --- |
| `STORE_KEYS_OVERFLOW` | 批量操作超限 | pipeline > 512 或 multiGet > 1024 | 拆分批次 |
| `STORE_BIG_VALUE` | Value 超过 1MB | 写入的数据过大 | 拆分大 Value 或使用 Cellar |
| `STORE_CONNECT_ERROR` | 连接异常 | 节点宕机、网络问题 | 重试 + 降级到其他节点 |
| `STORE_TIMEOUT` | 请求超时 | 节点负载高、大 Key 阻塞 | 检查慢查询、大 Key |
| `STORE_SERIALIZE_ERROR` | 序列化失败 | 类路径不一致、Hessian 版本差异 | 检查类定义、统一序列化版本 |
| `STORE_ROUTE_ERROR` | 路由错误 | 路由表过期、Slot 迁移中 | 客户端自动刷新路由表 |
| `STORE_QUOTA_EXCEEDED` | 配额超限 | Category 内存超限 | 清理无用 Key 或申请扩容 |
| `STORE_AUTH_ERROR` | 鉴权失败 | AppKey 未注册 | 在管理平台注册 AppKey |
| `MOVED` | Slot 重定向 | Slot 已永久迁移 | 客户端自动处理 |
| `ASK` | 临时重定向 | Slot 迁移中 | 客户端自动处理（发 ASKING） |
| `TRYAGAIN` | 临时不可用 | Key 正在迁移中 | 短暂等待后重试 |
| `CROSSSLOT` | 跨 Slot 操作 | 事务中的 Key 不在同一 Slot | 使用 Hash Tag 强制同 Slot |
| `NOSCRIPT` | 脚本不存在 | Lua 脚本未缓存 | 先 SCRIPT LOAD 加载脚本 |
| `LOADING` | 数据加载中 | Squirrel 正在加载 RDB/AOF | 等待加载完成 |
