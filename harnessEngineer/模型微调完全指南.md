## 第一章 大模型训练全景：微调在哪里

### 1.1 大模型训练的三阶段流水线

现代大语言模型（LLM）的训练通常经历三个主要阶段，每个阶段解决不同的问题。理解这三个阶段是理解微调的前提。

```
┌─────────────────────────────────────────────────────────────────┐
│                    大模型训练流水线                               │
│                                                                   │
│  阶段一：Pre-training（预训练）                                   │
│  ┌─────────────────────────────────────────┐                     │
│  │  海量语料（万亿 token）+ 自回归语言建模  │                     │
│  │  目标：学习语言、知识、推理能力          │                     │
│  └─────────────────────────────────────────┘                     │
│                         ↓                                        │
│  阶段二：Post-training / SFT（后训练 / 监督微调）                 │
│  ┌─────────────────────────────────────────┐                     │
│  │  指令数据（万~百万条）+ 监督学习         │                     │
│  │  目标：学会听懂指令、遵循格式            │                     │
│  └─────────────────────────────────────────┘                     │
│                         ↓                                        │
│  阶段三：Alignment（对齐微调）                                    │
│  ┌─────────────────────────────────────────┐                     │
│  │  偏好数据 + 强化学习（RLHF/DPO/GRPO）    │                     │
│  │  目标：对齐人类偏好、价值观、安全性       │                     │
│  └─────────────────────────────────────────┘                     │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 预训练：大模型的"大学教育"

预训练阶段是大模型学习基础知识的过程。在这个阶段，模型通过阅读海量的互联网文本（通常是万亿级别的token），学习语言的基本规律和世界知识。

预训练的核心特点：

第一，它是无监督学习。模型不需要人工标注的标签，而是通过"预测下一个词"这个简单但强大的任务来学习。给定一段文本的前N个词，模型需要预测第N+1个词是什么。通过不断迭代这个过程，模型逐渐学会了词汇的含义、句子的结构、知识之间的关联，甚至初步的推理能力。

第二，数据量极其庞大。以GPT-4为例，据估计其预训练数据量达到了数万亿token。这些数据来自网页爬取、书籍、论文、代码等各种来源。数据的多样性和质量直接决定了模型的基础能力。

第三，计算成本极高。预训练一个千亿参数的模型，通常需要数千张GPU连续运行数月，成本可能高达数百万甚至数千万美元。这也是为什么绝大多数企业和团队不会从头预训练模型，而是选择在已有预训练模型的基础上进行微调。

用一个通俗的类比来理解：预训练就像是学生时代的通识教育。在大学里，你广泛学习了数学、物理、编程、英语等各种基础课程，建立了知识体系的框架。虽然这些知识还不能直接用来解决某个具体的工作问题，但它们为你未来的职业发展奠定了坚实的理论基础。同样，预训练让模型掌握了语言的基本规律和世界知识，但这些知识还不足以直接解决特定的业务问题。

### 1.3 监督微调（SFT）：大模型的"岗前培训"

预训练完成后，得到的是所谓的"基座模型"（Base Model）。基座模型本质上是一个"续写机器"——给它一段文本，它会继续往下写。但它还不会"听指令"。

举个例子，如果你给基座模型输入"中国的首都是哪里？"，它可能会续写出"日本的首都是哪里？韩国的首都是哪里？"——因为它把这个问题当成了文本的一部分在续写，而不是在回答问题。

监督微调（Supervised Fine-Tuning，SFT）就是为了解决这个问题。在SFT阶段，我们给模型提供大量的"指令-回答"对，让模型学会理解人类的指令，并给出符合预期的回答。

SFT的数据格式通常是这样的：

```json
{
  "instruction": "请将以下句子翻译成英文",
  "input": "今天天气真好",
  "output": "The weather is really nice today."
}
```

通过在成千上万这样的数据上训练，模型逐渐学会了"听懂指令"和"给出回答"的能力。

继续用前面的类比：SFT就像是校招生进入公司后的岗前培训。在学校里学的是理论知识，进入公司后需要学习公司内部的技术栈（比如企业内部的各类中间件、数据库、缓存等组件）、代码规范、开发流程。这个过程就是在"微调"你的知识网络，使其更加适配公司的特定需求。

### 1.4 对齐微调：大模型的"职业道德培训"

即使经过SFT，模型的回答可能还不够"好"。比如，它可能会生成有害的内容、带有偏见的言论，或者虽然回答了但不够礼貌、不够有用。

对齐微调（Alignment Fine-tuning）的目标就是让模型的输出更好地符合人类的偏好和价值观。这通常通过人类反馈的强化学习（RLHF）或直接偏好优化（DPO）等方法来实现。

用类比来说：对齐微调就像是你在工作中接受了职业道德培训和行为规范指导。你不仅学会了怎么做事情（SFT），还学会了怎么做事情才是"好的"——要负责任、要符合公司价值观、要让用户满意。

### 1.5 微调在大模型生命周期中的位置

总结一下，微调在大模型生命周期中的位置如下：

```
预训练（Pre-training）
  → 产出：基座模型（Base Model），如 LLaMA-3-8B、Qwen2-7B
  → 能力：具备语言理解和知识，但不会遵循指令
  → 成本：极高（百万美元级）

监督微调（SFT）
  → 产出：指令模型（Instruct Model），如 LLaMA-3-8B-Instruct
  → 能力：能听懂指令、给出回答
  → 成本：中等（数千到数万美元）

对齐微调（Alignment）
  → 产出：对齐模型（Aligned Model），如 ChatGPT
  → 能力：回答符合人类偏好，安全、有用
  → 成本：较高（需要偏好标注数据 + RL训练）

领域微调（Domain Fine-tuning）← 这就是本指南的重点
  → 产出：领域专用模型，如医疗问答模型、法律助手模型
  → 能力：在特定领域表现优异
  → 成本：可控（从几百到数万美元不等）
```

对于大多数企业和开发者来说，我们不需要从头预训练模型，而是选择一个已经经过预训练（甚至已经经过SFT和对齐）的开源模型，然后在自己的领域数据上进行微调，使其适应特定的业务需求。这就是本指南要详细讲解的内容。

## 第二章 微调基础概念：从小白到入门

### 2.1 什么是微调

微调（Fine-tuning）是指在已经训练好的预训练模型基础上，利用特定的数据进一步训练该模型，对模型权重进行微小调整，以使其更好地适应特定任务或特定领域。

想象一下，你有一只机器人狗，它已经在基本的狗行为上进行了初步训练，比如行走和听从简单的命令。微调就像是对这只机器狗进行进一步的训练以适应特定的任务环境。比如说，你希望这只机器狗能够在公园里捡回特定种类的球。通过微调，你可以在原有的训练基础上，用一组特定的数据集（比如各种颜色和大小的球）来对它进行垂直领域的针对性训练，从而调整其行为，使其在新环境中表现得更好。

从技术角度来说，大模型本质上是一个由多层神经元和大量矩阵组成的神经网络。每个矩阵包含模型的权重（weight）或参数（parameter），直观来说就是储存着模型对不同词的理解。当我们将prompt输入到这个神经网络时，模型通过权重预测下一个token的概率。微调的核心在于通过特定的训练数据更新模型内部参数的权重，以改变输出的概率分布。

### 2.2 为什么要微调

理解了微调是什么之后，一个自然的问题就是：为什么不直接用预训练好的模型，还要费力气去微调？主要有三个原因：

第一，训练成本的问题。大模型的参数量非常大，训练成本极高。以GPT-4级别的模型为例，据估计单次预训练成本超过1亿美元。如果每一个应用都从头训练一个自己的大模型，这个过程的性价比非常低。而微调可以跳过复杂且昂贵的预训练流程，直接基于预训练模型进行训练，成本可以降低好几个数量级。

第二，领域专精的需求。基座模型虽然说已经可以完成很多任务，比如回答问题、总结摘要、编写代码等。但是，并没有一个模型可以解决所有的问题，尤其是行业内的专业问答、公司的私有数据问答等，是通用基座模型无法解决的。比如，一个通用的GPT模型可能不知道你公司内部的报销流程、不知道你们产品的技术细节、不了解你们行业的专业术语。在这种情况下，就需要通过使用自有数据，选择合适的基础模型进行微调，以更好地提升大模型在特定领域的能力。

第三，数据安全的问题。如果数据是不能传递给第三方大模型供应商的（比如医疗数据、金融数据、企业内部数据），那么搭建自己的大模型就非常必要。通常开源的大模型都是基座模型，需要用自有数据进行微调，才能够满足业务的需求。微调让企业可以在本地部署模型，数据不出企业，保证了数据安全。

### 2.3 微调的本质：概率分布的调整

为了更深入地理解微调，我们需要理解它的数学本质。

大模型的生成过程本质上是一个概率预测过程：给定前面的token序列，预测下一个token的概率分布。模型内部的权重决定了这个概率分布。

当模型没有经过微调时，对于"某外卖平台的配送范围是"这个输入，模型可能会给出各种可能的续写：

```
某外卖平台的配送范围是 → "3-5公里"（概率 0.15）
某外卖平台的配送范围是 → "根据不同城市而定"（概率 0.12）
某外卖平台的配送范围是 → "由商家自行设置"（概率 0.08）
某外卖平台的配送范围是 → "全国范围内"（概率 0.05）
...其他各种回答（概率 0.60）
```

可以看到，概率分布比较分散，没有一个明显占优的答案。

经过微调后，模型对于同样的输入，概率分布会发生变化：

```
某外卖平台的配送范围是 → "由商家根据实际情况设置，一般在3-5公里范围内..."（概率 0.75）
某外卖平台的配送范围是 → "不同商家的配送范围不同，具体以..."（概率 0.18）
...其他回答（概率 0.07）
```

微调后的模型给出更准确、更符合预期的回答的概率大大增加了。这就是微调的本质——通过训练数据调整模型内部的权重，从而改变输出的概率分布，使其在特定领域或任务上表现更好。

### 2.4 微调的两个核心维度

理解微调，需要从两个维度来看：

维度一：训练数据的来源和训练目标。从这个角度，微调可以分为有监督微调（SFT）和基于人类反馈的强化学习（RLHF）。SFT使用有标签的数据进行训练，模型学习的是"给定输入，应该输出什么"。RLHF则使用人类的偏好反馈来训练模型，模型学习的是"什么样的输出是更好的"。

维度二：参数更新的规模。从这个角度，微调可以分为全量微调（Full Fine-Tuning，FFT）和参数高效微调（Parameter-Efficient Fine-Tuning，PEFT）。FFT会更新模型的所有参数，效果最好但成本最高。PEFT只更新模型的一小部分参数，成本大幅降低但效果略有牺牲。

这两个维度的组合构成了微调的主要技术路线：

```
                    全量微调(FFT)     参数高效微调(PEFT)
有监督微调(SFT)     SFT + FFT        SFT + LoRA/QLoRA
偏好对齐(RLHF)      RLHF + FFT       RLHF + LoRA（较少使用）
```

在实际业务中，最常用的组合是"SFT + LoRA"，因为它在效果和成本之间取得了最好的平衡。

### 2.5 微调与预训练的联系与区别

虽然微调和预训练都是"训练模型"，但它们在很多方面有显著区别：

预训练是从头开始训练模型，使用的是海量无标注数据（万亿级别），训练目标是预测下一个词，需要大量计算资源（数千GPU，数月时间），产出的模型具备通用的语言能力。

微调是在预训练模型的基础上继续训练，使用的是少量有标注数据（通常数千到数十万条），训练目标是适应特定任务，需要的计算资源少得多（单卡或数卡，数小时到数天），产出的模型在特定领域或任务上表现更好。

一个关键的区别是学习率（learning rate）。预训练通常使用较大的学习率（如1e-4到5e-4），而微调使用较小的学习率（如1e-5到5e-5），因为微调只是在已有知识的基础上做"微调"，不能用太大的步幅否则会破坏已经学到的知识。

### 2.6 从一个简单例子理解微调全流程

假设我们要微调一个模型，让它能够回答某外卖平台相关的问题。整个流程大致如下：

第一步，准备数据。我们收集一批"问题-答案"对，比如：
- 问："某外卖平台的配送费怎么计算？" 答："某外卖平台的配送费根据配送距离、时间段和商家设置等因素计算..."
- 问："外卖订单超时了怎么办？" 答："如果您的订单超时，可以通过..."
- ...（收集几千到几万条这样的数据）

第二步，数据格式化。将这些数据转换成模型能理解的格式。通常使用类似如下格式：

```
<|user|>某外卖平台的配送费怎么计算？<|end|>
<|assistant|>某外卖平台的配送费根据配送距离、时间段和商家设置等因素计算...<|end|>
```

第三步，选择基座模型。选择一个合适的预训练模型作为基础，比如Qwen2-7B-Instruct。

第四步，配置训练参数。设置学习率、batch size、训练轮数等超参数。

第五步，开始训练。使用训练框架（如LLaMA-Factory、DeepSpeed等）在GPU上训练模型。

第六步，评测。训练完成后，用一批测试数据评估模型的效果，看是否达到了预期。

第七步，部署。将训练好的模型部署到推理服务中，供业务系统调用。

这就是微调的完整流程。后面各章会详细讲解每个环节的技术细节。

## 第三章 微调的技术路线分类

### 3.1 按训练数据来源分类

从训练数据的来源和训练目标的角度出发，大模型的微调有以下几条技术路线：

**有监督微调（Supervised Fine-Tuning，SFT）**

监督微调是指在进行微调时使用有标签的训练数据集。这些标签提供了模型在微调过程中的目标输出。在监督微调中，通常使用带有标签的任务特定数据集，例如分类任务的数据集，其中每个样本都有一个与之关联的标签。通过使用这些标签来指导模型的微调，可以使模型学习到特定任务的模式和规律。

在SFT中，训练数据通常是"指令-输出"对的形式。模型学习的是在给定指令的情况下，应该生成什么样的输出。SFT是最基础也是最常用的微调方式，绝大多数的领域微调都是从SFT开始的。

**基于人类反馈的强化学习（Reinforcement Learning from Human Feedback，RLHF）**

RLHF是一种更高级的微调方法，它通过收集人类对模型输出的偏好数据来训练模型。具体来说，对于同一个问题，模型会生成多个不同的回答，人类标注员对这些回答进行排序或评分，然后利用这些偏好数据来训练一个奖励模型（Reward Model），最后通过强化学习算法（如PPO）来优化模型，使其生成更符合人类偏好的回答。

RLHF相比SFT的优势在于：SFT只能学习"正确答案"，而RLHF可以学习"什么是更好的答案"。这对于那些没有唯一正确答案的任务（如创意写作、对话风格等）尤其重要。

**直接偏好优化（Direct Preference Optimization，DPO）**

DPO是RLHF的简化版本。RLHF需要先训练一个奖励模型，再用强化学习优化策略模型，流程复杂且训练不稳定。DPO通过巧妙的数学推导，跳过了奖励模型的训练步骤，直接从偏好数据中优化模型。这大大简化了训练流程，同时效果与RLHF相当。

### 3.2 按参数更新规模分类

从参数规模的角度，大模型的微调分成两条技术路线：

**全量微调（Full Fine-Tuning，FFT）**

全量微调会调整模型的所有参数。这意味着在训练过程中，模型中的每一个权重都会被更新。全量微调的优点是效果通常最好，因为模型有最大的自由度来适应新任务。缺点是计算资源需求大（需要大量显存来存储梯度、优化器状态等），训练时间长，且容易出现灾难性遗忘（模型学新任务时忘掉旧知识）。

全量微调适用于以下场景：计算资源充足、追求最优效果、任务与预训练领域差异较大、有足够的高质量训练数据。

**参数高效微调（Parameter-Efficient Fine-Tuning，PEFT）**

参数高效微调只调整模型的一小部分参数（通常是0.1%到10%），而将其余参数冻结。PEFT技术可以在提高模型效果的同时，大幅减少训练所需的计算资源和存储空间。

PEFT的核心思想是：虽然大模型有数十亿甚至上千亿参数，但在微调时，真正需要调整的只是其中很小一部分。研究表明，微调时的"有效参数变化"实际上集中在一个低维空间里，因此只需要更新少量参数就能达到很好的效果。

PEFT的主要优势包括：训练速度快（需要更新的参数少）、显存占用低（不需要为所有参数存储梯度和优化器状态）、存储成本低（微调后的模型文件可以很小，比如LoRA文件通常只有几十MB）、可以避免灾难性遗忘（原始参数不变，模型不会"忘记"已学到的知识）、支持多任务切换（同一个基座模型可以挂载不同的PEFT模块来服务不同任务）。

### 3.3 两种维度的交叉

将两个维度的技术路线交叉组合，就得到了实际的微调方案：

```
                    全量微调(FFT)           参数高效微调(PEFT)
                    ─────────              ──────────────────
有监督微调(SFT)     SFT + FFT              SFT + LoRA / QLoRA
                    最传统的方式             当前最主流的方式
                    效果最好，成本最高       效果接近FFT，成本低很多

偏好对齐(RLHF/DPO)  RLHF + FFT             DPO + LoRA
                    ChatGPT使用的方式        成本敏感场景的选择
                    训练复杂，需要大量资源    效果有损失但可接受
```

在实际业务中，最常见的组合是：
1. SFT + LoRA：最主流，适用于大多数场景
2. SFT + FFT：追求最优效果且资源充足时使用
3. SFT + LoRA → DPO + LoRA：先SFT再做偏好对齐，效果最好但流程复杂
4. SFT + QLoRA：资源极度受限时使用（如单卡消费级GPU）

### 3.4 选择微调方案的关键考量因素

选择哪种微调方案，需要考虑以下因素：

因素一：计算资源。你有多少GPU？每张GPU有多少显存？这是最硬性的约束。如果只有一张消费级显卡（如RTX 4090的24GB显存），那基本只能选择QLoRA。如果有A100 80GB级别的显卡，可以选择LoRA甚至全量微调。

因素二：数据量。你有多少训练数据？数据质量如何？如果数据量较少（几百到几千条），LoRA通常是更好的选择，因为全量微调容易过拟合。如果数据量很大（数万条以上），全量微调可能效果更好。

因素三：效果要求。你的业务对效果的要求有多高？如果是核心业务、对效果要求极高，可能需要全量微调。如果是辅助工具、对效果要求适中，LoRA就够了。

因素四：任务类型。你的任务是知识密集型还是能力密集型？如果是注入领域知识（如医疗、法律知识），可能需要全量微调或持续预训练。如果是教模型新的输出格式或行为模式，LoRA就够了。

因素五：部署约束。你能部署多大的模型？如果推理资源有限，可能需要量化后的模型加LoRA适配器。如果推理资源充足，可以用全量微调的模型。

因素六：迭代频率。你需要多频繁地更新模型？如果需要频繁迭代，LoRA更合适，因为每次训练成本低、模型文件小、切换方便。

## 第四章 有监督微调（SFT）详解

### 4.1 SFT的本质：模仿学习

有监督微调（SFT）的本质是一种模仿学习——让模型学习模仿训练数据中的"标准答案"。通过大量的"指令-回答"对，模型学会在特定领域或任务中，给定一个输入时应该输出什么样的回答。

从数学角度来说，SFT使用的损失函数是标准的语言模型损失（交叉熵损失）：

```
Loss = -Σ log P(output_i | input, output_{<i})
```

其中，output_i是标准答案的第i个token，P(output_i | input, output_{<i})是模型在给定输入和前面所有输出token的条件下，预测第i个token的概率。训练的目标就是最小化这个损失，让模型生成标准答案的概率越来越大。

### 4.2 SFT的数据格式

SFT的数据格式直接影响训练效果。常见的格式有以下几种：

**单轮对话格式**

最基础的数据格式是单轮的"指令-回答"对：

```json
{
  "instruction": "请解释什么是机器学习",
  "input": "",
  "output": "机器学习是人工智能的一个分支，它使计算机系统能够通过数据自动学习和改进..."
}
```

其中，instruction是用户给出的指令，input是补充输入（可以为空），output是期望的模型输出。

**多轮对话格式**

对于对话场景，数据需要包含多轮交互：

```json
{
  "conversations": [
    {"role": "user", "content": "你好，我想咨询一下退款流程"},
    {"role": "assistant", "content": "您好！很高兴为您服务。请问您是要退什么订单呢？"},
    {"role": "user", "content": "是一个外卖订单"},
    {"role": "assistant", "content": "好的，外卖订单退款流程如下..."}
  ]
}
```

**ChatML格式**

不同模型有不同的对话模板。以Qwen系列模型为例，使用的是ChatML格式：

```
<|im_start|>system
你是一个客服助手，请友好地回答用户问题。<|im_end|>
<|im_start|>user
退款多久到账？<|im_end|>
<|im_start|>assistant
退款一般在1-3个工作日内原路退回您的支付账户...<|im_end|>
```

**思维链（Chain-of-Thought）格式**

对于需要推理的任务，可以在输出中包含思维链：

```json
{
  "instruction": "一个商品原价200元，打8折后再减30元，最终价格是多少？",
  "output": "让我一步步计算：\n1. 原价200元\n2. 打8折：200 × 0.8 = 160元\n3. 再减30元：160 - 30 = 130元\n\n最终价格是130元。"
}
```

思维链格式在推理类任务中特别有效，它让模型学会"展示推理过程"，而不只是给出答案。这在数学计算、逻辑推理、代码生成等任务中能显著提升准确率。

### 4.3 SFT训练数据的作用机制

理解SFT训练数据如何影响模型参数，需要理解典型训练样本的处理流程及其对模型的作用机制。

当一条训练数据输入到模型中时，大致经历以下步骤：

第一步，Token化。模型的分词器（tokenizer）将文本转换为token ID序列。例如，"退款流程"可能被分割为[退, 款, 流, 程]四个token，每个token对应一个数字ID。

第二步，Embedding。每个token ID被映射为一个高维向量（比如768维或4096维），这些向量构成了模型的输入表示。

第三步，前向传播。输入向量通过模型的多个Transformer层，每层包含自注意力机制和前馈神经网络，最终输出每个位置上各个token的概率分布。

第四步，计算损失。将模型预测的概率分布与标准答案进行比较，计算交叉熵损失。

第五步，反向传播。根据损失值计算每个参数的梯度，指示应该如何调整参数来降低损失。

第六步，参数更新。优化器（如AdamW）根据梯度更新模型参数。

通过在大量训练数据上反复执行这个过程，模型逐渐学会了在特定领域中的知识表示和生成模式。

### 4.4 SFT的关键训练技巧

**损失掩码（Loss Masking）**

在SFT训练中，一个重要的技巧是只对"回答部分"计算损失，而不对"问题部分"计算损失。也就是说，模型只学习如何生成好的回答，而不需要学习如何生成问题。

具体来说，对于输入"用户：退款多久到账？助手：退款一般在1-3个工作日内..."，损失只计算"退款一般在1-3个工作日内..."这部分token的损失，"退款多久到账？"这部分的损失被设为0。

这样做的原因是：我们的目标是让模型学会回答问题，而不是学会生成问题。如果对问题部分也计算损失，模型会浪费一部分学习能力在模仿问题的表述上。

**梯度累积（Gradient Accumulation）**

当GPU显存有限，无法使用大的batch size时，可以通过梯度累积来模拟大batch size的效果。具体做法是：每次前向传播和反向传播计算梯度后，不立即更新参数，而是累积几次梯度后再更新。这样等效于使用了更大的batch size。

例如，如果显存只支持batch_size=2，但你想用batch_size=16的效果，可以设置gradient_accumulation_steps=8，即累积8次梯度后更新一次参数。

**学习率调度（Learning Rate Scheduling）**

微调时通常使用余弦退火（Cosine Annealing）学习率调度策略：学习率从一个初始值开始，随着训练进行按余弦曲线逐渐降低。这有助于模型在训练初期快速收敛，在训练后期精细调整。

典型的学习率设置：
- SFT + LoRA：学习率通常为1e-4到5e-4
- SFT + 全量微调：学习率通常为1e-5到5e-5
- 学习率需要根据具体模型和任务进行调整

**Warmup**

在训练开始时，模型的参数离最优解较远，使用大的学习率可能导致训练不稳定。Warmup策略是在训练的前几个step使用较小的学习率，然后逐渐增加到目标学习率。这有助于训练的稳定。

### 4.5 SFT的适用场景

SFT适用于以下场景：

场景一：领域知识注入。当你需要让模型掌握某个特定领域的知识时，比如医疗、法律、金融等。通过在领域数据上进行SFT，模型可以学习到领域的专业术语、知识结构和回答模式。

场景二：任务能力增强。当你需要让模型在某个特定任务上表现更好时，比如代码生成、数学推理、文本分类等。通过在任务特定的数据上SFT，模型可以提升在该任务上的准确率。

场景三：输出格式控制。当你需要模型按照特定格式输出时，比如JSON格式、特定模板等。SFT可以让模型学会遵循特定的输出格式。

场景四：风格和语调调整。当你需要模型的回答具有特定的风格或语调时，比如客服风格、教学风格等。SFT可以让模型学习到特定的语言风格。

场景五：安全和合规。当你需要模型避免输出某些敏感内容时，可以通过SFT让模型学会在特定场景下的安全边界。

## 第五章 参数高效微调（PEFT）全解

### 5.1 PEFT的动机：双重挑战

随着大模型参数规模的增长，全量微调面临着"双重挑战"：

存储挑战：全量微调需要存储模型参数、梯度、优化器状态等。以一个7B参数的模型为例，模型参数本身需要约14GB（FP16），梯度需要14GB，AdamW优化器状态需要28GB（一阶矩和二阶矩），加起来至少需要56GB的显存。如果是一个70B参数的模型，全量微调需要约560GB显存，这远超单张GPU的容量。

部署挑战：全量微调后，每个任务都需要保存一份完整的模型副本。如果有10个不同的任务，就需要保存10个完整的模型，存储成本极高。而且切换任务时需要加载不同的模型，耗时较长。

针对这双重挑战，参数高效微调技术（Parameter-Efficient Fine-Tuning，PEFT）应运而生。PEFT旨在通过仅训练一小部分参数来解决计算资源的问题，因此PEFT技术可以在提高模型效果的同时，显著降低训练和存储的成本。

### 5.2 PEFT技术分类

高效微调技术粗略分为三个大类：

**Additive（增加额外参数）**

这类方法的核心思想是在预训练模型的基础上添加小型辅助模块或新参数集来扩展基础模型。主要分为两个小类：

Adapters（适配器）：在前馈神经网络模块内部增添一个辅助模块，以此实现对模型的针对性增强，而无需全面调整原有架构。适配器通常是一个小型的瓶颈网络（bottleneck network），先降维再升维，参数量很小。

Soft Prompts（软提示）：包括Prefix Tuning、Prompt Tuning、P-Tuning V1和P-Tuning V2等。其特点是绕过对庞大预训练模型权重的直接调整，转而专注于优化模型的响应机制，仅通过对提示（Prompts）的精心设计与调整，即可有效引导大模型产生期望的输出变化。

**Selective（选取一部分参数更新）**

这类方法聚焦于有选择性地对模型现有的参数集合进行细微调整。调整依据可涉及模型层次的深度、不同类型的功能层，乃至具体参数的重要性。比如只更新模型最后几层的参数，或者只更新特定类型的参数（如偏置项bias）。

**Reparametrization-based（引入重参数化）**

这类方法通过变换预训练模型的参数配置，乃至对网络架构本身进行适度改造，力求以较小规模的模型或参数调整来逼近并复制大模型的性能表现。LoRA是这一类中的典型代表。

### 5.3 PEFT的核心优势

PEFT相比全量微调有以下核心优势：

训练效率高：需要更新的参数量从数十亿降到几百万甚至几十万，训练速度大幅提升。反向传播只需要计算少量参数的梯度，计算量大幅减少。

显存占用低：不需要为所有参数存储梯度和优化器状态。以7B模型为例，全量微调需要56GB显存，而LoRA只需要不到10GB，一张消费级显卡就能跑。

存储成本低：微调后的模型文件只有几十MB（LoRA）而不是几十GB。同一个基座模型可以挂载多个不同的PEFT模块来服务不同任务，极大降低了存储成本。

避免灾难性遗忘：原始模型参数保持不变，模型不会"忘记"预训练阶段学到的知识。PEFT模块只是在此基础上增加新的能力。

多任务灵活切换：同一个基座模型可以准备多套PEFT模块，需要哪个任务就加载对应的模块，切换只需要几秒钟。

### 5.4 PEFT的理论基础

为什么只更新少量参数就能达到很好的效果？这背后有一个关键洞察：

当你微调大模型时，虽然理论上所有参数都会变化，但真正"有意义的变化"其实集中在一个很低维的空间里。通俗地说，大部分参数的调整幅度非常微小，真正起作用的变化只涉及参数空间的一个小角落。

这个现象被称为"内在维度"（Intrinsic Dimension）。研究表明，一个有数十亿参数的大模型，其微调时的有效内在维度可能只有几百到几千。这意味着，我们不需要更新所有参数，只需要在低维空间中找到正确的调整方向就够了。

LoRA正是利用了这个原理。它不是给每个参数都加一个修正量，而是用两个很小的矩阵相乘来近似表示参数的变化。这两个小矩阵的"秩"（rank）很低，所以总参数量极少，但乘出来的结果却能覆盖原始参数需要调整的那部分空间。

### 5.5 PEFT的主要方法概览

以下是PEFT领域的主要方法和它们的特点：

| 方法 | 类型 | 参数量 | 效果 | 训练稳定性 | 推理开销 | 代表论文 |
|------|------|--------|------|-----------|---------|---------|
| Adapter | Additive | 中等 | 较好 | 稳定 | 有额外开销 | 2019, Houlsby et al. |
| Prefix Tuning | Additive | 很少 | 一般 | 不稳定 | 无额外开销 | 2021, Li & Liang |
| P-Tuning v2 | Additive | 很少 | 较好 | 较稳定 | 无额外开销 | 2022, Liu et al. |
| LoRA | Reparam. | 很少 | 接近FFT | 稳定 | 可合并无开销 | 2021, Hu et al. |
| QLoRA | Reparam. | 极少 | 接近LoRA | 稳定 | 可合并无开销 | 2023, Dettmers et al. |
| AdaLoRA | Reparam. | 自适应 | 优于LoRA | 稳定 | 可合并无开销 | 2023, Zhang et al. |
| DoRA | Reparam. | 很少 | 优于LoRA | 稳定 | 可合并无开销 | 2024, Liu et al. |

目前，LoRA及其变体（QLoRA、AdaLoRA、DoRA等）是最主流的PEFT方法，几乎成为了微调的默认选择。下面几章将详细讲解这些方法。

## 第六章 LoRA深度解析：极低成本微调大模型

### 6.1 LoRA的核心思想

LoRA（Low-Rank Adaptation，低秩适配）的核心思想可以用一句话概括：给大模型贴一张"便签纸"，在原始参数完全不动的情况下，额外训练一组极小的新参数来补充新能力。想用就贴上，不想用就撕掉，互不影响。

用一个更详细的类比来理解：你有一本很厚的百科全书，内容涵盖天文地理物理化学，什么都有。现在你接到一个新任务：下周要参加一场法律知识竞赛。你需要让这本百科全书"懂法律"。

最笨的方法是把整本百科全书重新印一遍，在每一页都加上法律相关的内容。成本极高，而且改完之后如果你下周又要参加医学竞赛，难道再重印一遍？

聪明的做法是：百科全书一个字都不改，你另外准备一小叠便签纸，把法律知识写在便签上，贴在百科全书相关页面的边上。查阅的时候，你同时看正文和便签，两部分信息合在一起就是答案。下周要参加医学竞赛？把法律便签撕掉，换贴一叠医学便签就行。百科全书本身始终是那本百科全书。

LoRA做的就是这件事：大模型的原始参数是那本百科全书，完全不动。LoRA训练出来的是一小叠"便签纸"（额外的小参数矩阵），贴上去就获得了新能力，撕掉就恢复原样。

### 6.2 LoRA的数学原理

在标准的微调中，模型中某个权重矩阵W的更新可以表示为：

```
W' = W + ΔW
```

其中W是原始权重（冻结不动），ΔW是微调导致的权重变化。在全量微调中，ΔW与W具有相同的维度，参数量相同。

LoRA的核心创新是将ΔW分解为两个小矩阵的乘积：

```
ΔW = A × B
```

其中A是一个d×r的矩阵，B是一个r×k的矩阵，r是"秩"（rank），通常远小于d和k。例如，如果原始权重矩阵W是4096×4096的，有约1600万个参数，当r=8时，A是4096×8（约3.3万个参数），B是8×4096（约3.3万个参数），总共只有约6.6万个参数，是原始参数量的0.4%。

为什么这种分解是合理的？因为前面提到的"内在维度"理论：微调时真正有意义的变化集中在低维空间中。两个小矩阵的乘积虽然参数量少，但能够表达足够丰富的变化模式。

具体来说，LoRA的参数分解如下：

- 原始权重矩阵 W ∈ R^(d×k)：冻结不训练
- 降维矩阵 A ∈ R^(d×r)：可训练，使用随机高斯初始化
- 升维矩阵 B ∈ R^(r×k)：可训练，初始化为零
- 缩放因子 α/r：控制LoRA更新的幅度

在前向传播中：

```
h = Wx + (α/r) × BAx
```

其中x是输入，h是输出，α是缩放超参数，r是秩。

注意B初始化为零，这意味着在训练开始时BA=0，LoRA不改变模型的输出。随着训练进行，A和B逐渐学习到有意义的参数变化。

### 6.3 LoRA的具体数字：从70亿到几百万

让我们用一个70亿参数的模型来算一笔账。

传统的全量微调需要更新全部70亿个参数。训练时的显存占用包括：
- 模型参数（FP16）：约14GB
- 梯度（FP16）：约14GB
- AdamW优化器状态（FP32的一阶矩和二阶矩）：约56GB
- 总计：约84GB

至少需要两张A100 80GB显卡才能跑。

用LoRA呢？它在模型的某些关键层旁边插入一对很小的矩阵，这对矩阵的参数量通常只有原始模型的0.1%到1%。以70亿参数模型为例，LoRA额外增加的参数大约是700万到7000万个。训练时：
- 模型参数（FP16，冻结）：约14GB
- LoRA参数（可训练）：约14MB到140MB
- LoRA梯度：约14MB到140MB
- AdamW优化器状态（只针对LoRA参数）：约28MB到280MB
- 激活值和其他开销：约2-4GB
- 总计：约16-18GB

一张普通的消费级显卡（比如RTX 4090的24GB显存）就足够跑。

效果呢？在大多数任务上，LoRA能达到全量微调效果的95%以上。而且训练速度快了好几倍，因为要更新的参数少了上百倍。

更重要的是，训练完的LoRA文件体积极小。一个70亿参数模型对应的LoRA文件可能只有几十MB，而原始模型有14GB。这意味着你可以给同一个基础模型准备几十套不同的LoRA：一套专门写代码、一套专门做翻译、一套专门聊法律、一套专门写小说。需要哪个技能就加载哪个LoRA，切换只需要几秒钟。

### 6.4 LoRA在哪些层上应用

一个大模型有很多层，包括注意力层（Attention）和前馈神经网络层（FFN）。LoRA应该应用在哪些层上？

原始的LoRA论文建议应用在注意力层的Query和Value投影矩阵上。但后续研究表明，将LoRA应用在更多层上（包括Key投影、Output投影、FFN的up和down投影等）可以获得更好的效果，当然参数量也会相应增加。

不同框架的默认配置：
- HuggingFace PEFT默认只应用在Query和Value上
- LLaMA-Factory默认应用在所有线性层上
- 实践中，应用在所有线性层上效果最好，但参数量增加

常见的LoRA配置：

| 配置 | 应用层 | 参数量占比 | 效果 | 适用场景 |
|------|--------|-----------|------|---------|
| 最小配置 | Q, V | ~0.1% | 一般 | 资源极度受限 |
| 标准配置 | Q, K, V, O | ~0.3% | 较好 | 日常使用 |
| 完整配置 | 所有线性层 | ~1% | 最好 | 追求最优效果 |

### 6.5 LoRA的关键超参数

**秩（Rank, r）**

秩r是LoRA最重要的超参数，控制着LoRA的表达能力。r越大，LoRA能表达的参数变化模式越丰富，但参数量也越多。

- r=4或8：适用于简单任务（如格式控制、简单分类）
- r=16或32：适用于中等复杂度任务（如领域问答、翻译）
- r=64或128：适用于复杂任务（如代码生成、数学推理）

实践中，r=8或16是常用的起始值。如果效果不够好，可以逐步增大r。

**缩放因子（Alpha, α）**

Alpha控制LoRA更新的幅度，实际作用类似于学习率。LoRA的更新量为(α/r) × BA，因此α/r的比值决定了LoRA对原始模型的影响程度。

- 通常设置α = r或α = 2r
- 如果α太小，LoRA的影响不够，效果可能不好
- 如果α太大，可能破坏预训练模型的知识

**Dropout**

LoRA中也可以使用Dropout来防止过拟合，通常设置为0.05或0.1。

### 6.6 LoRA的训练和推理

**训练阶段**

在训练阶段，LoRA的做法是：
1. 加载预训练模型，冻结所有原始参数
2. 在指定的层旁边添加LoRA矩阵A和B
3. 只对A和B的参数计算梯度和更新
4. 训练完成后，保存A和B的参数

**推理阶段**

在推理阶段，有两种使用LoRA的方式：

方式一：合并模式。将LoRA参数合并到原始权重中：

```
W_merged = W + (α/r) × BA
```

合并后，模型的结构和大小与原始模型完全相同，没有任何额外的推理开销。这是最常用的方式。

方式二：适配器模式。保持LoRA参数与原始模型分离，在推理时动态加载。这种方式的好处是可以随时切换不同的LoRA，适合多任务场景。

### 6.7 LoRA的变体

**AdaLoRA（Adaptive LoRA）**

AdaLoRA在训练过程中动态调整不同层的LoRA秩r。它根据各层的重要性自动分配参数预算，重要的层分配更高的秩，不重要的层分配更低的秩。这样可以更有效地利用有限的参数预算。

**DoRA（Weight-Decomposed LoRA）**

DoRA将权重矩阵分解为方向（direction）和幅度（magnitude）两个部分，分别对它们应用LoRA。研究表明这种分解方式更接近全量微调的权重更新模式，效果通常优于标准LoRA。

**LoRA+**

LoRA+对矩阵A和B使用不同的学习率。矩阵B使用更高的学习率，矩阵A使用更低的学习率。这种非对称的学习率设置可以加速训练收敛并提升最终效果。

### 6.8 LoRA的实际使用示例

以下是使用HuggingFace PEFT库进行LoRA微调的示例代码：

```python
from peft import LoraConfig, get_peft_model, TaskType
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import SFTTrainer, SFTConfig

# 1. 加载预训练模型
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2-7B-Instruct",
    torch_dtype=torch.float16,
    device_map="auto"
)
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2-7B-Instruct")

# 2. 配置LoRA
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                    # 秩
    lora_alpha=32,           # 缩放因子
    lora_dropout=0.05,       # dropout
    target_modules=[         # 应用LoRA的层
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj"
    ],
)

# 3. 将LoRA应用到模型上
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# 输出: trainable params: 19,981,312 || all params: 7,621,681,152 || trainable%: 0.2621%

# 4. 配置训练参数
training_config = SFTConfig(
    output_dir="./output",
    num_train_epochs=3,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    learning_rate=2e-4,
    warmup_ratio=0.1,
    lr_scheduler_type="cosine",
    logging_steps=10,
    save_strategy="epoch",
    fp16=True,
)

# 5. 开始训练
trainer = SFTTrainer(
    model=model,
    args=training_config,
    train_dataset=train_dataset,
    tokenizer=tokenizer,
)
trainer.train()

# 6. 保存LoRA权重
model.save_pretrained("./lora_output")
```

训练完成后，LoRA权重通常只有几十MB：

```
./lora_output/
├── adapter_config.json    # LoRA配置
├── adapter_model.safetensors  # LoRA权重（几十MB）
```

使用时，可以将LoRA权重合并到基座模型中：

```python
from peft import PeftModel

# 加载基座模型
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2-7B-Instruct")

# 加载LoRA
model = PeftModel.from_pretrained(base_model, "./lora_output")

# 合并权重（推理时无额外开销）
model = model.merge_and_unload()
```

## 第七章 QLoRA：在消费级显卡上微调大模型

### 7.1 QLoRA的动机

LoRA已经大幅降低了微调的显存需求，但对于更大的模型（如33B、65B参数），即使使用LoRA，仍然需要相当大的显存来加载基座模型。QLoRA就是为了解决这个问题而提出的。

QLoRA（Quantized LoRA）的核心思想是：在LoRA的基础上，将基座模型量化到4位精度（4-bit），进一步降低显存占用，同时尽量保持模型精度。

QLoRA的论文标题是"QLoRA: Efficient Finetuning of Quantized LLMs"，由华盛顿大学的Tim Dettmers等人于2023年提出。这篇论文是一个里程碑式的工作，它首次证明了可以在一张消费级显卡上微调一个相当大的模型，而效果几乎没有损失。

### 7.2 QLoRA的三大创新

QLoRA包含三个关键创新：

**创新一：4位NormalFloat量化（NF4）**

传统的量化方法（如INT4量化）使用均匀分布的量化级别，但神经网络的权重通常不是均匀分布的——它们更接近正态分布。NF4（4-bit NormalFloat）是一种专为正态分布设计的量化格式，它的量化级别按照正态分布的分位点排列，因此在量化正态分布的权重时，信息损失更小。

NF4的量化过程：
1. 将权重的绝对值归一化到[-1, 1]范围
2. 将归一化后的权重映射到16个NF4量化级别之一
3. 存储4位索引而不是完整权重

反量化时，根据索引查表恢复近似的权重值。

**创新二：双重量化（Double Quantization）**

量化过程中需要存储每个量化组的缩放因子（scale）和零点（zero point），这些额外的参数也会占用显存。双重量化是对这些缩放因子本身再进行一次量化，从FP32量化到8位，进一步减少显存占用。

虽然双重量化节省的显存看起来不多（约0.4 bits/parameter），但对于大模型来说，累积起来也很可观。以65B模型为例，双重量化可以节省约3GB显存。

**创新三：分页优化器（Paged Optimizer）**

QLoRA使用NVIDIA的统一内存机制来实现分页优化器。当GPU显存不足时，优化器状态会自动"溢出"到CPU内存中，需要时再加载回GPU。这避免了显存不足导致的OOM错误，使得训练过程更加稳定。

### 7.3 QLoRA的显存优势

以不同模型大小为例，对比全量微调、LoRA和QLoRA的显存需求：

| 模型大小 | 全量微调 | LoRA | QLoRA |
|---------|---------|------|-------|
| 7B | ~84GB | ~16GB | ~6GB |
| 13B | ~156GB | ~28GB | ~10GB |
| 33B | ~400GB | ~64GB | ~24GB |
| 65B | ~780GB | ~120GB | ~40GB |

可以看到，QLoRA让7B模型的微调只需要6GB显存，这意味着连一张RTX 3060（12GB）就能跑。33B模型的QLoRA微调只需要24GB显存，一张RTX 4090就能搞定。这在QLoRA出现之前是不可想象的。

### 7.4 QLoRA的精度

QLoRA的核心担心是：4位量化会不会导致精度严重下降？答案是：在大多数任务上，精度损失非常小。

QLoRA论文中的实验结果表明：
- QLoRA在多个基准测试上达到了与全量微调匹配的效果
- 量化后的基座模型虽然精度有所降低，但LoRA训练的梯度仍然是高精度的（BF16），因此模型可以学习到精细的调整
- 在推理时，可以将LoRA权重合并到量化模型中，或者反量化后合并

### 7.5 QLoRA的使用示例

```python
from transformers import BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

# 1. 配置4位量化
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",          # 使用NF4量化
    bnb_4bit_use_double_quant=True,      # 启用双重量化
    bnb_4bit_compute_dtype=torch.bfloat16, # 计算时用BF16
)

# 2. 加载量化后的模型
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2-7B-Instruct",
    quantization_config=bnb_config,
    device_map="auto"
)

# 3. 为量化模型准备训练
model = prepare_model_for_kbit_training(model)

# 4. 配置LoRA（与普通LoRA相同）
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    task_type="CAUSAL_LM",
)

model = get_peft_model(model, lora_config)

# 后续训练流程与普通LoRA相同
```

### 7.6 QLoRA的适用场景与限制

QLoRA最适合以下场景：
- 计算资源有限（如只有消费级GPU）
- 需要微调较大的模型（33B以上）
- 快速实验和原型开发
- 教育和个人学习

QLoRA的限制：
- 量化会引入少量精度损失，虽然通常可以忽略
- 训练速度比非量化的LoRA慢一些（因为需要频繁反量化）
- 量化模型在某些推理框架上的兼容性可能不如标准模型

## 第八章 其他PEFT方法详解

### 8.1 Prefix Tuning

Prefix Tuning是一种增量调整策略，通过在模型输入前附加一系列专为特定任务设计的连续向量来实现其独特性。在此机制中，仅对这些被称为"前缀"的参数进行优化，并将其融入模型每一层级的隐藏状态之中，而模型的其余部分保持不变。

通俗理解：Prefix Tuning就像是在每次对话之前，先给模型"念一段咒语"。这段"咒语"不是人类能读懂的文字，而是一组连续的向量，模型在处理输入时会同时考虑这些向量。这些向量是可训练的，通过训练让模型学会在"念了这段咒语"后更好地完成特定任务。

Prefix Tuning的优势在于参数效率高——只需要训练很少的前缀参数。但它也有局限性：前缀占用了模型的输入容量，可能对生成质量产生不利影响；而且训练不太稳定，对超参数敏感。

### 8.2 P-Tuning v2

P-Tuning v2是Prefix Tuning的改进版本。与Prefix Tuning类似，它在模型的每一层都添加可训练的前缀向量。但P-Tuning v2解决了一些技术问题，使得训练更加稳定，效果也更好。

P-Tuning v2的核心改进：
1. 去掉了Prefix Tuning中的多层感知机（MLP）结构，简化了模型
2. 在更多层上添加前缀，而不仅仅是在输入层
3. 引入了多任务学习的支持

P-Tuning v2在效果上接近LoRA，但不如LoRA流行，主要原因是LoRA的推理更加方便（可以合并权重，无额外开销）。

### 8.3 Adapter

Adapter是在Transformer层内部添加小型瓶颈网络模块的方法。一个标准的Adapter包含：
1. 降维层：将隐藏维度从d降到r（如4096→64）
2. 非线性激活函数（如ReLU或GELU）
3. 升维层：将隐藏维度从r升回d（如64→4096）
4. 残差连接：输出 = 输入 + Adapter(输入)

Adapter的参数量很少（因为瓶颈维度r很小），训练效率高。但它的缺点是推理时会引入额外的计算开销（每次前向传播都要经过Adapter层），不如LoRA方便。

### 8.4 各种PEFT方法的选择建议

在实际应用中，PEFT方法的选择建议如下：

对于大多数场景：选择LoRA。它是目前最成熟、最流行、生态支持最好的PEFT方法。效果接近全量微调，使用方便，推理无额外开销。

对于资源极度受限的场景：选择QLoRA。在LoRA的基础上进一步量化基座模型，最小化显存需求。

对于追求最优效果且资源充足：选择DoRA或LoRA+。这些LoRA变体在效果上有所提升，且使用方式与标准LoRA类似。

对于特殊需求（如只能修改提示不能改模型）：考虑P-Tuning v2。但一般不推荐，因为LoRA通常效果更好且更方便。

## 第九章 全量微调（Full Fine-Tuning）

### 9.1 什么是全量微调

全量微调（Full Fine-Tuning，FFT）是指在微调过程中更新模型的所有参数。这是最传统的微调方式，也是效果理论上最好的方式——因为模型有最大的自由度来适应新任务。

全量微调的适用场景：
- 有充足的计算资源（多张A100/H100级别的GPU）
- 追求最优效果，效果差异1%也很重要
- 任务与预训练领域差异较大，需要模型做较大幅度的调整
- 有大量高质量训练数据（数万条以上）
- 需要注入大量领域知识

### 9.2 全量微调的显存分析

全量微调的显存占用是理解其成本的关键。以一个7B参数模型为例：

| 组件 | 精度 | 显存占用 |
|------|------|---------|
| 模型参数 | FP16 | 14GB |
| 梯度 | FP16 | 14GB |
| AdamW优化器-一阶矩 | FP32 | 28GB |
| AdamW优化器-二阶矩 | FP32 | 28GB |
| 激活值 | FP16 | 2-8GB（取决于batch size和序列长度） |
| 总计 | | ~86-92GB |

这意味着全量微调一个7B模型，至少需要一张A100 80GB（配合梯度检查点等技术勉强够用）或两张A100 80GB。对于更大的模型，成本更高。

### 9.3 降低全量微调显存的技术

虽然全量微调显存需求大，但有一些技术可以降低显存使用：

**混合精度训练（Mixed Precision Training）**

使用FP16或BF16进行前向传播和反向传播，减少显存占用。优化器状态仍然使用FP32存储以保证训练稳定性。

**梯度检查点（Gradient Checkpointing）**

正常情况下，反向传播需要前向传播时所有中间层的激活值。梯度检查点技术不保存所有中间激活值，而是在反向传播时重新计算部分激活值。这以增加约30%的计算时间为代价，大幅减少显存占用。

**ZeRO优化（Zero Redundancy Optimizer）**

DeepSpeed的ZeRO优化将优化器状态、梯度和模型参数分散到多个GPU上，消除数据并行中的冗余：

- ZeRO Stage 1：分片优化器状态，显存减少约4倍
- ZeRO Stage 2：分片优化器状态+梯度，显存减少约8倍
- ZeRO Stage 3：分片优化器状态+梯度+模型参数，显存减少约N倍（N为GPU数量）

**CPU Offload**

将不常用的参数或优化器状态卸载到CPU内存中，需要时再加载到GPU。这可以大幅减少GPU显存需求，但会增加训练时间（因为CPU-GPU数据传输有延迟）。

### 9.4 全量微调 vs LoRA：何时选择全量微调

虽然LoRA在大多数场景下已经足够好，但在以下情况下，全量微调可能更好：

情况一：需要注入大量新知识。LoRA更适合调整模型的行为模式（如输出格式、回答风格），而全量微调更适合注入大量新知识（如特定领域的深度知识）。如果你的任务需要模型"知道很多新东西"，全量微调可能效果更好。

情况二：任务与预训练领域差异巨大。如果你的任务与模型的预训练领域差异很大（比如用英文模型做中文任务，或用通用模型做高度专业的医学诊断），全量微调可能更有效。

情况三：有充足的资源和数据。如果你有充足的GPU资源和大量高质量训练数据，全量微调可以榨取更好的效果。

但在实际业务中，90%以上的场景，LoRA已经足够好。除非你有明确的理由需要全量微调，否则建议从LoRA开始。

## 第十章 对齐微调：RLHF、DPO、GRPO

### 10.1 为什么需要对齐微调

SFT教会了模型"怎么回答问题"，但SFT有一个根本性的局限：它只能学习"正确答案"，无法学习"什么是更好的答案"。

很多任务没有唯一的正确答案。比如：
- "写一首关于秋天的诗"：可以有无数种写法，有的比其他的好
- "帮我回复这封邮件"：有的回复更礼貌、更得体
- "解释量子力学"：有的解释更清晰、更易懂

对于这类任务，我们需要一种方法来教模型"什么是更好的回答"，而不仅仅是"什么是正确的回答"。这就是对齐微调要解决的问题。

### 10.2 RLHF：基于人类反馈的强化学习

RLHF（Reinforcement Learning from Human Feedback）是OpenAI在训练ChatGPT时使用的方法，也是最早被广泛采用的对齐技术。

RLHF的流程分为三个步骤：

**步骤一：训练奖励模型（Reward Model）**

对于同一个问题，让模型生成多个不同的回答。然后让人类标注员对这些回答进行排序（从最好到最差）。利用这些排序数据训练一个奖励模型，这个模型可以给任意一个"问题-回答"对打分，分数越高表示回答越好。

奖励模型的训练数据格式：

```json
{
  "prompt": "解释什么是机器学习",
  "chosen": "机器学习是人工智能的一个分支，它使计算机系统能够通过数据自动学习和改进，而无需明确编程...",
  "rejected": "机器学习就是让机器学习东西。"
}
```

人类标注员认为chosen比rejected好，奖励模型需要学会给chosen打更高的分。

**步骤二：使用强化学习优化模型**

有了奖励模型后，就可以使用强化学习来优化策略模型（即我们要微调的LLM）。常用的强化学习算法是PPO（Proximal Policy Optimization）。

PPO的训练过程：
1. 策略模型对一批问题生成回答
2. 奖励模型对每个"问题-回答"对打分
3. 使用PPO算法根据奖励信号更新策略模型
4. 同时使用KL散度约束，防止策略模型偏离原始模型太远

**步骤三：迭代优化**

步骤一和步骤二可以交替进行：收集新的人类反馈→更新奖励模型→用新的奖励模型优化策略模型→收集新的人类反馈→...

**RLHF的优点：**
- 理论上效果最好，ChatGPT的成功证明了这一点
- 可以学习到非常精细的人类偏好

**RLHF的缺点：**
- 流程复杂，需要训练奖励模型和策略模型两个模型
- PPO训练不稳定，需要大量调参
- 需要大量人类标注数据，成本高
- 计算资源需求大（PPO需要同时运行策略模型、奖励模型、参考模型和价值模型）

### 10.3 DPO：直接偏好优化

DPO（Direct Preference Optimization）是RLHF的简化版本，由斯坦福大学等机构于2023年提出。DPO通过巧妙的数学推导，跳过了奖励模型的训练步骤，直接从偏好数据中优化模型。

**DPO的核心思想：**

DPO的推导过程使用了RLHF的优化目标函数，得出了对齐模型的显示解。具体来说，DPO证明了：在RLHF的最优策略下，奖励函数可以用策略模型本身来表达。因此，不需要单独训练奖励模型，可以直接用偏好数据来优化策略模型。

**DPO的损失函数：**

```
L_DPO = -log σ(β × (log π_θ(y_w|x)/π_ref(y_w|x) - log π_θ(y_l|x)/π_ref(y_l|x)))
```

其中：
- π_θ是正在训练的策略模型
- π_ref是参考模型（通常是SFT后的模型，训练过程中冻结）
- y_w是偏好数据中"更好"的回答（chosen）
- y_l是偏好数据中"更差"的回答（rejected）
- β是温度参数，控制偏离参考模型的程度
- σ是sigmoid函数

这个损失函数的含义是：让策略模型给"更好的回答"赋予比参考模型更高的概率，给"更差的回答"赋予比参考模型更低的概率。

**DPO的优点：**
- 无需奖励模型，简化了训练流程
- 训练稳定，不像PPO那样需要复杂的调参
- 计算资源需求低（只需要策略模型和参考模型两个模型）
- 效果与RLHF相当

**DPO的缺点：**
- 需要偏好数据（比SFT的数据更难收集）
- 对于非常复杂的多轮对话场景，效果可能不如RLHF
- β参数需要仔细调整

### 10.4 GRPO：群体相对策略优化

GRPO（Group Relative Policy Optimization）是DeepSeek团队提出的一种新的强化学习算法，在DeepSeek-R1中得到了应用。GRPO的核心创新是移除了PPO中的价值模型（Critic），通过同一问题下多个输出的组内比较来估计优势信号。

**GRPO的动机：**

PPO采用Actor-Critic架构，包含Actor（策略）、Critic（价值）、Reward（奖励）和Reference（参考）四种模型。Critic模型用于估计每个状态的价值，但actor与critic的交互会带来过高的计算成本。

GRPO的亮点在于去除Critic模型，用精心设计的Rule-based Reward取代难以调试的Reward模型进行判别，最终仅需要Actor和Reference两个模型，成本更低。

**GRPO的工作方式：**

对于每个问题，模型生成一组（通常是4-16个）不同的回答。然后使用规则奖励（如答案是否正确）对每个回答打分。通过组内比较（同一问题的不同回答之间的相对比较）来计算优势函数，指导模型优化。

**GRPO的适用场景：**

GRPO特别适合可验证奖励的场景——即答案的正确性可以自动验证的场景，如数学推理（答案对不对可以自动检查）和代码生成（代码能不能通过测试可以自动验证）。在这些场景中，GRPO的组内比较能够提供足够稳定的信号。

**从PPO到GRPO的对比：**

| 特性 | PPO | DPO | GRPO |
|------|-----|-----|------|
| 需要奖励模型 | 是 | 否 | 否（使用规则奖励） |
| 需要价值模型 | 是 | 否 | 否 |
| 训练稳定性 | 一般 | 好 | 较好 |
| 计算资源需求 | 最高 | 最低 | 中等 |
| 适合可验证任务 | 可以 | 可以 | 非常适合 |
| 适合开放式任务 | 非常适合 | 适合 | 一般 |
| 代表应用 | ChatGPT | LLaMA-2-Chat | DeepSeek-R1 |

### 10.5 对齐微调的实践建议

**何时需要对齐微调：**

对于大多数业务场景，SFT + LoRA已经足够好。对齐微调（RLHF/DPO）适用于以下情况：
- SFT后模型效果基本达标，但在某些细节上不够好
- 有明确的"好回答"和"差回答"的判断标准
- 有能力收集偏好数据
- 追求极致的用户体验

**DPO的实践流程：**

1. 先用SFT训练一个基础模型
2. 收集偏好数据：让SFT模型对每个问题生成多个回答，人工或自动选择"好"和"差"
3. 使用偏好数据训练DPO
4. 评估DPO后的模型效果

**企业实践参考：**

某互联网公司服务零售团队在QwQ-32B模型的微调中，先使用SFT将标注准确率从63.60%提升到86.80%，然后针对SFT模型较难解决的bad case，使用DPO进一步优化，将准确率从86.80%提升到92.57%。这是一个典型的"SFT + DPO"两阶段微调实践。

## 第十一章 微调数据工程：数据是王道

### 11.1 数据质量 > 数据数量

在微调领域，有一个被反复验证的规律：数据质量远比数据数量重要。1000条高质量数据的训练效果，往往优于10000条低质量数据。

这背后的原因很简单：微调本质上是在教模型新的知识和行为模式。如果"教材"（训练数据）质量差，模型学到的也会差。低质量数据不仅不能帮助模型学习，还可能引入噪声，导致模型效果下降。

一个经典的例子是LIMA论文（"Less Is More for Alignment"）。研究者仅用1000条精心筛选的高质量数据就微调出了效果惊人的模型，证明了数据质量的极端重要性。

### 11.2 微调数据的来源

微调数据通常来自以下几个渠道：

**人工标注**

最直接的方式是请专业人员编写"问题-答案"对。这种方式的数据质量最高，但成本也最高。适用于对质量要求极高的场景。

**业务日志挖掘**

从实际业务交互中挖掘数据。比如从客服对话记录中提取高质量的问答对。这种方式的数据最贴近实际业务场景，但需要处理隐私和敏感信息问题。

**开源数据集**

利用公开的数据集，如Alpaca、ShareGPT、FLAN等。这些数据集通常包含大量通用的指令-回答对，适合作为微调的初始数据。但它们可能不够垂直，需要结合领域数据使用。

**合成数据（Synthetic Data）**

使用强大的模型（如GPT-4）来生成训练数据。这种方式可以快速大量地生成数据，但需要注意质量控制。合成数据的质量取决于生成模型的能力和prompt的设计。

**数据增强**

对现有数据进行改写、扩展、翻译等操作来生成更多数据。比如将一个问题的答案换一种表述方式，或者将英文数据翻译成中文。

### 11.3 指令数据构造

指令数据的构造是SFT微调的核心环节。好的指令数据需要满足以下要求：

**多样性**

指令应该覆盖尽可能多的场景和任务类型。如果所有指令都是"请解释XXX"这种格式，模型可能只会学会这种模式。应该包含问答、翻译、总结、分类、推理、创作等多种任务类型。

**准确性**

答案必须准确。如果答案本身是错误的，模型就会学到错误的知识。这听起来是显然的，但在实际操作中，保证每条数据的准确性是非常耗时耗力的。

**格式一致性**

如果希望模型以特定格式输出，训练数据的格式就应该统一。如果有的答案用markdown格式，有的用纯文本，模型可能学到混乱的格式。

**难度分布**

指令应该有不同难度级别。如果所有问题都很简单，模型可能学不到复杂的推理能力。应该包含简单、中等和困难不同难度的问题。

**指令数据构造的具体方法：**

方法一：Self-Instruct。使用已有的强大模型生成指令数据。给GPT-4一个种子指令，让它生成更多类似的指令和答案。这种方法快速但需要质量控制。

方法二：Evol-Instruct。从一个简单的指令开始，逐步增加复杂度。比如从"1+1等于几"开始，逐步演化为更复杂的数学问题。

方法三：人工编写。请领域专家直接编写指令和答案。质量最高但成本也最高。

方法四：混合方法。结合以上多种方法，先用自动方法生成大量数据，再由人工筛选和修正。

### 11.4 数据质量控制

**数据清洗**

在收集到原始数据后，需要进行严格的清洗：
- 去除重复数据（完全重复和近似重复）
- 去除过短或过长的样本
- 去除格式异常的样本
- 去除包含敏感信息（PII）的数据
- 过滤低质量内容（如无意义的回答、与问题不匹配的答案等）

**数据质量评估**

可以采用以下方法评估数据质量：
- 人工抽检：随机抽取一部分数据进行人工审查
- 模型评分：使用强大的模型（如GPT-4）对数据质量打分
- 困惑度过滤：使用语言模型计算每条数据的困惑度，过高或过低的可能是异常数据
- 长度和分布分析：检查数据长度分布、任务类型分布等是否合理

**数据配比**

如果同时使用多种类型的数据，需要注意各类型数据的配比。比如，如果领域数据占80%，通用数据占20%，模型可能在领域任务上表现好，但通用能力下降。合理的配比需要通过实验确定。

某互联网公司服务零售团队的实践是一个很好的例子。他们采用了"规则+LLM判断"的两阶段数据筛选方法来提升SFT微调数据集质量：首先通过规则过滤掉原始数据中意图理解数据缺失以及人工标注原因为"不清楚怎么分类"的数据；然后通过梳理人工标注链路，利用DeepSeek-r1生成思维链，通过ChatGPT-4o-mini来判断思维链与已有标注结果的逻辑一致性，最终获得高质量CoT数据集用于SFT微调。

### 11.5 偏好数据构造（用于DPO/RLHF）

对于对齐微调，需要的是偏好数据而不是简单的"指令-答案"对。偏好数据的格式是：

```json
{
  "prompt": "用户的问题",
  "chosen": "更好的回答",
  "rejected": "更差的回答"
}
```

偏好数据的构造方法：

方法一：人工标注。让标注员对模型的多个输出进行排序，选择最好和最差的作为chosen和rejected。

方法二：利用已有数据。在SFT数据中，正确的答案作为chosen，模型生成的错误答案作为rejected。

方法三：模型辅助。让SFT模型生成多个回答，使用更强大的模型（如GPT-4）来判断哪个更好。

某互联网公司服务零售团队在DPO偏好数据构造中，针对模型较难解决的bad case类型，精心构造偏好数据对，通过DPO直接偏好优化的方式对SFT参考模型进行继续训练。

### 11.6 数据量需要多少

这是最常见的问题之一。答案取决于任务复杂度和数据质量：

| 任务类型 | 建议数据量 | 说明 |
|---------|-----------|------|
| 简单格式控制 | 100-500条 | 如让模型按特定格式输出 |
| 单一领域问答 | 1000-5000条 | 如客服FAQ、产品问答 |
| 多任务领域微调 | 5000-50000条 | 多种任务类型的综合微调 |
| 复杂推理任务 | 10000-100000条 | 如数学推理、代码生成 |
| 通用对话能力 | 50000+条 | 如ChatGPT级别的对话能力 |

重要提醒：以上是参考值，不是绝对标准。1000条高质量数据的效果可能优于10000条低质量数据。建议从小规模开始，逐步增加数据量，观察效果变化。

### 12.6 分布式训练策略

对于大型模型的微调，通常需要使用多张GPU进行分布式训练。主要的分布式策略包括：

**数据并行（Data Parallelism）**

每张GPU上有一份完整的模型副本，但处理不同的数据批次。训练完成后，各GPU的梯度进行同步，然后统一更新参数。最简单的并行策略，但要求每张GPU能放下完整模型。

**张量并行（Tensor Parallelism）**

将模型的单个层（如注意力矩阵）切分到多张GPU上。每张GPU只处理矩阵的一部分，需要频繁的GPU间通信。适合模型太大无法放入单卡的场景。

**流水线并行（Pipeline Parallelism）**

将模型的不同层分配到不同GPU上。数据像流水线一样依次通过各GPU。适合深度很大的模型。

**3D并行**

同时使用数据并行、张量并行和流水线并行，充分利用多GPU资源。这是训练超大模型的标准做法。

对于LoRA微调，通常使用数据并行就够了，因为LoRA的显存需求不大。对于全量微调，可能需要组合使用多种并行策略。

## 第十三章 微调超参数调优指南

### 13.1 关键超参数一览

微调中的关键超参数包括：

| 超参数 | 典型值范围 | 说明 |
|--------|-----------|------|
| 学习率 (learning_rate) | 1e-5 ~ 5e-4 | 最重要的超参数 |
| 训练轮数 (epochs) | 1 ~ 10 | 过多会过拟合 |
| 批量大小 (batch_size) | 4 ~ 128 | 受显存限制 |
| 梯度累积步数 | 1 ~ 16 | 模拟更大batch size |
| 预热比例 (warmup_ratio) | 0.03 ~ 0.1 | 训练初期的学习率预热 |
| 学习率调度器 | cosine / linear | 控制学习率衰减方式 |
| 权重衰减 (weight_decay) | 0.01 ~ 0.1 | 正则化，防止过拟合 |
| 最大梯度范数 (max_grad_norm) | 1.0 | 梯度裁剪，防止梯度爆炸 |
| LoRA秩 (r) | 4 ~ 128 | LoRA特有参数 |
| LoRA alpha (α) | r ~ 2r | LoRA缩放因子 |
| LoRA dropout | 0 ~ 0.1 | LoRA正则化 |

### 13.2 学习率选择

学习率是微调中最重要的超参数。选择不当的学习率可能导致训练不收敛（学习率太大）或训练过慢（学习率太小）。

不同微调方式的推荐学习率：

```
全量微调：1e-5 ~ 5e-5
LoRA微调：1e-4 ~ 5e-4
QLoRA微调：1e-4 ~ 3e-4
DPO微调：5e-7 ~ 5e-6（比SFT小很多）
```

为什么LoRA的学习率比全量微调大？因为LoRA只更新少量参数，这些参数是从零或随机初始化开始的，需要更大的学习率来快速收敛。而全量微调更新所有参数，这些参数已经在预训练中被优化过了，只需要微小的调整，因此学习率要小。

学习率的选择建议：
1. 从推荐范围的中间值开始（如LoRA用2e-4）
2. 如果训练loss不下降，增大学习率
3. 如果训练loss震荡或发散，减小学习率
4. 如果训练loss下降但效果不好，可能需要调整其他超参数

### 13.3 训练轮数选择

训练轮数（epochs）是指模型完整遍历训练数据集的次数。

选择建议：
- 数据量少（<1000条）：3-10轮
- 数据量中等（1000-10000条）：2-5轮
- 数据量大（>10000条）：1-3轮

训练轮数过多会导致过拟合——模型在训练数据上表现很好，但在未见过的数据上表现下降。判断过拟合的方法是观察验证集的loss：如果训练loss持续下降但验证loss开始上升，说明过拟合了。

### 13.4 Batch Size选择

Batch size影响训练的稳定性和速度。大的batch size通常使训练更稳定，但需要更多显存。小的batch size训练更快但可能不太稳定。

对于LoRA微调，推荐的batch size设置：
- per_device_train_batch_size: 4-8
- gradient_accumulation_steps: 4-8
- 等效batch size: 16-64

某互联网公司服务零售团队在QwQ-32B的微调中，发现"3轮-32步长"的效果最好。这里的"32步长"可能指的是梯度累积步数或等效batch size。

### 13.5 超参数搜索策略

对于重要的微调任务，建议进行系统的超参数搜索：

策略一：网格搜索。选择几个关键超参数（如学习率和训练轮数），为每个超参数设定几个候选值，然后尝试所有组合。适合计算资源充足的场景。

策略二：随机搜索。在超参数空间中随机采样，通常比网格搜索更高效。

策略三：贝叶斯优化。使用贝叶斯优化算法（如Optuna）智能地搜索超参数空间，适合昂贵的训练任务。

策略四：基于经验的初始值 + 微调。从推荐值开始，根据训练情况逐步调整。这是最实用的策略。

### 13.6 一个完整的超参数配置示例

以下是一个使用LoRA微调7B模型的推荐配置：

```yaml

# 训练配置
```

## 第十四章 灾难性遗忘与多任务微调

### 14.1 什么是灾难性遗忘

灾难性遗忘（Catastrophic Forgetting）是微调中最常见的问题之一。它指的是模型在学习新任务时，会丢掉之前学到的技能。具体表现为：经过特定领域微调后，虽然目标领域性能提升，但原始预训练阶段获得的通用知识易发生遗忘。

举个例子：你用一个通用大模型在医疗数据上微调，模型在医疗问答上的表现提升了，但你发现它现在不会写代码了，也不会做数学题了，甚至连基本的闲聊都不太行了。这就是灾难性遗忘。

### 14.2 灾难性遗忘的原因

灾难性遗忘的根本原因在于神经网络的参数共享机制。模型的所有知识都存储在同一组参数中。当你用新数据训练模型时，新数据的梯度会调整参数以适应新任务，但这些调整可能会覆盖模型原来存储的旧知识。

全量微调最容易导致灾难性遗忘，因为它会更新所有参数。LoRA等PEFT方法可以在一定程度上缓解这个问题，因为原始参数保持不变。

### 14.3 缓解灾难性遗忘的方法

**方法一：使用PEFT方法**

LoRA等PEFT方法是缓解灾难性遗忘最简单有效的方法。因为原始参数冻结不变，模型不会"忘记"预训练阶段学到的知识。LoRA只是在原有知识的基础上增加新能力。

**方法二：混合训练数据**

在微调数据中加入一部分通用数据（如通用问答、代码、数学等），让模型在学习新领域知识的同时，也"复习"旧知识。这被称为"经验回放"（Experience Replay）。

典型的数据配比可能是：70%领域数据 + 30%通用数据。具体比例需要通过实验确定。

**方法三：降低学习率**

使用较小的学习率可以减少参数的变化幅度，从而减轻对原有知识的破坏。但学习率太小又可能导致模型学不好新任务，需要找到平衡点。

**方法四：减少训练轮数**

训练轮数越多，模型对新数据的拟合越深，对旧知识的破坏也越大。适当减少训练轮数可以缓解遗忘。

**方法五：弹性权重整合（EWC）**

EWC（Elastic Weight Consolidation）是一种更高级的方法。它计算每个参数对旧任务的重要性，在训练新任务时对重要参数施加约束，限制其变化幅度。这种方法效果较好但实现复杂。

**方法六：多任务微调**

同时训练多个任务的数据，让模型同时学习多种能力，避免过度偏向某一个任务。

### 14.4 多任务微调

多任务微调是指同时在多个任务的数据上训练模型，让模型同时具备多种能力。

多任务微调的数据组织方式：

```json
// 任务1：客服问答
{"task": "customer_service", "instruction": "退款多久到账", "output": "退款一般在1-3个工作日..."}

// 任务2：商品推荐
{"task": "recommendation", "instruction": "推荐一家附近的火锅店", "output": "根据您的位置..."}

// 任务3：评价总结
{"task": "summarization", "instruction": "总结以下评价的要点", "input": "...", "output": "..."}
```

多任务微调的关键是数据配比。如果某个任务的数据量远大于其他任务，模型会偏向那个任务。通常需要通过采样或加权来平衡各任务的数据量。

多任务微调与LoRA的结合：可以为不同任务训练不同的LoRA适配器，在推理时根据任务类型加载对应的LoRA。这样每个任务的能力独立存储，不会互相干扰。

### 14.5 检测灾难性遗忘

如何判断模型是否发生了灾难性遗忘？可以通过以下方式：

1. 保留一部分通用能力的测试数据（如MMLU、C-Eval等通用基准）
2. 在微调前后用同样的测试数据评估模型
3. 如果微调后通用基准的分数显著下降，说明发生了灾难性遗忘

某代码补全团队的实践经验：微调后模型相较基座某能力项出现灾难性遗忘，多和微调阶段对部分训练数据过拟合有关，另外也和整体训练过程中出现大幅度分布变化相关。适当提高微调任务多样性可以缓解这个问题。

## 第十五章 微调模型评测体系

### 15.1 为什么要评测

评测是微调过程中不可或缺的环节。没有评测，你不知道微调是否有效，不知道效果提升了多少，不知道是否引入了新的问题。

评测的核心目的是回答两个问题：第一，模型好不好？第二，到底哪里好，哪里不好？前者用于判断是否可以上线，后者用于指导下一轮迭代。

### 15.2 评测的层次

大模型微调的评测可以分为以下几个层次：

**层一：通用能力评测**

使用标准化的基准测试来评估模型的通用能力是否受损。常用的基准包括：
- MMLU：多任务语言理解，覆盖57个学科
- C-Eval：中文多任务评测
- GSM8K：小学数学推理
- HumanEval：代码生成
- MT-Bench：多轮对话能力

在微调前后运行这些基准，可以判断模型是否发生了灾难性遗忘。

**层二：领域特定评测**

评估模型在目标领域的表现。这通常需要构建领域特定的测试集，包含该领域的典型问题和标准答案。

**层三：业务场景评测**

在真实业务场景中测试模型的表现。这可能包括：
- A/B测试：将微调模型与原模型在真实流量上对比
- 人工评估：让评估员对模型的输出进行评分
- 业务指标：如用户满意度、问题解决率、转化率等

**层四：安全评测**

评估模型是否可能产生有害输出，包括：
- 价值观对齐测试
- 有害内容检测
- 隐私信息泄露检测
- 越狱攻击测试

### 15.3 评测方法

**自动评测**

使用程序化的方法评估模型输出，适用于有明确标准答案的任务：

```python
def evaluate_model(model, test_data):
    correct = 0
    total = len(test_data)
    for item in test_data:
        response = model.generate(item["question"])
        if check_answer(response, item["answer"]):
            correct += 1
    return correct / total
```

自动评测的优点是快速、客观、可重复。缺点是无法评估开放式任务（如创意写作）。

**人工评测**

让人类评估员对模型的输出进行评分。通常使用"好/中/差"或1-5分的评分标准。

人工评测的优点是可以评估任何类型的任务，结果更接近真实用户体验。缺点是成本高、速度慢、有主观性。

**LLM辅助评测**

使用更强大的模型（如GPT-4）来评估微调模型的输出质量。这种方法介于自动评测和人工评测之间，既有一定的效率，又能评估开放式任务。

```python
def llm_evaluate(question, response, reference):
    prompt = f"""
    问题：{question}
    模型回答：{response}
    参考答案：{reference}
    
    请给模型回答打分（1-5分），并说明理由。
    """
    score = gpt4.generate(prompt)
    return score
```

### 15.4 评测的注意事项

注意事项一：评测数据不能与训练数据重叠。如果评测数据出现在训练数据中，评测结果会虚高。

注意事项二：评测需要覆盖多种场景。不能只测试简单的场景，还要测试边界情况和困难case。

注意事项三：需要对比基线。评测微调效果时，应该与微调前的基座模型进行对比，看效果提升了多少。

注意事项四：关注负面效果。不仅要看微调后模型在目标任务上的提升，还要看通用能力是否下降。

注意事项五：评测要可重复。记录评测数据、评测方法、随机种子等信息，确保评测结果可以复现。

### 15.5 企业级评测实践

某互联网公司服务零售团队在QwQ-32B微调中进行了系统化的评测：

SFT阶段评测结果：
- 标注结果准确率：86.80%（baseline：63.60%）
- 标注原因准确率：80.00%（baseline：50.25%）
- 人工标注结果为"好"和"差"占比97.03%时，标注结果准确率达93.94%

DPO阶段评测结果：
- 标注结果准确率：92.57%（baseline：86.80%）
- 标注原因准确率：86.68%（baseline：80.00%）

这种系统化的评测——有baseline对比、有分阶段评测、有不同维度的指标——是值得学习的评测实践。

## 第十六章 模型量化与推理部署

### 16.1 为什么需要量化

微调完成后，模型需要部署到线上提供服务。但大模型的推理成本很高——一个7B模型在FP16精度下需要约14GB显存，一个13B模型需要约26GB。这意味着需要昂贵的GPU来部署。

量化（Quantization）是降低推理成本的重要手段。它通过降低模型参数的精度（从FP16降到INT8或INT4），减少模型大小和推理延迟。

量化的收益包括：
1. 内存占用：量化可以显著降低模型的大小，使得模型可以在更多的设备上部署
2. 推理延迟：量化能够大幅度降低访存延迟，加速推理计算过程
3. 计算开销：量化通过使用低比特数据计算，降低模型计算开销

### 16.2 常用量化方法

**GPTQ（GPT-Quantization）**

GPTQ是一种训练后量化方法，通过逐层量化来最小化量化误差。它的精度损失较小，适用于大多数场景。

GPTQ的特点：
- 训练后量化，不需要重新训练
- 支持INT4和INT8量化
- 精度损失小
- 需要校准数据集

**AWQ（Activation-aware Weight Quantization）**

AWQ是一种激活感知的量化方法，它根据激活值的大小来确定权重的量化精度。对激活值大的权重保持更高精度，对激活值小的权重降低精度。

AWQ的特点：
- 训练后量化
- 量化速度快
- 精度损失较小
- 适合大模型

**GGUF（GPT-Generated Unified Format）**

GGUF是llama.cpp使用的模型格式，特别适合CPU推理。它支持多种量化级别（Q4_0, Q4_1, Q5_0, Q5_1, Q8_0等），适合在消费级硬件上运行模型。

**FP8**

FP8是8位浮点格式，相比INT8有更好的数值范围和精度。新一代GPU（如H100）原生支持FP8计算，可以带来显著的推理加速。

**量化方法对比：**

| 方法 | 精度 | 速度 | 精度损失 | 适用场景 |
|------|------|------|---------|---------|
| GPTQ-INT4 | 4位 | 快 | 较小 | GPU推理 |
| AWQ-INT4 | 4位 | 快 | 较小 | GPU推理 |
| GGUF-Q4 | 4位 | 中等 | 中等 | CPU推理 |
| INT8 | 8位 | 中等 | 很小 | 通用 |
| FP8 | 8位浮点 | 最快 | 极小 | 新一代GPU |

### 16.3 推理框架

**vLLM**

vLLM是目前最流行的开源大模型推理框架，具有以下特点：
- PagedAttention技术，高效管理KV Cache
- 支持连续批处理（continuous batching）
- 高吞吐量
- 支持多种量化方法

**TensorRT-LLM**

NVIDIA的推理框架，针对NVIDIA GPU深度优化：
- 极高的推理速度
- 支持多种精度和量化方法
- 部署较复杂

**llama.cpp**

C++实现的推理引擎，特别适合CPU推理：
- 支持GGUF格式
- 可以在普通电脑上运行
- 适合边缘部署

**企业内部的推理部署**

某互联网公司到家搜索团队在13B模型的量化实践中，基于vLLM搭建推理环境，对比了Llama模型量化前后的推理速度、单GPU吞吐变化和模型性能。量化使得模型可以在更少的GPU上部署，大幅降低了推理成本。

### 16.4 微调模型的部署流程

一个完整的微调模型部署流程如下：

```
1. 微调训练
   └─ 基座模型 + 训练数据 → 微调模型

2. 模型处理
   ├─ 如果是LoRA：合并权重（W_merged = W + α/r × BA）
   ├─ 如果需要量化：GPTQ/AWQ量化
   └─ 格式转换（如转换为推理框架支持的格式）

3. 推理部署
   ├─ 使用vLLM等框架启动推理服务
   ├─ 配置推理参数（max_tokens, temperature等）
   └─ 部署到GPU服务器

4. 效果监控
   ├─ 监控推理延迟、吞吐量
   ├─ 监控输出质量
   └─ 收集bad case用于下一轮迭代
```

### 16.5 垂域模型量化实践

某互联网公司履约团队在构建垂域模型时，进行了模型量化实践。他们的经验是：

量化方法之间的性能大致符合以下排序：GPTQ-W4A16-部分量化 > GPTQ-W4A16 > AWQ-W4A16 > 其他。其中W4A16表示权重4位量化、激活16位精度。

部署建议：
- 7B模型FP16部署至少需要1张A100 40GB
- 7B模型INT4量化后可以用更小的GPU部署
- 13B模型W4量化后至少需要1张A100

## 第十七章 RAG vs 微调：如何选择

### 17.1 两种主流的大模型应用方案

在大模型应用中，RAG（检索增强生成）和微调是两种最主流的技术方案。它们各有优劣，适用于不同的场景。

RAG的原理是在推理时，先从外部知识库中检索与用户问题相关的信息，然后将检索到的信息和用户问题一起输入给大模型，让模型基于检索到的信息生成回答。

微调的原理是在训练时，用特定领域的数据调整模型参数，让模型"记住"领域知识，在推理时不需要外部检索。

### 17.2 RAG与微调的对比

| 特性 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 直接更新检索知识库，确保信息持续更新，无需重新训练 | 需要准备和整理高质量训练数据集，重新训练 |
| 数据安全 | 数据存储在本地知识库中 | 数据用于训练，模型部署在本地 |
| 实时性 | 可以实时更新知识 | 需要重新训练才能更新知识 |
| 适应性 | 通过更换知识库适应不同领域 | 需要重新微调适应不同领域 |
| 成本 | 开发成本低，维护知识库即可 | 需要训练资源、标注成本 |
| 效果上限 | 受限于检索质量和模型理解能力 | 可以深度学习领域知识 |
| 推理延迟 | 需要额外的检索步骤，延迟较高 | 直接推理，延迟较低 |
| 数据处理要求 | 对数据加工和处理的要求低 | 依赖高质量训练数据集 |
| 幻觉问题 | 可以通过检索结果约束模型输出，减少幻觉 | 微调后可能仍有幻觉 |
| 长尾知识 | 只要知识库中有就能回答 | 如果训练数据中没有可能不知道 |

### 17.3 何时选择RAG

RAG更适合以下场景：
- 知识需要频繁更新（如产品信息、政策法规等）
- 知识量很大但不需要"理解"，只需要"查找"
- 需要引用来源（让用户知道答案来自哪里）
- 开发资源有限，希望快速上线
- 需要处理多个不同领域的知识

### 17.4 何时选择微调

微调更适合以下场景：
- 需要改变模型的行为模式（如输出格式、回答风格）
- 需要增强模型的推理能力（如数学推理、代码生成）
- 领域知识需要深度理解而非简单查找
- 对推理延迟敏感（RAG的检索步骤会增加延迟）
- 数据安全要求高，不能将数据放入知识库（可能被检索到）
- 需要模型学会特定领域的术语和表达方式

### 17.5 RAG + 微调：最佳实践

在实际业务中，RAG和微调并不矛盾，可以结合使用：

```
用户提问
  ↓
[微调后的模型] ← 理解问题、改写query
  ↓
[RAG检索] ← 从知识库检索相关信息
  ↓
[微调后的模型] ← 基于检索结果生成回答
  ↓
最终回答
```

这种组合的优势在于：
- 微调让模型更好地理解领域问题和术语
- RAG提供最新的、准确的知识
- 两者互补，效果优于单独使用

某互联网公司到综业务的实践就采用了这种模式：先用微调让模型具备领域理解能力，再用RAG提供具体的商家和商品信息。

### 17.6 决策流程图

```
                    ┌─ 需要模型学会新的行为模式？─→ 微调
                    │
                    ├─ 知识需要频繁更新？─→ RAG
                    │
你的需求是什么？ ────├─ 需要深度推理能力？─→ 微调
                    │
                    ├─ 需要引用知识来源？─→ RAG
                    │
                    ├─ 对延迟敏感？─→ 微调
                    │
                    └─ 两者都需要？─→ RAG + 微调
```

## 第十八章 多模态模型微调

### 18.1 多模态模型概述

多模态大模型是指能够处理来自多种模态（如图像、文本、视频、音频等）的数据，并能够在这些模态之间建立联系和推理的深度学习模型。

代表性的多模态模型包括：
- GPT-4V/4o：OpenAI的多模态模型，能处理文本、图像、音频
- Gemini：Google的多模态模型，原生支持多模态
- LLaVA：开源的视觉-语言模型
- Qwen-VL：阿里的视觉-语言模型
- 某自研视觉-语言模型：部分企业自研的多模态模型

### 18.2 多模态模型的架构

典型的多模态模型由以下几部分组成：

```
┌─────────────────────────────────────┐
│         多模态大模型架构              │
│                                       │
│  ┌──────────┐   ┌──────────┐         │
│  │ 视觉编码器│   │ 文本编码器│         │
│  │ (CLIP等) │   │ (Tokenizer│        │
│  │          │   │  +Embed) │         │
│  └────┬─────┘   └────┬─────┘         │
│       │               │               │
│       └───────┬───────┘               │
│               │                       │
│        ┌──────┴──────┐               │
│        │  模态对齐/  │               │
│        │  投影层     │               │
│        └──────┬──────┘               │
│               │                       │
│        ┌──────┴──────┐               │
│        │   大语言模型 │               │
│        │  (LLM基座)  │               │
│        └──────┬──────┘               │
│               │                       │
│          文本输出                     │
└─────────────────────────────────────┘
```

视觉编码器负责将图像转换为特征向量，模态对齐层将视觉特征映射到语言模型能理解的空间，大语言模型负责综合多模态信息并生成回答。

### 18.3 多模态模型的微调

多模态模型的微调与纯文本模型类似，但数据格式和微调策略有所不同：

**数据格式**

多模态微调数据包含图像和文本：

```json
{
  "image": "path/to/image.jpg",
  "conversations": [
    {"role": "user", "content": "<image>\n这张图片中有什么？"},
    {"role": "assistant", "content": "图片中有一只猫坐在窗台上..."}
  ]
}
```

其中`<image>`是图像占位符，模型会将图像编码后插入到这个位置。

**微调策略**

多模态模型的微调可以选择性更新不同组件：
1. 只微调投影层（参数最少，适合简单任务）
2. 微调投影层 + LLM的LoRA（参数适中，效果较好）
3. 微调视觉编码器 + 投影层 + LLM的LoRA（参数最多，效果最好）
4. 全量微调所有组件（效果最好但成本最高）

### 18.4 企业多模态模型实践

一些互联网企业在多模态模型方面有丰富的实践：

**自研多模态模型系列**

部分企业自研的多模态模型系列包括Mini、Medium、Lite等版本，是较轻便敏捷的图像理解模型，有良好的图文理解能力，适用于较高精度和较高吞吐的业务场景。

**电商图像理解**

某互联网公司电商治理团队在电商图像理解领域进行了大模型实践。他们发现通用大模型在专业领域表现欠佳、闭源模型成本过高、外部模型存在信息泄密问题，因此构建了领域大模型来处理图像理解任务。

**多模态POI识别**

一些企业使用多模态大模型识别POI（兴趣点）的堂食/自提/纯外卖属性，通过分析商户的图片信息来辅助判断。

### 18.5 多模态微调的挑战

多模态微调相比纯文本微调面临更多挑战：

数据收集困难：多模态数据需要同时收集图像和文本，且需要保证图文匹配。标注成本更高。

计算资源需求大：图像编码器本身就有大量参数，加上LLM基座，总参数量更大。训练时需要处理图像数据，计算开销也更大。

模态对齐问题：视觉和文本是两种不同的信息表示方式，如何让模型正确理解两种模态之间的关系是一个挑战。

评估更复杂：多模态模型的评估不仅需要考虑文本质量，还需要考虑视觉理解准确性，评估方法更加复杂。

## 第十九章 企业级微调最佳实践与沉淀

### 19.1 企业级微调的完整流程

在企业环境中，微调不是一个孤立的训练任务，而是一个完整的工程流程。一个成熟的企业级微调流程包括以下环节：

```
需求分析 → 数据准备 → 模型选型 → 微调训练 → 评测验证 → 部署上线 → 监控反馈 → 迭代优化
   ↑                                                                    │
   └────────────────────────────────────────────────────────────────────┘
                              持续迭代
```

### 19.2 需求分析

在开始微调之前，需要明确以下问题：

业务目标是什么？是要提升准确率、降低成本、提高效率还是改善用户体验？不同的目标决定了不同的微调策略。

现有基座模型的效果如何？如果基座模型已经能解决80%的问题，微调可能只需要优化剩下的20%。如果基座模型只能解决30%的问题，可能需要更大的调整。

有多少训练数据？数据质量如何？数据决定了微调的上限。

计算资源有多少？能投入多少GPU？这决定了可以选择的模型大小和微调方法。

上线时间要求？需要多快产出结果？如果时间紧迫，可以选择更简单但效果稍差的方案。

### 19.3 数据准备的最佳实践

**建立数据飞轮**

数据飞轮是一个持续改进的数据循环：
1. 收集业务数据（用户交互日志、人工标注等）
2. 清洗和质量筛选
3. 用于微调训练
4. 模型上线后收集新的业务数据
5. 人工审核模型输出，标注好/差案例
6. 将好案例加入训练数据，差案例用于偏好数据
7. 重复以上过程

这种持续迭代的数据飞轮是提升模型效果的关键。某互联网公司服务零售团队在QwQ-32B微调后就提到，后续可通过数据飞轮和DPO进一步提升效果。

**数据版本管理**

每次微调使用的数据应该有明确的版本管理：
- 记录数据来源、清洗方法、数据量
- 保存数据集的hash值，确保可追溯
- 记录每次微调使用的数据版本，便于对比和回溯

**数据安全与合规**

企业级微调必须考虑数据安全：
- 训练数据中的PII（个人身份信息）必须脱敏
- 不能将敏感数据用于第三方模型的训练
- 需要评估训练数据是否可能被模型"记住"并在推理时泄露

### 19.4 模型选型最佳实践

选择基座模型时需要考虑以下因素：

**开源 vs 闭源**

开源模型（如Qwen、LLaMA、DeepSeek）可以本地部署、数据不出企业、可以自由微调。闭源模型（如GPT-4、Claude）效果可能更好但无法微调（或微调成本极高）、数据需要发送给第三方。

对于需要微调的企业场景，通常选择开源模型。企业自研的模型系列、开源的Qwen系列、DeepSeek系列都是常用选择。

**模型大小**

模型大小需要根据任务需求和资源约束选择：
- 7B模型：适合大多数任务，推理成本低，单卡可部署
- 13B-33B模型：效果更好，但推理成本更高
- 70B+模型：效果最好，但需要多卡部署，成本高

实践建议：从7B模型开始，如果效果不够再尝试更大的模型。模型大小带来的效果提升通常不如数据质量带来的提升明显。

**已有能力**

选择基座模型时，要考虑它已经具备的能力。如果你的任务是中文问答，选择一个在中文上表现好的模型（如Qwen）比选择一个主要在英文上训练的模型（如LLaMA原始版本）更合适。

### 19.5 微调训练的最佳实践

**从简单开始**

不要一开始就使用最复杂的方案。推荐的渐进策略：

```
第一步：Prompt Engineering（提示词工程）
  → 如果效果够好，到此为止

第二步：SFT + LoRA
  → 最主流的微调方案，90%的场景够用

第三步：SFT + LoRA + DPO
  → 如果SFT后还有改进空间

第四步：SFT + 全量微调
  → 如果LoRA效果不够且资源充足

第五步：SFT + 全量微调 + DPO
  → 追求极致效果
```

**控制变量实验**

在迭代过程中，每次只改变一个变量，这样才能知道是什么改变导致了效果变化。例如，不要同时改变学习率和数据量，否则不知道效果变化是哪个因素导致的。

**记录实验日志**

每次微调实验都应该记录：
- 基座模型版本
- 训练数据版本和量
- 微调方法（LoRA/FFT等）
- 超参数配置
- 评测结果
- 训练loss曲线

这些记录对于后续的复盘和迭代至关重要。

**早停（Early Stopping）**

在训练过程中定期评估验证集效果，如果验证集效果不再提升甚至下降，应该停止训练。这可以防止过拟合。

### 19.6 部署上线的最佳实践

**灰度发布**

不要一次性将微调模型全量替换原有模型。应该先在小比例流量上灰度测试，观察效果和用户反馈，逐步扩大流量比例。

**A/B测试**

将微调模型与原模型在相同流量上并行运行，对比业务指标（如准确率、用户满意度、解决率等），用数据驱动决策。

**兜底策略**

在线上服务中，应该准备兜底策略：
- 如果微调模型出现异常，自动切换到基座模型
- 如果推理超时，返回缓存的回答或预设回答
- 监控模型输出质量，发现异常及时告警

**版本管理**

线上模型应该有完善的版本管理：
- 每个版本有唯一的标识
- 可以快速回滚到任意历史版本
- 记录每个版本的训练数据和配置

### 19.7 监控与反馈

**推理质量监控**

上线后持续监控模型的推理质量：
- 输出长度分布是否正常
- 输出内容是否包含有害信息
- 用户反馈（点赞/踩）
- 推理延迟和吞吐量

**Bad Case收集**

系统化收集bad case（模型回答不好的案例），用于后续迭代：
- 自动收集用户反馈为"不满意"的案例
- 定期人工抽检模型输出
- 将bad case分类整理，找出共性问题

**数据飞轮**

将收集到的bad case转化为训练数据，用于下一轮微调迭代。这就是"数据飞轮"——模型越用越好，数据越来越多。

### 19.8 LLMOps：大模型运维

企业级LLMOps理念继承了MLOps整体框架和机器学习全生命周期等主要环节，并针对大模型的变化进行了适配：

在数据加工环节，大模型在无监督数据和未标注数据的使用上大幅上升，LLMOps需要对这部分数据的加工进行强化。

在训练调优环节，LLMOps几乎不需要修改大模型代码，通常通过PEFT、SFT等方式来强化和调整模型，同时也需要注重并行分布式训练能效的提升。

在评估环节，由于大模型生成的海量内容暂无标准的答案，LLMOps需要建立与以往不同的评估基准和评估方法。

在推理环节，LLMOps需要从工具链的角度思考哪些可以更加自动化，如何提供模板、插件等新引入的能力。

## 第二十章 企业级微调实践案例

### 20.1 案例一：QwQ-32B在服务零售业务中的SFT微调

**背景**

服务零售搜索bad case无法得到高效的系统性解决，根因在于识别bad case成本高。约20人在进行到综搜索相关体验标注，每个标注专家每天最多标200条Case，标注规则复杂，新人难以快速上手。

**方案**

团队选择QwQ-32B推理模型作为基座，通过SFT微调将其推理能力迁移至服务零售的标注场景。

**数据准备**

基于标注规则更新后2025年1月6日到3月20日的服务零售场景原始标注数据共4158条。采用"规则+LLM判断"两阶段数据筛选方法：

第一阶段（规则过滤）：过滤掉意图理解数据缺失以及人工标注原因为"不清楚怎么分类"的数据，剩余1682条。

第二阶段（LLM判断）：利用DeepSeek-r1生成思维链，通过ChatGPT-4o-mini来判断思维链与已有标注结果的逻辑一致性，获得高质量CoT数据集1400条用于SFT微调。

**训练结果**

3轮-32步长的效果最好：
- 标注结果准确率：86.80%（baseline：63.60%），提升23.2个百分点
- 标注原因准确率：80.00%（baseline：50.25%），提升29.75个百分点
- 人工标注结果为"好"和"差"占比97.03%时，标注结果准确率为93.94%，标注原因准确率为86.58%

**业务价值**

- 单卡标注速度相比单个专家提升5倍
- 单条case标注成本下降97%

### 20.2 案例二：QwQ-32B的DPO偏好对齐

**背景**

SFT模型在处理某些人类偏好的问题上存在局限性。例如在主区相关性判断中，SFT微调后的模型可能根据poi名称、类目和下挂信息发散思考，但专家标注更倾向于直接命中原则。这种差异导致SFT模型在某些特定case上的判断与专家不一致。

**方案**

针对模型较难解决的bad case类型，采用DPO直接偏好优化的方式对SFT参考模型进行继续训练。

**训练结果**

- 标注结果准确率：92.57%（baseline：86.80%），提升5.77个百分点
- 标注原因准确率：86.68%（baseline：80.00%），提升6.68个百分点

**经验总结**

SFT + DPO的两阶段微调策略效果优于单独使用SFT。SFT负责基础能力建设，DPO负责精细的偏好对齐。

### 20.3 案例三：履约垂域模型

**背景**

履约垂域包含骑手运营、管控等丰富业务场景，模型对运营规则、管控流程、疑难处理方案等垂域知识的掌握和理解是保证应用效果的基础。通用开源大模型在这些特定领域的效果不理想。

**方案**

构建适用于履约场景的垂域模型，通过对开源LLM进行垂类知识注入（继续预训练）和特定指令强化。

**模型轻量化**

为了解决推理瓶颈，采用了模型压缩技术：
- 模型量化：GPTQ-W4A16-部分量化效果最好
- 部署建议：7B模型FP16部署至少1张A100

### 20.4 案例四：代码补全模型

**背景**

某互联网公司的代码补全工具，Java代码补全代码采纳率已超过30%。这背后离不开自研模型的助力。

**微调经验**

团队在微调实践中积累了以下经验：

关于过拟合和灾难性遗忘：微调模型对训练任务出现过拟合一般是由于微调数据类型单一影响，适当提高微调任务多样性可以缓解。微调后模型相较基座某能力项出现灾难性遗忘也多和微调阶段对部分训练数据过拟合有关。

关于温度值：不同的场景、不同的模型超参会有不一样的表现。代码补全场景希望稳定输出，温度值会设置得低一些（0或偏0）；文创场景对发散容忍度更高，超参可以设得再高一点。

### 20.5 案例五：大模型推理量化在到家场景的落地

**背景**

某互联网公司外卖搜索使用13B大模型进行生成式搜索，但推理速度和成本成为限制业务迭代和发展的主要瓶颈。13B模型对推理设备的显存容量提出了较高要求。

**方案**

对Llama模型进行量化加速，对比了量化前后的推理速度、单GPU吞吐变化和模型性能。

**技术挑战**

1. 误差累计：量化过程中的舍入和钳位操作会引入量化误差，多层累积后可能导致显著的效果下降
2. 任务适配：不同业务场景对量化精度的敏感度不同
3. 性能平衡：需要在精度损失和推理加速之间找到平衡点

**收益**

量化使得模型可以在更少的GPU上部署，大幅降低了推理成本，同时保持了可接受的效果。

### 20.6 案例六：金融LLM在智能权益的实践

**背景**

微贷业务中，权益营销是促动用户借款转化的核心手段。传统营销模型在稀疏客群上反事实推断失效，长周期价值预测面临稀疏奖励困境。

**方案**

采用大模型替代传统营销模型，使用SFT和偏好对齐强化学习（ORPO、DPO等）来优化模型。

**偏好对齐方法对比**

团队对比了DPO和ORPO等方法：
- DPO：基于参考模型，将RLHF目标等价转化为偏好概率对比优化
- ORPO：移除参考模型，将偏好优化融入SFT过程

**经验**

偏好驱动型对齐方法是当前大模型对齐的主流范式之一，其核心思路是直接利用人类偏好数据对（chosen/rejected）进行模型优化，不再显式训练奖励模型。

## 第二十一章 微调常见问题与陷阱

### 21.1 训练相关问题

**问题一：训练loss不下降**

可能原因：
- 学习率太小 → 尝试增大学习率
- 学习率太大导致梯度爆炸 → 尝试减小学习率
- 数据格式错误 → 检查数据是否正确加载和格式化
- 模型加载错误 → 确认模型和tokenizer是否匹配
- 梯度为零 → 检查是否正确设置了requires_grad

**问题二：训练loss下降但效果不好**

可能原因：
- 过拟合 → 减少训练轮数，增加正则化
- 数据质量问题 → 检查训练数据是否有错误
- 评测数据与训练数据分布不一致 → 确保评测数据有代表性
- 超参数不合适 → 尝试不同的学习率和LoRA秩

**问题三：训练过程中OOM（显存不足）**

解决方案：
- 减小batch_size
- 增加gradient_accumulation_steps
- 启用梯度检查点（gradient checkpointing）
- 使用QLoRA代替LoRA
- 使用DeepSpeed ZeRO优化
- 减小最大序列长度

**问题四：训练速度太慢**

优化方法：
- 使用flash attention加速注意力计算
- 使用混合精度训练（FP16/BF16）
- 增大batch_size（如果显存允许）
- 减小序列长度（如果不需要长序列）
- 使用更快的GPU

### 21.2 效果相关问题

**问题一：微调后模型出现"复读机"现象**

表现：模型反复重复相同的内容。

原因：通常是训练数据中有重复模式，或训练轮数过多导致过拟合。

解决：清洗训练数据中的重复模式，减少训练轮数，增加数据多样性。

**问题二：微调后模型通用能力下降（灾难性遗忘）**

表现：模型在目标任务上表现提升，但在通用任务（如闲聊、常识问答）上表现下降。

解决：参考第十四章的方法，使用PEFT方法、混合通用数据、降低学习率等。

**问题三：模型输出格式不稳定**

表现：有时按正确格式输出，有时不按格式输出。

原因：训练数据中格式不一致，或训练不够充分。

解决：确保训练数据格式完全统一，增加格式相关的训练数据，适当增加训练轮数。

**问题四：模型"胡说八道"（幻觉）**

表现：模型生成看似合理但实际上不正确的内容。

原因：微调不能完全消除幻觉，因为幻觉的根源在于模型的概率生成机制。

解决：使用RAG提供准确知识，在训练数据中包含"不知道就说不知道"的样本，降低temperature。

### 21.3 部署相关问题

**问题一：微调模型推理速度比原模型慢**

原因：如果是LoRA适配器模式（未合并），推理时需要额外计算LoRA层。

解决：将LoRA权重合并到基座模型中（merge_and_unload），合并后推理速度与原模型相同。

**问题二：量化后效果下降明显**

原因：某些模型对量化比较敏感，特别是较小的模型。

解决：尝试不同的量化方法（GPTQ vs AWQ），使用更高的量化精度（INT8代替INT4），或在量化后进行少量微调。

**问题三：不同推理框架结果不一致**

原因：不同推理框架的实现细节不同（如采样策略、padding方式等），可能导致结果差异。

解决：固定随机种子，使用相同的推理参数，选择一个推理框架作为标准。

### 21.4 数据相关问题

**问题一：训练数据太少**

建议：
- 使用数据增强技术扩充数据
- 使用合成数据（GPT-4生成）
- 使用LoRA（对数据量要求更低）
- 从简单任务开始，逐步增加复杂度

**问题二：训练数据质量参差不齐**

建议：
- 建立数据质量评估标准
- 使用模型辅助筛选（GPT-4打分）
- 人工抽检和修正
- 分批次迭代，先使用高质量子集训练

**问题三：数据标注成本高**

建议：
- 利用业务日志中的高质量交互数据
- 使用主动学习（Active Learning）策略，优先标注最有价值的样本
- 使用弱监督方法降低标注成本
- 使用合成数据补充

## 第二十二章 前沿趋势与未来展望

### 22.1 SFT与RL的融合

当前主流的"先SFT后RL"范式正在被挑战。越来越多的研究发现SFT和RL存在可以调和的共性，业界正在探索"大一统"（unified）的后训练框架。

SFT倾向于记忆，而RL倾向于泛化。SFT作为一种模仿学习，其核心是让模型复现高质量的专家示范，但存在灾难性遗忘、过拟合和泛化能力不足的问题。RL的优势在于其探索能力，允许模型生成训练数据中从未出现过的回答，并通过奖励信号判断优劣。

Thinking Machines Lab（前OpenAI CTO Mira Murati的新公司）的研究科学家Luke Metz分享的经验值得参考：以"少少SFT+大量RL"的配比相结合往往能带来更好的效果。即"Do a bit of SFT to get a good initial policy, RL a bunch to maximize performance"。

### 22.2 可验证奖励的扩展

LLM强化学习的核心张力不是算法之争（PPO vs GRPO），而是"可验证奖励的覆盖范围"直接塑造了模型能力的边界。

在可验证领域（如数学、代码），GRPO的简化设计足以实现高效的能力跃升。但在不可验证领域（如开放式对话、伦理判断），PPO的稳定性机制是防止reward hacking的必要条件。

当前LLM训练的关键问题不是"选择哪种RL算法"，而是"如何扩展可验证奖励的边界"和"如何在不可验证领域建立有效的稳定性约束"。

### 22.3 合成数据的重要性日益增长

随着强大模型（如GPT-4、Claude）的普及，使用合成数据进行微调训练越来越重要。合成数据可以解决训练数据不足的问题，但也带来了新的挑战：

- 合成数据可能继承生成模型的偏见
- 过度使用合成数据可能导致模型"近亲繁殖"，效果退化
- 需要有效的质量控制机制来筛选合成数据

### 22.4 推理能力的提升

DeepSeek-R1通过纯强化学习训练（无需SFT）成功复现了o1的推理能力，展示了RL在提升模型推理能力方面的巨大潜力。这开创了一条新的技术路线：不依赖大量人类标注数据，通过精心设计的奖励机制来训练模型自己学会推理。

Rule-based Reward（基于规则的奖励）在其中发挥了关键作用。DeepSeek-R1和Kimi 1.5都使用了简洁的RL框架，都没有采用复杂的树搜索（MCTS），都没有采用昂贵的PRM（过程奖励模型），且都精心设计了基于事实的奖励机制来进行判别。

### 22.5 模型即服务的演进

随着微调技术的普及和工具的成熟，模型即服务（MaaS）正在演进。未来的趋势包括：

- 更低门槛的微调工具：让非技术人员也能完成微调
- 自动化超参数优化：AI辅助选择最佳超参数
- 持续学习：模型在不遗忘旧知识的情况下持续学习新知识
- 个性化模型：为每个用户或场景定制专属模型
- 边缘部署：在手机、IoT设备上运行微调后的模型

### 22.6 企业的前沿探索

一些互联网企业在模型微调领域持续进行前沿探索：

自研模型迭代：企业自研的系列模型持续迭代，包括高效推理版本、服务零售优化版本、多模态理解版本等。

强化学习训练平台：企业级模型训练平台支持GRPO等强化学习训练任务，为内部团队提供模型训练基础设施。

AI迭代AI：探索基于Agent的多模态大模型自动优化部署，让AI自动化地参与自身的迭代过程来提升模型优化服务部署效率。

垂域模型建设：在履约、金融、电商治理等多个垂直领域建设专用模型，通过微调将通用大模型适配到特定业务场景。

### 22.7 给初学者的建议

对于刚开始学习模型微调的读者，以下是一些建议：

建议一：从实践开始。不要一开始就钻进论文和理论中。选择一个开源模型（如Qwen2-7B），用一个简单的数据集，跑通一次LoRA微调。有了实践经验后再回头理解理论。

建议二：重视数据。微调的效果70%取决于数据质量。花时间在数据收集、清洗和质量控制上，比花时间调超参数更有价值。

建议三：从简单开始。先尝试Prompt Engineering，如果效果不够再考虑微调。微调先试LoRA，如果效果不够再试全量微调。

建议四：建立评测体系。在微调之前先准备好评测数据和方法。没有评测，你不知道微调是否有效。

建议五：学会看loss曲线。训练loss曲线能告诉你很多信息：loss是否在下降、是否收敛、是否过拟合。学会解读loss曲线是微调的基本功。

建议六：关注社区。大模型领域发展极快，关注HuggingFace、GitHub、arXiv等平台上的最新进展。

建议七：善用工具。LLaMA-Factory、PEFT、DeepSpeed等工具可以大大简化微调流程，不需要从零开始写代码。

建议八：理解原理但不必纠结于细节。你不需要完全理解LoRA的数学推导就能使用它。理解核心思想（低秩近似、冻结原始参数）就够了。

建议九：实验记录很重要。每次实验都记录配置和结果，建立自己的"微调经验库"。

建议十：耐心。微调是一个需要反复实验和迭代的过程，很少有第一次就完美的。保持耐心，持续优化。

```python
"""
大模型LoRA微调完整脚本模板
适用于Qwen2/LLaMA等主流开源模型
"""

import os
import json
import torch
from datasets import Dataset
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments,
    DataCollatorForSeq2Seq,
)
from peft import LoraConfig, get_peft_model, TaskType
from trl import SFTTrainer, SFTConfig

# ============ 配置区 ============
MODEL_PATH = "Qwen/Qwen2-7B-Instruct"  # 基座模型路径
TRAIN_DATA_PATH = "data/train.json"     # 训练数据路径
EVAL_DATA_PATH = "data/eval.json"       # 评估数据路径
OUTPUT_DIR = "./output_lora"            # 输出目录

# LoRA配置
LORA_R = 16                # LoRA秩
LORA_ALPHA = 32            # 缩放因子
LORA_DROPOUT = 0.05       # Dropout
TARGET_MODULES = [         # 应用LoRA的层
    "q_proj", "k_proj", "v_proj", "o_proj",
    "gate_proj", "up_proj", "down_proj"
]

# 训练配置
NUM_EPOCHS = 3
BATCH_SIZE = 4
GRAD_ACCUM_STEPS = 4
LEARNING_RATE = 2e-4
WARMUP_RATIO = 0.05
MAX_SEQ_LENGTH = 2048
FP16 = True

# ============ 数据准备 ============

def load_data(path):
    """加载JSON格式的训练数据"""
    with open(path, 'r', encoding='utf-8') as f:
        data = json.load(f)
    return Dataset.from_list(data)

def format_chat_template(example, tokenizer):
    """将数据格式化为模型的对话模板"""
    messages = [
        {"role": "user", "content": example["instruction"]},
        {"role": "assistant", "content": example["output"]}
    ]
    text = tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=False
    )
    return {"text": text}

# ============ 主流程 ============

def main():
    # 1. 加载Tokenizer
    tokenizer = AutoTokenizer.from_pretrained(
        MODEL_PATH,
        trust_remote_code=True,
        padding_side="right"
    )
    if tokenizer.pad_token is None:
        tokenizer.pad_token = tokenizer.eos_token

    # 2. 加载模型
    model = AutoModelForCausalLM.from_pretrained(
        MODEL_PATH,
        torch_dtype=torch.float16 if FP16 else torch.bfloat16,
        device_map="auto",
        trust_remote_code=True,
    )

    # 3. 配置LoRA
    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM,
        r=LORA_R,
        lora_alpha=LORA_ALPHA,
        lora_dropout=LORA_DROPOUT,
        target_modules=TARGET_MODULES,
        bias="none",
    )
    model = get_peft_model(model, lora_config)
    model.print_trainable_parameters()

    # 4. 加载和处理数据
    train_dataset = load_data(TRAIN_DATA_PATH)
    eval_dataset = load_data(EVAL_DATA_PATH)

    train_dataset = train_dataset.map(
        lambda x: format_chat_template(x, tokenizer),
        remove_columns=train_dataset.column_names
    )
    eval_dataset = eval_dataset.map(
        lambda x: format_chat_template(x, tokenizer),
        remove_columns=eval_dataset.column_names
    )

    # 5. 配置训练参数
    training_args = SFTConfig(
        output_dir=OUTPUT_DIR,
        num_train_epochs=NUM_EPOCHS,
        per_device_train_batch_size=BATCH_SIZE,
        per_device_eval_batch_size=BATCH_SIZE,
        gradient_accumulation_steps=GRAD_ACCUM_STEPS,
        learning_rate=LEARNING_RATE,
        warmup_ratio=WARMUP_RATIO,
        lr_scheduler_type="cosine",
        weight_decay=0.01,
        max_grad_norm=1.0,
        fp16=FP16,
        logging_steps=10,
        save_strategy="epoch",
        eval_strategy="epoch",
        save_total_limit=3,
        load_best_model_at_end=True,
        metric_for_best_model="eval_loss",
        greater_is_better=False,
        max_seq_length=MAX_SEQ_LENGTH,
        dataset_text_field="text",
        report_to="none",
    )

    # 6. 创建训练器
    trainer = SFTTrainer(
        model=model,
        args=training_args,
        train_dataset=train_dataset,
        eval_dataset=eval_dataset,
        tokenizer=tokenizer,
        data_collator=DataCollatorForSeq2Seq(
            tokenizer=tokenizer,
            padding=True,
            return_tensors="pt"
        ),
    )

    # 7. 开始训练
    print("=" * 50)
    print("开始训练...")
    print("=" * 50)
    train_result = trainer.train()

    # 8. 保存模型
    model.save_pretrained(os.path.join(OUTPUT_DIR, "final"))
    tokenizer.save_pretrained(os.path.join(OUTPUT_DIR, "final"))

    # 9. 打印训练统计
    print(f"\n训练完成！")
    print(f"总训练步数: {train_result.global_step}")
    print(f"训练Loss: {train_result.training_loss:.4f}")
    print(f"模型已保存到: {os.path.join(OUTPUT_DIR, 'final')}")

if __name__ == "__main__":
    main()
```

### D.4 模型合并与推理脚本

```python
"""
LoRA权重合并与推理脚本
"""

import torch
from peft import PeftModel
from transformers import AutoModelForCausalLM, AutoTokenizer

def merge_and_save(base_model_path, lora_path, output_path):
    """合并LoRA权重到基座模型"""

    # 1. 加载基座模型
    base_model = AutoModelForCausalLM.from_pretrained(
        base_model_path,
        torch_dtype=torch.float16,
        device_map="auto",
    )
    tokenizer = AutoTokenizer.from_pretrained(base_model_path)

    # 2. 加载LoRA
    model = PeftModel.from_pretrained(base_model, lora_path)

    # 3. 合并权重
    model = model.merge_and_unload()

    # 4. 保存合并后的模型
    model.save_pretrained(output_path)
    tokenizer.save_pretrained(output_path)
    print(f"合并后的模型已保存到: {output_path}")

def inference(model_path, question, max_new_tokens=512):
    """使用微调模型进行推理"""
    model = AutoModelForCausalLM.from_pretrained(
        model_path,
        torch_dtype=torch.float16,
        device_map="auto",
    )
    tokenizer = AutoTokenizer.from_pretrained(model_path)

    messages = [{"role": "user", "content": question}]
    text = tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=True
    )
    inputs = tokenizer(text, return_tensors="pt").to(model.device)

    with torch.no_grad():
        outputs = model.generate(
            **inputs,
            max_new_tokens=max_new_tokens,
            temperature=0.7,
            top_p=0.9,
            do_sample=True,
        )

    response = tokenizer.decode(
        outputs[0][inputs["input_ids"].shape[1]:],
        skip_special_tokens=True
    )
    return response

# 使用示例
if __name__ == "__main__":
    # 合并LoRA
    merge_and_save(
        base_model_path="Qwen/Qwen2-7B-Instruct",
        lora_path="./output_lora/final",
        output_path="./merged_model"
    )

    # 推理测试
    answer = inference("./merged_model", "某外卖平台的退款流程是什么？")
    print(f"模型回答: {answer}")
```

```python
"""
训练数据格式化工具
支持多种数据源转换为微调训练格式
"""

import json
import random

def format_alpaca_to_chat(instruction, input_text, output_text):
    """将Alpaca格式转换为Chat格式"""
    if input_text:
        prompt = f"{instruction}\n\n{input_text}"
    else:
        prompt = instruction
    return {
        "conversations": [
            {"role": "user", "content": prompt},
            {"role": "assistant", "content": output_text}
        ]
    }

def format_sharegpt_to_standard(conversations):
    """将ShareGPT格式转换为标准格式"""
    standard_convs = []
    for conv in conversations:
        if conv["from"] == "human":
            standard_convs.append({"role": "user", "content": conv["value"]})
        elif conv["from"] == "gpt":
            standard_convs.append({"role": "assistant", "content": conv["value"]})
    return {"conversations": standard_convs}

def create_cot_data(question, answer, reasoning):
    """创建思维链训练数据"""
    cot_output = f"{reasoning}\n\n最终答案：{answer}"
    return {
        "instruction": question,
        "output": cot_output
    }

def split_dataset(data, train_ratio=0.9):
    """划分训练集和验证集"""
    random.shuffle(data)
    split_idx = int(len(data) * train_ratio)
    return data[:split_idx], data[split_idx:]

def validate_data(data):
    """验证数据质量"""
    issues = []
    for i, item in enumerate(data):
        # 检查必填字段
        if "instruction" not in item or not item["instruction"]:
            issues.append(f"第{i}条：缺少instruction字段")
        if "output" not in item or not item["output"]:
            issues.append(f"第{i}条：缺少output字段")
        # 检查长度
        if len(item.get("instruction", "")) < 5:
            issues.append(f"第{i}条：instruction过短")
        if len(item.get("output", "")) < 10:
            issues.append(f"第{i}条：output过短")
        # 检查输出是否包含敏感信息
        output = item.get("output", "")
        if "密码" in output and "请勿" not in output:
            issues.append(f"第{i}条：output可能包含敏感信息")
    return issues

# 使用示例
if __name__ == "__main__":
    # 加载原始数据
    with open("raw_data.json", "r") as f:
        raw_data = json.load(f)

    # 格式转换
    formatted_data = [
        format_alpaca_to_chat(
            item["instruction"],
            item.get("input", ""),
            item["output"]
        )
        for item in raw_data
    ]

    # 数据验证
    issues = validate_data(formatted_data)
    if issues:
        print(f"发现{len(issues)}个问题：")
        for issue in issues[:10]:
            print(f"  - {issue}")

    # 划分数据集
    train_data, eval_data = split_dataset(formatted_data, train_ratio=0.9)
    print(f"训练集：{len(train_data)}条")
    print(f"验证集：{len(eval_data)}条")

    # 保存
    with open("data/train.json", "w") as f:
        json.dump(train_data, f, ensure_ascii=False, indent=2)
    with open("data/eval.json", "w") as f:
        json.dump(eval_data, f, ensure_ascii=False, indent=2)
```

## 附录G 微调损失函数详解

### G.1 SFT损失函数

SFT使用标准的自回归语言模型损失（交叉熵损失）：

```
L_SFT = -(1/N) × Σ_{i=1}^{N} Σ_{t=1}^{T_i} log P(y_{i,t} | x_i, y_{i,<t}; θ)
```

其中：
- N是batch中的样本数
- T_i是第i个样本的回答长度
- y_{i,t}是第i个样本回答的第t个token
- x_i是第i个样本的输入（指令）
- θ是模型参数
- P(y_{i,t} | x_i, y_{i,<t}; θ)是模型预测第t个token的概率

注意：损失只对回答部分的token计算，输入部分的token不参与损失计算（loss masking）。

### G.2 DPO损失函数

DPO的损失函数基于偏好数据：

```
L_DPO = -(1/N) × Σ_{i=1}^{N} log σ(β × [log(π_θ(y_w|x)/π_ref(y_w|x)) - log(π_θ(y_l|x)/π_ref(y_l|x))])
```

其中：
- y_w是偏好数据中更好的回答（chosen）
- y_l是偏好数据中更差的回答（rejected）
- π_θ是当前训练的策略模型
- π_ref是参考模型（冻结不动）
- β是温度参数，控制偏离参考模型的程度
- σ是sigmoid函数

DPO损失的含义：让策略模型相对于参考模型，给"好回答"更高的概率提升，给"差回答"更低（或不变）的概率。

### G.3 PPO损失函数

PPO的目标函数：

```
L_PPO = E[min(r_t × A_t, clip(r_t, 1-ε, 1+ε) × A_t)] - β × KL(π_θ || π_ref)
```

其中：
- r_t = π_θ(y|x) / π_old(y|x) 是重要性采样比率
- A_t 是优势函数（由Critic模型估计）
- ε是裁剪参数，限制策略更新幅度
- KL是KL散度，防止策略偏离参考模型太远
- β是KL惩罚系数

### G.4 GRPO损失函数

GRPO的核心创新是去除Critic模型，通过组内比较估计优势：

```
A_i = (R_i - mean(R_group)) / std(R_group)
```

其中R_i是同一问题下第i个回答的奖励，R_group是同一问题所有回答的奖励集合。这样不需要Critic模型就能估计优势函数。
