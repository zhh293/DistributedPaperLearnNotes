# Claude Code 工具和权限机制深度分析

## 一、架构总览

Claude Code 的工具与权限系统是整个 Harness 工程中最复杂的部分，它解决的核心问题是：**如何让 AI 拥有强大的工具能力，同时确保每次操作都在用户授权和安全边界内**。

系统采用 **fail-closed**（默认拒绝）的安全哲学——除非明确允许，否则假设操作是危险的。

```
┌────────────────────────────────────────────────────────────────────┐
│                       工具与权限系统架构                              │
├────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  Tool Registry（工具注册表）                                    │  │
│  │  getAllBaseTools() → getTools() → assembleToolPool()           │  │
│  └────────────────────────────────┬─────────────────────────────┘  │
│                                   ↓                                  │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  Permission Layer（权限层）                                    │  │
│  │  Rules → Mode → Tool Check → Hooks → Classifier → User       │  │
│  └────────────────────────────────┬─────────────────────────────┘  │
│                                   ↓                                  │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  Execution Layer（执行层）                                     │  │
│  │  Validation → Permission → Execute → PostHook → Result        │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                      │
└────────────────────────────────────────────────────────────────────┘
```

## 二、工具类型系统与定义

### 2.1 Tool 泛型接口

核心类型定义在 `src/Tool.ts` 中，这是一个约 40 个属性/方法的大型泛型接口：

```typescript
interface Tool<
  Input extends AnyObject,    // Zod schema 定义的输入类型
  Output,                     // 工具返回的数据类型
  P extends ToolProgressData  // 进度事件类型
> {
  // 元信息
  name: string
  description: string
  inputSchema: ZodSchema<Input>
  
  // 核心方法
  call(args, context, canUseTool, parentMessage, onProgress): Promise<Output>
  checkPermissions(input, context): Promise<PermissionResult>
  validateInput(input, context): Promise<ValidationResult>
  
  // 安全属性
  isReadOnly(input): boolean        // 是否只读操作
  isConcurrencySafe(input): boolean // 是否可以并发执行
  isDestructive(input): boolean     // 是否不可逆
  isEnabled(): boolean              // 是否启用
  
  // Hook 支持
  preparePermissionMatcher(input): PermissionMatcher
}
```

### 2.2 buildTool 工厂函数

所有工具必须通过 `buildTool(def)` 构建，其默认值设计是 **fail-closed** 的：

| 属性 | 默认值 | 安全含义 |
|------|--------|---------|
| `isReadOnly` | `false` | 假设会写入 |
| `isConcurrencySafe` | `false` | 假设并发不安全 |
| `isDestructive` | `false` | — |
| `checkPermissions` | `{ behavior: 'allow' }` | 延迟到通用权限系统 |
| `toAutoClassifierInput` | `''` | 跳过分类器（安全相关工具必须覆盖） |

### 2.3 工具分类

系统约有 40+ 内置工具，按功能分类：

**核心文件操作**：BashTool, FileReadTool, FileEditTool, FileWriteTool

**搜索工具**：GlobTool, GrepTool

**代理工具**：AgentTool, SkillTool, SendMessageTool

**环境特定**：REPLTool（仅 ant 用户）、PowerShellTool（仅 Windows）

**控制工具**：TaskStopTool, ExitPlanModeTool, AskUserQuestionTool

## 三、工具注册与组装管线

### 3.1 注册

`getAllBaseTools()` 是所有工具的唯一真相来源（single source of truth）：

```typescript
function getAllBaseTools(): Tool[] {
  return [
    BashTool,
    FileReadTool,
    FileEditTool,
    FileWriteTool,
    GlobTool,
    GrepTool,
    AgentTool,
    // ... 约 40+ 工具
    // 部分工具通过 feature flag 条件注册
    ...(feature('COORDINATOR_MODE') ? [CoordinatorTool] : []),
    ...(isWindows ? [PowerShellTool] : []),
  ]
}
```

### 3.2 组装管线

```
getAllBaseTools()                    所有内置工具（带环境/feature flag 过滤）
       ↓
getTools(permissionContext)         deny rule 过滤 + isEnabled() 过滤
       ↓
assembleToolPool(context, mcpTools) 合并内置 + MCP 工具，名称去重，内置优先
       ↓
filterToolsByDenyRules(tools, ctx)  API 发送前的最终过滤
```

### 3.3 工具限制集

`src/constants/tools.ts` 定义了不同场景下的工具白名单/黑名单：

| 限制集 | 适用场景 | 规则 |
|--------|---------|------|
| `ALL_AGENT_DISALLOWED_TOOLS` | 所有子代理 | 禁用 TaskOutput、ExitPlanMode、AskUserQuestion 等 |
| `ASYNC_AGENT_ALLOWED_TOOLS` | 异步代理 | 白名单：文件操作、搜索、shell |
| `COORDINATOR_MODE_ALLOWED_TOOLS` | 协调器模式 | 只允许 Agent、TaskStop、SendMessage |

## 四、权限模式系统

### 4.1 权限模式定义

```typescript
type PermissionMode = 
  | 'default'          // 需要询问用户
  | 'acceptEdits'      // 自动允许文件编辑，shell 仍需批准
  | 'bypassPermissions'// 跳过所有权限提示（但 deny/ask/safety 仍生效！）
  | 'dontAsk'          // 将所有 'ask' 转为 'deny'
  | 'plan'             // 规划模式
  | 'auto'             // AI 分类器决定（需 feature flag）
  | 'bubble'           // 内部模式
```

### 4.2 各模式详解

**default** — 最保守模式。每次写操作、shell 命令都弹出确认对话框。

**acceptEdits** — 中等信任。在工作目录内的文件编辑自动通过，但 shell 命令（可能有副作用）仍需确认。

**bypassPermissions** — 高信任模式。跳过大部分权限提示，但有三样东西**永远不会被 bypass**：
- Deny rules（显式禁止的操作）
- Ask rules（显式要求询问的操作）
- Safety checks（安全检查：.git/、.claude/ 等受保护路径）

**dontAsk** — 无人值守模式。不能弹对话框时使用——把所有"需要确认"转为"拒绝"。

**auto** — 最智能的模式。用 AI 分类器（transcript classifier）分析操作上下文，自动决定是允许还是拒绝。

## 五、权限规则系统

### 5.1 规则结构

```typescript
type PermissionRule = {
  source: PermissionRuleSource    // 规则来源
  ruleBehavior: 'allow' | 'deny' | 'ask'  // 行为
  ruleValue: {
    toolName: string              // 工具名
    ruleContent?: string          // 内容匹配（可选）
  }
}
```

### 5.2 规则来源与优先级

| 来源 | 说明 | 优先级 |
|------|------|--------|
| `policySettings` | 企业策略设置 | 最高 |
| `flagSettings` | Feature flag 设置 | ↑ |
| `cliArg` | 命令行参数 | ↑ |
| `command` | 命令来源 | ↑ |
| `userSettings` | 用户级设置 (~/.claude/) | ↑ |
| `projectSettings` | 项目级设置 (.claude/) | ↑ |
| `localSettings` | 本地设置 | ↑ |
| `session` | 会话内临时规则 | 最低 |

### 5.3 规则匹配语法

规则可以是工具级或内容级：

```
# 工具级规则（匹配该工具的所有调用）
Bash                    → 匹配所有 Bash 调用
FileWrite              → 匹配所有文件写入

# 内容级规则（匹配特定内容模式）
Bash(prefix:git *)     → 匹配以 "git " 开头的命令
Bash(npm publish:*)    → 匹配包含 "npm publish" 的命令
FileWrite(/etc/*)      → 匹配写入 /etc/ 的操作

# MCP 服务器级规则
mcp__server1           → 匹配该服务器的所有工具
mcp__server1__tool1    → 匹配特定工具
```

## 六、工具执行生命周期

### 6.1 完整执行管线

`checkPermissionsAndCallTool()` 实现了完整的八阶段管线：

```
┌─────────────────────────────────────────────────────────────────┐
│  Stage 1: Input Validation（输入验证）                            │
│  ├── Zod schema 验证（类型安全）                                  │
│  └── 语义验证 tool.validateInput()（业务逻辑）                    │
│                          ↓                                        │
│  Stage 2: Speculative Classifier（预测性分类器启动）              │
│  └── 对 Bash 工具，提前启动分类器（并行加速）                     │
│                          ↓                                        │
│  Stage 3: Input Preprocessing（输入预处理）                       │
│  ├── 安全剥离 _simulatedSedEdit 字段（防御注入）                  │
│  └── backfillObservableInput 填充衍生字段                         │
│                          ↓                                        │
│  Stage 4: PreToolUse Hooks（前置钩子）                            │
│  └── 可返回: allow/deny/ask/修改输入/阻止继续/停止                 │
│                          ↓                                        │
│  Stage 5: Permission Decision（权限决策）                         │
│  └── resolveHookPermissionDecision()                              │
│      ├── Hook allow ──→ 仍检查 deny/ask rules（不能绕过！）       │
│      ├── Hook deny ──→ 直接拒绝                                   │
│      └── Hook ask / 无决策 ──→ canUseTool() 正常流程              │
│                          ↓                                        │
│  Stage 6: Tool Execution（工具执行）                              │
│  └── tool.call(input, context, ...)                               │
│                          ↓                                        │
│  Stage 7: PostToolUse Hooks（后置钩子）                           │
│  └── 可修改 MCP 输出 / 添加上下文 / 阻止继续                      │
│                          ↓                                        │
│  Stage 8: Result Processing（结果处理）                           │
│  ├── mapToolResultToToolResultBlockParam()                        │
│  ├── 大结果持久化到磁盘                                           │
│  └── 附加用户反馈和内容块                                         │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 Hook 系统详解

**Hook 事件类型**：

| 事件 | 时机 | 能力 |
|------|------|------|
| `PreToolUse` | 工具执行前 | allow/deny/ask/修改输入/阻止/停止 |
| `PostToolUse` | 工具成功后 | 修改 MCP 输出/添加上下文/阻止继续 |
| `PostToolUseFailure` | 工具失败后 | 错误处理 |
| `PermissionRequest` | 权限请求时 | headless 代理的权限代理 |
| `PermissionDenied` | 权限被拒后 | auto mode 拒绝通知 |

**关键不变式**：Hook 的 `allow` 决策永远不会绕过设置中的 deny/ask 规则！

```typescript
// 即使 Hook 说 allow，仍然要检查规则
if (hookResult === 'allow') {
  const ruleResult = checkRuleBasedPermissions(tool, input)
  if (ruleResult === 'deny') return 'deny'  // 规则覆盖 Hook
  if (ruleResult === 'ask') return 'ask'    // 规则覆盖 Hook
  return 'allow'  // 规则无异议，Hook allow 生效
}
```

## 七、核心权限算法 hasPermissionsToUseTool

这是整个权限系统的心脏，实现了一个分步决策管线：

```
┌──────────────────────────────────────────────────────────────────┐
│                    hasPermissionsToUseTool                         │
├──────────────────────────────────────────────────────────────────┤
│                                                                    │
│  Step 1a: 全工具 Deny 规则                                        │
│  getDenyRuleForTool() → 匹配则立即 DENY                           │
│                          ↓ (未匹配)                                │
│  Step 1b: 全工具 Ask 规则                                         │
│  getAskRuleForTool() → 匹配则返回 ASK                             │
│  (例外: sandbox auto-allow 可以绕过)                               │
│                          ↓ (未匹配)                                │
│  Step 1c: 工具实现的权限检查                                      │
│  tool.checkPermissions(input, context)                             │
│  → 工具自定义逻辑（如 BashTool 检查子命令）                       │
│                          ↓                                         │
│  Step 1d: 工具返回 deny → 立即拒绝                                │
│                          ↓ (非 deny)                               │
│  Step 1e: requiresUserInteraction → 即使 bypass 也要交互          │
│                          ↓ (否)                                    │
│  Step 1f: 内容特定 ask 规则                                       │
│  如 Bash(npm publish:*) → 即使 bypass 也生效                      │
│                          ↓ (未匹配)                                │
│  Step 1g: Safety Checks（安全检查）                               │
│  .git/ .claude/ .vscode/ shell configs → 即使 bypass 也必须提示   │
│                          ↓ (未触发)                                │
│  Step 2a: 模式检查                                                │
│  bypassPermissions 或 (plan + bypass可用) → ALLOW                  │
│                          ↓ (非 bypass)                             │
│  Step 2b: 全工具 Allow 规则                                       │
│  toolAlwaysAllowedRule() → ALLOW                                   │
│                          ↓ (未匹配)                                │
│  Step 3: passthrough → ask                                        │
│  工具返回 passthrough 意为"我不关心，交给通用系统"                  │
│  → 转为 ASK                                                       │
│                                                                    │
└──────────────────────────────────────────────────────────────────┘
```

### 7.1 外层后处理

对于返回 `ask` 的结果，还有额外处理：

**dontAsk 模式**：ask → deny（自动拒绝）

**auto 模式**（AI 分类器决策流程）：
1. 非 classifier-approvable 的 safetyCheck → 保持 ask / headless 中 deny
2. `requiresUserInteraction` → 保持 ask
3. **acceptEdits 快速路径**：模拟 acceptEdits 模式，如果通过则跳过分类器
4. **安全工具白名单**：`isAutoModeAllowlistedTool()` 检查
5. **AI 分类器**：`classifyYoloAction()` 调用 transcript classifier
6. 分类器失败 → fail-closed（deny）或 fail-open（fallback 到用户提示）

**headless 模式**：
- 运行 PermissionRequest hooks 给 hook 机会做决定
- 无 hook 决策 → auto-deny

## 八、Bash 权限的特殊处理

BashTool 有最复杂的权限逻辑，因为 shell 命令的危险性远高于文件操作：

### 8.1 安全分析管线

```
用户命令 → parseForSecurity()        AST 解析
         → splitCommandWithOperators() 分解复合命令
         → 每个子命令独立权限检查
         → dangerousPatterns.ts        危险模式检测
         → shouldUseSandbox()          沙箱决策
```

### 8.2 前缀匹配

Allow 规则支持前缀匹配语法：

```
Bash(prefix:git *)       → 允许所有 git 开头的命令
Bash(prefix:npm test)    → 允许 npm test
Bash(prefix:cargo build) → 允许 cargo build
```

### 8.3 通配符匹配

`matchWildcardPattern()` 支持 `*` 通配：

```
Bash(npm *:*)    → 匹配 "npm install lodash"、"npm test" 等
Bash(docker *)   → 匹配所有 docker 命令
```

### 8.4 沙箱集成

```typescript
function shouldUseSandbox(command): boolean {
  // 检查是否在沙箱环境中
  // 检查 autoAllowBashIfSandboxed 配置
  // 检查 dangerouslyDisableSandbox 字段
}
```

- `autoAllowBashIfSandboxed`：沙箱内的命令可以跳过权限提示
- `dangerouslyDisableSandbox`：工具可以请求退出沙箱（需要额外权限确认）

### 8.5 预测性分类器

```typescript
// 在 hooks 运行前就启动分类器（异步并行）
const speculativeCheck = startSpeculativeClassifierCheck(command)
// ... hooks 运行 ...
// 到需要分类器结果时，可能已经有结果了
const result = await speculativeCheck
```

## 九、并发控制与工具编排

### 9.1 批次分区

`partitionToolCalls()` 将一轮中的多个工具调用分为批次：

```typescript
// 连续的 concurrencySafe 工具合并为并发批
[Read A, Read B, Read C]     → 并发执行
[Write X]                    → 串行执行
[Read D, Grep E]             → 并发执行
[Bash "deploy"]              → 串行执行
```

### 9.2 并发控制

- **最大并发数**：由 `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` 控制，默认 10
- **并发批**：`runToolsConcurrently()` — 所有工具同时启动
- **串行批**：`runToolsSerially()` — 逐个执行，每个完成后更新 context

### 9.3 StreamingToolExecutor

流式工具执行器支持：
- 工具流式到达时立即开始执行（如果条件允许）
- 结果按接收顺序缓冲和发射
- `discard()` — 流式回退时丢弃所有待处理和进行中的工具
- Context modifiers 按工具接收顺序排队应用

### 10.1 命名约定

MCP 工具通过 `isMcp: true` 标识，命名格式：`mcp__<server>__<tool>`


- MCP 工具的 `checkPermissions` 默认返回 `passthrough`（让通用权限系统决定）
- 权限规则支持服务器级匹配：deny `mcp__server1` 会禁用该服务器所有工具

## 十一、Denial Tracking（拒绝追踪）

### 11.1 追踪状态

```typescript
type DenialTrackingState = {
  consecutiveDenials: number  // 连续拒绝计数
  totalDenials: number        // 总拒绝计数
}
```

### 11.2 安全阀机制

| 条件 | 行为 |
|------|------|
| 连续拒绝达到阈值 | Fallback 到用户提示 |
| 总拒绝达到阈值 | 同样 fallback |
| Headless 模式达到阈值 | `AbortError`（终止代理） |
| 一次成功允许 | 重置连续计数 |

这防止了 AI 陷入"反复尝试被拒绝的操作"的死循环。

## 十二、Safety Checks（安全检查）

即使在 `bypassPermissions` 模式下，以下路径的操作**永远需要用户确认**：

| 受保护路径 | 原因 |
|-----------|------|
| `.git/` | Git 仓库元数据，修改可能导致数据丢失 |
| `.claude/` | Claude 配置文件，修改可能改变权限设置 |
| `.vscode/` | IDE 配置 |
| `~/.bashrc`, `~/.zshrc` | Shell 配置文件 |
| `~/.ssh/` | SSH 密钥 |
| `/etc/` | 系统配置 |

安全检查有一个 `classifierApprovable` 标志——某些安全检查可以被 AI 分类器通过（如 .vscode/settings.json），而另一些永远不行（如 .git/config）。

## 十四、设计理念总结

Claude Code 工具权限系统的核心设计哲学：

1. **规则优先于一切**：deny rules 不能被 bypass mode、hooks、甚至 AI 分类器覆盖。这保证了管理员设置的安全策略永远有效。

2. **安全检查免疫**：`.git/`、`.claude/` 等路径在任何模式下都需要确认。没有任何方式可以静默修改这些文件。

3. **分层决策**：hook → rule check → mode check → tool-specific check → classifier → user prompt。每一层都是上一层的兜底。

4. **渐进式自动化**：auto mode 先尝试 acceptEdits 快速路径、再查白名单、最后才调分类器。用最便宜的方式尝试，只在必要时使用昂贵的 AI 分类。

5. **容错设计**：分类器不可用时可 fail-closed（deny）或 fail-open（fallback to user）。系统永远不会因为某个组件故障而完全瘫痪。

6. **并发安全**：通过 `isConcurrencySafe` 分区确保写操作串行化，读操作可以自由并行。

7. **可观测性**：每个决策点都有 analytics event 和 OTel span，可以精确追踪权限流程中的每一步。

8. **Fail-closed by default**：新工具如果忘记设置安全属性，默认行为是最保守的（不可读、不可并发、需要权限）。安全不依赖于开发者记得做正确的事。
