# Claude Code 上下文管理机制深度分析

---

## 〇、设计概览：先看森林，再看树木

### 这套系统要解决什么问题？

AI 模型有一个硬约束：**上下文窗口有限**（通常 200K tokens）。但用户的需求是无限的——一次对话可能持续上百轮，涉及数十个文件。如果什么都往窗口里塞，很快就会爆掉；如果随意丢弃信息，AI 又会"失忆"给出错误答案。

所以这套系统的核心使命是一句话：**在有限的窗口里，始终保留"最有用"的信息，同时让 API 调用尽量命中缓存（省钱省时间）。**

### 设计思路：三大原则

**原则一：分层递进，各司其职。** 就像城市供水系统——水源（固定指令）、水厂（项目规则）、管网（实时信息）、水表（压缩控制）各层独立运作，但最终为同一个水龙头供水。每一层只关心自己擅长的事，不越界。

**原则二：缓存优先于新鲜度。** 系统宁可用"会话开始时的快照"（稍微过时），也不在对话中途频繁刷新内容。因为 API 缓存是按字节匹配的——哪怕多一个空格，之前缓存的几十万 token 全部失效，需要重新计费。

**原则三：渐进式降级，不一步到位。** 窗口快满时不会直接"全量压缩"（成本高、信息损失大），而是先尝试最轻量的手段（删除旧工具输出），不够再升级（折叠旧对话），实在不行才上"全量摘要"。像洋葱一样一层一层剥。

### 五层架构：为什么这么分？

```
┌───────────────────────────────────────────────────────────────────┐
│  Layer 5: API Call Assembly（API 调用组装）                          │
│  为什么需要？── 最后一步把所有材料拼成 API 能理解的格式，              │
│               同时标记哪些部分可以跨用户共享缓存                       │
├───────────────────────────────────────────────────────────────────┤
│  Layer 4: Compaction Pipeline（压缩管道）                            │
│  为什么需要？── 对话越来越长，必须有"垃圾回收"机制                    │
│               5 道防线确保永远不会超限，同时尽量少丢有用信息             │
├───────────────────────────────────────────────────────────────────┤
│  Layer 3: Per-turn Attachments（每轮附件注入）                       │
│  为什么需要？── 环境是变化的（文件被改了、新工具上线了），              │
│               每一轮对话都需要把"刚发生的变化"告诉 AI                  │
├───────────────────────────────────────────────────────────────────┤
│  Layer 2: User/Project Context（用户/项目上下文）                    │
│  为什么需要？── 不同项目有不同规则（代码规范、架构约定），              │
│               相当于给 AI 一份"入职须知"让它了解这个项目                │
├───────────────────────────────────────────────────────────────────┤
│  Layer 1: System Prompt Assembly（系统提示组装）                     │
│  为什么需要？── AI 的"出厂设置"，定义身份、能力边界、行为准则，         │
│               所有用户共享，像操作系统的内核一样稳定不变                 │
└───────────────────────────────────────────────────────────────────┘
```

**从下往上看**：Layer 1 是"AI 是谁"，Layer 2 是"它在哪个项目里工作"，Layer 3 是"刚刚发生了什么"，Layer 4 是"窗口快满了怎么回收空间"，Layer 5 是"把这一切打包发出去"。

### 一个类比：图书馆管理员

把整个系统想象成一个AI图书馆管理员在有限的书桌上工作：

- **Layer 1（系统提示）**= 管理员的"工作手册"，规定了他是谁、怎么跟读者说话、什么能做什么不能做。永远放在桌上，不会变。
- **Layer 2（项目上下文）**= 今天负责的"楼层指南"——这个楼层有什么书、分类规则是什么。每天上班看一次就够了。
- **Layer 3（每轮附件）**= 读者刚递过来的"便签条"——"刚才3楼新到了一批书"、"5楼有本书被借走了"。每次有新变化就递一张。
- **Layer 4（压缩管道）**= 桌面空间不够了，管理员的整理策略——先把最旧的便签收起来，再把不重要的笔记精简成一行摘要，实在不够就把上午所有的工作记录压缩成一段总结。
- **Layer 5（API 组装）**= 管理员最终回答读者问题时，桌面上剩下的内容就是他回答的全部依据。

### 读后续内容的建议

下面每一章对应一层的详细实现。如果你只想了解某一层，可以直接跳到对应章节。如果你关心"对话太长时系统怎么处理"，直接看第五章（压缩管道）。如果你想理解"为什么这么在乎缓存"，看第七章（Prompt Cache 优化）。

## 一、架构总览

Claude Code 的上下文管理系统是整个 Harness 工程的核心，它解决的根本问题是：**如何在有限的 Token 窗口内，为 AI 提供最精准、最有用的信息，同时最大化 API 缓存命中率以降低成本**。

整个系统可以分为五个核心层次：

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 5: API Call Assembly（API 调用组装）                    │
│  ── 最终拼装 system prompt + messages，优化 cache scope       │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: Compaction Pipeline（压缩管道）                      │
│  ── Snip → Microcompact → Collapse → Autocompact → Reactive │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Per-turn Attachments（每轮附件注入）                 │
│  ── 动态注入文件变更、记忆、技能发现等实时信息                   │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: User/Project Context（用户/项目上下文）              │
│  ── CLAUDE.md 多层文件 + Git 状态快照                         │
├─────────────────────────────────────────────────────────────┤
│  Layer 1: System Prompt Assembly（系统提示组装）               │
│  ── 静态指令 + 动态 section（记忆、环境、MCP 等）              │
└─────────────────────────────────────────────────────────────┘
```

## 二、System Prompt 组装机制

### 2.1 入口函数 `getSystemPrompt()`

位于 `src/constants/prompts.ts`，这是系统提示的主入口。它返回一个 `string[]` 数组，每个元素是一个独立的 prompt 块。结构严格按照**静态→动态**的顺序排列。

### 2.2 静态部分（可全局缓存）

静态部分是所有用户共享的指令，内容在所有会话中完全一致：

| Section | 功能 |
|---------|------|
| `getSimpleIntroSection()` | AI 身份和角色定义（"你是 Claude，由 Anthropic 创建..."） |
| `getSimpleSystemSection()` | 工具权限规范、Hook 机制说明、系统标签含义 |
| `getSimpleDoingTasksSection()` | 任务执行规范（代码风格、安全约束、验证要求） |
| `getActionsSection()` | 操作安全性与可逆性原则 |
| `getUsingYourToolsSection()` | 工具使用优先级和选择策略 |
| `getSimpleToneAndStyleSection()` | 输出格式和语气要求 |
| `getOutputEfficiencySection()` | 输出效率（减少冗余、避免重复） |

### 2.3 动态边界标记

```typescript
export const SYSTEM_PROMPT_DYNAMIC_BOUNDARY = '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'
```

这个标记将 prompt 分为两个区域：
- **标记之前**：内容在所有用户间完全一致，可使用 `cacheScope: 'global'` 跨用户共享 API 缓存
- **标记之后**：包含用户特定信息（记忆、环境、MCP 配置等），不能使用全局缓存

### 2.4 动态部分（通过 Section Registry 解析）

动态 section 通过 `resolveSystemPromptSections()` 解析，每个 section 注册时指定是否可缓存：

```typescript
// 可缓存的 section（会话内计算一次）
export function systemPromptSection(name, compute) {
  return { name, compute, cacheBreak: false }
}

// 不可缓存的 section（每轮重新计算，会打破 prompt cache）
export function DANGEROUS_uncachedSystemPromptSection(name, compute, _reason) {
  return { name, compute, cacheBreak: true }
}
```

动态 section 列表：

| Section | 类型 | 内容 |
|---------|------|------|
| `session_guidance` | cached | 会话特定指导（Agent 工具说明、技能发现等） |
| `memory` | cached | 自动记忆系统内容（`loadMemoryPrompt()`） |
| `env_info_simple` | cached | 环境信息（cwd、git 分支、平台、模型信息） |
| `language` | cached | 用户语言偏好 |
| `output_style` | cached | 输出风格配置 |
| `mcp_instructions` | **DANGEROUS** | MCP 服务器指令（每轮变化，打破缓存） |
| `scratchpad` | cached | 临时文件目录信息 |
| `frc` | cached | Function Result Clearing 说明 |
| `summarize_tool_results` | cached | 工具结果摘要指导 |

### 2.5 缓存策略

Section 的缓存逻辑是会话级的：

1. 首次调用时计算值，存入 bootstrap state 的 cache map
2. 后续调用如果 `cacheBreak === false`，直接返回缓存值
3. 只有 `/clear` 或 `/compact` 命令才会清除缓存

这种设计保证了即使 GrowthBook feature flag 在会话中途翻转，prompt 内容也不会突变（避免打破 API 缓存）。

## 三、用户/项目上下文管理

### 3.1 CLAUDE.md 多层文件系统

`getUserContext()` 是一个 **memoized** 函数（整个会话只执行一次），它加载多层 CLAUDE.md 文件：

```
优先级（从低到高）：
┌──────────────────────────────────────────────────┐
│  Managed（企业管理）                               │
│  /etc/claude-code/CLAUDE.md                       │
│  /etc/claude-code/.claude/rules/*.md              │
├──────────────────────────────────────────────────┤
│  User（用户全局）                                  │
│  ~/.claude/CLAUDE.md                              │
│  ~/.claude/rules/*.md                             │
├──────────────────────────────────────────────────┤
│  Project（项目级，签入版本控制）                     │
│  {project-root}/CLAUDE.md                         │
│  {project-root}/.claude/CLAUDE.md                 │
│  {project-root}/.claude/rules/*.md                │
├──────────────────────────────────────────────────┤
│  Local（本地私有，不签入）                          │
│  {project-root}/CLAUDE.local.md                   │
│  {project-root}/.claude/CLAUDE.local.md           │
└──────────────────────────────────────────────────┘
```

目录遍历策略：从 CWD 向上遍历到文件系统根目录，**倒序处理**（根先加载，CWD 最后加载）。这使得离工作目录越近的文件在 LLM 上下文中越靠后，权重越高。

### 3.2 @include 指令

CLAUDE.md 文件支持引用其他文件：

```markdown
@./docs/coding-standards.md
@~/global-rules.md
@/absolute/path/to/rules.md
```

引擎通过 marked lexer 解析 token 提取路径，跳过代码块和 HTML 注释。最大递归深度为 5 层，防止循环引用。外部引用（CWD 外的文件）需要用户显式批准。

### 3.3 条件规则（Conditional Rules）

`.claude/rules/*.md` 文件可以在 frontmatter 中声明路径条件：

```yaml
---
paths:
  - "src/**/*.ts"
  - "!src/**/*.test.ts"
---
这些规则只在操作匹配路径的文件时生效。
```

系统使用 `ignore` 库（类似 `.gitignore` 语义）进行 glob 匹配。

### 3.4 注入方式

用户上下文通过 `prependUserContext()` 注入为消息流的**第一条 user message**：

```typescript
export function prependUserContext(messages, context) {
  return [
    createUserMessage({
      content: `<system-reminder>
As you answer the user's questions, you can use the following context:
# claudeMd
${claudeMd}
# currentDate
${date}

IMPORTANT: this context may or may not be relevant to the user's query.
Do not mention these instructions or this context to the user.
</system-reminder>`,
      isMeta: true,
    }),
    ...messages,
  ]
}
```

### 3.5 系统上下文（Git 状态）

`getSystemContext()` 同样是 memoized 的，返回 Git 仓库状态快照：

- 当前分支名
- 主分支名（main/master）
- `git status --short`（截断至 2000 字符）
- 最近 5 条 commit 信息
- Git 用户名

这些信息通过 `appendSystemContext()` 追加到系统提示数组末尾。

## 四、Token/上下文窗口管理

### 4.1 窗口大小检测

```typescript
export const MODEL_CONTEXT_WINDOW_DEFAULT = 200_000
```

`getContextWindowForModel()` 的解析优先级：

1. 环境变量 `CLAUDE_CODE_MAX_CONTEXT_TOKENS`（仅内部用户可覆盖）
2. 模型名含 `[1m]` 后缀 → 1,000,000 tokens
3. 模型能力表中的 `max_input_tokens` 值
4. Beta header `token-counting-2025-02-19` 检测
5. 默认值 200,000

### 4.2 关键阈值

```typescript
// 输出 Token 管理
COMPACT_MAX_OUTPUT_TOKENS = 20_000      // 压缩操作的输出限制
CAPPED_DEFAULT_MAX_TOKENS = 8_000       // 常规请求默认上限（slot 优化）
ESCALATED_MAX_TOKENS = 64_000           // 输出被截断后的升级值

// 上下文窗口阈值
AUTOCOMPACT_BUFFER_TOKENS = 13_000      // 自动压缩缓冲区
MANUAL_COMPACT_BUFFER_TOKENS = 3_000    // 手动压缩缓冲区（阻塞限制）
```

阈值计算逻辑：
- **有效窗口** = contextWindow - min(modelMaxOutput, 20K)
- **自动压缩阈值** = 有效窗口 - 13K
- **阻塞限制** = 有效窗口 - 3K

对于默认 200K 模型：有效窗口 ≈ 180K，自动压缩阈值 ≈ 167K，阻塞限制 ≈ 177K。

### 4.3 输出截断恢复

当模型输出被截断（触发 `max_output_tokens` stop reason）：
1. 先尝试将限制升级到 64K（`ESCALATED_MAX_TOKENS`）
2. 如果仍然不够，注入恢复消息："Resume directly — no apology, no recap"
3. 最多重试 3 次

## 五、压缩管道（Compaction Pipeline）

这是上下文管理最精华的部分——五层递进式压缩，确保永远不会超限：

### 5.1 第一层：Tool Result Budget

```typescript
messagesForQuery = await applyToolResultBudget(messagesForQuery, ...)
```

对过大的工具结果进行截断或替换，控制单条消息的 token 开销。例如，一个 Grep 工具返回了 50KB 的搜索结果，会被截断到合理长度。

### 5.2 第二层：Snip（历史裁剪）

```typescript
if (feature('HISTORY_SNIP')) {
  const snipResult = snipModule.snipCompactIfNeeded(messagesForQuery)
  messagesForQuery = snipResult.messages
  snipTokensFreed = snipResult.tokensFreed
}
```

移除早期对话轮次中不再需要的内容——比如三十轮之前的工具调用详情。释放的 token 数量会传递给下游步骤作为参考。

### 5.3 第三层：Microcompact（微压缩）

```typescript
const microcompactResult = await deps.microcompact(messagesForQuery, toolUseContext, querySource)
```

基于时间和位置的工具结果清理策略：保留最近 N 条的完整输出，将更早的 Read/Bash/Grep/Glob 等工具的结果替换为摘要或占位符。

这不是"压缩"——更像是"遗忘不重要的细节"。

### 5.4 第四层：Context Collapse（上下文折叠）

```typescript
if (feature('CONTEXT_COLLAPSE') && contextCollapse) {
  const collapseResult = await contextCollapse.applyCollapsesIfNeeded(messagesForQuery, ...)
  messagesForQuery = collapseResult.messages
}
```

将旧的对话段落替换为 AI 生成的摘要。与 autocompact 不同的是，collapse 可以保留更细粒度的结构——比如只折叠"讨论需求"的部分，保留"实现决策"的部分。

### 5.5 第五层：Autocompact（自动压缩）

```typescript
const { compactionResult, consecutiveFailures } = await deps.autocompact(
  messagesForQuery, toolUseContext, cacheSafeParams, querySource, tracking, snipTokensFreed
)
```

当前四层都不够用，token 使用量仍超过阈值时，触发完整的会话压缩：
- 使用 **forked agent**（共享 prompt cache）生成整个对话的摘要
- 摘要替换掉大部分历史消息，只保留最近几轮
- 设有 **circuit breaker**：连续失败 3 次后停止重试，防止无限循环

### 5.6 兜底：Reactive Compact

如果以上所有压缩都不够，且 API 返回 413（prompt too long）：

```typescript
// 在收到 413 错误后立刻执行一次紧急压缩，然后重试
// 每次查询循环最多尝试一次 reactive compact
```

### 5.7 最终防线：Blocking Limit

如果一切压缩手段都失败，且 token 仍然超过 `有效窗口 - 3K`：直接返回错误，终止查询。

```
│                        queryLoop 主循环                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  1. 用户输入 / 工具结果进入 messages                               │
│                          ↓                                        │
│  2. applyToolResultBudget()  ── 裁剪过大的工具结果                 │
│                          ↓                                        │
│  3. snipCompactIfNeeded()    ── 裁剪早期历史                       │
│                          ↓                                        │
│  4. microcompact()           ── 清理旧工具输出                     │
│                          ↓                                        │
│  5. contextCollapse()        ── 折叠旧对话段落                     │
│                          ↓                                        │
│  6. autocompact()            ── 全量压缩（如果仍超阈值）            │
│                          ↓                                        │
│  7. Blocking Limit Check     ── 最终检查，超限则终止                │
│                          ↓                                        │
│  8. prependUserContext()     ── 注入 CLAUDE.md + 日期               │
│     appendSystemContext()    ── 注入 git 状态                      │
│                          ↓                                        │
│  9. splitSysPromptPrefix()   ── 拆分 prompt 设置 cache scope       │

│                          ↓                                        │
│  11. 流式响应 → 解析 tool_use blocks                               │
│                          ↓                                        │
│  12. 执行工具 → 收集结果                                           │
│                          ↓                                        │
│  13. getAttachmentMessages() ── 生成下一轮的附件消息                │
│                          ↓                                        │
│  14. 回到步骤 1（或返回最终结果）                                   │
│                                                                   │

```

## 七、Prompt Cache 优化策略

### 7.1 缓存分区

`splitSysPromptPrefix()` 将系统提示拆分为带有独立 `cacheScope` 的块：

**模式 1：Global Cache（1P 直连 + 有 boundary marker）**

```
[Attribution Header]              → cacheScope: null（不缓存）
[System Prompt Prefix]            → cacheScope: null
[Static content before boundary]  → cacheScope: 'global'  ← 跨所有用户共享！
[Dynamic content after boundary]  → cacheScope: null
```

**模式 2：Org Cache（有 MCP tools 或第三方 provider）**

```
[Attribution Header]  → cacheScope: null
[Everything else]     → cacheScope: 'org'  ← 同组织内共享
```

### 7.2 全局缓存的意义

`cacheScope: 'global'` 意味着所有使用同一模型的 Claude Code 用户共享同一份 prompt 缓存。这就是为什么：
- 静态部分必须在所有用户间**完全一致**（字节级相同）
- 任何会话特定的内容都必须放在 boundary 之后
- `memoize` 确保即使代码中有分支逻辑，实际输出在会话内保持稳定

### 7.3 Memoization 策略

关键函数都使用 memoize，整个会话只计算一次：
- `getUserContext()` — CLAUDE.md 内容
- `getSystemContext()` — Git 状态
- `getGitStatus()` — Git 仓库信息
- `getAutoMemPath()` — 记忆目录路径
- `getMemoryFiles()` — 记忆文件列表

这不仅是性能优化，更是 cache 正确性保证——如果每次调用都重新读取文件，内容的微小变化会导致 prompt 字节变化，打破缓存。

## 八、Attachments 系统（每轮动态注入）

`getAttachmentMessages()` 在每次工具执行后生成附件消息，作为额外的 user message 注入到下一次 API 调用中。这些不是系统提示的一部分，而是动态的"实时信息更新"：

| Attachment 类型 | 触发条件 | 内容 |
|----------------|---------|------|
| `queued_commands` | 用户排队了新命令 | 队列中的命令文本 |
| `date_change` | 日期变更 | 新的日期信息 |
| `deferred_tools_delta` | 新工具可用 | 新工具列表 |
| `agent_listing` | Agent 列表变更 | 活跃 Agent 信息 |
| `mcp_instructions_delta` | MCP 指令变更 | MCP 服务器新指令 |
| `changed_files` | 检测到文件系统变更 | 变更的文件路径 |
| `nested_memory` | 进入/离开新目录 | 该目录的 CLAUDE.md 内容 |
| `skill_discovery` | 技能搜索完成 | 相关技能列表 |
| `plan_mode` | 规划模式 | 计划文件内容 |
| `todo_reminder` | 待办提醒 | 当前待办列表 |
| `token_usage` | Token budget 功能 | 当前 token 使用量 |
| `relevant_memory` | 记忆预取完成 | 相关的自动记忆内容 |

## 九、Project Onboarding State

`projectOnboardingState.ts` 跟踪用户在特定项目中的状态，影响上下文注入决策：

- **是否为空目录** — 如果是，可能需要额外的项目初始化引导
- **是否存在 CLAUDE.md** — 如果没有，可能建议用户创建
- **访问计数**（seen count）— 首次访问时需要更多背景说明

这些状态影响 session_guidance section 的内容生成。

## 十、关键设计模式与决策

### 10.1 Cache Stability > Freshness

系统宁可使用稍微过时的值（session-start snapshot），也不在会话中途改变 prompt 内容打破缓存。`systemPromptSection()` 的缓存设计就是这个理念的体现。

### 10.2 Separation of Concerns

四种上下文各自有独立的注入路径和生命周期：
- **系统指令**（system prompt）→ 固定指令，引导行为
- **用户上下文**（CLAUDE.md）→ 第一条 user message，个性化规则
- **系统上下文**（git status）→ system prompt 末尾，环境感知
- **每轮附件**（attachments）→ user messages，实时信息

### 10.3 多级防线设计

5 层压缩机制确保**永远不会超限**，同时尽量保留最有价值的上下文：
- 轻量级操作（snip、microcompact）频繁执行，代价低
- 重量级操作（autocompact）只在必要时触发，有断路器保护
- 最终防线（blocking limit）确保系统永远不会崩溃

### 10.4 Feature Flag 隔离

所有实验性功能通过 `feature()` 宏在编译时进行 dead code elimination。外部构建不包含内部实验代码，确保：
- 外部用户看不到未发布的功能
- 编译后的代码更小、更快
- 安全边界清晰

---

## 十一、总结

Claude Code 的上下文管理系统是一个工程杰作，它的核心智慧在于：

1. **分层不分离**：虽然逻辑上分为五层，但运行时它们紧密协作，每层的输出是下层的输入
2. **缓存为王**：从全局 prompt cache 到 memoize 到 section cache，每个设计决策都在问"这会不会打破缓存？"
3. **渐进式降级**：从轻量的 microcompact 到重量的 autocompact，系统不会一上来就用最贵的方案
4. **可观测性**：每一步压缩都有 telemetry，可以精确追踪 token 使用和缓存命中率
5. **用户无感**：所有这些复杂性对用户完全透明——用户只需要打字，系统自动处理一切
