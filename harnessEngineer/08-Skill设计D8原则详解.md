# Skill 设计 D8 原则详解

> 本文档整理自 CatPaw skill-judge 技能，该技能通过分析 17+ 个官方 Skill 提炼出 8 个设计评估维度（D1~D8），满分 120 分。这 8 个维度既是评估标准，也是编写 Skill 时的设计指南。

---

## 核心理念

在展开 8 个维度之前，需要先理解 Skill 的本质。

### Skill 不是教程，而是知识外化机制

传统 AI 学习新能力的路径是：收集数据 → GPU 集群训练 → 部署新版本，成本高昂且周期长。Skill 改变了这一点——编辑一个 Markdown 文件，模型的行为在下次调用时即刻改变，成本为零。

这就像一个可热插拔的 LoRA 适配器，不需要训练，只需用自然语言编辑文件。

### 核心公式

> **好的 Skill = 专家独有知识 − 模型已掌握的知识**

Skill 的价值取决于它的**知识增量**（knowledge delta）——它提供的内容与模型本身已掌握知识之间的差距。

- **专家独有知识**：决策树、权衡取舍、边界情况、反模式、领域特定思维框架——这些需要多年经验积累
- **模型已掌握的知识**：基础概念、标准库用法、常见编程模式、通用最佳实践

当 Skill 在解释"什么是 PDF"或"怎么写 for 循环"时，它是在压缩模型已经知道的知识，这是**token 浪费**——上下文窗口是与系统提示、对话历史、其他 Skill 共享的公共资源。

### 工具 vs Skill

| 概念 | 本质 | 功能 | 示例 |
|------|------|------|------|
| 工具（Tool） | 模型能做什么 | 执行动作 | bash、read_file、web_search |
| Skill | 模型知道怎么做 | 引导决策 | PDF 处理、前端设计、文档创建 |

工具定义能力边界——没有 bash 工具，模型就无法执行命令。Skill 注入知识——没有前端设计 Skill，模型产出的是平庸 UI。

> **通用 Agent + 优秀 Skill = 领域专家 Agent**

同一个模型，加载不同的 Skill，就变成不同的领域专家。

### Skill 中的三类知识

| 类型 | 定义 | 处理方式 |
|------|------|----------|
| **专家知识（Expert）** | 模型确实不知道的 | 必须保留——这是 Skill 的价值所在 |
| **激活知识（Activation）** | 模型知道但可能想不到 | 简短保留即可——起到提醒作用 |
| **冗余知识（Redundant）** | 模型肯定知道的 | 应该删除——浪费 token |

Skill 设计的艺术在于：最大化专家知识，精简使用激活知识，无情删除冗余知识。

好的 Skill 的知识比例大致为：专家 >70%，激活 <20%，冗余 <10%。

## D1: Knowledge Delta — 知识增量（20 分）

**这是最重要的维度。** Skill 是否提供了真正的专家知识？

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-5 | 解释模型已知的基础知识（什么是 X、如何写代码、标准库教程） |
| 6-10 | 混合：有些专家知识被显而易见的内容稀释 |
| 11-15 | 主要是专家知识，冗余极少 |
| 16-20 | 纯知识增量——每一段都配得上它消耗的 token |

### 红旗信号（直接扣到 ≤5 分）

- "什么是 [基础概念]" 的章节
- 标准操作的逐步教程
- 解释如何使用常见库
- 通用最佳实践（"写干净的代码"、"处理错误"）
- 行业标准术语的定义

### 绿旗信号（高分指标）

- 非显而易见选择的决策树（"当 X 失败时，尝试 Y，因为 Z"）
- 只有专家才知道的权衡（"A 更快但 B 能处理边界情况 C"）
- 来自真实经验的边界情况
- "NEVER 做 X，因为 [非显而易见的原因]"
- 领域特定的思维框架

### 评估方法

对每个章节问三个问题：

1. "模型已经知道这个吗？"
2. "这是在向模型解释，还是在帮模型解释？"
3. 统计专家段落 vs 激活段落 vs 冗余段落的数量

## D2: Mindset + Appropriate Procedures — 思维模式 + 领域流程（15 分）

Skill 是否传递了专家的**思维模式**以及**必要的领域特定流程**？

专家和新手的区别不在于"知道怎么操作"，而在于"如何思考问题"。但光有思维模式也不够——当模型缺乏领域特定的流程知识时，光会思考也做不对。

### 三种流程的价值对比

| 类型 | 示例 | 价值 |
|------|------|------|
| **思维模式** | "在设计之前，先问：什么让这个设计令人难忘？" | 高——塑造决策方式 |
| **领域特定流程** | "OOXML 工作流：解包 → 编辑 XML → 验证 → 打包" | 高——模型可能不知道这个 |
| **通用流程** | "第一步：打开文件，第二步：编辑，第三步：保存" | 低——模型已经知道 |

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-3 | 只有模型已知的通用流程 |
| 4-7 | 有领域流程但缺乏思维框架 |
| 8-11 | 较好的平衡：思维模式 + 领域特定工作流 |
| 12-15 | 专家级：塑造思维 AND 提供模型不知道的流程 |

### 有价值的领域流程示例

模型没有被训练过的操作序列，比如：

```
### 红线修订工作流（模型不会知道这个顺序）
1. 转为 markdown：`pandoc --track-changes=all`
2. 将文本映射到 XML：在 document.xml 中 grep 文本
3. 分批实现修改，每批 3-10 个
4. 打包并验证：检查所有修改是否已应用
```

### 冗余的通用流程示例

```
第一步：打开文件
第二步：找到章节
第三步：进行修改
第四步：保存并测试
```

这种内容模型完全知道，写在 Skill 里就是浪费。

### 评估方法

1. 它是否告诉模型**思考什么**？（思维模式）
2. 它是否告诉模型**怎么做它不会做的事**？（领域流程）

好的 Skill 在需要时两者都提供。

## D3: Anti-Pattern Quality — 反模式质量（15 分）

Skill 是否有有效的 NEVER 列表？

### 为什么这很重要

专家知识的一半是知道**什么不能做**。一个资深设计师看到白底紫渐变会本能地皱眉——"太 AI 生成了"。这种对"绝对不能做什么"的直觉来自踩过无数坑。

模型没有踩过这些坑。它不知道 Inter 字体被滥用了，不知道紫渐变是 AI 生成内容的标志。好的 Skill 必须明确指出这些"绝对不要"。

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-3 | 没有提到任何反模式 |
| 4-7 | 通用警告（"避免错误"、"小心"、"考虑边界情况"） |
| 8-11 | 具体的 NEVER 列表，附带部分原因 |
| 12-15 | 专家级反模式，附带 WHY——只有经验才能教会的知识 |

### 专家级反模式示例（具体 + 有原因）

```markdown
NEVER 使用通用的 AI 生成美学，例如：
- 过度使用的字体族（Inter、Roboto、Arial）
- 老套的配色方案（特别是白底紫渐变）
- 可预测的布局和组件模式
- 所有元素都用默认 border-radius
```

### 弱反模式示例（模糊，无原因）

```markdown
避免犯错。
小心处理边界情况。
不要写糟糕的代码。
```

### 评估方法

问自己：一个专家看到这个反模式列表会不会说"是的，这是我踩坑学到的"？还是会说"这不是显而易见的吗"？

## D4: Specification Compliance — 规范合规性，特别是 Description（15 分）

Skill 是否遵循官方格式要求？**特别关注 description 字段的质量。**

### 为什么 description 是最重要的字段

```
┌─────────────────────────────────────────────────────────────────────┐
│  SKILL 激活流程                                                      │
│                                                                     │
│  用户请求 → Agent 看到所有 Skill 的 description → 决定激活哪个       │
│             （只能看到 description，看不到正文！）                    │
│                                                                     │
│  如果 description 不匹配 → Skill 永远不会被加载                     │
│  如果 description 模糊 → Skill 可能在该用时没被触发                 │
│  如果 description 缺关键词 → Skill 对 Agent 不可见                  │
└─────────────────────────────────────────────────────────────────────┘
```

残酷的事实：一个内容完美但 description 糟糕的 Skill 是**无用的**——它永远不会被激活。description 是告诉 Agent "在这些场景下用我"的**唯一机会**。

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-5 | 缺少 frontmatter 或格式无效 |
| 6-10 | 有 frontmatter 但 description 模糊或不完整 |
| 11-13 | 有效 frontmatter，description 有 WHAT 但 WHEN 不足 |
| 14-15 | 完美：全面的 description，包含 WHAT、WHEN 和触发关键词 |

### Description 必须回答三个问题

1. **WHAT**：这个 Skill 做什么？（功能）
2. **WHEN**：什么情况下应该使用？（触发场景）
3. **KEYWORDS**：哪些词应该触发这个 Skill？（可搜索的术语）

### 优秀的 description 示例

```yaml
description: "Comprehensive document creation, editing, and analysis
with support for tracked changes, comments, formatting preservation,
and text extraction. When Claude needs to work with professional
documents (.docx files) for: (1) Creating new documents,
(2) Modifying or editing content, (3) Working with tracked changes,
(4) Adding comments, or any other document tasks"
```

分析：
- WHAT：创建、编辑、分析、修订追踪、评论
- WHEN："When Claude needs to work with... for: (1)... (2)... (3)..."
- KEYWORDS：.docx files、tracked changes、professional documents

### 糟糕的 description 示例

```yaml
description: "处理文档相关功能"
```

问题：WHAT 模糊（"文档相关功能"——具体什么？）、WHEN 缺失、KEYWORDS 缺失。

### Description 质量检查清单

- [ ] 列出了具体能力（不只是"帮助处理 X"）
- [ ] 包含明确的触发场景（"Use when..."、"When user asks for..."）
- [ ] 包含可搜索的关键词（文件扩展名、领域术语、动作动词）
- [ ] 足够具体，让 Agent 知道**确切**什么时候使用
- [ ] 包含必须使用的场景（不只是"可以使用"）

### Frontmatter 基本要求

- `name`：小写，字母数字 + 连字符，≤64 字符
- `description`：**最关键的字段**——决定 Skill 是否会被使用

## D5: Progressive Disclosure — 渐进式加载（15 分）

Skill 是否实现了正确的内容分层？

### 三层加载体系

```
第 1 层：元数据（始终在内存中）
         只有 name + description
         每个 Skill 约 100 token

第 2 层：SKILL.md 正文（触发后加载）
         详细指南、代码示例、决策树
         理想：< 500 行

第 3 层：引用资源（按需加载）
         scripts/、references/、assets/
         无限制
```

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-5 | 所有内容都堆在 SKILL.md 中（>500 行，无结构） |
| 6-10 | 有引用文件但不清楚何时加载 |
| 11-13 | 较好的分层，有必须加载的触发器 |
| 14-15 | 完美：决策树 + 明确触发器 + "不要加载"指引 |

### 加载触发器质量

| 质量等级 | 特征 |
|----------|------|
| 差 | 引用文件列在末尾，没有加载指引 |
| 一般 | 有一些触发器但未嵌入工作流 |
| 好 | 工作流步骤中有必须加载的触发器 |
| 优秀 | 场景检测 + 条件触发 + "不要加载"指引 |

### 加载的核心矛盾

```
加载太少 ◄─────────────────────────────────► 加载太多
- 引用文件闲置不用                         - 浪费上下文空间
- Agent 不知道何时加载                     - 无关信息稀释关键内容
- 知识存在但永远不会被访问                 - 不必要的 token 开销
```

### 好的加载触发器示例（嵌入工作流）

```markdown
### 创建新文档

**MANDATORY - READ ENTIRE FILE**: 在继续之前，你必须完整阅读
[`docx-js.md`](docx-js.md)（约 500 行），从头到尾。
**NEVER 设置任何范围限制来读取此文件。**

**不要加载** `ooxml.md` 或 `redlining.md` 用于此任务。
```

### 差的加载触发器示例（仅列出）

```markdown
## 引用文件
- docx-js.md - 用于创建文档
- ooxml.md - 用于编辑
- redlining.md - 用于追踪修订
```

对于简单的 Skill（无引用文件，<100 行），根据简洁性和自包含性评分。

## D6: Freedom Calibration — 自由度校准（15 分）

约束的严格程度是否与任务的脆弱性匹配？

不同的任务需要不同程度的约束。核心原则是：**根据任务出错的后果严重程度来匹配自由度。**

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-5 | 严重不匹配（创意任务用僵化脚本，脆弱操作用模糊指引） |
| 6-10 | 部分匹配，有一些错配 |
| 11-13 | 大多数场景校准良好 |
| 14-15 | 全程自由度校准完美 |

### 自由度光谱

| 任务类型 | 应该有 | 原因 | 示例 Skill |
|----------|--------|------|------------|
| 创意/设计 | 高自由度 | 多种有效方案，差异化即价值 | frontend-design |
| 代码审查 | 中等自由度 | 有原则但需要判断 | code-review |
| 文件格式操作 | 低自由度 | 一个字节错误就损坏文件，一致性至关重要 | docx、xlsx、pdf |

### 高自由度示例（文本指令）

```markdown
Commit to a BOLD aesthetic direction. Pick an extreme: brutally minimal,
maximalist chaos, retro-futuristic, organic natural...
```

### 中等自由度示例（伪代码或参数化）

```markdown
Review priority:
1. Security vulnerabilities (must fix)
2. Logic errors (must fix)
3. Performance issues (should fix)
4. Maintainability (optional)
```

### 低自由度示例（精确脚本，确切步骤）

```markdown
**MANDATORY**: Use exact script in `scripts/create-doc.py`
Parameters: --title "X" --author "Y"
Do NOT modify the script.
```

### 评估方法

问自己："如果 Agent 犯了错，后果是什么？"

- 后果严重 → 低自由度
- 后果轻微 → 高自由度

## D7: Pattern Recognition — 模式识别（10 分）

Skill 是否遵循了已建立的官方设计模式？

通过分析 17 个官方 Skill，提炼出 5 种主要设计模式：

### 五种设计模式

| 模式 | 约行数 | 关键特征 | 示例 | 适用场景 |
|------|--------|----------|------|----------|
| **Mindset（思维）** | ~50 | 思维 > 技术，强 NEVER 列表，高自由度 | frontend-design | 需要品味的创意任务 |
| **Navigation（导航）** | ~30 | 极简 SKILL.md，路由到子文件 | internal-comms | 多个不同子场景 |
| **Philosophy（哲学）** | ~150 | 两步走：哲学 → 表达，强调工艺 | canvas-design | 需要原创性的艺术/创作 |
| **Process（流程）** | ~200 | 分阶段工作流，检查点，中等自由度 | mcp-builder | 复杂的多步项目 |
| **Tool（工具）** | ~300 | 决策树，代码示例，低自由度 | docx、pdf、xlsx | 对特定格式的精确操作 |

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-3 | 无可识别模式，结构混乱 |
| 4-6 | 部分遵循某种模式但有显著偏离 |
| 7-8 | 清晰的模式，有轻微偏离 |
| 9-10 | 对合适模式的精通运用 |

### 模式选择指南

| 你的任务特征 | 推荐模式 |
|-------------|----------|
| 需要品味和创意 | Mindset（~50 行） |
| 需要原创性和工艺质量 | Philosophy（~150 行） |
| 有多个不同子场景 | Navigation（~30 行） |
| 复杂多步项目 | Process（~200 行） |
| 对特定格式的精确操作 | Tool（~300 行） |

## D8: Practical Usability — 实际可用性（15 分）

Agent 能否实际有效地使用这个 Skill？

### 评分标准

| 分数 | 标准 |
|------|------|
| 0-5 | 令人困惑、不完整、矛盾或未经测试的指引 |
| 6-10 | 可用但有明显缺口 |
| 11-13 | 对常见场景有清晰指引 |
| 14-15 | 全面覆盖，包括边界情况和错误处理 |

### 检查清单

- **决策树**：多路径场景是否有清晰的路由指引？
- **代码示例**：它们真的能运行吗？还是会报错伪代码？
- **错误处理**：主方案失败怎么办？有兜底方案吗？
- **边界情况**：不常见但现实的场景是否覆盖？
- **可操作性**：Agent 能立即行动，还是需要自己摸索？

### 好的可用性示例（决策树 + 兜底）

```markdown
| 任务 | 主工具 | 兜底工具 | 何时使用兜底 |
|------|--------|----------|-------------|
| 读取文本 | pdftotext | PyMuPDF | 需要布局信息时 |
| 提取表格 | camelot-py | tabula-py | camelot 失败时 |

常见问题：
- 扫描版 PDF：pdftotext 返回空白 → 先用 OCR
- 加密 PDF：权限错误 → 用 PyMuPDF 加密码
```

### 差的可用性示例（模糊）

```markdown
使用适当的工具处理 PDF。
正确处理错误。
考虑边界情况。
```

## 常见失败模式

### 模式 1：教程型

```
症状：解释什么是 PDF、Python 怎么工作、基础库用法
根因：作者认为 Skill 应该"教"模型
修复：模型已经知道这些。删除所有基础解释。
     聚焦于专家决策、权衡取舍和反模式。
```

### 模式 2：堆砌型

```
症状：SKILL.md 超过 800 行，所有内容都塞在里面
根因：没有渐进式加载设计
修复：核心路由和决策树放在 SKILL.md（<300 行为佳）
     详细内容放在 references/，按需加载
```

### 模式 3：孤儿引用型

```
症状：references 目录存在但文件从不被加载
根因：没有明确的加载触发器
修复：在工作流决策点添加 "MANDATORY - READ ENTIRE FILE"
     添加 "Do NOT Load" 防止过度加载
```

### 模式 4：清单流程型

```
症状：第一步、第二步、第三步……机械式流程
根因：作者用流程而非思维框架来思考
修复：转化为"在做 X 之前，先问自己……"
     聚焦于决策原则，而非操作序列
```

### 模式 5：模糊警告型

```
症状："小心"、"避免错误"、"考虑边界情况"
根因：作者知道可能出问题但没有具体说明
修复：具体的 NEVER 列表，带实例和非显而易见的原因
     "NEVER 使用 X，因为 [需要经验才能学到的具体问题]"
```

### 模式 6：隐形 Skill 型

```
症状：内容很好但 Skill 很少被激活
根因：description 模糊、缺关键词、缺触发场景
修复：description 必须回答 WHAT、WHEN 并包含 KEYWORDS
     "Use when..." + 具体场景 + 可搜索术语
```

### 模式 7：位置错误型

```
症状："何时使用此 Skill" 的信息在正文中，不在 description 里
根因：误解三层加载机制
修复：将所有触发信息移到 description 字段
     正文只在触发决策做出之后才被加载
```

### 模式 8：过度工程型

```
症状：包含 README.md、CHANGELOG.md、INSTALLATION_GUIDE.md、CONTRIBUTING.md
根因：把 Skill 当成软件项目
修复：删除所有辅助文件。只保留 Agent 执行任务所需的内容。
     不需要关于 Skill 自身的文档。
```

### 模式 9：自由度错配型

```
症状：创意任务用僵化脚本，脆弱操作用模糊指引
根因：没有考虑任务脆弱性
修复：创意任务给高自由度（原则而非步骤）
     脆弱操作给低自由度（精确脚本，不允许修改参数）
```

## 元问题

评估任何 Skill 时，始终回到这个根本问题：

> **"一个领域专家看了这个 Skill，会不会说：'是的，这浓缩了我多年积累的经验'？"**

如果答案是肯定的这个 Skill 有真正价值。如果答案是否定的，它在压缩模型已经知道的东西。

最好的 Skill 是**压缩的专家大脑**——它把设计师 10 年的审美积累压缩成 43 行，或者把文档专家的运营经验压缩成 200 行决策树。

被压缩的必须是模型不具备的知识。否则就是垃圾压缩。

## 评估流程

### 第一步：知识增量扫描

完整阅读 SKILL.md，对每个章节标记：

- **[E] 专家**：模型确实不知道——有价值
- **[A] 激活**：模型知道但简短提醒有用——可接受
- **[R] 冗余**：模型肯定知道——应删除

计算大致比例 E:A:R

### 第二步：结构分析

- [ ] 检查 frontmatter 有效性
- [ ] 统计 SKILL.md 总行数
- [ ] 列出所有引用文件及其大小
- [ ] 识别 Skill 遵循的模式
- [ ] 检查加载触发器（如有引用文件）

### 第三步：逐维度评分

对 8 个维度分别：找到具体证据（引用相关行）→ 打分并附一句话理由 → 如果不是满分，记录具体改进建议。

### 第四步：计算总分和等级

### 第五步：生成评估报告

报告结构：总结（总分、等级、模式、知识比例、一句话评价）→ 维度得分表 → 关键问题 → Top 3 改进建议 → 详细分析（对低于 80% 的维度展开）。
