# Claude Code 记忆功能机制深度分析

## 一、系统全局概览

Claude Code 的持久化记忆系统是一个多层次、多来源的架构，设计目标是让 AI 助手**跨会话保留用户偏好、项目知识和工作上下文**。它不是一个简单的 key-value 存储，而是一个包含文件发现、相关性评分、团队同步、自动整合的完整生态系统。

整体由三大子系统构成：

```
┌──────────────────────────────────────────────────────────────┐
│  Traditional Memory（CLAUDE.md 体系）                          │
│  ── 基于文件发现的静态指令注入，类似 .editorconfig 对编辑器的作用 │
├──────────────────────────────────────────────────────────────┤
│  AutoMem / MEMDIR（自动记忆系统）                              │
│  ── AI 自主提取和管理的结构化记忆，含主题文件、相关性选择       │
├──────────────────────────────────────────────────────────────┤
│  TeamMem（团队记忆）                                          │
│  ── 组织级共享记忆，通过 API 与服务端双向同步                   │
└──────────────────────────────────────────────────────────────┘
```

## 二、Traditional Memory：CLAUDE.md 文件体系

### 2.1 文件层次与优先级

系统从多个位置发现和加载记忆文件，形成一个层叠的优先级体系：

```
最低优先级
┌────────────────────────────────────────────────────────┐
│  Managed（企业管理员部署）                                │
│  /etc/claude-code/CLAUDE.md                             │
│  /etc/claude-code/.claude/rules/*.md                    │
├────────────────────────────────────────────────────────┤
│  User（用户全局配置）                                    │
│  ~/.claude/CLAUDE.md                                    │
│  ~/.claude/rules/*.md                                   │
├────────────────────────────────────────────────────────┤
│  Project（项目级，签入版本控制）                          │
│  {CWD→root}/CLAUDE.md                                   │
│  {CWD→root}/.claude/CLAUDE.md                           │
│  {CWD→root}/.claude/rules/*.md                          │
├────────────────────────────────────────────────────────┤
│  Local（本地私有，不签入）                               │
│  {CWD→root}/CLAUDE.local.md                             │
│  {CWD→root}/.claude/CLAUDE.local.md                     │
└────────────────────────────────────────────────────────┘
最高优先级
```

**目录遍历策略**：从 CWD 向上遍历到文件系统根，倒序处理（根先加载，CWD 最后加载）。在 LLM 上下文中，越靠后的内容权重越大，所以离工作目录越近的规则越优先。

### 2.2 @include 引用机制

CLAUDE.md 文件支持通过 `@path` 语法引用外部文件：

```markdown
# 项目规范
@./docs/coding-standards.md
@~/global-rules/typescript.md
@/etc/company/security-policy.md
```

技术实现细节：
- 使用 marked lexer 解析 markdown token 提取路径
- 跳过代码块和 HTML 注释中的 `@` 引用（防止误解析）
- 最大递归深度为 5 层，防止循环引用
- 支持 `#fragment` 后缀剥离
- 支持空格转义（`\ `）
- 外部引用（CWD 外的文件）需要用户通过 `hasClaudeMdExternalIncludesApproved` 显式批准

### 2.3 条件规则

`.claude/rules/*.md` 文件可以包含 frontmatter 中的 `paths` 字段：

```yaml
---
paths:
  - "src/**/*.tsx"
  - "!src/**/*.test.tsx"
---
# React 组件规范
所有 React 组件必须使用 functional component...
```

这些"条件规则"只在 AI 操作匹配 glob 模式的文件时注入上下文。匹配使用 `ignore` 库（`.gitignore` 语义）。

### 2.4 注入上下文的方式

记忆内容通过 `prependUserContext()` 作为第一条 user message 注入：

```typescript
// 格式化为 XML 标签包裹的系统提醒
`<system-reminder>
As you answer the user's questions, you can use the following context:
# claudeMd
Contents of ~/.claude/CLAUDE.md (User instructions):
${userClaudeMd}

Contents of ./CLAUDE.md (Project instructions):
${projectClaudeMd}

# currentDate
Today's date is 2026-04-06.

IMPORTANT: this context may or may not be relevant to the user's query.
</system-reminder>`
```

## 三、AutoMem / MEMDIR：自动记忆系统

### 3.1 目录结构

自动记忆存储在用户主目录下的项目特定路径：

```
~/.claude/projects/<sanitized-cwd-path>/memory/
├── MEMORY.md           # 入口文件（索引），最大 200 行 / 25KB
├── user-preferences.md # 主题文件（含 frontmatter）
├── project-arch.md     # 主题文件
├── coding-feedback.md  # 主题文件
└── team/               # 团队记忆子目录（API 同步）
    ├── MEMORY.md       # 团队入口文件
    └── shared-conventions.md
```

路径通过 `getAutoMemPath()` 获取（memoized），基于 `getOriginalCwd()` 标准化处理后生成唯一路径。

### 3.2 记忆类型分类

系统定义了四种语义类型，每个主题文件在 frontmatter 中声明其类型：

| 类型 | 用途 | 典型内容 |
|------|------|---------|
| `user` | 用户身份/偏好/风格 | "喜欢简洁注释"、"偏好函数式编程" |
| `feedback` | 用户反馈和修正 | "不要用 var"、"commit message 用中文" |
| `project` | 项目事实和架构 | "使用 monorepo"、"API 在 src/api/ 目录" |
| `reference` | 参考资料和文档链接 | API 文档 URL、架构决策记录位置 |

### 3.3 主题文件格式

```markdown
---
title: TypeScript 编码偏好
type: feedback
---

## 变量命名
用户偏好 camelCase，不使用匈牙利命名法。

## 错误处理
总是使用 try-catch 包裹 async 调用，不要用 .catch()。

## 导入顺序
1. Node.js 内置模块
2. 第三方库
3. 项目内部模块
```

### 3.4 入口文件（MEMORY.md）的特殊处理

MEMORY.md 是索引文件，有特殊的截断保护：
- 最大 200 行
- 最大 25KB
- 通过 `truncateEntrypointContent()` 强制执行

这确保索引文件不会占用过多上下文窗口。

### 3.5 什么应该存储 vs 什么不应该存储

系统内置了明确的指导（`memoryTypes.ts`）：

**应该存储的**：
- 无法从代码推导的用户偏好
- 用户明确表达的反馈和修正
- 项目特有的约定（不在 README 中记录的）
- 外部参考资料链接

**不应该存储的**：
- 可以从代码结构推导的信息（如"这是一个 React 项目"）
- 临时的会话上下文
- 正在进行的 debugging 细节
- Git 历史中已有的信息

## 四、相关性评分与智能选择

### 4.1 核心机制：findRelevantMemories

系统不是盲目注入所有记忆，而是用 AI 做**智能选择**：

```
┌─────────────────────────────────────────────────────────┐
│  1. scanMemoryFiles()                                     │
│     读取所有 .md 文件的 frontmatter（最多 200 个）          │
│     按 mtime 最新优先排序                                  │
│                     ↓                                      │
│  2. formatMemoryManifest()                                │
│     将文件列表格式化为文本清单                              │
│     包含标题、类型、修改时间                                │
│                     ↓                                      │
│  3. Side Query（发送给 Sonnet 模型）                       │
│     "以下是可用的记忆文件，当前用户查询是 X，                │
│      请选择最多 5 个最相关的记忆"                           │
│                     ↓                                      │
│  4. 返回 RelevantMemory[]                                 │
│     每个包含 path 和 mtime                                 │
└─────────────────────────────────────────────────────────┘
```

### 4.2 时效性感知

`memoryAge.ts` 实现了记忆的"新鲜度"评估：

- `memoryAgeDays(mtime)` — 计算记忆的天数年龄
- `memoryFreshnessText(days)` — 生成人类可读文本（如 "2 days old"、"3 weeks old"）
- `memoryFreshnessNote(days)` — 对超过 1 天的记忆生成 staleness 警告

这些信息会传递给 LLM，让它知道某条记忆可能已经过时，需要谨慎使用。

### 4.3 注入路径

相关记忆通过两种方式注入上下文：

**方式 A：系统提示注入**（默认）
通过 `loadMemoryPrompt()` 将记忆内容加入 system prompt 的 `memory` section。

**方式 B：Attachments 注入**（实验）
当 `tengu_moth_copse` feature flag 启用时，通过每轮 attachments 传递记忆内容，而非注入系统提示。此时 `filterInjectedMemoryFiles()` 会过滤掉 AutoMem 和 TeamMem 类型避免重复。

## 五、记忆的 CRUD 生命周期

### 5.1 创建：自动提取

后台记忆提取是系统最精妙的设计之一：

```
┌─────────────────────────────────────────────────────────┐
│            每轮查询循环结束后                              │
│                     ↓                                     │
│  runForkedAgent()                                        │
│  （创建 forked 子代理，共享 prompt cache 以降低成本）       │
│                     ↓                                     │
│  子代理分析对话内容                                       │
│  决定是创建新记忆文件还是更新现有文件                       │
│                     ↓                                     │
│  写入 ~/.claude/projects/<path>/memory/ 目录              │
└─────────────────────────────────────────────────────────┘
```

关键设计细节：
- **互斥锁**：使用 closure-scoped 状态变量防止与主代理的 memory 写入冲突
- **工具约束**：提取代理只能使用有限的工具集（不能执行 shell、不能读文件）
- **成本优化**：forked agent 共享父级的 prompt cache prefix，大幅降低 API 成本

### 5.2 读取：loadMemoryPrompt()

```typescript
async function loadMemoryPrompt() {
  // 1. 获取所有发现的 memory 文件（memoized）
  const files = await getMemoryFiles()
  
  // 2. 格式化为结构化文本
  const formatted = getClaudeMds(files)
  // 每个文件呈现为: "Contents of <path> (<description>):\n\n<content>"
  
  // 3. 添加指令前缀
  return `${MEMORY_INSTRUCTION_PROMPT}\n\n${formatted}`
}
```

`MEMORY_INSTRUCTION_PROMPT` 的核心指令：

> "Codebase and user instructions are shown below. Be sure to adhere to these instructions. IMPORTANT: These instructions OVERRIDE any default behavior..."

### 5.3 更新：用户命令

- `/memory` 命令 — 打开 UI 界面让用户手动编辑 memory 文件
- `/remember` 技能 — 允许用户审阅并提升记忆条目

### 5.4 删除与整合：AutoDream

AutoDream 是记忆的"睡眠整合"机制，模拟人类大脑在睡眠时整理记忆的过程。

## 六、AutoDream：自动记忆整合

### 6.1 触发条件

两个条件必须同时满足：
- **时间门控**：距上次整合至少 24 小时
- **会话门控**：至少 5 个新会话

### 6.2 四阶段整合流程

```
┌──────────────────────────────────────────────┐
│  Phase 1: Orient（定向）                       │
│  理解现有记忆结构，识别重复和过时内容           │
│                    ↓                           │
│  Phase 2: Gather（收集）                       │
│  回顾近期会话 transcript                       │
│                    ↓                           │
│  Phase 3: Consolidate（整合）                  │
│  合并冗余记忆，提炼关键知识，更新过时信息       │
│                    ↓                           │
│  Phase 4: Prune（修剪）                        │
│  删除不再相关的记忆文件                        │
└──────────────────────────────────────────────┘
```

### 6.3 整合锁

使用 mtime-based lock 防止多会话并发整合：
- 整合开始时更新 lock 文件的 mtime
- 其他会话检查 lock mtime 决定是否可以开始
- 如果整合被 kill，回滚 lock mtime 让下次会话可重试

## 七、Session Memory：会话级短期记忆

### 7.1 设计目的

Session Memory 独立于 MEMDIR，用于在自动压缩（compaction）时**保留关键的会话上下文**。当对话被压缩后，重要的结构化信息不会丢失。

### 7.2 模板结构

会话记忆文件包含固定的段落：

```markdown
# Session Memory

## Title
当前任务的简短标题

## Current State
当前进度状态

## Task Spec
任务规格说明

## Files
涉及的关键文件列表

## Workflow
工作流程记录

## Errors
遇到的错误和解决方案

## Codebase
代码库关键信息

## Learnings
学到的经验教训

## Key Results
关键成果

## Worklog
工作日志
```

### 7.3 触发条件

基于 token 使用量阈值自动触发提取——当对话变长、即将触发 compaction 时，先将关键信息压缩到 session memory 文件中。

## 八、TeamMem：团队记忆系统

### 8.1 架构设计

团队记忆存储在 `memory/team/` 子目录中，通过 GitHub OAuth 认证，以 GitHub repo 为作用域在团队成员间同步共享。

```
┌─────────┐     push/pull      ┌─────────────┐
│  User A │ ◄──────────────► │  API Server  │
└─────────┘                    └──────┬──────┘
                                      │
┌─────────┐     push/pull      ┌─────┴──────┐
│  User B │ ◄──────────────► │  API Server  │
└─────────┘                    └─────────────┘
```

### 8.2 同步机制

**Pull（拉取）**：
- 从服务端获取最新团队记忆
- 使用 ETag 实现高效增量检查（304 Not Modified）
- 只下载变更的内容

**Push（推送）**：
- 本地变更检测后上传到服务端
- 基于 ETag 的乐观锁（optimistic locking）处理冲突
- 变更以 delta 包形式批量上传

**文件监视**：
- 使用 `fs.watch` 监视团队记忆目录
- 变更事件经过 debounce 处理后触发推送
- 防止频繁写入导致的网络风暴

### 8.3 安全机制

团队记忆的安全性要求更高（内容可能来自他人）：

- **路径遍历检测**：检查 `..` 段落，防止写入 memory 目录外
- **Symlink 解析**：先 resolve symlink 再验证路径，防止符号链接逃逸
- **空字节检查**：防止 null byte 注入
- **键名验证**：只允许合法字符（字母、数字、连字符、下划线）
- **Secret Scanning**：上传前执行密钥扫描，防止意外泄露 API keys

### 8.4 提示构建

`buildCombinedMemoryPrompt()` 将私有记忆和团队记忆合并：

```xml
<!-- 私有记忆 -->
Contents of ~/.claude/projects/myproject/memory/coding-style.md:
...

<!-- 团队记忆（用 XML 标签区分来源） -->
<team-memory-content source="shared">
Contents of ~/.claude/projects/myproject/memory/team/api-conventions.md:
...
</team-memory-content>
```

## 九、KAIROS 模式：助手日志

### 9.1 概念

KAIROS 是一种"助手日志"范式，结合了 proactive/autonomous 工作模式。AI 维护自己的每日工作日志，支持：

- 按日期命名的追加式日志文件
- 夜间蒸馏（nightly distillation）将日志精简为要点
- 结合 proactive 模式实现自主工作

### 9.2 与 Memory 的关系

在 KAIROS 模式下，系统提示的组装逻辑简化，直接注入 `loadMemoryPrompt()` + proactive section，跳过常规的 section registry 流程。

## 十、缓存与生命周期管理

### 10.1 Memoization 策略

关键函数使用 memoize，会话内只计算一次：
- `getMemoryFiles()` — 记忆文件列表
- `getAutoMemPath()` — 记忆目录路径
- `getUserContext()` — 完整用户上下文

### 10.2 缓存失效

两种失效方式：
- `clearMemoryFileCaches()` — 纯缓存失效（worktree 切换、设置同步时使用）
- `resetGetMemoryFilesCache(reason)` — 失效 + 触发 InstructionsLoaded hook（compaction 后重加载）

### 10.3 与 Compaction 的交互

自动压缩后，必须调用 `resetGetMemoryFilesCache('compact')` 确保 memory 文件重新加载到新的压缩上下文中。这是因为压缩会重写整个对话历史，原有的 memory 引用可能已经丢失。

### 10.4 Prompt Cache 定位

Memory 内容位于 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 之后，与静态内容分离：
- 静态部分可以使用 `scope: 'global'` 进行跨用户缓存
- Memory 部分是用户特异性内容，每次需要重新处理

## 十一、安全模型

### 11.1 外部引用控制

- `claudeMdExcludes` 设置允许用户排除特定路径的 CLAUDE.md 文件
- External include（@路径引用 CWD 外的文件）需要显式用户批准

### 11.2 注入攻击防护

- HTML 注释剥离：防止通过 `<!-- -->` 隐藏恶意指令
- 系统提示中提醒 LLM 对工具结果中的 prompt injection 尝试保持警惕

### 11.3 二进制文件过滤

`TEXT_FILE_EXTENSIONS` 白名单防止加载非文本内容到上下文中。

### 11.4 团队记忆安全

如上文第八章所述，团队记忆有完整的路径安全检查和 secret scanning 机制。

## 十三、设计理念总结

Claude Code 的记忆系统体现了几个核心设计理念：

1. **记忆应该像人脑一样工作**：有短期（session memory）、长期（MEMDIR）、共享（team memory）三种记忆，有遗忘（aging）、整合（consolidation）、回忆（retrieval）的完整周期。

2. **不重复存储可推导的信息**：记忆系统只存储无法从项目代码/git 历史推导的知识——用户偏好、明确的反馈、无法从代码看出的约定。

3. **相关性优于完整性**：不是把所有记忆都塞给 AI，而是用 AI 本身（Sonnet）来选择最相关的记忆。这在记忆文件很多时尤为重要。

4. **安全性贯穿始终**：从 @include 的外部文件批准，到团队记忆的 secret scanning，再到路径遍历防护，安全考虑无处不在。

5. **成本意识驱动设计**：forked agent 共享 prompt cache、memoize 减少重复计算、ETag 减少网络传输——每个设计决策都在平衡功能和成本。
