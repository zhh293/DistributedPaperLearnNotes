# RAG（Retrieval-Augmented Generation）检索增强生成深度解析

## 一、RAG 概述与发展历程

### 1.1 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与大语言模型（LLM）生成能力相结合的技术范式。其核心思想是：在 LLM 生成回答之前，先从外部知识库中检索相关信息，将检索到的上下文作为 Prompt 的一部分输入给模型，从而让模型基于真实、最新的知识进行回答，而不仅仅依赖其训练时学到的参数化知识。

RAG 的诞生源于 LLM 面临的几个核心问题：幻觉（Hallucination）——模型会生成看似合理但实际错误的内容；知识过时——模型的知识截止于训练数据的时间点；缺乏专业领域知识——通用模型在垂直领域的专业性不足；不可追溯——用户无法验证回答的来源。RAG 通过引入外部知识检索，为这些问题提供了一种优雅的解决方案。

### 1.2 发展历程

RAG 的概念最早由 Meta（Facebook AI Research）在 2020 年的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》中正式提出。此后经历了快速演进：

2020 年，RAG 论文发布，提出将参数化记忆（LLM）与非参数化记忆（外部文档库）结合的思路。2022-2023 年，随着 ChatGPT 的爆发和向量数据库（如 Pinecone、Milvus、Weaviate）的成熟，RAG 成为企业级 AI 应用的主流架构。2023 年下半年至今，RAG 技术快速迭代，出现了 Advanced RAG、Modular RAG、GraphRAG、Agentic RAG 等多种进阶范式。

### 1.3 RAG vs Fine-tuning vs Prompt Engineering

在将 LLM 适配到特定场景时，主要有三种路径：

Prompt Engineering 是最轻量的方式，通过精心设计提示词来引导模型输出，不需要额外数据或训练，但受限于上下文窗口长度。Fine-tuning 通过在特定数据集上继续训练模型来注入知识，适合需要模型学习特定风格或格式的场景，但成本高、数据准备复杂、且知识更新需要重新训练。RAG 则在推理时动态检索外部知识，兼具灵活性和准确性，是目前最具性价比的企业知识增强方案。

实践中，三者并非互斥，而是可以组合使用：先通过 Fine-tuning 让模型具备领域基础能力，再用 RAG 注入最新知识，最后通过 Prompt Engineering 优化输出格式。

## 二、RAG 架构范式演进

### 2.1 Naive RAG（朴素 RAG）

Naive RAG 是最基础的 RAG 实现，遵循"索引-检索-生成"（Indexing-Retrieval-Generation）的线性流程：

**索引阶段**：将文档进行分块（Chunking），通过 Embedding 模型将每个文本块转换为向量，存入向量数据库。

**检索阶段**：用户提问时，将问题同样通过 Embedding 模型转为向量，在向量数据库中进行相似度搜索，返回 Top-K 个最相关的文本块。

**生成阶段**：将检索到的文本块与用户问题拼接为 Prompt，交给 LLM 生成最终回答。

Naive RAG 的局限性非常明显：检索质量高度依赖 Embedding 模型和分块策略；对用户问题的理解停留在字面意义，缺乏深层语义理解；检索结果可能包含冗余或矛盾信息；生成阶段缺乏对检索结果的质量判断。

### 2.2 Advanced RAG（进阶 RAG）

Advanced RAG 针对 Naive RAG 的缺陷，在检索前、检索中、检索后三个阶段引入优化：

**Pre-Retrieval（检索前优化）**包括：查询重写（Query Rewriting）将模糊问题转化为清晰的检索意图；查询扩展（Query Expansion）生成多个相关查询以覆盖更多语义；查询分解（Query Decomposition）将复杂问题拆分为多个子问题分别检索；知识图谱增强，利用结构化知识补充语义信息。

**Retrieval（检索阶段优化）**包括：混合检索（Hybrid Search）结合稀疏检索（BM25）和稠密检索（向量搜索）；多路召回策略，从不同维度检索相关信息；自适应检索，根据问题类型动态调整检索策略。

**Post-Retrieval（检索后优化）**包括：重排序（Reranking）对检索结果进行精细化排序；上下文压缩（Context Compression）去除冗余信息，提取核心内容；结果过滤，基于相关性阈值过滤低质量结果。

### 2.3 Modular RAG（模块化 RAG）

Modular RAG 将 RAG 系统解构为可灵活组合的功能模块，每个模块可独立替换和升级。典型模块包括：

- 数据处理模块（解析、清洗、分块）
- 索引模块（向量索引、图索引、倒排索引）
- 查询理解模块（意图识别、查询改写）
- 检索模块（稠密检索、稀疏检索、混合检索）
- 重排序模块（Cross-Encoder、LLM-based Reranking）
- 生成模块（答案生成、引用追溯）
- 评估与反馈模块（自动评估、用户反馈收集）

模块化设计的优势在于：可以根据不同场景灵活组装流水线；每个模块可独立迭代优化；支持 A/B 测试比较不同模块实现的效果。

### 2.4 Agentic RAG

Agentic RAG 将 Agent 能力引入 RAG 系统，使系统具备自主决策能力：能够判断是否需要检索（有些问题 LLM 可以直接回答）；能够选择合适的检索策略和数据源；能够对检索结果进行批判性评估，决定是否需要再次检索；能够在多轮交互中逐步收敛到准确答案。这种范式将 RAG 从被动的"查-答"系统升级为主动的"思考-查-验-答"系统。

## 三、数据处理与分块策略

### 3.1 文档解析

文档解析是 RAG 流水线的第一步，其质量直接影响下游所有环节。不同格式的文档需要不同的解析策略：

**PDF 文档**是最常见也是最具挑战性的格式。解析难点包括：多栏排版的阅读顺序识别、表格结构的保持、图片中的文字提取（OCR）、页眉页脚的过滤。常用工具包括 PyPDF、pdfplumber（擅长表格）、Unstructured.io（综合能力强）、以及基于视觉模型的方案如 Nougat（学术论文解析效果好）。

**HTML/网页**需要处理 DOM 结构、去除广告和导航等噪声、保留语义标记（标题层级、列表结构、代码块等）。Beautiful Soup 和 Trafilatura 是常用工具。

**Office 文档**（Word、PPT、Excel）需要分别处理文本、格式信息、嵌入对象等。python-docx、python-pptx、openpyxl 等库可完成基础解析。

**结构化数据**（JSON、数据库记录）需要转化为自然语言描述或保持结构化格式以支持不同的检索方式。

### 3.2 分块策略（Chunking Strategies）

分块是 RAG 中至关重要的环节，分块质量直接决定了检索的精度和生成的质量。理想的分块应该满足：语义完整性（一个 chunk 表达一个完整的信息单元）、适当的粒度（不宜过长导致噪声多，也不宜过短导致信息碎片化）、上下文自足性（chunk 本身能被理解，不过度依赖上下文）。

#### 3.2.1 固定长度分块（Fixed-size Chunking）

这是最简单直接的方式，按固定字符数或 Token 数切分文本，通常设置一定的重叠（overlap）来避免信息断裂。典型参数为 chunk_size=512 tokens，overlap=50-100 tokens。优点是实现简单、计算可预测；缺点是完全忽略语义边界，可能在句子中间甚至单词中间切断。

#### 3.2.2 递归分块（Recursive Character Splitting）

LangChain 中最常用的策略，按照分隔符优先级递归切分：先尝试按双换行符（段落）切分，如果 chunk 仍然过长，再按单换行符切分，继续按句号、逗号切分，直到满足长度要求。这种方式在简单性和语义保持之间取得了较好的平衡。

#### 3.2.3 语义分块（Semantic Chunking）

基于文本语义相似度进行动态分块。核心思想是：计算相邻句子之间的语义相似度，当相似度出现显著下降时，认为这里是一个自然的语义边界，在此处切分。Greg Kamradt 提出的方法通过 Embedding 相邻句子并计算余弦相似度，设定阈值来确定分割点。这种方式能更好地保持语义完整性，但计算成本较高。

#### 3.2.4 文档结构感知分块

利用文档自身的结构信息（标题层级、Markdown 标记、HTML 标签等）进行智能分块。例如，按 Markdown 的标题层级切分，每个章节作为一个 chunk，保留标题作为 chunk 的元数据。这种方式特别适合有良好结构的技术文档和知识库文章。

#### 3.2.5 基于 LLM 的智能分块

使用 LLM 来判断文本的语义边界和主题转换点。虽然效果最好，但成本极高（每个文档都需要 LLM 调用），通常只在高价值、小规模文档集上使用。

#### 3.2.6 Meta-Chunking

Meta-Chunking 是一种新兴策略，核心思想是在段落级别引入分块决策。首先按段落或自然单元进行初步分割，然后通过语义相似度或 LLM 判断相邻段落是否应该合并，最终形成语义连贯的 chunk。包含两种具体实现：Margin Sampling Chunking（基于边际采样判断相邻段落的语义关系）和 Perplexity Chunking（基于困惑度变化识别主题边界）。

#### 3.2.7 Late Chunking

Late Chunking 由 Jina AI 提出，是一种创新的分块思路。传统方式是"先分块再 Embedding"，每个 chunk 独立编码，丢失了跨 chunk 的上下文信息。Late Chunking 则是"先对整个文档做 Embedding（获取每个 token 的上下文化表示），再进行分块并对每个 chunk 内的 token 表示做池化"。这样每个 chunk 的向量实际上编码了整篇文档的上下文信息，显著提升了检索效果，尤其在处理代词指代和跨段落引用时表现优异。

#### 3.2.8 Contextual Retrieval（上下文化分块）

Anthropic 提出的 Contextual Retrieval 方法，在分块后为每个 chunk 添加上下文说明。具体做法是：使用 LLM 为每个 chunk 生成一段简短的上下文描述（如"这段文本来自某某文档的第三章，讨论的是某某主题，前文提到了某某概念"），将这段描述拼接到 chunk 前面，再进行 Embedding。实验结果表明，Contextual Embeddings + Contextual BM25 + Reranking 的组合相比朴素 RAG 减少了 67% 的检索失败率。

### 3.3 分块参数选择建议

分块大小的选择需要综合考虑多个因素：Embedding 模型的最大输入长度（如 text-embedding-ada-002 最大支持 8191 tokens）；LLM 的上下文窗口大小（决定了能放入多少 chunk）；信息的密度（代码通常需要更小的 chunk，叙述性文本可以更大）；检索精度与召回的权衡（小 chunk 精度高但可能丢失上下文，大 chunk 上下文完整但可能引入噪声）。

经验性建议：对于问答场景，256-512 tokens 是较好的起点；对于文档摘要场景，1024-2048 tokens 更合适；对于代码检索，按函数/类粒度切分效果最好。无论选择何种 chunk_size，保持 10-20% 的 overlap 通常是有益的。

## 四、Embedding 与向量数据库

### 4.1 Embedding 模型

Embedding（嵌入）是将文本映射为高维向量空间中稠密向量的过程。好的 Embedding 模型应该使语义相近的文本在向量空间中距离接近。

**主流 Embedding 模型**：

OpenAI text-embedding-ada-002 / text-embedding-3-small/large：通用性强，维度可配置（256-3072），性能优异。text-embedding-3-large 在 MTEB 基准上表现出色。

BGE 系列（BAAI）：开源模型中的佼佼者，包括 bge-large-zh（中文）、bge-large-en（英文）、bge-m3（多语言多粒度多功能，支持 dense、sparse、multi-vector 三种表示）。

Jina Embeddings：支持长文本（8192 tokens），Late Chunking 原生支持。

Cohere embed-v3：支持多语言，提供专门的搜索优化版本。

**Dense vs Sparse Embedding**：Dense Embedding 将文本编码为固定长度的稠密向量（每个维度都有值），擅长捕捉语义相似性。Sparse Embedding 生成高维稀疏向量（大部分维度为零），类似于传统的 TF-IDF/BM25 表示，擅长精确的词汇匹配。BGE-M3 等模型同时输出 dense 和 sparse 表示，天然支持混合检索。

### 4.2 向量数据库

向量数据库是 RAG 系统的核心基础设施，负责存储向量并提供高效的近似最近邻（ANN）搜索。

**Milvus**：开源分布式向量数据库，支持多种索引类型（HNSW、IVF_FLAT、IVF_SQ8、ANNOY 等），适合大规模生产部署。提供标量过滤、分区、多副本等企业级特性。Zilliz Cloud 是其托管版本。

**Pinecone**：全托管的向量数据库服务，开箱即用，支持 Namespace 隔离和 Metadata 过滤，适合快速原型开发。

**Weaviate**：开源向量数据库，内置 Embedding 和 LLM 集成，支持混合搜索（向量+BM25），GraphQL API 易用。

**Qdrant**：Rust 实现的高性能向量数据库，支持丰富的过滤条件，内存效率高。

**Chroma**：轻量级开源向量数据库，适合本地开发和小规模应用。

**FAISS**（Facebook AI Similarity Search）：严格来说是一个向量检索库而非数据库，性能极高，适合嵌入到应用中使用，不具备持久化和分布式能力。

### 4.3 向量索引类型

**HNSW（Hierarchical Navigable Small World）**：基于图的索引，构建多层图结构，检索时从顶层开始逐层下降找到最近邻。优点是检索速度快、精度高；缺点是内存占用大（需要存储整个图结构），构建速度较慢。适合对延迟要求高、数据规模中等的场景。

**IVF（Inverted File Index）**：先通过聚类将向量空间划分为多个 Voronoi cell，检索时只在最近的几个 cell 中搜索。IVF_FLAT 在 cell 内暴力搜索（精确），IVF_SQ8 通过标量量化压缩向量（近似，节省内存），IVF_PQ 通过乘积量化进一步压缩。适合大规模数据集。

**ANNOY（Approximate Nearest Neighbors Oh Yeah）**：基于随机投影树的索引，内存映射友好，适合静态数据集（不支持动态插入）。

选择建议：数据量小于 100 万条时 HNSW 通常是最佳选择；数据量超过千万条时考虑 IVF 系列；需要频繁更新的场景避免使用 ANNOY。

### 4.4 相似度度量

**余弦相似度（Cosine Similarity）**：衡量两个向量方向的相似程度，不考虑模长，值域为 [-1, 1]。最常用于文本相似度计算，因为文本 Embedding 的模长通常不具有明确语义含义。

**欧氏距离（L2 Distance）**：衡量向量空间中两点的直线距离。值越小越相似。当向量已经归一化时，L2 距离与余弦相似度等价。

**内积（Inner Product）**：两个向量的点积。当向量已归一化时等价于余弦相似度。在向量未归一化时可以同时考虑方向和模长。

实践中，对于归一化的 Embedding 向量，三种度量的检索结果排序完全一致。多数 Embedding 模型输出的向量已经过归一化处理。

## 五、检索策略

### 5.1 稀疏检索（Sparse Retrieval）

**BM25（Best Matching 25）** 是最经典的稀疏检索算法，基于词频（TF）和逆文档频率（IDF）计算文档与查询的相关性。其核心公式综合考虑了：查询词在文档中出现的频率、该词在整个语料库中的稀有程度、文档长度的归一化。

BM25 的优势在于：对精确的关键词匹配非常有效（如专有名词、编号、术语）；不需要额外的模型训练；计算效率极高；可解释性强。其劣势是无法理解语义（"汽车"和"轿车"被视为完全不同的词）。

**SPLADE**（Sparse Lexical and Expansion Model）是一种学习型稀疏检索方法，通过 BERT 模型学习词汇扩展，既保持稀疏表示的效率，又具备一定的语义理解能力。

### 5.2 稠密检索（Dense Retrieval）

稠密检索通过 Embedding 模型将查询和文档都映射为稠密向量，基于向量相似度进行检索。

**双塔模型（Bi-Encoder）**：查询和文档分别通过独立的编码器得到向量表示，通过向量相似度计算相关性。优点是文档向量可以离线预计算，在线检索只需编码查询并做 ANN 搜索，速度极快。缺点是查询和文档的交互仅发生在最终的相似度计算环节，对细粒度语义匹配能力有限。

稠密检索的优势在于语义理解能力：能够处理同义词、释义、概念层面的相似性。劣势是对低频专有名词、数字、缩写等的匹配不如 BM25 精确。

### 5.3 混合检索（Hybrid Search）

混合检索结合稀疏和稠密两种检索方式的优势，是目前工业界 RAG 系统的标配。

**实现方式**：分别执行 BM25 检索和向量检索，各返回 Top-K 结果，然后通过融合策略合并两路结果。

**RRF（Reciprocal Rank Fusion）** 是最常用的融合策略。其公式为：`RRF_score(d) = Σ 1/(k + rank_i(d))`，其中 k 是常数（通常取 60），rank_i(d) 是文档 d 在第 i 路检索结果中的排名。RRF 的优点是不依赖各路检索的分数量纲，只关注排名，实现简单且效果稳定。

**加权融合**：对两路检索的归一化分数进行加权求和：`final_score = α * dense_score + (1-α) * sparse_score`。需要调优权重 α，但可以灵活控制两路检索的贡献比例。

Anthropic 的 Contextual Retrieval 实验表明，Contextual Embeddings + Contextual BM25 的混合检索相比单独使用向量检索，检索失败率降低了 49%，再加上 Reranking 可进一步降低至 67%。

### 5.4 多路召回

除了稀疏/稠密两路之外，实际系统中还可以加入更多召回通道：基于知识图谱的实体检索、基于文档结构的层次化检索（先定位章节再定位段落）、基于时间衰减的最新文档优先检索、基于用户画像的个性化检索等。多路召回的结果统一通过融合与重排序模块进行整合。

## 六、查询理解与改写

### 6.1 查询改写（Query Rewriting）

用户的原始查询往往存在表述模糊、信息不完整、口语化等问题，直接用原始查询进行检索效果不佳。查询改写通过 LLM 将原始查询转化为更适合检索的形式。

典型的改写策略包括：将口语化表述转为正式表述（"这东西怎么用" → "产品使用说明和操作指南"）；补全隐含信息（结合对话上下文补全指代）；去除无关修饰词，提取核心检索意图。

实现时通常使用一个专门的 Prompt 指导 LLM 进行改写，例如：

```
请将以下用户问题改写为更适合在知识库中搜索的查询。
保持原始意图不变，但使查询更加明确、具体。
用户问题：{query}
改写后的查询：
```

### 6.2 Multi-Query（多查询策略）

一个用户问题可能涉及多个方面，单一查询难以覆盖所有相关信息。Multi-Query 策略通过 LLM 从不同角度生成多个查询变体，分别执行检索，最后合并去重结果。

例如，用户问"RAG 系统如何提升回答准确性？"可以扩展为：
1. RAG 系统中提升检索精度的方法有哪些？
2. 如何减少 RAG 生成中的幻觉问题？
3. RAG 系统中 Reranking 对回答质量的影响
4. 分块策略如何影响 RAG 的检索效果？

### 6.3 RAG-Fusion

RAG-Fusion 是 Multi-Query 的进阶版本，不仅生成多个查询变体，还使用 RRF 融合多路检索结果的排名，最终输入给 LLM 的是经过多视角检索和排名融合后的高质量上下文。

### 6.4 查询分解（Query Decomposition）

对于复杂的多跳问题（如"公司 A 的创始人的母校的现任校长是谁？"），单次检索难以找到完整答案。查询分解将复杂问题拆分为多个简单子问题，依次检索和回答，最终综合所有子问题的答案。

分解策略有两种模式：**串行分解**——后续子问题依赖前序子问题的答案（如上述例子必须先知道创始人是谁）；**并行分解**——子问题相互独立可以并行检索（如"比较 A 产品和 B 产品的优缺点"可以分别查询两个产品）。

### 6.5 HyDE（Hypothetical Document Embeddings）

HyDE 是一种创新的查询增强技术：不直接用问题进行检索，而是先让 LLM 基于问题生成一个"假想答案"（可能不准确，但包含了相关的语义信息），然后用这个假想答案的 Embedding 去检索真实文档。其原理是：假想答案与真实答案在语义空间中的距离，可能比问题与答案的距离更近。

### 6.6 Step-back Prompting

让 LLM 先"退后一步"思考问题背后的更高层概念或原理，生成一个更抽象层面的查询，检索到更基础、更全面的知识后再回答具体问题。例如，对于"Python 中 dict 的 get 方法和直接用 [] 访问有什么区别？"，step-back query 可能是"Python 字典的各种访问方式及其行为差异"。

## 七、重排序（Reranking）

### 7.1 为什么需要 Reranking

向量检索（Bi-Encoder）虽然速度快，但存在精度不足的问题：由于查询和文档独立编码，无法进行细粒度的交互匹配。初检可能返回表面相似但实际不太相关的结果。Reranking 作为"精排"步骤，对初检返回的候选集进行更精细的相关性评分和重新排序。

### 7.2 Cross-Encoder

Cross-Encoder 是最常用的 Reranking 方式。与 Bi-Encoder 不同，Cross-Encoder 将查询和文档拼接在一起作为输入，通过 BERT 等模型联合编码，让查询和文档的 token 之间进行充分的注意力交互，最终输出一个相关性分数。

优点是精度远高于 Bi-Encoder（能捕捉细粒度的语义匹配），缺点是计算量大（每对 query-document 都需要一次前向传播），因此只能用于对初检返回的少量候选（通常 Top-20 到 Top-100）进行重排，不能用于全库检索。

主流 Cross-Encoder 模型包括：bge-reranker-large/v2-m3（BAAI 开源，中英文效果好）、Cohere Rerank（商业 API，多语言支持）、ms-marco-MiniLM（轻量级选择）。

### 7.3 基于 LLM 的 Reranking

直接使用 LLM 对检索结果进行相关性判断和排序。优点是利用了 LLM 强大的语义理解能力，适应性强；缺点是成本高、延迟大。实现方式包括：让 LLM 对每个文档给出相关性评分（Pointwise）、让 LLM 比较两个文档哪个更相关（Pairwise）、让 LLM 直接对一批文档排序（Listwise）。

### 7.4 ColBERT

ColBERT（Contextualized Late Interaction over BERT）是一种介于 Bi-Encoder 和 Cross-Encoder 之间的方案。它为查询和文档的每个 token 分别生成向量表示（类似 Bi-Encoder），但在匹配阶段使用 MaxSim 操作（对每个查询 token，找到最相似的文档 token）进行细粒度交互。既保留了文档向量可以离线预计算的优势，又具备较好的交互匹配能力。

### 7.5 Reranking 工程实践

在实际系统中，Reranking 的典型流程为：向量检索返回 Top-100 候选 → Cross-Encoder 重排 → 取 Top-5 到 Top-10 作为最终上下文。需要注意的工程细节包括：Reranking 的候选集大小需要权衡精度和延迟；可以级联多个 Reranker（先用轻量模型缩小范围，再用重量模型精排）；Reranker 的分数可以作为额外的过滤信号（设置阈值，低于阈值的不返回）。

## 八、GraphRAG 与知识图谱

### 8.1 传统 RAG 的局限

基于向量相似度的传统 RAG 在处理以下场景时表现不佳：多跳推理（需要跨多个文档串联信息）；全局性问题（如"这个项目的主要技术栈有哪些？"需要综合全局信息）；实体关系推理（如"A 和 B 之间是什么关系？"）；因果链推理（如"X 事件导致了什么后果？"）。这些场景需要的是结构化知识表示和图上的推理能力。

### 8.2 GraphRAG 概述

GraphRAG（由微软研究院提出）将知识图谱与 RAG 结合，核心流程包括：

**知识图谱构建**：从文档中使用 LLM 提取实体（人物、地点、组织、概念等）和实体间的关系，构建知识图谱。这一步通常使用专门的 Prompt 指导 LLM 进行信息抽取。

**社区检测**：对构建的知识图谱应用 Leiden 等社区检测算法，将紧密相关的实体聚类为社区（community），形成层次化的知识结构。

**社区摘要**：为每个社区使用 LLM 生成摘要描述，概括该社区涉及的主要实体、关系和主题。

**检索与推理**：查询时，先确定问题涉及的实体和社区，然后在相关社区内进行图遍历和推理，综合多个社区的信息生成全面的回答。

### 8.3 GraphRAG 的两种查询模式

**Local Search（局部搜索）**：适合具体的、聚焦的问题。从与查询最相关的实体出发，沿关系边扩展到邻近实体，收集局部子图中的信息。类似于传统 RAG 的针对性检索，但利用了图结构进行多跳推理。

**Global Search（全局搜索）**：适合需要综合全局信息的概括性问题。利用预先计算的社区摘要，通过 Map-Reduce 方式对多个社区的摘要进行汇总，生成全局性的回答。这是 GraphRAG 相比传统 RAG 最大的优势所在。

### 8.4 LightRAG

LightRAG 是对 GraphRAG 的轻量化改进，主要解决 GraphRAG 成本高、不支持增量更新的问题：

**双层级检索**：同时支持 low-level（实体/关系级别的细粒度检索）和 high-level（主题/概念级别的粗粒度检索），根据问题类型自动选择合适的检索层级。

**增量更新**：支持在已有图谱上增量添加新文档的知识，无需重建整个图谱。通过去重和合并策略处理新旧知识的融合。

**成本优化**：相比 GraphRAG 显著减少了 LLM 调用次数和 Token 消耗，使得知识图谱增强的 RAG 在实际生产中更具可行性。

### 8.5 知识图谱构建实践

知识图谱的构建质量直接决定 GraphRAG 的效果。关键考虑包括：

**实体类型定义**：根据业务领域预定义实体类型（如"人物、组织、产品、技术概念"），引导 LLM 进行有针对性的抽取。

**关系类型定义**：明确关系的方向性和类型（如"开发了、属于、依赖于"），建立统一的关系本体。

**实体消歧与合并**：同一实体可能有不同的表述形式（如"ML"和"机器学习"），需要通过 Embedding 相似度或 LLM 判断进行合并。

**质量验证**：对 LLM 抽取的三元组进行抽样人工审核或自动化验证，确保知识图谱的准确性。

## 九、RAG 评估体系

### 9.1 评估维度

RAG 系统的评估需要从检索和生成两个维度分别考察：

**检索质量评估**：

- **Context Precision（上下文精度）**：检索到的文档中有多少是真正相关的。高精度意味着检索结果中噪声少。
- **Context Recall（上下文召回）**：所有相关文档中有多少被检索到了。高召回意味着相关信息没有被遗漏。
- **Hit Rate / MRR**：第一个相关文档出现在结果列表中的位置。
- **NDCG（Normalized Discounted Cumulative Gain）**：考虑相关性程度和排名位置的综合指标。

**生成质量评估**：

- **Faithfulness（忠实度）**：生成的回答是否忠实于检索到的上下文，没有添加上下文中不存在的信息（即没有幻觉）。
- **Answer Relevance（回答相关性）**：生成的回答是否切实回答了用户的问题。
- **Answer Correctness（回答正确性）**：与标准答案对比，生成回答的事实准确性。

### 9.2 RAGAS 评估框架

RAGAS（Retrieval Augmented Generation Assessment）是最流行的 RAG 评估开源框架。其核心思想是利用 LLM 本身作为评判者（LLM-as-a-Judge），对 RAG 系统的输出进行多维度自动评估。

RAGAS 的典型评估流程：准备评估数据集（包含 question、ground_truth、contexts、answer）→ 调用各维度评估指标 → 输出各维度得分和综合得分。

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall]
)
```

### 9.3 评估数据集构建

高质量的评估数据集是 RAG 评估的基础。构建方式包括：

**人工标注**：领域专家针对知识库内容设计问题和标准答案，标注每个问题对应的相关文档。质量最高但成本大。

**半自动生成**：使用 LLM 基于文档内容自动生成问答对，再经人工审核筛选。RAGAS 框架提供了 TestsetGenerator 工具支持自动生成。

**线上日志**：从实际用户的提问和反馈中收集评估样本，最能反映真实使用场景。

### 9.4 持续评估与监控

生产环境中的 RAG 系统需要持续监控：定期在评估集上跑回归测试，确保系统迭代不引入退化；监控线上的用户反馈（点赞/点踩、追问率）；追踪检索延迟、Token 消耗等运维指标；设置告警阈值，当关键指标下降时及时预警。

## 十、RAG 工程实践与最佳实践

### 10.1 端到端流水线设计

一个生产级 RAG 系统的完整流水线包括：

```
文档源 → 文档解析 → 文本清洗 → 分块 → Embedding → 向量入库
                                                         ↓
用户查询 → 查询理解/改写 → 混合检索 → 重排序 → 上下文组装 → LLM 生成 → 答案 + 引用源
```

每个环节都有对应的工程考量：文档解析需要处理各种格式和异常；分块策略需要根据文档类型动态调整；Embedding 需要考虑批量计算和增量更新；检索需要平衡精度和延迟；生成需要控制幻觉和格式。

### 10.2 MDP-AI 平台实践（基于 Spring AI）

在美团内部，MDP-AI 平台基于 Spring AI 框架提供了 RAG 的标准化实现。核心组件包括：

**QuestionAnswerAdvisor**：Spring AI 提供的标准 RAG Advisor，封装了检索-增强-生成的完整流程。通过配置 VectorStore 和检索参数即可快速搭建 RAG 应用。

**VectorStore API**：统一的向量数据库抽象层，支持多种底层实现（Milvus、PgVector、Redis 等），通过 Spring Boot Starter 可便捷集成。

**ETL Pipeline**：提供 DocumentReader → DocumentTransformer → DocumentWriter 的标准化文档处理流水线，支持自定义分块器和 Embedding 模型。

### 10.3 Prompt 工程

RAG 系统中的 Prompt 设计直接影响生成质量，关键原则包括：

**明确角色和任务**：告诉 LLM 它是一个基于检索结果回答问题的助手，必须基于给定上下文回答。

**处理无法回答的情况**：明确指示当检索结果不包含足够信息时，应该坦诚告知用户而不是编造答案。

**引用标注**：要求 LLM 在回答中标注信息来源（如 [1]、[2]），便于用户验证。

**格式控制**：根据应用场景指定输出格式（如 Markdown、JSON、纯文本等）。

典型的 RAG Prompt 模板：

```
你是一个基于知识库回答问题的助手。请根据以下检索到的上下文信息回答用户问题。
如果上下文中没有足够的信息来回答问题，请明确说明"根据现有知识库信息，无法回答该问题"。
请在回答中标注信息来源编号。

上下文信息：
{context}

用户问题：{question}

回答：
```

### 10.4 常见问题与优化策略

**问题一：检索到了相关文档但 LLM 没有正确利用**

可能原因：上下文过长导致"中间丢失"（Lost in the Middle）现象；多个 chunk 之间信息冲突；Prompt 设计不当。解决方案：将最相关的 chunk 放在上下文首尾位置；对检索结果进行去重和冲突消解；使用 Context Compression 提取关键信息。

**问题二：召回率低，相关文档没有被检索到**

可能原因：分块粒度不合适；Embedding 模型在特定领域效果不好；查询与文档的表述差异大。解决方案：优化分块策略，增加 overlap 或使用语义分块；在领域数据上 Fine-tune Embedding 模型；引入查询改写和混合检索。

**问题三：幻觉（Hallucination）**

即使有了检索增强，LLM 仍可能生成与上下文不一致的内容。解决方案：在 Prompt 中强化"仅基于提供的信息回答"的约束；使用 Faithfulness 检测后处理（对比回答与源文档）；设置温度参数为较低值（0-0.3）减少随机性。

**问题四：延迟过高**

RAG 系统的端到端延迟 = Embedding 计算 + 向量检索 + Reranking + LLM 生成。优化策略：使用更小的 Embedding 模型或降低向量维度；缓存高频查询的检索结果；使用流式输出减少用户感知延迟；并行化 Reranking 计算。

### 10.5 数据飞轮

成熟的 RAG 系统应建立数据飞轮：收集用户的提问模式和反馈 → 分析检索失败的 case → 优化分块/Embedding/检索策略 → 补充知识库内容 → 更新评估集 → 验证效果 → 上线新版本。这是一个持续迭代优化的闭环过程。

## 十一、前沿趋势与展望

### 11.1 Long-context LLM vs RAG

随着 LLM 上下文窗口不断扩大（GPT-4 Turbo 128K、Claude 200K、Gemini 1M），一个自然的问题是：是否还需要 RAG？直接将所有文档塞入上下文不就行了？

实际上，RAG 在可预见的未来仍然不可或缺：长上下文的计算成本随文档数量线性增长，而 RAG 的检索成本是对数级的；Long-context 存在"大海捞针"（Needle in a Haystack）问题，对中间位置信息的利用率下降；RAG 提供了明确的信息溯源能力；RAG 支持知识的动态更新而无需重新加载全部上下文。

更合理的趋势是二者结合：先用 RAG 检索出最相关的文档子集，再利用长上下文窗口容纳更多上下文。

### 11.2 Multimodal RAG

多模态 RAG 将检索和生成扩展到文本之外：图像检索（用文本查询检索相关图片，或用图片检索相关文档）、表格理解（将表格转为文本描述或使用专门的表格 Embedding）、音视频检索（基于转录文本或视觉特征进行检索）。随着多模态 Embedding 模型（如 CLIP、ImageBind）和多模态 LLM 的发展，多模态 RAG 正在快速成熟。

### 11.3 Agentic RAG 与自适应检索

未来的 RAG 系统将越来越具备"自主性"：能够判断何时需要检索、检索什么、从哪里检索；能够对检索结果进行自我评估，决定是否需要补充检索；能够结合多种工具（搜索引擎、数据库查询、API 调用、代码执行）进行信息获取；能够在多轮交互中逐步逼近最优答案。

### 11.4 RAG 与 Fine-tuning 的融合

RAFT（Retrieval Augmented Fine Tuning）等方法探索将 RAG 的思想融入模型训练：在 Fine-tuning 阶段模拟 RAG 的检索过程，让模型学会从"有噪声的检索结果"中提取正确信息。这样训练出的模型在推理时配合 RAG 使用效果更好。

## 十三、Self-RAG 与 CRAG：自反思检索增强

### 13.1 Self-RAG（自反思 RAG）

Self-RAG 是一种让 LLM 自身学会"何时检索、如何评估检索结果"的方法。传统 RAG 无论问题是否需要外部知识都执行检索，而 Self-RAG 通过引入特殊的反思标记（Reflection Tokens）让模型具备以下自主判断能力：

**Retrieve Token**：判断当前输入是否需要进行检索。如果问题是简单的常识问答，模型输出"No Retrieval"跳过检索；如果问题需要外部知识，模型输出"Retrieval"触发检索流程。

**ISREL Token（相关性判断）**：对检索到的每个文档片段，判断其是否与当前问题相关，标注"Relevant"或"Irrelevant"，过滤掉无关信息。

**ISSUP Token（支持性判断）**：对模型生成的每个声明（claim），判断是否被检索文档所支持，分为"Fully Supported"、"Partially Supported"和"No Support"三级。

**ISUSE Token（实用性判断）**：对最终生成的回答进行整体有用性评估。

Self-RAG 的训练采用两阶段：首先用 GPT-4 标注一批数据生成反思标记的训练集，然后对基础模型进行端到端微调。推理时无需额外外部模块，模型自身就能完成检索决策和结果评估。

### 13.2 CRAG（Corrective RAG，纠正式 RAG）

CRAG 在生成之前加入"检索评估器"（Retrieval Evaluator），对检索文档进行置信度评估，根据评估结果采取不同策略：

**Correct（正确）**：检索文档高度相关时，进行知识精炼（Knowledge Refinement），将文档拆分为更细粒度的知识条目（Knowledge Strips），对每条独立评分，只保留高分条目，过滤噪声。

**Incorrect（不正确）**：检索文档完全不相关时，放弃内部知识库结果，转而通过 Web 搜索等外部来源获取补充信息。

**Ambiguous（模糊）**：置信度居中时，同时使用内部检索结果和外部搜索结果，综合生成。

CRAG 的关键创新在于细粒度的 Knowledge Strips 过滤——比直接使用完整文档片段能显著减少噪声干扰。

### 13.3 Adaptive RAG（自适应 RAG）

Adaptive RAG 通过轻量级分类器判断查询复杂度等级，据此选择不同处理策略：简单查询不检索直接生成；中等查询执行标准 RAG 流程；复杂查询进入 Iterative RAG 或 Agentic RAG 流程多轮迭代。这种分级处理在保证质量的同时显著降低平均延迟和计算成本。

## 十四、查询路由与 Semantic Cache

### 14.1 查询路由（Query Routing）

实际 RAG 系统中通常存在多个知识库或数据源，查询路由的作用是将用户问题分发到最合适的数据源：

**元数据路由（Metadata Routing）**：基于文档元数据标签进行路由，为每个知识库定义涵盖的主题和文档类型。通过关键词匹配或简单分类器确定查询目标。速度快、可控性强，但依赖人工维护。

**语义路由（Semantic Routing）**：使用 Embedding 将查询和各知识库的"描述向量"进行相似度比较，自动选择最匹配的知识库。也可为每个知识库维护一组代表性查询的 Embedding 作为路由依据。

**LLM 路由**：使用 LLM 根据查询内容和各知识库描述推理判断路由目标，可同时路由到多个数据源（多路由），适合跨域复杂问题。

### 14.2 Semantic Cache（语义缓存）

传统缓存基于精确 key 匹配，而 RAG 场景中相同意图的查询有无数种表述。Semantic Cache 通过语义相似度匹配来命中缓存。

**GPTCache 架构**：开源语义缓存方案，核心流程为——查询到来 → Embedding 编码 → 缓存向量库中搜索相似查询 → 相似度超阈值则命中缓存 → 否则执行正常 RAG 并写入缓存。关键组件包括 Embedding Manager、Cache Store、Similarity Evaluator（可配置阈值）、Eviction Manager（LRU/TTL 淘汰策略）。

**Prompt Cache（前缀缓存）**：Anthropic 提出的推理层优化——将 RAG 系统 System Prompt 中不变的部分进行前缀缓存。当多次请求共享相同 Prompt 前缀时，复用前缀计算结果，减少推理延迟和 Token 成本。与语义缓存不同，Prompt Cache 是在 LLM 推理层面的优化，对用户完全透明。

**缓存失效策略**：知识库更新时需主动失效相关缓存。实现方式包括 TTL 被动过期、知识库版本号全量刷新、基于文档 ID 关联的精准失效（缓存中记录答案依赖的文档 ID）。

## 十五、Text-to-SQL 与结构化数据 RAG

### 15.1 从非结构化到结构化

传统 RAG 处理非结构化文本，但企业大量核心数据存储于结构化数据源（MySQL、Hive、数据仓库）。Text-to-SQL 将自然语言查询转换为 SQL，实现 RAG 向结构化数据的延伸。

核心挑战包括：理解自然语言意图并映射到数据库 Schema；处理复杂查询逻辑（多表关联、子查询、聚合函数、窗口函数）；业务术语到字段的映射；跨方言适配（BigQuery、Snowflake、MySQL 各有语法差异）。

### 15.2 NL2SQL + RAG 融合架构（Multi-Agent 模式）

美团内部 NL2SQL 系统采用 Multi-Agent 协作模式（基于 Spider2.0 数据集验证）：

**Schema Retrieval Agent**：从数据字典中检索相关表和字段信息。使用标准 RAG 技术——将表的 DDL、字段注释、业务含义向量化，根据用户问题检索最相关的表结构。

**Query Generation Agent**：基于检索到的 Schema 和用户问题，使用 LLM 生成 SQL。Prompt 包含表结构、字段含义、示例 SQL。

**Validation Agent**：对生成的 SQL 进行语法检查和逻辑验证。

**Execution & Summarization Agent**：执行 SQL 获取结果，用 LLM 将结构化结果转为自然语言回答。

Spider2.0 基准测试特征：632 个企业级 Text2SQL 工作流问题，平均单库含 812 列，涉及 BigQuery、Snowflake 等 6 种 SQL 方言，SQL 查询平均 144 tokens，需要多步复杂查询实现数据转换与分析。

### 15.3 Friday 结构化数据 RAG

Friday 平台正在建设结构化数据 RAG 能力：业务方提供 Hive/MySQL 数据源连接信息和字段配置，平台自动完成数据导入、索引建立与查询。核心价值在于一站式自动化的数据接入与检索；支持多字段混合检索（向量+稀疏索引）并可配置权重；支持按数据标签动态圈选检索范围。

## 十六、多轮对话 RAG 与记忆系统

### 16.1 多轮对话中的 RAG 挑战

多轮对话中用户的当前提问往往包含隐含指代关系和省略信息，直接用当前 turn 的文本检索效果很差。例如用户先问"推荐北京火锅店"，再问"那个最贵的人均多少"——如果直接用后者检索，系统无法理解"那个最贵的"指代什么。

### 16.2 上下文信息补全（Query Contextualization）

核心策略是利用对话历史对当前查询进行指代消解和信息补全：使用 LLM 将对话历史和当前查询融合，生成自包含的独立查询。

实现时使用专门的 Prompt 进行改写，这里的"上下文"不仅是多轮对话信息，还包含当前对话的背景信息（如用户角色、场景设定等）。上下文信息补全可以提高 query 的清晰度，但需要多调用一次 LLM，存在成本与延迟的权衡。

### 16.3 对话历史管理策略

**滑动窗口**：保留最近 N 轮对话。简单有效但可能丢失早期重要上下文。

**摘要压缩**：对话历史超阈值时，使用 LLM 对较早对话进行摘要压缩。

**关键信息提取**：从对话中提取结构化状态信息（用户偏好、已讨论实体、约束条件），以 slot 形式保存。

### 16.4 AI Agent 记忆系统

Agent 记忆系统是多轮对话 RAG 的进阶形态，实现真正的"状态持久化"：

**短期记忆**：等价于当前会话的上下文窗口，包含状态槽位（State Slots）和对话历史（Dialogue History）。生命周期仅限当前会话。典型实现如召回的知识 + 最近几轮对话 History = 完整的上下文窗口。

**长期记忆**：对对话历史、用户行为等信息压缩提炼后的结构化知识，跨会话保留。以旅行规划为例："用户喜欢自然风景" → 后续更新为"用户喜欢自然风景和骑行"。

**记忆生命周期**：写入（从对话中抽取值得记忆的信息）→ 存储（向量数据库存语义信息、图数据库存实体关系、KV 存储存结构化事实）→ 检索（需要时找到相关记忆注入上下文）→ 更新与遗忘（过时记忆需清除，避免噪声淹没）。

**RAG vs 记忆的边界**：RAG 是知识检索（从外部文档库获取领域知识），记忆是状态持久化（记住用户是谁、做过什么、有什么偏好）。两者解决不同维度问题，但工程上可复用相似的检索基础设施。

## 十七、Contextual Retrieval 与高级检索模式

### 17.1 Contextual Retrieval 深度解析

Anthropic 提出的 Contextual Retrieval 解决传统 RAG "上下文无关切片"问题。核心洞察：传统分块后每个片段失去了"它在原文中的位置和前后文在讨论什么"的背景信息，语义密度极低。

**Contextual Embeddings**：索引阶段使用轻量 LLM（如 Claude Haiku）为每个切片生成 50-100 token 的上下文描述——该切片在整体文档中的位置和作用，拼接到切片前面再 Embedding。

**Contextual BM25**：本质是 Document Expansion 策略——索引前添加上下文扩展切片词汇表。即使原始切片只写"该错误已修复"，上下文注入的"ACME 服务器 TS-999 故障"直接提升 BM25 精准度。

**效果**：Contextual Embeddings + Contextual BM25 混合检索降低 49% 检索失败率；集成 Reranking 后达 67%。结合 Prompt Caching 控制成本。

### 17.2 Parent Document Retrieval（父文档检索）

解决"小 chunk 精度高但上下文不足"的矛盾：将文档切为大的父 chunk（2000 tokens，上下文完整）和小的子 chunk（200 tokens，检索精确）。索引时存储子 chunk 向量并建立到父 chunk 的映射。检索时用子 chunk 精确匹配，返回对应父 chunk 确保 LLM 获得充分上下文。

### 17.3 Sentence Window Retrieval（句子窗口检索）

以句子级别构建索引（每个句子独立向量化），检索时根据匹配句子向前后扩展 N 个句子作为上下文窗口返回。既保证检索精度（句子级匹配），又提供足够上下文（窗口扩展）。窗口大小通常前后 3-5 个句子。

### 17.4 Auto-merging Retrieval（自动合并检索）

LlamaIndex 中的层次化检索策略：文档按树状结构组织（文档 → 章节 → 段落 → 句子），检索从叶子节点匹配，当同一父节点下超过阈值数量的子节点被命中时，自动"上卷"到父节点，自适应调整返回粒度。

### 17.5 Multi-Vector Retrieval（多向量检索）

为同一文档构建多种向量表示：Summary Vector（文档摘要 Embedding，适合全局问题）；Hypothetical Question Vector（LLM 生成"这段内容可回答什么问题"的假设性问题 Embedding）；Keyword Vector（关键实体和术语向量，增强精确匹配）。多种索引覆盖同一文档，从多个角度命中。

## 十八、RAG 可观测性与生产评测

### 18.1 为什么需要 RAG 可观测性

RAG 系统失败模式复杂：可能发生在意图识别、查询改写、检索召回、文档相关性、上下文拼装、LLM 生成、业务约束等环节。传统日志/APM 无法回答"为什么回答不好"。RAG 可观测性目标是将系统从"黑箱"变为"透明玻璃"。

### 18.2 Arize Phoenix 框架理念

面向 AI/LLM 应用的开源可观测与评测平台，核心工程理念：

1. **先标准化记录执行过程**：每次运行拆成可比较的 span（查询理解、知识检索、重排序、LLM 生成等），记录输入/输出/耗时/token。
2. **失败样本沉淀为 dataset**：线上差评、人工标注、灰度失败都进入回归集。
3. **用 experiments 管住变更**：每次 prompt/参数/模型变化，在同一批 dataset 上重放并比较。
4. **annotations/evals 做错误归因**：给检索 span、生成 span 分别打标签，判断问题来自哪一层。

### 18.3 Friday 观测平台

美团内部基于 Friday 建设的 Agent/RAG 观测体系：

**Tracing 数据上报**：基于 OpenTelemetry/OpenInference 标准，每次 RAG 调用拆解为 Trace（完整请求）和 Span（操作单元，如知识检索 Span、LLM 生成 Span），每个 Span 记录输入输出、token、耗时。

**多维度聚合**：支持按 Session、User、Trace 维度聚合分析。

**实时自动化评测**：结合在线评测指标实时监控质量变化趋势。

**OpenClaw Tracing Plugin**：Friday 提供的观测插件，实现全链路透明化——从黑箱到"透明玻璃"，每次执行都有据可查、有迹可循。

### 18.4 RAG 评测指标体系（基于 ZeroAgent 实践）

**检索阶段指标**：

- Context Precision：检索结果中信息排序的准确度（正确信息排后面会影响模型利用）
- Context Recall：参考答案中有多少事实可归因于检索上下文
- Context Relevance：检索上下文与用户输入的相关性
- Context Entities Recall：参考答案中实体在检索文档中的出现比例

**生成阶段指标**：

- Faithfulness：模型回答中每个声明是否被检索上下文支持（检测幻觉的核心指标）
- Answer Relevance：回答是否切实回答了用户问题
- Answer Correctness：与标准答案的事实准确性对比

**评估方法论**：RAGAS 采用 LLM-as-a-Judge 模式，将比较对象提取为 claims/statements 再量化评分。部分框架引入两个独立 LLM 综合评估减少偏见。

## 十九、GraphRAG 深度解析与 LLM Wiki

### 19.1 GraphRAG 完整工作流程

**Graph-Based Indexing**：文档分块 → LLM 提取实体和关系 → 实体消歧合并 → 构建知识图谱 → Leiden 社区检测（紧密相关实体聚类）→ 为每个社区生成 LLM 摘要。

**Graph-Guided Retrieval**：
- Local Search：从相关实体出发沿关系边 K 跳遍历，收集局部子图。适合具体聚焦问题。
- Global Search：利用预计算社区摘要通过 Map-Reduce 汇总。适合总结性概括问题。

**Graph-Enhanced Generation**：将子图或社区摘要作为结构化上下文输入 LLM，支持多跳推理。

GraphRAG 适用场景：文档中存在大量实体且实体间关系对回答至关重要——法律文书分析、企业知识图谱、生物医学关系抽取、人物关系网络等。

### 19.2 LLM Wiki：第三代知识检索范式

Karpathy（2026 年 4 月）提出的 LLM Wiki 代表从"解释器模式"到"编译器模式"的范式转换：

**RAG = 解释器模式**：文档进来不理解直接存储；每次查询临时检索拼接让 LLM 推理。知识从未被真正"整合"。

**LLM Wiki = 编译器模式**：文档进来时就让 LLM "编译"成结构化知识资产。

三层存储架构：
- **Raw 层**：原始文档不可变保存，信息的"真理来源"
- **Wiki 层**：LLM 综合多份原始文档后提炼的知识页面，每页对应一个概念/人物/组件，包含摘要、关联概念、置信度标注和溯源信息
- **Schema 层**：元数据索引，记录 Wiki 页面目录、frontmatter、知识图谱骨架

控制面核心文件：index.md（Wiki 目录）、log.md（Ingest 操作流水账）、hot.md（热点页面 LRU 可视化）。

Ingest 八步流水线：哈希去重 → 解析分块 → 实体识别 → Wiki 页面定位 → 冲突检测 → 增量更新 → 交叉引用维护 → 质量审计。

### 19.3 Graphify 工具

Graphify 将 LLM Wiki 理念落地为生产力工具（MIT 开源），将任意文件夹转化为可查询的知识图谱：

**双通道提取**：通道 A（AST 确定性提取，tree-sitter，零 LLM 开销，支持 20 种语言）；通道 B（语义提取，LLM 子代理处理文档/论文/图片）。

**三级置信度**：EXTRACTED（显式，1.0）、INFERRED（推断，0.6-0.9）、AMBIGUOUS（不确定）。

**Leiden 社区检测**：基于图拓扑的社区发现，不需要向量数据库。查询仅消耗原始 token 的 1/71.5。

### 19.4 知识图谱检索技术全景

知识表示层的核心技术栈：

**本体论（Ontology）**：对领域中"有什么东西、什么关系"的形式化描述。语义网三件套——RDF（数据层三元组）、RDFS（轻量模式层）、OWL（重量级本体层支持推理）。

**知识图谱**：用图结构（节点+边）表示实体及其关系，核心数据模型为三元组 SPO（主体-关系-客体）。与关系数据库的本质区别——关系数据库按"表"组织（查关系需 JOIN），图数据库按"关系"组织（遍历是 O(1) 指针跳转）。

**NER（命名实体识别）**：从非结构化文本识别命名实体。技术演进：CRF → BiLSTM-CRF → BERT-NER → LLM 直接抽取。

**图数据库选型**：RDF 图（W3C 标准，Jena/Virtuoso，适合开放数据交换和推理）vs 属性图（Neo4j/JanusGraph，边可带属性，灵活建模）。

## 二十、Agentic RAG 与 ReAct 工程落地

### 20.1 Agentic RAG 核心理念

Agentic RAG 是 RAG 技术的最高演进形态：Agent 自主决策检索策略、工具调用与多步推理，而非被动执行固定的检索-生成流程。

与传统 RAG 的关键差异：传统 RAG 是"有问必检、检完必答"的固定流水线；Agentic RAG 中 Agent 可以判断是否需要检索、选择合适的数据源和检索策略、对结果进行批判性评估、决定是否需要补充检索、结合多种工具完成任务。

### 20.2 充电宝渠道运维 AI Native 助手案例

美团充电宝业务落地了完整的 Agentic RAG 架构（从 Naive RAG 升级到 Agentic RAG）：

**技术架构**：Agent 自主编排检索策略与工具调用 + LLM Wiki 自动结构化知识管理 + MCP 工具调用协议。

**Query 改写模块**：对用户原始 Query 进行指代消解、上下文补全、扩展和术语规范化。

**知识库管理闭环**：非结构化输入 → 结构化知识 → 自动巡检（Lint）→ 版本更新 → 高效应用 → 持续反馈。

**上下文管理演进**：从简单拼接 → 上下文压缩/选择 → Agent 管理长期记忆 → 实体关系上下文。

### 20.3 ReAct + RAG 模式

ReAct（Reasoning + Acting）模式与 RAG 结合的工作方式：

1. **Thought**：Agent 分析用户问题，推理需要什么信息
2. **Action**：决定调用哪个工具（知识库检索、Web 搜索、数据库查询、API 调用等）
3. **Observation**：获取工具返回结果
4. **Thought**：评估结果是否充分，是否需要继续检索
5. 循环直到信息充分，最终生成回答

这种模式使得系统不再局限于单一知识库，而是能够根据需要组合使用多种信息源和工具。

### 20.4 1024 Agent 与 Friday DeepAgent

美团内部的 Agent 框架支持 RAG 能力深度集成：

## 二十二、Milvus 分布式向量数据库架构

### 22.1 整体架构

Milvus 采用存算分离（Shared Storage）+ 计算存储分离的云原生架构，主要分为四层：

**Access Layer（接入层）**：Proxy 节点，负责客户端请求的接入和路由，无状态可水平扩展。

**Coordinator Layer（协调层）**：包含 Root Coordinator（管理元数据和时间戳）、Query Coordinator（管理查询节点和负载均衡）、Data Coordinator（管理数据节点和段分配）、Index Coordinator（管理索引构建任务）。

**Worker Layer（工作层）**：包含 Query Node（执行查询和加载数据）、Data Node（消费日志流写入存储）、Index Node（构建向量索引）。

**Storage Layer（存储层）**：基于对象存储（如 S3/MinIO）实现持久化，使用消息队列（如 Pulsar/Kafka）作为日志骨架。

### 22.2 关键设计理念

**日志即数据（Log as Data）**：所有数据变更先写入日志系统，然后异步持久化到对象存储。保证了写入的可靠性和一致性。

**段（Segment）管理**：数据以 Segment 为单位组织，分为 Growing Segment（接收新数据）和 Sealed Segment（不再修改，可建索引）。

**多副本与负载均衡**：Query Node 可以加载相同 Segment 的多个副本，实现查询的高可用和负载均衡。

### 22.3 性能调优建议

索引选择：数据量 < 100 万用 HNSW；> 千万用 IVF_SQ8/IVF_PQ；超大规模用 DiskANN。合理设置 nprobe（IVF 系列）和 ef（HNSW）平衡精度与速度。分区策略按业务维度分区（如按日期、按类目），减少检索范围。预加载策略对热数据预加载到内存。

## 二十三、总结与展望

RAG 技术从 2020 年诞生至今，已经经历了从 Naive RAG 到 Advanced RAG、Modular RAG、Agentic RAG、GraphRAG、LLM Wiki 的多次范式演进。其核心价值在于以较低成本为 LLM 注入动态知识、减少幻觉、支持知识溯源。

一个生产级 RAG 系统需要综合考虑的维度包括：数据处理（解析、分块、上下文化）；索引（Embedding 选型、向量数据库、多种索引策略）；检索（混合检索、查询路由、Semantic Cache、高级检索模式）；后处理（Reranking、Self-RAG/CRAG 自纠正、Context Compression）；生成（Prompt 工程、引用溯源、幻觉检测）；评估（RAGAS 指标体系、可观测性平台、A/B 实验）；工程化（分布式架构、缓存策略、数据飞轮、多轮对话管理）。

未来的发展趋势包括：Agentic RAG 的普及（Agent 自主决策检索策略）；GraphRAG 与 LLM Wiki 的融合（从文档碎片到结构化知识资产）；多模态 RAG 的成熟（图像、表格、音视频）；RAG + Fine-tuning 的深度融合（RAFT 等方法）；结构化数据 RAG 的落地（Text-to-SQL + 知识图谱）；记忆系统与 RAG 的统一架构。

RAG 不是银弹，但它是当前大模型应用落地的最重要基础设施之一。掌握其全貌——从理论原理到工程实践，从单点技术到系统架构——才能构建出真正解决业务问题的 AI 应用。
