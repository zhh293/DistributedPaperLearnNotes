Spring AI 检索增强生成（RAG）核心知识点 & 常用 API 整理
RAG 是解决大模型 “事实不准确、长文本能力弱” 的核心技术，Spring AI 提供 “开箱即用的 Advisor API” 和 “模块化自定义流程” 两种支持方式，以下是常用的核心内容：
一、核心定位与依赖
1. RAG 作用
   通过 “检索外部文档（如向量库）+ 增强查询上下文”，让大模型基于真实 / 最新数据生成回答，避免 “幻觉”。
2. 核心依赖（Advisor 必加）
   使用开箱即用的 RAG Advisor 需引入：
   xml
   <dependency>
   <groupId>org.springframework.ai</groupId>
   <artifactId>spring-ai-advisors-vector-store</artifactId>
   </dependency>
   二、常用开箱即用 Advisor（重点）
   Spring AI 提供 QuestionAnswerAdvisor（简单）和 RetrievalAugmentationAdvisor（灵活）两种常用 Advisor，是 RAG 最常用的方式。
1. QuestionAnswerAdvisor（最简开箱即用）
   定位：自动完成 “检索向量库文档 → 增强查询 → 生成回答” 全流程，适合快速落地 RAG。
   （1）基础用法
   需先向 VectorStore 加载数据，再通过 ChatClient 绑定 Advisor：
   java
   运行
   // 1. 配置Advisor（设置相似度阈值、返回数量）
   QuestionAnswerAdvisor qaAdvisor = QuestionAnswerAdvisor.builder(vectorStore)
   .searchRequest(SearchRequest.builder()
   .similarityThreshold(0.8) // 仅保留相似度≥0.8的文档
   .topK(6) // 返回前6条相关文档
   .build())
   .build();

// 2. 绑定到ChatClient执行RAG
String response = ChatClient.builder(chatModel)
.build()
.prompt()
.advisors(qaAdvisor)
.user("Spring Boot如何启动？") // 用户问题
.call()
.content();
（2）动态过滤（按元数据筛选文档）
运行时通过 FILTER_EXPRESSION 参数，按文档元数据（如类型、标签）过滤检索结果：
java
运行
// 全局配置Advisor（无默认过滤）
ChatClient chatClient = ChatClient.builder(chatModel)
.defaultAdvisors(QuestionAnswerAdvisor.builder(vectorStore).build())
.build();

// 运行时动态添加过滤：仅检索元数据type="Spring"的文档
String response = chatClient.prompt()
.user("Spring Boot如何启动？")
.advisors(a -> a.param(QuestionAnswerAdvisor.FILTER_EXPRESSION, "type == 'Spring'"))
.call()
.content();
（3）自定义提示模板
默认模板可能不符合需求，可自定义模板（必须包含 query 和 question_answer_context 两个占位符）：
java
运行
// 1. 定义自定义模板
PromptTemplate customTemplate = PromptTemplate.builder()
.renderer(StTemplateRenderer.builder()
.startDelimiterToken('<')
.endDelimiterToken('>')
.build())
.template("""
<query>

            上下文信息：
            ---------------------
            <question_answer_context>
            ---------------------

            规则：
            1. 答案仅来自上下文，不知道就说“无法回答”
            2. 不要说“基于上下文”这类话术
            """)
    .build();

// 2. 绑定到Advisor
QuestionAnswerAdvisor qaAdvisor = QuestionAnswerAdvisor.builder(vectorStore)
.promptTemplate(customTemplate)
.build();
2. RetrievalAugmentationAdvisor（更灵活的模块化 RAG）
   定位：基于 “模块化组件” 组装 RAG 流程，支持自定义检索前 / 后处理、查询转换等，比 QuestionAnswerAdvisor 更灵活。
   （1）基础用法
   核心是搭配 VectorStoreDocumentRetriever 检索文档：
   java
   运行
   // 1. 配置Advisor（绑定向量库检索器）
   RetrievalAugmentationAdvisor ragAdvisor = RetrievalAugmentationAdvisor.builder()
   .documentRetriever(VectorStoreDocumentRetriever.builder()
   .similarityThreshold(0.5) // 相似度阈值
   .vectorStore(vectorStore) // 向量库
   .build())
   .build();

// 2. 执行RAG
String response = ChatClient.builder(chatModel)
.build()
.prompt()
.advisors(ragAdvisor)
.user("Spring Boot如何启动？")
.call()
.content();
（2）允许空上下文
默认情况下，若检索不到文档，Advisor 会让模型拒绝回答；可设置允许空上下文（模型用自身知识回答）：
java
运行
RetrievalAugmentationAdvisor ragAdvisor = RetrievalAugmentationAdvisor.builder()
.documentRetriever(/* ... */)
.queryAugmenter(ContextualQueryAugmenter.builder()
.allowEmptyContext(true) // 允许空上下文
.build())
.build();
（3）高级用法：查询重写（优化检索效果）
通过 RewriteQueryTransformer 重写模糊 / 冗长的用户查询，提升检索准确性：
java
运行
RetrievalAugmentationAdvisor ragAdvisor = RetrievalAugmentationAdvisor.builder()
// 检索前重写查询
.queryTransformers(RewriteQueryTransformer.builder()
.chatClientBuilder(chatClientBuilder.build().mutate())
.build())
.documentRetriever(/* ... */)
.build();
三、常用模块化 RAG 组件（自定义流程用）
若需更精细控制 RAG 流程（如多查询扩展、多数据源合并），可使用 Spring AI 的模块化组件：
1. 检索前处理（优化查询）
   作用：处理用户查询，提升检索准确性。
   组件	作用	常用场景
   RewriteQueryTransformer	重写冗长 / 模糊的查询（如 “我学机器学习，LLM 是啥？”→“什么是 LLM？”）	查询表述不清晰时
   CompressionQueryTransformer	压缩对话历史 + 后续查询（如 “丹麦首都是？”→“哥本哈根”，后续 “第二大城市？”→“丹麦第二大城市是？”）	长对话场景
   MultiQueryExpander	将 1 个查询扩展为多个语义变体（如 “Spring Boot 启动”→“Spring Boot 启动命令”“Spring Boot 如何运行”）	提升检索覆盖度
   示例：MultiQueryExpander 扩展查询
   java
   运行
   MultiQueryExpander expander = MultiQueryExpander.builder()
   .chatClientBuilder(chatClientBuilder)
   .numberOfQueries(3) // 扩展为3个查询
   .build();

// 扩展查询
List<Query> queries = expander.expand(new Query("Spring Boot如何启动？"));
2. 检索模块（获取文档）
   VectorStoreDocumentRetriever（核心）：从向量库检索相关文档，支持静态 / 动态过滤：
   java
   运行
   // 静态过滤：仅检索genre="技术文档"的文档
   VectorStoreDocumentRetriever retriever = VectorStoreDocumentRetriever.builder()
   .vectorStore(vectorStore)
   .filterExpression(new FilterExpressionBuilder()
   .eq("genre", "技术文档")
   .build())
   .build();

// 动态过滤：运行时按租户筛选（从上下文获取租户ID）
VectorStoreDocumentRetriever retriever = VectorStoreDocumentRetriever.builder()
.vectorStore(vectorStore)
.filterExpression(() -> new FilterExpressionBuilder()
.eq("tenant", TenantContextHolder.getTenantId())
.build())
.build();
3. 检索后处理（合并文档）
   ConcatenationDocumentJoiner：拼接 “多查询 / 多数据源” 检索到的文档，自动去重（保留首次出现的文档）：
   java
   运行
   // 假设documentsForQuery是“查询→多数据源文档列表”的映射
   Map<Query, List<List<Document>>> documentsForQuery = /* ... */;

DocumentJoiner joiner = new ConcatenationDocumentJoiner();
List<Document> mergedDocs = joiner.join(documentsForQuery); // 合并为单一文档列表
四、关键细节
过滤表达式：类似 SQL 语法（如 type == 'Spring'、score > 0.8），所有 VectorStore 通用。
模板占位符：QuestionAnswerAdvisor 自定义模板必须包含 query（用户问题）和 question_answer_context（检索到的文档）。
查询转换的温度值：使用 QueryTransformer 时，建议将 ChatClient 的 temperature 设为 0.0（避免生成不确定的查询变体）。
五、核心对比
方式	特点	适用场景
QuestionAnswerAdvisor	开箱即用、配置简单	快速落地基础 RAG
RetrievalAugmentationAdvisor	模块化、灵活扩展	自定义 RAG 流程（如多查询、多数据源）













这些拦截器底层会干些什么事情啊，是不是跟embedding模型和向量数据库有关系啊
你问到了核心！这些 Advisor（你称的 “拦截器”）底层核心逻辑就是围绕 Embedding 模型和向量数据库展开的 —— 它们不是传统意义上的 “拦截器”，而是 Spring AI 对 RAG 全流程的自动化封装器，底层每一步都和 Embedding 模型、向量数据库强绑定。
下面用通俗的方式拆解底层逻辑，重点讲和 Embedding / 向量库的关联：
一、先纠正：Advisor 不是 “拦截器”，是 RAG 流程的 “自动化管家”
你可以把 QuestionAnswerAdvisor/RetrievalAugmentationAdvisor 理解为：帮你自动完成 “文本向量化 → 向量检索 → 上下文增强 → 模型生成” 全流程的工具类，而这个流程的 “核心底座” 就是 Embedding 模型（文本转向量）和向量数据库（向量检索）。
二、Advisor 底层完整执行流程（以最常用的 QuestionAnswerAdvisor 为例）
我用 “用户问‘Spring Boot 如何启动？’” 这个场景，拆解底层每一步，重点标红和 Embedding / 向量库相关的环节：
步骤 1：预处理（文档已提前入库，依赖 Embedding）
在你使用 Advisor 之前，必须先把文档（如《Spring Boot 官方文档》）存入向量数据库，这一步底层已完成：
调用 Embedding 模型（如 OpenAI Embedding、BGE 等），把文档的每一段文本转换成向量（Embedding Vector）（比如 “Spring Boot 启动命令是 java -jar”→ [0.12, 0.34, -0.05,...]）；
把 “向量 + 文档元数据（如 type='Spring'、score=0.9）” 存入向量数据库（如 Chroma、Milvus、PgVector）。
步骤 2：接收用户查询，先做 “向量化”（核心依赖 Embedding）
当你调用 chatClient.prompt().user("Spring Boot 如何启动？").call() 时：
Advisor 底层自动拦截用户查询，调用同一个 Embedding 模型，把用户问题转换成向量（比如 “Spring Boot 如何启动？”→ [0.11, 0.33, -0.06,...]）；
✅ 关键：必须用同一个 Embedding 模型（文档入库和用户查询的向量化要统一），否则向量空间不一致，相似度计算完全失效。
步骤 3：向量数据库检索（核心依赖向量库）
Advisor 拿着用户问题的向量，调用向量数据库的相似性检索 API：
先执行你配置的过滤表达式（如 type == 'Spring'）：向量库先按元数据过滤（只保留 “Spring 相关文档”），减少检索范围；
再计算 “用户问题向量” 和 “库中文档向量” 的余弦相似度（向量数据库的核心能力）；
按你配置的 similarityThreshold（如 0.8）过滤低相似度结果，按 topK（如 6）返回前 N 条最相关的文档向量；
向量库把 “向量对应的原始文档内容” 返回给 Advisor。
步骤 4：上下文增强（Advisor 封装的逻辑）
Advisor 把检索到的文档内容，按你配置的 PromptTemplate 拼接成 “增强上下文”：
plaintext
用户问题：Spring Boot 如何启动？

上下文信息：
---------------------
Spring Boot 启动方式有2种：1. java -jar xxx.jar；2. mvn spring-boot:run
---------------------
步骤 5：调用大模型生成回答（最终环节）
Advisor 把 “增强后的上下文” 传给 OpenAI/Gemini 等大模型，模型基于上下文生成准确回答（而非靠自身记忆），最后把结果返回给你。
三、和 Embedding 模型 / 向量数据库的核心关联（重点）
组件	在 Advisor 底层的核心作用
Embedding 模型	1. 文档入库时：把文本 → 向量（向量库能存储的格式）；
2. 用户查询时：把问题 → 向量（能和库中向量做相似度对比）；
   ✅ 无 Embedding 就无 “语义相似检索”，只能做关键词匹配
   向量数据库	1. 存储 “文档向量 + 元数据”；
2. 快速计算向量相似度（余弦 / 欧氏距离），找到语义相关文档；
3. 支持过滤、TopK、阈值等检索规则；
   ✅ 无向量库就无法高效检索（传统数据库做不到语义相似）
   四、RetrievalAugmentationAdvisor 的底层差异（更灵活，但核心不变）
   RetrievalAugmentationAdvisor 比 QuestionAnswerAdvisor 更 “底层”，允许你自定义 RAG 流程的每个模块，但核心依赖 Embedding / 向量库的逻辑完全一致，只是多了这些可扩展的底层步骤：
   检索前：自定义 “查询重写 / 压缩 / 扩展”（比如把模糊问题 “Spring Boot 咋跑？” 重写成 “Spring Boot 启动命令”），但重写后的查询仍需 Embedding 转向量；
   检索中：支持多数据源检索（比如同时查 2 个向量库），但每个库的检索仍依赖向量相似度计算；
   检索后：自定义 “文档去重 / 排序 / 压缩”，但数据源还是向量库返回的文档。
   五、关键细节（新手必知）
   为什么不用传统数据库？
   传统 MySQL/PG 只能做 “关键词匹配”（比如搜 “启动” 只能找到含 “启动” 的文档），但 Embedding + 向量库能做 “语义匹配”（搜 “咋跑？” 也能找到 “启动” 相关文档），这是 RAG 的核心价值。
   Advisor 帮你省了什么？
   你不用手动写 “调用 Embedding 转向量 → 调用向量库检索 → 拼接上下文” 这些重复代码，Advisor 全封装了，你只需配置参数（阈值、TopK、过滤条件）即可。
   相似度阈值 / TopK 的底层作用？
   这两个参数是 Advisor 传给向量数据库的检索参数：
   similarityThreshold=0.8：向量库只返回相似度≥0.8 的文档；
   topK=6：向量库按相似度排序后，只返回前 6 条。
   总结
   Advisor 底层核心：把 RAG 流程自动化，而流程的 “灵魂” 是 Embedding 模型（文本转向量）和向量数据库（向量检索）；
   无 Embedding → 无法做 “语义相似检索”，只能关键词匹配；
   无向量数据库 → 无法高效存储 / 检索向量，RAG 流程无法落地；
   你配置的 similarityThreshold、topK、filterExpression 等参数，最终都会传给向量数据库，是向量库的检索规则。









以 QuestionAnswerAdvisor 为例，它的执行时机完全符合 “拦截器逻辑”：
拦截时机：在 ChatClient 调用大模型之前执行；
拦截行为：修改用户的输入（把 “纯问题”→“问题 + 检索到的上下文”）；
最终效果：让大模型的输入被 “增强”，输出更准确。
从这个角度看，你说它像 “拦截器” 完全没问题 —— 都是 “在核心流程中间插一脚，改改内容”。
