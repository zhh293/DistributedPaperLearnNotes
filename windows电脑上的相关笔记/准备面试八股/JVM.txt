


既然要学习java虚拟机，先来了解一下虚拟机

一、JVM 是什么？（核心定义 + 通俗比喻）
JVM 是 Java Virtual Machine（Java 虚拟机）的缩写，你可以把它理解成：
一台 “虚拟的计算机”：它有自己的内存结构、执行指令的规则，像真实的物理计算机一样能执行代码；
Java 程序和操作系统之间的 “翻译官”：你写的 Java 代码（.java 文件）编译后生成的是字节码（.class 文件）（不是操作系统能直接执行的机器码），JVM 的核心工作就是把字节码 “翻译” 成对应操作系统（Windows/Linux/Mac）能识别的机器码，让 Java 程序能跨平台运行。



二、JVM 的核心作用（为什么学它？）
这是 JVM 最核心的价值，也是 Java 语言的核心优势：
跨平台（Write Once, Run Anywhere）
不同操作系统有对应的 JVM 实现（比如 Windows 版 JVM、Linux 版 JVM），只要你的 Java 字节码符合规范，就能在任何装了 JVM 的系统上运行，不用为不同系统重新编译代码。
自动内存管理（垃圾回收 GC）
JVM 内置了垃圾回收器（GC），会自动识别并回收 “不再使用的对象内存”，不用像 C/C++ 那样手动调用malloc/free管理内存，大大降低内存泄漏、野指针等问题。
安全校验
执行字节码前，JVM 会校验字节码的合法性（比如是否有非法指令、内存越界风险），避免恶意代码执行，保证程序运行安全。
执行字节码
通过 “解释器 + 即时编译器（JIT）” 组合执行字节码：解释器启动快（逐行执行），JIT 会把频繁执行的 “热点代码” 编译成机器码缓存，提升执行效率。
三、JVM 的核心组成（入门级框架）
不用一开始深究细节，先记住核心模块的分工：


JVM核心组成
├── 类加载子系统：加载.class文件到JVM（加载→链接→初始化）
├── 运行时数据区：JVM的内存空间（核心重点）
│   ├── 方法区：存储类信息、常量、静态变量（JDK8后叫“元空间”）
│   ├── 堆：存储所有对象实例（GC主要回收区域，线程共享）
│   ├── 虚拟机栈：每个线程独有，存储方法的局部变量、方法调用信息
│   ├── 本地方法栈：服务于本地方法（比如调用C/C++代码）
│   └── 程序计数器：记录线程执行的字节码地址（唯一不会内存溢出的区域）
├── 执行引擎：执行字节码（解释器+JIT+GC）
└── 本地方法接口（JNI）：让Java调用非Java代码（如操作系统底层API）





四、Java 程序的执行流程（直观理解）
用一个简单的流程帮你串联 JVM 的作用：
你编写Hello.java源文件 → 用javac Hello.java编译 → 生成Hello.class字节码文件；
执行java Hello命令 → JVM 的类加载子系统把Hello.class加载到方法区；
执行引擎（解释器）开始逐行解释字节码 → 把需要创建的对象分配到堆中，方法调用的临时数据（比如局部变量）存入虚拟机栈；
执行过程中，GC 会自动扫描堆中的对象，回收不再使用的对象内存；
最终，执行引擎把字节码转换成机器码，交给操作系统执行，输出结果。
总结
JVM 是 Java 跨平台和自动内存管理的核心，是 Java 程序运行的 “底层容器”；
JVM 的核心重点是运行时数据区（堆、虚拟机栈、方法区等），也是后续学习的核心；
Java 程序的执行本质是 “字节码通过 JVM 翻译成机器码” 的过程，JVM 屏蔽了不同操作系统的差异。




一、JVM 的位置：在整个计算机体系中的 “层级定位”
要理解 JVM 的位置，先看完整的计算机软件 / 硬件层级结构，JVM 的位置是操作系统之上、Java 应用程序之下，是连接两者的 “中间层”，具体层级如下（从底层到上层）：


┌─────────────────────────────────────────┐
│            Java应用程序（你的代码）         │ 比如HelloWorld、Spring项目
└─────────────────────┬───────────────────┘
                      │
┌─────────────────────▼───────────────────┐
│               JVM（Java虚拟机）           │ 不同系统有对应版本（Windows/Linux/Mac）
└─────────────────────┬───────────────────┘
                      │
┌─────────────────────▼───────────────────┐
│             操作系统（OS）               │ Windows/Linux/macOS
└─────────────────────┬───────────────────┘
                      │
┌─────────────────────▼───────────────────┐
│             硬件（CPU/内存/磁盘）         │ 物理计算机的硬件资源
└─────────────────────────────────────────┘


通俗比喻理解位置
你可以把整个计算机体系比作 “一家工厂”：
硬件是工厂的机器设备（CPU 是生产线、内存是原料仓、磁盘是仓库）；
操作系统是工厂的管理层，负责调度机器设备、分配资源；
JVM 是工厂里的 **“Java 专属生产线”**：管理层（OS）不管生产线具体怎么运作，只负责给生产线分配设备（CPU / 内存）；而这条生产线（JVM）只处理 Java “原料”（字节码），把它加工成管理层能识别的 “成品指令”；
Java 应用程序是要加工的 **“生产任务”**（比如生产一个 “HelloWorld” 产品）。
这个位置的核心价值
正因为 JVM 处在 “OS 之上、Java 程序之下”，才实现了 Java 的 “跨平台”：
你写的 Java 代码（任务）只需要符合 JVM 的 “生产标准”（字节码规范），不用管底层是 Windows 还是 Linux 的 “工厂管理层”；
不同系统的 JVM 会适配对应 OS 的 “管理规则”，把相同的字节码翻译成对应 OS 能执行的指令，最终调用硬件完成工作。
二、Java 程序执行流程（超详细拆解）
以你熟悉的HelloWorld为例，我把每一步拆到 “JVM 具体模块参与 + 内存变化 + 交互逻辑”，让你看到 JVM 在每一步的具体动作：
步骤 1：编写 Java 源文件（.java）
你在编辑器（IDEA/Notepad++）中编写Hello.java：
java
运行
public class Hello {
    public static void main(String[] args) {
        String message = "Hello, JVM!"; // 局部变量
        System.out.println(message);    // 输出语句
    }
}
这一步和 JVM 无关，只是你编写符合 Java 语法的 “源文件”，本质是纯文本文件。


步骤 2：编译成字节码（.class）
执行命令：javac Hello.java
这是Java 编译器（javac） 的工作，不是 JVM，但会生成 JVM 能识别的 “中间代码”—— 字节码；
编译后生成Hello.class文件，这个文件里不是操作系统能直接执行的机器码，而是 JVM 的字节码指令（比如aload_1、invokevirtual等）。


步骤 3：启动 JVM 并加载类（核心第一步）
执行命令：java Hello
这个命令的本质是启动 JVM 进程，并告诉 JVM 要执行的主类是Hello；


JVM 启动后，首先调用类加载子系统 处理Hello.class，分 3 个子步骤：
加载：类加载器（ClassLoader）从磁盘读取Hello.class文件，把字节码数据加载到 JVM 的方法区（存储类的元信息：类名、方法名、变量类型等）；
链接：验证字节码合法性（比如是否符合 JVM 规范）→ 准备内存（给静态变量分配内存）→ 解析（把符号引用转成直接引用，比如找到System.out.println的实际地址）；
初始化：执行类的静态代码（这里Hello没有静态代码，直接进入下一步）。



步骤 4：执行 main 方法（JVM 核心执行阶段）
main方法是 Java 程序的入口，JVM 会创建一个主线程，并为这个线程分配对应的内存区域：
虚拟机栈分配帧栈：主线程的虚拟机栈中会创建一个main方法的栈帧（每个方法调用对应一个栈帧），栈帧里存储方法的局部变量（比如message变量）、操作数栈（临时计算数据）；


解释器逐行执行字节码：
JVM 执行引擎的解释器 先逐行解释main方法的字节码：
第一步：创建字符串对象"Hello, JVM!"，并把对象分配到 JVM 的堆 中；
第二步：把堆中这个对象的引用（地址）存入main栈帧的局部变量message中（局部变量存在栈里，对象存在堆里）；
第三步：执行System.out.println(message)，JVM 会通过本地方法接口（JNI）调用底层 C/C++ 写的本地方法，最终找到操作系统的输出 API；


JIT 编译器优化（可选）：如果这段代码被频繁执行（成为 “热点代码”），JVM 的即时编译器（JIT） 会把字节码一次性编译成机器码，缓存起来，后续执行时直接用机器码，提升效率（解释器启动快，JIT 执行快，两者结合是 JVM 的 “混合执行模式”）。
步骤 5：内存管理（GC 参与）
执行过程中，堆里的对象由 JVM 的垃圾回收器（GC） 管理：
这里message对象在main方法执行完前都被引用，不会被回收；
当main方法执行结束，主线程销毁，message的引用消失，这个对象就变成 “垃圾”，后续 GC 扫描堆时会回收它的内存。
步骤 6：与操作系统 / 硬件交互
JVM 的执行引擎把字节码翻译成对应操作系统的机器码（比如 Windows 的 x86 机器码、Linux 的 ARM 机器码）；
机器码通过操作系统的系统调用（比如 Windows 的 API、Linux 的 syscall），调用硬件资源（CPU 执行指令、显卡 / 显示器输出文字）；
最终，显示器上输出Hello, JVM!，程序执行完成。
步骤 7：JVM 退出
main方法执行完毕，主线程结束，JVM 进程回收所有占用的内存（堆、栈、方法区等），然后退出，释放操作系统分配的资源。
三、总结
JVM 的核心位置是操作系统之上、Java 程序之下，这个位置是 Java 跨平台的关键，屏蔽了不同 OS 的底层差异；
Java 程序执行的核心逻辑是：源文件→编译成字节码→JVM加载类→执行引擎解释/编译字节码→内存管理→调用OS/硬件；
JVM 的核心模块（类加载子系统、运行时数据区、执行引擎、GC）在执行流程中各司其职，其中运行时数据区（堆 / 栈 / 方法区） 是理解 JVM 内存模型的核心。








JVM的架构模型

Java编译器输入的指令流基本上是一种基于栈的指令集架构，另外一种指令集架构则是基于寄存器的指令集架构


这个概念这么陌生，该怎么办呢，接下来我来给你们清晰的讲解一下



一、先从生活类比开始（核心入口）
我们把 “CPU 做计算” 想象成 “厨师做菜”：
栈式架构 = 厨师只有一叠盘子，只能拿最上面的盘子用，用完再放回去。
寄存器架构 = 厨师有一排抽屉，每个抽屉都有编号，想用哪个直接开哪个。
二、栈式指令集架构（Stack ISA）
1. 核心概念
所有计算都围绕 “栈”（就是那叠盘子）：
要算的数→先 “压栈”（放到盘子最上面）
运算指令→自动 “弹栈” 取最上面的 1-2 个数
结果→自动 “压回” 栈顶
关键：指令里不用写 “用哪个数”，默认就是栈顶的数。
2. 举个超简单例子：计算 1 + 2
栈式指令只有 3 步：
plaintext
push 1   ; 把1压到栈顶（盘子最上面放1）
push 2   ; 把2压到栈顶（现在最上面是2，下面是1）
add      ; 自动弹栈2和1，相加得3，再把3压回栈顶
你看，add 指令根本没说 “加 1 和 2”，它默认就加栈顶的两个数。
3. 特点
优点：指令短、简单，不用记编号，编译器好写。
缺点：只能碰栈顶，想拿下面的数得先把上面的挪开，慢（频繁读写内存）。
4. 使用场景
Java 虚拟机（JVM）
WebAssembly（Wasm）
.NET 的 CLR
简单的嵌入式虚拟机
一句话：适合 “跨平台、简单” 的虚拟机，不追求极致速度。
三、寄存器式指令集架构（Register ISA）
1. 核心概念
CPU 内部有一排高速 “抽屉”（叫寄存器），每个抽屉有编号（比如 r1、r2、r3）：
要算的数→先放到指定抽屉里
运算指令→必须明确写 “用哪个抽屉的数”
结果→放到指定抽屉里
关键：指令里必须写清楚 “源抽屉” 和 “目标抽屉”。
2. 同样算 1 + 2
寄存器式指令也是 3 步，但更明确：
plaintext
mov r1, 1   ; 把1放到r1抽屉
mov r2, 2   ; 把2放到r2抽屉
add r3, r1, r2  ; 把r1和r2的数相加，结果放到r3抽屉
你看，add 指令清清楚楚写了：用 r1、r2，结果放 r3。
3. 特点
优点：抽屉（寄存器）极快（比内存快几十倍），想用哪个直接拿，能并行、乱序计算，速度超快。
缺点：指令长，要记编号，编译器得费劲想 “怎么分配抽屉”。
4. 使用场景
所有真实物理 CPU：x86（电脑）、ARM（手机）、RISC-V（新兴开源）
高性能服务器、游戏机
一句话：适合 “要速度、要性能” 的真实硬件 CPU。





维度	栈式架构	寄存器架构
操作数来源	栈顶（默认，不用写）	寄存器（必须写编号）
速度	慢（频繁碰内存）	极快（只碰高速寄存器）
硬件复杂度	低（好做）	高（要很多寄存器、优化）
典型代表	JVM、Wasm	x86、ARM、RISC-V
用途	虚拟机、跨平台	真实 CPU、高性能



五、两者的联系（不是对立，是配合）
栈式底层还是寄存器：JVM 是栈式，但它跑在 x86/ARM 的寄存器 CPU 上 ——JVM 的 “栈” 其实存在内存里，真正计算时还是要加载到硬件寄存器。
寄存器也用栈：函数调用、存局部变量时，寄存器 CPU 也会用内存里的栈，但运算本身不靠栈，栈只是 “存数据的地方”，不是 “计算中心”。
可以互相翻译：编译器把高级语言→栈式字节码（JVM），JIT 即时编译器再把栈式字节码→寄存器机器码（x86）。
六、终极总结
栈式：像叠盘子，简单、通用、慢，适合虚拟机。
寄存器式：像一排抽屉，复杂、高速、强，适合真实 CPU。
关系：栈式是 “抽象层”，最终一定跑在寄存器硬件上。







JVM架构
Java编译器输入的指令流基本上是一种基于栈的指令集架构，另外一种指令集架构则

是基于寄存器的指令集架构。

具体来说:这两种架构之间的区别:

基于栈式架构的特点

设计和实现更简单，适用于资源受限的系统:

避开了寄存器的分配难题:使用零地址指令方式分配。

指令流中的指令大部分是零地址指令

，其执行过程依赖于操作栈。指令集更小，

编译器容易实现。

不需要硬件支持，可移植性更好，更好实现跨平台



基于寄存器架构的特点

典型的应用是x86的二进制指令集:比如传统的PC以及Android的Davlik虚

拟机。

指令集架构则完全依赖硬件，可移植性差

性能优秀和执行更高效;

花费更少的指令去完成一项操作。

在大部分情况下，基于寄存器架构的指令集往往都以一地址指令、二地址指令

和三地址指令为主，而基于栈式架构的指令集却是以零地址指令为主。



通俗的讲解一下
一、栈式架构：像食堂打饭的流水线
核心思路：所有操作都围绕一个「栈」（后进先出的容器）进行，就像食堂打饭时，餐盘一个个叠起来，只能从最上面拿或放。
类比场景：计算 3 + 4 × 2
第一步：先把 3 放进栈（餐盘堆最上面）。
→ 栈：[3]
第二步：再把 4 放进栈。
→ 栈：[3, 4]
第三步：把 2 放进栈。
→ 栈：[3, 4, 2]
第四步：执行乘法 4×2：
自动从栈顶取最后两个数 4 和 2，相乘得 8。
结果 8 放回栈顶，原来的 4 和 2 被 “吃掉”。
→ 栈：[3, 8]
第五步：执行加法 3+8：
取栈顶两个数 3 和 8，相加得 11。
结果 11 放回栈顶。
→ 栈：[11]

特点：

指令简单：不需要告诉计算机 “去哪找数据”，反正数据都在栈顶，指令只需要说 “做什么”（如 push、add、pop）。
跨平台友好：因为不依赖硬件寄存器，适合虚拟机（如 Java 的 JVM、Python 解释器），方便在不同电脑上运行相同代码。
缺点：频繁操作栈（压栈、弹栈）速度较慢，适合简单逻辑，但复杂计算时 “倒腾餐盘” 很麻烦。


二、寄存器架构：像厨房做菜的操作台
核心思路：计算机有多个「寄存器」（相当于厨房的小盘子），数据直接放在这些 “盘子” 里，指令需要明确告诉计算机 “去哪个盘子取数据”。
类比场景：同样计算 3 + 4 × 2
假设计算机有 3 个寄存器：A、B、C（相当于 3 个小盘子）。

第一步：把 3 放进寄存器 A。
→ 指令：MOV A, 3（Move 3 到 A 盘）
第二步：把 4 放进寄存器 B。
→ 指令：MOV B, 4
第三步：把 2 放进寄存器 C。
→ 指令：MOV C, 2
第四步：执行乘法 B×C，结果存到 B 中。
→ 指令：MUL B, C（Multiply B 和 C，结果放 B）
→ 此时 B 里是 8，C 还是 2。
第五步：执行加法 A+B，结果存到 A 中。
→ 指令：ADD A, B（Add A 和 B，结果放 A）
→ 最终 A 里是 11。

特点：

指令更 “具体”：每条指令必须指定寄存器（如 A、B），就像厨师做菜时会说 “把左边盘子的肉和右边盘子的菜炒在一起”。
速度快：寄存器在 CPU 内部，访问速度比内存（栈）快得多，适合高性能计算（如 x86、ARM 芯片）。
缺点：依赖硬件寄存器数量（通常只有几十个），复杂程序需要 “精打细算” 地分配寄存器（类似厨房盘子不够时要反复洗盘子）。

栈式架构：简单、跨平台，但像 “排队取餐” 一样慢一点。
寄存器架构：直接、高效，但像 “厨房做菜” 一样需要管理好盘子（寄存器）。

偏移量字节码指令	指令含义	局部变量表变化	操作数栈变化
0	iconst_2	将常量 2 压入操作数栈	无	栈：[2]
1	istore_1	将操作数栈顶的 2 弹出，存入局部变量表索引 1 的位置（即变量 i）	索引 1：2	栈：[]（空）
2	iconst_3	将常量 3 压入操作数栈	无	栈：[3]
3	istore_2	将操作数栈顶的 3 弹出，存入局部变量表索引 2 的位置（即变量 j）	索引 2：3	栈：[]
4	iload_1	从局部变量表索引 1 的位置（i）取出值 2，压入操作数栈	无	栈：[2]
5	iload_2	从局部变量表索引 2 的位置（j）取出值 3，压入操作数栈	无	栈：[2, 3]
6	iadd	弹出操作数栈顶的两个 int 值（2 和 3），执行加法运算，将结果 5 压回栈	无	栈：[5]
7	istore_3	将操作数栈顶的 5 弹出，存入局部变量表索引 3 的位置（即变量 k）	索引 3：5	栈：[]
8	return	方法执行完毕，返回（void 类型无返回值）	无	无



更通俗的分步解释（新手友好版）
0: iconst_2
JVM 说：“我把数字 2 先放到临时工作台（操作数栈）上。”
1: istore_1
JVM 说：“把工作台最上面的 2 拿下来，放到编号 1 的抽屉（局部变量表）里，这个抽屉就叫变量 i。”
2: iconst_3
JVM 说：“再把数字 3 放到临时工作台上。”
3: istore_2
JVM 说：“把 3 拿下来放到编号 2 的抽屉里，这个抽屉叫变量 j。”
4: iload_1
JVM 说：“从编号 1 的抽屉里把 2 拿出来，放回工作台。”
5: iload_2
JVM 说：“从编号 2 的抽屉里把 3 拿出来，也放到工作台（现在工作台有 2、3 两个数）。”
6: iadd
JVM 说：“把工作台上的 2 和 3 拿出来相加，得到 5，再把 5 放回工作台。”
7: istore_3
JVM 说：“把 5 拿下来放到编号 3 的抽屉里，这个抽屉叫变量 k。”
8: return
JVM 说：“main 方法执行完了，没有要返回的值，结束！”


JVM 执行方法的核心是操作数栈（临时计算）+ 局部变量表（存储变量） 的配合；
赋值操作：iconst_常量（压栈）→ istore_索引（存局部变量）；
运算操作：iload_索引（取变量压栈）→ iadd（计算）→ istore_索引（存结果）；
字节码指令的命名有规律：i=int、const= 常量、load= 读取、store= 存储、add= 加法。






一、JVM 生命周期的整体概述
JVM 的生命周期可以分为三个核心阶段：启动阶段、运行阶段、退出阶段。它本质上是一个进程级的生命周期 —— 一个 JVM 实例对应一个独立的操作系统进程，进程的生灭就是 JVM 实例的生灭。
简单来说：
启动：通过启动类加载器加载核心类，初始化 JVM 运行时环境；
运行：执行 Java 字节码，管理内存、线程、垃圾回收等核心功能；
退出：完成所有任务或触发退出条件，释放所有资源。
二、JVM 生命周期各阶段详解
1. 启动阶段（JVM 实例的创建）
JVM 的启动是由引导类加载器（Bootstrap ClassLoader） 触发的，核心是创建 JVM 实例并初始化运行时环境。
1.1 启动触发方式
手动启动：最常见的方式是通过命令行执行 java 命令（如 java MainClass），操作系统会创建一个新进程，在进程内初始化 JVM 实例；
嵌入式启动：通过 JNI（Java Native Interface）调用 JNI_CreateJavaVM() 函数，在 C/C++ 程序中嵌入 JVM 实例（如 Tomcat、Android 虚拟机的启动）。
1.2 启动核心步骤


flowchart TD
    A[执行java命令] --> B[操作系统创建进程]
    B --> C[加载JVM核心动态库（如jvm.dll/libjvm.so）]
    C --> D[初始化JVM参数（堆大小、GC策略等）]
    D --> E[创建引导类加载器]
    E --> F[加载核心类（如java.lang.Object、java.lang.String）]
    F --> G[初始化JVM运行时数据区（堆、方法区、虚拟机栈等）]
    G --> H[创建主线程（main线程）]
    H --> I[调用main方法，进入运行阶段]


1.3 关键细节
引导类加载器是 JVM 内置的加载器（非 Java 实现），负责加载 JRE/lib 下的核心类库（如 rt.jar）；
JVM 启动时会解析命令行参数（如 -Xms 初始堆、-Xmx 最大堆、-XX:+UseG1GC 垃圾回收器），并初始化运行时数据区的大小和规则；
启动阶段失败的常见原因：核心类库缺失、参数配置错误（如堆大小设置不合理）、操作系统资源不足。
2. 运行阶段（JVM 实例的核心生命周期）
JVM 启动后进入运行阶段，这是生命周期中最长的阶段，核心是执行 Java 字节码，同时管理内存、线程、垃圾回收等。
2.1 核心运行机制
类加载机制：运行时通过类加载器（引导类加载器、扩展类加载器、应用类加载器）的双亲委派模型，按需加载类的字节码到方法区，并创建 Class 对象；
字节码执行：
解释执行：逐行解释字节码为机器码执行（启动快，执行慢）；
即时编译（JIT）：热点代码（频繁执行的代码）被 JIT 编译器编译为本地机器码，缓存后直接执行（启动慢，执行快）；
内存管理：
虚拟机栈：为每个线程分配栈帧，存储局部变量、方法调用栈；
堆：存储对象实例，是垃圾回收（GC）的核心区域；
方法区：存储类元数据、常量池、静态变量等；
程序计数器：记录当前线程执行的字节码指令地址；
线程管理：JVM 内置主线程、GC 线程、编译线程等，所有 Java 线程对应操作系统的原生线程，由 JVM 调度管理；
垃圾回收（GC）：运行时自动回收堆中不再被引用的对象，释放内存，核心流程：标记 - 清除 / 复制 / 整理 → 分代回收（新生代、老年代）。
2.2 运行阶段的关键状态
正常运行：JVM 稳定执行字节码，GC 正常触发，内存使用在合理范围；
阻塞 / 等待：线程因锁、I/O、sleep () 等进入阻塞状态，JVM 仍存活，仅线程暂停执行；
异常运行：如 OOM（OutOfMemoryError），此时 JVM 不会立即退出，仅抛出异常，若程序未捕获且影响核心线程，可能触发退出。
3. 退出阶段（JVM 实例的销毁）
JVM 的退出是生命周期的终点，核心是释放所有资源并终止进程，退出分为正常退出和异常退出。
3.1 正常退出的触发条件
主线程（main 方法）执行完毕，且没有非守护线程（用户线程）运行；
调用 System.exit(int status) 方法（主动退出，status 为退出码，0 表示正常）；
调用 Runtime.getRuntime().exit(int status)（与 System.exit 等价）；
接收到操作系统的正常终止信号（如 Linux 的 SIGTERM 信号）。
3.2 异常退出的触发条件
未捕获的异常 / 错误导致核心线程终止（如 main 线程抛出 NullPointerException 且未捕获）；
接收到操作系统的强制终止信号（如 Linux 的 SIGKILL、Windows 的任务管理器结束进程）；
JVM 内部错误（如 JVM 崩溃、内存访问违规）；
硬件故障、断电等外部因素。
3.3 退出的核心步骤


flowchart TD
    A[触发退出条件] --> B[执行Shutdown Hook（关闭钩子）]
    B --> C[终止所有非守护线程]
    C --> D[执行Finalizer方法（回收未执行finalize的对象）]
    D --> E[释放JVM占用的内存、文件句柄、端口等资源]
    E --> F[终止JVM进程，返回退出码给操作系统]

3.4 关键细节：Shutdown Hook（关闭钩子）
JVM 提供了关闭钩子机制，允许程序在退出前执行自定义逻辑（如释放连接、保存数据）：

public class ShutdownHookDemo {
    public static void main(String[] args) {
        // 注册关闭钩子
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.out.println("JVM即将退出，执行关闭钩子：释放数据库连接");
        }));
        
        System.out.println("程序正常运行中...");
        // 模拟程序执行
        try {
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        // 主动触发退出
        System.exit(0);
    }
}



关闭钩子是普通线程，JVM 退出时会启动所有注册的钩子线程；
钩子线程执行时间有限，不能执行耗时操作；
强制终止（如 SIGKILL）不会执行关闭钩子。
三、JVM 生命周期的核心特性
单实例性：一个 JVM 实例对应一个操作系统进程，进程内的所有 Java 类、对象都属于该实例，不同 JVM 实例之间内存隔离；
线程驱动：JVM 的生命周期由线程驱动，只要有非守护线程运行，JVM 就不会退出；
资源隔离：JVM 实例的资源（内存、线程、文件句柄）独立于其他 JVM 实例，一个 JVM 崩溃不会影响其他 JVM；
可配置性：启动参数可定制 JVM 的运行行为（如内存大小、GC 策略），影响生命周期内的性能。





双亲委派机制

你希望我把双亲委派机制和之前提到的关闭钩子、JVM 生命周期核心特性这几个知识点，用更详细、全面且通俗易懂的方式讲解清楚，我会拆解每个概念的核心逻辑，结合例子和对比让你彻底理解。
一、双亲委派机制（类加载的核心规则）
1. 先搞懂：什么是类加载器？
在讲双亲委派前，先明确基础：JVM 运行时需要把.class 文件（字节码）加载到内存中，这个工作由类加载器（ClassLoader） 完成。JVM 内置了 3 层核心类加载器（按 “辈分” 从高到低）：

类加载器类型	作用	加载路径
引导类加载器（Bootstrap）	最顶层的加载器，JVM 原生实现（非 Java 代码），加载核心类库	JRE/lib/rt.jar（如 java.lang.Object）
扩展类加载器（Extension）	加载 JRE 的扩展类库	JRE/lib/ext/*.jar
应用类加载器（Application）	加载自己写的代码、第三方依赖（如 maven 包）	ClassPath 下的所有类（项目代码）


2. 双亲委派机制的核心定义
“双亲” 不是指父类，而是 “父级加载器”。核心规则：当一个类加载器需要加载某个类时，它不会自己先加载，而是先把请求交给父级加载器，父级加载器再交给它的父级，直到最顶层的引导类加载器；只有当父级加载器说 “我加载不了这个类”（找不到对应的.class 文件），子级加载器才会自己尝试加载。





flowchart TD
    A[应用类加载器收到加载"com.MyClass"的请求] --> B[先交给父级：扩展类加载器]
    B --> C[扩展类加载器再交给父级：引导类加载器]
    C --> D{引导类加载器能加载吗？}
    D -- 能（如java.lang.String） --> E[引导类加载器加载，返回Class对象]
    D -- 不能（如com.MyClass） --> F[扩展类加载器尝试加载]
    F --> G{扩展类加载器能加载吗？}
    G -- 能 --> H[扩展类加载器加载，返回Class对象]
    G -- 不能 --> I[应用类加载器自己加载]
    I --> J{应用类加载器能加载吗？}
    J -- 能 --> K[加载成功，返回Class对象]
    J -- 不能 --> L[抛出ClassNotFoundException]





4. 为什么要有双亲委派机制？（核心价值）
用通俗的话讲：防止类被重复加载、防止核心类被篡改。
例子 1（防止重复加载）：你自己写了一个java.lang.String类，按照双亲委派，加载请求会先到引导类加载器，它会加载 JDK 自带的String类，而不会让应用类加载器加载你写的，避免内存中出现两个String类；
例子 2（防止核心类被篡改）：如果没有双亲委派，恶意代码可以写一个java.lang.System类替换 JDK 原生的，导致系统安全问题，双亲委派从根本上杜绝了这种情况。


public class ParentDelegationDemo {
    public static void main(String[] args) {
        // 1. 获取当前类（ParentDelegationDemo）的类加载器
        ClassLoader appClassLoader = ParentDelegationDemo.class.getClassLoader();
        System.out.println("应用类加载器：" + appClassLoader); // sun.misc.Launcher$AppClassLoader@18b4aac2
        
        // 2. 获取应用类加载器的父级（扩展类加载器）
        ClassLoader extClassLoader = appClassLoader.getParent();
        System.out.println("扩展类加载器：" + extClassLoader); // sun.misc.Launcher$ExtClassLoader@4554617c
        
        // 3. 获取扩展类加载器的父级（引导类加载器，返回null，因为是JVM原生实现）
        ClassLoader bootstrapClassLoader = extClassLoader.getParent();
        System.out.println("引导类加载器：" + bootstrapClassLoader); // null
        
        // 4. 验证核心类由引导类加载器加载
        ClassLoader stringClassLoader = String.class.getClassLoader();
        System.out.println("String类的加载器：" + stringClassLoader); // null（代表引导类加载器）
    }
}




输出结果说明：
自定义类由应用类加载器加载；
JDK 核心类（如 String）由引导类加载器加载（返回 null 是因为引导类加载器不是 Java 对象）。
二、关闭钩子（Shutdown Hook）深度解析
你之前关注的 “关闭钩子是普通线程，JVM 退出时启动所有注册的钩子线程；钩子执行时间有限；强制终止不执行”，我拆成 3 个核心点讲透：
1. 本质：JVM 退出前的 “收尾线程”
关闭钩子是你注册到 JVM 的普通 Thread 对象，JVM 在正常退出时会自动启动这些线程，让你执行 “收尾工作”（比如关闭数据库连接、保存配置文件、释放网络端口）。
它是 “普通线程”：有线程的所有特性（可以设置优先级、是否为守护线程等），但 JVM 会保证在退出前启动它；
“启动所有注册的钩子线程”：你可以注册多个钩子，JVM 会并发启动它们（注意线程安全）。
2. 代码示例：注册多个关闭钩子


public class ShutdownHookDetailDemo {
    public static void main(String[] args) {
        // 钩子1：释放数据库连接
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.out.println("钩子1执行：关闭MySQL连接");
            // 模拟耗时操作（注意：这里不要写耗时逻辑！）
            try {
                Thread.sleep(100); // 短时间可以，长时间会被JVM中断
            } catch (InterruptedException e) {
                System.out.println("钩子1被中断：" + e.getMessage());
            }
        }, "DB-Hook"));
        
        // 钩子2：保存日志
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.out.println("钩子2执行：保存运行日志到文件");
        }, "Log-Hook"));
        
        System.out.println("程序正常运行中...");
        // 模拟程序执行5秒后主动退出
        try {
            Thread.sleep(5000);
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        System.out.println("准备退出程序...");
        System.exit(0); // 触发正常退出，执行钩子
    }
}


 
规则	                             通俗解释	             例子
钩子是普通线程，JVM 启动所有钩子	钩子不是特殊对象，就是 Thread；注册多少个，JVM 就启动多少个（并发执行）	上面例子中注册了 2 个钩子，JVM 退出时都会执行
钩子执行时间有限，不能耗时	JVM 不会无限等待钩子执行，若钩子执行太久（比如 sleep (10000)），会被强制中断	若钩子中写Thread.sleep(10000)，大概率会被 JVM 中断，收尾逻辑执行不全
强制终止不执行钩子	只有 “正常退出” 才执行，强制杀死进程不会触发	Linux 下kill -9 进程号、Windows 任务管理器结束进程，钩子完全不执行

一、双亲委派机制最初的核心设计目的（按优先级排序）
1. 首要目的：防止核心类库被篡改，保障 JVM 运行安全（最核心）
这是双亲委派机制被设计出来的第一驱动力。
设计背景：Java 的核心类（java.lang.String、java.lang.System、java.lang.Class等）是 JVM 运行的基础，如果这些类能被开发者随意替换，恶意代码可以轻松篡改核心逻辑（比如修改System.exit()让程序无法退出，或篡改String.equals()导致数据校验失效），整个 JVM 的安全性会完全崩塌。
机制的解决思路：把核心类的 “加载权” 完全收归最顶层的引导类加载器（Bootstrap ClassLoader） —— 这个加载器是 JVM 原生实现（非 Java 代码），开发者无法修改或干预，只能加载 JRE/lib 下官方签名的核心类库（如 rt.jar）。
通俗举例：就像银行的金库，只有总行的核心安保（引导类加载器）能打开，分支网点（应用类加载器）哪怕想偷换金库的东西，也得先交给总行安保，而总行安保只会用官方的 “金库内容”（原生核心类），根本不会用网点递过来的 “假货”（自定义核心类）。
2. 次要目的：避免类的重复加载，保证类的唯一性与 JVM 稳定
这是设计的第二核心目标，服务于 JVM 运行的稳定性。
设计背景：如果没有统一的加载规则，不同的类加载器可能加载同一个类（比如应用类加载器加载一次com.MyClass，扩展类加载器又加载一次），内存中会出现两个完全独立的Class对象 —— 而 JVM 判断 “两个类是否相同” 的标准是：类的全限定名 + 加载它的类加载器，这会导致 “同一个类在 JVM 中被识别为不同类”，引发类型转换异常（ClassCastException）、单例模式失效等问题。
机制的解决思路：通过 “先找父级” 的规则，让同一个类只会被 “最顶层能加载它的类加载器” 加载一次，保证内存中每个类的Class对象唯一。
通俗举例：公司报销流程，员工（应用类加载器）要报销，先交给部门经理（扩展类加载器），经理再交给总经理（引导类加载器）；如果总经理能处理（比如核心类），就直接处理，员工 / 经理不再重复处理；如果总经理处理不了（比如业务类），再退回给员工处理 —— 避免了多人重复处理同一件事，保证结果唯一。
二、补充：容易混淆的 “非设计目的”
很多人会误以为双亲委派的目的是 “分层管理类加载”，但这其实是机制的表现形式，而非设计目的 —— 分层是为了实现 “安全 + 唯一” 这两个核心目的而采用的手段，不是最终目标。
比如：
引导类加载器负责核心类、扩展类加载器负责扩展类、应用类加载器负责业务类 —— 这种分层是为了明确 “谁该加载什么类”，本质是为了让 “核心类只能被引导类加载器加载”，而非单纯为了分层。
三、用官方视角印证：JVM 规范中的设计初衷
在《Java 虚拟机规范》中，关于类加载器的章节明确提到：
类加载器的委派模型（双亲委派）主要为了两个目的：一是保证 Java 核心库的类型安全，二是保证类在整个 JVM 中的唯一性。
这和我们拆解的 “安全优先、稳定其次” 完全一致。
总结
双亲委派机制最核心、最初的设计目的是：保护 JVM 核心类库不被篡改，杜绝恶意代码通过替换核心类破坏 JVM 安全；
第二个重要设计目的是：避免同一个类被多次加载，保证类在 JVM 中的唯一性，防止类型混乱，保障 JVM 运行稳定；
“类加载器分层” 是实现上述目的的手段，而非设计目的本身。
















一、先明确：HotSpot VM 是什么？
HotSpot VM 是Oracle/Sun 官方主推的 Java 虚拟机实现，也是 OpenJDK、Oracle JDK 的默认 JVM，我们日常开发、部署中用到的 JVM 几乎都是 HotSpot（比如运行 Spring Boot 项目、Tomcat 的 JVM）。
它的名字 “HotSpot”（热点）精准概括了核心设计理念：识别并优化 “热点代码”（频繁执行的代码），通过即时编译（JIT）将字节码编译为本地机器码，大幅提升执行效率。
简单说：HotSpot = 解释执行（启动快） + JIT 编译（运行快） + 高效的垃圾回收（GC） + 完善的运行时管理，是兼顾 “启动速度” 和 “运行性能” 的工业级 JVM 实现。
二、HotSpot VM 的核心架构（从底层到上层）
HotSpot 的架构可以分为 “运行时数据区”“执行引擎”“类加载子系统”“垃圾回收系统”“本地接口（JNI）” 五大核心模块，我们先看整体架构图，再逐一拆解：



. 类加载子系统（基础：加载字节码）
这部分实现了我们之前讲的双亲委派机制，是 HotSpot 加载类的入口：
核心组件：引导类加载器（Bootstrap，C++ 实现）、扩展类加载器（Extension，Java 实现）、应用类加载器（Application，Java 实现）；
核心流程：加载（查找.class 文件）→ 验证（校验字节码合法性，防止恶意字节码）→ 准备（为静态变量分配内存、设置默认值）→ 解析（将符号引用转为直接引用）→ 初始化（执行静态代码块、赋值静态变量）；
HotSpot 特有优化：类缓存（加载后的 Class 对象会缓存，避免重复加载）、懒加载（类只有在被首次使用时才加载，而非启动时全部加载）。
2. 运行时数据区（核心：内存管理）
这是 HotSpot 存储数据的核心区域，也是 GC 的主要操作对象，完全遵循 JVM 规范，但 HotSpot 做了大量实现优化：


程序计数器	   记录当前线程执行的字节码指令地址，线程私有	无锁设计，性能极致，不会抛出 OOM

虚拟机栈	存储线程的栈帧（局部变量、方法调用栈），线程私有	栈帧大小可配置（-Xss 参数），支持栈动态扩展 / 收缩，避免栈溢出（StackOverflowError）

本地方法栈	为 Native 方法（如 JNI 调用的 C/C++ 方法）
提供栈空间，线程私有	
与虚拟机栈共享实现（HotSpot 不区分两者），减少内存开销

堆（Heap）	存储对象实例，所有线程共享，GC 核心区域	分代设计（新生代 Eden/S0/S1 + 老年代）、元空间（Metaspace）替代永久代（JDK8+）

方法区（Method Area）	存储类元数据、常量池、静态变量，所有线程共享	
JDK7 前：永久代（PermGen）；
JDK8+：元空间（Metaspace），直接使用本地内存，避免 PermGen OOM

常量池	存储字面量、符号引用，属于方法区	
JDK7 后移到堆中，提升 GC 效率；
支持动态常量（String.intern ()）



关键优化：元空间替代永久代
永久代（JDK7 及以前）：属于堆的一部分，大小固定，容易触发 OOM（比如大量动态生成类）；
元空间（JDK8+）：使用操作系统的本地内存，大小仅受物理内存限制，彻底解决 PermGen OOM 问题，这是 HotSpot 的核心改进之一。


3. 执行引擎（核心：执行字节码）
这是 HotSpot “HotSpot” 名字的来源，核心是 “解释执行 + JIT 编译” 的混合执行模式，兼顾启动速度和运行性能：


3.1 解释器（Interpreter）
作用：逐行将字节码翻译为机器码执行，不做优化；
优势：启动快（无需编译），适合冷启动、低频代码；
HotSpot 实现：模板解释器（Template Interpreter），为每个字节码指令预生成对应的机器码模板，比传统解释器快 30% 以上。


3.2 即时编译器（JIT，Just-In-Time Compiler）
作用：识别 “热点代码”（通过热点探测器统计执行次数），将其编译为优化后的本地机器码，缓存后直接执行；
热点判断标准：方法被调用次数达到阈值（默认 10000 次），或循环体执行次数达到阈值；
HotSpot 的双 JIT 编译器（核心特色）：



编译器	简称	特点	适用场景
客户端编译器	C1	编译速度快，优化程度低（简单优化：方法内联、常量折叠）	桌面应用、客户端程序（启动快）
服务端编译器	C2	编译速度慢，优化程度高（深度优化：循环展开、逃逸分析、锁消除）	服务器应用（运行快）




关键优化：逃逸分析

C2 编译器的核心优化手段，判断对象是否 “逃逸” 出方法 / 线程：
若对象未逃逸（仅在方法内使用）：触发 “栈上分配”（对象直接分配在虚拟机栈，而非堆），无需 GC；
若对象逃逸但无竞争：触发 “锁消除”（去掉不必要的 synchronized 锁）；
示例：
java
运行
public void test() {
    StringBuffer sb = new StringBuffer(); // sb仅在方法内使用，未逃逸
    sb.append("a").append("b");
    // C2编译时会消除sb的锁（StringBuffer是线程安全的，有锁），且将sb分配在栈上
}



4. 垃圾回收系统（GC：HotSpot 的核心竞争力）
HotSpot 内置了多款垃圾回收器，适配不同场景，是其成为工业级 JVM 的关键，核心设计是 “分代回收”（基于 “对象存活时间不同” 的假设）：
4.1 分代模型（HotSpot 的 GC 基础）
新生代（Young Generation）：存储新创建的对象，存活时间短，GC 频率高、速度快；
细分：Eden 区（80%）、Survivor 0 区（S0，10%）、Survivor 1 区（S1，10%）；
回收算法：复制算法（将存活对象从 Eden/S0 复制到 S1，清空原区域，效率高）；
老年代（Old Generation）：存储从新生代存活下来的对象，存活时间长，GC 频率低、速度慢；
回收算法：标记 - 整理算法（标记存活对象，将其移动到一端，清空另一端，避免内存碎片）；
元空间（Metaspace）：存储类元数据，单独回收（触发条件：元空间使用率达到阈值）。




HotSpot 的 GC 触发时机
新生代 GC（Minor GC）：Eden 区满时触发，只回收新生代；
老年代 GC（Major GC/Full GC）：老年代满、元空间满、Minor GC 后存活对象过多无法放入老年代时触发，回收整堆（新生代 + 老年代）；
Full GC 会导致 JVM 长时间暂停（Stop-The-World，STW），是性能优化的重点规避目标。


5. 本地接口（JNI）
作用：连接 Java 代码和本地代码（C/C++），让 HotSpot 能调用操作系统 API、本地库；
典型场景：HotSpot 的引导类加载器、GC 核心逻辑、网络 IO 都是通过 JNI 调用 C/C++ 实现；
注意：JNI 调用会脱离 JVM 管控，容易导致内存泄漏、崩溃，需谨慎使用。


三、HotSpot VM 的关键特性（区别于其他 JVM）
除了上述核心架构，HotSpot 还有几个独有的特性，使其成为主流：
1. 热点探测机制
实现：通过方法计数器（统计方法调用次数）和循环计数器（统计循环执行次数）识别热点代码；
优化：计数器溢出时触发 JIT 编译，编译完成后替换解释执行，实现 “边运行边优化”。

2. 自适应优化（Adaptive Optimization）
核心：JVM 运行时动态调整优化策略（比如根据 CPU 核心数切换 C1/C2 编译器、根据内存使用调整 GC 策略）；
举例：如果检测到应用是客户端程序（启动频繁、运行时间短），自动用 C1 编译器；如果是服务器程序（运行时间长），自动切换到 C2 编译器。


3. 完善的监控和诊断工具
HotSpot 配套了丰富的工具，方便排查问题：
jps：查看 JVM 进程；
jstat：监控 GC 状态、类加载情况；
jmap：导出堆快照、查看内存使用；
jstack：查看线程栈、排查死锁；
jvisualvm/JMC：图形化监控工具，分析性能瓶颈。


4. 跨平台性
HotSpot 的核心逻辑（如解释器、JIT 编译器）针对不同操作系统（Windows/Linux/macOS）做了适配，实现 “一次编写，到处运行”——Java 字节码在不同平台的 HotSpot 上都能执行。
四、HotSpot VM 的版本演进（关键里程碑）
了解演进能帮你理解其优化方向：
JDK 1.2：首次引入 HotSpot VM，替代 Classic VM，成为默认 JVM；
JDK 1.4：引入 C2 编译器，大幅提升服务器端性能；
JDK 6：优化 JIT 编译，引入 G1 GC（实验性）；
JDK 7：移除永久代，将常量池移到堆中；
JDK 8：正式移除永久代，替换为元空间，默认 GC 改为 Parallel GC；
JDK 9：将 G1 GC 设为默认 GC，引入模块化（Module）；
JDK 11：引入 ZGC（实验性），长期支持版（LTS）；
JDK 17：ZGC/Shenandoah 转正，成为生产可用的低延迟 GC。






JRockit 核心优势（对比 HotSpot）
启动后性能极致：纯 JIT 编译，启动时虽然慢（要编译所有代码），但运行后性能比 HotSpot 更优（尤其长时间运行的服务器程序）；
低延迟 GC：JRockit 的 JRT GC 能做到毫秒级 STW，适合金融交易、电信计费等 “不能长时间暂停” 的场景；
高可靠性：内置内存泄漏检测、死锁检测、线程分析等功能，且监控几乎无性能损耗；
简化调优：自动适配硬件（CPU / 内存），无需手动配置大量 GC 参数，调优成本低。
3. JRockit 核心劣势（为什么不如 HotSpot 主流）
启动慢：纯 JIT 编译导致启动时间长，不适合客户端应用、短生命周期应用（如脚本、测试程序）；
生态差：第三方工具（如 Arthas、MAT）对 JRockit 支持远不如 HotSpot；
功能单一：仅支持服务器端，不支持移动端、嵌入式等场景；
Oracle 战略调整：Oracle 将 JRockit 的核心特性（如低延迟 GC、JMC）整合到 HotSpot，JRockit 逐渐停止维护，目前主流场景已完全被 HotSpot 替代。







Taobao VM（淘宝虚拟机，全称 Alibaba Dragonwell，曾用名 Taobao JDK/Alibaba JDK）是阿里巴巴基于 OpenJDK 深度定制、面向大规模电商与云原生场景优化的企业级 JVM 发行版，核心目标是在高并发、大流量、长稳运行的生产环境中，实现更高性能、更低延迟、更强稳定性与可观测性。
一、核心定位与背景
定位：阿里巴巴内部全栈生产环境标准 JVM，同时对外开源（Dragonwell），面向电商、金融、云原生、微服务等高并发场景。
血统：基于 OpenJDK 主线（长期支持 LTS 版本，如 8/11/17）深度定制，兼容标准 Java SE 规范，可无缝替换 OpenJDK/Oracle JDK。
目标：解决大规模集群下的性能瓶颈、GC 延迟、内存占用、故障排查、资源利用率等生产痛点。
二、核心架构与关键模块
Taobao VM 在标准 HotSpot 架构基础上，做了大量生产级增强，核心模块如下：
1. 执行引擎（JIT 编译）
分层编译增强：优化 C1/C2 编译器调度，缩短热点代码预热时间，提升冷启动与稳态性能。
激进内联与逃逸分析：针对电商高频业务（如订单、商品、支付）做深度内联与栈上分配，减少对象创建与 GC 压力。
Profile 引导优化（PGO）：基于线上真实运行数据做离线 / 在线混合优化，让 JIT 更贴合实际业务模型。
AOT 支持：提供提前编译能力，消除 JIT 预热开销，适合容器化与短生命周期服务。
2. 垃圾回收（GC）系统（核心优势）
Taobao VM 对 GC 做了极致优化，是支撑阿里万亿级流量的关键：
G1 深度增强（G1-Plus）
大幅缩短 STW 暂停时间（目标 < 10ms，优于标准 G1）。
优化混合回收、 remembered set、并发标记，提升大堆（数十 GB）下的吞吐量与稳定性。
支持动态调整分区大小、自适应回收策略，适配电商流量波动。
ZGC/Shenandoah 定制化：在 LTS 版本中提前引入并增强低延迟 GC，满足金融 / 支付等微秒级延迟场景。
CMS 兼容与优化：对老版本服务提供兼容，并降低其碎片与停顿风险。
GC 日志与调优增强：提供更细粒度的 GC 事件、内存分配统计，内置自动调优建议。
3. 内存管理与运行时
元空间 / 堆优化：优化类元数据存储，降低元空间 OOM 风险；支持弹性堆伸缩，适配容器资源限制。
压缩指针与大页支持：默认启用压缩指针，降低 64 位环境内存开销；深度优化大页（HugePage）使用，提升 TLB 命中率。
对象分配优化：针对电商高频小对象做线程本地分配（TLAB）增强，减少锁竞争与 GC 扫描量。
共享类缓存（SCC）：类似 OpenJ9 的 SCC，多 JVM 实例共享已加载类，降低内存与启动开销。
4. 类加载与动态更新
类加载性能优化：双亲委派机制增强，并行加载、懒加载优化，提升启动与类解析速度。
热部署 / 热更新：内置生产级类热替换能力，支持不重启更新业务逻辑，降低发布影响。
模块化与安全增强：兼容 JPMS，提供更细粒度的类隔离与权限控制，适合多租户与微服务。
5. 监控、诊断与可观测性（生产级标配）
Arthas 深度集成：内置阿里开源的 Arthas 诊断工具，无侵入、低开销排查线上问题（CPU / 内存 / 锁 / 方法耗时）。
JFR 增强（Java Flight Recorder）：扩展事件类型，支持业务埋点、GC 细粒度、网络 / IO 事件，与阿里监控体系打通。
内存泄漏 / 死锁自动检测：内置生产级检测与告警，提前发现隐患。
全链路追踪集成：与阿里内部链路系统打通，实现 JVM 级别的调用链分析。
6. 云原生与容器优化
容器感知：自动识别容器资源限制（CPU / 内存配额），自适应调整 GC、线程池、堆大小。

内存结构









一、类加载器子系统的核心定位
首先要明确：类加载器子系统（ClassLoader Subsystem）是 JVM 的核心组成部分之一，它的核心职责是将编译后的.class字节码文件（无论是本地磁盘、网络、数据库等来源）加载到 JVM 的内存中，并生成对应的java.lang.Class对象，供后续的链接、初始化等操作使用。
简单比喻：类加载器就像 JVM 的 “快递员”，把硬盘上的.class文件（快递包裹）送到 JVM 内存（仓库），并完成 “拆包、验货、登记” 等一系列操作。
二、类加载器子系统的整体结构
类加载器子系统主要分为三个核心阶段，同时类加载器本身有明确的层级划分，先看整体结构：
2.1 类加载器的层级划分（核心！双亲委派模型）
JVM 中的类加载器并非单一实例，而是遵循 “双亲委派模型” 的层级结构，从顶层到底层分为 4 类（注意：“启动类加载器” 并非 Java 实现，其余是）：




类加载器类型	英文名称	核心职责	实现方式	加载路径（示例）
启动类加载器（根加载器）	Bootstrap ClassLoader	加载 JVM 核心类库（如java.lang、java.util等）	C/C++ 实现（JVM 内置）	$JAVA_HOME/jre/lib/rt.jar、resources.jar等
扩展类加载器	Extension ClassLoader	加载 JVM 扩展类库（非核心，但为 JVM 扩展功能）	Java 实现（sun.misc.Launcher$ExtClassLoader）	$JAVA_HOME/jre/lib/ext/*.jar
应用程序类加载器（系统类加载器）	Application ClassLoader	加载应用程序自身的类（classpath 下的所有类）	Java 实现（sun.misc.Launcher$AppClassLoader）	CLASSPATH环境变量指定的路径
自定义类加载器	Custom ClassLoader	开发者自定义的类加载器（如加载加密类、网络类、非 classpath 下的类）	继承ClassLoader实现	自定义路径（如磁盘特定目录、网络 URL）



关键细节：
启动类加载器没有父类加载器，且无法在 Java 代码中直接获取其实例（因为是 C/C++ 实现）；
扩展类加载器的父类加载器是启动类加载器（逻辑上，而非继承）；
应用程序类加载器的父类加载器是扩展类加载器；
自定义类加载器的父类加载器默认是应用程序类加载器。
2.2 类加载器子系统的三大核心阶段
类加载的完整流程分为加载（Loading）、链接（Linking）、初始化（Initialization） 三个阶段，其中链接又细分为验证、准备、解析三步，整体流程如下：



三、类加载的完整流程（逐阶段拆解）
3.1 第一阶段：加载（Loading）
核心目标：将.class文件的字节流读取到内存，并生成Class对象。
具体步骤：
查找并读取字节码：类加载器根据类的全限定名（如java.lang.String），从指定来源（磁盘、网络、jar 包等）查找对应的.class文件，读取其字节流；
将字节流转换为运行时数据结构：将读取的字节流解析为 JVM 能识别的运行时数据结构（存储在方法区）；
生成 Class 对象：在堆内存中创建一个java.lang.Class对象，作为该类在 JVM 中的唯一标识（后续所有对该类的操作都通过这个对象）。
关键细节：
同一个类被不同类加载器加载，会生成不同的Class对象（JVM 判断 “类是否相同” 的标准：全限定名 + 类加载器）；
加载阶段可以被自定义类加载器覆盖（重写ClassLoader的findClass()或loadClass()方法）。
3.2 第二阶段：链接（Linking）
链接阶段是将加载后的类数据整合到 JVM 运行时环境的过程，分为 3 个子步骤：
3.2.1 验证（Verification）
核心目标：确保加载的.class文件字节流符合 JVM 规范，防止恶意或错误的字节码导致 JVM 崩溃。
验证的主要内容：
文件格式验证：检查字节流是否符合 Class 文件格式规范（如魔数是否为0xCAFEBABE、版本号是否兼容当前 JVM 等）；
元数据验证：检查类的元数据（如类名、父类、接口）是否符合 Java 语法规范（如不能继承final类、不能出现非法方法重载等）；
字节码验证：检查字节码指令的逻辑是否合法（如指令执行顺序、操作数栈的类型匹配、不会出现栈溢出 / 空指针等）；
符号引用验证：检查符号引用（如引用的类、方法、字段）是否存在且可访问。
关键细节：验证阶段是可选的（可以通过-Xverify:none参数关闭），但生产环境不建议关闭，会带来安全风险。
3.2.2 准备（Preparation）
核心目标：为类的静态变量分配内存，并设置默认初始值（而非代码中定义的初始值）。
示例：
java
运行
public class Test {
    // 静态变量
    private static int num = 10;
    private static final String str = "hello";
}
准备阶段：为num分配 int 类型的内存，设置默认值0（而非 10）；
对于final修饰的静态常量（编译期常量）：准备阶段会直接设置为代码中的初始值（如str会被设置为"hello"），因为final常量在编译期就已确定。
关键细节：
仅处理静态变量，实例变量的内存分配在对象实例化时（堆内存），而非准备阶段；
内存分配的区域是方法区（JDK 8 及以后是元空间，JDK 7 及以前是永久代）。
3.2.3 解析（Resolution）
核心目标：将常量池中的符号引用转换为直接引用。
符号引用：以字符串形式描述的引用（如java.lang.String、add(int)），不直接指向内存地址；
直接引用：指向内存中具体对象 / 方法 / 字段的指针、偏移量等，可直接访问。
解析的主要内容：
类 / 接口解析：将符号引用的类名转换为对应的Class对象；
字段解析：将符号引用的字段名转换为该字段在类中的内存偏移量；
方法解析：将符号引用的方法名转换为该方法的直接引用（如方法区中的方法地址）。
关键细节：解析阶段是懒加载的 —— 不一定在准备阶段后立即执行，可能延迟到该符号引用首次被使用时才执行（如调用方法时）。
3.3 第三阶段：初始化（Initialization）
核心目标：执行类的静态代码块（static{}）和为静态变量赋值（执行代码中定义的初始值），这是类加载流程中首次执行 Java 代码的阶段。
初始化的触发条件（主动使用，JVM 规范规定）：
创建类的实例（new Test()）；
调用类的静态方法（Test.staticMethod()）；
访问类的静态变量（除了final常量）；
反射调用类（Class.forName("com.test.Test")）；
初始化子类时，父类会先被初始化；
JVM 启动时，执行主类（main()方法所在的类）。
初始化的执行顺序：
先执行父类的初始化（递归向上，直到java.lang.Object）；
按代码书写顺序执行静态变量的赋值语句和静态代码块。
示例：
java
运行
public class Parent {
    static {
        System.out.println("Parent 静态代码块");
    }
    public static int parentNum = 100;
}

public class Child extends Parent {
    static {
        System.out.println("Child 静态代码块");
    }
    public static int childNum = 200;
}

// 测试代码
public class Test {
    public static void main(String[] args) {
        System.out.println(Child.childNum);
    }
}
输出结果：
plaintext
Parent 静态代码块
Child 静态代码块
200
关键细节：
一个类只会被初始化一次（JVM 保证线程安全）；
被动使用不会触发初始化（如仅引用final常量、仅通过子类引用父类静态变量、数组创建Child[] arr = new Child[10]）。
四、核心机制：双亲委派模型
这是类加载器最核心的设计原则，理解它才能掌握类加载的核心逻辑。
4.1 双亲委派模型的定义
当一个类加载器收到类加载请求时，它不会自己先加载，而是先将请求委派给父类加载器，父类加载器再委派给它的父类加载器，直到顶层的启动类加载器；只有当父类加载器无法加载该类（在其加载路径中找不到对应的.class文件），子加载器才会尝试自己加载。
4.2 双亲委派模型的执行流程


4.3 双亲委派模型的核心作用
保证核心类的唯一性：如java.lang.String只会被启动类加载器加载，避免自定义的String类替换核心类（防止核心 API 被篡改）；
避免类的重复加载：父类加载器加载过的类，子加载器不会再加载，节省内存；
保证类加载的安全性：防止恶意代码伪造核心类（如自定义java.lang.System类）。
4.4 打破双亲委派模型的场景
虽然双亲委派模型是默认规则，但某些场景下需要打破（如 Tomcat 的类加载器）：
Tomcat 需要为不同 Web 应用加载各自的类（即使类名相同），因此自定义了类加载器，优先加载自身应用的类，再委派给父类加载器；
JDBC 的DriverManager（SPI 机制）：核心类由启动类加载器加载，但具体驱动实现（如 MySQL 驱动）在 classpath 下，需要应用程序类加载器加载，因此通过Thread.currentThread().getContextClassLoader()获取上下文类加载器打破委派。
五、类加载器的核心 API（Java 层面）
对于自定义类加载器，核心是继承java.lang.ClassLoader类，关键方法：

方法名	作用

自定义类加载器示例（加载本地磁盘指定路径的类）：
java
运行
import java.io.ByteArrayOutputStream;
import java.io.FileInputStream;
import java.io.IOException;

public class CustomClassLoader extends ClassLoader {
    // 自定义类加载路径
    private String classPath;

    public CustomClassLoader(String classPath) {
        this.classPath = classPath;
    }

    // 重写findClass方法，实现自定义加载逻辑
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            // 将全限定名转换为文件路径（如com.test.Test -> com/test/Test.class）
            byte[] classData = loadClassData(name);
            if (classData == null) {
                throw new ClassNotFoundException();
            }
            // 将字节数组转换为Class对象
            return defineClass(name, classData, 0, classData.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }

    // 读取指定类的字节数据
    private byte[] loadClassData(String className) throws IOException {
        String path = classPath + "/" + className.replace(".", "/") + ".class";
        try (FileInputStream fis = new FileInputStream(path);
             ByteArrayOutputStream bos = new ByteArrayOutputStream()) {
            int b;
            while ((b = fis.read()) != -1) {
                bos.write(b);
            }
            return bos.toByteArray();
        }
    }

    // 测试
    public static void main(String[] args) throws Exception {
        // 自定义类加载路径（如D:/myclasses）
        CustomClassLoader loader = new CustomClassLoader("D:/myclasses");
        // 加载自定义类
        Class<?> clazz = loader.loadClass("com.test.MyTest");
        // 输出类加载器
        System.out.println("类加载器：" + clazz.getClassLoader());
        // 创建实例
        Object obj = clazz.newInstance();
        System.out.println("实例：" + obj);
    }
}
总结
核心结构：类加载器子系统分为加载、链接（验证 / 准备 / 解析）、初始化三个阶段，类加载器本身遵循双亲委派模型，分为启动类、扩展类、应用程序类、自定义类加载器四层；
核心流程：加载（读字节流生成 Class 对象）→ 链接（验证合法性、准备静态变量、解析符号引用）→ 初始化（执行静态代码块和静态变量赋值）；
核心机制：双亲委派模型保证核心类的唯一性和安全性，自定义类加载器可重写findClass()打破委派（按需），JVM 通过 “全限定名 + 类加载器” 判断类是否相同。

























JVM面试题目


JVM 的内存结构主要分为以下几个部分：
程序计数器：可以看作是当前线程所执行的字节码的行号指示器，用于存储当前线程正在执行的 Java 方法的 JVM 指令地址。如果线程执行的是 Native 方法，计数器值为 null。是唯一一个在 Java 虚拟机规范中没有规定任何 OutOfMemoryError 情况的区域，生命周期与线程相同。


Java 虚拟机栈：每个线程都有自己独立的 Java 虚拟机栈，生命周期与线程相同。每个方法在执行时都会创建一个栈帧，用于存储局部变量表、操作数栈、动态链接、方法出口等信息。可能会抛出 StackOverflowError 和 OutOfMemoryError 异常。


本地方法栈：与 Java 虚拟机栈类似，主要为虚拟机使用到的 Native 方法服务，在 HotSpot 虚拟机中和 Java 虚拟机栈合二为一。本地方法执行时也会创建栈帧，同样可能出现 StackOverflowError 和 OutOfMemoryError 两种错误。



Java 堆：是 JVM 中最大的一块内存区域，被所有线程共享，在虚拟机启动时创建，用于存放对象实例。从内存回收角度，堆被划分为新生代和老年代，新生代又分为 Eden 区和两个 Survivor 区（From Survivor 和 To Survivor）。如果在堆中没有内存完成实例分配，并且堆也无法扩展时会抛出 OutOfMemoryError 异常。



方法区（元空间）：在 JDK 1.8 及以后的版本中，方法区被元空间取代，使用本地内存。用于存储已被虚拟机加载的类信息、常量、静态变量等数据。虽然方法区被描述为堆的逻辑部分，但有 “非堆” 的别名。方法区可以选择不实现垃圾收集，内存不足时会抛出 OutOfMemoryError 异常。



运行时常量池：是方法区的一部分，用于存放编译期生成的各种字面量和符号引用，具有动态性，运行时也可将新的常量放入池中。当无法申请到足够内存时，会抛出 OutOfMemoryError 异常。


直接内存：不属于 JVM 运行时数据区的一部分，通过 NIO 类引入，是一种堆外内存，可以显著提高 I/O 性能。直接内存的使用受到本机总内存的限制，若分配不当，可能导致 OutOfMemoryError 异常。












JVM 内存模型里的堆和栈有什么区别？
用途：栈主要用于存储局部变量、方法调用的参数、方法返回地址以及一些临时数据。每当一个方法被调用，一个栈帧（stack frame）就会在栈中创建，用于存储该方法的信息，当方法执行完毕，栈帧也会被移除。堆用于存储对象的实例（包括类的实例和数组）。当你使用 new 关键字创建一个对象时，对象的实例就会在堆上分配空间。
生命周期：栈中的数据具有确定的生命周期，当一个方法调用结束时，其对应的栈帧就会被销毁，栈中存储的局部变量也会随之消失。堆中的对象生命周期不确定，对象会在垃圾回收机制（Garbage Collection, GC）检测到对象不再被引用时才被回收。
存取速度：栈的存取速度通常比堆快，因为栈遵循先进后出（LIFO, Last In First Out）的原则，操作简单快速。堆的存取速度相对较慢，因为对象在堆上的分配和回收需要更多的时间，而且垃圾回收机制的运行也会影响性能。
存储空间：栈的空间相对较小，且固定，由操作系统管理。当栈溢出时，通常是因为递归过深或局部变量过大。堆的空间较大，动态扩展，由 JVM 管理。堆溢出通常是由于创建了太多的大对象或未能及时回收不再使用的对象。
可见性：栈中的数据对线程是私有的，每个线程有自己的栈空间。堆中的数据对线程是共享的，所有线程都可以访问堆上的对象。






栈中存的到底是指针还是对象？
在 JVM 内存模型中，栈（Stack）主要用于管理线程的局部变量和方法调用的上下文，而堆（Heap）则是用于存储所有类的实例和数组。

当我们在栈中讨论 “存储” 时，实际上指的是存储基本类型的数据（如 int, double 等）和对象的引用，而不是对象本身。

这里的关键点是，栈中存储的不是对象，而是对象的引用。

也就是说，当你在方法中声明一个对象，比如MyObject obj = new MyObject();，这里的 obj 实际上是一个存储在栈上的引用，指向堆中实际的对象实例。这个引用是一个固定大小的数据（例如在 64 位系统上是 8 字节），它指向堆中分配给对象的内存区域。










Java 堆（Heap）是 Java 虚拟机（JVM）中内存管理的一个重要区域，主要用于存放对象实例和数组。随着 JVM 的发展和不同垃圾收集器的实现，堆的具体划分可能会有所不同，但通常可以分为以下几个部分：


新生代（Young Generation）：新生代分为 Eden Space 和 Survivor Space。在 Eden Space 中，大多数新创建的对象首先存放在这里。Eden 区相对较小，当 Eden 区满时，会触发一次 Minor GC（新生代垃圾回收）。在 Survivor Spaces 中，通常分为两个相等大小的区域，称为 S0（Survivor 0）和 S1（Survivor 1）。在每次 Minor GC 后，存活下来的对象会被移动到其中一个 Survivor 空间，以继续它们的生命周期。这两个区域轮流充当对象的中转站，帮助区分短暂存活的对象和长期存活的对象。



老年代（Old Generation/Tenured Generation）：存放过一次或多次 Minor GC 仍存活的对象会被移动到老年代。老年代中的对象生命周期较长，因此 Major GC（也称为 Full GC，涉及老年代的垃圾回收）发生的频率相对较低，但其执行时间通常比 Minor GC 长。老年代的空间通常比新生代大，以存储更多的长期存活对象。


元空间（Metaspace）：从 Java 8 开始，永久代（Permanent Generation）被元空间取代，用于存储类的元数据信息，如类的结构信息（如字段、方法信息等）。元空间并不在 Java 堆中，而是使用本地内存，这解决了永久代容易出现的内存溢出问题。


大对象区（Large Object Space / Humongous Objects）：在某些 JVM 实现中（如 G1 垃圾收集器），为大对象分配了专门的区域，称为大对象区或 Humongous Objects 区域。大对象是指需要大量连续内存空间的对象，如大数组。这类对象直接分配在老年代，以避免因频繁的年轻代晋升而导致的内存碎片化问题。







如果有个大对象一般是在哪个区域？
大对象通常会直接分配到老年代。
新生代主要用于存放生命周期较短的对象，并且其内存空间相对较小。如果将大对象分配到新生代，可能会很快导致新生代空间不足，从而频繁触发 Minor GC。而每次 Minor GC 都需要进行对象的复制和移动操作，这会带来一定的性能开销。将大对象直接分配到老年代，可以减少新生代的内存压力，降低 Minor GC 的频率。
大对象通常需要连续的内存空间，如果在新生代中频繁分配和回收大对象，容易产生内存碎片，导致后续分配大对象时可能因为内存不连续而失败。老年代的空间相对较大，更适合存储大对象，有助于减少内存碎片的产生。






程序计数器的作用，为什么是私有的？
Java 程序是支持多线程一起运行的，多个线程一起运行的时候 cpu 会有一个调动器组件给它们分配时间片，比如说会给线程 1 分给一个时间片，它在时间片内如果它的代码没有执行完，它就会把线程 1 的状态执行一个暂停，切换到线程 2 去，执行线程 2 的代码，等线程 2 的代码执行到了一定程度，线程 2 的时间片用完了，再切换回来，再继续执行线程 1 剩余部分的代码。
我们考虑一下，如果在线程切换的过程中，下一条指令执行到哪里了，是不是还是会用到我们的程序计数器啊。每个线程都有自己的程序计数器，因为它们各自执行的代码的指令地址是不一样的呀，所以每个线程都应该有自己的程序计数器。






方法区中的方法的执行过程？
当程序中通过对象或类直接调用某个方法时，主要包括以下几个步骤：
解析方法调用：JVM 会根据方法的符号引用找到实际的方法地址（如果之前没有解析过的话）。
栈帧创建：在调用一个方法前，JVM 会在当前线程的 Java 虚拟机栈中为该方法分配一个新的栈帧，用于存储局部变量表、操作数栈、动态链接、方法出口等信息。
执行方法：执行方法内的字节码指令，涉及的操作可能包括局部变量的读写、操作数栈的操作、跳转控制、对象创建、方法调用等。
返回处理：方法执行完毕后，可能会返回一个结果给调用者，并清理当前栈帧，恢复调用者的执行环境。






String s = new String ("abc") 执行过程中分别对应哪些内存区域？
如果abc这个字符串常量不存在，则创建两个对象，分别是abc这个字符串常量，以及new String这个实例对象。如果abc这字符串常量存在，则只会创建一个对象。






引用类型有哪些？有什么区别？
引用类型主要分为强软弱虚四种：
强引用：指的就是代码中普遍存在的赋值方式，比如A a = new A()这种。强引用关联的对象，永远不会被 GC 回收。
软引用：可以用SoftReference来描述，指的是那些有用但不是必须要的对象。系统在发生内存溢出前会对这类引用的对象进行回收。
弱引用：可以用WeakReference来描述，它的强度比软引用更低一点，弱引用的对象在下一次 GC 的时候一定会被回收，而不管内存是否足够。
虚引用：也被称作幻影引用，是最弱的引用关系，可以用PhantomReference来描述，它必须和ReferenceQueue一起使用，同样的当发生 GC 的时候，虚引用也会被回收。可以用虚引用管理堆外内存。





弱引用了解吗？举例说明在哪里可以用？
Java 中的弱引用是一种引用类型，它不会阻止一个对象被垃圾回收。

在 Java 中，弱引用是通过 java.lang.ref.WeakReference 类实现的。弱引用的一个主要用途是创建非强制性的对象引用，这些引用可以在内存压力大时被垃圾回收器清理，从而避免内存泄漏。

弱引用的使用场景：
缓存系统： 弱引用常用于实现缓存，特别是当希望缓存项能够在内存压力下自动释放时。如果缓存的大小不受控制，可能会导致内存溢出。使用弱引用来维护缓存，可以让 JVM 在需要更多内存时自动清理这些缓存对象。

对象池： 在对象池中，弱引用可以用来管理那些暂时不使用的对象。当对象不再被强引用时，它们可以被垃圾回收，释放内存。

避免内存泄漏： 当一个对象不应该被长期引用时，使用弱引用可以防止该对象被意外地保留，从而避免潜在的内存泄漏。

示例代码：
假设我们有一个缓存系统，我们使用弱引用来维护缓存中的对象：

Java
import java.lang.ref.WeakReference;
import java.util.HashMap;
import java.util.Map;

public class CacheExample {

    private Map<String, WeakReference<MyHeavyObject>> cache = new HashMap<>();

    public MyHeavyObject get(String key) {
        WeakReference<MyHeavyObject> ref = cache.get(key);
        if (ref != null) {
            return ref.get();
        } else {
            MyHeavyObject obj = new MyHeavyObject();
            cache.put(key, new WeakReference<>(obj));
            return obj;
        }
    }

    // 假设MyHeavyObject是一个占用大量内存的对象
    private static class MyHeavyObject {
        private byte[] largeData = new byte[1024 * 1024 * 10]; // 10MB data
    }
}
核心逻辑解读：
在这个例子中，使用 WeakReference 来存储 MyHeavyObject 实例，当内存压力增大时，垃圾回收器可以自由地回收这些对象，而不会影响缓存的正常运行。

如果一个对象被垃圾回收，下次尝试从缓存中获取时，get() 方法会返回 null，这时我们可以重新创建对象并将其放入缓存中。因此，使用弱引用时要注意，一旦对象被垃圾回收，通过弱引用获取的对象可能会变为 null，因此在使用前通常需要检查这一点。












内存泄漏和内存溢出的理解？
内存泄漏： 内存泄漏是指程序在运行过程中不再使用的对象仍然被引用，而无法被垃圾收集器回收，从而导致可用内存逐渐减少。虽然在 Java 中，垃圾回收机制会自动回收不再使用的对象，但如果有对象仍然被不再使用的引用持有，垃圾收集器无法回收这些内存，最终可能导致程序的内存使用不断增加。

内存泄漏常见原因：
静态集合： 使用静态数据结构（如 HashMap 或 ArrayList）存储对象，且未清理。

事件监听： 未取消对事件源的监听，导致对象持续被引用。

线程： 未停止的线程可能持有对象引用，无法被回收。

内存溢出： 内存溢出是指 Java 虚拟机（JVM）在申请内存时，无法找到足够的内存，最终引发 OutOfMemoryError。这通常发生在堆内存不足以存放新创建的对象时。

内存溢出常见原因：
大量对象创建： 程序中不断创建大量对象，超出 JVM 堆的限制。

持久引用： 大型数据结构（如缓存、集合等）长时间持有对象引用，导致内存累积。

递归调用： 深度递归导致栈溢出（注：通常对应 StackOverflowError，但也属于广义内存问题）。



















JVM 内存结构有哪几种内存溢出的情况？
堆内存溢出：当出现Java.lang.OutOfMemoryError: Java heap space异常时，就是堆内存溢出了。原因是代码中可能存在大对象分配，或者发生了内存泄露，导致在多次 GC 之后，还是无法找到一块足够大的内存容纳当前对象。


栈溢出：如果我们写一段程序不断地进行递归调用，而且没有退出条件，就会导致不断地进行压栈。类似这种情况，JVM 实际会抛出StackOverFlowError；当然，如果 JVM 试图去扩展栈空间的时候失败，则会抛出OutOfMemoryError。


元空间溢出：元空间的溢出，系统会抛出Java.lang.OutOfMemoryError: Metaspace。出现这个异常的问题的原因是系统的代码非常多或引用的第三方包非常多或者通过动态代码生成类加载等方法，导致元空间的内存占用很大。


直接内存溢出：在使用ByteBuffer中的allocateDirect()的时候会用到，很多 Java NIO（像 Netty）的框架中被封装为其他的方法，出现该问题时会抛出Java.lang.OutOfMemoryError: Direct buffer memory异常。











类加载核心分为加载、链接（验证 / 准备 / 解析）、初始化 三个阶段（使用 / 卸载非核心考点，可略提），回答如下：


加载：通过类的全限定名获取.class 文件二进制字节流，将其转化为方法区（元空间）的运行时数据结构，同时在内存生成该类的Class对象（作为访问类数据的唯一入口）。


链接：
验证：校验.class 文件合法性（如魔数 0xCAFEBABE）、安全性，确保符合 JVM 规范；
准备：为静态变量分配内存并赋默认值（int=0、引用 = null），final static变量直接赋编译期确定的真实值；
解析：将常量池的符号引用替换为直接引用（内存地址 / 偏移量），定位目标对象。


初始化：执行编译器自动生成的<clinit>()方法，完成静态变量显式赋值、静态代码块执行；仅当类被 “主动使用”（new 实例、调用静态成员、反射、初始化子类、启动类）时触发，且<clinit>()由 JVM 保证线程安全，仅执行一次。











类加载器与双亲委派模型

启动类加载器（Bootstrap Class Loader）：这是最顶层的类加载器，负责加载 Java 的核心库（如位于jre/lib/rt.jar中的类），它是用 C++ 编写的，是 JVM 的一部分。启动类加载器无法被 Java 程序直接引用。

扩展类加载器（Extension Class Loader）：它是 Java 语言实现的，继承自ClassLoader类，负责加载 Java 扩展目录（jre/lib/ext或由系统变量java.ext.dirs指定的目录）下的 jar 包和类库。扩展类加载器由启动类加载器加载，并且父加载器就是启动类加载器。

系统类加载器（System Class Loader）/ 应用程序类加载器（Application Class Loader）：这也是 Java 语言实现的，负责加载用户类路径（ClassPath）上的指定类库，是我们平时编写 Java 程序时默认使用的类加载器。系统类加载器的父加载器是扩展类加载器。它可以通过ClassLoader.getSystemClassLoader()方法获取到。

自定义类加载器（Custom Class Loader）：开发者可以根据需求定制类的加载方式，比如从网络加载 class 文件、数据库、甚至是加密的文件中加载类等。自定义类加载器可以用来扩展 Java 应用程序的灵活性和安全性，是 Java 动态性的一个重要体现。











Java 中双亲委派是什么？有啥用？

Java 中的「双亲委派」是类加载机制的核心原则，简单说就是 「一个类加载器要加载类时，先让父加载器去尝试加载，只有父加载器加载不了，自己才会去加载」。这里的「双亲」并不是指真正的继承关系，而是类加载器之间的一种层级委派关系。


具体来说，Java 的类加载器有一套默认的层级结构：最顶层是 Bootstrap ClassLoader（启动类加载器，负责加载 JDK 核心类，如 java.lang.String），往下是 Extension ClassLoader（扩展类加载器，加载 JDK 扩展目录的类），再往下是 AppClassLoader（应用类加载器，加载我们自己写的类和第三方 jar 包），我们也可以自定义类加载器，放在最下层。


当某个类加载器（比如自定义加载器）收到加载类的请求时，它不会先自己动手，而是把请求「委派」给父加载器；父加载器同样会继续委派给它的父加载器，直到传到最顶层的启动类加载器。如果父加载器能找到并加载这个类，就直接返回；如果所有父加载器都加载不了（比如不在它们的加载范围内），子加载器才会自己去尝试加载。
举个例子：我们自己写了一个 java.lang.String 类，当 AppClassLoader 要加载它时，会先委派给 Extension ClassLoader，再委派给 Bootstrap ClassLoader。而启动类加载器发现自己已经加载过 JDK 自带的 String 类了，就直接返回这个类，不会去加载我们自定义的 String 类。


这种机制的核心作用有两个：

保证类的唯一性和安全性：避免同一个类被不同加载器重复加载，确保核心类（如 JDK 的 String、Integer）不会被篡改。比如上面的例子，防止我们自定义的 String 类替换掉 JDK 的核心类，否则可能引发安全问题（比如修改 String 的底层实现导致系统混乱）。

实现类的复用：核心类只需要被顶层加载器加载一次，所有子加载器都能共享这个类，减少内存消耗。
简单说，双亲委派就像「孩子找东西先问家长，家长解决不了了再自己找」，通过层级委派确保了 Java 核心类的安全和类加载的有序性，是 Java 运行时环境稳定的基础。



















双亲委派模型的作用

保证类的唯一性：通过委托机制，确保了所有加载请求都会传递到启动类加载器，避免了不同类加载器重复加载相同类的情况，保证了 Java 核心类库的统一性，也防止了用户自定义类覆盖核心类库的可能。

保证安全性：由于 Java 核心库被启动类加载器加载，而启动类加载器只加载信任的类路径中的类，这样可以防止不可信的类假冒核心类，增强了系统的安全性。例如，恶意代码无法自定义一个Java.lang.System类并加载到 JVM 中，因为这个请求会被委托给启动类加载器，而启动类加载器只会加载标准的 Java 库中的类。


支持隔离和层次划分：双亲委派模型支持不同层次的类加载器服务于不同的类加载需求，如应用程序类加载器加载用户代码，扩展类加载器加载扩展框架，启动类加载器加载核心库。这种层次化的划分有助于实现沙箱安全机制，保证了各个层级类加载器的职责清晰，也便于维护和扩展。

简化了加载流程：通过委派，大部分类能够被正确的类加载器加载，减少了每个加载器需要处理的类的数量，简化了类的加载过程，提高了加载效率。











什么是 Java 里的垃圾回收？如何触发垃圾回收？

垃圾回收（Garbage Collection, GC）是自动管理内存的一种机制，它负责自动释放不再被程序引用的对象所占用的内存，这种机制减少了内存泄漏和内存管理错误的可能性。垃圾回收可以通过多种方式触发，具体如下：


内存不足时：当 JVM 检测到堆内存不足，无法为新的对象分配内存时，会自动触发垃圾回收。
手动请求：虽然垃圾回收是自动的，开发者可以通过调用 System.gc() 或 Runtime.getRuntime().gc() 建议 JVM 进行垃圾回收。不过这只是一个建议，并不能保证立即执行。
JVM 参数：启动 Java 应用时可以通过 JVM 参数来调整垃圾回收的行为，比如：-Xmx（最大堆大小）、-Xms（初始堆大小）等。
对象数量或内存使用达到阈值：垃圾收集器内部实现了一些策略，以监控对象的创建和内存使用，达到某个阈值时触发垃圾回收。







判断垃圾的方法有哪些？
在 Java 中，判断对象是否为垃圾（即不再被使用，可以被垃圾回收器回收）主要依据两种主流的垃圾回收算法来实现：引用计数法和可达性分析算法。
引用计数法（Reference Counting）
原理：为每个对象分配一个引用计数器，每当有一个地方引用它时，计数器加 1；当引用失效时，计数器减 1。当计数器为 0 时，表示对象不再被任何变量引用，可以被回收。
缺点：不能解决循环引用的问题，即两个对象相互引用，但不再被其他任何对象引用，这时引用计数器不会为 0，导致对象无法被回收。
可达性分析算法（Reachability Analysis）
Java 虚拟机主要采用此算法来判断对象是否为垃圾。
原理：从一组称为 GC Roots（垃圾收集根）的对象出发，向下追溯它们引用的对象，以及这些对象引用的其他对象，以此类推。如果一个对象到 GC Roots 没有任何引用链相连（即从 GC Roots 到这个对象不可达），那么这个对象就被认为是不可达的，可以被回收。














Java 的 GC 机制你知道哪些？
Java 的 GC（垃圾回收）简单说就是「自动识别并回收不再使用的对象，释放内存空间」，避免内存泄漏。主要可以从 “哪些对象会被回收”“怎么回收”“回收器有哪些” 这几个角度来理解。
首先，判断一个对象是否该被回收，核心是看它「是否还被引用」。最经典的是「可达性分析」：以 GC Roots（比如虚拟机栈里的局部变量、静态变量、常量等）为起点，遍历对象的引用链，如果某个对象从 GC Roots 出发不可达，就会被标记为可回收对象。比如方法里的局部变量，方法执行完后出栈，它引用的对象如果没有其他引用，就会被标记。



然后是具体的回收算法。

标记 - 清除算法：标记 - 清除算法分为 “标记” 和 “清除” 两个阶段，首先通过可达性分析，标记出所有需要回收的对象，然后统一回收所有被标记的对象。标记 - 清除算法有两个缺陷，一个是效率问题，标记和清除的过程效率都不高，另外一个就是，清除结束后会造成大量的碎片空间。有可能会造成在申请大块内存的时候因为没有足够的连续空间导致再次 GC。


复制算法：为了解决碎片空间的问题，出现了 “复制算法”。复制算法的原理是，将内存分成两块，每次申请内存时都使用其中的一块，当内存不够时，将这一块内存中所有存活的复制到另一块上。然后再把已使用的内存整个清理掉。复制算法解决了空间碎片的问题。但是也带来了新的问题。因为每次在申请内存时，都只能使用一半的内存空间。内存利用率严重不足。


标记 - 整理算法：复制算法在 GC 之后存活对象较少的情况下效率比较高，但如果存活对象比较多时，会执行较多的复制操作，效率就会下降。而老年代的对象在 GC 之后的存活率就比较高，所以就有人提出了 “标记 - 整理算法”。标记 - 整理算法的 “标记” 过程与 “标记 - 清除算法” 的标记过程一致，但标记之后不会直接清理。而是将所有存活对象都移动到内存的一端。移动结束后直接清理掉剩余部分。


分代回收算法：分代收集是将内存划分成了新生代和老年代。分配的依据是对象的生存周期，或者说经历过的 GC 次数。对象创建时，一般在新生代申请内存，当经历一次 GC 之后如果对象还存活，那么对象的年龄 +1。当年龄超过一定值 (默认是 15，可以通过参数 -XX:MaxTenuringThreshold 来设定) 后，如果对象还存活，那么该对象会进入老年代。









gc触发的条件有哪些



1. Minor GC (Young GC) —— 新生代回收
这是最频繁的 GC，由 JVM 自动管理。

触发条件： Eden 区空间不足。

实现逻辑： 当 Java 程序尝试创建一个新对象（且该对象不是大对象）往 Eden 区放，但 Eden 区剩余连续空间无法容纳该对象时，立刻触发。

注意点： Survivor 区满了不会直接触发 Minor GC，它只是 Minor GC 的“搬运目的地”。

2. Major GC —— 老年代回收
主要针对 CMS 收集器或传统的 Serial Old/Parallel Old。

触发条件： 老年代空间达到设定的阈值。

实现逻辑： * CMS 收集器： 默认在老年代占用约 92%（可通过 -XX:CMSInitiatingOccupancyFraction 调节）时触发。

分配担保失败： 在进行 Minor GC 前，JVM 发现老年代最大的连续可用空间小于历次晋升对象的平均大小，为了避免 Full GC 风险，可能提前发起 Major GC。

3. Full GC —— 全堆回收
代价最高（STW 时间最长），回收新生代、老年代以及元空间。

触发条件：

老年代空间真正不足： 经过 Minor GC 后，Survivor 区放不下的对象晋升到老年代，而老年代也放不下。

元空间 (Metaspace) 空间不足： 加载了太多的类信息（如动态代理类、反射产生的类）。

显示调用： 程序代码中执行了 System.gc()（虽然只是建议，但通常会触发）。

CMS 运行失败（Concurrent Mode Failure）： CMS 异步回收时，用户线程产生垃圾过快，导致回收未完成老年代就满了。

空间分配担保失败： 统计发现历次晋升平均值大于老年代剩余空间。










G1各阶段的STW细节





1. Young GC 阶段：全量 STW
这是最常见的回收动作。当 Eden 角色（逻辑新生代）的 Region 数量达到阈值时触发。

是否 STW： 是，全程暂停。

核心操作： 根扫描（Root Scanning）、处理跨代引用（RSet 更新）、对象拷贝。

STW 原因： 涉及到 Region 之间大量对象的物理迁移。为了保证对象引用地址（指针）在移动过程中不失效，必须“冻结”所有用户线程。

2. 并发标记周期（Concurrent Marking Cycle）：间歇性 STW
这是为了给老年代 Region 做“体检”，确定哪些 Region 垃圾多，为 Mixed GC 铺路。

A. 初始标记（Initial Mark）
是否 STW： 是。

细节： 标记 GC Roots 能直接关联的对象。

专业点： G1 会通过 “隐式调用（Piggybacking）”，把这一步塞进一次正常的 Young GC 中顺便完成，所以你感觉不到额外的停顿。

B. 最终标记（Remark）
是否 STW： 是。

细节： 处理并发标记期间由于用户程序运行产生变动的引用记录。

算法支持： 使用 SATB（Snapshot-At-The-Beginning） 算法。虽然要停顿，但因为只处理增量变动，时间非常短。

C. 筛选回收（Cleanup）
是否 STW： 是。

细节： 统计各 Region 回收价值并排序。如果发现某个 Region 里面全是垃圾，会直接在这一步抹除。

注意： 虽然名字叫 Cleanup，但它并不在这个阶段搬运对象，它只是在“整理账本”。

3. Mixed GC 阶段：全量 STW
当老年代 Region 堆积到一定比例后触发。

是否 STW： 是，全程暂停。

核心操作： 回收全部的 Young Region + 选定的部分 Old Region（选垃圾最多的）。

专业点： 它是基于 复制算法（Copying） 的。G1 会根据你设定的 MaxGCPauseMillis（预期停顿时间）来计算这一波能收多少个 Old Region。如果时间快到了，它就收手，剩下的留给下次 Mixed GC。

4. Full GC 阶段：灾难性 STW
当 Mixed GC 速度跟不上分配速度，或者没有足够的空闲 Region 承接对象时触发。

是否 STW： 是，极其漫长。

核心操作： 整个堆（所有 Region）的标记-整理。








































常见垃圾回收器及特点
  
Serial 收集器（复制算法）：新生代单线程收集器，标记和清理都是单线程，优点是简单高效；

ParNew 收集器（复制算法）：新生代并行收集器，实际上是 Serial 收集器的多线程版本，在多核 CPU 环境下有着比 Serial 更好的表现；

Parallel Scavenge 收集器（复制算法）：新生代并行收集器，追求高吞吐量，高效利用 CPU。吞吐量 = 用户线程时间 /(用户线程时间 + GC 线程时间)，高吞吐量可以高效率地利用 CPU 时间，尽快完成程序的运算任务，适合后台应用等对交互响应要求不高的场景；

Serial Old 收集器（标记 - 整理算法）：老年代单线程收集器，Serial 收集器的老年代版本；

Parallel Old 收集器（标记 - 整理算法）：老年代并行收集器，吞吐量优先，是 Parallel Scavenge 收集器的老年代版本；

CMS (Concurrent Mark Sweep) 收集器（标记 - 清除算法）：老年代并行收集器，以获取最短回收停顿时间为目标，具有高并发、低停顿的特点，追求最短 GC 回收停顿时间；

G1 (Garbage First) 收集器（标记 - 整理算法）：Java 堆并行收集器，JDK1.7 提供的新收集器，基于 “标记 - 整理” 算法实现，不会产生内存碎片。核心特点是回收范围覆盖整个 Java 堆（新生代 + 老年代），区别于前六种仅回收新生代或老年代的收集器。













标记清除算法的缺点是什么？


主要缺点有两个：
一个是效率问题，标记和清除过程的效率都不高；
另外一个是空间问题，标记清除之后会产生大量不连续的内存碎片，空间碎片太多可能会导致，当程序在以后的运行过程中需要分配较大对象时无法找到足够的连续内存而不得不提前触发另一次垃圾收集动作。


垃圾回收算法哪些阶段会 stop the world？
标记 - 复制算法应用在 CMS 新生代（ParNew 是 CMS 默认的新生代垃圾回收器）和 G1 垃圾回收器中。

标记 - 复制算法可以分为三个阶段：
标记阶段，即从 GC Roots 集合开始，标记活跃对象；
转移阶段，即把活跃对象复制到新的内存地址上；
重定位阶段，因为转移导致对象的地址发生了变化，在重定位阶段，所有指向对象旧地址的指针都要调整到对象新的地址上。














区别一：使用范围不同
CMS：老年代专用收集器，需配合新生代的 Serial 或 ParNew 收集器一起使用。
G1：全堆收集器（覆盖新生代 + 老年代），无需结合其他收集器即可独立工作。


区别二：STW 时间控制不同
CMS：以最小化停顿时间为目标，但无法精准控制停顿时长。
G1：可预测垃圾回收停顿时间，通过 -XX:MaxGCPauseMillis 参数建立可预测的停顿模型，精准控制单次回收停顿。


区别三：内存碎片问题
CMS：基于「标记 - 清除」算法，回收后会产生大量不连续的内存碎片，易导致提前触发 Full GC。
G1：基于「标记 - 整理」算法（新生代用复制算法），回收后会整合空间，无内存碎片，分配大对象时更稳定。


区别四：回收过程不同
CMS：回收过程分为初始标记→并发标记→重新标记→并发清除，并发清除阶段与用户线程并行，会产生浮动垃圾。
G1：回收过程分为 Young GC→并发标记→最终标记→筛选回收→Mixed GC，按 Region 优先级回收，空间连续且无浮动垃圾。


区别五：浮动垃圾问题
CMS：并发清除阶段会产生浮动垃圾，需预留内存空间存放；若浮动垃圾过多，会退化为 Serial Old 收集器，效率大幅下降。
G1：无浮动垃圾问题，并发清理阶段产生的可回收对象会留到下次回收处理；若预留内存不足会触发 Concurrent Mode Failure，此时会切换到 Serial Old 收集方式。










适用场景对比
CMS 适用场景
低延迟需求：对停顿时间要求敏感的应用。
老年代收集：主要针对老年代进行垃圾回收。
内存较小场景：堆内存较小（通常 <4G），碎片化问题可通过定期 Full GC 缓解。
G1 适用场景
大内存堆：适用于 GB 级以上大堆内存的场景，能高效管理大容量内存。
对内存碎片敏感：需要避免内存碎片、稳定分配大对象的场景。
平衡性能需求：需要在低停顿和高吞吐量之间取得平衡，且对停顿时间有明确目标的场景。















三种 GC 的区别和触发场景
Minor GC (Young GC)
作用范围：只针对年轻代进行回收，包括 Eden 区和两个 Survivor 区（S0 和 S1）。
触发条件：当 Eden 区空间不足时，JVM 会触发一次 Minor GC，将 Eden 区和一个 Survivor 区中的存活对象移动到另一个 Survivor 区或老年代（Old Generation）。
特点：通常发生得非常频繁，因为年轻代中对象的生命周期较短，回收效率高，暂停时间相对较短。



具体操作

依托算法：复制算法（Copying Algorithm）

为什么用这个算法？ 因为新生代里的对象 98% 都是“朝生夕死”的（比如一个方法里的局部变量）。既然活下来的对象很少，最快的方法就是把活着的挑出来带走，剩下的直接全部干掉。

具体操作流程：

当 Eden 区快满时，触发 Minor GC。

GC 线程会暂停所有用户的业务线程（这叫 STW，Stop The World，不过时间极短）。

扫描 Eden 区和当前在使用的一个 Survivor 区（From 区），把所有存活的对象复制到另一个空的 Survivor 区（To 区）里，并且让这些对象的“年龄” +1。

直接清空 Eden 区和 From 区的所有内存（垃圾全被干掉了）。

From 区和 To 区的角色互换，等待下一次 Minor GC。

特殊情况： 如果 To 区装不下这些存活对象，或者某个对象的年龄达到了阈值（默认 15 岁），这些对象就会被直接“晋升”到老年代。










Major GC
作用范围：主要针对老年代进行回收，但不一定只回收老年代。
触发条件：当老年代空间不足时，或者系统检测到年轻代对象晋升到老年代的速度过快，可能会触发 Major GC。
特点：相比 Minor GC，Major GC 发生的频率较低，但每次回收可能需要更长的时间，因为老年代中的对象存活率较高。




注意，在官方标准中，只有 CMS 垃圾回收器 会单独触发这种只收集老年代的 Major GC。

依托算法：标记-清除算法（Mark-Sweep Algorithm）

为什么用这个算法？ 老年代里装的都是“老油条”（生命周期长的对象，比如 Spring 的单例 Bean、连接池）。这里的对象存活率极高，如果还用“复制算法”，不仅没有多余的空间给你复制，而且搬运大量存活对象的成本太高了。

具体操作流程（以 CMS 为例）：

老年代空间使用率达到某个阈值（比如 92%）时触发。

标记阶段： 顺着根节点（GC Roots），把所有活着的对象打上“存活”的标签。

清除阶段： 直接把没有打标签的垃圾对象清理掉，把位置空出来。

痛点： 标记清除算法会产生内存碎片。清理完后，内存里东空一块西空一块，如果这时候来了一个超级大对象，发现没有连续的空间放得下，就会被迫触发 Full GC。











Full GC
作用范围：对整个堆内存（包括年轻代、老年代以及永久代 / 元空间）进行回收。
触发条件：
直接调用 System.gc() 或 Runtime.getRuntime().gc() 方法时，虽然不能保证立即执行，但 JVM 会尝试执行 Full GC。

Minor GC（新生代垃圾回收）时，如果存活的对象无法全部放入老年代，或者老年代空间不足以容纳存活的对象，则会触发 Full GC，对整个堆内存进行回收。
当永久代（Java 8 之前的版本）或元空间（Java 8 及以后的版本）空间不足时。


特点：Full GC 是最昂贵的操作，因为它需要停止所有的工作线程（Stop The World），遍历整个堆内存来查找和回收不再使用的对象，因此应尽量减少 Full GC 的触发


这是 JVM 最不愿意看到的“终极重度大扫除”。它会把整个新生代、老年代，甚至方法区（元空间）全部清理一遍。

依托算法：标记-整理算法（Mark-Compact Algorithm）

为什么用这个算法？ 因为 Full GC 要彻底解决内存碎片的问题，给大对象腾出连续的空间。

具体操作流程：

当老年代空间不足、元空间不足，或者程序里手动调用了 System.gc() 时触发。

触发漫长的 STW (Stop The World)，整个系统仿佛卡死了一样。

标记阶段： 像 Major GC 一样，先标记出全堆所有存活的对象。

整理阶段（核心）： 把所有存活的对象，像推土机一样全部往内存的一端移动。

直接清理掉边界以外的所有空间。这样清理完后，存活的对象整整齐齐排在左边，右边是一整块干净的、连续的空闲内存。




























G1 回收器的特色是什么？
G1 的特点：
G1 最大的特点是引入分区的思路，弱化了分代的概念。
合理利用垃圾收集各个周期的资源，解决了其他收集器、甚至 CMS 的众多缺陷。


G1 相比较 CMS 的改进：
算法：G1 基于标记 - 整理算法，不会产生空间碎片，在分配大对象时，不会因无法得到连续的空间而提前触发一次 FULL GC。


停顿时间可控：G1 可以通过设置预期停顿时间（Pause Time）来控制垃圾收集时间，避免应用雪崩现象。

并行与并发：G1 能更充分地利用 CPU 多核环境下的硬件优势，来缩短 stop the world 的停顿时间。



GC 只会对堆进行 GC 吗？


JVM 的垃圾回收器不仅仅会对堆进行垃圾回收，它还会对方法区进行垃圾回收。

堆（Heap）：堆是用于存储对象实例的内存区域。大部分的垃圾回收工作都发生在堆上，因为大多数对象都会被分配在堆上，而垃圾回收的重点通常也是回收堆中不再被引用的对象，以释放内存空间。


方法区（Method Area）：方法区是用于存储类信息、常量、静态变量等数据的区域。虽然方法区中的垃圾回收与堆有所不同，但是同样存在对不再需要的常量、无用的类信息等进行清理的过程。




















Eden 和 Survivor 比例、回收流程（核心必考点！你漏了比例）
1. 核心比例（面试官必问）
HotSpot 虚拟机默认：Eden : Survivor0 : Survivor1 = 8 : 1 : 1
Eden 占新生代 80%
两个 Survivor（S0/S1，又叫 From/To）各占 10%
2. 回收流程（Minor GC）
新对象优先在 Eden 区分配；
Eden 区满 → 触发 Minor GC；
标记 Eden + 存活的 Survivor 区，存活对象复制到空的 Survivor；
清空 Eden 和原 Survivor，交换 From/To 角色；
每次复制，对象年龄 + 1；
永远保证一个 Survivor 是空的，无内存碎片。






对象进入老年代的 4 个条件（你只记了 1 个，补全满分）

年龄阈值达标（你说的）
默认年龄15（对象头用 4 位存储年龄，最大值就是 15），每次 Minor GC 年龄 + 1，达到阈值直接进老年代。

大对象直接进入
超过-XX:PretenureSizeThreshold设置的大小，直接分配到老年代，避免新生代复制开销。


动态年龄判断
Survivor 区中，相同年龄的对象总大小 > Survivor 空间的一半，年龄≥该值的对象直接进老年代（不用等 15）。


Survivor 空间不足（分配担保）
Minor GC 后，存活对象放不下 Survivor 区，直接进入老年代。










 三色标记是什么？
是 CMS/G1 并发标记阶段 用的算法（GC 和用户线程同时跑），把对象分为三种颜色：
白色：没被 GC 扫描 → 默认为垃圾
灰色：自己扫了，子对象没扫 → 正在处理
黑色：自己 + 子对象全扫完 → 存活对象


漏标问题（最核心）
什么是漏标？
本该存活的白色对象，被误判为垃圾回收 → 程序崩溃

漏标必须同时满足 2 个条件（缺一不可）
黑色对象 指向了 白色对象
所有灰色对象 到 这个白色对象的引用 全部断开

解决方案（面试必背）
CMS：用增量更新 → 黑色对象引用白色对象时，把黑色变回灰色，重新扫描

讲一下G1垃圾回收算法吧，G1这个玩意还是蛮神奇的

最初我了解到JVM的堆大致分为这么两个部分，新生代和老年代，新生代采用Minor gc，老年代使用Major gc，Minor GC（新生代垃圾回收）时，如果存活的对象无法全部放入老年代（也就是说Minor gc的时候如果Survivor区存不下的时候，会迁移到老年代），或者老年代空间不足以容纳存活的对象，则会触发 Full GC，对整个堆内存进行回收。

垃圾回收器CMS是针对老年代回收的，采用的标记清除算法，这个我是知道的，但是G1回收器的回收全过程我听得好懵逼，到底是怎么一回事呢，什么region，什么混合回收，跟我学到的垃圾回收算法，堆的分类什么的完全没有重合的点，于是呢，我广查资料，终于还是搞明白了这个玩意儿的真面目。。。。



1. 物理上的颠覆：什么是 Region？
在之前的认知里，堆内存就像一块大蛋糕，被狠狠地切成了两半：左边一大块叫新生代，右边一大块叫老年代。这就是物理隔离。

G1 的做法是：把整块大蛋糕切成了几千个一模一样的小方块。 这些小方块就叫 Region（区域）。

旧知识重合点：G1 里依然有 Eden 区、Survivor 区和老年代（Old 区）。

不同点：它们不再是固定的一大片连续内存了。这几千个 Region 中，系统会动态指定：这 50 个小方块现在当 Eden 用，那 20 个当 Survivor 用，还有 100 个当老年代用。

巨大优势：如果某个当 Eden 的 Region 被清空了，它马上可以被重新标记为老年代去装大对象。身份是动态流转的！

除此之外，G1 还多了一个特殊的 Region 叫 Humongous（巨型区），专门用来存那种比半个 Region 还要大的超级大对象（以前这种大对象是直接塞进老年代的）。

2. 核心思想：为什么叫 G1 (Garbage-First)？
G1 的中文直译是“垃圾优先”。什么意思呢？

以前的 CMS 清理老年代，是一次性把整个老年代扫一遍，如果老年代很大，停顿时间（STW）就会很长。
G1 因为把内存切成了小方块（Region），它可以计算出每个方块里有多少垃圾。哪个方块里的垃圾最多，回收它带来的收益最大，G1 就优先回收哪个方块。 绝不干那种为了几根杂草把整个操场翻一遍的蠢事。

3. 彻底搞懂“混合回收 (Mixed GC)”
这是你最懵的地方。我们把 G1 的工作模式和你熟悉的 Minor GC、Full GC 对接一下：

Young GC（相当于你熟悉的 Minor GC）：
当 Eden 类型的 Region 被装满了，触发 Young GC。G1 会把存活的对象复制到 Survivor 类型的 Region 中，或者晋升到 Old 类型的 Region 中。这跟你学过的没有任何区别，只不过是在小方块之间搬运。

并发标记（类似 CMS 的标记阶段）：
当整个堆的内存使用率达到一个阈值（默认 45%），G1 就会在后台偷偷开始扫描，计算出每个 Old Region 里面有多少存活对象，有多少垃圾。

Mixed GC（混合回收 —— G1 的杀手锏）：
标记完成后，就进入了 Mixed GC 阶段。它回收什么呢？
它不仅回收所有的新生代 Region，还会挑出那些“垃圾最多”的部分老年代 Region 一起回收！
这也就是它叫“混合”的原因：新生代和老年代混合在一起收。通过控制一次挑多少个老年代 Region，G1 就能精准控制垃圾回收的停顿时间（比如你设置最多停顿 200ms，它就看 200ms 内能收多少个老年代 Region，剩下的下次再说）。

Full GC（最后的兜底）：
如果程序写得太烂，垃圾产生的速度实在太快，G1 搬运对象的时候发现没有任何空的 Region 可以用了，就会退化成惨烈的 Full GC（全程单线程或多线程 Stop The World，极慢）。G1 的终极目标就是尽量避免 Full GC。
