1. NEW（新建状态）
定义：用 new Thread() 创建了线程对象，但还没有调用 start() 方法。
特点：线程未启动，只是一个普通 Java 对象。
状态转换：调用 start() → 进入 RUNNABLE。
2. RUNNABLE（可运行状态）⭐【重点】
定义：Java 把操作系统的 就绪态（Ready） + 运行态（Running）合并为这一个状态！
就绪：线程已经启动，等待 CPU 分配时间片；
运行：线程正在 CPU 上执行代码。
触发：调用 start() 后，线程直接进入该状态。
这是纠正你之前的误区：Java 没有单独的「就绪态」，统一叫 RUNNABLE。
3. BLOCKED（阻塞状态）
定义：线程等待获取 synchronized 锁，被挡在同步代码块 / 方法外面。
触发：想进入 synchronized 修饰的代码，但锁被其他线程持有。
特点：被动等待，只有拿到锁才能回到 RUNNABLE。
4. WAITING（无限等待状态）
定义：线程无限期等待，必须由其他线程显式唤醒，不会自动醒来。
触发方法（无参）：
Object.wait()、Thread.join()、LockSupport.park()
状态转换：被 notify()/notifyAll() 唤醒 → 回到 RUNNABLE/BLOCKED。
5. TIMED_WAITING（限时等待状态）
定义：线程有时间限制的等待，时间一到自动唤醒，也可以提前唤醒。
触发方法（带时间参数）：
Thread.sleep(long)、Object.wait(long)、Thread.join(long)
再次纠正你的错误：sleep() 进入的是 TIMED_WAITING，不是 WAITING！
6. TERMINATED（终止状态）
定义：线程执行完 run() 方法正常结束，或因异常终止。
特点：线程死亡，无法再次调用 start() 重启（会抛异常）。




方法	               状态转换路径
thread.start()	NEW → RUNNABLE
Thread.sleep(1000)	RUNNABLE → TIMED_WAITING → 时间到 → RUNNABLE
obj.wait()	RUNNABLE → WAITING → 被唤醒 → RUNNABLE




NEW：新建未启动
RUNNABLE：可运行（就绪 + 运行）
BLOCKED：等 synchronized 锁
WAITING：无限等（需手动唤醒）
TIMED_WAITING：限时等（sleep / 带参 wait）
TERMINATED：执行完毕 / 终止
四、面试高频核心区分
sleep() vs wait()
sleep()：TIMED_WAITING，不释放锁；
wait()：WAITING，释放锁。
BLOCKED vs WAITING
BLOCKED：只等 synchronized 锁；
WAITING：主动等待，需要被其他线程唤醒。

方法重载（Overload）和重写（Override）的区别		


特性	方法重载（Overload）	方法重写（Override）
定义	同一类中，方法名相同、参数列表（个数 / 类型 / 顺序）不同	子类中，重写父类的方法（方法名、参数列表、返回值完全一致）
返回值	无强制要求（可不同）	子类返回值需≤父类返回值范围（协变返回）
访问修饰符 	无强制要求	        子类访问权限≥父类（如父类 public，子类不能 private）
异常	  无强制要求	                      子类抛出异常≤父类异常范围（不能抛父类没有的检查异常）
绑定时机	编译期绑定（静态绑定）	运行期绑定（动态绑定）
核心目的	方便调用，同一功能不同入参	实现多态，子类自定义父类逻辑






哪些方法不能被重写？
final 修饰的方法：final 表示 “最终”，禁止子类修改，无法重写；
static 修饰的方法：静态方法属于类而非实例，子类只能 “隐藏”（重新定义同名静态方法），而非重写；
private 修饰的方法：私有方法仅在当前类可见，子类无法访问，自然无法重写；
构造方法：构造方法名与类名一致，子类无法重写（子类构造方法是super()调用父类，而非重写）；
final 类中的所有方法：final 类不能被继承，其方法自然无法被重写。


什么是函数式接口？
函数式接口是仅包含一个抽象方法的接口（可包含默认方法、静态方法、私有方法），核心用于支持 Lambda 表达式和方法引用。
核心特征：
接口中有且仅有一个抽象方法（@FunctionalInterface注解可校验，非必须但推荐）；
可继承其他函数式接口（只要不新增抽象方法）；
支持 Lambda 表达式直接实现抽象方法。




接口名	抽象方法	功能描述	示例场景
Consumer<T>	accept(T t)	消费型：接收参数，无返回值	遍历集合打印元素
Supplier<T>	get()	供给型：无参数，返回值	生成随机数 / 创建对象
Function<T,R>	apply(T t)	函数型：接收 T，返回 R	字符串转整数、数据转换
Predicate<T>	test(T t)	断言型：接收 T，返回 boolean	集合过滤、条件判断
BiFunction<T,U,R>	apply(T t,U u)	双参数函数型：接收 T/U，返回 R	两个数运算（加法 / 乘法）
Runnable	run()	无参无返回值（线程执行逻辑）	线程任务定义
Callable<V>	call()	无参，返回 V（可抛异常）	异步任务带返回值




JDK8 之后接口的定义变动
JDK8 为接口新增 3 类方法，打破 “接口只有抽象方法” 的限制，核心变动如下：
默认方法（default 方法）
定义：用default修饰，有方法体，实现类可直接继承或重写；
作用：接口新增方法时，不强制所有实现类修改，兼容老代码；
示例：List.sort(Comparator c)（JDK8 新增的默认方法）。
静态方法（static 方法）
定义：用static修饰，有方法体，只能通过接口名调用；
作用：提供接口级别的工具方法，替代工具类（如Collections）；
示例：Comparator.comparing(Function f)（静态方法）。
私有方法（JDK9+）
定义：用private/private static修饰，有方法体，仅接口内部调用；
作用：抽取默认方法 / 静态方法的公共逻辑，避免代码重复。
注意事项：
默认方法冲突：实现类同时实现两个接口，若有同名默认方法，必须重写；
类优先原则：子类继承父类 + 实现接口，若父类和接口有同名方法，优先用父类的。

10. Java 中实现异步线程的方式
基础方式
继承Thread类：重写run()方法，new Thread().start()；
实现Runnable接口：重写run()，传入 Thread 构造器；
实现Callable<V>接口：重写call()（有返回值、可抛异常），结合FutureTask获取结果。
线程池方式（生产首选）
通过Executors工具类：newFixedThreadPool/newCachedThreadPool/newSingleThreadExecutor；
手动创建ThreadPoolExecutor（推荐，可自定义核心参数）；
异步获取结果：ExecutorService.submit(Callable)返回Future<V>，通过get()获取结果。
JDK8 + 异步工具
CompletableFuture：支持链式调用、异步回调、多任务组合（supplyAsync/runAsync），生产环境主流。
框架层面
Spring 的@Async注解：标注方法为异步，结合线程池使用；
Guava 的ListenableFuture：支持回调式异步。




11. 生产环境：主线程与子线程日志异步串联 + 通信
核心需求
子线程执行异步任务时，需将日志（如 traceId/spanId）与主线程串联，同时主线程可获取子线程执行结果 / 状态。
实现方案
（1）日志串联：MDC（Mapped Diagnostic Context）+ ThreadLocal
原理：MDC 是日志框架（Log4j/Logback）的线程本地存储，可存放 traceId 等上下文；子线程需手动拷贝主线程 MDC 数据。
步骤：
主线程生成 traceId，放入 MDC：MDC.put("traceId", UUID.randomUUID().toString())；
子线程执行前，拷贝主线程 MDC 数据（ThreadLocal 传递）；
线程池场景：自定义ThreadFactory，在创建线程时拷贝 MDC；
示例代码：
java
运行
// 主线程
String traceId = UUID.randomUUID().toString();
MDC.put("traceId", traceId);
// 子线程（线程池）
executorService.submit(() -> {
    // 拷贝主线程MDC
    Map<String, String> context = MDC.getCopyOfContextMap();
    MDC.setContextMap(context);
    try {
        // 子线程业务逻辑，日志自动携带traceId
        log.info("子线程执行异步任务");
    } finally {
        MDC.clear(); // 防止内存泄漏
    }
});
（2）主线程与子线程通信
基于 Future/CompletableFuture（获取结果）
Future.get()：阻塞获取子线程结果（可设置超时）；
CompletableFuture.whenComplete()：非阻塞回调，子线程执行完触发回调逻辑；
示例：
java
运行
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    // 子线程逻辑
    return "异步任务结果";
}, executor);
// 主线程非阻塞回调
future.whenComplete((result, ex) -> {
    if (ex != null) {
        log.error("子线程执行失败", ex);
    } else {
        log.info("子线程结果：{}", result);
    }
});
基于 CountDownLatch/CyclicBarrier（等待通知）
CountDownLatch：主线程await()等待，子线程执行完countDown()，主线程继续；
CyclicBarrier：多子线程等待彼此，全部完成后执行屏障任务。
基于回调函数（自定义）
子线程执行完调用主线程提供的回调方法，传递结果 / 异常。



12. ThreadLocal 实现原理
ThreadLocal 是线程本地存储工具，为每个线程提供独立的变量副本，避免多线程共享变量冲突。
核心结构
Thread 类：包含ThreadLocalMap成员变量（ThreadLocal.ThreadLocalMap threadLocals）；
ThreadLocalMap：ThreadLocal 的内部类，类似 HashMap，key 是ThreadLocal（弱引用），value 是变量副本；
弱引用（WeakReference）：key 为弱引用，避免 ThreadLocal 对象被回收后，key 一直占用内存。
核心方法
set(T value)：给当前线程的 ThreadLocalMap 设置 value（无 map 则创建）；
get()：从当前线程的 ThreadLocalMap 获取 value（无则调用initialValue()初始化）；
remove()：移除当前线程的 ThreadLocalMap 中对应的 entry（关键，防止内存泄漏）。
内存泄漏风险
原因：若 ThreadLocal 对象被回收（key 为弱引用），但 Thread 未结束，value 仍被 ThreadLocalMap 引用，导致内存泄漏；
解决：使用完 ThreadLocal 后，调用remove()释放资源（尤其线程池场景，线程复用易泄漏）。
适用场景
日志 traceId 传递、用户登录信息（UserContext）、数据库连接（Connection）隔离等。
13. Java 动态代理（原理 + 应用场景）
动态代理是运行时动态生成代理类，无需手动编写代理类，核心实现 AOP（面向切面编程）。
两种实现方式



特性	JDK 动态代理	CGLIB 动态代理
实现原理	基于接口，反射生成代理类（实现目标接口）	基于继承，ASM 字节码生成代理类（继承目标类）
前提条件	目标类必须实现接口	目标类不能是 final（无法继承）
性能	JDK8 + 优化后性能接近 CGLIB	生成字节码时稍慢，运行时更快
核心类	Proxy、InvocationHandler	Enhancer、MethodInterceptor


核心原理（JDK 动态代理）
定义InvocationHandler：重写invoke()方法，封装增强逻辑（如日志、事务）；
通过Proxy.newProxyInstance()生成代理对象；
调用代理对象方法时，最终执行invoke()方法（目标方法 + 增强逻辑）。
应用场景
Spring AOP：默认 JDK 动态代理（目标类有接口），否则 CGLIB；
MyBatis Mapper 代理：Mapper 接口无实现类，JDK 动态代理生成代理对象，执行 SQL；
RPC 框架（Dubbo）：服务接口的远程调用，动态代理封装网络通信逻辑；
权限控制 / 日志记录 / 事务管理：统一增强方法逻辑，无需修改业务代码。

15. MyBatis 中 @Param 注解
作用
当 Mapper 接口方法有多个参数时，@Param给参数命名，让 XML / 注解 SQL 能精准匹配参数。
使用场景

多参数方法：java运行// 接口
List<Order> selectByUserIdAndStatus(@Param("userId") Long userId, @Param("status") Integer status);
// XML
WHERE user_id = #{userId} AND status = #{status}

参数为集合 / 数组：
结合foreach标签，默认名称为list/array，用@Param可自定义：
java运行List<Order> selectByIds(@Param("ids") List<Long> ids);
// XML
WHERE id IN <foreach collection="ids" item="id" open="(" close=")" separator=",">#{id}</foreach>

参数为 POJO + 单个参数：java运行List<Order> select(@Param("order") Order order, @Param("startTime") String startTime);
// XML
WHERE user_id = #{order.userId} AND create_time > #{startTime}


注意

若方法只有一个参数且是 POJO / 集合，可不用@Param；
若参数是基本类型（int/Long）且多个，必须用@Param。

16. MyBatis 中实现分表查询
分表查询核心是动态拼接表名（用 ${}），结合拦截器 / 插件实现自动分表，常见方案：
方案 1：基础方案（XML / 注解手动拼接表名）java运行// Mapper接口
List<Order> selectByMonth(@Param("month") String month, @Param("userId") Long userId);
// XML
SELECT * FROM t_order_${month} WHERE user_id = #{userId}

方案 3：框架整合（如 Sharding-JDBC）

分布式分库分表框架，配置分表规则（如按 order_id 取模、按时间范围），MyBatis 透明使用，无需修改 SQL。

关键注意

分表字段必须作为查询条件（如 month/user_id），否则需全表扫描；
避免跨表联合查询，尽量单表查询后聚合。






五、JVM 核心
21. 垃圾回收（GC）算法
（1）标记 - 清除算法（Mark-Sweep）
步骤：标记需要回收的对象 → 清除标记的对象；
优点：简单；
缺点：产生内存碎片，大对象无法分配连续内存。
（2）标记 - 复制算法（Mark-Copy）
步骤：标记存活对象 → 复制到新内存区域 → 清空原区域；
优点：无内存碎片，效率高；
缺点：占用双倍内存空间；
适用：新生代（Eden/Survivor 区，存活对象少）。
（3）标记 - 整理算法（Mark-Compact）
步骤：标记存活对象 → 存活对象向一端移动 → 清除边界外的内存；
优点：无内存碎片，无需额外内存；
缺点：移动对象耗时，效率低；
适用：老年代（存活对象多）。
（4）分代收集算法（主流）
核心思想：按对象存活周期分代（新生代 / 老年代 / 永久代 / 元空间），不同代用不同算法：
新生代：标记 - 复制算法（Eden:Survivor=8:1）；
老年代：标记 - 清除 / 标记 - 整理算法；
优势：兼顾效率和内存利用率。
（5）分区收集算法
将内存分成多个小块，逐块回收，减少单次 GC 停顿时间（如 G1 回收器）。
22. 主流的垃圾回收器
表格
回收器	适用区域	核心算法	特点	适用场景
Serial	新生代	标记 - 复制	单线程，停顿时间长	单核心、小内存应用
ParNew	新生代	标记 - 复制	Serial 多线程版本	老年代 CMS 配合使用
Parallel Scavenge	新生代	标记 - 复制	关注吞吐量（CPU 利用率）	后台运算、批量处理

CMS（Concurrent Mark Sweep）	老年代	标记 - 清除	并发回收，低停顿	高并发、低延迟场景（如 Web）
G1（Garbage First）	新生代 + 老年代	标记 - 整理 + 分区	兼顾吞吐量和低停顿，可预测停顿	大内存、高并发场景
ZGC/Shenandoah	全区域	标记 - 整理 + 着色指针	极低停顿（毫秒级）	超大内存（TB 级）、超低延迟
23. CMS 回收器原理（Concurrent Mark Sweep）
CMS 是老年代并发回收器，核心目标是低停顿（低延迟），基于 “标记 - 清除” 算法实现。
核心回收步骤（4 个阶段）
初始标记（Initial Mark）
暂停所有线程（STW，Stop The World）；
标记 GC Roots 直接关联的老年代对象；
特点：速度快，停顿时间短。
并发标记（Concurrent Mark）
恢复所有线程，GC 线程与用户线程并发执行；
从初始标记的对象出发，遍历整个老年代，标记所有存活对象；
特点：无 STW，耗时较长，但不影响业务。
重新标记（Remark）
暂停所有线程（STW）；
修正并发标记期间，用户线程修改的对象标记（如对象新增 / 删除）；
特点：停顿时间比初始标记长，但远短于 Full GC。
并发清除（Concurrent Sweep）
恢复所有线程，GC 线程与用户线程并发执行；
清除标记的垃圾对象，释放内存；
特点：无 STW，耗时较长。
核心优缺点
优点：并发回收，低停顿，适合高并发低延迟场景；
缺点：
产生内存碎片（标记 - 清除算法）；
并发阶段占用 CPU 资源，影响业务吞吐量；
无法处理浮动垃圾（并发标记期间产生的新垃圾，需下次 GC 回收）；
老年代内存不足时，触发 Full GC，停顿时间长。
适用场景
Web 应用、电商系统等对响应时间敏感的场景（JDK8 前主流，JDK9 已标记为废弃，推荐 G1）。

@Component
@Slf4j
publicclass OrderEventListener implements StreamListener<String, MapRecord<String, String, String>> {
    
    privatefinal OrderService orderService;
    
    @Override
    public void onMessage(MapRecord<String, String, String> message) {
        try {
            String stream = message.getStream();
            String messageId = message.getId().getValue();
            Map<String, String> messageBody = message.getValue();
            
            log.info("收到订单事件: stream={}, messageId={}, body={}", 
                    stream, messageId, messageBody);
            
            // 解析消息内容
            String eventType = messageBody.get("eventType");
            String orderId = messageBody.get("orderId");
            
            // 根据事件类型处理
            switch (eventType) {
                case"ORDER_CREATED":
                    orderService.processOrderCreated(orderId, messageBody);
                    break;
                case"ORDER_PAID":
                    orderService.processOrderPaid(orderId, messageBody);
                    break;
                case"ORDER_CANCELLED":
                    orderService.processOrderCancelled(orderId, messageBody);
                    break;
                default:
                    log.warn("未知的订单事件类型: {}", eventType);
            }
            
            // 确认消息处理完成
            acknowledgeMessage(stream, "order_processor_group", messageId);
            
        } catch (Exception e) {
            log.error("处理订单事件失败: messageId={}", message.getId(), e);
            // 可以选择重新入队或者发送到死信队列
        }
    }
    
    private void acknowledgeMessage(String stream, String group, String messageId) {
        redisTemplate.opsForStream().acknowledge(stream, group, messageId);
        log.debug("消息确认完成: stream={}, group={}, messageId={}", stream, group, messageId);
    }
}

@Component
@Slf4j
publicclass StreamErrorHandler {
    
    privatefinal RedisTemplate<String, Object> redisTemplate;
    
    public void handleProcessingError(String stream, String group, String messageId, Exception error) {
        try {
            // 记录错误日志
            log.error("消息处理失败: stream={}, messageId={}", stream, messageId, error);
            
            // 将消息发送到死信队列
            moveToDeadLetterQueue(stream, messageId, error.getMessage());
            
            // 确认原消息（避免重复消费）
            redisTemplate.opsForStream().acknowledge(stream, group, messageId);
            
        } catch (Exception e) {
            log.error("处理消息错误时发生异常", e);
        }
    }
    
    private void moveToDeadLetterQueue(String stream, String messageId, String errorMessage) {
        Map<String, Object> deadLetterMessage = new HashMap<>();
        deadLetterMessage.put("originalStream", stream);
        deadLetterMessage.put("originalMessageId", messageId);
        deadLetterMessage.put("errorMessage", errorMessage);
        deadLetterMessage.put("timestamp", System.currentTimeMillis());
        
        redisTemplate.opsForStream().add("dead_letter_queue", deadLetterMessage);
    }
}






SpringBoot + 任务执行超时控制 + 强制中断：长时间运行任务自动熔断，防资源耗尽


长时间运行的任务会有如下问题

资源耗尽问题，线程池阻塞：长时间运行的任务占用线程池资源，导致其他任务无法执行

// 没有超时控制的任务执行
@Async
public void processData() {
    // 任务可能运行数小时
    heavyTask();
}


内存泄漏：任务执行过程中创建的对象无法及时释放，导致内存占用持续增长

数据库连接耗尽：长时间运行的任务占用数据库连接，导致连接池耗尽

文件句柄泄漏：打开的文件句柄没有及时关闭，导致系统资源耗尽


雪崩效应：一个长时间运行的任务失败，导致大量任务堆积，最终系统崩溃

性能下降：系统资源被长时间运行的任务占用，导致整体性能下降

响应超时：用户请求长时间得不到响应，体验极差

任务卡死：用户提交的任务卡死，无法知道任务状态（可以用状态机管理任务状态，到时候前端发请求查看进度就可以了，这波我的轻贴已经完美拿下了）



解决办法


首先
1. 任务执行超时控制
定义：为任务设置最大执行时间，超过时间自动终止任务
作用：
防止任务无限期运行
保护系统资源不被耗尽
提高系统可用性

实现方式：
Future.get(timeout)
CompletableFuture.orTimeout()
ExecutorService.submit() + Future
Spring @Async + Future


这一点我强推redis延迟队列

Redis 双 ZSet + List 延迟队列原理（标准实现）
你说的 “双 ZSet + List” 就是经典的 有赞延迟队列模型：
1. 结构
ZSet1：delay_zset（待执行 / 待超时队列）
score = 任务超时时间戳（毫秒）
value = 任务唯一 ID
ZSet2：run_zset（正在执行中的任务）
score = 当前时间戳
value = 任务 ID
作用：标记任务正在执行，防止重复消费 & 超时监控
List：task_queue（真正消费队列）
正常执行的任务从这里消费

@Service
publicclass Resilience4jTimeoutService {

    privatefinal CircuitBreaker circuitBreaker;
    privatefinal TimeLimiter timeLimiter;

    public Resilience4jTimeoutService() {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
                .failureRateThreshold(50)
                .waitDurationInOpenState(Duration.ofMillis(1000))
                .permittedNumberOfCallsInHalfOpenState(2)
                .slidingWindowType(SlidingWindowType.COUNT_BASED)
                .slidingWindowSize(10)
                .build();

        this.circuitBreaker = CircuitBreaker.of("taskBreaker", config);

        TimeLimiterConfig timeLimiterConfig = TimeLimiterConfig.custom()
                .timeoutDuration(Duration.ofSeconds(10))
                .build();

        this.timeLimiter = TimeLimiter.of(timeLimiterConfig);
    }

    public <T> T executeWithTimeout(Supplier<T> supplier) {
        Supplier<CompletableFuture<T>> futureSupplier = () -> 
                CompletableFuture.supplyAsync(supplier);

        CompletableFuture<T> future = timeLimiter
                .executeFutureSupplier(futureSupplier);

        T result = circuitBreaker.executeSupplier(() -> {
            try {
                return future.get();
            } catch (Exception e) {
                thrownew TaskExecutionException("Task execution failed", e);
            }
        });

        return result;
    }

}

一、Java 语言与平台：JVM/JDK/JRE/跨平台

1）Java 的特点（常见开场题）
- 跨平台：Java 源码编译成字节码；不同 OS 上由对应 JVM 执行字节码
- 面向对象：以类/对象组织代码，支持封装/继承/多态
- 自动内存管理：GC 管内存；开发者不手动 free
- 生态成熟：标准库、工具链、框架丰富（企业应用广）

2）Java 为什么跨平台？“跨平台的是谁？”
- 跨平台的是字节码/Java 程序，不是 JVM
- JVM 是平台相关的软件（不同 OS/CPU 有不同实现）
- 思路：统一中间表示（字节码） + 不同平台的执行引擎（JVM）

也就是说字节码文件肯定是一样的，不管平台怎么变，但是JVM在不同平台的实现是不一样的，不同平台要使用对应的JVM，才能把字节码文件翻译成操作系统能看懂的机器码文件，也才能正常的运行程序


3）JVM / JRE / JDK 关系怎么回答（必须顺口）
- JVM：执行字节码的虚拟机（解释器 + JIT），提供内存管理/GC/类加载/安全等
- JRE：JVM + 核心类库（运行环境）
- JDK：JRE + 开发工具（javac/jdb/javap 等）+ 更多类库（开发环境）
关系：JDK ⊃ JRE ⊃ JVM

4）Java 为什么既像编译型又像解释型？
- javac 把源码编译成字节码（不是直接机器码）
- JVM 解释执行字节码以保证通用性/启动
- 热点方法会被 JIT 编译成机器码缓存，提高长期运行性能
一句话：字节码 + 解释器 + JIT 的混合执行

5）编译型 vs 解释型：差异点
- 编译型：先整体编译成可执行目标（或接近目标），运行快但平台相关
- 解释型：运行时逐句解释执行，跨平台好但运行开销大
Java：先编译成字节码，再由 JVM 解释/编译执行

一、BigDecimal 解决了什么问题？
首先要明确：float 和 double 这类基本浮点类型，在计算机中是基于 二进制（Binary） 存储的，而很多十进制小数（比如 0.1）无法被二进制精确表示，会产生无限循环的二进制小数，导致计算时出现精度丢失。
问题示例（浮点数精度丢失）：

public class BigDecimalDemo {
    public static void main(String[] args) {
        // 预期结果是 0.2，但实际不是
        double d1 = 0.1;
        double d2 = 0.1;
        System.out.println("double 相加：" + (d1 + d2)); // 输出：0.20000000000000004
        
        // 用 BigDecimal 解决
        BigDecimal bd1 = new BigDecimal("0.1");
        BigDecimal bd2 = new BigDecimal("0.1");
        System.out.println("BigDecimal 相加：" + bd1.add(bd2)); // 输出：0.2
    }
}


核心问题总结：
float/double 是二进制浮点型，无法精确表示所有十进制小数，适用于科学计算 / 工程计算（允许微小误差）；
金融、电商等场景要求精确的十进制计算（比如金额、税费），必须用 BigDecimal。


二、BigDecimal 的基本使用
BigDecimal 提供了丰富的方法来实现精确的加减乘除、比较、舍入等操作，核心使用要点如下：
1. 正确创建 BigDecimal 对象
⚠️ 重点：不要用 new BigDecimal(double) 构造器（因为 double 本身有精度问题，会继承误差），优先用：
new BigDecimal(String)：最推荐，直接基于字符串的十进制数字创建，无精度丢失；
BigDecimal.valueOf(double)：内部会把 double 转成字符串，也能避免大部分误差。


方法	作用	示例
add()   	加法	bd1.add(bd2)
subtract()	减法	bd1.subtract(bd2)
multiply()	     乘法	bd1.multiply(bd2)
divide()	     除法	bd1.divide(bd2, 2, RoundingMode.HALF_UP)（指定精度和舍入模式）


import java.math.BigDecimal;
import java.math.RoundingMode;

public class BigDecimalUsage {
    public static void main(String[] args) {
        // 正确创建：用字符串构造
        BigDecimal price = new BigDecimal("99.9"); // 商品单价
        BigDecimal count = new BigDecimal("3");    // 购买数量
        BigDecimal discount = new BigDecimal("0.8"); // 8折优惠
        
        // 1. 计算总价：99.9 * 3 = 299.7
        BigDecimal total = price.multiply(count);
        // 2. 计算折后价：299.7 * 0.8 = 239.76
        BigDecimal finalPrice = total.multiply(discount);
        
        // 3. 除法示例：拆分3人付款，保留2位小数，四舍五入
        BigDecimal perPerson = finalPrice.divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP);
        
        System.out.println("总价：" + total);       // 299.7
        System.out.println("折后价：" + finalPrice); // 239.76
        System.out.println("每人付款：" + perPerson); // 79.92
    }
}


BigDecimal 底层是如何解决精度问题的？
你提到的 “十进制什么玩意”，核心是 BigDecimal 底层没有用二进制浮点存储，而是基于 十进制的整数 + 标度（Scale） 来表示数字，本质是把十进制小数转换成 “整数运算”，从根源上避免二进制转换的精度丢失。



1. 核心底层属性（简化理解）
BigDecimal 内部有两个核心成员变量：
int scale：标度，即小数点后的位数（比如 0.1 的 scale 是 1，123.45 的 scale 是 2，100 的 scale 是 0）；
BigInteger intVal：无符号整数，存储的是 “数字去掉小数点后的整数值”（比如 0.1 的 intVal 是 1，123.45 的 intVal 是 12345）。
2. 底层计算逻辑（以 0.1 + 0.1 为例）
0.1 被存储为：intVal = 1，scale = 1（即 1 / 10¹）；
0.1 + 0.1 的计算过程：
统一标度：两个数的 scale 都是 1，无需调整；
整数相加：1 + 1 = 2；
保留标度：结果的 scale 还是 1，即 2 / 10¹ = 0.2；




再来一个例子


底层计算逻辑拆解（123.45 + 0.1）
核心：BigDecimal 会先统一两个数的标度，再做十进制整数相加，最后还原标度，全程无二进制转换。
步骤 1：拆解两个数的底层存储
123.45：intVal = 12345（去掉小数点的整数），scale = 2（小数点后 2 位），即 12345 / 10²；
0.1：intVal = 1（去掉小数点的整数），scale = 1（小数点后 1 位），即 1 / 10¹。
步骤 2：统一标度（取较大的 scale，这里是 2）
为了让两个数的分母一致（都是 10²），需要把 0.1 的标度调整为 2：
0.1 的 intVal 乘以 10（因为 scale 从 1 变 2，需要补 1 个 0），变成 intVal = 10，scale = 2；
调整后：0.1 被表示为 10 / 10²（即 0.10），和 123.45（12345 / 10²）的分母一致。
步骤 3：十进制整数相加
统一标度后，直接对 intVal 做整数加法：12345（123.45 的 intVal） + 10（0.1 调整后的 intVal） = 12355。
步骤 4：还原标度得到结果
相加后的 intVal = 12355，scale = 2，因此结果是 12355 / 10² = 123.55，完全精准。



整个过程是十进制整数的运算，没有二进制转换，因此完全精准。
3. 除法 / 复杂运算的处理
如果遇到除不尽的情况（比如 1 / 3），BigDecimal 会要求你指定舍入模式（比如四舍五入）和保留的小数位数，本质是对整数运算的结果做十进制的舍入，而非二进制的近似。

六、面向对象：封装/继承/多态、重载/重写



面向对象
怎么理解面向对象？简单说说封装继承多态
面向对象是一种编程范式，它将现实世界中的事物抽象为对象，对象具有属性（称为字段或属性）和行为（称为方法）。面向对象编程的设计思想是以对象为中心，通过对象之间的交互来完成程序的功能，具有灵活性和可扩展性，通过封装和继承可以更好地应对需求变化。


Java 面向对象的三大特性包括：封装、继承、多态：


封装：封装是指将对象的属性（数据）和行为（方法）结合在一起，对外隐藏对象的内部细节，仅通过对象提供的接口与外界交互。封装的目的是增强安全性和简化编程，使得对象更加独立。


继承：继承是一种可以使得子类自动共享父类数据结构和方法的机制。它是代码复用的重要手段，通过继承可以建立类与类之间的层次关系，使得结构更加清晰。


多态：多态是指允许不同类的对象对同一消息作出响应。即同一个接口，使用不同的实例而执行不同操作。多态性可以分为编译时多态（重载）和运行时多态（重写）。它使得程序具有良好的灵活性和扩展性。



多态体现在哪几个方面？
多态在面向对象编程中可以体现在以下几个方面：
方法重载：
方法重载是指同一类中可以有多个同名方法，它们具有不同的参数列表（参数类型、数量或顺序不同）。虽然方法名相同，但根据传入的参数不同，编译器会在编译时确定调用哪个方法。
示例：对于一个 add 方法，可以定义为 add(int a, int b) 和 add(double a, double b)。


方法重写：
方法重写是指子类能够提供对父类中同名方法的具体实现。在运行时，JVM 会根据对象的实际类型确定调用哪个版本的方法。这是实现多态的主要方式。
示例：在一个动物类中，定义一个 sound 方法，子类 Dog 可以重写该方法以实现 bark，而 Cat 可以实现 meow。


接口与实现：
多态也体现在接口的使用上，多个类可以实现同一个接口，并且用接口类型的引用来调用这些类的方法。这使得程序在面对不同具体实现时保持一贯的调用方式。
示例：多个类（如 Dog、Cat）都实现了一个 Animal 接口，当用 Animal 类型的引用来调用 makeSound 方法时，会触发对应的实现。


向上转型和向下转型：
在 Java 中，可以使用父类类型的引用指向子类对象，这是向上转型。通过这种方式，可以在运行时期采用不同的子类实现。
向下转型是将父类引用转回其子类类型，但在执行前需要确认引用实际指向的对象类型以避免 ClassCastException。




重载与重写有什么区别

重载指的是在同一个类中，可以有多个同名的方法，它们具有不同的参数列表（参数类型，数量和顺序都可以不一样），编译器根据调用的时候参数类型来决定调用哪个方法

重写指的是子类可以重新定义父类中的方法，但是方法名，参数和返回值必须与父类中的方法一致，通过@Override注解来明确表示这是对父类方法的重写








23）封装怎么答不空？
- 把状态与行为封装在类中，通过方法对外提供能力
- 目的：隐藏实现细节、保护对象不变量、降低耦合
- 实战：字段私有；构造器/Setter 校验；只暴露必要能力

- 过度继承会强耦合，优先组合（has-a）+ 接口抽象

- 重写发生在运行期动态分派，体现多态

26）重载 vs 重写（追问版）
- 重载：同名不同参；编译期决定调用哪个（静态绑定）
- 重写：子类改父类实现；运行期决定调用哪个（动态绑定）

- 静态方法不参与重写：子类同名是隐藏

27）哪些方法不能被重写（你前面有，这里补“为什么”）

- static：属于类，编译期绑定，不能运行期动态分派
- private：对子类不可见，不存在“覆盖”的入口
- 构造方法：用于初始化对象，不是普通可覆盖的方法

28）抽象类 vs 接口（追问链）
- 抽象类：共享代码/状态/骨架；可有构造器；单继承
- 接口：能力契约；可多实现；JDK8+ 可 default/static，JDK9+ 可 private
- 选型口径：优先接口 + 组合；需要共享通用实现再引入抽象类





抽象类和接口的区别

接口没有构造方法，抽象类有，一般给子类使用

接口是行为的抽象，是一种行为的规范。而这个抽象类是对类的抽象，是一种模板设计，可以描述一个完整的事物和特有行为


接口只有定义，不能有方法的实现，但是1.8之后可以定义默认方法，而抽象类可以有定义也可以有具体的实现

接口成员变量默认为public static final修饰，必须初赋值，不能修改，所有成员方法都是public abstract的。抽象类中成员变量默认default，可在子类中被重新定义，也可被重新赋值；抽象方法被abstract修饰














































抽象类不能加final修饰，Java的抽象类是用来被继承的，而final修饰之后会被禁止继承或方法被重写，因此，这两个东西是互斥的，不能同时使用

接口中可以定义哪些方法

抽象方法，像void makeSound();

默认方法，default void sleep(){
		sout("sleep");
}


静态方法，static void staticMethod(){sout("hahahah")},可以通过接口名字直接调用

私有方法，私有方法是在Java9引入的，为接口中默认方法或者其他方法提供辅助的，只能在接口内部使用






抽象类可以被实例化吗


在 Java 中，抽象类本身不能被实例化。
这意味着不能使用 new 关键字直接创建一个抽象类的对象。抽象类的存在主要是为了被继承，它通常包含一个或多个抽象方法（由 abstract 关键字修饰且无方法体的方法），这些方法需要在子类中被实现。


抽象类可以有构造器，这些构造器在子类实例化时会被调用，以便进行必要的初始化工作。然而，这个过程并不是直接实例化抽象类，而是创建了子类的实例，间接地使用了抽象类的构造器。
例如：
java
运行
public abstract class AbstractClass {
    public AbstractClass() {
        // 构造器代码
    }

    public abstract void abstractMethod();
}

public class ConcreteClass extends AbstractClass {
    public ConcreteClass() {
        super(); // 调用抽象类的构造器
    }

    @Override
    public void abstractMethod() {
        // 实现抽象方法
    }
}

// 下面的代码可以运行
ConcreteClass obj = new ConcreteClass();
在这个例子中，ConcreteClass 继承了 AbstractClass 并实现了抽象方法 abstractMethod()。当我们创建 ConcreteClass 的实例时，AbstractClass 的构造器被调用，但这并不意味着 AbstractClass 被实例化；实际上，我们创建的是 ConcreteClass 的一个对象。







接口可以包含构造函数吗，不可以，构造函数就是初始化class的属性或者方法的，在new的一瞬间自动调用，但是接口本来就不能new，所以说构造函数没有办法被调用，作用为零







解释 Java 中的静态变量和静态方法
在 Java 中，静态变量和静态方法是与类本身关联的，而不是与类的实例（对象）关联。它们在内存中只存在一份，可以被类的所有实例共享。
静态变量
静态变量（也称为类变量）是在类中使用 static 关键字声明的变量。它们属于类而不是任何具体的对象。主要的特点：
共享性：所有该类的实例共享同一个静态变量。如果一个实例修改了静态变量的值，其他实例也会看到这个更改。
初始化：静态变量在类被加载时初始化，只会对其进行一次分配内存。
访问方式：静态变量可以直接通过类名访问，也可以通过实例访问，但推荐使用类名。
示例：
java
运行
public class MyClass {
    static int staticVar = 0; // 静态变量

    public MyClass() {
        staticVar++; // 每创建一个对象，静态变量自增
    }

    public static void printStaticVar() {
        System.out.println("Static Var: " + staticVar);
    }
}

// 使用示例
MyClass obj1 = new MyClass();
MyClass obj2 = new MyClass();
MyClass.printStaticVar(); // 输出 Static Var: 2





静态方法
静态方法是在类中使用 static 关键字声明的方法。类似于静态变量，静态方法也属于类，而不是任何具体的对象。主要的特点：
无实例依赖：静态方法可以在没有创建类实例的情况下调用。对于静态方法来说，不能直接访问非静态的成员变量或方法，因为静态方法没有上下文的实例。
访问静态成员：静态方法可以直接调用其他静态变量和静态方法，但不能直接访问非静态成员。
多态性：静态方法不支持重写（Override），但可以被隐藏（Hide）。
java
运行
public class MyClass {
    static int count = 0;

    // 静态方法
    public static void incrementCount() {
        count++;
    }

    public static void displayCount() {
        System.out.println("Count: " + count);
    }
}

// 使用示例
MyClass.incrementCount(); // 调用静态方法
MyClass.displayCount();   // 输出 Count: 1
使用场景
静态变量：常用于需要在所有对象间共享的数据，如计数器、常量等。
静态方法：常用于助手方法（utility methods）、获取类级别的信息或者是没有依赖于实例的数据处




非静态内部类和静态内部类的区别？
区别包括：
非静态内部类依赖于外部类的实例，而静态内部类不依赖于外部类的实例。
非静态内部类可以访问外部类的实例变量和方法，而静态内部类只能访问外部类的静态成员。
非静态内部类不能定义静态成员，而静态内部类可以定义静态成员。
非静态内部类在外部类实例化后才能实例化，而静态内部类可以独立实例化。
非静态内部类可以访问外部类的私有成员，而静态内部类不能直接访问外部类的私有成员，需要通过实例化外部类来访问。





非静态内部类可以直接访问外部方法，编译器是怎么做到的？
非静态内部类可以直接访问外部方法是因为编译器在生成字节码时会为非静态内部类维护一个指向外部类实例的引用。
这个引用使得非静态内部类能够访问外部类的实例变量和方法。编译器会在生成非静态内部类的构造方法时，将外部类实例作为参数传入，并在内部类的实例化过程中建立外部类实例与内部类实例之间的联系，从而实现直接访问外部方法的功能。

40）final 的三种修饰对象
- final 类：不能继承
- final 方法：不能重写
- final 变量：引用不可变，但对象内部可能可变


关键字
Java 中 final 作用是什么？
final 关键字主要有以下三个方面的作用：用于修饰类、方法和变量。
修饰类：当 final 修饰一个类时，表示这个类不能被继承，是类继承体系中的最终形态。例如，Java 中的 String 类就是用 final 修饰的，这保证了 String 类的不可变性和安全性，防止其他通过继承来改变 String 类的行为和特性。
修饰方法：用 final 修饰的方法不能在子类中被重写。比如，java.lang.Object 类中的 getClass 方法就是 final 的，因为这个方法的行为是由 Java 虚拟机底层实现来保证的，不应该被子类修改。
修饰变量：当 final 修饰基本数据类型的变量时，该变量一旦被赋值就不能再改变。例如，final int num = 10;，这里的 num 就是一个常量，不能再对其进行重新赋值操作，否则会导致编译错误。对于引用数据类型，final 修饰意味着这个引用变量不能再指向其他对象，但对象本身的内容是可以改变的。例如，final StringBuilder sb = new StringBuilder("Hello");，不能让 sb 再指向其他 StringBuilder 对象，但可以通过 sb.append(" World"); 来修改字符串的内容。
Java 中 static 的作用是什么？
static 关键字主要用于修饰类的成员（变量、方法、代码块）和内部类，其核心作用是将成员与类本身关联，而非与类的实例（对象）关联。具体作用如下：
1、修饰变量
被 static 修饰的变量属于类本身，而非类的某个实例。所有对象共享同一份静态变量，内存中只存在一份副本。可以通过 类名.变量名 直接访问，无需创建对象（也可通过对象访问，但不推荐）。
通常用于存储所有对象共享的数据，如常量、计数器等。


1、修饰变量

public class Student {
    // 静态变量（所有学生共享同一个学校名称）
    public static String schoolName = "阳光中学";
    // 实例变量（每个学生有自己的姓名）
    private String name;
}

// 访问静态变量
public class Test {
    public static void main(String[] args) {
        System.out.println(Student.schoolName); // 直接通过类名访问
    }
}


2、修饰方法
静态方法属于类，不属于任何实例，因此不能直接访问类中的非静态成员（变量 / 方法）（因为非静态成员依赖于对象存在），但可以访问静态成员。通过 类名。方法名 直接调用，无需创建对象。
通常用于工具类方法（如 Math.random()）、工厂方法等，不需要依赖对象状态即可完成操作。

public class MathUtils {
    // 静态方法（无需创建对象即可调用）
    public static int add(int a, int b) {
        return a + b;
    }
}

// 调用静态方法
public class Test {
    public static void main(String[] args) {
        int result = MathUtils.add(2, 3); // 直接通过类名调用
    }
}



3、修饰代码块
静态代码块在类加载时执行，且只执行一次（优于对象构造方法），用于初始化静态变量或执行类级别的预处理操作。
多个静态代码块按定义顺序执行，且先于非静态代码块和构造方法。

public class Database {
    private static String url;

    // 静态代码块：初始化静态变量
    static {
        url = "jdbc:mysql://localhost:3306/test";
        System.out.println("数据库连接地址初始化完成");
    }
}



4、修饰内部类
静态内部类不依赖于外部类的实例，可以独立存在，不能直接访问外部类的非静态成员（需通过外部类实例访问）。
当内部类与外部类的实例无关时使用，避免内部类持有外部类的引用导致的内存泄漏。

public class OuterClass {
    private static int staticVar = 10;
    private int instanceVar = 20;

    // 静态内部类
    public static class StaticInnerClass {
        public void print() {
            System.out.println(staticVar); // 可访问外部类静态变量
            // System.out.println(instanceVar); // 错误：不能直接访问非静态变量
        }
    }
}

// 使用静态内部类
public class Test {
    public static void main(String[] args) {
        OuterClass.StaticInnerClass inner = new OuterClass.StaticInnerClass();
        inner.print();
    }
}






浅拷贝是指只复制对象本身和其内部的值类型字段，但不会复制对象内部的引用类型字段。换句话说，浅拷贝只是创建一个新的对象，然后将原对象的字段值复制到新对象中，但如果原对象内部有引用类型的字段，只是将引用复制到新对象中，两个对象指向的是同一个引用对象。
深拷贝是指在复制对象的同时，将对象内部的所有引用类型字段的内容也复制一份，而不是共享引用。换句话说，深拷贝会递归复制对象内部所有引用类型的字段，生成一个全新的对象以及其内部的所有对象。





1. 实现 Cloneable 接口并重写 clone () 方法
这种方法要求对象及其所有引用类型字段都实现 Cloneable 接口，并且重写 clone() 方法。在 clone() 方法中，通过递归克隆引用类型字段来实现深拷贝。
java
运行
class MyClass implements Cloneable {
    private String field1;
    private NestedClass nestedObject;

    @Override
    protected Object clone() throws CloneNotSupportedException {
        MyClass cloned = (MyClass) super.clone();
        cloned.nestedObject = (NestedClass) nestedObject.clone(); // 深拷贝内部的引用对象
        return cloned;
    }
}

class NestedClass implements Cloneable {
    private int nestedField;

    @Override
    protected Object clone() throws CloneNotSupportedException {
        return super.clone();
    }
}
2. 使用序列化和反序列化
java
运行
import java.io.*;

class MyClass implements Serializable {
    private String field1;
    private NestedClass nestedObject;

    public MyClass deepCopy() {
        try {
            ByteArrayOutputStream bos = new ByteArrayOutputStream();
            ObjectOutputStream oos = new ObjectOutputStream(bos);
            oos.writeObject(this);
            oos.flush();
            oos.close();

            ByteArrayInputStream bis = new ByteArrayInputStream(bos.toByteArray());
            ObjectInputStream ois = new ObjectInputStream(bis);
            return (MyClass) ois.readObject();
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
            return null;
        }
    }
}

class NestedClass implements Serializable {
    private int nestedField;
}
3. 手动递归复制
针对特定对象结构，手动递归复制对象及其引用类型字段。适用于对象结构复杂度不高的情况。
java
运行
class MyClass {
    private String field1;
    private NestedClass nestedObject;

    public MyClass deepCopy() {
        MyClass copy = new MyClass();
        copy.setField1(this.field1);
        copy.setNestedObject(this.nestedObject.deepCopy());
        return copy;
    }
}

class NestedClass {
    private int nestedField;

    public NestedClass deepCopy() {
        NestedClass copy = new NestedClass();
        copy.setNestedField(this.nestedField);
        return copy;
    }
}

4、使用反序列化：通过 ObjectInputStream 从一个字节流（通常是文件或网络）中重建一个对
java

import java.io.*;

// 必须实现 Serializable 接口
public class Person implements Serializable {
    private String name;
    // ... 构造器和其他方法 ...
}

public class Main {
    public static void main(String[] args) {
        Person personToSave = new Person("David");

        // 序列化对象到文件
        try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("person.data"))) {
            oos.writeObject(personToSave);
        } catch (IOException e) {
            e.printStackTrace();
        }

        // 从文件反序列化对象
        try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("person.data"))) {
            Person restoredPerson = (Person) ois.readObject(); // 创建新对象
            restoredPerson.sayHello(); // 输出: Hello, David
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}

New 出的对象什么时候回收？
通过关键字 new 创建的对象，由 Java 的垃圾回收器（Garbage Collector）负责回收。垃圾回收器的工作是在程序运行过程中自动进行的，它会周期性地检测不再被引用的对象，并将其回收释放内存。
具体来说，Java 对象的回收时机是由垃圾回收器根据一些算法来决定的，主要有以下几种情况：
引用计数法：某个对象的引用计数为 0 时，表示该对象不再被引用，可以被回收。
可达性分析算法：从根对象（如方法区中的静态属性、方法中的局部变量等）出发，通过对象之间的引用链进行遍历，如果存在一条引用链到达某个对象，则说明该对象是可达的，反之不可达，不可达的对象将被回收。
终结器（Finalizer）：如果对象重写了 finalize() 方法，垃圾回收器会在回收该对象之前调用 finalize() 方法，对象可以在 finalize() 方法中进行一些清理操作。然而，终结器机制的使用不被推荐，因为它的执行时间是不确定的，可能会导致不可预测的性能问题。




如何获取私有对象

可以通过getter方法

或者反射，反射机制允许在运行时检查和修改类，方法，字段等信息，通过反射可以绕过private访问修饰符的限制来获取私有对象



什么是反射？
Java 反射机制是在运行状态中，对于任意一个类，都能够知道这个类的所有属性和方法，对于任意一个对象，都能够调用它的任意一个方法和属性；这种动态获取的信息以及动态调用对象的方法的功能称为 Java 语言的反射机制。


反射具有以下特性：
运行时类信息访问：反射机制允许程序在运行时获取类的完整结构信息，包括类名、包名、父类、实现的接口、构造函数、方法和字段等。
动态对象创建：可以使用反射 API 动态地创建对象实例，即使在编译时不知道具体的类名。这是通过 Class 类的 newInstance() 方法或 Constructor 对象的 newInstance() 方法实现的。
动态方法调用：可以在运行时动态地调用对象的方法，包括私有方法。这通过 Method 类的 invoke() 方法实现，允许你传入对象实例和参数值来执行方法。
访问和修改字段值：反射还允许程序在运行时访问和修改对象的字段值，即使是私有的。这是通过 Field 类的 get() 和 set() 方法完成的。

Java注解本质上是一个继承了Annotation的特殊接口，具体实现类是java运行时生成的动态代理类

编译后Java编译器会将其转换成一个继承自Annotation的接口，并生成相应的字节码文件

根据注解范围，Java注解可以分为以下几种

源码级别注解：仅存在于源码中，编译后不会保留（@Retention(RetentionPolicy.SOURCE)）。
类文件级别注解：保留在 .class 文件中，但运行时不可见（@Retention(RetentionPolicy.CLASS)）。
运行时注解：保留在 .class 文件中，并且可以通过反射在运行时访问（@Retention(RetentionPolicy.RUNTIME)）。


当注解被标记为RUNTIME的时候，Java编译器会在生成的.class文件中保存注解信息。


注解的解析方法（依赖java反射机制）

1、获取注册信息：通过反射 API 可以获取类、方法、字段等元素上的注解。例如：
Class<?> clazz = MyClass.class;
MyAnnotation annotation = clazz.getAnnotation(MyAnnotation.class);
if (annotation != null) {
    System.out.println(annotation.value());
}
2、底层原理：反射机制的核心类是 java.lang.reflect.AnnotatedElement，它是所有可以被注解修饰的元素（如 Class、Method、Field 等）的父接口。该接口提供了以下方法：
getAnnotation(Class<T> annotationClass)：获取指定类型的注解。
getAnnotations()：获取所有注解。
isAnnotationPresent(Class<? extends Annotation> annotationClass)：判断是否包含指定注解。
这些方法的底层实现依赖于 JVM 提供的本地方法（Native Method），例如：
native Annotation[] getDeclaredAnnotations0(boolean publicOnly);
native <A extends Annotation> A getAnnotation(Class<A> annotationClass);



Java 注解的作用域呢？
注解的作用域（Scope）指的是注解可以应用在哪些程序元素上，例如类、方法、字段等。Java 注解的作用域可以分为三种：
类级别作用域：用于描述类的注解，通常放置在类定义的上面，可以用来指定类的一些属性，如类的访问级别、继承关系、注释等。
方法级别作用域：用于描述方法的注解，通常放置在方法定义的上面，可以用来指定方法的一些属性，如方法的访问级别、返回值类型、异常类型、注释等。
字段级别作用域：用于描述字段的注解，通常放置在字段定义的上面，可以用来指定字段的一些属性，如字段的访问级别、默认值、注释等。












Java 的异常体系主要基于 Throwable 及其子类。Throwable 有两个重要的子类：Error 和 Exception，它们分别代表了不同类型的异常情况。


Error（错误）：表示运行环境的错误，错误是程序无法处理的严重问题，如虚拟机错误、动态链接库失效等。程序不应该尝试捕获这类错误。例如，OutOfMemoryError、StackOverflowError 等。需要程序员检查运行环境，是否缺少依赖等等


Exception（异常）：表示程序本身可以处理的异常情况。异常分为两大类：
非运行时异常（受检异常，Checked Exception）：这类异常在编译时就必须被捕获或者声明抛出。它们通常是外部错误，如文件不存在（FileNotFoundException）、类未找到（ClassNotFoundException）等。非运行时异常强制程序员处理这些可能出现的问题，增强了程序的健壮性。
如果不进行处理的话是不会让你运行的


运行时异常（非受检异常，Unchecked Exception 或 RuntimeException）：这类异常特指 RuntimeException 及其子类。运行时异常由程序逻辑错误导致，如空指针访问（NullPointerException）、数组越界（ArrayIndexOutOfBoundsException）等。运行时异常是不需要在编译时强制捕获或声明的，需要程序员自己在可能出现问题的地方写try catch进行捕获和处理






异常处理方式

try-catch块，可以使用多个catch来处理不同类型的异常

throw语句，可以手动抛出异常

finally块，无论是否发生异常，都会执行代码




try{return "a"} finally{return "b"} 这条语句返回啥？
finally 块中的 return 语句会覆盖 try 块中的 return 返回，因此，该语句将返回 "b"。




步骤 1：执行 try 块的 return 语句（但不返回）
当 JVM 执行到 return "a" 时，会做两件事：
计算返回值 "a"，并把这个值暂存到「方法栈帧的返回值临时变量」中；
标记 “准备执行 return”，但不会立刻退出方法 —— 因为 JVM 规定：try/catch 块的 return 执行前，必须先执行 finally 块。
步骤 2：执行 finally 块的 return 语句（覆盖并返回）
JVM 进入 finally 块后，执行 return "b"：
计算返回值 "b"，覆盖掉之前暂存的 "a"；
直接触发方法退出，返回 "b"—— 此时 try 块中 “准备执行的 return” 被彻底覆盖，再也没有机会执行。
关键补充：finally 块的 “强制执行” 特性
JVM 对 finally 块的执行有硬性规则：
除非遇到 System.exit(0)（强制终止 JVM），否则无论 try/catch 块是正常执行、return、抛异常，finally 块必然会执行；
如果 finally 块中有 return 语句，会直接 “抢占” 方法的返回权，覆盖 try/catch 块的所有 return / 异常。
反面例子：更直观理解覆盖逻辑
如果 finally 块没有 return，才会返回 try 块的暂存值：
java
运行
public static String test2() {
    try {
        return "a";  // 暂存 "a"
    } finally {
        System.out.println("finally执行");  // 执行完这个，再返回try的"a"
    }
}
总结
try{return "a"} finally{return "b"} 最终返回 b，核心是 finally 块的 return 会覆盖 try 块的 return；
JVM 执行顺序：try 块计算返回值并暂存 → 强制执行 finally 块 → finally 块的 return 直接退出方法；
开发中禁止在 finally 块中写 return：会覆盖异常（比如 try 抛异常，finally 的 return 会让异常 “消失”），导致问题排查困难。

举个例子吧

实际开发中我们常常需要按对象的内容比较，比如两个用户对象只要 id 相同就认为相等，这时候就需要重写 equals。比如：

class User {
    private int id;
    private String name;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (obj == null || getClass() != obj.getClass()) return false;
        User user = (User) obj;
        return id == user.id;
    }
}



和 equals 配套的必须重写 hashCode 方法，因为 Java 的约定是如果两个对象 equals 返回 true，它们的 hashCode 必须相等；如果 hashCode 不相等，equals 一定返回 false。如果只重写 equals 不重写 hashCode，会导致对象在 HashMap、HashSet 等集合中无法正确存储，比如两个 id 相同的 User 对象，equals 返回 true，但 hashCode 不同，会被当成两个不同元素存入集合。重写示例：

@Override
public int hashCode() {
    return Integer.hashCode(id);
}

wait 方法有三个重载，作用是让当前持有对象锁的线程释放锁并进入等待状态，直到被 notify/notifyAll 唤醒或者等待时间到期。同样需要在 synchronized 同步块或方法中使用，否则会抛 IllegalMonitorStateException，比如：

== 与 equals 有什么区别？
对于字符串变量来说，使用 == 和 equals 比较字符串时，其比较方法不同。== 比较两个变量本身的值，即两个对象在内存中的首地址，equals 比较字符串包含内容是否相同。
对于非字符串变量来说，如果没有对 equals() 进行重写的话，== 和 equals 方法的作用是相同的，都是用来比较对象在堆内存中的首地址，即用来比较两个引用变量是否指向同一个对象。



hashCode 和 equals 方法有什么关系？
在 Java 中，对于重写equals方法的类，通常也需要重写hashCode方法，并且需要遵循以下规定：
一致性：如果两个对象使用equals方法比较结果为true，那么它们的hashCode值必须相同。也就是说，如果obj1.equals(obj2)返回true，那么obj1.hashCode()必须等于obj2.hashCode()。
非一致性：如果两个对象的hashCode值相同，它们使用equals方法比较的结果不一定为true。即obj1.hashCode() == obj2.hashCode()时，obj1.equals(obj2)可能为false，这种情况称为哈希冲突






String、StringBuffer、StringBuilder 的区别和联系
可变性：String 是不可变的（Immutable），一旦创建，内容无法修改，每次修改都会生成一个新的对象。StringBuilder 和 StringBuffer 是可变的（Mutable），可以直接对字符串内容进行修改而不会创建新对象。
线程安全性：String 因为不可变，天然线程安全。StringBuilder 不是线程安全的，适用于单线程环境。StringBuffer 是线程安全的，其方法通过 synchronized 关键字实现同步，适用于多线程环境。
性能：String 性能最低，尤其是在频繁修改字符串时会生成大量临时对象，增加内存开销和垃圾回收压力。StringBuilder 性能最高，因为它没有线程安全的开销，适合单线程下的字符串操作。StringBuffer 性能略低于 StringBuilder，因为它的线程安全机制引入了同步开销。
使用场景：如果字符串内容固定或不常变化，优先使用 String。如果需要频繁修改字符串且在单线程环境下，使用 StringBuilder。如果需要频繁修改字符串且在多线程环境下，使用 StringBuffer。

Java 的泛型是编译期语法糖（仅在编译阶段生效，运行时会被擦除），且泛型的本质是对「对象」进行类型约束；而基本类型（int、byte、char 等）不是 Object 的子类，无法被泛型容器存储，因此泛型只能写包装类（Integer、Byte、Character）这类对象类型。





1. 第一步：先分清「基本类型 vs 引用类型」
Java 数据类型分两类，核心差异是是否继承 Object：
基本类型：8 种（int/byte/short/long/float/double/char/boolean），直接存储值，不继承 Object，也没有对象的特性（比如方法、属性）；
引用类型：所有类（包括包装类 Integer、String）、数组、接口等，本质是指向对象的指针，继承 Object，能被统一当作 Object 处理。
2. 第二步：泛型的底层实现 —— 类型擦除
Java 泛型在编译后会被「擦除」，最终都会变成「Object 类型」的处理逻辑（除非指定了上限）。举个例子，你写的代码：
java
运行
List<Integer> list = new ArrayList<>();
list.add(1); // 自动装箱：int→Integer
Integer num = list.get(0);
编译后会被擦除成：
java
运行
List list = new ArrayList();
list.add(Integer.valueOf(1)); // 手动装箱
Integer num = (Integer) list.get(0); // 强制类型转换
👉 关键：泛型擦除后，容器内部存储的是「Object 对象」，而基本类型不是 Object，自然无法被存储，只能用对应的包装类（Integer、Double 等）。
3. 第三步：为什么不能直接写基本类型？（反例 + 报错）
如果强行写基本类型，编译阶段就会报错，比如：
java
运行
// 编译报错：Type argument cannot be of primitive type
List<int> list = new ArrayList<int>(); 
原因：编译器会检查泛型参数必须是「引用类型」，基本类型不满足这个要求 —— 因为擦除后要转成 Object，但 int 无法转成 Object（只能先装箱成 Integer）。
4. 补充：自动装箱 / 拆箱的「兜底」作用
你平时写list.add(1)不报错，不是因为泛型支持 int，而是 Java 的自动装箱机制：把基本类型 int 自动转换成包装类 Integer，本质还是存储的对象。同理，int num = list.get(0)是自动拆箱：把 Integer 转成 int。



三、面试精简回答（直接背）
面试官问「为什么集合泛型不能用基本类型？」，可以按这个逻辑答：
核心原因有两点：
Java 泛型是编译期语法糖，运行时会发生「类型擦除」，泛型参数最终会被擦除为 Object 类型，而基本类型（如 int、char）不是 Object 的子类，无法被存储；
Java 数据类型分为基本类型和引用类型，泛型要求参数必须是引用类型（继承 Object），因此只能用包装类（Integer、Character）而非基本类型；
日常写list.add(1)不报错，是因为自动装箱把 int 转成了 Integer，本质还是存储对象，并非泛型支持基本类型。



四、扩展：JDK 1.8 后的优化（加分项）
如果想进一步体现深度，可以补充：
虽然泛型不支持基本类型，但 JDK 提供了专门的「基本类型集合框架」（如 Eclipse Collections、Guava 的 IntArrayList），避免装箱拆箱的性能损耗；
Java 17 的 Valhalla 项目正在尝试支持「值类型」，未来可能让泛型直接支持基本类型，但目前主流版本仍不支持。



总结
泛型擦除后存储的是 Object，基本类型不是 Object 子类，无法直接存储；
泛型参数必须是引用类型，因此只能用包装类（Integer/Double）；
自动装箱 / 拆箱是语法糖，并非泛型支持基本类型的证明。









Native 方法解释一下
在 Java 中，native 方法是一种特殊类型的方法，它允许 Java 代码调用外部的本地代码，即用 C、C++ 或其他语言编写的代码。native关键字是 Java 语言中的一种声明，用于标记一个方法的实现将在外部定义。
在 Java 类中，native 方法看起来与其他方法相似，只是其方法体由native关键字代替，没有实际的实现代码。例如：
java
运行
public class NativeExample {
    public native void nativeMethod();
}
要实现 native 方法，你需要完成以下步骤：
生成 JNI 头文件：使用javah工具从你的 Java 类生成 C/C++ 的头文件，这个头文件包含了所有 native 方法的原型。
编写本地代码：使用 C/C++ 编写本地方法的实现，并确保方法签名与生成的头文件中的原型匹配。
编译本地代码：将 C/C++ 代码编译成动态链接库（DLL，在 Windows 上），共享库（SO，在 Linux 上）。
加载本地库：在 Java 程序中，使用System.loadLibrary()方法来加载你编译好的本地库，这样 JVM 就能找到并调用 native 方法的实现了。

        // 1. 参数校验（金额/数量>0，单位：分，避免浮点精度问题）
        if (dto.getTotalAmount() <= 0 || dto.getPacketCount() <= 0) {
            throw new BusinessException("红包金额/数量必须大于0");
        }

        // 2. 生成全局唯一红包ID（雪花算法）
        Long redPacketId = IdGenerator.generateId();
        // 3. 同步创建红包记录（必须先写库，避免支付时数据不存在）
        RedPacketDO redPacketDO = RedPacketDO.builder()
                .id(redPacketId)
                .userId(userId)
                .totalAmount(dto.getTotalAmount())
                .packetCount(dto.getPacketCount())
                .status(RedPacketStatus.WAIT_PAY.getCode()) // 待支付
                .build();
        redPacketMapper.insert(redPacketDO);

        // 4. 创建支付订单
        Long orderId = IdGenerator.generateId();
        PayOrderDO payOrderDO = PayOrderDO.builder()
                .orderId(orderId)
                .redPacketId(redPacketId)
                .amount(dto.getTotalAmount())
                .userId(userId)
                .status(PayOrderStatus.WAIT_PAY.getCode()) // 待支付
                .build();
        payOrderMapper.insert(payOrderDO);

        try {
            // 5. 响应式调用支付平台，生成支付参数（防IO阻塞）
            Mono<PayParamVO> payParamMono = payPlatformClient.createPayOrder(orderId, dto.getTotalAmount(), userId);
            PayParamVO payParam = payParamMono.block(Duration.ofSeconds(3)); // 超时控制

            // 6. 返回支付参数给前端
            return PayCreateVO.builder()
                    .redPacketId(redPacketId)
                    .orderId(orderId)
                    .payParam(payParam)
                    .build();
        } catch (Exception e) {
            // 异常回滚：删除红包/订单记录
            redPacketMapper.deleteById(redPacketId);
            payOrderMapper.deleteById(orderId);
            log.error("创建支付参数失败", e);
            throw new BusinessException("创建红包失败，请重试");
        }
    }

    /**
     * 支付平台回调接口（核心：验签+二次校验）
     */
    @Transactional(rollbackFor = Exception.class)
    public String handlePayCallback(PayCallbackDTO callbackDTO) {
        // 1. 验签（防止伪造回调）
        if (!payPlatformClient.verifySign(callbackDTO)) {
            return "fail";
        }

        // 2. 查询订单并校验状态
        PayOrderDO payOrder = payOrderMapper.selectByOrderId(callbackDTO.getOrderId());
        if (payOrder == null || payOrder.getStatus() != PayOrderStatus.WAIT_PAY.getCode()) {
            return "success"; // 重复回调直接返回成功
        }

        // 3. 响应式确认支付状态（二次校验）
        Mono<Boolean> paySuccessMono = payPlatformClient.queryPayStatus(callbackDTO.getOrderId());
        Boolean paySuccess = paySuccessMono.block(Duration.ofSeconds(2));
        if (!Boolean.TRUE.equals(paySuccess)) {
            return "fail";
        }

	//下面这个实际上可以先更新redis，然后异步更新数据库，性能有一个提升，而且方便后续抢红包业务的处理，不用担心缓存还没更新，还得去查数据库了。。。。。。。。。。。唉唉唉唉，这块确实实现的不太行。。。。。。。。。。。。。。。。

	
        // 4. 更新订单/红包状态
        payOrderMapper.updateStatus(payOrder.getOrderId(), PayOrderStatus.SUCCESS.getCode());
        redPacketMapper.updateStatus(payOrder.getRedPacketId(), RedPacketStatus.PAY_SUCCESS.getCode());

        // 5. 发送消息到MQ，将红包写入Redis
        rabbitTemplate.convertAndSend("redPacket.pay.success", payOrder.getRedPacketId());

        return "success"; // 必须返回success，否则支付平台会重复回调
    }

    /**
     * MQ消费：将红包写入Redis缓存
     */
    @RabbitListener(queues = "redPacket.pay.success")
    public void syncRedPacketToRedis(Long redPacketId) {
        RedPacketDO redPacket = redPacketMapper.selectById(redPacketId);
        if (redPacket == null) {
            log.warn("红包不存在，ID：{}", redPacketId);
            return;
        }

        // Redis Key设计：red_packet:{id}（Hash类型，存储核心信息）
        String redisKey = String.format("red_packet:%d", redPacketId);
        redisTemplate.opsForHash().putAll(redisKey, Map.of(
                "total_amount", redPacket.getTotalAmount().toString(),
                "packet_count", redPacket.getPacketCount().toString(),
                "remain_count", redPacket.getPacketCount().toString(), // 剩余数量
                "remain_amount", redPacket.getTotalAmount().toString(), // 剩余金额
                "status", redPacket.getStatus().toString()
        ));
        redisTemplate.expire(redisKey, Duration.ofHours(24)); // 设置过期时间，防止缓存堆积
    }
}

    /**
     * 抢红包核心逻辑（原子操作+分布式锁防超抢/重复抢）
     */
    public RedPacketGrabVO grabRedPacket(Long redPacketId, Long userId) {
        String redisKey = String.format("red_packet:%d", redPacketId);
        // 1. 分布式锁：防止同一用户重复抢红包
        String lockKey = String.format("red_packet_grab_lock:%d:%d", redPacketId, userId);
        Boolean lock = redisTemplate.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(5));
        if (Boolean.FALSE.equals(lock)) {
            throw new BusinessException("你已抢过该红包，请勿重复操作");
        }

        try {
            // 2. 检查红包状态（Redis原子操作）
            Map<Object, Object> redPacketMap = redisTemplate.opsForHash().entries(redisKey);
            if (CollectionUtils.isEmpty(redPacketMap)) {
                throw new BusinessException("红包不存在或未生效");
            }

            // 校验红包是否已支付、是否抢完
            String status = (String) redPacketMap.get("status");
            if (!RedPacketStatus.PAY_SUCCESS.getCode().equals(status)) {
                throw new BusinessException("红包未支付，无法抢");
            }
            int remainCount = Integer.parseInt((String) redPacketMap.get("remain_count"));
            if (remainCount <= 0) {
                throw new BusinessException("红包已被抢完");
            }

            // 3. Redis原子操作：剩余数量-1（防超抢）
            Long newRemainCount = redisTemplate.opsForHash().increment(redisKey, "remain_count", -1);
            if (newRemainCount < 0) {
                redisTemplate.opsForHash().increment(redisKey, "remain_count", 1); // 回滚
                throw new BusinessException("红包已被抢完");
            }


//下面这段写在Lua脚本中，否则会出大问题

            // 4. 二倍均值法分配金额（保证随机且不超发）
            long remainAmount = Long.parseLong((String) redPacketMap.get("remain_amount"));
            long grabAmount = calculateGrabAmount(remainAmount, newRemainCount + 1);

            // 5. 更新Redis剩余金额
            redisTemplate.opsForHash().increment(redisKey, "remain_amount", -grabAmount);

            // 6. 同步写入抢红包记录（保证数据不丢失）
            RedPacketGrabDO grabDO = RedPacketGrabDO.builder()
                    .id(IdGenerator.generateId())
                    .redPacketId(redPacketId)
                    .userId(userId)
                    .grabAmount(grabAmount)
                    .status(GrabStatus.WAIT_ENTRY.getCode()) // 待入账
                    .build();
            redPacketGrabMapper.insert(grabDO);

            // 7. 异步更新DB/用户账户
            rabbitTemplate.convertAndSend("redPacket.grab.success", grabDO);

            // 8. 返回抢红包结果
            return RedPacketGrabVO.builder()
                    .redPacketId(redPacketId)
                    .userId(userId)
                    .grabAmount(grabAmount)
                    .build();
        } finally {
            // 释放分布式锁
            redisTemplate.delete(lockKey);
        }
    }

    /**
     * 二倍均值法：保证每个红包金额在(0, 2*剩余金额/剩余数量)之间，总金额不超发
     */
    private long calculateGrabAmount(long remainAmount, long remainCount) {
        // 最后一个红包：剩余金额全给
        if (remainCount == 1) {
            return remainAmount;
        }
        // 随机金额范围：1 ~ 2*remainAmount/remainCount（单位：分）
        long max = 2 * remainAmount / remainCount;
        return ThreadLocalRandom.current().nextLong(1, max + 1);
    }

    /**
     * MQ消费：更新DB+用户账户入账

    @RabbitListener(queues = "redPacket.grab.success")

一、整体架构思路
整个红包系统分为 发红包、抢红包、红包过期、高可用保障 四块，核心原则：
发红包：DB 保证事务，Redis 做缓存
抢红包：全走 Redis，原子化、高并发
落库：异步 MQ，最终一致性
过期：Redis 延迟队列，精准不扫库
高并发：热 Key 处理、限流、熔断、降级



二、发红包流程
用户点击塞红包
前端传入：总金额、红包个数、过期时间、备注等。
后端先在 红包表 插入一条数据，状态为 待支付。
这一步用数据库事务保证红包基础数据可靠。
跳转支付，支付回调
调用支付系统，用户完成付款。
支付成功回调后，更新红包表状态：待支付 → 可领取。
这里使用 状态机 管理红包生命周期：
待支付 → 可领取 → 已领完 → 已过期 → 已退款
严格控制状态流转，防止非法状态变更。
红包信息缓存到 Redis
支付成功后，把红包信息全量放入 Redis：
总金额、总个数、剩余金额、剩余个数
过期时间、红包状态、发红包人 ID
同时缓存 已抢用户集合，用来防重复抢夺。
加入 Redis 延迟队列，用于过期处理
用 Redis ZSet 实现延迟队列：
key：red_packet_delay_queue
value：红包 ID
score：过期时间戳
等到时间自动触发过期逻辑，不用定时任务全表扫描。



三、抢红包流程（高并发核心）
请求进来先做前置校验
用户是否登录、红包是否存在、是否过期、是否已领完。
这些判断全部走 Redis，不查库。
防重复抢
在 Redis 里用 Set 结构保存已抢用户 ID。
判断用户是否已经在集合里，存在直接返回 “已抢过”。
Lua 脚本原子扣减（核心）
用一段 Lua 脚本原子执行：
判断剩余个数、剩余金额是否 > 0
判断用户是否已抢
扣减剩余个数、剩余金额
把用户 ID 加入已抢集合
保证 高并发下不会超发、超抢、重复抢。
二分均值法计算抢到金额
根据剩余金额、剩余人数，用二分均值算法随机生成金额。
保证金额相对均匀，不会出现极端大小额，最后一个兜底。
计算逻辑也可以 放在 Lua 里一起执行，保证原子。
抢成功，不直接写库
抢红包接口只做 Redis 操作，性能极高。
把抢夺记录（红包 ID、用户 ID、金额、时间）发送到 MQ。
MQ 消费异步落库
消费者监听队列，插入 红包领取记录表。
使用 本地事务表 + 消息重试 保证最终一致性。
通过 userId + redPacketId 做 幂等去重，防止重复入库、重复到账。


四、红包过期处理（Redis 延迟队列）
后台任务消费延迟队列
定时拉取 ZSet 中 score（时间戳）≤ 当前时间的红包 ID。
使用 Lua 原子弹出，避免多实例重复处理。
过期处理逻辑
修改 Redis 中红包状态为 已过期。
禁止继续抢夺。
计算剩余金额，发送 MQ 异步退款给发红包用户。
更新 DB 红包状态为已过期，生成退款流水。
兜底保证
加一个低频率定时任务，每天扫一次 DB，做 数据对账。
防止 Redis 异常导致过期消息丢失，双保险。


五、高并发、高可用保障

热 Key 问题
单个红包高并发会产生热 Key。

幂等全程保证
接口防重提交
Redis 判重

抢：Redis 强一致

如果有这个场景，平时线程池只需要调用两个核心线程就能实现所有任务，但是在高并发的时候，显然需要更多的核心线程，比如，我们可以可以不急着把任务放到等待队列，反而是增加核心线程数去执行，再放到任务队列中，你会怎么解决


先把问题说直白：默认线程池策略：核心线程满 → 进队列 → 队列满 → 开最大线程 → 拒绝你想要的是：核心线程满 → 先开新线程（直到最大线程）→ 再进队列
我用最通俗、工程可落地的方式给你讲清楚怎么做。


一、先回忆原生线程池执行顺序（ThreadPoolExecutor）
执行流程：
线程数 < corePoolSize → 新建核心线程执行
线程数 == corePoolSize → 任务入队列
队列满 → 新建线程，直到 maximumPoolSize
达到最大线程 → 拒绝策略
痛点：就算你瞬间高并发，它也先塞满队列，才肯加线程，导致：
队列积压
响应变慢
线程利用率上不去
你要的：先扩线程，再排队。



二、实现思路：先开线程，再入队列
方案：自定义一个队列，队列.offer () 时返回 false，逼线程池创建新线程
原理：
线程池判断：core 满了 → 尝试放进队列
如果队列 offer 返回 false → 线程池认为队列满了
就会 新建非核心线程，直到达到 maximumPoolSize
等线程也满了，我们再真正把任务放进队列



三、代码实现（可直接用）
1. 自定义队列：先拒绝，让线程池扩容
java
运行
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;

public class CustomQueue<E> extends LinkedBlockingQueue<E> {

    private final ThreadPoolExecutor executor;

    public CustomQueue(ThreadPoolExecutor executor, int capacity) {
        super(capacity);
        this.executor = executor;
    }

    @Override
    public boolean offer(E e) {
        // 关键：当前线程数 < 最大线程数时，返回 false
        // 逼线程池新建线程，而不是入队列
        if (executor.getPoolSize() < executor.getMaximumPoolSize()) {
            return false;
        }
        // 线程已经到最大了，才真正入队列
        return super.offer(e);
    }
}
2. 构建线程池
java
运行
int corePoolSize = 2;
int maxPoolSize = 10;
int queueCapacity = 100;

ThreadPoolExecutor executor = new ThreadPoolExecutor(
        corePoolSize,
        maxPoolSize,
        60L,
        TimeUnit.SECONDS,
        // 传入自定义队列
        new CustomQueue<>(executor, queueCapacity)
);


四、现在执行流程变成你想要的
任务进来
线程数 < core（2）→ 新建核心线程
线程数 == core（2）→ 尝试进队列
队列发现：当前线程 < max（10）→ 返回 false
线程池以为队列满 → 新建线程（直到 10）
线程数达到 max（10）→ 任务才真正进队列
队列也满 → 拒绝策略
完全符合你说的：
不急着放队列，先增加线程去执行，线程不够了再放队列



五、优缺点 & 注意事项
优点
高并发时 线程快速扩容到最大，不积压队列
低并发时，依然只用 core 线程，资源可控
缺点 / 风险
瞬间流量暴增时，线程会瞬间打到 maximumPoolSize
→ 要合理设置 max，避免 OOM、CPU 打爆
非核心线程空闲会被回收，符合线程池设计



















java探针技术


为什么突然聊到这个东西了呢，阿里云的Arthas，这个java程序故障检测利器，它里面使用了这种高级技术，它不同于我们所学的动态代理，反射这种高级用法，它是另一种难度的高级，与JVM紧紧相连，可以说，你要先懂JVM的基本架构了，才能够明白这个技术到底在解决什么问题




一、先搞懂：Java 探针到底是什么？
你可以把 Java 探针（Java Agent）理解成 Java 程序的 “外挂” 或 “插件”：
它是一段特殊的 Java 代码，能在不修改目标程序源代码、不重启程序的前提下，动态修改 / 监控目标程序的字节码；
它不属于业务代码，而是独立的 “辅助程序”，核心作用是监控、诊断、修改运行中的 Java 程序；
常见应用场景：性能监控（如 Arthas 底层就是探针）、日志增强、方法耗时统计、接口调用追踪、甚至动态修复线上问题。
核心原理（通俗版）
Java 程序运行依赖 JVM，JVM 在启动或运行过程中，会预留 “钩子”（Hook），探针就是通过这些钩子，在字节码加载到 JVM 之前 / 之后，对字节码进行修改（比如给方法加日志、统计耗时），最终让修改后的字节码被 JVM 执行。
二、Java 探针的两种核心使用方式
探针主要分两种使用模式，对应不同的应用场景，先记住这两个核心模式：



模式                    	触发时机                                     	核心特点	                                              典型场景
启动时探针（Premain）	目标程序启动时（JVM 启动阶段）	必须在程序启动时指定探针，无法动态附加	程序启动时就需要监控 / 修改的场景（如全局日志增强）
运行时探针（Agentmain）	目标程序运行中	可以动态附加到已运行的 JVM 进程，无需重启	线上程序诊断、动态监控（如 Arthas）


三、从实战入手：先写一个最简单的 Premain 探针
先从最容易上手的「启动时探针」开始，带你写一个能统计方法耗时的探针，步骤清晰，直接跟着做就能跑通。
前置准备
JDK 8+（推荐 8，兼容性最好）
IDE（IDEA/Eclipse）
核心依赖：不需要额外包，JDK 自带 java.lang.instrument 包（探针的核心 API）
步骤 1：编写探针核心类（Premain 类）
这个类是探针的入口，必须包含 premain 方法（固定写法）：


import java.lang.instrument.Instrumentation;

/**
 * 最简单的 Java 探针（Premain 模式）
 * 作用：在程序启动时，打印被监控类的加载信息，并后续演示方法耗时统计
 */
public class TimeCostAgent {

    // 【固定写法】Premain 方法是探针的入口，JVM 启动时会先执行这个方法
    // 参数1：agentArgs - 启动探针时传入的自定义参数
    // 参数2：inst - Instrumentation 是探针的核心工具类，用来操作字节码
    public static void premain(String agentArgs, Instrumentation inst) {
        System.out.println("===== Java 探针启动成功 =====");
        System.out.println("探针接收的自定义参数：" + agentArgs);

        // 关键：注册字节码转换器（核心逻辑，用来修改目标类的字节码）
        // TimeCostTransformer 是我们自定义的“字节码修改器”，下一步写
        inst.addTransformer(new TimeCostTransformer());
    }

    // 备用入口（如果上面的方法不存在，JVM 会找这个无参版本）
    public static void premain(String agentArgs) {
        premain(agentArgs, null);
    }
}

步骤 2：编写字节码转换器（核心，修改目标方法）
要修改字节码，最常用的是 ASM 框架（JDK 自带，无需额外依赖），这里写一个简单的转换器，给目标方法加 “耗时统计”：



import javassist.ClassPool;
import javassist.CtClass;
import javassist.CtMethod;
import java.lang.instrument.ClassFileTransformer;
import java.lang.instrument.IllegalClassFormatException;
import java.security.ProtectionDomain;

/**
 * 字节码转换器：用来修改目标类的字节码
 * 这里用 Javassist（比 ASM 更简单），需要先引入依赖（下面会说）
 */
public class TimeCostTransformer implements ClassFileTransformer {

    // 【核心方法】当 JVM 加载类时，会调用这个方法，返回修改后的字节码
    @Override
    public byte[] transform(ClassLoader loader, String className, Class<?> classBeingRedefined,
                            ProtectionDomain protectionDomain, byte[] classfileBuffer) throws IllegalClassFormatException {
        // 只处理我们指定的目标类（比如 com.example.Demo），避免修改所有类
        if (className == null || !className.replace("/", ".").equals("com.example.Demo")) {
            return null; // 不修改其他类，返回原字节码
        }

        try {
            // 1. 将类名从 JVM 格式（com/example/Demo）转为普通格式（com.example.Demo）
            String targetClassName = className.replace("/", ".");
            System.out.println("===== 探针开始修改类：" + targetClassName + " =====");

            // 2. 使用 Javassist 获取类对象（Javassist 简化了字节码操作）
            ClassPool pool = ClassPool.getDefault();
            CtClass ctClass = pool.get(targetClassName);
            ctClass.stopPruning(true); // 防止类被修剪

            // 3. 遍历类中的所有方法，给每个方法加耗时统计
            for (CtMethod method : ctClass.getDeclaredMethods()) {
                // 跳过构造方法和静态初始化方法
                if (method.getName().equals("<init>") || method.getName().equals("<clinit>")) {
                    continue;
                }

                // 4. 核心：修改方法体，在方法前后加耗时统计代码
                // $proceed() 代表原方法的执行逻辑
                method.addLocalVariable("startTime", CtClass.longType); // 定义局部变量
                method.insertBefore("startTime = System.currentTimeMillis();"); // 方法开始前记录时间
                method.insertAfter("System.out.println(\"方法 " + method.getName() + " 耗时：\" + (System.currentTimeMillis() - startTime) + \"ms\");"); // 方法结束后计算耗时
            }

            // 5. 返回修改后的字节码
            byte[] modifiedByteCode = ctClass.toBytecode();
            ctClass.detach(); // 释放资源
            return modifiedByteCode;

        } catch (Exception e) {
            e.printStackTrace();
            return null; // 出错则返回原字节码
        }
    }
}

步骤 3：动态附加探针（使用 Attach API）
需要用 JDK 自带的 com.sun.tools.attach 包，写一个附加工具类：
java
运行
import com.sun.tools.attach.AttachNotSupportedException;
import com.sun.tools.attach.VirtualMachine;
import com.sun.tools.attach.VirtualMachineDescriptor;

import java.io.IOException;
import java.util.List;

/**
 * 动态附加探针到已运行的 JVM 进程
 */
public class AgentAttacher {
    public static void main(String[] args) throws IOException, AttachNotSupportedException {
        // 1. 获取所有正在运行的 JVM 进程
        List<VirtualMachineDescriptor> vms = VirtualMachine.list();
        for (VirtualMachineDescriptor vm : vms) {
            // 2. 找到目标进程（比如进程名包含 Demo）
            if (vm.displayName().contains("Demo")) {
                // 3. 附加到目标进程
                VirtualMachine virtualMachine = VirtualMachine.attach(vm.id());
                // 4. 加载探针 Jar 包
                virtualMachine.loadAgent("/path/to/agent-demo-1.0-SNAPSHOT.jar");
                // 5. 分离
                virtualMachine.detach();
                System.out.println("探针已成功附加到进程：" + vm.id());
                break;
            }
        }
    }
}
运行步骤：
先启动 Demo 程序（让它一直运行，比如加个死循环）；
运行 AgentAttacher 类，探针会动态附加到 Demo 进程；
Demo 程序后续执行的方法，会自动打印耗时（无需重启）。
五、实际应用场景（新手能落地的）
方法耗时统计：像上面的案例，监控线上接口的耗时，定位慢接口；
日志增强：动态给指定方法加日志（比如打印入参、出参），无需改代码重启；
性能监控：结合 MBean 收集 JVM 指标（内存、GC、线程），实现简易版监控；
动态调试：线上程序出问题时，动态附加探针，打印关键变量，不用重启；
第三方工具底层：Arthas、SkyWalking（链路追踪）、Pinpoint（性能分析）都是基于探针实现的。
总结
核心概念：Java 探针是 JVM 提供的 “字节码修改钩子”，分 Premain（启动时）和 Agentmain（运行时）两种模式，核心是通过 Instrumentation 操作字节码；
核心步骤：写探针入口类（Premain/Agentmain）→ 写字节码转换器（修改目标类）→ 打包为带 MANIFEST.MF 的 Jar 包 → 启动时指定 / 运行时附加；

1. 一句话定义
Java 内存模型（JMM）是一套规范，用来屏蔽各种硬件和操作系统的内存访问差异，保证多线程环境下对共享变量的读写是原子、可见、有序的。
2. 核心抽象：主内存 & 工作内存
JMM 规定：
主内存：所有共享变量（实例对象、静态变量、数组元素）存放的地方，所有线程共享。
工作内存：每个线程私有，保存该线程用到的共享变量副本。
线程不能直接读写主内存，只能操作自己工作内存中的副本，再同步回主内存。
注意：局部变量、方法参数不存在主内存与工作内存交互，天然线程安全。
3. JMM 要解决的三大问题（三大特性）
① 原子性
定义：一个操作不可中断，要么全部执行，要么不执行。
保证：
基本读写（int、boolean 等）具有原子性
synchronized、Lock 保证复合操作原子性
② 可见性
定义：一个线程修改了共享变量，其他线程能立即看到修改结果。
保证：
volatile
synchronized
Lock
final（一旦初始化完成，其他线程可见）
③ 有序性
定义：程序执行顺序按代码顺序，不被重排序。
原因：CPU 和编译器为了优化，会指令重排序。
保证：
volatile（禁止指令重排）
synchronized
Lock
happens-before 原则
4. 核心机制：happens-before 原则（必背）
如果 A happens-before B，那么 A 的结果对 B 可见。
八大规则（面试说 4～5 条就够）：
程序次序规则：单线程内，前面代码 happens-before 后面
锁规则：对一个锁的解锁 happens-before 后续加锁
volatile 规则：对 volatile 变量写 happens-before 后续读
传递性：A→B，B→C ⇒ A→C
线程启动规则：start() happens-before 线程内所有动作
线程终止规则：线程所有动作 happens-before 终止检测
5. volatile 关键字（JMM 最常考点）
volatile 两个核心作用：
保证可见性
禁止指令重排序（通过内存屏障）
volatile 不保证：
复合操作的原子性（如 i++）
适用场景：
状态标记量（如 volatile boolean flag）
单例模式 DCL 必须加 volatile



volatile 保证可见性的核心是：
写 volatile 变量时，立刻刷回主内存，并且让其他线程的缓存副本失效；
读 volatile 变量时，必须放弃本地缓存，重新从主内存拿最新值；
这样就杜绝了线程读「过期副本」的问题，实现了一个线程修改，其他线程能立即看到的可见性。



6. JMM 最终目的
让多线程在并发场景下，安全、正确、高效地访问共享变量，
解决可见性、原子性、有序性问题。










java线程和操作系统里面的线程是一模一样的，本质上就是1对1的线程模型




异常法停止，调用interrupt方法，在线程的run方法中判断当前对象的interrupted状态，如果是中断状态则抛出异常，达到中断线程的效果

在沉睡中停止：先将线程sleep，然后调用interrupt标记中断状态，interrupt会将阻塞状态的线程中断，会抛出中断异常，达到停止线程的效果

stop暴力停止：调用stop方法会被暴力停止，但是这个方法已经被弃用了

使用return停止线程



调用 interrupt () 让线程抛异常的「完整原理」

步骤 1：调用 interrupt () → 设置中断标记
每个线程都有一个内置的中断标记位（默认 false）：
调用 thread.interrupt() → 标记位被设为 true；
这个操作是线程安全的，无需加锁。

步骤 2：线程检测中断标记（两种场景）
线程只会在特定时机检测这个标记，触发异常的核心场景是：

场景 A：线程处于「阻塞状态」（sleep/wait/join/park）
如果线程正在执行这些阻塞方法，此时检测到「中断标记为 true」：
首先清除中断标记（把标记位重置为 false）；
立即抛出 InterruptedException 异常；
阻塞方法停止执行，线程从阻塞态转为就绪态。


场景 B：线程处于「运行状态」
如果线程在正常运行（没有阻塞），interrupt() 只会设置标记位，不会抛异常！此时需要线程自己主动检测标记：
// 运行态线程主动检测中断标记
while (!Thread.currentThread().isInterrupted()) {
    // 正常业务逻辑
    doWork();
    
    // 手动检测，主动退出
    if (Thread.currentThread().isInterrupted()) {
        System.out.println("检测到中断，主动退出");
        break;
    }
}


步骤 3：异常的捕获与处理
抛出的 InterruptedException 是受检异常，必须捕获：
Thread t = new Thread(() -> {
    try {
        // 阻塞方法：sleep 会检测中断标记
        Thread.sleep(10000); 
    } catch (InterruptedException e) {
        // 这里捕获到异常，说明线程被中断了
        System.out.println("线程被中断，sleep 提前结束");
        // 注意：此时中断标记已经被清除（false），如果需要可手动重置
        Thread.currentThread().interrupt();
    }
});

t.start();
// 主线程调用 interrupt()，设置中断标记
Thread.sleep(1000);
t.interrupt();

核心通信方式


1. 共享内存 / 共享变量（最基础）
原理
基于 JMM（Java 内存模型），多个线程访问同一个共享变量（实例变量、静态变量），通过修改 / 读取变量完成通信。
关键保障
必须保证可见性和原子性，否则会出现数据不一致：
可见性：volatile 关键字（强制变量读写刷主内存）；
原子性：synchronized/Lock（保证复合操作不被打断）。


// volatile保证可见性
    private static volatile boolean flag = false;
    private static int count = 0;

    public static void main(String[] args) {
        // 线程1：等待flag为true后执行
        new Thread(() -> {
            while (!flag) {
                // 自旋等待
            }
            System.out.println("线程1收到信号，count=" + count);
        }).start();

        // 线程2：修改共享变量，完成通信
        new Thread(() -> {
            count = 100;
            flag = true; // 发送信号
            System.out.println("线程2发送信号，flag=true");
        }).start();
    }






Object 类的 wait ()/notify ()/notifyAll ()


原理
基于「对象监视器（monitor）」实现，线程通过释放 / 获取锁 + 等待 / 唤醒机制协调执行：
wait()：线程释放对象锁，进入该对象的等待队列，等待被唤醒；
notify()：唤醒该对象等待队列中的一个线程（随机）；
notifyAll()：唤醒该对象等待队列中的所有线程。
核心规则
必须在 synchronized 代码块 / 方法中调用（否则抛 IllegalMonitorStateException）；
唤醒后的线程需重新竞争锁，拿到锁后才会从 wait() 处继续执行。

适用场景
生产者 - 消费者模型，缺点是唤醒线程随机（notify()），易出现「虚假唤醒」（需用 while 循环检测条件）。






Lock 锁的 Condition 条件变量（进阶版 wait/notify）
原理
java.util.concurrent.locks.Condition 是 Lock 锁的配套工具，替代传统的 wait/notify，支持多条件队列：
await()：替代 wait()，释放锁并进入条件队列；
signal()：替代 notify()，唤醒单个等待线程；
signalAll()：替代 notifyAll()，唤醒所有等待线程。

核心优势
可创建多个 Condition，实现精准唤醒（解决 notify 随机唤醒问题）。


 private static final Lock lock = new ReentrantLock();
    // 两个条件队列：生产者队列、消费者队列
    private static final Condition producerCond = lock.newCondition();
    private static final Condition consumerCond = lock.newCondition();
    private static String data;
    private static boolean hasData = false;

    public static void main(String[] args) {
        // 消费者
        new Thread(() -> {
            lock.lock();
            try {
                while (!hasData) {
                    consumerCond.await(); // 消费者等待
                }
                System.out.println("消费者收到：" + data);
                hasData = false;
                producerCond.signal(); // 唤醒生产者
            } catch (InterruptedException e) {
                e.printStackTrace();
            } finally {
                lock.unlock();
            }
        }).start();

        // 生产者
        new Thread(() -> {
            lock.lock();
            try {
                while (hasData) {
                    producerCond.await(); // 生产者等待
                }
                data = "Condition 通信数据";
                hasData = true;
                consumerCond.signal(); // 精准唤醒消费者
                System.out.println("生产者发送数据完成");
            } catch (InterruptedException e) {
                e.printStackTrace();
            } finally {
                lock.unlock();
            }
        }).start();
    }





阻塞队列（BlockingQueue）（最高效）
原理
基于「队列 + 阻塞」机制，底层封装了 Lock 和 Condition，实现生产 / 消费的自动阻塞：
队列空时，消费者线程 take() 会阻塞；
队列满时，生产者线程 put() 会阻塞。
核心优势
无需手动处理锁和等待 / 唤醒，JDK 原生实现，开箱即用。
常用阻塞队列
ArrayBlockingQueue：数组实现，有界队列；
LinkedBlockingQueue：链表实现，可选无界 / 有界；
SynchronousQueue：无容量，生产消费一对一。


// 有界阻塞队列，容量1
    private static final BlockingQueue<String> queue = new ArrayBlockingQueue<>(1);

    public static void main(String[] args) {
        // 消费者
        new Thread(() -> {
            try {
                String data = queue.take(); // 队列空则阻塞
                System.out.println("消费者收到：" + data);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();

        // 生产者
        new Thread(() -> {
            try {
                queue.put("BlockingQueue 通信数据"); // 队列满则阻塞
                System.out.println("生产者发送数据完成");
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();
    }







一、核心定义（先一句话分清）
Java 线程：基于操作系统内核线程（1:1 映射），是操作系统级别的执行单元，由 OS 内核调度。
Go 协程（Goroutine）：Go 语言运行时（Goruntime）管理的轻量级执行单元，基于 M:N 调度模型（M 个协程映射到 N 个 OS 线程），由 Go 运行时而非内核调度。



1. Java 线程 1:1 模型的痛点
Java 线程直接映射内核线程，意味着：
每创建一个线程，OS 需分配内核栈、TCB（线程控制块）等资源，开销大；
线程切换需从「用户态→内核态→用户态」，上下文切换成本高；
线程数过多时，内核调度压力大，CPU 大部分时间消耗在切换上，而非执行业务逻辑。


2. Go 协程 GPM 调度模型（核心）
GPM 是 Go 协程调度的核心，三者分工：
G（Goroutine）：协程，包含业务逻辑和栈信息，是调度的基本单位；
P（Processor）：处理器，相当于「执行上下文」，绑定 M 后才能执行 G，默认数量 = CPU 核心数；
M（Machine）：对应 OS 内核线程，是真正执行代码的载体。
核心优势：
协程切换在用户态完成，无需内核参与，上下文切换仅需保存 / 恢复少量寄存器，成本是线程的 1/100 甚至更低；
协程阻塞时（如网络 IO、Channel 操作），P 会与 M 解绑，M 去执行其他 P 中的 G，避免内核线程空等。




3. 协程栈动态扩容缩容
Java 线程栈是固定大小（启动时指定，默认 1MB），过小易栈溢出，过大浪费内存；

Go 协程栈初始仅 2KB，采用「分段栈 + 连续栈」技术，可动态扩容（最大 1GB）、缩容，完全适配业务需求，内存利用率极高。



通信方式


java通过共享内存（volatile/synchronized/Lock）、阻塞队列、wait/notify 等

go通过「通道（Channel）」，当然共享内存也行，但是不推荐



 Go 协程的抢占式调度解决了什么问题？
Go 1.14 前是协作式调度，若协程执行无限循环（无 IO/Channel 操作），会霸占 P（处理器），导致其他协程无法执行；1.14 后引入基于信号的抢占式调度，运行时可强制中断长时间执行的协程，保证所有协程都有执行机会，解决了「协程饿死」问题。



 什么场景下用 Java 线程，什么场景下用 Go 协程？
Java 线程：适合 CPU 密集型任务（充分利用多核）、企业级应用（生态完善，框架丰富）；
Go 协程：适合高并发 IO 密集型任务（如微服务、网关、消息队列），百万级并发场景下资源占用远低于 Java 线程。








JUC常用包

原子操作类
基于CAS机制，保证单个变量操作的原子性

AtomicInteger/AtomicLong：替代 int/long + synchronized，实现原子自增 / 自减（如计数器）；
AtomicBoolean：原子布尔值，用于状态标记（如开关）；
AtomicReference：原子引用类型，用于对象的原子更新；
AtomicStampedReference：解决 CAS 的「ABA 问题」（带版本号的原子引用）。


 显式锁框架

ReentrantLock：可重入锁（和 synchronized 一样支持重入），支持公平 / 非公平锁，常用方法：
lock()：加锁；unlock()：解锁（必须放 finally 中）；
tryLock(long timeout, TimeUnit unit)：超时获取锁，避免死锁；
lockInterruptibly()：可中断获取锁。

 阻塞队列（java.util.concurrent）
核心原理
基于「队列 + 阻塞」机制，封装了锁和 Condition，实现生产 / 消费的自动阻塞，是线程通信的首选工具。



队列类型	特点	适用场景

LinkedBlockingQueue	链表实现、可选无界（默认 Integer.MAX_VALUE）	高并发生产消费

线程池（java.util.concurrent）
核心价值
复用线程、控制并发数、管理任务队列，避免频繁创建 / 销毁线程的性能开销。
核心类 & 方法
ThreadPoolExecutor：线程池核心实现类（推荐直接使用，而非 Executors 工具类），构造参数（面试必问）：


// 核心参数说明
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, // 核心线程数（常驻线程）
    5, // 最大线程数（核心+临时）
    60, // 临时线程空闲超时时间
    TimeUnit.SECONDS, // 超时时间单位
    new ArrayBlockingQueue<>(10), // 任务队列
    Executors.defaultThreadFactory(), // 线程工厂
    new ThreadPoolExecutor.AbortPolicy() // 拒绝策略
);

Executors 工具类的问题：
newCachedThreadPool()：最大线程数无上限（Integer.MAX_VALUE），易创建大量线程导致 OOM；
newFixedThreadPool()/newSingleThreadExecutor()：任务队列无界（LinkedBlockingQueue），任务过多易 OOM；
自定义 ThreadPoolExecutor 可手动控制核心线程数、最大线程数、队列容量、拒绝策略，更安全。










1. AbortPolicy（默认策略）
行为：直接抛出 RejectedExecutionException 运行时异常
特点：不处理任务，直接中断流程，让调用方感知失败
适用：关键业务、不能丢失任务，需要上层捕获异常处理
2. CallerRunsPolicy
行为：让提交任务的调用线程自己执行该任务
特点：不抛弃任务、不抛异常，用调用者压力反向限流
适用：允许轻微性能下降、不允许任务丢失的场景，如日志、低优先级任务
3. DiscardPolicy
行为：默默丢弃当前任务，不抛异常、无任何提示
特点：风险极高，任务丢失无感知
适用：极不重要、可丢失的非核心任务，极少使用
4. DiscardOldestPolicy
行为：丢弃队列中最早的一个任务，再尝试提交当前任务
特点：牺牲旧任务保新任务
适用：实时性要求高、旧任务已无意义的场景（如实时数据上报）















同步器（java.util.concurrent）
核心作用
实现线程间的同步等待，解决复杂的并发协调问题。
高频类 & 场景
CountDownLatch：倒计时门闩，让主线程等待多个子线程执行完毕（如汇总多线程结果）；
CyclicBarrier：循环屏障，让多个线程互相等待，到达屏障点后一起执行（如多阶段任务）；
Semaphore：信号量，控制同时访问资源的线程数（如限流）；
FutureTask：封装 Callable 任务，获取异步执行结果。


CountDownLatch
其核心是通过一个计数器（Counter）实现线程间的协调，常用于多线程任务的分阶段控制或主线程等待多个子线程就绪的场景，核心原理：
初始化计数器：创建 CountDownLatch 时指定一个初始计数值（如 N）。
等待线程阻塞：调用 await() 的线程会被阻塞，直到计数器变为 0。
任务完成通知：其他线程完成任务后调用 countDown()，使计数器减 1。
唤醒等待线程：当计数器减到 0 时，所有等待的线程会被唤醒。









AQS 是 java.util.concurrent.locks 包下的抽象队列同步器，是 JUC 中绝大多数同步组件（锁、同步器）的底层实现框架，核心目标是封装「等待队列 + 状态管理」的通用逻辑，让开发者只需实现少量核心方法就能快速构建自定义同步器（如 ReentrantLock、CountDownLatch 等）。



AQS核心东西就这么些


核心状态：volatile 变量 state
AQS 用一个volatile 修饰的 int 型变量 state 表示同步状态（如锁的持有次数、计数器值）；
对 state 的修改通过 CAS 操作 保证原子性，结合 volatile 保证可见性；
开发者可通过 getState()/setState()/compareAndSetState() 操作该状态。


2. 核心结构：双向链表（CLH 队列）
当线程获取同步状态失败时，AQS 会将该线程封装成 Node 节点，加入到双向阻塞队列（CLH 队列） 中，等待被唤醒：
Node 节点核心属性：
thread：当前等待的线程；
waitStatus：节点状态（CANCELLED (1)、SIGNAL (-1)、CONDITION (-2)、PROPAGATE (-3)、0）；
prev/next：前驱 / 后继节点。
队列特性：FIFO（先进先出），头节点是「已获取锁的线程」，其余节点是「等待锁的线程」。


AQS 是 JUC 同步组件的底层框架，核心：
用 volatile 的 state 表示同步状态，CAS 保证原子修改；
失败线程封装成 Node 加入 CLH 双向队列，LockSupport 阻塞；
支持独占式（ReentrantLock）和共享式（CountDownLatch）；
开发者只需重写 tryAcquire/tryRelease 等模板方法，即可实现自定义同步器。







死锁触发条件

互斥条件：资源（锁）只能被一个线程持有，不能被多个线程共享；
持有并等待条件：线程持有已获取的资源，同时等待其他线程持有的资源；
不可剥夺条件：线程持有的资源（锁）不能被强制剥夺，只能主动释放；
循环等待条件：多个线程形成「A 等 B、B 等 C、C 等 A」的循环等待资源链。


// 死锁示例代码
public class DeadLockDemo {
    private static final Object lock1 = new Object();
    private static final Object lock2 = new Object();

    public static void main(String[] args) {
        // 线程1：先拿lock1，再拿lock2
        new Thread(() -> {
            synchronized (lock1) {
                System.out.println("线程1持有lock1，等待lock2");

        // 线程2：先拿lock2，再拿lock1

            synchronized (lock2) {
                System.out.println("线程2持有lock2，等待lock1");
                try { Thread.sleep(100); } catch (InterruptedException e) {}
                synchronized (lock1) {
                    System.out.println("线程2获取lock1，执行完成");
                }
            }
        }).start();
    }
}

 JVM 几种垃圾回收算法
核心答案：JVM 垃圾回收算法主要有 4 种，核心是分代收集思想：
标记 - 清除算法：先标记存活对象，再清除垃圾对象；缺点是产生内存碎片，效率低。
复制算法：将内存分为两块，存活对象复制到空块，清空原块；优点是无碎片，效率高，适合年轻代（对象朝生夕死）。
标记 - 整理算法：标记存活对象后，将其向一端移动并清空边界外区域；无碎片，适合老年代（对象存活久）。
分代收集算法：根据对象存活周期划分区域，年轻代用复制算法，老年代用标记 - 清除 / 整理算法，兼顾效率与内存利用率。





会发生 OOM 的区域及场景
核心答案：除程序计数器外，其他区域都可能 OOM：
堆 OOM：对象过多且无法回收，如创建大量对象、内存泄漏未释放。
方法区（元空间）OOM：加载类过多（如动态生成大量类、反射滥用），元空间耗尽。
虚拟机栈 / 本地方法栈 OOM：递归过深、创建大量线程，栈帧过多超出栈容量。
直接内存 OOM：NIO 频繁分配直接内存，未及时释放，超出最大限制。




  




 双亲委派机制，如何破坏双亲委派
核心答案：
双亲委派机制：类加载时，先委托父类加载器尝试加载，父类加载失败才由自身加载；保证类的唯一性（同个类由同个类加载器加载），避免类冲突。
破坏方式：
自定义类加载器，重写 loadClass() 方法，绕过父类加载逻辑。
SPI 机制（如 JDBC）：用线程上下文类加载器，打破双亲委派，让父类加载器委托子类加载器加载。
OSGi 模块化：模块间类加载器相互可见，实现动态加载与卸载。


避免类重复加载，保证 Java 核心类（如 java.lang.Object）的唯一性。
防止核心 API 被恶意篡改，保障程序安全。






 类加载过程
核心答案：类加载分为 5 个阶段：
加载：读取 class 文件（字节流），生成 Class 对象。
验证：验证 class 文件格式、语义、字节码等，保证安全。
准备：为静态变量分配内存，赋默认值（如 int=0）。
解析：将符号引用替换为直接引用（如方法名→内存地址）。
初始化：执行 <clinit>() 方法，为静态变量赋实际值、执行静态代码块。




 常见垃圾回收器
新生代：Serial（单线程）、Parallel Scavenge（并行，关注吞吐量）、ParNew（并行，配合 CMS）。
老年代：Serial Old、Parallel Old、CMS（并发标记清除，关注低停顿）、G1（区域化回收，兼顾吞吐量与低停顿）。
现代推荐：G1 为 JDK 9+ 默认回收器，适合大内存、低延迟场景。





 G1 回收过程
初始标记：STW，标记 GC Roots 直接关联的对象。
并发标记：与用户线程并发，遍历堆标记所有存活对象。
最终标记：STW，修正并发标记期间变动的对象。
筛选回收：选择回收收益高的区域，STW 进行复制清除，控制停顿时间。







1. 核心基础算法：标记 - 复制（Mark-Copy）
G1 将整个堆内存划分为多个大小相等的独立区域（Region），回收时的核心逻辑是：
标记：先标记出 Region 中存活的对象；
复制：将存活对象复制到空的、干净的 Region 中，原 Region 直接清空（无需清理垃圾，效率高）。
这种算法解决了传统标记 - 清除（Mark-Sweep）的内存碎片问题，也避免了标记 - 整理（Mark-Compact）的全堆移动开销。
2. 辅助算法：标记 - 清除（Mark-Sweep）
G1 并非完全依赖标记 - 复制：
当待回收 Region 中存活对象占比极高（复制成本大于清除成本）时，会降级使用标记 - 清除算法；
此外，G1 的 “并发标记” 阶段本质是标记算法的实现，为后续的复制 / 清除做准备。
3. 关键补充：分代回收思想
G1 保留了新生代（Eden、Survivor）和老年代的概念（但不再是物理隔离，而是通过 Region 动态划分）：
新生代回收（Young GC）：纯标记 - 复制，快速回收年轻对象；
混合回收（Mixed GC）：同时回收新生代 + 部分老年代 Region（优先选垃圾占比高的 Region，即 “Garbage-First” 的由来），核心仍是标记 - 复制。













 GC 停顿过久优化
短期缓解：
增大堆内存，减少 GC 频率。
切换至 G1/CMS 等低停顿回收器。
长期根治：
优化代码，减少大对象创建，及时释放无用引用。
合理设置新生代大小，避免频繁 Full GC。
分析 GC 日志（-XX:+PrintGCDetails），定位停顿原因。






开发选择 synchronized 还是 ReentrantLock
核心答案：
优先选 synchronized：
代码简洁，无需手动释放锁，避免死锁。
JVM 优化后性能与 ReentrantLock 接近。
适合简单同步场景（如方法级、代码块级同步）。
选 ReentrantLock：
需要可中断锁、公平锁、多个条件变量。
需要细粒度控制（如尝试获取锁 tryLock()）。
复杂同步场景（如读写分离、定时锁等待）。




Redis 过期策略
惰性删除：访问 key 时检查是否过期，过期则删除。
定期删除：定时随机抽取部分 key，删除过期项，平衡 CPU 与内存。
内存淘汰机制：当内存满时，按策略删除 key（如 allkeys-lru 淘汰最少使用的 key）。





Redis 高可用方案
主从复制：主节点写，从节点读，实现读写分离与数据备份。
哨兵模式：监控主节点状态，主节点故障时自动选举新主节点，实现故障转移。
集群模式：分片存储数据，支持水平扩展，提升并发与容量。






38. 订单系统超时未支付设计方案
核心答案
基于「Redis ZSet + 定时扫描 + 消息队列」实现，兼顾实时性与系统稳定性，核心是用 ZSet 做 “延时任务池”，避免数据库轮询压力。
实现流程
订单创建时入 ZSet：
订单生成后，以订单ID为 value、超时时间戳为 score，存入 Redis ZSet（如 key：order:timeout:pool）。
后台线程循环扫描：
启动独立线程（或定时任务），每秒扫描 ZSet 中score ≤ 当前时间戳的订单（ZRANGEBYSCORE order:timeout:pool 0 {当前时间}）。
过滤有效订单：
取出超时订单后，先校验订单状态（未支付），避免重复处理（防止消息重复消费）。
发消息队列异步处理：
将有效超时订单 ID 发送到 MQ（如 RocketMQ/Kafka），消费端接收后执行：
更新订单状态为 “已取消”；
释放库存 / 优惠券；
记录订单日志。
删除 ZSet 中已处理订单：
处理完成后，从 ZSet 中删除该订单 ID（ZREM），避免重复扫描。
面试金句
核心是 “Redis ZSet 做延时任务池 + MQ 异步解耦”，既避免数据库全表扫描的性能问题，又通过 MQ 保证订单状态更新的最终一致性；扫描时需校验订单状态，防止重复处理。

XXL-Job 处理订单超时未支付会有什么问题
核心答案
XXL-Job 作为分布式调度框架，处理订单超时未支付时，存在以下核心问题：
调度精度不足：
XXL-Job 基于 cron 表达式调度（最小精度秒级），若配置 “每秒扫描”，仍可能出现 “订单超时 1 秒后才被处理” 的延迟；高频扫描（如每秒）还会增加调度中心压力。
任务堆积与性能问题：
若短时间内大量订单超时（如大促），XXL-Job 的执行器线程池会被占满，任务堆积，导致订单取消延迟，甚至影响其他定时任务。
分布式重复执行风险：
若执行器多实例部署，即使配置 “单机执行”，仍可能因调度中心与执行器网络抖动，导致同一批超时订单被多个执行器处理（需额外加幂等性校验）。
资源占用过高：
若直接在 XXL-Job 任务中查询数据库（如 “select * from order where status = 未支付 and pay_timeout < now ()”），大订单量下全表扫描会导致数据库压力陡增，甚至锁表。
无实时性保障：
XXL-Job 是 “被动调度”，而非 “主动触发”，无法做到订单超时瞬间立即处理，适合非极致实时的场景（若要求毫秒级处理，需用 Redis ZSet + 实时扫描）。







支付系统防止重复支付（保证幂等性）
核心答案
通过「前端防重 + 后端多层幂等校验 + 数据库兜底」三层防护，确保同一订单仅支付一次，核心是 “唯一标识 + 状态校验 + 原子操作”。
完整实现方案
1. 前端防重（第一道防线）
支付按钮点击后立即置灰禁用，防止重复点击；
支付请求发送后，用localStorage/sessionStorage记录 “订单支付中” 状态，页面刷新后校验状态，避免重复发起请求；
前端拦截重复请求（如 axios 取消重复的支付请求）。
2. 后端核心幂等校验（第二道防线）
Redis 分布式锁 + 状态记录：
① 生成唯一支付标识：pay:lock:{订单ID}；
② 支付请求到达时，先用SET pay:lock:{订单ID} {请求ID} NX EX 30加锁（30 秒过期，防止死锁）；
③ 加锁成功：校验订单状态（未支付），执行业务逻辑；加锁失败：直接返回 “支付中，请稍后”；
④ 支付完成 / 失败后，删除 Redis 锁，并记录订单最终状态。
请求唯一 ID 校验：
前端生成唯一请求 ID（如 UUID），后端用 Redis 记录 “请求 ID - 处理状态”，重复请求直接驳回。
3. 数据库兜底（最后一道防线）
唯一索引：给订单支付记录表（pay_record）的order_id字段加唯一索引，重复插入会触发主键 / 唯一索引冲突，数据库直接拒绝；
订单状态机管控：
订单状态设计为 “待支付→支付中→已支付 / 支付失败”，支付前必须校验当前状态为 “待支付”，状态变更用UPDATE order SET status='支付中' WHERE order_id={ID} AND status='待支付'（行锁 + 条件更新，原子操作）。
4. 回调幂等（第三方支付回调场景）
微信 / 支付宝回调时，用回调参数中的out_trade_no（订单 ID）+transaction_id（支付流水号）做唯一标识；
回调接口先校验 Redis / 数据库中的支付状态，已支付则直接返回 “成功”，不重复处理。

电商秒杀扣库存：悲观锁真实场景（你说的完全正确）
场景：库存 = 1两个请求同时来扣库存。
不加锁会发生什么？
A、B 同时执行：
sql
SELECT stock FROM goods WHERE id=1;
都读到 stock=1。
然后各自执行：
sql
UPDATE goods SET stock=stock-1 WHERE id=1;
最终库存变成 0，但实际卖了 2 件 → 超卖。
原因：普通 SELECT 是快照读，不加锁，彼此看不见对方的修改。
为什么必须用 SELECT ... FOR UPDATE
你这句话是核心真理：
MVCC 会导致快照读，并发下更新会覆盖，加普通行锁没用，必须 SELECT ... FOR UPDATE 做当前读 + 阻塞。
关键结论（面试必背）
普通 UPDATE 确实加行锁但它是执行时才加锁，前面的 SELECT 还是快照读，读到的是旧值。→ 依然会超卖。
MVCC 救不了并发扣库存不管是 RC（读已提交）还是 RR（可重复读），快照读都会读到旧数据。你判断库存够不够，是基于旧数据做的，然后再 UPDATE。→ 逻辑已经错了，锁加在 UPDATE 上已经晚了。
SELECT ... FOR UPDATE 做两件事
把这条记录加排他锁
强制当前读，拿到最新数据
→ 后面的请求必须阻塞，等锁释放才能继续。
正确悲观锁流程（真实业务代码）
sql
START TRANSACTION;

-- 关键：锁住当前行 + 当前读
SELECT stock FROM goods WHERE id=1 FOR UPDATE;

IF stock > 0 THEN
    UPDATE goods SET stock=stock-1 WHERE id=1;
    -- 生成订单...
END IF;

COMMIT;
第二个请求会阻塞在 SELECT ... FOR UPDATE，直到第一个事务提交 / 回滚释放锁，才能读到最新库存。
你这段话的精华总结（可以直接背）
MVCC 解决的是读 - 写冲突，不解决写 - 写冲突。
秒杀扣库存是先查后改的复合操作，必须把 “查” 和 “改” 变成原子操作。
普通 SELECT 是快照读，会读到旧库存，导致超卖。
必须用 SELECT ... FOR UPDATE 做当前读 + 排他锁，强制串行化，才能保证不超卖。

常见限流方法
计数器法：固定时间窗口内计数，超过则拒绝，实现简单但存在临界问题。
滑动窗口：将时间窗口拆分为多个小窗口，动态统计，更精确。
漏桶算法：请求以恒定速率流出，平滑流量，应对突发流量。
令牌桶算法：以恒定速率生成令牌，请求需获取令牌才能执行，允许一定突发流量（Guava RateLimiter、Sentinel 实现）。
分布式限流：基于 Redis（如INCR、Lua 脚本）或网关层（如 Spring Cloud Gateway）实现集群级限流。



1. 计数器法（固定窗口计数器）
核心思想：在固定时间窗口（如 1 秒）内，对请求次数进行计数，超过阈值则拒绝服务。
实现：使用原子变量或 Redis 的INCR命令，每来一个请求计数 + 1，窗口重置时清零。
优点：实现简单、性能极高，适合对精度要求不高的场景。
缺点：存在临界问题（边界穿透）。例如限制每秒 100 次请求，若第 1 秒最后 10ms 和第 2 秒前 10ms 各来了 100 次请求，实际 20ms 内就处理了 200 次，瞬间流量是阈值的 2 倍，可能压垮服务



2. 滑动窗口算法
核心思想：将固定时间窗口拆分为多个更小的时间片（如 1 秒拆为 10 个 100ms 的小窗口），每次请求只统计当前时间往前推一个窗口内的所有小窗口请求总和，动态滑动窗口边界。
实现：用数组或链表记录每个小窗口的计数，随时间推移丢弃过期的小窗口，加入新的小窗口。
优点：解决了固定窗口的临界问题，统计更精确，能平滑处理边界流量。
缺点：时间片划分越细，精度越高，但内存占用和计算复杂度也随之上升。





3. 漏桶算法
核心思想：将请求比作水滴，注入一个固定容量的漏桶，漏桶以恒定速率向外漏水（处理请求）。若水滴注入速度过快，桶满则溢出（拒绝请求）。
实现：用队列缓冲请求，后台线程以固定速率从队列中取出请求处理；或用令牌桶变种实现。
优点：强制平滑流量，无论请求多么突发，输出速率始终恒定，能有效保护下游服务。
缺点：无法应对突发的合法流量，即使系统有空闲资源，也必须等待漏桶漏水，资源利用率较低。

一、先搞懂：AQS 到底是个啥？（本质 + 核心定位）
AQS 的全称是AbstractQueuedSynchronizer（抽象队列同步器），你可以把它理解为：Java 并发包（JUC）中所有锁 / 同步工具的 “通用骨架”。
打个生活化的比方：
你去银行办理业务，银行有「叫号机（同步状态）」+「排队区（等待队列）」—— 这就是 AQS 的核心；
叫号机显示 “0”= 没人办理（无锁），显示 “1”= 有人办理（加锁）；
顾客（线程）来办理业务，先抢叫号机：抢到了直接办（拿到锁），没抢到就去排队区等着（进入等待队列），等前面的人办完了，叫号机重置，再叫下一个人（唤醒线程）。
AQS 的核心定位：
JUC 包中的ReentrantLock（可重入锁）、CountDownLatch（倒计时门闩）、Semaphore（信号量）、ReentrantReadWriteLock（读写锁）等，底层全是基于 AQS 实现的——AQS 把 “排队、阻塞、唤醒、状态管理” 这些通用逻辑抽成模板，子类只需要重写少量方法，就能实现不同的锁 / 同步器。
二、AQS 的核心原理：3 大核心组件 + 2 大核心流程
AQS 的核心设计就三件事：管理同步状态、维护等待队列、处理线程阻塞 / 唤醒，拆解如下：
1. 核心组件 1：同步状态（volatile int state）——“银行叫号机”
这是 AQS 最核心的变量，相当于 “锁的标识”：
volatile 修饰：保证多线程间的可见性（一个线程改了 state，其他线程立刻能看到）；
CAS 操作：保证修改 state 的原子性（比如多个线程同时抢锁，只有一个能成功修改 state）；
可自定义含义：不同同步工具对 state 的解读不同：
ReentrantLock：state=0→无锁，state=1→加锁，重入时 state 递增（比如重入 2 次→state=2）；
Semaphore（信号量）：state=5→允许 5 个线程同时访问；
CountDownLatch：state=3→需要等 3 个线程执行完，state 减到 0 才放行。
2. 核心组件 2：CLH 等待队列 ——“银行排队区”
这是一个双向链表实现的队列，专门存放 “抢锁失败” 的线程，特点：
FIFO（先进先出）：保证线程等待的公平性（非公平锁可插队）；
每个节点对应一个线程：节点里存了线程引用、等待状态（比如是否取消、是否需要唤醒）、前驱 / 后继节点；
阻塞 / 唤醒：用LockSupport.park()阻塞线程（相当于 “冻结排队的顾客”），LockSupport.unpark()唤醒线程（相当于 “叫下一个顾客”）—— 比Object.wait()/notify()更灵活。
3. 核心组件 3：可重写的核心方法 ——“自定义业务规则”
AQS 是抽象类，本身不实现具体的锁逻辑，而是提供模板方法，子类（比如 ReentrantLock）通过重写以下方法定义 “怎么抢锁、怎么释放锁”：
方法	作用（大白话）	适用场景
tryAcquire(int arg)	尝试独占式获取锁（比如 ReentrantLock）	独占锁（一次只能一个线程拿）

计网讲了讲cookie，session这个东西，突然我想到了企业中登录功能之前主流方法不就是这个吗，所以说我们来细细的讲一下



session存在服务器中，cookie通过提供sessionId来帮助服务器找到session对象，完成状态的保存，这是前提，不用多说了吧



一、先明确：企业里为什么曾经（现在很多内网 / 传统项目依然）主流是 Cookie+Session？
HTTP 是无状态协议，服务端记不住你是谁。
Cookie：存在客户端，用来存一个「会话标识」
Session：存在服务端，用来存真正的用户登录信息
这套方案最大优势：服务端完全可控，这对企业系统（内网、金融、政企、管理后台）极其重要。
二、单体应用下：企业标准 Cookie+Session 登录流程（基础必背）
用户登录
前端提交账号 / 密码到服务端。
服务端校验 & 创建 Session
校验通过后，在服务端内存创建一个 Session 对象，存储：
userId
用户名
角色 / 权限
登录时间等
并生成全局唯一的 SessionID（一般是 UUID）。
通过 Cookie 下发 SessionID
服务端通过响应头：
plaintext
Set-Cookie: JSESSIONID=xxxx; HttpOnly; Path=/; ...
把 SessionID 写入浏览器 Cookie。
后续请求自动鉴权
浏览器每次请求都会自动携带该 Cookie。
服务端根据 Cookie 里的 JSESSIONID 查找对应 Session，判断是否登录、是否有权限。
登出
服务端销毁 Session；客户端清除 Cookie。


分布式 / 集群环境下：原生 Cookie+Session 直接崩掉（面试核心痛点）
企业一上集群（多 Tomcat、多实例、Nginx 负载均衡），原生 Session 完全不能用。
分布式下的 3 个致命问题
Session 不共享
第一次请求落到 Tomcat A，生成 SessionA；
第二次负载均衡落到 Tomcat B，B 里没有 SessionA → 直接登出。
服务重启就丢登录
Session 存在应用内存里，重启 / 发版 → 用户全部重新登录。
无法水平扩展
单机内存有限，大量在线用户会 OOM。
面试官问：为什么分布式不能直接用单机 Session？你就答这 3 点。




企业级分布式环境：Cookie+Session 的 4 种解决方案（按企业真实使用优先级排序）
这是面试最核心、最加分的部分。
方案 1：Session 集中式存储（✅ 企业真正主流方案）
原理
把 Session 从「应用服务器内存」剥离出来，统一存在共享中间件里：
主流：Redis
备选：Memcached
所有应用实例都访问同一个 Redis。
完整流程
登录成功，生成 SessionID
Session 数据存入 Redis
Key：session:xxxx（SessionID）
Value：用户信息（JSON / 序列化）
设置过期时间（30min~2h）
SessionID 依旧通过 Cookie 下发
任意请求、任意应用实例，都从 Redis 取 Session
登出 / 踢人：直接删 Redis 里的 Key
优点（面试必说）
✅ 真正解决分布式共享
✅ 应用重启不影响登录
✅ 支持水平扩展
✅ Redis 高性能、支持过期、支持持久化
✅ 服务端可控（随时踢人、封禁）
缺点
强依赖 Redis，Redis 挂掉会影响登录（所以要 Redis 集群 / 主从 / 哨兵）
企业落地
SpringBoot + Spring Session 一行配置就能自动把 Session 存 Redis，零业务代码侵入。
这是目前传统 Web 项目、内网管理系统、金融政企系统的标准方案。



Session 粘性（Sticky Session / IP 哈希）
原理
在 Nginx 配置 ip_hash 策略：同一个客户端 IP，永远转发到同一台 Tomcat。
优点
极其简单
不用改代码、不用加中间件
缺点（致命）
某台 Tomcat 挂掉 → 这一批用户直接丢登录
负载严重不均
无法真正水平扩展
企业场景
只用于早期、非核心、小集群临时过渡，绝不用于核心生产。



方案 3：Session 复制（Session Replication）
原理
利用 Tomcat 内置机制，节点之间互相同步 Session。一台创建，所有节点都拷贝一份。
优点
不用改业务代码
缺点
性能极差：同步耗带宽
数据冗余：每台机器都存全量 Session
节点一多就出现同步风暴，集群直接崩
企业场景
几乎淘汰，只在极老的小集群（2~3 台）里偶尔见到。



方案 4：加密 Cookie 存储（把 Session 直接放客户端）
原理
不存服务端，把用户信息加密 + 签名后直接存在 Cookie 里。
优点
不占服务端存储
无共享问题
缺点
Cookie 只有～4KB，存不了多少东西
每次请求都带一大段 Cookie，浪费流量
加密也存在泄露风险
企业场景
极轻量小系统，几乎不用。



企业级 Cookie+Session 安全配置（面试加分项）
企业不会裸用 Cookie，必须加这些安全头：
HttpOnly=true
禁止 JS 读取 Cookie，防 XSS 窃取 SessionID
Secure=true
只在 HTTPS 下传输，防中间人劫持
SameSite=Strict/Lax
防御 CSRF 跨站请求伪造
Session 超时
Redis 过期 + 滑动过期（操作一次刷新过期时间）
SessionID 必须随机
使用强随机 UUID，不可被猜测

一、先说结论（面试直接背）
Web Cache（Web 缓存）= 专门用来缓存 HTTP 内容、减轻源站压力的中间服务器它本质就是：把后端返回的内容存一份，下次直接返回，不再请求源站。
你记住一句话：
凡是 “提前存好内容，直接返回” 的 HTTP 中间层，都叫 Web Cache。
二、Web Cache 通常指什么？（标准定义）
企业 / 教材 / 面试里说的 Web Cache / Proxy Cache 一般指三类：
反向代理缓存（最典型）Nginx、Squid、Varnish、HAProxy 这类→ 放在用户和源站之间→ 缓存页面、接口、静态资源→ 属于服务端缓存
CDN（本质就是分布式 Web Cache）全国 / 全球节点缓存静态资源→ 本质就是超级大规模的反向代理缓存集群
正向代理缓存（公司内网网关、浏览器代理）比如公司统一上网代理，缓存大家共同访问的资源→ 企业内部用得多，面试一般不问
三、你最关心的：
Nginx 缓存 = 反向代理 + 缓存，不是二选一！
你说：
“nginx 可以缓存静态资源，然后就直接返回了，不需要反向代理了”
这句话不对，我给你纠正（面试很重要）：
Nginx 做的是：
反向代理 + 缓存同时存在
它首先是反向代理
接收用户请求 → 转发给后端（Tomcat/Java/Node）
然后开启 proxy_cache
把后端返回的内容缓存下来
下次请求来时：
有缓存 → 直接返回（不转发）
没缓存 → 转发后端，并缓存
所以：Nginx 缓存 = 带缓存功能的反向代理不是 “有缓存就不用反向代理”。
四、CDN 算不算 Web Cache？
算！而且是最典型、规模最大的 Web Cache。
CDN = 一堆分布在各地的 反向代理缓存服务器。
流程一模一样：
用户请求资源
CDN 节点看有没有缓存
有 → 直接返回
没有 → 回源站拉取，再缓存
所以面试可以直接说：
CDN 本质就是分布式、多节点的 Web Cache。
五、企业里 Web Cache 分层（面试加分）
企业真实架构是多层缓存：
浏览器缓存（客户端）
CDN 缓存（边缘）
Nginx/Varnish 反向代理缓存（接入层）
应用缓存（Redis、本地缓存）
数据库缓存
你看：CDN、Nginx Proxy Cache 都是标准 Web Cache只是位置不同。
六、面试标准回答（你直接背）
Web Cache 就是位于用户与源站之间，用于缓存 HTTP 响应内容的代理服务器，目的是减少源站压力、降低延迟、提高访问速度。
主要包括两类：
反向代理缓存如 Nginx proxy_cache、Varnish、Squid，部署在源站前面，缓存页面、接口、静态资源。它本身是反向代理，只是开启了缓存功能。
CDN本质是分布式、多节点的反向代理缓存，专门缓存静态资源（图片、JS、CSS、下载包）。
所以：
Nginx 缓存 = 反向代理 + Web Cache
CDN = 分布式 Web Cache
两者都属于 Web Cache。













Redisson 分布式锁实现
核心答案：Redisson 分布式锁基于 Redis 实现，核心解决原子性、死锁、误删、集群安全问题：
基础加锁：用SET key unique_value NX EX 30（NX 仅不存在时设置，EX 自动过期防死锁）；
防误删：删除锁前用 Lua 脚本判断 value 是否为当前线程标识，保证只删自己的锁；
可重入性：用 Hash 结构存储锁的重入次数（线程 ID 为 key，次数为 value）；
自动续期（看门狗）：业务执行超锁过期时间时，Redisson 后台定时续期，避免锁过期；
集群高可用：基于 RedLock 算法，仅多数节点成功加锁才生效，解决单节点单点问题




指数退避的实现
核心答案：指数退避是重试间隔按指数级增长的重试策略（1s→2s→4s→8s…），核心目的是缓解下游压力，防止雪崩。实现流程：
定义初始延迟、最大延迟、重试倍数（如初始 1s，倍数 2，最大 30s）；
重试时，等待时间 = 初始延迟 ×2^(重试次数 - 1)，且不超过最大延迟；
超过最大重试次数则放弃并告警。
代码核心：循环重试 + 动态计算等待时间 + 终止条件。
面试金句：指数退避是 “下游过载保护” 的重试策略；间隔指数增长，避免频繁重试压垮下游。



幂等性保障
核心答案：幂等性是同一请求多次执行，结果与一次执行完全一致，无副作用。实现方案分 4 类：
数据库唯一约束：用订单号、请求 ID 建唯一索引，重复插入触发冲突拒绝；
Redis 防重：生成唯一请求 ID（如用户 + 接口 + 参数），Redis 存 ID 并设过期，存在则拒绝；
Token 机制：前端获取一次性 Token，请求携带 Token，后端验证后删除 Token；
状态机：通过业务状态（如订单待支付→已支付）限制重复操作。














Ring buffer（环形缓冲区）相关内容
核心原理：
用固定大小的数组模拟环形结构，通过 ** 读指针（read index）和写指针（write index）** 标记数据位置。
指针到达数组末尾时自动回到开头，实现循环复用。
关键特性：
无锁实现：在单写单读场景下可实现无锁并发，避免线程切换开销。
边界处理：通过(write+1)%size == read判断满，read == write判断空。
应用场景：高性能 IO（如 Netty、Redis）、消息队列、日志缓冲等，适合生产 - 消费模型。
优势：相比普通队列，避免了内存碎片，读写效率更高。

反向代理原理、常用工具及正向代理
反向代理：
原理：代理服务器接收客户端请求，转发到后端真实服务器，并将响应返回给客户端，客户端感知不到真实服务器。
作用：隐藏后端服务器、负载均衡、SSL 卸载、静态资源缓存、安全防护。
常用工具：Nginx、HAProxy、Apache、Traefik。
正向代理：
原理：客户端通过代理服务器访问外部服务，服务端感知不到真实客户端。
作用：突破网络限制、匿名访问、缓存加速。
常用工具：Shadowsocks、Squid、Charles。

 MySQL 主从复制实现原理（基于 binlog、redolog）
核心流程：
主库写入：主库执行事务时，将变更写入redolog（保证事务持久性），同时生成binlog（记录数据变更逻辑）。
从库连接：从库的 IO 线程连接主库，请求 binlog 增量。
binlog 同步：主库的 dump 线程将 binlog 发送给从库，从库 IO 线程写入本地relay log。
重放执行：从库的 SQL 线程读取relay log，重放事务，保证与主库数据一致。
关键日志作用：
redolog：保证主库事务 ACID，是 InnoDB 引擎的物理日志。
binlog：是 MySQL Server 层的逻辑日志，用于主从复制和数据恢复。

小哈希（ziplist 编码）：

面试官：怎么理解String的不可变性？底层为什么能保证？不可变性的好处是什么？

一、什么是 String 的不可变性？
一旦 String 对象被创建，它的字符内容、长度就永远无法修改。所有看似修改字符串的方法（substring/replace/toUpperCase 等），都不会改变原对象，而是返回一个全新的 String 对象。
二、底层如何保证不可变性？（4 个核心点，按优先级说）
String 类被 final 修饰
禁止被继承，杜绝子类重写方法破坏不可变性；
底层存储数组被 private final 修饰
Java8 用 char[]，Java9+ 优化为 byte[] + coder（节省内存）：
final：保证数组引用不能改变（无法指向新数组）；
private：保证外部无法直接访问、修改数组内容（这是最关键的一点！你刚才漏了）；
无任何对外修改的方法
没有 set()/update() 这类修改内部字符的 API，从源头禁止修改；
所有修改操作都返回新对象
不操作原对象，彻底保证不可变。
三、不可变性的好处？（5 个高频得分点）
天然线程安全

支持字符串常量池复用

适合作为集合的 Key
HashMap/HashSet 依赖哈希值，String 会缓存 hashCode，不可变保证哈希值永远不变；
安全性极高
避免字符串被恶意篡改（比如文件路径、网络地址、密码等核心参数）；
简化开发
无需做防御性拷贝，使用、传参都更安全可靠。
对你原始回答的点评
✅ 说对的部分：
final 修饰 String 类，防止篡改；
底层数组 final 修饰，无修改方法；

文件上传中断了可以调用查询接口获取上传过的分块信息，进行断点续传，用bitmap可以记录第几个分块收到了，哪些没收到，当然完全可以使用redis哈希表记录收到的分块，bitmap可能占用空间特别少，上传不丢失的话，就是如果正常上传成功会返回一个类似于ack的成功响应，失败的话返回失败触发重传，不重复的话就是上传要分块之后检验哈希表中是否存在当前分快，kafaka没了解过，然后redis集群分区是什么鬼




1. 文件上传中断 & 断点续传
核心思路：将大文件拆分为多个分块（Chunk），上传时记录已成功上传的分块，中断后从断点继续。
实现步骤：
前端计算文件 MD5，作为唯一标识。
调用后端接口，查询该 MD5 已上传的分块列表。
仅上传未完成的分块，每个分块携带索引。
后端用Bitmap或 Redis 哈希表记录已接收分块，空间效率极高。
所有分块上传完成后，后端合并文件并校验 MD5。


2. 为什么用 Bitmap 而不是其他结构
空间优势：Bitmap 用 1bit 表示一个分块是否上传，1MB 可记录 8,388,608 个分块，远小于哈希表 / 数组。
高效计算：位运算（SETBIT/GETBIT/BITCOUNT）极快，适合判断分块是否存在、统计已上传数量。
对比其他结构：
哈希表：每个分块存一个 key-value，内存开销大。
数组：稀疏场景下浪费空间，且索引范围受限。
布隆过滤器：存在误判，不适合精确记录。



3. 保证上传不丢失 & 不重复
不丢失：
分块上传后，后端返回 ACK 响应。
前端未收到 ACK 则触发超时重传，直到成功。
后端持久化分块到磁盘 / 对象存储，避免内存丢失。
不重复：
分块上传前，先查询 Bitmap / 哈希表是否已存在该分块索引。
已存在则直接返回成功，不再写入存储。
用文件 MD5 + 分块索引作为幂等键，保证重复上传无副作用。



4. Kafka 相关（入门版回答）
为什么用 Kafka：
解耦系统：上传服务与文件合并 / 日志服务异步通信。
削峰填谷：应对突发大流量上传，避免下游服务过载。
持久化：消息落盘，保证数据不丢失，支持重试。
分区设置：
分区数 ≈ 下游消费者线程数（最大化并行消费）。
按文件 MD5 哈希取模分区，保证同一文件的分块消息进入同一分区。
副本数设为 2-3，提高可用性。
保证顺序性：
同一文件的分块发送到同一分区，Kafka 保证单分区内消息有序。
消费者按分区顺序消费，避免乱序。



5. Redis 集群分区
核心机制：Redis Cluster 采用 ** 哈希槽（Hash Slot）** 分区，共 16384 个槽。
分区规则：
对 key 计算 CRC16，取模 16384 得到槽位。
每个节点负责一部分槽位，数据自动分布到不同节点。
为什么这么设计：
水平扩展：新增 / 移除节点时，仅迁移部分槽位，不影响整体服务。
高可用：主从复制，主节点故障时从节点自动提升为主。


6. ZSet & 跳表 vs B + 树
ZSet 是什么：有序集合，每个元素带 score，按 score 排序，支持范围查询、排名。
底层结构：跳表（SkipList）+ 哈希表。
跳表 vs B + 树：
跳表优势：
实现简单，无复杂平衡操作。
高并发场景下，锁粒度更细，插入 / 删除性能更优。
内存布局更友好，缓存命中率高。
B + 树优势：
磁盘 IO 友好，适合数据库等存储引擎。
范围查询效率极高，适合顺序访问。
为什么 Redis 用跳表：
Redis 数据在内存中，无需考虑磁盘 IO。
跳表在内存中的随机读写性能优于 B + 树，且实现更简洁。



7. MySQL 调优 & 深分页
实际调优场景：

慢 SQL 优化：将SELECT * FROM table WHERE status = 1 ORDER BY create_time LIMIT 1000000, 10改为SELECT * FROM table WHERE id > (SELECT id FROM table WHERE status = 1 ORDER BY create_time LIMIT 1000000, 1) LIMIT 10，避免全表扫描。

加索引：为status和create_time建立联合索引，覆盖查询条件。


深分页处理：
游标分页：用上一页最后一条数据的 ID / 时间作为游标，WHERE id > last_id LIMIT 10，避免OFFSET跳过大量数据。
禁止跳页：只允许上一页 / 下一页，不支持直接跳转到第 N 页。
业务优化：限制最大分页页数，或用 ES 做全文检索，避免深分页。



8. ES & MySQL 数据不一致
常见原因：
异步同步延迟：MySQL 数据变更后，通过 binlog / 消息队列同步到 ES，存在时间差。
同步失败：网络抖动、ES 集群故障导致部分数据未同步。
双写问题：直接写入 MySQL 和 ES，若一方失败则不一致。
解决方案：
最终一致性：用 Kafka/Canal 监听 binlog，保证最终一致。
对账补偿：定时任务对比 MySQL 和 ES 数据，修复差异。
事务消息：用可靠消息队列，保证变更消息必达 ES。
读写分离：读请求优先走 ES，写请求走 MySQL，异步同步。





















新增删除节点的话，槽要迁移，节点中的数据也要是吗
是的，在 Redis Cluster 中，新增 / 删除节点时，哈希槽（slot）和对应的数据都需要迁移，这是 Redis 集群扩缩容的核心流程。
1. 槽迁移与数据迁移的关系
Redis Cluster 的数据是按 哈希槽（16384 个） 分布的，每个槽对应一段 key 空间，且只属于一个主节点。
当你新增节点：需要从其他主节点迁出部分槽，并将这些槽里的所有数据一起迁移到新节点。
当你删除节点：需要将该节点负责的所有槽迁移到其他主节点，同时把对应数据也迁走，之后才能下线该节点。
所以：槽迁移 = 数据迁移，槽只是数据的 “归属标签”，槽的归属变化必然伴随实际数据的搬迁。
2. 迁移的具体流程（以新增节点为例）
准备新节点：启动新的 Redis 实例，加入集群，初始状态为 “无槽”。
分配槽：通过 redis-cli --cluster reshard 命令，指定从哪些源节点迁出多少个槽到目标节点。
数据迁移：
集群会逐个将源节点的槽迁移到目标节点。
对每个槽：先从源节点遍历所有 key，批量迁移到目标节点；迁移完成后，更新集群元数据，将槽的归属改为目标节点。
迁移过程中，Redis 会处理客户端请求：对正在迁移的 key，源节点会尝试重定向或临时持有，保证业务不中断（这就是 迁移时的请求重定向 / ASK 重定向）。
完成迁移：所有槽迁移完毕后，新节点正式接管这些槽，开始对外提供服务。
3. 关键特性与注意事项
在线迁移：Redis Cluster 支持在线迁移槽和数据，不需要停止服务，业务侧只会短暂感知到少量 ASK/MOVED 重定向。
主从同步：迁移完成后，目标节点的从节点会自动从主节点同步新迁入的数据，保证高可用。
数据一致性：迁移过程中，Redis 会通过 key 锁定 和 重定向机制 保证数据不丢失、不重复。
性能影响：迁移会占用源节点和目标节点的 CPU/IO，大流量下建议低峰期操作，或分批迁移少量槽。
4. 面试话术版精简回答
Redis Cluster 扩缩容时，槽和数据是一起迁移的。因为每个槽绑定了一段 key 空间，槽的归属变化必须把对应数据也搬到新节点，否则数据就找不到了。迁移是在线进行的，通过遍历槽内 key 批量搬迁，同时用 ASK/MOVED 重定向保证业务不中断，迁移完成后更新集群元数据，新节点就接管了这些槽和数据。
