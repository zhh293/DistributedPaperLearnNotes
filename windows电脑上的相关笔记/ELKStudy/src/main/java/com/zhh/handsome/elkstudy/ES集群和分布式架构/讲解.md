Elasticsearch 集群里的节点（Server 01/02/03）本身也有明确的角色划分，这些角色决定了节点在集群中的核心职责：
1. Data 节点（数据节点）
   图中的 Server 01/02/03 都属于这类节点，因为它们实际存储了分片（shard 01/02/03 的 primary 或 replica 副本）。
   核心职责：负责数据的存储、索引、搜索、聚合等读写操作，是集群中承载业务数据的核心节点。
2. Coordinating 节点（协调节点）
   图中 Client 直接连接的节点（比如 Server 01）就承担了这个角色。
   核心职责：接收客户端的请求（如写、读、搜索），将请求路由到对应的分片所在节点（写请求找 primary shard，读请求找 replica/primary），然后收集各节点的响应结果，汇总后返回给客户端。
   每个节点默认都是协调节点，无需额外配置。
3. Master 节点（主节点，含候选主节点）
   图中未直接标出，但 Elasticsearch 集群必须有主节点来管理集群元数据。
   核心职责：负责集群的全局管理，包括节点加入 / 离开、分片分配、集群状态维护（如元数据更新）等，不处理具体的数据读写。
   集群会从 “候选主节点（master-eligible）” 中选举出一个主节点，其余候选节点作为备用，保证集群高可用。




协调节点是怎么知道这个请求应该找索引的哪个分片的，计算了什么东西吗
没错，协调节点确实是通过一套确定性的哈希路由算法来精准定位请求该发往哪个分片的，整个过程是完全可预测的。我给你拆解一下背后的计算逻辑和流程：
🔍 核心计算逻辑：哈希取模
Elasticsearch 会用固定公式计算目标分片，核心公式是：
plaintext
shard_index = hash(routing_key) % number_of_primary_shards
routing_key（路由键）：默认是文档的 _id，你也可以在写入 / 查询时通过 routing 参数自定义路由键。
hash()：默认使用 MurmurHash3 哈希函数，它能生成均匀分布的哈希值，避免数据倾斜。
number_of_primary_shards：索引创建时指定的主分片数量（这个值一旦设定就不能修改，否则哈希取模的结果会失效，导致数据无法找到）。
举个例子（结合你图里的场景）：假设你的 Index A 有 3 个主分片（对应图里的 Shard 01/02/03），当客户端写入一个文档 _id = "user_123" 时：
用 MurmurHash3 对 "user_123" 哈希，得到一个整数（比如 123456）。
用哈希值对主分片数 3 取模：123456 % 3 = 0。
计算结果 0 对应目标分片是 Shard 01（分片索引从 0 开始）。
📍 协调节点的定位流程
接收请求 & 提取路由键协调节点拿到客户端的请求后，先提取出路由键（默认用文档 _id，如果是自定义路由则用指定的 routing 值）。
计算目标分片用上面的哈希取模公式，算出请求要发往的分片索引（比如 0 → Shard 01，1 → Shard 02，2 → Shard 03）。
查询集群元数据协调节点会缓存集群的元数据（由主节点维护），里面记录了每个分片（主 / 副）所在的节点位置。比如你的图里：
Shard 01 的 Primary 在 Server 01，Replica 在 Server 02/03。
Shard 02 的 Primary 在 Server 02，Replica 在 Server 01/03。
Shard 03 的 Primary 在 Server 03，Replica 在 Server 01/02。
转发请求
写请求：必须转发到目标分片的 Primary 副本（比如 Shard 01 的 Primary 在 Server 01，就把请求发往 Server 01）。
读请求：可以转发到目标分片的 Primary 或任意 Replica 副本（ES 会做负载均衡）。
⚠️ 关键注意事项
主分片数不可修改：因为 number_of_primary_shards 是哈希取模的分母，一旦修改，所有现有数据的分片路由结果都会失效，导致数据无法被找到。
自定义路由的风险：如果用自定义 routing 让相关文档落到同一个分片，虽然能提升查询效率，但可能导致数据倾斜（某个分片存储过多数据）。
元数据一致性：主节点负责维护集群元数据，协调节点会定期同步最新的元数据，确保能准确找到分片位置。

你对这张图的核心逻辑理解得大部分是对的，但有几个关键细节需要修正，这样能更精准地理解 ES 分片的读写规则和集群架构：
先肯定你的核心认知（没错的部分）
索引的分片数由 settings 中的 number_of_shards 决定（图中 Index A 是 3 个主分片），副本数由 number_of_replicas 决定（图中每个主分片有 2 个副本）；
同一个节点内不会出现同一个分片的主副副本（比如 Shard 01 的 Primary 在 Server 01，Replica 就只会分布在 Server 02/03），保证单点故障不影响分片可用性；
每个分片（shard）必有且仅有一个 Primary，其余是 Replica，Primary 是写入的核心入口。
需要修正的关键细节（避免理解偏差）
1. “primary 只负责写，replica 负责读” → 表述不准确
   Primary 的职责：
   ✅ 必须处理所有写请求（新增 / 修改 / 删除文档），这是核心规则（图中 Client 的 write doc 请求先到 Shard 01 的 Primary）；
   ✅ 也可以处理读请求（不是只能写），只是 ES 会优先把读请求分发到 Replica，分摊 Primary 的压力。
   Replica 的职责：
   ✅ 只能同步 Primary 的数据（图中 Primary 到 Replica 的 sync 箭头），不能直接处理写请求（写请求必须先到 Primary，再由 Primary 同步给 Replica）；
   ✅ 专门承接读请求（查询 / 聚合），但不是 “只能读”——Replica 的核心价值还有故障容灾：如果 Primary 挂了，集群会从 Replica 中选举一个升级为新的 Primary。
2. “同一个节点中的 shard 各不相同” → 补充完整
   同一个节点内的 shard 是 “同一个索引的不同分片”（比如 Server 01 里有 Shard 01 Primary、Shard 02 Replica、Shard 03 Replica），本质是 “同一个索引的不同分片实例”，而非 “完全无关的 shard”；
ES 会刻意避免把同一个分片的主副副本放在同一个节点（比如 Shard 01 的 Primary 和 Replica 绝不会在 Server 01 共存）。

7. 协调节点的路由逻辑（图中隐含但你没提的关键）
   Client 的写请求不是直接到 Primary，而是先到协调节点（图中未标注，但 ES 集群必有）：
   协调节点通过「哈希路由算法」计算出文档该归属哪个分片（比如 Shard 01）；
   查集群元数据找到该分片的 Primary 所在节点（Server 01）；
   把写请求转发到 Primary，Primary 写入成功后同步给所有 Replica；
   所有 Replica 同步完成后，Primary 才向 Client 返回 “ok”（图中 Client 收到的 ok）。
   总结（核心关键点回顾）
   分片规则：主分片数固定，副本数可动态调整，同分片的主副副本必分布在不同节点；
   读写规则：Primary 承接所有写请求 + 可承接读请求，Replica 仅承接读请求 + 作为 Primary 的容灾备份；
   路由规则：写请求必须路由到目标分片的 Primary，读请求可路由到 Primary 或任意 Replica（ES 负载均衡）。
