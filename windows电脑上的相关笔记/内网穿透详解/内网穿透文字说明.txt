对于十年前的网络环境来说，几乎每一个路由器都有属于他的公网ip，此时我们只需要手动配置路由器的NAT端口映射，就可以在外网直接访问路由器，然后把流量导入到配置的那台内网设备上面去了，但是随着时代的快速发展，ipv4的公网ip显然完全不够用了，于是路由器失去了它原有的公网ip，转而统一交给了运营商进行转发。虽然说现在有ipv6的存在，大家也完全可以通过ipv6实现同样的效果，但是由于现在仍然存在着许多只支持ipv4而不支持ipv6的设备，所以说学习如何使用ipv4实现内网穿透仍然是必不可少的，下面我仅讲解一种大家最常用的内网穿透的方式，还有一种我将以一个视频给大家讲解




这个方式就是FRP内网穿透，当然花生壳也可以实现同样的效果，两者的原理是大差不差的







FRP 内网穿透原理及完整工作流程
FRP（Fast Reverse Proxy）是一款高性能的反向代理工具，核心作用是解决内网设备无法被公网直接访问的问题。其本质是借助一台拥有公网 IP 的服务器，搭建内网设备与公网请求之间的通信桥梁。
之所以公网服务器能和内网私有设备建立连接，核心原因是：内网设备主动发起并维持与公网服务器的长连接，而 NAT 设备（路由器）会放行主动连接的流量；公网请求则通过这根 “长连接管道”，被转发到内网设备上。
一、核心角色与基础前提
在 FRP 内网穿透架构中，存在 3 个核心角色：
服务端（frps）
部署在拥有公网 IP 的服务器上（如阿里云、腾讯云服务器）。
开放指定端口（默认 7000 端口用于与客户端通信，还有各类业务端口用于接收公网请求）。
核心功能：接收内网客户端的长连接、转发公网请求到内网客户端、管理代理规则。
客户端（frpc）
部署在需要被公网访问的内网设备上（如家里的 NAS、公司内网的 Web 服务器）。
核心功能：主动连接公网服务端并维持长连接、接收服务端转发的公网请求、将请求转发到内网目标服务。
公网用户（访问方）
想要访问内网设备的终端（如手机、电脑），处于公网环境。
基础前提：
公网服务器有固定公网 IP，且防火墙 / 安全组放行 frps 的端口（7000 及业务端口）。
内网设备能正常访问公网（可以连接到 frps 的 IP 和端口）。
二、FRP 完整工作流程（以 HTTP 服务代理为例）
我们以 “公网用户访问内网的 HTTP 服务（如内网 Web 站点，端口 80）” 为例，拆解每一步的通信过程。
步骤 1：服务端（frps）启动，监听端口
在公网服务器上启动 frps，并加载配置文件。
配置文件中会指定：
bind_port = 7000：监听 7000 端口，用于接收内网客户端的连接。
vhost_http_port = 8080：监听 8080 端口，用于接收公网用户的 HTTP 请求（反向代理端口）。
frps 启动后，会在公网服务器上开启 7000 端口的 TCP 监听 和 8080 端口的 HTTP 监听，等待客户端连接和公网请求。
步骤 2：内网客户端（frpc）启动，主动建立长连接
这是内网穿透的核心关键步骤，解决了 “公网无法主动连接内网设备” 的问题。
在内网设备上启动 frpc，并加载配置文件。
配置文件中会指定：
服务端地址：server_addr = 公网服务器IP
服务端端口：server_port = 7000
代理规则：[web]（代理名称）、type = http（代理类型）、local_port = 80（内网 Web 服务的端口）、custom_domains = test.example.com（公网访问的域名，需解析到公网服务器 IP）。
frpc 启动后，会主动向 frps 的 7000 端口发起 TCP 连接。
内网设备的 NAT 路由器会为这个连接分配一个临时的公网端口映射（记录：内网 IP: 内网端口 → 公网 IP: 临时端口），并允许 frps 的响应流量通过。
frps 接收到 frpc 的连接请求后，会与 frpc 建立并维持一个长连接（这个连接会一直保持，除非网络中断或主动断开）。
同时，frps 会根据 frpc 发送的代理规则（如 [web] 代理），记录映射关系：公网 8080 端口 + 域名 test.example.com → 该 frpc 长连接 → 内网 80 端口。
步骤 3：公网用户发起访问请求
公网用户想要访问内网 Web 服务，需要在浏览器中输入地址：http://test.example.com:8080（域名解析到公网服务器 IP）。
浏览器会向 test.example.com:8080 发送 HTTP 请求，这个请求会被路由到公网服务器的 8080 端口。
frps 正在监听 8080 端口，因此会接收这个 HTTP 请求。
步骤 4：服务端转发请求到内网客户端
frps 接收到公网用户的 HTTP 请求后，会进行以下处理：
解析请求的域名和端口：判断请求的是 test.example.com，端口是 8080。
匹配代理规则：根据步骤 2 中记录的映射关系，找到对应的 frpc 长连接（即与内网 Web 服务绑定的那个长连接）。
转发请求数据：frps 将公网用户的 HTTP 请求数据，通过已建立的长连接，发送给内网的 frpc。
步骤 5：客户端转发请求到内网目标服务
内网的 frpc 接收到 frps 转发的请求数据后：
根据代理配置中的 local_port = 80，将请求转发到本地的 80 端口（即内网 Web 服务）。
内网 Web 服务处理请求，生成 HTTP 响应（如返回网页内容），并将响应数据发送给 frpc。
步骤 6：响应数据原路返回给公网用户
响应的路径与请求路径完全相反：
frpc 接收到内网 Web 服务的响应数据后，通过长连接发送给 frps。
frps 接收到响应数据后，将其转发到公网用户的浏览器（即 8080 端口对应的请求连接）。
公网用户的浏览器接收到响应数据，渲染网页，完成一次完整的访问。
三、关键技术点：为什么 NAT 设备不会拦截流量？
内网设备处于 NAT 网络下，路由器会阻止公网主动发起的连接，但 FRP 巧妙规避了这个限制，核心依赖两个技术点：
主动长连接穿透 NAT
NAT 设备的规则是：放行内网主动发起的连接的双向流量。
frpc 主动连接 frps，NAT 路由器会记录这个连接的会话，并允许 frps 向 frpc 发送的流量通过（即步骤 4 的请求转发流量）。
frp 会通过心跳机制维持这个长连接（定期发送心跳包，防止连接被 NAT 设备或防火墙断开）。
反向代理转发
公网用户的请求不是直接访问内网设备，而是访问公网服务器的端口，由 frps 作为中间节点转发。
整个过程中，内网设备始终是 “被动接收 frps 转发的请求”，而非直接接收公网请求。
四、其他代理类型的流程差异
除了 HTTP 代理，FRP 还支持 TCP、UDP、HTTPS、SSH 等代理类型，核心流程与 HTTP 一致，差异仅在于：
TCP 代理：frps 监听一个 TCP 端口，直接转发 TCP 流量（如 SSH 代理：frps 监听 6000 端口，公网用户通过 ssh -p 6000 公网IP 访问内网 SSH 服务）。
UDP 代理：基于 UDP 协议建立连接，转发 UDP 数据包（如内网游戏服务器）。
HTTPS 代理：类似 HTTP 代理，但使用 TLS 加密，frps 监听 HTTPS 端口。
五、总结
FRP 内网穿透的本质是 “内网主动建联，公网反向转发”：
内网客户端主动和公网服务端建立长连接，打通通信管道。
公网请求先到服务端，再通过管道转发到内网。
响应数据沿原路返回，完成整个通信闭环。
这种方式不依赖内网路由器的端口映射配置，能穿透绝大多数 NAT 环境（如家庭宽带、公司内网），是解决内网服务公网访问的主流方案。

Cloudflare Tunnel 和 FRP 在内网穿透的核心逻辑上高度一致，都是 **「客户端主动出站连服务端 + 中心化转发」** 的方案，和传统 P2P NAT 打洞是完全不同的路子，这也是为啥你会觉得 “一个道理”——两者的底层设计思想同源，只是工程实现、服务形态、配套能力天差地别。
简单说：FRP 是「轻量开源的中心化穿透工具」，Cloudflare Tunnel 是「基于全球云边缘集群的商业化穿透服务」，核心逻辑一样，但前者需要你自己搭 “服务端”，后者把 “服务端” 做成了全球可用的云服务，还叠满了 Cloudflare 的安全、加速 buff。
下面用 **「核心共性 + 关键差异」** 讲透，贴合你能实际部署使用的视角，不搞虚的：
一、核心共性：两者完全一致的设计逻辑
这是你觉得 “一个道理” 的根本原因，3 个核心点完全重合，和 P2P 打洞形成鲜明对比：
1. 都是「客户端主动出站」，无需端口转发
FRP：内网装frpc（客户端），主动连接你自己部署在公网 VPS 上的frps（服务端）；
Cloudflare Tunnel：内网装cloudflared（客户端），主动连接 Cloudflare 的全球边缘节点（相当于 Cloudflare 帮你搭好了超大规模的 “frps 集群”）；
两者都利用路由器放行出站连接的默认规则，全程不用在路由器做任何端口映射，内网防火墙完全不用动。
2. 都是「中心化转发」，依赖服务端做中转站
FRP：外网访问你的内网服务，需先到你 VPS 上的 frps，再通过 frpc 和 frps 之间的长连接，转发到内网服务；
Cloudflare Tunnel：外网访问需先到 Cloudflare 边缘节点，再通过 cloudflared 和边缘节点的长连接，转发到内网服务；
两者都没有 “端到端” 通信，所有流量都要经过中间的服务端 / 边缘节点转发，和 P2P 打洞 “触发映射表后直连” 完全不同。
3. 都是「基于长连接 + 转发规则」实现流量路由
两者的客户端和服务端建立连接后，都会维持持久化长连接（避免被路由器断开）；
都支持自定义转发规则：比如 FRP 通过配置文件指定 “外网域名 / 端口→内网 IP: 端口”，Cloudflare Tunnel 通过config.yml指定 “hostname→内网服务地址”，本质都是 “流量路由映射”。
简单总结：FRP 的「frpc→frps」和 Cloudflare Tunnel 的「cloudflared→Cloudflare 边缘节点」，在网络层面是完全等价的，只是换了个名字、换了服务端的部署方。
二、关键差异：天差地别的工程实现和服务能力
这是两者最核心的区别，也是 Cloudflare Tunnel 能做到 “开箱即用、全球可用” 的原因，本质是 **「自己搭服务端」和「用云服务商的现成集群」** 的差异，分 6 个维度讲透，都是你实际用能感受到的点：
对比维度	FRP（开源穿透工具）	Cloudflare Tunnel（云穿透服务）
服务端部署	需自己准备公网 VPS，手动安装配置 frps，还要维护 VPS（开机、带宽、防御）	无需部署服务端，直接用 Cloudflare 全球 300 + 边缘节点集群，Cloudflare 全程维护，零运维
网络覆盖	服务端只有你 VPS 的 1 个 / 几个公网节点，外网用户访问的延迟取决于 VPS 位置	全球边缘节点，外网用户自动接入最近的节点，延迟极低，全球访问体验一致
传输加密	默认裸传（流量明文），需手动配置 TLS / 加密插件，步骤繁琐	TLS 1.3 全程加密，从边缘节点到 cloudflared 客户端，流量全程密文，开箱即用，无需额外配置

三、通俗比喻：用 “快递站” 理解两者的差异
还是用之前的 “家里（内网）- 快递站（服务端）” 比喻，瞬间懂：
FRP：你自己在小区门口租了一个小快递站（VPS），自己买货架、装监控、雇人维护（自己运维 frps）。家里（内网）主动把东西送到这个快递站，朋友取东西只能来这个快递站拿，快递站被偷 / 被砸了（VPS 被攻击 / 宕机），就用不了了，而且东西在运输中是裸装的（未加密），需自己包保鲜膜（手动配加密）。
Cloudflare Tunnel：全国有 300 + 个顺丰直营快递站（边缘节点），顺丰全程维护（Cloudflare 运维），家里（内网）主动把东西送到最近的顺丰站，朋友取东西能去全国任何一个顺丰站（自动就近接入），东西全程顺丰保价加密运输（TLS 1.3），还能帮你拦截可疑包裹（WAF/DDoS），不用自己管任何杂事。
四、总结：什么时候用 FRP，什么时候用 Cloudflare Tunnel？
两者核心逻辑一样，但适用场景完全不同，结合你的使用场景选就行：
用 FRP 的情况
需穿透UDP 协议（比如游戏服务器、内网测速、IoT 设备的 UDP 通信）；
对协议灵活性要求高（想透什么端口 / 协议就透什么，无限制）；
有现成的公网 VPS，且愿意花时间运维，追求低成本（几元 / 月）；
内网服务仅在小范围使用（比如只有自己 / 朋友用，无需全球低延迟）。
用 Cloudflare Tunnel 的情况
主要穿透Web 服务（博客、NAS 管理界面、开发测试环境），追求开箱即用、零运维；
希望外网用户全球低延迟访问，且需要HTTPS 自动配置（不用自己搞证书）；
重视安全，需要 WAF、DDoS 防护，避免内网服务被攻击；
没有公网 VPS，也不想花时间运维服务端，个人 / 小场景用免费版就够。
最后再划重点
两者都是「客户端主动连服务端的中心化穿透」，只是 FRP 是 “裸框架”，需要你自己填服务端、填加密、填防护；而 Cloudflare Tunnel 是把这个 “框架” 做成了成品服务，还叠满了云厂商的全球节点、安全、加速 buff。
简单说：FRP 是 “自己买菜做饭”，Cloudflare Tunnel 是 “点外卖（还送餐具和配菜）”，做饭的核心逻辑（把食材弄熟）一样，但前者自由灵活，后者省心省力～

openfrp + lucky + NAS + 域名 + HTTPS + Zotero/WebDAV

纯中继型内网穿透（TCP 长连接隧道）全程没有任何 P2P、没有任何 UDP 打洞行为。



0. 前提条件
你家 NAS：在内网，没有公网 IP 或不想暴露
你有一台 openfrp 服务器：有公网 IP
你有一个域名：比如 test.com


1. 内网 NAS → 主动连接 openfrp 服务器（建立隧道）
动作：
NAS 上运行 openfrp 客户端，主动发起 TCP 连接→ 连到 openfrp 公网服务器的某个端口
网络层面：
这是内网主动出站
家庭路由器 NAT 允许 “内部→外部” 的连接
路由器会建立一条：
内网 IP: 随机端口 ↔ 公网服务器 IP: 端口
的映射记录
这一步是什么？
这是「建立中继隧道」，不是打洞。



2. 心跳保活，让隧道不断
动作：
NAS 客户端 ↔ openfrp 服务器定时发心跳包，维持这条 TCP 连接不断。
目的：
防止家庭路由器 NAT 会话超时，把端口映射回收。
这一步是什么？
隧道保活，还是中继。

网络本质：
外网 <-> 服务器
服务器 <-> 家中 NAS
两段连接，服务器在中间转发。
这一步是什么？
这就是「中继」的定义：服务器转发所有流量。

NAS 完全隐藏在内网里，不直接暴露公网。

整个链路：外网设备 → openfrp 服务器 → 家中 NAS → lucky → WebDAV → Zotero
全程流量都经过服务器转发。

第五步：lucky 接手：解密、认域名、转发
这是 lucky 的核心工作，我拆成 3 小步：

一、WireGuard 到底是干嘛的？（大白话版）
1. 一句话定义
WireGuard = 现代版、轻量级、超高速的 VPN 隧道协议你可以把它理解成：在公网上给你挖一条只有你能走的加密地下通道
2. 它在我们这个项目里具体做三件事
① 加密传输
所有在公网上跑的流量（校外用户→云服务器→校内服务器）全部被加密
学校网管、运营商、黑客都看不到你传了什么内容
只能看到 "有流量在两个 IP 之间传输"，不知道里面是什么
② 建立点对点隧道
它会在两端设备上创建一个虚拟网卡（叫wg0）
云服务器有一个虚拟 IP：10.0.0.1
校内服务器有一个虚拟 IP：10.0.0.2
每个校外用户有一个唯一虚拟 IP：10.0.0.3、10.0.0.4...
所有走 VPN 的流量，都是通过这些虚拟 IP 在隧道里传输的
③ 路由转发
它会自动帮你把流量从一个隧道端点转发到另一个端点
校外用户发往202.118.0.0/16（校园网段）的流量 → 自动通过隧道发到云服务器
云服务器收到后 → 自动通过另一条隧道发到校内落地服务器
校内落地服务器收到后 → 转发到真实的校园网
3. 为什么不用 OpenVPN/SoftEther？
速度快：比 OpenVPN 快 3-10 倍，因为它跑在 Linux 内核里

二、修改源 IP（SNAT）到底在哪里？（重点中的重点）
我之前写了，但可能写得太隐蔽了，现在单独拉出来给你讲透，这就是整个 VPN 最核心的魔法
1. 它在哪里？
不在 Spring Boot 后端代码里，不在 WireGuard 配置里，而是直接配置在校内落地服务器（202.118.70.251）的 Linux 系统上
就是这一行命令：
bash
运行
# 这就是你说的"修改源IP"的命令
iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -o eth0 -j SNAT --to-source 202.118.70.251
2. 这条命令到底干了什么？
它告诉 Linux 内核：
所有来自10.0.0.0/24网段（也就是所有 VPN 用户的虚拟 IP）的数据包，当它们要从eth0网卡（也就是连接校园网的网卡）发出去的时候，把数据包的源 IP 地址改成202.118.70.251（也就是这台校内服务器的真实校园公网 IP）
3. 完整的 IP 地址变化过程（一步一步给你拆）
假设：
校外用户真实 IP：114.114.114.114
校外用户 VPN 虚拟 IP：10.0.0.3
云服务器公网 IP：8.8.8.8
云服务器 VPN 虚拟 IP：10.0.0.1
校内服务器 VPN 虚拟 IP：10.0.0.2
校内服务器真实校园 IP：202.118.70.251
要访问的校内教务系统 IP：202.118.1.100
流量从校外用户到校内教务系统的 IP 变化：
校外用户电脑：
源 IP：10.0.0.3（虚拟 IP）
目标 IP：202.118.1.100
封装进 WireGuard 隧道，发往云服务器
云服务器：
解封装，看到源 IP：10.0.0.3，目标 IP：202.118.1.100
根据路由规则，转发给校内服务器的虚拟 IP10.0.0.2
重新封装进 WireGuard 隧道，发往校内服务器
校内落地服务器（关键一步！SNAT）：
解封装，看到源 IP：10.0.0.3，目标 IP：202.118.1.100
执行 iptables SNAT 规则：把源 IP 从10.0.0.3改成202.118.70.251
从eth0网卡发往校园网
校内教务系统：
收到数据包，看到源 IP：202.118.70.251（校园网 IP）
以为是校内某台机器发来的请求，正常响应
响应数据原路返回的 IP 变化：
校内教务系统：
源 IP：202.118.1.100
目标 IP：202.118.70.251
校内落地服务器：
收到响应，自动把目标 IP 从202.118.70.251改回10.0.0.3（内核自动做的，叫 "连接跟踪"）
封装进隧道，发往云服务器
云服务器：
转发给校外用户10.0.0.3
校外用户电脑：
解封装，收到响应数据
4. 为什么要在校内服务器做 SNAT，而不是在云服务器做？
因为：
云服务器的 IP 是公网 IP（8.8.8.8），校内系统不认
只有校内服务器的 IP（202.118.70.251）是校园网 IP，校内系统才会放行
这就是为什么我们必须要有 "云服务器 + 校内服务器" 双节点架构的根本原因
三、再给你补一个关键知识点
1. SNAT 和 DNAT 的区别
SNAT（源地址转换）：修改数据包的源 IP，就是我们这里用的，用来 "伪装" 成校内 IP
DNAT（目标地址转换）：修改数据包的目标 IP，用来做端口映射，把外网端口映射到内网机器
2. 为什么不用写代码实现 SNAT？
因为 Linux 内核已经提供了最完美、最高效的实现
直接用 iptables 命令配置，一行搞定
跑在内核层面，性能损耗几乎为 0
比你自己写 Java 代码处理数据包快 100 倍以上
3. 怎么验证 SNAT 生效了？
你可以在校内服务器上抓包看看：
bash
运行
tcpdump -i eth0 host 202.118.1.100
你会看到所有发往教务系统的数据包，源 IP 都是202.118.70.251，而不是 VPN 用户的虚拟 IP10.0.0.x
