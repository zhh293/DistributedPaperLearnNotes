你想了解 ReentrantLock 可打断特性的实现原理，并且希望结合源码梳理具体的执行流程。我会从 ReentrantLock 的核心入口方法开始，逐层拆解 AQS（AbstractQueuedSynchronizer）的底层逻辑，讲清楚 “可打断” 是如何通过源码落地的。
前置基础说明
ReentrantLock 的 “可打断” 能力是通过 lockInterruptibly() 方法提供的（区别于普通 lock() 方法的 “不可打断”），其核心依赖 AQS 的中断处理逻辑：
ReentrantLock 内部封装了继承 AQS 的Sync类（分公平FairSync/ 非公平NonfairSync），可打断的核心逻辑在 AQS 层面，公平 / 非公平仅在 “尝试获取锁” 阶段有差异；
AQS 的同步队列是实现锁竞争的核心，队列节点（Node）有关键状态：CANCELLED(1)（取消）、SIGNAL(-1)（后继节点需被唤醒）、0（初始）；
“可打断” 的本质：线程在等待获取锁的过程中，若收到中断信号，会立即终止等待、抛出InterruptedException，并清理队列中的节点。
一、源码实现流程（基于 JDK 8）
我们从lockInterruptibly()入口，逐层拆解每一步的执行逻辑。
步骤 1：ReentrantLock 的入口方法 lockInterruptibly()
这是暴露给用户的可打断锁入口，源码如下：
java
运行
public class ReentrantLock implements Lock, java.io.Serializable {
    private final Sync sync;

    // 可打断锁的入口方法
    public void lockInterruptibly() throws InterruptedException {
        // 调用内部Sync的lockInterruptibly，Sync继承AQS
        sync.lockInterruptibly();
    }

    // 内部Sync类（继承AQS）
    abstract static class Sync extends AbstractQueuedSynchronizer {
        // 转发到AQS的acquireInterruptibly方法
        final void lockInterruptibly() throws InterruptedException {
            acquireInterruptibly(1); // arg=1：独占锁，获取1个许可
        }
    }
}
核心说明：
方法会抛出InterruptedException，明确告知用户 “该操作可被打断”；
arg=1是 ReentrantLock 的约定：1 表示获取锁，0 表示释放锁（重入时计数累加）。
步骤 2：AQS 的核心分发方法 acquireInterruptibly(int arg)
这是 AQS 对 “可打断获取锁” 的顶层封装，源码如下：
java
运行
public abstract class AbstractQueuedSynchronizer extends AbstractOwnableSynchronizer {
    public final void acquireInterruptibly(int arg) throws InterruptedException {
        // 第一步：检查当前线程是否已被打断（核心！可打断的前置检测）
        if (Thread.interrupted()) {
            throw new InterruptedException();
        }
        // 第二步：尝试获取锁（tryAcquire由ReentrantLock的公平/非公平实现）
        if (!tryAcquire(arg)) {
            // 第三步：获取失败，进入同步队列等待，并处理中断
            doAcquireInterruptibly(arg);
        }
    }
}
核心说明：
Thread.interrupted()：检测当前线程的中断状态，并清除中断标记（若已中断，直接抛异常，无需进入队列）；
tryAcquire(arg)：ReentrantLock 的核心重写方法（公平锁会检查队列是否有等待节点，非公平锁直接 CAS 抢锁），获取成功则直接返回，失败则进入队列。
步骤 3：可打断的核心逻辑 doAcquireInterruptibly(int arg)
这是 “可打断” 的核心实现，线程会进入同步队列自旋等待，且在等待过程中持续检测中断，源码如下（关键行加注释）：
java
运行
private void doAcquireInterruptibly(int arg) throws InterruptedException {
    // 1. 创建独占模式的节点，加入同步队列尾部
    final Node node = addWaiter(Node.EXCLUSIVE);
    boolean failed = true; // 标记是否获取锁失败
    try {
        // 2. 自旋（for(;;)）尝试获取锁，这是AQS的核心
        for (;;) {
            final Node p = node.predecessor(); // 获取前驱节点
            // 2.1 若前驱是头节点，尝试抢锁（头节点是已获取锁的节点，释放后唤醒后继）
            if (p == head && tryAcquire(arg)) {
                setHead(node); // 抢锁成功，将当前节点设为头节点
                p.next = null; // 帮助GC，断开旧头节点的引用
                failed = false;
                return; // 成功获取锁，退出自旋
            }

            // 2.2 抢锁失败，判断是否需要挂起线程（park）
            if (shouldParkAfterFailedAcquire(p, node) && parkAndCheckInterrupt()) {
                // 核心！park被唤醒后，检测到中断→直接抛异常（可打断的关键）
                throw new InterruptedException();
            }
        }
    } finally {
        // 3. 若因异常退出（比如打断），取消当前节点的锁获取请求
        if (failed) {
            cancelAcquire(node);
        }
    }
}


你对这段代码的核心理解完全正确—— 这个for(;;)无限循环并不是无意义的空转，而是带有 “抢锁 - 暂停 - 唤醒 - 再抢锁” 的智能逻辑，你的分析精准抓住了核心：抢到锁就正常退出，没抢到会通过parkAndCheckInterrupt()让线程暂停，唤醒来源要么是锁释放后的unpark，要么是中断信号，唤醒后才会继续执行后续逻辑。
我再帮你补充几个关键细节，让你对这个循环的执行逻辑理解更完整：
一、循环的完整执行逻辑（逐轮拆解）
这个无限循环的每一轮执行都有明确的目的，绝非 “空转”，我们分首次进入循环和被唤醒后再次循环两个阶段拆解：
阶段 1：首次进入循环（线程刚入队）
先尝试抢锁：检查前驱是否是头节点（只有头节点释放锁后，后继才有抢锁资格），如果是则调用tryAcquire(arg)抢锁；
抢锁失败→执行shouldParkAfterFailedAcquire(p, node)：
这个方法的核心是将前驱节点的状态设为 SIGNAL（表示 “你释放锁时要唤醒我”），第一次执行时通常不会直接返回 true（因为要先完成前驱状态的设置），所以不会立即调用parkAndCheckInterrupt()；
第一次循环结束后，会进入第二轮循环，再次尝试抢锁（依然失败），此时shouldParkAfterFailedAcquire会返回 true，才会执行parkAndCheckInterrupt()；
执行parkAndCheckInterrupt()：线程调用LockSupport.park()进入阻塞状态（CPU 不再调度该线程，彻底暂停，不是空转），此时线程不再消耗 CPU 资源。
阶段 2：线程被唤醒后（两种唤醒场景）
线程从park()中被唤醒后，会从parkAndCheckInterrupt()继续执行：
场景 1：被锁释放的unpark唤醒（正常唤醒）
parkAndCheckInterrupt()调用Thread.interrupted()检测中断，返回false；
循环继续执行→再次检查前驱是否是头节点，尝试抢锁；
抢锁成功→退出循环；抢锁失败→再次执行shouldParkAfterFailedAcquire→park暂停。
场景 2：被interrupt()中断唤醒（可打断核心）
parkAndCheckInterrupt()调用Thread.interrupted()检测中断，返回true；
触发throw new InterruptedException()，直接终止循环，进入finally块执行cancelAcquire(node)清理节点。
二、你理解中需要补充的关键细节
“唤醒这些线程” 的精准表述：锁释放时，并不是唤醒所有等待线程，而是头节点的释放逻辑只会唤醒其直接后继节点（通过unparkSuccessor(node)方法），避免 “惊群效应”，只有被唤醒的这一个线程会从 park 中恢复，继续抢锁；
shouldParkAfterFailedAcquire的 “铺垫” 作用：这个方法是 park 的前置条件，目的是确保当前线程的前驱节点 “承诺” 会唤醒它，避免线程 park 后无人唤醒（永久阻塞），所以首次循环时它会先完成状态设置，第二次才会允许 park；
park 后的线程状态：线程调用park()后，会从RUNNABLE变为WAITING状态，此时完全不占用 CPU 资源，这也是为什么说循环不是 “空转”—— 大部分时间线程是暂停的，只有被唤醒后才会短暂执行抢锁逻辑。
总结
这个无限循环的核心是 “抢锁失败→暂停→唤醒→再抢锁” 的闭环，线程大部分时间处于 park 暂停状态（不消耗 CPU），绝非空转；
循环退出只有两种情况：①抢锁成功正常返回；②检测到中断抛异常终止；
线程唤醒来源有且只有两个：锁释放后的unpark()（继续抢锁）、线程的interrupt()（抛异常终止）。









关键子方法解析（支撑可打断逻辑）
shouldParkAfterFailedAcquire(p, node)：作用是检查前驱节点状态，确保当前线程可以安全挂起（park），核心逻辑是将前驱节点状态设为SIGNAL（表示 “前驱释放锁时要唤醒我”）。
parkAndCheckInterrupt()：这是 “可打断” 的核心触发点，源码如下：
java
运行
private final boolean parkAndCheckInterrupt() {
    LockSupport.park(this); // 挂起当前线程，等待被唤醒（unpark）或打断
    return Thread.interrupted(); // 唤醒后检测中断状态，清除标记并返回
}
核心说明：
LockSupport.park()：线程进入阻塞状态，此时有两种唤醒方式：
其他线程调用unpark(this)（锁释放时）；
其他线程调用thread.interrupt()（打断）；
线程被唤醒后，立即调用Thread.interrupted()检测中断：
若返回true（被打断），则向上抛InterruptedException；
若返回false（正常唤醒），则继续自旋抢锁。
cancelAcquire(node)：当线程因中断抛出异常时，会执行该方法清理节点，核心逻辑：
将节点状态设为CANCELLED(1)（取消状态）；
移除该节点从同步队列中，调整前驱 / 后继节点的引用，避免无效节点影响队列结构；
确保队列中仅保留 “等待中” 的有效节点。
二、可打断 vs 不可打断的核心差异
为了更清晰理解，对比 ReentrantLock 普通lock()（不可打断）的核心逻辑：
特性	可打断（lockInterruptibly ()）	不可打断（lock ()）
核心方法	doAcquireInterruptibly()	doAcquire()
中断处理	检测到中断→抛异常 + 取消节点	检测到中断→仅标记状态，不抛异常
异常声明	throws InterruptedException	无异常声明
线程状态	被打断后立即退出等待	即使被打断，仍继续自旋等待
总结（核心要点）
入口层：ReentrantLock 的lockInterruptibly()是可打断的入口，底层转发到 AQS 的acquireInterruptibly()；
检测层：AQS 在两个关键节点检测中断：①进入队列前直接检测；②线程 park 唤醒后检测，任一环节检测到中断都抛异常；
核心层：parkAndCheckInterrupt()是 “可打断” 的触发点，线程被打断唤醒后，立即返回中断状态并抛异常，同时cancelAcquire()清理无效节点。
















不可打断原理



一、不可打断锁的核心原理
不可打断锁的本质是：线程在等待获取锁的过程中，即使检测到中断标记，也不会立即响应中断（不抛异常、不终止等待），仅保留中断标记；直到线程成功获取锁后，中断标记依然存在，由用户自行决定是否处理，全程不会主动抛出InterruptedException。
其原理依赖两个核心设计：
中断标记的 “保留” 而非 “响应”：Java 线程中断是 “标记位” 机制，不可打断锁对中断的处理是 “记下来但不处理”，直到获取锁后再暴露这个标记；
AQS 的自旋等待逻辑：线程在 AQS 同步队列中自旋等待时，检测到中断后仅记录 “被中断过” 的状态，继续自旋抢锁，而非终止流程；
无异常抛出的设计：lock()方法不声明InterruptedException，因此底层逻辑也刻意规避了该异常的抛出，仅通过标记传递中断信号。
二、源码实现流程（基于 JDK 8，对比可打断逻辑更易理解）
我们从lock()入口逐层拆解，重点看 “中断检测后不终止等待” 的核心逻辑：
步骤 1：ReentrantLock 的入口方法 lock()
这是不可打断锁的入口，转发到内部 Sync 的 lock 方法（公平 / 非公平 Sync 仅抢锁逻辑不同，不可打断的核心一致）：
java
运行
public class ReentrantLock implements Lock {
    private final Sync sync;

    public void lock() {
        // 转发到Sync的lock方法，最终调用AQS的acquire(1)
        sync.lock();
    }

    // 非公平Sync示例（公平Sync逻辑类似，仅tryAcquire不同）
    static final class NonfairSync extends Sync {
        final void lock() {
            // 1. 先CAS抢锁，失败则调用AQS的acquire(1)
            if (compareAndSetState(0, 1))
                setExclusiveOwnerThread(Thread.currentThread());
            else
                acquire(1); // 进入AQS的不可打断获取逻辑
        }
    }
}
步骤 2：AQS 的顶层分发方法 acquire(int arg)
这是不可打断获取锁的核心入口，逻辑是 “尝试抢锁→失败则入队等待”，且对中断仅记录不处理：
java
运行
public abstract class AbstractQueuedSynchronizer {
    public final void acquire(int arg) {
        // 核心逻辑：
        // 1. tryAcquire(arg)：尝试抢锁（ReentrantLock重写）
        // 2. 抢锁失败则调用acquireQueued()入队等待，返回是否被中断过
        // 3. 若被中断过，调用selfInterrupt()恢复中断标记
        if (!tryAcquire(arg) && acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) {
            selfInterrupt(); // 关键：恢复中断标记（因为检测中断时会清除标记）
        }
    }
}
核心说明：
acquireQueued()是不可打断的核心，返回值表示 “线程在等待过程中是否被中断过”；
selfInterrupt()：重新给当前线程设置中断标记（因为Thread.interrupted()会清除标记，这里要恢复，保证用户后续能检测到）。
步骤 3：不可打断的核心逻辑 acquireQueued(Node node, int arg)
这是 “不可打断” 的核心实现 —— 线程在队列中自旋等待，检测到中断后仅标记、不终止、不抛异常：
java
运行
final boolean acquireQueued(final Node node, int arg) {
    boolean failed = true; // 标记是否抢锁失败
    try {
        boolean interrupted = false; // 标记：等待过程中是否收到过中断
        // 自旋等待（核心：死循环，直到拿到锁才退出）
        for (;;) {
            final Node p = node.predecessor(); // 获取前驱节点
            // 前驱是头节点，尝试抢锁
            if (p == head && tryAcquire(arg)) {
                setHead(node); // 抢锁成功，设为头节点
                p.next = null; // 帮助GC
                failed = false;
                return interrupted; // 返回是否被中断过，退出自旋
            }

            // 抢锁失败，判断是否需要park，并检测中断
            if (shouldParkAfterFailedAcquire(p, node) && parkAndCheckInterrupt()) {
                // 核心！检测到中断→仅把interrupted设为true，继续自旋（不抛异常、不终止）
                interrupted = true;
            }
        }
    } finally {
        if (failed) {
            cancelAcquire(node); // 仅当异常时清理节点（不可打断逻辑中几乎不会触发）
        }
    }
}
关键子方法：parkAndCheckInterrupt()（和可打断逻辑共用，但处理不同）
java
运行
private final boolean parkAndCheckInterrupt() {
    LockSupport.park(this); // 挂起线程，等待唤醒（中断或正常唤醒）
    return Thread.interrupted(); // 检测中断标记，**并清除标记**
}
核心说明：
线程被唤醒（无论是unpark正常唤醒，还是interrupt中断唤醒），都会执行Thread.interrupted()；
若返回true（被中断），acquireQueued()仅把interrupted设为true，然后继续自旋抢锁 —— 这是 “不可打断” 的关键：中断只标记，不终止等待。
步骤 4：恢复中断标记 selfInterrupt()
当acquireQueued()返回true（表示等待中被中断过），会调用该方法恢复中断标记：
java
运行
static void selfInterrupt() {
    // 重新设置中断标记，让用户后续能检测到
    Thread.currentThread().interrupt();
}
核心说明：因为Thread.interrupted()会清除中断标记，这里要 “补回来”，保证线程拿到锁后，用户能通过Thread.isInterrupted()检测到中断。
三、不可打断 vs 可打断的核心原理差异
通过对比，更易理解 “不可打断” 的本质：
原理维度	不可打断锁（lock()）	可打断锁（lockInterruptibly()）
中断检测后处理	仅标记interrupted=true，继续自旋抢锁	直接抛InterruptedException，终止自旋
异常抛出	全程不抛InterruptedException	检测到中断立即抛InterruptedException
中断标记处理	先清除（Thread.interrupted()），最后恢复（selfInterrupt()）	抛异常时清除，不恢复
等待终止条件	只有拿到锁才退出自旋	拿到锁 或 检测到中断 都可退出自旋
四、总结（不可打断锁的核心原理要点）
核心逻辑：中断仅作为 “标记” 存在，线程在等待锁时检测到中断，不会终止等待，仅记录标记，继续自旋直到拿到锁；
标记恢复：通过selfInterrupt()恢复被清除的中断标记，保证用户在获取锁后能检测到中断；
无异常设计：底层逻辑不抛InterruptedException，因此lock()方法也无需声明该异常，中断的处理权完全交给用户。
