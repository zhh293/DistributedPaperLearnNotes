你想搞懂 AQS 的核心原理，以及它相比传统synchronized加锁的独特优势 —— 而且你也知道 AQS 是 Java 并发编程里的 “基石级” 技术，我会先从 AQS 的 “本质是什么” 入手，用生活化的例子讲透核心原理，再对比它和synchronized的差异、优势，最后结合实际应用场景总结，保证既详细又易懂。
一、先搞懂：AQS 到底是个啥？（本质 + 核心定位）
AQS 的全称是AbstractQueuedSynchronizer（抽象队列同步器），你可以把它理解为：Java 并发包（JUC）中所有锁 / 同步工具的 “通用骨架”。
打个生活化的比方：
你去银行办理业务，银行有「叫号机（同步状态）」+「排队区（等待队列）」—— 这就是 AQS 的核心；
叫号机显示 “0”= 没人办理（无锁），显示 “1”= 有人办理（加锁）；
顾客（线程）来办理业务，先抢叫号机：抢到了直接办（拿到锁），没抢到就去排队区等着（进入等待队列），等前面的人办完了，叫号机重置，再叫下一个人（唤醒线程）。
AQS 的核心定位：
JUC 包中的ReentrantLock（可重入锁）、CountDownLatch（倒计时门闩）、Semaphore（信号量）、ReentrantReadWriteLock（读写锁）等，底层全是基于 AQS 实现的——AQS 把 “排队、阻塞、唤醒、状态管理” 这些通用逻辑抽成模板，子类只需要重写少量方法，就能实现不同的锁 / 同步器。
二、AQS 的核心原理：3 大核心组件 + 2 大核心流程
AQS 的核心设计就三件事：管理同步状态、维护等待队列、处理线程阻塞 / 唤醒，拆解如下：
1. 核心组件 1：同步状态（volatile int state）——“银行叫号机”
这是 AQS 最核心的变量，相当于 “锁的标识”：
volatile 修饰：保证多线程间的可见性（一个线程改了 state，其他线程立刻能看到）；
CAS 操作：保证修改 state 的原子性（比如多个线程同时抢锁，只有一个能成功修改 state）；
可自定义含义：不同同步工具对 state 的解读不同：
ReentrantLock：state=0→无锁，state=1→加锁，重入时 state 递增（比如重入 2 次→state=2）；
Semaphore（信号量）：state=5→允许 5 个线程同时访问；
CountDownLatch：state=3→需要等 3 个线程执行完，state 减到 0 才放行。
2. 核心组件 2：CLH 等待队列 ——“银行排队区”
这是一个双向链表实现的队列，专门存放 “抢锁失败” 的线程，特点：
FIFO（先进先出）：保证线程等待的公平性（非公平锁可插队）；
每个节点对应一个线程：节点里存了线程引用、等待状态（比如是否取消、是否需要唤醒）、前驱 / 后继节点；
阻塞 / 唤醒：用LockSupport.park()阻塞线程（相当于 “冻结排队的顾客”），LockSupport.unpark()唤醒线程（相当于 “叫下一个顾客”）—— 比Object.wait()/notify()更灵活。
3. 核心组件 3：可重写的核心方法 ——“自定义业务规则”
AQS 是抽象类，本身不实现具体的锁逻辑，而是提供模板方法，子类（比如 ReentrantLock）通过重写以下方法定义 “怎么抢锁、怎么释放锁”：
方法	作用（大白话）	适用场景
tryAcquire(int arg)	尝试独占式获取锁（比如 ReentrantLock）	独占锁（一次只能一个线程拿）
tryRelease(int arg)	尝试独占式释放锁	独占锁
tryAcquireShared(int arg)	尝试共享式获取锁（比如 Semaphore）	共享锁（多个线程可同时拿）
tryReleaseShared(int arg)	尝试共享式释放锁	共享锁


4. AQS 的核心流程（以独占锁 ReentrantLock 为例）
用 “银行办理业务” 的流程对应，一步一步看线程怎么抢锁 / 释放锁：

A[线程抢锁] --> B{调用tryAcquire()尝试CAS改state};
    B -->|成功（state从0→1）| C[拿到锁，执行临界区代码];
    B -->|失败| D[创建节点，加入CLH队列尾部];
    D --> E[调用LockSupport.park()阻塞线程];
    C --> F[执行完代码，调用tryRelease()改state为0];
    F --> G[调用unparkSuccessor()唤醒队列头的线程];
    G --> H[被唤醒的线程重新执行tryAcquire()抢锁];
    H --> B;



逐步解释：
抢锁：线程调用lock()，底层触发 AQS 的acquire()方法；
尝试抢锁：先调用tryAcquire()（ReentrantLock 重写的方法），CAS 修改 state：
如果 state=0→改成 1，成功→直接执行代码（拿到锁）；
如果 state≠0（有人占着）→抢锁失败；
入队阻塞：抢锁失败后，创建一个 “独占式节点”，加入 CLH 队列尾部，然后线程被park()阻塞（暂停执行）；
释放锁：拿到锁的线程执行完代码，调用unlock()，底层触发release()方法：
调用tryRelease()，把 state 改回 0；
找到队列头的节点，调用unpark()唤醒对应的线程；
重新抢锁：被唤醒的线程从park()处恢复，再次执行tryAcquire()抢锁，重复上述流程。


先回顾 synchronized 的特点（JDK6 后已优化）
synchronized是 “傻瓜式锁”：
自动加锁 / 释放锁（方法结束 / 抛异常都会自动释放），不用手动操作；
底层优化：JDK6 后加入偏向锁、轻量级锁、重量级锁，低并发下性能很好；
缺点：灵活性差、功能单一、高并发下性能一般。







AQS（以 ReentrantLock 为例）的核心优势
对比维度	synchronized	AQS（ReentrantLock）	优势解读
锁获取方式	仅阻塞式获取（抢不到就死等）	支持 3 种方式：
1. 阻塞式（lock ()）
2. 非阻塞式（tryLock ()）
3. 超时获取（tryLock (timeout)）
4. 可中断获取（lockInterruptibly ()）	避免死等：比如超时获取，到时间没抢到就放弃，防止死锁
公平性	固定非公平锁（线程可插队抢锁）	公平 / 非公平锁可选（构造方法传 boolean）	公平锁保证排队顺序，适合对顺序敏感的场景
同步模式	仅独占式（一次只能一个线程拿）	支持 2 种模式：
1. 独占式（ReentrantLock）
2. 共享式（Semaphore/CountDownLatch）	可实现 “多线程同时访问”（比如 Semaphore 允许 5 个线程同时拿锁）
条件等待	一个锁对应一个条件队列（Object.wait ()）	一个锁可对应多个 Condition 队列（newCondition ()）	比如：生产者消费者模型，可分 “生产队列”“消费队列”，精准唤醒
手动控制	自动加锁 / 释放，无法手动干预	手动加锁（lock ()）、手动释放（unlock ()，需 finally 保证）	可在加锁后执行非临界区代码，再释放，适配复杂场景
高并发性能	重量级锁阶段依赖操作系统互斥量，切换成本高	基于 CAS + 队列，线程阻塞 / 唤醒更轻量，高并发下更高效







举个例子：AQS 的 “可中断获取锁” 解决 synchronized 的痛点
synchronized的问题：线程 A 抢不到锁会一直阻塞，就算你想中断它（thread.interrupt()），也没用，只能死等；AQS 的解决方案：lockInterruptibly()，线程抢锁时如果被中断，会立刻抛出InterruptedException，停止等待：
java
运行
// AQS的可中断锁示例（ReentrantLock）
public class AQSInterruptDemo {
    private static final ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            try {
                // 可中断获取锁：如果线程被中断，直接抛异常
                lock.lockInterruptibly();
                System.out.println("t1拿到锁");
            } catch (InterruptedException e) {
                System.out.println("t1被中断，放弃抢锁");
                return;
            } finally {
                lock.unlock();
            }
        });

        lock.lock(); // main线程先拿到锁
        t1.start();
        Thread.sleep(1000);
        t1.interrupt(); // 中断t1线程
    }
}
// 输出：t1被中断，放弃抢锁
如果用synchronized，t1 会一直阻塞，就算中断也没用 —— 这就是 AQS 的灵活性。











误区扫盲
一、先搞懂：AQS 到底是什么？
AQS 是 Java 并发包（java.util.concurrent.locks）的底层核心框架，不是直接给开发者用的，而是用来给 Lock（如 ReentrantLock）、同步器（如 CountDownLatch、Semaphore）提供 “锁 / 同步” 的底层能力。
你可以把 AQS 理解为一个 “模板工具箱”：它定义了锁的核心逻辑（排队、等待、唤醒、状态管理），而 Lock 的实现类（比如 ReentrantLock）只需要 “填模板”（实现少量自定义方法），就能快速实现一把功能完整的锁。
二、AQS 的核心内容
AQS 的核心设计围绕「状态管理 + 等待队列」展开，所有逻辑都基于这两个核心，再结合 “模板方法模式” 让子类定制化。



1. 核心属性（基础骨架）
属性名	类型	作用
state	volatile int	同步状态（核心），用 volatile 保证可见性。
- 独占锁（如 ReentrantLock）：state=0 表示无锁，state>0 表示重入次数；
- 共享锁（如 Semaphore）：state 表示可用许可数。
CLH 队列	双向链表（Node 节点）	管理所有等待获取锁的线程，也叫 “同步队列”。每个 Node 封装了：
- 等待的线程（Thread）；
- 节点状态（如 SIGNAL：后继节点需要唤醒）；
- 前驱 / 后继节点引用。
exclusiveOwnerThread	Thread	仅独占模式下使用，记录当前持有锁的线程。





2. 核心模式（两种使用方式）
AQS 支持两种锁模式，Lock 主要用独占模式：
独占模式（Exclusive）：同一时间只有 1 个线程能获取锁，比如 ReentrantLock（可重入独占锁）。
共享模式（Shared）：同一时间多个线程可获取锁，比如 Semaphore（信号量）、CountDownLatch（倒计时器）。
3. 核心方法（模板方法模式）
AQS 定义了一套 “模板方法”，子类（如 ReentrantLock 的内部类 Sync）只需要实现「尝试获取 / 释放锁」的逻辑，AQS 会自动处理 “排队、挂起、唤醒” 等底层细节。
AQS 核心模板方法	作用	子类需要实现的自定义方法
acquire(int arg)	独占式获取锁（不响应中断）	tryAcquire(int arg)：尝试独占获取锁（CAS 修改 state）
acquireInterruptibly(int arg)	独占式获取锁（响应中断）	同上
release(int arg)	独占式释放锁	tryRelease(int arg)：尝试独占释放锁（修改 state）
acquireShared(int arg)	共享式获取锁	tryAcquireShared(int arg)：尝试共享获取锁
releaseShared(int arg)	共享式释放锁	tryReleaseShared(int arg)：尝试共享释放锁
4. Node 节点的核心状态（辅助队列管理）
Node 是 CLH 队列的基本单元，它的状态决定了线程的行为：
CANCELLED(1)：线程取消等待（比如超时、中断），会被移出队列；
SIGNAL(-1)：当前节点的后继节点需要被唤醒（核心）；
CONDITION(-2)：节点在 “条件队列” 中（配合 Condition 使用）；
PROPAGATE(-3)：共享模式下，唤醒会向后续节点传播。




三、AQS 与 Lock 接口方法的对应关系
Lock 是面向开发者的 “锁接口”，定义了锁的通用行为；而 AQS 是 Lock 实现类的 “底层支撑”，Lock 的所有核心方法最终都通过调用 AQS 的模板方法实现。
先看 Lock 接口的核心方法，再看每个方法如何基于 AQS 实现（以最典型的 ReentrantLock 为例）：
Lock 接口方法	核心功能	对应 AQS 的实现逻辑
void lock()	独占获取锁，不响应中断	1. 调用 AQS 的 acquire(1)；
2. acquire 先调用 ReentrantLock 内部类的 tryAcquire(1)：
- 成功：CAS 修改 state=1，设置 exclusiveOwnerThread 为当前线程；
- 失败：将当前线程封装成 Node 加入 CLH 队列，挂起线程等待唤醒。
void lockInterruptibly() throws InterruptedException	独占获取锁，响应中断	1. 调用 AQS 的 acquireInterruptibly(1)；
2. 逻辑和 acquire 一致，但如果线程被中断，会直接抛出 InterruptedException，不再等待。
boolean tryLock()	非阻塞尝试获取锁	直接调用 ReentrantLock 内部类的 tryAcquire(1)：
- 成功：返回 true；
- 失败：返回 false（不加入队列，非阻塞）。
boolean tryLock(long time, TimeUnit unit) throws InterruptedException	超时获取锁，响应中断	1. 调用 AQS 的 tryAcquireNanos(1, 超时纳秒数)；
2. 在指定时间内循环尝试 tryAcquire，超时 / 中断则返回 false，成功则返回 true。
void unlock()	释放锁	1. 调用 AQS 的 release(1)；
2. release 先调用 tryRelease(1)：
- 重入锁：state 减 1，直到 state=0 才算真正释放；
- 释放成功后，调用 unparkSuccessor() 唤醒 CLH 队列的后继节点。
Condition newCondition()	创建条件对象	返回 AQS 的内部类 ConditionObject：
- Condition 的 await()：将线程移到 “条件队列”，释放锁；
- Condition 的 signal()：将线程从条件队列移回 CLH 队列，等待获取锁。
举个极简例子：ReentrantLock 基于 AQS 的核心实现
java
运行
// Lock 接口的实现类 ReentrantLock
public class ReentrantLock implements Lock {
    // 内部类 Sync 继承 AQS，实现自定义的 tryAcquire/tryRelease
    private abstract static class Sync extends AbstractQueuedSynchronizer {
        // 实现 AQS 要求的 tryAcquire（独占获取锁）
        @Override
        protected boolean tryAcquire(int arg) {
            Thread current = Thread.currentThread();
            int c = getState();
            // 无锁状态，CAS 获取锁
            if (c == 0) {
                if (compareAndSetState(0, arg)) {
                    setExclusiveOwnerThread(current);
                    return true;
                }
            }
            // 重入锁：当前线程已持有锁，state 加 1
            else if (current == getExclusiveOwnerThread()) {
                setState(c + arg);
                return true;
            }
            return false;
        }

        // 实现 AQS 要求的 tryRelease（独占释放锁）
        @Override
        protected boolean tryRelease(int arg) {
            int c = getState() - arg;
            if (Thread.currentThread() != getExclusiveOwnerThread()) {
                throw new IllegalMonitorStateException();
            }
            boolean free = false;
            // 只有 state=0 时，才算真正释放锁
            if (c == 0) {
                free = true;
                setExclusiveOwnerThread(null);
            }
            setState(c);
            return free;
        }
    }

    // 非公平锁的实现（默认）
    private static class NonfairSync extends Sync {
        // lock() 调用 AQS 的 acquire(1)
        final void lock() {
            acquire(1);
        }
    }

    // Lock 接口的 lock() 方法
    @Override
    public void lock() {
        sync.lock(); // sync 是 NonfairSync/FairSync 的实例
    }

    // Lock 接口的 unlock() 方法
    @Override
    public void unlock() {
        sync.release(1); // 调用 AQS 的 release(1)
    }

    // 其他 Lock 方法同理...
    private final Sync sync;
    public ReentrantLock() {
        sync = new NonfairSync();
    }
}


Lock 实现类（比如 ReentrantLock）会在内部定义一个继承 AQS 的自定义同步器（如 Sync），这个同步器只需要重写 AQS 要求的「核心逻辑方法」（比如 tryAcquire/tryRelease）；然后在实现 Lock 接口的对外方法（lock()/unlock() 等）时，直接调用 AQS 已经封装好的模板方法（比如 acquire()/release()），而这些模板方法会自动调用我们重写的 tryAcquire/tryRelease，排队、挂起、唤醒等复杂逻辑全由 AQS 兜底。
举个更通俗的例子帮你理解：
AQS 就像一个 “半成品蛋糕胚”，已经做好了基础的奶油、夹层（排队、唤醒逻辑）；
Lock 实现类里的自定义同步器（继承 AQS），只需要给这个胚子 “加口味”（重写 tryAcquire 定义 “怎么抢锁”、tryRelease 定义 “怎么放锁”）；
Lock 接口的对外方法（lock()/unlock()），就是把这个加好口味的蛋糕 “端给用户”（调用 AQS 的模板方法，触发完整的抢锁 / 放锁流程）。
总结（关键点回顾）
核心层级：Lock 是 “对外接口”，AQS 是 “底层骨架”，中间靠「Lock 实现类内部的 AQS 子类」衔接；
核心动作：AQS 子类只重写 tryAcquire/tryRelease（抢 / 放锁的核心逻辑），Lock 对外方法调用 AQS 的 acquire/release（模板方法）；
分工：AQS 管 “通用的复杂逻辑”（排队、唤醒），Lock 实现类管 “定制化的简单逻辑”（修改 state 判断锁状态）。
