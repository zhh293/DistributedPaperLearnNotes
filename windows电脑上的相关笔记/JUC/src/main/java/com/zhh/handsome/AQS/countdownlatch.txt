CountDownLatch（倒计时门闩）全解析：核心用法与实战细节
一、CountDownLatch 基础认知
1.1 核心定义
CountDownLatch（倒计时门闩）是 JUC（java.util.concurrent）包下的同步工具，核心作用是让一个或多个线程等待其他线程完成一组操作后，再继续执行。
它的工作机制像 “倒计时器”：
初始化时指定一个计数器值（比如 5）；
每个子线程完成任务后，调用countDown()方法让计数器减 1；
调用await()方法的线程（通常是主线程）会阻塞，直到计数器值变为 0；
计数器归 0 后，所有等待的线程被唤醒，继续执行后续逻辑。
1.2 底层原理（极简版，新手易懂）
CountDownLatch基于 AQS（AbstractQueuedSynchronizer）实现，核心是将 AQS 的state变量直接作为倒计时计数器：
state = N：初始化时的计数器值（N 为需要等待的任务数）；
子线程调用countDown()：原子性地将state-1（线程安全，无需额外加锁）；
主线程调用await()：若state > 0，则进入 AQS 等待队列阻塞；若state = 0，则直接返回；
当state被减至 0 时，AQS 会唤醒所有等待队列中的线程。
1.3 核心特性（必记）
一次性：计数器值归 0 后，CountDownLatch就失效了，无法重置计数器（这是和CyclicBarrier的核心区别）；
非独占性：多个线程可同时调用await()等待，计数器归 0 时所有线程被唤醒；
支持超时：可指定等待超时时间，避免线程永久阻塞；
支持中断：等待中的线程可被中断，抛出InterruptedException。
1.4 核心适用场景
CountDownLatch的核心价值是 **“等待多线程完成”**，最典型的场景：
主线程等待子线程初始化：项目启动时，主线程等待多个子线程加载配置、初始化连接池、加载缓存后，再对外提供服务；
多任务并行执行后汇总：比如多线程下载文件的不同分片，等待所有分片下载完成后，主线程合并文件；
并发性能测试：统计多个线程同时执行某个接口 / 方法的总耗时；
批量任务触发：等待所有前置任务完成后，再执行后续批量操作。
二、核心 API 与基础用法
2.1 核心 API（必记）
CountDownLatch的 API 极少且易用，核心只有 4 个方法：
方法	作用	关键特性
CountDownLatch(int count)	创建倒计时门闩，指定初始计数器值	count必须≥0，否则抛IllegalArgumentException
await()	让当前线程阻塞，直到计数器归 0	可中断（线程被中断时抛InterruptedException）
await(long timeout, TimeUnit unit)	让当前线程阻塞，直到计数器归 0 或 超时	超时返回false，计数器归 0 返回true；可中断
countDown()	计数器值减 1	原子操作（多线程调用安全）；若计数器已为 0，调用无效果
getCount()	获取当前计数器值	用于监控 / 调试，生产中极少使用
2.2 最简使用模板（生产必守）
核心原则：
子线程必须在任务完成后调用countDown()（即使任务抛出异常，也要在finally中调用）；
主线程优先使用await(timeout, unit)，避免永久阻塞；
计数器值必须和子线程数 / 任务数匹配。
基础示例：主线程等待 5 个子线程完成任务
java
运行
import java.util.concurrent.CountDownLatch;

/**
 * CountDownLatch基础用法：主线程等待5个子线程完成任务
 */
public class CountDownLatchBasicDemo {
    public static void main(String[] args) throws InterruptedException {
        // 1. 初始化CountDownLatch：计数器值=5（对应5个子线程）
        CountDownLatch countDownLatch = new CountDownLatch(5);

        // 2. 创建5个子线程执行任务
        for (int i = 0; i < 5; i++) {
            int taskId = i;
            new Thread(() -> {
                try {
                    // 模拟子线程执行任务
                    System.out.println("子线程" + taskId + "开始执行任务");
                    Thread.sleep(1000); // 模拟任务耗时
                    System.out.println("子线程" + taskId + "完成任务");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    System.out.println("子线程" + taskId + "被中断");
                } finally {
                    // 3. 任务完成（无论成功/失败），计数器减1
                    countDownLatch.countDown();
                    System.out.println("子线程" + taskId + "调用countDown，剩余计数器值：" + countDownLatch.getCount());
                }
            }, "子线程-" + i).start();
        }

        // 4. 主线程等待：阻塞直到计数器归0（超时时间设为10秒，避免永久阻塞）
        System.out.println("主线程等待所有子线程完成任务...");
        boolean awaitResult = countDownLatch.await(10, java.util.concurrent.TimeUnit.SECONDS);

        // 5. 所有子线程完成，主线程继续执行
        if (awaitResult) {
            System.out.println("所有子线程任务完成，主线程开始执行后续逻辑");
        } else {
            System.out.println("等待超时，部分子线程未完成任务");
        }
    }
}
运行结果特征：
5 个子线程同时启动并执行任务；
每个子线程完成后调用countDown()，计数器从 5 逐步减至 0；
计数器归 0 后，主线程被唤醒，执行后续逻辑；
若子线程执行超时（比如超过 10 秒），主线程会直接返回 “等待超时”。
三、经典实战场景（生产高频）
3.1 场景 1：项目启动初始化（核心场景）
项目启动时，主线程需要等待多个初始化任务（加载配置、初始化连接池、加载缓存）完成后，再对外提供服务，这是CountDownLatch最典型的生产用法：
java
运行
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

/**
 * CountDownLatch实战：项目启动初始化
 */
public class ProjectInitDemo {
    // 初始化任务数：3（加载配置、初始化DB连接池、加载缓存）
    private static final int INIT_TASK_COUNT = 3;
    private static final CountDownLatch INIT_LATCH = new CountDownLatch(INIT_TASK_COUNT);

    // 初始化任务1：加载配置
    private static void loadConfig() {
        new Thread(() -> {
            try {
                System.out.println("开始加载系统配置...");
                Thread.sleep(1500); // 模拟加载耗时
                System.out.println("系统配置加载完成");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.out.println("加载配置被中断");
            } finally {
                INIT_LATCH.countDown();
            }
        }, "配置加载线程").start();
    }

    // 初始化任务2：初始化DB连接池
    private static void initDbPool() {
        new Thread(() -> {
            try {
                System.out.println("开始初始化DB连接池...");
                Thread.sleep(2000); // 模拟初始化耗时
                System.out.println("DB连接池初始化完成");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.out.println("初始化DB连接池被中断");
            } finally {
                INIT_LATCH.countDown();
            }
        }, "DB连接池线程").start();
    }

    // 初始化任务3：加载缓存
    private static void loadCache() {
        new Thread(() -> {
            try {
                System.out.println("开始加载缓存...");
                Thread.sleep(1000); // 模拟加载耗时
                System.out.println("缓存加载完成");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.out.println("加载缓存被中断");
            } finally {
                INIT_LATCH.countDown();
            }
        }, "缓存加载线程").start();
    }

    public static void main(String[] args) throws InterruptedException {
        // 1. 启动所有初始化任务
        System.out.println("项目开始初始化...");
        loadConfig();
        initDbPool();
        loadCache();

        // 2. 主线程等待初始化完成（超时时间30秒，适配生产场景）
        boolean initSuccess = INIT_LATCH.await(30, TimeUnit.SECONDS);

        // 3. 初始化完成，对外提供服务
        if (initSuccess) {
            System.out.println("所有初始化任务完成，项目启动成功，开始对外提供服务");
        } else {
            System.err.println("初始化超时，项目启动失败");
            System.exit(1); // 启动失败，退出程序
        }
    }
}
核心设计亮点：
每个初始化任务独立线程执行，并行初始化，提升启动速度；
finally中调用countDown()，即使任务异常也能保证计数器递减；
主线程设置超时等待，避免初始化卡住导致程序挂起；
初始化失败时直接退出程序，符合生产中 “启动失败快速失败” 的原则。
3.2 场景 2：多线程并行任务汇总（文件下载示例）
多线程下载文件的不同分片，等待所有分片下载完成后，主线程合并文件，这是 “并行任务 + 结果汇总” 的典型场景：
java
运行
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

/**
 * CountDownLatch实战：多线程下载文件分片并汇总
 */
public class FileDownloadDemo {
    // 文件分片数：4
    private static final int FILE_PART_COUNT = 4;
    private static final CountDownLatch DOWNLOAD_LATCH = new CountDownLatch(FILE_PART_COUNT);

    // 下载单个分片
    private static void downloadPart(int partNum) {
        new Thread(() -> {
            try {
                System.out.println("开始下载文件分片" + partNum);
                // 模拟下载耗时（不同分片耗时不同）
                Thread.sleep(500 + partNum * 200);
                System.out.println("文件分片" + partNum + "下载完成");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.out.println("下载分片" + partNum + "被中断");
            } finally {
                DOWNLOAD_LATCH.countDown();
            }
        }, "下载线程-" + partNum).start();
    }

    public static void main(String[] args) throws InterruptedException {
        // 1. 启动所有分片下载线程
        System.out.println("开始多线程下载文件...");
        for (int i = 0; i < FILE_PART_COUNT; i++) {
            downloadPart(i);
        }

        // 2. 等待所有分片下载完成（超时时间10秒）
        boolean downloadComplete = DOWNLOAD_LATCH.await(10, TimeUnit.SECONDS);

        // 3. 汇总结果
        if (downloadComplete) {
            System.out.println("所有文件分片下载完成，开始合并文件...");
            Thread.sleep(1000); // 模拟合并耗时
            System.out.println("文件合并完成，下载成功");
        } else {
            System.err.println("部分分片下载超时，文件下载失败");
        }
    }
}
核心设计亮点：
多线程并行下载分片，比单线程下载效率提升数倍；
计数器值与分片数一致，确保所有分片下载完成后才合并；
超时机制避免某一分片下载卡住导致整体任务挂起。
3.3 场景 3：并发性能测试（统计接口执行耗时）
统计多个线程同时执行某个接口的总耗时，这是测试并发性能的常用方法：
java
运行
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

/**
 * CountDownLatch实战：并发性能测试（统计接口执行耗时）
 */
public class PerformanceTestDemo {
    // 并发线程数：100
    private static final int CONCURRENT_THREAD_COUNT = 100;
    // 1. 准备门闩：等待所有线程准备就绪
    private static final CountDownLatch READY_LATCH = new CountDownLatch(CONCURRENT_THREAD_COUNT);
    // 2. 执行门闩：等待所有线程执行完成
    private static final CountDownLatch FINISH_LATCH = new CountDownLatch(CONCURRENT_THREAD_COUNT);

    // 模拟接口调用
    private static void callApi() {
        new Thread(() -> {
            try {
                // 1. 线程准备就绪，计数器减1
                READY_LATCH.countDown();
                // 2. 等待所有线程准备就绪（确保同时开始执行）
                READY_LATCH.await();

                // 3. 执行接口调用（模拟耗时）
                long start = System.currentTimeMillis();
                Thread.sleep(50); // 模拟接口耗时
                long end = System.currentTimeMillis();

                System.out.println(Thread.currentThread().getName() + "接口执行耗时：" + (end - start) + "ms");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                System.out.println(Thread.currentThread().getName() + "执行被中断");
            } finally {
                // 4. 执行完成，计数器减1
                FINISH_LATCH.countDown();
            }
        }).start();
    }

    public static void main(String[] args) throws InterruptedException {
        // 1. 创建线程池，启动所有测试线程
        ExecutorService executor = Executors.newFixedThreadPool(CONCURRENT_THREAD_COUNT);
        for (int i = 0; i < CONCURRENT_THREAD_COUNT; i++) {
            executor.submit(PerformanceTestDemo::callApi);
        }

        // 2. 等待所有线程准备就绪
        READY_LATCH.await();
        System.out.println("所有线程准备就绪，开始执行接口测试...");
        long totalStart = System.currentTimeMillis();

        // 3. 等待所有线程执行完成
        FINISH_LATCH.await();
        long totalEnd = System.currentTimeMillis();

        // 4. 统计结果
        System.out.println("所有线程执行完成，总耗时：" + (totalEnd - totalStart) + "ms");
        executor.shutdown();
    }
}
核心设计亮点：
双门闩设计：READY_LATCH确保所有线程同时开始执行（避免线程启动时间差影响测试结果），FINISH_LATCH等待所有线程执行完成；
精准统计总耗时，符合并发性能测试的 “公平性” 要求；
线程池管理线程，避免手动创建线程的资源泄漏问题。
四、核心使用细节（面试高频 + 生产必守）
4.1 一次性特性（核心区别）
CountDownLatch的计数器是一次性的：一旦计数器归 0，后续调用await()会直接返回（不再阻塞），调用countDown()也无任何效果。若需要复用 “倒计时” 功能，需重新创建CountDownLatch对象（这是和CyclicBarrier的核心区别）。
示例验证一次性特性：
java
运行
public void testOneTime() throws InterruptedException {
    CountDownLatch latch = new CountDownLatch(1);
    latch.countDown(); // 计数器归0

    // 第一次await：直接返回（不阻塞）
    latch.await();
    System.out.println("第一次await完成");

    // 第二次await：依然直接返回
    latch.await();
    System.out.println("第二次await完成");

    // 再次countDown：无效果
    latch.countDown();
    System.out.println("countDown后计数器值：" + latch.getCount()); // 输出0
}
4.2 超时等待的正确使用（生产必守）
生产中严禁使用无参的await()，必须指定超时时间，避免因子线程卡死（比如死锁、无限循环）导致主线程永久阻塞。
正确写法：
java
运行
// 超时时间根据业务场景设置（比如初始化设30秒，接口测试设10秒）
boolean result = latch.await(30, TimeUnit.SECONDS);
if (result) {
    // 计数器归0，正常处理
} else {
    // 超时处理（比如记录日志、报警、退出程序）
    System.err.println("等待超时，任务未完成");
}
4.3 中断处理（避免线程状态异常）
await()方法会响应线程中断，抛出InterruptedException，捕获异常后必须恢复线程的中断状态（Thread.currentThread().interrupt()），否则会导致后续依赖中断状态的逻辑出错。
正确的中断处理示例：
java
运行
public void testInterrupt() {
    CountDownLatch latch = new CountDownLatch(1);
    Thread thread = new Thread(() -> {
        try {
            latch.await();
        } catch (InterruptedException e) {
            // 恢复中断状态（必做）
            Thread.currentThread().interrupt();
            System.out.println("线程被中断，中断状态：" + Thread.currentThread().isInterrupted()); // 输出true
        }
    });
    thread.start();
    thread.interrupt(); // 中断线程
}
4.4 计数器值的匹配原则
初始化的计数器值必须和需要countDown()的次数严格匹配：
若计数器值 > 子线程数 / 任务数：主线程会永久等待（除非超时）；
若计数器值 < 子线程数 / 任务数：部分子线程的countDown()无意义，但不影响主线程唤醒。
生产建议：计数器值 = 需要等待的任务数（比如 5 个子线程，计数器值设为 5）。
五、避坑指南（生产常见错误）
5.1 误区 1：忘记在 finally 中调用 countDown ()
子线程任务抛出异常时，若未在finally中调用countDown()，会导致计数器无法归 0，主线程永久阻塞（或超时）。
错误示例：
java
运行
// 错误：countDown()不在finally中，任务异常时无法调用
new Thread(() -> {
    System.out.println("执行任务");
    if (1 == 1) {
        throw new RuntimeException("任务异常");
    }
    latch.countDown(); // 异常时不会执行
}).start();
正确示例：
java
运行
// 正确：countDown()在finally中，无论是否异常都会调用
new Thread(() -> {
    try {
        System.out.println("执行任务");
        if (1 == 1) {
            throw new RuntimeException("任务异常");
        }
    } catch (Exception e) {
        System.err.println("任务异常：" + e.getMessage());
    } finally {
        latch.countDown();
    }
}).start();
5.2 误区 2：复用 CountDownLatch 对象
计数器归 0 后，CountDownLatch失效，复用会导致逻辑错误（比如后续await()直接返回，无法等待新任务）。
错误示例：
java
运行
CountDownLatch latch = new CountDownLatch(2);
// 第一次使用
latch.countDown();
latch.countDown();
// 尝试复用：await()直接返回，无法等待新任务
latch.await();
正确示例：
java
运行
// 需要重新创建对象
CountDownLatch latch1 = new CountDownLatch(2);
latch1.countDown();
latch1.countDown();

CountDownLatch latch2 = new CountDownLatch(2); // 新对象
latch2.await();
5.3 误区 3：计数器值设置错误
比如需要等待 5 个子线程，却将计数器值设为 4，导致主线程等待超时（或永久阻塞）。
生产建议：通过常量定义计数器值，避免硬编码错误：
java
运行
// 正确：常量定义，便于维护和核对
private static final int TASK_COUNT = 5;
private static final CountDownLatch latch = new CountDownLatch(TASK_COUNT);
5.4 误区 4：在主线程中调用 countDown ()
误将countDown()写在主线程中，导致计数器提前归 0，主线程无需等待子线程完成就继续执行。
错误示例：
java
运行
CountDownLatch latch = new CountDownLatch(1);
new Thread(() -> {
    try {
        Thread.sleep(1000);
        System.out.println("子线程完成");
    } catch (InterruptedException e) {
        e.printStackTrace();
    }
}).start();
latch.countDown(); // 主线程调用，计数器提前归0
latch.await(); // 直接返回，子线程还未完成
六、CountDownLatch 与 CyclicBarrier 核心对比（面试高频）
CountDownLatch和CyclicBarrier都是 JUC 中用于线程同步的工具，极易混淆，核心区别如下：
特性	CountDownLatch	CyclicBarrier
核心作用	让一个 / 多个线程等待其他线程完成任务	让多个线程互相等待，直到所有线程都到达 “屏障点”
复用性	一次性（计数器归 0 后失效）	可复用（调用reset()重置计数器）
计数器方向	递减（countDown () 减 1）	递增（await () 加 1，直到达到指定值）
等待方	主线程等待子线程（单向等待）	线程之间互相等待（双向等待）
触发动作	计数器归 0 后，唤醒等待线程，无额外动作	达到屏障点后，可执行指定的Runnable（屏障动作）
适用场景	主线程等待子线程初始化、并行任务汇总	多线程阶段任务（比如分阶段处理数据，所有线程完成第一阶段后再开始第二阶段）
记忆口诀：
CountDownLatch：倒计时，一次性，主线等子线程；
CyclicBarrier：循环屏障，可复用，线程互等。
总结
核心定位：CountDownLatch是 JUC 中用于 **“让一个 / 多个线程等待其他线程完成任务”** 的同步工具，基于一次性倒计时计数器实现；
核心用法：初始化计数器值→子线程任务完成后countDown()（必须在 finally 中）→主线程await(timeout, unit)等待→计数器归 0 后执行后续逻辑；
核心特性：一次性、支持超时 / 中断、非独占性，计数器递减是原子操作；
关键原则：严禁使用无参await()、计数器值与任务数匹配、禁止复用对象、countDown()必须在 finally 中；
核心场景：项目启动初始化、多线程并行任务汇总、并发性能测试；
核心区别：与CyclicBarrier相比，CountDownLatch是 “单向等待、一次性”，CyclicBarrier是 “互相等待、可复用”。

CountDownLatch 核心函数源码解析（基于 JDK 8）
一、CountDownLatch 源码整体结构
CountDownLatch的核心逻辑全部封装在内部类Sync 中，Sync继承自 AQS（AbstractQueuedSynchronizer）——JUC 同步工具的核心骨架。先看CountDownLatch的整体源码结构，建立全局认知：
java
运行
package java.util.concurrent;
import java.util.concurrent.locks.AbstractQueuedSynchronizer;

public class CountDownLatch {
    // 核心内部类：继承AQS，实现CountDownLatch的同步逻辑
    private static final class Sync extends AbstractQueuedSynchronizer {
        private static final long serialVersionUID = 4982264981922014374L;

        // Sync构造器：初始化AQS的state（计数器值）
        Sync(int count) {
            setState(count); // AQS的state变量 = CountDownLatch的计数器
        }

        // 获取当前计数器值（对外暴露为CountDownLatch的getCount()）
        int getCount() {
            return getState();
        }

        // 核心：尝试获取共享锁（对应await()）
        @Override
        protected int tryAcquireShared(int acquires) {
            // state=0时返回1（获取成功），否则返回-1（获取失败，进入等待队列）
            return (getState() == 0) ? 1 : -1;
        }

        // 核心：尝试释放共享锁（对应countDown()）
        @Override
        protected boolean tryReleaseShared(int releases) {
            // 循环CAS：保证state原子性递减
            for (;;) {
                int c = getState();
                // 若state已为0，直接返回false（countDown()无效果）
                if (c == 0)
                    return false;
                // 计数器减1
                int nextc = c - 1;
                // CAS更新state：原子操作，避免多线程竞争导致计数错误
                if (compareAndSetState(c, nextc))
                    // 只有当state减到0时，返回true（触发唤醒等待线程）
                    return nextc == 0;
            }
        }
    }

    // CountDownLatch持有Sync的实例（核心逻辑委托给Sync）
    private final Sync sync;

    // ---------------------- CountDownLatch 核心对外方法 ----------------------
    // 1. 构造器：初始化计数器
    public CountDownLatch(int count) {
        if (count < 0) throw new IllegalArgumentException("count < 0");
        this.sync = new Sync(count); // 初始化Sync，设置state=count
    }

    // 2. 核心：等待计数器归0（可中断）
    public void await() throws InterruptedException {
        sync.acquireSharedInterruptibly(1); // 调用AQS的共享模式获取方法（支持中断）
    }

    // 3. 核心：等待计数器归0（带超时）
    public boolean await(long timeout, TimeUnit unit) throws InterruptedException {
        // 调用AQS的共享模式超时获取方法
        return sync.tryAcquireSharedNanos(1, unit.toNanos(timeout));
    }

    // 4. 核心：计数器减1
    public void countDown() {
        sync.releaseShared(1); // 调用AQS的共享模式释放方法
    }

    // 5. 获取当前计数器值
    public long getCount() {
        return sync.getCount();
    }

    // 重写toString，便于调试
    public String toString() {
        return super.toString() + "[Count = " + sync.getCount() + "]";
    }
}
核心前置知识（必懂）
AQS 的state变量：CountDownLatch的计数器本质就是 AQS 的state（int 类型，原子操作），state = 初始化的count值，countDown()就是state-1，await()就是等待state=0。
共享模式：CountDownLatch是 AQS共享模式的典型应用（多个线程可同时await()，计数器归 0 时所有线程被唤醒），区别于ReentrantLock的独占模式。
CAS 操作：compareAndSetState(c, nextc)是原子操作，保证多线程下计数器递减的线程安全，无需额外加锁。

public final void acquireSharedInterruptibly(int arg)
        throws InterruptedException {
    // 1. 检查线程是否被中断：若已中断，抛InterruptedException
    if (Thread.interrupted())
        throw new InterruptedException();
    // 2. 调用Sync重写的tryAcquireShared(arg)：尝试获取共享锁
    if (tryAcquireShared(arg) < 0)
        // 3. 获取失败（state≠0），进入AQS等待队列并阻塞
        doAcquireSharedInterruptibly(arg);
}

第三步：AQS 的doAcquireSharedInterruptibly(int arg)（核心阻塞逻辑）
这是 AQS 的底层实现，作用是：将当前线程加入 AQS 的等待队列，挂起线程，直到state=0被唤醒。核心源码简化版（保留关键逻辑）：

private void doAcquireSharedInterruptibly(int arg)
    throws InterruptedException {
    // 1. 将当前线程封装为共享模式的节点，加入AQS等待队列尾部
    final Node node = addWaiter(Node.SHARED);
    boolean failed = true;
    try {
        for (;;) {
            // 2. 获取当前节点的前驱节点
            final Node p = node.predecessor();
            if (p == head) {
                // 3. 再次尝试获取（双重检查）
                int r = tryAcquireShared(arg);
                if (r >= 0) {
                    // 4. 获取成功（state=0）：唤醒后续等待线程，退出循环
                    setHeadAndPropagate(node, r);
                    p.next = null; // help GC
                    failed = false;
                    return;
                }
            }
            // 5. 获取失败：挂起当前线程（LockSupport.park()），等待被唤醒
            if (shouldParkAfterFailedAcquire(p, node) &&
                parkAndCheckInterrupt())
                // 6. 若线程被中断，抛InterruptedException
                throw new InterruptedException();
        }
    } finally {
        if (failed)
            cancelAcquire(node);
    }
}
await()整体逻辑总结（通俗版）：
调用await()的线程先检查自己是否被中断，若中断则抛异常；
检查state是否为 0：
是 → 直接返回（无需等待）；
否 → 进入 AQS 等待队列，线程被挂起（暂停执行）；
直到其他线程调用countDown()将state减到 0，该线程会被唤醒，继续执行。

public final boolean releaseShared(int arg) {
    // 1. 调用Sync重写的tryReleaseShared(arg)：尝试释放共享锁
    if (tryReleaseShared(arg)) {
        // 2. 释放成功（state=0）：唤醒AQS等待队列中的所有线程

第二步：Sync 重写的tryReleaseShared(int releases)（核心）

protected boolean tryReleaseShared(int releases) {
    // 死循环+CAS：保证state原子性递减（多线程安全）
    for (;;) {
        // 1. 获取当前state值
        int c = getState();
        // 2. 若state已为0，返回false（countDown()无效果）
        if (c == 0)
            return false;
        // 3. 计数器减1
        int nextc = c - 1;
        // 4. CAS更新state：原子操作，失败则循环重试
        if (compareAndSetState(c, nextc))
            // 5. 只有当state减到0时，返回true（触发唤醒等待线程）
            return nextc == 0;
    }
}
第三步：AQS 的doReleaseShared()（唤醒等待线程）
这是 AQS 的底层实现，作用是：当state=0时，唤醒 AQS 等待队列中的所有线程。核心源码简化版：
java
运行
private void doReleaseShared() {
    for (;;) {
        Node h = head;
        if (h != null && h != tail) {
            int ws = h.waitStatus;
            // 1. 若头节点状态为SIGNAL（表示需要唤醒后继节点）
            if (ws == Node.SIGNAL) {
                // 2. CAS修改头节点状态，避免重复唤醒
                if (!compareAndSetWaitStatus(h, Node.SIGNAL, 0))
                    continue;
                // 3. 唤醒头节点的后继线程（LockSupport.unpark()）
                unparkSuccessor(h);
            }
            // 4. 传播唤醒：确保所有等待线程都被唤醒
            else if (ws == 0 &&
                     !compareAndSetWaitStatus(h, 0, Node.PROPAGATE))
                continue;
        }
        if (h == head) // 头节点未变化，退出循环
            break;
    }
}
countDown()整体逻辑总结（通俗版）：
线程调用countDown()，进入 AQS 的releaseShared方法；
通过 “死循环 + CAS” 原子性地将state减 1：
若减 1 后state≠0 → 返回 false，不做其他操作；
若减 1 后state=0 → 返回 true，触发doReleaseShared()；
doReleaseShared()唤醒 AQS 等待队列中的所有线程（所有调用await()的线程被唤醒）。

三、核心源码关键细节（面试高频）
3.1 为什么CountDownLatch是 “一次性” 的？
从源码可见：state一旦被减到 0，后续调用：
tryAcquireShared()永远返回 1（await()直接返回，不再阻塞）；
tryReleaseShared()永远返回 false（countDown()无任何效果）；
AQS 没有提供 “重置 state” 的方法，因此CountDownLatch无法复用，只能重新创建对象。
3.2 为什么countDown()必须用 “死循环 + CAS”？
java
运行
for (;;) {
    int c = getState();
    if (c == 0) return false;
    int nextc = c - 1;
    if (compareAndSetState(c, nextc))
        return nextc == 0;
}
多线程并发调用countDown()时，CAS 可能失败（比如线程 A 和 B 同时读取c=5，A 先 CAS 成功将c改为 4，B 的 CAS 就会失败）；
死循环会让 CAS 失败的线程重新读取最新的state，再次尝试 CAS，直到成功 —— 这是 JUC 中实现原子操作的标准写法，比加锁更高效。
3.3 await()的中断响应逻辑
await()调用的acquireSharedInterruptibly()会先检查线程中断状态：
java
运行
if (Thread.interrupted())
    throw new InterruptedException();
若线程在await()期间被中断（其他线程调用thread.interrupt()），会立即抛InterruptedException，并退出等待；
捕获异常后必须恢复中断状态（Thread.currentThread().interrupt()），否则会丢失中断信号。
3.4 共享模式的 “传播唤醒”
doReleaseShared()中的setHeadAndPropagate(node, r)和PROPAGATE状态，是为了保证所有等待线程都被唤醒：
当state=0时，不仅唤醒头节点的后继线程，还会 “传播” 唤醒后续所有节点的线程；
这是共享模式和独占模式的核心区别（独占模式只唤醒一个线程，共享模式唤醒所有线程）。
四、源码层面的避坑点（生产必守）
4.1 为什么countDown()必须放在finally中？
从源码看，若子线程任务抛出异常，未调用countDown()，则state无法减到 0，await()的线程会永久阻塞（或超时）。比如：
java
运行
// 错误：countDown()未在finally中，异常时无法调用
new Thread(() -> {
    if (1 == 1) throw new RuntimeException("异常");
    latch.countDown(); // 不会执行，state永远≠0
}).start();
源码层面的后果：tryReleaseShared()从未被调用，state保持初始值，await()的线程永远卡在doAcquireSharedInterruptibly()的parkAndCheckInterrupt()处。
4.2 为什么不能复用CountDownLatch？
源码中state归 0 后：
tryAcquireShared()永远返回 1 → await()直接返回；
tryReleaseShared()永远返回 false → countDown()无效果；
AQS 的state是private volatile int，无公开方法重置，因此只能重新创建CountDownLatch对象。
4.3 为什么getCount()不能用于业务逻辑判断？
getCount()只是瞬间读取state值，源码中无任何锁保护：
java
运行
int getCount() {
    return getState(); // 直接返回state，无原子性保证
}
比如：
java
运行
if (latch.getCount() == 1) {
    // 此处可能被其他线程的countDown()修改，导致逻辑错误
    latch.countDown();
}
源码层面的问题：getCount()和countDown()之间无原子性，多线程下会出现 “检查 - 执行” 的竞态条件。
总结
核心源码关键点（必记）
CountDownLatch的核心是AQS 的共享模式，state作为倒计时计数器，await()等待state=0，countDown()原子性减state；
await()的底层是acquireSharedInterruptibly() → tryAcquireShared()（判断state=0） → doAcquireSharedInterruptibly()（挂起线程）；
countDown()的底层是releaseShared() → tryReleaseShared()（CAS 减state） → doReleaseShared()（state=0时唤醒所有等待线程）；
“死循环 + CAS” 保证计数器递减的线程安全，finally中调用countDown()保证计数器能归 0；
一次性的根源：state归 0 后无法重置，AQS 无公开方法修改state。
