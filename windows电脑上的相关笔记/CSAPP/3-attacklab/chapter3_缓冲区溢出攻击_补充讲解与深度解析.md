### 1.1 x86-64 栈帧结构

#### 1.1.1 栈的基本概念

栈（Stack）是程序运行时最重要的数据结构之一。在 x86-64 体系结构中，栈具有以下核心特性：

- **增长方向**：栈从高地址向低地址增长。这意味着新压入栈的数据位于更低的内存地址。
- **栈指针**：`%rsp`（Stack Pointer）寄存器始终指向栈顶元素（即最后一个压入的数据）。
- **栈的操作**：仅支持两种基本操作——push（压栈）和 pop（出栈），遵循后进先出（LIFO）原则。

在内存中的布局示意：

```
高地址 0xFFFFFFFFFFFFFFFF
  ┌──────────────────────────┐
  │          ...              │
  │   命令行参数与环境变量     │
  │          ...              │
  ├──────────────────────────┤
  │       栈 (Stack)          │ ← 栈从高地址向低地址增长
  │         ↓↓↓               │    （向低地址方向扩展）
  │                           │
  │     [当前栈帧]             │ ← %rsp 指向这里
  │                           │
  ├──────────────────────────┤
  │   共享库映射区              │
  ├──────────────────────────┤
  │   堆 (Heap)               │ ← 堆向高地址增长
  │         ↑↑↑               │
  ├──────────────────────────┤
  │   BSS 段（未初始化数据）    │
  ├──────────────────────────┤
  │   数据段（已初始化数据）     │
  ├──────────────────────────┤
  │   代码段（Text）           │
  └──────────────────────────┘
低地址 0x0000000000000000
```

#### 1.1.2 push 操作的详细机制

`push` 指令将一个值压入栈中。以 `pushq %rax` 为例，它等价于以下两步操作：

```assembly
subq   $8, %rsp          # 第一步：栈指针减 8（向下移动一个 64 位槽位）
movq   %rax, (%rsp)      # 第二步：将值存入栈指针指向的内存位置
```

需要注意的要点：

1. **先减后写**：`push` 指令是原子操作，但在逻辑上先减少 `%rsp`，再写入数据。这意味着 `push` 执行后，`%rsp` 指向新压入的数据。
2. **地址递减**：每次 `push` 使 `%rsp` 减少 8（64 位模式下），因为栈向低地址增长。
3. **对齐**：`push` 操作保证 `%rsp` 始终是 8 字节对齐的（如果初始对齐的话）。

多个连续 `push` 的效果：

```assembly
pushq $0xAAAA            # rsp -= 8; *rsp = 0xAAAA
pushq $0xBBBB            # rsp -= 8; *rsp = 0xBBBB
pushq $0xCCCC            # rsp -= 8; *rsp = 0xCCCC
# 此时栈布局（从高地址到低地址）：
#   [0xAAAA] [0xBBBB] [0xCCCC] ← rsp 指向 0xCCCC
```

#### 1.1.3 pop 操作的详细机制

`pop` 指令从栈顶弹出一个值。以 `popq %rax` 为例，它等价于：

```assembly
movq   (%rsp), %rax      # 第一步：从栈顶读取值到目标寄存器
addq   $8, %rsp          # 第二步：栈指针加 8（向上移动一个槽位）
```

需要注意的要点：

1. **先读后增**：先读取 `%rsp` 指向的值，然后增加 `%rsp`。
2. **内存未清除**：`pop` 后，原来栈顶的数据仍然留在内存中，只是 `%rsp` 不再指向它。这片内存可能会被后续的 `push` 覆盖。
3. **pop 不等于 delete**：理解这一点对缓冲区溢出攻击至关重要——函数返回后，栈上的数据并没有消失，只是 `%rsp` 移动了。

#### 1.1.4 call 操作的详细机制

`call` 指令用于函数调用。以 `call func` 为例，它等价于：

```assembly
pushq  %rip_after_call    # 第一步：将 call 指令的下一条指令地址压栈（作为返回地址）
jmp    func               # 第二步：跳转到目标函数
```

详细说明：

1. **返回地址**：`call` 压入的返回地址是 `call` 指令**之后**的那条指令的地址，即函数正常返回后应该继续执行的位置。
2. **rip 的变化**：在 `call` 执行时，`%rip` 已经指向了下一条指令（因为 x86 采用流水线取指，`%rip` 总是指向下一条要执行的指令）。`call` 压入的正是这个 `%rip` 的值。
3. **栈的变化**：`call` 执行后，`%rsp` 减少了 8，栈顶多了一个 8 字节的返回地址。

示例：

```assembly
0x400540: callq 0x400560    # 调用 func
0x400545: movq $1, %rax     # 返回后执行这条（返回地址 = 0x400545）
```

执行 `call` 后的栈：

```
          ↓ rsp
  ┌───────────────────┐
  │    0x0000000000400545   │  ← 返回地址（call 指令的下一条指令）
  ├───────────────────┤
  │   caller 的栈帧     │
  └───────────────────┘
```

#### 1.1.5 ret 操作的详细机制

`ret` 指令用于函数返回。它等价于：

```assembly
popq   %rip               # 从栈顶弹出返回地址到 %rip，实现跳转
```

详细说明：

1. **弹出返回地址**：`ret` 从栈顶弹出一个 8 字节的值，将其加载到 `%rip`，CPU 接着从该地址取指执行。
2. **缓冲区溢出的核心**：如果攻击者能够覆写栈上的返回地址，那么 `ret` 执行时就会跳转到攻击者指定的地址——这就是 ret2text、ret2shellcode、ROP 等攻击的基本原理。
3. **控制流劫持**：`ret` 是攻击者最关注的指令，因为它从栈上读取数据作为跳转目标。

```
  rbp →   ├────────────────────────────┤
          │      临时存储区              │  ← 偏移 -8
          ├────────────────────────────┤
          │      ...                    │
          ├────────────────────────────┤
          │      栈帧对齐填充            │
  rsp →   ├────────────────────────────┤
          │                            │

```

更精确的布局，考虑 System V ABI 的调用约定：

```
高地址
          ┌───────────────────────────────────────┐
          │   第 n 个栈参数（n > 6）               │  ← caller 的栈帧顶部
          │   第 8 个参数 h          [rsp+7*8]    │
          │   第 7 个参数 g          [rsp+6*8]    │
          ├───────────────────────────────────────┤  ← caller 的 rsp 在 call 前
          │   返回地址 (Return Address)             │  ← call 指令自动压入
          ├───────────────────────────────────────┤
          │   保存的 %rbp (Old Frame Pointer)      │  ← push %rbp
          ├───────────────────────────────────────┤
          │   Callee 的局部变量 / 保存的寄存器      │
          │   ...                                  │
          │   ...                                  │
          ├───────────────────────────────────────┤
          │   对齐填充 (Padding)                    │
  rsp →   └───────────────────────────────────────┘
低地址
```

关键偏移量总结：

| 相对于 callee 的 `%rbp` | 内容 |
|:---:|:---|
| +24 | 返回地址 |
| +16 | 旧 %rbp（如果有） |
| +8 | 局部变量（如果有） |
| 0 | callee 的 %rbp 指向处 |
| -8 | 局部变量 / 临时值 |
| -N | 栈帧底部（%rsp 指向处） |

注意：以上偏移是**有 %rbp 帧指针**的情况。如果编译器省略帧指针（`-fomit-frame-pointer`），布局会有所不同。

#### 1.1.7 有 rbp vs 无 rbp（-fomit-frame-pointer）的对比

**有帧指针（使用 %rbp）的函数序言和尾声**：

```assembly
# 函数序言 (prologue)
pushq   %rbp               # 保存调用者的帧指针
movq    %rsp, %rbp          # 设置当前函数的帧指针
subq    $N, %rsp            # 分配局部变量空间

# ... 函数体 ...

# 函数尾声 (epilogue)
movq    %rbp, %rsp          # 恢复栈指针（等价于 leave 的前半部分）
popq    %rbp                # 恢复调用者的帧指针（等价于 leave 的后半部分）
ret                        # 返回
```

**无帧指针（-fomit-frame-pointer）的函数序言和尾声**：

```assembly
# 函数序言 (prologue)
subq    $N, %rsp            # 直接分配局部变量空间，不使用 %rbp

# ... 函数体 ...
# 所有局部变量通过 %rsp + offset 访问

# 函数尾声 (epilogue)
addq    $N, %rsp            # 直接释放局部变量空间
ret                        # 返回
```

两种方式的对比：

| 特性 | 有 %rbp | 无 %rbp |
|:---|:---|:---|
| 函数序言 | push %rbp; mov %rsp,%rbp; sub $N,%rsp | sub $N,%rsp |
| 函数尾声 | leave; ret | add $N,%rsp; ret |
| 局部变量访问 | %rbp - offset | %rsp + offset |
| 栈回溯 | 简单（%rbp 链） | 需要 DWARF 调试信息 |
| 寄存器使用 | 多用 %rbp | %rbp 可作为通用寄存器 |
| 代码大小 | 略大 | 略小 |
| 调试便利性 | 高 | 低 |
| GCC 默认 | -O0 时使用 | -O1 及以上使用 |
| GDB backtrace | 直接可用 | 需要调试信息 |

对 Attack Lab 的影响：

- Attack Lab 使用了 `-fomit-frame-pointer` 编译选项，因此你在反汇编中看不到 `push %rbp` 和 `mov %rsp, %rbp`。
- 局部变量全部通过 `%rsp + offset` 访问，这是计算缓冲区溢出偏移量的关键。
- 没有帧指针意味着 `%rbp` 在函数中可能被用作通用寄存器，也可能保存了调用者的 `%rbp`（如果函数需要）。

#### 1.1.8 函数调用示例 1：简单函数调用

考虑以下 C 代码：

```c
int add(int a, int b) {
    int result = a + b;
    return result;
}

int main() {
    int sum = add(3, 5);
    return sum;
}
```

对应的汇编代码（-O0 级别）：

```assembly
# ---- add 函数 ----
add:
    pushq   %rbp                # 保存旧帧指针
    movq    %rsp, %rbp          # 设置新帧指针
    movl    %edi, -4(%rbp)      # 保存参数 a 到栈上
    movl    %esi, -8(%rbp)      # 保存参数 b 到栈上
    movl    -4(%rbp), %edx      # 加载 a
    movl    -8(%rbp), %eax      # 加载 b
    addl    %edx, %eax          # a + b
    movl    %eax, -12(%rbp)     # 存储到 result
    movl    -12(%rbp), %eax     # 设置返回值
    popq    %rbp                # 恢复帧指针
    ret                         # 返回

# ---- main 函数 ----
main:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $16, %rsp            # 分配栈空间
    movl    $5, %esi             # 第二个参数
    movl    $3, %edi             # 第一个参数
    call    add                  # 调用 add 函数
    movl    %eax, -4(%rbp)      # 保存返回值到 sum
    movl    -4(%rbp), %eax      # 设置 main 的返回值
    leave
    ret
```

调用 `add(3, 5)` 时栈的变化过程：

**步骤 1：call 指令前（main 的栈帧）**

```
          ┌──────────────────────────────┐
  rbp →   │  main 的旧 %rbp               │
          ├──────────────────────────────┤
          │  sum (未初始化)               │   ← -4(%rbp)
          ├──────────────────────────────┤
          │  对齐填充                     │
  rsp →   └──────────────────────────────┘
```

**步骤 2：参数传递（通过寄存器）**

```
%edi = 3  (第一个参数)
%esi = 5  (第二个参数)
```

**步骤 3：call add 执行后**

```
          ┌──────────────────────────────┐
  main:   │  main 的旧 %rbp               │
  rbp →   ├──────────────────────────────┤
          │  sum (未初始化)               │
          ├──────────────────────────────┤
          │  对齐填充                     │
          ├──────────────────────────────┤
          │  返回地址 (call 后的指令地址)   │  ← call 压入
  rsp →   └──────────────────────────────┘
```

**步骤 4：add 函数序言执行后**

```
          ┌──────────────────────────────┐
          │  main 的旧 %rbp               │
          ├──────────────────────────────┤
          │  sum (未初始化)               │
          ├──────────────────────────────┤
          │  对齐填充                     │
          ├──────────────────────────────┤
          │  返回地址                      │
          ├──────────────────────────────┤
  add:    │  main 的 %rbp（被 push 保存） │  ← push %rbp
  rbp →   ├──────────────────────────────┤
          │  a = 3                       │  ← -4(%rbp)
          ├──────────────────────────────┤
          │  b = 5                       │  ← -8(%rbp)
          ├──────────────────────────────┤
          │  result = 8                  │  ← -12(%rbp)
  rsp →   └──────────────────────────────┘
```

**步骤 5：add 函数返回后**

```
%eax = 8 (返回值)

栈恢复到步骤 1 的状态（rsp 回到 main 的栈帧底部）
```

#### 1.1.9 函数调用示例 2：超过 6 个参数的调用

考虑以下 C 代码：

```c
int func(int a, int b, int c, int d, int e, int f, int g, int h) {
    return a + b + c + d + e + f + g + h;
}

int main() {
    int result = func(1, 2, 3, 4, 5, 6, 7, 8);
    return result;
}
```

调用 `func(1, 2, 3, 4, 5, 6, 7, 8)` 时的参数传递：

```
参数 1 → %edi = 1      （第 1 个整数参数寄存器）
参数 2 → %esi = 2      （第 2 个整数参数寄存器）
参数 3 → %edx = 3      （第 3 个整数参数寄存器）
参数 4 → %ecx = 4      （第 4 个整数参数寄存器）
参数 5 → %r8d = 5      （第 5 个整数参数寄存器）
参数 6 → %r9d = 6      （第 6 个整数参数寄存器）
参数 7 → [rsp+0] = 7   （第 7 个参数，通过栈传递）
参数 8 → [rsp+8] = 8   （第 8 个参数，通过栈传递）
```

main 函数在调用前的汇编代码：

```assembly
# 传递栈参数（注意顺序：从右到左压栈，或者直接通过 mov 写入）
movl    $8, (%rsp)          # 第 8 个参数（最右边的栈参数先放）
movl    $7, 8(%rsp)         # 第 7 个参数
# 传递寄存器参数
movl    $6, %r9d            # 第 6 个参数
movl    $5, %r8d            # 第 5 个参数
movl    $4, %ecx            # 第 4 个参数
movl    $3, %edx            # 第 3 个参数
movl    $2, %esi            # 第 2 个参数
movl    $1, %edi            # 第 1 个参数
call    func
```

等等，这里需要注意栈参数的放置顺序。在 System V ABI 中，栈参数从右到左压栈，所以：

```
          ┌──────────────────────────────┐
          │  第 8 个参数 h = 8            │  ← %rsp + 8（更靠近高地址）
          ├──────────────────────────────┤
          │  第 7 个参数 g = 7            │  ← %rsp + 0（更靠近低地址）
          ├──────────────────────────────┤
          │  返回地址                      │  ← call 压入
  rsp →   └──────────────────────────────┘
```

在 func 内部访问参数的方式（假设有帧指针）：

```assembly
movl    16(%rbp), %eax      # 访问第 7 个参数 g（跳过返回地址和旧 rbp）
movl    24(%rbp), %eax      # 访问第 8 个参数 h
```

**为什么是 16 和 24？** 因为从 `%rbp` 向上依次是：

```
%rbp + 0:  旧 %rbp
%rbp + 8:  返回地址
%rbp + 16: 第 7 个参数 g（最先压栈的栈参数）
%rbp + 24: 第 8 个参数 h（最后压栈的栈参数）
```

#### 1.1.10 练习题

**练习题 1**：假设函数 `foo` 的栈帧如下（无帧指针），`%rsp` 初始值为 `0x7fffffffe200`：

```assembly
foo:
    subq    $32, %rsp           # 分配 32 字节局部变量空间
    movq    %rdi, -8(%rsp)      # 保存第一个参数
    movq    %rsi, -16(%rsp)     # 保存第二个参数
    # ... 函数体 ...
    addq    $32, %rsp           # 释放栈空间
    ret
```

问题：在 `subq $32, %rsp` 执行后，`%rsp` 的值是多少？参数分别存储在什么地址？

<details>
<summary>参考答案</summary>

- `%rsp` 的新值 = `0x7fffffffe200 - 32 = 0x7fffffffe1e0`
- 第一个参数存储地址 = `0x7fffffffe1e0 - 8 = 0x7fffffffe1d8`（即 `-8(%rsp)` = `%rsp + (-8)`）
- 等等，注意：`-8(%rsp)` 是 `%rsp - 8`，即 `0x7fffffffe1e0 - 8 = 0x7fffffffe1d8`

等等，这里有个常见的混淆。`-8(%rsp)` 表示 `%rsp` 减去 8 的地址，也就是比 `%rsp` 更低的地址。但 `subq $32, %rsp` 后，`%rsp = 0x7fffffffe1e0`，而 `-8(%rsp) = 0x7fffffffe1d8`。

实际上，在许多编译器输出中，局部变量的偏移是正的（相对于分配后的 `%rsp`），例如 `24(%rsp)` 表示 `%rsp + 24`。上面的例子中，`-8(%rsp)` 更像是在红区中使用，或者是在分配栈空间之前访问。

让我修正一下：更常见的模式是：

```assembly
foo:
    subq    $32, %rsp           # 分配 32 字节局部变量空间
    movq    %rdi, 24(%rsp)      # 保存第一个参数到栈顶附近
    movq    %rsi, 16(%rsp)      # 保存第二个参数
    # ... 函数体 ...
    addq    $32, %rsp
    ret
```

在这种情况下：
- `%rsp = 0x7fffffffe1e0`
- 第一个参数地址 = `0x7fffffffe1e0 + 24 = 0x7fffffffe1f8`
- 第二个参数地址 = `0x7fffffffe1e0 + 16 = 0x7fffffffe1f0`

</details>

**练习题 2**：在 Attack Lab 中，函数 `getbuf` 的反汇编如下：

```assembly
00000000004017a8 <getbuf>:
  4017a8:  48 83 ec 28          sub    $0x28,%rsp
  4017ac:  48 89 e7             mov    %rsp,%rdi
  4017af:  e8 5c 02 00 00       callq  401a10 <Gets>
  4017b4:  b8 01 00 00 00       mov    $0x1,%eax
  4017b9:  48 83 c4 28          add    $0x28,%rsp
  4017bd:  c3                   retq
```

问题：
1. `getbuf` 分配了多少字节的局部变量空间？
2. 缓冲区的起始地址在哪里（相对于 `%rsp`）？
3. 返回地址存储在栈上的什么位置（相对于缓冲区起始地址的偏移量）？
4. 如果要覆盖返回地址，需要输入多少字节的数据？

<details>
<summary>参考答案</summary>

1. `sub $0x28, %rsp` → 分配了 `0x28 = 40` 字节。
2. `mov %rsp, %rdi` 后调用 `Gets`，说明缓冲区起始地址就是 `%rsp`（即分配空间后的 `%rsp`）。
3. 返回地址在 `%rsp + 0x28` 的位置（因为 `sub $0x28, %rsp` 分配了 0x28 字节，返回地址紧挨着分配空间的上方）。
4. 需要填充 40 字节（覆盖缓冲区和局部变量空间）+ 8 字节（覆盖保存的返回地址前不需要覆盖其他东西，因为没有帧指针）... 等等，实际上返回地址就在 `%rsp + 0x28` 处，所以要覆盖返回地址需要 40 字节填充 + 8 字节新返回地址 = 48 字节。但仅覆盖缓冲区到返回地址之前，需要 40 字节的填充，然后第 41-48 字节就是新的返回地址。

</details>

### 1.2 System V AMD64 ABI

#### 1.2.1 什么是 ABI

ABI（Application Binary Interface，应用程序二进制接口）定义了编译后的机器代码之间的接口规范。它规定了：

- 函数参数如何传递
- 返回值如何传递
- 哪些寄存器由调用者保存，哪些由被调用者保存
- 栈帧的布局规则
- 栈对齐要求

x86-64 Linux 系统遵循的是 **System V AMD64 ABI**，这是 Unix/Linux 系统的标准调用约定。Windows 有自己不同的调用约定（Microsoft x64 Calling Convention），两者不兼容。

#### 1.2.2 整数参数传递寄存器

在 System V AMD64 ABI 中，函数的前 6 个整数/指针参数通过以下寄存器传递（按顺序）：

| 参数序号 | 寄存器 | 64 位名 | 32 位名 | 16 位名 | 8 位名（低） | 8 位名（高） |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 1 | rdi | %rdi | %edi | %di | %dil | - |
| 2 | rsi | %rsi | %esi | %si | %sil | - |
| 3 | rdx | %rdx | %edx | %dx | %dl | %dh |
| 4 | rcx | %rcx | %ecx | %cx | %cl | %ch |
| 5 | r8 | %r8 | %r8d | %r8w | %r8b | - |
| 6 | r9 | %r9 | %r9d | %r9w | %r9b | - |

记忆口诀（按顺序）：**R**DI, **R**SI, **R**DX, **R**CX, **R**8, **R**9

在 Attack Lab 中最常见的用法：

- `mov %rsp, %rdi` → 将栈指针作为第一个参数传给 `Gets`
- 在 ROP 中通过 `pop rdi; ret` gadget 设置函数参数

#### 1.2.3 浮点参数传递寄存器

浮点参数通过 SSE 寄存器传递：

| 参数序号 | 寄存器 |
|:---:|:---:|
| 1 | %xmm0 |
| 2 | %xmm1 |
| 3 | %xmm2 |
| 4 | %xmm3 |
| 5 | %xmm4 |
| 6 | %xmm5 |
| 7 | %xmm6 |
| 8 | %xmm7 |

每个 %xmm 寄存器为 128 位宽，可以存放：
- 一个单精度浮点数（float, 32 位）
- 一个双精度浮点数（double, 64 位）
- 一组打包的浮点数（SIMD）

整数和浮点参数的寄存器分配是**独立计数**的。例如：

```c
void func(int a, double b, int c, double d);
// a → %edi,  b → %xmm0,  c → %esi,  d → %xmm1
```

注意：整数参数用整数寄存器计数，浮点参数用 SSE 寄存器计数，两者互不影响。

#### 1.2.4 超过 6 个参数走栈传递

当一个函数的整数参数超过 6 个时，第 7 个及以后的参数通过栈传递。

栈参数的放置规则：

1. **压栈顺序**：从第 7 个参数开始，按参数声明顺序从左到右依次放置在栈上。
2. **放置位置**：在执行 `call` 指令之前，调用者需要将栈参数放在栈顶。
3. **栈参数的访问**：被调用函数通过 `%rbp + 16 + 8*n` 访问第 `n+7` 个参数（从第 7 个开始）。

示例：

```c
void func(int a, int b, int c, int d, int e, int f, int g, int h);
```

调用 `func(1, 2, 3, 4, 5, 6, 7, 8)` 时的完整参数布局：

```
寄存器参数：
  a=1 → %edi
  b=2 → %esi
  c=3 → %edx
  d=4 → %ecx
  e=5 → %r8d
  f=6 → %r9d

栈参数（call 指令前 caller 的栈布局）：
                ┌─────────────────┐
                │   h = 8          │  ← [rsp + 8]  （第 8 个参数）
                ├─────────────────┤
                │   g = 7          │  ← [rsp + 0]  （第 7 个参数）
  rsp →         └─────────────────┘
```

在 func 内部（有帧指针时）访问栈参数：

```
%rbp + 16:  第 7 个参数 g
%rbp + 24:  第 8 个参数 h
```

为什么偏移从 16 开始？因为 `%rbp + 0` 是旧 `%rbp`，`%rbp + 8` 是返回地址。

#### 1.2.5 返回值传递

**整数/指针返回值**：

- 通过 `%rax` 返回。
- 如果返回值是 128 位整数（如 `__int128`），低 64 位在 `%rax`，高 64 位在 `%rdx`。

**浮点返回值**：

- 通过 `%xmm0` 返回。
- 如果返回值是双精度浮点数对，`%xmm0` 返回第一个，`%xmm1` 返回第二个。

**结构体返回值**：

- 小结构体（≤16 字节）可以通过寄存器返回。
- 大结构体：调用者分配空间，将地址作为第一个隐含参数（在 `%rdi` 中）传递给被调用函数。

返回值约定总结：

| 返回值类型 | 返回位置 |
|:---|:---|
| 整数/指针（≤64 位） | %rax |
| 128 位整数 | %rax（低 64 位）+ %rdx（高 64 位） |
| 浮点数（float/double） | %xmm0 |
| 小结构体（≤16 字节，2 个寄存器） | %rax + %rdx（或 %xmm0 + %xmm1） |
| 大结构体 | 隐含第一参数 %rdi 指向的内存 |

#### 1.2.6 Callee-saved 寄存器

Callee-saved 寄存器（被调用者保存）意味着：如果一个函数使用了这些寄存器，它必须在返回前恢复其原始值。通常的做法是在函数序言中 `push` 这些寄存器，在尾声中 `pop` 恢复。

Callee-saved 寄存器列表：

| 寄存器 | 用途 |
|:---:|:---|
| %rbx | 通用寄存器，常用于保存局部变量 |
| %rbp | 帧指针 / 通用寄存器 |
| %r12 | 通用寄存器 |
| %r13 | 通用寄存器 |
| %r14 | 通用寄存器 |
| %r15 | 通用寄存器 |
| %rsp | 栈指针（特殊，必须保存） |

记忆口诀：**RBX, RBP, R12-R15**（6 个通用 callee-saved 寄存器 + RSP）

在 Attack Lab 中的重要性：

- ROP gadget 经常来自 callee-saved 寄存器的 `pop` 指令。例如 `pop %rbx; ret`、`pop %r12; ret` 等。
- 这些 gadget 的存在是因为编译器在函数尾声中恢复 callee-saved 寄存器。
- 在 ROP 链中，我们可以利用这些 `pop` gadget 来设置寄存器的值。

#### 1.2.7 Caller-saved 寄存器

Caller-saved 寄存器（调用者保存）意味着：调用函数前，如果调用者需要保留这些寄存器的值，必须在调用前自行保存。被调用函数可以自由修改这些寄存器而不需要恢复。

Caller-saved 寄存器列表：

| 寄存器 | 用途 |
|:---:|:---|
| %rax | 返回值 |
| %rcx | 第 4 个参数 / 计数器 |
| %rdx | 第 3 个参数 / I/O |
| %rsi | 第 2 个参数 / 源索引 |
| %rdi | 第 1 个参数 / 目标索引 |
| %r8 | 第 5 个参数 |
| %r9 | 第 6 个参数 |
| %r10 | 通用 / PLC |
| %r11 | 通用 |

注意：`%r10` 和 `%r11` 不属于参数传递寄存器，但也是 caller-saved 的。

#### 1.2.8 红区（Red Zone）

红区是 x86-64 System V ABI 中的一个特殊概念：

**定义**：在 `%rsp` 以下的 128 字节区域（`%rsp - 128` 到 `%rsp - 1`）被称为红区。

**规则**：信号处理程序和操作系统不会修改这片区域。因此，叶子函数（leaf function，即不调用其他函数的函数）可以不修改 `%rsp` 就直接使用这片区域作为临时存储。

红区的示意：

```
          ┌─────────────────────────────┐
          │   函数的正式栈帧              │
  rsp →   ├─────────────────────────────┤
          │   红区字节 0                 │  ← rsp - 1
          │   红区字节 1                 │  ← rsp - 2
          │   ...                       │
          │   红区字节 127               │  ← rsp - 128
          └─────────────────────────────┘
```

**叶子函数使用红区的示例**：

```assembly
# 普通函数需要 sub rsp, N 来分配空间
# 叶子函数可以直接使用红区，无需修改 rsp
leaf_func:
    movq    %rdi, -8(%rsp)      # 直接写入红区，无需 sub rsp
    # ... 使用 -8(%rsp) 到 -16(%rsp) 等
    movq    -8(%rsp), %rax
    ret
```

**红区对 Attack Lab 的影响**：

1. Attack Lab 的目标程序不是叶子函数，所以通常不使用红区。
2. 但了解红区很重要，因为如果函数是叶子函数，它的局部变量可能在 `%rsp` 以下，这会影响缓冲区溢出的偏移量计算。
3. 在信号处理相关的攻击中，红区的内容可能被信号处理程序覆盖。
4. 可以通过 `-mno-red-zone` 编译选项禁用红区。

#### 1.2.9 可变参数函数

可变参数函数（如 `printf`、`scanf`）在调用时有特殊的 ABI 要求：

**%al 寄存器的作用**：

- `%al`（`%rax` 的最低字节）必须设置为本次调用中使用了多少个 SSE 寄存器来传递浮点参数。
- 即使没有浮点参数，也必须设置 `%al = 0`。
- 这是编译器在调用可变参数函数时自动生成的代码。

示例：

```c
printf("%d %f %d %f", 1, 2.0, 3, 4.0);
```

对应的汇编：

```assembly
movl    $4, %eax             # al = 4，因为使用了 4 个 xmm 寄存器
                        # （xmm0, xmm1, xmm2, xmm3 传递 4 个浮点值）
movsd   ...,%xmm3            # 第 4 个浮点参数
movsd   ...,%xmm2            # 第 3 个浮点参数
movsd   ...,%xmm1            # 第 2 个浮点参数
movsd   ...,%xmm0            # 第 1 个浮点参数
movl    $3, %edx             # 第 3 个整数参数
movl    $1, %esi             # 第 1 个整数参数
leaq    ...,%rdi              # 格式字符串
call    printf
```

**为什么这很重要？** 在 Attack Lab 的 ROP 链中，如果我们需要调用 `printf` 或其他可变参数函数，必须正确设置 `%al`。如果 `%al` 的值不正确，`printf` 可能会从错误的位置读取浮点参数，导致参数解析混乱，进而引发 crash。

#### 1.3.2 各段权限表

| 段名 | 内容 | 读 | 写 | 执行 | 典型地址范围 |
|:---|:---|:---:|:---:|:---:|:---|
| 代码段 (Text) | 机器指令 | Y | N | Y | 0x400000 起（非 PIE） |

| 堆 (Heap) | 动态分配的内存 | Y | Y | N | BSS 之后，向高地址增长 |
| 共享库 | libc 等共享库代码和数据 | Y | 部分 | 部分 | 栈和堆之间 |
| 栈 (Stack) | 局部变量、返回地址等 | Y | Y | N | 高地址，向低地址增长 |
| 内核空间 | 操作系统内核 | - | - | - | 顶部 1/4 |

权限的含义：

- **读 (R)**：可以读取该段的内容
- **写 (W)**：可以修改该段的内容
- **执行 (X)**：可以将该段的内容作为指令执行

关键安全含义：

- 代码段可执行但不可写 → 不能通过修改代码段来注入 shellcode
- 栈可写但不可执行 → 不能在栈上执行 shellcode（NX/DEP 保护）
- 堆可写但不可执行 → 不能在堆上执行 shellcode
- 这些保护措施就是为什么需要 ROP 技术

#### 1.3.3 ASLR 的随机化范围

ASLR（Address Space Layout Randomization，地址空间布局随机化）是现代操作系统的一项安全特性，它在每次程序运行时随机化以下区域的基地址：

| 区域 | 是否随机化 | 随机化位数 | 示例（64 位 Linux） |
|:---|:---:|:---:|:---|
| 代码段 | PIE 开启时随机化 | ~30 位 | 0x55???????? |
| 代码段 | PIE 关闭时不随机化 | 0 | 0x400000（固定） |
| 数据段 | 跟随代码段 | ~30 位 | 跟随代码段偏移 |
| 堆 | 是 | ~28 位 | 0x55???????? |
| 栈 | 是 | ~24 位 | 0x7FF??????? |
| 共享库 | 是 | ~28 位 | 0x7F???????? |
| brk/sbrk | 跟随堆 | ~28 位 | - |

ASLR 的限制：

1. **随机化位数有限**：虽然地址是 64 位，但实际随机化的只有低位（约 24-30 位），高位是固定的。例如栈地址总是在 `0x7FFx xxxx xxxx` 附近。
2. **偏移量不变**：同一模块内各段的相对偏移是固定的。如果知道代码段的地址，就能推算出数据段的地址。
3. **信息泄露可绕过**：如果攻击者能泄露任何一个地址，就可以通过已知的偏移计算出其他段的地址。
4. **PIE 关闭时代码段不随机化**：Attack Lab 关闭了 PIE，所以代码段地址始终从 `0x400000` 开始，这使得 ret2text 攻击成为可能。

ASLR 的实际随机化效果（64 位 Linux）：

```
# 第 1 次运行
栈:     0x7ffffffde000
libc:   0x7ffff7a0d000
堆:     0x555555756000

# 第 2 次运行
栈:     0x7ffffffce000    ← 不同
libc:   0x7ffff79fd000    ← 不同
堆:     0x555555746000    ← 不同

# 但代码段（非 PIE）始终在：
代码:   0x400000          ← 相同
```

Attack Lab 中的 ASLR：

- Attack Lab 关闭了 ASLR（使用 `setarch -R` 或类似的 `disable-aslr` 设置），所以栈地址在每次运行时是固定的。
- 这使得我们可以在攻击字符串中硬编码地址。
- 在真实环境中，需要先泄露栈地址，然后才能构造精确的攻击。

### 2.1 Stack Canary 与 TLS

#### 2.1.1 Stack Canary 的概念

Stack Canary（栈金丝雀/栈哨兵）是一种缓冲区溢出检测机制。其名称来源于煤矿中用来检测有毒气体的金丝雀——如果金丝雀死了，说明有危险。

基本原理：

1. 在函数序言中，在返回地址和局部变量之间插入一个随机值（canary）
2. 在函数返回前（ret 指令前），检查这个值是否被修改
3. 如果 canary 被修改，说明发生了缓冲区溢出攻击，程序立即终止

Canary 在栈帧中的位置：

```
          ┌──────────────────────────────┐
          │   返回地址 (Return Address)    │  ← 攻击目标
          ├──────────────────────────────┤
          │   Canary 值 (随机)             │  ← 插入在返回地址之前
          ├──────────────────────────────┤
          │   局部变量 / 缓冲区            │  ← 溢出从这里开始
  rsp →   └──────────────────────────────┘
```

如果攻击者通过缓冲区溢出覆盖返回地址，必须先经过 canary 的位置，从而破坏 canary 值。

#### 2.1.2 Canary 值的生成

Canary 值在程序启动时由操作系统随机生成，存储在一个特殊的位置。具体过程：

1. **程序加载时**：Linux 内核在进程启动时，通过 `arch_setup_canary()` 生成一个随机 canary 值。
2. **存储位置**：canary 值存储在 TLS（Thread Local Storage，线程本地存储）中的一个固定偏移位置。在 x86-64 上，这个偏移是 `%fs:0x28`（对于主线程）。
3. **每个线程独立**：每个线程都有自己的 TLS，因此每个线程有自己的 canary 值。

Canary 值的特性：

- **随机性**：每次程序运行时 canary 值都不同（受 ASLR 影响）
- **不可预测**：canary 值是内核生成的，用户空间无法直接读取（通常）
- **特殊字节**：canary 的最低字节通常是 `\x00`（null byte），这样字符串函数（如 `strcpy`）在遇到 canary 时会停止复制，从而无法简单地通过字符串操作覆盖 canary

Canary 值的典型格式：

```
0x??????00????????   (64 位 canary，最低字节为 \x00)
```

例如：`0xa3b2c1d000e4f5a6`（注意最低字节是 `00`，在小端序中第一个字节就是 `\x00`）

#### 2.1.3 %fs:0x28 的含义

`%fs:0x28` 是 x86-64 上访问 TLS 中 canary 值的方式：

- `%fs` 是一个段寄存器，指向当前线程的 TLS 区域
- `0x28` 是 canary 值在 TLS 中的偏移量
- `%fs:0x28` 的完整含义：从 TLS 基地址偏移 0x28（40 字节）处读取 8 字节的 canary 值

在 GDB 中查看 canary 值：

```gdb
(gdb) p/x *(unsigned long long*)($fs_base + 0x28)
$1 = 0x4b2c1a00e7f3d180
```

注意：
- GDB 中使用 `$fs_base` 获取 TLS 基地址
- 不同线程的 `$fs_base` 不同
- 如果在 GDB 中 `$fs_base` 不可用，可以尝试 `info reg fs_base`

#### 2.1.4 函数序言/尾声中的 Canary 代码

编译器开启了 `-fstack-protector` 后，会在函数中插入 canary 检查代码。

**函数序言（插入 canary）**：

```assembly
func:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $N, %rsp

    # ↓ 插入 canary 检查代码 ↓
    movq    %fs:0x28, %rax          # 从 TLS 读取 canary 值
    movq    %rax, -8(%rbp)          # 将 canary 存储到栈上（返回地址之前）
    xorq    %rax, %rax              # 清除 %rax（防止 canary 值泄露）
```

**函数尾声（检查 canary）**：

```assembly
    # ↓ 检查 canary ↓
    movq    -8(%rbp), %rax          # 从栈上读取 canary
    xorq    %fs:0x28, %rax          # 与 TLS 中的 canary 比较
    jne     .Lstack_chk_fail        # 如果不等，跳转到失败处理

    # 正常返回
    leave
    ret

.Lstack_chk_fail:
    callq   __stack_chk_fail        # 调用失败处理函数
```

**`__stack_chk_fail` 函数**：

当 canary 检查失败时，调用 `__stack_chk_fail`，它的行为是：

1. 向 stderr 输出错误消息：`*** stack smashing detected ***: <program name> terminated`
2. 调用 `__libc_message` 或 `__fortify_fail`
3. 最终调用 `abort()` 终止程序
4. 可能还会调用 `__backtrace` 输出调用栈

#### 2.1.5 Canary 的绕过方法

虽然 canary 提供了基本的缓冲区溢出检测，但仍然有多种绕过方法：

**方法 1：信息泄露（Canary 泄露）**

如果程序存在格式化字符串漏洞或越界读取漏洞，攻击者可以读取栈上的 canary 值，然后在溢出时将 canary 值放在正确的位置。

```
原始栈布局：
  [buffer]  [canary]  [rbp]  [ret addr]

攻击步骤：
1. 通过信息泄露读取 canary 值
2. 在溢出时，在 canary 位置放置正确的 canary 值
3. 在返回地址位置放置攻击目标地址

覆盖后的栈：
  [AAAA...AAAA]  [正确的canary]  [AAAA]  [target addr]
```

**方法 2：覆盖 TLS 中的 Canary**

如果攻击者能够写入 TLS 中 `%fs:0x28` 的位置，就可以将 canary 修改为已知值，然后在溢出时使用这个已知值。

**方法 3：覆盖 `__stack_chk_fail` 的 GOT 条目**

如果程序有 canary 检查但同时存在 GOT 覆写漏洞，攻击者可以将 `__stack_chk_fail` 的 GOT 条目修改为攻击目标地址。这样 canary 检查失败时，不是终止程序，而是跳转到攻击者指定的地址。

**方法 4：爆破 Canary**

对于 `fork()` 创建的子进程，canary 值在所有子进程中相同（因为 TLS 是从父进程复制的）。攻击者可以逐字节爆破 canary：

- 第 1 次：猜测 canary 的第 1 个字节（256 种可能）
- 如果猜对了，canary 检查不会失败（程序不会 crash）
- 如果猜错了，程序 crash，父进程重新 fork
- 重复此过程，逐字节猜测 canary
- 由于 canary 最低字节是 `\x00`，实际只需猜测 7 个字节

**方法 5：不需要覆盖返回地址的攻击**

如果攻击者可以通过覆盖其他关键数据（如函数指针、vtable 指针等）来实现攻击，就不需要经过 canary 的位置。

**Attack Lab 中的 Canary**：

Attack Lab 的目标程序**没有启用** stack canary（编译时使用了 `-fno-stack-protector`），因此我们可以自由地覆盖返回地址而不需要考虑 canary。

### 2.2 完整 ABI 调用约定补充

#### 2.2.1 结构体传递

在 System V AMD64 ABI 中，结构体的传递规则取决于其大小和字段类型：

**分类（Classification）规则**：

每个 8 字节的结构体部分会被分类为以下之一：
- **INTEGER**：整数类型（可以放入通用寄存器）
- **SSE**：浮点类型（可以放入 SSE 寄存器）
- **SSEUP**：SSE 上半部分
- **X87**：x87 浮点类型
- **X87UP**：x87 上半部分
- **MEMORY**：必须通过内存传递

**传递规则**：

1. 如果结构体被分类为 MEMORY，则通过栈传递（隐含的第一参数 `%rdi` 指向调用者分配的空间）
2. 如果结构体被分类为 INTEGER，则通过通用寄存器传递（消耗 %rdi, %rsi, %rdx, %rcx, %r8, %r9 的配额）
3. 如果结构体被分类为 SSE，则通过 SSE 寄存器传递（消耗 %xmm0-%mm7 的配额）

**示例**：

```c
// 两个整数字段，各 4 字节，共 8 字节 → 分类为 INTEGER
struct Point { int x; int y; };
void func(struct Point p);  // p 通过 %rdi 传递（x 在低 32 位，y 在高 32 位）

// 1 个整数 + 1 个浮点 → 分别分类
struct Mixed { int a; float b; };
void func(struct Mixed m);  // a 通过 %edi 传递，b 通过 %xmm0 传递

// 大结构体 → MEMORY
struct Big { long arr[10]; };
void func(struct Big b);  // 通过隐含第一参数 %rdi 指向调用者分配的内存
```

结构体返回值的规则类似：

1. 如果可以分类为 INTEGER/SSE，通过 `%rax` 和 `%rdx`（或 `%xmm0` 和 `%xmm1`）返回
2. 如果分类为 MEMORY，调用者在 `%rdi` 中传递一个指向返回值存储空间的指针（作为隐含的第一参数），返回时 `%rax` 包含该指针

#### 2.2.2 可变参数的 al 寄存器

详细说明 `%al` 在可变参数函数调用中的作用：

**原理**：

可变参数函数（如 `printf`）需要知道有多少个浮点参数通过 SSE 寄存器传递，以便正确地从寄存器保存区（Register Save Area）中读取这些参数。

`%al` 的值表示使用了多少个 SSE 寄存器，取值范围是 0-8。

**编译器生成的代码**：

```c
printf("%d %f %f", 1, 2.0, 3.0);
```

```assembly
movl    $2, %eax               # al = 2，使用了 2 个 xmm 寄存器
movsd   3.0, %xmm1            # 第 2 个浮点参数
movsd   2.0, %xmm0            # 第 1 个浮点参数
movl    $1, %edx               # 整数参数
leaq    .LC0, %rdi             # 格式字符串
call    printf
```

**在 ROP 中的影响**：

如果 ROP 链需要调用 `printf` 或其他可变参数函数：

1. 必须设置 `%al` 为正确的值（至少为 0）
2. 如果 `%al` 的值过大，`printf` 会尝试从不存在的 SSE 寄存器保存区读取数据，可能导致段错误
3. 最简单的做法是设置 `%al = 0`，表示没有浮点参数

### 2.3 leave 指令

#### 2.3.1 leave 的等价操作

`leave` 指令是 x86 中用于恢复栈帧的指令，等价于：

```assembly
movq    %rbp, %rsp          # 第一步：将栈指针恢复到帧指针位置
popq    %rbp                # 第二步：恢复调用者的帧指针
```

或者更简洁地说：

```
leave ≡ mov %rbp, %rsp; pop %rbp
```

**执行过程详解**：

1. **`mov %rbp, %rsp`**：将 `%rsp` 设为 `%rbp` 的值。这一步释放了当前函数的所有局部变量空间（因为局部变量在 `%rbp` 之下）。
2. **`pop %rbp`**：从栈顶弹出一个值到 `%rbp`，恢复调用者的帧指针。同时 `%rsp` 增加 8。

执行前后的栈变化：

```
执行 leave 前：
          ┌──────────────────┐
          │  返回地址          │
          ├──────────────────┤
  rbp →   │  旧 %rbp         │
          ├──────────────────┤
          │  局部变量         │
          ├──────────────────┤
          │  ...             │
  rsp →   └──────────────────┘

执行 mov %rbp, %rsp 后：
          ┌──────────────────┐
          │  返回地址          │
          ├──────────────────┤
  rbp →   │  旧 %rbp         │ ← rsp 也指向这里了
          ├──────────────────┤
          │  局部变量（已释放）│
          └──────────────────┘

执行 pop %rbp 后：
          ┌──────────────────┐
          │  返回地址          │ ← rsp 指向这里
  rbp →   ├──────────────────┤  ← rbp 被恢复为旧值
          │  旧 %rbp（已弹出）│
          └──────────────────┘
```

#### 2.3.2 leave 在栈迁移攻击中的应用

栈迁移（Stack Pivoting）是一种高级攻击技术，当缓冲区空间不足以放置完整的 ROP 链时使用。

**基本原理**：

利用 `leave; ret` 指令序列，将 `%rsp` 迁移到攻击者控制的内存区域。

**攻击步骤**：

假设缓冲区在栈上的地址为 `0x7fffffffe100`，攻击者在另一个可写的内存区域（如堆、BSS 段）准备了 ROP 链，地址为 `0x555555758000`。

**第一步：覆盖返回地址和 saved %rbp**

```
原始栈布局（有帧指针的函数）：
          ┌──────────────────────────┐
          │  返回地址                  │
          ├──────────────────────────┤
  rbp →   │  保存的 %rbp              │
          ├──────────────────────────┤
          │  缓冲区（溢出）            │
  rsp →   └──────────────────────────┘

覆盖后的栈布局：
          ┌──────────────────────────┐
          │  leave; ret gadget 地址   │  ← 覆盖返回地址
          ├──────────────────────────┤
  rbp →   │  0x555555758001          │  ← 覆盖 saved %rbp 为目标地址 +1
          ├──────────────────────────┤
          │  AAAAAAA...（填充）        │
  rsp →   └──────────────────────────┘
```

**第二步：执行过程**

```
1. 原函数执行 leave:
   a. mov %rbp, %rsp  →  rsp = rbp = 0x7fffffffe110（saved %rbp 的地址）
   b. pop %rbp        →  rbp = 0x555555758001, rsp += 8（指向返回地址）

2. 原函数执行 ret:
   → 跳转到 leave; ret gadget

3. leave; ret gadget 执行 leave:
   a. mov %rbp, %rsp  →  rsp = 0x555555758001（目标地址 +1！）
   b. pop %rbp        →  rbp = [0x555555758001], rsp = 0x555555758009

4. leave; ret gadget 执行 ret:
   → 跳转到 [0x555555758009] 处的值（攻击者控制的 ROP 链的第一条 gadget）
```

注意：目标地址通常需要减 1 或做微调，因为 `pop %rbp` 会消耗 8 字节。

**栈迁移的要点**：

1. 需要知道目标可写区域的地址
2. 需要一个 `leave; ret` gadget
3. 通过两次 `leave` 实现 `%rsp` 的迁移
4. 第一次 `leave` 恢复被覆盖的 `%rbp`，第二次 `leave` 将 `%rsp` 设为被覆盖的 `%rbp` 值

### 2.4 PLT/GOT 延迟绑定

#### 2.4.1 为什么需要延迟绑定

动态链接的程序在运行时需要调用共享库中的函数（如 `printf`、`scanf` 等）。这些函数的地址在编译时是未知的，只有在运行时才能确定。

**静态绑定的缺点**：

- 如果在程序启动时解析所有函数地址，会导致启动延迟
- 大部分函数可能根本不会被调用，解析它们是浪费时间

**延迟绑定（Lazy Binding）**：

- 只有在函数第一次被调用时才解析其地址
- 后续调用直接使用已解析的地址，无需再次解析
- PLT（Procedure Linkage Table）和 GOT（Global Offset Table）是实现延迟绑定的机制

#### 2.4.2 PLT/GOT 结构

```
┌────────────────────────────────────────────────────────────────────┐
│  PLT (Procedure Linkage Table) - 代码段，可读可执行                    │
│                                                                    │
│  PLT[0]: 特殊条目，跳转到动态链接器                                   │
│    pushq  GOT[1]            # 推入模块标识                          │
│    jmp     *GOT[2]          # 跳转到动态链接器 (_dl_runtime_resolve) │
│                                                                    │
│  PLT[1]: 例如 printf 的 PLT 条目                                    │
│    jmp     *GOT[4]          # 跳转到 GOT 中 printf 的地址           │
│    pushq   $reloc_index     # 推入重定位索引                        │
│    jmp     PLT[0]           # 跳转到 PLT[0] 解析地址               │
│                                                                    │
│  PLT[2]: 例如 scanf 的 PLT 条目                                     │
│    jmp     *GOT[8]          # 跳转到 GOT 中 scanf 的地址            │
│    pushq   $reloc_index     # 推入重定位索引                        │
│    jmp     PLT[0]           # 跳转到 PLT[0] 解析地址               │
│                                                                    │
├────────────────────────────────────────────────────────────────────┤
│  GOT (Global Offset Table) - 数据段，可读可写                        │
│                                                                    │
│  GOT[0]: .dynamic 段的地址                                         │
│  GOT[1]: link_map 结构的地址（模块标识）                              │
│  GOT[2]: _dl_runtime_resolve 的地址（动态链接器解析函数）              │
│  GOT[4]: printf 的实际地址（初始为 PLT[1] 中 pushq 指令的地址）       │
│  GOT[8]: scanf 的实际地址（初始为 PLT[2] 中 pushq 指令的地址）       │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

#### 2.4.3 完整调用流程图

**第一次调用 printf 的流程**：

```
程序代码
  │
  │  call printf@plt
  ↓
PLT[1] (printf 的 PLT 条目)
  │
  │  jmp *GOT[4]          ← GOT[4] 初始值为 PLT[1] 中 pushq 的地址
  ↓                        （不是 printf 的实际地址！）
PLT[1] 的 pushq 指令
  │
  │  pushq $0              ← 推入重定位索引（0 表示 printf）
  ↓
PLT[0]
  │
  │  pushq GOT[1]          ← 推入 link_map（模块标识）
  │  jmp *GOT[2]           ← 跳转到 _dl_runtime_resolve
  ↓
_dl_runtime_resolve
  │
  │  1. 根据 link_map 和重定位索引，查找 printf 的实际地址
  │  2. 将 printf 的实际地址写入 GOT[4]（更新 GOT 条目）
  │  3. 跳转到 printf 的实际地址
  ↓
printf 函数体
```

**第二次及之后调用 printf 的流程**：

```
程序代码
  │
  │  call printf@plt
  ↓
PLT[1]
  │
  │  jmp *GOT[4]          ← GOT[4] 现在是 printf 的实际地址！
  ↓
printf 函数体
  （不再需要 _dl_runtime_resolve）
```

#### 2.4.4 _dl_runtime_resolve

`_dl_runtime_resolve` 是 glibc 中的动态链接器解析函数，它的工作是：

1. **保存寄存器**：保存所有调用者保存的寄存器（因为解析过程可能调用其他函数）
2. **解析地址**：调用 `_dl_fixup` 函数，根据 `link_map` 和重定位索引，找到目标函数的实际地址
3. **更新 GOT**：将解析到的地址写入对应的 GOT 条目
4. **恢复寄存器**：恢复之前保存的寄存器
5. **跳转到目标**：跳转到解析到的函数地址

#### 2.4.5 GOT 覆写攻击

GOT 覆写（GOT Overwrite）是一种利用 GOT 可写特性来劫持控制流的攻击技术。

**攻击前提**：

1. 程序存在任意地址写入漏洞（如格式化字符串漏洞）
2. GOT 没有被保护（没有开启 RELRO）

**攻击方法**：

1. 找到目标函数的 GOT 条目地址（如 `printf@GOT`）
2. 通过任意地址写入漏洞，将该 GOT 条目修改为攻击者指定的地址（如 `system` 函数的地址）
3. 当程序下次调用 `printf` 时，实际会跳转到 `system` 函数

**攻击示例**：

假设：
- `printf@GOT` 的地址为 `0x404020`
- `system` 函数的地址为 `0x7ffff7a52390`

攻击：
```python
# 通过格式化字符串漏洞写入
payload = fmtstr_payload(offset, {0x404020: 0x7ffff7a52390})
```

执行后，`printf@GOT` 被修改为 `system` 的地址，下次调用 `printf("/bin/sh")` 时实际执行 `system("/bin/sh")`。

#### 2.4.6 RELRO 保护

RELRO（RELocation Read-Only）是一种保护 GOT 的安全机制，分为两个级别：

**Partial RELRO（部分 RELRO）**：

- 编译选项：`-Wl,-z,relro`（GCC 默认开启）
- 效果：
  - GOT 之前的段（如 .ctors, .dtors, .jcr, .dynamic, .got.plt 之前的部分）被标记为只读
  - `.got.plt`（包含需要延迟绑定的 PLT 条目）仍然可写
- 保护程度：有限，GOT 覆写攻击仍然可能

**Full RELRO（完全 RELRO）**：

- 编译选项：`-Wl,-z,relro,-z,now`
- 效果：
  - 程序启动时解析所有函数地址（失去延迟绑定的性能优势）
  - 整个 GOT（包括 `.got.plt`）被标记为只读
  - GOT 覆写攻击不可行
- 保护程度：强，但会增加启动时间

RELRO 级别对比：

| 特性 | No RELRO | Partial RELRO | Full RELRO |
|:---|:---:|:---:|:---:|
| .got.plt 可写 | 是 | 是 | 否 |
| GOT 覆写可行 | 是 | 是 | 否 |
| 延迟绑定 | 是 | 是 | 否 |
| 启动速度 | 最快 | 快 | 较慢 |
| 安全性 | 最低 | 中等 | 最高 |

使用 `checksec` 工具检查 RELRO 状态：

```bash
$ checksec --file=ctarget
    RELRO           STACK CANARY      NX            PIE             RPATH
    Partial RELRO   No canary found   NX enabled    No PIE          No RPATH
```

### 2.5 De Bruijn 序列

#### 2.5.1 数学定义

De Bruijn 序列（De Bruijn Sequence）是组合数学中的一个重要概念。

**定义**：对于字母表大小为 k、子序列长度为 n 的情况，De Bruijn 序列 B(k, n) 是一个循环序列，其中每个可能的长度为 n 的子序列在该循环序列中恰好出现一次。

**性质**：

- B(k, n) 的长度为 k^n
- 每个 n 长子串在循环序列中恰好出现一次
- 对于线性（非循环）序列，长度为 k^n + n - 1

**示例**：

B(2, 3)（二进制，3 位子串）：

```
00010111

循环序列中包含所有 2^3 = 8 个可能的 3 位子串：
000, 001, 010, 101, 011, 111, 110, 100
```

B(4, 4)（4 个字符，4 位子串，常用于缓冲区溢出偏移定位）：

这是在漏洞利用中使用的形式，4 个字符的字母表通常是 `{a, b, c, d,...}` 或特定的 ASCII 字符。

#### 2.5.2 Cyclic Pattern 在漏洞利用中的应用

在缓冲区溢出攻击中，De Bruijn 序列被用作 cyclic pattern（循环模式），用于快速确定溢出的偏移量。

**原理**：

1. 生成一个不包含重复子串的模式字符串
2. 将该模式作为输入传给目标程序
3. 当程序 crash 时，检查被覆盖的返回地址（或其他目标位置）的值
4. 在模式字符串中搜索该值，即可确定偏移量

**为什么需要 De Bruijn 序列**：

- 如果使用重复字符（如 `AAAA...AAAA`），crash 时的返回地址也是 `0x4141414141414141`，无法确定偏移量
- 如果使用递增字符（如 `AAAABBBBCCCC...`），精度只有 4 字节
- 使用 De Bruijn 序列可以精确定位到字节级别的偏移

#### 2.5.3 偏移定位方法

**使用 pwntools 的 cyclic 工具**：

```python
from pwn import *

# 生成长度为 200 的 cyclic pattern
pattern = cyclic(200)
print(pattern)
# 输出类似于：aaaabaaacaaadaaaeaaafaaagaaahaaaiaaaj...

# 假设 crash 时的返回地址值为 0x61616168
# (即 'haaa' 在小端序下的表示)

# 查找偏移量
offset = cyclic_find(0x61616168)
print(f"Offset: {offset}")
# 输出：Offset: 24
```

**手动构造的简单 cyclic pattern**：

一个简单的 4 字节不重复模式构造方法：

```
aaaa  baab  caab  daab  eaab  faab  gaab  haab
iaab  jaab  kaab  laab  maab  naab  oaab  paab
...
```

每个 4 字节块都是唯一的，因此可以通过 4 字节值确定偏移量。

**使用 metasploit 的 pattern_create 和 pattern_offset**：

```bash
# 生成 200 字节的 pattern
$ /usr/share/metasploit-framework/tools/exploit/pattern_create.rb -l 200
Aa0Aa1Aa2Aa3Aa4Aa5Aa6Aa7Aa8Aa9Ab0Ab1Ab2Ab3Ab4Ab5Ab6Ab7Ab8Ab9Ac0...

# 假设 crash 时的值是 0x41366241 (即 "Ab6A" 的小端表示)
$ /usr/share/metasploit-framework/tools/exploit/pattern_offset.rb -q 41366241
[*] Exact match at offset 28
```

**Attack Lab 中的应用**：

在 Attack Lab 中，我们可以通过以下步骤确定偏移量：

1. 查看 `getbuf` 的反汇编，确定缓冲区大小（0x28 = 40 字节）
2. 返回地址在缓冲区起始地址 + 40 字节处
3. 因此需要 40 字节填充 + 8 字节返回地址
4. 这比使用 cyclic pattern 更直接，因为我们可以直接从反汇编中计算偏移量

但对于更复杂的漏洞（如堆溢出、格式化字符串漏洞等），cyclic pattern 是确定偏移量的标准方法。

### 2.6 call/pop 获取 RIP

#### 2.6.1 位置无关代码中的 RIP 获取

在位置无关可执行文件（PIE, Position Independent Executable）或位置无关代码（PIC, Position Independent Code）中，代码段在运行时的加载地址是未知的。然而，代码中经常需要引用全局数据（如全局变量、字符串常量等），这些数据的绝对地址在编译时也是未知的。

x86-64 提供了 `%rip` 相对寻址来解决这个问题，但在某些情况下（如编写 shellcode），攻击者需要手动获取当前指令的地址。

**call/pop 技术的基本原理**：

`call` 指令会将下一条指令的地址压入栈中，然后跳转。如果在 `call` 之后紧跟一个 `pop` 指令，就可以从栈中获取 `call` 之后的指令地址，也就是当前代码的位置。

```assembly
    call    after_call           # 压入 after_call 的地址，然后跳转
after_call:
    pop     %rax                 # 弹出 after_call 的地址到 %rax
    # 现在 %rax 中存储的是 after_call 标签的地址
    # 通过 %rax + 已知偏移，可以访问附近的数据
```

#### 2.6.2 在 Shellcode 中的应用

**示例：获取字符串地址**

```assembly
    call    string_addr          # 压入字符串地址，跳转到 string_addr
string_addr:
    pop     %rdi                 # %rdi = string_addr 的地址
    add     $6, %rdi             # %rdi = string_addr + 6 = "/bin/sh" 的地址
    # ... 使用 %rdi 作为参数
    # ...
    jmp     continue             # 跳过字符串数据
string_data:
    .string "/bin/sh\0"          # 字符串数据
continue:
    # ... 继续执行
```

更简洁的写法：

```assembly
    jmp     get_string           # 先跳转到 get_string
shellcode:
    pop     %rdi                 # 弹出字符串地址到 %rdi
    # ... 其他 shellcode ...
get_string:
    call    shellcode            # 压入下一条指令地址（即字符串地址），跳回 shellcode
    .string "/bin/sh\0"          # 字符串紧接在 call 指令之后
```

这个模式的执行流程：

```
1. jmp get_string          → 跳转到 get_string
2. call shellcode          → 压入 "/bin/sh\0" 的地址（call 下一条指令的地址），跳转到 shellcode
3. pop %rdi               → %rdi = "/bin/sh" 的地址
4. ... 其他 shellcode ...
```

**在 Attack Lab 中的意义**：

Attack Lab 的 Phase 2 和 Phase 3 需要注入 shellcode。如果你的 shellcode 需要引用自身中的数据（如字符串），就需要使用 call/pop 技术来获取当前地址。

但在 Attack Lab 中：
- Phase 2 只需要设置 `%rdi` 为一个已知值，不需要 call/pop
- Phase 3 需要将字符串放在栈上，字符串地址可以直接通过 `%rsp` 计算，因此也不一定需要 call/pop

### 2.7 栈对齐与 movaps

#### 2.7.1 16 字节对齐要求

System V AMD64 ABI 要求在执行 `call` 指令时，`%rsp` 必须是 16 字节对齐的。也就是说，`%rsp % 16 == 0` 在 `call` 执行前必须成立。

这个要求的原因：

1. **SSE 指令的对齐要求**：许多 SSE 指令（如 `movaps`、`movdqa`）要求内存操作数是 16 字节对齐的。如果操作数未对齐，会触发 General Protection Fault（#GP），导致程序崩溃。
2. **性能优化**：对齐的内存访问比未对齐的访问更快
3. **ABI 一致性**：保证所有函数都遵循相同的对齐约定

对齐规则的具体内容：

```
在 call 指令执行前：  %rsp % 16 == 0    （16 字节对齐）
call 执行后：        %rsp % 16 == 8    （因为 call 压入 8 字节的返回地址）
进入被调用函数后：    %rsp % 16 == 8
push %rbp 后：       %rsp % 16 == 0    （再压入 8 字节，重新对齐）
```

#### 2.7.2 未对齐导致的 crash

当 `%rsp` 未正确对齐时，调用使用了 SSE 指令的函数会导致 crash。最常见的场景：

```c
// 这个函数内部可能使用 movaps 指令
void vulnerable_function() {
    printf("Hello\n");  // printf 内部可能使用 movaps
}
```

如果 `%rsp` 未对齐，`printf` 内部的 `movaps` 指令会触发 SIGSEGV。

**在 ROP 链中导致未对齐的原因**：

1. 每次执行 `ret` 指令，`%rsp` 增加 8（`pop` 一个地址到 `%rip`）
2. 在 ROP 链中，每个 gadget 执行 `ret` 后，`%rsp` 的对齐状态可能改变
3. 如果 ROP 链中 gadget 的数量是奇数（每个 gadget 末尾有一个 `ret`），那么对齐状态会在对齐和未对齐之间交替

```
初始状态（假设 ret 前对齐）：
  ret 执行后：rsp += 8 → 未对齐（rsp % 16 == 8）
  gadget1 ret 后：rsp += 8 → 对齐（rsp % 16 == 0）
  gadget2 ret 后：rsp += 8 → 未对齐（rsp % 16 == 8）
  ...
```

#### 2.7.3 在 ROP 链中修复对齐

**方法 1：添加额外的 ret gadget**

在 ROP 链中，如果发现 `%rsp` 未对齐，可以添加一个额外的 `ret` gadget（不执行任何有用的操作，只是消耗 8 字节）来修复对齐。

```
# 假设当前 ROP 链导致 rsp 未对齐
# 添加一个 ret gadget 来修复

原始 ROP 链：
  [gadget1_addr]
  [gadget1_arg]
  [target_func_addr]    ← 这里调用时 rsp 未对齐，可能 crash

修复后的 ROP 链：
  [gadget1_addr]
  [gadget1_arg]
  [ret_gadget_addr]     ← 额外的 ret，消耗 8 字节，修复对齐
  [target_func_addr]    ← 现在调用时 rsp 是对齐的
```

**方法 2：使用 push; ret 代替 pop; ret**

某些 gadget 如 `push rax; ret` 会先减少 `%rsp`（8 字节），然后 `ret` 再增加 `%rsp`（8 字节），净效果是 `%rsp` 不变。但这不能修复对齐。

**方法 3：调整 ROP 链的结构**

重新排列 ROP 链中的 gadget，确保在调用需要 16 字节对齐的函数时，`%rsp` 是对齐的。

**在 Attack Lab 中的实例**：

Attack Lab 的 ROP 阶段（Phase 4 和 Phase 5）中，如果你构造的 ROP 链在调用 `touch3` 时 crash，很可能就是栈对齐的问题。解决方法：

```python
# 添加一个额外的 ret gadget
ret_gadget = 0x40141b  # 一条单纯的 ret 指令

# 在 ROP 链中适当位置添加
rop_chain = [
    pop_rdi_ret,      # pop rdi; ret
    cookie_value,     # rdi 的值
    ret_gadget,       # 额外的 ret，修复对齐 ← 关键！
    touch3_addr,      # 目标函数地址
]
```

判断是否需要额外 `ret` 的经验法则：

- 如果 ROP 链从 `getbuf` 的 `ret` 开始，`%rsp` 此时已经偏移了（因为 `getbuf` 的 `add $0x28, %rsp` 已经执行，`ret` 又弹出了 8 字节）
- 从 `getbuf` 返回后，`%rsp` 的值取决于具体的栈布局
- 最简单的方法：先不加 `ret`，如果 crash，再尝试加一个 `ret`

**快速诊断对齐问题**：

在 GDB 中检查：

```gdb
# 在 ret 指令前设断点
(gdb) break *0x4017bd
(gdb) continue
# 检查 %rsp 是否 16 字节对齐
(gdb) p $rsp % 16
$1 = 8    # 未对齐！需要添加额外的 ret
```

#### 2.8.4 x 命令的状态记忆

GDB 的 `x` 命令有状态记忆特性：

1. **默认值**：首次使用 `x` 命令时，N=1, F=x, U=w
2. **状态保持**：后续使用 `x` 命令时，如果省略了 N、F 或 U，GDB 会使用上次设定的值
3. **常见陷阱**：如果你之前执行了 `x/10i $pc`，再执行 `x $rsp`，GDB 会以指令格式（i）显示 `$rsp` 处的数据，这可能不是你想要的

#### 2.8.5 小端序显示差异

x86-64 是小端序（Little-Endian），在查看内存时需要特别注意：

```gdb

(gdb) x/1xg $rsp
0x5561dc78: 0x00000000004017a8

# 两种显示方式表示同一个值，只是粒度不同
```

理解这一点对 Attack Lab 非常重要，因为：
- 攻击字符串中的字节顺序是小端序的
- 在 GDB 中检查时，需要确认字节顺序是否正确

### 2.10 非对齐指令解码

#### 2.10.1 x86-64 变长指令特性

x86-64 体系结构的一个核心特征是**变长指令编码**（Variable-Length Instruction Encoding）。这意味着：

1. 指令的长度从 1 字节到 15 字节不等
2. 指令的起始位置不需要对齐到任何特定的边界
3. 同一段二进制数据，从不同的偏移开始解码，可能得到不同的指令序列

**变长指令的编码格式**：

```
┌──────┬──────────┬───────────┬──────────┬─────────┐
│Prefix│  Opcode  │ ModR/M    │  SIB     │Displace │Immediate│
│      │ (1-3 B)  │ (0-1 B)   │ (0-1 B)  │ment(0-4)│ (0-4 B) │
└──────┴──────────┴───────────┴──────────┴─────────┴─────────┘
```

各字段说明：

- **Prefix**（0-4 字节）：指令前缀，如 `0x66`（操作数大小覆盖）、`0x48`（REX.W，64 位操作数）
- **Opcode**（1-3 字节）：操作码，决定指令类型
- **ModR/M**（0-1 字节）：寻址模式，指定操作数
- **SIB**（0-1 字节）：比例-索引-基址寻址
- **Displacement**（0-4 字节）：偏移量
- **Immediate**（0-4 字节）：立即数

**示例**：

```
# ret 指令
c3                    # 1 字节

# pop %rbx
5b                    # 1 字节

# sub $0x28, %rsp
48 83 ec 28           # 4 字节（REX.W + opcode + ModR/M + immediate）

# movabs $0x1234567890abcdef, %rax
48 b8 ef cd ab 90 78 56 34 12   # 10 字节
```

#### 2.10.2 Gadget 发现原理

由于 x86-64 的变长指令特性，一段代码的中间部分可能恰好构成了另一条有意义的指令。这就是 ROP gadget 发现的基本原理。

**示例**：

假设某个函数中有以下代码（编译器生成的正常代码）：

```assembly
# 原始指令序列
0x400600:  48 89 c7    mov %rax,%rdi
0x400603:  e8 28 02 00 00   callq 0x400830
0x400608:  5b          pop %rbx
0x400609:  c3          ret
```

如果我们从不同的偏移开始解码：

**从 0x400600 开始解码（正常解码）**：

```
0x400600:  48 89 c7              mov %rax, %rdi
0x400603:  e8 28 02 00 00       callq 0x400830
0x400608:  5b                    pop %rbx
0x400609:  c3                    ret
```

**从 0x400601 开始解码**：

```
0x400601:  89 c7                 mov %eax, %edi        ← 有效的 gadget！
0x400603:  e8 28 02 00 00       callq ...
0x400608:  5b                    pop %rbx
0x400609:  c3                    ret
```

**关键发现**：`0x400609` 处的 `c3`（ret 指令）是一个单字节 gadget，无论从哪里开始解码，`c3` 始终解码为 `ret`。

### 2.11 syscall vs 函数调用 ABI

#### 2.11.1 两种调用方式的区别

在 x86-64 Linux 中，有两种调用操作系统服务的方式：

1. **函数调用**：通过 `call` 指令调用 C 库函数（如 `printf`, `system`）
2. **系统调用**：通过 `syscall` 指令直接调用内核服务

这两种方式使用不同的调用约定：

| 特性 | 函数调用 (C ABI) | 系统调用 (syscall ABI) |
|:---|:---|:---|
| 调用指令 | `call` | `syscall` |
| 返回指令 | `ret` | `sysret`（内核返回） |
| 系统调用号 | 不适用 | `%rax` |
| 第 1 个参数 | `%rdi` | `%rdi` |
| 第 2 个参数 | `%rsi` | `%rsi` |
| 第 3 个参数 | `%rdx` | `%rdx` |
| 第 4 个参数 | `%rcx` | **`%r10`** ← 不同！ |
| 第 5 个参数 | `%r8` | `%r8` |
| 第 6 个参数 | `%r9` | `%r9` |
| 返回值 | `%rax` | `%rax` |

#### 2.11.2 r10 vs rcx 的差异

最关键的区别是**第 4 个参数**：

- C 函数调用约定：第 4 个参数在 `%rcx` 中
- syscall 约定：第 4 个参数在 `%r10` 中

**为什么不同？**

`syscall` 指令在执行时会将返回地址保存到 `%rcx` 中（类似于 `call` 将返回地址压栈）。因此，`%rcx` 会被 `syscall` 指令覆盖，不能用于传递参数。所以 syscall 使用 `%r10` 替代 `%rcx` 作为第 4 个参数。

**常见的系统调用号**：

| 系统调用 | 号码 | 参数数量 |
|:---|:---:|:---:|
| `read` | 0 | 3 |
| `write` | 1 | 3 |
| `open` | 2 | 3 |
| `close` | 3 | 1 |
| `mmap` | 9 | 6 |
| `mprotect` | 10 | 3 |
| `clone` | 56 | 5 |
| `fork` | 57 | 0 |
| `execve` | 59 | 3 |
| `exit` | 60 | 1 |
| `exit_group` | 231 | 1 |

### 2.12 movabs vs movq

#### 2.12.1 编码差异

在 x86-64 汇编中，`mov` 指令有多种变体，根据操作数大小和类型使用不同的助记符：

**movq**：

- `movq $imm32, %reg`：将 32 位符号扩展的立即数移动到 64 位寄存器
- 编码：`48 c7 c0 + 4 字节立即数`（共 7 字节）
- 立即数范围：`-2^31` 到 `2^31 - 1`（因为符号扩展）

**movabsq**：

- `movabsq $imm64, %reg`：将完整的 64 位立即数移动到 64 位寄存器
- 编码：`48 b8 + 8 字节立即数`（共 10 字节）
- 立即数范围：完整的 64 位值

**关键区别**：

| 特性 | movq | movabsq |
|:---|:---|:---|
| 立即数大小 | 32 位（符号扩展到 64 位） | 64 位 |
| 指令长度 | 7 字节 | 10 字节 |
| 立即数范围 | -2^31 到 2^31-1 | 0 到 2^64-1 |
| 用途 | 小立即数 | 大立即数（如 64 位地址） |

#### 2.12.2 对 Shellcode 的影响

在编写 shellcode 时，这个区别很重要：

**如果地址 < 0x80000000（即 < 2GB）**：

```assembly
movq $0x400000, %rdi    # 可以使用 movq（32 位符号扩展）
# 编码：48 c7 c7 00 00 40 00（7 字节）
```

**如果地址 >= 0x80000000（如栈地址、libc 地址）**：

```assembly
movabsq $0x7fffffffe100, %rdi    # 必须使用 movabsq
# 编码：48 bf 00 e1 ff ff ff 7f 00 00（10 字节）
```

**更短的替代方案**：

```assembly
# 方法 1：使用 xor + mov（8 字节总计）
xorq    %rdi, %rdi          # 48 31 ff（3 字节）
movl    $0xffffe100, %edi   # bf 00 e1 ff ff（5 字节）
# 总共 8 字节，但需要地址 < 4GB

# 方法 2：使用 push + pop
pushq   $0x7fffffffe100     # 可能需要特殊编码
popq    %rdi                # 5f（1 字节）
```

**在 Attack Lab 中的影响**：

- Attack Lab 的 `ctarget` 代码段地址在 `0x400000` 范围内，可以用 `movq` 加载
- 栈地址在 `0x5561dc78` 范围内，需要使用 `movabsq` 或替代方案
- 在编写 shellcode 时要注意指令长度，确保不超出缓冲区空间

### 2.13 Cookie 概念

#### 2.13.1 Attack Lab 中的 Cookie

在 Attack Lab 中，cookie 是一个与每个学生关联的唯一 64 位值。它在实验中的作用是：

1. **身份验证**：确保攻击者知道自己的 cookie 值，而不是随意猜测
2. **防止作弊**：每个人的 cookie 不同，不能直接复制别人的答案
3. **增加难度**：在 Phase 3 和 Phase 5 中，需要将 cookie 的字节表示作为参数传递

**Cookie 的格式**：

```
Cookie: 0x59b997fa    (示例，每个人的值不同)
```

**Cookie 的存储位置**：

- 在代码段中：作为立即数存储在 `touch2` 和 `touch3` 的比较指令中
- 在 `cookie` 全局变量中：存储在数据段

**查看你的 cookie**：

```bash
# 方法 1：查看 cookie 文件
$ cat ~/.cookie
0x59b997fa

# 方法 2：在 GDB 中查看
(gdb) p/x cookie
$1 = 0x59b997fa

# 方法 3：反汇编 touch2 查看立即数
(gdb) disas touch2
```

#### 2.13.2 Cookie 与 Stack Canary 的区别

注意区分两个完全不同的概念：

| 特性 | Attack Lab Cookie | Stack Canary |
|:---|:---|:---|
| 目的 | 验证攻击者身份 | 检测缓冲区溢出 |
| 存储位置 | 全局变量 | 栈帧中（返回地址前） |
| 是否随机 | 每个学生固定 | 每次运行随机 |
| 是否可预测 | 可以查看 | 通常不可预测 |
| 长度 | 64 位 | 64 位 |
| 检查时机 | touch2/touch3 中 | 函数返回时 |

### 2.14 禁用 PIE 后的地址

#### 2.14.1 PIE 原理

PIE（Position Independent Executable，位置无关可执行文件）是一种安全特性，它使程序的代码段在每次运行时加载到不同的随机地址。

**PIE 的工作原理**：

1. **编译时**：使用 `-fPIE` 选项编译，生成位置无关代码
2. **链接时**：使用 `-pie` 选项链接，生成 PIE 可执行文件
3. **加载时**：内核/动态链接器在每次运行时选择一个随机的加载基地址
4. **运行时**：所有代码和数据的地址都基于加载基地址计算

**PIE 的地址变化**：

```
# PIE 启用（每次运行地址不同）
第 1 次运行：代码段从 0x55a0001000 开始
第 2 次运行：代码段从 0x55b0001000 开始（地址不同！）

# PIE 禁用（地址固定）
第 1 次运行：代码段从 0x400000 开始
第 2 次运行：代码段从 0x400000 开始（地址相同！）
```

#### 2.14.2 代码段地址固定性

当 PIE 被禁用时，程序的代码段始终从固定的地址开始加载：

- **默认基址**：`0x400000`（在 x86-64 Linux 上）
- **ELF 头**：从 `0x400000` 开始
- **代码段（.text）**：通常从 `0x400000` 之后的某个地址开始
- **数据段**：在代码段之后

**在 Attack Lab 中的影响**：

- Attack Lab 禁用了 PIE，因此 `touch1`、`touch2`、`touch3` 等函数的地址在每次运行时都相同
- 这使得 ret2text 攻击成为可能：可以直接在攻击字符串中硬编码目标函数的地址
- 如果启用了 PIE，攻击者需要先泄露代码段的基址，然后计算目标函数的地址

**查看程序是否为 PIE**：

```bash
# 方法 1：使用 file 命令
$ file ctarget
ctarget: ELF 64-bit LSB executable, ...  ← "executable" 表示非 PIE

# 方法 2：使用 checksec
$ checksec --file=ctarget
PIE: No PIE    ← 非 PIE

# 方法 3：使用 readelf
$ readelf -h ctarget | grep Type
  Type:    EXEC    ← EXEC 表示非 PIE（PIE 为 DYN）
```

**PIE 对 ROP 的影响**：

| PIE 状态 | ROP 难度 | 说明 |
|:---|:---|:---|
| No PIE | 简单 | gadget 地址固定，可直接使用 |
| PIE enabled | 困难 | gadget 地址随机化，需要先泄露基址 |

在真实世界的漏洞利用中，PIE 是非常常见的保护机制。Attack Lab 禁用 PIE 是为了降低实验难度，让同学们专注于理解核心概念。

### 3.1 栈帧与调用约定

**题目 1**：请描述 x86-64 上 `call func` 指令执行时栈的变化，以及被调用函数内部如何访问第 7 个整数参数。

<details>
<summary>标准答案</summary>

`call func` 指令的执行过程：

1. 将 `call` 指令的下一条指令地址（返回地址）压入栈中：`%rsp -= 8; *%rsp = %rip_next`
2. 跳转到 `func` 的入口地址：`%rip = func`

栈的变化：`%rsp` 减少了 8，栈顶多了一个 8 字节的返回地址。

被调用函数访问第 7 个整数参数：

由于 System V AMD64 ABI 规定前 6 个整数参数通过 `%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9` 传递，第 7 个及以后的参数通过栈传递。第 7 个参数在调用者栈帧的栈顶。

在 `call` 执行前，调用者将第 7 个参数放在 `%rsp` 处。`call` 执行后，返回地址被压栈，第 7 个参数位于 `%rsp + 8` 处。

如果被调用函数有帧指针（`push %rbp`），则：
- `%rbp + 0`：保存的旧 `%rbp`
- `%rbp + 8`：返回地址
- `%rbp + 16`：第 7 个参数

访问方式：`movq 16(%rbp), %rax`（有帧指针）或 `movq 8(%rsp+offset), %rax`（无帧指针，offset 取决于局部变量空间大小）。

</details>

**题目 2**：Callee-saved 寄存器和 Caller-saved 寄存器各有哪些？为什么在 ROP 攻击中 callee-saved 寄存器的 pop gadget 更常见？

<details>
<summary>标准答案</summary>

Callee-saved 寄存器：`%rbx`, `%rbp`, `%r12`, `%r13`, `%r14`, `%r15`（6 个通用寄存器，加上 `%rsp` 是特殊的 callee-saved）

Caller-saved 寄存器：`%rax`, `%rcx`, `%rdx`, `%rsi`, `%rdi`, `%r8`, `%r9`, `%r10`, `%r11`

在 ROP 攻击中 callee-saved 寄存器的 `pop` gadget 更常见的原因：

1. **保存/恢复模式**：编译器在函数序言中保存 callee-saved 寄存器（如果函数使用了它们），在函数尾声中恢复。恢复操作就是 `pop %rbx; pop %r12; ...; ret` 这样的序列。
2. **固定的尾声模式**：编译器生成的函数尾声通常包含连续的 `pop` 指令来恢复多个 callee-saved 寄存器，然后 `ret`。这些 `pop; ret` 序列恰好就是可用的 ROP gadget。
3. **Caller-saved 不需要保存**：编译器不需要在函数尾声中恢复 caller-saved 寄存器，因此很少有 `pop %rax; ret` 这样的 gadget（除非偶然在非对齐解码中发现）。
4. **非对齐解码的补充**：虽然编译器不会有意生成 `pop %rdi; ret`，但由于 x86 变长指令的特性，在非对齐位置解码可能产生这样的 gadget。Attack Lab 的 farm.c 就是故意设计了包含这些 gadget 的函数。

</details>

**题目 3**：假设函数 `foo` 使用了 `%rbx` 和 `%r12` 两个 callee-saved 寄存器，请写出函数序言和尾声中保存/恢复这两个寄存器的汇编代码。

<details>
<summary>标准答案</summary>

函数序言（保存 callee-saved 寄存器）：

```assembly
foo:
    pushq   %rbp                # 保存旧帧指针（标准序言）
    movq    %rsp, %rbp          # 设置新帧指针
    pushq   %rbx                # 保存 %rbx
    pushq   %r12                # 保存 %r12
    subq    $N, %rsp            # 分配局部变量空间
```

函数尾声（恢复 callee-saved 寄存器）：

```assembly
    addq    $N, %rsp            # 释放局部变量空间
    popq    %r12                # 恢复 %r12（后保存的先恢复）
    popq    %rbx                # 恢复 %rbx（先保存的后恢复）
    popq    %rbp                # 恢复旧帧指针
    ret                         # 返回
```

注意：`push` 和 `pop` 的顺序必须相反（LIFO），就像栈操作一样。

从 ROP 的角度看，函数尾声中的这些 `pop` 指令就是可用的 gadget：

```
pop %r12; ret    ← 可以用来设置 %r12 的值
pop %rbx; ret   ← 可以用来设置 %rbx 的值
```

而且由于这些 `pop` 指令是连续的，攻击者可以利用中间的某个 `pop` 开始的序列，例如：

```
原始序列：pop %r12; pop %rbx; pop %rbp; ret

如果从 pop %rbx 开始：pop %rbx; pop %rbp; ret（跳过了 %r12 的恢复）
如果从 pop %rbp 开始：pop %rbp; ret（跳过了 %r12 和 %rbx 的恢复）
```

</details>

### 3.2 缓冲区溢出基础

**题目 4**：在 `getbuf` 函数中，缓冲区大小为 0x28 字节，`Gets` 函数读取输入时不检查边界。请计算要覆盖返回地址需要输入多少字节，并说明字节序。

<details>
<summary>标准答案</summary>

需要输入的字节数：**40 字节填充 + 8 字节返回地址 = 48 字节**

详细计算：

1. `getbuf` 执行 `sub $0x28, %rsp` 分配了 `0x28 = 40` 字节的空间
2. `Gets` 从 `%rsp`（缓冲区起始地址）开始写入
3. 返回地址位于 `%rsp + 0x28`（紧接在分配空间之后）
4. 因此需要 40 字节填充来覆盖缓冲区空间，然后 8 字节来覆盖返回地址

字节序：

x86-64 使用小端序（Little-Endian），因此返回地址的字节顺序是低位字节在前。例如，如果目标地址是 `0x4017c0`，则输入的字节序列为：

```
c0 17 40 00 00 00 00 00
```

</details>

**题目 5**：如果 `getbuf` 使用了帧指针（即有 `push %rbp; mov %rsp, %rbp` 序言），那么覆盖返回地址需要的填充字节数是否变化？为什么？

<details>
<summary>标准答案</summary>

**不变化**。原因如下：

即使 `getbuf` 使用了帧指针，返回地址仍然位于缓冲区上方紧邻的位置。从缓冲区到返回地址的偏移量由 `sub $N, %rsp` 中的 N 和 `push` 指令的数量共同决定。

如果有帧指针，序言可能是：

```assembly
pushq   %rbp                # 8 字节
movq    %rsp, %rbp
subq    $0x20, %rsp         # 0x28 - 8 = 0x20（因为 push %rbp 已经占了 8 字节）
```

从缓冲区到返回地址的偏移量 = 0x20（缓冲区大小）+ 8（saved %rbp）= 0x28 = 40 字节。

所以需要的填充字节数不变，仍然是 40 字节填充 + 8 字节返回地址 = 48 字节。

</details>

### 3.3 ROP 基础

**题目 6**：什么是 ROP？为什么需要 ROP 而不是直接注入 shellcode？

<details>
<summary>标准答案</summary>

ROP（Return-Oriented Programming，面向返回的编程）是一种利用代码段中已有的指令片段（gadget）来构造任意程序逻辑的攻击技术。

需要 ROP 而不是直接注入 shellcode 的原因：

1. **NX/DEP 保护**：现代操作系统默认启用 NX（No-eXecute）保护，使栈和堆的内存区域不可执行。如果在栈上注入 shellcode 并尝试执行，CPU 会触发段错误（SIGSEGV）。
2. **shellcode 注入的前提**：只有在栈/堆可执行的情况下（NX 被禁用），才能直接注入并执行 shellcode。
3. **ROP 不需要可写可执行的内存**：ROP 使用的 gadget 来自代码段（只读可执行），通过 `ret` 指令将它们串联起来，不需要在任何新位置执行代码。

ROP 的工作原理：

1. **寻找 gadget**：在代码段中搜索以 `ret`（`0xc3`）结尾的指令序列
2. **构造 ROP 链**：将 gadget 的地址和参数依次放在栈上
3. **触发执行**：通过缓冲区溢出覆盖返回地址，使程序跳转到第一个 gadget
4. **自动串联**：每个 gadget 末尾的 `ret` 指令会弹出栈上的下一个地址，跳转到下一个 gadget

Attack Lab 中的对应关系：
- `ctarget`（NX 禁用）→ Phase 1-3 使用 shellcode 注入
- `rtarget`（NX 启用）→ Phase 4-5 使用 ROP

</details>

**题目 7**：请解释 ROP 链的执行过程，说明 `ret` 指令如何在 gadget 之间传递控制。

<details>
<summary>标准答案</summary>

ROP 链的执行过程：

**假设 ROP 链如下**：

```
栈布局（从低地址到高地址）：
  ┌─────────────────────────────┐
  │  填充字节 (0x28 字节)         │
  ├─────────────────────────────┤
  │  gadget1 地址: pop rdi; ret   │  ← 覆盖的返回地址
  ├─────────────────────────────┤
  │  0x59b997fa (cookie 值)      │  ← pop rdi 的操作数
  ├─────────────────────────────┤
  │  gadget2 地址: ret            │  ← 栈对齐修复
  ├─────────────────────────────┤
  │  touch3 的地址               │  ← 最终目标
  └─────────────────────────────┘
```

**执行步骤**：

1. `getbuf` 的 `ret` 指令执行：弹出 gadget1 的地址到 `%rip`，跳转到 `pop rdi; ret`
2. `pop rdi` 执行：从栈顶弹出 `0x59b997fa` 到 `%rdi`，`%rsp` 指向 gadget2 的地址
3. `ret` 执行：弹出 gadget2 的地址到 `%rip`，跳转到 `ret`
4. `ret` 执行：弹出 touch3 的地址到 `%rip`，跳转到 `touch3`
5. `touch3` 执行：此时 `%rdi = 0x59b997fa`

**`ret` 指令的作用**：

`ret` 指令等价于 `pop %rip`，它从栈顶弹出一个 8 字节的值作为下一条指令的地址。在 ROP 链中：

- 每个 gadget 末尾的 `ret` 从栈上读取下一个 gadget 的地址
- 这形成了一条隐式的 "程序"，其中 `ret` 充当了 "取指" 的角色
- `%rsp` 充当了 "程序计数器"：栈上 gadget 地址的排列顺序就是 ROP "程序" 的执行顺序

</details>

### 3.4 安全机制

**题目 8**：请说明 Stack Canary 的工作原理，以及为什么 Attack Lab 的程序没有使用 canary。

<details>
<summary>标准答案</summary>

Stack Canary 的工作原理：

1. **插入 canary**：编译器在函数序言中，从 TLS（`%fs:0x28`）读取一个随机值，存储在返回地址之前的栈位置
2. **检查 canary**：编译器在函数尾声中（`ret` 之前），将栈上的 canary 值与 TLS 中的 canary 值进行比较
3. **检测溢出**：如果两者不同，说明栈上的 canary 被覆写（缓冲区溢出），调用 `__stack_chk_fail` 终止程序
4. **正常返回**：如果两者相同，正常执行 `ret`

Attack Lab 不使用 canary 的原因：

1. **教学目的**：Attack Lab 的目标是让学生理解缓冲区溢出的基本原理，如果启用了 canary，学生需要先学习如何绕过 canary，增加了入门难度
2. **编译选项**：Attack Lab 使用 `-fno-stack-protector` 编译选项禁用了 canary
3. **简化实验**：学生可以直接覆盖返回地址，专注于理解栈帧结构和控制流劫持

</details>

**题目 9**：ASLR 和 PIE 的关系是什么？它们各自保护什么？

<details>
<summary>标准答案</summary>

ASLR 和 PIE 的关系：

- **ASLR**（Address Space Layout Randomization）是操作系统级别的安全特性，在每次程序运行时随机化内存布局
- **PIE**（Position Independent Executable）是编译器/链接器级别的安全特性，使程序本身可以被加载到任意地址

两者的关系：**PIE 是 ASLR 对代码段保护的实现方式**。

- 没有 PIE 的程序：代码段地址固定（0x400000），即使 ASLR 启用，代码段也不会被随机化
- 有 PIE 的程序：代码段地址也被随机化，ASLR 可以完全发挥作用

各自保护的内容：

| 保护机制 | 保护的区域 | 不开启时 |
|:---|:---|:---|
| ASLR | 栈、堆、共享库 | 这些区域的地址在每次运行时相同 |
| PIE | 代码段、数据段 | 代码段从固定地址 0x400000 开始 |
| ASLR + PIE | 所有区域 | 所有区域的地址在每次运行时都随机化 |

</details>

**题目 10**：NX 保护如何防止 shellcode 注入？为什么 ROP 能绕过 NX？

<details>
<summary>标准答案</summary>

NX（No-eXecute，又称 DEP/W^X）保护通过将栈和堆的内存页面标记为不可执行来防止 shellcode 注入。

NX 的工作原理：

1. 操作系统在设置内存页面的页表项时，将栈和堆页面的 NX 位置 1
2. 当 CPU 尝试执行位于 NX 页面中的指令时，会触发 Page Fault
3. 内核将 Page Fault 转换为 SIGSEGV 信号，发送给进程
4. 进程因 SIGSEGV 而终止

ROP 绕过 NX 的原因：

1. **Gadget 在代码段中**：ROP 使用的 gadget 来自代码段（.text），代码段是可执行的
2. **不执行新代码**：ROP 不在任何新位置写入和执行代码，只是复用代码段中已有的指令
3. **ret 在代码段中执行**：每次 `ret` 跳转到的地址都在代码段中，不违反 NX 保护

本质上，NX 限制的是"在不可执行的区域执行代码"，而 ROP 始终在可执行的代码段中运行，只是改变了执行的顺序。

</details>

### 3.5 调试与分析

**题目 11**：如何使用 GDB 确定 `getbuf` 的缓冲区起始地址和返回地址的位置？

<details>
<summary>标准答案</summary>

步骤如下：

**第一步：反汇编 getbuf**

```gdb
(gdb) disas getbuf
Dump of assembler code for function getbuf:
   0x00000000004017a8 <+0>:     sub    $0x28,%rsp
   0x00000000004017ac <+4>:     mov    %rsp,%rdi
   0x00000000004017af <+7>:     callq  0x401a10 <Gets>
   0x00000000004017b4 <+12>:    mov    $0x1,%eax
   0x00000000004017b9 <+17>:    add    $0x28,%rsp
   0x00000000004017bd <+21>:    retq
End of assembler dump.
```

**第二步：在 getbuf 入口设断点并运行**

```gdb
(gdb) break *0x4017a8
Breakpoint 1 at 0x4017a8
(gdb) run -q
```

**第三步：单步执行到 sub 指令之后，获取缓冲区地址**

```gdb
(gdb) si                     # 执行 sub $0x28, %rsp

$1 = 0x5561dc78
```

**第四步：查看返回地址**

```gdb
(gdb) x/1xg $rsp+0x28        # 返回地址在缓冲区起始 + 0x28 处
0x5561dca0: 0x0000000000401976
```

总结：
- 缓冲区起始地址：`0x5561dc78`
- 返回地址位置：`0x5561dc78 + 0x28 = 0x5561dca0`
- 返回地址内容：`0x401976`（test 函数中的某个位置）

</details>

**题目 13**：在 Phase 5 中，需要将 cookie 的字符串表示放在栈上，并将 `%rdi` 指向它。请说明为什么要这样做，以及如何确保字符串地址的正确性。

<details>
<summary>标准答案</summary>

为什么需要将 cookie 的字符串表示放在栈上：

1. `touch3` 函数调用 `hexmatch`，需要 `%rdi` 指向一个以 null 结尾的字符串
2. 在 ROP 阶段，不能直接注入代码，只能通过 ROP 链来设置寄存器
3. 字符串不能放在代码段（不可写），必须放在栈上或其他可写区域

如何确保字符串地址的正确性：

1. **计算字符串在栈上的位置**：字符串放在 ROP 链的末尾，地址 = 缓冲区起始 + 填充 + ROP 链字节数
2. **使用 `mov %rsp, %rdi` 或类似 gadget**：在 ROP 链执行到某个位置时，`%rsp` 恰好指向字符串
3. **考虑 `%rsp` 的变化**：每次 `ret` 执行后，`%rsp` 增加 8；每个 `pop` 也会增加 `%rsp`
4. **注意 `hexmatch` 可能覆写栈**：`hexmatch` 在栈上分配了较大的缓冲区，字符串应放在安全位置

</details>

**题目 14**：请解释 `leave` 指令在栈迁移攻击中的作用，画出执行两次 `leave` 后 `%rsp` 的变化过程。

<details>
<summary>标准答案</summary>

`leave` 指令等价于 `mov %rbp, %rsp; pop %rbp`。

在栈迁移攻击中，利用连续两次执行 `leave`，将 `%rsp` 从原始栈迁移到攻击者控制的内存区域。

**第一次 leave（原函数中）**：

```
1. mov %rbp, %rsp    →  rsp = rbp（帧指针位置）
2. pop %rbp          →  rbp = [栈上saved %rbp] = target_addr
                        rsp += 8（指向返回地址）
```

**原函数执行 ret**：跳转到 leave;ret gadget

**第二次 leave（gadget 中）**：

```
1. mov %rbp, %rsp    →  rsp = rbp = target_addr（迁移成功！）
2. pop %rbp          →  rbp = [target_addr]
                        rsp = target_addr + 8
```

**gadget 执行 ret**：跳转到 [target_addr + 8]（ROP 链的第一个 gadget）

**关键点**：

1. 第一次 `leave` 恢复了被覆盖的 `%rbp`（即 target_addr）
2. 第二次 `leave` 将 `%rsp` 设为 `%rbp` 的值（即 target_addr），完成栈迁移
3. 迁移后，`%rsp` 指向攻击者控制的内存区域

</details>

**题目 15**：如果同时启用了 NX、Stack Canary、Full RELRO 和 PIE，是否还能进行缓冲区溢出攻击？请讨论可能的攻击思路。

<details>
<summary>标准答案</summary>

即使同时启用了所有这些保护机制，仍然可能进行缓冲区溢出攻击，但难度大大增加。可能的攻击思路：

1. **信息泄露 + ROP**：泄露 canary 值和代码段基址，构造 ROP 链
2. **Partial Overwrite**：只覆写返回地址的低位字节
3. **ret2libc / ret2csu**：利用 libc 或 __libc_csu_init 中的 gadget
4. **栈迁移到堆**：通过栈迁移将 ROP 链放在堆上
5. **SROP**：利用 `sigreturn` 系统调用一次性设置所有寄存器
6. **JOP**：使用间接跳转代替 `ret` 来串联 gadget
7. **覆盖 .fini_array**：覆写程序退出时调用的函数指针

结论：**安全保护是纵深防御，不是银弹**。每种保护都有其局限性，多种保护的组合可以显著增加攻击难度，但不能完全消除漏洞的风险。

</details>

### Q1：为什么 Attack Lab 中 ctarget 可以用 shellcode 而 rtarget 不行？

**解答**：

核心区别在于 **NX（No-eXecute）保护** 是否开启：

- **ctarget**：编译时使用了 `-z execstack` 选项，使得栈页面被标记为可读可写可执行（RWX）。因此，注入到栈上的 shellcode 可以被 CPU 执行。
- **rtarget**：编译时没有使用 `-z execstack`（使用默认的 `-z noexecstack`），栈页面被标记为可读可写但不可执行（RW-）。因此，当程序跳转到栈上的 shellcode 时，CPU 会因为尝试在不可执行的页面执行指令而触发段错误。

可以通过以下命令验证：

```bash
# 查看 ctarget 的栈权限
$ readelf -l ctarget | grep -A1 GNU_STACK
  GNU_STACK      ... RWE    ← 可执行！

# 查看 rtarget 的栈权限
$ readelf -l rtarget | grep -A1 GNU_STACK
  GNU_STACK      ... RW     ← 不可执行！
```

`RWE` 表示 Read-Write-Execute，`RW` 表示 Read-Write 不可执行。

---

### Q2：ROP 链中的 gadget 是从哪里来的？为什么代码中会有这些看起来没用的指令片段？

**解答**：

ROP gadget 有三个主要来源：

**来源 1：编译器生成的正常代码片段**

编译器在函数尾声中恢复 callee-saved 寄存器，产生 `pop; ret` 序列：

```assembly
addq    $N, %rsp          # 释放局部变量
popq    %rbx               # 恢复 callee-saved 寄存器
popq    %r12               # 恢复 callee-saved 寄存器
...
retq                       # 返回
```

**来源 2：x86 变长指令的非对齐解码**

从代码的中间位置开始解码可能得到完全不同的指令序列：

```assembly
# 原始代码
0x400600:  48 89 c7       mov %rax, %rdi
0x400603:  5b             pop %rbx
0x400604:  c3             ret

# 从 0x400601 开始解码（偏移 1 字节）
0x400601:  89 c7          mov %eax, %edi    ← 不同的 gadget！
0x400603:  5b             pop %rbx
0x400604:  c3             ret
```

**来源 3：Attack Lab 特意设计的 farm.c**

`farm.c` 中定义了一组特殊函数，它们的二进制表示中编码了有用的 gadget：

```c
void setval_210(unsigned *p) {
    *p = 3347663335U;  // 编码了有用的 gadget 字节
}
```

### Q3：小端序到底是怎么回事？为什么地址 0x4017c0 在内存中是 c0 17 40 00 00 00 00 00？

**解答**：

**小端序（Little-Endian）** 的规则是：**最低有效字节存储在最低地址**。

以 `0x00000000004017c0` 为例：

```
这个值的字节拆分（从高位到低位）：
  0x00  0x00  0x00  0x00  0x00  0x40  0x17  0xc0
  ↑高位                                          ↑低位

在内存中的存储（小端序）：
  地址       字节
  0x1000:    0xc0    ← 最低有效字节存储在最低地址
  0x1001:    0x17
  0x1002:    0x40
  0x1003:    0x00
  ...
  0x1007:    0x00    ← 最高有效字节存储在最高地址
```

**记忆方法**：

1. "Little-Endian" = "小端在前" = "最低有效字节在最前面（最低地址）"
2. 数字 `0x12345678`：
   - 大端序：`12 34 56 78`（和日常书写一致）
   - 小端序：`78 56 34 12`（"颠倒"了）

在 Python 中生成小端序字节：

```python
import struct
addr = 0x4017c0
bytes_le = struct.pack('<Q', addr)  # '<' 小端序，'Q' unsigned long long
# 输出：b'\xc0\x17\x40\x00\x00\x00\x00\x00'

# 使用 pwntools
from pwn import *
bytes_le = p64(addr)
```

---

### Q4：为什么栈要从高地址向低地址增长？反过来不行吗？

**解答**：

栈从高地址向低地址增长是历史设计决策，主要原因是：

**1. 避免堆和栈冲突**

```
低地址 ─→  [代码|数据|堆 →→→]  ...  [←←← 栈]  ←─ 高地址
```

堆向高地址增长，栈向低地址增长，两者背向而行，中间有大量空闲空间，不容易碰撞。

**2. 历史兼容性**

x86 架构从 8086 开始就采用了这种设计，所有后续的 x86 处理器都保持了这一传统。

**3. 对安全的影响**

- 缓冲区从低地址开始，溢出时向高地址覆盖
- 返回地址在缓冲区上方（更高地址），恰好是溢出的方向
- 如果栈向高地址增长，缓冲区溢出不会直接覆盖返回地址

---

### Q5：为什么 Phase 2 的 shellcode 可以直接使用 `mov` 指令设置 cookie，而 Phase 3 必须把字符串放在栈上？

**解答**：

这是因为 `touch2` 和 `touch3` 对参数的处理方式不同：

**touch2**：接收 `unsigned int` 值，直接与 cookie 进行数值比较。只需将 cookie 数值放入 `%rdi`。

```assembly
movq    $0x59b997fa, %rdi    # 将 cookie 数值直接放入 %rdi
retq
```

**touch3**：接收 `char *` 字符串指针，通过 `hexmatch` 将 cookie 值转换为字符串后与 `%rdi` 指向的字符串比较。需要 `%rdi` 指向一个以 null 结尾的字符串。

字符串是多个字节的序列，不能通过一个寄存器传递。必须将字符串存储在内存中，然后让 `%rdi` 指向这个位置。

---

### Q6：什么是"栈对齐"？为什么 movaps 会 crash？

**解答**：

**什么是栈对齐？**

System V AMD64 ABI 要求在 `call` 指令执行前，`%rsp` 必须是 16 字节对齐的（即 `%rsp % 16 == 0`）。

**为什么需要 16 字节对齐？**

SSE 指令集中有些指令要求内存操作数 16 字节对齐：

- `movaps`：Move Aligned Packed Single-precision
- `movdqa`：Move Aligned Double Quadword
- `movapd`：Move Aligned Packed Double-precision

这些指令的 "A" 代表 "Aligned"。如果内存操作数未对齐，CPU 触发 General Protection Fault，转换为 SIGSEGV，导致程序崩溃。

**在 ROP 中为什么会出现未对齐？**

1. 每次 `ret` 弹出 8 字节，改变 `%rsp` 的对齐状态
2. 每个 `pop` 也弹出 8 字节
3. 如果 ROP 链中 gadget 的数量使得 `%rsp` 的变化不是 16 的倍数，就会导致未对齐

**修复方法**：在 ROP 链中添加一个额外的 `ret` gadget，消耗 8 字节来修复对齐。

---

### Q7：为什么 GDB 中看到的地址和实际运行的地址不同？ASLR 关了也不一样？

**解答**：

**GDB 和直接运行的区别**：

1. **环境变量不同**：GDB 运行程序时会设置额外的环境变量（如 `LINES`、`COLUMNS`），占用了栈空间
2. **ASLR 的影响**：即使关闭了 ASLR，环境变量的差异也会导致栈地址不同

**Attack Lab 中的解决方法**：

1. **始终在 GDB 中调试**：在 GDB 中获取地址并在 GDB 中验证
2. **关闭 ASLR**：在 GDB 中 `set disable-randomization on`
3. **统一环境变量**：在 GDB 中 `unset env LINES` 和 `unset env COLUMNS`
4. Attack Lab 的 Makefile 已经配置了关闭 ASLR，大多数情况下地址应该是固定的
