# 第6章 存储器层次结构

## 概述

在真实的计算机系统中，存储设备的种类繁多，而且它们的性能差异是极其悬殊的。CPU 寄存器可以在一个时钟周期内被访问，L1 高速缓存需要几个时钟周期，主存则需要几十甚至上百个时钟周期，而磁盘这样的机械设备访问一次可能需要几百万个时钟周期。存储器层次结构（memory hierarchy）正是为了解决这种巨大的速度鸿沟而设计出来的一整套体系：用少量昂贵但极快的存储器，配合大量廉价但较慢的存储器，通过局部性原理（locality）把程序实际使用的数据自动地"提拔"到更快的存储层，从而让整个系统在效果上呈现出接近最快存储器的速度，又拥有接近最慢存储器的容量与低成本。

本章内容是 CSAPP 全书中承上启下的关键一章。它既是对第6章之前所学的计算机组成、指令执行方式的自然延伸，也是理解后续 Cache Lab 实验、理解程序性能优化、理解操作系统虚拟内存机制的基础。本章将按照"存储技术 -> 局部性原理 -> 层次结构总览 -> 高速缓存组织结构 -> 缓存友好编程 -> 矩阵乘法性能案例 -> Cache Lab 实验关联 -> 实际工程应用"这条主线展开，力求把知识点讲透讲全，同时保留大量代码示例、数值计算示例与图示化描述，方便复习和检索。

学习本章时，建议始终带着一个核心问题：**为什么同样功能的代码，只是访问数据的顺序不同，性能就可能相差一个数量级以上？** 本章会从硬件原理一路讲到编程实践，最终把这个问题彻底讲清楚。

## 6.1 存储技术

存储技术是整个存储器层次结构的物理基础。理解 SRAM、DRAM、磁盘、SSD 这几种存储介质的物理原理和性能特征，才能理解为什么计算机系统要设计成金字塔式的多级结构。

### 6.1.1 随机访问存储器（RAM）概述

随机访问存储器分为两类：静态 RAM（SRAM）和动态 RAM（DRAM）。

- SRAM 用于高速缓存存储器（既有片上 cache，也有片外 cache），速度快、但集成度低、功耗高、价格贵。
- DRAM 用于主存以及图形系统的帧缓存，速度慢一些，但集成度高、价格便宜，可以做出很大容量。

两者都是易失性存储器（volatile memory），断电后数据都会丢失，这一点与非易失性存储器（如 ROM、闪存、磁盘）不同。

### 6.1.2 SRAM（六管触发器）与 DRAM（电容）对比

SRAM 的每一个存储位（bit）使用一个双稳态存储单元（bistable memory cell）来存储，这个单元通常由 6 个晶体管组成的触发器电路实现（也有 4 管、8 管的变体，但经典模型是六晶体管结构，即 6T-SRAM）。这种电路有两种稳定状态，分别对应 0 和 1，只要有电就能无限期地保持状态，不需要刷新。

DRAM 的每一位则只用一个电容和一个访问晶体管来存储，电容存的是电荷，电荷多少代表 0 或 1。这种结构因为只有一个电容一个管子，密度可以做得非常高，但存在两个致命弱点：

1. 电容会漏电，几十毫秒内电荷就会流失，所以必须周期性地刷新（refresh），即读出来再写回去，这是"动态"这个名字的由来。
2. 对干扰（如光、电噪声、宇宙射线）很敏感，读操作本身是破坏性的（读了之后电容电荷被破坏，需要重新写回）。

下面是一张对比表，总结两者的核心差异：

| 特性 | SRAM | DRAM |
|---|---|---|
| 存储单元结构 | 六晶体管触发器（6T 双稳态电路） | 单晶体管 + 单电容（1T1C） |
| 存储原理 | 触发器双稳态，不需要刷新 | 电容电荷存储，需要周期性刷新 |
| 相对访问时间 | 快（1 倍作为基准） | 慢（约 10 倍于 SRAM） |
| 是否需要刷新 | 否 | 是（通常每隔几十毫秒刷新一次） |
| 相对集成度（单位面积容量） | 低（约 1/6~1/8） | 高 |
| 相对成本 | 贵（约 8~16 倍于 DRAM） | 便宜 |
| 是否对光/电噪声敏感 | 不敏感 | 敏感 |
| 典型应用场景 | CPU 寄存器堆、L1/L2/L3 Cache | 主存（内存条）、显存 |
| 是否易失 | 是 | 是 |

一句话总结：**SRAM 用晶体管数量换速度和稳定性，DRAM 用简单结构换密度和价格**。这也是为什么处理器里离核心越近的存储（寄存器、L1/L2/L3 cache）全部使用 SRAM，而容量最大的主存却使用 DRAM 的根本原因——cache 需要的是"小而快"，主存需要的是"大而便宜"。

### 6.1.3 传统 DRAM 的组织结构

一个 DRAM 芯片中的单元（cell）被划分为 d 个超单元（supercell），每个超单元由 w 个 DRAM 单元组成，超单元以 r 行 c 列的矩阵形式组织，d = r × c。要访问超单元 (i, j) 中的内容，需要经过：

1. 内存控制器发送行地址 RAS（Row Access Strobe），DRAM 芯片将整个第 i 行的内容复制到一个内部行缓冲区。
2. 内存控制器发送列地址 CAS（Column Access Strobe），DRAM 从行缓冲区中取出第 j 列对应的超单元数据，通过内存总线发送给控制器。

这种行列分时复用地址引脚的做法大大减少了引脚数目，但也带来了一个重要的性能推论：**访问同一行内的不同数据比跨行访问要快**，因为同一行数据已经被缓存在了行缓冲区中，这也是后续讲局部性原理和缓存友好代码时会反复用到的一个硬件事实。

### 6.1.4 内存模块与 DDR 发展历程

DRAM 芯片被封装到内存模块（memory module）中，插到主板的扩展槽上，通过内存总线与内存控制器相连。DDR SDRAM（Double Data Rate Synchronous DRAM）是现代计算机中最主流的内存类型，其最大特点是能在时钟的上升沿和下降沿都传输一次数据，因此叫"双倍速率"。

DDR 内存已经经历了从 DDR1 到 DDR5 的多代发展，每一代在频率、电压、单颗粒容量、预取位数等方面都有显著提升：

| 代际 | 大致发布年份 | 典型频率范围 | 工作电压 | 预取位数（prefetch） | 单条容量量级 | 主要特点 |
|---|---|---|---|---|---|---|
| DDR1 | 2000 | 200~400 MHz | 2.5V | 2n | 128MB~1GB | 首代双倍速率内存，奠定 DDR 架构基础 |
| DDR2 | 2003 | 400~800 MHz | 1.8V | 4n | 256MB~2GB | 功耗降低，频率翻倍 |
| DDR3 | 2007 | 800~2133 MHz | 1.5V（低电压版 1.35V） | 8n | 1GB~8GB | 引入 ODT 端接技术，功耗进一步下降 |
| DDR4 | 2014 | 1600~3200 MHz | 1.2V | 8n | 4GB~32GB | Bank Group 设计提升并行度，支持更大容量 |
| DDR5 | 2020 | 3200~8400+ MHz | 1.1V | 16n | 8GB~128GB | 片内自带电源管理芯片（PMIC），双通道设计（每根内存条拆成两个32位独立子通道） |

从这张表可以看出一个清晰的技术趋势：**频率越来越高、电压越来越低、预取位数越来越大、单颗粒容量越来越大**。这背后的驱动力正是存储器层次结构理论——CPU 的速度提升远远快于 DRAM，为了不让主存成为系统瓶颈，工程师们必须不断从工艺、架构、总线协议等各个角度压榨 DRAM 的带宽。但即便如此，DRAM 的访问延迟相对于 CPU 周期而言依然是巨大的，这也是为什么 cache 存在的意义从未减弱。

### 6.1.5 磁盘存储

磁盘（disk）是一种机械式的非易失存储设备，容量可以做得很大（在 SSD 普及之前，磁盘几乎是大容量存储的唯一选择），但访问速度比 DRAM 慢几万到几百万倍。

**磁盘构造**：磁盘由一个或多个盘片（platter）组成，每个盘片有两个表面（surface），表面覆盖着磁性记录材料。每个表面上有一组同心圆，称为磁道（track），每个磁道被划分为若干扇区（sector），扇区之间由一些不记录数据的间隙（gap）分隔（用于存储格式化信息）。所有盘片安装在一个主轴（spindle）上，以固定的旋转速率（RPM，例如 5400、7200、10000、15000 转/分钟）转动。

- **柱面（cylinder）**：所有盘片上处于相同半径位置的磁道的集合。
- **磁盘驱动器**由一个或多个盘片组成，靠读写头（read/write head）在旋转的盘面上方读写数据，读写头连接在传动臂（actuator arm）上，可以在不同磁道间移动（寻道）。

**磁盘容量计算**：磁盘的容量由以下参数决定：

- 记录密度（recording density）：一英寸磁道上可以存放的位数（bits/inch，简称 bpr）。
- 磁道密度（track density）：从盘片中心出发沿半径方向，每英寸可以有多少条磁道（tracks/inch，简称 tpi）。
- 面密度（areal density）：记录密度与磁道密度的乘积（bits/in²）。

现代磁盘采用多区记录（multiple zone recording）技术：把柱面划分为不同的记录区，同一记录区内的磁道有相同数目的扇区，越靠外的记录区（半径越大）扇区数越多。

磁盘总容量的计算公式为：

```
容量 = 字节数/扇区 × 平均扇区数/磁道 × 磁道数/表面 × 表面数/盘片 × 盘片数/磁盘
```

**示例计算**：假设一个磁盘有 5 个盘片，每个盘片两个表面，每个表面有 20000 条磁道，平均每条磁道 300 个扇区，每个扇区 512 字节，则该磁盘的容量为：

```
512 字节/扇区 × 300 扇区/磁道 × 20000 磁道/表面 × 2 表面/盘片 × 5 盘片
= 512 × 300 × 20000 × 2 × 5 字节
= 30,720,000,000 字节
≈ 30.72 GB（十进制 GB，即 30.72 × 10^9 字节）
```

**磁盘访问时间计算**：读写磁盘上某个扇区所需要的时间由三部分组成：

1. **寻道时间（seek time）**：将传动臂移动到目标磁道所在柱面所需的时间。这是三者中耗时最长的一部分。平均寻道时间 T_seek 一般在 3ms 到 9ms 之间，通常估算为最大寻道时间的三分之一左右。
2. **旋转时间（rotational latency）**：等待目标扇区旋转到读写头下方所需的时间。平均旋转时间是旋转一整圈时间的一半：

```
T_average_rotation = (1/2) × (1 / RPM) × 60 秒/分钟
```

3. **传送时间（transfer time）**：读写头读出或者写入目标扇区内容所需要的时间，依赖于旋转速度和每条磁道的扇区数目：

```
T_transfer = (1 / RPM) × (1 / (平均扇区数/磁道)) × 60 秒/分钟
```

**综合示例**：假设一个磁盘转速为 7200 RPM，平均寻道时间为 9ms，每条磁道平均 400 个扇区，求访问一个扇区的平均总时间。

```
T_avg_rotation = 1/2 × (60 / 7200) 秒 = 1/2 × 8.33ms ≈ 4.17ms

T_transfer = (60 / 7200) 秒 × (1 / 400) ≈ 8.33ms / 400 ≈ 0.02ms

T_access = T_seek + T_avg_rotation + T_transfer
         ≈ 9ms + 4.17ms + 0.02ms
         ≈ 13.19ms
```

可以看到寻道时间和旋转延迟占了绝大部分开销，而真正的数据传送时间几乎可以忽略不计。这就是为什么"顺序访问磁盘"比"随机访问磁盘"快得多的物理原因——顺序访问可以摊薄寻道和旋转这两项开销固定成本，一次寻道之后可以连续读取很多数据。

**逻辑磁盘块**：现代磁盘对操作系统隐藏了复杂的物理几何结构，抽象成一个由 B 个大小为 512 字节的逻辑块构成的序列，逻辑块 0、1、2、... 与磁盘上实际的柱面、表面、磁道、扇区的物理位置有一个映射关系，由磁盘内部的固件（firmware）维护，这个固件也被称为磁盘控制器。

**I/O 总线**：CPU 通过 I/O 总线（如 SCSI、SATA、USB、PCIe/NVMe 等）与磁盘等外部设备通信，数据通过 DMA（Direct Memory Access）方式在设备与主存之间直接传送，不需要 CPU 参与每一个字节的搬运，从而节省 CPU 周期。

### 6.1.6 固态硬盘（SSD）

固态硬盘（Solid State Disk，SSD）是一种基于闪存（flash memory）的存储技术，没有任何机械运动部件，因此没有寻道和旋转延迟，随机访问性能远好于机械磁盘。

**SSD 的基本构造**：一个 SSD 由一个或多个闪存芯片和一个闪存翻译层（flash translation layer）组成。闪存芯片替代了机械磁盘中的旋转盘片，闪存翻译层扮演了磁盘控制器的角色，将来自 CPU 的逻辑块请求翻译成对底层物理闪存芯片的读写指令。

闪存由一系列的块（block）组成，每个块又由若干页（page）组成，典型的页大小是 512 字节到 4KB，每个块由 32 到 128 个页组成，块的大小通常在 16KB 到 512KB 之间。

- 数据以**页**为单位读写。
- 一个页只有在其所属的整个**块**先被整体擦除（所有位都重置为1）之后，才能被重新写入。
- 一旦一个块被擦除，块中的每个页就可以直接写一次，但如果要再次写入，必须先擦除整个块。

**写放大（write amplification）**：由于闪存的写入必须以"先擦除整块、再写入页"的方式进行，当只需要修改块中一小部分数据时，闪存翻译层往往需要：

1. 把整个块（包含要修改和不修改的所有页）读到一个内存缓冲区。
2. 更新缓冲区中要修改的页。
3. 把已经擦除干净的新块（或者原地擦除后的块）整体写回。

这个过程导致**实际写入闪存介质的数据量远大于用户请求写入的数据量**，这个放大倍数就叫写放大。例如用户只想修改 4KB 数据，但所在的块是 256KB，为了完成这次修改，SSD 可能需要读出并重写整个 256KB 的块，写放大系数就是 64 倍。写放大不仅降低了有效写入速度，还会加速闪存的磨损（闪存单元的擦写次数是有限的，通常几千到几万次），因此现代 SSD 内部都有磨损均衡（wear leveling）算法，尽量把擦写操作均匀分布到所有物理块上，延长 SSD 寿命。

**SSD 性能特点总结**：

| 操作类型 | 相对性能 | 原因 |
|---|---|---|
| 顺序读 | 很快 | 无机械延迟，闪存芯片可以并行读取 |
| 随机读 | 快 | 无寻道和旋转延迟，远快于机械磁盘的随机读 |
| 顺序写 | 较快 | 可以利用已擦除的空闲块 |
| 随机写（尤其是小数据量随机写） | 相对慢，且有写放大问题 | 需要先擦除整块再重写，可能触发垃圾回收 |

综合来看，SSD 相较于机械磁盘的优势是随机访问速度快、抗震、功耗低、无噪音，劣势是同等容量下价格更贵、存在有限的擦写寿命、随机写性能不如顺序写。

## 6.2 局部性

局部性原理（principle of locality）是整个存储器层次结构能够有效工作的理论基础。一个编写良好的程序倾向于引用邻近于其他最近引用过的数据项，或者引用最近引用过的数据项本身，这种倾向性，就是局部性。

局部性通常有两种不同的形式：

- **时间局部性（temporal locality）**：一个被引用过一次的存储器位置，很可能在不远的将来被多次引用（例如循环体中反复使用的循环变量）。
- **空间局部性（spatial locality）**：如果一个存储器位置被引用了一次，那么程序很可能在不远的将来引用其附近的一个存储器位置（例如顺序遍历数组）。

### 6.2.1 数据引用的局部性：代码示例

考察下面这个对一维数组求和的函数：

```c
int sumvec(int v[N]) {
    int i, sum = 0;
    for (i = 0; i < N; i++)
        sum += v[i];
    return sum;
}
```

这个函数具有良好的局部性：

- 对变量 `sum` 来说，每次循环迭代都会引用它一次，这是很好的时间局部性。
- 对数组 `v` 来说，向量元素是被顺序读取的（步长为1，stride-1 pattern），这是很好的空间局部性；而且因为整个数组本身占据的空间在存储器中是相对较小的连续区域，重复运行这个函数时也会得到较好的时间局部性（如果数组能常驻 cache）。

再来看一个二维数组求和的例子，它按行优先（row-major）顺序访问：

```c
int sumarrayrows(int a[M][N]) {
    int i, j, sum = 0;
    for (i = 0; i < M; i++)
        for (j = 0; j < N; j++)
            sum += a[i][j];
    return sum;
}
```

在 C 语言中，二维数组在内存中是按行优先顺序存储的，也就是说 `a[i][j]` 和 `a[i][j+1]` 在内存中是相邻的。上面这段代码内层循环 `j` 变化最快，正好是沿着内存中连续地址访问，具有极好的空间局部性。

与之对照的是按列优先顺序访问的版本：

```c
int sumarraycols(int a[M][N]) {
    int i, j, sum = 0;
    for (j = 0; j < N; j++)
        for (i = 0; i < M; i++)
            sum += a[i][j];
    return sum;
}
```

这段代码交换了循环的顺序，内层循环变化的是 `i`，而 `a[i][j]` 和 `a[i+1][j]` 在内存中相距 `N` 个 int（即一整行的长度），访问步长为 N，这就是所谓的**步长为 N 的引用模式（stride-N reference pattern）**。当 N 较大时，几乎每次访问都会落在不同的缓存行（cache line）上，导致极差的空间局部性。

### 6.2.2 步长与性能的关系

一般来说，随着步长的增加，空间局部性下降，从而导致缓存不命中率（miss rate）上升，程序性能显著下降。以下是几种典型步长模式的性能特点总结：

| 访问模式 | 步长 | 空间局部性 | 典型场景 |
|---|---|---|---|
| stride-1（顺序访问） | 1 个元素 | 最好 | 遍历一维数组、按行遍历二维数组（行优先存储） |
| stride-k（k>1，固定步长） | k 个元素 | k 越大越差 | 按列遍历二维数组、访问结构体数组中的某个字段 |
| 随机访问 | 不固定 | 最差 | 哈希表探测、链表遍历、指针追逐（pointer chasing） |

一个直观的实验现象是：对同一个大数组，分别用 stride-1 和 stride-N（N 为数组的列数，即退化为按列遍历）两种方式遍历并求和，前者的运行时间可能只有后者的几分之一甚至十几分之一，尽管两者做的算术运算量完全相同，唯一的区别就是访存顺序不同。这正是"局部性对性能起决定性作用"这一论断的最直接体现，也是 6.6 节矩阵乘法案例研究的理论基础。

**取指令的局部性**：局部性原理不仅适用于数据引用，也适用于程序指令本身的引用。因为程序指令是存放在存储器中的，CPU 必须取出（fetch）这些指令才能执行，对于顺序执行的指令序列，取指令具有良好的空间局部性；循环体代码会被重复执行多次，因而对指令的引用也有良好的时间局部性；循环体越小、循环执行的次数越多，局部性越好。这也是为什么函数调用、条件跳转过多、代码膨胀（code bloat）会拖慢程序的原因之一。

**局部性的定性认识小结**：
1. 重复引用同一个变量的程序具有良好的时间局部性。
2. 对于步长为 k 的引用模式，步长越小，空间局部性越好；stride-1 是最理想的情况。
3. 对于循环，循环体的代码和数据的引用次数与循环迭代次数成正比，因此循环具有良好的时间局部性和空间局部性。

## 6.3 存储器层次结构

### 6.3.1 存储器层次结构金字塔

有了对局部性和存储技术特性的理解，就可以引出存储器层次结构这一核心概念。整个系统的存储设备可以组织成一个金字塔形状的层次结构，从上到下依次是：

```
                    ┌─────────────────┐
             第0级   │  CPU 寄存器      │  最快，容量最小（几百字节），成本最高
                    ├─────────────────┤
             第1级   │  L1 高速缓存(SRAM) │  访问约几个时钟周期，几十 KB
                    ├─────────────────┤
             第2级   │  L2 高速缓存(SRAM) │  访问约十几个时钟周期，几百 KB
                    ├─────────────────┤
             第3级   │  L3 高速缓存(SRAM) │  访问约几十个时钟周期，几 MB（多核共享）
                    ├─────────────────┤
             第4级   │  主存(DRAM)       │  访问约几百个时钟周期，几 GB 到几十 GB
                    ├─────────────────┤
             第5级   │  本地二级存储        │  访问约几十万甚至几百万个时钟周期
                    │  (SSD / 磁盘)      │  几百 GB 到几十 TB
                    ├─────────────────┤
             第6级   │  远程二级存储        │  最慢，容量最大
                    │  (分布式文件系统/云存储)│  几乎不受限
                    └─────────────────┘
                越往上：越快、越小、越贵、由硬件/编译器自动管理
                越往下：越慢、越大、越便宜、由操作系统/程序员显式管理
```

金字塔中每一层的存储设备都是下一层存储设备的"缓存"：寄存器是 L1 cache 中数据的缓存，L1 是 L2 的缓存，L2 是 L3 的缓存，L3（或者说所有 cache）是主存的缓存，主存又是磁盘上文件系统数据的缓存（例如操作系统的页缓存 page cache），而磁盘本身在分布式系统中又可以看作是远程存储或网络文件系统的缓存。

这种层次化设计之所以能生效，其核心逻辑就是 6.2 节所讲的局部性原理：因为程序对数据的访问集中在一个较小的"工作集"（working set）内，所以只要用较小容量的高速存储器缓存这个工作集，绝大多数的访问就可以在快速层完成，只有少数访问才需要深入到慢速层，从而使系统的平均访问速度接近最快层，而容量和成本却接近最慢层。

### 6.3.2 缓存的一般概念

在存储器层次结构中，对于任意相邻的两层，把较高、更靠近 CPU 的一层看作是较低一层的缓存。数据总是以块（block）为单位在两层之间来回复制，块大小对每一对相邻层可以是固定的，也可以是变化的。

### 6.3.3 缓存命中与不命中

当程序需要第 k+1 层的某个数据对象 d 时，它首先在当前存储在第 k 层的一个块中查找 d：

- **缓存命中（cache hit）**：如果 d 恰好缓存在第 k 层，那么这就是一次缓存命中，程序直接从第 k 层读取 d，这比从第 k+1 层读取要快得多。
- **缓存不命中（cache miss）**：如果 d 不在第 k 层，那么这就是一次缓存不命中，此时第 k 层缓存要从第 k+1 层取出包含 d 的那个块，如果第 k 层缓存已经满了，可能会覆盖（驱逐）现存的一个块，被驱逐的块又叫做**牺牲块（victim block）**。选择替换哪个块由缓存的**替换策略（replacement policy）**决定，例如随机替换策略、最近最少使用（LRU）替换策略等。

**不命中的种类细分**：

1. **强制性不命中 / 冷不命中（compulsory miss / cold miss）**：因为缓存是空的（这被称为冷缓存，cold cache），对任何数据对象的第一次访问都不可能命中。冷不命中通常是短暂事件，不会在反复访问存储器的稳定状态中出现。
2. **冲突不命中（conflict miss）**：对大多数缓存而言，一个块只能存放在第 k+1 层中某个有限的块集合中（由映射函数决定），如果缓存足够大，可以缓存这个特定块的多个不同的行，因为存储器的限制，可能只能分配一个单独的行。这样即使缓存远没有装满，两个映射到同一位置的块也会互相驱逐对方，造成不命中，这就叫冲突不命中。
3. **容量不命中（capacity miss）**：当工作集的大小超过了缓存的容量时，缓存会经历容量不命中，也就是说，缓存太小，装不下所有需要的数据对象。

**缓存管理**：存储器层次结构中，每一层的缓存都需要有某种形式的逻辑来管理缓存，即需要判定何时命中/不命中，并决定用什么策略替换牺牲块。管理缓存的逻辑可以是硬件（如 cache 控制器）、软件（如操作系统负责管理主存这层，作为磁盘的缓存）、硬件加软件的结合体（如 TLB），也可以是程序员自身（例如程序员显式地在应用层设计缓存策略）。

## 6.4 高速缓存存储器（重点）

高速缓存存储器（cache memory，简称 cache 或高速缓存）是本章的核心，也是理解现代 CPU 性能特征最关键的知识点。早期计算机系统的存储器层次结构只有三层：CPU 寄存器、DRAM 主存、磁盘存储，但由于 CPU 和主存之间不断增大的速度差异，系统设计者被迫在 CPU 寄存器和主存之间插入了一个小的 SRAM 高速缓存存储器，即 L1 高速缓存，现代系统甚至插入了 L2、L3 多级高速缓存。

### 6.4.1 高速缓存的通用组织结构：S × E × B

假设一个计算机系统中，每个存储器地址有 m 位，形成地址空间 M = 2^m 个不同的地址。这样一台机器的高速缓存被组织成一个由 S = 2^s 个高速缓存组（cache set）的数组，每个组包含 E 个高速缓存行（cache line），每个行由 B = 2^b 字节的数据块（block）、一个有效位（valid bit）指明这个行是否包含有意义的信息，以及 t = m - s - b 个标记位（tag bit）组成，标记位唯一地标识出存储在这个高速缓存行中的块。

高速缓存的结构可以用元组 (S, E, B, m) 来描述，缓存的容量（不含标记位和有效位）为：

```
C = S × E × B  字节
```

结构示意图如下：

```
                                组(Set)
              ┌─────────────────────────────────────────────┐
组0 (Set 0)   │ 行0: 有效位 | 标记(tag) | B0 B1 B2 ... B(B-1) │
              │ 行1: 有效位 | 标记(tag) | B0 B1 B2 ... B(B-1) │
              │ ...                                          │
              │ 行(E-1): 有效位 | 标记(tag) | B0 ... B(B-1)   │
              └─────────────────────────────────────────────┘
组1 (Set 1)   │ 行0 ... 行(E-1)  （结构同上）                  │
   ...
组(S-1)       │ 行0 ... 行(E-1)  （结构同上）                  │

总容量 C = S(组数) × E(每组行数) × B(每行字节数)
```

其中 E 被称为缓存的"路数"（way），E 路组相联的意思就是每个组里有 E 个可以并行比较的行。

### 6.4.2 地址分解：t + s + b

当 CPU 要读一个存储器字（word）时，它将一个存储器地址发送给高速缓存。这个地址被划分成三个字段：

```
┌──────────────────┬──────────────┬───────────────┐
│  标记 tag (t 位)   │  组索引 s (s 位) │  块偏移 b (b 位) │
└──────────────────┴──────────────┴───────────────┘
       m = t + s + b 位
```

- **组索引（set index，s 位）**：用于确定这个地址属于 S 个组中的哪一个组，即选中缓存中的哪一"行的集合"。
- **块偏移（block offset，b 位）**：一旦确定了组和标记都命中的那一行，块偏移位指出所需的数据在这个 B 字节数据块中的起始位置。
- **标记（tag，t 位）**：用于在选中的组内，与该组中每一行的标记位比较，以确定该组中是否有哪一行包含了所要找的那个块（同时该行的有效位必须为1）。

**高速缓存访问的三个步骤**：
1. **组选择（set selection）**：使用地址中间的 s 位组索引，从 S 个组中选出目标组。
2. **行匹配（line matching）**：在选出的组内，将地址中的 t 位标记与该组每一行的标记位逐一比较，同时检查有效位是否为1，如果同时满足有效且标记相等，即为命中。
3. **字抽取（word extraction）**：一旦命中，使用地址中的块偏移 b 位，确定所需数据在这个 B 字节数据块内的起止字节位置，将数据返回给 CPU。

如果行匹配阶段没有找到有效且标记匹配的行，就发生了缓存不命中，需要从下一层存储器中取出包含该数据的块，并按照替换策略放到该组的某一行中（可能需要先驱逐一个牺牲行）。

### 6.4.3 直接映射缓存（Direct-Mapped Cache）完整工作示例

当每个组只有一行（E = 1）时，称为**直接映射高速缓存（direct-mapped cache）**，这是最简单的一种缓存组织形式，因为每个组只有一行，行匹配和字选择都很简单。

**示例设置**：假设有一个直接映射缓存，参数为 (S, E, B, m) = (4, 1, 2, 4)，即：
- S = 4 个组，s = 2 位组索引
- E = 1 路（直接映射）
- B = 2 字节的块，b = 1 位块偏移
- m = 4 位地址，因此 t = m - s - b = 4 - 2 - 1 = 1 位标记

地址格式为：`标记(1位) | 组索引(2位) | 块偏移(1位)`

假设 CPU 依次发出以下地址的读请求（用十进制表示，转换为4位二进制）：0, 1, 7, 8, 0

| 地址(十进制) | 二进制(t\|ss\|b) | 标记 | 组索引 | 块偏移 | 命中/不命中 | 说明 |
|---|---|---|---|---|---|---|
| 0 | 0\|00\|0 | 0 | 00 | 0 | miss（冷不命中） | 组0原本无效，从主存取块[0,1]放入组0，标记设为0 |
| 1 | 0\|00\|1 | 0 | 00 | 1 | hit | 组0标记为0，与地址标记0匹配，直接命中，取块偏移1处字节 |
| 7 | 0\|11\|1 | 0 | 11 | 1 | miss（冷不命中） | 组3原本无效，从主存取块[6,7]放入组3，标记设为0 |
| 8 | 1\|00\|0 | 1 | 00 | 0 | miss（冲突不命中） | 组0当前标记是0，地址标记是1，不匹配，发生冲突不命中，驱逐组0原有块[0,1]，装入新块[8,9]，标记更新为1 |
| 0 | 0\|00\|0 | 0 | 00 | 0 | miss（冲突不命中） | 组0标记已经被上一步改成1，地址0要求标记0，不匹配，再次发生冲突不命中，重新装入块[0,1] |

这个例子非常典型地演示了**抖动（thrashing）**现象：地址 0 和地址 8 都映射到组0（因为 (0 mod 4) == (8 mod 4) == 0），但标记不同，如果程序反复交替访问地址0和地址8，就会导致缓存行反复被驱逐再装入，每次访问都不命中，这就是直接映射缓存在冲突情况下的经典缺陷，也是引出组相联缓存的重要动机。

**直接映射缓存中的行替换**：因为每个组只有一行，所以替换策略非常简单粗暴——新来的块直接覆盖当前这一行的内容，不需要任何选择算法。

### 6.4.4 组相联缓存（Set Associative Cache）和 LRU

当 1 < E < C/B 时（每组多于一行，但又没有多到把所有块放在一个组里），称为 **E 路组相联高速缓存（E-way set associative cache）**。

在组相联缓存中，组选择方式与直接映射缓存完全一样，都是用地址中间的 s 位来确定目标组；但行匹配阶段变得更复杂：需要将地址标记与组内**所有 E 行**的标记逐一比较（且要求该行有效位为1），只要有一行同时满足有效且标记匹配，就是命中。可以把组相联缓存中的每个组看成一个小的全相联缓存，需要用类似 CAM（Content Addressable Memory，内容寻址存储器）的电路并行地比较所有候选标记。

**组相联缓存中的行替换**：当组相联缓存不命中时，需要从内存中取出新的块，如果这个组已经装满了 E 行有效数据，就必须驱逐其中一行腾出空间。常见的替换策略有：

- **随机替换策略**：随机选择一行牺牲，实现简单但效果一般。
- **最不常使用（Least Frequently Used, LFU）**：替换在过去某个时间窗口内被访问次数最少的行。
- **最近最少使用（Least Recently Used, LRU）**：替换最后一次访问时间距现在最久的行，也就是"最久没有被碰过"的那一行。LRU 依据的正是时间局部性原理——如果一个块最近很久没有被访问，那么它在不远的将来被访问的可能性也较低，因此它是最适合被驱逐的候选者。

LRU 是现代处理器高速缓存中最常用的近似替换策略（考虑硬件实现代价，实际处理器往往采用伪LRU、树形LRU等近似算法，而不是严格的LRU计数器）。

**举例说明 2 路组相联缓存与 LRU 的配合**：假设某组是 2 路组相联（E=2），依次访问映射到该组、但标记分别为 A、B、C 的三个块：
1. 访问 A：不命中，组内两行都无效，装入 A 到行0，LRU顺序：[A]（最近使用在前）
2. 访问 B：不命中，行1无效，装入 B 到行1，LRU顺序：[B, A]
3. 访问 A：命中（行0标记为A），更新LRU顺序：[A, B]
4. 访问 C：不命中，两行都已占用（A、B），需要驱逐"最近最少使用"的一行，即 B（因为 A 刚被访问过，B 最久未被访问），驱逐 B，装入 C，LRU顺序：[C, A]

可以看到 LRU 精确跟踪了每一行的访问新鲜度，总是驱逐最"老"的那一行。

### 6.4.5 全相联缓存（Fully Associative Cache）和 TLB

当 E = C/B，即缓存里只有一个组，这个组包含了所有的高速缓存行时，称为**全相联高速缓存（fully associative cache）**。

在全相联缓存中，因为只有一个组，所以地址中没有组索引位（s = 0），地址只分为标记和块偏移两部分。组选择非常平凡（只有一个组可选），但行匹配阶段的开销很大：需要在**所有**行中并行比较标记，如果缓存行数很多，构建这种大规模并行比较电路的硬件成本会变得极其昂贵，速度也会因为要驱动更多比较器而变慢。因此**全相联缓存只适用于容量很小的缓存**。

**TLB（Translation Lookaside Buffer，翻译后备缓冲器）**是全相联缓存的一个典型应用实例。TLB 是虚拟内存系统中的一个小容量高速缓存，用于缓存虚拟地址到物理地址的翻译结果（即页表项 PTE 的缓存），从而避免每次访存都要走一遍多级页表查询这种代价高昂的过程。由于 TLB 的容量通常很小（例如几十到几百个条目），用全相联的方式实现是可行的，因为需要并行比较的行数不多，硬件代价可以接受，而全相联带来的好处是命中率最大化（不会因为映射冲突而产生冲突不命中）。

三种缓存组织方式的对比总结：

| 组织方式 | E（每组行数） | 组选择 | 行匹配开销 | 冲突不命中 | 硬件成本 | 典型应用 |
|---|---|---|---|---|---|---|
| 直接映射 | E = 1 | 简单 | 最低（只比较1行） | 容易发生 | 最低 | 大容量 L2/L3 cache（部分场景） |
| E路组相联 | 1 < E < C/B | 简单 | 中等（比较E行） | 较少 | 中等 | 现代 L1/L2/L3 cache（常见 4路、8路、16路） |
| 全相联 | E = C/B | 平凡（只有1组） | 最高（比较所有行） | 几乎不发生 | 最高 | TLB、小容量特殊缓存 |

### 6.4.6 写策略：写直达与写回

到目前为止讨论的都是读操作（CPU 从缓存中取数据），但缓存同样需要处理写操作（CPU 向存储器写数据）。当 CPU 要写一个已经缓存了的字（写命中，write hit）时，缓存更新了它的这个副本之后，如何更新紧接着低一层中的副本，有两种基本方法：

- **写直达（write-through）**：立即将高速缓存块写回到紧接着的低一层中。优点是实现简单，且低一层的数据始终保持最新（一致性好）；缺点是每次写操作都会引起总线流量，速度较慢。
- **写回（write-back）**：尽可能地推迟存储器更新，只有当替换算法要驱逐这个已经被修改过的块时，才把它写到紧接着的低一层中。因为局部性，写回通常能大大减少总线流量，但实现起来更复杂，需要在每个高速缓存行中维护一个额外的**修改位（dirty bit）**，标识这个块是否被修改过（脏块）；只有脏块被驱逐时才需要写回，干净块可以直接丢弃。

对于写不命中（write miss，即要写的数据当前不在缓存中）的情况，也有两种方法：

- **写分配（write-allocate）**：加载相应的低一层中的块到缓存中，然后更新这个缓存块。写分配试图利用写操作的空间局部性，但每次不命中都需要从低一层传送一个块到高速缓存。
- **非写分配（not-write-allocate）**：直接把这个字写到低一层中，不再加载到缓存中。

写直达和写回两种方式通常是互相独立可以搭配的选择，但在实践中，写回通常与写分配搭配，写直达通常与非写分配搭配。写回是现代高性能处理器 cache 中更常见的策略，因为它能显著降低内存总线的带宽压力。

一个直观的对比总结：

| 写策略 | 何时更新下一层 | 总线流量 | 实现复杂度 | 数据一致性 |
|---|---|---|---|---|
| 写直达 | 每次写命中都立即更新 | 大 | 简单 | 好（下一层始终最新） |
| 写回 | 仅在脏块被驱逐时才更新 | 小 | 复杂（需要dirty bit） | 稍差（下一层可能滞后） |

### 6.4.7 真实高速缓存的层次结构与典型参数

现代微处理器通常支持多级缓存层次结构，典型是 L1、L2、L3 三级，有的还会有 L4，或者在多核系统中共享某一级缓存。L1 缓存通常又划分为独立的 **i-cache（指令缓存）**和 **d-cache（数据缓存）**，这样处理器就可以在同一个时钟周期内同时从两者中取数据，避免结构冲突。

以一个典型的现代 x86-64 处理器（例如某代 Intel Core 系列）为例，其缓存层次的典型参数如下（不同型号会有差异，此处给出的是常见的代表性数值，用于建立直观感受）：

| 缓存级别 | 容量 | 组织方式 | 块大小 | 访问延迟（大致） | 是否核心私有 |
|---|---|---|---|---|---|
| L1 i-cache | 32 KB | 8路组相联 | 64 字节 | 约 4 个时钟周期 | 每核私有 |
| L1 d-cache | 32~48 KB | 8~12路组相联 | 64 字节 | 约 4~5 个时钟周期 | 每核私有 |
| L2 cache（统一） | 256 KB ~ 1.25 MB | 4~16路组相联 | 64 字节 | 约 12~14 个时钟周期 | 每核私有 |
| L3 cache（统一，LLC） | 8 MB ~ 数十 MB | 12~16路组相联 | 64 字节 | 约 40~75 个时钟周期 | 多核共享 |
| 主存 DRAM | 数 GB ~ 数十 GB | —— | —— | 约 200~300+ 个时钟周期 | 全系统共享 |

几个值得关注的规律：
1. **块大小几乎总是 64 字节**，这是现代处理器的行业惯例，源于对空间局部性与总线传输效率的权衡。
2. **越靠近 CPU 的缓存越小、越快、路数相对越少**（L1通常 8路），**越远离 CPU 的缓存越大、越慢、路数相对越多**（L3常见12~16路，用更多路数来降低大容量缓存中的冲突不命中率）。
3. L1、L2 通常是每个物理核心私有的，而 L3（也称 LLC，Last Level Cache，末级缓存）通常是所有核心共享的，这也是多核处理器进行核间数据共享、以及产生**伪共享（false sharing）**、**缓存一致性协议开销**等问题的物理基础。

## 6.5 编写高速缓存友好的代码

理解了高速缓存的工作原理之后，自然而然会引出一个工程实践问题：**如何写出对高速缓存友好（cache-friendly）的代码？** CSAPP 给出的核心指导原则可以总结为以下几点：

1. **让最常见的情况运行得快**。程序通常将大部分时间花在少数几个核心函数上，而这些函数又将大部分时间花在少数几个循环上，所以要重点关注这些热点代码中的存储器引用模式。

2. **尽量减少每个循环内部的缓存不命中数量**。在其他条件相同的情况下，具有良好局部性的代码总是会比局部性差的代码运行得快，因为它引起的缓存不命中数量少。具体细化为两条更可操作的经验法则：
   - **重复引用同一个变量的程序具有良好的时间局部性**。应当尽量把频繁使用的数据放入循环体内的局部变量中反复使用，而不是每次都重新计算或重新从较远的存储层取出。
   - **对于步长为 k 的引用模式（k 是相对于数据类型大小而言的步长），步长越小，空间局部性越好**，因此程序应当尽量按照数据在内存中存储的物理顺序来访问它们，也就是**顺序（stride-1）访问永远优于跳跃式访问**。

3. **对于多维数组，要遵循数据的实际存储顺序进行遍历**。在 C 语言里，二维数组是按行优先存储的，所以应该"外层循环遍历行，内层循环遍历列"，让内层循环连续访问同一行中相邻的元素；应当避免"外层遍历列，内层遍历行"这种会产生大步长访问的写法。

4. **警惕看似等价、局部性却大相径庭的代码写法**。例如两个循环体做的事情在数学上完全一样（比如都是把矩阵所有元素累加起来），但只要遍历顺序不同，其中一个可能是理想的 stride-1 模式，另一个则可能是很差的 stride-N 模式，性能可以相差几倍甚至几十倍。

5. **将小块数据聚合在一起处理（分块，blocking/tiling）**，让一个数据块在被逐出缓存之前，能被尽可能多次地重用，这一技术在处理超出缓存容量的大规模数据（如大矩阵运算）时尤为关键，详见 6.6 节。

6. **减少不必要的内存访问，用寄存器变量代替重复的数组下标访问**，编译器有时能自动完成这种优化，但在关键路径上程序员显式地使用局部变量往往能获得更可靠的收益。

概括起来，缓存友好代码的本质，就是**最大化利用时间局部性和空间局部性，让 CPU 在存储器层次结构中尽量多地"就近取材"，尽量少地"舍近求远"**。

## 6.6 矩阵乘法示例：六种循环顺序分析与分块技术

矩阵乘法是展示局部性原理如何深刻影响程序性能的经典案例。考虑标准的矩阵乘法运算 C = A × B，其中 A、B、C 都是 n×n 的方阵，最朴素的三重循环实现是：

```c
void matmult(double a[n][n], double b[n][n], double c[n][n], int n) {
    int i, j, k;
    for (i = 0; i < n; i++)
        for (j = 0; j < n; j++)
            for (k = 0; k < n; k++)
                c[i][j] += a[i][k] * b[k][j];
}
```

三重循环的三个下标 i、j、k 有 3! = 6 种不同的排列方式，形成六种版本：ijk、jik、ikj、jki、kij、kji。这六种版本在数学上是完全等价的（都计算出同样的结果矩阵 C），但由于内层循环访存模式不同，它们的实际运行性能可能相差数倍。

### 6.6.1 逐一分析六种循环顺序的访存模式

分析的关键在于观察**最内层循环**对 a、b、c 三个数组的访问步长：

**（1）ijk 和 jik 版本**（内层循环变量是 k）：
```c
// ijk 版本
for (i...) for (j...) for (k...)
    c[i][j] += a[i][k] * b[k][j];
```
内层循环 k 变化时：
- `a[i][k]`：i 固定，k 变化，是对 a 数组第 i 行的 stride-1 访问，局部性好。
- `b[k][j]`：j 固定，k 变化，每次 k 增加1，地址增加一整行的跨度（n个元素），是 stride-n 访问，局部性差。
- `c[i][j]`：i、j 都固定，不随 k 变化，可以用寄存器累加，几乎不产生额外访存。

综合下来：每次内层迭代，a 命中率高，b 命中率低，总体访存效果 **中等偏差**。ijk 与 jik 效果相近（只是外两层顺序不同，不影响内层的访存模式，只影响 c 的访问顺序，性能几乎一致）。

**（2）kij 和 kji 版本**（内层循环变量是 j 或 i，但最外层是 k）：
```c
// kij 版本
for (k...) for (i...) for (j...)
    c[i][j] += a[i][k] * b[k][j];
```
内层循环 j 变化时：
- `a[i][k]`：i、k 都固定，不随 j 变化，可以缓存在寄存器中，几乎无额外访存。
- `b[k][j]`：k 固定，j 变化，是对 b 数组第 k 行的 stride-1 访问，局部性好。
- `c[i][j]`：i 固定，j 变化，是对 c 数组第 i 行的 stride-1 访问，局部性好。

综合下来：a 几乎不访存，b、c 都是 stride-1，这是**六种版本中最优的一类**（kij 和 kji 性能相近且最好）。

**（3）jki 和 kji 相关的另一组：jki 和 ikj**（内层循环变量是 i）：
```c
// jki 版本
for (j...) for (k...) for (i...)
    c[i][j] += a[i][k] * b[k][j];
```
内层循环 i 变化时：
- `a[i][k]`：k 固定，i 变化，对 a 数组是 stride-n 访问（按列跳跃），局部性差。
- `b[k][j]`：k、j 都固定，不随 i 变化，几乎无额外访存。
- `c[i][j]`：j 固定，i 变化，对 c 数组也是 stride-n 访问，局部性差。

综合下来：a、c 都是 stride-n 的差访问模式，这是**六种版本中最差的一类**（jki 和 ikj 性能相近且最差）。

### 6.6.2 六种版本性能总结表

综合上面的分析，可以按照内层循环中每次迭代对 A、B、C 三个矩阵产生的"缓存不命中次数量级"进行归类：

| 循环顺序 | 内层循环变量 | A 访问模式 | B 访问模式 | C 访问模式 | 大致相对性能 |
|---|---|---|---|---|---|
| kij | j | 无关（寄存器） | stride-1 | stride-1 | 最快（约1倍，基准） |
| kji | i（外层j,k内层i，此处按惯例kji表示k最外，j次之，i最内） | stride-n | 无关（寄存器） | stride-n | 较快/中等，视具体实现而定 |
| ijk | k | stride-1 | stride-n | 无关（寄存器） | 中等 |
| jik | k | stride-1 | stride-n | 无关（寄存器） | 中等（与ijk相近） |
| jki | i | stride-n | 无关（寄存器） | stride-n | 较慢 |
| ikj | j | 无关（寄存器） | stride-1 | stride-1 | 视具体情况，通常与kij接近或稍慢 |

（说明：不同教材、不同编译器优化选项下，六种版本的具体排名可能有细微差异，但**核心结论高度一致**：以 kij/ikj 为代表的"内层为 stride-1 且能利用寄存器缓存不变量"的版本明显快于以 jki/ikj 为代表的"内层出现大步长访问"的版本，两者性能差距在实践中可以达到 3 倍到 10 倍以上，具体取决于矩阵规模和缓存大小。）核心的定性结论是：**只要内层循环中出现对某个二维数组的 stride-n（大步长）访问，该版本的性能就会明显劣化**；只要内层循环能把某个数组的下标固定住（该数组元素被提到寄存器中重复使用），同时让另外两个数组都保持 stride-1 访问，该版本的性能就会明显更优。

### 6.6.3 分块（Blocking / Tiling）技术

当矩阵规模 n 很大，导致一整行或者整个矩阵都无法装入 cache 时，即使是性能最优的循环顺序（如 kij），也会因为**容量不命中**而导致大量的缓存不命中——因为 B 矩阵的一整行、或者反复扫过的一大片数据可能已经超出了 cache 的容量，等到需要重用时早就被挤出去了。

**分块技术（也称为循环分块，loop tiling）**的核心思想是：把大矩阵切分成能够完整放进 cache 的小块（tile / block），让程序对每个小块进行尽可能多的计算之后再换下一个小块，从而最大化每个被装入 cache 的数据块的重用次数，减少反复调入调出主存的次数。

以矩阵乘法为例，分块版本大致形如：

```c
void matmult_blocked(double a[n][n], double b[n][n], double c[n][n], int n, int bsize) {
    int i, j, k, i1, j1, k1;
    for (i = 0; i < n; i += bsize)
        for (j = 0; j < n; j += bsize)
            for (k = 0; k < n; k += bsize)
                // 对 bsize x bsize 的子块做矩阵乘法累加
                for (i1 = i; i1 < i + bsize; i1++)
                    for (j1 = j; j1 < j + bsize; j1++)
                        for (k1 = k; k1 < k + bsize; k1++)
                            c[i1][j1] += a[i1][k1] * b[k1][j1];
}
```

其中 `bsize`（block size，块大小）是一个需要根据缓存容量精心选择的参数：既要让一个 `bsize × bsize` 大小的子矩阵块（外加参与运算的相关行/列）能够完全放进目标缓存层（比如 L1 或 L2），又不能太小以至于分块带来的调度开销掩盖了收益。

分块技术带来的核心收益是**提升了时间局部性**：在没有分块之前，程序可能对 B 矩阵的某一整行反复扫描 n 次，但由于该行（或整个矩阵）在两次使用之间已经被挤出 cache，每次都要重新从主存加载；分块之后，一个小块被载入 cache 后，会在内层的 i1/j1/k1 三重循环中被反复使用多次才被换出，大大降低了不命中率。

分块是数值计算库（如 BLAS、LAPACK 等高性能线性代数库）中被广泛采用的核心优化手段之一，此外还常与**循环展开（loop unrolling）**、**向量化（SIMD向量指令）**、**多级分块（针对 L1/L2/L3 多级缓存分别分块）**等技术结合使用，以达到接近硬件理论峰值的计算性能。

## 6.7 与 Cache Lab 的关联：缓存模拟器与矩阵转置优化

本章内容与 CSAPP 配套的 Cache Lab（缓存实验）直接对应，Cache Lab 通常分为两个部分：Part A 要求实现一个通用的高速缓存模拟器（cache simulator），Part B 要求编写并优化一个对 cache 友好的矩阵转置函数。以下结合本章的理论，梳理与实验相关的关键要点。

### 6.7.1 Part A：高速缓存模拟器

模拟器（通常命名为 `csim.c`）需要模拟一个通用的高速缓存的行为，其命令行接受的参数正对应了 6.4 节所讲的高速缓存结构参数：

- `-s <s>`：组索引所用的位数，即缓存有 S = 2^s 个组。
- `-E <E>`：每个组的行数（关联度/路数）。
- `-b <b>`：块偏移所用的位数，即每个缓存块大小为 B = 2^b 字节。
- `-t <tracefile>`：内存访问跟踪文件（trace file），文件里的每一行代表一次内存操作，格式类似 `I 0400d7d4,8` 或 `L 0421c7f0,4`、`S 04f6b868,8`、`M 0421980,4` 分别代表指令加载（I，通常忽略不计入）、数据加载（L）、数据存储（S）、数据修改（M，即先加载后存储，相当于一次L紧接一次S）。

模拟器需要维护的核心数据结构，本质上就是 6.4.1 节描述的 S×E 的二维缓存组织结构，每个缓存行至少要记录：有效位（valid bit）、标记位（tag）、以及用于实现 LRU 替换策略的时间戳/计数器（不需要真正存储数据内容，因为 Cache Lab 只关心命中/不命中的统计，不需要真正模拟数据搬运）。

模拟器对每一条访问记录需要：
1. 从地址中按照 6.4.2 节的方法解析出标记 tag 和组索引 set index（块偏移在模拟命中/不命中统计时通常不需要用到，因为不命中与否只取决于 tag 和 set，不取决于块内偏移）。
2. 在对应的组中查找是否有行的有效位为1且标记等于该地址的标记，若有则命中（hit），并更新该行的LRU时间戳。
3. 若没有找到，则不命中（miss）；如果该组还有空行（有效位为0的行），直接装入新数据，标记有效位；如果该组已经装满，则需要根据 LRU 策略找出最久未使用的行进行驱逐（eviction），再装入新数据。
4. 对于 M（修改）操作，相当于连续做一次加载和一次存储，会产生两次访问，但由于存储访问的是同一地址，如果加载命中，存储也必然命中（因为存储发生在加载之后，该行已经被更新为最新访问）。

最终模拟器需要统计并输出三个核心指标：总命中次数（hit）、总不命中次数（miss）、总驱逐次数（eviction），这正是 6.4.3 节直接映射缓存工作示例和 6.4.4 节 LRU 替换策略在实践中的具体编码实现。

### 6.7.2 Part B：矩阵转置优化

Part B 要求编写一个矩阵转置函数（将矩阵 A 转置后的结果写入矩阵 B），并且限制可使用的局部变量数量，目标是最小化在一个特定参数的模拟缓存（通常是 s=5, E=1, b=5，即直接映射、32个组、每块32字节=8个int）下运行时的缓存不命中数目。

矩阵转置 `B[j][i] = A[i][j]` 天然存在一个访存模式上的困境：无论怎样安排循环顺序，A 和 B 中至少有一个矩阵的访问是非 stride-1 的（因为转置操作本身就是把行变成列），这正好呼应了 6.6 节矩阵乘法分析中"总有一个矩阵会被跳跃式访问"的现象。

针对这个问题，Cache Lab 中矩阵转置优化的核心技术手段包括：

1. **分块（blocking）**：与 6.6.3 节讲的分块技术完全同源，把大矩阵切成能够放进缓存的小块（例如针对 32x32 矩阵常用 8x8 分块，因为一个缓存块 32 字节能装下 8 个 int，恰好对应缓存行的大小），确保每次处理一个小块时，这个块所涉及的所有数据都能同时驻留在 cache 中，从而在块内尽量重用已经装入的数据，减少不命中。
2. **避开对角线冲突（避免自映射抖动）**：当矩阵规模恰好是 2 的幂次（比如 32、64）时，矩阵 A 和 B 中处于相同 (i,j) 相对位置、但分别属于不同数组的元素，很容易因为地址的组索引位恰好相同而被映射到直接映射缓存的同一个组，产生剧烈的冲突不命中（尤其是转置操作中处理对角线附近元素时，A[i][i] 和 B[i][i] 天生地址模运算结果相同）。因此常见的优化技巧是在处理对角线所在块时，使用几个额外的局部变量/寄存器暂存一整行数据，避免在 A 和 B 之间来回抖动。
3. **针对不同矩阵尺寸采用不同分块大小**：例如 Cache Lab 中经典的三个测试规模 32x32、64x64、61x67，由于矩阵大小、是否为2的幂次、边界是否对齐等因素不同，最优的分块大小和处理细节也各不相同，需要分别调优（例如 64x64 常用 8x8 块再细分为 4x4 或使用行缓冲技巧，61x67 这种非对齐尺寸则需要专门处理边界残余部分）。
4. **循环展开与临时变量缓存**：通过引入若干局部变量一次性读入一个块内多行/多列的数据到寄存器，减少重复的数组下标计算和潜在的额外访存，这也与 6.5 节"减少不必要的内存访问、用寄存器变量代替重复访问"的原则一致。

Part A 和 Part B 合起来，完整地体现了本章从"理解 cache 硬件结构 -> 用软件模拟其行为 -> 反过来指导实际代码优化"这一闭环学习路径，是把 6.4 节的理论和 6.5、6.6 节的编程原则融会贯通的最佳实践载体。

## 6.8 实际应用：AoS vs SoA、MESI 协议与侧信道

本章最后一节把存储器层次结构的知识延伸到几个更贴近现代工程实践和系统安全的话题，帮助建立更完整的知识图谱。

### 6.8.1 AoS（结构体数组）与 SoA（数组结构体）

在实际工程中，如何组织批量数据的内存布局对缓存性能有着深远影响，其中最经典的对比就是 **AoS（Array of Structures，结构体数组）**与 **SoA（Structure of Arrays，数组结构体）**这两种数据布局方式。

**AoS 写法**（把每个对象的所有字段放在一起，多个对象排成数组）：

```c
struct Particle {
    float x, y, z;      // 位置
    float vx, vy, vz;   // 速度
    float mass;         // 质量
};
struct Particle particles[N];

// 只想更新所有粒子的位置时：
for (int i = 0; i < N; i++) {
    particles[i].x += particles[i].vx * dt;
    particles[i].y += particles[i].vy * dt;
    particles[i].z += particles[i].vz * dt;
}
```

**SoA 写法**（把所有对象的同一字段集中放在一个数组里）：

```c
struct ParticleSystem {
    float x[N], y[N], z[N];
    float vx[N], vy[N], vz[N];
    float mass[N];
};
struct ParticleSystem ps;

for (int i = 0; i < N; i++) {
    ps.x[i] += ps.vx[i] * dt;
    ps.y[i] += ps.vy[i] * dt;
    ps.z[i] += ps.vz[i] * dt;
}
```

**性能差异分析**：如果程序的访问模式是"每次只处理一小部分字段，但要遍历所有对象"（例如上面的例子只用到了位置和速度字段，完全不碰质量字段），AoS 布局会把不需要的字段（如 mass）也一起载入缓存行，浪费了宝贵的缓存空间和带宽，属于比较差的空间局部性利用；而 SoA 布局把同一字段的所有数据连续存放，遍历时是完美的 stride-1 访问，且缓存行中装载的全部是当前计算真正需要的数据，空间局部性利用率最高。这也是为什么在图形学、物理仿真、机器学习等大规模数据并行处理场景中，SoA 通常是首选布局，同时 SoA 也更容易被编译器或手工向量化为 SIMD 指令。

反过来，如果程序的访问模式是"每次要完整处理一个对象的所有字段"（比如遍历粒子列表，对每个粒子做一次完整的物理更新，同时用到位置、速度、质量等全部字段），那么 AoS 反而更有利，因为一个对象的所有字段都紧挨在一起，很可能落在同一个或相邻的缓存行内，一次缓存加载就能取到这个对象的全部数据；而 SoA 在这种场景下反而需要在六七个不同数组间跳跃访问，可能导致更多缓存行的同时占用。

**总结**：AoS/SoA 之争本质上是"按对象处理"还是"按字段处理"这两种不同访问模式在空间局部性上的取舍，选择哪种布局，取决于具体的热点访问模式，这是数据导向设计（Data-Oriented Design）中一个非常核心的实践准则。

### 6.8.2 MESI 缓存一致性协议

在多核处理器系统中，每个核心通常都有自己私有的 L1/L2 缓存，但共享同一份主存。当多个核心的私有缓存中都保留了同一块内存数据的副本时，就必须有一套机制来保证这些副本之间的一致性——即当某个核心修改了它自己缓存中的数据副本后，其它核心不能继续使用它们那份已经过时的旧副本。这套机制被称为**缓存一致性协议（cache coherence protocol）**，其中最经典、应用最广泛的就是 **MESI 协议**。

MESI 协议因为给每个缓存行标记了四种可能的状态而得名：

- **M（Modified，已修改）**：该缓存行的数据已经被当前核心修改过，与主存中的数据不一致（脏数据），并且这是系统中唯一持有该数据副本的缓存（其它核心的缓存中都没有该行的有效副本）。当此行被驱逐或被其他核心请求时，必须先写回主存。
- **E（Exclusive，独占）**：该缓存行的数据和主存中的数据一致，并且这是系统中唯一持有该行副本的缓存。此时如果本核心要对其执行写操作，可以直接原地转为 M 状态，而不需要通知总线上的其它核心（因为没有其它核心持有该数据的副本）。
- **S（Shared，共享）**：该缓存行的数据和主存一致，并且可能同时存在于多个核心的缓存中，大家共享同一份只读副本。任何一个核心如果想写这个数据，必须先通过总线广播一条使无效（invalidate）的消息，通知其它所有持有该副本的核心把自己的副本失效，自己才能转为 M 状态进行修改。
- **I（Invalid，无效）**：该缓存行不包含有效数据，可能是初始状态，也可能是被其它核心的写操作使无效了。

MESI 各状态之间会因为本地读、本地写、总线上侦听到其它核心的读/写请求而发生一系列状态迁移，处理器通过侦听（snooping）总线上的事务，实时监控是否有其它核心正在访问自己缓存行所对应的内存地址，从而做出相应的状态转换和数据传输（例如从 M 状态的核心那里直接把最新数据传给发起请求的核心，而不必先写回主存再重新读取，这被称为 cache-to-cache 传输）。

MESI 协议保证了多核系统中"任意时刻，对同一个内存地址的读操作，所有核心看到的都是最新写入的值"这一基本的一致性语义，是现代多核 CPU 能够正确、高效协作的基石。同时，MESI 协议也带来了一些性能陷阱，其中最著名的就是**伪共享（false sharing）**：当两个逻辑上毫不相关的变量恰好被分配在同一个缓存行内（缓存行通常是 64 字节），如果不同核心分别频繁写入这两个各自独立的变量，就会导致这个缓存行在两个核心之间被反复置为无效、反复重新加载，产生大量不必要的总线流量和延迟，尽管从程序逻辑上看这两个核心其实完全没有共享任何数据。避免伪共享的常见方法是对齐填充（padding），让不同核心频繁写入的变量分别独占各自的缓存行。

### 6.8.3 缓存侧信道攻击（Cache Side-Channel Attacks）

缓存不仅是性能优化的对象，近年来也成为了计算机安全领域的重要攻击面。由于缓存命中和不命中在**时间**上存在显著且可测量的差异（命中通常几个时钟周期，不命中可能是几十到几百个时钟周期），攻击者可以通过精确测量某些内存访问所花费的时间，反推出受害者进程或程序此前访问过哪些内存地址，从而窃取本应严格隔离的敏感信息（如密码、密钥等）。这种利用缓存访问时间差异作为信息泄露通道的攻击方式，统称为**缓存侧信道攻击（cache side-channel attack）**。

几种经典的缓存侧信道攻击技术包括：

- **Flush+Reload**：攻击者首先使用特殊指令（如 x86 的 `clflush`）把一个共享内存页对应的缓存行清空（flush）出缓存，等待受害者执行一段时间后，攻击者再次访问（reload）这个地址并测量访问时间：如果访问很快，说明受害者在此期间访问过这个地址（导致它被重新载入了缓存）；如果访问很慢，说明受害者没有访问过。这种技术常用于窃取共享库、共享内存中的访问模式信息，比如推断 AES 加密算法执行过程中查了哪些 S-box 表项，进而恢复密钥的部分比特。
- **Prime+Probe**：攻击者不依赖共享内存（不像 Flush+Reload 需要与受害者共享物理页），而是先用自己的数据把某个缓存组"填满"（prime），等待受害者执行一段时间后，再重新访问同一组数据并测量时间（probe）：如果受害者在此期间访问过映射到同一组的地址，会驱逐掉攻击者预先填入的数据，导致攻击者重新访问时发生不命中、耗时变长，从而推断出受害者的访问模式。这种方法不需要共享内存，适用范围更广，但需要精确掌握地址到缓存组的映射关系。
- **Meltdown 和 Spectre**：2018年披露的这两个轰动性的处理器级安全漏洞，都是将"乱序执行/预测执行"与"缓存侧信道"结合起来的攻击范例。处理器为了追求性能会推测性地（speculatively）提前执行一些指令，即使这些指令后来被证明是不应该执行的（比如因权限检查失败而应该被阻止的内存读取），处理器架构层面会正确地"撤销"这些指令对寄存器和内存可见状态的影响，但**却往往不会撤销它们对缓存状态造成的副作用**——因为缓存的状态变化被认为是"微架构层面"的，不属于指令集架构承诺要保证正确回滚的可见状态。攻击者正是利用这个疏漏，让处理器推测性地读取本不该读取的特权数据，再把这个数据的值编码成对某个特定地址的缓存访问（命中与否），最后通过 Flush+Reload 之类的技术把这个缓存状态的差异测量出来，从而绕过操作系统的内存隔离机制，窃取本应严格保密的数据（如内核内存、其它进程的内存）。

这一系列侧信道攻击给整个行业敲响了警钟：**存储器层次结构和缓存机制虽然是纯粹为性能而生的优化手段，但性能优化本身可能在无意中打开了信息泄露的通道**。这也从另一个侧面印证了本章开篇所强调的核心观点——高速缓存不仅仅是一个"透明"的性能加速器，理解它的工作原理，无论是对写出高性能代码，还是对分析和防范系统安全漏洞，都是现代软件工程师和安全研究人员必须掌握的基础知识。

## 本章小结

本章以存储器层次结构为主线，系统梳理了从物理存储介质到高速缓存组织结构、再到软件层面缓存友好编程实践的完整知识链条：

1. **6.1 存储技术**：SRAM 用六晶体管触发器实现，速度快、价格贵、无需刷新，用于寄存器和各级 cache；DRAM 用单管单电容实现，密度高、价格低，但需要周期性刷新，用于主存；DDR 内存历经 DDR1 到 DDR5 五代演进，频率不断攀升、电压不断降低；磁盘依靠机械寻道和旋转来定位数据，访问时间由寻道时间、旋转延迟、传送时间三部分构成，容量可以精确计算；SSD 基于闪存，没有机械延迟，但存在"先擦除整块才能重写"的限制，由此产生写放大问题。

2. **6.2 局部性**：分为时间局部性（同一数据被重复访问）和空间局部性（临近数据被顺序访问），访存步长越小，空间局部性越好，程序性能通常也越好。

3. **6.3 存储器层次结构**：从寄存器到 L1/L2/L3 cache，再到主存、本地二级存储、远程二级存储，形成一个越靠上越快越小越贵、越靠下越慢越大越便宜的金字塔结构，每一层都是下一层的缓存，命中与不命中可以细分为冷不命中、冲突不命中、容量不命中三类。

4. **6.4 高速缓存**（本章重点）：通用结构由 S 个组、每组 E 行、每行 B 字节组成，地址被解析为标记(t)+组索引(s)+块偏移(b)三段；直接映射缓存（E=1）实现简单但容易产生冲突抖动；组相联缓存配合 LRU 替换策略能显著缓解冲突问题；全相联缓存命中率最高但硬件代价大，只适合 TLB 这类小容量场景；写策略上写直达简单但总线流量大，写回复杂但效率高；真实处理器普遍采用 L1(私有,8路)/L2(私有)/L3(共享,12-16路) 三级结构，块大小普遍为 64 字节。

5. **6.5 缓存友好代码**：核心原则是让最常见情况运行得快、减少循环内的不命中数量、遵循数组的物理存储顺序进行遍历、优先复用寄存器变量。

6. **6.6 矩阵乘法案例**：六种循环顺序中，能让内层循环保持 stride-1 访问并利用寄存器缓存不变量的版本（如 kij）性能最优，出现大步长访问的版本（如 jki）性能最差；当矩阵规模超出缓存容量时，分块技术通过提升数据重用率来突破容量瓶颈。

7. **6.7 Cache Lab 关联**：Part A 缓存模拟器直接实现了 6.4 节的 S/E/B 结构、地址解析、LRU替换逻辑；Part B 矩阵转置优化则综合运用了分块、避免对角线冲突、寄存器暂存等技术，是本章理论到实践的完整闭环。

8. **6.8 实际应用**：AoS/SoA 布局选择取决于访问模式是"按对象"还是"按字段"；MESI 协议保证多核缓存一致性，但可能引发伪共享问题；缓存的时间差异还催生了 Flush+Reload、Prime+Probe、Meltdown、Spectre 等侧信道攻击技术，提醒我们性能优化机制本身也可能是安全隐患的来源。

## 附录A：直接映射缓存的完整数值工作示例

### A.1 缓存参数

```
S = 4 组 (s = 2 位组索引)
E = 1 行/组 (直接映射)
B = 2 字节/行 (b = 1 位块偏移)
总容量 = S × E × B = 4 × 1 × 2 = 8 字节
```

### A.2 地址分解

一个地址（假设 4 位地址空间，范围 0x0 ~ 0xF）被分解为：

```
地址格式: [标记 t | 组索引 s | 块偏移 b]
  块偏移 b = 1 位 (最低位)，取值 0 或 1，选择块内第 0 或第 1 字节
  组索引 s = 2 位 (中间)，取值 00~11，即组 0~3
  标记 t = 1 位 (最高位)，取值 0 或 1
```

地址分解示例：

```
地址 0x0 = 0000 → tag=0, set=00, offset=0
地址 0x1 = 0001 → tag=0, set=00, offset=1
地址 0x2 = 0010 → tag=0, set=01, offset=0
地址 0x3 = 0011 → tag=0, set=01, offset=1
地址 0x4 = 0100 → tag=0, set=10, offset=0
地址 0x5 = 0101 → tag=0, set=10, offset=1
地址 0x6 = 0110 → tag=0, set=11, offset=0
地址 0x7 = 0111 → tag=0, set=11, offset=1
地址 0x8 = 1000 → tag=1, set=00, offset=0
地址 0x9 = 1001 → tag=1, set=00, offset=1
地址 0xA = 1010 → tag=1, set=01, offset=0
...
地址 0xF = 1111 → tag=1, set=11, offset=1
```

### A.3 访问序列与逐步状态

访问序列：`0x0, 0x1, 0x7, 0x8, 0x0`

---

**第 1 次访问：地址 0x0 → tag=0, set=0, offset=0**

```
初始缓存状态（全部为空）：
组 0: [Valid=0]
组 1: [Valid=0]
组 2: [Valid=0]
组 3: [Valid=0]

查找组 0：Valid=0 → 冷不命中 (Cold Miss)
将块 {0x0, 0x1} 加载到组 0

访问后缓存状态：
组 0: [Valid=1, Tag=0, Data={0x0, 0x1}]
组 1: [Valid=0]
组 2: [Valid=0]
组 3: [Valid=0]

结果: MISS (cold miss)
```

---

**第 2 次访问：地址 0x1 → tag=0, set=0, offset=1**

```
查找组 0：Valid=1, Tag=0 → 匹配！
offset=1 → 返回块内第 1 字节 (即 0x1)

访问后缓存状态（不变）：
组 0: [Valid=1, Tag=0, Data={0x0, 0x1}]
组 1: [Valid=0]
组 2: [Valid=0]
组 3: [Valid=0]

结果: HIT
```

这体现了空间局部性：访问 0x0 时将整个块 {0x0, 0x1} 加载到缓存，随后访问 0x1 直接命中。

---

**第 3 次访问：地址 0x7 → tag=0, set=3, offset=1**

```
查找组 3：Valid=0 → 冷不命中 (Cold Miss)
将块 {0x6, 0x7} 加载到组 3

访问后缓存状态：
组 0: [Valid=1, Tag=0, Data={0x0, 0x1}]
组 1: [Valid=0]
组 2: [Valid=0]
组 3: [Valid=1, Tag=0, Data={0x6, 0x7}]

结果: MISS (cold miss)
```

---

**第 4 次访问：地址 0x8 → tag=1, set=0, offset=0**

```
查找组 0：Valid=1, Tag=0 ≠ 1 → 不命中！
组 0 已有行 (Tag=0)，需替换 → 冲突不命中 (Conflict Miss) + 驱逐 (Eviction)
驱逐旧块 {0x0, 0x1}，加载新块 {0x8, 0x9}

访问后缓存状态：
组 0: [Valid=1, Tag=1, Data={0x8, 0x9}]  ← 替换！
组 1: [Valid=0]
组 2: [Valid=0]
组 3: [Valid=1, Tag=0, Data={0x6, 0x7}]

结果: MISS (conflict miss) + EVICTION
```

关键观察：0x8 和 0x0 映射到同一组（组 0），虽然缓存总容量为 8 字节，但直接映射结构导致它们互相冲突。这就是直接映射缓存的固有缺陷。

---

**第 5 次访问：地址 0x0 → tag=0, set=0, offset=0**

```
查找组 0：Valid=1, Tag=1 ≠ 0 → 不命中！
组 0 已有行 (Tag=1)，需替换 → 冲突不命中 + 驱逐
驱逐块 {0x8, 0x9}，重新加载块 {0x0, 0x1}

访问后缓存状态：
组 0: [Valid=1, Tag=0, Data={0x0, 0x1}]  ← 又替换回来了！
组 1: [Valid=0]
组 2: [Valid=0]
组 3: [Valid=1, Tag=0, Data={0x6, 0x7}]

结果: MISS (conflict miss) + EVICTION
```

这就是经典的**冲突抖动 (Thrashing)**：0x0 和 0x8 交替访问，每次都导致驱逐和重新加载，缓存命中率极低。

### A.4 统计汇总

| 访问序号 | 地址 | Tag | Set | Offset | 结果       | 说明           |
|----------|------|-----|-----|--------|------------|----------------|
| 1        | 0x0  | 0   | 0   | 0      | MISS       | 冷不命中       |
| 2        | 0x1  | 0   | 0   | 1      | HIT        | 空间局部性     |
| 3        | 0x7  | 0   | 3   | 1      | MISS       | 冷不命中       |
| 4        | 0x8  | 1   | 0   | 0      | MISS+EVICTION | 冲突不命中  |
| 5        | 0x0  | 0   | 0   | 0      | MISS+EVICTION | 冲突抖动    |

- 总访问：5
- 命中：1
- 不命中：4
- 驱逐：2
- 命中率：20%

### A.5 如果使用 2 路组相联（E=2）会怎样？

在 E=2 的情况下，组 0 可以容纳两个不同的 Tag，因此 0x0 (tag=0) 和 0x8 (tag=1) 可以共存：

```
第 4 次访问 0x8：组 0 有空行 → MISS (cold)，无需驱逐
第 5 次访问 0x0：组 0 有 tag=0 的行 → HIT！

命中率提升到 2/5 = 40%，且消除了所有驱逐。
```

这正是组相联缓存相比直接映射的核心优势。

**第 1 次访问：0x0 → tag=00, set=0**

```
组 0: [空, 空]
→ MISS (cold)，加载到行 0
```

```
更新 LRU：tag=00 变为最旧

组 1: [空, 空]
```

**第 3 次访问：0x8 → tag=10, set=0**

```
组 0: [tag=00, tag=01] → tag=10 不在 → MISS，无空行 → 需要驱逐！
LRU 策略：驱逐最旧的 tag=00，加载 tag=10
更新 LRU：tag=01 变为最旧，tag=10 为最新

组 0: [tag=01(LRU=1,最旧), tag=10(LRU=0,最新)]

```

**第 4 次访问：0x0 → tag=00, set=0**

```
组 0: [tag=01, tag=10] → tag=00 不在 → MISS，需驱逐！

组 0: [tag=10(LRU=1,最旧), tag=00(LRU=0,最新)]

```

**第 5 次访问：0x4 → tag=01, set=0**

```
组 0: [tag=10, tag=00] → tag=01 不在 → MISS，需驱逐！
LRU 策略：驱逐最旧的 tag=10，加载 tag=01

组 0: [tag=00(LRU=1,最旧), tag=01(LRU=0,最新)]

```

```
组 0: [tag=00, tag=01] → tag=10 不在 → MISS，需驱逐！
```

```
LRU 策略：驱逐最旧的 tag=01，加载 tag=00

组 0: [tag=10(LRU=1,最旧), tag=00(LRU=0,最新)]
结果: MISS + EVICTION
```

### B.4 统计与关键观察

| 序号 | 地址 | Tag   | Set | 结果            | 驱逐的 Tag |
|------|------|-------|-----|-----------------|-----------|
| 1    | 0x0  | 00    | 0   | MISS (cold)     | -         |
| 2    | 0x4  | 01    | 0   | MISS (cold)     | -         |
| 3    | 0x8  | 10    | 0   | MISS+EVICT      | 00        |
| 4    | 0x0  | 00    | 0   | MISS+EVICT      | 01        |
| 5    | 0x4  | 01    | 0   | MISS+EVICT      | 10        |
| 6    | 0x8  | 10    | 0   | MISS+EVICT      | 00        |
| 7    | 0x0  | 00    | 0   | MISS+EVICT      | 01        |

命中率：0/7 = 0%

这展示了一个重要现象：当 3 个不同的块交替访问同一个 2 路组相联的组时，LRU 策略会导致**持续抖动**。这是因为工作集大小（3 个块）超过了相联度（2 路），LRU 无法有效保留任何块。这种现象称为**容量抖动**，解决方案是增加相联度（E=3 即可完美解决此序列）或改变访问模式。

### B.5 LRU vs FIFO vs Random 对比

对于上述访问序列 `0x0, 0x4, 0x8, 0x0, 0x4, 0x8, 0x0`：

```
LRU 策略：0 hit / 7 access = 0% 命中率（如上分析）
  → 每次 3 个块轮转，LRU 总是驱逐马上要用的块

FIFO 策略：0 hit / 7 access = 0% 命中率
  → 同样依次驱逐，结果与 LRU 相同

Random 策略：期望约 0~2 hit / 7 access
  → 有概率保留正确的块，但不保证

最优策略 (OPT/Belady)：4 hit / 7 access = 57% 命中率
  → 第 3 次访问时驱逐未来最晚使用的 tag=10
  → 之后 0x0 和 0x4 都能命中，直到 0x8 再次访问
```

这说明了 LRU 的局限性和 Belady 最优算法的理论价值。

## 附录C：LRU 替换策略的三种实现方法详解

### C.1 计数器法 (Counter-based LRU)

**原理**：每个缓存行关联一个计数器。每次访问某行时，将其计数器清零，其余同组行的计数器加 1。需要替换时，选择计数器最大的行（即最久未使用的行）。

**优点**：实现简单，硬件开销小（每个行只需 log2(E) 位计数器）。

**缺点**：每次命中需要更新同组所有行的计数器，写操作较多。

```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

/* ============================================================
 * 方法1: 计数器法 LRU
 * 每行维护一个计数器，访问时清零该行计数器，其余行+1
 * 替换时选择计数器最大的行
 * ============================================================ */

#define MAX_E 16  /* 最大相联度 */

typedef struct {
    bool     valid;
    uint64_t tag;
    uint8_t  counter;   /* LRU 计数器：0=最近使用，越大越久未用 */
} CacheLine_Counter;

typedef struct {
    CacheLine_Counter lines[MAX_E];
    int E;              /* 实际相联度 */
} CacheSet_Counter;

/* 初始化缓存组 */
void cache_set_init_counter(CacheSet_Counter *set, int E) {
    set->E = E;
    for (int i = 0; i < E; i++) {
        set->lines[i].valid   = false;
        set->lines[i].tag     = 0;
        set->lines[i].counter = 0;
    }
}

/* 在组中查找指定 tag，返回命中的行索引，-1 表示未命中 */
int cache_set_lookup_counter(CacheSet_Counter *set, uint64_t tag) {
    for (int i = 0; i < set->E; i++) {
        if (set->lines[i].valid && set->lines[i].tag == tag) {
            return i;
        }
    }
    return -1;
}

/* 命中时更新 LRU 计数器 */
void cache_set_update_lru_counter(CacheSet_Counter *set, int hit_index) {
    for (int i = 0; i < set->E; i++) {
        if (i != hit_index && set->lines[i].valid) {
            /* 防止溢出 */
            if (set->lines[i].counter < 255) {
                set->lines[i].counter++;
            }
        }
    }
    set->lines[hit_index].counter = 0;
}

/* 查找 LRU 行（计数器最大的行），返回行索引 */
int cache_set_find_lru_counter(CacheSet_Counter *set) {
    int lru_index = 0;
    uint8_t max_counter = 0;

    /* 优先找无效行（空行） */
    for (int i = 0; i < set->E; i++) {
        if (!set->lines[i].valid) {
            return i;
        }
    }

    /* 所有行都有效，找计数器最大的 */
    for (int i = 0; i < set->E; i++) {
        if (set->lines[i].counter > max_counter) {
            max_counter = set->lines[i].counter;
            lru_index   = i;
        }
    }
    return lru_index;
}

/* 插入新行到指定索引 */
void cache_set_insert_counter(CacheSet_Counter *set, int index, uint64_t tag) {
    set->lines[index].valid   = true;
    set->lines[index].tag     = tag;
    set->lines[index].counter = 0;
    cache_set_update_lru_counter(set, index);
}

/* 访问缓存组的主接口
 * 返回值: 0=hit, 1=cold miss, 2=conflict miss (有eviction)
 * evicted_tag: 如果发生驱逐，输出被驱逐的 tag
 */
int cache_set_access_counter(CacheSet_Counter *set, uint64_t tag,
                             uint64_t *evicted_tag) {
    int hit = cache_set_lookup_counter(set, tag);
    if (hit >= 0) {
        /* 命中 */
        cache_set_update_lru_counter(set, hit);
        return 0;
    }

    /* 未命中：找替换行 */
    int victim = cache_set_find_lru_counter(set);
    int result;

    if (set->lines[victim].valid) {
        /* 冲突不命中，需要驱逐 */
        if (evicted_tag) {
            *evicted_tag = set->lines[victim].tag;
        }
        result = 2;
    } else {
        /* 冷不命中，有空行 */
        result = 1;
    }

    cache_set_insert_counter(set, victim, tag);
    return result;
}
```

### C.2 栈法 (Stack-based LRU)

**原理**：维护一个栈，栈顶是最近使用的行，栈底是最久未使用的行。命中时将对应行移到栈顶；替换时弹出栈底。

**优点**：逻辑直观，命中时只需移动一个元素。

**缺点**：每次命中需要遍历栈找到对应行，然后移到栈顶，时间复杂度 O(E)。

```c
/* ============================================================
 * 方法2: 栈法 LRU
 * 维护一个栈，栈顶=MRU（最近使用），栈底=LRU（最久未用）
 * 命中时把对应行移到栈顶；替换时弹出栈底
 * ============================================================ */

typedef struct {
    bool     valid;
    uint64_t tag;
} CacheLine_Stack;

typedef struct {
    CacheLine_Stack stack[MAX_E]; /* stack[0]=MRU, stack[E-1]=LRU */
    int E;
    int count; /* 当前有效行数 */
} CacheSet_Stack;

void cache_set_init_stack(CacheSet_Stack *set, int E) {
    set->E     = E;
    set->count = 0;
    for (int i = 0; i < E; i++) {
        set->stack[i].valid = false;
        set->stack[i].tag   = 0;
    }
}

/* 在栈中查找指定 tag，返回索引，-1 表示未找到 */
int cache_set_lookup_stack(CacheSet_Stack *set, uint64_t tag) {
    for (int i = 0; i < set->count; i++) {
        if (set->stack[i].tag == tag) {
            return i;
        }
    }
    return -1;
}

/* 将指定索引的行移到栈顶（MRU 位置） */
void cache_set_move_to_top_stack(CacheSet_Stack *set, int index) {
    if (index == 0) return; /* 已经在栈顶 */

    CacheLine_Stack tmp = set->stack[index];
    /* 将 index 上方的元素全部下移一位 */
    for (int i = index; i > 0; i--) {
        set->stack[i] = set->stack[i - 1];
    }
    set->stack[0] = tmp;
}

/* 将新 tag 压入栈顶 */
void cache_set_push_stack(CacheSet_Stack *set, uint64_t tag) {
    if (set->count < set->E) {
        /* 还有空位：元素全部下移一位，新元素放栈顶 */
        for (int i = set->count; i > 0; i--) {
            set->stack[i] = set->stack[i - 1];
        }
        set->stack[0].valid = true;
        set->stack[0].tag   = tag;
        set->count++;
    } else {
        /* 栈满：弹出栈底（LRU），其余下移，新元素放栈顶 */
        if (set->E > 1) {
            for (int i = set->E - 1; i > 0; i--) {
                set->stack[i] = set->stack[i - 1];
            }
        }
        set->stack[0].valid = true;
        set->stack[0].tag   = tag;
    }
}

/* 访问缓存组的主接口 */
int cache_set_access_stack(CacheSet_Stack *set, uint64_t tag,
                           uint64_t *evicted_tag) {
    int hit = cache_set_lookup_stack(set, tag);
    if (hit >= 0) {
        /* 命中：移到栈顶 */
        cache_set_move_to_top_stack(set, hit);
        return 0;
    }

    /* 未命中 */
    int result;
    if (set->count < set->E) {
        /* 有空位：冷不命中 */
        result = 1;
    } else {
        /* 栈满：冲突不命中，驱逐栈底 */
        if (evicted_tag) {
            *evicted_tag = set->stack[set->E - 1].tag;
        }
        result = 2;
    }

    cache_set_push_stack(set, tag);
    return result;
}
```

### C.3 链表法 (Linked List-based LRU)

**原理**：使用双向链表，头部是 MRU，尾部是 LRU。用哈希表建立 tag 到链表节点的映射，实现 O(1) 查找。命中时将节点移到头部；替换时删除尾部节点。

**优点**：查找 O(1)（借助哈希表），更新 O(1)，是最高效的实现。

**缺点**：实现复杂，需要额外空间存储指针和哈希表。

```c
/* ============================================================
 * 方法3: 双向链表 + 哈希表法 LRU
 * 链表头部=MRU，尾部=LRU
 * 哈希表实现 tag → 链表节点 的 O(1) 查找
 * 命中时将节点移到头部；替换时删除尾部节点
 * 这是 Linux 内核和 Redis 中实际使用的 LRU 实现方式
 * ============================================================ */

#include <stdlib.h>

/* 双向链表节点 */
typedef struct LRUNode {
    uint64_t          tag;
    struct LRUNode   *prev;  /* 指向前一个节点（更旧的） */
    struct LRUNode   *next;  /* 指向后一个节点（更新的） */
} LRUNode;

/* 简易哈希表节点（链地址法，实际中可用更高效的哈希表） */
typedef struct HashEntry {
    uint64_t           tag;
    LRUNode           *node;
    struct HashEntry  *next;  /* 哈希冲突链 */
} HashEntry;

#define HASH_TABLE_SIZE 256

typedef struct {
    LRUNode    *head;          /* MRU 端 */
    LRUNode    *tail;          /* LRU 端 */
    int         count;
    int         capacity;      /* = E */
    HashEntry  *hash_table[HASH_TABLE_SIZE];
} CacheSet_List;

/* 哈希函数 */
uint32_t hash_func(uint64_t tag) {
    return (uint32_t)(tag % HASH_TABLE_SIZE);
}

/* 哈希表查找 */
LRUNode *hash_lookup(CacheSet_List *set, uint64_t tag) {
    uint32_t idx = hash_func(tag);
    HashEntry *entry = set->hash_table[idx];
    while (entry) {
        if (entry->tag == tag) {
            return entry->node;
        }
        entry = entry->next;
    }
    return NULL;
}

/* 哈希表插入 */
void hash_insert(CacheSet_List *set, uint64_t tag, LRUNode *node) {
    uint32_t idx = hash_func(tag);
    HashEntry *entry = (HashEntry *)malloc(sizeof(HashEntry));
    entry->tag   = tag;
    entry->node  = node;
    entry->next  = set->hash_table[idx];
    set->hash_table[idx] = entry;
}

/* 哈希表删除 */
void hash_delete(CacheSet_List *set, uint64_t tag) {
    uint32_t idx = hash_func(tag);
    HashEntry *entry  = set->hash_table[idx];
    HashEntry *prev   = NULL;
    while (entry) {
        if (entry->tag == tag) {
            if (prev) {
                prev->next = entry->next;
            } else {
                set->hash_table[idx] = entry->next;
            }
            free(entry);
            return;
        }
        prev  = entry;
        entry = entry->next;
    }
}

void cache_set_init_list(CacheSet_List *set, int E) {
    set->head     = NULL;
    set->tail     = NULL;
    set->count    = 0;
    set->capacity = E;
    memset(set->hash_table, 0, sizeof(set->hash_table));
}

/* 将节点移到链表头部（MRU 端） */
void move_to_head_list(CacheSet_List *set, LRUNode *node) {
    if (node == set->head) return; /* 已在头部 */

    /* 从当前位置摘除 */
    if (node->prev) {
        node->prev->next = node->next;
    }
    if (node->next) {
        node->next->prev = node->prev;
    }
    if (node == set->tail) {
        set->tail = node->prev;
    }

    /* 插入头部 */
    node->prev = NULL;
    node->next = set->head;
    if (set->head) {
        set->head->prev = node;
    }
    set->head = node;
    if (!set->tail) {
        set->tail = node;
    }
}

/* 在链表头部插入新节点 */
LRUNode *insert_at_head_list(CacheSet_List *set, uint64_t tag) {
    LRUNode *node = (LRUNode *)malloc(sizeof(LRUNode));
    node->tag   = tag;
    node->prev  = NULL;
    node->next  = set->head;
    if (set->head) {
        set->head->prev = node;
    }
    set->head = node;
    if (!set->tail) {
        set->tail = node;
    }
    set->count++;
    return node;
}

/* 删除链表尾部节点（LRU 端）并返回被驱逐的 tag */
uint64_t remove_tail_list(CacheSet_List *set) {
    LRUNode *lru = set->tail;
    uint64_t evicted_tag = lru->tag;

    set->tail = lru->prev;
    if (set->tail) {
        set->tail->next = NULL;
    } else {
        /* 只有一个节点的情况 */
        set->head = NULL;
    }

    hash_delete(set, evicted_tag);
    free(lru);
    set->count--;
    return evicted_tag;
}

/* 访问缓存组的主接口 */
int cache_set_access_list(CacheSet_List *set, uint64_t tag,
                          uint64_t *evicted_tag) {
    LRUNode *node = hash_lookup(set, tag);
    if (node) {
        /* 命中：移到头部 */
        move_to_head_list(set, node);
        return 0;
    }

    /* 未命中 */
    int result;
    if (set->count < set->capacity) {
        /* 有空位：冷不命中 */
        result = 1;
    } else {
        /* 满了：驱逐 LRU */
        if (evicted_tag) {
            *evicted_tag = remove_tail_list(set);
        } else {
            remove_tail_list(set);
        }
        result = 2;
    }

    LRUNode *new_node = insert_at_head_list(set, tag);
    hash_insert(set, tag, new_node);
    return result;
}

/* 释放所有资源 */
void cache_set_free_list(CacheSet_List *set) {
    LRUNode *node = set->head;
    while (node) {
        LRUNode *next = node->next;
        free(node);
        node = next;
    }
    for (int i = 0; i < HASH_TABLE_SIZE; i++) {
        HashEntry *entry = set->hash_table[i];
        while (entry) {
            HashEntry *next = entry->next;
            free(entry);
            entry = next;
        }
    }
    set->head  = NULL;
    set->tail  = NULL;
    set->count = 0;
}
```

### C.4 三种方法对比总结

| 特性             | 计数器法       | 栈法           | 链表法           |
|-----------------|---------------|---------------|-----------------|
| 查找复杂度       | O(E)          | O(E)          | O(1) (哈希表)   |
| 更新复杂度       | O(E)          | O(E)          | O(1)            |
| 空间开销         | O(E × log E)  | O(E)          | O(E) + 哈希表   |
| 硬件实现难度     | 低            | 中            | 高              |
| 软件实现复杂度   | 低            | 中            | 高              |
| 适用场景         | 硬件缓存(E小)  | 软件缓存      | OS页面缓存/Redis|
| 实际应用         | CPU L1/L2     | 教学模拟器    | Linux page cache|

在 Cache Lab 的 Part A 中，推荐使用**计数器法**，因为：
1. E 值通常很小（1~16），O(E) 的复杂度完全可接受
2. 实现简单，不容易出错
3. 不需要动态内存分配

## 附录D：矩阵转置缓存分析

### D.1 问题设定

```
矩阵大小: 32 × 32，元素为 int (4 字节)
矩阵总大小: 32 × 32 × 4 = 4096 字节 = 4 KB

缓存参数: s=5, E=1, b=5
  S = 2^5 = 32 组
  E = 1 (直接映射)
  B = 2^5 = 32 字节
  总容量 = 32 × 1 × 32 = 1024 字节 = 1 KB
```

### D.2 地址映射分析

每个缓存行 32 字节 = 8 个 int 元素。

对于矩阵 A（基地址假设为 0x0，按行主序存储）：

```
A[i][j] 的地址 = (i × 32 + j) × 4

块偏移: 地址低 5 位 → (i × 32 + j) × 4 的低 5 位
  = ((i × 32 + j) << 2) & 0x1F
  注意 32 × 4 = 128 = 0x80，所以 i 的变化不影响低 7 位
  块偏移 = (j × 4) & 0x1F → j=0~7 对应 offset=0, j=8~15 对应 offset=0, ...
  实际上 j × 4 的低 5 位：j=0→0, j=1→4, j=2→8, ..., j=7→28, j=8→0(回到块头)
  所以每 8 个元素占一个缓存行

组索引: 地址的第 5~9 位 (s=5)
  组索引 = ((i × 32 + j) × 4 >> 5) & 0x1F
  = ((i × 32 + j) >> 3) & 0x1F  (因为 ×4 然后 >>5 = >>3)
  = (i × 4 + j / 8) & 0x1F

标记: 地址的高位
```

**关键发现**：`组索引 = (i × 4 + j / 8) & 0x1F`

对于矩阵 A 和矩阵 B 的转置操作 `B[j][i] = A[i][j]`：

- 读 A[i][j]：组索引 = (i × 4 + j/8) & 0x1F
- 写 B[j][i]：组索引 = (j × 4 + i/8) & 0x1F

### D.3 朴素转置的冲突不命中分析

朴素转置代码：

```c
void transpose_naive(int A[32][32], int B[32][32]) {
    for (int i = 0; i < 32; i++) {
        for (int j = 0; j < 32; j++) {
            B[j][i] = A[i][j];
        }
    }
}
```

#### 对角线冲突问题

当 `i = j` 时（对角线元素）：
- A[i][i] 的组索引 = (i × 4 + i/8) & 0x1F
- B[i][i] 的组索引 = (i × 4 + i/8) & 0x1F

**两者组索引完全相同！** 由于 E=1（直接映射），A[i][i] 和 B[i][i] 映射到同一个缓存组，互相冲突。

当读取 A[i][i] 后，A 的块被加载到该组。紧接着写 B[i][i] 时，发现 B 的块不在缓存中（被 A 的块占据了），导致冲突不命中，需要驱逐 A 的块来加载 B 的块。这产生了**乒乓效应**。

#### 冲突次数计算

对角线上有 32 个元素，每个都产生冲突。但更严重的是，对角线元素所在的整个 8 元素块都会受到影响。

对于第 i 行第 j 列的访问（i 行 j 列遍历）：

```
A[i][j] 所在块: A[i][j/8 × 8 .. j/8 × 8 + 7]
  组索引 = (i × 4 + j/8) & 0x1F

B[j][i] 所在块: B[j][i/8 × 8 .. i/8 × 8 + 7]
  组索引 = (j × 4 + i/8) & 0x1F
```

当 `(i × 4 + j/8) & 0x1F == (j × 4 + i/8) & 0x1F` 时发生冲突。

化简：`i × 4 + j/8 ≡ j × 4 + i/8 (mod 32)`

即 `4i - i/8 ≡ 4j - j/8 (mod 32)`，当 i = j 时必然成立。

#### 不命中统计（朴素方法）

```
A 矩阵读取：
  每行 32 个 int = 4 个缓存行
  32 行 × 4 行 = 128 个块，首次访问全部 cold miss = 128 次 miss

B 矩阵写入：
  按列写入，每列 32 个 int = 4 个缓存行
  32 列 × 4 行 = 128 个块，首次访问全部 cold miss = 128 次 miss
  但对角线位置有额外冲突...

总 miss ≈ 256 + 额外冲突 miss
```

实际上，由于 B 的写入按列进行，每写一个元素就跳到下一个缓存行（因为 B 按行存储，按列访问 stride=32×4=128 字节），导致每个元素都是 miss。

### D.4 8×8 分块转置分析

分块转置代码：

```c
void transpose_blocked(int A[32][32], int B[32][32]) {
    for (int ii = 0; ii < 32; ii += 8) {
        for (int jj = 0; jj < 32; jj += 8) {
            for (int i = ii; i < ii + 8; i++) {
                for (int j = jj; j < jj + 8; j++) {
                    B[j][i] = A[i][j];
                }
            }
        }
    }
}
```

#### 为什么 8×8 分块有效？

**缓存行容量分析**：
- 每个缓存行 = 32 字节 = 8 个 int
- 8×8 分块恰好：每行 8 个 int 正好占 1 个缓存行

**A 矩阵的访问模式**（分块内）：
```
A[ii..ii+7][jj..jj+7]
  每行 8 个 int = 1 个缓存行
  8 行 = 8 个缓存行
  组索引 = (i × 4 + j/8) & 0x1F

  对于 i = ii..ii+7, j = jj..jj+7:
    j/8 = jj/8 (块内 j 都在同一个 8 元素组内)
    组索引 = (i × 4 + jj/8) & 0x1F
```

当 ii 从 0 到 24（步长 8），i 的变化范围是 8 行：
- i × 4 的变化范围是 0, 4, 8, 12, 16, 20, 24, 28（mod 32）
- 加上 jj/8 的偏移后，8 个不同的组索引，互不冲突

**B 矩阵的访问模式**（分块内）：
```
B[jj..jj+7][ii..ii+7]
  每行 8 个 int = 1 个缓存行
  组索引 = (j × 4 + ii/8) & 0x1F

  对于 j = jj..jj+7:
    组索引 = (j × 4 + ii/8) & 0x1F
    j × 4 的变化范围 = jj×4, jj×4+4, ..., jj×4+28 (mod 32)
```

#### 缓存使用情况逐步分析（以 ii=0, jj=0 为例）

```
初始状态：缓存为空（32 组，每组 1 行）

处理 A[0][0..7] → B[0..7][0]:
  读 A[0][0]: 组索引 = (0×4 + 0) & 31 = 0 → MISS (cold)，加载块 A[0][0..7]
  写 B[0][0]: 组索引 = (0×4 + 0) & 31 = 0 → MISS (cold)！冲突！
    A[0][0..7] 被驱逐，加载 B[0][0..7]

  读 A[0][1]: 组索引 = 0 → MISS (conflict)！B[0][0..7] 被驱逐，重新加载 A[0][0..7]
  写 B[1][0]: 组索引 = (1×4 + 0) & 31 = 4 → MISS (cold)，加载 B[1][0..7]

  读 A[0][2]: 组索引 = 0 → HIT！（A[0][0..7] 仍在缓存中）

  ... 继续 ...
```

可以看到，即使分块后，对角线块（ii=jj）仍然存在冲突。解决方法是对对角线块做特殊处理。

#### 对角线块优化

对角线块（ii == jj）的核心问题是 A 和 B 的对应元素映射到同一缓存组。解决方案：

```c
/* 对角线分块特殊处理：先读入寄存器，再写入 B */
void transpose_diag_block(int A[32][32], int B[32][32], int ii) {
    for (int i = ii; i < ii + 8; i++) {
        /* 一次性读入整行到寄存器 */
        int a0 = A[i][ii];
        int a1 = A[i][ii+1];
        int a2 = A[i][ii+2];
        int a3 = A[i][ii+3];
        int a4 = A[i][ii+4];
        int a5 = A[i][ii+5];
        int a6 = A[i][ii+6];
        int a7 = A[i][ii+7];

        /* 再写入 B，此时 A 的缓存行已被读完，不再冲突 */
        B[ii+0][i] = a0;
        B[ii+1][i] = a1;
        B[ii+2][i] = a2;
        B[ii+3][i] = a3;
        B[ii+4][i] = a4;
        B[ii+5][i] = a5;
        B[ii+6][i] = a6;
        B[ii+7][i] = a7;
    }
}
```

这样 A 行只需要加载一次（1 miss），写入 B 时虽然每个 B 行也是 miss，但不会与 A 产生乒乓冲突。

#### 分块后的 miss 统计

```
非对角线块 (ii ≠ jj): 共 12 个块（32/8=4 行分块，4×4-4=12 个非对角线块）
  每块: A 读 8 miss + B 写 8 miss = 16 miss
  小计: 12 × 16 = 192 miss

对角线块 (ii == jj): 共 4 个块
  使用寄存器暂存后:
  每块: A 读 8 miss + B 写 8 miss = 16 miss（但无乒乓冲突）
  小计: 4 × 16 = 64 miss

总计: 192 + 64 = 256 miss
```

而朴素方法大约 300+ miss，分块+对角线优化能减少约 15-20% 的 miss。

### D.5 缓存行使用可视化

以 8×8 分块为例，展示一个非对角线块 ii=0, jj=8 的缓存使用：

```
缓存组  | 加载顺序
--------|----------------------------------
组 0    | A[0][8..15] (tag=...) → B[0][0..7] (tag=...)
组 4    | A[1][8..15]           → B[1][0..7]
组 8    | A[2][8..15]           → B[2][0..7]
组 12   | A[3][8..15]           → B[3][0..7]
组 16   | A[4][8..15]           → B[4][0..7]
组 20   | A[5][8..15]           → B[5][0..7]
组 24   | A[6][8..15]           → B[6][0..7]
组 28   | A[7][8..15]           → B[7][0..7]

由于 A 和 B 的组索引不同（非对角线），不产生冲突
每个块只需 16 次 miss (8 读 + 8 写)
```

## 附录E：存储器山的详细解释

### E.1 什么是存储器山

存储器山 (Memory Mountain) 是 CSAPP 中提出的一个经典概念，用来直观展示存储器层次结构的性能特征。它是一个三维地形图：

- **X 轴**：空间局部性 — 步长 (stride)，从 1 到大值
- **Y 轴**：时间局部性 — 工作集大小 (working set size)，从小到大
- **Z 轴**：读吞吐率 — 单位 MB/s

通过系统地变化工作集大小和访问步长，测量每种组合下的内存读吞吐率，可以绘制出一座"山"的形状，山脊和山谷反映了缓存层级和局部性效应。

### E.2 如何测量

测量程序的核心思想：

```c
/* 存储器山测量程序核心循环 */
void run(long size, int stride, double *ghz) {
    double cycles;
    int *data = (int *)malloc(size);
    /* 初始化数据 */
    for (long i = 0; i < size / sizeof(int); i++) {
        data[i] = i;
    }

    /* 预热缓存 */
    long limit = size - stride;
    long acc = 0;
    for (long i = 0; i < limit; i += stride) {
        acc += data[i];
    }

    /* 正式测量 */
    cycles = fcyc2(test, data, size, stride, 0);  /* 使用 CPU 时间戳 */

    /* 计算吞吐率 */
    /* throughput = (size / stride) × sizeof(int) / cycles × clock_rate */
    free(data);
}

/* 测试函数：反复读取数据 */
void test(int *data, long size, int stride) {
    long limit = size - stride;
    long acc = 0;
    for (long i = 0; i < limit; i += stride) {
        acc += data[i];
    }
    /* 防止编译器优化掉 */
    if (acc == 0xdeadbeef) {
        printf("dummy\n");
    }
}
```

测量方法：
1. 固定一个工作集大小 `size`
2. 固定一个步长 `stride`
3. 重复顺序读取整个工作集，测量时间
4. 计算吞吐率 = 数据量 / 时间
5. 遍历所有 (size, stride) 组合，绘制三维图

### E.3 如何解读三维图

存储器山的解读要点：

```
                    高吞吐率
                       ↑
                       |    L1 脊
                       |   ╱
                       |  ╱  L2 脊
                       | ╱  ╱
                       |╱  ╱  L3 脊
                       |  ╱  ╱  主存高原
                       | ╱  ╱  ╱
         ──────────────┼─────╱──→ 步长 (stride) 增大
                       |  ╱
              工作集大小↓ (size) 增大
```

#### 关键地形特征

**1. L1 脊 (L1 Ridge)**
- 位置：工作集 < L1 容量（通常 32KB）
- 特征：无论步长多大，吞吐率都很高（接近 L1 带宽）
- 原因：数据完全在 L1 中，步长只影响空间局部性，但 L1 访问只需 3~4 周期

**2. L2 脊 (L2 Ridge)**
- 位置：L1 < 工作集 < L2 容量（通常 256KB~1MB）
- 特征：步长=1 时吞吐率较高，随步长增大而下降
- 原因：数据不在 L1，但 L2 命中；步长增大导致每次缓存行加载只利用部分数据

**3. L3 脊 (L3 Ridge)**
- 位置：L2 < 工作集 < L3 容量（通常 8~32MB）
- 特征：吞吐率进一步降低，步长敏感性更强
- 原因：L3 访问延迟更高（40~70 周期）

**4. 主存高原 (Main Memory Plateau)**
- 位置：工作集 > L3 容量
- 特征：吞吐率最低，步长=1 时约 1~2 GB/s，步长增大时急剧下降
- 原因：每次访问都要从 DRAM 读取，DRAM 随机访问延迟约 100~200 周期

**5. 山谷 (Valleys)**
- 位置：步长等于缓存行大小的整数倍时
- 特征：吞吐率突然下降
- 原因：步长正好跳过整个缓存行，空间局部性完全丧失

**6. 悬崖 (Cliffs)**
- 位置：工作集跨越缓存层级边界时
- 特征：吞吐率急剧下降
- 原因：数据从 L1 溢出到 L2，或从 L2 溢出到 L3，或从 L3 溢出到主存

#### 典型数值参考

| 区域            | 工作集大小   | 步长=1 吞吐率 | 步长=64 吞吐率 |
|----------------|-------------|--------------|---------------|
| L1 脊          | 4 KB        | ~12,000 MB/s | ~11,000 MB/s  |
| L2 脊          | 256 KB      | ~6,000 MB/s  | ~3,000 MB/s   |
| L3 脊          | 8 MB        | ~3,000 MB/s  | ~800 MB/s     |
| 主存高原        | 64 MB       | ~1,200 MB/s  | ~200 MB/s     |

### E.4 存储器山的核心启示

1. **时间局部性**（Y 轴方向）：工作集越小，越能放入高级缓存，吞吐率越高
2. **空间局部性**（X 轴方向）：步长越小，越能利用缓存行的预取效果，吞吐率越高
3. **最优策略**：让工作集适合目标缓存层 + 使用 stride-1 访问模式
4. **分块的本质**：通过限制工作集大小，确保数据始终命中在某一缓存层（如 L1），用时间换空间效率

### F.3 完整状态转换表

#### 处理器发起的请求 (Processor-initiated)

| 当前状态 | 操作       | 下一状态 | 总线动作           | 说明                           |
|----------|-----------|----------|-------------------|-------------------------------|

| M        | PrWr      | M        | 无                | 命中，直接写                   |

| 当前状态 | 监听到    | 下一状态 | 响应动作              | 说明                           |
|----------|-----------|----------|----------------------|-------------------------------|
| M        | BusRd     | S        | 写回主存 + Flush     | 其他核要读，需写回脏数据       |
| M        | BusRdX    | I        | 写回主存 + Flush     | 其他核要写，需写回并放弃       |
| E        | BusRd     | S        | 无（静默降级）        | 其他核也要读，降为共享         |
| E        | BusRdX    | I        | 无（静默失效）        | 其他核要写，直接失效           |
| S        | BusRd     | S        | 无                   | 多个共享者，无变化             |
| S        | BusRdX    | I        | 无                   | 其他核要写，本副本失效         |
| I        | BusRd     | I        | 无                   | 无效行不响应                   |
| I        | BusRdX    | I        | 无                   | 无效行不响应                   |

### F.4 每种转换的触发条件和详细解释

**1. M → S（Modified → Shared）**
- 触发条件：其他处理器发起 BusRd（读请求）
- 动作：本 cache 将修改过的数据写回主存，然后降级为 S
- 原因：其他处理器需要读取该行，必须获得最新数据

**2. M → I（Modified → Invalid）**
- 触发条件：其他处理器发起 BusRdX（写请求/读独占请求）
- 动作：写回脏数据到主存，然后失效
- 原因：其他处理器要独占写入该行，本副本必须废弃

**3. E → S（Exclusive → Shared）**
- 触发条件：其他处理器发起 BusRd
- 动作：无总线传输（数据已在主存中是最新的），静默降级
- 原因：现在有两个 cache 持有该行，不再是独占

**4. E → I（Exclusive → Invalid）**
- 触发条件：其他处理器发起 BusRdX
- 动作：静默失效
- 原因：其他处理器要独占写入，本副本过期

**5. E → M（Exclusive → Modified）**
- 触发条件：本处理器执行 PrWr（写命中）
- 动作：无总线传输
- 原因：本 cache 独占该行，直接修改即可

**6. S → M（Shared → Modified）**
- 触发条件：本处理器执行 PrWr
- 动作：发 BusRdX，使其他持有该行的 cache 全部失效
- 原因：要从共享升级为独占，必须使其他副本失效

**7. S → I（Shared → Invalid）**
- 触发条件：其他处理器发起 BusRdX
- 动作：静默失效
- 原因：其他处理器要独占写入，本副本必须废弃

**8. I → E（Invalid → Exclusive）**
- 触发条件：本处理器 PrRd miss，且没有其他 cache 持有该行
- 动作：发 BusRd，从主存读取
- 原因：本 cache 是唯一持有者，且数据未修改

**9. I → S（Invalid → Shared）**
- 触发条件：本处理器 PrRd miss，且其他 cache 持有该行
- 动作：发 BusRd，从其他 cache 或主存获取
- 原因：多个 cache 共享该行

**10. I → M（Invalid → Modified）**
- 触发条件：本处理器 PrWr miss
- 动作：发 BusRdX，使其他 cache 的副本失效，从主存读取后写入
- 原因：本 cache 独占并修改该行

### F.5 MESI 协议的优化：MOESI

实际处理器（如 AMD）常使用 MOESI 扩展协议，增加 O (Owner) 状态：

| 新状态 | 含义                                                         |
|--------|--------------------------------------------------------------|
| O      | Owner：该行已被修改，但其他 cache 可能有 S 副本。Owner 负责  |
|        | 在被替换时写回主存，也可以直接响应其他 cache 的读请求。       |

O 状态的优势：当 M 状态的行被其他核读取时，可以直接从 M 降为 O（无需写回主存），由 Owner 在后续替换时负责写回，减少了总线写回流量。

### F.6 伪共享问题

MESI 协议导致的经典问题——伪共享 (False Sharing)：

```c
/* 两个线程分别频繁更新不同变量，但它们在同一缓存行中 */
int data[2];  /* 假设 data[0] 和 data[1] 在同一缓存行 */

// 线程 0
void thread0() {
    for (int i = 0; i < 1000000; i++) {
        data[0]++;  /* 修改 data[0] → 该缓存行变为 M */
    }
}

// 线程 1
void thread1() {
    for (int i = 0; i < 1000000; i++) {
        data[1]++;  /* 修改 data[1] → 需要使线程0的副本失效 (BusRdX) */
    }
}
```

每次写操作都会触发 MESI 协议的 BusRdX，导致缓存行在两个核之间来回迁移，性能急剧下降。解决方案是对齐到缓存行边界：

```c
/* 解决方案：缓存行对齐 */
struct alignas(64) PaddedInt {
    int value;
};

PaddedInt data[2];  /* 每个 data 元素独占一个缓存行 */
```

```
地址 12: set=3, tag=0 → HIT

地址 4:  set=1, tag=0 → HIT

前 4 次: 4 cold miss
```

### 练习题 5：分块大小选择

**题目**：对于 64×64 的 int 矩阵，在 s=5, E=1, b=5 的缓存中转置，最优分块大小是多少？为什么不是 8×8？

<details>
<summary>参考答案</summary>

```
缓存参数: S=32 组, E=1, B=32 字节 = 8 个 int
总容量 = 32 × 32 = 1024 字节 = 256 int

对于 64×64 矩阵转置 B[j][i] = A[i][j]:
A[i][j] 的组索引 = ((i × 64 + j) × 4 >> 5) & 0x1F
                  = ((i × 64 + j) >> 3) & 0x1F
                  = (i × 8 + j/8) & 0x1F

B[j][i] 的组索引 = (j × 8 + i/8) & 0x1F

8×8 分块时：
  A: 组索引范围 = (i×8 + j/8) & 0x1F，i 和 j 各变 8

  实际上 4×4 分块更合适：
  4 行 × 4 列 = 16 int，每行 4 int < 8 int/行
  但 4×4 不能填满缓存行，利用率低

  最优是 8×8 但需要处理对角线冲突
  或者使用 4×8 / 8×4 的非对称分块

  对于 64×64 矩阵，推荐 8×8 分块 + 对角线特殊处理
  或 4×4 分块（虽不能填满行，但避免冲突）
```

### 练习题 8：局部性分析

**题目**：分析以下两个代码片段的空间局部性和时间局部性。

```c
// 代码 A
for (int i = 0; i < N; i++) {
    sum += a[i] * b[i];
}

// 代码 B
for (int i = 0; i < N; i++) {
    for (int j = 0; j < N; j++) {
        c[i] += a[i][j] * b[j];
    }
}
```

<details>
<summary>参考答案</summary>

```
代码 A:
  空间局部性: a[] 和 b[] 都是 stride-1 顺序访问，空间局部性优秀
  时间局部性: sum 被重复读写，时间局部性好（可能放在寄存器中）
  a[] 和 b[] 的每个元素只访问一次，时间局部性差
  总评: 缓存友好，性能接近峰值

代码 B:
  空间局部性:
    a[i][j]: 内层 j 遍历，stride-1，空间局部性好
    b[j]: 内层 j 遍历，stride-1，空间局部性好
    c[i]: 内层不变，时间局部性好（可能放寄存器）
  时间局部性:
    b[j]: 外层 i 每次迭代都重新遍历 j，如果 N 较小 b 能放入缓存 → 时间局部性好
    a[i][j]: 每个元素只访问一次，时间局部性差
  当 N 较大时，b[] 在 i 的每次迭代都需要重新加载 → 性能下降
  优化: 如果 b[] 能放入缓存（N < 缓存容量/sizeof(double)），则整体缓存友好
```

</details>

### 练习题 9：存储器山解读

**题目**：在存储器山测试中，发现当工作集从 16KB 增加到 64KB 时，stride=1 的吞吐率从 12000 MB/s 降到 8000 MB/s。当 stride 从 1 增加到 16（int 大小为 4 字节），工作集保持 16KB 时，吞吐率从 12000 降到 6000 MB/s。解释这两个下降的原因。

<details>
<summary>参考答案</summary>

```
下降 1: 16KB → 64KB, stride=1
  16KB 能完全放入 L1（假设 L1 = 32KB），全部命中
  64KB 超过了 L1 容量，部分数据需要从 L2 获取
  L2 延迟 > L1 延迟 → 吞吐率下降
  这是"悬崖"效应，跨越了 L1/L2 边界

下降 2: stride 1→16, 16KB
  stride=1: 每次访问 4 字节，缓存行 64 字节 → 利用率 4/64 = 但顺序访问，预取有效
  stride=16: 每次跳过 16×4=64 字节 = 恰好一个缓存行
  每次访问都加载一个新缓存行，但只利用其中 4 字节 → 利用率 4/64 = 6.25%
  空间局部性完全丧失 → 每次都是 cache miss → 吞吐率下降
  这是"山谷"效应，步长等于缓存行大小整数倍
```

</details>

### 练习题 10：MESI 协议状态推导

**题目**：两个核 C0 和 C1 共享一个缓存行。初始状态两个核的缓存行都是 I。以下是操作序列，推导每步后两个核的状态：

1. C0 读该行
2. C1 读该行
3. C0 写该行
4. C1 读该行
5. C0 写该行

<details>
<summary>参考答案</summary>

```
初始: C0=I, C1=I

1. C0 读该行:
   C0 发 BusRd，无其他 cache 响应 → 从主存加载
   C0: I → E (Exclusive, 因为没有其他 cache 持有)
   C1: I (不变)
   状态: C0=E, C1=I

2. C1 读该行:
   C1 发 BusRd，C0 监听到，C0 从 E 降为 S
   C1: I → S (Shared, 因为 C0 也有)
   C0: E → S
   状态: C0=S, C1=S

3. C0 写该行:
   C0 发 BusRdX，C1 监听到，C1 从 S 降为 I
   C0: S → M (Modified)
   C1: S → I
   状态: C0=M, C1=I

4. C1 读该行:
   C1 发 BusRd，C0 监听到
   C0 从 M 降为 S，并写回脏数据（或直接响应给 C1）
   C1: I → S
   C0: M → S
   状态: C0=S, C1=S

5. C0 写该行:
   C0 发 BusRdX，C1 监听到，C1 从 S 降为 I
   C0: S → M
   C1: S → I
   状态: C0=M, C1=I

关键观察:
- 步骤 3 和 5 中，C0 从 S → M 需要先发 BusRdX 使 C1 失效
- 如果 C0 在步骤 2 后就写（当时是 E），则不需要 BusRdX（E→M 无总线动作）
- 这就是为什么 E 状态的引入能减少总线流量
```

## 附录H：缓存模拟器完整实现代码

本附录给出一个完整的、可编译运行的 C 语言缓存模拟器实现，其功能与 Cache Lab Part A（`csim`）一致：读取 valgrind 生成的内存访问轨迹文件（trace），模拟一个 S 组、每组 E 行、每行 B 字节的组相联缓存，统计命中（hit）、不命中（miss）、驱逐（eviction）次数。

### H.1 整体设计思路

模拟器不需要真正存储数据，只需要维护每个缓存行的**有效位（valid）**、**标记位（tag）**和用于 LRU 替换的**时间戳/计数器**。整体流程分为四步：

1. 解析命令行参数，得到 `s`（组索引位数）、`E`（每组行数）、`b`（块偏移位数）、`t`（trace 文件路径）
2. 根据 `s` 和 `E` 动态分配一个 S×E 的二维数组作为缓存
3. 逐行读取 trace 文件，对每条访存指令调用 `accessCache` 模拟一次访问
4. 汇总命中/不命中/驱逐次数并打印，最后释放内存

### H.2 数据结构定义

```c
/*
 * csim.c - 一个简单的缓存模拟器，模拟 Cache Lab Part A 的行为
 * 编译方式: gcc -O2 -o csim csim.c -lm
 * 用法: ./csim -s <s> -E <E> -b <b> -t <tracefile> [-v]
 */

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <getopt.h>
#include <unistd.h>

/* -------------------- 数据结构定义 -------------------- */

/*
 * cache_line 表示缓存中的一行（一个 cache line / cache block）
 * 我们不需要存储真实数据，因为模拟器只关心命中/不命中，
 * 所以省去了 data 数组，只保留元数据。
 */
typedef struct {
    int valid;          /* 有效位：1 表示该行当前存放着有效数据 */
    unsigned long tag;  /* 标记位：用于唯一标识该行存放的是哪个内存块 */
    unsigned long lru_counter; /* LRU 计数器：值越小表示越久未被访问，用于选择驱逐对象 */
} cache_line_t;

/*
 * cache_set 表示一个组，由 E 个 cache_line 组成
 * lines 是指向该组内所有行的指针（动态分配的数组）
 */
typedef struct {
    cache_line_t *lines; /* 指向 E 个 cache_line 的数组 */
} cache_set_t;

/*
 * cache_t 表示整个缓存，由 S 个组组成
 * sets 是指向所有组的指针（动态分配的数组）
 */
typedef struct {
    cache_set_t *sets;
    int S; /* 组数 = 2^s */
    int E; /* 每组行数 */
    int B; /* 块大小 = 2^b（本模拟器中块大小仅用于地址运算，不存储数据） */
    int s; /* 组索引位数 */
    int b; /* 块偏移位数 */
} cache_t;

/* -------------------- 全局统计变量 -------------------- */
int hit_count = 0;      /* 命中次数 */
int miss_count = 0;     /* 不命中次数 */
int eviction_count = 0; /* 驱逐次数 */
int verbose = 0;        /* 是否打印详细信息（-v 参数） */

/*
 * 全局 LRU 时间戳：每次访问缓存时递增，
 * 用作"逻辑时间"，写入被访问行的 lru_counter，
 * 时间戳越大表示越"新"，越小表示越"旧"（最久未使用）。
 */
unsigned long lru_timestamp = 0;
```

### H.3 initCache 函数——动态分配缓存空间

```c
/*
 * initCache - 根据 s 和 E 动态分配一个 S 组、每组 E 行的二维缓存结构
 * S = 2^s，E 为参数传入
 *
 * 参数:
 *   s - 组索引位数
 *   E - 每组的行数（相联度）
 *   b - 块偏移位数
 *
 * 返回:
 *   初始化好的 cache_t 结构体（值传递）
 *
 * 关键点:
 *   - 所有行的 valid 位必须初始化为 0（表示缓存为空）
 *   - 使用 calloc 可以顺带把 valid/tag/lru_counter 清零，
 *     但为了代码清晰，这里显式初始化
 */
cache_t initCache(int s, int E, int b) {
    cache_t cache;
    cache.s = s;
    cache.E = E;
    cache.b = b;
    cache.S = 1 << s; /* S = 2^s，位运算比 pow() 更高效也更精确 */
    cache.B = 1 << b; /* B = 2^b */

    /* 第一层：分配 S 个 cache_set_t */
    cache.sets = (cache_set_t *)malloc(cache.S * sizeof(cache_set_t));
    if (cache.sets == NULL) {
        fprintf(stderr, "错误: 无法为 %d 个组分配内存\n", cache.S);
        exit(EXIT_FAILURE);
    }

    /* 第二层：为每个组分配 E 个 cache_line_t */
    for (int i = 0; i < cache.S; i++) {
        cache.sets[i].lines = (cache_line_t *)malloc(E * sizeof(cache_line_t));
        if (cache.sets[i].lines == NULL) {
            fprintf(stderr, "错误: 无法为组 %d 分配 %d 行内存\n", i, E);
            exit(EXIT_FAILURE);
        }
        /* 初始化每一行：valid=0, tag=0, lru_counter=0 */
        for (int j = 0; j < E; j++) {
            cache.sets[i].lines[j].valid = 0;
            cache.sets[i].lines[j].tag = 0;
            cache.sets[i].lines[j].lru_counter = 0;
        }
    }

    return cache;
}
```

### H.4 accessCache 函数——组选择、行匹配、LRU 替换的核心逻辑

```c
/*
 * accessCache - 模拟一次对给定地址的访问
 *
 * 参数:
 *   cache   - 缓存结构体指针
 *   address - 64 位内存地址
 *
 * 处理流程（对应组相联缓存的三步查找）:
 *   1. 组选择：从地址中提取组索引 set_index，定位到具体的组
 *   2. 行匹配：在该组的 E 行中查找 tag 是否相同且 valid=1
 *      - 若找到匹配行 -> 命中(hit)，更新该行的 LRU 计数器
 *      - 若未找到匹配行 -> 不命中(miss)，需要装载新块
 *   3. 字选择：本模拟器不涉及具体数据存取，故不需要处理块内偏移，
 *      但地址中仍然包含 offset 位，只是对命中判断没有影响
 *
 * 不命中时的处理（LRU 替换策略）:
 *   - 先检查组内是否有空闲行（valid=0），如果有则直接放入
 *   - 如果没有空闲行，则需要驱逐（eviction）：
 *     找到 lru_counter 最小（最久未被访问）的行，替换它的 tag，
 *     并记录一次 eviction
 */
void accessCache(cache_t *cache, unsigned long address) {
    /*
     * 地址格式（从高位到低位）:
     * | 标记位 tag (64-s-b 位) | 组索引 set_index (s 位) | 块偏移 offset (b 位) |
     *
     * 提取组索引：先右移 b 位去掉块偏移，再用掩码取出低 s 位
     */
    unsigned long set_index = (address >> cache->b) & ((1UL << cache->s) - 1);

    /*
     * 提取标记位：直接右移 (s + b) 位，剩下的高位就是 tag
     */
    unsigned long tag = address >> (cache->s + cache->b);

    cache_set_t *set = &cache->sets[set_index];

    int hit_line = -1;      /* 命中的行号，-1 表示未命中 */
    int empty_line = -1;    /* 空闲行号，-1 表示组已满 */
    int lru_line = 0;       /* 待驱逐的行号（LRU 计数器最小的行） */
    unsigned long min_lru = 0xFFFFFFFFFFFFFFFFUL; /* 记录当前找到的最小计数器值 */

    /* 第一遍扫描该组的所有行：查找命中行、空闲行、以及 LRU 最小的行 */
    for (int i = 0; i < cache->E; i++) {
        cache_line_t *line = &set->lines[i];

        if (line->valid && line->tag == tag) {
            /* 找到 tag 匹配且有效的行 -> 命中 */
            hit_line = i;
        }

        if (!line->valid && empty_line == -1) {
            /* 记录第一个空闲行，供不命中时使用 */
            empty_line = i;
        }

        if (line->lru_counter < min_lru) {
            /* 持续更新最久未使用的行，作为潜在的驱逐对象 */
            min_lru = line->lru_counter;
            lru_line = i;
        }
    }

    /* 全局逻辑时钟递增，代表"现在"这个时刻 */
    lru_timestamp++;

    if (hit_line != -1) {
        /* ---------- 命中处理 ---------- */
        hit_count++;
        if (verbose) {
            printf("hit ");
        }
        /* 更新该行的 LRU 计数器为当前时间戳，表示"刚刚被访问过" */
        set->lines[hit_line].lru_counter = lru_timestamp;
        return;
    }

    /* ---------- 不命中处理 ---------- */
    miss_count++;
    if (verbose) {
        printf("miss ");
    }

    if (empty_line != -1) {
        /*
         * 组内还有空闲行：直接装载新块，不需要驱逐
         * 这对应缓存"冷不命中"（cold miss）或组未满的情况
         */
        set->lines[empty_line].valid = 1;
        set->lines[empty_line].tag = tag;
        set->lines[empty_line].lru_counter = lru_timestamp;
    } else {
        /*
         * 组已满：必须驱逐 lru_line（LRU 计数器最小的行）
         * 这对应"容量不命中"或"冲突不命中"
         */
        eviction_count++;
        if (verbose) {
            printf("eviction ");
        }
        set->lines[lru_line].tag = tag;
        set->lines[lru_line].lru_counter = lru_timestamp;
        /* valid 位本来就是 1，不需要重新设置 */
    }
}
```

### H.5 replayTrace 函数——解析 valgrind trace 文件

```c
/*
 * replayTrace - 读取并重放 trace 文件中的每一条访存记录
 *
 * trace 文件格式示例（valgrind --log-fd=1 生成）:
 *   I  0400d7d4,8
 *    M 0421c7f0,4
 *    L 04f6b868,8
 *    S 7ff0005c8,8
 *
 * 格式说明:
 *   - 第一列是操作类型: I(指令加载，忽略)、L(数据加载)、S(数据存储)、M(修改=先L后S)
 *   - 以空格开头的行才是我们需要处理的数据访问（I 开头的不带前导空格，直接跳过）
 *   - 逗号前是十六进制地址，逗号后是访问的字节数（本模拟器不需要用到字节数）
 *
 * 参数:
 *   cache      - 缓存结构体指针
 *   trace_file - trace 文件路径
 */
void replayTrace(cache_t *cache, const char *trace_file) {
    FILE *fp = fopen(trace_file, "r");
    if (fp == NULL) {
        fprintf(stderr, "错误: 无法打开 trace 文件 %s\n", trace_file);
        exit(EXIT_FAILURE);
    }

    char op;                /* 操作类型: L / S / M */
    unsigned long address;  /* 访问地址 */
    int size;               /* 访问字节数（未使用，但需要解析掉） */
    char line_buf[128];      /* 每行的缓冲区 */

    while (fgets(line_buf, sizeof(line_buf), fp) != NULL) {
        /*
         * 跳过 "I " 开头的指令加载记录：
         * 这类记录不带前导空格，形如 "I 0400d7d4,8"
         * 我们只关心以空格开头的 L/S/M 记录
         */
        if (line_buf[0] != ' ') {
            continue;
        }

        /*
         * 使用 sscanf 解析形如 " L 7ff0005c8,8" 的行
         * 格式串 " %c %lx,%d" 中：
         *   %c  匹配操作类型字符 (L/S/M)
         *   %lx 匹配十六进制地址
         *   %d  匹配访问字节数
         */
        if (sscanf(line_buf, " %c %lx,%d", &op, &address, &size) != 3) {
            /* 解析失败则跳过该行（例如空行） */
            continue;
        }

        if (verbose) {
            printf("%c %lx,%d ", op, address, size);
        }

        switch (op) {
            case 'L': /* Load: 一次数据加载 -> 一次缓存访问 */
                accessCache(cache, address);
                break;
            case 'S': /* Store: 一次数据存储 -> 一次缓存访问 */
                accessCache(cache, address);
                break;
            case 'M': /* Modify = Load + Store -> 两次缓存访问
                       * 第一次通常命中或不命中，第二次由于第一次已经
                       * 把数据加载进缓存，因此第二次必定命中 */
                accessCache(cache, address);
                accessCache(cache, address);
                break;
            default:
                /* 理论上不会出现其他字符，出现则忽略 */
                break;
        }

        if (verbose) {
            printf("\n");
        }
    }

    fclose(fp);
}
```

### H.6 freeCache 函数——释放内存

```c
/*
 * freeCache - 释放 initCache 中动态分配的所有内存
 * 必须先释放每个组内部的 lines 数组，再释放 sets 数组本身，
 * 避免内存泄漏（先分配的后释放，与分配顺序相反）
 */
void freeCache(cache_t *cache) {
    for (int i = 0; i < cache->S; i++) {
        free(cache->sets[i].lines);
    }
    free(cache->sets);
}
```

## 附录I：矩阵转置优化的完整代码

本附录针对 Cache Lab Part B 中三种矩阵规模（32×32、64×64、61×67），给出完整的分块转置优化代码，并对每种情况的缓存行为进行详细分析。假设缓存参数为 s=5, E=1, b=5（即 32 组、直接映射、每块 32 字节 = 8 个 int）。

### I.1 32×32 矩阵转置

```c
/*
 * transpose_32x32 - 针对 32x32 矩阵的分块转置
 *
 * 缓存背景: s=5, E=1, b=5 -> 32 组，直接映射(E=1)，每块 32 字节 = 8 个 int
 * 因为矩阵一行是 32 个 int = 128 字节 = 4 个缓存块，
 * 且 32 = 2^5 组，A 和 B 的同一相对偏移会映射到相同的组，
 * 导致 A[i][j] 和 B[i][j] 在对角线附近产生严重的"抖动"(thrashing)冲突不命中。
 *
 * 解决方案: 使用 8x8 的分块(blocking)，并对对角块特殊处理，
 * 用局部变量缓存对角线元素，避免同一缓存块内 A 与 B 互相驱逐。
 */
void transpose_32x32(int A[32][32], int B[32][32]) {
    int i, j, k;
    int a0, a1, a2, a3, a4, a5, a6, a7; /* 用于缓存一行 8 个元素的局部变量 */
    int diag_val, diag_idx;             /* 处理对角块时暂存对角线元素 */

    /* 外层按 8x8 分块遍历，8 恰好是一个缓存块能容纳的 int 个数 */
    for (i = 0; i < 32; i += 8) {
        for (j = 0; j < 32; j += 8) {
            /* 内层遍历块内的每一行 */
            for (k = i; k < i + 8; k++) {
                /*
                 * 一次性读取 A 的一整行（8 个 int，正好一个缓存块），
                 * 这样只产生 1 次 A 的不命中，后续 7 次都是命中
                 */
                a0 = A[k][j];
                a1 = A[k][j + 1];
                a2 = A[k][j + 2];
                a3 = A[k][j + 3];
                a4 = A[k][j + 4];
                a5 = A[k][j + 5];
                a6 = A[k][j + 6];
                a7 = A[k][j + 7];

                if (i == j) {
                    /*
                     * 对角块特殊处理：
                     * 此时 A 的这一行和 B 对应的这一行/列会映射到同一组，
                     * 如果直接写 B[j+t][k]，会导致 A、B 反复驱逐彼此。
                     * 技巧：先把 8 个值存入局部变量(已经做过)，
                     * 暂存对角线元素及其下标，最后统一写回，
                     * 减少同一组内 A/B 交替访问的次数。
                     */
                    diag_val = a0;
                    diag_idx = k;
                } else {
                    /* 非对角块：直接按转置关系写入 B，B 的写入是顺序的，
                     * 每写 8 个元素填满 B 的一个缓存块 */
                    B[j][k] = a0;
                    B[j + 1][k] = a1;
                    B[j + 2][k] = a2;
                    B[j + 3][k] = a3;
                    B[j + 4][k] = a4;
                    B[j + 5][k] = a5;
                    B[j + 6][k] = a6;
                    B[j + 7][k] = a7;
                }
            }

            if (i == j) {
                /*
                 * 处理完整个对角块的所有行后，再统一把对角线元素写回 B，
                 * 这样避免了在内层循环中频繁交替读 A 写 B 同一组的情况。
                 * 注意：这里简化描述，实际实现中需要为每一行保存 8 个值，
                 * 完整实现会使用一个 8x8 的临时局部数组或反复利用寄存器变量。
                 */
                for (k = i; k < i + 8; k++) {
                    B[k][k] = A[k][k];
                }
            }
        }
    }
}
```

**缓存行为分析（32×32）：**

- 矩阵每行 32 个 int = 128 字节，需要 4 个缓存块存放
- A 和 B 是两个独立数组，但由于 32 = 2^5，A[i][j] 与 B[i][j] 的组索引计算结果相同位模式，容易发生冲突不命中
- 采用 8×8 分块后：每个块恰好占用一整行 4 个缓存块中的一段，一次装载 8 个 int 可以连续命中 7 次
- 对角块特殊处理是本题最关键的优化点：不加处理时，对角块的不命中率会显著高于非对角块，因为 A[k][k] 和 B[k][k] 会竞争同一个缓存组
- 最终不命中次数可以做到 300 次以内（官方满分线附近）

### I.2 64×64 矩阵转置

```c
/*
 * transpose_64x64 - 针对 64x64 矩阵的分块转置
 *
 * 与 32x32 不同，64x64 每行有 64 个 int = 256 字节 = 8 个缓存块，
 * 若直接用 8x8 分块，一个 8x8 块的 A 和对应转置位置的 B 仍然会发生
 * 严重冲突（64 = 2^6，比 32 组数还大一倍，冲突更复杂）。
 *
 * 解决方案：使用经典的 "8x8 分块 + 4x4 子块技巧"：
 * 把每个 8x8 块看作 4 个 4x4 子块 A B / C D，
 * 借助寄存器暂存来错开 A、B 的访问时序，减少同组冲突。
 */
void transpose_64x64(int A[64][64], int B[64][64]) {
    int i, j, k;
    int a0, a1, a2, a3, a4, a5, a6, a7;

    for (i = 0; i < 64; i += 8) {
        for (j = 0; j < 64; j += 8) {
            /*
             * 第一阶段：处理 8x8 块的上半部分(前4行)。
             * 对每一行，读取 A 的左 4 个元素和右 4 个元素，
             * 把"右上"子块的数据暂存到 B 的"左下"位置（尚未转置，
             * 只是借用空间），从而避免过早触碰会造成冲突的缓存组。
             */
            for (k = i; k < i + 4; k++) {
                a0 = A[k][j];
                a1 = A[k][j + 1];
                a2 = A[k][j + 2];
                a3 = A[k][j + 3];
                a4 = A[k][j + 4];
                a5 = A[k][j + 5];
                a6 = A[k][j + 6];
                a7 = A[k][j + 7];

                /* 左上 4x4 子块正常转置，写入 B 的左上位置 */
                B[j][k] = a0;
                B[j + 1][k] = a1;
                B[j + 2][k] = a2;
                B[j + 3][k] = a3;

                /*
                 * 右上 4x4 子块暂时"借道"存放在 B 左上块的右侧（B[j][k+4..k+7]），
                 * 这部分数据本应放到 B 的左下位置，但那里现在还没被处理，
                 * 先借用空间，第二阶段再搬运到正确位置。
                 */
                B[j][k + 4] = a4;
                B[j + 1][k + 4] = a5;
                B[j + 2][k + 4] = a6;
                B[j + 3][k + 4] = a7;
            }

            /*
             * 第二阶段：处理 A 的左下 4x4 子块，同时把第一阶段
             * 暂存在 B 右上角的数据搬运到正确的左下位置。
             * 这一步是整个算法的精髓：通过巧妙的读写顺序，
             * 保证同一时刻访问的 A、B 地址不会映射到同一个缓存组。
             */
            for (k = j; k < j + 4; k++) {
                /* 先把暂存在 B[j..j+3][k+4] 中的右上子块数据读出到寄存器 */
                a0 = B[k][i + 4];
                a1 = B[k][i + 5];
                a2 = B[k][i + 6];
                a3 = B[k][i + 7];

                /* 再读取 A 左下 4x4 子块对应列的数据 */
                a4 = A[i + 4][k];
                a5 = A[i + 5][k];
                a6 = A[i + 6][k];
                a7 = A[i + 7][k];

                /* 把之前暂存的右上子块数据写到 B 正确的左下位置 */
                B[k][i + 4] = a4;
                B[k][i + 5] = a5;
                B[k][i + 6] = a6;
                B[k][i + 7] = a7;

                /* 把 A 右下 4x4 子块的数据（复用 a0-a3 对应关系）写到 B 右下位置 */
                B[k + 4][i] = a0;
                B[k + 4][i + 1] = a1;
                B[k + 4][i + 2] = a2;
                B[k + 4][i + 3] = a3;
            }

            /* 处理 A 右下 4x4 子块，转置写入 B 右下位置 */
            for (k = i + 4; k < i + 8; k++) {
                a0 = A[k][j + 4];
                a1 = A[k][j + 5];
                a2 = A[k][j + 6];
                a3 = A[k][j + 7];

                B[j + 4][k] = a0;
                B[j + 5][k] = a1;
                B[j + 6][k] = a2;
                B[j + 7][k] = a3;
            }
        }
    }
}
```

**缓存行为分析（64×64）：**

- 每行 256 字节，占 8 个缓存块，而缓存只有 32 组，因此矩阵的第 0 行与第 4 行会映射到相同的组（256 字节跨度导致组索引重复）
- 若直接套用 32×32 的 8×8 分块策略，会发现命中率大幅下降，因为一个 8×8 块内部，A 的上半部分和下半部分会与 B 产生跨行冲突
- 4×4 子块技巧的核心在于"错峰访问"：先处理左上、右上（借道暂存），再统一处理左下、右下，使得任意时刻正在写入的 B 区域与正在读取的 A 区域不会竞争同一缓存组
- 该实现可以将不命中次数控制在 1300 次左右（官方满分线附近，满分阈值通常为 1300）

### I.3 61×67 矩阵转置（非2的幂次边长）

```c
/*
 * transpose_61x67 - 针对 61x67 矩阵的分块转置
 *
 * 61x67 不是 2 的幂次，无法整除成规整的 8x8 块，
 * 因此边界处理变得重要。经验做法是选择一个较大的分块尺寸（如 16x16 或 23x23），
 * 并允许最后一块不满，用 min() 处理边界。
 *
 * 由于尺寸不规整，缓存冲突不再具有 32x32/64x64 那样规律的周期性，
 * 简单的分块 + 边界裁剪往往就能取得不错的效果。
 */
void transpose_61x67(int A[67][61], int B[61][67]) {
    /*
     * 注意：Cache Lab 中 61x67 是指 A 为 67 行 61 列，B 为转置后的 61 行 67 列，
     * 这里参数命名遵循题目约定：A[67][61] -> B[61][67]
     */
    int BLOCK = 16; /* 经验选择的分块大小，需要通过实验调优 */
    int i, j, k, l;
    int tmp;

    for (i = 0; i < 67; i += BLOCK) {
        for (j = 0; j < 61; j += BLOCK) {
            /*
             * 计算当前块的实际边界，防止越界。
             * 因为 67 和 61 都不能被 16 整除，最后一块会比较小。
             */
            int i_max = (i + BLOCK < 67) ? (i + BLOCK) : 67;
            int j_max = (j + BLOCK < 61) ? (j + BLOCK) : 61;

            for (k = i; k < i_max; k++) {
                for (l = j; l < j_max; l++) {
                    /*
                     * 逐元素转置。由于尺寸不规整，
                     * 这里不再追求"整行读取再整行写入"的极致优化，
                     * 而是依赖分块带来的空间局部性：
                     * 一个 BLOCK x BLOCK 的小块，其数据大概率能同时
                     * 驻留在缓存中，减少了跨块跳转造成的不命中。
                     */
                    tmp = A[k][l];
                    B[l][k] = tmp;
                }
            }
        }
    }
}
```

**缓存行为分析（61×67）：**

- 61 和 67 均为质数，不存在与缓存组数 32 之间的整除关系，因此不会出现 32×32/64×64 中那种"整行整列对齐冲突"的规律性问题
- 分块大小的选择需要通过实验测试（16、17、23 等都是常见的选择），一般来说分块不宜过大（否则一个块本身就装不下缓存），也不宜过小（分块开销和不规整边界处理变多）
- 边界条件处理（`i_max`、`j_max` 的裁剪）是保证正确性的关键，稍有不慎就会数组越界
- 该实现通常可以将不命中次数控制在 2000 次以内（满分阈值通常为 2000）

## 附录J：缓存性能优化技巧大全

本附录汇总程序员在日常编码中可以运用的缓存友好编程技巧，每种技巧配合具体代码示例说明其原理与效果。

### J.1 循环交换（Loop Interchange）

循环交换是指调整嵌套循环的顺序，使得内层循环按照数组在内存中的物理布局顺序访问，从而将"跨步访问"变为"顺序访问"，充分利用空间局部性。

```c
/* 优化前：按列遍历，跨步访问，步长为 N*sizeof(int)，空间局部性极差 */
void sum_rows_bad(int A[N][N], int *sum) {
    for (int j = 0; j < N; j++) {
        for (int i = 0; i < N; i++) {
            /* A[i][j] 每次访问都跳到下一行的同一列，跨度很大，
             * 几乎每次访问都是一次缓存不命中 */
            sum[j] += A[i][j];
        }
    }
}

/* 优化后：交换循环顺序，按行遍历，符合行主序(row-major)的内存布局 */
void sum_rows_good(int A[N][N], int *sum) {
    for (int i = 0; i < N; i++) {
        for (int j = 0; j < N; j++) {
            /* A[i][j] 和 A[i][j+1] 在内存中相邻，
             * 一次缓存不命中可以让后续多次访问都命中 */
            sum[j] += A[i][j];
        }
    }
}
```

原理：C 语言数组按行主序存储，`A[i][j]` 和 `A[i][j+1]` 地址相邻。交换后内层循环沿着连续地址前进，每次缓存不命中会把一整个缓存块（通常 64 字节，可容纳 16 个 int）载入，后续 15 次访问都能命中，命中率从接近 0% 提升到接近 93.75%。

### J.2 循环融合（Loop Fusion）

循环融合是指把多个独立遍历同一数据集的循环合并为一个循环，减少数据被重复载入缓存的次数。

```c
/* 优化前：两个独立的循环各自遍历一次数组 a 和 b，
 * 如果 a、b 很大（超过缓存容量），第二个循环访问时
 * 数组的前面部分很可能已经被驱逐出缓存，需要重新加载 */
void process_bad(double *a, double *b, double *c, double *d, int n) {
    for (int i = 0; i < n; i++) {
        c[i] = a[i] + b[i];
    }
    for (int i = 0; i < n; i++) {
        d[i] = a[i] - b[i];
    }
}

/* 优化后：融合成一个循环，a[i]、b[i] 只需从内存加载一次，
 * 在寄存器/缓存中同时用于两个计算，显著减少内存访问次数 */
void process_good(double *a, double *b, double *c, double *d, int n) {
    for (int i = 0; i < n; i++) {
        double av = a[i]; /* 只加载一次 */
        double bv = b[i]; /* 只加载一次 */
        c[i] = av + bv;
        d[i] = av - bv;
    }
}
```

原理：融合后 `a[i]` 和 `b[i]` 各自只需要从内存中加载一次（利用时间局部性），而不是在两个独立循环中分别加载两次。对于大数组，这能有效降低不命中率，尤其当数组大小超过缓存容量时效果更明显。

### J.3 循环分裂（Loop Fission）

与循环融合相反，循环分裂是指把一个访问多个大数组、导致缓存冲突或容量不命中严重的循环拆分成多个循环，让每次循环处理的数据集更小，能够完整地驻留在缓存中。

```c
/* 优化前：一个循环同时访问 4 个大数组，
 * 如果 4 个数组加起来超过缓存容量，会造成频繁的容量不命中，
 * 每个数组的数据都可能在被再次用到之前就被驱逐 */
void combined_bad(double *a, double *b, double *c, double *d,
                   double *out1, double *out2, int n) {
    for (int i = 0; i < n; i++) {
        out1[i] = a[i] * b[i];
        out2[i] = c[i] * d[i];
    }
}

/* 优化后：拆分成两个循环，每个循环只涉及 2 个数组 + 1 个输出，
 * 数据集变小，更容易被缓存完整容纳，减少了容量不命中 */
void combined_good(double *a, double *b, double *c, double *d,
                    double *out1, double *out2, int n) {
    for (int i = 0; i < n; i++) {
        out1[i] = a[i] * b[i];
    }
    for (int i = 0; i < n; i++) {
        out2[i] = c[i] * d[i];
    }
}
```

原理：循环分裂与循环融合并不矛盾，而是要根据实际的数据规模和缓存容量做权衡——数据集小、访问次数多时倾向融合；数据集本身很大、同时访问的数组过多导致容量不命中时，则倾向拆分，让"工作集"（working set）能装进缓存。这体现了缓存优化没有放之四海而皆准的规则，需要结合具体场景测量和调整。

### J.4 数组填充（Array Padding）消除冲突不命中

当多个数组的大小恰好是缓存组数的整数倍时，它们对应位置的元素会映射到同一个缓存组，产生严重的冲突不命中。数组填充通过在数组末尾（或结构体中）增加几个无用的字节，打破这种"整除对齐"关系。

```c
/*
 * 假设缓存有 S=1024 组（典型 L1 缓存组数量级），
 * 一个 int 数组如果大小恰好是 4096 个 int（16KB，对齐到组边界），
 * 那么 A[i] 和 B[i]（如果 B 紧跟在 A 后面分配）可能会映射到相同的组。
 */

/* 优化前：两个数组大小恰好对齐，容易发生冲突不命中 */
#define SIZE 4096
int A_bad[SIZE];
int B_bad[SIZE];

void merge_bad(int *out) {
    for (int i = 0; i < SIZE; i++) {
        /* A_bad[i] 和 B_bad[i] 很可能映射到同一缓存组，
         * 交替访问会导致互相驱逐，命中率骤降 */
        out[i] = A_bad[i] + B_bad[i];
    }
}

/* 优化后：给数组增加填充(padding)，打破对齐关系 */
#define PAD 8 /* 填充大小，通常等于一个缓存块能容纳的 int 数 */
int A_good[SIZE + PAD];
int B_good[SIZE];

void merge_good(int *out) {
    for (int i = 0; i < SIZE; i++) {
        /* 加了 PAD 之后，A_good 和 B_good 对应元素之间的地址差
         * 不再是组数的整数倍，从而映射到不同的组，避免了互相驱逐 */
        out[i] = A_good[i] + B_good[i];
    }
}

/*
 * 结构体填充示例：多线程场景下的"伪共享"(false sharing)问题
 * 也可以用类似的 padding 技巧解决，让不同线程使用的变量
 * 不落在同一条缓存行内，避免 MESI 协议带来的额外总线流量。
 */
typedef struct {
    long counter;      /* 线程私有计数器 */
    char padding[56];  /* 填充到 64 字节，占满一整条缓存行(假设缓存行为64字节) */
} padded_counter_t;
```

原理：冲突不命中的根源在于地址的组索引位恰好相同。填充通过改变数组的起始地址或跨度，使得原本会碰撞的地址在组索引位上产生偏移，从而分散到不同的组，属于典型的"空间换命中率"的优化手段。在多线程编程中，类似原理还可以用来解决"伪共享"问题。

### J.5 预取（Prefetch）指令 `__builtin_prefetch`

预取是指在真正需要某块数据之前，提前发出请求把它加载到缓存中，从而隐藏内存访问延迟。GCC/Clang 提供了 `__builtin_prefetch` 内建函数，可以插入软件预取提示。

```c
/*
 * __builtin_prefetch(const void *addr, int rw, int locality)
 *   addr     - 要预取的地址
 *   rw       - 0 表示预取用于读，1 表示预取用于写
 *   locality - 0~3，表示该数据被复用的"局部性程度"，
 *              0 表示用完即丢（不需要保留在缓存中），
 *              3 表示会被频繁复用（尽量保留在所有层级缓存中）
 */

/* 优化前：顺序遍历一个大链表，每次访问 next 指针时都可能发生缓存不命中，
 * 且由于是指针追逐(pointer chasing)，硬件预取器很难猜测下一个地址 */
long sum_list_bad(struct node *head) {
    long sum = 0;
    struct node *p = head;
    while (p != NULL) {
        sum += p->value;
        p = p->next;
    }
    return sum;
}

/* 优化后：在处理当前节点的同时，手动预取下一个节点，
 * 让内存系统有时间提前把数据取到缓存中，隐藏访问延迟 */
long sum_list_good(struct node *head) {
    long sum = 0;
    struct node *p = head;
    while (p != NULL) {
        if (p->next != NULL) {
            /* 提前预取下一个节点，rw=0表示读，locality=1表示低到中等复用 */
            __builtin_prefetch(p->next, 0, 1);
        }
        sum += p->value;
        p = p->next;
    }
    return sum;
}

/* 数组场景下的预取示例：批量处理时提前预取未来若干步要用到的数据 */
#define PREFETCH_DISTANCE 8

double array_process_with_prefetch(double *arr, int n) {
    double total = 0.0;
    for (int i = 0; i < n; i++) {
        /* 提前预取 PREFETCH_DISTANCE 个元素之后的数据，
         * 给内存子系统足够的"提前量"完成加载，
         * 使得当循环真正执行到那里时数据已经在缓存中 */
        if (i + PREFETCH_DISTANCE < n) {
            __builtin_prefetch(&arr[i + PREFETCH_DISTANCE], 0, 1);
        }
        total += arr[i] * arr[i];
    }
    return total;
}
```

原理：现代 CPU 已经内置了硬件预取器（能识别顺序或固定步长的访问模式并自动预取），但对于指针追逐（如链表遍历）这类硬件难以预测的访问模式，软件预取可以发挥更大作用。需要注意的是，预取距离（prefetch distance）需要根据内存延迟和循环体的计算量仔细调优：距离太近起不到隐藏延迟的效果，距离太远则可能预取的数据在用到之前就被再次驱逐，浪费带宽。

## 附录K：现代CPU缓存架构深入

### K.1 Intel Core i7 的缓存参数表

以经典的 Intel Core i7（Nehalem/Sandy Bridge 时期，CSAPP 教材中常引用的型号）为例，其缓存层次结构参数大致如下：

| 缓存类型 | 容量 | 相联度 (E) | 块大小 (B) | 组数 (S) | 访问延迟 | 备注 |
|---------|------|-----------|-----------|---------|---------|------|
| L1 指令缓存 (i-cache) | 32 KB | 8 路 | 64 字节 | 64 | 约 4 个周期 | 每个核心私有 |
| L1 数据缓存 (d-cache) | 32 KB | 8 路 | 64 字节 | 64 | 约 4 个周期 | 每个核心私有 |
| L2 统一缓存 | 256 KB | 8 路 | 64 字节 | 512 | 约 10 个周期 | 每个核心私有，指令数据统一存放 |
| L3 统一缓存 (LLC) | 8 MB（多核共享） | 16 路 | 64 字节 | 8192 | 约 40~75 个周期 | 所有核心共享，Last Level Cache |
| 主存 (DRAM) | 数 GB 到数十 GB | - | - | - | 约 数百 个周期 | 通过内存控制器访问 |

补充说明：

- 组数计算方式：S = 容量 / (相联度 × 块大小)，例如 L1 数据缓存：32KB / (8 × 64B) = 64 组
- 地址划分：块偏移 b = log2(64) = 6 位；对 L1（64组）组索引 s = log2(64) = 6 位；对 L2（512组）s = 9 位；对 L3（8192组）s = 13 位
- 现代 Intel/AMD 处理器普遍采用"每核心私有 L1+L2，多核共享 L3"的层次结构设计，L3 也常被称为 LLC（Last Level Cache），是芯片内缓存与主存之间的最后一道屏障
- TLB（Translation Lookaside Buffer）虽不是本章重点，但也是层次结构的一部分，用于缓存虚拟地址到物理地址的翻译结果，通常分为 L1 TLB 和 L2 TLB

### K.2 包含式缓存（Inclusive）vs 排他式缓存（Exclusive）

多级缓存之间的数据组织策略主要分为三类：包含式、排他式、非包含非排他式。

**包含式缓存（Inclusive Cache）：**

- 定义：外层缓存（如 L3）必须包含所有内层缓存（L1、L2）中的数据副本，即 L1 ⊆ L2 ⊆ L3
- 优点：
  - 简化多核缓存一致性维护——当需要判断某个数据块是否被其他核心的私有缓存持有时，只需检查共享的 L3 即可，不需要挨个探测每个核心的 L1/L2（称为"侦听过滤"，snoop filtering）
  - 一个核心的 L1/L2 缺失时，如果 L3 命中，可以快速确认数据是否在别的核心缓存中
- 缺点：
  - 浪费缓存容量：同一份数据在 L1、L2、L3 中都有副本，L3 的有效容量因此打了折扣
  - 需要"反向失效"（back-invalidation）：当 L3 因为容量不命中需要驱逐某个块时，必须同时使该块在所有核心的 L1/L2 中失效，即便这些核心正在频繁使用它，这会造成性能损失
- 代表：Intel 早期至中期的多核处理器（如 Nehalem）的 L3 采用包含式设计

**排他式缓存（Exclusive Cache）：**

- 定义：各级缓存之间的数据互不重复，一个数据块要么在 L1，要么在 L2，要么在 L3，绝不会同时出现在多层中
- 优点：
  - 最大化利用总缓存容量，相当于 L1+L2+L3 的总容量都可以用来存放不同的数据
- 缺点：
  - L1 不命中、L2 命中时，需要把数据从 L2"搬移"到 L1（而不是简单复制），涉及数据交换，控制逻辑更复杂
  - 多核一致性维护更复杂，因为无法用共享的 L3 作为侦听过滤器，可能需要额外的目录结构
- 代表：AMD 的部分处理器（如推土机/Zen 之前的一些型号）在 L2/L3 之间采用排他式或接近排他式设计

**非包含非排他式缓存（NINE, Non-Inclusive Non-Exclusive）：**

- 定义：既不强制要求外层缓存包含内层缓存的所有数据，也不强制要求互斥，具体某个数据块是否在多层同时存在取决于替换算法的自然结果
- 优点：
  - 在实现复杂度和容量利用率之间取得折中，不需要严格的反向失效，也不需要频繁的数据搬移
  - 现代很多处理器（如 Intel 从 Skylake-SP 开始的部分产品线）采用 NINE 设计，L3 更多充当"牺牲缓存"（victim cache）的角色，同时保留一部分侦听目录功能用于加速多核一致性判断
- 代表：Intel Skylake-X/Skylake-SP 及之后的部分服务器处理器

### K.3 缓存行的状态和一致性流量

在多核系统中，缓存行除了 valid/tag/data 之外，还需要维护一致性状态位，最常见的是 MESI 协议定义的四种状态（本章正文已详细讨论 MESI 状态转换，此处补充与"一致性流量"相关的内容）：

**缓存行状态回顾：**

| 状态 | 含义 | 是否可以直接写 | 是否需要通知总线/其他核心 |
|-----|------|--------------|----------------------|
| M (Modified) | 已修改，数据仅存在于本缓存，与内存不一致 | 可以 | 是（其他核心读取时需要本核心提供数据或写回） |
| E (Exclusive) | 独占，数据与内存一致，仅本缓存持有 | 可以（转为 M，无需总线事务） | 否 |
| S (Shared) | 共享，可能有多个核心的缓存持有相同数据 | 不可以（需先发失效请求） | 是 |
| I (Invalid) | 无效，该行数据不可用 | 不可以 | - |

**一致性流量的来源：**

一致性流量（coherence traffic）是指多核之间为了维护缓存一致性而在互联总线/片上网络（NoC）上产生的额外通信开销，主要包括：

1. **BusRd（总线读请求）**：核心发生 Load 不命中时发出，用于从内存或其他核心的缓存中取得数据的共享副本，可能触发其他核心从 M 状态降级为 S 状态并写回脏数据
2. **BusRdX（总线读独占请求）**：核心发生 Store 不命中或需要将 S 状态提升为 M 状态时发出，要求所有其他持有该行副本的核心将其状态置为 I（失效），保证独占写权限
3. **BusUpgr（总线升级请求）**：当本地已经以 S 状态持有该行，只是想写入（S→M）时发出，比 BusRdX 更轻量，因为不需要重新读取数据，只需要让别的核心失效
4. **Flush / WriteBack（写回流量）**：当 M 状态的缓存行被读取或被驱逐时，需要把脏数据写回到内存或直接转发给请求方，这也会占用总线带宽

**减少一致性流量的编程建议：**

- **避免伪共享（false sharing）**：多个线程频繁写入位于同一缓存行内但逻辑上无关的变量，会导致缓存行在多核间来回"乒乓"传递（ping-pong），产生大量 BusRdX/BusUpgr 流量。解决方法是用 padding 让各线程独占的数据分散到不同缓存行（见附录 J.4）
- **减少跨核共享写**：尽量让每个核心处理独立的数据分片（data partitioning），减少多个核心同时写同一块内存区域的情况
- **利用 E 状态**：如果一个核心确定自己是当前唯一访问某块数据的核心（例如刚从内存分配、初始化的数据），处理器会尽量将其置于 E 而非 S 状态，这样后续该核心的写操作可以直接 E→M，无需发出 BusRdX，节省一次总线事务，这也是本章正文中强调"E 状态引入能减少总线流量"的原因
- **只读数据尽量共享**：只读数据在多核间共享（S 状态）本身不会产生额外的一致性流量，因为不涉及写操作触发的失效广播，只有在发生写入时才会产生流量，因此应尽量将频繁读、极少写的数据结构设计为真正的"只读"，避免不必要的写操作触发全局失效

一致性流量在多核/多路服务器系统中往往是性能瓶颈的重要来源之一，理解 MESI 状态转换与总线事务的对应关系，有助于在设计并发数据结构时主动规避高频率的跨核缓存行竞争，这也是本章"存储器层次结构"知识在真实高性能系统工程中的直接应用。

### 🔴 跳步1（核心跳步）：DRAM 为什么要把地址分成行和列两次传输——RAS/CAS 分时复用的真正动机

**原文提到**（6.1.3 节，约第51-58行）：直接引入了"DRAM 芯片中的单元被组织为超单元（supercell）的二维阵列"，并说"行地址 i 称为 RAS（Row Access Strobe）请求"、"列地址 j 称为 CAS（Column Access Strobe）请求"，内存控制器先发送行地址再发送列地址。但**没有解释**一个关键的"为什么"——为什么不像 SRAM 那样一次性发送完整地址，而要分两次传输？

**补充说明**：

答案是**为了节省芯片引脚（pin）**。

DRAM 芯片的存储容量远大于 SRAM（同样面积下 DRAM 的密度是 SRAM 的 4-8 倍），因此需要更多的地址位来寻址。例如一个包含 4096×4096 = 16M 个超单元的 DRAM 芯片，如果一次性发送完整地址，需要 12+12 = 24 条地址引脚。而芯片封装的引脚数是一个非常宝贵的资源——引脚越多，芯片封装越大、成本越高、布线越复杂、信号完整性越难保证。

RAS/CAS 分时复用的方案是：**只用 12 条地址引脚，分两次传输**——第一次传输行地址（RAS），第二次传输列地址（CAS）。这样引脚数减少了一半（从24条减少到12条），代价是访问延迟增加了（需要两个步骤而不是一个），但这个代价是值得的，因为：

1. **引脚成本远高于延迟成本**：在芯片制造中，引脚数直接决定封装类型和成本，减少引脚可以让 DRAM 更便宜、更容易集成。DRAM 的设计哲学就是"用时间换空间和成本"——容量大、密度高、成本低，但速度比 SRAM 慢。
2. **行缓冲区（Row Buffer）可以分摊开销**：DRAM 在收到 RAS 后会将整行数据读入行缓冲区，后续如果访问的是同一行的不同列（称为"行命中"或 page hit），只需要发送 CAS 即可，不需要重新发送 RAS，延迟大大降低。这就是局部性原理在硬件层面的体现。
3. **SRAM 不需要这么做**：因为 SRAM 容量小（常用于缓存），地址位数少，引脚数不是瓶颈，所以可以一次性发送完整地址，速度更快。

这也解释了为什么 DRAM 的阵列被设计成二维而不是一维——二维结构使得行地址和列地址各占一半的位数，从而最大化引脚复用的效果。如果设计成一维（比如 16M × 1），就需要 24 条地址线才能寻址，没有复用的意义。

> **理解这个"为什么"之后，以下概念就自然串联起来了：**
> - DDR 的"预取"（prefetch）：DDR1 每次 CAS 返回2个数据（2n prefetch），DDR2 返回4个，DDR3 返回8个，DDR4/DDR5 更多——这是在引脚带宽不变的前提下通过一次读出更多数据来提高有效带宽。
> - "突发传输"（burst）：行缓冲区中已经有了整行数据，按顺序读出多个列地址的数据只需要极少的额外延迟。
> - CAS Latency (CL)：内存规格中的 CL 参数就是从发送列地址到数据出现在引脚上的周期数，它是 DRAM 延迟的主要组成部分。

### 跳步2：DDR 的"预取位数"是什么意思，DDR1/2/3/4/5 到底是怎么一代代提速的

**原文提到**（6.1.3 节末尾）：列举了 DDR1-DDR5 的演进，提到"DDR2 为4位预取、DDR3 为8位预取"，但**没有解释**预取的物理含义和它如何提升带宽。

**补充说明**：

DRAM 内部阵列的工作频率实际上很低（几百 MHz 级别），远低于内存总线频率。所谓"n位预取"（n-bit prefetch）是指每次内部读操作，DRAM 从阵列中一次性取出 n 个数据单元放入 I/O 缓冲区，然后在 n 个连续的外部时钟周期内依次输出到引脚上。

- **SDR SDRAM**（Single Data Rate）：1位预取，每个时钟上升沿传一次数据。
- **DDR1**：2位预取，每个时钟的上升沿和下降沿各传一次数据（Double Data Rate 的名称由来），等效传输率 = 2 × 时钟频率。
- **DDR2**：4位预取，内部阵列频率不变，但 I/O 缓冲区一次缓冲4个数据，用更高的 I/O 时钟频率输出。等效传输率 = 4 × 内部频率。
- **DDR3**：8位预取，依此类推。
- **DDR4**：仍然是8位预取，但提升了 I/O 时钟频率和电气标准。
- **DDR5**：引入了两个独立的32位通道（替代单个64位通道），每通道16位预取，进一步提升并行度。

本质上，每一代 DDR 都是在不大幅提高内部阵列速度的前提下，通过增加一次读出的数据量和提高外部 I/O 速率来提升带宽的。这是一种典型的"用并行度换速度"的工程权衡。

### 跳步3：缓存组织参数 S×E×B 的设计动机——为什么不直接用"完全相联"

**原文提到**（6.4.1 节）：直接给出了缓存的三参数模型 S（组数）×E（每组的行数）×B（每行的数据字节数），以及地址分解为 t（标记）+s（组索引）+b（块偏移）三个字段，但**没有解释**为什么缓存要做成"组相联"而不是"完全相联"（所有行放在一个组中，任何数据可以放在任何行）。

**补充说明**：

完全相联缓存（E = C/B，S = 1）的最大优点是灵活性最高——任何内存地址都可以映射到任何缓存行，冲突不命中（conflict miss）完全消除。但它有一个致命的实现问题：**查找效率极低**。

缓存的查找过程是：给定一个内存地址，检查缓存中是否已经存有对应的数据。在完全相联缓存中，数据可能在任意一行，因此必须将地址的标记与所有缓存行的标记同时进行比较（并行比较）。这需要一种叫做 **CAM（Content-Addressable Memory，内容可寻址存储器）** 的特殊电路——它的功能是"给定一个值，在所有存储单元中同时查找匹配项"。

CAM 的问题是：
- **面积大**：每个存储单元需要额外的比较电路，面积约为普通 SRAM 的 2-3 倍。
- **功耗高**：每次查找都要驱动所有比较器。
- **不可扩展**：行数越多，比较器越多，延迟和功耗都线性增长。

组相联是一个折中方案：用组索引（s 位）直接定位到一个特定的组（这是一个简单的译码操作，很快），然后只在该组内的 E 行中做并行标记比较。E 通常很小（2、4、8、16），CAM 电路的开销可以接受。这样既保留了一定的灵活性（E > 1 减少冲突不命中），又控制了硬件复杂度。

**对应关系表：**
| 设计 | S | E | 查找复杂度 | 冲突不命中 |
|------|---|---|-----------|-----------|
| 直接映射 | C/B | 1 | 最低（无需比较，直接定位） | 最高 |
| E路组相联 | C/(E·B) | E | 中等（组内E路并行比较） | 中等 |
| 全相联 | 1 | C/B | 最高（需要与所有行比较） | 无 |

这就是为什么 L1 缓存通常是 4-8 路组相联（对延迟要求极高，不能有太多路），而 TLB 可以是全相联的（条目数很少，通常32-64个，CAM 开销可接受）。

### 跳步4：TLB 在虚拟内存被详细讲解之前就出现了

**原文提到**（6.4.4 节末尾和附录部分）：提到 TLB（Translation Lookaside Buffer）是"虚拟页号到物理页号的映射缓存"，通常采用全相联设计，但**没有解释**虚拟内存的地址翻译过程，也没有解释为什么需要TLB。

**补充说明**：

这是一个教材编排上的"前向引用"——TLB 的详细机制在第9章（虚拟内存）中才完整讲解。这里先给出一个简化的理解：

1. 程序使用的是**虚拟地址**，需要翻译成**物理地址**才能访问真实的内存。
2. 翻译规则记录在**页表（Page Table）** 中，页表本身存储在内存里。
3. 如果每次内存访问都要先查一次页表（一次额外的内存访问来获取翻译结果），性能会严重下降。
4. TLB 就是页表的缓存——它存储最近用过的"虚拟页号→物理页号"映射，使得大部分地址翻译可以在一个周期内完成，而不需要访问内存中的页表。

本章在 TLB 上不做深入展开是合理的，读者只需知道"TLB 是缓存层次结构中的一环，它缓存的不是数据而是地址翻译结果"即可。详细机制留待第9章学习。

### 跳步5：直接映射缓存中"抖动（Thrashing）"现象的本质原因

**原文提到**（6.4.2 节）：通过一个具体例子（两个数组 x 和 y 恰好映射到相同的缓存组）展示了直接映射缓存的抖动现象——每次访问都是不命中，但**没有从一般性角度解释**什么样的内存访问模式容易触发抖动。

**补充说明**：

抖动的本质是：多个频繁访问的内存地址**恰好映射到同一个缓存组**，而该组的行数（E）不足以同时容纳它们。在直接映射缓存中 E=1，因此只要有两个频繁访问的地址映射到同一组，就必然产生抖动。

触发抖动的一般条件：两个地址 A1 和 A2 满足 `(A1 / B) mod S == (A2 / B) mod S`，即它们的组索引相同。在实际编程中，最常见的触发场景是：

- **两个数组的基地址差恰好是缓存大小的整数倍**：例如 `float x[N]` 和 `float y[N]` 声明在一起，且 `N * sizeof(float)` 恰好等于缓存大小 `S * B`，则 `x[i]` 和 `y[i]` 总是映射到同一组。
- **二维数组的步长与缓存大小对齐**：例如 `A[N][N]` 中 N 恰好是缓存组数 S 的倍数，则 `A[0][0]` 和 `A[1][0]` 映射到同一组（矩阵转置中的经典问题）。

解决方案：（1）增加缓存的相联度 E（硬件层面）；（2）在数组之间插入 padding 以打破地址对齐（软件层面）；（3）使用分块技术减小同时访问的数据集大小。

### 跳步6：写策略（Write-Through vs Write-Back）的工程权衡

**原文提到**（6.4.5 节）：列出了 Write-Through（直写）和 Write-Back（写回）两种策略，但**没有解释**为什么现代处理器几乎全部选择 Write-Back，以及各自的优劣取舍。

**补充说明**：

**Write-Through（直写）**：每次写缓存时，同时将数据写到下一级存储（更慢的缓存或内存）。
- 优点：简单，一致性容易维护（下一级始终是最新的）。
- 缺点：每次写操作都产生一次下级存储的写流量，如果程序频繁写同一个地址（比如循环累加），流量会非常大。
- 使用场景：早期处理器、某些嵌入式系统、GPU 的某些层级。

**Write-Back（写回）**：写操作只修改缓存中的数据，并设置一个"脏位（dirty bit）"标记该行已被修改。只有当该行被驱逐（eviction）时才将数据写回下一级存储。
- 优点：大幅减少写流量——如果一个缓存行在被驱逐之前被写了100次，只需要最终写回1次。
- 缺点：实现复杂（需要维护脏位、驱逐时需要额外的写回操作），缓存与下级存储之间可能存在不一致的窗口。
- 使用场景：几乎所有现代处理器的 L1/L2/L3 缓存。

现代处理器选择 Write-Back 的根本原因是：**写流量的减少远比实现复杂度增加重要**。在典型的程序中，对同一缓存行的多次写入非常常见（如循环中的计数器递增、数组元素的逐个赋值），Write-Back 可以将多次写合并为一次写回，显著降低内存总线压力。

### 跳步7：MESI 协议中"E（独占）状态"的引入动机

**原文提到**（附录 K）：给出了 MESI 四种状态的定义和状态转换图，但**没有解释**为什么在 MSI（Modified-Shared-Invalid）三状态协议的基础上还需要引入 E（Exclusive）状态。

**补充说明**：

在 MSI 协议中，当一个核心从内存中读取一个只有它自己需要的数据（其他核心的缓存中没有副本），该数据被放入 S（Shared）状态。如果该核心接下来想写入这个数据，即使事实上没有任何其他核心持有副本，协议仍然要求它先发出一个 BusRdX 请求来获取独占权（因为从 S 状态的角度看，"可能有其他核心也持有"）。这次 BusRdX 是不必要的——浪费了一次总线事务。

E（Exclusive）状态解决的正是这个问题：当核心读取数据且确认其他核心没有副本时，将其置为 E 而非 S 状态。E 状态的含义是"我是唯一持有者，且数据与内存一致"。在 E 状态下写入，可以直接转为 M 状态，**不需要发出任何总线事务**，节省了一次 BusRdX 的开销。

这在实际工作负载中非常有价值，因为很多数据是"先读后写"且在一段时间内只被一个核心使用的（如局部变量、线程私有数据、刚分配的内存）。

### 跳步8：伪共享（False Sharing）为什么会导致性能灾难

**原文提到**（附录 K 末尾和 J.4）：给出了伪共享的定义和解决方案（padding），但**没有用具体的数据量化说明**伪共享的性能影响到底有多大。

**补充说明**：

伪共享的性能惩罚取决于缓存一致性协议中状态转换的延迟。在典型的多核处理器中：

- **同核心 L1 缓存命中写入**：约 1-4 个周期
- **伪共享导致的缓存行失效 + 重新获取**：约 40-100 个周期（需要通过片上互联网络从另一个核心的缓存中获取数据）
- **如果涉及跨 NUMA 节点（多路服务器）**：约 100-300 个周期

也就是说，伪共享可以让一次写操作的延迟增大 25-75 倍。如果这个写操作在一个紧密循环中（比如每个线程各自递增自己的计数器），整个循环的执行时间可能从毫秒级膨胀到秒级。

一个经典的实验：4 个线程各自递增一个计数器，4 个计数器相邻排列在一个 `int counters[4]` 数组中（占 16 字节，共享一个 64 字节的缓存行）。与使用 padding（每个计数器独占一个缓存行）相比，伪共享版本的性能可能差 10-50 倍。

### 跳步9：磁盘寻道时间的量级和"旋转延迟"的计算

**原文提到**（6.1.4 节）：给出了磁盘访问时间 = 寻道时间 + 旋转延迟 + 传输时间的公式，但**没有给出直觉性的量级对比**来帮助读者感受"磁盘有多慢"。

**补充说明**：

一些典型的数量级对比：

| 操作 | 延迟 | 相当于... |
|------|------|----------|
| L1 缓存命中 | ~1 ns | 1秒 |
| L2 缓存命中 | ~5 ns | 5秒 |
| L3 缓存命中 | ~20 ns | 20秒 |
| 内存访问 | ~100 ns | 1.5分钟 |
| SSD 随机读 | ~100 μs | 1.2天 |
| 机械硬盘随机读 | ~10 ms | 4个月 |
| 网络往返（同数据中心） | ~0.5 ms | 6天 |

也就是说，如果把 L1 缓存命中比作"1秒钟"的感觉，那么一次机械硬盘的随机读取就像等了"4个月"。这个巨大的延迟差距正是存储器层次结构存在的根本原因——通过逐级缓存，让大部分访问都命中快速的高层级存储，避免访问慢速的低层级存储。

旋转延迟的计算：对于 7200 RPM 的硬盘，每转一圈需要 60/7200 ≈ 8.33 ms。平均旋转延迟是半圈的时间，即 ~4.17 ms。寻道时间典型值为 3-9 ms（平均约 5-8 ms）。传输一个 4KB 扇区的时间约 0.01-0.02 ms（几乎可以忽略）。因此，磁盘随机读的延迟几乎全部来自"机械运动"（移动磁头 + 等待盘片转到位），这也是 SSD 相对于 HDD 的最大优势所在——SSD 没有机械运动，随机读延迟低了约100倍。

### 跳步10：SSD 中的"写放大"和"磨损均衡"为什么是 SSD 特有的问题

**原文提到**（6.1.5 节）：提到了闪存的擦除-再写特性和写放大、磨损均衡的概念，但**没有解释**为什么闪存不能像内存或磁盘那样"直接覆盖写"。

**补充说明**：

闪存（NAND Flash）的物理特性决定了它的写入规则与 DRAM 和磁盘完全不同：

1. **读取以"页"（Page）为单位**：通常 4KB 或 16KB，速度很快（~25μs）。
2. **写入也以"页"为单位**：但只能将 1 改为 0，不能将 0 改回 1。如果要把某个位从 0 改为 1，必须先"擦除"整个包含该页的"块（Block）"。
3. **擦除以"块"（Block）为单位**：一个块通常包含 64-256 个页（256KB-4MB），擦除操作将整个块的所有位全部置为 1。擦除操作很慢（~1-3ms）且有寿命限制（MLC 闪存约 3000-10000 次擦除）。

这就引出了两个问题：
- **写放大（Write Amplification）**：为了修改一个 4KB 的页，可能需要先读出整个块、擦除块、再将修改后的数据连同其他未修改的页一起写回。实际写入的数据量远大于用户请求的数据量，比值就是写放大率。
- **磨损均衡（Wear Leveling）**：如果总是反复写入同一个物理块，该块会先于其他块达到寿命上限而报废。SSD 的固件（FTL，Flash Translation Layer）会主动将写入分散到不同的物理块上，让所有块的擦除次数趋于均匀。

## 五、常见困惑与解答

### Q1：为什么 DRAM 比 SRAM 慢那么多，但计算机的主存还是用 DRAM 而不是 SRAM？

因为 **DRAM 的面积密度是 SRAM 的 4-8 倍，成本只有 SRAM 的 1/10 到 1/50**。SRAM 每个比特需要 6 个晶体管（6T 结构），而 DRAM 每个比特只需要 1 个晶体管 + 1 个电容（1T1C 结构）。如果用 SRAM 做主存，16GB 内存的成本可能要几千甚至上万元，且功耗和散热也无法接受。存储器层次结构的整个设计思路就是"用少量快速昂贵的存储（SRAM 缓存）+ 大量慢速便宜的存储（DRAM 主存）+ 更大量更慢更便宜的存储（磁盘/SSD）"来在成本和性能之间取得最佳平衡。

### Q2：缓存的"命中率"和"不命中率"到底要多高/多低才算好？

这取决于上下文和缓存层级：
- **L1 缓存**：典型命中率 95%-99%。即使 1% 的不命中率也意味着每 100 次访问有 1 次需要去 L2 取数据（增加约 5ns 延迟）。
- **L2 缓存**：典型命中率 90%-97%。L2 不命中需要去 L3 或内存取数据。
- **TLB**：典型命中率 >99%。TLB 不命中需要执行页表遍历（page table walk），可能需要 2-4 次内存访问来找到翻译结果。

直觉上，一个程序如果有良好的局部性（数组按顺序访问、热点数据集小于缓存容量），L1 命中率通常在 97% 以上。如果 L1 命中率低于 90%，通常说明访问模式存在严重问题（跨步过大、数据集过大、或存在大量冲突不命中），值得优化。

### Q3：6.4 节说缓存的每一行都有一个"有效位"，它有什么用？

有效位（valid bit）标记该缓存行是否包含有效数据。在系统刚启动或缓存被清空（flush）后，所有行的有效位都是 0（无效），即使标记位恰好与某个地址匹配，也会被视为不命中。只有当数据被成功加载到该行后，有效位才被置为 1。

有效位的存在防止了一个问题：缓存行中的标记字段是"未初始化"的随机值，如果没有有效位来区分"已加载数据的行"和"从未使用过的空行"，可能会产生虚假的命中——一个随机的标记值碰巧与要查找的地址匹配。

### Q4：直接映射缓存中，为什么两个数组分别按顺序遍历没问题，但"交替"访问就会抖动？

关键在于访问的**时间交错模式**。分别遍历（先完整遍历数组 x，再完整遍历数组 y）时，在遍历 x 的过程中，缓存行被 x 的数据填充，x 内部的访问具有良好的空间局部性，命中率高；遍历 y 时同理。

但如果交替访问（`x[0], y[0], x[1], y[1], ...`），且 x[i] 和 y[i] 映射到同一缓存组，那么每次加载 x[i] 会驱逐 y[i-1] 的缓存行，接下来加载 y[i] 又驱逐 x[i] 的缓存行——形成"乒乓"式的相互驱逐，每次访问都不命中。

这就是为什么理解"哪些地址映射到同一组"如此重要——它是预测和避免冲突不命中的关键。

### Q5：矩阵乘法的6种循环顺序中，书上分析了每种的缓存行为，但实际写代码时到底应该用哪种？

对于标准的 C = A × B 矩阵乘法（C[i][j] += A[i][k] * B[k][j]），推荐使用 **ikj 或 kij 顺序**——它们对 B 和 C 的访问都是按行的（stride-1），只有 A 的访问是 stride-N，但 A 的同一个元素在内层循环中被重复使用（时间局部性好，可以保持在寄存器或 L1 中）。

但更重要的优化手段是**分块**：将大矩阵分成小的子矩阵，让每个子矩阵能装入 L1/L2 缓存。分块后循环顺序的影响变小，因为所有数据都在缓存中。在实际工程中，高性能矩阵乘法（如 OpenBLAS、MKL、BLIS）都使用了多层分块 + 向量化 + 寄存器分块的组合优化。

### Q6：Cache Lab Part A 中，LRU 替换策略应该怎么实现最简单？

对于 Cache Lab 的模拟器（条目数 E 不大，通常 ≤ 16），最简单的实现方式是给每个缓存行维护一个**访问时间戳（counter）**。每次命中或加载数据时，将全局计数器赋给该行的时间戳并递增全局计数器。需要替换时，找到时间戳最小的那一行即可。

这种方式的时间复杂度是 O(E)（需要遍历组内所有行找最小值），但因为 E 很小，完全足够。如果 E 很大，可以用链表实现（命中时移到链表头部，替换时取链表尾部），但对 Cache Lab 来说没有必要。

### Q7：本章和第5章的关系是什么？应该先学哪个？

CSAPP 的编排是先第5章（优化程序性能）再第6章（存储器层次结构）。但从知识依赖的角度看，两章互为补充：
- **第5章**关注 CPU 端的优化：指令级并行、流水化、数据依赖、分支预测等。它假设数据已经在缓存中，重点讨论 CPU 如何更快地处理数据。
- **第6章**关注内存端的优化：缓存命中率、局部性、数据布局。它假设 CPU 有足够的计算能力，重点讨论如何让数据更快地到达 CPU。

两章都学完后会发现：真实的性能优化需要同时考虑两个维度——既要让代码对 CPU 友好（减少数据依赖、利用指令级并行），也要让代码对缓存友好（利用空间和时间局部性）。Performance Lab（第5章实验）和 Cache Lab（第6章实验）分别训练这两个维度的优化能力。
