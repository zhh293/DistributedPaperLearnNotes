# RustDesk 远程控制真实机制说明

## 1. 文档目的

本文档基于当前仓库代码，对 `RustDesk` 的远程控制链路进行一次尽量贴近实现的整理，重点回答下面几个问题：

- 客户端启动后，到底先做了什么。
- 设备如何向服务端注册“自己在线”。
- 主控端输入目标 ID 后，连接是如何被建立的。
- 所谓“打洞”在这个项目里到底是怎么做的。
- 什么时候走直连，什么时候退化为 relay 中继。
- 密码、确认、2FA、权限是在什么地方验证的。
- 视频、输入、文件传输在链路层面是怎样承载的。
- 常见的 `ICE/STUN/TURN/DTLS/TLS1.3` 叙事，哪些适用于这个项目，哪些并不准确。

本文不照搬远控软件常见营销描述，也不按 ToDesk 的公开叙事来解释，而是尽量按照本仓库当前代码中能直接看到的行为来说明。


## 2. 先给结论

如果只用一句话概括这份项目的真实机制，可以概括为：

`RustDesk` 客户端/被控端启动后，会通过 `rendezvous server` 注册在线状态与身份信息；主控端连接某个目标 ID 时，先联系 `rendezvous server` 进行地址交换和建链协调；双方根据 NAT 情况尝试 `TCP`、`UDP(KCP)`、`IPv6` 直连；若条件不理想则转为 `relay server` 中继；在真正的端到端会话流建立后，再由被控端本地完成密码、2FA、确认和权限检查，最后进入远控、文件传输、终端或其他业务模式。

换句话说，它更像：

- `rendezvous` 负责在线注册、寻址、协调打洞、协调中继；
- `relay` 负责在无法直连时转发数据；
- 被控端本地会话对象负责真正的认证授权；
- 业务数据主要跑在已经建立好的会话流上。

它不是一个标准 WebRTC 栈，也不是教科书式完整 `ICE agent + STUN/TURN candidate pool + DTLS + SRTP` 的实现。


## 3. 本项目里最关键的文件

要理解整个机制，最重要的是下面这些文件：

- `src/server.rs`
  - 被控端服务启动入口。
  - 负责启动 `RendezvousMediator`。
  - 负责把打洞或 relay 建出来的流接入真正的会话。

- `src/rendezvous_mediator.rs`
  - 这是整个“在线注册、建链协调、打洞、中继回退”的核心文件。
  - 被控端常驻在线时，基本就在这里和 `rendezvous server` 交互。

- `src/client.rs`
  - 主控端发起连接的核心逻辑。
  - 负责向 `rendezvous server` 发建链请求。
  - 负责决定尝试 TCP、UDP(KCP)、IPv6 还是 relay。

- `src/client/io_loop.rs`
  - 会话建立后的客户端主循环。
  - 负责接收视频帧、登录响应、剪贴板、光标、错误等消息。

- `src/server/connection.rs`
  - 被控端真正的“会话对象”。
  - 负责发送 challenge/hash，接收登录请求，校验密码、2FA、权限与确认逻辑。
  - 负责进入远控、文件传输、终端、摄像头查看等不同业务模式。

- `src/common.rs`
  - 放了 NAT 探测、`secure_tcp()`、`punch_udp()` 等公共网络辅助逻辑。

- `src/kcp_stream.rs`
  - UDP 直连成功后，项目会在 UDP 之上跑 KCP，这个文件就是对应的封装。


## 4. 整体架构：这不是标准 WebRTC，而是 RustDesk 自己的协议栈

很多人第一次看这类远控软件时，容易下意识套用下面这套叙事：

- 先连信令服务器；
- 下发 ICE 配置；
- 收集 host / srflx / relay 候选；
- 用 STUN/TURN 走完整 ICE；
- 在 UDP 上 DTLS 握手；
- 再开多个业务子通道。

这套说法对“某些”远控产品或 WebRTC 产品并非完全错误，但对当前这个 `RustDesk` 仓库来说，并不准确。

从代码上看，`RustDesk` 当前更接近下面这套实现风格：

1. 启动后先测试 NAT 和可用的 rendezvous server。
2. 被控端通过 `RendezvousMediator` 向 rendezvous 注册自己在线。
3. 主控端输入目标 ID 后，联系 rendezvous 发起 `PunchHoleRequest`。
4. rendezvous 将建链消息转发给被控端。
5. 双方根据 NAT 类型、是否代理、是否支持 UDP/TCP/IPv6 等条件，直接尝试若干“预定义路径”：
   - TCP 直连
   - UDP 打洞后 KCP 会话
   - IPv6 直连
   - relay 中继
6. 底层流一旦建立，双方再在该流上完成会话握手与身份确认。
7. 被控端收到登录请求后，再本地做密码、2FA、确认窗口与权限控制。

因此更准确地说，项目使用的是：

- 自定义 `rendezvous_proto` 协议；
- 自定义 `register / punch / relay / health-check` 语义；
- UDP 直连时使用 `KCP`；
- TCP/rendezvous 侧使用项目自己的密钥交换与流加密逻辑。


## 5. 阶段一：启动与初始化

### 5.1 服务启动入口

被控端服务的核心入口在 `src/server.rs`。

主要启动逻辑：

- `start_server(is_server, no_server)` 会做 IPC 初始化、平台相关准备工作等。
- 真正进入在线与建链协调逻辑时，会调用 `RendezvousMediator::start_all()`。

这说明：

- 项目里“被控端常驻在线”的核心不是 UI 页面；
- 真正的网络常驻与协调器是 `RendezvousMediator`。


### 5.2 启动时做了哪些事情

`RendezvousMediator::start_all()` 里会做一批前置工作，大致包括：

- 触发 NAT 类型检测；
- 在某些情况下测试 rendezvous server 的连通性/延迟；
- 启动本地 server 状态管理；
- 启动 `direct_server()`，用于某些直接访问场景；
- 在条件满足时启动局域网监听；
- 进入与一个或多个 rendezvous server 的长周期交互循环。

这个阶段可以理解为：

- 客户端会尽可能知道自己的网络条件；
- 客户端会挑选并连接 rendezvous server；
- 被控端会把自己置于“可被别人发现并发起连接”的状态。


### 5.3 NAT 探测到底做了什么

项目里 NAT 探测的核心逻辑在 `src/common.rs` 的 `test_nat_type()` 和 `test_nat_type_()`。

它的真实行为不是：

- 向多个标准 STUN server 收集完整公网映射画像；
- 按 RFC 规范区分 Full Cone / Restricted Cone / Port Restricted Cone / Symmetric；
- 输出一套标准 ICE 候选池。

而是更务实、更简化的做法：

- 从当前配置中取 rendezvous server；
- 对两个不同端口的服务端地址发起 NAT 测试请求；
- 观察自己在两个探测点看到的映射端口是否相同；
- 若相同则记为 `ASYMMETRIC`；
- 若不同则记为 `SYMMETRIC`；
- 若无法确定，则保持 `UNKNOWN_NAT`。

这说明两点：

- 这个项目里 NAT 分类比标准术语更粗糙；
- 它的目的是为后续“能不能直连、要不要尽快转 relay”服务，而不是做学术级 NAT 类型画像。


### 5.4 启动时是否“注册设备”

是的，但和很多人想象的不一样。

在 `src/rendezvous_mediator.rs` 中，启动后会周期性发两类注册：

- `RegisterPeer`
  - 主要是告诉 rendezvous：“这个 ID 在线”。

- `RegisterPk`
  - 主要是上报当前设备 ID、UUID、公钥等身份材料。

当前仓库代码里，能直接确认的注册信息主要是：

- 设备 ID；
- UUID；
- 公钥；
- serial；
- 某些配置态字段。

而不能从这份代码中直接确认的，是下面这些常见说法：

- “会把所有网卡内网 IP 列表上报到信令服务器”
- “会上传 3-5 个备用 UDP 端口”
- “会在注册阶段直接上传设备密码哈希”

这些说法至少在当前仓库中没有以你描述的形式出现。


### 5.5 启动时与服务端建立的到底是什么连接

项目里会和 rendezvous server 建立持续交互的连接，但不应该简单粗暴地概括成“固定 TLS 1.3 TCP 信令长连接”。

真实情况更接近：

- 默认会连 rendezvous server；
- 若使用 WebSocket Secure，则由 `wss://` 提供传输层加密；
- 若不是 `wss://`，项目会通过 `secure_tcp()` 做自己的密钥交换与流加密；
- 这部分是项目自定义协议，不等价于“固定 TLS 1.3 实现”。

也就是说：

- “有加密”这个结论是对的；
- “一定是 TLS 1.3”这个结论从仓库代码看并不严谨。


### 5.6 启动后的保活逻辑

在 rendezvous 长连接侧，代码中有 `keep_alive` 概念，并且该值可由服务端消息调整。

超时逻辑大致是：

- 若长时间没收到消息；
- 超过 `keep_alive * 3 / 2`；
- 则判定 rendezvous 连接超时。

因此：

- 它不是写死“每 15 秒心跳、30 秒切备”的简单策略；
- 它是一个带服务端参数控制的长连接保活机制。


## 6. 阶段二：连接发起

### 6.1 主控端从哪里开始发起连接

主控端连接逻辑核心在 `src/client.rs` 的：

- `Client::start()`
- `Client::_start()`
- `Client::_start_inner()`

这里完成的事情大致是：

1. 解析目标 ID 或目标地址；
2. 选择当前使用的 rendezvous server；
3. 视情况准备 UDP NAT 测试任务；
4. 构造并发送 `PunchHoleRequest`；
5. 等待 rendezvous server 的回复；
6. 根据返回信息决定后续直连还是 relay。


### 6.2 主控端发给 rendezvous 的不是普通“连接申请表”

很多人会想象主控端点连接时发的是：

- 对方设备 ID；
- 密码哈希；
- 本机网络信息；
- 连接类型。

当前项目里，真正的核心请求消息是 `PunchHoleRequest`。

它至少会包含：

- 目标 ID；
- token；
- 本端 NAT 类型；
- 连接类型；
- 版本号；
- UDP 端口；
- 是否强制 relay；
- 可选 IPv6 地址信息。

这说明该请求的重点并不只是“我要连谁”，更重要的是：

- “我当前的打洞条件是什么”
- “你现在可以如何指导我建链”


### 6.3 主控端是否会同时尝试多条连接路径

会。

`Client::_start_inner()` 以及 `Client::connect()` 中能清楚看到：

- 会同时准备 TCP 直连尝试；
- 若有可用 UDP socket，则会准备 UDP/KCP 直连尝试；
- 若有 IPv6 条件，则也会尝试 IPv6；
- 这些连接尝试可以并发执行；
- 谁先成功就优先用谁。

这也是它实际表现上“连接建立较快”的一个重要原因。


### 6.4 rendezvous server 的作用是什么

在这份项目中，rendezvous server 的职责更接近：

- 保存设备在线状态；
- 让主控端通过 ID 找到被控端；
- 协调双方交换必要的建链信息；
- 通知被控端开始 punch hole；
- 在不适合直连时协调双方进入 relay。

换句话说，它更像“寻址与建链协调中心”。


## 7. 阶段三：地址交换与打洞准备

### 7.1 项目并没有完整暴露标准 ICE candidate 池

这一点非常重要。

很多文章讲远控软件时喜欢说：

- 先收集 Host candidate；
- 再收集 Server Reflexive candidate；
- 再申请 Relay candidate；
- 然后对所有 candidate 排序；
- 再交换给对方做 checklist。

在当前仓库中，没有看到标准 ICE agent 那套完整候选池结构与状态机。

相反，项目采用的是一套更简洁的、针对远控业务定制的做法：

- 先测出本端 NAT 类型；
- 先尽量拿到一个 UDP 可用映射端口；
- 由 rendezvous 返回对方地址、relay 信息和一些建链参数；
- 双方直接进入若干预设路径的连接尝试。

因此，这里更准确的说法不是“完整 ICE”，而是：

“RustDesk 使用了类似 ICE 思想的地址交换与连通性尝试，但实现上是自己的简化协议与状态机。”


### 7.2 局域网/内网场景如何处理

在 `src/rendezvous_mediator.rs` 中可以看到 `FetchLocalAddr` 和 `handle_intranet()` 的处理逻辑。

这表明项目会特殊处理局域网或内网可直连场景：

- 若双方存在更短的内网路径；
- 则会优先尝试这类路径；
- 成功后就没有必要再走更复杂的公网打洞或 relay。

所以“同一局域网优先”这件事，在这个项目中是成立的。


### 7.3 relay server 是什么时候选出来的

relay server 的来源主要有几种：

- 配置里显式指定；
- rendezvous server 提供；
- 若都没有，则基于 rendezvous host 推导出默认 relay 端口。

这个逻辑在 `get_relay_server()` 中非常清楚。

这意味着：

- relay 不是最后才临时发现的；
- 它在建链协调阶段就已经是可选兜底路径的一部分。


## 8. 阶段四：P2P 打洞

### 8.1 被控端收到什么消息才开始打洞

被控端的 `RendezvousMediator` 在运行期间会处理多个来自 rendezvous 的消息类型：

- `RegisterPeerResponse`
- `RegisterPkResponse`
- `PunchHole`
- `RequestRelay`
- `FetchLocalAddr`

其中与打洞最直接相关的是：

- `PunchHole`
- `FetchLocalAddr`
- `RequestRelay`

收到 `PunchHole` 后，被控端就进入 `handle_punch_hole()`。


### 8.2 被控端如何决定“打洞还是直接 relay”

`handle_punch_hole()` 中有一个非常关键的决策逻辑。

以下情况会显著倾向于 relay：

- 对端 NAT 是 `SYMMETRIC`；
- 本端 NAT 是 `SYMMETRIC`；
- 当前在代理环境；
- 当前使用 WebSocket；
- 强制 relay；
- TCP/UDP 直连条件不满足。

这说明本项目在设计上并不“盲目执着直连”，而是：

- 只在直连有现实成功率时才尝试；
- 在明显不适合打洞时尽早转 relay，以减少建链时间。


### 8.3 UDP 打洞到底怎么做

`RustDesk` 的 UDP 直连不是“打通后直接在裸 UDP 上自定义收发所有业务数据”，而是：

1. 双方通过 rendezvous 协调得到对端地址和本次 punch 条件。
2. 双方各自通过 `punch_udp()` 持续向对端发非常小的 UDP 包。
3. 一旦收到对端数据，说明 NAT 通路打通。
4. 随后在这个 UDP socket 之上建立 `KcpStream`。
5. 上层再把该 KCP 流当作统一的会话 `Stream` 来使用。

这里的关键点是：

- 打洞阶段发的是很小的探测流量；
- 业务会话层并不直接暴露“裸 UDP 通道”；
- 真正上层使用的是 `KCP over UDP` 封装后的可靠流。

这和很多“远控产品默认全用裸 UDP 信道”的印象并不完全一样。


### 8.4 为什么它要用 KCP

KCP 的价值大致在于：

- 能在 UDP 之上提供类似可靠流的语义；
- 比纯 TCP 更适合某些复杂网络条件；
- 对实时业务更友好；
- 便于项目统一上层会话抽象。

在这个项目里，KCP 让“UDP 打通后的上层处理”更像“拿到一个 Stream”，从而简化上层逻辑。


### 8.5 TCP 打洞怎么做

在 `handle_punch_hole()` 的 TCP 分支中，可以看到这样的步骤：

1. 先和 rendezvous 建立一条临时 TCP 连接；
2. 取当前本地地址；
3. 用这个本地地址去向对端做一次 `connect_tcp_local(peer_addr, Some(local_addr), ...)`；
4. 这样做的目的，是尽量让 NAT/网关记录这一方向的合法外联；
5. 然后把 punch 成功消息发出去；
6. 最终由 `accept_connection()` 在本地监听并接住实际到来的连接。

这比很多文章里写的“双方精确控制源端口并镜像对端 NAT 表”要务实得多。

更准确地说，它是在做：

- 使用已有地址和时序条件触发 NAT/防火墙放行；
- 再由被控端真正 `accept` 连接。


### 8.6 主控端如何选择直连结果

主控端的 `Client::connect()` 会并发准备多个 future：

- TCP 直连 future；
- UDP/KCP future；
- IPv6 future。

然后使用“谁先成功就选谁”的策略。

若这些路径都失败，且存在 relay server，则主控端会调用 `request_relay()` 转到中继。

因此，主控端并不是：

- 先试完一整套标准 ICE 候选对，再慢慢降级；

而更像是：

- 结合项目自己的路径集合，同时试几个现实可行方案，最快者胜出。


### 8.7 什么时候彻底认定“直连失败”

大致是以下几类情况：

- UDP 打洞在超时窗口内没有成功；
- TCP 直连或 TCP punch 没有建立成功；
- IPv6 不可用；
- NAT 类型或代理环境提示直连成功率很低；
- 整体连接超时。

这时就会进入 relay 路径，或者向上层返回“无法直连”的错误。


## 9. 阶段五：relay 中继回退

### 9.1 relay 并不是标准 TURN

这点要单独强调。

当前仓库里并没有出现标准 TURN allocation、TURN credential、TURN relay candidate 管理那一套完整流程。

相反，它使用的是自己的 relay 协议消息：

- `RequestRelay`
- `RelayResponse`

也就是说：

- “它有中继兜底”是对的；
- “它使用标准 TURN server”这个说法从当前代码看不严谨。


### 9.2 relay 建立流程

主控端的 relay 路径大致是：

1. 连接 rendezvous；
2. 发送 `RequestRelay`；
3. 等待 `RelayResponse`；
4. 拿到 `uuid`、relay server 等信息；
5. 连接 relay server；
6. 在 relay server 上继续建立会话流。

被控端的 relay 路径则大致是：

1. 收到来自 rendezvous 的 `RequestRelay`；
2. 调用 `create_relay()`；
3. 再转入 `server.rs` 中的 `create_relay_connection()`；
4. 最后统一进入 `create_tcp_connection()`。

因此 relay 虽然是兜底，但在架构上仍然走统一的“建立 Stream -> 进入 Connection 会话”模式。


## 10. 阶段六：会话建立与安全握手

### 10.1 对 rendezvous 的安全握手

`src/common.rs` 中的 `secure_tcp()` 实现了项目自己的服务器连接加密逻辑。

其关键特征是：

- 若当前使用的是 `wss://`，则不再额外做一层项目内加密；
- 否则读取对端发来的 `KeyExchange`；
- 使用服务端公钥校验签名；
- 调用 `create_symmetric_key_msg()` 生成对称密钥封装；
- 最终对该连接调用 `conn.set_key(key)`。

所以这里能得出的正确结论是：

- rendezvous 通信支持加密；
- 采用了项目自己的密钥交换逻辑；
- 不能简单概括为“固定 TLS 1.3 信令通道”。


### 10.2 端到端会话建立后的安全握手

客户端在拿到与对端之间的底层 `Stream` 后，还会调用 `secure_connection()`。

这个过程主要做的是：

- 验证 rendezvous 返回的带签名的对端身份公钥；
- 等待对端发来 `SignedId`；
- 校验其签名是否匹配目标 peer_id；
- 生成会话对称密钥；
- 通过 `PublicKey` 消息交换加密材料；
- 对会话流调用 `conn.set_key(key)`。

被控端对应的实现则在 `server.rs` 的 `create_tcp_connection()` 中：

- 若当前连接要求 `secure`；
- 会先向客户端发 `SignedId`；
- 再等待客户端的 `PublicKey`；
- 解析出会话密钥并设置到流上。

这说明：

- 会话级的端到端安全是存在的；
- 但它不是你常见描述中的 DTLS；
- 它是项目自定义的基于签名和对称密钥协商的握手。


### 10.3 是否有“多个专用通道同时建立”

从当前仓库实现看，不应该这样概括。

更准确的说法是：

- 默认先建立一个底层会话 `Stream`；
- 该 `Stream` 可能来自 TCP、KCP over UDP、IPv6 或 relay；
- 上层会话消息基本都通过这个 `Stream` 进行收发；
- 某些特殊业务模式会建立各自的连接类型，但不是默认远控刚开始就把主控、视频、音频、文件全拆成多个底层链路同时并行建立。

因此，“多专用通道并行建立”在这个项目里并不是最准确的描述。


## 11. 阶段七：登录、密码、确认、2FA 与权限控制

### 11.1 真正的认证在哪里发生

这是很多人最容易搞错的地方。

在当前仓库里：

- rendezvous 负责寻址、协调建链；
- 真正的登录认证主要发生在被控端本地的 `Connection` 对象中。

也就是说，主控端不是把密码丢给 rendezvous，让 rendezvous 代替被控端验证。

更真实的流程是：

1. 底层直连或 relay 流建立；
2. 被控端会话 `Connection::start()` 开始工作；
3. 被控端先发 `Hash` challenge；
4. 主控端收到后构造登录请求；
5. 被控端收到 `LoginRequest`；
6. 被控端本地决定：
   - 密码是否正确
   - 是否需要 2FA
   - 是否需要用户确认
   - 是否允许该业务类型
   - 是否需要拒绝


### 11.2 `on_open()` 之后发生什么

被控端的 `Connection::start()` 中，首先会调用 `on_open()`。

`on_open()` 主要做：

- 白名单检查；
- 某些平台/窗口状态检查；
- 记录对端 IP；
- 立即向主控端发出 `Hash` challenge。

这一点很关键，因为它解释了为什么后续密码验证是在被控端本地完成：

- challenge 是被控端发的；
- 响应是主控端根据 challenge 算出来再发回来的；
- 最终比较也发生在被控端。


### 11.3 `LoginRequest` 到底包含什么

收到 `LoginRequest` 后，被控端会先进入 `handle_login_request_without_validation()`，记录：

- 对端身份信息；
- 业务类型；
- 一些登录选项；
- trusted devices、视频 ACK、终端模式等状态。

之后才进入真正的验证流程。


### 11.4 密码校验逻辑

`src/server/connection.rs` 中有一整套密码校验相关函数，例如：

- `validate_password()`
- `validate_password_plain()`
- `validate_password_storage()`

说明当前项目支持多种密码来源或密码表示形式，例如：

- 临时密码；
- 永久密码；
- 本地存储形式的密码；
- 某些场景下的额外兼容路径。

这进一步说明：

- 密码校验确实发生在被控端本地；
- 它不是信令服务器中心化验证。


### 11.5 用户确认与拒绝

被控端在密码和模式判断之后，还会结合当前配置决定：

- 是否必须点确认；
- 是否允许无确认连接；
- 是否需要 2FA；
- 是否直接拒绝。

若被控端拒绝或校验失败，主控端最终看到的只是错误结果：

- 密码错误；
- 无权限；
- 需要 2FA；
- 连接被拒绝；
- 目标离线；
- 目标当前不可控制。

但决策主体多数时候是在被控端，而不是 rendezvous server。


### 11.6 2FA 与 trusted devices

当前仓库里确实支持 2FA。

相关逻辑包括：

- 是否需要 2FA；
- trusted devices 是否允许绕过 2FA；
- 通过 Telegram bot 发送验证码等。

这都发生在被控端会话逻辑内部。


### 11.7 权限控制不是建链时一次性定死的

在会话对象创建时，连接会带着 `control_permissions`。

随后 `Connection` 会根据这些权限决定是否允许：

- 键盘控制；
- 剪贴板；
- 音频；
- 文件传输；
- 远程重启；
- 录制；
- Block Input；
- Privacy Mode；
- 摄像头；
- 终端；
- 端口转发。

因此权限模型既体现在建链阶段，也体现在会话处理阶段。


## 12. 阶段八：进入业务会话

### 12.1 授权成功后会返回什么

一旦被控端判定授权通过，会构造 `LoginResponse`，其中最重要的是 `PeerInfo`。

`PeerInfo` 中会携带许多业务能力信息，例如：

- 用户名；
- 版本号；
- 主机名；
- 平台；
- 显示器信息；
- 当前显示器；
- 可用分辨率；
- 编码能力；
- 平台附加能力；
- 是否支持隐私模式；
- 是否支持终端；
- 某些系统特定能力。

这意味着主控端在“真正开始远控”前，会先拿到一份相当丰富的能力描述。


### 12.2 主控端如何确认“连接已经成功”

在 `src/client/io_loop.rs` 中，客户端主循环会持续读取来自 peer 的消息。

重要节点包括：

- 收到 `Hash`，说明要开始登录交互；
- 收到 `LoginResponse::PeerInfo`，说明认证与能力协商完成；
- 收到第一帧 `VideoFrame`，通常才意味着用户视觉上真正“进入桌面”。

因此“连接成功”其实有多个层次：

1. 底层流建立成功；
2. 登录认证成功；
3. 业务能力协商成功；
4. 第一帧桌面画面到达。


### 12.3 视频、输入、剪贴板等是如何承载的

客户端 `io_loop` 中能看到：

- 视频帧；
- Hash；
- LoginResponse；
- CursorData；
- CursorPosition；
- Clipboard；
- MultiClipboards；
- 其他控制消息；

都在同一个会话流的消息循环里被处理。

这说明：

- 项目上层消息复用一条已建立的会话流；
- 不是一开始就必须拆成多个底层传输管道。


## 13. 阶段九：数据传输子系统

### 13.1 桌面采集

桌面采集主要不在连接协调层，而在视频服务和平台实现层。

关键位置包括：

- `src/server/video_service.rs`
- `libs/scrap/`

可推断出的事实：

- 项目根据平台选择不同采集后端；
- Windows 下涉及 DXGI/GDI 等路径；
- macOS 下有 Quartz 路径；
- Linux 下有 X11/Wayland 路径；
- 编码能力也会受平台和硬件条件影响。

因此“驱动级采集”这个说法只能在部分平台与路径上成立，不能无条件泛化。


### 13.2 输入控制

输入控制主要在：

- `src/server/input_service.rs`
- `libs/enigo/`

这说明项目确实具备跨平台输入注入能力，但是否一定是“驱动级输入模拟”，要看平台和具体实现路径。


### 13.3 文件传输

文件传输不是普通远控消息的一个小附属，而是一个明确的业务模式。

从 `Connection` 逻辑上看：

- 文件传输有专门的登录分支；
- 权限是单独控制的；
- 目录读取、文件块传输、状态更新都在独立逻辑里处理。

所以更准确的说法是：

- 文件传输是 RustDesk 体系中的一种独立连接类型或业务模式；
- 而不是“默认远控链路上顺手附带的一个文件子通道”。


### 13.4 终端、端口转发、摄像头查看

同样地，终端、端口转发、查看摄像头等都是被明确建模的业务模式：

- `ConnType::TERMINAL`
- `ConnType::FILE_TRANSFER`
- `ConnType::VIEW_CAMERA`
- `PortForward`

这再次说明：

- 项目的“业务分型”非常明确；
- 建链后的认证、能力、权限也会按业务类型走不同分支。


## 14. 阶段十：保活、超时与异常处理

### 14.1 rendezvous 长连接保活

`RendezvousMediator` 和 `hc_connection()` 都体现了和 rendezvous 的健康检查思路：

- 有 keep_alive；
- 会有 heartbeat 风格的空包处理；
- 若长时间没有收到消息，则视为超时。

这属于“协调连接”的保活。


### 14.2 会话超时

在客户端 `io_loop` 和服务端 `Connection` 中，都能看到一个显著的 `SEC30` 计时。

这表示：

- 若会话在一段时间内没有收到数据；
- 就可能提示 `Timeout` 或认为连接断开。

所以这项目确实存在明确的会话超时控制。


### 14.3 备用 rendezvous server

在客户端建链入口处可以看到：

- 若当前 rendezvous server 连接失败；
- 并且配置中还有其他 rendezvous server；
- 则会尝试切换到其他 server。

这说明多 server 容灾是存在的。

但需要注意：

- 这不意味着它一定按你描述的固定 30 秒策略切换；
- 实际行为取决于连接超时、延迟测量和当前配置状态。


### 14.4 网络变化后的重连

仓库中存在一些 NAT 测试、server 刷新、重连与状态恢复逻辑，但并不能从当前片段中简单下结论说：

- 它实现了完全无缝的 ICE candidate 重新收集与无感迁移。

更准确的说法应该是：

- 项目具备重新测试 NAT、重新选择 rendezvous server、重新建链的机制；
- 在网络切换场景下可以尝试恢复；
- 但不要轻率说成“像移动实时通信那样做完整无缝迁移”。


## 15. 这一套机制与常见说法的逐条对照

下面把最容易混淆的点直接列出来。

### 15.1 “它是标准 ICE/STUN/TURN 吗？”

不准确。

更准确的说法是：

- 它借鉴了“通过中间协调服务器交换地址并尝试直连”的思想；
- 但实现是 `RustDesk` 自己的协议，不是标准 WebRTC ICE agent 全家桶。


### 15.2 “它的信令一定是 TLS 1.3 吗？”

不能这样下结论。

更准确的说法是：

- 它和 rendezvous 之间有加密；
- 若使用 `wss://`，底层由 WebSocket Secure 提供传输安全；
- 否则使用项目自己的 `secure_tcp()` 密钥交换。


### 15.3 “密码在信令服务器上校验吗？”

从当前仓库看，主要不是。

更准确的说法是：

- rendezvous 负责协助建链；
- 被控端本地的 `Connection` 负责 challenge、密码、2FA、确认和权限判断。


### 15.4 “它会在启动时把所有内网 IP 和多个备用 UDP 端口都上报吗？”

当前仓库中无法这样确认。

能直接确认的重点注册内容是：

- ID；
- UUID；
- 公钥；
- serial；
- 某些版本/配置相关信息。


### 15.5 “它把 NAT 分成四种标准锥型吗？”

当前仓库没有看到这种完整划分。

更准确地说，它做的是为建链决策服务的简化 NAT 分类。


### 15.6 “打洞成功后会做 DTLS 1.3 握手吗？”

当前仓库没有看到标准 DTLS 流程。

更准确的说法是：

- 项目在已建立的对端流上执行自己的身份签名校验与会话密钥协商。


### 15.7 “默认会建立多个专用并行通道吗？”

当前仓库不支持这样简单描述。

更准确的说法是：

- 先得到一个可用底层会话流；
- 再在该流上承载视频、输入、剪贴板等消息；
- 部分业务模式使用独立连接类型，而不是默认同时并行拉多条底层通道。


## 16. 一条最贴近代码的完整时序

下面给出一版简化但贴近实现的时序说明。

### 16.1 被控端上线

1. 被控端启动 `start_server()`。
2. 进入 `RendezvousMediator::start_all()`。
3. 测试 NAT 类型与 rendezvous server。
4. 周期性发送 `RegisterPeer` / `RegisterPk`。
5. rendezvous 知道该 ID 在线。


### 16.2 主控端发起连接

1. 主控端调用 `Client::start()`。
2. 选择当前 rendezvous server。
3. 启动 UDP NAT 端口测试任务。
4. 向 rendezvous 发送 `PunchHoleRequest`。


### 16.3 rendezvous 协调

1. rendezvous 查找目标 ID。
2. 将 `PunchHole` 或相关地址信息发给被控端。
3. 必要时下发 relay server 信息。


### 16.4 双方尝试建链

1. 被控端进入 `handle_punch_hole()`。
2. 若适合直连，则准备 UDP/KCP、TCP、IPv6 尝试。
3. 主控端并发尝试 TCP、UDP(KCP)、IPv6。
4. 若成功，得到一个可用 `Stream`。
5. 若不成功，则进入 `request_relay()`。


### 16.5 建立安全会话

1. 双方在对端流上执行 `SignedId/PublicKey` 风格的身份与密钥交换。
2. 流加密启用。


### 16.6 被控端本地认证

1. 被控端 `Connection::start()` 调用 `on_open()`。
2. 被控端发送 `Hash` challenge。
3. 主控端发送 `LoginRequest`。
4. 被控端本地验证密码、2FA、确认窗口、权限。
5. 若通过，返回 `LoginResponse::PeerInfo`。


### 16.7 进入业务模式

1. 主控端收到 `PeerInfo`。
2. 初始化显示、编码、剪贴板、输入能力。
3. 收到首帧视频后，用户看到远程桌面。
4. 后续所有视频、输入、剪贴板、文件或终端消息通过已建立会话流持续传输。


## 17. 给讲解时可直接用的口语版总结

如果你后面要给别人讲，可以直接这么说：

“RustDesk 不是那种完全照搬 WebRTC 教科书的实现。它的核心是一个 rendezvous 协调器。被控端启动后会先向 rendezvous 注册在线状态和身份材料；主控端输入目标 ID 后，先找 rendezvous 帮忙找到对端并协调建链；然后双方根据 NAT 情况尝试 UDP 打洞、TCP 直连、IPv6 直连，谁先通就用谁，不通就退到 relay。真正的密码校验、2FA 和确认窗口并不是由信令服务器来做，而是在被控端本地会话对象里完成。连接建立后，上层很多业务消息都跑在一个已经加密好的会话流上，视频、输入、剪贴板和文件传输都建立在这条基础链路或对应业务模式之上。”

## 20. 完整实例串讲：把整条链路按一次真实连接走一遍

前面各章节讲的是“机制拆解”。如果第一次看，容易觉得概念很多但不够直观。

这一章用一个具体例子，把整条链路按时间顺序串起来，让你看到每一步到底是在做什么。


### 20.1 场景设定

假设有下面几个角色：

- 主控端 A
  - 你的笔记本电脑，准备去控制另一台机器。

- 被控端 B
  - 办公室里一台已经开着 `RustDesk` 的 Windows 机器。

- `rendezvous server`
  - 负责“找人、传话、协调建链”。

- `relay server`
  - 当双方直连失败时负责中继转发。

再假设当前条件如下：

- B 的设备 ID 是 `123456789`。
- B 早就已经启动并在线。
- A 和 B 不在同一个局域网。
- A 和 B 都在 NAT 后面。
- B 设置了密码访问，但没有要求人工点击“接受”。
- 我们先看“直连成功”的情况，再看“直连失败转 relay”的情况。


### 20.2 第零幕：B 早就已经在线

在你真正发起连接之前，B 其实已经做了不少事情。

可以把它想象成：

- B 先去前台登记：“我今天在公司，工位号是 `123456789`，别人找我时你们能联系到我。”

落到项目实现里，大致是：

1. B 启动 `start_server()`。
2. 进入 `RendezvousMediator::start_all()`。
3. 先做 NAT 测试、server 测试等启动前准备。
4. 与 `rendezvous server` 保持长周期交互。
5. 周期性发送 `RegisterPeer` 和 `RegisterPk`。

这时 `rendezvous server` 知道的事情大概是：

- `123456789` 在线。
- 这台设备当前可联系。
- 它当前的身份材料、公钥、部分网络状态信息是有效的。

注意：

- 这时候还没有任何远控会话。
- 这只是“被控端处于可被找到状态”。


### 20.3 第一幕：A 打开 RustDesk

A 打开客户端之后，不是立刻就去连 B。

A 自己也要先做一些准备工作，可以理解为：

- 先看看自己当前网络怎么样；
- 先知道自己大概适不适合打洞；
- 先选一个当前可用的 `rendezvous server`。

从实现角度理解，A 这时会做类似下面的准备：

- 测试 NAT 类型；
- 测试当前 server；
- 准备后面可能要用的 UDP socket；
- 确认当前配置是否强制 relay、是否启用了 UDP、是否可用 IPv6。

所以这一幕的本质不是“开始连人”，而是：

- A 在为后面的建链做准备。


### 20.4 第二幕：A 输入 B 的 ID 并点击连接

你输入 `123456789`，点下“连接”的瞬间，真正的建链流程开始了。

很多人直觉上会以为：

- A 会直接向 B 发包；
- 或者 A 先把密码扔给服务器去验。

但当前项目的真实动作不是这样。

A 更像是在先找一个中间协调员：

- “我要找 `123456789`，请帮我联系它，并告诉我现在该怎么把链路搭起来。”

项目里这一步主要发生在 `Client::start()` 和 `Client::_start_inner()`。

A 此时做的大概是：

1. 连接当前选中的 `rendezvous server`。
2. 若条件允许，启动一个 UDP NAT 端口测试任务。
3. 构造 `PunchHoleRequest`。
4. 在请求里附带：
   - 目标 ID；
   - 自己的 NAT 类型；
   - 自己的连接类型；
   - 自己当前的 UDP 端口信息；
   - 是否强制 relay；
   - 版本与一些必要参数。

你可以把这一幕想象成：

- A 不是先去敲 B 的门；
- A 是先去前台登记：“我要找 `123456789`，这是我的联系方式和当前交通条件，请帮我安排。”


### 20.5 第三幕：rendezvous server 找到 B，并通知它准备接线

`rendezvous server` 收到 A 的 `PunchHoleRequest` 后，会去查自己的在线状态表。

它发现：

- `123456789` 确实在线；
- 对应的就是 B。

于是它开始做两件事情：

- 给 A 返回一些建链相关信息；
- 给 B 下发类似 `PunchHole`、`FetchLocalAddr` 或 relay 协调相关消息。

这一步最重要的作用不是“替双方传输业务数据”，而是：

- 让 A 和 B 知道“现在可以开始尝试见面了”。

你可以把这一幕想象成：

- 前台给 B 打电话：“有人找你，工号是 A，请准备接线。”


### 20.6 第四幕：B 收到建链通知，先判断值不值得直连

B 收到 `PunchHole` 之后，不会立刻上来就问密码。

它先想的是：

- 我和 A 现在有没有现实可能直接通上？

这一步对应 `handle_punch_hole()`。

B 会检查很多条件，例如：

- A 的 NAT 类型是不是很糟糕；
- 我自己的 NAT 类型是不是很糟糕；
- 当前是不是在代理环境里；
- 当前是不是 WebSocket 模式；
- 当前有没有可用 UDP；
- 当前有没有必要强制 relay。

所以这一幕本质上不是认证，而是：

- 路线判断。

也就是说，B 此时的思路不是：

- “你密码先给我。”

而是：

- “我先判断我们俩有没有希望把底层链路搭起来。”


### 20.7 第五幕 A：最理想情况，UDP/KCP 直连成功

我们先看第一种结局：

- A 和 B 经过判断后，发现有希望用 UDP 打洞。


#### 20.7.1 双方开始互相发小 UDP 包

此时 A 和 B 会开始向对方地址方向发送很小的 UDP 数据。

注意：

- 这些包不是正式的视频数据；
- 它们主要是为了“把 NAT 通路打通”。

可以把它想象成：

- A 和 B 站在各自小区门口同时喊对方名字；
- 不是为了正式聊天；
- 而是为了让各自门卫知道：“这个方向的人是我要联系的，允许回话进来。”

在项目实现中，这一步对应：

- `punch_udp()`
- `punch_udp_hole()`
- `udp_nat_listen()`


#### 20.7.2 某个瞬间，NAT 路通了

随着双方持续发小 UDP 包，总会出现一个关键时刻：

- A 第一次收到来自 B 的有效 UDP 数据；
- 或者 B 第一次收到来自 A 的有效 UDP 数据。

这个瞬间意味着：

- NAT 通路已经被各自网关“允许”了。

你可以把它想象成：

- 门卫终于记住这个访客，允许这条路上的回话进入小区。


#### 20.7.3 RustDesk 不是直接拿裸 UDP 跑会话，而是先起 KCP

这是这个项目非常关键的一个特点。

很多人脑补的是：

- 打洞成功了；
- 之后视频、输入、控制信令全部裸 UDP 开始飞。

但当前仓库里的实际做法是：

1. 先把 UDP 通路打通；
2. 再在这个 UDP socket 之上建立 `KcpStream`；
3. 然后把这个 KCP 流当作统一的会话 `Stream` 来使用。

这相当于：

- 路虽然打通了；
- 但项目不想直接在“裸路面”上跑所有东西；
- 它先铺一层“轨道”，这层轨道就是 `KCP`。

这样后面上层逻辑就可以更统一地处理数据流。


#### 20.7.4 A 和 B 终于有了一条真正能用的底层会话流

到了这一步，要注意一个很容易搞错的地方：

- “有可用流了”不等于“已经远控成功了”。

此时只能说明：

- A 和 B 底层网络通路打通了；
- 可以开始做正式会话握手了。

你可以把它想象成：

- 电话线已经接通；
- 但双方还没有开始核验身份。


#### 20.7.5 双方进行会话级安全握手

接下来，A 和 B 会在这条刚建立的流上做会话级别的安全握手。

它大致包括：

- 一方发送 `SignedId`；
- 另一方验证这个身份签名；
- 双方交换密钥材料；
- 最终为这条会话流设置对称密钥。

注意：

- 这不是标准 DTLS；
- 这是 RustDesk 自己的会话握手与加密逻辑。

你可以把它想象成：

- “路通了以后，先验明正身，再切换到加密对话。”


#### 20.7.6 B 发送 challenge，A 才开始发登录信息

在被控端，真正的会话对象 `Connection::start()` 起来后，会做一件很关键的事：

- 先向 A 发送 `Hash` challenge。

这个 challenge 的意义是：

- B 要先出一道题；
- A 用自己输入的密码去解这道题；
- 再把结果放在 `LoginRequest` 里回给 B。

这一步非常直观地说明：

- 密码验证的主导权在 B；
- 不是 rendezvous server 先替 B 把密码验掉。


#### 20.7.7 B 本地验证密码、2FA、确认和权限

B 收到 `LoginRequest` 后，才进入真正的认证逻辑。

B 会本地判断：

- 密码是否正确；
- 是否要求 2FA；
- trusted device 是否允许跳过某些验证；
- 当前会话类型是否允许；
- 是否需要本机用户确认；
- 是否允许键盘、文件、终端、摄像头、隐私模式等能力。

你可以把这一幕想象成：

- 前台已经把人送到门口；
- 现在真正决定“让不让进办公室”的，是办公室主人 B 自己。


#### 20.7.8 验证通过后，B 返回 `PeerInfo`

如果 B 认可 A 的身份，就会返回 `LoginResponse::PeerInfo`。

这份 `PeerInfo` 可以理解成一张“远端设备能力说明书”，会告诉 A：

- 我是什么系统；
- 我有几块显示器；
- 当前主显示器是谁；
- 有哪些编码能力；
- 支不支持终端；
- 支不支持隐私模式；
- 当前有哪些平台附加能力。

所以这一步不仅是：

- “密码对了”；

还包括：

- “你现在可以按这些能力来和我交互。”


#### 20.7.9 A 初始化远控环境，直到收到第一帧画面

A 收到 `PeerInfo` 之后，会开始：

- 初始化远控状态；
- 准备视频解码与显示；
- 准备输入控制；
- 准备剪贴板相关能力；
- 进入客户端主消息循环。

但从用户体感上，真正看到“远控连上了”通常还要等：

- 第一帧 `VideoFrame` 到来。

所以“连接成功”其实至少分四层：

1. 底层流建立成功；
2. 会话安全握手成功；
3. 登录认证成功；
4. 第一帧视频到达。


#### 20.7.10 稳定远控阶段

一旦第一帧视频到了，后续就进入稳定远控阶段：

- B 采集桌面、编码、发送画面；
- A 接收视频、解码、渲染；
- A 采集本地鼠标键盘操作，发给 B；
- B 在本机执行输入注入；
- 剪贴板、光标、文件、终端等消息继续在这条会话流上运转。

在这个阶段里：

- `rendezvous server` 已经退居幕后；
- 主舞台变成了 A 和 B 之间的会话流。


### 20.8 第五幕 B：如果直连失败，就转 relay

下面再看第二种结局：

- UDP 失败；
- TCP 也不理想；
- NAT 或网络条件很差；
- 最终只能走 relay。


#### 20.8.1 前半段和直连时完全一样

要注意，前面的很多步骤其实完全不变：

- B 提前在线并注册；
- A 找 `rendezvous server`；
- A 发 `PunchHoleRequest`；
- rendezvous 找到 B 并通知它；
- B 开始评估直连可能性。

所以 relay 并不是一开始就走的另一套世界，它只是：

- 直连路径的失败兜底。


#### 20.8.2 B 或 A 很快发现直连价值不大

例如下面这些情形：

- 一方是 `SYMMETRIC NAT`；
- 当前处于代理/WebSocket 环境；
- 没有合适的 UDP 条件；
- TCP 也不具备高成功率。

这时项目不会傻等太久，而是尽快转向 relay。

你可以把它想象成：

- A 和 B 本来想在路上碰头；
- 但都发现路况太差；
- 最后决定别折腾了，直接约到中转站见面。


#### 20.8.3 rendezvous 协调双方去同一个 relay 会话

这一阶段里，项目会使用：

- `RequestRelay`
- `RelayResponse`

这不是标准 TURN allocation，而是 RustDesk 自己的 relay 协议。

`rendezvous server` 在这里起到的作用是：

- 告诉双方去哪个 relay server；
- 给双方分配同一次 relay 会话所需的 `uuid`；
- 让两端最终能在 relay 上对上号。

你可以把它想象成：

- 前台对你们说：“别在路上找了，都去 3 号会议室，会议号是这串 UUID。”


#### 20.8.4 A 和 B 分别连接 relay server

接下来：

- A 去连 relay server；
- B 也去连 relay server；
- 双方通过相同的 `uuid` 进入同一个 relay 会话。

这时数据路径变成：

- A -> relay -> B
- B -> relay -> A

这条链路不如直连短，但能用。


#### 20.8.5 relay 建好后，后面的登录认证流程几乎不变

这是理解这套架构时一个特别关键的点：

- 进入 relay 并不意味着上层认证逻辑完全重写一套。

一旦 relay 把底层 `Stream` 建好，后面几乎和直连成功时一样：

1. 进行会话安全握手；
2. B 发送 `Hash` challenge；
3. A 发送 `LoginRequest`；
4. B 本地验证密码、2FA、权限、确认；
5. B 返回 `PeerInfo`；
6. A 收第一帧视频，进入远控。

所以 relay 改变的核心只是：

- 数据如何送达；

而不是：

- 会话认证是谁负责；
- 登录逻辑长什么样；
- 上层业务怎么跑。


### 20.9 用一句最接近实现的话概括整个例子

如果把这个例子再压缩成一句话，可以记成：

`RustDesk` 的真实流程不是“先把密码交给服务器验证，然后服务器决定你怎么连过去”，而是“先通过 rendezvous 把主控端和被控端的底层路搭起来，能直连就直连，不行就 relay；路通了以后，再由被控端本地会话对象决定你有没有资格进来，以及你能做什么”。 

这句话基本能把整个项目的职责边界一次性说清：

- `rendezvous` 负责找人、传话、协调；
- `punch / relay` 负责把路打通；
- `Connection` 负责认证与授权；
- `io_loop` 负责进入远控后的业务收发。


### 20.10 再给一个非常口语化的类比

如果还想再直观一点，可以把整个流程想成“去别人公司拜访”：

1. B 提前在前台登记
   - “我今天在公司，工位号 `123456789`。”

2. A 到前台找人
   - “我找 `123456789`。”

3. 前台负责联系 B
   - 但前台不负责决定你能不能进办公室。

4. A 和 B 尝试见面
   - 能直接碰头最好；
   - 路不通就去中转会议室见面。

5. 真见到面之后
   - B 才问：“你是谁？密码对不对？要不要 2FA？我要不要同意你进来？”

6. B 同意后
   - 再把自己的办公室情况告诉 A：
   - “我有几块屏幕，我支持哪些功能，你接下来可以怎么用我这台机器。”

7. 最后正式开始办公
   - A 看画面；
   - A 发鼠标键盘；
   - B 执行输入；
   - 文件、终端、剪贴板继续传。

这个类比虽然不严谨，但很适合在脑子里快速建立直觉。


## 21. 从计网底层看 RustDesk 的打洞与中继

前面文档已经把“谁负责什么”讲清楚了，但如果你真正关心的是计网层面的底层机理，那么只知道“先 rendezvous，再 punch，再 relay”还不够。

这一章专门换一个视角：

- 不再站在产品流程角度；
- 而是站在 `socket / NAT / 路由器状态表 / UDP 回包放行条件 / 中继转发` 的角度；
- 把 `RustDesk` 这套链路拆到尽量贴近网络层和传输层。

这一章的目标不是复述市场材料，而是把下面这些问题讲透：

- 为什么双方都在 NAT 后面，UDP 还能打通。
- NAT 到底记录了什么，什么时候会放回包。
- RustDesk 能控制什么，不能控制什么。
- 为什么对称型 NAT 更容易失败。
- 为什么 relay 稳定。
- 为什么这个项目在 UDP 打通后还要起 KCP。


### 21.1 先纠正一个最容易误解的点

很多面向大众的打洞文章喜欢写成下面这种口吻：

- “应用让 B 用源端口 50000 发包”
- “应用精确控制公网源端口”
- “双方交换完公网 IP 和端口之后，就能按指定端口互打”

这种说法很容易误导。

对当前项目、更准确也更符合计网事实的说法是：

- 应用程序通常只能稳定控制“本地 socket 绑定的端口”；
- 应用程序不能直接命令家用 NAT 路由器“公网映射端口必须是多少”；
- 公网映射端口由 NAT 设备按自己的策略决定；
- RustDesk 真正做的是：
  - 尽量复用同一个本地 socket；
  - 让 `rendezvous` 观察到该 socket 当前的公网映射 endpoint；
  - 再把这个 endpoint 交换给对端；
  - 让双方都朝这个 endpoint 发包，赌 NAT 映射在短时间内足够稳定。

所以本项目 punch 成功的关键不是：

- “指定公网端口”

而是：

- “复用 socket + 让 server 观察映射 + 在映射失效前快速互打”


### 21.2 RustDesk 里 Host 直连、UDP punch、relay 三条路本质上有什么区别

从计网视角看，这三条路径本质上分别解决不同问题。

#### 21.2.1 Host / 内网直连

适用场景：

- 双方在同一局域网；
- 或双方之间存在可直达的内网三层路径。

本质：

- A 直接向 B 的内网 IP:端口发包；
- 由交换机 / 内网路由器直接转发；
- 不需要公网 NAT 映射；
- 不需要 relay。

#### 21.2.2 UDP punch

适用场景：

- 双方都在 NAT 后；
- 但 NAT 行为足够“稳定”和“宽松”；
- 双方都能主动向对方公网 endpoint 发出站 UDP。

本质：

- A 和 B 各自先发出站 UDP；
- 让各自 NAT / 防火墙里出现“允许对方回包进入”的状态；
- 只要这两个状态在时间上重叠，就会有某个 UDP 包真正穿进去。

#### 21.2.3 relay

适用场景：

- 直连难度太高；
- 对称型 NAT；
- 严格防火墙；
- 代理/WebSocket 环境；
- UDP 不可靠或被封禁。

本质：

- A 和 B 都不再试图互相直接找；
- 而是各自主动访问同一个公网 relay server；
- relay 再把两个方向的数据转发起来。


### 21.3 站在 NAT 设备角度，到底发生了什么

下面先不讲 RustDesk，先只讲一个最基本的 NAT 认知。

当内网主机通过 NAT 路由器向公网发一个 UDP 包时，路由器一般会做几件事：

1. 把源地址从内网地址改成自己的公网地址。
2. 为这次会话分配一个公网端口映射。
3. 在自己的状态表 / NAT 表里记住：
   - 这个公网端口当前对应哪个内网主机、哪个内网端口；
   - 某些 NAT 还会进一步记住这个映射当前允许哪些外部 endpoint 回包。
4. 只要回包满足该状态表的条件，就把公网回包重新转发回对应的内网 socket。

所以对 punch 来说，最关键的不是“穿墙”，而是：

- 让 NAT 表里出现一条状态；
- 并且让对方发来的包恰好命中这条状态。


### 21.4 一个更贴近 RustDesk 实现的 UDP 打洞例子

下面给一个比通俗文章更贴近当前项目实现的例子。

假设：

- A 内网地址：`192.168.1.100:55000`
- A 路由器公网 IP：`1.1.1.1`
- B 内网地址：`192.168.2.200:56000`
- B 路由器公网 IP：`2.2.2.2`
- `rendezvous server`：`9.9.9.9:21116`

假设 NAT 映射结果如下：

- A 这个本地 UDP socket 对外映射成 `1.1.1.1:32001`
- B 这个本地 UDP socket 对外映射成 `2.2.2.2:45002`

注意，这里的 `32001` 和 `45002`：

- 不是应用直接指定的公网端口；
- 而是 NAT 设备给这两个本地 socket 分配出来、并被 `rendezvous` 观察到的公网端口。


#### 21.4.1 A 先暴露自己的外网 UDP endpoint

`0ms`

- A 创建本地 UDP socket，绑定 `192.168.1.100:55000`

`1ms`

- A 用这个 socket 向 `rendezvous 9.9.9.9:21116` 发送一个 NAT 测试或打洞相关的 UDP 包

`2ms`

- A 的 NAT 路由器看到一条出站 UDP：
  - 内网：`192.168.1.100:55000 -> 9.9.9.9:21116`
  - NAT 选择公网映射端口 `32001`
  - 公网看到的是：`1.1.1.1:32001 -> 9.9.9.9:21116`

这时 A 的 NAT 表里会出现一条状态，可以粗略理解为：

- `1.1.1.1:32001 <-> 192.168.1.100:55000`

如果把它再展开一点，可以理解成：

- 允许满足当前 NAT 策略的回包，落到 `1.1.1.1:32001` 后，转回 `192.168.1.100:55000`

`3ms`

- `rendezvous` 收到 A 的 UDP 包，于是知道：
  - “A 当前这个 socket 对外显示为 `1.1.1.1:32001`”


#### 21.4.2 B 也暴露自己的外网 UDP endpoint

`5ms`

- B 创建本地 UDP socket，绑定 `192.168.2.200:56000`

`6ms`

- B 用这个 socket 向 `rendezvous 9.9.9.9:21116` 发出自己的 UDP 探测或 `PunchHoleSent`

`7ms`

- B 的 NAT 路由器看到：
  - 内网：`192.168.2.200:56000 -> 9.9.9.9:21116`
  - NAT 分配公网映射端口 `45002`
  - 公网看到的是：`2.2.2.2:45002 -> 9.9.9.9:21116`

于是 B 的 NAT 表里也出现对应状态：

- `2.2.2.2:45002 <-> 192.168.2.200:56000`

`8ms`

- `rendezvous` 收到 B 的 UDP 包，于是知道：
  - “B 当前这个 socket 对外显示为 `2.2.2.2:45002`”


#### 21.4.3 rendezvous 交换双方的公网 endpoint

`10ms`

- A 通过 TCP 控制连接对 `rendezvous` 发出 `PunchHoleRequest`
- `rendezvous` 把 B 的公网 endpoint `2.2.2.2:45002` 告诉 A
- `rendezvous` 同时把 A 的公网 endpoint `1.1.1.1:32001` 告诉 B

到这一刻：

- A 知道应该朝 `2.2.2.2:45002` 打
- B 知道应该朝 `1.1.1.1:32001` 打

这一步是整个 punch 的信息前提。

如果没有这个观察与交换过程：

- A 不知道 B 当前 NAT 映射成哪个公网端口；
- B 也不知道 A 当前 NAT 映射成哪个公网端口；
- 双方根本无从互打。


#### 21.4.4 A 和 B 同时朝对方 endpoint 发空 UDP 包

`20ms`

- A 不新开 socket，而是继续复用 `192.168.1.100:55000`
- A 把目标设置为 `2.2.2.2:45002`
- A 开始持续发送很小的 UDP 包

如果 A 的 NAT 映射在不同目标间仍然保持稳定，那么公网侧看到的是：

- `1.1.1.1:32001 -> 2.2.2.2:45002`

与此同时，A 的 NAT / 防火墙会刷新或新增一条状态，可以理解成：

- 允许来自 `2.2.2.2:45002` 的回包，回到 `1.1.1.1:32001` 后转发给 `192.168.1.100:55000`

`21ms`

- B 也继续复用 `192.168.2.200:56000`
- B 把目标设置为 `1.1.1.1:32001`
- B 开始持续发送很小的 UDP 包

如果 B 的 NAT 映射也稳定，那么公网侧看到的是：

- `2.2.2.2:45002 -> 1.1.1.1:32001`

与此同时，B 的 NAT / 防火墙也刷新或新增状态：

- 允许来自 `1.1.1.1:32001` 的回包，回到 `2.2.2.2:45002` 后转发给 `192.168.2.200:56000`


#### 21.4.5 首个穿透包成功到达

`25ms`

- A 发出的某个 UDP 包到达 B 的 NAT 路由器
- B 的路由器去查状态：
  - 是否允许 `1.1.1.1:32001 -> 2.2.2.2:45002`
- 如果 B 已经先朝 A 打过包，并且 NAT 策略允许，则这条状态存在
- 于是这个包被转发给：
  - `192.168.2.200:56000`

或者反过来：

`26ms`

- B 发出的某个 UDP 包到达 A 的 NAT 路由器
- A 的路由器去查状态：
  - 是否允许 `2.2.2.2:45002 -> 1.1.1.1:32001`
- 如果存在，则把这个包转给：
  - `192.168.1.100:55000`

这一步的关键结论是：

- 打洞成功不要求“第一个包就穿透”
- 它只要求：
  - 双方都持续发；
  - 两边 NAT 都已经出现允许回包的状态；
  - 某个时刻有一个包刚好命中对端状态表。


#### 21.4.6 一旦收到数据，说明 UDP 通路已经打通

只要 A 或 B 有一边第一次真正收到来自对方的 UDP 数据，就说明：

- 这条 UDP 路在当前时刻是可用的。

此时 RustDesk 不会立刻开始在“裸 UDP”上发送桌面视频，而是：

- 在这个 UDP socket 之上建立 `KCP`；
- 后续把这条 `KCP` 流包装成统一的会话 `Stream`。

所以对当前项目来说，UDP punch 的最终目标不是：

- “证明空包能来回”

而是：

- “让 KCP 有一条能跑起来的 UDP 路”


### 21.5 为什么这个项目在 UDP 打通后还要起 KCP

这是本项目很重要的一层设计。

从网络视角看：

- UDP punch 只是负责把 NAT 门打开；
- 但 UDP 本身是无连接、无重传、无顺序保证的；
- 上层业务如果直接靠裸 UDP 自己重写全部会话语义，会很复杂。

所以项目采用的做法是：

- UDP 通路一旦打通；
- 马上在该 UDP socket 上建立 `KcpStream`；
- 后续上层看到的更像是一条可靠流。

你可以把它想成：

- UDP 打洞负责“修通一条路”
- KCP 负责“在路上铺轨道”
- 真正的会话数据跑在“轨道”上

这也是为什么当前项目更准确的描述应该是：

- `UDP punch + KCP over UDP`

而不是简单一句：

- “UDP 打洞成功后就直接开始发业务包”


### 21.6 为什么对称型 NAT 更容易失败

这部分是 punch 理解的核心。

先说一个事实：

- `rendezvous` 能观察到的，是 A/B 各自“朝 rendezvous 发包时”的公网映射端口。

但这不等于：

- A/B 朝 peer 发包时，一定还会继续使用同一个公网映射端口。

如果 NAT 是对称型，可能发生这样的事情：

#### 21.6.1 A 朝 rendezvous 发包时

- A 本地 socket：`192.168.1.100:55000`
- 目标：`9.9.9.9:21116`
- NAT 映射成：`1.1.1.1:32001`

于是 `rendezvous` 观察到：

- “A 是 `1.1.1.1:32001`”

#### 21.6.2 但 A 朝 B 发包时

- A 仍然是同一个本地 socket `192.168.1.100:55000`
- 目标变成了 `2.2.2.2:45002`
- 对称型 NAT 可能重新给它分配一个新的公网端口：
  - `1.1.1.1:32077`

这会带来一个致命问题：

- `rendezvous` 告诉 B：去找 A 的 `1.1.1.1:32001`
- 但 A 真正朝 B 发包时，在公网出现的却是 `1.1.1.1:32077`

也就是说：

- server 观察到的端口；
- peer 实际应该回打的端口；

不再是同一个。

这时 punch 极其容易失败。

所以对称型 NAT 难点的本质不是：

- “防火墙太严格”

而更准确地说是：

- “同一本地 socket 面向不同远端时，公网映射不稳定，导致 rendezvous 观察到的 endpoint 不能可靠代表 peer 方向上的真实 endpoint”

这就是为什么当前项目里一旦看到 `SYMMETRIC` 条件明显不利，就会更倾向快速转 relay。


### 21.7 TCP 打洞从状态机角度为什么更难

UDP 打洞之所以相对常见，是因为：

- UDP 没有连接状态机；
- 只要对端包能穿过来，应用就能收到。

但 TCP 不一样。

TCP punch 需要面对更多状态机约束：

- `SYN`
- `SYN-ACK`
- `ACK`
- NAT / 防火墙对 TCP 状态的跟踪通常更严格

当前项目里，TCP punch 更像是在做下面这件事：

- 先用某个本地地址主动向对端发起一次 TCP connect；
- 不是为了马上在这条连接上发业务；
- 而是为了在 NAT / 防火墙中制造一个“我主动尝试过这个 peer”的状态；
- 然后尽量在这个时间窗口里接住对端回来的连接。

可以把它理解成：

- 先在状态机里“预热”一条允许路径；
- 再赌双方的状态窗口能重叠起来。

因此 TCP punch 失败率通常更高，原因不是它“比 UDP 少发几个包”，而是：

- TCP 中间盒的状态要求更复杂；
- NAT / 防火墙更在意三次握手是否完整匹配。


### 21.8 relay 为什么稳定

relay 稳定的原因，其实非常朴素。

直连时，难点在于：

- A 在 NAT 后面；
- B 也在 NAT 后面；
- 双方要彼此“找到并命中对方 NAT 的允许状态”。

relay 时，问题被改写成：

- A 主动访问公网 relay server；
- B 也主动访问公网 relay server。

这时：

- A 不需要命中 B 的 NAT；
- B 也不需要命中 A 的 NAT；
- 它们都只需要命中“公网服务器的固定地址”。

从 NAT 的视角看，这就简单多了：

- 内网主机主动访问公网服务器，是 NAT 最擅长处理的常规模式；
- 只要两边都能稳定访问 relay，relay 就能在应用层把两个方向的数据拼起来。

所以 relay 成功率高的本质不是：

- relay 更“高级”

而是：

- relay 把“双边 NAT 互找”这个困难问题，降级成了“两边分别找公网服务器”这个简单问题。


### 21.9 把 RustDesk 的计网本质压缩成一句话

如果只从计网底层总结当前项目的建链机制，可以记成下面这句：

`RustDesk` 的 UDP 打洞本质上是：双方先各自使用同一个本地 UDP socket 向 `rendezvous` 暴露当前的公网映射 endpoint，随后由 `rendezvous` 交换双方 endpoint；接着两端都持续朝对方 endpoint 发小 UDP 包，使各自 NAT / 防火墙中出现允许对方回包进入的状态；只要两边状态重叠，首个穿透包一旦到达，对端就在同一 socket 上切到 `KCP`，从而建立后续会话承载通道。 


### 21.10 这一章和常见宣传话术的区别

为了防止后续又被“标准术语”带偏，这里把区别再明确列一下。

- 不是“应用指定公网源端口”
  - 更准确是：应用复用本地 socket，NAT 选择公网映射端口，server 观察并交换 endpoint。

- 不是“完整标准 ICE checklist”
  - 更准确是：项目使用自己的 `rendezvous + punch + relay` 协议与连接路径集合。

- 不是“打通 UDP 后直接裸传业务”
  - 更准确是：UDP 打通后在同一 socket 上起 `KCP`。

- 不是“对称型 NAT 只是更严格一点”
  - 更准确是：对称型 NAT 让 `rendezvous` 观察到的 endpoint 对 peer 方向不再可靠。

- 不是“relay 是一种神秘穿墙手段”
  - 更准确是：relay 把难题从“双向 NAT 互找”变成“两边各自访问公网服务器”。
