# 秒杀系统架构设计

## 一、问题背景

### 1.1 业务场景

秒杀是指在某一时刻，大量用户同时争抢购买同一商品并完成交易的过程。自2011年首次出现以来，无论是双十一购物还是抢票场景，秒杀已随处可见。从架构视角来看，秒杀系统本质上是一个高性能、高一致、高可用的"三高"系统。

典型秒杀场景的特征：

1. **瞬时高并发**：平时QPS可能只有几百，秒杀开始瞬间QPS暴增到数十万甚至百万级
2. **库存有限**：商品库存通常只有几十到几千件，远小于参与抢购的用户数
3. **时间极短**：秒杀活动通常在几秒到几分钟内结束
4. **绝不超卖**：库存100件就只能卖100件，超卖意味着直接资金损失
5. **绝不少卖**：有库存却卖不出去，意味着营销效果打折

### 1.2 核心挑战分析

| 挑战维度 | 具体问题 | 影响 |
|---------|---------|------|
| 高性能 | 瞬时流量是日常的百倍，系统直接被压垮 | 页面打不开、请求超时 |
| 一致性 | 并发扣减库存导致超卖 | 100件商品卖出200单 |
| 高可用 | 秒杀流量波及非秒杀业务 | 全站不可用 |
| 防作弊 | 黄牛用秒杀器扫货 | 真实用户买不到 |
| 资金安全 | 恶意下单不付款占库存 | 商家无法正常售卖 |

### 1.3 减库存方案选型

在电商平台中，用户购买分为"下单"和"付款"两个步骤。在哪一步减库存，是秒杀系统设计的第一个核心决策：

**方案一：下单减库存**
- 用户下单时直接扣减库存
- 优点：逻辑简单，控制精确，不会超卖
- 缺点：恶意买家可下单不付款占完库存
- 适用场景：秒杀（抢到就是赚到，不付款概率低）

**方案二：付款减库存**
- 用户付款时才扣减库存
- 优点：避免恶意下单占库存
- 缺点：可能超卖（100件商品300人下单成功，但只有100人能付款成功）
- 适用场景：普通电商（库存充足，恶意下单概率低）

**方案三：预扣库存**
- 下单时预扣，保留一定时间（如10分钟），超时自动释放
- 优点：折中方案，兼顾两者
- 缺点：逻辑复杂，恶意买家仍可在超时后重新下单
- 适用场景：机票、电影票

**选型结论**：秒杀场景采用"下单减库存"最合理，因为秒杀商品"抢到就是赚到"，不付款概率极低，且逻辑简单性能更优。

### 1.4 设计目标

| 目标维度 | 具体要求 |
|---------|---------|
| 峰值QPS | 支撑10万+ QPS |
| 响应时间 | P99 < 200ms |
| 库存一致性 | 绝不超卖，不少卖 |
| 可用性 | 99.99%（秒杀期间不宕机） |
| 隔离性 | 秒杀流量不影响非秒杀业务 |
| 防作弊 | 识别并拦截秒杀器 |

### 2.2 分层架构设计

秒杀系统采用六层漏斗式架构，每一层逐级削减流量：

| 层级 | 职责 | 技术手段 | 流量削减效果 |
|------|------|---------|------------|
| CDN层 | 静态资源缓存 | 活动页静态化、JS/CSS缓存 | 削减90%静态请求 |
| 前端层 | 交互控制 | 答题验证码、按钮防重复点击 | 削减50%无效请求 |
| Nginx层 | 接入限流 | 令牌桶限流、IP黑名单 | 削减70%超量请求 |
| 网关层 | 业务限流 | 滑动窗口限流、用户维度限流 | 控制到系统能承受的QPS |
| 服务层 | 核心逻辑 | Redis Lua预扣减、MQ泄洪 | 串行化处理，防超卖 |
| 存储层 | 持久化 | MySQL事务、分库分表 | 最终一致性落库 |

### 2.3 热点隔离策略

秒杀流量必须与非秒杀业务隔离，防止0.01%的商品影响99.99%的商品：

1. **物理隔离**：秒杀服务独立部署，独立数据库，独立Redis集群
2. **逻辑隔离**：网关层根据URL路径将秒杀流量路由到独立集群
3. **资源隔离**：秒杀服务使用独立的线程池、连接池，防止资源争抢

## 三、核心链路设计

### 3.1 秒杀链接动态生成

**问题**：如果秒杀链接固定，黄牛可以提前写脚本在秒杀开始瞬间发起请求。

**方案**：秒杀链接动态生成，每次活动的URL都不同，且在活动开始前1秒才生成。

```java
/**
 * 秒杀链接动态生成器
 * 核心思路：活动ID + 商品ID + 时间戳 + 密钥 → MD5 → 拼接成动态URL
 */
public class SeckillUrlGenerator {

    private static final String SECRET_KEY = "seckill_dynamic_secret_2024";

    /**
     * 生成秒杀链接
     * @param activityId 活动ID
     * @param itemId 商品ID
     * @return 动态秒杀URL
     */
    public String generateSeckillUrl(Long activityId, Long itemId) {
        // 1. 获取当前秒级时间戳
        long timestamp = System.currentTimeMillis() / 1000;

        // 2. 拼接签名原料：活动ID + 商品ID + 时间戳 + 密钥
        String signSource = activityId + "_" + itemId + "_" + timestamp + "_" + SECRET_KEY;

        // 3. MD5签名
        String sign = DigestUtils.md5Hex(signSource);

        // 4. 拼接动态URL
        return String.format("/seckill/%d/%d?ts=%d&sign=%s", activityId, itemId, timestamp, sign);
    }

    /**
     * 验证秒杀链接合法性
     */
    public boolean validateSeckillUrl(Long activityId, Long itemId, long timestamp, String sign) {
        // 1. 检查时间戳是否在有效期内（防止链接被提前获取）
        long now = System.currentTimeMillis() / 1000;
        if (now < timestamp - 5 || now > timestamp + 3600) {
            return false; // 链接未生效或已过期
        }

        // 2. 重新计算签名比对
        String signSource = activityId + "_" + itemId + "_" + timestamp + "_" + SECRET_KEY;
        String expectedSign = DigestUtils.md5Hex(signSource);

        return expectedSign.equals(sign);
    }
}
```

### 3.2 前端层防护：答题验证码

**问题**：即使链接动态生成，秒杀开始瞬间仍有大量请求同时涌入。

**方案**：在秒杀按钮点击后，弹出答题验证码，将用户请求在时间维度上错开。

```java
/**
 * 验证码生成与校验
 * 核心思路：生成简单数学题，用户需计算后提交答案
 * 效果：将1秒内的10万请求分散到10秒
 */
public class SeckillCaptchaService {

    /**
     * 生成数学验证码
     * @param userId 用户ID
     * @return 验证码题目
     */
    public CaptchaDTO generateCaptcha(Long userId) {
        Random random = new Random();
        int a = random.nextInt(20) + 1;  // 1~20
        int b = random.nextInt(20) + 1;  // 1~20
        int operator = random.nextInt(3); // 0:+ 1:- 2:×

        String question;
        int answer;
        switch (operator) {
            case 0:
                question = a + " + " + b + " = ?";
                answer = a + b;
                break;
            case 1:
                question = a + " - " + b + " = ?";
                answer = a - b;
                break;
            default:
                question = a + " × " + b + " = ?";
                answer = a * b;
                break;
        }

        // 生成验证码唯一标识
        String captchaId = UUID.randomUUID().toString();

        // 将答案存入Redis，60秒过期
        String redisKey = "seckill:captcha:" + captchaId;
        redisTemplate.opsForValue().set(redisKey, String.valueOf(answer), 60, TimeUnit.SECONDS);

        return new CaptchaDTO(captchaId, question);
    }

    /**
     * 校验验证码
     */
    public boolean validateCaptcha(String captchaId, String userAnswer) {
        String redisKey = "seckill:captcha:" + captchaId;
        String correctAnswer = (String) redisTemplate.opsForValue().get(redisKey);

        if (correctAnswer == null) {
            return false; // 验证码已过期
        }

        // 答对后删除验证码，防止复用
        redisTemplate.delete(redisKey);
        return correctAnswer.equals(userAnswer);
    }
}
```

### 3.3 Nginx层限流：令牌桶算法

**问题**：即使前端做了错峰，Nginx仍可能收到超过后端承受能力的请求。

**方案**：在Nginx层使用令牌桶算法限流，控制进入后端的请求速率。

```nginx
# Nginx限流配置
# 每秒只允许1000个请求进入后端
limit_req_zone $binary_remote_addr zone=seckill:10m rate=1000r/s;

location /seckill/ {
    limit_req zone=seckill burst=2000 nodelay;
    proxy_pass http://seckill_backend;
}
```

**令牌桶算法原理**：
1. 以固定速率向桶中放入令牌（rate=1000r/s → 每毫秒放1个令牌）
2. 桶有最大容量（burst=2000 → 最多存2000个令牌）
3. 请求到来时从桶中取1个令牌，取到则放行，取不到则拒绝
4. `nodelay`：超出burst的请求立即拒绝，不排队等待

### 3.4 网关层限流：滑动窗口算法

**问题**：Nginx限流是IP维度的，同一个IP后可能有多个用户（如公司内网）。需要更细粒度的限流。

**方案**：在API网关层实现用户维度的滑动窗口限流。

```java
/**
 * 滑动窗口限流器
 * 核心思路：用Redis ZSet实现滑动窗口
 * - key: rate_limit:{userId}:{api}
 * - score: 请求时间戳
 * - member: 请求唯一ID
 * 
 * 工作流程：
 * 1. 请求到来时，先删除窗口外的旧记录（score < 当前时间 - 窗口大小）
 * 2. 统计当前窗口内的请求数
 * 3. 如果请求数 < 限制值，允许通过并记录
 * 4. 如果请求数 >= 限制值，拒绝
 */
public class SlidingWindowRateLimiter {

    private final RedisTemplate<String, String> redisTemplate;

    /**
     * 滑动窗口限流
     * @param userId 用户ID
     * @param api 接口标识
     * @param limit 限制次数
     * @param windowSeconds 窗口大小（秒）
     * @return 是否允许通过
     */
    public boolean allowRequest(Long userId, String api, int limit, int windowSeconds) {
        String key = "rate_limit:" + userId + ":" + api;
        long now = System.currentTimeMillis();
        long windowStart = now - windowSeconds * 1000L;
        String memberId = now + "_" + UUID.randomUUID();

        // 使用Lua脚本保证原子性
        String luaScript =
            // 1. 移除窗口外的旧记录
            "redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1])\n" +
            // 2. 获取当前窗口内请求数
            "local count = redis.call('ZCARD', KEYS[1])\n" +
            // 3. 如果未超限，添加本次请求
            "if count < tonumber(ARGV[2]) then\n" +
            "    redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4])\n" +
            "    redis.call('EXPIRE', KEYS[1], ARGV[5])\n" +
            "    return 1\n" +
            "else\n" +
            "    return 0\n" +
            "end";

        DefaultRedisScript<Long> script = new DefaultRedisScript<>();
        script.setScriptText(luaScript);
        script.setResultType(Long.class);

        Long result = redisTemplate.execute(
            script,
            Collections.singletonList(key),
            String.valueOf(windowStart),
            String.valueOf(limit),
            String.valueOf(now),
            memberId,
            String.valueOf(windowSeconds)
        );

        return result != null && result == 1L;
    }
}
```

### 3.5 核心链路：Redis Lua预扣减库存

**这是整个秒杀系统最核心的一步。**

**问题**：高并发下直接操作MySQL减库存会导致大量行锁竞争，TPS骤降，响应时间飙升。

**方案**：将库存预热到Redis，用Lua脚本原子性扣减，将并发写从数据库层移到缓存层。

**为什么用Lua脚本**：Redis单线程执行Lua脚本，保证了"检查库存>0 → 扣减库存 → 记录用户"这三步的原子性，不会被其他请求打断。

```java
/**
 * 秒杀核心服务：Redis Lua预扣减
 * 
 * 完整链路：
 * 1. 检查是否已购买过（防重复购买）→ Redis Set
 * 2. 检查库存是否充足 → Redis String
 * 3. 扣减库存 → Redis DECR
 * 4. 记录已购买用户 → Redis Set
 * 5. 以上4步用Lua脚本保证原子性
 * 6. 扣减成功后发送MQ消息异步创建订单
 */
@Service
public class SeckillService {

    /**
     * Lua脚本：原子性检查+扣减+记录
     * KEYS[1] = 库存key: seckill:stock:{itemId}
     * KEYS[2] = 已购用户set: seckill:bought:{itemId}
     * ARGV[1] = userId
     * 
     * 返回值：
     *   0 = 成功
     *   1 = 库存不足
     *   2 = 重复购买
     */
    private static final String SECKILL_LUA_SCRIPT =
        "if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then\n" +
        "    return 2\n" +  // 已购买过
        "end\n" +
        "local stock = redis.call('GET', KEYS[1])\n" +
        "if not stock or tonumber(stock) <= 0 then\n" +
        "    return 1\n" +  // 库存不足
        "end\n" +
        "redis.call('DECR', KEYS[1])\n" +  // 扣减库存
        "redis.call('SADD', KEYS[2], ARGV[1])\n" +  // 记录已购用户
        "return 0\n";  // 成功

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Autowired
    private RocketMQTemplate mqTemplate;

    /**
     * 执行秒杀
     */
    public SeckillResult executeSeckill(Long activityId, Long itemId, Long userId) {
        // 1. 执行Lua脚本原子预扣减
        String stockKey = "seckill:stock:" + itemId;
        String boughtKey = "seckill:bought:" + itemId;

        DefaultRedisScript<Long> script = new DefaultRedisScript<>();
        script.setScriptText(SECKILL_LUA_SCRIPT);
        script.setResultType(Long.class);

        Long result = redisTemplate.execute(
            script,
            Arrays.asList(stockKey, boughtKey),
            String.valueOf(userId)
        );

        // 2. 处理结果
        if (result == null || result == 1L) {
            return SeckillResult.fail("手慢了，库存已抢完");
        }
        if (result == 2L) {
            return SeckillResult.fail("您已抢购过该商品");
        }

        // 3. 扣减成功，生成预订单号
        String orderNo = generateOrderNo(userId, itemId);

        // 4. 将"冷冻库存"信息存入Redis，等待消费者确认
        // 冷冻库存 = 已经从Redis扣减但尚未在DB落库的库存
        String frozenKey = "seckill:frozen:" + orderNo;
        Map<String, String> frozenInfo = new HashMap<>();
        frozenInfo.put("userId", String.valueOf(userId));
        frozenInfo.put("itemId", String.valueOf(itemId));
        frozenInfo.put("activityId", String.valueOf(activityId));
        frozenInfo.put("createTime", String.valueOf(System.currentTimeMillis()));
        redisTemplate.opsForHash().putAll(frozenKey, frozenInfo);
        redisTemplate.expire(frozenKey, 15, TimeUnit.MINUTES); // 15分钟过期

        // 5. 发送MQ消息，异步创建订单（泄洪削峰）
        SeckillMessage message = new SeckillMessage();
        message.setOrderNo(orderNo);
        message.setUserId(userId);
        message.setItemId(itemId);
        message.setActivityId(activityId);

        mqTemplate.asyncSend("seckill-order-topic", message, new SendCallback() {
            @Override
            public void onSuccess(SendResult sendResult) {
                log.info("秒杀消息发送成功, orderNo={}", orderNo);
            }

            @Override
            public void onException(Throwable e) {
                // MQ发送失败，需要恢复Redis库存
                log.error("秒杀消息发送失败, 恢复库存, orderNo={}", orderNo, e);
                rollbackRedisStock(itemId, userId, orderNo);
            }
        });

        // 6. 返回排队中，前端轮询订单状态
        return SeckillResult.success("排队中", orderNo);
    }

    /**
     * 恢复Redis库存（MQ发送失败时调用）
     */
    private void rollbackRedisStock(Long itemId, Long userId, String orderNo) {
        String stockKey = "seckill:stock:" + itemId;
        String boughtKey = "seckill:bought:" + itemId;
        String frozenKey = "seckill:frozen:" + orderNo;

        // 用Lua脚本保证原子性：恢复库存 + 移除已购记录 + 删除冷冻记录
        String rollbackScript =
            "redis.call('INCR', KEYS[1])\n" +
            "redis.call('SREM', KEYS[2], ARGV[1])\n" +
            "redis.call('DEL', KEYS[3])\n" +
            "return 1";

        DefaultRedisScript<Long> script = new DefaultRedisScript<>();
        script.setScriptText(rollbackScript);
        script.setResultType(Long.class);

        redisTemplate.execute(script,
            Arrays.asList(stockKey, boughtKey, frozenKey),
            String.valueOf(userId));
    }

    private String generateOrderNo(Long userId, Long itemId) {
        // 时间戳 + 用户ID后4位 + 商品ID后4位 + 随机数
        return System.currentTimeMillis() + ""
            + userId % 10000 + ""
            + itemId % 10000 + ""
            + (int)(Math.random() * 1000);
    }
}
```

### 3.6 MQ异步下单：消费端处理

**问题**：预扣减成功后，需要创建正式订单并扣减DB库存，这一步较慢，不能阻塞秒杀主流程。

**方案**：通过消息队列异步处理，消费者从MQ拉取消息创建订单。

```java
/**
 * 秒杀消息消费者：异步创建订单
 * 
 * 完整流程：
 * 1. 从MQ拉取秒杀消息
 * 2. 幂等校验（防止重复消费）
 * 3. 本地事务：创建订单 + 扣减DB库存
 * 4. 成功：删除冷冻库存，通知用户
 * 5. 失败：重试3次，仍失败则进入死信队列，恢复Redis库存
 */
@Component
@RocketMQMessageListener(
    topic = "seckill-order-topic",
    consumerGroup = "seckill-order-consumer-group",
    maxReconsumeTimes = 3  // 最多重试3次
)
public class SeckillOrderConsumer implements RocketMQListener<SeckillMessage> {

    @Autowired
    private OrderService orderService;

    @Autowired
    private InventoryService inventoryService;

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Override
    public void onMessage(SeckillMessage message) {
        String orderNo = message.getOrderNo();
        log.info("收到秒杀消息, 开始创建订单, orderNo={}", orderNo);

        try {
            // 1. 幂等校验：检查订单是否已创建
            if (orderService.orderExists(orderNo)) {
                log.info("订单已存在, 跳过, orderNo={}", orderNo);
                return;
            }

            // 2. 检查冷冻库存是否还存在（可能已超时被清理）
            String frozenKey = "seckill:frozen:" + orderNo;
            if (!redisTemplate.hasKey(frozenKey)) {
                log.warn("冷冻库存已过期, 无法创建订单, orderNo={}", orderNo);
                return; // 冷冻已过期，Redis库存已通过定时任务恢复
            }

            // 3. 本地事务：创建订单 + 扣减DB库存
            // 使用本地事务表模式保障一致性
            OrderDTO order = orderService.createSeckillOrder(message);

            // 4. 删除冷冻库存记录
            redisTemplate.delete(frozenKey);

            // 5. 发送通知（Push/站内信）
            notifyService.sendOrderSuccessNotification(message.getUserId(), orderNo);

            log.info("秒杀订单创建成功, orderNo={}", orderNo);

        } catch (Exception e) {
            log.error("秒杀订单创建失败, orderNo={}", orderNo, e);
            // 抛出异常，RocketMQ会自动重试
            throw new RuntimeException("订单创建失败", e);
        }
    }
}
```

### 3.7 本地事务表模式：保障最终一致性

**问题**：消费者创建订单时，"创建订单"和"扣减DB库存"必须在同一事务中，但如何保证消息可靠投递？

**方案**：使用本地事务表模式（也称为"事务消息"模式）。

```java
/**
 * 订单服务：本地事务表模式
 * 
 * 核心思路：
 * 1. 在同一个本地事务中：写入订单 + 写入本地事务表（记录已处理的消息）
 * 2. 如果事务成功，订单和消息记录一起提交
 * 3. 如果事务失败，一起回滚
 * 4. 幂等性：消费前检查本地事务表，已处理则跳过
 */
@Service
public class OrderServiceImpl implements OrderService {

    @Autowired
    private OrderMapper orderMapper;

    @Autowired
    private InventoryMapper inventoryMapper;

    @Autowired
    private LocalTransactionMapper localTransactionMapper;

    /**
     * 创建秒杀订单（本地事务）
     */
    @Transactional(rollbackFor = Exception.class)
    public OrderDTO createSeckillOrder(SeckillMessage message) {
        String orderNo = message.getOrderNo();

        // 1. 幂等检查：查询本地事务表
        LocalTransactionRecord existRecord = localTransactionMapper
            .selectByBizId(orderNo);
        if (existRecord != null) {
            // 已处理过，直接返回
            return orderMapper.selectByOrderNo(orderNo);
        }

        // 2. 扣减DB库存（使用CASE WHEN防超卖，作为最后一道防线）
        int affected = inventoryMapper.deductStock(
            message.getItemId(), 1);
        if (affected == 0) {
            throw new RuntimeException("DB库存不足, itemId=" + message.getItemId());
        }

        // 3. 创建订单
        Order order = new Order();
        order.setOrderNo(orderNo);
        order.setUserId(message.getUserId());
        order.setItemId(message.getItemId());
        order.setStatus(OrderStatus.CREATED);
        order.setCreateTime(new Date());
        orderMapper.insert(order);

        // 4. 写入本地事务表（与订单在同一事务中提交）
        LocalTransactionRecord record = new LocalTransactionRecord();
        record.setBizId(orderNo);
        record.setBizType("SECKILL_ORDER");
        record.setStatus("PROCESSED");
        record.setCreateTime(new Date());
        localTransactionMapper.insert(record);

        return convertToDTO(order);
    }
}
```

DB层防超卖的SQL（最后一道防线）：

```sql
-- 使用CASE WHEN确保库存不会减为负数
UPDATE item_inventory 
SET stock = CASE WHEN stock >= 1 THEN stock - 1 ELSE stock END
WHERE item_id = #{itemId} AND stock > 0;
```

### 3.8 超时未支付：延时任务取消订单

**问题**：用户抢到商品后可能不付款，库存被占用。

**方案**：创建订单时同时创建一个15分钟的延时任务，超时未支付则取消订单、恢复库存。

```java
/**
 * 延时任务：订单超时自动取消
 * 
 * 实现方式：Redis ZSet延时队列
 * - key: delay_queue:order_timeout
 * - score: 到期时间戳
 * - member: orderNo
 * 
 * 后台定时任务每秒扫描到期任务
 */
@Service
public class OrderTimeoutService {

    private static final String DELAY_QUEUE_KEY = "delay_queue:order_timeout";
    private static final int TIMEOUT_MINUTES = 15;

    /**
     * 添加超时取消任务
     */
    public void addTimeoutTask(String orderNo) {
        long executeTime = System.currentTimeMillis() + TIMEOUT_MINUTES * 60 * 1000L;
        redisTemplate.opsForZSet().add(DELAY_QUEUE_KEY, orderNo, executeTime);
    }

    /**
     * 定时扫描到期任务（每秒执行）
     */
    @Scheduled(fixedRate = 1000)
    public void scanTimeoutOrders() {
        long now = System.currentTimeMillis();

        // 1. 获取所有已到期的订单号
        Set<String> timeoutOrders = redisTemplate.opsForZSet()
            .rangeByScore(DELAY_QUEUE_KEY, 0, now);

        if (timeoutOrders == null || timeoutOrders.isEmpty()) {
            return;
        }

        for (String orderNo : timeoutOrders) {
            try {
                // 2. 查询订单状态
                Order order = orderMapper.selectByOrderNo(orderNo);

                if (order != null && order.getStatus() == OrderStatus.CREATED) {
                    // 3. 未支付，取消订单
                    cancelOrderAndRestoreStock(order);
                }

                // 4. 从延时队列移除
                redisTemplate.opsForZSet().remove(DELAY_QUEUE_KEY, orderNo);

            } catch (Exception e) {
                log.error("处理超时订单失败, orderNo={}", orderNo, e);
            }
        }
    }

    /**
     * 取消订单并恢复库存
     */
    @Transactional(rollbackFor = Exception.class)
    public void cancelOrderAndRestoreStock(Order order) {
        // 1. 更新订单状态为已取消
        orderMapper.updateStatus(order.getOrderNo(), OrderStatus.CANCELLED);

        // 2. 恢复DB库存
        inventoryMapper.restoreStock(order.getItemId(), 1);

        // 3. 恢复Redis库存 + 移除已购记录
        String stockKey = "seckill:stock:" + order.getItemId();
        String boughtKey = "seckill:bought:" + order.getItemId();
        redisTemplate.opsForValue().increment(stockKey);
        redisTemplate.opsForSet().remove(boughtKey, String.valueOf(order.getUserId()));

        log.info("订单超时取消成功, orderNo={}", order.getOrderNo());
    }
}
```

### 3.9 定时任务对账：Redis与DB库存一致性

**问题**：Redis预扣减和DB实际扣减之间存在时间差，可能出现不一致（如MQ消息丢失、消费者宕机）。

**方案**：定时任务每分钟对账，发现不一致则补偿。

```java
/**
 * 库存对账定时任务
 * 
 * 对账逻辑：
 * Redis剩余库存 + 冷冻库存（未落库的预扣减） = DB剩余库存
 * 如果不等，说明有数据丢失，需要补偿
 */
@Component
public class InventoryReconcileTask {

    /**
     * 每60秒执行一次对账
     */
    @Scheduled(fixedRate = 60000)
    public void reconcile() {
        // 1. 获取所有秒杀商品
        List<Long> itemIds = seckillActivityMapper.getActiveItemIds();

        for (Long itemId : itemIds) {
            try {
                reconcileItem(itemId);
            } catch (Exception e) {
                log.error("对账失败, itemId={}", itemId, e);
            }
        }
    }

    private void reconcileItem(Long itemId) {
        // 2. 获取Redis中的剩余库存
        String stockKey = "seckill:stock:" + itemId;
        String redisStockStr = redisTemplate.opsForValue().get(stockKey);
        int redisStock = redisStockStr != null ? Integer.parseInt(redisStockStr) : 0;

        // 3. 获取冷冻库存数量（已从Redis扣减但未在DB落库的）
        // 扫描所有冷冻记录，统计该商品的数量
        int frozenCount = countFrozenStock(itemId);

        // 4. 获取DB中的剩余库存
        int dbStock = inventoryMapper.getStock(itemId);

        // 5. 获取已售数量（DB中已创建的秒杀订单数）
        int soldCount = orderMapper.countSeckillOrders(itemId);

        // 6. 对账公式：redisStock + frozenCount + soldCount == 初始库存
        int initialStock = seckillActivityMapper.getInitialStock(itemId);
        int expected = redisStock + frozenCount + soldCount;

        if (expected != initialStock) {
            log.warn("库存不一致! itemId={}, Redis={}, 冷冻={}, 已售={}, 初始={}, 预期={}",
                itemId, redisStock, frozenCount, soldCount, initialStock, expected);

            // 7. 自动补偿：以DB为准，重新计算Redis库存
            int correctRedisStock = initialStock - soldCount - frozenCount;
            if (correctRedisStock < 0) correctRedisStock = 0;
            redisTemplate.opsForValue().set(stockKey, String.valueOf(correctRedisStock));

            // 8. 发送告警
            alertService.sendInventoryInconsistencyAlert(itemId, expected, initialStock);
        }
    }

    /**
     * 统计冷冻库存数量
     */
    private int countFrozenStock(Long itemId) {
        // 扫描seckill:frozen:*的所有key，统计对应itemId的数量
        Set<String> frozenKeys = redisTemplate.keys("seckill:frozen:*");
        if (frozenKeys == null) return 0;

        int count = 0;
        for (String key : frozenKeys) {
            Object storedItemId = redisTemplate.opsForHash().get(key, "itemId");
            if (storedItemId != null && storedItemId.equals(String.valueOf(itemId))) {
                count++;
            }
        }
        return count;
    }
}
```

### 3.10 死信队列处理

**问题**：消费者重试3次仍然失败，消息进入死信队列，此时Redis库存已被扣减但DB订单未创建。

**方案**：监听死信队列，恢复Redis库存。

```java
/**
 * 死信队列消费者：处理彻底失败的消息
 */
@Component
@RocketMQMessageListener(
    topic = "%DLQ%seckill-order-consumer-group",
    consumerGroup = "seckill-dlq-consumer-group"
)
public class SeckillDLQConsumer implements RocketMQListener<SeckillMessage> {

    @Override
    public void onMessage(SeckillMessage message) {
        log.error("秒杀消息进入死信队列, 恢复库存, orderNo={}", message.getOrderNo());

        // 1. 恢复Redis库存
        String stockKey = "seckill:stock:" + message.getItemId();
        String boughtKey = "seckill:bought:" + message.getItemId();
        String frozenKey = "seckill:frozen:" + message.getOrderNo();

        // 原子性恢复：库存+1，移除已购记录，删除冷冻记录
        String restoreScript =
            "redis.call('INCR', KEYS[1])\n" +
            "redis.call('SREM', KEYS[2], ARGV[1])\n" +
            "redis.call('DEL', KEYS[3])\n" +
            "return 1";

        redisTemplate.execute(new DefaultRedisScript<>(restoreScript, Long.class),
            Arrays.asList(stockKey, boughtKey, frozenKey),
            String.valueOf(message.getUserId()));

        // 2. 告警通知运维
        alertService.sendSeckillFailureAlert(message);

        // 3. 记录失败日志，供后续排查
        failureLogService.record(message, "DLQ_PROCESSING");
    }
}
```

## 四、异常处理与容错机制

### 4.1 Redis宕机容灾

```java
/**
 * Redis宕机时的降级策略
 * 
 * 降级链路：
 * 1. 尝试从备用Redis集群读取
 * 2. 备用也挂了，直接走DB扣减（性能急剧下降，但保证不超卖）
 * 3. DB也扛不住，返回"系统繁忙"拒绝请求
 */
@Service
public class SeckillFallbackService {

    public SeckillResult executeSeckillWithFallback(Long itemId, Long userId) {
        try {
            // 1. 正常走Redis Lua扣减
            return seckillService.executeSeckill(itemId, userId);
        } catch (RedisConnectionFailureException e) {
            log.warn("Redis不可用，降级到DB扣减, itemId={}", itemId);

            // 2. 降级：直接DB扣减（使用CASE WHEN防超卖）
            try {
                return executeSeckillInDB(itemId, userId);
            } catch (Exception dbEx) {
                log.error("DB扣减也失败", dbEx);
                return SeckillResult.fail("系统繁忙，请稍后重试");
            }
        }
    }

    /**
     * DB层秒杀（降级方案）
     * 使用SELECT FOR UPDATE行锁 + CASE WHEN保证不超卖
     * 性能远低于Redis方案，仅作为兜底
     */
    @Transactional(rollbackFor = Exception.class)
    public SeckillResult executeSeckillInDB(Long itemId, Long userId) {
        // 1. 检查是否已购买
        if (orderMapper.countUserOrders(userId, itemId) > 0) {
            return SeckillResult.fail("您已抢购过该商品");
        }

        // 2. CASE WHEN扣减库存
        int affected = inventoryMapper.deductStock(itemId, 1);
        if (affected == 0) {
            return SeckillResult.fail("手慢了，库存已抢完");
        }

        // 3. 创建订单
        Order order = new Order();
        order.setUserId(userId);
        order.setItemId(itemId);
        order.setStatus(OrderStatus.CREATED);
        orderMapper.insert(order);

        return SeckillResult.success("抢购成功", order.getOrderNo());
    }
}
```

### 4.2 MQ消息丢失补偿

消息从生产到消费的每个环节都可能丢失，需要多重保障：

| 环节 | 风险 | 保障措施 |
|------|------|---------|
| 生产者→MQ | 网络中断 | 发送失败回调中恢复Redis库存 |
| MQ存储 | Broker宕机 | 开启同步刷盘+主从同步 |
| MQ→消费者 | 消费者宕机 | 消费失败重试3次 |
| 重试3次失败 | 消息进死信队列 | 死信消费者恢复Redis库存 |
| 全部失败 | 库存永久不一致 | 定时对账任务补偿 |

### 4.3 库存预热失败处理

```java
/**
 * 库存预热：活动开始前将DB库存同步到Redis
 * 
 * 容错策略：
 * 1. 预热失败时重试3次
 * 2. 仍失败则告警，人工介入
 * 3. 活动开始前10分钟自动检查预热状态
 */
@Component
public class StockPreheatTask {

    @Scheduled(cron = "0 */5 * * * ?")
    public void preheatStock() {
        List<SeckillActivity> activities = activityMapper
            .findActivitiesStartingSoon(10); // 10分钟内开始的活动

        for (SeckillActivity activity : activities) {
            preheatWithRetry(activity, 3);
        }
    }

    private void preheatWithRetry(SeckillActivity activity, int maxRetry) {
        for (int i = 0; i < maxRetry; i++) {
            try {
                String stockKey = "seckill:stock:" + activity.getItemId();
                redisTemplate.opsForValue().set(
                    stockKey, String.valueOf(activity.getStock()));
                log.info("库存预热成功, itemId={}, stock={}",
                    activity.getItemId(), activity.getStock());
                return;
            } catch (Exception e) {
                log.warn("库存预热失败, retry={}/{}, itemId={}",
                    i + 1, maxRetry, activity.getItemId(), e);
                if (i == maxRetry - 1) {
                    alertService.sendPreheatFailureAlert(activity);
                }
            }
        }
    }
}
```

## 五、性能优化

### 5.1 热点库存分桶

**问题**：单个热点商品的库存扣减集中在Redis同一个key上，虽然Redis单线程不会冲突，但单key的QPS上限约为10万。

**方案**：将库存分到多个桶中（如10个桶），请求随机路由到不同桶。

```java
/**
 * 库存分桶策略
 * 
 * 将1000件库存分到10个桶，每桶100件
 * key: seckill:stock:{itemId}:bucket:0 ~ seckill:stock:{itemId}:bucket:9
 * 
 * 用户请求时随机选择一个桶扣减
 * 桶库存不足时，尝试从其他桶"借调"
 */
@Service
public class BucketStockService {

    private static final int BUCKET_COUNT = 10;

    /**
     * 分桶扣减库存
     */
    public boolean deductStock(Long itemId, Long userId) {
        // 1. 随机选择一个桶
        int bucketIndex = ThreadLocalRandom.current().nextInt(BUCKET_COUNT);
        String bucketKey = "seckill:stock:" + itemId + ":bucket:" + bucketIndex;

        // 2. 尝试在当前桶扣减
        Long result = redisTemplate.opsForValue().decrement(bucketKey);
        if (result != null && result >= 0) {
            return true; // 扣减成功
        }

        // 3. 当前桶不足，尝试其他桶（最多尝试BUCKET_COUNT次）
        for (int i = 1; i < BUCKET_COUNT; i++) {
            int nextBucket = (bucketIndex + i) % BUCKET_COUNT;
            String nextKey = "seckill:stock:" + itemId + ":bucket:" + nextBucket;
            result = redisTemplate.opsForValue().decrement(nextKey);
            if (result != null && result >= 0) {
                return true;
            }
        }

        return false; // 所有桶都空了
    }

    /**
     * 库存预热：将总库存均分到各桶
     */
    public void preheatBucketStock(Long itemId, int totalStock) {
        int perBucket = totalStock / BUCKET_COUNT;
        int remainder = totalStock % BUCKET_COUNT;

        for (int i = 0; i < BUCKET_COUNT; i++) {
            String bucketKey = "seckill:stock:" + itemId + ":bucket:" + i;
            int stock = perBucket + (i < remainder ? 1 : 0);
            redisTemplate.opsForValue().set(bucketKey, String.valueOf(stock));
        }
    }
}
```

### 5.2 本地缓存预热

```java
/**
 * 本地缓存：减少Redis访问

@Service

            ItemDTO item = itemMapper.selectById(key);
            if (item != null) {
                redisTemplate.opsForValue().set("item:" + key,
                    JSON.toJSONString(item), 30, TimeUnit.MINUTES);
            }
            return item;
        });
    }
}
```

## 六、最佳实践与总结

### 6.1 秒杀系统设计原则

1. **数据动静分离**：静态数据走CDN，动态数据走接口，减少回源
2. **分层过滤**：从CDN到DB，每一层都削减无效流量，像漏斗一样
3. **隔离保护**：秒杀流量必须与非秒杀业务物理或逻辑隔离
4. **最终一致**：Redis预扣减 + MQ异步下单 + 定时对账，追求最终一致性而非强一致性
5. **兜底防线**：每一层都有兜底方案，Redis挂了走DB，MQ挂了走对账

### 6.2 核心设计决策回顾

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 减库存时机 | 下单减库存 | 秒杀场景不付款概率低，逻辑简单 |
| 库存扣减位置 | Redis Lua脚本 | 原子性+高性能，单key QPS可达10万 |
| 订单创建方式 | MQ异步创建 | 泄洪削峰，保护DB |
| 一致性保障 | 本地事务表+定时对账 | 最终一致，避免分布式事务性能问题 |
| 超时处理 | Redis ZSet延时队列 | 简单可靠，无需引入额外组件 |
| 防超卖 | 三道防线 | Lua脚本 + CASE WHEN + 对账补偿 |

### 6.3 容易踩的坑

1. **忘记防重复购买**：用户在极短时间内发两次请求，Lua脚本中的SISMEMBER检查是关键
2. **MQ消息发送失败不恢复库存**：发送失败回调中必须恢复Redis库存
3. **消费者不做幂等**：MQ可能重复投递消息，不做幂等会创建重复订单
4. **对账公式错误**：正确公式是 Redis库存 + 冷冻库存 + 已售数量 = 初始库存
5. **延时任务漏处理**：服务重启时正在延时的任务可能丢失，需要持久化或用MQ延时消息
6. **热点库存单key瓶颈**：单key QPS上限约10万，超高并发需要分桶
7. **忘记DB层兜底**：即使Redis做了扣减，DB层也要用CASE WHEN做最后防线

### 6.4 完整链路总结

```
用户点击"立即抢购"
  → 前端弹出验证码（错峰）
    → Nginx令牌桶限流（削峰）
      → 网关滑动窗口限流（用户维度）
        → Redis Lua脚本原子预扣减（核心）
          → 扣减成功，记录冷冻库存
            → 发送MQ消息（泄洪）
              → 消费者异步创建订单+扣减DB库存
                → 成功：删除冷冻，通知用户
                → 失败：重试3次→死信队列→恢复Redis库存
            → 15分钟未支付→延时任务取消订单→恢复库存
          → 扣减失败：返回"售罄"
        → 定时任务每分钟对账（兜底）
```

这就是秒杀系统的完整架构设计和核心链路实现，从流量入口到数据落库，每一步都有明确的算法、设计模式和容错策略。

## 七、全链路实战案例详解

> 前面六章讲清楚了每一层的设计原理与关键组件。本章从"一次真实请求"的视角，把所有组件串成一条完整的链路，逐步跟踪一个请求从进入系统到最终响应的全过程。每个案例都从入口开始，到出口结束，中间每一步的代码、异常分支、日志、幂等都不省略。目标是：面试官问到链路上的任何一个环节，都能立刻答出"这一步做了什么、为什么这么做、异常了怎么办"。

### 案例一：用户秒杀下单全链路

**场景**：秒杀活动 `activityId=8001` 正在进行，商品 `itemId=2001`（iPhone，库存 1000 件），用户 `userId=100234` 在 App 上点击"立即抢购"。我们跟踪这一次请求，从按钮点击到前端拿到"抢购成功"结果的完整过程。

#### 链路时序总览

```
[App 点击"立即抢购"]
  │  携带 activityId / itemId / 动态sign / 验证码captchaId+answer / Token
  ▼
[① Nginx 限流层]  令牌桶 1000r/s，超量直接 503
  ▼
[② 网关层]  鉴权(Token→userId) + 防重复提交(Redis SETNX) + 用户维度滑动窗口限流
  ▼
[③ Controller]  参数校验 + 动态URL签名校验 + 验证码校验
  ▼
[④ 资格校验 Service]  活动是否开始/结束 + 白名单 + 单用户限购
  ▼
[⑤ Redis Lua 原子预扣减]  防重复购买 + 库存判断 + DECR + 记录已购
  ▼
[⑥ 写冷冻库存 + 发送 MQ(事务消息/异步确认)]
  ▼  同步返回 "排队中" + orderNo
[⑦ 前端轮询订单结果接口]  CREATED→成功 / null→排队中 / FAILED→失败
  ▲
[⑧ MQ 消费端(异步)]  幂等校验 → 本地事务(建单+扣DB库存) → 删冷冻 → 写结果缓存 → 通知
       │ 失败重试3次 → 死信队列 → 恢复 Redis 库存 → 写失败结果缓存
```

#### 步骤 ① Nginx 限流层

用户请求首先命中 Nginx。这一层做两件事：**IP 黑名单拦截**（风控旁路推送的黑名单）和**令牌桶接入限流**。

```nginx
# /etc/nginx/conf.d/seckill.conf

# 1. 令牌桶限流：全局每秒放行 1000 个请求，突发缓冲 2000
limit_req_zone $binary_remote_addr zone=seckill_ip:20m rate=1000r/s;

# 2. 连接数限制：单 IP 最多 20 个并发连接（防单机脚本刷）
limit_conn_zone $binary_remote_addr zone=seckill_conn:10m;

# 3. 黑名单（由风控系统通过 reload 或 ngx_lua 动态下发）
geo $seckill_blacklist {
    default 0;
    include /etc/nginx/conf.d/seckill_blacklist.conf;  # 内含 "1.2.3.4 1;" 形式
}

server {
    location /seckill/order {
        # 黑名单直接拒绝
        if ($seckill_blacklist) {
            return 403 '{"code":403,"msg":"请求被拒绝"}';
        }
        # 令牌桶：nodelay 表示超出 burst 立即返回 503，不排队
        limit_req zone=seckill_ip burst=2000 nodelay;
        limit_conn seckill_conn 20;

        # 限流触发时返回自定义 JSON（默认 503 前端不好处理）
        limit_req_status 503;
        limit_conn_status 503;
        error_page 503 = @seckill_busy;

        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_pass http://seckill_gateway;
    }

    location @seckill_busy {
        default_type application/json;
        return 200 '{"code":503,"msg":"活动太火爆，请稍后再试","success":false}';
    }
}
```

**异常分支**：
- 命中黑名单 → 直接 403，不消耗后端资源。
- 超出令牌桶 → 走 `@seckill_busy`，返回业务可解析的 JSON（`code=503`），前端提示"活动太火爆"。
- 这一层削掉约 70% 的超量请求，后端网关只需承接约 1000 QPS。

#### 步骤 ② 网关层：鉴权 + 防重复提交 + 用户维度限流

请求穿过 Nginx 到达网关。网关是**第一次能识别到"用户身份"**的地方（Nginx 只知道 IP）。这里依次做三件事。

```java
/**
 * 秒杀网关过滤器（Spring Cloud Gateway GlobalFilter）
 * 执行顺序：鉴权 → 防重复提交 → 用户维度限流
 * 任一步失败都短路返回，不再往下传递。
 */
@Component
@Slf4j
public class SeckillGatewayFilter implements GlobalFilter, Ordered {

    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private TokenService tokenService;
    @Autowired
    private SlidingWindowRateLimiter rateLimiter;

    /** 防重提交的 Lua：SET NX PX，成功返回1，已存在返回0 */
    private static final String DEDUP_LUA =
        "if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then\n" +
        "    return 1\n" +
        "else\n" +
        "    return 0\n" +
        "end";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getPath().value();

        // 只拦截秒杀下单接口
        if (!path.startsWith("/seckill/order")) {
            return chain.filter(exchange);
        }

        // ---------- 2.1 鉴权：Token → userId ----------
        String token = request.getHeaders().getFirst("Authorization");
        Long userId;
        try {
            userId = tokenService.parseUserId(token);   // 校验签名+过期
        } catch (Exception e) {
            log.warn("秒杀鉴权失败, path={}, err={}", path, e.getMessage());
            return writeJson(exchange, HttpStatus.UNAUTHORIZED,
                    "{\"code\":401,\"msg\":\"登录已失效\",\"success\":false}");
        }
        // 把 userId 透传给下游，避免下游再解一次 Token
        ServerHttpRequest mutated = request.mutate()
                .header("X-User-Id", String.valueOf(userId)).build();

        // ---------- 2.2 防重复提交：同一用户同一商品 3 秒内只放一次 ----------
        String itemId = request.getQueryParams().getFirst("itemId");
        String dedupKey = "seckill:dedup:" + userId + ":" + itemId;
        Long dedup = redisTemplate.execute(
                new DefaultRedisScript<>(DEDUP_LUA, Long.class),
                Collections.singletonList(dedupKey),
                "1", "3000");   // value=1, 过期 3000ms
        if (dedup == null || dedup == 0L) {
            log.info("重复提交被拦截, userId={}, itemId={}", userId, itemId);
            return writeJson(exchange, HttpStatus.OK,
                    "{\"code\":429,\"msg\":\"请勿重复提交\",\"success\":false}");
        }

        // ---------- 2.3 用户维度滑动窗口限流：10 秒内最多 5 次 ----------
        if (!rateLimiter.allowRequest(userId, "seckill_order", 5, 10)) {
            log.info("用户限流触发, userId={}", userId);
            return writeJson(exchange, HttpStatus.OK,
                    "{\"code\":429,\"msg\":\"操作过于频繁\",\"success\":false}");
        }

        return chain.filter(exchange.mutate().request(mutated).build());
    }

    private Mono<Void> writeJson(ServerWebExchange exchange, HttpStatus status, String body) {
        ServerHttpResponse resp = exchange.getResponse();
        resp.setStatusCode(status);
        resp.getHeaders().add("Content-Type", "application/json;charset=UTF-8");
        DataBuffer buffer = resp.bufferFactory().wrap(body.getBytes(StandardCharsets.UTF_8));
        return resp.writeWith(Mono.just(buffer));
    }

    @Override
    public int getOrder() { return -100; }  // 尽量靠前执行
}
```

**关键点与异常分支**：

| 子步骤 | 成功 | 失败/异常 | 处理 |
|--------|------|-----------|------|
| 鉴权 | 解析出 userId，透传 `X-User-Id` | Token 无效/过期 | 返回 401，前端跳登录 |
| 防重复提交 | SETNX 成功，key 3 秒过期 | key 已存在（3 秒内重复点） | 返回 429"请勿重复提交" |
| 用户限流 | 滑动窗口未超限 | 10 秒内超过 5 次 | 返回 429"操作过于频繁" |

> 注意：防重复提交用的是**短过期 SETNX**（3 秒），它防的是"用户手抖/网络重发"。真正的"一个用户只能买一件"由后面步骤 ⑤ 的 Lua `SISMEMBER` 保证，两者职责不同，不能互相替代。

#### 步骤 ③ Controller：参数校验 + 签名校验 + 验证码校验

请求进入秒杀服务的 Controller。这里做**入参合法性**的最后把关，任何非法请求在这里被挡下，绝不进入核心扣减逻辑。

```java
@RestController
@RequestMapping("/seckill")
@Slf4j
public class SeckillController {

    @Autowired private SeckillUrlGenerator urlGenerator;
    @Autowired private SeckillCaptchaService captchaService;
    @Autowired private SeckillQualifyService qualifyService;
    @Autowired private SeckillService seckillService;

    /**
     * 秒杀下单入口
     * 动态 URL 形如 /seckill/order?activityId=&itemId=&ts=&sign=&captchaId=&answer=
     * userId 由网关通过 X-User-Id 透传，不信任前端传的 userId（防越权）
     */
    @PostMapping("/order")
    public SeckillResult order(@RequestParam Long activityId,
                               @RequestParam Long itemId,
                               @RequestParam long ts,
                               @RequestParam String sign,
                               @RequestParam String captchaId,
                               @RequestParam String answer,
                               @RequestHeader("X-User-Id") Long userId) {
        // ---------- 3.1 参数基础校验 ----------
        if (activityId == null || activityId <= 0
                || itemId == null || itemId <= 0
                || userId == null || userId <= 0) {
            return SeckillResult.fail(400, "参数非法");
        }

        // ---------- 3.2 动态 URL 签名校验（防黄牛提前构造链接）----------
        if (!urlGenerator.validateSeckillUrl(activityId, itemId, ts, sign)) {
            log.warn("秒杀签名校验失败, userId={}, activityId={}, itemId={}",
                    userId, activityId, itemId);
            return SeckillResult.fail(403, "非法请求");
        }

        // ---------- 3.3 验证码校验（错峰，且防机器脚本）----------
        if (!captchaService.validateCaptcha(captchaId, answer)) {
            return SeckillResult.fail(403, "验证码错误或已过期");
        }

        // ---------- 3.4 资格校验（见步骤 ④）----------
        QualifyResult qualify = qualifyService.check(activityId, itemId, userId);
        if (!qualify.isPass()) {
            return SeckillResult.fail(qualify.getCode(), qualify.getMsg());
        }

        // ---------- 3.5 进入核心扣减（见步骤 ⑤⑥）----------
        try {
            return seckillService.executeSeckill(activityId, itemId, userId);
        } catch (Exception e) {
            // 兜底：任何未预期异常都不能把堆栈暴露给用户
            log.error("秒杀执行异常, userId={}, itemId={}", userId, itemId, e);
            return SeckillResult.fail(500, "系统繁忙，请稍后重试");
        }
    }

    /**
     * 订单结果轮询接口（步骤 ⑦，前端每 500ms~1s 调一次）
     */
    @GetMapping("/order/result")
    public SeckillResult queryResult(@RequestParam String orderNo,
                                     @RequestHeader("X-User-Id") Long userId) {
        return seckillService.queryOrderResult(orderNo, userId);
    }
}
```

**为什么 userId 从 Header 取而不是前端传**：前端传的 userId 可被篡改（越权替别人下单）。网关已用 Token 解析出可信 userId 并透传，Controller 只信任 `X-User-Id`。

#### 步骤 ④ 资格校验 Service

在扣库存之前，必须确认这个用户"有资格"参与。三项检查缺一不可，且检查顺序按"成本从低到高"排列（先查缓存里的活动状态，再查白名单，最后查限购）。

```java
@Service
@Slf4j
public class SeckillQualifyService {

    @Autowired private StringRedisTemplate redisTemplate;
    @Autowired private LocalCacheService localCacheService;

    /**
     * 资格校验：活动状态 + 白名单 + 单用户限购
     */
    public QualifyResult check(Long activityId, Long itemId, Long userId) {
        // ---------- 4.1 活动时间窗口校验 ----------
        // 活动信息预热在 Redis Hash：seckill:activity:{activityId}
        Map<Object, Object> act = redisTemplate.opsForHash()
                .entries("seckill:activity:" + activityId);
        if (act == null || act.isEmpty()) {
            return QualifyResult.fail(404, "活动不存在");
        }
        long now = System.currentTimeMillis();
        long startTime = Long.parseLong((String) act.get("startTime"));
        long endTime = Long.parseLong((String) act.get("endTime"));
        String status = (String) act.get("status");   // NOT_START/RUNNING/ENDED

        if ("ENDED".equals(status) || now > endTime) {
            return QualifyResult.fail(4001, "活动已结束");
        }
        if ("NOT_START".equals(status) || now < startTime) {
            return QualifyResult.fail(4002, "活动尚未开始");
        }

        // ---------- 4.2 白名单校验（仅限白名单活动才检查）----------
        boolean whitelistOnly = "1".equals(act.get("whitelistOnly"));
        if (whitelistOnly) {
            Boolean inWhite = redisTemplate.opsForSet()
                    .isMember("seckill:whitelist:" + activityId, String.valueOf(userId));
            if (!Boolean.TRUE.equals(inWhite)) {
                return QualifyResult.fail(4003, "您不在本次活动的参与名单内");
            }
        }

        // ---------- 4.3 单用户限购预检（软校验，硬约束仍在 Lua）----------
        // 这里是"快速失败"，减少无谓的 Lua 调用；真正的原子限购在步骤 ⑤
        Boolean bought = redisTemplate.opsForSet()
                .isMember("seckill:bought:" + itemId, String.valueOf(userId));
        if (Boolean.TRUE.equals(bought)) {
            return QualifyResult.fail(4004, "您已抢购过该商品");
        }

        return QualifyResult.pass();
    }
}
```

> **软校验 vs 硬约束**：4.3 的 `isMember` 是"软校验"——它能挡掉绝大多数重复请求，降低核心 Lua 的压力，但存在并发窗口（两个请求同时都读到"未购买"）。真正保证"只买一件"的硬约束是步骤 ⑤ Lua 脚本里的 `SISMEMBER`，它和扣减在同一次单线程执行中，绝无并发窗口。这是"分层过滤"思想在资格校验上的体现。

#### 步骤 ⑤⑥ 核心扣减 + 发送 MQ

这两步复用第 3.5 节的 `SeckillService.executeSeckill`，这里补充**订单结果缓存**和**MQ 可靠投递**两个在全链路中不可省略的细节，让链路真正闭环。

```java
@Service
@Slf4j
public class SeckillService {

    // ... 复用 3.5 节的 SECKILL_LUA_SCRIPT ...

    @Autowired private StringRedisTemplate redisTemplate;
    @Autowired private RocketMQTemplate mqTemplate;

    /** 订单结果缓存 key：供步骤 ⑦ 轮询 */
    private String resultKey(String orderNo) { return "seckill:result:" + orderNo; }

    public SeckillResult executeSeckill(Long activityId, Long itemId, Long userId) {
        String stockKey = "seckill:stock:" + itemId;
        String boughtKey = "seckill:bought:" + itemId;

        // ⑤ Lua 原子预扣减：0成功 1库存不足 2重复购买
        Long r = redisTemplate.execute(
                new DefaultRedisScript<>(SECKILL_LUA_SCRIPT, Long.class),
                Arrays.asList(stockKey, boughtKey), String.valueOf(userId));
        if (r == null || r == 1L) return SeckillResult.fail(4005, "手慢了，库存已抢完");
        if (r == 2L) return SeckillResult.fail(4004, "您已抢购过该商品");

        // 生成预订单号
        String orderNo = generateOrderNo(userId, itemId);

        // ⑥.1 写冷冻库存（15 分钟）——已扣 Redis 但未落库的凭证
        String frozenKey = "seckill:frozen:" + orderNo;
        Map<String, String> frozen = new HashMap<>();
        frozen.put("userId", String.valueOf(userId));
        frozen.put("itemId", String.valueOf(itemId));
        frozen.put("activityId", String.valueOf(activityId));
        frozen.put("createTime", String.valueOf(System.currentTimeMillis()));
        redisTemplate.opsForHash().putAll(frozenKey, frozen);
        redisTemplate.expire(frozenKey, 15, TimeUnit.MINUTES);

        // ⑥.2 写"排队中"结果缓存，供前端轮询（30 分钟过期）
        redisTemplate.opsForValue().set(resultKey(orderNo),
                "{\"status\":\"QUEUING\"}", 30, TimeUnit.MINUTES);

        // ⑥.3 发送 MQ（异步确认；失败回调里回滚 Redis）
        SeckillMessage msg = new SeckillMessage(orderNo, userId, itemId, activityId);
        mqTemplate.asyncSend("seckill-order-topic", msg, new SendCallback() {
            @Override public void onSuccess(SendResult sr) {
                log.info("秒杀消息投递成功, orderNo={}, msgId={}", orderNo, sr.getMsgId());
            }
            @Override public void onException(Throwable e) {
                log.error("秒杀消息投递失败, 回滚 Redis, orderNo={}", orderNo, e);
                rollbackRedisStock(itemId, userId, orderNo);   // 复用 3.5 节
                // 结果缓存标记失败，前端轮询到后提示重试
                redisTemplate.opsForValue().set(resultKey(orderNo),
                        "{\"status\":\"FAILED\",\"msg\":\"网络异常，请重试\"}",
                        30, TimeUnit.MINUTES);
            }
        });

        // 同步返回排队中 + orderNo，前端据此轮询
        return SeckillResult.queuing(orderNo);
    }

    /**
     * 步骤 ⑦：订单结果轮询
     */
    public SeckillResult queryOrderResult(String orderNo, Long userId) {
        String json = redisTemplate.opsForValue().get(resultKey(orderNo));
        if (json == null) {
            // 结果缓存已过期，兜底查 DB
            Order order = orderMapper.selectByOrderNo(orderNo);
            if (order != null && Objects.equals(order.getUserId(), userId)) {
                return SeckillResult.success(4200, "抢购成功", orderNo);
            }
            return SeckillResult.fail(4404, "订单不存在");
        }
        SeckillResultCache c = JSON.parseObject(json, SeckillResultCache.class);
        switch (c.getStatus()) {
            case "SUCCESS":  return SeckillResult.success(4200, "抢购成功", orderNo);
            case "FAILED":   return SeckillResult.fail(4500, c.getMsg());
            default:         return SeckillResult.queuing(orderNo);  // QUEUING
        }
    }

    // rollbackRedisStock / generateOrderNo 见 3.5 节
}
```

#### 步骤 ⑧ MQ 消费端：幂等 + 本地事务 + 写结果缓存

消费端在第 3.6/3.7 节已给出主体，这里补上全链路闭环必需的**写结果缓存**（否则前端永远轮询不到"成功"）与更完整的**异常分支处理**（重试耗尽进死信、回滚 Redis 库存）。下面给出消费端的完整代码，每一步的幂等控制、事务边界、异常处理都不省略。

```java
/**
 * 秒杀订单消费者（全链路闭环版）
 *
 * 完整流程：
 * 1. 幂等校验：orderExists → 已有订单直接写 SUCCESS 缓存并返回
 * 2. 冷冻库存校验：frozen key 不存在说明已超时被回收，写 FAILED 缓存并返回
 * 3. 本地事务：创建秒杀订单 + 扣减 DB 库存（乐观锁 WHERE stock >= deductNum）
 * 4. 写结果缓存到 Redis（前端轮询使用）
 * 5. 删除冷冻库存记录
 * 6. 发送用户通知（Push / 站内信）
 * 7. 消费失败：RocketMQ 自动重试 3 次，仍失败进死信队列，死信消费者回滚 Redis 库存
 */
@Component
@RocketMQMessageListener(
    topic = "seckill-order-topic",
    consumerGroup = "seckill-order-consumer-group",
    maxReconsumeTimes = 3,           // 最多重试 3 次
    messageModel = MessageModel.CLUSTERING
)
@Slf4j
public class SeckillOrderConsumer implements RocketMQListener<SeckillMessage> {

    @Autowired private OrderService orderService;
    @Autowired private InventoryService inventoryService;
    @Autowired private NotifyService notifyService;
    @Autowired private StringRedisTemplate redisTemplate;

    /** 订单结果缓存 key，与 SeckillService 中的规则保持一致 */
    private String resultKey(String orderNo) { return "seckill:result:" + orderNo; }

    @Override
    public void onMessage(SeckillMessage message) {
        String orderNo = message.getOrderNo();
        Long userId = message.getUserId();
        Long itemId = message.getItemId();
        log.info("收到秒杀消息, 开始创建订单, orderNo={}, userId={}, itemId={}",
                orderNo, userId, itemId);

        try {
            // ---------- 8.1 幂等校验：订单是否已创建 ----------
            // 场景：MQ 重投递（如 Consumer 宕机后 Rebalance 重新消费）
            if (orderService.orderExists(orderNo)) {
                log.info("订单已存在, 幂等返回, orderNo={}", orderNo);
                // 补写结果缓存（防止上次消费成功但写缓存失败）
                writeResultCache(orderNo, "SUCCESS", null);
                return;
            }

            // ---------- 8.2 冷冻库存校验 ----------
            // 场景：用户抢到后 15 分钟内未支付，冷冻 key 已被延时任务清理
            String frozenKey = "seckill:frozen:" + orderNo;
            if (!Boolean.TRUE.equals(redisTemplate.hasKey(frozenKey))) {
                log.warn("冷冻库存已过期, 无法创建订单, orderNo={}", orderNo);
                writeResultCache(orderNo, "FAILED", "订单超时未支付，请重新抢购");
                return;
            }

            // ---------- 8.3 本地事务：创建订单 + 扣减 DB 库存 ----------
            // 事务内部已有幂等检查（本地事务表模式），此处不再赘述
            OrderDTO order = orderService.createSeckillOrder(message);
            log.info("秒杀订单创建成功, orderNo={}, orderId={}", orderNo, order.getOrderId());

            // ---------- 8.4 写结果缓存（前端轮询拿到"成功"）----------
            writeResultCache(orderNo, "SUCCESS", null);

            // ---------- 8.5 删除冷冻库存记录 ----------
            redisTemplate.delete(frozenKey);

            // ---------- 8.6 发送用户通知 ----------
            try {
                notifyService.sendOrderSuccessNotification(userId, orderNo);
            } catch (Exception notifyEx) {
                // 通知失败不影响订单主流程，只记日志
                log.warn("发送秒杀成功通知失败, orderNo={}", orderNo, notifyEx);
            }

        } catch (Exception e) {
            // 消费失败，RocketMQ 会自动重试（最多 3 次）
            // 重试耗尽后进入死信队列，由 SeckillDLQConsumer 回滚 Redis 库存
            log.error("秒杀订单创建失败, orderNo={}, 将重试", orderNo, e);
            throw new RuntimeException("订单创建失败, orderNo=" + orderNo, e);
        }
    }

    /**
     * 写订单结果缓存，供前端轮询
     */
    private void writeResultCache(String orderNo, String status, String msg) {
        String key = resultKey(orderNo);
        SeckillResultCache cache = new SeckillResultCache();
        cache.setStatus(status);
        cache.setMsg(msg);
        cache.setTimestamp(System.currentTimeMillis());
        try {
            redisTemplate.opsForValue().set(key,
                    JSON.toJSONString(cache), 30, TimeUnit.MINUTES);
        } catch (Exception e) {
            // 缓存写失败不影响主流程，前端轮询兜底会查 DB
            log.error("写结果缓存失败, orderNo={}", orderNo, e);
        }
    }
}
```

**本地事务：创建秒杀订单 + 扣减 DB 库存（乐观锁）**

第 3.7 节给出了基本版，这里补上**乐观锁 WHERE stock >= deductNum**的完整实现和更细的异常分支：

```java
/**
 * 订单服务：本地事务表模式（全链路闭环版）
 *
 * 事务边界：createSeckillOrder 内的所有操作要么全部成功，要么全部回滚
 * 幂等保证：LocalTransactionRecord 表的 bizId 唯一索引
 */
@Service
@Slf4j
public class OrderServiceImpl implements OrderService {

    @Autowired private OrderMapper orderMapper;
    @Autowired private InventoryMapper inventoryMapper;
    @Autowired private LocalTransactionMapper localTransactionMapper;

    /**
     * 创建秒杀订单（本地事务）
     *
     * @param message MQ 消息体
     * @return 订单 DTO
     * @throws InsufficientStockException DB 库存不足
     * @throws DuplicateOrderException    订单已存在（并发场景）
     */
    @Transactional(rollbackFor = Exception.class)
    public OrderDTO createSeckillOrder(SeckillMessage message) {
        String orderNo = message.getOrderNo();
        Long itemId = message.getItemId();
        Long userId = message.getUserId();
        int deductNum = 1;  // 秒杀默认扣减 1 件

        // 1. 幂等检查：查询本地事务表
        LocalTransactionRecord existRecord = localTransactionMapper.selectByBizId(orderNo);
        if (existRecord != null) {
            log.info("本地事务表已有记录, 幂等返回, orderNo={}", orderNo);
            Order existing = orderMapper.selectByOrderNo(orderNo);
            return convertToDTO(existing);
        }

        // 2. 扣减 DB 库存（乐观锁：WHERE stock >= deductNum）
        int affected = inventoryMapper.deductStockWithOptimisticLock(itemId, deductNum);
        if (affected == 0) {
            // DB 库存不足——理论上 Redis 预扣减成功后这里不应失败
            // 可能原因：对账任务修正了 DB 库存、人工干预等
            log.error("DB 库存扣减失败, itemId={}, deductNum={}", itemId, deductNum);
            throw new InsufficientStockException(
                "DB 库存不足, itemId=" + itemId + ", deductNum=" + deductNum);
        }

        // 3. 创建秒杀订单
        Order order = new Order();
        order.setOrderNo(orderNo);
        order.setUserId(userId);
        order.setItemId(itemId);
        order.setActivityId(message.getActivityId());
        order.setStatus(OrderStatus.CREATED);
        order.setQuantity(deductNum);
        order.setCreateTime(new Date());
        order.setExpireTime(new Date(System.currentTimeMillis() + 15 * 60 * 1000L)); // 15 分钟未支付自动取消
        orderMapper.insert(order);

        // 4. 写入本地事务表（与订单在同一事务中提交，保证幂等）
        LocalTransactionRecord record = new LocalTransactionRecord();
        record.setBizId(orderNo);
        record.setBizType("SECKILL_ORDER");
        record.setStatus("PROCESSED");
        record.setCreateTime(new Date());
        try {
            localTransactionMapper.insert(record);
        } catch (DuplicateKeyException dke) {
            // 并发场景：两个相同 orderNo 的事务同时提交，唯一索引兜底
            log.warn("本地事务表唯一索引冲突, 触发回滚, orderNo={}", orderNo);
            throw new DuplicateOrderException("订单已存在, orderNo=" + orderNo);
        }

        // 5. 添加超时取消任务（延时队列）
        orderTimeoutService.addTimeoutTask(orderNo);

        log.info("秒杀订单创建+扣DB库存成功, orderNo={}, itemId={}, deductNum={}",
                orderNo, itemId, deductNum);
        return convertToDTO(order);
    }
}
```

**死信队列消费者：回滚 Redis 库存**

消费失败重试 3 次仍不成功时，消息进入死信队列。此时 Redis 库存已被预扣减，但 DB 订单未创建，必须回滚 Redis 库存，否则用户买不到、库存也回不来：

```java
/**
 * 死信队列消费者：处理彻底失败的秒杀消息
 *
 * 核心动作：
 * 1. 原子性回滚 Redis：库存 +1，移除已购记录，删除冷冻记录
 * 2. 写失败结果缓存，前端轮询到后提示"系统繁忙"
 * 3. 告警通知运维
 * 4. 记录失败日志，供后续排查
 */
@Component
@RocketMQMessageListener(
    topic = "%DLQ%seckill-order-consumer-group",
    consumerGroup = "seckill-dlq-consumer-group"
)
@Slf4j
public class SeckillDLQConsumer implements RocketMQListener<SeckillMessage> {

    @Autowired private StringRedisTemplate redisTemplate;
    @Autowired private AlertService alertService;
    @Autowired private FailureLogService failureLogService;

    /** 回滚 Redis 库存的 Lua 脚本（原子操作） */
    private static final String ROLLBACK_LUA =
        "if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then\n" +
        "    redis.call('INCR', KEYS[1])\n" +
        "    redis.call('SREM', KEYS[2], ARGV[1])\n" +
        "    redis.call('DEL', KEYS[3])\n" +
        "    return 1\n" +
        "else\n" +
        "    return 0\n" +
        "end";

    @Override
    public void onMessage(SeckillMessage message) {
        String orderNo = message.getOrderNo();
        Long itemId = message.getItemId();
        Long userId = message.getUserId();
        log.error("秒杀消息进入死信队列, 开始回滚 Redis 库存, orderNo={}, itemId={}, userId={}",
                orderNo, itemId, userId);

        String stockKey = "seckill:stock:" + itemId;
        String boughtKey = "seckill:bought:" + itemId;
        String frozenKey = "seckill:frozen:" + orderNo;

        try {
            // 1. 原子性回滚 Redis 库存
            Long result = redisTemplate.execute(
                    new DefaultRedisScript<>(ROLLBACK_LUA, Long.class),
                    Arrays.asList(stockKey, boughtKey, frozenKey),
                    String.valueOf(userId));

            if (result != null && result == 1L) {
                log.info("Redis 库存回滚成功, orderNo={}, itemId={}", orderNo, itemId);
            } else {
                // 可能已被延时任务处理（冷冻过期回收）或已被其他死信消费者处理
                log.warn("Redis 库存回滚跳过(已购记录不存在或已处理), orderNo={}", orderNo);
            }

            // 2. 写失败结果缓存
            String resultKey = "seckill:result:" + orderNo;
            SeckillResultCache cache = new SeckillResultCache();
            cache.setStatus("FAILED");
            cache.setMsg("系统繁忙，请稍后重试");
            cache.setTimestamp(System.currentTimeMillis());
            redisTemplate.opsForValue().set(resultKey,
                    JSON.toJSONString(cache), 30, TimeUnit.MINUTES);

            // 3. 告警通知运维
            alertService.sendSeckillFailureAlert(message);

            // 4. 记录失败日志
            failureLogService.record(message, "DLQ_PROCESSING");

        } catch (Exception e) {
            // 死信消费也失败，只能靠对账任务兜底
            log.error("死信队列处理失败, 需人工介入, orderNo={}", orderNo, e);
            alertService.sendCriticalAlert(
                "死信队列处理失败, 需人工介入! orderNo=" + orderNo);
        }
    }
}
```

**步骤 ⑧ 的关键点与异常分支**：

| 子步骤 | 成功 | 失败/异常 | 处理 |
|--------|------|-----------|------|
| 幂等校验 | 订单不存在，继续 | 订单已存在（重投递） | 写 SUCCESS 缓存，直接 return |
| 冷冻校验 | frozen key 存在，继续 | frozen key 不存在（已超时回收） | 写 FAILED 缓存，return |
| 本地事务 | 订单创建 + DB 扣库存成功 | DB 库存不足 / 唯一索引冲突 | 抛异常 → MQ 重试 |
| 写结果缓存 | 前端轮询拿到 SUCCESS | Redis 写失败 | 记日志，前端兜底查 DB |
| 删冷冻记录 | 冷冻 key 删除 | 删除失败 | 无影响，key 15 分钟后自动过期 |
| 通知用户 | Push/站内信发送成功 | 通知服务超时 | 记日志，不影响主流程 |
| 死信处理 | 原子回滚 Redis 库存 | 回滚脚本异常 | 告警，等对账任务兜底 |

> **为什么死信回滚用 Lua 脚本而不是三条独立命令**：`INCR stock` + `SREM bought` + `DEL frozen` 如果分三条执行，中间可能被其他请求插入（例如恰好有新的秒杀请求读到被错误恢复的库存），导致超卖。Lua 脚本在 Redis 单线程中原子执行，中间不会被打断。脚本中先 `SISMEMBER` 判断，确保只有真正需要回滚时才操作，避免重复回滚。

### 案例二：库存预热与活动初始化全链路

**场景**：运营在管理后台创建秒杀活动 `activityId=8002`，商品 `itemId=2002`（iPad，库存 500 件），活动时间为 `2025-01-20 20:00:00 ~ 20:30:00`。系统需要在活动开始前完成库存预热、活动配置入库、时间窗口控制，确保活动开始瞬间 Redis 中已有正确的库存数据。

#### 链路时序总览

```
[运营后台创建活动]
  │  活动配置写入 MySQL
  ▼
[定时任务：活动开始前 10 分钟]
  │  读取活动配置 → 加载库存到 Redis → 设置活动状态为 NOT_START
  ▼
[定时任务：活动开始时间到达]
  │  活动状态 NOT_START → RUNNING
  ▼
[秒杀请求进入]  资格校验读取 Redis 活动状态，确认 RUNNING 且在时间窗口内
  ▼
[定时任务：活动结束时间到达]
  │  活动状态 RUNNING → ENDED，停止受理新请求
```

#### 活动配置入库

```java
/**
 * 秒杀活动管理 Service
 *
 * 负责活动配置的创建、修改、状态流转
 */
@Service
@Slf4j
public class SeckillActivityService {

    @Autowired private SeckillActivityMapper activityMapper;
    @Autowired private StringRedisTemplate redisTemplate;

    /**
     * 创建秒杀活动
     *
     * @param request 活动配置请求
     * @return 活动ID
     */
    @Transactional(rollbackFor = Exception.class)
    public Long createActivity(SeckillActivityRequest request) {
        // 1. 参数校验
        validateActivityRequest(request);

        // 2. 写入活动配置到 MySQL
        SeckillActivity activity = new SeckillActivity();
        activity.setActivityId(idGenerator.nextId());
        activity.setItemId(request.getItemId());
        activity.setItemName(request.getItemName());
        activity.setInitialStock(request.getStock());
        activity.setStartTime(request.getStartTime());
        activity.setEndTime(request.getEndTime());
        activity.setLimitPerUser(request.getLimitPerUser());
        activity.setWhitelistOnly(request.isWhitelistOnly());
        activity.setStatus("NOT_START");  // 初始状态：未开始
        activity.setCreateTime(new Date());
        activityMapper.insert(activity);

        // 3. 写入商品库存到 DB（item_inventory 表）
        Inventory inventory = new Inventory();
        inventory.setItemId(request.getItemId());
        inventory.setStock(request.getStock());
        inventory.setLockedStock(0);
        inventory.setCreateTime(new Date());
        inventoryMapper.insertOrUpdate(inventory);

        // 4. 如果有白名单，写入 Redis Set
        if (request.isWhitelistOnly() && request.getWhitelist() != null) {
            String whitelistKey = "seckill:whitelist:" + activity.getActivityId();
            for (Long userId : request.getWhitelist()) {
                redisTemplate.opsForSet().add(whitelistKey, String.valueOf(userId));
            }
            redisTemplate.expire(whitelistKey,
                    computeExpireSeconds(request.getEndTime()), TimeUnit.SECONDS);
        }

        log.info("秒杀活动创建成功, activityId={}, itemId={}, stock={}, start={}, end={}",
                activity.getActivityId(), activity.getItemId(), activity.getInitialStock(),
                activity.getStartTime(), activity.getEndTime());

        return activity.getActivityId();
    }

    private void validateActivityRequest(SeckillActivityRequest req) {
        if (req.getItemId() == null || req.getItemId() <= 0) {
            throw new IllegalArgumentException("商品ID非法");
        }
        if (req.getStock() <= 0) {
            throw new IllegalArgumentException("库存必须大于0");
        }
        if (req.getStartTime() == null || req.getEndTime() == null) {
            throw new IllegalArgumentException("活动起止时间不能为空");
        }
        if (!req.getEndTime().after(req.getStartTime())) {
            throw new IllegalArgumentException("结束时间必须晚于开始时间");
        }
        // 活动开始时间至少在当前时间 30 分钟之后，给预热留时间
        if (req.getStartTime().getTime() - System.currentTimeMillis() < 30 * 60 * 1000L) {
            throw new IllegalArgumentException("活动开始时间至少在30分钟之后");
        }
    }

    private long computeExpireSeconds(Date endTime) {
        long diff = endTime.getTime() - System.currentTimeMillis();
        // 额外给 1 小时缓冲
        return (diff + 3600_000L) / 1000;
    }
}
```

#### 定时任务：库存预热 + 活动状态流转

```java
/**
 * 秒杀活动定时任务
 *
 * 职责：
 * 1. 活动开始前 10 分钟：库存预热（DB → Redis）
 * 2. 活动开始：状态 NOT_START → RUNNING
 * 3. 活动结束：状态 RUNNING → ENDED
 *
 * 设计要点：
 * - 预热幂等：已预热的活动不会重复预热
 * - 预热失败重试：每分钟扫描，直到预热成功
 * - 状态流转幂等：基于 DB 版本号乐观更新
 */
@Component
@Slf4j
public class SeckillActivityScheduler {

    @Autowired private SeckillActivityMapper activityMapper;
    @Autowired private InventoryMapper inventoryMapper;
    @Autowired private StringRedisTemplate redisTemplate;

    /** 活动开始前 10 分钟预热 */
    private static final int PREHEAT_LEAD_MINUTES = 10;

    /**
     * 每 60 秒扫描一次，处理库存预热和状态流转
     */
    @Scheduled(fixedRate = 60_000)
    public void scanActivities() {
        // 查询所有未结束的活动
        List<SeckillActivity> activities = activityMapper.selectByStatusNot("ENDED");
        if (activities == null || activities.isEmpty()) return;

        for (SeckillActivity activity : activities) {
            try {
                processActivity(activity);
            } catch (Exception e) {
                log.error("处理活动失败, activityId={}", activity.getActivityId(), e);
            }
        }
    }

    private void processActivity(SeckillActivity activity) {
        long now = System.currentTimeMillis();
        long startTs = activity.getStartTime().getTime();
        long endTs = activity.getEndTime().getTime();
        Long activityId = activity.getActivityId();
        Long itemId = activity.getItemId();

        // ---------- 阶段 1：库存预热（开始前 10 分钟）----------
        long preheatTs = startTs - PREHEAT_LEAD_MINUTES * 60_000L;
        if (now >= preheatTs && now < startTs && "NOT_START".equals(activity.getStatus())) {
            preheatStock(activity);
            // 预热成功后不立即改状态，等到达开始时间再改
        }

        // ---------- 阶段 2：活动开始（NOT_START → RUNNING）----------
        if (now >= startTs && now < endTs && "NOT_START".equals(activity.getStatus())) {
            // 确认库存已预热
            String stockKey = "seckill:stock:" + itemId;
            String stockStr = redisTemplate.opsForValue().get(stockKey);
            if (stockStr == null) {
                log.warn("活动即将开始但库存未预热, 紧急预热, activityId={}", activityId);
                preheatStock(activity);
            }
            // 乐观更新状态
            int affected = activityMapper.updateStatusWithVersion(
                    activityId, "NOT_START", "RUNNING", activity.getVersion());
            if (affected > 0) {
                // 同步活动信息到 Redis Hash（资格校验读取）
                writeActivityToRedis(activity, "RUNNING");
                log.info("活动状态变更 NOT_START → RUNNING, activityId={}", activityId);
            }
        }

        // ---------- 阶段 3：活动结束（RUNNING → ENDED）----------
        if (now >= endTs && "RUNNING".equals(activity.getStatus())) {
            int affected = activityMapper.updateStatusWithVersion(
                    activityId, "RUNNING", "ENDED", activity.getVersion());
            if (affected > 0) {
                writeActivityToRedis(activity, "ENDED");
                log.info("活动状态变更 RUNNING → ENDED, activityId={}", activityId);
            }
        }
    }

    /**
     * 库存预热：DB 库存 → Redis
     *
     * Redis 数据结构设计：
     * ┌────────────────────────────────────────────────────────────┐
     * │ Key                          │ Type   │ Value              │
     * ├──────────────────────────────┼────────┼────────────────────┤
     * │ seckill:stock:{itemId}       │ String │ 剩余库存数量        │
     * │ seckill:bought:{itemId}      │ Set    │ 已购用户ID集合      │
     * │ seckill:activity:{actId}     │ Hash   │ 活动元信息          │
     * │ seckill:whitelist:{actId}    │ Set    │ 白名单用户ID集合    │
     * └────────────────────────────────────────────────────────────┘
     */
    public void preheatStock(SeckillActivity activity) {
        Long itemId = activity.getItemId();
        Long activityId = activity.getActivityId();

        // 1. 幂等检查：已预热则跳过
        String stockKey = "seckill:stock:" + itemId;
        if (Boolean.TRUE.equals(redisTemplate.hasKey(stockKey))) {
            log.info("库存已预热, 跳过, activityId={}, itemId={}", activityId, itemId);
            return;
        }

        // 2. 从 DB 读取库存
        int dbStock = inventoryMapper.getStock(itemId);
        if (dbStock < 0) {
            log.error("DB 库存查询异常, itemId={}, stock={}", itemId, dbStock);
            return;
        }

        // 3. 写入 Redis（使用 SETNX 保证幂等：只有 key 不存在时才写入）
        Boolean setOk = redisTemplate.opsForValue()
                .setIfAbsent(stockKey, String.valueOf(dbStock));
        if (!Boolean.TRUE.equals(setOk)) {
            log.info("库存已被其他节点预热, 跳过, itemId={}", itemId);
            return;
        }

        // 4. 设置过期时间（活动结束后 2 小时过期）
        long expireSeconds = (activity.getEndTime().getTime() - System.currentTimeMillis()) / 1000
                + 2 * 3600;
        redisTemplate.expire(stockKey, expireSeconds, TimeUnit.SECONDS);

        // 5. 初始化已购用户集合（空集合，设置过期时间）
        String boughtKey = "seckill:bought:" + itemId;
        redisTemplate.expire(boughtKey, expireSeconds, TimeUnit.SECONDS);

        // 6. 写入活动元信息到 Redis Hash
        writeActivityToRedis(activity, activity.getStatus());

        log.info("库存预热成功, activityId={}, itemId={}, stock={}, expireSeconds={}",
                activityId, itemId, dbStock, expireSeconds);
    }

    /**
     * 将活动元信息写入 Redis Hash（供资格校验读取）
     */
    private void writeActivityToRedis(SeckillActivity activity, String status) {
        String actKey = "seckill:activity:" + activity.getActivityId();
        Map<String, String> map = new HashMap<>();
        map.put("activityId", String.valueOf(activity.getActivityId()));
        map.put("itemId", String.valueOf(activity.getItemId()));
        map.put("startTime", String.valueOf(activity.getStartTime().getTime()));
        map.put("endTime", String.valueOf(activity.getEndTime().getTime()));
        map.put("initialStock", String.valueOf(activity.getInitialStock()));
        map.put("limitPerUser", String.valueOf(activity.getLimitPerUser()));
        map.put("whitelistOnly", activity.isWhitelistOnly() ? "1" : "0");
        map.put("status", status);
        redisTemplate.opsForHash().putAll(actKey, map);

        long expireSeconds = (activity.getEndTime().getTime() - System.currentTimeMillis()) / 1000
                + 2 * 3600;
        redisTemplate.expire(actKey, expireSeconds, TimeUnit.SECONDS);
    }
}
```

**预热异常处理与补偿**：

| 异常场景 | 影响 | 处理策略 |
|----------|------|----------|
| DB 查询失败 | 无法获取库存 | 下次定时任务重试（每 60 秒） |
| Redis 写入失败 | 预热不成功 | 下次定时任务重试 |
| 重复预热（多节点并发） | 可能覆盖 | SETNX 保证幂等，已存在则跳过 |
| 活动开始时仍未预热 | 用户无法秒杀 | 活动开始时紧急预热（同步） |
| 库存预热数量与 DB 不一致 | 超卖或少卖 | 对账任务修正 |

> **为什么用 SETNX 而不是 SET**：秒杀服务通常部署多实例，定时任务在多个节点上同时运行。如果用 `SET`，后执行的会覆盖先执行的，虽然结果一样但会产生不必要的写入。`SETNX`（`setIfAbsent`）保证只有第一个节点写入成功，其余节点发现 key 已存在直接跳过，减少 Redis 写压力。

### 案例三：秒杀结束后的对账与补偿全链路

**场景**：秒杀活动 `activityId=8002` 结束后，系统需要确保 Redis 库存、DB 库存、订单数据三者一致。如果有不一致（MQ 消息丢失、消费者宕机、人工干预等），需要自动补偿。同时，超时未支付的订单需要回收库存，并生成对账报告供运营审计。

#### 链路时序总览

```
[活动结束]
  │
  ▼
[定时任务：每 60 秒对账]
  │  Redis剩余库存 + 冷冻库存 + 已售订单数 == 初始库存 ?
  │  ├─ 一致 → 记录对账通过
  │  └─ 不一致 → 自动补偿：以 DB 为准修正 Redis 库存 + 告警
  ▼
[定时任务：超时未支付订单回收]
  │  订单状态 CREATED 且超过 15 分钟 → 取消订单 + 恢复 DB/Redis 库存
  ▼
[活动结束后 30 分钟：生成对账报告]
  │  汇总：初始库存 / 已售 / 已取消 / 剩余 / 异常数
  │  写入 DB + 发送邮件给运营
```

#### 定时任务对账：三量校验 + 自动补偿

第 3.9 节给出了基础对账逻辑，这里补全为**全链路闭环版**——增加订单数量校验、超时订单回收联动、对账报告生成：

```java
/**
 * 秒杀全链路对账定时任务（闭环版）
 *
 * 对账公式：
 *   Redis剩余库存 + 冷冻库存数量 + DB已售订单数 == 活动初始库存
 *
 * 三量校验：
 *   1. Redis 剩余库存（seckill:stock:{itemId}）
 *   2. 冷冻库存（seckill:frozen:* 中对应 itemId 的记录数）
 *   3. DB 已售订单数（order 表中 CREATED / PAID 状态的秒杀订单数）
 *
 * 不一致时：以 DB 为准，修正 Redis 库存
 */
@Component
@Slf4j
public class SeckillReconcileTask {

    @Autowired private SeckillActivityMapper activityMapper;
    @Autowired private InventoryMapper inventoryMapper;
    @Autowired private OrderMapper orderMapper;
    @Autowired private StringRedisTemplate redisTemplate;
    @Autowired private AlertService alertService;
    @Autowired private ReconcileReportService reportService;

    /**
     * 每 60 秒执行一次对账
     */
    @Scheduled(fixedRate = 60_000)
    public void reconcile() {
        // 1. 获取所有进行中或刚结束（30 分钟内）的活动
        List<SeckillActivity> activities = activityMapper
                .selectActiveOrRecentlyEnded(30);

        if (activities == null || activities.isEmpty()) return;

        for (SeckillActivity activity : activities) {
            try {
                reconcileActivity(activity);
            } catch (Exception e) {
                log.error("对账失败, activityId={}", activity.getActivityId(), e);
            }
        }
    }

    /**
     * 单个活动的对账逻辑
     */
    private void reconcileActivity(SeckillActivity activity) {
        Long itemId = activity.getItemId();
        Long activityId = activity.getActivityId();
        int initialStock = activity.getInitialStock();

        // 2. 获取 Redis 剩余库存
        String stockKey = "seckill:stock:" + itemId;
        String redisStockStr = redisTemplate.opsForValue().get(stockKey);
        int redisStock = redisStockStr != null ? Integer.parseInt(redisStockStr) : 0;

        // 3. 获取冷冻库存数量（已从 Redis 扣减但未在 DB 落库的预扣减）
        int frozenCount = countFrozenStock(itemId);

        // 4. 获取 DB 已售订单数（CREATED + PAID 状态）
        int soldCount = orderMapper.countSeckillOrdersByStatus(itemId,
                Arrays.asList("CREATED", "PAID"));

        // 5. 对账公式校验
        int expected = redisStock + frozenCount + soldCount;

        if (expected == initialStock) {
            // 一致，记录 debug 日志
            log.debug("对账通过, activityId={}, itemId={}, redis={}, frozen={}, sold={}, initial={}",
                    activityId, itemId, redisStock, frozenCount, soldCount, initialStock);
            return;
        }

        // ========== 不一致，开始补偿 ==========

        log.warn("库存不一致! activityId={}, itemId={}, Redis={}, 冷冻={}, 已售={}, 初始={}, 预期={}",
                activityId, itemId, redisStock, frozenCount, soldCount, initialStock, expected);

        // 6. 自动补偿：以 DB 为准，重新计算 Redis 库存
        //    correctRedisStock = 初始库存 - 已售订单数 - 冷冻库存数量
        int correctRedisStock = initialStock - soldCount - frozenCount;
        if (correctRedisStock < 0) {
            // 严重异常：已售 + 冷冻 > 初始库存，说明出现超卖
            log.error("严重不一致：计算出的 Redis 库存为负数! activityId={}, itemId={}, " +
                    "correctRedisStock={}, soldCount={}, frozenCount={}",
                    activityId, itemId, correctRedisStock, soldCount, frozenCount);
            correctRedisStock = 0;
            // 发送紧急告警
            alertService.sendCriticalAlert(String.format(
                "秒杀超卖告警! activityId=%d, itemId=%d, soldCount=%d, frozenCount=%d, initialStock=%d",
                activityId, itemId, soldCount, frozenCount, initialStock));
        }

        // 7. 修正 Redis 库存
        redisTemplate.opsForValue().set(stockKey, String.valueOf(correctRedisStock));
        log.info("Redis 库存已修正, itemId={}, 旧值={}, 新值={}",
                itemId, redisStock, correctRedisStock);

        // 8. 同时校验 DB 库存是否一致
        //    DB 库存应该 = 初始库存 - 已售订单数
        int dbStock = inventoryMapper.getStock(itemId);
        int expectedDbStock = initialStock - soldCount;
        if (dbStock != expectedDbStock) {
            log.error("DB 库存也不一致! itemId={}, dbStock={}, expectedDbStock={}",
                    itemId, dbStock, expectedDbStock);
            // DB 库存不一致不自动修正（需人工确认），只告警
            alertService.sendInventoryInconsistencyAlert(itemId, dbStock, expectedDbStock);
        }

        // 9. 发送不一致告警
        alertService.sendReconcileAlert(activityId, itemId, expected, initialStock);

        // 10. 记录对账异常日志
        reportService.recordReconcileAnomaly(activityId, itemId,
                redisStock, frozenCount, soldCount, initialStock, expected);
    }

    /**
     * 统计冷冻库存数量
     * 扫描 seckill:frozen:* 的所有 key，统计对应 itemId 的数量
     */
    private int countFrozenStock(Long itemId) {
        Set<String> frozenKeys = redisTemplate.keys("seckill:frozen:*");
        if (frozenKeys == null || frozenKeys.isEmpty()) return 0;

        int count = 0;
        for (String key : frozenKeys) {
            Object storedItemId = redisTemplate.opsForHash().get(key, "itemId");
            if (storedItemId != null && storedItemId.equals(String.valueOf(itemId))) {
                count++;
            }
        }
        return count;
    }
}
```

#### 超时未支付订单的库存回收

第 3.8 节给出了基础版，这里补全为**闭环版**——增加幂等控制、Redis 库存恢复的原子性保证、与对账任务的联动：

```java
/**
 * 超时未支付订单回收定时任务（闭环版）
 *
 * 职责：扫描超时未支付的秒杀订单，取消订单并回收库存
 *
 * 幂等保证：
 * - DB 层面：订单状态只能 CREATED → CANCELLED（乐观锁 WHERE status = 'CREATED'）
 * - Redis 层面：Lua 脚本中先判断 SISMEMBER，避免重复恢复库存
 */
@Service
@Slf4j
public class OrderTimeoutReclaimService {

    @Autowired private OrderMapper orderMapper;
    @Autowired private InventoryMapper inventoryMapper;
    @Autowired private StringRedisTemplate redisTemplate;

    private static final int TIMEOUT_MINUTES = 15;

    /** 原子恢复 Redis 库存的 Lua 脚本 */
    private static final String RESTORE_STOCK_LUA =
        "if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then\n" +
        "    redis.call('INCR', KEYS[1])\n" +
        "    redis.call('SREM', KEYS[2], ARGV[1])\n" +
        "    return 1\n" +
        "else\n" +
        "    return 0\n" +
        "end";

    /**
     * 每 30 秒扫描一次超时订单
     */
    @Scheduled(fixedRate = 30_000)
    public void scanTimeoutOrders() {
        Date deadline = new Date(System.currentTimeMillis() - TIMEOUT_MINUTES * 60_000L);

        // 1. 查询所有超时未支付的秒杀订单
        List<Order> timeoutOrders = orderMapper
                .selectByStatusAndCreateTimeBefore("CREATED", deadline);

        if (timeoutOrders == null || timeoutOrders.isEmpty()) return;

        log.info("扫描到 {} 笔超时未支付订单, 开始回收库存", timeoutOrders.size());

        for (Order order : timeoutOrders) {
            try {
                cancelAndRestore(order);
            } catch (Exception e) {
                log.error("超时订单回收失败, orderNo={}", order.getOrderNo(), e);
            }
        }
    }

    /**
     * 取消订单并回收库存（单笔）
     */
    @Transactional(rollbackFor = Exception.class)
    public void cancelAndRestore(Order order) {
        String orderNo = order.getOrderNo();
        Long itemId = order.getItemId();
        Long userId = order.getUserId();

        // 1. 乐观锁更新订单状态：CREATED → CANCELLED（幂等）
        int affected = orderMapper.updateStatusWithCondition(
                orderNo, "CREATED", "CANCELLED");
        if (affected == 0) {
            // 订单状态已变更（可能用户刚支付，或已被其他任务取消），跳过
            log.info("订单状态已变更, 跳过回收, orderNo={}", orderNo);
            return;
        }

        // 2. 恢复 DB 库存
        inventoryMapper.restoreStock(itemId, order.getQuantity());
        log.info("DB 库存已恢复, itemId={}, quantity={}", itemId, order.getQuantity());

        // 3. 原子恢复 Redis 库存（Lua 脚本保证幂等）
        String stockKey = "seckill:stock:" + itemId;
        String boughtKey = "seckill:bought:" + itemId;
        Long result = redisTemplate.execute(
                new DefaultRedisScript<>(RESTORE_STOCK_LUA, Long.class),
                Arrays.asList(stockKey, boughtKey),
                String.valueOf(userId));

        if (result != null && result == 1L) {
            log.info("Redis 库存已恢复, orderNo={}, itemId={}", orderNo, itemId);
        } else {
            // result == 0 说明已购记录不存在（可能已被死信消费者回滚，或对账任务修正）
            log.info("Redis 已购记录不存在, 跳过恢复, orderNo={}", orderNo);
        }

        // 4. 删除冷冻库存记录（如果还存在）
        redisTemplate.delete("seckill:frozen:" + orderNo);

        // 5. 更新结果缓存为"超时取消"
        String resultKey = "seckill:result:" + orderNo;
        SeckillResultCache cache = new SeckillResultCache();
        cache.setStatus("FAILED");
        cache.setMsg("订单超时未支付，已自动取消");
        cache.setTimestamp(System.currentTimeMillis());
        redisTemplate.opsForValue().set(resultKey,
                JSON.toJSONString(cache), 30, TimeUnit.MINUTES);

        log.info("超时订单回收完成, orderNo={}, itemId={}, userId={}",
                orderNo, itemId, userId);
    }
}
```

#### 对账报告生成

活动结束后 30 分钟，自动生成对账报告并通知运营：

```java
/**
 * 对账报告生成 Service
 *
 * 活动结束后 30 分钟自动生成，包含：
 * - 库存消耗明细：初始库存 / 已售 / 已取消 / 剩余
 * - 异常记录：对账不一致次数 / 超卖告警 / 死信消息数
 * - 订单统计：成功下单数 / 支付率 / 超时取消数
 */
@Service
@Slf4j
public class ReconcileReportService {

    @Autowired private SeckillActivityMapper activityMapper;
    @Autowired private OrderMapper orderMapper;
    @Autowired private InventoryMapper inventoryMapper;
    @Autowired private ReconcileAnomalyMapper anomalyMapper;
    @Autowired private StringRedisTemplate redisTemplate;
    @Autowired private EmailService emailService;

    /**
     * 每分钟检查是否有需要生成报告的活动
     * 条件：活动已结束 30 分钟，且尚未生成报告
     */
    @Scheduled(fixedRate = 60_000)
    public void generateReports() {
        List<SeckillActivity> activities = activityMapper
                .selectEndedWithoutReport(30);  // 结束 30 分钟且无报告

        if (activities == null || activities.isEmpty()) return;

        for (SeckillActivity activity : activities) {
            try {
                generateReport(activity);
            } catch (Exception e) {
                log.error("对账报告生成失败, activityId={}", activity.getActivityId(), e);
            }
        }
    }

    /**
     * 生成单个活动的对账报告
     */
    @Transactional(rollbackFor = Exception.class)
    public void generateReport(SeckillActivity activity) {
        Long activityId = activity.getActivityId();
        Long itemId = activity.getItemId();
        int initialStock = activity.getInitialStock();

        // 1. 统计订单数据
        int totalOrders = orderMapper.countByActivityId(activityId);
        int paidOrders = orderMapper.countByActivityIdAndStatus(activityId, "PAID");
        int cancelledOrders = orderMapper.countByActivityIdAndStatus(activityId, "CANCELLED");
        int createdOrders = orderMapper.countByActivityIdAndStatus(activityId, "CREATED");

        // 2. 库存数据
        int dbStock = inventoryMapper.getStock(itemId);
        String redisStockStr = redisTemplate.opsForValue().get("seckill:stock:" + itemId);
        int redisStock = redisStockStr != null ? Integer.parseInt(redisStockStr) : 0;

        // 3. 异常记录
        int anomalyCount = anomalyMapper.countByActivityId(activityId);
        List<ReconcileAnomaly> anomalies = anomalyMapper.selectByActivityId(activityId);

        // 4. 构建报告
        ReconcileReport report = new ReconcileReport();
        report.setActivityId(activityId);
        report.setItemId(itemId);
        report.setItemName(activity.getItemName());
        report.setInitialStock(initialStock);
        report.setSoldStock(paidOrders + createdOrders);  // 已售 = 已支付 + 待支付
        report.setCancelledStock(cancelledOrders);
        report.setRemainingDbStock(dbStock);
        report.setRemainingRedisStock(redisStock);
        report.setTotalOrders(totalOrders);
        report.setPaidOrders(paidOrders);
        report.setPaymentRate(totalOrders > 0 ? (double) paidOrders / totalOrders : 0);
        report.setAnomalyCount(anomalyCount);
        report.setAnomalies(anomalies);
        report.setActivityStartTime(activity.getStartTime());
        report.setActivityEndTime(activity.getEndTime());
        report.setReportCreateTime(new Date());

        // 5. 判断最终一致性
        boolean consistent = (redisStock + paidOrders + createdOrders == initialStock)
                && (dbStock + paidOrders + createdOrders == initialStock);
        report.setConsistent(consistent);

        // 6. 写入 DB
        reportMapper.insert(report);

        // 7. 标记活动已生成报告
        activityMapper.markReportGenerated(activityId);

        // 8. 发送邮件给运营
        String subject = String.format("[秒杀对账报告] 活动 %d - %s - %s",
                activityId, activity.getItemName(),
                consistent ? "数据一致" : "存在异常需关注");
        String content = buildReportEmailContent(report);
        emailService.sendToOperations(subject, content);

        log.info("对账报告生成完成, activityId={}, consistent={}, totalOrders={}, paidOrders={}",
                activityId, consistent, totalOrders, paidOrders);
    }

    /**
     * 构建报告邮件内容
     */
    private String buildReportEmailContent(ReconcileReport report) {
        StringBuilder sb = new StringBuilder();
        sb.append("=== 秒杀活动对账报告 ===\n\n");
        sb.append(String.format("活动ID: %d\n", report.getActivityId()));
        sb.append(String.format("商品: %s (itemId=%d)\n", report.getItemName(), report.getItemId()));
        sb.append(String.format("活动时间: %s ~ %s\n",
                report.getActivityStartTime(), report.getActivityEndTime()));
        sb.append("\n--- 库存明细 ---\n");
        sb.append(String.format("初始库存: %d\n", report.getInitialStock()));
        sb.append(String.format("已售(含待支付): %d\n", report.getSoldStock()));
        sb.append(String.format("已取消: %d\n", report.getCancelledStock()));
        sb.append(String.format("DB剩余: %d\n", report.getRemainingDbStock()));
        sb.append(String.format("Redis剩余: %d\n", report.getRemainingRedisStock()));
        sb.append("\n--- 订单统计 ---\n");
        sb.append(String.format("总订单数: %d\n", report.getTotalOrders()));
        sb.append(String.format("已支付: %d\n", report.getPaidOrders()));
        sb.append(String.format("支付率: %.2f%%\n", report.getPaymentRate() * 100));
        sb.append("\n--- 异常记录 ---\n");
        sb.append(String.format("异常次数: %d\n", report.getAnomalyCount()));
        if (!report.isConsistent()) {
            sb.append("\n⚠ 最终数据不一致，请人工核查！\n");
        }
        for (ReconcileAnomaly anomaly : report.getAnomalies()) {
            sb.append(String.format("  - [%s] %s\n",
                    anomaly.getCreateTime(), anomaly.getDescription()));
        }
        return sb.toString();
    }
}
```

#### 对账与补偿的关键设计要点

| 设计点 | 方案 | 为什么 |
|--------|------|--------|
| 对账基准 | 以 DB 为准 | DB 是最终一致性的锚点，Redis 可能丢失数据 |
| 补偿方向 | 修正 Redis 库存 | DB 层面已有乐观锁防超卖，Redis 更容易出偏差 |
| DB 库存不一致 | 只告警不自动修正 | DB 数据修改影响面大，需人工确认 |
| 超时回收幂等 | 乐观锁 WHERE status='CREATED' | 防止延时任务和定时任务同时取消同一订单 |
| Redis 恢复幂等 | Lua 脚本先 SISMEMBER | 防止死信回滚和超时回收重复恢复库存 |
| 报告生成时机 | 活动结束后 30 分钟 | 给对账任务和超时回收留足时间 |
| 报告幂等 | markReportGenerated 标记 | 防止重复生成报告 |

> **对账公式的本质**：`Redis剩余 + 冷冻中 + 已落库订单 = 初始库存`。这三个量分别代表了库存的三个"状态"——还在 Redis 里可被抢的、被抢走但还在异步处理管道中的、已经处理完变成正式订单的。任何一个环节出问题（MQ 丢消息、消费者宕机、人工改库），都会导致等式不成立。对账任务就是这条等式的守护者，发现不等就修正、告警。

> **超时回收与死信回滚的"双重恢复"问题**：一笔订单可能同时触发"超时回收"和"死信回滚"——例如 MQ 重试 3 次失败进死信，同时冷冻 key 15 分钟过期。两个流程都会尝试恢复 Redis 库存。解决方案是 Redis 恢复操作用 Lua 脚本内嵌 `SISMEMBER` 判断：如果用户已不在已购集合中，说明库存已被恢复，直接返回 0 跳过。这保证无论哪个流程先执行，库存都只会被恢复一次。
