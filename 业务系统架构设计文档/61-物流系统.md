# 物流系统架构设计

## 一、问题背景

### 1.1 业务场景

物流系统是连接下单与履约的核心基础设施，覆盖从商家揽收、干线运输、末端配送到用户签收的完整链路。一个典型的物流场景需要满足：

1. **多物流商接入**：平台通常不会只对接一家物流服务商，而是同时接入多家快递公司、即时配送商、自建运力，需要屏蔽各家私有协议差异。
2. **运单全生命周期管理**：一个运单从创建到签收要经历十几个状态节点，任何一个节点都可能出现异常（超时、丢件、破损）。
3. **轨迹实时性要求高**：用户需要实时查看包裹在哪里，轨迹更新延迟直接影响体验。
4. **海量数据存储与查询**：大促期间，日运单量可达千万级，轨迹明细数据是运单量的数十倍。
5. **路由规划与调度**：即时配送场景下，需要为骑手规划配送路径，兼顾时效与成本。

### 1.2 旧系统痛点分析

早期系统直接将物流商的对接代码写死在业务主流程中，典型反面案例：

```java
/**
 * 旧系统反面案例：业务代码直接耦合具体物流商实现
 * 每接入一家新物流商，都要在主流程里加一个 if-else 分支
 */
public class LegacyLogisticsService {

    public void createWaybill(OrderDTO order) {
        if (order.getLogisticsProvider() == 1) {
            // SF 物流商专属参数拼接、专属签名算法
            SfApiClient sfClient = new SfApiClient();
            SfCreateOrderRequest req = new SfCreateOrderRequest();
            req.setCustomerCode("SF_CUSTOMER_001");
            req.setOrderId(order.getOrderId());
            // ... 几十行 SF 专属字段映射
            sfClient.createOrder(req);
        } else if (order.getLogisticsProvider() == 2) {
            // 另一家物流商，又是一套完全不同的字段和签名方式
            YtoApiClient ytoClient = new YtoApiClient();
            // ... 又是几十行专属逻辑
        } else if (order.getLogisticsProvider() == 3) {
            // 即时配送商，字段结构又不一样
            // ...
        }
        // 新增一家物流商，就要在这里再加一个分支，代码持续膨胀
    }
}
```

这种设计存在的核心问题：

1. **强耦合**：业务主流程直接依赖具体物流商 SDK，物流商接口变更会直接影响主流程稳定性。
2. **扩展困难**：新增物流商需要修改核心代码并全量回归测试，违反开闭原则。
3. **无法降级**：某个物流商接口抖动时，无法快速切换到备用物流商。
4. **轨迹数据割裂**：不同物流商的轨迹状态码体系不同，前端展示时需要做大量特判。

### 1.3 设计目标

| 目标维度 | 具体要求 |
|---------|---------|
| 解耦 | 业务层与具体物流商实现解耦，支持插拔式接入 |
| 状态一致 | 统一运单状态机，屏蔽各物流商私有状态码差异 |
| 高可用 | 单一物流商故障不影响整体服务，具备自动降级能力 |
| 实时性 | 轨迹更新端到端延迟控制在秒级 |
| 可扩展 | 新增物流商接入成本控制在人天级别 |
| 可追溯 | 全链路操作留痕，异常运单可追溯定责 |

### 2.2 核心域模型

物流系统的核心域对象包括运单（Waybill）、轨迹节点（TrackPoint）、物流商（Carrier）、配送任务（DeliveryTask）。运单是聚合根，轨迹节点作为其内部实体，物流商信息作为值对象引用。

```java
/**
 * 运单聚合根
 */
public class Waybill {
    private String waybillNo;           // 运单号（内部唯一标识）
    private String carrierWaybillNo;    // 物流商侧运单号
    private Long orderId;                // 关联订单
    private CarrierType carrierType;     // 物流商类型
    private WaybillStatus status;        // 统一状态机状态
    private AddressInfo senderAddress;   // 发货地址
    private AddressInfo receiverAddress; // 收货地址
    private List<TrackPoint> trackPoints;// 轨迹节点列表
    private WaybillException exception;  // 异常信息（丢件/破损/拒收）
    private Long createTime;
    private Long updateTime;

    /**
     * 状态流转的唯一入口，禁止外部直接 setStatus
     */
    public void transitTo(WaybillStatus target, TrackPoint point) {
        WaybillStateMachine.validate(this.status, target);
        this.status = target;
        this.trackPoints.add(point);
        this.updateTime = System.currentTimeMillis();
    }
}
```

### 2.3 技术选型概览

| 组件 | 选型 | 选型理由 |
|------|------|---------|
| 运单主库 | MySQL 分库分表 | 强一致性要求，按运单号哈希分片支撑海量写入 |
| 轨迹缓存 | Redis | 高频读取场景，最新轨迹节点需要毫秒级响应 |
| 轨迹明细存储 | 时序数据库/宽表 | 轨迹是典型的时间序列数据，按时间范围查询效率高 |
| 异步解耦 | 消息队列 | 轨迹回调、状态变更通知需要削峰填谷，避免物流商回调压垮系统 |
| 适配层 | 适配器模式 + SPI | 屏蔽多物流商协议差异，支持动态插拔 |
| 路由规划 | 图算法 + 启发式搜索 | 配送路径规划本质是带约束的最短路径问题 |

## 三、核心链路设计

物流系统的核心链路可以拆解为六大环节：运单创建、多物流商适配、状态机驱动的生命周期管理、轨迹采集与缓存、配送路由规划、异常运单处理。下面逐一展开每一步的问题、方案、技术选型理由与代码实现。

### 3.1 运单创建链路

#### 3.1.1 问题分析

运单创建是整个物流链路的起点，需要解决的问题是：如何在不感知具体物流商接口差异的前提下，完成运单号生成、地址校验、物流商选择、下发调用这一系列动作，并且保证幂等——同一个订单不能被重复创建两次运单。

#### 3.1.2 方案设计：适配器模式统一多物流商接口

第一步，定义统一的物流商接口协议，所有物流商适配器都必须实现这个接口，业务层只依赖接口，不依赖具体实现：

```java
/**
 * 统一物流商接口 —— 所有物流商适配器的契约
 */
public interface CarrierAdapter {

    /**
     * 创建运单，返回统一格式的运单结果
     */
    CarrierCreateResult createWaybill(WaybillCreateRequest request);

    /**
     * 取消运单
     */
    boolean cancelWaybill(String carrierWaybillNo);

    /**
     * 主动查询轨迹（用于回调缺失时的兜底补偿）
     */
    List<CarrierTrackPoint> queryTrack(String carrierWaybillNo);

    /**
     * 标识该适配器支持的物流商类型
     */
    CarrierType supportType();
}
```

第二步，为每个物流商实现具体适配器，将物流商私有协议转换为统一模型。这里以两个物流商为例，展示适配器如何屏蔽差异：

```java
/**
 * 物流商 A 适配器实现
 * 物流商 A 使用 XML 报文 + MD5 签名
 */
@Component
public class CarrierAAdapter implements CarrierAdapter {

    @Autowired
    private CarrierAHttpClient httpClient;

    @Override
    public CarrierCreateResult createWaybill(WaybillCreateRequest request) {
        // 1. 将统一请求模型转换为物流商 A 的私有 XML 报文格式
        CarrierAXmlRequest xmlRequest = convertToCarrierAFormat(request);
        // 2. 按物流商 A 的规则生成签名
        String sign = signWithMd5(xmlRequest, "carrierA_secret_key");
        xmlRequest.setSign(sign);
        // 3. 调用物流商 A 的 HTTP 接口
        CarrierAXmlResponse response = httpClient.post(xmlRequest);
        // 4. 将私有响应转换为统一结果模型，屏蔽差异
        return CarrierCreateResult.builder()
                .success(response.getCode() == 0)
                .carrierWaybillNo(response.getWaybillNo())
                .estimatedPickupTime(response.getPickupTime())
                .build();
    }

    @Override
    public boolean cancelWaybill(String carrierWaybillNo) {
        return httpClient.cancel(carrierWaybillNo);
    }

    @Override
    public List<CarrierTrackPoint> queryTrack(String carrierWaybillNo) {
        CarrierATrackResponse resp = httpClient.queryTrack(carrierWaybillNo);
        // 将物流商 A 私有的轨迹状态码映射为统一状态枚举
        return resp.getTracks().stream()
                .map(t -> CarrierTrackPoint.builder()
                        .rawStatus(t.getStatusCode())
                        .unifiedStatus(CarrierAStatusMapping.map(t.getStatusCode()))
                        .location(t.getLocation())
                        .occurTime(t.getTime())
                        .build())
                .collect(Collectors.toList());
    }

    @Override
    public CarrierType supportType() {
        return CarrierType.CARRIER_A;
    }

    private CarrierAXmlRequest convertToCarrierAFormat(WaybillCreateRequest request) {
        // 字段映射逻辑，例如统一模型的 receiverPhone 映射为物流商 A 的 rec_mobile
        // ...省略具体映射代码
        return new CarrierAXmlRequest();
    }

    private String signWithMd5(Object obj, String secretKey) {
        // MD5 签名实现
        return DigestUtils.md5Hex(JSON.toJSONString(obj) + secretKey);
    }
}
```

```java
        return HmacUtils.hmacSha256Hex(key, JSON.toJSONString(obj));
```

第三步，用工厂模式统一管理所有适配器，业务层通过物流商类型动态获取对应实现，新增物流商时只需新增一个适配器类并注册，不需要改动任何已有代码，符合开闭原则：

```java
/**
 * 适配器工厂，基于 Spring 自动注入所有实现类完成注册
 */
@Component
public class CarrierAdapterFactory {

    private final Map<CarrierType, CarrierAdapter> adapterMap = new ConcurrentHashMap<>();

    @Autowired
    public CarrierAdapterFactory(List<CarrierAdapter> adapters) {
        // Spring 启动时自动收集所有 CarrierAdapter 实现类
        for (CarrierAdapter adapter : adapters) {
            adapterMap.put(adapter.supportType(), adapter);
        }
    }

    public CarrierAdapter getAdapter(CarrierType type) {
        CarrierAdapter adapter = adapterMap.get(type);
        if (adapter == null) {
            throw new UnsupportedCarrierException("不支持的物流商类型: " + type);
        }
        return adapter;
    }
}
```

#### 3.1.3 幂等设计与创建主流程

运单创建必须保证幂等，核心手段是利用数据库唯一索引 + 分布式锁双重保护。以订单号作为幂等键，先加锁再判断是否已存在运单，避免并发场景下重复下发：

```java
/**
 * 运单创建服务，串联幂等校验、地址校验、路由选择、适配器调用、落库
 */
@Service
public class WaybillCreateService {

    @Autowired
    private CarrierAdapterFactory adapterFactory;
    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private RedissonClient redissonClient;
    @Autowired
    private CarrierRouteSelector routeSelector;
    @Autowired
    private WaybillIdGenerator idGenerator;

    public WaybillCreateResponse createWaybill(WaybillCreateRequest request) {
        String lockKey = "waybill:create:lock:" + request.getOrderId();
        RLock lock = redissonClient.getLock(lockKey);
        boolean locked = false;
        try {
            // 第一步：加锁，防止同一订单并发创建多个运单
            locked = lock.tryLock(3, 10, TimeUnit.SECONDS);
            if (!locked) {
                throw new ConcurrentCreateException("运单创建请求正在处理，请勿重复提交");
            }

            // 第二步：幂等校验，若已存在有效运单直接返回
            Waybill existing = waybillRepository.findByOrderId(request.getOrderId());
            if (existing != null) {
                return WaybillCreateResponse.fromExisting(existing);
            }

            // 第三步：地址合法性校验（收发地址不能为空、不能超出配送范围）
            validateAddress(request);

            // 第四步：路由选择 —— 根据业务规则选择最优物流商
            // 例如：即时性要求高选即时配送商，跨城场景选快递物流商
            CarrierType carrierType = routeSelector.select(request);
            CarrierAdapter adapter = adapterFactory.getAdapter(carrierType);

            // 第五步：生成内部统一运单号（自研发号器，格式：日期+分片位+序列号）
            String waybillNo = idGenerator.generate();

            // 第六步：调用具体物流商适配器完成下发
            CarrierCreateResult result = adapter.createWaybill(request);
            if (!result.isSuccess()) {
                // 下发失败，触发降级到备用物流商（见 3.1.4 节）
                return fallbackToBackupCarrier(request, carrierType);
            }

            // 第七步：构建运单聚合根并持久化，初始状态置为 CREATED
            Waybill waybill = Waybill.builder()
                    .waybillNo(waybillNo)
                    .carrierWaybillNo(result.getCarrierWaybillNo())
                    .orderId(request.getOrderId())
                    .carrierType(carrierType)
                    .status(WaybillStatus.CREATED)
                    .senderAddress(request.getSenderAddress())
                    .receiverAddress(request.getReceiverAddress())
                    .createTime(System.currentTimeMillis())
                    .build();
            waybillRepository.save(waybill);

            // 第八步：发布运单创建事件，供下游（消息通知、数据统计）异步订阅
            publishWaybillCreatedEvent(waybill);

            return WaybillCreateResponse.success(waybill);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new SystemException("获取锁被中断", e);
        } finally {
            if (locked) {
                lock.unlock();
            }
        }
    }

    private void validateAddress(WaybillCreateRequest request) {
        if (request.getReceiverAddress() == null || StringUtils.isBlank(request.getReceiverAddress().getDetail())) {
            throw new InvalidAddressException("收货地址不完整");
        }
    }

    private WaybillCreateResponse fallbackToBackupCarrier(WaybillCreateRequest request, CarrierType failedType) {
        CarrierType backupType = routeSelector.selectBackup(failedType, request);
        CarrierAdapter backupAdapter = adapterFactory.getAdapter(backupType);
        CarrierCreateResult backupResult = backupAdapter.createWaybill(request);
        if (!backupResult.isSuccess()) {
            throw new WaybillCreateFailedException("主备物流商均创建失败，订单号：" + request.getOrderId());
        }
        // ... 构建运单并保存，逻辑同主流程
        return WaybillCreateResponse.success(null);
    }

    private void publishWaybillCreatedEvent(Waybill waybill) {
        // 通过消息队列异步通知下游系统
    }
}
```

这一段设计的关键点：使用分布式锁而非单纯依赖数据库唯一索引，是因为下发物流商接口是一次远程调用，耗时可能达到数百毫秒，如果只依赖唯一索引，并发请求会有多个线程都执行到调用物流商接口这一步，造成物流商侧的重复下单；而加锁可以在校验幂等之前就把并发请求串行化，避免了这种浪费。

### 3.2 运单状态机设计

#### 3.2.1 问题分析

不同物流商的状态码体系完全不同，例如物流商 A 可能用数字状态码 1/2/3，即时配送商可能用字符串阶段名 PICKUP/DELIVERING/DONE。如果业务层直接感知这些私有状态码，前端展示逻辑会写满 if-else，并且新增物流商时前端也要跟着改。

#### 3.2.2 方案设计：统一状态机 + 状态映射表

第一步，定义统一的运单状态枚举，覆盖所有物流商的公共生命周期节点：

```java
/**
 * 统一运单状态枚举
 */
public enum WaybillStatus {
    CREATED(0, "已创建"),
    WAIT_PICKUP(10, "待揽收"),
    PICKED_UP(20, "已揽收"),
    IN_TRANSIT(30, "运输中"),
    ARRIVED_DESTINATION(40, "已到达目的地网点"),
    OUT_FOR_DELIVERY(50, "派送中"),
    SIGNED(60, "已签收"),
    EXCEPTION(70, "异常"),      // 丢件、破损、拒收等
    CANCELLED(80, "已取消"),
    RETURNED(90, "已退回");

    private final int code;
    private final String desc;

    WaybillStatus(int code, String desc) {
        this.code = code;
        this.desc = desc;
    }

    public boolean isTerminal() {
        return this == SIGNED || this == CANCELLED || this == RETURNED;
    }
}
```

第二步，定义状态流转规则表，只有表中登记的流转路径才允许发生，防止因物流商回调乱序或重复回调导致状态被非法篡改：

```java
/**
 * 运单状态机 —— 维护合法的状态流转关系
 */
public class WaybillStateMachine {

    // key: 当前状态, value: 该状态允许流转到的目标状态集合
    private static final Map<WaybillStatus, Set<WaybillStatus>> TRANSITIONS = new EnumMap<>(WaybillStatus.class);

    static {
        TRANSITIONS.put(WaybillStatus.CREATED, EnumSet.of(WaybillStatus.WAIT_PICKUP, WaybillStatus.CANCELLED));
        TRANSITIONS.put(WaybillStatus.WAIT_PICKUP, EnumSet.of(WaybillStatus.PICKED_UP, WaybillStatus.CANCELLED, WaybillStatus.EXCEPTION));
        TRANSITIONS.put(WaybillStatus.PICKED_UP, EnumSet.of(WaybillStatus.IN_TRANSIT, WaybillStatus.EXCEPTION));
        TRANSITIONS.put(WaybillStatus.IN_TRANSIT, EnumSet.of(WaybillStatus.ARRIVED_DESTINATION, WaybillStatus.EXCEPTION));
        TRANSITIONS.put(WaybillStatus.ARRIVED_DESTINATION, EnumSet.of(WaybillStatus.OUT_FOR_DELIVERY, WaybillStatus.EXCEPTION));
        TRANSITIONS.put(WaybillStatus.OUT_FOR_DELIVERY, EnumSet.of(WaybillStatus.SIGNED, WaybillStatus.EXCEPTION, WaybillStatus.RETURNED));
        TRANSITIONS.put(WaybillStatus.EXCEPTION, EnumSet.of(WaybillStatus.IN_TRANSIT, WaybillStatus.OUT_FOR_DELIVERY, WaybillStatus.RETURNED, WaybillStatus.CANCELLED));
        // 终态不允许再流转
        TRANSITIONS.put(WaybillStatus.SIGNED, EnumSet.noneOf(WaybillStatus.class));
        TRANSITIONS.put(WaybillStatus.CANCELLED, EnumSet.noneOf(WaybillStatus.class));
        TRANSITIONS.put(WaybillStatus.RETURNED, EnumSet.noneOf(WaybillStatus.class));
    }

    /**
     * 校验状态流转是否合法，非法流转直接抛异常拦截
     */
    public static void validate(WaybillStatus current, WaybillStatus target) {
        if (current == target) {
            // 幂等场景：重复回调相同状态，直接放行但上层需要做去重不重复处理业务逻辑
            return;
        }
        Set<WaybillStatus> allowedTargets = TRANSITIONS.get(current);
        if (allowedTargets == null || !allowedTargets.contains(target)) {
            throw new IllegalStateTransitionException(
                    String.format("非法状态流转：%s -> %s", current, target));
        }
    }
}
```

### 3.3 轨迹采集与更新链路

#### 3.3.1 问题分析

轨迹数据有两个特点：写多读也多。物流商会通过回调接口持续推送轨迹节点，用户端也会频繁刷新查看最新轨迹。如果每次都直接查数据库，在大促期间数据库压力会非常大；同时轨迹回调可能出现乱序（网络延迟导致晚发生的事件先到达），需要处理时序问题。

#### 3.3.2 方案设计：回调接收 + 消息队列削峰 + 状态机校验 + 缓存双写

轨迹更新的完整数据流：物流商回调 -> 接入层快速响应 -> 消息队列异步处理 -> 状态机校验合法性 -> 落库 -> 更新缓存 -> 触发下游通知。

```java
/**
 * 轨迹回调接收控制器
 * 核心原则：回调接口必须快速返回，避免阻塞物流商的回调队列
 */
@RestController
@RequestMapping("/callback/track")
public class TrackCallbackController {

    @Autowired
    private MessageProducer messageProducer;

    @PostMapping("/{carrierType}")
    public CallbackResponse receiveTrack(@PathVariable String carrierType,
                                          @RequestBody String rawPayload) {
        // 第一步：验签，防止伪造回调
        if (!SignatureValidator.verify(carrierType, rawPayload)) {
            return CallbackResponse.fail("签名校验失败");
        }
        // 第二步：不做任何业务处理，直接将原始报文丢进消息队列，立即返回成功
        // 这样可以保证接口响应时间在毫秒级，避免物流商因超时重复投递回调
        TrackCallbackMessage message = TrackCallbackMessage.builder()
                .carrierType(carrierType)
                .rawPayload(rawPayload)
                .receiveTime(System.currentTimeMillis())
                .build();
        messageProducer.sendAsync("topic.track.callback", message);
        return CallbackResponse.success();
    }
}
```

```java
/**
 * 轨迹消息消费者 —— 真正的业务处理在这里异步完成
 */
@Component
public class TrackCallbackConsumer {

    @Autowired
    private CarrierAdapterFactory adapterFactory;
    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private TrackCacheService trackCacheService;
    @Autowired
    private WaybillExceptionDetector exceptionDetector;

    @MessageListener(topic = "topic.track.callback")
    public void onMessage(TrackCallbackMessage message) {
        try {
            // 第一步：根据物流商类型解析原始报文为统一轨迹模型
            CarrierAdapter adapter = adapterFactory.getAdapter(CarrierType.valueOf(message.getCarrierType()));
            CarrierTrackPoint trackPoint = adapter.parseCallback(message.getRawPayload());

            // 第二步：根据物流商侧运单号找到内部运单
            Waybill waybill = waybillRepository.findByCarrierWaybillNo(trackPoint.getCarrierWaybillNo());
            if (waybill == null) {
                LogUtils.warn("收到未知运单的轨迹回调: {}", trackPoint.getCarrierWaybillNo());
                return;
            }

            // 第三步：时序校验 —— 处理乱序回调问题
            // 如果新到达的轨迹节点发生时间早于已记录的最新节点，说明是延迟到达的旧消息，只做记录不驱动状态流转
            TrackPoint lastPoint = waybill.getLastTrackPoint();
            boolean isOutOfOrder = lastPoint != null && trackPoint.getOccurTime() < lastPoint.getOccurTime();

            TrackPoint newPoint = TrackPoint.builder()
                    .status(trackPoint.getUnifiedStatus())
                    .location(trackPoint.getLocation())
                    .occurTime(trackPoint.getOccurTime())
                    .rawStatus(trackPoint.getRawStatus())
                    .build();

            if (!isOutOfOrder) {
                // 第四步：驱动状态机流转（内部会校验流转合法性）
                waybill.transitTo(trackPoint.getUnifiedStatus(), newPoint);
                waybillRepository.updateStatus(waybill);
            } else {
                // 乱序消息仅作为轨迹历史记录补充，不驱动状态变更
                waybillRepository.appendHistoryTrackOnly(waybill.getWaybillNo(), newPoint);
                LogUtils.info("检测到乱序轨迹回调，仅记录不驱动状态: {}", trackPoint);
            }

            // 第五步：更新缓存，保证用户查询轨迹时能读到最新数据
            trackCacheService.refreshLatestTrack(waybill.getWaybillNo(), newPoint);

            // 第六步：异常检测 —— 判断是否触发异常运单处理（详见 3.5 节）
            exceptionDetector.detect(waybill, newPoint);

        } catch (Exception e) {
            LogUtils.error("轨迹消息处理失败: {}", message, e);
            // 抛出异常触发消息队列重试机制，避免轨迹丢失
            throw new TrackProcessFailedException(e);
        }
    }
}
```

#### 3.3.3 轨迹缓存策略设计

轨迹查询是典型的读多写少场景（虽然写入量也不小，但读取量通常是写入量的数十倍），采用 Redis 缓存最新轨迹节点 + 历史明细走数据库分页查询的组合策略：

```java
/**
 * 轨迹缓存服务
 * 缓存策略：Hash 结构存储运单最新轨迹摘要，List 结构存储最近 N 条轨迹用于快速展示
 */
@Service
public class TrackCacheService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    private static final String LATEST_TRACK_KEY_PREFIX = "track:latest:";
    private static final String RECENT_TRACK_LIST_PREFIX = "track:recent:";
    private static final int RECENT_TRACK_MAX_SIZE = 10;
    private static final long CACHE_EXPIRE_HOURS = 72; // 签收后运单查询频率骤降，缓存无需长期保留

    /**
     * 刷新最新轨迹节点缓存
     */
    public void refreshLatestTrack(String waybillNo, TrackPoint point) {
        String latestKey = LATEST_TRACK_KEY_PREFIX + waybillNo;
        Map<String, String> latestData = new HashMap<>();
        latestData.put("status", point.getStatus().name());
        latestData.put("location", point.getLocation());
        latestData.put("occurTime", String.valueOf(point.getOccurTime()));
        redisTemplate.opsForHash().putAll(latestKey, latestData);
        redisTemplate.expire(latestKey, CACHE_EXPIRE_HOURS, TimeUnit.HOURS);

        // 维护最近 N 条轨迹的有序列表，用于用户端时间线展示，避免每次都查数据库
        String recentKey = RECENT_TRACK_LIST_PREFIX + waybillNo;
        redisTemplate.opsForList().leftPush(recentKey, JSON.toJSONString(point));
        redisTemplate.opsForList().trim(recentKey, 0, RECENT_TRACK_MAX_SIZE - 1);
        redisTemplate.expire(recentKey, CACHE_EXPIRE_HOURS, TimeUnit.HOURS);
    }

    /**
     * 查询轨迹，缓存未命中时回源数据库并重建缓存（Cache Aside 模式）
     */
    public List<TrackPoint> queryRecentTrack(String waybillNo) {
        String recentKey = RECENT_TRACK_LIST_PREFIX + waybillNo;
        List<String> cached = redisTemplate.opsForList().range(recentKey, 0, -1);
        if (CollectionUtils.isNotEmpty(cached)) {
            return cached.stream().map(s -> JSON.parseObject(s, TrackPoint.class)).collect(Collectors.toList());
        }
        // 缓存未命中：从数据库回源，并重建缓存
        List<TrackPoint> fromDb = loadRecentTrackFromDb(waybillNo);
        rebuildCache(waybillNo, fromDb);
        return fromDb;
    }

    private List<TrackPoint> loadRecentTrackFromDb(String waybillNo) {
        // 从数据库按时间倒序取最近 N 条
        return Collections.emptyList(); // 具体实现省略
    }

    private void rebuildCache(String waybillNo, List<TrackPoint> points) {
        String recentKey = RECENT_TRACK_LIST_PREFIX + waybillNo;
        for (TrackPoint point : points) {
            redisTemplate.opsForList().rightPush(recentKey, JSON.toJSONString(point));
        }
        redisTemplate.expire(recentKey, CACHE_EXPIRE_HOURS, TimeUnit.HOURS);
    }
}
```

这里选择 Hash 存储最新节点、List 存储最近 N 条历史，而不是把全部历史轨迹都放进 Redis，原因是历史轨迹数据量会随运单生命周期不断增长，全量缓存既浪费内存也没必要——用户端首屏只需要展示最近若干条即可，更早的历史轨迹通过分页接口回源数据库查询。

### 3.4 配送路由规划链路

#### 3.4.1 问题分析

即时配送场景下，一个配送员可能同时携带多个包裹，需要规划一条访问顺序，既要保证时效（先到期的先送），又要兼顾总配送距离最短。这是一个带时间窗约束的旅行商问题（TSP with Time Windows），在包裹数量较多时精确求解的计算复杂度是指数级的，因此需要采用启发式算法在合理时间内求出近似最优解。

#### 3.4.2 方案设计：最近邻贪心 + 2-opt 局部优化

第一步，使用最近邻贪心算法快速构造一个初始可行解：

```java
/**
 * 配送路由规划服务
 * 核心算法：最近邻贪心构造初始解 + 2-opt 局部搜索优化
 */
@Service
public class DeliveryRouteService {

    /**
     * 为骑手规划配送路径
     * @param currentLocation 骑手当前位置
     * @param tasks 待配送任务列表（每个任务含收货地址、期望送达时间）
     */
    public List<DeliveryTask> planRoute(GeoPoint currentLocation, List<DeliveryTask> tasks) {
        if (tasks.size() <= 1) {
            return tasks;
        }
        // 第一步：最近邻贪心构造初始路径
        List<DeliveryTask> initialRoute = nearestNeighborGreedy(currentLocation, tasks);

        // 第二步：2-opt 局部优化，消除路径交叉，进一步缩短总距离
        List<DeliveryTask> optimizedRoute = twoOptOptimize(currentLocation, initialRoute);

        // 第三步：时间窗校验与调整 —— 若优化后的顺序违反了时效承诺，优先保证时效而非纯距离最优
        return adjustForTimeWindow(currentLocation, optimizedRoute);
    }

    /**
     * 最近邻贪心：每一步都选择离当前点最近的未访问任务
     */
    private List<DeliveryTask> nearestNeighborGreedy(GeoPoint start, List<DeliveryTask> tasks) {
        List<DeliveryTask> remaining = new ArrayList<>(tasks);
        List<DeliveryTask> route = new ArrayList<>();
        GeoPoint current = start;

        while (!remaining.isEmpty()) {
            DeliveryTask nearest = null;
            double minDistance = Double.MAX_VALUE;
            for (DeliveryTask task : remaining) {
                double distance = GeoUtils.haversineDistance(current, task.getReceiverLocation());
                if (distance < minDistance) {
                    minDistance = distance;
                    nearest = task;
                }
            }
            route.add(nearest);
            remaining.remove(nearest);
            current = nearest.getReceiverLocation();
        }
        return route;
    }

    /**
     * 2-opt 优化：反复尝试交换路径中的两段，若交换后总距离变短则接受
     * 时间复杂度 O(n^2) 每轮，通常迭代若干轮即可收敛到局部最优
     */
    private List<DeliveryTask> twoOptOptimize(GeoPoint start, List<DeliveryTask> route) {
        boolean improved = true;
        List<DeliveryTask> best = new ArrayList<>(route);

        while (improved) {
            improved = false;
            for (int i = 0; i < best.size() - 1; i++) {
                for (int j = i + 1; j < best.size(); j++) {
                    List<DeliveryTask> candidate = twoOptSwap(best, i, j);
                    double bestDistance = calculateTotalDistance(start, best);
                    double candidateDistance = calculateTotalDistance(start, candidate);
                    if (candidateDistance < bestDistance) {
                        best = candidate;
                        improved = true;
                    }
                }
            }
        }
        return best;
    }

    private List<DeliveryTask> twoOptSwap(List<DeliveryTask> route, int i, int j) {
        List<DeliveryTask> newRoute = new ArrayList<>(route.subList(0, i));
        List<DeliveryTask> reversed = new ArrayList<>(route.subList(i, j + 1));
        Collections.reverse(reversed);
        newRoute.addAll(reversed);
        newRoute.addAll(route.subList(j + 1, route.size()));
        return newRoute;
    }

    private double calculateTotalDistance(GeoPoint start, List<DeliveryTask> route) {
        double total = 0;
        GeoPoint current = start;
        for (DeliveryTask task : route) {
            total += GeoUtils.haversineDistance(current, task.getReceiverLocation());
            current = task.getReceiverLocation();
        }
        return total;
    }

    /**
     * 时间窗调整：对即将超时的任务提前插队
     */
    private List<DeliveryTask> adjustForTimeWindow(GeoPoint start, List<DeliveryTask> route) {
        long now = System.currentTimeMillis();
        List<DeliveryTask> urgent = route.stream()
                .filter(t -> t.getExpectDeliveryTime() - now < 15 * 60 * 1000) // 剩余不足 15 分钟视为紧急
                .collect(Collectors.toList());
        if (urgent.isEmpty()) {
            return route;
        }
        List<DeliveryTask> normal = route.stream()
                .filter(t -> !urgent.contains(t))
                .collect(Collectors.toList());
        // 紧急任务优先排在前面，牺牲部分总距离最优换取时效达成率
        List<DeliveryTask> adjusted = new ArrayList<>(urgent);
        adjusted.addAll(normal);
        return adjusted;
    }
}
```

选择“最近邻贪心 + 2-opt”而不是动态规划精确求解的原因：骑手实际携带的包裹数一般在个位数到十几个之间，2-opt 在这个规模下能在几毫秒内收敛到一个足够好的近似解，而动态规划的状态空间是 `O(n * 2^n)`，当 n 超过 15 左右计算成本就会显著上升，对于需要实时响应的调度场景不划算。

### 3.5 异常运单处理链路

#### 3.5.1 问题分析

物流链路中异常运单（超时未揽收、长时间无轨迹更新、丢件、破损、拒收）如果不能及时发现，会导致用户投诉集中爆发。异常检测不能靠人工巡检，需要系统化、规则化地自动识别。

#### 3.5.2 方案设计：规则引擎驱动的异常检测 + 状态机接管

```java
/**
 * 运单异常检测器 —— 在每次轨迹更新后被调用，基于规则判断是否触发异常
 */
@Component
public class WaybillExceptionDetector {

    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private ExceptionNotifyService notifyService;

    // 各状态节点允许停留的最长时间（毫秒），超时视为潜在异常
    private static final Map<WaybillStatus, Long> STAGE_TIMEOUT = new EnumMap<>(WaybillStatus.class);
    static {
        STAGE_TIMEOUT.put(WaybillStatus.WAIT_PICKUP, 24 * 3600 * 1000L);      // 24 小时未揽收
        STAGE_TIMEOUT.put(WaybillStatus.IN_TRANSIT, 72 * 3600 * 1000L);       // 72 小时无新轨迹
        STAGE_TIMEOUT.put(WaybillStatus.OUT_FOR_DELIVERY, 24 * 3600 * 1000L); // 派送 24 小时未签收
    }

    public void detect(Waybill waybill, TrackPoint newPoint) {
        // 规则一：轨迹节点本身就是异常上报（如物流商主动上报丢件/破损）
        if (newPoint.getStatus() == WaybillStatus.EXCEPTION) {
            handleReportedException(waybill, newPoint);
            return;
        }
        // 规则二：停留超时检测由定时任务扫描触发，此处仅处理实时上报的异常类型
    }

    private void handleReportedException(Waybill waybill, TrackPoint newPoint) {
        ExceptionType exceptionType = parseExceptionType(newPoint.getRawStatus());
        WaybillException exception = WaybillException.builder()
                .waybillNo(waybill.getWaybillNo())
                .type(exceptionType)
                .occurTime(newPoint.getOccurTime())
                .status(ExceptionHandleStatus.PENDING)
                .build();
        waybillRepository.saveException(exception);

        // 根据异常类型分流处理策略
        switch (exceptionType) {
            case LOST:
                // 丢件：直接触发理赔流程，通知客服介入
                notifyService.notifyLostPackage(waybill, exception);
                break;
            case DAMAGED:
                // 破损：需要拍照留证，走定损流程
                notifyService.notifyDamagedPackage(waybill, exception);
                break;
            case REJECTED:
                // 拒收：判断是否需要走退回流程
                triggerReturnProcess(waybill);
                break;
            default:
                notifyService.notifyGenericException(waybill, exception);
        }
    }

    private void triggerReturnProcess(Waybill waybill) {
        TrackPoint returnPoint = TrackPoint.builder()
                .status(WaybillStatus.RETURNED)
                .occurTime(System.currentTimeMillis())
                .build();
        waybill.transitTo(WaybillStatus.RETURNED, returnPoint);
        waybillRepository.updateStatus(waybill);
    }

    private ExceptionType parseExceptionType(String rawStatus) {
        // 根据物流商上报的具体异常码解析异常类型，具体映射表省略
        return ExceptionType.UNKNOWN;
    }
}
```

超时类异常通过定时任务批量扫描处理，而不是在每次轨迹更新时同步计算，这是因为超时是"没有发生新事件"这一状态本身触发的，无法由事件驱动，只能靠定时轮询：

```java
/**
 * 定时任务：扫描长时间停留在某状态未流转的运单，标记为超时异常
 */
@Component
public class WaybillTimeoutScanJob {

    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private ExceptionNotifyService notifyService;

    @Scheduled(fixedRate = 5 * 60 * 1000) // 每 5 分钟扫描一次
    public void scan() {
        // 分批扫描，避免一次性拉取全量运单造成内存压力和数据库压力
        int pageSize = 500;
        String cursor = null;
        while (true) {
            List<Waybill> batch = waybillRepository.scanActiveWaybills(cursor, pageSize);
            if (batch.isEmpty()) {
                break;
            }
            for (Waybill waybill : batch) {
                checkTimeout(waybill);
            }
            cursor = batch.get(batch.size() - 1).getWaybillNo();
            if (batch.size() < pageSize) {
                break;
            }
        }
    }

    private void checkTimeout(Waybill waybill) {
        Long timeoutThreshold = getTimeoutThreshold(waybill.getStatus());
        if (timeoutThreshold == null) {
            return;
        }
        long stayDuration = System.currentTimeMillis() - waybill.getUpdateTime();
        if (stayDuration > timeoutThreshold) {
            notifyService.notifyTimeoutException(waybill, stayDuration);
        }
    }

    private Long getTimeoutThreshold(WaybillStatus status) {
        Map<WaybillStatus, Long> thresholds = new EnumMap<>(WaybillStatus.class);
        thresholds.put(WaybillStatus.WAIT_PICKUP, 24 * 3600 * 1000L);
        thresholds.put(WaybillStatus.IN_TRANSIT, 72 * 3600 * 1000L);
        thresholds.put(WaybillStatus.OUT_FOR_DELIVERY, 24 * 3600 * 1000L);
        return thresholds.get(status);
    }
}
```

## 四、异常处理与容错机制

### 4.1 物流商接口调用容错

物流商作为外部依赖，其接口稳定性不受自身系统控制，必须设计完善的容错机制：

```java
/**
 * 物流商接口调用的容错封装
 * 组合使用超时控制、重试、熔断三种手段
 */
@Component
public class CarrierApiCircuitBreaker {

    private final Map<CarrierType, CircuitBreaker> breakers = new ConcurrentHashMap<>();

    public CarrierApiCircuitBreaker() {
        // 每个物流商独立熔断，避免一家故障影响其他物流商调用
    }

    public <T> T callWithProtection(CarrierType type, Supplier<T> apiCall, Supplier<T> fallback) {
        CircuitBreaker breaker = breakers.computeIfAbsent(type, t ->
                CircuitBreaker.ofDefaults(t.name()));

        return breaker.executeSupplier(() -> {
            try {
                // 设置接口调用超时时间，避免线程被慢接口拖死
                return TimeLimiter.of(Duration.ofSeconds(3))
                        .executeFutureSupplier(() -> CompletableFuture.supplyAsync(apiCall));
            } catch (Exception e) {
                LogUtils.error("物流商[{}]接口调用失败", type, e);
                throw e;
            }
        });
    }
}
```

```java
    @Autowired
    private StringRedisTemplate redisTemplate;

        Boolean result = redisTemplate.opsForValue().setIfAbsent(
```

## 五、性能优化

### 5.1 分库分表策略

运单数据量级达到千万到亿级别时，单表已无法支撑，需要按运单号做哈希分片：

```java
/**
 * 分库分表路由策略：按运单号后两位哈希取模
 */
public class WaybillShardingStrategy {

    private static final int SHARD_COUNT = 32;

    public static String getTableSuffix(String waybillNo) {
        int hash = waybillNo.hashCode();
        int shard = Math.abs(hash) % SHARD_COUNT;
        return String.format("%02d", shard);
    }
}
```

运单主表按运单号分片，轨迹明细表则同时按运单号分片并结合时间做冷热数据分离——近 3 个月的轨迹放在热表，更早的归档到冷表或转存到对象存储，降低热表数据量。

### 5.2 查询链路优化：多级缓存

用户查询轨迹的请求量远大于轨迹写入量，构建多级缓存体系：

```
本地缓存(Caffeine, 秒级TTL) -> Redis 缓存(小时级TTL) -> 数据库
```

```java
/**
 * 多级缓存查询封装
 */
@Service
public class TrackQueryService {

    private final Cache<String, TrackSummary> localCache = Caffeine.newBuilder()
            .maximumSize(100_000)
            .expireAfterWrite(5, TimeUnit.SECONDS)
            .build();

    @Autowired
    private TrackCacheService trackCacheService;

    public TrackSummary query(String waybillNo) {
        // 第一层：本地缓存，应对短时间内的重复刷新请求
        TrackSummary cached = localCache.getIfPresent(waybillNo);
        if (cached != null) {
            return cached;
        }
        // 第二层：Redis 缓存
        TrackSummary fromRedis = trackCacheService.queryLatestSummary(waybillNo);
        if (fromRedis != null) {
            localCache.put(waybillNo, fromRedis);
            return fromRedis;
        }
        // 第三层：数据库兜底
        TrackSummary fromDb = loadFromDatabase(waybillNo);
        trackCacheService.refreshLatestTrack(waybillNo, fromDb.toTrackPoint());
        localCache.put(waybillNo, fromDb);
        return fromDb;
    }

    private TrackSummary loadFromDatabase(String waybillNo) {
        return null; // 具体实现省略
    }
}
```

### 5.4 轨迹写入批量合并

高频轨迹上报场景（如即时配送骑手每几秒上报一次位置）没有必要每次都写数据库，可以先写 Redis，再通过定时任务批量落库：

```java
/**
 * 轨迹写入批量合并：先写缓冲区，定时批量刷盘
 */
@Component
public class TrackBatchFlusher {

    private final BlockingQueue<TrackPoint> buffer = new LinkedBlockingQueue<>(10000);

    @Autowired
    private WaybillRepository waybillRepository;

    public void offer(TrackPoint point) {
        if (!buffer.offer(point)) {
            LogUtils.warn("轨迹缓冲队列已满，触发同步落库降级");
            waybillRepository.batchInsertTrack(Collections.singletonList(point));
        }
    }

    @Scheduled(fixedRate = 1000) // 每秒批量刷盘一次
    public void flush() {
        List<TrackPoint> batch = new ArrayList<>();
        buffer.drainTo(batch, 500);
        if (!batch.isEmpty()) {
            waybillRepository.batchInsertTrack(batch);
        }
    }
}
```

## 六、最佳实践与总结

### 6.1 设计原则回顾

1. **适配器模式解耦多物流商差异**：业务层只依赖统一接口，新增物流商不需要改动核心代码，符合开闭原则。
2. **统一状态机屏蔽私有状态码**：所有物流商的私有状态都要经过映射层转换为统一状态，状态流转必须经过状态机校验，避免非法跳变。
3. **异步化处理外部回调**：回调接口只做验签和入队，真正的业务逻辑放到消息消费端异步处理，保证接口响应时间可控。
4. **多重容错兜底**：熔断保护物流商接口调用、补偿任务应对回调丢失、幂等校验应对重复消费，三层机制共同保证系统健壮性。
5. **冷热数据分离**：轨迹数据具有明显的时间衰减访问特征，近期数据放缓存和热表，历史数据归档，兼顾性能与成本。

### 6.2 常见坑位总结

| 坑位 | 现象 | 解决方案 |
|------|------|---------|
| 状态回退 | 物流商回调乱序，导致运单状态从"已签收"又跳回"运输中" | 引入时序校验，比较事件发生时间而非到达时间 |
| 重复创建运单 | 高并发下单场景，同一订单创建了多个运单 | 分布式锁 + 数据库唯一索引双重幂等保护 |
| 回调风暴 | 大促期间物流商回调集中到达压垮系统 | 回调接口快速入队，消息队列削峰填谷 |
| 轨迹丢失 | 物流商回调偶发丢失，运单状态长期卡在中间态 | 定时补偿任务主动查询长时间无更新的运单 |
| 缓存雪崩 | 大量运单缓存同时过期，瞬时全部穿透到数据库 | 缓存过期时间加随机抖动，避免同一时刻集中失效 |

### 6.3 容量评估参考

设计物流系统时，建议按以下维度提前评估容量：

- **运单创建 QPS**：按日常峰值的 3-5 倍预留余量，用于应对大促场景。
- **轨迹回调 QPS**：通常是运单量的数倍到数十倍（一个运单在生命周期内会产生多条轨迹），需要重点评估消息队列的吞吐能力。
- **存储容量**：轨迹明细表增长速度远快于运单主表，需要设计好归档策略，避免热表无限膨胀影响查询性能。

物流系统作为连接交易与履约的关键基础设施，其架构设计的核心矛盾在于：既要面对外部多物流商的异构性，又要对内提供统一、稳定、可预测的服务契约。通过适配器模式、统一状态机、异步化处理和多层次容错机制的组合应用，可以在保证系统稳定性的同时，具备良好的横向扩展能力。

## 七、全链路实战案例

前面几章分别拆解了物流系统各个子链路的设计要点，本章从"端到端"视角还原三个最典型的实战场景：商家发货触发运单创建、快递回调驱动轨迹更新、以及物流停滞后的异常自愈处理。每个案例都会给出从入口 Controller 到底层持久化的完整调用链，并重点标注异常处理、日志埋点与幂等控制的落地方式。

### 7.1 案例一：订单发货与物流单创建全链路

#### 7.1.1 业务场景与链路概览

商家在商家后台点击"发货"按钮，录入快递公司与运单号后提交，系统需要完成：参数校验 -> 订单状态流转 -> 创建物流追踪单 -> 订阅物流商轨迹推送 -> 通知用户，全程要求接口幂等（重复点击发货不能产生副作用），并对运单号无效、订单已发货等异常场景给出明确反馈。

```
商家点击发货
    │
    ▼
ShipmentController.ship()  ──▶ 参数校验（订单号/快递公司/运单号格式）
    │
    ▼
幂等校验（Redis 分布式锁 + 订单发货状态双重保护）
    │
    ▼
订单状态流转：待发货 -> 已发货（状态机校验 + 乐观锁更新）
    │
    ▼
创建物流追踪单（Waybill 落库，初始状态 CREATED）
    │
    ▼
订阅物流商轨迹推送（调用物流商开放平台的"运单订阅"接口）
    │
    ▼
发货通知（异步：短信 + App 推送，失败不阻塞主流程）
```

#### 7.1.2 Controller 入口与参数校验

发货接口作为商家后台的核心写操作，入参校验必须在 Controller 层就拦截绝大部分非法请求，避免脏数据流入后续业务逻辑：

```java
/**
 * 商家发货接口
 * 入口原则：快速失败 —— 参数问题在最外层拦截，不把校验逻辑下沉到 Service 内部
 */
@RestController
@RequestMapping("/merchant/shipment")
public class ShipmentController {

    private static final Logger log = LoggerFactory.getLogger(ShipmentController.class);

    @Autowired
    private ShipmentService shipmentService;

    @PostMapping("/ship")
    public Result<ShipmentResponse> ship(@RequestBody ShipmentRequest request,
                                          @RequestHeader("X-Merchant-Id") Long merchantId) {
        // 第一步：基础参数非空校验
        ParamCheckResult checkResult = validateParams(request);
        if (!checkResult.isPass()) {
            log.warn("[发货] 参数校验失败, merchantId={}, request={}, reason={}",
                    merchantId, request, checkResult.getReason());
            return Result.fail(ErrorCode.PARAM_INVALID, checkResult.getReason());
        }

        // 第二步：快递公司枚举合法性校验，防止前端传入未接入的物流商编码
        if (!CarrierType.isSupported(request.getCarrierCode())) {
            log.warn("[发货] 不支持的快递公司编码, merchantId={}, carrierCode={}",
                    merchantId, request.getCarrierCode());
            return Result.fail(ErrorCode.CARRIER_NOT_SUPPORTED, "暂不支持该快递公司");
        }

        // 第三步：运单号格式校验（不同物流商运单号规则不同，走各自的正则规则）
        if (!WaybillNoFormatValidator.isValid(request.getCarrierCode(), request.getCarrierWaybillNo())) {
            log.warn("[发货] 运单号格式非法, merchantId={}, carrierWaybillNo={}",
                    merchantId, request.getCarrierWaybillNo());
            return Result.fail(ErrorCode.WAYBILL_NO_INVALID, "运单号格式不正确，请核对后重新填写");
        }

        try {
            ShipmentResponse response = shipmentService.ship(merchantId, request);
            return Result.success(response);
        } catch (DuplicateShipmentException e) {
            // 重复发货是可预期的业务异常，不打 error 级别日志，避免误报警
            log.info("[发货] 订单重复发货请求已拦截, orderId={}, msg={}", request.getOrderId(), e.getMessage());
            return Result.fail(ErrorCode.DUPLICATE_SHIPMENT, e.getMessage());
        } catch (InvalidWaybillNoException e) {
            log.warn("[发货] 运单号校验未通过, orderId={}, msg={}", request.getOrderId(), e.getMessage());
            return Result.fail(ErrorCode.WAYBILL_NO_INVALID, e.getMessage());
        } catch (OrderStatusNotAllowShipException e) {
            log.warn("[发货] 订单状态不允许发货, orderId={}, currentStatus={}",
                    request.getOrderId(), e.getCurrentStatus());
            return Result.fail(ErrorCode.ORDER_STATUS_ILLEGAL, e.getMessage());
        } catch (Exception e) {
            log.error("[发货] 系统异常, merchantId={}, orderId={}", merchantId, request.getOrderId(), e);
            return Result.fail(ErrorCode.SYSTEM_ERROR, "发货失败，请稍后重试");
        }
    }

    private ParamCheckResult validateParams(ShipmentRequest request) {
        if (request.getOrderId() == null) {
            return ParamCheckResult.fail("订单号不能为空");
        }
        if (StringUtils.isBlank(request.getCarrierCode())) {
            return ParamCheckResult.fail("快递公司不能为空");
        }
        if (StringUtils.isBlank(request.getCarrierWaybillNo())) {
            return ParamCheckResult.fail("运单号不能为空");
        }
        if (request.getCarrierWaybillNo().length() > 64) {
            return ParamCheckResult.fail("运单号长度超出限制");
        }
        return ParamCheckResult.pass();
    }
}
```

#### 7.1.3 发货主流程：状态流转 + 运单创建 + 幂等控制

发货流程涉及订单表与运单表两处写入，需要保证"要么都成功、要么都不生效"，同时要防御"商家网络抖动重复点击发货按钮"这种典型幂等场景：

```java
/**
 * 发货服务：串联订单状态流转、运单创建、轨迹订阅、通知发送
 */
@Service
public class ShipmentService {

    private static final Logger log = LoggerFactory.getLogger(ShipmentService.class);

    @Autowired
    private OrderRepository orderRepository;
    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private CarrierAdapterFactory adapterFactory;
    @Autowired
    private RedissonClient redissonClient;
    @Autowired
    private WaybillIdGenerator idGenerator;
    @Autowired
    private ShipmentNotifyService notifyService;
    @Autowired
    private MessageProducer messageProducer;

    @Transactional(rollbackFor = Exception.class)
    public ShipmentResponse ship(Long merchantId, ShipmentRequest request) {
        String idempotentKey = "shipment:lock:" + request.getOrderId();
        RLock lock = redissonClient.getLock(idempotentKey);
        boolean locked = false;
        try {
            // 第一步：加锁，防止同一订单并发发货请求同时穿透
            locked = lock.tryLock(3, 10, TimeUnit.SECONDS);
            if (!locked) {
                log.warn("[发货] 获取发货锁失败，可能存在并发重复提交, orderId={}", request.getOrderId());
                throw new DuplicateShipmentException("发货请求正在处理，请勿重复提交");
            }

            // 第二步：查询订单并做归属校验，防止越权操作他人订单
            Order order = orderRepository.findById(request.getOrderId());
            if (order == null) {
                throw new OrderNotFoundException("订单不存在: " + request.getOrderId());
            }
            if (!Objects.equals(order.getMerchantId(), merchantId)) {
                log.warn("[发货] 商家越权发货尝试, merchantId={}, orderMerchantId={}, orderId={}",
                        merchantId, order.getMerchantId(), request.getOrderId());
                throw new PermissionDeniedException("无权操作该订单");
            }

            // 第三步：幂等校验 —— 订单已处于已发货及之后状态，视为重复发货，直接返回已有结果
            if (order.getStatus() == OrderStatus.SHIPPED || order.getStatus().isAfterShipped()) {
                Waybill existing = waybillRepository.findByOrderId(request.getOrderId());
                log.info("[发货] 订单已发货，幂等返回已有运单, orderId={}, waybillNo={}",
                        request.getOrderId(), existing == null ? "null" : existing.getWaybillNo());
                return ShipmentResponse.fromExisting(order, existing);
            }

            // 第四步：订单状态合法性校验，只有"待发货"状态才允许发货
            if (order.getStatus() != OrderStatus.WAIT_SHIP) {
                throw new OrderStatusNotAllowShipException(order.getStatus(),
                        "订单当前状态[" + order.getStatus().getDesc() + "]不允许发货");
            }

            // 第五步：运单号有效性校验 —— 调用物流商接口做真实性核验，防止商家随意填写虚假单号
            CarrierType carrierType = CarrierType.of(request.getCarrierCode());
            CarrierAdapter adapter = adapterFactory.getAdapter(carrierType);
            boolean waybillValid = validateCarrierWaybillNo(adapter, request.getCarrierWaybillNo());
            if (!waybillValid) {
                log.warn("[发货] 运单号未通过物流商侧核验, orderId={}, carrierCode={}, waybillNo={}",
                        request.getOrderId(), request.getCarrierCode(), request.getCarrierWaybillNo());
                throw new InvalidWaybillNoException("运单号无效，请核对快递公司与运单号是否匹配");
            }

            // 第六步：订单状态流转，使用乐观锁防止并发更新覆盖
            int updated = orderRepository.updateStatusWithVersion(
                    order.getOrderId(), OrderStatus.WAIT_SHIP, OrderStatus.SHIPPED, order.getVersion());
            if (updated == 0) {
                // 乐观锁更新失败，说明订单状态已被其他线程并发修改，属于典型的竞态场景
                log.warn("[发货] 订单状态乐观锁更新失败，存在并发修改, orderId={}", request.getOrderId());
                throw new DuplicateShipmentException("订单状态已变更，请刷新后重试");
            }

            // 第七步：创建物流追踪单，初始状态置为 CREATED
            String waybillNo = idGenerator.generate();
            Waybill waybill = Waybill.builder()
                    .waybillNo(waybillNo)
                    .carrierWaybillNo(request.getCarrierWaybillNo())
                    .orderId(request.getOrderId())
                    .carrierType(carrierType)
                    .status(WaybillStatus.CREATED)
                    .senderAddress(order.getSenderAddress())
                    .receiverAddress(order.getReceiverAddress())
                    .createTime(System.currentTimeMillis())
                    .build();
            waybillRepository.save(waybill);
            log.info("[发货] 物流追踪单创建成功, orderId={}, waybillNo={}, carrierCode={}",
                    request.getOrderId(), waybillNo, request.getCarrierCode());

            // 第八步：订阅物流商轨迹推送（部分物流商需要显式订阅才会推送回调）
            subscribeCarrierTrackPush(adapter, waybill);

            // 第九步：本地事务内落地"待发送通知"事件，事务提交后由监听器异步发出，避免事务未提交就通知用户
            publishShipmentSucceedEvent(order, waybill);

            return ShipmentResponse.success(order, waybill);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("[发货] 获取分布式锁被中断, orderId={}", request.getOrderId(), e);
            throw new SystemException("发货处理被中断，请重试", e);
        } finally {
            if (locked) {
                lock.unlock();
            }
        }
    }

    /**
     * 调用物流商接口核验运单号真实性，避免商家误填或恶意填写不存在的运单号
     */
    private boolean validateCarrierWaybillNo(CarrierAdapter adapter, String carrierWaybillNo) {
        try {
            List<CarrierTrackPoint> tracks = adapter.queryTrack(carrierWaybillNo);
            // 部分物流商对全新运单号查询轨迹会返回空列表而非报错，空列表也视为有效（尚未产生轨迹）
            return tracks != null;
        } catch (CarrierWaybillNotFoundException e) {
            return false;
        } catch (Exception e) {
            // 物流商接口抖动导致校验失败时，不应武断判定运单号无效，记录告警后放行，交由后续轨迹回调兜底
            log.warn("[发货] 运单号校验接口异常，降级放行, carrierWaybillNo={}", carrierWaybillNo, e);
            return true;
        }
    }

    private void subscribeCarrierTrackPush(CarrierAdapter adapter, Waybill waybill) {
        try {
            adapter.subscribeTrackPush(waybill.getCarrierWaybillNo());
        } catch (Exception e) {
            // 订阅失败不阻塞发货主流程，记录日志后交由轨迹补偿任务（见 4.2 节）主动查询兜底
            log.error("[发货] 订阅物流商轨迹推送失败，将依赖补偿任务兜底, waybillNo={}", waybill.getWaybillNo(), e);
        }
    }

    private void publishShipmentSucceedEvent(Order order, Waybill waybill) {
        // 借助 Spring 事务同步机制，保证事件在事务提交后才被处理，避免"通知已发但事务回滚"的不一致场景
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronizationAdapter() {
            @Override
            public void afterCommit() {
                ShipmentSucceedEvent event = new ShipmentSucceedEvent(order.getOrderId(),
                        order.getUserId(), waybill.getWaybillNo(), waybill.getCarrierType());
                messageProducer.sendAsync("topic.shipment.succeed", event);
            }
        });
    }
}
```

#### 7.1.4 发货通知：异步短信与 App 推送

通知类操作对实时性要求不高但对主流程稳定性要求高，必须异步化并做好失败重试与日志埋点：

```java
/**
 * 发货成功通知消费者：短信 + App 推送双通道，互不阻塞
 */
@Component
public class ShipmentNotifyConsumer {

    private static final Logger log = LoggerFactory.getLogger(ShipmentNotifyConsumer.class);

    @Autowired
    private SmsService smsService;
    @Autowired
    private PushService pushService;
    @Autowired
    private IdempotentChecker idempotentChecker;

    @MessageListener(topic = "topic.shipment.succeed")
    public void onMessage(ShipmentSucceedEvent event) {
        // 消息可能因消费失败重试，通过幂等键防止重复发送通知打扰用户
        String idempotentKey = "notify:shipment:" + event.getWaybillNo();
        if (!idempotentChecker.isProcessed(idempotentKey)) {
            log.info("[发货通知] 检测到重复消息，跳过处理, waybillNo={}", event.getWaybillNo());
            return;
        }

        // 短信通知：失败不影响推送通道，两者独立捕获异常
        try {
            smsService.sendShipmentSms(event.getUserId(), event.getWaybillNo(), event.getCarrierType());
            log.info("[发货通知] 短信发送成功, userId={}, waybillNo={}", event.getUserId(), event.getWaybillNo());
        } catch (Exception e) {
            log.error("[发货通知] 短信发送失败, userId={}, waybillNo={}", event.getUserId(), event.getWaybillNo(), e);
        }

        // App 推送
        try {
            pushService.pushShipmentNotice(event.getUserId(), event.getWaybillNo());
            log.info("[发货通知] App推送发送成功, userId={}, waybillNo={}", event.getUserId(), event.getWaybillNo());
        } catch (Exception e) {
            log.error("[发货通知] App推送发送失败, userId={}, waybillNo={}", event.getUserId(), event.getWaybillNo(), e);
        }
    }
}
```

#### 7.1.5 异常场景处理小结

| 异常场景 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 运单号无效 | 物流商侧核验运单号不存在 | 抛 `InvalidWaybillNoException`，提示商家核对；物流商接口抖动时降级放行，避免误伤正常发货 |
| 重复发货 | 短时间内重复点击发货按钮，或订单已处于已发货状态 | 分布式锁拦截并发请求 + 订单状态幂等判断，重复请求直接返回已有运单结果，不产生副作用 |
| 并发状态竞争 | 极端场景下锁与状态判断之间发生了状态变化 | 乐观锁（version 字段）兜底，更新影响行数为 0 视为竞态失败，抛出异常提示重试 |
| 轨迹订阅失败 | 物流商开放平台订阅接口临时不可用 | 不阻塞发货主流程，记录日志，依赖轨迹补偿定时任务后续主动查询轨迹 |
| 通知发送失败 | 短信网关或推送网关异常 | 通知走异步消息通道，短信与推送两个通道独立容错，互不影响，也不影响发货结果 |

### 7.2 案例二：物流轨迹更新与推送全链路

#### 7.2.1 业务场景与链路概览

快递公司在包裹揽收、运输、派送、签收等关键节点会通过回调接口主动推送轨迹信息，系统需要在接到回调后完成鉴权解析、轨迹入库、关键节点识别、用户端实时推送，并在签收节点触发"超时自动确认收货"的延迟任务，同时对长时间无新轨迹的运单发出超时预警。

```
快递公司回调
    │
    ▼
TrackPushCallbackController  ──▶ 回调鉴权（验签）+ 报文解析
    │
    ▼
幂等去重（同一轨迹事件重复推送直接丢弃）
    │
    ▼
轨迹入库（追加模式，不覆盖历史轨迹）
    │
    ▼
关键节点识别（揽件/运输中/派送中/签收）
    │
    ├──▶ 用户端实时推送（WebSocket/长连接 + App 推送兜底）
    │
    └──▶ 若为"签收"节点 ──▶ 投递延迟任务：N 天后自动确认收货
    │
    ▼
（定时任务）物流超时预警：长时间无新轨迹的运单主动告警
```

#### 7.2.2 回调鉴权与数据解析

回调接口是外部系统主动调用的入口，安全性要求最高，必须做严格的验签，同时要保证接口响应足够快，避免拖慢物流商的回调队列：

```java
/**
 * 快递公司轨迹推送回调入口
 * 设计原则：验签 + 最小化处理 + 快速返回，真正业务逻辑放到异步消费端
 */
@RestController
@RequestMapping("/callback/carrier")
public class TrackPushCallbackController {

    private static final Logger log = LoggerFactory.getLogger(TrackPushCallbackController.class);

    @Autowired
    private MessageProducer messageProducer;
    @Autowired
    private IdempotentChecker idempotentChecker;

    @PostMapping("/{carrierCode}/track/push")
    public CallbackResponse onTrackPush(@PathVariable String carrierCode,
                                         @RequestHeader Map<String, String> headers,
                                         @RequestBody String rawPayload) {
        String traceId = UUID.randomUUID().toString();
        try {
            // 第一步：回调鉴权 —— 校验签名，防止伪造回调污染数据
            boolean signValid = SignatureValidator.verify(carrierCode, headers, rawPayload);
            if (!signValid) {
                log.warn("[轨迹回调][{}] 验签失败, carrierCode={}, headers={}", traceId, carrierCode, headers);
                // 验签失败返回 4xx 而非 5xx，避免物流商误判为系统故障而无限重试
                return CallbackResponse.fail("SIGN_INVALID", "签名校验失败");
            }

            // 第二步：报文格式解析，先做基础的 JSON/XML 合法性校验，防止脏数据进入队列
            if (StringUtils.isBlank(rawPayload)) {
                log.warn("[轨迹回调][{}] 回调报文为空, carrierCode={}", traceId, carrierCode);
                return CallbackResponse.fail("PAYLOAD_EMPTY", "回调报文为空");
            }

            // 第三步：回调层幂等去重 —— 依据物流商提供的事件唯一 ID（如无则用 报文摘要）
            String eventId = extractEventId(carrierCode, rawPayload);
            String idempotentKey = "callback:raw:" + carrierCode + ":" + eventId;
            if (!idempotentChecker.isProcessed(idempotentKey)) {
                log.info("[轨迹回调][{}] 重复回调已拦截, carrierCode={}, eventId={}", traceId, carrierCode, eventId);
                // 重复回调也要返回成功，避免物流商因为收不到成功响应而持续重试
                return CallbackResponse.success();
            }

            // 第四步：不做业务处理，直接入队，保证接口毫秒级响应
            TrackCallbackMessage message = TrackCallbackMessage.builder()
                    .traceId(traceId)
                    .carrierType(carrierCode)
                    .rawPayload(rawPayload)
                    .eventId(eventId)
                    .receiveTime(System.currentTimeMillis())
                    .build();
            messageProducer.sendAsync("topic.track.callback", message);

            log.info("[轨迹回调][{}] 接收成功并已入队, carrierCode={}, eventId={}", traceId, carrierCode, eventId);
            return CallbackResponse.success();
        } catch (Exception e) {
            log.error("[轨迹回调][{}] 处理异常, carrierCode={}", traceId, carrierCode, e);
            // 系统异常返回失败，触发物流商侧的重试机制，保证消息不丢
            return CallbackResponse.fail("SYSTEM_ERROR", "系统繁忙，请稍后重试");
        }
    }

    private String extractEventId(String carrierCode, String rawPayload) {
        String eventId = CallbackEventIdExtractor.extract(carrierCode, rawPayload);
        if (StringUtils.isBlank(eventId)) {
            // 部分物流商不提供事件唯一 ID，退化为对报文内容做摘要作为去重键
            eventId = DigestUtils.sha256Hex(rawPayload);
        }
        return eventId;
    }
}
```

#### 7.2.3 轨迹入库（追加模式）与关键节点识别

轨迹消费端在 3.3.2 节已有基础实现，这里补充关键节点识别与"追加不覆盖"的入库细节，以及每个关键节点触发的下游动作：

```java
/**
 * 轨迹处理消费者：入库 + 关键节点识别 + 下游动作分发
 */
@Component
public class TrackPushConsumer {

    private static final Logger log = LoggerFactory.getLogger(TrackPushConsumer.class);

    // 需要重点关注、触发下游动作的关键节点
    private static final Set<WaybillStatus> KEY_STATUS_SET = EnumSet.of(
            WaybillStatus.PICKED_UP, WaybillStatus.IN_TRANSIT,
            WaybillStatus.OUT_FOR_DELIVERY, WaybillStatus.SIGNED);

    @Autowired
    private CarrierAdapterFactory adapterFactory;
    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private TrackCacheService trackCacheService;
    @Autowired
    private RealtimePushService realtimePushService;
    @Autowired
    private DelayTaskScheduler delayTaskScheduler;
    @Autowired
    private IdempotentChecker idempotentChecker;

    @MessageListener(topic = "topic.track.callback")
    public void onMessage(TrackCallbackMessage message) {
        // 消费端二次幂等校验，防止消息队列重投递导致重复处理（回调入口的幂等只保证"入队幂等"，这里保证"处理幂等"）
        String processedKey = "track:consumed:" + message.getCarrierType() + ":" + message.getEventId();
        if (!idempotentChecker.isProcessed(processedKey)) {
            log.info("[轨迹消费][{}] 消息已处理过，跳过, eventId={}", message.getTraceId(), message.getEventId());
            return;
        }

        try {
            // 第一步：按物流商类型解析报文为统一轨迹模型
            CarrierAdapter adapter = adapterFactory.getAdapter(CarrierType.valueOf(message.getCarrierType()));
            CarrierTrackPoint rawPoint = adapter.parseCallback(message.getRawPayload());

            // 第二步：定位内部运单
            Waybill waybill = waybillRepository.findByCarrierWaybillNo(rawPoint.getCarrierWaybillNo());
            if (waybill == null) {
                log.warn("[轨迹消费][{}] 未找到匹配的内部运单，可能是发货尚未落库完成或运单号不一致, carrierWaybillNo={}",
                        message.getTraceId(), rawPoint.getCarrierWaybillNo());
                // 找不到运单时不能直接丢弃，短暂延迟后重试一次，应对"发货事务提交慢于回调到达"的时序问题
                throw new WaybillNotReadyException("运单尚未就绪，触发重试: " + rawPoint.getCarrierWaybillNo());
            }

            TrackPoint newPoint = TrackPoint.builder()
                    .status(rawPoint.getUnifiedStatus())
                    .location(rawPoint.getLocation())
                    .occurTime(rawPoint.getOccurTime())
                    .rawStatus(rawPoint.getRawStatus())
                    .build();

            // 第三步：轨迹入库 —— 追加模式，历史轨迹永远不会被覆盖或删除，只做新增
            waybillRepository.appendTrackPoint(waybill.getWaybillNo(), newPoint);
            log.info("[轨迹消费][{}] 轨迹追加入库成功, waybillNo={}, status={}, occurTime={}",
                    message.getTraceId(), waybill.getWaybillNo(), newPoint.getStatus(), newPoint.getOccurTime());

            // 第四步：时序校验通过后，驱动状态机流转（乱序场景仅记录不流转，逻辑见 3.3.2 节）
            TrackPoint lastPoint = waybill.getLastTrackPoint();
            boolean isOutOfOrder = lastPoint != null && newPoint.getOccurTime() < lastPoint.getOccurTime();
            if (!isOutOfOrder) {
                waybill.transitTo(newPoint.getStatus(), newPoint);
                waybillRepository.updateStatus(waybill);
            }

            // 第五步：刷新缓存
            trackCacheService.refreshLatestTrack(waybill.getWaybillNo(), newPoint);

            // 第六步：关键节点识别与下游动作分发
            if (KEY_STATUS_SET.contains(newPoint.getStatus()) && !isOutOfOrder) {
                dispatchKeyStatusAction(waybill, newPoint);
            }

        } catch (WaybillNotReadyException e) {
            log.warn("[轨迹消费][{}] {}", message.getTraceId(), e.getMessage());
            throw e; // 抛出后交由消息队列按退避策略重试
        } catch (Exception e) {
            log.error("[轨迹消费][{}] 处理失败, carrierType={}, eventId={}",
                    message.getTraceId(), message.getCarrierType(), message.getEventId(), e);
            throw new TrackProcessFailedException(e);
        }
    }

    /**
     * 关键节点触发的下游动作：用户端实时推送 + 签收后的延迟确认收货任务
     */
    private void dispatchKeyStatusAction(Waybill waybill, TrackPoint point) {
        // 用户端实时推送：优先走长连接/WebSocket，失败降级为 App 推送
        try {
            realtimePushService.pushTrackUpdate(waybill.getOrderId(), waybill.getWaybillNo(), point);
            log.info("[轨迹推送] 用户端实时推送成功, orderId={}, waybillNo={}, status={}",
                    waybill.getOrderId(), waybill.getWaybillNo(), point.getStatus());
        } catch (Exception e) {
            log.error("[轨迹推送] 用户端实时推送失败，已降级为离线推送, orderId={}, waybillNo={}",
                    waybill.getOrderId(), waybill.getWaybillNo(), e);
            realtimePushService.fallbackToOfflinePush(waybill.getOrderId(), waybill.getWaybillNo(), point);
        }

        // 签收节点：投递"超时自动确认收货"的延迟任务
        if (point.getStatus() == WaybillStatus.SIGNED) {
            scheduleAutoConfirmTask(waybill);
        }
    }

    /**
     * 签收后 N 天用户未主动确认收货，则系统自动确认，触发交易结算等下游流程
     */
    private void scheduleAutoConfirmTask(Waybill waybill) {
        long delayMillis = TimeUnit.DAYS.toMillis(7); // 签收后 7 天自动确认收货
        AutoConfirmTask task = AutoConfirmTask.builder()
                .orderId(waybill.getOrderId())
                .waybillNo(waybill.getWaybillNo())
                .expectExecuteTime(System.currentTimeMillis() + delayMillis)
                .build();
        try {
            delayTaskScheduler.schedule("topic.order.auto-confirm", task, delayMillis);
            log.info("[自动确认收货] 延迟任务投递成功, orderId={}, waybillNo={}, 预计执行时间={}",
                    waybill.getOrderId(), waybill.getWaybillNo(), task.getExpectExecuteTime());
        } catch (Exception e) {
            // 延迟任务投递失败不能静默吞掉，否则会导致订单永久无法自动确认收货，需要记录并触发告警交由人工/补偿任务兜底
            log.error("[自动确认收货] 延迟任务投递失败，需人工介入或依赖兜底扫描任务, orderId={}, waybillNo={}",
                    waybill.getOrderId(), waybill.getWaybillNo(), e);
            AlertUtils.alert("AUTO_CONFIRM_TASK_SCHEDULE_FAILED", waybill.getOrderId());
        }
    }
}
```

#### 7.2.4 自动确认收货延迟任务的消费与幂等

延迟任务到期后被消费执行，此时订单可能已经被用户提前手动确认，或者已经进入售后流程，消费端必须重新校验订单当前状态，不能无脑执行：

```java
/**
 * 自动确认收货延迟任务消费者
 */
@Component
public class AutoConfirmTaskConsumer {

    private static final Logger log = LoggerFactory.getLogger(AutoConfirmTaskConsumer.class);

    @Autowired
    private OrderRepository orderRepository;
    @Autowired
    private IdempotentChecker idempotentChecker;

    @MessageListener(topic = "topic.order.auto-confirm")
    public void onMessage(AutoConfirmTask task) {
        String idempotentKey = "auto-confirm:" + task.getOrderId();
        if (!idempotentChecker.isProcessed(idempotentKey)) {
            log.info("[自动确认收货] 任务已执行过，跳过, orderId={}", task.getOrderId());
            return;
        }

        try {
            Order order = orderRepository.findById(task.getOrderId());
            if (order == null) {
                log.warn("[自动确认收货] 订单不存在, orderId={}", task.getOrderId());
                return;
            }
            // 重新校验订单状态：只有仍处于"已签收待确认"状态才需要自动确认
            // 用户可能已提前手动确认收货，或订单已进入售后流程，这两种情况都不应再执行自动确认
            if (order.getStatus() != OrderStatus.SIGNED_PENDING_CONFIRM) {
                log.info("[自动确认收货] 订单状态已变化，无需自动确认, orderId={}, currentStatus={}",
                        task.getOrderId(), order.getStatus());
                return;
            }
            orderRepository.updateStatus(task.getOrderId(), OrderStatus.SIGNED_PENDING_CONFIRM, OrderStatus.COMPLETED);
            log.info("[自动确认收货] 自动确认收货成功, orderId={}, waybillNo={}", task.getOrderId(), task.getWaybillNo());
        } catch (Exception e) {
            log.error("[自动确认收货] 处理失败, orderId={}", task.getOrderId(), e);
            throw new AutoConfirmFailedException(e); // 抛出异常交由队列重试
        }
    }
}
```

#### 7.2.5 物流超时预警

对于超过预期时长没有新轨迹更新的运单，需要主动预警，这个能力与 3.5.2 节的异常检测定时任务复用同一套扫描机制，但预警属于"提前告警"而非"确定性异常"，触发阈值更宽松，动作也更轻量（只通知不改状态）：

```java
/**
 * 物流超时预警任务：识别"即将超时但尚未达到异常判定阈值"的运单，提前预警
 */
@Component
public class TrackTimeoutWarningJob {

    private static final Logger log = LoggerFactory.getLogger(TrackTimeoutWarningJob.class);

    // 预警阈值略小于异常判定阈值（见 3.5.2 节 STAGE_TIMEOUT），起到提前预警的作用
    private static final Map<WaybillStatus, Long> WARNING_THRESHOLD = new EnumMap<>(WaybillStatus.class);
    static {
        WARNING_THRESHOLD.put(WaybillStatus.WAIT_PICKUP, 18 * 3600 * 1000L);
        WARNING_THRESHOLD.put(WaybillStatus.IN_TRANSIT, 48 * 3600 * 1000L);
        WARNING_THRESHOLD.put(WaybillStatus.OUT_FOR_DELIVERY, 18 * 3600 * 1000L);
    }

    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private ExceptionNotifyService notifyService;
    @Autowired
    private IdempotentChecker idempotentChecker;

    @Scheduled(fixedRate = 15 * 60 * 1000) // 每 15 分钟扫描一次
    public void scan() {
        int pageSize = 500;
        String cursor = null;
        int warnedCount = 0;
        try {
            while (true) {
                List<Waybill> batch = waybillRepository.scanActiveWaybills(cursor, pageSize);
                if (batch.isEmpty()) {
                    break;
                }
                for (Waybill waybill : batch) {
                    if (checkAndWarn(waybill)) {
                        warnedCount++;
                    }
                }
                cursor = batch.get(batch.size() - 1).getWaybillNo();
                if (batch.size() < pageSize) {
                    break;
                }
            }
            log.info("[物流超时预警] 本轮扫描结束，触发预警运单数={}", warnedCount);
        } catch (Exception e) {
            // 扫描任务本身失败不能影响下一轮调度，记录告警日志，等待下一次定时触发
            log.error("[物流超时预警] 扫描任务执行异常", e);
        }
    }

    private boolean checkAndWarn(Waybill waybill) {
        Long threshold = WARNING_THRESHOLD.get(waybill.getStatus());
        if (threshold == null) {
            return false;
        }
        long stayDuration = System.currentTimeMillis() - waybill.getUpdateTime();
        if (stayDuration <= threshold) {
            return false;
        }
        // 同一运单同一状态只预警一次，避免每 15 分钟重复打扰
        String warnKey = "track:warning:" + waybill.getWaybillNo() + ":" + waybill.getStatus();
        if (!idempotentChecker.isProcessed(warnKey)) {
            return false;
        }
        try {
            notifyService.notifyTrackTimeoutWarning(waybill, stayDuration);
            log.warn("[物流超时预警] 运单长时间无更新, waybillNo={}, status={}, 已停留={}ms",
                    waybill.getWaybillNo(), waybill.getStatus(), stayDuration);
            return true;
        } catch (Exception e) {
            log.error("[物流超时预警] 预警通知发送失败, waybillNo={}", waybill.getWaybillNo(), e);
            return false;
        }
    }
}
```

#### 7.2.6 异常场景处理小结

| 异常场景 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 回调伪造 | 未知来源或篡改的回调请求 | 验签失败直接拒绝并返回 4xx，不进入后续处理，记录警告日志 |
| 回调重复推送 | 物流商网络重试导致同一事件多次到达 | 入口层按事件 ID/报文摘要幂等，消费端按处理幂等键二次去重，双重保护 |
| 回调早于发货落库完成 | 分布式环境下回调到达快于本地事务提交 | 找不到匹配运单时抛出可重试异常，交由消息队列延迟重试而非直接丢弃 |
| 轨迹乱序 | 网络延迟导致旧事件后到达 | 时序校验，仅追加历史记录，不驱动状态机倒退 |
| 延迟任务投递失败 | 消息队列瞬时不可用 | 记录错误日志并触发告警，同时保留定时兜底扫描任务作为补偿 |
| 自动确认执行时状态已变 | 用户提前手动确认或已进入售后 | 消费时重新校验订单状态，非预期状态直接跳过，不强制覆盖 |

### 7.3 案例三：物流异常处理全链路

#### 7.3.1 业务场景与链路概览

对于丢件、破损、拒收、退回等物流异常，系统需要主动发现（而非等待用户投诉），自动分类并发起对应的售后流程，同时做好商家与用户的双向通知，并在丢件/破损场景下触发理赔流程。

```
定时任务：物流停滞检测（长时间无轨迹更新的运单）
    │
    ▼
异常分类（丢件 / 破损 / 拒收 / 退回）
    │
    ▼
幂等校验：同一运单同一异常不重复处理
    │
    ▼
自动发起售后单
    │
    ├──▶ 通知商家（处理提醒）
    ├──▶ 通知用户（进度告知）
    │
    ▼
理赔流程触发（丢件/破损场景）
```

#### 7.3.2 物流停滞检测定时任务

停滞检测是异常处理链路的起点，与 3.5.2 节的超时扫描相比，这里的目标是"确定性判定异常并推进售后"，因此判定阈值更严格，且必须做幂等控制防止同一运单被重复处理：

```java
/**
 * 物流停滞检测任务：扫描长时间无更新的运单，判定为异常并推进售后
 */
@Component
public class LogisticsStagnationDetectionJob {

    private static final Logger log = LoggerFactory.getLogger(LogisticsStagnationDetectionJob.class);

    // 停滞判定阈值：超过此时长仍无新轨迹，确定性判定为异常（严于 3.5.2 节的预警阈值）
    private static final Map<WaybillStatus, Long> STAGNATION_THRESHOLD = new EnumMap<>(WaybillStatus.class);
    static {
        STAGNATION_THRESHOLD.put(WaybillStatus.WAIT_PICKUP, 48 * 3600 * 1000L);
        STAGNATION_THRESHOLD.put(WaybillStatus.IN_TRANSIT, 120 * 3600 * 1000L);
        STAGNATION_THRESHOLD.put(WaybillStatus.OUT_FOR_DELIVERY, 48 * 3600 * 1000L);
    }

    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private LogisticsExceptionHandler exceptionHandler;
    @Autowired
    private IdempotentChecker idempotentChecker;

    @Scheduled(cron = "0 0/30 * * * ?") // 每 30 分钟执行一次
    public void detect() {
        int pageSize = 500;
        String cursor = null;
        int detectedCount = 0;
        int failedCount = 0;
        try {
            while (true) {
                List<Waybill> batch = waybillRepository.scanActiveWaybills(cursor, pageSize);
                if (batch.isEmpty()) {
                    break;
                }
                for (Waybill waybill : batch) {
                    try {
                        if (isStagnant(waybill)) {
                            handleStagnantWaybill(waybill);
                            detectedCount++;
                        }
                    } catch (Exception e) {
                        // 单个运单处理失败不能影响整批任务的继续执行
                        failedCount++;
                        log.error("[物流停滞检测] 单个运单处理失败, waybillNo={}", waybill.getWaybillNo(), e);
                    }
                }
                cursor = batch.get(batch.size() - 1).getWaybillNo();
                if (batch.size() < pageSize) {
                    break;
                }
            }
            log.info("[物流停滞检测] 本轮扫描完成，识别异常数={}, 处理失败数={}", detectedCount, failedCount);
        } catch (Exception e) {
            log.error("[物流停滞检测] 扫描任务整体异常", e);
        }
    }

    private boolean isStagnant(Waybill waybill) {
        Long threshold = STAGNATION_THRESHOLD.get(waybill.getStatus());
        if (threshold == null) {
            return false;
        }
        long stayDuration = System.currentTimeMillis() - waybill.getUpdateTime();
        return stayDuration > threshold;
    }

    private void handleStagnantWaybill(Waybill waybill) {
        // 幂等控制：同一运单不重复判定为停滞异常，防止每 30 分钟扫描一次导致重复发起售后
        String idempotentKey = "logistics:stagnation:handled:" + waybill.getWaybillNo();
        if (!idempotentChecker.isProcessed(idempotentKey)) {
            log.info("[物流停滞检测] 运单已处理过停滞异常，跳过, waybillNo={}", waybill.getWaybillNo());
            return;
        }
        log.warn("[物流停滞检测] 判定运单为停滞异常, waybillNo={}, status={}, 已停留时长={}ms",
                waybill.getWaybillNo(), waybill.getStatus(),
                System.currentTimeMillis() - waybill.getUpdateTime());
        exceptionHandler.handle(waybill, LogisticsExceptionType.STAGNANT, null);
    }
}
```

#### 7.3.3 异常分类与自动售后发起

无论异常是由停滞检测发现，还是由物流商回调直接上报（如丢件/破损/拒收），都统一收敛到同一个异常处理器，按类型分流处理：

```java
/**
 * 物流异常统一处理器：分类识别 + 自动发起售后 + 双向通知 + 理赔触发
 */
@Component
public class LogisticsExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(LogisticsExceptionHandler.class);

    @Autowired
    private WaybillRepository waybillRepository;
    @Autowired
    private AfterSaleService afterSaleService;
    @Autowired
    private ExceptionNotifyService notifyService;
    @Autowired
    private ClaimService claimService;
    @Autowired
    private IdempotentChecker idempotentChecker;

    /**
     * 统一异常处理入口
     * @param waybill 运单
     * @param exceptionType 异常类型（丢件/破损/拒收/退回/停滞）
     * @param rawExceptionInfo 物流商上报的原始异常信息（停滞场景为 null）
     */
    @Transactional(rollbackFor = Exception.class)
    public void handle(Waybill waybill, LogisticsExceptionType exceptionType, String rawExceptionInfo) {
        // 全局幂等：同一运单的同一类型异常只处理一次，防止重复触发售后与理赔
        String idempotentKey = "logistics:exception:" + waybill.getWaybillNo() + ":" + exceptionType;
        if (!idempotentChecker.isProcessed(idempotentKey)) {
            log.info("[物流异常处理] 该运单该类型异常已处理过，跳过, waybillNo={}, type={}",
                    waybill.getWaybillNo(), exceptionType);
            return;
        }

        try {
            // 第一步：落地异常记录
            WaybillException exception = WaybillException.builder()
                    .waybillNo(waybill.getWaybillNo())
                    .type(mapToExceptionType(exceptionType))
                    .rawInfo(rawExceptionInfo)
                    .occurTime(System.currentTimeMillis())
                    .status(ExceptionHandleStatus.PENDING)
                    .build();
            waybillRepository.saveException(exception);

            // 第二步：驱动运单状态流转为异常态（停滞类异常不强制切状态，保留原状态便于后续人工判断是否恢复）
            if (exceptionType != LogisticsExceptionType.STAGNANT) {
                TrackPoint exceptionPoint = TrackPoint.builder()
                        .status(WaybillStatus.EXCEPTION)
                        .occurTime(System.currentTimeMillis())
                        .build();
                waybill.transitTo(WaybillStatus.EXCEPTION, exceptionPoint);
                waybillRepository.updateStatus(waybill);
            }

            // 第三步：按异常类型分流处理
            switch (exceptionType) {
                case LOST:
                    handleLostPackage(waybill, exception);
                    break;
                case DAMAGED:
                    handleDamagedPackage(waybill, exception);
                    break;
                case REJECTED:
                    handleRejectedPackage(waybill, exception);
                    break;
                case RETURNED:
                    handleReturnedPackage(waybill, exception);
                    break;
                case STAGNANT:
                    handleStagnantException(waybill, exception);
                    break;
                default:
                    log.warn("[物流异常处理] 未识别的异常类型，走通用处理, waybillNo={}, type={}",
                            waybill.getWaybillNo(), exceptionType);
                    handleGenericException(waybill, exception);
            }
        } catch (Exception e) {
            log.error("[物流异常处理] 处理失败, waybillNo={}, type={}", waybill.getWaybillNo(), exceptionType, e);
            // 处理失败需要抛出以回滚本次事务内的状态变更，避免出现"状态改了但售后没发起"的不一致
            throw new LogisticsExceptionHandleFailedException(e);
        }
    }

    /**
     * 丢件：自动发起售后 + 双向通知 + 直接触发理赔
     */
    private void handleLostPackage(Waybill waybill, WaybillException exception) {
        AfterSaleOrder afterSale = afterSaleService.createAfterSale(
                waybill.getOrderId(), AfterSaleType.PACKAGE_LOST, exception.getWaybillNo());
        log.info("[物流异常-丢件] 自动发起售后成功, orderId={}, waybillNo={}, afterSaleId={}",
                waybill.getOrderId(), waybill.getWaybillNo(), afterSale.getAfterSaleId());

        notifySafely(() -> notifyService.notifyMerchantException(waybill, exception, "包裹疑似丢失，请及时处理"));
        notifySafely(() -> notifyService.notifyUserException(waybill, exception, "您的包裹物流异常，我们正在为您跟进处理"));

        // 丢件场景直接触发理赔流程，无需等待人工审核售后单
        triggerClaim(waybill, exception, ClaimType.LOST_COMPENSATION);
    }

    /**
     * 破损：自动发起售后，理赔需要举证材料，先创建理赔单等待用户补充凭证
     */
    private void handleDamagedPackage(Waybill waybill, WaybillException exception) {
        AfterSaleOrder afterSale = afterSaleService.createAfterSale(
                waybill.getOrderId(), AfterSaleType.PACKAGE_DAMAGED, exception.getWaybillNo());
        log.info("[物流异常-破损] 自动发起售后成功, orderId={}, waybillNo={}, afterSaleId={}",
                waybill.getOrderId(), waybill.getWaybillNo(), afterSale.getAfterSaleId());

        notifySafely(() -> notifyService.notifyMerchantException(waybill, exception, "包裹疑似破损，请配合处理"));
        notifySafely(() -> notifyService.notifyUserException(waybill, exception, "您的包裹可能存在破损，请拍照留证以便理赔"));

        triggerClaim(waybill, exception, ClaimType.DAMAGE_COMPENSATION);
    }

    /**
     * 拒收：判断是否需要触发退回流程，不直接进入理赔
     */
    private void handleRejectedPackage(Waybill waybill, WaybillException exception) {
        afterSaleService.createAfterSale(waybill.getOrderId(), AfterSaleType.PACKAGE_REJECTED, exception.getWaybillNo());
        log.info("[物流异常-拒收] 自动发起售后成功, orderId={}, waybillNo={}", waybill.getOrderId(), waybill.getWaybillNo());

        notifySafely(() -> notifyService.notifyMerchantException(waybill, exception, "用户已拒收，包裹即将退回"));

        TrackPoint returnPoint = TrackPoint.builder()
                .status(WaybillStatus.RETURNED)
                .occurTime(System.currentTimeMillis())
                .build();
        waybill.transitTo(WaybillStatus.RETURNED, returnPoint);
        waybillRepository.updateStatus(waybill);
    }

    private void handleReturnedPackage(Waybill waybill, WaybillException exception) {
        afterSaleService.createAfterSale(waybill.getOrderId(), AfterSaleType.PACKAGE_RETURNED, exception.getWaybillNo());
        notifySafely(() -> notifyService.notifyMerchantException(waybill, exception, "包裹已退回，请及时确认收货"));
    }

    /**
     * 停滞类异常：不确定是否真的丢失，先发起"物流跟进"类售后，交由客服人工核实，不直接理赔
     */
    private void handleStagnantException(Waybill waybill, WaybillException exception) {
        afterSaleService.createAfterSale(waybill.getOrderId(), AfterSaleType.LOGISTICS_FOLLOW_UP, exception.getWaybillNo());
        notifySafely(() -> notifyService.notifyUserException(waybill, exception, "您的包裹物流信息长时间未更新，客服正在为您跟进"));
        log.info("[物流异常-停滞] 已发起客服跟进工单, orderId={}, waybillNo={}", waybill.getOrderId(), waybill.getWaybillNo());
    }

    private void handleGenericException(Waybill waybill, WaybillException exception) {
        afterSaleService.createAfterSale(waybill.getOrderId(), AfterSaleType.LOGISTICS_GENERIC, exception.getWaybillNo());
        notifySafely(() -> notifyService.notifyUserException(waybill, exception, "您的包裹出现物流异常，我们正在处理"));
    }

    /**
     * 理赔流程触发，理赔单创建失败不应阻塞售后主流程，记录告警交由人工兜底
     */
    private void triggerClaim(Waybill waybill, WaybillException exception, ClaimType claimType) {
        try {
            ClaimOrder claim = claimService.createClaim(waybill.getOrderId(), waybill.getWaybillNo(), claimType);
            log.info("[理赔流程] 理赔单创建成功, orderId={}, waybillNo={}, claimId={}, claimType={}",
                    waybill.getOrderId(), waybill.getWaybillNo(), claim.getClaimId(), claimType);
        } catch (Exception e) {
            log.error("[理赔流程] 理赔单创建失败，需人工介入, orderId={}, waybillNo={}, claimType={}",
                    waybill.getOrderId(), waybill.getWaybillNo(), claimType, e);
            AlertUtils.alert("CLAIM_CREATE_FAILED", waybill.getWaybillNo());
        }
    }

    /**
     * 通知类操作统一包装：任何一路通知失败都不应影响售后与理赔主流程
     */
    private void notifySafely(Runnable notifyAction) {
        try {
            notifyAction.run();
        } catch (Exception e) {
            log.error("[物流异常处理] 通知发送失败", e);
        }
    }

    private WaybillExceptionType mapToExceptionType(LogisticsExceptionType type) {
        switch (type) {
            case LOST: return WaybillExceptionType.LOST;
            case DAMAGED: return WaybillExceptionType.DAMAGED;
            case REJECTED: return WaybillExceptionType.REJECTED;
            case RETURNED: return WaybillExceptionType.RETURNED;
            default: return WaybillExceptionType.UNKNOWN;
        }
    }
}
```

#### 7.3.4 物流商主动上报异常的接入

除了定时任务发现的停滞异常，物流商也会通过轨迹回调直接上报丢件、破损等确定性异常，这类异常需要在轨迹消费链路中识别并路由到同一个 `LogisticsExceptionHandler`，做到"发现渠道不同、处理逻辑收敛统一"：

```java
/**
 * 在轨迹消费链路中识别物流商主动上报的异常轨迹节点，路由到统一异常处理器
 * （与 3.5.2 节 WaybillExceptionDetector 配合使用，二者共同覆盖"主动上报"与"被动发现"两类异常来源）
 */
@Component
public class CarrierReportedExceptionRouter {

    private static final Logger log = LoggerFactory.getLogger(CarrierReportedExceptionRouter.class);

    @Autowired
    private LogisticsExceptionHandler exceptionHandler;

    public void routeIfException(Waybill waybill, CarrierTrackPoint rawPoint) {
        if (rawPoint.getUnifiedStatus() != WaybillStatus.EXCEPTION) {
            return;
        }
        LogisticsExceptionType exceptionType = parseCarrierExceptionType(rawPoint.getRawStatus());
        log.warn("[物流异常上报] 物流商主动上报异常, waybillNo={}, rawStatus={}, 解析异常类型={}",
                waybill.getWaybillNo(), rawPoint.getRawStatus(), exceptionType);
        try {
            exceptionHandler.handle(waybill, exceptionType, rawPoint.getRawStatus());
        } catch (Exception e) {
            log.error("[物流异常上报] 异常处理失败, waybillNo={}", waybill.getWaybillNo(), e);
            throw e; // 交由消息队列重试机制兜底
        }
    }

    private LogisticsExceptionType parseCarrierExceptionType(String rawStatus) {
        // 各物流商异常码含义不同，此处按约定的关键字规则做兜底解析，具体映射表按物流商实现省略
        if (rawStatus == null) {
            return LogisticsExceptionType.UNKNOWN;
        }
        String lower = rawStatus.toLowerCase();
        if (lower.contains("lost")) {
            return LogisticsExceptionType.LOST;
        } else if (lower.contains("damage")) {
            return LogisticsExceptionType.DAMAGED;
        } else if (lower.contains("reject")) {
            return LogisticsExceptionType.REJECTED;
        } else if (lower.contains("return")) {
            return LogisticsExceptionType.RETURNED;
        }
        return LogisticsExceptionType.UNKNOWN;
    }
}
```

#### 7.3.5 异常场景处理小结

| 异常场景 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 重复判定停滞异常 | 定时任务每 30 分钟扫描一次，同一运单可能多次命中阈值 | 以运单号 + 异常类型为幂等键，一次异常只处理一次，避免重复发起售后与理赔 |
| 售后单创建失败 | 售后服务临时不可用 | 整体处理逻辑放在事务内，创建失败抛出异常回滚状态变更，等待下一次重试而非留下不一致的中间态 |
| 理赔单创建失败 | 理赔服务异常 | 理赔创建独立捕获异常，不回滚已生效的售后流程，记录告警交由人工兜底介入 |
| 通知发送失败 | 短信/推送网关异常 | 所有通知统一包装捕获异常，任意通知失败都不影响售后与理赔主流程的推进 |
| 异常来源重复 | 定时任务与物流商主动上报同时命中同一运单的同一异常 | 统一收敛到 `LogisticsExceptionHandler` 并共用同一幂等键，无论来源是哪个入口都只处理一次 |
| 停滞异常后又恢复 | 客服跟进期间运单又收到新的正常轨迹 | 停滞异常不强制切换终态，运单仍可通过状态机继续正常流转，只是保留了一条跟进类售后记录 |

以上三个全链路案例覆盖了物流系统最核心的正向发货、轨迹回调、异常自愈三条主线。它们共同验证了前面章节的架构设计：适配器模式让不同物流商的运单核验、轨迹解析可以复用同一套业务流程；统一状态机保证了无论轨迹数据来自主动回调还是补偿查询，状态流转都遵循同一套合法性规则；分布式锁、乐观锁、Redis SETNX 幂等键三种手段结合，在发货、轨迹消费、延迟任务、异常处理等各个环节层层拦截重复操作；而所有对外部依赖（短信、推送、理赔、售后）的调用都做了独立异常隔离，确保局部故障不会拖垮主链路。
