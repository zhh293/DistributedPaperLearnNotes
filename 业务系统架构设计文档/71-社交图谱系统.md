# 社交图谱系统架构设计

## 一、问题背景

社交图谱（Social Graph）是描述用户与用户之间、用户与内容之间关系的核心数据结构，广泛应用于社交网络、社区产品、内容平台的关注体系、好友体系、群组体系等场景。随着用户规模从百万级增长到亿级，好友关系数量将达到百亿甚至千亿级别，社交图谱系统面临以下核心挑战：

1. **海量关系存储**：假设每个用户平均拥有200个关注/粉丝关系，1亿用户规模下关系总数将达到200亿条，传统关系型数据库难以支撑如此大规模的关系存储与高并发读写。

2. **多跳查询性能**：好友推荐、共同好友计算、社交影响力分析等场景，本质上是对图结构进行多跳遍历（2跳、3跳甚至更深），而关系型数据库通过JOIN实现多跳查询时，性能会随着跳数增加呈指数级下降。有实验数据表明，在包含100万用户、人均50个好友的社交网络中查找最大深度为5的好友关系，图数据库的查询效率相较于关系型数据库有数量级的提升。

3. **读写比例悬殊**：社交关系的读取（查询好友列表、判断是否互相关注、查询共同好友）远高于写入（加好友、取关），读写比例通常在100:1以上，需要针对性设计缓存与索引策略。

4. **热点账号问题**：明星、大V等头部账号可能拥有千万级粉丝，这类账号的关系读写会形成明显的热点，需要专门的分片与缓存策略应对，否则会导致数据倾斜与服务雪崩。

5. **关系模型的多样性**：不同产品形态需要支持不同的关系模型——即时通讯类产品通常采用双向好友模型（互相同意才能建立关系），内容社区类产品通常采用单向关注模型（无需对方同意即可关注），部分产品还需要同时支持两种模型的混合。

6. **数据一致性与实时性**：好友关系变更（新增、删除、拉黑）需要尽快对下游好友数、动态可见性、推荐系统等产生影响，同时避免产生脏数据（例如互相好友关系不一致：A的好友列表中有B，但B的好友列表中没有A）。

如果不能很好地解决上述问题，会导致社交类功能响应缓慢、好友推荐不准确、共同好友计算超时，进而直接影响用户体验和平台的社交粘性。

### 2.2 各层职责说明

**接入层**统一收敛所有社交关系相关请求，承担限流、鉴权、请求合并等职责。由于好友列表查询、关注状态查询等接口调用量极大，接入层需要支持批量查询接口（例如一次性查询A对B、C、D是否关注），减少网络往返次数。

**关系读写层**是系统的核心业务逻辑所在，包含好友关系管理、关注粉丝管理、关系状态机流转、共同好友计算、好友推荐、社交影响力计算等核心能力，下文将在"核心链路设计"中详细展开。

**缓存层**采用Redis的Set/ZSet结构缓存高频访问的好友列表、粉丝列表、以及好友数/粉丝数等计数信息，是应对海量读请求的第一道防线。

**图存储层**是社交图谱的核心持久化存储，选用图数据库（如Neo4j、JanusGraph、NebulaGraph等）存储用户节点及好友/关注边，充分利用图数据库在多跳查询上的性能优势。

**关系型存储**作为兜底与审计手段，记录关系变更的操作流水，便于问题排查、数据对账、以及历史行为分析。

**图计算与挖掘层**运行社区发现、影响力计算、六度分隔验证等离线或近实时的图算法任务，产出的中间结果（如社交圈子标签、KOL影响力分数）会反哺给推荐系统和运营系统。

### 2.3 关键组件选型一览

| 组件 | 用途 | 选型理由 |
| --- | --- | --- |
| Redis Cluster | 好友列表/粉丝列表缓存、计数缓存、热点账号缓存 | 高吞吐、低延迟，Set/ZSet天然契合关系数据的去重与排序需求 |
| 图数据库（Neo4j/JanusGraph/NebulaGraph） | 好友关系、关注关系的持久化存储与多跳查询 | 原生支持图遍历，多跳查询性能远超关系型数据库JOIN方案 |
| MySQL（分库分表） | 关系变更流水、审计日志、冷数据归档 | 事务能力强，适合做审计追溯与最终一致性校验 |
| 消息队列 | 关系变更事件异步分发（好友数更新、推荐系统感知、风控感知） | 削峰填谷，解耦关系写入与下游消费方 |
| 离线计算引擎（Spark/Flink） | 社区发现、影响力计算、推荐特征生产 | 适合大规模图数据的批量迭代计算 |

## 三、核心链路设计

### 3.1 好友关系存储模型设计：邻接表 vs 邻接矩阵

**问题出发点**：社交关系本质上是一张图，第一个要解决的问题是如何存储这张图。

**方案对比**：

图的两种经典存储方式是邻接矩阵和邻接表：

- **邻接矩阵**：用一个 N×N 的二维矩阵表示用户之间的关系，`matrix[i][j] = 1` 表示用户i与用户j存在关系。这种方式的优点是判断两个用户是否存在关系的时间复杂度是O(1)，但空间复杂度是O(N²)。当N达到1亿时，矩阵存储量将是天文数字，完全不可行，因此在超大规模社交网络场景下几乎不会采用纯邻接矩阵方案。

- **邻接表**：为每个用户维护一个"关系列表"，只存储真实存在的边，空间复杂度为O(N+E)，E为边的数量。这是绝大多数大规模社交图谱系统采用的存储方式。

**技术选型理由**：由于社交网络是典型的稀疏图（每个用户平均只有几十到几百个好友，远小于用户总数N），邻接表的空间效率远高于邻接矩阵，因此我们选择邻接表作为核心存储模型。

**具体实现思路**：

1. 在图数据库中，将每个用户建模为一个节点（Vertex），节点上携带用户基础属性（用户ID、注册时间、账号状态）。
2. 将好友关系、关注关系建模为边（Edge），边上携带关系属性（建立时间、关系来源、关系状态）。
3. 图数据库底层实际上就是用邻接表来组织节点与边的关系，每个节点上挂载一个出边列表和入边列表，这样从某个节点出发查询其所有邻居，只需要O(degree)的时间复杂度，而不需要扫描全表。

```java
/**
 * 好友关系边的领域模型
 */
public class FriendEdge {
    private Long fromUserId;
    private Long toUserId;
    private RelationType relationType; // FRIEND(双向好友), FOLLOW(单向关注)
    private RelationStatus status;     // PENDING, ACCEPTED, BLOCKED
    private long createTime;
    private String source;             // 关系建立来源：搜索、推荐、扫码、群聊等

    // getter/setter省略
}

/**
 * 邻接表在应用层的抽象：每个用户维护一份出边（我关注的人）和入边（关注我的人）
 */
public interface RelationAdjacencyStore {

    /**
     * 获取用户的出边列表（分页），即该用户关注/添加的好友
     */
    List<FriendEdge> getOutEdges(Long userId, int offset, int limit);

    /**
     * 获取用户的入边列表（分页），即关注该用户/添加该用户为好友的人
     */
    List<FriendEdge> getInEdges(Long userId, int offset, int limit);

    /**
     * O(1)判断两点之间是否存在边（利用图数据库索引或缓存Set）
     */
    boolean hasEdge(Long fromUserId, Long toUserId, RelationType type);
}
```

在图数据库中对应的存储示意（以Cypher风格为例）：

```cypher
// 创建用户节点
CREATE (u:User {userId: 1001, nickname: "alice", createTime: 1700000000})

// 创建好友关系边（双向好友本质上是两条单向边或一条无向边，视具体图库实现而定）
MATCH (a:User {userId: 1001}), (b:User {userId: 1002})
CREATE (a)-[:FRIEND {createTime: 1700000100, source: "search"}]->(b)
CREATE (b)-[:FRIEND {createTime: 1700000100, source: "search"}]->(a)

// 查询用户1001的所有好友
MATCH (u:User {userId: 1001})-[:FRIEND]->(friend)
RETURN friend
```

### 3.2 单向关注 vs 双向好友模型的设计与状态机

**问题出发点**：不同产品形态对关系的语义要求不同——内容社区（如微博类产品）通常是单向关注模型，即时通讯产品通常是双向好友模型，需要设计一套能同时兼容两种语义的模型。

**方案设计**：

1. **单向关注模型（Follow Model）**：A关注B，不需要B同意，A的"关注列表"增加B，B的"粉丝列表"增加A。这本质上是一条有向边 A → B。
2. **双向好友模型（Friend Model）**：A添加B为好友，需要经过"申请-同意"的状态机流转，最终形成一条双向可见的关系，通常在图数据库中用两条对称的有向边表示，或者用一条带方向无关标记的边表示。

**状态机设计**（以双向好友为例）：

```
                 申请添加好友
   [无关系] ────────────────────▶ [待确认(PENDING)]
                                        │
                          ┌─────────────┼─────────────┐
                     对方同意          对方拒绝        超时/撤回
                          ▼             ▼               ▼
                    [已成为好友]     [无关系]       [无关系]
                   (ACCEPTED)
                          │
                     任一方删除/拉黑
                          ▼
                    [无关系] 或 [BLOCKED]
```

使用状态模式（State Pattern）实现关系流转，避免大量if-else堆积：

```java
public enum RelationStatus {
    NONE, PENDING, ACCEPTED, BLOCKED
}

/**
 * 关系状态转换接口，每种状态实现自己的合法转换逻辑
 */
public interface RelationStateHandler {
    RelationStatus currentStatus();

    /**
     * 处理某个事件后返回下一个状态，如果事件在当前状态下不合法则抛出异常
     */
    RelationStatus handle(RelationEvent event);
}

public class PendingStateHandler implements RelationStateHandler {
    @Override
    public RelationStatus currentStatus() {
        return RelationStatus.PENDING;
    }

    @Override
    public RelationStatus handle(RelationEvent event) {
        switch (event) {
            case ACCEPT:
                return RelationStatus.ACCEPTED;
            case REJECT:
            case WITHDRAW:
            case TIMEOUT:
                return RelationStatus.NONE;
            default:
                throw new IllegalStateException("PENDING状态不支持事件: " + event);
        }
    }
}

public class AcceptedStateHandler implements RelationStateHandler {
    @Override
    public RelationStatus currentStatus() {
        return RelationStatus.ACCEPTED;
    }

    @Override
    public RelationStatus handle(RelationEvent event) {
        switch (event) {
            case DELETE:
                return RelationStatus.NONE;
            case BLOCK:
                return RelationStatus.BLOCKED;
            default:
                throw new IllegalStateException("ACCEPTED状态不支持事件: " + event);
        }
    }
}

/**
 * 状态机上下文，负责路由到具体的状态处理器
 */
public class RelationStateMachine {
    private final Map<RelationStatus, RelationStateHandler> handlers;

    public RelationStateMachine() {
        handlers = new EnumMap<>(RelationStatus.class);
        handlers.put(RelationStatus.PENDING, new PendingStateHandler());
        handlers.put(RelationStatus.ACCEPTED, new AcceptedStateHandler());
        // 其余状态处理器省略
    }

    public RelationStatus transfer(RelationStatus current, RelationEvent event) {
        RelationStateHandler handler = handlers.get(current);
        if (handler == null) {
            throw new IllegalStateException("未知状态: " + current);
        }
        return handler.handle(event);
    }
}
```

**数据流向**：客户端发起"添加好友"请求 → 关系读写层校验双方账号状态（是否被封禁、是否已拉黑对方）→ 写入PENDING状态的关系边 → 通过消息队列异步通知对方（触达消息通知中心）→ 对方同意后触发状态机流转到ACCEPTED → 双向写入正式好友边 → 异步更新双方好友数缓存 → 异步通知推荐系统与风控系统关系变更事件。

**异常分支处理**：
- 重复申请：需要在写入前做幂等校验，已存在PENDING记录时直接复用，不重复创建。
- 双方互相申请（A申请B的同时B也申请A）：需要在数据库层用唯一索引（fromUserId, toUserId的最小值+最大值组合）避免产生两条冗余的PENDING记录，或者在应用层检测到对方也有一条指向自己的PENDING记录时直接自动同意。
- 拉黑场景下的申请拦截：写入前检查是否存在BLOCKED边，存在则直接拒绝申请请求。

### 3.3 共同好友计算

**问题出发点**：共同好友是社交产品中最高频的图计算场景之一，用于好友推荐、社交破冰、身份验证辅助等。给定用户A和用户B，需要快速计算出他们共同的好友集合。

**算法思路**：本质上是两个集合的交集运算。设A的好友集合为 `F(A)`，B的好友集合为 `F(B)`，共同好友即 `F(A) ∩ F(B)`。

**技术选型理由**：
- 如果好友数量不大（例如都在几千以内），可以直接从缓存中取出双方好友ID的Set，使用Redis的`SINTER`命令在服务端完成交集运算，这是最简单高效的方案。
- 如果好友数量巨大（例如头部账号拥有千万级粉丝），全量取出两个大集合做交集的开销会非常高，此时应该借助图数据库的原生多跳查询能力，通过 `MATCH (a)-[:FRIEND]->(mutual)<-[:FRIEND]-(b)` 这样的路径查询在图引擎内部完成交集计算，避免把海量ID搬到应用层。

**具体实现（Redis方案）**：

```java
@Service
public class MutualFriendService {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final String FRIEND_SET_KEY_PREFIX = "friend:set:";

    /**
     * 计算A、B的共同好友，优先走Redis SINTER，好友数超过阈值时降级为图数据库查询
     */
    public List<Long> getMutualFriends(Long userIdA, Long userIdB) {
        String keyA = FRIEND_SET_KEY_PREFIX + userIdA;
        String keyB = FRIEND_SET_KEY_PREFIX + userIdB;

        Long sizeA = redisTemplate.opsForSet().size(keyA);
        Long sizeB = redisTemplate.opsForSet().size(keyB);

        // 双方好友数都在阈值以内，直接用Redis做交集，性能最优
        if (sizeA != null && sizeB != null && sizeA < 50_000 && sizeB < 50_000) {
            Set<String> intersection = redisTemplate.opsForSet().intersect(keyA, keyB);
            return intersection == null ? Collections.emptyList()
                    : intersection.stream().map(Long::parseLong).collect(Collectors.toList());
        }

        // 任一方是超大账号（如大V），走图数据库多跳查询，避免海量数据搬运到应用层
        return graphQueryService.queryMutualFriendsViaGraph(userIdA, userIdB);
    }
}
```

**图数据库方案（Cypher示例）**：

```cypher
MATCH (a:User {userId: $userIdA})-[:FRIEND]->(mutual:User)<-[:FRIEND]-(b:User {userId: $userIdB})
RETURN mutual.userId
LIMIT 100
```

**性能优化点**：
1. 共同好友结果集通常不需要全量返回，产品上一般只展示前N个（如前10个），因此在图查询与Redis查询中都应当加上LIMIT，避免大结果集拖慢响应。
2. 对于查询频率极高的用户对（例如互相频繁访问主页的用户），可以将计算结果缓存一段时间（如5分钟），减少重复计算。
3. 对于超大账号（千万级粉丝的KOL），共同好友的语义价值有限（普通用户与KOL的共同好友对推荐意义不大），可以针对这类账号做特殊降级，直接返回空结果或走近似算法（如HyperLogLog基数估算配合抽样交集）。

### 3.4 六度分隔理论的工程实现

**问题出发点**："六度分隔"理论认为世界上任意两个人之间，通过平均6层关系即可建立联系。在社交产品中，这一理论常用于"最短路径"类功能，例如"你和TA之间的关系链"、"如何认识某个人"等场景。

**算法思路**：这是一个经典的图最短路径问题，在无权图中，广度优先搜索（BFS）是求最短路径的标准算法。

**技术选型理由**：
- 深度优先搜索（DFS）不保证第一次找到的路径是最短路径，因此不适用。
- BFS按层扩展，第一次到达目标节点时所经过的层数即为最短路径长度，天然契合"最短关系链"的语义。
- 由于社交图谱是海量稀疏图，从单个用户出发做全量BFS的扇出（fan-out）可能非常大（好友的好友数量呈指数级增长），因此需要设计**双向BFS**来优化性能：从起点和终点同时展开搜索，在中间相遇时路径长度最短，可以将搜索空间从O(b^d)降低到O(b^(d/2))，这是搜索层面上的显著优化（b为分支因子，d为路径深度）。

**具体实现思路（双向BFS）**：

```java
/**
 * 基于双向BFS实现的社交关系链最短路径查询
 * 用于查找两个用户之间最短的好友关系链（六度分隔验证）
 */
@Service
public class ShortestSocialPathService {

    @Autowired
    private RelationAdjacencyStore adjacencyStore;

    private static final int MAX_DEPTH = 6; // 超过6跳视为无关联，直接放弃

    public List<Long> findShortestPath(Long startUserId, Long targetUserId) {
        if (startUserId.equals(targetUserId)) {
            return Collections.singletonList(startUserId);
        }

        // 正向搜索：从起点扩展
        Map<Long, Long> forwardVisited = new HashMap<>(); // 节点 -> 前驱节点
        Queue<Long> forwardQueue = new LinkedList<>();
        forwardQueue.offer(startUserId);
        forwardVisited.put(startUserId, null);

        // 反向搜索：从终点扩展
        Map<Long, Long> backwardVisited = new HashMap<>();
        Queue<Long> backwardQueue = new LinkedList<>();
        backwardQueue.offer(targetUserId);
        backwardVisited.put(targetUserId, null);

        int depth = 0;
        while (!forwardQueue.isEmpty() && !backwardQueue.isEmpty() && depth < MAX_DEPTH) {
            // 每次优先扩展较小的一侧队列，进一步降低搜索空间
            Long meetNode = expandLayer(forwardQueue, forwardVisited, backwardVisited);
            if (meetNode != null) {
                return buildPath(meetNode, forwardVisited, backwardVisited);
            }
            meetNode = expandLayer(backwardQueue, backwardVisited, forwardVisited);
            if (meetNode != null) {
                return buildPath(meetNode, forwardVisited, backwardVisited);
            }
            depth++;
        }
        return Collections.emptyList(); // 超过最大深度未相遇，认为无短链路径
    }

    /**
     * 扩展一层BFS队列，如果扩展过程中与另一侧的visited集合相遇，返回相遇节点
     */
    private Long expandLayer(Queue<Long> queue, Map<Long, Long> visited, Map<Long, Long> otherVisited) {
        int levelSize = queue.size();
        for (int i = 0; i < levelSize; i++) {
            Long current = queue.poll();
            List<Long> neighbors = adjacencyStore.getOutEdges(current, 0, 500)
                    .stream().map(FriendEdge::getToUserId).collect(Collectors.toList());
            for (Long neighbor : neighbors) {
                if (!visited.containsKey(neighbor)) {
                    visited.put(neighbor, current);
                    if (otherVisited.containsKey(neighbor)) {
                        return neighbor; // 双向搜索相遇
                    }
                    queue.offer(neighbor);
                }
            }
        }
        return null;
    }

    private List<Long> buildPath(Long meetNode, Map<Long, Long> forwardVisited, Map<Long, Long> backwardVisited) {
        LinkedList<Long> path = new LinkedList<>();
        Long node = meetNode;
        while (node != null) {
            path.addFirst(node);
            node = forwardVisited.get(node);
        }
        node = backwardVisited.get(meetNode);
        while (node != null) {
            path.addLast(node);
            node = backwardVisited.get(node);
        }
        return path;
    }
}
```

**异常分支处理**：
- 超大扇出账号（好友数千万级）在BFS展开时会导致队列爆炸，需要对单个节点的扩展数量做上限截断（如上面示例中的`limit 500`），牺牲一定准确性换取可用性。
- 如果起点和终点分属完全不相连的两个社交孤岛（在最大深度内未相遇），应直接返回空结果，避免无限搜索。
- 生产环境中通常不会对任意两个用户实时计算最短路径（成本过高），更多是通过离线批量计算 + 缓存的方式，仅对少量高频查询（如"共同好友"页面的关系链展示）做实时兜底。

### 3.5 图数据库选型：Neo4j vs JanusGraph

**问题出发点**：选择合适的图数据库直接决定了系统的可扩展性上限和查询性能。

**方案对比**：

| 维度 | Neo4j | JanusGraph |
| --- | --- | --- |
| 架构模式 | 原生图存储引擎，早期版本以单机为主，企业版支持集群 | 基于外部存储（HBase/Cassandra）+ 索引引擎（Elasticsearch/Solr）的分布式图计算框架 |
| 扩展性 | 单机容量受限，集群方案对超大规模（千亿级边）支撑相对复杂 | 天然分布式，可利用底层存储的水平扩展能力支撑超大规模图数据 |
| 查询语言 | Cypher，语法直观，学习成本低 | Gremlin，图灵完备但学习曲线更陡峭；也可通过适配层支持类Cypher查询 |
| 事务能力 | 支持ACID事务 | 依赖底层存储的一致性模型，跨分片事务能力较弱 |
| 运维复杂度 | 相对简单，一体化产品 | 依赖多套外部组件（存储+索引），运维复杂度较高 |
| 适用场景 | 中等规模（亿级节点/边以内）、对事务一致性要求高的场景 | 超大规模（百亿级以上）、可接受最终一致性的场景 |

**选型建议**：

- 如果社交图谱规模在亿级节点、十亿级边以内，且需要较强的事务一致性保证（例如好友关系的双向写入要保证原子性），优先选择Neo4j一类的原生图数据库，工程实现简单、运维成本低。
- 如果社交图谱规模达到百亿级以上边的量级，且系统已经有成熟的分布式KV存储与搜索引擎作为基础设施，可以选择JanusGraph一类基于外部存储扩展的方案，充分复用已有的分布式存储能力。
- 也可以采用国产分布式图数据库（如NebulaGraph）作为折中方案，兼具原生分布式架构和相对友好的类Cypher查询语言（openCypher），在超大规模场景下具备较好的工程落地经验。

**渐进式演进路径**：绝大多数系统在初期并不需要一步到位引入图数据库，可以先用关系型数据库+Redis缓存邻接表的方式支撑，当好友关系规模、多跳查询需求达到一定量级后，再平滑迁移到图数据库，迁移过程可以采用双写、离线校验、灰度切流的方式渐进完成。

### 3.6 好友推荐算法设计

**问题出发点**：好友推荐是提升社交产品活跃度和用户粘性的关键功能，核心是从海量用户中筛选出"最可能被添加为好友"的候选人。

**算法思路**：好友推荐通常融合多种信号，核心包括：

1. **共同好友数量**（协同过滤的图版本）：共同好友越多，成为好友的可能性越大，这是最基础也是效果最稳定的信号。
2. **兴趣相似度**：基于用户的行为标签（关注的话题、浏览的内容类型）计算余弦相似度或Jaccard相似度。
3. **图结构特征**：例如"三角闭合"（Triadic Closure）理论——如果A和B有共同好友C，那么A和B之间形成好友关系的概率显著高于随机两个用户，这是社交网络中被广泛验证的现象。
4. **地理位置、通讯录匹配等外部信号**：辅助信号，权重通常较低但转化率较高。

**具体实现（共同好友 + 兴趣相似度融合排序）**：

```java
/**
 * 好友推荐候选生成与排序服务
 * 采用"召回-排序"两阶段架构：先从图结构中召回候选人，再用多信号融合排序
 */
@Service
public class FriendRecommendService {

    @Autowired
    private RelationAdjacencyStore adjacencyStore;

    @Autowired
    private UserInterestService userInterestService;

    /**
     * 第一阶段：候选召回
     * 通过"好友的好友"这一二跳查询，召回潜在候选人（典型的图遍历应用）
     */
    public Set<Long> recallCandidates(Long userId) {
        Set<Long> directFriends = adjacencyStore.getOutEdges(userId, 0, 1000)
                .stream().map(FriendEdge::getToUserId).collect(Collectors.toSet());

        Set<Long> candidates = new HashSet<>();
        for (Long friendId : directFriends) {
            List<Long> friendsOfFriend = adjacencyStore.getOutEdges(friendId, 0, 200)
                    .stream().map(FriendEdge::getToUserId).collect(Collectors.toList());
            candidates.addAll(friendsOfFriend);
        }
        candidates.removeAll(directFriends); // 排除已经是好友的
        candidates.remove(userId);           // 排除自己
        return candidates;
    }

    /**
     * 第二阶段：多信号融合排序
     */
    public List<RecommendResult> rankCandidates(Long userId, Set<Long> candidates) {
        List<RecommendResult> results = new ArrayList<>();
        Set<Long> myFriends = adjacencyStore.getOutEdges(userId, 0, 1000)
                .stream().map(FriendEdge::getToUserId).collect(Collectors.toSet());

        for (Long candidateId : candidates) {
            Set<Long> candidateFriends = adjacencyStore.getOutEdges(candidateId, 0, 1000)
                    .stream().map(FriendEdge::getToUserId).collect(Collectors.toSet());

            // 信号1：共同好友数
            int mutualCount = countIntersection(myFriends, candidateFriends);

            // 信号2：兴趣相似度（Jaccard相似度）
            double interestSimilarity = userInterestService.jaccardSimilarity(userId, candidateId);

            // 加权融合得分，权重可通过离线实验/AB测试持续调优
            double score = mutualCount * 0.6 + interestSimilarity * 0.4;

            results.add(new RecommendResult(candidateId, score, mutualCount, interestSimilarity));
        }

        results.sort((a, b) -> Double.compare(b.getScore(), a.getScore()));
        return results.stream().limit(20).collect(Collectors.toList());
    }

    private int countIntersection(Set<Long> setA, Set<Long> setB) {
        Set<Long> smaller = setA.size() < setB.size() ? setA : setB;
        Set<Long> larger = setA.size() < setB.size() ? setB : setA;
        int count = 0;
        for (Long id : smaller) {
            if (larger.contains(id)) {
                count++;
            }
        }
        return count;
    }
}
```

**工程优化点**：
1. 候选召回阶段（二跳查询）计算量较大，通常放在离线批处理中每天/每小时全量计算一次，写入结果缓存，在线服务只做实时的过滤和微调（例如过滤掉刚刚拒绝过的推荐）。
2. 对于活跃用户，可以引入实时特征（如最近共同参与的群聊、最近互动行为）做在线重排序，提升推荐时效性。
3. 需要对推荐结果做多样性打散，避免推荐列表被同一个小圈子的人占满。

### 3.7 社交影响力计算

**问题出发点**：识别KOL、活跃传播节点，用于内容分发优先级、广告定向、风控预警等场景。

**算法思路**：经典的图算法PageRank及其变种可用于衡量节点的影响力。基本思想是：一个节点的重要性取决于指向它的边的数量和质量（指向它的节点本身影响力越大，贡献的权重越高）。

**简化版实现思路**：

```java
/**
 * 简化版PageRank算法，用于计算社交图谱中用户的影响力得分
 * 生产环境通常基于Spark GraphX等分布式图计算框架实现，此处给出单机简化版本便于理解算法核心
 */
public class SocialInfluenceCalculator {

    private static final double DAMPING_FACTOR = 0.85;
    private static final int MAX_ITERATIONS = 20;
    private static final double CONVERGENCE_THRESHOLD = 1e-6;

    /**
     * @param graph 邻接表：key为节点，value为该节点指向的所有节点（即"关注了谁"）
     */
    public Map<Long, Double> calculatePageRank(Map<Long, List<Long>> graph) {
        int n = graph.size();
        Map<Long, Double> rank = new HashMap<>();
        Map<Long, Integer> outDegree = new HashMap<>();

        for (Long node : graph.keySet()) {
            rank.put(node, 1.0 / n);
            outDegree.put(node, graph.get(node).size());
        }

        // 构建反向图：谁关注了我
        Map<Long, List<Long>> reverseGraph = buildReverseGraph(graph);

        for (int iter = 0; iter < MAX_ITERATIONS; iter++) {
            Map<Long, Double> newRank = new HashMap<>();
            double diff = 0.0;

            for (Long node : graph.keySet()) {
                double sum = 0.0;
                List<Long> incomingNodes = reverseGraph.getOrDefault(node, Collections.emptyList());
                for (Long inNode : incomingNodes) {
                    int deg = outDegree.getOrDefault(inNode, 1);
                    sum += rank.get(inNode) / deg;
                }
                double newValue = (1 - DAMPING_FACTOR) / n + DAMPING_FACTOR * sum;
                newRank.put(node, newValue);
                diff += Math.abs(newValue - rank.get(node));
            }

            rank = newRank;
            if (diff < CONVERGENCE_THRESHOLD) {
                break; // 提前收敛，减少不必要的迭代
            }
        }
        return rank;
    }

    private Map<Long, List<Long>> buildReverseGraph(Map<Long, List<Long>> graph) {
        Map<Long, List<Long>> reverse = new HashMap<>();
        for (Map.Entry<Long, List<Long>> entry : graph.entrySet()) {
            for (Long target : entry.getValue()) {
                reverse.computeIfAbsent(target, k -> new ArrayList<>()).add(entry.getKey());
            }
        }
        return reverse;
    }
}
```

**工程落地说明**：单机版PageRank仅适用于小规模验证，生产环境面对亿级节点、十亿级边的社交图谱，必须使用Spark GraphX、Flink Gelly等分布式图计算框架，将迭代计算分布到集群中并行执行，并通过增量计算（只对发生变化的子图重新计算）降低每次全量计算的成本。

### 3.8 大规模社交图谱的分片策略

**问题出发点**：单机或单一图数据库集群无法承载千亿级边的社交图谱，必须进行水平分片（Sharding）。

**分片策略选择**：

1. **按用户ID哈希分片**：将用户ID经过哈希后分配到不同分片，简单均匀，但会导致好友关系边经常跨分片（A和B可能被分到不同分片），多跳查询需要跨分片网络调用，性能下降明显。
2. **按社区/社交圈分片（图分割算法）**：使用图分割算法（如METIS、Louvain社区发现）将联系紧密的用户尽量分到同一分片，减少跨分片边的比例，多跳查询大概率能在单分片内完成。这种方案在读多写少的场景下收益明显，但分片再平衡的复杂度较高。
3. **混合策略**：核心的高频访问关系数据采用社区分片以优化查询局部性，同时用一致性哈希做故障转移与动态扩缩容。

**具体实践建议**：

- 初期用户规模不大时，可采用简单的按用户ID哈希分片 + 关系冗余存储（例如A和B成为好友时，在A所在分片和B所在分片都写一份关系记录），用空间换时间，避免跨分片查询。
- 当规模进一步增长，可以引入离线的社区发现算法定期计算用户聚类，将同一社区的用户尽量迁移到同一物理分片，配合灰度迁移与双写校验保证迁移过程数据一致。
- 对于头部大V账号的粉丝关系，由于粉丝分布通常较为分散（跨越所有分片），无法通过社区分片优化，需要专门设计"大V关系读扩散/写扩散"策略（例如粉丝关注大V采用写扩散到粉丝的收件箱，而不是每次都实时查询大V的关注列表）。

### 3.9 关系数据的批量导入与冷启动

**问题出发点**：新用户注册后如果没有任何好友关系，会直接影响留存——业内普遍认为"新用户在注册后短时间内建立一定数量的社交关系"是关键的活跃度先行指标。因此需要设计一套冷启动阶段的关系导入与好友链路建立机制。

**方案设计**：

1. **通讯录匹配导入**：用户授权通讯录权限后，将手机号（脱敏哈希后）与平台已注册用户的手机号哈希值做匹配，找出通讯录中已经在平台注册的用户，推荐为"可能认识的人"。

2. **第三方账号关系导入**：如果平台支持第三方账号登录（如某社交平台的开放授权），可以在用户同意的前提下，导入其在第三方平台上的已有关系链，作为好友推荐的候选来源。

3. **批量导入的工程实现**：批量导入涉及百万甚至千万级的手机号比对，需要设计高效的批处理链路。

```java
/**
 * 通讯录匹配服务：将用户上传的通讯录（哈希后）与平台注册用户库做批量匹配
 */
@Service
public class ContactMatchService {

    @Autowired
    private UserPhoneHashRepository userPhoneHashRepository;

    private static final int BATCH_SIZE = 1000;

    /**
     * 批量匹配通讯录，返回已注册的用户ID列表
     * 采用分批查询避免一次性构造超大IN查询导致数据库压力过大
     */
    public List<Long> matchContacts(Long currentUserId, List<String> phoneHashes) {
        List<Long> matchedUserIds = new ArrayList<>();

        List<List<String>> batches = Lists.partition(phoneHashes, BATCH_SIZE);
        for (List<String> batch : batches) {
            List<Long> partialResult = userPhoneHashRepository.findUserIdsByPhoneHashIn(batch);
            matchedUserIds.addAll(partialResult);
        }

        // 排除自己和已经是好友的用户，得到真正的推荐候选
        matchedUserIds.remove(currentUserId);
        Set<Long> existingFriends = adjacencyStoreFriendIds(currentUserId);
        matchedUserIds.removeIf(existingFriends::contains);

        return matchedUserIds;
    }

    private Set<Long> adjacencyStoreFriendIds(Long userId) {
        // 复用好友关系存储查询当前好友，避免推荐已存在的关系
        return Collections.emptySet(); // 具体实现依赖RelationAdjacencyStore
    }
}
```

**异常分支处理**：
- 通讯录数据涉及用户隐私，上传前必须对手机号做单向哈希处理（如加盐SHA-256），服务端不应存储明文手机号用于匹配，匹配完成后原始哈希数据应设置较短的保留期限并定期清理。
- 匹配结果可能命中大量弱关系（如快递员、外卖员等联系人），需要结合双方是否互相在通讯录中出现（双向匹配）来提升推荐质量，避免"我加了对方联系方式但对方从未加过我"这种弱关系被误判为强社交推荐。
- 批量导入过程中如果部分批次查询超时或失败，应该采用重试+跳过策略保证整体任务不被单个批次阻塞，导入完成后记录成功率指标便于观测。

### 3.10 关系读扩散与写扩散的权衡

**问题出发点**：当好友或粉丝数量差异巨大时（普通用户 vs 头部大V），采用统一的关系查询策略会造成体验不一致或者资源浪费，需要针对不同量级的账号设计不同的扩散策略。

**方案对比**：

- **写扩散（Push模型）**：关系变更时主动将变更结果写入到所有相关方的"收件箱"（例如好友的动态列表缓存）。优点是读取时直接读收件箱，速度快；缺点是当账号粉丝量极大时，一次写入会扇出成千万次写操作，写入成本高。
- **读扩散（Pull模型）**：关系变更时只更新自身数据，查询方在读取时实时从源头拉取并聚合。优点是写入成本恒定；缺点是读取时如果需要聚合大量关注对象的数据，读取延迟会变高。

**工程实践**：对普通用户（好友数在合理范围内，如几千以内）采用写扩散，保证读取体验最佳；对头部大V采用读扩散或"写扩散+读扩散混合模型"，即普通粉丝走写扩散，但当粉丝量超过某个阈值后自动切换为读扩散，由查询方在读取时做实时合并（例如让活跃用户的Feed流服务在拉取关注列表动态时，对大V账号做特殊的实时查询而非依赖预先推送的收件箱数据）。这种混合模型在保证多数场景读取性能的同时，避免了大V账号造成的写扩散风暴。

## 四、异常处理与容错机制

### 4.1 双向关系一致性保障

好友关系通常需要双向写入（A的好友列表加B，B的好友列表加A），如果两次写入之间发生故障，会导致数据不一致（脏关系）。解决方案：

1. **本地消息表 + 异步补偿**：在同一个事务内，先写入本地关系表和一条"待同步事件"，再由异步任务保证对端数据最终写入成功，失败则重试。
2. **对账任务**：定期扫描全量关系数据，检测"A有B无"的不一致记录，自动修复或告警。

### 4.2 热点账号读写保护

- **读保护**：对粉丝数超过阈值的账号，好友/粉丝列表查询强制走多级缓存（本地缓存 + Redis），并对缓存设置合理的过期时间与随机抖动，避免缓存同时失效造成雪崩。
- **写保护**：大V发布内容或关系变更事件的下游通知，采用异步队列削峰，并对下游消费方做限流保护，避免瞬时扇出流量打垮通知系统。

### 4.3 图数据库故障降级

图数据库出现性能抖动或不可用时，应保证核心链路（是否为好友、好友数展示）可以降级到Redis缓存数据，牺牲一定的实时性（例如缓存的关系数据可能有几秒到几分钟的延迟），保证核心可用性不受影响。对于共同好友、推荐等非强一致场景，可以直接降级返回空结果或使用离线预计算结果兜底。

### 4.4 幂等与并发控制

好友申请、关注等操作需要保证幂等，通常通过数据库唯一索引（fromUserId + toUserId + relationType）或分布式锁实现，避免用户重复点击导致产生重复关系记录。

## 五、性能优化

### 5.1 多级缓存架构

- **一级缓存（本地缓存）**：用于缓存极热账号（如粉丝千万级的大V）的部分聚合数据（如好友数），减少Redis访问压力。
- **二级缓存（Redis）**：缓存好友列表、关注列表、好友数、粉丝数，使用Set/ZSet结构天然支持交集、并集、排序等操作。
- **三级存储（图数据库/关系型数据库）**：作为数据的最终一致性来源。

### 5.2 读写分离与异步化

关系写入采用"同步写主存储 + 异步更新缓存与计数"的模式，避免缓存更新拖慢写入链路的响应时间。计数类数据（好友数、粉丝数）采用增量更新而非每次重新统计，进一步降低计算成本。

### 5.3 批量接口与请求合并

针对"批量查询是否互相关注"等高频场景，提供批量接口，将N次网络往返合并为1次，显著降低网络开销和服务端连接压力。

### 5.4 冷热数据分层

长期不活跃用户的关系数据可以归档到成本更低的冷存储，仅在用户重新活跃时按需加载回热存储，降低整体存储成本。

### 5.5 图查询优化

- 对高频查询路径建立合适的索引（如按relationType、按创建时间的复合索引）。
- 限制单次查询的跳数和返回结果集大小，避免超大结果集拖垮图数据库。
- 对复杂的多跳查询做查询计划分析，必要时通过预计算（如离线计算好每个用户的二跳好友集合）以空间换时间。

## 六、最佳实践与总结

1. **存储模型选择邻接表而非邻接矩阵**，充分利用社交图谱的稀疏性，同时结合图数据库和缓存构建分层存储架构。
2. **关系状态机化**，用状态模式管理好友申请、同意、拒绝、拉黑等复杂流转逻辑，避免代码腐化。
3. **共同好友、六度分隔等图算法优先在小规模场景走精确计算（Redis交集、双向BFS），大规模场景走图数据库原生多跳查询或离线预计算**，根据数据规模动态选择计算路径。
4. **好友推荐采用"离线召回 + 在线排序"的两阶段架构**，兼顾计算成本与推荐时效性。
5. **社交影响力计算依赖分布式图计算框架**，单机算法仅用于原型验证。
6. **大规模图谱必须做分片设计**，优先考虑基于社区发现的图分割策略以优化查询局部性，同时保留一致性哈希作为动态扩缩容的兜底方案。
7. **异常处理的核心是保证双向关系最终一致**，通过本地消息表、异步补偿、定期对账等手段兜底。
8. **性能优化的核心思路是分层降级**：本地缓存 → 分布式缓存 → 图数据库 → 离线预计算结果，任何一层出现问题都有下一层兜底，保证核心链路的高可用。

社交图谱系统的设计本质上是在"存储成本、查询性能、一致性保证"三者之间做权衡。没有一种方案能同时满足所有场景的最优解，实际工程实践中往往需要针对不同的关系规模、不同的业务场景（普通用户 vs 头部大V）采用差异化的技术方案，并通过合理的分层架构将复杂度控制在可维护的范围内。

## 七、全链路实战案例

本章节选取三个最具代表性的业务场景，从Controller入口到存储层、缓存层、消息异步通知，完整展示社交图谱系统在实际生产环境中的全链路实现。每个案例均包含完整的异常处理、日志记录与幂等控制。

### 7.1 案例一：用户关注/取关操作全链路

**问题出发点**：关注/取关是社交图谱中写入频率最高的操作，一次关注操作需要同时维护双向关系数据（关注列表 + 粉丝列表）、更新计数缓存、判断是否形成互相关注（好友关系）、触发Feed流收件箱更新、推送关注通知，整个链路涉及多个存储系统与异步消息，需要在保证数据一致性的同时控制写入延迟。

#### 7.1.1 Controller入口与参数校验

```java
/**
 * 社交关系操作Controller
 * 收敛关注/取关/查询等入口，统一做参数校验与限流
 */
@RestController
@RequestMapping("/api/social/relation")
public class RelationController {

    @Autowired
    private FollowService followService;

    @Autowired
    private RateLimiter rateLimiter;

    private static final Logger log = LoggerFactory.getLogger(RelationController.class);

    /**
     * 关注用户
     * 幂等设计：同一用户对同一目标的重复关注请求不会产生副作用
     */
    @PostMapping("/follow")
    public ResponseEntity<ApiResponse<Void>> follow(
            @RequestHeader("X-User-Id") Long currentUserId,
            @RequestBody @Valid FollowRequest request) {

        // 基础参数校验（@Valid已覆盖注解校验，此处补充业务校验）
        if (currentUserId.equals(request.getTargetUserId())) {
            return ResponseEntity.badRequest()
                    .body(ApiResponse.fail("RELATION_001", "不能关注自己"));
        }

        // 接入层限流：单用户每秒最多5次关系操作
        if (!rateLimiter.tryAcquire("relation:write:" + currentUserId, 5, 1, TimeUnit.SECONDS)) {
            log.warn("用户{}关注操作触发限流, targetUserId={}", currentUserId, request.getTargetUserId());
            return ResponseEntity.status(429)
                    .body(ApiResponse.fail("RELATION_002", "操作过于频繁，请稍后再试"));
        }

        try {
            FollowResult result = followService.follow(currentUserId, request.getTargetUserId(), request.getSource());
            log.info("关注操作完成, userId={}, targetUserId={}, source={}, result={}",
                    currentUserId, request.getTargetUserId(), request.getSource(), result);
            return ResponseEntity.ok(ApiResponse.success(null));
        } catch (RelationBizException e) {
            log.warn("关注操作业务异常, userId={}, targetUserId={}, code={}, msg={}",
                    currentUserId, request.getTargetUserId(), e.getCode(), e.getMessage());
            return ResponseEntity.badRequest().body(ApiResponse.fail(e.getCode(), e.getMessage()));
        } catch (Exception e) {
            log.error("关注操作系统异常, userId={}, targetUserId={}",
                    currentUserId, request.getTargetUserId(), e);
            return ResponseEntity.internalServerError()
                    .body(ApiResponse.fail("RELATION_500", "系统繁忙，请稍后再试"));
        }
    }

    /**
     * 取消关注
     */
    @PostMapping("/unfollow")
    public ResponseEntity<ApiResponse<Void>> unfollow(
            @RequestHeader("X-User-Id") Long currentUserId,
            @RequestBody @Valid UnfollowRequest request) {

        if (currentUserId.equals(request.getTargetUserId())) {
            return ResponseEntity.badRequest()
                    .body(ApiResponse.fail("RELATION_001", "参数非法"));
        }

        if (!rateLimiter.tryAcquire("relation:write:" + currentUserId, 5, 1, TimeUnit.SECONDS)) {
            log.warn("用户{}取关操作触发限流, targetUserId={}", currentUserId, request.getTargetUserId());
            return ResponseEntity.status(429)
                    .body(ApiResponse.fail("RELATION_002", "操作过于频繁，请稍后再试"));
        }

        try {
            followService.unfollow(currentUserId, request.getTargetUserId());
            log.info("取关操作完成, userId={}, targetUserId={}", currentUserId, request.getTargetUserId());
            return ResponseEntity.ok(ApiResponse.success(null));
        } catch (RelationBizException e) {
            log.warn("取关操作业务异常, userId={}, targetUserId={}, code={}, msg={}",
                    currentUserId, request.getTargetUserId(), e.getCode(), e.getMessage());
            return ResponseEntity.badRequest().body(ApiResponse.fail(e.getCode(), e.getMessage()));
        } catch (Exception e) {
            log.error("取关操作系统异常, userId={}, targetUserId={}",
                    currentUserId, request.getTargetUserId(), e);
            return ResponseEntity.internalServerError()
                    .body(ApiResponse.fail("RELATION_500", "系统繁忙，请稍后再试"));
        }
    }
}
```

#### 7.1.2 关注关系写入与缓存更新

```java
/**
 * 关注服务核心实现
 * 关注操作全链路：幂等校验 → 黑名单校验 → 双向关系写入 → 计数更新 → 互关判断 → Feed更新 → 通知推送
 */
@Service
public class FollowService {

    @Autowired
    private RelationAdjacencyStore adjacencyStore;

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    @Autowired
    private BlockRelationService blockRelationService;

    @Autowired
    private FeedInboxService feedInboxService;

    @Autowired
    private NotificationService notificationService;

    @Autowired
    private RelationEventProducer eventProducer;

    @Autowired
    private RedissonClient redissonClient;

    private static final Logger log = LoggerFactory.getLogger(FollowService.class);

    // Redis Key 前缀定义
    private static final String FOLLOW_SET_KEY = "follow:set:";   // 关注列表Set
    private static final String FANS_SET_KEY = "fans:set:";       // 粉丝列表Set
    private static final String FOLLOW_COUNT_KEY = "follow:count:"; // 关注数计数器
    private static final String FANS_COUNT_KEY = "fans:count:";   // 粉丝数计数器
    private static final String FRIEND_SET_KEY = "friend:set:";   // 好友（互关）Set

    /**
     * 关注用户全链路
     *
     * @param userId       操作发起者
     * @param targetUserId 被关注者
     * @param source       关注来源（搜索/推荐/主页/扫码等）
     */
    @Transactional(rollbackFor = Exception.class)
    public FollowResult follow(Long userId, Long targetUserId, String source) {

        // ---------- 第1步：分布式锁保证幂等，防止并发重复关注 ----------
        String lockKey = "lock:follow:" + userId + ":" + targetUserId;
        RLock lock = redissonClient.getLock(lockKey);
        boolean acquired = false;
        try {
            acquired = lock.tryLock(3, 10, TimeUnit.SECONDS);
            if (!acquired) {
                log.warn("关注操作获取锁失败, 可能存在并发重复请求, userId={}, targetUserId={}", userId, targetUserId);
                throw new RelationBizException("RELATION_003", "操作处理中，请勿重复提交");
            }

            // ---------- 第2步：幂等校验，已关注则直接返回成功 ----------
            if (isFollowing(userId, targetUserId)) {
                log.info("用户{}已关注{}，幂等返回", userId, targetUserId);
                return FollowResult.alreadyFollowing();
            }

            // ---------- 第3步：黑名单校验 ----------
            if (blockRelationService.isBlocked(targetUserId, userId)) {
                log.info("用户{}被{}拉黑，关注请求被拒绝", userId, targetUserId);
                throw new RelationBizException("RELATION_004", "操作无法完成");
            }

            // ---------- 第4步：双向关系写入（图数据库 + MySQL流水） ----------
            long now = System.currentTimeMillis();
            FriendEdge followEdge = new FriendEdge(userId, targetUserId, RelationType.FOLLOW,
                    RelationStatus.ACCEPTED, now, source);

            try {
                // 写入图数据库：关注列表（A→B）与粉丝列表（B→A的入边）
                adjacencyStore.addEdge(followEdge);
                log.debug("图数据库关系写入成功, {} -> {}", userId, targetUserId);
            } catch (Exception e) {
                log.error("图数据库写入失败, userId={}, targetUserId={}", userId, targetUserId, e);
                throw new RelationBizException("RELATION_005", "关系写入失败");
            }

            // ---------- 第5步：Redis缓存更新（关注列表Set + 粉丝列表Set + 双方计数器） ----------
            updateFollowCache(userId, targetUserId, true);

            // ---------- 第6步：判断是否互相关注（好友关系建立） ----------
            boolean mutualFollow = isFollowing(targetUserId, userId);
            if (mutualFollow) {
                // 互相关注，将对方加入各自的好友Set
                redisTemplate.opsForSet().add(FRIEND_SET_KEY + userId, targetUserId.toString());
                redisTemplate.opsForSet().add(FRIEND_SET_KEY + targetUserId, userId.toString());
                log.info("互相关注建立好友关系, userId={}, targetUserId={}", userId, targetUserId);
            }

            // ---------- 第7步：Feed流收件箱更新 ----------
            // 采用写扩散模型：将被关注者的近期动态推送到关注者的收件箱
            try {
                feedInboxService.onNewFollow(userId, targetUserId);
            } catch (Exception e) {
                // Feed更新失败不影响关注操作本身，记录日志由补偿任务处理
                log.warn("Feed收件箱更新失败, userId={}, targetUserId={}", userId, targetUserId, e);
            }

            // ---------- 第8步：异步通知推送 ----------
            try {
                notificationService.sendFollowNotification(targetUserId, userId, source);
            } catch (Exception e) {
                log.warn("关注通知推送失败, targetUserId={}, followerId={}", targetUserId, userId, e);
            }

            // ---------- 第9步：发布关系变更事件，供下游（推荐系统/风控/数据分析）消费 ----------
            RelationChangeEvent event = RelationChangeEvent.builder()
                    .userId(userId)
                    .targetUserId(targetUserId)
                    .action(RelationAction.FOLLOW)
                    .mutualFollow(mutualFollow)
                    .source(source)
                    .timestamp(now)
                    .build();
            eventProducer.publish(event);

            return FollowResult.success(mutualFollow);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RelationBizException("RELATION_006", "操作被中断");
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }

    /**
     * 取消关注（逆向流程）
     */
    @Transactional(rollbackFor = Exception.class)
    public void unfollow(Long userId, Long targetUserId) {

        String lockKey = "lock:unfollow:" + userId + ":" + targetUserId;
        RLock lock = redissonClient.getLock(lockKey);
        boolean acquired = false;
        try {
            acquired = lock.tryLock(3, 10, TimeUnit.SECONDS);
            if (!acquired) {
                throw new RelationBizException("RELATION_003", "操作处理中，请勿重复提交");
            }

            // 幂等校验：未关注则直接返回
            if (!isFollowing(userId, targetUserId)) {
                log.info("用户{}未关注{}，取关幂等返回", userId, targetUserId);
                return;
            }

            // 逆向写入：删除图数据库中的关注边
            try {
                adjacencyStore.removeEdge(userId, targetUserId, RelationType.FOLLOW);
                log.debug("图数据库关系删除成功, {} -> {}", userId, targetUserId);
            } catch (Exception e) {
                log.error("图数据库删除失败, userId={}, targetUserId={}", userId, targetUserId, e);
                throw new RelationBizException("RELATION_005", "关系删除失败");
            }

            // 逆向缓存更新：从关注列表/粉丝列表移除，计数器递减
            updateFollowCache(userId, targetUserId, false);

            // 如果之前是互相关注，需要移除好友关系
            if (redisTemplate.opsForSet().isMember(FRIEND_SET_KEY + userId, targetUserId.toString())) {
                redisTemplate.opsForSet().remove(FRIEND_SET_KEY + userId, targetUserId.toString());
                redisTemplate.opsForSet().remove(FRIEND_SET_KEY + targetUserId, userId.toString());
                log.info("取关导致好友关系解除, userId={}, targetUserId={}", userId, targetUserId);
            }

            // Feed流收件箱清理：移除被取关者的动态
            try {
                feedInboxService.onUnfollow(userId, targetUserId);
            } catch (Exception e) {
                log.warn("Feed收件箱清理失败, userId={}, targetUserId={}", userId, targetUserId, e);
            }

            // 发布取关事件
            RelationChangeEvent event = RelationChangeEvent.builder()
                    .userId(userId)
                    .targetUserId(targetUserId)
                    .action(RelationAction.UNFOLLOW)
                    .timestamp(System.currentTimeMillis())
                    .build();
            eventProducer.publish(event);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RelationBizException("RELATION_006", "操作被中断");
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }

    /**
     * 更新关注/粉丝缓存
     * @param isFollow true=关注操作, false=取关操作
     */
    private void updateFollowCache(Long userId, Long targetUserId, boolean isFollow) {
        try {
            if (isFollow) {
                // 关注操作：A的关注列表加B，B的粉丝列表加A
                redisTemplate.opsForSet().add(FOLLOW_SET_KEY + userId, targetUserId.toString());
                redisTemplate.opsForSet().add(FANS_SET_KEY + targetUserId, userId.toString());
                redisTemplate.opsForValue().increment(FOLLOW_COUNT_KEY + userId);
                redisTemplate.opsForValue().increment(FANS_COUNT_KEY + targetUserId);
            } else {
                // 取关操作：逆向移除
                redisTemplate.opsForSet().remove(FOLLOW_SET_KEY + userId, targetUserId.toString());
                redisTemplate.opsForSet().remove(FANS_SET_KEY + targetUserId, userId.toString());
                redisTemplate.opsForValue().decrement(FOLLOW_COUNT_KEY + userId);
                redisTemplate.opsForValue().decrement(FANS_COUNT_KEY + targetUserId);
            }
        } catch (Exception e) {
            // 缓存更新失败不回滚事务，由缓存补偿任务定期校正
            log.error("缓存更新失败, userId={}, targetUserId={}, isFollow={}",
                    userId, targetUserId, isFollow, e);
        }
    }

    /**
     * 判断userId是否关注了targetUserId
     * 优先查Redis Set（O(1)），缓存不存在时降级查图数据库
     */
    public boolean isFollowing(Long userId, Long targetUserId) {
        try {
            Boolean isMember = redisTemplate.opsForSet().isMember(FOLLOW_SET_KEY + userId, targetUserId.toString());
            if (isMember != null) {
                return isMember;
            }
        } catch (Exception e) {
            log.warn("Redis查询关注状态失败, 降级查图数据库, userId={}, targetUserId={}", userId, targetUserId, e);
        }
        // 缓存未命中或异常，降级查图数据库
        return adjacencyStore.hasEdge(userId, targetUserId, RelationType.FOLLOW);
    }
}
```

### 7.2 案例二：好友推荐全链路

#### 7.2.2 推荐Facade：多路召回 + 过滤 + 排序

```java
/**
 * 好友推荐Facade：编排多路召回、过滤、排序的完整链路
 */
@Service
public class FriendRecommendFacade {

    @Autowired
    private MutualFriendRecallService mutualFriendRecallService;

    @Autowired
    private InterestTagRecallService interestTagRecallService;

    @Autowired
    private ContactRecallService contactRecallService;

    @Autowired
    private RecommendFilterService filterService;

    @Autowired
    private RecommendCacheService cacheService;

    @Autowired
    private UserBasicInfoService userBasicInfoService;

    private static final Logger log = LoggerFactory.getLogger(FriendRecommendFacade.class);

    private static final int RECALL_LIMIT = 500;   // 每路召回上限
    private static final int FINAL_PAGE_SIZE = 20;  // 最终返回数量

    /**
     * 获取推荐列表全链路
     * 离线预计算结果 → 在线多路召回补充 → 过滤 → 排序 → 缓存
     */
    public RecommendPageResult getRecommendList(Long userId, int page, int pageSize) {
        long startTime = System.currentTimeMillis();

        // ---------- 第1步：优先读取缓存 ----------
        RecommendPageResult cached = cacheService.getCachedRecommend(userId, page, pageSize);
        if (cached != null && !cached.getList().isEmpty()) {
            log.info("推荐命中缓存, userId={}, page={}, count={}", userId, page, cached.getList().size());
            return cached;
        }

        // ---------- 第2步：多路召回 ----------
        Set<Long> candidates = new HashSet<>();

        // 路径A：二度好友（共同好友数排序），优先使用离线预计算结果
        try {
            List<Long> mutualFriendCandidates = mutualFriendRecallService.recall(userId, RECALL_LIMIT);
            candidates.addAll(mutualFriendCandidates);
            log.debug("二度好友召回完成, userId={}, count={}", userId, mutualFriendCandidates.size());
        } catch (Exception e) {
            log.warn("二度好友召回失败, userId={}", userId, e);
        }

        // 路径B：基于兴趣标签的推荐
        try {
            List<Long> interestCandidates = interestTagRecallService.recall(userId, RECALL_LIMIT);
            candidates.addAll(interestCandidates);
            log.debug("兴趣标签召回完成, userId={}, count={}", userId, interestCandidates.size());
        } catch (Exception e) {
            log.warn("兴趣标签召回失败, userId={}", userId, e);
        }

        // 路径C：通讯录匹配推荐（冷启动用户专属，转化率高）
        try {
            List<Long> contactCandidates = contactRecallService.recall(userId, RECALL_LIMIT);
            candidates.addAll(contactCandidates);
            log.debug("通讯录召回完成, userId={}, count={}", userId, contactCandidates.size());
        } catch (Exception e) {
            log.warn("通讯录召回失败, userId={}", userId, e);
        }

        if (candidates.isEmpty()) {
            log.info("推荐召回为空, userId={}", userId);
            return RecommendPageResult.empty();
        }

        // ---------- 第3步：过滤（已关注、已屏蔽、黑名单、已推荐拒绝过） ----------
        List<Long> filtered = filterService.filter(userId, new ArrayList<>(candidates));
        log.debug("过滤后剩余候选, userId={}, before={}, after={}",
                userId, candidates.size(), filtered.size());

        if (filtered.isEmpty()) {
            return RecommendPageResult.empty();
        }

        // ---------- 第4步：多信号融合排序 ----------
        List<RecommendItem> ranked = rankAndMerge(userId, filtered);

        // ---------- 第5步：分页截取 ----------
        int fromIndex = (page - 1) * pageSize;
        int toIndex = Math.min(fromIndex + pageSize, ranked.size());
        List<RecommendItem> pageData = fromIndex < ranked.size()
                ? ranked.subList(fromIndex, toIndex)
                : Collections.emptyList();

        // ---------- 第6步：聚合用户基础信息（头像、昵称等） ----------
        List<Long> userIds = pageData.stream().map(RecommendItem::getUserId).collect(Collectors.toList());
        Map<Long, UserBasicInfo> userInfos = userBasicInfoService.batchGet(userIds);

        List<RecommendVO> voList = pageData.stream().map(item -> {
            UserBasicInfo info = userInfos.get(item.getUserId());
            RecommendVO vo = new RecommendVO();
            vo.setUserId(item.getUserId());
            vo.setNickname(info != null ? info.getNickname() : "");
            vo.setAvatar(info != null ? info.getAvatar() : "");
            vo.setMutualFriendCount(item.getMutualFriendCount());
            vo.setSource(item.getSource());
            return vo;
        }).collect(Collectors.toList());

        RecommendPageResult result = new RecommendPageResult(voList, page, pageSize, ranked.size());

        // ---------- 第7步：写入缓存 ----------
        try {
            cacheService.cacheRecommend(userId, page, pageSize, result);
        } catch (Exception e) {
            log.warn("推荐结果缓存写入失败, userId={}", userId, e);
        }

        long costMs = System.currentTimeMillis() - startTime;
        log.info("推荐链路完成, userId={}, page={}, totalCandidates={}, finalCount={}, costMs={}",
                userId, page, candidates.size(), voList.size(), costMs);

        return result;
    }

    /**
     * 多信号融合排序
     */
    private List<RecommendItem> rankAndMerge(Long userId, List<Long> candidates) {
        List<RecommendItem> items = new ArrayList<>();

        for (Long candidateId : candidates) {
            RecommendItem item = new RecommendItem();
            item.setUserId(candidateId);

            // 信号1：共同好友数（权重0.5）
            int mutualCount = mutualFriendRecallService.getMutualFriendCount(userId, candidateId);
            item.setMutualFriendCount(mutualCount);

            // 信号2：兴趣相似度（权重0.3）
            double interestScore = interestTagRecallService.getInterestSimilarity(userId, candidateId);

            // 信号3：来源权重（通讯录0.2 > 二度好友0.15 > 兴趣0.1）
            double sourceScore = item.getSource() == RecommendSource.CONTACT ? 0.2
                    : item.getSource() == RecommendSource.MUTUAL_FRIEND ? 0.15 : 0.1;

            double finalScore = mutualCount * 0.5 + interestScore * 0.3 + sourceScore;
            item.setScore(finalScore);

            items.add(item);
        }

        // 降序排列，取前FINAL_PAGE_SIZE * 页数
        items.sort((a, b) -> Double.compare(b.getScore(), a.getScore()));
        return items.stream().limit(FINAL_PAGE_SIZE * 5).collect(Collectors.toList());
    }
}
```

#### 7.2.3 二度好友推荐算法（共同好友数排序）

```java
/**
 * 二度好友召回服务
 * 算法：好友的好友（二跳邻居），按共同好友数排序
 * 离线预计算 + 在线实时补充
 */
@Service
public class MutualFriendRecallService {

    @Autowired
    private RelationAdjacencyStore adjacencyStore;

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final Logger log = LoggerFactory.getLogger(MutualFriendRecallService.class);

    private static final String RECALL_CACHE_KEY = "recommend:recall:mutual:";
    private static final int FRIEND_SCAN_LIMIT = 500;      // 每个用户扫描的好友数上限
    private static final int FOF_SCAN_LIMIT = 200;        // 每个好友扫描的二跳好友数上限

    /**
     * 召回二度好友候选
     */
    public List<Long> recall(Long userId, int limit) {
        // 优先读取离线预计算结果
        try {
            String cacheKey = RECALL_CACHE_KEY + userId;
            Set<String> cached = redisTemplate.opsForZSet().reverseRange(cacheKey, 0, limit - 1);
            if (cached != null && !cached.isEmpty()) {
                return cached.stream().map(Long::parseLong).collect(Collectors.toList());
            }
        } catch (Exception e) {
            log.warn("读取离线召回缓存失败, userId={}, 降级实时计算", userId, e);
        }

        // 缓存未命中，实时计算（降级路径，通常仅在缓存失效时触发）
        return recallRealtime(userId, limit);
    }

    /**
     * 实时二跳遍历召回
     * 使用计数Map统计每个候选人的共同好友数
     */
    private List<Long> recallRealtime(Long userId, int limit) {
        // 第1步：获取直接好友列表
        Set<Long> directFriends = adjacencyStore.getOutEdges(userId, 0, FRIEND_SCAN_LIMIT)
                .stream().map(FriendEdge::getToUserId).collect(Collectors.toSet());

        if (directFriends.isEmpty()) {
            return Collections.emptyList();
        }

        // 第2步：遍历每个好友的好友，统计二跳出现频次（即共同好友数）
        Map<Long, Integer> candidateScoreMap = new HashMap<>();

        for (Long friendId : directFriends) {
            try {
                List<FriendEdge> fofEdges = adjacencyStore.getOutEdges(friendId, 0, FOF_SCAN_LIMIT);
                for (FriendEdge edge : fofEdges) {
                    Long candidateId = edge.getToUserId();
                    // 排除自己和已是好友的用户
                    if (candidateId.equals(userId) || directFriends.contains(candidateId)) {
                        continue;
                    }
                    candidateScoreMap.merge(candidateId, 1, Integer::sum);
                }
            } catch (Exception e) {
                log.warn("遍历好友{}的二跳邻居失败, userId={}", friendId, userId, e);
                // 单个好友遍历失败不影响整体召回
            }
        }

        // 第3步：按共同好友数降序排序，取TopN
        return candidateScoreMap.entrySet().stream()
                .sorted(Map.Entry.<Long, Integer>comparingByValue().reversed())
                .limit(limit)
                .map(Map.Entry::getKey)
                .collect(Collectors.toList());
    }

    /**
     * 获取共同好友数（用于排序阶段）
     */
    public int getMutualFriendCount(Long userIdA, Long userIdB) {
        try {
            // 使用Redis SINTER在服务端求交集大小，避免数据搬运
            Long count = redisTemplate.opsForSet()
                    .intersectAndStore(
                            "friend:set:" + userIdA,
                            "friend:set:" + userIdB,
                            "tmp:mutual:" + userIdA + ":" + userIdB);
            // 清理临时Key
            redisTemplate.delete("tmp:mutual:" + userIdA + ":" + userIdB);
            return count != null ? count.intValue() : 0;
        } catch (Exception e) {
            log.warn("Redis求交集失败, 降级为图数据库查询, userIdA={}, userIdB={}", userIdA, userIdB, e);
            return 0;
        }
    }
}
```

#### 7.2.4 推荐结果过滤

```java
/**
 * 推荐结果过滤服务
 * 过滤维度：已关注、已屏蔽、黑名单、已拒绝推荐、账号异常
 */
@Service
public class RecommendFilterService {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    @Autowired
    private BlockRelationService blockRelationService;

    @Autowired
    private RelationAdjacencyStore adjacencyStore;

    private static final Logger log = LoggerFactory.getLogger(RecommendFilterService.class);

    private static final String RECOMMEND_REJECT_KEY = "recommend:rejected:"; // 用户已拒绝的推荐
    private static final int REJECT_RETENTION_HOURS = 72;                     // 拒绝记录保留72小时

    /**
     * 过滤候选列表
     */
    public List<Long> filter(Long userId, List<Long> candidates) {
        if (candidates.isEmpty()) {
            return candidates;
        }

        // 获取用户的关注列表Set，用于排除已关注
        Set<String> followingSet;
        try {
            Set<String> cached = redisTemplate.opsForSet().members("follow:set:" + userId);
            followingSet = cached != null ? cached : Collections.emptySet();
        } catch (Exception e) {
            log.warn("读取关注列表缓存失败, 降级查图数据库, userId={}", userId, e);
            followingSet = adjacencyStore.getOutEdges(userId, 0, 5000)
                    .stream().map(e -> String.valueOf(e.getToUserId()))
                    .collect(Collectors.toSet());
        }

        // 获取已拒绝推荐的候选人列表
        Set<String> rejectedSet;
        try {
            Set<String> cached = redisTemplate.opsForSet().members(RECOMMEND_REJECT_KEY + userId);
            rejectedSet = cached != null ? cached : Collections.emptySet();
        } catch (Exception e) {
            log.warn("读取已拒绝推荐列表失败, userId={}", userId, e);
            rejectedSet = Collections.emptySet();
        }

        List<Long> filtered = new ArrayList<>(candidates.size());
        for (Long candidateId : candidates) {
            String candidateStr = candidateId.toString();

            // 过滤1：已关注
            if (followingSet.contains(candidateStr)) {
                continue;
            }

            // 过滤2：用户已主动拒绝过该推荐
            if (rejectedSet.contains(candidateStr)) {
                continue;
            }

            // 过滤3：黑名单（任一方拉黑对方）
            try {
                if (blockRelationService.isBlocked(userId, candidateId)
                        || blockRelationService.isBlocked(candidateId, userId)) {
                    continue;
                }
            } catch (Exception e) {
                log.warn("黑名单查询失败, userId={}, candidateId={}", userId, candidateId, e);
                // 黑名单查询失败时保守处理：跳过该候选人
                continue;
            }

            filtered.add(candidateId);
        }

        return filtered;
    }

    /**
     * 记录用户拒绝某条推荐，后续不再展示
     */
    public void recordReject(Long userId, Long rejectedUserId) {
        try {
            String key = RECOMMEND_REJECT_KEY + userId;
            redisTemplate.opsForSet().add(key, rejectedUserId.toString());
            redisTemplate.expire(key, REJECT_RETENTION_HOURS, TimeUnit.HOURS);
        } catch (Exception e) {
            log.error("记录推荐拒绝失败, userId={}, rejectedUserId={}", userId, rejectedUserId, e);
        }
    }
}
```

#### 7.2.5 推荐结果缓存与更新策略

```java
/**
 * 推荐结果缓存服务
 * 缓存策略：首页缓存5分钟，翻页缓存1分钟，用户产生新关注后主动失效
 */
@Service
public class RecommendCacheService {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final String CACHE_KEY_PREFIX = "recommend:result:";
    private static final int FIRST_PAGE_TTL_MINUTES = 5;
    private static final int OTHER_PAGE_TTL_MINUTES = 1;

    private static final Logger log = LoggerFactory.getLogger(RecommendCacheService.class);

    /**
     * 读取缓存的推荐结果
     */
    public RecommendPageResult getCachedRecommend(Long userId, int page, int pageSize) {
        try {
            String key = CACHE_KEY_PREFIX + userId + ":" + page + ":" + pageSize;
            String json = redisTemplate.opsForValue().get(key);
            if (json != null) {
                return JSON.parseObject(json, RecommendPageResult.class);
            }
        } catch (Exception e) {
            log.warn("读取推荐缓存失败, userId={}, page={}", userId, page, e);
        }
        return null;
    }

    /**
     * 写入推荐结果缓存
     */
    public void cacheRecommend(Long userId, int page, int pageSize, RecommendPageResult result) {
        try {
            String key = CACHE_KEY_PREFIX + userId + ":" + page + ":" + pageSize;
            String json = JSON.toJSONString(result);
            int ttl = page == 1 ? FIRST_PAGE_TTL_MINUTES : OTHER_PAGE_TTL_MINUTES;
            redisTemplate.opsForValue().set(key, json, ttl, TimeUnit.MINUTES);
        } catch (Exception e) {
            log.warn("写入推荐缓存失败, userId={}, page={}", userId, page, e);
        }
    }

    /**
     * 用户产生新关注/取关后，主动失效推荐缓存
     * 由FollowService在关系变更后调用
     */
    public void invalidateCache(Long userId) {
        try {
            Set<String> keys = redisTemplate.keys(CACHE_KEY_PREFIX + userId + ":*");
            if (keys != null && !keys.isEmpty()) {
                redisTemplate.delete(keys);
                log.info("推荐缓存已失效, userId={}, keyCount={}", userId, keys.size());
            }
        } catch (Exception e) {
            log.warn("推荐缓存失效失败, userId={}", userId, e);
        }
    }
}
```

#### 7.2.6 推荐链路异常处理总结

| 异常场景 | 处理策略 | 影响范围 |
| --- | --- | --- |
| 离线预计算结果缓存未命中 | 降级为实时二跳遍历召回，限制扫描范围 | 响应延迟增加但功能可用 |
| 单路召回服务超时 | 跳过该路召回，使用其他路结果补充 | 推荐多样性下降 |
| 兴趣相似度计算失败 | 该信号得分置0，不影响整体排序流程 | 排序精度下降 |
| 过滤服务中黑名单查询失败 | 保守跳过该候选人 | 推荐数量减少 |
| 用户信息聚合部分失败 | 缺失字段返回默认值，不阻断整体响应 | 展示不完整但页面可用 |
| 全链路异常 | 返回空列表，保证页面不白屏 | 用户需稍后重试 |

### 7.3 案例三：共同好友查询全链路

**问题出发点**：共同好友查询是社交产品中高频使用的功能，用户查看他人主页时通常会展示"你们有N个共同好友"。该查询本质上是两个好友集合的交集运算，在普通用户间可快速完成，但当一方为千万级粉丝的大V时，集合求交的开销会急剧上升，需要设计分级降级策略。

#### 7.3.1 共同好友查询入口


#### 7.3.2 共同好友Facade：分级查询策略

```java
/**
 * 共同好友查询Facade
 * 根据双方好友数量规模选择不同的查询策略：
 *   - 双方好友数 < 阈值：Redis SINTER求交集（最优路径）
 *   - 任一方好友数 >= 阈值：图数据库多跳查询（避免大Set搬运）
 *   - 超大V账号（千万级粉丝）：近似估算 + 结果缓存（降级路径）
 */
@Service
public class MutualFriendFacade {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    @Autowired
    private GraphQueryService graphQueryService;

    @Autowired
    private UserBasicInfoService userBasicInfoService;

    @Autowired
    private MutualFriendCacheService cacheService;

    private static final Logger log = LoggerFactory.getLogger(MutualFriendFacade.class);

    private static final String FRIEND_SET_KEY = "friend:set:";
    private static final String FRIEND_COUNT_KEY = "friend:count:";

    // 策略选择阈值
    private static final long REDIS_SINTER_THRESHOLD = 50_000;     // 5万以下走Redis
    private static final long SUPER_VIP_THRESHOLD = 1_000_000;     // 百万以上走降级估算

    /**
     * 查询共同好友完整列表（分页）
     */
    public MutualFriendResult getMutualFriends(Long userIdA, Long userIdB, int page, int pageSize) {
        long startTime = System.currentTimeMillis();

        // ---------- 第1步：查询缓存 ----------
        MutualFriendResult cached = cacheService.getCachedResult(userIdA, userIdB, page, pageSize);
        if (cached != null) {
            log.debug("共同好友查询命中缓存, userIdA={}, userIdB={}", userIdA, userIdB);
            return cached;
        }

        // ---------- 第2步：获取双方好友数，决定查询策略 ----------
        long sizeA = getFriendCount(userIdA);
        long sizeB = getFriendCount(userIdB);

        List<Long> mutualIds;

        if (sizeA >= SUPER_VIP_THRESHOLD || sizeB >= SUPER_VIP_THRESHOLD) {
            // ---------- 策略C：超大V降级，返回空列表或走近似估算 ----------
            log.info("超大V共同好友降级, userIdA={}, sizeA={}, userIdB={}, sizeB={}", userIdA, sizeA, userIdB, sizeB);
            mutualIds = Collections.emptyList();

        } else if (sizeA < REDIS_SINTER_THRESHOLD && sizeB < REDIS_SINTER_THRESHOLD) {
            // ---------- 策略A：Redis SINTER求交集 ----------
            mutualIds = queryViaRedisSinter(userIdA, userIdB);

        } else {
            // ---------- 策略B：图数据库多跳查询 ----------
            log.info("走图数据库查询共同好友, userIdA={}, sizeA={}, userIdB={}, sizeB={}", userIdA, sizeA, userIdB, sizeB);
            mutualIds = queryViaGraph(userIdA, userIdB);
        }

        // ---------- 第3步：分页截取 ----------
        int totalCount = mutualIds.size();
        int fromIndex = (page - 1) * pageSize;
        int toIndex = Math.min(fromIndex + pageSize, totalCount);
        List<Long> pageIds = fromIndex < totalCount
                ? mutualIds.subList(fromIndex, toIndex)
                : Collections.emptyList();

        // ---------- 第4步：聚合用户信息 ----------
        Map<Long, UserBasicInfo> userInfos = userBasicInfoService.batchGet(pageIds);
        List<MutualFriendVO> voList = pageIds.stream().map(id -> {
            UserBasicInfo info = userInfos.get(id);
            MutualFriendVO vo = new MutualFriendVO();
            vo.setUserId(id);
            vo.setNickname(info != null ? info.getNickname() : "未知用户");
            vo.setAvatar(info != null ? info.getAvatar() : "");
            return vo;
        }).collect(Collectors.toList());

        MutualFriendResult result = new MutualFriendResult(voList, totalCount, page, pageSize);

        // ---------- 第5步：写入缓存 ----------
        try {
            cacheService.cacheResult(userIdA, userIdB, page, pageSize, result);
        } catch (Exception e) {
            log.warn("共同好友结果缓存失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
        }

        long costMs = System.currentTimeMillis() - startTime;
        log.info("共同好友查询完成, userIdA={}, userIdB={}, total={}, returned={}, strategy={}, costMs={}",
                userIdA, userIdB, totalCount, voList.size(), getStrategyName(sizeA, sizeB), costMs);

        return result;
    }

    /**
     * 仅查询共同好友数量（轻量接口）
     */
    public int getMutualFriendCount(Long userIdA, Long userIdB) {
        // 优先查缓存
        Integer cachedCount = cacheService.getCachedCount(userIdA, userIdB);
        if (cachedCount != null) {
            return cachedCount;
        }

        long sizeA = getFriendCount(userIdA);
        long sizeB = getFriendCount(userIdB);

        int count;
        if (sizeA >= SUPER_VIP_THRESHOLD || sizeB >= SUPER_VIP_THRESHOLD) {
            // 超大V降级：返回0或近似值
            count = 0;
        } else if (sizeA < REDIS_SINTER_THRESHOLD && sizeB < REDIS_SINTER_THRESHOLD) {
            // Redis SINTERCARD求交集大小（Redis 7.0+），不需要搬运结果集
            try {
                String keyA = FRIEND_SET_KEY + userIdA;
                String keyB = FRIEND_SET_KEY + userIdB;
                Long result = redisTemplate.opsForSet().intersectAndStore(keyA, keyB, "tmp:mutual:count:" + userIdA + ":" + userIdB);
                redisTemplate.delete("tmp:mutual:count:" + userIdA + ":" + userIdB);
                count = result != null ? result.intValue() : 0;
            } catch (Exception e) {
                log.warn("Redis SINTER求交集失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
                count = 0;
            }
        } else {
            // 图数据库COUNT查询
            try {
                count = graphQueryService.countMutualFriends(userIdA, userIdB);
            } catch (Exception e) {
                log.warn("图数据库共同好友计数失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
                count = 0;
            }
        }

        // 缓存计数结果
        try {
            cacheService.cacheCount(userIdA, userIdB, count);
        } catch (Exception e) {
            log.warn("共同好友计数缓存失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
        }

        return count;
    }

    /**
     * Redis SINTER求交集
     */
    private List<Long> queryViaRedisSinter(Long userIdA, Long userIdB) {
        try {
            String keyA = FRIEND_SET_KEY + userIdA;
            String keyB = FRIEND_SET_KEY + userIdB;
            Set<String> intersection = redisTemplate.opsForSet().intersect(keyA, keyB);
            if (intersection == null || intersection.isEmpty()) {
                return Collections.emptyList();
            }
            return intersection.stream().map(Long::parseLong).collect(Collectors.toList());
        } catch (Exception e) {
            log.warn("Redis SINTER查询失败, 降级图数据库, userIdA={}, userIdB={}", userIdA, userIdB, e);
            return queryViaGraph(userIdA, userIdB);
        }
    }

    /**
     * 图数据库多跳查询
     */
    private List<Long> queryViaGraph(Long userIdA, Long userIdB) {
        try {
            return graphQueryService.queryMutualFriendsViaGraph(userIdA, userIdB, 200);
        } catch (Exception e) {
            log.error("图数据库共同好友查询失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
            return Collections.emptyList();
        }
    }

    /**
     * 获取用户好友数（优先读Redis计数器）
     */
    private long getFriendCount(Long userId) {
        try {
            String countStr = redisTemplate.opsForValue().get(FRIEND_COUNT_KEY + userId);
            if (countStr != null) {
                return Long.parseLong(countStr);
            }
        } catch (Exception e) {
            log.warn("读取好友数计数器失败, userId={}", userId, e);
        }
        // 降级：从Set的size获取
        try {
            Long size = redisTemplate.opsForSet().size(FRIEND_SET_KEY + userId);
            return size != null ? size : 0;
        } catch (Exception e) {
            log.warn("读取好友Set大小失败, userId={}", userId, e);
            return 0;
        }
    }

    private String getStrategyName(long sizeA, long sizeB) {
        if (sizeA >= SUPER_VIP_THRESHOLD || sizeB >= SUPER_VIP_THRESHOLD) {
            return "SUPER_VIP_DOWNGRADE";
        } else if (sizeA < REDIS_SINTER_THRESHOLD && sizeB < REDIS_SINTER_THRESHOLD) {
            return "REDIS_SINTER";
        } else {
            return "GRAPH_QUERY";
        }
    }
}
```

#### 7.3.3 共同好友结果缓存服务

```java
/**
 * 共同好友查询结果缓存
 * 缓存策略：结果缓存5分钟，计数缓存10分钟，高频用户对缓存延长
 */
@Service
public class MutualFriendCacheService {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final String RESULT_CACHE_KEY = "mutual:result:";
    private static final String COUNT_CACHE_KEY = "mutual:count:";

    private static final int RESULT_TTL_MINUTES = 5;
    private static final int COUNT_TTL_MINUTES = 10;

    private static final Logger log = LoggerFactory.getLogger(MutualFriendCacheService.class);

    /**
     * 获取缓存的查询结果
     * 注意：Key使用userIdA和userIdB的最小值+最大值组合，保证A查B和B查A命中同一缓存
     */
    public MutualFriendResult getCachedResult(Long userIdA, Long userIdB, int page, int pageSize) {
        try {
            String key = buildResultKey(userIdA, userIdB, page, pageSize);
            String json = redisTemplate.opsForValue().get(key);
            if (json != null) {
                return JSON.parseObject(json, MutualFriendResult.class);
            }
        } catch (Exception e) {
            log.warn("读取共同好友结果缓存失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
        }
        return null;
    }

    public void cacheResult(Long userIdA, Long userIdB, int page, int pageSize, MutualFriendResult result) {
        try {
            String key = buildResultKey(userIdA, userIdB, page, pageSize);
            redisTemplate.opsForValue().set(key, JSON.toJSONString(result), RESULT_TTL_MINUTES, TimeUnit.MINUTES);
        } catch (Exception e) {
            log.warn("写入共同好友结果缓存失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
        }
    }

    public Integer getCachedCount(Long userIdA, Long userIdB) {
        try {
            String key = buildCountKey(userIdA, userIdB);
            String val = redisTemplate.opsForValue().get(key);
            if (val != null) {
                return Integer.parseInt(val);
            }
        } catch (Exception e) {
            log.warn("读取共同好友计数缓存失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
        }
        return null;
    }

    public void cacheCount(Long userIdA, Long userIdB, int count) {
        try {
            String key = buildCountKey(userIdA, userIdB);
            redisTemplate.opsForValue().set(key, String.valueOf(count), COUNT_TTL_MINUTES, TimeUnit.MINUTES);
        } catch (Exception e) {
            log.warn("写入共同好友计数缓存失败, userIdA={}, userIdB={}", userIdA, userIdB, e);
        }
    }

    /**
     * 构建对称的缓存Key：min(userIdA, userIdB) + max(userIdA, userIdB)
     * 保证A查B和B查A命中同一份缓存，减少重复计算
     */
    private String buildResultKey(Long userIdA, Long userIdB, int page, int pageSize) {
        long min = Math.min(userIdA, userIdB);
        long max = Math.max(userIdA, userIdB);
        return RESULT_CACHE_KEY + min + ":" + max + ":" + page + ":" + pageSize;
    }

    private String buildCountKey(Long userIdA, Long userIdB) {
        long min = Math.min(userIdA, userIdB);
        long max = Math.max(userIdA, userIdB);
        return COUNT_CACHE_KEY + min + ":" + max;
    }
}
```

#### 7.3.4 大粉丝量用户优化策略

```java
/**
 * 图数据库共同好友查询服务
 * 针对大粉丝量用户的优化策略：
 * 1. 限制返回结果集大小，避免超大结果集拖垮图引擎
 * 2. 使用图数据库原生多跳查询，避免将海量ID搬运到应用层
 * 3. 对超大V账号做特殊降级（返回空或近似估算）
 */
@Service
public class GraphQueryService {

    @Autowired
    private GraphDatabaseClient graphClient; // 图数据库客户端封装

    private static final Logger log = LoggerFactory.getLogger(GraphQueryService.class);

    private static final int GRAPH_QUERY_LIMIT = 200; // 图查询结果集上限

    /**
     * 通过图数据库多跳查询共同好友
     * Cypher: MATCH (a:User {userId: $A})-[:FRIEND]->(mutual:User)<-[:FRIEND]-(b:User {userId: $B})
     *         RETURN mutual.userId LIMIT $limit
     */
    public List<Long> queryMutualFriendsViaGraph(Long userIdA, Long userIdB, int limit) {
        String cypher = "MATCH (a:User {userId: $userIdA})-[:FRIEND]->(mutual:User)<-[:FRIEND]-(b:User {userId: $userIdB}) "
                + "WHERE mutual.userId <> $userIdA AND mutual.userId <> $userIdB "
                + "RETURN mutual.userId "
                + "LIMIT $limit";

        Map<String, Object> params = new HashMap<>();
        params.put("userIdA", userIdA);
        params.put("userIdB", userIdB);
        params.put("limit", Math.min(limit, GRAPH_QUERY_LIMIT));

        try {
            long start = System.currentTimeMillis();
            List<Long> result = graphClient.queryForList(cypher, params, "mutual.userId");
            long cost = System.currentTimeMillis() - start;

            if (cost > 500) {
                log.warn("图数据库共同好友查询耗时较长, userIdA={}, userIdB={}, costMs={}, resultCount={}",
                        userIdA, userIdB, cost, result.size());
            }

            return result;
        } catch (Exception e) {
            log.error("图数据库查询异常, userIdA={}, userIdB={}", userIdA, userIdB, e);
            throw new GraphQueryException("图数据库查询失败", e);
        }
    }

    /**
     * 图数据库COUNT查询（仅返回数量，不返回具体ID列表）
     */
    public int countMutualFriends(Long userIdA, Long userIdB) {
        String cypher = "MATCH (a:User {userId: $userIdA})-[:FRIEND]->(mutual:User)<-[:FRIEND]-(b:User {userId: $userIdB}) "
                + "WHERE mutual.userId <> $userIdA AND mutual.userId <> $userIdB "
                + "RETURN count(mutual.userId) AS count";

        Map<String, Object> params = new HashMap<>();
        params.put("userIdA", userIdA);
        params.put("userIdB", userIdB);

        try {
            return graphClient.queryForObject(cypher, params, "count");
        } catch (Exception e) {
            log.error("图数据库COUNT查询异常, userIdA={}, userIdB={}", userIdA, userIdB, e);
            return 0;
        }
    }
}
```

#### 7.3.5 分级查询策略与异常处理总结

**三级查询策略选择逻辑**：

```
                    获取双方好友数 sizeA, sizeB
                            │
                ┌───────────┼───────────────┐
                ▼           ▼               ▼
        sizeA 或 sizeB    双方都 < 5万     任一方 >= 5万
        >= 100万          且 < 100万       且 < 100万
                │           │               │
                ▼           ▼               ▼
          策略C:降级     策略A:Redis      策略B:图数据库
          返回空/近似      SINTER求交集     多跳查询
          (HyperLogLog)                   (LIMIT 200)
```

| 异常场景 | 处理策略 | 用户感知 |
| --- | --- | --- |
| Redis SINTER超时 | 自动降级为图数据库查询 | 响应稍慢但结果准确 |
| 图数据库查询超时 | 返回空列表，记录告警 | 显示"暂无共同好友" |
| 图数据库不可用 | 降级返回缓存数据（可能过期） | 数据可能有延迟 |
| 好友数计数器异常 | 降级从Set的size获取，再降级返回0 | 可能走错误策略但不报错 |
| 用户信息聚合部分失败 | 缺失字段返回默认值 | 部分展示不完整 |
| 超大V共同好友查询 | 直接返回空结果 | 无共同好友展示（语义价值低） |

**幂等控制**：共同好友查询为纯读操作，天然幂等。缓存Key使用对称设计（min+max），保证A查B和B查A命中同一缓存，避免重复计算。缓存TTL设置为5分钟（结果）/10分钟（计数），在好友关系变更时由FollowService主动失效相关缓存。

**性能数据参考**（基于压测估算）：

| 场景 | 好友数量级 | 查询策略 | 平均延迟 | P99延迟 |
| --- | --- | --- | --- | --- |
| 普通用户间 | 双方 < 1000 | Redis SINTER | 3ms | 8ms |
| 活跃用户间 | 双方 < 5万 | Redis SINTER | 15ms | 50ms |
| 普通用户 vs KOL | 一方 5万~100万 | 图数据库查询 | 80ms | 200ms |
| 普通用户 vs 超大V | 一方 > 100万 | 降级返回空 | 1ms | 2ms |
