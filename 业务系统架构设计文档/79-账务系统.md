# 账务系统架构设计

## 一、系统概述

### 1.1 业务场景

账务系统是所有资金类业务的最终"账本"，负责记录每一笔资金变动、维护账户余额、保障资金安全。与支付系统关注"钱怎么走"不同，账务系统关注"钱走了之后账怎么记"：一笔交易发生后，账务系统需要以复式记账的方式，把资金在不同账户主体之间的流转如实、完整、不可篡改地记录下来，并保证任意时刻"记出去的钱"和"记进来的钱"严格相等。

账务系统通常处于整个资金链路的核心低层位置，上游对接支付、交易、营销、结算等业务系统，下游对接清算、核算、财务报表、风控审计等系统。它不关心业务语义（例如"这是一笔外卖订单支付"），只关心"资金从 A 账户的什么科目，以什么金额，转移到了 B 账户的什么科目"。

### 1.2 核心挑战

| 挑战维度 | 具体问题 |
|---------|---------|
| 数据一致性 | 一笔业务可能涉及多个账户、多个科目的联动记账，必须全部成功或全部失败 |
| 高并发记账 | 大促、活动期间瞬时记账 TPS 可能达到数万甚至数十万，数据库行锁竞争激烈 |
| 热点账户 | 平台账户、活动补贴账户等少数账户会被海量交易并发命中，形成写入热点 |
| 资金安全 | 一分钱都不能错，不能重复记账、不能漏记、不能篡改，需要多重校验兜底 |
| 可审计性 | 每一笔资金变动都要可追溯、可核对，满足财务合规与审计要求 |
| 系统可用性 | 账务系统一旦不可用，会导致整个交易链路阻塞，可用性要求极高（4 个 9 以上） |
| 历史数据量 | 流水数据只增不减，长期积累后数据量巨大，需要分库分表与冷热分离 |

### 1.3 设计原则

账务系统的设计始终围绕以下几个原则展开，后续每一章都会看到这些原则如何落地为具体的算法与设计模式：

1. **借贷平衡原则**：任何一笔记账，借方发生额之和必须等于贷方发生额之和，这是复式记账法的根基，也是账务系统自我校验的第一道防线。
2. **幂等原则**：同一笔业务请求无论重试多少次，最终只能产生一次真实的账务影响，通过唯一业务流水号 + 状态机实现。
3. **最终一致性优先原则**：账务系统更看重资金正确性而非低延迟，宁可牺牲部分实时性，采用分布式事务或异步对账保证最终一致。
4. **不可变账本原则**：流水一旦生成不可修改、不可删除，任何纠错都通过新增反向冲正记录实现，类似区块链的"只增不改"思想。
5. **分层隔离原则**：查询、记账、调账三类操作在权限、链路、限流策略上严格隔离，避免高危操作影响核心链路稳定性。

### 2.2 各层职责说明

**接入层**：所有记账请求和查询请求的统一入口。记账网关负责幂等校验（防止重复记账）、令牌桶限流（防止突发流量打垮数据库）、签名鉴权（防止非法调用方伪造记账请求）。查询网关负责读写分离路由，将查询流量导向只读副本或查询专用存储，与记账链路物理隔离。

**账户管理层**：维护账户的生命周期（创建、启用、冻结、注销、恢复），维护账户的余额模型（可用余额、冻结余额、总余额三者的一致性），提供账户类型配置能力。

**记账引擎层**：账务系统的核心，实现复式记账算法、保障分布式事务一致性、实现记账幂等、针对热点账户做专门的并发优化。这一层是本文档着墨最多的部分。

**流水管理层**：负责流水号生成（改进版雪花算法）、流水查询（多维度索引设计）、日终余额快照生成、记账凭证生成与管理。

**对账层**：账务系统与上游业务系统、下游清算系统之间的对账机制，通过日终对账发现差异并驱动自动或人工修复，是资金安全的最后一道防线。

**调账平台**：当出现线上事故、产品缺陷、人工失误导致账务数据错误时，提供有严格审批流程和权限隔离的人工干预入口，是整个系统里权限最敏感的模块。

### 2.4 采用的设计模式总览

| 场景 | 设计模式 | 说明 |
|------|---------|------|
| 记账操作抽象 | 策略模式 + 模板方法模式 | 不同业务类型的记账规则可插拔，公共流程固定 |
| 账户类型扩展 | 工厂模式 | 根据账户类型创建不同的账户实体与校验规则 |
| 记账流程编排 | 责任链模式 | 幂等校验→余额校验→冻结校验→执行记账→生成流水，链式处理 |
| 分布式事务 | TCC模式 / Saga模式 | 跨账户、跨库记账场景下保证最终一致性 |
| 热点账户优化 | 生产者消费者模式 + 异步聚合 | 将同一账户的并发请求排队合并处理 |
| 调账审批 | 状态机模式 | 调账单从发起到执行的生命周期管理 |
| 对账差异处理 | 观察者模式 | 差异发现后通知多个下游处理器（告警、自动修复、工单） |
| 余额缓存 | 装饰器模式 + 本地缓存兜底 | Redis缓存余额，DB兜底，降级链路清晰 |

## 三、账户模型设计

### 3.1 账户主体与账户体系

账务系统中的"账户"并不是用户注册的那个账号，而是一个**记账主体**的抽象。一个用户可能对应多个账务账户（如可提现余额账户、优惠金账户、保证金账户），一个商户也可能对应多个账户（如营业收入账户、待结算账户、保证金账户）。

### 3.2 余额模型：可用余额 + 冻结余额 + 总余额

账务系统最核心的数据模型是余额模型。这里采用三段式余额设计，这是资金类系统的行业惯例：

- **总余额（Total Balance）**：账户内资金的全部数量。
- **可用余额（Available Balance）**：可以被用户使用、提现、消费的部分。
- **冻结余额（Frozen Balance）**：因风控、担保交易、争议处理等原因被临时锁定，不可动用的部分。

三者满足不变式：**总余额 = 可用余额 + 冻结余额**，这个不变式会贯穿本文档所有涉及余额变更的代码，是资金安全设计里最基础也最重要的一条约束（在第八章会专门讲如何通过数据库约束和应用层双重校验来强制保证）。

```java
/**
 * 账户余额模型
 * 使用不可变对象（Immutable Object）模式设计，避免余额被意外修改，
 * 任何变更都必须通过创建新的 Balance 实例完成，天然线程安全。
 */
public final class Balance {

    /** 总余额，单位：分，使用 long 避免浮点数精度问题 */
    private final long totalAmount;

    /** 可用余额 */
    private final long availableAmount;

    /** 冻结余额 */
    private final long frozenAmount;

    public Balance(long totalAmount, long availableAmount, long frozenAmount) {
        // 构造时强制校验不变式，任何违反不变式的余额对象都不允许被创建
        if (totalAmount != availableAmount + frozenAmount) {
            throw new IllegalStateException(
                String.format("余额不变式被打破: total=%d, available=%d, frozen=%d",
                        totalAmount, availableAmount, frozenAmount));
        }
        if (availableAmount < 0 || frozenAmount < 0) {
            throw new IllegalArgumentException("余额不能为负数");
        }
        this.totalAmount = totalAmount;
        this.availableAmount = availableAmount;
        this.frozenAmount = frozenAmount;
    }

    /** 加币：只影响可用余额和总余额 */
    public Balance increase(long amount) {
        checkPositive(amount);
        return new Balance(totalAmount + amount, availableAmount + amount, frozenAmount);
    }

    /** 减币：只影响可用余额和总余额，需要保证可用余额充足 */
    public Balance decrease(long amount) {
        checkPositive(amount);
        if (availableAmount < amount) {
            throw new InsufficientBalanceException(
                    "可用余额不足: available=" + availableAmount + ", need=" + amount);
        }
        return new Balance(totalAmount - amount, availableAmount - amount, frozenAmount);
    }

    /** 冻结：从可用余额转移到冻结余额，总余额不变 */
    public Balance freeze(long amount) {
        checkPositive(amount);
        if (availableAmount < amount) {
            throw new InsufficientBalanceException(
                    "可用余额不足以冻结: available=" + availableAmount + ", need=" + amount);
        }
        return new Balance(totalAmount, availableAmount - amount, frozenAmount + amount);
    }

    /** 解冻：从冻结余额转移到可用余额，总余额不变 */
    public Balance unfreeze(long amount) {
        checkPositive(amount);
        if (frozenAmount < amount) {
            throw new InsufficientBalanceException(
                    "冻结余额不足以解冻: frozen=" + frozenAmount + ", need=" + amount);
        }
        return new Balance(totalAmount, availableAmount + amount, frozenAmount - amount);
    }

    /** 扣减冻结余额（解冻后直接核销，例如担保交易最终打款给对方） */
    public Balance deductFrozen(long amount) {
        checkPositive(amount);
        if (frozenAmount < amount) {
            throw new InsufficientBalanceException(
                    "冻结余额不足以扣减: frozen=" + frozenAmount + ", need=" + amount);
        }
        return new Balance(totalAmount - amount, availableAmount, frozenAmount - amount);
    }

    private void checkPositive(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("变更金额必须为正数: " + amount);
        }
    }

    public long getTotalAmount() { return totalAmount; }
    public long getAvailableAmount() { return availableAmount; }
    public long getFrozenAmount() { return frozenAmount; }
}
```

### 3.4 账户数据库设计

```sql

    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    account_id BIGINT NOT NULL COMMENT '账户ID，全局唯一，雪花算法生成',
    subject_id BIGINT NOT NULL COMMENT '主体ID（用户/商户/平台）',
    subject_type TINYINT NOT NULL COMMENT '1用户 2商户 3平台 4渠道',
    account_type VARCHAR(32) NOT NULL COMMENT '账户类型编码',
    currency VARCHAR(8) NOT NULL DEFAULT 'CNY',
    total_amount BIGINT NOT NULL DEFAULT 0 COMMENT '总余额(分)',
    available_amount BIGINT NOT NULL DEFAULT 0 COMMENT '可用余额(分)',
    frozen_amount BIGINT NOT NULL DEFAULT 0 COMMENT '冻结余额(分)',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '1正常 2冻结 3注销',
    version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    create_time DATETIME NOT NULL,

    UNIQUE KEY uk_account_id (account_id),
```

### 3.5 账户创建、注销与恢复

账户创建、注销、恢复是相对低频但需要严谨状态控制的操作，这里用一个简单的**有限状态机**来约束合法的状态迁移，防止已注销账户被误操作恢复到不一致的状态。

```java
public enum AccountStatus {
    NORMAL(1, "正常"),
    FROZEN(2, "冻结"),
    CLOSED(3, "已注销");

    private final int code;
    private final String desc;
    AccountStatus(int code, String desc) { this.code = code; this.desc = desc; }
}

/**
 * 账户状态迁移校验器。
 * 使用状态机模式约束合法的状态跳转，非法跳转直接拒绝，
 * 避免"已注销账户"被恢复到"正常"之外的非法状态。
 */
public class AccountStatusMachine {

    private static final Map<AccountStatus, Set<AccountStatus>> TRANSITIONS = new EnumMap<>(AccountStatus.class);

    static {
        TRANSITIONS.put(AccountStatus.NORMAL, EnumSet.of(AccountStatus.FROZEN, AccountStatus.CLOSED));
        TRANSITIONS.put(AccountStatus.FROZEN, EnumSet.of(AccountStatus.NORMAL, AccountStatus.CLOSED));
        TRANSITIONS.put(AccountStatus.CLOSED, EnumSet.of(AccountStatus.NORMAL)); // 仅支持恢复到正常
    }

    public static void checkTransition(AccountStatus from, AccountStatus to) {
        Set<AccountStatus> allowed = TRANSITIONS.get(from);
        if (allowed == null || !allowed.contains(to)) {
            throw new IllegalStateTransitionException(
                    "不允许的状态迁移: " + from + " -> " + to);
        }
    }
}

@Service
public class AccountLifecycleService {

    @Autowired
    private AccountRepository accountRepository;
    @Autowired
    private AuditLogService auditLogService;

    /** 注销账户：要求余额清零后才允许注销，防止资金悬空 */
    @Transactional
    public void closeAccount(Long accountId, String operator, String reason) {
        Account account = accountRepository.selectForUpdate(accountId);
        AccountStatusMachine.checkTransition(account.getStatus(), AccountStatus.CLOSED);

        if (account.getBalance().getTotalAmount() != 0) {
            throw new BusinessException("账户余额不为零，不允许注销，当前余额：" 
                    + account.getBalance().getTotalAmount());
        }
        account.setStatus(AccountStatus.CLOSED);
        accountRepository.updateStatus(account);
        auditLogService.record(AuditAction.CLOSE_ACCOUNT, accountId, operator, reason);
    }

    /** 恢复账户：仅超管权限可操作，恢复后账户回到正常状态，余额从0开始 */
    @Transactional
    public void restoreAccount(Long accountId, String operator, String reason) {
        Account account = accountRepository.selectForUpdate(accountId);
        AccountStatusMachine.checkTransition(account.getStatus(), AccountStatus.NORMAL);

        account.setStatus(AccountStatus.NORMAL);
        accountRepository.updateStatus(account);
        auditLogService.record(AuditAction.RESTORE_ACCOUNT, accountId, operator, reason);
    }
}
```

## 四、记账引擎

记账引擎是账务系统的心脏。本章分四部分展开：复式记账法的落地实现、分布式事务保障、幂等记账机制、以及热点账户的并发优化方案。

### 4.1 复式记账法：借贷必相等

复式记账法（Double-Entry Bookkeeping）要求任何一笔经济业务都必须同时记录在至少两个账户中，一个借方，一个贷方，且**借方发生额之和恒等于贷方发生额之和**。这是几百年来会计学的基本方法，也是账务系统自证清白的数学基础。

```
示例：用户支付 100 元购买商品，其中平台抽成 5 元
借：用户可用余额账户   100元
贷：平台过渡账户       100元
（第一步：资金从用户账户转移到平台过渡账户）

借：平台过渡账户       100元
贷：商户待结算账户      95元
贷：平台收入账户        5元
（第二步：平台过渡账户按分账规则拆分给商户和平台）
```

#### 4.1.1 记账分录模型

```java
/**
 * 记账方向：借/贷。
 * 采用会计学标准约定：
 *  - 资产类科目：借方增加，贷方减少
 *  - 负债/权益类科目：贷方增加，借方减少
 */
public enum EntryDirection {
    DEBIT,   // 借方
    CREDIT   // 贷方
}

/** 单条记账分录 */
public class AccountingEntry {
    private Long accountId;
    private EntryDirection direction;
    private long amount;          // 必须为正数，方向由 direction 决定语义
    private String subjectCode;   // 会计科目编码

    public AccountingEntry(Long accountId, EntryDirection direction, long amount, String subjectCode) {
        if (amount <= 0) {
            throw new IllegalArgumentException("记账金额必须为正数");
        }
        this.accountId = accountId;
        this.direction = direction;
        this.amount = amount;
        this.subjectCode = subjectCode;
    }
    // getter 省略
}

/**
 * 一笔完整的记账凭证（Voucher），包含若干借方分录和贷方分录。
 * 采用"凭证"这一会计概念对多分录记账进行封装，
 * 校验逻辑集中在 validate() 方法中，保证任何凭证在提交前都经过借贷平衡校验。
 */
public class AccountingVoucher {

    private String voucherNo;              // 凭证号
    private String bizNo;                  // 业务流水号，用于幂等
    private String bizType;                // 业务类型，对应类型配置表
    private List<AccountingEntry> entries = new ArrayList<>();
    private Date occurTime;

    public void addEntry(AccountingEntry entry) {
        entries.add(entry);
    }

    /**
     * 借贷平衡校验算法：
     * 对所有分录按方向分组求和，比较借方合计与贷方合计是否相等。
     * 这是记账引擎提交前的强制前置校验，任何不平衡的凭证一律拒绝提交。
     */
    public void validateBalance() {
        long debitSum = entries.stream()
                .filter(e -> e.getDirection() == EntryDirection.DEBIT)
                .mapToLong(AccountingEntry::getAmount)
                .sum();
        long creditSum = entries.stream()
                .filter(e -> e.getDirection() == EntryDirection.CREDIT)
                .mapToLong(AccountingEntry::getAmount)
                .sum();
        if (debitSum != creditSum) {
            throw new UnbalancedVoucherException(
                    String.format("凭证借贷不平衡: debit=%d, credit=%d, bizNo=%s",
                            debitSum, creditSum, bizNo));
        }
        if (entries.isEmpty()) {
            throw new IllegalArgumentException("凭证不能没有分录");
        }
    }

    // getter/setter 省略
}
```

#### 4.1.2 记账引擎核心执行流程（责任链模式）

记账请求进入引擎后，需要依次经过幂等校验、余额校验、冻结状态校验、执行记账、生成流水这几个步骤。这里使用**责任链模式**将各个步骤解耦为独立的 Handler，既方便单元测试，也方便未来插入新的校验环节而不用改动已有代码。

```java
/** 记账上下文，在责任链各节点间传递 */
public class AccountingContext {
    private AccountingVoucher voucher;
    private Map<Long, Account> lockedAccounts = new HashMap<>();
    private boolean idempotentHit = false;   // 是否命中幂等，命中则直接短路返回
    private AccountingResult result;
    // getter/setter 省略
}

/** 责任链处理节点抽象 */
public abstract class AccountingHandler {
    protected AccountingHandler next;

    public AccountingHandler setNext(AccountingHandler next) {
        this.next = next;
        return next;
    }

    public final void handle(AccountingContext context) {
        if (context.isIdempotentHit()) {
            return; // 幂等命中，链路短路，不再继续往下执行
        }
        doHandle(context);
        if (next != null) {
            next.handle(context);
        }
    }

    protected abstract void doHandle(AccountingContext context);
}

/** 第一环：幂等校验 */
@Component
public class IdempotentCheckHandler extends AccountingHandler {

    @Autowired
    private AccountingRecordRepository recordRepository;

    @Override
    protected void doHandle(AccountingContext context) {
        String bizNo = context.getVoucher().getBizNo();
        AccountingRecord existing = recordRepository.findByBizNo(bizNo);
        if (existing != null) {
            // 命中幂等，直接返回历史结果，不重复记账
            context.setResult(AccountingResult.fromExisting(existing));
            context.setIdempotentHit(true);
        }
    }
}

/** 第二环：借贷平衡校验 */
@Component
public class BalanceValidationHandler extends AccountingHandler {
    @Override
    protected void doHandle(AccountingContext context) {
        context.getVoucher().validateBalance();
    }
}

/** 第三环：账户加锁与状态校验（悲观锁，见4.2节） */
@Component
public class AccountLockHandler extends AccountingHandler {

    @Autowired
    private AccountRepository accountRepository;

    @Override
    protected void doHandle(AccountingContext context) {
        // 收集本次凭证涉及的所有账户ID，按ID升序加锁，避免死锁（见4.2.2节）
        List<Long> accountIds = context.getVoucher().getEntries().stream()
                .map(AccountingEntry::getAccountId)
                .distinct()
                .sorted()
                .collect(Collectors.toList());

        for (Long accountId : accountIds) {
            Account account = accountRepository.selectForUpdate(accountId);
            if (account.getStatus() != AccountStatus.NORMAL) {
                throw new AccountNotAvailableException("账户状态异常，不允许记账: " + accountId);
            }
            context.getLockedAccounts().put(accountId, account);
        }
    }
}

/** 第四环：可用余额充足性校验（借方为减少可用余额的分录才需要校验） */
@Component
public class SufficientFundsHandler extends AccountingHandler {
    @Override
    protected void doHandle(AccountingContext context) {
        for (AccountingEntry entry : context.getVoucher().getEntries()) {
            Account account = context.getLockedAccounts().get(entry.getAccountId());
            boolean isDeduction = isDeductionEntry(entry, account.getAccountType());
            if (isDeduction && !account.getAccountType().isAllowNegative()
                    && account.getBalance().getAvailableAmount() < entry.getAmount()) {
                throw new InsufficientBalanceException(
                        "账户可用余额不足: " + entry.getAccountId());
            }
        }
    }

    private boolean isDeductionEntry(AccountingEntry entry, AccountType type) {
        // 资产类账户贷方为减少，此处简化，实际应结合科目性质表判断
        return entry.getDirection() == EntryDirection.CREDIT;
    }
}

/** 第五环：真正执行余额变更 */
@Component
public class BalanceMutationHandler extends AccountingHandler {

    @Autowired
    private AccountRepository accountRepository;

    @Override
    protected void doHandle(AccountingContext context) {
        for (AccountingEntry entry : context.getVoucher().getEntries()) {
            Account account = context.getLockedAccounts().get(entry.getAccountId());
            Balance newBalance = entry.getDirection() == EntryDirection.DEBIT
                    ? account.getBalance().increase(entry.getAmount())
                    : account.getBalance().decrease(entry.getAmount());
            account.setBalance(newBalance);
            // 带版本号的乐观更新，防止并发覆盖（与外层悲观锁形成双保险）
            accountRepository.updateBalanceWithVersion(account);
        }
    }
}

/** 第六环：生成流水与记账记录（见第五章） */
@Component
public class RecordGenerationHandler extends AccountingHandler {

    @Autowired
    private FlowNoGenerator flowNoGenerator;
    @Autowired
    private AccountingRecordRepository recordRepository;
    @Autowired
    private FlowRepository flowRepository;

        AccountFlow flow = new AccountFlow();
        flow.setFlowNo(flowNo);
        flow.setAccountId(entry.getAccountId());
        flow.setBizNo(voucher.getBizNo());
        flow.setDirection(entry.getDirection());
        flow.setAmount(entry.getAmount());
        flow.setBizType(voucher.getBizType());
        flow.setOccurTime(voucher.getOccurTime());
        return flow;
    }

    private AccountingRecord buildAccountingRecord(AccountingVoucher voucher) {
        AccountingRecord record = new AccountingRecord();
        record.setBizNo(voucher.getBizNo());
        record.setVoucherNo(voucher.getVoucherNo());

}

/** 组装责任链的引擎门面类 */

    @Autowired private IdempotentCheckHandler idempotentCheckHandler;
    @Autowired private BalanceValidationHandler balanceValidationHandler;
    @Autowired private AccountLockHandler accountLockHandler;
    @Autowired private SufficientFundsHandler sufficientFundsHandler;
    @Autowired private BalanceMutationHandler balanceMutationHandler;
    @Autowired private RecordGenerationHandler recordGenerationHandler;

    private AccountingHandler chainHead;

    @PostConstruct
    public void init() {
        idempotentCheckHandler.setNext(balanceValidationHandler)
                .setNext(accountLockHandler)
                .setNext(sufficientFundsHandler)
                .setNext(balanceMutationHandler)
                .setNext(recordGenerationHandler);
        chainHead = idempotentCheckHandler;
    }

    @Transactional(rollbackFor = Exception.class)
    public AccountingResult post(AccountingVoucher voucher) {

        context.setVoucher(voucher);
        chainHead.handle(context);

    }
```

### 4.2 分布式事务保障

单库场景下，责任链内的记账操作可以直接依赖数据库本地事务（`@Transactional`）保证原子性。但当涉及跨库、跨服务的记账场景（例如用户账户和商户账户分布在不同的分库，或者账务系统需要联动库存、订单系统时），本地事务无法覆盖，需要引入分布式事务方案。

#### 4.2.1 TCC 模式在记账中的应用

TCC（Try-Confirm-Cancel）模式将一次业务操作拆分为三个阶段：尝试阶段预留资源、确认阶段真正提交、取消阶段回滚预留。账务系统里常用于"支付扣款 + 账务记账"这种跨系统场景。

```java
/** TCC 记账接口定义 */
public interface TccAccountingAction {
    /** Try：冻结资金，预留记账资源，不做最终余额变更 */
    boolean tryFreeze(String txId, Long accountId, long amount);

    /** Confirm：将冻结金额正式核销，转为真实的账务记录 */
    boolean confirm(String txId);

    /** Cancel：释放冻结金额，恢复到 Try 之前的状态 */
    boolean cancel(String txId);
}

@Service
public class TccAccountingActionImpl implements TccAccountingAction {

    @Autowired private AccountRepository accountRepository;
    @Autowired private TccTransactionLogRepository tccLogRepository;

    @Override
    @Transactional
    public boolean tryFreeze(String txId, Long accountId, long amount) {
        // 幂等：同一个 txId 只允许 try 一次
        if (tccLogRepository.exists(txId, TccPhase.TRY)) {
            return true;
        }
        Account account = accountRepository.selectForUpdate(accountId);
        Balance newBalance = account.getBalance().freeze(amount); // 冻结而非直接扣减
        account.setBalance(newBalance);
        accountRepository.updateBalanceWithVersion(account);

        tccLogRepository.insert(new TccTransactionLog(txId, accountId, amount, TccPhase.TRY));
        return true;
    }

    @Override
    @Transactional
    public boolean confirm(String txId) {
        TccTransactionLog log = tccLogRepository.findByTxId(txId);
        if (log == null || log.getPhase() == TccPhase.CONFIRMED) {
            return true; // 幂等短路
        }
        Account account = accountRepository.selectForUpdate(log.getAccountId());
        // 冻结余额正式核销，同时生成流水
        Balance newBalance = account.getBalance().deductFrozen(log.getAmount());
        account.setBalance(newBalance);
        accountRepository.updateBalanceWithVersion(account);

        tccLogRepository.updatePhase(txId, TccPhase.CONFIRMED);
        return true;
    }

    @Override
    @Transactional
    public boolean cancel(String txId) {
        TccTransactionLog log = tccLogRepository.findByTxId(txId);
        if (log == null || log.getPhase() == TccPhase.CANCELLED) {
            return true; // 幂等短路，允许空回滚
        }
        Account account = accountRepository.selectForUpdate(log.getAccountId());
        Balance newBalance = account.getBalance().unfreeze(log.getAmount());
        account.setBalance(newBalance);
        accountRepository.updateBalanceWithVersion(account);

        tccLogRepository.updatePhase(txId, TccPhase.CANCELLED);
        return true;
    }
}
```

TCC 协调器负责驱动各参与方按顺序执行，并在任意一方失败时触发已成功参与方的 Cancel：

```java
@Service
public class TccTransactionCoordinator {

    @Autowired
    private List<TccAccountingAction> participants; // 多个账户参与方

    public void executeTransfer(String txId, Long fromAccount, Long toAccount, long amount) {
        List<TccAccountingAction> tried = new ArrayList<>();
        try {
            for (TccAccountingAction participant : participants) {
                boolean ok = participant.tryFreeze(txId, fromAccount, amount);
                if (!ok) {
                    throw new TccTryFailedException("Try 阶段失败");
                }
                tried.add(participant);
            }
            for (TccAccountingAction participant : tried) {
                participant.confirm(txId);
            }
        } catch (Exception e) {
            // 任意阶段失败，对已成功 Try 的参与方执行 Cancel 补偿
            for (TccAccountingAction participant : tried) {
                try {
                    participant.cancel(txId);
                } catch (Exception cancelEx) {
                    // Cancel 失败进入重试队列，由定时任务兜底重试，见4.2.3节
                    retryQueue().enqueue(txId, participant);
                }
            }
            throw new TccTransactionFailedException("分布式记账事务失败，已回滚", e);
        }
    }

    private TccRetryQueue retryQueue() {
        return TccRetryQueue.getInstance();
    }
}
```

#### 4.2.2 死锁预防：账户排序加锁算法

多个记账请求并发执行时，如果对多个账户加锁的顺序不一致，会产生经典的死锁问题（事务 A 先锁账户1再锁账户2，事务 B 先锁账户2再锁账户1）。解决方案是**固定加锁顺序算法**：任何一次记账，无论转账方向如何，永远按账户 ID 从小到大的顺序加锁。

```java
/**
 * 死锁预防：固定顺序加锁。
 * 这是数据库并发编程中的经典算法（Resource Ordering），
 * 通过强制所有事务以相同顺序获取锁资源，从数学上消除循环等待条件，
 * 从而破坏死锁产生的四个必要条件之一。
 */
public class AccountLockOrderResolver {

    public List<Long> resolveOrder(Collection<Long> accountIds) {
        return accountIds.stream()
                .distinct()
                .sorted(Long::compareTo)  // 严格按ID升序
                .collect(Collectors.toList());
    }
}
```

在 `AccountLockHandler` 中已经体现了这一算法的应用（`.sorted()` 调用），此处不再重复代码，仅强调这是保障高并发记账场景下事务不发生死锁的关键设计。

#### 4.2.3 Saga 模式：长事务补偿

对于涉及多个下游服务、执行时间较长的记账链路（例如清算批处理场景），TCC 的资源锁定时间过长会影响并发度，此时更适合使用 **Saga 模式**：将大事务拆分为一系列本地事务，每个本地事务都有对应的补偿操作，一旦某一步失败，则从后往前依次执行已完成步骤的补偿操作。

```java
/** Saga 步骤抽象 */
public interface SagaStep {
    void execute(SagaContext context) throws Exception;
    void compensate(SagaContext context);
}

public class DeductFromSourceStep implements SagaStep {
    @Override
    public void execute(SagaContext context) throws Exception {
        // 从源账户扣款
    }
    @Override
    public void compensate(SagaContext context) {
        // 补偿：把扣掉的钱加回源账户
    }
}

public class AddToTargetStep implements SagaStep {
    @Override
    public void execute(SagaContext context) throws Exception {
        // 向目标账户加款
    }
    @Override
    public void compensate(SagaContext context) {
        // 补偿：把加的钱从目标账户扣回
    }
}

/** Saga 编排器：顺序执行步骤，失败时逆序补偿 */
@Service
public class SagaOrchestrator {

    public void execute(List<SagaStep> steps, SagaContext context) {
        Deque<SagaStep> executedSteps = new ArrayDeque<>();
        try {
            for (SagaStep step : steps) {
                step.execute(context);
                executedSteps.push(step);
            }
        } catch (Exception e) {
            // 逆序补偿，后执行的步骤先补偿，保证补偿顺序与执行顺序相反
            while (!executedSteps.isEmpty()) {
                SagaStep step = executedSteps.pop();
                try {
                    step.compensate(context);
                } catch (Exception compensateEx) {
                    // 补偿失败记录进差错队列，转人工介入（对接第七章调账平台）
                    SagaCompensationFailureQueue.getInstance().record(step, context, compensateEx);
                }
            }
            throw new SagaExecutionException("Saga 事务执行失败，已触发补偿", e);
        }
    }
}
```

### 4.3 幂等记账机制

幂等是账务系统的生命线。网络超时导致的重试、消息队列的重复投递、用户的重复点击，都可能导致同一笔业务请求被多次提交给记账引擎。如果没有幂等保障，会直接导致重复扣款或重复入账的资损事故。

#### 4.3.1 幂等的三层防护

```
第一层：业务流水号唯一索引（数据库层面强约束）
第二层：状态机 + 分布式锁（应用层面前置拦截）
第三层：乐观锁版本号（并发更新时的最后防线）
```

```java
/**
 * 幂等控制服务：结合数据库唯一索引与 Redis 分布式锁实现双重幂等保障。
 * 使用 INSERT 唯一索引冲突作为最终幂等判定依据（数据库是唯一真相源），
 * Redis 分布式锁仅用于减少并发场景下对数据库的无效冲击，是性能优化手段而非正确性保障手段。
 */
@Service
public class IdempotentService {

    @Autowired
    private RedissonClient redissonClient;
    @Autowired
    private AccountingRecordRepository recordRepository;

    public <T> T executeIdempotent(String bizNo, Supplier<T> action, Function<String, T> onDuplicate) {
        RLock lock = redissonClient.getLock("accounting:idempotent:" + bizNo);
        boolean locked = false;
        try {
            // 尝试加锁，最多等待500ms，锁自动过期时间10秒防止死锁
            locked = lock.tryLock(500, 10000, TimeUnit.MILLISECONDS);
            if (!locked) {
                // 拿不到锁说明同一笔业务正在处理中，直接判定为重复请求
                return onDuplicate.apply(bizNo);
            }
            AccountingRecord existing = recordRepository.findByBizNo(bizNo);
            if (existing != null) {
                return onDuplicate.apply(bizNo);
            }
            try {
                return action.get();
            } catch (DuplicateKeyException e) {
                // 数据库唯一索引冲突兜底：极端情况下锁失效但仍然重复提交，
                // 依赖数据库唯一约束作为最终防线
                return onDuplicate.apply(bizNo);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new SystemException("幂等锁获取被中断", e);
        } finally {
            if (locked) {
                lock.unlock();
            }
        }
    }
}
```

#### 4.3.2 乐观锁与悲观锁的双重保障

第四章前面的 `AccountLockHandler` 使用了 `SELECT ... FOR UPDATE` 悲观锁，这里补充说明为什么还要在更新语句上叠加乐观锁版本号：悲观锁只能保证同一数据库实例内、同一事务生命周期内的互斥，但如果记账引擎存在多个实例、或者存在跨越悲观锁作用域的更新路径（例如热点账户优化引入的异步合并写入），版本号能提供额外一层校验。

```java
@Repository
public class AccountRepository {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    /** 悲观锁读取，用于责任链内的强一致场景 */
    public Account selectForUpdate(Long accountId) {
        String sql = "SELECT * FROM account WHERE account_id = ? FOR UPDATE";
        return jdbcTemplate.queryForObject(sql, this::mapRow, accountId);
    }

    /**
     * 带版本号的乐观更新：
     * UPDATE 语句的 WHERE 条件带上 version = ?，
     * 若受影响行数为0，说明版本号已被其他事务修改，抛出并发冲突异常，
     * 由上层决定是重试还是失败。
     */
    public void updateBalanceWithVersion(Account account) {
        String sql = "UPDATE account SET total_amount = ?, available_amount = ?, frozen_amount = ?, "
                + "version = version + 1, update_time = NOW() "
                + "WHERE account_id = ? AND version = ?";
        int rows = jdbcTemplate.update(sql,
                account.getBalance().getTotalAmount(),
                account.getBalance().getAvailableAmount(),
                account.getBalance().getFrozenAmount(),
                account.getAccountId(),
                account.getVersion());
        if (rows == 0) {
            throw new OptimisticLockConflictException("账户版本冲突，可能存在并发更新: " + account.getAccountId());
        }
    }

    private Account mapRow(ResultSet rs, int rowNum) throws SQLException {
        // 省略字段映射细节
        return new Account();
    }
}
```

### 4.4 热点账户优化：异步记账 + 合并写入

大促、秒杀等场景下，平台过渡账户、活动补贴账户这类"热点账户"会被数以万计的并发交易同时命中，行级锁会成为整个记账链路的性能瓶颈。这里介绍热点账户专用的优化方案。

#### 4.4.1 问题本质

一个热点账户的余额更新语句本质上是一个串行化的临界区，无论应用层并发多高，数据库层面对同一行的更新永远是串行执行的。TPS 上限被单行更新的 RT 严格限制：`TPS_max = 1000ms / 单次更新RT(ms)`。要突破这个上限，必须把"多次独立的行更新"合并为"一次批量的行更新"。

#### 4.4.2 方案一：内存队列合并写入（生产者消费者模式）

```java
/**
 * 热点账户异步聚合器。
 * 核心思想：将短时间窗口内针对同一账户的多笔记账请求，
 * 在内存队列中聚合成一个批次，只对数据库执行一次 UPDATE，
 * 将 N 次数据库行锁竞争降低为 1 次，大幅提升热点账户吞吐量。
 * 这是典型的生产者-消费者模式 + 批量合并（Batching）算法的组合应用。
 */
@Component
public class HotAccountAggregator {

    /** 每个热点账户对应一个独立的任务队列，账户之间互不影响 */
    private final ConcurrentHashMap<Long, BlockingQueue<AggregateTask>> queues = new ConcurrentHashMap<>();
    /** 每个热点账户对应一个独立的消费线程，避免线程池排队相互阻塞 */
    private final ConcurrentHashMap<Long, Thread> consumers = new ConcurrentHashMap<>();

    @Autowired
    private AccountRepository accountRepository;

    /** 提交一笔针对热点账户的记账任务，返回 Future 供调用方等待结果 */
    public CompletableFuture<AccountingResult> submit(Long accountId, AccountingEntry entry) {
        CompletableFuture<AccountingResult> future = new CompletableFuture<>();
        AggregateTask task = new AggregateTask(entry, future);

        BlockingQueue<AggregateTask> queue = queues.computeIfAbsent(accountId, id -> {
            LinkedBlockingQueue<AggregateTask> q = new LinkedBlockingQueue<>(10000);
            startConsumer(id, q);
            return q;
        });

        boolean offered = queue.offer(task);
        if (!offered) {
            future.completeExceptionally(new SystemBusyException("热点账户队列已满，请稍后重试"));
        }
        return future;
    }

    private void startConsumer(Long accountId, BlockingQueue<AggregateTask> queue) {
        Thread consumer = new Thread(() -> {
            while (true) {
                List<AggregateTask> batch = new ArrayList<>();
                try {
                    // 阻塞等待第一个任务
                    AggregateTask first = queue.take();
                    batch.add(first);
                    // 在一个很短的时间窗口内(如 10ms)尽量多地捞取积压任务，形成批次
                    queue.drainTo(batch, 200, 10, TimeUnit.MILLISECONDS);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
                processBatch(accountId, batch);
            }
        }, "hot-account-consumer-" + accountId);
        consumer.setDaemon(true);
        consumer.start();
        consumers.put(accountId, consumer);
    }

    /**
     * 批量处理：将同方向的多笔金额在内存中先聚合求和，
     * 只对数据库执行一次 UPDATE account SET amount = amount +/- 聚合值，
     * 事后再为每一笔原始请求补写各自的流水记录，保证审计粒度不丢失。
     */
    private void processBatch(Long accountId, List<AggregateTask> batch) {
        long netDebit = batch.stream()
                .filter(t -> t.getEntry().getDirection() == EntryDirection.DEBIT)
                .mapToLong(t -> t.getEntry().getAmount()).sum();
        long netCredit = batch.stream()
                .filter(t -> t.getEntry().getDirection() == EntryDirection.CREDIT)
                .mapToLong(t -> t.getEntry().getAmount()).sum();
        long netChange = netDebit - netCredit;

        try {
            accountRepository.incrementBalanceAtomically(accountId, netChange); // 原子UPDATE amount=amount+netChange
            // 批量插入所有原始明细流水，保证每一笔业务仍然可查、可审计
            List<AccountFlow> flows = batch.stream()
                    .map(t -> buildFlow(accountId, t.getEntry()))
                    .collect(Collectors.toList());
            flowRepository().batchInsert(flows);

            for (AggregateTask task : batch) {
                task.getFuture().complete(AccountingResult.success(task.getEntry().toString()));
            }
        } catch (Exception e) {
            for (AggregateTask task : batch) {
                task.getFuture().completeExceptionally(e);
            }
        }
    }

    private AccountFlow buildFlow(Long accountId, AccountingEntry entry) {
        AccountFlow flow = new AccountFlow();
        flow.setAccountId(accountId);
        flow.setDirection(entry.getDirection());
        flow.setAmount(entry.getAmount());
        return flow;
    }

    private FlowRepository flowRepository() {
        return SpringContextHolder.getBean(FlowRepository.class);
    }

    private static class AggregateTask {
        private final AccountingEntry entry;
        private final CompletableFuture<AccountingResult> future;
        AggregateTask(AccountingEntry entry, CompletableFuture<AccountingResult> future) {
            this.entry = entry;
            this.future = future;
        }
        AccountingEntry getEntry() { return entry; }
        CompletableFuture<AccountingResult> getFuture() { return future; }
    }
}
```

`incrementBalanceAtomically` 使用数据库原子自增语句而非"读出-计算-写回"模式，从根本上避免读写间隙的并发问题：

```java
public void incrementBalanceAtomically(Long accountId, long delta) {
    // delta 可正可负，SQL 层面原子完成加减，不需要先 SELECT 再 UPDATE
    String sql = "UPDATE account SET total_amount = total_amount + ?, "
            + "available_amount = available_amount + ?, version = version + 1, update_time = NOW() "
            + "WHERE account_id = ? AND available_amount + ? >= 0"; // 防止透支的行级条件校验
    int rows = jdbcTemplate.update(sql, delta, delta, accountId, delta);
    if (rows == 0) {
        throw new InsufficientBalanceException("热点账户余额不足或不存在: " + accountId);
    }
}
```

#### 4.4.3 方案二：账户余额分段（Sharding Counter 算法）

除了时间维度的批量合并，还可以在空间维度对热点账户做"分段"处理：将一个逻辑账户的余额拆分为 N 个物理分段（Segment），每个分段独立加锁更新，查询时对所有分段求和。这是解决高并发计数器问题的经典算法（类似于 `LongAdder` 的 Cell 分段思想）。

```java
/**
 * 热点账户分段算法，思路借鉴 JUC 中 LongAdder 的分段累加设计：
 * 把一个账户的余额拆分成多个分段，写入时随机（或按线程哈希）落到某个分段，
 * 分散锁竞争；读取时对所有分段求和得到真实余额。
 * 代价是余额的强一致读需要汇总多行，因此更适合"最终一致展示、定期合并"的场景，
 * 例如活动补贴账户这种对实时精确读要求不高、但写入吞吐要求极高的场景。
 */
@Component
public class ShardedHotAccount {

    private static final int SEGMENT_COUNT = 16;

    @Autowired
    private JdbcTemplate jdbcTemplate;

    /** 写入：分段哈希打散，降低单行锁竞争 */
    public void increment(Long accountId, long delta) {
        int segment = (int) (Thread.currentThread().getId() % SEGMENT_COUNT);
        String sql = "UPDATE account_segment SET amount = amount + ? "
                + "WHERE account_id = ? AND segment_no = ?";
        jdbcTemplate.update(sql, delta, accountId, segment);
    }

    /** 读取：汇总所有分段，得到该账户的真实余额（最终一致） */
    public long sumBalance(Long accountId) {
        String sql = "SELECT COALESCE(SUM(amount), 0) FROM account_segment WHERE account_id = ?";
        return jdbcTemplate.queryForObject(sql, Long.class, accountId);
    }

    /** 定时任务：将分段余额合并回主账户表，收敛数据，便于对账 */
    @Scheduled(cron = "0 0/5 * * * ?")
    public void mergeToMainAccount() {
        // 查询所有存在分段余量的账户，逐个原子合并后清零分段
        // 实现细节：使用分布式锁保护合并过程，避免与写入并发冲突
```

#### 4.4.4 热点账户识别机制

热点账户不是静态配置的，而是需要系统动态识别。这里采用滑动窗口计数算法实时探测：

```java
/**
 * 热点账户探测器：基于滑动窗口计数算法，
 * 统计最近N秒内每个账户的访问次数，超过阈值自动标记为热点，
 * 并动态切换到 4.4.2 节的异步聚合链路，非热点账户走常规同步记账链路，
 * 是一种自适应限流/分流思想的应用。
 */
@Component
public class HotAccountDetector {

    private static final int WINDOW_SECONDS = 10;
    private static final int HOT_THRESHOLD = 500; // 10秒内超过500次判定为热点

    private final ConcurrentHashMap<Long, SlidingWindowCounter> counters = new ConcurrentHashMap<>();

    public boolean isHot(Long accountId) {
        SlidingWindowCounter counter = counters.computeIfAbsent(accountId,
                id -> new SlidingWindowCounter(WINDOW_SECONDS));
        long count = counter.incrementAndGet();
        return count > HOT_THRESHOLD;
    }

    /** 滑动窗口计数器：按秒分桶，统计窗口内总请求数 */
    static class SlidingWindowCounter {
        private final int windowSeconds;
        private final ConcurrentHashMap<Long, AtomicLong> buckets = new ConcurrentHashMap<>();

        SlidingWindowCounter(int windowSeconds) {
            this.windowSeconds = windowSeconds;
        }

        long incrementAndGet() {
            long currentSecond = System.currentTimeMillis() / 1000;
            buckets.computeIfAbsent(currentSecond, k -> new AtomicLong()).incrementAndGet();
            // 清理过期桶
            buckets.keySet().removeIf(second -> currentSecond - second > windowSeconds);
            return buckets.values().stream().mapToLong(AtomicLong::get).sum();
        }
    }
}
```

### 5.1 流水号生成算法：改进版雪花算法

流水号是每一笔账务变动的唯一标识，需要满足：全局唯一、趋势递增（利于索引）、高并发下无锁生成、且能反解出生成时间和分片信息辅助排查问题。标准雪花算法（Snowflake）在多机房部署时容易发生时钟回拨问题，这里介绍改进方案。

```java
/**
 * 改进版雪花算法流水号生成器。
 * 标准雪花算法结构：1位符号位 + 41位时间戳 + 10位机器ID + 12位序列号。
 * 改进点：
 *   1. 引入时钟回拨检测与等待策略，避免回拨导致ID重复；
 *   2. 机器ID通过账户ID哈希取模分配，使同一账户的流水号具备局部聚集性，便于分库分表路由；
 *   3. 增加业务类型标志位，流水号可直接反解出业务大类，便于快速排查。
 */
public class FlowNoGenerator {

    private static final long EPOCH = 1609459200000L; // 起始纪元 2021-01-01
    private static final long SEQUENCE_BITS = 12L;
    private static final long MACHINE_ID_BITS = 10L;
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);
    private static final long MACHINE_ID_SHIFT = SEQUENCE_BITS;
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + MACHINE_ID_BITS;

    private final long machineId;
    private long lastTimestamp = -1L;
    private long sequence = 0L;

    private static volatile FlowNoGenerator instance;

    private FlowNoGenerator(long machineId) {
        this.machineId = machineId;
    }

    public static FlowNoGenerator getInstance() {
        if (instance == null) {
            synchronized (FlowNoGenerator.class) {
                if (instance == null) {
                    instance = new FlowNoGenerator(MachineIdAllocator.resolveMachineId());
                }
            }
        }
        return instance;
    }

    /** 针对某个账户生成流水号，账户ID参与机器位映射以获得分片局部性（可选特化路径） */
    public synchronized String generate(Long accountId) {
        long timestamp = System.currentTimeMillis();

        if (timestamp < lastTimestamp) {
            long offset = lastTimestamp - timestamp;
            if (offset <= 5) {
                // 小幅度回拨（<=5ms），等待时钟追平，避免ID重复
                try {
                    Thread.sleep(offset << 1);
                    timestamp = System.currentTimeMillis();
                    if (timestamp < lastTimestamp) {
                        throw new ClockBackwardsException("时钟回拨等待后仍未追平");
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    throw new ClockBackwardsException("时钟回拨等待被中断", e);
                }
            } else {
                // 大幅度回拨，直接拒绝生成，避免潜在的ID重复风险，交由上层告警并切机
                throw new ClockBackwardsException("检测到严重时钟回拨: " + offset + "ms");
            }
        }

        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {
                // 同一毫秒内序列号耗尽，自旋等待下一毫秒
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        lastTimestamp = timestamp;

        long id = ((timestamp - EPOCH) << TIMESTAMP_SHIFT)
                | (machineId << MACHINE_ID_SHIFT)
                | sequence;

        // 前缀增加日期与业务标志，最终格式：FL + yyyyMMdd + 雪花ID，兼顾可读性与唯一性
        return "FL" + DateFormatUtils.format(new Date(timestamp), "yyyyMMdd") + id;
    }

    private long waitNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}

/** 机器ID分配器，实际生产中通常从注册中心/配置中心获取，此处简化为本地配置读取 */
class MachineIdAllocator {
    static long resolveMachineId() {
        // 生产环境建议基于 ZooKeeper 临时顺序节点或配置中心分配，保证集群内不重复
        String configuredId = System.getProperty("accounting.machine.id", "1");
        return Long.parseLong(configuredId) & 0x3FF; // 限制在10位范围内
    }
}
```

### 5.2 流水查询设计

流水查询模块要同时支撑高频的"按账户查流水"和低频但复杂的"按业务类型、时间范围、金额范围"多维查询，这里采用**读写分离 + 冷热分离**的存储策略。

```java
/** 流水查询请求对象，采用建造者模式组装复杂查询条件 */
public class FlowQueryRequest {
    private Long accountId;
    private String bizType;
    private Date startTime;
    private Date endTime;
    private Long minAmount;
    private Long maxAmount;
    private int pageNo = 1;
    private int pageSize = 20;

    public static class Builder {
        private final FlowQueryRequest request = new FlowQueryRequest();
        public Builder accountId(Long accountId) { request.accountId = accountId; return this; }
        public Builder bizType(String bizType) { request.bizType = bizType; return this; }
        public Builder timeRange(Date start, Date end) { request.startTime = start; request.endTime = end; return this; }
        public Builder amountRange(Long min, Long max) { request.minAmount = min; request.maxAmount = max; return this; }
        public Builder page(int pageNo, int pageSize) { request.pageNo = pageNo; request.pageSize = pageSize; return this; }
        public FlowQueryRequest build() { return request; }
    }
    // getter 省略
}

@Service
public class FlowQueryService {

    @Autowired
    private FlowRepository flowRepository;         // 指向热数据分库（近3个月）
    @Autowired
    private FlowArchiveRepository archiveRepository; // 指向冷数据归档库（3个月以上）

    public PageResult<AccountFlow> query(FlowQueryRequest request) {
        // 冷热分离路由算法：根据查询时间范围自动判断走热库还是归档库，
        // 跨越冷热边界的查询需要分别查询后在内存合并，对调用方透明
        Date hotBoundary = DateUtils.addMonths(new Date(), -3);

        if (request.getStartTime() != null && request.getStartTime().after(hotBoundary)) {
            return flowRepository.query(request);
        } else if (request.getEndTime() != null && request.getEndTime().before(hotBoundary)) {
            return archiveRepository.query(request);
        } else {
            // 跨边界查询：分别查询两侧后合并分页，实际生产中建议引导用户缩小查询范围
            PageResult<AccountFlow> hotResult = flowRepository.query(request);
            PageResult<AccountFlow> coldResult = archiveRepository.query(request);
            return PageResult.merge(hotResult, coldResult, request.getPageNo(), request.getPageSize());
        }
    }
}
```

### 5.3 日终余额快照

日终余额快照用于两个目的：一是加速历史某天余额的查询（不需要从流水表逐条累加），二是作为对账层比对的基准数据。快照生成使用**增量计算 + 全量校验**结合的算法。

```java
/**
 * 日终余额快照生成服务。
 * 算法思路：
 *   1. 增量计算：昨日快照余额 + 今日全部流水发生额 = 今日快照余额，
 *      避免每天都全量扫描历史流水，时间复杂度从 O(全部历史流水) 降低到 O(当日流水)；
 *   2. 全量校验：每月第一天做一次全量校验（从账户表当前余额直接取值对比），
 *      防止增量计算过程中的误差累积，属于典型的"增量+周期校准"组合策略，
 *      与卫星导航中"惯性导航+GPS校准"的思路是同一类工程哲学。
 */
@Service
public class DailyBalanceSnapshotService {

    @Autowired private AccountRepository accountRepository;
    @Autowired private FlowRepository flowRepository;
    @Autowired private DailyBalanceSnapshotRepository snapshotRepository;

    @Scheduled(cron = "0 30 0 * * ?") // 每日00:30执行，处理前一天的数据
    public void generateSnapshot() {
        Date targetDate = DateUtils.addDays(new Date(), -1);
        List<Long> accountIds = accountRepository.listAllActiveAccountIds();

        for (Long accountId : accountIds) {
            try {
                generateForAccount(accountId, targetDate);
            } catch (Exception e) {
                // 单账户快照失败不影响整体，记录差错供后续补偿
                SnapshotFailureQueue.getInstance().record(accountId, targetDate, e);
            }
        }
    }

    private void generateForAccount(Long accountId, Date targetDate) {
        DailyBalanceSnapshot previousSnapshot = snapshotRepository.findByAccountAndDate(
                accountId, DateUtils.addDays(targetDate, -1));
        long baseBalance = previousSnapshot != null ? previousSnapshot.getEndBalance() : 0L;

        FlowAggregateResult aggregate = flowRepository.aggregateByAccountAndDate(accountId, targetDate);
        long endBalance = baseBalance + aggregate.getDebitSum() - aggregate.getCreditSum();

        // 每月1号做全量校验，与账户当前实际余额（结合期间流水回溯）进行比对
        if (isFirstDayOfMonth(targetDate)) {
            long actualBalance = accountRepository.selectForUpdate(accountId).getBalance().getTotalAmount();
            if (actualBalance != endBalance) {
                // 触发差异告警，转由对账层处理（见第八章、第六章）
                DiscrepancyAlertPublisher.publish(accountId, targetDate, endBalance, actualBalance);
            }
        }

        DailyBalanceSnapshot snapshot = new DailyBalanceSnapshot();
        snapshot.setAccountId(accountId);
        snapshot.setSnapshotDate(targetDate);
        snapshot.setBeginBalance(baseBalance);
        snapshot.setDebitSum(aggregate.getDebitSum());
        snapshot.setCreditSum(aggregate.getCreditSum());
        snapshot.setEndBalance(endBalance);
        snapshotRepository.upsert(snapshot);
    }

    private boolean isFirstDayOfMonth(Date date) {
        Calendar calendar = Calendar.getInstance();
        calendar.setTime(date);
        return calendar.get(Calendar.DAY_OF_MONTH) == 1;
    }
}
```

## 六、冻结与解冻

### 6.1 冻结场景与冻结模型

冻结是账务系统里区别于普通转账记账的另一条重要链路，典型场景包括：担保交易的资金锁定、风控临时冻结疑似异常资金、账户注销前的余额锁定、预授权（如信用支付的预扣额度）。

```java
/** 冻结记录实体：每一笔冻结都是独立的、可追踪的记录，而非仅仅修改账户的冻结余额字段 */
public class FreezeRecord {
```

### 6.2 部分冻结与解冻算法

一笔冻结记录支持被多次部分解冻（例如担保交易分批放款给多个供应商），这里需要保证"已解冻金额不能超过冻结金额"这一约束，并且要处理并发解冻请求的原子性。

```java
/**
 * 冻结/解冻服务。
 * 核心算法：每笔冻结独立建档追踪剩余可解冻额度，
 * 通过数据库原子 UPDATE 语句 + WHERE 条件校验，实现"检查-更新"的原子化，
 * 避免"先查询剩余额度，再更新"模式下的并发超发问题（这是经典的 CAS 思想在SQL层面的体现）。
 */
@Service
public class FreezeService {

    @Autowired private AccountRepository accountRepository;
    @Autowired private FreezeRecordRepository freezeRecordRepository;
    @Autowired private FlowNoGenerator flowNoGenerator;

    /** 冻结金额 */
    @Transactional
    public String freeze(Long accountId, long amount, FreezeReason reason, String bizNo, Date expireTime) {
        Account account = accountRepository.selectForUpdate(accountId);
        Balance newBalance = account.getBalance().freeze(amount);
        account.setBalance(newBalance);
        accountRepository.updateBalanceWithVersion(account);

        FreezeRecord record = new FreezeRecord();
        record.setFreezeNo(generateFreezeNo());
        record.setAccountId(accountId);
        record.setAmount(amount);
        record.setReason(reason);
        record.setStatus(FreezeStatus.FROZEN);
        record.setReleasedAmount(0);
        record.setBizNo(bizNo);
        record.setFreezeTime(new Date());
        record.setExpireTime(expireTime);
        freezeRecordRepository.insert(record);
        return record.getFreezeNo();
    }

    /**
     * 部分解冻：支持一笔冻结记录被多次调用释放，
     * releasedAmount 字段配合原子 UPDATE 保证"累计解冻金额不超过原冻结金额"。
     */
    @Transactional
    public void partialUnfreeze(String freezeNo, long releaseAmount) {
        FreezeRecord record = freezeRecordRepository.selectForUpdate(freezeNo);
        if (record.getStatus() == FreezeStatus.RELEASED || record.getStatus() == FreezeStatus.DEDUCTED) {
            throw new BusinessException("冻结记录已终态，无法继续解冻: " + freezeNo);
        }
        long remainingFrozen = record.getAmount() - record.getReleasedAmount();
        if (releaseAmount > remainingFrozen) {
            throw new BusinessException("解冻金额超过剩余可解冻额度: remaining=" + remainingFrozen);
        }

        Account account = accountRepository.selectForUpdate(record.getAccountId());
        account.setBalance(account.getBalance().unfreeze(releaseAmount));
        accountRepository.updateBalanceWithVersion(account);

        long newReleasedAmount = record.getReleasedAmount() + releaseAmount;
        FreezeStatus newStatus = newReleasedAmount == record.getAmount()
                ? FreezeStatus.RELEASED : FreezeStatus.PARTIAL_RELEASED;
        freezeRecordRepository.updateReleaseProgress(freezeNo, newReleasedAmount, newStatus);
    }

    /** 冻结核销：将冻结金额直接转为扣减（如担保交易最终放款给对方账户，本账户冻结金额核销） */
    @Transactional
    public void deductFrozen(String freezeNo, long deductAmount) {
        FreezeRecord record = freezeRecordRepository.selectForUpdate(freezeNo);
        long remainingFrozen = record.getAmount() - record.getReleasedAmount();
        if (deductAmount > remainingFrozen) {
            throw new BusinessException("核销金额超过剩余冻结额度");
        }

        Account account = accountRepository.selectForUpdate(record.getAccountId());
        account.setBalance(account.getBalance().deductFrozen(deductAmount));
        accountRepository.updateBalanceWithVersion(account);

        long newReleasedAmount = record.getReleasedAmount() + deductAmount;
        FreezeStatus newStatus = newReleasedAmount == record.getAmount()
                ? FreezeStatus.DEDUCTED : FreezeStatus.PARTIAL_RELEASED;
        freezeRecordRepository.updateReleaseProgress(freezeNo, newReleasedAmount, newStatus);
    }

    private String generateFreezeNo() {
        return "FZ" + flowNoGenerator.generate(0L);
    }
}
```

### 6.3 预授权机制与自动过期释放

预授权场景（例如先享后付类业务）需要设置冻结的过期时间，超过有效期自动释放，避免资金被长期无意义锁定。这里采用**延迟队列 + 定时扫描双保险**的方式实现自动释放。

```java
/**
 * 预授权自动释放服务。
 * 双保险策略：
 *   1. 提交时向延迟队列（基于时间轮算法实现）注册到期任务，实现精确到期释放；
 *   2. 定时任务每分钟扫描一次数据库中已过期但未释放的冻结记录作为兜底，
 *      防止延迟队列因服务重启等原因丢失任务。
 * 两种机制通过幂等的 partialUnfreeze/deductFrozen 操作互不冲突。
 */
@Service
public class PreAuthExpirationService {

    @Autowired private FreezeService freezeService;
    @Autowired private FreezeRecordRepository freezeRecordRepository;
    private final HashedWheelTimer timeWheel = new HashedWheelTimer(100, TimeUnit.MILLISECONDS, 512);

    /** 冻结创建时注册时间轮任务 */
    public void registerAutoRelease(String freezeNo, Date expireTime) {
        long delay = expireTime.getTime() - System.currentTimeMillis();
        if (delay <= 0) {
            return;
        }
        timeWheel.newTimeout(timeout -> doRelease(freezeNo), delay, TimeUnit.MILLISECONDS);
    }

    private void doRelease(String freezeNo) {
        try {
            FreezeRecord record = freezeRecordRepository.findByFreezeNo(freezeNo);
            if (record != null && record.getStatus() == FreezeStatus.FROZEN) {
                long remaining = record.getAmount() - record.getReleasedAmount();
                freezeService.partialUnfreeze(freezeNo, remaining);
            }
        } catch (Exception e) {
            // 释放失败不抛出，等待兜底定时任务重试
        }
    }

    /** 兜底定时扫描：每分钟扫一次已过期未处理的冻结记录 */
    @Scheduled(fixedRate = 60000)
    public void scanExpiredFreezeRecords() {
        List<FreezeRecord> expired = freezeRecordRepository.findExpiredUnreleased(new Date());
        for (FreezeRecord record : expired) {
            doRelease(record.getFreezeNo());
        }
    }
}
```

## 七、调账平台

### 7.1 调账平台的定位

调账平台是账务系统面向内部运营与研发人员的高危操作入口，用于处理线上事故善后、产品能力缺陷补偿等场景下的人工账务调整。由于调账直接修改资金数据，其设计核心是**审批流控制 + 操作可追溯 + 强制隔离危险操作**。

### 7.2 调账审批流程（状态机 + 责任链）

```java
/** 调账单状态机 */
public enum AdjustOrderStatus {
    PENDING_APPROVAL,   // 待审批
    APPROVED,           // 审批通过，待执行
    REJECTED,           // 审批拒绝
    EXECUTING,          // 执行中
    SUCCESS,            // 执行成功
    FAILED,             // 执行失败
    ROLLED_BACK         // 已回滚
}

/** 调账审批责任链：多级审批人依次审核，任一环节拒绝则终止 */
public abstract class ApprovalHandler {
    protected ApprovalHandler next;
    public ApprovalHandler setNext(ApprovalHandler next) { this.next = next; return next; }

    public final ApprovalResult approve(AdjustOrder order, Approver approver) {
        ApprovalResult result = doApprove(order, approver);
        if (!result.isPassed()) {
            return result;
        }
        if (next != null) {
            return next.approve(order, approver);
        }
        return result;
    }

    protected abstract ApprovalResult doApprove(AdjustOrder order, Approver approver);
}

/** 金额阈值校验：超过一定金额需要更高级别审批人 */
public class AmountThresholdApprovalHandler extends ApprovalHandler {
    private static final long HIGH_RISK_THRESHOLD = 1000000L; // 1万元(分)

    @Override
    protected ApprovalResult doApprove(AdjustOrder order, Approver approver) {
        if (order.getAmount() >= HIGH_RISK_THRESHOLD && approver.getLevel() < ApproverLevel.SENIOR) {
            return ApprovalResult.rejected("大额调账需高级审批人审批");
        }
        return ApprovalResult.passed();
    }
}

/** 操作权限校验：调用方需具备"账务平台-调账(写)"角色 */
public class PermissionApprovalHandler extends ApprovalHandler {
    @Autowired private PermissionService permissionService;

    @Override
    protected ApprovalResult doApprove(AdjustOrder order, Approver approver) {
        if (!permissionService.hasRole(approver.getMisId(), Role.ACCOUNTING_ADJUST_WRITE)) {
            return ApprovalResult.rejected("审批人不具备调账写权限");
        }
        return ApprovalResult.passed();
    }
}

/** 申请人回避校验：审批人不能是申请人本人，防止自审自批 */
public class SelfApprovalAvoidanceHandler extends ApprovalHandler {
    @Override
    protected ApprovalResult doApprove(AdjustOrder order, Approver approver) {
        if (order.getApplicantMisId().equals(approver.getMisId())) {
            return ApprovalResult.rejected("不允许申请人自行审批");
        }
        return ApprovalResult.passed();
    }
}
```

```java
@Service
public class AdjustApprovalService {

    private ApprovalHandler chain;

    @PostConstruct
    public void init() {
        ApprovalHandler permission = new PermissionApprovalHandler();
        ApprovalHandler selfAvoidance = new SelfApprovalAvoidanceHandler();
        ApprovalHandler amountThreshold = new AmountThresholdApprovalHandler();
        permission.setNext(selfAvoidance).setNext(amountThreshold);
        this.chain = permission;
    }

    @Transactional
    public void approve(String adjustNo, Approver approver) {
        AdjustOrder order = adjustOrderRepository().selectForUpdate(adjustNo);
        if (order.getStatus() != AdjustOrderStatus.PENDING_APPROVAL) {
            throw new BusinessException("调账单当前状态不允许审批: " + order.getStatus());
        }

        ApprovalResult result = chain.approve(order, approver);
        if (result.isPassed()) {
            order.setStatus(AdjustOrderStatus.APPROVED);
        } else {
            order.setStatus(AdjustOrderStatus.REJECTED);
            order.setRejectReason(result.getReason());
        }
        adjustOrderRepository().updateStatus(order);
        AuditLogService.getInstance().record("ADJUST_APPROVAL", approver.getMisId(), order.getAdjustNo(), result);
    }

    private AdjustOrderRepository adjustOrderRepository() {
        return SpringContextHolder.getBean(AdjustOrderRepository.class);
    }
}
```

### 7.3 调账操作：策略模式封装多种调账类型

调账平台需要支持转账、加币、减币、冻结、解冻、批量冻结等多种操作，使用**策略模式**统一调度，每种操作独立实现、互不干扰，便于扩展新的调账类型。

```java
/** 调账操作策略接口 */
public interface AdjustStrategy {
    AdjustType supportType();
    void execute(AdjustOrder order);
}

/** 转账调账：从A账户调整到B账户，本质上是一笔人工发起的复式记账 */
@Component
public class TransferAdjustStrategy implements AdjustStrategy {
    @Autowired private AccountingEngine accountingEngine;

    @Override
    public AdjustType supportType() { return AdjustType.TRANSFER; }

    @Override
    public void execute(AdjustOrder order) {
        AccountingRequest request = new AccountingRequest();
        request.setBizNo("ADJUST_" + order.getAdjustNo());
        request.setBizType("MANUAL_ADJUST_TRANSFER");
        request.addEntry(order.getFromAccountId(), EntryDirection.DEBIT, order.getAmount());
        request.addEntry(order.getToAccountId(), EntryDirection.CREDIT, order.getAmount());
        accountingEngine.doAccounting(request);
    }
}

/** 加币调账：无对手方账户，直接为目标账户增加余额（如系统赔付） */
@Component
public class AddAmountAdjustStrategy implements AdjustStrategy {
    @Autowired private AccountingEngine accountingEngine;

    @Override
    public AdjustType supportType() { return AdjustType.ADD_AMOUNT; }

    @Override
    public void execute(AdjustOrder order) {
        AccountingRequest request = new AccountingRequest();
        request.setBizNo("ADJUST_" + order.getAdjustNo());
        request.setBizType("MANUAL_ADJUST_ADD");
        // 对手方记入平台"调账损益"专用账户，保证复式记账借贷平衡，不产生资金黑洞
        request.addEntry(SystemAccountConstants.ADJUST_PROFIT_LOSS_ACCOUNT, EntryDirection.DEBIT, order.getAmount());
        request.addEntry(order.getToAccountId(), EntryDirection.CREDIT, order.getAmount());
        accountingEngine.doAccounting(request);
    }
}

@Component
public class DeductAmountAdjustStrategy implements AdjustStrategy {
    @Autowired private AccountingEngine accountingEngine;

/** 批量冻结调账：对多个账户执行同一冻结操作，内部逐笔调用单笔冻结，任一失败记录差错但不影响其余 */
@Component
public class BatchFreezeAdjustStrategy implements AdjustStrategy {
    @Autowired private FreezeService freezeService;

    @Override
    public AdjustType supportType() { return AdjustType.BATCH_FREEZE; }

    @Override
    public void execute(AdjustOrder order) {
        List<Long> accountIds = order.getBatchAccountIds();
        List<String> failedAccounts = new ArrayList<>();
        for (Long accountId : accountIds) {
            try {
                freezeService.freeze(accountId, order.getAmount(), FreezeReason.MANUAL,
                        "ADJUST_" + order.getAdjustNo(), null);
            } catch (Exception e) {
                failedAccounts.add(accountId + ":" + e.getMessage());
            }
        }
        if (!failedAccounts.isEmpty()) {
            throw new PartialFailureException("批量冻结部分失败: " + String.join(",", failedAccounts));
        }
    }
}

/** 策略调度器：根据调账类型路由到对应策略实现，符合开闭原则，新增调账类型无需修改已有代码 */
@Service
public class AdjustExecutionService {

    @Autowired
    private List<AdjustStrategy> strategies;
    @Autowired
    private AdjustOrderRepository adjustOrderRepository;
    @Autowired
    private AuditLogService auditLogService;

    private Map<AdjustType, AdjustStrategy> strategyMap;

    @PostConstruct
    public void init() {
        strategyMap = strategies.stream()
                .collect(Collectors.toMap(AdjustStrategy::supportType, Function.identity()));
    }

    /**
     * 执行调账单。
     * 单据隔离设计：调账单本身有独立的"重试/确认/回滚"三个操作按钮，
     * 分别对应下面三个方法，互相之间不能跨状态调用，防止误操作。
     */
    @Transactional
    public void execute(String adjustNo) {
        AdjustOrder order = adjustOrderRepository.selectForUpdate(adjustNo);
        if (order.getStatus() != AdjustOrderStatus.APPROVED) {
            throw new BusinessException("调账单未处于已审批状态，不允许执行: " + order.getStatus());
        }
        AdjustStrategy strategy = strategyMap.get(order.getAdjustType());
        if (strategy == null) {
            throw new BusinessException("不支持的调账类型: " + order.getAdjustType());
        }

        order.setStatus(AdjustOrderStatus.EXECUTING);
        adjustOrderRepository.updateStatus(order);

        try {
            strategy.execute(order);
            order.setStatus(AdjustOrderStatus.SUCCESS);
            adjustOrderRepository.updateStatus(order);
            auditLogService.record(AuditAction.ADJUST_EXECUTE_SUCCESS, order.getAdjustNo(),
                    order.getOperatorMisId(), "调账执行成功");
        } catch (Exception e) {
            order.setStatus(AdjustOrderStatus.FAILED);
            order.setFailReason(e.getMessage());
            adjustOrderRepository.updateStatus(order);
            auditLogService.record(AuditAction.ADJUST_EXECUTE_FAILED, order.getAdjustNo(),
                    order.getOperatorMisId(), "调账执行失败: " + e.getMessage());
            throw e;
        }
    }
}
```

### 7.4 调账单据操作隔离：重试、确认、回滚

调账平台在单据层面设计了"重试、确认、回滚"三个相互隔离的操作按钮，分别对应不同的故障恢复场景，且每个按钮背后绑定不同的权限校验，避免误操作扩大事故影响面。

```java
@Service
public class AdjustOrderOperationService {

    @Autowired private AdjustOrderRepository adjustOrderRepository;
    @Autowired private AdjustExecutionService adjustExecutionService;
    @Autowired private AccountingEngine accountingEngine;
    @Autowired private PermissionService permissionService;
    @Autowired private AuditLogService auditLogService;

    /**
     * 重试：仅允许对状态为 FAILED 的调账单重试，
     * 重试复用原始 bizNo（"ADJUST_" + adjustNo），依靠幂等机制天然防止重复扣款，
     * 即使调账单被误点多次重试，底层记账引擎也只会真正执行一次。
     */
    public void retry(String adjustNo, String operatorMisId) {
        checkPermission(operatorMisId, Role.ACCOUNTING_ADJUST_WRITE);
        AdjustOrder order = adjustOrderRepository.selectForUpdate(adjustNo);
        if (order.getStatus() != AdjustOrderStatus.FAILED) {
            throw new BusinessException("仅失败状态的调账单允许重试，当前状态: " + order.getStatus());
        }
        order.setStatus(AdjustOrderStatus.APPROVED); // 回退到已审批，重新走执行流程
        adjustOrderRepository.updateStatus(order);
        adjustExecutionService.execute(adjustNo);
        auditLogService.record(AuditAction.ADJUST_RETRY, adjustNo, operatorMisId, "手动重试调账单");
    }

    /**
     * 确认：适用于需要二次人工确认才能最终生效的调账场景（例如高危大额调账），
     * 确认动作本身不产生新的记账副作用，仅将单据从"待确认"推进到"已确认"状态，
     * 真正的记账仍由 execute() 完成，确认与执行解耦是为了给操作人留出"最后一次反悔"的窗口。
     */
    public void confirm(String adjustNo, String operatorMisId) {
        checkPermission(operatorMisId, Role.ACCOUNTING_ADJUST_WRITE);
        AdjustOrder order = adjustOrderRepository.selectForUpdate(adjustNo);
        if (order.getStatus() != AdjustOrderStatus.APPROVED) {
            throw new BusinessException("仅已审批状态的调账单允许确认执行");
        }
        adjustExecutionService.execute(adjustNo);
        auditLogService.record(AuditAction.ADJUST_CONFIRM, adjustNo, operatorMisId, "确认执行调账单");
    }

    /**
     * 回滚：仅允许对状态为 SUCCESS 的调账单回滚，
     * 回滚不是物理删除原记账记录（不可变账本原则，见第八章），
     * 而是生成一笔方向相反的冲正凭证，实现"账面可查、影响可消"的效果。
     */
    @Transactional
    public void rollback(String adjustNo, String operatorMisId, String reason) {
        checkPermission(operatorMisId, Role.ACCOUNTING_ADJUST_WRITE);
        AdjustOrder order = adjustOrderRepository.selectForUpdate(adjustNo);
        if (order.getStatus() != AdjustOrderStatus.SUCCESS) {
            throw new BusinessException("仅执行成功的调账单允许回滚，当前状态: " + order.getStatus());
        }

        AccountingRequest reverseRequest = buildReverseRequest(order);
        accountingEngine.doAccounting(reverseRequest);

        order.setStatus(AdjustOrderStatus.ROLLED_BACK);
        order.setRollbackReason(reason);
        adjustOrderRepository.updateStatus(order);
        auditLogService.record(AuditAction.ADJUST_ROLLBACK, adjustNo, operatorMisId, "回滚原因: " + reason);
    }

    /** 构建与原调账方向相反的冲正记账请求，业务流水号追加后缀避免与原流水冲突 */
    private AccountingRequest buildReverseRequest(AdjustOrder order) {
        AccountingRequest request = new AccountingRequest();
        request.setBizNo("REVERSE_ADJUST_" + order.getAdjustNo());
        request.setBizType("MANUAL_ADJUST_REVERSE");
        switch (order.getAdjustType()) {
            case TRANSFER:
                request.addEntry(order.getToAccountId(), EntryDirection.DEBIT, order.getAmount());
                request.addEntry(order.getFromAccountId(), EntryDirection.CREDIT, order.getAmount());
                break;
            case ADD_AMOUNT:
                request.addEntry(order.getToAccountId(), EntryDirection.DEBIT, order.getAmount());
                request.addEntry(SystemAccountConstants.ADJUST_PROFIT_LOSS_ACCOUNT, EntryDirection.CREDIT, order.getAmount());
                break;
            case DEDUCT_AMOUNT:
                request.addEntry(SystemAccountConstants.ADJUST_PROFIT_LOSS_ACCOUNT, EntryDirection.DEBIT, order.getAmount());
                request.addEntry(order.getFromAccountId(), EntryDirection.CREDIT, order.getAmount());
                break;
            default:
                throw new BusinessException("该调账类型暂不支持自动回滚，请走人工冲正流程: " + order.getAdjustType());
        }
        return request;
    }

    private void checkPermission(String misId, Role role) {
        if (!permissionService.hasRole(misId, role)) {
            throw new PermissionDeniedException("缺少必要权限: " + role);
        }
    }
}
```

### 7.5 授信资产：出资规则与退款规则配置

授信资产模块管理"谁为交易垫资、垫资规则如何配置、不同业务线的退款资金从哪个账户出"这类配置化能力，采用**规则引擎 + 优先级匹配算法**实现灵活配置。

```java
/** 出资规则实体：定义特定业务场景下资金的来源账户与出资比例 */
public class FundingRule {
    private Long ruleId;
    private String bizLine;         // 业务线编码
    private String sceneCode;       // 场景编码，如"预付订单""担保交易"
    private Long fundingAccountId;  // 出资账户
    private BigDecimal fundingRatio; // 出资比例，支持部分出资场景
    private int priority;           // 优先级，数值越小优先级越高
    private boolean enabled;
}

/** 退款规则实体：定义特定业务线的退款资金应从哪个账户扣减 */
public class RefundRule {
    private Long ruleId;
    private String bizLine;
    private Long refundSourceAccountId;
    private RefundStrategy strategy; // ORIGINAL_ROUTE(原路退回) / PLATFORM_ADVANCE(平台垫付后追偿)
    private boolean enabled;
}

/**
 * 规则匹配引擎：按业务线+场景查找出资/退款规则，
 * 使用优先级排序 + 最小匹配原则（第一个满足条件的规则即命中并短路返回），
 * 这是规则引擎中常见的"责任链式规则匹配"算法。
 */
@Service
public class FundingRuleEngine {

    @Autowired
    private FundingRuleRepository fundingRuleRepository;
    @Autowired
    private RefundRuleRepository refundRuleRepository;

    public FundingRule matchFundingRule(String bizLine, String sceneCode) {
        List<FundingRule> candidates = fundingRuleRepository.findByBizLineAndScene(bizLine, sceneCode);
        return candidates.stream()
                .filter(FundingRule::isEnabled)
                .sorted(Comparator.comparingInt(FundingRule::getPriority))
                .findFirst()
                .orElseThrow(() -> new BusinessException("未找到匹配的出资规则: " + bizLine + "/" + sceneCode));
    }

    public RefundRule matchRefundRule(String bizLine) {
        return refundRuleRepository.findByBizLine(bizLine).stream()
                .filter(RefundRule::isEnabled)
                .findFirst()
                .orElseThrow(() -> new BusinessException("未找到匹配的退款规则: " + bizLine));
    }

    /** 新增出资规则，写权限受角色"账务平台-写"控制 */
    @Transactional
    public void addFundingRule(FundingRule rule, String operatorMisId) {
        validateRatioSum(rule);
        fundingRuleRepository.insert(rule);
        AuditLogService.getInstance().record(AuditAction.ADD_FUNDING_RULE, rule.getRuleId().toString(),
                operatorMisId, "新增出资规则: " + rule.getBizLine());
    }

    /** 校验同一场景下多条出资规则的比例之和不超过100%，防止资金重复出资导致的配置性资损 */
    private void validateRatioSum(FundingRule newRule) {
        List<FundingRule> existing = fundingRuleRepository.findByBizLineAndScene(
                newRule.getBizLine(), newRule.getSceneCode());
        BigDecimal sum = existing.stream()
                .filter(FundingRule::isEnabled)
                .map(FundingRule::getFundingRatio)
                .reduce(BigDecimal.ZERO, BigDecimal::add)
                .add(newRule.getFundingRatio());
        if (sum.compareTo(BigDecimal.ONE) > 0) {
            throw new BusinessException("出资比例之和超过100%，配置非法");
        }
    }
}
```

### 7.6 角色权限体系

调账平台及账务系统整体的权限设计遵循最小权限原则，划分为五类角色，读、写、超管、调账读、调账写严格隔离，尤其是"调账写"作为最高危权限被单独管控。

| 角色 | 权限范围 | 说明 |
|------|---------|------|
| 账务平台-读 | 账户查询、流水查询、冻结查询、凭证查询、日终余额查询 | 面向客服、财务、风控等只读诉求方 |
| 账务平台-写 | 类型配置、余额报警配置、账户注销/恢复、部分操作按钮 | 面向运营、产品配置人员 |
| 账务平台-超管(RD) | 以上全部权限（不含调账写） | 面向研发人员日常排障 |
| 账务平台-调账(读) | 查询调账单、查询审批记录 | 面向审计、风控人员 |
| 账务平台-调账(写) | 发起调账、审批调账、执行调账、回滚调账 | 高危权限，需多级审批 + 操作留痕 |

### 8.1 余额不变性约束的三层防护

```
第一层：应用层 Balance 值对象构造时强制校验（第三章 3.2 节）
第二层：数据库 CHECK 约束强制校验（第三章 3.4 节）
第三层：定时任务全量扫描校验，发现即告警（本节新增）
```

```java
/**
 * 余额不变性全量巡检任务。
 * 算法：全表扫描（分批次，避免大事务长锁表），对每一行执行
 * total_amount == available_amount + frozen_amount 的校验，
 * 一旦发现不满足的记录，说明可能存在代码缺陷绕过了应用层校验，
 * 立即触发最高优先级告警并自动创建差错工单。
 * 这是防御性编程思想的体现：不完全信任前面几层防护，始终假设"总有漏网之鱼"。
 */
@Component
public class BalanceInvariantAuditor {

    @Autowired private AccountRepository accountRepository;
    @Autowired private AlertService alertService;
    @Autowired private DiscrepancyOrderService discrepancyOrderService;

    private static final int BATCH_SIZE = 1000;

    @Scheduled(cron = "0 0 3 * * ?") // 每天凌晨3点执行，避开业务高峰
    public void audit() {
        long lastId = 0;
        int abnormalCount = 0;
        while (true) {
            List<Account> batch = accountRepository.scanByIdRange(lastId, BATCH_SIZE);
            if (batch.isEmpty()) {
                break;
            }
            for (Account account : batch) {
                Balance balance = account.getBalance();
                if (balance.getTotalAmount() != balance.getAvailableAmount() + balance.getFrozenAmount()) {
                    abnormalCount++;
                    alertService.sendCritical("账户余额不变式被打破: accountId=" + account.getAccountId());
                    discrepancyOrderService.createOrder(account.getAccountId(), "余额不变式校验失败");
                }
            }
            lastId = batch.get(batch.size() - 1).getId();
        }
        if (abnormalCount > 0) {
            alertService.sendCritical("本次余额不变式巡检共发现" + abnormalCount + "个异常账户");
        }
    }
}
```

### 8.2 记账幂等的兜底：对账反查

第四章已经介绍了记账链路内的幂等机制，这里补充一道跨系统的兜底：定期将账务系统的流水与上游业务系统的订单/交易记录做数量与金额的双向核对，确保没有"业务发生了但没记账"或"记账了但业务没发生"的情况。

```java
/**
 * 双向对账算法（借鉴分布式系统中的"最终一致性校验"思想）：
 *  正向核对：以上游业务流水为基准，逐笔检查账务系统是否存在对应的记账记录（防止漏记）；
 *  反向核对：以账务系统流水为基准，逐笔检查上游是否存在对应业务单据（防止多记/重复记账）。
 * 两个方向的核对覆盖了幂等失效可能导致的两类问题：数据丢失与数据冗余。
 */
@Service
public class CrossSystemReconciliationService {

    @Autowired private UpstreamBizClient upstreamBizClient; // 抽象的上游业务系统客户端
    @Autowired private AccountingRecordRepository recordRepository;
    @Autowired private DiscrepancyOrderService discrepancyOrderService;

    @Scheduled(cron = "0 0 4 * * ?")
    public void reconcile(Date targetDate) {
        List<UpstreamBizOrder> upstreamOrders = upstreamBizClient.listOrdersByDate(targetDate);
        Set<String> upstreamBizNos = upstreamOrders.stream()
                .map(UpstreamBizOrder::getBizNo).collect(Collectors.toSet());

        List<AccountingRecord> accountingRecords = recordRepository.listByDate(targetDate);
        Set<String> accountingBizNos = accountingRecords.stream()
                .map(AccountingRecord::getBizNo).collect(Collectors.toSet());

        // 正向：上游有但账务没有 -> 漏记，需要立即补记账
        Set<String> missingInAccounting = new HashSet<>(upstreamBizNos);
        missingInAccounting.removeAll(accountingBizNos);
        for (String bizNo : missingInAccounting) {
            discrepancyOrderService.createOrder(bizNo, "上游业务存在但账务系统未记账，疑似漏记");
        }

        // 反向：账务有但上游没有 -> 疑似重复记账或脏数据，需要人工排查
        Set<String> extraInAccounting = new HashSet<>(accountingBizNos);
        extraInAccounting.removeAll(upstreamBizNos);
        for (String bizNo : extraInAccounting) {
            discrepancyOrderService.createOrder(bizNo, "账务系统存在但上游业务未找到，疑似重复记账或脏数据");
        }
    }
}
```

### 8.3 日终对账与自动修复（观察者模式）

日终对账是资金安全的关口，需要将"发现差异"和"处理差异"解耦：发现差异后，可能需要同时触发告警通知、自动修复尝试、生成差错工单等多个动作，这里使用**观察者模式**实现一对多的通知与处理。

```java
/** 差异事件 */
public class DiscrepancyEvent {
    private Long accountId;
    private long expectedBalance;
    private long actualBalance;
    private Date discoverTime;
    private String source; // 日终快照对账 / 跨系统对账 / 不变式巡检
}

/** 差异观察者接口 */
public interface DiscrepancyObserver {
    void onDiscrepancy(DiscrepancyEvent event);
}

/** 观察者一：告警通知 */
@Component
public class AlertDiscrepancyObserver implements DiscrepancyObserver {
    @Autowired private AlertService alertService;
    @Override
    public void onDiscrepancy(DiscrepancyEvent event) {
        alertService.sendCritical(String.format("账户%d发现余额差异，期望值%d，实际值%d，来源%s",
                event.getAccountId(), event.getExpectedBalance(), event.getActualBalance(), event.getSource()));
    }
}

/** 观察者二：小额差异自动修复（例如舍入误差在容忍范围内的差异，自动生成修复凭证） */
@Component
public class AutoRepairDiscrepancyObserver implements DiscrepancyObserver {
    private static final long AUTO_REPAIR_THRESHOLD = 1L; // 1分以内的差异允许自动修复

    @Autowired private AccountingEngine accountingEngine;

    @Override
    public void onDiscrepancy(DiscrepancyEvent event) {
        long diff = Math.abs(event.getExpectedBalance() - event.getActualBalance());
        if (diff <= AUTO_REPAIR_THRESHOLD) {
            AccountingRequest request = new AccountingRequest();
            request.setBizNo("AUTO_REPAIR_" + event.getAccountId() + "_" + event.getDiscoverTime().getTime());
            request.setBizType("AUTO_REPAIR_ROUNDING");
            long delta = event.getExpectedBalance() - event.getActualBalance();
            if (delta > 0) {
                request.addEntry(SystemAccountConstants.ROUNDING_ADJUST_ACCOUNT, EntryDirection.DEBIT, delta);
                request.addEntry(event.getAccountId(), EntryDirection.CREDIT, delta);
            } else {
                request.addEntry(event.getAccountId(), EntryDirection.DEBIT, -delta);
                request.addEntry(SystemAccountConstants.ROUNDING_ADJUST_ACCOUNT, EntryDirection.CREDIT, -delta);
            }
            accountingEngine.doAccounting(request);
        }
    }
}

/** 观察者三：生成差错工单，大额差异必须走人工调账平台处理，不允许自动修复 */
@Component
public class WorkOrderDiscrepancyObserver implements DiscrepancyObserver {
    @Autowired private DiscrepancyOrderService discrepancyOrderService;
    @Override
    public void onDiscrepancy(DiscrepancyEvent event) {
        long diff = Math.abs(event.getExpectedBalance() - event.getActualBalance());
        if (diff > 1L) {
            discrepancyOrderService.createOrder(String.valueOf(event.getAccountId()),
                    "日终对账发现大额差异，需人工介入调账平台处理");
        }
    }
}

/** 差异事件发布器：主题（Subject）角色，负责通知所有注册的观察者 */
@Component
public class DiscrepancyEventPublisher {

    @Autowired
    private List<DiscrepancyObserver> observers;

    public void publish(DiscrepancyEvent event) {
        for (DiscrepancyObserver observer : observers) {
            try {
                observer.onDiscrepancy(event);
            } catch (Exception e) {
                // 单个观察者失败不影响其他观察者执行，保证告警、修复、工单三条链路互相独立
                LoggerFactory.getLogger(getClass()).error("差异观察者处理失败: " + observer.getClass(), e);
            }
        }
    }
}
```

### 8.4 双写校验：影子记账

对于极端重要的资金链路，账务系统会引入"影子记账"机制：在正式记账的同时，用完全独立的第二套简化逻辑重新计算一遍结果，两者比对，只有一致才认为记账真正可信，这是从硬件领域"双模冗余"借鉴过来的软件工程实践。

```java
/**
 * 影子记账校验器：使用与主链路完全独立的简化计算逻辑，
 * 对同一笔记账请求的最终余额结果进行"旁路计算"，并与主链路结果比对，
 * 如果不一致，说明主链路代码可能存在缺陷，立即阻断并告警，
 * 这种"双实现互相校验"的思路能够发现单一实现自身逻辑漏洞导致的错误（而非仅仅是环境类故障）。
 */
@Component
public class ShadowAccountingValidator {

    @Autowired private AlertService alertService;

    public void validate(AccountingVoucher voucher, Map<Long, Long> actualBalanceAfter) {
        Map<Long, Long> shadowResult = shadowCompute(voucher, actualBalanceAfter);
        for (Map.Entry<Long, Long> entry : shadowResult.entrySet()) {
            Long expected = entry.getValue();
            Long actual = actualBalanceAfter.get(entry.getKey());
            if (!expected.equals(actual)) {
                alertService.sendCritical(String.format(
                        "影子记账校验不一致: accountId=%d, shadow=%d, actual=%d, bizNo=%s",
                        entry.getKey(), expected, actual, voucher.getBizNo()));
                throw new ShadowValidationFailedException("影子记账校验失败，主链路结果不可信，已阻断");
            }
        }
    }

    /** 使用最朴素的累加方式重新计算一遍余额变化，逻辑与主链路完全独立实现，不复用任何主链路代码 */
    private Map<Long, Long> shadowCompute(AccountingVoucher voucher, Map<Long, Long> balanceBefore) {
        Map<Long, Long> result = new HashMap<>(balanceBefore);
        for (AccountingEntry entry : voucher.getEntries()) {
            long before = result.getOrDefault(entry.getAccountId(), 0L);
            long after = entry.getDirection() == EntryDirection.DEBIT
                    ? before + entry.getAmount()
                    : before - entry.getAmount();
            result.put(entry.getAccountId(), after);
        }
        return result;
    }
}
```

### 8.6 余额监控告警：热点账户与余额配置

对应"余额配置"模块，为特定账户（尤其是平台核心账户）配置监控规则，一旦余额触及阈值即触达相关责任人，是资金安全的主动防御手段。

```java
/** 余额监控规则 */
public class BalanceAlertRule {
    private Long accountId;
    private Long minThreshold;   // 最低余额阈值，低于此值告警（如平台账户即将穿底）
    private Long maxThreshold;   // 最高余额阈值，超过此值告警（如异常大额入账）
    private List<String> notifyMisIds; // 触达人群
    private boolean enabled;
}

@Service
public class BalanceAlertService {

    @Autowired private BalanceAlertRuleRepository ruleRepository;
    @Autowired private AccountRepository accountRepository;
    @Autowired private NotificationService notificationService;

    /** 记账完成后异步触发检查，避免影响主链路记账性能 */
    @Async
    public void checkAfterAccounting(Long accountId) {
        BalanceAlertRule rule = ruleRepository.findByAccountId(accountId);
        if (rule == null || !rule.isEnabled()) {
            return;
        }
        Account account = accountRepository.selectByAccountId(accountId);
        long total = account.getBalance().getTotalAmount();

        if (rule.getMinThreshold() != null && total < rule.getMinThreshold()) {
            notificationService.notify(rule.getNotifyMisIds(),
                    "账户" + accountId + "余额过低告警，当前余额：" + total);
        }
        if (rule.getMaxThreshold() != null && total > rule.getMaxThreshold()) {
            notificationService.notify(rule.getNotifyMisIds(),
                    "账户" + accountId + "余额异常偏高告警，当前余额：" + total);
        }
    }
}
```

## 九、系统总结

### 9.1 关键设计回顾

账务系统的架构设计始终围绕"资金安全"这一核心目标展开，本文档从九个维度构建了完整的技术方案：

1. **账户模型**：以不可变值对象（Balance）承载余额，在构造阶段就强制校验"总余额=可用余额+冻结余额"的不变式，把安全校验前移到最早的时间点。

2. **记账引擎**：以复式记账法为理论基础，通过责任链模式将幂等校验、余额校验、账户加锁、余额变更、流水生成等步骤解耦，每个环节职责单一、可独立测试；通过 TCC/Saga 两种分布式事务模式覆盖不同复杂度的跨系统记账场景；通过固定顺序加锁算法从根本上杜绝死锁。

3. **热点账户优化**：通过生产者消费者模式实现的批量合并写入，以及借鉴 LongAdder 思想的分段计数算法，将热点账户的并发瓶颈从"单行锁竞争"转移到"内存队列聚合"，数量级提升吞吐能力。

4. **流水管理**：通过改进版雪花算法解决分布式环境下流水号生成的唯一性与时钟回拨问题；通过冷热分离与增量快照算法，兼顾查询性能与历史数据存储成本。

5. **冻结解冻**：通过独立的冻结记录建档与原子化的 CAS 式更新语句，支持部分冻结、部分解冻、预授权自动过期释放等复杂场景。

6. **调账平台**：通过状态机严格约束调账单生命周期，通过责任链实现多级审批，通过策略模式支持可扩展的调账操作类型，通过"重试/确认/回滚"三按钮隔离将高危操作的爆炸半径降到最低。

7. **资金安全**：构建了从应用层校验、数据库约束、定时巡检、跨系统对账、观察者模式驱动的差异处理、影子记账双写校验、到不可篡改审计日志的多层防御体系，任何单一防线被突破都有后续防线兜底。

### 9.2 核心不变量清单

账务系统的正确性最终可以归纳为几条必须始终成立的不变量，所有的架构设计都是为了保障它们不被打破：

- 借贷平衡不变量：任意一笔记账凭证，借方发生额合计恒等于贷方发生额合计。
- 余额不变量：任意账户任意时刻，总余额恒等于可用余额加冻结余额。
- 幂等不变量：任意业务流水号对应的记账操作，无论重试多少次，最终效果等价于只执行一次。
- 非负不变量：任意账户的可用余额与冻结余额不允许为负数（明确配置为允许透支的特殊账户类型除外）。
- 账本不可变不变量：流水与凭证一旦生成不可修改、不可物理删除，任何纠错都通过新增反向记录实现。

### 9.3 演进方向

实际生产系统在本文档方案基础上，通常会朝以下方向继续演进：账户与流水表按业务量持续做更细粒度的分库分表；引入实时流计算对异常资金变动做毫秒级风控识别；将影子记账从单一比对升级为多副本共识校验；调账审批流引入更细粒度的分级授权与风险评分模型，让审批强度与调账金额、调账类型的风险等级动态匹配。账务系统没有"完成态"，只有伴随业务复杂度不断加固的过程，每一次线上事故的复盘都应该转化为新的自动化校验规则，持续收窄人为出错的空间。

### 10.1 案例一：交易入账全链路

#### 10.1.1 场景描述

用户在平台完成一笔支付后（例如外卖订单付款 100 元），支付系统通过消息队列通知账务系统"支付已完成"，账务系统需要完成以下全链路操作：

1. **消费支付消息**：从消息队列接收支付完成事件，提取关键业务信息（支付单号、付款人、收款商户、金额等）。
2. **生成会计凭证**：根据业务类型和分账规则，构建一张包含多条分录的会计凭证（用户账户减少、商户待结算账户增加、平台收入账户增加）。
3. **复式记账**：将凭证提交到记账引擎，经过幂等校验→借贷平衡校验→账户加锁→余额充足性校验→余额变更→流水生成的完整责任链处理。
4. **余额更新与结果确认**：各账户余额完成原子更新，记账流水持久化，返回记账结果。

#### 10.1.2 入账消息消费者

```java
/**
 * 支付完成消息消费者：账务系统入账的入口。
 * 设计要点：
 *  1. 消息消费采用"先处理后 ACK"模式，处理失败不确认消息，等待重投递；
 *  2. 重投递会导致重复消费，依赖记账引擎的幂等机制保证不会重复入账；
 *  3. 整个消费过程有完整的结构化日志，便于问题追溯与线上排查；
 *  4. 异常分类处理：业务异常（如账户不存在）直接告警不重试，系统异常（如数据库超时）抛出异常触发重投递。
 */
@Component
public class PaymentSuccessConsumer {

    private static final Logger log = LoggerFactory.getLogger(PaymentSuccessConsumer.class);

    @Autowired private VoucherBuilder voucherBuilder;
    @Autowired private AccountingEngine accountingEngine;
    @Autowired private AlertService alertService;

    @RocketMQMessageListener(topic = "PAYMENT_SUCCESS_TOPIC", consumerGroup = "accounting_payment_group")
    public void onMessage(PaymentSuccessMessage message) {
        String traceId = TraceContext.getTraceId();
        long startTime = System.currentTimeMillis();

        log.info("[入账消费] 收到支付完成消息, traceId={}, paymentNo={}, payerUserId={}, merchantId={}, amount={}",
                traceId, message.getPaymentNo(), message.getPayerUserId(),
                message.getMerchantId(), message.getPayAmount());

        try {
            // 第一步：消息基本校验
            validateMessage(message);

            // 第二步：构建会计凭证（分账计算 + 凭证组装）
            AccountingVoucher voucher = voucherBuilder.buildPaymentVoucher(message);

            log.info("[入账消费] 凭证构建完成, traceId={}, paymentNo={}, voucherNo={}, entryCount={}",
                    traceId, message.getPaymentNo(), voucher.getVoucherNo(), voucher.getEntries().size());

            // 第三步：提交记账引擎执行复式记账
            AccountingResult result = accountingEngine.post(voucher);

            long costMs = System.currentTimeMillis() - startTime;
            log.info("[入账消费] 记账完成, traceId={}, paymentNo={}, result={}, costMs={}",
                    traceId, message.getPaymentNo(), result.getStatus(), costMs);

            // 记账耗时监控，超过 500ms 告警
            if (costMs > 500) {
                log.warn("[入账消费] 记账耗时过长, traceId={}, paymentNo={}, costMs={}",
                        traceId, message.getPaymentNo(), costMs);
            }

        } catch (AccountNotFoundException e) {
            // 账户不存在属于数据配置问题，不重试，直接告警人工介入
            log.error("[入账消费] 账户不存在，需人工排查, traceId={}, paymentNo={}, error={}",
                    traceId, message.getPaymentNo(), e.getMessage());
            alertService.sendCritical("入账失败-账户不存在: paymentNo=" + message.getPaymentNo()
                    + ", error=" + e.getMessage());
            // 不抛出异常，ACK 消息，避免无限重试

        } catch (UnbalancedVoucherException e) {
            // 凭证借贷不平衡属于系统缺陷，不重试，立即告警
            log.error("[入账消费] 凭证借贷不平衡，疑似系统缺陷, traceId={}, paymentNo={}, error={}",
                    traceId, message.getPaymentNo(), e.getMessage());
            alertService.sendCritical("入账失败-凭证不平衡: paymentNo=" + message.getPaymentNo());

        } catch (InsufficientBalanceException e) {
            // 余额不足（如用户余额账户已被扣光），记录差错单
            log.error("[入账消费] 余额不足, traceId={}, paymentNo={}, error={}",
                    traceId, message.getPaymentNo(), e.getMessage());
            alertService.sendWarning("入账失败-余额不足: paymentNo=" + message.getPaymentNo());

        } catch (Exception e) {
            // 系统异常（数据库超时、网络抖动等），抛出异常触发消息重投递
            log.error("[入账消费] 系统异常, traceId={}, paymentNo={}",
                    traceId, message.getPaymentNo(), e);
            throw new RuntimeException("入账处理系统异常，等待重试", e);
        }
    }

    private void validateMessage(PaymentSuccessMessage message) {
        if (message.getPaymentNo() == null || message.getPaymentNo().isEmpty()) {
            throw new IllegalArgumentException("支付单号不能为空");
        }
        if (message.getPayAmount() <= 0) {
            throw new IllegalArgumentException("支付金额必须为正数: " + message.getPayAmount());
        }
        if (message.getPayerUserId() == null) {
            throw new IllegalArgumentException("付款用户ID不能为空");
        }
        if (message.getMerchantId() == null) {
            throw new IllegalArgumentException("收款商户ID不能为空");
        }
    }
}
```

#### 10.1.3 会计凭证构建器

```java
/**
 * 会计凭证构建器：将支付完成消息转化为符合复式记账要求的会计凭证。
 * 核心职责：
 *  1. 根据分账规则引擎计算各参与方的分账金额；
 *  2. 查找各参与方对应的账务账户；
 *  3. 按照复式记账要求组装借方/贷方分录；
 *  4. 在凭证离开构建层之前执行借贷平衡校验，将校验前移到最早的时间点。
 */
@Service
public class VoucherBuilder {

    private static final Logger log = LoggerFactory.getLogger(VoucherBuilder.class);

    @Autowired private SplitRuleEngine splitRuleEngine;
    @Autowired private AccountRepository accountRepository;
    @Autowired private FlowNoGenerator flowNoGenerator;

    /**
     * 构建支付入账凭证。
     * 示例：用户支付 100 元，平台抽成 5%
     * 借：用户可用余额账户 100 元（用户的资金减少）
     * 贷：商户待结算账户 95 元（商户的待结算收入增加）
     * 贷：平台收入账户 5 元（平台服务费收入）
     * 借方合计 100 = 贷方合计 95 + 5 = 100，满足借贷平衡。
     */
    public AccountingVoucher buildPaymentVoucher(PaymentSuccessMessage message) {
        // 查询分账规则
        SplitRule splitRule = splitRuleEngine.resolve(message.getBizType(), message.getMerchantId());
        long merchantAmount = splitRule.calculateMerchantAmount(message.getPayAmount());
        long platformFee = message.getPayAmount() - merchantAmount;

        log.info("[凭证构建] 分账计算完成, bizNo={}, totalAmount={}, merchantAmount={}, platformFee={}",
                message.getPaymentNo(), message.getPayAmount(), merchantAmount, platformFee);

        // 校验分账金额一致性：分账后各项之和必须等于支付总额
        if (merchantAmount + platformFee != message.getPayAmount()) {
            throw new SplitAmountMismatchException(
                    String.format("分账金额不一致: total=%d, merchant=%d, platform=%d, bizNo=%s",
                            message.getPayAmount(), merchantAmount, platformFee, message.getPaymentNo()));
        }

        // 查找各参与方的账务账户
        Account payerAccount = accountRepository.findBySubjectAndType(
                message.getPayerUserId(), AccountType.USER_AVAILABLE);
        Account merchantAccount = accountRepository.findBySubjectAndType(
                message.getMerchantId(), AccountType.MERCHANT_SETTLEMENT);
        Account platformAccount = accountRepository.findBySubjectAndType(
                SystemAccountConstants.PLATFORM_SUBJECT_ID, AccountType.PLATFORM_INCOME);

        if (payerAccount == null || merchantAccount == null || platformAccount == null) {
            throw new AccountNotFoundException(
                    String.format("记账账户不存在, payerUserId=%d, merchantId=%d, bizNo=%s",
                            message.getPayerUserId(), message.getMerchantId(), message.getPaymentNo()));
        }

        // 组装凭证
        AccountingVoucher voucher = new AccountingVoucher();
        voucher.setVoucherNo(flowNoGenerator.generateVoucherNo());
        voucher.setBizNo(message.getPaymentNo());
        voucher.setBizType(message.getBizType());
        voucher.setOccurTime(message.getPayTime());

        // 借方：用户可用余额减少（资产类科目借方为增加，但此处语义是"用户付出了钱"，
        // 从平台视角看是用户的负债/应付减少，具体借贷方向由科目性质决定，此处简化处理）
        voucher.addEntry(new AccountingEntry(
                payerAccount.getAccountId(), EntryDirection.DEBIT, message.getPayAmount(), "1001"));

        // 贷方：商户待结算账户增加
        voucher.addEntry(new AccountingEntry(
                merchantAccount.getAccountId(), EntryDirection.CREDIT, merchantAmount, "2001"));

        // 贷方：平台收入账户增加
        voucher.addEntry(new AccountingEntry(
                platformAccount.getAccountId(), EntryDirection.CREDIT, platformFee, "4001"));

        // 提交前强制做一次借贷平衡校验，在凭证离开构建层之前就拦截不平衡问题
        voucher.validateBalance();

        log.info("[凭证构建] 凭证组装完成, bizNo={}, voucherNo={}, entryCount={}",
                message.getPaymentNo(), voucher.getVoucherNo(), voucher.getEntries().size());

        return voucher;
    }
}
```

#### 10.1.5 分账规则引擎

```java
/**
 * 分账规则引擎：根据业务类型和商户维度确定分账比例。
 * 实际生产系统中分账规则通常来自运营配置中心，支持按商户、品类、活动等多维度差异化配置。
 * 此处简化为固定比例 + 商户级别覆盖两层规则。
 */
@Service
public class SplitRuleEngine {

    private static final Logger log = LoggerFactory.getLogger(SplitRuleEngine.class);

    @Autowired private SplitRuleRepository splitRuleRepository;

    /** 默认平台抽成比例（万分比），5% = 500/10000 */
    private static final int DEFAULT_PLATFORM_FEE_RATE = 500;

    public SplitRule resolve(String bizType, Long merchantId) {
        // 优先查找商户级别的特殊规则（如新商户优惠期免佣金）
        SplitRule merchantRule = splitRuleRepository.findByBizTypeAndMerchant(bizType, merchantId);
        if (merchantRule != null && merchantRule.isEnabled()) {
            log.info("[分账规则] 命中商户级规则, bizType={}, merchantId={}, feeRate={}",
                    bizType, merchantId, merchantRule.getPlatformFeeRate());
            return merchantRule;
        }

        // 回退到业务类型级别的默认规则
        SplitRule defaultRule = splitRuleRepository.findByBizType(bizType);
        if (defaultRule != null) {
            return defaultRule;
        }

        // 兜底：使用系统默认比例
        log.warn("[分账规则] 未找到配置规则，使用系统默认, bizType={}, merchantId={}", bizType, merchantId);
        SplitRule fallback = new SplitRule();
        fallback.setPlatformFeeRate(DEFAULT_PLATFORM_FEE_RATE);
        return fallback;
    }
}

/**
 * 分账规则实体。
 * 金额计算统一使用"分"为单位的整数运算，避免浮点精度问题。
 * 分账尾差统一归属商户（行业惯例：平台不多收一分钱）。
 */
public class SplitRule {

    /** 平台抽成比例，万分比，例如 500 表示 5% */
    private int platformFeeRate;

    private boolean enabled = true;

    /**
     * 计算商户应得金额。
     * 算法：先算平台费（向下取整），商户得到剩余部分，
     * 保证 merchantAmount + platformFee == totalAmount 恒成立，不会出现尾差丢失。
     */
    public long calculateMerchantAmount(long totalAmount) {
        long platformFee = totalAmount * platformFeeRate / 10000;
        return totalAmount - platformFee;
    }

    public int getPlatformFeeRate() { return platformFeeRate; }
    public void setPlatformFeeRate(int platformFeeRate) { this.platformFeeRate = platformFeeRate; }
    public boolean isEnabled() { return enabled; }
    public void setEnabled(boolean enabled) { this.enabled = enabled; }
}
```

### 10.2 案例二：日终轧账全链路

#### 10.2.1 场景描述

每日营业结束后（通常在凌晨业务低谷期），账务系统需要执行一套完整的日终轧账流程，确认当日所有账务数据的正确性。日终轧账是整个账务系统"自证清白"的核心机制，也是金融级系统的硬性合规要求。完整链路如下：

1. **汇总当日交易**：按账户维度聚合当日所有借方、贷方发生额，生成每个账户的当日借贷汇总。
2. **试算平衡验证**：对全系统所有账户执行试算平衡校验——全部账户的借方余额总和必须等于贷方余额总和（复式记账法的系统级校验）。
3. **生成日终报表**：将汇总结果写入日报表，包括总交易笔数、总交易金额、各业务类型分布、异常账户清单。
4. **差异处理**：发现的任何差异通过观察者模式分发给告警通知、自动修复、差错工单三条处理链路。

#### 10.2.2 日终轧账调度器

```java
/**
 * 日终轧账主调度器。
 * 设计要点：
 *  1. 分布式锁保证多实例部署时只有一台机器执行轧账，避免重复计算；
 *  2. 轧账任务本身也具备幂等性——同一天的轧账结果写入采用 UPSERT 语义，重复执行不会产生脏数据；
 *  3. 全链路耗时监控与告警，轧账超时意味着数据量异常或系统性能退化，需要及时关注。
 */
@Component
public class DayEndReconciliationScheduler {

    private static final Logger log = LoggerFactory.getLogger(DayEndReconciliationScheduler.class);

    @Autowired private RedissonClient redissonClient;
    @Autowired private TransactionSummaryService summaryService;
    @Autowired private TrialBalanceService trialBalanceService;
    @Autowired private DailyReportService dailyReportService;
    @Autowired private DiscrepancyEventPublisher discrepancyPublisher;
    @Autowired private AlertService alertService;

    /** 每日凌晨 1:00 触发，处理前一个自然日的数据 */
    @Scheduled(cron = "0 0 1 * * ?")
    public void execute() {
        String lockKey = "day_end_reconciliation_lock";
        RLock lock = redissonClient.getLock(lockKey);
        boolean locked = false;

        Date targetDate = DateUtils.addDays(new Date(), -1);
        String dateStr = DateFormatUtils.format(targetDate, "yyyy-MM-dd");
        String traceId = TraceContext.getTraceId();
        long startTime = System.currentTimeMillis();

        log.info("[日终轧账] 开始执行, traceId={}, targetDate={}", traceId, dateStr);

        try {
            // 分布式锁，防止多实例重复执行，锁过期时间 2 小时（轧账通常 30 分钟内完成）
            locked = lock.tryLock(0, 7200000, TimeUnit.MILLISECONDS);
            if (!locked) {
                log.info("[日终轧账] 其他实例正在执行，本实例跳过, traceId={}", traceId);
                return;
            }

            // 幂等检查：查询当日轧账是否已经完成
            if (dailyReportService.isReportGenerated(targetDate)) {
                log.info("[日终轧账] 当日报表已存在，跳过重复执行, traceId={}, targetDate={}", traceId, dateStr);
                return;
            }

            // 第一步：汇总当日交易
            log.info("[日终轧账] 开始汇总当日交易, traceId={}, targetDate={}", traceId, dateStr);
            TransactionSummary summary = summaryService.summarize(targetDate);
            log.info("[日终轧账] 交易汇总完成, traceId={}, totalCount={}, totalDebit={}, totalCredit={}",
                    traceId, summary.getTotalCount(), summary.getTotalDebit(), summary.getTotalCredit());

            // 第二步：试算平衡验证
            log.info("[日终轧账] 开始试算平衡验证, traceId={}", traceId);
            TrialBalanceResult trialResult = trialBalanceService.verify(targetDate);
            log.info("[日终轧账] 试算平衡结果, traceId={}, balanced={}, debitTotal={}, creditTotal={}",
                    traceId, trialResult.isBalanced(), trialResult.getDebitTotal(), trialResult.getCreditTotal());

            // 第三步：生成日终报表
            log.info("[日终轧账] 开始生成日报, traceId={}", traceId);
            DailyReport report = dailyReportService.generate(targetDate, summary, trialResult);
            log.info("[日终轧账] 日报生成完成, traceId={}, reportId={}", traceId, report.getReportId());

            // 第四步：处理差异
            if (!trialResult.isBalanced() || !trialResult.getDiscrepancies().isEmpty()) {
                log.warn("[日终轧账] 发现差异，启动差异处理, traceId={}, discrepancyCount={}",
                        traceId, trialResult.getDiscrepancies().size());
                for (DiscrepancyEvent event : trialResult.getDiscrepancies()) {
                    discrepancyPublisher.publish(event);
                }
            }

            long costMs = System.currentTimeMillis() - startTime;
            log.info("[日终轧账] 执行完成, traceId={}, targetDate={}, costMs={}", traceId, dateStr, costMs);

            // 轧账耗时超过 1 小时发出告警，提示可能需要优化
            if (costMs > 3600000) {
                alertService.sendWarning(
                        String.format("日终轧账耗时过长: %d ms, targetDate=%s", costMs, dateStr));
            }

        } catch (Exception e) {
            long costMs = System.currentTimeMillis() - startTime;
            log.error("[日终轧账] 执行异常, traceId={}, targetDate={}, costMs={}", traceId, dateStr, costMs, e);
            alertService.sendCritical("日终轧账执行失败: " + dateStr + ", error=" + e.getMessage());
        } finally {
            if (locked) {
                lock.unlock();
            }
        }
    }
}
```

#### 10.2.3 交易汇总服务

```java
/**
 * 当日交易汇总服务。
 * 算法：分批扫描当日流水表，按账户ID维度聚合借方发生额和贷方发生额，
 * 同时按业务类型维度做二次聚合，生成两个维度的汇总数据。
 * 分批扫描避免全表锁和内存溢出，每批 5000 条，使用游标式分页（基于自增ID而非 OFFSET）。
 */
@Service
public class TransactionSummaryService {

    private static final Logger log = LoggerFactory.getLogger(TransactionSummaryService.class);
    private static final int BATCH_SIZE = 5000;

    @Autowired private FlowRepository flowRepository;
    @Autowired private TransactionSummaryRepository summaryRepository;

    public TransactionSummary summarize(Date targetDate) {
        Map<Long, AccountDaySummary> accountSummaries = new HashMap<>();
        Map<String, BizTypeSummary> bizTypeSummaries = new HashMap<>();
        long totalCount = 0;
        long totalDebit = 0;
        long totalCredit = 0;
        long lastId = 0;

        while (true) {
            List<AccountFlow> batch = flowRepository.scanByDateAndIdRange(targetDate, lastId, BATCH_SIZE);
            if (batch.isEmpty()) {
                break;
            }

            for (AccountFlow flow : batch) {
                totalCount++;

                // 按账户维度聚合
                AccountDaySummary accountSummary = accountSummaries.computeIfAbsent(
                        flow.getAccountId(), id -> new AccountDaySummary(id, targetDate));

                if (flow.getDirection() == EntryDirection.DEBIT) {
                    accountSummary.addDebit(flow.getAmount());
                    totalDebit += flow.getAmount();
                } else {
                    accountSummary.addCredit(flow.getAmount());
                    totalCredit += flow.getAmount();
                }
                accountSummary.incrementCount();

                // 按业务类型维度聚合
                BizTypeSummary bizSummary = bizTypeSummaries.computeIfAbsent(
                        flow.getBizType(), type -> new BizTypeSummary(type, targetDate));
                bizSummary.addAmount(flow.getAmount());
                bizSummary.incrementCount();
            }

            lastId = batch.get(batch.size() - 1).getId();

            if (batch.size() < BATCH_SIZE) {
                break; // 最后一批不足一页，说明已经扫完
            }
        }

        // 批量写入汇总表（UPSERT 语义，保证幂等）
        for (AccountDaySummary summary : accountSummaries.values()) {
            summaryRepository.upsert(summary);
        }

        log.info("[交易汇总] 汇总完成, targetDate={}, accountCount={}, bizTypeCount={}, totalCount={}",
                DateFormatUtils.format(targetDate, "yyyy-MM-dd"),
                accountSummaries.size(), bizTypeSummaries.size(), totalCount);

        TransactionSummary result = new TransactionSummary();
        result.setTargetDate(targetDate);
        result.setTotalCount(totalCount);
        result.setTotalDebit(totalDebit);
        result.setTotalCredit(totalCredit);
        result.setAccountSummaries(accountSummaries);
        result.setBizTypeSummaries(bizTypeSummaries);
        return result;
    }
}

/** 单账户当日汇总数据 */
public class AccountDaySummary {
    private Long accountId;
    private Date summaryDate;
    private long debitSum = 0;
    private long creditSum = 0;
    private int flowCount = 0;

    public AccountDaySummary(Long accountId, Date summaryDate) {
        this.accountId = accountId;
        this.summaryDate = summaryDate;
    }

    public void addDebit(long amount) { this.debitSum += amount; }
    public void addCredit(long amount) { this.creditSum += amount; }
    public void incrementCount() { this.flowCount++; }

    public Long getAccountId() { return accountId; }
    public long getDebitSum() { return debitSum; }
    public long getCreditSum() { return creditSum; }
    public int getFlowCount() { return flowCount; }
    public Date getSummaryDate() { return summaryDate; }
}
```

#### 10.2.4 试算平衡验证服务

```java
/**
 * 试算平衡验证服务。
 * 试算平衡表（Trial Balance）是会计学中的基本工具：
 * 将所有账户的期末借方余额加总，与所有账户的期末贷方余额加总，两者必须相等。
 * 如果不相等，说明系统中一定存在记账错误（借贷不平衡的凭证被错误地提交了）。
 *
 * 算法：
 *  1. 读取当日余额快照（由 5.3 节的快照服务提前生成），获取每个账户的期末余额；
 *  2. 按账户科目性质判断该余额属于借方余额还是贷方余额（资产类账户余额在借方，负债/权益类在贷方）；
 *  3. 分别求和比较，差额为零则试算平衡通过。
 *  4. 额外校验：逐账户比对快照余额与实时余额，发现不一致则记录差异事件。
 */
@Service
public class TrialBalanceService {

    private static final Logger log = LoggerFactory.getLogger(TrialBalanceService.class);

    @Autowired private DailyBalanceSnapshotRepository snapshotRepository;
    @Autowired private AccountRepository accountRepository;
    @Autowired private AccountTypeConfigRepository configRepository;

    public TrialBalanceResult verify(Date targetDate) {
        List<DailyBalanceSnapshot> snapshots = snapshotRepository.findAllByDate(targetDate);
        List<DiscrepancyEvent> discrepancies = new ArrayList<>();

        long debitTotal = 0;
        long creditTotal = 0;
        int accountCount = 0;
        int abnormalCount = 0;

        for (DailyBalanceSnapshot snapshot : snapshots) {
            accountCount++;

            // 根据账户类型判断科目性质：资产类余额归借方，负债/权益类余额归贷方
            AccountTypeConfig config = configRepository.findByAccountId(snapshot.getAccountId());
            boolean isDebitNature = isDebitNatureAccount(config);

            if (isDebitNature) {
                debitTotal += snapshot.getEndBalance();
            } else {
                creditTotal += snapshot.getEndBalance();
            }

            // 逐账户校验：快照余额与当前实时余额的一致性
            try {
                Account currentAccount = accountRepository.selectByAccountId(snapshot.getAccountId());
                if (currentAccount != null) {
                    // 注意：由于快照是截止到昨日的数据，而当前余额已经包含了今日的变动，
                    // 所以此处需要用"快照期末余额 + 今日已发生的流水"来与当前余额比对。
                    // 简化处理：在轧账时段（凌晨1点），今日流水极少，直接比对差异是否在合理范围内
                    long snapshotBalance = snapshot.getEndBalance();
                    long currentBalance = currentAccount.getBalance().getTotalAmount();
                    long todayFlowNet = calculateTodayNetFlow(snapshot.getAccountId(), targetDate);
                    long expectedCurrent = snapshotBalance + todayFlowNet;

                    if (expectedCurrent != currentBalance) {
                        abnormalCount++;
                        DiscrepancyEvent event = new DiscrepancyEvent();
                        event.setAccountId(snapshot.getAccountId());
                        event.setExpectedBalance(expectedCurrent);
                        event.setActualBalance(currentBalance);
                        event.setDiscoverTime(new Date());
                        event.setSource("日终试算平衡校验");
                        discrepancies.add(event);

                        log.warn("[试算平衡] 账户余额不一致, accountId={}, expected={}, actual={}, diff={}",
                                snapshot.getAccountId(), expectedCurrent, currentBalance,
                                currentBalance - expectedCurrent);
                    }
                }
            } catch (Exception e) {
                log.error("[试算平衡] 账户校验异常, accountId={}", snapshot.getAccountId(), e);
            }
        }

        boolean balanced = (debitTotal == creditTotal);
        if (!balanced) {
            log.error("[试算平衡] 试算不平衡! debitTotal={}, creditTotal={}, diff={}",
                    debitTotal, creditTotal, debitTotal - creditTotal);

            // 全局不平衡本身就是一个最高级别的差异事件
            DiscrepancyEvent globalEvent = new DiscrepancyEvent();
            globalEvent.setExpectedBalance(debitTotal);
            globalEvent.setActualBalance(creditTotal);
            globalEvent.setDiscoverTime(new Date());
            globalEvent.setSource("试算平衡全局校验");
            discrepancies.add(globalEvent);
        }

        log.info("[试算平衡] 验证完成, accountCount={}, debitTotal={}, creditTotal={}, balanced={}, abnormalCount={}",
                accountCount, debitTotal, creditTotal, balanced, abnormalCount);

        TrialBalanceResult result = new TrialBalanceResult();
        result.setTargetDate(targetDate);
        result.setDebitTotal(debitTotal);
        result.setCreditTotal(creditTotal);
        result.setBalanced(balanced);
        result.setAccountCount(accountCount);
        result.setAbnormalCount(abnormalCount);
        result.setDiscrepancies(discrepancies);
        return result;
    }

    /**
     * 判断账户科目性质是否为借方（资产类）。
     * 资产类、费用类账户余额正常在借方；负债类、权益类、收入类账户余额正常在贷方。
     */
    private boolean isDebitNatureAccount(AccountTypeConfig config) {
        if (config == null) return true; // 默认按资产类处理
        String subjectCode = config.getDebitSubjectCode();
        // 科目编码约定：1xxx=资产，2xxx=负债，3xxx=权益，4xxx=收入，5xxx=费用
        return subjectCode != null && (subjectCode.startsWith("1") || subjectCode.startsWith("5"));
    }

    /** 计算账户在目标日期之后至当前的净流水变动 */
    private long calculateTodayNetFlow(Long accountId, Date targetDate) {
        Date todayStart = DateUtils.addDays(targetDate, 1);
        FlowAggregateResult aggregate = flowRepository.aggregateByAccountAndDateRange(
                accountId, todayStart, new Date());
        return aggregate != null ? aggregate.getDebitSum() - aggregate.getCreditSum() : 0;
    }

    @Autowired private FlowRepository flowRepository;
}

/** 试算平衡结果 */

    private long debitTotal;
    private long creditTotal;
    private boolean balanced;
    private int accountCount;
    private int abnormalCount;
    private List<DiscrepancyEvent> discrepancies = new ArrayList<>();

    // getter/setter 省略
}
```

```java
                report.getReportId(), DateFormatUtils.format(targetDate, "yyyy-MM-dd"),
```

### 10.3 案例三：商户提现/结算全链路

#### 10.3.1 场景描述

商户在平台上产生的营业收入，经过账务系统的复式记账后，资金先进入商户的"待结算账户"。当结算周期到达（例如 T+1 日结）后，系统自动发起结算流程，将可结算金额从待结算账户转移到商户的"可提现账户"，商户随后可以发起提现操作，将资金转出到其银行卡。完整链路如下：

1. **结算周期到达与任务触发**：定时调度检测哪些商户的结算周期已到达，生成结算任务。
2. **计算应结金额**：汇总商户在结算窗口内的所有已入账交易，扣除退款、平台扣罚，计算净应结金额。
3. **结算记账**：将应结金额从商户待结算账户转移到商户可提现账户，生成结算凭证。
4. **商户发起提现**：商户提交提现申请，系统校验可提现余额、冻结提现金额、调用银行通道打款。
5. **银行到账回调**：银行返回打款结果，成功则扣减冻结余额完成提现，失败则解冻恢复余额。

#### 10.3.2 结算任务调度器

```java
/**
 * 结算任务调度器。
 * 设计要点：
 *  1. 结算周期配置化：不同商户可以有不同的结算周期（T+0 实时结算、T+1 日结、T+7 周结），
 *     周期规则存放在 settlement_cycle_config 表中；
 *  2. 分批扫描与分布式任务分片：商户量大时，使用分布式任务调度框架按 merchantId 哈希分片，
 *     多实例并行处理不同分片的商户；
 *  3. 每个结算任务有独立的任务 ID 和状态机（INIT -> CALCULATING -> BOOKING -> SETTLED -> FAILED），
 *     支持断点续跑，失败后可以从上次中断的步骤继续执行。
 */
@Component
public class SettlementScheduler {

    private static final Logger log = LoggerFactory.getLogger(SettlementScheduler.class);
    private static final int MERCHANT_BATCH_SIZE = 200;

    @Autowired private SettlementCycleConfigRepository cycleConfigRepository;
    @Autowired private MerchantRepository merchantRepository;
    @Autowired private SettlementTaskService settlementTaskService;
    @Autowired private AlertService alertService;

    /** T+1 日结商户，每日凌晨 2:00 触发 */
    @Scheduled(cron = "0 0 2 * * ?")
    public void triggerDailySettlement() {
        executeSettlement("T+1", DateUtils.addDays(new Date(), -1));
    }

    /** T+7 周结商户，每周一凌晨 3:00 触发 */
    @Scheduled(cron = "0 0 3 ? * MON")
    public void triggerWeeklySettlement() {
        executeSettlement("T+7", DateUtils.addDays(new Date(), -7));
    }

    private void executeSettlement(String cycleType, Date settlementDate) {
        String traceId = TraceContext.getTraceId();
        long startTime = System.currentTimeMillis();

        log.info("[结算调度] 开始执行, traceId={}, cycleType={}, settlementDate={}",
                traceId, cycleType, DateFormatUtils.format(settlementDate, "yyyy-MM-dd"));

        long lastMerchantId = 0;
        int totalMerchants = 0;
        int successCount = 0;
        int failCount = 0;

        while (true) {
            List<Long> merchantIds = merchantRepository.scanMerchantsByCycle(
                    cycleType, lastMerchantId, MERCHANT_BATCH_SIZE);
            if (merchantIds.isEmpty()) {
                break;
            }

            for (Long merchantId : merchantIds) {
                totalMerchants++;
                try {
                    settlementTaskService.settleForMerchant(merchantId, settlementDate, cycleType, traceId);
                    successCount++;
                } catch (Exception e) {
                    failCount++;
                    log.error("[结算调度] 单商户结算失败, traceId={}, merchantId={}, error={}",
                            traceId, merchantId, e.getMessage(), e);
                    // 单商户失败不影响其他商户，记录失败供后续补偿
                    settlementTaskService.markFailed(merchantId, settlementDate, e.getMessage());
                }
            }

            lastMerchantId = merchantIds.get(merchantIds.size() - 1);
        }

        long costMs = System.currentTimeMillis() - startTime;
        log.info("[结算调度] 执行完成, traceId={}, cycleType={}, totalMerchants={}, success={}, fail={}, costMs={}",
                traceId, cycleType, totalMerchants, successCount, failCount, costMs);

        if (failCount > 0) {
            alertService.sendWarning(String.format("结算调度存在失败商户: cycleType=%s, failCount=%d/%d",
                    cycleType, failCount, totalMerchants));
        }
    }
}
```

#### 10.3.3 结算任务服务：计算应结金额与结算记账

```java
/**
 * 结算任务服务：单商户结算的核心逻辑。
 * 一次结算包含两个关键步骤：
 *  1. 计算应结金额：汇总结算窗口内的交易流水，扣除退款和扣罚，得到净应结金额；
 *  2. 结算记账：通过记账引擎将应结金额从待结算账户转移到可提现账户。
 *
 * 幂等控制：每个结算任务有唯一的 settlementNo（格式：STL_{merchantId}_{yyyyMMdd}），
 * 作为记账引擎的 bizNo，天然具备幂等性。
 */
@Service
public class SettlementTaskService {

    private static final Logger log = LoggerFactory.getLogger(SettlementTaskService.class);

    @Autowired private FlowRepository flowRepository;
    @Autowired private RefundRepository refundRepository;
    @Autowired private PenaltyRepository penaltyRepository;
    @Autowired private AccountRepository accountRepository;
    @Autowired private AccountingEngine accountingEngine;
    @Autowired private SettlementTaskRepository taskRepository;
    @Autowired private FlowNoGenerator flowNoGenerator;

    @Transactional(rollbackFor = Exception.class)
    public void settleForMerchant(Long merchantId, Date settlementDate, String cycleType, String traceId) {
        String settlementNo = generateSettlementNo(merchantId, settlementDate);

        // 幂等检查：是否已经结算过
        SettlementTask existingTask = taskRepository.findBySettlementNo(settlementNo);
        if (existingTask != null && existingTask.getStatus() == SettlementStatus.SETTLED) {
            log.info("[商户结算] 幂等命中，已结算, traceId={}, merchantId={}, settlementNo={}",
                    traceId, merchantId, settlementNo);
            return;
        }

        log.info("[商户结算] 开始计算应结金额, traceId={}, merchantId={}, settlementNo={}",
                traceId, merchantId, settlementNo);

        // 第一步：计算应结金额
        Date windowStart = getSettlementWindowStart(settlementDate, cycleType);
        Date windowEnd = DateUtils.ceiling(settlementDate, Calendar.DATE);

        // 结算窗口内的交易入账总额
        long grossIncome = flowRepository.sumCreditByAccountAndDateRange(
                merchantId, AccountType.MERCHANT_SETTLEMENT, windowStart, windowEnd);

        // 结算窗口内的退款总额
        long totalRefund = refundRepository.sumRefundByMerchantAndDateRange(
                merchantId, windowStart, windowEnd);

        // 结算窗口内的平台扣罚总额（违规罚款、活动扣费等）
        long totalPenalty = penaltyRepository.sumPenaltyByMerchantAndDateRange(
                merchantId, windowStart, windowEnd);

        // 净应结金额 = 交易入账 - 退款 - 扣罚
        long netSettlementAmount = grossIncome - totalRefund - totalPenalty;

        log.info("[商户结算] 应结金额计算完成, traceId={}, merchantId={}, gross={}, refund={}, penalty={}, net={}",
                traceId, merchantId, grossIncome, totalRefund, totalPenalty, netSettlementAmount);

        if (netSettlementAmount <= 0) {
            log.info("[商户结算] 净应结金额为零或负数，跳过结算, traceId={}, merchantId={}, netAmount={}",
                    traceId, merchantId, netSettlementAmount);
            taskRepository.upsert(buildTask(settlementNo, merchantId, settlementDate,
                    netSettlementAmount, SettlementStatus.SKIPPED, "净应结金额非正数"));
            return;
        }

        // 第二步：结算记账——从待结算账户转到可提现账户
        Account settlementAccount = accountRepository.findBySubjectAndType(
                merchantId, AccountType.MERCHANT_SETTLEMENT);
        Account withdrawableAccount = accountRepository.findBySubjectAndType(
                merchantId, AccountType.USER_AVAILABLE); // 商户可提现账户

        if (settlementAccount == null || withdrawableAccount == null) {
            throw new AccountNotFoundException(
                    String.format("商户结算账户不存在, merchantId=%d, settlementNo=%s", merchantId, settlementNo));
        }

        // 校验待结算账户余额是否充足
        if (settlementAccount.getBalance().getAvailableAmount() < netSettlementAmount) {
            log.warn("[商户结算] 待结算账户余额不足, traceId={}, merchantId={}, available={}, need={}",
                    traceId, merchantId, settlementAccount.getBalance().getAvailableAmount(), netSettlementAmount);
            taskRepository.upsert(buildTask(settlementNo, merchantId, settlementDate,
                    netSettlementAmount, SettlementStatus.FAILED, "待结算账户余额不足"));
            return;
        }

        // 构建结算凭证
        AccountingVoucher voucher = new AccountingVoucher();
        voucher.setVoucherNo(flowNoGenerator.generateVoucherNo());
        voucher.setBizNo(settlementNo);
        voucher.setBizType("MERCHANT_SETTLEMENT");
        voucher.setOccurTime(new Date());

        // 借方：商户待结算账户减少（资金从待结算转出）
        voucher.addEntry(new AccountingEntry(
                settlementAccount.getAccountId(), EntryDirection.DEBIT, netSettlementAmount, "2001"));
        // 贷方：商户可提现账户增加（资金转入可提现）
        voucher.addEntry(new AccountingEntry(
                withdrawableAccount.getAccountId(), EntryDirection.CREDIT, netSettlementAmount, "1002"));

        voucher.validateBalance();

        // 提交记账引擎执行
        AccountingResult result = accountingEngine.post(voucher);

        if (result.isSuccess()) {
            log.info("[商户结算] 结算记账成功, traceId={}, merchantId={}, settlementNo={}, amount={}",
                    traceId, merchantId, settlementNo, netSettlementAmount);
            taskRepository.upsert(buildTask(settlementNo, merchantId, settlementDate,
                    netSettlementAmount, SettlementStatus.SETTLED, "结算成功"));
        } else {
            log.error("[商户结算] 结算记账失败, traceId={}, merchantId={}, settlementNo={}, reason={}",
                    traceId, merchantId, settlementNo, result.getMessage());
            taskRepository.upsert(buildTask(settlementNo, merchantId, settlementDate,
                    netSettlementAmount, SettlementStatus.FAILED, result.getMessage()));
            throw new SettlementException("结算记账失败: " + result.getMessage());
        }
    }

    public void markFailed(Long merchantId, Date settlementDate, String reason) {
        String settlementNo = generateSettlementNo(merchantId, settlementDate);
        taskRepository.upsert(buildTask(settlementNo, merchantId, settlementDate,
                0, SettlementStatus.FAILED, reason));
    }

    private String generateSettlementNo(Long merchantId, Date settlementDate) {
        return "STL_" + merchantId + "_" + DateFormatUtils.format(settlementDate, "yyyyMMdd");
    }

    private Date getSettlementWindowStart(Date settlementDate, String cycleType) {
        switch (cycleType) {
            case "T+1":
                return DateUtils.truncate(settlementDate, Calendar.DATE);
            case "T+7":
                return DateUtils.addDays(DateUtils.truncate(settlementDate, Calendar.DATE), -6);
            default:
                return DateUtils.truncate(settlementDate, Calendar.DATE);
        }
    }

    private SettlementTask buildTask(String settlementNo, Long merchantId, Date settlementDate,
                                     long amount, SettlementStatus status, String remark) {
        SettlementTask task = new SettlementTask();
        task.setSettlementNo(settlementNo);
        task.setMerchantId(merchantId);
        task.setSettlementDate(settlementDate);
        task.setNetAmount(amount);
        task.setStatus(status);
        task.setRemark(remark);
        task.setUpdateTime(new Date());
        return task;
    }
```

#### 10.3.4 商户提现服务

```java
/**
 * 商户提现服务：完整的提现全链路实现。
 * 提现流程分为三个阶段：
 *  1. 申请阶段：校验可提现余额，冻结提现金额，生成提现单；
 *  2. 打款阶段：调用银行通道发起转账，等待异步回调；
 *  3. 回调阶段：根据银行返回结果，成功则扣减冻结余额，失败则解冻恢复。
 *
 * 幂等控制：
 *  - 提现单号（withdrawNo）全局唯一，作为幂等键；
 *  - 银行通道调用以 withdrawNo 作为外部订单号，银行侧也做幂等；
 *  - 回调处理以 withdrawNo + 回调状态做幂等，防止银行重复回调。
 */
@Service
public class WithdrawService {

    private static final Logger log = LoggerFactory.getLogger(WithdrawService.class);

    @Autowired private AccountRepository accountRepository;
    @Autowired private WithdrawOrderRepository withdrawOrderRepository;
    @Autowired private AccountingEngine accountingEngine;
    @Autowired private BankChannelClient bankChannelClient;
    @Autowired private FlowNoGenerator flowNoGenerator;
    @Autowired private IdempotentService idempotentService;
    @Autowired private AlertService alertService;

    /** 提现申请金额上限（分），超过此金额需要人工审批 */
    private static final long AUTO_APPROVE_LIMIT = 50000_00L; // 5万元

    /**
     * 第一阶段：提现申请。
     * 校验余额 -> 冻结金额 -> 创建提现单 -> 小额自动打款 / 大额走审批。
     */
    @Transactional(rollbackFor = Exception.class)
    public WithdrawResult applyWithdraw(WithdrawRequest request) {
        String withdrawNo = flowNoGenerator.generateWithdrawNo();
        String traceId = TraceContext.getTraceId();

        log.info("[提现申请] 收到提现请求, traceId={}, merchantId={}, amount={}, bankCard={}",
                traceId, request.getMerchantId(), request.getAmount(), maskBankCard(request.getBankCardNo()));

        // 1. 参数校验
        validateWithdrawRequest(request);

        // 2. 查询商户可提现账户
        Account withdrawableAccount = accountRepository.findBySubjectAndType(
                request.getMerchantId(), AccountType.USER_AVAILABLE);
        if (withdrawableAccount == null) {
            throw new AccountNotFoundException("商户可提现账户不存在, merchantId=" + request.getMerchantId());
        }

        // 3. 校验可提现余额
        if (withdrawableAccount.getBalance().getAvailableAmount() < request.getAmount()) {
            log.warn("[提现申请] 可提现余额不足, traceId={}, merchantId={}, available={}, need={}",
                    traceId, request.getMerchantId(),
                    withdrawableAccount.getBalance().getAvailableAmount(), request.getAmount());
            return WithdrawResult.fail(withdrawNo, "可提现余额不足");
        }

        // 4. 冻结提现金额（从可用余额移动到冻结余额，总余额不变）
        Balance newBalance = withdrawableAccount.getBalance().freeze(request.getAmount());
        withdrawableAccount.setBalance(newBalance);
        accountRepository.updateBalanceWithVersion(withdrawableAccount);

        log.info("[提现申请] 冻结成功, traceId={}, merchantId={}, frozenAmount={}, remainAvailable={}",
                traceId, request.getMerchantId(), request.getAmount(), newBalance.getAvailableAmount());

        // 5. 创建提现单
        WithdrawOrder order = new WithdrawOrder();
        order.setWithdrawNo(withdrawNo);
        order.setMerchantId(request.getMerchantId());
        order.setAccountId(withdrawableAccount.getAccountId());
        order.setAmount(request.getAmount());
        order.setBankCardNo(request.getBankCardNo());
        order.setBankCode(request.getBankCode());
        order.setAccountName(request.getAccountName());
        order.setStatus(WithdrawStatus.FROZEN);
        order.setCreateTime(new Date());
        order.setUpdateTime(new Date());
        withdrawOrderRepository.insert(order);

        log.info("[提现申请] 提现单创建成功, traceId={}, withdrawNo={}, status={}",
                traceId, withdrawNo, order.getStatus());

        // 6. 金额在自动审批阈值内，直接发起打款；否则需要人工审批
        if (request.getAmount() <= AUTO_APPROVE_LIMIT) {
            try {
                submitToBankChannel(order, traceId);
            } catch (Exception e) {
                log.error("[提现申请] 自动打款提交失败，转为人工处理, traceId={}, withdrawNo={}",
                        traceId, withdrawNo, e);
                order.setStatus(WithdrawStatus.PENDING_MANUAL);
                withdrawOrderRepository.updateStatus(order);
            }
        } else {
            log.info("[提现申请] 金额超过自动审批阈值，需人工审批, traceId={}, withdrawNo={}, amount={}",
                    traceId, withdrawNo, request.getAmount());
            order.setStatus(WithdrawStatus.PENDING_APPROVAL);
            withdrawOrderRepository.updateStatus(order);
        }

        return WithdrawResult.success(withdrawNo, "提现申请已受理");
    }

    /**
     * 第二阶段：提交银行通道打款。
     * 以 withdrawNo 作为银行侧的外部订单号，银行通道会对同一外部订单号做幂等处理。
     */
    private void submitToBankChannel(WithdrawOrder order, String traceId) {
        log.info("[银行打款] 提交打款请求, traceId={}, withdrawNo={}, amount={}, bankCode={}",
                traceId, order.getWithdrawNo(), order.getAmount(), order.getBankCode());

        BankTransferRequest bankRequest = new BankTransferRequest();
        bankRequest.setOutTradeNo(order.getWithdrawNo());
        bankRequest.setAmount(order.getAmount());
        bankRequest.setBankCardNo(order.getBankCardNo());
        bankRequest.setBankCode(order.getBankCode());
        bankRequest.setAccountName(order.getAccountName());
        bankRequest.setRemark("商户提现");

        BankTransferResponse response = bankChannelClient.submitTransfer(bankRequest);

        if (response.isAccepted()) {
            order.setStatus(WithdrawStatus.BANK_PROCESSING);
            order.setBankOrderNo(response.getBankOrderNo());
            order.setUpdateTime(new Date());
            withdrawOrderRepository.updateStatus(order);

            log.info("[银行打款] 银行受理成功, traceId={}, withdrawNo={}, bankOrderNo={}",
                    traceId, order.getWithdrawNo(), response.getBankOrderNo());
        } else {
            log.error("[银行打款] 银行拒绝受理, traceId={}, withdrawNo={}, rejectReason={}",
                    traceId, order.getWithdrawNo(), response.getRejectReason());
            throw new BankRejectException("银行拒绝受理: " + response.getRejectReason());
        }
    }

    /**
     * 第三阶段：银行回调处理。
     * 银行异步通知打款结果，本方法处理成功和失败两种情况。
     * 幂等控制：以 withdrawNo + 当前状态做幂等判断，已处于终态的提现单不再重复处理。
     */
    @Transactional(rollbackFor = Exception.class)
    public void handleBankCallback(BankCallbackMessage callback) {
        String traceId = TraceContext.getTraceId();

        log.info("[银行回调] 收到回调, traceId={}, withdrawNo={}, bankResult={}, bankOrderNo={}",
                traceId, callback.getOutTradeNo(), callback.getResult(), callback.getBankOrderNo());

        // 查找提现单
        WithdrawOrder order = withdrawOrderRepository.findByWithdrawNo(callback.getOutTradeNo());
        if (order == null) {
            log.error("[银行回调] 提现单不存在, traceId={}, withdrawNo={}", traceId, callback.getOutTradeNo());
            throw new OrderNotFoundException("提现单不存在: " + callback.getOutTradeNo());
        }

        // 幂等检查：已处于终态则跳过
        if (order.getStatus() == WithdrawStatus.SUCCESS || order.getStatus() == WithdrawStatus.REFUNDED) {
            log.info("[银行回调] 提现单已处于终态，跳过, traceId={}, withdrawNo={}, status={}",
                    traceId, order.getWithdrawNo(), order.getStatus());
            return;
        }

        Account account = accountRepository.selectForUpdate(order.getAccountId());

        if ("SUCCESS".equals(callback.getResult())) {
            // 打款成功：扣减冻结余额（资金已经离开平台，到达商户银行卡）
            Balance newBalance = account.getBalance().deductFrozen(order.getAmount());
            account.setBalance(newBalance);
            accountRepository.updateBalanceWithVersion(account);

            // 生成提现成功的记账凭证（借方：商户可提现账户减少，贷方：银行存管账户减少）
            AccountingVoucher voucher = new AccountingVoucher();
            voucher.setVoucherNo(flowNoGenerator.generateVoucherNo());
            voucher.setBizNo("WD_" + order.getWithdrawNo());
            voucher.setBizType("MERCHANT_WITHDRAW");
            voucher.setOccurTime(new Date());
            voucher.addEntry(new AccountingEntry(
                    order.getAccountId(), EntryDirection.DEBIT, order.getAmount(), "1002"));
            voucher.addEntry(new AccountingEntry(
                    SystemAccountConstants.BANK_CUSTODY_ACCOUNT, EntryDirection.CREDIT, order.getAmount(), "1001"));
            voucher.validateBalance();
            accountingEngine.post(voucher);

            order.setStatus(WithdrawStatus.SUCCESS);
            order.setBankFinishTime(callback.getFinishTime());
            order.setUpdateTime(new Date());
            withdrawOrderRepository.updateStatus(order);

            log.info("[银行回调] 提现成功, traceId={}, withdrawNo={}, amount={}, merchantId={}",
                    traceId, order.getWithdrawNo(), order.getAmount(), order.getMerchantId());

        } else if ("FAIL".equals(callback.getResult())) {
            // 打款失败：解冻恢复余额（资金未离开平台，恢复商户可用余额）
            Balance newBalance = account.getBalance().unfreeze(order.getAmount());
            account.setBalance(newBalance);
            accountRepository.updateBalanceWithVersion(account);

            order.setStatus(WithdrawStatus.REFUNDED);
            order.setFailReason(callback.getFailReason());
            order.setUpdateTime(new Date());
            withdrawOrderRepository.updateStatus(order);

            log.warn("[银行回调] 提现失败已解冻, traceId={}, withdrawNo={}, amount={}, reason={}",
                    traceId, order.getWithdrawNo(), order.getAmount(), callback.getFailReason());

            // 通知商户提现失败
            alertService.sendWarning(String.format("商户提现失败: merchantId=%d, withdrawNo=%s, amount=%d, reason=%s",
                    order.getMerchantId(), order.getWithdrawNo(), order.getAmount(), callback.getFailReason()));

        } else {
            log.warn("[银行回调] 未知回调结果, traceId={}, withdrawNo={}, result={}",
                    traceId, order.getWithdrawNo(), callback.getResult());
        }
    }

    private void validateWithdrawRequest(WithdrawRequest request) {
        if (request.getMerchantId() == null) {
            throw new IllegalArgumentException("商户ID不能为空");
        }
        if (request.getAmount() <= 0) {
            throw new IllegalArgumentException("提现金额必须为正数: " + request.getAmount());
        }
        if (request.getBankCardNo() == null || request.getBankCardNo().isEmpty()) {
            throw new IllegalArgumentException("银行卡号不能为空");
        }
        if (request.getAmount() < 100) {
            throw new IllegalArgumentException("最低提现金额为 1 元（100分）");
        }
    }

    /** 银行卡号脱敏：保留前6后4，中间用星号代替 */
    private String maskBankCard(String cardNo) {
        if (cardNo == null || cardNo.length() < 10) return "****";
        return cardNo.substring(0, 6) + "****" + cardNo.substring(cardNo.length() - 4);
    }
}
```

#### 10.3.5 提现超时补偿服务

```java
/**
 * 提现超时补偿服务。
 * 银行通道可能因为各种原因未能及时回调（网络故障、银行系统延迟等），
 * 导致提现单长时间停留在 BANK_PROCESSING 状态。补偿服务定期扫描超时订单，
 * 主动查询银行通道获取最新状态，避免资金长期冻结。
 */
@Component
public class WithdrawTimeoutCompensator {

    private static final Logger log = LoggerFactory.getLogger(WithdrawTimeoutCompensator.class);

    /** 超过 30 分钟未收到银行回调视为超时 */
    private static final long TIMEOUT_MS = 30 * 60 * 1000;

    @Autowired private WithdrawOrderRepository withdrawOrderRepository;
    @Autowired private BankChannelClient bankChannelClient;
    @Autowired private WithdrawService withdrawService;
    @Autowired private AlertService alertService;

    @Scheduled(cron = "0 */5 * * * ?") // 每5分钟扫描一次
    public void compensate() {
        Date timeoutBefore = new Date(System.currentTimeMillis() - TIMEOUT_MS);
        List<WithdrawOrder> timeoutOrders = withdrawOrderRepository.findByStatusAndUpdateTimeBefore(
                WithdrawStatus.BANK_PROCESSING, timeoutBefore);

        if (timeoutOrders.isEmpty()) {
            return;
        }

        log.info("[提现补偿] 发现超时提现单, count={}", timeoutOrders.size());

        for (WithdrawOrder order : timeoutOrders) {
            try {
                // 主动查询银行通道获取最新状态
                BankQueryResponse bankResult = bankChannelClient.queryTransfer(order.getWithdrawNo());

                if ("SUCCESS".equals(bankResult.getStatus())) {
                    BankCallbackMessage fakeCallback = new BankCallbackMessage();
                    fakeCallback.setOutTradeNo(order.getWithdrawNo());
                    fakeCallback.setResult("SUCCESS");
                    fakeCallback.setBankOrderNo(bankResult.getBankOrderNo());
                    fakeCallback.setFinishTime(bankResult.getFinishTime());
                    withdrawService.handleBankCallback(fakeCallback);

                    log.info("[提现补偿] 补偿成功（银行已打款）, withdrawNo={}", order.getWithdrawNo());

                } else if ("FAIL".equals(bankResult.getStatus())) {
                    BankCallbackMessage fakeCallback = new BankCallbackMessage();
                    fakeCallback.setOutTradeNo(order.getWithdrawNo());
                    fakeCallback.setResult("FAIL");
                    fakeCallback.setFailReason(bankResult.getFailReason());
                    withdrawService.handleBankCallback(fakeCallback);

                    log.info("[提现补偿] 补偿完成（银行打款失败，已解冻）, withdrawNo={}", order.getWithdrawNo());

                } else {
                    // 银行仍在处理中，继续等待
                    log.info("[提现补偿] 银行仍在处理中, withdrawNo={}, bankStatus={}",
                            order.getWithdrawNo(), bankResult.getStatus());

                    // 超过 2 小时仍未有结果，升级告警
                    long pendingMs = System.currentTimeMillis() - order.getUpdateTime().getTime();
                    if (pendingMs > 2 * 3600 * 1000) {
                        alertService.sendCritical(String.format(
                                "提现单长时间未完成: withdrawNo=%s, merchantId=%d, amount=%d, pendingMinutes=%d",
                                order.getWithdrawNo(), order.getMerchantId(), order.getAmount(), pendingMs / 60000));
                    }
                }

            } catch (Exception e) {
                log.error("[提现补偿] 补偿异常, withdrawNo={}", order.getWithdrawNo(), e);
            }
        }
    }
}
```
