# KMS 与登录认证系统、权限系统的融合架构

本文聚焦于三大安全基础设施——KMS（密钥管理系统）、登录认证系统（SSO）、权限系统——之间的协作关系。通过通俗的讲解和多个完整的实例，说明它们是如何在实际业务中串联运作的。

---

## 一、三大系统的定位与关系

### 1.1 各系统职责

在企业安全体系中，这三个系统各自解决一个核心问题：

```
  ┌──────────────────────────────────────────────────────────────┐
  │                   企业安全铁三角                               │
  │                                                              │
  │   ┌──────────────────┐                                       │
  │   │  登录认证系统      │  解决的问题：你是谁？                   │
  │   │  (SSO / CAS)      │  核心能力：                             │
  │   │                  │  · 用户身份验证（账号密码/短信/人脸）     │
  │   │                  │  · 单点登录（一次登录，多处使用）         │
  │   │                  │  · Token 签发与管理                     │
  │   │                  │  · 多因子认证（MFA）                    │
  │   └────────┬─────────┘                                       │
  │            │                                                  │
  │            │ 认证通过后，携带身份凭证                            │
  │            ▼                                                  │
  │   ┌──────────────────┐                                       │
  │   │  权限系统          │  解决的问题：你能做什么？                │
  │   │  (RBAC / ABAC)    │  核心能力：                             │
  │   │                  │  · 功能权限（能访问哪些菜单/按钮/API）   │
  │   │                  │  · 数据权限（能看到哪些范围的数据）       │
  │   │                  │  · 角色管理（用户-角色-权限 映射）        │
  │   │                  │  · 权限缓存与高效校验                   │
  │   └────────┬─────────┘                                       │
  │            │                                                  │
  │            │ 鉴权通过后，执行业务操作                            │
  │            ▼                                                  │
  │   ┌──────────────────┐                                       │
  │   │  KMS 密钥管理系统  │  解决的问题：数据如何安全保护？           │
  │   │                  │  核心能力：                             │
  │   │                  │  · 密钥/密码的安全存储                  │
  │   │                  │  · 数据加密/解密服务                    │
  │   │                  │  · 密钥生命周期管理                     │
  │   │                  │  · 访问控制与审计                       │
  │   └──────────────────┘                                       │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
```

## 二、SSO 认证系统如何依赖 KMS

### 2.1 clientSecret 的安全存储

每个接入 SSO 的业务系统都有一对 clientId + clientSecret，其中 clientSecret 是机密信息，必须安全存储。

```
  传统方式（不安全）：
  
  业务系统的配置文件：
  sso:
    client-id: order-service
    client-secret: a3f8b2c1d4e5f6g7h8i9j0  ← 明文！
  
  问题：
  · 配置文件提交到代码仓库，所有开发者都能看到
  · 配置中心被攻破，所有 clientSecret 泄露
  · clientSecret 泄露后，攻击者可以冒充该业务系统
  
  
  使用 KMS 后（安全）：
  
  业务系统的配置文件：
  sso:
    client-id: order-service
    client-secret: $KMS{sso_client_secret_order_prod}
                    ↑ KMS 占位符
  
  启动流程：
  ┌──────────┐      ┌──────────┐      ┌──────────┐
  │ 业务系统  │      │KMS Agent │      │KMS Server│
  └────┬─────┘      └────┬─────┘      └────┬─────┘
       │                 │                  │
       │ 1. 解析配置      │                  │
       │ 发现 $KMS{...}  │                  │
       │                 │                  │
       │ 2. 请求密钥      │                  │
       │────────────────▶│                  │
       │                 │ 3. 获取密钥       │
       │                 │─────────────────▶│
       │                 │                  │
       │                 │ 4. 返回明文       │
       │                 │◀─────────────────│
       │ 5. 返回明文      │                  │
       │◀────────────────│                  │
       │                 │                  │
       │ 6. 替换占位符    │                  │
       │ sso.client-secret                  │
       │ = "a3f8b2c1d4e5f6g7h8i9j0"        │
       │ (仅存在于内存中)                     │
       │                 │                  │
       │ 7. 用 clientSecret                 │
       │ 完成 OAuth2 认证流程                │
```

### 2.2 JWT 签名密钥的托管

SSO 系统使用 JWT 作为 Token 格式时，签名密钥的安全性至关重要。

```
  JWT 的签名流程：
  
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  SSO 签发 Token：                                         │
  │                                                          │
  │  1. 用户登录成功后，SSO 需要签发 JWT                        │
  │                                                          │
  │  2. SSO 从 KMS 获取 JWT 签名密钥                           │
  │     jwt_signing_key = KMS.get("sso_jwt_key_prod")        │
  │                                                          │
  │  3. 构造 JWT Payload                                     │
  │     {                                                    │
  │       "sub": "zhangsan",                                 │
  │       "client_id": "order-service",                      │
  │       "roles": ["admin", "user"],                        │
  │       "exp": 1705420800,                                 │
  │       "iat": 1705334400                                  │
  │     }                                                    │
  │                                                          │
  │  4. 用 KMS 托管的密钥签名                                  │
  │     signature = HMAC-SHA256(jwt_signing_key, payload)     │
  │                                                          │
  │  5. 返回 JWT = header.payload.signature                   │
  │                                                          │
  │                                                          │
  │  业务系统验证 Token：                                       │
  │                                                          │
  │  1. 收到请求中的 JWT                                       │
  │                                                          │
  │  2. 从 KMS 获取同一个签名密钥                               │
  │     jwt_signing_key = KMS.get("sso_jwt_key_prod")        │
  │                                                          │
  │  3. 重新计算签名并对比                                      │
  │     expected = HMAC-SHA256(jwt_signing_key, payload)      │
  │     actual = jwt.signature                                │
  │                                                          │
  │  4. 签名一致 → Token 未被篡改，身份有效                     │
  │     签名不一致 → 拒绝请求                                   │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
  
  KMS 在其中的价值：
  · JWT 签名密钥不在代码或配置中出现
  · 多个业务系统共用同一个签名密钥进行验证
  · 密钥轮换时只需在 KMS 中更新，所有系统自动获取新密钥
  · 完整的密钥访问审计日志
```

### 2.3 MTLS 证书体系与 KMS 的关联

在服务间通信中，MTLS（双向 TLS）是比 AKSK 更安全的身份认证方式。KMS 与 MTLS 证书体系紧密配合。

```
  MTLS 证书体系中 KMS 的角色：
  
  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │                    CA（证书颁发机构）                          │
  │                    ┌─────────────┐                            │
  │                    │  CA 根证书   │                            │
  │                    │  私钥由 HSM  │ ← KMS 的 HSM 保管 CA 私钥  │
  │                    │  安全保管    │                            │
  │                    └──────┬──────┘                            │
  │                           │ 签发                              │
  │              ┌────────────┼────────────┐                     │
  │              ▼            ▼            ▼                     │
  │        ┌──────────┐ ┌──────────┐ ┌──────────┐               │
  │        │ 服务 A    │ │ 服务 B    │ │ KMS      │               │
  │        │ 证书      │ │ 证书      │ │ Server   │               │
  │        │          │ │          │ │ 证书      │               │
  │        └──────────┘ └──────────┘ └──────────┘               │
  │                                                              │
  │  证书签发流程：                                                │
  │  1. 服务启动时生成密钥对（公钥+私钥）                           │
  │  2. 用公钥创建 CSR（证书签名请求）                              │
  │  3. CSR 发送给 CA                                             │
  │  4. CA 用 HSM 中的根私钥签名 → 生成证书                        │
  │  5. 证书下发到服务                                             │
  │                                                              │
  │  KMS 在其中的作用：                                            │
  │  · CA 的根私钥保管在 KMS 的 HSM 中（最高安全级别）              │
  │  · 服务的私钥可以通过 KMS 托管（可选）                          │
  │  · 证书的吊销列表（CRL）可以通过 KMS 管理                      │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
```

## 三、权限系统如何依赖 KMS

### 3.1 权限系统的数据库密码托管

权限系统作为安全基础设施，自身的数据库密码同样需要安全管理。

```
  权限系统的数据库连接：
  
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  权限系统的配置：                                           │
  │  spring:                                                  │
  │    datasource:                                            │
  │      url: jdbc:mysql://perm-db:3306/permission            │
  │      username: perm_admin                                  │
  │      password: $KMS{perm_db_password_prod}                │
  │                                                          │
  │  启动时：                                                  │
  │  1. 权限系统从 KMS 获取数据库密码                            │
  │  2. 用明文密码连接数据库                                    │
  │  3. 加载 RBAC 模型数据（用户、角色、权限）                   │
  │  4. 构建权限缓存                                           │
  │                                                          │
  │  为什么权限系统自己也需要 KMS：                              │
  │  · 权限数据库包含所有用户的权限信息（高度敏感）               │
  │  · 如果权限数据库密码泄露，攻击者可以修改任何人的权限          │
  │  · 权限系统是安全基础设施的核心，必须自身也足够安全            │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

### 3.2 API 鉴权密钥的安全管理

权限系统对外提供鉴权 API，API 本身也需要防止被未授权调用。

```
  权限系统的 API 鉴权：
  
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  业务系统调用权限系统 API 的流程：                            │
  │                                                          │
  │  ┌──────────┐              ┌──────────────┐              │
  │  │ 业务系统  │              │  权限系统      │              │
  │  └────┬─────┘              └──────┬───────┘              │
  │       │                           │                       │
  │       │  1. 调用鉴权 API           │                       │
  │       │  POST /api/v1/auth/check  │                       │
  │       │  Authorization: Bearer xxx │                       │
  │       │  X-Sign: HMAC(secret, body)│                       │
  │       │──────────────────────────▶│                       │
  │       │                           │                       │
  │       │                           │  2. 验证调用方身份      │
  │       │                           │  · 验证 Bearer Token  │
  │       │                           │  · 验证 HMAC 签名     │
  │       │                           │                       │
  │       │  3. 返回鉴权结果           │                       │
  │       │  { "allowed": true }      │                       │
  │       │◀──────────────────────────│                       │
  │                                                          │
  │  其中 HMAC 签名的密钥 (secret) 由 KMS 托管：                │
  │  · 业务系统从 KMS 获取 secret 用于签名                      │
  │  · 权限系统从 KMS 获取同一个 secret 用于验签                 │
  │  · 密钥在 KMS 中统一管理，定期轮换                           │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

## 四、KMS 自身如何依赖认证系统和权限系统

KMS 不仅被认证系统和权限系统依赖，KMS 自身也需要认证和权限控制。

### 4.1 KMS 的访问认证

```
  KMS 如何确认"谁在访问我的密钥"：
  
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  认证方式一：MTLS 证书认证（服务间调用）                     │
  │  ┌──────────────────────────────────────────┐             │
  │  │  业务系统带着自己的 MTLS 证书访问 KMS        │             │
  │  │  KMS 从证书中提取身份信息（AppKey / 服务名）  │             │
  │  │  无需额外的账号密码                          │             │
  │  │                                          │             │
  │  │  适用：服务器端自动化访问                     │             │
  │  └──────────────────────────────────────────┘             │
  │                                                          │
  │  认证方式二：STS 票据认证（用户级别访问）                    │
  │  ┌──────────────────────────────────────────┐             │
  │  │  用户先通过 SSO 登录获取 accessToken         │             │
  │  │  用 accessToken 换取 STS 短期票据            │             │
  │  │  携带 STS 票据访问 KMS                       │             │
  │  │                                          │             │
  │  │  适用：Web 控制台操作密钥管理                 │             │
  │  └──────────────────────────────────────────┘             │
  │                                                          │
  │  认证方式三：AppKey + IP 反查（兼容旧系统）                 │
  │  ┌──────────────────────────────────────────┐             │
  │  │  根据请求来源 IP 反查所属的 AppKey            │             │
  │  │  通过 AppKey 确定调用方身份                   │             │
  │  │                                          │             │
  │  │  适用：不支持 MTLS 的旧系统                   │             │
  │  └──────────────────────────────────────────┘             │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

### 4.2 KMS 的权限控制

```
  KMS 内部的权限模型：
  
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  KMS 的权限控制融合了认证系统和权限系统的理念：                │
  │                                                          │
  │  层级一：应用级别                                           │
  │  ┌──────────────────────────────────────────┐             │
  │  │  某个 AppKey 能访问哪些密钥组               │             │
  │  │  类似 RBAC 的"角色-权限"映射                │             │
  │  │                                          │             │
  │  │  例如：                                    │             │
  │  │  AppKey: order-service                    │             │
  │  │  可访问密钥组：order_*                      │             │
  │  │  权限：读取 + 加密 + 解密                   │             │
  │  └──────────────────────────────────────────┘             │
  │                                                          │
  │  层级二：密钥级别                                           │
  │  ┌──────────────────────────────────────────┐             │
  │  │  每个密钥独立配置哪些 AppKey 可以访问        │             │
  │  │  类似 ACL（访问控制列表）                    │             │
  │  │                                          │             │
  │  │  例如：                                    │             │
  │  │  密钥 "user_phone_key":                   │             │
  │  │    order-service: 加密+解密                │             │
  │  │    analytics-service: 仅解密              │             │
  │  │    admin-service: 全部权限                 │             │
  │  └──────────────────────────────────────────┘             │
  │                                                          │
  │  层级三：操作级别                                           │
  │  ┌──────────────────────────────────────────┐             │
  │  │  细分到具体操作的权限控制                     │             │
  │  │  · 读取密钥值（getSecret）                  │             │
  │  │  · 加密数据（encrypt）                      │             │
  │  │  · 解密数据（decrypt）                      │             │
  │  │  · 管理密钥（create/update/delete）         │             │
  │  └──────────────────────────────────────────┘             │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

## 五、完整实例解析

### 实例一：用户登录到看到数据的全链路

这个实例展示了一个用户从输入密码到最终看到业务数据的完整流程，涉及认证系统、权限系统、KMS 三个系统的协作。

```
  场景：用户张三登录订单管理系统，查看自己部门的订单列表
  
  参与系统：
  · SSO 认证中心
  · 权限系统
  · KMS 密钥管理系统
  · 订单管理系统（业务系统）
  
  
  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │  张三     │   │订单管理   │   │  SSO     │   │ 权限系统  │   │  KMS     │
  │ (浏览器)  │   │系统      │   │ 认证中心 │   │          │   │          │
  └────┬─────┘   └────┬─────┘   └────┬─────┘   └────┬─────┘   └────┬─────┘
       │              │              │              │              │
  ═══════════════ 阶段一：用户登录认证 ══════════════════════════════
       │              │              │              │              │
       │ 1. 访问订单管理│              │              │              │
       │    系统首页    │              │              │              │
       │─────────────▶│              │              │              │
       │              │              │              │              │
```

```
  │                                                          │
  │  1. 王五已登录（JWT 中包含 user_id = 789）               │
  │                                                          │

  │                                                          │

  协同工作的关键点：
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  权限系统负责"谁能看到哪些行"（行级别过滤）                  │
  │  → 通过 SQL WHERE 条件控制                                 │
  │  → 李四只能看到 dept_id=100 的数据                         │
  │                                                          │
  │  KMS 负责"数据列的加密保护"（列级别保护）                    │
  │  → 手机号加密存储，即使数据库泄露也不怕                      │
  │  → 只有有 KMS 解密权限的服务才能看到明文                     │
  │                                                          │
  │  两者结合的效果：                                           │
  │  · 行级别：不同角色看到不同范围的数据                        │
  │  · 列级别：敏感字段加密保护，防止数据库泄露                   │
  │  · 双重保障：即使权限系统有漏洞，加密数据仍然安全              │
  │             即使 DBA 有数据库访问权限，没有 KMS 解密权限      │
  │             也无法读取敏感字段的明文                         │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

### 6.3 故障隔离策略

```
  当某个系统故障时的影响和应对：

  ┌──────────────────────────────────────────────────────────┐
  │  影响：                                                    │
  │  · 用户无法登录任何系统（包括 KMS 控制台）                   │
  │  · 已登录的用户在 Token 有效期内不受影响                     │
  │  · KMS 的服务端鉴权（MTLS / AppKey）不受影响               │
  │                                                          │
  │  应对：                                                    │
  │  · KMS Agent 缓存的密钥继续工作                             │
  │  · 业务系统的加解密不受影响                                  │
  │  · 暂时无法通过 Web 管理密钥                                │
  └──────────────────────────────────────────────────────────┘
  
  场景二：权限系统故障
  ┌──────────────────────────────────────────────────────────┐
  │  影响：                                                    │
  │  · 无法进行细粒度的权限校验                                  │
  │  · 数据范围过滤可能失效                                     │
  │                                                          │
  │  应对：                                                    │
  │  · 权限缓存（二级缓存）在一段时间内仍可用                    │
  │  · KMS 内置的 AppKey 级鉴权仍然工作                         │
  │  · 降级策略：使用最小权限原则，默认拒绝                      │
  └──────────────────────────────────────────────────────────┘
  
  场景三：KMS 故障
  ┌──────────────────────────────────────────────────────────┐
  │  影响：                                                    │
  │  · 新的密钥操作不可用                                       │
  │  · 已缓存的密钥继续工作（Agent 缓存）                       │
  │  · SSO 的 JWT 签名密钥已缓存，短期内不受影响                │
  │                                                          │
  │  应对：                                                    │
  │  · Agent P2P 共享保障新机器获取密钥                         │
  │  · 紧急情况使用灾备 KMS 集群                                │
  └──────────────────────────────────────────────────────────┘
```

## 八、全链路实战案例

前面的章节讲解了 SSO、权限系统、KMS 三者的协作原理，本章给出两个可以直接落地参考的完整实战案例：JWT Token 的签发与验证如何依托 KMS 管理签名密钥，以及服务间 API 调用如何基于 KMS 托管的密钥实现签名认证和防重放攻击。两个案例均包含完整的 Java 实现、异常处理、日志记录与幂等控制。

### 8.1 案例一：JWT Token 签发与验证全链路

#### 8.1.1 场景描述

SSO 认证中心使用 KMS 托管的密钥对 JWT 进行签名，业务系统使用同一把（或对应的公钥）密钥验证 JWT 合法性。这条链路里最容易被忽视、但生产环境中最常出问题的环节是：**密钥轮换如何不影响正在使用旧密钥签发的、尚未过期的 Token 的验证**。

```
  JWT 签发与验证全链路（含密钥轮换兼容）：

  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  用户     │    │  SSO     │    │   KMS    │    │ 业务系统  │
  │ (浏览器)  │    │ 认证中心  │    │          │    │ (校验方)  │
  └────┬─────┘    └────┬─────┘    └────┬─────┘    └────┬─────┘
       │               │               │               │
  ═══════════════ 阶段一：签发 JWT ═══════════════════════════
       │ 1. 提交账号密码│               │               │
       │──────────────▶│               │               │
       │               │ 2. 校验密码通过│               │
       │               │               │               │
       │               │ 3. 请求当前   │               │
       │               │ 活跃签名密钥  │               │
       │               │──────────────▶│               │
       │               │               │ 4. 返回当前   │
       │               │               │ 密钥 kid=v3   │
       │               │◀──────────────│               │
       │               │               │               │
       │               │ 5. 构造 JWT   │               │
       │               │ header: {     │               │
       │               │   alg: HS256, │               │
       │               │   kid: "v3"   │ ← 记录密钥版本  │
       │               │ }             │               │
       │               │ payload: {    │               │
       │               │   sub: userId,│               │
       │               │   iat, exp,   │               │
       │               │   jti: uuid   │ ← 唯一标识,支持黑名单│
       │               │ }             │               │
       │               │               │               │
       │               │ 6. 用 v3 密钥 │               │
       │               │ 计算签名       │               │
       │               │               │               │
       │ 7. 返回 JWT    │               │               │
       │◀──────────────│               │               │
       │               │               │               │
  ═══════════════ 阶段二：携带 JWT 访问业务系统 ═══════════════
       │ 8. 携带 JWT   │               │               │
       │ 访问业务接口   │               │               │
       │─────────────────────────────────────────────▶│
       │               │               │ 9. 解析 JWT   │
       │               │               │ header，取出  │
       │               │               │ kid="v3"      │
       │               │               │               │
       │               │               │ 10. 按 kid    │
       │               │               │ 向 KMS 请求   │
       │               │               │ 对应版本密钥   │
       │               │               │◀──────────────│
       │               │               │ 11. 返回 v3   │
       │               │               │ 密钥(可能是   │
       │               │               │ DECRYPT_ONLY  │
       │               │               │ 状态，仍可验签)│
       │               │               │──────────────▶│
       │               │               │               │
       │               │               │ 12. 用 v3     │
       │               │               │ 密钥验证签名   │
       │               │               │ → 通过 ✅      │
       │               │               │               │
       │               │               │ 13. 校验 exp   │
       │               │               │ 未过期 ✅      │
       │               │               │               │
       │               │               │ 14. 校验 jti   │
       │               │               │ 未在黑名单中 ✅ │
       │               │               │               │
       │ 15. 返回业务   │               │               │
       │ 数据          │               │               │
       │◀─────────────────────────────────────────────│
  ═══════════════ 阶段三：密钥轮换期间的兼容 ═══════════════════
       │               │ 密钥轮换：v3 → v4              │
       │               │ v3 状态变为 DECRYPT_ONLY        │
       │               │ v4 成为 ACTIVE                 │
       │               │               │               │
```

关键设计点：JWT 的 header 中携带 `kid`（Key ID，标识签名所用的密钥版本），验证方据此精确查找对应版本的密钥，而不是只用"当前最新密钥"去验证——这正是密钥轮换能够对业务无感知的核心机制。

#### 8.1.2 完整 Java 实现

```java
/**
 * JWT 签发服务：使用 KMS 托管的密钥对 Token 签名
 *
 * 幂等设计：签发接口本身不是幂等操作（每次登录都应产生新的 Token 和新的 jti），
 * 但通过 jti（JWT ID）唯一标识每一个 Token，配合黑名单机制支持"撤销"操作的幂等——
 * 重复撤销同一个 jti 不会产生副作用。
 */
@Service
public class JwtTokenService {

    private static final Logger log = LoggerFactory.getLogger(JwtTokenService.class);

    private static final String ALGORITHM = "HmacSHA256";
    private static final Duration TOKEN_TTL = Duration.ofHours(2);

    private final KmsKeyGateway kmsKeyGateway;
    private final TokenBlacklistRepository blacklistRepository;
    private final AuditLogger auditLogger;

    public JwtTokenService(KmsKeyGateway kmsKeyGateway,
                            TokenBlacklistRepository blacklistRepository,
                            AuditLogger auditLogger) {
        this.kmsKeyGateway = kmsKeyGateway;
        this.blacklistRepository = blacklistRepository;
        this.auditLogger = auditLogger;
    }

    /**
     * 签发 JWT
     *
     * @param userId 用户标识
     * @param extraClaims 附加声明，例如角色、部门等
     * @return 签发好的 JWT 字符串
     */
    public String issueToken(String userId, Map<String, Object> extraClaims) {
        try {
            // 1. 从 KMS 获取当前活跃的签名密钥（连同其版本标识 kid）
            KmsKeyVersion signingKey = kmsKeyGateway.getActiveSigningKey("sso_jwt_signing_key");
            if (signingKey == null) {
                throw new SigningKeyUnavailableException("无法获取有效的 JWT 签名密钥");
            }

            String jti = UUID.randomUUID().toString();
            Instant now = Instant.now();
            Instant exp = now.plus(TOKEN_TTL);

            // 2. 构造 header，写入 kid，供验证方精确定位密钥版本
            Map<String, Object> header = new LinkedHashMap<>();
            header.put("alg", "HS256");
            header.put("typ", "JWT");
            header.put("kid", signingKey.getKeyId());

            // 3. 构造 payload
            Map<String, Object> payload = new LinkedHashMap<>();
            payload.put("sub", userId);
            payload.put("iat", now.getEpochSecond());
            payload.put("exp", exp.getEpochSecond());
            payload.put("jti", jti);
            if (extraClaims != null) {
                payload.putAll(extraClaims);
            }

            String headerB64 = base64UrlEncode(JsonUtil.toJson(header));
            String payloadB64 = base64UrlEncode(JsonUtil.toJson(payload));
            String signingInput = headerB64 + "." + payloadB64;

            // 4. 用 KMS 返回的密钥明文计算 HMAC 签名
            //    （生产环境中签名计算也可以下沉到 KMS Server/HSM 内部完成，
            //     密钥明文完全不出 KMS 边界，此处为便于讲解在本地演示计算过程）
            String signature = computeHmacSignature(signingInput, signingKey.getKeyMaterial());

            String jwt = signingInput + "." + signature;

            log.info("JWT 签发成功: userId={}, jti={}, kid={}, expireAt={}",
                     userId, jti, signingKey.getKeyId(), exp);

            auditLogger.log(AuditEvent.builder()
                .action("JWT_ISSUE")
                .keyName("sso_jwt_signing_key")
                .operatorUser(userId)
                .success(true)
                .build());

            return jwt;
        } catch (SigningKeyUnavailableException e) {
            log.error("JWT 签发失败：签名密钥不可用: userId={}", userId, e);
            throw e;
        } catch (Exception e) {
            log.error("JWT 签发发生未预期异常: userId={}", userId, e);
            throw new TokenIssueException("JWT 签发失败", e);
        }
    }

    /**
     * 验证 JWT 合法性并解析出 Claims
     *
     * 校验顺序（每一步失败都要有明确的异常类型和日志，便于问题定位）：
     * 1. 格式合法性 2. 签名正确性 3. 是否过期 4. 是否在黑名单中
     */
    public JwtClaims verifyToken(String jwt) {
        try {
            String[] parts = jwt.split("\\.");
            if (parts.length != 3) {
                throw new InvalidTokenException("Token 格式非法：段数不正确");
            }

            String headerB64 = parts[0];
            String payloadB64 = parts[1];
            String signature = parts[2];
            String signingInput = headerB64 + "." + payloadB64;

            Map<String, Object> header = JsonUtil.fromJson(base64UrlDecode(headerB64), Map.class);
            Map<String, Object> payload = JsonUtil.fromJson(base64UrlDecode(payloadB64), Map.class);

            String kid = (String) header.get("kid");
            if (kid == null || kid.isEmpty()) {
                throw new InvalidTokenException("Token header 缺少 kid 字段");
            }

            // 1. 按 kid 精确获取签发时使用的那个密钥版本，
            //    即使该版本已因轮换降级为 DECRYPT_ONLY（仅解密/仅验签），依然能取到
            KmsKeyVersion signingKey = kmsKeyGateway.getSigningKeyByKid("sso_jwt_signing_key", kid);
            if (signingKey == null) {
                // 密钥版本已被彻底废弃（RETIRED），说明这是一个远超正常生命周期的 Token
                log.warn("Token 验证失败：签名密钥版本不存在或已废弃: kid={}", kid);
                throw new SigningKeyRetiredException("签名密钥版本已废弃: " + kid);
            }

            // 2. 验证签名
            String expectedSignature = computeHmacSignature(signingInput, signingKey.getKeyMaterial());
            if (!constantTimeEquals(expectedSignature, signature)) {
                log.warn("Token 验证失败：签名不匹配，疑似被篡改或伪造");
                throw new InvalidTokenException("签名校验失败");
            }

            // 3. 校验过期时间
            long exp = ((Number) payload.get("exp")).longValue();
            if (Instant.now().getEpochSecond() > exp) {
                throw new TokenExpiredException("Token 已过期");
            }

            // 4. 校验是否在黑名单中（用户主动登出、管理员强制下线等场景）
            String jti = (String) payload.get("jti");
            if (blacklistRepository.isBlacklisted(jti)) {
                log.warn("Token 验证失败：Token 已被加入黑名单: jti={}", jti);
                throw new TokenRevokedException("Token 已被撤销");
            }

            log.info("JWT 验证通过: kid={}, jti={}, sub={}", kid, jti, payload.get("sub"));

            return new JwtClaims(payload);
        } catch (InvalidTokenException | TokenExpiredException
                 | TokenRevokedException | SigningKeyRetiredException e) {
            // 这几类是"预期内"的验证失败，记录 warn 级别日志即可，不需要 error 告警
            auditLogger.log(AuditEvent.builder()
                .action("JWT_VERIFY")
                .keyName("sso_jwt_signing_key")
                .success(false)
                .failReason(e.getClass().getSimpleName())
                .build());
            throw e;
        } catch (Exception e) {
            log.error("JWT 验证发生未预期异常", e);
            throw new TokenVerifyException("Token 验证异常", e);
        }
    }

    /**
     * 撤销 Token（加入黑名单），幂等：重复撤销同一个 jti 不会报错也不会重复生效
     */
    public void revokeToken(String jti, Duration remainingTtl) {
        try {
            boolean added = blacklistRepository.addIfAbsent(jti, remainingTtl);
            if (added) {
                log.info("Token 已加入黑名单: jti={}", jti);
            } else {
                log.info("Token 已在黑名单中，忽略重复撤销请求: jti={}", jti);
            }
        } catch (Exception e) {
            log.error("Token 撤销失败: jti={}", jti, e);
            throw new TokenRevokeException("Token 撤销失败: " + jti, e);
        }
    }

    private String computeHmacSignature(String data, byte[] keyMaterial) throws GeneralSecurityException {
        Mac mac = Mac.getInstance(ALGORITHM);
        mac.init(new SecretKeySpec(keyMaterial, ALGORITHM));
        byte[] rawHmac = mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        return Base64.getUrlEncoder().withoutPadding().encodeToString(rawHmac);
    }

    /** 使用恒定时间比较，防止基于响应时间差异的签名猜测攻击（Timing Attack） */
    private boolean constantTimeEquals(String a, String b) {
        return MessageDigest.isEqual(
            a.getBytes(StandardCharsets.UTF_8),
            b.getBytes(StandardCharsets.UTF_8)
        );
    }

    private String base64UrlEncode(String content) {
        return Base64.getUrlEncoder().withoutPadding()
            .encodeToString(content.getBytes(StandardCharsets.UTF_8));
    }

    private String base64UrlDecode(String content) {
        return new String(Base64.getUrlDecoder().decode(content), StandardCharsets.UTF_8);
    }
}

/** JWT 中解析出的声明集合 */
```

```java
/**
 * 业务系统的鉴权过滤器：拦截请求，验证 JWT
 */
@Component
public class JwtAuthFilter extends OncePerRequestFilter {

    private static final Logger log = LoggerFactory.getLogger(JwtAuthFilter.class);

    private final JwtTokenService jwtTokenService;

    public JwtAuthFilter(JwtTokenService jwtTokenService) {
        this.jwtTokenService = jwtTokenService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                     FilterChain filterChain) throws ServletException, IOException {
        String authHeader = request.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            writeUnauthorized(response, "缺少 Authorization 头");
            return;
        }

        String token = authHeader.substring("Bearer ".length());
        try {
            JwtClaims claims = jwtTokenService.verifyToken(token);
            request.setAttribute("userId", claims.getSubject());
            filterChain.doFilter(request, response);
        } catch (TokenExpiredException e) {
            writeUnauthorized(response, "登录已过期，请重新登录");
        } catch (TokenRevokedException e) {
            writeUnauthorized(response, "登录状态已失效，请重新登录");
        } catch (InvalidTokenException | SigningKeyRetiredException e) {
            log.warn("非法 Token 访问: uri={}, reason={}", request.getRequestURI(), e.getMessage());
            writeUnauthorized(response, "无效的登录凭证");
        } catch (Exception e) {
            log.error("Token 验证过程发生异常: uri={}", request.getRequestURI(), e);
            writeUnauthorized(response, "认证服务异常，请稍后重试");
        }
    }

    private void writeUnauthorized(HttpServletResponse response, String message) throws IOException {
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":401,\"message\":\"" + message + "\"}");
    }
}
```

### 8.2 案例二：API 签名认证全链路

#### 8.2.1 场景描述

延续 5.2 节"微服务间调用"的场景，这里把 HMAC 签名认证的完整实现细化，重点补齐防重放攻击的机制：调用方使用 KMS 托管的共享密钥对请求签名，被调方用同一密钥验签；同时通过时间戳窗口和 Nonce（一次性随机数）去重，防止签名被截获后被重复提交（重放攻击）。

```
  API 签名认证全链路（含防重放）：

  ┌──────────┐               ┌──────────┐               ┌──────────┐
  │ 订单服务  │               │ 支付服务  │               │   KMS    │
  │ (调用方)  │               │ (被调方)  │               │          │
  └────┬─────┘               └────┬─────┘               └────┬─────┘
```

防重放攻击依赖两个要素共同起作用，缺一不可：**时间戳窗口**限制了签名的有效期（超过窗口，即使签名正确也拒绝），**Nonce 去重**则防止在有效期窗口内同一个请求被截获后重复提交。两者结合，才能既防止旧请求被长期重放，又防止窗口期内的重复提交。

```java
/**
 * API 签名生成器：调用方使用，基于 KMS 托管的共享密钥生成请求签名
 */
@Component
public class ApiSignatureGenerator {

    private static final Logger log = LoggerFactory.getLogger(ApiSignatureGenerator.class);

    private final KmsSecretGateway kmsSecretGateway;
    private final SecureRandom secureRandom = new SecureRandom();

    public ApiSignatureGenerator(KmsSecretGateway kmsSecretGateway) {
        this.kmsSecretGateway = kmsSecretGateway;
    }

    /**
     * 为一次请求生成签名所需的全部请求头
     *
     * @param appKey 调用方标识
     * @param secretName KMS 中托管的共享密钥名称
     * @param requestBody 请求体原始字节（需要与被调方校验时使用完全一致的序列化结果）
     */
    public Map<String, String> generateSignedHeaders(String appKey, String secretName, byte[] requestBody) {
        try {
            byte[] secret = kmsSecretGateway.getSecret(secretName);

            long timestamp = Instant.now().getEpochSecond();
            String nonce = generateNonce();

            String signStr = buildSignString(appKey, timestamp, nonce, requestBody);
            String signature = computeHmac(secret, signStr);

            Map<String, String> headers = new LinkedHashMap<>();
            headers.put("X-App-Key", appKey);
            headers.put("X-Timestamp", String.valueOf(timestamp));
            headers.put("X-Nonce", nonce);
            headers.put("X-Signature", signature);

            log.info("生成请求签名成功: appKey={}, nonce={}, timestamp={}", appKey, nonce, timestamp);

            return headers;
        } catch (KmsUnavailableException e) {
            log.error("生成请求签名失败：无法从 KMS 获取共享密钥: secretName={}", secretName, e);
            throw e;
        } catch (Exception e) {
            log.error("生成请求签名发生未预期异常: appKey={}", appKey, e);
            throw new SignatureGenerationException("签名生成失败", e);
        }
    }

    private String buildSignString(String appKey, long timestamp, String nonce, byte[] requestBody) {
        String bodyHash = DigestUtils.sha256Hex(requestBody);
        return appKey + "\n" + timestamp + "\n" + nonce + "\n" + bodyHash;
    }

    private String generateNonce() {
        byte[] randomBytes = new byte[16];
        secureRandom.nextBytes(randomBytes);
        return Hex.encodeHexString(randomBytes);
    }

    private String computeHmac(byte[] secret, String data) throws GeneralSecurityException {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(secret, "HmacSHA256"));
        byte[] rawHmac = mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        return Hex.encodeHexString(rawHmac);
    }
}

/**
 * API 签名验证器：被调方使用，校验请求签名合法性并防重放
 *
 * 幂等/防重放核心设计：
 * 1. 时间戳窗口校验——拒绝超出有效期的请求
 * 2. Nonce 去重——基于 Redis SETNX 语义，同一 Nonce 在窗口期内只能被消费一次，
 *    重复提交（无论是恶意重放还是网络重试导致的重复请求）都会在这一步被拦截
 */
@Component
public class ApiSignatureValidator {

    private static final Logger log = LoggerFactory.getLogger(ApiSignatureValidator.class);

    /** 允许的时间戳偏差窗口 */
    private static final long TIMESTAMP_WINDOW_SECONDS = 5 * 60;

    private final KmsSecretGateway kmsSecretGateway;
    private final RedisTemplate<String, String> redisTemplate;
    private final AuditLogger auditLogger;

    public ApiSignatureValidator(KmsSecretGateway kmsSecretGateway,
                                  RedisTemplate<String, String> redisTemplate,
                                  AuditLogger auditLogger) {
        this.kmsSecretGateway = kmsSecretGateway;
        this.redisTemplate = redisTemplate;
        this.auditLogger = auditLogger;
    }

    /**
     * 校验请求签名，任何一步不通过都抛出对应的异常，调用方应统一转换为 401/403 响应
     */
    public void validate(String appKey, String secretName, long timestamp, String nonce,
                          String signature, byte[] requestBody) {
        try {
            // 1. 校验时间戳窗口：防止很久之前截获的请求被重放
            long now = Instant.now().getEpochSecond();
            if (Math.abs(now - timestamp) > TIMESTAMP_WINDOW_SECONDS) {
                log.warn("签名校验失败：时间戳超出允许窗口: appKey={}, timestamp={}, now={}",
                         appKey, timestamp, now);
                recordFailAudit(appKey, "TIMESTAMP_EXPIRED");
                throw new SignatureExpiredException("请求已过期");
            }

            // 2. 校验并占用 Nonce：防止窗口期内同一请求被重复提交
            String nonceKey = "api:sign:nonce:" + appKey + ":" + nonce;
            Boolean firstUse = redisTemplate.opsForValue().setIfAbsent(
                nonceKey, "1", Duration.ofSeconds(TIMESTAMP_WINDOW_SECONDS + 60)
            );
            if (Boolean.FALSE.equals(firstUse)) {
                log.warn("签名校验失败：检测到重放请求，Nonce 已被使用: appKey={}, nonce={}",
                         appKey, nonce);
                recordFailAudit(appKey, "REPLAY_DETECTED");
                throw new ReplayAttackException("检测到重复请求，可能是重放攻击");
            }

            // 3. 从 KMS 获取共享密钥，重新计算签名并比较
            byte[] secret = kmsSecretGateway.getSecret(secretName);
            String signStr = buildSignString(appKey, timestamp, nonce, requestBody);
            String expected = computeHmac(secret, signStr);

            if (!constantTimeEquals(expected, signature)) {
                log.warn("签名校验失败：签名不匹配，疑似伪造请求: appKey={}", appKey);
                recordFailAudit(appKey, "SIGNATURE_MISMATCH");
                throw new InvalidSignatureException("签名校验失败");
            }

            log.info("API 签名校验通过: appKey={}, nonce={}", appKey, nonce);
        } catch (SignatureExpiredException | ReplayAttackException | InvalidSignatureException e) {
            throw e;
        } catch (KmsUnavailableException e) {
            log.error("签名校验失败：KMS 不可用，无法获取共享密钥: secretName={}", secretName, e);
            throw e;
        } catch (Exception e) {
            log.error("签名校验发生未预期异常: appKey={}", appKey, e);
            throw new SignatureVerificationException("签名校验异常", e);
        }
    }

    private void recordFailAudit(String appKey, String reason) {
        auditLogger.log(AuditEvent.builder()
            .action("API_SIGNATURE_VERIFY")
            .operatorApp(appKey)
            .success(false)
            .failReason(reason)
            .build());
    }

    private String buildSignString(String appKey, long timestamp, String nonce, byte[] requestBody) {
        String bodyHash = DigestUtils.sha256Hex(requestBody);
        return appKey + "\n" + timestamp + "\n" + nonce + "\n" + bodyHash;
    }

    private String computeHmac(byte[] secret, String data) throws GeneralSecurityException {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(secret, "HmacSHA256"));
        byte[] rawHmac = mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        return Hex.encodeHexString(rawHmac);
    }

    private boolean constantTimeEquals(String a, String b) {
        return MessageDigest.isEqual(
            a.getBytes(StandardCharsets.UTF_8),
            b.getBytes(StandardCharsets.UTF_8)
        );
    }
}

/** KMS 共享密钥（Secret）查询网关 */
public interface KmsSecretGateway {
    byte[] getSecret(String secretName);
}

    public SignatureGenerationException(String message, Throwable cause) { super(message, cause); }
}

    public SignatureVerificationException(String message, Throwable cause) { super(message, cause); }

}
```

```java
/**
 * 支付服务侧的签名校验拦截器
 */
@Component
public class ApiSignatureInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(ApiSignatureInterceptor.class);

    private final ApiSignatureValidator signatureValidator;

    public ApiSignatureInterceptor(ApiSignatureValidator signatureValidator) {
        this.signatureValidator = signatureValidator;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        String appKey = request.getHeader("X-App-Key");
        String timestampStr = request.getHeader("X-Timestamp");
        String nonce = request.getHeader("X-Nonce");
        String signature = request.getHeader("X-Signature");

        if (appKey == null || timestampStr == null || nonce == null || signature == null) {
            writeError(response, 400, "缺少必要的签名请求头");
            return false;
        }

        try {
            long timestamp = Long.parseLong(timestampStr);
            byte[] body = readRequestBody(request);
            String secretName = "auth_" + appKey + "_payment_secret";

            signatureValidator.validate(appKey, secretName, timestamp, nonce, signature, body);
            return true;
        } catch (NumberFormatException e) {
            writeError(response, 400, "时间戳格式非法");
            return false;
        } catch (SignatureExpiredException e) {
            writeError(response, 401, "请求已过期");
            return false;
        } catch (ReplayAttackException e) {
            log.error("检测到重放攻击，来源: appKey={}, ip={}", appKey, request.getRemoteAddr());
            writeError(response, 403, "检测到重复请求");
            return false;
        } catch (InvalidSignatureException e) {
            log.warn("签名非法，来源: appKey={}, ip={}", appKey, request.getRemoteAddr());
            writeError(response, 403, "签名校验失败");
            return false;
        } catch (Exception e) {
            log.error("签名拦截器处理异常: appKey={}", appKey, e);
            writeError(response, 500, "服务暂时不可用");
            return false;
        }
    }

    private byte[] readRequestBody(HttpServletRequest request) throws IOException {
        // 实际工程中通常配合可重复读取的请求包装类（ContentCachingRequestWrapper）实现，
        // 避免 InputStream 被读取一次后无法再被后续 Controller 消费
        return StreamUtils.copyToByteArray(request.getInputStream());
    }

    private void writeError(HttpServletResponse response, int status, String message) throws IOException {
        response.setStatus(status);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":" + status + ",\"message\":\"" + message + "\"}");
    }
}
```
