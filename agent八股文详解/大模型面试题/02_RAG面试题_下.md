## 问题11：请你介绍一下向量检索和关键词检索的区别？

面试官：请你介绍一下向量检索和关键词检索的区别？

我：向量检索就是用余弦相似度算向量距离，关键词检索就是 BM25 算法嘛，我觉得向量检索各方面都比关键词检索好，毕竟语义理解能力更强。

面试官：那你解释一下，用户搜「M4 Pro 芯片参数」，知识库里就写着「M4 Pro」，向量检索却召不回来，反而关键词检索秒找到，这是为什么？

面试官：换个模型就能解决精确词匹配的问题？你有没有想过这两种检索方式各自的天花板在哪？遇到同义词的时候关键词检索又是什么表现？

### 简要回答

关键词检索（BM25 这类）靠的是词频统计，看查询词在文档里出现了多少次，擅长精确命中；向量检索靠的是语义空间里的距离，能理解「换了种表达方式的同一个意思」，擅长模糊语义匹配。两者各有盲区：BM25 遇到同义词就没辙，向量检索遇到专有名词、产品型号这类精确词就容易漏。所以 RAG 系统里通常两路都跑，向量检索捕获语义相关的内容，BM25 精准命中关键词，再用 RRF 算法把两路结果合并，这样覆盖面比单路宽很多。

### 详细解析

#### 检索要解决的核心问题

检索的本质是：给你一段查询，从海量文档里找出最相关的那几条。这个「相关」可以有两种理解方式，一种是字面意义上的词汇重叠，一种是语义层面的意思接近。关键词检索和向量检索分别对应这两种理解，各有各的擅长和盲区。

#### 关键词检索：字面匹配，靠统计

关键词检索的代表是 BM25（Best Match 25），这是 Elasticsearch、Lucene 等传统搜索引擎的核心算法。它的基本思路是通过**倒排索引**记录「每个词出现在哪些文档里」，打分时核心看两个因素：**词频（TF）** 和 **稀缺度（IDF）**。

![](https://cdn.xiaolincoding.com//picgo/1776825482068-52fdbb31-ae60-4bca-bdee-1328778265ab.png)

![](https://cdn.xiaolincoding.com//picgo/1776851398242-e179f6e1-6948-486a-abc9-08fe9ec09d6d.png)

IDF 的作用是给常见词降权、给罕见词加权，让真正有区分力的词决定排序结果。BM25 在 TF-IDF 基础上又加了饱和度限制，防止某个词重复出现太多次后权重无限叠加。

BM25 的优势是对**精确词汇命中率极高**，但劣势是**遇到同义词就束手无策**。用户查「手机截图」，文档里写的是「iPhone 截屏教程」，BM25 看到没有任何词汇重叠，分数为零。

#### 向量检索：语义匹配，靠 Embedding

向量检索先用 Embedding 模型把每段文本转成高维数字向量，语义相近的文本坐标就靠近。「苹果手机怎么截图」和「iPhone 如何截屏」经过 Embedding 之后，向量的余弦相似度可以高达 0.95。

向量检索的优势是**语义理解能力强**，但劣势是**对精确词汇不敏感**，产品型号、人名、版本号这类词在 Embedding 空间里可能彼此距离并不近。两种方式的盲区恰好互补，谁也不能替代谁。

![](https://cdn.xiaolincoding.com//picgo/1776825627654-6310c739-d396-41ae-aef5-01f138ea051c.png)

#### 两者的核心区别对比

| 维度 | 关键词检索（BM25） | 向量检索 |
|------|--------------|--------|
| 匹配方式 | 词汇重叠统计 | 语义空间距离 |
| 索引结构 | 倒排索引（稀疏） | 向量库（稠密） |
| 同义词处理 | 无法处理 | 天然支持 |
| 精确词命中 | 极好 | 容易漏 |
| 计算方式 | 基于统计，可解释 | 黑盒，向量距离 |
| 适合场景 | 专有名词、代码、精确查询 | 语义问答、模糊表达 |

#### 混合检索：两路都跑，合并取长补短

工程实践中的标准做法叫**混合检索（Hybrid Search）**：同时跑向量检索和 BM25，各自召回一批候选，然后用 RRF（Reciprocal Rank Fusion，互倒排名融合）算法把两路结果合并排序。RRF 不看各路的原始分数，只看排名，用排名的倒数来打分。

![](https://cdn.xiaolincoding.com//picgo/1776825705859-d73e4557-d85f-4525-87ec-5a640860a30f.png)

两路检索可以**并行执行**，总延迟取两路中的最大值而不是两者相加，几乎没有额外的时间代价，但召回质量比单路明显更好。

### 面试总结

向量检索并不是「什么都比关键词检索好」，两者是互补关系。正确的做法不是二选一，而是混合检索，两路并行召回，用 RRF 融合排序，取长补短。

## 问题12：如何润色用户的 Query（Query Rewrite）？目的是什么？

面试官：RAG 系统里为什么要做 Query Rewrite？你了解哪些方法？

面试官：那用户问「这个功能怎么用」，知识库里写的是「XX 模块操作指南」，你光改写成书面语就能命中了？如果改写之后还是对不上呢？

面试官：蒙？你是说靠运气做检索优化？你有没有听说过 HyDE、Step-back Prompting 这些方法？它们各自解决什么问题你清楚吗？

### 简要回答

Query Rewrite 主要是为了弥补用户提问方式和知识库文档表述之间的语义鸿沟。方法主要有四种：第一是直接改写，让 LLM 把口语化的问题转成更精准的表述；第二是 Query 扩展，补充相关关键词；第三是 HyDE，让 LLM 先生成一个假设答案，然后用答案的向量去检索；第四是 Step-back Prompting，把具体问题往上抽象一层，检索更通用的背景知识。

### 详细解析

#### 为什么需要 Query Rewrite

用户和文档写作者之间有一道天然的表述鸿沟。用户可能这样问：「这东西坏了咋整」，而文档里写的是「产品故障排查与维修指南」。即便语义相关，向量相似度也可能低到召回不了正确文档。Query Rewrite 就是在检索之前先对用户的问题做加工，让它在向量空间里离正确文档更近。

![](https://cdn.xiaolincoding.com//picgo/1776825805308-db8dd766-72ed-44ef-9699-eedc7d84aa02.png)

#### 方法一：直接改写（Query Rewriting）

把口语化、模糊的问题改写成更精准、更书面化的检索表述。同时还可以补全上下文，处理代词指代。

![](https://cdn.xiaolincoding.com//picgo/1776825886765-2c5721ea-84f9-4ac5-85d1-e65ee8ffb2dc.png)

#### 方法二：HyDE（Hypothetical Document Embeddings）

先让 LLM 根据用户问题生成一段「假设性的答案」，再用这段假设答案的向量去检索文档。在向量空间里，答案到答案的距离比问题到答案的距离要近得多。假设答案的作用是充当一个向量上更好的「检索代理」。

![](https://cdn.xiaolincoding.com//picgo/1776825956495-f7d46fc4-72b2-47d5-b580-3a3705518ca4.png)

#### 方法三：Step-back Prompting（后退提问）

把具体问题「后退一步」，提升到更抽象的层次，先检索背景知识，再结合背景知识回答具体问题。比如：具体问题「Qdrant 的 HNSW ef 参数设多少合适」-> 后退问题「HNSW 索引的参数调优原则是什么」。

![](https://cdn.xiaolincoding.com//picgo/1776826053676-5c7605f0-72c7-4e2a-bfaf-45f711f655aa.png)

#### 方法四：多 Query 扩展

用 LLM 把用户原始问题改写成 3~5 个不同角度的版本，分别去检索，然后把所有结果合并去重。只要有一个改写版本和文档的表述对上了，就能把正确的内容召回来。

![](https://cdn.xiaolincoding.com//picgo/1776826169999-dabd9a4f-3d2f-47fb-8526-2281ffcb60e9.png)

| 方法 | 解决的核心问题 | 额外开销 | 适合场景 |
|------|-------------|---------|---------|
| 直接改写 | 口语化、指代不清、上下文丢失 | 1 次 LLM 调用 | 多轮对话场景 |
| HyDE | 问题和文档文体风格差异大 | 1 次 LLM 调用 | 专业知识库、文体差异明显 |
| Step-back | 具体问题需要背景知识辅助 | 1 次 LLM 调用 | 技术文档、需要原理支撑的场景 |
| 多 Query 扩展 | 单一角度覆盖不全 | N 次 LLM 调用 | 答案涉及多个维度的复杂问题 |

### 面试总结

Query Rewrite 的核心目的是弥合用户提问和文档表述之间的语义鸿沟。口语化表达用直接改写，文体差异用 HyDE，问题太具体用 Step-back，角度单一用多 Query 扩展。

## 问题13：什么是多路召回？具体怎么做？

面试官：你的 RAG 系统用的什么检索方式？

面试官：那用户搜「RTX 4090 显卡功耗」，你知识库里就写着「RTX 4090」，向量检索召不回来怎么办？

面试官：调大 top-K 召回一堆无关内容有什么用？你有没有想过问题的根源在于向量检索本身对精确词就不敏感？多路召回了解过吗？

### 简要回答

多路召回就是同时用多种不同的检索方式去捞候选内容，然后合并排序，而不是只靠单一的向量检索。核心出发点是向量检索和关键词检索各有盲区。常用的组合是向量检索加 BM25 混合检索，再加上多 Query 扩展。多路的结果用 RRF 算法融合，最后送进 Rerank 精排。

### 详细解析

#### 什么是多路召回？

多路召回就是同时用多种不同的检索方式去捞候选内容，最后再把各路结果合并、排序，交给 LLM 生成答案。没有任何一种检索方式是全能的，把它们组合起来互相补盲区，总召回质量才会比单路高。

常见的组合是三路：

![](https://cdn.xiaolincoding.com//picgo/1776826264785-4201982e-ea41-4322-8cb4-5d6f850e9665.png)

第一路是**向量检索**，负责语义层面的覆盖；第二路是**BM25 关键词检索**，负责精确词匹配；第三路是**多 Query 扩展**，把用户问题改写成多个不同角度的版本，覆盖更多表述差异。

#### 为什么单路召回不够用?

单纯依赖向量检索有一个明显的短板：**对精确词语的召回效果差**。向量检索「只看语义、不看字面」的固有局限，不管用哪个模型都存在。反过来，关键词检索（BM25）对同义词和不同表达方式无能为力。两种检索方式的盲区恰好互补。

![](https://cdn.xiaolincoding.com//picgo/1776826361507-0681f2c1-756d-48d5-9234-53f66c88efb4.png)

#### 第一路：向量检索（Dense Retrieval）

把文档和用户问题都用 Embedding 模型转成向量，然后用余弦相似度在向量库里找最近的 top-K 个 chunk。擅长语义匹配，但对精确词语效果不佳。

#### 第二路：BM25 关键词检索（Sparse Retrieval）

BM25 根据词频和文档频率给每个词打分，找出包含查询词最多、且这些词区分度高的文档。纯文本匹配，速度极快，对精确词语、数字、专有名词的召回效果非常好。

#### 第三路：多 Query 扩展召回

用 LLM 把用户的原始问题改写成 3~5 个不同角度的版本，分别去检索，然后把所有结果合并去重。在用户提问风格多变的场景下，召回覆盖率能提升 10%~20%。

![](https://cdn.xiaolincoding.com//picgo/1776826453586-21f9b1db-7f95-4224-96c9-70050555d593.png)

#### 结果融合：RRF 算法

三路召回各自拿回一批候选，用 RRF（Reciprocal Rank Fusion，倒数排名融合）把排名融合成一个统一的结果列表。RRF 只用排名而不用原始分数，巧妙地绕开了分数不可比的问题。

![](https://cdn.xiaolincoding.com//picgo/image-20260305142428378.png)

公式是 `score(chunk) = 求和(1 / (k + rank))`，其中 k 是平滑参数，通常取 60。RRF 不需要训练、计算量极小，工程落地成本很低。

![](https://cdn.xiaolincoding.com//picgo/1776826569766-fd69cf9e-11ae-4142-80cc-2ad7e5cb6f7b.png)

| 召回方式 | 擅长 | 短板 | 适合场景 |
|---------|------|------|---------|
| 向量检索 | 语义相似、同义词、不同表达 | 精确词语、数字、专有名词 | 通用语义检索 |
| BM25 关键词 | 精确词匹配、专有名词 | 同义词、语义相关但词不重叠 | 有大量精确词语的知识库 |
| 多 Query 扩展 | 覆盖不同表述角度 | 增加 LLM 调用开销 | 用户提问风格多变的场景 |

### 面试总结

多路召回的思路：既然没有任何一种检索方式是全能的，那就同时走多条路，向量检索管语义，BM25 管精确词，多 Query 扩展管表述差异，三路结果用 RRF 融合，互为补充。

## 问题14：RAG 检索优化策略有哪些？

面试官：RAG 系统的检索效果不好，你会从哪些方面优化？

面试官：光调参数就能解决所有问题？你有没有一个系统性的优化框架？索引层、查询层、召回层、重排序层，每一层解决什么问题你能讲清楚吗？

### 简要回答

RAG 的检索优化可以从四个层次来看：索引层决定知识怎么存，查询层决定问题怎么转换，召回层决定从哪些路径去找，重排序层决定最终哪些内容进入 prompt。先靠索引优化和多路召回来保证覆盖率，再用 Rerank 保证精度，如果用户提问质量比较差，再额外加上查询优化。

### 详细解析

#### 检索是 RAG 的命脉

LLM 只能根据送进去的 context 来回答，检索召回的内容就是整个系统的天花板。检索优化是投入产出比最高的环节。

#### 四层优化全貌

![](https://cdn.xiaolincoding.com//picgo/image-20260305143010121.png)

- **索引层**决定知识怎么「存」
- **查询层**决定问题怎么「转」
- **召回层**决定知识从哪里「找」
- **重排序层**决定候选里谁「最相关」

![](https://cdn.xiaolincoding.com//picgo/1776826697885-6a99316a-c21b-44e1-8f24-8135c302c31a.png)

#### 第一层：索引优化

索引优化聚焦于一个核心矛盾：**检索用的粒度和 LLM 读的粒度天然是矛盾的**。小 chunk 检索准但内容太碎，大 chunk 内容完整但检索时语义稀释。

![](https://cdn.xiaolincoding.com//picgo/image-20260306155147897.png)

![](https://cdn.xiaolincoding.com//picgo/1776826802336-9e3cafcc-60f7-4bb2-9521-7a49081cc17a.png)

解决这个矛盾的核心思路叫 Small-to-Big，也就是**小块检索、大块使用**：

![](https://cdn.xiaolincoding.com//picgo/1776826884231-9caf3b77-e859-4f66-8083-b75b876cb2ee.png)

- **Parent-Child Chunking**：细粒度子 chunk 建向量索引用于检索，命中后取出对应的粗粒度父 chunk 给 LLM 阅读
- **摘要索引**：用 LLM 为每段内容生成摘要建索引，命中后把原始段落给 LLM
- **多粒度分层索引**：同时建章节级、段落级、句子级三层索引，根据问题类型选择粒度

#### 第二层：查询优化

在检索之前对用户的 query 做加工，让它在向量空间里离正确文档更近。主要方法：Query 改写、多 Query 扩展、HyDE、Step-back Prompting。

![](https://cdn.xiaolincoding.com//picgo/1776827176880-0cb52aaa-ccd7-446a-92f0-57cc8cecdc92.png)

#### 第三层：召回优化

同时走多条检索路径，向量 + BM25 + 多 Query，用 RRF 融合。

![](https://cdn.xiaolincoding.com//picgo/image-20260305143414882.png)

#### 第四层：重排序

多路召回后候选 chunk 可能有 20~30 个，用 Cross-encoder Rerank 模型精排后取 Top-3~5 拼入 prompt。

![](https://cdn.xiaolincoding.com//picgo/1776827252260-f445096c-c929-47f7-8f6f-4e4c697b472d.png)

向量检索用 Bi-encoder（双塔独立编码，速度快但精度有限），Rerank 用 Cross-encoder（query+chunk 拼在一起整体打分，精度高但速度慢）。

![](https://cdn.xiaolincoding.com//picgo/1776827483387-b04880ae-bd5c-4202-a3a3-1396a80b471c.png)

#### 四层优化怎么组合

| 层次 | 解决的核心问题 | 推荐程度 |
|------|-------------|---------|
| 索引优化（Parent-Child） | 检索粒度 vs 上下文完整性的矛盾 | 推荐，效果稳定 |
| 查询优化（Multi-Query / HyDE） | 用户提问和知识库表达不对齐 | 视场景，提问质量差时必做 |
| 多路召回（向量 + BM25） | 单路检索漏召 | 推荐，低成本高收益 |
| Rerank 精排 | 粗召精度不足 | 强烈推荐，提升精度最直接的手段 |

典型生产级搭配：**Parent-Child 索引 + 向量 BM25 多路召回 + Rerank 精排**。

![](https://cdn.xiaolincoding.com//picgo/1776827717745-bf9fea4b-6b3b-4bcf-bb80-bdc7568c02d3.png)

### 面试总结

检索优化需要系统性的四层框架：索引层解决「知识怎么存」，查询层解决「问题怎么转」，召回层解决「从哪些路径找」，重排序层解决「最终谁最相关」。

## 问题15：什么是 Rerank（重排序）？为什么需要它？

面试官：你的 RAG 系统检索之后直接把结果给 LLM 了？

面试官：那如果 Top-10 里有 3 个是高度相关的，7 个是沾边但不太相关的，全塞进去会怎样？

面试官：LLM 的注意力是有限的，塞一堆无关内容进去，它很可能会被干扰，甚至「Lost in the Middle」。你知道 Rerank 是怎么解决这个问题的吗？

### 简要回答

Rerank 是在向量检索（粗排）之后加的一道精排步骤。向量检索用 Bi-encoder 把 query 和文档分别编码再算相似度，速度快但精度有限；Rerank 用 Cross-encoder 把 query 和每个候选 chunk 拼在一起整体打分，精度远高于向量检索，但速度慢，所以只适合对少量候选做精排。

整个流程是：向量检索召回 20~30 个候选，Rerank 精排后取 Top-3~5 个最相关的，再拼入 prompt 给 LLM。

### 详细解析

#### 为什么需要 Rerank？

向量检索返回的 Top-K 结果质量参差不齐。query 和 chunk 是**分别独立编码**的，模型在编码 chunk 时根本不知道 query 长什么样。向量相似度高不一定真的相关，需要一个更精细的打分器来判断「这个 chunk 是不是在回答这个 query」。

#### Bi-encoder vs Cross-encoder

**Bi-encoder（双塔模型）**：query 和 chunk 各自独立编码，互相看不到对方的内容。优点是 chunk 向量可以离线提前算好，速度极快；缺点是相关性判断粗糙。

**Cross-encoder（交叉编码器）**：把 `[query] + [SEP] + [chunk]` 拼成一个输入序列整体送入 Transformer，模型能看到词级别的语义交互，精度极高；缺点是每个候选都要单独跑一遍，速度慢。

#### Rerank 的工作流程

1. **粗排阶段**（向量检索）：从向量库中召回 20~30 个候选 chunk
2. **精排阶段**（Rerank）：Cross-encoder 逐一给每个 (query, chunk) 对打分
3. **截断**：按 Rerank 分数降序排列，取 Top-3~5 拼入 prompt

常用的开源 Rerank 模型有 BGE-Reranker-v2（BAAI 出品，中英双语效果好）、BCE-Reranker。API 服务有 Cohere Rerank 和 Jina Reranker。

### 面试总结

Rerank 的本质是用更精准的 Cross-encoder 结构对粗排结果做精排，解决「向量检索精度不够」和「LLM 上下文容量有限」的问题。关键是讲清楚 Bi-encoder 和 Cross-encoder 的区别，以及「先粗后精」的流程设计。

## 问题16：RAG 系统如何做评估（Evaluation）？

面试官：你说你做了 RAG 系统，效果怎么样？

面试官：「用户反馈挺好」不是评估。你怎么量化「好」？检索准不准，和生成准不准，是两回事吧？

### 简要回答

RAG 评估需要分两个维度：检索质量和生成质量。检索质量看的是「有没有找到正确的内容」，常用指标是召回率（Recall）和命中率（Hit Rate）；生成质量看的是「给了正确内容之后 LLM 有没有好好利用」，常用指标是忠实度（Faithfulness）和相关度（Answer Relevancy）。可以用 RAGAS 框架做自动化评估。

### 详细解析

#### 为什么要分开评估

RAG 是两阶段 pipeline：先检索再生成。如果最终答案不好，可能是检索没找到正确内容，也可能是找到了但 LLM 没正确利用。评估必须分层，才能定位问题。

#### 检索质量评估

- **召回率（Recall@K）**：Top-K 结果中，正确答案被包含的比例
- **命中率（Hit Rate@K）**：Top-K 结果中是否至少包含了一个正确答案
- **MRR（Mean Reciprocal Rank）**：第一个正确答案出现在第几位

#### 生成质量评估

- **忠实度（Faithfulness）**：LLM 的回答是否忠实于检索到的上下文，有没有编造信息
- **答案相关度（Answer Relevancy）**：LLM 的回答是否真正回答了用户的问题

#### RAGAS 评估框架

RAGAS 用「LLM 当评委」，定义四个核心指标：Context Precision、Context Recall、Faithfulness、Answer Relevancy，覆盖检索和生成两个环节。

#### 评估数据集构建

三种方法：人工标注（质量高成本高）、LLM 自动生成再人工审核（效率高）、线上日志挖掘（最贴近真实场景）。

### 面试总结

RAG 评估的核心是「分层量化」：检索层看召回率和命中率，生成层看忠实度和相关度。用 RAGAS 框架可以自动化评估。

## 问题17：RAG 和微调（Fine-tuning）怎么选？什么时候该用哪个？

面试官：你为什么选择用 RAG 而不是微调来做这个项目？

面试官：那如果你的场景需要模型学会一种特定的输出风格，或者需要处理某个专业领域的术语和推理模式，RAG 能搞定吗？

### 简要回答

RAG 解决的是「让模型获取它不知道的知识」，微调解决的是「让模型学会它不会的能力」。两者不是互斥的，很多生产系统是组合使用。

### 详细解析

#### 两者解决不同层面的问题

**RAG 作用在「输入层」**：通过外挂知识库，在推理时动态地把相关信息注入到 prompt 里。模型本身没变，类比开卷考试。

**微调作用在「参数层」**：通过训练修改模型的权重参数，让模型内化某种知识或能力。模型本身变了，类比闭卷考试前的复习。

如果问题出在「模型没看到需要的信息」用 RAG；如果问题出在「模型看到了信息但处理不好」用微调。

#### RAG 的适用场景

- **知识更新频繁**：只需更新知识库，不需重新训练
- **需要引用来源**：天然知道答案来自哪个文档
- **知识量大且长尾**：存在向量库里随时检索
- **对事实准确性要求高**：基于文档生成，可验证

#### 微调的适用场景

- **需要特定输出风格**：法律文书格式、医疗报告模板
- **需要领域推理能力**：医疗诊断、法律逻辑推理
- **需要理解专业术语的隐含关系**
- **输入输出格式固定**：实体抽取、关系抽取

#### 组合使用

先用微调让模型掌握领域能力（理解术语、输出风格），再用 RAG 在推理时注入最新的具体知识。

#### 决策对比

| 维度 | RAG | 微调 |
|------|-----|------|
| 解决的问题 | 模型不知道的知识 | 模型不会的能力 |
| 知识更新 | 更新知识库即可 | 需要重新训练 |
| 开发成本 | 低，不需要训练 | 高，需要标注数据和 GPU |
| 可解释性 | 高，可追溯来源 | 低，知识融化在参数里 |
| 幻觉风险 | 较低（基于文档） | 较高（可能编造） |
| 输出风格控制 | 弱 | 强 |
| 适合的知识量 | 大量、长尾 | 少量、核心 |

### 面试总结

RAG 和微调不是二选一，而是解决不同层面问题的工具。RAG 解决「知识获取」问题，微调解决「能力习得」问题。关键是不要说哪个更好，而是说看具体需求选合适的工具。

## 问题18：RAG 系统中如何处理多轮对话？

面试官：你的 RAG 系统支持多轮对话吗？

面试官：那用户第一轮问「RAG 是什么」，第二轮问「它和微调有什么区别」，这个「它」指的是什么？你直接拿「它和微调有什么区别」去检索，能找到正确内容吗？

### 简要回答

多轮对话的核心挑战是：用户后续的问题往往依赖前面的对话上下文，直接拿去检索会因为信息不完整而失败。解决方案是在检索前做一步「对话改写」（Conversational Query Rewriting），把当前问题和历史上下文合并成一个独立完整的问题，再拿这个完整问题去检索。

### 详细解析

#### 多轮对话为什么难

单轮对话直接拿问题去检索就行，但多轮对话中用户的问题往往不完整：

- **代词指代**：「它怎么用」「这个方法的缺点是什么」
- **省略主语**：「那性能呢？」
- **话题延续**：「还有别的方案吗？」

如果直接拿不完整的问题去检索，向量相似度会很低，导致召回不到正确内容。

#### 解决方案：对话改写

核心思路是在检索前加一步改写：把依赖上下文的问题转化成一个独立完整的问题。

示例：
- 历史：「用户：RAG 是什么？助手：RAG 是...」
- 当前问题：「它和微调有什么区别？」
- 改写后：「RAG 和微调（Fine-tuning）有什么区别？」

#### 对话历史管理

- **滑动窗口**：只保留最近 3~5 轮对话
- **摘要压缩**：对更长的对话让 LLM 压缩成摘要

#### 完整流程

1. 用户发来新问题
2. 把最近几轮对话历史 + 新问题发给 LLM 做对话改写
3. 拿改写后的独立问题去检索
4. 检索结果 + 对话历史 + 当前问题一起拼入 prompt
5. LLM 生成答案

### 面试总结

多轮对话的核心问题是「不完整的问题检索不到正确内容」，解决方案是在检索前加一步对话改写，把依赖上下文的问题转化为独立完整的问题。

## 问题19：GraphRAG 是什么？和普通 RAG 有什么区别？

面试官：你了解 GraphRAG 吗？

面试官：那你说说它和普通 RAG 的核心区别在哪？为什么有些场景下普通 RAG 效果不好，GraphRAG 能解决？

### 简要回答

普通 RAG 把文档切成独立的 chunk，每个 chunk 之间没有关联，检索时各找各的。这在回答「局部细节」问题时效果好，但在回答需要跨文档综合信息的「全局性」问题时效果差。

GraphRAG 的核心区别是：先从文档中提取实体和关系构建知识图谱，再基于图谱做检索。它能沿着实体之间的关系链路，把散落在不同文档里的相关信息串联起来，回答需要多跳推理的复杂问题。

### 详细解析

#### 普通 RAG 的局限

普通 RAG 把文档切成独立 chunk，检索时向量相似度只能找到和 query 最像的那几个 chunk，但找不到「虽然和 query 不直接相似，但通过关系链路相关」的内容。这就是普通 RAG 的根本局限：**无法处理需要多跳推理的问题**。

#### GraphRAG 的核心思路

第一步是**图谱构建**：用 LLM 从文档中提取实体和关系，构建知识图谱。

第二步是**图谱检索**：从问题中识别出关键实体，然后在图谱上沿着关系边进行遍历，找到所有通过关系链路相关的实体和文档片段。

#### 微软 GraphRAG 的实现

- **社区检测（Community Detection）**：把关系紧密的实体聚成「社区」，为每个社区生成摘要
- **分层摘要**：对社区做多层级摘要，根据问题抽象程度选择合适层级

#### GraphRAG vs 普通 RAG

| 维度 | 普通 RAG | GraphRAG |
|------|---------|----------|
| 知识组织 | 独立 chunk，无连接 | 实体-关系图谱 |
| 检索方式 | 向量相似度 | 图谱遍历 + 向量相似度 |
| 多跳推理 | 不支持 | 支持 |
| 全局性问题 | 效果差 | 效果好（社区摘要） |
| 构建成本 | 低 | 高（需要 LLM 提取实体关系） |
| 适合场景 | 局部细节问答 | 需要跨文档综合的复杂问题 |

#### 什么时候用 GraphRAG

适用场景：问题经常需要跨文档综合信息、实体间关系是回答关键、需要回答全局性问题、知识库有明确的实体关系结构。如果问题都是局部细节问题，普通 RAG 就够用。

### 面试总结

GraphRAG 的核心价值是解决普通 RAG 无法处理的「多跳推理」和「全局性问题」，通过构建知识图谱让散落在不同文档里的相关信息能通过关系链路被串联起来。

## 问题20：RAG 系统有哪些常见的失败模式（Failure Modes）？如何排查和解决？

面试官：你的 RAG 系统上线后遇到过什么问题？

面试官：「回答不准确」是个很笼统的描述。是检索没找到正确内容？还是找到了但 LLM 没利用好？还是文档本身就没有答案？你能系统地分析 RAG 的失败模式吗？

### 简要回答

RAG 系统的失败可以归纳为三大类：检索失败（该找到的没找到）、生成失败（找到了但没用好）、知识缺失（知识库里就没有答案）。排查时按 pipeline 顺序逐层定位。

### 详细解析

#### 失败模式一：检索失败

知识库里有正确答案，但检索没能把它召回来。常见原因：

- **表述不对齐**：用户问法和文档写法差距太大 -> 加 Query Rewrite 或多 Query 扩展
- **精确词漏召**：向量检索搞不定专有名词 -> 加 BM25 混合检索
- **chunk 切分不当**：正确答案被切到两个 chunk 里 -> 优化 Chunking 策略，加 overlap
- **Embedding 模型不适配** -> 换用更适合的模型（中文场景用 BGE 或 M3E）

#### 失败模式二：生成失败

检索已经召回了正确内容，但 LLM 没有正确利用。常见原因：

- **幻觉（Hallucination）**：LLM 自己编造信息 -> prompt 中明确指示「只根据上下文回答」
- **Lost in the Middle**：塞了太多 chunk，LLM 忽略中间内容 -> 加 Rerank，只送 3~5 个 chunk
- **答非所问**：LLM 从上下文提取了信息但回答的不是用户想问的 -> 优化 prompt

#### 失败模式三：知识缺失

知识库里就没有能回答这个问题的内容。解决方案：让系统能识别出「我不知道」，不强行编造答案；定期收集回答不了的问题补充到知识库。

#### 排查流程

1. **看检索结果**：召回的 chunk 里有没有正确答案？没有 -> 检索问题
2. **看 Rerank 结果**：正确答案在 Rerank 后还在 Top-K 里吗？排到后面了 -> Rerank 问题
3. **看 LLM 回答**：有没有忠实引用检索内容？编造了 -> 生成问题
4. **看知识库**：知识库里真的有答案吗？没有 -> 知识缺失

### 面试总结

RAG 系统的失败不是笼统的「不准确」，而是可以精确定位到具体环节。关键是建立「检索 -> Rerank -> 生成 -> 知识库」的分层排查意识。不要笼统地说「效果不好就调参」，而是展示系统性排查的能力。
